# MSW 新游戏规划模式 (msw-planning)

## 目的
当用户处于“我想制作一个类似这样的游戏”阶段时，将其转化为 **在 MSW 中构建什么 + 如何构建**：引导式会话产出 **GDD/路线图**，然后技能指导分阶段构建 — 详细阶段计划、进度跟踪和计划修订 — **直到每个里程碑的构建准备进入全面实施**。对于不知道游戏设计的人来说，只需跟随问题即可；对于了解游戏设计的人来说，可以快速记录决策。

## 核心原则（为什么这样工作）
- **目录基础**：MSW 是 2D · mLua（一种 Lua 扩展脚本语言）· 跨平台，因此“可以构建什么”的空间是有限的。将模糊的想法映射到 [`references/genre-catalog.md`](references/genre-catalog.md) 中的真实类型/地图类型/机制上，以获得一个 *可行的* 计划。仅从通用游戏知识出发进行规划会导致 MSW 无法实现的方案。
- **控制构建规模**：目录为每个类型提供 **构建工作量提示**（低 / 中 / 高）—— 这是一个信号，而不是一个判决（基准 1-5 个地图 · 10-20 个单位/物品 · 基础到中级 mLua；**塔防位于舒适单人模式的顶端**）。使用它来设定预期，而不是拒绝一个类型。根据 **构建工作量 + 范围（地图/内容）** 来确定第一个构建，而不是根据日历/开发时间估计 — 技能无法知道用户的技能水平或可用时间，因此不会承诺“这需要 N 天/周。” **当用户的雄心很大**（高工作量类型，或许多系统/地图，或“我想拥有所有东西”）时，不要一次性规划全部内容 — **将第一个构建的范围缩小到一个小型可玩核心（MVP）**，并将其余部分推迟到后续阶段。这适用于任何类型。
- **单次通过（无来回）+ 单向检查**：限制用户触点为 **步骤 1（批量问题）** 和 **步骤 3（方向检查）** — 不要在中间反复询问。但 **在编写 GDD 之前，永远不要跳过步骤 3（方向检查）**：不要只展示基础结果，直接跳到 GDD。一旦方向确定，立即产出可交付成果。
- **标准化可交付成果**：将结果放入固定的 GDD 结构 ([`references/gdd-template.md`](references/gdd-template.md)) 作为 Markdown，以便实施技能可以接手并将其带到 MVP。
- **“后续”的单一归宿**：GDD 仅涵盖其自身的里程碑。任何超出它的内容 — 切割功能、后续里程碑的想法、“让我们以后再做”的讨论中提出的请求 — 都是在其出现时 **记录在** 站立 **里程碑路线图** (`Docs/<游戏>-Roadmap.md`：一个未来里程碑的槽位，或当时间未知时为它的 Backlog），并且 **永远不会停放在 GDD 中**。一个归宿，无重复：路线图拥有当前里程碑之外的所有内容；GDD 拥有其内部内容。
- **推动项目进展**：在每次可交付成果后，**首先提出下一步**（例如，“我接下来写阶段 1 详细计划好吗？”）。如果用户同意，继续；如果他们说不，停止 — 这是一个建议，不是强迫。（这与无休止的文档中来回讨论不同 — 它连接了可交付成果之间的流程。）
- **决策门 = 可选选择，非自由文本**：在每个用户决策门 — **步骤 3 方向检查**、**阶段交接**（立即实施 vs 写下一个阶段的计划）和 **软阶段门** — 通过代理的多选 UI（例如，Claude Code 的 `AskUserQuestion`）以 **结构化可选选择** 的形式呈现选项，以便用户点击选项而不是输入自由文本回复。标记推荐选项但不要强迫；如果代理没有这样的 UI，则回退到清晰的枚举文本选择。

## 启动时 — 检查现有 GDD（恢复 / 新建 / 阻止）
构建跨越多个会话和 **里程碑 — 每个里程碑是一个 GDD**。存放位置（所有项目根目录，RootDesk 外部，以幸存 `refresh_workspace`）：
- **活动** GDD + 阶段计划 → `Docs/`.
- **`Docs/<游戏>-Roadmap.md`** → 游戏的 **站立里程碑路线图**（愿景 · 发布标准 · 每个里程碑一个槽位 · Backlog）：跨里程碑方向，与 M1 GDD 一起创建，永久（永远不会存档）。它 **不是** GDD — 活动里程碑的合同保留在其 `-M<n>-GDD.md` 中。
- **已完成** GDD → `Archive/`（里程碑完成后）。
- **`Archive/As-built.md`** → 世界运行实施记录：由技能维护的当前状态地图，一个 **AI / 交接参考，不是面向用户的规划文档**（由 [`references/build-management.md`](references/build-management.md) 清理维护；通过 *Brownfield* 下方种子）。

**在运行以下流程之前，检测计划文件** — 检查 **`Docs/` 和 `Archive/`** 中是否存在 `<游戏>-M<n>-GDD.md`：
- **列出这些目录的完整内容**（大写 `Docs/` / `Archive/`）— 一个目录级列表，返回其中 *所有* 内容（例如，代理的文件列表器 / `Glob` with `Docs/*`）— 然后 **你自己从该列表中** 匹配以 `-GDD.md` / `-Phase<N>.md` 结尾的名称。**不要** 通过狭义的模式或内容搜索检测（`*-GDD.md` glob 或 grep 案敏 + 范围脆弱：`*.md` 仅限顶层，`docs/` ≠ `Docs/` — 漏读会静默地读取为“无 GDD”），也不要从内存中检测。
- 仅从 **真正空的 `Docs/` + `Archive/` 列表** 中得出 **“任何地方都没有 GDD”** 的结论。
- 如果 **`Archive/As-built.md`** 存在，**首先读取它** 以获取当前状态地图；如果 **`Docs/<游戏>-Roadmap.md`** 存在，**与它一起读取** 以获取跨里程碑方向（**永远不会**将其误认为活动 GDD）。
- 通常最多只有一个活动 GDD；**如果存在多个，首先询问这是关于哪个游戏**，然后应用以下规则。

**门控规则 — 只有当 `Docs/` 或 `Archive/` 中存在计划时，“继续” / “下一个任务” / 恢复请求才会生效**（一个 `<游戏>-M<n>-GDD.md` / `<游戏>-M<n>-Phase<k>.md`，或先前的里程碑 + `Archive/As-built.md`）。如果 **两者中都没有** 存在，则必须 **不** 将请求视为恢复，并且必须 **不** 自动启动步骤 1 问卷 — 相反：如果请求是 **继续 / “下一步”意图**，或用户表示他们正在基于自己的现有工作构建（**不是** 从空白模板开始），则转到 *Brownfield* 下方；否则（新游戏或意图不明确）告诉用户没有保存的计划，并询问是否要开始新游戏（然后是 STEP 1）。**不要** 从工作区文件中推断 Brownfield — 模板附带示例，因此非空工作区不是先前工作的证据。

**如果存在 GDD，根据 GDD / 阶段文档任务状态 (`⬜/🟡/✅`) 判断实际完成多少 — **不是** 从工作区文件判断**（模板附带 `.mlua`/`.model`/`.ui`，因此文件存在不是可靠的进度信号）。然后分支：

- **用户明确要求继续/恢复** → **恢复**（以下步骤），无论状态如何。
- **每个路线图 & 阶段项目都是 `⬜`**（一个零进度的计划）**并且它是游戏的第一个里程碑** — 没有相同 `<游戏>` 的 GDD 在 `Archive/` 中 **并且** GDD 的编号是 `M1`。（在提供之前检查这一点：一个存档的先前的里程碑，或当前 GDD 上的 `M2+` 编号本身就证明了这个世界已经包含构建的工作 — 零进度计划仅仅是 *它之上* → 那是以下 `🟡/✅` 案例中，**不是** 这个案例。）→ 提供一个 **可选选择**（见核心原则）：**① 继续此计划 (*[游戏]*)** / **② 放弃它并规划一个新游戏**。如果他们选择放弃，**首先明确哪些文件将被删除** — `Docs/<游戏>-M<n>-GDD.md`，该游戏的 `Docs/<游戏>-M<n>-Phase<k>.md`，**以及该游戏的 `Docs/<游戏>-Roadmap.md`**（它是与 M1 GDD 一起创建的，因此它随它一起被删除 — 留下它会将已删除游戏的方

### 第一步 — 引导性问题（批量处理）
不要重复用户已经提供的内容；仅批量处理缺失部分：
1. **类型/参考** — 感觉如何？有类似的游戏吗？（如有不确定，从“你想获得什么样的乐趣？”开始）
2. **核心乐趣/核心循环** — 你在一个会话中重复什么？（例如，击杀敌人 → 成长 → 更强的敌人）
3. **目标 · 平台** — PC/移动设备？单人/多人？
4. **范围（首次构建）** — 快速原型还是更复杂的项目？大约有多少地图/多少内容？
5. **必须包含项/可删减项**

批量处理成约5个问题。如果用户说“你决定”，则使用合理的默认值继续，但**必须说明假设**。

### 第二步 — 目录基础性检查+可行性验证
阅读 [`references/genre-catalog.md`](references/genre-catalog.md) 并：
- 找到与用户想法**最接近的类型**。
- 拉取该类型的**推荐地图类型**和**核心机制标签**。
- 拉取该类型的**`MVP:` 切片提示**（最小的可玩切片 — 用于范围缩小后的首次构建和第四步的第一阶段）以及**`Growth:` 轴**（完成的核心通常会添加的内容 — 用于后续阶段和未来里程碑）。根据用户想法进行调整；它们是提示，不是固定规格。
- **阅读 `build-effort` 提示**（低/中/高）并评估用户的雄心。如果它是高工作量或用户一次性要求太多，请明确说明，并**建议范围缩小后的首次构建**（一个地图 · 仅核心循环 — 从类型的 `MVP:` 提示开始），保持相同的乐趣，其余部分放到后续阶段或里程碑路线图中 — 无论类型如何。
- 如有需要，挑选并组合机制标签，形成一句话概念。

### 第三步 — 方向检查（用户确认关卡） ⚑ 不可跳过
**在编写 GDD 之前，始终通过用户确认方向。** 简要展示基础结果，**不要直接跳转到 GDD** — 类型 和 地图类型决定整个堆栈，所以如果你在一个错误的选择上编写整个 GDD，你必须重做所有内容。

**简要展示并询问用户**：
- **推荐方向**：匹配的*子类型*（1-2 个候选）+ **推荐地图类型 ↔ 身体**（例如，RectTile + `KinematicbodyComponent`）+ **build-effort 提示（低/中/高）** + **一句话概念**。
- 如果是高工作量或用户范围过大，展示**范围缩小后的首次构建（MVP）选项** — 同样的乐趣在一个较小的首次切片中，其余部分路由到后续阶段/里程碑路线图。
- 然后询问，展示选项**作为可选择的选项**（见核心原则）：**“我是否按这个方向构建 GDD？还是有其他候选/变更？”**
- **只有在用户确认（或选择）后** 才进入第四步。（如果他们明确说“你决定”，锁定推荐，但用一句话说明你选择了什么。）
- 地图类型 ↔ 身体在此处确定 ([`references/msw-mapping.md`](references/msw-mapping.md))。如果选择错误会导致“无法移动”/`[LEA-3004]` 实施中的静默失败。它是在设置时应用的，通过**在已经具有此类型的地图中构建**（例如，每个类型保留一个 TileMap / RectTile / SideView 模板）；否则用户在 Maker 中设置它。AI 从不自己切换地图的类型（见第五步）。

### 第四步 — 生成 GDD/路线图
**在用户在第三步确认的方向中**，使用 [`references/gdd-template.md`](references/gdd-template.md) 结构编写 markdown：
**一句话概念/关键决策表/核心循环/核心系统/系统↔MSW 映射/阶段路线图检查清单/里程碑范围决策。**
- 对于系统↔MSW 映射，使用 [`references/msw-mapping.md`](references/msw-mapping.md) 将每个系统连接到 `@Logic`/`@Component`/.model/.ui/数据集（UserDataSet）。
- 将路线图分成阶段，**从最小的可玩构建（第一阶段）开始**，例如“移动、击中并破坏。”匹配类型的 `MVP:` 提示（第二步）是第一阶段的自然种子；其 `Growth:` 轴建议后续阶段。使用三个状态跟踪每个路线图项 — `⬜ 未开始` / `🟡 已实现（未测试）` / `✅ 已测试`（全部从 `⬜` 开始；状态规则 → [`references/build-management.md`](references/build-management.md)）。
- **路线图检查清单仅包含*手交就绪原型所需*的项 — 并且所有项都必须达到 `✅`。** 精炼/锦上添花/后续工作放到**里程碑路线图**（`Docs/<game>-Roadmap.md` — 一个未来里程碑槽，或其 Backlog）**在规划时**，永远不会作为检查清单项，也永远不会放在 GDD 中的任何地方（见*单一归属“后续”*）。区分标准：*移除它会让完整实现团队的基础更不完整？* → 所需（检查清单）；*生产会精炼它？* → 里程碑路线图。
- 对于数据密集型游戏，在路线图中声明“数据驱动（UserDataSet/CSV 是事实来源）”。早期阶段可能为速度硬编码值，但一旦值集增长或稳定，**计划硬编码→数据集（UserDataSet/CSV）迁移**：在此里程碑内 → GDD §6 中的后续阶段任务；超出它 → 一个**里程碑路线图条目**（槽或 Backlog；§7 仅保留一个指针 — 仅在 GDD 文本中写入的意图会被埋没时 GDD 存档）— 这样平衡/内容不再需要代码编辑。仅在**有充分理由**时包含此内容（许多可调值 · 平衡迭代预期 · 内容扩展），而不是少量常量。数据集本身通过 `msw-general` 编写（见其 `references/dataset.md`）。
- **保存 GDD 前进行覆盖检查**：§6 阶段必须*共同交付* §1 一句话概念（以及，对于 M2+，被提升的路线图槽行）— 追踪这些行声称的功能到将实现它的检查清单项。没有项的声明是规划中的漏洞，后续规则无法捕获（未规划的任務不会留下 `⬜`）。**验证限制不会缩小范围**：AI 无法单独验证的流程（真实多人匹配、设备上感觉、商业）仍然按任务规划 — 它们将简单地结束 `🟡 需要用户测试` — 永远不会因为无法自动验证而静默遗漏。如果用户同意排除声明的功能，请重写 §1 / 路线图槽，以便文档停止承诺它。
- **如果项目发布占位符/样本实体**：包括一个任务，在原型交给完整实现之前**删除它们**，以免它们带入真实构建。**范围 = 整个项目，而不仅仅是选定的构建地图** — **任何**项目中的地图都可能携带其自己的样本（模板派生的地图经常这样做；一些不发布任何样本），因此任务的完成标准是“**检查并清理所有地图**”：首先**枚举所有地图**（完整的 `map/` 列表），然后检查每个；一个地图扫描干净不是其他证据。**不要假设固定名称 — 通过检查识别每个地图的样本**（通常是 `*Template`-命名的空闲/移动/追逐怪物样本，但名称因模板而异）。它们在早期作为 AI 模式参考很有用；实际删除在实施期间通过 MapBuilder 从 `.map` 中删除它们。**未使用的模板地图也是手交残留**：在手交时，**询问用户是否删除或保留**游戏未使用的每个模板地图（永远不会删除未经确认的）— 并在样本清理之前决定；然后“所有地图干净”适用于剩余的地图。

### 第五步 — 保存 + 下一步
- 将生成的 markdown 保存到**项目根目录 `Docs/`** 下，作为 **`Docs/<game>-M<n>-GDD.md`** — **`<game>`** 是一个简短的 ASCII（英文/罗马化）缩写（**永远不会是原始非英文标题**；CJK/非 ASCII 文件名会破坏 globbing 和跨平台路径 — 例如 `MapleIdle-M1-GDD.md`，而不是原始 CJK 标题）并且 **`<n>` 是里程碑编号**。**里程碑编号**：第一个里程碑是 **M1**；后续里程碑取 `Docs/` 中 `Archive/` 的**数值最高的现有 `-M<n>-GDD.md` + 1** — *解析数字，不要按字母顺序排序*（所以 M9 → M10，不是 M2）。文档的**内容保持在用户的语言**；只有*文件名*是 ASCII。阶段文档继承相同的 **`<game>-M<n>-` 前缀**（第六步）。在此处收集所有规划交付物（GDD · 阶段详细计划）。如果缺失则创建文件夹。作为文件保留，实施技能可以接手并将其带到 MVP。
- ⚠️ **不要保存到 `RootDesk/` 下。** Maker 的 `refresh_workspace` 清理（删除）`RootDesk/` 下的非 MSW 文件（.md 等），所以当实施/测试期间运行刷新时，这些文件**会消失**。始终将它们保留在 RootDesk 外面（项目根目录 `Docs/`）。
- **与 M1 GDD 一起创建里程碑路线图** — `Docs/<game>-Roadmap.md`（名称中无 `M<n>`；每个游戏一个；永久，永远不会存档）。遵循 **'里程碑路线图模板'** 在 [`references/gdd-template.md`](references/gdd-template.md) 中：一句话 **愿景** + **发布标准**（什么必须为游戏可发布 — 标准，不是功能清单），**每个里程碑一个槽**（M1 = 指向活动的 GDD；未来的 M's = 一句话主题 + 指定的功能），以及一个 **Backlog** 用于想要但未分配的项。**将 STEP 2–3 从首次构建中裁剪掉的所有内容**（Growth 轴 · 修剪功能 · 用户的“后续”愿望）放入未来槽或 Backlog。**根据游戏进行扩展**：单里程碑游戏的路线图只有几行（M1 = 发布）。对于后续里程碑（M2+），不要重新创建 — **更新**现有的路线图（提升该槽）。
- **当基础 GDD 完成时，自然地首先提议**：“我是否接下来编写 **第一阶段详细计划**？” → 如果用户同意，直接进入第六步。
- 其他分支建议：如果数字/数据密集型，转到数据集设计；如果屏幕密集型，使用 `msw-ui-system` 编写 UI；要立即构建，使用 `msw-general`·`msw-scripting` 开始实施。默认推荐流程是“详细第一阶段 → 实施。”
- **应用地图类型 — 如果存在匹配的地图则构建在其中，否则用户设置它**：原型必须构建在 `TileMapMode` 已经等于决定类型的地图中。在设置时，检查现有地图的 `MapBuilder.read().getTileMapMode()`，然后：
  - **如果地图已经匹配** — 例如，项目保留**每个地图类型的模板地图**（每个 TileMap / RectTile / SideView 一个）— **在地图中构建原型**，无需切换（破坏性切换被避免）。*此快捷方式仅当存在匹配的地图/模板时适用。*
  - **如果地图不匹配** — 没有按类型模板，或从头开始 — 回退到标准策略：**用户在 Maker 中切换地图的类型**（msw-general `tile.md`；AI 随后使用 `getTileMapMode()` 验证）。
  - **无论如何，AI 从不自己切换地图的 `TileMapMode`。**（如果构建在模板中，其样本 `*Template` 实体将根据清理规则稍后删除。）
  - **在模板时尽早重命名构建地图**：如果原型将存在于一个 `*Template`-命名的地图中，计划一个**第一阶段任务，在真实构建开始之前将其重命名为游戏合适的 ASCII 名称** — 地图引用（区域注册 · 门户 · `GetEntityByPath` 路径 · 活动地图）随着阶段的进展而累积，所以第一阶段重命名几乎免费，在交接时昂贵；并且一个生活在 `*Template`-命名地图中的游戏会污染模板与游戏分类，这个技能本身也依赖于此分类。完成标准：文件重命名 + 每个引用更新 + 刷新 + 条目验证。机制属于实施技能；**如果引用存在于只读配置（`Global/`）中，那部分是用户的 Maker 操作** — 与 `TileMapMode` 切换相同的策略。
  - **在构建之前将活动地图切换到目标地图**（一旦通过上述任一情况固定）：使用 `maker_move_map`（AI 可完成）将 Maker 的**活动（打开）地图**移动到它，以便实体/瓦片编辑和截图落在正确的地图上。（这**不是**禁止的 `TileMapMode` 切换。）不要沉默跳过 — 否则工作目标针对的是错误的地图。

### 第六步 — （可选）按阶段详细计划
基础输出（第四步）高达*完整路线图 + 每个阶段的检查清单*。如果用户想要特定阶段的详细计划（例如，“编写第一阶段详细计划”，“分解阶段 1”），生成一个额外的**详细计划 markdown**，更深入地扩展该阶段的检查清单项。
- 对于每个任务，编写：**目标 · 所需系统/组件**（`references/msw-mapping.md`）**· 数据（UserDataSet）· UI · 完成（验证）标准 · 依赖项 · 要参考的技能（预测 — 技能及其参考文档，`references/msw-mapping.md` §4）。** 还在阶段文档顶部记录，**“本阶段要参考的技能”** 摘要 — 实施会首先阅读它。
- **生成一个状态检查清单**与任务一起 — 每个项目从**未开始**开始，随着工作进展通过三个状态：
  - `⬜ 未开始` — 尚未实现。
  - `🟡 已实现（未测试）` — 实现完成，尚未验证。
  - `✅ 已测试` — 实现和验证都完成。
- 遵循 **'按阶段详细计划模板'** 在 [`references/gdd-template.md`](references/gdd-template.md) 中。
- 保存：`Docs/<game>-M<n>-Phase<k>.md`（相同的 **`<game>-M<n>-` 前缀**作为里程碑的 GDD — 见第五步；`<k>` = 阶段编号；项目根目录 `Docs/`，**在 RootDesk 外面** — 避免刷新删除）。
- 这也仅限于*详细规划* — 编写实际代码（.mlua/.model 等）仍然是实施技能（msw-general/msw-scripting 等）的工作；这些技能在实施和验证时更新检查清单状态。

#### 构建管理（实施时间规则）→ [`references/build-management.md`](references/build-management.md)
执行计划的完整规则 — 任务状态处理、阶段/里程碑完成程序和开发中计划修订 — 存在于 **[`references/build-management.md`](references/build-management.md)** 中。在实施计划任务、更新任何检查清单状态、完成阶段或里程碑、或应用计划修订**之前**完整阅读它。**硬性门槛：如果你即将编辑任何 `⬜/🟡/✅` 标记、运行阶段/里程碑完成、或存档/删除计划文档，并且在本会话中**未完整阅读 [`references/build-management.md`](references/build-management.md)** — 停止并首先阅读它。加载此 SKILL.md（或在本会话中在早期会话中阅读了参考）不能替代。不可协商的不变量，在此重申，因为打破它们会破坏记录：
- 状态**仅是 `⬜` / `🟡` / `✅`**，立即在阶段文档**根据任务更新** — 永远不会批量到最后，永远不会仅在瞬态工具中，永远不会使用虚构的标记。
- **阶段完成和里程碑完成每个都有一个强制清理程序**（[Completed-stage](references/build-management.md#completed-stage-cleanup-mandatory) · [Milestone-complete](references/build-management.md#milestone-complete-cleanup-mandatory)：将状态镜像到 GDD §6 → As-built → 路线图 → 删除/存档）。永远不要在没有运行它的情况下删除阶段文档或存档 GDD。**完成是针对里程碑声明的愿景，而不仅仅是检查清单** — 里程碑完成程序从愿景覆盖检查开始，并且一个剩余项都等待用户测试的里程碑是 **`⏳ 用户测试待定`**，永远不会“完成”和永远不会是自我发明的标签。
- **计划变更请求通过那里的修订流程路由**；当前里程碑之外的工作直接进入里程碑路线图 — 并且一个有意占位符/阻塞的代码路径必须在写入时获得一个跟踪项。

## 边界（本技能不做什么）
- 它不编写实际的代码（.mlua/.model/.map/.ui）——那是实现类技能的工作。本技能**规划并管理游戏在其各个里程碑中的构建**（GDD · 里程碑路线图 · 详细阶段计划 · 进度跟踪 · 计划修订），并将代码工作移交给 msw-general/msw-scripting 等技能。
- 对已构建并发布的现有世界进行重大改进或扩展不在范围内（本技能规划的是游戏的构建——一个新游戏及其后续里程碑——直至为全面实施做好准备）。
- 在计划中体现 MSW 平台规则（地图类型↔Body、1 个单位 = 100px、SpriteRUID 等），但具体实施规则请遵循 msw-general 的平台参考文档。
