## 此技能的作用

运行结构化探索，权衡选项，并在 `docs/specs/` 中编写或更新构建规范。主线程写入；它只将读取代码库或从网络获取的任务卸载给一个廉价的子代理（见 *子代理*）。四种模式：

| 模式 | 何时 | 设计行为 |
|---|---|---|
| `FEATURE` | 从零开始设计一个新功能，无论是否有现有代码 | 基于原理的设计，最佳实践，最小化代码阅读 |
| `ARCHITECTURE` | 为新项目选择技术堆栈或基础架构 | 全面评估堆栈，行业模式，不读取代码 |
| `ENHANCEMENT` | 改进、替换或扩展现有内容 | 读取现有代码 + 规范，专注选项比较 |
| `CROSS-CUTTING` | 在整个代码库中标准化模式（错误处理、日志记录、认证、命名） | 样本当前状态，精确定义标准，建议执行 |

- **创建**：新决策 → 新规范，状态为 `Proposed`
- **更新**：改进现有决策 → 就地编辑现有规范
- **取代**：替换过去的决策 → 新规范 + 更新旧规范的状态行
- **批准**：审议 `/develop` 记录的 `Assumed` 规范，当工程师选择在决定之前构建时 → 见 *批准一个假设的决策* 下面

规范状态有两种行为，由一个可构建的范围功能是否链接规范决定（一个 `docs/scope/` 行，其 `spec` 单元指向它）：

- **功能链接规范**（典型的 FEATURE/ENHANCEMENT，或一个具有范围行的 ARCHITECTURE 基础）：状态镜像功能生命周期。/architect 创建它为 `Proposed` 并拥有其内容，但从不推进状态；/develop 在功能进入进行中时将其推进到 `In Progress`，然后在构建并验证（范围 `done`）时推进到 `Accepted`。工程师确认仅批准内容；`Accepted` 表示已发布。
- **独立决策规范**（基础/堆栈或跨切标准，没有范围行链接它）：决策状态。`Proposed` 时编写，`Accepted` 一次工程师在确认上批准它时（决策然后生效）。/develop 不推进它。

记录已发布工作的规范（“已构建”路径，或已链接的功能已为 `existing`）出生为 `Accepted`。

**`Assumed` 状态。** `/develop` 可能在工程师选择在决定之前构建时创建状态为 `Assumed` 的规范。它记录构建使用的假设，而不是一个审议的决策。功能仍然可以标记为 `done`；`Assumed` 规范保持标记为需要批准，并且不会阻止它。只有 `/architect` 通过批准（下面）清除 `Assumed` 状态。/architect 从不创建 `Assumed` 规范；它只审议一个已存在的规范。

不写代码。从不更新 `AGENTS.md`/`CLAUDE.md` (/sync 拥有这些）。

## 子代理（主线程写入；子代理只读取、获取或交叉检查）

主线程运行对话并写入规范；它从不将编写或任何修复交给子代理。它生成的每个子代理都是只读的，并且永远不会继承会话模型：

- **读取代码库**（最便宜的模型，Claude Code `haiku`）：当存储库很大时（ENHANCEMENT/CROSS-CUTTING）对现有代码的只读扫描。Claude Code：`scout` 类型。返回紧凑的映射，从不文件转储。
- **从网络获取**（最便宜的模型，Claude Code `haiku`）：当前工具景观检查和 Agent Skill / MCP 发现，都在设计对话（阶段 c）期间，当需要当前事实时。Claude Code：`researcher` 类型。返回紧凑的摘要，从不原始页面。
- **交叉检查草拟的规范**（它的主要工作是决策完整性：找到规范未命名的行为必须产生的值源，以及构建者会否则发明的决策）：一个只读传递，读取完成的规范并返回评论，不写入任何内容。/architect **总是询问**是否运行它（从不代表工程师运行或跳过它），强烈建议 `Another model` 在 `GA`/`Beta`（这些错误存在的层）中，在 `Alpha` 中提供它，并在 `Prototype` 中建议 `Skip`；它发现的任何差距都向工程师展示推荐的修复方案，供他们决定，而不是自动解决。见 *规范编写后*。

网络获取只发生一次，当决策需要它时（阶段 (c) 景观和工具发现检查）。它返回的链接进入规范的参考文献，供人类跟随；人工智能永远不会再次获取它们（在交叉检查、/develop 或 /audit 中）。

## 询问与行动

在编写规范之前（以及在任何时候生成读取/获取辅助工具之前）提出有针对性的问题；将预算用于实质内容。对每个问题进行分类：

- **INFER**：提示或代码库揭示的任何内容（功能与架构、堆栈、范围内的 UI、已选择的提供者）。推导，不要询问。
- **ASK**：只有工程师单独知道的内容（需求、偏好、业务规则、合规范围）。
- **RECOMMEND**：任何由专业知识确定的（哪个提供者/库/模式适合）。声明选择，一句为什么，以及备选方案；他们可以覆盖。从不提供中性菜单，从不沉默决定。

不要将完整的数据模型、完整堆栈或现成的验收标准集捆绑到一个接受或更改面板中，并且不要为他们默默地决定工具、提供者或设置选择。

建议与当前使用的堆栈一致（在 BaaS 上，优先考虑其认证/存储而不是新的外部工具；重用优于蔓延）。无论是网络还是移动：推断平台，永远不要假设网络。

这就是意图，不是程序。如何运行提问过程生活在 `internal/design-conversation.md` 中，执行下面会让你在问一个设计问题之前完整阅读。

## 物品所有权

此技能仅创建或更新的 `docs/specs/` 中的规范文件，以及它产生的任何支持证据（清单、审计），这些证据生活在规范的 `rationale.md`（目录规范）或内联（单个文件规范），永远不会在范围文件夹中（`docs/scope/` 由 `/scope` 拥有，而不是规范）。

两个独立选择，位置（存储库形状）和形状（决策大小）：

- **位置 = 存储库形状。** 单个存储库 → `docs/specs/`。单一代码库 → `docs/specs/<workspace>/` 用于工作空间决策，`docs/specs/_root/` 用于整个存储库的决策（镜像范围）。编号是按位置（扫描该目录以查找下一个 `NNNN`）。将解析位置称为 `$SPEC_DIR`。
- **形状 = 决策大小**，在任何存储库形状中都是相同的。简单决策：一个文件 `$SPEC_DIR/NNNN-title.md`（所有内容内联，编写紧凑）。一个父级（相关的子决策）、一个重型或基础决策，或一个值得 `verify.md` 的使用目录形状：`$SPEC_DIR/NNNN-title/`，其 `index.md` 作为顶级文件，旁边有一个 `rationale.md`（对于父级，子规范 `NNNN-<child>.md`）。从不重复名称（`NNNN-title/NNNN-title.md`）；目录携带编号，顶级文件是 `index.md`。默认为单个文件。

  目录规范始终有两个核心文件（加上可选的 `verify.md` 和子规范）：
  - **`index.md`**：构建规范 `/develop` 读取：`## Summary`，`## Requirements`，`## Decision`，设计/规范部分，`## Build plan`，`## Consequences`，`## Follow-up`，以及指向 `rationale.md` 的一行 `## Rationale` 指针。对于父级，它还以列表和链接每个子规范开头（每行一个：它是什么以及它支持哪个决策），并包含任何跨子合同。
  - **`rationale.md`**：决策记录 `/develop` 跳过：`## Context`，`## Options considered`，`## Rationale`，`## References` 部分，以及它自己的子标题下的任何大型证据（清单、审计）。没有 `research/` 文件夹；所有证据都生活在这里。
  - 子规范（父级仅限）是扁平的 `NNNN-<child>.md` 文件，每个文件足够完整，可以独立构建，并带有简短的内置推理（没有自己的 `rationale.md`）；只有当它变得沉重时才将其提升为其自己的目录。跨子合同生活在父级 `index.md` 中。
- **范围中的一个狭窄例外**：确认规范后，更新匹配的功能为准备构建的形状（*规范编写后*，步骤 3 中的确切编辑）。不要将原子任务列表倒入范围。没有匹配的功能：提供注册一个（见推导任务步骤）。

**物品基础。** 规范默认生活在 `docs/` 下。如果 `docs/` 是一个发布的文档站点（`docusaurus.config.*`，`.vitepress/`，`mkdocs.yml`，Astro Starlight 或 Nextra 检测到），则使用 `.workflow/` 而不是（`.workflow/specs/`）。始终遵循已经存在的基（这里的路径假设 `docs/`）。

## 可移植性（任何操作系统，任何代理）

- **命令**：`git` 是唯一需要的 CLI，在所有操作系统上都是相同的。其他 shell 片段（`mkdir -p`，`date`，`find`，`ls`，`cat`，`wc`）是 POSIX 参考，不是字面脚本；使用你的代理的跨平台文件工具（读取、搜索/glob、写入、创建目录）和你对今天日期的了解。使用你的写入工具创建 `docs/specs/`，而不是 `mkdir`。
- **捆绑文件**：`agent-prompt.md`，`agent-modes/*.md`，和 `spec-template.md` 生活在此技能文件夹的相对路径下。主线程在写入规范之前自己读取这些（见 *编写规范*）：`agent-prompt.md`（角色、规则和报告格式），匹配的 `agent-modes/<mode>.md`，和 `spec-template.md`（部分结构）。只在写入时读取它们，不在预飞行期间读取，这样它们就不会在整个面试中坐在上下文中。
- **没有交互式问题支持？** 使用你的代理提供的任何东西（选项选择器），并且只在缺少时回退：作为纯文本提问问题，并提供相同的选项。

## 执行

### 步骤 0：主题检查（预飞行之前）

如果未提供设计主题（`/architect` 无参数或空描述），则在做任何其他事情之前停止并询问：

“你想处理哪个设计决策？用一到两句话描述你需要设计的功能、系统或选择。”

等待答案；将其用作预飞行前的设计主题。

---

### 预飞行（主模型）

运行这些步骤（`git` 命令是字面的；其他使用你的代理的文件工具）：

- **新鲜度（团队）**：`git fetch` 安静地，选择基础分支（如果 `git rev-parse --verify main` 成功，则为 `main`，否则为 `master`），计算与基础分支的提交数 `git rev-list --count HEAD..origin/<base>`。如果 >0，则在决定之前警告“先拉取”（一个队友可能已经添加了规范或更改了此功能）。
- **解析规范位置** (`SPEC_DIR`) = 范围工作空间镜像到 `docs/specs/`：单个存储库 → `docs/specs/`；单一代码库工作空间 → `docs/specs/<workspace>/`；整个存储库 → `docs/specs/_root/`。确定 `<workspace>` 如范围所做（主题/路径/范围行）。如果缺少，则创建目录。
- **今天的日期**：使用今天的日期（将其注入规范）。
- **列出此位置的现有规范**：命名 `NNNN-*.md` 的文件，以及 `$SPEC_DIR` 中的任何 `index.md`，用于编号（按位置）和相关的决策检测。
- **计算源文件数量**（例如 `.ts`，`.tsx`，`.js`，`.py`，`.go`，`.rs`，`.java`），排除 `node_modules/`，`.git/`，`dist/`。这提供了要读取的代码量，并决定是否将读取卸载给 `scout` 子代理。
- **读取项目上下文**，堆栈和社区技能的真相来源：根 `AGENTS.md`（回退到 `CLAUDE.md`，否则缺失），以及此功能区域的嵌套 `<area>/AGENTS.md` 如果存在（例如 `src/auth/AGENTS.md` 对于一个认证功能）。
- **读取此功能的构建方法**，管理规范 `## Build plan` 如何排序和切片的交付策略。优先级：此功能的范围行 `Approach` 覆盖（如果声明），否则项目默认（根 `AGENTS.md` 首先否则 `docs/scope/` 中的范围标题）。有自己的方法的功能按其方法构建；其他使用项目默认值。四个意味着实质上不同的 `## Build plan` 排序，而不是重新标记的相同顺序：**Tracer Bullet** 首先建立通过每一层的薄端到端线程，然后变厚；**Skateboard** 首先构建最薄的可用整体，然后增长；**Facade** 领先于 UI 壳牌在占位符数据上，并推迟迁移（一个原型路径）；**Journey** 在下一个用户路径的任务完全完成之前完成一个用户路径的任务。可能的特定项目变体。如果两者都不记录一个，则假设默认值并按 Staff/Principal 判断设置（为生产工作优先考虑端到端 Tracer Bullet 切片）。让记录的方法明显塑造排序。
- **定位链接的范围功能（如果有）**：廉价扫描 `docs/scope/` 文件名/标题（包括每个工作空间子目录），寻找匹配此主题的功能；仅打开包含它的单个范围文件（`scope.md`，或在拆分中匹配的 `<epic>.md`）。如果找到，读取该行的意图加上任何验收标准种子（它们为阶段 (a) 种子），并记住文件/行以供推导任务和链接步骤使用；这也确定了功能链接与独立状态。如果没有行匹配，则注意独立决策路径，现在不要创建一个。
- **（可选）列出安装的技能目录以供仅可用性参考（`.claude/skills/`，`.agents/skills/`，`skills/`）。相关性由 AGENTS.md 加上功能决定，而不是名称匹配。

从规格列表（相对于 `$SPEC_DIR` 的路径）：
- **编号**：现有最高编号加1，补零至4位；若无则从 `0001` 开始（一个总目录算作一个编号）。冲突防护（团队）：在写入前立即列出 `$SPEC_DIR`；如果选择的 `NNNN` 已存在，则跳到下一个可用编号。切勿覆盖现有规格；写入后，确认没有并发运行使用了相同编号。
- **文件名/结构**：从主题中提取 `kebab-case` 形式的缩写，最多5个词，无冠词，全部小写。
  - 简单决策 → `$SPEC_DIR/NNNN-kebab-title.md`。
  - 总决策（拆分为≥2个相关子决策）→ `$SPEC_DIR/NNNN-kebab-title/` 目录，包含 `index.md`（列出其子决策的总决策）、`rationale.md`（理由+任何清单/审计），以及其中的子规格 `NNNN-child.md`。在写入前根据主题的广度决定结构，并在写入时牢记该结构。
- **相关规格**：分两步处理，以保持成本低廉，随着规格的积累。首先只读取每个现有规格的标题行（即使有几十个也很便宜）；然后只读取标题可能与此主题重叠的少数规格的前20行（标题、状态、上下文的开头），以确认。标记匹配项。
- **子决策检测**：如果主题是现有总决策的子决策（`$SPEC_DIR/NNNN-<umbrella>/`），例如在构建过程中出现的，将新规格放在该目录中作为下一个子决策（`NNNN-child.md`），并将其添加到总决策的 `index.md` 列表中，而不是创建一个新的顶层规格。当 `/develop` 在构建中途遇到决策时，路径相同。告知工程师它将放置的位置。
- **更新/替代检测**：如果现有规格明显与主题重叠（相同领域、系统、决策），在阶段对话之前呈现决策面板（纯文本选项，代理没有选择器；选择器会自动添加“其他”）：“我发现了一个可能重叠的现有规格：`[路径]`，[标题]。我应该如何处理？”，选项：**新决策（创建新规格）** · **原地更新现有规格** · **替代它（新规格替代它）**。默认为重叠强度（几乎相同→更新或替代；相邻→新）。在更新/替代时：设置 `OPERATION`，完整读取现有规格，并跳过原地更新的阶段对话。
  - **假设规格发现**：如果重叠规格的 `**状态**:` 是 `Assumed`，这是一个确认，而不是上面的面板。遵循 *确认假设决策*（运行设计对话，然后要么填写真实内容并清除 `Assumed`，要么如果假设错误则替代）。

**社区技能** 来自项目的 `AGENTS.md`，永远不会是硬编码的名称表（名称和堆栈会变化）。项目范围的技能/约定位于根 `AGENTS.md`，区域特定的在嵌套的 `<area>/AGENTS.md`（由 `/audit` 和 `/sync` 维护）：

1. 读取根 `AGENTS.md` 和此功能区域的嵌套 `AGENTS.md`；它们的 `## Agent skills` 部分将每个安装的技能作为带有其位置和一行说明（说明其管理内容）的要点列出，以便你可以直接挑选出相关的技能及其路径。
2. 仅识别与 *此* 功能相关的技能。取每个相关技能的路径，并从该 `## Agent skills` 要点中记录，在写入时按需打开它，只有当它实质性地影响决策时（见 *编写规格*，项目12）。跳过功能不涉及的技能。
3. 可用≠相关。你可以列出安装的技能目录以查看存在的内容，但相关性来自功能加上 `AGENTS.md`。如果有一个明显相关的技能已安装但尚未在 `AGENTS.md` 中引用，仍然使用它，并标记（规格后续）它属于正确的上下文文件：根文件如果是项目范围的，嵌套的 `<area>/AGENTS.md` 如果是区域特定的。
4. 无论上下文文件显示项目已使用的内容（一个BaaS、一个ORM、一个支付提供者、一个认证库）都是你的库/提供者推荐必须基于或优先考虑的，而不是一个无关的外部工具。如果有一个真正更好的选项未安装，将其作为规格后续标记，而不是默默假设。

**工作流技能**（永远不要视为社区技能）：`audit`、`architect`、`scope`、`develop`、`check`、`test`、`document`、`debug`、`sync`，以及新创建的工作流技能。

### 范围验证、框架和阶段设计对话

对于创建或替代操作，这是一个硬性门槛：**在向工程师提出第一个设计问题之前，完整阅读 `internal/design-conversation.md` 并遵循它。** 它包含范围验证（包括已构建的文档路径）、框架和阶段设计对话。*提问与行动* 上面只是意图，不是协议；在阅读该文件之前，不要开启访谈、生成问题或编写规格。（仅对于原地规格更新可跳过。）

### 编写规格（主线程）

阶段对话后，你自己编写规格。不要生成任何人来起草、研究或评论它。将此技能的文件夹解析为绝对路径（你已经解析了这些相对路径，所以你知道文件夹）并现在读取三个文件（仅现在，所以它们不会在访谈中作为上下文存在）：`agent-prompt.md`、`spec-template.md`，以及匹配推断的 `MODE` 的一个模式文件：
- `FEATURE` → `agent-modes/feature.md`
- `ARCHITECTURE` → `agent-modes/architecture.md`
- `ENHANCEMENT` → `agent-modes/enhancement.md`
- `CROSS-CUTTING` → `agent-modes/cross-cutting.md`

然后编写规格，应用：
- **从 `agent-prompt.md`**：采用角色（“你是谁/你如何思考/你不会做什么”），并遵循通用指令、步骤0、步骤0b、`## 专家规则适用于所有模式` 和 `## 报告格式`。在 `## 按模式指令` 中，仅跟随上述唯一模式特定块；忽略其他模式文件。`agent-prompt.md` 是作为子代理简报编写的，带有 ALL_CAPS 占位符；读取这些占位符作为你在对话中已经收集的输入（列在下文），并将规则应用于你自己。
- **从 `spec-template.md`**：仅使用 `=== SPEC TEMPLATE START ===` 和 `=== SPEC TEMPLATE END ===` 之间的部分（规格部分结构和字段指导）。尾随的引用/元数据部分（`## 文件名约定`、`## 状态值` 表格、总决策结构/子状态注释、`## 编写规则`）是自己的指导：你在预飞行中解析了文件名、形状和初始 `**状态**:`；根据 `## 专家规则适用于所有模式` 中的“初始 `**状态**:` 行”规则编写 `**状态**:` 行。不要编辑 `spec-template.md`。

**引用和链接：重用阶段（c）`REFERENCES_LEVEL`；不要现在获取。** 根据在 `agent-prompt.md` 中的 *关于来源和引用* 规则，在该级别编写 `## 引用` 部分和 `(basis: ...)` 引用。阶段（c）检查运行一次；仅重用它们确认的链接，并按名称引用未验证的来源，无URL。只有如果阶段（c）从未运行（例如文档路径），现在呈现引用同意面板（推荐选择 `无引用，保持干净`）并将 `REFERENCES_LEVEL` 设置为 `none` 或 `sources`（`sources+links` 不提供，写入时没有获取可用）。

推断的 `MODE`（来自框架）已经是 `FEATURE` / `ARCHITECTURE` / `ENHANCEMENT` / `CROSS-CUTTING` 之一。

应用输入（你已经从设计对话和预飞行中拥有它们）：
1. 设计主题（来自用户的原始消息）
2. 推断的框架：`MODE`、平台（web/移动/API）、堆栈和约定（来自 `AGENTS.md`），以及任何推断或确认的约束/合规性
2a. 功能的构建方法（预飞行优先级：范围行 `Approach` 覆盖，否则来自 `AGENTS.md`/范围标题的项目默认，否则注释的默认）→ `BUILD_APPROACH`；根据方法对此功能隐含的内容对 `## 构建计划` 进行排序和切片
3. 所有阶段对话答案，按阶段：确认的验收标准（已识别 AC-1…，以填充 `## 要求`）、确认的数据模型（实体/字段/关系，目标种子 `## 构建计划` 迁移，大小适合此功能）、确认的堆栈/工具选择、API 表面、授权模型和边缘情况。在文档路径（跳过阶段对话）中将其视为 `"跳过阶段设计，记录一个已做出的决策"`，而不是错误
3a. `RECOMMEND` 项目 → `RECOMMEND_ITEMS_OR_NONE`：你必须做出并说明理由的特定决策（与堆栈对齐的工具/提供者、会话模型等）；做出每个调用，不要将其作为开放式问题回显。如果没有，将其视为 `"无"`。
3b. 引用级别 → `REFERENCES_LEVEL`（`none` | `sources` | `sources+links`，按上述规则）。如果阶段（c）从未运行且你尚未询问，默认为 `none`
4. 上下文文件内容：`AGENTS.md`（根+功能区域的嵌套），或 `CLAUDE.md` 作为后备，或 `"缺失"`
5. 现有规格列表（文件名+每个的第一行）
6. 相关规格路径（预飞行中标记的）
7. 解析的规格位置（`$SPEC_DIR`）、下一个编号和形状：一个文件 `$SPEC_DIR/NNNN-title.md`，或一个目录 `$SPEC_DIR/NNNN-title/`（`index.md` + `rationale.md`，以及嵌套的子规格）。总决策：编写命名的子决策；任何清单/审计都放在 `rationale.md` 中，绝不放在 `docs/scope/` 中，绝不散落在代码树中。只有 `index.md` 带有 `**状态**:` 行（它镜像功能）；子规格省略生命周期状态（规格内容受总决策管理）
8. 源文件计数（是否有代码可读取；对于大型 ENHANCEMENT/CROSS-CUTTING 代码库，根据 *子代理* 将读取卸载到 `scout` 子代理，并从其地图编写）
9. 操作：`create` | `update` | `supersede`
10. 今天的日期（来自预飞行）
11. 文档上下文（如果“已构建”路径运行：工程师关于为什么选择此方案的自由文本答案、替代方案和权衡）
12. 与此功能相关的社区技能（从 `AGENTS.md` 识别，按预飞行）：按需打开技能文件，只有当它实质性地影响此决策时；当咨询时，其约定是权威的。在 `## 决策` **实施技能** 字段中列出每个技能。

### 规格编写后

一旦规格文件存在，读取 `internal/after-subagent.md` 并遵循它以自我检查规格、自我审查、确认、状态确认、范围链接和最终口头总结。在编写规格之前不要读取它。

### 更新/替代路径

如果任务是更新或替代现有规格：
- 预飞行：完整读取现有规格
- 如果操作是原地更新，跳过阶段对话
- 设置操作：`update` 或 `supersede`
- 如果替代：编写新规格并更新旧规格的状态为 `Superseded by [NNNN](NNNN-title.md)`

### 确认假设决策

当主题解析为现有的 `Assumed` 规格时（工程师通过 `/develop` 的逃生通道首先构建，现在正在确认，通常表述为 `/architect <feature>: ratify …`），预飞行将找到该规格。完整读取它：它的 `## Owed decision`、`## Assumption built on` 和 `## Code area` 告诉你临时决定的内容和代码位置。然后运行正常设计对话，以实际构建为锚点，并适当讨论决策。有两种结果：

- **假设成立。** 填写真实决策内容（上下文、考虑的选项、决策、理由、设计部分、后果），使规格成为真实讨论记录，并清除 `Assumed`：将 `**状态**:` 行设置为功能的生命周期状态（如果功能已构建但尚未 `done` 则为 `In Progress`，如果已验证和测试则为 `Accepted`）。`/develop` 则在 `done` 时按常规将其关闭为 `Accepted`。决策不再短暂。
- **假设错误。** 编写更正规格（`create` 或 `supersede`）并包含真实决策，将假设规格标记为 `Superseded by [NNNN](…)`，并告知工程师构建基于一个错误的假设，应针对更正规格重新构建。

无论如何，确认是 `Assumed` 规格可以离开该状态的原因：`/develop` 记录假设，`/architect` 确认或更正它并提供理由。确认运行后不要将规格 `Assumed`。
