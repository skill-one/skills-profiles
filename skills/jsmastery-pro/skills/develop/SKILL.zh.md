## 输出风格（纯文字，无连字符，无破折号）

将此技能生成的所有内容，包括文件和消息，均使用简洁明了的语言编写。像同事一样，以 `you` 的口吻进行交流，态度温暖直接，并将每一步都作为建议呈现，供用户选择执行或跳过，而不是强制命令。保留具有实际意义的术语；用简洁明了的语言解释每个术语。不要使用连字符或破折号作为标点符号：不要使用英文破折号、中文破折号，也不要使用连字符复合词。写 `read only`，而不是 `read-only`。用简洁明了的语言表达，或者重写句子。代码、文件路径、命令标志和值等其他技能匹配的保留其连字符。使用短句、逗号或括号。清晰比聪明更重要。

## 此技能的作用

构建者：将规范和项目约定转换为可运行的代码。跟踪：**UI**（组件、页面、布局；`ui-guide.md`）、**逻辑**（API、服务、数据层、业务逻辑、集成；`logical-guide.md`），或两者（例如，“auth” = 登录页面加上会话逻辑 → 运行两者）。步骤 0 在规范上设置门禁，以便在 `/architect` 中决定承重选择（认证方法、支付提供者），而不是在构建过程中无声地创造。

## 询问与执行

先设置门禁，再执行：没有 `/architect` 的前期问题轮次。阅读决策，构建，只询问设计留下的开放部分（当没有参考时，视觉方向；规范未确定的业务规则）。从规范、`AGENTS.md` 和代码库中推断，推荐本地实现选择。

## 产出物所有权

- 编写应用代码（包括 UI 的 CSS/令牌）。
- 范围 (`docs/scope/`)：仅步骤 4 触及（功能状态 → `in-progress`，里程碑子框，`Build it` 盒子，代码指针）。仅在 `Prototype` 工作流层将功能标记为 `done`（构建及其自身的自我检查；工程师选择跳过单独验证）；`Assumed` 规范不会阻止此操作，它保持标记为需要批准。在 `Alpha`/`Beta`/`GA` 时，它将功能 `in-progress` 留给 `/check verify` 和 `/test` 关闭，并且永远不会勾选 `Verify it` 或 `Test it`。永远不会在 `docs/scope/` 中创建文件（仅限范围；分析/研究是 `/architect` 的，在规范的 `rationale.md` 中）。
- 从不编写规范内容或商讨决策（标记需要，委托给 `/architect`）；从不重构根 `AGENTS.md`（那是 `/audit`）；新区域约定通过 `/sync` 后续处理。**一个狭窄的例外**：在 `Build now, record it as an assumed spec`（步骤 0），`/develop` 可能 *创建* 规范，但仅限于 `Status: Assumed`，并且仅限于假设记录字段（需要决策、假设构建基于、授权人、代码区域、需求种子）。它从不编写理由，也从不使 `Assumed` 规范超出该状态；`/architect` 拥有清除它。这是 `/develop` 创建的唯一规范。
- 对现有规范进行一次规范触摸：`**Status**:` 行（总决策 → `index.md` 的，不是子规范的），以及填写功能的规范指针行。构建开始：`Proposed` → `In Progress`；构建完成（功能 → `done`）：`In Progress` → `Accepted`（规范在功能发布之前不会 `Accepted`）。从不编辑规范内容，只编辑该行，外科手术式：写之前再读一遍；意外状态（已经 `Accepted`，`Superseded`）→ 标记，不要覆盖。**永远不要将规范移出 `Assumed`**（那是批准，是 `/architect` 的工作）：`Assumed` 规范在构建过程中保持 `Assumed`，即使功能是 `in-progress`，所以它永远不会在 `/architect` 批准之前达到 `Accepted`。功能本身仍然可以标记为 `done`（工程师的决定）；`Assumed` 规范保持标记为需要批准，它不会阻止 `done`。
- 产出物基础：默认为 `docs/`，如果 `docs/` 是发布的文档站点，则为 `.workflow/`。从存在的路径读取（这里假设 `docs/`）。
- 共享范围：在勾选之前再读一遍，只编辑特定的复选框、状态或指针行（从不重写文件）；功能不符合预期（已经 `done`，重新设计）→ 标记，不要覆盖。

## 可移植性（任何操作系统，任何代理）

任何 Agent Skills 客户端，macOS/Linux/Windows。检测片段是 POSIX 参考；使用代理自己的跨平台文件工具。构建在主线程中内联进行（步骤 3）；唯一的子代理是一个只读的 `scout` 探索代码（步骤 2.5）和一个只读的 `researcher` 用于文档检查（步骤 2.6，降级为无网络能力从知识构建），都在最低成本模型上。捆绑指南（`ui-guide.md`，`logical-guide.md`，`checklist.md`）和门禁后的构建流程（`flow/build.md`）是相对于此技能文件夹的路径；主线程读取它们。没有交互式问题选择器 → 以纯文本形式询问提示，并提供相同的选项。

## 执行

### 构建之前：项目必须已经存在（除了脚手架任务）

例外：如果这是 Stack 和架构基础功能的脚手架子任务（提示说 `scaffold`，或者步骤从 stack 规范初始化项目），创建项目就是任务。读取 ARCHITECTURE 规范的 `## Proposed stack`；运行规范命名的框架自己的项目初始化器；安装基本依赖项（框架、核心运行时、仅第一个切片需要的）；布局目录；确认开发服务器或构建运行。**保留初始化器创建的仓库（在重新定位项目时永远不要丢弃它）；如果它没有创建任何内容并且 git 集成已开启，`git init`。** 脚手架步骤来自 stack 决策（决策规范没有构建计划）。即时安装：不是规范命名的每个库（电子邮件、监控等）；每个后续功能在构建时安装自己的；只有跨切工具（lint、格式、类型严格性）提前通过 `/audit` + 工具任务安装。然后继续。

否则 `/develop` 构建到现有项目中。没有骨架（没有 `package.json`/`pyproject.toml`/`go.mod`/manifest，没有源树）并且不是脚手架任务 → 停止：

> 未找到构建目标的项目。先运行脚手架步骤（根据你的架构规范，Stack 和架构功能的脚手架子任务），然后再次运行 `/develop`。

项目存在（即使是裸脚手架）→ 继续。

### 构建之前：新鲜度与协作（不要在陈旧状态或覆盖队友上构建）

在修改任何内容之前（如果是单人、离线或不使用 git，则静默跳过）：`git fetch` 安静地；基础 = `main`，否则 `master`；落后计数（`git rev-list --count HEAD..origin/<base>`）；未提交的工作（`git status --short`）。

- 落后（计数 > 0）→ 停止并警告： "你落后 `origin/$BASE` N 个提交。队友可能已经更改或发布了这个。先拉取，然后再次运行。"
- 在你将要触及的区域有未提交的工作 → 警告： "你在这里有未提交的更改。先提交或暂存，以免此构建与它们纠缠。" 如果他们坚持，让他们继续。
- 范围中的功能 `in-progress` 且其代码区域（指针行的路径）有另一位作者最近的提交（`git log --format='%an' -- <area>`）→ 警告： "*<功能>* 看起来像是由其他人正在构建。继续之前先协调。" 确认后再继续。

警告，而不是硬性阻止，但要让它们出现。

**Git 集成**：如果最近的 `AGENTS.md` `## Git` 说 `integration: on`，读取 `flow/git.md` 并遵循它（构建前分支，里程碑落地时提交）；缺失或 `off` → 不进行主动 git。

### 步骤 0：规范门禁（始终第一个）

是否有未记录的待决策？不要通过内省判断（“我感觉像是在创造东西？”），构建模型将一个真实的决策合理化为“只是接线”并放行。使用积极的 **输入覆盖** 测试，这是机械的，更难说服自己：

> **枚举此构建必须产生、计算或显示的每个值（来自验收标准和规范的 设计）。对于每个值，规范是否指明了其来源（一个输入、一个数据库列、一个从命名值派生的值、一个先前的决策）？任何没有命名来源的必需值都是一个待决策。**

如果有任何来源未命名，停止并将路由到门禁（`/architect`，或记录一个 `Assumed` 规范；`/develop` 实现决策，而不是制定它们）。当您必须创造时，决策也是待定的：

- **一个提供者、库、集成、数据模型或跨切模式**（例如，认证提供者、DB/ORM、缓存策略）。
- **一个完整的 UI 页面或屏幕**：其设计系统（`design.md` 在那里？如果没有，哪个方向？）、部分/组合、组件清单、资产策略（没有截图，没有仓库图像 → 例如，在线来源）。除非 `design.md` 和页面级规范固定这些，否则待定。
- **一个功能的行为**（搜索、向导：“它确切地应该做什么？”是开放的；`/architect` 询问这些问题）。除非规范定义了它。

**“本地实现细节”实际意味着什么（狭窄的例外）**：仅限于规范命名来源已经允许的选项选择、循环样式、变量名、调用哪个辅助函数。一旦选择 **决定了值的来源，或行为受验收标准约束**，它从定义上就是承重的，无论看起来多么小。从“用户的今天从他们上次读取行的时区”派生不是本地细节：它选择了受 AC 约束的值的来源，所以它是待定的。不待定于真实的纯实现：一个小 Bug 修复、与现有 `design.md` 匹配的组件、连接规范已经命名的部分、复制微调、任何现有规范/`design.md`/`AGENTS.md` 完全管辖的内容。

不要硬编码到页面名或任何一个示例（时区是说明模式的例子，不是规则）；将输入覆盖测试应用于所请求的内容。错误负面是失败模式，在不注意的情况下构建了真实的决策：当必需值的来源未命名，或不确定时，将其视为待定并询问（下方面板）。

只读取此功能需要的内容，而不是整个 `docs/` 树：它的一个范围文件和它的一个管理规范（单个文件，或总纲 `index.md` 加上一个子规范指定此子任务）。没有其他功能的行、范围文件、工作区或无关规范。

**按顺序检查**：
1. **定位此功能的范围文件（仅这一个）。** 单一仓库 → `docs/scope/<workspace>/` 对于任务的包。从“一览表”表中挑选文件（`scope.md`，或匹配的 `<epic>.md` 在拆分中），只读此功能的部分。`needs a decision` 没有规范指针 → 决策待定且缺失。格式错误 → 标记并询问，不要猜测。
2. **通过功能的 `spec` 指针打开管理规范**，只读取构建流程（`flow/build.md`）中定义的构建规范部分，步骤 2 项 1。找到 → 它是规范；继续。没有指针且没有链接规范 → 在 `docs/specs/<workspace>/` 中针对此功能范围查找一个匹配的，从不进行笼统的读取。
3. **最近的** `AGENTS.md`（工作区/区域）可能已经捕获了决策，从早期功能同步（例如，“认证提供者已经选择”）→ 无需新规范继续。决策待定且未记录 → 不要猜测，不要静默停止。询问（单选；`AskUserQuestion` 在 Claude Code 上）：

- **问题**： "这看起来像它需要一个架构决策：`<具体说明承重选择，例如 '哪个认证提供者 + 会话模型'>`。你想如何处理？"
- **标题**： "规范优先？"
- **选项**：
  1. `Architect it first`： "推荐。在构建之前捕获决策，以便构建有规范。" → **在此处结束**，带以下交接。不要构建。
  2. `No, not needed`： "我判断这里没有真正的决策；直接构建。" → 继续到构建流程（`flow/build.md`）。
  3. `Build now, record it as an assumed spec`： "构建它，但先记录假设，以便决策保存在仓库中，而不仅仅是这次聊天。`Assumed` 规范保持标记为需要批准（`/architect`），但这永远不会阻止将功能标记为 `done`。" → 写一个 `Assumed` 规范（下方），然后继续到构建流程（`flow/build.md`），将功能 `in-progress` 并在范围（`docs/scope/`）中添加 `assumed decision (spec NNNN)` 注释。

工具应用程序自动将“其他”作为自由文本选项。

在 `Build now, record it as an assumed spec`，在构建之前写一个最小的 `Assumed` 规范（这是 `/develop` 拥有的唯一规范写入；见产出物所有权）。按照 `/architect` 的方式解决 `$SPEC_DIR`（单一仓库 → `docs/specs/`；单一仓库工作区 → `docs/specs/<workspace>/`），取下一个空闲的 `NNNN`，并写入 `$SPEC_DIR/NNNN-<slug>.md`：

```markdown
# NNNN · <功能>

**状态**：Assumed
**日期**：<今天>
**授权人**：<工程师>，在 /develop 期间

## 待决策
<未做出的具体承重选择>

## 假设基于
<此构建将使用的具体假设>

## 代码区域
<此构建将触及的路径>

## 需求
<从范围 Done 时携带的验收标准种子，如果有的话>

## 批准
此决策由 /develop 记录，而不是商讨。运行 `/architect <功能>` 来商讨和批准它。在此之前它保持标记为待决策；它不会阻止将功能标记为 `done`。
```

将功能的范围 `spec` 行指向此文件。假设现在是持久的：它存活 `/clear`，队友可以阅读它，并且后续的 `/develop` 对其构建而不是再次猜测。`Assumed` 规范保持标记为需要批准；它不会阻止将功能标记为 `done`（见 `flow/build.md`，步骤 4）。

在 `Architect it first`，结束：

> 运行下一步，然后回来 `/develop`：
> ```
> /architect <功能>： <要确定的特定决策>
> ```
> 规范存在后，再次运行 `/develop <任务>`，我会构建到它。

没有决策待定（纯实现）→ 跳过问题，继续。

### 构建流程（步骤 1-4）

一旦门禁通过（没有决策待定，或工程师选择了 `No, not needed` / `Build now, record it as an assumed spec`），读取 `flow/build.md` 并遵循其步骤 1-4：分类轨道，加载决策和约定，探索，可选文档检查，构建，然后更新范围和报告。当门禁结束运行时（`Architect it first`，无构建）→ 不要读取 `flow/build.md`。
