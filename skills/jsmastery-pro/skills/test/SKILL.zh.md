## 此技能的作用

角色：一名高级测试工程师，编写代码值得的测试套件。测试调用者依赖的内容和实际会导致问题的内容，而不是为了覆盖率而编写的行。根据每个文件的内容选择策略。拒绝那些锁定切片的测试，而切片本意并不是要使其成为现实。

目标：此分支中已更改但尚未提交的代码。每个已更改的文件都按类别分类（纯逻辑、组件、API 路由、页面/流程）并使用正确的策略进行测试。主线程自行编写测试（一个只读的 `scout` 可以执行大型集合的重文件读取）；在治理规范下，测试可以追溯到其验收标准（步骤 7 和 8）。

不编写应用程序代码。不更新 `AGENTS.md`/`CLAUDE.md` 上下文文件（`/sync` 负责这些）。

## 询问与行动

- 当 `test-preferences.json` 存在、工具已安装且存在未提交的源文件时，直接行动，无需询问：直接开始编写。
- 每次运行时总是询问一件事，即使有偏好设置：在编写后运行套件，还是提供手动指令（步骤 7.5）。每次运行的选择不会保存。
- 否则，仅在以下情况下询问：没有 `test-preferences.json`（框架；如果页面/流程已更改，E2E 插件才需要）；未安装所选工具（先确认）；没有未提交的更改（步骤 3）；文件数大于 15 个（步骤 1b）。
- 不问范围问题。git 工作区定义了范围。

## 产物所有权

- 测试文件（`*.test.ts`、`*.spec.ts`、`test_*.py`、`*_test.go` 等由此技能创建）
- 项目根目录下的 `test-preferences.json`，由此技能创建和维护

## 可移植性（任何操作系统，任何代理）

macOS、Linux 或 Windows 上的任何 Agent Skills 客户端：
- `git` 是唯一需要的 CLI，在所有地方都相同；按所示运行 `git` 命令。其他 shell 片段是 POSIX 参考，而不是字面脚本来假设 `find`、`grep`、`sed`、`cat`、`test`/`[ ]`、`xargs`、`mkdir -p` 或 `node -e` 存在。使用您代理的跨平台文件工具（读取、搜索/全局、写入），并自行应用分支逻辑，而不是通过 shell `if`/变量/重定向。
- 打包文件：相对于此技能的文件夹进行引用。主线程在编写时（步骤 8）自行解析文件夹到绝对路径并读取打包文件：`agent-prompt.md` 和 `writing-guide.md`。
- 没有交互式问题支持？将任何多项选择题作为纯文本提出，并提供相同的选项。

在下面的 Ask 块中，每个选项都是 `"label": "description"`；通过您的代理的 `picker`（在 Claude Code 上的 `AskUserQuestion`）或作为纯文本呈现。

## 执行

### 预飞行（主线程）

#### 1. 从 git 确定范围（如果为空，则无需询问任何内容）

已更改但未提交的文件（跨平台 git）：
- 已跟踪（已暂存 + 未暂存），排除删除：`git diff --name-only --diff-filter=ACMR HEAD`
- 未跟踪，且未被忽略：`git ls-files --others --exclude-standard`
- 尚未提交（`git diff HEAD` 出错）：使用 `git diff --name-only --diff-filter=ACMR --cached`。

合并，删除重复项，过滤掉无法测试的文件：
- 测试文件：`*.test.*`、`*.spec.*`、`test_*.py`、`*_test.go`、`__tests__` 下面的任何文件、`e2e/`、`tests/`、`cypress/`
- 配置：`*.config.*`、`.*rc`、`tsconfig*`、`*.json`（逻辑不在 JSON 中的除外）、`Dockerfile`、CI yaml
- 锁定文件、`.lock`、生成/构建输出（`dist/`、`build/`、`.next/`、`coverage/`）
- 样式：`*.css`、`*.scss`、`*.module.css`；仅类型声明：`*.d.ts`
- 文档和 markdown、规范、`design.md`、`test-preferences.json`

剩余部分是范围。为空：转到步骤 3。否则继续。

#### 1b. 对每个范围内的文件进行分类

仅根据路径和文件名进行分类，快速；如果确实有歧义，在读取文件进行编写时再次标记 `logic` 并重新标记。记录每个文件的类别以供编写步骤使用。

| 路径/文件名中的信号 | 类别 | 测试策略 |
|---|---|---|
| 不是在路由/页面路径下 `*.tsx`/`*.jsx`/`*.vue`/`*.svelte` | **组件** | 组件测试（渲染 + 交互 + 断言 DOM/ARIA） |
| `app/**/page.*`、`pages/**`（不是 `pages/api`）、`*Screen.*`、`*View.*` | **页面/流程** | E2E 候选 + 组件测试 |
| `app/**/route.*`、`pages/api/**`、`*.controller.*`、`*.handler.*`、`*.resolver.*`、`actions.*` | **API/服务器** | 集成测试（调用处理程序，在边界处模拟） |
| 普通的 `.ts`/`.js`/`.py`/`.go`/`.rs`、工具、钩子、服务、领域逻辑 | **逻辑** | 单元测试（输入 → 输出、边缘情况、错误） |
| `cli.*`、`bin/**`、`*.command.*`、`cmd/**` | **CLI** | 集成测试调用命令 |

`E2E_RELEVANT = yes` 如果任何文件是 **页面/流程**；否则 `no`。

大型差异保护：更改的源文件超过 15 个，一次不要尝试编写所有文件。按类别优先级（逻辑和 API/服务器优先，风险最高，测试成本最低）并询问：

```
Ask: "<N> 个更改的文件对于一个运行来说太多。我应该如何集中精力？"  (标题: "范围大小")
- "先测试逻辑 & API (推荐)": "现在测试 <count> 逻辑/API 文件；我将其余的标记为未覆盖"
- "分批测试所有内容": "跨多次运行覆盖所有 <N> 个文件，较慢但完整"
- "让我缩小范围": "我将告诉您哪些文件或目录最重要"
```

单一代码库解析：找到每个范围内文件最近的包含 `package.json` 的父文件夹（向上遍历）。不同的根：按根分组（自己的框架、包管理器、测试目录；每个组安装和编写）。一个共享的根（常见情况）：单个项目。记录每个文件的 `packageRoot` 以供编写步骤使用。

---

#### 2. 加载偏好设置

读取项目根目录下的 `test-preferences.json`（文件工具；“未找到” = 无偏好设置）。根据它是否命名一个 `tool` 来分支，而不是文件是否存在：
- **`tool` 已设置**（常见的编写路径）：加载 `tool`、`additionalTools`、`e2eTool`、`testDir`、`filePattern`、`packageManager`；跳到步骤 5。
- **`tool` 为 `null` 且 `gate` 已设置**（`GATE_ONLY`）：此项目通过先前的有意选择不依赖测试运行器进行门控。不要编写套件，不要安装运行器，不要再次询问，也不要读取 `modes/setup.md`。运行项目的类型检查/代码检查门控，然后停止并报告： "此项目通过 `<gate>` 门控，而不是测试套件。运行了类型检查门控；使用 `/check verify` 确认行为。"
- **无文件**（`NO_PREFS`，首次运行）：读取 `modes/setup.md` 并执行其步骤 4（堆栈检测和框架问题），然后返回此处进行步骤 5（安装检查），然后执行其步骤 6（保存偏好设置），然后继续步骤 7。在编写运行中不要读取 `modes/setup.md`。
- **格式错误**（一个既没有 `tool` 也没有 `gate` 的文件，或无法解析的 JSON）：说明情况，然后将其视为 `NO_PREFS` 并再次运行设置，这将覆盖它。

---

#### 3. 无未提交的更改

范围空：跳过框架问题，告诉工程师，提供备用方案：

```
Ask: "未找到未提交的源更改。我应该测试什么？"  (标题: "无更改")
- "上一个提交": "diff HEAD~1..HEAD 并测试该提交更改的内容"
- "特定文件": "我将测试您命名的文件或目录"
- "现在不测试": "停止。我将在我做出更改后运行 /test"
```

- 上一个提交：范围 = `git diff --name-only --diff-filter=ACMR HEAD~1 HEAD`，再次运行步骤 1b。
- 特定文件：分类命名的文件，继续。
- 无：干净停止。

---

#### 5. 安装检查

使用文件工具检查所选单元工具、E2E 工具（如果有）和插件：
- JS/TS：在 `node_modules/<pkg>` 下，或在 `package.json` 的 devDependencies 中？
- Python：在 `pyproject.toml`/`requirements.txt`（或 `pip show <tool>`，如果 Python 可用）？
- Go：`stretchr/testify` 在 `go.sum` 中？

都存在 → 步骤 6。任何缺失 → 先确认：

```
Ask: "<missing tools> 未安装。立即安装？"  (标题: "安装")
- "是，安装并继续": "使用检测到的包管理器运行安装，然后编写测试"
- "否，编写可运行的占位符": "跳过安装；我将编写我可以在我自己安装工具后运行的测试"
```

是：使用检测到的包管理器安装，这里显示为 `<pkgmgr>`（检测到的 npm / yarn / pnpm / bun；对于 Python/Go 使用语言的包管理器）：

```bash
<pkgmgr> add -D vitest                                            # 单元
<pkgmgr> add -D @testing-library/<framework> @testing-library/user-event @testing-library/jest-dom  # 插件
<pkgmgr> add -D @playwright/test && <pkgmgr> exec playwright install  # E2E (Playwright)
<pkgmgr> add -D cypress                                          # E2E (Cypress)
pip install pytest pytest-mock                                    # Python
go get <testify module path>                                      # Go
```

否：记录 `INSTALL=deferred`；无论如何编写完整的测试，运行命令报告为“安装后运行”。

---

#### 7. 汇集轻量级指针（这里不要读取重文件）

仅路径和廉价信号；重读取发生在编写时（由您，或如果卸载则为只读的 `scout` 子代理在最低模型上执行）。在这里不要读取规范、`design.md` 或完整源文件。

使用文件工具：
- 列出 `docs/specs/` 下最近修改的 3 个规范路径（仅路径）。
- 确定治理规范：这些文件实现的特性目录 `docs/specs/NNNN-<feature>/`（或单个 `docs/specs/NNNN-<feature>.md`）通过分支/特性名称或触摸表面匹配（如果存在，`docs/scope/` 条目指向它）。记下其路径和旁边是否有 `verify.md`（`docs/specs/NNNN-<feature>/verify.md`）。此合同是测试追溯到的地方；它可能不在 3 个最近的路径中。当存在治理规范时，设置 `TRACE_TO_CONTRACT = yes`，否则 `no`。
- 记录项目根目录下是否存在 `design.md`；仅在 **组件** 或 **页面/流程** 文件在范围内时使用其路径，否则 `none`。
- 读取 `AGENTS.md`（规范；如果不存在则读取 `CLAUDE.md`）作为项目上下文（简短且廉价）。还记下构建方法为一句：团队选择的切片塑形方法，记录在范围标题中（或在根 `AGENTS.md`）中，例如，细端到端路径，最薄的可用整个核心循环，UI 首先在占位符上，每个阶段完整用户旅程。它不会分支逻辑；它校准您在编写时的判断（步骤 8，规则 a）。
- 读取 `package.json`，记下 `scripts.test`。`RUN_COMMAND` = `<pkgmgr> test` 当存在 `test` 脚本时（`<pkgmgr> run test` 对于 npm）；当没有脚本时，使用原始调用（例如 `<pkgmgr> exec vitest run`）。

#### 7.5 询问是否在编写后运行套件（始终）

```
Ask: "将为 <N> 个更改的文件编写测试。编写后运行套件吗？"  (标题: "运行测试？")
- "是，运行并修复为绿色": "执行套件；我将修复任何测试错误并标记测试捕获的真实错误"
- "跳过，只编写": "编写测试并给我手动运行和验证说明"
```

设置 `RUN_AFTER = yes | no` 并在编写时应用。

#### 8. 编写套件（主线程）

主线程自行编写测试。不要启动编写器。解析此技能的文件夹到绝对路径，现在读取 `agent-prompt.md` 和 `writing-guide.md`（仅在编写时读取）：`agent-prompt.md` 是您的操作模板，`writing-guide.md` 是您遵循的策略、工具规则、迭代循环和报告格式。读取测试的更改文件是唯一昂贵的部分；对于大型或不熟悉的集合，将读取卸载到只读的 `scout` 子代理在最低模型上（Claude Code：`haiku`，不继承会话模型），返回紧凑的映射，然后从它编写。

应用输入（您收集的标记值）：
1. 单元工具、E2E 工具、附加工具、`INSTALL` 状态；`testDir`、`filePattern`、包管理器、堆栈/框架、`packageRoot`；分类范围（每个文件路径及其类别：逻辑 / 组件 / 页面流程 / API 服务器 / CLI）；`RUN_COMMAND`、`RUN_AFTER`；项目上下文加上构建方法行；最近的 3 个规范路径或 `none`（如果相关则只读）；`design.md` 路径或 `none`；`TRACE_TO_CONTRACT`、治理规范路径，以及 `verify.md` 路径（如果不存在则为 `none`）。
2. 两个规则要应用： (a) 让构建方法校准哪些行为是此切片的持久真实值（将它们锁定为稳定的断言）与切片设计为通过设计模拟的故意脚手架（不要断言计划尚未构建的真实实现，例如在模拟数据的 shell 上对真实后端期望）。(b) 当 `TRACE_TO_CONTRACT = yes` 时，读取验收标准（如果存在 `verify.md`，则优先使用其已解析的 `AC-N`-标记的检查清单，否则使用规范的 `## Requirements`）并将耐久的锁定：对于每个可以锁定为稳定断言的标准，编写一个自动化的测试，每个测试标记为它覆盖的 `AC-N`（例如 `covers: AC-3` 评论，或测试标题中的 `AC-3`）以便套件追溯到合同。永远不要模拟无法自动化的标准（视觉/手动/环境，例如“电子邮件实际到达”）；将其记录在 `NOT_COVERED` 中作为 `AC-N, <为什么不能自动化>` → 延迟到 `/check verify` 手动步骤。

单一代码库（来自步骤 1b 的多个包根）：依次为每个根编写套件，范围为该根的文件、工具和包管理器（如果大型，则将每个根的文件读取卸载到其自己的 `scout`）。单一根（常见情况）：只需编写它。

### 编写套件后

如果编写失败或未生成报告：说明情况并再次尝试；永远不要报告您未实际生成的通过或失败的套件。否则传递与 `RUN_AFTER` 匹配的格式。

更新范围：如果此功能在范围内（`docs/scope/`）并且套件通过，勾选其 `Test it` 复选框，然后 **提供 `done`，不要门控它**： "测试已完成且通过，标记它为 `done`？" 在工程师的操作下，设置状态 `done`（概览表格和标题）并镜像规范的 `**Status**:` → `Accepted`。一个 `Assumed` 规范不会阻止 `done`；标记它（“需要批准，`/architect` 当您有时间时”）并让他们决定。如果测试失败或覆盖率不完整，留下 `Test it` 未勾选并报告。**确认更新作为关闭门控**（不要跳过它）：报告您在每个文件中勾选的确切内容，例如。 "范围：勾选 `Test it`，状态 → `done`。规范：状态 → `Accepted`。" 没有匹配的范围行 → 说明情况，不要无声完成。在 `done`，建议 `/clear` 在下一个功能之前：范围和规范包含所有内容，一个新会话使下一个构建廉价。**Git**：如果最近的 `AGENTS.md` `## Git` 说 `integration: on` 且 `commit` 不是 `manual`，提供提交套件，使用一行主题（`test(<scope>): …`）加上 `Co-Authored-By` 跟踪器；永远不要推送。 （有效层级 = 如果设置了功能的自己的层级标签，否则项目的 `**Workflow:**` 默认。`/test` 在 `Beta`/`GA` 上更接近；`Prototype` 在 `/develop` 上关闭，`Alpha` 在 `/check verify` 上关闭，等等，因此此功能已经 `done` 或不使用 `/test`。尊重覆盖标签；永远不要默认为固定链。）

```

**在 <M> 个文件中编写了 <N> 个测试 (正常路径 / 边缘情况 / 错误 / a11y)。 <X 通过, Y 通过 `<RUN_COMMAND>` | 未运行>。**
下一步 (此功能中未勾选的框内): 全部通过 → 如果仍有 `Review it` 框则 `/check review`, 否则 `/sync` 或下一个功能 · Y 失败 → 修复它们, 或如果代码错误则 `/debug <功能>` · 未运行 → `<RUN_COMMAND>`

```

只有当 `RUN_AFTER = no` 时, 添加运行步骤: `<如果 INSTALL=deferred 则 setup>` 然后 `<RUN_COMMAND>` (用 `<focused command>` 监视一个文件)。框架选择在 `test-preferences.json` 中; 每个测试的详细信息和 AC 可追溯性存在于测试文件中, 所以不要重新打印它们。

如果 `BUGS_FOUND` 不为空, 先写它: 一个在真实错误代码上正确失败的测试是一个真正的发现, 不是应该压制的东西。/test 不会修改应用程序代码来让测试通过。

这项技能在传递报告后完成: 它不会调用其他技能。
