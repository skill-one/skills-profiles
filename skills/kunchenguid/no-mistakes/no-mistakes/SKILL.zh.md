# no-mistakes

`no-mistakes` 是一个本地网关，它通过一个管道（意图、变基、审查、测试、文档、代码检查、推送、拉取请求、持续集成）来验证你的代码更改，在它们到达配置的推送目标之前。你通过 `no-mistakes axi` 命令系列来驱动它，该命令系列将机器可读的 [TOON](https://toonformat.dev) 打印到标准输出，并将进度打印到标准错误。

## 活跃的验证步骤边界

一个 no-mistakes 验证步骤代理已经在一个活跃的外部运行中。它必须检查、修复并只返回其分配的阶段。它绝不能初始化、启动、重新附加、重新运行、响应、同步、中止、弹出或直接推送一个 no-mistakes 管道。用户意图中的交付要求仍然是接受上下文，但外部执行者单独执行其他验证、推送、拉取请求和持续集成阶段。

`NO_MISTAKES_GATE` 是快速诊断证据，本身不是授权。运行时结合了管理的 Git 身份和经过身份验证的进程祖先。如果一个管道控制命令返回 `error.code: nested_gate_context`，请立即停止并返回控制权给外部执行者。通过 `no-mistakes axi status`、`no-mistakes axi logs`、帮助和 `no-mistakes doctor`，仍然可以安全地进行检查。

当用户调用 `/no-mistakes` 时，在末尾报告结果。如果用户要求特定内容，请自己将请求转换为匹配的 `axi run` 标志——例如，“跳过代码检查步骤”变为 `--skip=lint`。运行 `no-mistakes axi run --help` 以查看可用标志。

## 两种调用方式

`/no-mistakes` 在两种模式下工作，具体取决于用户是否在命令中提供了任务：

- **仅验证** - 纯 `/no-mistakes`（可选地带有标志式请求，如“跳过代码检查步骤”）。用户的代码更改已经提交；验证它们并报告结果。
- **任务优先** - `/no-mistakes <任务>`，例如 `/no-mistakes 向状态命令添加一个 --json 标志`。首先自己执行任务，然后通过管道验证结果：
  1. **检查范围**。在更改或提交任何内容之前，检查 `git status`。保留与用户任务无关的现有未提交更改，并在提交时，只提交属于用户任务的变化。
  2. **执行工作**。根据任务描述进行更改，然后将它们提交到一个特性分支上。如果用户在存储库的默认分支上，请先创建一个特性分支——网关验证非默认分支上的提交历史，因此工作必须在运行之前到达那里。
  3. **然后验证**，将用户的任务作为你的 `--intent` 传递。任务文本是用户试图完成的内容，用他们自己的话表达，所以它 *就是* 意图——保留用户直接陈述的要求，包括约束、排除、验收标准以及后续决定；不要在添加实现上下文时将它们简化为差异摘要或丢弃它们。用你在执行工作时所做的决定和权衡来丰富它（见 [意图是必需的](#intent-is-required)）。

## 测试质量规则

永远不要添加一个其唯一证据是打开、读取、grep、解析或快照实现源代码并找到或省略特定字符串、标记、行、命令、函数名、提示短语、正则表达式匹配、AST 形状或偶然快照的测试。这不能证明行为：匹配的文本可能是无效的或被注释掉的，并且行为保留的重构可能会改变它。

相反，执行公共或可执行接口，并断言可观察的行为、状态、输出、副作用和失败模式。对于机器消费的声明性工件，如工作流 YAML、JSON、策略、.gitignore 或生成的配置，在可行的情况下调用实际消费者，或者解析为类型化或归一化的语义模型并断言含义。文件上的原始子字符串或正则表达式仍然是反模式。

当文件本身是生成的公共输出、序列化协议、持久化状态、有意快照或另一个明确拥有的文本或字节合同时，读取文件是合法的。命名该合同时，不要使用其内容作为无关代码工作的代理。自然语言提示或指令因为其源包含一个句子而证明是有效的，确定性 CI 可能测试最终发送给代理的作为有意生成接口的提示；模型解释属于开发评估，而不是实时 LLM CI。

对于回归，在可行的情况下重现报告的失败：测试应在修复之前失败并在修复后通过。

一旦工作提交到特性分支，以下内容——先决条件、意图、验证和决策循环——都以相同的方式适用。

## 开始之前

- 你要验证的工作必须在一个分支上**提交**。网关验证提交的历史记录，而不是你的未提交工作区。
- 你必须在**特性分支**上，而不是存储库的默认分支上。
- 存储库必须已经使用 `no-mistakes init` 初始化。
- 守护进程必须有一个可运行的配置管道代理：一个受支持的本地代理二进制文件、`agent: cursor` 或 `agent: devin` ACP 别名，或通过 `acpx` 显式的 `acp:<目标>`。你是 AXI 驱动程序，而不是隐式管道代理后端。如果没有可用，运行会在第一步之前失败；`no-mistakes doctor` 会报告配置问题。

如果这些条件之一不满足，`axi run` 会返回一个 `error:`，其中包含修复它的确切命令——阅读它并采取行动（提交你的工作或创建一个分支）。如果存储库未初始化，请先运行 `no-mistakes init`；如果 `no-mistakes` 命令本身丢失或行为异常，`no-mistakes doctor` 会报告出错了。
开始之前，运行 `no-mistakes axi`（主页视图）。
如果它在你的当前分支上显示一个活跃运行，请使用 `no-mistakes axi status` 检查它。
如果它在网关处停泊，请使用 `no-mistakes axi respond` 驱动它。
通过重新运行 `no-mistakes axi run` 来重新附加正在进行的运行，当它仍然与你的当前 `HEAD` 匹配时——无论是作为提交的头部还是作为当前管道头部。
只有在打算在重新开始之前丢弃该运行时，才使用 `no-mistakes axi abort` 它；中止是在运行之间进行的操作，永远不会在运行仍在进行时用来接管或绕过网关（见 [验证和决策](#validate-and-decide)）。
如果它显示在另一个分支上的活跃运行，请留那个运行一独，并为你的当前分支使用 `no-mistakes axi run --intent "..."` 开始验证。

## 意图是必需的

当你开始运行时，你必须传递 `--intent`：**用户试图完成什么**——这个工作的目标或请求，用他们的术语表达。这不是对差异或你更改的文件的描述；它是旨在实现更改的目标。你知道它来自对话，所以直接传递它——`no-mistakes` 将其原封不动地使用，而不是从本地代理转录中推断它（更慢且更不稳定）。

倾向于完整性而不是简洁性。审查步骤使用 `--intent` 来区分有意决定和错误，所以简短的摘要会使用户已经选择的事情被标记。捕捉细微差别：用户的意图、他们沿途做出的具体决定和权衡、他们纳入或排除的任何约束或方法，以及他们明确要求但可能在差异中看起来令人惊讶的任何内容。几句话到简短段落是正常的——写下你从对话中学到的东西，而只阅读差异的审查者不会知道。

## 验证和决策

运行管道并随着发现的出现做出决定：

1. 开始运行。它阻塞，直到第一个决策点或结束：
   ```sh
   no-mistakes axi run --intent "<用户试图完成什么>"
   ```
   `axi run` 和每个 `axi respond` 都同步阻塞——审查、测试和 CI 步骤可以分别花费 **几分钟**，所以一次调用可能不会很快返回。这是正常的；不要因为看起来慢而取消或重新提交命令。两个命令默认为 `--wait 8m`，所以带有 10 分钟工具上限的 harness 会得到结构化返回，而不是无限制的挂起。如果命令因为等待时间到期而返回，它不是失败的运行，也不意味着守护进程死了：使用 `no-mistakes axi status` 检查并重新运行 `axi run` 或 `axi respond` 重新附加。慢速的实时守护进程在健康探测后重试，而不是作为 I/O 失败处理。要在不干扰运行的情况下检查进度，请从单独的调用中使用 `no-mistakes axi status`。
   长时间运行的调用是正在工作，而不是停滞——如果你的 harness 需要，将其放到后台，但运行 **永远不会自行越过网关**。阅读每次返回；在 `gate:` 上，响应；循环，直到 `outcome:`。永远不要闲置等待运行自行前进。
   当状态输出在运行下包括 `awaiting_agent: parked <持续时间>` 时，运行停在批准或修复审查网关并等待你发送 `axi respond`。该字段仅用于可观察性：它不会改变网关分辨率、自动恢复运行或使 `--yes` 成为默认值。
   当一个步骤处于 `running` 或 `fixing` 状态时，`axi status` 可能包括 `active_steps`，其中包含步骤范围的 `active_for`、当前轮次的 `round_active_for`、`last_activity`、当子进程代理运行时本地 `agent_pid`，以及当前轮次，例如 `round 1`、`auto-fix 1/3` 或 `fix 2`。如果 `last_activity` 以 `quiet` 开头，则没有步骤日志或本地代理生命周期活动已到达比 `step_quiet_warning` 更长的时间，将其视为生存线索，而不是取消、重新运行或自己编辑工作树的权限。

2. 如果输出包含 `gate:` 对象，管道正在等待你。
   阅读其 `findings` 表。每个发现都有一个 `id`、`severity`、`file`、`description` 和一个 `action`，告诉你知道管道如何将其分类：
   - `auto-fix` - 机械和低风险；你可以根据自己的判断通过使用 `--action fix` 来授权修复。
   - `no-op` - 仅信息性；无事可做。
   - `ask-user` - 发现挑战用户的故意意图或触及产品行为。这是只有用户才能做出的调用——见下文 [升级 `ask-user` 发现](#escalate-ask-user-findings)。

   **默认情况下禁用自动修复审查** (`auto_fix.review: 0`；如果存储库或全局 `auto_fix.review > 0` 覆盖重新启用它)，所以阻塞和 `ask-user` 审查发现会等待你的决定，而不是被静默自动修复。（其他步骤，如测试和代码检查，可能在管道内自动修复并在它们到达网关之前重新运行。）

   选择一个响应：
   ```sh
   # 接受步骤原样继续
   no-mistakes axi respond --action approve

   # 让管道修复特定发现，然后继续
   no-mistakes axi respond --action fix --findings <id1,id2> --instructions "<可选指导>"

   # 跳过此步骤
   no-mistakes axi respond --action skip
   ```
   当运行处于活动状态时，永远不要通过自己编辑代码来修复发现——管道拥有发现和修复。你在网关处的任务是决定和响应；`--action fix` 让管道应用修复并重新审查结果。出于同样的原因，当运行处于活动状态时，**不要** `abort` 或 `rerun` 以便自己修复发现——即使是你的代码中的真实错误——因为这会丢弃管道的进行中的工作并强制完整重新验证。`abort` 和 `rerun` 是在 *运行之间* 的操作，永远不会在运行仍在进行时用来绕过网关。

    每个 `respond` 阻塞，直到下一个 `gate:`、`checks-passed` 决策点或最终结果，受相同的默认 `--wait 8m` 持久性约束。

    `respond` 上的额外标志：
    - `--wait` 限制持久性（默认 8m）。
    - `--reason "操作员的解释"` 记录一个明确授权的测试异常，使用 `--step test --action approve`。
      这不会授予批准权限；如前所述升级 `ask-user` 发现。
      没有理由，测试批准仍然有效；在失败命令、`no-go` 或 `inconclusive` 裁决之后通过批准是报告为没有操作员理由提供的异常。
    - `--add-finding '<json>'`（与 `--action fix` 一起使用）将你自己发现的发现——管道没有揭示的——折叠到修复轮次中，作为 JSON 发现对象。用于你注意到的未在网关自己的 `findings` 表中列出的问题。
    - `--step <name>` 而不是当前等待批准的步骤响应。你很少需要这个；省略它以回答活动的网关。

3. 重复步骤 2，直到输出包含 `outcome:` 而不是 `gate:`。结果是：
   - `checks-passed` - 更改已验证且 CI 为绿色（或受信任的默认分支配置声明 `no_ci: true` 且没有注册检查——当适用时帮助行会命名该声明），但 PR 尚未合并。**你不再驱动管道。** 不要等待合并：告诉用户 PR 已准备好，并要求他们审查和合并它（PR 链接在帮助行中）。一个通用空锻造检查列表如果没有该声明则不准备就绪。no-mistakes 在后台持续监控 PR，直到它被合并、关闭或其配置的空闲超时到期，所以人类可以在 TUI 中观察它。
   - `passed` - 管道在请求的步骤下完成，包括任何显式的每运行跳过。这本身不是证据表明 PR 已合并。
   - `passed-with-override` - 管道在明确批准的测试异常或 CI 失败的情况下完成。
     报告异常，而不是干净的通过。
     测试证据在 `run.test_override_reason` 中，包括当 CI 准备返回 `checks-passed` 时；不要从摘要中省略它。
   - `passed-with-skips` - 发布或 CI 验证自动跳过。
     报告缺失的证据及其原因，从 `run.automatic_skips`，绑定到完整的 `run.head_sha`。这既不是 CI 准备性也不是失败的代码裁决。显式的每运行跳过保留其现有行为。
   - `failed` 或 `cancelled` - 他们没有；阅读输出并解决它。
     在输出指向的输出之前（一个失败的测试、代码检查错误、你跳过的发现）遵循保管指导。在同一个特性分支上提交修复，然后使用 `no-mistakes axi run --intent "..."` 提交。一个新鲜运行或 `rerun` 是一个 *运行之间* 的操作，只有在终端结果之后才能纠正——永远不会在运行中绕过网关。不要在 `failed` 结果下留下用户而没有重试或解释阻碍它的原因。

`no-mistakes rerun` 保留其现有的头部选择：网关头部，或最新终端运行的已验证未发布的保留头部，而保管仍然未解决。如果已知的干净调用者 `HEAD` 与所选头部不同，它会在开始或覆盖任何运行之前拒绝，并报告两个完整的 SHA。
在拒绝时，检查 `no-mistakes axi status` 并遵循下文的保管指导。脏调用者和没有干净头部证据的调用者保留现有的选择行为。

在进行任何后管道本地提交或全新运行之前，请阅读AXI主页、状态或驱动结果返回的结构的`branch_sync`对象。
只有在其`next_action.code`为`sync`时，才首先运行`no-mistakes axi sync`。
这种受保护的同步可能是一个严格的快速前移，或是一个内容等效的分支前进，它在移动分支之前锚定预同步头；真实的分支差异会被阻止。
如果它报告`next_action.code`为`continue_active_run`，则管道仍然拥有该分支：运行报告的命令，继续驱动活跃运行，不要进行本地后续提交。
当`next_action.code`为`recover_custody`时，运行其确切的`next_action.command`，而不是重建一个。这是`no-mistakes axi sync --recover`，以获取仍然可用的保留的管道头，或在两种保留本地情况下运行`no-mistakes axi sync --recover --keep-local`：当可访问的网关确认已验证的保留头丢失，并且你明确丢弃了这些未发布的提交时；或者当一个绑定的存档证明后续的分支差异工作仍然保留，而恢复将分支保持在精确报告的所需头，并且永远不会选择、合并或重放存档。不要用普通的`--recover`或`rerun`来替代报告的保留本地操作。`no-mistakes rerun`可以继续验证仍然可用的普通保留头，但需满足上述干净头检查。
普通恢复通过快速前移获取该头，或者通过采用一个被证明包含所有本地更改的分支保留头——这是管道将你的提交重新基于一个更新的基础上的普通结果——在将你的预恢复头锚定在`refs/no-mistakes/recover-local/<run>`下之后。
普通的包含证明是故意限制的，因此一个修复轮次也重写了你自己的行的变基会拒绝而不是被采用：当无法区分一个故意的管道修复和一个丢失的更改时，决定权在你。
当`next_action.code`为`recover_remote_rewritten`时，配置的推送目标在终端运行后外部强制重写：运行确切的`no-mistakes axi sync --recover`。它重新验证活动目标，将过时的管道头锚定在`refs/no-mistakes/recover-rewritten/<run>/<generation>`下，并且仅将记录的推送绑定重新绑定到验证的活动头；它永远不会移动你的分支、网关或远程。它拒绝`--keep-local`、在恢复期间变化的活跃头或目标、它无法锚定的头、以及合并或关闭的PR。之后遵循它报告的普通`next_action`。
当`next_action.code`为`adopt_published`时，一个在网关通道停止移动后重新基于的保留分支：运行`no-mistakes axi sync --adopt-published`。它验证配置的推送目标已经具有精确的重新基于的本地头，保留旧通道头，并仅更新那个过时的网关通道。如果目标不同或在验证期间发生变化，它会拒绝而不替换通道。
`branch_sync.state`为`user_owned`意味着运行在更改提交头之前就终止了，并且取消释放了分支：精确的分支和头都是你的，并且可以立即用于任何授权的交付路径——不需要同步操作，重复的`--recover`在那里是无害的空操作。
一个脏的工作树，或无法证明包含的差异，会使恢复拒绝明确的选项；`--keep-local`保留你的当前头，而保留的提交被锚定在`refs/no-mistakes/recover/<run>`下。相同的标志是在一个可访问的网关确认已验证的保留头丢失并且恢复引用兼容时进行的恢复：它在当前本地头处返回所有权，而不需要那个对象。
如果同步被阻止，请处理那个结构化状态，而不是临时重置、暂存、合并、变基、强制或分支替换。
同步后，在顶部提交后续工作，并重新运行`no-mistakes axi run --intent "..."`使用原始用户意图。
这保留了所有先前的网关修复提交，无论其配置的主题如何。

CI步骤故意持续监视PR，所以
`axi run`在检查通过时立即返回`checks-passed`（或一个信任的`no_ci: true`声明覆盖了零检查的存储库）而不是在人类合并上阻塞。永远不要轮询或重新运行等待合并。
永远不要单独将“无CI检查报告”视为绿色。

由于那个监视器保持活跃，一个落后于默认分支的PR或在检查通过后遇到合并冲突——通常是因为另一个PR首先合并——不需要你的任何命令：永远不要手动变基。当CI监视器看到一个实际冲突时，它会**变基到基础、解决它、从Review重新验证，因为变基不能证明与已审查头的连续性，并重新推送分支通过Push**；一个仅仅是落后但仍然干净的PR也需要什么，因为平台会合并它。唯一的例外是当那个监视器不再运行时——PR被关闭、运行被中止或取代、它空闲超时了，或其自动修复尝试耗尽——在这种情况下，用`no-mistakes rerun`恢复，并遵守上述干净头检查。一个接受的重新运行取消了过时的监视器并重新运行完整的管道，包括一个确定性的变基步骤。**不要**使用`no-mistakes axi run`来刷新一个仍然活跃的PR：在`checks-passed`后它会重新附加到运行的监视器（HEAD不变）并返回其输出而不变基。

在成功结果（`checks-passed`或`passed`）下，与用户关闭循环：以简洁、易于阅读的格式总结管道期间发生的事情——验证了什么和发现了什么。如果输出包括一个`fixes`表，则管道修复了原始更改遗漏的发现：承认这些遗漏并明确列出每个修复，以便用户可以轻松地审查它们。

## 升级`ask-user`发现

一个其发现全部为`auto-fix`或`no-op`的网关可以凭你自己的判断来驱动：用`--action fix`或`--action approve`作为适当的响应。但一个标记为`ask-user`的发现是一个属于用户的决定，而不是你的——管道标记它是因为它挑战了他们的故意意图或改变了产品行为。不要自行批准、修复或跳过它。相反，在响应之前停止并把它带到用户那里：

- 将每个`ask-user`发现按管道写入的方式传递给他们——它的`id`、`file`和完整的`description`逐字。不要释义、总结细节或预先判断答案。
- 询问他们想如何进行，然后将他们的决定翻译成匹配的`respond`调用：`--action fix`（通过`--instructions`传递他们的指导）、`--action approve`或`--action skip`。

例外是`--yes`（下面）：它是用户对无监督驱动符合条件的网关的持久同意，因此下`--yes`时，你会自动解决普通的`ask-user`发现，而不是停下来询问。

如果你有明确的自动驱动运行的同意，将`--yes`传递给`axi run`或`axi respond`。对于符合条件的网关，它将可操作的发现——`auto-fix`和`ask-user`一样——视为同意修复它，选择当前所有发现进行一次修复轮次，接受产生的修复审查，并批准只有`no-op`发现的网关。仅在用户要求你无检查地驱动整个运行时使用它。

一个`protected-path-refusal`网关在`--yes`下仍然需要明确的操作员响应。传递它的路径和规则；不要自动修复、批准或跳过它。批准被拒绝。让操作员检查并解决报告的编辑，然后发送`--action fix`重试未完成的步骤。
[受保护路径引用](https://kunchenguid.github.io/no-mistakes/reference/repo-config/#protected_paths)
拥有暂存保护的范围和限制。

一个`test-agent-unvalidated-work`发现意味着一个超时的测试代理留下了提交或更改，这些提交或更改没有在测试轮次中验证。批准被拒绝，所以`--yes`在到达那个网关时停止而不响应。传递发现的名称，不要跳过测试，这会发布那项工作。询问操作员选择：`--action fix`花费另一个代理预算来验证工作，并且`no-mistakes axi abort`停止运行。

## 检查状态

```sh
no-mistakes axi               # 主页视图：当前分支、活跃运行、下一步
no-mistakes axi status        # 完整详细信息加上相关时缓存的branch_sync
no-mistakes axi sync --check  # 验证提议的同步计划
no-mistakes axi sync          # 应用仅提议的受保护同步
no-mistakes axi sync --recover  # 终端运行后返回所有权，留下了未发布的管道提交
no-mistakes axi sync --adopt-published  # 将精确发布的重新基于的头采纳到其过时的网关通道
no-mistakes axi logs --step <name> --full   # 一个步骤的记录发现、完整摘要和完整日志
no-mistakes axi abort         # 取消当前分支的活跃运行
no-mistakes axi abort --run <id>   # 通过id取消特定运行（在其工作树外有效）
```

## 阅读输出

- 输出是TOON：`key: value`对、`name[N]{cols}:`表和`help[N]:`提示。
- `axi status`在省略`--run`时针对你的当前分支：有一个已知的当前分支，隐式解析的`run:`是这个分支。在`other_branch_run:`下的运行是你用`--run <id>`命名属于另一个分支的——永远不要读取其状态或结果作为你自己的工作。在当前分支未知（分离的`HEAD`或分支查找失败）时显式的`--run <id>`在`run:`下渲染不编码任何分支关系。在一个成功的状态响应中，没有任何运行对象意味着这个分支还没有运行，无论最近的运行表列出什么；`error:`响应证明不了运行所有权，所以根据错误行动而不是得出分支是空闲的结论。
- 一个非终端运行对象可能包括`awaiting_agent: parked <duration>`立即在`status`之后；这意味着运行在网关处停泊。只有隐式解析的当前分支网关提供`axi respond`；即使其分支匹配，显式的`--run <id>`状态也是仅用于检查，因为分支可能有一个更新的活跃运行。遵循响应的`help`。
- 一个具有`running`或`fixing`步骤的运行对象可能包括一个`active_steps`表。`active_for`是包含步骤的持续时间；`round_active_for`是显示的执行或修复轮次持续时间，并在修复轮次中重置。没有轮次时间的旧运行将`round_active_for`留空。
- 大多数响应底部的`help`列表告诉你要运行的下一个命令。
- 错误作为`error: ...`在stdout上打印，并带有`help`列表；根据建议行动。
- 退出代码：`0`成功、无操作或正常决定网关，`1`失败或取消的最终结果，`2`错误用法。

一个等待你的`gate:`大致如下——一个命名步骤的`gate:`行、可选的步骤特定字段（如`note`）、一个包含每行发现的一行的`findings[N]{...}:`表，以及一个`help[N]:`列出下一个命令的列表：

```
gate: review
note: Review自动修复默认禁用（auto_fix.review: 0；存储库或全局auto_fix.review > 0覆盖重新启用它），因此阻塞和ask-user审查发现为你的决定而停泊，而不是被无声地自我修复。
findings[2]{id,severity,file,line,action,description}:
  r1,warning,internal/pipeline/executor.go,,auto-fix,Error from os.Remove is ignored
  r2,error,cmd/no-mistakes/main.go,,ask-user,New --force flag bypasses the confirm prompt
help[6]:
  运行`no-mistakes axi respond --action approve`以接受此步骤并继续
  运行`no-mistakes axi respond --action fix --findings <ids>`以让管道修复选定的发现（不要自己编辑文件）
  运行`no-mistakes axi respond --action skip`以跳过此步骤
  运行`no-mistakes axi logs --step review --full`以阅读完整的步骤摘要和日志
  一个长时间运行的调用正在工作，而不是停滞——如果你的harness需要，将其后台化，但运行永远不会自行越过网关。阅读每个返回；在`gate:`上响应；循环直到`outcome:`
  在现有分支顶部提交管道后续工作，以保留每个管道修复提交。永远不要中止并重新启动、重置或替换分支，以丢弃先前的网关修复提交。
```

逐行阅读`action`列：根据你自己的判断决定`r1`（auto-fix）——`respond --action fix --findings r1`将它交给管道修复——但在响应之前停止并将`r2`（ask-user）升级给用户。一个最终状态
显示`outcome: <checks-passed|passed|passed-with-override|passed-with-skips|failed|cancelled>`，没有`findings`表。字段名和确切列可能因步骤和版本而异，所以阅读实际的`findings`标题而不是假设这种布局。
