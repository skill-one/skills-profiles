# 架构顾问

## 核心原则

1. **在推荐前先询问** — 在不了解项目的情况下不要指定架构。先运行问卷来收集关于领域、团队、生命周期和约束的背景信息。
2. **按需调整架构** — 最佳架构是能处理项目实际复杂性的最简单架构。CRUD 应用不需要领域驱动设计（DDD）。初创公司不需要整洁架构（Clean Architecture）。根据实际需求匹配复杂度，而不是愿望。
3. **架构不是永久不变的** — 每个架构都有进化路径。从简单开始，当复杂度要求时再添加结构。记录决策，以便团队知道何时进化。
4. **四种支持的架构** — dotnet-claude-kit 提供了垂直切片架构（VSA）、整洁架构（CA）、DDD + 整洁架构和模块化单体（Modular Monolith）的一流模式。每种都有特定的优势和权衡。

## 架构问卷

在推荐架构前，在以下 6 个类别中提出问题。并非每个问题都适用于每个项目 — 跳过不相关的问题。

### 类别 1：领域复杂度

| # | 问题 | 低信号 | 高信号 |
|---|------|--------|--------|
| 1 | 系统管理多少个不同的业务实体？ | < 10 个实体 | 20+ 个实体且存在关系 |
| 2 | 业务规则是否涉及多个实体交互？ | 规则是按实体 CRUD | 实体组之间存在复杂不变性 |
| 3 | 是否存在多步骤的业务工作流？ | 简单请求→响应 | 悖论、审批链、状态机 |
| 4 | 领域专家是否使用专业术语？ | 通用术语（创建、更新） | 共享语言（承保、裁决） |

### 类别 2：团队与组织

| # | 问题 | 低信号 | 高信号 |
|---|------|--------|--------|
| 5 | 开发团队规模多大？ | 1-3 名开发人员 | 8+ 名开发人员，多个团队 |
| 6 | 不同的团队是否拥有系统的不同部分？ | 单个团队拥有所有内容 | 团队按业务领域对齐 |
| 7 | 团队在 .NET 上的经验水平如何？ | 初级或混合 | 高级，熟悉模式 |

### 类别 3：系统生命周期与规模

| # | 问题 | 低信号 | 高信号 |
|---|------|--------|--------|
| 8 | 预期系统生命周期？ | < 2 年，MVP/原型 | 5+ 年，长期产品 |
| 9 | 每秒有多少并发用户或请求？ | < 100 RPS | 1000+ RPS，可变负载 |
| 10 | 系统是否需要按功能区域独立扩展？ | 均匀负载 | 热点需要独立扩展 |

### 类别 4：监管与合规

| # | 问题 | 低信号 | 高信号 |
|---|------|--------|--------|
| 11 | 是否存在审计追踪或合规要求？ | 基本日志足够 | 完整审计追踪，SOX/HIPAA/PCI |
| 12 | 系统的不同部分是否具有不同的安全边界？ | 单一认证边界 | 多租户，数据隔离 |

### 类别 5：现有代码库

| # | 问题 | 低信号 | 高信号 |
|---|------|--------|--------|
| 13 | 这是绿色田野还是棕色田野？ | 绿色田野，从零开始 | 棕色田野，从遗留系统迁移 |
| 14 | 团队是否遵循现有的架构模式？ | 没有既定模式 | 已建立强规范 |

### 类别 6：集成复杂度

| # | 问题 | 低信号 | 高信号 |
|---|------|--------|--------|
| 15 | 此系统与多少外部系统集成？ | 0-2 个简单 API | 5+ 个系统，复杂的合同 |
| 16 | 是否存在事件驱动或异步通信需求？ | 同步请求/响应 | 事件溯源，发布/订阅，最终一致性 |

## 决策矩阵

将问卷答案映射到架构推荐：

| 配置 | 推荐架构 | 原因 |
|------|----------|------|
| 低领域复杂度，小团队，短生命周期 | **垂直切片架构** | 最小仪式，快速功能交付，易于理解 |
| 低-中领域复杂度，任何团队规模，API 聚焦 | **垂直切片架构** | 功能内聚，每个操作一个文件，适合极简 API |
| 中等领域复杂度，中等团队，长生命周期 | **整洁架构** | 通过项目引用强制边界，可测试的领域，清晰的依赖方向 |
| 高领域复杂度，专业术语，复杂不变性 | **DDD + 整洁架构** | 聚合保护不变性，值对象建模领域概念，领域事件解耦副作用 |
| 多个限界上下文，按领域分团队，独立部署潜力 | **模块化单体** | 模块隔离，独立数据存储，进化路径到微服务 |
| 棕色田野，现有分层架构 | **整洁架构** | 熟悉 N 层架构的团队，保留层分离，更好的依赖方向 |

### 信号冲突时

如果信号指向不同的架构：

1. **默认选择更简单** — 不确定时，从 VSA 开始并进化
2. **领域复杂度优先** — 高领域复杂度会覆盖团队规模和生命周期信号
3. **团队熟悉度很重要** — 熟悉整洁架构的团队会比学习 VSA 更高效，即使 VSA 技术上更简单
4. **合规驱动结构** — 监管要求通常强制更严格的边界（整洁架构或 DDD）

## 模式

### 垂直切片架构（VSA）

按功能组织，而不是按层。每个操作是一个自包含的切片。

```
src/MyApp.Api/
  Features/
    Orders/CreateOrder.cs    # 请求 + 处理器 + 响应 + 端点
    Orders/GetOrder.cs
  Common/
    Behaviors/ValidationBehavior.cs
    Persistence/AppDbContext.cs
```

**最适合：** CRUD 密集型应用，API，MVP，小-中等团队，短-中等生命周期。
**负载技能：** `vertical-slice`

### 整洁架构（CA）

同心圆层，依赖反转。领域在中心，基础设施在边缘。

```
src/
  MyApp.Domain/              # 实体，接口，领域逻辑
  MyApp.Application/         # 用例，DTO，验证
  MyApp.Infrastructure/      # EF Core，外部服务
  MyApp.Api/                 # 端点，中间件
```

**最适合：** 中等复杂度，长期系统，熟悉分层模式的团队。
**负载技能：** `clean-architecture`

### DDD + 整洁架构

整洁架构，搭配战术 DDD 模式：聚合，值对象，领域事件。

```
src/
  MyApp.Domain/              # 聚合，值对象，领域事件，领域服务
  MyApp.Application/         # 用例编排聚合
  MyApp.Infrastructure/      # 持久化，外部服务适配器
  MyApp.Api/                 # 薄端点
```

**最适合：** 复杂领域，专业术语，严格不变性，经验丰富的团队。
**负载技能：** `ddd` + `clean-architecture`

### 模块化单体

独立模块在单个可部署单元中，每个模块内部有自己的架构。

```
src/
  MyApp.Host/                # 连接模块
  Modules/
    Orders/                  # 自己的功能，自己的 DbContext，自己的架构
    Catalog/                 # 可以内部使用 VSA，CA 或 DDD
  MyApp.Shared/              # 仅集成事件合同
```

**最适合：** 多个限界上下文，按领域分团队，未来微服务提取。
**负载模板：** `modular-monolith`

## 进化路径

架构不是一次性决策。系统会进化。以下是常见的迁移路径：

| 从 | 到 | 触发器 | 如何 |
|---|----|--------|------|
| VSA | CA | 领域逻辑超出处理器 | 提取领域 + 应用层，将功能作为用例保留 |
| VSA | 模块化单体 | 出现多个限界上下文 | 将功能分组到模块，添加模块边界 |
| CA | DDD + CA | 不变性变得复杂，原始类型成瘾 | 引入聚合，值对象，领域事件 |
| 单体 | 模块化单体 | 团队互相冲突，共享数据库耦合 | 分割为具有自己的 DbContext 和架构的模块 |
| 模块化单体 | 微服务 | 需要独立扩展，独立部署 | 将模块提取为单独的可部署服务 |

## 反模式

### 为 CRUD 应用选择整洁架构

```
// BAD — 4 个项目，每个功能 6+ 文件用于简单的 CRUD
src/MyApp.Domain/Entities/Product.cs
src/MyApp.Application/Products/CreateProduct/CreateProductCommand.cs
src/MyApp.Application/Products/CreateProduct/CreateProductHandler.cs
src/MyApp.Application/Products/CreateProduct/CreateProductValidator.cs
src/MyApp.Infrastructure/Persistence/ProductRepository.cs
src/MyApp.Api/Endpoints/ProductEndpoints.cs

// GOOD — VSA：1 文件用于简单的 CRUD 功能
src/MyApp.Api/Features/Products/CreateProduct.cs
```

### 处处使用 DDD

```
// BAD — 值对象和聚合用于设置表
public class UserSettings : AggregateRoot  // 过度设计
{
    public ThemeName Theme { get; private set; }  // 值对象用于“暗”/“亮”？
    public void ChangeTheme(ThemeName theme) { /* 领域事件？真的吗？ */ }
}

// GOOD — 简单实体用于简单数据
public class UserSettings
{
    public Guid UserId { get; init; }
    public string Theme { get; set; } = "light";
}
```

### 过早的微服务

```
// BAD — 一开始就拆分为 5 个微服务，2 名开发人员
OrderService (自己的仓库，自己的 DB，自己的 CI/CD)
CatalogService (自己的仓库，自己的 DB，自己的 CI/CD)
IdentityService (自己的仓库，自己的 DB，自己的 CI/CD)
NotificationService (自己的仓库，自己的 DB，自己的 CI/CD)
GatewayService (自己的仓库，自己的 CI/CD)

// GOOD — 先作为模块化单体，有证据时再提取
src/
  Modules/Orders/
  Modules/Catalog/
  Modules/Identity/
  Modules/Notifications/
```

### 跳过问卷

```
// BAD — “我总是使用整洁架构”
用户: “为待办事项应用设置一个新项目”
代理: *立即构建 4 项目 CA 解决方案*

// GOOD — 先询问，再推荐
用户: “为待办事项应用设置一个新项目”
代理: “让我问几个关于您项目的问题来推荐最佳架构……”
代理: *运行问卷，为低复杂度应用推荐 VSA*
```

## 决策指南

| 场景 | 推荐 |
|------|------|
| 新项目，未知需求 | 运行问卷 |
| 简单 CRUD API，1-3 名开发人员 | VSA |
| 中等复杂度，长期，经验丰富的团队 | 整洁架构 |
| 复杂领域，专业术语 | DDD + 整洁架构 |
| 多个限界上下文，多团队 | 模块化单体 |
| 现有 N 层代码库，需要现代化 | 整洁架构（熟悉的迁移） |
| MVP / 初创公司，速度是优先级 | VSA |
| 监管 / 合规性重 | 整洁架构或 DDD（强制边界） |
| 后续需要独立扩展 | 模块化单体（提取就绪） |
