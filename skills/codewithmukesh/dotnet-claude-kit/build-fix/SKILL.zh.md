# /build-fix

## 什么是

工具包的自动迭代循环功能。它通过循环运行、解析失败、按根本原因分类、应用针对性修复、重新运行，将损坏的 `dotnet build`（或失败的 `dotnet test`）驱动变为绿色。它重复执行直到变为绿色或触发保护机制——这与经验丰富的开发者处理一堵红色错误墙的方式相同，但具有硬性限制以防止反复无效操作。

这不是单次修复。它处理级联错误，即修复一个问题会暴露下一个问题。

## 何时使用

- 构建损坏且存在多个编译器错误
- 代码变更或构建修复后测试失败
- 在涉及类型名称、命名空间或签名的重大重构之后
- 更新 NuGet 包后（尤其是主要版本升级）
- 合并存在冲突但未编译的分支后
- 需要手动调整的脚手架或代码生成后
- 用户说：“修复构建”、“让它编译”、“让测试通过”、“继续直到它工作”、“继续修复”

## 如何使用

### 循环规范（适用于每个循环）

1. **有界迭代，始终** — 默认最大 5 次迭代，硬性上限 10（用户“继续”扩展 3 次，不超过 10）。如果 5 次迭代无法解决，问题需要人工判断，而不是第 6 次相同的尝试。
2. **进度或退出** — 每次迭代必须减少错误/失败计数。修复尝试后出现相同错误 = 卡住：停止、报告，并使用不同方法重新规划。永远不要重试已经失败的相同修复。
3. **修复前分类** — 按根本原因分组错误，并首先修复最高杠杆的错误（一个缺少 `using` 可能消除下游的十几个错误）。
4. **每次迭代的透明度** — 报告变更原因：
   `迭代 3/5：通过添加 using System.Text.Json 修复 CS0246，剩余 2 个`。永远不要无声地修改文件。
5. **原子性** — 每次迭代都使代码库状态不比之前更差。如果迭代 3 失败，代码保持迭代 2 的状态。

### 主要流程：构建修复循环（最大 5 次迭代）

1. **构建** — 运行 `dotnet build`，捕获完整错误输出
2. **解析** — 提取每个 `error CS####` 及其文件、行和消息
3. **分类** — 按根本原因分组：

   | 类别 | 代码 | 修复策略 |
   |---|---|---|
   | 缺少 using/引用 | CS0246, CS0234 | 添加 using、包或项目引用 |
   | 类型不匹配 | CS0029, CS1503 | 检查预期类型，强制转换或转换 |
   | API 变更 | CS0117, CS7036 | 检查新签名，更新调用位置 |
   | 可空性 | CS8600–CS8604 | 添加空检查、`?.` 或 `??` |
   | 模糊/重复 | CS0104, CS0121, CS0111 | 限定命名空间，删除重复 |
   | 缺少成员 | CS1061 | 检查拼写，验证成员是否存在 |
   | 缺少实现 | CS0535 | 实现 interface/abstract 成员 |
   | 过时的 API | CS0618 | 用推荐的替代方案替换 |

4. **修复** — 应用针对性修复，优先处理根本原因/最高杠杆错误
5. **重新构建** — 再次运行 `dotnet build`，比较错误计数
6. **评估** — 零错误：运行 `dotnet test` 作为合理性检查，报告成功。错误减少：继续。相同错误：卡住——退出并重新规划。错误增加：回滚迭代，报告回归。

### 变体：测试修复循环（最大 5 次；如果跟随构建修复则最大 3 次）

相同循环，相同保护机制，但使用 `dotnet test --no-build` 作为运行器，并增加一个关键步骤——**修复前诊断**：

1. 阅读测试——理解断言和设置
2. 阅读生产代码——理解实际行为
3. 确定错误位置：错误预期 → 修复测试；生产错误 → 修复代码；设置不完整 → 修复设置；契约变更 → 更新测试以匹配
4. **永远不要削弱断言以使测试通过。**
   BAD: `Assert.Equal(expected, actual)` → `Assert.NotNull(actual)`。
   GOOD: 修复生产代码使原始断言通过。

### 安全保护机制（立即退出）

- **卡住** — 修复后出现相同错误/失败，或计数来回波动（3 → 2 → 3）：报告无法修复的内容和人类应检查的内容
- **回归** — 迭代引入的错误多于修复的错误：回滚其更改，报告
- **级联失败** — 修复一个错误连续两次产生 3 个以上新错误：方法错误，停止
- **关键错误** — 错误的 SDK、缺少项目文件、损坏的解决方案，或测试运行器本身失败：需要人工干预，停止
- **用户中断** — 完成当前迭代，报告进度，询问如何继续

### 其他循环

相同的规范——有界迭代、进度检测、安全保护机制——管理重构传递（`/de-sloppify`：每次目标后验证构建+测试，失败时回滚）和脚手架（`/scaffold`：生成，然后运行嵌套的构建修复和测试修复循环）。嵌套循环获得较小预算（父级 5 → 嵌套 3），最大嵌套深度 2，总预算 15。

### 使用的 MCP 工具

- `get_diagnostics` — 编译器错误/警告按文件或项目范围

- `find_references` — 评估损坏的 API 变更的破坏范围
- `get_project_graph` — 修复引用错误的依赖顺序

## 示例

```
用户: /build-fix

Claude: 运行 dotnet build...
  在 4 个文件中找到 12 个错误。

  迭代 1/5:
  - 6 个错误：缺少命名空间 (CS0246) — 添加 using 指令
  - 3 个错误：类型不匹配 (CS1503) — 更新方法签名
  - 3 个错误：接口未实现 (CS0738) — 包 API 变更

  重新构建... 剩余 3 个错误。

  迭代 2/5:
  - 3 个错误：xunit.v3 升级后的 CS0738
    - IAsyncLifetime.InitializeAsync 现在返回 ValueTask（v2 中是 Task），并且 DisposeAsync 来自 IAsyncDisposable
    - 更新 3 个测试用例到 ValueTask 签名

  重新构建... 0 个错误。构建变为绿色。

  运行 dotnet test... 所有 47 个测试通过。
  添加到 Memory > 包："xunit.v3 IAsyncLifetime 使用 ValueTask 签名"
```
