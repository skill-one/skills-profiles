# /arch-check

## 什么是

验证代码是否仍然与其声称的架构相匹配。
架构会因许多看似合理的小改动而腐化——一个领域项目引入了 EF Core 的引用，一个模块访问了兄弟模块的内部实现，一个端点定义在主机之外。此工作流使用项目图和依赖分析来捕获这种腐化，而不是逐文件读取。

输出：一个包含严重性、文件：行证据和具体修复方案的违规报告——或者一个干净的符合通过。

## 何时使用

- "检查我的架构"、"是否存在层违规"、"依赖方向"
- 发布前或大型功能落地后
- 在不熟悉的代码库上入职，该代码库声称有架构
- 在多人合并到共享模块的团队中定期使用
- 不用于选择架构——那是 `architecture-advisor`

## 如何使用

**步骤 1：建立声明的架构**

按权威顺序：项目的 CLAUDE.md、`docs/decisions/` 中的 ADR，或询问用户。切勿无声地推断——错误的基线会产生错误的报告。支持的四个基线和它们的规则：

| 架构 | 检查的规则 |
|---|---|
| 垂直切片 | 功能不引用兄弟功能；共享代码仅通过显式共享的文件夹/项目 |
| 干净架构 | 领域 → 无；应用 → 仅领域；基础设施 → 应用；API → 应用（永不 API → 基础设施类型，仅接线） |
| DDD + 干净 | 干净规则 + 聚合仅通过根引用；跨聚合领域事件 |
| 模块化单体 | 模块之间除 `*.Contracts` 外无项目引用；跨模块调用通过集成事件或合同 |

**步骤 2：项目级依赖方向（最经济，捕获最多）**

```
get_project_graph()
```

将每个项目引用与基线允许的箭头进行映射。这里单个错误的引用（领域 → 基础设施）是一个关键发现——它使得所有下游违规成为可能。

**步骤 3：循环**

```
detect_circular_dependencies()
```

循环在所有基线中都是违规。报告完整链。

**步骤 4：命名空间级泄漏（抽查）**

项目引用可以干净，但代码仍可能泄漏。探测风险边缘：

```
get_dependency_graph(symbolName: <一个领域实体>, depth: 2)
   -- 领域类型是否拉入了 EF Core、HttpClient 或基础设施命名空间？
find_references(symbolName: <一个模块内部类型>)
   -- 是否从模块外部引用？
detect_antipatterns()
   -- 已知的结构性异味作为支持证据
```

根据基线选择探测：干净 → 抽样 3-5 个领域实体和应用处理器；模块化单体 → 抽样每个模块的内部类型；VSA → 抽样两个或三个功能文件夹内的类型。

**步骤 5：表示边界**

```
get_endpoint_map()
```

端点必须仅存在于主机/Api 层（干净）或在其所属模块内（模块化单体、VSA 功能文件夹）。在应用或共享项目中定义的端点是边界违规。任何未标记的端点认证都会被报告为侧边发现（路由到 `/security-scan` 进行深度处理）。

**步骤 6：报告**

| 严重性 | 含义 |
|---|---|
| 关键 | 错误方向的 项目引用、模块间引用、循环 |
| 高 | 命名空间泄漏（领域使用基础设施/EF 类型）、端点在其层外 |
| 中 | 共享核心逻辑蔓延、通过直接成员访问绕过聚合 |
| 信息 | 未标记的端点认证、值得一看的反模式命中 |

每个发现：证据（文件：行）、为何违反基线、修复方案（移动代码、通过接口反转、引入合同项目、发起集成事件）。提供立即修复关键项。

### MCP 工具使用

- `get_project_graph` — 引用方向审计（骨干）
- `detect_circular_dependencies` — 循环检测
- `get_dependency_graph` / `find_references` — 命名空间级泄漏探测
- `get_endpoint_map` — 表示边界 + 认证态势
- `detect_antipatterns` — 支持结构性证据

## 示例

```
用户: /arch-check

Claude: 基线来自 CLAUDE.md：干净架构（4 个项目）。

  项目图 (get_project_graph)...
  关键  领域 → 基础设施引用（Domain.csproj:14）
            违反依赖规则；使领域无法独立测试。
            修复：反转——在应用中定义 IEmailSender，在基础设施中实现。
  循环 (detect_circular_dependencies)... 无。
  对 4 个领域实体进行泄漏探测...
  高      Order.cs:8 使用 Microsoft.EntityFrameworkCore（领域必须保持无持久化依赖）。修复：将 [Index] 配置移动到 Infrastructure 中的 OrderConfiguration。
  端点图... 23 个端点，全部在 Api。2 个未标记的认证（侧边发现——运行 /security-scan）。

  判定：不符合规范——1 个关键，1 个高。先修复引用；要我立即修复吗？
```

## 相关

- `architecture-advisor` — 选择基线（在此技能有用之前）
- `clean-architecture`, `vertical-slice`, `ddd`, `modular-monolith` 模板 — 被执行的规则
- `/security-scan` — 认证侧边发现的深度
- `/health-check` — 更广泛的报告卡；arch-check 是其架构维度的深度
