# 平台：GitHub

指南 GitHub 用于寄生虫 SEO、GEO（AI 引用）和精选列表创建。GitHub 是一个二级技术权威平台——域名权威高、索引速度快、AI 引用概率非常高。用于存储库、README、GitHub Pages、gists 和 Awesome 风格的导航列表。

**调用时**：在**首次使用**时，如果有帮助，先用 1-2 句话说明这个技能涵盖的内容及其重要性，然后提供主要输出。在**后续使用**或当用户要求跳过时，直接进入主要输出。

## 为什么选择 GitHub 进行 SEO

| 因素 | 影响 |
|------|------|
| **域名权威** | 高 DA；存储库、gists、Pages 排名良好 |
| **快速索引** | 搜索引擎频繁抓取 GitHub |
| **AI 引用** | ChatGPT、Perplexity 在技术查询中引用 GitHub；在 GEO 框架中为二级 |
| **技术专长** | 强大的专长信号；结构化文档成为 AI 参考材料 |
| **跨平台** | 在 Dev.to、Stack Overflow、论坛上分享；扩大可见性 |

## 用例

| 用例 | 格式 | 目的 |
|----------|--------|---------|
| **寄生虫 SEO** | 存储库、README、Pages、gists | 利用 GitHub 权威进行排名和反向链接 |
| **GEO** | 文档、教程、精选列表 | AI 工具引用 GitHub 进行技术答案 |
| **精选 / 导航列表** | Awesome 风格的存储库 | 主题特定的资源目录；反向链接、发现 |

## 表面：个人资料与存储库

| 表面 | 它是什么 | 优化重点 |
|---------|------------|---------------------|
| **个人资料 README** | 同名于用户名的公共存储库；根 `README.md` 在个人资料上渲染 | 个人品牌、旗舰链接、社交证明 |
| **置顶** | 个人资料上最多 **6** 个存储库或 gists | 展示顶级项目；与实体信号（**entity-seo**）保持一致 |
| **每个存储库的 README** | 每个存储库的 **Code** 选项卡上的根 `README.md` | 产品着陆页；安装、证明、CTA |

更改普通存储库的 README 不会更改个人资料横幅，除非该内容是 **个人资料 README** 存储库或从它链接。

### 个人资料 README (`username/username`)

**不等于产品存储库的 README。** 优化用于 **身份 + 导航**，在约 15-40 行渲染内容，除非用户明确要求长篇简历。官方设置：[管理您的个人资料 README](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-github-profile/customizing-your-profile/managing-your-profile-readme)。

| 原则 | 做 | 避免 |
|-----------|-----|--------|
| **长度** | 短、可扫描的段落；**省略目录**，除非文件确实很长 | 应用“产品存储库典型的 500-1,500 字”在这里 |
| **标题** | `###` 块（例如 *我做什么 · 开源 · 找我*）用于快速浏览 | 许多嵌套 `##` + 长篇叙述，没有中断 |
| **链接** | 每个主要 URL 在 **找我 / 连接** 行中**一次**（或徽章**或**一个细长的表格——不要三个都重复相同的目的地） | 在徽章、表格和散文中重复网站/LinkedIn/电子邮件 |
| **存储库块** | **粗体存储库名称** + **≤2 短行** + 最多 **一个**复制粘贴命令（例如 `npx skills add …`）——相同的扫描模式流行个人资料用于“旗舰 OSS”，而无需克隆存储库的完整 README | 完整的功能矩阵、变更日志或安装文档粘贴到个人资料文件中 |
| **布局** | 可选 **居中** 标题（`<div align="center">`）仅用于**名称 + 标语 + 徽章**；正文保持左对齐 Markdown 以提高可读性 | 居中缠绕整个 README |
| **可选小部件** | 紧凑的 Shields（平面样式）；可选 [github-readme-stats](https://github.com/anuraghazra/github-readme-stats) / [star-history](https://star-history.com) — **第三方**，视为**转换/社交证明**，而不是核心 SEO | 当文本中重复相同的 CTA 时，墙壁上的 `for-the-badge` 徽章 |

**最小轮廓（典型个人资料）：**

1. 标题 + 答案优先的标语 (+ 细长的徽章行)。
2. `### 我做什么` — 身份、证明链接（**不**重复后面相同的 URL）。
3. `### 开源` — 粗体存储库链接 + 陈述 + 可选一个代码分隔符。
4. `### 找我` — 单行去重的链接（网站 · 个人简介 · 案例 · 社交 · 电子邮件）。
5. `### 活动`（可选）— 小 **github-readme-stats** + **star-history**；`<img>` 上的 **替代文本**。

参考模式（高信号、低噪音）：扫描优先的个人资料，例如 [alchaincyf](https://github.com/alchaincyf) — 短 `###` 块，粗体产品/存储库名称，一个“找我”集群。

**实体中心模式：** 当这个人有一个规范网站时，在**开头行**领先它，并在 **置顶** / **个人资料 About**（如果使用）中镜像相同的 URL，以便 **网站 ↔ GitHub OSS** 保持一致以进行 **entity-seo**。

### 个人资料 README 检查表（短）

- [ ] H1 + **一个**答案优先的标语（关键词：角色、技术栈、领域）
- [ ] 规范 **外部** 链接（网站、社交、电子邮件）**去重**
- [ ] **置顶** 存储库（≤6）与 README 讲述的故事匹配
- [ ] 可选：**活动** 部分 — 将统计信息 / star-history 组合在同一个标题下，而不是分散小部件
- [ ] **最后更新** 脚注以保持新鲜度（GEO 信号）

## 存储库名称、关于和 README（SEO/GEO 优先级）

**排名权重**（GitHub + Google）：存储库名称 & 关于 ≈ 最高；主题 ≈ 高；README ≈ 高。

### 存储库名称

| 实践 | 指南 |
|----------|-----------|
| **描述性** | 暗示项目做什么 |
| **关键词丰富** | 包含主要关键词（`markdown-editor` 而不是 `my-project`） |
| **连字符** | 分隔单词（`react-component-library`） |
| **简洁** | 短 = 易记、可分享 |

### 关于部分（描述）

| 限制 | 指南 |
| **350 字符** | 硬限制；GitHub 强制执行 |
| **~128 字符** | 最佳简洁性；通常完全显示 |
| **内容** | 主要关键词 + 自然变化；它是什么，它为谁服务；如果空间允许，链接到网站或文档 |

**示例**： "一个快速、轻量级的 Markdown 编辑器，用于 React，具有实时预览、语法高亮和导出到 PDF。使用 TypeScript 构建。"

### 主题

| 限制 | 指南 |
| **6-20 个主题** | 最大 20；6-10 个推荐 |
| **~50 字符** 每个主题 | 格式 |
| **格式** | 小写、连字符、数字 |
| **混合** | 技术（react、python）、目的（cli、库）、类别（seo、ai-tools）、社区（hacktoberfest） |

**未充分利用** 但对发现和 GEO 非常有效。

### README 结构和组件

针对 **存储库（项目）README**，除非另有说明。**个人资料 README** 覆盖：更短，更少的部分——见 **个人资料 README (`username/username`)** 以上。

| 部分 | 目的 | SEO/GEO |
|---------|---------|---------|
| **标题 + 标语** | H1 + 1-2 句话总结；第一段包含关键词 | 关键；前 100 字加权重 |
| **目录** | 链接到 H2/H3；**用于长存储库 README**（通常 >500 字）。**通常在个人资料 README 上跳过** | 导航；可爬性 |
| **安装 / 快速入门** | 前提条件；确切命令；准备好复制粘贴 | 用例清晰度 |
| **使用示例** | 代码块；常见场景 | 可引用；可提取 |
| **截图 / GIF** | 演示、输出；需要替代文本 | 参与度；可访问性 |
| **徽章** | 构建、版本、许可证 | 信任信号 |
| **贡献** | 链接到 CONTRIBUTING.md | 社区信号 |
| **许可证** | 链接到 LICENSE | 完整性 |

**字数**：没有硬限制；**500-1,500 字** 典型用于 **产品 / 库** 存储库。先提供价值；稍后扩展。**个人资料 README**：优先 **密集简洁**——长篇属于规范网站或在置顶存储库的自己的 README 中。

### README GEO / AI 引用

| 实践 | 指南 |
|----------|-----------|
| **答案优先** | 在前 1-2 句话中直接回答（40-60 字）；**个人资料 README** 可以压缩到 H1 下 **一个响亮的标语**，如果外部链接承载其余部分 |
| **短段落** | 最多 2-3 句话；可提取的清晰度 |
| **问题式标题** | H2/H3 作为问题，在相关的地方（**存储库 README**）；在 **个人资料 README** 中，可选——**部分的清晰度** 比问题措辞更重要 |
| **数据包含** | 统计数据、数字；引用内容 ~40% 更可能包含数据 |
| **新鲜度** | 定期更新；~76% 的引用内容在 30 天内更新 |

**实体信号**：清晰的项目名称、作者、维护者；一致的标识。见 **entity-seo**。

### README 检查表——**存储库（默认）**

- [ ] 项目标题包含关键词
- [ ] 第一段简洁的描述
- [ ] H2/H3 结构；图像的替代文本
- [ ] 安装 + 使用示例
- [ ] 截图或演示
- [ ] 徽章；贡献；许可证
- [ ] 内部链接到相关文档/存储库
- [ ] 6-20 个主题在存储库

## GitHub 上的寄生虫 SEO

### 关键表面

| 表面 | 用途 |
|---------|-----|
| **README** | 存储库的着陆页；关键词优化的摘要、标题、链接 |
| **GitHub Pages** | 静态网站；博客、FAQ、文档；额外的排名机会 |
| **Gists** | 微内容；长尾关键词；链接到存储库或外部资源 |
| **Wiki** | 关键词丰富的文档 |
| **问题** | Q&A、讨论；可索引 |

### GitHub Pages 与 README

| 表面 | 角色 |
|---------|------|
| **README** | 第一印象；星星/分支；简短陈述和深度链接 |
| **Pages** | 多页 **静态** 网站：长文档、博客、变更日志 |

**默认 URL 模式**：用户或组织网站通常使用 `username.github.io` 存储库，并在 `https://username.github.io` 上提供。项目网站从给定的存储库发布，通常显示在 `https://username.github.io/repository/`（路径可能因设置而异）。见 [关于 GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages)。

**限制**：构建大小、带宽和构建频率限制随时间变化——当用户需要数字而不是这个技能的硬编码数字时，引用 [GitHub Pages 限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)。

### 优化

| 元素 | 实践 |
|---------|----------|
| **存储库标题** | 主要关键词；描述性；连字符 |
| **关于** | 350 字符最大；关键词丰富；主要关键词 + 自然变化 |
| **描述** | 次要关键词；链接到网站或资源 |
| **README** | 关键词优化的摘要首先；标题、项目符号；截图；链接到文档、教程 |
| **主题 / 标签** | 6-20 个相关主题；每个 50 字符 |
| **GitHub Pages** | 移动友好；元数据；博客/FAQ 以便额外的关键词 |

### Gists 用于微内容

- 针对特定的长尾关键词
- 链接到更大的存储库或外部资源
- 分享代码片段、小工具

### 社区参与

- 回应问题和 PR；建立信任
- 为热门项目做出贡献；反向链接、可见性
- 保持存储库更新；过时 = 较低可信度

## GitHub 上的 GEO

| 因素 | 实践 |
|--------|----------|
| **README 清晰度** | 清晰、可引用的段落；直接答案 |
| **文档** | 结构化；AI 工具解析良好 |
| **实体信号** | 清晰的项目、作者身份；见 **entity-seo** |
| **一致性** | 积极维护；参与（星星、分支、观察者） |

## 存储库原型

| 原型 | 意图 | 首屏重点 |
|-----------|--------|------------------------|
| **产品 / 库** | 可安装的软件、SDK、CLI、服务 | 安装、快速入门、证明（CI、许可证）、支持路径 |
| **精选 / 资源** | Awesome 风格的列表、索引 | 范围、策展条、贡献规则 |
| **个人资料中心** | 个人资料上公共 **`username/username`** README | 身份 + 规范链接 + **置顶** 旗舰存储库；**不**重复完整产品 README |

根据类型匹配指标：精选列表优化用于信任和反向链接；产品存储库优化用于采用和问题质量。

## 精选 / 导航列表（Awesome 风格）

**Awesome 列表** = GitHub 上的精选、主题特定的资源列表。像导航目录一样；高流量、反向链接、发现。 sindresorhus/awesome（441K+ 星）是主列表；6,500 多个精选列表存在于各个主题中。

### 按类别示例

| 类别 | 示例 |
|----------|----------|
| **主列表** | sindresorhus/awesome — 所有 Awesome 列表的中心 |
| **SEO / 营销** | awesome-seo, awesome-ai-seo, bmpi-dev/awesome-seo |
| **AI / ML** | awesome-ai-tools, AITreasureBox, awesome-ai |
| **开发工具** | awesome-tools, awesome-cli, awesome-nodejs |
| **语言** | awesome-python, awesome-javascript, awesome-go |
| **前端 / 后端** | awesome-react, awesome-vue, awesome-django |
| **其他** | awesome-security, awesome-gaming, awesome-databases |

### 创建时机

- 您有一个具有许多高质量资源可以策展的细分领域
- 现有列表缺乏您主题的覆盖
- 您想获得反向链接资产和主题权威

### 列表结构（sindresorhus/awesome 指南）

| 元素 | 实践 |
|---------|----------|
| **标题** | 清晰、专注（例如，"Awesome SEO"、"Awesome AI Tools"） |
| **描述** | 简洁；范围清晰 |
| **部分** | 分类（例如，教程、工具、文章） |
| **项目** | 策展，而不是收集；只包含您推荐的内容 |
| **项目格式** | `- [名称](URL) - 简要描述为什么它很棒` |
| **许可证** | CC0 或类似 |
| **贡献** | contributing.md 用于 PR 过程 |

### 被列入与创建

| 操作 | 用途 |
|--------|-----|
| **提交到现有列表** | PR 到 awesome-* 存储库；遵循列表格式；联系维护者 |
| **创建新列表** | 当您的细分领域没有列表时；遵循 awesome 指南 |
| **列表之间链接** | 链接到其他 Awesome 列表，这些列表更好地覆盖了主题 |

### 发现

- **sindresorhus/awesome** — Awesome 列表的中心列表
- **AwesomeSearch** — 跨 Awesome 列表搜索
- **more-awesome** — Awesome 列表目录

## 常见错误

| 错误 | 避免 |
|------|------|
| **忽视互动** | 不回应问题/PR会降低信任 |
| **更新不规律** | 过时的仓库会显示不活跃 |
| **文档不完整** | 缺乏清晰的描述会让用户沮丧 |
| **标题泛泛** | 缺少关键词会降低可发现性 |
| **精选列表质量低** | 低质量或未经筛选的项目会损害信誉 |
| **个人资料README = 产品README** | 在`username/username`上粘贴安装/贡献/截图为主的模板 — 使用**个人资料**清单 |
| **个人资料链接泛滥** | 相同的网站/社交媒体/电子邮件在徽章、表格和长文本中重复出现 — 整合 |

## 输出格式

- **使用场景** (寄生SEO / GEO / 精选列表)
- **表面范围** (个人资料 vs 特定仓库；README vs Pages)
- **仓库名称、关于、主题** (如果优化元数据)
- **表面** (README、Pages、gist、精选仓库)
