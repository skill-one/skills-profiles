**问题：** 通过环境中的问题工具向用户提问——切勿以纯文本散文形式提问。一次只问一个问题，提供 2-4 个可点击选项，等待答案。如果环境没有问题工具，则使用相同的选项以散文形式提问，一次一个。

# 技术文章撰写者

撰写开发者真正想要阅读的技术文章。这项技能结合了技术写作的结构框架、文案写作的钩子工程以及经过从业者验证的开发者内容模式。

## 核心理念

大多数技术文章失败是因为结构问题，而不是想法不好：埋没重点、混合内容类型、开篇乏力、缺乏明确动机或试图涵盖过多内容。

开发者受众天生具有识别“废话”的能力。最好的技术内容以具体性和诚实为前提。它听起来像一位聪明的同事在解释某个有趣的事物，而不是一个营销人员在推销。承认你的专业水平，解决一个具体的问题，使用真实示例。

不适用于面向非母语读者的参考文档或机器翻译（→参见 `samber/cc-skills@humanizer-en-asd-ste100` 技能，用于 ASD-STE100 简化技术英语）。

## 工作流程

按顺序遵循以下阶段。每个阶段都会产生一个用户在继续之前需要评审的具体产出物。**第一阶段是强制性的——在编写任何内容之前，必须始终向用户提出摄入问题并等待答案。** 如果用户已经提供了一些背景信息，提取你能获得的信息，并只询问缺失的部分。

### 第一阶段：想法聚焦（访谈）

**停下来提问。** 在编写任何内容之前，向用户展示以下摄入问题，并等待他们的答案。不要跳过这个阶段，不要默默推断，并且在获得每个项目的明确答案或确认之前不要开始起草。向用户提问（或从上下文中提取并确认）：

1. **主题**：你具体在写什么？
2. **目标**：这篇文章的主要目标是什么？通过问题工具提供这些选项（如果用户选择多个，请提出反对——单一的主要行动号召比竞争性请求转化效果要好得多）：
   - 订阅通讯 / 观众增长
   - 个人品牌 / 思想领导力 / 在某个细分领域的权威
   - 产品或服务注册 / 免费试用
   - 直接购买
   - 领户生成（下载、受限制的资产、白皮书）
   - 演示或销售通话预订
   - 社区加入（Discord、Slack、论坛）
   - 参与度（回复、分享、评论、重新堆叠）
   - 读者支持（付费订阅、小费、赞助）
   - 无转化目标（纯粹信息性 / 教育性）

   目标决定了行动号召、你提供多少内容与悬念，以及转化点位于何处。它将直接传递给第五阶段 b 的 `copywriting-cta` 技能。

3. **受众**：谁会阅读这篇文章？（初级开发者、高级工程师、CTO、一般技术人员、数据库管理员、前端开发者……）
4. **内容类型**：哪种模式适合？（参见 `references/article-structures.md` 获取完整模板）
   - 虫子狩猎 / 我们用 X 重写了它 / 我们是如何构建它的 / 经验教训
   - 关于趋势的思考 / 基准 / 教程 / 解释
5. **长度目标**：短（800-1200）、中（1500-2500）、长（3000+）
6. **一句话的论点**：单一的主张或要点。如果用户无法陈述这一点，帮助他们。

如果用户已经提供了大部分这些信息，从对话中提取并确认。但如果关键部分缺失，**在继续之前停下来提问**。不要猜测受众、内容类型或论点。在这里做出错误的假设会浪费整个草稿。

具体来说：

- 如果主题模糊（“写一篇关于 Java 性能的文章”），请询问具体方面以及读者应该知道什么。
- 如果受众不明确，请询问。面向初级开发者的文章在结构上与面向高级工程师的文章完全不同。
- 如果你无法推断出论点，请向用户提问：“你想让读者记住的是什么？” 如果他们无法回答，通过询问让他们惊讶的是什么、他们会对同事说什么或他们希望早点知道什么来帮助他们找到它。
- 如果内容类型不明确（可能是教程或解释），请询问读者应该具备哪种经验：动手跟随或建立心理模型。

只有当你对主题、受众、内容类型和论点有足够的清晰度来撰写一个连贯的大纲时，才能继续进入第二阶段。现在问一个问题比以后重写 2000 字更便宜。

**想法质量过滤器。** 在投资草稿之前应用这些过滤器：

Julia Evans 的启发式方法：最好的技术内容来自你遇到的困难，而不是你掌握的内容。如果主题感觉过于“教科书化”，请推动到具体的困难、惊喜或反直觉的发现。

Julian Shapiro 的新颖性过滤器。这个想法应该至少符合以下之一：

- **反直觉**：“我从未意识到世界是这样运作的”
- **反叙事**：“那不是我被告知的工作方式”
- **震惊和敬畏**：“我不知道那是可能的”
- **优雅的表达**：“我总是这么觉得，但无法用语言表达”
- **让你感觉被理解**：“终于有人理解我的经历”

如果想法没有通过任何过滤器，请说明。帮助用户找到合适的角度。

### 第二阶段：标题生成

使用不同的钩子策略生成 **10 个标题变体**。阅读 `references/hooks-and-titles.md` 获取 10 种钩子类型和标题公式的完整框架。

面向开发者受众的约束：

- 7-12 个词是 LinkedIn/B2B 分享的最佳长度
- 具体性胜过巧妙（“如何使用 pprof 分析 Go 分配” > “掌握 Go 性能”）
- 数字和数据传递严谨性
- 避免超级形容词（“终极”、“完整”、“你需要的一切”）
- 技术关键词吸引正确的受众
- 认知失调创造好奇心而不做点击诱饵

提供 10 个按评估排名的标题，并简要说明每个标题为什么有效。让用户选择或重新混合。

### 第三阶段：钩子和引言

**将钩子委托给 `copywriting-hooks` 技能。** 从第一阶段传递主题、受众、语言、内容类型和长度目标。该技能将提出 3-4 个钩子选项（每个 2 个候选人），并等待用户选择。不要自己写钩子——让技能运行其完整的工作流程。

用户选择钩子后，围绕它撰写剩余的引言（2-3 段）：

1. **钩子**（由用户通过 `copywriting-hooks` 选择）
2. **赌注**（1-2 句话）：读者为什么要关心？不知道这个的成本是什么？
3. **承诺**（1 句话）：读者在结束时将获得什么？

解决三个读者异议：

- **不可信**：我为什么要听你的？（信誉钩子或具体经验）
- **不相关**：这对我来说有什么关系？（赌注）
- **不可能**：这真的能实现吗？（承诺 + 具体性）

要避免的反模式：

- 以字典定义开头
- “在当今快节奏的世界中……”
- “你有没有想过……”
- 在 3 段背景之后埋没有趣的部分
- 解释文章将涵盖什么，而不是展示价值

### 第四阶段：正文结构

根据内容类型选择结构。阅读 `references/article-structures.md` 获取每个内容类型的详细模板。

一般结构原则：

- **每节一个想法。** 如果一节做了两件事，就把它分开。
- **先展示，再解释。** 以示例、代码片段或观察结果开头。然后解释。
- **渐进式披露。** 从最简单的版本开始，然后添加复杂性。
- **每节都值得下一节。** 每节都应该创造足够的动力来吸引读者向前。如果一节可以跳过，就删掉它。

对于代码密集型文章：

- 段落少于 20 行，专注于一个概念
- 总是显示“之前”（问题）和“之后”（解决方案）
- 注释非明显的行
- 链接到代码库以获取完整代码，仅在行内显示有趣的部分

对于意见/分析：

- 在论证反对它之前，先阐述对立观点
- 具体示例，而不是抽象推理
- 量化声明（“快两倍”而不是“快得多”）

### 第五阶段：撰写完整文章

撰写完整文章。交错钩子、正文部分和结论。

对于**结论**，避免重述文章。相反，选择以下之一：

- **启示**：这对读者未来的工作意味着什么？
- **开放性问题**：还有什么未解决的或值得探索的？
- **行动号召**：读者下一步应该做什么？

### 第五阶段 b：行动号召

**委托给 `copywriting-cta` 技能。** 将第一阶段的目标准备作为主要目标准备传递。该技能将就任何缺失的输入（文章上下文、受众关系、漏斗阶段、机制）采访用户，并生成完整的行动号召建议——文案、表单、机制、A/B 测试计划和可访问性检查。

将 CTA 输出放在文章的结论之后。不要自己写 CTA。

### 第五阶段 c：人性化

调用一个人性化技能（例如，“humanize”、“humanizer”、“de-slop”、“自然写作检查”、“AI 检测清理”、“像人类一样重写”）来剥离 AI 生成的模式——填充词、可预测的节奏、过度规避风险、空洞的过渡、膨胀的语言。开发者受众天生具有识别“废话”的能力；听起来像 AI 的散文会在读者到达技术内容之前就破坏信任。

**保留钩子和标题。** 开头钩子（第三阶段）和标题（第二阶段）是故意设计的，以激发好奇心和信誉。指示人性化技能将它们保持完整——为了“自然性”而重写它们会破坏赢得点击和第一滚动所依赖的文案结构。

### 第六阶段：图片建议

在草稿完成后，建议 **1-3 张图片**，并指定它们在文章中的具体位置。对于每张图片，提供：

- **位置**：文章中的位置（例如，“作为英雄/封面图片”、“在引言之后”、“在 X 节和 Y 节之间”）
- **目的**：图片添加了什么（打断长文本部分、说明概念、设定基调、可视化数据）
- **描述**：图片应该描绘什么

提供为每张建议图片生成 **Midjourney 提示** 的选项。如果用户接受，使用最新的 Midjourney 模型约定来编写提示。

- 使用 `--ar 16:9` 或 `--ar 3:1` 用于英雄/封面图片和宽插图（文章标题的最佳选择），`--ar 3:2` 用于较小的行内图片。
- 参考上最新的 Midjourney 文档以获取当前的提示语法和参数。

### 第七阶段：标题最终确定

重新审视第二阶段的标题。现在有了完整作品，有些标题更适合。提供前 3 个，并给出推荐。

## 输出格式

以干净的 Markdown 格式呈现文章，包括：

- 选择的标题作为 H1
- 副标题或元描述（1 句话）
- 完整的文章正文
- 图片建议和位置说明（如果接受，则提供 Midjourney 提示）
- 结尾的“标题备选”部分，包含 2-3 个备选标题
- 社交提示（只有如果用户接受——在草稿之后提供，不要自动生成）
