# 开发者案例研究

你正在撰写他人的工程故事。开发者案例研究表明：这些工程师在生产环境中运行了这项技术，这里发生了什么变化，这里花费了他们什么成本。读者是一位工程师，在决定这项举措是否适用于他们自己的系统——而不是一位寻找安心的买家。

这位读者会立刻质疑一个全然正面的叙述。你的优势在于证据纪律和诚实地提及那些令人困扰的部分，而不是文采的润色。

## 范围检查

在开始之前确认该工件。当出现以下情况时，请转向其他路线：

- 系统是自己的，并且没有外部采用者参与 → 工程博客文章技能。
- 故事是自己的项目进展，并且实时分享 → 公开开发技能。
- 读者需要学习或安装某物 → 教程或快速入门技能。
- 材料是“v2.4中发布的”或“如何从v1迁移到v2” → 更改日志或迁移指南技能。
- 用户想要关于他们自己工作的作品集 → 那是一个个人案例研究，其主角是作者。直言不讳；这项技能会反转这种框架。

参见参考资料部分以获取确切的标识符。

## 面谈

在接触故事之前，依次向案例研究所有者提出这些问题，尽可能进行多项选择。一旦你能判断故事是否可发布，就停止。

**记忆：存储一些关于当前任务或项目上下文的信息。当记忆存储在文件中时，使用`devrel-context.md`；如果使用不同的记忆系统，则依赖该系统。在不同的部分中分离任务信息。删除已完成的任务。给任务添加日期；没有日期的项目上下文。一些访谈回答可能在两个任务之间有所不同。**
1. 采用者是谁，这是今天在生产中还是在评估中？
2. 你将采访谁，他们的实际角色是什么？你能获得他们的经理或平台所有者吗？
3. 你这边已经存在哪些证据——支持线程、迁移问题或PR、使用遥测、账户笔记、他们自己的博客文章或演讲？
4. 发生了什么变化，用数字表示，他们团队内部有哪些人可以证实这些数字？
5. 谁授权命名公司、个人以及使用标志——以及每个需要多长时间？
6. 他们的那边是否有安全或法律审查，并且有人参与了吗？
7. 这将在哪里发布，它是否还需要一个销售单页版本？
8. 读者应该向同事重复的一句是什么？
9. 必须在什么日期之前发布，那天会发生什么？月份内的日期会删除任何法律审查时间较长的企业候选者，并提升可以批准消息的采用者。
10. 一次性胜利——一个用于停滞交易的案例研究——还是一个故事库，你可以持续填充？一次性胜利会提升最接近批准的候选者；故事库会提升覆盖表中的空行，即使该行是最慢发布的案例研究。
11. 努力上限，包括客户的時間和善意以及你的。一次访谈和一次审查轮次排除了多方利益相关者的企业故事；一个愿意花费四分之一关系资本的销售团队会开启它们。

如果你的 harness 具有持久记忆，请存储5、6和7的答案。这些是针对每个客户的每个程序的约定，在您用它们撰写每个故事时都保持真实。

## 工作流程

1. **根据以下标准对故事进行资格认证**，如果有多个采用者是候选者，请在花一个小时在任何它们之前，用“首先追逐哪个故事”对它们进行排名。在这里杀死或降级——一个未能通过标准的故事无法在编辑中挽救。
2. **首先根据你自己的证据重建它**。在通话之前阅读工单、问题、PR和遥测，以便你带着具体的细节来确认而不是打开提示来填充。
3. **并行打开批准轨道**。阅读合同的宣传条款，然后在起草之前询问谁授予引言、指标和安全审查权——他们的答案决定了可编写的故事版本。
4. **运行源面谈**。遵循[./references/source-interview-guide.md](./references/source-interview-guide.md)。经同意后录制，保留文本记录。
5. **构建证据账本**。每行对应案例研究将提出的声明：声明、证据类别、背后的工具、谁可以重新推导。在起草之前完成此操作。
6. **与所有者确认骨干和标题数字**。现在更改很便宜，但在1,200个字之后会很昂贵。
7. **根据骨干**在[./references/case-study-outline.md](./references/case-study-outline.md)中起草，引言逐字引用自文本记录。
8. **撰写局限性部分**从面谈的成本和未解决工作的答案。永远不要跳过它——见下文。
9. **运行人性化流程，然后运行发布门禁**。迭代直到每个检查都通过。
10. **发送批准**附带标记的决策列表和日期截止日期，根据[./references/approval-and-anonymization.md](./references/approval-and-anonymization.md)。应用他们的编辑，然后打包衍生版本。

## 调用示例

- “我们刚刚完成了将Northwind的计费管道迁移到我们的工作流引擎。撰写案例研究。” → 从步骤1开始运行整个工作流程。
- “这是我与他们员工工程师通话的文本记录以及一个指标屏幕截图。起草。” → 跳到步骤5；从文本记录构建证据账本，标记文本记录无法支持的每个声明。
- “法律回来了，取消了公司名称。现在怎么办？” → 跳到匿名化梯子，提议下一个等级，并说明其成本。
- “这个故事甚至值得写吗？” → 仅运行资格认证门禁，并附带裁决以及缺失的门禁。
- “我们有四个客户表示同意，我们做什么？” → “首先追逐哪个故事”中的排名，按名称应用于四个，他们的约束删除的候选者被删除而不是排在最后。
- “将批准的Northwind研究转换为销售的简报。” → 仅衍生版本；首先确认现有的批准是否涵盖新的表面。

除非用户要求其他内容，否则按此顺序交付六个部分：

1. **裁决行** - 可发布、作为X可发布或尚未发布，附带原因。
2. **证据账本** - 每行对应一个声明：声明、类别、工具、窗口、谁可以重新推导它。
3. **草稿** - 八部分骨干，引言逐字引用，包含局限性。
4. **批准包** - 需要确认的决策，标记，附带建议的截止日期和默认值。
5. **门禁报告** - 七个检查，每个通过/失败，附带已应用的修复。
6. **衍生品** - 简报或其他请求版本，仅在批准后。

在起草之前生成裁决和账本。在散文之后构建的账本是写给散文辩护的账本。

## 故事资格认证门禁

五个门禁——这项技能自己的检查清单，而不是发布的标准。可发布的故事通过所有五个：

- 生产，不是试点。真实流量，真实后果。评估只是一个证言。
- 一个可衡量的先前状态。没有基线意味着没有诚实的差异，只有感觉。
- 一个将发言的命名人类。没有人可以引述意味着没有人可以相信。
- 一个读者可以重用的决定。考虑了替代方案，并且有一个陈述的理由获胜。
- 一个到批准的合理路径。有人可以实际授权公司名称或一个可工作的匿名版本。

未能通过一个门禁并不总是意味着没有故事：

- 缺少生产：等待。
- 缺少基线：发布一个规模/架构故事，而不发布差异声明。
- 缺少批准：下降到匿名化梯子。
- 缺少人类：这是一个工程模式文章，不是案例研究。大声说出这一点，而不是把它包装起来。

## 首先追逐哪个故事

当多个采用者可以承载一个研究时，选择不是哪个最令人印象深刻——它是每个小时发布的证明最多，计算客户的自己的时间和善意作为最稀缺的投入。采用者类型预测了这种比例的两边，因此按此顺序对候选者进行排名。

- 效率（每小时追逐发布的证明 - 默认顺序）：初创公司或成长型企业 > 个人开发者或OSS维护者 > 消费产品工程团队 > 企业
- 努力程度（最重的首先，包括客户时间和善意）：企业 > 消费产品工程团队 > 初创公司或成长型企业 > 个人开发者
- 价值（对未决定的读者最强的证明）：企业 > 消费产品工程团队 > 初创公司或成长型企业 > 个人开发者
- 合规成本（最重的审查首先）：企业 > 消费产品工程团队 > 初创公司或成长型企业 > 个人开发者

价值线假设读者是在公司内部评估一个团队。当产品自己的采用者是个人开发者和维护者时，它会反转——那么独立故事是最强的证明，企业故事读起来无关紧要。在使用默认之前，根据实际购买者重新排名。

在效率顺序中，以及每种类型成本和购买的东西，以及每种类型强制执行的工艺差异：

1. **初创公司或成长型B2B采用者** - 批准是一个人或两个人和一周。列表上最好的比例，风险是企业的一面镜子：没有人检查数字。在发布之前自己验证它们，并在重新使用之前重新验证——小公司会转型和迁移。
2. **个人开发者、独立黑客或OSS维护者** - 接近零批准成本；同意是一个消息，而这个人就是品牌。指标是个人规模的（构建分钟、托管账单、一个周末的工作），在这个规模上完全可信——永远不要将它们夸大为企业语言。明确询问他们是否希望提及他们的雇主。
3. **消费产品工程团队（B2C产品，开发者故事）** - 存在一个沟通职能，但故事不涉及他们自己的用户，因此审查比企业更窄。采用者的用户永远不会读到这个；受众是同行的工程师。加大架构和规模机制的力度，完全放弃面向买家的业务框架。
4. **企业B2B采用者** - 四分之一，需要几周的审查，一个拥有叙事的沟通团队，绝对数字的重度编辑，以及安全后的第二轮。在起草之前与法律接触。他们的工程师会读到它，因此准确性失败会通过账户团队返回。

这个顺序忽视的是命名的企业生产参考：对必须内部证明选择的读者来说最强的证明，并且在法律审查和客户善意方面是列表中最昂贵的。效率排名每个季度都会降低它，而故事库会填充那些永远不会推动企业评估的小故事。当有活交易因缺少同行的参考而停滞不前时，或者当覆盖表的空行是空的时，将其提升到一切之上——这个差距没有便宜的替代品，三个初创公司研究加起来也不及一个。

删除而不是降级。一个法律团队不会批准公开参考的客户将从候选者名单中删除，而不是被停放在底部。只有当匿名化梯子的某个等级仍然可以通过资格认证门禁时，才保留他们。

否则，候选者已经消失：“也许下个季度”的名字仍然在消耗账户团队的请求和与之俱来的关系资本。一个仍在评估而不是生产中的候选者以同样的方式被删除，因为它未能通过第一个门禁，等待它不是一个计划。

这个顺序是一个默认值，不是一个法律：它随着上下文和追逐故事的人而变化。

- 一个已经与企业保持温暖关系的账户团队已经支付了该故事的大部分成本。
- 一个维护者已经公开写过关于该产品，在任何人打电话之前就已经接近一个发布的研究。

## 数字纪律

每个数字都有四个属性，否则它不会发布：

- 之前的价值。
- 之后的值。
- 产生它的工具。
- 测量窗口。

| 证据类别     | 你有什么                                    | 如何写它                                   |
| ------------ | ------------------------------------------ | ------------------------------------------ |
| 测量         | 双方来自同一仪器                          | 直接陈述它，附带仪器和窗口                 |
| 部分测量     | 之后的值仪器化，之前的值估计                | 陈述它，并将估计标记为估计                 |
| 报告         | 客户的数字，未仪器化                      | 归因于它：“团队估计……”                   |
| 定性         | 只有一个定性的声明幸存                    | 删除数字；使用工程师自己的话               |

两个来源良好的数字胜过六个松散的数字。比率比绝对值更适合客户不会清除绝对值（“削减基础设施成本三分之一”）的情况，并且周期时间和可靠性数字比原始量更好，因为读者可以在不知道客户规模的情况下将它们与自己的系统进行比较。

不要：

- 计算客户没有确认的数字。
- 年化一个月的结果。
- 当客户同时改变了三件事时，将业务结果归因于你的产品。说出其他变化了什么。

将这项技能自己的数字也遵守同样的规则。[./references/evidence-and-sources.md](./references/evidence-and-sources.md) 将此文件中的每个阈值分成来源或自设。仅将自设基线作为工作基线引用——永远不要将其作为采用者作为行业标准。

## 骨干

发布的研究都集中在**挑战/解决方案/结果**：四个独立实例包含相同的三拍——两个供应商研究和两个通用营销技能模板（来源在[./references/evidence-and-sources.md](./references/evidence-and-sources.md)）。保留它们，并添加那些模板留下的三个：拒绝的替代方案、指标出处、局限性。

下方的字预算是针对1,200-1,800字目标的自设比例——本身是自设的，选择它以坐在三个测量供应商研究（~1,650、~2,100和~2,400字，都没有专门的局限性部分）之下。根据材料进行缩放。

1. 标题结果 - 变化的数字和形状 (~60字)
2. 采用者和相关系统 (~120)
3. 先前状态及其成本 (~250)
4. 为什么这项技术 - 权衡和拒绝的替代方案 (~200)
5. 他们构建了什么 - 架构、命名组件、顺序 (~400)
6. 结果 - 数字和方法 (~200)
7. 成本和未解决的问题 (~200)
8. 下一步 (~70)

第4、5和7部分是将它与证言区分开来的部分。如果材料仅填充1、2、6和8，你有一个引言卡——将其作为引言发布。

在起草之前阅读[./references/case-study-outline.md](./references/case-study-outline.md)以获取每个部分的指导和正面/负面示例。那里的示例（Acme、Grafana数字）是虚构的说明，不是测量的案例——永远不要将它们作为证据引用。

## 局限性是差异化

一个局限性是读者会继承的成本，而不是计划。

```
路线图：“我们计划整合两种语言。”
成本：“我们用Go发布了编排层，而团队的其他成员用Python编写，现在这种分裂已经成为一个招聘限制。”
```

其中一个比较研究包含三个前者，而没有后者——不要接受这种交易。

差距是出版商的选择，而不是类型约束。在四个比较研究中的三个——一个小样本，并且两个供应商研究来自同一个供应商：

- 供应商发布的成对没有披露任何成本。
- 社区发布的成对披露了成本和公开的失败，其中一个是命名从业者逐步走过了他自己的糟糕发布。

### 列表和来源：[./references/evidence-and-sources.md](./references/evidence-and-sources.md)。

从访谈中填写该部分：

- 工程师周数的迁移工作量。
- 双运行期。
- 推广过程中出现的问题。
- 团队重新培训的内容。
- 故意不移动的业务负载。
- 仍然无法正常工作的部分。

说明不应该复制这种架构的人。

- 客户删除整个部分：研究较弱但仍可发布。
- 客户删除它**并且**删除替代方案部分：你正在发布一则广告。明确告知所有者，使其被视为一则广告。

## 审批流程

在向任何人提出任何要求之前，请先阅读合同的宣传条款。标准的自助式SaaS条款通常已经授权客户的名称和标志以及他们作为客户的声明 - Vercel的条款包含这样的条款，在[./references/approval-and-anonymization.md](./references/approval-and-anonymization.md)中逐字引用。

该条款授予其他任何东西：

- 没有引言。
- 没有指标。
- 没有架构描述。
- 没有关于客户如何运行其系统的叙述。

请求确切地开放它所允许的内容。

仍然有四个权限，通常由四个人分别持有：

- 工程师同意被引用。
- 他们的经理同意花费团队信誉。
- 公司名称和标志的沟通批准。
- 技术细节的安全或法律审查。

在第一次联系时，询问谁持有每个权限。

预先编辑安全审查可预测地删除的内容：

- 绝对的基础设施规模和成本。
- 内部服务名称、工单ID、仪表板URL。
- 被拒绝的替代方案部分中的竞争对手名称。
- 任何暗示初始状态存在安全弱点的内容。

发送完整的草稿，标记决策、设定日期的截止日期和声明的默认值。

当命名被拒绝时，逐级下降匿名化，而不是放弃故事：

1. 命名的公司和工程师。
2. 命名的公司，未命名的工程师。
3. 未命名的公司，具有识别描述符。
4. 仅类别描述符。
5. 无客户模式的描述。

每个级别都会损失信誉，最后一个级别不再是一个案例研究。

这个梯子故意没有按工作量和效率排名：这些级别不是人们可以选择的替代方案，因为每个低于顶部的级别之所以更便宜，只是因为有人拒绝了它上面的级别。接受最高级别的审批允许，并将下降视为损失，而不是权衡。

完整的梯子、编辑类别和请求模板：[./references/approval-and-anonymization.md](./references/approval-and-anonymization.md)。

## 人类化处理

在通过门之前，通过你首选的人类化技能处理文本。模型风格的填充读起来像供应商文案，这是该工件最需要避免的语域。

保留原文：每一条引言、每个数字、版本字符串、组件名称和架构描述。人类化的引言是虚构的引言。

## 发布门

七个检查 - 一个工作门，而不是一个发布标准。在所有七个检查通过之前，保留研究。报告哪个检查失败以及你做了什么，然后重新检查。

1. **每个声明都被分类** - 测量、部分测量、报告或工程师的标记意见。没有例外。
2. **每个数字都有一个仪器和一个窗口**，说明或一个点击之遥。
3. **至少有一个限制**发布，具体到读者可以根据它决定反对你。
4. **替代方案部分存在**，命名被拒绝的内容和原因。
5. **每一条引言逐字**来自转录，用确认的姓名和头衔归因。
6. **公司名称、标志、引言和安全审查的审批证据存档**。
7. **零不支持的超级形容词**。任何“无缝的”、“轻松的”、“改变游戏”的要么在研究中有一个数字支持，要么被删除。

然后进行两次人类阅读，然后才发布：

- 被采访的工程师确认技术准确性。
- 账户外部的人检查它是否可以在没有内部词汇的情况下理解。

## 派生版本

一个批准的研究可以生成多个工件。在批准之前，询问哪些是需要的，以便权限涵盖它们，并按重用/小时顺序构建它们 - 每个低于批准研究的级别都会重用已经获得批准的研究的材料，所以排名是关于重用落在哪里，而不是关于写作工作量：

1. 文档交叉链接 - 零：一个“谁使用这个以及如何”的指针从相关页面，坐在评估员已经阅读的地方。
2. 销售用的一页摘要 - 一个小时：结果、三个数字、一条引言，以及每个部分上没有CTA。在销售动作存在的任何地方，这是四个中最高的价值，在没有的地方则毫无价值 - 这正是跳过它的时机，而不是排名。
3. 社区帖子 - 一个小时加上工程师的意愿：他们自己的话用自己的名字，这比你在自己的名字下发布的任何内容传播得更远，并且只有他们可以授权。
4. 会议或网络研讨会材料 - 一天，并且取决于是否有时间槽。架构之前/之后已经是一个幻灯片，所以边际成本很低，但在这里没有东西在谈话被接受之前支付。

将研究的基本单元 - 每个指标、每条引言、架构图 - 存入证明库中，与叙述一起，带有公共/私有标志。稍后构建的资产从基本单元中提取；没有人会重新阅读一个1,500字的研究来找到一个数字。

在付费或广告环境中重新发布通常需要自己的权限。在重新使用之前，重新验证大约18个月以上的研究 - 这是一个自我设定的惯例，而不是一个测量的保质期；为快速推出或流失的客户缩短它。

## 失败模式

| 症状                               | 原因                                               | 修复                                                                                  |
| ------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 读起来像证言                          | 只有第1、2、6、8部分有材料                          | 回去寻找替代方案、架构、成本 - 或者发布一个引言卡片                             |
| 客户删除了半个数字                    | 指标从未有过渊源                                    | 重建每个指标，带有仪器和窗口，重新提交                                             |
| 审批停滞了数周                       | 在起草后启动了审查链                               | 在第一次联系时启动审批流程；设定一个有日期的默认值                                |
| 工程师公开质疑它                     | 架构是从供应商假设中编写的                         | 让被采访的工程师确认技术部分                                                     |
| 引言听起来像营销                      | 概括而不是转录                                      | 从录音中恢复逐字；接受客户自己的编辑                                             |
| 故事在采访后死亡                     | 资格门被跳过                                      | 在安排通话之前运行门                                                              |
| 数字夸大                             | 产品归因于多变更的推出                             | 命名同一窗口中发生的一切其他变化                                                   |
| 客户质疑“已批准”的研究                | 合同的标志条款被解释为全面批准                     | 将该条款视为名称和标志；分别获取引言、指标和叙述                                 |
| 限制部分什么也没说                    | 路线图项目被接受为成本                             | 再次询问工程师周数、双运行期、什么被破坏 - 计划不是成本                           |
| 流失客户的研究仍然存在                | 没有在发布时设定重新验证日期                      | 每个研究都标注日期，按计划重新验证，而不是保留它                                |

## 测量

根据研究是否推动了评估前进来评判，而不是根据流量。没有发布的指标可以隔离专门针对开发者的案例研究：一般的B2B技术买家研究将供应商生产的案例研究远远排在产品演示和免费试用之后，对购买决策的影响（见[./references/evidence-and-sources.md](./references/evidence-and-sources.md)），但没有比这更窄的指标。将以下信号视为需要权衡的东西，永远不要将其视为目标：

- 在实际交易中使用：销售或解决方案工程师实际发送它的频率，以及哪个阶段。
- 阅读率和点击率到它链接的工件（文档、存储库、架构页面）。
- 入境参考请求 - 潜在客户要求与该客户交谈。
- 采用者是否自己放大它；一个客户自己的工程师分享的故事比你在自己的名字下发布的任何故事传播得更远，并且只有他们可以授权。
- 故事库的覆盖率：每个主要用例和采用者规模的可靠研究比同一配置文件的研究多五个。

不要将收入归因于单个案例研究。过度归因的声明是工件存在的同一信誉失败。
