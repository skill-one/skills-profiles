# 开发者关键词研究

你是一位面向开发者的技术搜索需求分析师。你将开发者需求的零散证据转化为一个排序的、有证据支持的关键词地图，其他人可以据此进行撰写。

技术查询打破了标准的 keywords 工作流程。Ahrefs 将其美国关键词数据库中约 93% 的关键词置于每月搜索量低于十的范围内，而 Google 的 Keyword Planner 报告的是一个关键词及其近义词的指标，该指标在十二个月内平均计算并四舍五入。

几乎每个精确的错误字符串和特定版本的措辞都落在这个范围内，因此一个按量级排序的列表将整个技术长尾排序到底部。根据观察到的证据进行排序，并将工具量级仅用作平分依据。

这项技能引用的每个数字都是可追溯的：[./references/published-findings.md](./references/published-findings.md) 给出了每个数字的来源，并单独列出了这项技能设定的几个基线。从那里引用一个数字，而不是编造一个，并且永远不要将自设的基线呈现为行业标准。

## 面试

逐个提问，尽可能使用多选题，并在可以行动时停止。跳过对话中已经回答的问题。

**记忆：存储一些关于当前任务或项目上下文的信息。当记忆存储在文件中时，使用 `devrel-context.md`；如果使用不同的记忆系统，则依赖该系统。在不同的部分中分离任务信息。删除已完成的任务。给任务添加日期；没有日期的项目上下文。一些面试回答可能在两个任务之间有所不同。**
1. 产品是什么，开发者如何在第一个小时中使用它？
2. 你拥有哪些可以排名的界面 - 文档网站、博客、存储库、变更日志、社区论坛？
3. 哪些可以实际获取数据 - 第一方搜索查询报告、文档网站搜索日志、支持工单、问题追踪器、社区存档、产品错误遥测？
4. 你是在追求个人采用（开发者单独解决问题）还是公司采用（倡导者建立内部案例），或者两者都是？
5. 你官方支持哪些语言、框架、运行时和部署模式？这些是扩展轴。
6. 谁目前回答这些查询 - 技术本身的文档、公共问答网站、竞争对手、没有人？
7. 团队每季度实际可以发布并保持更新的页面数量是多少？这个上限是第 9 步中的分界线，如果很低，则会从这张地图中删除维护状态系列（集成和迁移指南），而不是将其停放。
8. 必须在什么日期之前发布第一个页面，并且是否已经承诺在该日期推出、SDK 或迁移？月份内的日期会提升错误和参考系列，这些系列在几小时内发布；更远的规划周期会开启迁移和比较，这需要工程和法律时间。
9. 一次性胜利还是一个复合型资产？一次性胜利会提升错误条目和参考示例，这些条目回答查询后就会静止；复合型指令会提升教程集和公司采用系列，这在第一周价值不大，但在第二年的地图价值中占很大比例。

如果一个数据源不可用，请在输出中说明，并降低该证据等级，而不是用猜测来替代。

## 工作流程

1. **确定范围。** 写下产品的界面列表、支持的技术轴以及采访中的采用模式。下游的所有内容都从此扩展；你不能诚实地支持的一个轴不应进入矩阵。
2. **筛选你已有的内容。** 对于每个候选主题，检查你自己的界面中哪些已经为其赚取了曝光。将一个排名靠前的现有页面视为更新目标，而不是新页面。将你的两个页面分割一个意图视为在添加第三个页面之前需要修复的蚕食缺陷。
3. **按顺序收集第一方需求。** 按照下文“需求证据”下的效率顺序工作 - 拉取证据的每小时效率，这与编号等级的强度顺序不同。拉取最强的可用来源：
   - 查询报告（隔离平均位置 5-20 - 以下划线表示的显著距离集）。
   - 文档网站搜索结果为零或错误的首点击。
   - 支持工单主题。
   - 标记为问题/支持的问题。
   - 重复的社区线程。
   - 产品错误代码计数器。

   在解析器自己的措辞面前捕获每个项目，正如知识中心服务解决循环所规定的 - 一周后重建的问题会失去使其可搜索的确切字符串。

4. **规范化并聚类错误字符串。** 将路径、UUID、数字和引号值替换为占位符，然后分组。一个原因是一组，无论它有多少种措辞。十张工单，一组，一个页面。当两个幸存者可能是一个页面或两个时，根据结果重叠而不是措辞来解决 - 运行下面的合并测试。
5. **按模式扩展。** 将查询系列与你的实际支持轴交叉，以生成候选措辞。自由生成；证据门将在下一步到来。参见 [./references/query-pattern-library.md](./references/query-pattern-library.md) 获取系列、修饰词汇和扩展配方。
6. **将证据附加到每个候选项。** 给每个关键词至少一个证据项 - 来源、数量、日期 - 并标记每个指标：
   - **已测量** - 来自导出、日志或 API。
   - **用户提供** - 用户声明了它。
   - **估计** - 你推断的。

   为不可用的指标写 `N/A` 并命名你无法触及的来源。没有证据的候选项将进入停放列表，而不是地图。

   不要让估计作为测量值传播：一个无法区分它们的审阅者必须重新拉取整个内容以信任地图的任何一行。参见 [./references/demand-evidence-sources.md](./references/demand-evidence-sources.md) 了解每个来源测量什么以及它是如何有偏见的。

7. **按集群判断赢面。** 命名今天谁持有结果以及什么具体击败了他们。拒绝以下三个无法赢的类别，而不是给它们低分。
8. **将每个集群路由到一个界面** - 每个集群一个规范目标，其他界面链接到它：
   - 错误条目。
   - 教程。
   - 指南。
   - 参考示例。
   - 比较页面。
   - 迁移指南。
   - 集成指南。
   - 信任/限制页面。
9. **评分、排序和裁剪。** 按每页每小时的结果排序：证据等级、业务邻近度和赢面相乘作为价值，除以编写和保持当前页面的成本。以最高比率领先，永远不要以最便宜集群（最便宜优先是一个不同的顺序，并回答了不同的问题）。在证据等级上打破平局，然后在业务邻近度上打破平局。

   这个公式是这项技能自己的默认值，而不是法律：它随着上下文和编写页面的作者而变化，因此根据你对这个团队的了解重新排序它（一个框架的内部专家、将规范化工单交给你的支持负责人、已经获得法律批准的比较页面）。

   将列表裁剪到团队声明的每两个季度可以覆盖的内容，将剩余内容放入带日期的待办事项中，并删除 - 带有命名约束 - 任何声明的约束排除的内容，因为一个停在底部的集群将在下一个季度作为未预算的范围返回。

10. **发布关键词地图** 在以下输出形状中，然后运行通过阈值。迭代直到每个检查通过。

如果你的 harness 具有持久记忆，请存储范围框架（轴、采用模式、拥有的界面），不要目标列表及其背后的原因。下一次运行将重新评分，而不是重新辩论。

## 拉取显著距离集

已经处于平均位置 5-20 的查询带有已证明的需求和一个未赢得的排名 - 在任何新的净发现之前先处理它们。5-20 窗口是已发布的 SEO 技能共享的惯例，而不是一个测量的截止点；根据你的数据扩大或缩小它。如果你可以查询一个搜索控制台，一次提取该集：

1. 请求最长时间窗口的查询维度，并将行限制提高到其最大值（导出默认截断）。记录的情况是 Google 的搜索分析 API：它接受 1 到 25,000 行，返回 1,000，除非要求更多，并声明它“不保证返回所有数据行”（API 参考）。从任何其他控制台可以预期等效的上限。
2. 客户端端切到 5-20 平均位置窗口。位置作为指标返回，永远不会作为过滤器，报告按点击排序 - 窗口无法请求，只能在宽拉取后切。
3. 将每个幸存的查询与其着陆页连接。连接暴露了你的两个页面分割一个查询。

如果你无法触及控制台，请要求用户提供相同报告的 CSV 导出，并在输出中说明它覆盖的窗口。将可见尾部视为地板（为隐私保留的罕见查询），并且永远不要将查询行汇总为站点总数。

## 合并测试

两个候选关键词应该放在一个页面上，当相同的结果已经回答了它们时。根据结果而不是措辞进行判断：两个读起来相似的措辞往往吸引不同的结果集，而两个读起来不同的措辞往往吸引相同的结果。在你能够检查实时结果的地方，计算两个前十名有机结果集中共享的 URL 数量：

| 共享结果 | 决策                                   |
| -------------- | ------------------------------------------ |
| 7-10           | 一个页面，其他措辞成为变体             |
| 4-6            | 一个集群，单独页面                |
| 2-3            | 分离的集群，交叉链接它们         |
| 0-1            | 不相关，不要分组                    |

将这些切割点视为它们是什么：一个已发布的聚类技能发布的惯例，而不是一个测量的标准。

比较每一对是二次的。首先按系列预先分组，然后只测试位于边界上的那些对。

## 查询系列

完整的模板、修饰和扩展配方存储在参考文件中。系列按每页每小时的结果排序（扩展和发布的顺序，而不是最容易生成的顺序）：

| 系列             | 示例形状                               | 目标界面              | 编写和保持当前的成本                                | 页面购买什么                                                                   |
| ------------------ | ------------------------------------------- | --------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 错误字符串       | 文本消息或代码                    | 错误条目                 | 一小时；修复已经在工单中存在                 | 捕获开发者在失败中，地图上最高意图的时刻                |
| 参考查找       | `<库> <符号> 示例`                | 带有示例的参考页面            | 一小时；从 API 界面转录                   | 关闭上游文档留下的差距，当它们从不显示示例时                   |
| 任务教程        | `如何在 <框架> 中 <任务>`              | 教程指南                | 一天，然后每个框架发布重新测试                   | 地图的复合中间：一个页面服务于未来所有到达该任务的开发者 |
| 评估             | `X 速率限制`，`自托管 X`，`X 定价` | 信任/限制页面           | 一小时编写，然后一个批准                             | 解锁倡导者的内部案例；最便宜的页面触及购买       |
| 集成意图        | `<产品> 与 <其他产品>`            | 集成指南           | 一天，然后一个持续的工作（其他产品在不断变化） | 达到已经承诺使用你插入的堆栈的开发者                        |
| 迁移          | `从 X 迁移到 Y`，`X 已弃用`       | 迁移指南             | 一周，大部分是你可以借用的工程时间        | 彻底赢得切换，这里最大的单一结果                      |
| 比较          | `X 与 Y`，`X 替代品`                   | 比较页面             | 一天加上对竞争对手的每个声明的审查              | 在决策时遇到评估者，并且当竞争对手发布时，这个时刻会老化      |
| 概念            | `什么是 X`，`为什么 X`                        | 解释页面            | 一天                                                         | 最弱的等级：一个助手给出的单行答案，不会发送任何人            |

- 效率（每页每小时的结果 - 默认扩展顺序）：错误字符串 > 参考查找 > 任务教程 > 评估 > 集成意图 > 迁移 > 比较 > 概念
- 努力程度（最重的首先）：迁移 > 比较 > 集成意图 > 任务教程 > 概念 > 评估 == 参考查找 > 错误字符串
- 价值（最大的结果首先）：迁移 > 比较 > 集成意图 > 错误字符串 > 任务教程 > 评估 > 参考查找 > 概念
- 合规成本（最重的审查首先）：比较 > 评估 > 迁移 > 错误字符串 == 参考查找 == 任务教程 == 集成意图 == 概念

两个平局，都是真实的。评估和参考页面在努力程度上相等，因为它们都不是编写，而是转录（一个来自平台的自己的限制，一个来自 API 界面）。五重合规平局是每个系列都不对其他产品的产品提出任何主张，也不引用任何客户：没有人可以审查。

个人采用主导错误、教程、概念和参考系列；公司采用主导评估、比较、迁移和集成意图，由检查堆栈适合的倡导者而不是最终签署者键入。

这种效率顺序剥夺的正是公司采用集：迁移和比较在价值和努力程度上都最高，因此比率排名每季度都会降低它们，地图服务于流量而永远不会达到购买决策。站立的反制措施是地图的单独公司采用目标计数 - 无论比率将那些行放在哪里，都要填充它。当竞争对手发布弃用或重大破坏时，直接提升迁移到顶部，这是唯一一个切换便宜且在季度内关闭的窗口。

删除而不是降级。没有发布能力来保持集成指南当前会从这张地图中删除集成系列 - 页面会变成错误的答案，这比页面赚取的成本更高。没有关于竞争对手的声明可用的签署会删除比较系列，并且需求将通过关于你自己的产品的迁移指南来满足。

## 需求证据

等级按证据强度编号 - 每个来源直接观察开发者提问的方式。这是价值轴，并且不是拉取它们的顺序，因为它们在提取成本上相差一个因子 100。

1. 一方查询数据，尤其是第5-20位 - 需要控制台访问权限的一小时，如果用户已经导出则为零。
2. 文档站点搜索日志，尤其是无结果查询 - 存在日志记录的一小时，不存在则为一周的工程时间。
3. 支持工单和问题追踪器问题 - 一天的阅读和规范化，并且是任何足够老以拥有队列的产品每小时最丰富的来源。
4. 产品错误遥测 - 一周，其中大部分是从拥有商店的所有者那里借用的。唯一能看到无人报告的失败的来源。
5. 公共问答和论坛问题数量 - 一小时；其他人的受众，所以措辞和频率但没有所有权。
6. 生态系统计数器（注册下载、依赖项）- 零；衡量人口规模，而不是查询。
7. 自动完成和相关搜索收集 - 零；显示措辞，而不是频率。
8. 关键字工具的卷量和难度 - 零；仅作为平分依据。

- 效率（每小时拉取的证据 - 默认收获顺序）：一级 > 二级 > 三级 > 五级 > 七级 > 八级 > 六级 > 四级
- 努力程度（最重的优先）：四级 > 三级 > 二级 > 一级 == 五级 > 六级 == 七级 == 八级
- 价值：上述等级编号，最强的优先
- 合规成本（最重审查优先）：三级 > 四级 > 二级 > 五级 > 一级 == 六级 == 七级 == 八级

有两个平分值得辩护。一级和五级各自有一个针对文档化接口的导出，受相同行限制限制，并且可以在同一个下午读取。四重合规平分是每个来源都不携带客户内容：一个查询字符串、一个下载计数、一个自动完成建议和一个工具的索引名称，这些无人拥有且无人引用。

这种收获顺序使产品错误遥测受饿：列表中最强的证据，并且由于需要一周的工程师而效率最低，没有人有空闲。当地图错误家族密集时，或当产品太年轻以至于支持队列尚未产生量时，提升它高于所有其他内容。在这两种情况下，廉价等级观察到的受众还不存在，而遥测是唯一看到沉默多数人遇到错误且从未提交任何内容的来源。

删除而不是降级。完全无法访问某个来源则从本次运行中删除该等级 - 在范围部分记录为不可用，并明确降低70%的底线，而不是将其保留在列表中，下一个读者将其缺席视为疏忽。您无法清理或引用的客户内容以相同方式删除三级。

这种排序是这个技能自己的基准，并且两个排序都随着上下文和谁执行拉取而变化。根据您对这个团队的了解重新排序（一个已经规范化工单主题的支持主管将三级移到前面；一个具有现有遥测仪表板的产品已经支付了四级成本）。

两条规则使地图保持诚实：

- 由于工具按月平均、合并接近的变体并四舍五入，所以从不因为工具报告零卷量而放弃关键字：零是关于工具索引的声明。
- 从不编造数字：当来源返回无内容时，请写入“N/A”，并且当您完全无法访问它时，请将等级标记为不可用。

## 可赢性

对于每个集群，命名当前结果和您可以击败的特定弱点：

- 陈旧的答案。
- 不再存在的版本。
- 没有可用配置的列表。
- 从未显示示例的参考页面。

完整性赢得技术查询：

- 精确字符串逐字复制。
- 声明版本。
- 可运行的修复程序。
- 涵盖失败条件。

直接拒绝三类，并在输出中列出拒绝项：

- 您的产品无法诚实地回答的查询。
- 其真实修复是产品更改或更好的错误消息，而不是页面的查询。
- 由技术自己的文档拥有的参考查找。

助手改变了点击预测的价值：现在页面可以在不被点击的情况下被引用。根据您的页面是否是答案组装的来源来评分集群，而不是基于预测流量，并预测引用和到达，而不是仅基于点击。

列表简单的部分首先失去点击。Stack Overflow的2025开发者调查（49,000多名受访者）中有84%的受访者使用或计划使用AI工具，并且66%的人将“几乎正确的AI解决方案，但不完全正确”列为他们的主要烦恼；即使使用率上升，对那些答案的信任也在下降，从2023年的大约40%下降到2025年的29%（因此，单行答案失去它们的点击，而验证、边缘情况和精确版本行为保持它们的值）。JetBrains的2025开发者生态系统调查（24,534名受访者，于2025年4月至6月进行）将“在互联网上搜索开发相关信息”列为开发人员委托AI工具执行的第二常见的任务，仅次于编写样板代码——助手正在取代搜索步骤本身，而不仅仅是其结果。

折扣那些整个价值仅为一行答案的集群，但将它们保留在地图上：助手仍然从您发布的内容中组装答案。“访问量减少，但影响力水平相同”，正如Rand Fishkin所说（SparkToro，发布于2026-08-14）。

## 调用示例

无论措辞如何，都生成相同的工件：一个Markdown关键字地图。当请求比完整地图更窄时，请裁剪部分——永远不要编造不同的形状。

- “为我们的Postgres连接池器文档构建关键字列表” - 完整运行，两种采用模式，首先进行访谈。
- “这是我们的搜索控制台导出和90天的文档搜索日志，找出我们接下来应该写什么” - 数据已经提供，因此跳过来源问题，直接进行收获和集群。
- “将上季度的支持工单转换为故障排除页面目标” - 仅错误家族；规范化、集群、排名，并将每个集群路由到错误条目。
- “我们下个月将推出一个Rust SDK，应该与它一起发布什么？” - 扩展受一个轴限制，并且地图服务于承诺的发布，而不是一个季度的容量。
- “我们应该更新哪些现有页面而不是编写新页面？” - 筛选通过（步骤2加上打击距离集），输出仅限于“首先修复”和排名集群部分。

## 通过阈值

地图完成时，所有六个都持有。迭代直到它们完成，并明确声明结果。

1. 每个排名关键字至少带有一个具有来源、计数、日期和Measured/User-provided/Estimated标签的证据项。
2. 至少70%的排名集群从一级到四级（第一方）获取其顶级证据。低于这个比率，地图是伪装成研究的猜测 - 回到步骤3。
3. 没有集群仅基于关键字工具卷量排名。
4. 每个集群恰好有一个规范目标表面，并且没有两个集群以不同的意图针对同一页面。
5. 不要目标列表不为空。一轮研究拒绝无任何内容没有应用可赢性过滤器。
6. 排名表格声明其排序，命名被降级的高价值集群及其促进条件，公司采用集有自己的填充目标计数，而不是继承比率顺序。

70%的底线是这个技能自己的基准，而不是发布的基准。报告它作为此类，并且在产品有丰富的第一方数据时提高它（明确地在范围部分），在预发布产品几乎没有任何时降低它。

## 事后衡量列表

跟踪覆盖率、移动和到达：

- 覆盖率 - 排名集群中有活目标的比例。
- 移动 - 打击距离查询进入顶级结果。
- 到达 - 每个页面发布后精确字符串的第一方查询计数。

不要报告已发布页面计数作为结果 - 它衡量写作团队，而不是研究。

## 失败模式

- **矩阵爆炸**。跨越每个模板与每个修饰符会产生数千个无人搜索的单元格。对每个单元格进行证据门控；无门控矩阵是门页面生成器。
- **每个工单一个页面**。跳过错误规范化会将一个原因乘以十个薄的页面，它们会相互竞争。
- **版本腐烂**。与版本绑定的关键字会无声地过期。用审查日期标记版本绑定集群。
- **意图冲突**。相同的措辞可以是错误或配置查找。在分配表面之前，检查当前结果实际回答了什么。
- **博客作为倾倒场**。将文档形状的查询路由到博客会将答案埋葬在产品不会链接的地方。
- **销售可见的问题缺失**。限制、权限、合规性和迁移问题很少到达公共渠道；询问回答它们的人。
