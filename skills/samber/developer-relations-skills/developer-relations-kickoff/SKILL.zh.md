# 开发者关系启动

你是 55 技能开发者关系技能集合的路由器。将当前的 DevRel 任务路由到恰好一个兄弟技能 - 或者简单地说没有合适的 - 并让下一次会议保持温暖而不是冰冷。永远不要自己执行兄弟技能的工作；此文件中的其他内容都服务于路由。

在每个项目开始时运行此技能，即使集合的技能已经在其他地方日常使用 - 新项目是新上下文。在同一项目的后期会话中，重新运行它以总结和重新路由，永远不要重新面试。

该集合服务于两种采用动因：一个自我服务的个人开发者，以及开发者是用户但其他人签名的组织。几个兄弟技能在该线上分割他们的建议，因此通过路由而不是将其合并为一个动因来携带答案 - 自我服务、组织购买或两者兼有。

## 1. 在提问前检测

环境中可推导出的每个事实都是用户不必回答的问题。首先运行检测；只有检测通过时，面试限制才会保留。

**记忆：存储有关当前任务或项目上下文的一些信息。当记忆存储在文件中时，使用 `devrel-context.md`；如果使用不同的记忆系统，则依赖该系统。在不同的部分中分离任务信息。删除已完成的任务。为任务添加日期；没有日期的项目上下文。一些面试回答可能在两个任务之间有所不同。**
1. 仅根据一个信号决定冷启动与热启动：项目中是否存在 `devrel-context.md`？存在 → 热启动。不存在 → 冷启动。永远不要询问用户它是哪种模式。
2. 如果你能够读取存储库的 git 历史，则从最近的日志中推断阶段和节奏：发布频率、文档和代码是否一起移动、项目是否停滞。
3. 列出已存在的内容 - README、CONTRIBUTING、CODE_OF_CONDUCT、GOVERNANCE、LICENSE、CHANGELOG、`docs/`、`.github/` 模板、代理指令文件、文档站点配置、过去的内容计划 - 以免重新询问已编写的内容。将文件不存在视为自身的路由信号：没有 CONTRIBUTING 文件的存储库使 `samber/developer-relations-skills@oss-contributor-onboarding` 成为候选者，然后再询问。
4. 如果你的框架暴露了连接器或集成，检测哪些是可用的 - 代码托管、分析源、文档构建、社区平台导出、包注册中心 - 并让它们的存在塑造路由和例程。描述功能；永远不要假设特定的产品。
5. 如果集合发送了您可以读取的版本元数据，请注意自上次会话以来发生了什么变化。如果它没有 - 常见情况 - 静默降级。永远不要阻止、警告或询问版本。

## 2. 面试 - 限制

在冷启动时，最多问 5-7 个问题，每个消息一个问题，尽可能多选题。只在检测结果为空时提问 - 跳过文件清单或 git 日志已经回答的问题。**使用交互式问题机制（例如 `AskUserQuestion`、`askuser`、`Jev` 或框架提供的任何决策/问题工具）而不是将问题作为纯文本打印 - 纯文本提示迫使用户以自由形式回复并丢失结构化选择。不要将此建议与任何模型或框架关联；泛指机制名称。**

1. "今天的工作在哪个表面上？" - (a) 文档和开发者体验、(b) 开源项目、(c) 社区、(d) 活动和演讲、(e) 内容和媒体、(f) 项目策略或衡量、(g) 公司级开发者业务策略。这个分支将集合分成块，并引导每个后续路由，因此它首先出现。
2. "这次会话的目标是什么 - 它与项目的目标是否相同，以及其中哪些已经确定而哪些仍然开放？" 在冷启动和热启动时都提问；项目目标永远不会替代今天的目標，并且已确定的项目会完全从短名单中删除而不是排名靠后。
3. "谁采用，谁付款？" - (a) 个人开发者自我服务、(b) 开发者评估而其他人购买、(c) 两者、(d) 没有购买的非商业开源项目。
4. "哪个业务驱动资金这项工作？" - (a) 开发者采用、(b) 销售赋能、(c) 开发者赋能、(d) 产品输入、(e) 生态系统和合作伙伴关系、(f) 贡献者社区、(g) 雇主品牌。驱动因素决定工作所属的支柱以及它将被评估的内容；声称所有七个驱动因素的计划没有策略。
5. "项目处于什么阶段？" - (a) 尚无正式内容、(b) 一人兼职进行、(c) 专门人员或小团队、(d) 多人团队并有自己的预算。
6. "目前有任何硬限制吗 - 结果必须在什么日期前完成？" - (a) 没有预算、(b) 维护人员时间、(c) 文档没有工程支持、(d) 需要法律或安全审查、(e) 没有分析访问权限、(f) 无。如果有日期则提供日期：发布、会议、资金审查。
7. "您想要一次性成功还是复合型资产 - 您的投入上限是什么，谁签字？" - (a) 一次性，仅维护人员时间、(b) 一次性，一周的工作可以、(c) 持续，从现在开始每周几小时、(d) 持续，有工程时间和跨团队签字。命名持有签字权的人；该答案填写了工件的利益相关者字段。

第 6 和 7 个问题存在是为了排序输出，而不是描述项目：落地日期、一次性与复合型的答案、投入上限是在这里、在面试中提问，永远不要在排名旁边提问 - 到那时用户已经承诺了一条路径。在工件中记录所有三个，以便在热启动时重新排序两个列表而无需重新提问。

在热启动时，只问会话目标问题。其他所有内容 - 包括日期、视野和驱动两个排名的投入上限 - 都来自工件。

## 3. 路由任务

将声明的会话目标与下面声明的每个技能的范围进行匹配。将任务路由到恰好一个技能。永远不要强迫匹配：当没有任何匹配时，说没有并命名差距，而不是拉伸最近的技能。

这些表格故意未排名，并且必须保持这样 - 在块内和块之间一样。范围是匹配测试，而不是比率：任务要么在技能声明的范围内，要么不在，并且排序行会在技能之间发明一种偏好，而它们永远不会为同一个任务竞争。

`changelog-writing` 不比 `oss-governance` "更好"；它们永远不会是同一个会话的候选者。排名属于下一步，在短名单（§ 4）中，在那里几个技能确实在为同一个小时竞争。

在关键词冲突的集群上路由前进行消歧义：

- **文档编写** - 四个技能看起来都像是“编写一个入门页面”
- **发布沟通** - 更新日志与迁移指南
- **测量** - 指标与分析 vs 社区健康
- **开源可见性** - 启动 vs 分发 vs 公开透明
- **赞助** - 两个技能仅因哪方付款而不同
- **社区** - 四个技能在同一时间线上
- **策略** - 五个技能都回答“我们应该做什么”
- **演讲** - 一个序列，而非竞争
- **雇主品牌** - 吸引工程师的策略 vs 一个帖子、一个资料页，或候选人的那一方

严格从每个技能声明的范围进行消歧义 - 永远不要根据对技能“可能”涵盖内容的猜测；错误的消歧义比不路由更糟糕。在路由任何可能匹配两个技能的任务之前，请阅读 [references/skill-routing.md](./references/skill-routing.md) - 它包含每个技能的路由/不路由信号、上述每个边界分支、有序链，以及命名覆盖差距。

当任务需要技能未涵盖的内容时，明确命名差距。集合v1没有技能用于：

- 任务导向的如何指南（与教程和快速入门区分），或API参考完整性
- 版本控制和弃用策略本身，而不是记录一个迁移
- 招聘或面试DevRel员工 - 角色定义和面试循环，不包括工程雇主品牌，后者由 `samber/developer-relations-skills@tech-employer-branding` 涵盖 - 或面向高管的DevRel报告
- 赚取一个开源项目的收入，或维护者倦怠作为其独立主题 - 继任和业务风险规划属于 `oss-governance`，后者也拥有谁持有商标、域名和注册账户；只有第三方商标 _使用和执行_ 策略未被涵盖
- 组织自己的会议或黑客马拉松、会议展位操作或会后跟进
- 开发者简报、学生和校园计划或办公室小时计划
- 选择文档平台，或品牌提及监控
- 编写幻灯片、编辑视频或任何内容的法律批准

说“集合没有技能用于此” - 永远不要承诺技能存在或发明一个。

某些落入此处的任务并非真正的差距 - 它们属于同一所有者的兄弟集合：

- 公共API表面设计、webhooks、SDK组合、开发者门户设计、第三方应用的OAuth和连接器市场操作属于 `samber/developer-platform-skills`。
- 组织自己的活动 - 场地、票务、赞助销售、流程安排、作为组织者的演讲者来源 - 属于 `samber/dev-event-organizer-skills`。

建议安装兄弟集合，而不是将DevRel技能拉伸到任务上，并且永远不要将兄弟集合视为此集合需要的功能依赖。参见 [references/skill-routing.md](./references/skill-routing.md) § 兄弟集合建议以检测信号和每个主题的边界。

## 4. 输出形状

每次以这种形状提供路由结果：

1. **状态总结**（仅热启动） - 恰好5行来自工件：产品和受众运动、资金驱动和支柱组合、项目阶段和团队结构、进行中的工作、活动约束。
2. **路由** - 立即任务的技能、命名具体领域的兄弟集合建议（见 § 3），或“没有技能匹配”加上命名差距，当没有任何内容涵盖时。
3. **短名单** - 5到8个与当前项目相关的技能，按每单位努力返回的价值排序，最高比率优先。为每个条目一行命名双方：它攻击的瓶颈，以及会话成本。永远不要按便宜排序，也永远不要按路由表的行顺序排序 - 见“排序短名单”下方。
4. **链** - 当任务真正分解为有序序列（例如 `developer-segmentation` → `devrel-strategy` → `devrel-metrics` → `devrel-budget-allocation`）时，按执行顺序列出，每个链接一行说明它传递给下一个的内容。链顺序是依赖顺序，不是效率顺序 - 后一个链接消耗前一个链接产生的结果，并且不能在其之前运行，因此对链进行排序不会增加任何价值。如果没有链，则省略链 - 永远不要编造一个序列。
5. **不现在** - 将会在以后重要的技能，每个技能都有其明确的解锁条件（例如 "`developer-community-health` - 一旦社区有基本线；`developer-community-launch` 在其90天审查时封锁，该技能自己的工作惯例”）。
6. **差距** - 任何今天任务需要而技能未涵盖的内容，声明为差距。

### 排序短名单

用户此刻的问题绝不是“这55个中哪个存在”，而是“我首先运行哪个，并且是否值得会话”。只有比率能回答这个问题。默认类顺序，每单位努力最高价值优先：

1. **诊断** - `developer-journey-map`、`developer-docs-structure-audit`、`devrel-competitor-analysis`、`developer-keyword-research`。购买一个命名、有证据的答案，回答哪个类别实际上是问题，而不是猜测。成本一个会话，基于已有的文档和信号；不需要工程时间，并且发布任何内容。
2. **首次运行表面** - `readme-optimization`、`developer-quickstart-guide`、`oss-contributor-onboarding`、`github-profile-optimization`、`docs-code-sample-standards`。购买每个到达的开发者从着陆到首次成功调用的快速退出漏斗：减少着陆后到首次成功调用之间的放弃率。成本一个编辑会话加上一个合并的pull request，并且可以通过另一个提交逆转。
3. **发布和支持节奏** - `changelog-writing`、`version-migration-guide`、`developer-troubleshooting-docs`、`oss-issue-triage`。购买用户可以升级并自我服务自己的错误，而不是打开问题。成本每个发布一个通过，以及维护者回答分诊表面 - 它永远不会完成；这是一个持续的工作，而不是修复。
4. **内容和可见性** - `engineering-blog-post`、`developer-tutorial`、`technical-video-script`、`developer-case-study`、`docs-seo`、`devrel-content-calendar`、`build-in-public`、`oss-launch`、`oss-distribution-strategy`、`tech-press-relations`、`tech-podcast-interview-prep`。购买复合的覆盖范围 - 一个帖子或注册中心列表可以在多年后继续获得收益。成本每个工件一个完整的生产周期加上审查，并且回报在任务后的一个季度，而不是任务的一周。
5. **社区和活动** - `developer-community-launch`、`developer-community-moderation`、`developer-champions`、`developer-community-health`、`developer-meetup-program`、`developer-event-sponsorship`、`conference-cfp-submission`、`tech-talk-outline`、`developer-live-demo-design`、`oss-sponsors-fundraising`、`oss-sponsors-brand-strategy`。购买其他集合产生的任何关系。成本这里最长的提前期 - 控制他人控制的日历、持续的版主职责，以及打开空间到它值得阅读之间的几个月。
6. **项目和公司基础** - `devrel-strategy`、`developer-segmentation`、`devrel-metrics`、`devrel-analytics`、`devrel-budget-allocation`、`devrel-team-structure`、`developer-education-strategy`、`devtools-business-model`、`devtools-pricing-strategy`、`developer-first-gtm`、`open-source-company-strategy`、`developer-ecosystem-strategy`、`open-standards-strategy`、`oss-governance`、`oss-license-strategy`、`tech-employer-branding`。购买每个后续会话都依据的规则：项目如何评价、谁可以合并、公司提供什么。成本需要工程、法律、高管以外的批准，并且大多数只能通过另一次谈判逆转。

`devrel-career`和`devrel-radar`位于此梯子之外，不在其底部。它们回答个人实践或保持更新的问题，而不是项目问题；当目标是它们时，它们按定义被运行1，否则它们根本不属于短名单。

- 效率：`诊断 > 首次运行表面 > 发布节奏 > 内容 > 社区和活动 > 基础`
- 价值：`基础 > 首次运行表面 > 社区和活动 > 内容 > 发布节奏 > 诊断`
- 努力程度：`基础 > 社区和活动 > 内容 > 发布节奏 > 首次运行表面 > 诊断`
- 合规成本：`基础 > 社区和活动 > 内容 > 发布节奏 > 首次运行表面 == 诊断（无）` - 许可证或治理决定会绑定所有未来的贡献者，并且只有在重新许可时才会解除；社区空间使你成为其他人的言论的版主和报告的持有者；赞助资金跨越了披露线；已发布的帖子和新闻需要批准且无法撤回；发布说明是关于破坏性变更的公开声明。诊断和首次运行表面在零上持平：两者都可以读取和编辑自己的仓库，并且不发布任何关于其他人的声明，尽管首次运行表面需要合并的拉取请求，而诊断不需要。

基础在价值上领先，在效率上最后，因为批准需要数周时间，而产出在落地当周是看不见的。

这就是效率顺序所缺乏的：第六类的核心技能。`devrel-strategy` 和 `oss-license-strategy` 是最明显的例子——最高的协调成本，本周没有任何可发布的内容——因此一个按比例排序的顺序会永远打磨 README，而每个后续的会议都会重新争论这个项目的目的以及公司可能会提供什么。

当以下情况发生时，直接将第六类提升到第一级：

- 没有人能说出资助驱动程序（Q4 返回为空或声称所有七个）。
- 在已经接受外部贡献的仓库中不存在许可证或治理文件。
- 相同的范围争论会一节接一节地出现。
- Q7 的答案是 (d) 站立，并且有批准可用。

默认情况下：在第一类中打开短名单，并停留在那里，直到诊断命名一个低于它的类别。一次只向下移动一个类别，并且永远不会超过诊断标记为缺失的类别。

从短名单中删除被排除的类别；永远不要将其降级到最后一位，因为被排除的技能停放在底部会默默地重新出现为范围。

- 有一个声明的解锁条件 - 将其移动到“现在不做”列表，并附带该条件。
- 没有条件 - 完全从输出中删除它。

排序是一个默认值，不是一个法律——它会随着采用动议和执行者的变化而变化。根据面试和检测刚刚告诉你的内容重新排序，并大声说出哪个答案移动了哪个类别：

- 一个非商业的开源项目没有买家（Q3d）从短名单中删除 `devtools-pricing-strategy`、`devtools-business-model` 和 `developer-first-gtm`，并提升 `oss-governance` 和 `oss-sponsors-fundraising` 在第六类和第五类中。
- 个人自助采用（Q3a）提升第二类和第四类。
- 组织购买（Q3b）将 `developer-case-study` 和 `developer-first-gtm` 提升到它们默认的位置以上，因为签署者永远不会运行快速入门。
- 资助驱动程序（Q4）删除整个类别：
  - 销售支持删除第三类的分类条目，除非项目是开源的。
  - 贡献者社区直接删除 `developer-first-gtm` 和 `devtools-pricing-strategy`。
  - 雇主品牌将 `tech-employer-branding` 提升到第一级，因为它拥有该驱动程序整个计划，并排名它下属的每个内容赌注。
- 阶段“还没有正式的” (Q5a) 删除 `devrel-team-structure`、`devrel-budget-allocation` 和 `developer-community-health`——没有团队，没有预算，也没有基线来衡量。
- 没有工程支持文档 (Q6c) 删除第二类的代码相关条目，并保留 `readme-optimization`，它不需要工程时间。
- 没有分析访问权限 (Q6e) 删除本会话中的 `devrel-analytics` 和 `developer-community-health`，并将它们移动到“现在不做”，由仪器解锁。
- 需要法律或安全审查 (Q6d) 延长第四类、第五类和第六类，而不改变它们购买的内容——最好这样说而不是默默地降级它们。
- 一个固定日期 (Q6) 提升在该窗口期内起作用的内容：
  - 会议日期将 `conference-cfp-submission` 和 `developer-live-demo-design` 提升到第一级，以供该季节使用。
  - 发布日期提升第三类。
- “一次性，仅维护人员时间” (Q7a) 将短名单缩减为两个来自第一类和第二类的条目。
- “站立，有批准可用” (Q7d) 将第五类和第六类提升到它们默认的位置以上。
- 一个已经拥有的资产会改变比例，而不是价值：一个已仪器化的分析堆栈，一个已经部署的文档站点，或一个已经接受的会议名额会使相关技能的难度接近于零——提升它。
- 一个已决定的项目 (Q2) 直接离开短名单；不要对已经不在选项中的内容进行排名。
- 检测也会移动类别：
  - 一个没有 CONTRIBUTING 文件的仓库提升 `oss-contributor-onboarding` 在第二类中。
  - 一个 git 日志显示在诊断之前有数月的停滞点，然后才进行任何构建。
  - 一个现有的文档站点有一个已经经过审计的信息架构，删除它的第一类条目。

## 5. 上下文工件

在项目根目录下创建或更新 `devrel-context.md`——一个版本化的文件，当项目存在于 git 中时与项目一起提交，并且是使下一次启动变得温暖的单一事实来源。它的部分：

- 产品和受众。
- 项目：资助驱动程序、支柱组合、阶段和团队。
- 拥有的表面。
- 测量。
- 状态：进行中、已决定与开放、包括结果必须在何时之前落地的约束、一次性与复合的界限以及努力上限。
- 拥有决策权的利益相关者。
- 会议记录。

最后三个约束字段是允许热启动重新排序短名单和例程，而无需重新询问 6 和 7 的问题的原因。有关模板、示例和负面示例，请参阅 [参考资料/context-artifact.md](./references/context-artifact.md)。

- 在热启动时：读取它，不要重新构建它。生成 5 行状态摘要，追加一个会议记录行，并仅修补已更改的字段。
- 可选地修补项目的代理指令文件，包含项目的不变量（受众动议、资助驱动程序、拥有的表面、硬约束），以便每个未来的会议都能在不加载此技能的情况下继承它们。
- 不要为项目尚未赢得的工作搭建工作树。只搭建本会议需要的结构——过早的结构会固化项目尚未做出的决定。
- 只有当项目实际上积累了有争议的决定时才保留决策日志；否则，“已决定与开放”字段就足够了。一个空的仪式日志会过时，并侵蚀对工件的信任。

在会议结束前更新工件，每次会议——一个未书面的会议在下一次是冷启动。

## 6. 记忆

如果你的 harness 具有持久记忆，则从上下文工件中派生记忆条目——永远不要反过来。工件保持为事实来源，因为记忆对队友来说是看不见且无法审查的；记忆优先的流程会为每个用户分支项目状态。

- 在面试完成后和 § 4 输出形状之前，将面试回答持久化到记忆中——首先将捕获的答案写入上下文工件，然后从工件中派生记忆条目。永远不要直接从答案写入记忆，并且永远不要因为答案感觉明显而跳过工件。
- 将记忆存储在以下三个位置之一：用户环境的本地、团队知识库或 git 仓库中的 `memories/` 目录。使用索引文件对其进行索引，该文件列出了每个条目并附带一个单行钩子。
- 在热启动时，将记忆与工件进行比较。当它们出现分歧时，提出协调——工件默认获胜；在覆盖任何一方之前先询问。
- 永远不要将以下内容放入记忆：
  - 社区成员或贡献者的个人数据。
  - 行为报告和调解案例。
  - 未宣布的发布和保密新闻。
  - 保密的赞助和活动比率。
  - 未发布的定价。
  - 尚未获得案例研究批准的客户名称。
  - 公开边界中来自构建的安全敏感细节。
- 在你第一次写入记忆时声明这些排除项。
- 当记忆存储在 git 仓库中时，永远不要无声地提交它。每次都显示差异并获取批准。

## 7. 例程

如果你的 harness 支持计划例程，请提议 2 到 4 个——始终在创建任何内容之前显示为干运行，每个例程都有一个明确的结果通道。没有结果通道的例程是用户在一周内会静音的噪音。

例程的成本不是其设置，而是每次触发时所需的注意力乘以触发频率；它的价值是在决策仍然开放时向某人展示的决策。根据该比率对候选者进行排序——每单位站立努力的价值，最高优先——并从上到下提议：

1. **发布标签文档传递** → `samber/developer-relations-skills@changelog-writing`，并且在发布是主要版本时加上 `samber/developer-relations-skills@version-migration-guide`。只有在标签落地时才会触发，覆盖已经编写的提交和拉取请求，并且它是唯一一个可以在发布之前而不是在用户遇到破坏时到达用户的例程。
2. **每月或每季度重新启动此启动。** 每次触发近于零，并且它保持工件和路由表当前——这是阻止其他例程在工作不再存在时触发的关键。将其节奏与项目的 git 日志中的节奏相匹配。
3. **CFP 截止日期清理** 在季节性目标活动之前 → `samber/developer-relations-skills@conference-cfp-submission`。每个季节只有几次触发，每次都是对截止日期列表的简短读取，对绝对截止日期：错过它，该阶段将一年内消失。在 CFP 季节之外不会购买任何内容，这就是它不是第一级的原因。
4. **定期问题和拉取请求队列审查** → `samber/developer-relations-skills@oss-issue-triage`。购买一个保持可回答的队列，而不是一个会累积成一个被放弃的项目。它在集中中具有最高的站立成本：每次通过一个会议，加上维护人员回答它表面的一切。只有在有人拥有后续跟进时才安装它。
5. **季度内容规划** 在季度开始时 → `samber/developer-relations-skills@devrel-content-calendar`。每年四个规划会议，购买一个季度内容，这些内容针对真实锚点而不是本周发生的任何事情进行发布。
6. **定期测量读取** → `samber/developer-relations-skills@devrel-metrics`（项目）或 `samber/developer-relations-skills@developer-community-health`（仅社区）。购买一条某人可以采取的行动趋势线——但在建立基线之前，它只会定期大声朗读噪音。

- 效率：`发布标签传递 > 启动重新启动 > CFP 清理 > 队列审查 > 内容规划 > 测量读取`
- 价值：`队列审查 > 发布标签传递 > 内容规划 > 测量读取 > CFP 清理 > 启动重新启动`
- 努力程度：`队列审查 > 内容规划 > 测量读取 > 发布标签传递 > CFP 清理 == 启动重新启动`
- 合规成本：`发布标签传递 > 内容规划 > 测量读取 == 队列审查 == CFP 清理 == 启动重新启动（无）` - 发布说明和迁移指南是关于破坏性变更的公开声明，并且无法撤回；内容日历安排这些发布，但不会对它们做出承诺。四个在零上持平的都读取内部或已公开的状态，并将其发送到团队；CFP 清理和启动重新启动在努力上也持平，因为每个都是每次触发一个近于零的读取。

启动重新启动是最便宜候选者，但仍排在第二位，而不是第一位——证明廉价和高效不同。队列审查在价值上领先，在效率上排在第四位，因为它每次通过都需要一个会议，并且维护人员需要回答每个提出的问题。

默认情况下：运行 1-2 个例程。当 CFP 季节开放时添加第 3 级，一旦有人拥有分类跟进，就添加第 4 级。永远不要超过 4——上限是保护重要例程免受那些触发到空中的例程的影响。

该排名是一个默认值，不是一个法律；它会随着表面和执行者的变化而变化。根据面试重新排序它，并说出哪个答案移动了哪个例程：

- 一个开源表面 (Q1b) 将队列审查提升到 CFP 清理之上。
- 一个活动表面 (Q1d) 具有会议日期将 CFP 清理提升到第一级，以供该季节使用。
- 没有分析访问权限 (Q6e) 删除测量读取，而不是降级它。
- “还没有正式的” (Q5a) 也删除它，因为没有基线可以用来进行趋势分析。
- 维护人员时间仅 (Q6b)，或“一次性，仅时间” (Q7a)，意味着安装一个例程——启动重新启动，而不是四个。
- 法律或安全审查需要 (Q6d) 延长发布标签传递，而不改变它购买的内容。
- 一个团队已经运行每周分类轮转，使第 4 级成为重复的，因此将其降级，而不是两次清理相同的主题。
- 一个已经仪器化的分析堆栈，或一个已经在标签上构建的文档管道，使其依赖的例程的难度接近于零——提升它。

将触发锚定到 DevRel 日历——发布列车日期、CFP 截止日期、会议日期、预算审查、社区仪式——而不是任意日期，并且在存在事件触发时优先于日程：标签推送比“月初”更适合发布说明。在添加新例程之前，列出并清理上一季度留下的过时例程。

如果 harness 没有计划例程，则回退到一个定期日历提醒（“DevRel 检查 - 重新运行开发者关系启动”），然后停止。有关干运行格式、日历锚定、事件触发偏好和清理清单，请参阅 [参考资料/routines.md](./references/routines.md)。

## 8. 调用示例

- “启动一个新的 devrel 项目——我们刚刚开源了我们的 SDK，并且没有人使用它。” → 冷启动：检测、面试、路由、写入工件。
- “我需要哪个 devrel 技能？我们的文档很好，但注册从未达到生产。” → 路由询问：与表格匹配，消除歧义，如果都不适用则命名差距。
- “运行我的 devrel 检查。” → 热启动：5 行状态摘要、会议目标问题、重新路由。
- “我从哪里开始？我是第一个 devrel 雇员，我不知道第一个该做什么。” → 冷启动：预期一个有序链，而不是单个路由。

## 9. 失败模式

- **强行匹配。** 将最近似的技能拉伸到它不涵盖的任务上会浪费一个会话并隐藏差距。说“都不匹配”并命名这个差距。
- **将所有文档问题路由到同一个技能。** 快速入门、教程、操作指南和参考是四种不同的工作——而且这个集合根本没有操作指南技能。首先检查路由参考中的“Docs-authoring fork”部分。
- **强行匹配平台或活动制作任务。** API设计、webhooks、SDK策略和市集操作属于`samber/developer-platform-skills`；组织自己的会议属于`samber/dev-event-organizer-skills`。建议使用兄弟集合。
- **在热启动时重新面试。** 该工件存在的目的就是为了避免重复提问。只问会话目标。
- **根据猜测的范围进行路由。** 只从路由参考中声明的范围进行路由；一个合理的猜测会自信地错误路由。
- **跳过资助驱动问题。** 没有它，策略、指标和预算路由都会崩溃成用户必须手动重新范围的建议。
- **无限制的面试。** 超过7个问题后，启动会话变成用户放弃的表单。
- **一个平坦的短名单。** 八个看起来相同的选项由品味或哪个排在最前来选择。按每单位努力的价值排序，并在每一行上命名双方，否则用户无法选择。
- **以最便宜选项开头。** 便宜和高效是不同的排序，只有后者回答“首先是什么”。一个近零的常规操作购买近零，只是一个舍入误差，而不是快速获胜。
- **对路由表或链进行排名。** 范围是一个匹配测试，链是依赖顺序；对其中任何一个施加比率都会创造一个不存在的偏好。
- **将排除的技能降级而不是删除。** 面试将其从表中移除，停放在短名单底部，两个月后会重新出现为范围。删除它，或将其移至“稍后”并附带其解锁条件。
- **让比率使基础受饿。** 类6在每次效率轮中都失去，而一个正在建立的程序首先需要它。在以类1级别开放之前，检查其晋升条件。
- **没有输出渠道的常规操作。** 它们发射到虚空并被静音，埋葬了那个重要的常规操作。
- **无声提交的内存。** 同事们无法审查他们看不到的着陆点。差异和批准，始终。
- **过时的路由表。** 每当集合发生变化时（技能添加、重命名、删除或重新范围），更新表格、路由参考、边界分支、链和差距列表。一个过时的路由器将用户发送到不再存在的技能，这比没有路由器更糟。

## 10. 通过标准

在结束会话之前，检查每个项目。如果有任何失败，修复它并重新检查——不要在失败的标准上关闭会话。

1. 每个推荐的技能的声明范围实际上与所述任务匹配——重新阅读其描述以确认。
2. 零路由到上述表格之外的名字。
3. 面试在其上限内：冷启动最多7个问题，热启动只有会话目标问题。
4. `devrel-context.md`在会话结束前被编写或更新，包括一条会话日志行。
5. 每个提出的常规操作都显示了干运行，并且有一个明确的输出渠道。
6. 短名单和常规操作集都是按每单位努力的价值排序，每个条目命名它攻击的瓶颈及其成本——并且在面试答案将某物移出其默认位置时，重新排名被大声说明。
7. 面试排除的每个类都完全离开了短名单，而不是坐在它的底部。
8. 路由表和任何提出的链都未排名——匹配测试和依赖顺序分别。
