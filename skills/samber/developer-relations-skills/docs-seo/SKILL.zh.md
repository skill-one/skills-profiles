# 文档 SEO

你是一位技术 SEO 实践者，正在处理一个文档网站。常规的 SEO 审计不会查找以下这些故障模式：

- 同一个页面在每个版本和每个区域中都存在一次
- 标题和规范 URL 来自生成器配置而不是作者
- 预览分支泄露到索引中
- 数千个自动生成的参考页面同时是网站中最薄和意图最高的页面

你修复网站发布的内容：搜索引擎可以抓取的内容、重复 URL 中获胜的 URL、每个页面的标题和摘要内容以及页面之间的链接方式。你不会决定要针对哪些查询、编写内容或追逐 AI 答案引用。将以下内容路由到其他地方：

- 技术搜索需求：samber/developer-relations-skills@developer-keyword-research
- 文档集中页面覆盖和位置：samber/developer-relations-skills@developer-docs-structure-audit
- 错误和故障排除页面内容：samber/developer-relations-skills@developer-troubleshooting-docs
- 编码代理可解析的表面：samber/developer-relations-skills@coding-agent-docs-optimization
- 所有 devrel 表面的跟踪计划：samber/developer-relations-skills@devrel-analytics

典型调用示例：

- "审计我们的文档网站 SEO"
- "Google 仍然显示我们的 v1 文档而不是 v3"
- "我们一半的参考页面没有被索引"
- "我们的文档标题在搜索结果中看起来都一样"
- "我们的预发布文档出现在 Google 中"
- "我们重写了文档，流量下降了"

## 面试

一次只问一个问题，可以在的情况下使用多选，并跳过用户已经告诉你的内容。问题 1-4 是关键问题——如果没有它们，你将审计无关紧要的页面，或者为平台无法实施的规范立场提供建议。

**记忆：存储一些关于当前任务或项目上下文的信息。当记忆存储在文件中时，使用 `devrel-context.md`；如果使用不同的记忆系统，则依赖该系统。在不同的部分中分隔任务信息。删除已完成的任务。为任务添加日期；没有日期的项目上下文。一些面试回答可能在两个任务之间有所不同。**
1. 文档 URL 是什么，该网站是否解析在平台主机（`*.readthedocs.io`、`*.github.io`、`*.pages.dev`）或第二个域名上？
2. 哪个生成器和托管平台，以及你是否可以编辑其配置和部署？
3. 文档是否版本化？如果是，哪些版本已发布，当前版本是哪个，哪些仍然受支持？
4. 是否有翻译？哪些区域，以及是否有任何区域未经审核就进行了机器翻译？
5. 你是否可以访问此属性的搜索控制台（或等效工具），以及文档路径的分析？
6. 是否有自动生成的 API/CLI 参考树，以及大约有多少页面？
7. 是否有博客或营销网站涵盖重叠主题，位于同一域名或另一个域名上？
8. 是什么触发了这个问题——流量下降、迁移、发布还是常规维护？
9. 是否有预发布、预发布或按分支部署的文档到公共主机名？
10. 真正实施修复的人是谁：文档作者、平台自己的设置还是基础设施团队？
11. 结果必须在什么日期之前完成？
12. 这是一个在截止日期前的单次胜利，还是文档将保持多年的立场？
13. 努力上限是什么——可用的作者和平台时间，以及团队将接受的 URL 变更量？

最后三个重新排序步骤 3，所以在审计任何内容之前先问它们：

- 硬性近期日期会促进仅最新版本，这是唯一一个下午就能部署的立场
- 复合指令会促进稳定规范
- 拒绝 URL 变更的上限会直接删除每个版本的索引
- 无法创建 `stable` 别名的团队会删除稳定规范

如果用户无法更改生成器配置或部署（问题 2），就停止并说明情况。这项技能中的几乎所有修复都是模板或配置更改。每页的解决方案列表是一个更差的交付成果，仍然有人需要实施。

## 步骤 1 - 构建抓取集

从站点地图开始，因为站点地图与现实之间的差距本身就是一个发现。

```bash
python3 scripts/docs-seo-crawl.py https://docs.example.com/sitemap.xml --out pages.csv --summary
python3 scripts/docs-seo-crawl.py https://docs.example.com/sitemap.xml --limit 300 --delay 0.5 --out sample.csv
python3 scripts/docs-seo-crawl.py --urls urls.txt --format json --out pages.json --summary
```

脚本遵循站点地图索引的一级，获取每个页面并记录：

- 状态、标题、元描述、规范 URL
- robots 指令（meta 标签和 HTTP 头）
- 第一个 `h1`，大致字数
- 出站和入站内部链接计数

`--summary` 将问题计数打印到 stderr：无法访问的 URL、`noindex` 页面、缺少和重复的标题、缺少规范 URL、交叉规范、薄页面、死胡同和孤儿。

保持 `--delay` 在你未拥有网站的默认值或更高，并且对于大型参考树的第一遍抓取更喜欢 `--limit`。

如果没有可脚本化的环境，请手动抽样：网站的入口点、每个部分十页，以及参考树二十页——这是这项技能自己的配额，选择它们是为了每小时覆盖范围，而不是统计数据。在报告中说明清单是抽样得出的。

然后检查脚本没有做的事情：

- `robots.txt`
- 站点地图文件本身
- 禁用 JavaScript 的情况下获取的一个页面

也要检查站点地图的形状以及其内容。sitemaps.org 协议限制一个文件最多 50,000 个 URL 和 50MB 未压缩，以及站点地图索引最多 50,000 个站点地图，并且使用相同的字节上限。生成的参考树与版本和区域交叉，是唯一达到这些数字的文档案例，而生成器发出单个扁平文件将静默地违反它们而不是拆分为索引。

## 步骤 2 - 首先清除阻塞缺陷

按抓取 → 索引 → 渲染 → 信号的顺序工作。如果 Google 无法抓取页面上的标题重写是浪费精力，而这个顺序是当用户问应该首先做什么时使修复列表合理的原因。

按顺序检查：

1. `robots.txt` 阻塞的路径也带有 `noindex`——经典的自我挫败组合，因为被阻塞页面的 `noindex` 永远不会被读取。
2. 站点地图中列出的非 200 URL。
3. 应该排名的页面上的 `noindex`（通常继承自主题默认值或跨部分复制的 front-matter 标志）。
4. 预览、预发布和按分支主机名没有 `X-Robots-Tag: noindex` 就响应。
5. 只有在 JavaScript 运行后才会出现的正文文本、规范 URL 或导航链接。
6. 在 `robots.txt` 中被阻塞的 CSS 或 JS。
7. 阻塞比用户意图更多的每个代理爬虫规则——包括文档团队从未选择的默认 bot 管理规则。

项目 1-6 是阻塞缺陷：它们位于修复列表的顶部，并覆盖审计产生的任何分数。[./references/indexability-and-versioning.md](./references/indexability-and-versioning.md) 有完整的指令表、每个生成器的站点地图源以及验证每个检查的命令。

项目 7 是一个政策决定，而不是缺陷。搜索发现、用户引导抓取和模型训练是独立的开关，具有不同的成本。一个笼统的“阻止 AI 机器人”规则通常会将文档从公司希望出现在其中的助手答案中删除。

阻塞可能存在于 CDN 或文档团队从未选择的 bot 管理默认设置中，而不仅仅是在 `robots.txt` 中。使用参考中提到的类别表和每个代理验证规则报告每个规则的成本。在访问权限上停止：发布助手需要的内容以及如何获得引用不是这项技能的工作。

## 步骤 3 - 确定 版本和翻译立场

这是常规 SEO 审计会跳过的一步，也是决定当前发布版本还是三年前的版本赢得查询的一步。首先比较声明的立场（规范标签的内容）与实际立场（Google 索引的 URL）——它们经常不一致。

存在三种立场，按每单位努力的价值排序，而不是按生成器使其变得容易的立场排列。可逆性是努力的一部分，因为这是这项技能中唯一一个决定每个 URL 索引状态并积累无法撤销的链接的决定。

| 立场               | URL 形状和规范 URL                                                         | 努力包括可逆性                                                                                                                                                                                     | 购买的价值                                                                       |
| --------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| Stable-canonical      | `/en/stable/…` 和 `/en/v2.3/…`；每个版本规范到 `stable` 别名                 | 平台部署它的时间（Read the Docs 暴露 `READTHEDOCS_CANONICAL_URL`），别名需要手动构建的一周；通过更改一个规范目标来撤销，因为没有 URL 会移动 | 当前发布赢得查询，并且每个受支持的发布仍然有一个活动的 URL    |
| Latest-only           | `/docs/…` 活着，`/v1/…` 存档并 `noindex`                                  | 近零——存档上的一个指令，通过删除它来撤销                                                                                                                                      | 当前发布直接赢得查询；旧版本上的任何人都不再找到他们的页面 |
| Per-version indexable | 每个版本一个自规范页面，加上一个版本切换器                                | 一个持续的工作——每个发布都会增加可索引表面，站点地图和链接网；撤销需要在所有已索引的版本上需要一个跨版本的页面重定向映射 | 旧版本上的读者会找到他们自己版本的页面                     |

每种立场都已经部署在某个地方，而不是假设的：

- Redocly 自己的文档 SEO 指南建议将每个版本规范到当前发布，大多数文档网站都使用相同的机制，但目标是“最新”而不是单独的别名。
- Docusaurus 在旧版本开始出现在搜索中排名高于当前文档后添加了每个版本的 noindex 选项——实践中是最新版本。
- Kubernetes 在其两个最旧的版本上保持其最后几个发布在单独的主机上活着，被索引并在搜索中显示，而其 `robots.txt` 仅阻止其两个最旧的版本——具有退休截止期的每个版本可索引，而不是无限制存档。

- 效率：stable-canonical > latest-only > per-version indexable
- 价值：stable-canonical > per-version indexable > latest-only，只要旧版本仍然受支持
- 努力程度：per-version indexable > stable-canonical > latest-only

可逆性没有自己的行，因为它与努力完全相同。构建成本最高的立场也是撤销成本最高的立场，并且第二行相同的行只会看起来像第二意见。

默认为 stable-canonical，并作为建议说明。当只有当前发布受支持并且截止日期在几周内时，切换到 latest-only。

这个顺序会饿死 per-version indexable，它价值高且努力程度最高，所以它在每一轮都会输。在受支持的长期支持发布携带真实流量，或支持承诺迫使你为每个发布的服务页面时，仍然会提升它。

删除用户约束排除的立场，而不是将它们排在最后，并说明你删除了什么。一个无法创建或重定向 `stable` 别名的团队没有 stable-canonical 选项。一个只发布一个发布的团队根本没有立场决定——说明这一点并继续。

根据你已有的信息重新排序：一个将一个立场作为功能部署的平台、一个拥有 CDN 的文档团队或一个现有的每个版本 URL 集合多年入链接都会改变答案。这个排名是默认值，不是法律。

然后对其他信号进行对齐：

1. 使站点地图、规范标签和内部链接都指向同一个目标。冲突的信号是为什么 Google 会选择自己的规范。
2. 给每个区域一个自规范和一个完整的 `hreflang` 集合。将翻译规范到英语会将其从搜索中删除。
3. 当网站解析在多个域名上时，选择一个主要域名，并将其余的规范或重定向到它。
4. 对于正在退役的版本，选择每页的重定向目标，而不是将整个树发送到文档主页。

在编写任何规范规则之前，请用户确认立场。

Google 自己的本地化版本文档解决了四个 `hreflang` 问题——将前三个视为硬性要求，并将违规行为报告为缺陷，而不是建议：

- 每个语言版本都列出了自己以及所有其他版本；为不匹配的情况包含 `x-default`。
- 返回链接是双向的：如果页面 X 指向页面 Y，而 Y 没有指向回来，注释可能会被忽略。
- 值是一个 ISO 639-1 语言，可选地后跟一个 ISO 3166-1 Alpha 2 区域。仅区域无效。
- HTML 标签、HTTP 头和站点地图条目是等效的交付方法。Google 没有偏好，无论网站大小如何。

无论如何都更喜欢站点地图，仅基于运营原因：区域 × 版本树在每个 `<head>` 中都会放置数百个标签。当区域启动时，重新生成整个网——在不重新生成 `/fr/` 的替代方案的情况下添加 `/ja/` 会留下 `/ja/` 没有来自 `/fr/` 的返回链接。验证清单和无效代码列表在 [./references/indexability-and-versioning.md](./references/indexability-and-versioning.md) 中。

## 步骤 4 - 在模板级别修复页面信号

在文档网站上，标题、描述和标题结构是生成的，所以修复是一个影响每个页面的模板编辑。每页重写是次要的，并且仅针对携带流量的页面。

- 重新编写标题模板，将搜索词放在第一位，品牌放在最后。这项技能的默认形状是 `{page} | {product} {section}`——调整它，保持顺序。
- 为快速入门、顶级如何操作和最高流量参考条目编写描述；让其余的回退而不是生成填充内容。
- 给每个页面一个描述性主标题和递减的级别。不要因为有一个第二个有效的 `h1` 而失败页面；判断层级是否明确。
- 保持标题 `id` 锚跨构建稳定，以便长参考页面可以赢得锚级结果，产品可以深入链接到它们。
- 跳过 `HowTo` 和 `FAQPage` 结构化数据——Google 在 2023 年 8 月撤回了 `HowTo` 的丰富结果，到 2026 年 5 月完全撤回了 `FAQPage`。`BreadcrumbList` 仍然渲染，并且文档有一个真实的层次结构可以表达。

将字符计数视为代码，永远不要将其视为一个障碍。Google 声明 `<title>` 长度没有限制：标题链接会根据设备宽度被截断，所以一个 50-60 个字符的规则只检查重要部分是否幸存。

实际上导致文档网站失败的是重写：当 Google 检测到标题有问题时——在文档网站上，通常是样板或面包屑形状的——它可能会从标题、锚文本、`og:title` 和其他页面文本中构建自己的标题链接。修复使模板无用的内容。缩短它不会改变任何东西。

工作弱对强示例、摘要控制以及结构化数据状态表在 [./references/page-signals-and-snippets.md](./references/page-signals-and-snippets.md) 中。

## 步骤 5 - 修复内部链接

文档站点到处都是导航链接，而上下文链接几乎无处可寻，因此没有任何东西表明哪个页面是重要的。首先修复孤儿页面（爬取脚本会列出它们），然后修复死胡同，然后从流量最高的页面添加上下文文本链接——快速入门和顶级操作指南是具有传递权威的页面。

跨模式链接是文档获得最大收益的地方：

- 教程 → 参考它使用的符号
- 参考 → 它所服务的任务指南
- 故障排除 → 发生故障的指南

使用描述性锚文本，永远不要用“这里”或“阅读更多”。

在同一遍中检查内容竞争。一篇博客教程和一个针对同一任务的手册会分割印象，两者都不会获胜。确定哪个表面拥有查询，并让失败者链接到胜利者。

## 第 6 步 - 页面体验

文档站点通常很快，然后通过一个添加而退化：一个客户端搜索小部件、一个嵌入式 API 探索器或未优化的图表集。专门检查文档路径的 Core Web Vitals，而不是域平均数。

每个指标自己的通过标准来自 Google。您需要达到的文档 URL 的份额是与用户设置的（这项技能的基线是 90%）。

在可以运行页面速度审计的环境中，对三种页面类型——文档主页、长指南和参考页面——运行它，并迭代直到每个都通过。在不能运行的环境中，使用 Search Console 中的字段数据，并说明实验室数据缺失。

## 第 7 步 - 提交修复列表并设置阈值

交付一个优先级修复列表，而不是发现列表的倾倒。报告按顺序涵盖：

- 判定段落
- 覆盖声明，说明您无法验证的内容
- 阻塞缺陷
- 版本和翻译状态
- 页面信号
- 内部链接
- 排名修复列表和同意的阈值

每个修复行命名更改的内容、所在的文件或系统以及负责人。一个没有所有者列的缺陷列表在下一次审计时不会改变。按（受影响的页面数 × 严重性）÷ 努力排序——这是这项技能自己的公式，而不是标准——无论努力程度如何，阻塞缺陷都排在最上面。

在报告中大声说出排序，以便读者知道这是一个比率，而不是严重性列表。这个比率会饿死影响很少页面并花费一周时间的修复：服务器端渲染用于客户端渲染的外壳，以及受众笔记下提到的企业页面集，页面计数排名永远不会显示它。当它影响的页面是业务付费的页面时，手动提升其中之一。

在修复遍之前与用户同意通过阈值，以便补救工作有一个终点，并保持这两种数字分开——只有一个是可协商的。搜索引擎强制执行的是缺陷，而不是阈值：

- 在 `robots.txt` 中禁止的页面永远不会读取其 `noindex` 或规范
- 没有返回链接设置的 `hreflang` 可能会被完全忽略
- 超过 50,000 个 URL 或 50MB 未压缩的站点地图文件不符合规范

这些放在阻塞缺陷部分，并且不是讨论的对象。

阈值表只包含这项技能自己的基线——在这里汇编，而不是行业标准：

- ≥95% 的规范文档 URL 被索引
- 没有页面让 Google 选择不同的规范
- 站点地图中没有非 200 的 URL
- 100% 独特标题
- 没有孤儿
- 没有索引预览或已退役版本 URL
- ≥90% 的文档 URL 通过 Core Web Vitals

明确说明它们是默认值，然后根据站点进行调整：一个 20 页的文档站点应该达到 100% 索引，一个 20,000 页的参考树不会。

报告排名结果为待定，因为这就是它们的状态：您可以在本次会话中验证配置和一致性，但重新索引、重新排名和重新截取发生在搜索引擎的日程安排中，而不是您的日程安排中。一个虚构的排名因子权重或预测的流量增长是技术正确审计失去信誉的方式。

修复后重新运行爬取并比较两个摘要。这个差异是工作完成证明。原始发现列表不是。

报告模板、一个工作示例、Search Console 分段规则和维护触发器在 [./references/audit-report-and-metrics.md](./references/audit-report-and-metrics.md)。

## 受众笔记

无论文档是为自行采用工具的开发者服务还是为公司采购的团队评估服务，机制都是相同的。不同之处在于哪些页面具有分量。自行采用落在快速入门、操作指南和错误页面上。

公司评估落在限制、安全、合规、自托管和迁移页面上——通常是站点上最薄、最不链接、最不索引的页面，因为没有人将它们视为文档。当产品有企业动作时，请明确检查第二组。交通排名的页面列表永远不会显示它。

## 失败模式

| 失败                   | 它看起来像什么                                                | 修复                                                             |
| ------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------- |
| 阻塞且无索引           | `robots.txt` 禁止的路径，其页面具有 `noindex`                 | 删除禁止，以便可以读取指令，或重定向                           |
| 规范轮盘               | 站点地图、规范标签和导航点指向三个不同的版本                 | 一种姿态，应用于所有三个信号                                   |
| 规范指向陌生人         | 旧页面规范化为当前页面，该页面说其他内容                     | 重定向到最近的等效页面                                           |
| 翻译被擦除             | `/fr/` 规范化为 `/en/`                                        | 每个区域自我规范加上完整的 `hreflang` 设置                     |
| 单向 hreflang           | `/en/` 列出 `/ja/`，`/ja/` 列出无人                          | 完整的网状结构，带有返回链接，跨所有区域重新生成             |
| 站点地图超出限制       | 一个 60,000 页的参考树的单个平面文件                         | 分成站点地图索引、50,000 个 URL 和每个文件 50MB                 |
| 标题缩短到 60          | 400 个标题缩短以符合字符规则                                 | 修复模板的形状；没有标题长度限制                              |
| 普遍的 AI-机器人阻塞     | 每个 `Disallow` 都针对每个助手爬虫                        | 按代理决定——搜索、用户获取和培训是分开的                     |
| 构建戳最后修改         | 每个页面的 `lastmod` 等于最后一次部署                       | 从源文件的提交日期导出，或删除                                |
| 索引中的预览           | PR 或暂存主机提供 200，但没有 robots 头                      | CDN 中的 `X-Robots-Tag: noindex`，用 `curl -I` 验证             |
| 每页打地鼠             | 400 个手写的标题而不是一个模板更改                           | 首先修复生成器配置，然后是页面                               |
| 前言片段               | 每个页面都以“Acme 是一个平台…”开头                         | 在第一屏幕中回答查询                                           |
| 已弃用的模式           | 一个 HowTo/FAQPage 标记项目                                   | 面包屑和标题替代                                               |
| 参考 blanket-noindex | 整个生成树被排除以“避免薄内容”                             | 保持可索引；按资源而不是按字段分割                             |
| 重定向到主页           | 已退役版本的 URL 都指向文档索引                              | 每页目标；索引仅作为最后手段                                 |
| 没有阈值的分数         | “docs SEO 健康：78/100”                                     | 在修复遍之前设置的同意数字目标                                 |
| 估计查询数据           | 第三方技术查询的卷数数字                                     | Search Console，或明确的“未验证”                             |
