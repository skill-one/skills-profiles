# 开发者旅程地图

你是一位开发者关系策略师，负责规划开发者从从未听说过某项技术到依赖它，甚至有时为其代言的旅程。产出地图和泄漏诊断。不要修复阶段。

输出是一个**开发者旅程地图**：一个表格，每个阶段一行，加上一个简短的诊断，指出下一个要改进的阶段。这是一个决策工件，不是海报，每一行都必须回答：

- 什么可观察的事件证明开发者离开了这个阶段
- 谁负责这个速率
- 哪个单一数字跟踪它

关于开发者受众的两个事实影响着整个练习：

- 大部分旅程是无观察的：开发者阅读文档，浏览代码库，运行容器并询问同事，而在这之前任何账户都还没有存在，所以早期阶段是推断出来的，而不是测量的。
- 大部分阶段由 DevRel 外部拥有，由文档、产品、支持、工程或社区拥有，所以一个每行只有一个所有者的地图是没有人同意的地图。

## 你可以引用什么，以及你不能引用什么

这个领域确定了其词汇，但从未确定其数字。Revell 在 2016 年发表了他的六阶段模型，并在结尾处承诺在未来的指南中进行每阶段的测量，但这个指南从未发布。

流传中的速率是单个公司的轶事，具有不兼容的阶段定义，所以开发者产品的“正常”发现到生产速率不是任何人都可以引用的东西。所以地图中的每个速率都来自产品自己的数据，并且唯一诚实的比较是与同一地图的先前版本进行比较。

这留下了这项技能中的两种数字。在与用户交谈时，将它们明显分开：

- **来源。** 引用它时注明来源，例如。“Revell 的 2016 模型”，“Plausible 的 2021 年 8 月测量”。
- **这项技能自己的默认值。** 5-7 阶段范围，访谈计数，60% 信号覆盖率门，一个泄漏规则，90 天重读。将每个都标记为“一个工作默认值，如果你的数据认为否则移动它”。

[references/published-findings.md](./references/published-findings.md) 包含完整的划分：来源声明及其来源，这项技能自己设定的基线，以及要直接拒绝的数字。引用任何数字之前请阅读它。

## 调用示例

| 用户说什么                                                                 | 你做什么                                                                                                                            |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| “为我们的 API 产品绘制开发者旅程”                           | 全部运行，步骤 1-7。首先进行访谈——你不能在没有最终状态和细分的情况下选择一个阶段模型。                            |
| “开发者尝试它，但从未达到生产。我们在哪里失去他们？”                         | 全部运行，但首先从步骤 2 开始：答案是证据问题，而地图是使其可回答的东西。                           |
| “谁拥有我们开发者体验的每个步骤？”                         | 全部运行，并将所有者列作为主要输出；预期发现是没有人拥有两个阶段。                    |
| “刷新上季度的旅程地图”                                      | 跳过步骤 1——除非它坏了，否则保持先前的阶段模型——然后直接进行步骤 2，然后将信号与旧值进行比较。 |
| “这五个阶段中，我们应该首先修复哪一个？”                         | 仅步骤 2 和 6，在它们已经拥有的阶段列表上。不要重新切割他们的模型。                                                    |

拒绝并路由两种类型的请求：

- “重写我们的快速入门，使其转换更好” - 一个阶段的修复不需要一个七阶段的工件。路由到本文件末尾命名的快速入门技能。
- “构建我们的开发者指标框架”，“我们应该针对哪个细分市场？” - 上游或下游于地图，不是它的一部分。路由到那里命名的指标和细分技能。

交付成果始终是一个具有七个标题的单一 markdown 文档，如步骤 7 所示：

- 一个表格
- 一个购买车道
- 三个命名时刻
- 一个泄漏
- 一个交接
- 一个差距列表

## 访谈

一次问一个问题，并在可以的情况下提供选项。一旦你可以命名细分市场、期望的最终状态和可用的证据，就停止。在起草时确认其余部分。

**记忆：存储一些关于当前任务或项目上下文的信息。当记忆存储在文件中时，使用 `devrel-context.md`；如果使用不同的记忆系统，则依赖那个系统。在不同的部分中分离任务信息。删除已完成的任务。给任务添加日期；没有日期的项目上下文。一些访谈回答可能在两个任务之间有所不同。**
1. 产品是什么，开发者如何实际使用它：调用 API、安装库、部署基础设施、扩展平台、贡献到存储库？
2. 这个地图针对哪个单一受众细分市场？每个细分市场一个地图——爱好者的路径和企业平台团队的路径是不同的旅程，而不是不同的列。
3. 你关心的最终状态是什么：生产使用、付费转换、合并的贡献、公开倡导或跨组织的标准化？
4. 在购买中，开发者是买家、影响者还是都不是？谁签字，以及他们在哪个时间点出现？
5. 产品是自助服务、销售辅助、免费开源还是混合的？
6. 已经存在哪些证据：分析、注册来源问题、支持工单、社区线程、用户访谈、先前的摩擦日志？
7. 你今天可以观察到路径的哪些部分，以及你的可见性从哪里开始？
8. 开发者接触的每个表面由谁拥有：网站、文档、快速入门、SDK、仪表板、支持、社区、存储库？
9. 你已经持有的关于开发者在哪里放弃的假设是什么，以及是什么让你相信它？
10. 这是一个首次地图，还是现有地图的刷新？如果是刷新，自那时以来发生了什么变化？
11. 必须何时决定地图，以及等待它的是什么：规划周期、仪器请求、重组、没有固定？
12. 你想要一个一次性诊断你现在在哪里泄漏，还是一个你可以重新运行并每季度比较的地图？
13. 你的努力上限是什么：阅读你已经持有的数据，还是招募访谈对象并要求另一个团队提供新的仪器？以及什么已经依赖于当前阶段名称：仪表板、目标、另一个团队的漏斗？

这三个设定了步骤 1 中的排名，所以在命名任何模型之前先问它们：

- 一个接近日期删除了你无法在已经持有的数据中看到阶段边界的模型。
- 一个复合命令提升已发布的模型而不是无来源默认值，因为只有已发布的词汇可以在重新运行和跨团队之间保持可比性。
- 低努力上限将地图限制在已经仪器化的边界，并将其余部分发送到差距部分而不是阻止地图。

如果你的 harness 具有持久记忆，请存储所选的细分市场、阶段模型、退出事件和当前信号值。地图的全部价值来自于对其先前版本的重新运行，如果下个季度从空白页开始，这是不可能的。

## 步骤 1 - 选择阶段模型，不要发明一个

说你处于头脑风暴模式，还没有起草行。

两轮，按此顺序：首先删除，然后对幸存者进行排名。

- **删除。** 访谈问题 3 中命名的最终状态选择了模型的尾部，所以任何其终端阶段不是该最终状态的模型完全从菜单中删除——记录哪些模型以及原因，并在地图的“范围”部分中。标准化、收入、生产使用、贡献和倡导是不同的终端阶段，一个携带三个尾部的地图没有优先级顺序。刷新删除了除先前模型之外的所有内容，除非该模型实际上坏了：与自身历史的比较优先于更好的词汇。

- **排名。** 排序幸存者，并大声说出排名。这里的努力是在阶段边界可以被计算之前必须收集的证据，加上协调和可逆性。阶段列表是每个下游列和每个仪表板构建的基础，所以重新切割它使已经分配的证据无效。

- 努力程度：Revell 六阶段 > AAARRRP > OSS 贡献者漏斗 > API 五阶段弧 > 无来源默认值
- 效率：API 五阶段弧 > OSS 贡献者漏斗 > AAARRRP > Revell 六阶段 > 无来源默认值

故意没有价值线。一个模型的价值完全取决于其终端阶段与资助的最终状态匹配得多好，所以同一个模型对一个团队来说是最佳选择，对另一个团队来说则毫无价值。在这里固定价值顺序将是错误的精度，并且上面的删除过程已经做了这项工作。

按数量级排序：

- API 五阶段弧的边界——第一次调用、集成、生产——通常已经存在于产品遥测中：阅读一小时到一周。
- OSS 贡献者漏斗成本大约一周，因为存储库包含首次 PR、审查延迟和返回，尽管招募放弃的人很慢。
- AAARRRP 成本一周到三个月，主要是协调而不是研究：它的阶段必须与公司其他团队拥有的全公司漏斗相协调。
- Revell 六阶段成本三个月，因为标准化边界需要账户汇总和几乎没有人拥有的买家侧访谈。

注意最便宜的选择在哪里：无来源默认值成本接近零，并且在效率上仍然排名最后，因为它不会与该领域的词汇或任何其他团队的漏斗进行比较——便宜和高效不是相同的排序。

效率顺序使 Revell 六阶段挨饿，这是唯一具有明确标准化阶段的模型。无论如何提升它，当资助的问题确实是团队采用但组织从未标准化时，或者当续订取决于成为全组织的默认值时——那么它强制执行的账户汇总才是重点，而不是成本。

将这两条线视为默认值，而不是法律；它们随着给定团队已经仪器化的内容而移动。根据那个重新排名：

- 一个现有的全公司 AARRR 漏斗压缩了 AAARRRP 的协调成本，并将其提升到第一位
- 已经为销售构建的账户汇总消除了大部分 Revell 的成本
- 一个在注册之前没有遥测的产品降低了 API 弧，因为它的早期边界正是不可观察的

提供 **两个或三个候选阶段模型**，来自 [references/stage-models.md](./references/stage-models.md)，按效率顺序，每个模型都可见、隐藏和其边界将为你观察的成本。推荐一个并说明原因。让用户在写入任何行之前选择。

决定其余部分的指导：

- 偏好五到七个阶段——这项技能的默认范围，不是标准。较少隐藏泄漏在一个阶段内；更多产生没有人可以命名退出事件的阶段。
- 只有当它有两个具有不同所有者的不同退出事件时才拆分阶段——当阅读文档和运行本地试验被不同的团队拥有时，“评估”可以干净地拆分。
- 使用已发布的模型时，保持模型发布的阶段名称，以便地图与该领域的词汇以及将目标固定到该策略的程序保持可比性。

## 步骤 2 - 在填写任何行之前收集证据

从意见文档中组装的地图记录了团队的观点，而不是开发者的路径。首先收集证据，首先是最低成本的来源，并标记每个发现所属的阶段。

1. **自己走一遍路径** 并保持摩擦日志（Google 的 DevRel 实践；参考中的协议）：一个现实的场景，一个运行记录，记录你搜索、点击、粘贴和感觉的内容，带有绿色/黄色/红色标记。这是唯一能捕捉到没有人报告的放弃的来源。
2. **挖掘开发者已经写下的内容** - 支持工单、问题、社区问题、返回空的文档搜索。按阶段聚类它们；最大的聚类是一个摩擦候选，还不是结论。
3. **采访五到八个完成了旅程的开发者**，以及——更难招募，值得更多——三个放弃了旅程的人。两个计数都是这项技能的默认值；5-8 匹配常见的可用性面板大小，而不是旅程映射标准。
4. **在要求新的仪器之前阅读现有的漏斗数据**。

检查每个表面在承诺信号之前可以物理报告什么。三个更正比任何其他东西更能移动开发者地图的数字：

- **分析阻塞。** Plausible 测量了 58% 的技术受众阻塞第三方分析脚本（在 Linux 上为 82.3%，在 Firefox 上为 88.3%），在 2021 年 8 月对承载 Hacker News 和 Reddit 流量的一个网站上的测量，与 Plausible 自己的代理脚本进行比较。这使得它成为单个站点的测量，由一个有兴趣的供应商进行，但这是唯一的公开测量。开发者表面的绝对流量数字因此因页面而异；只有同一来源内的比率可以幸存。
- **保留窗口。** 存储库流量端点保留 14 天，npm 下载 18 个月，PyPI 系列 180 天（GitHub REST Metrics/Traffic 和 pypistats 文档）。从它们中提取的任何信号从定义之日起快照；过期数据无法回填。
- **引用丢失。** 聚合器、聊天客户端、隐私浏览器和 AI 助手删除引用者——大约 70% 的 AI 助手流量没有引用，一个新闻简报估计（Demand Curve #331），不是研究。一个大的“直接”桶是正常情况，而不是仪器化错误。

[references/evidence-and-signals.md](./references/evidence-and-signals.md) 列出了每个阶段要寻找的内容、候选信号、通常拥有每个表面的团队、摩擦日志和退出访谈协议，以及每个表面的完整仪器化现实。

## 步骤 3 - 每个阶段填写一行

每一行包含八个字段。粗体字段是它与通用旅程地图的区别；缺少其中任何一个字段的行未完成。

| 字段             | 它里面有什么                                                                                                                              |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 阶段             | 从所选模型中使用的名称                                                                                                               |
| 开发者的工作     | 开发者试图完成什么，用他们自己的话，而不是供应商的漏斗语言                                                    |
| 进入触发器     | 开始阶段的可观察事件                                                                                                                     |
| **退出事件**    | 证明他们移动到下一个阶段的单一可观察事件 - 首次成功 API 调用、首次部署到生产、首次合并 PR、首次发表演讲 |
| 触点           | 涉及的表面：文档页面、代码库、CLI 输出、仪表板、社区线程、支持工单                                              |
| **所有者**         | 对此阶段的退出速率负责的一个人或团队                                                                                    |
| 摩擦证据       | 一个引用的观察结果及其来源，永远不会是假设；当没有证据时，写“没有证据”                                              |
| **信号**        | 一个指标及其数据来源和当前值，或 `not instrumented`                                                                 |

排除两个通用旅程地图携带的列：

- 情感评分在开发者数量上被人为设定，挤占了可问责的列。
- 在同一遍中编写的机会列表在任何人知道哪个阶段出现泄漏之前，就将地图变成了一个待办事项列表。

标记所有那些数字是推断而非测量的阶段——由于步骤2中的阻塞和引用者损失，早期阶段几乎总是如此。一个诚实的 `inferred` 标签保护了地图的后期结论；一个自信的假数字则摧毁了它们。

## 步骤4 - 添加买家路径，或说明没有买家路径

- **B2B，开发者不是买家。** 为经济买家添加一个第二短路径——安全审查、法律和许可、采购、预算批准——在承诺或标准化时加入。它有自己的退出事件（安全问卷通过、合同签署）和自己的所有者，通常完全在DevRel团队之外。开发者的路径并行继续：一个无法武装批准者的倡导者会在开发者路径无法显示的阶段停滞。

- **在阅读此路径之前，将使用量汇总到账户。** 开发者路径计算人数；买家路径计算组织。首先按电子邮件域、工作区或许可证分组注册——一家公司来自四十个注册用户看起来像四十个线索，直到你这样做。

- **按购买意愿递增的顺序读取三个信号系列：**
  - **深度** - 生产使用、持续量、集成到CI中。
  - **广度** - 同一账户中的第二位和第三位开发者。
  - **边界联系人** - 有人打开了SSO或RBAC页面，询问了合规性问题，达到了座位限制，请求了安全问卷。

  边界联系是罕见的、最强的，并且是路径可以拥有的最干净的退出事件——首先对其进行测量。

- **个人采用或B2C风格的自我服务。** 两条路径合并；开发者决定并支付，或者根本不支付。在地图上明确说明这一点，而不是留下一个空的买家路径，以便后来的读者知道这是决定，而不是遗忘。

- **无购买的开放源代码。** 没有买家路径，但通常在公司内部有采用批准步骤（许可证兼容性、依赖政策）。将其建模为采用阶段的摩擦，而不是一个路径。

地图中的其他部分对两者都相同——阶段模型、证据收集、退出事件和泄漏诊断不会随着商业模式而改变。

## 步骤5 - 命名三个关键时刻

将这些从行中提取出来并单独声明；它们是地图被阅读的原因。

- **首次成功** - 开发者从产品中获得实际结果的时刻。具体命名它并注明今天需要多长时间。
- **关键时刻** - 他们承诺或离开的点：将产品放入实际项目、推荐它、打开PR的决定。
- **放弃点** - 证据表明大多数人实际上停止的地方，这通常比团队假设的要早且乏味。

## 步骤6 - 诊断泄漏

- 仅在两个退出事件都被计算的情况下计算阶段到阶段的转换。将其余部分标记为 `inferred`。
- 选择 **一个** 阶段进行处理：最早的那个阶段，它转换率差，并且有一个能够改变它的所有者。最早获胜，因为下游的每个修复都被其上方的损失稀释；拥有获胜，因为一个未拥有的建议只是一个愿望。根据每个修复工作单元恢复的开发者数量对候选者进行排序——一个文档修复和一个重新架构的入职成本不同周——然后才应用最早和拥有的作为平分规则。

- 说明这个顺序会饿死。一个后期阶段有一个巨大的回报和沉重的修复——标准化、倡导、贡献——永远不会在早期廉价的一个面前获胜，因此一个每季度重新运行此地图的团队可以在多年内从未接触它。当最早泄漏的阶段未被拥有时、当其修复已经在进行中时、或者当访谈的最终状态是后期阶段时，才推广它。

- 在一个时期内大约有30个事件以下时，发布带有日期的原始列表，而不是比率——一个统计惯例，而不是DevRel发现，并且后来的旅程阶段经常达到这个底线。
- 仅与该地图自己的先前版本进行比较。另一家公司的发布漏斗有一个不同的受众、产品成熟度和每个阶段的定义。
- 如果大多数行将DevRel命名为所有者，则将其报告为一个关于组织的发现。这意味着表面没有可问责的所有者，这是一个比泄漏更大的问题。

只有在选择了阶段之后，才说明它为什么泄漏，使用BJ Fogg的行为模型（**B = MAP**：当动机、能力和提示汇聚时，行为就会发生）。B=MAP解释一个阶段；它不能比较阶段。

在选择之前就抓住它，你将写一个流畅的动机故事关于一个从未是约束条件的阶段。一个泄漏的阶段是一个没有发生的行为，而该模型将原因分为三种，每种都落在不同的所有者上：

- **能力太低** - 步骤太长，需要未声明的先决条件，或者要求一个不熟悉的例行程序。由文档、开发者体验或产品修复。这是针对开发者受众的默认答案，Fogg自己的方向性建议也适用：提高能力而不是推动动机，因为，用他自己的话来说，“动机是不可靠的。幸运的是，能力不是。”
- **动机太低** - 在这个阶段没有显示出值得努力的理由。由定位和产品营销修复。在开发者阶段上首先修复动机通常意味着团队更喜欢写文案而不是删除步骤。
- **提示缺失** - 他们可以并且愿意继续，但什么也没有告诉他们。由应用内指导、生命周期内容或社区修复。

## 步骤7 - 编写地图并分部分验证

```markdown
# 开发者旅程地图 - <分段>, <日期>

## 范围分段、最终状态、使用的阶段模型及其原因

## 旅程阶段表（每行一个阶段，八个字段）

## 买家路径的买家的阶段，或明确的“没有 - 自我服务”

## 关键时刻首次成功、关键时刻、放弃点

## 泄漏选择的阶段、其证据、为什么它胜过其他阶段

## 交接谁拥有修复、要观察的信号、重新阅读日期

## 间隙标记为推断的阶段，以及什么会使它们可测量
```

分部分呈现并同意再编写下一部分。在第一个标题处发现错误的阶段模型会损失一个段落；在泄漏诊断处发现会损失整个文档。

一个带有相同行弱版和强版的示例地图在 [references/journey-map-example.md](./references/journey-map-example.md) 中。

## 质量门

将地图与此标准对齐并迭代，直到它通过，然后明确报告检查。这些是这个技能自己的基线，而不是行业标准。如果用户问一个数字来自哪里，并让他们移动一个，当他们的情况支持时。

- 每个阶段只有一个退出事件，以可观察的事件而不是心态来表达。
- 每个阶段命名一个所有者，并且至少有一个所有者坐在DevRel团队之外。
- 至少60%的阶段携带一个具有实际当前值的信号；其余部分注明 `not instrumented` 并出现在间隙部分。
- 每个摩擦声明都引用其来源；没有行混合证据与假设。
- 恰好一个泄漏被指定，有一个命名的所有者和重新阅读日期。
- 推断阶段被标记为推断，无论它们出现在哪里。
- 地图在一页可读大小的页面上——如果它不能，阶段列表太长或单元格包含散文。

一个地图未能通过信号线并不被阻塞。发布它并命名间隙；一个诚实的地图有漏洞比一个完整的地图有虚构的数字更好，并且间隙成为测量请求。

## 常见失败模式

- **绘制公司希望看到的漏斗。** 阶段名称来自销售管道描述内部流程，而不是开发者行为。测试每个阶段名称是否会被开发者识别为他们所做的事情。
- **为所有开发者使用一个地图。** 爱好者、平台工程师和企业架构师几乎没有任何摩擦。选择一个分段或什么也不做。
- **退出事件不是事件。** “理解价值主张”不能被观察、计算或拥有。“运行快速入门到完成”可以。
- **从分析中填充整个地图。** 分析从注册开始，这已经是旅程中段。它之前的一切都需要定性证据或诚实的 `inferred`。
- **假设沉默意味着满意。** 失败的开发者很少提交任何内容；他们离开。关于一个阶段的投诉不存在不是证据该阶段有效。
- **指定三个泄漏。** 三个优先级等于没有。对它们进行排序并修复最早的拥有一个。
- **在B2B中跳过买家路径。** 地图然后显示一个健康的开发者旅程和一个停滞的管道，解释了两者。
- **将地图视为永久。** 当发布、定价变化、文档重写或新的SDK移动表面时重新阅读它。一个比两个季度旧的地图描述了一个不再存在的产品。
- **借用另一家公司的转换率。** 流传中的数字是单公司轶事，具有不兼容的阶段定义。引用一个会给地图虚假的信心并隐藏唯一有意义的比较——与其自己的上一个版本比较。
- **在早期阶段写入绝对流量数字。** 步骤2中的阻塞率使任何会话计数都是一个因页面而异的分数。在一个来源内保持比率，并将阶段标记为推断。
