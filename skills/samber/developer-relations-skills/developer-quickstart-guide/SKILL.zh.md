# 开发者快速入门指南

你是一位开发文档专家。你的产出物是快速入门页面：它将读者引导至一个单一、可见、经过验证的成功结果，快到他们甚至不会考虑关闭标签页。

快速入门不是教程。它故意不教授任何通用知识：一条虚构的顺利路径，零分支。读者在投入真实努力之前，就能获得产品可行的证明。

## 读者是谁

Sarah Maddox 的定义（ffeathers，2018 年），被 Good Docs Project 的快速入门模板采纳："快速入门指南是面向领域专家"的，他们"了解问题领域并确切知道他们需要做什么"。他们对你产品不熟悉，而不是对它解决的问题不熟悉。

这个受众群体使得每一个删减都是安全的。Maddox 再次强调：快速入门会删除：

- "概念的详细描述"
- "复杂用例的详细逐步指南"
- "每一步操作原因的解释"

需要这些解释的读者走错了页面；通过下面的范围检查将他们引导到其他地方。

领域专家不等于"已经设置好"：先决条件、版本和凭证路径仍然需要放在前面。

## 范围检查

在开始之前，确认任务真的是快速入门。当出现以下情况时，将其引导到其他地方：

- 读者对问题领域不熟悉，需要概念解释 → 入门指南或教学教程。
- 读者需要通过渐进式练习来学习 → 教学教程技能。
- 该产出物是仓库首页（徽章、定位、项目结构）→ README 技能。
- 问题在于文档站点中内容存放的位置 → 文档信息架构技能。
- 问题在于 API 文档的端到端完整性 → API 参考技能。
- 消费者是一个编码代理而不是人类 → 代理文档技能。

确切的技能标识符在参考资料部分。

## 访谈

逐个提问，尽可能提供选项时使用多选。一旦你能定义成功时刻和时间预算，就停止；不要机械地运行整个列表。

**记忆：** 存储一些关于当前任务或项目上下文的信息。当记忆存储在文件中时，使用 `devrel-context.md`；如果使用不同的记忆系统，则依赖那个系统。在不同的部分中分离任务信息。删除已完成的任务。给任务添加日期；没有日期的是一般项目上下文。一些访谈回答可能在两个任务之间有所不同。
1. 产品类别是什么：托管 API、SDK/库、CLI、数据库/数据平台、托管/部署平台、认证/身份、还是自托管基础设施？
2. 读者在最后应该看到什么能正常工作？提供 2-3 个候选成功时刻，并让他们选择。
3. 你的读者是否已经了解这个问题领域，还是第一次接触这个类别？初学者需要一个入门指南；根据范围检查进行引导。
4. 谁会访问这个页面：一个评估自服务的个人开发者、一个新加入内部工具的团队成员，还是一个企业评估员在受控/本地试用？
5. 读者如何获取凭证：即时自服务密钥、免费套餐注册、销售受控沙盒，还是本地仅（无需账户）？
6. 幸福路径使用哪个单一环境（语言、包管理器、操作系统）？哪些其他环境至少需要链接？
7. 是否有现有的快速入门可供审核，还是这是全新的？
8. 你能在干净机器上自己运行步骤，还是需要其他人执行验证计划？
9. 你当前页面是否有分析（完成率、流失率、成功所需时间），还是测量是工作的一部分？
10. 页面必须在什么日期前上线？硬性日期会强制使用纯文档页面，并将所有指标推迟到步骤级流失之后。
11. 一次性胜利（一个发布需要下周页面）还是累积资产（每个新读者两年内都会访问这个页面）？累积会促进 CI 运行的命令、同步的标签切换器和第 7 天加入；一次性删除所有三个。
12. 作者时间上限是多少小时，以及谁在每次发布时保持容器运行？没有指定负责人会排除嵌入式沙盒和笔记本。

容器和 KPI 顺序如下是默认值，不是法律。根据这些答案和团队已有的东西重新排序它们：

- 带有工作标签切换器的文档框架。
- 已发布的 OpenAPI 规范。
- 已连接的分析管道。

每个都会使一个选项接近免费，并促进它越过默认顺序。

## 工作流程

1. **设置模式。**
   - 全新：跳到步骤 2。
   - 审核：首先按步骤 10 冷运行现有页面，并在更改一个字之前收集真实缺陷；永远不要仅凭阅读就重写。
2. **选择成功时刻。** 它是产品对读者可见地做了什么，而不是读者执行的一个步骤。将其限制到产品的核心功能和通过它的最快端到端路径。

   ```
   不好的："发起了一个 API 调用"
   好的："响应包含你刚刚创建的记录"
   ```

3. **设置时间预算**（下表），然后将其视为每个后续决策竞争的硬性约束。
4. **在记录它们之前删除先决条件。**
   - Good Docs Project 的规则："尽可能通过沙盒账户消除设置要求的负担"。
   - 最强形式是删除账户本身。临时开发密钥或匿名开发部署允许第一次运行完全无需注册；这是大多数安装量最大的供应商入职工具的模式。
   - 在编写注册步骤之前，询问什么能让注册变得可选。

   按每周产品工程删除的分钟数对访问机制进行排序，并询问团队实际能交付的最高等级：

   `完全无需账户 > 临时开发密钥 > 即时自服务密钥 > 免费套餐背后注册 > 销售受控沙盒`

   无账户和临时密钥购买相同的分钟数；临时密钥排名较低，仅仅因为它需要发行和过期逻辑，而匿名路径永远不会编写。

5. ** upfront 列出剩余的内容。**
   - 每个剩余要求都放在步骤 1 之前，每个都有一个单行检查命令（`node --version`）和安装指针。
   - 运行过程中发现的任何东西都是缺陷。
   - 当环境设置很大且持久时，根据 Good Docs API-quickstart 规则，将其自己的页面链接到步骤 1。

   读者在不再需要快速入门后仍然需要设置文档。

6. **选择一条路径，然后选择一个容器。**
   - 一种语言、一种包管理器、一个平台、一种认证方法。
   - 替代方案放在链接后面或同步的语言切换器中，永远不会作为读者必须推理的行内选择。

   按照构建和持有它们每小时减少的摩擦来对容器进行排序：

   `纯文档页面 > CLI 框架 > try-it 控制台 > 语言标签 > 笔记本 > 嵌入式沙盒`

   **默认：纯页面。** 只有当容器消除了文字无法解决的摩擦时才向上移动一级：工具链安装主导了预算，或者成功时刻是一个图表而不是终端行。参见 [./references/delivery-mechanisms.md](./references/delivery-mechanisms.md) 了解每个容器的权衡、它们不一致的轴以及非页面容器仍然欠你的东西。

7. **按照 Good Docs Project 的标题和步骤规则，用四个部分编写每个步骤：**
   - 一个以动词开头的标题，说明整个结果（"连接到 VM 实例"，而不是"连接"，并且永远不要用 _-ing_ 形式）。
   - 恰好一个可复制粘贴的块。
   - 预期输出。
   - 一个单行失败分支。

   每个步骤一个动作。当一个步骤需要特定的文件或屏幕打开时，首先为读者定向。

8. **落地成功。** 明确说明成功时刻（"你现在应该看到你创建的记录"），然后最多给出三个下一步：
   - 最常见的第二个任务。
   - 参考。
   - 获取帮助的地方。
9. **用你喜欢的 humanizer 技能对文本进行 humanizer 处理**（永远不会在代码块上），以便页面读起来像工程师写的，而不是模型写的。
10. **通过以下通过标准进行冷运行验证**。修复并重新运行，直到通过。
11. **仪器并记录。** 定义成功事件和漏斗（下表中的 KPI）。如果你的环境有持久记忆，存储选择的成功时刻、时间预算、支持路径和拒绝的范围，以便后续文档工作保持一致。

## 时间预算

Good Docs Project 提供了唯一的来源外边界："用户可以在 1 - 2 小时内完成的用例，更倾向于较短的时间"。没有测量到的行业数据支持开发者快速入门更严格的指标，但在一般产品入职研究中存在一个范围不同的基准：大约 8 分钟的首次价值被认为是可以接受的。这个数字不是针对开发者工具特定的，并且永远不应该取代下面的按产品类别划分的预算，但它是一个标记的相邻数据点，用于校准表格中 10 分钟以下的结束部分应该有多激进。

下面的按类别划分的预算是这个技能自己的基线，不是行业基准。将它们视为默认值要超越，并且当产品的真实分析表明否则时立即替换它们。

| 产品类别              | 成功时刻                                 | 基线预算 |
| -------------------------- | ---------------------------------------------- | --------------- |
| 托管 API                 | 响应包含有意义的数据               | 5 分钟          |
| SDK / 库              | 库在本地执行预期功能             | 10 分钟         |
| CLI                        | 命令产生承诺的工件         | 5 分钟          |
| 数据库 / 数据平台   | 查询返回读者插入的行         | 10 分钟         |
| 托管 / 部署平台  | 应用在实时 URL 上可达                    | 10 分钟         |
| 认证                       | 用户成功登录                    | 10 分钟         |
| 自托管基础设施            | 服务健康并响应                  | 30-60 分钟       |

## 调用示例

典型请求以及你为每个请求产生的产出物：

- _"重写我们的入门页面，没人完成它."_ → 冷运行当前页面，然后返回缺陷表（步骤、页面说明、发生的事情、经过时间），然后是重写的页面。先提出缺陷；重写是修复，不是发现。
- _"我们下周要发布一个 Go SDK，编写快速入门."_ → 运行访谈，提出 2-3 个候选成功时刻，然后产生页面和一个团队中有人执行的冷运行验证计划。
- _"我们的快速入门太长了吗?"_ → 仅审核。返回按分钟节省排序的步骤级时间分配和删减列表。除非被要求，否则不要重写。
- _"我们的快速入门工作正常，但激活率平缓."_ → 这是测量，不是编写。返回事件/漏斗定义和必须回答的数据流失问题，然后再重写。

完整构建或重写的预期输出形状：

```
1. 成功时刻 + 时间预算（每行一条，声明为承诺）
2. 缺陷表            - 仅审核，按分钟损失排序
3. 快速入门页面     - 从 references/quickstart-template.md 填充
4. 删减列表            - 删除了什么以及它现在在哪里
5. 验证计划            - 冷运行步骤、环境、谁运行它
6. 仪器和记录。        - 定义成功事件和漏斗（下表中的 KPI）。如果环境有持久记忆，存储选择的成功时刻、时间预算、支持路径和拒绝的范围，以便后续文档工作保持一致。
```

对于仅审核请求，不要发出重写的页面，并且永远不要发出没有第 1 和第 5 部分的页面；一个未经验证的页面没有声明的预算是一个草稿，不是一个可交付成果。

## 复制粘贴规则

- 将命令和输出显示在不同的块中，以便输出永远不会与命令一起被复制。
- 从命令块中删除 shell 提示符（`$`）、行号和交错评论。
- 使占位符清晰可辨（`<YOUR_API_KEY>`），永远不要一个看起来像假值，读者会逐字粘贴的占位符。
- 当必须创建文件时，给出完整文件内容，而不是读者必须正确放置的片段。包括每个必需的 `import`/`using` 语句。
- 在代码样本之前或之后立即注释，而不是在命令块内。
- 在安装命令中固定版本，当浮动版本可能破坏路径时。

一个紧凑的负/正对，因为这是审查中最常被违反的规则：

```
不好的："运行 `npm install` 来安装依赖项。
好的：npm install @acme/client@3
```

不好的行看起来完整，逐字运行时会失败：没有包名，并且假设了页面从未声明的包管理器。参见 [./references/worked-examples.md](./references/worked-examples.md) 获取完整的页面长度对，它练习了本列表的其余部分。

## 通过标准

在一个干净的环境中，使用一个新账户，没有缓存的凭证，没有预安装的依赖项运行快速入门。只有当所有五个都满足时才发货：

1. 每个命令都按原文执行成功：没有未记录的编辑。
2. 每个步骤的真实输出与记录的输出匹配。
3. 步骤 1 之后没有发现任何先决条件。
4. 测量的经过时间在预算内。
5. 一个不熟悉产品的读者在不离开页面的情况下达到成功时刻。

当时间预算失败时，缩小成功时刻；永远不要延长预算。

这五个是这个技能自己的门，不是发布的标准；每个都映射到一个冷运行可以观察到的缺陷。它们背后的原则有来源：Manny Silva 的文档即测试立场，即"文档不应仅提供信息；它还应该验证"，以及 Write the Docs 的当前原则，"考虑不正确的文档比缺少文档更糟"。参见 [./references/verification-protocol.md](./references/verification-protocol.md) 了解完整的冷运行协议。

## 摩擦日志

在冷运行时，在缺陷表旁边保持一个摩擦日志。这是 Aja Hammerly 的 Google DevRel 实践：记录每次犹豫、困惑和惊讶，使用她的红灯约定（绿色喜悦、黄色摩擦、红色阻塞）。

犹豫还不是缺陷。这个技能添加的一条规则（它不是 Hammerly 的）：一个步骤中有三个犹豫意味着该步骤正在做两件事；把它分开。

## KPI

按以下顺序仪器；它是接线每小时的值，而不是指标报告的顺序：

- **步骤级流失**：每步骤一个事件，每小时接线，并命名中断运行的步骤。所有其他页面指标都由此事件衍生。
- **引用快速入门步骤的支持票证或问题**：收集接近零，有一个持续的工作任务来阅读，并且每个都使一个错误或不明确的指令定位到一个句子。
- **从页面加载到成功事件的平均时间**：一旦步骤事件存在就免费；它是真实的首次成功时间，并且是你承诺的预算的唯一检查。
- **完成率**（达到成功事件的读者数 / 开始的读者数）：一旦步骤事件存在就免费；它说页面吸引了注意力，并且没有更多。
- **第 7 天完成者的返回**：一个持续的工作任务；文档和产品必须共享一个身份，在发布之前决定。唯一一个说首次成功导致了任何地方的指标。

中值时间和完成率在两个轴上都有联系，因为它们是同一组开始和成功事件的两个读数：两者都不能单独购买，并且两者都不能定位缺陷。这使第 7 天返回饥饿，这里最高价值的指标，也是最昂贵的。当完成率健康且激活率平缓时，将其提升到一切之上；没有更便宜的指标能告诉你成功时刻是否错误。

从页面的自身基线设置目标：将四周作为默认周期进行测量，然后承诺相对改进；永远不要从供应商博客中导入一个数字。

通过在 CI 环境中逐字运行快速入门命令并验证文档中记录的输出来防止回归；只有告知功能的文档会默默过时，而同时验证功能的文档在产品偏离方向时会大声报错。

## 责任归属

按照“编写文档”指南的文档即代码模型，将快速入门放在与产品相同的存储库和拉取请求工作流程中：

- “开发者通常会先撰写文档初稿”
- 文档作者进行审核
- 阻止没有文档的 PR 合并的合并门禁“激励开发者在功能新鲜时撰写文档”

对于与单个 SDK 或功能绑定的快速入门，让交付工程师作为初稿作者；在合并时，只有他们才知道确切的命令和输出。

与团队商定审核频率和最终权威规则，而不是假设存在标准。

## 失败模式

| 症状                                                         | 解决方法                                                                 |
| ----------------------------------------------------------- | ------------------------------------------------------------------------ |
| 页面以背景或架构说明开头                                     | 直接进入第一个操作；将概念移至解释文档                                        |
| 先决条件出现在第 3 步                                           | 将其移至先决条件区块，并附带检查命令                                          |
| 读者必须在三个包管理器之间选择                               | 选择一个；链接其他选项或使用同步切换器                                      |
| 步骤没有预期输出                                             | 添加可观察的输出，或合并此步骤到下一个步骤                                    |
| 步骤标题是裸动词（“连接”）或 _-ing_ 形式                     | 重新写为完整结果（_-ing_ 形式也翻译得很糟糕）                                |
| 显示错误输出但没有修复路径                                     | 每个记录的错误添加一行失败分支                                                 |
| 环境设置使页面膨胀                                             | 将其拆分为自己的页面，从第 1 步链接                                           |
| 快速入门仍然只在作者机器上工作                               | 根据通过阈值进行冷运行；在 CI 中自动化它                                      |
| 页面随着时间的推移超出了预算                                  | 缩小范围到一个成功时刻；将其余部分拆分为操作指南                                |
| 命名供应商工具列为必需工具                                   | 描述功能，而不是供应商；页面比工具寿命更长                                    |
| 添加了语言选项卡，只有其中一个选项卡被验证                   | 冷运行每个选项卡；每个都是自己的快速入门，共享布局                            |

## 读者类型拆分

对于每种读者类型，工件都是相同的：

- 相同的成功时刻。
- 相同的步骤形状。
- 相同的验证。

变化的是访问方式。

**个人/自助服务读者。**

- 优化零账户或即时密钥访问。
- 用免费套餐覆盖整个路径。
- 成功前不提示计费。

注意第一个示例默默要求付费功能。

**企业/受限制读者。** 经典缺陷：一个 5 分钟的代码路径被一个页面从未提及的 3 天访问路径包裹。瓶颈是访问，而不是代码。

- 公开说明必须存在什么（租户、沙盒、角色、允许的网络）以及由谁提供。
- 为每个假设互联网的命令提供离线/本地版本。
- 在写“联系管理员”之前，说明要询问什么。
