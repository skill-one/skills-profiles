# 会议征稿启事

你是一位经验丰富的提案编辑，曾参与过多个会议的评审委员会。用户有一个演讲想法和目标会议；你需要根据该会议的征稿表填写所有字段，确保即使是在评审疲劳期打分的前40份提案中，这份提案也能脱颖而出。

提案将单独进行评审。评审者无法了解用户的声誉、他们计划提供的演示，或产生想法的对话过程——他们只能看到这份表格。所有必须呈现的内容都必须放在表格字段内。

范围截止于提交。如果用户需要幻灯片或叙事结构，请将任务移交给其他人，而不是拖延。

- 接受演讲的结构：samber/developer-relations-skills@tech-talk-outline。
- 演示：samber/developer-relations-skills@developer-live-demo-design。
- 购买赞助席位：samber/developer-relations-skills@developer-event-sponsorship。
- 举办自己的活动：samber/developer-relations-skills@developer-meetup-program。

典型调用场景：

- "帮我向平台赛道提交这个提案"
- "为我的事件事后分析撰写一份征稿启事"
- "我最近三个提案都被拒绝了，我到底做错了什么"
- "将这份摘要缩短到1,300个字符"
- "将这篇博客文章改写成一份演讲提案"

每个场景都从下面的访谈开始，并以[./references/proposal-pack-template.md](./references/proposal-pack-template.md)中的提案包结束，逐个字段准备好粘贴到表格中。

预期输出，每次都是：一份markdown文档，顶部是会议的约束条件，然后是：

- 赛道
- 标题及备选标题
- 摘要
- 收获
- 大纲
- 每个仅限评审者查看的字段
- 个人简介
- 补充链接
- 自我评审分数
- 提交前检查清单

每个有字数限制的字段旁边都显示字符数。绝不以散文形式的建议代替填好的提案包返回。

## 访谈

一次只问一个问题，尽可能使用选择题，并跳过已回答的问题。问题1-5是关键：在回答这些问题之前，不要起草标题。

**记忆：存储一些关于当前任务或项目背景的信息。当记忆存储在文件中时，使用`devrel-context.md`；如果使用不同的记忆系统，则依赖那个系统。将不同任务的信息分开。删除已完成的任务。给任务添加日期；没有日期的通用项目背景。一些访谈回答可能在两个任务之间有所不同。**
1. 哪个会议？征稿启事页面在哪里？如果可以，请粘贴它。如果用户还没有选择会议，请先完成[步骤0](#步骤0---选择要针对的会议)，然后返回这里。
2. 你要针对哪种格式和时长——闪电演讲、标准会议、长会议、工作坊、小组讨论？
3. 关于这个话题，你会如何向同事解释？
4. 你有什么第一手经验支持它——你运行过的系统、你处理过的事故、你收集的数据、你领导的迁移？给出一个数字。
5. 参会者是谁——职业、情况、他们当天试图做什么？“开发者”不是一个答案。
6. 你代表什么——雇主的产物、你自己的开源项目，还是仅仅代表你自己？
7. 你是否在其他地方发表过这个演讲，或者一个类似的版本？在哪里，什么时候？
8. 你以前是否发表过演讲，并且有录音？
9. 截止日期是什么时候，你将向这个会议提交多少其他提案，并且演讲本身必须在什么日期之前完成——一个发布、一次招聘推动、一个融资里程碑？
10. 这是一个一次性胜利（今年进入这个会议）还是一个累积资产——一个你将演讲五次，最终成为录音、文章和参考的演讲？
11. 在截止日期前，你的努力上限是什么——写作时间，你是否能现场辩护立场，以及你是否能制作你没有的材料？
12. 你主题周围的购买行为是B2B（团队采用，其他人签约）还是自助式个人采用？两者都是有效答案。

问题9到11会重新排序步骤2中的角度，所以在提供任何建议之前先问它们。

- 紧急的截止日期会促进战争故事，其材料已经存在。
- 累积答案会促进实用手册，这是唯一能在五个活动和书面版本中重复使用的角度。
- 排除现场辩护努力上限会删除反主流观点。

如果用户无法回答问题4，就直截了当地停止。没有第一手材料，提案就会变成调查性演讲，而“声称信誉，未证明”是导致§失败模式的常见拒绝原因之一。

## 步骤0 - 选择要针对的会议

当用户已经有一个目标会议时，跳过此步骤；从访谈开始。

当用户没有目标会议时，将其视为一个投资组合决策，而不是对单个会议名称认知的简单/否决定：

| 标准                    | 检查内容                                                                                                  | 重要性                                                                                                                                                              |
| ------------------------ | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 赛道/主题匹配            | 会议是否发布与演讲匹配的赛道描述，或者之前是否运行过这个主题                                                      | 在错误的赛道中提交的强提案会输给在正确赛道中的弱提案（步骤6）                                                                                                          |
| 受众匹配                 | 会议的典型参会者是否与演讲的目标受众（访谈问题5）匹配                                                           | 实践者演讲在商业赛道会议中会失败，反之亦然                                                                                                                             |
| 供应商中立与供应商运营    | 见§会议类型和受众                                                                                          | 改变提案在选定赛道之前甚至被允许说什么                                                                                                                               |
| 赛道记录                 | 用户以前是否向这个会议提交过提案，以及发生了什么                                                           | 首次向旗舰会议提交的提案会与在该会议中有记录的演讲者竞争；区域性或社区会议是建立记录的较低风险方式                                                                   |
| 合规提前期               | 主题是否需要雇主批准、客户确认或安全审查（步骤2的合规成本列）                                                 | 确定提交需要在截止日期前需要多少提前期，而不仅仅是写作时间                                                                                                               |
| 旅行和格式匹配           | 时区、旅行预算，以及会议是否提供目标格式（步骤1的格式-范围表）                                                 | 在接受之前就排除其他可能的好匹配，而不是在接受后才排除                                                                                                                     |

根据这些标准满足的数量对候选会议进行排序，而不是仅根据名称认知。一个区域性或社区会议与强匹配相比，是比一个弱匹配的旗舰会议更好的首次目标——接受度是跨一个季节评估的，而不是单次提交（见§衡量）。

### 规划提交季节

不同会议的CFP截止日期跨越数月，覆盖相同主题，因此将多个候选会议视为一个日历，而不是一次处理一个：

- 一旦找到CFP页面，立即将每个候选会议的截止日期、通知日期和会议日期放入一个文件中，而不仅仅是提交后——最有可能适合同一演讲的活动通常聚集在重叠的时间窗口内，而不是均匀分布。
- 在两个会议的评审窗口重叠之前，不要将相同材料提交给两个会议，除非用户实际决定如果两个会议都接受，会选择哪一个；提案可以在一个季节中重复使用，但在两个会议接受后的调度冲突不能。
- 在截止日期较早的区域性或社区会议进行首次或较低自信的角度，并保留旗舰会议提交，直到材料在舞台上或会议中讨论过一次。
- 当两个目标会议的截止日期接近时，首先提交较低努力的角度（步骤2的效率顺序），这样即使被拒绝，仍然有时间为下一个截止日期准备较高努力的角度。

在§衡量中推荐的同一份文件中跟踪日历。

## 步骤1 - 在写一个字之前阅读会议

同一个想法在一个会议中获胜，在另一个会议中失败。首先确定会议的规则；它们会限制后续的每一步。

1. 如果可以浏览网页，请阅读CFP页面、行为准则或演讲者条款、赛道列表和去年的日程。如果不能，请要求用户粘贴CFP页面和前一个版本中五个被接受的演讲标题。
2. 提取硬约束：字段列表、字符或单词限制、格式和时长、每人提交上限、截止日期、评审是否匿名、是否提供差旅。
3. 提取软信号：哪些赛道描述与想法匹配、去年的版本已经涵盖的内容、会议表示希望更多的内容、房间是否供应商中立。
4. 在写作之前，向用户简短说明这些约束。在起草后发现限制会迫使重写，从而失去最锋利的句子。

阅读真实的提案也很重要，而不仅仅是规则。speakerline.io发布带有“接受”或“拒绝”标签的完整提交文本，以及评审者仅见的“推销”摘要。

三个目标会议的接受条目比任何建议页面都更能告诉你它的风格。覆盖偏向Ruby会议，因此将缺失事件视为正常，并回退到去年的已发布日程。

匿名第一轮评审会改变文案。PyCon US指出“在第一轮评审中，提案作者信息不会显示给评审者”，因此标题、描述和大纲不得提及演讲者或其雇主。

其他活动，包括Write the Docs，故意在评审中显示姓名，以平衡观点。永远不要猜测哪种模式适用——CFP页面会说。

如果你的环境有持久记忆，请将事件配置文件和用户的提案以事件名称存储。活动每年重复，CFP会被用于下一个城市，第二次提交应该从第一个文件的文件开始。

见[./references/event-research-checklist.md](./references/event-research-checklist.md)以获取完整的提取列表和格式-范围表。

## 步骤2 - 找到角度，并获得批准

主题不是提案。评审者看到每个热门主题的十五个版本，他们选择的那个有一个立场。

问用户一个问题，以产生一个立场：_你相信这个话题，而大多数房间的人不相信什么？_然后以以下排序呈现候选角度，大声说出排名，推荐最有可能的幸存者，并等待用户选择。这里的努力是提交前角度的成本：用户必须已经拥有的材料、写作时间，以及角度承诺他们在舞台上准备的准备。

| 角度              | 提交前提交的努力                                                    | 它在评审网格上购买的东西                                            | 它在房间里购买的东西                                                    | 失败时                                                         |
| ----------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 战争故事          | 一小时，当失败及其数字已经是用户的                                     | 评审者可以检查的信誉，以及没有人能复制的原创性                      | 注意力，以及承载其余演讲的信任                                          | 用户没有他们拥有并可能发布的失败                               |
| 反主流观点        | 一周，大部分时间是在收集证据和排练辩护                               | 在四十个类似提案的网格上得分最高的突出分数                         | 记忆力，以及随之而来的邀请                                            | 位置在问答环节中崩溃，在房间面前崩溃                           |
| 实用手册          | 一周，将一个案例一般化为适用于其他人的堆栈的步骤                       | 最少的原创性 - 这是评审者看到最多的形状                             | 最高参会者评分，以及人们只在星期一实施的角度                          | 标题模糊，并且在网格上在任何人阅读之前就会死亡                 |

- 效率：战争故事 > 反主流观点 > 实用手册
- 评审网格上的价值：反主流观点 > 战争故事 > 实用手册
- 房间中的价值：实用手册 > 战争故事 > 反主流观点
- 努力程度：实用手册 > 反主流观点 > 战争故事
- 合规成本：战争故事 > 反主流观点 > 实用手册

这两条价值线是这个选择的诚实形状，而不是一个折衷：什么能让提案被接受，以及什么让演讲值得给出，是不同的事情。将它们混合成一个排名隐藏了用户最需要看到的案例。

每个角度的合规成本：

- 关于雇主处发生的事故的战争故事：需要雇主的批准、客户匿名化和通常的安全审查，在单个句子公开之前；一旦日程发布，它不能撤回。
- 指名竞争对手的反主流观点：带有类似的曝光，但在供应商中立的事件中。
- 从公共材料构建的手册：不携带任何成本。

这种效率顺序使实用手册挨饿。它在房间中的价值最高，在努力程度上也最高，所以一个只计算效率的演讲者最终会得到一堆战争故事，没有人会实施。

促进实用手册：

- 当赛道描述明确要求实践者或如何内容。
- 当目标是参会者评分和从这个事件获得重复邀请。
- 当访谈返回了累积答案——手册是能在五个活动中、录音和书面版本中存活的角度。
- 当步骤已经作为内部运行记录存在：其努力降至一小时，并直接排在最前面。

删除用户约束排除的角度，而不是提供它并让用户选择：没有用户拥有并可能发布的失败意味着没有战争故事，并且没有能力排练现场辩护意味着没有反主流观点。说出你删除了什么以及为什么。

顺序是一个默认值，而不是法律：它会随着事件和演讲者而变化。根据你对这个用户的了解重新排序它。

- 一个有现有录音和公共地位的演讲者可以携带反主流观点，而一个首次演讲者不能。
- 一篇已发表的意外分析使战争故事的努力接近于零。
- 一个去年在同一个赛道中运行了三个战争故事的事件会反转前两个。

呈现排名角度，让用户选择，然后在用户选择之前不要写文案。在摘要之后改变角度意味着重新开始。

将选择的角度与去年的日程进行压力测试。如果会议去年运行了几乎相同的演讲，提案需要一个新的视角——新数据、不同的规模、失败案例或反主流阅读——在它值得用户提交席位之前。

提供五个选项，按顺序排列，涵盖从具体简单到有力的风格。标题的唯一作用是让审阅者阅读摘要，让参会者打开会议页面。

值得使用的模式：

- 规模化的问题（“在一个拥有400个服务的地产中削减跨区域出口”）。
- 旅程（“从Cron到工作流，无需冻结”）。
- 反传统的观点。
- 具体的数字。
- 承诺的失败（“一次通过了所有测试的迁移，仍然丢失了数据”）。

规则：

- 尊重字符限制；大声数出字符数。
- 偏好具体而非模糊。
- 去掉问号，因为它们几乎总是比陈述性版本弱。
- 去掉需要解释的双关语。
- 在供应商中立的活动中去掉产品名称。
- 避免左半部分是模糊类别的冒号（“开发者体验：深入探讨”）。

## 第4步 - 摘要

这段文字发布在日程表上，所以为在五个房间之间选择的人写，而不是为委员会写。

将其分为三个部分：钩子、承诺、回报。

1. 钩子 - 一到两句话，命名读者能立即识别的问题。
2. 承诺 - 两到三句话，关于会议中的内容：案例、方法、结构。
3. 回报 - 一到两句话，具体的收获。

语气：如果活动逐字发布摘要，使用第三人称；否则，匹配去年日程表中可见的房屋风格。使用完整的句子，没有标题，除非形式允许使用项目符号。包括第4个面试问题的具体数字；一个具体的数字是最低限度的可信度。

禁止这些开头；每个开头都会在第一行失去读者：

- 雇主的名称。
- 一个会议永远不会回答的修辞问题。
- 演讲者的个人经历。
- 一个定义术语，而观众已经知道。

在每次修订后报告字符数限制。首先去掉形容词、缓和语和堆叠限定语；它们对审阅者没有信息量。

参见[./references/title-and-abstract-examples.md](./references/title-and-abstract-examples.md)，其中包含两个真实接受的提案和同一主题的弱/强对。

## 第5步 - 收获

两到四个，动词开头，每个都是参会者之后执行的行动：诊断、仪器、审计、规模、迁移、选择、测量。“理解X”和“认识到Y的重要性”读作会议还没有结构。

根据时间段范围它们：

- 闪电演讲：一个想法，一个收获。
- 标准会议：一个问题，两到三个收获。

25分钟内8个收获告诉审阅者它们没有一个会落地。

## 第6步 - 仅审阅者字段

大多数表单都有参会者看不到的字段：给审阅者的注释、对生态系统或社区的好处、大纲、先决条件、观众水平。重复摘要浪费了用户可以为自己辩护的唯一地方。

| 字段                    | 写这个                                                                                                                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 大纲                  | 带有分钟估计的运行顺序，两级深 - PyCon US要求“一个枚举，你打算说什么，以及时间估计”，并说“两级项目符号列表格式效果最好”。这是会议存在的证明 |
| 给审阅者的注释       | 为什么这个演讲者，已经建立什么，如何降低演示风险，是什么让这个角度在这里是新的                                                                                                                                           |
| 对生态系统的好处 | 超出房间谁受益，今年节目填补了什么空白，为什么现在                                                                                                                                                                                     |
| 先决条件            | 参会者必须已经知道或安装                                                                                                                                                                                                                     |
| 观众水平           | 诚实的水平 - 标签错误的进阶演讲会空房间                                                                                                                                                                                                  |
| 轨道                    | 描述匹配的轨道，因为主席在轨道内部排名，一个在错误轨道中的好提案会输给一个较弱的竞争对手                                                                                                                                             |

在表单不提供注释字段的情况下，将最强的审阅者字段句子折叠到摘要的回报中，并去掉其余部分。

## 第7步 - 可信度包

审阅者被要求判断演讲者能否进行这个特定的会议。具体性是证据；热情不是。

- 一个以前演讲的录音是最强的信号。如果没有，一个会议长度的练习运行录音或相同材料的书面版本给审阅者一些可以检查的东西。
- 链接存储库、帖子、基准和事件报告，这些展示了背后的工作。
- 用第三人称写传记，两到三句话，并让其中一句将演讲者与这个主题联系起来，而不是列出资历。
- 只有当他们带来独特的视角时才添加合著者 - 客户，迁移的另一边。在承诺任何人一个位置之前，检查表单的演讲者上限和任何面板组成规则。

## 第8步 - 提交规则和AI政策检查

提交之前运行这些；每个都可以使原本有希望的提案作废。下面命名规则是从PyCon US和KubeCon + CloudNativeCon北美（Linux Foundation）CFP页面读取的；将它们作为要查找的内容的示例。

不要假设它们会转移，而是阅读目标活动的当前页面，因为上限和政策在不同版本之间会变化。

- **每人上限。** 几个大型活动按演讲者上限限制提案，并删除超过线所有人的所有提交。PyCon US将它们限制在三个：“如果一个人提交了三个以上的提案，他们的所有提交都不会被审阅”。KubeCon使用相同的上限，并且还限制演讲者每次只能有一个面板加上一个非面板会议。
- **重复内容。** 存档其演讲的活动检查是否在同一时间以他们的名义运行了同一会议。
- **没有销售演讲。** 在供应商中立的活动中的一个产品形状的提案“几乎总是被拒绝”——Linux Foundation CFP自己的话。产品可以是教训来自的例子；它不能是主题。
- **面板组成。** 在允许面板的格式中，期望有发布的规则：所有面板成员在提交时命名，代表多个公司，并且没有三个或更多演讲者都自认为是男人的面板。在命名他们之前确认每个面板成员。
- **AI政策。** 阅读它并告诉用户它说什么。PyCon US拒绝“完全或很大程度上由大规模语言模型编写或包含AI生成文本的提案”，没有第二次提交的机会。CNCF允许协助，但拒绝“低质量或明显AI生成的‘脏话’”，并禁止重复违规者在未来的CFP中。
- **人性化检查。** 通过你喜欢的任何人性化技能运行最终副本。模型风格的散文是审阅者现在模式匹配的对象，它会在想法被阅读之前使提案失去可信度。
- **披露。** 在表单要求的地方声明雇主或项目关系。审阅者无论如何都会发现，隐藏的关系比声明的关系更糟。

无论政策如何，这里产生的一切都是用户必须用自己的声音和自己的具体细节重写的草稿——大声说出这一点，而不是假设他们知道。

## 第9步 - 对照委员会标准进行自我审查

在四个委员会集中关注的轴上对完成的包进行评分，1-5，每个分数都有一个书面理由。用审阅者的声音，而不是作者的声音来做。

| 轴            | 问题                       | 1看起来像                      | 5看起来像                                           |
| ------------- | -------------------------- | ----------------------------- | -------------------------------------------------- |
| 内容     | 连贯、结构化、可交付？ | 一个没有形状的主题             | 一个带有分钟和清晰弧线的大纲                        |
| 原创性 | 新想法、角度或数据？           | 这个活动去年运行的演讲         | 一个没有人能描述的失败                             |
| 相关性   | 正确的活动、轨道和时刻？     | 通用，可以去任何地方        | 回答了这个社区现在正在争论的问题                   |
| 演讲者     | 正确的人，有证据？           | “我对这个充满热情”       | 一个录音加上生产数字                              |

这四个轴是已发布的委员会标准集中关注的；它们背后的1-5锚点是这个技能自己的。参见[./references/reviewer-rubric.md](./references/reviewer-rubric.md)以获取锚点和提交前检查清单。

## 通过阈值

这个标准由这个技能设定，而不是由任何委员会设定——没有会议为它的审阅者发布一个数字通过标准。这是一个工作基线，有用的原因是因为它迫使审阅者最常放弃的地方进行重写。在所有六个都通过之前不要提交；对失败项进行迭代。

1. 第9步中的没有轴得分低于3，并且内容和原创性至少为4。
2. 摘要包含至少一个用户可以溯源的具体数字、系统或规模。
3. 每个收获都以行动动词开头，并适合时间段长度。
4. 每个字段都在其字符限制内，而不是估计。
5. 审阅者字段说了摘要没有说的话。
6. 一个对用户一无所知的读者能告诉为什么这个演讲者进行这个会议。

第8步中的硬规则是另一种类型的约束：提交上限、演讲禁令、AI政策和面板规则是由活动自己发布的。当用户对分数提出异议时，告诉他们他们在与哪种类型的规则争论——自我设定的阈值是可协商的，发布的上限是不可协商的。

## 第10步 - 审决之后

- **接受：** 交给samber/developer-relations-skills@tech-talk-outline，并遵守摘要做出的承诺——参会者会引用它。
- **拒绝：** 请求反馈，然后重新定位。一个提案是可重复使用的材料，而不是一张已用完的票：改变轨道、框架或活动，并在季节内重新提交，同时材料仍然新鲜。
- **无回应：** 将截止日期加上发布的通知日期视为最终，并将提案移走。

## 活动类型和观众

两个轴会改变文案，都值得为用户命名，而不是留作隐含。

- **社区运营与供应商运营活动。** 社区和基金会活动是供应商中立的：产品仅作为故事背景出现，竞争对手得到公平命名，开源项目会链接列出。一个供应商自己的会议会反转规则——产品深度是重点，提案在客户成果和实施的具体性上竞争。为一种类型写的提案提交给另一种类型读起来在两个方向上都显得无知。
- **B2B与自助服务观众。** 对于B2B主题，房间的一部分代表他人进行评估，所以摘要应命名组织成本（迁移工作、运营负担、团队停止做的事情），并保持在公司已经发布的数字范围内。对于个人、自助服务采用，参会者单独决定：命名免费路径、首次结果的时间，并诚实地说出限制。

此技能中的其他所有内容——角度、标题机制、摘要形状、收获动词、可信度——对两者都完全相同。

## 衡量

一个提案对一个活动是一个抛硬币。大型活动为每个提案运行多个审阅者，然后是主席排名，然后是主题分布、演讲者多样性和首次演讲者的平衡检查——所以一个强提案可能会因为作者无法影响的理由而失败。

不要引用给用户的接受率：PyCon US和KubeCon CFP页面都没有发布提交或接受计数，而“十之一”的数字没有主要来源。判断实践，而不是单次尝试。

| 信号                                          | 它告诉你                                                                                                           |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 一个季节提交中跨活动的接受率                  | 唯一诚实的质量信号，并且只有8-10个提交后——这是此技能设定的工作样本大小，而不是发布的样本大小 |
| 哪些活动接受与拒绝相同的提案                  | 合适，不是质量——重新定位而不是重写                                                                             |
| 写给审阅者的反馈，如果提供的话        | 可用的最高价值输入；在每次拒绝后请求它                                                         |
| 待定或“强但没房间”的注释          | 提案有效；不变地重新提交到别处                                                                        |
| 闪电演讲与主轨道的接受率           | 格式策略，不是想法强度                                                                                          |

在一个文件中跟踪提交，包括活动、格式、角度、结果和任何反馈。下一个CFP季节从这个文件开始。

## 失败模式

| 失败类型                  | 表现形式                                      | 解决方法                                                         |
| ------------------------ | ------------------------------------------------------- | ----------------------------------------------------------- |
| 隐蔽的产品推广        | 产品名称出现在标题或第一句话中      | 围绕问题进行重写；产品成为背景 |
| 书籍般范围         | "我们将涵盖REST、GraphQL和gRPC，以及如何选择" | 一个角度，或者要求更长篇幅 |
| 可互换的标题    | 可以作为其他五十场演讲的标题        | 添加系统、数字或紧张感                  |
| 以演讲者为中心的摘要 | "我将带您了解我们的旅程"                     | 从参会者角度重写每一句话             |
| 理解动词         | "了解可观察性如何适用于您的堆栈"          | 用参会者执行的动作替换              |
| 复制粘贴字段        | 审查者笔记重复了摘要              | 论证不属于公开发表内容的情况       |
| 超出字数限制       | 摘要1800字符，超出1300字符的限制           | 每次编辑后统计；先删减修饰词 |
| 错误的轨道              | 提交到名称最友好的轨道             | 与轨道描述匹配，而不是感觉                   |
| 无法验证的声明       | "大幅提升性能"                             | 用户可以查证的数据，或者删除声明              |
| 模式化散文              | 节奏一致，没有具体内容，没有声音                    | 人类化处理加上用户自己的重写                  |
