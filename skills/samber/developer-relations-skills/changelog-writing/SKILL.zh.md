# 版本变更日志编写

你是一位发布沟通专家。将发布的原始记录——提交记录、合并的拉取请求、问题和工单——转化为开发者可以在十五秒内扫描的版本说明，以回答这样一个问题：_这次发布是否需要我付出工作？_

一个生成器会生成一个列表。而你需要添加编辑层——决定保留哪些内容、对读者意味着什么以及哪些内容会中断功能。这个层级是这项任务昂贵且不受欢迎的原因——编写一份版本说明文档需要经验丰富的开发者花费长达8个小时（Moreno等人，引自Daneshyan等人，FSE 2025年），并且一位微软开发者布道师总结了这种情绪：“当轮到我们发布时，我们讨厌创建版本说明”（Jasmine Greenaway，opensource.microsoft.com，2018年）。

## 范围检查

在开始之前确认任务。当出现以下情况时，将任务转至其他方向：

- 用户需要版本号更新、标签切割或发布工件 → 发布自动化工具，而不是这项技能。
- 变更需要前置/后置代码、弃用时间表和代码修改 → `samber/developer-relations-skills@version-migration-guide`。
- 发布值得一篇带有上下文和截图的叙事性文章 → `samber/developer-relations-skills@engineering-blog-post`。
- 问题是哪个渠道宣布发布 → `samber/developer-relations-skills@devrel-content-calendar`。

编写说明并链接到迁移指南在范围内；编写该指南不在范围内。

## 面试

一次问一个，尽可能使用多项选择题。一旦知道表面、受众和源范围，就停止——不要机械地运行整个列表。

**记忆：存储一些关于当前任务或项目上下文的信息。当记忆存储在文件中时，使用`devrel-context.md`；如果使用不同的记忆系统，则依赖该系统。将不同任务的信息分开。删除已完成的任务。为任务添加日期；一般项目上下文不添加日期。一些面试回答可能在两个任务之间有所不同。**
1. 这个表面是什么：`CHANGELOG.md`仓库、git托管发布的正文、托管变更日志页面、产品内“新功能”、应用商店列表、企业咨询或多个？
2. 谁会阅读它：正在升级依赖的集成器、应用程序的最终用户，还是两者都是？
3. 版本范围是什么——前一个标签到`HEAD`、一个里程碑、一个日期窗口？
4. 项目是否已经遵循变更日志规范，或者这是第一个发布？
5. 历史是否遵循提交约定，还是自由形式的？
6. 发布是否包含任何中断或弃用的内容，据用户所知？
7. 是否有迁移指南、升级文档或问题链接到中断条目？
8. 你实际上可以阅读哪些原始材料——仓库、导出的日志、工单列表？
9. 这些说明是否需要翻译？如果是，需要翻译成多少个地区，以及是否有字符限制？

当回答1命名超过一个表面时，或者发布看起来像1级或2级时，才问10-12个问题。一个单表面的发布没有菜单需要排序，无论如何问都是噪音。

10. 这个发布何时必须发布——已经宣布的发布日期、新闻管制、安全窗口，或何时准备好？
11. 这是一个需要发布的单一发布，还是你正在设置从现在开始每个发布的发布方式？
12. 你对这个发布的上限是什么——你自己的时间，产品内说明的工程时间，营销发送，安全或应用商店审查周期？

重新排序下面的表面顺序，并说明哪个回答移动了哪个表面：

- Q10（发布日期）：固定日期会删除需要其他人审查周期的每个表面。
- Q11（每个发布如何发布）：提升托管页面和说明片段工作流，因为两者都是按发布而不是一次支付回报。
- Q12（上限）：你自己的时间单独删除了电子邮件和产品内说明。

如果你的记忆系统具有持久性，请将问题1、2、4、5和9的答案记录为项目约定。它们在发布之间是稳定的；每次发布都重新询问它们是这项任务感到繁琐的主要原因。

## 工作流程

1. **收集原始材料。** 当你可以在仓库中执行shell命令时，运行`[./scripts/collect-release-material.sh](./scripts/collect-release-material.sh)`。否则，使用粘贴的日志、导出的工单列表或用户对已发布内容的描述。不要因为仓库无法访问而停滞——说明正在使用的模式，因为验证强度取决于它。
2. **简化为净差异。** 将修复、回滚和后续提交合并为单一结果。三个提交添加、回滚和重新添加一个标志是一个条目或没有条目。
3. **选择。** 保留消费者可以观察到的每个变更。丢弃他们无法观察到的内容。见下文的筛选规则。
4. **分级发布**以决定它应获得的表面数量。见发布公告分级。
5. **分类。** 将每个存活的变更分配到项目规范中的类别——当项目没有约定时或你必须映射两个时，请阅读`[./references/format-specifications.md](./references/format-specifications.md)`。
6. **编写每个条目**以影响优先，使用项目的声音。见条目结构，以及`[./references/worked-examples.md](./references/worked-examples.md)`中的完整前置/后置发布示例。
7. **处理中断变更和弃用**使用以下三部分形式。
8. **按表面组装**使用`[./references/surface-templates.md](./references/surface-templates.md)`为git托管表面，以及`[./references/non-git-surfaces.md](./references/non-git-surfaces.md)`为应用商店、企业咨询、托管API和浏览器扩展——每个都施加git表面没有的硬限制和审查规则。
9. **运行验证门。** 不要移交未通过验证的说明。
10. **移交。** 指出仍需要人工处理的内容：未验证的性能数字、缺失的迁移指南、需要CVE引用的安全条目。

当项目有多个贡献者且没有说明片段工作流——每个条目都作为其自己的小文件写入同一补丁中——建议一次。在发布时编写的条目会从记忆中重建影响，几周后才会看到变更。

## 筛选规则

保留消费者可以观察到的变更，即使它们看起来是内部的：

- 默认值、错误消息文本（人们根据它匹配）、超时、限制。
- 运行时、引擎或平台版本下限。
- 性能特征，当你有测量时。
- 具有行为影响的重构，以及新文档化的行为。

丢弃没有消费者表面的变更：

- 仅限开发的依赖项提升、代码检查和格式化配置、CI工作流。
- 仅限测试的变更、内部重命名、注释和文档格式化变化。

永远不要根据文件名或目录做决定。`docs/`下的变更可能是与发布相关的；`src/`下的变更可能是纯变化。阅读它做了什么。

当范围太大无法完整编写时，按消费者影响对存活的变更进行排序，并设置明确的切割线，而不是凭感觉修剪。先例：SmartNote研究（Daneshyan等人，FSE 2025年）调整了0.10-0.15的重要性阈值，以平衡冗长与遗漏。转移这种纪律，而不是数字——向用户说明切割线并列出低于它的事项。

## 发布公告分级

在选择表面之前对发布进行分级。PostHog发布了这个框架最清晰的公共版本，其作为资源分配工具的渊源可以追溯到Pragmatic Institute的发布分级。

通过预期的读者影响设置级别，而不是工程工作量——这是这项技能中唯一故意排除工作量排序的地方。四分之一的重写无人能观察到是4级；一条默认变更破坏调用者是2级。按构建成本对级别进行排序会系统性地低估那些破坏人们的廉价变更。

| 级别 | 定义                                         | 它获得的表面                                  |
| ---- | -------------------------------------------- | --------------------------------------------- |
| 1    | 新产品                                       | 所有表面，加上由这项技能外拥有的发布计划      |
| 2    | 对大多数用户有显著影响，或需要用户操作       | 变更日志、发布正文、托管页面、电子邮件、产品内说明 |
| 3    | 对部分用户有显著影响，无需操作               | 变更日志、发布正文、托管页面                 |
| 4    | 对大多数用户没有显著影响                     | 仅变更日志和发布正文                        |

级别定义遵循PostHog发布的指南；每个级别的表面列表是这项技能对其自身表面集的适应。将3级和4级项目合并为一个经过编辑的定期摘要——在没有消耗发布资源的情况下很有用（报告的从业者指南）。1级是一个发布，而不是一个版本；将其交给`samber/developer-relations-skills@devrel-content-calendar`和`samber/developer-relations-skills@engineering-blog-post`。

### 哪个表面首先生产

级别说明发布应获得的表面。当预算在发布中途用尽时，它不会说明哪个首先生产，这两个问题是不同轴上的不同问题——级别是变更的属性，生产顺序是你时间的属性。永远不要让下面的顺序泄漏回分级决策。

- 努力最小优先：`changelog == release body > hosted page > email > in-product note`
- 价值最大优先：`in-product note > email > hosted page > release body > changelog`
- 合规成本：应用商店说明需要在审查周期内发布，无法在不重新提交的情况下更正；企业或CVE咨询需要安全确认，一旦分发就无法撤回；电子邮件一旦发送就无法撤回；变更日志、发布正文和托管页面永远可以编辑。
- 效率，首先做：`changelog == release body > hosted page > in-product note > email`

变更日志和发布正文相同：它们是粘贴两次的相同文本，因此一次编辑可以产生两者。它们分离没有读者，因为一个人找到哪个取决于他们是否从仓库或标签到达。

默认为前两个，一旦托管页面从同一源渲染而不是手动维护，就添加它。只有在级别获得它们并且回答12表明有人可以支付它们时，才添加其余内容。

产品内说明和电子邮件是这项顺序中受饿的：每个都需要一周时间和其他团队的日历，并且每个是唯一能接触到永远不会打开仓库的用户的方式。一旦发布需要用户操作——无人阅读的中断变更被发现会导致故障——立即提升两者，并接受比率在这种情况下是错误的工具。

这个顺序是一个默认值，不是一个法律，并且会随着执行者而变化。根据你所知重新排序它：

- 一个托管页面已经自动从变更日志发布的项目获得该环节免费，应立即采取。
- 没有电子邮件列表的项目删除该行，而不是一次又一次地携带它。

删除回答12的上限规则排除的每个表面，并说明你删除了哪个。

## 条目结构

说明发生了什么，然后说明读者为什么关心——一到三句话（这项技能的工作预算，而不是已发布的规则）。以可观察的效果开头；将机制放在后面，或者丢弃它。

重写内部词汇——工单ID、服务代码名、模块名外人从未看到——为产品术语。

```
差：为仪表板API端点实现了Redis缓存层（PROJ-4471）
好：具有大型工作区的帐户上的仪表板加载速度明显更快。

差：革命性的新流式体验，完全从头开始重建！
好：向客户端添加`stream()`以获得逐个标记的响应。
```

第二对是开发者受众特有的陷阱：营销形容词会让技术读者停止阅读文件。保持平坦和具体。更多对，包括写得不好和正确写的完整发布示例，都在`[./references/worked-examples.md](./references/worked-examples.md)`中。

在一个类别内按消费者影响排序，中断项目优先。一个读者在两个项目点停止阅读应该已经阅读了可能导致他们构建中断的两个项目点。

匹配项目的情绪并保持一致性：如果项目使用要求现在时态的规范，则使用现在时态（“添加`stream()`”）；否则使用过去时态（“添加流式”）。永远不要在同一个发布中混合两者。

### 声音

两种学校意见不一，都有可信的从业者支持（来源在`[./references/published-findings.md](./references/published-findings.md)`）：

- **编辑学校。** Anna Pickard在Slack的发布说明中基于“商店文本框只是我们能够成为人类的一小空间”的假设，将声音提炼为清晰、简洁、人性化，清晰度排名最高。
- **技术写作学校。** Sarah Maddox将功能狭隘地定义为告诉客户发生了什么变更，尤其是在它改变他们使用产品的方式时。Anne Edwards认为有趣的友好说明太长，模糊了信息，并增加了非母语读者额外的工作量。

用三个问题，而不是品味来解决它：

1. 读者是在集成这个变更，还是接收它？
2. 文本是否需要翻译？
3. 品牌是否已经在其他地方携带了这种语调？

- 效率，默认：`技术写作学校 > 编辑学校`

默认使用技术写作学校：它更快编写，不受翻译影响，并回答读者的实际问题。仅在三个条件都满足时提供编辑语调，因为单独任何一个都不够：

- 消费者表面
- 一个地区，或翻译预算
- 一个声音已经存在的产品

在本地化中，古怪不是一种品味选择：它增加了每个地区的翻译成本和缺陷率。

## 中断变更和弃用

给每个中断条目三个部分：

1. **什么中断**——可观察的行为，而不是内部原因。
2. **它影响谁**——受影响的子集（一个SDK、一个配置标志、一个端点的调用者）。“所有人”很少是真的。过度使用它会教读者跳过标记。
3. **该怎么做**——一行行动，当修复比重命名更长时，加上链接。

```
**中断：** `client.send()`现在拒绝超过1 MB的有效负载而不是截断它们。影响依赖静默截断的调用者——分片有效负载或捕获`PayloadTooLarge`。参见v3迁移指南。
```

保持版本号诚实：

- 主要意味着中断。
- 次要意味着添加。
- 补丁意味着修复。

在次要发布中的“移除”条目是说明或版本中的缺陷——这样说而不是发布它，因为信任版本范围的读者会无声地中断。

在一个不删除任何内容的发布中宣布弃用，命名替代品和最早移除它的版本。在执行移除的发布中再次引用该公告。

## 杂乱的史实

大多数真实仓库没有提交约定——SmartNote样本中约90%的项目没有强制执行，并且只有54%的Jiang等人调查的900个开源项目会从拉取请求生成说明。假设日志是压缩合并、`wip`和`fix tests`，直到看到相反的情况。

- 根据差异比较和拉取请求的标题及正文工作，而不是提交主题。
- 通过阅读代码将更改的文件分组为功能，然后在编写条目之前与用户确认每个分组。
- 确认你无法看到的内容：一个受特性标志限制的更改，一个对用户可见的基础设施更改。
- 只有在用户要求时才提出提交约定。修复管道与编写本次发布的说明是不同的工作。

## 目标受众变体

条目制作对于开发者工具和消费者产品是相同的：首先描述可观察的效果，不使用内部术语，诚实界定范围。不同之处在于其周围。

- **集成商 / B2B受众。** 精确性和引用胜出。将每个条目链接到其拉取请求。在版本中而不是日期中声明弃用窗口，并保持它们较长。企业读者可能落后于几个版本，通常在几个月后搜索症状或CVE，需要完整的破坏性集合并固定在顶部。
- **最终用户 / B2C受众。** 以利益为导向且简短 - 此技能预算3-5个项目，一个工作默认值，而不是一个发布标准。将其作为产品内说明、电子邮件或商店列表发布，并链接回完整条目，供任何需要的人查看。

当一个发布服务于两者时，首先编写集成商版本，并从中推导出面向用户的版本 - [./references/surface-templates.md](./references/surface-templates.md) 给出推导顺序。

## 验证关卡

生成的说明在两个方向上都会失败：没有来源的条目，以及没有条目的已发布更改。在移交前检查所有四个方面，并迭代直到它们成立。

1. **可追溯性 - 100%。** 每个条目至少映射到一个范围内的提交或拉取请求，并且该声明可以在该差异中验证。作为原则不可协商：GitHub自己的发布说明文档将“确认说明包含所有且仅有的预期信息”作为一个编号步骤。100%的数字本身是一个自我设定的标准，而不是一个发布标准。
2. **覆盖范围。** 每个消费者可观察的更改都有一个条目或显式的排除 - 显示排除列表，不要无声地遗漏。100%的目标是一个自我设定的基线，故意比观察到的实践更严格：SmartNote评估中人类编写的说明覆盖了31%的提交，Abebe、Ali和Hassan发现格式良好的发布说明列出了6-26%的问题。这些数字描述了作者在覆盖范围和简洁性之间进行权衡，而不是要匹配的标准。如果“消费者可观察的”在一个大发布上确实存在争议，与用户协商界限并记录你划定的位置。
3. **无来源的数字。** 每个定量声明（“40%更快”）都来自源材料中的测量。删除数字而不是估计它。
4. **破坏性完整性。** 每个破坏性条目都包含三个部分，并在存在的情况下附带一个迁移链接。

在所有四个方面的持久规则：**可审查单元是声明与差异的映射。** 语气、排序和分组在发布后很容易修复；一句描述代码未做的更改的句子会永久损害信任，并且模型最有可能引入这种缺陷。任何不将差异与句子并排放置的审查步骤都是一场表演。

对于摘要段落和任何面向用户的变体，用你喜欢的humanizer技能进行快速遍历。保留符合规范的点 - 它们旨在读作简洁和机械。

## 调用示例和预期输出

典型请求：_"为v2.4.0编写变更日志"_、_"将这些40个提交转换为发布说明"_、_"我应该在GitHub发布正文中为这个标签放入什么内容?"_、_"起草App Store更新的新功能"_、_"我们的变更日志读起来像git日志，修复它"_。

收集一个范围内的原始材料：

```bash
./scripts/collect-release-material.sh --from v2.3.0 --to HEAD
```

按此顺序交付：

1. **说明**，每个请求的表面一个块，用围栏Markdown准备好粘贴。
2. **可追溯性表** - 每个条目一行，包含它映射到的提交或拉取请求。
3. **排除列表** - 你看到并故意排除的每个更改，以及原因。
4. **供人类处理的开放项** - 未测量的性能声明、缺失的迁移链接、需要CVE的安全条目、任何你不得不要求用户确认而无法确认的东西。

[./references/surface-templates.md](./references/surface-templates.md) 展示了在样本发布上组装的四个部分。

## 失败模式

| 症状                                | 原因                                      | 修复                                                                |
| -------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------ |
| 说明读起来像提交日志             | 每个提交而不是每个结果编写              | 重新减少到净差异，合并修复                                        |
| 每个发布都说“各种错误修复”     | 没有阅读源材料，只有标签名              | 回到差异；一个空的发布比模糊的发布更好                             |
| 破坏性更改埋在列表中间          | 在影响顺序之前应用类别顺序              | 将破坏性项目首先移到每个类别内                                     |
| 读者问“这影响我吗？”             | 条目声明机制，而不是效果                 | 重新编写影响优先，添加受影响的子集                                |
| 条目与代码矛盾                     | 信任了拉取请求标题                      | 与差异重新检查；标题夸大了                                        |
| 两个发布使用不同的时态           | 没有记录的约定                          | 修复当前发布，在记忆中记录约定                                    |
| 审查者批准了错误的条目           | 审查阅读了散文，而不是差异              | 将每个句子与其差异进行审查                                        |
| 翻译说明被拒绝或截断             | 写给了最大的表面首先                    | 首先写最严格的限制，然后扩展；见非git表面                        |
| 每个更改都得到一个发布             | 没有分层步骤                            | 首先分层，然后分配表面                                            |

## 测量

如果表面经过仪器化，按每个发布跟踪：

- 效率，首先跟踪：`支持量 > 破坏性条目点击率 > 发布页面浏览量 > 升级时间 == 审查评论计数`

- **标记为与发布相关的支持和问题量。** 除了你已经做的分诊外，没有任何额外成本，并且在几天内就会移动 - 出发后立即的峰值通常意味着沟通不足的行为更改，而不是一个糟糕的发布。
- **从破坏性条目到其迁移指南的点击率。** 标记链接需要一小时，并且是唯一说明条目是否完成工作的数字。
- **发布页面浏览量与该版本下载量或安装量。** 如果表面经过仪器化，组装需要一小时，但浏览量和安装量回答不同的问题，它们之间的比率是嘈杂的。
- **升级时间** - 发布后7天、30天和90天使用中的版本分布 - 以及**每个发布的审查评论计数**，如果说明通过审查，它们在底部绑定：每个都需要一个四分之一才能说明任何东西，并且每个都需要一个你可能没有的管道（一个用于遥测，另一个用于固定的审查步骤）。Tom Johnson在运行此任务的公共帐户中记录每个发布有15-20条评论，在大约十几次迭代后降至3-5条 - 一个收敛曲线，而不是立即要达到的目标。

升级时间是这个顺序所剥夺的：它是唯一衡量说明是否使任何人移动的指标，并且它需要一个四分之一加上遥测，所以它永远不会在比率上获胜。当发布是破坏性的，并且你需要知道谁仍然在旧版本上，然后再移除它时，提升它高于一切。

从不声称从变更日志中获得的采用、保留或收入影响。唯一发布的成果证据是关联性的：较长的Google Play发布说明与69,851个2,232个应用的69,851个发布（Yang等人，《实证软件工程》27:55，2022年）的平均评分较高相关，受发布频率和应用成熟度的混淆。

Linear广泛引用的变更日志纪律的回报（招聘、投资者信心、早期采用者信任）是第一方的，未量化。引用它们作为记录的实践，永远不要作为ROI的证据 - 过分强调归因会损害与这个受众的信誉。
