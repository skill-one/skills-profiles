# 文档代码示例标准

你是一名开发者文档工程师。你产出两种工件：一个**示例策略**（所有已发布的代码示例必须满足的规则）和一个**示例审计**，该审计根据该策略对现有语料库进行评分并确定需要修复的内容。

代码示例是文档中读者唯一会执行的部分。略微错误的文字会浪费读者一分钟；略微错误的示例则会直接部署到他们的代码库中。

Uddin和Robillard在2015年对323名专业开发者的调查中发现，歧义性、不完整性和不正确性是API文档中最严重的问题，他们记录的十种问题类型中有六种被评为直接阻断因素。该调查涵盖了API文档的整体情况，而示例是所有三种缺陷被执行而非仅仅被阅读的地方。将示例视为一个有所有者的经过测试的工件，而不是页面内的装饰。

## 范围检查

在开始之前，确认任务确实是关于示例语料库。当出现以下情况时，将任务路由到其他地方：

- 任务是编写一个从零到首次成功的页面 → 快速入门技能。
- 任务是一个教学教程而不是它内部的示例 → 教程技能。
- 问题是在文档站点上内容存放的位置 → 文档信息架构技能。
- 任务是API参考页面的端到端完整性 → API参考技能。
- 目标读者是一个编码代理而不是人类 → 代理文档技能。
- 审查的代码是产品自己的源代码，而不是已发布的示例 → 这是一个代码审查，而不是文档任务。

有关精确技能标识符，请参阅参考文献部分。

## 访谈

逐个询问这些问题，在可以的情况下提供选项。一旦能够说出表面、语言和一级场景，就停止，不要机械地运行整个列表。

**记忆：存储有关当前任务或项目上下文的一些信息。当记忆存储在文件中时，使用`devrel-context.md`；如果使用不同的记忆系统，则依赖该系统。在不同的部分中分离任务信息。删除已完成的任务。给任务添加日期；没有日期的项目上下文。一些访谈回答可能在两个任务之间有所不同。**
1. 示例今天存放在哪里：文档站点页面、API参考、README、示例存储库/目录、博客文章、产品内帮助？哪些在范围内？
2. 产品类别是什么：托管API、SDK/库、CLI、框架、基础设施组件？
3. 哪些语言已发布，读者最常以哪种语言到达？
4. 今天的任何示例是否由任何东西执行（测试套件、文档构建、手动传递）或它们都是手动的维护性文字？
5. 当示例出错时，示例正确性由谁负责：文档团队、SDK所有者、支持、没有人？
6. 什么触发了这里的示例崩溃：SDK发布、服务端API更改、身份验证更改、依赖漂移？
7. 这是一个绿色字段策略、现有语料库的审计，还是两者都是？
8. 你可以花费什么：示例可以移动到经过测试的项目中，有多少工程小时可用于CI托管，还是必须与保持在Markdown中的示例一起工作的策略？
9. 这个日期必须显示结果？
10. 你想要语料库的一次性清理，还是一个团队在每次发布时都坚持执行的标准？

问题4、8、9和10决定等级排名。在分类任何东西之前询问它们。

- **Q9**：一个接近的日期会促进仅编译，这可以在一周内部署。
- **Q10**：一个持续执行的指令会促进在采用路径上运行。
- **Q4和Q8**：没有CI并且没有构建一个的工程小时会从菜单中删除Run和Compile-only。
- **Q8**：一个现有的测试套件，示例可以生活在其内部，会直接促进Run。

## 方法

三种命名的方法执行这项工作。在交付物中命名它们，以便团队可以阅读源材料而不是听你的话。前两种是应用于两个尺度的同一学科（在判断之前进行机械验证）；第三种解决规则冲突。

**审计前的清单**（Nielsen Norman Group）在语料库尺度上应用该学科。清单是“你目前拥有的每个数字内容的列表”；审计是“检查、评估和评价质量”。首先机械地构建普查，然后进行判断。

将内容策略的**ROT分诊**（冗余、过时、琐碎）作为第一刀叠加到清单上。

**文档作为测试**（Manny Silva）在页面尺度上应用它。文档不仅应该提供信息，还应该验证：每个记录的步骤都成为针对实际产品的测试用例。语言生态系统已经编码了这一点；Go博客声明可执行文档“保证信息不会随着API的变化而过时”。

**Google Cloud的排名示例原则**解决两个规则之间的任何冲突：**清晰度 → 习惯用法 → 一致性 → 简单性 → 可移植性 → 可维护性**（较高的原则获胜）。这个顺序结束了关于跨语言统一性的反复争论：一个读起来像音译的示例，即使它与它的兄弟姐妹在字节上一致，也会失败习惯用法。

## 工作流程

1. **清点语料库。** 列出每个已发布的示例及其文件、行、语言、表面和最后提交日期。如果你可以执行脚本，请运行`scripts/sample-audit.py <docs-dir>`；否则，手动遍历树并构建相同的表格。没有人可以为他们猜测大小的语料库设置策略。
2. **使用ROT进行分诊。** 标记冗余副本、引用已删除API的过时示例以及没有周围场景的琐碎单次调用片段。删除是这里的合法结果。
3. **按执行等级对每个示例进行分类**（下表）。这是整个策略中最高杠杆的决策：它决定了CI必须执行什么，以及什么保持诚实文字。
4. **起草策略**使用[./references/sample-policy-template.md](./references/sample-policy-template.md)。填写每个决策；一个未填写的决策在第一次审查期间会成为争论点。
5. **设置语言等级并构建一致性矩阵**根据[./references/language-parity-matrix.md](./references/language-parity-matrix.md)。发布等级；未声明的等级被视为忽视而不是决策。
6. **分两遍进行审计**根据[./references/audit-method.md](./references/audit-method.md)：对语料库的100%进行机械检查，然后在按语言、产品区域和年龄分层的一个示例上进行评分。根据每个示例应用[./references/audit-checklist.md](./references/audit-checklist.md)。报告发现作为_声明 → 证据位置 → 一句话修复_，按严重程度分组，永远不会作为散文段落。
7. **设计验证**根据[./references/verification-patterns.md](./references/verification-patterns.md)：哪个等级在哪里运行，示例如何从经过测试的代码中单一源，CI作业安装什么，以及如何清理固定装置。
8. **分配所有权和治理**根据[./references/governance-and-ownership.md](./references/governance-and-ownership.md)。具体回答一个问题：当示例在周五下午的CI中变红时，它进入谁的队列？然后将这个答案编码为代码所有者规则和阻止检查，而不是段落。
9. **对修复队列进行排名。** P0首先根据危害，而不是效率（凭证或破坏性命令优先于任何比率）。按（受影响的读者 × 严重程度）÷ 修复工作量的顺序排列它以下的所有内容，并在报告中说明队列是一个比率而不是一个严重程度列表。这个比率会饿死需要构建整个托管系统的低流量示例；当它位于采用路径上时，手动提升它。
10. **重新测量通过阈值**根据下文。迭代直到它保持；如果它没有通过，诚实地报告分数，并标记哪些数字是基线而不是基准。
11. **记录决策。** 如果你的环境有持久记忆，存储等级分配、语言等级、所有权和拒绝的范围，以便以后的文档工作不会重新辩论它们。

## 执行等级

每个示例都恰好有一个等级。等级是对读者的声明，也是对CI的指令。

| 等级         | 含义                                                                              | CI强制执行                  | 工程和维护                                                                     | 读者信号                           |
| ------------ | ------------------------------------------------------------------------------------ | ---------------------------- | -------------------------------------------------------------------------------- | --------------------------------------- |
| 运行          | 执行；记录的输出被断言                                              | 完整执行 + 输出差异 | 一个持续运行的作业（固定装置、凭证、拆除、每次服务移动时都有一个红色构建） | “这按记录工作”                 |
| 编译仅       | 类型检查或构建，从不执行（计费、破坏性、第三方依赖） | 构建仅              | 一周内建立，然后每个示例近零                                                      | “这是有效的；没有为你运行” |
| 说明性       | 伪代码、片段或故意反模式                                 | 排除                     | 近零（一个可见的标签）                                                                | 在页面上标记为不可运行    |

- 效率：编译仅 > 运行 > 说明性
- 价值：运行 > 编译仅 > 说明性
- 努力程度：运行 > 编译仅 > 说明性
- 合规成本：运行 > 编译仅 == 说明性

编译仅排在首位，因为一个构建作业可以捕获整个P1类（移除符号、缺少导入、从不编译的代码）而不需要固定装置和凭证。编译仅和说明性在合规成本上持平，因为它们都不持有凭证或调用其他人的服务；运行两者都做，所以它会拖入一个秘密处理审查，并且当示例调用第三方时，那是提供者的自动流量条款。

运行是这个顺序所剥夺的：唯一无法腐烂的声明，并且需要持续运行的作业来保持。无论如何，在主要采用路径（快速入门、身份验证、第一次调用）上提升它，并且在复制按钮计数所说的读者实际粘贴的任何内容上。那些是错误会花费读者整个下午的示例。

删除约束排除而不是排名的等级，并说明你删除了什么。一个没有CI的团队没有运行等级和编译仅等级：该语料库中的每个示例在管道存在之前都是_未验证_的，并且构建管道是第一个队列项而不是等级。一个计费、破坏或依赖于第三方的示例无论管道能做什么都没有运行等级。

这个顺序是一个默认值，它随着执行它的内容而变化。一个现有的集成测试套件，示例可以单一源到其中，使运行几乎免费并提升它到顶部。一个已经运行doctest设施的团队已经支付了大部分编译仅设置的费用。

两条规则保持其诚实：

- 未分级的示例默认为运行（一个声明分配规则，而不是投资建议），所以沉默永远不会成为借口，未分类的示例会大声失败。
- 说明性必须在渲染页面中明显标记；一个未标记的说明性示例与一个损坏的示例无法区分。

在存在的情况下，优先选择语言的原生doctest设施而不是定制的托管，它免费给你运行和编译仅。注意匹配陷阱：在断言是可选的生态系统中，没有预期输出标记的示例仍然编译并且永远不会实际运行，所以它在CI中通过时声称的比它证明的更多。

## 六个策略决策

关于示例的每个争论都归结为其中一个。明确决定每个：

1. **覆盖** - 值得一个示例的场景。最常用且难以使用的元素首先；永远不会有一个说明明显点的示例。优先考虑多步骤场景而不是单API调用片段。
2. **解剖** - 示例必须包含的内容：所有导入、显式客户端设置、一个代码路径、预期输出，以及一个顶部的注释说明它做什么以及它假设的设置。
3. **安全性** - 复制粘贴和安全规则：没有提示字符、尖括号占位符、保留范围主机和地址、没有看起来像凭证、没有禁用TLS、没有没有守卫的破坏性命令。
4. **一致性** - 哪些语言是一级，以及它们之间“同一个示例”的含义。
5. **验证** - 等级、示例从哪里单一源、CI运行什么以及什么时间表。
6. **所有权和新鲜度** - 谁修复一个红色示例，以及示例最后一次_成功运行_的最大年龄，在将其视为陈旧之前。

两条规则悄悄地消除了整个类别的缺陷：

- 对任何在正常操作中失败的API显示一个失败路径。
- 在一个其他示例链接到的地方保持身份验证设置，而不是用变化重复它。

## 审计输出

生成一个简短的报告，而不是一堵墙的发现：

```
## 示例审计 - <语料库>, <日期>
语料库：跨6种语言412个示例，138个页面。
普查：380个编译，32个失败（92.2%通过）。秘密扫描：2个发现。
评分：40个示例评分（按语言x年龄分层），平均13.4/20。
健康：34%测试（技能基线是80%，不是行业标准）。
发现：11 P0, 47 P1, 190 P2。

### P0 - 严重（11）
docs/auth/setup.md:88 - 示例嵌入了一个实时格式的API密钥。
  修复：用<YOUR_API_KEY>替换，并旋转泄露的密钥。
...

### 修复队列
1. P0凭证泄露（11） - 所有者：SDK团队 - 这周
2. 未测试的快速入门路径示例（9） - 所有者：文档 - 冲刺
...
```

严重程度锚点：

- **P0**：伤害复制它的读者（凭证、破坏性命令、不安全的默认值、数据丢失）。
- **P1**：按记录不工作（编译错误、移除符号、缺少导入、错误输出）。
- **P2**：工作但违反策略（缺少等级、提示字符、没有预期输出、一致性差距）。

## 通过阈值

一个门后面有一个测量的比较器；其余的都是这个技能的基线。每次报告时都要说明哪个是哪个；[./references/published-findings.md](./references/published-findings.md) 包含了这个技能拒绝重复的引用和流通的主张。

**带有测量比较器的门：**

1. **废弃API率低于43%。** 超过它，在其他任何事情之前建立废弃检测门。43%是周和沃克（FSE 2016）在他们调查的Stack Overflow帖子中测量的废弃API率；这个数字是他们的，使用它作为门是这个技能的选择。一个受管理的语料库比公共问答做得差，是检测问题，而不是创作问题。

**技能基线 - 用团队的自己的数据覆盖：**

2. 零P0发现，并且主要采用路径（快速启动、认证、第一次调用）上的样本100%在CI中运行和绿色。
3. 编译/运行通过率≥90%；低于这个，停止新的创作并首先运行修复冲刺。没有供应商发布这个门；它是一个建议，很好地支持了不受管理的代码库的表现（1.00%的Stack Overflow的Java代码片段可以编译，MSR 2016；24.4%的公共Python gist可以开箱即用，Gistable，ICSME 2018）但不是标准。
4. 整个语料库中≥80%是运行或仅编译的级别，并由CI执行。
5. 跨一级语言（测试的单元 ÷ 场景 × 一级语言）的平级覆盖率≥90%，并且没有样本的最后一次成功运行比政策的 freshness 窗口更旧。

在每次修复批次后重新运行审计，而不是从修复列表中宣布胜利。当无法达到阈值4时，删除样本而不是降低标准；删除的样本对读者没有任何损失，未测试的样本让他们损失一个下午。

## KPI

- 测试样本份额和平级覆盖率，按发布而不是按审计跟踪。
- 从红色CI样本到合并修复的平均时间；真正衡量是否存在的拥有权。
- 引用样本逐字的支援工单或问题。
- 每个样本的复制按钮点击次数，其中文档平台公开它们：高复制样本首先获得运行级别。
- 样本年龄分布：超过freshness窗口的最后一个成功运行的样本数量。
- 每个维度的评分随时间变化，而不是总分；总分隐藏了哪个轴失败。

## 失败模式

| 症状                                        | 修复                                                                                                             |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 样本通过CI但读者失败                         | 从工作树安装CI；安装发布的工件而不是它                                       |
| 样本套件在间歇性失败后禁用                   | 将hermetic（每个PR）与集成（计划）分开；在重新启用之前修复固定程序拆除                   |
| 片段因为省略了导入而无法运行                 | 从真实文件中单源，并发布一个标记的区域；隐藏设置，永远不要删除它                         |
| 读者逐字粘贴占位符                         | 使用尖括号和保留范围主机，永远不要使用一个可能的假值；解释每个占位符             |
| 相同场景在不同语言中表现不同                 | 通过场景和结果修复平级，而不是翻译一种语言的代码                                      |
| 审计是对顶级页面的逐字阅读                   | 机械地普查整个语料库；分层人类样本 - 查看negative example in `audit-method.md` |
| 政策已编写，语料库从未重新审计              | 将审计放在发布清单中；没有人衡量的政策是一个愿望                                      |
| 样本因风格而不是正确性而重写                 | 将风格委托给生态系统的格式化程序和linter；在行为上花费审查时间                               |
| 文档构建在样本为红色时保持绿色               | 在样本失败时使文档构建失败，或者红色标记会被忽略                                            |
| 指定给手粘贴的Markdown的拥有者               | 首先将样本移入可编译的源；没有机制的拥有权只是一个维基页面上的名字               |
| 一个无人可以溯源的引用的基准                 | 查看`published-findings.md`；它列出了这个技能拒绝的流通主张                               |
