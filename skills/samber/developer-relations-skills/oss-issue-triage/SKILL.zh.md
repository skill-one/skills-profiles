# 开源项目问题筛选

您设计的系统决定了项目收到的待处理问题和拉取请求如何被处理——标签、接收流程、响应承诺、职责轮换、关闭规则——根据维护者实际拥有的能力来调整规模。

队列失控并非因为标签错误。它失控是因为流入量超过了可用的注意力，并且没有书面规则说明差异的处理方式。让这种算术变得明确，然后围绕它进行设计。

2025年机器生成的提交破坏了其中一部分。RedMonk的Kate Holterhoff为安全报告命名了这种不对称性（2026年5月）："现在生成一份看似合理的漏洞报告成本仅为几美分。而判断其真实性仍然需要专家花费一小时的时间。" 流入量不再受人类工作量的限制，而筛选能力仍然受限制，因此每个设计都需要对数量有计划的答案，而不仅仅是分类。

不要单独筛选项目，而是管理首次贡献者队列、审查代码或处理行为事件。将这些工作转交给其他地方：

- 首次贡献路径、良好首次问题：samber/developer-relations-skills@oss-contributor-onboarding
- 重复问题转入文档：samber/developer-relations-skills@developer-troubleshooting-docs
- 敌对行为：samber/developer-relations-skills@developer-community-moderation
- 范围由谁决定：samber/developer-relations-skills@oss-governance
- 更广泛的测量框架：samber/developer-relations-skills@developer-community-health

## 面试

一次问一个问题，尽可能使用多项选择题，跳过用户已经回答的内容。问题1-6是关键；没有它们，您设计的将是一个虚构项目的流程。

**记忆：存储一些关于当前任务或项目上下文的信息。当记忆存储在文件中时，使用`devrel-context.md`；如果使用不同的记忆系统，则依赖该系统。在不同的部分中分隔任务信息。删除已完成的任务。为任务添加日期；没有日期的项目上下文。一些面试回答可能在两个任务之间有所不同。**
1. 努力上限是什么：今天有多少人筛选，每个人在坏月份中可以每周投入多少小时，以及是否任何人可以添加筛选者或更改跟踪器设置？
2. 是否有一个日期必须在此之前完成——发布、审计、已发布的响应目标？
3. 您希望清空积压问题，还是希望有一个在明年仍然有效且维护者不同的系统？
4. 队列有多大：打开的问题、打开的外部拉取请求、最老的问题的年龄？
5. 流入量是什么样的——主要是错误报告、功能请求或使用问题？
6. 项目是志愿者运营、公司支持还是混合的，并且是否有人有合同规定的响应义务？
7. 哪个跟踪器，您可以在上面更改标签、模板和自动化，今天存在什么（标签、模板、贡献指南、机器人）？
8. 外部拉取请求是否计为筛选工作，或者是否有单独的审查流程拥有它们？
9. 过去一年低质量或机器生成的提交的比例是否增加，并且您可以估计吗？
10. 安全报告今天在哪里到达——公共跟踪器、私人频道或未定义的任何地方？
11. 使用问题应该去哪里——论坛、聊天、讨论、尚未定义的任何地方？
12. 谁可以关闭问题，谁决定什么是超出范围，是什么让您现在打开它？

如果问题1回答有效为零小时，则停止设计并说明：诚实的交付成果是减少接收量加上发布的"此项目处于维护模式"声明，而不是无人会应用的分类法。

对1、2和3的回答会重新排序下面的每个菜单；说明哪些被移动了什么。

- 硬日期：促进本周起作用的行为（缩短承诺、选择器路由、方向检查）；降低任何在季度内获得回报的事项。
- "明年仍然有效"：促进添加筛选者和验证表单，两者在任何单个月份内按比例都会降低。
- 低努力上限：删除选项而不是降低它们——如果没有添加人的权限，添加筛选者不是一个杠杆，也不应出现在交付成果中。

## 第1步 - 在更改队列之前测量队列

导出跟踪器的问题并运行基线；每个后续决策都参考这些数字。

```bash
gh issue list --state all --limit 2000 \
  --json number,title,state,createdAt,updatedAt,closedAt,labels,author,comments > issues.json
python3 scripts/triage-baseline.py issues.json --triage-prefix "kind/,priority/"
python3 scripts/triage-baseline.py issues.json --stale-days 120 --format json > baseline.json
```

它报告，从JSON数组、JSON Lines或CSV：

- 打开数量
- 年龄中位数/p90
- 未筛选的比例
- 非活跃数量
- 第一条人类响应的中位数和p90时间
- 创建与关闭的流量
- 标签使用情况，包括一次性使用的标签

在没有可脚本化环境的情况下，手动抽样50个打开的项目并估计相同的数字——估计比盲目设计更好，并且没有基线，您无法判断重新设计是否有效。

在提出任何建议之前，回顾这些数字：一个80%是使用问题的队列需要不同的干预措施，而一个80%是未回答的错误报告的队列需要不同的干预措施。

然后询问每项任务的框架隐藏了什么：**这些项目会聚集吗？**在一个大的陈旧积压中，将具有共同根本原因的问题分组到跟踪问题下，并将其余问题重定向到该问题，通常比逐项筛选清除的队列更多。在设计逐项机械装置之前，在这里决定逐项与聚集。

## 第2步 - 做能力算术

将筛选者 × 每周会话次数 × 每次会议分钟数 ÷ 每个项目分钟数，并与基线的流入量进行比较。

不要导入每项任务的分钟数常数。在步骤9中测试试点会话，并使用项目的数字；在此之前，三分钟是一个规划占位符，这个技能设定，而不是一个测量的行业数字。深度调查不是筛选——它是工作筛选时间表。

当能力低于流入量时，没有标签方案可以修复它。有三个杠杆可以缩小差距；根据每个维护者小时释放的队列来选择，而不是最快输入哪个：

- 效率：减少接收量 > 缩短承诺 > 添加筛选者
- 努力程度：缩短承诺（重写一行，辩护一次）> 减少接收量（一天表单和选择器配置）> 添加筛选者（招募、授予权限、校准——在新的筛选者成为净积极之前需要三个月）
- 价值：减少接收量（永久降低算术的左侧）> 添加筛选者（唯一可以提高能力的杠杆）> 缩短承诺（没有改进；承诺仅仅是停止被破坏）
- 合规成本：减少接收量 == 添加筛选者（因为两者都是内部决策，没有外部交易对手）> 在问题6发现合同义务的地方缩短承诺，因为在那里发布的靶标是一个承诺，缩短它是合同变更

效率会消耗添加筛选者的资源——唯一可以提高能力的杠杆，也是最慢支付的杠杆。每当项目期望在一年后仍然存在时，请推广它：一个只切割接收量的项目会缩小以适应其最坏的情况。在交付成果中说明选择的杠杆，以免用户在三个月后感到惊讶。

现在决定**量级门禁触发器**，在一切着火之前：流入率或有效报告份额，项目将限制谁可以打开项目，限制每个作者的打开提交数量，或更改吸引流量的激励措施。采用门禁的项目只有在筋疲力尽后才采取行动；在设计时间决定触发器，使其成为政策而不是危机即兴创作。[./references/worked-examples.md](./references/worked-examples.md)展示了curl如何通过这种算术减少到20%的有效份额，并显示了为什么它的答案作用于提交的经济性而不是筛选的速度。

根据能力数字而不是雄心设定首次响应目标——人类回复，而不是修复或机器人问候。算术、志愿者与公司支持的区别和合同义务：[./references/policy-and-metrics.md](./references/policy-and-metrics.md)。

## 第3步 - 设计标签分类法

将标签作为正交轴——类型、状态、优先级、区域、面向贡献者——每个项目在每个轴上最多有一个值。状态移动队列；优先级引发争论，因此尽可能保持项目可以忍受的最小化。

根据[./references/published-findings.md](./references/published-findings.md)中的参考点调整规模：

- 新仓库上的十个默认标签
- 最常用的筛选技能中的五个状态角色加上两个类别
- Kubernetes规模的前缀家族六个

将它们映射到项目是这个技能的判断，而不是一个来源规则：诚实的答案通常介于前两者之间，并且只有在所有权真正分裂时才接近第三者。

来自PyTorch分类法的两个规则——这是唯一记录在生产中运行的分类法，在PyTorch自己的主仓库上：

- **根据信心限制标签。** 在高或中等信心时应用标签；在低信心时应用"需要审查"状态而不是猜测。猜测的区域标签将项目发送到错误的负责人，并且比没有标签的成本更高。
- **永远不要让自动化应用最高优先级级别。** 将每个候选者路由到人工确认而不是自动化。优先级是具有最多下游后果和最少机器可检查定义的轴。

轴、启动集规模、命名规则、清理现有标签混乱而不删除历史记录、允许列表和验证模式、跟踪器机制：[./references/label-taxonomy.md](./references/label-taxonomy.md)。

在触摸跟踪器之前批准分类法——强加给未同意维护者的分类法一个月内就会衰减。

## 第4步 - 减少接收量

用于应该从未到达的问题的能力是最大的可回收块。按每小时恢复的筛选分钟数对四个削减进行排序——没有合规成本轴适用，因为四个中没有一个是创建对任何人的义务：

- 效率：选择器路由 > 验证表单 > 禁用空白问题 > 自动应用类型标签
- 努力程度：禁用空白问题 == 自动应用类型标签（一个设置，一行表单YAML）> 选择器路由（需要一个可能尚未存在的目标）> 验证表单（每个真实类别一个表单，编写、测试和修订，当报告者跳过字段时）
- 价值：选择器路由（移除整个类别而不是加速它们）> 验证表单（将两个往返转变为每个错误报告一个提交，永远）> 禁用空白问题（关闭使表单可选的绕过）> 自动应用类型标签（一个轴，项目秒数）

1. **选择器路由**——使用问题到论坛或聊天，商业请求到销售联系人。停止条件：一个路由的报告永远不会到达跟踪器，因此步骤5-8永远不会触及它。
2. **验证表单**替换Markdown模板。要求报告者提供恰好改变结果的字段；报告者跳过的每个可选字段都教会他们表单是装饰性的。
3. **禁用空白问题**一旦表单覆盖了真实类别。
4. **自动应用类型标签**从表单，加上跟踪器拥有的问题类型。

效率会消耗选项2：最高重复价值，最高设置，因此一个有自由晚上的维护者会做切换而不是继续往返。当错误报告主导流入量时，推广它为第一个——成本在每个项目上支付。一个没有路由使用问题的项目（问题12）没有选项1——从这次过中删除它，而不是将其列为待办工作。

**安全报告完全离开跟踪器。** 每个成熟的项目都运行相同的三个元素管道，与一般筛选分开：

- 一个私人接收通道
- 一个命名、规模限制的响应团队
- 一个协调披露的封禁机制

Apache指示贡献者永远不要在公共跟踪器中输入漏洞详细信息。没有安全列表，代码主机的私人漏洞报告是默认值。

表单功能、选择器配置、完整的安全路径和量级门禁选项：[./references/issue-intake-and-routing.md](./references/issue-intake-and-routing.md)——在编写表单YAML之前阅读它。

## 第5步 - 分配职责

未拥有的流程不是一个流程。

1. 命名谁筛选，在一个有明确轮换时间（一周是常用单位）和命名备份的轮换中。Mozilla的两层模型是最稳健记录的模式：一个长期的**筛选负责人**按组件负责，加上一个**筛选职责**每周轮换并执行工作。
2. 修复一个节奏和一个停止规则：一个会话在其时间框内结束，而不是在收件箱为零时结束，以便筛选在尖峰期间生存下来。
3. 设置会话顺序：最新未筛选的首先（保护响应目标），然后是报告者回复的项目，然后是一个固定的积压配额。
4. 授予筛选级权限而不是提交访问权限——大多数跟踪器都有一个用于标签、关闭和分配而不需要写入访问的角色，这是筛选团队如何超过提交者的方式。
5. 定义升级：筛选者单独决定什么，什么等待维护者，等待时间可以有多长。

三个决定决定一个定期筛选会议是否生存：

- 为它构建的队列视图
- 异步预筛选，以便会议是决策而不是首次联系
- 记录标签或状态更改的决策，而不仅仅是会议记录

Rust的编译器筛选会议是最清晰的例子：一个Zulip流预筛选，并通过替换标签来设置优先级，因此输出保持可查询。

## 第6步 - 给拉取请求自己的门禁顺序

拉取请求携带问题没有的硬自动化检查；不要重用问题流程。

两个门禁不是菜单项，因为两者都是自动化先决条件，在人类查看之前就会触发：

- 签署（CLA或DCO）
- 外部编写的拉取请求的CI权限

没有签署就不会合并，因为记录的许可证来源是项目对代码来源的唯一记录。

按每分钟审查者时间解决的拒绝数对三个门禁进行排序——不是最便宜的第一，这会埋葬方向问题在机械装置下：

- 效率：方向检查（"这个属于项目吗"）> 基于大小的风险标签 > 代码正确性审查
- 努力程度：方向检查（在标题、描述和链接问题上花一分钟）> 基于大小的风险标签（从差异计算，但它只排序）> 代码正确性审查（这是这个顺序存在的昂贵通行证以保护）
- 价值：代码正确性审查（唯一可以接受更改的门禁）> 方向检查（解决从未关于代码的拒绝）> 基于大小的风险标签（路由；不做决定）
- 合规成本：方向检查 == 大小标签（绑定：一个维护者阅读描述和一个机器人测量差异都让项目欠债）> 代码正确性审查（接受更改使项目对其来源和安全态势负责，这是签署文件的内容）

方向检查领先，因为大约三分之二的被拒绝的代理拉取请求根本不需要阅读代码——MSR 2026采矿研究的353个手动检查拒绝的分解在[./references/published-findings.md](./references/published-findings.md)中。

效率会消耗代码正确性审查：最高价值，最高努力，永久最后。当受信任的重复贡献者发送一个小更改时，推广它为第一个——方向问题在PR打开之前得到回答，运行顺序的成本大于阅读。

每项任务的决策路径、带有弱/强对的回复模板、PR差异和拒绝知识库在[./references/response-playbook.md](./references/response-playbook.md)中。

## 第7步 - 编写关闭和陈旧政策

明确决定哪些事项会自动关闭，哪些不会。可辩护的界限：仅自动关闭等待报告者但已停止回复的事项；绝不自动关闭等待维护者的事项——由机器人关闭的确认错误会告诉报告者他们的证据毫无价值。

配置清理流程：

- 仅限制在等待报告者状态
- 免除确认和阻止状态
- 关闭前发出警告
- 以干运行模式运行第一次遍历，以便在启动前知道影响范围

每次关闭都附带原因，并说明如何重新打开。

将每个时钟锚定到命名的等待方，而不是抽象中的事项。Kubernetes发布的时钟、清理配置以及一次性积压破产何时合法：[./references/policy-and-metrics.md](./references/policy-and-metrics.md)。

## 第 8 步 - 自动化分类，永不自动第一回复

首先确定性地自动化机械层：

- 从更改路径填充区域标签
- 从表单应用类型
- 请求所属团队进行审查
- 运行陈旧时钟

每个记录的机器学习分派部署都保留人为最终决策者：将模型辅助视为评分和建议层，永不作为自主接受、拒绝或关闭。

在考虑任何分类器之前，复制两个模式：

- **自动化值班人员，而非决定内容。** Mozilla 将 triage-owner 字段同步到轮值日历上的人，以便请求到达实际工作的人员，而不是堆积在一个名字上。
- **将标签集作为验证的工件保留**，以便自动化不能发明标签或覆盖人工工作——`label-taxonomy.md` 中的机制。

将第一句人类话语留给人类。响应指标按定义排除机器人回复，报告者同样这样处理；一个自动问候后三周的沉默使等待更糟。当代理发布分派评论时，在评论中披露。

## 第 9 步 - 发布，运行试点遍历，测量

发布政策：

- 将其写入存储库，紧邻贡献指南
- 从摄入表单中链接
- 在项目的自有频道中一次性宣布变更

用 15-20 个事项对用户运行一次真实的分派会话，并计时。这将产生步骤 2 拖后的每项事项的分钟数，并暴露设计中的错误——缺失状态、模糊标签、不适合的回复模板。从未执行一次的政策是草案。

每月对第一季度重新运行 `triage-baseline.py`，并针对三个起始目标进行迭代。这三个都是这项技能自我设定的基线，不是行业基准——一旦每个季度有数据，就用项目的实际测量趋势替换它们：

- 未分派事项占开放事项的比例低于 10%。
- 至少 90% 的事项满足发布的第一响应目标。
- 季度净流入量在零或以下。

迭代直到它们成立，或降低发布的承诺到一个成立的承诺。

永不单独阅读计数指标。CHAOSS 的指导将此类指标限制为“主要由人类驱动”的活动，在机器生成量的情况下，关闭率和关闭时间可以改善，而实际维护者负担会上升。将每个计数与人类驱动的信号配对：排除机器人和作者自我回复的第一响应，以及如果一个人离开，有多少人可以覆盖分派。

有持久内存时，存储持久决策：

- 容量数字
- 确认的响应目标
- 标签轴及其定义
- 路由到跟踪器外的类别
- 量级门控触发器
- 声明的超出范围请求

下一次审查是与这些进行差异比较。

## 交付物

按顺序生成这些五个工件，每个工件在使用户验证后才能进行下一个——永不全部在一个无声的遍历中：

1. **基线** - 第 1 步的数字、它们的单行阅读，以及每项事项与聚类比较的调用。
2. **分派政策** - 发布的文档：哪些属于跟踪器、响应目标、状态及其含义、何时事项关闭、谁分派、量级门控触发器。模板在 [./references/policy-and-metrics.md](./references/policy-and-metrics.md)。
3. **标签变更列表** - 创建、重命名、合并、删除，每个都有一个单句定义及其轴。
4. **摄入变更列表** - 添加或重写所需字段的表单、选择器路由条目、安全路径、启用的自动化，每个都应节省的分派分钟数。
5. **值班和网关设计** - 带有命名人员和轮班长度的轮值、升级规则、拉取请求网关顺序。

保持每个工件在项目的自有词汇中——真实的标签字符串、真实频道、真实维护者名称。

## 失败模式

每一行命名步骤尚未明确说明的失败；修复是整行。

| 失败                                                       | 修复                                                                  |
| ------------------------------------------------------------- | -------------------------------------------------------------------- |
| 理想目标 - "24 小时响应"来自两名志愿者  | 发布基线支持的数量                             |
| 沉睡的轮值 - 一个记录的轮值一年没有人运行 | 给它一个所有者和活性检查；如果它懈怠，大声退役它 |
| 优先级戏剧 - 一切都是 `priority/high`              | 两个或三个级别，由后果定义                          |
| 大爆炸迁移 - 新标签、旧表单、旧保存视图   | 一次性迁移标签、表单、视图和自动化              |
| 分派作为修复 - 一个会话花在调试一个事项         | 时间限制遍历；分派计划工作；它不是工作         |
| 未测量的重新设计 - 新流程，不知道是否有所帮助  | 每月重新运行基线                                          |
