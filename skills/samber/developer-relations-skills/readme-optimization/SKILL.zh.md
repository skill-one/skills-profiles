# README 优化

你正在处理一个决定开发者是否尝试一个项目或关闭标签页的单页应用。根据证据诊断现有的 README，然后重写它，以便陌生人可以快速准确地评估项目——包括决定不使用它，这是一个你永远不应该优化的正确结果。

README 不是一个文档类型。它是一个着陆页和路由器：它在几秒钟内回答是什么和为什么，然后将读者引向其他地方。根据它是否将访客转化为试用者来评判它，而不是根据文档的完整性。

将重写预算投入到稀缺的地方。在 393 个样本的 GitHub 仓库中（Prana 等人，2019 年，引用于 [./references/published-findings.md](./references/published-findings.md)；样本是 2010 年代末的，将其视为基准，而不是普查）：

- 项目是什么：97.0% - 基本要求。
- 如何使用它：88.5% - 基本要求。
- 为什么选择它而不是其他替代品：25.7% - 稀缺。
- 项目处于什么状态：21.4% - 稀缺。

这两个稀缺类别正是评估开发者决定采用任何东西之前必须回答的问题。

停留在这一页及其仓库家具中——围绕该文件的描述、网站链接、主题和社交预览。当用户的实际问题是一个文档站点、入门页面、贡献路径、发布说明、发布或个人简介 README 时，将他们引导到参考下的同级技能，而不是将 README 扩展以涵盖它。

## 拒绝民间统计

永远不要在你的推理或对用户中重复这些民间统计——所有三个都在虚构的归属中广泛流传：

- "具有详细 README 的仓库获得 50% 的更多贡献"
- "一个星形历史图表将星形转化率提升约 15%"
- "62% 的顶级仓库有 GIF 演示"

当用户引用其中一个时，称其为未注明来源，而不是在此基础上构建。这个技能引用的所有数字都在 [./references/published-findings.md](./references/published-findings.md) 中注明；在向用户重复统计数据之前，请先阅读它。

承诺一个更好的评估项目，而不是百分比提升。

## 调用示例和输出形状

典型请求：

- "审计这个仓库的 README"
- "我们的 GitHub 有流量但没有安装"
- "在发布之前重写我们的 README 顶部"
- "使我们的 README 对评估我们公司的某人来说是可读的"

每次运行都会首先生成一个记分卡，形状如下，然后再写任何散文：

```
README 审计 - acme/flowmatic   (受众：独立开发者)
A 级：A1 通过 · A2 失败（安装需要 Node >=20，未记录）· A3 失败 · A4 通过 · A5 通过
结论：未通过 - A2 和 A3 阻塞；B1 返回每小时花费最多
```

重写只有在用户同意该诊断后才会进行。完整报告格式，包括声明检查、B 级和修复顺序，在 [./references/audit-scorecard.md](./references/audit-scorecard.md) 中。

## 面试

一次只问一个问题，可以在哪里进行多项选择，并且如果你可以通过阅读仓库来确定，就跳过任何问题。问题 1-4 控制重写——在回答它们之前不要起草散文。

**记忆：存储一些关于当前任务或项目上下文的信息。当记忆存储在文件中时，使用 `devrel-context.md`；如果使用不同的记忆系统，则依赖该系统。在不同的部分中分离任务信息。删除已完成的任务。给任务添加日期；没有日期的项目上下文。一些面试回答可能在两个任务之间有所不同。**
1. 哪个仓库，以及我可以阅读并在其中运行命令吗？
2. 项目是什么：库或 SDK、CLI 工具、应用程序或服务、框架或平台，还是模板和学习资源？
3. 谁会看到这个页面：一个语言生态系统中的开发者、多语言开发者、平台或运维工程师，或非开发者评估者，如安全和采购？
4. 采用方式如何——一个独立开发者安装它并单独决定，还是一家公司采用它并由其他人批准许可证、安全态势和支持故事？两者都是有效答案，并且它会改变页面的中间部分。
5. 你希望更多什么样的结果：安装、贡献者、星标、招聘信号、企业对话，还是更少的重复性支持问题？
6. 诚实的项目状态是什么：实验性、积极维护、稳定且功能冻结，还是正在寻找维护者？
7. 阅读者已经了解哪些替代品？它们比你好在哪里？
8. 出于法律或政策原因必须出现什么——许可证条款、商标声明、出口或合规声明、雇主披露？
9. 是否有现有的品牌材料——一个标志、一个口号、一个在网站上使用的定位句——README 应该与之匹配？
10. README 是否也发布在其他地方：一个包注册页面、一个镜像、一个文档站点着陆页？每个渲染目标都有不同的规则。
11. 是否有一个日期必须在此之前完成——一个发布、一个会议、一个资金对话——或者页面只是过期？
12. 你希望在那之前获得一次性成功，还是一个持续产生效益的资产：一个定位句和页面形状，你可以在未来两年内重复使用？
13. 你的上限是什么——一个下午、一周的时间、允许你向客户请求一个标志、对治理或基金会承诺的意愿，你无法轻易撤销？

回答 11-13 会重新排序以下所有排序；在提出计划时，说明哪个答案移动了哪个修复。

- **硬日期（Q11）**——促进在小时内完成的修复，从本次通过中删除漏斗重构。
- **复合指令（Q12）**——促进差异化段落和重构，其单行语句会传播到注册页面、发布帖子以及每个展开的链接。
- **低上限（Q13）**——直接删除终端演示和Enterprise信号，而不是将它们列在列表的底部。

如果用户无法回答 7，将其视为一个发现，而不是一个障碍。一个无法说出其替代品的维护者通常没有一个能够区分的 README，而这是最有价值的修复内容。

## 第一步 - 声明受众，然后确认 README 是否是瓶颈

回答 4 决定了整个审计。企业评估者和独立开发者想要结构上不同的内容，优化一个会损害另一个：一个爱好者会从一堆合规徽章的墙边弹开，而一个采购阅读者会不信任一个没有安全或治理信号的页面。在记分卡顶部写下声明的受众，以便每个后续的判断都可以与它进行核对。

然后确认 README 是什么被破坏了。如果代码托管服务暴露了流量数据，请取过去两周的唯一访客和克隆。

- 良好流量，但克隆到访客的比例只有几个百分比：这是这个技能适用的情况——人们到达并带着未信心的离开。
- 最初访客很少：一个分布问题，不是一个散文问题——将用户引导到发布或分发工作，而不是重写一个几乎没人读的页面。

这个“几个百分比”的边界是一个工作启发式算法，而不是一个基准；在边缘数字上，请查看引用者，而不是进行裁决。

## 第二步 - 收集证据

永远不要从记忆中审计好的 README 看起来像什么。

1. 逐字阅读 README，并记下你个人在哪里感到困惑。你的第一阅读困惑是你最接近冷读者的东西。
2. 运行机械审计：`scripts/readme-audit.sh <repo-root>`。它报告：
   - 阴影副本
   - 截断风险
   - 标题树
   - 与 7 的中位数相比的节数量
   - 第一个可复制命令之前的字数
   - 徽章数量
   - 缺少替代文本
   - 仓库不友好的原始 HTML
   - 破坏的相对链接
   - 占位符文本
   - 缺少内容类别
3. 阅读围绕 README 的仓库：真实运行时要求的清单文件、许可证文件、最近的提交日期、开放问题数量，以及它引用的示例是否存在于磁盘上。
4. 如果你的环境可以浏览网页，请打开项目的包注册页面，并将其与代码托管渲染进行比较。相对链接和原始 HTML 经常在那里破坏，而且那个页面通常是流量更高的页面。
5. 如果你的环境有持久记忆，请重用为这个项目存储的定位语句、受众定义或竞争对手列表，而不是重新推导它。

可选地添加一个结构化 README 评分器和代码主机的社区标准检查表作为第二意见，将两者都视为卫生基线——参见 [./references/tooling-and-measurement.md](./references/tooling-and-measurement.md) 中的有效性上限。脚本报告事实，而不是判断：一个 25 个节的节数量是一个需要回答的问题，而不是一个裁决。

## 第三步 - 评估当前 README

工作通过 [./references/audit-scorecard.md](./references/audit-scorecard.md) 并产生上述形状的记分卡。

- A 级：五个阻塞检查——身份、安装确实运行、每个声明都可验证、诚实状态、可访问的许可证。
- B 级：八个评分检查，每个检查值 2 分。

将证据附加到每个检查上——行号、引用的句子或你运行的命令的终端输出。在重写任何东西之前，获得用户的同意：一个拒绝诊断的维护者会拒绝治疗，他们有时是正确的，因为从仓库中看不见的约束可以证明你评分为零的检查。

### 排序修复

按每个修复每小时返回的价值排序，而不是按它如何容易编写，也不是按它造成的损害——这三个排序不一致，所以声明所有它们并首先列出第三个：

- 努力度，最少优先：`状态行 == 徽章行 > 声明检查 > 安装路径 > 差异化段落 > 漏斗重构`
- 价值，最多优先：`安装路径 > 差异化段落 > 声明检查 > 状态行 > 漏斗重构 > 徽章行`
- 效率，先做：`状态行 > 安装路径 > 声明检查 > 差异化段落 > 徽章行 > 漏斗重构`

状态行和徽章行在努力程度上打成平手：每个都是对一块编辑的一个编辑，从维护者已经知道的内容开始，验证什么也不需要——没有命令运行，没有源阅读。它们在价值上分离，因为状态行只回答了 21.4% 的 README 回答的问题，而徽章行回答了 61% 的贡献者忽略的问题。

默认情况下，对前三项进行第一遍；一旦阻塞检查变绿，或者当冷读者在一个三个问题都没有触及的问题上回答错误时，再向下移动。

漏斗重构在每一轮中都输掉——一个星期与在小时内完成的修复相比——所以这个顺序低估了使页面起作用的唯一变化。当冷读者回答错误因为他们从未滚动到足够远时，或者当审计的原因是发布时，提升它，并说明你是在与比率对抗时提升它的。

排序是一个默认值，不是一个法律，并且它会随着执行者而变化。根据你已经知道的内容重新排序它：

- 一个能够用一句话说出其替代品的维护者几乎免费获得差异化段落，这使其排在安装路径之上。
- 一个没有安装命令的项目——规范、数据集、模板——删除该行，而不是永远将其评分为零。

删除修复 13 排除的每个修复，而不是将其列在最后。

## 第四步 - 验证每个声明与源

README 是关于代码库的一组声明，每个声明都是可验证的。代理和维护者一样都从记忆中知道 API 通常看起来像什么；读者无法区分一个经过验证的行和一个虚构的行，而你能够，因为你拥有仓库。

列出每个声明：

- 命令
- 标志
- 默认值
- 环境变量
- 配置键
- 端点
- 导出的符号
- 文件路径
- 版本要求
- 隐藏在动词中的行为断言，例如“自动重新连接”、“重试三次”、“不区分大小写”

通过阅读而不是回忆来验证每个声明与其自身的真实来源——参数解析器、定义站点、路由表、变更日志。在 README 中记录的标志但不在解析器中是一个幻觉，而不是一个错误。

然后运行安装路径本身，因为它捕获了最多的实际损害：

1. 从干净的状态开始——一个容器、一个新鲜虚拟环境、一个临时目录，无论你的环境支持什么。如果你无法执行命令，请明确说明，并要求用户运行序列并粘贴输出；永远不要在检查中标记通过。
2. 按照记录的方式精确执行文档的安装命令，然后执行第一个使用示例。
3. 记录每个差距：未记录的运行时版本、假设存在的系统包、必需的环境变量、与 README 不同的输出。
4. 将每个差距作为明确的先决条件或验证步骤折叠到 README 中，然后从干净的状态再次运行序列。

重复直到记录的路径从端到端运行没有任何未记录的步骤。任何性能数字、兼容性矩阵、扩展限制或“生产就绪”声明都需要仓库内的来源——一个基准脚本、一个 CI 矩阵、一个变更日志条目——或者它出来。当你无法验证某事时，将声明降级为你可以验证的内容，并说明哪部分未确认。

## 第五步 - 选择形状，然后逐节重写

从 [./references/readme-skeletons.md](./references/readme-skeletons.md) 中选择与读者正在做出的决定相匹配的骨架，而不是代码碰巧是什么。

- 库读者正在判断与现有代码库的匹配度。
- CLI 读者正在与已安装的工具进行比较。
- 框架读者正在做一个多年的赌注。

按每个部分让读者快速排除项目的顺序排序部分。这是 **认知漏斗**，由 Kira 在《README 的艺术》中命名：最宽和最排除信息首先，然后缩小到只有承诺的读者才能达到的细节。一个后果：非许可许可证应靠近顶部，因为它最快排除，隐藏它浪费了读者的时间。

在写作之前，明确地而不是伸手去第一个措辞，进行定位头脑风暴。草拟三个候选单行句，在不同的轴上：

- 机械上做什么
- 移除什么问题
- 允许你停止使用什么

将它们与每个权衡和你的建议一起呈现，并让用户选择。单行语句会传播到仓库描述、注册页面和每个展开的链接。

逐节草拟并得到同意后再继续；逐节批准会浮现出分歧，而此时修复仍然很便宜。对于每个部分：

1. 写最短的版本，完全回答它的问题。
2. 用读者可以检查的东西替换每个无法验证的声明（“简单”、“飞快”、“开发者友好”）——一个数字、依赖计数、支持平台列表、命名的权衡。
3. 链接读者可能不知道的术语。
4. 声明项目故意不做什么，以及何时使用其他东西。这是大多数 README 中最高信任的句子，它只占一行。
5. 将任何超出屏幕的内容移动到链接的文档中，并留下一个单行指针。重新定位溢出，永远不要删除它。

将社区健康内容排除在文件之外——贡献指南、行为准则、安全披露、支持政策。每个都属于自己的公认文件，代码托管服务在它重要的时候会显示它；内联它们只会增加读者做出决定之前的滚动距离。一个例外：许可证文件必须随仓库一起交付，所以组织级别的默认值是不够的。

在展示之前，请使用您首选的“人性化”技能处理完成的文本。复制那些看起来像是自动生成的文本会削弱页面其余部分建立的信誉，而开发者很容易就能发现这一点。

有关开篇行、差异部分、状态声明、徽章行、安装块和用法片段的正面和负面示例，请参阅 [./references/before-after-examples.md](./references/before-after-examples.md)。

## 第 6 步 - 将徽章与证据校准

徽章是 README 元素中唯一具有严格证据基础的：Trockman 等人研究了 294,941 个 npm 包（ICSE 2018）。使用该研究中的区分，而不是凭感觉。

- 保留**评估信号** - 由第三方检查支持的徽章，除非底层事物为真则无法通过：CI 状态、覆盖率、发布版本、依赖项新鲜度。
- 删除**传统信号** - 仅仅声明意图的徽章，例如“欢迎 PR”，而没有验证它们的。它们不传递任何信息。
- 限制行数。在已经流行的包中，过度使用徽章与流行度的下降相关，采用徽章并不能提高流行度——流行的项目只是更有可能拥有徽章。方向是来源；四个的限额是一个工作默认值，而不是一个已发布的数字，因此请根据读者问题说明每个幸存者的理由，而不是争论数字。
- 预期维护者会高估它们。该研究的附属小型调查发现，维护者比贡献者更频繁地将徽章视为质量指标，而大多数贡献者表示徽章对他们没有任何影响。当维护者反对删除行时，请引用来自 [./references/published-findings.md](./references/published-findings.md) 的数据。

## 第 7 步 - 修复仓库家具和渲染机制

这一步的预算中，有三件事竞争，而且不是接近：

- 效率，首先做：`家具 > 渲染机制 > 终端演示`

- **家具**几乎不需要努力，它为读者在打开仓库之前看到的唯一文本：描述、网站链接和主题是搜索列表携带的，而社交预览是在有人将链接粘贴到聊天中时展开的。
- **渲染机制**大约需要一个小时，它为那些永远不会看到代码宿主渲染的读者使页面工作——注册页面、终端、屏幕阅读器。
- **终端演示**制作良好需要一周时间，然后它成为一项持续的工作，每当输出变化时就会过时。

演示是这一顺序中被忽视的，对于 CLI 或视觉工具来说，输出本身就是产品，其中最高价值的元素在页面上。在这种情况下，将它在渲染机制之上提升，并从脚本中生成它，而不是手动录制它，以便重新渲染保持足够便宜，以保持作为持续工作的状态。对于没有可见输出的库，删除它——导入语句的演示一无所获——而不是让它作为范围后来再次出现。

修复家具，然后修复文件本身的渲染方式：

1. 为每个图像提供替代文本，并将任何指令、命令或与决策相关的信息从截图和动画演示中移出到文本中。读者在终端中遇到 README，在剥离 HTML 的注册页面上，以及通过屏幕阅读器——动画演示对三者都不可见。
2. 删除手写的目录——代码宿主从标题中生成大纲，手动复制会过时。
3. 确保相对链接从默认分支上的仓库根目录解析，并且页面在剥离原始 HTML 时仍然可以正确阅读。
4. 只保留一个渲染的 README。当宿主在根文件之前渲染 `.github/` 复本时，根复本是注册表和镜像发布的，因此这两个复本会无声地分化。
5. 在单体仓库中，将根 README 作为到每个包的 README 的路由器，而不是内联覆盖每个包。

当演示确实赢得其位置时，保持其简短、高对比度和在嵌入比例下可读，并将其放在标语之后。将其转换收益视为从业者共识，而不是衡量结果——没有研究定价它，这也是不默认让它优先于两个更便宜的行的另一个原因。

## 第 8 步 - 仅当受众要求时添加企业信任信号

仅在步骤 1 声明公司或采购受众时执行此步骤。

企业决策者优化的是防御性，而不是最佳技术匹配，因此可识别的第三方信号——基金会层级、审计、证明、知名采用者——优于新颖声明。已发表的评估清单将维护活动、许可证清晰度和安全态势置于展示质量之上；来源在 [./references/published-findings.md](./references/published-findings.md) 中。

有六种信号可用，它们在成本上跨越两个数量级：

- 努力程度，首先：`支持预期 == 发布节奏 > 安全策略 > 命名采用者 == 供应链证明 > 治理和维护深度 > 基金会关联`
- 价值，首先：`基金会关联 > 命名采用者 > 安全策略 > 治理和维护深度 > 供应链证明 > 发布节奏 == 支持预期`
- 合规成本：
  - 基金会关联要求商标或 IP 转让，并需要法律认可，你无法撤销
  - 命名采用者需要每个公司的市场认可，可撤销，但只能通过再次询问
  - 安全策略公开承诺响应窗口，然后你必须遵守
  - 剩下的三个不会触发审查，并且可以通过一次提交逆转
- 效率，首先：`支持预期 == 发布节奏 > 安全策略 > 命名采用者 > 治理和维护深度 > 供应链证明 > 基金会关联`

支持预期和发布节奏各占两次：每个都是一句声明已经为真的句子，不需要任何人的许可，并且不需要阅读提交日志之外的工作。命名采用者和供应链证明在努力程度上各约一周，但在效率上分离——证明说服了一个本来就要说好的工程师，而一个可识别的标志说服了签发的人。

默认为前三个，它们之间下午的时间可以清除大多数评估清单评分的内容。当交易正在进行中，并且有人问“还有谁在使用这个”时，转向命名采用者。

基金会关联是这一顺序中被忽视的：页面最强的信号，四分之一或更多的工作，因此它永远不会在比例上获胜，而一个由 README 驱动的计划永远不会达到它。当项目作为基础设施而不是依赖项被采用时，或者当基金会层级是你不断输掉的障碍时，提升它——然后将这个决定交给用户，因为它的可逆成本不是文档成本。

删除每个被 13 条规则排除的信号答案，而不是将其列为未来工作：没有法律意愿意味着没有基金会行，并且一个单人维护者会写一个诚实的支持预期，而不是一个空的治理标题。

## 第 9 步 - 重新评分并使用冷读者测试

重新运行评分卡。当所有五个阻止检查都通过，并且评分检查总计至少 16 中的 14 分时，README 通过——这是一个工作默认值，而不是一个已发布的标准，因此允许用户根据声明的理由将其移动，并在报告中记录该理由。

然后运行评分卡中定义的冷读者测试——五个问题，60 秒，五个正确答案通过——使用一个人如果用户能找到的话，否则使用没有仓库上下文的全新代理会话。每个错误答案都映射到一个特定的检查，因此失败会告诉你确切要修复什么。

如果你的环境具有持久内存，请存储商定的简短语句、受众定义、竞争对手列表和最终分数。兄弟工作——发布帖子、文档着陆页、会议摘要——应从此定位开始，而不是发明一个新的定位。

## 之后要跟踪的内容

README 上的归因很弱。记录启航日期，比较完整周期前后的完整周期，并标注混杂因素，而不是声称差异。四到六周后重新测量；较短的窗口是噪音。

- 效率，首先跟踪：`支持负载 > 转化率 > 贡献者转化`

- **支持负载**跟踪成本为零，并在几周内移动：计算每月“如何安装这个”和“这个做什么”的问题数量，并观察它们下降。
- **转化率**——克隆或下载除以唯一访客——需要从宿主的流量数据中组装大约一个小时，并且是可用的最真实的单一数字，但在完整周期通过之前或之后都不会有任何信息。
- **贡献者转化**是最慢和最混杂的；四分之一后阅读它。

完全从跟踪计划中删除星级，即使当答案 5 将其命名为目标：它们只会上升，因此该指标无法显示回归，并且报告成功，因为该变化使页面更糟。提供转化率。

如果克隆上升但贡献者数量没有上升，那么贡献路径是断裂的，而不是 README。测量表面及其注意事项：[./references/tooling-and-measurement.md](./references/tooling-and-measurement.md)。

## 常见的失败模式

**在诊断之前重写。** 修复文本并保留损坏的安装的重写什么都没修复。在审查模式下，除非被要求，否则不要重写。

**填充以看起来很严肃。** 所有 README 有一半都位于 5 到 12 个部分之间，中位数 7。对于单一目的项目，四部分的 README 是完整的；向 200 行实用工具添加架构和路线图部分使其看起来像被遗弃，而不是成熟。

**营销声音。** 没有证据的超级形容词对此受众来说读作噪音，并主动降低信任。每个声明都应该可验证或删除。

**只审计一个渲染目标。** 注册页面经常有更多的流量和不同的规则。只在单个宿主上工作的 README 对很大一部分读者来说是损坏的。

**编造状态。** 永远不要写“生产就绪”、“经过战斗测试”或你没有从用户那里得到的用户数。一个夸大的声明被提交历史的一瞥证伪，并且比诚实的“早期 Beta”失去更多信任。

**以最低价的修复为起点。** 徽章行是列表中最快的东西，几乎是最没有价值的。按修复顺序，而不是按你能首先完成的顺序呈现。
