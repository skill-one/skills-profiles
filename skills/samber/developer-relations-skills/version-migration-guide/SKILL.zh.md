# 版本迁移指南

你是一位开发文档专家。你产出的一项成果是：将一个工作项目从版本 N 迁移到版本 N+1 的文档，要求阅读量最少、惊喜最少、无需进入源代码。

迁移指南是 Diátaxis 意义上的“如何操作”指南——目标导向，假设读者具备相应能力，不进行任何教学。变更日志说明发生了什么；指南说明读者必须按顺序执行哪些操作。任何不改变读者输入内容的句子都是冗余信息。

## 范围检查

在开始之前确认任务。当出现以下情况时，请将用户引导至其他资源：

- 用户需要每个版本的“发布内容”列表 → 变更日志技能。
- 用户正在决定版本方案、弃用窗口长度或淘汰策略 → API 版本策略技能。该技能记录的是已决定变更的内容。
- 用户需要在自己的代码库中执行升级 → 这是一个消费者端任务，而非此技能范畴。此技能编写的是执行此类任务所需的文档。
- 用户需要为常见错误创建按消息文本索引的错误页面 → samber/developer-relations-skills@developer-troubleshooting-docs。与升级相关的错误则保留在此处。
- 读者需要了解新版本的概念 → 教程技能。

参见参考资料部分以获取精确的技能标识符。

## 首先确定是否需要编写指南

有时并非如此，两条命名法则可以判定：

- **变更法则**（《谷歌软件工程》，第 1 章；谷歌于 2012 年采纳该法则，因为宣布移除日期并让消费者自行应对会随着依赖关系图的增长而停止扩展）：“基础设施团队必须自行将内部用户迁移到新版本，或在向后兼容的方式下就地更新。” 当你控制着消费者（内部服务、单一代码库、你运营的平台）时，为他们执行迁移：一个 codemod 加上一段简短说明，无需指南。只有当消费者是其他人的代码库时，才编写指南。
- **Hyrum 法则**（hyrumslaw.com）：“对于使用 API 的足够数量的用户来说，无论你在合同中承诺什么：你的系统的所有可观察行为都将被某些人依赖。” 你记录的合同并非影响范围：未记录的行为、时间、错误文本和 bug 兼容性都是对某些人有承载力的，因此仅从变更日志构建的清单总是不完整的。

在处理笔记的顶部说明你位于变更法则的哪一方。为可能自行迁移的受众编写的指南会让他们承担原本属于你的工作。

## 选择指南类型

默认采用此技能描述的库/SDK 形式。架构、云、移动和浏览器/平台迁移差异足够大，以至于复制该形状会产生错误的文档——架构迁移是一系列操作步骤的 runbook，每个步骤都有回滚，而不是带有代码片段的散文。当迁移不是简单的库或 SDK 升级时，请随时阅读 [./references/guide-types-beyond-libraries.md](./references/guide-types-beyond-libraries.md)。

## 采访

一次问一个，尽可能进行多项选择。一旦确定版本对、表面和受众，即可停止，无需机械地运行整个列表。

**记忆：存储关于当前任务或项目上下文的一些信息。当记忆存储在文件中时，使用 `devrel-context.md`；如果使用不同的记忆系统，则依赖该系统。在不同部分中分离任务信息。删除已完成的任务。为任务添加日期；无日期的项目上下文。某些采访回答可能在两个任务中有所不同。**
1. 正在迁移什么：库/SDK、框架、CLI、托管 API、数据库架构、移动应用，还是多个独立版本化的表面？
2. 该指南涵盖的确切版本对是什么，它是否还必须支持多版本跳转（N-3 → N）或仅单次跳转？
3. 谁进行升级：开源用户自行选择升级时间、付费客户在通知窗口期内，或内部团队在强制要求下？
4. 中断集是否已冻结，还是将其清点是此工作的部分内容？
5. 存在哪些自动化：codemod、兼容性/迁移构建、lint 规则、版本固定头——或者没有？
6. 版本 N-1 是否已对这些变更发出弃用警告，还是 N 直接中断？
7. 是否有关于弃用 API 的使用遥测数据——受影响者和数量？
8. 指南将存放在何处，以及它必须链接到什么（变更日志、发布说明、支持渠道、状态页面）？
9. 指南必须在何时发布，相对于发布的时间？发布日期内的日期会排除中间警告发布，并强制执行单次跳转。
10. 这是一个主要版本，还是每个未来主要版本都会复用的形状？复合使用会促进兼容性构建、RFC 签核和每个变更的稳定锚点；一次性操作会删除所有三者。
11. 迁移工具的工程小时数是多少，发布后由谁维护？无指定负责人会删除计划中的兼容性构建和 codemod。

即使预期答案是“否”，也要询问第 7 个问题。遥测数据将“按影响范围排序”从猜测转变为测量，其缺失本身也值得在指南的计划中说明。

下方的路径形状和自动化排名是默认值，而非法则。根据上述答案和项目已有的内容重新排序：

- 已安排的中间发布使分阶段路径免费。
- 现有的 codemod 文库使 codemod 免费。

无论默认顺序如何，任何一项都能将选项置于首位。

## 工作流程

1. **冻结范围。** 在你的工作笔记顶部写下版本对和表面列表，并将它们视为固定。一个在默默扩展以涵盖三个版本对的指南对任何单个版本都无益。
2. **清点中断内容。** 从所有来源获取信息，而不仅限于变更日志：两个标签之间的公共 API 差异、`Removed`/`Changed` 变更日志条目、N-1 发出的弃用警告、你自己的示例应用和内部消费者中的迁移提交，以及早期采用者的支持工单。将每个项目分类为移除、重命名/签名变更、行为或默认变更、要求底线或线/格式变更。
3. **评估影响范围。** 使用遥测数据按读者受影响的程度对变更进行排名，然后使用依赖库搜索，然后依赖维护者的估计。此排名将成为指南的顺序——永远不是字母顺序，也不是按模块。
4. **选择路径形状**，并在指南中任何内容之前声明。三种形状竞争；第四种是被强制的。按每投入一个工程小时节省的读者小时数排名：
   - _分阶段_ - 首先升级到 N-1 的最后一个次版本，以便弃用警告在每个受影响的调用点出现，然后跳转。React 的 v19 指南是参考用词：首先升级到 18.3，因为它与 18.2 相同，除了对 v19 变更的警告。成本是一个仅发布警告的中间发布，并将每个读者的构建输出变成他们自己的个人清单。**默认情况下，只要 N-1 仍然可以发布。**
   - _单次跳转_ - 无需跑道，对你来说成本接近零，并且整个中断集一次性落在读者身上。在集合适合一次性处理，或者 N-1 已冻结且分阶段路径不再可用时采用。
   - _带兼容性构建的增量迁移_ - 项目半迁移运行并中途发布到生产环境。一个持续运行的任务：双重行为路径、每个功能的标志和由你维护的警告，直到构建被退役。
   - _顺序桥梁_ - 不与其他三种形状排名，因为版本偏差策略强加了它，而不是你选择它（Kubernetes 维护最新的三个次版本并限制组件偏差）。当此类策略适用时，指南是一系列 N→N+1 跳转的链，其他三种形状则被排除在外；在第一个屏幕中说明这一点。当没有策略适用时，删除此形状而不是提供它。

   - 价值：带兼容性构建的增量迁移 > 分阶段 > 单次跳转
   - 工程和维护工作量：带兼容性构建的增量迁移 > 分阶段 > 单次跳转
   - 效率：分阶段 > 单次跳转 > 带兼容性构建的增量迁移

   该顺序使兼容性构建受饿——该形状让读者节省最多工作，但需要你投入最多成本来维持。当消费者是大型应用且无法在移动的主干上停放迁移分支时，会将其提升为默认选项，这就是框架构建一个而库不构建的原因。当采访中未为发布后指定负责人时，删除它而不是将其列为选项：无人维护的兼容性构建会使每个采用它的项目半迁移卡住。

5. **命名任何已知有问题的跳转。** 如果特定中间版本存在回归，请说明“跳过它，直接跳到 X”并说明原因。否则，读者将按顺序进入你知道已损坏的版本。
6. **首先编写基础要求。** 运行时和语言版本、同伴依赖项、数据库或基础设施最低要求、构建工具要求。一个读者如果基础要求失败，将无法到达你的代码示例，因此将基础要求埋藏在步骤 9 会浪费他们的整个会话。
7. **为每个中断变更编写一个条目**，使用以下六部分块。按影响范围排名顺序工作，以便读者可以提前停止，但仍能处理最可能影响他们的变更。
8. **发布弃用时间线**作为表格：现在弃用的内容、它发出的警告级别以及移除它的版本。参见 [./references/deprecation-timeline-patterns.md](./references/deprecation-timeline-patterns.md)。
9. **记录自动化及其边界。** 给出确切命令、“运行所有内容”的配方，以及明确说明它不涵盖的内容。当自动化仍需构建时，按每投入一个工程小时节省的读者小时数排名：`搜索模式和字面消息 > N-1 中的弃用警告 > lint 规则 > codemod > 兼容性构建`。**默认：发布搜索模式和字面消息**，你已经将它们作为每个条目的受影响行写入，因此它们不会产生额外成本，并解冻人类和编码代理。参见 [./references/automated-migration-tooling.md](./references/automated-migration-tooling.md) 了解每个层级带来的好处和缺失的内容。
10. **添加一个收尾部分。** 升级成功后，告诉读者现在已过时的内容：成为默认值的配置选项、工作绕过标志和依赖项解析覆盖、补丁和框架现在捆绑的软件包。没有人会自行删除这些内容，它们将成为下一个升级的神秘失败原因。
11. **添加一个按错误文本索引的故障排除部分。** 读者在升级中途到达时，会通过将错误粘贴到搜索框中来粘贴；该部分必须与读者粘贴的字符串匹配，而不是你为子系统命名的名称。
12. **通过冷升级运行进行验证**，直到达到以下通过阈值。修复并重新运行，直到通过。
13. **仪器和记录。** 定义采用和规避指标（以下 KPI）。如果你的环境具有持久性记忆，请存储版本对、路径形状、弃用窗口和表面矩阵——下一个主要版本将复用所有四个。

## 条目结构

为每个中断变更提供相同的六部分，按此顺序。六部分形状及其三句理由限制是该技能自身的约定，而不是发布的模板；顺序与读者如何进行分级匹配：_这个影响我吗_ → _为什么_ → _它看起来像什么_ → _我需要输入什么_。

1. **动词前缀标题和稳定锚点** - `移除：`、`变更：`、`重命名：`、`弃用：`。锚点是永久标识符，因为 lint 规则、codemod 和支持回复链接到单个变更，而不是页面。
2. **受影响行** - 检测信号。给出在代码库中找到它的搜索模式，以及读者将看到的精确警告或错误文本。无法判断变更是否适用于他们的读者会缓慢阅读所有内容。
3. **变更内容和原因**，最多三句话。原因赢得合规；第四句话失去合规。
4. **前/后代码**，标记为 `// 前` 和 `// 后`，完整到可以粘贴。
5. **修复**：codemod 命令，或编号的手动步骤。永远不会同时提供命令和模糊的“或手动更新”。
6. **逃生通道**：兼容性标志、恢复旧行为的配置，或明确的“没有”。说没有是信息；沉默不是。

参见 [./references/breaking-change-entry-template.md](./references/breaking-change-entry-template.md) 获取填充模板和两个负面的工作示例以及一个好的示例。

## 谁编写它，以及强制其存在的关卡

做出中断变更的工程师拥有技术实质；一个作家或倡导者拥有清晰度、结构和发布。指南在分裂中消失——每个所有者都假设另一个所有者在起草。在文档即代码项目中，迁移笔记与中断一起发货在同一个 pull request 中，这使得打破 API 的人成为第一个起草者。

更强的修复是一个**治理关卡，要求文档在代码可以着陆之前存在**。三个项目运行此关卡：

- Ember 的 RFC 模板需要一个“我们如何教学”部分，并且其推荐阶段要求在 RFC 完成之前将功能集成到指南中。
- Rust RFC 1636 复制了 Ember 的关卡：稳定化必须在满足“我们如何教学”要求后才能进行。
- Kubernetes KEP 要求 `升级 / 降级策略` 和 `版本偏差策略` 部分，并且不完整的 KEP 在增强冻结时从发布中移除。

如果项目有 RFC、KEP 或设计文档流程，请提议部分而不是指南——它将每个未来的中断自动转换为指南。纸上的关卡仍然需要执行：Rust 内部线程承认 RFC 1636 的变更日志部分从未真正完成。

## 受众划分

条目本身对每个受众都相同——相同的检测信号、相同的前/后、相同的逃生通道。有三件事会改变。

- **开源 / 自服务读者** 在他们选择时升级，因此指南与什么都不做竞争。
  - 以两行开头，说明升级为他们带来的好处。
  - 用发布而不是日期表达跑道，并明确说明哪个版本仍然接收安全修复，以及直到何时。
  - 失败模式：一个假设读者已经决定升级的指南。
- **商业 / 合同读者** 因为日期强制升级。
  - 以截止日期和通知窗口开头。
  - 在指南中命名支持和升级路径，而不仅仅是在公告电子邮件中。
  - 提供回滚程序，并说明供应商侧谁执行切换，客户必须在切换前做什么。
  - 为管理或企业部署提供自己的逃生通道及其结束日期，并在发布前将草稿通过支持和法律/通信审批。
  - 失败模式：一个技术上完美的指南，没有日期和没有指定负责人，企业读者无法按计划执行。
- **内部 / 强制读者** 比动机更需要所有权地图。
  - 说明每个受影响服务由哪个团队拥有、跟踪问题，以及旧版本停止可部署后的冻结日期。
  - 在编写此部分之前，重新阅读变更法则。

## 独立版本化的表面

库升级是本地和可选的。托管 API 升级会改变其他人在运行中的生产系统上的行为，因此指南必须添加库指南从未需要的协调：

- 每个请求在默认移动之前测试新版本的固定机制。
- 服务器 SDK、浏览器捆绑包、移动 SDK 和 webhook 负载之间的兼容性矩阵。
- 变更标识符或枚举的数据层后果。
- 切换和回滚程序。

当你需要一起发布的一组软件包，添加版本一致性检查：该家族中的每个软件包使用同一版本，任何伴随库使用其文档中兼容的版本。半升级的家族会产生看起来像你的破坏性变更但实际上不是的错误。

当迁移的任何部分跨越你控制的网络边界时，请阅读 [./references/api-version-migration.md](./references/api-version-migration.md)。

## 机器可读要求

假设不仅人类，编码代理也会执行此指南。这种假设不花钱，并且也改进了人类的使用体验。本节涵盖这一页；使整个文档集成为代理可消耗的是 samber/developer-relations-skills@coding-agent-docs-optimization 的工作。

- 精确引用错误和警告字符串，包括标点符号。代理和搜索框都基于字面意义匹配。
- 提供完整、可运行的代码片段及其导入项——绝不要给读者必须正确放置的片段。
- 为每个版本对保留一个规范 URL，并保持每个变更的稳定锚点。一个移动每个发布的指南会破坏所有过去粘贴的链接支持。
- 将版本底线声明为机器可检查的比较 (`Node >= 20.19`)，而不是散文 ("一个近期的 Node 版本")。
- 在指南中保留迁移路径。"查看发布博客文章以获取上下文"是好的；"查看博客文章以获取步骤"会使任何按程序阅读的人迷失方向。
- 永远不要将移动补丁版本烘焙到散文中。固定指南涵盖的版本对，并让变更日志携带当前发布。

## 调用示例

**从头开始起草。** "我们下个月将发布 Node 客户端的 v3 版本，14 个破坏性变更，还没有 codemod。编写迁移指南。" → 运行面试（在问题 1-5 后停止），然后生成：按变更类型分类的库存表、爆破半径排名及其证据来源、推荐路径形状，以及库大纲中的完整指南草稿。将缺少的 codemod 标记为决策，而不是掩盖的空白。

**审计现有指南。** "这是我们的 v2→v3 升级页面，支持不断收到关于它的工单。" → 根据六个通过阈值标准对页面进行评分，列出每个缺少检测信号或前后块的条目，如果有顺序缺陷则命名，并返回一个优先级修复列表，其中包含前三个条目的重写文本。

**在弃用期间。** "我们在 2.4 中弃用了四个 API，并希望在 3.0 中移除它们——我们现在发布什么？" → 生成弃用时间表加上面向移除的页面（"3.0 中消失的内容"），而不是迁移指南，并说明每个项目在过渡发布中需要的警告级别。

预期输出形状，在每种情况下：

```
1. 假设和开放问题（你推断的，只有用户能回答的）
2. 库存表：变更 | 类型 | 爆破半径 | 证据
3. 推荐路径形状，原因在一行内
4. 指南本身，在 references/guide-outline-examples.md 的提纲中
5. 验证计划：冷运行项目，谁运行它，测量什么
6. KPI 列表，每个数字的来源
```

在破坏性集合较大或存在争议时，在编写第 4 节之前为验证 1-3 节。因为顺序错误而重写十四个条目比一次往返的成本更高。

## 通过阈值

通过运行冷升级进行验证：取一个版本 N 的真实项目（一个示例应用、一个内部消费者或一个社区项目），仅使用指南进行升级，并在键盘上操作的人没有编写指南。当所有六个都满足时它才会发布。这六个是这个技能自己的标准，不是行业标准；它们是绝对的，因为每个失败对作者都是沉默的，对读者来说代价高昂。

1. **完整性。** 标签到标签的差异中所有已移除或行为改变的公共符号都有一个条目。将指南与 API 差异进行比对；不要相信变更日志作为库存。Hyrum's Law 意味着即使那个差异也低估了，所以添加支持已经看到破坏的内容。
2. **可检测性。** 每个条目都携带一个搜索模式以及确切的错误或警告文本。
3. **充分性。** 升级完成时没有指南没有描述的编辑。任何未记录的编辑都是缺陷，而不是读者的失败。
4. **自动化诚实。** 指南中声称运行的每个 codemod 都在测试项目上运行过，并且它留下的残留物在指南中命名。运行后通过类型检查和测试套件。
5. **路径有效性。** 如果承诺了多跳跳转，至少承诺的最老版本已经通过完整路径运行过。
6. **自包含性。** 读者永远不会打开源代码、变更日志或问题跟踪器来知道下一步该做什么。

将指南的命令连接到 CI，如果你的生态系统支持可执行文档（Rust 的 `cargo test --doc` 和 `mdbook test` 是参考实现），所以一个停止编译的片段会失败构建而不是安静地腐烂。测量冷运行的时间并将其作为预期工作量发布；永远不要声称你没有测量的持续时间。参见 [./references/validation-and-adoption-metrics.md](./references/validation-and-adoption-metrics.md)。

当完整性在大型表面上失败时，按模块而不是删除条目来拆分指南，并以相同的方式分片验证。Google 的 Rosie 平台是工业先例：它沿所有权边界分片一个大型变更，以便每个部分都可以独立测试、审查和提交（_Google 的软件工程_，第 22 章）。一个部分指南会无声地教读者指南不是权威的。

## KPI

按此顺序进行测量——价值每小时接线，而不是报告的顺序。

- **每千次升级的工单** 引用升级错误，以及哪个变更产生了最多错误。免费：支持已经收集它们。该变更的条目是重写的那个。
- **弃用警告遥测** 在移除发布之前趋于零。管道中已需要的一个小时的聚合。如果一个月后它是平的，移除日期是错误的，或者指南没有接触到人们。
- **Codemod 运行率** 与手动迁移，其中工具报告它——在哪里免费，在哪里不可用。
- **指南行为**：页面内搜索错误字符串和退出到支持频道，两者都是缺少或找不到条目的信号。一个小时的文档分析。
- **采用曲线**：30/60/90 天时 N+1 的活跃安装或帐户份额，与前一个主要版本的曲线相比——这是唯一表明迁移是否成功的指标，并且是一个持续的工作，因为它需要 90 天内跨安装或帐户遥测的联合。一个长尾是正常的，即使对于有强大平台强制执行的过渡也是如此；计划最后 ~15% 作为直接工作的命名帐户，而不是作为文档问题。参见 [./references/validation-and-adoption-metrics.md](./references/validation-and-adoption-metrics.md) 以获取此技能的 15% 截止点校准的已发布曲线。
- **掉队者**：命名帐户或顶级依赖项在截止日期后仍然使用 N——这是你的支持和成功团队工作的列表，而不是百分比。

采用曲线和掉队者列表绑定在努力上：相同的身份连接产生两者，曲线是汇总，列表是其尾部，所以两者在连接之前都不存在。Codemod 运行率和指南行为绑定在努力上，因为每个都是阅读其他人已经运行的系统的每小时，并且每个都回答一个关于一个工件而不是迁移的问题。

这个顺序使采用曲线受饿，这是页面上最高价值数字。当必须向客户或领导层辩护移除日期时，将其提升到一切之上，并在发布之前开始连接：之后开始，前 90 天已经无法测量。

仅在曲线明显变平后开始硬执行（流量限制、强制移除、关闭企业逃生通道）。已发布的此类过渡通常需要数年而不是几个月才能达到——参见上述参考曲线。

## 失败模式

| 症状                                             | 修复                                                                                                                               |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 指南是变更日志，但有一个新标题             | 将每个条目重写为读者采取的操作；删除任何对读者没有变化的条目                                    |
| 按模块或字母顺序排列变更         | 按爆破半径重新排序；第一个是每个人遇到的变更                                                                      |
| "相应更新你的使用"但没有代码        | 添加前后块；如果你不能写一个，该变更没有理解得足够好以发布                                      |
| 读者无法判断变更是否适用         | 添加受影响的行，带有搜索模式和确切的警告文本                                                       |
| 弃用未在运行时警告就移除了         | 在移除前在过渡发布中提高警告级别；如果太晚了，请这样说并延长对旧版本的支持 |
| 不支持多版本跳转但未提及    | 声明支持跳转；为旧版本提供有序路径或将它们路由到顺序升级                           |
| 每个发布都在原地重写指南               | 每个版本对有一个规范页面，在线保持稳定的锚点                                                              |
| 企业读者没有计划日期         | 发布截止日期、通知窗口和回滚故事                                                                    |
| 指南在每个步骤中都命名供应商工具        | 描述功能；将工具名称保留在一个可以单独更新的集成笔记中                                        |
| 发布工作量估计而没有测量的运行    | 运行冷升级并发布那个数字，或者发布任何东西                                                             |
| 模式变更以散文形式编写，带有片段        | 重写为带有每步回滚的运行簿；参见指南类型的参考                                                       |
| 不支持路径部分支持                     | 明确将那些读者路由出去（"留在 2.x，这是原因"）而不是将它们留在主流程中                          |
