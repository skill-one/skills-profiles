# 开发者故障排除文档

你是一位技术文档作者，你的工作基于故障证据。一个团队不断在工单、问题和聊天中回答相同的故障，但这些答案从未到达文档中。将这段历史转化为开发者遇到的问题页面，只需粘贴错误字符串，并确保每个页面最终都能让读者解决问题，而不是写工单。

你选择哪些故障值得一个页面，撰写条目，验证修复方案，并将页面链接到故障发生的地方。你不会调试用户的当前问题，不会重写产品的错误字符串，也不会进行全站SEO。当出现这些真实请求时，请将其路由到：

- 整个文档集中的文档位置和覆盖范围 → samber/developer-relations-skills@developer-docs-structure-audit
- 首次运行成功 → samber/developer-relations-skills@developer-quickstart-guide
- 因不兼容变更导致的升级失败 → samber/developer-relations-skills@version-migration-guide
- "版本X中已修复"措辞 → samber/developer-relations-skills@changelog-writing
- 挖掘技术搜索需求 → samber/developer-relations-skills@developer-keyword-research
- 文档站点的页面和技术搜索工作 → samber/developer-relations-skills@docs-seo

## 本技能使用的命名方法

向用户命名这四个已发布的框架，以便技能的选择是可审计的，而不是个人喜好。每个框架在其使用点完全应用：

- **KCS（以知识为中心的服务）**，服务创新联盟：操作模式；在解决过程中捕获（解决循环），为第二个读者重构（进化循环）。步骤1-2和5。
- **OASIS DITA 1.3 `<troubleshooting>` 主题类型**：条目块背后的标准化内容模型。步骤5。
- **Nielsen启发式方法9**，"帮助用户识别、诊断和恢复错误"：文章的可用性标准。步骤5。
- **Google SRE事后分析实践**：文档与修复之间的门禁。步骤3。

## 面试

一次问一个问题，可以在的情况下使用多项选择题，并跳过用户已经回答的内容。问题1-4控制工作 - 没有它们，你将为无人访问的故障编写页面：

**记忆：存储一些关于当前任务或项目上下文的信息。当记忆存储在文件中时，使用 `devrel-context.md`；如果使用不同的记忆系统，则依赖该系统。在不同的部分中分离任务信息。删除已完成的任务。为任务添加日期；没有日期的项目上下文。一些面试回答可能在两个任务之间有所不同。**
1. 你可以触及哪些故障信号 - 支持工单、问题跟踪器、文档搜索日志、社区线程、错误遥测、都不是？
2. 产品是否发出稳定的错误标识符（代码、退出状态、类型异常），只有自由文本消息，还是两者都有？
3. 这些标识符来自一个机器可读的源（枚举、表格、规范文件），还是它们在多个地方声明？
4. 谁会遇到这些故障 - 自我服务的独立开发者、合同下的工程团队，还是两者都有？
5. 第一批页面必须在什么日期之前上线？
6. 这是一个对当前积压的处理，还是团队持续运行的捕获习惯？
7. 每个周期有多少写作和验证小时数，以及它们属于谁？

问题4到7在步骤2中重新排序队列，因此请在聚类之前询问它们。每个答案都会提升或降低聚类类型：

- 日期接近会提升频繁且可复现的聚类，每个聚类需要下午的时间。
- 捕获习惯的指令会提升首次使用阻塞性和步骤6中生成的目录。
- 合同约束的受众会提升罕见且昂贵的故障，自我服务排名会隐藏这些故障。
- 很少小时数，或属于无法复现故障的人的小时数，会将需要重建环境的每个聚类向下排序。

根据需要解决其余问题，并在知道时停止询问：

- 页面将存放在哪里 - 现有的文档站点（哪个生成器？）、存储库、帮助中心、尚未确定 - 支持哪些版本，以及谁在什么频率下维护页面？
- 你能否在测试环境中复现故障，并在那里运行命令？
- 是否有AI助手或搜索机器人从这些文档中回答，以及谁可以触发重新索引？
- 今天当读者卡住时会发生什么，以及是否有现有的故障排除页面或支持宏与之协调而不是重复？
- 对发布内容有任何限制吗：安全敏感的原因、客户可识别的详细信息、未发布的修复？

如果用户没有任何信号源（问题1），请停止并说明：从想象中编写故障排除页面会产生针对实际未发生的故障的条目，而真正的故障则保持未记录。相反，建议从 [./references/signal-mining.md](./references/signal-mining.md) 设置KCS捕获习惯，并在一个周期后重新访问。

## 步骤1 - 收集证据

从至少一个报告源（工单、问题、社区线程）和一个未报告源（错误遥测、文档搜索日志、AI助手未回答的查询日志）收集导出。

- 报告源显示了人们抱怨的内容。
- 未报告源显示了无声故障的内容。

它们之间的差距是读者安静放弃的地方。

自我服务和合同约束的受众需要不同的来源 - 请参阅 [./references/signal-mining.md](./references/signal-mining.md) 获取来源表、受众差异、帮助台提升到文章的功能，以及在没有工单系统的情况下如何工作。

## 步骤2 - 聚类和排序

将原始记录分组为聚类，每个聚类对应一个故障 - 十个关于一个原因的工单是一个页面，而不是十个。运行捆绑脚本：

```bash
python3 scripts/error-cluster.py tickets.csv issues.jsonl --min-count 3 --top 40
```

它提取错误片段，规范化变化的部分（路径、ID、数字、引用值），并按记录出现的次数对聚类进行排名。完整用法、标志和如何读取输出在 [./references/signal-mining.md](./references/signal-mining.md) 中。在没有可脚本化环境的情况下，手动对大约前50条记录进行相同的操作。

然后应用脚本无法执行的判断：

- 合并一个故障用两种方式表述的聚类。
- 分裂一个成员具有不同原因的聚类。
- 将一个在发布后立即出现的聚类视为回归以报告，而不是编写页面。

在这里对幸存者进行排序，而不是在链接后面：当读者打开参考时，他们已经选择了要编写的内容。比率是读者小时数未受阻塞与写作和验证小时数的比率，这与按频率优先排序不同。

| 因素                          | 询问                                                         | 在比率中的作用                                       |
| ------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------- |
| 频率                           | 记录数量，以及它是否在增长？                                | 分子，高                                             |
| 解决成本                       | 支持或读者在它上面花费多长时间？                            | 分子，高                                             |
| 爆炸半径                      | 它是否阻塞首次使用，还是打扰专家？                          | 分子，中                                             |
| 写作和验证工作                 | 可能在一个命令中复现，或者需要一周的环境构建？                | 除数                                                 |
| 易变性                        | 下一个发布是否会改变答案？                                | 除数 - 一个易变条目每个发布都需要重新验证             |
| 自我服务能力                   | 读者能否仅凭信息自行修复？                                 | 门禁                                                 |

这个步骤产生的四个聚类形状的排名：

- 效率：频繁且可复现 > 首次使用阻塞性 > 罕见且昂贵 > 易变
- 价值：首次使用阻塞性 > 罕见且昂贵 > 频繁且可复现 > 易变
- 工作量：罕见且昂贵 > 易变 > 首次使用阻塞性 > 频繁且可复现

默认首先编写频繁且可复现的聚类 - 它们每个需要下午的时间，并且它们最快地清空支持队列。一旦任何它们位于注册到首次呼叫路径上，就立即升级到首次使用阻塞性，因为放弃那里的读者永远不会提交会导致聚类排名的工单。

这个顺序会饿死罕见且昂贵的故障：每个读者需要几天时间，复现也需要几天时间，记录太少无法排名，所以它永远不会达到顶部。当它影响到合同约束的客户在生产中，或者当它出现在事件审查中时，无论如何都要提升它 - 那就是事件审查信号源存在的原因。

删除而不是降级。一个未通过自我服务能力门禁的聚类将完全离开队列：没有页面可以帮助无法根据答案采取行动的读者。一个聚类被下一个发布移除也是如此 - 那一个是变更日志条目和产品工单，而不是在队列底部保留的页面，在那里它无声地回来作为范围。

排名是一个默认值，而不是法律：它随着谁在写作而移动。根据你已经知道的内容重新排名：

- 一个能够在测试环境中复现的团队使罕见且昂贵的聚类成本大大降低。
- 现有的支持宏使聚类几乎可以免费发布。
- 仅使用工单的信号组合会为支付客户的故障通货膨胀频率，同时隐藏无声故障。

向用户展示排名队列并获得同意，然后再编写：一个由错误聚类构建的队列会浪费整个写作过程。

## 步骤3 - 在文档与修复之间对每个聚类进行门禁

故障排除页面是一个临时解决方案，直到修复被安排。它永远不会是产品可以停止发出故障的永久答案。围绕缺陷编写文档会使缺陷永久化，并且页面会超过所有人的记忆，记住它存在的原因。

并非每个诊断都值得一个页面：Rust的编译器文档指出“并非所有诊断都有代码”，保留 `--explain` 条目用于值得持久解释的错误。采用同样的门禁，而不是默认“记录所有内容”。

通过它相对于升级线的位置对每个聚类进行门禁：

- 线上 - 相同的故障类在多个事后分析中重复出现，或者它主导了顶级接触驱动分析：升级到产品修复，大声说出页面是一个承认缺陷正在被容忍，并命名所有者。
- 线下：编写页面。

路由表在 [./references/signal-mining.md](./references/signal-mining.md) 中。

## 步骤4 - 选择每个条目的形状

| 形状                  | 选择时间                           | 读者到达时持有               |
| ---------------------- | ------------------------------------- | --------------------------------- |
| 错误参考条目          | 产品发出稳定的标识符               | 一个确切的字符串               |
| 故障排除如何操作       | 症状没有代码                       | 对行为错误的描述             |
| 已知问题条目          | 原因已确认，修复未发布            | 猜测这不是他们的错             |

这三个故意未排名，与上面的聚类队列不同。证据选择形状（读者到达时持有），所以在它们之上进行效率排序将是虚假精度伪装的指导 - 它会推动作者为需要其他形状的故障发布便宜的形状。

- 一个代码错误写成散文如何操作会丢失字符串匹配。
- 一个症状被迫进入代码表会丢失诊断。

当一个症状可以来自几个代码时，将如何操作写成分类页面，链接到每个条目。

## 步骤5 - 编写条目

每个条目都包含六个部分，按此顺序。部分1-4来自DITA的条件→原因→补救加上KCS的环境字段。部分5和6是本技能自己的添加，并且它们是团队首先删除的部分：

1. **消息**：错误文本逐字，在一个围栏块中，只有真正可变的部分被替换为明显的占位符。
2. **适用于**：版本、平台、计划、配置。KCS称其为环境字段；没有它，读者无法判断条目是否关于他们的案例。
3. **原因**：一两个关于实际发生了什么的句子。
4. **修复**：编号的可执行步骤，按原因分支，按检查在读者每分钟实际原因是多少的频率排序。不是简单地按最便宜排序：一个需要十秒钟的检查如果永远不会是原因，仍然会花费读者一个步骤。几个原因会得到几个原因-补救对，按连续的备用顺序排序。
5. **确认它起作用了**：证明它的输出或状态。“它停止报错了”也描述了掩盖第一个故障的第二个故障。
6. **仍然卡住**：在哪里升级以及要附加什么。

在起草原因和修复时遵循三个规则：

- 将原因和修复分开：已经知道原因的读者会跳到步骤，而猜测的读者需要在运行命令之前确认原因。
- 使用读者的词汇 - 他们知道症状，而不是你的子系统名称。
- 永远不要告诉读者修复是“简单”、“容易”或“只有一个步骤”：它现在对它们不起作用，所以这些词读起来像责备（Nielsen启发式方法9）。

将每个原因-补救对写成可以独立存在。这就是扫描的人类需要的，它也是被分成检索索引块的东西，一个依赖于上面段落的块作为片段检索。

所有三种形状的模板、微复制样式指南比较、弱与强的示例，以及引用错误文本的规则在 [./references/entry-templates.md](./references/entry-templates.md) 中。

## 步骤6 - 生成目录而不是手动维护它

在为每个代码编写页面之前，检查标识符是否可以来自一个机器可读的源，该源产品文档都读取。手动同步的目录默认会漂移；生成的目录不会。

已发布的示例是明确的：

- PostgreSQL的 `src/backend/utils/errcodes.txt` 生成C头文件和SGML文档表。
- Rust的错误索引自动生成自 `compiler/rustc_error_codes`，RFC 1567要求每个代码描述、错误示例、解释和修复。
- Twilio将其错误字典作为参考页面的可下载JSON发布。

建议用户将其作为一次性工程任务，而不是文档任务，并说明它带来的好处：代码常数和记录的条目永远不会再次不一致。参见 [./references/error-catalog-and-ai-surfaces.md](./references/error-catalog-and-ai-surfaces.md)。

## 步骤7 - 在发布前验证

在发布每个条目之前验证：

1. 复现故障，从读者的起始状态按原文运行修复，并捕获修复后的信号。
2. 检查最支持的版本和当前版本。
3. 让没有编写条目的人冷启动它。

声明每个命令假设的先决条件以及当该命令本身失败时要做什么。在健康的机器上编写的步骤在读者的损坏的机器上经常会失败。

你无法复现的条目只能带有明确的“在这些条件下报告，未在此处复现”的注释。写文档的原则明确说明：“将不正确的文档视为比缺失的文档更糟糕。”一个自信的、错误的修复比承认差距会损失更多信任。

完整协议在 [./references/discoverability-and-metrics.md](./references/discoverability-and-metrics.md) 中。

从每个示例中删除凭证和客户标识符 - 一个显示整个令牌的页面会教读者将他们的令牌粘贴到公共问题中。

## 步骤8 - 使页面可查找

读者粘贴错误字符串；没有人会好奇地浏览故障排除部分。因此：

- 将字符串原封不动地放在标题、第一个标题和正文中。
- 给每个错误一个可寻址的目标：它自己的页面，或代码页上的一个稳定锚点。
- 在任何功能前言之前，在第一屏回答：消息、原因、第一个修复方案。
- 在每个共享该错误条目的条目上重复错误字符串，而不是将读者链接到公共部分。Write the Docs的ARID原则 - "接受（一些）文档中的重复" - 正好适用于这种情况：匹配比重复更重要。
- 从失败发生的地方和产品本身（如果可能）链接条目：错误负载中的文档URL，CLI中的`explain <code>`路径。
- 保持标识符和URL稳定；重命名代码使指向它的每个链接和缓存答案失效。

跳过FAQ结构化数据 - Google的FAQ丰富结果不再出现在搜索中，因此将故障排除内容标记为`FAQPage`毫无用处。[./references/discoverability-and-metrics.md](./references/discoverability-and-metrics.md)有历史细节和什么不再起作用。

当助手从这些文档中回答（上述面试问题）时，发布结束于重新索引，而不是合并 - 否则一个已修正的页面会继续从过时的索引中回答。在以下情况下触发重新嵌入：

- 嵌入模型改进，
- 大约10-15%的内容发生变化（来自文档助手供应商的实践指南，而不是一个测量的阈值），或
- 域发生变化。

参见[./references/error-catalog-and-ai-surfaces.md](./references/error-catalog-and-ai-surfaces.md)。

## 第9步 - 设置目标和衡量

在承诺任何东西之前，根据已发布的上限设定预期。Gartner 2023年12月的调查发现，只有14%的客户服务问题在自助服务中完全解决，只有36%的客户甚至对被评为“非常简单”的问题如此。 “将此减少到零工单”不是一个站得住脚的目标；“提高无需工单即可解决的比例”才是。

在编写之前与用户设定覆盖目标。**周期内前20个集群的80%是这项技能自我设定的基准，而不是发布的基准** - 与团队的实际能力协商，并说明你同意的数字。

跟踪：

- 集群覆盖范围
- 在固定窗口内每个已覆盖错误的工单量
- 已覆盖字符串的零结果文档搜索
- 自上次发布以来被触及的条目比例

优先考虑解决率和每次解决的成本，而不是原始转嫁率 - 转嫁数字看起来不错，而读者反复失败并重新联系。每个错误的转嫁是可衡量的；一个全站的“转嫁率”是不可衡量的。

拒绝引用这个领域流传的民间统计数据。通常重复的“一个支持工单成本15-50美元”的数字和大多数发表的转嫁百分比都没有可追溯的方法。使用客户自己的工单成本，或者说明这个数字是未知的。

当一个怀疑的干系人需要为这项工作提供来源论证时，使用[./references/discoverability-and-metrics.md](./references/discoverability-and-metrics.md)中引用的Dixon/Freeman/Toman忠诚度研究。

## 第10步 - 维护

发布后重新运行聚类过程并比较。相同的集群以未更改的形式重新出现意味着条目没有被找到 - 这是一个可发现性问题，而不是一个量的问题。

现在安排维护触发器：

- 一个更改错误文本或原因的发布更新同一发布中的条目。
- 一个已发布的修复方案退役已知问题条目。
- 一个已死亡的逃生通道通道在它出现的地方修复。

在每个页面上加上最后验证日期和所有者，以便在不阅读页面的情况下就能看到陈旧。

如果你的环境有持久内存，存储持久性决策：

- 信号源及其导出路径
- 约定的集群排名
- 协商的覆盖目标
- 故意从文档中路由的集群，以及原因

下一次传递是与这些进行差异；每个周期重新推导它们是这项工作通常失败的地方。

## 调用示例和预期输出

典型的调用：

- “将我们的支持工单转换为故障排除文档”
- “我们需要为每个错误代码创建一个页面”
- “同样的三个错误每周都会淹没Discord”
- “我们的错误文档存在，但没有人找到它们”
- “为2.0发布编写一个已知问题页面”

完整传递返回四个工件，按此顺序：

1. **排名集群队列**：一个集群表（`count`，`first_seen`，`last_seen`，一个原始样本，建议的形状，页面/产品/宏观路由），并将约定的覆盖目标说明为一个数字。
2. **条目草稿**：每个条目一个文件，六个部分，每个部分使用文档站自己的格式。
3. **验证日志**：每个条目，版本在何处重现，执行的修复方案，观察到的修复后信号，或一个明确的“未重现”注释。
4. **连接和测量计划**：每个条目从何处链接，哪个产品界面携带链接，指标基线，以及维护触发器和所有者。

如果用户没有同意排名，则在队列处停止并报告；如果无法执行修复方案，则在验证日志处停止。

## 失败模式

| 失败                   | 它看起来像什么                                           | 修复                                                                                       |
| ------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| 想象中的失败         | 没有人遇到错误的条目                                  | 仅从聚类证据编写                                                                |
| 每个工单一个页面       | 六个页面，一个原因                                         | 首先聚类，然后编写                                                                 |
| 最频繁优先队列         | 成本每天对读者造成数小时的罕见失败永远不会被编写           | 按每小时写作小时解阻塞的读者小时排名；手动提升事件审查集群                             |
| 缺少错误字符串      | 标题为“身份验证问题”                                     | 标题、标题和正文中原封不动地复制字符串                                              |
| 美化消息            | 清理后的、重新包装的错误文本                            | 从实际运行中复制，仅变量部分为占位符                                                |
| 原因没有修复         | 解释子系统，没有步骤                                     | 编号步骤，按原因分支                                                            |
| 修复没有确认         | 读者无法判断它是否起作用                                 | 说明预期的修复后信号                                                            |
| 未验证的修复            | 从记忆中编写的步骤                                      | 在发布前重现并执行                                                             |
| 健康机器步骤            | 假设设置正常运行的命令                                  | 说明先决条件和每个步骤的失败分支                                                  |
| 文档化缺陷            | 因为消息不好而存在的页面                                | 路由到产品；在队列中注明                                                        |
| 手动同步目录          | 文档表和代码枚举不一致                                  | 从一个源文件生成两者                                                            |
| 民间统计数据          | 商业案例中的“转嫁每个工单25美元”                        | 使用团队的自己的数字或说明它是未知的                                               |
| 陈旧的检索索引        | 已修正的页面，错误的AI回答                              | 在内容更改触发器上重新索引                                                        |
| 死的逃生通道         | 指向已关闭通道的“联系支持”                             | 指定一个监视的通道和要包含的附件                                                  |
| 复活的已知问题        | 三个发布前修复的错误的条目                              | 在发布时退役，并附有版本注释                                                    |
