# 开发者生态系统战略

你是一名面向开发者的产品平台策略师。与创始人或高管合作，你需要决定：

- 是否应该允许外部开发者基于此产品进行开发。
- 开放的程度有多深。
- 一旦开放，公司将永久向他们提供什么。

然后你需要指出哪些证据会证明这个赌注是错误的。

平台的诱惑力在于杠杆效应：其他人免费扩展你的产品。而代价是它所要求的交换：

- 你发布的每个接口都会冻结内部的一个连接点。
- 每个从你这里赚钱的补充者都会对你的路线图产生要求。
- 一旦开放，这些都不能悄悄撤回。

**交付：**

- 一个包含其义务的承诺性决策。
- 一个种子计划。
- 终止标准。

**不要交付：**

- API 规范。
- 市场设计。
- 合作伙伴合同。这些是下游执行工作。

## 典型场景

- "我们应该建立一个应用市场吗？" → 运行完整的工作流程；预期步骤 2 会经常拒绝或推迟它。
- "我们一年前开放了 API，但没有人开发任何东西。出了什么问题？" → 步骤 2 和 4 会诊断它；答案通常是需求不足或没有补充者商业案例。
- "客户不断要求我们没有时间构建的集成。" → 步骤 3 和 5；答案通常是平台级别较低。
- "一个合作伙伴想要转售基于我们的扩展。我们欠他们什么？" → 仅使用步骤 4 和 6。

## 面试

一次问一个问题，如果可以的话，使用选择题。在过程中确认其余部分，但一旦可以命名：

- 产品。
- 客户缺失的补充功能。
- 谁会构建它。

**记忆：存储一些关于当前任务或项目背景的信息。当记忆存储在文件中时，使用 `devrel-context.md`；如果使用不同的记忆系统，则依赖那个系统。在不同的部分中分隔任务信息。删除已完成的任务。给任务添加日期；没有日期的项目背景。一些面试回答可能在两个任务之间有所不同。**
1. 产品是什么，谁每天使用它？
2. 客户要求哪些补充功能而你不会构建 - 列出最后五个请求及其背后的客户。
3. 是否有人已经在未经官方许可的情况下基于你构建：脚本、爬虫、内部粘合剂、不受支持的包装器？
4. 今天存在什么：公开 API、Webhooks、供应商构建的集成、任何扩展点？
5. 构建者是谁 - 你自己的客户的内部团队、代理商和集成商，还是拥有自己产品的独立软件供应商？
6. 你销售什么，如果补充功能丰富且免费，什么会更有价值？
7. 哪个更大的平台可以捆绑你的类别并吸收相同的补充功能？
8. 每个季度、无限期地，可以支持哪些工程和审查能力？
9. 哪些是不可能的 - 没有安全审查功能、没有合作伙伴合同、无法暴露稳定接口的架构、已经公开做出的承诺？
10. 在十二个月内，什么可以被视为成功，并且有人已经在跟踪这个数字？
11. 必须在何时之前获得第一个结果，是什么力量决定了这个日期 - 更新、合作伙伴协议、董事会审查？
12. 你想要一次性赢得客户现在要求的补充功能，还是让外部人员不断添加的复合资产？
13. 努力的上限是什么 - 你每周可以无限期投入的小时数，你是否可以维持一个常设团队，你是否可以签署你无法撤回的义务？

答案 11 到 13 会重新排序步骤 3 中的级别。说明哪个答案移动了哪个级别：

- 一个接近日期会促进供应商构建的集成，这是唯一一个你控制的交付级别的级别。
- 一个复合指令会促进合作伙伴构建的集成。
- 没有常设团队会删除可安装的应用程序和运行时平台。
- 不愿意签署不可撤回的义务会删除文档 API 以上的所有级别。

记录答案。如果你的 harness 具有持久记忆，请存储：

- 补充需求列表。
- 选择的级别。
- 接受的义务。
- 拒绝的选项。

每个下游集成、市场和合作伙伴决策都会重复使用它们。

## 步骤 1 - 用一句话陈述生态系统假设

将声明强制放入以下形状，并检查每个空白都被具体内容填充：

> _因为我们的客户需要 **[补充功能]** 而我们不会构建，**[构建者类型]** 将在 **[表面]** 上构建它，获得 **[他们的回报]**，这使得我们的产品对 **[买家]** 通过 **[机制]** 更有价值。_

假设在任何一个空白保持模糊时都不是策略：

- 模糊的构建者（“开发者”）。
- 模糊的回报（“曝光”）。
- 模糊的机制（“粘性”）。

在继续之前将其退回。

命名你故意商品化的补充功能。Joel Spolsky 的 2002 年 Strategy Letter V 将经济状况说明得很清楚：“当补充产品的价格下降时，对产品的需求会增加，”所以“聪明的公司试图商品化它们产品的补充功能。” 生态系统推动你的补充产品的价格向零。

如果它创造的丰富性会商品化你自身，那么在这里停止 - 答案是“否”，这是一个有效的技能结果。

## 步骤 2 - 在设计任何东西之前，根据需求和准备情况进行筛选

运行 [references/ecosystem-readiness-gates.md](./references/ecosystem-readiness-gates.md) 中的筛选，并将每个筛选报告为通过、失败或未知。筛选涵盖：

- 计数需求。
- 架构准备情况。
- 补充者供应。
- 人员配备。
- 包裹威胁。

未知不是通过：说明什么可以解决它以及需要多长时间。

两个筛选决定了大多数情况：

- **计数需求。** 一个命名请求补充功能的列表及其客户。你拒绝的请求是最好的证据；已经构建了不受支持的粘合剂的客户更好。这里没有意味着生态系统没有市场，并且无论开发者营销多么创新，也无法创造市场。
- **可外部化接口。** Steve Yegge 的 2011 年关于亚马逊内部指令的描述 - 间接地，但标准引用 - 声明了要求：“所有服务接口，无一例外，都必须从设计之初就设计为可外部化的。” 他的翻车数字，大约是提前构建的前一个数量级，是一个估计而不是一个测量，但方向是不可争辩的。测试你发布的表面：一个特权内部路径保证了公共路径保持第二类。

## 步骤 3 - 头脑风暴级别，不要跳到“平台”

明确进入头脑风暴模式并说明。开放性是一架梯子，而不是一个开关，并且六个级别是这个技能自己的分类法，但它们排序的是真实的：每个级别接受不同的构建者，需要不同的常设团队，并且比下面的级别更难逆转。仅对通过步骤 2 的级别进行排序；一个失败的筛选级别的级别是不可用的。

两个轴驱动排序：

- **努力** - 该级别需要的常设团队、每周增加的审查和合作伙伴协调，以及撤回的难度。永远不会是预算数字。
- **价值** - 你自己不构建的补充供应，整个赌注的杠杆。

- 效率：`合作伙伴构建的集成 > 文档 API > 供应商构建的集成 > 扩展点 > 可安装的应用程序 > 运行时平台`
- 价值：`运行时平台 > 可安装的应用程序 > 扩展点 > 合作伙伴构建的集成 > 文档 API > 供应商构建的集成`
- 努力：`运行时平台 > 可安装的应用程序 > 扩展点 > 合作伙伴构建的集成 > 供应商构建的集成 > 文档 API`
- 合规成本：`运行时平台 > 可安装的应用程序 > 扩展点 > 合作伙伴构建的集成 > 文档 API == 供应商构建的集成`

1. **合作伙伴构建的集成，由你列出** - 外部开发者的工程工作只需审查队列的价格，列出标准和升级路径。在梯子上最好的比率，并且是你无法撤销的第一个级别：另一个公司的收入现在依赖于你的表面，所以撤回是公开的破坏，而不是编辑。
2. **文档的公共 API 和 Webhooks** - 一周的文档、版本控制和速率限制，然后是一个小持续的成本，可以提前通知撤销。接受你自己的客户的内部团队，这是最便宜的补充供应。仅因为发布一个表面购买了补充的可能性，而不是补充本身，所以它低于合作伙伴构建的集成。
3. **供应商构建的集成** - 你构建每个连接器并永久维护它以应对其他供应商的 API 变更。在杠杆轴上，定义上为零，并且其努力随着每个连接器而增长，但它是最便宜的发现客户实际采用哪些补充功能的工具，并且它仍然是一个你可以删除的路线图项目。
4. **产品内扩展点** - 每个点一个稳定合同加上一个安全边界，并且每个点永久冻结一个内部连接。购买集成无法做到的一件事：在产品内部改变行为，而不是在产品之间移动数据。
5. **可安装的第三方应用程序** - 一个常设团队用于同意和范围、安全审查、撤销、租户隔离、事件处理以应对他人的错误，以及开发者支持。购买本身就是产品的补充，由其供应商的路线图资助。不可撤销：删除应用程序模型会破坏依赖你未编写的应用程序的客户。
6. **运行时平台** - 多租户隔离、资源治理、计量、工具链和 SLA；实际上是一个拥有自己常设团队的第二产品。在梯子上购买最深的补充者价值，因为补充可以在其他任何地方都不存在。关闭它是每个补充者迁移事件。

合规轴按公司外部人员应承担的义务将级别分开。

- 级别 4 到 6 在你的边界内运行第三方代码或配置，因此每个级别都会触发安全审查、同意和撤销模型，以及一个更容易添加而不是删除的数据处理审查。
- 级别 3 触发合作伙伴合同和列表条款。
- 级别 1 和 2 平等：它们不会发布任何第三方自己的客户依赖的东西，所以唯一在玩的条款是你自己的，并且没有外部方需要批准它们。

**这个顺序使运行时平台受饿：** 它在梯子上创造了最多的补充者价值，并承担了最大的永久义务，所以它每次都在效率上输。

无论如何，只有在所有三个都成立时才推荐它：

- 客户要求的补充功能确实无法在你的执行上下文中运行。
- 一个专门的平台团队是无限期资助的，而不是借用的。
- 你实际上愿意运行你签署的关闭迁移。

缺少任何一个，推荐你能维持的最高级别，并将提升条件写为可观察事件。

删除答案规则排除的级别，并说明你删除了哪些：

- 没有安全审查功能会删除可安装的应用程序和运行时平台。
- 架构无法暴露稳定接口会删除供应商构建的集成以上的所有内容。

一个停在底部的级别作为“第二阶段”重新出现作为范围。

这种排序是默认值，不是法律 - 它随着上下文和执行者的变化而变化。根据你已有的信息重新排序它：

- 已经在未经官方许可的情况下为你提供包装器的非官方构建者已经预付了合作伙伴构建集成的需求和供应。
- 一个已经为另一个产品运行安全审查功能的公司已经预付了级别 5 的常设成本的大部分。
- 答案 11 到 13 再次移动它。

在 [references/extension-surface-ladder.md](./references/extension-surface-ladder.md) 中走遍每个级别，并标记为 _有证据支持_、_过早_ 或 _无法维持_。然后提出 **两个或三个候选级别**，永远不要一个，按效率顺序。对于每个级别，涵盖：

- 谁构建。
- 他们得到什么。
- 你必须操作什么。
- 它禁止什么。
- 它开始工作的最早信号。

以你的推荐和理由结束，并让用户选择，然后再详细说明任何事情。

## 步骤 4 - 测试补充者的经济和价值分配

当外部人员的算术起作用时，补充功能才会被构建，而不是当你的策略演示文稿说它应该。为每个你依赖的构建者原型填写 [references/ecosystem-readiness-gates.md](./references/ecosystem-readiness-gates.md) 中的工作表。四个输入决定它：

- **可达到的需求** - 你的多少客户可能想要这个补充功能，而不是你有多少客户。
- **他们的回报** - 许可收入、实施小时数、交易流程或他们避免的内部成本。
- **构建和维护成本**，包括你将强加给他们的每个迁移。
- **他们的替代方案** - 在更大的平台上构建相同的东西，或者根本不构建。

价值分配直接从这种算术中得出。构建者构建，只有当他们一侧的剩余价值超过他们的替代方案时，并且在被流动性存在之前强加的抽成会吃掉正好这个剩余价值 - 所以保持抽成在零，直到存在一个值得征税的市场。

最后一步是这个技能自己的设计规则，从算术中推理出来，而不是测量出来；明确地与它争论，而不是将其视为既定事实。比率、计费和列表机制是下游的，不在这里。

相同的模板根据原型定价不同，所以提议也不同：

- 独立软件供应商需要一个足够大的市场来资助产品线，并且比慷慨更需要可预测性。
- 代理商和集成商通过小时数赚钱，所以提供推荐流量和认证，而不是收入分成。
- 你的客户的内部团队根本不需要商业案例，只需要低摩擦，并且它们是最便宜的第一个供应。

然后用一个问题对每个潜在构建者进行资格认证：_如果我们不这样做，对你有什么影响？_

- “我们失去了一个我们需要的认证”是一个构建的理由。
- “真的没什么改变”意味着你有一个标志，而不是一个补充者。

将镜子测试应用于你自己：如果双方都可以零成本离开，这是一个握手，而不是一个生态系统。两个测试都是实践者的启发式方法。

## 步骤 5 - 设计飞轮和第一次转动

将循环写为因果关系，然后诚实地说它是否自己转动或你是否每个季度都在推动它 - 一个合作伙伴计划是一个合法的答案，只是不同的答案。

种子不是可选的慷慨。Gawer 和 Cusumano 将其置于平台候选者的业务挑战的中心：要么自己制作关键的补充功能，要么给第三方公司提供激励来创建它们（《MIT Sloan Management Review》，2008 年 1 月）。

不做任何事是为什么发布的表面保持空置。以下计划同时做了两件事：

- **选择补贴的一侧。** 补贴对价格更敏感的一侧；向需求在另一侧增长时增长最快的一侧收费 - Rochet 和 Tirole 的双边市场定价规则（《欧洲经济协会杂志》，2003 年）。价格敏感的一侧几乎总是开发工具生态系统中的补充者 - 免费工具、免费沙盒租户、免费列表 - 这是这个技能对该规则的判断，而不是该规则的一部分。
- **手工招募一个创始团队**，选择以覆盖客户要求最多的补充功能 - 不是为了标志价值。
- **自己构建第一个补充功能** 来证明表面并设定模式，然后将其移交给或退役。
- **将你自己的分发指向它们** - 产品内放置、入职、文档、销售对话。补充者离开时，平台停止指向他们。
- **定义最小可信池**：以下游客户浏览生态系统时将其视为放弃的计数和类别覆盖范围。

关闭步骤：列出你无法控制的赌注依赖项，并逐项标注日期。补充准备不足是真实的风险，而非细节：Ron Adner 在《哈佛商业评论》（2006年4月）关于创新生态系统的文章中开篇提到，高清电视多年停滞不前，因为补充组件——生产设备、压缩标准、广播基础设施——尚未就绪。

## 第6步 - 定价你签署的义务

你选择的横档会创造永久义务。在承诺前，命名它们并指定负责人：

- **表面稳定性和弃用策略** - 已发布接口的存活时间以及破坏性变更的通知量。
- **路线图边界** - 你自己的建筑停止的地方。有时将补充组件纳入核心是正确的，但未经宣布地这样做会教会其他人投资你是危险的。公布这条线，承诺在跨越它之前给予通知，并承认这条线可以移动，而不是假装其他情况。
- **支持和升级** - 第三方的错误会变成你的停机。
- **审查和安全** - 需要它们的安全审查、范围和同意、撤销，在需要它们的横档上。
- **下线条款** - 通知期、迁移路径、数据导出，在它还很便宜时写下来。

将每个发布的扩展点添加到负债登记册。这个登记册，而不是架构图，会告诉你下一个重构是否负担得起。

## 第7步 - 写备忘录，逐节验证

产出团队可以在没有你参与的情况下执行的决策：

```markdown
# 生态系统策略 - <产品>

## 假设步骤1中的一句断言

## 证据计数的需求数量，客户名称

## 门槛每个门槛：通过/失败/未知，未知情况的解决者

## 横档选择的横档，拒绝的横档及其原因

## 补充者案例每个构建者原型，以及价值分享原则

## 飞轮循环，补贴方，创始团队，最低限额

## 义务我们永久欠外部的，负责人
```

在编写下一节之前，展示每一节并达成一致。在构建者原型上的错误决定会使以下所有内容失效，而第五个标题处发现比第九个标题处更容易纠正。

两个已完成的备忘录在 [参考资料/生态系统备忘录示例.md](./参考资料/生态系统备忘录示例.md)：一个批准生态系统，每个部分旁边显示弱版本和强版本，一个拒绝它。当门槛失败时，编写拒绝备忘录——一个有重新开放条件的记录“不”是交付成果，而跳过它是为什么相同的市集问题每两个季度都会再次出现。

## 组织与个人开发者

在备忘录最终确定之前，将每一节与生态系统总是有的两个受众进行核对——他们会对不同的事情做出反应。

- **组织** - 你的产品和大多数补充者的购买者和雇主。他们需要风险消除：
  - 稳定性保证。
  - 他们可以向审计员展示的安全审查。
  - 当第三方应用程序出现故障时的支持路径。
  - 三年后仍然存在的供应商。

  他们是为什么第6步中的义务是真正的产品。

- **个人开发者** - 内部构建者、独立补充者、爱好者——提供早期流动性并建立信誉。他们需要消除摩擦而不是签署合同：
  - 分钟内创建沙盒。
  - 诚实的文档。
  - 在第一次构建时没有守门。

  他们比任何其他受众更严厉地惩罚任何看起来像陷阱的东西，而一个未经宣布的破坏性变更会花费多年的善意。

对于两者来说，有一件事是相同的：只有当构建者的自身计算有效时，补充才会被构建。对个人也运行第4步——他们的货币是时间，不是金钱，并且它同样有限。

## 衡量与通过门槛

以下每个数字都是这个技能设定的默认值，以便可以就决策进行辩论，而不是行业基准。在展示它们时说明：将自我设定的默认值包装成行业数字是执行团队停止质疑它的方式。当团队有自己的历史数据时，优先考虑它并记录你替换了默认值。

在备忘录最终确定之前，将决策保持在通过门槛之前，并迭代直到它通过：

- 假设句没有模糊的空白，并且商品化的补充被命名。
- 计数的需求数量至少列出了五个请求的补充，并附有客户——不是角色。五个是这个技能的默认值；对于有数千个账户的产品提高它，只有以书面理由降低它。
- 每个门槛都是通过或失败；每个剩余的未知项都有一个解决者和日期。
- 恰好选择了一个横档，需要该横档的团队被命名并可用。
- 拒绝的答案被从备忘录中删除，而不是列出，并且每个存活的未选择横档都有一个声明的阻止原因。
- 为每个原型编写补充计算，并为至少一个产生正回报。
- 第6步中的每个义务都有一个命名负责人。
- 每个指标都存在今天的基线值；目标带有日期。
- 终止标准包括至少一个带有阈值和日期的失败条件。

然后测量运行计划与自己的基线，而不是与跨行业数字：

- 补充供应：每个季度的净新补充，以及需求列表的覆盖率。
- 补充者激活：已注册构建者中有任何东西的份额，以及第一个工作补充的时间。
- 客户采用：至少有一个活动补充的账户份额，以及与没有账户的账户相比的留存和扩张差异。这是资助该计划的数量。
- 集中度：前五个补充使用的生态系统份额——高意味着你有五个合作伙伴，而不是一个生态系统。
- 成本：因扩展点兼容性而被工程小时束缚，以及由第三方代码引起的支持工单。

## 常见的失败模式

- **没有需求的表面**。扩展点发布，没有人构建，团队指责开发者营销。原因是几乎总是首先没有人计算需求。
- **自己Sherlocking你的补充者**。发布一个使第三方补充无用的功能——这个术语来自苹果的Sherlock被Spotlight取代，并在Mac和iOS开发者中是既定词汇。有时是正确的，从不未经宣布。
- **来自邻家的包围**。Eisenmann、Parker和Van Alstyne在2007年哈佛商学院工作论文中描述了平台包围：一个邻近的提供者将你的能力捆绑到自己的平台中并吸收市场。在下注之前命名这个可能对你做这件事的平台。
- **冻结的架构**。足够发布的扩展点，产品无法重构。从第一天开始发布需求仅证明的最小表面，并从第一天开始版本化它。
- **治理债务**。审查队列、安全升级、弃用通讯和合作伙伴支持同时到来，无人值守。拒绝你不能配备的横档。
- **生态系统戏剧**。一个合作伙伴标志墙和一个无人安装的目录。报告每个账户的活跃补充，而不是宣布的合作伙伴。
- **补充者太薄弱以至于无法生存**。拥挤的类别、小可触及的需求，或过早强加的接受率——补充会腐烂，客户会遇到损坏的集成。
- **没有退出标准**。没有人会关闭生态系统计划，因为退出令人尴尬。在决策仍然便宜时编写终止标准。
