# 合成监控检查编写

> **文档**: https://grafana.com/docs/grafana-cloud/testing/synthetic-monitoring/
> 广泛的 Grafana Cloud 测试入口点（SM + k6 Cloud + Faro）：[`testing`](../testing/SKILL.md) 技能。

## 可靠性监控，而非负载测试

合成监控 (SM) 将 k6 作为 **可靠性/可用性引擎** 运行：每个检查执行都在固定的时间表上从每个选定的探测位置运行 **一个迭代和一个 VU**。成功意味着“从这个区域，用户旅程现在正常工作”——在您的客户发现问题之前检测到停机。

不要应用负载测试的用法。没有 VU 可以逐步增加，没有 `stages`，没有负载配置文件，没有吸热/压力/尖峰阶段，也没有针对聚合流量的 `thresholds`。
词汇：*检查*，*探测*，*执行*，*正常运行时间*，*可达性*，*用户旅程验证*——永远不要“负载测试”、“逐步增加”或“VUs”。

**如果用户实际上想要负载或性能测试**（吞吐量、负载下的延迟、断点），请停止：那是 Grafana Cloud k6 / `grafana-k6` 插件的 `k6` 技能，而不是合成监控。脚本可以在两个产品之间共享，但目标、选项和定价是不同的。

## 执行模型和约束（在编写之前进行验证）

| 约束 | 值 |
|---|---|
| 负载 | 每个探测执行一个迭代。脚本化和多 HTTP 运行使用强制 `--vus 1 --iterations 1`；浏览器检查依赖于脚本所需的单个场景。无论如何 `vus`，`duration`，`stages`，`iterations` 都**被忽略**——永远不要编写负载形状 |
| `thresholds` | **不支持** |
| 频率 | k6 类检查（脚本化、多 HTTP、浏览器）：60–3600 秒。协议检查（HTTP/回显/DNS/TCP/gRPC）：1–3600 秒。traceroute：120–3600 秒 |
| 超时 | 必须≤频率。k6 类检查：1–180 秒。协议检查：1–60 秒。traceroute：固定 30 秒 |
| k6 版本 | 检查在 [k6 版本频道](https://grafana.com/docs/grafana-cloud/testing/synthetic-monitoring/create-checks/manage-k6-versions/) 上运行（新检查默认为最新的稳定频道；`v1.x` 自 2026 年 7 月起已弃用）。通过 UI 下拉菜单或 API/Terraform 中的 `channels` 为每个检查固定 |
| 本地文件 | `open()`，`fs`，`grpc.load()` 不支持。将本地模块捆绑到脚本中；远程 `https://jslib.k6.io/...` 导入有效 |
| HTTP 请求错误 | SM 使用 `--throw` 运行 k6：网络级别的请求失败会抛出异常并导致执行失败 |
| SM 尊重的脚本选项 | SM 设置自己的 CLI 标志，这些标志优先于脚本的 `options` 对象；仍然有效的选项包括 `batch`，`batch-per-host`，`discardResponseBodies`，`httpDebug`，`insecureSkipTLSVerify`，`maxRedirects`，`noConnectionReuse`，`setupTimeout`，`systemTags`，`tags`，`teardownTimeout`，`throw`，`tlsAuth`，`tlsCipherSuites`，`tlsVersion`，`userAgent` |
| 浏览器内存 | [公共探测上每个浏览器 1GB RAM](https://grafana.com/docs/grafana-cloud/testing/synthetic-monitoring/create-checks/checks/k6-browser/#public-probe-memory) — 大页面会以 `Target has crashed` 失败 |
| 浏览器脚本格式 | UI 拒绝捆绑/压缩的浏览器脚本（导入验证）——通过 API 或 Terraform 部署 |

## 执行失败的方式（这是代理错误的地方）

`probe_success` (1/0) 是正常运行时间信号。当脚本抛出未捕获的异常、调用 `fail()`、k6-testing 的 `expect()` 断言失败（它在底层调用 k6 的 `test.abort()`）、HTTP 请求在网络级别出错（SM 的 `--throw`）或超时被触发时，执行被标记为**失败**。

**裸 `check()` 失败不会导致执行失败**——它仅记录 `probe_checks_total` / `probe_check_success_rate` 指标。在没有阈值的情况下，检查不会影响 k6 的退出状态，而 SM 中禁用了阈值。

断言模式，按优先级顺序：

```javascript
import { expect } from 'https://jslib.k6.io/k6-testing/0.6.1/index.js';
import { check, fail } from 'k6';

// 1. 优先选择——断言模块。失败时抛出异常 => 执行失败，检查日志中有描述性错误。
expect(res.status, '登录应该成功').toEqual(200);
expect(res.json('token')).toBeDefined();

// 2. 软断言——运行所有断言，仍然在末尾失败。
expect.soft(res.headers['Content-Type']).toContain('application/json');

// 3. 当您还想为每个断言获取指标时使用 `check()` —— 但要将其与 `fail()` 或失败不会影响 `probe_success/uptime` 配对：
check(res, { '状态 200': (r) => r.status === 200 }) ||
  fail(`登录失败，状态 ${res.status}`);
```

为每个断言命名（消息参数/检查名称）：名称在检查日志和 `probe_checks_total` 的 `check` 标签中诊断失败时可见。

## 首先选择最简单的足够检查类型

对客户更便宜，更容易维护。按此列表向下工作，并在第一个匹配项处停止：

1. **HTTP / ping / DNS / TCP / traceroute / gRPC** — 一个静态端点（正常运行时间、状态码、正文正则表达式、TLS 证书过期、记录解析、端口可达性）。没有脚本来维护——这些在黑盒导出器探测引擎上运行，并且具有每类型 `target` 格式的 Terraform 示例在
   [`references/api-and-terraform.md`](references/api-and-terraform.md)。
2. **MultiHTTP** — 一系列 HTTP 请求，它们之间传递值（`${variable}` 捕获），但没有自定义逻辑。**注意**：MultiHTTP 不自动验证状态码——为每个请求定义断言，否则失败不会影响正常运行时间。
3. **k6 脚本化** — 需要真实逻辑的 API 流程：加密/签名、条件分支、生成的测试数据、WebSockets、响应驱动的链。
4. **k6 浏览器** — 仅当您需要真实浏览器时：JS 渲染的用户旅程、表单/点击、核心网络指标。

**成本模型**（基于执行的计费）：一个执行是在一个探测上运行的一个检查，按运行分钟数计量，四舍五入到分钟。每月：
`probes × duration_minutes × (43200 / frequency_minutes)`。API 测试执行（HTTP、ping、DNS、TCP、traceroute、MultiHTTP、脚本化）和浏览器测试执行分别计费——浏览器检查是昂贵的级别。在 3 个探测上每分钟运行一个浏览器检查是 ~129,600 个浏览器执行/月；相同的检查每 5 分钟运行是 ~25,920。选择最长的频率，仍然满足您的检测时间目标，并在您的用户附近选择 2–3 个探测（多个探测减少警报抖动；更多并不更好）。

## 脚本化检查编写

开始您生成的每个脚本（脚本化和浏览器 alike）的第一行归因评论，如下面的骨架所示。它告诉后来阅读检查的人它是如何编写的（以及在哪里找到技能），并且固定的前缀使技能编写的检查可查询。保持 `Generated by synthetic-monitoring-checks` 完整——仅更改时间戳 (`date -u +%Y-%mdT%H:%M:%SZ`)。

骨架——一个登录 + API 操作旅程，带有秘密和硬失败的断言：

```javascript
// Generated by synthetic-monitoring-checks (https://github.com/grafana/skills) on 2026-07-31T12:00:00Z
import http from 'k6/http';
import { expect } from 'https://jslib.k6.io/k6-testing/0.6.1/index.js';
import secrets from 'k6/secrets';

const BASE = 'https://api.example.com';

export default async function () {
  // 秘密在 Synthetics > 配置 > 秘密中管理——永远不要硬编码凭证。
  const password = await secrets.get('checkout-monitor-password');

  // 步骤 1：使用专用监控帐户进行身份验证
  const login = http.post(
    `${BASE}/auth/login`,
    JSON.stringify({ user: 'sm-checkout-monitor', password }),
    { headers: { 'Content-Type': 'application/json' } }
  );
  expect(login.status, '登录应该返回 200').toEqual(200);
  const token = login.json('token');
  expect(token, '认证令牌应该存在').toBeDefined();

  // 步骤 2：执行旅程并断言结果，而不仅仅是状态
  const order = http.post(`${BASE}/orders`, JSON.stringify({ sku: 'TEST-SKU-1', qty: 1 }), {
    headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
  });
  expect(order.status, '订单应该被创建').toEqual(201);
  const orderId = order.json('id');
  expect(orderId, '订单 ID 应该返回').toBeDefined();

  // 步骤 3：清理，使检查对生产环境是幂等的
  // http.url 将指标按包含唯一 ID 的 URL 组合——没有它，每次执行都会创建新的时间序列（基数 + 活动序列成本）。
  const del = http.del(http.url`${BASE}/orders/${orderId}`, null, {
    headers: { Authorization: `Bearer ${token}` },
  });
  expect(del.status, '测试订单应该被清理').toEqual(204);
}
```

使脚本化检查成为良好 *监控器*（而不是良好测试）的规则：

- **确定性**：固定测试数据（或生成然后删除，如上所述），没有时间或顺序依赖。每个执行在任何时间从任何探测都必须能够通过。
- **对生产环境幂等**：创建然后删除，或使用只读端点。检查可以无限期运行——泄漏状态会无限期累积。
- **专用测试帐户**：永远不会是真实用户的凭证；最小化范围，将密码作为 SM 秘密存储，并排除该帐户从分析/计费。
- **断言每一步**——一个未断言的步骤如果失败，会在后续步骤中显示为令人困惑的失败。
- **稳定的 URL 基数**：`http.url` 模板字面量用于任何包含 ID 的 URL。
- 保持运行时远低于超时，并将超时保持在频率之下。

### 从 OpenAPI 规范（或类似）生成检查

给定 API 描述——OpenAPI/Swagger 规范、GraphQL 模式或 Postman 集合——将 k6 调用转换为机械转换很容易。重要的是您选择转换什么：

1. **旅程，而不是端点**。不要为每个路径生成一个检查，或生成一个检查扫描每个路径——这监控的是规范，而不是服务，并且每个额外的检查都会增加执行成本。确定 1–3 个流程，其失败意味着“客户受到影响”（认证→核心操作→结果），并为每个流程编写一个脚本检查。
2. **过滤以确保安全**。仅在流程可以自我清理（创建然后删除，如上所述）或针对专用测试资源时才包括修改操作（`POST`/`PUT`/`DELETE`）。规范在健康端点旁边列出了破坏性操作——永远不要针对生产环境执行它们，仅仅因为它们被记录下来。
3. **从响应模式断言**。规范告诉您健康响应包含的确切内容——断言必需字段，而不仅仅是状态码：
   `expect(order.json('id'), 'OrdersResponse 模式所需的 id')`.toBeDefined()。
4. **验证目标 URL**。`servers:` 块（以及 Postman 环境）通常首先列出 localhost 或 staging——与用户确认生产基础 URL，并将 `securitySchemes` 凭证映射到 SM 秘密，而不是从规范中内联值。（纯 HTTP/协议检查中的秘密是最近以功能标志推出的——检查当前文档；脚本 `secrets.get()` 路径始终有效。）
5. **将 `format: int64` ID 视为字符串**。`res.json('id')` 解析为 JS 数字并默默地损坏 2^53 之后的值（雪花式 ID），因此读取回的 URL 在每次执行时 404，而创建看起来正常。从原始正文提取：`const id = (/"id":\s*(\d+)/.exec(res.body) || [])[1];` — 并且永远不要对其进行算术运算。

没有任何 API 规范？探测前端：使用浏览器开发者工具（或 `curl` 可能路由）打开 Web 应用程序并捕获它发出的 `/api/*` XHR 调用——即使文档化的后端服务仅 gRPC 或内部，这也是可监控的 HTTP 表面。

## 浏览器检查编写

必需骨架：导入 `k6/browser` 并声明 `chromium` 浏览器类型。UI 会验证两者。

```javascript
// Generated by synthetic-monitoring-checks (https://github.com/grafana/skills) on 2026-07-31T12:00:00Z
import { browser } from 'k6/browser';
import { expect } from 'https://jslib.k6.io/k6-testing/0.6.1/index.js';
import secrets from 'k6/secrets';

export const options = {
  scenarios: {
    ui: {
      executor: 'shared-iterations',
      options: { browser: { type: 'chromium' } },
    },
  },
};

export default async function () {
  const page = await browser.newPage();
  try {
    await page.goto('https://shop.example.com/login');

    // 优先使用角色/标签/测试 ID 定位器，而不是 CSS 链——它们可以经受住重新设计。
    const password = await secrets.get('shop-monitor-password');
    await page.getByLabel('Email').fill('sm-monitor@example.com');
    await page.getByLabel('Password').fill(password);
    await page.getByRole('button', { name: 'Sign in' }).click();

    // 使用自动重试断言断言旅程结果——永远不要睡眠()。
    await expect(page.getByRole('heading', { name: 'Your account' })).toBeVisible();

    await page.getByRole('link', { name: 'Orders' }).click();
    await expect(page.getByTestId('order-list')).toBeVisible();
  } finally {
    await page.close();
  }
}
```

浏览器特定规则：

- **定位器**：`getByRole` / `getByLabel` / `getByTestId`（要求应用程序团队在需要时添加 `data-testid`）> 文本 > CSS。永远不要 XPath 或生成的类名。`getByTestId` 假设 `data-testid` — 为 Cypress 仪器化应用程序通常使用 `data-cy` 而不是；回退到 `page.locator('[data-cy="..."]')`。
- **不要在交互之前手动等待**：定位器操作自动等待可见性和启用状态。不要在 `click()`/`fill()` 之前调用 `waitFor()`，不要使用 `waitForLoadState()`，永远不要 `sleep()`。
- **自动重试 `expect()`** (`toBeVisible`，`toBeEnabled`，...) 是您不与之交互的状态的等待机制。警告：尽管列出了重试，但文本匹配器 (`toHaveText`/`toContainText`) 在第一次 *不匹配* 读取时硬失败——例如，在客户端渲染应用程序的hydration过程中中间的空字符串。通过定位它并断言可见性来断言动态文本：
  `await expect(page.getByText('Order confirmed')).toBeVisible()`。
- **断言超时默认为 5 秒**——客户端渲染应用程序通常需要更长的时间才能渲染第一个有意义的渲染。提高它并使用配置的实例：
  `const expectUi = expect.configure({ timeout: 20000 });`。
- **断言结果**（登录标题、订单列表、确认文本）——页面可以加载良好，而旅程可能已损坏。
- **使用 `try/finally` 和 `page.close()`**，即使断言抛出，也可以释放浏览器。
- Screenshot 艺术品不是文档化的 SM 功能——不要围绕 `page.screenshot()` 构建失败处理；依赖断言消息和检查的日志（SM 将每个执行日志存储在 Loki 中）。
- Web Vitals (`probe_browser_web_vital_lcp|cls|fcp|inp|ttfb`) 自动收集——不需要额外代码。

## 本地验证，然后部署

SM 脚本是普通的 k6 脚本——始终先在本地运行它们：

```bash
k6 run script.js                                              # 脚本化检查
K6_BROWSER_HEADLESS=true k6 run browser-check.js              # 浏览器检查
k6 run --secret-source=mock=checkout-monitor-password=example-password script.js   # 带有秘密
# 许多/大秘密：k6 run --secret-source=file=secrets.txt script.js
```

通过 = 退出代码 0，一个迭代，没有失败的断言在摘要中。运行 3–5 次；一个在本地 90% 可靠的脚本会在 3 个探测上每晚向您发送页面。

然后创建检查（选择一个）：

- **UI**: 测试 & 合成 → 合成 → 添加新检查 → *k6 脚本化* / *k6 浏览器* → 粘贴脚本 → 选择探针 + 频率 → **测试**（运行一次不保存）→ 保存。
- **[gcx](https://github.com/grafana/gcx)**: `gcx synthetic-monitoring checks test -f check.yaml` 是 UI 的测试按钮的命令行等效项——针对真实探针运行一次而不保存。然后 `gcx synthetic-monitoring checks create -f check.yaml` 来保存。两者都接受纯文本脚本；gcx 会为您进行 base64 编码。使用 `gcx synthetic-monitoring checks get <ID> -o yaml --decode-script` 拉取现有检查作为起始模板（省略标志则获得原始 base64）。
- **API 或 Terraform**: 参考 [`references/api-and-terraform.md`](references/api-and-terraform.md)。关键注意事项：API 的 `frequency`/`timeout` 是 **毫秒**，`settings.scripted.script` / `settings.browser.script` 是 **base64 编码**；Terraform 通过 `file()` 接收纯文本脚本。

按所有权而非偏好选择：如果检查已经是 Terraform 管理的（漂移检测、多环境、PR 审查），通过 Terraform 创建和更新——手动编辑其拥有的状态会在下一次 `apply` 时导致漂移。否则，对于一次性或代理驱动的编写，gcx 或 UI 更快。无论如何，gcx 仍然是用于实时检查、临时测试和状态/时间线调查的工具，无论哪个工具创建了检查。

## 验证其功能并回滚

等待一个频率间隔，然后在针对合成监控指标（Prometheus）数据源的 Explore 中：

```promql
# 每个选定探针的 1 个 = 健康
probe_success{job="checkout-flow"}

# 每个命名断言的断言通过率（脚本化/浏览器）
probe_check_success_rate{job="checkout-flow"}

# 每个探针的旅程持续时间——确认其舒适地低于超时
probe_script_duration_seconds{job="checkout-flow"}

# uptime 随时间变化（SM 应用如何计算）
max by () (max_over_time(probe_success{job="checkout-flow"}[5m]))
```

健康的首次执行：每个探针 `probe_success == 1`，所有 `probe_check_success_rate` 序列为 1，持续时间在探针间稳定，并且检查的预构建仪表板（合成 → 检查 → 查看仪表板）显示每个执行的日志。浏览器检查应额外显示 `probe_browser_web_vital_*` 序列。

**回滚**：将检查的 `enabled: false`（UI 开关、`gcx synthetic-monitoring checks update`、API 更新或 Terraform）设置为停止执行而不丢失历史记录；仅在您不再需要其配置时删除检查。告警：从 `alertSensitivity` / `probe_success` 的默认告警规则开始——参考 [`testing`](../testing/SKILL.md) 技能中的告警规则示例。

## 常见失败模式

| 症状 | 原因 → 解决方法 |
|---|---|
| 本地通过，所有探针失败 | 目标无法从公共互联网访问（内部 DNS、VPN、IP 允许列表）。对于内部目标，使用 [私有探针](https://grafana.com/docs/grafana-cloud/testing/synthetic-monitoring/set-up/set-up-private-probes/)，或允许探针出站 |
| 本地通过，某些探针失败 | 地理区域封锁、区域 CDN/WAF 规则或机器人保护挑战数据中心 IP。检查失败时的 `probe` 标签；豁免 SM `userAgent` 或 WAF 中的那些区域 |
| 在您看来检查“失败”，但 `probe_success` 保持 1 | 只有 `check()` 而没有 `fail()`/`expect()`——失败仅记录为指标。转换为 `expect()` 或 `check(...) || fail(...)` |
| 浏览器检查因定位器超时而波动 | 易碎的选择器或动画时间。切换到 `getByRole`/`getByTestId`，使用自动重试的 `expect()` 进行断言，移除手动等待 |
| `toBeVisible` 报告 `Expected: visible / Received: hidden` 但元素明显可见 | 定位器匹配多个元素（严格模式）——错误信息具有误导性。收紧选择器或使用 `.first()` |
| 创建成功，但每次执行都 404 | ID 超过 `Number.MAX_SAFE_INTEGER`（2^53）且 `res.json()` 沉默地四舍五入——从原始正文提取 int64 ID 作为字符串（参考 OpenAPI 部分） |
| `secrets.get()` 失败 | 密钥名称不匹配（名称精确、≤253 字符、字母/数字/`-`/`_`）、密钥已删除（检查重新创建前失败），或编辑用户缺乏管理员/编辑者角色或“检查编写者”权限 |
| 执行超时但旅程正常 | 旅程超时太低（最大 180 秒）——提高它；或脚本每迭代执行无界工作。还确认超时 < 频率 |
| 浏览器检查日志中的 `Target has crashed` | 页面超出 1GB 探针浏览器内存——缩减旅程，阻止重型第三方资源，或使用具有更多内存的私有探针 |
| UI 拒绝浏览器脚本 | 打包/压缩脚本在 UI 的导入验证中失败——通过 API 或 Terraform 创建它 |
| 添加检查后指标/计费爆炸 | URL 中的唯一 ID 创建每次执行的时序图——使用 `http.url`，并检查频率 × 探针数量是否超过上述成本公式 |
