# k6 趋势分析

分析 Grafana Cloud k6 测试多次运行中的指标趋势，以便及早发现性能下降——在阈值被突破并触发警报之前。P95 延迟为 380ms，阈值为 500ms，今天处于“绿色”状态，但如果一个月前是 250ms，则存在潜在的性能下降；这项技能能够揭示这种漂移并建议采取行动。

## 这项技能不做什么

- **深入分析单个运行失败**：加载 `k6-cloud-investigate-test`
- **编辑脚本或应用阈值变更**：加载 `k6-test-maintenance`
- **创建新的测试脚本**：使用适当的测试创建工作流
- **直接查询服务端指标**：当需要可观测性关联时，这项技能会转交给 `debug-with-grafana`

## 依赖项

这项技能将所有 GCk6 API 机制委托给 **`k6-manage`**。在执行任何 API 调用之前，请先阅读它——它涵盖了认证、路径构建（双重的 `cloud/cloud/` 前缀）、使用 `@nextLink` 的分页、溢出信封和指标查询语法。不要在这里重复这些知识。

使用的工具：**`gcx`**（通过 k6-manage 模式）。

## 工作流

按顺序执行以下步骤。在最后呈现结果——不要直接应用变更。

### 第 1 步：识别测试

用户提供以下其中一种：
- GCk6 URL（从路径中提取负载测试 ID）
- 直接提供测试 ID
- 测试名称（通过 `gcx k6 tests list` 或 v6 API 搜索）

通过获取其元数据来确认测试是否存在。记录 `id`、`name`、`project_id` 和 `created` 时间戳。您将需要负载测试 ID（而不是运行 ID）用于多运行指标端点。

### 第 2 步：确定分析窗口

默认为 **过去 30 天**。如果：
- 用户请求特定窗口
- 测试在 30 天内运行次数非常少（<5 次）——扩大窗口并记录这一点
- 测试运行非常频繁（30 天内数百次运行）——考虑采样或缩小。如果数量极端（>200 次），请询问用户

明确说明窗口：“分析 {start_date} 至 {end_date} 的运行。”

### 第 3 步：获取窗口内的运行

使用 v6 API 列出测试的所有运行，使用 `$orderby=created desc` 分页（参考 k6-manage 第 3 节的 `@nextLink` 循环模式）。过滤到分析窗口内的运行。

对于每个运行，记录：
- `id`、`created`、`ended`
- `result`（通过/失败/超时）
- `status`（创建/排队/初始化/运行/完成/中止）
- `note`（如果存在——用户有时会注释运行）

丢弃未达到 `finished` 状态的运行（中止、超时等），除非用户特别询问——不完整的运行会产生不可靠的指标聚合。

统计运行次数。如果可用运行少于 3 次，通知用户趋势分析在此样本量下没有意义，并建议扩大窗口或等待更多运行。

### 第 4 步：获取所有指标及其类型

在查询值之前，发现测试发出哪些指标。使用多运行指标列表端点（参考 k6-manage metrics.md 第 2 节）：

```
GET /cloud/v5/load_tests/{loadTestId}/metrics(test_run_ids=[{id1},{id2},...])
```

将一组有代表性的运行 ID（第一个和最后几个）传递给此端点，以捕获在窗口期间可能已添加或删除的指标。记录每个指标的 `name` 和 `type`（计数器、仪表、趋势、速率）。

按类型分组指标——查询方法必须与指标类型匹配（参考 metrics.md “查询方法”）。使用错误的方法将返回空结果。

### 第 5 步：获取每运行聚合值

对于每个指标，使用多运行聚合端点（参考 metrics.md 第 8 节）查询其在窗口内所有运行上的聚合值：

```
GET /cloud/v5/load_tests/{loadTestId}/query_aggregate_k6(
  query='<method>',
  metric='<metric_name>',
  test_run_ids=[{id1},{id2},...]
)
```

具体的 `gcx` 形式（通过 k6-manage §2 的代理前缀；`-o json` 避免溢出信封）：

```bash
LT=<load_test_id>; IDS="123,124,125"
gcx --context <ctx> api "/api/plugins/k6-app/resources/cloud/cloud/v5/load_tests/$LT/query_aggregate_k6(query='histogram_quantile(0.95)',metric='http_req_duration',test_run_ids=[$IDS])" -o json
```

根据指标类型选择聚合方法：

| 指标类型 | 主要方法 | 捕获的内容 |
|-------------|---------------|------------------|
| **趋势** | `histogram_quantile(0.95)` | P95 延迟——最常见的 SLO 目标 |
| **趋势** | `histogram_quantile(0.5)` | 中位数——显示典型行为 |
| **趋势** | `histogram_avg` | 均值——对异常值敏感 |
| **计数器** | `increase` | 每次运行的总计数 |
| **速率** | `ratio` | 成功/失败比率 |
| **仪表** | `max` | 每次运行的峰值值 |

对于趋势型指标（延迟），查询多个分位数（P50、P90、P95、P99），以查看性能下降是均匀的还是在尾部集中。

**始终按请求分组进行多目标测试的分解。** 整个测试的单一聚合 P95 会掩盖局限于单个端点或单个页面的回归——如果一个 URL 出现 3 倍的减速，如果测试访问许多 URL，则在测试级别的 P95 可能会看不到。默认为分组查询：

| 指标模式 | 默认分组 | 原因 |
|----------------|------------------|-----|
| `browser_web_vital_*` (LCP, FCP, CLS, TTFB, INP, FID) | `by (url)` | 每个导航都会发出自己的 Web 生命体征；按 URL 的趋势可以将回归定位到特定页面。 |
| `http_req_duration`, `http_req_failed`, `http_reqs` | `by (name, status)` 如果请求带有 `name`；否则 `by (url, status)` | 不同端点具有不同的基线；混合它们会隐藏每个端点的漂移。 |
| `iteration_duration` (多场景测试) | `by (scenario)` | 浏览器和协议场景的持续时间差异很大；混合它们没有意义。 |
| 带标签的自定义趋势 | `by (<the tag>)` | 用户标记的内容就是他们关心的内容。 |

首先通过标签端点（metrics.md §4）和标签值端点（metrics.md §5）发现可用标签，然后再构建分组查询。不要假设通过读取脚本获得的标签——标签重命名或重构可能会无声地改变标签空间。示例：

```
# 列出特定指标在代表性运行上的标签
GET /cloud/v5/test_runs/{id}/labels?match[]=browser_web_vital_lcp

# 然后枚举有用标签的值
GET /cloud/v5/test_runs/{id}/label/url/values
```

仅当分组不提供信息时才回退到无 `by` 的基本聚合——例如，`vus`、`load_generator_cpu_percent`、单目标测试中每个请求都访问相同 URL。

响应包括 `test_run_id` 作为标签——使用此标签将每个值映射回第 3 步中的运行时间戳。分组查询返回每个（分组，运行）组合的一个序列；展平为整洁的“rid x group”表格，用于第 7 步的趋势计算。

如果运行 ID 太多无法放入单个 URL（数百个），将查询批处理为 50 个运行 ID 的组，并合并结果。

### 第 6 步：提取阈值

阈值定义了“通过”的含义。获取测试的当前脚本（通过 k6-manage 第 5 节），并解析 `export const options = { thresholds: {...} }` 块。记录每个阈值的：
- 指标名称和选择器（例如，`http_req_duration{name:homepage}`)
- 条件（例如，`p(95)<500`)
- 是否设置了 `abortOnFail`

还检查最近一次运行的阈值结果，以查看哪些阈值目前通过，哪些未通过。

并非所有指标都会有阈值——这没关系。没有阈值的指标仍然会进行趋势分析；它们只是不会进行裕量计算。

### 第 7 步：计算趋势

**确定性地检测拐点并排除脚本变更。** 在得出回归结论之前，查找指标值中的不连续性——在同一日期多个指标上出现的突然跳跃或下降。当你发现一个时，不要猜测脚本是否更改。运行捆绑脚本端点在几秒钟内提供确定性答案：

1. **在边界处对捆绑脚本进行 sha256 差分。** 通过 `GET /cloud/v6/test_runs/{id}/script`（参考 k6-manage 第 5 节，“两个不同的脚本端点”——使用运行范围的端点，而不是负载测试端点，因为后者仅显示当前版本）获取最后“之前”运行和第一个“之后”运行的快照。使用 `shasum -a 256` 进行比较。

   ```bash
   gcx --context <ctx> api /api/plugins/k6-app/resources/cloud/cloud/v6/test_runs/<before_id>/script > /tmp/before.bin
   gcx --context <ctx> api /api/plugins/k6-app/resources/cloud/cloud/v6/test_runs/<after_id>/script > /tmp/after.bin
   shasum -a 256 /tmp/before.bin /tmp/after.bin
   ```

   对于跨转换的多运行拐点彻底性，对每个运行进行哈希——如果 N 个连续运行共享一个哈希，而 N 个更多运行共享另一个哈希，则你有一个干净的之前/之后边界。如果哈希中途更改，则测试被多次编辑。

2. **如果 sha256 不同**，则测试脚本更改——拐点可能是测试侧的副作用，而不是服务回归。在边界处将分析分为不同的时期，并在每个时期内分别计算趋势。跨脚本变更比较指标会产生误导性的趋势——如果脚本只是停止访问一个慢速端点，从 3,000ms 下降到 150ms 不是一个“改进”。在报告中明确说明时期，并将建议集中在最新时期。

3. **如果 sha256 相同**，则脚本完全相同，回归是测试外部（服务端、基础设施或负载区）。这是高置信度信息——将其带入第 9 步（服务端关联），而不是将“测试是否更改？”作为一个悬而未决的问题。

这种 sha256 差分是一个 5 秒的确定性检查，可以排除一大类原因。在每次检测到的拐点运行它，而不仅仅是在用户询问时。

对于每个指标，构建一个按时间排序的（运行时间戳，值）对序列。然后计算：

**基本统计：**
- 所有运行中的均值、标准差、最小值、最大值
- 当前值（最近一次运行）
- 基线值（窗口中最旧的运行，或前 3 次运行的平均值以保持稳定性）

**趋势方向：**
将运行分为两半（时间窗口的前半部分和后半部分）。比较每半的均值：
- **下降**：后半部分的均值比前半部分差 >10%（延迟/错误更高，成功率更低）
- **改善**：后半部分的均值比前半部分好 >10%
- **稳定**：变化在 10% 以内
- **波动**：标准差超过均值的 25%，无论方向如何

10% 和 25% 阈值是起点。如果用户测试的容差非常严格或指标非常嘈杂，请调整并解释原因。

**变化率：**
表示为每周百分比变化：`((recent_mean - baseline_mean) / baseline_mean) * 100 / weeks_in_window`。这可以跨不同窗口大小进行标准化。

**异常检测：**
标记任何指标值偏离整体均值超过 2 个标准差的运行。这些是值得单独调查的潜在拐点。

### 第 8 步：裕量分析

对于有定义阈值的指标（来自第 6 步），计算裕量：

```
headroom_pct = ((threshold_value - current_value) / threshold_value) * 100
```

分类裕量：
- **舒适** (>50%)：远低于限制
- **充足** (20-50%)：健康但值得监控
- **薄弱** (<20%)：如果趋势继续，有突破风险
- **已突破** (<0%)：已经失败

对于下降且裕量薄弱的指标，如果当前变化率继续，估计阈值何时会被突破：

```
weeks_until_breach = headroom_absolute / rate_of_change_per_week
```

这是一个粗略的预测，不是预测——将其呈现为“在当前下降率下，此指标可能在大约 N 周内突破。”

### 第 9 步：服务端关联（当适用时）

如果第 7 步显示下降，提供（不要自动运行）与服务端数据关联，以分离 **服务端退化**（修复服务）、**测试环境变更**（负载区延迟、LG 疲劳）和 **脚本变更**（速度较慢的编辑）。先呈现结果并询问。

转交给 `debug-with-grafana`（通过 `gcx`）查询服务的 Prometheus 指标和 Loki 日志，用于相同窗口；查找服务错误率变化、上游延迟、资源压力（CPU/内存/池）以及与服务拐点重合的部署。

**当服务没有可观测性**（第三方服务或另一个团队的服务——没有 Prometheus 作业、Loki 流或探针），回退到客户端信号，这仍然可以将回归定位：

- **浏览器测试**：比较 Tempo 迭代跟踪（参考 k6-manage §7，`/api/v1/tempo/api/search` + `/traces/{id}`）的“之前”/“之后”运行。跨度名称汇总、最慢跨度以及按 URL 导航持续时间将回归定位到 URL、定位器操作或资源；Web 生命体征是 `web_vital.*` 跨度属性——直接读取它们。
- **协议测试**：比较 `http_req_duration by (name, status)` 和 `http_req_failed by (name, status)`；一个命名请求的回归指向该端点。拆分 `http_req_waiting`（服务器时间）与 `http_req_receiving`（传输）以分离慢速处理与慢速下载。
- **有效载荷佐证**（两者）：查询 `data_received` / `browser_data_received`。延迟上升 + 有效载荷上升 -> 服务器内容变更；延迟上升 + 有效载荷稳定 -> 服务器处理变更；间歇性有效载荷 -> 不可靠的缓存或 A/B 测试。

当可用时，优先选择服务端关联——它直接回答“为什么”；回退回答“在哪里”和“什么类型的变更”，并使拥有团队的良好工单。

### 第 10 步：呈现报告

始终以结构化报告的形式呈现结果。永远不要直接应用变更。

## 报告模板

使用此结构。省略不相关的部分（例如，如果没有检测到异常，则跳过“异常”部分）。

```markdown
# 趋势分析：{test_name}

**测试 ID**：{test_id}
**分析窗口**：{start_date} 至 {end_date} ({N} 次运行分析)
**整体健康状况**：{健康 | 观察 | 下降 | 危急}

## 运行摘要

| 时期 | 运行次数 | 通过 | 失败 | 通过率 |
|------|----------|------|------|--------|
| 前半部分 | N | N | N | N% |
| 后半部分 | N | N | N | N% |

## 指标趋势

| 指标 | 类型 | 当前 | 基线 | 变化 | 趋势 | 阈值 | 裕量 |
|------|------|------|------|------|------|------|------|
| http_req_duration (P95) | 趋势 | 380ms | 250ms | +52% | 下降 | 500ms | 24% |
| http_req_failed | 速率 | 0.8% | 0.3% | +167% | 下降 | 1% | 20% |
| http_reqs | 计数器 | 15,230 | 15,100 | +0.9% | 稳定 | - | - |

## 标记问题

### 1. {metric_name}: {分类}
- **当前**：{value} | **基线**：{value} | **变化**：{pct}%
- **阈值**：{threshold} | **裕量**：{pct}%
- **变化率**：{pct}% 每周
- **预计突破**：~{N} 周在当前变化率下
- **异常运行**：{run_ids with dates, if any}

## 阈值建议

| 指标 | 当前阈值 | 建议 | 理由 |
|------|----------|------|------|
| http_req_duration | p(95)<500 | p(95)<420 | 当前 P95 为 380ms；将阈值收紧到 420ms 可在当前性能下提供 10% 的裕量，同时及早发现进一步下降 |

## 建议的下一步

- [ ] **调查服务端**：P95 延迟增加了 52% —— 考虑加载 `debug-with-grafana` 检查服务健康状况
- [ ] **深入分析运行 {run_id}**：{date} 的异常 P95 拐点——考虑加载 `k6-cloud-investigate-test` 进行此运行分析
- [ ] **收紧阈值**：2 个指标的裕量超过 30% 可收紧——考虑加载 `k6-test-maintenance` 应用变更

## 整体健康状况分类

从最坏情况指标中推导整体健康状况：
- **健康**：所有指标稳定或改善，裕量充足或合适
- **关注**：至少有一个指标正在恶化，但裕量仍然充足
- **恶化**：至少有一个指标正在恶化，且裕量不足
- **关键**：至少有一个指标已超过其阈值，或多个指标正在恶化且裕量不足

## 阈值建议

在建议更改阈值时，请遵循以下原则：

- **仅收紧，永不放宽**，除非用户要求。放宽阈值会掩盖问题。
- **目标设定在指标近期P95值的10-20%裕量之上**。足够容纳正常波动，但又足够紧以捕获真实恶化。
- **使用后半段平均值作为基准**，而不是最近单次运行（这可能是一个异常值）。
- **尊重用户的意图**：如果当前阈值非常宽松（>100%裕量），它们可能是故意宽松的。提及收紧的机会，但不要强推——用户了解其上下文。
- **考虑分组阈值**：如果测试使用基于标签的阈值（例如，`http_req_duration{name:homepage}`），建议按端点设置阈值，因为不同端点之间的趋势可能不同。

## 注意事项

| 问题 | 详情 |
|-------|-------|
| **零观测阈值** | 在k6中，具有零观测值的阈值默认通过。如果一个指标看似通过但没有数据，请标记它——实际上并未评估该阈值。 |
| **运行间指标类型变化** | 如果一个指标的类型在运行之间发生变化（例如，脚本重构），多运行聚合端点使用最新类型。较早运行的查询使用错误方法会返回空值。如果检测到这种情况，请标记。 |
| **不完整运行导致趋势偏差** | 中止或超时的运行通常持续时间较短且迭代次数较少，产生的指标值不能代表整体情况。默认情况下排除它们。 |
| **LG资源指标** | `load_generator_cpu_percent` 和 `load_generator_file_handles` 趋势上升可能表明测试正在超出其负载生成器分配，而不是服务正在恶化。单独指出这一点。 |
| **速率指标方向** | 对于 `ratio` 类型的速率指标（如检查通过率），"恶化"意味着值在*减少*（通过次数减少），这与延迟指标的方向相反。 |
