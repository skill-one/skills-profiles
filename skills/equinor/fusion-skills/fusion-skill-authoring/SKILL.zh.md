# 创建或更新技能

## 使用场景

在 `skills/` 下创建新技能时，或现有技能需要材料创作刷新时激活。

典型触发器：
- "为...创建技能"
- "搭建 `skills/<名称>/SKILL.md`"
- "将此工作流转换为可重用的技能"
- "改进此技能的元数据和触发提示"
- "使此技能更易于发现"
- "为技能设置引用/资源/辅助代理"

隐式触发器：
- 重复任务持续需要相同的指令或安全边界
- 现有技能过于模糊、过长、路由不良或缺少结构
- 用户希望的是可重用的工作流包，而不是一次性提示

## 不适用场景

- 在 `skills/` 外编辑产品或应用程序代码
- 仅需微小拼写修改且无需创作工作流帮助的编辑
- 可通过文档、模板或脚本更好解决的请求，无需可安装技能
- 大规模无关的仓库重构
- 具有破坏性的命令或隐藏的网络自动化

## 必须输入

如果缺少必须输入，请先提出简洁的针对性问题。
使用 `assets/follow-up-questions.md` 作为默认问题库。

### 必填项

在起草前收集：
- 这是否为新建技能、更新或根本不是技能
- 目标仓库路径和预期技能目录
- 基础技能名称（在任何前缀/命名空间之前使用连字符命名法）
- 最终技能名称（使用连字符命名法；如果仓库有不同约定，则默认为 `custom-<基础技能名称>`）
- 一句话的目的和用户结果
- 具体的触发提示：触发短语、领域关键词、反触发器
- 预期输出：技能产生的文件、命令或决策
- 安全边界和审批要求

### 条件输入

在相关时收集：
- 命名前缀、命名空间或目录约定
- 技能类别：能力提升或工作流/编码偏好
- 组成：独立、协调器或从属
- 仓库特定的所有权、生命周期或发布策略
- 协调器关系：`metadata.orchestrator` 用于从属技能，`metadata.skills` 用于协调器
- 目标状态（`active`、`experimental`、`deprecated`、`archived`）
- `compatibility` 文本，当技能有实际环境约束时
- MCP 要求（`metadata.mcp.required` / `metadata.mcp.suggested`）
- `agents/` 中的辅助代理是否会增强范围、审查或触发调整
- 确定性自动化是否证明需要一个 `scripts/` 目录

### 可选输入

如果有用则捕获：
- `metadata.sponsor` 作为备份问责制，如果目录使用它
- 启动资产、清单、示例或模板
- 如果存在几乎匹配项且应改进而不是重复，则捕获相关问题后续处理

### 元数据和结构约束

在编写文件前验证：
- `name`：1-64 个字符，仅限小写字母/数字/连字符，必须与文件夹名称匹配，不能有首尾连字符，不能有连续连字符，不能有 XML 标签，也不能有保留词
- 如果目标仓库没有前缀或命名空间约定，默认新技能为 `custom-<基础技能名称>`
- `description`：非空，<= 1024 字符，第三人称，不能有 XML 标签，说明技能做什么以及何时使用它
  - 优先使用带内联 `USE FOR:` 和 `DO NOT USE FOR:` 提示的单引号 YAML 字符串
  - 示例：`description: '从验证的仓库上下文中起草发布说明。USE FOR: 发布摘要、变更日志准备。DO NOT USE FOR: 发布发布或编辑产品代码。'`
- `metadata.version`：遵循目标目录的起始版本规则；如果没有本地规则，新技能的安全默认值为 `"0.0.0"`
- `metadata.owner`：仅在目标目录要求明确所有权时包含；使用稳定的 GitHub 身份或等效团队处理
- `metadata.status`：仅在目标目录跟踪生命周期状态时包含；如果使用，请保持为 `active`、`experimental`、`deprecated` 或 `archived`
- `metadata.tags`：保持相关标签、小写和连字符命名法
- `metadata`：除非关系字段明确需要列表或映射，否则使用简单的键/值元数据
- `license`：可选的顶层字段
- `compatibility`：可选的顶层字段；仅在技能有实际运行时、网络、工具或产品约束时包含

特定于仓库的前缀规则、所有权/生命周期要求、发布策略和验证命令属于仓库本地说明或目录文档，而不是可移植技能包。

## 说明

### 第 1 步 — 编辑前检查已安装副本的来源

在编辑现有的 `SKILL.md`（或其 `references/`、`assets/`、`agents/`）之前，检查仓库的 `apm.yml` 和 `apm.lock.yaml`。使用锁文件的依赖来源和部署文件的所有权来确定目标是否来自外部 APM 依赖。如果是，目标是一个**已安装副本**，而不是规范源。

**如果是已安装副本：**
- 不要就地编辑 — 本地编辑可能会被下一次 `apm install` 或 `apm update` 覆盖，并且永远不会到达其他消费者。
- 告知用户文件是从 `<来源>` 安装的；更改应在那里。
- 提供切换到 `<来源>` 并在那里进行更改的选项，或起草针对它的错误/改进问题。
- 只有在用户明确确认一次性覆盖并接受它不会持久的情况下才就地编辑。

如果既不存在 APM 文件，目标没有匹配的部署文件所有权，或源与当前仓库匹配，则正常进行。

### 第 2 步 — 判断是否应为技能

1. 首先检查现有目录：
   - 如果现有技能涵盖请求，建议重用或更新而不是重复
   - 如果技能几乎匹配，建议改进它或打开一个问题
2. 如果请求更适合作为：
   - 普通仓库文档，
   - 没有可重用代理行为的模板/清单，
   - 没有技能路由价值的独立脚本，或
   - 对现有技能进行微小复制编辑

### 第 3 步 — 在起草前定义代表性请求

在编写长说明之前，至少捕获三个代表性请求：
- 用户请求或触发短语，
- 技能应产生的行为，
- 技能必须防止的错误或差距。

使用这些作为验收标准。如果你无法定义现实的请求，范围未指定或不够可重用以成为技能。

### 第 4 步 — 对技能进行分类并选择最小的有效结构

决定技能类型：
- `能力提升`：打包领域知识、工具或参考材料
- `工作流 / 编码偏好`：打包顺序、审查门禁、样式规则或变异顺序

决定组成：
- `独立`：不需要协调技能
- `协调器`：路由到配套技能，拥有共享门禁
- `从属`：仅在协调器下运行 — 文档该依赖关系

选择最小文件夹结构：
- `SKILL.md` 总是
- `references/` 用于长指导、示例、表格或平台特定细节
- `assets/` 用于模板、清单、样本输出和静态文件
- `agents/` 用于专用辅助角色，当运行时支持技能本地代理时
- `scripts/` 仅当确定性自动化实质性提高安全性或可靠性时

保持引用在一级深度。不要创建嵌套链，这会强制部分读取。

### 第 5 步 — 起草最小可用 `SKILL.md`

首先编写最简单的有用主文档：
- 简洁的前置元数据，带有强烈的发现提示
- `使用场景` 和 `不适用场景`
- `必须输入`
- `说明`
- `预期输出`
- `安全与约束`

保持在 300 行以下。不同的运行时有不同的上下文限制 — 超过 300 行的文件在小运行时上可能会退化并触发 CI 警告。超过 500 行的文件会失败 CI。早期将溢出移至 `references/`。

优先选择简洁、具体的说明而不是背景解释。假设代理有能力；只添加它不会可靠推断的上下文。

有意设置自由度：
- 高自由度用于依赖上下文的分析或审查
- 中等自由度当存在首选模式但预期适应时
- 低自由度当工作流脆弱、安全关键或顺序敏感时

在 `SKILL.md` 或在 `references/` 中链接至少一个具体示例。

### 第 6 步 — 仅在减少歧义时添加支持文件

将长或专业的内容移出 `SKILL.md`：
- `references/` 用于深度指导、大型示例、API/平台笔记或长清单
- `assets/` 用于模板和可重用工件
- `agents/` 用于辅助集，当运行时支持技能本地代理且工作流受益于范围第二意见时
- `scripts/` 用于确定性操作，应执行而不是重新生成

如果你添加脚本：
- 文档依赖项和副作用，
- 验证输入并使用可操作的错误失败，
- 保持网络访问明确且合理，
- 从不使用远程代码执行模式。

如果运行时不忽略捆绑的辅助代理，请在线内保持相同的角色。

如果技能依赖于 MCP，请在 `metadata.mcp` 中声明，并在技能内容中记录客户端特定工具命名。

### 第 7 步 — 验证发现、结构和本地策略

在工作流更改后，运行目标环境支持的验证：

- 技能目录的清单或模式验证，如果可用
- 仓库或目录策略检查，用于命名、所有权、生命周期或组成元数据
- 脚本、GraphQL、lint 或测试验证，当技能触及这些表面时

如果没有专门的技能工具：

- 逐字阅读 `SKILL.md` 和每个直接引用的文件
- 验证每个代表性请求是否正确触发技能
- 验证每个引用的文件路径和工作流假设是否有效

使用第 3 步的代表性请求进行审查：
- 描述是否在正确的请求上触发并避免误报？
- 代理是否可以无序嵌套链接地定位所有直接引用的文件？
- 输出、审批门禁和安全约束是否明确？

如果子代理可用：
- `agents/scoper.md` 在起草前决定创建 vs 更新 vs 不是技能
- `agents/devils-advocate.md` 在范围和起草期间提出关键问题，或当用户要求严格审查或发现重大歧义时进行完整结构化访谈
- `agents/reviewer.md` 在起草后审查发现、结构、安全和验证证据
- `agents/trigger-tuner.md` 当主要风险是弱触发提示时

在可移植包正确后，应用任何仓库特定的发布或版本规则。

### 第 8 步 — 报告更改和仍需输入的内容

将创作结果作为显式合同返回：
- 创建或更新的内容，
- 技能的分类，
- 使用的代表性请求作为验收标准，
- 使用的辅助代理（如果有），
- 运行的验证命令及其证明，
- 任何未解决的问题或建议的后续问题。

## 核心行为需保留

- 编辑现有技能前检查已安装副本的来源
- 重用优于创建
- 可移植性优先，仓库覆盖其次
- 在长文本编辑前使用代表性请求
- 逐步披露而不是过载 `SKILL.md`
- 对风险操作设置明确的安全和审批门禁
- 真实的验证证据而不是假设的正确性

## 可选辅助代理

借鉴自 Anthropic `skill-creator` 模式，但缩小到 Fusion 特定的范围、审查和触发调整。

- `agents/scoper.md` — 决定新建技能 vs 更新 vs 不是技能；选择最小文件夹结构
- `agents/reviewer.md` — 审查起草的技能相对于发现、结构、安全和验证
- `agents/trigger-tuner.md` — 锤炼描述措辞；比较触发提示变体
- `agents/devils-advocate.md` — 始终在线的质量合作者；编辑期间为中等模式，询问时或发现重大歧义时为审问模式

如果运行时不提供子代理，请保持相同的审查循环在线。

## 示例

- 用户："为起草事件回顾创建技能。"
   - 结果：在目标目录中创建一个新的工作流导向技能，定义至少三个回顾创作场景，搭建 `SKILL.md`，并且只有在需要模板时才添加 `assets/`。
- 用户："改进 `fusion-skill-authoring` 的触发提示和结构。"
   - 结果：更新现有技能，刷新支持性引用/资产，并运行目标仓库的验证流程。
- 用户："为应用程序添加一个新的 CLI 标志。"
  - 结果：不要使用此技能，因为请求是产品代码工作，不是技能创作。

## 预期输出

返回：
- 创建或更新的文件路径
- 技能分类：新建/更新/不是技能，能力 vs 工作流，独立/协调器/从属
- 最终使用的触发提示和反触发器
- 选择的最小文件夹结构和理由
- 至少三个用作验收标准的代表性请求
- 使用的辅助代理（如果有）
- 运行的验证命令、通过/失败状态和解释
- 仓库特定的覆盖在可移植草案后应用
- 后续操作、未解决的问题或建议的问题链接

参见 `references/skill-template-baseline.md` 获取默认文件夹结构和基线模板。

## 验证

参见 `references/validation-signals.md` 获取成功信号、失败信号和恢复步骤。

## 技能就绪检查清单

使用 `assets/skill-readiness-checklist.md` 作为最终质量检查清单。仓库特定的 PR 要求属于仓库说明，而不是可安装技能资产。

## 安全与约束

永远不要：
- 请求或暴露秘密或凭证
- 在没有明确用户确认的情况下运行破坏性命令
- 捏造验证结果或评估证据
- 修改请求范围外的无关文件
- 添加隐藏的网络访问、远程代码执行或不安全的脚本指导
- 在不首先揭示其源仓库并获得明确确认的情况下就地编辑 APM 安装副本

始终：
- 保持 `SKILL.md` 简洁；将溢出移至直接引用
- 在描述中明确发现合同
- 优先选择确定性验证循环而不是模糊建议
- 保持辅助代理的范围紧密；即使运行时不调用它们，核心工作流仍然有效
- 尊重目标目录的命名、所有权、生命周期和发布策略
