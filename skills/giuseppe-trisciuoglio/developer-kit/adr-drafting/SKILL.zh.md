# ADR 草稿撰写

为重要的架构决策创建新的架构决策记录 (ADR) 文档，以便团队能够清晰地记录重要技术决策的原因。

## 概述

此技能可帮助从发现到最终 Markdown 文件创建新的 ADR。它会确认决策详情，检查存储库中是否存在任何现有的 ADR 规范，并使用标准部分 `标题`、`状态`、`背景`、`决策` 和 `影响` 起草新的 ADR。

当存储库中尚未存在 ADR 规范时，默认将 ADR 存储在 `docs/architecture/adr` 中，并使用零填充的文件名，例如 `0001-use-postgresql-for-primary-database.md`。

请参阅 `references/template.md` 获取默认的 ADR 模板，以及 `references/examples.md` 获取示例 ADR 和命名模式。

## 何时使用

当用户或代理已决定进行有意义的架构变更，并需要通过新的架构决策记录记录其理由、选择的方向和权衡时，请使用此技能。它适用于创建 ADR、记录架构决策、编写决策记录或保留重要技术选择背后的项目历史记录等请求。

## 说明

### 第一阶段：确认 ADR 输入

向用户询问起草新 ADR 所需的最少信息：

1. 决策标题
2. 决策状态（如果尚未最终确定，则默认为 `Proposed`）
3. 背景：导致决策的问题、约束或力量
4. 决策：选择的方法
5. 影响：哪些方面变得更容易、更困难、风险更高或成本更高
6. 确认此请求是用于创建**新的 ADR**，而不是编辑现有的 ADR
7. 确认所需的存储库语言（如果文档语言不明确）
8. 确认是否必须保留任何现有的 ADR 命名规范

如果用户实际上想要更新现有的 ADR、更改旧 ADR 中的状态或管理替代链接，请解释此技能仅起草**新的 ADR 文档**，并询问他们是否希望改为创建新记录。

### 第二阶段：在存储库中发现 ADR 规范

起草之前检查存储库：

1. 搜索可能的 ADR 位置，例如：
   - `docs/architecture/adr`
   - `docs/adr`
   - `adr`
   - `architecture/adr`
2. 如果 ADR 文件已存在，读取一个到三个示例以推断：
   - 编号格式
   - 文件名模式
   - 标题格式
   - 语言和语气
3. 如果不存在 ADR 目录，建议使用 `docs/architecture/adr`
4. 在可能的情况下，从现有文件中确定下一个 ADR 编号
5. 如果没有先前的 ADR，则从 `0001` 开始

当不存在规范时的首选默认命名：

- 目录：`docs/architecture/adr`
- 文件名：`NNNN-short-kebab-title.md`
- 标题：`# ADR-NNNN: <决策标题>`

### 第三阶段：起草 ADR

使用标准结构创建草稿：

```markdown
# ADR-NNNN: 决策标题

## 状态
Proposed

## 背景
是什么问题、约束或权衡导致了此决策？

## 决策
做出了什么架构选择？

## 影响
由于此决策，哪些方面变得更容易、更困难、风险更高或成本更高？
```

起草规则：

- 保持标题具体且面向决策
- 捕获足够的背景信息以解释*为什么*需要此决策
- 清晰直接地记录选择的方向
- 当已知时，包含正面和负面的影响
- 不要编造用户未提供的理由、约束或结果
- 如果关键信息缺失，请在最终确定之前插入简洁的占位符或询问后续问题

### 第四阶段：与用户审查草稿

在写入文件之前，提供：

- 提议的文件路径
- 提议的标题
- ADR 状态
- 草稿部分的简短预览

在创建文件之前请求批准。如果用户希望进行调整，请先修改草稿。

### 第五阶段：创建 ADR 文件

批准后：

1. 如果 ADR 目录不存在，则创建该目录
2. 当可用时，使用存储库建立的模式编写 ADR Markdown 文件
3. 尽可能保留用户的决策理由措辞，同时保持文档简洁
4. 报告最终文件路径并总结创建的内容
5. 创建新的 ADR 文件后停止，以使技能专注于单个新的决策记录

## 示例

### 示例 1：新的数据库决策

**用户请求：** "为从 SQLite 迁移到 PostgreSQL 创建 ADR"

**预期流程：**

1. 确认标题、状态、变更的原因和预期影响
2. 检查存储库是否已存在 ADR 文件
3. 按照现有规范起草新的 ADR，或默认为 `docs/architecture/adr/0001-move-to-postgresql.md`
4. 在写入文件之前请求批准

### 示例 2：新的服务边界

**用户请求：** "记录将计费拆分为独立服务的决策"

**预期流程：**

1. 询问架构背景以及当前设计为何不足
2. 确认选择的边界和运营影响
3. 使用标准部分起草新的 ADR
4. 仅在用户批准后创建文件

请参阅 `references/examples.md` 获取更长的 ADR 示例。

## 最佳实践

- 每个ADR应专注于一个架构决策
- 当已存在 ADR 时，匹配现有的存储库命名、编号和写作风格
- 优先使用简洁的解释而不是长篇叙述
- 如实记录权衡，包括缺点和新的风险
- 除非用户确认其他状态，否则默认状态为 `Proposed`
- 当明确时，使用存储库的首选文档语言

## 限制和警告

- 此技能仅用于**新的 ADR 创建**
- 不要更新现有的 ADR 文件、状态历史记录或替代链
- 不要编造缺失的理由或影响
- 如果存储库已使用其他 ADR 位置，不要强制使用 `docs/architecture/adr`
- 当决策、背景或影响过于模糊无法负责任地记录时，请随时询问澄清问题
