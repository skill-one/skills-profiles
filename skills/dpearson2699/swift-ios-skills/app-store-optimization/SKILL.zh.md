# 应用商店优化 (ASO)

应用商店产品页面的搜索可见性和转化率优化。这项技能涵盖了战略元数据决策——要针对哪些关键词，如何构建描述以促进转化，以及如何使用自定义产品页面和应用内事件来提高可发现性。有关元数据合规性规则（字符限制、截图设备要求、拒绝触发因素），请参阅 `app-store-review` 技能。

## 工作流程和边界

1. 将建议分为 **可见性**（索引元数据、本地化、评分、事件）和 **转化**（消息、资源、变体、实验）。
2. 为每个建议命名证据、负责人、目标指标和验证检查点。
3. 应用 [评价清单](#评价清单)。

| 工作 | 负责人 |
|---|---|
| 列表、关键词/消息匹配度、资源、页面变体、本地化、事件、评分策略 | 本技能 |
| 提交合规性、隐私清单/标签、ATT措辞、拒绝风险 | `app-store-review` |
| 购买、付费墙、权限、订阅机制 | `storekit` |

## 标题和副标题策略

苹果会索引应用名称和副标题进行搜索。两者结合提供了 60 个字符（30 + 30）的索引、高可见性的关键词位置。

### 定位框架

当品牌已有知名度时，使用 **品牌 -- 关键词**；当新应用必须通过类别术语进行竞争时，使用 **关键词 -- 品牌**；当品牌自然包含相关关键词时，使用混合名称。

### 规则

- 不要在名称和副标题之间重复单词——苹果会索引两者，因此重复的字符是浪费。
- 在有更多空间的字段中优先放置最高价值的关键词。
- 避免使用通用填充词（"the"、"best"、"app"）——它们占用空间但没有搜索价值。
- 副标题应传达主要价值主张，而不是标语。

## 关键词字段策略

App Store Connect 接受关键词字段中最多 100 个 UTF-8 字节（苹果的一些概览页面将此总结为 100 个字符）。使用逗号分隔的术语，逗号后不加空格；每个术语必须超过两个字符。

### 优先级

根据三个因素对候选关键词进行排序：

| 因素 | 权重 | 信号 |
|--------|--------|--------|
| **相关性** | 最高 | 关键词是否描述了应用的实际功能？ |
| **搜索量** | 中等 | 用户是否实际搜索这个术语？ |
| **竞争** | 较低 | 有多少应用针对这个关键词？ |

优先考虑用户意图和元数据匹配度。除了应用名称、副标题和关键词字段外，还要考虑主要类别；不要重复它。

### 战术规则

- 与标题和副标题去重——苹果已经索引了这些词。
- 不要同时包含同一术语的单数和复数形式；苹果将它们视为重复。
- 忽略类别名称——苹果会自动将应用的主要类别添加到搜索中。
- 逗号后不要加空格——它们会占用 100 个字符的限制。
- 如果它们是真实的搜索术语，请考虑缩写和常见拼写错误。
- 为最相关、最高意图的术语保留空间；不要为仅弱描述应用的关键词花费字符。

**参见：** [参考资料/关键词研究方法.md](references/keyword-research-methodology.md) 了解完整的研究过程、评分框架和索引详细信息。

**验证检查点：** 将最终名称、副标题和关键词字段放在一起。计算其 UTF-8 字节，用逗号分割，拒绝空白、以空格开头或两个字符或更短的标记，比较三个索引字段和主要类别的标准化单词，并要求每个保留的术语都有相关性或需求信号。如果字段需要修改，请重复检查，直到每个标记都值得其空间。

## 描述结构

苹果的搜索指南以应用名称、副标题、关键词和主要类别为中心，加上行为信号（如下载量、评分和评价）。将描述视为转化文案，而不是填充额外搜索术语的地方：展开描述的用户正在评估是否要下载。

### 四部分结构

1. **钩子**（前 1-3 行）——这是“更多”折叠之前唯一可见的文本。以最强的利益或差异化点开头。这是页面最重要的文案。
2. **功能亮点**——4-6 个简短的功能描述。使用 Unicode 项目符号字符（•），因为应用商店不渲染 markdown。专注于结果，而不是技术细节。
3. **社会证明**——奖项、新闻引用、用户数量里程碑或值得注意的评分。一到两行。
4. **行动号召**——鼓励下载的结束语。保持简短并利益导向。

### 格式说明

- 应用商店不渲染 markdown、HTML 或富文本。使用纯文本和 Unicode 字符进行结构。
- 短段落，段落之间换行。大段文字会扼杀转化。
- 按地区编写——翻译结构，而不是单词。参见 [本地化元数据优化](#本地化元数据优化)。

## 促销文本

促销文本显示在描述上方，限制为 170 个字符，可以随时更新，无需提交新版本的应用。

### 轮换策略

为功能发布、季节性时刻、奖项或新闻、促销和应用内事件更新促销文本。不要在发布之间保持静态；如果没有及时推广的内容，请轮换应用的最强卖点。

## 截图和预览优化

大多数用户永远不会滚动到前 3 个可见的截图。这些位置决定了用户是会与完整的产品页面互动还是继续浏览。

### 前 3 个截图

- 首先展示主要价值主张——最好展示为什么某人应该下载应用的屏幕。
- 不要在前 3 个位置放置引导、启动或加载屏幕。
- 每个截图应展示不同的利益或功能。

### 标题写作

- 写效益导向的标题，而不是功能标签。"Never miss a deadline" 转化得比 "Calendar View" 更好。
- 标题保持在截图上方 2-5 个词，下方一行简短。
- 使用动词："Track"、"Share"、"Discover"、"Build"。

### 排序策略

使用位置 1 展示主要价值主张，位置 2 展示核心差异化点，位置 3 展示下一个最强功能，后续位置展示支持性功能、社会证明或边缘情况。

### 应用预览视频

如果存在预览视频，它会占据第一个位置。当禁用自动播放时，第一帧将成为海报图像——选择一个可以作为独立截图的帧。

对于截图设备要求和合规性规则，请参阅 `app-store-review` 技能。

**验证检查点：** 预览每个本地化产品页面在第一折尺寸下的效果。确认前三个可见的资源传达了不同的利益，标题与 UI 和公共声明匹配，并且页面的元数据目标与排序的意图一致。替换或重新排序任何失败的资源，然后再次将第一折作为一组进行审查。

## 应用内评价提示

StoreKit 提供 `RequestReviewAction` 用于 SwiftUI 和 `AppStore.requestReview(in:)` 用于 UIKit。使用本节进行时间策略；有关完整的 StoreKit API 表面，请参阅 `storekit` 技能。

### 系统行为

- 系统强制执行每 365 天每个设备对尚未评价应用的用户最多 3 次提示。
- API 是请求，不是保证——StoreKit 决定是否显示提示。
- 在开发期间，提示始终出现。在 TestFlight 中，它永远不会出现。

### 提示时间

好的触发因素包括完成有意义的任务、达到里程碑或连续记录、积极的内应用时刻或多个活跃会话。不好的触发因素包括首次启动、引导、错误、崩溃、失败交易或直接按钮预览。不要将提示锁定在“评价此应用？”对话框后面——苹果不鼓励拦截系统提示，并且可能会拒绝预览的应用。

### 持久评价链接

对于设置屏幕或“评价我们”选项，使用以下 URL 格式直接链接到应用商店评价页面：

```
https://apps.apple.com/app/id{APP_ID}?action=write-review
```

这会直接打开评价写作屏幕，并且不受每年 3 次系统限制的影响。

## 自定义产品页面

自定义产品页面允许每个应用最多 70 个变体产品页面。每个变体可以有不同的截图、应用预览视频、促销文本和分配的搜索关键词——针对特定受众或获取渠道进行定制。

在推荐自定义产品页面时，明确提到 70 页容量和分配关键词的搜索可见性，然后将每页映射到不同的受众、消息、关键词/广告意图和测量计划。

### 用例

为付费搜索广告组、社交活动、特定功能着陆页、季节性活动和其他获取路径使用单独的页面，在这些路径中，第一个截图或促销文本应匹配不同的用户意图。

### 设置

- 每个自定义产品页面都会获得一个唯一的 App Store URL，可用于广告活动、深度链接和网页。
- 批准的页面也可以根据分配的关键词从最新批准的应用版本出现在应用商店搜索中。
- 页面可以独立本地化。
- 在 App Store Connect 的自定义产品页面选项卡下创建页面。
- 以描述性方式命名页面以供内部跟踪（例如，“Search-FitnessTracking”、“Social-HolidayCampaign”）。

**参见：** [参考资料/product-page-variants.md](references/product-page-variants.md) 了解设置详细信息、URL 结构和活动映射策略。

## 应用内事件

应用内事件出现在应用商店搜索结果、今日标签和个性化推荐中。它们在事件窗口期间增加可见性，并可以重新吸引流失用户。

### 事件类型

选择与实际应用内体验相匹配的苹果事件徽章：挑战、竞赛、直播事件、重大更新、新季节、首映或特别事件。不要制造没有实际时间限制内容的事件。

### 元数据限制

事件名称 30 个字符，简短描述 50 个字符，长描述 120 个字符，事件卡片图像需要 16:9（1920x1080 或类似）。

### 策略

- 围绕功能发布、季节性时刻或内容发布安排事件。
- 为事件卡片上下文编写名称和简短描述，在产品页面、搜索和今日中测量及时卡片是否提高了点击率。
- 策略性重叠事件：在当前事件结束时开始下一个事件，以保持持续搜索可见性。

**参见：** [参考资料/product-page-variants.md](references/product-page-variants.md) 了解事件调度模板。

## 产品页面优化

App Store Connect 提供了产品页面元素的本地测试。

### 可以测试的内容

- 应用图标（备用图标）
- 截图（顺序、内容、标题）
- 应用预览视频

每个测试最多可以包含三个处理方案，原始产品页面作为默认基线。

### 测试设计

- 运行测试的最短时间为 7 天，以考虑周内变化。
- 确保有足够的流量以获得统计显著性——低流量应用可能需要更长的测试持续时间。
- 每次测试一次一个假设，作为方法选择（例如，截图顺序或标题文案，而不是同时测试两者），即使 App Store Connect 允许多个处理方案。
- 选择测试中包含的本地化；默认情况下，所有支持的本地化都会被选中。
- 一个测试最多运行 90 天或手动停止。结果在 App Analytics 中出现后，至少有五个首次下载与应用测试相关联。
- PPO 建议应命名假设、最多三个处理方案、选定的本地化、目标指标和决策规则。

### 解释结果

- 关注转化率提升（展示量到下载量），而不是绝对下载数量。
- App Store Connect 报告转化率、提升和置信度。将 90%+ 的置信度视为“表现更好”或“表现更差”决策的阈值。
- 应用获胜后，在开始下一个测试之前等待一段时间，以建立干净的基线。

## 评分和评价管理

评分和评价出现在产品页面和搜索结果中，影响应用商店搜索排名，并影响转化。策略是通过对成功用户时刻进行提示来赚取更多积极的最新反馈，并对问题进行建设性回应。

### 评价回应策略

- 在 App Store Connect 中回应负面评价——专业的回应即使不改变评分数字也会提高感知质量。
- 承认问题，说明正在做什么（或已经修复），并保持中立的语气。
- 将评价语言用作客户研究：用户经常用描述其目标、挫折和类别词汇的词语来改进未来的元数据和截图消息。

### 评分重置

在提交新版本时，可以选择重置显示的评分。策略性使用：

仅在显示的评分在重大改进后显著低于应用的当前质量时重置。不要重置强劲、有代表性的评分；不要为普通错误修复重置；并且在风险重设计后等待稳定。

## 本地化元数据优化

本地化 ASO 与翻译应用 UI 不同。关键词策略、描述和截图标题必须按市场进行研究和编写，而不是从主要地区进行机器翻译。

### 关键原则

- **按市场研究关键词。** 日语中“照片编辑器”的最常用术语不是“照片编辑器”的直接翻译。
- **按地区重写描述。** 调整钩子-功能-证明-行动号召结构以适应当地惯例和卖点。
- **本地化每个元数据表面。** 应用商店指南明确指出本地化描述、关键词、应用预览和截图；不要假设直接翻译或不受支持的跨地区索引行为。
- **本地化截图标题。** 用户语言的标题比未翻译的英语标题转化效果更好。

对于应用内字符串本地化（字符串目录、FormatStyle、从右到左布局），请参阅 `ios-localization` 技能。

## 常见错误

1. **写功能描述性的截图标题，而不是效益导向的截图文案。**
2. **翻译关键词，而不是按市场研究搜索术语。**
3. **在引导、错误、崩溃或失败交易后提示评价。**
4. **忽略前三个截图槽位或以引导/启动屏幕开头。**
5. **在没有足够持续时间、流量或一个清晰假设的情况下运行 PPO 测试。**
6. **在所有自定义产品页面中重复相同的资源。**

## 评价清单

- [ ] 元数据索引通过标题/副标题和关键词验证检查点
- [ ] 描述、促销文本和首屏资产通过其转换检查
- [ ] 元数据和资产根据地区进行调研、撰写、排序和预览
- [ ] 审查提示遵循成功的用户时刻和StoreKit的系统行为
- [ ] 页面变体、事件和PPO测试命名其受众、证据、指标和决策规则
- [ ] 公开声明和截图通过`app-store-review`合规性检查清单
