# 添加依赖项

**必要背景知识：** `principal-engineering` 技能。

## 概述

依赖项是一种招聘，而非代码片段：随着功能而来的是其缺陷、其发布节奏、其传递依赖树以及其维护者的注意力持续时间。核心原则：**充分利用现有资源，审查所引入的依赖项，固定版本并记录原因。**

## 充分利用现有资源

按列表顺序检查，在第一个满足条件的层级停止；好的答案通常由两个层级组成，其中一个现有的依赖项负责核心部分，而您只需围绕它添加几行自己的代码：

1. **需求本身。** 投机性需求不算需求；跳过它，并在一行代码中说明这一点。
2. **此代码库。** 几个文件之外的助手、类型或模式可以完成这项工作；重用它。仓库中已有的内容的第二个副本是数据 `keeping-one-source-of-truth` 禁止保留的缺陷。
3. **标准库。** 在安装重复它的包之前，先阅读其索引。
4. **平台。** 应用代码上的数据库约束、小部件库上的原生控件、运行时自身的原始类型而非包装器。
5. **项目已携带的依赖项。** 其传递依赖树已经支付过费用。两个边界。您开始使用的传递依赖项是新的直接依赖项：声明它，将其固定到已解析的版本，并轻量级审查它，因为代码已经发布。检查重用的类：开发工具的传递依赖项提升为运行时将成本转移到每个消费者的安装中，而不仅仅是 CI。
6. **几行自己的代码。** 拥有二十行代码胜过拥有陌生人的仓库，当二十行代码确实是全部所需时。
7. **仅通过以上六个步骤：** 新的依赖项，以下列方式审查。

## 审查所引入的依赖项

- **计算整体成本：** 它引入的传递依赖树、安装和构建的重量、与项目的许可证冲突、安全历史记录（公告和扫描器运行时的供应链评分）。
- **检查脉搏：** 近期发布情况、问题如何得到解答、有多少人可以合并。一个承重包只有一个疲惫的维护者是一个您选择承担的风险。
- **阅读您将调用的部分：** 您依赖的 API 表面及其失败模式，而不是 README 中的承诺。基础原则也适用于他人的代码。
- **优先选择单一任务的工具** 而非拥有四十个功能的框架；其他三十九个功能无论如何都会随之而来，无论是重量还是攻击面。
- **记录决策。** 新的依赖项是一个决策：它的用途、权衡的其他因素以及它离开的条件（通过 `recording-decisions` 安装时）。

## 依赖项立场

依赖项容忍度是项目声明的，就像其风险等级一样：完全自包含（某些应用正确地禁止使用外部代码）、经过策展的允许列表，或审查后添加。项目的规则或 CLAUDE.md 说明哪一种；当没有说明时，询问系统必须永不依赖的内容，并将答案视为声明。即使不方便也要维护立场；改变立场是一个记录的决策，而不是 npm install。

未声明的立场不是一个硬性门槛：当今天没有人能回答时，在声明的假设立场下进行，在决策中记录假设，并跟踪声明问题与所有者。

## 固定并验证

- 提交锁文件并固定版本；CI 中的未固定 `latest` 或基础镜像是一个定时炸弹，带有他人的时钟。
- 更新就像任何其他变更一样。在重大版本更新之前阅读发布说明（破坏性变更和迁移优先）。针对它运行测试 (`testing-changes`)。为重大版本更新单独提交，以便责任链保持可读；分组补丁更新可能会一起移动。
- 本地代码在树中携带其来源和版本；您无法更新无法标记的代码。

## 移除

- 工作消失的依赖项在移除工作的同一变更中移除；保留“以防万一”的包是第一级中的投机性需求，反向。
- 当依赖项只有一个小的调用点时，考虑拥有这些行代码。
- 未维护但承重是一个有所有者和计划的风险项，永远不会是希望。

## 常见错误

- 小工具反射：依赖树不是通过重大决策生长的；它们一次一个小包地生长，每个包单独合理。
- 安装框架仅调用一个函数。
- 依赖包的内部或私有路径；只有公共契约才是一个承诺。
- 将传递依赖项作为自己的导入：今天未声明，下一个锁文件刷新时消失。如果您需要它，请声明它。
- 添加依赖项以避免阅读仓库中已有的代码（第二级，跳过）。
- 没有来源就本地化，然后想知道副本是哪个版本。
- 一次性更新所有内容，然后二分法查找哪个更新破坏了构建。
