# 范围变更

**必要背景：** `principal-engineering` 技能。

## 概述

范围在两个方向上都会失败：过度装饰会使修复超出触发点；无声地缩小范围会使已批准的任务缩小到未达成共识的程度。两者都是一个缺陷：交付的变更不再与其原因匹配。核心原则：**修复的大小应与其触发点一致，当现实迫使削减时，应明显地分解，而不是悄悄地修剪。**

## 按触发点确定大小

- **触发点是缺陷或需求本身，而不是关于它的工单句子。** 在第二条路径上发现的相同缺陷在范围内（报告“已修复”而它仍存在于其他地方是半真报告）；因为文件打开而发现的相邻改进不在范围内。
- 修复的大小应与触发它的东西一样大。没有过度装饰，没有围住系统无法触及的边缘，没有因为文件打开而进行的重构。
- 你注意到的相邻改进是真实的，应该记录在追踪器中，而不是在这个差异中。
- 边界添加测试：如果主修复不存在，它是否会因其自身价值而发布？如果不是，它是别人差异上的装饰。如果是，它会因其自身价值发布：通过测试允许一个单独的变更，而不是附带项。
- 所有者可以重新确定范围；所有者不能合并范围。“把它挤进去”从合法拥有工作的人那里添加了第二个任务，并且它仍然作为自己的变更发布。这些规则控制工作如何成型；所有者决定存在哪些工作。
- 未请求的结构是戴着设计模式外衣的范围蔓延：只有一个实现者的接口、只构建一个东西的工厂、配置了无人会更改的值。在第二个情况出现时添加结构，而不是在想象时添加。
- 一个接受真实限制的故意简化应在注释中包含该限制：上限和什么情况下可以提升它（“一个共享队列；每个租户一个分片，当单个消费者无法跟上时”）。上限是当前约束：注释描述了系统今天的行为，而不是决策的历史。
- 在编写新代码之前，先耗尽代码库、标准库、平台和已安装的依赖项；在考虑引入新包之前，请参阅 `adding-dependencies`。

## 分解，永不无声地缩小范围

- 所有者将一个批准的、但结果太大的任务分解为具有明确切分线的命名部分，绝不交付一个看似完整的“务实最小值”的悄无声息的交付。
- 作者将每个延迟的部分作为有追踪器的项目进行记录，或者在没有所有者时明确记录为“所有者待筛选”。追踪器纪律存在于安装了技术作者插件的位置的 `writing-issues` 中。只存在于作者记忆中的延迟工作是被缩小范围，而不是被延迟。
- 报告明确说明哪些部分已发布，哪些部分未发布。一个诚实地标记为部分的交付是一个计划；一个标记为完整的部分交付是一个缺陷。

## 驱动完成

- 一个批准的计划在没有“需要我继续吗？”检查点的情况下运行到完成；只有在遇到真正的阻塞、破坏性行为或需要操作员的硬门槛时才停止。
- 阻塞在一个部分：完成未阻塞的部分，暴露阻塞点及其需求，绝不让一个卡住的任务无声地停滞其他任务。
- 已决定的决策在执行中途保持不变。真正重新打开一个新信息的决策成为明确的重新决策，而不是悄无声息的转向；通过安装了技术作者插件的位置的 `recording-decisions` 进行记录。

## 审查中的范围

- 审查：在旁路中注意到的不相关的缺陷不是你的发现；在追踪器中记录一次，并停留在差异上。
- 被审查：差异中的发现需要修复或明确回答；差异外的发现需要追踪，而不是被吸收到变更中。

## 常见错误

- “在我这里的时候”作为理由。你在这里是为了触发点。
- 为了赶上截止日期而缩小范围并报告完成。截止日期的压力是真实的；诚实的做法是分解并说明哪一半已发布。
- 围住系统无法触及的边缘，以感觉周全。无法触及的防御性是意图良好但已死代码。
- 在实施中途重新争论一个已批准的设计，因为出现了一个稍微更好的想法。写下这个想法；完成计划；针对已发布的现实提出它。
- 让审查者的范围外愿望扩展差异。记录它，感谢他们，发布触发点。
