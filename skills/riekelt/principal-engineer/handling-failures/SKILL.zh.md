# 处理失败

**必要背景：** `principal-engineering` 技能。

## 概述

被吞没的错误是一个证据被销毁的 Bug。核心契约：**每个失败路径必须且仅做以下三件事之一，并且这三种情况都必须是明显的。** 一个看似健康但返回错误数据的系统比崩溃的系统更糟糕。

## 契约

每个捕获和失败路径必须：

1. **以 WARN 或 ERROR 级别记录日志并重新抛出**，或
2. **记录日志并返回一个调用者必须处理的类型化失败**（结果类型、密封错误、编译器或契约强制下游代码承认的状态），或
3. **记录日志并进入明确文档化的降级模式**（在代码和文档中命名，并观察到系统处于降级状态）。

禁止，无例外：

- 空的捕获和继续。
- 捕获并返回默认值（空列表、null、零、缓存副本）来掩盖失败。
- `?? fallback` 及其变种，其中回退隐藏了主操作失败。回退只有在缺失也在其他地方明显暴露时才是可接受的。

## 推论

- **缺失的必要条目会明显失败。** 从注册表、配置或目录中缺失某物是构建或启动失败，绝不是静默的默认值。
- **错误状态是可见的。** 工作流不应在失败时看似健康；在 UI、指标或有人实际监控的日志中暴露错误状态。
- **面向操作员的修复措施是具体的。** "连接失败，检查 REDIS_URL 并确认 redis 是否响应 PING" 比 "发生错误" 更好。
- **重试是有限且可观察的。**
- **有副作用的操作的重放是无副作用的。**
- **降级模式有上限。** 跳过并继续需要在降级变为中止的明确阈值处，作为命名、操作员可调的常量。必须存在防护措施；其值是与所有者共同做出的判断。无上限的降级模式是慢速吞没。
- **失败路径中，可观察性是最低要求，而非锦上添花。** 日志行、计数器和警报随修复一起交付；没有它们的失败路径是意图更好的静默吞没。

## 修改现有吞没代码

正在编辑的已吞没代码：作为工作的一部分修复它，或明确标记它隐藏了什么。沉默地留下是认可它。在代码审查中，新的静默吞没是自动的阻止项；你接触过且未标记的现有吞没是对变更的警告。

## 常见错误

- 以 "它永远不会发生" 为理由吞没。那些路径正是需要明显警报时才需要处理的路径。
- 以 DEBUG 级别记录日志并称其为已处理。如果生产中无人看到，它就是带额外步骤的吞没。
- 捕获宽泛的 (`Exception`, `catch {}`) 来处理狭窄的。意外失败在预期失败旁边无声地死去。
- 未记录的降级模式。只有作者知道的降级是操作员无法诊断的停机。
- 通过默认失败使测试通过。测试变绿；缺陷升级到生产。
