# 记录决策

**必要背景：** `技术写作` 技能（硬性规则、事实规则、风格）。

## 概述

两种格式，按重要性区分：一份具有架构级影响的决策的完整 ADR；一份用于较小选择连续流的决策日志条目。两者都是仅追加写入：一个被接受的决策是不可变的；新的上下文是一个新的条目，它将取代旧的条目。

## 何时调用，以及不调用的情况

当选择已做出并需要记录时调用，当有人问“我们为什么这样做”时调用，或者当现有决策被取代时调用。不应用于仍在争论中的决策（那是 `编写设计文档`；其“原因与内容”框在被接受后成为 ADR）。

还在经过未记录的决策的信号时也调用：”我们决定 X 而不是 Y“，”我们就这么定了“，在 PR 评论或聊天线程中解决的权衡，或者有人已经解释两次的推理。每个都是存在于非持久化位置的决策；提供记录它的机会。

在引用之前记录决策。聊天会话不是持久的来源。将日期内容放入日志，在措辞重要的情况下引用决策者，提交条目，然后引用它。记录最小的完整决策，而不是一个转录文本。

## ADR

Nygard 格式。每个 ADR 一个决策。

```markdown
# ADR-[编号]: [决策的简短标题]

| | |
|---|---|
| **状态** | 提案 / 已接受 / 被 ADR-XXX 取代 |
| **日期** | YYYY-MM-DD |
| **决策者** | [参与人员] |

## 背景
[博弈的力量：技术、组织、政治。必须解决的问题。
事实性的，不透露决策。]

## 决策
[决定的内容。主动语态：“我们基于标签发布”，而不是“决定是发布”。]

## 后果
**正面：** [变得更容易的事情]
**负面：** [变得更难的事情，我们接受的权衡]
**中性：** [没有变得更好或更坏的变化]

## 考虑过的替代方案
**[替代方案]** - 支持：[...] 反对：[...] 没有被选择的原因： [...]

## 参考
[证据、相关决策、测量]

```

**负面是强制性的，并且不能为空。** 每个替代方案都带有其最强的论点；没有它的拒绝是一个稻草人。

对已接受的 ADR 唯一允许的编辑是其状态行获得“被 ADR-XXX 取代”。提出的反对意见但从未得到回答的进入作为具有命名所有者的负面后果，以全部强度进入：作者从不编造反驳意见，也从不隐瞒其所有者已宣布的决策。写作时未知姓名的标记为填写前提交，因为提交的记录包含真人。

## 决策日志（轻量级）

对于运行日志，完整的 ADR 会杀死它。维护成本足够低：

```markdown
## YYYY-MM-DD

### [将决策陈述为祈使句]
[一段话：规则。]
原因：
- [原因]
- [原因]
而不是：[拒绝的选项] - [原因]
```

## 规则

- 仅追加写入。一个错误的条目会得到一个新日期的条目来取代它，永远不会编辑。将相对日期转换为绝对日期。
- 记录原因，而不仅仅是内容。
- 当书写的规则和已发布的现实出现分歧时，记录团队意图的是哪一个。每个教义文档都声明它拥有什么，以及它留给别人的什么。
- 在可能重叠的兄弟顶部设置作用域保护：”产品想法存在于 ROADMAP.md 中；这个文件是用于工程决策的。“
- 明确捕获负面结果和未知因素：”四个理论，四个被证伪，原因未找到“是一个结果。一个返回空的结果也是一个结果。
