# 撰写事后分析报告

**必要背景：** 需要具备 `技术写作` 技能（硬性规则、事实规则、风格）。

## 概述

受众：一年后可能遇到类似问题的工程师，而非现场人员。核心原则：**事实基于证据，原因基于机制，经验教训源于两者，且不涉及姓名。** 分类：历史性；一旦评审通过即不可变，更正以日期标注的附录形式存在。

## 何时撰写，以及不撰写的情况

在事件解决后或长期事件的关键稳定节点后撰写。用户遇到的问题和险些发生的事件（审查发现的防护措施拦截了遗漏的问题）应使用相同的撰写方式。**在事件发生时不撰写：** 运行手册负责该部分。**不用于分配责任：** 需要提及姓名才能理解的事后分析报告描述的是流程漏洞。**不用于向利益相关者提供状态更新：** 这是报告的工作。

## 框架

```markdown
# [系统名称]: [故障症状，一句话描述]

| | |
|---|---|
| **事件日期** | YYYY-MM-DD |
| **持续时间** | 从发现到解决 |
| **严重程度** | [根据组织分类法定义，在使用的位置定义] |
| **状态** | 起草 / 已评审 |

## 摘要
[用户可见影响（含数字），根本原因（一句话），当前状态。即使读者只看这部分，也了解发生了什么。]

## 影响
[受影响的人和事（量化）：请求失败，记录受影响，损失的资金或时间。
估计值需标注为估计值；"无数据丢失证据"仅当实际检查时才使用，并说明检查内容。]

## 时间线
[带时间戳的条目，仅记录事实，每条均可追溯至证据：警报、日志行、提交记录、消息。解释性内容位于下文，此处不包含。]

## 根本原因和促成因素
[机制，基于代码和提交记录。促成因素以列表形式呈现；"所有组件均正确，缺陷存在于它们之间"是有效的根本原因。指出哪个检查层遗漏了问题，哪个检查层发现了问题。]

## 响应过程中的错误操作
[错误的初次修复，误导性信号，耗费时间的错误理论。]

## 行动项
[每个行动项需有负责人和验收检查，作为追踪问题记录并链接。
没有负责人的"调查X"在此处及任何地方均被禁止。]

## 审批
[- YYYY-MM-DD <评审人>: 批准 <范围>，每条评审事件一行。]
```

## 规则

- **无责备意味着结构性。** 指出角色、关卡、依赖关系、缺失的防护措施；绝不涉及个人。指责个人止于"更小心"；指责结构会产生行动项。这适用于叙事（时间线、原因、响应）；行动项负责人是分配，而非指责：本文件中的角色，追踪问题中的个人。
- **时间线是证据，而非叙事。** 每条记录均可追溯至可验证的内容，时间戳来自系统而非记忆。当记忆是唯一来源时，需说明。
- **错误修复是内容。** 合理但无效的修复应包含其合理性论证；尴尬不是保留政策。
- **严重程度来自组织分类法**，在使用的位置定义，而非假设。当不存在分类法时，明确标注未分配，而非自行创建。
- **行动项遵循 `writing-issues`**：结果、负责人、验收检查、记录并链接，绝不以散文形式存在于事后分析报告中。当无法从你的位置记录时，将每个项目标记为 `[待记录：<谁记录>]`；事后分析报告保持"起草"状态，直到链接存在。
- **一旦评审即不可变。** 新发现以日期标注的附录形式存在；重写的事后分析报告是伪造记录。评审本身记录在审批行（参见 `references/truth.md` 在核心技能中）。
- **险些发生的事件使用相同的框架**，Impact部分描述本会发生的情况，并标注其为反事实。

事后分析报告后做出的决策（新不变量、政策变更）通过 `recording-decisions` 记录并链接，而非嵌入。运行手册更新的事件通过 `writing-runbooks` 在与修复相同的变更中记录；文档是已完成工作的一部分，而非后续工单。
