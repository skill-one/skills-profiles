# 消除 AI 垃圾

AI 垃圾在特定方面显得**丑陋**：它堆砌了所有可能的风格和细节，却始终无法聚焦。渐变、光晕、吉祥物、表情符号、发光卡片墙，所有默认选项同时启用，直到每个产品都看起来像同一个花哨的模板。它在缩略图中看起来像是“设计过”的，但一旦有人仔细查看，它就土崩瓦解。你的工作是将它简化到人们真正会选择的东西。

你每次修复都必须遵循的原则：

1. **装饰前先决定。** 每个视觉选择都必须有解释。
2. **一个强调，一个声音。**
3. **从规模和空间建立层级。** 给文字上色或更换字体是一种捷径。
4. **先削减。** 向不那么丑陋迈出的第一步是移除东西。
5. **具体胜于响亮** 在文案中。
6. **装饰必须有意义** — 图标、徽章、标注是信号。

## 工作流程

按顺序遵循以下步骤。在用户看到报告之前不要进行批量编辑。

### 1. 范围
确认要扫描的内容。默认为应用程序/网站源代码（跳过 `node_modules`、`dist`、`build`、`.git`、`vendor`、锁文件、压缩文件）。如果项目混合了多个应用程序，请询问。

### 2. 扫描
运行捆绑的扫描器，它会通过代码库中的每个信号代码级别的指示来搜索，并打印分组后的 `文件:行号` 匹配：

```
node scripts/scan.mjs <根目录>          # 人类可读的报告
node scripts/scan.mjs <根目录> --json   # 机器可读的，用于分派
```

它是纯 Node.js（无依赖项）且永远不会编辑文件。将其输出用作起始地图，而不是福音 — 通过阅读代码来确认每个匹配项。

要缩小扫描范围：`--only=01,06` / `--skip=19` 按指示 ID 过滤，`--exclude=legacy` 会删除路径（在项目相对路径上匹配子字符串）。`--rules=extra.mjs` 加载额外的项目或语言特定的指示（`scripts/rules.ru.mjs` 是一个已发布的俄语文案示例，也是你自己的模板）。用户已确认的故意匹配项可以在源代码中使用 `deslop-ignore`、`deslop-ignore-next-line 06` 或 `deslop-ignore-file` 注释固定 — 优先使用 ID 范围的形式，以便新的指示仍然会浮现。

### 3. 分派
对于每个匹配项，打开文件并决定**垃圾 vs. 故意**。这是将这项技能与 lint 规则区分开来的步骤。渐变、衬线字体或表情符号可以是一个真实且受保护的选项。保留用户明显选择的东西（品牌标记、标志、有意为之的插图）。仅标记默认选项。

阅读 `references/taxonomy.md` 了解每个指示是什么以及为什么它看起来像机器制作的，以及 `references/detection.md` 了解确切的模式和它们的常见误报。

### 4. 报告
在更改任何东西之前，给用户提供一个分组摘要：每个指示、你确认的 `文件:行号` 匹配、一句话说明原因以及建议的修复。镜像格式：

```
垃圾  src/Hero.tsx:12   靛蓝→紫罗兰渐变        → 一个实色强调
垃圾  src/Hero.tsx:31   渐变剪裁标题        → 实色墨水，放大尺寸
垃圾  src/Note.tsx:8    border-l-4 标注 ×3         → 1 个 aside，其余是正文
垃圾  copy.md:1         "不仅仅是 X — 它是 Y"         → 具体说明
→ 4 组，11 个匹配项。
```

然后询问要应用哪些组，或者是否要全部进行。

### 5. 修复
应用最小的更改，以消除指示，同时保留意图和功能。使用 `references/fixes.md` 查找每个指示的 `之前→之后` 模式。

- 优先编辑共享标记/组件，而不是触摸每个调用位置。
- 永远不要发明新的品牌颜色；如果调色板必须更改，请提议中性色 + 项目的现有强调色，并让用户确认。
- 保持文案意义；使其具体，不要只是删除它。
- 修复后重新运行扫描器以确认计数减少，并记录任何故意保留的匹配项（并说明原因）。

## 安全措施

- **尊重作者。** 将不熟悉的文件和有意为之的装饰视为某人的选择。当不确定某物是否是垃圾时，请询问 — 不要去除它。
- **小而可审查的差异。** 永远不要重新格式化无关的代码。永远不要运行 `git add -A`；仅暂存显式文件，并保留他人的工作进度。
- **不引入新的依赖项**来做这项工作。
- **在可能的情况下进行视觉验证。** 如果存在开发服务器，请查看之前和之后；通过扫描通过并不是页面更好的同义词。
