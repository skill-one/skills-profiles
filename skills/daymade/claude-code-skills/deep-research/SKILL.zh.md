# 深度研究

创建具有严格格式控制、证据映射、来源管理以及多轮综合的高保真度研究报告。

## 架构：主代理 + 子代理

```
主代理 (协调器 — 最小化原始搜索上下文)
  |
  P0: 环境和来源策略设置
  |
  P1: 问题和主张映射 (决策问题、证据路径、停止规则)
  |
  派发 ──→ 子代理 A ──→ 编写 task-a.md ──┐
           ──→ 子代理 B ──→ 编写 task-b.md ──┤ (并行)
           ──→ 子代理 C ──→ 编写 task-c.md ──┘
  |                                               |
  |     research-notes/  <────────────────────────┘
  |
  P2: 构建证据包 + 引用注册表
  P3: 证据映射的提纲，包含反证和未知项
  P4: 从证据包中生成草稿；重新打开决定性原始资料
  P5: 反复审读 (主张、置信度、替代方案)
  P6: 验证每个承重主张和精确事实
  P7: 精炼 → 带置信度标记的最终报告
```

**上下文规范：** 将原始搜索结果噪声保留在任务工作区中。将证据包传递给主代理，包括定位器和简短的来源摘录。笔记是路由辅助工具，不是权威来源：主代理必须为每个承重主张、冲突主张以及报告中使用的精确数字/日期/引文打开原始来源。

## 运行和资产合同 — 每次调用

在外部检索之前，阅读 [research-asset-contract.md](references/research-asset-contract.md)。创建或恢复一个持久的项目研究**对于单路线和多路线研究同样适用**。搜索其明确的先前研究目录，打开相关的早期原始资料并记录重用/改编/拒绝的决定。在 `study.json` 中起草决策问题和提供者 × 实际模式通道。编写一个包含用户提供的种子 URL、命名实体以及验证代码或其他标识符的精确 `dispatch_context`。将那个字符串包含在**每个**通道提示中；[research_assets.py](scripts/research_assets.py) `start` 会拒绝遗漏。在对外派送之前，捕获用户的命名种子文章或文档作为原始资料，并在提供者无法读取其 URL 时遵循 [provider handoff](references/provider-run-contract.md#seed-source-handoff)。模型工作区可能不会因为协调器而看到用户的链接或本地文件。然后运行 `provider_runs.py plan`。在计划中保留每个用户请求的模式；一个不增加价值、不可用或缺乏付费授权的路线会得到一个有理由的 `deferred` 事件。一个由直接网络搜索和内部子代理汇编的报告仍然需要一个直接来源通道和相同的存档。

在研究过程中，保留未编辑的提供者输出、每个打开的原始资料以及每个提供者发现的来源 URL（状态和来源）。将报告主张绑定到批准的原始来源；模型报告仅定位候选证据。在调用报告完成之前，运行 `provider_runs.py validate`、`research_assets.py check`，并注册该研究以供后续发现。一个带有引用但没有研究/来源/主张记录的答案不能满足此技能。本地脚本记录和检查文件；它们不会进行提供者调用，也不会授权付费工作。

在发送可能自行选择数据插件的 Work/Agent 任务之前，检查相关的插件目录以查看每次调用的信用额度或费用。一个已登录的账户和一个使用数据源的请求不会设定无限制的支出上限。如果一个自主任务可以在没有每次调用暂停的情况下调用计费插件，而该任务没有明确的支出授权，则推迟该通道或使用可以首先批准确切调用的路线。即使有预算，提示也不是技术费用限制：当自主任务无法执行时，使用可控路线。在提供者提示中声明授权限制以供可追溯性，然后在执行后读取原始工具日志；如果超出边界发生费用，请记录观察到的使用情况并告知用户。不要进行另一次付费调用以填补覆盖差距。

## 模式选择

在开始之前确定研究模式：

| 维度 | 选项 |
|-----------|---------|
| **主题模式** | 企业研究 (公司/企业) 或 一般研究 (行业/政策/技术) |
| **深度模式** | 标准 (多个决策问题或争议证据) 或 轻量级 (一个有边界的问题和一个小证据表面) |
| **提供者模式** | 一个明确的单路线或提供者 × 模式计划。保留每个用户请求或项目接受的选定的模式或合理地推迟；当它们可以实质性测试决策时，选择额外的独立路线 |

- **企业研究模式**：以问题为导向的公司研究，仅在它们有助于回答决策时才选择可选的分析框架
- **一般研究模式**：带来源管理的标准 P0-P7 研究流程
- **深度选择**：根据未解决问题数量和后果选择，而不是提示长度、任务数量或目标字数
- **提供者选择**：当用户说“我们的方式”或调用命名的研究例程时，读取用户的既定工作流程。当它们添加一个独特的证据路线、结构化工具访问或一个有意义的挑战时，额外的模型报告是有用的。检查每个提供者的可用性、隐私边界和付费授权；不要在沉默中将请求的模式集减少为直接来源报告。默认情况下，不要运行所有可用路线或硬编码供应商名单。

## 来源管理 (V6)

### 来源可访问性分类

按可访问性对每个来源进行分类：

| 可访问性 | 定义 | 示例 | 使用规则 |
|--------------|------------|----------|------------|
| `public` | 任何外部研究人员都可以无身份验证访问 | 公共网站、新闻文章、WHOIS (无隐私)、学术论文 | ✅ 总是允许 |
| `semi-public` | 需要注册或有限访问 | LinkedIn 个人资料、Crunchbase 基本版、行业报告 (免费层) | ✅ 允许并披露 |
| `exclusive-user-provided` | 用户的付费订阅、私有 API、专有数据库 | Crunchbase Pro、PitchBook、私有数据源、内部数据库 | ✅ **允许** 用于第三方研究 |
| `authorized-first-party` | 用户授权的关于用户自己组织的记录、交易或工作 | 合同、发票、CRM 记录、会议记录 | ✅ 可能建立内部业务事实；标记来源 |

**第一方边界：** 用户授权的记录可以建立组织做了什么、同意什么、支付什么、交付什么或观察到什么。它们不作为市场地位、客户情绪、监管合规性或第三方主张的独立外部验证。永远不要将内部记录重新标记为外部发现。

**✅ EXCLUSIVE INFORMATION ADVANTAGE**: 您 SHOULD:
- 使用用户的 Crunchbase Pro 研究竞争对手
- 使用用户的专有数据库进行市场研究
- 使用用户的私有 API 进行投资分析
- 利用用户提供的任何专有来源进行第三方研究

### 来源类型标签

每个来源还必须带有：

| 标签 | 定义 | 示例 |
|-------|------------|----------|
| `official` | 主要来源、官方文档 | 公司 SEC 文件、政府报告、官方博客 |
| `academic` | 同行评审研究 | 期刊文章、会议论文、学位论文 |
| `secondary-industry` | 专业分析 | 行业报告、分析师覆盖、贸易出版物 |
| `journalism` | 新闻报道 | 可靠的媒体机构、调查性新闻 |
| `community` | 用户生成的内容 | 论坛、评论、社交媒体、问答网站 |
| `other` | 未分类或混合 | 聚合器、未验证来源 |

**覆盖诊断：** 跟踪来源数量、域名、来源类型组合和集中度以揭示覆盖不足。仅凭这些总数单独通过或失败研究。根据每个决策问题和承重主张是否具有适合目的的证据、是否寻求反证以及剩余未知项是否明确来设置门禁。

## AS_OF 日期政策

在 P0 中明确设置 `AS_OF` 日期。对于所有时间敏感的主张：
- 每个引用都包含来源发布日期
- 如果来源比相关时间范围旧，则降低置信度
- 为每个主张类别定义新鲜度时间范围并标记超出范围的材料；一个通用年龄截止日期仅是诊断

## P0：环境和策略设置

在开始之前检查功能：

| 检查 | 要求 | 缺失影响 |
|-------------|-------------|-------------------|
| 必要的证据通道可用 | 必要的 | 范围变窄或标记受影响的问​​题为未知 |
| 原始来源检索可用 | 对于承重主张是必要的 | 不要将摘要/片段提升为最终证据 |
| 子代理派发 | 优选的 | 降级为顺序 |
| 文件系统可写 | 必要的以完成 | 内存笔记可能支持部分调查；报告存档差距并使研究不完整 |

设置策略变量：
- `AS_OF`：今天的日期 (YYYY-MM-DD) - 对于有时间主题是强制的
- `MODE`：标准 (默认) 或 轻量级，由问题映射证明
- `SOURCE_TYPE_POLICY`：执行官方/学术/二级/新闻/社区/其他标签
- `COUNTER_REVIEW_PLAN`：每个初步结论会被推翻的证据

在设置提供者模式之前，运行 [research asset](references/research-asset-contract.md) 目录搜索。一个早期的模型总结是一个引导；在重用之前，重新打开其来源并检查新鲜度。

报告：`[P0 完成] 子代理：{是/否}。模式：{标准/轻量级}。AS_OF：{YYYY-MM-DD}。`

在研究特定公司时，使用专用工作流程按问题路由证据。将六个维度视为覆盖地图，而不是强制报告大纲。

### 企业工作流程概述

```
企业研究进度：
- [ ] E1: 摄入 — 确认公司实体、研究深度、格式合同
- [ ] E2: 问题引导的证据收集跨相关维度
  - [ ] D1: 公司基本资料 (实体、成立、融资、所有权)
  - [ ] D2: 业务和产品 (细分、产品、收入结构)
  - [ ] D3: 竞争地位 (行业排名、竞争对手、壁垒)
  - [ ] D4: 财务和运营 (3年财务报表、效率指标)
  - [ ] D5: 近期发展 (6个月事件、战略信号)
  - [ ] D6: 内部/专有来源 (或注明限制)
- [ ] E3: 可选的分析框架为决策选择 (或无)
- [ ] E4: 在每个阶段转换时进行主张/证据/未知项检查
- [ ] E5: 按用户请求的结构起草
- [ ] E6: 多轮起草 + UNION 合并 (与一般步骤 6-7 相同)
- [ ] E7: 提交草稿供人工审查和迭代
```

## P1：研究任务板

对于每个研究，使用便携式 [provider-run contract](references/provider-run-contract.md)：一个问题映射、精确提示，以及每个提供者 × 实际模式都有一个独特的 `lane_id`，包括使用直接原始来源路线时。在派发之前运行 [provider_runs.py](scripts/provider_runs.py) `plan`。当两个或多个提供者/模式通道被选中时，加载 [parallel-provider-ops.md](references/parallel-provider-ops.md) **在分叉之前** 并协调可用的提供者、浏览器/应用程序、检索和验证技能与独立代理。为每个控制表面分配一个所有者，并串行化该所有者的 UI 操作。不要在此技能中实现提供者调用或假设固定的供应商名单。
提前提交长异步任务并收集每个原始结果在其自己的通道下；通过其现有来源重新启动活动任务，而不是开始重复的付费工作。在实际派发之前，解决并读取每个通道的当前执行者技能，遵循其授权规则；本地规划器不会进行提供者调用。提供者的报告是 P3 的输入，而不是一个独立验证的来源。不要根据模型名称或报告长度推断正常聊天使用了原生 Deep Research；验证实际的 UI 或 API 路由。通过底层原始来源和决策值合成，而不是模型报告的投票。

将任务分解为决策问题。仅在单独的证据路线或专业知识使工作更清晰时创建任务。

每个任务分配包括：
- **专家角色**：专家角色 (例如，“政策历史学家”、“生态系统映射器”)
- **目标**：一句调查目标
- **查询**：2-3 个预计划搜索查询
- **深度**：DEEP (获取 2-3 篇完整文章) 或 SCAN (片段足够)
- **输出**：研究笔记文件路径
- **并行组**：组 A (独立) 或组 B (依赖于组 A)
- **决策问题**：该任务帮助回答的确切问题
- **承重主张**：会改变结论的初步主张
- **反证和未知项**：寻求了什么、发现了什么、还有哪些未解决

### 任务分解规则

1. 每个任务涵盖一个专家会拥有的连贯子主题
2. 组 A 任务在逻辑上必须是独立的；通过底层证据、所有权和激励来评估来源独立性，而不是领域计数
3. 每个并行组最多 3 个任务 (并发限制)
4. 每个任务都必须标记时间敏感的主张、寻求反证以及预期的引用老化风险

### 企业研究集成

在企业研究模式下，将问题映射到相关维度，而不是自动创建所有六个任务：
- 任务 A：公司基本资料 (实体、成立、融资、所有权)
- 任务 B：业务和产品 (细分、产品、收入结构)
- 任务 C：竞争地位 (行业排名、竞争对手、壁垒)
- 任务 D：财务和运营 (3年财务报表、效率指标)
- 任务 E：近期发展 (6个月事件、战略信号)
- 任务 F：授权第一方记录 (当它们可以回答业务事实时；永远不会计为外部证实)

报告：`[P1 完成] {N} 个任务在 {M} 个组中。正在派发组 A。`

## 企业研究模式 (专用管道)

在研究特定公司时，将每个决策问题通过相关企业维度路由。使用维度来找到缺失的证据路径；默认情况下，不要运行所有六个或添加量化框架。

### E1: 摄入

与上述 P0/P1 相同，加上：
- 确认正在研究的确切法律实体 (母公司 vs 子公司)
- 根据决策问题、证据难度和请求输出选择研究深度；页数是规划诊断仅
- 确定任何特定的比较目标 (基准公司)

## P2：派发 + 调查

子代理使用 [references/subagent_prompt.md](references/subagent_prompt.md) 执行任务，并以 [references/research_notes_format.md](references/research_notes_format.md) 格式输出证据包。

### 使用子代理 (Claude Code / Cowork / DeerFlow)

1. 并行派发组 A 任务 (最多 3 个并发)
2. 每个子代理搜索、获取并标记来源类型
3. 每个来源行包括 `Source-Type` 和 `As Of`
4. 等待组 A 完成
5. 派发组 B (可以读取组 A 笔记)

### 子代理输出要求

每个 task-{id}.md 必须包含：
- **问题状态**：已回答 / 相矛盾 / 未知，以及停止证据
- **来源部分**：来自实际检索的稳定定位器，包括来源类型、可访问性、日期和来源家族身份
- **主张-证据表**：主张、证据摘录/定位器、范围、置信度，以及是否打开原始资料
- **反证和未知项**：寻求了什么、发现了什么，以及还有哪些未解决

### 没有子代理 (降级模式)

主导代理按顺序执行任务，扮演每位专家。在最终证据包之外保留原始搜索噪声；在需要可复现性时，保留查询日志。

### 企业研究：六维收集

遵循 [references/enterprise_research_methodology.md](references/enterprise_research_methodology.md) 进行：
- 每个维度的详细收集工作流程（查询策略、数据字段、验证）
- 数据源优先级矩阵（P0-P3 排序）
- 特定主张的佐证与冲突处理规则

**关键原则**：
- 证据驱动：每个结论必须可追溯至可引用的来源
- 佐证：只有当第二来源独立于同一底层披露或数据集时，才增加权重
- 克制判断：明确标注推测，避免无依据的主张
- 结构化呈现：通过表格、列表、层级展示复杂信息

每完成一个维度后，运行 L1 质量检查（参见 enterprise_quality_checklist.md）。

每个任务的状态：`[P2 task-{id} 完成] {N} 个来源，{M} 项发现。`
全部任务状态：`[P2 完成] {N} 个任务完成，{M} 个总来源。正在构建登记册。`

### E3：仅在有价值时选择分析框架

仅当用户的决策能从框架中受益时，加载 [references/enterprise_analysis_frameworks.md](references/enterprise_analysis_frameworks.md)。使用 SWOT 进行战略选项框架化，使用风险矩阵处理具有明确概率/影响输入的决策，仅在权重和量表可辩护时进行评分。宁缺毋滥，不要编造条目或精度。

分析完成后，运行 L2 质量检查。

### E4：质量控制

来自 [references/enterprise_quality_checklist.md](references/enterprise_quality_checklist.md) 的三级检查：
- **L1（数据）**：来源数量、归属、交叉验证、时效性
- **L2（分析）**：决策问题覆盖范围、主张支持、反证、以及使用框架时的框架适用性
- **L3（文档）**：结构合规性、格式一致性、可读性、附录

### E5：使用企业模板起草

仅当 7 章节企业报告模板（来自 enterprise_quality_checklist.md）与所需决策匹配时，才使用该模板。否则，围绕问题图谱调整结构。
1. 公司概况
2. 业务与产品结构
3. 市场与竞争地位
4. 财务与运营分析
5. 风险与关注点
6. 近期发展
7. 综合评估与结论

外加附录：数据源索引、术语表、免责声明。

### E3-E7：企业分析、起草与审查

## P3：引用登记册 + 来源治理

主导代理阅读所有任务笔记并构建统一登记册。

将每个打开的来源和提供商展示的 URL 附加到研究的 `source-ledger.jsonl` 中，包括被拒绝和不可用的线索；在可用时存储原始字节。在 `claims.jsonl` 中绑定每个决策相关主张及其精确定位器到已批准的来源 ID。参见 [research-asset-contract.md](references/research-asset-contract.md)。下文中的编号报告引用登记册仍是面向读者的映射；它不替代持久的来源和主张记录。

### 登记册流程

1. 阅读每个任务文件的主张-证据表格和来源
2. 合并来源；去重 URL，但也将源自同一研究、备案、新闻稿、数据集、采访或赞助方的多个出版物分组为一个证据族
3. 按首次出现的顺序分配顺序 [n] 编号
4. 标记：source_type（来源类型）、accessibility（可访问性）、as_of 日期、evidence family（证据族）、authority（权威性）、independence limits（独立性限制）、以及 task id（任务 ID）
5. 构建主张覆盖矩阵：支持证据、反证、已检查的决定性原始来源、以及剩余未知项
6. 记录被排除的来源及其原因。不要仅因来源未通过任意评分而将其排除；将其限制在其能支持的主张范围内

### 登记册输出格式

```
引用登记册

已批准：
[1] 作者/组织 — 标题 | URL | 来源类型：official（官方） | 可访问性：public（公开） | 证据族：filing-123（备案-123） | 日期：2026-03-01 | task-a（任务a）
[2] ...

已舍弃：
x 来源 | URL | 来源类型：secondary-industry（二手行业） | 可访问性：public（公开） | 证据族：unknown（未知） | 原因：无法检索原始记录；摘要无法承载该主张

诊断信息：{已批准}/{总数}，{N} 个域，{N} 个独立证据族，来源类型组合
覆盖范围：{已回答}/{总问题数}；{N} 个承重大主张未解决
```

**关键规则：** 这些 [n] 是最终的。P5 仅能从已批准列表中引用。已舍弃的来源永远不会重新出现。

**授权第一方处理**：在研究用户自身组织或资产时：
1. 使用授权原始记录来处理其直接记录的内部业务事实
2. 将其标记为 `authorized-first-party`（授权第一方）并注明这是谁的记录
3. 仅当主张需要外部佐证时才寻求外部来源
4. 保持结论明确：内部确立、外部佐证、冲突、或外部未知

**专属来源处理**：当用户明确提供其付费订阅或私有 API 用于第三方研究时（例如，“使用我的 Crunchbase Pro 研究竞争对手”），你应当：
1. 接受其为“exclusive-user-provided”（专属用户提供）的可访问性
2. 将其作为竞争优势使用
3. 在登记册中正确引用
4. 如果不存在独立的等效来源，保留该来源有效的第一方范围，并将外部主张标记为未知

报告：`[P3 完成] {已回答}/{总问题数} 个问题已回答。{N} 个承重大主张已支持，{M} 个未解决。来源总数为诊断信息。`

### 处理信息黑箱

当研究对象没有公开足迹时：

**外部研究人员会发现：**
- WHOIS：隐私保护 → 无所有者信息
- 网络搜索：无新闻，无新闻稿
- 社交媒体：无公司页面
- 商业登记处：无公共 API 或需要本地访问
- 结果：**完全的信息黑箱**

**正确响应：**
```
发现：无公开信息可用

已检查来源：
- WHOIS（公开）：隐私保护 [失败]
- 公司登记处（公开）：访问拒绝/无 API [失败]
- 新闻媒体：无报道 [失败]
- 公司网站：仅占位符 [极少]

结论：从外部视角无法验证公司存在
找到的来源：0（或极少，例如，仅有 WHOIS 显示域存在）
置信度：N/A - 证据不足
```

**禁止事项：**
- ❌ 将内部确立的事实描述为独立的外部佐证
- ❌ 仅基于域注册假设公司存在
- ❌ 用推测填补缺失数据
- ❌ 当授权第一方记录直接确立内部业务事实时将其丢弃

**应当事项：**
- ✅ 清楚陈述外部研究人员可以/不能验证什么
- ✅ 将授权第一方事实作为内部确立的内容单独报告，与外部可见性分开
- ✅ 记录所有失败的搜索尝试
- ✅ 将主张标记为 [未验证] 或完全省略
- ✅ 当证据无法回答决策问题时缩小范围或停止
- ✅ 建议直接联系以进行尽职调查

## P4：证据映射大纲

主导代理阅读证据包 + 登记册以构建大纲，然后重新打开决定性原始来源。

1. 识别跨任务模式
2. 设计部分时以主题为先，而非以任务顺序为先
3. 将每个部分映射到带有来源编号的具体发现
4. 标记需要反证审查的部分
5. 用 AS_OF 检查标记时效敏感的主张
6. 将每个承重大主张标记为已支持/被反驳/未知

大纲格式：
```
## N. {部分标题}
来源：来自任务 a, b 的 [1][3][7]
主张：{来自任务-a 发现 3 的主张}, {来自任务-b 发现 1 的主张}
反主张候选：{替代解释}
时效检查：{来源日期 + AS_OF}
缺口：{有限的官方证据}
```

## P5：从笔记起草

使用 [references/report_template_v6.md](references/report_template_v6.md) 逐节撰写，将其适应用户格式契约。

**规则：**
- 每个事实主张都需要引用 [n]
- 数字/百分比必须有来源
- 为每个部分添加**置信度标记**：高/中/低并附理由
- 当证据冲突时添加**反主张句**
- 新来源仅能通过相同的登记册和验证路径进入
- 使用 [未验证] 标记无支持的说法

**反幻觉：**
- 主导代理绝不编造 URL；每个定位器必须来自实际检索
- 主导代理绝不将笔记视为证明；对于承重大主张、冲突、确切数字/日期和引文，重新打开原始来源
- 主导代理绝不捏造数据；无支持的主张保持未知或被省略

状态：`[P5 进行中] {N}/{M} 部分，~{字数} 字。`

## P6：反证审查（强制）

对每个主要结论，执行相反观点检查。这些检查并不自动要求另一个代理或团队；仅当用户请求或适用的工作区指令要求时使用独立审查者：

1. **结论可能是错误的吗？**
2. **哪些高影响主张依赖于单个证据族，即使许多域重复它？**
3. **哪些主张缺乏能够直接观察该事实的来源？**
4. **是否使用了过时的来源支持时效敏感的主张？**
5. **仅报告有证据支持的问题；零发现是有效结果。** 明确陈述未解决的 uncertainty。不要为了达到问题数量而编造问题或重复已完成的检查。

### 使用反证审查团队（可选）

为了全面的并行审查，使用反证审查团队：

```bash
# 1. 准备输入
counter-review-inputs/
  ├── draft_report.md
  ├── citation_registry.md
  ├── task-notes/
  └── p0_config.md

# 2. 并行分派给 4 个专家代理
SendMessage to: claim-validator（主张验证器）
SendMessage to: source-diversity-checker（来源多样性检查器）
SendMessage to: recency-validator（时效性验证器）
SendMessage to: contradiction-finder（矛盾查找器）

# 3. 等待所有专家完成

# 4. 发送给协调者进行综合
SendMessage to: counter-review-coordinator（反证审查协调者）
  inputs: [4 份专家报告]

# 5. 接收最终 P6 反证审查报告
```

详细用法参见 [references/counter_review_team_guide.md](references/counter_review_team_guide.md)。

### 手动反证审查（默认）

当未选择审查团队时，直接执行这些证据检查。如果用户请求或适用的工作区指令要求，获得个别独立审查：
- 对照决定性原始来源验证每个承重大主张
- 检查佐证来源是否真正独立且能够观察该主张
- 验证时效敏感主张的 AS_OF 日期
- 记录对立解释

### 输出

最终报告中仅包含有证据支持的争议。仅当此类争议存在时使用编号条目。如果未确立任何争议，明确陈述；切勿为了填充模板而捏造争议。单独报告未解决的 uncertainty，或陈述没有剩余 uncertainty。

```
## 核心争议 / Key Controversies
未发现有证据支持的核心争议。
未解决的不确定性：无。
```

上述示例仅适用于当这两个陈述都由已完成的检查支持时；否则列出实际的争议或未解决问题。

报告：`[P6 完成] 发现 {N} 个问题：{critical} 个严重，{high} 个高，{medium} 个中。`

## P7：验证

定稿前交叉检查：

1. **登记册交叉检查：** 列出报告中所有 [n] 与已批准登记册对比
2. **承重大检查：** 追溯每个决定性结论、确切数字/日期/引文和有争议事实至原始来源
3. **抽查低影响主张：** 仅将抽查用作诊断；当一个失败时，扩展到受影响的完整类别
4. **验证没有已舍弃的来源复活**
5. **检查关键主张的证据族集中度**

报告：`[P7 完成] {N} 次抽查，修正了 {M} 个违规。`

在 P7 之后运行研究的最终资产检查和目录注册。如果选定的通道仍保持活跃，或某个来源缺乏有效的原始/定位器，则报告该研究为不完整或有界限，而不是呈现完成的深度研究运行。

## 反模式

- 没有并行完整路径的单遍起草
- 按部分而不是完整报告草稿拆分路径
- 忽略格式契约或用户模板
- 没有引用或证据表格映射的主张
- 混合冲突日期而没有指出差异
- 未经验证地复制外部 AI 输出
- 删除中间草稿或原始研究输出
- **主导代理信任笔记为权威** — 使用证据包进行路由，然后重新打开决定性原始来源
- **编造 URL** — 仅使用来自实际搜索结果中的 URL
- **复活已舍弃的来源** — 在 P3 中舍弃的永远不会重新出现
- **时效敏感主张缺失 AS_OF** — 始终包括来源日期
- **跳过证据检查** — 完成 P6，仅报告有支持的结果，当没有确立问题时允许零问题。
- **第一方过度主张** — 授权记录可以确立内部业务事实，但不能冒充外部验证
- **忽略专属来源** — 当用户提供 Crunchbase Pro 等进行竞争对手研究时，使用它
