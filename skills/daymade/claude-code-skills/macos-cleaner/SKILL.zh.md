# macOS 清理工具

诊断磁盘压力的实际来源，仅回收经批准的空间，并证明清理操作未损坏用户数据或共驻服务。

## 入口路由

选择能回答请求的最窄路径：

| 用户信号 | 路径 |
|---|---|
| Apple 内容缓存、`AssetCacheManagerUtil`、`CacheUsed`、`ActualCacheUsed`、iCloud 缓存或“需要更多缓存空间” | 在探测或提议命令前，完全阅读 `references/apple_content_caching.md` |
| Docker、OrbStack、镜像、容器或卷 | 阅读 `references/docker_analysis.md`；检查每个对象，并永不使用 prune-family 命令 |
| Docker 构建缓存 | 使用 `docker builder du` 进行测量；此技能报告它但不会删除它，因为 Docker 提供的是跨类别的 prune 控制，而不是逐条记录的意图 |
| Chrome、ChromeDriver、Playwright、Codex Computer Use、Edge 或 Chromium 拥有大型 `*.code_sign_clone` 目录 | 完全阅读 `references/chromium_code_sign_clones.md`；使用捆绑的分析器分离活动、非活动和未知的确切子项，并永不将 `du` 等同于物理释放 |
| 已知名称的缓存、目录、应用程序或服务已经是嫌疑对象 | 首先检查该目标，并阅读 `references/cleanup_targets.md` 中匹配的语义；不要开始家目录或全盘扫描 |
| 用户询问最近增长或填充磁盘的内容，自由空间在两次读取之间下降，或存在旧的扫描导出（GrandPerspective 文本导出、保存的 `du` 输出） | 阅读 `references/growth_attribution.md`；使用 delta 表格回答，表格的行命名其作者，而不是大小排名 |
| 来源确实未知 | 使用以下通用分析工作流；Mole 是可选的，不是通用的第一步 |

用户提供的范围排除项会覆盖所有通用扫描建议。当用户排除它们时，不要检查个人目录、凭证、数据库、应用程序状态或不相关的服务。

## 安全和授权协议

1. **将观察与变异分开。** 首先完成只读诊断。不要删除、停止服务、编辑设置、安装或升级工具，或在该阶段运行可能改变状态的清理预览。
2. **确认确切目标。** 在远程 Mac 上，在任何其他工作之前记录当前主机身份。永远不要从 IP、旧 PID、目录名称或先前报告中推断机器。
3. **计划后再询问。** 在任何状态更改之前，列出每个命令、它更改的内容、预期的物理空间回收、影响、可恢复性以及后置条件。然后，如果用户请求仅计划阶段，则停止。
4. **要求明确批准。** 如果用户提供了一个确切的确认短语，则需要该短语。否则，要求对列出的命令和目标给出不可混淆的批准。对一个计划的批准不会授权回退或更广泛的清理。
5. **使用精确的受支持控制——并在运行前检查它们是否存在已知缺陷。** 优先选择应用程序的受支持的缓存管理命令或确切的对象 ID。“官方”和“精确”不是安全性的证据，因此在使用第一个受支持控制命令之前，在安装的版本上对该确切命令进行已知问题检查：在工具的问题跟踪器中搜索命令名称，加上其发布说明中在安装版本之后的修复。具有开放、与版本相关的缺陷的命令不是此技能的受支持控制——将其视为下一规则中的跨类别命令，要么升级以绕过该修复，要么使用确切的路径替代方案。如果不存在受支持控制，只有在验证其所有者、确认应用程序已停止或目录以其他方式非活动、解释重建/重新下载的影响并获得批准后，才能删除确切属于应用程序的缓存目录。永远不要针对广泛的缓存根或活动的应用程序状态。
6. **永远不要使用 Docker prune-family 命令。** 这包括图像、容器、卷、系统、构建器和 buildx prune。跨类别的删除不能表达逐对象的用户意图。
7. **避免使用广泛的破坏性 shell 形式。** 不要建议或执行广泛的 `rm -rf` 或 glob 删除。对于确切批准的普通文件，优先使用 Finder 垃圾箱。捆绑的遗留辅助工具永久删除，并且只有下面记录的有限保护措施；永远不要将其视为等同于垃圾箱。
8. **保留有价值的状态。** 不要仅为了增加报告的节省而针对用户文档、凭证、SSH 材料或活动数据库、应用程序配置或运行服务状态。在执行任何文件删除之前，请阅读 `references/safety_rules.md`。
9. **执行遵循用户的授权。** 如果用户仅请求分析或想亲自运行命令，请转交命令。如果用户要求代理修复机器并明确确认了范围计划，则执行确切的批准命令并验证它们。未经单独批准，不要编写或启用无人值守的定期删除逻辑。
10. **快速失败。** 意外的非零命令、不匹配的后置条件、意外的目标或更改的依赖关系会停止清理。在决定它们是失败之前，解释记录的探测状态，例如 `lsof` 退出状态 1 且输出为空。报告部分状态；不要临时制定回退方案。
11. **在承诺任何删除的物理释放之前，命名机制——并从创建命令而不是猜测中获取它。** `df` 之间的名义 `du` 总和和实际回收之间的差距意味着某个候选机制正在工作，**最强证据是创建该文件夹的逐字命令**，因为复制动词单独决定了空间语义。在理论化之前，在会话历史中找到它；基于文件夹名称或大小推断不是机制。只有在找不到命令的情况下，差距才会保持 `unknown`——不要用最可能听起来的机制来替代你可以证明的机制。

    机制由 `du` 报告的内容和删除释放的内容区分（所有四个测量日期为 2026-09-19，1 GiB 源，漂移控制）：

    | 创建方式 | `du` 名义 | 删除副本释放 | 指纹 |
    |---|---|---|---|
    | `cp` (裸) / `cp -a` | 完整，按路径计数 | 完整 | 独立的 inodes，独立的 extent |
    | **`cp -c` / `cp -cR`** (clonefile) | **完整，按路径计数** | **≈0** | **不同的 inode，`nlink=1`，共享 extent** |
    | `ln` / `cp -l` (硬链接) | **计数一次**——兄弟读取 `0` | **≈0** | **相同的 inode，`nlink=2`** |
    | 本地 APFS 快照 | 完整 | ≈0 直到快照被精简 | `tmutil listlocalsnapshots /` |

    此表存在是为了避免两个陷阱。**克隆文件和硬链接行在 `du` 上相反但在删除时相同**——两者都释放 ≈0，所以“删除它释放了 nothing”不能将它们区分开，而 `du` 可以：硬链接的兄弟计数一次（或作为 `0`），克隆文件的副本计数完整。并且**使用错误的复制动词证明不了任何东西**：由于探测使用了裸 `cp`，而文件夹是用 `cp -cR` 构建的，因此 98 GiB 的差距被错误地归因于错误的机制。在执行任何删除之前，使用与创建命令相同的标志运行探测。克隆文件值得标记为常见情况——macOS `cp` 默认为 `-c` 使用它，并且为交付/套件复制的目录通常带有它。

## 阶段协议

使用此状态机进行每次清理：

1. **观察——只读。** 捕获身份、磁盘基线、疑似子系统状态和配置、物理分配和关键服务健康。
1b. **在不可避免时授权状态ful 观察。** 如果需要更深入的证据需要创建临时容器、拉取图像、挂载卷或写入快照，首先完成元数据观察，列出确切的观察命令及其副作用，并获得单独批准。观察批准不是清理批准。
2. **计划——无变异。** 首先通过 Phase 2 入口门（四步：目标确认、分类表、门规则、检查器——见下文），然后解释发现、命令、影响、恢复、预期释放和成功标准。在确认门停止。
3. **执行——仅批准范围。** 在执行前立即重新读取实时状态，然后单独运行每个批准的命令并检查其退出状态和后置条件。
4. **验证——独立重读。** 再次测量磁盘空间和子系统状态，重新检查受保护的服务，并观察足够长的时间以检测立即填充。

不要将阶段 2 和 3 压缩为一条消息。打印在清理命令旁边的计划不是确认门。

## Phase 1：只读诊断

### 建立基线

至少捕获：

```bash
/bin/date "+%F %T %Z %z"
/usr/sbin/scutil --get ComputerName
/usr/sbin/scutil --get LocalHostName
/usr/bin/sw_vers
/bin/df -k /System/Volumes/Data
/bin/df -h /System/Volumes/Data
```

使用 `df -k` 进行计算，使用 `df -h` 进行人类可读报告。将扩展、标签或旧报告视为提示，直到实时命令确认它。

在未知来源扫描之前建立成功目标。精确复制用户提供的自由空间或容量目标。如果用户未提供，请报告当前值并要求 GiB、容量百分比或两者为目标的值；不要编造一个。命名嫌疑诊断可以继续而没有清理目标，但有序的未知来源扫描不能在目标明确之前声称停止条件。

保持此第一阶段只读。不要运行 `scripts/cleanup_report.py`：它会创建本地状态目录和快照文件。将命令输出保存在报告中。在远程目标上，始终在该主机上运行直接的 `df` 命令；本地辅助工具必须不能错误地测量控制器 Mac。

### 在广泛扫描之前遵循命名嫌疑

- 查询子系统自身的状态和设置。
- 在权限和用户范围允许时，仅在确切的路径上使用有边界的 `du` 测量物理分配。
- 区分逻辑内容大小、稀疏文件表观大小、可清除空间和物理分配的字节。
- 对于 APFS 克隆，将 `du` 标记为路径计费或名义而不是物理：共享 extent 可以归因于每个路径，因此实际释放直到删除和 `df` 重读时才未知。
- 对于疑似增长的日志，在两个或多个时间戳记录确切的文件大小。一个大型文件或一个最近的 mtime 不足以证明持续增长。
- 捕获用户标记为关键的所有共驻服务的当前进程、监听器、启动机制和支持的健康探测。在每个检查点重新解析 PIDs。

如果已知嫌疑单独可以满足用户的自由空间目标，则不要扫描“以防万一”无关的个人或开发目录。

### 当来源未知时的通用分析

运行能识别足够物理空间以满足目标的最小有序序列。只有在具有受支持的精确操作和可辩护的预期物理释放的候选者可以满足它时才停止。原始分配总计、逻辑缓存大小、共享 Docker 层、垃圾箱移动和未经验证的“潜在节省”不满足停止条件。

不要让物理置信度排名隐藏用户最大的可见热点。当名义/路径计费候选者大于推荐操作时，显示两个数字并解释其物理释放的不确定性。
按可辩护的物理释放、安全性和努力排名；将名义大小报告为单独的列，而不是将其无声地视为零或完全可回收。

| 顺序/信号 | 只读操作 | 停止或继续 |
|---|---|---|
| 1. 总是 | 捕获身份和 `df -k/-h`；列出用户排除项 | 在目标不匹配时停止 |
| 2. 缓存/日志压力，以及 `~/Library/Caches`、`~/Library/Logs`，以及 XDG 开发缓存被批准为只读范围 | `uv run scripts/analyze_caches.py --user-only --include-dev` | 当测量的候选者可以满足目标时停止 |
| 3. 开发工具存在并且脚本的固定范围被批准 | `uv run scripts/analyze_dev_env.py` 读取 Docker/包管理器以及现有的 `~/Projects`、`~/workspace`、`~/dev`、`~/src` 和 `~/code` 根 | 将 Docker/OrbStack 结果路由到其专用参考；当任何固定根超出范围时跳过此辅助工具 |
| 4. 未安装应用程序的残留物合理并且其固定根被批准 | `uv run scripts/find_app_remnants.py` 读取 `/Applications`、`~/Applications` 和四个记录的 `~/Library` 应用程序状态根 | 将每个结果视为候选者，永远不会证明已放弃；当该范围未批准时跳过 |
| 5. 一个内容路径被明确批准 | `uv run scripts/analyze_large_files.py --threshold 100MB --path "<approved-path>"` | 不要用 `~`、下载、文档或数据卷根来替代未批准的路径 |
| 6. 在有边界检查后仍然未知，并且用户明确批准了 Mole 的固定广泛扫描根 | 阅读 `references/mole_integration.md` 并通过 TTY 使用 `mo analyze` | Mole 不能接受任意的路径范围；当批准比其记录的根更窄时跳过它 |

一个 `<approved-path>` 是用户命名或在其范围描述后明确接受的精确路径。如果不存在，则跳过大文件和重复内容扫描，说明此证据分支未经授权，并继续使用非内容承载证据。除非用户单独授权该更改，否则不要在只读阶段安装或升级 Mole。

Mole 的分析器扫描一组固定的内容，包括家目录、应用程序数据、系统库、应用程序和卷。在结果中的导航不会使底层的扫描路径受限。如果该广泛的读取范围未批准，则不要运行 Mole；使用已收集的边界证据停止或请求缺失的扫描授权。

对于明确批准的重复文件调查，请阅读 `references/cleanup_targets.md` 中的“可选重复文件”部分。它是只读的，并且永远不会使用自动删除选项。

**大数据文件夹不是缓存——提议其删除需要一个证据链，而不是大小排名。** 当发现一个大项目资产/媒体/数据集目录（不是缓存，不是应用程序残留物）时，不要仅凭大小将其放入操作集：阅读 `references/proving-redundancy-before-deletion.md` 并爬上它的梯子（文件级重复→创建来源→引用检查→会话历史工具调用普查→.DS_Store 手动使用跟踪→项目的决策记录）之前不要提议任何东西。交付物是证据表；无法证明的行（纯粹手动使用）交给用户，永远不会用听起来最合理的机制来掩盖一个你可以证明的机制。

当发现被扩展到子代理时，每个代理只返回候选者和测量值——分类、接受和提议发生在运行 Phase 2 入口门的会话中。子代理的清单是分类表的输入，永远不会是计划。

### Docker 和 OrbStack

在报告 Docker 节省之前，请阅读 `references/docker_analysis.md`。单独列出每个图像、容器和卷；检查引用和类似数据库的内容；使用实际的稀疏文件分配而不是表观大小。报告为悬挂的资源不是其数据无价值的证据。构建缓存测量受支持，但构建缓存删除故意超出范围，因为可用的 Docker 控制是 prune-family 操作。

一个真实的2026-09-19运行严格遵循了第一阶段机械操作，仍然发送了三个有问题的计划：它提议将npm `_cacache`、Playwright浏览器、Homebrew等默认保留缓存作为“低风险组合”，因为规则存在于`references/cleanup_targets.md`文件中——发现工作流永远不会打开该文件；它提议`uv cache prune`作为零影响，仅根据`--help`行和大小比例，从未验证语义或安装版本；并且它将2 GB的项目与一个91 GB的候选项目并列，因为没有设置空闲空间目标。将捕获所有三个问题的规则已经存在于这项技能中——在一个该程序从未打开的参考文件中，这使得它们在实际中不是规则。散文清单只是它所总结的参考文件的一个级别更好：对这道门的第一稿的独立审查发现了十三个阻塞缺陷，最深层的是这道门本身没有机械执行。因此，步骤4是一个脚本，而不是一个承诺——运行它，否则计划不存在。

1. **确认空闲空间目标。** 一个命名嫌疑诊断可以在没有目标的情况下继续（第一阶段豁免）；一个未知来源的扫描则不能——如果用户没有提供，请在排名前询问。没有目标的扫描没有停止条件，并且会产生按大小排序的噪音。
2. **打开`references/cleanup_targets.md`**并将发现产生的每个候选项目分类到该表中，写入文件（步骤4解析它）：

   | 目标 | 标称大小 | 物理置信度 | 类别 | 统治规则（逐字引用） | 预期物理释放+基础 | 恢复成本 | 裁决 |
   |---|---|---|---|---|---|---|---|
   | 精确目标：路径、服务设置（例如`AssetCacheManagerUtil`或plist键），或支持的控制（例如`chrome://settings/clearBrowserData`） | du输出 | 路径会计（第一阶段对APFS共享或标称du的标签）/稀疏感知/引擎报告（子系统自己的会计，例如Docker `system df`）/未知——永远不会输入标称数字作为释放 | 保留 / 可提议 / 可重建 / 用户数据 / 用户决策 | 来自`cleanup_targets.md`的引用、该路由的专用参考或这项技能自己的SKILL.md（检查器将每个引用与整个包进行比对并打印每个文件的来源，因此仅SKILL.md的引用保持可见）；"未找到规则"本身就是一个发现 | 估计及其推导方式；未知是一个允许的值 | 重新下载/重建成本，或n/a | 在行动集中 / 不在行动集中 / 由用户解锁（引用方向） |

   - **保留**——`cleanup_targets.md`中保留默认表的每一行（在本步骤中打开并引用在表中——步骤4验证引用，因此虚构的引用会失败）。除非（a）存在已验证从未使用的证据为目标，或（b）用户明确命名该目标进行清理并了解成本。接受你声明的成本不是（b）：用户必须自己命名目标。
   - **可提议**——已验证从未使用的证据（一个已死的项目、明确的用户声明、工件检查）。大小比例不是证据："缓存持有586个环境，28个项目venv存在"证明不了其他558个。
   - **可重建**——不在保留默认表中，有支持的管理命令或廉价重建（Homebrew、pip），行中声明了恢复成本。
   - **用户数据**——永远不会在行动集中；报告位置，而不是命令。
   - **用户决策**——由用户的流程或所有权知识决定；询问，不要提议。也是没有参考涵盖的目标的归宿（"未找到规则"）：计划在提议它们之前会询问。

   如果没有任何参考涵盖目标，则说"未找到规则"并将其分类为USER-DECISION——不要将不相关的规则扩展以涵盖它。

3. **应用门规则。** 步骤4的检查器机械地执行每一条规则——这就是它们成为规则而不是提醒的原因：
   - 行动集包含正好是标记为"在行动集中"的行加上标记为"由用户解锁"的行，并引用了用户的方向。任何可能改变状态的命令都不能命名表中没有的目标。保留行只能通过从未使用的证据或明确的用户方向（步骤2）进入行动集。
   - 计划以持有最大预期物理释放的行开始——除非表将另一行标记为用户可见的热点或瓶颈（磁盘压力实际关注的东西）并说明原因。任何其他引导行都会失败这道门；那是小鱼失败，而不是保守主义。永远不要仅按标称大小排名：标称不是释放，对于共享扩展候选，释放直到删除和`df`回读（步骤2的标签）才未知。
   - 每个破坏性命令记录：拥有工具的安装版本（对于应用程序控制或服务命令，是拥有应用程序或服务）；语义来源（工具自己的帮助或文档——如果唯一可用来源是这项技能的转录，请说明并廉价地与实时工具进行验证）；对于类别范围的命令——范围是一个对象类的整个类别，没有按对象选择；这项技能现有的术语是prune-family——一个已知问题检查。`uv cache prune`、`npm cache clean`、`brew cleanup --prune`和Docker prune系列按定义是类别范围的。
   - 这项技能声明为不认可的命令（`uv cache prune`、`npm cache clean`、Docker prune系列）即使在其他所有规则都通过时也不能出现在行动集中——无论大小如何，无论版本如何。`npm cache clean`加入列表，因为它会整批清除保留默认的`_cacache`。只有明确的用户指令才能移动它，并且它在第三阶段作为定向动作运行，永远不会作为提议。
   - 行动集为零行是一个合法结果：交付排名决策列表（保留和USER-DECISION行及其解锁成本和证据），并询问用户要解锁哪个。一个空的行动集与决策列表通过；编造行或降低保留到填充它是不行的。

4. **将计划写入文件，然后在发送前运行检查器：**
   ```bash
   uv run scripts/check_gate_plan.py --table <gate-table.md> --plan <plan.md>
   ```
   必须退出0。检查器验证：表存在并分类候选；每个统治规则引用都逐字出现在参考中（这就是强制打开参考的原因——虚构的引用会失败）；检查器识别的每个破坏性命令都有其声明的目标与表行匹配（未识别形式的命令被计数并报告，永远不会被沉默地忽略）；行动集遵守类别和解锁规则，包括保留默认的交叉检查；没有类别范围的命令位于行动集中；引导行遵守排名规则；每个破坏性命令都携带其工具验证。失败的运行会命名违反的规则——修复计划；不要削弱检查器。

报告观察到的值而不是推断的属性。使用`references/report_templates.md`进行长格式布局，并为每个提议的行动包括这些字段：

| 字段 | 必要内容 |
|---|---|
| 当前状态 | 时间戳、目标身份、磁盘使用/空闲/容量和子系统状态 |
| 证据 | 命令和观察值；声明数字是逻辑的还是物理的 |
| 精确命令 | 会改变状态的命令，带有精确目标或对象ID |
| 变化 | 命令修改或删除的内容 |
| 可恢复性 | 可逆命令、废纸篓恢复、备份恢复或仅重新下载 |
| 预期释放 | 带单位和假设的物理空间估计 |
| 服务影响 | 用户可见效果和保护服务的不变量 |
| 后置条件 | 在行动被成功调用前必须为真的值 |

按后果分类发现，而不是按数字有多诱人：

- **可重建缓存**：删除只会丢失本地副本，但声明重新下载或重建成本。**可重建不是默认可提议的**：`references/cleanup_targets.md`中的保留默认表（在第二阶段入口门的条目中打开并引用）决定；这些目标直到从未使用的证据或明确的用户方向移动它们之前都不会进入行动集。
- **需要用户决策**：值取决于用户的流程或所有权知识。
- **保留**：用户数据、凭证、数据库状态、活动配置或任何角色不确定的内容。

仅仅因为软件可以重新生成缓存，就不要称其为“绝对安全”。重新生成时间、带宽、身份验证和离线可用性都是真实成本。

## 第三阶段：执行确认的计划

在第一个状态改变命令立即之前：

1. 再次确认目标身份和当前磁盘状态。
2. 再次查询对象或子系统状态；清理计划在实时状态变化时过期。
3. 再次检查保护服务健康。
4. 将批准的命令和精确目标集与即将运行的命令进行比较。任何更宽或不同的目标集都需要新的批准。一个单独保留的项目变得不活跃时，只要它仍然被明确排除并且批准的目标集哈希仍然匹配，计划就不会失效。

如果批准的计划包括创建本地前后报告工件，现在捕获快照，在批准后和第一个清理命令之前：

```bash
uv run scripts/cleanup_report.py --snapshot before
```

这会在`~/.macos-cleaner`下写入，因此请在计划中列出它。它是可选的，仅限本地目标；直接`df -k/-h`读取仍然是真相来源。永远不会在控制器Mac上运行它作为替代远程目标测量。

一次运行一个状态改变命令。在发送下一个命令之前读取结果。每次命令后，运行可以区分成功和部分成功的后置条件。

对于不是用户数据、应用程序状态、数据库或受保护路径的精确普通文件，在用户确认精确路径后，优先选择可恢复的Finder废纸篓移动：

```bash
/usr/bin/osascript \
  -e 'on run argv' \
  -e 'tell application "Finder" to delete (POSIX file (item 1 of argv))' \
  -e 'end run' -- "<exact-path>"
```

移动到废纸篓通常在废纸篓被清空之前不会释放物理空间；在计划中说明这一点。`scripts/safe_delete.py`是一个遗留永久删除辅助工具，具有交互式提示和有限系统/凭证拒绝列表。它不会移动到废纸篓，不会检查每个用户数据根，不会检测打开的文件，或独立证明回收的字节。只有在精确的非用户数据目标和不可逆删除被明确批准时才使用它：

```bash
uv run scripts/safe_delete.py <exact-path> [<exact-path> ...]
```

不要使用此辅助工具处理用户文档、应用程序管理的缓存（例如Apple Content Caching）、数据库、凭证或任何角色不确定的目标。

两个窄Finder废纸篓分支在没有削弱这些排除的情况下仍然可用：

- 对于一个精确的未使用应用程序缓存，没有经过验证的支持管理控制，请遵循`references/cleanup_targets.md`中的命名缓存发现/使用协议，说明重建成本，并获得对该精确缓存路径的明确批准。
- 对于精确批准的用户数据根内的重复文件，首先显示每个重复集的大小/哈希和每个路径。用户必须命名要保留的副本和每个要删除的副本。仅将确认的文件移动到Finder废纸篓；永远不要使用永久辅助工具、自动重复选择标志、`all`、glob或目录级目标。验证移动到废纸篓的源路径，并说明物理空间只有在废纸篓被单独审查和清空时才会释放。

## 第四阶段：验证和观察

验证必须涵盖批准计划的所有条款：

- 重新读取`df -k`和`df -h`；从前后读取计算回收空间，而不是从删除工具的声明中计算。
- 重新查询清理的子系统的激活、配置和物理使用。
- 重新解析每个保护服务的PID、监听器、启动机制和健康探针。健康的磁盘并不能证明服务存活。
- 在有界间隔内观察，当APFS会计可能滞后或源可能重新填充时。记录每个时间戳和值。
- 如果错过了空闲空间目标，停止所有删除。开始第二次只读分析，并按测量的物理分配对剩余来源进行排名。

在仅知道命令退出代码时，永远不要报告“已修复”。成功的清理需要预期的状态和保护不变量。

对于其前后快照由辅助工具捕获的本地目标，使用以下内容生成比较：

```bash
uv run scripts/cleanup_report.py --snapshot after --compare
```

## 不要使用这项技能当

- 目标是 Windows 或 Linux。
- 所请求的操作需要禁用 SIP 或绕过 macOS 保护。
- 用户要求进行无声或自动删除，且没有可审计的范围和确认关卡。
- 该任务仅需调整应用程序行为，没有磁盘空间诊断或恢复目标。
