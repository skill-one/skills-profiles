# OWASP 安全

在编写或审查代码时，请应用这些标准。对于审查，请遵循以下工作流程。

**参考文件**（仅阅读与任务相关的部分）：
- [`reference/review-checklist.md`](reference/review-checklist.md)：每个 OWASP Top 10 类别的覆盖清单，以及 LLM 和代理检查。在审查的步骤 3 中阅读。
- [`reference/languages.md`](reference/languages.md)：针对 20 多种语言的不安全/安全示例的按语言划分的陷阱。阅读正在审查的语言的部分。
- [`reference/config-and-supply-chain.md`](reference/config-and-supply-chain.md)：Dockerfiles、Kubernetes、Terraform、框架配置、安全头、锁文件和 CI/CD 中的 A02 和 A03。当更改涉及配置、IaC、依赖项或管道时阅读。
- [`reference/owasp-report.md`](reference/owasp-report.md)：每个 OWASP Top 10:2025、ASVS 5.0、LLM Top 10 和 Agentic 项目的攻击向量、缓解措施和工作示例。大约 1100 行：跳转到您需要的部分。

## 安全审查工作流程

将此清单复制到您的回复中，并随着您的进行进行勾选：

```
安全审查进度：
- [ ] 步骤 1：映射入口点和信任边界
- [ ] 步骤 2：加载此代码需要的参考
- [ ] 步骤 3：扫描候选问题
- [ ] 步骤 4：对每个候选问题进行分诊
- [ ] 步骤 5：报告发现
```

**步骤 1：映射入口点和信任边界。** 列出攻击者控制的数据进入的地方：
路由和处理器、头部和 Cookie、上传、Webhooks、队列消费者、CLI 参数、第三方 API 响应，以及 LLM 读取或返回的任何内容。注意身份验证和授权的实施位置；它通常集中在中件件中，而不是每个路由。

**步骤 2：加载此代码需要的参考。** `languages.md` 的语言部分；如果配置、IaC、依赖项或 CI 发生更改，则加载 `config-and-supply-chain.md`；如果代码调用模型或运行代理，则加载 `owasp-report.md` 的 LLM 和 Agentic 部分。

**步骤 3：扫描候选问题。** 遍历 `review-checklist.md` 中代码触及的类别。对于每个候选问题，从步骤 1 中的入口点跟踪路径到接收器。

**步骤 4：使用“报告发现之前”中的标准对每个候选问题进行分诊。** 丢弃未通过标准或降级为纵深防御的候选问题。如果候选问题的可达性不明确，请在决定之前回到步骤 1 以检查该输入。

**步骤 5：按照以下格式报告发现，最高严重性优先。**

## 报告发现之前

模式匹配不是漏洞。自动化安全审查中最常见的失败模式是报告无法到达或已缓解的代码，这会掩盖真正的发现。在报告之前，请确认以下四个方面：

1. **输入是否实际上由攻击者控制？** 追溯到真实的入口点：请求参数、头部、Cookie、上传的文件、Webhooks、队列消息或第三方 API 响应。仅来自常量、枚举或受信任的内部配置的值不是注入源。
2. **使用该输入是否可以到达接收器？** 检查验证、白名单、ORM 或框架级控制是否已经位于它们之间。在将路由标记为缺少授权之前，查找身份验证中件件（`middleware.ts`、`proxy.ts`、Express/Django/Rails 中件件、基础控制器、装饰器）。
3. **影响范围是什么？** 谁可以触发它，他们能得到什么，以及它是否跨越了信任边界？到达云元数据的 SSRF 与仅到达 localhost 的 SSRF 不同。
4. **攻击者是否可以执行每一步？** 利用的每一步都必须从攻击者的位置可能实现。符号链接竞争需要在服务器上创建符号链接的方法；头部攻击需要一个可以设置该头部的客户端。如果某个步骤需要代码未显示攻击者拥有的功能，则发现结果为“需要验证”，而不是高。

按可利用性报告严重性，而不是按模式。说明具体路径（*此输入到达此接收器*），并在发现是理论上的或纵深防御而不是直接可利用时明确说明。如果从可用的代码中无法确定可达性，则不要断言任何一方。

## 报告格式

每个发现一个代码块，最高严重性优先：

```
[严重性] 标题 (CWE-###, OWASP A##:2025, LLM## 风险名称, ASI## 风险名称)
位置：   path/to/file.ext:LINE
路径：       <入口点> -> <中间跳转> -> <接收器>
影响：     谁可以触发它，他们能得到什么，它跨越了哪个信任边界
修复：     具体的更改，当不明显时附带代码片段
置信度：   已确认 | 可能 | 需要验证（说明您看不到的内容）
```

用其风险名称报告每个 LLM 和 ASI ID，例如 "LLM03 过度代理"。裸 LLM ID 是模糊的：2025 年和 2026 年的版本使用相同的数字表示不同的风险。

| 严重性 | 含义 |
|---|---|
| 关键 | 未身份验证的远程代码执行、身份验证绕过或大量数据暴露 |
| 高 | 身份验证利用跨越信任边界（IDOR 到其他租户、登录后的 SQLi） |
| 中 | 需要非正常先决条件，或影响仅限于攻击者自己的数据 |
| 低 | 纵深防御差距，没有证明的利用路径 |
| 信息 | 强化建议；明确说明它不是漏洞 |

如果审查未发现可利用的内容，请直接说明。不要用信息项填充报告以使其看起来全面；长列表会导致真正的发现被忽略。

## OWASP Top 10:2025

三个类别从 2021 年起被重命名，两个类别是新的（A03、A10）。使用这些名称和编号；网上许多 OWASP 材料仍然引用 2021 年的列表。

| # | 类别 | 关键预防措施 |
|---|----------|----------------|
| A01 | 访问控制失效（现在包括 SSRF） | 默认拒绝，服务器端强制，验证所有权 |
| A02 | 安全配置错误 | 强化配置，禁用默认值，最小化功能 |
| A03 | 软件供应链故障 | 锁定版本，验证完整性，审计依赖项 |
| A04 | 密码学故障 | TLS 1.2+，AES-256-GCM，Argon2/bcrypt 用于密码 |
| A05 | 注入 | 参数化查询，输入验证，安全 API |
| A06 | 不安全设计 | 威胁模型，速率限制，设计安全控制 |
| A07 | 身份验证故障 | MFA，检查泄露密码，安全会话 |
| A08 | 软件或数据完整性故障 | 签名包，CDN 的 SRI，安全序列化 |
| A09 | 安全日志和警报故障 | 记录安全事件，结构化格式，警报 |
| A10 | 处理异常情况不当 | 故障关闭，隐藏内部，上下文记录 |

## LLM 应用的 OWASP Top 10 (2026)

适用于调用 LLM 的应用程序（聊天机器人、RAG、协作者、代理）。2026 年版重新编号了列表；使用 `owasp-report.md` 中的表格翻译 2025 年 ID，仅引用 2026 年 ID。

| # | 风险 | 关键缓解措施 |
|---|------|----------------|
| LLM01 | 提示注入 | 没有完全修复的方法。围栏不受信任的内容（包括图像、音频、工具输出），将权限保持在模型之外，过滤输出 |
| LLM02 | 敏感信息泄露 | 清理训练/RAG 数据，从上下文中删除 PII，限制模型可以按用户检索的内容 |
| LLM03 | 过度代理 | 最小化工具和权限，要求对破坏性行为进行人工批准，按任务范围凭证 |
| LLM04 | 供应链 | 验证模型来源和签名，审查第三方模型中心，锁定模型和适配器版本 |
| LLM05 | 数据和模型中毒 | 验证训练/微调来源，数据摄入时异常检测，保留完整性测试 |
| LLM06 | 无限制消耗 | 按用户/密钥速率限制，每请求限制令牌和工具调用，监控成本，设置硬超时 |
| LLM07 | 错误信息 | 引用来源，显示置信度，要求对高风险答案进行接地，披露 AI 起源 |
| LLM08 | 隐藏上下文暴露 | 假设系统提示符、工具模式和其他隐藏上下文是可提取的：没有秘密在那里，也没有依赖于它们保持隐藏的授权或策略 |
| LLM09 | 向量和嵌入弱点 | 客户端隔离向量存储，检索时访问控制，对间接提示注入进行签名或哈希块 |
| LLM10 | 不当输出处理 | 将所有 LLM 输出（包括生成的代码）视为不受信任的输入：在到达接收器（SQL、shell、HTML、代码、工具调用）之前进行验证、转义或沙盒 |

## 代理应用的 OWASP Top 10 (2026)

适用于计划、调用工具或保留内存的 AI 代理系统。

| 风险 | 描述 | 缓解措施 |
|------|-------------|------------|
| ASI01: 代理目标劫持 | 提示注入改变代理目标 | 将工具和检索的内容视为数据，目标边界，行为监控 |
| ASI02: 工具滥用和利用 | 工具以意外方式使用 | 最小权限，细粒度权限，验证 I/O |
| ASI03: 身份和权限滥用 | 委托信任，继承凭证，角色链利用 | 短寿命范围令牌，身份验证 |
| ASI04: 代理供应链漏洞 | 受感染的插件/MCP 服务器 | 验证签名，沙盒，白名单插件 |
| ASI05: 预期之外的代码执行 | 不安全的代码生成/执行 | 沙盒执行，静态分析，人工批准 |
| ASI06: 内存和上下文中毒 | 损坏的 RAG/上下文数据 | 验证存储的内容，按信任级别分段 |
| ASI07: 不安全的代理间通信 | 欺骗/拦截代理间消息 | 身份验证，加密，验证消息完整性 |
| ASI08: 级联故障 | 错误传播到系统 | 电路断路器，优雅降级，隔离 |
| ASI09: 人类-代理信任利用 | 过度信任代理以操纵用户 | 标记 AI 内容，用户教育，验证步骤 |
| ASI10: 恶意代理 | 受感染的代理恶意行为 | 行为监控，关闭开关，异常检测 |

## ASVS 5.0 关键要求

ASVS 5.0（2025 年 5 月）重新编号并重新组织了每个章节。**4.0 要求 ID 不映射到 5.0** — `V2.1.1` 在 4.0 中意味着“密码长度”，现在意味着其他内容。仅引用 5.0 ID。级别由要求份额定义，而不是由应用程序类别定义：

| 级别 | 份额 | 意图 |
|---|---|---|
| L1 | ~20% | 最低标准；故意保持较小以降低进入门槛 |
| L2 | ~50%（≈70% 累计） | 大多数应用程序应瞄准的目标 |
| L3 | 剩余 ~30% | 最高保证 |

### L1 — 最低标准
- 密码**至少 8 个字符**；强烈建议 15+（6.2.1）
- 没有组合规则——允许任何字符、粘贴和密码管理器（6.2.5、6.2.7）
- 至少阻止前 3000 个常见密码（6.2.4）
- 对凭证填充和暴力破解的反自动化（6.3.1）
- 没有默认账户，如 `root`/`admin`/`sa`（6.3.2）
- 从具有 128+ 比特熵的 CSPRNG 引用会话令牌（7.2.3）
- 在身份验证和重新身份验证时发出新的会话令牌（7.2.4）
- 登出或过期后会话完全不可用（7.4.1）
- 函数级和数据级访问限制为明确的权限（8.2.1、8.2.2）
- 在客户端无法操纵的可信服务层强制执行授权（8.3.1）
- 所有数据访问使用参数化查询/ORM（1.2.4）；参数化操作系统调用（1.2.5）
- 上下文适当的输出编码用于 HTML、URL 和 JavaScript/JSON（1.2.1–1.2.3）
- 避免 `eval()` 和动态代码执行（1.3.2）
- 在可信服务层验证输入，尽可能使用正则/白名单（2.2.1、2.2.2）
- 所有外部流量使用 TLS 1.2+，公开受信任的证书（12.1.1、12.2.1、12.2.2）
- 仅使用批准的密码和模式——没有 ECB，没有 PKCS#1 v1.5 填充（11.3.1、11.3.2）
- URL 或查询字符串中不包含敏感数据（14.2.1）

### L2 — 大多数应用程序应瞄准的目标
- MFA，或文档化的单一因素组合（6.3.3）
- 检查泄露密码集中的密码（6.2.12）
- 不强制执行定期密码旋转——仅在泄露时旋转（6.2.10）
- **所有安全日志从此开始。** ASVS 5.0 没有李的日志要求；整个 V16 都是 L2+。记录身份验证尝试、授权失败、安全事件和意外错误（16.3.1–16.3.4）
- 日志条目包含时间/地点/谁/什么元数据，使用同步时钟（16.2.1、16.2.2）
- 日志编码以防止日志注入，受保护以防止修改，从机外发送（16.4.1–16.4.3）
- 对用户显示通用错误消息；详细信息保留在日志中（16.5.1）

### L3 — 最高保证

ASVS 5.0 有 **92 个 L3 要求**；它们在此未列出。两个值得了解，因为它们收紧了 L2 要求，而不是添加了新要求：

- 必须有一个基于硬件且防钓鱼的因素，例如 FIDO 密钥（6.3.3，L3 子句）
- 记录**所有**授权决定，而不仅仅是失败（16.3.2，L3 子句）

对于实际的 L3 评估，请参考标准本身——请参阅 [`reference/owasp-report.md`](reference/owasp-report.md) 以获取章节映射。
