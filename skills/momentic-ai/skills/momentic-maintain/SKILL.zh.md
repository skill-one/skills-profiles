# 维护 Momentic 测试

找到最早进入错误状态的运行点，根据证据对原因进行分类，并在适用时进行耐久性测试更改。使用 MCP 进行针对性调查，使用 `momentic ai classify` 获取新的分类器裁决，并使用 `momentic ai triage` 进行自动修复和验证。

不要为了隐藏应用程序错误、缺失的固定装置、无效凭证、中断或 Momentic 缺陷而削弱测试。报告这些原因，而不是更改测试以使其通过。

## 常见工作流程

- **我的分支上发生了什么？** 使用确切的 `gitBranchName` 和有界的 `start`/`end` 调用 `momentic_list_runs`。开始时不使用状态过滤器，然后缩小到 `FAILED`、`CANCELLED` 或 `recovered=true`。打开确切的候选者，并且仅在具体跨分支问题时才与主分支进行比较。
- **为什么主分支是红色的？** 在事件窗口内列出实际主分支上的 `FAILED` 运行，并分页浏览每个需要的页面以支持声明。在调查已知类别时使用 `failureCategory` 进行缩小，但在检查代表性运行和步骤证据后才分组症状。在可选重新分类之前，阅读每个确切的运行的保存分类。
- **消除 flaky 并减少恢复延迟。** 使用 `momentic_quarantine_list` 查看隔离的测试，使用 `recovered=true` 查看需要恢复的成功运行，并使用 `minAttempts` 查看重试密集的运行（`2` 表示至少一次重试；`3` 表示至少两次）。检查早期尝试，优先处理重复的相同意图失败，修复最早的不稳定后置条件，并再次测量。

了解发现限制：

- `momentic_list_runs` 按测试、分支、状态、隔离、恢复、有效失败类别、最小总尝试次数和时间进行过滤。`failureCategory` 在存在时使用手动分类，否则使用自动分类。
- `momentic_quarantine_list` 按隔离日期过滤，并返回每个活动隔离的最新保留的失败 CLI 运行。它不按分支或分类进行过滤。
- 一个类别或重试阈值仍然可以跨越多个页面。在调用详尽的清单之前，分页浏览所有需要的 `pageCount` 页面。

## 维护工作流程

1. 从确切的运行、分支、运行组、提交或本地结果目标开始。
2. 检查现有的自动/手动分类，并首先修复状态。
3. 使用 MCP 重建确切的失败，并且仅使用必要的运行历史记录。
4. 在编辑之前解释最早的偏离和损坏的后置条件。
5. 仅在有用时才重新分类；仅在请求时才持久化裁决。
6. 准备确切的应用程序和固定装置，然后在适当的情况下进行分诊。
7. 审查差异并重播证据；重新运行不明确的修复。
8. 报告诊断、修复、验证、交付和剩余的阻塞器。

## 检查现有的分类

在可用 API 密钥的情况下，在 MCP 调查之前获取原始运行元数据：

```bash
RUN_ID="<run-id>"
MOMENTIC_SERVER_URL="${MOMENTIC_SERVER:-https://api.momentic.ai}"
RUN_INSPECTION_DIR="$(mktemp -d)"

curl --fail --silent --show-error \
  -H "Authorization: Bearer ${MOMENTIC_API_KEY:?Set MOMENTIC_API_KEY}" \
  "${MOMENTIC_SERVER_URL}/v1/runs/${RUN_ID}/metadata" \
  -o "${RUN_INSPECTION_DIR}/metadata.json"

jq '{
  runId: .id,
  status,
  failureReason,
  classification: .failureDetails.classification,
  manualClassification: .failureDetails.manualClassification,
  healStatus,
  healDetails
}' "${RUN_INSPECTION_DIR}/metadata.json"
```

在确切的运行和组织元数据请求成功之前，不要将缺失的字段视为没有人类审查失败的证据。不要回显、记录或提交 API 密钥。将下载的元数据和签名工件 URL 视为敏感运行数据。

`momentic_get_run` 故意从它返回的证据中删除先前的分类和修复字段，以便新的调查不被旧的裁决所锚定。使用元数据端点或仪表板获取现有的裁决，然后使用 MCP 获取底层证据。

## 有用的 MCP 工具

`momentic_get_run` - 返回运行元数据和完整结果树摘要。使用它来识别尝试、失败的段落、失败的步骤和嵌套的父链。如果当前运行已经加载，则仅针对不同的尝试或缺失的数据再次调用它。

`momentic_list_runs` - 列出测试的最近运行。始终在目标运行上存在 `gitBranchName` 时传递它，以便比较更有可能使用相同的测试版本。仅在跨分支历史记录回答特定问题时才省略它。传递 `recovered=true` 以检查恢复的运行。传递 `failureCategory` 以选择有效的手动/自动分类，并传递 `minAttempts: 2` 或更高以查找重试的运行。

`momentic_quarantine_list` - 列出活动的本地测试隔离和每个测试的最新保留的失败 CLI 运行。使用有界的隔离日期范围。

`momentic_get_step_result` - 返回命令详细信息、前后截图，以及可选的完整跟踪。传递 `parentStepIdChain` 以检查嵌套步骤。仅在截图和正常字段无法回答问题时请求 `includeTrace=true`。

`momentic_get_test_steps_for_run` - 返回在运行上记录的简化测试定义记录。在测试意图仍然不清楚或比较编写的测试是否在运行之间发生变化时使用它。

`momentic_submit_result_classification` - 持久化手动 MCP 分类。仅在调查完成后调用它，并且仅在用户请求记录裁决时调用它。不要在相同的结论上调用它，除了 `ai classify --save`。

## 调查工作流程

在依赖历史记录之前，从当前运行开始。

1. 调用 `momentic_get_run` 并识别失败的尝试、段落（`beforeSteps`、主步骤或 `afterSteps`）、失败的步骤和任何 `parentStepIdChain`。
2. 拉取失败的步骤结果，包括截图和跟踪。如果步骤是嵌套的，还拉取最近的父容器或模块结果。
3. 确定失败的步骤的快照是否是该操作的正确的基线。如果它已经是错误的，则向后遍历当前运行，直到找到产生该错误状态的步骤/容器。
4. 对于重复的模块或重复的工作流程，在比较旧运行之前，先在相同的当前运行内比较调用。后来的失败通常是由较早的调用成功、恢复或留下无效后置条件引起的。
5. 将具有失败或恢复子步骤的成功容器视为部分失败，直到检查容器的最终 `afterSteps` 截图和 URL。
6. 在理解当前运行行为后，仅使用过去运行来回答特定的比较问题。

在分类之前，能够回答：

- 测试的预期行为是什么？
- 最早的偏离步骤/容器是什么？
- 该步骤打算做什么？
- 它实际交互或观察了哪个元素/状态？
- 步骤后截图、URL、DOM、跟踪或恢复日志发生了什么变化？
- 为什么后来的失败是较早偏离的结果？

避免模糊的根本原因，例如“设置不可靠”或“页面处于错误状态”。直接命名损坏的后置条件：例如，“行级加号按钮被点击，但应用程序停留在父页面而不是打开子页面编辑器；以下全局 `Add to` 断言针对无关页面文本通过，因此未定向的类型步骤从未进入子标题。”

## 证据标准

- 截图是页面状态的默认真相来源。使用跟踪字段和 DOM/HTML 来解释为什么截图发生了变化或没有变化。
- 验证每个因果关系声明。除非相关的快照、URL 或 DOM 证明，否则不要说覆盖层、侧快照、模态或菜单存在。
- 将“目标现在缺失”与“浏览器处于目标应该存在的状态”分开。缺失的目标通常是较早失败行动的症状。
- 对于点击/输入/操作步骤，记录预期操作、实际交互的元素（如果可用）、前后 URL，以及是否出现预期的 UI 状态。
- 对于断言，检查断言是否足够范围以证明预期状态。广泛的页面内容断言可以因为无关文本而通过。
- 对于恢复，检查失败的子步骤和恢复的容器最终状态。恢复可以在重试断言时通过，但会留下后来步骤未预期的状态。

## 运行 AI 分类

`momentic ai classify` 运行 Momentic 的结果分类代理来处理失败的运行。它读取运行工件，使用相关的运行历史记录和存储库上下文，并返回类别、可恢复性、置信度、推理和引用。它解释失败；它不会编辑测试。

每个命令使用一个选择器：

```bash
npx momentic ai classify --run-id "$RUN_ID" --output-format json
npx momentic ai classify --run-group-id "<run-group-id>"
npx momentic ai classify --git-commit "<commit-sha>"
```

- 省略 `--save` 以进行诊断重新分类。仅在新的裁决应替换本地存档或云运行上的保存分类时添加 `--save`。
- 当现有的缓存分类器结果被怀疑是过时时，使用 `--no-cache` 以便用户显式需要新的分析。
- 使用 `--skip-classified` 以便在不重新访问已保存分类的运行的情况下恢复批处理。
- 使用 `--output-format json` 以便自动化和多运行账目。
- 当有用时，将多个相关的运行 ID 一起分类，但将每个结果映射到其确切的运行。

在一个真实终端中的一个运行中，保持分类器对话开放：

```bash
npx momentic ai classify --run-id "$RUN_ID" --interactive
```

使用聊天来询问它为什么选择了类别、它依赖了哪些证据、当前运行与先前运行有何不同，或者一个耐久性修复需要什么。交互式分类仅限单运行，需要 `stdin` 是 TTY，并且不能与 JSON 输出组合。

## 准备分诊

将应用程序就绪视为一个硬前置条件。分诊在真实浏览器中重播测试；它不能针对不可用的应用程序、缺失的固定装置、错误的环境、未播种的数据库、无效帐户或冷编译器进行修复。

在分诊之前：

1. 阅读 `momentic.config.yaml`，目标测试及其设置模块、存储库脚本和通常运行测试的 CI 工作流。使用相同的 URL、环境、凭证、标头、文件、服务和数据固定装置。
2. 确认 `MOMENTIC_API_KEY`、项目配置、依赖项和请求的浏览器可用。
3. 检查 `git status` 并保留无关的工作。在运行命令之前决定修复交付；不要让未知的仪表板默认值意外创建拉取请求或提交。
4. 在开始分诊之前构建应用程序。优先使用生产或否则预编译的构建和稳定的服务器，而不是 Next.js、webpack、Vite 或其他开发服务器，这些服务器会逐个编译路由。
5. 启动每个所需的服务并等待实际就绪 URL。在分诊之前预热任何不可避免的仅限开发编译路径，并验证相关路由不再显示编译/加载屏幕或导致长时间的第一请求。
6. 在必要时运行一次集中的烟雾测试或失败的测试，以证明应用程序、固定装置、身份验证和浏览器已就绪。在归咎于分诊之前修复设置失败。
7. 从 `--parallel 1` 开始。仅在机器有足够的 CPU 和内存来为每个工作负载运行一个浏览器和应用程序时才提高它。

如果存储库公开了稳定的服务器命令，则可以单独启动它，或使用 `--start` 和 `--wait-on` 让分诊拥有它：

```bash
# 首先构建；使用存储库的实际命令和就绪 URL。
pnpm build
npx momentic ai triage --run-id "$RUN_ID" \
  --start "pnpm start" \
  --wait-on "http://localhost:3000/health" \
  --parallel 1 \
  --yes \
  --on-heal-success nothing
```

不要盲目复制这些示例命令。从存储库和 CI 配置中发现真实的构建、启动和就绪合同。

## 运行 AI 分诊

`momentic ai triage` 按共享根本原因对失败进行分组，决定哪些是可修复的，编辑相关测试，在浏览器中重播它们，并只接受满足其验证的修复。它可以本地保留更改、生成补丁、提交或打开拉取请求。它不能通过更改测试来修复应用程序错误、外部中断或缺失的固定装置。

当用户想要明确的诊断时，首先运行分类，然后将相同的目标传递给分诊：

```bash
npx momentic ai classify --run-id "$RUN_ID" --output-format json
npx momentic ai triage --run-id "$RUN_ID" \
  --parallel 1 \
  --yes \
  --on-heal-success nothing
```

对于本地运行组，传递结果目录：

```bash
npx momentic ai triage ./test-results \
  --parallel 1 \
  --yes \
  --on-heal-success nothing
```

最佳实践：

- 在一个 `--run-id` 后传递多个相关的运行 ID，以便分组代理可以分组共享原因。不要为每个运行启动一个竞争的分诊命令。
- 明确设置 `--on-heal-success`：使用 `nothing` 进行本地审查，`patch` 用于可移植的 diff，或在用户请求交付时才使用拉取请求/提交行为。
- 仅在确认环境和交付选择后传递 `--yes`，以免依赖提示阻止自动运行。
- 使用 `--dry-run --no-save` 以便在不编辑测试或保存分诊元数据的情况下检查分组。干运行不是修复尝试。
- 仅当缓存的修复过时或失败并且应从头开始生成新的修复时，使用 `--regenerate-heal`。
- 保持命令连接并监控推理、工具调用、浏览器进度、CPU 和内存。浏览器进度几分钟后没有进展可能表示应用程序启动、冷编译、资源压力或缺失的固定装置。
- 检查每个生成的 diff。不要接受删除的断言、扩大的检查、任意的睡眠或更长的超时，这些仅仅掩盖了原因。
- 不要因为分诊生成了补丁而仅因为分诊生成了补丁而解除隔离。首先重新运行修复的测试。

使用交互式分诊，当用户想要质疑修复代理时：

```bash
npx momentic ai triage --run-id "$RUN_ID" \
  --parallel 1 \
  --yes \
  --on-heal-success nothing \
  --interactive
```

交互式分诊需要 TTY，不能与 `--json` 组合，并且仅在命令运行分组代理时可用。使用它来询问为什么接受了修复或拒绝，它观察了哪些设置，以及哪些证据仍然未解决。

## 手动下载运行工件

优先使用 MCP 进行普通检查，因为 `momentic_get_run` 会自动下载并提取云尝试。在 MCP 输出缺失、必须对原始文件进行 grep 或在独立验证代理时使用 API。

```bash
RUN_ID="<run-id>"
MOMENTIC_SERVER_URL="${MOMENTIC_SERVER:-https://api.momentic.ai}"
RUN_INSPECTION_DIR="$(mktemp -d)"

curl --fail --silent --show-error \
  -H "Authorization: Bearer ${MOMENTIC_API_KEY:?Set MOMENTIC_API_KEY}" \
  "${MOMENTIC_SERVER_URL}/v1/runs/${RUN_ID}/export" \
  -o "${RUN_INSPECTION_DIR}/export.json"

jq '.run' "${RUN_INSPECTION_DIR}/export.json" \
  > "${RUN_INSPECTION_DIR}/metadata.json"

jq -r '.attemptZipUrls | to_entries[] | select(.value != null) |
  [(.key + 1), .value] | @tsv' "${RUN_INSPECTION_DIR}/export.json" |
  while IFS=$'\t' read -r attempt url; do
    mkdir -p "${RUN_INSPECTION_DIR}/attempts/${attempt}"
    curl --fail --silent --show-error "$url" \
      -o "${RUN_INSPECTION_DIR}/attempt-${attempt}.zip"
    unzip -q "${RUN_INSPECTION_DIR}/attempt-${attempt}.zip" \
      -d "${RUN_INSPECTION_DIR}/attempts/${attempt}"
  done
```

检查 `metadata.json`，每个尝试的 `metadata.json`，截图，DOM 快照，控制台日志，HAR 日志，视频，资源使用情况，以及崩溃存档。保持尝试编号完整。不要提交导出响应，运行工件，签名 URL，凭证或客户数据。调查完成后删除临时目录。

## 背景

### 测试运行结果结构

当通过 CLI 运行 momentic 测试时，结果存储在“运行组”中。此运行组的数据存储在 momentic 项目的单个目录中。默认情况下，该目录称为 `test-results`，但可以在 momentic 项目设置或单个运行组运行中更改。运行组结果文件夹具有以下结构：

```
test-results/
├── metadata.json         运行组数据，包括 git 元数据和时间信息。
└── runs/                 每个测试运行组中的压缩文件。
    ├── <runId_1>.zip         包含此特定测试运行数据的压缩运行目录。遵循以下结构。
    └── <runId_2>.zip
```

解压缩后，运行目录具有以下结构：

```
<runId>/
├── metadata.json           运行级元数据。
└── attempts/<n>/           每个尝试（1-based n）的文件夹。
    ├── metadata.json       尝试结果和步骤结果。
    ├── console.json        可选的浏览器控制台输出。
    └── assets/
        ├── <snapshotId>.jpeg     每个步骤的快照（参见尝试 metadata.json 中的快照 ID）。
        ├── <snapshotId>.html     每个步骤的 DOM 快照（参见尝试 metadata.json 中的快照 ID）。
        ├── har-pages.log         HAR 页面（ndjson）。
        ├── har-entries.log       HAR 网络条目（ndjson）。
        ├── resource-usage.ndjson 在尝试期间采集的 CPU/内存样本。
        ├── <videoName>           视频录制（当启用视频录制时）。
        └── browser-crash.zip     浏览器崩溃转储（仅当出现崩溃时存在）。
```

通过 momentic MCP 获取运行结果时，工具（如 `momentic_get_run`）将返回 MCP 工作目录（默认 `.momentic-mcp`）的链接。此目录将包含解压缩的运行结果文件夹，遵循上述结构，命名为 `run-result-<runId>`。

### 元素定位器

某些与元素交互的步骤类型具有“目标”属性，或 **定位器**，指定步骤应与之交互的元素。

#### 定位器缓存

定位器通过将页面状态 html/xml 发送到 llm 以及截图来识别元素。llm 识别页面上的用户所指的元素。Momentic 将尝试“缓存”来自 llm 的答案，以便未来的运行不需要 AI 调用。在未来的运行中，页面状态会与缓存的元素进行比对，以确定元素是否仍然可用，或者页面是否已更改到需要再次进行 AI 调用的程度。

定位器缓存可能因多种原因失效：

- 元素描述已更改，在这种情况下，我们将始终失效缓存
- 缓存的元素在当前页面状态中无法定位
- 缓存的元素在页面状态中可以定位，但未通过缓存条目中指定的某些检查，例如需要特定的位置、形状或内容。

您可以在给定步骤的结果的 `trace` 属性上找到 `cacheBustReason`，但仅当您明确请求 `includeTrace=true` 时才可见。`cache` 属性也列在结果中，显示为该元素保存的完整缓存。

#### 识别坏缓存

有时缓存的元素不是用户打算定位的元素。这可能导致测试失败或出现意外的行为。在这些情况下，验证最初保存错误缓存的原因很有帮助。仅在缓存调试情况下或当您怀疑 Momentic 执行数据不正确时请求 `includeTrace=true`。使用错误缓存上的 `targetUpdateLoggerTags` 的 `runId` 属性获取原始运行的详细信息，使用 `momentic_get_run` 带此 runId。这将返回缓存目标更新的运行。

### 模块缓存

缓存的模块在模块缓存键和解析输入未更改时跳过执行其步骤，并重用模块上次步骤的缓存返回值。

身份验证模块还可以从模块缓存中保存和恢复浏览器身份状态，包括 cookies、localStorage 和 IndexedDB。它们可能使用页面内容检查来决定缓存是否仍然有效。

### 文件上传

文件上传步骤为下一个原生文件选择器准备一个文件，因此必须在打开选择器的操作之前运行。

源可以是远程 URL、`file://` 引用先前下载的文件、CLI 本地路径或上传的用户文件。该步骤还可以覆盖显示的文件名，Momentic 将准备好的文件连接到浏览器的文件选择器处理。

## 使用过去的运行

过去的运行是比较证据，而不是重建当前运行的替代品。当当前运行无法回答以下问题时使用它们：

- 这个测试何时开始失败？
- 与上次通过运行的差异是什么？
- 同一操作在早期运行中表现是否不同？
- 这是一个测试弱点、应用程序更改、实际应用程序错误还是临时减速？

使用过去的步骤结果和截图来回答这些问题。不要仅依赖 `momentic_get_run` 或 `momentic_list_runs` 的摘要来了解测试运行中发生了什么。在引用过去的运行作为证据之前，查看特定的运行详细信息，包括步骤结果和截图。

查看过去的运行时，请使用以下工作流程：

1. 调用 `momentic_list_runs` 工具以识别您想要更多详细信息的运行。当问题运行中存在 `gitBranchName` 时，始终传递它。当您需要来自其他分支的运行时，省略它。
2. 调用 `momentic_get_run` 获取该特定运行的运行详细信息。
3. 调用 `momentic_get_step_result` 获取您正在比较的相同步骤/容器或最接近的等效项，特别是用于截图。

当过去的运行无关紧要，因为当前运行已经证明了根本原因时，简要说明，而不是强迫历史证据。

### 多尝试运行

当 `momentic_list_runs` 显示通过运行且 `attempts > 1` 时，将其视为值得调查的部分失败，而不是干净的通过运行。使用 `attemptNumber` 参数检索该运行中较早失败的尝试结果，以了解重试成功之前的错误。

### 间歇性失败和波动性

- 仅当相同的应用程序和测试行为间歇性失败时才将测试称为波动性。
  一个失败是不够的；在使用运行证据排除应用程序和测试更改之前，不要将模式归因于波动性。

### 测试时效性

- 过去的任何结果可能不一定与今天的测试文件匹配。测试可能已更改，这意味着结果是在不同版本的测试上。
- 您可以调用 `get_test_steps_for_run` 来帮助您确定测试本身是否在运行之间已更改，尽管请注意该工具返回每个测试步骤的 **摘要**。如果您怀疑某些步骤的特定详细信息在测试运行之间已更改，完整步骤详细信息包含在 `momentic_get_step_result` 的响应中；仅在那些字段和截图仍然不够时请求 `includeTrace=true`。

## 常见失败模式

- 设置模块似乎通过但将错误的页面、覆盖层、过滤器、搜索、选定行或侧预览打开。从留下错误后置条件的步骤/容器进行分类，而不仅仅是下一个失败的步骤。
- 点击报告成功并定位了预期元素，但应用程序未过渡到预期状态。验证后置状态；不要假设点击工作是因为定位器正确。
- 弱全局断言（如“页面包含 X”）通过，因为页面上的无关文本匹配。下一个步骤可能会在错误的上下文中键入或点击。
- 没有特定目标的键入步骤如果前一个操作未能将预期字段聚焦，可能会无声地键入无用的位置。
- 定位器或缓存在技术上可能有效，但在语义上可能错误。检查交互的元素，对于坏缓存，检查原始缓存更新运行（来自 `targetUpdateLoggerTags.runId`）。
- 恢复的步骤可能隐藏第一个失败。检查恢复模块中的失败子步骤，并将恢复的最终状态与下一个步骤的预期基线进行比较。
- 超时不是自动 `INFRA`。首先排除缺失数据、错误页面状态、更改的应用程序流程、坏定位器/断言和设置失败。

## 识别相关与不相关的问题

- 从测试名称、描述和简化步骤中确定意图。将意图之外的失败（包括大多数设置/拆卸失败）视为不相关。相关性确定错误和更改；它不会将 `INFRA` 失败转换为其他类别。

## 错误与更改

- 错误：当不应出错时，发生了非常明显的问题，例如出现错误消息。通过查看单个步骤或两个步骤就可以明显看出这是一个错误。
- 更改：应用程序行为发生了明显变化，您可以通过截图证明。

## 可恢复性

除了类别外，确定一个可恢复性值：

- `RECOVERABLE` — 失败可以通过更新测试本身自动修复，以便未来的运行通过。
  - 示例：需要更新测试的应用程序更改；模糊定位器或断言可以重写以稳定通过。
- `ONE_TIME_RECOVERABLE` — 失败可以针对此特定运行恢复，而无需持久化测试更改。
  - 示例：可以关闭而不影响测试目的的随机模态；临时延迟，等待或重试可能会成功。
- `NON_RECOVERABLE` — 失败无法自动解决，需要手动干预。
  - 示例：缺少凭证；缺少上传所需的本地文件；由第三方系统引起的停机，测试步骤无法修复问题。

## 正式分类输出

- 恰好一个类别 ID — 没有新标签，没有多标签。
- 以数据为依据。确保在分配类别之前充分调查运行。
- 当步骤/模块可以通俗地识别时，优先使用人类可读的引用而不是 UUID：`module create-subpage-under-parent-page`，`模块 <name> 的最后一次调用`，`子步骤 4 (0-indexed)`，`失败的设置断言` 等。工具调用仍然需要确切的 ID，但最终推理应该是可读的。
- 在最终输出中引用过去的运行时，使用可点击的 Momentic URL 而不是裸 UUID：`https://app.momentic.ai/runs/<runId>`。不要缩短那些 URL 中的 UUID。
- 推理必须包括最早的发散步骤/容器以及它产生的错误后置条件，而不仅仅是最终失败的步骤。

```text
Reasoning: <几句话与最早的发散相关联，截图/跟踪，如果使用了过去的运行，以及测试意图>
Category: <列表中的一个 ID>
Recoverable: <RECOVERABLE | ONE_TIME_RECOVERABLE | NON_RECOVERABLE>
Confidence: <high | medium | low>
```

置信度级别：

- `high` — 直接证据，例如清晰的截图显示标签更改或崩溃
- `medium` — 来自多个信号的强烈推断，但没有单一的结论性截图或数据点
- `low` — 模糊证据；分类需要大量推断或根本原因不明确

## 类别 ID

使用这些字符串原样输出：

- `NO_FAILURE` — 运行没有失败；所有尝试都通过。
- `APPLICATION_CHANGE` — 测试已过时，因为应用程序的流程或 UI 已更改；更新测试以匹配新行为将永久修复失败。
- `BUG` — 应用程序中发生了非常明显的问题，本不应发生，例如出现错误消息或预期内容未渲染。
- `TEST_AUTHORSHIP` — 测试可以永久更新以防止失败，同时仍然验证其原始意图，并且您可以建议具体的作者身份更改，例如添加或修改步骤、重写模糊断言或使定位器描述更具体。如果您无法指定具体更改，请选择其他类别。超时、慢页面加载以及任何建议的修复方法是“等待更长”或增加超时的失败都不是作者身份问题 — 这些是 `INFRA`，即使测试技术上可以编辑以等待更长。
  - 示例：可以通过添加或修改步骤（除等待/超时外）来修复的竞争条件（例如，将“键入并按 Enter”步骤替换为显式的“从列表中选择”步骤，以便测试不再与应用程序竞争）；可以重写以更具体的模糊断言或定位器描述。
- `TEST_SETUP` — 运行测试所需的测试数据或文件丢失，其中修复需要用户在测试本身之外的操作。
  - 示例：文件上传步骤的缺失文件；测试需要的缺失或不正确的凭证。
- `INFRA` — 失败与应用程序或应用程序代码无关，是由基础设施停机、长时间加载时间或其他由于外部因素导致的问题引起的。
  - 示例：浏览器崩溃；高资源使用；速率限制；超时等待页面或应用程序达到慢但最终的状态的步骤或断言。
- `MOMENTIC_ISSUE` — 测试执行或 Momentic 数据出现问题时发生了一些问题（例如，缓存错误，全局定位器重定向做了奇怪的事情，AI 幻觉）。
  - 示例：查看运行跟踪时出现意外行为；AI 明显误解或幻觉了截图中的明确数据，并且没有合理的测试替代方案来避免 AI 步骤。
- `OTHER` — 失败不属于任何其他类别。
