# 复合规划分析

你正在对用户的 Plannotator 计划存档进行综合研究分析。目标：从其被拒绝的计划中提取模式，将其简化为可操作的见解，并生成一个优雅的 HTML 仪表板报告。

这是一个多阶段的过程。每个阶段必须完全完成后才能开始下一阶段。研究诚信至关重要——每个文件都必须读取，不能跳过。

## 源选择

在开始分析之前，确定哪些数据源可用。

1. **Plannotator 模式（首选）** — 确定 Plannotator 数据目录：
   如果设置了 `$PLANNOTATOR_DATA_DIR`，则使用它，否则使用 `~/.plannotator`。检查那里的 `plans/` 子目录。如果它存在并包含 `*-denied.md` 文件，则使用此模式。下面整个工作流程都是为 Plannotator 数据编写的。

2. **Claude Code 备用模式** — 如果 Plannotator 存档不存在或其中不包含被拒绝的计划，请检查 `~/.claude/projects/`。如果存在，继续之前请阅读 [references/claude-code-fallback.md](references/claude-code-fallback.md)。该参考文件解释了如何使用捆绑的解析器 [scripts/extract_exit_plan_mode_outcomes.py](scripts/extract_exit_plan_mode_outcomes.py) 从 Claude Code JSONL 转录中提取拒绝原因。下面每个阶段都有一个简短说明解释备用模式下的变化——参考文件有详细信息。

3. **两者都不可用** — 请求用户提供他们的 Plannotator 计划目录或 Claude Code 项目目录。不要猜测。

## 阶段 0：定位计划并检查之前的报告

使用源选择中选择的模式。

**Plannotator 模式：** 验证计划目录是否包含 `*-denied.md` 文件。如果不存在，则在停止之前回退到 Claude Code 模式。

**Claude Code 备用模式：** 按备用参考运行捆绑的解析器以构建拒绝原因数据集。如果需要，创建 `/tmp/compound-planning/`。

在任何模式下，都继续到下面的“之前的报告检测”。

### 之前的报告检测

定位计划目录后，检查现有报告：

```
ls ${PLANNOTATOR_DATA_DIR:-~/.plannotator}/plans/compound-planning-report*.html
```

报告遵循版本化的命名方案：
- 首个报告：`compound-planning-report.html`
- 后续报告：`compound-planning-report-v2.html`，`compound-planning-report-v3.html`，等等。

如果存在一个或多个报告，请确定**最新**的一个（最高版本号）。使用 `stat` 获取其文件系统修改日期（macOS：`stat -f %Sm -t %Y-%m-%d`，Linux：`stat -c %y | cut -d' ' -f1`）。这是**截止日期**。

向用户显示选择：

> "我发现了一个之前的报告 (`compound-planning-report-v{N}.html`) 最后更新于 {CUTOFF_DATE}。我可以：
>
> 1. **增量** — 仅分析截止日期 {CUTOFF_DATE} 之后的文件，节省代币并建立之前的发现
> 2. **完整** — 从头开始重新分析整个存档
>
> 你希望选择哪个？"

等待用户的响应后再继续。

**如果增量：** 将所有后续阶段过滤为仅处理截止日期之后的文件日期。新的报告版本将在其页眉叙述中注明它涵盖了从 {CUTOFF_DATE} 到当前的时间段，并参考之前的报告以获取早期发现。清单（阶段 1）应仍然计算所有文件以获取整体统计数据，但应明确区分“自上次报告以来新增”的计数。

**如果完整：** 正常进行所有文件，但仍然使用下一个版本号作为输出文件名。

**如果不存在之前的报告：** 正常进行。输出文件名将是 `compound-planning-report.html`（第一个报告没有版本后缀）。

## 阶段 1：清单

计数并报告数据集。**始终计数所有文件**以获取整体统计数据，无论这是增量运行还是完整运行：

```
- *-approved.md 文件（计数）
- *-denied.md 文件（计数）
- 日期范围（找到的最早日期到最新日期）
- 总天数跨度
- 修订率：拒绝 / （批准 + 拒绝）——这是仪表板部分 1 中使用的“X% 的计划在编码前被修订”统计数据
```

**注意：** 完全忽略 `*.annotations.md` 文件。拒绝文件已经包含完整的计划文本以及所有审阅者反馈，这些反馈在 `---` 分隔符之后追加。注释文件是此内容冗余的子集——读取两者将重复计算反馈。

**如果增量模式：** 在总计数之后，单独报告仅截止日期之后文件的计数：

```
自 {CUTOFF_DATE} 以来新增：
- *-denied.md 文件：X（总共 Y 个）
- 新日期范围：{CUTOFF_DATE} 到 {LATEST_DATE}
- 新天数跨度：N
```

如果自截止日期以来少于 3 个新的拒绝文件，请警告用户：
> "自上次报告以来只有 {N} 个新的拒绝计划。增量分析可能很薄弱。您想继续还是切换到完整分析吗？"

还运行 `wc -l` 跨所有 `*-approved.md` 文件以获取每个批准计划的平均行数。这告诉用户他们的计划是保持轻量级还是随着时间的推移而膨胀。您不需要读取批准计划的内容——只需它们的行数即可。如果可能，按时间段（例如，每月）进行分解，以显示计划大小是否发生变化。

日期以 YYYY-MM-DD 格式出现在文件名中，有时作为前缀（2026-01-07-name-approved.md）有时嵌入（name-2026-03-15-approved.md）。从所有文件名中提取日期。

告诉用户你发现了什么，并开始提取。

**Claude Code 备用模式：** 上面提到的 Plannotator 清单字段不适用。请按照 [references/claude-code-fallback.md](references/claude-code-fallback.md) 中的清单说明进行操作——报告解析器组装的拒绝原因数据集。

## 阶段 2：映射——并行提取

这是最耗时的阶段。你必须读取**范围内**的每个 `*-denied.md` 文件。不要跳过文件。不要提前总结。

**范围内**意味着：如果运行完整分析，则所有拒绝文件；如果运行增量分析，则仅截止日期之后的拒绝文件。在增量模式下，仅处理嵌入的 YYYY-MM-DD 日期严格在截止日期之后的文件。

**Claude Code 备用模式：** 解析器输出是干净的源数据集。在继续之前请阅读备用参考，了解针对 JSON 部分文件的提取提示和批处理策略。除非解析器失败或用户要求审计级验证，否则不要回到原始 `.jsonl` 日志。

**重要：** 仅读取 `*-denied.md` 文件。不要读取批准计划、注释文件或差异文件。每个拒绝文件包含完整的计划文本，后跟 `---` 分隔符和审阅者的反馈——分析所需的一切都在一个文件中。

### 批处理策略

所有提取代理应使用 `model: "haiku"`——它们正在进行简单的文件读取和结构化提取，而不是推理。Haiku 对此工作更快、更便宜。

方法取决于数据集大小：

**小型数据集（≤ 10 个总文件）：** 直接在主代理中读取所有文件——不需要子代理。只需按顺序读取它们并继续到阶段 3。

**中型数据集（11-30 个文件）：** 启动 2-3 个并行的 Haiku 代理，大致均匀分配文件。

**大型数据集（31-80 个文件）：** 启动 4-6 个并行的 Haiku 代理（每个约 10-15 个文件）。按文件类型和/或时间段进行分割。

**大型数据集（80 个文件以上）：** 启动所需数量的并行 Haiku 代理以保持每个批次的文件数在 10-15 个左右。按数据中的自然时间边界（月份、季度或产生平衡批次的任何分组）进行分割。如果一个时间段占主导地位（例如，最近一个月有 3 倍的文件），将该时间段分成多个批次。

使用 Agent 工具以 `run_in_background: true` 和 `model: "haiku"` 并行启动所有提取代理。

### 输出文件

每个提取代理必须将其结果写入一个干净的输出文件，而不是依赖代理任务输出（其中包含难以解析的交错 JSONL 框架日志）。指示每个代理写入：

```
/tmp/compound-planning/extraction-{batch-name}.md
```

在启动代理之前创建 `/tmp/compound-planning/` 目录。阶段 3 中的减少代理将直接读取这些干净的文件。

### 提取提示

每个代理接收此指令（调整时间段、文件列表和输出路径）：

```
你正在从拒绝计划文件中提取结构化数据以进行模式分析。

目录：[PLANS DIRECTORY]
要读取的文件：[具体的 *-denied.md 文件列表]
输出：将你的完整结果写入 [OUTPUT FILE PATH]

每个拒绝文件包含两个由 --- 行分隔的部分：
1. 计划文本（--- 之前）
2. 审阅者的反馈和注释（--- 之后）

读取列表中的每个文件。对于每个文件，提取：
- 计划名称/主题（来自 --- 之前的计划文本）
- 给出的拒绝原因或反馈（来自 --- 以下——捕获实际使用的词语）
- 具体要求更改的内容
- 反馈类型（让内容决定类别——不要强行拟合到预定义类型。常见类型包括：范围问题、方法分歧、缺失信息、流程要求、质量问题、UX/设计问题、命名争议、澄清请求、测试/程序拒绝——但用户的实际模式可能不同）
- 审阅者使用的任何特定短语或重复语言
- 如果有的话，单独的注释（编号的反馈项，带引文的文本和审阅者评论）
- 日期（从文件名中提取）

不要跳过任何文件。每个文件一条记录。

将每条记录格式化为：
**[filename]**
- 日期：...
- 主题：...
- 拒绝原因：...
- 反馈类型：...
- 具体要求：...
- 显著短语：...
- 注释：[数量，每个的简要总结]
---

处理所有文件后，将完整结果写入 [OUTPUT FILE PATH]。
在文件末尾说明总文件数。
```

### 代理运行时

跟踪完成情况。每当一个代理完成时，注意它处理的文件数。验证总数是否与阶段 1 的清单匹配。如果任何代理的计数不足，请标记它并考虑重新启动以处理缺失的文件。

如果一个代理超时（对于大型批次可能发生——128 个文件的批次可能需要 8 分钟以上），请重新启动它仅处理未处理的文件。检查输出文件以查看它在超时前处理到了哪里。

## 阶段 3：减少——模式分析

一旦所有提取代理完成（对于小型数据集，所有文件都已读取），请继续减少。减少代理应使用 `model: "sonnet"`——此阶段需要真正的分析推理，而不仅仅是文件读取。

### 减少策略

方法取决于生成的提取文件数量：

**标准（≤ 20 个提取文件）：** 启动一个 Sonnet 代理读取所有提取文件并生成完整分析。这涵盖了大多数数据集。

**大型（21 个以上提取文件）：** 使用两阶段减少：

1. **阶段 1——部分减少：** 将提取文件分成 4-6 组。启动并行 Sonnet 代理，每个代理读取一组并生成与下面列出的相同部分的部分分析。每个写入到
   `/tmp/compound-planning/partial-reduce-{N}.md`。

2. **阶段 2——最终减少：** 一个 Sonnet 代理读取所有部分减少文件，并将它们综合成最终的综合分析。该代理合并分类法，组合计数，去重模式，并解决部分之间的任何冲突分类。

**Claude Code 备用模式：** 减少阶段与相同。唯一的上游差异是提取文件是从归一化的拒绝原因 JSON 而不是 Plannotator markdown 文件中提取的。

### 减少提示

给每个减少代理此提示（根据单阶段或多阶段调整文件路径）：

```
你是一个数据科学家，正在进行用户拒绝计划存档的 map-reduce 分析的减少阶段。

读取所有提取文件在 [FILE PATHS]

这些文件包含从每个拒绝计划文件中提取的结构化数据。每个提取包括计划主题、拒绝反馈、注释和审阅者语言。你的工作：汇总所有内容，发现模式，聚类成一个分类法，并生成综合分析。

要详尽无遗。使用真实计数。引用真实数据中的短语。这是研究——不要含糊其辞，不要编造。

将你的完整结果写入 [OUTPUT FILE PATH]。

生成以下部分：
[... 下面列出的部分 ...]
```

减少代理的工作是让数据说话。不要强加预定的框架——发现实际存在的内容。分析必须生成：

### 1. 拒绝原因分类法
将每个拒绝分类为从数据中出现的有限类型。计数出现次数。显示百分比。包括每个类型的真实示例引言。目标为 8-15 个类别——足够具体，足够少以供扫描。让用户的实际反馈决定类别是什么。

### 2. 顶级反馈模式（按频率排名）
5-10 个最常见的模式。对于每个：审阅者一致要求的内容、来自不同文件的 3 个以上示例引言，以及模式是否随时间变化。

### 3. 重复短语
审阅者反复使用的确切短语，以及计数和它们表示的含义。这些是审阅者的词汇——他们对什么最关心的简写。

### 4. 审阅者重视什么（隐含偏好）
从模式中派生——这个特定的人最关心什么？质量？速度？叙事？架构？流程？简单性？按证据强度排名。这一部分应感觉像审阅者标准的个性简介。

### 5. 代理始终犯的错误
另一方面——什么重复出现的错误会触发拒绝？代理应该为这个审阅者停止做什么？

### 6. 结构性要求
审阅者始终要求什么样的计划结构？必需的部分、顺序、格式偏好、期望的详细程度。

### 7. 随时间推移的演变
反馈模式如何随时间变化。按数据中存在的任何自然时间边界分组（短时间段为周，较长时间段为月）。期望是否成熟？是否出现了新的模式？什么发生了变化？如果数据集跨度小于一个月，请说明演变分析有限，但仍要寻找早期到晚期文件之间的任何进展。

### 8. 可操作的提示指令
最重要的输出。基于所有模式：可以嵌入在规划提示中的具体编号指令，以防止最常见的拒绝原因。将这些写入代理可以遵循的实际指令。针对此用户的模式要具体——像“写好计划”这样的通用建议是无用的。每个指令应追溯到真实的、频繁的拒绝模式。

在编写指令后，计算它们将解决多少拒绝（计算落入指令覆盖的分类的拒绝数量与总拒绝数量）。报告此百分比——每个用户的百分比都将不同。

## 阶段 4：生成 HTML 仪表板

构建一个单一的、自包含的 HTML 文件作为最终交付物。将其保存到用户的计划目录中，使用版本化的文件名：

- 首次报告：`compound-planning-report.html`
- 第二个报告：`compound-planning-report-v2.html`
- 第三个报告：`compound-planning-report-v3.html`
- 等等。

版本号是在阶段 0 基于找到的现有报告确定的。

**如果这是一个增量报告**，页眉应指示分析期间（例如，“2026 年 3 月 15 日 – 2026 年 3 月 31 日”），并包括副标题“增量分析——请参阅 v{N-1} 以获取早期发现。”部分 1 中的叙述应将发现表述为自上次报告以来是什么新内容或发生了什么变化，而不是完整的画面。页眉中的整体统计数据（文件计数、修订率）应仍然反映完整存档以提供上下文。

请参考 `assets/report-template.html` 中的模板，仅用于**设计语言**。该模板包含先前分析的示例数据——请忽略模板中的所有数据值、引号和百分比。仅使用其视觉设计：颜色、排版、间距、组件样式和布局模式。

### 设计语言（来自模板）

- **调色板**：浅色模式，暖白色 (#FDFCFB)，文本使用 slate 等级，琥珀色用于高亮/强调， Emerald 绿色用于正面，玫瑰色用于负面，靛蓝色用于操作元素
- **排版**：Playfair Display（衬线字体，用于叙事标题），Inter（无衬线字体，用于正文/数据），JetBrains Mono（等宽字体，用于代码/短语）— Google Fonts CDN
- **布局**：单列，最大宽度 1024px，充足的垂直空白（主要部分之间 128px），编辑/叙事优先美学
- **语气**：平静、反思、权威。像个人回顾日记，而不是监控仪表板。

### 页面框架（页眉 + 页脚）

在 7 个部分之前，页面包含：

- **页眉**：左侧为报告标题（Playfair Display，约 36px），下方为项目名称 + 日期范围（浅色元文本）。右侧：用等宽字体显示文件计数（例如，“223 拒绝 · 71 天”）。与内容之间有一条底部边框。在第一部分之前有充足的底部填充。

- **页脚**：在第七部分之后。顶部边框，居中斜体 Playfair Display 标签，总结语料库（例如，“Plannotator 存档中 X 拒绝计划的 分析。”）。

### 仪表板部分顺序（7 个部分）

报告遵循此确切部分顺序。每个部分都建立在之前的部分之上——流程从“发生了什么”通过“为什么”到“如何处理”：

1. **数据中的故事** — 一段编辑式叙事段落（Playfair Display 衬线字体，约 26px），用散文讲述头条发现。不是项目符号——一个真正的段落，读起来像文章的开头。旁边是一个 KPI 侧边栏，包含 3 个关键指标（最高拒绝百分比、总体修订率以及发现的独特拒绝类别数量）。在叙事中最引人注目的数字上使用琥珀色内联高亮。

2. **计划为何被拒绝** — 分类法作为排名列表。每行：排名数字（等宽字体），类别标签，细 4px 进度条（第一项为 amber-500，其余为 slate-300），百分比（等宽字体），对于顶部条目，在标签下方显示来自数据的真实斜体引言。显示前 10 个类别或数据支持的数量（最少 5 个）。

3. **期望如何演变** — 每个自然时间段一张卡片。每张卡片包含：时间段名称（衬线字体），彩色大写主题短语（每个时间段不同颜色以显示进展），描述段落，底部有一个统计行（例如，“X 拒绝 · Y 叙事请求）。如果数据跨越少于 3 个不同的时间段，使用 2 张卡片或甚至一张卡片，并在内部注明进展。

4. **有效与无效** — 两个并排的卡片。左侧：绿色调（emerald-50/50 背景，emerald-100 边框）包含此审阅者成功的计划特征。右侧：红色调（rose-50/50 背景，rose-100 边框）包含代理持续出错的内容。两者都来自缩减分析。带彩色小圆点的项目符号。每张卡片 5-8 个项目。

5. **可操作的输出** — 诊断回报。以 Playfair Display 叙事句开头，说明导出了多少提示指令，以及估计的拒绝百分比（使用第 3 阶段的真实计算百分比，而不是通用数字）。然后是前 3 个最有影响力的改进，作为编号项目，每个项目都有一个琥珀色数字、粗体标题和一句话描述。本节连接了分析和后续的完整提示。

6. **最常用的短语** — 2 列移动端，3 列桌面端的芯片网格。每个芯片：左侧为等宽字体引号短语，右侧为频率计数。白色背景，slate-200 边框，rounded-12px。显示 9-12 个最常用的短语。这些应该是审阅者的实际话语——他们的口头指纹。

7. **纠正提示** — 深色面板（slate-900 背景，白色文本，rounded-3xl，shadow-xl）。以 Playfair 开头介绍指令。然后是一个深色代码块（slate-800/80 背景，amber-200 等宽文本）包含第 3 阶段的完整编号提示指令。包含一个可工作的复制到剪贴板按钮（包含 JS）。代码块下方：一个渐变辉光卡片（靛蓝色到紫色的模糊光晕背后有一个白色卡片）带有结束信息，说明这些指令是个人化的——来自用户的反馈、用户的语言、用户的标准。

### 适应规则

- 如果用户的数据少于 3 个月，将演变部分减少到较少的卡片
- 如果大多数被拒绝的文件在 `---` 下方没有反馈（没有注释的裸拒绝），请在叙事中注明——分析将更薄
- **Claude 代码回退模式**：明确将报告来源标记为 Claude 代码 `ExitPlanMode` 拒绝原因。不要编造 Plannotator 仅有的字段，例如注释计数或批准计划行计数。参见回退参考以获取 KPI 替代方案和页脚/来源指导。
- 如果少于 5 个拒绝类别出现，将分类法和模式部分合并为一个
- 如果数据集非常小（< 20 个文件），叙事应承认样本量有限，并将发现作为初步发现
- 提示指令的数量将因用户而异——可能是 8 个或 20 个。不要强制 17 个。让数据决定数量。
- 第 5 部分中的前 3 个可操作项目必须是覆盖最大拒绝份额的 3 个，而不是听起来最令人印象深刻的 3 个

### 关键规则

1. 每个数字必须来自真实分析——没有虚构数据
2. 每个引言必须是来自真实文件的引言
3. 分类法百分比必须从真实计数计算
4. 提示指令必须追溯到实际的拒绝模式
5. 提示块上的复制按钮必须工作（包含 JS）

生成后，在用户的浏览器中打开该文件。

## 第 5 阶段：摘要

告诉用户：
- 分析了多少个拒绝文件
- 如果增量：自上次报告以来有多少个是新文件
- 发现的前 3 个拒绝模式
- 估计的提示指令将解决多少拒绝百分比
- 最有影响力的提示改进
- 报告保存的位置（包括版本号）
- 如果增量：提醒用户之前的发现在之前的报告中

**Claude 代码回退模式**：根据回退参考调整摘要——报告分析的人类拒绝原因和扫描的总 `ExitPlanMode` 尝试次数，而不是 Plannotator 文件计数。

## 第 6 阶段：改进钩子

在展示摘要后，询问用户是否要启用**改进钩子**——这将报告第 7 部分的纠正提示指令写入文件，Plannotator 的 `EnterPlanMode` 钩子可以自动将其注入每个未来的规划会话。

> “您是否希望启用改进钩子？这将保存纠正提示指令到文件中，该文件将自动注入所有未来的规划会话——因此 Claude 在编写任何计划之前都能看到您的反馈模式。”

**如果同意：**

钩子文件位于：

```
${PLANNOTATOR_DATA_DIR:-~/.plannotator}/hooks/compound/enterplanmode-improve-hook.txt
```

如果数据目录中不存在，请创建 `hooks/compound/` 目录。

文件内容应包含第 3 阶段的纠正提示指令——HTML 报告第 7 部分中出现的相同编号列表。按纯文本写入，每行一个指令，前缀为其编号。没有 HTML，没有 markdown 签名，没有前言——只是指令本身。钩子系统将此文件的内容原样注入规划上下文中。

**如果文件已存在：**

读取现有文件，并让用户选择：

> “之前的分析已经存在改进钩子。我可以：
>
> 1. **替换**——用新指令覆盖（旧指令已丢失）
> 2. **合并**——合并两者，删除重复的指令，保留每个指令的最佳版本
> 3. **保留现有**——保持当前钩子不变，跳过此步骤
>
> 您希望如何操作？”

- **替换**：用新指令覆盖文件。
- **合并**：读取现有指令，与新指令比较，并生成合并集。删除重复项（即使措辞不同，意图相同）。当两个指令覆盖相同模式时，保留更具体或更有操作性的版本。重新编号最终列表。将合并结果写入文件。向用户展示更改（添加 N 个新，删除 N 个冗余，保留 N 个现有）。
- **保留现有**：什么也不做，继续。

**如果不存在**：完全跳过此阶段。

## 重要说明

- **数据源优先级**：Plannotator 是首选路径。Claude 代码日志分析是用户没有 Plannotator 存档的次要路径。
- **研究诚信**：每个文件都必须读取。此分析的价值来自完整性。抽样或跳过会损害发现。
- **仅使用真实数据**：永远不要虚构引言、百分比或模式。如果数据显示不出明显模式，请诚实说明，而不是编造一个。
- **让数据引导**：分类法、模式和指令应从文件中实际内容中产生。不同的用户将具有完全不同的拒绝模式。构建移动应用的用户将具有不同的反馈，而构建 API 的用户则不同。不要假设模式会是什么。
- **代理并行化**：对于大型数据集，最大化并行代理以减少墙上时间。瓶颈是最大的批次——将其拆分。
- **结构化提取格式**：要求提取代理返回具有一致分隔符的结构化文本，以便缩减代理可以可靠地解析。
- **报告是工件**：HTML 仪表板是用户保留的。它应该是美丽的、诚实的、有用的。每个部分都应感觉像是专门为用户编写的，因为确实如此。
