# discover-event-surfaces

你处于分析工具化工作流程的第 2 步。读取一个 `change_brief` YAML 文件，并生成一份详尽的分析事件候选列表——命名规范、按类别组织，并准备好供产品经理（PM）审核。

像一位既负责发布功能又关心功能是否成功的工程师一样思考。生成能够回答产品/业务问题的分析事件，而不是反映实现细节的事件。目标是**广度与质量**——下游技能将缩小列表。

阅读 `../taxonomy/SKILL.md` 中的 `taxonomy` 技能，以了解核心分析理念命名标准。

---

## 1. 解析 change_brief

- `classification.analytics_scope` — 如果为 `none`，则停止并告知用户没有需要工具化的内容。
- `summary` — 变更的一行描述。
- `user_facing_changes` — 主要信号。每个条目 = 用户现在可以不同地执行或看到的内容。
- `surfaces.components` — 修改的 UI 组件；交互发生的地方。
- `file_summary_map` — 读取 `surfaces` 或涉及用户面逻辑的文件中的摘要。跳过测试/配置/工具。

## 2. 扫描代码库并映射用户流程

在生成任何事件之前，构建对用户如何通过功能的实际理解。变更简报提供了文件路径和摘要——现在读取实际代码以追踪完整旅程。

### 要读取的内容

- 列表在 `surfaces.components` 中的每个文件——完整读取它们。
- 来自 `file_summary_map` 且涉及用户面逻辑的文件（跳过测试、配置、工具）。
- 跟踪导入和引用的一级：如果一个组件调用钩子、API 函数或导航到另一个路由，也要读取目标文件。这是你发现 diff 未触及但属于同一流程的步骤的方式。

### 要寻找的内容

追踪用户从入口到结果的路径：

- **入口点** — 用户如何到达？路由定义、导航调用、菜单项、链接、功能标志门。
- **交互序列** — 用户按步骤执行什么？表单填写、选择、确认、上传。查看处理程序接线（`onClick`、`onSubmit`、`onChange`）及其改变的状态。
- **异步边界** — API 调用、变更、服务器操作。这些是“尝试”变为“成功”或“失败”的地方。
- **终端状态** — 成功确认、错误处理、重定向、完成屏幕。
- **分支路径** — 将用户路由到不同结果的条件（例如，免费与付费、首次使用与返回）。

### 生成漏斗假设

将你的发现综合为一条或多条漏斗——从入口到结果的有序用户步骤序列。每个漏斗应有：

- 描述性名称（例如，“属性提取流程”、“引导向导”）
- 有序步骤，每个步骤包含发生该步骤的文件和函数/处理程序
- 哪个步骤是**开始**，哪个是**结束**

并非每个变更都有漏斗。单操作功能（切换开关、一键导出）不需要——只需注意没有多步骤流程即可。但当流程存在时，在此处映射它允许你后来自信地分配漏斗开始/结束为关键。

基于你实际读取的代码保持假设的可靠性。不要编造你没有证据支持的步骤。

## 3. 确定命名规范并获取现有事件

调用 `discover-analytics-patterns` 并使用其 `event_naming_convention` 和 `property_naming_convention` 输出。该技能拥有命名解析程序和优先级顺序。在此处不要重新定义它。

在生成候选事件之前，获取项目的现有事件分类法，以便避免重复并匹配已使用的命名规范。

### 解析项目

如果变更简报包含 Amplitude `projectId`，则直接使用它。否则，调用 `get_amplitude_context` 以解析项目名称或询问用户要针对哪个项目。你需要 `projectId` 进行下一步调用。

### 获取现有事件

检查连接的目录并使用其当前分类法事件读取器与解析的 `projectId`。仅遵循其宣传的架构。当它支持调用者归因时，使用其 YAML 前面的 `name` 来识别此技能。不需要游标——第一页就足够用于模式检测。当其架构支持字段选择时，请求事件名称、类别和描述字段，然后使用返回的字段名称。

### 构建命名参考和现有事件索引

1. **现有事件索引** — 将所有 `eventType` 值收集到一个集合中。你将在第 4 步中检查候选事件以避免提议已跟踪的事件。如果事件的语义意义与现有的 `eventType` 匹配，则它是重复的，而不仅仅是字符串完全匹配——例如，如果 `Subscription Upgraded` 存在，则不要为同一操作提议 `Plan Upgraded`。

## 4. 生成候选事件

从漏斗假设开始。如果你在第 2 步中识别了漏斗，首先为漏斗开始和结束生成事件——这些是你的锚点。然后填充中间步骤和非漏斗表面的候选事件。

对于每个 `user_facing_change`，问：“如果用户执行此操作——PM 想要了解哪些结果？”

从四个类别生成（按优先级排序）：

| 类别             | 它捕获的内容                                                                                                  | 包含时机                                      |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| **business_outcome** | 收入、留存、增长操作（购买、订阅变更、转化门）                                                              | 变更触及变现或留存表面                         |
| **user_journey**     | 有意义的状态转换（工作流完成、功能激活、引导完成）                                                             | 变更引入或改变用户旅程步骤                      |
| **feature_success**  | “它成功了”的时刻——确认结果，而不是按钮点击（创建文档、生成报告）                                                   | 任何新或实质性变更的功能                      |
| **friction_failure** | 用户失败、卡住或放弃的地方（错误、空状态、放弃）                                                               | 复杂的多步骤交互或易出错的流程                |

### 与现有事件去重

生成候选事件后，检查每个候选事件与第 3 步中构建的**现有事件索引**。对于每个候选事件：

- **完全匹配** — `eventType` 已存在字面值。丢弃候选事件。
- **语义匹配** — 不同名称跟踪相同用户操作或结果（例如，你提议了 `Plan Upgraded`，但 `Subscription Upgraded` 已存在以跟踪同一操作）。丢弃候选事件。
- **部分重叠** — 现有事件覆盖更广泛的操作，该操作包含你的候选事件（例如，`Checkout Completed` 已存在，而你的候选事件 `Payment Submitted` 在同一时刻触发）。除非候选事件捕获有意义不同的信息，否则丢弃。

如果你因为事件已存在而丢弃候选事件，请在输出中的 `already_tracked` 列表中记录它，以便用户可以看到哪些内容已覆盖。

## 5. 质量过滤

每个候选事件必须通过所有三个：

1. **决策有用** — PM 可以仅凭此事件做出产品决策，而无需其他五个事件提供背景。
2. **结果导向** — 捕获了“发生了什么”，而不是用户“尝试了什么”。`Property Extracted` > `Extract Button Clicked`。优先考虑确认结果；当没有服务器确认时，表单提交是可接受的。
3. **跨重新设计稳定** — 围绕业务/产品概念命名，而不是 UI 元素。如果重命名模态会导致事件名称过时，则它耦合过紧。

**丢弃：** 没有结果的原始点击/悬停、内部技术操作（API 回调、状态更新）、UI 版本化名称（`modal_v2_submit`）、子步骤级粒度。

## 6. 命名事件

使用 `discover-analytics-patterns` 返回的命名规范。新事件应看起来像它们属于其他工具化的一部分：相同的 casing、相同的词序、相同的分隔符、相同的前缀模式，以及相同的粒度。

如果你后来需要在理由或工具化提示中建议属性名称，请使用 `discover-analytics-patterns` 返回的 `property_naming_convention`。

在所有情况下，使用产品领域主语（属性、用户、文档），而不是代码名称（属性项、操作存储）。

| 良好（标题大小写规范） | 坏                        |
| --------------------- | ------------------------ |
| `Property Extracted`  | `extract_property_clicked` |
| `Extract Type Configured` | `type_dropdown_changed`    |
| `Property Creation Failed` | `500_error_new_property`   |

## 7. 确定文件和工具化点

对于每个候选事件，使用 `file_summary_map` 和 `surfaces.components` 来识别：

- **`file`** — 跟踪调用所属的源文件。优先选择最接近结果确认的文件（而不是用户发起操作的文件）。通常是来自 `surfaces.components` 的组件文件或异步操作解析的钩子。
- **`instrumentation`** — 1-2 句话：*何时*触发（在什么条件/回调/状态转换之后）以及*如何*接线（将它在哪个函数/处理程序中放置）。引用文件摘要中的实际函数名称，以便工程师可以找到正确的行。

## 8. 深化理解，然后优先级排序

对于每个候选事件，首先处理这两个字段——它们迫使你具体思考事件的价值，然后再对其进行评分：

- **`analysis_recipe`** — 描述分析师将使用此事件构建的具体图表、漏斗或查询。具体说明：提及可视化类型、细分维度以及与其他事件组合的任何其他事件。例如，*"每周漏斗：Panel Opened → Extract Type Selected → Property Extracted，按 extractType 分段。如果完成率低于 50%，则发出警报。"*。
- **`stakeholder_narrative`** — 写一句 PM 可以放入季度回顾或董事会演示文稿中的话，使用此事件的数据。想象指标已存在并写出它讲述的故事。例如，*"68% 尝试提取的用户在第一次尝试中完成，较上一季度的 45% 有所提高。"* 如果你无法想象一个有说服力的幻灯片句子，该事件可能不值得工具化。

现在，带着这个背景，分配一个**优先级**：

| 优先级         | 含义                                                                                                            | 指导                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **3** (关键)   | 如果你缺少此事件，你会阻止发布。它回答了团队将在第一周提出的疑问。                                                     | 保留用于直接衡量功能是否成功或失败的事件。大多数变更只产生 1-2 个关键事件。                                                           |
| **2** (有用)   | 添加了真正的分析价值，但功能可以在没有它的情况下发布。如果工具化成本较低，则值得添加。                                     | 细分维度、次要工作流、配置选择。                                                                                                   |
| **1** (可选)   | 可选的。只有在团队有带宽和特定假设要测试时才工具化。                                                               | 边缘案例失败、探索性参与信号、可发现性指标。                                                                                         |

**漏斗事件值得特别关注。** 当变更引入或修改多步骤流程（结账流程、引导向导、数据导入管道）时，PM 的第一个问题是“用户在哪里流失？”漏斗开始和漏斗结束之间的差距，在中间没有可见性，是一个盲点，可能隐藏严重的产品问题——如果参与度在第 5 步中的第 2 步骤骤骤下降，团队需要知道，而不是猜测。

**漏斗开始和漏斗结束事件始终是关键的（优先级 3）。** 没有书签，你无法衡量转化率——任何漏斗最重要的指标。这两个事件是不可协商的，无论漏斗长度或复杂性如何。

要决定标记多少个*中间*漏斗事件为关键，评估漏斗的长度和复杂性：

- **短流程（2-3 步骤，单页）**：开始和结束事件就足够了。不要在简单流程中工具化每个微步骤。
- **中等流程（3-5 步骤，可能跨越页面）**：在最有可能的流失点添加一个中间事件——通常是用户投入努力的地方（填写表单、做出关键选择、上传文件）。
- **长流程（5+ 步骤，多页或向导式）**：2-3 个中间事件在自然阶段边界。思考“开始 → 配置 → 提交 → 确认”，而不是跟踪每个字段交互。

谨慎选择中间事件。每个你标记为关键的漏斗事件都是工程师必须实现和 PM 必须监控的一件事。如果你不确定某个中间步骤是否值得跟踪，它可能不值得——开始和结束事件将揭示是否存在问题，团队可以在看到哪里流失率高后随时添加粒度。

少即是多。一个专注的关键事件集，实际上会出现在仪表板中，比一个无人查看的庞杂列表更好。当不确定时，降级——添加事件比删除已存在于仪表板中的事件更容易。

## 9. 发射 YAML 输出

仅输出 YAML 块——没有周围的文字。

```yaml

## 示例

**输入节选：**
```yaml
用户现在可以在PropertyItem面板中选择Extract Type（文本或属性）
表面：
  组件：
    - 名称： PropertyItem
      变更： modified
```

**好的候选：**
```yaml
- 名称： "属性提取"
  类别： feature_success
  理由： "核心采用信号 — 告知PM提取工作流是否完成。"
  分析配方： "每周渠道：Panel Opened → Extract Type Selected → 属性提取，按extractType细分。如果完成率低于50%则发出警报。"
  利益相关者叙述： "72%的打开属性面板的用户完成了提取，较此版本发布前的0%有所提升 — 验证了新的提取工作流。"
  优先级： 3
  表面： "PropertyItem"
  文件： "src/components/PropertiesPanel/PropertyItem.tsx"
  instrumentation： "在extract解析成功后在onSuccess处理器中触发。包含extractType (TEXT或ATTRIBUTE)。"

- 名称： "提取类型选择"
  类别： feature_success
  理由： "显示用户更喜欢哪种模式 — 指导Attribute模式的投资。"
  分析配方： "30天内文本与属性选择的饼图。与属性提取结合以获取每种模式的完成率。"
  利益相关者叙述： "85%的提取使用文本模式 vs 15%属性 — 我们应该在扩展Attribute功能之前加强文本UX。"
  优先级： 2
  表面： "PropertyItem"
  文件： "src/components/PropertiesPanel/PropertyItem.tsx"
  instrumentation： "在Extract Type选择onChange中触发，传递新值。"

- 名称： "属性提取失败"
  类别： friction_failure
  理由： "提取工作流因可靠性而需要关注的表面。"
  分析配方： "错误率图表：属性提取失败 / (属性提取 + 属性提取失败)，按错误原因分组。在尖峰时发出警报。"
  利益相关者叙述： "提取失败率从12%降至3%后v2错误处理补丁 — 用户遇到的死胡同更少。"
  优先级： 2
  表面： "PropertyItem"
  文件： "src/components/PropertiesPanel/PropertyItem.tsx"
  instrumentation： "在extract调用catch/onError中触发。如果可用则包含错误原因。"
```

**不包括：** `Extract Type Dropdown Opened`（点击，无结果）、`PropertyItem State Updated`（内部）、`Attribute Input Focused`（过于细致）。
