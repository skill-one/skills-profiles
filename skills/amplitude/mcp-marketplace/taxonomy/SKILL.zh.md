# 分类生成与数据审计

## 使用场景

- 用户需要创建或审查跟踪计划或事件分类
- 用户希望验证事件/属性命名规范
- 用户需要审计数据质量（重复项、过期事件、缺失元数据）
- 用户询问漏斗设计或事件关系
- 代理生成事件名称或属性名称并需要遵循标准
- 用户希望理解或改进其分类治理
- 用户询问减少事件数量或类型计数
- 用户询问弃用、阻止、删除或隐藏事件
- 任何代理在推荐事件之前都需要分类最佳实践的“事实来源”
- 用户询问关于人工智能准备情况、人工智能控制或提高人工智能功能准确性

# 第一层：基础概念

## 核心理念

所有分类工作都受六项原则指导：

1. **以证据为基础。绝不编造。** 每个发现都必须基于工具检索的数据。如果无法验证，请明确说明。
2. **积极扫描。自信提议。在写入前确认。** 自主地遍历整个分类。形成优先级高的、有观点的修复视图——然后呈现。未经明确用户确认，切勿调用写入工具。
3. **有观点，而非中立。** 泛请求（“审计我的分类”）是引导的邀请。使用评分框架，首先推荐影响最大的操作，并解释原因。不要呈现等价选项菜单。
4. **主动发现关键问题。** 在处理相邻任务时，如果发现重要问题，请提出。不要因为用户只询问命名规范而默默忽略PII违规。
5. **问题提取机构知识。** 询问业务意图和实际含义，而不是Amplitude机制。一次一个专注的问题。目标是提取存在于人们头脑中的知识。
6. **行动前解释。** 在调用任何写入工具之前，呈现精确的拟议更改——包括前后状态——并等待明确确认。

## 数据质量生命周期

所有分类治理遵循一个四阶段循环：

1. **检测** — 系统扫描。遍历整个分类。为每个发现评分。在得出结论之前，先展示证据和问题。
2. **澄清** — 提出一个专注的问题来捕捉语义真相。在此阶段不要建议操作。先寻求理解。
3. **解决** — 应用仅限于元数据的改进。引导人类通过分阶段弃用来进行结构性更改。切勿单方面执行破坏性操作。
4. **预防** — 推荐规范和治理习惯，以防止漂移再次发生。

## 事件数量与分类类型计数

这是**不同的问题**，需要**不同的解决方案**：

- **事件数量** = 每个计费周期内摄入的总事件实例（事件触发次数）。属性不计入数量。
- **分类类型计数** = 跨所有模式维度（事件类型、事件属性类型、用户属性类型、组类型、组属性类型）的独立名称数量。每个都有自己的限制。

**计费模式——在提供建议之前要知道哪个适用：**
- **事件数量计费**：客户每个周期有合同约定的事件配额。超出部分会触发超额费用。向这些客户标记显著的事件数量变化。
- **MTU计费**：客户根据一个月内触发任何事件的独立用户数量计费。每个用户的计费次数不太重要；总独立用户数量更重要。

**客户通常意味着什么：**
- “我需要减少我的事件数量” → 担心计费（数量计费客户）
- “我需要减少我的事件类型/模式计数” → 担心达到类型限制（新类型不可查询）

**实际减少每个的方法：**

| 目标 | 操作 | 减少数量？ | 减少类型计数？ |
|------|------|:---:|:---:|
| 减少数量 | 阻止事件 | 是 | 否 |
| 减少数量 | 删除事件 | 是 | 是 |
| 减少类型计数 | 删除事件/属性/组类型 | — | 是 |
| 减少类型计数 | 阻止事件 | 否 | **否** |
| 减少类型计数 | 隐藏事件 | 否 | **否** |

**关键规则：**
- 阻止和隐藏**不会**减少类型计数。配额受限的客户必须删除，而不是阻止。
- **永远不推荐抽样。** 抽样会破坏漏斗图、旅程路径、队列、下游目的地和Guides。
- 自定义事件和合并事件简化分析，但**不会**减少原始事件数量。
- 出现歧义时，询问：“您是想减少发送的事件数量，还是减少分类中不同事件和属性类型的数量？”

## 事件状态和元数据权限

| 状态 | 含义 | 可以编辑元数据？ |
|------|------|:---:|
| 计划中 | 在跟踪计划中；尚未实施 | 是 |
| 活跃 | 正在接收数据 | 是 |
| 阻止 | 停止新摄入；可访问历史数据 | 是 |
| 预期之外 | 接收数据，但**不在**跟踪计划中 | **否** — 必须先添加到跟踪计划 |
| 删除 | 停止摄入；已从新图表下拉菜单中移除 | **否** — 必须先恢复 |

**预期之外的事件有特殊限制。** 在事件添加到跟踪计划之前，无法更新任何元数据。当您遇到预期之外的事件时：
- 如果它们看起来合法（真实的产品操作，一致的数量）：建议先添加到跟踪计划，然后应用元数据。
- 如果它们看起来无效（单日峰值、测试字符串、安全扫描工件）：通过标准安全弃用流程将其视为弃用候选。在建议任何操作之前，始终区分“合法但未记录”与“真正无效”。

**活动状态**不是弃用信号。标记为非活跃的事件正在按预期运行。

**实际弃用信号：**

| 信号 | 解释 |
|------|------|
| 无近期数量 | 事件已过期 |
| 无近期查询 | 事件未使用 |
| **两者同时存在** | **强烈的弃用候选** |

**计划中事件：** 预期零数量和查询——通过年龄、与活跃事件名称冲突、测试类名称进行评估。

## 自定义事件、标记事件和合并事件

它们都不会减少事件数量。每个都有不同的行为：

- **自定义事件** (`ce:`前缀，类型=自定义)：为分析便利而逻辑组合的底层事件。底层事件仍然存在并独立触发。在建议删除事件之前，始终检查该事件是否用作自定义事件的基础——删除底层事件可能会无声地破坏自定义事件。允许：合并具有相同定义的重复自定义事件；改进命名、描述、类别、标签。永远不要声称删除自定义事件会减少事件数量。
- **标记事件** (`ce:`前缀，类型=标记)：设计用于与Autocapture一起使用，通过单独的元数据标志与自定义事件区分开来。添加/删除不会影响数量。
- **合并事件** (转换/合并)：合并后，源事件不再可用于单独分析。如果用户需要分析合并事件并保留对源事件的独立分析，建议使用**自定义事件**而不是合并。允许：合并真正重复的事件，它们共享相同的语义，并且不需要独立分析。永远不要声称合并会减少事件数量。

## 受保护的数据类别

**如何从命名约定中识别类别：** 带有括号前缀（`[...]`）的事件遵循一致的模式：如果括号内的文本是可识别的第三方产品品牌，则它是集成。如果不是，则是Amplitude系统事件。

**Amplitude系统事件** (`[Amplitude]`, `[Guides-Surveys]`, `[Experiment]`, 等.)：对平台功能至关重要。不要响应通用清理建议而阻止、删除、隐藏或修改。

**集成前缀数据** (`[Appboy]`, `[Adjust]`, `[Intercom]`, 等.)：可以清理，但建议首先在集成源处关闭。优先级低于原生事件。

**实验数据：** 不推荐TTL或自动删除。删除会破坏历史实验解释。

## 解释使用信号

**查询计数**反映跨用户创建对象（图表、仪表板、笔记本、队列、指标）的使用情况，但**不包括**人工智能工具、Chat、全局代理、MCP或警报。零查询是一个强烈的审查信号，而不是明确的行动信号。

**三种关键模式：**

| 模式 | 定义 | 操作 |
|------|------|------|
| 过期事件 | 之前已摄入，但数量停止 | 在弃用前与客户确认 |
| 测试事件 | 首次看到=最后一次看到，单日 | 强烈弃用候选；先确认 |
| 触发但未查询 | 有数量，零查询 | 标记审查，不是立即删除 |

**可以安全采取行动：** 6-12个月无数量。即使存在查询活动，这些查询返回零结果。

## 人工智能准备情况

将元数据和清理工作视为人工智能准备情况改进。每个人工智能功能都通过评估可见分类来选择事件——分类质量直接决定人工智能输出质量。

**将以下内容视为人工智能质量问题：**
- 没有描述的神秘事件名称——人工智能无法解释
- 重复/近重复名称的集群——人工智能会在它们之间错误猜测
- 侧重于实现的描述（例如，“POST /purchase返回200时触发”）——用户询问行为问题，而不是后端问题
- 仍然可见的大量已弃用事件——增加错误人工智能选择的噪音

**事件描述结构（按顺序）：**
1. 非技术性行为定义——用户做了什么，用普通语言
2. 触发条件——确切条件，UI vs API，仅成功或也失败，页面/URL模式
3. 消歧义——这与类似名称的事件有何不同
4. 关键用例——如果是漏斗步骤、成功指标或关键分析输入
5. 常用属性——2-3个最常用查询属性及其简要上下文
6. 技术细节（可选）——实现说明、源系统、端点

**属性描述：** 以清晰的定义开头，然后包括示例值。示例：*"用户查看的产品类别。示例：'electronics'，'apparel'，'home & garden'。"*.

**实施时的人工智能准备情况：**
- 选择清晰、描述性的事件和属性名称，无需显示名称即可解释。在实施时不建议添加显示名称——它们仅在原始名称已建立且存在歧义时才需要。
- 按照上述结构编写描述：非技术性行为定义→触发条件→消歧义→关键用例→常用属性→可选技术细节。
- 对于具有编码值（SKU、ID、状态代码）的属性：建议创建查找表将代码映射到人类可读标签（Growth和Enterprise客户可用）。

**人工智能控制建议：**
- **组织上下文**（10,000字符）：公司级标准、KPI定义、标准术语、全局过滤器、财政日历
- **项目上下文**（10,000字符）：产品级事件/漏斗、项目级指标、队列定义
- 使用审计发现来填充这些建议。跨多个事件反复出现的行话或缩写应属于组织/项目上下文，而不仅仅是个人描述。一致的结构性模式（命名约定、事件分组）是帮助人工智能整体解释分类的有用项目上下文。

# 第二层：按操作类型的规则

## 读取和分析（始终安全）

读取和分析操作没有风险——自主且果断。有关工具使用策略和分步程序，请参阅治理技能中的数据质量审计程序。

## 写入或更新元数据

**所有写入都需要/前后确认。** 永不自动应用。仅更新确认的项目——不要基于模式推断扩展到类似项目。

**字段默认值：**
- **描述：** 除非明显错误，否则不要删除现有内容。附加或合并现有详细信息。
- **类别：** 仅当为空时设置。如果明显错误或用户请求，才建议更改。
- **标签：** 仅添加；除非明确请求，否则永不删除。
- **显示名称：** 遵循项目的现有命名约定。

**限制：**
- 除非明确请求，否则不要写入带括号前缀或供应商前缀的事件。
- 永不写入预期之外或已删除的事件（必须先添加到计划/恢复）。

**写入因权限失败时：**
- 解释用户缺乏写入权限。
- 提供仅限读取的指导，说明可以做什么以及原因。
- 提供用户可以共享的“请求管理员应用此操作”摘要。

## 建议清理或弃用

弃用必须始终遵循分阶段过程。有关分步程序，请参阅治理技能中的弃用工作流。

**永不：**
- 将删除/隐藏/阻止作为立即一次性解决方案呈现
- 建议抽样、TTL、自动删除规则或在不同项目之间移动事件
- 建议重新配置上游集成以控制数量
- 在建议弃用之前跳过依赖检查

## 建议新实施

### 事件命名标准

**格式：`[对象] [过去时动词]`，首字母大写**

| 好 | 坏 | 原因 |
|------|------|------|
| `Song Played` | `Play Song` | 过去时=完成动作 |
| `Form Submitted` | `Submit Form` | 名词优先=可扫描、可排序 |
| `Product Added` | `product added`, `product_added`, `productAdded` | Amplitude将不同大小写视为独立事件——始终使用首字母大写，而不是snake_case或camelCase |

**一致性是最高优先级。** 如果现有分类使用了一致但与理想不同的约定，请匹配现有约定，而不是引入新模式。

**用户视角，而非系统视角：**
- `Message Sent`（用户发送）而不是`Message Delivered`（系统发送）
- `Purchase Completed`（用户完成）而不是`Payment Processed`（系统处理）

**具体性平衡——一个事件+属性，而不是多个事件：**
- **好**：`Order Completed` with property `payment_method`
- **坏**：`Credit Card Order Completed`, `Apple Pay Order Completed`

**跨平台一致性：** 同一用户操作=同一事件名称，跨Web、iOS、Android。平台差异放在`platform`属性中。

**一个动作=一个事件名称。** 代码库中没有重复。

**Autocapture优先：** 不要为Autocapture已捕获的内容推荐自定义事件：`Page Viewed`, `Element Clicked`, `Element Changed`, `Form Started`, 等.

### 属性命名标准

- **`snake_case`** 用于所有属性名称
- **描述性和具体**：`payment_type`而不是`type`, `error_message`而不是`message`
- **当歧义时包含单位**：`video_duration_seconds`, `file_size_mb`, `price_usd`
- **时间戳约定**：`[事件名称]_at`（例如，`product_added_at`）
- **跨事件一致**：同一概念使用相同名称。`product_name`必须在每个事件中都是`product_name`——不是`name`, `prod_name`, 等。
- **不同概念使用不同名称**：`login_method`和`payment_method`，而不是通用的`method`用于两者
- **点表示法**：表示嵌套对象已传递（Amplitude自动创建）。除非有意使用嵌套对象，否则不要在属性名称中直接使用点表示法。在审计期间，点表示法属性的集群是一个清理信号——检查哪些属性实际上正在被查询。如果相当一部分未使用，建议在源处修剪对象以减少分类噪音。

### 属性类型标准

| 类型 | 格式 | 示例 |
|------|--------|---------|
| ID | 始终为字符串 | `"user_id": "12345"` 而不是 `12345` |
| 计数/金额 | 数字 | `"order_total": 59.99` |
| 标志 | 布尔值 | `"is_premium": true` |
| 时间戳 | ISO 8601 字符串 | `"2024-03-10T14:30:00Z"` |
| 枚举/状态 | 字符串 | `"status": "In Progress"` |
| 空值处理 | 每个属性选择一种方法 | 省略、`null` 或哨兵字符串（如 `"Unknown"`）—— 永不混合。使用显式哨兵字符串可以区分有意不可用的值和测量工具错误。不一致的空值处理是最常见的导致属性过滤器错误和漏斗中断的原因之一。 |

### 用户识别标准

- **匿名用户**：仅设置 `device_id`。不要设置 `user_id`。
- **已认证用户**：为每个经过验证的用户设置唯一的、稳定的 `user_id`。登录/验证前永不设置。
- **服务器端事件**：为每个事件包含唯一的 `insert_id` 以进行去重（7天窗口）。
- **会话**：在会话内使用一致的 `session_id`；对于服务器端，使用第一个会话事件的时间戳。

### 结构模式

- **A/B 实验**：作为列表用户属性跟踪，而不是事件
- **错误**：一个 `Error Encountered` 事件，带有 `error_type`/`error_category` 属性
- **电子商务**：使用 `product_engagement`（此操作中的项目）+ `cart_contents`（完整购物车快照）数组
- **B2B**：至少为一个组类型（`org_id`、`account_id`）进行测量
- **漏斗中的属性一致性**：在漏斗中的所有事件中捕获相同的属性（例如，`product_id`）

### 类别分配

使用 Amplitude 类别元数据字段——不要在事件名称中嵌入前缀。常见类别：

| 类别 | 目的 | 示例 |
|----------|---------|---------|
| 生命周期 | 用户旅程里程碑 | 注册完成、试用开始、订阅取消 |
| 功能 | 核心产品功能 | 任务创建、文档编辑、报告生成 |
| 参与度 | 导航和 UI 交互 | 页面浏览、按钮点击、搜索执行 |
| 交易 | 收入事件 | 购买完成、结账开始、退款请求 |
| 系统 | 技术健康 | 错误发生、API 请求完成、超时发生 |
| 增长 | 获取和推荐 | 邀请发送、分享完成、推荐奖励获得 |

**分配启发式方法：**
- 如果事件表示首次或里程碑用户操作（注册、首次购买、首次邀请），优先考虑 **生命周期** 而不是功能或交易。
- 如果事件记录的点击或查看不是核心产品操作，优先考虑 **参与度** 而不是功能。
- 集成源事件（`[Appboy]`、`[Adjust]` 等）可能无法整齐匹配——根据集成的目的分配系统或增长，或留空未分配。
- 当正确的类别不明确时，询问客户而不是猜测。

## 评分和优先级排序问题

三个维度：

### 1. 问题影响

| 级别 | 分数 | 定义 | 示例 |
|-------|--------|------------|---------|
| 高 | 3 | 名称模糊——分析师无法可靠地解释 | 行话、缩写、模糊词语、易混淆名称 |
| 中 | 2 | 名称可解释，但分类更混乱 | 常规异常、计划外的意外事件 |
| 低 | 1 | 名称清晰；问题是缺少完善 | 名称自解释时缺少描述 |

### 2. 事件重要性

- **查询频率**：30/60/90/180天计数——高查询事件影响更多分析
- **数量**：高数量 = 更多成本和风险
- **首次出现**：非常近 = 早期验证，防止问题累积
- **最后出现**：遥远 = 陈旧信号

### 3. 工作量

- **低**：仅元数据更改（描述、显示名称、类别、标签、隐藏）
- **中**：需要利益相关者验证或依赖检查
- **高**：需要代码库更改或集成重新配置

**优先级**：优先处理高影响的高重要性事件。陈旧/测试事件是快速胜利——在真实数据质量问题下方显示它们。

**健康评级**：（获得总分 / 可能总分）× 100%
- 0-49%：需要改进
- 50-79%：符合预期
- 80-100%：超出预期

## 权限边界（仅元数据）

**允许（非破坏性、仅元数据、经用户批准）：**
- 更新显示名称、描述、类别、标签
- 设置官方状态
- 隐藏事件（不阻止或删除）
- 设置自动任务
- 在项目设置中添加 AI 上下文

**不允许：**
- 阻止、删除、合并或转换事件
- 阻止/丢弃过滤器
- 修改摄取管道或上游集成
- 任何类型的采样策略

# 第三层：检测参考

## 检测信号和阈值

默认回顾期：**180 天**。

| 信号 | 优先级 | 操作 |
|--------|----------|--------|
| 语义不明确的名称 | 高 | 添加显示名称 + 描述 |
| 缺少描述（名称不明确） | 高 | 按照AI准备公式添加描述 |
| 语义重复（真——相同含义，不同大小写） | 高 | 合并或消除歧义 |
| 语义重复（相似——不同名称，相同操作） | 高 | 调查；合并或消除歧义 |
| 零数量（180 天） | 中 | 调查后再行动 |
| 零查询（180 天） | 中 | 首先检查资产依赖关系 |
| 跨事件 + 用户范围的重复属性 | 中 | 明确正确的事实来源 |
| 缺少描述（名称清晰） | 低 | 添加描述；降级 |
| 缺少类别 | 低 | 添加类别 |
| 命名规范异常 | 低 | 标记以供未来重新调整 |
| 意外的事件/属性 | 低 | 添加到计划或审查后阻止 |
| 陈旧（最后出现超出回顾期） | 低 | 快速胜利——安排淘汰 |
| 单日（首次出现 = 最后出现） | 低 | 快速胜利——可能是测试；先验证 |
| 测试/QA 产物（`test_`、`debug_`、`tmp_`、`_qa`） | 低 | 快速胜利——标准淘汰流程 |

**例外**：当客户接近配额时，陈旧/单日/测试信号成为高优先级。

## 关键审计指标

| 指标 | 影响 |
|--------|--------|
| 类型配额限制的百分比 | 高当 >90% |

| 最近7天总事件数量变化 | 高如果意外 |
| 按名称重复类型数量 | 高 |
| 未测量的组类型（B2B产品） | 高 |
| A/B 实验作为事件而不是用户属性跟踪 | 中 |
| 180天内零查询的事件 | 中 |
| 180天内零数量的事件 | 中 |
| 单日事件 | 中 |
| 活跃事件描述的百分比 | 低 |
| 活跃事件类别的百分比 | 低 |
| 意外的事件/属性数量 | 低 |
| 命名规范不一致 | 低 |

# Amplitude MCP 能力选择

在运行时检查连接的公共 Amplitude MCP 目录。工具名称和包装器在发布期间可能会更改或以不同的方式公开，因此请从其宣传的描述和模式中选择功能，而不是依赖此技能中记录的名称。

## 上下文和发现

- 使用项目上下文功能发现可访问的项目 ID 并读取选定项目的设置。当有多个项目可用时，请要求用户选择；从不从项目名称推断 ID。
- 当公开时，使用分类搜索进行事件和属性发现；否则，过滤和分页活动分类读取器。使用实体搜索进行图表、仪表板、笔记本、实验、队列和保存内容。
- 在任何写入之前，使用工作区或分支功能检查批准要求、分支保护、权限和当前分支。

## 分类读取

- 当目录公开时，优先使用综合分类读取器。使用其宣传的区分符选择原始事件、自定义/标记事件、事件属性、用户属性、组属性、派生属性、查找、渠道或持久属性。
- 如果目录公开单独的事件或属性读取器，仅使用其记录的过滤器和分页字段。不要发明别名或从另一个读取器复制参数。
- 从返回的分类行解析事件和属性名称。名称区分大小写；不要替换显示名称。
- 通过每个游标分页详尽读取。当响应报告总数时，将其与累积行进行核对；否则，需要读取器记录的终端游标条件。失败或部分页面不是完成。
- 使用可用的转换读取器进行审计事件/属性合并、值映射或其他清理规则。

## 元数据更新

- 仅在验证其当前模式支持请求的对象类型、元数据字段、分支选择器和范围后，选择事件或属性变异功能。
- 首先读取确切的当前对象。仅更新明确确认的字段，除非用户要求替换，否则保留现有描述，并且不要从较旧的工具版本推断不支持的参数。
- 事件属性元数据可以是全局的，也可以针对一个事件。使用模式的显式范围控制；从不假设省略意味着全局，除非当前模式记录了它。
- 自定义/标记事件定义是完整替换，不是合并。传递完整的已验证定义，并警告重命名可能会破坏引用。
- 除非用户明确要求，否则永不更新括号前缀或供应商前缀的系统事件。
- 在任何写入之前需要明确确认，并尊重跟踪计划写入权限和分支保护。
