# Mastra 工厂主管

使用 `mastra api factory` 作为工厂的操作控制平面。

## 首次使用：检查前先连接

阅读 [`references/connection.md`](references/connection.md)。检查 CLI 可用性，建立用户的实际工厂 URL，对于平台托管的部署运行 `mastra auth whoami`。如果已登出，则提供 `mastra auth login` 而不是静默启动浏览器登录。本地/自托管认证可能有所不同。

从空目录运行显式的 `mastra api --url "$FACTORY_URL" factory project list` 可以工作；不需要已部署的仓库或 `.mastra-project.json`。永远不要假设共享主机、组织、项目名称或 ID。在后续命令中保留显式目标。

## 默认行为

对于状态、检查、诊断、队列审查或建议请求：

1. 保持只读。
2. 选择唯一或显式命名的项目；在模糊时报告选择。
3. 检查项目状态、工作项、指标、阈值、决策、关注点和主管健康/会话。
4. 关联阶段、修订、会话、决策和健康发现。
5. 报告活动/排队的工作、阻塞或状态不健康的项目、运行中的会话、待处理的决策、人工关注，以及一个建议的下一步操作。
6. 只有当当前请求或先前授予的操作范围授权时，才执行建议。

## 必需参考

在运行工厂命令以控制输出、合同、只读工作流、变异协议、治理约束、持久会话限制和错误处理之前，阅读 [`references/factory-supervisor.md`](references/factory-supervisor.md)。

对于“我的工作”、实际执行进度、线程消息、内存或健康解释，也阅读 [`references/session-inspection.md`](references/session-inspection.md)。区分卡片阶段与运行代理、历史消息与当前内存、代理声明与验证的仓库结果。

## 安全边界

- 永远不要读取或泄露 `.env`、令牌、保存的登录内容或平台/提供者凭证。
- 永远不要编造 ID、阶段、修订、请求 ID 或会话。
- 在变异前建立用户的操作范围。授权可能涵盖一个操作或授予对命名项目、资源、操作类型或目标的命名自主权。
- 在明确的授权范围内，在每次变异前无需询问确认。只有在操作模糊、超出范围或比授予的权限实质上更具破坏性时才询问。
- 在写入前获取当前状态，做出范围内的最小变更，然后重新获取并报告 ID、修订和最终状态。
- 使用转换而不是元数据更新来进行阶段变更，使用当前修订和一个新的 UUID 请求 ID。
- 永远不要使用私有 HTTP 路由来绕过不受支持的 CLI 操作。
- 如果 `work-item start` 缺少支持的持久用户会话，报告阻塞；永远不要替代主管会话或编造会话 UUID。
