# 调试和修复

找出失败的根源，然后在用户选择时，以测试优先的原则进行修复。

**完成标准：** 从触发因素到症状的因果关系链被完整陈述，且具有文件：行号证据，并且要么已移交经过验证的修复（PR、提交，或用户选择的停止点），要么已交付诊断摘要。**优先升级而非坚持：** 2-3个假设被穷尽而未经确认，或3次失败的修复尝试，意味着诊断“为什么”而不是再次尝试——这就是 `references/investigate.md` 描述的智能升级。一个假设，一次更改；同时更改多个以查看什么有效是散弹调试。

`<bug_description>` 是此技能被调用时提供的任何内容——失败描述、`mode:` 令牌或问题引用（`#123`、`org/repo#123`、问题URL）——来自用户或调用技能（`ce-babysit-pr` / `lfg` 在 `mode:pipeline` 传递失败的作业和日志尾部；`lfg` 的缺陷路线传递 `mode:return-to-caller` 和用户的引用）。如果未提供任何内容，则为空。

## 模式

默认为 **交互式**：调查，运行第2阶段修复选择门，然后运行第4阶段移交。

**`mode:pipeline`**（由 `ce-babysit-pr` 或 `lfg` 等编排器设置）：完全非交互式运行，并且永远不会调用阻塞问题工具。从 `<bug_description>` 中移除令牌，然后 **阅读 `references/pipeline-mode.md` 并遵循它**——它用保守的默认值覆盖了所有“询问用户”点，将第2阶段修复门替换为“修复收敛性错误，推迟发散性错误”，并将第4阶段移交替换为具有 `status` 恰好为 `fixed-and-pushed | fixed-not-pushed | diagnosed-no-fix | flaky-infra | needs-human` 的结构化返回。调用者根据这些确切的拼写分支，因此永远不要重命名、缩写或添加到它们。

**`mode:return-to-caller`**（由 `lfg` 在其缺陷路线设置）：非交互式运行，但调用者拥有修复后的所有内容。移除令牌，然后 **阅读 `references/return-to-caller.md` 并遵循它**——它保留第0-3阶段和收敛或推迟修复边界，应用第3阶段分支规则，使修复位于特性分支上，提交修复拥有的文件而不推送，跳过修复后的精炼和审查步骤，并返回具有 `status` 恰好为 `fixed | diagnosed-no-fix | needs-human | blocked` 的结构化结果。相同的拼写规则适用。

## 阻塞问题

每当此技能询问用户内容时，使用主机当前工具列表中已有的阻塞问题工具（按能力匹配，而不是按主机特定名称）。存在于当前工具列表中是工具存在的证明；永远不要调用面向用户的问题工具来发现它是否存在。如果列出了匹配的工具但已卸载，则使用主机的工具发现原语加载该功能——不要搜索另一个主机的工具名称。仅在列表中不存在此类工具或真实问题调用出错时，才回退到主机聊天界面的编号选项。永远不要无声地跳过问题，并且永远不要在未获得响应的情况下结束阶段。

## 证据中的秘密

调试不断显示原始输出——命令结果、捕获的有效载荷、日志摘录——并且 harness 可能会在命令运行时渲染命令的输出，因此请在构建命令时检查秘密，而不是之后。将凭证保存在环境变量中而不是命令行上；当命令的输出可能包含秘密（详细 HTTP 跟踪、转储的标题、配置或环境打印）时，将其捕获到文件中，并仅显示清理后的摘录，将 `<REDACTED>` 写入每个秘密的位置。任何秘密（凭证、令牌、认证头、连接字符串）都不会出现在任何显示、写入或提交的内容中。如果清理移除了诊断所需的内容，请说明并询问用户，而不是取消清理。

## 证据根

仅在您首次组成 `<root>/` 路径时才解析 `<root>`——一个不组成任何 `<root>/` 路径的运行将完全跳过此步骤。

<!-- ce-docs-root:start -->
**在组成任何证据路径之前解析 CE 证据根 `<root>`。**

- 仅从 `<repo-root>/.compound-engineering/config.yaml` 读取 `docs_root`（`<repo-root>` = `git rev-parse --show-toplevel`）。不要从 `config.local.yaml` 读取它。未设置 -> `<root>` 是 `docs`，与之前完全相同。
- **验证** 设置的值：一个相对于存储库的目录，其真实路径（解析符号链接后）仍然在存储库内，并且既不是存储库根，也不在 `.git/` 下。否则出错，并命名 `docs_root` 和值——永远不要回退到 `docs`。
- **使用** `<root>` 作为唯一的证据位置：如果不存在则创建它，使用此技能自己的子目录，将每个路径组成 `<root>/<subdir>`，并且永远不要再读取 `docs`。

## 执行流程

五个阶段按顺序：**0 分诊 -> 1 调查 -> 2 根本原因 -> 3 修复 -> 4 移交。** 除了 0 阶段的 trivial-bug 快速路径外，没有跳过和复杂性级别。一个难缠的错误在每个阶段花费更长时间；它不会进入较少的阶段。

**现在阅读 `references/investigate.md` 并遵循它以进行第 0-2 阶段**——问题获取、可重复性、环境健全性和脏树暂存实验、反向跟踪、跟踪器/PR 历史搜索、假设基础和升级表。下面仅陈述以下门。

**记录中的问题。** 如果用户将工单或问题交给您，那么这个错误已经在其中某个系统中存在，无论它是什么系统；Sentry 问题与 Linear 工单一样重要。携带其标识符和 URL 到第 4 阶段。如果输入只是一个堆栈跟踪、测试路径或描述，则此运行**没有记录中的问题**。这是一个普通状态，不是需要填补的空白：没有记录地发送修复，永远不要打开工单来制造记录，并且永远不要询问用户是否要。第 1 阶段的跟踪器搜索读取先前的工作，并且**永远不会为错误建立新家**。此错误的一个现有工单是在第 4 阶段*链接*，而不是创建。

**trivial-bug 快速路径**（从输入中可读的原因、单行修复、无需深度跟踪）仍然在编辑之前运行第 2 阶段的修复选择门：它节省了调查仪式，而不是用户是否要应用修复的选择。

**选择回归测试。** *已确认缺陷* 的回归测试属于现有覆盖率已拥有该行为的任何地方：从现有的测试开始，而不是从新文件开始。在编写第 2 阶段建议之前阅读 `references/fix.md` 以获取家和新命名规则，而不仅是在第 3 阶段编辑之前。一个因为更改故意反转其断言的行为而失败的测试没有错误的期望——那是下面的发散情况，被推迟而不是更新。

### 第 2 阶段门：先呈现，然后询问

**因果关系链门：** 在您能够解释完整链条——触发因素通过每个步骤到观察到的症状——没有任何空白之前，不要继续到第 3 阶段。“不知怎的 X 导致 Y”是一个空白。只有用户才能在调查受阻时授权基于最佳可用假设继续进行。

一旦根本原因得到确认，将发现结果作为用户可见的块写入：因果关系链和文件：行号引用；建议的修复及其更改的文件；要使用、添加、修改或加强的测试，以及现有测试是否应该已捕获此内容；以及任何相关工单或 PR 以及它如何塑造建议——如果打开的 PR 已经修复此问题，则优先显示该链接，而不是一个全新的修复。

**门前的同轮呈现：** 在完全编写完该发现块（在本轮或立即前一个助手消息中）之前，不要打开修复选择问题。阻塞问题工具在模态 harness 上仅渲染其自己的茎，因此仅在“根本原因确认”上触发的问题会留下用户在没有因果关系链的情况下选择。命名选项不是呈现发现，并且在选择后承诺解释太晚了。

当请求尚未授权下一个操作时，询问（根据 **阻塞问题**）要采取哪条路径，提供以下三个选项。明确的修复请求是第 3 阶段。明确的仅诊断请求跳转到第 4 阶段。`mode:pipeline` 和 `mode:return-to-caller` 从不询问。测试建议无论如何都是诊断的一部分。

1. **立即修复**——继续到第 3 阶段
2. **仅诊断——我将自行处理**——跳过修复，编写第 4 阶段的摘要，结束此技能
3. **重新思考设计**（`ce-brainstorm`）——仅在错误无法在当前设计中修复时：根本原因是错误的职责或接口，而不是错误的逻辑，需求本身是错误的，或者每个候选修复都是围绕不再成立的假设的工作around。仅凭大小不是设计问题。

**`mode:pipeline` 和 `mode:return-to-caller`：** 不要询问。继续到第 3 阶段并应用**收敛性**修复；一个**发散性**修复——一个会反转故意合同/行为/产品决策的修复，包括一个“失败”的测试断言预期行为——被推迟，而不是应用，根据 `references/pipeline-mode.md` 或 `references/return-to-caller.md`。在此处永远不要路由到 `ce-brainstorm`；设计问题成为 `needs-human` 残余。

### 第 3 阶段：修复

如果用户选择了“仅诊断”，则跳转到第 4 阶段的摘要。如果他们选择了“重新思考设计”，则控制权已转移到 `ce-brainstorm` 并结束此技能。

**在编辑任何文件之前阅读 `references/fix.md`** — 测试优先序列、失败修复规则和深度防御和事后分析触发器。两个规则决定修复是否可以开始，因此它们保留在此处：

- **分支。** 检查 `git status`；如果用户在需要修改的文件中有未暂存的更改，请在编辑前确认。如果当前分支是默认分支，则创建特性分支而不询问——从错误中派生名称，`git checkout -b <name>`，并说明您已移动到哪个分支。通过将当前分支与 `main`、`master` 或 `git rev-parse --abbrev-ref origin/HEAD`（**带 `origin/` 前缀去除**）比较来检测默认值——原始输出是 `origin/<name>`，因此未去除比较永远不会匹配。
- **记录修复前的范围：** 当前 `HEAD`、`git status --short` 是否干净以及任何预先存在的已更改文件。然后保持一个**修复拥有的文件**（为此错误更改的测试和实现）的列表，以便您在处理时使用。第 4 阶段从此记录中回答它的问题，并且无法在之后重建它。

### 第 4 阶段：移交

**`mode:pipeline` — 跳过整个交互式移交。** 没有精炼或审查步骤，没有残余问题，没有预览，没有学习捕获提议。根据 `references/pipeline-mode.md` 提交并推送收敛性修复，然后发出该引用的**结构化返回**。发散性 / 需要人工项被推迟在那里（打开线程或调用者的运行报告评论——永远不会是 PR 主体部分）。**`mode:return-to-caller` — 也跳过它：** 在特性分支上提交修复拥有的文件，不推送任何内容，并发出 `references/return-to-caller.md` 定义的结构化返回。在这两种模式下，返回是此技能写入的最后一件事。它结束此技能，而不是回合。调用者在同一会话中运行，并且其下一步跟随返回；不要向它宣布移交。本节的其余部分仅适用于交互式路径。

**结构化摘要**——始终首先编写此内容：

```
## 调试摘要
**问题**：[什么被破坏了]
**根本原因**：[完整的因果关系链，带文件：行号引用]
**推荐测试**：[为防止再次发生要添加/修改的测试，带具体文件和断言指导]
**修复**：[发生了什么更改——或者如果第 3 阶段被跳过，则为“仅诊断”]
**预防措施**：[添加的测试覆盖率；如果适用，结构性修复或深度防御，或结构性修复留作后续]
**信心**：[高/中/低]
```

**如果第 3 阶段被跳过**，在摘要后停止——用户已经表示他们将自行处理。不要提示。

**如果第 3 阶段运行**，现在阅读 `references/post-fix-handoff.md` 并遵循它，然后再路由。它定义了修复后的质量步骤：上下文覆盖检查、机械修复的跳过规则、保持 `ce-simplify-code` 和 `ce-code-review` 不参与无关分支工作的范围，如何处理剩余发现，`## 修复后质量` 块，以及提供学习捕获的标准。所有这些都不出现在本文体中。下面的路由命名运行*哪个*操作，而不是使它安全的范围规则，因此无法即兴创作。跳过阅读会发送未审查的修复，让审查深入到无关分支工作，并将接受的发现困在会话中。

#### 路由

**将修复部署，不要携带用户未主动提供的内容**——不进入提交，不进入推送，不进入 PR。不要询问是否要打开 PR；权限不是门。两个问题决定移交。从第 3 阶段记录的修复前范围回答它们，而不是分支如何存在。**通过平台的技能调用原语本身触发操作**——永远不要仅仅告诉用户要键入命令。

**1. 可以放入提交的内容——修复拥有的文件和任何其他内容。** 这是一个约束，无论哪个技能提交有问题，它自己的操作。它在每条路由上都保持不变，远程或非远程。在这里不要提交。

- 如果修复拥有的文件未携带预先存在的编辑，则这些文件是提交范围。将它们传递给要提交的技能。
- 如果修复拥有的文件已经携带了用户的编辑，则无法将它们分离：`ce-commit` 在文件级别分组，并且永远不会拆分文件。根据 **阻塞问题** 在任何提交之前询问是否要提交该文件（包括他们的编辑）、留下修复未提交或停止。只有第一个答案继续。其他两个结束移交，因此问题 2 从不运行并且没有内容提交；说明留下了什么以及原因。每个选项都失去了代理无法代表用户选择的东西，这就是为什么这个问题幸存的原因。第 3 阶段的确认覆盖了*编辑*文件，而不是将用户的编辑与修复一起提交。

如果你无法建立全部三个，请选择本地路径；那是安全的方向，预览不能替代它。否则，预览将要提交的内容、所在的分支，以及是否打开PR或更新，然后**使用 `branding:on` 调用 `ce-commit-push-pr` 技能**。它在问题1的范围内提交，所以不要先提交。预览是一个陈述，不是一个问题。显示生成的PR URL。
- **保持本地**，当其中任何一个失败时。在问题1的范围内调用 `ce-commit` 技能，不推送任何内容。用一句话说明保持本地的原因，并说明你将在请求时推送和打开PR。不要先询问；本地提交是可逆的。
- **不是git仓库**：不进行任何提交。在摘要和质量块之后停止。

**上下文覆盖**（“不要从技能中打开PR”、“仅提交”、“修复后停止”）—— 遵循用户的说法，当用户要求这样时，**在此停止**而不提交。模糊的语气提示不是覆盖。

**PR打开后**—— 应用引用的学习捕获标准。只有当这个门禁合格时，才提供捕获；如果用户接受，调用 `ce-compound` 技能，然后仅提交它实际写入或更新的工件，以便打开的PR可以获取它们。如果它没有写入任何内容，则不进行文档提交而结束。
