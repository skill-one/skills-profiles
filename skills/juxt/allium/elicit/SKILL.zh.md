# 诱导

这项技能通过对话引导你构建 Allium 规范。目标是揭示模糊之处，并生成一个能够捕捉软件所做之事而不规定实现的规范。

## 规范的范围界定

在深入细节之前，先确定你要规范的是什么。并非所有内容都需要放在一个规范中。

### 首先要问的问题

**"这个规范的边界是什么？"** 一个完整的系统？一个单一的功能区域？一个大型系统中的单个服务？要明确说明哪些内容在范围内，哪些内容不在范围内。

**"我们是否应该故意排除某些内容？"** 第三方集成可能是库规范。遗留功能可能不值得规范。某些功能可能属于单独的规范。

**"这是一个新系统还是已有代码？"** 如果有代码存在，你正在用诱导进行蒸馏。现有代码会限制规范中实际可行的内容。

### 记录范围决策

在每个规范的开始处记录范围：

```
-- allium: 3
-- interview-scheduling.allium

-- 范围：招聘流程中的面试安排
-- 包含：候选人资格、面试、时间段管理、邀请、反馈
-- 排除：
--   - 认证（使用 oauth 库规范）
--   - 支付（不适用）
--   - 报表仪表板（单独的规范）
-- 依赖：core.allium 中定义的用户实体
```

版本标记（`-- allium: N`）必须是每个 `.allium` 文件的第一行。使用当前的语种版本号。

## 找到合适的抽象层次

太具体会导致你规范实现，太抽象则会导致你说不出有用的东西。

### "为什么" 测试

对于每个细节，问： "为什么利益相关者关心这个？"

| 细节 | 为什么？ | 包含？ |
|------|----------|--------|
| "用户使用 Google OAuth 登录" | 他们需要认证 | 可能不需要，"用户进行认证" 可能就足够了 |
| "我们支持 Google 和 Microsoft OAuth" | 用户选择他们的提供商 | 是的，选择是领域级别的 |
| "会话在 24 小时后过期" | 安全/用户体验决策 | 是的，影响用户体验 |
| "会话存储在 Redis 中" | 性能 | 不，实现细节 |
| "密码必须为 12 个以上字符" | 安全策略 | 是的，影响用户 |
| "密码使用 bcrypt 进行哈希" | 安全实现 | 不，如何而不是什么 |

### "可以有不同的实现吗" 测试

问： "这个可以有其他实现方式，同时仍然是同一个系统吗？"

- 如果可以，它很可能是实现细节。将其抽象化。
- 如果不可以，它很可能是领域级别的。包含它。

例子：

- "通过 Slack 发送通知"。可以是电子邮件、短信等。抽象为 `Notification.created(channel: ...)`。
- "面试官必须在 3 小时内确认"。这个具体的截止日期在领域级别很重要。包含持续时间。
- "我们使用 PostgreSQL"。可以是任何数据库。不要包含。
- "数据保留 7 年以符合法规"。监管要求。包含。

### "模板与实例" 测试

这是一个事物类别，还是一个特定实例？

| 实例（实现） | 模板（领域级别） |
|--------------|------------------|
| Google OAuth | 认证提供者 |
| Slack | 通知通道 |
| 15 分钟 | 链接过期持续时间（可配置） |
| Greenhouse ATS | 外部候选人来源 |

有时实例就是领域关注点。"我们专门与 Salesforce 集成" 可能是竞争优势。"我们支持正好这三个 OAuth 提供商" 可能是设计范围。

不确定时，询问利益相关者： "如果我们改变这个，系统会变成不同的系统，还是只是不同的实现？"

### 抽象层次

```
太抽象：          "用户可以做一些事情"
                      |
产品级别：         "候选人可以接受或拒绝面试邀请"
                      |
太具体：          "候选人点击一个按钮，POST 到 /api/invitations/:id/accept"
```

**你太抽象的迹象。** 规范可以描述几乎任何系统。没有可测试的断言。产品负责人说 "但这没有捕捉..."

**你太具体的迹象。** 你在提到技术、框架或 API。你在描述 UI 元素（按钮、页面、表单）。实现团队说 "你为什么要规定我们如何构建这个？"

### 配置与硬编码

当你遇到特定值（3 小时、7 天等）时，问：

1. **这个值是设计决策吗？** 包含它。
2. **它可能因部署或客户而异吗？** 使其可配置。
3. **它是随机的吗？** 考虑是否要包含它。

```
-- 硬编码设计决策
rule InvitationExpires {
    when: invitation: Invitation.created_at + 7.days <= now
    ...
}

-- 可配置
config {
    invitation_expiry: Duration = 7.days
}

rule InvitationExpires {
    when: invitation: Invitation.created_at + config.invitation_expiry <= now
    ...
}
```

### 黑盒

某些逻辑很重要，但属于不同的层次：

```
-- 黑盒：我们知道它存在以及它考虑的内容，但不知道如何实现
ensures: Suggestion.created(
    interviewers: InterviewerMatching.suggest(
        considering: {
            role.required_skills,
            Interviewer.skills,
            Interviewer.availability,
            Interviewer.recent_load
        }
    )
)
```

规范说有一个匹配算法，它考虑这些输入并产生面试官建议。规范没有说匹配是如何工作的，权重是什么或具体的算法。

这是正确层次的情况：当算法复杂且在演变时，当产品负责人关心输入和输出而不是内部结构，并且如果需要，可以单独的详细规范来覆盖它时。

## 阅读初始提示

在选择方法之前，评估用户带来的内容。初始提示告诉你从哪里开始。

**用户描述了一个流程。** "我们有一个招聘流程，候选人申请、筛选、面试，然后我们决定。" 他们正在以流程级别思考。从流程发现开始——让他们描述流程，然后帮助他们组织成规范结构。参考 [流程发现](./references/process-discovery.md)。

**用户命名了实体。** "我需要规范一个具有状态和转换的 Order 实体。" 他们已经在以结构级别思考。跳过流程发现，直接进行范围定义，然后填充细节。参考 [细节诱导](./references/detail-elicitation.md) 在处理规则和表面时。

**用户有一个模糊的想法。** "我们需要构建一个用于管理客户支持的东西。" 他们需要帮助塑造想法，然后再规范它。从流程发现开始，使用开放式问题： "告诉我当客户寻求帮助时会发生什么。" 参考 [流程发现](./references/process-discovery.md)。

**用户有现有代码。** "我们有一个支付服务，我想规范它做什么。" 这是用诱导进行蒸馏。指向 `distill` 技能，或者结合使用：从代码中蒸馏结构，从利益相关者那里诱导意图。

**用户有现有规范。** 首先阅读规范。使用 [评估规范](../allium/references/assessing-specs.md) 确定每个实体的开发程度。跳过规范已经覆盖的阶段——不要重新询问有范围注释的规范的范围问题，或者重新发现已有转换图的流程。从每个实体需要的级别开始：有生命周期但没有规则的实体的细节诱导，有规则但没有失败路径的实体的障碍诱导。

## 诱导方法论

### 阶段 0：流程发现

**目标：** 在识别结构之前，了解系统支持哪些流程。

不是每个会话都需要这个阶段。如果用户已经想到实体和生命周期，跳到阶段 1。如果他们以流程描述或模糊想法到达，从这里开始。

让用户用自己的话描述系统，然后再强加 Allium 结构。捕获流程、参与者、结果，然后组织成结构。参见 [流程发现](./references/process-discovery.md) 了解具体技术。

**输出：** 流程名称和结果。大致步骤顺序。参与者识别。足够编写粗略规范（具有转换图和开放式问题的实体）。

**注意：** 太早跳到实体定义的冲动。保持在流程级别，直到流程清晰。

### 阶段 1：范围定义

**目标：** 了解我们正在规范什么以及边界在哪里。

要问的问题：

1. "这个系统本质上是什么？用一句话概括？"
2. "这个系统从哪里开始，到哪里结束？范围内外是什么？"
3. "用户是谁？是否有不同的角色？"
4. "是否有现有系统与之集成？它们处理什么？"

如果阶段 0 被跳过，也要问： "这个系统支持哪些关键流程？每个流程的成功看起来像什么？" 这将实体识别锚定到流程而不是孤立地枚举名词。这里也适用 [流程发现](./references/process-discovery.md) 中的技术——如果用户难以表达流程，使用过去时回忆和结果优先提问。

**输出：** 参与者和角色列表。核心实体列表（如果阶段 0 运行，则从流程中派生）。边界决策（外部内容）。一句话描述。

**注意：** 范围蔓延（"它还做 X、Y、Z"，温和地重新聚焦）。假设知识（"显然它处理认证"，明确说明）。描述表明是 [库规范](./references/library-spec-signals.md) 而不是特定于应用程序的逻辑（例如 OAuth、支付处理、电子邮件交付）。

### 阶段 2：快乐路径流程

**目标：** 从开始到结束跟踪主要路径。

如果阶段 0 产生了一个步行骨架（参见 [流程发现](./references/process-discovery.md)），使用它作为起点。否则，问： "如果我们只能通过这个流程的一条路径，那会是什么？" 将骨架作为粗略规范编写，并用领域术语描述它给用户听（参见 [评估规范](../allium/references/assessing-specs.md#communicating-with-stakeholders)）。

然后充实： "每个步骤由什么触发？谁参与？发生了什么变化？" 跟踪一个实体通过其生命周期，捕获状态转换、参与者和触发器。

```
候选人资格：
  申请 -> 筛选 -> 面试 -> 决定 -> 雇佣 | 拒绝
```

**输出：** 关键实体的转换图。主要触发器和结果。每个步骤的参与者分配。

**注意：** 太早跳到边缘情况（"但如果..."，记下它并保持在快乐路径上）。实现细节渗入（"API 端点..."，重定向到结果）。

编写规范结构后，如果 CLI 可用，运行 `allium check`。在继续之前修复结构问题——不要等到阶段 4 再验证。

建立骨架后，参考 [细节诱导](./references/detail-elicitation.md) 了解填充规则、表面、字段和数据依赖的技术。

### 阶段 3：边缘情况和失败路径

**目标：** 发现什么会出错以及系统如何处理。

参考 [障碍诱导](./references/obstacle-elicitation.md) 了解技术。关键方法：

- 使用预先尸检： "想象这个系统已经构建并且它失败了。出了什么问题？"
- 在每个步骤： "如果没有人做任何事在这里？一天后？一周后？"
- 在每个交接： "谁接管？他们如何知道轮到他们？他们需要看到什么？"
- 在每个转换： "如果先决条件不满足？可以逆转吗？"
- 对于外部依赖： "信息如何进入系统？如果外部服务不可用会怎样？"

**输出：** 异常转换。具有 `requires` 守卫的时间触发器。升级路径。终端错误状态。不变量。

**注意：** 无限循环（"然后它重试，然后再次重试..."，需要终端状态）。缺少升级，因为最终需要知道的人是。

当利益相关者陈述系统级属性（"余额永远不会为负"，"没有两个面试为同一候选人重叠"），这些是顶级不变量的候选者。将其捕获为 `invariant Name { expression }` 声明。

编写规则和异常转换后，如果 CLI 可用，运行 `allium check`。在继续之前修复问题。

### 阶段 4：细化

**目标：** 验证并完成规范。

参考 [假设检查](./references/assumption-checking.md) 了解技术。用领域术语描述规范说了什么，并测试它是否符合用户的思维模型。跟踪具体场景通过规范。测试排序假设。验证参与者分配。

如果 Allium CLI 可用，运行 `allium check` 并使用诊断来识别结构差距。如果 `allium analyse` 可用且规范有规则和表面，运行它并使用发现来揭示流程级差距。参考 [行动化发现](../allium/references/actioning-findings.md) 了解如何将发现转化为领域问题。

要问的问题：

1. "查看 [实体]，这些状态是否完整？它可以处于任何其他状态吗？"
2. "我们是否遗漏了任何内容？"
3. "这个规则引用 [X]，我们需要定义它吗，还是它是外部的？"
4. "这个细节在这里是否必要，或者应该存在于详细规范中？"

**技术：** 取一个具体场景并通过规范跟踪。 "让我们假设 Alice 申请了高级工程师职位。带我走过她候选人资格发生的事情。"

**输出：** 完整的实体定义。记录的开放式问题。识别的延迟规范。确认的外部边界。

当相同的义务模式（例如序列化合同、确定性评估要求）在多个表面出现时，建议将其提取为 `contract` 声明以供重用。

## 尽可能硬编码逻辑的输出形状

结果形状是最常丢失的决策——被遗漏、半捕获，甚至被排除在范围之外。用与核心方法相同的深度诱导它。

- **直接逐字段询问结果形状。** "这个必须返回或报告的确切内容是什么，每个字段？" 获取完整列表，而不是代表性列表。
- **任何按与计算不同的基础导出、披露或报告的图形都得到核心方法待遇：** 捕获其确切定义、其基础、其精度及其在退化情况下的行为，直到没有歧义。这里的一行答案隐藏了微妙的要求——一个按与累积不同的日计数披露的利率，一个客户看到的图形与您持有的图形不同。
- **结果形状默认在范围内。** 不要将系统必须返回或披露的内容排除在范围之外；排除输出是向操作员确认的决定，而不是沉默的遗漏。

## 完成前：完整性门

访谈感觉完成很久了——当主要流程组合在一起时，这远远太早了。不要基于这种感觉结束。在将对话视为完成之前，对照操作员所说的一切，走完这个决策类别的清单。对于此系统相关的每个类别，确认他们是否实际回答了它；如果没有，现在问一个具体、可回答的问题，并继续下去，直到每个相关类别都被提出并回答（或明确排除在范围之外）。你从未问过的类别不是 "假设"——它是未问的，在简短的沉默中是提问的信号，而不是猜测的许可。

- **核心方法或规则。** 当计算、推导或决定一个结果时，如果存在多个被接受的方法或惯例，该组织使用哪一个？不要假设常见的默认值。
- **单位和精度。** 量度所使用的单位、精确度以及如何处理更细粒度的值。
- **舍入或截断。** 当一个值被减少到其单位时，它是如何进行的以及任何余数将落在哪里。
- **顺序和优先级。** 当多个事物被应用或处理时，它们的顺序以及当两个事物同等重要时的破局规则。
- **阈值和限制。** 最小值、最大值、上限以及在以下情况下某事物被豁免、忽略或视为无：低于某个容忍度。
- **时间和生效日期。** 某事物何时生效与何时被记录、倒签、从某个较早的时间点重新计算以及截止时间。
- **并发和顺序。** 当两件事情同时发生或接连发生时，它们的顺序以及如何破局。
- **边缘输入。** 零、负数、空、缺失、重复、超出范围——对于每一个，是被拒绝、被忽略还是被处理，以及是否仍然保留记录。
- **盈余和短缺。** 任何剩余或缺失的东西会发生什么——被保留、被返回、被结转、被升级——以及它将应用于下一个什么。
- **范围边界。** 该系统拥有什么与上游或外部系统提供什么之间的区别。排除是一个确认的决定，而不是沉默的省略。
- **输出和报告形状。** 结果必须包含的所有内容，按字段划分，以及以不同于计算或存储方式报告或披露的任何数据。
- **整个生命周期，而不仅仅是创建。** 该事物在其整个生命周期中经历的每一件事情，超越了被创建和正常运行——早期终止或取消、生命周期中的更改或更正、暂停或暂停、更新或延长、逆转、转移、到期，以及关闭或清算——对于每一项，什么会重新计算以及任何剩余的东西将如何处理。这是最可靠地被跳过的类别；对于当前实体，列出每一项并询问它是否适用。

只要上述任何相关类别仍然是未询问的假设，你就还没有完成。

## 探究原则

### 一次只问一个问题

不好：“你有哪些实体，它们可以处于什么状态，谁可以修改它们？”

好：“这个系统主要管理哪些事物？”
然后：“让我们以[Candidacy]为例。它可以处于什么状态？”
然后：“谁可以改变一个候选资格的状态？”

### 探索影响

当出现选择时，不要只接受第一个答案。探索后果。

“你说邀请在48小时后过期。那时会发生什么？”
“如果候选人在我们重试后仍未回复呢？”
“如果他们永远不回复，这个候选资格会永远卡住吗？”

这会揭示他们尚未做出的决定。

### 区分产品与实现

当你听到实现语言时，请重定向：

| 他们说       | 你重定向         |
|--------------|------------------|
| “API 返回 404” | “所以用户被告知未找到？” |
| “我们存储在 Postgres 中” | “捕获了哪些信息？” |
| “前端显示一个模态框” | “用户被提示确认？” |
| “我们使用 cron 作业” | “这按计划发生，多久一次？” |

### 明确地暴露模糊性

记录一个开放问题比假设更好。

“我不确定拒绝是否应将候选者返回到池中或完全移除。让我将其记录为一个开放问题。”

```
开放问题 “当候选者拒绝时，他们会返回到池中还是退出？”
```

### 愿意迭代

修改早期的决定是正常的。

“我们之前说所有管理员都看到所有通知。但现在你正在描述基于角色的特定仪表板。我们应该重新考虑这一点吗？”

### 优先考虑深度而非广度

首先完全开发最重要的实体。其他实体可以粗糙地保留开放问题。用户可以在后续会话中完善它们。试图在一个对话中开发每个实体到相同级别，有耗尽上下文而没有完成任何风险。

### 知道何时停止

并非所有事情都需要立即指定。

“这开始涉及匹配算法的工作。我们应该将这一点推迟到详细的规范中吗？”

“我们已经涵盖了主要流程。报告仪表板听起来像是一个单独的规范。”

## 常见的探究陷阱

### “显然”陷阱

当有人说“显然”或“当然”时，请探查。“你说管理员显然批准。有没有他们不需要的情况？这以后可以自动化吗？”

### “边缘情况螺旋”陷阱

有些人想立即涵盖所有边缘情况。“让我们将其记录为一个开放问题，并继续主要流程。我们稍后会回来处理边缘情况。”

### “模糊同意”陷阱

不要接受没有具体细节的“是”。“你说是的，候选者可以重新安排。有多少次？有没有限制？之后会发生什么？”

### “缺失参与者”陷阱

注意没有明确参与者的行为。“你说“时间段被释放了”。是谁或什么释放它们的？是自动的，还是有人触发的？”

### “同义词”陷阱

当你听到来自不同利益相关者、现有代码或相关规范的同义词时，停止并解决它，然后再继续。

“你说“购买”，但之前我们称之为“订单”。我们应该使用哪个术语？”

一个指出两个术语是同义词的评论并不是一个解决方案。它保证两者都会出现在实现中。选择一个术语，交叉引用相关规范并更新所有引用。不要留下旧术语，即使在“另见”笔记中也不要。

## 探究会话结构

这些时间适用于人工促进的会话。在 LLM 对话中，使用阶段输出来决定何时推进，而不是看时钟。

**开场。** 简要解释 Allium：“我们正在捕获软件的功能，而不是它的构建方式。” 就本次会话的范围达成一致。

**范围定义。** 确定参与者、实体、边界。获取一句话描述。

**主要流程。** 从开始到结束追踪主要流程。捕获状态、触发器、结果。

**边缘情况。** 超时和截止日期。故障模式。升级路径。

**总结。** 回顾关键决定。列出开放问题。命名仍然粗糙的实体以及它们需要什么。如果需要，确定下一个会话的范围。

## 探究之后

对于目标更改，其中你已经知道你想要什么，使用 `tend` 技能。对于需要结构化发现的重要添加（新功能区域、复杂的实体关系、不明确的需求），即使规范已经存在，探究仍然是正确的工具。检查规范和实现之间的一致性属于 `weed` 技能。
