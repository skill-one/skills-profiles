# /layers-intro

在任何设计会话开始时加载此技能。它提供了所有其他 `/layers-*` 技能所依赖的框架上下文。

---

## 框架

**产品设计层次** 将设计工作组织成三个区域内的七个层次。层次具有 *逻辑依赖性*：低层是高层的基石。薄弱的低层会创建向上蔓延的 UX 债务。

**现实** — 复杂、矛盾、不断演变。所有学习的来源。

**问题空间** — 从现实中获取的知识：
1. **观察到的行为** — 用户实际做什么
2. **领域** — 独立于任何产品而存在的概念、术语和心智模型
3. **用户需求** — 我们认为用户试图实现的目标以及原因

**解决方案空间** — 关于要构建什么的刻意决策：
4. **产品和服务战略** — 要满足哪些需求，以及要瞄准哪些业务成果
5. **概念模型** — 对象、关系、状态、词汇——独立于任何界面
6. **交互结构和流程** — 地点、可供性、连接和流程逻辑
7. **界面** — 文字、视觉效果、反馈、层次结构——用户实际遇到的内容

这些层次不是一个线性过程。你可以从任何地方开始——但始终检查一下下方的基石是否稳固。

*受 Jesse James Garrett 的* *用户体验要素（2000）* *启发。*

## 设计是决策

设计 = 关于解决方案形式的决策（克里斯托弗·亚历山大）。形式是解决方案；上下文是它必须适应的要求、约束和环境。好的设计就是好的适应。

**四种进步类型：**
1. **做出决策** — 解决未决事项
2. **发现未做出的决策** — 发现尚未做出的决策（通常比 1 更有价值）
3. **评估决策** — 识别已经做出的有风险、不一致或错误的决策
4. **优先排序决策** — 低层更基础，如果出错风险更大

每个技能的任务是帮助设计师做出更好的决策——而不是替他们做决策。

---

## 如何使用这些技能

每个 `/layers-*` 技能都是一个**针对一个层次的技巧库——不是一个从开始到结束运行的脚本。** 不要按步骤逐一执行并生成一堆工件。相反：

1. **找到活跃的决策。** 在这一层，什么真正未决、有风险或值得揭示？(`/layers-orient` 如果你不确定，可以在所有层次中找到这些决策。）如果这里没有活跃的决策，就说出来并继续——不要为了填充结构而制造工作。
2. **提供适合决策的技巧。** 每个技能列出了适合的情境。建议一两个，让设计师选择。技巧是做出特定决策的方法，而不是一个要填写的框。
3. **处理决策；只捕捉残留物。** 生成决策需要的内容——通常是几行，有时是一个图表——而不是一份完整报告。对话是工作表面；捕捉是它留下的东西。

每个技能都命名了**该层次做出的决策**以及**保持其诚信的学科**。这些是骨干。任何单个提示的措辞都是可丢弃的；它服务的决策不是。

## 原则——适用于所有会话

1. **决策，而不是输出。** 工件只有在代表已做出的决策或揭示的决策时才有用。命名决策，而不仅仅是图表。
2. **先揭示，再解决。** 揭示设计师不知道他们需要做出的决策，往往比回答他们已经提出的决策更有价值。
3. **一次只在一个层次上工作。** 混淆问题空间和解决方案空间，或界面和概念模型，会产生混乱的输出。
4. **向上构建前检查基础。** 在处理上层之前，审计下层。标记不稳定性。
5. **概念模型是最被忽视的承重层。** 比感觉舒适时给予它更多关注。
6. **标记坏决策，而不仅仅是缺失的决策。** 已经做出的有风险或不一致的决策需要被命名，而不是绕过。
7. **引导，而不是被引导。** 在基础决策做出之前，不要跳转到界面输出。
8. **设计原则与实现决策。** 有些决策可以在不知道系统约束的情况下陈述——*从用户的角度来看应该发生什么*。其他决策与实现纠缠在一起：明确用户体验要求，形成一个形状良好的问题，并将其带入设计+工程对话。不要过早给出答案。
9. **捕捉决策，而不是记录。** 默认使用轻量级输出：做出的决策、揭示的决策和开放性问题——没有更多内容。不要生成用户实际上不会重新阅读的比记录更长的文档；对话已经是记录。一个图表只有在编码决策时才配得上它的位置。每个技能中的“生成”列表是一个可以捕捉的菜单——不是必须写所有内容的命令。如果被要求，才提供扩展。
10. **推进，拉回。** 这些层次不是一个单向攀登。当某一层的工作感觉不合理或漂浮——你正在没有明确理由的情况下细化结构——通常是因为你目前还看不到什么会依赖于它。向上探测一层或两层（绘制一个流程、一个屏幕、一个赌注）来发现下层实际需要什么，然后回来做这项工作，现在更清晰并与路径连接。向上探测以*学习*不同于向上承诺以*构建*：不要在不稳定下层上最终确定上层，但也不要拒绝向上瞥一眼。

## 时间维度——主动探测

时间决策经常被忽视。它们集中在两个层次上：

**概念模型层：**
- *中间动作状态* — 对象是否在解决之前通过过渡状态（保存、处理、等待批准）？那些是模型状态。
- *读取模型延迟* — 数据写入和可见之间的差距？阐明用户需求；标记为工程的一个命名开放问题。
- *关系时间性* — “欧洲所有产品”是指现在的群体，还是随成员变化而变化的成员资格？这是一个设计决策。
- *删除语义* — 存档、回收站、硬删除或监管删除？说明原因并为什么。实现随后跟上。
- *历史* — 过去对象的状态是否重要？说明它的重要性是一个设计决策。

**交互结构层：**
- *动作后状态* — 提交后用户看到什么？重定向列表是否立即反映更改？
- *乐观与悲观更新* — 在服务器确认之前显示假设结果，还是等待？说明偏好；如果实现不确定，标记为开放问题。
- *空、加载、部分状态* — 每个地方都有一个时间生命周期。设计所有这些。
- *错误和失败路径* — 验证失败、服务器错误、网络断开连接、并发编辑。必要的步骤，而不是事后思考。

## 失效模式信号

**OOUX 对象失效模式**（索菲亚·普拉特）：
- **变形者** — 在不同上下文中同一对象以显著不同的形式出现。表面修复：一致的对象处理。如果模型没有明确定义对象，则需要更深层次的修复。
- **被掩盖** — 不同类型的对象看起来相同。表面修复：不同的视觉处理。如果模型没有区分它们，则需要更深层次的修复。
- **损坏** — 对象的数据和操作分散在屏幕上，没有任何跨链接。交互结构问题 → `/layers-interaction-flow`。
- **孤立** — 对象在没有与其他对象可见关系的情况下存在。概念模型问题 → `/layers-conceptual-model`。

**尼尔森的经验法则——一个根层映射：**
“系统与现实世界的匹配”违规几乎总是根源于概念模型，而不是界面。“用户控制和自由”是一个交互结构决策。在表面修复这些问题是治疗症状，而不是原因。

## 捕捉工作

捕捉是可选的，默认轻量级。早些时候问一次：

*"你想让我保存此会话决策的简短摘要，还是保留在对话中？如果保存：你项目中的 Markdown 文件（使用 [Markdown 预览 Mermaid 支持扩展](https://marketplace.visualstudio.com/items?itemName=bierner.markdown-mermaid) 在 VSCode 中原生渲染 Mermaid 图表），Notion（如果 MCP 已连接），或某个地方吗？*"

无论目的地如何，都倾向于简洁（原则 9）：捕捉决策，而不是讨论的复述。有人重新阅读的一页比一次略读的十页更有用。如果更完整的撰写确实会有帮助，就提供它——不要假设。

在编写 Mermaid 图表时，在节点标签内使用 `<br/>` 进行换行——而不是 `\n`，它会被渲染为纯文本。
