# /layers-observed-behaviour

*假设已加载 `/layers-intro`。这项技能是一个技术库，而非脚本——请参阅那里的“如何使用这些技能”。*

观察行为层是我们能最接近现实的地方——用户实际的行为，而非我们认为他们应该做的或希望他们做的。它之上的一切都是解释；这一层是源头。

它分为两种情况。检测哪种情况适用并说明：
- **计划** — 尚未进行任何研究；设计一项研究。
- **综合** — 研究材料已存在；理解这些材料。

对于部分研究，首先综合现有材料，然后计划填补空白。

---

## 该层做出的决策

- 我们最需要了解用户的具体问题
- 现有的证据及其可靠性
- 如何获取缺失的部分
- 哪些模式有信心支持，哪些仍停留在假设

---

## 学科——使观察保持诚实的要素

- **贴近原始数据。** 观察应该是具体的，接近源头——用户所说的、所做、所感的——而不是被总结成结论。
- **基于所见或所闻，** 而非团队信念。
- **标注信心：** 观察 / 推断 / 假设。如果你标注某项为 *观察*，那么支持它的原始引文应该在同一笔记中可引用——没有可引用证据的观察性声明实际上是推断。
- **明确命名研究空白，** 而不是掩盖它们。
- **替代方案是信号。** 足以激发即兴发挥的需求是强烈的。

## 技术

### 计划研究

| 技术 | 使用场景 |
|---|---|
| **定义学习目标** | 总是从这里开始。超越“更好地理解用户”到 2-3 个具体问题——例如“是什么促使某人推荐朋友，又是什么让他们犹豫？” |
| **JTBD 访谈** | 理解触发因素、动机、焦虑。访谈关于真实的过去经历，而非假设情景。指南：开场（“告诉我上次你……”）、时间线（什么引发了它，你尝试了什么）、动机（你希望什么，你担心什么）、收尾。 |
| **情境查询 / 观察** | 用户所说的与所做的不同——观察真实工作中的隐性行为。 |
| **日记研究** | 行为分布在时间上或非频繁——用户在事件发生时自我报告。 |
| **支持工单 / 审查分析** | 现有产品积累了信号——规模化的痛点，无需招募。 |
| **分析审查** | 用户做了什么（而非为什么）。补充定性研究；不能替代定性研究。 |
| **可用性观察** | 用户在使用现有产品时遇到的困难或成功之处。 |

对于访谈，事先计划综合：每条笔记一个观察，标记它所回答的问题，原始引文优先于总结。（通常 6-10 次定性访谈就能达到饱和。）

### 综合材料

| 技术 | 使用目的 |
|---|---|
| **提取观察** | 提取用户所说的、所做、所感的具体事物——尚未进行解释。从记忆中提示：最令人惊讶的是什么？什么反复出现？他们意外遇到了什么困难？ |
| **模式分组** | 根据反复出现的情况、共同动机、共同焦虑和替代方案对观察进行分组。 |
| **候选任务故事** | *当 [情况] 时，我想 [动机]，以便 [结果]。* 检查“当”是否具体，“想”是否是动机而非解决方案；标注信心。 |
| **空白标记** | 观察尚未回答什么？这些将成为后续计划会话。 |

## 与设计师合作

首先了解现有材料——访谈、录音、工单、分析——并说明模式。倾听名词（候选领域对象）和用户使用的自然语言；这些信息将用于领域层。

提供合适的技术：在计划中，与学习目标匹配的方法；在综合中，提取 → 模式 → 候选故事。做下一件有用的事，而不是全套测试。

仅捕获残留物——关键原始观察、支持证据的模式、带信心评级的候选任务故事，以及命名的研究空白。

候选任务故事准备好在 `/layers-user-needs` 中进行完善。
