# 游戏节

将一个主题和固定的截止日期转化为一个完成的、提交的游戏。这是一个规划和范围控制的剧本，不是引擎代码：胜利条件是*提交可玩的内容*，而不是*你想象中的游戏*。

## 何时使用

- 在进入限时游戏节（Ludum Dare、GMTK Jam、全球游戏节、周末游戏节）时使用，规划 48 小时构建，或决定如何删减内容以赶上截止日期。
- 当用户问“我周末实际上能做什么”或“我如何提交这个游戏节”时使用。

**不使用时机：** 在引擎代码中构建*核心循环*（使用引擎技能——`godot-2d-movement`、`phaser-core`等——或一个类型技能如`platformer`）；没有截止日期的随手实验（使用`prototype-fast`）；发布商业版本（使用`steam-publish` / `itch-publish`）。

## 核心工作流程

1. **主题公布前阅读规则。** 确认游戏的*时长*、*主题公布时间*、*提交截止日期（含时区）*、是否允许团队/预制资源/引擎，以及是否需要评分其他作品。遗漏其中任何一项都会使一个原本完成的游戏失去资格。
2. **提前准备繁琐的部分**（大多数游戏节都允许）：一个可以构建和导出的空项目、输入+标题/结束界面占位符、一个你已运行过的导出流程，以及一个你有使用许可的字体/SFX 资源。第一天的宝贵时间不应浪费在这里。
3. **主题 → 一句话。** 在 15 分钟内头脑风暴 10 个想法，然后选择**一个**可以表达为：*"你需要[动词]去[目标]，同时[限制条件]。"* 如果一句话说不清楚，它就太大了。
4. **根据时间而非想法来规划范围。** 使用下面的预算表。选择**一个**核心机制和**一个**“钩子”。其他都是扩展目标。
5. **先构建可垂直切片。** 尽早得到一个 30 秒可玩的循环（开始→玩→失败/胜利→重启）运行起来。一个完整的微小循环胜过一个半成品的大循环。
6. **保留最后 ~20% 的时间用于发布**，而不是功能。导出，在一个干净的路径上测试构建，截屏，写页面。构建总是在第 47 小时出问题。
7. **尽早提交，如有时间则更新。** 在截止日期*之前很久*上传一个可运行构建；大多数游戏节页面允许你在关闭前更换文件。一个提交的平庸游戏得分；一个未提交的伟大游戏则不得分。

## 模式

### 1. 根据游戏节时长规划范围（从截止日期倒推计划）

```text
              | 48 小时游戏节            | 72 小时游戏节           | 一周游戏节
--------------|------------------------|-----------------------|------------------------
核心机制     | 1 个，在第 6 小时证明    | 1-2 个                 | 2-3 个交互
关卡/内容    | 1 个手工或生成         | 3-5 个                 | 8-12 个 + 进阶
美术         | 占位符/1 个调色板     | 1 个艺术家的协调集合   | 主题集合 + UI
音频         | 3-5 个 SFX + 1 个循环   | SFX + 1-2 个轨道      | 自适应音乐
发布缓冲区   | 最后 8-10 小时         | 最后 12-16 小时        | 最后完整一天
```

### 2. 48 小时时间线（具体区块）

```text
H0-2    想法生成 -> 锁定 ONE 句子概念 -> 确定核心机制 + 胜利/失败条件。
H2-8    用基础元素（方块/圆形）在代码中实现核心循环。使其可玩，无美术。
H8-12   睡觉。（疲惫的代码是明天的错误列表。）
H12-24  内容：1 个关卡/遭遇，调整难度，添加“钩子”功能。
H24-30  睡觉 + 和另一个人一起测试；删减任何不吸引人的内容。
H30-38  美术+音频过场。注入：屏幕震动、击打停止、缓动、粒子、SFX。
H38-44  Bug 修复冻结：不能添加新功能。只修复崩溃和软锁。
H44-48  导出，在干净路径上测试构建，截屏，写页面，提交（约 H46 时）。
```

### 3. 功能筛选——快速决定，大声决定

```text
对于每个功能按顺序问：
  1. 没有它核心循环也能运行吗？   -> 如果是，它是扩展目标，不是 MVP。
  2. 玩家能看出缺失吗？       -> 如果不是，删掉它。
  3. 是否少于 30 分钟的工作？               -> 如果不是，推迟到发布缓冲区之后。
在截止日期压力下的默认答案是删掉。你可以在游戏节后版本中添加。
```

### 4. 提交前构建检查（在干净的副本上运行，不是你的开发文件夹）

```text
[ ] 构建可以从解压的 zip 在没有安装引擎/IDE 的路径上运行。
[ ] 控制键显示在屏幕上或页面上（评委不会读你的心思）。
[ ] 没有开发控制台错误；没有软锁；重启有效。
[ ] 网页构建（如果有）设置为可在浏览器中运行的模式。
[ ] 页面包含：一句话的提案，控制键，截屏，致谢+资源许可。
[ ] 文件已上传，提交实际上已关联到游戏节，而不仅仅是页面。
```

## 陷阱

- **范围蔓延是游戏节最大的杀手。** 如果核心循环在截止时间的三分之一之前不可玩，现在就删减功能，而不是之后。
- **没有发布缓冲区。** 导出、压缩和写页面可靠地需要 1-3 小时，并且总会出现构建 Bug。将截止日期视为比实际早约 2 小时。
- **提交到页面但未提交到游戏节。** 在 itch.io 上，游戏节条目是一个从游戏节页面链接的独立*提交*——单独上传游戏不会使其参与游戏节。
- **未测试的导出。** “在编辑器中运行正常”不等于“在构建中运行正常。” 在干净路径上测试导出的工件；缺少资源和错误的可执行目录是经典的。
- **未许可的资源。** 从网上拉的音乐/字体/精灵可能违反游戏节规则并导致后期分发失败。使用你有许可的资源，并在致谢中列出它们。
- **在循环完成前打磨是有趣的。** 注入会倍增乐趣；它不能创造乐趣。先用占位符先得到正确的循环。

## 参考

- 对于随手丢弃与保留的原型设计心态和灰盒技术，阅读 `prototype-fast` 技能。
- 对于实际的上传机制（项目页面、频道、`butler push`），阅读 `itch-publish`。

## 相关技能

- `prototype-fast` — 在投入游戏节时间之前快速验证一个机制。
- `itch-publish` — 创建页面并上传构建（大多数游戏节都在 itch.io 上托管）。
- 引擎核心 (`phaser-core`、`love2d-core`、`godot-gdscript`、…) 和类型技能 (`platformer`、`roguelike`、…) — 构建游戏节围绕的范围实际循环。
