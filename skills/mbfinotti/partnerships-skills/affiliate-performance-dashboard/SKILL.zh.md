# 联盟绩效仪表盘

定义联盟计划仪表盘衡量什么以及如何布局，然后交付一个仪表盘规格文档。规格——而不是一个已构建的仪表盘——才是工件：无论谁拥有 BI 工具，都根据规格来实现它。

没有标准的联盟仪表盘框架，指标定义也不标准化：没有标准机构强制执行它们，IAB 和 PMA 仅发布指导。向用户明确说明这一点；永远不要展示一个不存在的品牌框架。

该方法借鉴了四个既定事物，除此之外别无其他：

- **增量性测量**，通过保留测试和地理提升测试，基于增量性、基线转化和模型验证的明确定义。
- **归因 ROAS 与归因 ROI 分割**，其中 ROAS 将归因收入除以媒体成本，ROI 将其除以媒体成本加 COGS。
- **来源与影响分离规则**。
- **分层指标层次结构加上良好指标标准**，来自 Croll & Yoskovitz 的《精益分析》：指标必须是可比较的、比率或速率、易于理解、并能改变行为的。

前两个定义背后的平台术语表命名为 [references/metric-definitions.md](references/metric-definitions.md)，而不是在这里；无论程序在哪个平台上运行，定义都是该技能的操作性定义。

## 基本规则

- 报告经过验证/批准的佣金和净收入，而不是毛收入——毛收入是更大的数字，也是最常见的从业者错误。
- 给每个指标一个定义，命名分子、分母、窗口、时区、计数方法。无法用一句话定义的定义是表演。
- 为每个基准添加来源标签：供应商、行业协会、综合或程序自己的派生基线。几乎所有发表的联盟基准都来自有动机夸大渠道的方。
- 永远不要将合作伙伴提供的收入和合作伙伴影响的收入相加；报告它们为两个独立的、封顶的数字。
- 永远不要比较具有不同验证窗口的两个时期——逆转滞后使最近的时期看起来人为地好。
- 将欺诈和合规信号与绩效放在同一视图上，永远不要在单独的工具中——日常决策者需要同时看到两者。

## 面谈

在指定任何内容之前，按照以下规则提问：

- 每条消息一个问题。
- 尽可能进行多项选择。
- 跳过已经回答的问题。

- B2B SaaS、B2C 电子商务，还是两者兼有？
- 程序规模和成熟度：活跃合作伙伴数量、月佣金支出、程序年龄？
- 谁阅读仪表盘——高管、操作员还是两者——以及它应该驱动什么决策？
- 佣金模式，以及其中是否有任何是经常性的？
- 验证/锁定窗口长度和追回政策？
- 归因模型和 Cookie 窗口？
- 哪些数据源存在——联盟平台、账单/订单、CRM、仓库——合作伙伴 ID 是否能到达账单或订单？
- 是否捕获合作伙伴类型/促销方法？
- 是否捕获新客户与返回客户，每个转化？
- 刷新能力和工具限制——实时查询、每日批量、手动导出？
- 当前痛点：程序无法回答的今天的问题是什么？
- 今天报告的节奏，以及已经存在的哪些审查会议？
- 必须在什么日期之前向读者展示第一个版本？
- 一次性胜利——现在解决一个有争议的问题——还是一个程序每周运行的复合资产？
- 努力上限：分析师可用时间、谁拥有数据连接，以及是否可以资助日常维护？

最后三个答案会重新排序此技能及其参考中的每个选项菜单。大声说出哪个答案移动了哪个选项：

- 一个接近日期将规格与订单骨干固定，并删除需要连接但尚未存在的每个指标。
- 一个复合指令会提升客户文件连接、队列视图和流失调整的合作伙伴 LTV。
- 一个薄的努力上限会删除建模的仓库、品牌出价警报和创意切片，而不是将它们放在规格的底部。

这里的每个排名都是一个默认值，而不是法律——它会随着上下文和执行者的变化而变化。根据您对这位用户已有的了解重新排序：一个可以干净地导出合作伙伴分类的网络，一个已经加载了账单和 CRM 的仓库，或者根本没有分析师，每个移动都会不同的梯级。

## 工作流程

1. 运行面谈；收集所有依赖规格的答案。
2. 修复真相来源并编写可比较合同——事件定义、日期基础、时区、货币、计数方法——在指定任何指标之前。每个后续数字都会继承这些选择；更改它们之后会使所有历史记录无效。这里有三个数据基础竞争，按每单位努力的价值排序，其中努力是协调工作和日常维护：
   - 效率：`账单/订单骨干 > 客户文件连接 > 建模仓库`
   - 价值：`建模仓库 > 客户文件连接 > 账单/订单骨干`
   - 努力上限（最前）：`建模仓库 > 客户文件连接 > 账单/订单骨干`

   这三个基础的区别在于这些成本：

   - 骨干：一周内将平台导出与订单或账单进行协调，然后日常成本接近零。
   - 客户文件连接：一个季度，因为合作伙伴 ID 必须在订单或账户创建时标记，才能计算新文件和来源与影响。
   - 建模仓库：一个日常任务。

   默认使用骨干，只有在有命名决策需要它时才升级。

   删除，而不是降级：联盟平台自己的导出作为真相来源。那是索赔者的数字，因此没有努力节省可以弥补；平台仍然是点击和流量的来源，与金钱骨干进行协调。

   这会剥夺建模仓库：最高价值，在每一轮中都会失去。当程序的实时问题是增量性而不是报告，或者一个重新定价决策比构建成本移动更多资金时，提升它。

   三个成本区分这些基础：

   - 客户文件连接：一个季度，因为合作伙伴 ID 必须在订单或账户创建时标记，才能计算新文件和来源与影响。

3. 选择指标层级集：业务/标题层级、输入/驱动层级、健康/护栏层级。

   四个指标是基础而不是选择，因为无法达到通过阈值而没有它们：

   - 程序净贡献
   - 销售成本
   - Top-N 合作伙伴集中度
   - 合作伙伴来源的 MRR/ARR（B2B）

   超过这个基础的所有内容都是一个菜单：取您所在细分市场的效率顺序中的顶层档位在 [references/metric-definitions.md](references/metric-definitions.md)，该顺序分别对 B2B 和 B2C 进行排序，并命名每个顺序剥夺的内容。拒绝任何失败的四个良好指标标准的指标，并在仪表盘显示所有内容因此什么之前停止添加档位。删除其数据不存在于面谈中，并在“开放项”下命名，而不是将其保留在规格中作为一个愿望。

4. 编写每个指标的规格行（见输出形状），明确解决每个竞争定义——选择的分子、分母、窗口和计数方法放在行中，而不是放在任何人的头脑中。
5. 选择程序数据实际上可以支持的切片维度，按 [references/layout-cadence-and-alerts.md](references/layout-cadence-and-alerts.md) 中的效率顺序：`合作伙伴 > 合作伙伴类型 > 产品/计划 > 地域 > 设备 > 登录页面 > 创意`。合作伙伴类型不是最便宜的切片，也是支付最多的——无论如何都要构建它。
6. 为每个受众选择一个视图：高管和操作员视图在指标上不同，而不仅仅是详细级别。
7. 按层级设置刷新和审查节奏——每个层级都有自己的自然节奏；整个仪表盘一个刷新率是一个缺陷。
8. 设置警报阈值，每个警报都有所有者、渠道和预期的响应时间；优先考虑滚动基线动态阈值而不是静态阈值。按 [references/layout-cadence-and-alerts.md](references/layout-cadence-and-alerts.md) 中的效率顺序发送它们——`逆转率尖峰 > 单个合作伙伴份额尖峰 > 点击到转化异常 > EPC 下降 > 品牌出价标志`——并在团队注意力耗尽时停止，而不是填满条带。
9. 从程序的历史中派生程序自己的基线；不采用任何供应商基准作为基线。发表数字仅校准预期（[references/concentration-and-cohorts.md](references/concentration-and-cohorts.md)，[references/roi-and-incrementality.md](references/roi-and-incrementality.md)）。
10. 在组装最终文档之前，与用户逐节验证规格——定义、然后视图、然后节奏、然后警报——将其建立在 [references/worked-examples.md](references/worked-examples.md) 中匹配的工作示例基础上。
11. 检查通过阈值下方；迭代直到每个标准都得到满足。
12. 如果您的框架具有持久内存，请记住可比较合同、商定的指标定义和派生的基线，以便后续运行从它们开始而不是重新协商。

## 输出形状

以这个工件交付每个规格：

```
DASHBOARD SPEC - <program>
Header    : program, audiences, source of truth, period conventions
            (timezone, date basis, currency, validation window)
Metrics   : 每个指标一行 -
            Metric | Definition (formula, window, counting method) | Tier | Source |
            Visualization | Target | Alert threshold | Provenance
Views     : 每个受众的布局 - KPI 瓷砖（值 + 与先前报告期的差异）
            -> 趋势/组成图表 -> 排行榜/详细表格 -> 警报条
Dimensions: 切片维度（合作伙伴，合作伙伴类型/促销方法，产品，
            地域，设备，登录页面，创意）
Cadence   : 每个层级 -> 刷新率 + 审查仪式（谁审查，何时，决定什么）
Alerts    : 注册 - 指标 | 触发器 | 所有者 | 渠道 | 预期响应时间
Open items: 数据差距，未确认的定义，由于数据或努力上限而被删除的指标和维度，以及
            使其可计算的；下一版修订的问题
```

在标题中记录选择的数据基础及其移动的原因——后来的读者无法仅从指标行中重新推导出这个选择。

完整的工作示例位于 [references/worked-examples.md](references/worked-examples.md)，永远不会内联。

## 通过阈值

只有当程序所有者可以一眼看出：_这个程序是否有利可图，以及谁在推动它_时，规格才会通过。具体来说，所有六个都必须满足；迭代直到它们满足：

- 每个标题数字都可以通过其书写的公式由未构建仪表盘的人重现。
- 净程序贡献——经过验证的佣金加上网络/代理费用与归因净收入——无需离开顶部视图即可看到。
- Top-合作伙伴集中度也在同一顶部视图中可见。
- 仪表盘上的每个指标都有一个命名的决策它会通知；否则删除它。
- 没有一个指标的定义不能在一句内陈述。
- 每个指标、维度和警报没有进入规格的，都在“开放项”下显示其可计算的内容——没有在底部无声地停放。

## B2B SaaS 与 B2C 电子商务

这些完全适用于两者：

- 可比较合同
- 指标层级
- 集中度分析
- 节奏纪律
- 警报设计
- 经过验证而不是毛收入报告

真正不同的地方：

- **收入对象。** B2B 跟踪合作伙伴来源的 MRR/ARR 和流失调整的合作伙伴 LTV；B2C 跟踪订单级别的 CPA、AOV 和购物车组成。
- **漏斗。** B2B 添加试用到付费作为第二个转化阶段，加上交易注册和 MQL/SQL 管道阶段；B2C 是从点击到订单，新文件是额外的维度。
- **窗口。** B2B Cookie 窗口运行 60-180 天用于长周期；B2C 默认为 ~30 天，优惠券/现金返还流量更短。`mbfinotti/partnerships-skills@affiliate-commission-structure` 拥有这些范围——根据其数字阅读窗口，而不是在这里陈述的第二组。
- **逆转驱动者。** B2B：试用失败、退款、降级、流失——经常性佣金使逆转成为每个周期性事件。B2C：返回和退货窗口内的退货和拒付。

## 失败模式

| 缺陷                                                 | 后果                                                         | 修复                                                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 虚荣指标标题（点击、展示、注册）                     | 仪表盘看起来很忙；不通知任何决策                           | 每个指标需要一个命名的决策；将计数降级为诊断                       |
| 报告毛佣金而不是经过验证的                             | 程序看起来比它实际更昂贵、更有效率                         | 标题仅经过验证/批准；单独显示待处理状态                               |
| 最后点击仅程序 ROI                                  | 优惠券/现金返还/扩展合作伙伴使膨胀；内容合作伙伴受饿           | 添加新文件份额和增量性测试；分别报告来源与影响                       |
| 没有集中度视图                                       | 一个合作伙伴的退出抹去了未被注意的大收入份额                | 高管视图上的 Top-1/5/10% 分享，每季度审查                             |
| 待处理和批准状态混合                                 | 总计无法重现；趋势无意义                                   | 可比较合同固定每个指标的每个状态                                       |
| 逆转滞后被忽视                                       | 最近时期看起来人为地好                                   | 仅比较完全验证的时期；标记不成熟的一个                               |
| 具有不同验证窗口的时期比较                           | 任何方向上的虚假趋势                                     | 永远不要比较它们；在每个图表上注释窗口变化                          |
| 子网络计为一个合作伙伴                               | 合作伙伴数量和集中度都被扭曲                             | 每个转化计一个归因实体；将子网络分开报告                       |
| 来源 + 影响 相加                                   | 双重计数的合作伙伴收入                                      | 两个封顶的数字；来源在符合两个条件的交易中优先                         |
| 网络/代理费用排除在销售成本之外                     | 真正的程序成本被低估                                       | 销售成本包括佣金、网络、代理和放置费用                               |
| 供应商基准被采用为程序的基线                         | 目标和警报在两个方向上都被误校准                           | 从程序自己的历史中派生基线；将供应商数字标记为仅校准                 |
| 静态警报阈值                                       | 警报疲劳；团队忽略条带                                   | 滚动基线动态阈值，带有所有者、渠道、响应时间                          |
| 没有附加决策的指标                                   | 审查会议背诵数字并决定什么                               | 在规格行中命名决策或删除指标                                      |

这些行不携带效率排序，故意地。每行都是一个缺陷，有一个修复，而不是一个问题的竞争修复菜单——对它们进行排名会排名读者的症状，而不是他们的选项。应用与每个匹配的行。

- 我们的SaaS联盟计划在400个合作伙伴中支付20%的持续收入。领导层每月都询问这是否盈利，而我无法回答。为我们设计一个仪表板。
- 我运行一个基于最后点击的电商联盟计划，优惠券网站看起来像是英雄。为我的团队每周审查的计划仪表板定义指标和视图。
- 为一个每月佣金支出80K的计划编写联盟计划KPI规范——我们每日和每月跟踪的内容，以及警报阈值和负责人。
