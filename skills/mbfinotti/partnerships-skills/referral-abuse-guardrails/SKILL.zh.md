# 推荐滥用防护措施

定义防护措施，阻止终端客户滥用客户推荐好友计划，并以防护措施规范的形式交付：包含阈值、验证关卡、奖励冻结政策、执行阶梯和监控信号。这项技能保护现有的任何奖励结构——它从不重新设计它。

没有公认的行业标准涵盖消费者推荐滥用。精确借鉴四件事，不多不少，仅作为思维模型，而非合规声明：

- GIVT/SIVT 形状（广告测量标准）：一个廉价的确定性层级和一个昂贵的佐证层级。
- OWASP OAT-019 账户创建：仅自动化部分。
- 信任与安全执行阶梯原则：比例性、一致性、透明度，适用于执行部分。
- Sybil 攻击结果，作为战略框架：没有中心化身份机构，虚假身份永远无法完全检测，因此每个防护措施实际上是对滥用者的成本。

目标是使滥用无利可图，而非捕获所有行为。

## 基本规则

- 严格防御性。仅描述每个滥用模式，以便防御者识别和阻止它所需的深度：在程序数据中陈述可观察的迹象，而非规避技术、工具或分步利用。
- 为每个数值阈值标注其来源：已发布的程序条款、学术结果、供应商经验法则或用户从自己的数据中得出的基线。永远不要将供应商经验法则呈现为行业常数。
- 警告两个流传的数字：“推荐欺诈占所有电商欺诈的21%”是循环供应商引用（供应商互相引用），而“4430亿美元虚假拒付与480亿美元欺诈”的数字是无法验证的精确度。引用机制——虚假阳性成本高于欺诈，因为它们导致失去LTV——而非那些数字。
- 区分真实滥用者与激进议价者。前者获得执行阶梯，后者获得规则调整，通常值得保留。
- 在推荐发生前未在程序条款中发布的规则，不可对该推荐执行。与发布规则一起设计每个规则。

## 面试

在设计任何东西之前提问。每条消息一个问题；尽可能提供选择题；跳过已回答的问题。

- 现行程序机制和奖励结构是什么：单边性、奖励类型和每方价值、支付触发条件？
- B2B、B2C 或两者兼有？
- 用户账户和身份模型是什么：仅电子邮件注册？电话？在符合资格事件发生前已有支付工具？
- 目前哪些验证功能存在（电子邮件确认、短信、可丢弃域名阻止、设备信号、计费网络钩子）？
- 实际上可以查询哪些数据：推荐事件、注册元数据、支付记录、退款/拒付记录、按群体保留率？
- 目前的滥用情况如何，以及如何发现的？
- 风险的奖励价值是多少：每个奖励，以及整个程序每月？
- 基础购买下的退款或拒付窗口期有多长？
- 对摩擦与泄漏的容忍度是多少——宁愿多支付几个滥用者，还是失去几个真实推荐？
- 程序条款目前是否发布，以及它们对上限、资格和奖励拒绝说了什么？
- 必须在什么日期前启用防护措施——重新上线、董事会审查或已出血的事件？
- 您想要一次性修复已看到的滥用，还是一个随着程序扩展而持续控制的复合控制集？
- 努力上限是什么：本周期工程时间、审查人数，以及符合资格事件是否可更改？

最后三个设定了工作流步骤4中的控制顺序，因此在设计任何东西之前要问它们——在步骤4中，读者已经承诺了某个路径。

## 工作流

1. 运行面试；收集规范依赖的每个答案。
2. 确认范围边界：奖励结构（单边性、类型、大小、触发条件）是既定的。如果它是问题，请说明并转到 `mbfinotti/partnerships-skills@referral-incentive-design`（见参考资料）。
3. 从 `[references/abuse-patterns.md](references/abuse-patterns.md)` 映射程序的滥用表面：奖励价值、身份模型和符合资格事件实际上暴露了哪些模式。
4. 使用 `[references/guardrail-mechanics.md](references/guardrail-mechanics.md)` 处理控制阶梯。六个控制争夺相同的时间：

   - **事件**：符合资格事件设计。
   - **上限**：预算上限、速度限制、冷却期。
   - **冻结**：奖励冻结窗口。
   - **资格**：具有记忆的规则。
   - **验证**：关卡。
   - **审查**：人工审查。

   供应商博客将这个顺序反过来了——检测工具优先，程序设计最后。对它们进行排序：

   - 效率：`事件 > 上限 == 冻结 > 资格 > 验证 > 审查`
   - 价值：`事件 > 资格 > 冻结 > 验证 > 上限 > 审查`
   - 努力程度：`审查 > 事件 > 验证 > 资格 > 上限 == 冻结`
   - 合规成本：`验证 > 资格 > 事件 == 上限 == 冻结 > 审查`

   上限和冻结平局，因为每个都是支付侧的数值，在条款中发布，通过一次配置更改交付，不涉及任何合法用户，并且每个都限制对方无法限制的损失——上限限制数量，冻结限制逆转。事件、上限和冻结在合规成本上平局，因为它们都不接触身份数据或需要批准。审查在该轴上最低，因为流程中的一个人减少了风险：几个体系禁止完全自动拒绝。

   努力程度是复合的——合法用户摩擦、构建时间、可逆性。事件设计在它上排名高，因为重新布线触发器是产品和计费工作的四分之一，但仍然在效率上领先：该成本是一次性工程，而验证对每个合法注册永远收费。

   默认：第一遍总是包含上限、冻结和已发布的资格。每当当前符合资格事件是仅注册或未支付行为时，就重新设计事件——在事件免费伪造时，没有比它更低的东西可以保持。

   这个顺序使验证关卡和人工审查挨饿。两者对上限和冻结无法触及的两种滥用——自动化账户种植、B2B空壳实体——都具有高价值，并且每轮效率都损失。当每项审查成本低于奖励价值时（B2B默认），或当确认事件是自动化的而非机会主义的时，提升它们。

   根据面试答案重新排序，并在规范中命名移动了哪个控制：

   - 一个硬性实时日期会提升上限、冻结和资格（配置，一个冲刺），并安排事件重新设计为下一个周期——永远不会放弃它。
   - 一个复合指令会提升事件设计和资格记忆，它们在持续成本下继续工作。
   - 一个低努力上限会从规范中直接删除人工审查和上限验证，而不是将它们放在底部；记录您删除的内容和原因。

   再次根据您对程序的已知信息重新排序：

   - 在符合资格事件之前收集支付工具会显著提升验证——最强的关卡已经付费。
   - 现有的信任与安全功能会降低审查的努力程度。
   - 一个受监管的程序已经运行身份检查，所以其顶层成本在边际上为零。

   将顺序视为默认，而非法律：它会随着上下文和执行者而变化。

5. 明确处理 B2B 和 B2C。上限、冻结和资格记忆对两者工作方式相同——请说明。B2B 的差异在于：

   - 推荐者和被推荐者之间的域名重叠检查：重要的检查，因为仅工作电子邮件检查很弱，因为空壳公司有真实域名。
   - 支付前人工审查：B2B 中 ROI 为正，B2C 中不是。
   - 默认公司账户信用：支付给个人员工是采购/礼品政策问题，在它是欺诈问题之前。

6. 从 `[references/detection-signals.md](references/detection-signals.md)` 选择监控信号，该文档包含每个轴的完整排名。

   - 效率：`支付重复 == 群体质量 > 速度 > 电子邮件相似度 > 图 > 指纹`

   两个领导者平局，因为它们都已经在计费数据中，都不会随着浏览器或设备更改而降低，并且每个都捕捉到对方完全遗漏的内容。Cookie 和 IP 链接被排除在排名之外，而不是降级：它们的值已经处于地板上，因此排序它们将是虚假精度。图信号是这个顺序挨饿的；见参考资料中提升它们的条件。

7. 根据 `[references/enforcement-and-compliance.md](references/enforcement-and-compliance.md)` 设计执行阶梯：已发布的层级、每个拒绝的特定原因字符串和可工作的申诉路径——在检测器之前构建原因字符串和申诉路径。将法律约束视为设计约束，并将实际法律问题转交给法律顾问。
8. 验证每条规则都是可发布的：将当前条款中缺失的任何规则标记为不可执行，直到发布，并将条款起草工作转交给 `mbfinotti/partnerships-skills@affiliate-program-terms`。
9. 如果可以查询程序的符合资格事件数据，从用户的合法推荐者分布中推导出速度和标记阈值（例如每周的 p95-p99）；否则，将它们标记为说明性默认值，在第一次审查周期内用推导基线替换。
10. 逐段发出防护措施规范（输出形状下方），用于用户验证；将其基于来自 `[references/worked-examples.md](references/worked-examples.md)` 的匹配工作示例。
11. 附上从 Pass Threshold 下的校准计划，并迭代直到它成立。
12. 如果您的框架具有持久内存，请记住决定的阈值、冻结窗口和执行层级，以便稍后的调整运行从它们开始，而不是重新进行面试。

## 输出形状

以该文档为载体交付每个参与。每条阈值行都带有来源标签；每条规则行都命名可能触发它的合法行为。

```
推荐防护措施规范 - <程序>, <日期>
符合资格事件：奖励触发 + 为什么它难以伪造 + 逆转性说明
上限             ：每推荐者（周期 + 终身），每被推荐者，程序预算上限。
                   如果存在，则从现有的奖励设计中获取这些值并记录为既定；本规范执行上限，它不调整它们
速度             ：每推荐者每窗口的推荐/索赔 + 爆发后的冷却期
冻结政策      ：冻结长度 = 退款/拒付窗口 (+ 处理)，待处理状态显示
资格             ：新客户定义，自我/家庭排除，跨推荐者冷却，
                   B2B 域名重叠规则
验证             ：按摩擦层级关卡，每层级的升级条件，永远不设关卡的内容
监控             ：监控的信号，预期的标志基线，群体质量仪表板
执行             ：已发布的阶梯层级，原因字符串，申诉路径 + 响应 SLA
条款状态      ：每条规则发布的位置；未发布的规则 = 尚未可执行
校准             ：保留单元设计，审查节奏，泄漏/摩擦计算
```

## Pass Threshold

一起评估规范在泄漏和摩擦上的表现——永远不要单独评估捕获率或精确度目标。没有任何地方发布特定的推荐相关虚假阳性基准；永远不要用行业数字代替用户的保留单元。

- 使用相同单位计算：泄漏 = （支付的无效奖励）x（奖励成本）；摩擦 = （错误扣留的奖励）x（奖励成本 + 支持成本 + P(流失) x LTV)。摩擦项包含 LTV 倍数，泄漏项不包含，所以 1:1 错误率交易几乎永远不会收支平衡——如有疑问，放宽。
- 使用保留单元校准：在较宽松的规则下运行一个小单元，并将其与所有三个条件下的严格规则进行比较。只有当所有三个条件都成立时，规范才通过：
  1. **总价值，而非每注册**：严格单元的 90 天群体价值**每 1,000 个暴露的推荐者**至少是保留单元的。这个条件是承重，永远不能被每注册平均所取代。
     - 收紧会移除边际注册，所以在严格性中每注册价值是非递减的。
     - 每注册关卡最容易由最过度收紧的配置满足，并且永远不会因过度收紧而失败，而整个这一节存在的目的就是为了捕获这种失败。
  2. **质量**：被推荐群体在保留率、退款率和 90 天收入上优于有机群体。
  3. **上述公式的净额**：严格规则通过严格规则节省的泄漏超过了它们产生的摩擦成本，两者都基于相同的暴露基础计算。
- 即使有合理的防护措施，如果被推荐群体输给有机群体，程序是在购买注册，而不是获取客户——缺陷是奖励结构，所以请转到 `mbfinotti/partnerships-skills@referral-incentive-design` 而不是进一步收紧。
- 迭代阈值，直到所有三个条件都成立；如果校准数据不存在，请在交付物中说明，并将保留单元安排为首次上线审查关卡。

## 常见失败模式

| 缺陷                                                         | 后果                                                         | 修复                                                                                                                                                                                                                   |
| ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 防护栏过于严格以至于扼杀了合法推荐                             | 项目资源枯竭；摩擦成本超过节省的流失成本                      | 应用流失/摩擦公式；放宽直到每1000名曝光推荐者带来的群体价值恢复。每注册用户平均值的上升伴随着交易量的下降是这种缺陷的典型特征，绝不是反对它的证据 |
| 没有速度检查的配额限制                                       | 恶意用户在一个周末内达到终身配额上限，且未被检测到             | 每个配额都要配以每个时间窗口的速度限制和突发冷却时间                                                                                                                                                  |
| 忽略设备和支付工具的重复使用                                 | 便宜的确定性自我推荐被遗漏                                  | 首先检查支付工具的重复使用；这是已经持有的最强信号                                                                                                                                       |
| 沉默的奖励拒绝                                               | 信任损害、支持负担、多个地区的法律风险                      | 具体原因字符串+已发布的申诉路径，在检测器构建之前就建立                                                                                                                                           |
| 事后收紧规则                                                 | 对过去的推荐无法执行；监管机构的关注                         | 先发布，后执行；对已获得的奖励进行追溯                                                                                                                                                                    |
| 持有窗口短于退款窗口                                           | 裁判在付款后退款；奖励无法追回                              | 设置持有时间=退款/拒付窗口+处理时间，按产品线                                                                                                                                                            |
| 将热情的倡导者视为一个团伙                                     | 顶级推荐者被禁止；最糟糕的口碑                               | 要求超出图形形状的佐证：奖励分割、退款、群体崩溃                                                                                                                                                |
| 手动审核成本超过奖励价值                                     | 每次审核都是净损失，无论准确性如何                           | 仅对高于审核成本的奖励进行审核；B2B默认，B2C例外                                                                                                                                                |
| 对低价值消费者奖励进行完整KYC                                 | 注册放弃的规模远大于预防的欺诈                              | 停留在支付工具验证；KYC是为受监管项目准备的                                                                                                                                                              |

## KPI

- 跟踪：
  - 无效奖励率（流失）
  - 从申诉得到支持的错误扣留率（摩擦）
  - 推荐用户与自然用户的群体差异在留存率、退款率和90天收入上
  - 对预期多账户行为的基线进行标记率
  - 持有到释放时间
  - 预算上限消耗
  - 被拒绝奖励的支持工单
- 在同一单位上并列报告流失和摩擦，用货币单位表示——单独一个数字总是误导。
- 当以下情况出现时，升级规范本身：
  - 申诉得到支持率上升（规则过于严格）
  - 群体质量下降而标记率保持不变（团伙在暗中）
  - 合格事件的退款率上升（事件过于便宜）

## 调用示例

- "我们的餐盒套餐给双方各提供25美元，有人刚用40多个地址的电子邮件账户进行了收割。在我们重新上线之前，请编写防护栏。"
- "我们下个月将在健身应用中推出给10送10的活动——设计配额、持有政策和验证门，以防止它在第一天被操纵。"
- "我们的B2B SaaS为每个成功转换为付费的推荐工作区提供500美元的账户信用；财务怀疑一个机构在推荐自己的空壳账户。设置滥用防护栏和审核流程。"
