# 推荐激励设计

设计客户推荐好友计划的奖励结构。该领域没有公认的命名框架——推荐只是 AARRR 等测量漏斗中的一个字母，而非设计方法。现有的是四个决策变量，每个变量都有其自身的证据基础，需要按顺序逐一分析，因为每个决策都会影响下一个决策：

1. **单边性** - 奖励推荐人、被推荐人，或两者都奖励（奖励我/奖励你/双方奖励分类法，Ryu & Feick，《营销杂志》2007年）。
2. **奖励类型** - 现金、账户积分、折扣、产品价值、地位或捐赠。
3. **奖励额度** - 以毛利润、LTV 和 CAC 为基准，并设定由非单调响应决定的最低额度（过小的奖励效果可能不如没有奖励）。
4. **支付触发条件和等级结构** - 奖励何时发放，以及奖励是否会随着累积推荐升级。

## 面谈

在提出任何建议之前进行面谈。每条消息只问一个问题；在可能的情况下提供多项选择题答案。只有当用户已经给出答案时才跳过问题。

- 业务是 B2B 还是 B2C？订阅制还是一次性购买？自助服务还是销售主导？
- 毛利润、平均 LTV（或第一年收入）、混合/付费 CAC 和入门计划价格是多少？
- 客户是否已经自发推荐产品？大约有多少新客户是通过这种方式来的？
- 推荐人会再次购买吗（账户积分对他们有价值），还是不会（只有现金等价物有用）？
- 对于 B2B：可能的推荐人是购买者，还是为公司支付的公司员工？
- 必须在什么日期之前看到结果？硬性的季度末日期会促进快速层级——在首次购买触发时提供固定奖励——并排除等级和保留触发，这些需要几个月才能看到效果。
- 一次性获取胜利，还是复合型资产？复合型会促进实物和地位奖励、等级层级和保留触发；一次性胜利会促进固定被推荐人侧的优惠。
- 努力上限是多少：由谁构建和管理这个系统，他们有多少时间，以及是否可以后来撤回已发布的奖励？低上限会直接删除赠品、抽奖和分阶段支付；有专人负责会重新将等级层级提上议程。

## 工作流程

1. 运行上述面谈；在设计结构之前收集所有相关答案。
2. 在设计前检查排除项。推荐计划捕获现有的口碑传播；它不会创造口碑。没有自发推荐信号，或 LTV 太低无法提供有意义的奖励，意味着诚实的答案是“目前还不行”——直接说明并停止。确认问题是关于最终客户推荐，而不是外部联盟伙伴或渠道合作伙伴（经济模式不同，工具也不同；随着 ACV 增长，B2B 计划往往会从前者迁移到后者）。
3. 决定单边性，参考 [参考资料/单边性和触发条件.md](references/sidedness-and-triggers.md)。效率顺序：**仅奖励被推荐人 > 双向奖励 > 仅奖励推荐人**——三个分支的付出是相同的，因此价值证据决定，并且实地实验发现，仅奖励被推荐人的奖励与成本是双倍的双向奖励效果相当。优先考虑仅奖励被推荐人；对于创新产品或品牌力弱、关系薄弱的情况，转向双向奖励；仅奖励推荐人仅适用于确实需要高努力推荐过程的情况。
4. 根据每侧选择奖励类型，参考 [参考资料/奖励类型.md](references/reward-types.md)，优先考虑其效率顺序：**实物产品价值 > 账户积分 == 免费月 > 折扣 > 地位 > 现金 > 赠品 > 慈善 > 抽奖**。然后应用覆盖它的标准：
   - 当推荐人永远不会回购或产品与金钱相关时使用现金等价物。
   - 推荐是公开的、以身份为导向的行为时，优先考虑地位而非现金。
   - 慈善永远只作为选择。

   对于 B2B，明确解决委托代理分支（个人奖励与公司账户积分）。

5. 使用 [参考资料/规模和层级.md](references/sizing-and-tiers.md) 调整奖励：计算毛利润上限，从最少的努力锚点开始选择目标（CAC 的百分比 > LTV 的百分比 > 投资回报纪律），验证最低额度（非单调响应：有意义地支付或根本不支付），并使用 100 规则包装数字（百分比低于 100，绝对金额高于）。
6. 在已验证的价值事件上设置支付触发条件，永远不要仅基于注册。效率顺序：**首次购买 > 合格激活 > 已成交/首次发票 > 保留阈值 > 分阶段支付**；对于销售主导的 B2B 运动优先考虑已成交，当退款或流失风险较大时优先考虑保留阈值。将持有期与退款风险和销售周期长度匹配。
7. 决定是否分层，参考 [参考资料/规模和层级.md](references/sizing-and-tiers.md) 中的层级规则。效率顺序：**固定 > 阈值层级 > 步进**；层级只有在量高、重复推荐者可能存在、倡导集中在少数倡导者时才值得其构建成本。第一层显然可实现；顶层始终有限制——该领域最明确的失败是无限层级的层级。
8. 逐一呈现四个决策——考虑过的选项、权衡、以及你的建议——并使用用户验证每个决策；在反对意见之前修改，然后进入下一个。
9. 在所有四个决策获得明确批准后，以可测试的规范形式发出完整结构（下一节），并在用户情况适合时，参考 [参考资料/示例.md](references/examples.md) 中匹配的工作示例作为基础。
10. 如果你的系统具有持久内存，记住已批准规范的决策要点和经济效益——后续诊断运行将从这些点开始，而不是重新面谈。

上述所有排序都按单位努力返回的价值排序——构建时间、管理、履行、协调以及一旦发布后难以逆转的选择有多难。永远不要按支付额度排序；奖励成本是一个独立的维度，两者经常不一致，以至于混合排名会掩盖最便宜选项和最强选项可能是不同选项的情况。

每个排序都是一个默认值，而不是法律：它会随着情况和执行者而变化。在呈现任何菜单之前，根据你对这个用户的了解重新排序：

- 边际单位成本接近零的产品会促进实物奖励高于一切。
- 拒绝现金支付的财务团队会从菜单中删除现金，而不是降级它。
- 现有的奖励平台会消除将等级层级和赠品置于底部的努力差距。

大声说出哪个事实移动了哪个选项，以便用户可以就推理而不是行顺序进行争论。

## 奖励结构规范

将每个参与都作为此工件交付——用户可以将其交给产品、财务和测试计划负责人：

```
奖励结构 - <产品>, <日期>
单边性        : 双向 | 仅奖励被推荐人 | 仅奖励推荐人，分割，披露选择
奖励（被推荐人）: 类型、金额、框架（“首月免费”，而不是“49 美元折扣”）
奖励（推荐人） : 类型、金额、框架
支付触发条件   : 每侧的已验证事件 + 持有期 + 待处理状态显示
层级            : 等级断点 + 顶级限制，或“固定 - 当 <条件> 时重新审视”
上限            : 每个推荐人/年，已赚取总额，计划预算上限
经济效益        : 毛利润上限，预计每个推荐客户的成本与当前 CAC 对比
验证            : 测试分支，基础暴露百分比，持续时间，决策指标，增量检查
KPI             : 参与率，注册转化率，增量推荐客户成本与 CAC 对比
```

规范的三个规则：

- **每行都有一个原因。**“推荐人账户积分在第二次发票时触发——在退款窗口内持续存在”是可审查的；裸金额不可审查。
- **验证计划不是可选的。**单边性在从业者之间和实地研究中确实存在争议，因此要命名其测试分支（双向 / 仅奖励被推荐人 / 仅奖励推荐人，占 5-10% 的基础）及其增量检查。增量检查意味着保留一部分：固定获取量与上升的 CAC 显示该计划为本来会来的客户付费。
- **规范有一个通过阈值。**增量推荐客户成本必须低于当前混合 CAC 并在毛利润上限内。迭代规模、类型或触发条件，直到两者都成立；如果没有结构通过，建议不启动。

## 诊断现有计划

当用户带着运行中的计划而不是空白页面到来（“我们提供 10 美元积分，但没人使用它”）时，按效率顺序工作——每单位努力修复最多的计划，这与最便宜的修复不同：

**效率**：重新定位请求 > 重新分配分割偏向被推荐人 > 提高规模超过最低额度 > 限制等级并移动触发条件 > 切换奖励类型 > 运行增量保留

| 症状                                     | 首先检查                                                                                       | 努力                                                                           | 故障变量                                                                    |
| ------------------------------------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 很少有客户分享                           | 请求的时机和摩擦 - 位置比奖励大小更能提高参与度 | 一个小时 - 移动提示，更改文案                                               | 无 - 在触摸奖励之前修复请求                                                    |
| 分享发生，朋友不转化                     | 被推荐人侧的优惠强度 - 朋友有更难的工作                                                         | 一个小时 - 重新分配你已经花费的预算                                           | 单边性/分割                                                                    |
| 添加奖励后参与率下降                     | 代币金额低于激励最低额度，将好事变成了低报酬的工作                                             | 一个小时的配置，对抗永久预算增加                                               | 规模                                                                           |
| 功劳推荐人榨干等级                     | 缺少顶级限制或注册触发的奖励                                                                    | 一周 - 并且限制已发布的等级是最难在此处坚持的改变                           | 等级/触发                                                                      |
| B2B 推荐人拒绝奖励                       | 企业礼品政策冲突                                                                               | 一个季度 - 财务、采购和法律都会触及它                                       | 类型：切换到双轨模式（公司积分 + 可选的个人代币）                                |
| 健康的推荐量，上升的 CAC                 | 增量 - 奖励为自发的口碑传播付费                                                              | 一个季度 - 设计保留，等待完整周期以阅读结果                                 | 经济效益：运行保留，然后缩小奖励到低有机触达部分                             |

顺序会饿死增量保留：它在比率上最后，在真相上第一个，因为它是可以揭示整个计划正在购买本来会来的客户的唯一检查。当推荐量看起来健康而 CAC 上升时立即推广它——这是没有便宜修复可以解释的症状。重新根据用户的约束重新排序其余部分：一个无法在本季度交付 UI 的团队不能重新定位请求，这会将分割重新加权推到顶部。

## B2B 和 B2C

无论 B2B 还是 B2C，都是相同的：

- 四个决策及其顺序。
- 毛利润上限。
- 非单调最低额度。
- 100 规则框架。
- 在已验证的价值事件上设置支付触发条件。
- 增量修剪。

不要为每侧重新发明任何东西。

证据基础是不对称性值得大声说明：该技能依赖的实地实验和学术结果绝大多数是消费者侧的。在建议 B2B 计划时，说明每个数字都是 B2C 测量并 B2B 推断的。

| 维度              | B2C                                                 | B2B                                                                                                                                                                     |
| ---------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 谁被奖励        | 客户，也是付款人                                     | 通常是非付款人——员工 - 在第 4 步明确解决委托代理分支                                                                                                                            |
| 奖励载体         | 个人账户积分或现金等价物                             | 默认为公司账户积分；个人奖励是礼品政策和采购问题，然后才是激励                                                                                                               |
| 支付触发条件         | 首次付款发票或激活里程碑                             | 晚 - 已成交或保留阈值，因为周期更长，退款风险更大                                                                                                                                     |
| 扩展上限        | 在规模上保持不变                                      | 真实情况：随着 ACV 增长，客户推荐计划会迁移到联盟或合作伙伴计划。注意迁移信号，而不是将此结构拉伸到它之外                                                                                   |
| 披露敏感性        | 中等                                                | 更高 - 推荐人向自己的网络推荐供应商，带有其雇主可能也会监管的物质联系                                                                                                             |

## 调用示例

- “设计一个 49 美元/月的 B2B SaaS 推荐好友奖励——80% 的毛利润，14 个月的平均任期，220 美元的付费 CAC。”
- “我们双方都提供 10 美元积分，但没人使用。诊断四个变量中哪个出了问题。”
- “我们的推荐奖励应该分层吗？大约 8% 的客户会推荐，少数客户会重复推荐。”
