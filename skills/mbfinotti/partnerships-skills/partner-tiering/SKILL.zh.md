# 合作伙伴层级

定义现有 B2B 合作伙伴计划中区分不同层级合作伙伴的标准和利益。不存在单一的规范层级设计方法——直白地说，而不是编造一个。该领域实际提供的方法有：

- **Forrester 的三级标准**：98% 的顶级 IT 合作伙伴计划使用层级制，平均分为三个层级，分别命名为“良好、更好、最佳”（分析师断言，非原始调查数据）。
- **The Alexander Group 的三级机制**：交易量、参与度或参与路径（跨多个维度的积分累积）——这是设计师做出的第一个结构选择。
- **Forrester 的渠道合作伙伴细分矩阵**（Stephanie Sissler，2023 年 2 月）：一个 3x3 当前表现 x 未来潜力的网格，明确是内部叠加在公共层级阶梯上的覆盖层，永远不会取代它。
- **Jay McBain 的批评**（一个归因于实践者的观点，而非框架）：“收入是一个滞后指标，非交易型合作伙伴——技术/ISV、推荐、咨询——在结构上不适合收入阶梯。”

## 面谈

在设计和任何东西之前提问，每条消息一个问题。提供多个选择。跳过用户已经回答的部分。

- 合作伙伴的数量和类型——分销商、MSP、代理、技术/ISV、推荐？哪些类型实际进行交易？
- 当前层级、标准及其分布——有多少合作伙伴位于每个层级？
- 具体痛点是什么：顶级层级拥挤、无人晋升、利益被忽视、长尾被忽视、渠道冲突？
- 合作伙伴收入集中度如何——大约有多少份额来自前 10-20% 的合作伙伴？
- 每个层级今天的成本是多少：利润让步、交易注册提升、MDF、PAM 人员数量？
- 今天的审查频率是什么，降级是否实际执行？
- 平均销售周期长度是多少？（任何作为层级利益的交易注册保护期都应 ≥75% 的周期长度，因此从标准范围内选择的窗口可能只有周期所需的一半。）
- 必须在什么日期前使新结构生效，以及必须在什么日期前其结果在层级变动中显现？
- 这是一个针对特定痛点的临时修复，还是一个将在此之后每个周期重新评分的复合资产？
- 努力上限是什么：合作伙伴运营小时数、可用数据工作，以及实际执行降级的政治资本？
- 这是仅限 B2B 渠道，还是计划也运行面向 B2C 的联盟、创作者或忠诚度层级？
- 什么是不可改变的：已签署的合作伙伴协议、财政日历、薪酬计划？
- 谁必须批准：渠道主管、CRO、财务、法律？

## 工作流程

1. 运行面谈。收集设计所依赖的每个当前状态事实。
2. 确认范围：细化已存在计划中的层级层。从头开始构建计划或修复单个合作伙伴表现属于参考部分中的兄弟技能。
3. 构建基线：合作伙伴、收入贡献和按当前层级每服务成本。预期幂律——10-20% 的合作伙伴驱动 70-80% 的渠道收入是常见的模式（PRM 供应商经验法则，非经验数据集）。
4. 确定层级数量（默认 3；在约 50 个合作伙伴以下合并为 2）——参见 `[references/distribution-and-cadence.md](references/distribution-and-cadence.md)`。然后在此处选择机制，此处实际做出选择：
   - **交易量**——仅收入阈值。近零设置：CRM 已包含数量。购买最弱的排名，因为收入是滞后指标，每个非交易型合作伙伴在它上面的得分都是零。
   - **参与度**——收入加上认证、能力或留存。大约四分之一的时间建立起来，之后每个周期近零。购买合作伙伴在申诉时无法争辩的标准，并且非分销商可以攀登的阶梯。
   - **积分路径**——一个发布公式对不同权重动作进行评分。一个持续的工作：公式、每个类别的最低标准，以及每个周期您需要向合作伙伴重新计算的重新计算。购买最精细的排名，并且它是唯一一个按基础无法正确排序的机制。
   - 效率（最佳比率优先）：`参与度 > 交易量 > 积分路径`
   - 价值（排名力量购买）：`积分路径 > 参与度 > 交易量`
   - 努力程度（最重优先）：`积分路径 > 参与度 > 交易量`
   - 成本不单独成行：一个机制的唯一成本是运行它的工作量，因此其成本顺序是其努力顺序。
   - 默认为参与度。当合作伙伴跨多个动作进行交易时——来源、协助、管理——升级到积分路径。没有单一指标可以按渠道团队会捍卫的顺序对它们进行排序。
   - 这个顺序使积分路径受饿：最高价值、最高努力，所以它在每一轮中都会输。尽管程序已经因降级争议而损失，或者每个周期每个案例都会进行层级分配的争论时，仍然提升它。
   - 一旦有相当一部分基础从不交易，就彻底删除交易量。一个交易量阶梯根本无法对那些合作伙伴进行排序，并且将其保留在短名单上会恢复一个将 ISV 和推荐合作伙伴视为不良合作伙伴的阶梯。
   - 根据面谈答案重新排序：
     - 一个季度内的硬日期会提升交易量，并在此轮中移除积分路径
     - 复合指令会提升它
     - 没有合作伙伴运营小时数的努力上限会移除它
   - 然后为不交易型合作伙伴类型提供适合它们的条件，或单独的轨道。
5. 在触摸利益之前定义资格和维护标准——标准决定谁会落在哪里；首先设计的利益承诺了一个从未建模的群体。参见 `[references/tier-criteria.md](references/tier-criteria.md)`。
6. 在接触现有合作伙伴基础之前对拟议标准进行回测：
   - 检查结果分布是否符合下方的通过阈值。
   - 调整阈值并重新运行。

   这一步产生下一阶段定价的模型化层级人数——在回测之前定价的捆绑包是对一个无人统计的群体做出的猜测。

7. 定价每个层级的利益捆绑，并检查双向的交换平衡：层级的收入覆盖其捆绑成本，并且每一步向上都明显奖励合作伙伴的攀登。参见 `[references/tier-benefits.md](references/tier-benefits.md)`。
8. 设计晋升、降级、审查频率、测量窗口、宽限期、追溯和申诉路径。
9. 规划迁移和社会化：合作伙伴咨询委员会预览、通知期、迁移沟通、已发布的决策日期。
10. 根据下一节进行头脑风暴和验证：候选结构首先，然后按部分验证规范。
11. 检查通过阈值；迭代标准、利益或层级数量，直到每个检查都成立。
12. 在获得用户的明确批准之前停止——不要在用户明确批准完整规范之前最终确定任何东西。
13. 如果您的框架具有持久内存，请记住批准的结构、阈值和第一个审查日期；否则请告诉用户将规范存储在合作伙伴运营可以检索的地方。

如果您可以浏览网页，请在引用之前验证任何命名供应商结构——主要计划在 2022-2026 年期间反复重组。否则将供应商示例标记为可能过时。

此技能及其参考文件中的每个排序——上述机制、标准、利益、频率和降级立场在参考文件中——都是默认值，不是法律。它会随着计划的环境和执行者的变化而变化。

根据您对用户已有的了解重新排序每一个：

- 一个活跃的认证注册表将参与度机制的设置降至近零，并绝对获胜
- 仓库中已构建的按动作归因将积分路径的持续工作变为查询
- 没有政治资本进行今年降级的渠道主管会改变频率顺序

说明用户的哪些事实移动了哪些选项，而不是重述默认值。

## 头脑风暴结构

按渠道团队实际运行的方式运行设计——一个压缩的 90 天设计冲刺，而不是单一答案：

- 每条消息一个问题；不要批量提问。
- 汇总渠道专业人员带来的数据：合作伙伴损益表、来源收入分布、服务成本、PSAT/NPS、门户参与信号。用现有数据进行建模；命名缺失的内容。
- 绘制 RACI：渠道主管负责，合作伙伴运营运行模型，合作伙伴营销拥有迁移沟通，财务验证利润，法律修订协议，CRO 维护计划。
- 首先细分基础（合作伙伴类型 x 规模 x 经济潜力）；内部叠加 Forrester 3x3 网格进行合理性检查，以检查关键合作伙伴会落在哪里。
- 提供 2-3 个候选层级结构，使用工作流程步骤 4 中排名的机制构建：首先提供该基础推荐的排名，然后说明每个替代方案必须满足什么条件才能击败它。
- 一旦用户选择方向，按部分一次呈现规范——标准，然后利益，然后频率，然后迁移——并在编写下一个之前验证每个部分。
- 建议在公开发布之前通过合作伙伴咨询委员会预览近最终结构；层级变更是通过协商和关系绑定的，而不是交付的。
- 以用户明确批准组装的规范为最终确定门槛。

## 层级结构规范

以该文档交付——用户将交给合作伙伴运营、财务和法律的决定记录：

```
层级结构 - <计划>, <日期>
机制         : 交易量 | 参与度 | 积分路径，如果积分则附上公式
层级数量       : N，以及为什么不 N-1 或 N+1
每个层级（重复每个，从底部到顶部）：
  名称           : 面向合作伙伴，可重复（从不使用“层级 2”）
  资格           : 标准加上阈值 + 测量窗口 + 数据源
  维护          : 在每个审查检查点保持层级的条件
  利益          : 捆绑包，每个利益及其模型化单位成本
  模型化人数     : 今天符合条件的合作伙伴（来自回测）+ 基础的百分比
  服务成本      : 该人数下模型化的年度捆绑包成本
  收入          : 该队列的模型化贡献
计划级别：
  审查频率      : 重新计算时刻 + 滚动 vs 固定窗口
  宽限期        : 降级生效前的长度
  申诉          : 路径 + 命名决策所有者 + 已发布的决策日期
  追溯          : 谁在迁移期间保持状态，直到何时
  迁移计划      : 通知期，咨询委员会预览，沟通里程碑
  验证          : 试点队列或模型检查，在全面推出之前
  KPIs          : 来自 KPI 部分的第一次审查日期
```

规范本身的规则：

- 将测量窗口和数据源附加到每个阈值——无人可以计算的标准不会降级任何人。
- 在每行上携带一个原因（“顶级层级要求 80% 的毛收入留存——控制交叉销售对留存质量的承诺”）；一个数字本身是不可审查的。
- 拒绝任何合作伙伴可以自我报告或操纵的标准；仅使用计划本身记录并在争议中可以辩护的数据。
- 将回测人数视为强制性的：一个从未针对真实合作伙伴基础运行的结构的结构是一个猜测，而不是设计。

## 通过阈值

在所有四个都成立之前不要发布任何东西；迭代设计直到它们成立：

1. **可达到，而不是拥挤。** 顶级层级可被大约 >=10% 的合作伙伴达到（PRM 供应商启发式，非经验基准）。如果远更多合格，则阈值滞后于基础——提升它们。
2. **每个相邻步骤都有明显的经济差异。** 一个 ~2% 的折扣提升加上一个更漂亮的徽章是记录的失败：合作伙伴理性地拒绝攀登。
3. **每个层级自我资助。** 每个层级的模型化利益捆绑成本低于该层级的模型化收入贡献。
4. **无游戏性。** 没有标准是自我报告或可操纵的——标志计数和自我报告的管道是记录的游戏向量。

## 诊断现有层级结构

当用户带着运行中的结构而不是空白页面到来时，在表中找到他们的症状——行按症状键入，而不是按优先级。

当同时出现多个症状时，按效率顺序（而不是严重性）按此顺序修复：

`标准阈值 > 利益差异化 > 频率、宽限期和沟通 > 利益分配到中间 > 层级数量`

- 提升阈值是对程序已经持有的数据的电子表格更改，并且会在下一个审查中落地。
- 合并层级数量是一个迁移，一个沟通计划，和一个协议修订，所以它支付最后，即使膨胀是用户进来抱怨的原因。

拥挤的顶级层级和无法解释的阶梯通常是同一种疾病，而阈值修复可以治愈两者。

层级数量是那个顺序受饿的——列表中最高价值的修复，仅就努力而言排名最低，所以比率在每一轮中都会推迟它，而阶梯在第一开始时无法解释。当相邻层级在标准和利益上停止不同时，或者当由于其他原因正在进行迁移并且数量可以免费搭乘而无需额外沟通成本时，提升它。删除程序约束排除的任何行，并说明它被删除——已签署的协议固定当前利益捆绑移除差异化行此周期——而不是将其保留在底部，它将作为无人规划的工作返回。

| 症状                                             | 首先检查什么                                                                | 故障设计变量                                |
| --------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------- |
| 无法解释的层级（5+，重叠标准）                     | 相邻层级是否在标准和利益上不同                | 层级数量 - 合并                                   |
| 顶级层级拥挤（压缩）                              | 阈值上次提升与基础增长的时间      | 标准阈值 - 提升                                  |
| 无人晋升；合作伙伴停滞在入口处                    | 阈值曲线：底部太容易，顶部太难；步骤之间的悬崖 | 阈值间距                                       |
| 合作伙伴忽视阶梯，不会投资                        | 每个步骤的经济差异：折扣、交易注册提升、返利          | 利益差异化                                     |
| 利益分配但未使用（未申领 MDF）                   | 申领摩擦和合作伙伴营销带宽                             | 利益设计，不是标准                              |
| 层级指标看起来很棒，结果不好                      | 哪些标准是自我报告的（管道、标志）                         | 标准游戏性                                    |
| 长尾休眠                                       | 投资份额达到中低层级                                | 利益分配 - 在添加层级之前修复中间部分             |
| 合作伙伴之间或与直接销售的交易冲突                 | 交易注册执行的持续性                               | 利益执行，不是结构                              |
| 审查日期后出现流失率激增                         | 降级意外：通知、宽限期、申诉                           | 频率、宽限期和沟通                               |

## KPIs

评估层级结构本身，而不是单个合作伙伴（个人评分卡属于 `mbfinotti/partnerships-skills@partner-performance`）：

- 连续审核期间等级分布形态 - 倾向于压缩或中间空缺。
- 每个审核期间晋升的合作伙伴比例。
- 每个等级的收入与每等级的服务成本对比。
- 利益使用率，尤其是MDF报销率：通常40-60%未被报销（行业常见数据来源）。
- 合作伙伴满意度（PSAT/NPS）按等级划分。
- 降级后的流失率与基准合作伙伴流失率对比。

## B2B与B2C

两者相同：幂律集中、阈值门控的资格→状态→权益→重新资格认证循环、上述等级数量规则（默认3个，合作伙伴数量低于50个时压缩为2个），以及上述失效模式。

不同 - 针对差异进行设计：

- **进阶货币**：B2B渠道 = 收入+认证+CSAT/留存；联盟/创作者 = 销售额或滚动窗口GMV；消费者忠诚度 = 年度资格消费、住宿次数或里程。
- **重置节奏**：B2B = 滚动或年度带宽限期；联盟 = 滚动；消费者忠诚度 = 严格的年度状态时钟。
- **人性化触达**：B2B = PAM覆盖和QBR；B2C = 全流程自助自动化。
- **可测试性**：联盟或消费者阶梯可在大用户群中进行A/B测试；B2B等级变更需协商、基于关系并经合作伙伴咨询委员会推广 - 而是进行模型和试点。

参见[references/worked-examples.md](references/worked-examples.md)获取与真实供应商案例的完整对比。

## 调用示例

- "所有人获得统一的20%折扣，我们的顶级合作伙伴在询问他们还能获得什么。设计等级阶梯 - 160个合作伙伴。"
- "我们的顶级等级人满为患且从未执行降级。修正标准并规划迁移。"
- "我们有25个非交易型ISV合作伙伴无法资格认证任何等级。给他们设定符合标准的资格。"
