# 合作渠道计划

从头开始设计一个 B2B 合作/渠道计划的总体架构。这项技能是架构师：它决定计划是否应该存在，它需要哪些结构组件——动作、层级、经济框架、治理、时间范围——以及它们如何组合在一起，然后将每个组件的详细设计交给专业技能（见参考）。

该领域最被充分记录的失败原因是结构性，而非战术性：启动一个计划来修复一个不工作的直接动作。合作伙伴放大一个有效的动作；他们不会修复一个有问题的动作。下面的顺序先进行战略，再进行结构，并且其门控允许回答“还不行”。

## 面谈

在设计和任何东西之前进行面谈。每次消息只问一个问题，尽可能提供多选答案。只有当用户已经给出答案时才跳过问题。

- 业务是 B2B 还是 B2C？对于消费者业务（经销商、特许经营、大使模式）设计部分确实存在差异——请参阅 [references/b2b-b2c-contrast.md](references/b2b-b2c-contrast.md)。
- 合作伙伴将销售或影响的产品或价格点是 ACV 或价格点？
- 直接销售动作是否已经可重复，产品市场契合度是否已经得到证明？证据是什么？
- 毛利率是多少，其中有多少可以用于合作伙伴补偿？
- 是否已经存在非正式合作伙伴——服务您客户的代理商、集成商、顾问——或者是否有人已经联系您进行合作？
- 谁将日常拥有该计划，他们向谁汇报？
- 哪些资源已经承诺：专职人员、预算和一位执行赞助人的姓名？
- 今天在合作伙伴接触的交易中，直接代表如何获得补偿——中立、受罚或未定义？
- 成功意味着什么，必须在什么日期之前实现第一个通过合作伙伴获取的结果？命名指标（收入分成、管道、覆盖范围）、日期和谁进行评判。
- 您想要今年的单次胜利还是一个复合型资产？两者都是合法的答案；它们选择不同的动作。
- 考虑到资源，该计划必须生活在其中的努力上限是什么——所有者每周的小时数，是否所有站立人员数量都是可资助的，以及设计中有多少必须保持可逆性。

最后三个答案会重新排序第 4 步的动作菜单——将它们带到那里而不是重新询问：

- 两个季度内的硬日期删除经销商和服务-SI：它们都不会那么快产生收入。
- 复合型任务会促进技术合作和经销商覆盖范围。
- 今年需要的人数会促进推荐。
- 没有可资助的站立人员数量会再次删除经销商和服务-SI，并且一个由一个人组成的团队会保留推荐加上最多一个集成。

## 工作流程

1. 运行面谈；收集门控和架构依赖的每个答案。
2. 应用准备门控。不合格项，任何一项都意味着诚实的答案是“还不行”：
   - 直接动作不可重复，或者合作伙伴关系预计会修复一个增长问题。
   - ACV 太低，无法资助人力密集型合作伙伴工作（非常低的 ACV 支持最多仅推荐——经销商/SI 动作需要更多）。
   - 毛利率无法资助合作伙伴利润。
   - 没有命名的执行赞助人。

   如此说明，命名必须改变的内容和较轻的动作（如果有），然后停止。完整门控：[references/readiness-and-failure-modes.md](references/readiness-and-failure-modes.md)。

3. 在任何供应商要求之前，编写合作伙伴价值主张——一个对“合作伙伴的收益是什么”的单句回答，加上其背后的经济形状。一个计划必须提供（赚钱的明确方式、培训、交易保护、供应商空中掩护）才能要求（专职代表、认证、注册纪律）。将其捕获为合作伙伴假设——1-2 页命名目标合作伙伴类型、他们为什么参与以及预期的经济——在构建任何东西之前与 2-3 位真实潜在合作伙伴进行验证。
4. 在进行任何合作伙伴档案工作之前，选择合作伙伴动作，从以下菜单中选择，按每单位努力返回的价值排序——不是按上限，也不是按最便宜优先。对用户大声说出顺序，然后选择最小可行集，而不是每个动作。轴不一致，所以请阅读所有内容：
   - 效率：`推荐 > 技术 > 服务-SI > 经销商`
   - 努力：`经销商 > 服务-SI > 技术 > 推荐`
   - 价值上限：`经销商 > 服务-SI > 技术 > 推荐`
   - 见效时间：`经销商 > 技术 > 服务-SI > 推荐`
   - 合规成本：`经销商 > 服务-SI > 技术 == 推荐`（平局争论：技术动作和推荐动作都不会创建合同利润承诺或第三方交付责任，并且都可以在一段话中终止）

   每个动作及其权衡：
   - **推荐** - 站立努力接近零：一个佣金规则、一个链接或一个表单、一个跟踪字段。购买您已经知道如何销售的账户中的温暖介绍。低上限，增加不会交付能力。默认第一档，除非以下约束将其删除。
   - **技术** - 四分之一的工程，然后是一个站立维护义务，并且不会支付利润。购买耐久表面：一个集成在推广停止后仍然产生联合账户和保留。轻动作中最慢的首次收入，因此它需要面谈中的复合型任务来证明自己。
   - **服务-SI** - 使能内容、交付质量标准，以及站立合作伙伴经理时间。购买您没有雇佣的交付能力，并解锁在实施上停滞的交易。只有在实施是一个真正的购买障碍时才支付；在不是的情况下，这是为无事购买的协调。
   - **经销商** - 一个站立工作：协议、利润表、订单流、交易注册、冲突政策、直接代表补偿中立性、对转售条款的法律批准。购买覆盖范围——您无法直接触及的细分市场和地理区域——在最高上限和最长时间内。最难逆转：取消它意味着重新书写已签署的协议。

   这顺序养活了：经销商和服务-SI。两者都位于价值上限线上，并且同时位于努力线上，所以比率将它们放在每一轮的最后。一个只遵守效率线的计划将永远是一个推荐计划：直接无法触及的覆盖范围和解除停滞实施的交付能力都将保持未购买。

   当达到命名细分市场或地理区域是计划声明的目标，并且站立人员数量已经资助时，将经销商提升到轻动作之上。当实施是失去或停滞交易中命名的原因时，将服务-SI提升——不是当 SI 关系仅仅是存在时。两者都不是由雄心提升的，并且两者都不会赢得它们构建的比率。

   约束删除行而不是降级它们。被删除的动作将放在规范的动作行上，并带有重新打开它的触发器：
   - 一个无法资助合作伙伴销售成本的 ACV 删除经销商和服务-SI。
   - 一个由于合同或技术原因无法转售的产品删除经销商。
   - 没有可资助的站立人员数量删除两者。

   这个顺序是一个默认值，不是一个法律：它随着上下文和执行者的不同而变化。在向用户展示之前，根据您已经了解的用户重新排序它：
   - 一个已经服务其客户的代理商或 SI 将服务-SI 提升到顶部，因为招募努力已经花费。
   - 一个现有的平台-市场关系会以相同的原因促进技术。
   - 一个由一个人组成的团队将菜单缩小到推荐加上最多一个集成。

   使用构建/销售/服务类型学和影响/交易/保留透镜对边缘候选者进行排序。理想的合作伙伴档案细节稍后出现在选择的动作中，正式的评分档案将在招募量需要时等待。见 [references/decision-sequence-and-frameworks.md](references/decision-sequence-and-frameworks.md)。

5. 在设计任何层级之前，决定是否要层级，以及差异化是为了什么。一个层级只有在其边界处有可衡量的变化时才存在，并且标准和利益差异是作为一对设计的：
   - 没有利益差异的标准是一个无人参与的排行榜。
   - 没有标准的利益差异是穿着标志的偏袒。

   将层级数量、标准和利益设计交给 `mbfinotti/partnerships-skills@partner-tiering`，它拥有所有三个：在这里决定是否要层级以及差异化是为了什么。两个层级是小或新计划的正确直觉，四个通常是虚荣的，但该技能根据合作伙伴基础大小设置数量。不要在这里固定一个数字，它将重新导出，或者已签署的合作伙伴协议将被重新书写。

   在这里也不根据效率对层级数量进行排序，因为在这个页面上第二个顺序将与该技能从基础大小导出的顺序相矛盾。

6. 设置计划范围的经济框架：合作伙伴利润必须来自合作伙伴从您手中拿走的成本（“如果您为您本来会做的工作支付利润，您就没有购买任何东西”），并且总计划成本必须适合毛利。在这里中立化直接代表在合作伙伴交易上的补偿，而不是在以后。

   将每合作伙伴建模交给 `mbfinotti/partnerships-skills@partner-economics`。见 [references/economics-and-benchmarks.md](references/economics-and-benchmarks.md)。

7. 修复治理：一个命名的所有者和汇报线，以及一个交易注册/渠道冲突政策，在第一个销售合作伙伴签署之前而不是在第一个争议之后编写。从业者争论在早期阶段要求 CEO 汇报，因为销售主管下的所有权对成熟需要 2-3 年的功能施加了季度目标。将规则细节交给共同销售和冲突技能（见参考）。

8. 在设计时设置成功时间范围：第一年只根据领先指标进行评判（合作伙伴激活、第一个交易注册、首次交易时间），第二年根据合作伙伴提供的管道，第三年根据实质性收入分成目标。该领域最常见的结构性错误是在直接销售 30-90 天周期上评判渠道；时间范围决策是架构的一部分，现在做出。将测量系统本身交给 `mbfinotti/partnerships-skills@partner-performance`。

9. 分部分段展示架构——对于每个，2-3 个候选方法及其权衡和明确建议——并在转到下一个部分之前与用户验证每个部分。在职业自己的协作格式适用的情况下，建议按照文件排名的顺序提出它们——每小时购买的证据，以合作伙伴假设验证为开端：[references/collaboration-formats.md](references/collaboration-formats.md)。

10. 在每个部分获得明确批准后，发出计划架构规范（下一节），并将其与通过阈值进行核对。迭代直到它通过；如果没有架构通过，建议不启动并记录原因。

11. 如果您的 harness 具有持久内存，请记住已批准架构的关键决策、经济框架和门控答案——稍后的战术运行（层级、使能、绩效）将从它们开始，而不是重新面谈。

## 计划架构规范

将每个从头开始的参与作为此工件交付——用户可以向财务、法律和销售提供此决策记录：

```
计划架构 - <公司>, <日期>
准备情况    : 直接动作证据、ACV 带宽、毛利空间、命名的执行赞助人
合作伙伴价值: 单句合作伙伴价值主张 + 验证记录（2-3 位命名的潜在合作伙伴，每个确认或反驳了什么）
动作      : 推荐中哪个 / 经销商 / 服务-SI / 技术，为什么每个，以及在重新排序此用户后选择的效率顺序；被约束删除的动作，以及重新打开每个的触发器
第一组    : 目标大小（~10），资格栏（能力、容量、覆盖范围、承诺），每个合作伙伴的激活里程碑
层级      : 是否要层级 + 差异化是为了什么；由 partner-tiering 设置的数量，或“无层级 - 当 <条件> 时重新审视
经济      : 每个动作的补偿形状、计划成本框架与毛利、直接代表补偿中立性声明
治理      : 所有者 + 汇报线，交易注册/冲突政策状态（在第一个销售合作伙伴签署之前编写）
时间范围  : 第一年领先指标，第二年管道预期，第三年收入分成目标；审查节奏和谁评判
```

规范的三个规则：

- **每行都有一个原因。**“因为唯一动作是推荐，并且在第三个边界处没有可衡量的变化，所以是两个层级”是可审查的；一个裸露的层级数量是不可审查的。
- **验证记录不是可选的。**一个合作伙伴价值主张从未与真实潜在合作伙伴接触过是一个猜测；规范必须命名谁进行了测试以及发生了什么。
- **规范有一个通过阈值。**经济必须适合毛利，合作伙伴价值主张必须经过 2-3 位真实潜在合作伙伴的验证，并且必须存在一个命名的执行赞助人。迭代动作、层级或经济，直到所有三个都成立——如果没有架构通过，建议不启动。

## 诊断现有计划

当用户带着一个运行计划而不是一个空白页面到来（“我们有 200 个合作伙伴但没有收入”）时，在战术之前诊断结构。通常同时适用几行；该表是一个查找表，因此修复顺序在这里说明，而不是由行顺序暗示：

- 效率：`时间范围重置 > 冲突和注册政策 > 激活超过招募 > 资金机制 > 补偿中立性 > 层级重建`
- 努力：`补偿中立性 > 层级重建 > 激活超过招募 > 冲突和注册政策 > 资金机制 > 时间范围重置`
- 价值：`补偿中立性 > 激活超过招募 > 冲突和注册政策 > 层级重建 > 资金机制 > 时间范围重置`
- 合规成本：`层级重建 == 补偿中立性 > 冲突和注册政策 > 所有其他`（平局争论：每个重新打开一个已签署的文件——在一个案例中是合作伙伴协议，在另一个案例中是代表补偿计划——并且两者在没有第二次修正的情况下都不会撤销）

重置时间范围是因为它只需要一次领导对话，并且可以阻止在可以实施任何其他修复之前杀死计划。补偿中立性是最高价值的修复，但仍然不是第一个：它是一个年中补偿变化，缓慢且政治上昂贵。根据用户重新排序——一个已经补偿中立的计划已经删除该行，并且一个单层级计划删除层级重建。

| 症状                          | 首先需要检查的结构性原因                                                                 |
| ----------------------------- | ---------------------------------------------------------------------------------------- |
| 签署的合作伙伴多，活跃的少   | 招募跟踪而非激活；从未验证合作伙伴价值主张                                             |
| 合作伙伴忽视等级提升         | 外观等级 - 在边界处没有可衡量的变化                                                   |
| 项目资金未被领取             | 市场发展资金与交易注册设计分离，申领存在摩擦                                           |
| 合作伙伴停止注册交易         | 供应商在已注册的交易上竞争（家庭账户）；冲突政策事后制定                             |
| 直接代表阻止合作伙伴交易     | 补偿惩罚合作伙伴参与 - 这是架构决策，而非行为问题                                       |
| 项目在6个月后“失败”         | 视野错误：基于直接销售周期进行评判；重置期望至1年/2年/3年阶梯                         |
| 合作伙伴经理负担过重         | 产品组合远超可持续范围；项目在激活前扩大了招募规模                                     |

包含修复措施和负面案例的完整失败目录：[参考资料/准备与失败模式.md](references/readiness-and-failure-modes.md)。

## B2B 和 B2C

两者相同：

- 在扩大招募前，先对一小批进行深度资格认证。
- 在设定任何数字前，从合作伙伴的角度模拟经济模型。
- 令人信服的经济提议，而非营销，才是招募的关键。

真正不同：

- 特许经营的法律工具和独家区域。
- 第一天文档的深度：特许经营中详尽无遗，B2B SaaS中故意简略。
- 消费者计划的销售点归因与B2B的多月管道归因。
- 唯有面向消费者的经销商才需要的前线思维/可找到性要求。

详细信息和可靠性标志：[参考资料/B2B-B2C对比.md](references/b2b-b2c-contrast.md)。

## 调用示例

- “我们有入站的合作伙伴请求，但没有正式的项目。我们是否甚至准备好接受合作伙伴，如果是，项目应该是什么样子？”
- “为一个12K ACV产品设计推荐计划 - 我们尝试过经销商，但利润计算从未可行。”
- “我们的合作伙伴项目要求没有人能满足，福利也没有人想要。从准备性门槛开始重建结构。”
