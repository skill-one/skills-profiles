# 联盟营销分成审计

在发布前审计一次联盟/合作伙伴佣金分成运行：重新计算数学问题，验证规则，并报告发现结果，附带建议的冻结和更正措施。假设活动已经通过欺诈筛查——这项技能检查分成是否正确，而不是是否合法。

没有命名、联盟原生的对账框架；平台提供锁定和争议机制，而不是方法论。这里的方法公开借鉴了相邻的金融学科：

- **账户对账**（编制者/审查者）。
- **三方匹配**——平台导出与计费/订单系统与CRM，联盟营销的采购订单/收据/发票类似物。
- **收入保障**。
- **职责分离/四人复核**。
- **SOX ICFR / COSO**——当项目位于上市公司内部时。

用简单的语言向用户解释；永远不要展示品牌框架。

## 面试

在审计任何东西之前提问。每条消息一个问题；在可能的情况下提供多项选择题答案。跳过用户已经回答的内容。

- B2B SaaS 定期收入分成，B2C 电商订单级 CPA，或两者都有？
- 生效的佣金结构：比率模型、分层方法（边际或追溯），按合作伙伴类型覆盖，促销/奖金窗口，新客户门槛，子联盟覆盖，遗留旧率？
- 分成节奏，以及本次运行的精确期间边界——日期和时区？
- 哪些数据导出存在，以及内部真相来源是什么：计费系统、订单数据库或CRM已赢得？
- 验证/锁定窗口长度？什么事件将佣金从待处理状态释放到批准状态？
- 本次运行中是否有任何行已经支付，或者所有内容仍然可逆？
- 最低分成门槛，涉及的货币，外汇处理政策？
- 每个收款人的税务表格状态——已收集、缺失、过期？
- 已知的歷史错误类型和过去的合作伙伴争议？
- 谁计算运行，谁释放资金？同一个人还是不同人？
- 重要程度阈值？该程序是否受外部财务控制要求（上市公司 ICFR）约束？
- 必须在什么日期之前提交审计结果，发布日期本身是否可变动？
- 一次性或复合型：仅修复本次运行，还是留下现有控制措施——可重复使用的重新计算脚本，保留政策，更长的验证窗口？
- 努力上限：可用的审查小时数，是否可以执行代码到导出，财务是否可以共同签署，以及本次运行可以花费多少合作伙伴关系资本？

缺少期间边界、真相来源或佣金结构会阻止审计——在重新计算任何东西之前坚持要求。

最后三个答案会重新排序以下每个菜单：

- 硬性发布日期会促进廉价门槛并放弃全人群重新计算。
- 复合型指令会促进全人群重新计算和修复运行等级。
- 没有代码访问会完全删除全人群重新计算。
- 没有财务共同签署人会删除直接从本次运行中恢复。

## 审计顺序

按顺序运行检查；每个门槛都假设前一个已经通过。底层生命周期在所有地方都是相同的五门机：拉取/导出 → 与真相来源对账 → 验证每行的比率/分层 → 去重 → 锁定 → 支付。

**当发布日期无法适应所有十二个。** 编号是依赖顺序，不是优先顺序。为了在短时间内有效利用预算，按每小时捕获的错误数量对门槛进行排序：

- 效率：去重（6）> 对账和可比性（3-4）> 生命周期窗口（8）> 比率/分层重新计算（7）> 货币、税务、阈值（9）
- 价值：对账和可比性（3-4）> 去重（6）> 比率/分层重新计算（7）> 生命周期窗口（8）> 货币、税务、阈值（9）
- 努力程度：比率/分层重新计算（7）——用代码一小时，用手工一周 > 对账（3-4）——在干净的导出上用一小时，在混乱的导出上用一周 > 生命周期窗口（8）== 货币、税务、阈值（9）——每小时一小时，日期计算和清单 > 去重（6）——在关键集上用代码几乎为零
- 合规成本：货币、税务、阈值（9）——没有有效税务表格的收款人是一个申报问题，而不仅仅是金钱问题 > 四人复核（12）——签署是外部控制测试要求证据 > 其他每个门槛 == 无，因为在这些地方出错会损失金钱，而不是申报

四人复核（12）永远不会是你要删除的门槛：它需要一次日程安排和第二次读者，而它的缺失是导致所有负面示例错误发货的原因。

比率/分层重新计算是这个顺序中受限制的——算术门槛中价值最高，手工最昂贵。当以下情况发生时将其提升到第一位：

- 合作伙伴对分层提出争议
- 运行跨越了追溯性断点
- 结构在期间内发生变化

顺序是一个默认值，不是法律，并且会随着执行者而变化：一个导出全机器可读日志的网络会崩溃（6）和（7）到接近零，并将两者都向上移动；没有计费系统访问会使（3-4）无法实现，并将（7）作为整个审计。

1. **冻结运行范围。** 记录运行 ID、期间开始/结束、时区、日期基础（交易 vs 验证 vs 修正日期）、货币、重要程度阈值和每个数据源。范围不明确 → 停止并解决；每个后续检查都依赖于它。
2. **在声明的日期基础上拉取导出。** 平台/网络转换导出加上同一期间内部部真相来源提取。如果你可以分析上传的电子表格或 CSV，加载两者；否则请用户提供行数、总计和要读取的特定行。
3. **可比性门槛。** 在比较或汇总任何两个数字来源之前，确认它们共享相同的事件定义、日期基础、时间窗口、时区、货币、计数方法和去重身份。任何不匹配 → 首先规范化，或者报告数字及其定义并拒绝计算总计。详情在 [references/reconciliation-and-dedup.md](references/reconciliation-and-dedup.md)。
4. **将总计与真相来源对账。** 比较行数和金额值：平台导出与计费/订单/CRM。通过 = 总计在重要程度范围内匹配。失败 = 必须逐行解释的差距，在批准任何东西之前 - 永远不要“差不多”。
5. **处理异常队列。** 在一个系统中但不在另一个系统中的记录，仅基于稳定 ID 匹配。
   - 在平台中，不在计费中：可能的超额信贷，冻结并调查。
   - 在计费中，不在平台中：未跟踪的销售，预期合作伙伴争议并明确决定信贷政策。
6. **去重。** 每个转换一个确定性键（订单 ID / 交易 ID / 订阅 ID）。隔离空或格式错误的键。将双重跟踪（平台像素 + 内部跟踪）合并到一个规范来源。检查没有键出现在先前的运行中 - 期间跨越会重复支付。
7. **验证每行的比率和分层。** 使用原始输入在原始交易日期生效的条款重新计算预期佣金：分层方法和边界操作符、合作伙伴类型覆盖、促销窗口与开始/结束日期时间、新客户门槛、子联盟覆盖、遗留旧率。如果你可以执行代码，重新计算每一行；否则手工重新计算样本行。数学在 [references/rate-and-tier-verification.md](references/rate-and-tier-verification.md)。
8. **验证每行的生命周期状态。** 每一行都必须清除其验证/锁定窗口或被明确释放；窗口内退款/流失的逆转必须已经应用；锁定后到达的退款必须作为下一期间的负调整出现，而不是消失。规则在 [references/lifecycle-and-clawback.md](references/lifecycle-and-clawback.md)。
9. **验证货币、舍入、税务和阈值。** FX 击中日期与政策匹配，在最后舍入到 2 位小数，低于阈值的余额向前传递，运行中每个收款人都有税务表格。详情在 [references/currency-tax-and-payment.md](references/currency-tax-and-payment.md)。
10. **选择覆盖方法**，按每小时发现的错误数量排序：
    - 效率：全人群重新计算 > 基于风险的分层 > 顶尖收入抽查
    - 价值：全人群重新计算 > 基于风险的分层 > 顶尖收入抽查
    - 努力程度：基于风险的分层 - 一小时设计，然后手工处理量一周 > 顶尖收入抽查 - 一小时 > 全人群重新计算 - 一小时编写脚本，之后每次运行接近零
    - 努力程度在这里反转价值：最彻底的方法在脚本存在后也是最便宜的，并且是唯一复合型的方法。它只有在你可以对完整的机器可读导出执行代码时才会领先；没有它则完全不在菜单上，基于风险的分层会领先。
    - 基于风险的分层 = 100% 的高价值行、高逆转合作伙伴和顶尖收入者（一小部分合作伙伴推动大部分佣金美元），加上根据重要程度调整的随机样本。顶尖收入抽查可以捕获集中错误，并且对长尾系统性是盲目的——仅在硬性截止日期下进行。
    - 仅随机抽样不是一个等级：它花费与基于风险相同的工时，但找到的金额更少。用于剩余部分，永远不要用于整个运行。记录每次选择的方法和理由。
11. **编制报告。** 分类每行清除/冻结/更正；每个差异都成为一个发现，附带严重程度、风险价值和建议行动（见输出，然后是补救措施）。将任何看起来不合法的模式（自我推荐、协调爆发）升级到欺诈审查——在这里永远不要做出裁决。
12. **四人复核签署。** 计算运行的人不能是释放资金的人；审计报告是审查者的证据。在发布前没有阻止性发现——否则冻结受影响的行或整个运行。

如果你的框架有持久内存，记住运行的参数和接受的例外（期间规则、真相来源、重要程度、已知单边记录），以便下一次运行从它们开始；否则将它们写入报告标题以供重复使用。

## 输出：审计报告

以这个工件交付每个审计：

```

范围     : <N> 行，建议总计 <金额> <货币>；来源：<平台导出> vs <真相来源>
检查    : 每个编号的检查上 -> 通过 / 失败 / 不适用，每行一行
发现    : F-<n> | 严重程度：阻止性 / 重要 / 轻微 / 信息性 | 风险金额 | 受影响的行 |
          行动：在发布前更正 / 冻结行 / 对未来佣金进行抵消 / 吸收并
          记录 / 修复向前 / 直接恢复（排名如下）+ 如有必要，升级到欺诈审查
```

## 补救措施：每个发现的行动

发现错误只是便宜的一半。按每单位努力和合作伙伴关系资本花费的价值恢复排名响应——永远不要按名义上处于风险中的金额排名。

1. **在发布前更正。** 重新计算该行，修复运行，支付正确的金额。完全恢复，没有关系成本——合作伙伴从未看到错误的数字。每当行仍然未支付时，默认使用。
2. **对冲未来佣金。** 将更正记录为向前期间的负调整，抵消合作伙伴的下一笔收入。一旦行支付，默认使用。完全恢复，但仅当合作伙伴继续赚取时。
3. **吸收并记录。** 删除该行并记录其价值。诚实的运行低于重要程度，并且是合作伙伴流失且余额为负时唯一剩下的选项。
4. **修复向前。** 延长验证窗口，增加保留/冻结，安装共享的唯一性键，或重新谈判该合作伙伴的费率卡，当差异是结构性定价错误而不是错误时。从本次运行中恢复什么；退役整个错误类别。
5. **直接恢复。** 向合作伙伴就超额支付开具发票。恢复不确定，并且是唯一可以结束关系的等级。

- 效率：在发布前更正 > 对冲 > 吸收并记录 > 修复向前 > 直接恢复
- 恢复价值：在发布前更正 == 对冲 > 直接恢复 > 吸收并记录 == 修复向前
- 努力程度：直接恢复 - 一周到四分之一的需求数，财务和法律协调 > 修复向前 - 一周到建立，然后是常规工作 > 对冲 - 一小时，在平台携带负余额的地方接近零 > 在发布前更正 == 吸收 - 接近零，每个编辑一次
- 关系资本：直接恢复 > 修复向前 > 对冲 > 在发布前更正 == 吸收 - 没有花费，合作伙伴永远不会被要求做任何事
- 合规成本：直接恢复 - 合同解释和法律签署，一旦发送不可逆转 > 对冲 - 必须由发布的条款授权，并且几个平台明确表示已支付的佣金永远不会被收回 > 修复向前 - 通知合作伙伴的条款修正 > 在发布前更正 == 吸收 - 无

解释平局的理由：

- 在发布前更正和对冲：两者都恢复 100% 的行，不同之处在于时间。
- 吸收和修复向前：两者都从本次运行中恢复什么，不同之处在于它们以后购买什么。
- 在发布前更正和吸收：每个都要求合作伙伴不做任何事。

- 删除，不要降级。如果本次运行中没有支付任何内容，运行 2、3 和 5 不是替代方案 - 删除并更正。如果条款或平台禁止收回已支付的佣金，删除对冲和直接恢复；吸收和修复向前是整个菜单。
- 修复向前是这个顺序中受限制的：高价值，本次运行中零恢复，因此它在每一轮中都输掉。一旦同一发现类别在连续两次运行中出现，或者当锁定后退款成为常规而不是例外时，将其提升到顶部。
- 升级到欺诈审查不是一个等级。它回答一个不同的问题，并与所选等级并行运行。
- 顺序是一个默认值，不是法律，并且会随着执行者而变化。根据你已经知道的内容重新排序：
  - 原生携带负余额的平台会促进对冲。
  - 本周期没有财务共同签署人将直接恢复从本次运行中删除。
  - 一个足够小以完整重新运行的排程将使在发布前更正重新回到你原本必须对冲的行上。

## 通过阈值和 KPI

运行只有在三个都满足时才通过；迭代更正并重新运行检查，直到它们满足，或者建议冻结运行：

- 每一行要么与真相来源对账，要么在例外列表中——没有沉默的差距。
- 重新计算和提议总计之间的未解释净差异处于或低于重要程度阈值。
- 在发布时没有阻止性发现。

按运行跟踪运行：

- **支付准确率**：重新计算值与提议值匹配的行份额。
- **例外价值**作为总运行价值的份额。
- **逆转/追回率**针对规划范围——大致 2-8% 的 CPA，收入分成低于 3%（基准范围，不是审计数据）。高于范围 → 延长验证窗口或收紧资格。
- **支付后更正率**——在资金移动后发现的更正。
- **争议率和争议解决时间**。

## B2B SaaS 与 B2C 电商

学科是相同的：待处理 → 已批准 → 已锁定 → 已支付的生命周期，可比性门槛，去重键，异常队列，抽样，以及制作者-检查者对两者都采用相同的方式。使用相同的顺序审计两者。只有三件事真正存在差异：

- **撤销触发器。** B2C：退货、拒付或退货窗口内的取消。B2B SaaS：试用到付费失败、退款、降级或中期流失。
- **重复。** B2C CPA 每个订单支付一次。B2B 收入分成在每个计费事件上重复 - 比例、升级/降级、座位扩展，以及 12 个月上限与终身规则使每个周期成为一条新的验证线。
- **事实来源集成。** B2B SaaS 平台通常直接读取计费系统，因此平台数据就是计费数据 - 检查 4 折叠成一个抽查。B2C 网络通过像素独立跟踪，因此完整的对账仍然是强制性的。

不要制造其他差异；将两者视为独立的学科会重复工作而不会捕获更多错误。

## 故障模式

| 故障                                       | 原因                                                                                                              | 修复                                                                                                |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 等级边界错误一位                      | 边际计算为追溯（反之亦然）；在断点处将 `>=` 编码为 `>`；追溯悬崖放大了错误 | 在每条边界线上重新计算两者；匹配书写结构；修复运算符      |
| 跨来源的重复订单 ID            | 平台像素和内部跟踪器都记录相同的转化                                                         | 每个转化一个规范来源；共享 idempotency 键；每个键支付一次 |
| 格式错误或空的去重键                 | 空的交易 ID 将许多转化折叠成一个记录 - 或者没有                                                   | 隔离空/格式错误的键；在总计之前手动解决                      |
| 在两个连续时期内计算的转化             | 断点处的重新导出重叠或时期跨越                                                                          | 半开式时期窗口；比较本次运行的关键字与先前运行           |
| 导出中的日期基础错误                | 导出提供交易日期、验证日期或修订日期；错误的选择使行跨运行移动                          | 在运行范围内声明日期基础；在声明的基于上重新拉取           |
| 断点处的时间区域边界错误             | 平台、计费系统和程序办公室各自保持不同的时钟                                                    | 在范围内修复一个时间区域；在应用断点之前规范化所有时间戳     |
| 忽略撤销窗口                       | 在验证窗口到期之前批准的行，因此退款永远不会撤销                                               | 持有仍在其窗口内的每条行；将窗口调整为撤销曲线             |
| 退款在记录锁定后到达               | 已锁定/已支付的行无法在平台上反转                                                                            | 预订下个时期的负调整；对未来的收益结转负余额             |
| 对当前条款重新计算              | 自销售以来利率已更改；一些平台在今天的条款下重新评估修改后的行                                    | 对原始交易日期生效的合同条款重新计算                     |
| 货币舍入漂移                       | 每步舍入在数百条小行中复合                                                                      | 在最后舍入到 2 位小数，而不是每步；超过重要性 → 审计舍入策略 |
| 低于阈值的余额被静默删除       | 最小支付阈值作为排除项而不是结转应用                                                              | 验证低于阈值的余额滚入下一个运行；它们绝不能消失          |
| 在税表文件之前释放支付             | 付款人入职被跳过或表格过期未被注意到                                                                         | 阻止任何缺少/过期的表格的付款人释放；每次运行重新检查     |
