# 预测诊断

调查一个预测失误或无人信任的预测，并凭借证据找出根本原因。预测调用会问“数字是多少？”，而诊断会问“这个数字曾经真实过吗？”

从业者普遍认为，大多数失误是检查失败，而非市场失败：一个承诺的交易是虚构的证据通常在失误发生前就存在于记录中。

范围边界，事先声明：这项技能消耗现有的任何预测方法——类别集、汇总规则、承诺标准、覆盖目标都是输入，而非交付物。重新设计或重新设计该方法不在范围内。当调查表明该方法本身未定义或模糊不清（“承诺对不同的代表意味着不同的东西”）时，将其作为发现报告并停止在边界处。

每个确认的根本原因都落在以下三个类别中的其中一个，因为每个类别都有不同的所有者和不同的修复方案：

- **数据**：记录错误，有人知道更好的情况。
- **行为**：记录忠实地反映了有偏见的个人调用。
- **需求**：诚实、有证据的管道仍然不足。

最常见的诊断错误是对数据问题发出行为裁决。

## 访谈

在分析之前提问：

- 每条消息一个问题；尽可能提供多项选择。
- 跳过已回答的内容。
- 在任何其他问题之前，先问下面三个问题。它们的修复方案在努力程度和需要多长时间才能反映在预测中的程度上相差两个数量级，答案决定了整个交付物的排序顺序。

问题：

- 必须在何时使数字更可靠——本期的调用、下期，还是下个规划周期？一个在本期结束后才落地的修复方案不会帮助这个预测：一个中期截止日期会删除所有比一个周期更慢的修复方案，并让小时级CRM管理员修复方案承担全部工作量。
- 一次性纠正这个失误，还是建立持续准确性计划？一次性纠正促进重建、僵尸清理和日期清理；持续计划促进证据门、校准评分卡和阈值推导。
- 努力上限：多少分析师小时，CRM管理员是否能在本周内完成现场或验证更改，以及谁有权重新打开补偿计划或更改审查周期。没有管理员会将每个小时级修复方案变成周级请求；没有补偿权限会完全删除补偿修复方案。
- 什么触发了这个问题——一个特定的失误期、慢性不准确，还是怀疑（沙袋、夸大的管道）？哪个时期？
- 错误的方向是什么——预测过高（错过了调用）、预测过低（大幅超出）、或双向波动？
- 数字在哪个级别出错——个人代表、经理汇总，还是公司范围？在汇总中，人类可以在哪里覆盖总和？
- 当前的流程是什么样子——使用的预测类别、提交周期、谁最终调用数字？（如实记录；不重新设计。）
- 历史记录是什么——机会快照、现场历史（阶段、关闭日期、类别、金额变更）、活动日志？有多远？
- 运动是什么——基于B2B交易的、基于B2C/高容量/自助服务的模型，还是混合的？每个周期大约有多少笔交易？
- 团队如何获得报酬——配额悬崖、加速器、季度末折扣授权、任何基于预测数字本身的奖励或惩罚？
- 期间是否有混杂因素——CRM迁移、阶段重新定义、区域变更、批量卫生清理？

## 工作流程

1. 运行访谈；在触摸交易数据之前，确定错误的时期、方向和级别。
2. 在解释失误之前量化失误：按时期、按汇总级别、按预测类别的预测与实际值。计算有符号误差（偏差）和绝对误差——对称平均值会隐藏相互抵消的误差，因为相同的失误根据所选的分母读起来非常不同，所以首先修复一个误差定义。这两个数字总是一起发送，作为正确性规则，而不是用于排名和选择菜单——参见[references/evidence-and-metrics.md](references/evidence-and-metrics.md)。
3. 梳理证据基础：期初快照、现场历史、活动日志。如果不存在快照或现场历史，现在开始捕获它们，从当前状态的指纹加上访谈进行诊断，并将每个结论标记为低置信度——没有历史记录，行为裁决很难辩护。
4. 从期初快照重建失误期。按结果（称为赢得、滑落、失去、移除、仍然开放）对每个在预测类别中的交易进行分类，并按实际赢得的来源（在预测中吗？哪个类别？何时创建？）对每个实际赢得的交易进行分类。如果你的harness可以执行代码，从两个文件导出（期初预测、期末实际值）来编写这个；否则，请用户提供两个列表并手动核对。
5. 在[references/root-cause-fingerprints.md](references/root-cause-fingerprints.md)中运行根本原因指纹。每项疑似原因需要两个独立的信号，至少一个来自记录历史。
6. 访谈被标记的交易的代表和经理，以将数据与行为分开。区分性问题：“在CRM说之前，你知道这笔交易是死（或活）的吗？”是意味着记录滞后于现实——数据问题。不是意味着行为或需求。
7. 最后隔离需求：用后见之明修正的数据重建期初预测——移除僵尸、诚实类别、有证据的关闭日期。无论什么差距在修正后仍然存在，都是真正的需求或覆盖不足，任何预测流程修复都无法恢复；如实说明。
8. 归因差距：每个失误的美元都对应一个命名的交易（或高容量运动中的命名模型假设），每个交易都有一个主要根本原因和一个类别。相互抵消的误差（沙袋赢得掩盖夸大的损失）单独归因，从不沉默地抵消。
9. 检查Measurement下方的通过阈值；调整指纹并重新运行，直到每个阈值都成立。
10. 使用Fix leverage下方对确认的原因进行交付排序：归因的美元优先，然后除以修复努力，并显示调整而不是两个数量级无声地合并。每个原因匹配其类别的一个修复，加上将证明每个修复在一个周期内起作用的指标。
11. 分部分交付以供用户批准；报告形状和工作示例在[references/worked-diagnosis-example.md](references/worked-diagnosis-example.md)中。
12. 如果你的harness具有持久内存，记住确认的原因、从这个团队的历史中推导出的阈值、这个团队的费力层级以及代表级别的校准基线——下一个周期的重新运行将从它们开始。

## 范围内的根本原因

紧凑地图：完整的检测指纹、第二信号和修复方案位于[references/root-cause-fingerprints.md](references/root-cause-fingerprints.md)，按此顺序。

价值轴无法在此处预先排名，这项技能也不假装：哪个原因是值得最多美元的，是归因表的输出，并且随着每次参与而不同。什么是稳定的，是修复方案——它发送的成本和预测反映它需要多长时间——因此注册按此排序，然后诊断重新对它进行排名（参见Fix leverage）。

- 修复努力（最优先）：`comp-driven bias > rep sandbagging > stage inflation == missing evidence > late-created deals > manager override == wrong category > stale dates == zombies`
- 起效时间（最慢）：`comp-driven bias > rep sandbagging > manager override > late-created deals > stage inflation == missing evidence > stale dates == wrong category > zombies`
- 合规成本（最优先）：只有两个携带任何——`comp-plan change > a behavior verdict naming an individual rep`；其他每个修复方案都是一个CRM设置或一个审查习惯，没有外部签字，所以轴不值得一个完整的排序。
- 相同美元的效率（最佳）：`zombies > stale dates == wrong category > stage inflation == missing evidence > late-created deals > manager override > rep sandbagging > comp-driven bias`

平局，每个平局都是挣来的，而不是回避的：

- **Stage inflation == missing evidence**：两个修复方案都是字面意义上的一个干预，一个买方证据门在承诺输入时，同一个所有者，同一个星期，同一个站立检查。
- **Manager override == wrong category**：两者都是一小时CRM管理员（一个原因字段、类别字段历史）加上与被更改约束判断的人进行一次谈判。
- **Stale dates == zombies**：两者都是一个管理员更改加上一个定期清理，没有人会约束判断，并且在它们发送当天可以撤销。
- **Stale dates == wrong category**，仅在起效时间上：两者都在下一个编辑中咬住，所以无论哪个完整周期，都是如此。

| 根本原因                       | 通常类别                   | 签名                                                                                                                               | 修复努力                                                                                                                                                             |
| -------------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Zombie / duplicate opportunities | 数据                          | 长期死亡的交易仍然开放并计入；相同的购买意愿被计算两次                                                            | 一小时用原因代码清理，然后进行定期卫生清理；在同一个周期中，覆盖是诚实的                                                                                                    |
| Stale / mass-pushed close dates  | 数据                          | 推送计数堆积；日期编辑集中在接近期末的某一天                                                                                         | 一小时的行政工作，要求原因代码的日期移动，然后是一个定期工作；咬下一个推送，所以一个周期                                                                                       |

| Missing / unverifiable evidence  | 数据或行为                  | 必填字段填充了占位符；没有人可以说买方最后一次做了什么                                                        | 同一周，同一个门，同一个所有者作为阶段通货膨胀——发送一个就发送了另一个                                                                                                   |
| Late-created deals               | 数据                          | 在几天内创建和关闭的交易，或直接在后期阶段创建的交易——管道可见性是事后账簿工作                                             | 一周设置记录规则，然后是代表习惯更改；覆盖数学在一个周期或两个周期后不可信                                                                                               |
| Manager roll-up override         | 行为                      | 经理数字与代表总和在一致的方向上分歧，没有任何记录的原因                                                            | 一小时捕获原因，但一个季度的滞后覆盖在个人经理分数有意义之前，经理必须接受被评分                                                                                             |
| Rep sandbagging                  | 行为                      | 代表大幅超出承诺，反复赢得来自预测之外                                                                                               | 一周建立开放校准评分卡，至少两个周期的历史才能完全命名该模式；任何触摸激励都属于下一行                                                                                         |
| Comp-driven bias                 | 行为（其他根本原因的根源） | 滑落集中在配额悬崖之后；可预测的季度末折扣教会买方等待                                                              | 最多一个季度——计划修正在下一个计划周期落地，需要财务/人力资源/法律签字，一旦发出几乎无法撤销                                                                                |

效率顺序使comp-driven bias受挫，这是导致其他原因的原因：在大多数诊断中，它是最高的影响轴，在每一个比率中都是最低的。一个仅按比率阅读的注册建议每个周期都进行相同的CRM卫生，而激励产生行为的东西保持不变，行为原因会重新生长。

在以下情况下，将comp-driven bias提升到一切之上：

- 指纹显示滑落集中在配额悬崖之后。
- 同一个代表的偏差随着他们的实现位置而翻转。
- 上一周期数据修复方案已发送，行为类别没有改善。

到那时，廉价的修复方案没有剩余价值，交付物会这样说，而不是重新列出它们。

与邻居的边界：这项技能检测到处于没有证据的阶段中的交易，但它不会重新设计阶段集（当定义本身是问题时，参见`mbfinotti/revops-skills@pipeline-stage-definition-audit`）。它是特定失误的根本原因调查，而不是经常性的陈旧交易/缺失字段清理（一旦原因固定，请参阅`mbfinotti/revops-skills@sales-pipeline-hygiene`进行预防）。

## 修复杠杆

上面的注册是平局裁决，而不是答案。一旦归因表存在，分三遍对确认的原因进行交付排序，并将所有三个都放在交付物中：

1. **影响顺序**——按归因差距美元排序的原因，直接来自归因表。这是失误的算术，它永远不会被调整掉；它是使每个问题可审计的东西。
2. **杠杆顺序**——相同的原因除以注册中的修复努力层级。永远不要除以货币金额：分母是分析师小时、管理员或工程工作、跨团队谈判，以及修复方案到达调用前的预测周期数。
3. **调整，显示**——每个在两个顺序之间移动的原因，用一条线命名移动它的努力。只显示杠杆顺序看起来像是影响算术被无声地否定了，第一个行政问题是为什么最大的数字不是第一。

按杠杆顺序交付，并在旁边打印影响顺序。以最佳比率开头，这通常是成本最低的修复——一个大型归因原因与相同的小时级修复方案排名更高，并且排名高于所有周级。一个工作调整示例在[references/worked-diagnosis-example.md](references/worked-diagnosis-example.md)中。

## 交付前重新排名

这里的每个排序都是一个默认值，而不是法律。它会随着团队和执行者的变化而变化，所以根据访谈和重建揭示的内容重新排名：

- 当前周期内截止日期 - 每周和季度修正项从本周期计划中删除，并说明具体是哪些，而不是在底部列出，以免它们重新成为范围。存活的规则是 `zombies > 过期日期 > 错误类别`，可交付成果明确说明导致行为的原因未受影响。
- 手头有一位有权本周发布验证规则的CRM管理员 - 小时级修正项保持一小时和领先。如果没有，它们会变成其他人的队列中的一周级请求，并失去相对于证据门的比率优势，而证据门至少在本周内发货。
- 不会重新开放补偿计划的销售负责人 - 从计划中删除补偿修正项，并命名由于它而会重新生长的具体行为原因。不要将其作为降级选项停放在底部。
- 没有快照或字段历史记录 - 管理员覆盖和沙袋操作原因在本轮中完全无法证明。从修正计划中删除它们，现在开始捕获历史记录，并安排它们重新运行。
- 季度中，预测周期已经运行 - 现在发货的修正项会改变下一次通话，而不是这次。说明每个修正项针对的是两个周期中的哪一个，并停止提供那些既不触及这两个周期的修正项。
- 团队已经拥有的任何默认订单假定放弃的内容 - 一个可工作的证据门、一个计分的覆盖日志、一个卫生自动化 - 将该原因从登记册中删除，而不是重新推荐。

## 数据与行为与需求

- **数据**：有人知道真相；记录没有。用卫生自动化和字段所有权规则（`mbfinotti/revops-skills@crm-data-governance`）修复，而不是用代表辅导。
- **行为**：记录忠实地反映了一种有偏见的判断 - 乐观、自我保护或对激励措施的理性反应。用证据标准修复类别入口、激励变更和审查纪律。仪表板永远不会修复行为。
- **需求**：有证据的管道仍然不足 - 覆盖率确实很薄或胜率确实发生了变化。修复属于管道生成和市场策略，而不是预测过程。覆盖率规则（目标 ≈ 胜率的倒数，因此流行的“3x”）是一种广泛重复的启发式算法，没有可追溯的原始研究 - 从团队自己的转化历史中推导出真实目标。

裁决纪律：一个行为裁决是一种指控。只有在满足双信号证据规则并且代表面试完成后才能做出，并将准确性的对话与绩效/补偿对话分开 - 一个输入惩罚的诊断会教会代表沙袋操作，下一个失误将成为诊断自己的过错。

## B2B与B2C / 高容量 / 自服务

- **B2B基于交易**：上述工作流程字面适用 - 按交易重建交易级指纹。
- **B2C / 高容量 / 自服务**：预测通常是一个模型（运行率、队列转化、漏斗数学）带有人工覆盖。将交易级指纹应用于任何存在的人工层（一个内部销售承诺列表、手动调整）。将其余部分转换为模型层：
  - 过期的转化假设是过期的关闭日期。
  - 过度包容的漏斗定义是阶段膨胀。
  - 持续保守的手动覆盖是沙袋操作。

  精确跟踪覆盖层与模型层准确性，就像管理员覆盖与汇总准确性一样。

- **两者相同**：失误分解方法、三类裁决系统、测量阈值和统计纪律都不会改变。

## 失效模式

| 陷阱                                            | 为什么它是错误的                                                                                               | 修复                                                                                                                                                               |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 从一个强劲季度诊断沙袋操作                      | 一个季度是噪音；沙袋操作是同一人重复的模式                                       | 要求跨2+周期的模式与代表的自己的历史对比                                                                                               |
| 在数据问题上的行为裁决                          | 模糊的类别定义使诚实的代表看起来不诚实                                                | 先运行区分性面试问题；检查代表之间定义的一致性                                                                         |
| 用周期末数据评判周期初通话                      | 后见之明偏见 - 通话必须在当时可知的内容基础上评判                                            | 从周期初快照重建，永远不要从今天的记录中重建                                                                                             |
| 锚定最大的滑落交易                             | 一个生动的交易很少能解释差距；长尾通常解释                                            | 在得出任何结论之前分解所有差距美元                                                                                                              |
| 对称准确性指标作为目标                         | 过度和不足预测有不同的原因和成本，并且它们会相互抵消                                    | 总是分别报告有符号偏差和绝对误差，按级别。不是菜单来排名并从中选择一个 - 两个数字都是另一个可读的必要条件 |
| 仅根据归因美元排名修复                         | 补偿计划重新设计优先于本周期本应落地的字段变更，并且没有东西及时发货                      | 将美元除以修复工作层，并显示调整（修复杠杆），然后根据面试答案重新排名                                                    |
| 删除僵尸并宣布胜利                            | 接受它们的证据标准未受影响；它们会重新生长                                            | 将每次清理与入口标准修复配对，并将持续预防交给卫生审计                                                                |
| 在补偿中惩罚预测错误                          | 代表会通过沙袋操作回应；错误会翻转而不是缩小                                            | 公开测量准确性，并将其与绩效审查分开                                                                                                     |
| 相信流通的基准统计数据                       | 大多数引用的预测准确性数字没有可追溯的原始研究                                         | 从团队自己的历史中推导出每个阈值；看到证据参考                                                                                    |

## 测量和通过阈值

诊断必须在发货前满足以下所有阈值；迭代直到满足：

- **归因覆盖率**：至少90%的归因于命名交易（或命名模型假设）的差距美元，每个都有恰好一个主要根本原因和一个类别；残差，最多10%，明确标记为未解释 - 永远不要无声地吸收。
- **证据规则**：每个确认的原因至少基于两个独立的信号，至少有一个来自记录的历史（快照、字段历史记录、活动日志）。面试证词永远不会确认一个原因。
- **回测**：相同的指纹规则，在较早的已关闭周期上运行，标记至少80%在该周期实际滑落或从承诺中失去的交易。低于80%，规则是符合故事而不是数据 - 修订并重新运行。
- **可操作性**：每个发货的修复项都命名其原因类别、所有者、工作层级，以及将在一个周期内显示它是否有效的单个指标。修复列表按杠杆顺序发货，并在其旁边打印影响顺序，并解释它们之间的每个移动；只携带两个顺序之一的列表未通过此阈值。

修复发货后，继续评分每个周期：每个级别的有符号偏差和绝对误差，代表相对于他们自己的基线校准。命名指标上的改进 - 不是更安静的预测通话 - 是关闭调查的内容。

## 可选集成说明

除非用户命名其中一个平台，否则跳过本节。

**Salesforce**：

- 预测类别（承诺 / 最佳情况 / 管道 / 遗漏）与阶段不同，并独立可编辑；诊断这两个字段。
- 字段历史记录跟踪是按字段可选的，并且不是回顾性的。立即在阶段、关闭日期、金额和预测类别上启用它，即使本周期必须在没有它的情况下诊断。
- 管道检查功能在支持版本上显示周与周的交易变化。

**HubSpot**：

- 交易阶段概率是可编辑的默认值，而不是测量的转化。在信任任何加权数字之前，用团队自己的历史替换它们。
- 手动预测提交被记录，并且可以与计算出的汇总比较。
