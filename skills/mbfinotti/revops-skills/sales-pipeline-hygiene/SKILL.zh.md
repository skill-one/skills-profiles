# 流程卫生

审计当前活跃流程中存在的交易 - 过期交易、截止日期异常推送、缺失预测关键字段 - 并将发现结果转化为异常列表，每个被标记的交易对应一个处置决策、一个整改和沟通计划，以及一个可衡量的通过阈值。所有权分为三部分，不是共享（ORM）：

- RevOps 拥有定义、快照、自动化和预发布数据包。
- 一线经理拥有每笔交易的处置和指导对话。
- 代表拥有更新和证据。

这种划分消除了争论 - 经理持有特定记录，这些记录触发了特定规则，而不是一般性投诉。反向划分会导致会议准时进行但无任何改变。

审计的承重定义选择首先：**有意义的活动是指阶段、截止日期或金额的变化 - 不是记录的通话或邮件**（ORM）。记录的接触在 CRM 意义上是活动，但它们不表示交易有进展，因此基于它们的规则可以在没有进展的情况下满足 - 这正是过期流程在多次审查后仍然存在的原因。这是一个现场从业者争议（许多工具以最后活动日期为关键）；默认采用字段变更定义，并将最后活动作为第二个独立触发器 - 两者结合，不可互换使用。

## 范围边界

在交付物中说明这些内容，以防止审计偏离：

- 这是对今天流程中交易的定期审计。设计防止过期的定期提醒/提示系统是另一项工作：审计可以建议自动化周期性检查并描述其交接内容，但不得设计提醒时间、渠道或通知疲劳政策。
- 它不审计或重写阶段定义或退出标准 - 这是 `mbfinotti/revops-skills@pipeline-stage-definition-audit`。卫生检查将现有的阶段集视为既定，并检查其内部交易。
- 它不诊断整体预测可靠性 - 这是 `mbfinotti/revops-skills@sales-forecast-diagnostic`。卫生提供干净的数据；它不修复预测方法。
- 它不设置组织范围的字段所有权或事实来源政策 - 这是 `mbfinotti/revops-skills@crm-data-governance`。卫生检查现有字段的完整性。
- 它不追踪漏斗收入流失 - 这是 `mbfinotti/revops-skills@revenue-leakage`。

## 面谈

审计前进行面谈。每个消息一个问题；尽可能使用多项选择；跳过已回答的内容。

- 你能从系统记录中导出或查询什么：有阶段的开放交易、金额、截止日期、所有者、最后活动日期、创建日期、下一步？阶段变更历史？截止日期变更历史？快照？
- 哪些运动和细分市场提供此流程：中小企业/高速度、中市场、企业、B2C/交易性、PLG 销售辅助、混合？每个细分市场的典型周期长度和交易规模？
- 哪些定期仪式已经存在 - 每周预测电话会议、流程审查、QBR、交易台？审计依赖于这些；它不能增加会议。
- 预测和流程决策实际读取哪些字段？（这些字段，而不是所有字段，是完整性检查的依据。）
- 是否有“过期”的书面定义或任何卫生规则？它是否被执行，以及由谁执行？
- 必须在什么日期之前提交结果 - QBR、预测电话会议、董事会编号？周内的日期会促进当天发货的整改措施（验证规则、提示），而推迟需要集成的任何内容。
- 这是一次性清理（预 QBR、预预测、新领导者）还是定期节奏的开始？定期指令使自动捕获值得其成本；一次性运行则留下未建设的系统，并在下个季度重复相同的手动检查。
- 努力上限：每笔交易代表将吸收多少额外摩擦，有多少管理员配置时间，以及每周有多少经理审查时间？已经达到摩擦极限的团队会排除完整性差距所说的任何提示，而薄弱的审查预算会将主要/对话划分推向主要（见 `[references/disposition-and-communication.md](references/disposition-and-communication.md)`）。
- 谁是与代表一起处理异常列表的经理，以及谁拥有关闭处置权？
- 任何大规模清理的历史，以及代表如何反应？是否有已知的仅声明“优先”的交易 - 仅为了保留账户而开启的早期阶段记录？
- 目前是否有任何补偿与 CRM 卫生、字段完成或预测准确性挂钩？

## 工作流

1. 运行面谈。确定审计范围：所有在指定快照日期的开放交易。冻结该快照 - 处置决策基于它，而不是动态账簿。
2. 提取数据。如果可以直接查询流程数据，提取开放交易加上阶段变更历史、截止日期变更历史和活动记录；否则请求包含这些命名列的导出。然后在进行任何测量之前进行清理和标准化（Umbrex 的审计顺序）：
   - 将自定义阶段映射到规范顺序。
   - 删除测试记录。
   - 补充缺失的阶段进入日期。
   - 规范货币和时区。
3. 首先确定过期层，使用四个过期桶 - 90 天以下 / 90-180 天 / 180-365 天 / 超过 365 天自上次有意义变更（ORM）。重新计算排除超过 365 天桶的覆盖率：该桶与头条覆盖率之间的差距是报告季度被高估的诚实衡量标准。如果超过 20-30% 的流程价值已过期，则在任何强制执行之前安排流程大赦（见 `[references/disposition-and-communication.md](references/disposition-and-communication.md)`）。
4. 从 12-18 个月的已关闭获胜历史中推导出每个细分市场的基线，**排除过期层** - 在测量前进行清理：承载大量死尾的交易组会产生比其活跃交易更长的、更平缓的关闭曲线（ORM），破坏审计依赖的非常数中位数。计算每个阶段每个细分市场的中位数阶段天数（中位数，不是平均值）。
5. 为每个细分市场设置阈值 - 约 1.5x 中位数（中小企业/高速度）到 2.0x（企业） - 加上新鲜窗口和推送触发器（检测规则下；推导和回退在 `[references/detection-rules.md](references/detection-rules.md)`）。
6. 运行三个规则族对快照。输出每笔交易每触发规则的行，以及触发它的证据。
7. 将标记合并为每笔交易的异常列表，附加流程价值；二次推送交易和多标记交易排在最前面。
8. 为每个被标记的交易提出处置，从分类法中提出。RevOps 提出；经理和代表决定 - 标记绝不能自动删除，代表不能给自己评分。每个决定的处置都得到命名所有者和记录理由。
9. 在任何强制执行或自动化之前起草沟通计划，并在会议至少 12 小时前发布异常列表 - 任何从报告开始的会议都已失败（ORM）。详情见 `[references/disposition-and-communication.md](references/disposition-and-communication.md)`。
10. 发出审计报告（输出形状下），按部分进行用户验证。
11. 计算 KPI 并检查通过阈值；迭代处置和整改，直到它成立，或安排差距进入下一个审计。
12. 将定期审计融入现有仪式（节奏下）并建议自动化周期性检查。审计移交的预防层是提示升级系统 - Jeff Ignacio（RevOps Impact）的机制是参考形状：
    - 在过期截止日期上通知所有者。
    - 增加提醒计数器。
    - 在第三次提醒时添加经理。

    描述该移交在范围内；设计系统不在范围内（范围边界）。
13. 如果您的系统具有持久内存，请存储基线、阈值、桶大小和异常计数，以便下一个审计从趋势线开始，而不是重新面谈。

## 节奏 - 骑用现有仪式，绝不增加会议

- **每周预测电话会议**：RevOps 带来过去 14 天内没有有意义活动的承诺交易；代表提供买方参与证据或交易退出承诺（ORM）。
- **每代表双周流程审查** - 季度最后一个月每周一次 - 处理过期、早期阶段和停滞交易，从预发布异常列表中移除。
- **季度区域清理**，在周期结束前约两周，以便清理在下一个季度覆盖之前完成。
- **交易台**：用于后期阶段、非标准或标记交易（重新阶段、交易拆分） - 不是常规卫生。
- 将高管排除在代表级流程审查之外：他们的存在使代表为流程辩护，而不是暴露其中的风险（ORM）。代表参加其经理的会议；领导层获得汇总。

## 检测规则

三个系列，都读取上述定义的“有意义活动”。用其来源标记每个阈值；数字是从业者起点，用于根据用户自己的数据校准。

- **过期交易** - 两个独立触发器，一起使用：
  - 阶段年龄：标记超过 1.5x-2.0x 该细分市场阶段中位数阶段天数的交易。乘数是细分市场相关的，不是口味问题：~1.5x（中小企业/高速度），1.5-2.0x 中市场，2.0x 企业（收敛：Umbrex、Outreach、DealHub）。
  - 最后活动年龄：中/后期阶段 14 天内无活动（Umbrex、Outreach）。作为不活跃规则的一般指南，中小企业标记 14-21 天，中市场 30-45 天，企业 60-90 天，法律和采购审查明确豁免（DealHub）。
  - 日期为过去的下一步，或没有计划的未来会议，也会标记。

  将每个过期交易分类到四个桶中。ORM 的 12 个月规则标记真正死亡的层 - 关闭曲线很少在 52 周后承载有意义预期。

- **推送次数异常** - 将推送作为字段跟踪，而不是记忆：计算每笔交易的截止日期变更次数，从字段历史中。
  - 第二次推送是升级触发器（ORM：最好的单一预测指标是代表更改截止日期，第二次推送是采取行动的对象）。它将交易移交给经理审查。
  - 跨季度边界的推送比季度内提示更糟：要求任何跨越周期边界的截止日期变更都必须有说明理由。
  - 三次或更多次滑移是有资格取消的（SalesOpsClub）。

  用证据测试区分滑移和死亡，而不是截止日期字段。问“在日期变得现实之前必须发生什么？”，然后堆叠信号：
  - 与日期所有者有共同行动计划的进展。
  - 多线程深度。
  - 经济买方参与。
  - 进入采购/法律。
  - 倡导者响应性。

  单独延迟下一步可能无害；与推送日期、单线程和预算犹豫结合，则成为可解释的干预案例。一旦确认滑移，立即更新截止日期并附上证据说明 - 最糟糕的结果是在交易上干预，但预测未更改。

- **字段完整性** - 仅检查预测关键字段，而不是整个架构：
  - 下一步及其日期、截止日期、金额、阶段、预测类别、已关闭亏损的损失原因，以及预测实际读取的资格字段。
  - 金额、阶段和截止日期是最高价值目标 - 它们本身就是有意义活动的字段。

  目标预测关键字段的完整性为 90-95%，最低限度为 80%。按效率顺序整改 - **阶段门控验证规则 > 所有者提示 > 自动捕获** - 背后的三个轴和幅度，在 `[references/detection-rules.md](references/detection-rules.md)` 中。

  - 验证规则领先：它成本约一小时管理员时间，仅在进入后期阶段时触发，因此对代表来说成本只是几秒钟，它保护了预测实际读取的字段，如果它误触会再次关闭。必需字段检查是否输入了内容；验证规则检查输入的内容是否有意义。
  - 更多必需字段不在该列表上：它被排除而不是排名最后，因为过多的要求会产生填充占位符（“n/a n/a n/a”大规模），比诚实的空白更糟，因为它看起来像信号。将上限保持在每个对象 5-7 个必需字段。
  - 自动捕获是顺序中受饿的：它永久移除摩擦，但需要集成项目加上同意审查，因此比率在每个回合中选择提示而不是它。在已部署捕获工具时或当代表达到摩擦极限且没有提示可花费时，提升它。

  顺序是默认值，不是法律；根据面谈答案和执行者重新排名它。

## 处置

每笔被标记的交易都以一个处置、所有者和记录理由退出审查。对于过期工作列表，只有两个答案是可以接受的：用真实的下一步和验证的截止日期重新激活它，或关闭它（ORM）。

| 处置                           | 当                                                                                           |
| ------------------------------ | ---------------------------------------------------------------------------------------------- |
| 已关闭亏损，带真实原因代码     | 没有买方侧证据表明活跃的购买过程；诚实的状态是“不发生”                                |
| 移至培育                       | 真诚的未来兴趣，但现在没有活跃的购买过程                                              |
| 向后重新阶段                   | 交易真实，但阶段高估了买方的实际位置                                                 |
| 重新日期带证据                 | 日期错误但交易在移动；新日期是“首先需要发生什么”的答案                               |
| 保留，带命名的下一步和日期     | 标记是数据差距，而不是死亡的交易；修复记录                                             |

此表故意未排名：每一行是不同的交易状态，由买方侧证据支持，而不是竞争相同结果的路线 - 按效率排序将是虚假精度。

非标准重新阶段和交易拆分通过交易台处理。永远不要删除 - 分类代替：删除会移除下一个审计将学习到的记录，破坏历史和转化基线，并且典型 CRM 中的回收站保留期短。默认返回买方为 `_新_` 记录，链接回已关闭亏损的记录；重新打开原始购买相同的恢复成本更高且不可逆转，并且只有两个命名条件会翻转它 - 见 `[references/disposition-and-communication.md](references/disposition-and-communication.md)`。

## B2B vs B2C / 高速度 / PLG

真正的差异不是阈值 - 是分析单位、可接受的自动化程度，以及资格是否完全存在于 CRM 中：

- **B2B（长周期、高ACV、采购委员会）**：交易流水线审查中进行逐笔检查；2.0倍乘数，企业静默期可容忍至60-90天；CRM字段中的资格深度（关键用户、经济买家、纸质流程）；推送次数和季度边界跨越是滑落关注的重点。
- **高速 / B2C**：聚合规则和基于异常的自动化取代逐笔审查；~1.5倍乘数，14-21天标记；3-5个阶段；仅对预认证早期阶段可接受计划自动关闭，参考最后活动日期以避免误报，并且需要销售领导层认可。速度和转化率阈值比推送次数更重要。
- **纯PLG**：潜在客户通过使用和自助交易在产品内自动转化——因此可能不需要传统的交易流水线，也不需要进行面向代表的卫生审计。与其强迫审计，不如直接说明；卫生要求转变为产品信号和PQL路由。

所有操作均相同：

- 有意义活动的定义（字段变更，非记录的接触）。
- 分类而非删除。
- 验证规则优先于必填字段。
- 指导而非监管的态度。

共享SLA机制：设置每个阶段的最高允许年龄与基线周期长度成正比，并在SLA违规时自动标记供经理审查——永不自动关闭，这会滋生不信任。

```
       修复（验证规则/提示 - 不是新的必填字段）

```

## 常见失败模式

| 失败                                          | 后果                                                                             | 修复                                                                                                                                  |
| ------------------------------------------------ | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 基于记录的通话/邮件的陈旧性                   | 规则满足但没有进展；陈旧流水线在每次审查中幸存                           | 基于阶段/关闭日期/金额变更；最后活动作为第二个触发                                                                                       |
| 所有阶段使用一个平面阈值                     | 过度标记企业，不足标记SMB                                                  | 阶段特定的中位数和乘数                                                                                             |
| 在清理前测量                               | 死尾使关闭曲线变平；基线损坏                                                | 排除陈旧层，然后计算中位数和覆盖率                                                                           |

## KPI和通过阈值

跟踪每次审计和作为审计趋势，每个都标明来源：

- 陈旧价值占开放流水线百分比：健康值低于20-30%，后期阶段陈旧值低于15%（Umbrex）；四个陈旧桶的分布。
- 诚实覆盖率：头条覆盖率与排除超过365天的桶的覆盖率对比 - 跟踪差距缩小。
- 滑落交易率（预测的交易推出期外）：目标低于20%；持续高于30%表明系统资格或纪律问题（Revenue.io）。
- 推送次数分布：0 / 1 / 2+ 推送的交易份额；季度边界推送有/无说明理由。
- 预测关键字段的字段完整性：90-95%目标，80%底线（Saber；Komo/DAMA）。
- 有未来日期下一步的开放交易百分比：核心指标；从用户自己的基线设定目标，而不是发布数字。
- 关闭日期准确性：CRM关闭日期与实际日期在容差内匹配的交易百分比（ORM的版本是14天；从自己的数据收紧）。
- 每个代表的EOQ关闭集中度，作为堆积的监控指标。

通过阈值——第一次审计设定基线；目标来自该基线，而不是发布数字。审计通过时：

- 每个标记的交易都有一个已决定的处理方式，带有所有者和原因——零未解决的。
- 审计关闭时没有过期关闭日期的开放交易。
- 没有记录证据答案的第二次推送或季度边界推送交易。
- 陈旧价值百分比、诚实覆盖率差距、完整性和下一步率都相对于基线向约定的目标改进。

迭代直到所有四个都成立。在向利益相关者（包括“40-60%的流水线是陈旧的”）引用任何卫生统计数据之前，检查其可信度标记在[references/evidence-and-benchmarks.md](references/evidence-and-benchmarks.md)——该领域的数字细节大部分来自销售预测工具供应商。

## 可选集成说明

除非用户指名其中一个平台，否则跳过。

- **Salesforce**：回收站仅保留删除记录15天，这是删除在实践中不可撤销的另一个原因；必须先为每个字段启用字段历史跟踪，才能使推送次数可重建。
- **Pipedrive**：每个阶段的“腐烂”天数阈值是原生功能，可以直接编码派生的陈旧阈值。

## 调用示例

- “在QBR之前，我们的流水线充满了垃圾——这些交易中有半数几个月没有移动。运行卫生审计，并告诉我该关闭、保留或推动以培育的交易。”

- “我的承诺中有三个交易每个都推送了两次关闭日期。审计账簿中的推送异常，并给我的经理一个例外列表供他们与代表合作。”
