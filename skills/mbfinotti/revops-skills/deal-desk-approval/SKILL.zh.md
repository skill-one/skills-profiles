# 交易台审批

设计谁可以批准非标准交易中的哪些内容——折扣、定制条款、高风险结构——并以规范形式交付：跨越五个让步杠杆的审批矩阵、禁止条款类别、具有SLA时钟和升级的例外处理、以及先例控制。这项技能仅涵盖交易台审批：一般业务流程审批（费用、采购、人力资源、工程变更）不在范围内——如果被要求，请说明并停止。

交易台阈值没有标准化：流通中的每个数字都来自从业者博客和咨询公司，其中一些来自内容农场。因此，这项技能的核心纪律是来源：标记每个阈值来源，并从用户自己的交易数据中推导出真实的阈值，而不是从导入的“行业”数字中得出。

## 基本规则

- 使用来源标签标记每个数值阈值。永远不要将供应商启发式算法呈现为行业常数。
  - 已发布的从业者来源
  - 单个供应商博客（仅作说明）
  - 从用户自己的交易数据中推导
- 永远不要将这些流传的数字作为事实。每个数字都在内容中重复出现而没有归属。省略它们，或者将它们命名为流传且未经验证：
  - “毛利率下限75%”
  - “每4亿美元收入对应1名交易台全职员工”
  - “中端市场35% / 大型企业交易台命中率70%”
  - Stripe归属的“在30%以上折扣时4.2倍的客户流失率”
  - Gartner归属的“到2028年90%的B2B采购将通过AI中介”
- “客户要求这样做”不是理由。最高权重的输入字段是拒绝的影响——如果例外被拒绝，会发生什么变化。
- 将会计和法律约束视为路由到财务、法律、安全或产品的设计约束。永远不要提供法律或会计建议。
- 在相关位置明确说明负面发现：价格歧视法几乎不会限制非主导SaaS供应商的差异化折扣（参见[references/accounting-legal-constraints.md](references/accounting-legal-constraints.md)）。不要制造合规风险。
- 在公共从业者指导不足的情况下保持诚实。与用户明确设计这些，而不是将虚构的实践作为标准：
  - 授予例外的续约处理
  - 转售商/MSP定价治理
  - 审批缺席协议
- 将此技能及其参考文献中的每个选项排序视为默认值，而不是法律。它随着上下文和执行者的变化而变化，因此在推荐任何内容之前，请根据您对用户的了解重新排序它。
- 具体来说：
  - 一个分析师的交易台无法资助升级注册或季度重新推导。
  - 拥有政策否决权的销售主管会提高收紧任何下限的政治成本，这会促进基于数据的下限，而他们无法争辩。
  - 已满载祖父条款的续约书使到期成为重新谈判而不是到期，并使升级成为实际的第一步。
- 将努力表示为分析师审查小时数、审批链延迟、收紧政策销售依赖的政治资本和可逆性——永远不要表示为货币金额。折扣百分比、利润率下限和赢率运算是主题，并保持原样。

## 面试

在设计任何内容之前提问。每条消息一个问题；尽可能使用多项选择；跳过已回答的内容。

- GTM策略：以销售为主导、PLG带销售协助、混合或纯自助/B2C？
- 市场细分混合和ACV区间——小型、典型和大型交易是什么样子？
- 谁今天批准折扣，以及通过什么渠道：没有人、经理提醒、邮件链、报价工具、正式交易台？
- 可以查询哪些交易数据：按细分市场的折扣分布、按折扣区间的赢率、每笔交易的利润率、审批周期时间？
- 利润结构：近零边际成本（经典软件），还是使用规模化的COGS（AI/推理、数据、基础设施密集型）？
- 今天出现哪些非价格让步：付款条款、免费服务、法律红线、定制SLA、安全/隐私补充条款、路线图要求？
- 每季度交易量，以及今天大约有多少份额需要任何例外？
- 痛点在哪里：速度（交易卡在审批中）或泄漏（利润侵蚀、未记录的让步）——或者两者都有？
- 哪些职能存在以进行路由：财务、法律、安全、产品/交付？
- 续约：谁拥有它们，以及之前的折扣是否今天默默地延续？
- 折扣在季度末是否会激增？
- 截止日期：必须在什么日期之前使此规范生效——在本季度结束前、下个季度，或没有固定日期？
- 一次性赢利或复合资产：修复本季度的折扣，还是为每个未来续约和每个新销售代表争论政策？复合在这里是字面意思——一次授予的让步将永远争论。
- 努力上限：交易台每周可以资助多少分析师小时数，谁拥有收紧政策的否决权，以及你可以与销售花费多少政治资本？

根据最后三个答案重新排序参考菜单，并大声说出哪个答案移动了哪个选项：

- 硬截止日期会促进快速行动的选项——占位符自动批准下限和到期续约处理都在一天内完成——并贬低任何需要数据提取的选项。
- 复合指令会促进基于赢率下限的选项，即使这意味着本季度的延迟，因为占位符将成为销售代表期望的折扣水平。
- 低努力上限会删除升级续约处理，其每账户跟踪是一项常规工作，并将例外通道的包组装到较少、较大的批次上。

## 工作流程

1. 运行面试；收集规范依赖的每个答案。
2. 确认范围边界：此交易台管理非标准交易。如果请求实际上是定价策略（列表价格、包装、层级）或非交易审批流程，请说明并路由出去。
3. 从[references/approval-matrix-design.md](references/approval-matrix-design.md)建立受管理的五个杠杆：
   - 价格/折扣
   - 付款条款和账单
   - 服务和交付承诺
   - 合同风险
   - 安全/隐私承诺

   仅管理价格的矩阵会将让步推入其他四个杠杆。

4. 从同一参考设计矩阵：
   - 超过折扣%的维度：交易规模、细分市场、策略、期限、产品线、利润率影响。
   - 3-4层，底部有一个自动批准下限。
   - 每层下方有政策利润率下限。
   - 无论审批者如何都禁止的类别：MFN/最佳价格、开放式价格持有、超出例外范围的未限制责任、未经批准的路线图承诺。

5. 使用[references/exception-taxonomy.md](references/exception-taxonomy.md)将每种例外类型映射到其拥有职能和升级触发器。
6. 从[references/intake-routing-and-precedent.md](references/intake-routing-and-precedent.md)设计输入、路由通道、两个SLA时钟、经过SLA升级、审批者缺席委托和季度末高峰模式。SLA时钟的完整性标准决定了时钟：不完整的请求会以结构化方式弹回，它们永远不会排队。
7. 从同一参考设计先例控制：
   - 例外注册、每个授予例外的到期日、模式到政策的审查、以及每类例外的续约处理。
   - 默认为到期：它以近乎零的常规努力收回整个让步，并保持可逆。仅在价格回弹已经导致该细分市场流失的情况下才促进升级。
   - 沉默的祖父条款不是选项之一。
   - 公共指导确实很薄弱：与用户决定并记录为内部政策。
8. 从[references/accounting-legal-constraints.md](references/accounting-legal-constraints.md)将会计和法律约束编码为路由规则：哪些交易结构在任何一个层级批准之前必须到达财务或法律，以及为什么。
9. 按照以下部分明确处理B2B和B2C——不对称地，而不是虚假对称。
10. 在该参考的优先级顺序中校准阈值：
    - 在存在赢率数据的情况下，从赢率按折扣区间推导自动批准下限。
    - 在赢率数据不足的情况下，退回到用户自己的折扣分布的百分位数。
    - 仅将说明性梯子用作一个周期的占位符，它永远不会作为政策交付。

    预计需要大约两个季度的数据，然后才能判断模式（RevOps Co-op）；如果它还不存在，请在交付物中说明。

11. 逐部分发出规范（输出形状以下）以供用户验证；使用来自[references/worked-examples.md](references/worked-examples.md)的匹配工作示例作为依据。
12. 附上KPIs和Pass Threshold以下，并迭代直到通过条件成立。
13. 如果您的框架具有持久内存，请记住决定的层级、下限、禁止列表和续约处理，以便稍后的校准从它们开始，而不是重新面试。

## B2B和B2C

人类交易台是B2B/企业结构：B2B价格按客户——报价和谈判——而B2C价格按产品——发布并接受。不存在B2C交易台；不要编造一个。

- PLG、自助服务和大量交易型SMB：等效的是规则驱动的折扣政策——自动促销引擎、发布折扣区间、优惠券治理和条款中发布的例外规则，没有人工链。只有在销售协助开始之前的交易规模，人类才会介入。
- B2C电子商务：促销/打折日历治理、优惠券发行和叠加规则、以及发布的价格调整政策扮演交易台的角色。
- 以下内容会完全相同地转移到所有内容中：例外导致的侵蚀动态、未记录的先例是其根本原因、以及定义区间、记录每个例外、监控蔓延的纪律。

将这种对比作为关于机制如何跨越两种策略的推理，而不是作为记录的行业发现。

## 输出形状

以该工件交付每个参与。每个阈值行都带有来源标签；每个审批者都有一个命名的代表。

```
交易台审批规范 - <公司>, <日期>
范围        : 什么被视为非标准；此交易台明确不管理的内容
杠杆       : 每个杠杆如何管理（价格、付款、服务、风险、安全）
矩阵       : 维度 x 层级，每层级审批者 + 委托人，自动批准下限，
               政策利润率下限（或使用规模化COGS的成本下限），每个细分市场的围栏
禁止       : 没有层级批准的条款需要明确的交换
输入       : 必填字段（拒绝的影响权重最高），完整性标准，
               不完整请求的弹回协议
路由       : 快速 / 复杂 / 例外通道，通道标准，每个通道的目标份额——批量在快速；例外通道由结构驱动，而不是大小
SLA        : 每个通道的响应时钟 + 决策时钟（工作小时，完整提交到记录和传达的决策），50/80/100经过SLA升级，
               委托和季度末高峰模式
先例       : 注册字段，每个例外到期日，模式到政策的节奏，
               每类例外的续约处理（默认到期；只有在有价格回弹流失证据时才升级；没有沉默的祖父条款）
约束       : 会计/法律路由表——哪些结构必须到达财务/法律，以及为什么
校准       : 每个阈值的数据源，来源标签，校准节奏
KPIs       : 五个KPI计分板 + 测量定义
```

## KPIs

- 一起跟踪五个KPI计分板，永远不要单独跟踪一个（Umbrex）：
  - 周期时间
  - 赢率
  - 折扣率
  - 利润率
  - 泄漏

  仅速度批准会快速批准坏交易；仅利润率会导致死锁，销售代表会绕过交易台。

- 还要注意：
  - 按类型分类的例外率：模式到政策的触发器。
  - 晚发现率：提案后出现的非标准条款，输入差距。
  - 价格实现：口袋价格 / 列表价格（SBI Growth）。
  - 期末折扣激增。

## Pass Threshold

规范仅在所有完整性条件满足时通过，然后迭代校准循环。

完整性 - 迭代规范，直到每个项目都成立：

- 所有五个杠杆受管理；存在禁止类别；利润率（或成本）下限已声明且与审批者无关。
- 每个层级都命名了审批者和委托人；两个SLA时钟和50/80/100升级按通道定义。
- 每个数值阈值都带有来源标签，并且警告的数字没有作为事实出现。
- 注册有到期日，并且已决定和记录了每类例外的续约处理。

校准 - 在例外审查节奏上迭代矩阵，直到两者都成立（RevOps Co-op启发式）：

- 批准近乎即时：太多事情需要批准，提高自动批准下限。
- 决策时间慢（p90超过例外通道SLA）：层级不正确，重新切割它们。
- 没有比两个审查周期更老的重复例外：将其提升为标准政策或明确拒绝它，同时折扣率和利润率在计分板上保持。

## 常见失败模式

| 缺陷                                                 | 后果                                                          | 修复                                                                        |
| ------------------------------------------------------ | -------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 矩阵仅管理折扣 %                                     | 让步迁移到付款条款、服务、法律、安全                          | 在一个矩阵中管理所有五个杠杆                                       |
| 一个高管作为最高审批点                                | 交易卡在审批中数天，而买方采购继续进行                  | 每个审批者有命名委托人 + 50/80/100升级                         |
| 审批逻辑存在于聊天线程和电子表格中                    | 上下文不会传递；在季度末中断；没有审计线索                 | 在记录系统路由和记录，记录每个决策               |
| 输入没有完整性门控                                  | 时钟在不完整请求上燃烧；重做循环                             | 在必填字段上门控SLA时钟；结构化弹回                   |
| “一次性例外”没有到期                              | 客户在第二年引用它作为先例                                | 每个例外都有时间限制；注册它；决定续约处理            |
| 在季度末压力下放松规则                              | 期末折扣激增；在最糟糕的时刻设定先例                      | 高峰模式增加容量和截止日期，永远不要放松规则                   |
| 报告平均周期时间                                  | 尾部疼痛被隐藏；销售代表绕过交易台                           | 中位数 + p90，从完整提交到传达的决策            |
| 成本下限被视为约束性下限                            | 近零软件COGS使其毫无意义；利润率在其上方侵蚀             | 政策利润率下限——除了使用规模化COGS产品，成本绑定         |
| 每笔交易都标记为“战略性”以证明让步                | 如果40%的交易是战略性的，那么什么都不是                      | 将战略性（高管批准、记录）与战术性区间分开        |

## 调用示例

- 我们的AE以最大力度打折，所有折扣都通过邮件直接发送给CFO——设计一个具有层级和SLA的真实折扣审批链。
- 我们正在建立一个价值30K中位数的交易台。建立非标准条款的审批矩阵和例外流程：净90天、定制SLA、安全补充协议。
- 每个季度末折扣都会激增，去年的“一次性”例外现在都在续约时重现。修复我们的例外处理和先例控制。
