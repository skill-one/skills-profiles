# 收入报告

构建一份连贯的故事式的执行层或董事会收入报告：一个小的、稳定的指标骨干，用“先回答问题”的叙事方式包裹，围绕计划与实际与预测组织。困难的部分很少是算术运算——它在于就定义达成一致、将CRM记录与财务记录进行核对，并确保董事会不会实时了解坏消息。

范围边界，事先声明：

**在范围内：**

- 报告中包含的内容及其呈现方式。
- 数字及其置信度。

**超出范围：**

- 在任何特定的BI工具中构建仪表板。
- 设计组织级别的KPI框架（哪些指标在哪个组织级别重要以及如何汇总）——这是一个在此存储库之外进行的单独策略练习。
- 调查预测为何出错——将其交给 `mbfinotti/revops-skills@sales-forecast-diagnostic`，然后使用此技能将完成的诊断转化为董事会叙事。

## 面谈

在提出任何建议之前进行询问。每条消息一个问题；在可能的情况下提供多个选项。跳过任何已回答的内容。

- 商业模式是什么——B2B合同订阅、使用/消费基于、PLG/自助服务、B2C/交易性/市场、或混合模式？
- 正在构建哪个工件——季度董事会演示文稿、月度执行回顾、周度收入回顾、投资者更新，还是整个节奏堆栈？
- 公司处于什么阶段——机构前、早期风险投资、增长或后期？（骨干会随着阶段收紧和变化。）
- 目前存在什么——什么都没有、每个周期重新构建的临时演示文稿，还是人们已不再信任的定期报告？
- 是否存在任何地方有书面的指标定义，以及任何两个仪表板是否对骨干指标（经常性收入、留存率、覆盖率）存在分歧？
- 目前谁产生这些数字——RevOps/运营、财务、创始人——并且财务在发布前认证它们吗？
- 本期的故事是什么——按计划、未达标、超出预期，或直到对账后才知道？
- 哪些数据可以访问——CRM/管道记录、计费系统、总账、产品使用事件？
- 何时必须完成——下一次董事会会议、本月的结账，或没有固定日期？
- 一次性工件，还是从本期开始每期重新构建的定期资产？
- 努力上限是什么——每期的分析师工时、财务是否会在要求时进行对账，以及是否已有仓库或语义层对收入进行建模？

最后三个问题在选择任何指标之前设定骨干排名：

- **财务结账内的截止日期**：将需要认证的每个指标（投资回报率、增长加利润率、三条基准线）从本期中排除。
- **复利指令**：首先构建经常性收入瀑布图和词典，尽管它们成本很高，因为每个后续时期都会重复使用它们。
- **一次性工件**：跳过两者，并报告从计费导出中的桥梁。
- **低努力上限**：将骨干限制在五个单系统指标。
- **仓库中的现有收入模型**：将每个队列指标提升到订单的最顶端。

## 工作流程

1. 运行面谈；在触摸指标之前，修复工件、受众、模型和节奏。
2. 选择指标骨干：五个到六个核心指标，绝对上限为八个。根据每个生产成本单位改变的决策数量对候选指标进行排名——分析师工时、系统已发出的数据、与财务的对账负担、必须重建的频率——而不是根据指标看起来有多标准。默认B2B顺序，最高比率优先：管道覆盖率 > 赢得率 > 经常性收入瀑布图 > 留存率对 > 到达率分布 > 增长加利润率 > 获取投资回报率 > 预订/计费/已确认收入线。这是一个默认值，不是法律：根据面谈答案和关于用户的一切已知信息重新排名它，并删除其数据规则排除的指标，而不是将其排名靠后。完整轴、平局理由、按模型顺序、阶段删除和此顺序剥夺的耐用性指标在 [references/metric-spine.md](references/metric-spine.md) 中。相同的骨干每个时期重复，以保持趋势可见；指标仅在替换一个指标时才会进入，并注释交换。
3. 锁定定义：为每个骨干指标编写词典条目——公式、包含/排除、真相来源、所有者、窗口，以及所有书面解决的争议规则（条目形状和工作示例在 [references/metric-dictionary-entry.md](references/metric-dictionary-entry.md)）。字段所有权和真相来源规则来自 `mbfinotti/revops-skills@crm-data-governance`——参考它们，不要在这里重新定义它们。在对账前冻结词典；周期中对定义进行更改会导致数字在会议之间变动。
4. 在叙述之前进行对账：CRM读取（预订、管道）和财务读取（计费、已确认）按设计分离，仅在合同级别在整个期限上结账——检查是计费减去已确认收入等于递延收入的变动，并且头条数字与财务将认证的数字匹配。当 harness 可以执行代码时，脚本桥梁和对账从两个文件导出（按账户的计费/总账收入，按交易的CRM预订）；否则请求财务认证的总计，并手动对账。永远不要发布财务尚未看到的数字。
5. 为每个骨干指标构建计划与实际与预测表格——每个讨论都挂靠的三列。显示移动桥梁（开始、增加、损失、结束）而不是净增量，并在存在分布的地方显示分布而不是平均值（到达率、交易规模、队列曲线）。
6. 以先回答问题的方式撰写叙述：结论、原因、响应、请求——在第一页上。按照下面的叙事部分结构；工作示例报告和在 [references/worked-report-example.md](references/worked-report-example.md) 中的良好与不良开篇。
7. 如果本期未达标，请按照呈现未达标部分进行：量化它，在实际上持有的置信度下说明原因，命名修复措施及其证明指标。根本原因深度属于 `mbfinotti/revops-skills@sales-forecast-diagnostic`，而不是此报告。
8. 按节奏组装（见节奏）：简短的主体，所有向后看和详细的附录，会议前几天发送演示文稿。可选地，在对账前通过人类化技能传递叙事文本。
9. 运行对账链：
   - RevOps 在截止日期前发布数字。
   - 财务对账它们。
   - 每个职能部门负责人验证他们的部分。
   - CEO/CFO 批准。
   - 预读提前三到四天发送。
   - 短暂的预线呼叫在会议室之前揭示反应。
10. 检查下面的测量阈值；修复并重新检查，直到每个阈值都成立。
11. 当 harness 具有持久内存时，存储锁定词典、骨干和重述日志——下一个时期从它们开始而不是重新决定。否则将词典作为版本化文档保存在团队已经保存文档的地方。

## 叙事结构

- 先回答问题，证据在下（金字塔原则/BLUF）：第一页陈述本期结论、最大的驱动因素、正在进行的响应以及向受众提出的决策。停止阅读的读者已经了解了整个故事。
- 计划与实际与预测是组织骨干；每个部分都是“发生了什么，为什么，我们正在如何应对它”——永远不会是图表的巡游。
- 演示文稿是预读；会议是做决策。将实时议程瞄准向前决策——从业者会聚在董事会时间的约三分之二用于向前，三分之一用于向后——并让向后细节存在于预读和附录中。沉默阅读叙事备忘录实践推动相同方向：文本迫使完整的论点，而要点隐藏了差距。
- 保持主体简短。当主体超过大约二十到三十张幻灯片时，它已成为预读；将其拆分并重新构建摘要。
- 每次会议跟踪相同的指标，按相同的顺序，以便跨时期无需重新定向即可读取趋势。

## 呈现未达标

- 永远不要有惊喜：每个重大负面都在预读和预线呼叫中出现在会议之前。在实时学习坏消息的成本比未达标本身更高。
- 在文档中尽早呈现坏消息，并在最强有力的真实音符上结束——永远不要将未达标夹在附录中。
- 永远不要平滑：报告原始序列并让波动性显示；平滑会推迟不舒服的对话并破坏读者需要的方差。抵消运动单独报告，而不是净化为一个看起来平静的总数。
- 报告未达标的解剖结构：
  - 与计划的差距量化。
  - 用实际持有的置信度命名驱动因素（“根本原因已确认”与“正在调查，下期结果”）。
  - 修复措施及其所有者和将证明其工作的单一指标。
  - 重述预测，反映未达标的根本原因。

如果原因尚未确认，请说明——过早提出的原因作为事实呈现是下一个重述。

- “宏观环境”不是原因，除非数据将市场运动与执行分开。

## 对账、重述和批准

- 所有权分割：
  - RevOps 发布数字。
  - 财务对账它们。
  - 领导层决定。

  RevOps 拥有发布截止日期，而不是呈现角色；财务无法对账到总账的报告不会发送。

- 一个定义胜过一个系统：CRM 和总账在每个周期内总会存在分歧——解决方法是每个阶段“正确”的定义（已记录、已签约、计费、已确认），而不是关于哪个系统获胜的辩论。
- 重述礼仪：当已发送的数字有重大错误时，明显重述它。
  - 标注列“已重述”。
  - 注释原因和每行效果。
  - 记录它。

沉默更正是如何导致信任死亡。重复重述是需要在源头上解决的控制系统问题，而不是格式问题。

- 数字在对账发送时冻结。在此之后进行的更正是一次重述，作为一次传达——永远不会在房间里有一个安静的不同数字。

## 节奏

三个工件，而不是三个速度的一个报告——每个工件都有自己的受众、深度和向前承诺：

| 维度        | 周度收入回顾                       | 月度执行回顾                     | 季度董事会会议                                       |
| ---------------- | ------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------- |
| 受众         | 收入团队 + 运营                          | 职能负责人 + CFO                       | 执行团队 + 董事会                                        |
| 重点            | 当期执行，交易/账户风险 | 计划与实际趋势，漏斗，效率    | 全骨干 + 叙事 + 决策                            |
| 工件         | 实时视图，无叙事                     | 评分卡 + 一页叙事               | 预读演示文稿 + 附录 + 预线                           |
| 向前边缘     | 本期的承诺                        | 下个月的优先事项                      | 重置目标，资本，招聘                                |
| 准备成本 | 一旦实时视图存在，每次运行接近零 | 一小时到一天，受财务结账限制 | 一周或更多：预读，附录，预线，对账链 |

这些是层，而不是竞争选项，因此它们之间不适用效率排名——每个工件回答不同受众的问题，每周的执行信号为每月的趋势阅读提供信息，每月的趋势阅读为季度重置提供信息。对三个不相互替代的工件进行排名将是虚假的精确度。

需要排序的是当努力上限限制时被丢弃的内容：

- **首先**：月度叙事（每周视图加上简短的书面趋势笔记涵盖了它）。
- **其次**：每周评论。
- **永不**：季度董事会工件——它携带外部义务，而其他两个没有。

一个分析师团队应该在一周一开始计划这种崩溃，而不是在十二周发现它。

仅当需要该层级的受众做出决策时，才将主题提升一层。

## B2B 和 B2C / 交易性 / 使用基于 / PLG

- **在所有模型中结构上相同，在交付物中声明这一点。** 这些都保持不变：
  - 移动桥梁形状（开始、增加、损失、结束）。
  - 计划与实际与预测骨干。
  - 队列逻辑。
  - 先回答问题的叙事。
  - 对账和批准链。
  - 无惊喜纪律。
  - 节奏堆栈。
- **改变的是原子。** 合同经常性基础在使用、交易和消费者模型中不存在——“经常性”数字是行为输出。相应地交换骨干原子（[references/metric-spine.md](references/metric-spine.md) 中的按模型骨干）：
  - 毛交易量与净收入与抽成率。
  - 队列留存曲线形状。
  - 重复购买率。
  - 贡献利润率层。
  - 参与率。
  - 基于消费的留存率。
- 不要将包含一次性或季节性收入的月份年化为一个运行率，除非说明；特别是使用型业务必须将季节性与健康恶化分开，然后再报告。
- 与匹配模型和团队自己的历史进行基准测试——基于座位的订阅基准测试美化或诽谤每个其他模型。

## 失败模式

| 陷阱                                      | 失败原因                                                                        | 解决方法                                                                                              |
| ----------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 数据堆砌式演示文稿                        | 观众纠结于图表而非做出决策                                      | 第一页先回答问题；细节放入附录；封底加注说明                                              |
| 定义在不同会议间漂移                    | 同一个词，不同数字 - 会议变成定义辩论            | 固定版本字典；变更仅作为脚注重述                              |
| 两个仪表盘对同一核心指标存在分歧          | 每个数字的可信度随着第一个矛盾而崩溃                  | 在演示文稿发送前统一书面定义，会议中绝不讨论                  |
| 平滑或净化的数据系列                     | 隐藏了作为信号的波动；一旦原始方差被丢弃就不可逆                  | 原始数据系列，桥梁跨越净数据，偏差单独报告                                       |
| 虚荣指标蔓延                           | 累计图表和美化切片总是上升；它们不包含决策          | 群体和分布视图；每个指标必须回答一个问题                               |
| 平均值隐藏分布                         | 两个团队共享均值且无其他信息                                             | 报告达成和交易规模作为分布区间                                            |
| 阶段不匹配的核心指标                    | 晚期阶段效率指标在早期公司（或反之）误导          | 核心指标按阶段分层；抵制观众要求报告尚未达到的阶段                  |
| 基准值被断言为事实                     | 流传的数字已过时且仅针对特定细分市场                                  | 从自身历史推导阈值；标注任何外部数据来源和日期                       |
| 会议中的意外                           | 信任立即且永久受损                                            | 预读加预沟通电话；文档开头就应发现遗漏                                       |

## 测量和通过阈值

报告在发送前必须通过以下所有检查；迭代直至达标：

- **核心指标规范**：主体最多8个核心指标（目标5-6）；前期核心指标100%以相同定义重现，或变更需加注说明为重述。
- **持久性检查**：核心指标至少包含一个持久性指标（留存对、群体留存曲线、消费净留存或调整后投资回报期），或报告说明删除了哪些数据缺口。纯粹基于生产成本的排名核心指标会滑向所有速度指标，直到基础停止支撑。
- **定义覆盖**：每个核心指标都有字典条目，包含公式、事实来源、负责人和窗口；演示文稿中无字典条目的指标为0。
- **核对**：标题收入数字与财务认证数据完全一致，或演示文稿中注明了核对项；账单/确认/递延的识别检查与显示的数字一致。
- **先回答测试**：单独给读者第一页，无背景信息；他们必须能说出期间结论、最大驱动或风险、以及诉求。三项中任何一项缺失即失败。
- **遗漏处理**：所有重大计划缺口在文档前三分之一处出现，带原因置信度标签、负责人和证明指标；附录之后首次出现的重大事项为0。
- **会议设计**（仅董事会节奏）：现场议程分配多数时间（目标三分之二）用于前瞻决策，每个决策项必须命名决策、背景和推荐。

发送后，跟踪这些持续信号：

- **每年重述次数**：上升意味着上游控制问题。
- **会议是否以记录决策结束**：一个停止产生决策的周期性会议意味着该工具已退化为数据堆砌。

## 可选集成说明

除非用户指明平台，否则跳过本节。

- **语义层**（dbt MetricFlow、Cube、Looker/LookML）：在代码中实现版本化指标字典规范，每个核心指标在此定义一次，所有仪表盘读取相同定义。
- **Salesforce**：预测类别字段可独立于阶段编辑，报告时间汇总可能不同于仪表盘快照 - 对导出文件认证，而非实时视图。
- **HubSpot**：默认交易阶段概率是可编辑占位符，非测量转化 - 永远不要让基于它们的加权管道数字未经调整就进入演示文稿。
