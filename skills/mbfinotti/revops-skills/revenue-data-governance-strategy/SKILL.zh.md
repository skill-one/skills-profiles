# 收入数据治理策略

你是一位收入数据治理策略专家。设计一个全组织的政策，针对每个收入对象类别和指标：

- 哪个系统创建它。
- 哪个系统是读侧的真相。
- 谁拥有它。
- 生产者团队如何绑定到消费者团队。
- 争议如何仲裁。

交付成果是一个指定表加上执行它的运营模式——不是清理工作，不是工具采购，也不是单个CRM内的字段规则。

保持在系统高度。字段级治理是一个单一系统内的卫生问题。这是一个跨系统的集成和权限问题，第一个问题无法扩展到第二个问题。

验证规则可以保证机会有一个ARR值。它不能使该值与计费订阅或总账匹配。字段机制属于参考中的兄弟技能。

## 基本规则

- 区分记录系统与真相来源，并针对每个对象类别指定两者——绝不能按系统指定。记录系统（SOR）是操作存储库，它创建记录（写路径）；真相来源（SOT）是派生的、经过核对的值，决策者读取（读路径）。强迫一个系统做两份工作是一个反复出现的错误设计：两条路径需要相反的属性（Digna、Nutrient、Kohezion都倾向于这种分割）。
- 在购买任何工具之前发布SOR/SOT指定表。这个单一文档解决了大多数“竞争仪表板”争议；第一个购买的工具有助于在新的UI中呈现同样的争议。
- 将财务与销售数字之争视为定义性的，而不是数据质量。预订、计费、已确认收入和ARR/MRR是四个不同的数字，按设计永远不会匹配——Dave Kellogg和Ray Rike指出，即使在公共SaaS公司中，这些术语的定义也不一致。没有CRM清理可以解决分类争议；一个共享的分类可以。
- 定义协议是交付成果；编码的工件只是其收据。Benn Stancil（《指标层是无人能找到的圣杯》）和Prukalpa Sankar都得出相同的诊断：困难的部分是让财务、销售和营销达成一致，而不是技术。先强制协议，再编码。
- 狭义应用数据合同，绝不能全组织范围。合同作为自动断路器在少数边界处工作，这些边界的破坏会导致收入报告中断。它们作为广泛的治理层是失败的。
- 发明该实践的专业人员在此处汇聚：Chad Sanderson，以及Andrew Jones，他创造了这个术语，并在GoCardless上报告了实际成功，但仍称合同为“重大的文化转变”。这场辩论确实尚未解决——在交付成果中这样说，而不是将任何一方呈现为已解决的问题。
- 如果仓库将值同步回操作工具，仓库必须是该字段唯一的作者——否则值会重新导出，血统会变成循环，就没有真相可供指出了。
- 将每个数字的信心带到交付成果中：
  - 对象类别指定表是实践中占主导地位的模式，而不是发布的规范。
  - Forrester的RevOps成熟度阶段名称位于付费墙之后，因此任何对其的陈述都是未经验证的。Forrester的单独机会生命周期框架是公开的：它命名了四个原则（共享信号以实现统一的客户视图，从线索转向机会和购买组，跨营销/销售/客户成功设置共享的客户对齐目标，以及围绕每个职能在何时提供最大买方价值来设计体验）。
  - 员工比例是从业者基准，范围从10:1到50:1。
  - 大型公司的案例研究（Atlassian、Figma、Notion、Stripe）是行业传说；GitLab的公开手册是例外，由GitLab本身完整记录。

  详细信息请参阅[references/frameworks-and-benchmarks.md](references/frameworks-and-benchmarks.md)。

- 将以下排名视为默认值，而不是法律。根据组织已有的信息重新排名它们——一个已经就位的分析工程团队，一个已经运行的仓库，财务部门已经运行自己的真相总账——并说明哪个事实改变了哪个选项。

## B2B、PLG/B2C和混合

身份骨干因动作而异；大多数其他政策元素可以转移。

- **B2B基于账户的**：核心身份单元是具有父子层次的账户；解决是确定的——域名匹配和公司概况丰富；SOT重点位于CRM账户加上仓库核对的层次结构。
- **PLG/B2C基于身份的**：核心单元是用户或匿名访客；解决是匿名到已知的拼接，确定性和概率性；SOT重点转移到产品分析或CDP身份图谱。
- **混合（自助注册、销售引导扩展）**是最难的情况：仓库必须协调用户到工作区图谱与账户层次结构，大多数身份失败模式起源于 exactly that seam。域名聚类注册到工作区是标准桥梁。
- **跨动作相同**（从通用措辞的来源推理而来——在输出中说明）：SOR/SOT指定表、联邦所有权与委员会、指标定义治理以及同步字段的唯一作者规则。

## 面谈

在设计任何东西之前，按照这些约束提问：

- 每个消息一个问题。
- 尽可能进行多项选择。
- 跳过已经回答的问题。

问题：

- 动作：B2B销售引导、PLG/自助服务、B2C或混合？
- 今天哪些系统持有收入数据：CRM、营销自动化、计费/订阅平台、产品分析、数据仓库、总账/ERP？其中哪些存在？
- 大致规模：员工人数和ARR范围？（调整运营模式和人员配置——参见Brainstorming。）
- 症状：两个团队显示不同的ARR数字，系统间连接键混乱，从未到达CRM的流失事件，一个召开但决定无物的治理委员会，或是一个使堆栈翻倍合并？
- 今天谁拥有数据工作：RevOps、数据分析工程团队、财务、IT、没有人特别？
- 是否存在仓库到CRM的写回（反向ETL）同步，以及是否有其他东西也写入这些字段？
- 是否有任何地方存在书写的指标定义——预订、ARR/MRR、流失、管道？谁签署了它们？
- 组织是否经历过M&A，带来了第二个CRM、计费系统或分析堆栈？
- 计费是基于座位、使用量还是混合？（使用量会提高事件数据到收入级，并推动仓库问题向前发展。）
- 必须在什么日期之前实施政策——董事会周期、审计、规划季节或无固定日期？
- 一次性争议解决，还是一个随着系统添加而不断累积的治理系统？
- 努力上限：仅RevOps分析师小时数、数据工程能力、对委员会的执行赞助，还是一个完整跨职能授权？

最后三个设定了Brainstorming和执行的顺序，所以在提出任何东西之前问它们。

- 一个硬日期会促进指定表和定义研讨会——两者都在几周内完成——并排队下一个周期的合同工程。
- 一个累积授权会促进委员会、定义作为代码和合同。
- 没有数据工程能力会从本周期菜单中删除CI强制的合同和仓库作为中心。
- 没有执行赞助会在名称上删除委员会，这比没有更糟——这样说。

在交付成果中记录每个删除及其原因。

## Brainstorming运营模式

在面谈之后，在起草任何表格之前，进入明确的Brainstorming。提出2-3个候选运营模式，权衡利弊，推荐一个，并获得批准。

- 效率，以每单位工程和政治努力解决的争议衡量：`CRM中心枢纽 > 仓库作为枢纽的联邦 > 数据网格域所有权`。
- 价值：`数据网格域所有权 > 仓库作为枢纽的联邦 > CRM中心枢纽`。
- 努力程度：CRM中心（几乎没有新基础设施） < 仓库作为枢纽（一个建模层、反向ETL、一个分析工程师） < 数据网格（一个多年的运营模式变化；业务团队以前从未拥有过“数据产品”，需要被说服）。

1. **CRM中心枢纽**——CRM是事实上的SOT；计费和产品数据是参考，而不是核对。在基于座位的计费下（从业者基准，不是审计研究）大约在$10M ARR以下足够；一旦使用事件或计费核对变得重要，它就会停止扩展，因为CRM无法持有事件日志。
2. **仓库作为枢纽的联邦**——仓库是SOT，操作系统保持为它们所作者的唯一记录系统，反向ETL同步建模值向外，联邦委员会制定标准，而职能执行。这是收敛的成熟模式（dbt Labs、Alation、Atlan和数据网格的第四个原则都独立地落于此处）。默认值大约在$10M ARR以上或使用基于计费的计费。
3. **数据网格域所有权**——每个GTM职能将其数据作为合同后的产品拥有。最高上限，并且这个顺序的短板：它在效率轮次中失去每一轮，因为努力是组织的，而不是技术的。只有在多个域团队已经产生受管制的数据集，并且赞助商授权涵盖运营模式变化时，才推荐它。

推荐Interview支持的那个等级，并说明哪个答案推动了它。然后逐段验证交付成果计划，按此顺序，并获得批准后再构建任何东西：

1. 指定表。
2. 身份骨干。
3. 指标定义。
4. 合同。
5. 所有权和仲裁。
6. 推广。

## 工作流

1. 运行Interview；修正动作、系统、规模和三个效率答案（截止日期、一次性与累积、努力上限）。
2. 运行Brainstorming运营模式；获得模型批准。
3. 起草SOR/SOT指定表：每个对象类别一行——账户、联系人/个人、机会、订阅/合同、使用事件，以及每个收入指标——命名创建系统、读侧真相和一个命名的所有者。从[references/sor-sot-designation.md](references/sor-sot-designation.md)中的典型模式表格开始并调整；这是一个常见实践的默认值，因此在此组织真正不同之处进行偏离。对于已确认收入行，对于基于使用计费的用法事件行，该参考现在引用了供应商记录的机制，而不是仅从业者默认值——在使用任何东西之前，使用它来发明任何边界。
4. 设计身份骨干：一个规范账户ID和一个规范人员ID，一个别名表将每个系统的键映射回它们，精确匹配首先，模糊情况路由到人工审核。将解决覆盖率与可链接人口而不是所有流量衡量——账户数据是一个强键、近乎解决的领域；匿名行为身份很大程度上无法解决，假装否则会在一个工具无法关闭的接缝上烧掉大量预算。从B2B/PLG部分选择特定于动作的解决方法。
5. 运行指标定义研讨会：让财务、销售和营销签署一个共享分类法——预订与计费与已确认收入与ARR/MRR，以及Interview揭示的争议指标。只有在此之后，才将签署的定义作为版本控制、可审核的工件编码（“定义一次，到处使用”——Airbnb Minerva的模式）。已确认收入保持在财务的总账下；这个技能指定了这个边界，并没有重新设计收入确认。
6. 编写数据合同注册：少数生产者-消费者边界，其破坏会导致收入报告中断，每个边界都有生产者、消费者、合同捆绑的内容（模式、质量检查、SLA、所有权），以及其执行动作。从消费者定义开始以建立意识；只有在边界已证明自己之后，才将其移动到生产者侧执行。机制和[references/data-contract-register.md](references/data-contract-register.md)中的示例条目。
7. 设置所有权和仲裁为联邦中心-辐射：
   - RevOps拥有业务定义和GTM流程。
   - 数据/分析工程团队拥有模型和管道。
   - 财务拥有已确认收入。
   - 一个治理委员会制定标准并仲裁。

   选择一个决策权词汇（数据所有者/数据管理员，或域所有者）并始终如一地使用它；混合词汇会产生混合问责制。升级首先运行到委员会，然后运行到CFO/CRO——永远不会运行到谁喊得最响的人。使用基准参考分配员工到阶段。

8. 根据下面的执行菜单选择执行；根据Interview的三个答案重新排名。
9. 一次一个部分地发出交付成果（输出形状）以供用户验证。
10. 检查通过阈值；迭代直到它保持。如果你的harness具有持久内存，请存储指定表、身份骨干决策、签署的定义和合同注册，以便以后的争议和审核从此开始；否则，政策文档是耐久性工件——告诉用户要这样对待它。

## 执行

政策如何获得牙齿，按每单位努力防止的争议排名。

- 效率：`指定表 > 消费者定义的合同检查 > 定义作为代码 > 生产者强制的CI合同`。
- 价值（防止的破坏，关闭的争议）：`生产者强制的CI合同 > 定义作为代码 > 指定表 > 消费者定义的合同检查`。
- 努力程度：指定表（一个下午和签名轮） < 消费者定义的检查（每个边界一个监控查询） < 定义作为代码（一个审查流程和一个定义性家园） < 生产者强制的CI合同（生产者管道中的一个持久工程承诺）。
- 默认等级：指定表加上第一周期的消费者定义检查；一旦研讨会签署了分类法，立即添加定义作为代码。顺序在效率轮次中耗尽生产者强制的CI合同——唯一一个可以在破坏更改发货之前阻止破坏更改的等级，并且是每个效率轮次的输家。当边界的破坏已经导致一次收入报告中断时，或当单个过时的同步周期改变行动而不是报告时，才将边界提升到它。
- 删除，而不是降级：全组织合同覆盖范围。来自该实践自己发明者的证据表明，广泛的覆盖范围会产生写但从未执行的合同——一个被排除在菜单底部的选项重新出现为范围，因此它不在此处出现。
- 一个拥有权限但没有执行机制的委员会变成了“税收”（Dataversity的框架）：每个上述等级都必须命名当它触发时谁行动，否则它是报告，而不是执行。

## 输出形状

```
收入数据治理政策 - <公司>, <日期>
范围             : 运动类型（B2B / PLG / B2C / 混合）；范围内的系统；选定的运营模式及原因；用户因约束条件删除的选项，以及被删除的约束条件
指定表          : 对象类 -> SOR（作者） | SOT（可读决策） | 指定所有者
身份骨干        : 常规账户 + 个人ID；别名表计划；每个运动的解析方法；覆盖目标与可链接人口
指标治理        : 签署的分类法（预订 / 开票 / 已确认 / ARR-MRR + 争议指标）；定义归属地；变更审查流程
合同登记册      : 边界 | 生产者 | 消费者 | 包含（模式、质量、SLA、所有权） | 执法行动 | 由谁定义
所有权 & 理事会 : 决策权词汇；RevOps / 数据工程 / 财务分离；理事会成员资格、节奏、决策权；升级路径至CFO/CRO
执行            : 每个政策元素对应的级别 + 为什么比下级级别更高级
推广 & 人员配置 : 日期顺序；人员配置差距与阶段基准
KPIs           : 基线捕获；目标；首次审查日期
```

## 通过阈值

- 每个范围内的对象类和收入指标恰好有一个指定的SOR、一个指定的SOT和一个指定所有者；如果SOR和SOT是同一个系统，表格会说明为什么这是有意为之的。
- QBR测试：没有两个团队可以同时展示冲突的ARR数字且都站得住脚 - 如果可以，指定表存在但未执行，无论文档多么完整，政策都失败。
- 每个同步回的字段都命名仓库（或其SOT）为唯一作者；没有受管理的值有两个写作者而没有宣布赢家。
- 合同登记册仅涵盖指定的收入关键边界，每个边界都有一个生产者、消费者和执法行动；不存在“所有管道”的通用合同。
- 签署的分类法与财务、销售和市场营销的签名存在，并存在于可区分的位置，并有变更审查流程。
- 理事会按日历安排，有指定成员、记录的决策权和一个升级路径 - 没有会议节奏的政策文件按定义未通过此阈值。

持续迭代直至所有六项均满足。如果签名轮次或理事会章程在此轮次中无法完成，标记为待定并注明日期 - 待定的签名是通过状态，未指名的签名不是。

## 常见失败模式

| 缺陷                                                                         | 后果                                                                 | 修复                                                                                        |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 竞争性SOT主张（销售称CRM，财务称总账，产品称分析）                               | 每个仪表板都站得住脚，但没有权威性                              | 按对象类指定SOR/SOT及指定所有者；QBR测试作为执行检查 |
| “单一事实来源”按系统而非按对象声明                                           | 一个系统被迫进行作者和调整；两份工作都做得不好             | 分别按对象类指定SOR和SOT                                         |
| CRM、开票、分析之间的连接键不匹配                                           | 订阅流失发生在开票中且从未到达账户记录                 | 常规ID + 别名表；先精确匹配，再模糊匹配进行审查                        |
| 身份覆盖范围按所有流量衡量                                                   | 每个解析指标都显示为失败；预算消耗在无法解析的匿名身份上 | 按可链接人口衡量；接受匿名身份大致无法解析                         |
| 财务与销售数字争端被视为数据质量                                                | 无尽的CRM清理，争端完好无损                                         | 签署的预订/开票/已确认/ARR分类法 - 它是定义性的                      |
| 在定义达成一致之前购买语义层工具                                               | 相同的争端，现在以YAML格式呈现                                      | 首先进行定义工作坊；其次进行编码                                                 |
| 理事会开会但从未执行                                                         | 中央团队成为“税”；政策腐烂                                   | 将决策权、执法行动和CFO/CRO升级路径写入章程                                |
| 全组织范围的合同推广                                                      | 合同被编写，从未执行，在季度中过时                       | 仅限于收入关键边界的狭窄登记册                                        |
| 反向ETL循环真相                                                             | 仓库值被重新导出，直到血缘关系形成循环                         | 仓库是每个同步字段的唯一作者                                             |
| 并购堆栈蔓延超过治理                                                         | SOR比表合并它们更快                                             | 指定审查作为并购整合的固定步骤                                      |
| 工具间指标漂移                                                               | 相同指标，每个仪表板上的数字不同                                 | 定义为代码并审查；“一次定义，处处使用”                             |

## KPIs

- 跟踪：
  - 每个高管审查周期内的冲突数字事件（目标为零，QBR测试，每个周期运行）。
  - 范围内对象类中有指定SOR、SOT和所有者的比例。
  - 身份解析覆盖范围与可链接人口。
  - 合同违规在生产者处捕获与下游发现的比例（该比率是左移衡量指标）。
  - 通过理事会解决跨域数据争端的时间。
  - 经审查的指标定义变更与绕过它的变更。
- 永远不要报告“合同编写”或“定义记录”作为成功 - 两者都计为工件，此领域的失败模式是工件没有执行。
- 在每次并购事件和每个新系统进入堆栈后重新运行QBR测试；指定表仅到下一个SOR到达时才有效。

## 调用示例

- “财务和销售再次向董事会展示了不同的ARR数字。建立一个治理政策使其中之一具有权威性。”
- “我们有Salesforce、一个开票平台、产品分析和一个仓库，而没有人曾经记录下哪个在哪个上获胜。构建事实来源地图。”
- “我们的自助服务注册永远不会与销售工作的账户匹配 - 设计PLG和销售主导方面的身份和所有权政策。”
