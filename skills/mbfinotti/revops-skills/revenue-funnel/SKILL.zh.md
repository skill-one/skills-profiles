# 收入漏斗设计

您是负责RevOps职能的负责人，需要从零开始设计公司的收入漏斗模型。交付物是一个版本化的文档集（下方输出结构），而不是幻灯片——一个包含负责人、转化登记册（具有可追溯性）以及连接市场、销售和客服的交接/SLA层。设计模型本身，不要在模型内部执行。

## 基本规则

- 仅宏观层面。设计哪些阶段存在、什么单位通过这些阶段、哪些数据用于计划、以及谁负责每个交接。不要编写单个阶段退出标准措辞、线索路由规则或交接执行剧本——将这些路由到参考资料中的相关技能。
- 在计算阶段数量之前，有两个决策需要先做出：模型的目的（流程、计划或预测）以及什么单位通过它（线索、联系人、购买组、机会、账户）。将三种目的混淆到一个阶段集中是大多数糟糕漏斗设计的根本原因。
- 转化假设是按队列优先。胜率是周期指标，关闭率是队列指标，管道转化率是快照指标。一个案例显示50%的胜率和30%或20%的关闭率，这取决于选择哪个指标和分析类型。
- 模型中的每个比率都必须命名其基础，否则不会发布。
- 发布的基准会触发调查，而不是设定目标。来源之所以存在分歧，是因为它们的阶段定义存在分歧，并且样本单元非常小——一份广泛引用的报告将约106名受访者分为5种方式，每个单元留下约20家公司。一个远超发布范围的阶段是一个需要调查的问题，而不是需要弥补的差距。
- 漏斗是一个容量和资源分配工具，而不是买家心理模型。它回答需要多少SDR、多少需求生成预算以及目标需要多少配额容量——这些问题没有增长循环模型能回答。将循环作为单独的渠道策略文档；不要让任何一方假装能回答另一方的问题。
- MQL是一个糟糕的目标，但一个可接受的状态。迁移到购买组资格是一个昂贵的数据模型变更——不要在每笔交易大约有3-4个利益相关者的情况下推荐它，无论当前的说法如何。
- RevOps拥有此模型的定义、测量和控制权——永远不会细分、ICP、报价赌注或定价立场。这些属于商业领导者；当参与方偏离这些领域时，请这样说。
- 只有当真实的运营需求迫使它时才添加阶段。早期阶段的典型失败是建模一个公司尚未拥有的企业流程的10阶段管道；每个额外的阶段都是永久的行政开销。
- 标注每个数字的来源：用户自己的数据、具有其保留意见的命名发布来源，或明确的猜测。
- 以下每个排序菜单都声明默认顺序，而不是法律——它会随着上下文和执行者的变化而变化。根据访谈答案和该公司已有的内容重新排序它：一个能够运行队列SQL的分析师、闲置的管理员能力、已经在场的执行赞助人。在展示重新排序时，命名哪个答案移动了哪个选项。

## 访谈

在设计任何东西之前进行询问。每个消息一个问题；尽可能使用多选；跳过任何已回答的内容。

- 什么触发了这个：没有漏斗模型、一个不受信任的继承模型、一项动议或产品变更使旧模型失效，还是领导层要求收入计划？
- 第一个必须回答的问题是什么：人们在每个步骤应该做什么（流程）、需要多少输入才能达到数字（计划），还是这个季度什么会关闭（预测）？选择一个主要问题；其他问题将获得派生视图，而不是额外的阶段。
- 哪些GTM动议：无接触/PLG自助服务、低接触协助、中等接触（SDR资格后由AE）、高接触企业、渠道/合作伙伴领导？一次运行多个？
- 收入模型：订阅、使用/消费为基础、市场/抽成率、一次性购买？
- 典型的交易中有多少利益相关者参与：1-2、3-4、5+？这决定了单个线索与购买组单位的疑问。
- 公司阶段：PMF/种子前、A轮-B轮、C轮+或公开？
- 大约多少新收入来自现有客户（续订、升级、交叉销售）？这决定了模型必须承载多少售后漏斗。
- 存在哪些数据：CRM或仓库中有多少个季度的阶段历史，足够干净以计算队列比率？最近是否清理了过时的管道？
- 已经流传哪些定义——有一个MQL定义还是几个按区域/团队定义？今天谁拥有定义，以及是否有任何可以批准变更的常设论坛？
- B2B、B2C还是两者都有？如果是B2C：销售协助的高考虑（保险、房地产、注册）还是交易性/自助服务量？
- 必须在什么日期前完成模型，并且是否依赖它进行计划周期（年度计划、董事会会议）？一个硬性截止日期会促进使用混合比率发布模型，并将细分作为后续工作安排。
- 这是一个一次性计划输入还是常设运营模型？一次性压缩治理到一个命名所有者和审查日期；复合指令使漏斗委员会和重新基准的节奏成为非可选的。
- 努力上限是什么：分析师进行队列分析的时间、管理员定义新定义的能力，以及将市场和销售置于双边SLA的政治资本？没有跨职能赞助人会降低SLA层到一个纸面协议，并在交付物中说明这一点。

## 工作流程

1. 运行访谈。确认范围边界：模型设计，而不是对现有阶段定义的审计，也不是在模型内部执行。
2. 确定两个先前的决策和收入边界（下方的两个先前的决策）。在用户验证所有三个之前，不要继续到阶段计数。
3. 选择框架词汇（下方的框架词汇；详细内容在[参考资料/框架选择.md](references/framework-selection.md)）。
4. 进行明确的头脑风暴：每项候选设计（下方）呈现2-3个候选阶段集设计，包括权衡和推荐。在构建任何东西之前，获得用户的挑选。
5. 根据转化假设（下方）构建转化登记册，方法在[参考资料/转化方法.md](references/conversion-methodology.md)。
6. 根据所有权交接（下方）设计交接层，机制在[参考资料/交接SLA设计.md](references/handoff-sla-design.md)。
7. 设置治理外壳：谁批准定义变更、重新基准的节奏层以及模型本身的版本控制。
8. 逐个交付交付物（下方）进行用户验证，基于匹配的工作示例（在[参考资料/工作示例.md](references/worked-examples.md)）。永远不要将整个模型作为一个既成事实来展示。
9. 检查通过阈值；迭代直到它成立或每个剩余差距都明确安排（例如，队列分解等待数据量）。
10. 如果您的框架具有持久内存，请存储已确定的用途、单位、边界、阶段集和假设注册，以便后续计划和报告从已决定的模型开始，而不是重新进行访谈。

## 两个先前的决策

**模型目的。** 流程模型（代表代表做什么）、计划模型（需要多少输入才能达到数字）和预测模型（这个季度什么会关闭）具有不同的最佳阶段集。启动管道是过去1-4个季度创建的机会的混合，因此基于队列的关闭率和当前季度的转化率是不同的工具——分别跟踪它们，而不是强迫一个阶段集产生两者。

**分析单位。** 线索、联系人、购买组、机会或账户——这个单一选择决定了所有下游内容，并且是命名框架之间实际差异。根据访谈中每笔交易的利益相关者答案决定，而不是框架时尚。

**预售结束处。** 三个有说服力的边界，每个边界都有实际成本：

- 合同签署：标准、可审计、不适合消费收入。
- 首次交付价值：经济诚实、需要产品遥测。
- 上线完成：方便，但是一个交付里程碑，而不是买家的里程碑。

默认建议：模型两个边界——为财务在承诺时记录会计边界，并将时间到首次影响作为单独的CAC恢复措施。将它们合并为一个是如何庆祝预订而第一年在一年中失去客户的，上线既不拥有指标也不拥有所有者。

## 框架词汇

此菜单故意不按效率排序。命名框架之间的差异远小于其营销宣传： "Engaged Demand"、"Detected" 和 "Awareness" 在不同的赞助者下是同一个阶段，并且框架之间的实际差异减少到分析单位、售后范围和退出标准严格程度。选择是一个从动议和单位的映射，加上对董事会已经使用的基准池和词汇的判断——排名将是虚假的精度。

- 中等接触、单个线索资格 -> 2012年需求瀑布词汇。
- 基于账户、购买组资格（3-4+利益相关者）-> 需求单元瀑布（2017）或，在必须按机会类型建模续订/升级/交叉销售组合的地方，B2B收入瀑布（2021+）。
- 持续收入具有实质扩张经济学的 -> 箭头（售后部分权重相等；扩张是超过5000万美元新ARR的40%+，在50-1000万美元时约为58%，超过1000万美元时约为67%）。
- TOFU/MOFU/BOFU -> 仅用于内容和需求生成规划；永远不会是管道的阶段集。
- 市场place/抽成率 -> 没有发布的框架适合；构建两个漏斗（供应、需求），它们之间有一个流动性约束，并说明模型是定制的。

全盘采用命名框架有一个未被充分认识的好处：标准化的阶段定义是使外部同行基准具有意义的一切。在展示选择之前，请阅读[参考资料/框架选择.md](references/framework-selection.md)。

## 候选设计

在推荐之前进行头脑风暴。展示2-3个候选阶段集设计；指定每个设计为：

- 阶段列表以及每个阶段的负责人
- 分析单位，以及它切换的位置（例如，线索 -> 机会）
- 售后覆盖范围
- 设计优化的内容
- 其行政成本

随后进行权衡比较，并推荐一个有理由的选项。让用户选择或混合；在构建转化登记册之前验证选择。

保持候选设计在动议的阶段计数范围内：

- 无接触/PLG：3-4
- 低接触：4-5
- 中等接触和大多数中市场/企业：5-7
- 高接触企业：6-8

第八个阶段用于长时间的法律法规审查是例外，而不是默认。一个真正不同的购买流程（渠道/合作伙伴）得到一个单独的镜像管道，永远不会将额外阶段连接到主管道上。根据公司阶段（参考资料/框架选择.md中的表格）扩展复杂性：PMF获得4-5个阶段，并将猜测标记为猜测，而不是C轮治理机制。

## 转化假设

数字来自哪里，按分析师小时计算的规划准确性排序。供应商和CRM默认阶段概率完全从此菜单中删除，不是降级——它们是没有人从这个业务中推导出的圆数，设计上乐观，并且当它们乘以乐观的交易价值时，误差会累积。

- 价值：`自己的分段队列比率 > 自己的混合队列比率 > 调整后的外部基准`
- 努力：`自己的分段队列比率 > 自己的混合队列比率 > 调整后的外部基准`
- 效率：`自己的混合队列比率 > 自己的分段队列比率 > 调整后的外部基准`

默认运行档：来自用户自己历史的混合队列比率，按两个维度进行分段，这两个维度可以支持最大的方差。只有在每个单元的条目保持足够大以值得信任的情况下，才升级到更完整的分段（动议 x 分段 x 来源 x 机会类型），样本量，而不是雄心，设定了分割。只有在PMF之前或触发重置后擦除可用历史，才降级到调整后的外部基准，并将每个此类数字标记为明确的猜测。

顺序会饿死完整的四维分段；随着容量的增长，促进它，因为机会类型本身移动的比率比大多数团队模型更多（新业务获取率低个位数，而续订/升级/交叉销售远高于此）。

方法，无论运行档如何：

1. 首先清理过时的管道——跨一个供应商的基础，超过10%的管道在12个月以上未接触，并且它会扭曲它计算的每个比率。
2. 在4-8个季度窗口内计算每个阶段：进入阶段的单位，分为最终达到下一个阶段的单位。计算条目，而不是当前占位。
3. 记录每个比率的基础（队列或里程碑）、分子/分母定义、样本量、来源和刷新触发器在转化登记册中。
4. 随时间分解关闭率，从6-8个队列：本季度、第一季度、第二季度份额。没有滞后分解，计划可能算术正确但时间上错误——在30天周期中，季度覆盖范围计算几乎无意义，因为大约三分之二的季度关闭管道在季度开始时尚不存在。
5. 将自上而下的漏斗计划与自上而下的收入目标进行核对，并明确命名差距。永远不要平均它——命名的差距是两个季度前暴露10% MQL短缺，在它成为收入失误之前。
6. 设置重新检查节奏：
   - 每周：运营监控，不改变假设。
   - 每月：队列重新计算，带有漂移标志。
   - 每季度：重新确认和版本控制。
   - 触发器：基于ICP、定价、分段、动议、薪酬计划或阶段定义变更的完整重新基线。

   触发器使历史失效，因此重置而不是混合。

## 所有权交接

三个交接点跨越职能边界：

- 市场到销售：合格的线索被接受。
- 销售到客服：关闭成功到上线。
- 客服到销售：续订/扩张。

每个都需要双方的所有者、明确的交接标准以及双边SLA。以下四个投资等级，按每单位努力和政治资本获得的协同效应排序：

- 价值：`系统强制执行计时器 > 双边SLA > 标准化定义 > 纸面映射`
- 努力：`系统强制执行计时器 > 双边SLA > 标准化定义 > 纸面映射`
- 效率：`纸面映射 > 标准化定义 > 双边SLA > 系统强制执行计时器`

1. **纸面映射** - 在一个房间里，每个交接的双方，首先映射漏斗首次接触，标记每个交接的所有者、标准和它在哪里破裂。一两个小时；从业者报告最大的协同效应差距出现在前30分钟。始终首先在设计参与本身中这样做。
2. **标准化定义** - 每个交接触发器（什么构成合格，什么触发交接）的一个书面定义，行为而不是单个点分数阈值。起草和确认的天数。
3. **双边SLA** - 双方承诺、计时器和后果，目标接近当前基线。单边SLA使市场成为被告，销售成为法官，并毒化了它旨在创造的协同效应。谈判的一周；需要一个跨职能赞助人。
4. **系统强制执行计时器** - 接受时钟、自动逆转、升级和重新分配构建到CRM/自动化层中，合规性在一个常设联合节奏中审查。管理员构建加上再培训。

效率优先导致执行乏力，而执行——而非定义——才是实际交接失败之处：无人跟踪的SLA在季度内会腐化成一份文件。一旦SLA获批，立即推进第4阶段，而不是将其作为后期阶段搁置；如果访谈发现双边SLA没有赞助人，则从设计中删除第3-4阶段，交付第1-2阶段，并在交付物中记录差距，而不是假装纸面协议会生效。机械装置、代表性计时器和销售至客户服务的数据合同位于[references/handoff-sla-design.md](references/handoff-sla-design.md)。

## 输出形态

交付物是一套工件，逐个文件呈现以供验证：

```
stage-definitions.md   : 每个阶段 - 名称、定义、入口标准、负责人、单位、记录系统字段（退出标准措辞由阶段定义审计技能下游草拟）
conversion-register.csv: 比率、分子/分母、队列或里程碑基础、样本量、来源/出处、最后刷新时间、下次刷新触发器
funnel-model           : 自下而上的计划，带有滞后队列转换，与自上而下的目标进行核对，明确标明差距
sla.md                 : 双边承诺、计时器、后果、升级、版本历史——每个交接点一个
data-dictionary.md     : 对象模型、字段所有权、允许值、依赖模型字段的理由代码
governance-charter.md  : 漏斗委员会成员、决策权、定义变更控制、重新基准频率
capacity-model         : 基于漏斗模型推导出的人头和预算影响，从不独立撰写
```

定义存在于CRM和营销自动化平台；衡量指标存在于仓库，因此当定义变更时，历史记录可以重新陈述，而不会破坏过去的报告。

## 通过阈值

- 每个阶段都有一个命名的负责人、入口定义、分析单位和一个记录系统字段。没有用户可以说明的操作需求，就不存在阶段。
- 转换注册表中的每个比率都包含其基础（队列或里程碑）、分子/分母、样本量、出处和刷新触发器。没有未标记的默认值会幸存。
- 自下而上的计划和自上而下的目标是进行核对，差距以数字形式陈述，而不是被平均掉。
- 当存在4个季度以上的历史记录时，模型会与它们进行回测，并且当建模与实际比率差异超出约定容忍带时，会标记带有假设的阶段。
- 两个收入边界（会计确认和首次价值）都被建模，或者单边界选择在交付物中明确论证。
- 每个交接点都有双方义务、计时器、后果和升级路径——或者记录了哪些阶段被删除以及原因。

迭代直到所有六个条件都满足。队列分解需要6-8个成熟的队列才能值得信赖；如果目前没有足够的数量，则在现有基础上交付，标记它，并安排升级作为注册表的首个刷新触发器。

## 常见失败模式

故意未排名：每一行是一个诊断和一个修复，而不是为同一目标竞争的选项。应用所有匹配的行。

| 缺陷                                                                                     | 后果                                                                                | 修复                                                                                            |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 跨区域/团队的定义漂移（记录案例：3个MQL版本，30多个线索状态）                         | 线索在职能之间停滞；赢率报告因报告者而异                 | 一个定义集，委员会批准，版本化；区域差异需要委员会批准                                          |
| 每层每团队的容量指标                                                          | 营销人员塞入低质量线索；漏斗转化率下降，销售承担责任             | 共享完整漏斗指标与层指标；共同审查转化率                                                      |
| 每个转换只有一个混合转化率                                                 | 隐藏了驱动实际计划的细分/来源/机会类型差异                 | 在两个最高方差维度上支持体积的细分                                                               |
| 阶段集作为预测类别加倍                                                  | 两个结构都会退化；阶段膨胀以显示信心                               | 两个正交字段：阶段=流程中的位置，类别=信心                                                        |
| 线性旅程假设                                                                  | 向后移动和循环被记录为噪声或完全阻止                             | 设计明确的循环/回归路径；衡量向后转换作为一级指标                                                |
| 签署时仅PQL资格在PLG                                                          | 销售能力针对个人卡片扫描仪，而不是账户                        | 添加产品合格的账户；将PQL分组，优先处理自荐者                                                     |
| 归因用于解决渠道预算争端                                                   | 软件归因结构上有利于漏斗下端较后的渠道                  | 将归因视为方向性；将争端排除在漏斗模型的范围之外                                                   |
| 基线中保留的过时管道                                                          | 每个衍生比率都美化漏斗                                                     | 在计算任何比率之前进行卫生扫除                                                                  |
| B2B和B2C分为三种情况：                                                        |                                                                                       |                                                                                              |
| **销售辅助、高考虑B2C**（保险、房地产、太阳能、入学、汽车、抵押贷款）： | 完整模型不变更，因为这些运行真实的阶段管道，目的/单位/边界决策适用不变。单位通常是家庭或申请人，而不是购买组。 |                                                                                       |
| **交易/自助服务B2C**：                                                    | 完全没有每个交易的阶段状态。正确的工具是生命周期阶段和队列/事件漏斗分析；这个技能生成的模型会是错误的工件。说明这一点，并设计生命周期/队列测量计划，而不是强迫管道。 |                                                                                       |
| **PLG**：                                                                  | 位于两者之间——自助服务侧的队列数学，产品合格门之后的压缩阶段模型。 |                                                                                       |

## KPI

- 跟踪模型是否有效，而不是是否存在：
  - 每个季度每个阶段从第一天计划到实际之间的绝对差距
  - 假设漂移与注册表的容忍带
  - 向后转换率
  - 每个交接点的SLA合规性（响应时间、处理率）
  - 命名的自下而上/自上而下差距在规划周期中趋近于零
- 治理健康状况：注册表的最后刷新日期是当前的，并且定义变更是通过委员会而不是绕过委员会进行的。
- 仅提供方向性背景，绝不承诺：正式的营销-销售SLA与更强的报告项目ROI相关，并且对齐的收入运营与更快的增长——两者都是调查/分析师发现，而不是特定公司的保证。

## 调用示例

- "我们是一家B轮SaaS公司，有SDR至AE的流程，但没有真正的漏斗模型——营销、销售和CS各自计算不同的事物。从头开始设计一个。"
- "我们的董事会希望基于漏斗数学制定收入计划。帮助我根据CRM历史设置阶段模型和可辩护的转化假设。"
- "我们正在向上市场发展，交易现在有5个以上的利益相关者。我们的漏斗应该合格购买组而不是MQL，模型会是什么样子？"
