# CRM 数据治理

构建并运行 CRM 的字段级治理。交付成果是一个动态规则手册加上一个会议节奏 - "治理因缺乏会议而消亡，而非因缺乏文档"（ORM Tech） - 由以下内容构建：

- 一个治理字段目录，每个字段有一个命名负责人。
- 每个字段的记录系统映射，包含写入优先级和冲突规则。
- 刷新和陈旧服务水平协议。
- 一个按单位努力价值排序的执行计划。
- 字段请求-审批-淘汰生命周期。
- 保持所有这些事物活跃的周期性节奏。

## 基本规则

- 治理收入关键字段，而非每个字段 - 这是第一个范围界定决策。CRM 包含数百个字段；治理所有字段既不可能也具有反作用力（从业者共识）。从 [references/field-ownership-and-dictionary.md](references/field-ownership-and-dictionary.md) 中的源字段列表开始，仅通过摄入扩展。
- 每个字段有一个命名的个人负责人 - "不是团队。是一个人。"（RevBlack）。将每个字段分配给消费它的职能，而不是填充它的职能。
- 指定每个字段的记录系统，而不是每个系统或对象。其他所有副本都是明确派生的。空白永远不会覆盖已填充的内容，无论时间戳如何。
- 代表永远不会是最后的执行机制。"销售代表不能负责数据录入...他们的薪酬、目标和心理激励都推动他们向销售而非数据管理"（Jared Barol）。优先考虑自动化、集成写入、丰富和默认值，而不是强制字段压力。
- 设计和运营一个常设系统。没有所有权地图、生命周期和预定节奏的清理不是治理；清理结束后，衰减会立即恢复。
- 为每个阈值标注其来源：已发布的公司实践、从业者共识，或派生于用户自己的数据。警告流传的统计数据 - "30% 的 CRM 数据每年衰减"和"CRM 数据只有 40-60% 的准确率"流传无出处，永远不能作为事实陈述。引用机制：存储值底层的现实变化（人员更换工作、公司成长和更名），以及无字段权限的多写入者同步会无声覆盖彼此。永远不要将供应商编造的专有复合分数作为行业标准呈现。
- 范围边界：记录去重和合并机制不在此范围内。周期性卫生清理、阶段退出标准、预测可靠性和路由逻辑属于参考中的兄弟技能 - 此技能编写这些工作消费的字段规则。

## B2B 和 B2C

**分歧：**

- **B2B** 运行在稀疏、慢速的数据上：长周期、账户层级、购买委员会，以及默认视为不可靠的代表录入层（"你不应该假设你的销售团队中有人会帮助你添加数据" - Stefano Mazzalai）。治理协调多个职能写入一个账户。
- **B2C** 运行在高容量、实时行为数据上，由没有代表层的系统写入。同意/偏好字段和保留时间表成为一级治理字段（同意政策由市场部拥有，同步可靠性由平台运营；即使页面创意是分权的，同意逻辑也保持集中）。
- **身份解析** 对 B2C 没有 B2B 的对应物，因为 B2C 的跨渠道匹配（确定性精确标识符与概率性）。B2B 通过域名匹配在账户级别解析身份。

**两者相同：** 每个字段的记录系统指定、空白永不覆盖已填充、丰富风险分层，以及最后验证为与最后修改不同的。这种等同性是从泛指来源的逻辑综合得出的，而不是一个已发布的声明 - 在交付成果中说明。

## 面试

在设计和任何东西之前提问。每条消息一个问题；尽可能提供选择题；跳过已回答的内容。

- 哪个 CRM，以及哪些其他系统写入它：市场自动化、计费、产品数据库、丰富提供商、支持台、数据仓库？
- 能否导出（或让我查询）范围内的对象字段列表？每个核心对象大约有多少自定义字段？
- 哪些字段今天用于预测、路由、薪酬或高管报告？（这为受治理集种下了种子。）
- 推动此症状的原因：系统间字段冲突、值神秘地回退、陈旧数据、字段蔓延、无人知道谁拥有什么？
- 谁今天进行数据操作：专门的 RevOps、CRM 管理员、IT、无人？
- 是否存在任何字段文档或词典，以及它存放在哪里？
- 哪些丰富提供商写入 CRM，以及写入哪些字段？
- B2B、B2C 或两者？范围内有任何同意/数据保护义务吗？
- 是否存在现有的治理论坛？谁现在批准新字段？
- 典型的销售周期长度和记录量？（校准 SLA 和阈值。）
- 必须在什么日期前完成 - 审计、董事会报告周期、CRM 迁移，或目前不受信任的预测？
- 你想要一次性纠正今天错误的字段，还是一个随着字段添加而累积的治理系统？
- 努力上限是什么：本季度管理员工时、任何集成工程能力，以及销售组织在吸收多少摩擦之前会绕过你？

最后三个设定了工作流步骤 4 和 6 中的选项排序，所以在设计任何东西之前要问它们：

- **一个硬日期** 推动配置-only 的步骤（限制选择列表、默认值、计划拉取、仅增强丰富），并安排下一个周期的条件验证和实时推送，而不是放弃它们。
- **一个累积指令** 推动按角色权限、条件必需-阶段，以及生命周期和节奏本身，并贬低默认值，默认值只是修补症状而不是创建规则。
- **没有集成工程能力** 直接删除实时推送。
- **销售组织已经对必需字段持敌对态度** 删除对代表录入字段的硬必需。

在规范中记录每个删除项 - 一个被排除的选项停放在列表底部，在下次升级时重新出现为范围。

## 工作流

1. 运行面试；确认范围边界（字段规则 - 不是去重，不是卫生清理，不是阶段设计）。
2. 界定受治理集：从 [references/field-ownership-and-dictionary.md](references/field-ownership-and-dictionary.md) 中的收入关键列表开始，添加每个用于预测/路由/薪酬/报告的字段，并故意限制。
3. 按字段分配所有权：消费者所有权原则，一个命名的人，按职能的 RACI 作为默认划分（参考相同）。
4. 构建每个字段的记录系统映射：权威系统、写入优先级、复制模式、丰富写入策略（风险分层）和冲突解决分层，每个受治理字段 - [references/system-of-record-rules.md](references/system-of-record-rules.md)。此步骤内有两个排名选项，并且都在这里做出决定，而不是在参考中：

   - 复制、效率：`计划拉取 > 仅对账 > 实时推送`。默认每个受治理字段按其新鲜 SLA 要求的计划拉取；仅在陈旧同步周期改变行动而非报告时，将字段升级为实时推送。实时推送是此顺序剥夺的 - 最佳新鲜度，最差比例 - 所以在贬低它时在规范中命名它，并在事件总线或 iPaaS 已经运行且边际字段成本为零的地方翻转顺序。
   - 丰富、效率：`增强 > 追加 > 覆盖`。默认整个受治理集为增强；仅在提供商定义上权威且存储值不带验证戳时才移动到覆盖。覆盖在这里被剥夺的原因相同，并且是唯一可以纠正已经错误的值的模式。

   参考包含两个顺序背后的价值、努力和合规成本轴、平局和约束，这些约束删除选项而不是贬低它。在编写映射之前，根据面试对该团队建立的背景重新排序这两个顺序。

5. 按字段类别设置刷新 SLA，并设计最后验证跟踪与触发式重新验证 - [references/freshness-slas.md](references/freshness-slas.md)。为每个 SLA 标注来源。
6. 从 [references/enforcement-menu.md](references/enforcement-menu.md) 中为每个字段选择执行，按单位努力价值排序，而不是按它有多轻松：

   - 效率：`选择列表 > 条件必需 > 默认值 > 权限 > 布局 > 硬必需`。第一遍默认为限制选择列表加上默认值；对于任何在已知转换时读取决策的字段，爬升到条件必需-阶段。
   - 按角色权限和硬必需是此顺序剥夺的：两者都携带廉价环节无法购买的真正价值，并且在每次效率轮中都失去。一旦受治理字段有两个忽略其记录系统指定的写入者，就提升权限，并且仅在记录没有该值时无法决定的情况下才提升硬必需。
   - 永远不要默认为硬必需 - 一个只选择廉价环节的程序最终会得到一个所有人均不信任的字段词典。

7. 建立生命周期和节奏：摄入问题集、审批/拒绝标准、淘汰过程、理事会成员资格、会议节奏、决策权 - [references/field-lifecycle.md](references/field-lifecycle.md)。
8. 使用工作默认列集（所有权参考）编制词典。当活 CRM 可直接查询时，从其元数据生成初始行；否则从用户的导出构建并标记未验证行为为未验证。
9. 分段发出交付成果（输出形状）供用户验证，基于 [references/worked-examples.md](references/worked-examples.md) 中的匹配示例。
10. 检查通过阈值；迭代直到它成立。如果你的 harness 具有持久内存，请存储受治理字段列表、所有权映射和记录系统决策，以便周期性审查和争议解决从此开始；否则词典本身是持久的工件 - 告知用户要这样对待它。

## 输出形状

每个阈值行都带有来源标签。

```
CRM 字段治理规范 - <公司>, <日期>
范围            : 范围内的对象；受治理字段数量与总字段数量；
                   动作（B2B / B2C / 两者）；用户约束删除的选项，
                   以及哪个约束删除了每个选项
所有权映射    : 字段 -> 命名的负责人（一个人）+ 拥有职能
记录系统      : 字段 -> 权威系统，写入优先级，复制模式，
                   丰富策略 + 风险分层，冲突规则
新鲜 SLA      : 字段/类别 -> 刷新节奏，重新验证触发器，
                   最后验证跟踪计划
执行          : 字段 -> 机制 + 为什么它优于下一条环节 +
                   推广笔记
词典          : 列集，初始行，词典与活 CRM
                   调和计划
生命周期      : 摄入表单，审批/拒绝标准，淘汰
                   过程，利用率审查阈值
节奏          : 理事会成员资格，每周/每月/每季度节奏，
                   决策权，升级路径
指标          : 捕获的基线值，KPI 目标，首次审查日期
```

## 通过阈值

- 每个受治理字段都有：
  - 一个命名的个人负责人（永远不会是团队名称）。
  - 恰好一个记录系统。
  - 每个触摸它的同步声明的写入优先级和冲突规则。
  - 一个刷新 SLA，或一个明确的事件驱动指定。
  - 至少一个执行机制。
  - 一个词典行。
- 没有受治理字段有两个写入者而没有声明赢家，并且丰富永远不会自动应用于身份或下游触发字段。
- 词典抽查：抽样 10-15 个受治理字段与活 CRM（类型、选择列表值、必需性、描述存在） - 至少 95% 的协议，一个工作条从用户的漂移数据收紧，而不是一个已发布的标准。
- 节奏存在于一个日历上，有命名的与会者和记录的决策权 - 单独的政策文件定义上会失败此阈值。

迭代直到所有四个成立。如果在此轮中不可能进行活 CRM 验证，请将抽查标记为待定，并安排它作为第一个理事会议程项目。

## 常见失败模式

| 缺陷                                        | 后果                                                         | 修复                                                                                                          |
| --------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 字段由团队拥有（"RevOps 拥有它"）      | 每个人都不拥有；问题被忽略或跨系统多重处理    | 每个字段一个命名的个人，在词典中可见                                                   |
| 治理每个字段                         | 努力稀释；治理被视为不可行                              | 治理收入关键集；仅通过摄入扩展                                                      |
| 反射要求必需                         | "n/a" 和垃圾条目通过大门；采用崩溃            | 工作效率顺序：选择列表和默认值优先，条件验证在硬必需之前                               |
| 丰富覆盖验证值                     | 信任数据无声被摧毁                                     | 默认增强/追加；仅在丰富是指定权威时覆盖；风险分层所有写入 |
| 双向同步，无字段权限                 | 摇摆值，无声覆盖，"数据是错误的"升级                | 每个字段的记录系统加上最后同步冲突检测                                               |
| 一次性清理被误认为治理              | 立即恢复衰减                                           | 生命周期 + 节奏；清理是系统的输出，不是系统                                      |
| 从不召开的理事会                      | 政策腐烂；请求绕过摄入                                 | 安排每周筛选，具有决策权；会议是机制                                   |
| 治理分配给 IT                     | 业务停止信任定义                                 | RevOps 拥有它；管理是业务角色                                                               |
| 孤儿一次性字段                       | 蔓延，重复字段，部落知识                          | 摄入时具有重复检查；利用率审查；淘汰队列                                           |
| 将成功衡量为"代表填充更多字段"           | 填充率上升，准确率下降                                         | 衡量冲突率、陈旧性和验证覆盖率，而不是                                              |

## KPIs

- 跟踪：
  - 受管字段的字段填充率，并非所有字段。
  - 字段利用率：在报告/自动化中消耗，而不仅仅是填写。
  - 陈旧度分布：每个字段自上次验证以来的时间。
  - 每次同步运行中的跨系统冲突率。
  - 验证失败率。出现峰值意味着存在摩擦——在庆祝强制执行之前，先检查垃圾值的工作around。
  - 字段请求的审批时间。从业者目标：从请求到发布不超过一周。
  - 自定义字段数量趋势，一旦数据摄入建立，应趋于平稳。

- 永远不要将“代表填写了更多字段”报告为成功——当关卡强制垃圾条目时，填写量上升而准确性下降。

- 每季度重新运行字典抽查；不断增长的漂移意味着对账循环已中断。

## 调用示例

- “我们的CRM显示一个员工数量，账单显示另一个，而营销自动化显示第三个。逐字段决定哪个系统获胜。”
- “任何人都可以添加自定义字段，而我们账户对象的字段已达到400个。建立字段请求流程和所有权模型。”
- “建立数据字典并刷新我们预测所依赖的字段的SLA——其中一半已过时，且无人负责。”
