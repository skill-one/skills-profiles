# RevOps 招聘

构建一个招聘经理需要用来招聘 RevOps 或销售运营人员的资料包：角色定义、面试流程、评分卡、工作样本、入职计划。

框架是 Geoff Smart 和 Randy Street 的《Who: The A Method for Hiring》中评分卡的传统 - 一个使命，3-8 个按排名的衡量结果，然后是能力。它适用于从业者实际认可的典型：

- RevOps Co-op 的五个职业路径：分析师、系统管理员、赋能、交易台、项目经理。
- 招聘时压缩为三个配置文件：系统、分析师、策略师。

在创建资料包之前有两个决定：

- 是否要开放招聘需求，而不是雇佣一个部分运营人员或进行范围明确的代理项目。
- 哪个典型 - 因为大多数失败的 RevOps 招聘是由于典型不匹配，而不是能力失败。

这仅是招聘者的视角。它不负责候选人搜寻、发布职位或跟踪申请人，并且它报告已发布的薪酬范围作为范围输入 - 它从不撰写录用通知书或提供法律或人力资源合规建议；这些需要人力资源/法律部门审核。

候选人方面 - 准备并获得 RevOps 职位 - 是 `mbfinotti/revops-skills@revops-career` 的镜像兄弟。在赢得后入职客户是 `mbfinotti/revops-skills@sales-to-cs-handoff`，完全是另一份工作。

## 面试

在设计之前提问。每条消息一个问题；尽可能提供多个选择答案。跳过已经回答的内容。

- 公司处于什么阶段和规模？（a）A 轮之前 / 25 人以下，(b) A-B 轮 / 25-150，(c) C 轮及以上 / 150 以上，(d) 不是风险投资路径 - 描述。
- GTM 团队是什么样的 - 大约有多少销售代表、营销人员和 CS 人员？
- 这是第一个专门的运营招聘，还是加入现有的运营团队？如果是现有团队：谁在团队中以及他们负责什么？
- 哪个痛点推动了招聘？（a）管理和工单积压 - 容量，(b) 没有人信任报告或预测 - 分析，(c) 跨团队边界的问题 - 流程和一致性，(d) 这些中的几个。
- 堆栈的成熟度如何？（a）CRM 配置基本，(b) CRM 加上营销自动化工作但混乱，(c) 包括数据仓库和 BI 的完整 GTM 堆栈。
- 预算和级别是多少 - 如果市场认为这个数字太低，这个数字是否可以协商？
- 这位招聘人员将向谁汇报，谁是执行赞助人？
- 面试小组由谁组成，您可以实际运行多少轮？
- 必须在何时之前解决这个问题？（a）一个日期事件迫使它在季度内解决 - 董事会会议、指标重置、迁移，(b) 本财年，(c) 开放。季度内的一个硬日期会删除内部高级选项：搜索本身就会超过截止日期。
- 您想要一次性修复还是复合能力？一次性修复促进部分运营和代理；复合任务促进内部招聘，并且是唯一证明其前两个季度合理性的答案。
- 您的努力上限是多少 - 每周有多少经理小时，面试小组是否可用，是否批准了人员编制，以及如果出错了是否可以在一个月内撤销？冻结或未批准的人员编制将完全删除招聘选项；对不可逆性的低容忍度促进合同选项。

## 工作流程

1. 运行面试；在设计任何内容之前收集所有答案。
2. 决定是否要开放招聘需求，使用 [references/role-archetypes-and-leveling.md](references/role-archetypes-and-leveling.md) 中的排名配置文件选择测试。按每小时返回的价值排序：`部分运营人员 > 范围明确的代理项目 > 内部专家 > 内部策略师`，内部行按痛点路由 - 报告信任到分析师，管理积压到系统专家，跨边界流程到策略师 - 并且痛点限制在一个功能内完全路由出 RevOps 完全到销售、营销或 CS 运营。删除面试答案排除的选项，而不是将它们排名靠后，并命名您删除了哪些。重新根据您已经了解的这家公司的信息对剩余的选项进行排名：已经保留的代理、内部招聘人员、第五个运营招聘与第一个。只有内部结果才使本工作流程适用 - 然后在起草任何其他内容之前以书面形式命名原型和级别。
3. 控制招聘需求：以书面形式锁定汇报线和 VP 或 C 级执行赞助人 - 实践者称赞助是第一个招聘成功的最大预测因素 - 并将预算与同一参考中发布的范围进行压力测试。引用每个范围及其来源和日期。RevOps Co-op 的警告适用：“与拥有您现有的资金并失败新招聘的 [情况] 相比，为雇佣一位经验丰富的专业人士而争取更多的资金更好。”
4. 将角色定义作为评分卡编写 - 一行使命，3-8 个按排名的结果，带有客观和可观察的日期，然后是能力 - 并将必须项转换为要求矩阵。大致勾勒出“好”的样子；RevOps Co-op：“您的任务是勾勒出‘好’可能的样子 - 即使只是一个便签纸上的草图。” 相对经验水平评分 - 过度合格和不合格都得分低 - 并且仅在系统原型公司在该平台上标准化时将供应商认证作为必须项。要求矩阵规则：
   - 围绕问题而不是工具编写。
   - 必须项限制在 5-7 个，并加权总和为 100%。
   - 将喜欢项作为附加积分点保留。
   - 将淘汰项保留在单独的检查表中，而不是作为评分卡内的负分。
5. 定义 4-6 个能力，并从 [references/competencies-and-question-bank.md](references/competencies-and-question-bank.md) 构建问题库：每个能力 2-3 个行为和 1-2 个情境问题，带有后续探测，领域故障模式作为难以伪造的探测，以及红/绿答案对作为评分锚点。
6. 将流程映射为阶段表 - 阶段、面试官、评估的能力 - 每个能力由 exactly 一个阶段拥有，并且每个面试小组员分配一个车道。保持紧凑：Matthew Volm（RevOps Co-op 的 CEO）主张一个大约两小时的带回家和“最多 3 轮”。
7. 在任何人面试之前固定评分纪律。编写一个带有行为描述的锚定评分量表，描述每个锚点在这个特定角色中看起来像什么 - 禁止裸数字 - 并要求每个提交的分数引用证据，一个引用或一个具体示例。面试官在讨论之前独立评分，淘汰信号单独记录，推荐由信心而不是匹配加权：”数据不足“是一个有效输出，并且没有单个分数可以覆盖整个流程。
8. 设计工作样本从 [references/work-sample-design.md](references/work-sample-design.md)。从那里的排名菜单中选择格式 - `现场模拟 > 支付的带回家 > 未支付的带回家` 按每小时花费的信号，未支付行既包括最佳候选人的流失，也包含真实的合规成本，并且八小时未支付的练习被删除而不是降级。然后构建：
   - 一个看起来像真实缺陷的提示，而不是一个项目。
   - 一个硬时间上限。
   - 在第一个提交之前编写的评分标准。
   - 一个简报计划 - 简报比工件携带更多信号。
9. 从 [references/ramp-plan-template.md](references/ramp-plan-template.md) 构建入职计划：入职前、第一天、第一周，然后 30/60/90 - 根据资历和原型分支，带有第一周访问列表、工单队列保护、诚实的里程碑预期和关闭监控区域。
10. 分部分发布资料包（下一节）以供用户验证，将每个部分与来自 [references/worked-examples.md](references/worked-examples.md) 的匹配示例联系起来。
11. 直到 Pass Threshold 中的每个项目都通过为止，迭代资料包。
12. 如果您的 harness 具有持久内存，请记住批准的资料包 - 原型、级别、能力、阶段映射、阈值、入职分支 - 这样筛选运行和最终的入职可以从它开始而不是重新面试。没有内存，请告诉用户将资料包文档作为未来运行的站立输入。

## 招聘资料包

以这个工件交付每个参与。完全工作的版本存储在 [references/worked-examples.md](references/worked-examples.md)。

```
招聘资料包 - <公司>, <角色>, <日期>, v<n>
配置文件选择 : 排名选项，说明顺序 | 删除的选项 + 原因 | 推荐
角色定义 : 原型 + 级别 | 使命 | 3-8 个按排名的结果，带有日期 | 能力
要求    : 必须项加权总和为 100% | 喜欢项作为积分 | 淘汰项检查表
能力输入  : 引用已发布的范围，附带来源 + 日期 | 标记：录用条款需要人力资源/法律
阶段映射 : 阶段 -> 面试官 -> 评估的能力（每个能力由 exactly 一个阶段拥有）
问题库   : 每个能力 - 行为 + 情境 + 后续探测 | 红绿锚点
评分卡       : 每个能力一个锚定量表 | 每个分数引用证据 | 信心评级
工作样本     : 提示 + 时间上限 + 支付/未支付调用 | 评分标准（首先编写） | 简报议程
简报规则   : 独立预评分 | 淘汰项单独 | 信心加权的决定
入职计划       : 入职前，第一天，第一周，30/60/90 | 资历 + 原型分支 |
                  第一周访问列表 | 监控区域
```

## B2B 和 B2C

招聘流程在各个细分市场中是相同的 - 评分卡、流程、工作样本、入职 - 并且在询问时说明。真正改变的是哪些能力携带权重，哪些指标角色拥有，候选人必须了解哪些堆栈，以及面试探测什么。

- **B2B 企业**：角色拥有管道覆盖率、胜率、交易速度、净收入留存、预测准确性、区域和指标；堆栈是 CRM、销售参与、收入智能、CPQ - 权重报价到现金深度、区域和薪酬设计，以及预测节奏判断。
- **B2C 和电子商务**：角色拥有客户获取成本、转化率、平均订单价值、购买频率、流失率和按队列建模的 LTV。
- **PLG**：激活、产品合格线索、免费到付费转化、扩展信号 - RevOps Co-op 指出在 PLG 中“使用漏斗阶段作为团队有效性的代理 [变得] 没有道理”。

PLG 的方向性供应商报告基准，标记为方向性，不具权威性：

- 激活：25-40% 的注册用户在 7-14 天内。
- 免费到付费：大约 2-5% 免费增值，15-25% 免费试用。
- PQL 用户转化率大约高三倍。
- 大约只有四分之一的 PLG 公司实际使用 PQL。

因此，PLG 和消费者 RevOps 需要分析工程相关的技能 - 强大的 SQL、实际的数据仓库工作、转换层 - 并且面试应该探测产品信号流利度而不是区域设计。

- 交易台接近于 B2B 独有的原型；消费者订阅很少有一个。
- 其计费和支付复杂性在 B2B 中没有对应物。
- 纯 B2C 订阅通常缺乏推动 B2B 净留存超过 100% 的扩展路径。

## Pass Threshold

迭代直到每个项目都通过。每个项目下方要么来自从业者指导，要么是这个技能自己的惯例。

- 原型和级别在书面命名，并且汇报线和执行赞助人在起草角色定义之前被锁定，否则没有赞助人就没有招聘需求（来源）。
- 角色定义命名问题和结果，而不是工具，并且必须项限制在 5-7 个（来源）。
- 4-6 个能力；每个问题映射到 exactly 一个；每个能力由 exactly 一个面试阶段拥有（来源）。
- 每个锚点都携带一个特定于角色的行为描述，并且每个提交的分数都引用一个引用或具体示例（来源）；裸数字未通过此检查。
- 流程最多运行 3 轮加上一个大约两小时的带回家，如果未支付则为 3 小时上限（来源）。
- 工作样本评分标准在第一个提交之前存在；其数值点值遵循这个技能自己的惯例。
- 入职计划基于资历和原型分支，以监控区域结束，并设定诚实的里程碑时间线 - 60-90 天内早期胜利，12 个月以上的收入水平结果（来源）。
- 资料包中的每个薪酬数字都携带其来源和日期；没有虚构的范围，没有覆盖来源不涵盖的地区的数字（自我设定）。
- 资料包提供的每个选项菜单 - 配置文件选择、工作样本格式、问题选择 - 都大声说明其顺序，删除被排除的选项而不是降级，并针对这家公司的自身背景重新排名一个（自我设定）。

## 常见失败模式

按此表每个预防措施删除多少表格内容进行排名，最佳比率第一：`承诺的执行赞助人 > 原型诊断 > 阶段映射和独立评分 > 防守的入职日历`。前两个每个成本一次对话，并在招聘需求开放之前预购前四行；其余是流程和入职纪律，只有在这两个坚持之后才会开始产生收益。

| 症状                                                 | 根本原因                                                       | 修复                                                                                                       |
| ------------------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 令人印象深刻的招聘，CRM 更干净，预测仍然不稳定      | 原型不匹配 - 为流程问题招聘系统管理员 | 重新运行配置文件选择测试；问题“从来不是软件；它是收入运动”                                                    |
| 招聘人员在会议中花费数月，然后辞职              | 指令不明确 - 三位高管各自认为他们拥有招聘  | 在招聘需求开放之前编写章程、结果和单一赞助人                                                              |
| 每个改进都变成谈判                 | 没有执行赞助人                                             | 在开放招聘需求之前，直到一位 VP 或 C 级赞助人在书面形式上承诺为止                                             |
| 第 90 天被工单队列消耗                 | 没有防守的日历或指令                                  | 明确保护入职时间；将工单队列捕获命名为监控区域                                                              |
| 面试小组的所有人都问相同的问题                    | 没有阶段映射                                                     | 一个能力，一个阶段；为每个面试小组员分配一个车道                                                            |
| 简报集中在第一个自信的声音上          | 分数在讨论之前共享                               | 独立评分在讨论之前；在简报时间上花费时间，在分数分歧的地方                                                        |
| 强势候选人因缺少认证而被拒绝  | 供应商认证设置为必须项                                   | 认证是基本要求，而不是预测 - 除非系统原型公司在标准化平台上，否则不是必须项                                |
| 精美的面试官，工作表现薄弱                   | 流程奖励完美而不是方法                                  | 工作样本加上红/绿方法锚点；弱点和强点的答案在方法上不同，而不是信心                                             |
| 最佳候选人拒绝带回家的练习                   | 长时间未支付的练习选择不投入时间的候选人               | 限制在 2-3 小时，考虑支付，并将信号转移到简报                                                              |
| 良好的招聘人员在第六个月被推出去，没有收入影响 | 不切实际的 时间线                                             | 事先设定诚实的里程碑 - “任何在 30 天内承诺收入影响的销售都在向您推销”                                        |

## 调用示例

- "我们是一家拥有 40 名员工的 A 轮 B2B SaaS 公司，CRM 系统混乱，没有人相信预测 - 帮助我确定工作范围并招聘我们的第一位 RevOps 人员。"
- "我在一个现有的五人运营团队中有一个 RevOps 分析师职位空缺 - 建立面试流程、评分卡，以及一个真正能测试工作的带回家的练习。"
- "我们的新收入运营总监将在三周后开始工作 - 编写 30-60-90 天的入职计划。"
