# 清洁架构框架

一种结构化软件的纪律性方法，使业务规则保持独立于框架、数据库和交付机制。在设计系统架构、审查模块边界或提供依赖管理建议时，请应用这些原则。

## 核心原则

**源代码依赖必须指向内部——指向更高级别的策略。** 内圈中的任何东西都不能知道外圈中的任何东西。这条单一规则产生了可测试且独立于框架、UI、数据库和任何外部机构的系统。业务规则才是重要的；数据库、Web框架和交付机制只是细节——当细节依赖于策略时，你可以推迟决策、更换实现，并在隔离状态下测试业务逻辑。

## 评分

**目标：10/10。** 对于架构满足的七个快速诊断行数（0-7）得一分，然后映射到0-10分范围：6-7满足 = **9-10**（依赖规则成立，业务逻辑独立于框架和数据库）；4-5 = **6-8**（核心可测试，但一些细节向内泄漏）；2-3 = **3-5**（框架或持久化决定了结构）；0-1 = **0-2**（没有边界——业务规则存在于控制器和ORM模型中）。报告分数、失败的诊断行以及修复每个问题的具体反转。

### 1. 依赖规则和同心圆

**核心概念：** 将架构组织为同心圆——实体（企业业务规则）最内部，然后是用例（应用程序业务规则），然后是接口适配器，框架和驱动器最外部。源代码依赖始终指向内部。

**为什么有效：** 当高级别策略不依赖于低级别细节时，你可以更换数据库、Web框架或API样式而无需触摸业务逻辑——系统对堆栈中最易变的部分具有弹性。

**关键洞察：**
- 内圈不能提及外圈名称——没有来自外部的类、函数、变量或数据格式
- 跨越边界的数据必须以最方便内圈的形式存在，而不是由外圈规定
- 依赖反转（接口定义内部，实现外部）是执行规则的机制
- 圈数是固定的——四个是典型的；规则保持不变
- 框架是细节，不是架构——它们属于最外层

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **层方向** | 内圈定义接口；外圈实现 | `UserRepository` 接口在用例中；`PostgresUserRepository` 在适配器中 |
| **数据跨越** | DTO跨越边界，不是ORM实体 | 用例返回 `UserResponse` DTO，而不是ActiveRecord模型 |
| **依赖方向** | 导入箭头始终指向内部 | 控制器导入用例；用例从不导入控制器 |

当内圈导入指向外部，并且你需要四圈代码演练、数据跨越规则和四步依赖反转程序来修复它时，请参阅 `[references/dependency-rule.md](references/dependency-rule.md)`。

### 2. 实体和用例

**核心概念：** 实体封装企业范围的业务规则——即使没有软件也会存在的规则。用例包含特定于应用程序的规则，这些规则协调数据到实体和从实体流出的流程。

**为什么有效：** 将业务做什么（实体）与应用程序如何协调它（用例）分开，可以跨应用程序重用实体，而无需更改核心业务规则即可更改应用程序行为。

**关键洞察：**
- 实体不是数据库行——它们是封装关键业务规则的类或纯函数
- 用例接受请求模型并返回响应模型——从不使用框架对象
- 每个用例是一个单个的应用程序操作（`CreateOrder`，`ApproveExpense`）
- Interactor模式：用例类实现输入边界接口并调用输出边界接口
- 对用例的更改不应影响实体；实体的更改可能会传播到用例

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **实体设计** | 关键业务规则，零框架依赖 | `Order.calculateTotal()` 应用税率规则；不知道HTTP |
| **请求/响应** | 简单数据结构跨越边界 | `CreateOrderRequest { items, customerId }`——没有ORM模型 |
| **单一职责** | 每个用例一个操作 | `PlaceOrder`，`CancelOrder`，`RefundOrder` 作为单独的类 |
| **Interactor** | 实现 Input Port，调用 Output Port | `PlaceOrderInteractor implements PlaceOrderInput` |

当设计Interactor或决定什么属于实体而不是用例时，请参阅 `[references/entities-use-cases.md](references/entities-use-cases.md)`——包含企业与应用程序业务规则处理的完整请求/响应模型示例。

### 3. 接口适配器和框架

**核心概念：** 接口适配器在用例/实体方便的形式和外部机构要求的格式之间转换数据。框架和驱动器是最外层——与外部世界的粘合代码。

**为什么有效：** 当Web框架、ORM或消息队列被限制在最外圈时，更换任何它们都是局部更改。数据库是细节；Web是细节；细节应该是业务规则的插件，而不是应用程序的骨架。

**关键洞察：**
- 控制器将HTTP转换为用例输入；呈现器将用例输出转换为视图模型
- 网关实现由用例定义的存储库接口——内圈定义合同，外圈履行合同
- 业务规则永远不会知道数据是否存在于SQL、NoSQL或平面文件中，或交付是否为HTTP
- 对框架持怀疑态度——它们想让你与它们耦合；保持距离

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **Controller** | 交付机制 → 用例输入 | `OrderController.create(req)` 构建 `CreateOrderRequest`，调用Interactor |
| **Presenter** | 用例输出 → 视图模型 | `OrderPresenter.present(response)` 格式化为JSON/HTML |
| **Gateway** | 存储库接口按DB实现 | `SqlOrderRepository implements OrderRepository` |
| **框架边界** | 框架调用内部，反之则不 | Express路由处理程序调用控制器；控制器从不导入Express |

当连接控制器、呈现器或网关，或争论数据库/Web是细节时，请参阅 `[references/adapters-frameworks.md](references/adapters-frameworks.md)`——涵盖插件架构以及如何将框架限制在边缘。

### 4. 组件原则

**核心概念：** 组件是部署的单位。三个内聚原则管理组件内部的元素；三个耦合原则管理组件之间的关系。

**为什么有效：** 组成不良的组件会创建涟漪效应，其中一次更改会迫使重新部署不相关的代码；这些原则使更改局部化，并使发布独立。

**关键洞察：**
- REP（重用/发布等效性）：组件中的类必须是可版本化和可发布的单元
- CCP（共同关闭）：同时以相同原因更改的类应放在一起——组件的SRP
- CRP（共同重用）：不要迫使用户依赖于他们不使用的类
- ADP（无环依赖）：组件图必须没有循环——用DIP或新组件打破它们
- SDP（稳定依赖）：依赖方向应稳定
- SAP（稳定抽象）：稳定的组件应该是抽象的；不稳定的应该是具体的

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **组件分组** | 将一起更改的类分组（CCP） | 所有与订单相关的用例在一个组件中 |
| **打破循环** | 应用DIP反转依赖边 | 提取接口到新组件以打破循环 |
| **稳定性指标** | 不稳定性I = Ce / (Ca + Ce) | 许多传入，没有传出依赖 → I接近0（稳定） |

当将类分组到可部署组件或打破依赖循环时，请参阅 `[references/component-principles.md](references/component-principles.md)`——每个REP、CCP、CRP、ADP、SDP、SAP都通过不稳定性指标进行了处理。

### 5. SOLID原则

**核心概念：** 五个类和模块级别的原则——单一职责、开闭、里氏替换、接口隔离、依赖反转——使依赖规则成为可能的中间层构建块。

**为什么有效：** 每个原则都针对依赖出错的具体方式，防止代码库变得僵化、脆弱且难以移动，从而成为遗留噩梦。

**关键洞察：**
- SRP：模块只有一个更改的原因——它服务于一个参与者（不是“做一件事”）
- OCP：通过添加新代码而不是修改现有代码来扩展行为——策略和插件模式
- LSP：子类型必须可以通过基本接口使用，而客户端不知道——由意外异常或忽略的方法违反
- ISP：客户端不应依赖于他们不使用的方法——胖接口会创建不必要的耦合
- DIP：高级别模块和低级别模块都依赖于高级别模块定义的抽象

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **SRP违反** | 类服务于多个参与者 | `Employee` 处理工资（CFO），报告（COO），持久化（CTO） |
| **OCP通过策略** | 新行为通过新类 | 添加 `ExpressShipping` 实现 `ShippingStrategy`；`Order` 未更改 |
| **LSP违反** | 子类型更改预期行为 | `Square extends Rectangle` 打破 `setWidth()`/`setHeight()` 合同 |
| **ISP应用** | 将胖接口拆分为角色接口 | `Printer`，`Scanner`，`Fax` 而不是 `MultiFunctionDevice` |
| **DIP接线** | 高级别定义接口；低级别实现 | `OrderService` 依赖于 `PaymentGateway`，而不是 `StripeClient` |

当将SRP/OCP/LSP/ISP/DIP应用于特定类或诊断违规时，请参阅 `[references/solid-principles.md](references/solid-principles.md)`——每个原则都通过代码示例和它防止的气味进行了处理。

### 6. 边界和边界解剖

**核心概念：** 边界是事物之间的一条线，这些事物重要，而其他事物是细节，通过多态实现：依赖指向内部，而控制流可以双向跨越。

**为什么有效：** 每个边界都提供了推迟决策或更换实现的选择；战略边界位置决定了系统是维护的乐趣还是痛苦。

**关键洞察：**
- 全边界在两边使用互惠接口；部分边界使用更简单的策略或外观
- Humble Object模式：将边界代码拆分为难以测试的部分（靠近边界）和易于测试的部分（逻辑）
- 服务不是自动的架构边界——具有胖共享数据模型的微服务是具有网络调用的单体
- 测试是最隔离的组件：它们依赖内部，没有依赖它们
- 过早的边界很昂贵，但缺少的边界也很昂贵——在可能易变的地方绘制它们

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **全 vs. 部分边界** | 互惠端口，或一个单独的策略 | 用例定义 `PlaceOrderInput`/`PlaceOrderOutput`；更简单的案例采用 `ShippingStrategy` |
| **Humble Object** | 将可测试逻辑与基础设施分开 | `PresenterLogic`（可测试）产生 `ViewModel`；`View`（humble）渲染它 |
| **Main作为插件** | 组合根组装系统 | `main()` 线接所有具体实现并启动应用程序 |

当决定在哪里绘制边界，选择全 vs. 部分，或应用Humble Object模式时，请参阅 `[references/boundaries.md](references/boundaries.md)`——还涵盖了服务作为边界、测试边界和Main作为终极插件。

## 常见错误

| 错误 | 为什么失败 | 修复 |
|------|-----------|------|
| **ORM泄漏到业务逻辑** | 实体与模式耦合；DB更改重写业务规则 | 将领域实体与持久化模型分开；在适配器层映射 |
| **业务规则在控制器中** | 无HTTP无法测试；跨端点重复 | 将逻辑移至用例Interactors；控制器仅翻译和委托 |
| **框架优先架构** | 框架决定结构；交换意味着重写 | 将框架视为插件；按业务功能结构代码 |
| **组件循环依赖** | 更改不可预测地传播；无法独立发布 | 应用DIP或提取共享抽象组件 |
| **每个功能一个巨大的用例** | 肿胀的千行协调器 | 分割为专注的单个操作用例 |
| **跳过边界“因为很简单”** | 耦合无声积累，直到成本巨大 | 主动在可能易变的地方绘制边界 |
| **微服务作为自动良好架构** | 分布式单体比清洁单体更糟 | 在服务和跨服务内应用依赖规则；服务是部署边界，不是架构边界 |

## 快速诊断

| 问题 | 如果没有 | 操作 |
|------|---------|------|
| 能否无DB、Web服务器或框架测试业务规则？ | 规则与基础设施耦合 | 提取实体和用例到接口后；模拟外部层 |
| 所有源依赖是否指向内部？ | 依赖规则违反 | 引入边界接口；反转违规依赖 |
| 能否无业务逻辑更换数据库？ | 持久化向内泄漏 | 存储库模式；在适配器中隔离持久化 |
| 用例是否独立于交付机制？ | 用例知道HTTP/CLI/队列 | 用例签名中使用纯DTO |
| 框架是否限制在最外层？ | 框架是你的架构 | 在接口后包装框架调用；推向边缘 |
| 组件图是否无环？ | 存在循环依赖 | 应用ADP：DIP或新组件打破每个循环 |
| Main（组合根）是否连接所有依赖？ | 内圈实例化具体类 | 将构造移至Main；使用DI或工厂 |

## 关于作者

**Robert C. Martin（“Uncle Bob”）** 是一位自1970年以来一直编程的软件工程师，敏捷宣言的共同签署人，以及 *Clean Code*、*The Clean Coder*、*Clean Architecture* 和 *Clean Agile* 的作者。他的SOLID原则是面向对象设计中基础词汇，他的工作认为架构是管理依赖关系并将业务规则独立于基础设施细节。
