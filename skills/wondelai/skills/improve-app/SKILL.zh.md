# 改进应用

应用已经发布并且可以运行——用户、界面、实际流程——但在应该轻松的地方体验却感觉粗糙。经过九个阶段，这次旅程修复了用户感受到的问题，按证据顺序：重新锚定应用的任务，消除摩擦，打磨外观和时刻，锐化措辞，诚实地说服，并以足够残酷的审查结束。它是交互式的（代理在决定前询问），并且可以恢复（状态存在于 `docs/` 中）。代码级别的因果关系导向代码旅程——这次修复了产品体验。

## 核心原则

**按证据顺序修复用户感受到的问题：重新锚定应用被雇佣的任务，在打磨前消除摩擦，锐化措辞，诚实地说服，并以足够残酷的审查结束。** 在令人困惑的流程上更漂亮的屏幕以相同的速率失去用户——阶段的顺序是整个游戏。

这项技能对阶段进行排序，提出决策问题，并记录你的决定。九个组成技能承载了方法——调用它们而不是即兴创作它们的框架。

## 运行规则

1. **首先恢复。** 在做任何事之前，阅读 `docs/IMPROVE-APP-PLAN.md` 和旅程地图中的每个产出物。如果存在跟踪器，用 3-5 行总结旅程状态，并询问进入哪个阶段。当用户确认了入口点时完成。带有跟踪器的旅程是恢复，而不是重新开始。
2. **仅在第一次运行时进行信息收集。** 没有跟踪器：运行下面的信息收集，然后创建 `docs/IMPROVE-APP-PLAN.md`，并将每个阶段的状态标记为 `pending | in-progress | awaiting-evidence | done | deferred: 原因 | skipped: 原因`。当跟踪器存在并且用户确认了阶段计划时完成。
3. **阶段入口。** 宣布：阶段的作用，它强迫的决策，它产生的产出物，粗略的工作量。提供继续 / 跳过 / 延迟——标记为 GATE 的阶段可以被延迟，但永远不能跳过。在继续时将阶段标记为 `in-progress`。当用户做出选择时完成。
4. **技能调用和回退。** 加载阶段的技能并使用它：每个阶段的调用行命名技能的缩写——使用该技能来运行阶段。如果它不可用，提供：`npx skills add wondelai/skills/<slug> --global`。如果用户拒绝，从它的简要信息运行阶段——最小的可行方法。说明你处于哪种模式。
5. **阶段内的决策。** 提问“与用户一起决策”下的每个问题——提供具体的选项和你的建议。在跟踪器的关键决策中记录选择。无声做出的决策是缺陷。
6. **阶段退出。** 在写入之前，展示草稿产出物内容以供批准。批准后：写入或扩展 docs/ 文件，更新跟踪器（状态、关键决策、下一步行动）。当文件写入并且阶段行显示 `done` 时完成。
7. **产出物纪律。** 写在阅读之前；如果文件缺失则创建，否则扩展——添加或更新你的部分，保留其他人的。文件在 `docs/` 中是大写的。每个建议都作为复选框或带有所有者和优先级的表格行落地。在创建 docs/ 文件时查看 [references/artifact-templates.md](references/artifact-templates.md)——从完整骨架（所有部分标题）创建它，然后填写你的阶段名称的部分。
8. **在重新设计之前提供证据；说服保持诚实。** 没有未经审计或来自阶段 1-3 的证据行的 UI 或文案更改可以发布——没有证据的更改会回到审计。每个发布的更改都与一个预提交的指标一起出现在 docs/EXPERIMENTS.md 中。应用中的稀缺提示、社会证明声明和升级承诺必须是真实的——用你有证据的技巧替换任何需要编造证据的技巧。

## 信息收集

在创建跟踪器之前询问这些问题：

1. **应用是什么，以及用户雇佣它来做什么工作——用他们的语言？** （锚定阶段 1；控制每个后续阶段。）
2. **在哪里感觉最粗糙**——令人困惑的屏幕、死气沉沉的交互、业余的 UI、薄弱的文案、强硬的升级提示或反应迟钝？ （设置入口阶段并提前加载修复阶段。）
3. **你有什么证据**——录制、支持票证、评论、漏斗流失、使用分析？ （“没有”将路由到可选的持续发现阶段。）
4. **应用运行在哪些平台**——网页、原生 iOS、两者？ （控制阶段 8 和可选 ios-hig-design；没有带有平滑原生性能的浏览器表面会跳过阶段 8。）
5. **哪些应用内表面销售或升级**——付费墙、升级提示、试用提示、徽章——并且稀缺和社会证明声明今天是否真实？ （范围阶段 7 和诚实护栏。）
6. **哪个流程流失的用户最多或产生最多的票证？** （针对阶段 2-3、5 和 8。）
7. **你已经有定位、设计或客户文档** (POSITIONING.md, DESIGN.md, CUSTOMER.md) 吗？ （阶段 1、4、6、7 建立在它们之上。）

阶段跳过启发式：没有浏览器表面和流畅原生速度时跳过阶段 8；没有应用内升级表面时跳过阶段 7；当 UI 已经在灰度上以一致的标记比例清晰可读时跳过阶段 4；当应用内文案已经具体且无行话时跳过阶段 6。永远不要跳过阶段 1——它瞄准了其他每个阶段（延迟它，不要跳过它）。然后从模板创建 `docs/IMPROVE-APP-PLAN.md` 并确认计划。当 `docs/IMPROVE-APP-PLAN.md` 存在并且每个阶段的状态都被标记并且用户确认了计划时完成。

## 阶段

### 阶段 1 — 重新锚定应用被雇佣的任务（jobs-to-be-done）— GATE

**目的：** 在任何屏幕更改之前命名用户雇佣应用的任务以及在哪里未能充分履行；阶段 2-9 只能修复审计或阶段 1-3 标记的问题。

**简要（回退）：** 客户雇佣产品是为了在特定情况下取得进展。将工作陈述为“当 [情况]，我想 [动机]，以便 [结果]”——永远不命名应用；每个工作有三个维度（功能、情感、社会），省略一个就会失去用户为什么继续。跟踪首次使用与重复使用（大雇佣 vs 小雇佣），并映射替代方案，包括非消费和即兴创作的解决方案。

**调用：** 使用 `jobs-to-be-done` 技能，应用、其使用数据和最粗糙的流程。询问工作陈述、三个维度以及应用在每个维度上未能充分履行的地方，以及用户切换到的替代方案。

**与用户一起决策：** (1) 确认工作陈述在没有产品名称的情况下也能读懂。 (2) 哪个未能充分履行的维度最差——功能、情感或社会？ (3) 漏洞是大型雇佣（入职）还是小型雇佣（日常使用）失败？

**产出物：** 扩展 docs/CUSTOMER.md `## 工作陈述`，`## 工作维度`（功能/情感/社会，每个都有其未能充分履行的注释），以及 `## 竞争性替代方案`（替代方案 | 为什么雇佣 | 弱点，包括非消费）。更新跟踪器。

**完成时：** 工作在没有产品名称的情况下被陈述，所有三个维度都带有未能充分履行的注释，替代方案被记录，并且阶段 1 显示为完成——只有到那时阶段 2-9 才被解锁。

### 阶段 2 — 移除让用户思考的摩擦（ux-heuristics）

**目的：** 削减导致用户流失的流程的认知负荷——找到界面让人们停止并困惑的地方。

**简要（回退）：** “不要让我思考”——用户扫描、满足和勉强通过。对尼尔森的 10 个启发式进行启发式评估；对每个问题评分 0-4 并按严重性 × 用户遇到它的频率排序，所以灾难性优先于装饰性。对关键屏幕（什么应用、什么屏幕、我的选项、我在哪里、搜索在哪里？）应用树干测试，删除一半的单词然后再次删除一半，并使用内联验证和说明什么、为什么和如何的错误消息修复表单。

**调用：** 使用 `ux-heuristics` 技能在最高流失流程上，以及阶段 1 的工作和维度。询问严重性评分的评估、每个关键屏幕的树干测试结果，以及重写的标签、表单和错误文案。

**与用户一起决策：** 哪些严重性 4 和 -3 的问题现在修复而不是积压？确认修复按严重性 × 频率运行，而不是按容易程度。

**产出物：** 扩展 docs/DESIGN.md `## UX 审计发现`（问题 | 启发式 | 严重性 0-4 | 修复 | 状态）；将每个修复追加到 docs/EXPERIMENTS.md `## 实验积压` 并带有 ICE。更新跟踪器。

**完成时：** 每个问题都带有 0-4 严重性和修复，树干测试在每个关键屏幕上通过或被记录，并且严重性 4 的问题有所有者。

### 阶段 3 — 设计消除错误（design-everyday-things）

**目的：** 让错误行为困难，让每个结果可读——用户做出错误行为的地方，是因为设计误导了他们，而不是用户。

**简要（回退）：** 没有人类错误，只有糟糕的设计。桥接两个鸿沟：执行（“我该如何做？”）与清晰的指示符和约束（日期选择器而不是自由文本，提交在有效之前禁用）；评估（“发生了什么？”）与 0.1 秒内的反馈和可见的系统状态。区分滑倒（正确意图，错误动作）和错误（错误意图）；优先考虑撤销而不是确认对话框，并编写错误消息说明什么出错了以及如何修复它，永远不要责备。

**调用：** 使用 `design-everyday-things` 技能，在核心流程（入职、主要操作、破坏性行为）上。询问薄弱的指示符、约束使错误不可能的地方、反馈差距和消息重写。

**与用户一起决策：** 哪里应该用约束替换错误消息，以及哪里应该用撤销替换确认对话框？

**产出物：** 扩展 docs/DESIGN.md `## UX 审计发现`（启发式 = 诺曼鸿沟；问题 | 严重性 0-4 | 修复 | 状态）；将修复追加到 docs/EXPERIMENTS.md `## 实验积压`。更新跟踪器。

**完成时：** 每个核心流程都有指示符/约束/反馈修复记录，错误消息符合什么/为什么/如何清单，并且破坏性行为提供撤销。

### 阶段 4 — 让外观清晰如工作（refactoring-ui）

**目的：** 给屏幕一个专业的视觉层次结构，以便没有任何业余的东西破坏你刚刚修复的流程。

**简要（回退）：** 伟大的 UI 是系统，而不是才能。首先用灰度设计：在颜色之前用大小、重量和对比度建立层次结构——结合杠杆，而不是乘法（三个都只为一个英雄元素）。强制执行间距比例（4/8/16/24/32/48/64），其中组之间的间隙大于组内的间隙；将文本限制为 45-75 个字符，将表单限制为 300-500 像素。最后添加颜色：每个色调 5-9 个阴影，灰色调色，而不是纯黑色。

**调用：** 使用 `refactoring-ui` 技能，在关键屏幕上，以及阶段 2-3 的发现和当前设计标记。询问灰度层次结构通行证、间距比例校正、系统化调色板和确切的标记/CSS 变化。

**与用户一起决策：** 在当前设计系统内修复还是引入新标记？确认颜色工作要在灰度布局可读后进行。

**产出物：** 扩展 docs/DESIGN.md `## 标记`（间距比例 · 调色板阴影 · 阴影）和 `## 组件`（组件 | 决策 | 状态）；将修复追加到 docs/EXPERIMENTS.md `## 实验积压`。更新跟踪器。

**完成时：** 关键屏幕在灰度上可读，间距比例已应用，每个屏幕都有一个主要操作占主导地位，并且标记决策被记录。

### 阶段 5 — 让每个操作感觉生动（microinteractions）

**目的：** 给用户每天触摸的时刻提供反馈，将他们忍受的产品与他们会爱的产品区分开来。

**简要（回退）：** 每个微交互有四个部分——触发器、规则、反馈、循环和模式。常见的失败是缺少或晚反馈：直接操作需要在 100 毫秒内响应，通常通过动画用户触摸的元素（按钮按下“保存中…”），而不是单独的吐司。映射每个状态——空、加载、部分、满、错误、禁用——并使用最少的反馈来传达，按事件的重要性缩放。

**调用：** 使用 `microinteractions` 技能，在最常用的交互（保存、提交、切换、删除、加载）上。询问触发器/规则/反馈/循环审计、每个需要的确切反馈、完整状态映射和一个标志性时刻。

**与用户一起决策：** (1) 首先要打磨哪些交互。 (2) 值得额外工艺的一个标志性时刻——应用去除测试：如果没有它，产品会感觉实质上更差吗？

**产出物：** 扩展 docs/DESIGN.md `## 微交互清单`（交互 | 触发器/规则/反馈/循环 | 修复 | 状态）；将修复追加到 docs/EXPERIMENTS.md `## 实验积压`。更新跟踪器。

**完成时：** 每个审计的交互都有其四个部分和所需反馈记录，每个状态都被映射，标志性时刻通过去除测试，并且修复是带有状态的行。

### 阶段 6 — 锐化应用内的措辞（made-to-stick）

**目的：** 让用户在应用中阅读的文案——入职、空状态、错误、CTA、工具提示——具体、清晰且无行话。

**简要（回退）：** 克服知识的诅咒：一旦你知道产品，你就无法想象不知道它。对关键应用内文案进行 SUCCESs（简单、意外、具体、可信、情感、故事）评分。具体胜过抽象：“用户每天打开应用 8 次”，而不是“增加参与度”。简单是指挥官的意图——屏幕必须落地的一件事；如果标签需要手册，重写标签。

**调用：** 使用 `made-to-stick` 技能，加上入职文案、空状态、错误字符串、CTA 和工具提示以及阶段 1 的工作语言。询问每个表面的 SUCCESs 评分，具体的去行话重写，以及每个屏幕的指挥官意图。

**与用户一起决策：** 哪些抽象变成哪些具体具体，以及每个屏幕必须落地的是什么？

**产出物：** 扩展 docs/POSITIONING.md `## 关键信息`（表面 = 应用内屏幕 | 信息 | 状态）带有 SUCCESs 评分和具体重写；将文案测试追加到 docs/EXPERIMENTS.md `## 实验积压`。更新跟踪器。

**完成时：** 每个应用内表面都有一个 SUCCESs 评分和一个具体重写，行话已消失，每个屏幕的指挥官意图被命名，并且信息按表面记录。

### 阶段 7 — 在决策点诚实地说服（influence-psychology）

**目的：** 让应用内的营销表面——付费墙、升级提示、试用提示、社会证明、徽章——用真实证据而不是技巧来说服。

**简介（备用）：** 人们通过思维捷径做决定——七个原则能触发“同意”：互惠、承诺、社会认同、权威、喜好、稀缺性、一体感。在用户做决定的地方（付费墙、升级、试用结束）应用这些原则；叠加原则，保持每个声明真实，保持决定可撤销。伦理门槛：任何编造的证据、虚假的稀缺性或隐藏成本的不良模式都是不合格的——这种策略只有在用户不知道策略是操控而非说服时才有效。

**调用：** 在引入阶段使用 `influence-psychology` 技能。询问每个决定点适合哪些原则、每个原则的诚实文案，以及可撤销性检查——标记任何需要你未掌握证据的提示。

**与用户一起做决定：** (1) 每个界面上的主导原则是什么。(2) 对于每个稀缺性或社会认同提示：今天它是否真实？如果不是，则在发货前删除或使其真实。

**产出物：** 扩展 `docs/POSITIONING.md` 中的 `## 关键信息`（界面 | 文案 | 状态），添加说服性文案；在 `docs/EXPERIMENTS.md` 中的 `## 实验待办` 中为每个变更排队，并记录它应该影响的指标。更新追踪器。

**完成条件：** 每个升级界面都命名了主导原则和诚实文案，每个稀缺性/社会认同声明都被验证为真实或删除，决定可撤销，变更已作为实验排队。

### 第 8 阶段——让用户接触的地方感觉快速（高性能浏览器）

**目的：** 解决用户感觉的交互和入口视图的延迟——速度是体验的一部分，而不是后端才考虑的细节。

**简介（备用）：** 延迟，不是带宽，是瓶颈——大多数痛苦在于往返次数过多。针对字段指标：关键交互的 INP 小于 200ms（打断长任务，延迟非关键 JS），入口视图的 LCP 小于 2.5s（预加载英雄图，提高 fetchpriority），CLS 小于 0.1（用明确尺寸预留空间）。对于剩余的真实延迟，用骨架屏和乐观 UI 隐藏它，以便界面在服务器响应之前就做出反应。

**调用：** 在最慢的关键交互和入口视图上使用 `high-perf-browser` 技能，如果有可用，则使用跟踪或 Lighthouse 运行。询问 INP 长任务、LCP 元素、布局偏移源，以及按影响排序的修复列表，包括骨架屏或乐观 UI 的应用位置。

**与用户一起做决定：** 首先要测量哪些交互和视图，并确认字段指标目标作为不可逾越的底线。

**产出物：** 扩展 `docs/DESIGN.md` 中的 `## UX 审计发现`（启发式 = 性能；问题 | 严重性 0-4 | 修复 | 状态），添加 INP/LCP/CLS 行；将修复追加到 `docs/EXPERIMENTS.md` 中的 `## 实验待办`。更新追踪器。

**完成条件：** INP/LCP/CLS 基线作为性能行记录，目标已设定（INP < 200ms，LCP < 2.5s，CLS < 0.1），并且每个修复按影响排序，延迟存在时注明骨架屏/乐观 UI 回退。

### 第 9 阶段——提交给残酷、诚实的审查（乔布斯设计审查）

**目的：** 在“极好或未完成”的冷评估下评判整个体验——并决定要删除什么。

**简介（备用）：** 从客户体验开始并逆向工作。像新用户一样冷体验产品，命名它必须做的唯一一件事，计算到核心价值的步骤数，并给出二元裁决，附带排名的删除和修复列表。聚焦是说“不”——每个功能都是删除候选。审查围栏后面：空状态、错误文案、404、计费、取消、收据邮件——都按英雄屏标准执行。

**调用：** 在第 1-8 阶段后对整个应用使用 `steve-jobs-design-review` 技能。要求进行冷体验、唯一一件事、到核心价值的步骤数、二元裁决、排名的删除和修复列表，以及围栏后面的审查。

**与用户一起做决定：** (1) 接受删除列表——要删除哪些功能。(2) 围栏后面的修复现在与后来发货。

**产出物：** 扩展 `docs/PRODUCT.md` 中的 `## 结果路线图`（结果/问题 | 满足的工作 | 优先级 | 状态），将删除和修复作为优先级行添加；将任何围栏后面的修复追加到 `docs/DESIGN.md` 中的 `## UX 审计发现`；将即将发货的修复排队到 `docs/EXPERIMENTS.md` 中的 `## 实验待办`。更新追踪器。

**完成条件：** 记录裁决，同意每个项目的删除处理，删除和修复是 `## 结果路线图` 中的优先级行，追踪器关闭第 9 阶段。

## 常见错误

| 错误 | 修复 |
|---|---|
| 在删除摩擦之前打磨视觉效果——在混乱流程上的美丽屏幕以相同的速率失去用户。 | 首先运行第 2-3 阶段（ux-heuristics, design-everyday-things）；没有第 1-3 阶段的发现，不进行视觉变更。 |
| 在灰度布局工作之前添加颜色。 | 灰度优先，颜色最后；如果屏幕在去饱和状态下失败，则调色板无法挽救它（refactoring-ui）。 |
| 将“用户错误”视为用户的错，并堆叠更多警告。 | 用约束防止错误，用撤销原谅它们，而不是用确认对话框（design-everyday-things）。 |
| 从团队外部无人测试的内部语言重写文案。 | 对抗 SUCCESs 过程进行去技术化，然后将重写作为 EXPERIMENTS 卡片发货，而不是猜测（made-to-stick）。 |
| 升级提示中的虚假稀缺性或编造的社会认同。 | 每个稀缺性提示和推荐信必须真实；用你拥有的证据替换任何需要编造证据的技巧（influence-psychology）。 |
| 发货修复并跳过残酷的端到端审查。 | 像新用户一样冷运行第 9 阶段；二元裁决和排名的删除列表会捕捉到分阶段修复遗漏的内容（steve-jobs-design-review）。 |

- [ ] `CUSTOMER.md` 重新锚定工作，并命名应用在每个维度上表现不足的地方。

转发路由：当体验保持良好，目标转向习惯、留存和增长循环时，继续使用 `grow-app` 技能。当审计持续打击代码级原因（慢查询、崩溃、不可测试模块）时，继续使用 `improve-code-quality` 或 `remove-technical-debt` 技能。当营销网站是下一个最薄弱的界面时，继续使用 `improve-website` 技能。
