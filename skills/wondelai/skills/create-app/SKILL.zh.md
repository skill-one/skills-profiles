# 创建应用程序

将一个原始的应用程序想法转化为一个经过验证、架构清晰的第一版，并以可持续的节奏发布——而不会为了尚未获得的规模而过度构建，或者编写一个固化成重写的原型。这段旅程分为十个阶段：它在每个决策之前都会提问，并将每个选择记录在 `docs/` 中，以便您可以在不同会话中停止和继续。早期的阶段通常不会产生任何代码；一旦实验批准构建，工程阶段就会构建出真正的东西。

## 核心原则

**快速验证同时保持选择开放：尽早做出难以逆转的决策，并将所有廉价的事情推迟。** 将稀缺的早期精力投入到少数几个复合的事情上——最危险的假设、依赖边界、领域语言——并在其他地方积极避免浪费。

这项技能排序阶段、提出问题并记录决策；构成技能承载着方法。调用它们，而不是即兴创作它们的框架。

## 运行规则

1. **首先继续。** 在做任何事之前，阅读 `docs/CREATE-APP-PLAN.md` 和旅程地图中的每个产出物。如果存在跟踪器，请用3-5行总结旅程状态，并询问进入哪个阶段。当用户确认了入口点时完成。带有跟踪器的旅程是继续，而不是重新开始。
2. **仅在第一次运行时进行摄入。** 没有跟踪器：运行下面的摄入，然后创建 `docs/CREATE-APP-PLAN.md`，并将每个阶段的状态标记为 `pending | in-progress | awaiting-evidence | done | deferred: reason | skipped: reason`。当跟踪器存在并且用户确认了阶段计划时完成。
3. **阶段入口。** 宣布：阶段的作用、它强制的决策、它产生的产出物、粗略的工作量。提供继续 / 跳过 / 推迟——标记为 GATE 的阶段可以推迟，但不能跳过。在继续时将阶段标记为 `in-progress`。当用户选择时完成。
4. **技能调用和回退。** 加载阶段的技能并使用它：每个阶段的调用行通过slug命名技能——使用该技能来运行阶段。如果不可用，提供：`npx skills add wondelai/skills/<slug> --global`。如果用户拒绝，从其简要中运行阶段——最低可行方法。说明您处于哪种模式。
5. **阶段内的决策。** 提问“与用户共同决策”下的每个问题——提供具体的选项和您的建议。在跟踪器的关键决策中记录选择。无声做出的决策是缺陷。
6. **阶段退出。** 在写入之前，展示草稿产出物内容以供批准。批准后：写入或扩展 docs/ 文件，更新跟踪器（状态、关键决策、下一步行动）。当文件写入并且阶段行显示 `done` 时完成。
7. **产出物纪律。** 写在阅读之前；如果文件缺失，则创建，否则扩展——添加或更新您的部分，保留其他人的部分。文件在 `docs/` 中是大写的。每个建议都作为复选框或带有所有者和优先级的表格行出现。在创建 docs/ 文件时查看 [references/artifact-templates.md](references/artifact-templates.md)——从完整骨架（所有部分标题）创建，然后填写您的阶段命名的部分。
8. **代理准备和处理；只有人类与客户和测试用户交谈。** 起草冲刺脚本和访谈指南并评分结果，然后暂停状态 `awaiting-evidence`，直到用户返回笔记。ios-hig-design 阶段仅当发布原生iOS应用时适用；否则在摄入时跳过它。

## 摄入

在创建跟踪器之前询问这些问题：

1. 应用程序想法用一句话是什么，它背后的最危险的信念是什么？（Gates Phase 1；如果应用程序所做的工作模糊不清，请添加工作要做的可选阶段。）
2. 根本想法是否已经通过行为证据验证，还是仍然是一个猜测？（未验证的高风险使 Phase 1 成为强制性；如果已经存在付费客户，您可能处于错误的旅程——改进应用或增长应用。）
3. 阶段是什么——周末原型、资助构建以发布，还是围绕它形成的团队？（原型依赖于 Phases 1-3 和 10；正在形成的团队可以添加 inspired-product。）
4. 您会发布原生iOS客户端吗？（是保留 Phase 8；不跳过它。）
5. 您有客户可以交谈，还是必须找到他们？（Gates Phases 1-2 中的人类证据循环和可选 mom-test / 持续发现。）
6. 您期望前几个月的负载——每日活跃用户和每日操作？（为 Phase 7 容量数学提供信息，并阻止过早的扩展。）
7. 独立构建还是团队，谁拥有发布节奏？（Gates Phase 9 塑形。）

阶段跳过启发式：当核心流程已经测试或简单时跳过 Phase 2；除非发布原生iOS，否则跳过 Phase 8；仅当负载明显很小时才跳过 Phase 7——但仍然记录估计；对于周末原型，将 Phases 3-6 作为一次通过运行，但永远不要跳过依赖规则。

然后从模板创建 `docs/CREATE-APP-PLAN.md`，将每个阶段的状态标记，并将 Phase 8 标记为 iOS-条件。当 `docs/CREATE-APP-PLAN.md` 存在，每个阶段都标记状态，并且用户确认了计划时完成。

## 阶段

### Phase 1 — 验证最危险的假设 (lean-startup)

**目的：** 证明如果错误，将杀死应用程序的信念——在编写生产代码之前。

**简要（回退）：** 向后计划 Build-Measure-Learn：您必须学习什么，您将如何知道，最小的构建是什么可以找出。按什么致命而不是容易测试来对跳跃假设进行排序。MVP 是一个学习工具，通常很粗糙（Dropbox 通过视频而不是同步引擎验证）。爬上验证阶梯——注册弱，付费存款强，活跃使用最强；目标是行为级别 4-5，而不是“您会使用这个吗？”的意见。

**调用：** 使用 `lean-startup` 技能，并带有想法，如果 CUSTOMER.md 存在，则带有工作声明。询问排序的跳跃假设、使最危险的唯一最小实验，以及预先承诺的行为成功阈值。

**与用户共同决策：** 哪个假设如果错误是致命的？哪种实验类型——烟雾测试（需求），concierge（价值），奥兹巫师（自动化）？什么 go/pivot 阈值，在运行之前固定？只有用户用真人运行它；然后暂停 `awaiting-evidence`。

**产出物：** 创建 docs/PRODUCT.md 带有 `## Vision` 和 `## MVP Definition`；创建 docs/EXPERIMENTS.md 带有 `## Experiment Cards`（EXP-001 带有假设、指标、决策规则）和 `## Experiment Backlog`。更新跟踪器。

**完成时：** 最危险的假设被命名，EXP-001 有预先承诺的阈值，PRODUCT.md 状态 MVP 范围，并且用户有实验要运行。

### Phase 2 — 降低核心体验的风险 (design-sprint)

**目的：** 使用测试过的外壳解决核心流程应该是什么，在投入工程时间之前。

**简要（回退）：** 五天：星期一映射问题，星期二绘制，星期三决定，星期四原型，星期五与五个真实用户测试。输出是一个高保真外壳加上证据，而不是代码。最危险的时刻是一个陌生人第一次十分钟——测试他们是否理解并完成核心任务，而无需解释。五个用户揭示模式；您需要模式，而不是显著性。永远不要解释原型；观察他们在哪里卡住。

**调用：** 使用 `design-sprint` 技能，并带有 PRODUCT.md 中的 MVP 范围。询问星期一的映射和 How Might We 重构，一个获胜概念故事板，和一个五幕访谈脚本带有笔记网格（每个参与者检查标记 / 交叉 / 波浪号）。在暂停时，在 docs/EXPERIMENTS.md 中的冲刺卡片下记录批准的脚本，以便它在会话中断期间幸存。

**与用户共同决策（返回时）：** 测试过的流程是否按原样工作，需要重塑，还是暴露了一个循环回 Phase 1 的需求问题？哪些困惑成为修复？

**产出物：** 创建 docs/DESIGN.md 带有 `## Design Direction`；扩展 docs/EXPERIMENTS.md `## Experiment Cards` 带有冲刺测试及其裁决。更新跟踪器。

**完成时：** DESIGN.md 记录了方向，冲刺结果和裁决在 EXPERIMENTS.md 中，并且用户选择了继续 / 重塑 / 循环。

### Phase 3 — 绘制边界 (clean-architecture)

**目的：** 隔离业务规则，使数据库、框架和提供者保持可互换的细节。

**简要（回退）：** 源代码依赖指向内部——框架指向用例指向实体。业务规则不得导入框架或 ORM。用例定义接口（例如 InvoiceRepository）；基础设施实现它们；控制器将 HTTP 请求转换为纯请求对象并接收纯响应——不要跨越边界跨越框架类型。诊断：您能否在没有数据库、Web 服务器或框架运行的情况下测试业务规则？四个圆圈是典型的，而不是神圣的——仅在波动点绘制边界。

**调用：** 使用 `clean-architecture` 技能，并带有 PRODUCT.md 中验证的 MVP 范围。询问层映射、核心用例及其请求/响应模型，以及它依赖的存储库接口。

**与用户共同决策：** 真实的波动边界在哪里（数据库、第三方API、交付机制）？完整的四层，或者对于小应用程序折叠适配器和框架？

**产出物：** 创建 docs/ARCHITECTURE.md 带有 `## System Context` 和 `## Layer Map & Dependency Rule`（层、什么依赖于什么、违规表格）。更新跟踪器。

**完成时：** ARCHITECTURE.md 命名了层，Dependency Rule 方向是明确的，核心业务规则可以在没有基础设施的情况下测试。

### Phase 4 — 域建模 (domain-driven-design)

**目的：** 使代码说出业务，以便领域专家可以阅读并发现哪里有问题。

**简要（回退）：** 模型是代码。构建一个通用语言——根据领域概念命名事物，而不是技术角色（InvoiceDraft.finalize() 击败 DataProcessor.process()）；难以命名是一个设计信号。边界上下文：一个词在一个边界内意味着一个东西（“Customer”在计费中不必等于“Customer”在支持中）。聚合：一个具有一个根的集群，它强制不变性——保持它们小，通过ID引用其他聚合。避免贫血模型；将行为推入实体和值对象。

**调用：** 使用 `domain-driven-design` 技能，并带有 ARCHITECTURE.md 的层映射。询问通用语言、边界上下文和上下文映射，以及核心聚合及其根强制的不变性的核心聚合。

**与用户共同决策：** 核心域是什么（您的竞争优势）与通用子域（认证、电子邮件、支付）相比是购买或使用开源的？同一个词在不同的上下文中是否真正意味着不同的东西？

**产出物：** 扩展 docs/ARCHITECTURE.md：添加 `## Bounded Contexts & Context Map` 和 `## Domain Glossary (Ubiquitous Language)`（术语 | 含义 | 代码名称）。更新跟踪器。

**完成时：** 涵盖表命名了核心概念，上下文和关系被映射，并且存储库接口根据 Phase 3 位于域层。

### Phase 5 — 编写可读的代码 (clean-code)

**目的：** 随着代码库的增长，保持每个函数可读和经过测试。

**简要（回退）：** 代码比编写得多得多。小函数做一件事，在单个抽象级别；意图揭示名称；没有标志参数（一种气味——函数做两件事）；命令与查询分离；一个命名良好的提取函数比注释更好。测试是一流的——脏测试比没有好。按 F.I.R.S.T.（快速、独立、可重复、自我验证、及时）编写行为命名测试，例如 shouldRejectNegativeTotal。

**调用：** 使用 `clean-code` 技能，并带有 Phase 3-4 的核心模块。询问针对规则的评分和修复审查以及核心用例的干净单元测试（安排-行动-断言、描述性名称、构建器辅助）。

**与用户共同决策：** 什么质量标准控制提交——函数大小、名称清晰度、没有吞没的异常？哪些 happy-path 和故障情况必须第一个测试覆盖？

**产出物：** 创建 docs/TESTING.md 带有 `## Test Strategy`（金字塔、工具、什么绿色门）和 `## Safety Net Map`（模块 | 固定的行为 | 测试文件 | 缺口）。更新跟踪器。

**完成时：** TESTING.md 状态了策略，核心用例有通过行为命名的测试，不需要数据库，并且提交质量标准被记录。

### Phase 6 — 安装元纪律 (pragmatic-programmer)

**目的：** 采用保持代码库多年易于更改的习惯。

**简要（回退）：** 发射一个跟踪子弹——每个层（UI 到用例到数据库和返回）的一个薄的真正切片，保持它，以在第二天发现集成错误。DRY 仅适用于知识，而不是偶然的相似性。正交性：更改数据库不得触及 UI。可逆性：将第三方 SDK 背靠您自己的接口，以便 Stripe 或模型提供者可以交换而不会触及业务逻辑。破损的窗户：修复第一个黑客或用跟踪的票证将其围起来——永远不要留下无声的腐烂。

**调用：** 使用 `pragmatic-programmer` 技能，并带有 ARCHITECTURE.md 和核心用例。询问最薄的端到端跟踪子弹设计和每个第三方依赖的适配器接口。

**与用户共同决策：** 跟踪子弹是什么？破损的窗户政策是零容忍并带有跟踪的票证吗？哪些依赖现在获得适配器接口，而不是以后？

**产出物：** 扩展 docs/TESTING.md (`## CI Gates`) 和 docs/TECH-DEBT.md (`## Debt Budget & Broken-Windows Policy` 和 `## Adopted Conventions`)。更新跟踪器。

**完成时：** 跟踪子弹端到端指定，为每个提供者命名适配器接口，并且破损的窗户政策被写下来。

### Phase 7 — 诚实地确定大小 (system-design)

**目的：** 估计真实的负载并证明您不需要构建什么。

**简要（回退）：** 从需求开始，而不是解决方案。QPS = 每日活跃用户 x 每日操作 / 86,400，峰值 2-5 倍平均；存储 = 每日记录数 x 记录大小 x 保留。对于几百个用户，数学几乎总是说一个索引良好的数据库加上缓存。按顺序扩展：垂直首先，然后读取副本，然后缓存旁路，最后分片。只有在估计或真实瓶颈证明它值得时，才使用队列来吸收峰值并解耦慢速工作（例如照片 OCR）与请求路径。

**调用：** 使用 `system-design` 技能，并带有摄入的负载数字。询问后见 QPS 和存储估计，以及明确列出您现在不需要的技术。

**工件：** 扩展 docs/ARCHITECTURE.md：添加 `## 数据与存储决策` 和 `## 决策日志`（日期 | 决策 | 原因 | 拒绝的替代方案），将每个“尚未”记录为决策。更新追踪器。

**完成时间：** 当容量估算被记录、延迟扩展技术被明确列出，并且任何缓存或队列都有数据支持时。

### 第 8 阶段 — 让它感觉原生 (ios-hig-design) — 仅限 iOS

**目的：** 使 iPhone 客户端感觉原生 — 这是 iOS 用户信任的基础。仅在交付原生 iOS 客户端时运行（在需求阶段决定）；否则跳过。

**简介（备用）：** 三个支柱 — 清晰性、顺从性、深度。尊重安全区域（动态岛、主屏幕指示器）；每个触摸目标至少 44x44 pt；语义颜色（Color(.label)、Color(.systemBackground)）以便自动适应暗黑模式；语义文本样式用于动态类型；原生导航 — 标签栏用于主要目的地，NavigationStack 用于下钻，弹出层用于专注任务，绝不使用汉堡菜单。无障碍设计是首要考虑：每个控件都有标签，并且 VoiceOver 可以完成每个任务。

**调用：** 使用 `ios-hig-design` 技能针对应用的关键屏幕。请求对安全区域、44pt 目标、语义颜色和类型、原生导航以及无障碍标签进行 HIG 审查。

**与用户决定：** 哪些屏幕是第一次审查的范围？任何有意的平台偏差，以及它们是否合理？

**工件：** 扩展 docs/DESIGN.md：添加 `## 组件`（组件 | 决策 | 状态）和 `## 用户体验审计发现`（问题 | 准则 | 严重性 0-4 | 修复 | 状态）。更新追踪器。

**完成时间：** 每个范围内的屏幕都被审查、发现被记录并标记严重性、无障碍差距被捕获为修复。

### 第 9 阶段 — 按节奏发布 (37signals-way)

**目的：** 在固定时间内发布一个专注的 v1 版本，以对抗功能蔓延。

**简介（备用）：** 建造半个产品，而不是半途而废。在投入之前塑造工作：粗糙到足以实现设计自由，解决足够的问题以消除大的未知数，有明确的范围（“这值得两周”）——而不是估算。固定时间并缩减范围以适应，绝不能反过来。将塑造的提案投入固定周期；一个断路器会在截止日期时终止任何未完成的工作。有观点的软件：每个提供的偏好都是一个拒绝的决策——选择合理的默认值；对功能的默认答案是尊重的“现在不考虑”。

**调用：** 使用 `37signals-way` 技能针对 PRODUCT.md 中的 MVP 范围。请求将下一个功能塑造为提案（问题、范围、原型、陷阱、禁区）和 v1 切片列表。

**与用户决定：** 下一个功能的范围是什么？哪些 v1 功能被裁剪，哪些用户可见的偏好成为有观点的默认值？

**工件：** 扩展 docs/PRODUCT.md（`## 结果路线图`）和 docs/STRATEGY.md（`## 禁止列表` — 我们明确不会做的事情）。更新追踪器。

**完成时间：** 下一个功能有一个带有范围的提案、v1 切片列表在 STRATEGY.md 的禁止列表中、路线图反映了固定时间/灵活范围。

### 第 10 阶段 — 将复杂性视为敌人 (software-design-philosophy)

**目的：** 在每个模块中控制复杂性——这是所有其他阶段的视角。

**简介（备用）：** 复杂性是任何关于结构使系统难以理解和更改的东西。优先考虑深度模块——强大的功能背后是简单的接口——而不是浅层模块；根据功能除以接口复杂度来评估模块，而不是行数。这纠正了 Clean Code 的“小”和 DDD 的许多概念滑入类itis（一大群只有一个方法的浅类）。战略优先于战术：在设计中稳定投资 10-20% 的额外时间，因为早期的捷径在团队和代码库增长时会成倍增加。

**调用：** 使用 `software-design-philosophy` 技能针对第 3-6 阶段的模块。请求深度与浅度的评估，标记浅类、传递方法、跨边界的信息泄漏，以及合并位置。

**与用户决定：** 哪些浅层模块应该合并到更深的模块中？在哪里战术捷径累积的债务值得现在的战略 10-20%？

**工件：** 扩展 docs/TECH-DEBT.md（`## 味觉清单`：味觉 | 位置 | 重构 | 状态）和 docs/ARCHITECTURE.md（`## 决策日志`）。更新追踪器。

**完成时间：** 浅层模块和泄漏被记录在味觉清单中、合并决策被记录、战略与战术立场被同意。

## 常见错误

| 错误 | 修复 |
|---|---|
| 在验证想法之前构建架构 | 首先运行第 1 阶段——验证是廉价的，重写不是 (`lean-startup`)。 |
| 将“MVP”视为写垃圾的许可 | 发布最小的事情来学习，然后在获得批准后构建真正的东西——最小不是低质量 (`lean-startup`)。 |
| 让框架决定架构 | 将框架作为插件保留在外层；没有 ORM 类型跨越用例边界 (`clean-architecture`)。 |
| 脆弱的领域模型 | 将行为推入实体和值对象，而不是胖服务类 (`domain-driven-design`)。 |
| 类itis——过度应用“小” | 根据深度（每单位接口的功能性）而不是行数来评估模块 (`software-design-philosophy`)。 |
| 预先扩展 | 做估算；一个数据库加上一个缓存足以让大多数应用远行——最后切片 (`system-design`)。 |
