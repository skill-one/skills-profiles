# 设计代码架构

设计新应用的架构：确保少数昂贵的、难以逆转的决定是正确的，并在其他地方保持激进简化。这是一个包含八个阶段的交互式、可中断的旅程——代理在做出每个决定前都会询问并记录结果在你的项目的 `docs/` 文件夹中，因此你可以在任何阶段停止并稍后继续。它从最基础且最难逆转的部分（边界、领域）开始，经过可调优的部分（数据、弹性），到整个过程中你应用的跨领域规范（复杂性、可逆转性、范围）。一个周末项目只需轻量使用三个阶段；一个为发布而组建的团队则需要整个技术栈。

## 核心原则

**架构是一组昂贵的、难以逆转的决定：刻意做出这些决定，并将所有廉价的部分推迟。** 这种技能按顺序排列阶段、提出决策问题，并将每个选择记录在 `docs/` 中。构成技能承载着方法——调用它们而不是即兴创作它们的框架。整个策略是将昂贵的决定转化为廉价的决定，通过在它们前面设置边界，使不可再简化的昂贵集合保持足够小，以便小心地将其纠正。

## 操作规则

1. **首先中断。** 在做任何事之前，阅读 `docs/DESIGN-CODE-ARCHITECTURE-PLAN.md` 和旅程地图中的每个产出物。如果存在追踪器，请用 3-5 行总结旅程状态并询问进入哪个阶段。当用户确认入口点时完成。带有追踪器的旅程是中断的，而不是重新启动的。
2. **仅在第一次运行时进行信息输入。** 没有追踪器：运行下面的信息输入，然后创建 `docs/DESIGN-CODE-ARCHITECTURE-PLAN.md`，将每个阶段的状态标记为 `pending | in-progress | awaiting-evidence | done | deferred: reason | skipped: reason`。当追踪器存在且用户确认阶段计划时完成。
3. **阶段入口。** 宣布：阶段的作用、它强制的决定、它产生的产出物、粗略的工作量。提供继续 / 跳过 / 推迟——标记为 GATE 的阶段可以推迟，但永远不能跳过。在继续时将阶段标记为 `in-progress`。当用户做出选择时完成。
4. **技能调用和回退。** 加载阶段的技能并使用它：每个阶段的调用行通过 slug 命名技能——使用该技能运行阶段。如果不可用，提供：`npx skills add wondelai/skills/<slug> --global`。如果用户拒绝，从其简要信息运行阶段——最小可行方法。说明你处于哪种模式。
5. **阶段内的决定。** 询问“与用户一起决定”下的每个问题——提供具体选项和你的建议。在追踪器的关键决定中记录选择。无声做出的决定是缺陷。
6. **阶段退出。** 在写入之前，展示草稿产出物内容以供批准。在批准后：写入或扩展 docs/ 文件，更新追踪器（状态、关键决定、下一步行动）。当文件写入且阶段行显示 `done` 时完成。
7. **产出物规范。** 写入前阅读；如果文件不存在则创建，否则扩展——添加或更新你的部分，保留其他人的部分。文件在 `docs/` 中为大写。每个建议都作为复选框或带有所有者和优先级的表格行出现。创建 docs/ 文件时，请参阅 [references/artifact-templates.md](references/artifact-templates.md)——从完整骨架（所有部分标题）创建它，然后填写你的阶段命名的部分。
8. **任何昂贵的、难以逆转的决定在代码假设它之前都会得到一个决策日志行（决定、原因、拒绝的替代方案）。** 默认为模块化单体：服务仅在经过验证的边界上下文中分割。

## 信息输入

在创建追踪器之前询问这些问题：

1. 应用将做什么，以及什么功能是你们真正的竞争优势？（为第二阶段的核子子域框架——在哪里进行深度建模与购买现成产品）
2. 你们倾向于哪个技术栈——语言、Web 框架、ORM、数据库？（为第一阶段边界和第四节数据决定设置门槛；被视为细节，而不是骨架）
3. 第一年的实际负载是多少——粗略的日活跃用户和每个用户采取的主要操作？ （为第三阶段规模设置门槛：需求在解决方案之前）
4. 它将调用哪些出站依赖项——支付、电子邮件、LLM API、运输、队列？ （为第六节集成点审计设置门槛）
5. 哪些数据是系统的记录，是否存在第二读取模式，如搜索、分析或信息流？ （为第四节一致性和派生数据决定设置门槛）
6. 是否有人验证了人们确实想要这个应用？（如果没有，请先路由到创建业务 / 创建应用——不要架构一个未经验证的想法）
7. 将有多少团队拥有这个系统，以及你们现在想要旅程的多少？ （为团队拓扑可选阶段和第八节需求设置门槛）

阶段跳过启发式方法：当第一年负载远低于任何阈值时（单个索引数据库是答案——记录它并继续前进），跳过第三阶段的扩展机械和第四节的大部分复制；对于单团队应用，跳过团队拓扑可选阶段。永远不要跳过第一阶段或第二阶段——边界和领域模型是使每个后续决定廉价的加成工作；一旦存在真实用户和出站调用，第六节弹性不是可选的。然后从模板创建追踪器并确认计划。

当 `docs/DESIGN-CODE-ARCHITECTURE-PLAN.md` 存在且每个阶段的状态都已确认，并且用户已确认计划时完成。

## 阶段

阶段按列表顺序运行，从最难逆转到可调优再到跨领域——每个阶段都假设前一个阶段的产出物存在。根据操作规则，任何阶段都可以进入、跳过或推迟；第一阶段和第二阶段是使之后所有决定廉价更改的加成工作。

阶段形成一个与系统镜像的依赖链：领域驱动设计说边界属于哪里（上下文和聚合接缝）；干净架构说依赖项如何跨越它们；数据密集型应用决定持久化层中哪些内容存在于其中；系统设计说实际需要多少基础设施——通常远低于恐惧。软件设计保持模块深度而不是乘以浅层仪式，Release It! 硬化集成点，务实程序员提供保持结构随时间推移的跨领域习惯，而 37signals 方式通过固定时间和削减范围来管理整个事情。

### 第一阶段——绘制边界（clean-architecture）

**目的：** 使业务规则独立于框架、数据库和供应商，以便每个后续决定保持可交换——这是买回所有其他工作的移动。

**简要信息（回退）：** 依赖规则——源代码依赖指向内部：框架 → 接口适配器 → 用例 → 实体；内部不命名任何外部内容。数据库、网络和供应商是细节，是你们规则的插件。通过依赖反转强制执行：用例拥有仓库接口；Postgres/Stripe 实现存在于外部适配器中。只在真实波动点（数据库、外部服务、交付）绘制完整边界；在其他地方折叠层——方向很重要，不是文件夹数量。

**调用：** 使用 `clean-architecture` 技能，使用从信息输入获取的具体第一个功能和技术栈。要求它分层该功能（实体、具有请求/响应模型的用例、仓库+网关接口、外环中的 HTTP 控制器和数据库适配器），并标记哪些边界是仪式而不是在真实波动点赚取成本。

**与用户一起决定：** (1) 模块化单体与服务——默认为具有干净内部边界的模块化单体；具有共享数据模型的微服务是分布式单体，严格更差。 (2) 哪些波动点现在获得完整边界接口，而不是折叠层。

**产出物：** 创建 docs/ARCHITECTURE.md，包含 `## 系统上下文`（做什么，集成）、`## 层级图 & 依赖规则`（层级、什么依赖于什么；违规 | 位置 | 修复 | 状态），以及模块化单体与服务的选择在 `## 决策日志`（日期 | 决定 | 原因 | 拒绝的替代方案）。更新追踪器。

**完成时：** 层级图存在，第一个功能使用框架/ORM 类型限制在外环，核心设计为在没有数据库/网络/框架的情况下进行测试，模块化单体与服务的决定是决策日志行，第一阶段显示 `done`。

### 第二阶段——建模领域（domain-driven-design）

**目的：** 在业务实际分割的地方绘制边界，并使代码使用领域——现在最便宜，从空白页发明词汇。

**简要信息（回退）：** 模型是代码——构建通用语言，使团队词汇成为代码词汇。命名领域概念（`Order.place()`，而不是 `OrderManager.process()`）；一个抵制命名的名称是设计信号，而不是烦恼。边界上下文：一个区域，一个词精确地意味着一件事（“Customer”在计费与支持中不同）——这些是你们未来的服务接缝。聚合：一个小型根集群强制执行不变量，内部立即一致，外部最终一致；通过 ID 引用其他聚合。将行为推入实体——没有贫血数据包。

**调用：** 使用 `domain-driven-design` 技能，使用领域词汇和第一阶段层级图。要求构建基于团队实际使用的词汇的边界上下文映射，核心聚合及其不变量，以及子域分类（核心 / 支持性 / 通用）。

**与用户一起决定：** (1) 同一个词在不同上下文中真正意味着不同的事情——不要统一成一个全知的模型。 (2) 哪个子域是核心（进行深度建模）与通用（购买或使用 OSS——认证、电子邮件、支付）。

**产出物：** 扩展 docs/ARCHITECTURE.md：`## 边界上下文 & 上下文映射`（上下文、关系、反腐败层）和 `## 领域词汇表（通用语言）`（术语 | 含义 | 代码名称）；记录聚合和核心领域选择在 `## 决策日志`。更新追踪器。

**完成时：** 上下文映射了它们的关系，词汇表命名了核心术语，每个聚合都声明了它的不变量和通过 ID 引用，核心子域被选择，上下文边界与第一阶段层级图一致。

### 第三阶段——诚实地调整系统大小（system-design）

**目的：** 用数字证明系统可以有多小，以便跳过你们无法证明的机械。

**简要信息（回退）：** 从需求开始，而不是解决方案。草稿估算：QPS = 日活跃用户 × 每日操作 ÷ 86,400，峰值 2-5× 平均；存储 = 记录/天 × 大小 × 保留。对于数百到数千用户，单个索引数据库加上读取路径缓存可以带你们走得很远。按顺序扩展：垂直优先，然后缓存旁路（TTL + 显式失效），然后读取副本，最后分片，只有有证据时。为缓慢/尖峰工作寻找消息队列来解耦，为全球静态资源寻找 CDN。过早分片和过早服务分割是命名错误。

**调用：** 使用 `system-design` 技能，使用从信息输入获取的负载现实。要求平均和峰值 QPS、年度存储、哪个组件首先瓶颈，以及你们现在不需要的简单列表（分片、副本、CDN、队列、多区域）。

**与用户一起决定：** 哪些扩展移动现在要做而不是推迟——与数字相关（不要为 50k 用户构建，而你们只有 50），以及如果有，第一个缓慢的工作负载要移动到消息队列后面。

**产出物：** 扩展 docs/ARCHITECTURE.md `## 系统上下文` 与负载现实和草稿估算数字；记录每个扩展移动（现在采用 / 推迟触发器）在 `## 决策日志`。更新追踪器。

**完成时：** 平均/峰值 QPS 和年度存储被写下来，第一个瓶颈被命名，并且每个扩展技术要么有理由采用，要么有触发器推迟。

**调用：** 使用 `software-design-philosophy` 技能，配合第 1-2 阶段提出的模块集。询问哪些模块是浅层传递，需要整合；哪些模块存在知识泄露；以及是否有任何计划中的边界只是形式而非实质。

**与用户共同决定：** 哪些浅层模块要整合到更深层模块中，同时避免过度合并真正无关的模块；团队采用的设计规范（命名、行为存放位置、每个知识点一个文件）。

**产出物：** 扩展 docs/TECH-DEBT.md 中的 `## Smell Inventory`（应用整合后的浅层模块/知识泄露条目），并将商定的规则记录在 `## Adopted Conventions` 下。更新追踪器。

**完成条件：** 每个浅层模块簇都被整合或记录了修复方案，没有单个设计决策在多个模块中重复，设计规范已书面化。

### 第 6 阶段 — 为失败设计（release-it）

**目的：** 当依赖项缓慢或宕机时，使系统优雅降级而不是崩溃——现在设计成本最低，而不是凌晨 2 点。

**简要（备用）：** 通过 QA 的软件不一定是能在生产中存活下来的。集成点是最大的杀手，缓慢的响应比没有响应更糟——悬挂依赖会耗尽线程和连接池，且在日志中无记录。不可协商：每个出站调用都有连接超时和读取超时；关键依赖项有断路器（打开时跳闸、快速失败、半开恢复）；为每个依赖项隔离连接池；带退避和抖动的重试。每个列表端点分页（无界结果集在真实数据下会崩溃）；安排稳态清理。用特性标志和向后兼容的扩展-收缩迁移将部署与发布解耦。

**调用：** 使用 `release-it` 技能，配合摄入阶段的出站依赖项。询问每个依赖项的超时值和断路器阈值、连接池位置、每个集成的优雅降级路径，以及深度健康检查 + RED 指标 + 扩展-收缩迁移的要素。

**与用户共同决定：** 断路器阈值、哪些依赖项获得专用连接池、当非关键依赖项宕机时核心流程如何降级，以及你信任的回滚路径。对于前千名用户，抵制混沌工程/多区域故障转移。

**产出物：** 创建 docs/RELIABILITY.md，包含 `## Integration-Point Audit`（依赖项 | 超时 | 断路器 | 连接池 | 重试策略 | 状态）、`## Query & Resource Findings`、`## Health Checks & Metrics` 和 `## Deploy vs Release`。更新追踪器。

**完成条件：** 每个计划的出站调用都有超时，关键依赖项有断路器和连接池，每个列表端点都已分页，指定了深度健康检查 + RED 指标 + 扩展-收缩迁移 + 可信赖的回滚，且审计对关键路径没有开放行。

### 第 7 阶段 — 证明连接并固化习惯（pragmatic-programmer）

**目的：** 通过每个层级的单薄真实切片来证明边界连接，并设定保持架构可逆的习惯。

**简要（备用）：** 快速测试——构建一个单薄但完全真实的垂直切片（HTTP → 用例 → 仓库 → 数据库 → 后端），作为生产代码保留，用于第二天端到端的反馈，并在充实它们之前证明边界连接。可逆性：将每个供应商隐藏在你自己的接口后面（分叉道路测试——你能在一周内更换数据库或 LLM 提供商吗？）。正交性：一个需求的大幅改变只影响一个模块。为知识而非巧合的 DRY——合并重复的规则，保留相似的规则。破损窗户：修复第一个 Hack 或用跟踪票证将其封上。

**调用：** 使用 `pragmatic-programmer` 技能，配合第 1 阶段的边界。询问最薄的端到端快速测试（执行每层）、每个供应商的适配器接口，以及一个审计，显示一个改变会影响多个模块或供应商 API 会泄露到业务逻辑。

**与用户共同决定：** 哪个切片是快速测试（一个经过身份验证的核心操作、最小功能）；破损窗户政策和每个迭代的债务预算；哪些供应商首先获得拥有的接口。

**产出物：** 扩展 docs/TESTING.md `## Test Strategy`、`## Safety Net Map`（快速测试路径作为第一个端到端测试）、和 `## CI Gates`；扩展 docs/TECH-DEBT.md `## Debt Budget & Broken-Windows Policy` 和 `## Adopted Conventions`（可逆性、正交性）。更新追踪器。

**完成条件：** 快速测试切片端到端地运行过每层，并被固定为第一个 CI 门禁，每个供应商都位于拥有的接口后面，破损窗户政策和债务预算已书面化。

### 第 8 阶段 — 将范围削减到必要（37signals-way）

**目的：** 决定是否发布任何内容——修复时间，灵活范围，并在它成为你携带的复杂性之前删除推测性抽象。

**简要（备用）：** 构建更少——最好的产品做少但做好；半成品胜过草率的成品。修复一个胃口（这项工作真正值得的时间），并将范围削减以适应，而不是估算一个无限扩展的架构。YAGNI：每个推测性抽象（通用插件系统、事件溯源、为零用户配置的多租户）都是推迟到想象中的未来的决策，以牺牲当前复杂性为代价。做出微小的可逆决策；默认拒绝，以便伟大的决策可以呼吸。永远不要削减小集合并昂贵的可逆决策。

**调用：** 使用 `37signals-way` 技能，配合第 1-7 阶段的完整架构计划。询问它如何将工作塑造成固定的胃口，区分发布必要与镀金，命名兔子洞，并列出要删除或用最简单能工作的替换的推测性抽象。

**与用户共同决定：** v1 架构工作的胃口；哪些抽象现在要删除、推迟到重新审查触发器、或用最简单的东西替换；确认没有昂贵的可逆决策只是为节省时间而被删除。

**产出物：** 扩展 docs/ARCHITECTURE.md `## Decision Log`，记录故意不为 v1 构建的；扩展 docs/TECH-DEBT.md `## Debt Ledger`（推迟的抽象作为故意承担的债务，每个都有重新审查的触发器）。更新追踪器。

**完成条件：** v1 范围固定到胃口，每个删除或推迟的抽象都是一个 Decision Log 或 Debt Ledger 行，带有重新审查触发器，且没有昂贵的可逆决策因节省时间而被删除。

## 常见错误

| 错误 | 修复 |
|---|---|
| 让框架成为架构 | 应用 Clean Architecture 的依赖规则（第 1 阶段）——框架调用向内；ORM 和请求类型保持在最外层。 |
| 过度设计以应对无法证明需要的规模 | 首先运行后门估算 QPS/存储计算（系统设计，第 3 阶段）；一个索引数据库加上一个缓存通常可以支撑数年的发展。 |
| 过度纠正导致类itis | 应用深层模块规则（software-design-philosophy，第 5 阶段）——几个深层模块胜过大量浅层模块；只有在真实波动性时才设置边界。 |
| 忽视数据库的实际一致性保证 | 检查默认隔离级别并锁定易写倾斜路径（ddia-systems，第 4 阶段）——写倾斜通过每个单用户测试。 |
| 将弹性视为发布后的关注点 | 从一开始就设计超时、断路器和分页（release-it，第 6 阶段）——没有超时的缓慢依赖会冻结一切。 |
| 混淆无构建与草率构建 | 删除功能和推测性抽象（37signals-way，第 8 阶段），而不是小集合并昂贵的可逆决策。 |

## 完成旅程

根据项目调整剂量：一个周末构建依赖于第 1 阶段的依赖规则、快速通用语言、出站调用超时，以及第 8 阶段的削减范围本能——几小时可以节省数周。一个有资金支持的团队正在为发布构建，将整个堆栈运行，随着真实的瓶颈和集成点出现，将数据和弹性阶段拉入。

退出清单——每个框都与一个产出物关联：

- [ ] 每个昂贵的可逆决策（边界、上下文、数据/一致性）都是一个 Decision Log 行，记录了拒绝的替代方案（ARCHITECTURE.md）。
- [ ] 核心业务规则设计为在没有数据库、网络或框架的情况下运行（ARCHITECTURE.md 层级图，没有向内指向的违规）。
- [ ] 每个出站调用都有超时，关键调用有断路器，每个列表都已分页（RELIABILITY.md Integration-Point Audit 清晰）。
- [ ] 一个快速测试切片证明了边界端到端的连接，并且是第一个 CI 门禁（TESTING.md）。
- [ ] v1 范围固定到胃口，每个删除或推迟的抽象都是一个 Decision Log 或 Debt Ledger 行，带有重新审查触发器（TECH-DEBT.md Debt Ledger）。

关闭追踪器：每个阶段 `done` 或 `skipped: reason`，将剩余的 Next Actions 带入 ARCHITECTURE.md Decision Log 和 TECH-DEBT.md，以免丢失。然后转发：当架构服务于仍需验证和构建的产品时，继续使用 `create-app` 技能；当必须将现有原型提升到这种结构时，继续使用 `improve-code-quality` 技能。
