# 高效处理遗留代码

一份关于修改没有测试的代码的手册，源自迈克尔·C·菲瑟斯（Michael C. Feathers）的《高效处理遗留代码》（Working Effectively with Legacy Code）。使用它来将无法测试的类放入测试框架中，用特征化测试锁定当前行为，并逐步安全地、可验证地进行更改——而无需进行重写。

## 核心原则

**遗留代码就是没有测试的代码。** 不是旧代码，不是丑陋的代码——未经测试的代码：没有测试，你无法知道更改是否保留了行为，因此每次编辑都是一场赌博。这门手艺是打破依赖关系，在更改任何东西之前引入测试——覆盖并修改，而不是编辑和祈祷。

## 评分

**目标：10/10。** 根据以下原则对未测试代码的更改进行0-10分的评分。报告当前分数以及达到10/10所需的特定步骤。

- **9-10：** 在任何编辑之前，用特征化测试覆盖更改点；行为更改和重构作为单独的验证步骤交付；用最侵入性最小的技术打破依赖关系
- **7-8：** 在最多更改点有测试，但偶尔有重构加行为混合的提交或比需要更重的依赖关系手术
- **5-6：** 一些特征化测试，但关键路径仍然凭信仰更改；无回报计划的新生代码不断累积
- **3-4：** 编辑和祈祷，手动验证；在更改后编写测试，断言新代码碰巧做什么
- **0-2：** 直接未测试地编辑混乱的代码，重构和行为更改混合在一个提交中，提议重写而不是测试

## 框架

### 1. 遗留代码困境和更改算法

**核心概念：** 困境：要安全地更改代码，我们需要测试，但要引入测试，必须更改代码。出路是一个固定序列——识别更改点，找到测试点，打破依赖关系，编写测试，然后进行更改和重构——其中预测试编辑是保守和机械的，而真正的更改只在安全网内发生。

**为什么有效：** 编辑和祈祷用反馈代替了谨慎，而谨慎无法扩展到你不完全理解的代码。覆盖和修改用测试的夹钳锁定了现有行为，因此任何意外的更改都会立即在你的机器上显示出来，而不是在生产中后期显示。

**关键洞察：**
- 更改代码有两个原因——改变行为（功能、错误修复）和改进结构（重构）——在一步中混合它们会使故障无法诊断
- 测试点很少是更改点：效果传播，所以你通常在更改效果出现的位置测试，而不是编辑发生的位置
- 在测试存在之前进行的打破依赖关系的编辑必须精确保留签名，并依赖编译器找到每个受影响的位置
- 覆盖沿着你实际更改的路径增长——这比任何专门的“测试项目”更有优势，后者永远无法获得资金
- “编程是一门一次做一件事的艺术”：算法的每一步都是单独可验证的

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 未测试模块中的错误修复 | 在触摸错误之前运行五个步骤 | 用测试固定 `parseInvoice()`，然后修复舍入错误 |
| 混合清理和功能的PR | 分成仅结构化和仅行为的提交 | 首先提取和重命名，测试变绿，然后添加折扣规则 |
| “只是一个单行更改” | 首先找到最近的测试点 | 在调用你要编辑的私有方法的公共方法上有一个固定测试 |

在运行五个步骤对实际更改进行操作时查看 [参考资料/更改算法.md](references/change-algorithm.md)——作为工作程序，具有更改点/测试点检查表和“没有时间”情况的分诊。

### 2. 界面：在哪里拆分代码

**核心概念：** 界面是你可以在不编辑该位置的情况下更改程序行为的地方。每个界面都有一个启用点——你决定运行哪个行为。将遗留代码置于测试之下很大程度上是在寻找界面：测试可以替代慢速、全局或外部依赖关系的地方，而生产源保持不变。

**为什么有效：** 如果你必须编辑代码来测试它，你冒着改变你所试图锁定的行为的风险。界面将替换移动到远处——一个子类、一个导入、一个构建标志——所以被测试的代码与生产中运行完全一样，而测试从启用点控制其依赖关系。

**关键洞察：**
- 对象界面是面向对象代码中的默认值：每个可重写的调用都是一个界面，其启用点是对象创建或传递的位置
- 链接和导入在构建或加载时间交换实现——`jest.mock` 和 `unittest.mock.patch` 是现代服装中的链接界面
- 预处理界面（C/C++ 宏）是最粗糙的工具；最后再使用它们
- `new Database()` 在方法体内是一个从未构建过的界面——执行实际工作的构造函数、全局变量、静态变量和硬接线 I/O 是界面死亡的地方
- 没有可到达的启用点的界面是无用的：如果测试不能做出决定，继续寻找
- 动态语言使几乎每个名称查找都成为界面——便宜，但修补内部将测试与文件布局耦合

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 类构建自己的DB客户端 | 通过构造函数参数的对象界面 | `constructor(db: Db = new ProdDb())` — 测试传递一个假 |
| 模块调用顶级 `send_email()` | 导入/链接界面 | `mocker.patch("billing.send_email")` 或 `jest.mock("./mailer")` |
| 逻辑直接读取墙时钟 | 时钟界面 | 注入一个 `now()` 提供程序；测试冻结时间 |

在特定堆栈中寻找界面时查看 [参考资料/界面.md](references/seams.md)——界面目录，包括代码、启用点以及现代工具中的界面（依赖注入容器、jest.mock、pytest monkeypatch、时钟和配置界面）。

### 3. 特征化测试

**核心概念：** 特征化测试记录了代码当前实际做什么——不是规范、注释或任何人的记忆所说的应该做什么。编写一个你知道会失败的探针，让失败消息揭示真实行为，然后将断言更改为锁定该行为。

**为什么有效：** 在遗留系统中，实际行为是事实规范：调用者、报告和客户可能依赖它，包括怪癖。从想象中的需求编写的测试会因原因而失败，这些原因告诉你什么，而特征化测试在重构期间会失败，正好是在——以及在哪里——你更改了现有行为。

**关键洞察：**
- 配方：在测试框架中调用代码，断言一些荒谬的事情 (`expect(total).toBe(-1)`), 读取失败，锁定观察到的值
- 感知和分离是打破依赖关系的两个原因：分离将代码放入测试框架，感知让断言看到它计算了什么
- 对于复杂输出（报告、生成文件、大型 JSON）使用黄金主件：一次捕获完整输出，永远与它进行比较
- 快照测试是黄金主件——像代码一样审查第一个快照，并规范化易变数据，否则你正在锁定噪声
- 在特征化过程中发现了一个错误？用注释和工单锁定它——下游代码可能依赖错误的行为；稍后作为有意、单独的更改进行修复
- 特征化你的更改将触及的分支，而不是整个系统——覆盖跟随更改

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 重构一个税务计算器 | 锁定代表输入的输出 | 运行 20 个案例，断言每个记录的结果 |
| 遗留报告生成器 | 黄金主件差异 | 生成报告，与检查入的主件文件进行比较 |
| 在锁定过程中发现进位错误 | 锁定错误值，记录它 | `assert days == 30  # BUG? expected 31 — TICKET-482` |

在编写你的第一个探针到锁定套件时查看 [参考资料/特征化测试.md](references/characterization-tests.md)——黄金主件，正确执行的快照测试，以及工作前后重构。

### 4. 发芽和包装：首先没有测试进行更改

**核心概念：** 当你真诚地无法在当天将区域置于测试之下时，不要将新逻辑编织到未测试的混乱中。发芽方法或发芽类：将新行为作为新鲜、完全测试的代码编写，并从遗留位置调用它。包装方法或包装类：将旧代码放在一边并重命名，在调用它的前面或后面添加行为，装饰风格。

**为什么有效：** 即使其主机无法在测试框架中实例化，新代码在一个新鲜的方法或类中也可以是测试驱动的——测试性不再等待将主机放入测试框架。未测试的主机通过一个调用位置更改，所以未验证的爆炸半径是一个单行而不是整个方法。

**关键洞察：**
- 当新逻辑在一个点插入时使用发芽方法；当主机类甚至无法在测试框架中实例化时使用发芽类
- 包装方法适用于围绕旧代码的行为（日志记录、通知、计量），而不是与它混合：将 `pay()` 重命名为 `rawPay()`，重新创建 `pay()` 作为包装器
- 包装类是装饰器模式——当几个调用位置需要添加行为或类已经臃肿时使用它
- 对权衡要诚实：主机保持未测试；你在一个坏街区添加了良好的代码
- 将发芽作为债务跟踪，并偿还它们——下次更改到达那里时覆盖主机
- 发芽是更改算法中的一个战术移动，而不是永久替代将代码置于测试之下的方法

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 400行的 `process()` 中的滞纳金规则 | 发芽方法，一个调用行 | `total += lateFee(order)` — `lateFee()` 测试优先编写 |
| 遗留 `pay()` 周围的审计日志 | 包装方法 | 新的 `pay()` 记录，调用 `rawPay()`，再次记录 |
| 新验证，类无法实例化 | 发芽类 | `new OrderValidator().validate(data)` 从遗留代码调用 |

### 5. 打破依赖关系的技术

**核心概念：** 一个机械、低风险的移动目录，切断所有阻止实例化或感知的东西：提取接口、参数化构造函数、参数化方法、提取并重写工厂方法或获取器、引入实例委托、适应参数、拆出方法对象、子类和重写方法。因为它们在测试存在之前运行，所以始终选择最不侵入性的技术来解除阻塞。

**为什么有效：** 代码抵抗测试的原因很小——构造函数执行实际工作、静态变量和单例、无法构造的参数、怪物方法。每个障碍都有一个命名的、实践中的反移动，所以你执行一个已知的动作，而不是对没有安全网的代码进行即兴手术。

**关键洞察：**
- 参数化构造函数使用生产默认值是主力：现有调用者未经更改即可编译，而测试注入假
- 提取接口是书中最安全的移动——引入接口不能改变行为，只能放松类型
- 子类和重写方法构成了目录的一半：一个测试子类，它阻止了危险的部分，是一个合法的工具，而不是一个黑客
- 对于静态变量和单例，引入实例委托向调用者提供了一个他们可以交换的实例；静态设置可以在测试中取代单例
- 适应参数击败了对抗无法伪造的框架类型——将 `HttpServletRequest` 包装在你的窄接口中并针对该接口进行测试
- 动态语言有更便宜的界面：`unittest.mock.patch` 或 `jest.mock` 可以代替几种技术，但参数化留下了更好的设计

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 构造函数打开DB连接 | 参数化构造函数 | `def __init__(self, conn=None): self.conn = conn or connect()` |
| 静态 `Billing.charge()` 每处调用 | 引入实例委托 | 实例 `charge()` 委托给静态；测试重写它 |
| 900行方法囤积本地变量 | 拆出方法对象 | `new RateCalculation(order, rates).run()` — 本地变量成为字段 |

在特定障碍阻止实例化或感知时查看 [参考资料/打破依赖关系.md](references/dependency-breaking.md)——每个技术的 before/after 代码加上将障碍映射到正确移动的决策表。

### 6. 拆解和理解

**核心概念：** 在更改你不理解的代码之前，投资于廉价的 comprehension：效果草图跟踪更改可以影响什么，功能草图显示方法和字段如何在神类中聚集，草稿重构意味着冒险重构以学习然后丢弃编辑，讲述系统的故事迫使简化摘要。回报是找到瓶颈——狭窄的地方，几个测试覆盖了广泛的行为。

**为什么有效：** 在遗留代码中，瓶颈是理解，而不是打字。效果草图将“什么可能破坏？”从焦虑变成一个有限列表，而瓶颈让少数测试作为一个夹钳覆盖整个方法集群——通常揭示隐藏的类边界想要在哪里绘制。

**关键洞察：**
- 效果草图：每个变量或方法一个气泡，每个“影响”一个箭头——从你的更改点向前跟踪行为可以泄漏到每个地方
- 瓶颈是效果草图中的狭窄处；在那里测试，它上游的一切都被覆盖了
- 草稿重构是作为阅读技术进行的重构：提取、重命名并简化一个小时，然后还原——洞察力在签出时幸存
- 怪物方法策略：在瓶颈处黄金主件它，拆出方法对象，然后在新的类内重构
- 神类策略：功能草图集群，然后沿着它们之间的自然边界提取
- 当没有时间时进行分诊：更改一次的位置得到发芽或包装；相同的位置再次更改已经值得它的测试

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| “如果改变这个字段会破坏什么？” | 从字段向外的效果草图 | 三个读者找到；两个瓶颈测试覆盖它们 |
| 5000行类中的功能 | 瓶颈测试，然后发芽 | 覆盖 `postInvoice()`，发芽新规则作为一个类 |
| 团队中没有人理解的代码 | 在分支上进行草稿重构 | 提取和重命名以学习，还原，计划真正的移动 |

在想要一个完整的 worked walkthrough 时查看 [参考资料/案例研究.md](references/case-studies.md)——三个场景：未测试的 800 行服务中的功能，被单例困扰的模块置于测试之下，以及在错误修复之前驯服的怪物方法。

## 常见错误

| 错误 | 为什么失败 | 修复方法 |
|------|-----------|---------|
| 在一次重构中同时改变行为 | 当出现问题时，无法判断是哪个修改导致的 | 分开提交；每一步都确保测试通过 |
| 在遗留代码上编写“应该”测试 | 想象中的规范会大声失败，而你“修复”了承重行为 | 描述代码的功能；单独提交错误报告 |
| 对所有可见内容进行模拟 | 测试绑定实现，因此每次重构都会破坏它们 | 仅模拟阻止实例化或感知的内容 |
| 一次性大改而不是逐步覆盖 | 旧系统不断变化；重写会延迟交付并错过多年的边缘案例 | 逐步覆盖和修改 |
| 在描述过程中默默修复发现的错误 | 调用者和报告可能依赖于错误的行为 | 固定它，记录它，作为单独的故意更改来修复它 |
| 在没有任何测试存在之前进行侵入式清理 | 每个手动编辑都可能导致没有支撑的行为 | 使用最侵入性最少的技术；保留签名；依赖编译器 |
| 无偿地无限增长 | 主机保持未经测试，并固化成下一层遗留层 | 跟踪增长债务；在下次接触时覆盖热点 |
| 等待专门的“测试项目” | 这个项目永远无法获得资金；覆盖率永远不会出现 | 随着每次交付的增长而增长覆盖率 |

## 快速诊断

| 问题 | 如果没有 | 动作 |
|------|-------|------|
| 测试是否覆盖了你即将更改的代码？ | 你在编辑时祈祷 | 运行更改算法；在编辑前固定行为 |
| 你能在测试框架中构建这个类吗？ | 依赖项阻止了分离 | 参数化构造函数，提取接口，或增长类 |
| 测试能否感知你更改的效果？ | 效果对断言不可见 | 找到一个感知点；提取并覆盖获取器 |
| 这次提交是行为-only还是结构-only？ | 混合的 | 分开它；在两者之间运行测试 |
| 你是否知道这次更改可以影响的一切？ | 未知的影响范围 | 绘制效果草图；在关键点进行测试 |
| 你的断言是否声明了观察到的行为？ | 测试愿望 | 探测，读取失败，固定实际值 |
| 你选择的接口是否是可用的最便宜的一个？ | 不必要的手术 | 优先选择构造函数参数和导入接口 |
| 这次更改后，代码的覆盖率会更好吗？ | 下一次更改的成本与这次一样 | 在最近的测试点至少留一个固定测试 |

## 关于作者

**Michael C. Feathers** 是 R7K 研究与传达咨询公司的创始人，该公司专注于软件设计和老化系统的康复。作为一名长期从事遗留代码咨询和会议演讲的顾问，他撰写了《有效与遗留代码一起工作》（2004 年），并为该领域定义了工作定义：遗留代码就是没有测试的代码。
