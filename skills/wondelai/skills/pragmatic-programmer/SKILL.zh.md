# 实用程序员框架

源自 Hunt & Thomas 合著的《实用程序员》（20周年纪念版）中关于系统层面的软件开发技艺方法。在设计系统、评审架构、编写代码或提供建议时，请应用这些元原则——思考软件的方式，而不仅仅是编写软件的方式。

## 核心原则

**重视你的技艺。** 软件开发需要持续学习、自律实践和责任担当——实用程序员会超越眼前问题，从上下文、权衡和长期后果的角度进行思考。优秀的软件来自优秀的习惯：无情地避免重复，保持组件正交，并将每一行代码视为必须证明其价值的活资产。目标不是完美——而是易于变更、易于理解、易于信任的系统。

## 评分

**目标：10/10。** 根据七个快速诊断行进行评分：每答对一行约得1.4分（7个对=10分）。然后对结果进行分级：
- **9-10**：所有原则都成立——DRY知识、正交层、可工作的追踪切片、边界契约、无破窗、可逆的供应商/数据库选择、范围估算。
- **5-6**：存在1-2个导致实际变更努力的违规项（例如，业务逻辑与数据库耦合、单点估算）。
- **<=3**：普遍的重复、全局状态或累积的破窗——熵在胜利。

始终说明分数，列出失败的诊断行，并给出从行动列中获取的具体修复措施以达到10/10。

## 七个元原则

构建持久软件的七个原则：

### 1. DRY（不要重复自己）

**核心概念：** 系统中每一份知识都必须有单一、明确、权威的表示。DRY关注的是知识，而非代码——重复的逻辑、业务规则或配置远比重复的语法更危险。

**为什么有效：** 重复的知识必须在多个地方更改；最终会遗漏一处，引入不一致性。DRY减少了错误表面区域，使系统更易于变更。

**关键洞察：**
- DRY适用于知识和意图，而非文本相似性——两个服务于不同业务规则的相同代码块不是重复
- 四种重复类型：强加的（环境强制）、无意的（开发者未意识到）、急躁的（懒得抽象）、开发者间的重复
- 重述代码的注释违反DRY——解释*为什么*，而非*什么*
- 数据库模式、API规范和文档除非来自单一来源，否则会重复知识
- DRY的反面是WET：“写两次所有内容”或“我们喜欢打字”

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **配置值** | 单一事实来源 | 一个环境文件中的数据库连接，被到处引用 |
| **验证规则** | 共享模式 | 一个JSON模式或Zod模式用于客户端和服务器 |
| **API契约** | 从规范生成 | OpenAPI规范生成类型、文档和客户端代码 |

参见：[参考资料/dry-正交性.md](参考资料/dry-正交性.md) 当对特定重复进行分类或决定两个代码块是否代表真正相同的知识时——按类型示例和四种重复类型的缓解措施。

### 2. 正交性

**核心概念：** 如果对一个组件的更改不会影响另一个组件，则这两个组件是正交的。设计系统，使组件自包含、独立，并具有单一、明确定义的用途。

**为什么有效：** 解耦使变更局部化——一个模块中的修复不会蔓延到无关模块，因此影响范围保持受限。更改数据库层，UI不应崩溃；更改认证提供者，业务逻辑不应关心。

**关键洞察：**
- 询问：“如果我对一个函数背后的需求进行大幅更改，有多少模块受影响？”答案应该是单一
- 消除无关事物之间的影响——日志更改绝不应破坏计费
- 分层架构促进正交性：表示层、领域逻辑、数据访问
- 避免全局数据——每个全局状态消费者都与它耦合
- 强制你从其类中继承的框架会降低正交性

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **架构** | 分层分离 | 控制器 -> 服务 -> 仓库，每个都可替换 |
| **依赖项** | 依赖注入 | 传递`Notifier`接口，而非`SlackClient`具体类 |
| **测试** | 独立单元测试 | 无需数据库、网络或文件系统即可测试业务逻辑 |

参见：[参考资料/dry-正交性.md](参考资料/dry-正交性.md) 当衡量耦合或重构为解耦层时——变更影响和陌生人测试、分层架构图和直升机类比。

### 3. 追踪子弹和原型

**核心概念：** 追踪子弹是连接系统所有层级的端到端实现，功能最小化。与原型不同（原型是可丢弃的），追踪子弹代码是生产代码——薄但真实。

**为什么有效：** 追踪子弹在投资完善所有功能之前提供即时端到端反馈。用户看到真实的东西，开发者有一个可构建的框架，集成问题会及早暴露。

**关键洞察：**
- 追踪子弹：系统（UI -> API -> DB）的薄但完整的路径——你会保留它
- 原型：专注于单一风险方面的集中探索——你会丢弃它
- 当“在黑暗中射击”时使用追踪子弹——模糊的需求、未验证的架构
- 如果追踪失败，调整并再次发射——迭代的成本很低
- 清晰标记原型为可丢弃——绝不要让一个成为生产代码

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **新项目** | 垂直切片 | 一个端到端功能：按钮 -> API -> DB -> 响应 |
| **不确定技术** | 刺激原型 | 在提交前测试WebSocket性能 |
| **微服务** | 骨干架构 | 通过完整CI/CD管道的Hello-world服务 |

参见：[参考资料/追踪子弹.md](参考资料/追踪子弹.md) 当在新项目上决定追踪与原型或构建骨干架构时——黑暗中射击的决策、迭代循环和常见陷阱。

### 4. 基于契约的设计和断言式编程

**核心概念：** 通过前置条件（必须为真）、后置条件（保证为真）和不变量（始终为真）来定义和执行软件模块的权利和责任。当契约被违反时，立即大声失败。

**为什么有效：** 契约使假设明确化。而不是默默地破坏数据或处于无效状态，系统会在问题点崩溃——死程序不会说谎。

**关键洞察：**
- 前置条件：调用者的责任——“我只接受正整数”
- 后置条件：例程的保证——“我会返回一个排序列表”
- 不变量：始终为真——“账户余额永远不会为负”
- 早期崩溃：死程序造成的损害远小于受损程序
- 断言用于永远不会发生的事情；错误处理用于可能发生的事情
- 在动态语言中，通过运行时检查和守卫子句实现契约

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **函数入口** | 前置条件守卫 | 函数开始处`assert age >= 0, "年龄不能为负"` |
| **类状态** | 不变量验证 | 每次状态变更后调用`validate!` |
| **API边界** | 模式验证 | 在处理之前根据模式验证请求正文 |

参见：[参考资料/契约-断言.md](参考资料/契约-断言.md) 当向例程添加契约或决定断言与错误处理时——工作型前/后/不变量模式、动态语言守卫子句和断言与错误处理的边界。

### 5. 破窗理论

**核心概念：** 一个破窗——设计不良的代码片段、糟糕的管理决策、一个“稍后修复”的hack——开始腐化。一旦系统显示出忽视，熵会加速，纪律会崩溃。

**为什么有效：** 心理学。当代码干净时，开发者会感到社会压力保持其干净；当代码已经混乱时，添加更多混乱的阈值降为零。质量是一个团队习惯，而不是个人英雄主义。

**关键洞察：**
- 不要留下破窗（不良设计、错误决策、糟糕的代码）未修复
- 如果现在无法修复，就封起来：带有工单的TODO、禁用功能、桩件
- 成为变革的催化剂：向人们展示未来工作的缩影（石头汤）
- 观察缓慢退化（煮熟的青蛙）——监控技术债务指标随时间推移
- 第一个hack最昂贵，因为它给了后续所有hack的许可

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **遗留代码** | 封窗 | 在添加功能之前用干净接口包装糟糕的代码 |
| **代码审查** | 对新债务零容忍 | 拒绝添加`// TODO: 稍后修复`而没有工单的PR |
| **技术债务** | 债务预算 | 每个冲刺分配20%用于修复破窗 |

参见：[参考资料/破窗.md](参考资料/破窗.md) 当团队正在规范化忽视或需要推动转型时——修复策略、石头汤催化剂游戏和建立质量文化。

### 6. 可逆性和灵活性

**核心概念：** 没有最终决定。构建易于更改数据库、框架、供应商、架构和部署目标的系统——变更成本应与变更范围成正比。

**为什么有效：** 需求会改变，供应商会被收购，技术会过时。如果你的架构硬编码了关于这些的假设，每个变更都会成为重写；灵活的架构将决策视为配置，而非结构。

**关键洞察：**
- 通过你自己的接口抽象第三方依赖——绝不让供应商API泄漏到业务逻辑
- “分叉路口”测试：你能在一周内从Postgres切换到DynamoDB吗？如果不能，你耦合了
- 元数据驱动系统（配置文件、功能标志）比硬编码逻辑更灵活
- YAGNI也适用于过早抽象——在你不需要它之前不要构建灵活性
- 可逆性不是预测未来；它不是把自己画进角落

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **数据库** | 仓库模式 | 业务逻辑调用`repo.save(user)`，而不是`pg.query(...)` |
| **外部API** | 适配器/包装器 | `PaymentGateway`接口包装Stripe；稍后切换到Braintree |
| **功能标志** | 运行时切换 | 新结账流程在标志后，几秒钟内回滚 |

参见：[参考资料/可逆性.md](参考资料/可逆性.md) 当提交到供应商或框架时，或权衡决策必须多可逆——每层可逆性模式、分叉路口测试，以及何时*不*优化可逆性。

### 7. 估算和知识投资组合

**核心概念：** 通过理解范围、构建模型、分解为组件和分配范围来可靠地估算。像管理金融投资组合一样管理你的学习：定期投资、分散化、再平衡。

**为什么有效：** 诚实的估算会与利益相关者建立信任（“1-3周”胜过自信错误的“2周”）。知识投资组合使你在技术变化时保持相关性——停止学习的程序员不再有效。

**关键洞察：**
- 询问“这个估算用于什么？”——上下文决定精度（预算规划与冲刺规划）
- 使用PERT：（乐观 + 4x最可能 + 悲观）/ 6
- 分解为组件并估算每个；总和比单次猜测更准确
- 保持估算日志：比较估算与实际，并校准
- 投资组合规则：定期投资（每周学习），分散化超越你的技术栈，混合安全和投机赌注，早期学习新兴技术（低价买入）

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **冲刺规划** | 范围估算 | “3-5天”带有置信度，而不是单个数字 |
| **新技术** | 时间限制的刺激 | “2天评估；然后我可以正确估算” |
| **学习** | 每周投资 | 每周1小时学习新语言、工具或领域 |

参见：[参考资料/估算-投资组合.md](参考资料/估算-投资组合.md) 当生成你将受其约束的估算或校准过去的失误时——PERT和分解程序、估算日志校准循环，以及投资组合再平衡。

## 常见错误

| 错误 | 为什么失败 | 修复 |
|------|------------|------|
| DRY相似外观的代码，但服务于不同目的 | 将不相关的概念耦合；更改一个会破坏另一个 | 仅DRY知识，而非偶然的代码相似性 |
| 跳过追踪子弹，逐层构建 | 集成问题会晚暴露；无端到端反馈 | 首先构建一个薄的垂直切片 |
| 忽略“因为稍后会重构”的破窗 | 熵加速；永远不会来；士气下降 | 立即修复或用带工单的TODO封起来 |
| 估算作为单点承诺 | 虚假精度当错过时侵蚀信任 | 始终给出带有置信度的范围 |
| 使所有事情“灵活” | 过度设计；过早抽象没有证据 | 当你有确凿证据需要它时才添加灵活性 |
| 为“性能”移除生产断言 | 断言会捕获的bug现在会默默地破坏数据 | 保留关键断言；移除任何之前都应进行基准测试 |
| “为了方便”的全局状态 | 毁坏正交性；一切都与一切都耦合 | 使用依赖注入和显式参数 |

## 快速诊断

| 问题 | 否 | 行动 |
|------|----|------|
| 我能不触碰业务逻辑就更改数据库吗？ | 正交性违规 | 引入仓库/适配器模式 |
| 我有一个端到端切片在工作吗？ | 缺少追踪子弹 | 在扩展之前构建一个垂直切片 |
| 每个业务规则都在恰好一个地方定义吗？ | DRY违规 | 确定权威来源；删除重复项 |
| 新开发者会称这个代码库为“干净”吗？ | 存在破窗 | 安排一个专门的清理冲刺 |
| 我的估算是否包括范围和置信度？ | 估算问题 | 切换到PERT或基于范围的估算 |
| 我能在5分钟内回滚此部署吗？ | 可逆性差距 | 添加功能标志和蓝绿部署 |
| 我每周都在学习新东西吗？ | 知识投资组合停滞 | 安排每周学习时间并跟踪它 |
