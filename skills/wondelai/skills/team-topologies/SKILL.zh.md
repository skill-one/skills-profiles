# 团队拓扑结构

来自马修·斯凯尔顿（Matthew Skelton）和曼努埃尔·佩斯（Manuel Pais）的著作《团队拓扑结构》（Team Topologies）中提出的一种以团队为中心的组织设计方法：四种基本的团队类型、三种交互模式，以及对康威定律（Conway's Law）和团队认知负荷（team cognitive load）的刻意关注。使用它来构建工程组织，以实现变化的快速流动——并在系统、技术和市场变化时持续演进它们。

## 核心原则

**团队是交付的单位，组织传递其沟通结构。** 康威定律保证了系统架构会镜像团队的实际沟通方式，因此团队边界和交互必须像软件本身一样被刻意设计。根据每个团队的认知负荷来划分其职责，将大多数团队与业务变化的流对齐，声明团队如何交互，并将由此产生的拓扑结构视为一个优化的快速流动的动态架构决策。

## 评分

**目标：10/10。** 根据以下原则对组织和团队设计进行0-10分的评分。报告当前分数以及达到10/10所需的特定更改。

- **9-10：** 流对齐团队拥有按认知负荷大小划分的端到端切片；平台、赋能和复杂子系统团队仅存在以减少该负荷；交互模式是明确的，并且会刻意演变
- **7-8：** 大部分流对齐，有一个真正的平台，但有一些共享所有权、未声明的交互模式或一个过载的团队
- **5-6：** 团队类型命名，但边界按技术层划分；协作无边界；平台采用是强制的
- **3-4：** 到处都是组件团队；工单驱动的共享服务；每个变更都会跨越多个团队
- **0-2：** 组织忽视了康威定律：基于项目的 staffing 淘汰，"每个人都与每个人都交谈"，没有认知负荷的概念

## 框架

### 1. 康威定律与反向康威策略（Inverse Conway Maneuver）

**核心概念：** "任何设计系统的组织都会产生一个其结构是组织沟通结构的副本的设计"（Mel Conway）。组织沟通和系统架构是同构的——它们通过强制而非隐喻而镜像彼此。反向康威策略利用这一点：确定你想要的架构，然后塑造团队及其沟通路径，使架构成为自然结果。

**为什么有效：** 团队只能构建它们能够协调的接口，因此组织可以发现的设计空间受其沟通路径的限制。重塑组织会重塑系统；对抗康威定律会产生永久性的摩擦和架构侵蚀。

**关键洞察：**
- 接口在团队沟通的地方出现；在它们不沟通的地方出现缝隙——系统记录了你的组织的对话
- 实际的沟通结构（聊天、代码审查、会议邀请）驱动架构，而不是组织结构图
- "每个人都与每个人都交谈"会产生混乱的系统：无约束的沟通意味着无约束的耦合
- 设计良好的组织需要*更少*的跨团队沟通，而不是更多——广泛的跨团队闲聊表明边界错误，而不是健康的协作
- 任何塑造团队、汇报线或招聘的人都正在做出架构决策——架构师必须与组织共同设计，重组需要架构审查
- 当目标架构和团队结构冲突时，团队结构会获胜

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 目标架构 | 首先设计团队；期待架构随之而来 | 想要解耦的服务 → 小型解耦的团队，具有独立的部署 |
| 重组提案 | 作为架构变更进行审查 | 技术主管/架构师批准团队合并，而不仅仅是人力资源 |
| 混乱的系统 | 绘制实际沟通，而不是组织结构图 | 聊天和审查图揭示了"独立"团队之间的隐藏耦合 |

### 2. 四种基本团队类型

**核心概念：** 将每个团队简化为四种类型之一。流对齐团队端到端拥有业务变更的流程——这是主要的类型，也是大多数团队。赋能团队在流对齐团队中发展能力，然后继续前进。复杂子系统团队封装了深度的专业知识（例如机器学习模型、编解码器、定价引擎）。平台团队提供一个引人入胜的内部产品，以减少流对齐团队的认知负荷。

**为什么有效：** 模糊的章程（"API团队"、"DevOps团队"）积累了无处可归的工作，并且交互不可预测。四种明确定义的类型使差距和重叠变得明显，为每个团队相对于变更流程提供了一个明确的目的，并使组织其他部分的期望变得清晰。

**关键洞察：**
- 流对齐是默认的；其他三种类型只有在它们减少负荷时才有意义
- 一个从未脱离的赋能团队已成为依赖——通过转移的能力来衡量，而不是关闭的工单
- 复杂子系统团队是由真正的专业知识的合理性证明的，而不是管理上的便利——大多数组织需要零个或一个
- 平台的存在是为了从流中移除负荷：如果采用它比自托管更困难，那么它是一个负债，而不是一个平台
- 反模式：共享服务团队成为工单队列瓶颈；开发者和运维之间的"DevOps团队"增加了一个第三隔离区；到处都是组件团队意味着每个功能跨越许多团队

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 模糊的团队章程 | 在四种类型中选择一个 | "核心服务团队" → 平台，具有内部客户和服务水平协议 |
| 深度专业能力 | 简单接口背后的复杂子系统 | 推荐引擎团队向流公开评分 API |
| 新实践推广 | 赋能团队，有时间限制 | 测试自动化专家为每个流提供 8 周的指导，然后退出 |

参见：[references/team-types.md](references/team-types.md)

### 3. 三种交互模式

**核心概念：** 团队以三种模式交互：协作（两个团队紧密合作进行发现）、X-as-a-Service（一个团队通过清晰的接口消费另一个团队提供的东西）、促进（一个团队帮助另一个团队学习或改进）。对于每对交互的团队，选择一种模式并明确声明它。

**为什么有效：** 大多数组织痛苦源于未定义的交互：一个期望服务的团队被拖入联合设计；一个期望指导的团队得到一个工单队列。声明的模式设定了相互期望，绑定了协调成本，并将人际摩擦转化为可用的设计信号。

**关键洞察：**
- 协作用于发现且成本高昂——它模糊了边界并提高了两个团队的认知负荷；限制它，并限制每个团队一次只有一个协作
- X-as-a-Service以发现速度换取可预测性——适用于已建立的接口，而不适用于边界仍然未知时
- 模式应刻意演变：协作以发现接口，然后随着接口的稳定转向 X-as-a-Service
- 持续的摩擦是组织感知数据：尴尬的协作表明边界错误；笨拙的服务表明平台需要产品工作
- 临时、声明的切换回协作是采用主要新平台功能的标准方式

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 新平台功能 | 首先协作，然后 X-as-a-Service | 流和平台团队就日志 API 配对 6 周，然后消费它 |
| 两个团队无休止的会议 | 声明预期模式 | 同意它是服务关系 → 删除例会，发布 API |
| 流中能力差距 | 促进参与 | 赋能团队就可观察性实践进行配对，在本季度内退出 |

参见：[references/interaction-modes.md](references/interaction-modes.md)

### 4. 团队认知负荷和团队规模的软件

**核心概念：** 使责任与团队的认知能力相匹配。三种负荷类型适用于团队：内在的（工作本身固有的技能和技术）、外在的（交付机制：工具、环境、流程）、相关的（增值领域思考）。最小化外在负荷，考虑内在负荷，并保护相关负荷的能力——并将软件规模调整为团队，而不是相反。

**为什么有效：** 当负荷超过容量时，团队会挣扎：上下文切换、浅层所有权、防御性规划、交付时间延长、呼叫恐惧。限制每个团队的领域可以使所有权足够深入以实现精通，而长寿团队可以摊销一个团队融合所需的时间。

**关键洞察：**
- 衡量领域，而不是人头：一个复杂领域每个团队一个，永远不会两个；一个团队可以持有两个或三个简单领域；永远不会将一个复杂领域拆分到多个团队
- 大团队不是过载的解决方案——较少的领域是；如果软件超过团队规模，请拆分软件
- 团队 API 使团队可消耗：代码、文档、呼叫、聊天频道和工作协议，让其他人无需会议即可交互
- 长寿团队优于项目 staffing——解散一个融合的团队会丢弃数月的信任，然后再次支付融合成本
- 尊重邓巴规模的分组：每个团队约 5-9 人，然后在接近 15、50 和 150 的人数附近形成团队的自然限制
- 外在负荷是最容易消除的：铺好的道路、模板和平台服务在不进行重组的情况下买回了相关能力

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 团队报告挣扎 | 计数并分类其领域 | 1 个复杂 + 3 个简单领域 → 放弃两个简单领域 |
| 慢速跨团队入职 | 发布团队 API | 每个团队列出所有者、文档、呼叫、频道、请求路径 |
| 项目结束 | 保留团队，移动工作 | 将融合的团队重新指向下一个流；默认情况下永不解散 |

参见：[references/cognitive-load.md](references/cognitive-load.md)

### 5. 断裂平面（Fracture Planes）：为团队所有权拆分软件

**核心概念：** 沿着自然缝隙拆分软件——断裂平面——以便每个部分可以被一个团队完全拥有。业务领域（DDD 有界上下文）是默认平面；其他是监管合规、变更节奏、团队位置/时区、风险、性能隔离、技术和用户画像。

**为什么有效：** 大于一个团队认知负荷的软件会强制共享所有权，而任意或按层划分会重新创建跨团队耦合。沿着一起变化的缝隙拆分可以保持大多数变更在一个团队内部——当服务边界与团队边界匹配时，康威定律会为你工作而不是对你不利。

**关键洞察：**
- 默认使用业务领域拆分；只有具体的强制原因（PCI 范围、10 倍性能热点、冲突的变更节奏）才使用其他平面
- 技术通常是最差的平面——前端/后端/DBA 拆分保证每个功能需要三个团队
- 任何拟议拆分的试金石：这个部分可以作为独立服务或 SaaS 提供？如果不是，边界有泄漏
- "单体"不仅仅是代码：单体数据库、耦合发布列车和强制全组织的标准化都在与团队独立性作斗争
- 由三个团队拥有的代码属于没有人——给每个工件一个所有者，提取它到平台，或作为内部源运行，并指定负责人
- 一个系统的一个部分可以沿不同的平面拆分；整个系统不必由一个平面统治

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 单体分解 | 首先映射有界上下文 | 订单、支付、目录 → 三个团队拥有的三个服务 |
| 处于监管负担中的每个地方 | 按监管范围拆分 | PCI 流在一个经过审计的服务中隔离，并由团队管理 |
| 混合变更速率 | 按节奏拆分 | 每周变化的定价与每年变化的账本分离 |

参见：[references/fracture-planes.md](references/fracture-planes.md)

### 6. 平台作为产品以及感知/演变

**核心概念：** 将平台作为内部产品运行，其客户是流对齐团队，从最薄的可行平台（Thinnest Viable Platform）开始——即加速流的最小事物，它可以是整理经过验证的服务的维基页面。然后，将整个拓扑结构视为动态的：使用摩擦、等待时间和呼叫信号来感知何时必须更改团队边界和交互模式。

**为什么有效：** 强制平台具有受困用户会逐渐变成官僚主义，因为失败没有反馈渠道；可选采用迫使平台保持吸引力，而产品纪律使其能够解决实际需求。将拓扑结构视为一次性重组的组织会随着产品和市场的变化而逐渐偏离康威失调。

**关键洞察：**
- 平台是根据移除的认知负荷来评判的，而不是发送的功能——更大的平台不一定是更好的平台
- 最薄的可行平台纪律：从整理和文档开始（"使用这些服务，以这种方式"）；只有在整理不再足够时才构建软件
- 内部开发人员是客户：进行用户研究，发布路线图和 SLA，跟踪采用和开发者体验，就像产品指标一样
- 如果流可以离开，平台必须在价值上竞争——强制隐藏平台失败，直到它变得灾难性
- 影子平台、增长等待时间、重复的跨团队摩擦和呼叫痛苦是拓扑结构需要演变的感知信号
- 没有最终的拓扑结构——每隔几个季度重新审视团队边界和交互模式，根据信号而不是仪式

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 组建平台团队 | 采用产品实践 | 路线图、内部用户研究、办公时间、版本化 API 与 SLA |
| 平台蔓延 | 重新锚定在 TVP | 切割到流实际使用的六个服务；整理其余部分 |
| 组织再次感觉"不对" | 运行感知审查 | 摩擦日志和等待时间数据推动一个刻意的边界变更 |

## 常见错误

| 错误 | 为什么失败 | 修复 |
|------|------|------|
| 创建开发者和运维之间的"DevOps团队" | 增加了一个第三隔离区和另一个交接队列 | 平台团队用于自助服务工具，或赋能团队发展能力 |
| 永久赋能团队 | 能力从未转移；流保持依赖 | 时间限制参与，并具有明确的退出标准 |
| 强制平台采用 | 受困用户隐藏失败；平台逐渐变成官僚主义 | 保持采用可选；使平台在价值上竞争 |
| 按技术层拆分团队 | 每个功能跨越多个团队；交接主导交付时间 | 沿业务领域断裂平面拆分；流对齐所有权 |
| 项目结束时解散团队 | 丢弃融合的信任；每次支付形成-风暴成本 | 长寿团队；将流工作分配给团队，而不是将人员分配给项目 |
| 共享服务团队作为工单队列 | 每个流的工单通过一个瓶颈串联 | 转换为平台作为产品（自助服务）或赋能团队 |
| 按人头规模团队，而不是认知负荷 | 大团队仍然挣扎，当领域太多或太复杂时 | 计数并分类领域；每个团队最多一个复杂领域 |
| 留下交互模式隐式 | 不匹配的期望；协调会议蔓延 | 每对团队声明一个模式；刻意审查和演变它 |

## 快速诊断

| 问题 | 若否 | 行动 |
|----------|-------|--------|
| 每个流对齐团队是否能在无交接的情况下交付其典型变更？ | 队列阻塞了团队间的流动 | 将团队重新对齐为业务变更的端到端切片 |
| 每个团队是否可明确标识为四种类型之一？ | 模糊的职责章程导致孤立的工作积累 | 对每个团队进行分类；转化或解散不匹配的团队 |
| 每对依赖团队之间的交互模式是否已声明？ | 期望不匹配导致摩擦 | 为每对团队声明协作、X-as-a-Service 或辅助 |
| 每个团队的领域数量是否在认知负荷启发式范围内？ | 效率低下、所有权浅薄、交付缓慢 | 重新分配领域；每个团队最多拥有一个复杂领域 |
| 服务和仓库边界是否匹配团队边界？ | 康威定律错位；共同所有权悄然侵入 | 沿断裂面重新拆分；每个工件一个所有者 |
| 平台采用是否可选，并以移除的负载来衡量？ | 强制要求掩盖了平台故障 | 将平台作为产品运行；追踪自愿采用情况和开发体验（DevEx） |
| 赋能参与是否有明确的时间框和退出标准？ | 永久依赖取代了学习 | 预先设定截止日期和能力转移目标 |
| 是否有定期机制来感知和演化拓扑结构？ | 随着系统和市场变化，设计腐化 | 每季度审查摩擦、等待时间和值班信号 |
