# 提升代码质量

将一个可用但未经测试的快速原型转变为可发布和可操作的产品。这是一个包含九个阶段的交互式、可中断的旅程：代理在做出每个决策前都会询问并记录结果在你的项目的 `docs/` 文件夹中，因此你可以在任何阶段停止并稍后继续。一个星期前的原型已经是遗留代码——因此第一步是一个安全网，之后的每个阶段都因为有了这个安全网而可以进行验证。

## 核心原则

**一个星期未经过测试的原型已经是遗留代码：从战术转向战略——首先设置安全网，然后依次进行可读性、结构和生产环境加固。**这项技能按顺序排列阶段，提出决策问题，并将每个选择记录在 `docs/` 中。组成技能承载着方法——调用它们而不是临时搭建它们的框架。跳过步骤（在测试前重构，在确定规模前扩展）是这种排序存在的目的——防止这种失败模式。

## 操作规则

1. **首先中断。** 在做任何事之前，阅读 `docs/IMPROVE-CODE-QUALITY-PLAN.md` 和旅程地图中的每个产出物。如果存在追踪器，请用3-5行总结旅程状态并询问要进入哪个阶段。当用户确认了入口点时完成。带有追踪器的旅程是中断的，而不是重新开始的。
2. **仅在第一次运行时进行输入。** 没有追踪器：运行下面的输入，然后创建 `docs/IMPROVE-CODE-QUALITY-PLAN.md`，将每个阶段的状态标记为 `pending | in-progress | awaiting-evidence | done | deferred: reason | skipped: reason`。当追踪器存在并且用户确认了阶段计划时完成。
3. **阶段入口。** 宣布：阶段的作用、它强制的决策、它产生的产出物、大致工作量。提供继续 / 跳过 / 推迟——标记为 GATE 的阶段可以推迟，但不能跳过。在继续时将阶段标记为 `in-progress`。当用户做出选择时完成。
4. **技能调用和回退。** 加载阶段的技能并使用它：每个阶段的调用行通过slug命名技能——使用该技能来运行阶段。如果它不可用，提供：`npx skills add wondelai/skills/<slug> --global`。如果用户拒绝，从其简要信息运行阶段——最小的可行方法。说明你处于什么模式。
5. **阶段内的决策。** 询问“与用户一起决策”下的每个问题——提供具体的选项和你的建议。将选择记录在追踪器的关键决策中。无声做出的决策是一个缺陷。
6. **阶段退出。** 在写入之前，展示草稿产出物内容以供批准。批准后：写入或扩展 docs/ 文件，更新追踪器（状态、关键决策、下一步行动）。当文件写入并且阶段行显示 `done` 时完成。
7. **产出物纪律。** 写在阅读之前；如果文件缺失则创建，否则扩展——添加或更新你的部分，保留其他人的部分。文件在 `docs/` 中是大写的。每个建议都作为复选框或带有所有者和优先级的表格行出现。在创建 docs/ 文件时查看 [references/artifact-templates.md](references/artifact-templates.md)——从完整骨架（所有部分标题）创建它，然后填写你的阶段名称的部分。
8. **阶段1是一个门控；提交保持单一目的。** 没有阶段会触及安全网地图中缺失的代码——首先固定它（缺失意味着未列在固定行为下；Gaps列中的条目也是禁止的）。结构和行为更改永远不会共享一个提交：在仅结构提交中用测试为绿色进行重构，然后在它自己的提交中更改行为。在重构过程中变红的测试意味着回滚并在更小的步骤中重试，而不是调试。安全网测试添加和 docs/ 更新是它们自己的单一目的提交。

## 输入

在创建追踪器之前询问这些问题：

1. 应用程序做什么，如果它崩溃了最坏的情况是什么？（确定风险和阶段优先级）
2. 你接下来要更改哪个模块，哪个模块的变更率最高（`git log`）或核心领域？ （选择阶段1开始的模块——三维启发式）
3. 今天是否存在任何自动化测试，测试命令是否运行为绿色？ （确定阶段1安全网的范围）
4. 堆栈是什么——框架、ORM、数据库？ （门控阶段5和9——边界和数据决策）
5. 这是否在生产中带有真实用户数据，以及大约有多少活跃用户或请求？ （门控阶段7-9——弹性是需求驱动的）
6. 它调用哪些出站依赖项——第三方API、支付、电子邮件、队列？ （门控阶段7——集成点审计）
7. 你现在想要旅程的多少？ （阶段1-3在真实用户之前；阶段7在发布之前；阶段8-9跟踪实际增长）

阶段跳过启发式：当真实负载远低于任何扩展阈值时跳过阶段8-9（从需求开始，而不是解决方案——不要在50个用户时为50k用户构建）。阶段7一旦存在真实用户就是可选的——超时和断路器即使在低流量下也是最低要求（它可能保持 `deferred: reason`，永远不会 `skipped`）。永远不要跳过阶段1；它是门控。然后从模板创建追踪器并确认计划。

完成时 `docs/IMPROVE-CODE-QUALITY-PLAN.md` 存在，每个阶段的状态都已标记，并且用户已确认计划。

## 阶段

阶段按列表顺序运行——每个阶段都假设前一个阶段的产出物存在。根据操作规则，任何阶段都可以进入、跳过或推迟，但阶段1门控它们所有：下游不会触及未固定的代码。

### 阶段1 — 建立安全网（与遗留代码一起工作）— GATE

**目的：** 在变更点固定当前行为，以便每个后续阶段都是可验证的。没有阶段可以触及安全网地图中缺失的代码。

**简要（回退）：** 遗留代码是没有测试的代码，所以一个星期前的原型符合条件。覆盖和修改，而不是编辑和祈祷：识别变更点，用最侵入性的接缝打破内联依赖（用生产默认值参数化构造函数；提取和覆盖一个隐藏的调用），然后编写特征化测试来拍摄实际行为——断言某事错误，读取失败，固定真实值。当在有限的时间内无法实现完整覆盖时，Sprout/Wrap 新代码并跟踪未测试的主机作为债务。

**调用：** 使用 `working-with-legacy-code` 技能，在输入时选择的起始模块。请求从入口方法的效果草图、接缝和固定当前注册/计费/核心行为的最小特征化测试集。

**与用户一起决策：** (1) 通过三维启发式确认起始模块——接下来要更改的、高变更率、核心领域的。 (2) 在特征化过程中发现的错误：固定错误行为并将其记录在债务登记册中，永远不要无声地修复——调用者可能依赖于这个怪癖。确认用户接受这一点。

**产出物：** 创建 docs/TESTING.md，带有 `## 测试策略`、`## 安全网地图`（模块 | 固定行为 | 测试文件 | 缺口），和 `## 特征化待办事项”；创建 docs/TECH-DEBT.md，带有 `## 债务登记册`（项目 | 位置 | 类型 | 风险 | 工作量 | 优先级 | 状态）和 `## Sprout / Wrap 注册”。更新追踪器。

**完成时：** 目标模块的行为被固定，套件运行为绿色，两个文件都存在，并且阶段1显示 `done`——只有到那时，后续阶段才会解锁。

### 阶段2 — 使代码可读（清晰代码）

**目的：** 优化以供阅读——名称、小型的单一目的函数、安全的错误处理——现在更改是可验证的。

**简要（回退）：** 代码比编写更频繁地被阅读。名称揭示意图（`elapsedTimeInDays`，而不是 `d`）；布尔值作为谓词读取；函数在一个抽象级别上做一件事，带有0-2个参数（一个标志参数是两个函数）。命令-查询分离：更改状态或返回值，永远不两者都做。错误处理：优先选择异常而不是返回代码，捕获特定类型，永远不返回或传递空值（使用空集合、Optional或空对象），并且在每个抛出的错误中放入操作+状态上下文。

**调用：** 使用 `clean-code` 技能，以目标模块为目标。请求在六个学科上的0-10分，以及按优先级排序的前十个修复，以及错误处理审计（裸捕获、空返回、无上下文的错误）。

**与用户一起决策：** 应用哪些修复现在与记录为债务，团队采用的命名/错误处理约定，以及是否清晰代码分数成为CI门控。

**产出物：** 扩展 docs/TECH-DEBT.md：为每个名称/函数/错误异味添加行到 `## 异味清单`（异味 | 位置 | 重构 | 状态），并记录商定的规则在 `## 采纳的约定”。更新追踪器。

**完成时：** 模块得分8+或每个低于8的缺口都是一个带有修复的异味清单行，约定被记录，并且阶段1的测试仍然通过。

### 阶段3 — 应用命名的重构（重构模式）

**目的：** 将“清理它”转换为命名的、保持行为的转换，以小步骤执行。

**简要（回退）：** 每个异味都对应一个命名的重构。提取方法是主力——如果你会写一个注释来解释一个块，提取它并以注释命名。还替换魔法数字为符号常量，替换嵌套条件为保护子句，替换条件为多态，引入参数对象。工作流程：测试为绿色，一个转换，测试为绿色，提交；测试变红意味着回滚，而不是调试。准备性重构（使更改变得容易，然后使容易的更改）和三个规则防止过早抽象。

**调用：** 使用 `refactoring-patterns` 技能，以一个有异味的函数和阶段1的测试为目标。请求它命名每个异味，引用转换，并一次应用一个，每次应用后运行测试。

**与用户一起决策：** 范围——这次要解决哪些异味，是否即将到来的功能值得在插入点首先进行准备性重构，以及重构的模块是否加入 TESTING.md 中的CI门控列表。

**产出物：** 扩展 docs/TECH-DEBT.md `## 异味清单`：对于每个异味，记录应用的命名重构及其状态。更新追踪器。

**完成时：** 目标异味显示命名的重构和 `done` / `ticketed` 状态，测试为绿色，结构更改以仅结构提交着陆。

### 阶段4 — 用深层模块减少复杂性（软件设计哲学）

**目的：** 与未受监督的代理创建的类itis作斗争——在简单的接口后面隐藏真实机制，而不是增加浅层类。

**简要（回退）：** 复杂性是敌人；最小化模块对整个系统施加的影响。模块深度 = 功能 ÷ 接口复杂性；深层模块在小型接口后面隐藏机制，浅层模块不这样做（类itis）。合并总是一起移动并共享状态的浅层类。注意信息泄漏（一个决策在许多模块中反映）和时间分解（按执行顺序组织，而不是按知识）。这是战术→战略的翻转：投资10-20%以保持设计清洁。

**调用：** 使用 `software-design-philosophy` 技能，以到目前为止触摸的模块集为目标。询问哪些类是浅层的，在哪里信息跨边界泄漏，以及如何合并成具有更简单接口的深层模块。

**与用户一起决策：** 现在要做出哪些合并，还是推迟，防止过度合并不相关的关注点。

**产出物：** 扩展 docs/TECH-DEBT.md `## 异味清单`带有类itis / 浅层模块 / 信息泄漏条目和应用的合并。更新追踪器。

**完成时：** 每个浅层模块集群被合并或记录为有修复，接口数量没有为了“模块化”而增加，并且测试为绿色。

### 阶段5 — 绘制架构边界（清晰架构）

**目的：** 使框架和数据库依赖于业务规则，而不是相反。

**简要（回退）：** 依赖规则：源依赖指向内部——实体，然后用例，然后接口适配器，然后框架/驱动；内部不命名任何外部。数据库和Web是细节，你的规则的插件。用依赖反转执行：用例拥有一个仓库接口；Postgres/Stripe实现生活在外部的适配器中。SOLID是中级工具。共享一个数据模型的微服务是一个分布式单体——首先在服务内部应用规则。

**调用：** 使用 `clean-architecture` 技能，以当前的模块映射和输入时的堆栈为目标。请求它映射依赖图，列出业务逻辑导入ORM或框架的每个违规行为，并显示提取到无框架用例背后的拥有接口。

**与用户一起决策：** 这次要推多远的边界，首先将哪些供应商（支付、存储）包装在拥有的接口后面，以及是否有计划的服务拆分等待服务内边界保持（避免分布式单体）。

**产出物：** 扩展 docs/ARCHITECTURE.md：记录层和当前违规行为在 `## 层映射 & 依赖规则`（违规行为 | 位置 | 修复 | 状态）和边界选择在 `## 决策日志”。更新追踪器。

**完成时：** 每个依赖规则违规行为都是一个带有修复的跟踪行，至少最高风险的供应商被包装，业务规则测试在没有框架的情况下运行，并且测试为绿色。

### 阶段6 — 固定习惯（实用程序员）

**目的：** 设置保持代码库在这次旅程结束后可变的元原则。

**简要（回退）：** DRY是关于知识，而不是文本——在两个地方重复相同的规则（客户端和服务器上的验证），留下偶然相似的东西。正交性：更改一个组件不应影响另一个。破损窗户理论：立即修复黑客或用跟踪的票证将其围起来——永远不要未跟踪的 `// TODO`。可逆性：将第三方供应商包装在你的自己的接口后面。子弹列车：构建下一个功能作为一个薄的真实的端到端切片，而不是逐层。

**调用：** 使用 `pragmatic-programmer` 技能，跨整个代码库。请求它标记重复的知识（忽略偶然的重复）和任何需要围起来的破损窗户或未跟踪的TODO。

**与用户一起决策：** 每次迭代的债务预算和破损窗户政策——什么现在被修复，什么被记录为票证。

**产出物：** 扩展 docs/TECH-DEBT.md：记录重复知识和破损窗户项目在 `## 债务登记册`，以及商定的政策在 `## 债务预算 & 破损窗户政策`和 `## 采纳的约定”。更新追踪器。

**完成时：** 重复知识打击被登记或修复，没有未跟踪的黑客剩余，并且债务预算政策被写下来。

### 阶段7 — 使其能够生存生产（发布它）

**目的：** 强化所有集成点，以便一个缓慢或失败的依赖项能够优雅地降级，而不是导致整个应用程序崩溃。

**简要（备用）：** 通过 QA 的软件并不一定能在生产中存活。集成点是首要杀手——缓慢的响应比没有响应更糟。不可协商的条款：每个出站调用都连接+读取超时；对失败的依赖项使用断路器（打开时跳转，快速失败，半开恢复）；隔离资源池的舱壁；指数退避+抖动重试；清除累积的冗余的稳态清理。使用特性标志和扩展-收缩迁移将部署与发布解耦。添加深度健康检查、RED 指标、基于症状的警报。

**触发：** 使用 `release-it` 技能，针对从引入中获取的出站依赖项。要求对无超时的调用、断路器+舱壁放置、深度健康检查+RED 指标+警报设计进行审计。

**与用户共同决定：** 断路器阈值、哪些依赖项获得专用池，以及警报症状和阈值（错误率、延迟）。

**工件：** 创建 `docs/RELIABILITY.md`，包含 `## 集成点审计`（依赖项 | 超时 | 断路器 | 舱壁 | 重试策略 | 状态）、`## 健康检查 & 指标` 和 `## 部署 vs 发布`。更新追踪器。

**完成时：** 每个出站调用都有超时，关键依赖项有断路器和舱壁，存在深度健康检查+RED 指标+基于症状的警报，累积的冗余的稳态清理已安排，可以无重新部署回滚发布，并且审计表对关键路径没有打开的行。

### 第 8 步 — 根据实际负载进行扩展（系统设计）

**目的：** 根据需求和数字进行有意扩展，而不是被动反应——只有在估算证明需要时才添加设备。

**简要（备用）：** 从需求开始，而不是解决方案。粗略估算：QPS = 每日活跃用户 × 每日操作数 ÷ 86,400，峰值 2-5 倍平均；存储 = 每日记录数 × 大小 × 保留期。按顺序扩展：首先垂直扩展，然后缓存（带 TTL 的缓存旁路和显式失效）用于读密集型路径，然后是读副本，最后才分片。使用消息队列将缓慢工作与请求路径解耦。使用已知设计（速率限制器 → 返回 `429 Retry-After` 的令牌桶）。

**触发：** 使用 `system-design` 技能，针对从引入中获取的负载现实。要求平均和峰值 QPS、年度存储、哪个组件首先成为瓶颈，以及缓存/队列/副本移动的优先级排序列表，不要过度设计。

**与用户共同决定：** 哪些扩展操作现在执行，哪些推迟执行，与实际数字挂钩（不要在 50 万用户时为 50 万用户构建），如果有的话，命名第一个缓慢的工作负载移动到消息队列后面。

**工件：** 扩展 `docs/ARCHITECTURE.md` 的 `## 系统上下文`，包含负载现实和粗略估算数字；扩展 `docs/RELIABILITY.md` 的 `## 查询 & 资源发现`，包含无界查询和瓶颈。更新追踪器。

**完成时：** 记录 QPS 和存储数字，命名第一个瓶颈，并且每个扩展操作要么应用，要么推迟，并记录触发数字。

### 第 9 步 — 正确处理数据层（ddia-systems）

**目的：** 保护比代码更长的数据——并发下的正确性，以及数据存储的选择由需求决定，而不是习惯。

**简要（备用）：** 数据比代码更持久。大多数数据库默认为读已提交或快照，而不是可序列化——简单的读后写会触发写偏差（两个请求都出售最后一个项目）。显式修复使用 `SELECT ... FOR UPDATE` 或可序列化事务；了解你的实际默认值。复制延迟意味着一旦存在副本，读你写的和单调读必须是故意的。使数据模型与访问模式匹配；多语言持久化通常是正确的；将记录系统与派生数据（CDC / 事件溯源）分开，而不是双重写入。

**触发：** 使用 `ddia-systems` 技能，针对从引入中获取的数据库和第 8 步的副本计划。要求它找到易受写偏差影响的读后写路径，声明实际默认隔离级别及其异常，并修复有风险的路径。

**与用户共同决定：** 哪些路径需要锁定，而不是可序列化事务，以及新的工作负载（搜索、信息流）是否值得保留第二个数据存储，该数据存储通过 CDC 同步。

**工件：** 扩展 `docs/ARCHITECTURE.md` 的 `## 数据 & 存储决策`，包含隔离级别、锁定路径和任何多语言/派生数据选择；在 `## 决策日志` 中记录推理。更新追踪器。

**完成时：** 文档化默认隔离级别，每个易受写偏差影响的路径都被锁定或变为可序列化，并且任何新的数据存储都有定义的同步机制。

## 可选阶段

| 技能 | 添加时 | 工件 |
|---|---|---|
| domain-driven-design | 业务逻辑因为代码不使用领域语言而缠绕 | 扩展 `docs/ARCHITECTURE.md` (`## 有界上下文 & 上下文图`, `## 领域词汇表 (通用语言)`) |

可选阶段遵循相同的操作规则——像核心阶段一样精确地加载和使用每个列出的技能；在添加-何时条件首次变为真时插入——在这里，在第 5 步之后立即插入，一旦边界存在。

## 常见错误

| 错误 | 修复 |
|---|---|
| 在编写单个测试之前清理 | 在第 1 步（处理遗留代码）中首先使用特征测试固定行为；安全网控制着每个后续阶段。 |
| 让代理“模块化”成一群微小的类 | 应用软件设计哲学的深度模块规则——合并一起移动的浅层类；减少接口，而不是增加接口。 |
| 使用无超时调用外部 API | 在第 7 步（release-it）中在每个出站调用上添加连接+读取超时，并在关键依赖项上添加断路器。 |
| 在测量任何东西之前扩展 | 首先进行粗略估算（系统设计）；数字通常表明缓存和读副本有几年的运行空间。 |
| 将微服务误认为架构 | 在服务内部首先应用依赖规则（干净架构）；共享一个数据模型的服务是一个分布式单体。 |
| 假设数据库是可序列化的 | 检查实际默认隔离级别并锁定读后写路径（ddia-systems）——写偏差通过每个单用户测试。 |

## 完成旅程

按顺序交付，而不是一次全部交付：第 1-3 步（网络、可读性、重构）属于真实用户到达之前；第 5 步的边界在代码库再次翻倍之前收益最大；在第 7 步之前加固（超时和断路器即使在低流量时也不是可选的）；让第 8-9 步跟踪你的实际增长数字。

退出清单——每个框都与工件相关联：

- [ ] 业务规则有在无数据库或框架的情况下运行的测试（TESTING.md 安全网映射完成，已更改模块）。
- [ ] 每个出站调用都有超时，关键依赖项有断路器，深度健康检查+RED 指标连接到基于症状的警报（RELIABILITY.md 集成点审计清晰，健康检查 & 指标已填写）。
- [ ] 依赖规则成立——业务逻辑不导入任何框架或 ORM（ARCHITECTURE.md 层映射，违规项已关闭）。
- [ ] 数据库隔离级别已知，读后写路径被锁定（ARCHITECTURE.md 数据 & 存储决策）。
- [ ] 没有未跟踪的黑客；每个推迟项都是债务凭证行，具有优先级（TECH-DEBT.md）。

关闭追踪器：每个阶段 `done` 或 `skipped: 原因`，将剩余的下一步行动带入 `TECH-DEBT.md` 债务凭证，以便不会丢失。然后转发：当代码库年长且杂乱，而不是年轻且杂乱时，继续使用 `remove-technical-debt` 技能；当下一个系统需要从一开始就进行精心设计时，继续使用 `design-code-architecture` 技能。
