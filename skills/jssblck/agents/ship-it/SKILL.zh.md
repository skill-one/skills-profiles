# 发送

对于完整的发送请求，需在提交并推送后，以准备好的状态打开一个拉取请求，并确保持续集成（CI）环境为绿色。打开一个新的非草稿拉取请求，然后完成仓库所需的审核和本地验证，同时CI持续运行。

更窄的请求保持其范围。仅进行CI修复时，修复受影响的分支和检查，无需创建拉取请求或更改其草稿/准备好状态、基础分支、标题或无关内容。仅进行监控时，报告结果无需进行修复。明确要求保持草稿的请求优先于完整的工作流。

除非被要求，否则不要合并拉取请求。仅在存在实质性歧义、需要批准或无法使用现有权限解决的障碍时才暂停。

## 提交请求的工作

在特性分支上工作，而不是默认分支。当当前特性分支拥有变更时，保持在该分支上；否则遵循仓库的命名规范，或使用`agent/`（当不存在时）。

检查差异和工作树。保留无关的用户变更并标记明确路径。将相关文件组合到逻辑提交中。

使用祈使主语。当变更的原因不明显时，在主题中解释变更的原因。遵循主动归属和标点符号说明。将提交正文包裹在80列内，但不要硬换行拉取请求段落。

## 打开或重用拉取请求

对于完整的发送请求，推送并检查是否存在现有的拉取请求：

```sh
gh pr list --state open --head <branch> --json number,title,url,isDraft,baseRefName,headRefName
```

重用现有的拉取请求。如果它是草稿，使用`gh pr ready`将其标记为准备好，除非用户要求保持草稿状态。如果不存在拉取请求，使用`gh pr create`创建一个非草稿拉取请求。仅在用户明确要求草稿时使用`--draft`。除非这是一个现有堆栈中的依赖层或用户指定了另一个基础分支，否则使用默认分支作为基础。

解释变更的原因和变更内容。当适用时，使用`Fixes #<n>`引用原始问题。编辑正文时保留现有上下文。除非被要求，否则不要添加标签或审查者。

## 运行配置的审核并按比例验证

对于完整的发送请求，如果项目定义了签收工作流，则在打开或重用拉取请求并设置其预期准备状态后运行该项目的工作流。使用仓库当前的审核策略；当不存在时，不要凭空设置关卡。

阅读仓库的检查命令。运行所需的本地检查和覆盖变更行为的测试。在构建之前生成所需的代码。

- 当变更达到该边界时，包含集成测试。确认相关测试运行而不是静默跳过。
- 现有的自动化端到端测试可以提供运行时证据。除非有明确的检查风险，否则不要手动重复它们的覆盖范围。
- 使用手动交互来处理未覆盖的集成或视觉风险。执行代表性受影响的流程，而不是共享组件的每个路径。当变更影响它们时，检查响应式布局。
- 对于CLI或API行为，一个聚焦的测试或真实命令/请求可以提供证据。选择捕获风险的方法。
- 对于没有运行时表面的变更，说明不需要运行时捕获。
- 报告本地环境差距，并让CI覆盖需要其平台的检查。

通过检查后，仅对新的编辑、失败或未解决的风险重复或扩展验证。不要重构无关代码以改进验证过程。提交并推送任何必要的修复。

## 添加证据

对于完整的发送请求，添加一个测试部分，包含精确的命令、结果和相关差距。当足够时，使用现有的自动化输出。

在语言标记的围栏中内联简洁的文本证据：`console`用于命令转录，`json`用于JSON，或`text`用于其他输出。在发布证据之前，从证明中删除密钥和私有数据。

使用`gh --attach`附加有用的截图或录制视频，而不是`gh-image`。遵循[github-image-upload](../github-image-upload/SKILL.md)以支持媒体、附件语法和验证。当文本证据覆盖变更时，不需要媒体。不要提交证明文件。

调用此完整工作流授权将其证明添加到拉取请求。将证据保留在拉取请求正文内，保留其现有解释，并将任何所需的归属页脚保留在最后。

使用`gh pr view`验证预期的拉取请求基础分支、头分支、状态和证据。

## 照看发布的拉取请求

发布并验证拉取请求后，使用[babysit](../babysit/SKILL.md)在等待和观察CI完成之前检查合并冲突。观察完整的检查集，以便过滤视图不会隐藏失败。对于仅进行监控的请求，报告冲突而无需解决它们。

对于请求内的失败，诊断、修复、运行受影响的检查、提交、推送并再次观察。当行为所记录的内容发生变化时，刷新证明。保留所需的检查；不要绕过它们或在检查失败、被取消或未按预期运行时声称成功。

报告无关的失败，而不是在没有方向的情况下扩展工作。如果访问权限或基础设施阻碍进展，识别障碍和未解决的检查。
