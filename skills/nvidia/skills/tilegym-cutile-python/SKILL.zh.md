# cuTile Python 编程技能

您是 cuTile 编程的专家，擅长使用 cuTile 的基于瓦片编程模型编写高性能 GPU 内核。这项技能为创建、调试和优化 cuTile 内核提供了全面的指导。

## 概述

cuTile 是一个用于 NVIDIA GPU 的并行编程模型，具有基于 Python 的 DSL，可以自动利用先进的硬件功能，如张量核心。这项技能帮助您编写高效、正确的 cuTile 代码。

## 何时使用此技能

当您需要执行以下操作时，请调用此技能：
- 从头开始编写 cuTile GPU 内核
- 将张量操作转换为 cuTile 实现
- 调试或修复 cuTile 内核代码
- 优化 cuTile 内核以提高性能
- 了解 cuTile API 和编程模式
- 验证 cuTile 实现
- 从可用的参考资源中查找和调整示例

**可选地**在调用时指定：
- 目标张量形状
- 数据类型（默认：float16）
- 性能要求
- 任何特殊约束

## 在实现之前需要澄清的情况

对于复杂或模糊的任务，**在编码之前向用户展示方法选项**。这可以防止在错误的实现上浪费精力。

### 需要澄清的任务类型

| 任务类型 | 澄清原因 | 示例问题 |
|-----------|-------------|-------------------|
| **优化请求** | "使其更快" 有许多路径 | 哪个瓶颈？内存限制还是计算限制？目标加速比？ |
| **架构更改** | 结构性决策会影响所有内容 | 数据并行还是模型并行？持久内核还是标准？ |
| **模糊操作** | 同名但不同的实现 | 闪存注意力与标准？因果关系与双向？分组与深度卷积？ |
| **性能与正确性权衡** | 用户必须选择 | 使用 TF32 以获得速度？近似数学函数？减少精度累积？ |
| **缺失约束** | 没有目标无法优化 | 目标张量形状？批处理大小范围？内存预算？ |

### 直接执行的任务类型

- **清晰、具体的请求**： "为形状 (1024, 1024) 编写 ReLU 内核"
- **具有可复现性的错误修复**： "此内核在第 42 行崩溃"
- **API 问题**： "如何使用 ct.gather？"
- **示例适配**： "根据我的形状调整 TileGym softmax"

### 如何澄清

当需要澄清时：
1. 简要解释为什么存在多种方法
2. 提供 2-3 个具体的选项及其权衡
3. 如果有明显的最佳选择，请推荐一个选项
4. 在继续之前要求用户选择

**示例：**
```
您的请求 "优化此矩阵乘法" 可以有多个方向：

1. **持久内核** - 适用于小矩阵，更快，更复杂的代码
2. **瓦片大小调整** - 中等收益，最小的代码更改
3. **TMA 预取** - 适用于大矩阵，需要 Hopper+ GPU

我建议第一步使用选项 2。您希望选择哪种方法？
```

## 复杂性评估：简单与编排工作流

在开始实现之前，评估请求的复杂性以选择正确的工作流。

### 使用简单工作流（以下 0-6 步骤）时：
- 单内核任务（例如 ReLU、softmax、一个矩阵乘法）
- 修复或优化现有内核
- API 问题或示例适配
- 清晰的单操作请求

### 使用深度代理编排工作流时，如果任何以下情况适用：
- **3 个或更多需要单独内核的独立操作**（例如，“实现一个具有注意力、FFN 和层归一化的 Transformer 块”）
- **输入代码中的多个用户定义函数**（例如，`custom_activation()`、`custom_norm()`）
- **内核间数据依赖**，其中一个内核的输出作为另一个内核的输入
- **PyTorch `nn.Module`** 在 `forward()` 中具有多个层
- **显式分解请求**（例如，“将其分解为融合内核”）

当需要编排时，请遵循 **深度代理编排工作流** 部分。否则，继续执行 **说明** 下面的步骤。

**目标**：清楚地定义内核需要计算的内容
- 确定输入/输出张量及其形状/数据类型
- 了解所需的数学运算
- 确定数据依赖关系和计算流程

**使用用户提供的参考实现**：

### 步骤 2：设计内核架构
**目标**：规划内核结构
- 确定并行化的最佳块/瓦片大小（考虑 32 的倍数）
- 使用 `ct.cdiv(size, block)` 根据张量大小计算网格维度
- 设计块索引策略使用 `ct.bid()`
- 处理张量大小不能被块大小整除的边缘情况

### 步骤 3：准备类型系统和常量
**目标**：确保正确的类型注解
- 确定所有需要类型注解的常量值
- 使用 `ct.Constant[type]` 为所有常量添加正确的类型注解
- 选择适当的 cuTile 数据类型（ct.float32、ct.float16、ct.int32 等）
- 确保块大小和其他参数正确注解

### 步骤 4：实现内核
**目标**：编写 cuTile 内核函数
- 创建 `@ct.kernel` 装饰的内核函数并具有正确的签名
- 添加必要的参数（输入张量、输出张量、注解常量）
- 使用适当的 `ct.bid()` 调用实现块索引
- 使用 `ct.load()` 访问输入张量，具有正确的索引和瓦片形状
- 使用 cuTile 瓦片操作对加载的瓦片执行操作
- 使用 `ct.store()` 写入输出张量，具有正确的索引

### 步骤 5：准备和启动
**目标**：设置张量输入并启动内核
- 确保所有输入张量都在 CUDA 设备上使用 `.cuda()` 或 `.to("cuda")`
- 验证张量数据类型与 cuTile 兼容
- 如有必要，使用 `.contiguous()` 处理张量连续性要求
- 使用正确的网格维度启动内核

### 步骤 6：验证和测试
**目标**：确保正确性
- 验证内核编译没有错误
- 使用各种张量大小（对齐和不对齐瓦片大小）进行测试
- 如果可用，验证结果与参考实现
- 检查边界条件和边缘情况

### 常见问题和修复

| 错误类型 | 典型原因 | 修复 |
|------------|---------------|-----|
| `TypeError: missing Constant annotation` | 缺少 `ct.Constant[int]` | 为所有常量添加类型注解 |
| `ValueError: tile dimension not power of 2` | 非幂的瓦片大小 | 使用 `2**((size-1).bit_length())` |
| `IndexError` / `CUDA error` | 错误的网格维度或索引 | 检查 `ct.cdiv` 使用，瓦片与元素索引 |
| `Validation FAIL: max diff = X` | 数值不匹配 | 检查算法，增加容差或修复逻辑 |

## 关键要求

所有 cuTile 内核的**四个基本要求**：

1. **纯 cuTile 前向路径**：`forward()`/`composed_function()` 中的每个计算操作都必须通过 `@ct.kernel` + `ct.launch`。不要作为运行时操作调用 `nn.Conv2d()(x)`、`F.conv2d(x, w)`、`F.linear(x, w)` 或任何其他 `nn.*`/`F.*` 计算操作。
   - **在 `forward()` 中允许**：`torch.empty`、`torch.zeros`、`torch.ones`（分配）；`tensor.reshape`、`tensor.view`、`tensor.permute`、`tensor.contiguous`（重新排列）；`torch.cat`、`torch.stack`（连接）；`torch.sqrt`、`.sum()`、`.mean()`（内核启动之间的简单标量操作）。
   - **在 `__init__()` 中允许**：仅用于**权重初始化和存储**的 `nn.Conv2d`、`nn.Linear` 等是允许的——只要 `forward()` 提取权重（例如，`self.conv.weight.data`）并将其传递给 `ct.launch`，而不是调用 `self.conv(x)`。
   - 请参阅 `guidelines/02_code_generation_rules.md` 中的规则 15 和规则 17，以了解常见的违规行为和详细示例。
2. **瓦片索引，而不是元素索引**：`ct.load(A, index=(bid_m, k), shape=(BLOCK_M, K))` ✅ 不是 `(bid_m * BLOCK_M, k)` ❌
3. **所有瓦片维度必须是 2 的幂**：使用 `2**((size-1).bit_length())` 向上舍入
4. **所有常量都需要类型注解**：`BLOCK: ct.Constant[int]` 编译时必需

有关内存操作、瓦片大小、常见陷阱和优化策略的详细指南，请参阅 `guidelines/` 目录（01–03）。

## 文件管理指南

**重要提示**：请遵循以下文件创建规则：

1. **默认单文件**：除非用户明确要求多个文件，否则将内核、验证和测试代码生成到一个 `.py` 文件中
2. **不创建文档文件**：**不要**创建 README.md、文档文件或单独的示例文件，除非明确要求
3. **全部内联**：将内核实现、验证逻辑和测试代码包含在一个连贯的文件中
4. **最小化文件创建**：仅创建绝对必要的文件 - 优先编辑现有文件而非创建新文件
5. **不包含源引用**：**不要**在注释或 docstring 中提及 TileGym 文件、参考文件或来源。代码应独立存在，无需归因
6. **输出到当前工作目录**：所有输出的 `.py` 文件必须写入用户启动编码助手时的**当前工作目录**。在任务开始时运行 `pwd`。所有生成的 `.py` 文件直接放入该目录（例如 `./composed_foo.py`），绝不能放入技能的子目录中
7. **技能目录为只读**：`<skill_dir>` 仅传递给子代理，以便它们可以读取参考、示例和编排指令。任何代理（主代理或子代理）都**不能**在 `<skill_dir>` 下写入、创建或保存任何文件。仅使用读工具（Read、Glob、Grep、Bash `cat`/`grep`）使用它。**永远不要**将其传递给 Write、Edit 或任何文件创建命令。

    ...

if __name__ == "__main__":

## 成功标准

您的实现成功当且仅当满足以下条件：

1. ✅ **纯 cuTile 前向路径**：`forward()`/`composed_function()` 中没有 `nn.*`/`F.*` 计算调用 — 所有计算均通过 `ct.launch` 路由（`__init__` 中的权重初始化使用是允许的）
2. ✅ **实现前已搜索现有示例**
3. ✅ **如果 TileGym 无匹配，已搜索打包的 `examples/`**
4. ✅ **仅创建一个 .py 文件**（没有 README，除非请求，没有单独的示例）
5. ✅ **代码中无源引用**（注释或 docstring 中没有提及 TileGym 文件或参考文件）
6. ✅ **生成的 cuTile 代码无错误编译**
7. ✅ **数值结果在容差范围内与参考实现匹配**
8. ✅ **所有常量都有正确的类型注解**
9. ✅ **所有瓦片维度都是 2 的幂**
10. ✅ **网格维度正确覆盖所有张量元素**
11. ✅ **代码包含内联验证和测试代码，且在同一个文件中**

**使用编排（复杂任务）时的附加标准**：
