# MoE 长上下文训练

稳定文档：@docs/training/moe-optimization.md
卡片：@skills/nemo-mbridge-perf-moe-long-context/card.yaml

## 长上下文中的变化

一旦序列长度远远超过 4K 级别的范围，注意力内存和激活驻留时间就成为了主要的限制因素。对于 MoE 模型来说，这通常意味着你需要一些组合：

- 上下文并行
- 选择性重计算
- 更低的精度
- 优化器状态的 CPU 卸载
- 一个不会浪费较小的剩余 DP 预算的调度器和 PP 布局

## 圆整的扩展模式

### DSV3 在 H100 上

DSV3 长上下文的运行显示出一个稳定的模式：

- 一旦你超过了最短的上下文，选择性重计算就比完全重计算效果更好
- 如果 CP 适当增加，吞吐量在中长上下文到非常长的上下文中保持在相当窄的范围内
- 随着 CP 的增长，权衡从“内存适配”转变为“GPU 数量可行性”

换句话说，如果布局选择得当，长上下文不会立即导致利用率下降，但它会非常快地消耗 DP 预算。

### Qwen3-Next 在 GB200 上

Qwen3-Next 的行为更像是一个对内存敏感的中型模型：

- 8K 和 32K 在适度的 CP 下仍然是可行的
- 64K 是可能的，但吞吐量下降明显，内存也变得非常紧张
- 管道布局和分组-GEMM 改进几乎与 CP 一样重要

### Qwen3 235B 在 GB200 上

Qwen3 235B 表明，当 TP、CP 和 HybridEP 协调一致时，长上下文在 NVL72 系统上仍然可以高效。最佳的 128K 级别的配置不仅仅是“适配”配方；如果路由、并行和重计算保持平衡，它们可以保持高度高效。

## CP 尺寸经验法则

1. **从 4K 片目标开始**：一个好的初步猜测是 `CP ~= seq_len / 4096`，然后四舍五入到实用的 2 的幂次布局。

2. **如果可能，保持 DP 活跃**：一旦 CP、EP、TP 和 PP 一起将 DP 压缩到底部，长上下文扩展就会变得脆弱。

3. **优先选择选择性重计算**：在达到完全重计算之前，先考虑 `up_proj`、`norm`、`moe`、`moe_act` 或 `mlp` 等重计算模块。

4. **在非常长的上下文中避免 SDPA 密集的重计算**：重计算注意力内部可能会增加很多工作，而内存收益比重计算较小的 MoE 和 MLP 端模块要少。

5. **在 NVL72 系统上使用 TP 作为另一个杠杆**：GB200 和 GB300 的运行有时可以在仍然保持高效的情况下，用一些 CP 交换 TP。

6. **假设 GBS 将需要缩小**：随着 CP 的上升和 DP 的下降，你可能需要减少全局批处理大小或接受更高的 GA。

## 典型的配置系列

### DSV3 在 H100 上的 128K

```text
TP=1  CP=32  EP=32  PP=8  VPP=4
精度：FP8 级别
调度器：DeepEP
重计算：up_proj、norm、moe、mlp
额外内存帮助：优化器 CPU 卸载
```

### DSV3 在 H100 上的 256K

```text
TP=1  CP=64  EP=32  PP=8  EDP=2  VPP=4
精度：FP8 级别
调度器：DeepEP
重计算：up_proj、norm、moe、mlp
额外内存帮助：优化器 CPU 卸载
```

### Qwen3 235B 在 GB200 上的 128K

```text
TP=4  CP=4  EP=32  PP=4  VPP=12
精度：BF16 或 MXFP8
调度器：HybridEP
重计算：moe_act、norm
CUDA 图：attn + moe_router + moe_preprocess
```

## 重计算和 CUDA 图指导

对于长上下文 MoE 训练：

- 从选择性重计算开始
- 只有在形状和路由路径稳定后才能添加 CUDA 图
- 使用 CUDA 图时保持序列长度和 MBS 不变
- 如果运行依赖于高度动态的批处理，优先选择急执行

## 陷阱

1. **CP 不能替代 EP 或 PP**：它增加了一个维度；它不会让其他因素消失。

2. **一个好的 4K 基线仍然可能是一个坏的长上下文基线**：路由模式、重计算选择和卸载策略通常需要改变。

3. **GPU 数量可行性成为真正的限制**：非常长的上下文在一个单一配方中可能看起来很好，但一旦在完整模型中诚实地添加 EP 和 PP 就会变得不可能。

4. **CUDA 图需要静态形状**：可变长度批处理和机会性填充策略可能会无声地破坏路径。

5. **在 128K+ 时容器和内核支持更重要**：长上下文路径往往比短上下文启动更依赖新内核和错误修复。
