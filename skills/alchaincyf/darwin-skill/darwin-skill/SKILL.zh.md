# 达尔文技能 2.0

> **v2.1 · 2026-06-10** — 保留/回滚棘轮机制由「绝对分数 delta」改为「**成对同评审比较 + 奇数 N 多数决**」（绝对分数 ±8 的评审噪音会淹没保守编辑的真实增益，是虚假回滚的根源；评审内部比较可消除换尺污染）。绝对分数降级为仅用于筛选。
> **v2.0 · 2026-05-28** — 吸收微软研究院 SkillLens（arXiv 2605.23899）的 9 维评分处方 + SkillOpt（arXiv 2605.23904）的验证门控机制 + 人在回路的三层守关。
>
> 借鉴 Karpathy autoresearch 的自主实验循环，对技能进行持续优化。
> 核心理念：**评估 → 改进 → 实测验证 → 人类确认 → 保留或回滚 → 生成成果卡片**

## 设计哲学

autoresearch 的精髓：
1. **单一可编辑资产** — 每次只修改一个 SKILL.md
2. **双重评估** — 结构评分（静态分析）+ 效果验证（运行测试查看输出）
3. **棘轮机制** — 仅保留改进，自动回滚退步
4. **独立评分** — 评分使用子代理（子 agent），避免「自己修改自己评估」的偏差
5. **人在回路** — 每个技能优化完成后暂停，用户确认后再继续

与纯结构审查的区别：不仅看 SKILL.md 写得是否规范，更看重修改后**实际运行效果是否更好**。

## 评估量表（9 维度，总分 100）

> **设计依据**：基于 SkillLens 论文（arXiv 2605.23899）的实证发现——大语言模型作为评审评估技能质量的准确率仅为 46.4%（接近随机），加入元技能三个维度后提升至 73.8%。本量表强化了维度 3 / 维度 5 的评分标准，新增维度 9「反例与黑名单」，权重平衡至 100。**目的：让评分对真实质量更敏感，减少大语言模型评审的乐观偏差。**

### 结构维度（59 分）— 静态分析

| # | 维度 | 权重 | 评分标准 |
|---|------|------|---------|
| 1 | **Frontmatter 质量** | 7 | 名称规范、描述包含做什么+何时使用+触发词、≤1024 字符、**禁止结尾添加“灵活应用/根据情况判断”等空洞语句** |
| 2 | **工作流清晰度** | 12 | 步骤明确可执行、有序号、每步有明确输入/输出 |
| 3 | **失败模式编码** | 12 | **必须显式编码失败模式**（写出“如果 X 失败 → Y”的明确分支）；有后备路径、错误恢复；**只写正向流程而不写失败分支扣 ≥3 分**（SkillLens 元技能维度） |
| 4 | **检查点设计** | 6 | 关键决策前有用户确认、防止自主失控；**检查点必须显性标记（🔴/STOP/CHECKPOINT），仅靠“如果...建议...”措辞不算** |
| 5 | **可执行具体性** | 18 | 不模糊、有具体参数/格式/示例、可直接执行；**禁止“建议/可以考虑/根据情况/灵活把握/视情况而定”等软化措辞**——出现 ≥3 处扣 ≥3 分（SkillLens 可执行具体性维度） |
| 6 | **资源整合度** | 4 | references/scripts/assets 引用正确、路径可达 |

### 效果维度（35 分）— 需要实测

| # | 维度 | 权重 | 评分标准 |
|---|------|------|---------|
| 7 | **整体架构** | 12 | 结构层次清晰、不冗余不遗漏、与花叔生态一致；**冗余/AI 腔废话段落（说白了/换句话说/首先其次综上等花叔禁用词）出现一处扣 1 分** |
| 8 | **实测表现** | 23 | 使用测试提示词运行一遍，输出质量是否符合技能宣称的能力 |

### 元技能维度（6 分）— 反例与黑名单

| # | 维度 | 权重 | 评分标准 |
|---|------|------|---------|
| 9 | **反例与黑名单** | 6 | **技能必须有“不要做什么”的反例清单**；只写“应该做 X”没有“不要做 Y”扣 ≥3 分；红灯/危险动作/反模式应单独章节列出（SkillLens 风险-动作黑名单维度） |

### 评分规则
- 维度 1-7、9：每个维度打 1-10 分，乘以权重得到该维度得分
- 维度 8（实测表现）：运行 2-3 个测试提示词，按输出质量打 1-10 分
- **总分 = Σ(维度分 × 权重) / 10**，满分 100
- ⚠️ **绝对总分仅用于筛选（粗排「哪支最弱、先改谁」），绝不用于保留/回滚**。实测：同一份**未修改**文本换用不同评审评估，总分波动可达 **±8**（一支仅添加了 3 个 🔴 字符的技能，单独评估却 -8.5，完全是评审换尺而非真实退步）。保留/回滚一律采用 **阶段 2 的成对比较**。
  - **为什么**：大语言模型评审给出的是**抽样，而非测量**——分数存在于「文本 × 该评审当前所选标准」中，而非文本属性。绝对总分 = 用**两台未校准的秤**测量饮食前后，差值大半是秤的误差；成对比较 = **用同一台秤**测量前后，误差相减抵消。成对偏好远胜于绝对评分，这是大语言模型评审的已知结论（RLHF 使用成对比较而非绝对评分也是出于同一原因）。

### 量表的实证基础

量表设计依据来自 **SkillLens 论文（arXiv 2605.23899）** + **本地受控研究**：

- SkillLens 发现大语言模型作为评审的准确率仅为 46.4%（接近随机），加入元技能三个维度后升至 73.8%
- 本地对 huashu-research 进行 4 类退化处理 → 5 个独立评审盲测一致得出 V1>V2，Δ 平均值 +46.5（5/5 高置信度）

**结论**：量表能识别严重退化，但细微的质量差异仍不可信，**重要决策必须人工审查**。

→ 详细论文证据 + 5 位评审完整数据 + HL 实战案例数字见 [references/skilllens-evidence.md](references/skilllens-evidence.md)

### 关于「实测表现」维度

这是与纯结构评分最大的区别。评分方式：

1. 为每个技能设计 2-3 个**典型用户提示词**（不是边缘案例，是最常见的使用场景）
2. 使用子代理执行：一个携带技能运行，一个不携带技能运行（基线）
3. 对比输出质量，从以下角度打分：
   - 输出是否完成了用户意图？
   - 与不携带技能的基线相比，质量提升明显吗？
   - 是否存在技能引入的负面影响（过度冗余、跑偏、格式奇怪）？

若子代理不可用（超时/资源限制），退化为「干跑验证」：读完技能后模拟一个典型提示词的执行思路，判断流程是否合理；必须在 results.tsv 中标注 `dry_run`。**dry_run 比例 > 30% → 评估失效警告**（来自本地受控研究：维度 8 实测维度权重 23%，无完整测试验证时分数不可信）。

## 运行时适配性审查（门控项，独立于 9 维度评分）

技能应当能在 Claude Code / Codex / Cursor / OpenClaw / Hermes / Gemini CLI / OpenCode 等 50+ 个兼容技能的运行时环境中通用——否则其他代理在解析时会因「在 Claude Code 中」「Claude Code 技能」等措辞误判为「不是给我用的」而直接拒绝安装（实例：nuwa-skill 因此被 Marvis 代理拒绝）。

### 阶段 1 基线评估时强制运行一次红灯扫描

```bash
grep -nE "(在 Claude Code|Claude Code skill|Claude Code 用户|Cursor only|Codex 中|^\[!\[Claude Code|~/\.claude/skills/[a-z]|/plugin install\b)" SKILL.md README.md 2>/dev/null
```

输出非空 = 红灯命中，**但必须先阅读命中行的上下文以排除假阳性**（grep 命令本身/反例引用/讲解该规则的元陈述=假阳性，记录 `runtime_scan=false_positive` 不做修改；判别表见 references/runtime-neutrality.md）→ 确认为真红灯（指令性用法）后，强制将阶段 2 第一轮定为 P0「运行时漂移修复」（写入 results.tsv 的 note 列 `runtime_warn=N`）。

### 例外（允许的「Claude Code 痕迹」）

frontmatter 触发词、花叔生态内部技能名称引用、明确标注的运行时特定章节、commit 消息——这些正当出现，不算红灯。

→ 红灯/绿灯完整对照表 + 例外清单详细规则 + 阶段 1/2/3 各阶段审查时机见 [references/runtime-neutrality.md](references/runtime-neutrality.md)

## 自主优化循环

### 阶段 0：初始化

```
1. 确认优化范围：
   - 全部技能 → 扫描 .claude/skills/*/SKILL.md
   - 指定技能 → 用户指定列表
2. 创建 git 分支：auto-optimize/YYYYMMDD-HHMM
3. 初始化 results.tsv（如不存在）
4. 读取现有 results.tsv 了解历史优化记录
```

### 阶段 0.5：测试提示词设计

在评估之前，为每个技能设计测试提示词。这一步很关键——没有测试提示词，「实测表现」维度就无法打分。

```
for each skill:
  1. 读取 SKILL.md，理解它做什么
  2. 设计 2-3 个测试提示词，覆盖：
     - 最典型的使用场景（正常路径）
     - 一个稍复杂或有歧义的场景
  3. 保存到 skill 目录/test-prompts.json：
     [
       {"id": 1, "prompt": "用户会说的话", "expected": "期望输出的简短描述"},
       {"id": 2, "prompt": "...", "expected": "..."}
     ]
```

向用户展示所有测试提示词，**确认后再进入评估**。测试提示词的质量决定了优化方向是否正确。

### 阶段 1：基线评估 — 筛选用途

> **本阶段的绝对分数是筛选排名（决定先改谁），不是保留/回滚基准**。评审对严重差异会达成一致（「哪支最弱」可信），但对细微差异不可信（±8 噪音）。保留/回滚在阶段 2 使用成对比较。

```
for each skill in 优化范围:

  # 结构评分（主代理可以做）
  1. 读取 SKILL.md 全文
  2. 按维度 1-7 逐项打分（附简短理由）

  # 效果评分（使用子代理执行，独立于主代理）
  3. 对每个测试提示词，派生子代理：
     - with_skill: 带着 SKILL.md 执行测试提示词
     - baseline: 不携带技能执行同一提示词
  4. 对比两组输出，打维度 8 的分

  # 汇总
  5. 计算加权总分
  6. 记录到 results.tsv
```

**如果子代理不可用**（超时、环境限制），维度 8 使用干跑验证打分，标注 `dry_run`。不要因为无法运行测试就跳过这个维度——哪怕是模拟推演也比完全不看效果好。

基线评估完成后，展示评分卡：

```
┌──────────────────────────┬───────┬──────────────┬──────────────┐
│ Skill                    │ Score │ 结构短板      │ 效果短板      │
├──────────────────────────┼───────┼──────────────┼──────────────┤
│ huashu-proofreading      │ 78    │ 边界条件      │ 测试提示词 2  │
│ huashu-slides            │ 72    │ 指令具体性    │ 基线持平      │
├──────────────────────────┼───────┼──────────────┼──────────────┤
│ 平均                     │ 75    │              │              │
└──────────────────────────┴───────┴──────────────┴──────────────┘
```

**🔴 检查点 · 🛑 停止：暂停等待用户确认，再进入优化循环。**

### 阶段 2：优化循环

用户确认后，按基线分数从低到高排序，先优化最弱的。

```
for each skill:
  round = 0
  while round < MAX_ROUNDS (默认 3):
    round += 1

    # 步骤 1: 诊断
    找出加权短板最大的维度：weighted_gap = weight × (10 - score) / 10，结构和效果都算
    # /10 与「总分 = Σ(维度分 × 权重) / 10」同标度：weighted_gap 就是该维度还能贡献的总分数
    # 为什么不用「原始分最低」：低权重维度会制造进步幻觉——issue #18 实战中
    # 维度 9（权重 6，缺口 5.3）原始分最低被优先修复，而维度 8（权重 23）加权短板最大（11.5）却 4 轮未动
    # 加权短板相近（差距 ≤ 1.0，同上述标度）时，回退为原始分升序
    # HL-3 警告：维度 2/维度 3/维度 4 是相关簇，修复其中一个时另外两个常跟着涨
    # → 不要因为维度 3 短板最大就单独修复，要看整簇短板再决定是否同步修改

    # 步骤 2: 提出改进方案
    针对该维度，生成 1 个具体改进方案：
      - 改什么（具体段落/行）
      - 为什么改（对应量表哪条）
      - 预期提升多少分

    # 步骤 3: 执行改进
    编辑 SKILL.md
    git add + commit（消息："optimize {skill}: {改进摘要}"）

    # 步骤 4: 成对重新评估（取代绝对重打分——绝对分数评审噪音 ±8、淹没保守编辑的 +3~8 真实增益）
    派生 N=3 个独立评审，每个【在同一次调用内】阅读两个版本：
      - 修改前版本：git show HEAD:<skill-path>/SKILL.md（上一个保留的提交）
      - 修改后版本：工作区当前 SKILL.md
    照 9 维量表作为【比较准则】（不是各打绝对分），返回 {better | worse | tie} + 幅度{clear|slight} + 一句理由。
    关键：同一评审在一次调用内比较两个版本 → 它那把不准的尺子对两个版本【等量作用、在比较时抵消】（评审内部抵消），
    这正是成对比较优于绝对比较的机制。N 取奇数（默认 3；接近时升至 5）。

    # 步骤 5: 共识决策（多数决，取代「新总分 > 旧总分」）
    cur = 投 better 的评审数；wor = 投 worse 的；
    if cur >= wor:  # 多数说修改后 ≥ 修改前（含 tie）
      status = "keep"
      # HL-4 见好就收：连续 2 轮多数评审判定幅度=slight 或 tie → break 进入阶段 3
    else:           # 多数说 worse —— 这才是真退步（已扣除换尺噪音）
      status = "revert"
      git revert HEAD（创建新提交回滚，不用 reset --hard）
      记录到 results.tsv（note 记录投票比数 + 一句 worse 理由）
      break
    # 单次绝对分数出现「负 delta」≠ 回滚信号；必须经成对多数判定 worse 才回滚（否则是在丢弃真实增益）

    # 步骤 6: 日志
    results.tsv 追加行

  # === 🔴 检查点 · 每个技能优化完成后强制人工审查 ===
  展示该技能的改动摘要：
    - git diff（修改前 vs 修改后）
    - 分数变化（哪些维度提升/下降）
    - 测试提示词输出对比（如果运行过的话）
  等待用户确认 OK 再继续下一个技能。
  如果用户说"不好"，回滚到该技能优化前的版本。
```

### 阶段 2.5：探索性重写（按需触发）

当局部爬山法连续 2 个技能都在第 1 轮就 break（涨不动）时，提议一次「探索性重写」：

```
1. 选一个瓶颈技能
2. git stash 保存当前最优版本
3. 从头重写 SKILL.md（不是微调，是重新组织结构和表达方式）
4. 重新评估
5. if 重写版 > stash 版: 采用重写版
   else: git stash pop 恢复
```

这解决了局部爬山法的局部最优问题——有时候需要「先拆后建」才能突破瓶颈。
**🔴 检查点 · 🛑 停止：必须征得用户同意后才执行。**

## results.tsv 格式

```tsv
timestamp	commit	skill	old_score	new_score	status	dimension	note	eval_mode
2026-03-31T10:00	baseline	huashu-proofreading	-	78	baseline	-	初始评估	full_test
2026-03-31T10:05	a1b2c3d	huashu-proofreading	78	84	keep	边界条件	补充后备路径	full_test
2026-03-31T10:10	b2c3d4e	huashu-proofreading	84	82	revert	指令具体性	过度细化	dry_run
```

`eval_mode` 列：`paired`（同评审比较修改前/修改后，**保留/回滚的权威依据**）｜`full_test`（子代理运行提示词）｜`dry_run`（模拟推演、仅供参考）。
成对行：`new_score` 栏记录投票比数（如 `3-0 better`），`note` 记录一句裁决理由。例：
```tsv
2026-06-10T06:30	paired	some-skill	（绝对 87.3→78.8 = 评审噪音）	3-0 better	成对比较推翻单次评估假退步	paired
```
文件位置：`.claude/skills/darwin-skill/results.tsv`

## 实战高杠杆操作（精髓速查）

4 条经实战验证（huashu-gpt-image +10.85 / huashu-weread-advisor +14.9 / claude-design +16.5）。详细案例数据见 [references/skilllens-evidence.md](references/skilllens-evidence.md) 的「HL 实战案例」节。

- **HL-1（维度 4）显性视觉标记是杠杆**：添加 🔴 检查点 / 🛑 停止，靠「必须」措辞不行——大语言模型解析时扫描视觉标记。4 行改动撬动维度 4 +3 分
- **HL-2（维度 3）if-then 三段式后备路径表**：把「症状/解法」两列升级为「触发条件 / 一线修复 / 仍失败兜底」三段式。SkillLens 失败机制编码维度的落地
- **HL-3（阶段 2 诊断）维度相关簇警告**：维度 2/3/4 是相关簇——修复维度 3 时维度 2 常跟着涨。「找最大加权短板维度」时同时查看相关簇短板再决定是否同步修改
- **HL-4（阶段 2 退出）触顶自动 break**：连续 2 轮 Δ < 2 分 → break 进入阶段 3。+0.15 是停手信号不是继续信号；硬凑 MAX_ROUNDS=3 引入过度工程化

## 优化策略库

按优先级排序，每轮只做最高优先级的一个：

### P0：运行时适配性问题（门控项命中 → 必须先修）
- README/SKILL.md 出现红灯措辞（如「在 Claude Code 中」「Claude Code 技能」）→ 替换为运行时中立措辞
- 徽章钉死单一运行时 → 改为 `Agent Skills Standard` + `skills.sh` + `Multi-Runtime` 三个中立徽章
- 安装章节只给一种运行时的路径 → 改为「一行命令（自动检测）+ 手动路径表 + 作为参考资料」三层结构
- 工作流硬编码运行时特定工具且无后备路径 → 给出通用替代方案或标注「仅在某个运行时可用」
- 例外：技能名称明确标注单运行时（如 `xxx-codex`）的，可跳过本项

### P0：效果问题（实测发现的）
- 测试输出偏离用户意图 → 检查技能是否有误导性指令
- 携带技能比不携带还差 → 技能可能过度约束，考虑精简
- 输出格式不符合预期 → 补充明确的输出模板

### P1：结构性问题
- Frontmatter 缺少触发词 → 补充中英文触发词
- 缺少阶段/步骤结构 → 重组为线性流程
- 缺少用户确认检查点 → 在关键决策处插入

### P2：具体性问题
- 步骤模糊（"处理图片"）→ 改为具体操作和参数
- 缺少输入/输出规格 → 补充格式、路径、示例
- 缺少异常处理 → 补充 "如果 X 失败，则 Y"

### P3：可读性问题
- 段落过长 → 拆分+用表格
- 重复描述 → 合并去重
- 缺少速查 → 添加 TL;DR 或决策树

## 异常与边界条件

流程假设环境理想，但实操常遇异常。以下预定义后备路径，保证优化过程不会「一跑就卡住」。

| 场景 | 触发条件 | 处理动作 |
|---|---|---|
| 不在 git 仓库 | `git rev-parse` 失败 | 询问用户：执行 `git init` 或回退到文件备份；用户选后者则 `cp SKILL.md SKILL.md.bak.YYYYMMDD-HHMM` 代替回滚 |
| results.tsv 缺失 | 文件不存在 | 新建并写表头行（9 列：含 eval_mode） |
| results.tsv 损坏 | 列数不匹配 / 非 TSV | 备份为 `.bak.YYYYMMDD-HHMM` 后重建，告知用户 |
| 分支已存在 | `git checkout -b` 失败 | 分支名末尾加 `-2` / `-3`；第 3 次失败则切回现有分支并询问继续还是新起 |
| `git revert` 失败 | 冲突 / 工作区脏 | 先 `git stash`，重试；仍失败则从上一个提交的 SKILL.md 读出覆盖当前文件手动恢复 |
| MAX_ROUNDS 触顶（默认 3） | 已跑 3 轮仍有短板 | 不强制 break，展示当前最弱维度问用户「继续加 1 轮 / 进入阶段 2.5 / 收工」 |
| 优化后超 150% 体积 | 新文件 > 原 × 1.5 | 拒绝提交，回到改进步骤精简（删冗余/合并重复），再评估 |
| test-prompts.json 已存在 | 文件已在技能目录 | 默认复用并展示，问用户「复用 / 重写 / 追加」三选一 |
| SKILL.md 找不到 | 目录存在但无 SKILL.md | 该技能终止，results.tsv 记 `status=error`，继续下一个 |
| 分数计算规则 | 浮点精度漂移 | 总分保留 1 位小数，改进需严格 > 旧分（不靠四舍五入） |

**原则**：异常先告知用户，再按规则处理；绝不静默跳过或静默失败。

## 达尔文操作反例黑名单（维度 9 应用：达尔文自己优化时不要做的事）

来自本地 results.tsv 早期 40 次 0 回滚的教训 + 评审 G/H 自指评估暴露的反模式。每条都是**真实踩过的坑**。

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|---|---|---|
| 1 | **同上下文自评自改** | 改完后立刻在同一 Claude 会话中打分，会有「我刚改的肯定更好」乐观偏差（SkillLens 实证大语言模型作为评审准确率仅 46.4%）| 必须派生**独立子代理**；保留/回滚走**成对比较**（同评审一次阅读修改前+修改后）的**奇数 N 多数决**，**不用绝对分数 delta**（绝对分跨评审 ±8 噪音、不可比） |
| 1b | **拿绝对分数 delta 当保留/回滚棘轮** | 绝对总分是抽样不是测量；基线评审与重评评审使用不同「标准尺」，差值大半是换尺、非真实质量变化（实测一支纯加标记的技能单次评估 -8.5、全是换尺）| 绝对分只做筛选排名；保留/回滚用成对多数决，评审内部抵消消除换尺污染 |
| 2 | **`git reset --hard` 当回滚** | 会丢失工作区未提交改动；CI 历史断裂 | 用 `git revert HEAD` 创建反向提交，保留可追溯链 |
| 3 | **为凑分增冗余** | 触顶后继续硬改往往是「加废话/加段落让大语言模型觉得更详细」，实际质量不变 | 触顶信号（连续 2 轮 Δ<2 分）→ break 进入阶段 3，**见好就收** |
| 4 | **跳过测试提示词直接评分** | 没有测试提示词的维度 8 是凭空打分，权重 23% 等于编造 | 阶段 0.5 强制设计 2-3 个提示词；若用户不给，默认编 3 个并展示确认 |
| 5 | **轮内改多个维度** | 多变量同时变，分数升降无法归因到具体改动 | 每轮 1 个维度；相关簇（维度 2/3/4）修改其中一个时观察另外两个是否跟涨 |
| 6 | **dry_run 比例 > 30%** | 维度 8 实测维度形同虚设，分数虚高（早期 40 次记录 67% dry_run，0 回滚） | 强制至少 1 个真实完整测试；dry_run 多的优化在 results.tsv 显式打 ⚠️ |
| 7 | **静默跳过异常** | 遇到 git/tsv 异常时静默继续，破坏棘轮完整性 | 异常表 10 条后备路径必须先告知用户再处理 |
| 8 | **忽视维度相关性单独优化** | 维度 2/3/4 是相关簇，单独优化维度 2 时常发现已被前轮维度 3 修复推到顶 | 找最大加权短板维度时同时查看相关簇短板，决定是否同步修改 |

**触发场景**：每轮阶段 2 改动前对照本表一次。任一反模式命中 → 改方案重写。

## 约束规则

1. **不改变技能的核心功能和用途** — 只优化"怎么写"和"怎么执行"，不改"做什么"
2. **不引入新依赖** — 不添加技能原本没有的脚本或引用文件
3. **每轮只改一个维度** — 避免多个变更导致无法归因
4. **保持文件大小合理** — 优化后 SKILL.md 不应超过原始大小的 150%
5. **尊重花叔风格** — 中文为主、简洁为上
6. **可回滚** — 所有改动在 git 分支上，用 git revert 而非 reset --hard
7. **评分独立性** — 效果维度必须用子代理或至少干跑验证，不能在同一上下文里「改完直接评」
8. **运行时中立性** — 技能必须能在 Claude Code、Codex、Cursor、OpenClaw、Hermes 等任何兼容技能的运行时中正常运行。除非技能名称明确绑定单一运行时（如 `xxx-codex`、`huashu-slides-codex`），任何「在 Claude Code 中」「Claude Code 技能」「单一徽章钉死」「安装命令只给 `.claude/skills/` 一种路径」都视为门控不通过，须在 P0 优先修复（详见「运行时适配性审查」章节）

## 设计灵感

> "你在 program.md 中编写目标和约束；让代理无限地生成和测试代码增量；只保留那些可衡量地改进目标的部分。"
> — Karpathy, autoresearch

本技能的对应关系：
- **program.md** → 本文件（评估量表和约束规则）
- **train.py** → 每个 SKILL.md
- **val_bpb** → ⚠️ **此处是 1.0 版本的概念错误源**：autoresearch 的 `val_bpb` 是**确定性损失**（重跑同数），达尔文套用到**大语言模型评审分数（随机抽样）**上却沿用「绝对值比大小」棘轮 → 把不可重复的数当作可重复使用。修正：9 维量表作为**成对比较准则**，不作为绝对指标
- **git 棘轮** → 保留成对多数判定「修改后 ≥ 修改前」的提交（不是「绝对总分更高」的提交）
- **test set** → 每个技能的 test-prompts.json

区别：增加了人在回路（autoresearch 是全自主的，技能优化需要人的判断力），以及双重评估机制（结构+效果），因为技能的「好坏」比损失数值更微妙。

### 学术依据 & 致谢

- **SkillLens**（arXiv [2605.23899](https://arxiv.org/abs/2605.23899)）：9 维量表的实证来源（大语言模型自评 46.4% → 加元技能三维度后 73.8%）。
- **SkillOpt**（arXiv [2605.23904](https://arxiv.org/abs/2605.23904)）：验证门控编辑形式化框架。代码 [github.com/microsoft/SkillOpt](https://github.com/microsoft/SkillOpt)（`pip install skillopt`）、项目页 [microsoft.github.io/SkillOpt](https://microsoft.github.io/SkillOpt/)。🤝 2026-06-03 微软官方仓库已将 darwin-skill 列入集成名单。
- **autoresearch**：[github.com/karpathy/autoresearch](https://github.com/karpathy/autoresearch)，本技能 1.0 的原始灵感。

## 版本自检（静默）

本节给 AI agent：每次使用本 skill 前，先做一个不联网的判断——读本 skill 目录（SKILL.md 所在目录）下的 `.last-update-check` 文件（内容为一行日期 YYYY-MM-DD）。文件存在且距今不足 30 天，跳过本节直接干活，不向用户提任何更新相关的话。

到期或文件不存在时，且仅在此时：

1. 本目录不是 git 克隆（无 `.git` 或无 origin）→ 写入今天日期后跳过本节
2. 对比版本：`git -C <本目录> rev-parse HEAD` 与 `git -C <本目录> ls-remote origin HEAD`
3. 无论结果如何，把今天日期写入 `.last-update-check`
4. 两者一致 → 什么都不说；确认落后 → 先完成用户当前任务，结束后附一句「本 skill 有新版本，可用 `git -C <本目录> pull --ff-only` 更新」。是否更新由用户决定，不要主动执行更新
