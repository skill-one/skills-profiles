# 可空引用迁移

在现有代码库中启用 C# 可空引用类型 (NRTs) 并系统性地解决所有警告。结果是具有 `<Nullable>enable</Nullable>`、零可空警告以及准确注释的公共 API 表面的项目（或解决方案），为编译器和消费者提供可靠的空值信息。

## 何时使用

- 在现有的 C# 项目或解决方案中启用可空引用类型
- 在启用该功能后系统性地解决 CS86xx 可空警告
- 注释库的公共 API 表面，以便消费者获得准确的空值信息
- 升级了添加了可空注解并出现新警告的依赖项
- 分析已启用 NRTs 的代码库中的抑制情况，以确定它们是否可以删除

## 何时不使用

- 项目已经具有 `<Nullable>enable</Nullable>` 和零警告——除非用户想重新检查抑制项以删除不必要的项（见步骤 6），否则迁移已完成
- 用户只想抑制警告而不修复它们（不建议这样做）
- 代码针对 C# 7.3 或更早版本，这些版本不支持可空引用类型

## 输入

| 输入 | 必填 | 描述 |
|-------|----------|-------------|
| 项目或解决方案路径 | 是 | 要迁移的 `.csproj`、`.sln` 或构建入口点 |
| 迁移范围 | 否 | `project-wide`（默认）或 `file-by-file`——控制推广策略 |
| 构建命令 | 否 | 如何构建项目（例如，`dotnet build`、`msbuild` 或特定于存储库的构建脚本）。如果未提供，则从存储库中检测 |
| 测试命令 | 否 | 如何运行测试（例如，`dotnet test` 或特定于存储库的测试脚本）。如果未提供，则从存储库中检测 |

## 工作流

> 🛑 **零运行时行为变化。** NRT 迁移纯粹是元数据和注解练习。生成的 IL 必须不改变——没有新的分支、没有新的空值检查、没有改变的控制流、没有添加或删除方法调用。唯一可接受的更改是可空注解（`?`）、可空属性（`[NotNullWhen]` 等）、`!` 运算符（仅元数据）和 `#nullable` 指令。如果在迁移过程中发现缺少运行时空值保护或潜在的 bug，**不要直接修复**。相反，建议在位置插入 `// TODO: 考虑添加 ArgumentNullException.ThrowIfNull(param)` 注释，以便用户可以将其作为单独的更改来解决。永远不要将行为修复与注解提交混合。

> **提交策略：** 在每个逻辑边界处提交——启用 `<Nullable>` 后（步骤 2）、修复解引用警告后（步骤 3）、注释声明后（步骤 4）、应用可空属性后（步骤 5）以及清理抑制项后（步骤 6）。这使每个提交保持专注且可审查，并防止如果后续步骤发现需要重新思考的设计问题而丢失工作。对于文件逐个迁移，单独提交每个文件或相关文件批次。

### 步骤 1：评估准备情况

> **可选：** 运行 `scripts/Get-NullableReadiness.ps1 -Path <project-or-solution>` 以自动化以下检查。脚本报告 `<Nullable>`、`<LangVersion>`、`<TargetFramework>`、`<WarningsAsErrors>` 设置以及 `#nullable disable` 指令、`!` 运算符和 `#pragma warning disable CS86xx` 抑制的计数。使用 `-Json` 获取机器可读输出。

1. 确定项目如何构建和测试。查找构建脚本（例如，`build.cmd`、`build.sh`、`Makefile`）、`.sln` 文件或单独的 `.csproj` 文件。如果存储库使用自定义构建脚本，则在整个工作流中使用它而不是 `dotnet build`。
2. 运行 `dotnet --version` 以确认已安装 SDK。可空引用类型 (NRTs) 需要 C# 8.0+（`.NET Core 3.0` / `.NET Standard 2.1` 或更高版本）。
3. 打开 `.csproj`（如果属性在存储库级别设置，则为 `Directory.Build.props`）并检查 `<LangVersion>` 和 `<TargetFramework>`。如果项目多目标，请记下所有 TFMs。

> **如果语言版本或目标框架不足，则停止。** 如果 `<LangVersion>` 低于 8.0，或者项目针对默认为 C# 7.x 的框架（例如，没有显式 `<LangVersion>` 的 `.NET Framework 4.x`），则无法按原样启用 NRTs。明确告知用户需要更改的内容（设置 `<LangVersion>8.0</LangVersion>` 或更高版本），或重新定位到 `.NET Core 3.0+` / `.NET 5+`），并询问他们是否想进行此更新并继续，或中止迁移。不要默默进行或假设更新是可接受的。

4. 检查 `<Nullable>` 是否已设置。如果已设置为 `enable`，则跳到步骤 5 以审计剩余警告。
5. 确定项目类型——这将塑造迁移过程中的注解优先级：
   - **库**：首先关注公共 API 合约。公共参数或返回类型上的每个 `?` 都是消费者依赖的合约更改。要精确和保守。
   - **应用程序（Web、控制台、桌面）**：关注边界处的空值安全性——反序列化、数据库查询、用户输入、外部 API 响应。内部管道可以更自由地注解。
   - **测试项目**：注解精确度优先级较低。在测试设置和断言中更自由地使用 `!`，因为空值永远不会预期。专注于确保测试代码干净地编译。

### 步骤 2：选择推广策略

根据代码库的大小和活跃程度选择以下策略之一。建议用户并确认后再继续。

> **多项目解决方案：** 按依赖顺序迁移——首先迁移共享库和核心项目，然后迁移使用它们的依赖项目。首先注释依赖项可以消除其消费者中的级联警告，并防止重复工作。

无论策略如何，**从中心开始向外工作**：从具有很少依赖但广泛使用的核心领域模型、DTO 和共享实用类型开始。首先注释这些可以消除整个代码库中的级联警告，并带来最大的投入回报。然后迁移到依赖核心类型的高级服务、控制器和 UI 代码。这种方法最大限度地减少了每一步的警告数量，并防止因大型项目全局启用而淹没大量警告。最好每个项目或每个层创建至少一个 PR，以保持更改集可审查和专注。如果注释相对较少，单个项目全局启用和单个 PR 可能是合适的。

#### 策略 A — 项目全局启用（小到中等项目）

当项目少于大约 50 个源文件或团队想一次性完成时最佳。

1. 在 `.csproj` 中的 `<PropertyGroup>` 中添加 `<Nullable>enable</Nullable>`。
2. 构建并一次性解决所有警告。

#### 策略 B — 先警告，然后注解（大型或活跃项目）

当代码库很大或由多个贡献者积极开发时最佳。

1. 在 `.csproj` 中添加 `<Nullable>warnings</Nullable>`。这启用了警告，但不会改变类型语义。
2. 构建，修复步骤 3 及以后的警告。
3. 更改为 `<Nullable>enable</Nullable>` 以激活注解——这将触发第二轮警告。
4. 解决步骤 4 及以后的注解阶段警告。

#### 策略 C — 文件逐个（非常大的项目）

适用于大型遗留代码库，其中项目全局启用将产生无法管理的警告数量。

1. 在项目级别设置 `<Nullable>disable</Nullable>`（或省略它）。
2. 在迁移每个文件时在其顶部添加 `#nullable enable`。
3. 按依赖顺序优先处理文件：首先处理共享实用程序和模型，然后处理高级消费者。

> **构建检查点：** 启用 `<Nullable>`（或向第一批文件添加 `#nullable enable`）后，执行**清理构建**（例如，`dotnet build --no-incremental`，或先删除 `bin`/`obj`）。增量构建仅重新编译更改的文件，并将隐藏未更改文件中的警告。记录初始警告计数——这是要从中降低的基线。在修复警告之前，请先确认项目仍然可以编译。在此工作流中的后续构建检查点使用清理构建。

### 步骤 3：修复解引用警告

> **优先级：** 按依赖顺序处理文件——首先处理其他代码依赖的核心模型和共享实用程序，然后迁移到高级消费者。在每个文件中，首先修复公共和受保护成员（这些定义了合约），然后修复内部和私有成员。这种顺序最大限度地减少了级联警告：修复核心类型的注解通常会自动解决其消费者中的警告。

构建项目并处理解引用警告。这些是最常见的：

| 警告 | 含义 | 典型修复 |
|---------|---------|-------------|
| CS8602 | 解引用可能的空引用 | 优先选择仅注解修复：如果空值有效，请使上游类型可空（`T?`），或者如果可以验证在此点值永远不会为空，请使用 `!`。添加空值检查或 `?.` 会改变运行时行为——将它们保留为单独的提交（见零行为更改规则） |
| CS8600 | 将可能的空转换为非可空类型 | 如果方法可以真实地返回空，请将目标类型添加 `?`，或者如果可以验证值在此点永远不会为空，请使用 `!`。添加空值保护会改变运行时行为 |
| CS8603 | 可能的空引用返回 | 如果方法可以真实地返回空，请将返回类型更改为可空（`T?`）。**如果方法可以真实地返回空，请不要用 `!` 抑制**——修复返回类型。这是 NRT 迁移中最重要的规则：非可空返回类型是对每个调用者的承诺，即永远不会返回空 |
| CS8604 | 可能的空引用参数 | 如果空值有效，请将参数标记为可空，或者如果参数可以验证非空，请使用 `!`。在传递之前添加空值检查会改变运行时行为 |

> ❌ **不要使用 `?.` 作为快速修复解引用警告的方法。** 将 `obj.Method()` 替换为 `obj?.Method()` 会无声地改变运行时行为——调用被跳过而不是抛出。仅在您有意容忍空时使用 `?.`。

> ❌ **不要随意使用 `!` 来抑制警告。** 每个 `!` 都是一个声明，即该值永远不会为空。如果该声明是错误的，您隐藏了一个 `NullReferenceException`。添加空值检查或使类型可空而不是添加 `!`。

> ❌ **永远不要使用 `return null!` 来保持返回类型非可空。** 如果方法返回 `null`，返回类型必须为 `T?`。编写 `return null!` 会将空值隐藏在非可空签名后面——调用者信任签名，跳过空值检查，并在运行时获得 `NullReferenceException`。这适用于 `null!`、`default!` 和任何使编译器接受非可空位置空的转换。返回值上 `!` 的唯一可接受用法是当值**可以证明永远不会为空**，但编译器无法看到原因时。

> ⚠️ **除非您打算更改运行时类型，否则不要向值类型添加 `?`。** 对于引用类型，`?` 是元数据仅有的。对于值类型（`int`、枚举、结构），`?` 将类型更改为 `Nullable<T>`，改变方法签名、二进制布局和装箱行为。

**每个警告的决策流程图：**

1. **按设计，此处是否为空值？**
   - **是** → 在声明中添加 `?`（使其可空）。
   - **否** → 跳到步骤 2。
   - **不确定** → 在继续之前询问用户。
2. **您能否证明在此点值永远不会为空？**
   - **是，编译器无法看到的代码路径** → 添加 `!` 并附上解释原因的注释。
   - **是，通过添加保护** → 添加空值检查（`if`、`??`、`is not null`）。
   - **否** → 类型应该是可空的（回到步骤 1——答案是“是”）。

指导：

- 优先使用显式空值检查（`if`、`is not null`、`??`）而不是空值消除运算符（`!`）。
- 仅当您可以证明值永远不会为空，但编译器无法看到时，才使用空值消除运算符，并添加解释原因的注释。
- 保护子句库（例如，Ardalis.GuardClauses、Dawn.Guard）通常用 `[NotNull]` 装饰参数，这会在保护调用后缩小空状态。在 `Guard.Against.NullOrEmpty(value, nameof(value))` 后，编译器已经将 `string?` 缩小为 `string`——不要在后续分配中添加冗余的 `!`。在假设编译器需要帮助之前，检查保护方法是否使用 `[NotNull]`。
- 当方法真实地返回空时，将返回类型更改为 `T?`——不要在非可空签名后面隐藏空值。
- `Debug.Assert(x != null)` 像断言检查一样向编译器提供空状态提示。在方法或块的顶部使用它，以通知流分析器关于不变量并消除该作用域中的后续 `!` 运算符。注意：`Debug.Assert` 通知编译器，但在发布构建中被剥离——它不会在运行时保护免受空值影响。对于公共 API 边界，优先使用显式空值检查或 `ArgumentNullException`。
- 如果您发现自己在每个内部方法的调用站点添加 `!`，请考虑使该参数可空。保留 `!` 用于编译器确实无法证明非空性的情况。
- 当布尔返回值的辅助方法的结果保证可空参数非空时（例如，`if (IsValid(x))` 意味着 `x != null`），优先添加 `[NotNullWhen(true)]` 到辅助方法的参数，而不是在每个调用站点使用 `!`。这是一个仅元数据的更改（没有行为更改），可以消除下游的 `!` 运算符，同时向编译器提供真实的流信息。
- 对于在构造后始终设置的字段（例如，由框架、`Init()` 方法或构建模式设置），优先在字段声明上使用 `= null!` 而不是在每个使用站点添加 `!`。被访问 50 次的字段应该有一个 `= null!`，而不是 50 个 `field!` 断言。这使字段在类型系统中保持非可空，同时承认延迟初始化。在可能的情况下，在初始化方法上添加 `[MemberNotNull]`。
- 对于返回约束类型参数 `default` 的泛型方法（例如，`FirstOrDefault<T>`），使用 `[return: MaybeNull] T` 而不是 `T?`。在约束泛型上写 `T?` 改变了值类型签名到 `Nullable<T>`，改变了方法签名和二进制布局。[return: MaybeNull] 保留了原始签名，同时传达返回可能为空（对于引用类型）。
- LINQ 的 `Where(x => x != null)` 不会将 `T?` 缩小为 `T`——编译器无法跟踪通过传递给泛型方法的 lambda 的空值。使用 `source.OfType<T>()` 以正确类型缩小过滤空值。

> **构建检查点：** 修复解引用警告后，构建并确认仍然没有 CS8602/CS8600/CS8603/CS8604 警告，然后迁移到注解警告。

### 步骤 4：注释声明

首先决定每个成员的**预期空值性**，基于其设计目的——这个参数是否接受空值？这个返回值是否可能为空？相应地注释，然后解决任何结果警告。不要让警告驱动您的注释；那样会导致过度注释 `?` 或分散 `!` 以抑制编译器。

> ❌ **切勿让警告驱动注解。** 首先确定每个成员的预期可空性，然后再添加注解。为了消除警告而到处添加 `?` 会违背目的——调用方随后必须添加不必要的空值检查。到处添加 `!` 会掩盖 bug。

> ⚠️ **返回类型必须反映语义上的可空性，而不仅仅是让编译器满意。** 一个常见错误是，因为实现中使用了 `default!` 或满足编译器的强制转换，而从返回类型中移除 `?`。如果方法在设计上可能返回 null，其返回类型必须是可空的——无论编译器是否发出警告。关键模式：
> - 名为 `*OrDefault`（`FirstOrDefault`、`SingleOrDefault`、`FindOrDefault`）的方法 → 返回类型必须可空（`T?`、`object?`、`dynamic?`），因为“或默认”对于引用类型意味着“或 null”。
> - `ExecuteScalar` 和类似的数据库方法 → 返回类型必须为 `object?`，因为没有匹配行时结果可以是 `DBNull.Value` 或 null。
> - `Find`、`TryGet*`（out 参数）和查找方法 → 当项目可能不存在时，返回类型应为可空。
> - 任何文档或设计规定在失败、未找到或空输入时返回 null 的方法 → 可空的返回类型。
>
> 当实现通过 `!` 或 `default!` 隐藏 null 时，编译器无法捕获返回类型上*缺失*的 `?`。这使得注解对消费者而言是错误的——他们信任非可空签名并跳过空值检查，导致在运行时发生 `NullReferenceException`。

> ⚠️ **不要移除现有的 `ArgumentNullException` 检查。** 非可空参数注解仅仅是编译期提示——它无法在运行时防止 null。使用旧版 C#、其他 .NET 语言、反射或 `!` 的调用者仍然可以传入 null。

> ⚠️ **标记缺少运行时 null 验证的公共 API 方法——但不要添加检查。** 在添加注解时，检查每个 `public` 和 `protected` 方法：如果参数是非可空的（`T`，而非 `T?`），则应该有运行时 null 检查（例如，`ArgumentNullException.ThrowIfNull(param)` 或 `if (param is null) throw new ArgumentNullException(...)`）。如果没有，运行时传入的 null 会导致方法体深处发生 `NullReferenceException`，而不是在入口处产生清晰的 `ArgumentNullException`。添加 null 防护属于运行时行为变更，不得作为 NRT 迁移的一部分。相反，询问用户是否希望在该位置插入 `// TODO: 考虑添加 ArgumentNullException.ThrowIfNull(param)` 注释。这对于库尤为重要，因为调用者可能未启用 NRT。

> **具有明确 null 行为定义的方法应接受可空参数。** 如果方法能优雅地处理 null 输入——返回 null、返回默认值或返回失败结果而非抛出异常——参数应为 `T?`，而不是 `T`。BCL 遵循此约定：`Path.GetPathRoot(string?)` 对 null 输入返回 null，而 `Path.GetFullPath(string)` 会抛出异常。仅当 null 会导致异常时才使用非可空参数。将实际允许 null 的方法参数标记为非可空，会迫使调用者在调用前添加不必要的空值检查。
>
> **灰色地带：** 当参数既未经验证、未清理、也未在文档中注明 null 行为时，请考虑：(1) 在您自己的代码库中是否曾传入 null？如果是 → 可空。(2) 调用者是否可能将 null 用作“默认”值或无操作占位符？如果是 → 可空。(3) 同一区域中的类似方法是否接受 null？如果是 → 为保持一致性，设为可空。(4) 如果该方法 largely 对 null 无感知且碰巧能工作，但 null 对 API 的目的没有语义意义 → 非可空。如果在参数的可空与非可空之间犹豫不决，优先选择可空——它更安全，且以后可以收紧。

在解决解引用警告后，处理注解警告：

| 警告 | 含义 | 典型修复 |
|---------|---------|-------------|
| CS8618 | 非可空字段/属性未在构造函数中初始化 | 初始化该成员，使其可空（`?`），或使用 `required`（C# 11+）。对于总是在构造后但在构造函数外部设置的字段（例如，由框架生命周期方法、`Init()` 调用或建造者模式设置），使用 `= null!` 来声明意图，同时保持字段在每个使用位置均为非可空。如果辅助方法初始化字段，请为其添加 `[MemberNotNull(nameof(field))]`，以便编译器知道调用该字段后该字段为非 null |
| CS8625 | 无法将 null 字面量转换为非可空类型 | 使目标类型可空或提供非 null 值 |
| CS8601 | 可能的 null 引用赋值 | 与 CS8600 相同的技巧 |

对于每种类型，请决定：**该成员是否应为 null？**

- **是** → 在其声明中添加 `?`。
- **否** → 确保它在每个构造函数路径中都已初始化，或将其标记为 `required`（C# 11+）。
- **否，但在构造函数之后设置**（例如，由框架方法、建造者或两阶段初始化模式设置） → 在字段声明中使用 `= null!`。这使得字段在使用它的任何地方都保持非可空类型，同时告诉编译器“我保证在访问之前它会设置”。这远胜于在每个使用位置添加 `!`——一个被访问 50 次的字段需要 50 个 `!` 运算符，而不是一个 `= null!`。如果初始化是由特定方法完成的，也请考虑在该方法上使用 `[MemberNotNull(nameof(field))]`。

首先将注解精力集中在公共和受保护 API 上——这些定义了消费者依赖的契约。内部和私有代码可以更自由地容忍 `!`，因为它不影响外部调用者。

> **公共库：跟踪破坏性变更。** 如果项目是供其他人使用的库，请创建一个 `nullable-breaking-changes.md` 文件（或等效文件），并记录每个可能影响消费者的公共 API 变更。虽然为引用类型添加 `?` 仅是元数据层面的变更且不是二进制破坏性的，但对于启用了 NRT 的消费者而言，它是源破坏性的——他们将收到新的警告或错误。需要记录的关键变更：
> - 返回类型从 `T` 更改为 `T?`（消费者现在必须处理 null）
> - 参数从 `T?` 更改为 `T`（消费者不再能传入 null）
> - 参数从 `T` 更改为 `T?`（调用者中现有的 null 检查变得多余——影响较低但值得记录）
> - 值类型参数或返回值的添加了 `?`（将 `T` 更改为 `Nullable<T>` —— 二进制破坏性）
> - 在没有之前没有 guard 的地方添加了新的 `ArgumentNullException` 防护
> - 在注解期间发现并修复的任何行为变更（例如，一个静默接受 null 的方法现在会抛出异常）
>
> 向用户展示此文件以供审查。它还可以作为发布说明的基础。

特别关注以下方面：

- **DTO 与领域模型**：根据类的角色应用不同的可空性策略。**DTO 和序列化模型**跨越信任边界（JSON、表单、外部 API）——除非由序列化器强制，否则其属性默认应为可空，因为反序列化的数据始终可以是 null，无论声明的类型如何。使用 `required`（C# 11+）、`[JsonRequired]`（.NET 7+）或运行时验证来强制非 null 约束。**领域模型**代表内部不变量——优先使用带有构造函数强制的非可空属性，使无效状态无法表示。这种区别是迁移中最常出错的地方：将 DTO 视为领域模型会导致运行时的 `NullReferenceException`；将领域模型视为 DTO 会导致到处添加不必要的 null 检查。
- **事件处理程序和委托**：模式 `EventHandler? handler = SomeEvent; handler?.Invoke(...)` 是惯用的。
- **结构体中的引用类型字段**：使用 `default(T)` 时，结构体中的引用类型字段为 null。如果 `default` 对于该结构体是有效用法，则这些字段必须为可空。如果从不期望使用 `default`（该结构体仅由特定 API 创建），则保持它们为非可空，以避免让每个消费者都承担不必要的 null 检查负担。
- **Dispose 后的状态**：如果字段或属性在对象整个有用生命周期内为非 null，但在 `Dispose` 后可能变为 null，请保持其非可空。在释放后使用对象违反了契约——不要为此情况削弱注解。
- **重写和接口实现**：重写方法可以返回比基类方法声明的更严格（非可空）的类型。如果您的实现从不返回 null，但基类/接口返回 `T?`，您可以将重写声明为返回 `T`。参数类型必须与基类完全匹配。
- **广泛重写的虚方法返回类型**：对于许多类重写的虚/抽象方法，请考虑现有的重写是否实际返回 null。如果它们经常如此（如 `Object.ToString()`），将返回类型注解为 `T?` —— 调用者需要知道。如果返回 null 的重写极其罕见（如 `Exception.Message`），将其注解为 `T`。对于广泛重写的虚方法，如果犹豫不决，优先选择 `T?`。
- **`IEquatable<T>` 和 `IComparable<T>`**：引用类型应实现 `IEquatable<T?>` 和 `IComparable<T?>`（带有可空的 `T`），因为调用者通常会向 `Equals` 和 `CompareTo` 传入 null。
- **`Equals(object?)` 重写**：为 `Equals(object? obj)` 重写的参数添加 `[NotNullWhen(true)]` —— 如果 `Equals` 返回 `true`，则保证参数非 null。这让调用者可以在相等性测试后跳过冗余的空值检查。

> **构建检查点：** 在注解声明后，进行构建并确认在继续处理可空属性之前，剩余的 CS8618/CS8625/CS8601 警告为零。

### 步骤 5：为高级场景应用可空属性

当简单的 `?` 注解无法表达空值契约时，请应用来自 `System.Diagnostics.CodeAnalysis` 的属性——参见 [references/nullable-attributes.md](references/nullable-attributes.md) 以获取完整的属性表（`[NotNullWhen]`、`[MaybeNullWhen]`、`[MemberNotNull]`、`[AllowNull]`、`[DisallowNull]`、`[DoesNotReturn]` 等）及每个属性的使用指导。

> **构建检查点：** 在应用可空属性后，进行构建以验证属性是否解决了目标警告且未引入新警告。

### 步骤 6：清理抑制

> **可选：** 重新运行 `scripts/Get-NullableReadiness.ps1` 以获取项目中 `#nullable disable` 指令、`!` 运算符和 `#pragma warning disable CS86xx` 抑制的当前数量。

1. 搜索任何作为临时变通方案添加的 `#nullable disable` 指令或 `!` 运算符。
2. 对于每一个，确定该抑制是否仍需要。
3. 移除不再必要的抑制。对于保留的任何抑制，添加注释说明原因。
4. 搜索 `#pragma warning disable CS86` 以查找被抑制的可空警告，并评估是否可以直接修复底层问题。

> **构建检查点：** 在移除抑制后，再次构建——移除 `#nullable disable` 或 `!` 可能会暴露出需要修复的新警告。

### 步骤 7：验证

1. 构建项目并确认可空警告为零。
2. 在项目文件（或整个仓库的 `Directory.Build.props`）中添加 `<WarningsAsErrors>nullable</WarningsAsErrors>`，以永久防止可空性回归。这是项目文件中等同于 `dotnet build /warnaserror:nullable` 的设置。
3. 运行现有测试以确认没有回归。
4. 如果项目是库，检查公共 API 表面，以验证可空注解是否匹配预期契约（接受 null 的参数为 `T?`，拒绝 null 的参数为 `T`）。

> **在声称迁移完成之前进行验证。** 零警告本身并不意味着迁移正确。在报告成功之前：(1) 抽查公共 API 签名——确认 `?` 注解符合实际设计意图，而不仅仅是编译器沉默；(2) 验证未添加改变运行时行为的 `?.` 运算符（在 diff 中搜索 `?.`）；(3) 确认未移除任何 `ArgumentNullException` 检查；(4) 检查 `!` 运算符很少使用，且每个都有佐证注释。

## 验证

- [ ] 项目文件包含 `<Nullable>enable</Nullable>`（或针对逐文件策略的逐文件 `#nullable enable`）
- [ ] 构建产生零 CS86xx 警告
- [ ] 已添加 `<WarningsAsErrors>nullable</WarningsAsErrors>` 到项目文件中以防止回归
- [ ] 测试通过且无回归
- [ ] 除非有注释证明其合理性，否则不保留 `#nullable disable` 指令
- [ ] 空值容恕运算符（`!`）使用很少，每个都有佐证注释
- [ ] 公共 API 签名准确反映空值契约
- [ ] 对于公共库：在 `nullable-breaking-changes.md` 中记录破坏性变更并由用户审查

### 代码审查清单

可空迁移更改需要比典型 diff 更广泛的审查：

1. **验证无行为变更**：确认 `?` 和 `!` 是仅有的添加——没有意外的 `?.`，没有移除的 null 检查，没有新的分支。生成的 IL 除了可空元数据外不应改变。
2. **审查显式注解变更**：对于添加到参数或返回类型的每个 `?`，确认其符合预期设计。该方法是否真的接受 null？它是否真的可能返回 null？
3. **审查范围内的未变更 API**：启用 `<Nullable>enable</Nullable>` 会隐式使该范围内每个未注解的引用类型变为非可空。扫描未变更的公共成员中实际接受 null 但未注解的参数。

## 常见陷阱

| 陷阱 | 解决方案 |
|------|--------|
| 在代码中到处使用 `!` 来抑制警告 | 空值忽略运算符会隐藏错误。添加空值检查或改为使用可空类型 |
| 将所有类型标记为 `T?` 以快速消除警告 | 过度使用 `?` 会违背其目的——调用者必须添加不必要的空值检查。仅在空值是有效值时使用 `?` |
| 构造函数未初始化所有不可空成员 | 在每个构造函数中初始化字段和属性，使用 `required`（C# 11+），或使成员可空 |
| 序列化绕过构造函数——不可空 ≠ 运行时安全 | 序列化器在创建对象时不调用构造函数，因此不可空的 DTO 属性在运行时仍可能为空。有关详细指导，请参阅第 4 步中的“DTOs vs 域模型” |
| 生成的代码产生警告 | 如果生成的文件包含 `<auto-generated>` 注释，则它们会自动排除在空值分析之外。如果警告仍然存在，请在生成的文件顶部添加 `#nullable disable`，或配置 `.editorconfig` 将 `generated_code` 设置为 `true` |
| 多目标项目和旧版 TFMs | NRT 注解可以在旧版 TFMs（例如 .NET Standard 2.0）上使用 C# 8.0+ 编译，但像 `[NotNullWhen]` 这样的空值属性可能不存在。使用 NuGet 的 `Nullable` 多重包装程序，或在内部定义属性 |
| 升级依赖项后警告重新出现 | 依赖项添加了空值注解。这是预期的且有益的——按照步骤 3-5 修复新警告 |
| 在注解时意外更改行为 | 为类型添加 `?` 或为表达式添加 `!` 仅是元数据注释，不会更改生成的 IL。但将 `obj.Method()` 替换为 `obj?.Method()`（空条件）会改变运行时行为——调用会被静默跳过而不是抛出异常。仅在您有意容忍空值时使用 `?.`，而不是作为快速修复警告的临时方案 |
| 为值类型（枚举、结构）添加 `?` | 对于引用类型，`?` 是一个元数据注解，在运行时没有效果。对于 `int` 或枚举等值类型，`?` 会将类型更改为 `Nullable<T>`，从而改变方法签名、二进制布局和装箱行为。请仔细确认您只将 `?` 添加到引用类型，除非您确实打算使值类型可空 |
| 移除现有的空值参数验证 | 不可空注解仅是编译时注解——调用者仍可以在运行时传递空值。保留现有的 `ArgumentNullException` 检查。有关详细信息，请参阅第 4 步 |
| `var` 根据分配的表达式推断空值性 | 使用 `var` 时，推断的类型会包含分配表达式的空值性，这与显式声明 `T` vs `T?` 相比可能令人意外。流分析会从该点确定实际的空值状态，但推断的声明类型可能包含您未预期的空值性。如果声明处的精确空值性很重要，请使用显式类型而不是 `var` |
| 消费未注解（忽视空值）的库 | 当依赖项未选择使用空值注解时，编译器将其所有类型视为“忽视”——您在解引用或分配空值时不会收到警告。这会给人一种虚假的安全感。将忽视 API 的返回值视为可能为空，特别是对于理论上可能返回空值的方法（字典查找、`FirstOrDefault` 风格的调用）。在可能的情况下升级依赖项或包装调用 |
