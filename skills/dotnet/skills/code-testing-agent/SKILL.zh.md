# 代码测试生成技能

一种使用协调的多智能体管道为任何编程语言生成全面、可工作的单元测试的 AI 驱动技能。

## 不可协商的执行合同

在编辑**之前**对范围进行分类：

- **广泛**（项目/包范围的套件，或多个生产文件/模块）：在实现之前，在解析的非暂存 `<TESTAGENT_DIR>` 中创建 `research.md` 和 `plan.md`，然后在最终测试质量审查后在那里创建 `status.md`。当 `code-testing-generator` 可用时，在实现之前调用该命名的自定义智能体；不要用带有相同标签的通用子智能体替换它，也不要内联实现广泛请求。如果状态文件不存在，则广泛工作流不完整。
- **聚焦**（用户明确限制工作范围到一个函数/类/文件或一个缺失的方法）：不要创建中间状态文件或扩展到多个智能体。一个稀疏的项目范围请求即使在只有一个源模块存在时仍然是广泛的。

对于任何范围，运行最相关的窄测试命令直到干净退出。保持交接成比例：对于一到三个聚焦要求，使用在 **要求覆盖** 标签下的紧凑的要点列表来命名测试和成功命令；对于更广泛或多要求的工作，使用 `要求 | 证据` 表。必须为每个请求的行为引用一个确切的测试名称。

中间状态文件是内部工作数据，永远不会是交付物。保持 `<TESTAGENT_DIR>` 非暂存，永远不要将其或其文件放在版本控制的 workspace 内容中，永远不要修改 `.gitignore` 来隐藏它们。

将完整性视为一个要求矩阵，而不是测试计数的靶子。给每个独立请求的状态、边界、错误路径或交互分配自己的具体断言。只有在一次执行真正证明整个请求的组合时才组合用例；不要让参数化 happy-path 用例代替空状态、无效区分器或边界之前的/边界处的/边界之后的用例。
对于命名了多个生产模块或层的广泛请求，给每个命名的模块直接测试其非平凡公共行为。跨模块测试证明组合，但不要用它来替代请求的模块级覆盖。根据行为矩阵判断范围，而不是匹配或超过原始测试计数。

对于**广泛或全面**的请求，显式矩阵是底线，而不是上限。将每个请求的模块或层视为一个清单标题，而不是一个行为：将其扩展为有界公共操作及其不同的验证路径、分支、边界、交互和状态转换。在满足显式矩阵后，检查每个目标 API 对于提示未命名的可观察等价分区和不变量：身份、空、单例和代表性内部输入；精确边界加上一个立即相邻的值；无效分区；以及排序、单调性、溢出、容量、截断或由实现隐含的状态不变量。为每个不同的分区添加一个与变异相关的用例，对于证明相同行为的兄弟用例，仅使用参数化或表格驱动用例。通过覆盖阈值来验证，而不是范围停止条件。当剩余输入执行相同的分支和不变量时停止，而不是仅仅当显式清单完成时；永远不要仅仅为了提高计数而添加用例。

## 何时使用此技能

当你需要时使用此技能：

- 为整个项目或特定文件生成单元测试
- 改进现有代码库的测试覆盖率
- 创建遵循项目约定的测试文件
- 编写实际编译和通过的测试
- 为新功能或未测试的代码添加测试
- 生成或扩展 MSTest 套件；在本文技能建立范围和项目约定后加载 `writing-mstest-tests` 作为支持性指导

## 何时不用

- 运行或执行现有测试（使用 `run-tests` 技能）
- 在测试框架之间迁移（使用迁移技能）
- 回答 MSTest API/模式或现代化问题，但问题不要求生成测试（使用 `writing-mstest-tests`）
- 调试失败的测试逻辑

## 工作原理

此技能协调多个专业智能体在 **研究 → 规划 → 实现** 管道中：

### 管道概述

```text
┌─────────────────────────────────────────────────────────────┐
│                     测试生成器                          │
│ 协调整个管道并管理状态            │
└─────────────────────┬───────────────────────────────────────┘
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
┌───────────┐  ┌───────────┐  ┌───────────────┐
│ 研究者   │  │  规划者   │  │  实现者   │
│           │  │           │  │               │
│ 分析代码库 │  │ 创建      │  │ 编写每个阶段的测试  │
│           │→ │ 阶段化计划 │→ │               │
└───────────┘  └───────────┘  └───────┬───────┘
                                      │
                    ┌─────────┬───────┼───────────┐
                    ▼         ▼       ▼           ▼
              ┌─────────┐ ┌───────┐ ┌───────┐ ┌───────┐
              │ 构建者   │ │ 测试者 │ │ 修复者 │ │ 格式化器 │
              │         │ │       │ │       │ │       │
              │ 编译代码 │ │ 运行测试 │ │ 修复错误 │ │ 格式化代码 │
              └─────────┘ └───────┘ └───────┘ └───────┘
```

## 分步说明

### 第 1 步：确定用户请求

确保你理解用户在请求什么以及范围是什么。
当用户对测试样式、覆盖目标或约定没有明确要求时，从 [unit-test-generation.prompt.md](unit-test-generation.prompt.md) 源引指南。此提示提供了发现约定、参数化策略、行为导向覆盖和语言特定模式的最佳实践。

### 第 2 步：在调用任何东西之前确定请求的规模

根据范围匹配机械。在一个文件请求上运行完整管道会浪费回合和工具调用，而不会改进测试。

| 范围 | 看起来像什么 | 如何运行它 |
| --- | --- | --- |
| **聚焦** | 一个函数、类或文件；"仅测试 X"；将现有套件扩展为缺失的用例 | 跳过中间状态文件和子智能体扩展。在脑海中保留要求清单（或保存在最终表格中），仅读取目标和一个相邻测试以获取约定，编写测试，运行最窄的测试命令，直接内联审查自己的断言。 |
| **广泛** | 一个项目、包或模块集；"全面套件"；跨多个文件清除覆盖阈值 | 在第 3 步中运行完整的研究 → 规划 → 实现管道，带有 `<TESTAGENT_DIR>` 下的中间状态文件和下面的完成合同。 |

当不确定时，从聚焦开始，如果请求跨越多个文件，再升级。升级成本一个额外回合；在聚焦请求上运行广泛管道会花费几个回合。

在结束聚焦请求之前，一起检查所有三个条件：

1. 每个命名的行为都有一个具体断言，包括每个请求的边界或错误路径；
2. 窄测试命令成功退出；
3. 最终交接将那些行为映射到确切的测试名称，并引用该成功命令。

不要用通用覆盖区域列表替换要求级别的证据。

### 第 3 步：调用测试生成器（广泛范围）

首先调用命名的 `code-testing-generator` 自定义智能体，并带上你的测试生成请求。不要使用一个名为 `code-testing-generator` 的通用/通用目的子智能体：

```text
为 [要测试的路径或描述] 生成单元测试，遵循 [unit-test-generation.prompt.md](unit-test-generation.prompt.md) 指南。将当前 workspace 视为权威的，即使它很稀疏、看起来很空洞、合成或缺少跟踪文件；永远不要恢复或重建它，包括使用 `git checkout`、`git restore`、`git reset` 或 `git clean`。
```

测试生成器将自动管理整个管道。

如果 `code-testing-generator` 不可用，不要跳过工作流。直接执行相同的研究 → 规划 → 实现序列，按照下面描述的解决 `<TESTAGENT_DIR>`，在那里创建中间状态文件，并应用相同的完成合同。

对于广泛范围，在创建中间状态文件之前解决一个绝对 `<TESTAGENT_DIR>`：

1. 优先使用主机提供的会话工件或临时目录。
2. 否则，在 Git 工作树中运行 `git rev-parse --path-format=absolute --git-path testagent`；这返回一个在工作树特定 Git 元数据中的路径，无法暂存。
3. 在 Git 外部，在操作系统临时目录下创建一个唯一目录。

将绝对目录传递给每个管道智能体。路径可能在仓库的 `.git` 元数据目录中，但它必须不是版本控制的 workspace 内容，不会出现在 `git status` 中，或可以被暂存。

### 第 4 步：使用有界上下文执行

对于多文件请求：

1. 在实现之前，将每个显式用户要求转换为一个清单。包括请求的层、要模拟的协作者、边界情况、集成、覆盖阈值和报告工件。逐字复制多条件要求——它们必须每个映射到一个测试，该测试执行整个组合。
2. 只研究请求的模块或项目，并将清单和一个紧凑的目标清单写入 `<TESTAGENT_DIR>/research.md`。
3. 重用清单、符号引用和确定性配对工具，而不是读取每个源文件和测试文件。
4. 对于 C#、Python、TypeScript/JavaScript、Go、Java、Rust、Ruby、Kotlin、Swift、PowerShell 或 C++ 的多文件范围，运行一次 `find-untested-sources` 并消费其配对和建议路径输出；不要手动重复该发现。
5. 一次规划每个目标文件，然后按顺序实现阶段。将每个清单项映射到至少一个具体测试或解释为什么它被阻塞。
6. 在修复周期中构建和测试窄目标。仅在结束时对广泛工作运行 workspace 级验证，当仓库合同要求该入口点，或更改会影响其他项目时。
7. 在报告成功之前，重新打开生成的测试，并对照具体测试名称和断言验证每个清单项。仅覆盖本身不是证明请求的模拟接缝、边界、状态转换或属性组合被测试的证据。
8. 只有当仓库没有代表性测试且基础扩展不足时，才从 `code-testing-extensions` 中读取语言示例。
9. 对于 .NET，在选择命令或创建文件之前，区分 SDK 风格与经典非 SDK。在经典项目中，保留 `packages.config`、现有框架/模拟版本和自定义基础固定件，将每个新测试文件添加到项目显式的 `<Compile Include>` 项中，并使用仓库的 MSBuild/test-runner 命令。永远不要为了生成测试而现代化项目或依赖堆栈。
10. 对于 MSTest，在选择异常断言之前检查固定包版本。MSTest 3.5.x 使用 `Assert.ThrowsException<T>`；不要用 `[ExpectedException]`、`Assert.Throws<T>` 或 `Assert.ThrowsExactly<T>` 替换它。

### 完成合同

每个范围必须满足下面的 3-5 点。1 和 2 是 **广泛范围** 的工件：在聚焦请求上，相同的推理直接发生，并且不编写中间状态文件。

在所有这些都为真之前，不要报告完成：

1. *(广泛范围)* `<TESTAGENT_DIR>/research.md` 记录了有界目标清单、现有测试约定和接受清单。
2. *(广泛范围)* `<TESTAGENT_DIR>/plan.md` 将每个清单项映射到计划的测试或显式阻塞器。
3. 生成的测试使用最相关的窄测试命令编译并通过。
4. 每个显式用户要求都有一个具体测试和断言支持。即使覆盖已经通过，也要修复缺失的模拟接缝、边界情况、状态转换和属性组合。在最终摘要中，为每个清单项至少引用一个生成的测试名称，以便完成可审计；如果一个项目没有测试可以引用，继续实施或报告它为阻塞。对于非行为要求，如脚手架、范围限制、命令或覆盖工件，引用相关文件、命令或报告，而不是强迫测试名称映射。
   通过覆盖的套件即使测试较少也不是自动较弱的：通过是否每个独立请求的行为都有直接、非冗余的证据来判断完整性，而不是原始测试量。
   对于广泛/全面范围，还验证在有界目标 API 中发现的每个可观察等价分区和不变量是否有一个与变异相关的用例，即使提示没有命名它。
   当请求命名多个模块时，验证除了任何端到端组合测试外，每个模块自己的非平凡公共行为是否都有直接测试证据。
5. 审查生成的测试以查找行为差距和弱断言。在广泛范围内，当可用时，调用 `test-gap-analysis` 和 `assertion-quality`，并将发现和修复记录在 `<TESTAGENT_DIR>/status.md` 中。在聚焦范围内，进行等效审查——重新阅读每个生成的断言与源代码——而无需启动额外回合。

最终响应必须提供按要求证据。对于一到三个聚焦要求，使用在 **要求覆盖** 标签下的紧凑要点；对于更广泛范围，使用 `要求 | 证据` 表。行为证据引用确切的生成测试名称。非行为证据引用相关项目文件、验证命令或覆盖报告。通用测试区域列表不能替代它。

在每个证据项目中保留用户的确切含义；只有在措辞区分了要求的组合时才逐字引用。一个仅仅执行相同协作者的测试并不能满足关于它们交互的要求，并且每个类的要求需要一个每个类引用。

**引用干净的运行，而不是尝试。** 最终证据背后的命令必须成功完成：引用最终的通过测试摘要，并在请求阈值时，引用一个退出为 0 的运行产生的每个模块覆盖表。如果最后一个覆盖运行退出非零，请修复并重新运行，然后再报告；永远不要从失败或部分运行中推断阈值清除。

在报告之前，检查最终工作树更改，并确认 `research.md`、`plan.md`、`status.md` 和任何其他中间状态文件不在打算提交的更改中。

## 状态管理

广泛范围运行将中间状态文件存储在非暂存的 `<TESTAGENT_DIR>` 中，该目录由主机临时存储、Git 元数据或操作系统临时支持。聚焦请求不会创建这些文件：

| 文件                     | 目的                      |
| ------------------------ | ---------------------------- |
| `<TESTAGENT_DIR>/research.md` | 代码库分析结果    |
| `<TESTAGENT_DIR>/plan.md`     | 阶段化实现计划   |
| `<TESTAGENT_DIR>/status.md`   | 最终质量审查和修复   |

## 要求

- 项目必须配置了构建/测试系统
- 应安装测试框架（或可安装）
- 需要安装带有 GitHub Copilot 扩展的 VS Code

当现有构建/测试工具链可用时，支持经典非 SDK .NET 项目。当当前机器上不可用时，代理仍可添加并注册兼容版本的测试，但必须报告执行受阻，而不是替换 `dotnet test`。

## 故障排除

### 测试不编译

`code-testing-fixer` 代理将尝试解决编译错误。检查 `<TESTAGENT_DIR>/plan.md` 以获取预期的测试结构。调用 `code-testing-extensions` 技能，并阅读特定语言的扩展文件以获取错误代码参考（例如，`dotnet.md` 用于 .NET）。

### 测试失败

生成测试中的大多数失败是由断言中的**错误预期值**引起的，而不是生产代码错误：

1. 阅读实际测试输出
2. 阅读生产代码以理解正确行为
3. 修复断言，而不是生产代码
4. 不要仅为了使测试通过而将测试标记为 `[Ignore]` 或 `[Skip]`

### 检测到错误的测试框架

在初始请求中指定您首选的框架："为 Jest 生成测试..."

### 依赖环境的测试失败

依赖外部服务、网络端点、特定端口或精确时间的测试在 CI 环境中会失败。改为专注于带模拟依赖的单元测试。

### 更广泛的验证失败

在实施过程中，仅构建和测试狭窄目标。仅在仓库契约使用该入口点，或目标变更可能影响其他项目时，才运行解决方案或工作区级命令。不要将聚焦的测试请求变成无条件的完整非增量构建。
