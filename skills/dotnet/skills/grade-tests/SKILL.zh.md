# 评分测试

对一组精选的测试方法进行评分，并生成一份紧凑的、适合 PR 评论的报告：每个测试方法占一行，包含字母等级、分数段和一句解释等级的评语。这项技能**不会自行发现测试**——调用者（通常是 PR 自动化工作流或持有特定列表的人工审阅者）提供要评分的测试方法。

> **语言特定指南**：调用 `test-analysis-extensions` 技能以发现可用的扩展文件，然后阅读与目标代码库的语言和框架匹配的文件（例如，`extensions/dotnet.md`、`extensions/python.md`、`extensions/typescript.md`、`extensions/go.md`）。你必须在使用断言 API 或惯用模式之前阅读相关的扩展文件，因为断言 API 和惯用模式在不同的框架中差异很大。

## 为什么每个测试单独评分

范围级审核（`test-anti-patterns`、`assertion-quality`、`test-smell-detection`）可以生成优秀的诊断报告，但它们很难作为简短的 PR 评论来消费。PR 的审阅者主要想知道：*对于这个 PR 添加或修改的测试，它们好吗？*这项技能用一个每行一个测试的裁决来回答这个问题，适合放在评论表格中。

## 使用场景

- PR 自动化工作流需要发布评论来评分 PR 中引入或修改的测试。
- 审阅者有一个特定的测试列表（文件、类、方法列表或 diff 片段），并希望得到每个测试的裁决而不是范围报告。
- 维护者希望分派哪些 N 个测试在贡献中值得后续改进。

## 不使用场景

- 调用者需要一个完整的范围审核或比较指标——使用 `test-anti-patterns`（实用）或 `test-smell-detection`（正式），并让 `test-quality-auditor` 代理来协调。
- 调用者想要*编写*新的测试——使用 `code-testing-generator`（任何语言）或 `writing-mstest-tests`（MSTest 特定）。
- 调用者想要测量代码覆盖率或 CRAP 分数——使用 `coverage-analysis` 或 `crap-score`（.NET 仅限）。
- 调用者想要直接在测试代码中修复问题——调用适当的编辑技能。
- 没有提供特定的测试列表。不要尝试评分工作区中的所有测试；向调用者索要明确的列表或范围。

## 输入

| 输入 | 必填 | 描述 |
|------|------|------|
| 测试方法 | 是 | 要评分的范围。提供以下之一：(a) 测试方法名称的明确列表（完全限定，例如 `Namespace.ClassName.TestMethodName`）；(b) 一个或多个文件路径加上明确的指令来评分这些文件中声明的每个测试；或 (c) 一个 diff 片段 / PR 标识符，其更改的测试应被评分。文件路径在方法名称在工作区中明确时是推荐但可选的。像 *"grade my tests"* 这样的模糊请求 upfront（见步骤 0）会被拒绝；这项技能是用于精选输入，不会自动评分整个工作区。 |
| 测试主体 / 跨度 | 推荐 | 每个测试方法的精确源代码行。如果省略，则从列出的文件中读取。 |
| 生产代码 | 否 | 要测试的代码，用于判断断言是否覆盖了有意义的行為。当不可用时，将相关发现标记为 "未验证" 而不是猜测。 |
| diff 上下文 | 否 | 当评分 PR 更改时，每个测试方法的统一 diff 有助于专注于实际更改的内容。 |

### 步骤 0：验证输入

在其他任何操作之前，检查调用者是否提供了以下之一：

1. 一个明确的测试方法名称列表，**或**
2. 一个或多个文件路径加上明确的指令来评分这些文件中声明的每个测试（例如，"在 `OrderTests.cs` 中评分每个测试"），**或**
3. 一个 diff 片段或 PR 标识符，其更改的测试应被评分。

如果请求是模糊的（例如，*"Grade my tests"*，*"Are these tests any good?"* 没有范围，*"Review the test suite"*），**不要加载扩展**，**不要读取文件**，**不要评分任何内容**。回复一条简短的消息，要求调用者提供明确的列表 / 文件 / diff，并可选地指向 `test-quality-auditor` 代理或 `test-anti-patterns` 技能进行完整范围分析。到此为止。

## 工作流

### 步骤 1：检测语言并加载扩展

从文件扩展和提供的列表中的测试方法标记中识别目标代码库的语言和测试框架。调用 `test-analysis-extensions` 技能并读取匹配的扩展文件（例如，`extensions/dotnet.md` 用于 MSTest/xUnit/NUnit/TUnit，`extensions/python.md` 用于 pytest，`extensions/typescript.md` 用于 Jest/Vitest，`extensions/go.md` 用于标准的 `testing` 包）。如果输入包含来自多种语言的测试，则加载每个相关扩展，并使用其语言的约定来评分每个测试。

### 步骤 2：解析测试主体

对于输入列表中的每个条目：

1. 如果测试主体直接提供，则直接使用它。
2. 否则，读取给定路径的文件，并通过其完全限定名称定位方法。捕获完整的方法主体，包括属性 / 装饰器 / 固定和测试调用的任何辅助代码。
3. 如果找不到方法，将其记录为 `N/A — 方法未找到` 并继续。永远不要编造主体来评分。

### 步骤 3：评分每个测试

每个测试从等级 **A（分数段 90–100）** 开始，然后严格应用捕获主体中的**可观察问题**进行扣分。不要因为假设性问题（例如，“可以有更多的负断言”）而扣分，除非生产代码明确要求它们并且生产代码是可用的。

当生产代码不可用时，正常评分测试主体中的可观察问题，但不要推断缺失的行为或扣分。在摘要中一次声明 `Production-dependent behavior coverage: Unverified`，以便读者可以将测试主体发现与需要源代码的声明区分开来。

#### 三个子维度

计算三个子等级（每个 A–F）共同决定总体等级。

##### A. 断言强度

读取加载的语言扩展的断言 API 列表，并将测试主体中的每个断言分类。从最高到最低评分：

| 子等级 | 模式 |
|------|------|
| **A** | 至少有一个有意义的值断言（相等性 / 结构性 / 异常 / 状态），并在适当的情况下，附加检查（负断言、类型、集合内容）。模拟调用验证（`Verify`、`toHaveBeenCalledWith`、`Should -Invoke`）和裸断言形式（pytest `assert`、Go `if got != want { t.Errorf(...) }`、Rust `assert!()`）计为真实断言。 |
| **B** | 一个清晰的、有意义的断言，验证测试的行为。 |
| **C** | 只有简单的断言（单个 `IsNotNull` / `toBeDefined` / `assert x is not None`），或断言检查单个字段，而操作产生更丰富的结果。 |
| **D** | 一个自引用 / 同义断言（`Assert.AreEqual(x, x)`、`assert dto.name == dto.name`、无非平凡输入的往返身份验证），或广泛的异常断言（`Assert.ThrowsException<Exception>`）。 |
| **F** | 完全没有断言；**所有**断言都是始终为真的字面量（`Assert.IsTrue(true)`、`assert True`、`expect(true).toBe(true)`）——这些验证什么也没有，等同于没有断言；或所有断言都是无声的未等待（例如，`expect(promise).resolves.toBe(x)` 没有 `await`/`return`，异步 TUnit/xUnit `Assert.ThrowsAsync` 没有 `await`，pytest-asyncio 中未等待的协程）。 |

异常和错误路径测试（`Assert.ThrowsException<T>`、约束的 `pytest.raises`、`expect(fn).toThrow`、`assertThrows`、`#[should_panic]`、`Should -Throw`、`EXPECT_THROW` 或 Go 代码验证预期的非 nil 错误）本身就完整。当测试检查其声明的范围的确切错误条件时，给断言强度 **A**。不要因为只有该断言而扣分，并且除非错误消息是记录合同的一部分，否则不要要求错误消息断言。一个只检查 `err == nil` 而丢弃有意义返回值的 Go 快速路径测试仍然是 **C**，因为它没有验证成功的结果。

##### B. 结构和焦点

| 子等级 | 模式 |
|------|------|
| **A** | 清晰的 Arrange-Act-Assert（或 Given-When-Then）分离。单个行为被测试。主体在 ~30 行以内。设置使用框架约定。 |
| **B** | 一个轻微的结构性问题（稍微长的主体，阶段之间缺少空行）但意图清晰。 |
| **C** | 多个行为混合在一个测试中，或 AAA 阶段交错到足以减慢理解。 |
| **D** | 测试中的条件逻辑（`if`/`switch` 驱动断言）——除了 Go/Rust 表格驱动子测试循环；或测试依赖于前一个测试状态（顺序依赖）。 |
| **F** | 测试超过 ~60 行并验证多个不相关的行為；或通过静态/全局共享可变状态而不重置与其他测试共享。 |

##### C. 反模式卫生

扫描下面的目录。反模式子等级是分两遍计算并确定性地组合的：

1. **硬上限遍历**。每个 **关键** 或 **高** 发现设置一个最大子等级（标记为 F、D 或 C）。取所有匹配的关键/高发现的**最差**上限——这些不会累积（一个 F 发现将子等级上限限制在 F，无论存在多少其他关键/高发现）。
2. **中等扣分遍历**。从 **A** 开始，然后对于每个 **中等** 发现扣一分子等级（A→B、B→C、C→D、D→F）。这些会跨发现累积。

最终的反模式子等级是两个遍历中的**较差**一个（即 `min(hard_ceiling, A − medium_count)`）。**低** 发现永远不会影响等级——只在评语中提及它们。

示例（关键/高和中等计数 → 反模式子等级）：

- 零关键/高，1 中等 → **B**（A − 1）
- 零关键/高，3 中等 → **D**（A − 3）
- 一个 C 上限（例如，过度模拟），0 中等 → **C**
- 一个 C 上限，2 中等 → **C**（`min(C, A − 2 = C) = C`；第三个中等会降到 **D**）
- 一个 F 发现（例如，吞噬异常）加上任何数量的中等 → **F**

**关键（直接降到 F 或 D）**

- 完全没有断言 → F（也驱动断言子等级到 F）
- 吞噬异常：`try { … } catch { }` (.NET)、裸 `except: pass` (Python)、`try { … } catch (e) {}` (JS/TS/Java)、`defer recover()` 而没有重新恐慌 (Go)、`rescue StandardError` 没有断言 (Ruby)、空的 `catch` (Kotlin/Swift) → F
- 捕获中的断言模式（`Assert.Fail(ex.Message)` 而不是 `Assert.ThrowsException`) → D
- 始终为真的字面量断言（`Assert.IsTrue(true)`、`assert True`、`expect(true).toBe(true)`）→ **F**（验证什么也没有；也驱动断言子等级到 F）
- 绑定值上的自引用 / 同义断言（`Assert.AreEqual(x, x)`、`assert dto.name == dto.name`) → D
- 注释掉的断言 → D

**高（降一到两分子等级）**

- 基于时钟的睡眠用于同步：`Thread.Sleep`、`Task.Delay`、`time.sleep`、基于 `setTimeout` 的等待、`Thread.sleep`、`time.Sleep`、`sleep`、`std::thread::sleep`、`Start-Sleep`、`std::this_thread::sleep_for`（在单元测试中）→ D
- 未播种的随机性，没有抽象的时钟读取（`DateTime.Now`、`datetime.now()`、`Date.now()`、`System.currentTimeMillis()`、`time.Now()`、`Time.now`、`Instant::now()`、`Get-Date`、`system_clock::now`) → D
- 硬编码的环境依赖路径（`C:\…`、`/tmp/…`、网络主机）→ D
- 对可变静态/包全局的顺序依赖 → D
- 广泛的异常断言（`Assert.ThrowsException<Exception>`、`pytest.raises(Exception)`、`expect(fn).toThrow(Error)` 没有匹配器、`#[should_panic]` 没有 `expected = "…"`、`Should -Throw` 没有 `-ExpectedMessage`、`EXPECT_ANY_THROW`) → C
- 过度模拟：模拟设置行数多于测试逻辑，或验证确切的调用序列而不是结果 → C
- 实现耦合：对私有成员的反射，将内部类型转换为访问状态 → C

**中等（降一分子等级）**

- 糟糕的名称：`Test1`、`TestMethod`、`test`、单个单词名称，说不清场景或预期结果（与语言扩展的约定进行判断）→ 降一分子等级
- 魔术值：未解释的 `42`、`"foo"`、`0x1234` 在安排/断言中未命名或注释 → 降一分子等级
- 巨大的测试（>30 行覆盖单个行为）→ 降一分子等级
- 断言消息只是重复断言文本 → 降一分子等级
- 缺少 AAA / GWT 分离，当测试非平凡时 → 降一分子等级

**低（仅在评语中提及，不扣分）**

- 未使用的设置/拆卸钩子；保留的打印调试（`Console.WriteLine`、`print`、`console.log`、`System.out.println`、`fmt.Println`、`puts`、`dbg!`、`Write-Host`、`std::cout`）；与兄弟姐妹不一致的命名；剩余的 TODO 评论。在评语列中提及，但不扣分。

#### 组合子等级

将子等级转换为数字点：A=4，B=3，C=2，D=1，F=0。
- **总体分数段** = 加权平均：
  `0.45 × 断言 + 0.30 × 反模式 + 0.25 × 结构`
- 映射到字母：
  - ≥ 3.5 → **A**（分数段 90–100）
  - ≥ 2.8 → **B**（分数段 80–89）
  - ≥ 2.0 → **C**（分数段 70–79）
  - ≥ 1.2 → **D**（分数段 60–69）
  - < 1.2 → **F**（分数段 0–59）
- 总体等级**上限为最差的子等级**——如果任何子等级是 **F**，总体等级是 **F**；如果最差的子等级是 **D**，总体等级最多是 **D**；以此类推。在任何维度上失败的测试都不能比该维度获得更高的总体等级。

报告**字母等级**和**分数段**（不是单个 0–100 数字）。假精度会引发争论；分数段使对话集中在标准上。

### 步骤 4：构建评语

评语列是一句短话（目标 ≤ 120 个字符）。声明等级的最重要原因。示例：

- A (90–100): `清晰的 AAA 结构；公共合同上的相等性 + 异常断言。`
- B (80–89): `良好的断言多样性，轻微长的主体——考虑拆分为每个条件测试。`
- C (70–79): `只检查结果上的 IsNotNull；没有值验证。`
- D (60–69): `自引用断言：往返身份验证验证管道，而不是转换。`
- F (0–59): `没有断言——测试执行方法但从未验证任何内容。`

如果一个测试得到 A 且没有值得注意的问题，评语可以简单地是 `No issues found.`——不要编造弱点来证明等级。

### 步骤 5：报告

生成两个部分。

#### 1. 摘要

一个简短的段落（2–4 句话），涵盖：评分的测试总数、等级分布、最常见问题以及最重要的建议。

#### 2. 每个测试表格

```markdown
| 测试 | 等级 | 分段 | 评语 |
|------|------|------|------|
| `Namespace.ClassName.Test_Method_Condition_Expected` | A | 90–100 | 清晰的 AAA；相等性 + 异常断言。 |
| `Namespace.ClassName.Test_Other` | C | 70–79 | 只有 `IsNotNull` — 没有值验证。 |
| `Namespace.ClassName.Test_Old` | F | 0–59 | 没有断言。 |
```

**上限和排序**：
- 如果表格会超过 **50 行**，首先显示所有评分低于 **B** 的测试（最差到最好），然后显示一些最好的测试，并将任何溢出包装在折叠的 `<details>` 块中。
- 在同一等级内，按文件路径然后按方法名称进行确定性排序。
- 如果提供了 diff 上下文，则在每个测试名称前加上 `(new)` 或 `(modified)` 标记。

如果存在多种语言，则每个语言生成一个表格，并在每个部分前缀语言名称和框架。

## 验证

- [ ] 输入列表中的每个测试用例都出现在表格中（或被记录为 `N/A — 方法未找到`）。
- [ ] 每个评分都有至少一个可观察的信号来支持，不进行推测性推断。
- [ ] 简单断言测试仅在**唯一**的断言为简单时才会被标记（在有意义断言之前的空值检查不是简单的）。
- [ ] 仅异常测试不会因为断言数量少而受罚。
- [ ] 模拟调用验证和裸断言形式被视为相应类别的真实断言。
- [ ] 对有意义属性的布尔断言（`Assert.IsTrue(result.IsValid)`）不被归类为始终为真；只有字面量 `true`/`false` 常量才被归类为始终为真。
- [ ] 自引用断言会与普通相等断言分开标记。
- [ ] 习惯用法不会被标记：Go/Rust 表驱动子测试、pytest 裸 `assert`、Go `if got != want { t.Errorf(...) }`、JS/TS `expect(mock).toHaveBeenCalledWith(...)`。
- [ ] 异步测试陷阱（未等待的 `resolves`/`rejects`/`ThrowsAsync`、没有 `await` 的 `pytest-asyncio`）会将断言子等级降为 F。
- [ ] 摘要以最高杠杆的观察结果开头，而不是表格的回顾。

## 常见陷阱

| 陷阱 | 解决方案 |
|------|----------|
| 在未提供列表的情况下对工作区中的每个测试用例进行评分 | 请求调用者提供明确的列表；这项技能适用于精选输入。 |
| 夸大推断以证明评分 | 从 A 开始；仅因可观察的问题进行扣分。 |
| 因断言数量少而惩罚异常测试 | 异常断言本身是完整的。 |
| 因为仅检查 `err != nil` 而降级 Go 错误路径测试 | 预期错误的存在是该范围内的可观察契约；除非生产契约要求特定的错误标识或消息，否则保持 A 级。 |
| 将 `IsNotNull` 在值断言之前视为简单 | 仅在空值检查是**唯一**的断言时才标记。 |
| 将任何布尔断言视为实际上没有断言 | 只有始终为真的字面量（`Assert.IsTrue(true)`，`assert True`）是；有意义的 `Assert.IsTrue(result.IsValid)` 是真实的断言。 |
