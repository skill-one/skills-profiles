# 解决可测试性障碍

引入最小的行为保持式接口，用于测试特定的 C# 行为，然后添加确定性测试来证明该行为和接口。生产代码的修改是为了实现所需的测试，而不是对相邻代码进行重新设计。

## 使用场景

- 请求的测试原本会读写真实的文件系统。
- 行为依赖于当前时间、延迟、随机值、环境、控制台、进程或其他环境依赖。
- 用户明确允许或请求安全的生产行为接口。
- 现有测试无法在不进行全局进程级修改的情况下控制依赖项。

## 不适用场景

- 依赖项已经通过依赖注入或作为参数传递。使用 `code-testing-agent` 通过现有接口编写测试，使用假对象。
- 用户需要整个仓库的可测试性审计。使用 `detect-static-dependencies`。
- 用户需要生成包装器但不更改调用点或测试。使用 `generate-testability-wrappers`。
- 用户请求广泛的机械迁移。使用 `migrate-static-to-wrapper`，然后单独生成测试。
- 用户已经选择了现有的替代方案（如 `TimeProvider` 或 `IFileSystem`），并要求将调用点迁移到它。使用 `migrate-static-to-wrapper`，它还会更新受影响的测试。
- 代码不是 C#/.NET。

## 输入

| 输入 | 是否必需 | 描述 |
|------|----------|-------|
| 要测试的行为 | 是 | 方法/工作流和预期的可观察行为 |
| 目标范围 | 否 | 当省略时，发现最窄的相关文件/项目 |
| 允许的生产行为修改 | 否 | 默认为最小的内部/构造函数接口 |

## 工作流程

### 第 1 步：证明障碍

读取目标生产路径及其现有测试。识别阻止确定性测试的确切环境操作以及必须保持不变的行为。不要为单个类请求执行仓库级静态扫描。

如果已经存在足够的接口，则停止重构并使用它。当可以使用假对象时，这项技能不会增加任何价值。

### 第 2 步：选择最小的安全接口

根据依赖项和仓库约束进行选择：

| 依赖项 | 推荐接口 |
|--------|----------|
| 当前时间/计时器 | 注入 `TimeProvider`；在测试中使用 `FakeTimeProvider` |
| 文件系统 | 现有仓库抽象；对于一次写/读操作，当约定允许时使用注入的委托，否则使用一个成员接口或已接受的 `System.IO.Abstractions` |
| HTTP | 现有的类型化 `HttpClient`/处理器或 `IHttpClientFactory` 接口 |
| 随机性 | 一个最终生成的值：注入 `Func<int>` 并在真实默认值中保留范围选择；仅在测试必须验证范围参数时注入 `Func<int, int, int>`；多个操作/状态：注入 `Random` 或最小的生成器接口 |
| 环境/控制台/进程 | 仅包含目标使用的成员的最小接口 |

作用域 `AsyncLocal<T>` 规则适用于所有必须保留其公共静态形状的静态 API——时钟、文件系统访问、环境查找、身份生成和随机性。作用域捕获并恢复先前的值；永远不要将 `Dispose()` 实现为无条件地将 `null` 赋值给 `null`。将提供程序/值本身存储在 `AsyncLocal<T>` 中。不要在槽中放置可变的 `Stack<T>`、列表或其他共享可变集合：子执行上下文可以继承相同的对象并相互破坏嵌套。当提供程序本身是可变的（例如内存存储或假时间提供程序）时，在每个并行流内部建立一个新的提供程序，而不是从一个父上下文继承一个已继承的实例。

实例类使用构造函数注入。重用仓库的 DI 和命名约定，但不要为了满足此工作流程而将 DI 容器添加到类库中。

除非用户授权 API 修改，否则保留现有的公共构造表面。将公共无参数构造函数保留为真实依赖项的默认值，并将测试专用委托/提供程序构造函数放在测试项目可以触及的最窄可见性级别。不要仅仅为了测试方便而将接口变成一个新的公共可选参数。

对于静态类或无法更改的公共 API，仅在构造函数/参数注入不可能的情况下使用作用域环境接口。重写必须：

- 跨越 `await`（`AsyncLocal<T>`，而不是 `[ThreadStatic]`）；
- 返回 `IDisposable` 并恢复先前的值，包括嵌套作用域；
- 默认为真实的生产行为依赖项；
- 避免进程级可变假对象，使测试无法并行。

使用内置的假时间感知重载，而不是发明 `IDelay` 包装器：

| 环境操作 | 替换 |
|---------|------|
| `Task.Delay(delay, token)` | `Task.Delay(delay, timeProvider, token)` |
| `new CancellationTokenSource(delay)` | `new CancellationTokenSource(delay, timeProvider)` |
| `PeriodicTimer(period)` | 当目标框架提供时使用 `new PeriodicTimer(period, timeProvider)` |

通过启动操作、证明它不完整、推进 `FakeTimeProvider`，然后等待它来测试延迟行为。对于截止日期或边界，推进到截止日期立即之前，并在推进之前断言任务仍然不完整；仅断言立即启动后的断言不能证明边界。永远不要等待墙上时间。

对于嵌套环境重写，每个作用域捕获启动时活动的值并恢复该值一次。使用 `using`/`finally` 以 LIFO 顺序释放作用域；永远不要无条件地将槽重置为 `null`。测试必须在内部作用域正常结束时观察到外部值，并在请求时在内部作用域异常展开后观察到。使用不同的值，以便清除槽不会意外传递。还重叠独立的异步流并断言每个只能看到自己的新鲜重写。不要修改进程环境变量来测试环境接口。

```csharp
var previous = s_provider.Value;
s_provider.Value = provider;
return new RestoreScope(() => s_provider.Value = previous);
```

### 第 3 步：保持行为和 API 形状

保持生产行为的机械性：

- 仅包装目标行为使用的成员。
- 默认实现直接委托给原始 API。
- 保留异常、路径处理、时区以及 `DateTime.Kind`。
- 除非用户明确允许 API 修改，否则保留现有的公共签名。
- 不要将业务逻辑移入包装器或修复无关的生产错误。

确定性序列化文本是对保留环境平台格式的一个故意例外。如果用户要求跨平台精确可重复的输出，请使用格式的显式分隔符（如果没有指定，请使用字面值 `\n`）并断言字面内容。仅在平台原生输出是现有合同的一部分时保留 `Environment.NewLine`。

对于时间替换：

- `DateTime.UtcNow` -> `timeProvider.GetUtcNow().UtcDateTime`
- `DateTime.Now` -> `timeProvider.GetLocalNow().LocalDateTime`
- `DateTimeOffset.UtcNow` -> `timeProvider.GetUtcNow()`
- `DateTimeOffset.Now` -> `timeProvider.GetLocalNow()`

### 第 4 步：保持生产行为的默认连接

更新受接口影响的每个组合根或构造函数调用。生产默认情况下必须使用真实时间/文件系统等。如果项目使用 DI，请使用与仓库约定匹配的生命周期注册默认实现。如果它不使用 DI，请显式组合；不要引入容器。
现有的手动工厂必须显式传递真实依赖项（例如，`new ExpirationPolicy(TimeProvider.System)`）。不要将责任移入可选构造函数或向工厂添加可选提供程序参数。

在编写测试之前构建受影响的生产行为项目。这里的编译失败是接口问题，而不是测试问题。

### 第 5 步：编写确定性测试

使用仓库现有的测试项目。如果没有，请先调用 `scaffold-dotnet-test-project`。

测试必须提供受控的依赖项：

- 固定/推进时间而不是墙上时间等待；
- 内存中的假文件系统或手写的假而不是临时/真实文件；
- 不进行环境修改、外部进程、控制台输入或网络。

在编写测试之前，检查测试项目并遵循现有的框架、全局使用和断言约定。使用该项目已经引用的框架包；永远不要添加手写的 `FactAttribute`、替代测试框架类型或与测试项目无关的管道，以使测试编译。

断言请求的业务结果以及至少一个交互/状态可观察项，以证明假依赖项驱动了路径。仅在它可以保持确定性时才包括生产行为默认测试；永远不要仅仅为了证明适配器委托而触摸真实文件系统。

覆盖所有明确请求的行为和边缘情况。理论或共享辅助方法可以保持套件紧凑，但不要因为最小化测试数量或用较小的集合替换保留测试而删除案例。接口应该是最小的；验证仍然应该是完整的。

选择支持行为的最窄接口。单个 `File.WriteAllText` 调用可以是具有真实默认值的注入 `Action<string, string>`；除非仓库约定或多个操作证明它们，否则不要创建接口、实现、朋友程序集设置和额外的项目连接。

保留公共 API 表面以及现有的签名。不要仅为测试添加一个公共依赖注入构造函数。当类目前只有其隐式公共无参数构造函数且已知的精确测试程序集时，保留该构造函数行为并将测试专用构造函数设置为内部；在这种情况下，`InternalsVisibleTo` 条目是合理的，因为它可以防止接口变成公共 API。当存在时，优先使用现有的仓库朋友程序集约定。

当现有的公共接口已经接受假或测试项目可以以其他方式提供它时，不要添加 `InternalsVisibleTo`。朋友程序集访问仅在以下情况下是合理的：选择的最小构造函数/委托接口必须保持内部以保留公共 API，并且已知的精确测试程序集是已知的。

### 第 6 步：验证完整路径

运行受影响的生产行为构建和最窄的目标测试命令。仅在用户请求广泛验证、仓库合同要求该入口点或接口更改了目标之外共享的组合时，才运行仓库级测试命令。重新阅读差异并确认：

1. 每个生产行为修改都是由接口所需的；
2. 新测试没有使用任何真实的环境资源；
3. 当前时间语义和公共行为得到保留；
4. 现有测试没有被替换或重复。

检查测试摘要，而不仅仅是退出代码。零发现的测试、没有运行请求测试的构建或任何失败的/错误的测试都意味着任务未完成。修复发现/执行并重新运行，然后再报告成功。当新的测试无法编译时，在更改生产行为之前，根据现有的测试框架修正其导入、断言重载或异步测试形状；不要在源代码中模拟缺失的框架 API。
对于静态环境接口，完成需要替换的执行测试、嵌套恢复、在请求时异常恢复以及重叠异步流隔离；仅生产编译不足以证明。在交接中捕获通过测试的数量或请求的测试名称。如果未发现测试或输出未证明执行，请修正项目/测试源并重新运行，而不是报告接口已验证。

## 输出契约

提供一个紧凑的 `需求 | 证据` 表。引用生产行为接口、生产行为默认连接、精确的测试名称和通过命令。如果包恢复或构建阻止验证，请报告该阻止器，而不是声称测试通过。

## 验证

- [ ] 原始障碍是具体的，并且在请求的路径中。
- [ ] 当可用时，重用了现有的接口。
- [ ] 新的抽象仅暴露了目标行为所需的成员。
- [ ] 生产行为默认值仍然委托给原始依赖项。
- [ ] 接口在内部测试接口足够的情况下没有扩大公共 API。
- [ ] 时间转换保留了本地/UTC 和 `DateTime.Kind` 语义。
- [ ] 静态环境重写是异步安全的、作用域的、嵌套的和可逆的。
- [ ] 新测试使用固定/内存依赖项，并且没有真实的 I/O 或墙上时间。
- [ ] 生产行为构建和目标/仓库测试至少发现了一个请求的测试。

## 常见陷阱

| 陷阱 | 修正措施 |
|------|----------|
| 在证明障碍之前进行重构 | 重用现有的接口并直接编写测试 |
| 包装整个静态 API | 仅暴露目标执行的成员 |
| 使用 `.DateTime` 转换 `UtcNow` | 使用 `.UtcDateTime` 以保留 `DateTimeKind.Utc` |
| 测试共享的可变静态假对象 | 使用构造函数注入或作用域 `AsyncLocal<T>` 重写 |
| 向没有容器的库添加 DI | 显式组合依赖项 |
| 使用临时文件作为捷径 | 提供内存中的假；该场景不需要真实 I/O |
| 在重构构建后停止 | 编写和运行证明接口的业务测试 |
| 将零测试运行报告为成功 | 修复发现并要求请求的测试执行并通过 |
