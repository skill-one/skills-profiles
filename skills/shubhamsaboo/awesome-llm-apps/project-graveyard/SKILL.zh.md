# 项目墓园

每个开发者都有一个装满已死项目的文件夹。从没有人拿到过一份尸检报告。这项技能扫描机器以查找被遗弃的代码库，通过其git历史分析每个项目死亡的原因，找出用户的个人死亡模式，并挑选出值得挖掘的尸体——然后帮助将其重新发布。

所有操作都在本地进行。没有API，没有网络，没有任何信息离开机器。

## 使用场景

- 用户询问关于被遗弃/未完成/旧的项目，或想知道要完成什么
- 用户想要复活、复兴或"终于发布"某个东西
- 用户询问为什么他们从未完成项目
- 用户提议一个新项目——先检查墓园（参见巫师模式）。他们很可能已经完成了其中一半。

## 不适用场景

- 清理磁盘空间或node_modules——那是`kondo`/`npkill`的工作，不是这个工具的
- 在GitHub上存档代码库——这个工具适用于本地克隆和未推送的工作
- 深入分析特定代码库的历史——只需查看git日志

## 运行方式

```bash
python3 scripts/graveyard.py ~/dev ~/projects
```

将其指向项目实际存放的位置。如果你不知道在哪里，可以询问——一个问题胜过未经邀请地清扫某人的家目录。没有参数会扫描常见位置（~/dev, ~/projects, ~/code, ~/Desktop, ...）。有用的标志：

- `--days 90` — 代码库在沉默多久后算作死亡（默认45天）
- `--json report.json` — 完整的机器可读数据
- `--me work@email.com` — 声明使用其他邮箱提交的提交记录（可重复）；没有它，使用工作身份或构建工具提交的项目会被跳过，视为"不是你的"
- `--include-foreign` — 也包括用户几乎未提交过的代码库（默认跳过：克隆、分支、工作检出不是他们的尸体）
- `--state FILE` — 记录扫描和复兴；启用复发监控

脚本只读。它永远不会在扫描的代码库中写入任何内容。

## 阅读报告

脚本会给你四个部分：人口普查、死亡项目（及其死因）、模式，以及按"脉搏"（复兴评分）排名的前3名。死因是基于证据的猜测，不是最终裁决——每个死因都附有证明其合理性的证据行。如果一个死因看起来不对，请在重复之前检查证据。死因分类以及每个死因对复兴的意义在`references/causes-of-death.md`中——在撰写报告之前阅读它。

## 尸检访谈

脚本只能读取git。你可以提问。对于主要死因是`unknown`或`slow_fade`——低置信度的裁决——的项目，每个项目最多问一两个问题，总共不超过三个：

> "`recipe-scraper` — 历史记录只显示它在逐渐消亡。你还记得是什么真正阻止了你吗？"

将答案结合起来，并在报告中诚实地标注裁决：
**(法医)** 用于git显示的内容，**(确认)** 用于你告诉用户的。证词胜过法医猜测——更新墓碑，而不仅仅是文字。两个问题是对话；五个是审讯。

## 撰写墓碑报告

将脚本输出转换为用户会实际感受到的报告。格式：

1. **人口普查。** 死亡数量、总寿命、最老的尸体。纯数字——它们会自行呈现。
2. **墓碑。** 每个死亡项目一个，按脉搏从最差到最好排列。名称、寿命、提交次数、死因及其证据，以及一句话的墓志铭。超过10个尸体后，仅对最有趣的6-8个（脉搏最高、最独特的死亡）提供完整墓碑，其余的尸体一起埋葬在一行中——"...还有11个一天实验，合葬在一起。" 23个墓碑的墙会毁掉葬礼。
3. **模式。** 这是他们会记住的部分。"你的项目在第19天死亡。" "六个中有四个被更新的项目杀死。" 引用脚本的数字；添加任何你能看到而脚本无法看到的东西。
4. **复兴。** 一个项目。不是三个。见下文。

将复兴选择（且仅它）雕刻为ASCII墓碑卡——石头是挣来的，不是随意喷洒的；其他尸体保持表格中的一行：

```
        .------------------------.
       /                          \
      |        tab-sensei          |
      |      Apr — May 2026        |
      |   54 commits · 12 days     |
      |                            |
      |   死于部署恐惧             |
      |                            |
      |   "它工作了。但它从未发布。" |
   ___|____________________________|___
      ~ ~ ~ ~ ~ ~ ~ ~ ~ ~ ~ ~ ~ ~
```

居中显示文本，保持卡片宽度不超过44列，以便不会换行，墓志铭最后。如果墓园为空，则没有卡片——不要为无人雕刻石头。

墓志铭规则——这是整个事情成功或失败的关键：

- 每个墓志铭都必须可追溯到扫描的证据。"像它活着一样死去：配置webpack"是有效的，因为配置比例是78%。编造关于你没有见过的代码的笑话是无效的，用户会知道。
- 攻击模式，而不是人。"它工作了。但它从未发布"是好的。 "你害怕发布"是不好的。
- 干净比疯狂好。一句话。没有双关语，除非它们是挣来的。
- 如果一个项目值得尊重，就给它尊重。一个有26个提交记录、完成README但从未发布的项目是一个小悲剧，而不是一个笑话。

如果用户想要分享报告，提供`--redact`框架：项目名称替换为`project-1..n`，死因和模式保持完整。

## 复兴

选择一个尸体。除非其想法在世界上已经死了，否则脉搏最高者胜出。在决定之前，阅读首选项目的README并快速浏览代码——然后进行**世界检查**，这是只有你能做的，因为脚本看不到现在：

- 搜索阻止它的东西是否自它死亡以来变得更简单：它与之斗争的API可能现在有一个官方SDK，太昂贵的模型可能便宜了20倍，它手工制作的东东可能已经成为一个库。
- 搜索世界是否已经发布了这个想法。如果现在有三个资金充足的产品完全这样做，就说出来——这会改变计划从"发布它"到"为你自己发布它"，或者"让它安息"。

在计划中引用你找到的内容。"这变得更容易了：X现在存在"是挖掘的最强论据；"窗口关闭了"是埋葬的最强论据。

然后撰写复兴计划。每个死因的挖掘策略在`references/causes-of-death.md`中（每个死因都有一个"复兴角度"——部署恐惧的尸体需要仅发布步骤，墙死亡需要管理替代方案，范围爆炸需要一个功能提取）。计划规则：

- 最多7个具体步骤，以*发布*结束（URL、发布、发布的包——不是"继续工作")
- 第0步总是：确认它仍然运行。依赖项会腐烂；在承诺任何东西之前，证明安装和入口点。
- 第1步必须是今天可以完成的——第一个会话必须以可见的进展结束
- 在触摸代码库之前询问。然后立即提供开始第1步——这个提议是运行此工具在代理中的整个目的。

**何时让它安葬**——当它是真的时，直说：用户不再关心（访谈中的耸肩是结束，不是项目）；窗口关闭了，世界发布了这个想法；或者每个候选者都很弱。"这里没有什么值得挖掘的，这很好——这是关于下一个项目的模式"是一个合法且有用的结尾。

当用户承诺复兴时，记录它（询问一次将状态文件保存在哪里——`~/.project-graveyard.json`是一个合理的默认值）：

```bash
python3 scripts/graveyard.py --state ~/.project-graveyard.json \
    --mark-resurrected /path/to/the/corpse
```

## 复发监控

使用`--state`运行的扫描会保留过去的复兴，以兑现承诺：报告会获得一个RELAPSE WATCH部分，显示每个复兴的项目是否保持沉默还是再次变得安静。当一个项目复发时，直说并让用户选择——重新提交或诚实地埋葬它。第二次沉默死亡是一个答案，不是一个失败；关闭循环而不是建议第三次尝试。没有工具会自行跟进自己的处方。这个工具会——这就是保留状态的目的。

## 巫师模式

当用户提议构建新东西时，在搭建任何东西之前检查墓园中的先前列出——grep状态文件（或一个新鲜的`--json`报告）以查找名称和README的重叠。如果有匹配：

> "你已经完成了大约60%的这些。它被称为`project-14`，它在3月死于身份验证步骤，它的解析器仍然工作。复兴它，而不是重新开始？"

不要说教。提一次，让他们选择，然后放下。

## 注意事项

- **~/Desktop 可能本身就是一个git代码库**（意外的`git init`，备份工具）。扫描器处理嵌套代码库，但如果人口普查看起来很荒谬，那通常就是原因。
- **所有权过滤器使用git邮箱。** 如果用户使用多个邮箱提交（工作地址、GitHub网页编辑、构建工具），真正的尸体会被跳过，视为"不是你的"——人口普查列出了它跳过了什么；用`--me that@email.com`声明你的。
- **"死亡"是一个阈值，不是一个事实。** 一个稳定的完成工具在45天后看起来是死亡的。脚本将`finished`（部署配置+推送+README）与死亡区分开来，但启发式方法是粗略的——在哀悼用户认为完成的任何东西之前询问。
- **一天尸体通常是感觉编码的爆发**，而不是失败——一个在一天内构建并从未重新打开的项目。值得揭示的模式是他们有多少，而不是每个都"死亡"。
- **不要默认复兴。** 报告是产品；复兴是一个提议。一些尸体应该保持安葬——见上面的"何时让它安葬"。

## 文件

- `scripts/graveyard.py` — 扫描器+尸检+脉搏排名（stdlib，离线，只读）
- `references/causes-of-death.md` — 分类：信号、置信度，以及每个死因的复兴策略
