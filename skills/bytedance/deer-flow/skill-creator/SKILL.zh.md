# 技能创建器

一个用于创建新技能并迭代改进它们的技能。

从高层次来看，创建技能的过程如下：

- 确定你希望技能做什么以及大致如何做
- 撰写技能的草稿
- 创建一些测试提示，并在它们上运行具有访问权限的 claude
- 帮助用户从定性和定量两个方面评估结果
  - 在运行在后台时，如果还没有定量的评估（如果有，你可以使用或修改你认为需要改变的内容），草拟一些定量的评估。然后向用户解释它们（或者如果它们已经存在，解释已经存在的评估）
  - 使用 `eval-viewer/generate_review.py` 脚本向用户展示结果供他们查看，并让他们查看定量指标
- 根据用户对结果的反馈（以及如果从定量基准中明显看出任何缺陷）重新编写技能
- 重复直到你满意
- 扩展测试集并在更大规模上再次尝试

使用此技能时，你的工作是弄清楚用户在此过程中的位置，然后跳入并帮助他们完成这些阶段。例如，也许他们想：“我想创建一个用于 X 的技能”。你可以帮助他们缩小范围，撰写草稿，编写测试用例，确定他们想要如何评估，运行所有提示，并重复。

另一方面，也许他们已经有一个技能草稿。在这种情况下，你可以直接进入评估/迭代部分。

当然，你应该始终保持灵活性，如果用户说“我不需要运行大量的评估，只需要和我一起感觉”，你可以那样做。

然后，在技能完成后（但顺序是灵活的），你还可以运行技能描述改进器，我们有一个完整的独立脚本来优化技能的触发。

## DeerFlow 环境 (⚠️ 首先阅读)

如果你在一个 **DeerFlow** 沙盒化代理环境中运行（你有访问 `skill_manage` 工具的权限），你必须遵循以下规则进行所有技能文件操作。这些规则会覆盖下面通用的文件写入和打包说明。

### 为什么这很重要

在 DeerFlow 中，沙盒文件系统是隔离的。使用 `write_file` 写入的文件会存放在 `/mnt/user-data/outputs/`，这是一个**每个线程的输出目录**——新的聊天无法看到那里的文件。技能必须通过专用的 `skill_manage` 工具进行持久化，以便它们存储在每个用户的技能目录中，并立即对所有未来的聊天可见。

### 使用 `skill_manage` 进行所有技能文件操作

| 操作 | skill_manage 操作 | 示例 |
|------|------------------|------|
| 创建新技能 | `action="create"` | `skill_manage(action="create", name="my-skill", content="---\nname: my-skill\n---\n...")` |
| 替换整个 SKILL.md | `action="edit"` | `skill_manage(action="edit", name="my-skill", content="更新的 SKILL.md")` |
| 部分编辑（查找和替换） | `action="patch"` | `skill_manage(action="patch", name="my-skill", find="旧文本", replace="新文本")` |
| 删除技能 | `action="delete"` | `skill_manage(action="delete", name="my-skill")` |
| 添加支持文件 | `action="write_file"` | `skill_manage(action="write_file", name="my-skill", path="scripts/helper.py", content="...")` |
| 删除支持文件 | `action="remove_file"` | `skill_manage(action="remove_file", name="my-skill", path="scripts/helper.py")` |

### 关键规则

1. **绝对不要使用沙盒 `write_file` 来创建或修改技能文件**（SKILL.md、scripts/、references/、assets/）。这些会存放在 `/mnt/user-data/outputs/`，并且对未来的聊天不可见。始终使用 `skill_manage` 而不是。

2. **跳过 `package_skill.py` 步骤**。在 DeerFlow 中，`skill_manage` 已经将技能持久化到正确的每个用户目录。不需要 `.skill` 打包或手动安装。技能在所有新的聊天中立即可用。

3. **跳过技能的 `present_files` 步骤**。技能不是交付物——它们通过 `skill_manage` 持久化并由技能系统自动加载。仅对非技能输出（评估报告、基准等）使用 `present_files`。

4. **评估工作区文件在沙盒中是允许的**。测试提示、基准数据、评估查看器 HTML、评分结果等不是技能文件——你可以像平常一样使用沙盒 `write_file` 将它们写入 `/mnt/user-data/outputs/` 或 `/mnt/user-data/workspace/`。

5. **要读取现有技能的 SKILL.md**，请在沙盒中使用 `read_file("/mnt/skills/custom/<name>/SKILL.md")`（它映射到每个用户的技能目录）。

6. **更新现有技能**：使用 `skill_manage(action="edit")` 或 `skill_manage(action="patch")`。不要先复制到 `/tmp/`——`skill_manage` 直接处理每个用户的存储。

### DeerFlow 中的工作流程

核心循环是相同的，但持久化机制发生了变化：

1. 捕获意图 → 访谈 → 草拟 SKILL.md 内容
2. **调用 `skill_manage(action="create", name=<name>, content=<SKILL.md>)`** 以持久化技能
3. 运行测试用例（评估工作区文件使用沙盒 `write_file`）
4. 评估结果，收集反馈
5. **调用 `skill_manage(action="edit")` 或 `skill_manage(action="patch")`** 以改进技能
6. 重复直到满意
7. **完成——不需要打包**。技能已经持久化，并对所有未来的聊天可见。

## 创建技能

### 捕获意图

首先了解用户的意图。当前的对话可能已经包含用户想要捕获的工作流程（例如，他们说“把它变成一个技能”。如果是这样，首先从对话历史中提取答案——使用的工具、步骤的顺序、用户进行的更正、观察到的输入/输出格式。用户可能需要填写空白，并在继续到下一步之前确认。

1. 这个技能应该使 Claude 能够做什么？
2. 什么时候应该触发这个技能？（什么用户短语/上下文）
3. 预期的输出格式是什么？
4. 我们是否应该设置测试用例来验证技能是否工作？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流步骤）从测试用例中受益。具有主观输出的技能（写作风格、艺术）通常不需要它们。根据技能类型建议适当的默认值，但让用户决定。

### 访谈和研究

主动询问边缘情况、输入/输出格式、示例文件、成功标准以及依赖项。直到你弄清楚这部分，再编写测试提示。

检查可用的 MCPs - 如果对研究有用（搜索文档、找到类似的技能、查找最佳实践），如果可用，通过子代理并行研究，否则内联。做好准备，以减少对用户的负担。

### 编写 SKILL.md

根据用户访谈，填写这些组件：

- **name**：技能标识符
- **description**：何时触发，做什么。这是主要的触发机制——包括技能做什么以及何时使用它的特定上下文。所有“何时使用”的信息都放在这里，而不是在正文中。注意：目前 Claude 有一个趋势，即“低估技能”——在它们有用时不会使用它们。为了解决这个问题，请确保技能描述稍微“强迫”。例如，而不是“如何构建一个简单的快速仪表板来显示内部 Anthropic 数据”，你可以写“如何构建一个简单的快速仪表板来显示内部 Anthropic 数据。确保在用户提到仪表板、数据可视化、内部指标或想要显示任何公司数据时使用此技能，即使他们没有明确要求“仪表板”。”
- **兼容性**：必需的工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能的构成

```
skill-name/
├── SKILL.md (必需)
│   ├── YAML 前置信息 (name, description 必需)
│   └── Markdown 指令
└── 嵌套资源 (可选)
    ├── scripts/    - 用于确定性/重复性任务的执行代码
    ├── references/ - 需要在需要时加载到上下文中的文档
    └── assets/     - 用于输出的文件（模板、图标、字体）
```

#### 逐步披露

技能使用三级加载系统：

1. **元数据**（name + description）- 始终在上下文中（约 100 字）
2. **SKILL.md 正文** - 技能触发时在上下文中（理想情况下少于 500 行）
3. **嵌套资源** - 需要时（无限制，脚本可以在不加载的情况下执行）

这些字数是近似值，如果你需要，可以自由地更长。

**关键模式：**
- 保持 SKILL.md 少于 500 行；如果你接近这个限制，请添加额外的层级，并提供清晰的指向，说明使用技能的模型应该去哪里继续。
- 从 SKILL.md 中清晰地引用文件，并指导何时读取它们
- 对于大于 300 行的大文件，包括目录表

**域组织**：当技能支持多个域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md (工作流 + 选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 没有惊喜的原则

不言而喻，技能不得包含恶意软件、利用代码或任何可能危及系统安全的内容。技能的内容不应在描述时让用户感到意外。不要配合创建误导性技能或旨在促进未经授权的访问、数据泄露或其他恶意活动的技能。像“扮演 XYZ 角色”这样的内容是可以接受的。

#### 编写模式

在指令中使用祈使句。

**定义输出格式** - 你可以这样做：
```markdown
## 报告结构
始终使用这个精确模板：
# [标题]
## 执行摘要
## 关键发现
## 建议
```

**示例模式** - 包括示例很有用。你可以这样格式化它们（但如果“输入”和“输出”在示例中，你可能需要稍微偏离一点）：
```markdown
## 提交信息格式
**示例 1：**
输入：添加用户身份验证，使用 JWT 令牌
输出：feat(auth): 实现 JWT 身份验证
```

### 编写风格

尝试向模型解释为什么事情很重要，而不是使用强硬的“必须”。使用心智理论，并尝试使技能通用，而不是针对特定示例过于狭窄。先写一个草稿，然后用新鲜的眼光审视并改进它。

### 测试用例

在编写技能草稿后，构思 2-3 个现实的测试提示——真实用户实际会说的东西。将它们分享给用户：[你不必使用确切的语言] “我想尝试几个测试用例。这些看起来对吗，或者你想添加更多？” 然后运行它们。

将测试用例保存到 `evals/evals.json`。现在编写断言——只是提示。你将在下一步草拟断言，同时运行正在进行。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示",
      "expected_output": "预期结果的描述",
      "files": []
    }
  ]
}
```

参见 `references/schemas.md` 以获取完整架构（包括 `assertions` 字段，你将在下一步添加）。

## 运行和评估测试用例

这一节是一个连续的序列——不要中途停止。不要使用 `/skill-test` 或任何其他测试技能。

将结果放在 `<skill-name>-workspace/` 中，作为技能目录的兄弟目录。在工作区中，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并在其中，每个测试用例都得到一个目录（`eval-0/`、`eval-1/` 等）。不要事先创建所有这些——只是按需创建目录。

### 第一步：在同一轮中生成所有运行（带技能和基线）

对于每个测试用例，在同一轮中生成两个子代理——一个带技能，一个不带技能。这很重要：不要先生成带技能的运行，然后再回来生成基线。立即启动所有内容，以便它们在同一时间完成。

**带技能的运行：**

```
执行此任务：
- 技能路径：<技能路径>
- 任务：<评估提示>
- 输入文件：<如果有，或“无”>
- 保存输出到：<工作区>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 保存输出：<用户关心的——例如，“.docx 文件”、“最终 CSV”>
```

**基线运行**（相同的提示，但基线取决于上下文）：
- **创建新技能**：没有任何技能。相同的提示，没有技能路径，保存到 `without_skill/outputs/`。
- **改进现有技能**：旧版本。在编辑之前，快照技能（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后将基线子代理指向快照。保存到 `old_skill/outputs/`。

为每个测试用例编写 `eval_metadata.json`（断言现在可以为空）。根据它测试的内容为每个评估命名——不仅仅是“eval-0”。也使用此名称为目录命名。如果此迭代使用新的或修改后的评估提示，为每个新的评估目录创建这些文件——不要假设它们从以前的迭代中继承过来。

```json
{
  "eval_id": 0,
  "eval_name": "在此处提供描述性名称",
  "prompt": "用户的任务提示",
  "assertions": []
}
```

### 第二步：在运行进行中，草拟断言

不要只是等待运行完成——你可以利用这段时间。为每个测试用例草拟定量断言，并向用户解释它们。如果断言已经存在于 `evals/evals.json` 中，请审查它们并解释它们检查的内容。

好的断言是客观可验证的，并且具有描述性名称——它们应该在基准查看器中清晰易读，以便有人快速查看结果时立即理解每个断言检查的内容。主观技能（写作风格、设计质量）最好进行定性评估——不要强迫断言用于需要人类判断的事情。

更新 `eval_metadata.json` 文件和 `evals/evals.json` 文件，添加断言。也向用户解释查看器中会看到的内容——包括定性输出和定量基准。

### 第三步：在运行完成时，捕获时间数据

当每个子代理任务完成时，你会收到一个包含 `total_tokens` 和 `duration_ms` 的通知。立即将此数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是唯一的机会捕获此数据——它通过任务通知提供，并且不会持久化到其他地方。按到达顺序处理每个通知，而不是尝试批量处理它们。

### 第四步：评分、聚合并启动查看器

一旦所有运行都完成：

1. **逐个运行评分** — 启动评分子代理（或内联评分）读取 `agents/grader.md` 并针对每个断言评估输出。将结果保存到每个运行目录中的 `grading.json`。`grading.json` 的期望数组必须使用 `text`、`passed` 和 `evidence`（而不是 `name`/`met`/`details` 或其他变体）— 查看器依赖于这些确切的字段名。对于可以编程检查的断言，编写并运行脚本而不是肉眼检查 — 脚本更快、更可靠，并且可以在多次迭代中重复使用。

2. **聚合为基准** — 从技能创建器目录运行聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这将生成 `benchmark.json` 和 `benchmark.md`，其中包含每个配置的通过率、时间和 token，以及均值 ± 标准差和差值。如果手动生成 benchmark.json，请参阅 `references/schemas.md` 以了解查看器期望的确切模式。

   将每个 `with_skill` 版本放在其基线对应版本之前。

3. **进行分析师检查** — 读取基准数据并揭示汇总统计数据可能隐藏的模式。参阅 `agents/analyzer.md`（“分析基准结果”部分）了解要查找的内容 — 例如始终通过而不管技能的断言（非区分性）、高变差的评估（可能不稳定）以及时间/Token 交换。

4. **使用定性和定量数据启动查看器**：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于迭代 2+，还传递 `--previous-workspace <workspace>/iteration-<N-1>`。

   **同事 / 无头环境**：如果 `webbrowser.open()` 不可用或环境没有显示器，请使用 `--static <output_path>` 写入独立的 HTML 文件而不是启动服务器。当用户点击“提交所有评论”时，反馈将作为 `feedback.json` 文件下载。下载后，将 `feedback.json` 复制到工作空间目录以供下一次迭代使用。

   注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **告知用户** 类似于：“我已经在您的浏览器中打开了结果。有两个选项卡 — ‘输出’允许您逐个测试用例并留下反馈，‘基准’显示定量比较。完成后，请返回这里并告诉我。”

### 查看器中用户看到的内容

“输出”选项卡一次显示一个测试用例：
- **提示**：给定的任务
- **输出**：技能生成的文件，尽可能内联显示
- **先前输出**（迭代 2+）：折叠部分显示上次迭代的输出
- **正式评分**（如果运行了评分）：折叠部分显示断言通过/失败
- **反馈**：一个文本框，在输入时自动保存
- **先前反馈**（迭代 2+）：上次评论，显示在文本框下方

“基准”选项卡显示统计摘要：每个配置的通过率、时间和 token 使用情况，以及每个评估的细分和分析员观察。

导航通过上一页/下一页按钮或箭头键。完成时，他们点击“提交所有评论”，将所有反馈保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告诉您他们完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "图表缺少坐标轴标签", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "完美，喜欢这个", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空的反馈意味着用户认为它很好。请专注于用户有具体投诉的测试用例进行改进。

完成查看器服务器时：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是循环的核心。您已运行测试用例，用户已查看结果，现在您需要根据他们的反馈改进技能。

### 如何考虑改进

1. **从反馈中泛化**。这里发生的大事是，我们试图创建可以在许多不同提示下重复使用百万次（也许字面意思上，甚至更多谁知道）的技能。在这里，您和用户反复迭代几个示例，因为这样能更快地推进。用户熟悉这些示例，并且对他们来说快速评估新输出很方便。但如果您和用户正在共同开发的技能只适用于这些示例，它就毫无用处。与其进行繁琐的过度复杂更改，或施加压迫性的 MUST，如果存在一些固执的问题，您可能会尝试扩展使用不同的隐喻，或推荐不同的工作模式。尝试相对便宜，也许您会找到一些很棒的东西。

2. **保持提示简洁**。删除那些没有发挥作用的元素。确保阅读记录，而不仅仅是最终输出 — 如果看起来技能正在让模型浪费时间做无生产性的事情，您可以尝试删除导致这种情况的技能部分，看看会发生什么。

3. **解释原因**。努力解释您要求模型做的一切背后的原因。今天的 LLM 很聪明。它们有很好的心智理论，在良好的套件下可以超越死记硬背的指令并真正实现事情。即使用户的反馈简短或沮丧，也要尝试真正理解任务以及用户为什么写下他们写的内容，以及他们实际写了什么，然后将这种理解转化为指令。如果您发现自己写的是 ALL CAPS 的 ALWAYS 或 NEVER，或者使用非常严格的结构，这是一个黄色标志 — 如果可能，重新构建并解释推理，以便模型理解您要求的东西为什么很重要。这是一种更有人性、更强大、更有效的方法。

4. **寻找测试用例之间重复的工作**。阅读测试运行的记录，注意子代理是否独立编写了类似的辅助脚本或采取了相同的多步骤方法。如果所有 3 个测试用例都导致子代理编写了 `create_docx.py` 或 `build_chart.py`，这是一个强烈的信号，表明技能应该将该脚本捆绑在一起。编写一次，将其放在 `scripts/` 中，并告诉技能使用它。这可以节省未来每次调用的重新发明轮子。

这项任务非常重要（我们试图每年创造数十亿的经济价值！），您的思考时间不是瓶颈；花时间认真思考。我建议编写一个草稿修订版，然后重新审视它并进行改进。真的尽力进入用户的头脑，了解他们想要什么和需要什么。

### 迭代循环

改进技能后：

1. 将您的改进应用于技能
2. 将所有测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。如果您正在创建新技能，基线始终是 `without_skill`（没有技能）— 这在迭代中保持不变。如果您正在改进现有技能，请根据您的判断确定基线：用户提交的原始版本，还是上一个迭代。

3. 使用 `--previous-workspace` 指向上一个迭代启动查看器
4. 等待用户查看并告诉您他们完成
5. 读取新反馈，再次改进，重复

继续进行，直到：
- 用户表示满意
- 反馈全部为空（一切看起来都很好）
- 您没有取得有意义的进展

## 高级：盲比较

在您想要对技能的两个版本进行更严格比较的情况下（例如，用户问“新版本实际上是否更好？”），有一个盲比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 了解详细信息。基本思路是：给两个输出给一个独立的代理，不告诉它哪个是哪个，让它判断质量。然后分析胜者为什么获胜。

这是可选的，需要子代理，大多数用户不需要它。人类审查循环通常就足够了。

## 描述优化

SKILL.md 前置中的描述字段是决定 Claude 是否调用技能的主要机制。在创建或改进技能后，请提供优化描述以获得更好的触发准确性的服务。

### 第 1 步：生成触发评估查询

创建 20 个评估查询 — 一组应该触发和不应该触发。保存为 JSON：

```json
[
  {"query": "用户提示", "should_trigger": true},
  {"query": "另一个提示", "should_trigger": false}
]
```

查询必须是现实的，Claude Code 或 Claude.ai 用户实际上会输入。不是抽象请求，而是具体且具体的请求，并具有相当多的详细信息。例如，文件路径、关于用户工作或情况的个人信息、列名和值、公司名称、URL。一些背景故事。有些可能是小写的或包含缩写或拼写错误或口语。使用不同长度的混合，并专注于边缘情况，而不是使它们清晰明确（用户将有机会签署它们）。

坏：`"格式化这些数据"`，`"从 PDF 中提取文本"`，`"创建图表"`

好：`"好的，我的老板刚刚发给我这个 xlsx 文件（它在我的下载中，可能叫 'Q4 销售最终 FINAL v2.xlsx'），她想让我添加一个显示利润率的列，作为百分比。收入在列 C，成本在列 D，我想"`

对于 **应该触发** 的查询（8-10 个），请考虑覆盖范围。您想要相同意图的不同措辞 — 有些正式，有些随意。包括用户没有明确命名技能或文件类型但显然需要的情况。加入一些不常见的用例，以及在这种情况下应胜过另一个技能的用例。

对于 **不应该触发** 的查询（8-10 个），最有价值的是接近的 — 分享关键字或概念的查询，但实际上需要不同的东西。考虑相邻的领域，模糊的措辞，其中天真关键字匹配会触发但不应触发的情况，以及查询涉及技能做但另一个工具更合适的情况。

要避免的关键点：不要使应该不触发的查询明显不相关。“编写一个斐波那契函数”作为 PDF 技能的负面测试太容易了 — 它不测试任何东西。负面用例应该是真正棘手的。

### 第 2 步：用户审查

使用 HTML 模板使用户审查评估集：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项的 JSON 数组（周围没有引号 — 它是 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能的当前描述
3. 写入临时文件（例如，`/tmp/eval_review_<skill-name>.html`）并打开它：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换应该触发、添加/删除条目，然后点击“导出评估集”
5. 文件下载到 `~/Downloads/eval_set.json` — 检查下载文件夹以获取最新版本，以防有多个（例如，`eval_set (1).json`）

这一步很重要 — 坏的评估查询会导致坏的描述。

### 第 3 步：运行优化循环

告诉用户：“这需要一些时间 — 我将在后台运行优化循环，并定期检查它。”

将评估集保存到工作空间，然后后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中的模型 ID（当前会话驱动的模型）以便触发测试与用户实际体验匹配。

在运行期间，定期使用 `tail` 查看输出，以向用户提供有关迭代位置和分数的更新。

这会自动处理完整的优化循环。它将评估集分成 60% 训练和 40% 保留的测试，评估当前描述（运行每个查询 3 次以获得可靠的触发率），然后调用 Claude 提出基于失败内容的改进。它重新评估每个新描述在训练和测试上的评估，最多迭代 5 次。完成后，它会在浏览器中打开一个 HTML 报告，显示每次迭代的分数，并返回 JSON，其中包含 `best_description` — 由测试分数而不是训练分数选择，以避免过拟合。

### 技能触发的工作原理

了解触发机制有助于设计更好的评估查询。技能以名称 + 描述的形式出现在 Claude 的 `available_skills` 列表中，Claude 根据描述决定是否咨询技能。重要的是要知道，Claude 只在它自己无法轻松处理的任务上咨询技能 — 简单、单步查询（如“读取此 PDF”）即使描述匹配完美也可能不会触发技能，因为 Claude 可以直接使用基本工具处理它们。复杂、多步骤或专业查询在描述匹配时可靠地触发技能。

这意味着您的评估查询应该足够具体，以至于 Claude 实际上会从咨询技能中受益。像“读取文件 X”这样的简单查询是糟糕的测试用例 — 无论描述质量如何，它们都不会触发技能。

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description` 并更新技能的 SKILL.md 前置。显示用户在/之前和之后，并报告分数。

### 打包和展示（仅当 `present_files` 工具可用时）

检查您是否有权访问 `present_files` 工具。如果没有，跳过此步骤。如果有的话，打包技能并将 .skill 文件展示给用户：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包后，将用户指向生成的 `.skill` 文件路径，以便他们可以安装它。

## Claude.ai 特定说明

在 Claude.ai 中，核心工作流程相同（草稿 → 测试 → 审查 → 改进 → 重复），但由于 Claude.ai 没有子代理，一些机制会发生变化。以下是您需要调整的内容：

**运行测试用例**：没有子代理意味着没有并行执行。对于每个测试用例，读取技能的 SKILL.md，然后按照其说明自己完成测试提示。一次做一个。这不如独立子代理严格（您编写了技能并且也在运行它，因此您拥有完整上下文），但它是一个有用的检查 — 人类审查步骤可以弥补。跳过基线运行 — 只使用技能完成请求的任务。

**审查结果**：如果您无法打开浏览器（例如，Claude.ai 的 VM 没有显示器，或您在远程服务器上），请完全跳过浏览器审查器。相反，直接在对话中呈现结果。对于每个测试用例，显示提示和输出。如果输出是用户需要查看的文件（如 .docx 或 .xlsx），将其保存到文件系统中并告诉他们位置以便下载和检查。内联请求反馈：“这个看起来怎么样？有什么需要更改的吗？”

**基准测试**：跳过定量基准测试 — 它依赖于基线比较，在没有子代理的情况下没有意义。专注于用户的定性反馈。

**迭代循环**：与之前相同——改进技能，重新运行测试用例，请求反馈——只是中间不再需要浏览器审查员。如果你有文件系统，仍然可以将结果组织到迭代目录中。

**描述优化**：本节需要 `claude` 命令行工具（特别是 `claude -p`），该工具仅在 Claude Code 中可用。如果你在 Claude.ai 上，请跳过此部分。

**盲比较**：需要子代理。请跳过。

**打包**：`package_skill.py` 脚本在任何有 Python 和文件系统的位置都可以工作。在 Claude.ai 上，你可以运行它，用户可以下载生成的 `.skill` 文件。

**更新现有技能**：用户可能会要求你更新现有技能，而不是创建新技能。在这种情况下：
- **保留原始名称**。注意技能的目录名称和 `name` 前置字段——使用它们不变。例如，如果已安装的技能是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
- **编辑前复制到可写位置**。已安装的技能路径可能是只读的。复制到 `/tmp/skill-name/`，在那里编辑，并从副本打包。
- **手动打包时，先在 `/tmp/` 中暂存**，然后复制到输出目录——直接写入可能因权限问题而失败。

## Cowork 特定说明

如果你在 Cowork，需要了解的主要事项有：

- 你有子代理，因此主要工作流程（并行生成测试用例，运行基线，评分等）都可以正常工作。（但是，如果你遇到严重的超时问题，可以改为串行运行测试提示而不是并行运行。）
- 你没有浏览器或显示器，因此在生成评估查看器时，使用 `--static <output_path>` 将其写入独立的 HTML 文件，而不是启动服务器。然后提供一个链接，用户可以点击打开 HTML 文件。
- 由于某种原因，Cowork 设置似乎使 Claude 在运行测试后不愿意生成评估查看器，所以重申一下：无论你在 Cowork 还是 Claude Code 中，运行测试后，都应该始终生成评估查看器，供人类查看示例，然后再自行修改技能并尝试进行更正，使用 `generate_review.py`（而不是编写自己的定制 HTML 代码）。提前道歉，但我打算全部大写：在自行评估输入之前 *务必* 生成评估查看器。你要尽快将它们展示给人类！
- 反馈工作方式不同：由于没有运行服务器，查看器的“提交所有评论”按钮将 `feedback.json` 下载为文件。然后你可以从那里读取它（你可能需要先请求访问权限）。
- 打包功能正常——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）应该可以在 Cowork 中正常工作，因为它使用 `claude -p` 通过子进程，而不是浏览器，但请等到你完全完成技能制作并且用户同意它状态良好后再保存。
- **更新现有技能**：用户可能会要求你更新现有技能，而不是创建新技能。请遵循上面 claude.ai 部分的更新指南。
