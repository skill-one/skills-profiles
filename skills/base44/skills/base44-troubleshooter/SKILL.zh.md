# 解决生产问题

## 前置条件

在获取日志前验证身份：

```bash
npx base44 whoami
```

如果未通过身份验证或令牌过期，请指示用户运行 `npx base44 login`。

通过以下方式之一解析应用上下文：

```bash
# 从链接的本地项目
cat base44/.app.jsonc

# 或者显式指定
npx base44 logs --app-id app_123
```

## 可用命令

| 命令 | 描述 | 参考 |
|------|------|------|
| `base44 logs` | 获取此应用的函数日志 | [project-logs.md](references/project-logs.md) |
| `base44 workflows runs` | 列出工作流运行记录，按最新优先；失败的运行记录会包含失败的任务和底层错误 | [workflows-runs.md](../base44-cli/references/workflows-runs.md) |
| `base44 workflows list` | 列出此应用的工作流，包含状态和运行摘要 | [workflows-list.md](../base44-cli/references/workflows-list.md) |

## 日志不会即时读取

**单次获取失败并不能证明任何问题。** 一次性 `base44 logs` 读取的是滞后于调用的索引，因此触发函数后立即获取到的空结果是其预期结果，而不是问题的证据。

- **实时调试：使用 `--follow`。** 当实时数据流可用时，它会以**不到一秒**的速度传输行。当实时数据流不可用时，CLI 会告知并改为轮询（`警告：此应用的实时日志不可用——回退到轮询（行可能滞后 ~20-30 秒）。`）。无论哪种情况，`--follow` 都是正确的工具——你永远不需要选择。
- **一次性获取会滞后 ~20-30 秒。** 这是数据摄入时间，不是过滤器问题。
- **当输出为空时，需要改变的是时间，而不是标志。** 等待并重新运行相同的命令。扩大 `--limit`、删除 `--level` 或切换 `--order` 都不会改变尚未摄入的行的状态，重新设置标志是代理自我误诊的方式。

## 排错流程

### 1. 观察问题发生——`--follow`

如果你可以触发失败（或它正在发生），从实时观察开始，而不是事后获取：

```bash
npx base44 logs --follow
npx base44 logs --follow --function <function_name>
```

然后调用函数并读取结果。以下规则可防止你误读健康的数据流：

- **不要基于时间做决定。** 打开数据流，触发函数，直到看到行出现——不要读取固定窗口，打印并得出“损坏”的结论。安静的数据流是安静的，因为没有任何调用。
- **数据传输是按调用而非按行进行的。** 长时间运行的函数的行会在调用结束时一起到达。调用期间的中断是正常的。
- **在实时观察期间重新部署是安全的。** 部署会在几秒钟内旋转脚本，相同的打开数据流会在下一次调用时传输新代码的行。不要在每次部署后关闭数据流并重建它。
- **`--since` 与 `--follow` 一起使用会被拒绝**（数据流从现在开始），`--until` 和 `--order` 也会被拒绝。对于历史数据，使用一次性获取。
- **模式在启动时一次性确定。** 如果第一个连接被拒绝或无法访问，该运行将一直轮询。如果数据流打开，则没有轮询回退可用。
- **运行期间丢失的数据流会结束命令**，显示 `Error: The realtime log stream stopped and could not be re-established`，退出码为 1。该退出是数据流放弃，而不是日志功能损坏的证据——重新运行相同的命令，而不是更改标志。

### 2. 确认是否为计划运行而非请求

工作流是自动化系统——cron 定时任务、实体触发、连接器事件、应用内代理操作。**当投诉是“我的计划任务未运行”或“自动化停止工作”时，函数日志是错误的工具。** 它们显示函数打印了什么；它们无法告诉你是否派发了运行、哪个任务内部失败，或为什么工作流停止触发。

```bash
npx base44 workflows runs --status failed
npx base44 workflows list
```

失败的运行记录会包含失败的任务和底层错误，因此从这些记录开始，只有在知道失败任务调用了哪个函数后，才进入 `base44 logs`。`workflows list` 报告 `consecutiveFailures`——任何大于零的值都是需要关注的流程。

这里容易误导的两个点：

- **触发列中的 `manual` 并不表示有人点击了什么。** 当运行被无触发类型派发时，它会被标记为 `manual`。
- **测试运行被包括在内**，作为触发类型的旁边标签 `(scheduled, test)`。你自己运行以检查某事的运行记录会出现在列表中。

### 3. 检查最近错误

首先获取所有函数的最新错误：

```bash
npx base44 logs --level error
```

### 4. 深入特定函数

如果你知道哪个函数失败：

```bash
npx base44 logs --function <function_name> --level error
```

如果你不在项目目录外，请显式传递应用 ID：

```bash
npx base44 logs --app-id app_123 --function <function_name> --level error
```

`--function` 过滤器是对 *标记* 行的过滤。仍在使用旧版按函数部署的应用会发出未标记的行，因此过滤视图可能会隐藏它们；这会在应用的下次部署时自动修复。如果过滤的运行记录为空，请在得出没有日志的结论前，不使用 `--function` 重新运行。

### 5. 检查时间范围

与用户报告的问题时间戳关联：

```bash
npx base44 logs --function <function_name> --since <start_time> --until <end_time>
```

### 6. 分析日志

- 在输出中查找堆栈跟踪和错误消息
- 检查时间戳以与用户报告的问题关联
- 显式传递 `--limit` 以获取更早的数据——没有默认页面大小，超过 500 的值会被限制为 500

## 读取空结果

`No logs found matching the filters.` 是模糊的——永远不要将其解释为“健康”。它表示以下之一：

- 运行尚未摄入（最常见——等待并重新运行，见上文）
- 没有该名称的函数，或过滤器丢弃了未标记的行（见步骤 3）
- 未发布的应用，在读取 `--env prod` 时（`No production logs found.` —— 尝试 `--env preview` 获取草稿日志）
