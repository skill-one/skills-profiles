# 为 meticulous 项目提高覆盖率

> 如果你还没有运行过 `meticulous-cli-update`，请先运行它（它也涵盖了认证和项目选择）。

## 你需要交付的内容

两个独立的输出，都期望得到——它们不能互相替代：

1. **一个或多个从新录制的会话中生成的测试运行，可证明扩展了覆盖率。** "可证明"意味着与基线进行比较，命名文件覆盖率提高的文件，以及提高的幅度（步骤 7）。如果一个目标结果证明无法覆盖，请如实说明，而不是凑数。
2. **一个提议 `.meticulousignore` 变化的 PR。** 只包含你 _确信_ 完全无法覆盖的路径——通常是整个目录。你仅仅在一次会话中未能达到的任何内容都不应包含在内；将其排除并在 PR 描述中提及。

## 开始前：在 `main` 分支上，使用干净的树运行

以下每个命令都依赖于 CLI 从你的本地签出中解析内容：`js-coverage` 默认为当前 git HEAD，`trigger-test-run` 默认为部署的 HEAD，而为基线默认分支的合并基线。在 `main` 分支上，干净的树中这些会合并为一个提交，这正是你想要的——没有差异，仅运行 HEAD，并且在步骤 7 中的联合会被 API 接受。

不在 `main` 上，这种方式会以繁琐的方式破坏：除非每个运行的执行了 _完全相同_ 的提交，否则联合覆盖率会被拒绝，并且每当其基线分支移动时，PR 的合并提交都会重新计算，因此较早触发的运行将不再与新运行联合。

所以：签出 `main`，拉取，并确保在步骤 1 之前 `git status` 是干净的。

然后确认确实有一个测试运行可供使用：

```bash
meticulous agent test-run-for-commit
```

保留它打印的 ID——步骤 7 会回退到它。如果它报告 **"未找到提交 … 的测试运行"**，停止并向用户报告；没有它就无法进行基线。最常见的原因是 CLI 指向了错误的项目，所以建议他们使用 `meticulous auth get-project` 进行检查。`meticulous auth set-project` 仅适用于 OAuth 令牌；API 令牌绑定到一个项目（所以 `set-project` 失败），并且注入的凭证没有本地令牌可供选择——在这些情况下，修复方法是使用不同的凭证，而不是 `set-project`。

## 步骤 1 — 基线覆盖率

获取标题中的数字。这是一个调用，它是步骤 7 和 8 比较的数字：

```bash
meticulous agent js-coverage --summary
```

不要输出整个仓库的每个文件覆盖率。这个技能中的每个问题都是一个狭义的查询（一个目录，或者最坏的文件首先），所以一页就足够了。每个分页命令会在 stderr 报告你得到的行数和匹配的文件数（`files 1-50 of 8214; …`）。阅读这个通知：总数通常是答案。

如果这报告 **"未找到提交 … 的测试运行"**（如果上面的检查通过，则不应该这样），停止并向用户报告。不要通过基于其他提交的运行进行基线来规避它：步骤 7 的联合要求新的运行和基线执行了相同的提交。

基线运行的会话通常还没有全部重播，这会低估其覆盖率——如果 `js-coverage` 这样说，运行 `meticulous agent complete-base-run`（它默认等待直到没有更多可以调度；这可能需要一段时间，所以检查回来或重新运行，而不是假设它挂了），然后重新运行 `js-coverage`。不要期望 `unexecutedSessionCount` 总是达到 `0`——一些会话可能永久无法获得，并且 `js-coverage` 容忍一小部分这些，而不是永远拒绝。

## 步骤 2 — 将死代码与真实目标分开

你在寻找两件不同的事情，将它们分开有助于：

- **`.meticulousignore` 候选文件**：在整个目录中 _一致_ 为 0% 的文件，这表明它们在浏览器中根本不会执行。
- **覆盖率目标**：一个真实用户流程可以到达，但记录的会话碰巧没有到达的文件。

每个都有自己的查询，所有查询都基于 `--orderBy`。它在服务器上对运行中的每个文件进行排序，包括 0% 文件（不需要 `--includeAllFiles`），并通过路径打破平局。`--globFilter` 将查询范围限定在目录中，并且可以重复。

### 忽略候选文件

从这里开始，因为它们会缩小列表。按目录逐个检查，从仓库自己的布局（在单体仓库中为 `ls packages/`，在单个应用中为顶层源目录）获取目录，而不是从覆盖率数据获取。对于每个目录，请求其最执行的文件：

```bash
meticulous agent js-coverage --globFilter "packages/<name>/**" \
  --orderBy=executedLines --includeLineCounts --limit=1
```

- **即使对于该文件 `executedLines` 也是 0**：该目录中的每个文件都是 0%，并且 stderr 通知说明了数量。这强烈表明该目录从未发送到浏览器（后端、CLI 工具、文档、e2e 测试框架），所以它是 `.meticulousignore` 候选文件。
- **没有文件匹配**：该目录已经在覆盖率报告中之外，并且为它添加规则将无任何作用。
- **其他任何情况**：该目录是活跃的。如果你怀疑其内部有一个死角，请以相同的方式检查其子目录。

有一个第二的、更强的信号，它完全依赖于覆盖率数据。它捕获了在一个否则活跃的目录中散布的单独死文件，而按目录检查完全错过了。列出活跃目录的 0% 文件（它们按路径排序；一旦行数超过 0% 就停止分页）：

```bash
meticulous agent js-coverage --globFilter "<live-dir>/**" \
  --orderBy=coveragePercentage --order=asc --includeLineCounts --limit=100
```

对于每个文件，在代码库中搜索其实际导出的符号，而不仅仅是其文件名：

```bash
# 示例仅作说明——根据此仓库调整源根和扩展名
grep -rn "theActualExportedName" <src-root> --include="*.ts" --include="*.tsx"
```

如果唯一匹配是文件自己的定义，没有任何内容导入它，因此没有任何会话——无论多么全面——可以执行它。这是无法到达的证据，而不是从沉默中推断，即使你在该文件中已经有了目录级规则，也值得检查。

一些类别是 **几乎到处都是安全的排除项**，并且值得提出，前提是按目录检查同意它们在所有目录中都是一致的 0%。它和目录一样好地处理像 `**/__tests__/**` 或 `**/*.stories.*` 这样的通配符：

- 测试文件及其目录——`__tests__/`、`__mocks__/`、`*.test.*`、`*.spec.*`
- Storybook——`*.stories.*`、`__stories__/`、`.storybook/`
- 测试/模拟框架目录——`testing/`、`mocks/`、`fixtures`
- 仅由 Node 执行的构建、检查和代码生成配置——`*.config.*`、`setupTests.*`、脚本目录

其中一些可能已经完全在覆盖率报告之外。一个匹配不到文件的通配符不需要规则。

如果你知道一个目录在所有地方都显示为 0%，要怀疑它——如果你知道它被捆绑到前端（主应用导入的共享组件/工具库），那么这种模式更有可能是 source-map/路径归属差距，而不是真正的死代码——将其排除在忽略列表之外，并将其标记为未解决。

### 覆盖率目标

这些不仅仅是 0% 的文件。一个 12% 或 40% 的文件通常意味着它的一条路径运行，而其余路径不运行。这些部分文件通常是最低成本的胜利：模块已经加载，所以一个额外的交互就可以点亮一大块。从应用程序的真实源开始，排除测试、故事和忽略候选文件，从那些有最多收益的文件开始：

```bash
meticulous agent js-coverage --globFilter "<app-src>/**" \
  --orderBy=uncoveredLines --includeLineCounts --includeCoveragePercentage \
  --limit=50
```

这混合了 0% 和部分文件，百分比列将它们区分开来。在收益相当的情况下，优先选择部分文件而不是 0% 的文件。要查看最少覆盖的部分文件，请使用 `--orderBy=coveragePercentage --order=asc`。没有过滤器可以排除 0% 的文件，所以该列表从整个 0% 块开始；使用 `--offset` 翻页。

按功能区域对候选文件进行分组，而不是选择单个最坏的文件。一个记录的流程通常一次性移动一簇相关的文件，所以一个在十几个文件中显示为 5-20% 的目录是一个比一个孤立的 0% 文件（位于一个不为人知的分支后面）更好的目标。重新运行针对功能目录的查询以查看该簇。

一些 0% 或低文件受功能切换控制，该切换默认关闭，而不是位于无人驾驶的 UI 路径上。在假设它需要一个全新的流程之前，检查切换注册表和文件的门控条件：在本地打开切换可以使看起来死掉的文件成为容易的目标。

## 步骤 3 — 追踪，而不是猜测

对于每个候选文件，找到它的实际调用者——例如：

```bash
# 示例仅作说明——根据此仓库调整源根和扩展名
grep -rln "<ExportedThing" <src-root> --include="*.tsx" | grep -v test
```

阅读调用者。确认：

- 它可以通过一个简单、可描述的 UI 操作（一个特定的按钮、一个特定的菜单项）到达——而不是隐藏在一个功能切换、禁用的配置（例如此环境中关闭的计费/SSO 切换）或仅对某些对象类型触发的条件分支后面。
- 如果目标是 **钩子**，检查每个调用它的分支。钩子通常在条件下被调用——一个分支可能通过一个完全不同的机制路由（一个普通的 `<Link>` 而不是应用程序自己的导航钩子，一个侧边面板打开而不是完整导航）。确认候选操作实际触发了哪个分支。

## 步骤 4 — 驱动流程

**这三种驱动器中的任何一种都可以正确记录**——通过两个不同的应用程序进行验证：

- **Claude in Chrome**——唯一一个可以驱动用户自己的已登录 Chrome 配置的驱动器，所以需要登录流程的应用不需要登录流程。它的输入路径也是那个会卡住（见下文）的路径，所以请尽早验证并准备好切换。
- **Playwright** 和 **`agent-browser`**——通过 CDP 启动的浏览器，更快、更可脚本化，并且在所有测试中都可靠。权衡是每次都有一个新配置文件，所以你必须登录。`agent-browser` 额外拒绝在目标被另一个元素覆盖时点击，并命名覆盖的节点，这捕获了其他两种驱动器会愉快执行的沉默错误点击的一类。

**设置一个现实的视口** 无论你选择哪种方式。CDP 浏览器默认为某个小尺寸（大约 1280px 宽），而真实 Chrome 窗口通常是其两倍。响应式布局在不同宽度下渲染不同的组件，所以默认视口可以安静地覆盖不同的代码——或者隐藏你想要控制的部分。

比选择工具更重要的是以下规则。

**只有可信事件才会被记录。** 记录器会忽略在页面 JS 中合成的内容，所以 `element.click()`、分配 `input.value` 或派发你自己的事件都可以令人信服地驱动应用程序并记录 _无_ 任何内容。页面看起来是正确的，会话返回为空。通过工具的真实输入动作驱动一切。

当某事不起作用时，找出哪个部分是损坏的，然后再改变策略——安装一个捕获探针并重复操作：

```js
window.__ev = [];
["pointerdown", "click", "keydown", "change"].forEach((t) =>
  window.addEventListener(
    t,
    (e) => window.__ev.push({ t, trusted: e.isTrusted }),
    true,
  ),
);
```

- 没有捕获到任何内容 → 你的输入从未到达页面；不同的选择器或坐标不会有所帮助（见下文卡住的扩展说明）
- 捕获到但 `trusted: false` → 它到达了页面但不会被记录；你在某个地方合成内容

### 三种方式使操作记录为无

所有三种方式在浏览器中看起来都像成功，这就是它们昂贵的原因——你从覆盖率数字中得知，但事后很久才知道。

**原生 `<select>`。** 通过表单填充操作设置值，或在 JS 中分配它，会触发一个 `change`，其 `isTrusted: false`——应用程序会做出反应，值会明显更新，所以看起来像它工作了，但记录器会忽略它，并且在重播时不会发生排序/过滤。点击 `<select>` 也没用：那会打开一个操作系统级别的弹出窗口，驱动器看不到。有效的方法是聚焦元素并按选项可见文本的第一个字母（"p" → "Priority"），这会产生一个可信的 `keydown` _和_ 可信的 `change`。重复字母以循环共享初始字母的选项。使用 `change` 监听器读取 `e.isTrusted`——无论如何值都会更新，所以仅凭值无法告诉你任何信息。

**修饰符快捷键。** 重播只有在记录了离散的修饰符按键并仍然按住时才会重播修饰符。一些驱动器只为基本键发送一个：Claude in Chrome 的 `cmd+k` 和 `agent-browser` 的 `press Alt+ArrowRight` 都记录了一个带有修饰符标志的单个按键，没有单独的修饰符按键，所以在重播时标志被清除，处理程序体从未运行——尽管在实时中工作得很好。Playwright 的 `press('Alt+ArrowRight')` 会记录离散的按键并正确重播（已通过覆盖率验证）。

所以：如果存在等效的 _点击_ 目标，请优先选择它，如果你必须使用和弦，请使用 Playwright 驱动它，并从覆盖率中确认。如果持有 `if (… && event.metaKey)` 的行被覆盖，但主体没有被覆盖，则按键已交付且条件评估为假——这就是这种情况。

**双击。** 双击可能被记录为一个单击，在这种情况下，重播永远不会触发 `onDoubleClick`，并且该会话中后续的每个事件都针对从未打开的 UI——所以覆盖率会 _下降_。检查记录的事件计数看起来像两个按下/释放对，并将任何仅双击的功能视为可疑，直到覆盖率确认它。

### 一些交互可能根本无法通过 agent 驱动的记录来生存

偶尔一个交互记录得干净，在实时中明显工作，但处理程序它本应触发在重播时从未触发——没有错误，并且受影响的文件在步骤 7 的联合中恰好是其基线百分比。一个看到的情况：在下拉菜单自己的门户渲染内容中的输入中输入一个值（一个过滤芯片，一个在 "..." 菜单后面的视图重命名）。在同一个门户中的普通点击，以及主页面树中输入的相同类型-然后-Enter 序列，都可以正常重播——所以这是特定于在门户中输入键盘/文本输入，而不是驱动器问题。

不要假设一个输入值的靶标工作只是因为实时交互工作——检查步骤 7 的差异。如果一个靶标只能通过这种交互重播，并且不会移动，那是 agent 驱动的记录对这个流程的缺陷：将其报告为未解决，并建议手动驱动该流程，而不是继续用重试来凑数。

### `claude-in-chrome` 的具体细节

- **截图被缩小** (~0.6倍)，因此它们不是CSS像素。从截图中读取点击坐标，或者通过 `screenshotWidth / window.innerWidth` 缩放 `getBoundingClientRect()` 的中心。在每次调整大小后重新计算，并重新截图而不是重用来自早期页面的坐标——布局会发生变化，并且过时的坐标可能会落在错误的元素上并记录下您未打算进行的交互。
- **在点击它之前立即重新获取 `ref`**，并且不要跨页面或标签页重用。不要预测一个数字——`read_page` 不会按顺序发出它们。引用和坐标同样可靠；选择 whichever 方便。这不仅仅适用于 `claude-in-chrome`——`agent-browser` 的 `snapshot` 引用也会以相同的方式过期，并且重用它们会默默地点击现在占据该引用的内容，而不是您打算点击的内容。它曾经导致了一个真实的错误：过时的引用落在了表格的“添加新项”交互元素上，并创建了一个空白记录。在每次点击之前立即获取一个新的快照，因为DOM可能已经发生变化，并将点击后意外页面/记录数变化视为一个刚刚出错的引用，而不是一个不相关的错误——在继续之前清理它创建的内容。
- **输入交付时断时续。** 每次点击和按键都会报告成功，读取操作仍然正常工作，但没有任何内容到达页面。引用和坐标会一起失效，所以这永远不会是选择器问题——并且它不会通过打开新标签页、重新导航、等待或重试来清除。完全重启Chrome有助于解决但不会持久修复它。**在您第一次交互后检查探测器**，在驱动整个流程之前，如果输入没有到达则切换到 Playwright 或 `agent-browser` 而不是切换选择器方法。两者在整个过程中都保持可靠，包括在Claude in Chrome停止工作的同一时刻的同一页面上。

### 驱动后验证

1. 导航到目标URL并执行实际操作。
2. 确认它对DOM有效（例如 `document.body.innerText.includes(...)`），而不仅仅是截图——一个出现的工具提示可能看起来像成功。检查您是否仍然在您认为的页面上：一个已经悄悄将您重定向到登录屏幕的应用程序会吸收盲坐标点击到空白空间，并给您一个没有任何事件的会话。
3. **关闭标签页。**

在触发任何操作之前，先对录制进行合理性检查。关闭标签页后等待 ~10秒，以便会话完成，并检查它是否捕获了某些内容：

```bash
meticulous agent sessions --limit 10 --excludeSyntheticSessions \
  --includeDurationSeconds --includeNumberUserEvents \
  --includeNumberUrlsVisited --includeStartUrl --includeAbandonedReason
```

读取您刚刚生成的行：

- **没有任何行**——还没有任何内容上传；在得出录制失败的结论之前再等待一段时间
- **`numberUserEvents` 为 0**——记录器没有看到任何用户输入。您的点击没有到达页面，或者被合成而不是信任；回到上面提到的输入交付探测器。重播此会话是无用的。
- **当您导航多次时 `numberUrlsVisited` 为 1**——后面的页面没有进入此会话。它们要么进入了它们自己的会话（没关系，收集那些id），要么被作为无法重播的尾部吞没（见步骤5中的硬导航注释）。
- **`durationSeconds` 超过 300**——5分钟后的所有内容在重播时将被静默修剪（步骤5）。重新录制溢出的部分作为其自己的会话，而不是希望它幸存。
- **`abandonedReason` 已填充**——记录器放弃了此会话（见步骤5中的10分钟限制）；它不值得重播。
- **`startUrl` 不是您驱动的页面**——您关心的导航属于您假设的不同的会话。

**会话只有在标签页关闭后才是完整的。** 当标签页打开时，该行仅反映到目前为止上传的片段，因此低或零 `numberUserEvents` 意味着“尚未刷新”，**而不是**“录制失败”。此技能测量的会话在标签页打开时读取 **0** 个事件，一旦关闭则为 **12** 个。过早判断几乎导致了一个完美的录制从头开始重新驱动。

事件以短间隔（几秒）上传，但在卸载时尚未刷新的内容仅存储在 `sessionStorage` 中，并在稍后的页面加载时重新发送到同一源——因此会话的尾部可能会延迟到下一次访问。优先选择离开而不是硬关闭浏览器，并且永远不要立即判断录制。

**一次性录制多个目标？在录制每个目标后**，而不是只在结束时一次运行此检查，运行此检查。仅在结束时检查会导致无法判断哪个操作丢失了会话，并且您将不得不重新驱动所有内容才能找出哪个需要重做。

### 步骤5 — 会话时间预算和关闭纪律

- **云重播会话时间限制为5分钟。** 在此之后记录的所有内容在重播时将被静默修剪——运行仍然成功并报告其准确性，因此损失只有在您寻找时才可见（截图路由提前停止；允许的事件比会话中的点击少得多）。不要让此问题留到感觉：`agent sessions --includeDurationSeconds` 给您提供数字，并且任何超过300的都是丢失尾部。
- **您的交互速度消耗此预算。** 每个查找/点击/验证往返需要10-60秒的 _记录_ 会话时间。在打开标签页之前完全规划流程，将您的操作批量处理为尽可能少的往返，并在它们之间保持短等待，之后从录制中验证而不是在流程中验证，并尽量保持在4分钟以内。几个短会话比一个长扫描更好。
- **直接URL导航是到达每个目标页面的合法快速路径**，并且可以很好地重播——优先选择它而不是慢速点击路径。但是硬导航会将录制分割成多个会话，因此之后收集每个结果会话id并将它们全部传递给 `--sessionIds`（步骤6）。通常这是没问题的，每个部分都保持在重播限制内。陷阱是过快地再次导航：一个在之前的几秒钟后到达的页面被附加到该会话的尾部而不是开始自己的会话，并且尾部通常无法重播——因此页面在您驱动它时渲染完美，但仍然不提供覆盖率。在转到下一个页面之前，为每个您实际关心的页面提供自己的停留时间（~10秒），并在步骤6中检查它是否作为自己的 `startUrl` 出现。对没有连接 `onSubmit` 处理器的简单 `<form>` 提交也适用相同的注意事项——它触发真实的浏览器重新加载而不是SPA转换，并且如果立即导航，也可能丢失刚刚录制的未刷新会话。
- **记录器限制：** 标签页打开时间的10分钟硬限制将整个会话标记为“放弃”；上传以5秒间隔刷新——在最后一个交互后关闭标签页前等待 ~6-8秒。

### 步骤6 — 收集会话id并触发测试运行

首先列出您实际录制的，按最新顺序：

```bash
meticulous agent sessions --limit 20 --excludeSyntheticSessions \
  --includeDurationSeconds --includeNumberUserEvents \
  --includeNumberUrlsVisited --includeStartUrl
```

跳过任何 `numberUserEvents` 为 0 的行——它将重播为空，并且只会稀释运行。注意任何 `durationSeconds` 超过 300 的行：它将重播，但只有它的前五分钟，因此将其尾部覆盖率视为缺失而不是假设整个流程运行。

通过记录时间和 `startUrl` 识别您的会话。在此处要小心：其他人——以及指向同一项目的其他应用程序——也在录制，因此永远不要假设最新的N行是您的。`--recordedSince` 和 `--visitedUrlFilter` 是在列表繁忙时快速缩小范围的最快方法。

预期 **比您驱动的页面更多的会话**：硬导航通常结束一个会话并开始另一个，因此一个五页扫描可以产生五个id。收集所有它们。一个URL从未作为 `startUrl` 出现的页面可能被作为前一个会话的尾部吞没，并且将无法重播——如果您需要它被覆盖，请单独重新录制它。

然后触发：

```bash
meticulous agent trigger-test-run --sessionIds "<id1>,<id2>,..."
```

### 步骤7 — 与联合而不是原始差异比较

从汇总开始。它回答“是否有任何内容移动”在一个调用中，并且您可以直接将其与步骤1的 `--summary` 比较：

```bash
meticulous agent js-coverage --summary --headPlusTestRunIds "<newRunId>"
```

这会将您的新运行与从HEAD解析的基线运行（步骤1使用的相同运行）联合，因此它是基线覆盖率 **加上** 您新会话的覆盖率。提交解析会跳过明确会话集的运行，因此您刚刚触发的运行不会被选为基线。您需要联合，因为 `--sessionIds` _替换_了该运行的选择集而不是将其添加到其中。单独地，您的运行覆盖范围远小于基线，并且直接比较它将读取大量回归。联合只能增加覆盖率，因此其数字永远不会低于步骤1。

仅传递您的新的运行：一个运行不能与其自身联合。

然后询问您打算覆盖的文件。将每个目标（重复 `--globFilter`），一次带联合一次不带它用于基线：

```bash
meticulous agent js-coverage --headPlusTestRunIds "<newRunId>" \
  --globFilter "<target1>" --globFilter "<target2>" \
  --includeLineCounts --includeCoveragePercentage
meticulous agent js-coverage \
  --globFilter "<target1>" --globFilter "<target2>" \
  --includeLineCounts --includeCoveragePercentage
```

HEAD解析为金色集运行的两个迹象：联合被拒绝“正在查询运行”，或者其摘要低于步骤1（您联合到另一个狭窄的会话集；这不是回归）。最可能的原因是预置会话运行早于跳过。无论如何，明确命名双方，使用步骤0的基线id：

```bash
meticulous agent js-coverage --summary --testRunIds "<baselineRunId>,<newRunId>"
```

在目标查询中使用相同的 `--testRunIds` 替换 `--headPlusTestRunIds`。

如果联合因运行了不同的提交而被拒绝，那就是 `main`/干净树前提条件咬人——见此技能的顶部。

### 步骤8 — 验证和报告

对于每个跟踪的目标文件：覆盖率是否移动？对于步骤2的每个 `.meticulousignore` 候选文件：它在联合中是否保持在0%？使用 `--headPlusTestRunIds "<newRunId>"` 添加重新运行步骤2的每个目录检查。如果 `executedLines` 仍然为 0，则您的会话所做的任何操作都没有到达它。

如果一个良好跟踪的目标没有移动，不要假设录制失败——首先检查会话（步骤4：它是否存在，它是否捕获了用户事件和URL访问，它是否被放弃，它的 `startUrl` 是否是您驱动的页面？），然后检查点击是否实际到达了您预期的文件（步骤3）而不是兄弟/父组件，而不是一个。如果目标仍然无法解析，请诚实报告；不要在没有覆盖率数字的情况下声称成功。

测试运行证明覆盖率是可到达的，但直到会话被选为集合之前，循环运行不会改变。提升那些移动了目标的会话，而不是等待下一次会话选择来拾取它们：

```bash
meticulous agent promote-sessions --testRunId="<newRunId>" \
  --sessionIds="<id1>,<id2>"
```

仅传递那些值得它——步骤7显示获得覆盖率的会话——因为每个提升的会话都会在之后的每个测试运行中运行。仅当所有它们都提升时才省略 `--sessionIds`。下一次会话选择会与其他集合中的其余部分重新排序，并丢弃任何最终证明是冗余的。

响应的 `updatedBaseTestRunId` 是您提交的更新后的基线运行：基线加上您提升的会话的重播。它需要几分钟来后处理，并且直到它完成，提交仍然解析为旧的基线运行——因此立即 `js-coverage` 返回的是 **旧的** 数字，没有任何内容表明它已过时。通过其id读取更新后的运行，它等待它完成：

```bash
meticulous agent js-coverage --summary --testRunId="<updatedBaseTestRunId>"
```

在您的报告中引用该数字：它是提交自己的数字，包含提升，并且应该与步骤7的联合匹配。如果 `updatedBaseTestRunId` 返回为空，stderr上的通知说明了原因；报告步骤7的联合而不是它。

除非您的提交的基线运行已经重播了其整个选择集，否则提升会被拒绝，因此如果您在步骤1中跳过了 `complete-base-run`，请现在运行它并再次提升。它也有上限：最多每调用20个会话，并且在两次会话选择之间最多10%的项目配置选择集大小。如果您达到上限，请提升具有最大收益的会话，并在报告中命名其余的会话。

### 步骤9 — 打开 `.meticulousignore` PR

第二个交付物。分支，提交 `.meticulousignore` 变更，并打开一个PR。

**仅建议您确信绝对无法覆盖的路径。** 标准是“没有任何会话可以执行这个”，而不是“我今天没有到达它”。优先选择目录级规则而不是长文件列表——目录规则随着文件的添加保持正确，而文件列表会默默地过期。实际上，大多数条目来自步骤2中的安全排除类别加上步骤2的每个目录检查显示的整个非浏览器包在统一的0%。

在提交之前确认：您即将忽略的每个路径在联合中保持为0%（步骤8的检查）。您的新会话刚刚覆盖的路径显然不属于忽略列表，并且该检查会捕获它。

一个常见的结构是“忽略所有内容，然后取消忽略在浏览器中运行的那些”——这是Meticulous自己的单体存储库使用的模式：

```
# 除了在浏览器中执行且具有有意义的前端覆盖率的包之外，忽略所有内容。

packages/*
!packages/<frontend-app>/
!packages/<frontend-app>/**
!packages/<shared-ui-lib>/
!packages/<shared-ui-lib>/**
```

请注意，`.meticulousignore` 遵循 gitignore 语义，因此一旦其父目录被排除，文件就不能重新包含——取消忽略目录（`!some/dir/**/`）以及文件。

在PR描述中，给出每个规则的推理——为什么这段代码无法在浏览器中运行（它是一个Node-only构建脚本、一个测试 harness、一个后端包）。基线只能显示您今天处于0%，这永远不会是它无法到达的证据，因此解释必须来自代码的实际内容。还明确指出：

- 您在忽略列表中遗漏的任何内容，尽管覆盖率低，但您怀疑存在源映射/归因差距而不是死代码（步骤2）
- 只因环境或功能标志配置而无法到达的任何内容——那是审查者的判断，而不是您的，因此请标记它而不是默默地忽略它
