# 代码库设计

设计 **深度模块**：将大量行为置于小接口之后，将接口置于清晰的连接点之上，并通过该接口进行测试。在设计和重构代码时，都应使用这套语言和原则。目标是给调用者带来杠杆效应，给维护者带来局部性，并让每个人都更容易测试。

## 术语表

准确使用这些术语，不要替换为 "组件"、"服务"、"API" 或 "边界"。一致的语言是重点。

**模块** - 任何拥有接口和实现的东西。它故意不限定规模：函数、类、包，或跨层的切片都可以。_避免使用_：单元、组件、服务。

**接口** - 调用者为了正确使用模块所需了解的一切：类型签名，以及不变式、顺序约束、错误模式、所需配置和性能特征。_避免使用_：API、签名（太狭窄，仅指类型级别的表面）。

**实现** - 模块内部的代码体。它与 **适配器** 不同：一个东西可以是小适配器但有大的实现（Postgres 仓库），也可以是大适配器但实现很小（内存中的假象）。讨论连接点时说适配器；其他时候说实现。

**深度** - 接口上的杠杆效应：调用者（或测试）每学习一单位接口，就能触达多少行为。当大量行为隐藏在小接口后面时，模块是 **深度** 的；当接口几乎和实现一样复杂时，模块是 **浅层** 的。

**连接点**（Michael Feathers）- 你可以在不编辑当前位置的情况下改变行为的地方；也就是模块接口所在的 *位置*。连接点的位置是独立的设计决策，不同于连接点后面放置的内容。_避免使用_：边界（它与领域驱动设计的限界上下文过载）。

**适配器** - 在连接点上满足某个接口的具体事物。描述的是 *角色*（填哪个槽位），而不是实质（内部是什么）。

**杠杆效应** - 调用者从深度获得的收益：每学习一单位接口，就获得更多能力。一个实现会在 N 个调用点和 M 个测试中收回成本。

**局部性** - 维护者从深度获得的收益：变更、错误、知识和验证集中在一个地方，而不是分散到调用者中。修一次，到处都修好。

## 深度与浅层

**深度模块** = 小接口 + 大量实现：

```text
+------------------+
| 小接口          | -> 少方法，简单参数
+------------------+
|                  |
| 深度            | -> 隐藏复杂逻辑
| 实现            |
|                  |
+------------------+
```

**浅层模块** = 大接口 + 少实现（避免）：

```text
+-------------------------------+
| 大接口                      | -> 多方法，复杂参数
+-------------------------------+
| 薄实现                      | -> 主要为透传
+-------------------------------+
```

设计接口时问：

- 我能减少方法数量吗？
- 我能简化参数吗？
- 我能把更多复杂度隐藏到内部吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 深度模块内部可以由小的、可模拟、可替换的部分组成，只是它们不属于接口。一个模块可以同时拥有 **内部连接点**（实现私有，供自身测试使用）和位于接口的 **外部连接点**。
- **删除测试。** 想象删除这个模块。如果复杂度消失了，它只是透传。如果复杂度重新分散到 N 个调用者中，它就在发挥价值。
- **接口是测试表面。** 调用者和测试穿过同一个连接点。如果你想测试接口之后的内部细节，这个模块的形状可能不对。
- **一个适配器意味着一个假设的连接点。两个适配器意味着一个真实的连接点。** 除非确实有东西会跨连接点变化，否则不要引入连接点。

## 为可测试性设计

好的接口让测试自然发生：

1. **接受依赖，不要创建它们。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面区域。** 更少方法 = 需要更少的测试。更少参数 = 更简单的测试设置。

## 关系

- 一个 **模块** 恰好有一个 **接口**（它呈现给调用者和测试的表面）。
- **深度** 是 **模块** 的属性，并以其 **接口** 衡量。
- **连接点** 是 **模块** 的 **接口** 所在的位置。
- **适配器** 位于 **连接点** 上，并满足 **接口**。
- **深度** 为调用者产生 **杠杆效应**，为维护者产生 **局部性**。

## 被拒绝的框架

- **将深度视为实现行与接口行的比例**（Ousterhout）：这会奖励填充实现。这里使用杠杆效应作为深度。
- **将 "接口" 理解为 TypeScript `interface` keyword 或类公共方法**：太狭窄；这里的接口包括调用者必须知道的所有事实。
- **"边界"**：与领域驱动设计的限界上下文过载。说 **连接点** 或 **接口**。
