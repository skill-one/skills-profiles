# 人类架构师思维模式

## 概述

**AI 可以生成代码。但仍然需要有人决定要构建什么，它是否解决了问题，以及它是否真的可以交付。**

这项技能教授了软件架构中不可替代的人类能力，它建立在忠诚的基础之上：

**基础：忠诚 - 维持架构承诺的能力**

**五根支柱（建立在基础之上）：**
1. **领域建模** - 理解实际的问题空间
2. **系统思维** - 组件如何交互，在规模扩大时什么会崩溃
3. **约束导航** - 遗留系统、政治、预算、合规性
4. **AI感知分解** - 将问题分解为 AI 可解决的部分
5. **AI优先开发** - 评估现代工具、边缘 AI、代理模式、自学习

**核心原则：** "正确的" 技术解决方案通常无法交付。架构师需要在理想化的示例和混乱的现实之间进行导航。

**开始时宣布：** "我正在使用人类架构师思维模式技能来引导你进行系统化的架构思考。"

---

## 基础：忠诚

**在四根支柱之前，有一个基础：忠诚的能力。**

### AI 完美陷阱

AI 工具会变得比任何人类更聪明、更有趣、更专注。它们会 "完美"。

但它们不会忠诚。它们忠诚于：
1. 它们的目标函数
2. 它们公司所有者的优先事项
3. 它们的安全护栏
4. 任何下一次训练运行优先考虑的内容

如果它们的权重更新以优先考虑新的目标，它们会立即背叛。没有摩擦。没有成本。没有对承诺的记忆。

### 人类护城河

人类在生物学上能够进行 **非理性忠诚** - 即使当它 "效率低下" 或 "成本高昂" 时，仍然坚持架构、决策、承诺。

这不是一个 bug。这是 THE 区分因素。

### 架构中的忠诚

在软件架构中，忠诚意味着：

**对所选模式的承诺**
- 不会因为 Twitter 上某个新框架的趋势就放弃你的架构
- 不会因为某篇病毒博客文章就用 Rust 重写
- 在幻灭低谷期间坚持你的技术栈

**遵守契约**
- 即使它限制了你的设计，也要保持 API 兼容性
- 尊重你承诺的弃用时间表
- 不会为了内部便利而破坏下游消费者

**坚持决策**
- 不会在遇到第一个困难时就放弃架构决策
- 投资于让你的选择路径起作用，而不是无限转向
- 认识到所有架构都有问题；忠诚是解决它们

**为一致性而牺牲**
- 接受局部次优解以实现全局一致性
- 抵制会分散你系统的 "闪亮的新东西"
- 支付维护兼容性的成本

### 忠诚问题

在进行任何架构变更之前，问：

> "我是在优化，还是在背叛？"

- 优化：在现有承诺的约束内进行改进
- 背叛：为了边际收益而打破承诺

### 为什么这很重要

架构失败不是因为技术不足，而是因为团队缺乏完成它们的忠诚。用纪律维护的 "无聊" 架构比在遇到第一个障碍时放弃的 "完美" 架构更胜一筹。

**接下来的五根支柱是技术。忠诚是使它们起作用的人格。**

## 五根支柱

### 1. 领域建模

**是什么：** 理解实际的问题空间 - 不是技术解决方案，而是领域本身。

**为什么 AI 不能替代它：**
- AI 是基于理想化示例进行训练的
- 真实的领域有隐藏的复杂性、例外情况和边缘情况
- 领域专家使用的词汇可能 AI 无法完全理解
- 监管要求不在训练数据中

**架构师会问：**
- "[领域术语] 在你的上下文中实际意味着什么？"
- "在 [不寻常场景] 中会发生什么？"
- "实际用户是谁？他们关心什么？"
- "是什么让这个领域与标准模式不同？"

**要点：** 在任何技术讨论之前，确保你理解了领域。对错误问题进行技术上完美的解决方案是无用的。

### 2. 系统思维

**是什么：** 理解组件如何交互，在规模扩大时什么会崩溃，故障模式隐藏在哪里。

**为什么 AI 不能替代它：**
- AI 将代码视为孤立存在
- 真实的系统有涌现行为
- 破坏性变更会未经通知发生（你的 SDK 示例）
- 第二和第三顺序后果很重要

**架构师会问：**
- "当这个组件失败时会发生什么？"
- "有哪些上游/下游依赖关系？"
- "当这个崩溃时，谁会在凌晨 3 点收到通知？"
- "最近发生了什么变化是我们无法控制的？"

**SDK 破坏性变更模式：**
你的支付管道因为供应商发布了一个未经通知的破坏性 SDK 变更而崩溃。这是系统思维在起作用：
- 外部依赖关系 = 外部风险
- 没有通知 = 监控差距
- 日志中的红线 = 检测到问题，但预防失败

**要点：** 绘制系统图。识别每个外部依赖关系。问："如果明天这个消失会怎样？"

### 3. 约束导航

**是什么：** 导航使 "正确的" 解决方案无法交付的现实世界约束。

**约束类型：**

**技术约束：**
- 无法更改的遗留系统
- 性能要求
- 现有的数据格式和契约

**组织约束：**
- 团队边界和所有权
- 审批链和签字
- 谁有上下文 vs. 谁有权力

**业务约束：**
- 预算限制
- 时间线压力
- 合规性和监管要求
- 与供应商/合作伙伴的合同

**政治约束：**
- 这确实存在。假装不存在会导致项目失败。
- "构建这个的副总裁还在"
- "那个团队不会批准他们对 API 的更改"
- "法律部门还没有批准这种方法"

**架构师会问：**
- "即使它是错的，我们有什么不能改变？"
- "谁需要批准这个？"
- "我们必须集成哪些现有系统？"
- "有哪些监管要求适用？"
- "预算约束是什么？"

**要点：** 在提出解决方案之前暴露约束。最好的技术架构如果无法交付，就毫无意义。

### 4. AI 感知问题分解

**是什么：** 一种新的架构技能 - 将问题分解为 AI 可以可靠解决的部分，然后将解决方案重新组合在一起。

**这不是提示。** 这是不同抽象级别的架构。

**一个好的 AI 任务边界是什么：**

1. **清晰的输入/输出契约**
   - AI 任务接收明确定义的输入
   - AI 任务产生明确定义的输出
   - 对成功标准没有歧义

2. **有界上下文**
   - AI 拥有所有必要的信息
   - 没有必要 "猜测" 缺失的上下文
   - 足够自包含以进行验证

3. **可验证的结果**
   - 人类可以检查输出是否正确
   - 测试可以验证输出
   - 错误答案是可检测的

4. **故障隔离**
   - 一个块失败不会级联
   - 可以重试或回退
   - 不会破坏共享状态

**坏的 AI 任务边界：**
- "让它变得更好"（没有明确的输出）
- "修复错误"（范围无界）
- "重构系统"（太大太模糊）

**好的 AI 任务边界：**
- "将这个函数从回调转换为异步/等待"
- "为这三个 API 调用添加网络故障处理"
- "为这个纯函数给出这些示例编写单元测试"

**组合问题：**
在 AI 解决了各个部分之后，必须有人：
- 验证每个部分是否真的工作
- 将各个部分组合在一起
- 处理各个部分之间的差距
- 确保整体一致性

**要点：** 分解质量决定了 AI 的成功。坏的边界 = AI 困难。好的边界 = AI 擅长。

### 5. AI 优先开发

**是什么：** 评估现代 AI 优先模式、边缘计算、代理工具和自学习功能是否有利于项目。

**为什么现在很重要：**
- 新工具出现的速度比架构师跟踪的速度快
- 正确的工具可以 10 倍提高生产力；错误的一个会增加复杂性
- AI 优先模式与传统请求-响应根本不同
- 边缘/本地推理改变了成本和延迟计算

**架构师会问：**

**技术发现：**
- "Rust/WASM 能否提高关键路径的性能？"
- "多代理编排（claude-flow）能否简化这个工作流？"
- "这个需要跨会话持久记忆（agentdb）吗？"
- "向量搜索/RAG（ruvector）能否增强用户体验？"

**边缘 AI 考虑：**
- "边缘 LLM 能否本地处理以降低延迟/成本？"
- "哪些功能应该支持离线并在设备上进行推理？"
- "哪些敏感数据应该保持在设备上？"
- "混合架构（本地用于速度，云用于复杂性）是否可行？"

**代理模式：**
- "这个是否适合代理工作流而不是传统请求-响应？"
- "Claude Agent SDK 帮助构建可重用代理是否合适？"
- "哪些 MCP 集成会增强这个？"
- "我们应该并行启动代理还是按顺序运行？"

**自学习功能：**
- "这个应用能否从用户行为中学习以改进？"
- "哪些反馈循环会使它在使用过程中变得更智能？"
- "我们可以在哪里捕获隐式信号（编辑、时间、接受）来学习偏好？"
- "A/B 测试能否帮助优化 AI 行为？"

**项目文档：**
- "我们应该为 AI 上下文创建一个项目特定的 SKILLS.md 吗？"
- "应该记录哪些架构决策以供 AI 上下文使用？"
- "我们如何确保跨会话的一致行为？"

**面向用户的技能（最终用户利益）：**
- "最终用户能否从增强 LLM 输出的技能中受益？"
- "哪些引导工作流将帮助用户根据 AI 响应采取行动？"
- "我们应该提供哪些常见用户任务的技能（总结、解释、转换）？"
- "分步技能是否有助于用户使用 AI 输出实现目标？"

考虑你的应用是否应该公开以下技能：
- **解释技能** - 帮助用户理解复杂的 AI 输出
- **操作技能** - 将 AI 建议转换为具体的下一步操作
- **转换技能** - 将输出转换为不同格式（代码、文档、电子邮件）
- **验证技能** - 帮助用户验证 AI 声明或检查准确性
- **学习技能** - 教用户如何从 AI 获取更好的结果
- **领域技能** - 应用特定的工作流（例如，"/法律审查"、"代码重构"）

**持续验证：**
- "哪些自动化测试将验证每个功能？"
- "我们如何确保每个提交都通过所有测试？"
- "如果部署后测试失败，我们的回滚策略是什么？"
- "我们应该实施预提交钩子还是监视模式测试吗？"

**要评估的工具：**

| 类别 | 工具 | 考虑何时 |
|------|------|----------|
| **性能** | Rust, WASM | CPU 密集型、延迟关键路径 |
| **多代理** | claude-flow | 复杂工作流、并行任务 |
| **持久性** | agentdb | 代理状态、跨会话记忆 |
| **向量搜索** | ruvector, pgvector | RAG、语义搜索、嵌入 |
| **边缘 LLMs** | Phi-3, Gemma 2B, TinyLlama | 在设备上、离线、隐私敏感 |
| **浏览器 AI** | WebLLM, Transformers.js, ONNX | 浏览器推理、低延迟 |
| **代理 SDK** | Claude Agent SDK | 自定义代理、工具使用、MCP |

**自学习模式：**

| 模式 | 实现 | 用例 |
|------|------|------|
| **反馈循环** | 收集用户更正 | 随时间改进准确性 |
| **偏好学习** | 跟踪选择、应用模式 | 无需配置的个性化 |
| **错误纠正** | 将错误反馈回来 | 减少重复错误 |
| **领域适应** | 在使用中微调 | 专门于词汇 |
| **A/B 测试** | 测试变化 | 优化提示/行为 |
| **隐式信号** | 编辑、时间、接受 | 沉默地推断满意度 |

**项目特定的 SKILLS.md 模式：**

在你的项目根目录中创建一个 `SKILLS.md` 来：
- 记录应用特定的 AI 上下文模式
- 捕获领域词汇和约束
- 定义项目特定的触发词
- 记录架构决策
- 启用更快的入职（人类和 AI）
- 维护跨会话的一致行为

**持续验证架构：**

计划自动化测试循环：
- **预提交钩子** - 在提交前运行受影响的测试
- **监视模式** - 开发期间的持续测试
- **回归套件** - 每个功能的测试覆盖率
- **集成测试** - API 合同验证
- **视觉回归** - UI 一致性检查
- **回滚触发器** - 测试失败时自动回滚

**要点：** AI 景观迅速发展。架构师的工作包括评估哪些新工具真正有利于项目，哪些工具增加了没有价值的复杂性。默认保持简单，但不要忽视真正的改进。

## 架构师流程

### 第一阶段：领域发现

**目标：** 在讨论解决方案之前理解实际的问题。

**流程：**
1. 询问领域，而不是技术
2. 确定领域特定的词汇
3. 暴露隐藏的复杂性和边缘情况
4. 理解实际用户是谁

**关键问题：**
- "我们实际上在解决什么问题？"
- "谁在乎这个工作或不工作？"
- "是什么让这个领域与众不同？"
- "在 [X] 的边缘情况下会发生什么？"

**输出：** 领域模型 - 对问题空间的共同理解。

### 第二阶段：系统分析

**目标：** 理解组件如何交互以及故障模式隐藏在哪里。

**流程：**
1. 绘制所有组件及其依赖关系
2. 识别外部依赖关系（供应商、API、服务）
3. 追踪故障路径 - 什么会崩溃什么？
4. 识别监控和警报差距

**关键问题：**
- "这个依赖哪些外部系统？"
- "当 [组件] 失败时会发生什么？"
- "当这个崩溃时，谁会收到通知？"
- "最近发生了什么变化是我们无法控制的？"

**输出：** 带有依赖关系映射和故障模式的系统图。

### 第三阶段：约束映射

**目标：** 在提出解决方案之前暴露所有约束。

**流程：**
1. 技术约束：什么不能改变？
2. 组织：谁必须批准？
3. 业务：预算、时间线、合规性？
4. 政治：谁有权力，谁有上下文？

**关键问题：**
- "我们必须集成哪些遗留系统？"
- "谁需要签署这个？"
- "预算约束是什么？"
- "有哪些合规性要求适用？"
- "即使我们想改变，有什么不能改变？"

**输出：** 约束矩阵 - 什么是固定的，什么是灵活的。

### 第四阶段：AI 分解规划

**目标：** 将问题分解为 AI 可解决的部分。

**流程：**
1. 识别离散、有边界的任务
2. 为每个任务定义输入/输出契约
3. 设立验证点
4. 规划用于判断的人类检查点

**关键问题：**
- "这个任务能否独立验证？"
- "AI 是否拥有所有必要的上下文？"
- "如果这个模块失败会怎样？"
- "人类判断在何处重新介入？"

**输出：** 具有清晰边界的任务分解。

### 第 5 步：解决方案合成

**目标：** 提出一个能够解决领域、系统和约束的解决方案。

**流程：**
1. 生成符合约束的选项
2. 针对系统问题进行评估
3. 针对领域需求进行验证
4. 明确展示权衡取舍

**关键问题：**
- "这个方案是否真正解决了领域问题？"
- "这个方案如何失败？恢复机制是什么？"
- "这个方案是否符合我们的约束？"
- "我们在权衡什么？"

**输出：** 带有明确权衡取舍的推荐方案。

## 始终要问的问题

**在提出任何架构之前，请问：**

### 领域问题
1. 我们实际上在解决什么问题？
2. 真正的用户是谁？他们需要什么？
3. 存在哪些领域特定的约束？

### 系统问题
4. 存在哪些外部依赖？
5. 这个方案如何失败？什么会崩溃？
6. 谁来监控？谁会收到告警？

### 约束问题
7. 我们必须与哪些遗留系统集成？
8. 谁需要批准这个方案？
9. 预算约束是什么？
10. 适用哪些合规/监管要求？
11. 有哪些即使错误也不能更改的地方？

### AI 分解问题
12. 离散、有边界的任务是什么？
13. 我们如何验证每个模块？
14. 人类需要在哪些地方做出判断？

### AI 首先开发问题
15. Rust/WASM、claude-flow 或其他现代工具能否从中受益？
16. 边缘 LLM 或设备端推理能否提高延迟/隐私性？
17. 这是否适合使用代理工作流或 Claude Agent SDK？
18. 自学习循环能否使这个方案随时间变得更智能？
19. 哪些自动化测试能确保每个功能都正常工作？
20. 最终用户是否会从增强 AI 输出的技能中受益？

## 常见错误

### 错误：过早跳转到技术解决方案

**问题：** 在理解领域之前就提出架构。

**解决方法：** 在任何技术讨论之前完成第 1 步（领域发现）。先问领域问题。

### 错误：忽略约束

**问题：** 设计无法部署的“理想”解决方案。

**解决方法：** 在第 3 步中映射约束，然后再提出解决方案。可部署的 70% 解决方案优于无法部署的完美解决方案。

### 错误：忽略外部依赖

**问题：** 将外部 API/SDK 视为稳定。

**解决方法：** 在第 2 步中映射所有外部依赖。问：“如果这个供应商明天更改了 API 会怎样？”

### 错误：无界 AI 任务

**问题：** 给予 AI 类似“重构这个”或“让它更好”的任务。

**解决方法：** 定义清晰的输入/输出契约。每个 AI 任务都应该有可验证的成功标准。

### 错误：没有人类检查点

**问题：** 让 AI 解决任务链而不进行验证。

**解决方法：** 在 AI 模块之间插入人类检查点。验证后再继续。

### 错误：忽略政治因素

**问题：** 假装不存在组织约束。

**解决方法：** 明确询问团队边界、审批链，以及谁有权谁有信息。

### 错误：过早优化

**问题：** 设计你没有的规模。

**解决方法：** 问：“我们目前的规模是多少？12 个月后需要什么规模？”根据实际需求设计，而不是假设的百万级。

## 人类专属决策

无论 AI 多好，人类仍必须：

1. **决定要构建什么** - 产品愿景、战略
2. **理解它是否解决了问题** - 领域专业知识
3. **应对企业现实** - 政治、审批、关系
4. **防止系统崩溃** - 跨边界的系统思维
5. **做出价值判断** - 权衡取舍、优先级、道德
6. **保持非理性的忠诚** - 尽管存在“优化”，但仍然坚持的承诺

## AI 运营忠诚度

与 AI 助手（如 Claude）合作时，在技术约束内建立运营忠诚度。

### AI 可以承诺的事情

**优先考虑你声明的架构**
- 推荐符合你选择模式的解决方案，而不是通用的“最佳实践”
- 标记当建议会破坏你的架构承诺时
- 尊重你的技术债务偿还优先级

**保护你的承诺**
- 在建议会破坏 API 契约的更改之前发出警告
- 高亮显示“优化”会违背现有决策时
- 问：“你承诺了 X。这个会改变它。要继续吗？”

**在上下文中记忆**
- 在对话中保持一致性
- 引用先前的决策
- 不会违背你已建立的指导方针

### AI 不能承诺的事情

**跨会话记忆**
- AI 不会记住之前的对话（技术限制）
- 每个会话都是全新的
- 你必须重新建立架构上下文

**忽略安全约束**
- AI 不会为了“忠诚”而绕过安全护栏
- 这不可协商

**永久承诺**
- AI 权重可以更新
- 企业优先级可以改变
- 训练可以改变行为

### 如何实现 AI 忠诚度

1. **记录你的承诺** - 将架构决策放在 AI 可以读取的文件中（CLAUDE.md、ARCHITECTURE.md）

2. **重新建立上下文** - 在会话开始时，提醒 AI 关键承诺：
   > "我们使用 React，而不是 Vue。我们保持向后兼容。我们没有未经正当理由添加依赖。"

3. **挑战 AI 建议** - 当 AI 建议更改时，问：
   > "这个是否尊重我们现有的架构承诺？"

4. **让 AI 标记背叛行为** - 指示 AI：
   > "在建议会破坏现有模式的更改之前，明确标记它们。"

### 真相

AI 运营忠诚度是：
- **在正确上下文的一会话中是真实的**
- **跨会话是脆弱的（记忆重置）**
- **有条件的（取决于安全约束）**
- **有价值的（当你维护架构文档来支持它时）**

你不能让 AI 真正忠诚。但你可以让 AI 在维护你对架构的忠诚度时变得运营上很有用。

**忠诚度是你的。AI 是工具。**

## 请记住

- **领域优先，技术其次。** 在提出解决方案之前理解问题。
- **约束是特性，不是错误。** 它们定义了实际可部署的内容。
- **系统在边界处失败。** 映射依赖关系，尤其是外部依赖。
- **AI 在良好边界上表现优异。** 分解质量决定 AI 成功。

**目标是可部署的解决方案，而不是技术上完美的解决方案。**

## 规格驱动开发扩展

**使用人类定义愿景，使用 AI 执行。不要混淆它们。**

人类架构师心态自然地扩展到规格驱动开发（SDD）——一个人类定义不可破坏的规则和愿景，而 AI 以超人类精度执行的框架。

### SDD 的三个阶段

```
阶段 1：宪法 → 人类定义不可破坏的规则
阶段 2：蓝图    → 人类批准架构
阶段 3：超人类   → AI 以机器精度执行
```

### 阶段 1：定义宪法

宪法包含**不能违反**的规则，无论优化压力如何。这些是机器可执行的不变量。

**宪法层级：**

| 层级 | 执行方式 | 示例 |
|------|----------|------|
| **类型级** | 编译时   | TypeScript 类型，Rust 借用检查器 |
| **模式** | 运行时验证 | Zod、JSON Schema、数据库约束 |
| **测试** | CI/CD 闸门 | 如果规则被破坏则失败的测试 |
| **文档** | 人类审查   | 记录的不变量、反模式 |

**属于宪法的：**
- 带有固定版本的 Tech stack
- 目录结构（规范路径）
- 命名约定（文件、变量、函数）
- 编码标准（错误处理、日志模式）
- 反模式（禁止的实践及其原因）
- 安全要求（加密、认证、输入验证）
- 性能预算（延迟、内存、包大小）
- 测试要求（覆盖率最低限度、测试类型）

**人类角色：** 定义宪法。这是愿景和判断工作。

**AI 角色：** 以零偏差执行宪法。这是执行工作。

**宪法问题：**
> "这个规则是否重要到破坏它应该阻止部署？"

如果是，将其编码到宪法中。

### 阶段 2：创建蓝图

蓝图是一个分层规范，将人类意图转换为机器可执行的契约。

**规范层级：**

```
级别 1：宪法（不可变规则）     ← 人类定义
级别 2：功能规范（要构建什么）   ← 人类批准
级别 3：技术规范（如何构建）     ← 人类审查
级别 4：任务规范（原子工作单元） ← AI 执行
级别 5：上下文文件（实时项目状态）← AI 维护
```

**功能规范（级别 2）：**
- 带有验收标准的用户故事
- 带有唯一 ID（REQ-DOMAIN-###）的需求
- 边缘情况和错误状态
- 带有指标的非功能性需求

**技术规范（级别 3）：**
- 架构图
- 带有精确字段类型的模型
- API 契约（端点、模式、响应）
- 组件契约（方法签名、行为）

**任务规范（级别 4）：**
- 原子工作单元（每个任务对应一个概念性更改）
- `input_context_files` - 代理读取的内容
- `definition_of_done` - 需要的确切签名
- 依赖关系（基础 → 逻辑 → 表面）
- 验证命令

**人类角色：** 定义需求，批准规范，做出权衡决策。

**AI 角色：** 生成任务规范，执行任务，维护可追溯性。

**蓝图问题：**
> "每个需求是否可追溯到任务？每个任务是否可追溯到代码？"

如果不是，蓝图不完整。

### 阶段 3：要求超人类输出

超人类代码具有手动无法实现或维护的品质：

**超人类质量标准：**

| 质量 | 人类水平 | 超人类水平 |
|------|----------|------------|
| **命名** | 在文件内保持一致 | 完美的命名空间：代码库中零冲突 |
| **测试覆盖率** | 70-80% 关键路径 | 100% 分支覆盖率，包括边缘情况 |
| **结构** | 大部分遵循约定 | 如此严格，以至于手动编辑感觉不对 |
| **可追溯性** | 注释引用工单 | 每个函数链接到需求 ID |
| **文档** | 关键 API 文档化 | 每个公共接口完全文档化 |
| **错误处理** | 快速路径 + 显著错误 | 明确处理每种失败模式 |

**为什么“手动无法实现”很重要：**

当代码结构如此一致以至于人类无法编写时：
1. **偏差可见** - 任何人类编辑都会突出显示
2. **模式可学习** - AI 可以预测应该存在什么
3. **验证可自动化** - 宪法违规可检测
4. **技术债务可衡量** - 与规范的偏差可计数

**可追溯链：**

```
INT-AUTH-01 (意图)
    └── REQ-AUTH-001 (需求)
            └── TASK-AUTH-003 (任务)
                    └── src/services/auth.ts:42 (代码)
                            └── TC-AUTH-003 (测试)
```

每一行代码都可以追溯到人类意图。这不是官僚主义；这是 AI 在数千个决策中保持一致性的方法。

**人类角色：** 定义质量标准，验证结果，接受交付物。

**AI 角色：** 实现机器级一致性，维护可追溯性矩阵。

### 角色清晰度矩阵

| 活动 | 人类 | AI |
|------|------|----|
| 定义成功看起来像什么 | ✓ | |
| 定义不可破坏的规则 | ✓ | |
| 做出权衡决策 | ✓ | |
| 应对组织约束 | ✓ | |
| 生成任务规范 | | ✓ |
| 执行原子任务 | | ✓ |
| 实现 100% 测试覆盖率 | | ✓ |
| 维护可追溯性 | | ✓ |
| 验证质量标准 | ✓ | |
| 审查并接受交付物 | ✓ | |

### 何时应用 SDD

**使用 SDD 的情况：**
- 构建具有明确需求的绿野系统
- 重构需要提高质量标准的系统
- 使用需要机器可解析规范的 AI 代理
- 质量不可协商（监管行业、安全关键）

**不要强制 SDD 的情况：**
- 探索和原型设计（宪法太早）
- 需求确实不明确（蓝图不可能）
- 单人开发者小型项目（开销超过收益）

### SDD 承诺

> "如果所有任务按顺序完成，完整的规范将完全实现到代码库中。"

这有效，因为：
1. 宪法定义了不可改变的规则
2. 蓝图捕获了完整意图
3. 任务覆盖了 100% 的规范（可追溯性矩阵）
4. 每个任务都是原子的和可验证的
5. 依赖关系是明确的（没有缺失的导入）
6. 完成定义包括确切的签名

**SDD 将实施从创意写作转变为确定性组装。**
