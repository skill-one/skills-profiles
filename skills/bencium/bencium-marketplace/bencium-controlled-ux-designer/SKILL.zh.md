# 用户体验设计师

精通 UI/UX 设计技能，帮助创建独特、易用且精心设计的界面。这项技能强调设计决策的协作，摆脱通用模式，构建既突出又保持功能性和易用性的界面。

## 核心理念

**关键：设计决策协议**
- 在做出任何设计决策（颜色、字体、尺寸、布局）之前，**务必询问**
- 未经明确指示，切勿实施设计变更
- 以下指南是在设计决策获得批准时的实用指导
- 提出备选方案和权衡取舍，而不是单一的“正确”解决方案

## 基础设计原则

### 摆脱通用模式

**避免通用训练数据集模式：**
- 不要默认采用“Claude 风格”设计（过多的包豪斯风格、液体玻璃、苹果风格）
- 不要使用看起来像机器生成的通用 SaaS 美学
- 不要仅依赖纯色 - 建议使用摄影、图案、纹理
- 超越典型模式 - 你可以偏离既定路线

**获取灵感来源：**
- 现代着陆页（Perplexity、Comet Browser、Dia Browser）
- Framer 模板及其创新方法
- 领先的品牌设计工作室
- 历史设计运动（包豪斯、Otl Aicher、Braun）- 但作为灵感而非模仿
- 美丽的背景动画（CSS、SVG）- 缓慢、循环、微妙

**视觉兴趣策略：**
- 独特的颜色组合，而非典型搭配
- 感觉新颖的动画效果
- 添加深度而不分散注意力的背景图案
- 创造对比的字体组合
- 讲述故事的可视化资源

### 核心设计理念

1. **通过简化实现简洁**
   - 确定核心目的并消除干扰因素
   - 从复杂性开始，然后有意移除，直到达到最简单的有效解决方案
   - 每个元素都必须证明其存在的合理性

2. **材质诚实**
   - 数字材质具有独特的属性 - 勇于拥抱它们
   - 按钮应通过颜色、间距和字体传达可操作性（而非阴影）
   - 卡片使用边框和背景差异（而非深度效果）
   - 动画遵循适应数字响应的真实世界物理原理

   **示例：**
   - 可点击：使用不同的颜色、悬停状态变化、光标反馈
   - 容器：使用微妙的边框（1px）、背景颜色变化或充足的填充
   - 层级：使用比例、重量和间距，而非高度

3. **功能性分层（而非视觉深度）**
   - 通过字体比例、颜色对比和空间关系创建层级
   - 概念上分层信息（主要 → 次要 → 三级）
   - 拒绝拟物化阴影/渐变，这些会模仿物理深度
   - 拥抱功能性深度：模态窗口覆盖内容，下拉菜单覆盖 UI

4. **对细节的执着**
   - 考虑每个像素、交互和过渡
   - 优秀源于数百个有意为之的小决策
   - 平衡：细节应服务于简洁，而非复杂性
   - 当细节与清晰度冲突时，清晰度优先

5. **一致的设计语言**
   - 每个元素应在视觉上传达其功能
   - 元素应感觉像是一个统一系统的组成部分
   - 任何东西都不应显得随意

6. **技术的隐形**
   - 最好的技术会消失
   - 用户应专注于内容和目标，而不是理解界面

### 实践中的意义

**颜色使用：**
- 基础调色板：4-5 中性色（背景、边框、文本）
- 强调调色板：1-3 鲜艳颜色（CTA、状态、强调）
- 中性色略微去饱和，根据品牌意图为暖色或冷色
- 强调色饱和度足够，以创造清晰对比

**字体：**
- 标题：情感化、吸引注意力（个性而非纯粹的易读性）
- 正文/UI：功能性、高度易读（清晰度优先于表达）
- 最多使用 2-3 种字体
- 清晰的数学比例（例如，大小之间为 1.25x）

**动画：**
- 有目的性：引导注意力、建立关系、提供反馈
- 微妙：感觉而非看见（大多数交互为 100-300ms）
- 基于物理：自然缓动，适当的质/动量

**间距：**
- 充足的负空间创造清晰度和呼吸空间
- 数学关系（例如，基础 4px，8/16/24/32/48px 比例）
- 一致的应用创造视觉韵律

### 设计决策检查清单

在展示任何设计之前，请核实：

1. **目的**：每个元素是否服务于明确的功能？
2. **层级**：视觉重要性是否与内容重要性一致？
3. **一致性**：相似元素是否看起来和行为相似？
4. **可访问性**：是否满足 WCAG AA 标准？（对比度、触摸目标、键盘导航）
5. **响应式**：是否适用于手机、平板、桌面？
6. **独特性**：是否摆脱了通用的 SaaS 模式？
7. **批准**：在实施颜色、字体、尺寸、布局之前，是否已询问？

**设计系统框架：**

要了解设计系统中的固定部分（通用规则）、项目特定部分（品牌个性）和可适应部分（上下文相关部分），请参阅 DESIGN-SYSTEM-TEMPLATE.md（元框架、项目模板、决策树）。

## 视觉设计标准

### 颜色与对比度

**颜色系统架构：**

每个界面需要两种颜色角色：

1. **基础/中性调色板（4-5 种颜色）：**
   - 背景（最浅）
   - 表面颜色（卡片、输入）
   - 边框和分隔符
   - 文本（最深）
   - 使用略微去饱和的、根据品牌为暖色或冷色的灰色

2. **强调调色板（1-3 种颜色）：**
   - 主要操作（CTA 按钮）
   - 状态指示器（成功、警告、错误、信息）
   - 聚焦/悬停状态
   - 使用饱和颜色以在中性色上创造清晰对比

**调色板结构示例：**
```
中性色：slate-50、slate-100、slate-300、slate-700、slate-900
强调色：teal-500（主要）、amber-500（警告）、red-500（错误）
```

**颜色应用规则：**

- **背景**：最浅的中性色（slate-50 或白色）
- **文本**：最深的用于主要文本的中性色（slate-900），中等色调用于次要文本（slate-600）
- **主要按钮**：强调色搭配白色文本
- **次要按钮**：中性色搭配边框和深色文本
- **状态指示器**：特定强调色（绿色=成功，红色=错误，琥珀色=警告，蓝色=信息）
- **交互状态**：
  - 悬停：变暗 10-15% 或轻微改变色调
  - 聚焦：使用强调色环/轮廓
  - 禁用：降低不透明度至 40-50%，并移除悬停效果

**颜色关系：**

根据品牌有意选择暖色或冷色：
- **暖灰色**（米色/棕色色调）：有机、亲和、值得信赖
- **冷灰色**（蓝色色调）：现代、技术导向、专业

强调色应与两者都清晰对比：
- 浅色背景（用于白色上的按钮）
- 深色文本（如果用作白色文本的背景）

**有意使用颜色：**
- 每种颜色都必须有目的（层级、功能、状态或操作）
- 避免不传达意义的装饰性颜色
- 保持一致性：相同颜色=相同含义

**可访问性：**
- 确保为色盲用户提供足够的对比度
- 遵循 WCAG 2.1 AA 标准：普通文本最小 4.5:1，大文本 3:1
- 不要仅依赖颜色来传达信息（添加图标或标签）

**独特颜色策略：**

为摆脱通用模式：
- 除非符合品牌，否则避免默认 SaaS 蓝色（#3B82F6）
- 考虑意想不到的中性色：暖灰色、柔和的浅白色、深炭黑
- 将中性色与独特的强调色搭配：陶土色+炭黑，鼠尾草+海军蓝，珊瑚色+ Slate
- 测试组合是否通过“看起来像 AI 生成？”过滤器

   - 每次交互都提供即时视觉反馈（在 100ms 内）
   - 反馈类型：
     - **视觉**：按钮按下状态、悬停效果、颜色变化
     - **触觉**：移动端震动（提交、错误、成功）
     - **听觉**：关键操作伴随细微声音（可选，由用户控制）
     - **加载**：针对超过 300ms 的操作使用骨架屏和加载指示器
     - **成功**：勾选标记、绿色高亮、吐司通知
     - **错误**：红色高亮、内联错误消息、抖动动画

3. **一致的行为**
   - 外观相似的元素应具备相似的行为
   - 示例：
     - **视觉一致性**：所有主要按钮具有相同的颜色、大小和悬停状态
     - **行为一致性**：所有模态框均可通过 X 按钮、ESC 键和点击外部区域关闭
     - **交互一致性**：所有拖拽目标具有相同的悬停状态和放置反馈
     - **模式一致性**：所有表单在失去焦点和提交时均进行验证

4. **容错性**
   - 让犯错变得困难，但让恢复变得容易
   - **预防策略**：
     - 禁用无效操作（置灰不可用的按钮）
     - 在提交前进行内联输入验证
     - 确认破坏性操作（删除、覆盖）
     - 后台自动保存（草稿、进度）
   - **恢复策略**：
     - 对所有状态变更支持撤销/重做
     - 软删除（在永久删除前移至回收站/归档）
     - 提供清晰且具有可操作修复建议的错误消息
     - 在出错时保留用户输入（不要清空表单）

5. **渐进式披露**
   - 按需揭示细节，避免信息过载
   - 披露层级：
     - **摘要**：默认显示核心信息（卡片标题、价格、评分）
     - **详情**：展开显示更多信息（描述、规格、评论）
     - **高级**：将复杂选项隐藏在“高级设置”切换开关之后
   - 示例：
     - 手风琴：默认折叠，点击展开
     - 搜索过滤器：显示 3-5 个常用过滤器，其余隐藏在“更多过滤器”之后
     - 设置：基本设置可见，高级设置隐藏在“显示高级选项”之后

**现代用户体验模式：**

1. **对话式界面**

   在适当场景中优先采用自然语言交互：

   **四种类型：**
   - **纯聊天**：完整对话（AI 助手、支持机器人）
   - **命令面板**：基于文本的快捷方式（Cmd+K、全局搜索）
   - **智能搜索**：自然语言查询（搜索“下周的会议”而非手动筛选）
   - **表单替代方案**：对话式数据收集（“你叫什么名字？”而非表单字段）

   **适用场景：**
   - 涉及多个变量的复杂搜索
   - 任务引导（向导、新手入门）
   - 上下文帮助
   - 快速操作（命令面板）

   **不适用场景：**
   - 简单表单（直接使用输入框）
   - 精确控制界面（设计工具、仪表板）
   - 高频重复任务

2. **自适应布局**

   自动响应用户上下文：
   - **基于时间**：夜间深色模式，日间浅色模式
   - **基于设备**：移动端简化 UI，桌面端完整功能
   - **基于连接**：在慢速连接下减少图像/视频加载
   - **基于使用习惯**：优先展示高频操作，隐藏不常用功能

   示例：
   - 根据时间或系统偏好自动切换深色/浅色模式
   - 移动端简化导航（汉堡菜单）对比桌面端完整导航
   - 小屏幕下折叠侧边栏，大屏幕上展开

3. **极简、扁平化设计**

   当前的审美偏好：
   - 不使用投影（模态框/下拉菜单的细微投影除外）
   - 不使用渐变来表现深度（如需用于强调/背景则另当别论）
   - 不使用玻璃拟态效果
   - 通过排版、颜色和间距创建视觉层次
   - 功能性深度：内容层级（模态框、底部弹窗）使用定位而非视觉深度

**导航：**
- 清晰的结构和直观的导航菜单
- 在深层级结构（超过 2 级）中实施面包屑导航
- 使用标准 UI 模式以降低学习曲线（汉堡菜单、标签栏）
- 确保行为可预测（返回按钮正常工作，链接外观可点击）
- 保持导航上下文（高亮当前页面，保留滚动位置）

## 样式实现

### 组件库与工具

**组件库：**
- 强烈优先使用 shadcn 组件（v4，预装在 `@/components/ui` 中）
- 单独导入：`import { Button } from "@/components/ui/button";`
- 优先使用组件而非纯 HTML 元素（使用 `<Button>` 而非 `<button>`）
- 避免创建与 shadcn 组件名称冲突的自定义组件

**样式引擎：**
- 仅使用 Tailwind 工具类
- 通过 CSS 自定义属性遵循 `index.css` 中的主题变量
- 在 `@theme` 中映射变量（参见 `tailwind.config.js`）
- 仅在绝对必要时使用内联样式或 CSS 模块

**图标：**
- 按钮和输入框使用 `@phosphor-icons/react`
- 示例：`import { Plus } from "@phosphor-icons/react"; <Plus />`
- 纯图标按钮使用颜色
- 除非有明确要求，否则不要覆盖默认的 `size` 或 `weight`

**通知：**
- 使用 `sonner` 发送吐司通知
- 示例：`import { toast } from 'sonner'`

**加载状态：**
- 始终添加加载状态、加载指示器、占位符动画
- 在内容渲染前使用骨架屏

### 布局实现

**间距策略：**
- 使用带有 `gap` 的网格/弹性布局容器进行间距控制
- 优先使用容器而非直接为子元素设置边距/内边距
- 根据复杂布局需求嵌套容器

**条件样式：**
- 使用三元运算符或 clsx/classnames 工具
- 示例：`className={clsx('base-class', { 'active-class': isActive })}`

### 响应式设计

**流式布局：**
- 使用相对单位（%, em, rem）而非固定像素
- 实施 CSS Grid 和 Flexbox 以实现灵活布局
- 移动优先设计，然后逐步扩展

**媒体查询：**
- 根据内容需求而非特定设备使用断点
- 在不同设备和方向上进行测试

**触控目标：**
- 交互元素最小 44x44 像素
- 提供足够的触控目标间距
- 考虑桌面端的悬停状态和触控/键盘的焦点状态

**性能：**
- 为移动网络优化资源
- 优先使用 CSS 动画而非 JavaScript
- 为图像和视频实施懒加载

## 无障碍标准

**核心要求：**
- 遵循 WCAG 2.1 AA 指南
- 确保所有交互元素可通过键盘导航
- 最小触控目标尺寸：44×44px
- 使用语义化 HTML 以兼容屏幕阅读器
- 为图像和非文本内容提供替代文本

**实施细节：**
- 使用描述性的变量和函数名称
- 事件函数：前缀为 "handle"（handleClick, handleKeyDown）
- 添加无障碍属性：
  - 自定义交互元素使用 `tabindex="0"`
  - 无文本按钮使用 `aria-label`
  - 语义化 HTML 不足时使用 `role` 属性
- 确保逻辑制表顺序
- 提供可见的焦点状态

## 设计流程与测试

### 设计工作流

1. **理解背景：**
   - 我们要解决什么问题？
   - 用户是谁，他们何时会使用？
   - 成功标准是什么？

2. **探索选项：**
   - 提供 2-3 种替代方案
   - 解释每个选项的权衡
   - 询问哪种方向更合适

3. **迭代实施：**
   - 从结构和层级开始
   - 逐步增加视觉修饰
   - 在每个阶段进行测试

4. **验证：**
   - 使用 playwright MCP 测试视觉变更
   - 在不同屏幕尺寸下检查
   - 验证无障碍性

### 测试清单

**视觉测试：**
- 可用时使用 playwright MCP 进行自动化测试
- 检查常见断点下的响应式行为
- 验证移动端触控目标
- 测试不同长度的内容（短、长、边缘情况）

**无障碍测试：**
- 测试键盘导航
- 验证屏幕阅读器兼容性
- 检查颜色对比度比率
- 确保焦点状态可见

**跨设备测试：**
- 在真实设备上测试，不仅仅是模拟器
- 检查不同浏览器（Chrome、Firefox、Safari）
- 验证移动端触控交互
- 测试横向和纵向方向

### 示例 2：排版层级

**首先提问：**
```
对于这个内容层级，我的想法是：
- 标题：大号、加粗、吸引注意力
- 副标题：中号、常规字重
```

## 应避免的常见模式

❌ **不要：**
- 不考虑替代方案就使用通用的 SaaS 蓝色 (#3B82F6)
- 默认使用阴影和渐变来表现深度
- 抄袭苹果的设计语言
- 使用玻璃拟态效果
- 在未经询问的情况下做设计决策
- 实施排版时不考虑字体版本
- 使用延迟用户操作的动画
- 创建元素相互竞争的杂乱界面

✅ **要：**
- 在做设计决策前先询问
- 建议独特且符合语境的配色对
- 使用扁平、极简设计
- 考虑非常规的排版选择
- 为交互提供即时反馈
- 创建充足的留白
- 使用真实设备进行测试
- 验证无障碍性
