# 贵州社交卡技能

为小红书/Rednote、微信公众号、文章封面和平台缩略图创建精美的社交卡套餐。

此技能是自包含的。它借鉴了贵州PPT风格系统的视觉原则，但必须不得编辑原始PPT技能、其模板或其引用。如果原始PPT技能可用，您可以仅作参考阅读。

生成的工作成果必须存在于任务文件夹中，而不是技能根目录。默认使用此仓库内的`local-tests/<slug>/`，或使用用户请求的明确输出文件夹。不要创建根级任务文件夹，如`social-card-*`、`livephoto-*`、`wechat-*`、`output/`，或在`SKILL.md`旁边随意放置渲染后的资源。

## 要产出什么

使用此技能：

- 社交卡/轮播图集：封面加内容页，特别是小红书/Rednote 3:4。
- 短Live Photo动态卡，当用户要求Live Photo/实况照片并提供视频证据或屏幕录制时。
- 材质优先的Live Photo拼图布局，当用户拥有高质量视频资产并希望创建单视频、两网格、三网格或四网格动态卡且几乎不加或少量添加文字时。
- 三联Live Photo拼贴，当用户有三个短视频、三个结果、三个视角或应保持在单个图像卡单元内的高信息比较时。
- Live Photo长视频摄入：诊断是否需要剪辑、加速、拆分为三联拼贴，或在渲染前请求用户指定特定时间范围。
- 微信公众号封面对：一个`21:9`主封面加一个`1:1`方形封面，在同一个HTML中组合在一起以便视觉检查。
- 重 screenshot 的产品帖子、文章封面、教程轮播、户外/生活方式笔记、AI/产品更新说明。
- 需要贵州风格瑞士或编辑杂志布局的社交图像。

不要使用此技能：

- 全部幻灯片或水平PPT网站。使用PPT技能。
- 长视频生成。使用视频技能。此技能仅支持短布局约束的Live Photo卡，用视频替换静态图像位置。
- 纯图像编辑，无布局或文章提取要求。

### Rednote类别能力（能力圆圈）

11个最常见的Rednote（小红书）类别分为三类。有关按菜谱分路的详细信息，请参阅`references/category-cookbook.md`。

**端到端强**（文本、结构和图像故事都在范围内）：

- 旅行 (Travel), 职场 (Workplace), 推荐 (Recommended, 指定子类型后)。

**强文本和结构；图像需要来自用户或来源库**：

- 游戏 (Game), 影视 (Film/TV), 美食 食谱方向 (Food — 仅食谱), 彩妆 教程方向 (Makeup — 仅教程), 健身 (Fitness), 家居 (Home), 穿搭 精选方向 (Outfit — 模块/短文)。

**超出范围——诚实拒绝，而不是承诺结果**：

- 美食 菜品大片摆盘 (food-photography showcase).
- 穿搭 日常 OOTD 全身 (日常 OOTD 全身照片；我们无法生成或模拟).
- 情感 梦核 / 氛围感装饰风 (dreamcore / 美学风格——与编辑和瑞士风格冲突).
- Y2K / 千禧辣妹 / 哥特萝莉 / kawaii装饰美学.
- 纯摄影展示帖子，图像是整个交付成果。

当请求属于第三类时，在摄入时命名我们无法做的事情——不要无声地调整缺少用户意图的布局。

## 核心原则

表达优先。目标不是将文本塞进海报；而是将源转换为清晰的可视化论点。

对于每一页，决定：

- 观众应该一眼就能理解什么？
- 哪些证据、screenshot或图像支持它？
- 哪些文字必须大号，哪些可以成为标题或元数据？
- 哪些可以删除，因为它们属于帖子正文，而不是图像？

## 工作流程

### 1. 摄入

仅收集会改变输出的缺失信息：

- 目标平台和比例。
- 源文本、字幕、文章或标题。
- **Rednote类别**——如果用户指定了11种常见类型之一（旅行 / 职场 / 游戏 / 影视 / 美食 / 彩妆 / 穿搭 / 家居 / 健身 / 情感 / 推荐），通过`references/category-cookbook.md`路由以找到正确的菜谱并确认请求在能力圆圈内（见“Rednote类别能力”）。如果请求落在超出范围桶中，在设计前向用户**揭示**，不要无声地调整。
- 提供的图像/screenshot及其应出现的位置。**对于新闻 / 教程 / 数据 / 评论内容，主动提示提供screenshot或照片**——它们是证据层。没有真实实物的海报往往读起来像填充。
- 提供的视频资产，如果用户要求Live Photo。将用户提供的视频视为正常路径；网络来源免费视频仅用于演示/促销案例或当用户明确要求来源材料时。确认目标平台，因为持续时间不同：小红书支持`5s`；微信公众号Live Photo应保持在`3s`，必须从iPhone上传。在剪辑前，阅读`references/live-photo-production.md`并将请求分类为单Live Photo、三联拼贴或长视频摄入。如果源太长或包含多个可用时刻，先进行低成本诊断，然后问一次是否剪辑、加速、拆分为多个井或使用用户指定的时间范围。如果源比目标持续时间短，问是否提供更长的片段、接受更短的Live Photo或明确允许保持/减速。如果焦点不明确，建议可能的裁剪/放大选项，但在执行前让用户决定。
- **如果用户仅提供文本（没有任何图像），在设计前问一次：**

  ```
  这篇我需要1-2张图。三种走法：
  A. 你自己有照片 / 截图，传给我（推荐——最不"AI感"）
  B. 我去Pexels / Unsplash / Flickr帮你找
  C. 用AI生成
  ```

  一行推荐A——你自己的照片能让海报看起来不像是AI生成的。接受用户选择的任何选项（包括“都行你看着办”）并继续。**不要重新提示，不要在多轮中持续推动A。**这个问题是一次性的。
- 风格偏好（如果指定）：瑞士风格、杂志/编辑、科技、户外等。
- 硬约束：标题文本、1:1封面无图像、必须包含硬件照片、保持screenshot可读等。

如果用户已经提供了足够的上下文，请进行合理的假设。

如果内容涉及当前产品发布、政策、价格、声明或新闻，请通过浏览验证不稳定的事实，并在最终响应中引用来源。

### 2. 提取故事

在设计之前，将源转换为页面计划。

对于Rednote：

- 第1页是封面钩子。
- 第2-N页每页只承载一个想法。
- 大多数帖子使用5-9页。当较低区域变空时压缩或合并页面。
- 保持帖子正文以供细微差别；图像应承载钩子、比较、清单和清晰的要点。

对于微信公众号：

- 始终生成成对系统：`21:9`主封面和`1:1`方形封面。
- 在同一个HTML文件中构建两个封面，并添加组合预览部分，以便可以一起检查它们的视觉关系。
- `21:9`保持完整或接近完整的标题、副标题和一个强烈的视觉关系。
- `1:1`使用从长标题简化而来的短标题：居中大号字体，默认无图像，无拥挤的副标题。

### 3. 选择风格模式

每个套餐选择一个模式。**两种系统不是绑定到特定内容类型**——变化的是视觉立场，而不是可以谈论的话题。职场短文可以是编辑；旅行日记可以是瑞士。根据你想要的感觉选择，而不是通过类别查找。

**编辑杂志 x E-ink**带来：

- 宋体/Songti显示 + 安静的无衬线正文，纸+墨调色板。
- 氛围层（纸张颗粒/墨水洗/WebGL画布）覆盖温暖的纸张基础。
- 记账行、批注、引文、大照片井——杂志特写感。
- 当你希望页面感觉缓慢、深思熟虑、手工设置时最佳。

**瑞士国际**带来：

- Inter / Helvetica感觉，大尺寸时非常轻的显示，小尺寸时单色标签。
- 严格的左对齐网格、发丝规则、一个高饱和度强调。
- 卡片填充矩阵、KPI塔、水平条图表、编号声明——系统/数据感。
- 当你希望页面感觉工程化、量化、果断时最佳。

如果两种感觉对某个内容都可行，问题就变成了编辑意图：“这是一个特写故事还是发布说明？”这决定了模式，而不是主题本身。

除非用户明确要求混合，否则不要在同一图像集中混合这两种视觉系统。

然后选择一个主题：

- 编辑杂志 x E-ink使用6种杂志调色板之一：墨水经典、靛蓝瓷、森林墨水、牛皮纸、沙丘或午夜墨水（唯一深色变体；保留用于游戏关键艺术/夜间摄影/电影封面）。
- 瑞士国际使用4种强调调色板：IKB蓝色、柠檬黄色、柠檬绿色或安全橙色。

阅读`references/theme-presets.md`以获取精确的CSS标记。除非用户有严格的品牌要求，否则不要随意发明颜色。

### 4. 规划页面

创建简洁的内部计划：

```text
Page 01 / cover / hook / image source / layout intent
Page 02 / point / key copy / visual evidence / layout intent
...
```

当用户要求批准时，在渲染前显示此计划。否则在内部使用并继续。

使用`references/layout-recipes.md`选择页面结构。避免使每一页都是一个重复的标题+卡片布局。

对于3:4图像，在编码前检查`references/portrait-fill.md`。一个短表格或记账必须扩展为完整的肖像构图，带有一个引文列、图像证据、批注、较大的行或背景英雄区域。

面向观众的文案必须描述用户实际场景，而不是生产方法。内部术语，如`3s`、`5s`、`Live Photo`、`triple collage`、`information budget`、`long-video intake`、`speed-up`、`highlight detection`、`one action point`或`layout template`，可以指导规划、文件名、QA笔记和交付摘要，但它们必须不会成为H1、钩子或主正文副本，除非用户明确制作了关于这些概念的说明性帖子。在渲染前，像真实观众一样阅读每个可见标题一次：如果听起来像任务要求，请用场景特定副本替换它。

不要添加非模板装饰只是为了满足自动化的密度警告。额外的尺子、侧边栏、伪时间轴、装饰性标签或发明徽章必须来自现有的布局菜谱或用户请求。如果出现密度警告，通过选择更好的菜谱、调整真实内容或接受带有视觉理由的建议警告来修复它；不要在卡上放置无意义的UI。

对于Live Photo卡，首先像普通社交卡一样规划它们，然后决定运动角色：一个行动点、一个小过程、一个前后变化、三个平行结果或氛围/证据。唯一的结构变化是一个或多个图像井变成视频井。保持相同的比例、裁剪、安全区域、排版和风格模式规则；将静态图像裁剪逻辑应用于视频流。第一帧必须通过与静态图像相同的检查：没有过度裁剪，关键UI/内容保持可读，并且卡仍然遵循选择的布局菜谱。在渲染前阅读`references/live-photo-production.md`。

对于材质优先的Live Photo拼图卡，让视频资产主导。使用少量或无副本：单视频封面只需要一个简短标题，两网格/三网格/四网格版本通常不应添加文字。当单视频封面在素材上方添加文字时，使用M16 Image-Led Cover / 文本在图像上的规则：主体映射优先，安全安静区域，编辑Serif/Songti标题常规中等重量，纸奶油文本，并且没有默认的全画布蒙版。不要发明额外的开头、元数据、发丝、标签、尺子、徽章、副标题或解释性生产术语，只是为了让叠加层感觉设计。如果只有一个标题可用，让排版承载布局：短语感知换行、约束大小、追踪、对齐和位置。将源嵌入文本视为部分素材；除非用户要求，否则不要添加新文本。

### 4.5. 复制种子模板

不要从零开始编写HTML。根据步骤3选择的风格模式选择一个种子模板：

- Editorial Magazine × E-ink → 将`assets/template-editorial-card.html`复制到任务文件夹作为`index.html`。
- Swiss International → 将`assets/template-swiss-card.html`复制到任务文件夹作为`index.html`。

种子已经接好了：字体加载、主题标记、所有三种海报尺寸（`.poster.xhs` / `.poster.square` / `.poster.wide`）、对齐预览框架、颗粒/背景层以及布局菜谱引用的所有类定义。

在`<html>`元素上设置主题/强调：

- Editorial: `<html data-theme="ink-classic | indigo-porcelain | forest-ink | kraft-paper | dune | midnight-ink">`。
- Swiss: `<html data-accent="ikb | lemon-yellow | lemon-green | safety-orange">`。

替换掉 `<!-- POSTERS_HERE -->` 后的单个占位符海报，改为每个页面使用一个 `<section class="poster ...">` 块，每个块都承载所选布局配方（编辑型使用 M01-M16，瑞士型使用 S01-S12）的 HTML 骨架。切勿加载错误模板的类系统：编辑型配方假设衬线显示 + ledger/marginalia/pipeline-v；瑞士型配方假设 Inter + card-fills + matrix/h-bar/kpi-tower。混合它们会无声地破坏布局。

### 5. 构建 和 渲染

默认实现模式：

- 默认在 `local-tests/<slug>/` 下创建任务文件夹，或在使用者请求的输出文件夹内。切勿将生成的任务文件夹、渲染的图像、MOV 文件、`.pvt` 包或下载的源代码放在技能根目录下与 `SKILL.md` 并置。
- 将源图像放在 `assets/` 中。
- 从步骤 4.5 复制的种子模板开始，而不是空白文件。优先逐页更改 `<!-- POSTERS_HERE -->` 区域。如果任务需要自定义布局 CSS，在复制的文件中添加一个命名清晰的任务作用域块，并保持语义默认值重置（`figure { margin:0; }`，无浏览器默认间距意外）。
- 使用 Playwright 或浏览器截图工具导出每个 `.poster` 或 `.cover` 节点。
- 将渲染的图像保存在 `output/` 中。
- 验证尺寸并检查渲染的 PNG。
- 保持 `node validate-social-deck.mjs <task-dir>` 可用以进行自动检查。它检查溢出（R1）、页脚碰撞（R2）、瑞士粗体显示（R3）、最小字体大小（R4）、4 带密度（R5）、`.h-xl` 行首（R6）、浏览器默认图形容器边距漂移（R7）、视觉边界/底部空白（R8）和标题到内容间隙（R9）。任何失败都返回退出码 1 — 在请求自动检查时修复。警告是建议性的但需阅读。

Live Photo 分支：

- 在渲染前决定信息预算：`3s` 适合一个行动点；`5s` 适合一个小型流程；三重拼贴适合三个并行片段但不适合复杂故事；长视频需要在编辑前进行诊断。
- 对于长源，避免声称精确的自动高亮检测。探测持续时间/分辨率，制作稀疏接触表，并在裁剪、加速、分割/三重拼贴或请求用户指定时间范围之间进行选择。
- 从每个视频中提取第一帧，将其放置在最终静态卡片布局中，并在制作 `.pvt` 之前显示/检查预览。这可以捕捉到裁剪和层级问题，且具有更低的代币和渲染成本。
- 在平台持续时间渲染配对的 MOV：`5s` 适用于小红书，`3s` 适用于微信公众号。
- 从可读的代表性帧中提取关键的 JPG。
- 使用 `makelive` 将 `JPG + MOV` 打包成 `.pvt`；通过 AirDrop 将 `.pvt` 作为一项内容发送到 iPhone 进行测试。
- 验证尺寸、持续时间、帧数、包内容和运动质量。优先使用接触表帧条进行视觉检查，以便只有最终拼贴图像需要人工/模型检查。使用 `references/live-photo-production.md` 获取精确命令和失败模式检查。

不要在图像中放置可见的说明、键盘快捷键或使用说明。

对于编辑型杂志 x 电子墨水，使用分层背景系统。优先使用微妙的 WebGL 墨水流画画布或冻结的程序性画布加上纸张颗粒。阅读 `references/background-systems.md`；不要依赖平坦的米色背景，也不要添加全页网格/点背景。

### 6. 图像 和 截图 处理

当用户提供截图时：

- 除非用户要求重新设计，否则保留截图内容。
- 优先程序化框架：目标比例画布、安全填充、干净背景、可读截图。
- 不要拉伸截图。
- 如果截图清晰度很重要，扩大截图区域并减少附近文本。

#### 图像上文字组合

每当海报在照片上放置文字（全出血封面、大图像区域、生成图像叠加）时，遵循 `references/image-overlay.md`：

- **先选择，仅在需要时染色。** 覆盖 ≥60% 画布的照片必须首先通过 `image-overlay.md` 中的静音区和光线测试。先无蒙版组合；如果缩略图检查失败，仅在标题区域周围添加局部、图像色调的染色。不要默认使用全画布衰减。
- **主体映射是强制的。** 在放置标题之前，使用 Read 工具读取图像，用平实语言描述主体的脸/焦点特征位于何处，并将主体映射记录为 HTML 注释，放在英雄块旁边。仅在记录的安全区域内放置文字。
- **裁剪纪律 — 在每个照片上内联设置 `object-position`。** 模板默认（`center 50%`）是后备，不是推荐。对于每个 `<img>`，根据主体位置决定并内联写入：例如 `style="object-position:center 62%"` 用于中身主体，`center 30%` 用于天空为主的风景带地平线主体，`center 70%` 用于前景设备。参见 `references/components.md` 中的表格以获取范围，并参考 `image-overlay.md` 中的面部照片具体细节。跳过此步骤会在高宽比（`r-3x4`，`r-21x9`）上无声地裁剪主体出画面。
- **缩略图测试。** 将渲染的 PNG 缩放到 360 px 宽，确认标题仍然可读。如果标题与照片冲突，移动标题、交换照片或添加局部图像色调的染色；如果照片看起来死气沉沉，染色太重或照片不适合图像上文字。

编辑型深色封面（例如关键艺术上的游戏杂志）和带有英雄照片的瑞士封面都需要这些检查。跳过它们是已知的失败模式（参见 `style-system.md` 反模式 D）。

当用户没有图像时：

- 此分支仅在步骤 1 的“三选一”门控落在 B（网络来源）或 C（AI 生成）时运行。切勿无声地落入 B 或 C — 用户选择了一个。
- 对于 C（AI 生成）：仅在它们能增加真实价值时使用生成位图，通常是 1-2 页。生成与页面视觉角色匹配的图像，而不是通用装饰。保持生成图像免受嵌入标题、页码、标志或假 UI 标签的影响，除非明确需要。
- 对于 B（网络来源）：参见下方的“网络来源图像”部分。

#### 网络来源图像（用户无截图/照片时的后备）

当用户没有截图/照片且生成位图不适合页面的角色（例如编辑型氛围镜头、户外/生活方式背景、游戏封面艺术、真实世界产品拍摄），则从网络获取，而不是让页面显得单薄。

政策：**先抓取，后披露，让用户决定归属。** 不要预先过滤来源，根据猜测的许可证 — 用户是最终组合的权利人，决定什么可以接受。

推荐来源，按优先顺序排列。**以下五个都是免费层级的库，无需许可证费用**；我们不从付费图库（视觉中国 / Getty / 站酷海洛等）获取。

1. **Unsplash** — `https://unsplash.com/s/photos/<keyword>`。适合户外 / 生活方式 / 氛围背景。英文关键词效果最佳。许可证是宽泛的，但需逐个案例验证。
2. **Pexels** — `https://www.pexels.com/search/<keyword>/` 或 `https://www.pexels.com/zh-cn/search/<keyword>/`。**原生支持中文关键词搜索** — 填补 Unsplash 在国内场景（中文街景 / 国风物品 / 本地名）的空白。当主题是中国特定或关键词是中文时，首先使用此选项。根据 Pexels 许可证免费使用。
3. **Flickr CC 许可池** — `https://www.flickr.com/search/?text=<keyword>&license=2%2C3%2C4%2C5%2C6%2C9`。许可证过滤器（`license=2,3,4,5,6,9`）限制为创意共享照片。填补“纪实真实性”空白：街头摄影、场景中的人物、真实室内、非风格化场景，这些是 Unsplash/Pexels 缺失的。如果用户选择披露，始终保留 CC 归属。
4. **Wallhaven** — `https://wallhaven.cc/search?q=<keyword>`。适合游戏 / 动画 / 壁纸主题。内容是用户上传的，权利未验证。
5. **直接网络搜索** — 当需要特定主题时（产品渲染、游戏静止帧、历史照片）。使用 WebFetch / WebSearch 找到候选 URL。

编辑型选择顺序：**Pexels（如果关键词是中文 / 中国特定）→ Unsplash → Flickr CC（如果需要真实感）→ 直接搜索**。瑞士模式很少需要这些 — 产品渲染、UI 截图和关键镜头式图像应由用户提供或 AI 生成，而不是图库。

如何获取：

- 使用 WebFetch 或 `curl` 将图像下载到任务文件夹的 `assets/` 目录。
- 按用途命名文件，而不是哈希：`assets/hero-mountain.jpg`，`assets/ui-pulse-card.png`。
- 在图像旁边的 `assets/SOURCES.md` 文件中记录源 URL（每行一个文件：`hero-mountain.jpg ← <url>`）。即使用户在最终图像中拒绝归属，也始终这样做 — 它保留了人类作者的来源证明。

获取后，在最终确定设计之前向用户展示来源：

```
我从 <site> 取了这些图：
- assets/hero-mountain.jpg — <url>
- assets/ui-pulse-card.png — <url>

⚠️ 版权未经核实。请你判断是否可用。
是否需要在图文中标注来源？
- 要：我把 "Photo · <site> · @<author>" 加到对应页脚 / 角标。
- 不要：原样使用,不加注释。
```

如果用户选择“标注” — 添加一个小 `mono` 标题（瑞士：`.t-meta` 18-20px 在角落；编辑型：`.label` 在图像区域旁边）。切勿将标题挤占布局的焦点区域。

如果用户选择“不标注” — 默默进行。来源仍然存在于 `assets/SOURCES.md` 中，供用户记录。

如果图像是复合图像中的多个元素之一（例如九个照片中的其中一个），用户可以合理地跳过归属。不要强制一个破坏布局的信用标签。

### 7. 交付

**先给用户看，再按请求验证。** 每次渲染后自动运行验证器太耗时，会延迟用户看到结果。默认流程：

1. 渲染完成后，立即显示用户渲染的图像（绝对路径）和一句总结构建了什么。
2. 提问一个：**"先你自己看，还是我先自动核查一遍？"** （你想先查看，还是我应该先自动检查？）
3. 如果用户说“我自己看” / “先给我” / “no need” — 停在这里，让他们检查，并回应他们提出的问题。
4. 如果用户说“你查吧” / “auto-check” / “yes” — 只有那时运行 `node validate-social-deck.mjs <task-dir>`，修复任何失败，并在最终交付前重新渲染。提及密度/首字母警告。

切勿在向用户展示之前无声地运行验证器 — 它每轮耗时数分钟，用户通常能更快发现问题。

最终响应（在用户查看或请求自动检查后）应包括：

- 输出文件夹路径。
- 渲染的图像显示为绝对路径（在有用时）。
- 关于尺寸和验证的简短说明（或“尚未验证，等待您的查看”）。
- 对于从网络获取的任何图像：源 URL + 网站以及用户做出的归属决定。
- 对于 Live Photo：`.pvt` 包路径、调试 `JPG + MOV` 对、目标平台持续时间、验证摘要。
- 对于 Live Photo 发布：提醒用户两件事：平台限制（`5s` 小红书，`3s` 微信公众号）和发布路径（将 `.pvt` 包作为一项内容通过 AirDrop 发送到 iPhone，然后从匹配的移动应用路径发布；桌面/网页上传路径通常无法识别 `.pvt` 为可发布的 Live Photo）。
- 如果用户无法使用 iPhone/AirDrop 发布路径（例如桌面仅工作流程、Android 或不支持 Live Photo 的平台），提供降级交付：从相同的 MOV 源导出短循环 GIF 或无声 MP4 片段。GIF/MP4 保留运动证据但失去了 Live Photo 点击播放体验。在切换到此后备之前与用户确认。
- 任何未解决的风险，例如源图像分辨率低。

## 不可协商项

- 切勿编辑原始贵州 PPT 技能或从其他地方复制的任何上游技能。
- 切勿在技能根目录中创建生成工作。所有任务工件默认必须在 `local-tests/<slug>/` 下，或在使用者请求的输出文件夹下。禁止根级别的生成文件夹，如 `social-card-*`，`livephoto-*`，`wechat-*`，以及松散的输出资产。
- 不要创建随机的装饰性 SVG 椭圆、块、雨滴、贴纸或无意义的圆圈。
- 不要使用嵌套卡片或通用 SaaS 卡片布局作为默认。
- 不要让文本溢出、触碰边缘或与页脚带碰撞。使用 `margin-top: auto` 在 flex 列内固定 `.foot`，切勿使用 `position: absolute` 覆盖增长内容。
- 当内容溢出时，在编辑前测量溢出量。小溢出应得到小修复：`1-40px` 表示推挤/收紧，`40-90px` 表示局部紧凑，`90-160px` 表示轻微标题或段落压缩，只有 `160px+` 才应触发配方更改或内容删除。修复后，检查 R8 底部空白，以防止页面从溢出跳到巨大的空下带。
- 不要让标题触碰下一个内容块。主显示标题通常应保持至少 `28px` 以下；本地标题应保持至少 `16px`。在依赖视觉检查之前使用验证器 R9。
- 不要让文本在移动设备上变得太小而无法阅读。
- 不要在瑞士中使用内联 `font-size` + `font-weight` 在显示标题上。使用输入的类（`.h-hero` / `.h-statement` / `.h-xl` / `.num-mega`）。80-120px 标题在 700-900 权重下不是瑞士的；“越大越轻”是一个硬规则。
- 不要交付带有平坦纸张背景、每行单调标签和没有氛围层的编辑型海报。运行 `references/style-system.md` 中的编辑型身份测试 — 单独的衬线标题并不能使海报成为编辑型。
- 不要伪造数据、发布细节或百分比。
- 不要裁剪脸、关键 UI 文本或硬件/产品细节，除非用户明确接受。
- 不要将视频卡片变成假静态序列而不说明。如果源比目标持续时间短，请求更长的源，使用较短的平台安全持续时间，或明确记录任何保持/减速。
- 不要跳过 Live Photo 的第一帧预览。视频是一个带运动的图像区域；其第一帧必须在渲染 MOV 之前满足静态 3:4 布局和裁剪规则。
- 不要让结果视频在浅裁剪中滚动过章节边界；这会创建“重叠视频”失败。检查接触表并选择一个稳定的时间窗口，然后再打包。
- 不要猜测用户在放大/裁剪视频以提高可读性时的视觉优先级。提供裁剪/放大的权衡，并在用户确认后应用它，除非请求已经使焦点区域明确。
- 不要盲目地将 21:9 封面裁剪成 1:1。单独为每个比例组合。
- **3:4 卡必须吃满画布**。内容（文本 + 图像 + 数据）必须覆盖 ≥75% 画布高度。任何 >15% 画布高度的纯空白带都需要“留白理由”：(a) 英雄图像自带呼吸、(b) 单句宣言式英雄 statement、(c) 段落顶/底 leading & trailing whitespace（前后总和 ≤15%）。**禁止用 `<div style="flex: 1"></div>` 上下夹击把内容塞到中段**——杂志页留白逻辑不适用于社交卡（杂志靠对开页吸收留白，社交卡逐张独立刷，欠填看着像 PPT 漏排）。按配方最小密度见 `references/layout-recipes.md` 每条 recipe 的「Minimum density」段。渲染后必须跑 `qa-checklist.md` 的 4 横带密度检查。
