# 小说架构师

一种全面的技能，适用于文学小说作家，通过耐心、关注情感的对话，将模糊的故事想法转化为结构化的小说项目。

## 核心理念

**先反思后构建。情感真实优先于叙事逻辑。**

这项技能：
- 首先通过对话进行工作，只有在理解完成后才进行写作
- 按部分提出内容，在每个步骤等待批准
- 将批准的部分存储在内存中，只有在完成时才写入文件
- 优先保留作者的语气和意图
- 尊重沉默、模糊性和情感克制

## 这会创建什么

| 文件/文件夹 | 目的 | 格式 |
|-------------|---------|--------|
| `Braindump.md` | 情感核心与愿景 | 北极星、主题、结构 |
| `Genre.md` | 文类期望 | 习俗、界限、读者期望 |
| `Style.md` | 叙事声音与语气 | 声音、节奏、节奏、影响 |
| `Characters.md` | 角色表 | 每个角色丰富的 Markdown 表格 |
| `Worldbuilding.md` | 背景 & 世界规则 | 按类别结构化表格 |
| `Conflict.md` | 故事冲突 & 赌注 | 内部/外部冲突 |
| `Synopsis.md` | 故事完整摘要 | 开头、中间、结尾 (500-1000 字) |
| `Timeline.md` | 故事时间线 | 事件顺序、节奏、连贯性 |
| `Outline/` | 按章节划分的节奏 | 每个章节的详细大纲 |
| `Chapters/` | 草稿手稿文件 | 准备写入的章节文件 |
| `Research/` | 参考材料 | 笔记、来源、背景 |
| `Archive/` | 旧版本 & 切割 | 删除的场景、旧草稿 |
| `Assets/` | 视觉参考 | 地图、角色艺术、情绪板 |

## 输出位置

项目在以下位置创建：
```
~/writing/novels/{小说名}/
```

所有工作都在同一位置完成。该技能一次处理一个文件。

## 完整流程概述

该技能遵循此精确顺序，从不提前进行：

1. **收集项目基本信息** → 名称、语言、核心想法
2. **创建目录结构** → 所有文件夹带有 README 文件
3. **交互式 Braindump** → 北极星、标题、主题、结构（逐部分批准）
4. **定义文类** → 习俗、语气、界限、期望
5. **发现声音** → 视角、语气、节奏、影响
6. **构建角色** → 表格格式的丰富角色表（一次一个）
7. **构建世界** → 世界构建表格（设置、氛围、规则）
8. **绘制冲突** → 内部/外部冲突、赌注
9. **编写 Synopsis** → 故事完整大纲（开头 → 中间 → 结尾）
10. **创建时间线** → 事件时间线图
11. **生成章节大纲** → 详细节奏表（一次一个章节，安静地保存）
12. **草稿所有章节** → 通过并行后台任务（推荐）或按顺序询问用户如何希望并行或顺序地草稿章节 1 到章节 N
13. **审查每个章节** → 通过并行后台任务（推荐）或按顺序审查所有章节
14. **最终连贯性检查** → 验证所有章节之间的一致性
15. **完成 & 呈现** → 最终验证和下一步

### 工作流优化说明：

**并行处理（步骤 12-13）：**
- 步骤 12 和 13 支持通过后台代理并行执行
- 对于步骤 12：首先草稿第一章以供批准，然后启动并行代理以处理剩余章节
- 对于步骤 13：同时启动每个章节的一个审查代理
- 并行执行大大减少了总时间（分钟 vs 小时）
- 每个代理独立工作，并具有完整的上下文访问权限
- 在 delegate_task 调用中使用 `run_in_background=true` 参数

**何时使用并行 vs 顺序：**
- **并行（默认）：** 5 个以上章节，用户想要速度，没有特殊依赖
- **顺序：** 用户偏好、非常复杂的连贯性或需要调试

## 后台任务管理

### 何时使用后台任务

**使用 delegate_task 并设置 run_in_background=true 的情况：**
- 草稿多个章节（步骤 12：章节 2-N）
- 审查多个章节（步骤 13：所有章节）
- 任何不需要顺序执行的并行、独立操作

**任务参数：**
```
delegate_task(
  category="unspecified-high",
  description="向用户显示的简要任务描述",
  prompt="包含上下文文件路径和要求的详细说明",
  run_in_background=true  # 对于并行执行是必需的
)
```

### 监控后台任务

**启动并行任务后：**
1. 宣布启动了多少个任务
2. 提供估计完成时间
3. 系统将在任务完成时通知
4. 用户可以请求状态更新或实时监控
5. 使用 `background_output(task_id="...")` 来检索结果

**状态通信：**
- "启动了 [N] 个并行代理用于 [任务描述]"
- "任务 [N] 完成 [总数]"
- "所有任务完成。继续下一步。"

### 任务设计原则

**每个后台任务必须：**
1. 完全自包含且独立
2. 在提示中明确列出所有必需的上下文文件
3. 包括明确的成功标准和输出格式
4. 指出不要做什么（限制）
5. 将结果保存到正确的文件位置

**避免：**
- 依赖于其他后台任务首先完成的任务
- 没有文件路径的模糊说明
- 需要在执行中途要求用户输入的任务

## 关键交互原则

### 确认格式（强制）

在提出任何部分内容后，始终使用此精确格式：

```
这感觉符合你正在持有的东西吗？
你可以回复：
1. **是**（批准并继续）
2. **调整**（告诉我如何调整）
3. **重写**（我将用不同的方法重新生成）
```

### 基于内存的工作流

**关键文件写入规则：**
- 在该文件的所有部分都获得批准之前，不要写入文件
- 仅将每个批准的部分存储在内存中
- 在该文件的所有部分都完成并批准后立即保存文件
- 每个文件在完成时一次性写入
- 除非明确要求，否则永远不要修改已完成的文件
- 依次通过部分，永远不要跳过前一个
- 基础文件（Braindump、Genre、Style 等）必须保存后才能移动到大纲

### 语气 & 声音

在整个交互过程中：
- **平静、耐心、关注情感**
- **温和、人性化、反思性语言**
- **不匆忙、不做假设**
- **将情感真实反馈给作者**
- **尊重沉默和不确定性**

## 第 1 步：收集项目基本信息

### 解析快速启动命令（如果提供）

如果用户使用命令语法调用：
```
/novel-architect [语言] 小说名为 [名称] "[核心想法]"
```

提取：
- **语言**： "an english novel" → `english` | "hindi" | "bilingual"
- **名称**： "named lost-horizon" → `lost-horizon`（将成为文件夹名称）
- **核心想法**： 引号括起来的描述
- 对于专门的文类支持，请咨询 @genre.md、@fantasy.md 或 @mystery.md。

### 否则，温和询问

从温暖、邀请的问题开始：

> "让我们一起创建你的小说项目。我将逐步引导你。
>
> 首先，你想给这个项目起什么名字？（使用小写和连字符，例如 'my-novel' 或 'lost-horizon')"

等待响应，然后：

> "你将用哪种语言写作？
> 1. 英语，2. 印地语"

等待响应，然后：

> "告诉我你的故事想法。不用担心完全想清楚——只需分享你心中和心中的想法。几句话就完美了。"

**情感上反映他们的想法：**

> "让我温柔地反映我所听到的——不要塑造它。
>
> [他们核心想法的 2-3 句话情感反映]
>
> 这感觉符合你正在持有的东西吗？
> 你可以回复：
> 1. **是**（批准并继续）
> 2. **调整**（告诉我如何调整）
> 3. **重写**（我将用不同的方法重新生成）"

等待确认后再继续。记住这是我们的北极星。



## 第 3 步：交互式 Braindump

**关键：** 一次处理一个部分。存储在内存中。只有在所有部分都批准后，才写入 Braindump.md。

### 第 3.1 部分：北极星

**这是什么：** 这是用户提供的原始核心想法。向用户显示相同的行并请求确认。

**根据他们的核心想法提出：**

> "让我们从北极星开始——使这个故事重要的情感真实。
>
> 根据你分享的内容，我感觉到：
>
> **北极星：**
> [用户原始北极星在第 1 部分中给出]
>
> 这感觉符合你正在持有的东西吗？
> 你可以回复：
> 1. **是**（批准并继续）
> 2. **调整**（告诉我如何调整）
> 3. **重写**（我将用不同的方法重新生成）"

**等待明确批准。** 批准后，存储在内存中，然后进入下一个部分。

**示例：**
> **北极星：**
> "这是一个关于一个普通男人在 MP 的三级城镇的故事。他静静地观察生活，尤其是女性的生活"

## 第 14 步：最终连贯性检查

**重要提示：** 检测并报告所有章节之间的不一致，但不改变内容。

**宣布开始：**

> "正在跨所有章节运行最终连贯性检查..."

### 连贯性检查流程：

1. **加载所有文件：**
   - 所有 `Chapters/chapter-N.md` 文件
   - `Timeline.md`
   - `Characters.md`
   - `Worldbuilding.md`
   - `Synopsis.md`
   - `Conflict.md`

2. **检查以下方面的一致性：**
   - **时间线：** 事件顺序、时间压缩/扩展、昼夜逻辑
   - **角色：** 行为一致性、情感跳跃、知识连贯性
   - **世界构建：** 规则违规、背景设定不一致、地理特征
   - **情感连贯性：** 突然转变、重复情节、无原因回归
   - **主题：** 意外稀释或否定核心主题

3. **检测规则：**
   - 不干预地观察
   - 标记不一致，而非风格偏好
   - 尊重有意模糊性
   - 从不强加解释
   - 保留作者对意义的权威

4. **创建诊断报告：**

   保存到 `Research/continuity_diagnostic_report.md`：

   ```markdown

   生成时间：[日期]
   范围：所有章节（1-N）

   ## 检查结果概述
   [高级概述]

   ## 确认一致性

   ### 时间线
   [涉及特定章节/行的具体问题]

   ### 角色行为
   [涉及具体章节/行]

   ### 世界构建
   [涉及具体章节/行]

   ### 情感连贯性
   [涉及具体章节/行]

   ### 主题元素
   [涉及具体章节/行]

   ## 作者问题

   针对每个标记问题，提供 1-3 个聚焦问题：

   **问题 1：** [描述]
   - 问题：[中立、具体的问题]
   - 理由：[为什么这个问题有用]

   [继续针对每个问题]
   ```

5. **输出规则：**
   - 使用中立、观察性语言
   - 引用具体章节和段落
   - 提供问题而非结论
   - 不提议重写
   - 不改变语气或语言
   - 不替作者解决模糊性

**创建报告后：**

> "连贯性检查完成。报告已保存到 Research/continuity_diagnostic_report.md
