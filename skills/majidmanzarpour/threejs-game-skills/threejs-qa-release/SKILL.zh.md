# Three.js 测试发布

验证游戏以玩家实际遇到的方式运行，然后准备一个包含已知风险的可发布版本。

从实际加载的技能文件中解析 `<this-skill-dir>` 和本地引用；在使用运行器发现的替代方案之前，先解析其旁边的同级技能。在安装了 npm 依赖项的游戏项目中运行检查器。

## 测试通过

对于完整游戏，使用以下完整测试流程。对于狭窄的编辑，选择涵盖受影响行为、状态和目标视口的检查。重用同一代码修订中的有效专家证据；负责人拥有一个整合的测试流程。只有在相关更改、失败或未解决的关注点后，才重复测试。显式的仅限桌面范围不需要添加移动端游戏玩法。

1.  安装依赖项，运行构建和类型检查，启动开发或预览服务器。
2.  打开浏览器目标并捕获控制台、页面和网络错误。
3.  确认非空白、视觉多样化的画布像素。
4.  在每个目标视口上捕获活动游戏（默认情况下为桌面和移动端），而不仅仅是标题屏幕。
5.  执行主要输入、目标进度、失败和重试，以及最近更改的内容。
6.  检查 HUD 文本适配、安全区域、触摸目标和对响应式布局。
7.  当音频更改时：用户手势解锁、SFX 触发、环境循环开始和停止、暂停和重启清理、静音和音量、解码错误。
8.  决定使用视觉测试框架。对于高级、发布就绪、UI 密集型或生成资产的工作，框架通常值得使用；无论哪种情况都要说明。
9.  运行机器人游戏测试（在框架游戏中的 `tests/bot-playtest.template.ts`）以获取发布就绪的游戏玩法声明，并报告其指标 JSON。
10. 当动画更改时，捕获一个短的非暂停序列，并使用 `references/visual-test-harness.md` 检查移动、剪辑过渡、脚步、 rig 变形和攻击/接触时间。

仅屏幕截图无法覆盖游戏玩法更改。

## 画布检查器

```bash
node <this-skill-dir>/scripts/inspect-threejs-canvas.mjs --manifest artifacts/evidence.json --url http://127.0.0.1:5188 --seed 42
```

首先在 `artifacts/evidence.json` 中声明测试的视口/状态对，并使用一个新的运行 ID；格式和测试钩子合同在负责人的 `references/evidence-manifest.md` 中。一个命令在一个浏览器中捕获每个声明的对，并为每个捕获打印一行：PASS/FAIL、GPU、像素指标、超预算行、错误计数以及报告和屏幕截图路径。仅当其行需要更多详细信息时才打开报告文件。包含所有请求的状态；不要删除一个失败的槽位以使清单通过。对于一次性检查，`--state <name> [--mobile]` 捕获单个视图，省略 `--state` 仅检查当前视图。框架游戏有自己的副本作为 `npm run inspect:canvas`。

指标是 `threejs-aaa-graphics-builder/references/visual-scorecard.md` 中视觉记分牌的测量证据。超预算行需要一个记录的权衡，空白画布或错误条件会非零退出。

## 发布测试

检查包脚本、Vite 配置、基本路径和公共资产 → 禁用调试 UI、日志记录和测试辅助工具 → 运行生产构建并在静态服务器上预览 → 在目标视口上检查构建输出 → 审查捆绑包和大型资产 → 记录部署命令、主机假设和残余风险。

## 报告

首先列出结果和未解决的缺陷。将详细的命令、清单、捕获、运动证据、执行的控制、修复的问题和部署说明放在项目的证据报告中。在范围内时包含框架决定和机器人指标。将工件路径返回给负责人；通过像素和确认的状态钩子本身不能建立美学质量或成功的游戏玩法。
