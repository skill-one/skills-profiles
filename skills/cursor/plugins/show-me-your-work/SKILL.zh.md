# 展示你的工作成果

保持一个标准的日志记录。

## 格式要求

一个单独的 TSV 文件，每行记录一个决策。单元格保持单行。证据是一个指针，而不是散文。

复制 `references/decision-log-template.tsv`（表头行）来开始一个干净的日志。列：

- **ts.** ISO8601 时间戳。
- **phase.** 阶段或工作流。
- **decision.** 所选择或执行的内容，一行即可。
- **why.** 简单明了的理由。如果是由原则驱动的，直接说明，不要用术语标签。
- **evidence.** 证明它的链接或路径：提交哈希值、PR 编号、`file:line` 或一个工件、追踪记录或截图路径。绝不使用段落。
- **result.** 结果或判定状态：`tests green`、`reverted`、`pixel-diff 0`、`INCONCLUSIVE`、`open`。

一个示例，用简单直白的语言编写，以便审阅者能一目了然地阅读。

```
ts	phase	decision	why	evidence	result
2026-05-24T09:02:00Z	frame	先统计了工作内容，大约有 100 个组件和 75 小时的工作量	在开始漫长的运行前想了解工作规模	commit 3a9f1c2	在开始前发现了 5 件需要整理的事情
2026-05-24T09:40:00Z	harness	在修改任何内容前对旧版本进行了截图	以便我们可以将旧版本与新版进行比较并捕捉任何视觉变化	scripts/snapshot.sh, baseline/	保存了 120 张参考截图
2026-05-24T11:15:00Z	widget	将小部件样式迁移过来，但没有改变其外观	保持变更小，结果保持一致	commit 7c21e0a, pixel-diff 0	外观一致，测试通过
2026-05-24T12:30:00Z	widget	因为一个辅助工具的截图为空而丢弃了它的工作	检查了实际文件而不是相信它的摘要	worktree reset	reverted, 重新调整了下一次的说明
```

## 记录一行日志

以你向队友解释你做了什么的方式来编写每条记录。使用简单直白的语言，具体行动，不要使用 AI 术语或抽象术语（**unslop** 技能也适用于日志文本）。

使用辅助工具 `scripts/log.sh <logfile> <phase> <decision> <why> <evidence> <result>`。它会标记 `ts`，在首次使用时写入表头，删除多余的制表符/换行符，并将以 `=`, `+`, `-`, 或 `@` 开头的任何单元格前缀一个单引号。一个简单的 `printf` 追加一行也可以，但要确保相同的字节，如果单元格来自生成或用户提供的文本。

记录决策点和检查点，而不是每个操作：一个分支的选择，一个单元的完成及其验证结果，一个转折或回滚及其触发因素，一个障碍的暴露，一个门控的修复。对于循环运行，每行记录一次迭代。忽略琐碎和显而易见的内容。

一个运行是一个代理对话，包括其后续回合以及任何对其的总结。一个接手、一个替换的代理或一个新的聊天会话开始一个新的运行。当一个运行添加到一个已经包含行的日志时，它的第一行 `phase` 为 `start`，另一个运行 `start` 行后的第一行也是 `start`。因此，一个在后续回合回到日志的运行首先会读取日志的最后几行，以查看是否有其他运行自那时以来写入。一个 `start` 行会命名它之前该运行未写入的行的 `ts` 范围，并且它的证据会命名这个运行，例如其代理 ID。使用 `phase` `start` 仅用于此目的。

## 存放位置

默认情况下，日志是一个工作产物，不提交。将其保存在工作目录中的 `decisions.tsv`，或者在同时进行多个工作努力时保存在 `.audit/<task-slug>.tsv`，并且不要将其提交到 git。

只有当工作足够雄心勃勃，以至于审阅者需要追踪记录来信任结果时，才提交它。

## 规则

- 只追加不删除。一个错误的决策会得到一个新的行来覆盖它。永远不要编辑或删除历史记录。
- 优先使用由已提交脚本生成的证据，而不是手工制作的单个实例（**encode-lessons-in-structure** 原则技能）。

## 对照文本审计日志

在运行结束时，在交还之前，检查日志是否如实记录。在当前工作空间的 `agent-transcripts/` 目录下读取此运行的文本（系统提示会命名路径）。不要跨 `~/.cursor/projects/*` 进行 glob 匹配。那会读取无关的私人聊天。逐行跟踪此运行的行与实际发生的情况。每段行从该运行的 `start` 行开始，如果该运行创建了日志，则从第一行开始，并结束于另一个运行的下一个 `start` 行：

- 检查每一行是否对应一个真实的决策或行动。
- 检查每一行的证据是否有效并显示该行所声称的内容。
- 一个塑造了工作但未记录的分支、转折或放弃的方法是一个空白。添加它。

修正日志，而不是故事。审计永远不会编辑或删除一行，即使是一个虚构的行。当一行既不记录真实的决策也不记录真实的行动，或其声明或证据是错误的时，添加一行来覆盖它，并包含实际发生的情况和指向有效证据的指针。这次审计不会检查此运行段外的行。如果该运行自己的工作显示其中之一是错误的，像处理任何错误决策一样覆盖它。

## 跨模型审查轨迹

在交还之前，在一个与执行工作不同的模型系列上生成一个子代理。自我审查不能替代。子代理阅读审计轨迹和运行的文本，然后标记用户应该注意的内容。不是重做工作，而是扫描哪些方面次优或存在风险。

- 使用弱证据或无证据记录的决策。
- 在文本中未提供证据的情况下跳过验证步骤或声称验证。
- 回顾时看起来有风险的选择（过早、范围蔓延、掩盖症状）。
- 用户在粗略浏览时可能遗漏的空白。

每个产生轨迹的运行的回复都以“注意”部分结束。以审阅者的模型名称单独一行开头（`reviewed by <model>`），然后列出每个指向特定行或时刻的标记。“No flags”是一个有效的值。模型名称不是。

## 审查轨迹

从上到下阅读，跟随证据指针，进行抽查。GitHub 将提交的 TSV 渲染为表格。`column -s$'\t' -t decisions.tsv` 在终端中渲染它。

## 组合这项技能

其他技能将它们的审计轨迹路由到这里，而不是自己发明一个。通过名称引用它，并让它拥有格式。不要重述列。
