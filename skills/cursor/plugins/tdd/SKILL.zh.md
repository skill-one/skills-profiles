# TDD Bug Fix

在修复具有明确、低成本测试路径的 Bug 时，在更改生产代码之前使错误行为可执行。目标是编写一个专注的回归测试，该测试在修复之前失败，修复后通过。

不要强迫进行测试，如果这样做不切实际。如果可用的测试需要广泛的框架设置、脆弱的 Mock、缓慢的端到端基础设施、仅限生产状态、模糊的复现步骤或大量不相关的 Fixture 更改，请跳过添加新测试，并使用最接近的有用验证方法。

## 工作流程

1. **理解 Bug。** 确定预期行为、当前行为、受影响路径和最小的可观察复现步骤。
2. **选择最窄的可执行检查。** 优先考虑已用于该代码路径的最近的单元测试、组件测试、集成测试或回归测试。如果没有明显的实用测试路径，不要为了满足工作流程而从零开始创建一个。
3. **首先编写失败的测试。** 添加最小的专注测试，该测试可以捕获 Bug。测试应编码预期行为，而不是镜像当前实现。
4. **在修复之前运行新测试。** 确认它因预期原因而失败。如果它通过或因不相关原因而失败，请在编辑实现之前更正测试或复现步骤。
5. **修复 Bug。** 进行最小的生产更改，以满足预期行为，同时保留附近的契约。
6. **重新运行回归测试。** 确认测试现在通过。

## 如果失败的测试不切实际

使用最接近的可执行回归检查：一个有针对性的脚本、手动复现命令、浏览器自动化、快照比较、日志断言或专注的集成检查。

优先考虑不添加新测试，而不是一个糟糕的测试。一个糟糕的测试是指主要测试 Mock、编码当前实现细节、依赖于时间或不相关的全局状态、需要昂贵的基础设施进行小修复，或在证明修复后会立即删除的测试。

## 安全网

- 不要仅仅为了匹配错误的实现而更改测试。
- 除非预期行为确实发生了变化且原因明确，否则不要削弱现有的断言。
- 保持回归测试专注于 Bug。避免广泛的 Fixture 更改或不相关的覆盖率扩展。
- 如果 Bug 不稳定，尽可能使测试确定性，并记录正在锁定的信号。
- 如果 Bug 暴露了一类更广泛的失败，首先部署专注的回归路径，然后考虑额外的兄弟覆盖率。

## 最终响应

报告证据，而不仅仅是结果：

- 命名在修复之前失败的测试或可执行检查及其产生的失败。
- 命名修复后运行的测试以及附近执行的任何验证。
- 如果无法证明修复之前的证据，请说明原因，并描述使用的最接近的回归检查。
