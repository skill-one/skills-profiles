# 验证此

验证不是重述。它通过可重复的证据来证明或反驳一个具体的声明。

## 何时使用

- 用户询问“验证这个”、“证明它有效”、“这个修复了吗”或“给我展示证据”。
- 软件缺陷修复需要前后可复现的测试。
- UI、CLI、API、性能或内存的声明需要测量。
- 测试通过，但用户可见的行为仍需确认。

不要用于模糊的声明，如“代码更整洁”。先要求一个可测量的声明。

## 工作流程

1. 将声明以可证伪的形式重述：条件、指标和阈值。
2. 选择能证伪它的最小本地表面。
3. 从旧状态捕获基线：合并基础、父提交、失败分支或当前损坏的可复现步骤。
4. 在变更状态捕获处理效果，使用相同的命令、数据、预热和环境。
5. 比较原始产物：数字、截图、终端记录、HTTP响应、性能分析、堆快照或测试输出。
6. 返回一个明确的判定：`VERIFIED`、`NOT VERIFIED` 或 `INCONCLUSIVE`。

## 本地表面

- 代码行为：聚焦的单元/集成测试或最小化可复现脚本。
- CLI/TUI行为：`control-cli`、终端记录或演示录制。
- UI行为：`control-ui`、截图、无障碍快照或浏览器跟踪。
- API行为：本地HTTP/RPC请求和响应差异。
- 性能：同机基线/处理效果计时或CPU性能分析。
- 内存：疑似操作前后的堆快照。

## 产物布局

在安全写入产物时：

```text
/tmp/verify-this/<声明缩写>/
├── claim.md
├── timeline.md
├── baseline/
├── treatment/
├── diff/
└── verdict.md
```

如果产物可能包含敏感代码、提示、截图、HTTP体或堆数据，除非用户同意磁盘存储，否则仅保留必要的内联证据。

## 判定规则

- `VERIFIED`：基线和处理效果在预期方向上差异，达到声明阈值，且无明显混杂因素。
- `NOT VERIFIED`：行为未改变、朝反方向变化或未达到阈值。
- `INCONCLUSIVE`：无有效基线、信号噪声、测量失败或环境差异使比较无效。

## 输出

使用此格式：

```text
VERIFIED | NOT VERIFIED | INCONCLUSIVE
声明：<可证伪声明>

证据：
<指标/产物>：基线=<...>，处理效果=<...>，差异=<...>，阈值=<...>

理由：
<一段紧密的段落，说明证据和任何混杂因素>
```

不要淡化负面结果。清晰的 `NOT VERIFIED` 很有用。
