name: arena
description: 在同一任务中并行生成N个候选者，选择一个基础，将失败者的最强部分嫁接到它上面。用于/arena、'arena this'、'throw it in the arena'，或在尝试制作一个非平凡物品时，避免锁定错误的形状。

# 场地

对同一任务并行执行 N 次尝试。逐个读取每个候选结果。挑选最强的作为基础。将其他最佳想法嫁接到它上。验证合成结果。

## 开始

在启动任何东西之前，使用一个条目对应每个阶段的待办事项列表。

1. 构架
2. 并行执行
3. 交叉评判
4. 挑选
5. 嫁接
6. 验证

## 阶段 A：构架

N 个候选将接收相同的提示，因此提示是合同。

1. 说明每个候选将生成的工件。
2. 推导评分标准。说明此任务的成功标准，然后将其转化为 3-6 个具体的可评分标准。评分标准是阶段 D 中挑选者的工具。候选者只看到任务。
3. 选择执行者。使用 `~/.cursor/rules/pstack-models.mdc` 中的 `arena runners` 行。如果规则或该行缺失，则默认在 `claude-opus-5-5-max`、`gpt-5.6-sol-max`、`grok-4.7-xhigh-fast` 上各运行一个。该行或交叉评判行中的 `auto` 或 `inherit-parent` 条目表示父模型，因此省略 `model`。如果任务工具拒绝配置的条目，则在该模型的家族默认值上运行该座位并说明。家族按前缀区分：`claude-*`、`gpt-*` 和 `grok-*`。没有家族匹配时，使用 `claude-opus-5-5-max`。如果它拒绝默认值，则使用错误消息中同一家族的最接近的有效 slug。当场地覆盖多个设计方向时，生成更多。当工作受生成限制而不是评判敏感时，多次使用相同模型。
4. 分配输出路径。每个候选者写入自己的位置（尽可能使用 git 工作树，否则 `/tmp/arena-<slug>/candidate-<n>/`），遵循 **在序列化共享状态之前分离** 原则技能。

## 阶段 B：并行执行

使用 `run_in_background: true` 在一条消息中生成所有 N 个子代理，每个子代理都有任务、共享基础的路径、自己的输出路径以及生成工件和简短理由的指令。

每个理由命名候选者考虑的替代方案及其拒绝的内容。

如果候选者未能生成输出，则继续使用 N-1 并在合成记录中注明退出。

## 阶段 C：交叉评判

在所有阶段 B 候选者完成后，从 `~/.cursor/rules/pstack-models.mdc` 中的 `arena cross-judge pool` 行中选择一个模型。如果规则或该行缺失，则从 `claude-opus-5-5-max`、`gpt-5.6-sol-max`、`grok-4.7-xhigh-fast` 中选择。优先选择与父模型不同家族的模型。在该模型上生成一个只读评判子代理。它看到评分标准以及候选者的路径标签，对每个标准进行评分，并推荐一个带有理由的基础。它与父模型在阶段 D 中并行读取，而不是与候选者本身并行。在候选者仍在写入时不要生成评判者。

## 阶段 D：挑选基础

在挑选之前逐个读取每个候选。

根据评分标准逐项评分每个候选，而不是整体感觉。与交叉评判进行比较。对基础的一致确认了挑选。不一致意味着其中一方有偏见或评分标准不明确。在决定之前阅读两个理由。

选择候选者可以最容易地扩展而不破坏不变性的基础。当两者感觉相当时，优先选择更干净的边界或更小的 API，根据懒惰协议。

在基础旁边记录挑选和原因的简短合成笔记，包括交叉评判的裁决。

## 阶段 E：嫁接

再次逐个遍历每个失败的候选者，并确定值得移植到基础中的内容。信号通常是每个候选者的一两个东西，而不是大部分。

手动将每个嫁接项折叠进来，根据 **从第一原理重新设计** 原则技能。不要机械地粘贴。结果必须在单个思维模型下保持连贯。

记录嫁接的内容、来源候选者以及拒绝的内容和原因。

当 N 个候选者收敛到同一形状时，这是一个强烈的协议信号。在记录中注明收敛并发送共识形状。不需要嫁接。当 N 个候选者 wildly 分化时，阶段 A 定义不明确。重新构架并重新运行，而不是平均分化。

## 阶段 F：验证

合成的工件必须与其他任何输出一样经受同样的审查，根据 **证明它有效** 原则技能。

如果验证发现场地未能捕获的问题，要么阶段 A 错误（重新构架并重新运行），要么一个候选者捕获了它而您错过了嫁接（回到阶段 E）。不要掩盖。

## 输出

一个合成的工件。一个简短的合成笔记，包括基础、嫁接（带来源候选者）、拒绝、退出（如有）和验证结果。
