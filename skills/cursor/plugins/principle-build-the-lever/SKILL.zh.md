# 制作杠杆

当工作并非微不足道时，制作一个工具来处理它，而不是手工完成。

**原因：** 两种收益。吞吐量：一个 codemod、生成器或脚本以相同的方式重复执行工作，并且可以免费重跑。信心：工具是审查者可以阅读和重跑以检查工作的单个工件。手工完成的更改只能通过重做来重新验证。一个确定性脚本将“相信我”转变为“运行这个”。

**模式：** 默认情况下制作杠杆。只有在任务微不足道时，即你一眼就能看到的一两个明显修改时，才跳过它。

- 手工完成第一个单元以学习配方，然后制作工具。通过在同一个单元上重跑它并与你手工完成的版本进行 diff 来证明它。确保杠杆可以安全地重跑。
- 使用 codemod 或脚本进行编辑，使用生成器处理重复文件，使用转储到 sqlite 的查询进行数据分析，使用可重跑的检查进行验证。
- 确定性杠杆优于发散。如果工具可以一次处理每个单元，请自己运行它。不要将委托发散到手工应用脚本可以完成的工作。
- 当你将工作发散到子代理时，将杠杆作为一个技能，让它们都读取：配方、验证合同和不可触碰的边界在一个工件中。将其保留在委托的写入范围之外，这样它们就无法悄悄地编辑合同。
- 应用此原则会产生一个文件。如果你引用了它，并且在 diff 中没有 codemod、脚本、生成器或委托技能，那么你没有应用它。
- 当工作超出会话范围时，提交杠杆。

**平衡：** 标准是微不足道，而不是重复。即使是一次性的，只要杠杆是使工作可检查的，仍然值得制作杠杆。根据 [懒惰协议](../principle-laziness-protocol/SKILL.md)，构建执行或证明工作的最小脚本，而不是框架。

与 [将经验教训编码在结构中](../principle-encode-lessons-in-structure/SKILL.md) 不同，后者将重复指令制作成持久的护栏。这是你面前工作的吞吐量和可审查性。有关脚本验证本身的，请参阅 [证明它有效](../principle-prove-it-works/SKILL.md)。
