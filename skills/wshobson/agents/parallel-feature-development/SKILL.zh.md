# 并行功能开发

将功能分解为并行工作流、建立文件所有权边界、避免冲突以及整合多个实现代理的结果的策略。

## 使用此技能的场景

- 为并行实现分解功能
- 在代理之间建立文件所有权边界
- 设计并行工作流之间的接口契约
- 选择集成策略（垂直切片 vs 水平层）
- 管理并行开发的分支和合并工作流

## 文件所有权策略

### 按目录划分

为每个实现者分配特定的目录所有权：

```
implementer-1: src/components/auth/
implementer-2: src/api/auth/
implementer-3: tests/auth/
```

**最适合**：具有清晰目录边界的结构良好的代码库。

### 按模块划分

分配逻辑模块的所有权（可能跨越目录）：

```
implementer-1: 认证模块（登录、注册、登出）
implementer-2: 授权模块（角色、权限、守卫）
```

**最适合**：面向功能的架构、领域驱动设计。

### 按层划分

分配架构层的所有权：

```
implementer-1: UI层（组件、样式、布局）
implementer-2: 业务逻辑层（服务、验证器）
implementer-3: 数据层（模型、仓库、迁移）
```

**最适合**：传统的MVC/分层架构。

## 避免冲突规则

### 基本原则

**每个文件只有一个所有者**。不应将文件分配给多个实现者。

### 必须共享文件的情况

如果文件确实需要多个实现者进行修改：

1. **指定单一所有者** — 一个实现者拥有该文件
2. **其他实现者请求修改** — 向所有者发送具体的修改请求
3. **所有者按顺序应用修改** — 防止合并冲突
4. **替代方案：提取接口** — 创建一个单独的接口文件，非所有者可以导入而不修改

### 接口契约

当实现者需要在边界处协调时：

```typescript
// src/types/auth-contract.ts (由team-lead拥有，实现者只读)
export interface AuthResponse {
  token: string;
  user: UserProfile;
  expiresAt: number;
}

export interface AuthService {
  login(email: string, password: string): Promise<AuthResponse>;
  register(data: RegisterData): Promise<AuthResponse>;
}
```

两个实现者都从契约文件导入，但都不修改它。

## 集成模式

### 垂直切片

每个实现者构建一个完整的功能切片（UI + API + 测试）：

```
implementer-1: 登录功能（登录表单 + 登录API + 登录测试）
implementer-2: 注册功能（注册表单 + 注册API + 注册测试）
```

**优点**：每个切片可以独立测试，需要的集成最少。
**缺点**：可能重复共享工具，紧密耦合的功能更难处理。

### 水平层

每个实现者构建跨所有功能的单个层：

```
implementer-1: 所有UI组件（登录表单、注册表单、个人资料页）
implementer-2: 所有API端点（登录、注册、个人资料）
implementer-3: 所有测试（单元测试、集成测试、E2E测试）
```

**优点**：每层内的一致性模式，自然的专门化。
**缺点**：更多集成点，第3层依赖于第1层和第2层。

### 混合模式

根据耦合度混合垂直和水平：

```
implementer-1: 登录功能（垂直切片 — UI + API + 测试）
implementer-2: 共享认证基础设施（水平 — 中间件、JWT工具、类型）
```

**最适合**：大多数具有部分共享基础设施的现实世界功能。

## 分支管理

### 单分支策略

所有实现者在同一功能分支上工作：

- 设置简单，无合并开销
- 需要严格的文件所有权以避免冲突
- 最适合：小型团队（2-3人），定义清晰的边界

### 多分支策略

每个实现者在一个子分支上工作：

```
feature/auth
  ├── feature/auth-login      (implementer-1)
  ├── feature/auth-register    (implementer-2)
  └── feature/auth-tests       (implementer-3)
```

- 更高的隔离度，明确的合并点
- 更高的开销，共享文件中仍可能出现合并冲突
- 最适合：大型团队（4人以上），复杂功能

## 故障排除

**实现者互相阻塞等待共享代码。**
将共享部分提取到其自己的接口契约文件中，由team-lead拥有，并让实现者从该文件导入。两个实现者都不修改契约 — 他们只针对契约进行实现。

**即使有明确的所有权规则，仍然出现合并冲突。**
文件被分配给了两个代理，或者自动导入所有内容的配置文件（例如 `index.ts`、`__init__.py`）被两个实现者修改。为所有桶/索引文件指定一个所有者，或者由负责人在最后合并它们。

**一个实现者提前完成，但集成步骤被阻塞。**
使用暂态接口：完成的实现者编写下游依赖的桩或模拟，以便其他实现者可以继续工作。在集成时替换为实际实现。

**功能分解在过程中发现是错误的。**
停止新工作，由负责人重新分配文件，并通过广播传达变更。部分编写的代码的沉没成本是可以接受的 — 继续错误的分割更糟。

**一个实现者编写的测试对另一个实现者编写的代码失败。**
接口契约发生了漂移：拥有API的实现者在不通知测试实现者的情况下更改了签名。强制执行规则，即契约文件在修改前需要广播。
