# 去事后分析写作

全面指南，教你如何撰写有效且无责备的去事后分析，推动组织学习并防止事件再次发生。

## 使用此技能的场景

- 进行事件后复盘
- 撰写去事后分析文档
- 主持无责备去事后分析会议
- 识别根本原因和促成因素
- 制定可执行的后续行动项
- 建立组织学习文化

## 核心概念

### 1. 无责备文化

| 责备导向            | 无责备                         |
| ------------------ | ---------------------------- |
| "谁造成的？"       | "哪些条件允许了此事？"         |
| "有人犯了错误"     | "系统允许了此错误"             |
| 惩罚个人           | 改进系统                      |
| 隐藏信息           | 分享学习成果                  |
| 恐惧发声           | 心理安全感                    |

### 2. 去事后分析触发条件

- SEV1 或 SEV2 事件
- 面向客户的停机 > 15 分钟
- 数据丢失或安全事件
- 可能造成严重后果的未遂事件
- 新的故障模式
- 需要异常干预的事件

## 快速入门

### 去事后分析时间线

```
第 0 天：事件发生
第 1-2 天：起草去事后分析文档
第 3-5 天：去事后分析会议
第 5-7 天：最终确定文档，创建工单
第 2 周后：行动项完成
每季度：回顾事件中的模式
```

### 模板 2：5 个为什么分析

```markdown
# 5 个为什么分析：[事件]

## 问题陈述

支付服务因数据库连接耗尽导致 47 分钟停机。

## 分析

### 为什么 #1：为什么服务失败？

**答案**：数据库连接耗尽，导致所有新请求失败。

**证据**：指标显示连接数达到 100/100（最大值），有 500+ 挂起请求。

---

### 为什么 #2：为什么数据库连接耗尽？

**答案**：每个入站请求都打开新的数据库连接，而不是使用连接池。

**证据**：代码差异显示直接使用 `DriverManager.getConnection()`，而不是池化的 `DataSource`。

---

### 为什么 #3：为什么代码绕过连接池？

**答案**：一名开发人员重构了仓库类，并无意中更改了连接获取方法。

**证据**：PR #1234 显示了该更改，当时正在修复另一个 Bug。

---

### 为什么 #4：为什么代码审查没有发现？

**答案**：审查者专注于功能变更（Bug 修复），没有注意到基础设施变更。

**证据**：审查评论仅讨论业务逻辑。

---

### 为什么 #5：为什么没有针对此类变更设置安全网？

**答案**：我们缺乏验证连接池行为的自动化测试，并且缺乏关于连接模式的文档。

**证据**：测试套件没有连接处理的测试；维基没有关于数据库连接的文章。

## 识别的根本原因

1. **主要**：缺少基础设施行为的自动化测试
2. **次要**：架构模式文档不足
3. **次要**：代码审查清单不包括基础设施考虑因素

## 系统性改进

| 根本原因    | 改进措施                       | 类型       |
| ---------- | ---------------------------- | ---------- |
| 缺少测试   | 添加基础设施行为测试           | 预防       |
| 缺少文档   | 记录连接模式                  | 预防       |
| 审查缺陷   | 更新审查清单                   | 检测       |
| 无金丝雀发布 | 实施金丝雀发布                | 缓解       |
```

### 模板 3：快速去事后分析（轻微事件）

```markdown
# 快速去事后分析：[简短标题]

**日期**：2024-01-15 | **时长**：12 分钟 | **严重性**：SEV3

## 发生了什么

由于缓存刷新后的缓存未命中风暴，API 延迟飙升到 5 秒。

## 时间线

- 10:00 - 启动缓存刷新以更新配置
- 10:02 - 延迟警报触发
- 10:05 - 确定为缓存未命中风暴
- 10:08 - 启用缓存预热
- 10:12 - 延迟恢复正常

## 根本原因

对配置进行全缓存刷新导致雷声阵阵。

## 修复措施

- 立即：启用缓存预热
- 长期：实施部分缓存失效（ENG-999）

## 经验教训

生产环境不要全刷新缓存；使用目标失效。
```

## 促进指南

### 主持去事后分析会议

```markdown
## 会议结构（60 分钟）

### 1. 开场（5 分钟）

- 提醒所有人无责备文化
- "我们在这里是为了学习，而不是责备"
- 回顾会议规范

### 2. 时间线回顾（15 分钟）

- 按时间顺序回顾事件
- 提出澄清问题
- 识别时间线中的空白

### 3. 分析讨论（20 分钟）

- 什么失败？
- 为什么失败？
- 哪些条件允许了此事？
- 什么可以防止？

### 4. 行动项（15 分钟）

- 头脑风暴改进措施
- 按影响和努力程度排序
- 指定负责人和截止日期

### 5. 结束（5 分钟）

- 总结关键学习成果
- 确认行动项负责人
- 如有必要，安排后续会议

## 促进技巧

- 保持讨论在正轨上
- 将责备转移到系统
- 鼓励沉默的参与者
- 记录不同意见
- 时间限制离题内容
```

## 需避免的反模式

| 反模式            | 问题                    | 更好的方法                 |
| ---------------- | ---------------------- | ------------------------ |
| **责备游戏**      | 关闭学习                | 关注系统                  |
| **浅层分析**      | 不会防止再次发生        | 重复问"为什么" 5 次       |
| **无行动项**      | 浪费时间                | 总是制定具体下一步        |
| **不切实际的行动** | 从未完成                | 范围到可完成的任务       |
| **无跟进**        | 行动被遗忘              | 在工单系统中跟踪          |

## 最佳实践

### 应做

- **立即开始** - 记忆很快会模糊
- **具体** - 准确时间，准确错误
- **包含图表** - 视觉证据
- **分配负责人** - 没有孤立的行动项
- **广泛分享** - 组织学习

### 不应做

- **不要点名和羞辱** - 永远不要
- **不要忽略小事件** - 它们揭示了模式
- **不要让文档变成责备文档** - 那会扼杀学习
- **不要制造忙乱工作** - 行动应该是有意义的
- **不要忽略跟进** - 验证行动是否完成
