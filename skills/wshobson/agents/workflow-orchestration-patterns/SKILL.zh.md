# 工作流编排模式

使用 Temporal 掌握工作流编排架构，涵盖基本设计决策、弹性模式以及构建可靠分布式系统的最佳实践。

## 何时使用工作流编排

### 理想用例（来源：docs.temporal.io）

- **跨机器/服务/数据库的多步骤流程**
- **需要全有或全无语义的分布式事务**
- **长时间运行的工作流**（数小时到数年），具有自动状态持久化
- **必须从最后成功步骤恢复的故障恢复**
- **业务流程**：预订、订单、活动、审批
- **实体生命周期管理**：库存跟踪、账户管理、购物车工作流
- **基础设施自动化**：CI/CD 管道、资源分配、部署
- **需要超时和升级的有人参与系统**

### 不应使用的场景

- 简单的 CRUD 操作（使用直接 API 调用）
- 纯数据处理管道（使用 Airflow、批处理）
- 无状态请求/响应（使用标准 API）
- 实时流（使用 Kafka、事件处理器）

## 最佳实践

### 工作流设计

1. **保持工作流专注** - 每个工作流只负责单一职责
2. **小工作流** - 使用子工作流实现可扩展性
3. **清晰的边界** - 工作流编排，活动执行
4. **本地测试** - 使用可跳过时间的测试环境

### 活动设计

1. **幂等操作** - 安全重试
2. **短生命周期** - 数秒到数分钟，而非数小时
3. **超时配置** - 始终设置超时
4. **长任务的心跳** - 报告进度
5. **错误处理** - 区分可重试和不可重试错误

### 常见陷阱

**工作流违规**：

- 使用 `datetime.now()` 而不是 `workflow.now()`
- 工作流代码中使用线程或异步操作
- 直接从工作流调用外部 API
- 工作流中的非确定性逻辑

**活动错误**：

- 非幂等操作（无法处理重试）
- 缺少超时（活动永远运行）
- 无错误分类（重试验证错误）
- 忽略有效载荷限制（每个参数 2MB）

### 运维考虑

**监控**：

- 工作流执行时长
- 活动失败率
- 重试尝试和退避
- 待处理工作流计数

**可扩展性**：

- 使用工作者的水平扩展
- 任务队列分区
- 子工作流分解
- 适当的活动批处理

**关键原则**：

1. 工作流 = 编排，活动 = 外部调用
2. 工作流的确定性是不可协商的
3. 活动的幂等性至关重要
4. 状态持久化是自动的
5. 设计要考虑故障和恢复
