# 在构建之前

在实施前进行一次紧凑型事前分析。目标是识别最高风险的假设、最小验证步骤以及应推迟到证据改善后的构建范围。

## 使用时机

当用户要求构建或发布时，使用此技巧：

- 新产品、MVP、原型、着陆页、SaaS应用、市场、内容网站、代理工作流或内部工具
- 具有模糊采用、收入、留存、信任或分发影响的重大功能
- 公开发布资产，其中薄弱的定位可能浪费开发或推广工作

当任务是一个狭窄的实施修复、重构、测试修复、依赖更新或具有明确验收标准的已验证变更时，跳过此技巧。

## 风险清单

跨以下风险审查想法：

- **需求**：是否有证据表明特定买家或用户迫切需要这个？
- **定位**：目标用户能否用一句话理解它是什么以及为什么它很重要？
- **变现**：是否有可信的支付、预算或战略价值路径？
- **留存**：用户在第一次尝试后是否有理由再次回来？
- **信任**：产品是否需要用户可能抵触的信誉、数据访问、集成或行为改变？
- **分发**：是否有可重复的方式触达目标用户？
- **功能采用**：对于功能工作，功能是否会改变用户行为，还是仅仅增加表面区域？

如果结论不明显，使用 `references/risk-checklist.md` 进行更深入的问题。

## 输出格式

保持简短且决策导向：

1. **风险结论**：低、中或高风险，并附有一句解释原因的话。
2. **主要假设**：最有可能导致项目失败的单个假设。
3. **首先寻找的证据**：构建更多之前的最小有用信号。
4. **下一步行动**：一个具体的验证步骤或缩减的构建范围。
5. **推迟**：目前不应构建的内容。

## 指导

- 直接说明证据薄弱，但避免否定用户的想法。
- 倾向于较小的验证步骤，而不是大型研究计划。
- 将产品风险与工程难度分开。
- 如果想法已经验证，说明哪些证据使其风险降低，并建议最小的实施切片。
- 如果事实缺失，命名缺失的证据，而不是编造市场声明。
