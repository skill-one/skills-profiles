# 评估工具集首次使用

整个插件的阶段 0 门禁：
`finetuning-method-selection` 以及所有下游技能假定在编写训练配置之前该工具集已经存在。该工具集不是运行结束后的产物——它是数据管理引擎。用于构建黄金数据的相同标记跟踪将用于训练数据，但会排除显式的保留集。

**输入：** 如果存在，则为生产/代理跟踪；如果不存在，则为任务规范，以及愿意对 ≥100 个示例进行评分的标记员。
**输出格式：** `eval/` 目录下——黄金数据、评分员、漂移套件以及后续阶段门禁的基础模型基线。

## 门禁

没有评估工具集，就无法微调。跳到训练配置，则没有可比较的基准，无法捕获回归，也没有标记数据进行训练。飞轮：

1. **收集跟踪**——生产/代理跨度，或者如果还没有，则为合成任务。
2. **错误分析**——对 ≥100 个跟踪进行开放式编码，轴向编码到 4–8 个失败桶。
3. **每个桶一个评分员**——首先确定性地；仅对真正主观的标准使用校准的 LLM 判决。
4. **按频率 × 严重性 × 价值排序**。
5. **标记跟踪用于数据集管理，但排除显式的保留集。** 每个 `eval/goldens.jsonl` ID 都会通过 ID 排除在训练数据之外。
6. **训练。**
7. **在检查点重新运行相同的工具集**——不是运行不同的、宽松的工具集。
8. **漂移检测将反馈到步骤 2**——新的生产失败模式重新打开错误分析。

步骤 2–4 构建工具集；步骤 5–8 是为什么它必须首先存在——它既是训练数据的来源，也是检查点的退出门禁。

## 构建黄金数据

- **从跟踪中，当它们存在时：** 运行错误分析——对 ≥100 个真实跟踪进行开放式编码（读取它们，用自己的话标记失败，还没有固定的分类法），然后轴向编码将那些标签压缩成 4–8 个命名的失败桶。少于 4 个意味着编码过程太浅；多于 8 个意味着需要合并桶。**例外：** 单一失败表面的任务（例如严格模式提取）可能落在 1–2 个桶中，其中一个评分员内有按字段细分的指标——不要在没有证据的情况下凭空创建人工分割。
- **合成，当跟踪不存在时：** 基于维度的生成——列举重要的轴（任务类型、难度、边缘情况、角色），并采样交叉乘积；自由生成的提示会聚集在最容易编写的内容周围。
- **黄金数据像代码一样进行版本控制**——提交 `eval/goldens.jsonl`，在审查中对其进行差异比较，按发布进行标记。它也充当 CI 回归套件。

## 评分员

错误分析中的每个失败桶一个评分员——不是整个评估集一个。单个混合分数会隐藏哪个桶发生了回归。

- **首先确定性地。** 正则表达式、模式验证或执行检查更便宜、可重复，且无需校准。
- **仅对真正主观的标准使用 LLM 判决**——语气、忠实度、“哪个响应更好”——在这些标准上没有确定性检查可以表达。
- **在李克特量表上二进制通过/失败。** 1–5 或 1–10 的量表校准噪声更大，更难一致地应用；折叠为通过/失败。
- **漂移套件 MMLU 风格的评分：优先使用 logprob 而不是生成并提取**——紧张的标记预算使生成并提取对预览模型来说解析脆弱，将格式合规性与被测量的知识混淆在一起。所有四个评分员形状的模板和此评分注释：
  `references/grader-templates.md`。

## 判决校准是先决条件

任何路由到 LLM 判决的桶都需要在校准其判决在探索之外有任何意义之前进行校准——这是一个硬性先决条件，而不是一个可选项。**当没有桶路由到判决时 N/A**——一个全确定性工具集没有校准对象；明确说明这一点，而不是忽略本节。

- 标记 ≥100 个项目，分成 **训练**/**开发**/**密封测试**（报告一次，之后不再触摸）。
- 报告 **TPR 和 TNR**，而不是一个混合的准确数字——一个判决可以通过总是在一个倾斜的集上说“通过”来达到 90%。
- **将判决固定到固定的模型快照**，并在判决模型更改时重新校准，每季度无论如何都进行。
- **判决必须来自与被测模型不同的模型系列。**
- 一个错过约定的 TPR/TNR 标杆的判决将 **仅提供咨询**——标记供人工审查，永远不会门禁升级。完整协议、偏差校正和重新校准清单：
  `references/judge-calibration.md`。

## 基线

在阶段 1（方法选择）开始之前，运行完整的工具集——黄金数据加上能力漂移套件——对未修改的基础模型。这是每个后续检查点进行比较的数字。

`eval/baseline-<model>.json` 是门禁令牌。没有基线文件，就没有 `checkpoint-promotion` 的比较基准——一个“看起来更好”但没有测量对象的检查点不是发现。

## 目录契约

```
eval/
├── goldens.jsonl          # 标记跟踪 + 合成黄金数据，版本控制
├── graders/                # 每个失败桶一个模块
│   ├── schema_compliance.py
│   ├── exact_match.py
│   └── rubric_judge.py
├── drift-suite.yaml        # 冻结的基准 + 200-500 个领域相邻的项目
└── baseline-<model>.json   # 门禁令牌：工具集 + 漂移套件与基础模型对比
runs/
└── <run-id>/
    └── results.json         # 每个运行的工具集输出，每个检查点一个
```

`eval/` 跨运行持久存在，并位于 `runs/` 之外——固定的测量标准，而不是运行工件。`runs/` 是可丢弃的；`eval/` 不是。永远不要让运行脚本写入 `eval/`。**规范位置：** 每个按跟踪的 `results.json`——包括阶段 0 基线——位于 `runs/<run-id>/results.json`，永远不会在 `eval/runs/...` 下；要求后者的指令是错误的，而不是这个契约。

### 阶段 0 退出检查清单

在 `finetuning-method-selection` 之前，确认：

1. ≥100 个跟踪进行开放式编码；4–8 个失败桶（对于单一失败表面的任务合成黄金数据 N/A 底线——见构建黄金数据的例外；桶计数然后来自基线后的错误分析而不是）。
2. `eval/goldens.jsonl` 提交并版本控制。
3. 每个桶一个评分员，首先确定性。
4. 判决已校准——TPR/TNR，快照固定，不同系列（**当没有桶路由到 LLM 判决时 N/A**；明确说明）。
5. `eval/drift-suite.yaml` 冻结。
6. `eval/baseline-<model>.json` 已写入。

缺少这六项中的任何一项（或其 N/A 声明）？阶段 0 不完整——`/finetune` 在运行前检查基线文件。

## 相关技能

通用评估指南（仪表板、A/B 测试、非微调工具集）位于 `llm-application-dev` 插件的 `llm-evaluation` 技能中——此技能仅涵盖微调耦合：黄金数据充当训练数据，以及门禁基线。

- `finetuning-method-selection` — 首先路由到这里。
- `dataset-curation` — 将这些跟踪格式化为训练行。
- `trace-to-training-data` — 将评分跟踪转换为训练示例。
- `checkpoint-promotion` — 消耗 `baseline-<model>.json`，对每个候选检查点重新运行此工具集。
