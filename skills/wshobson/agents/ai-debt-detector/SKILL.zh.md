# AI债务检测器

## 概述

AI代理生成的代码虽然能通过正常路径测试，但会隐藏债务：缺少错误处理、遗留资源、忽略失败模式、凭空编造的依赖包、无声的架构漂移。这项技能强制进行针对性审计，找出AI代理在哪些具体模式上出错。

## 使用场景

- 任何AI代码生成会话后（生成20行以上代码时）
- 合并AI生成的PR前
- 代码能运行但感觉不对劲时
- 氛围编码冲刺后（此时债务累积最快）
- 代理声称完成但未展示验证结果时

## 流程

代码生成后，扫描以下AI特有的债务模式：

1. **失败模式** - 当此功能失败时会发生什么？
   - 网络超时？磁盘满？权限拒绝？空输入？
   - 是否有try/catch？是否捕获特定错误或吞掉所有错误？
   - 失败时是否清理资源？（流关闭、连接释放、临时文件删除）

2. **遗留资源** - 创建了但未清理的资源有哪些？
   - 临时文件、事件监听器、定时器、订阅、连接
   - 每次打开/创建操作是否都有对应的清理/释放/关闭调用？
   - React中：每个addEventListener是否在清理时都有removeEventListener？

3. **边界情况** - 哪些输入会使其崩溃？
   - 空数组/字符串？null/undefined？多MB输入？Unicode？并发调用？
   - 代码是否假设正常路径？（AI几乎总是这样假设）

4. **凭空编造的依赖** - 所有导入是否真实存在？
   - package.json/requirements.txt中是否包含所有包？
   - API方法是否真实存在？（AI会编造听起来合理的不存在方法）
   - 该库的最新版本是否仍然导出这个函数？

5. **架构漂移** - 是否符合项目的模式？
   - 错误处理风格是否与现有代码一致？
   - 是否使用项目已建立的工具（而不是重新发明）？
   - 是否遵循文件结构约定？

## 红旗（立即停止并修复）

- `catch (e) {}` 或 `catch (e) { console.log(e) }` - 吞掉错误
- 资源打开时没有finally块
- `// TODO: handle error` - AI的回避方式
- 从项目中不存在的路径导入
- 设置了超时但超时时没有中止/清理
- 打开了数据库连接但从未归还给连接池

## 常见错误

- 相信编译意味着正确性（编译检查语法，不检查逻辑）
- 只审查diff，不检查AI未生成的部分（遗漏错误路径）
- 假设AI使用了正确的库版本（它经常使用已弃用的API）
- 因为垃圾回收会处理遗留资源而跳过遗留资源检查（连接、监听器、定时器不会）

## 存在原因

AI代理系统性地优化"看起来正确"和"通过正常路径测试"。它们在遗漏失败模式、遗留资源和凭空编造依赖方面的出错率显著高于人工代码。这项技能强制进行审计，找出这些特定的盲点。
