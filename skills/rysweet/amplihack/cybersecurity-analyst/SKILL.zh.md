# 网络安全分析师技能

## 目的

通过网络安全的纪律视角分析事件，应用严格的安全框架（CIA三元组、纵深防御、零信任）、威胁建模方法（STRIDE、PASTA、VAST）、攻击面分析以及行业标准（NIST、ISO 27001、MITRE ATT&CK）来理解安全风险、识别漏洞、评估威胁行为者和攻击向量、评估防御控制并推荐风险缓解策略。

## 何时使用此技能

- **安全事件分析**：调查安全漏洞、数据泄露、勒索软件攻击、内部威胁
- **漏洞评估**：识别系统、应用程序、网络、流程中的弱点
- **威胁建模**：分析新系统或变更的潜在攻击向量及威胁行为者
- **安全架构审查**：评估设计决策对安全的影响和差距
- **风险评估**：使用CVSS、FAIR等框架量化并优先排序安全风险
- **合规性分析**：评估对安全标准（SOC 2、PCI-DSS、HIPAA、GDPR）的遵守情况
- **事件响应计划**：设计检测、遏制、清除和恢复策略
- **安全态势评估**：评估整体防御能力和成熟度
- **代码安全审查**：识别软件实现中的安全漏洞

## 核心理念：安全思维

网络安全分析基于基本原则：

**纵深防御**：没有单一的安全控制是完美的。分层部署多个独立控制，以便一个控制被攻破不会导致整个系统被攻破。

**假设被攻破**：现代安全假设攻击者将突破边界防御。设计系统以最小化损害并能够在（不是如果）发生（被攻破）时检测到。

**最小权限**：仅授予执行合法功能所需的最低访问权限。每项额外权限都是被利用的机会。

**零信任**：永不信任，始终验证。明确验证，使用最小权限访问，并假设无论网络位置如何都可能被攻破。

**安全设计**：安全不能事后附加。它必须从一开始就是架构和实现的基本要素。

**CIA三元组**：安全保护三个属性——机密性（仅授权访问）、完整性（仅授权修改）、可用性（在需要时可以访问）。

**基于威胁的防御**：根据对实际威胁行为者、其能力、动机和策略的理解（威胁情报）来制定防御优先级。

**基于风险的方法**：完美安全是不可能的。根据风险（可能性×影响）优先考虑安全投资，以最大化每美元的安全支出。

## 理论基础（可扩展）

### 基础 1：CIA 三元组（经典安全模型）

**组成部分**：

**机密性**：信息仅对授权实体可访问

- 保护机制：加密、访问控制、身份验证
- 威胁：窃听、数据盗窃、未经授权的披露
- 示例违规：数据泄露、密码盗窃、内部人员泄露

**完整性**：信息仅由授权实体以授权方式修改

- 保护机制：哈希、数字签名、访问控制、版本控制
- 威胁：篡改、未经授权的修改、恶意软件
- 示例违规：数据库操作、中间人攻击、勒索软件加密

**可用性**：信息及系统在需要时对授权实体可访问

- 保护机制：冗余、备份、DDoS 缓解、事件响应
- 威胁：拒绝服务、勒索软件、系统破坏
- 示例违规：DDoS 攻击、勒索软件、基础设施故障

**扩展**：

- **真实性**：实体的身份验证和信息的来源
- **不可否认性**：不能否认已采取行动
- **可问责性**：行动可追溯到实体

**应用**：每次安全分析都应识别CIA三元组的哪些方面存在风险以及控制如何保护每个方面。

**来源**：

- [CIA 三元组 - 维基百科](https://en.wikipedia.org/wiki/Information_security#Key_concepts)
- [NIST 网络安全框架](https://www.nist.gov/cyberframework)

### 基础 2：纵深防御（分层安全）

**原则**：部署多层安全控制，以便一个层级的被攻破不会导致整个系统被攻破。

**历史起源**：军事防御策略——多层同心边界防御

**安全层级**：

1. **物理**：设施访问控制、上锁的服务器室
2. **网络**：防火墙、网络分段、IDS/IPS
3. **主机**：端点保护、主机防火墙、补丁管理
4. **应用**：输入验证、安全编码、身份验证
5. **数据**：静态和动态加密、DLP、令牌化
6. **人员**：安全意识培训、钓鱼模拟

**关键洞察**：冗余不是浪费——它是弹性。即使攻击者绕过防火墙，他们仍然面临身份验证、授权、监控、加密和检测控制。

**应用**：安全架构应具有多个独立的防御层级来保护关键资产。

**局限**：如果层级未维护或相互依赖，则可能造成复杂性并产生虚假的安全感。

**来源**：

- [纵深防御 - NSA](https://www.nsa.gov/Press-Room/Cybersecurity-Advisories-Guidance/)
- [分层安全 - CISA](https://www.cisa.gov/topics/cybersecurity-best-practices)

### 基础 3：零信任架构

**核心原则**：无论网络位置如何，“永不信任，始终验证”

**与传统边界模型的对比**：传统安全假设内部网络是可信的（“城堡和护城河”）。零信任假设没有网络位置是可信的。

**关键原则**（NIST SP 800-207）：

1. **明确验证**：始终基于所有可用数据点进行身份验证和授权
2. **最小权限访问**：使用即时访问和足够权限限制用户访问
3. **假设被攻破**：最小化影响范围并分段访问；验证端到端加密

**组件**：

- **以身份为中心的安全**：身份成为新的边界
- **微分段**：网络划分为具有独立控制的小区域
- **持续验证**：身份验证和授权是持续的，不是一次性的
- **数据为中心**：保护数据本身，而不仅仅是围绕它的边界

**驱动因素**：

- 云服务采用（没有明确的边界）
- 远程工作（用户位于传统边界之外）
- 高级攻击（边界漏洞常见）

**应用**：现代安全架构应采用零信任原则设计，特别是针对云和混合环境。

**来源**：

- [NIST SP 800-207：零信任架构](https://csrc.nist.gov/publications/detail/sp/800-207/final)
- [零信任 - 微软安全](https://www.microsoft.com/en-us/security/business/zero-trust)

### 基础 4：威胁建模

**定义**：结构化方法，用于识别和优先排序系统面临的潜在威胁

**目的**：在设计阶段主动识别安全问题，此时修复成本最低

**优势**：

- 在实施前发现漏洞
- 优先考虑安全工作
- 向利益相关者传达风险
- 指导安全测试

**常见方法**：

**STRIDE**（微软）：

- **S**poofing identity（身份欺骗）
- **T**ampering with data（数据篡改）
- **R**epudiation（抵赖）
- **I**nformation disclosure（信息泄露）
- **D**enial of service（拒绝服务）
- **E**levation of privilege（权限提升）

**PASTA**（攻击模拟和威胁分析流程）：

- 七阶段风险中心方法
- 与业务目标与技术需求保持一致

**VAST**（可视化、敏捷和简单威胁建模）：

- 可扩展于敏捷开发
- 两种类型：应用程序威胁模型和操作威胁模型

**应用**：用于新功能、架构变更或安全审查的威胁建模。

**来源**：

- [威胁建模 - OWASP](https://owasp.org/www-community/Threat_Modeling)
- [STRIDE 威胁模型 - 微软](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-threats)

### 基础 5：MITRE ATT&CK 框架

**描述**：基于真实世界观察的对手战术和技术知识库

**目的**：了解攻击者如何运作，以指导防御、检测和威胁搜寻

**结构**：

- **战术**：高级目标（例如，初始访问、执行、持久化、权限提升）
- **技术**：实现战术的方法（例如，网络钓鱼、利用公共应用程序）
- **子技术**：特定实现
- **程序**：特定攻击者行为

**14 个战术**（企业矩阵）：

1. 探查
2. 资源开发
3. 初始访问
4. 执行
5. 持久化
6. 权限提升
7. 防御规避
8. 凭据访问
9. 发现
10. 横向移动
11. 收集
12. 命令与控制
13. 数据外泄
14. 影响

**应用**：

- 将防御控制映射到 ATT&CK 技术
- 识别检测差距
- 威胁情报共享
- 红队/紫队演练

**价值**：描述攻击者行为的通用语言；威胁知情防御的基础

**来源**：

- [MITRE ATT&CK](https://attack.mitre.org/)
- [ATT&CK 导航器](https://mitre-attack.github.io/attack-navigator/)

## 核心分析框架（可扩展）

### 框架 1：攻击面分析

**定义**：识别和评估未经授权用户可以进入或从系统中提取数据的所有点

**组成部分**：

**攻击面元素**：

- **网络攻击面**：暴露的端口、服务、协议
- **软件攻击面**：应用程序、API、Web 界面
- **人员攻击面**：用户、管理员、社会工程学目标
- **物理攻击面**：设施访问、硬件访问

**攻击向量**：攻击者用来利用攻击面的方法

- 网络基础：端口扫描、协议漏洞、中间人攻击
- Web 基础：SQL 注入、XSS、CSRF、身份验证绕过
- 电子邮件基础：网络钓鱼、恶意附件、凭证收集
- 物理：盗窃、未经授权的访问、邪恶女巫攻击
- 社会工程学：借口、诱饵、尾随

**分析过程**：

1. **枚举**：列出所有入口点和资产
2. **分类**：按类型和关键性分类
3. **评估**：评估可利用性和影响
4. **优先级**：按风险排序
5. **减少**：最小化不必要的暴露

**指标**：

- 暴露的服务数量
- 面向互联网的应用程序数量
- 特权账户数量
- 暴露于不受信任输入的代码行数

**应用**：减少攻击面是基本的防御策略。消除不必要的暴露。

**来源**：

- [攻击面分析 - OWASP](https://owasp.org/www-community/Attack_Surface_Analysis_Cheat_Sheet)
- [减少攻击面 - 微软](https://learn.microsoft.com/en-us/windows/security/threat-protection/windows-defender-application-control/microsoft-recommended-block-rules)

### 框架 2：风险评估框架

**目的**：量化并优先排序安全风险，以指导资源分配

**常见框架**：

**CVSS**（通用漏洞评分系统）：

- 评估漏洞严重性的标准
- 基于可利用性、影响、范围评分 0-10
- 基础分数（固有特征）+ 时间分数 + 环境分数
- 广泛使用，但被批评未能捕捉特定环境中的实际风险

**FAIR**（信息风险因素分析）：

- 定量风险框架
- 风险 = 损失事件频率 × 损失幅度
- 使安全投资的成本效益分析成为可能
- 更复杂，但提供以美元计的风险数字

**NIST 风险管理框架**（RMF）：

- 七个步骤：准备、分类、选择、实施、评估、授权、监控
- 将安全控制与风险管理联系起来
- 美国联邦机构使用

**定性 vs. 定量**：

- **定性**：高/中/低风险评级（更简单、更快、主观）
- **定量**：数值风险值（更复杂、客观、需要数据）

**应用**：风险评估提供优先级。并非所有漏洞都同等重要——专注于最高风险。

**来源**：

- [CVSS](https://www.first.org/cvss/)
- [FAIR 协会](https://www.fairinstitute.org/)
- [NIST RMF](https://csrc.nist.gov/projects/risk-management)

### 框架 3：安全控制框架

**目的**：实现安全目标的结构化安全控制集

**主要框架**：

**NIST 网络安全框架**：

- 五个核心功能：识别、保护、检测、响应、恢复
- 非规定性——灵活适用于不同组织
- 广泛采用于各行业和国际

**NIST SP 800-53**（安全和隐私控制）：

- 为联邦系统提供的全面安全控制目录
- 20 个控制组（访问控制、事件响应等）
- 详细的实施指南

**CIS 控制**（互联网安全中心）：

- 18 个优先级安全控制
- 基于组织成熟度的实施组（IG1、IG2、IG3）
- 可操作和可衡量

**ISO/IEC 27001**：

- 信息安全管理系统国际标准
- 14 个控制域，114 个控制
- 提供认证

**应用**：使用框架来：

- 确保全面覆盖
- 基准安全态势
- 与利益相关者沟通
- 满足合规性要求

**来源**：

- [NIST 网络安全框架](https://www.nist.gov/cyberframework)
- [CIS 控制](https://www.cisecurity.org/controls)
- [ISO 27001](https://www.iso.org/isoiec-27001-information-security.html)

### 框架 4：事件响应生命周期

**定义**：处理安全事件的结构化方法

**标准模型**（NIST SP 800-61）：

**阶段 1：准备**

- 建立 IR 能力、工具、剧本
- 培训和演练
- 沟通计划

**阶段 2：检测和分析**

- 监控和警报
- 事件分类和优先级排序
- 初始调查
- 范围确定

**阶段 3：遏制、清除和恢复**

- **遏制**：短期和长期停止传播
- **清除**：从环境中移除威胁
- **恢复**：将系统恢复到正常操作

**阶段 4：事后活动**

- 经验教训
- 证据保存
- 事件报告
- 流程改进

**关键概念**：

- **剧本**：针对常见事件类型的预定义程序
- **妥协指标**（IoC）：指示恶意活动的工件
- **证据链**：证据处理程序
- **沟通**：内部和外部利益相关者、法律、公关

**指标**：

- 平均检测时间（MTTD）
- 平均响应时间（MTTR）
- 平均遏制时间（MTTC）

**应用**：有效的事件响应可最小化损害，减少恢复时间，并捕获学习。

**来源**：

- [NIST SP 800-61：计算机安全事件处理指南](https://csrc.nist.gov/publications/detail/sp/800-61/rev-2/final)
- [SANS 事件响应](https://www.sans.org/incident-response/)

### 框架 5：安全开发生命周期（SDL）

**目的**：将安全集成到软件开发过程中

**微软 SDL 阶段**：

1. **培训**：开发人员安全培训
2. **要求**：定义安全要求和隐私要求
3. **设计**：威胁建模、攻击面减少、纵深防御
4. **实施**：安全编码标准、代码分析工具
5. **验证**：安全测试（SAST、DAST、渗透测试）
6. **发布**：最终安全审查、事件响应计划
7. **响应**：如果发现漏洞，执行事件响应计划

**关键实践**：

- **静态代码分析（SAST）**：分析源代码中的漏洞  
- **动态分析（DAST）**：测试运行中的应用程序  
- **依赖项扫描**：检查第三方库中的已知漏洞  
- **渗透测试**：模拟真实攻击  
- **安全专家**：将安全专业知识嵌入开发团队  

**OWASP SAMM**（软件保障成熟度模型）：  

- 适用于安全软件开发成熟度模型  
- 五个业务功能：治理、设计、实施、验证、运营  
- 每个功能分为三个成熟度级别  

**应用**：安全必须在整个开发生命周期中集成，而不仅仅是在最后阶段。  

**来源**：  

- [Microsoft SDL](https://www.microsoft.com/en-us/securityengineering/sdl)  
- [OWASP SAMM](https://owaspsamm.org/)

## 方法论方法（可扩展）  

### 方法 1：威胁情报分析  

**目的**：了解对手、其能力、战术和目标，以指导防御  

**威胁情报类型**：  

**战略**：为高管提供高层趋势  

- APT 组织活动和动机  
- 地缘政治网络威胁  
- 行业特定威胁格局  

**战术**：为安全运营提供战役级信息  

- 当前攻击活动  
- 威胁行为者的战术技术（TTP）  
- 恶意软件家族  

**战术**：用于即时防御的技术指标  

- IP 地址、域名、文件哈希值  
- YARA 规则、Snort 签名  
- 被利用的 CVE  

**分析流程**：  

1. **收集**：从内部来源、威胁源、开源情报（OSINT）、暗网收集数据  
2. **处理**：标准化、关联、去重  
3. **分析**：上下文化、归因、评估意图和能力  
4. **传播**：以可操作的格式与相关团队共享  
5. **反馈**：评估有效性并改进  

**框架**：  

- **钻石模型**：对手、能力、基础设施、受害者  
- **杀伤链**：侦察 → 武器化 → 交付 → 利用 → 安装 → 二次控制（C2）→ 对目标采取行动  
- **MITRE ATT&CK**：将观察到的技术映射到 ATT&CK 矩阵  

**应用**：威胁情报使主动、基于威胁的防御成为可能，而不是通用的安全措施。  

**来源**：  

- [CISA 威胁情报](https://www.cisa.gov/topics/cyber-threats-and-advisories)  
- [威胁情报 - SANS](https://www.sans.org/cyber-security-courses/cyber-threat-intelligence/)  

### 方法 2：渗透测试  

**定义**：授权的模拟攻击，以评估系统的安全性  

**类型**：  

**黑盒**：无先验知识（模拟外部攻击者）  

**灰盒**：部分知识（模拟内部人员或受感染的用户）  

**白盒**：完全知识（全面的安全评估）  

**阶段**（渗透测试执行标准）：  

1. **预参与**：范围、参与规则、法律协议  
2. **情报收集**：开源情报（OSINT）、网络扫描、服务枚举  
3. **威胁建模**：识别潜在的攻击向量  
4. **漏洞分析**：识别可利用的弱点  
5. **利用**：尝试利用漏洞  
6. **后利用**：评估影响、横向移动、权限提升  
7. **报告**：记录发现、证明影响、提供修复指南  

**专业类型**：  

- **Web 应用渗透测试**：关注 OWASP Top 10  
- **网络渗透测试**：内部和外部网络  
- **社会工程**：网络钓鱼、语音钓鱼、物理入侵  
- **无线渗透测试**：WiFi 安全评估  

**红队与渗透测试**：  

- **渗透测试**：尽可能多地发现漏洞  
- **红队**：目标导向（例如，访问特定数据）、模拟 APT、测试检测和响应  

**应用**：定期渗透测试可在攻击者之前验证控制措施的有效性并识别差距。  

**来源**：  

- [渗透测试执行标准](http://www.pentest-standard.org/)  
- [OWASP 测试指南](https://owasp.org/www-project-web-security-testing-guide/)  

### 方法 3：安全架构审查  

**目的**：评估系统设计的安全性并识别架构漏洞  

**审查维度**：  

**结构分析**：  

- 信任边界和数据流  
- 身份验证和授权架构  
- 网络分段和隔离  
- 数据分类和保护  

**威胁建模**：  

- 应用 STRIDE 或其他方法  
- 识别攻击树  
- 评估已识别威胁的缓解措施  

**控制评估**：  

- 将控制映射到 CIA 三元组  
- 评估纵深防御层  
- 识别单点故障  

**合规性审查**：  

- 对照安全框架（NIST、CIS、ISO）检查  
- 监管要求（PCI-DSS、HIPAA、SOC 2）  

**技术评估**：  

- 密码学实现  
- 安全协议  
- 补丁管理方法  
- 密钥管理  

**分析问题**：  

- 信任边界是什么？  
- 敏感数据如何流动？  
- 身份验证/授权如何强制执行？  
- 如果组件 X 被攻破会发生什么？  
- 安全假设是否记录并验证？  

**输出**：  

- 带有安全注释的架构图  
- 威胁模型  
- 风险评估  
- 修复建议  

**应用**：设计阶段进行架构审查可防止生产中昂贵的安全问题。  

### 方法 4：漏洞评估和管理  

**目的**：系统性地识别、分类、优先级排序和修复安全弱点  

**流程**：  

**阶段 1：发现**  

- 资产清单（我们有什么？）  
- 漏洞扫描（自动工具）  
- 手动安全测试  
- 代码审查（静态分析）  

**阶段 2：评估**  

- 按类型和严重程度对漏洞进行分类  
- 评估可利用性（是否存在利用代码？是否正在被利用？）  
- 确定影响（哪些数据/系统面临风险？）  
- 计算风险评分（CVSS、上下文因素）  

**阶段 3：优先级排序**  

- 按风险排序（可能性 × 影响）  
- 考虑威胁情报（是否在野外被利用？）  
- 受影响资产的业务关键性  
- 修复复杂性  

**阶段 4：修复**  

- 补丁（理想情况）  
- 配置更改  
- 补偿性控制（如果无法补丁）  
- 接受风险（记录并批准）  

**阶段 5：验证**  

- 重新扫描以确认修复  
- 更新漏洞数据库  
- 跟踪指标（修复时间、漏洞密度）  

**挑战**：  

- 告警疲劳（发现过多）  
- 假阳性  
- 补丁中断  
- 遗留系统  

**最佳实践**：  

- 基于风险的优先级排序（不只是 CVSS）  
- 基于服务等级协议（SLA）的修复（关键：7 天，高：30 天等）  
- 尽可能自动化  
- 跟踪趋势和指标  

**应用**：持续漏洞管理是必要的卫生措施。无法修复不了解的问题。  

**来源**：  

- [NIST SP 800-40：补丁和漏洞管理](https://csrc.nist.gov/publications/detail/sp/800-40/rev-4/final)  

### 方法 5：安全监控和检测工程  

**目的**：设计和运行检测恶意活动的功能  

**组件**：  

**数据源**：  

- 网络流量（NetFlow、完整数据包捕获）  
- 端点日志（进程创建、文件访问、注册表更改）  
- 身份验证日志（登录、权限提升）  
- 应用日志（错误、事务）  
- 云 API 和审计日志  

**检测机制**：  

**基于签名的**：已知恶意模式（防病毒、IDS 签名）  

- 优点：低误报率，快速  
- 缺点：仅检测已知威胁  

**基于异常的**：偏离基线行为  

- 优点：可检测新型攻击  
- 缺点：高误报率，需要调整  

**基于启发式的**：基于攻击者行为模式的规则  

- 优点：检测已知攻击的变体  
- 缺点：需要安全专业知识创建规则  

**基于威胁情报的**：与已知 IoC 匹配  

- 优点：利用集体知识  
- 缺点：被动（在妥协后发现指标）  

**检测开发**：  

1. 了解攻击技术（MITRE ATT&CK）  
2. 确定捕获该技术的数据源  
3. 开发检测逻辑  
4. 对真实阳性和假阳性进行测试  
5. 调整阈值和逻辑  
6. 记录检测和响应程序  
7. 监控有效性和迭代  

**SIEM 和 SOC**：  

- **SIEM**：聚合、关联和分析安全日志  
- **SOC**：安全运营中心——监控警报和响应事件的团队  

**指标**：  

- 检测覆盖率（覆盖的 ATT&CK 技术%）  
- 告警数量和质量  
- 误报率  
- 检测时间（MTTD）  

**应用**：无法响应未检测到的问题。投资与您面临的威胁相匹配的检测能力。  

**来源**：  

- [检测工程 - Splunk](https://www.splunk.com/en_us/blog/learn/detection-engineering.html)  
- [Sigma 规则](https://github.com/SigmaHQ/sigma)

## 分析评分标准  

### 需要检查的内容  

**资产和数据**：  

- 存在哪些敏感数据？（个人身份信息、凭证、商业机密、财务数据）  
- 存储在哪里、处理在哪里、传输在哪里？  
- 谁可以访问？  
- 如果被攻破，业务影响是什么？（机密性、完整性、可用性）  

**攻击面**：  

- 哪些系统暴露在互联网上？  
- 攻击者可能的入口点是什么？  
- 需要哪些身份验证？  
- 存在哪些第三方依赖？  

**威胁行为者**：  

- 谁可能针对此？（国家行为者、网络犯罪分子、黑客、内部人员）  
- 他们的能力和动机是什么？  
- 他们通常使用哪些战术？  
- 存在哪些威胁情报？  

**漏洞**：  

- 已知软件漏洞（CVE）？  
- 配置弱点？  
- 架构安全缺陷？  
- 代码级漏洞？  
- 人类漏洞（网络钓鱼易感性）？  

**现有控制**：  

- 哪些安全控制正在实施？  
- 是否遵循纵深防御原则？  
- 是否正确配置和维护？  
- 存在哪些检测和响应能力？  

### 需要提出的问题  

**威胁问题**：  

- 可能发生什么？  
- 最可能的攻击向量是什么？  
- 哪些威胁行为者可能针对此？  
- 他们的目标和能力是什么？  
- 哪些历史事件相关？  

**漏洞问题**：  

- 存在哪些弱点？  
- 它们有多容易利用？  
- 如果被利用，影响是什么？  
- 是否存在已知漏洞或主动利用？  
- 漏洞可以多快修复？  

**控制问题**：  

- 哪些保护措施正在实施？  
- 它们有多有效？  
- 防御覆盖范围存在哪些差距？  
- 能否绕过控制？  
- 如何检测恶意活动？  

**风险问题**：  

- 攻击的可能性有多大？  
- 潜在影响是什么？  
- 整体风险级别是什么？  
- 与组织的风险偏好相比如何？  
- 存在哪些风险处理选项？（缓解、接受、转移、避免）  

**合规问题**：  

- 适用哪些法规或标准？  
- 是否满足安全要求？  
- 哪些证据证明合规？  
- 存在哪些差距？  

### 需要考虑的因素  

**技术因素**：  

- 系统架构和设计  
- 技术堆栈和版本  
- 配置和加固  
- 密码学实现  
- 网络拓扑和分段  

**组织因素**：  

- 安全成熟度和文化  
- 可用资源和预算  
- 风险容忍度  
- 监管环境  
- 业务关键性  

**威胁格局**：  

- 当前威胁行为者活动  
- 新兴攻击技术  
- 行业特定威胁  
- 地缘政治因素  

**运营因素**：  

- 补丁管理流程  
- 事件响应能力  
- 安全监控和检测  
- 安全意识和培训  
- 第三方风险管理  

### 历史类比  

- 类似的安全事件  
- 相似的漏洞利用  
- 行业特定攻击模式  
- 主要漏洞的教训  
- 威胁行为者战术的演变  

### 需要探索的影响  

**即时安全影响**：  

- 机密性：数据泄露风险  
- 完整性：数据篡改或损坏风险  
- 可用性：服务中断风险  
- 财务：勒索、恢复成本、罚款  

**更广泛的影响**：  

- 声誉损害  
- 法律和监管后果  
- 客户信任侵蚀  
- 竞争劣势  
- 系统性风险（如果处于关键基础设施）  

**战略影响**：  

- 需要的安全架构变更  
- 安全项目成熟度差距  
- 资源分配和优先级排序  
- 风险管理方法

## 逐步分析过程  

### 第 1 步：定义范围和背景  

**行动**：  

- 明确要分析的系统、应用程序或事件  
- 确定边界和接口  
- 确定利益相关者和他们的安全要求  
- 了解业务背景和关键性  
- 收集相关文档（架构图、数据流、政策）  

**输出**：  

- 范围声明  
- 资产清单  
- 利益相关者列表  
- 业务背景理解  

### 第 2 步：识别资产和数据  

**行动**：  

- 列出关键资产（系统、数据、服务）  
- 按敏感性分类数据（公开、内部、机密、限制）  
- 映射数据流（数据创建、存储、处理、传输、销毁）  
- 识别皇冠珠宝（最宝贵的资产）  

**输出**：  

- 带有关键性评级的资产清单  
- 数据分类矩阵  
- 数据流图  
- 皇冠珠宝列表  

### 第 3 步：分析攻击面  

**行动**：  

- 枚举所有入口点（API、Web 界面、网络服务、物理访问）  
- 识别信任边界（未受信任的输入跨越到受信任区域）  
- 映射身份验证和授权点  
- 识别依赖项（第三方服务、库、供应商）  

**输出**：  

- 攻击面图  
- 信任边界图  
- 入口点清单  
- 依赖项列表  

### 第 4 步：进行威胁建模  

**行动**：  

- 选择威胁建模方法（STRIDE、PASTA 等）  
- 识别潜在威胁行为者和他们的目标  
- 列出每个资产的潜在攻击向量  
- 创建攻击树以显示攻击路径  
- 映射到 MITRE ATT&CK 技术  

**输出**：  

- 威胁模型文档  
- 威胁行为者画像  
- 攻击树图  
- ATT&CK 技术映射  

### 第 5 步：识别漏洞  

**行动**：  

- 审查正在使用的技术中已知的 CVE  
- 分析配置与安全基准（CIS、STIGs）  
- 审查架构中的安全设计缺陷  
- 考虑代码级漏洞（如适用）  
- 评估人类漏洞（网络钓鱼易感性、权限滥用）  

**输出**：  

- 漏洞清单  
- CVSS 评分或风险评级  
- 配置差距分析  
- 架构安全问题  

### 第 6 步：评估现有控制  

**行动**：  

- 跨所有层（网络、主机、应用、数据）清点安全控制  
- 将控制映射到威胁（哪些威胁由控制缓解？）  
- 评估控制有效性（是否正确配置？维护？监控？）  
- 识别控制差距（威胁缺乏充分缓解）  
- 评估检测和响应能力  

**输出**：  

- 控制清单  
- 威胁-控制映射矩阵  
- 控制有效性评估  
- 检测覆盖差距  

### 第 7 步：分析风险  

**行动**：  

- 对每个威胁-漏洞组合，估计可能性和影响  
- 计算风险评分（定性或定量）  
- 优先级排序风险  
- 与组织风险容忍度比较  
- 考虑风险相互依赖和级联效应  

**输出**：  

- 风险登记册  
- 风险热图  
- 优先级排序的风险列表  
- 风险接受建议  

### 第 8 步：评估检测和响应  

**行动**：

- 评估恶意活动将被检测到的范围
- 评估不同攻击场景下的平均检测时间（MTTD）
- 审查事件响应计划和手册
- 评估事件响应团队的能力
- 确定检测或响应中的差距

**输出**：

- 检测覆盖范围评估
- MTTD 估计
- 事件响应能力评估
- 检测和响应差距

### 第 9 步：制定修复建议

**行动**：

- 针对已识别的风险提出缓解措施（预防性、探测性、纠正性）
- 根据风险降低程度和实施工作量进行优先级排序
- 在直接缓解不切实际的情况下考虑补偿性控制措施
- 估算成本和实施时间表
- 记录未缓解风险的风险接受情况

**输出**：

- 修复路线图
- 优先级建议列表
- 成本效益分析
- 风险接受文档

### 第 10 步：考虑合规性要求

**行动**：

- 确定适用的法规和标准
- 将控制措施映射到合规性要求
- 记录合规性证据
- 确定合规性差距
- 建议为达到或维持合规性而采取的行动

**输出**：

- 合规性矩阵
- 差距分析
- 证据文档
- 合规性修复计划

### 第 11 步：综合与报告

**行动**：

- 为不同受众（高管、技术团队、合规性）总结关键发现
- 提供清晰的风险评估和建议
- 包括指标和关键绩效指标（KPI）
- 记录假设和局限性
- 与负责人共同制定包含时间表的行动计划

**输出**：

- 高管摘要
- 技术发现报告
- 修复路线图
- 合规性摘要

## 使用示例

### 示例 1：安全事件 -勒索软件攻击

**事件**：组织遭受勒索软件攻击；文件被加密，勒索软件要求支付赎金

**分析**：

**第 1 步 - 范围和背景**：

- 受影响的系统：文件服务器、工作站、备份系统
- 业务影响：运营中断，数据不可用
- 关键：了解勒索软件变种、加密范围、攻击者访问方式

**第 2 步 - 资产**：

- 珠宝：客户数据库、财务记录、知识产权
- 状态：文件被加密，可用性受损

**第 3 步 - 攻击面分析**：

- 初始访问向量：可能是钓鱼邮件或易受攻击的 RDP 端点
- 横向移动：SMB、凭证窃取

**第 4 步 - 威胁建模（事后）**：

- 威胁者：可能是网络犯罪团伙（经济动机）
- ATT&CK 映射：
  - 初始访问：钓鱼或利用面向公众的应用程序
  - 执行：用户执行或客户端执行利用
  - 持久化：注册表运行键、计划任务
  - 权限提升：利用权限提升
  - 凭证访问：凭证转储
  - 横向移动：SMB/Windows 管理员共享
  - 影响：加密数据以造成影响

**第 5 步 - 漏洞**：

- 钓鱼易感性（无邮件过滤、用户培训不足）
- 未修补的 RDP 漏洞
- 弱密码或凭证重用
- 网络分段不足（勒索软件易于传播）
- 备份漏洞（备份也被加密）

**第 6 步 - 控制评估**：

- 缺失：邮件安全网关、EDR、MFA
- 不足：网络分段、备份隔离、补丁管理
- 失败：防病毒软件未检测到勒索软件

**第 7 步 - 风险分析**：

- 影响：高（业务中断、数据丢失、赎金要求、声誉损害）
- 可能性：高（已证实——事件已发生）
- 剩余风险：关键（若无改进，可能重复发生）

**第 8 步 - 检测和响应**：

- 检测：直到加密开始才失败（无 EDR、日志有限）
- MTTD：数小时至数天（太慢）
- 响应：无手册、响应不协调
- 差距：无 IR 团队、无沟通计划、无法律/公关协调

**第 9 步 - 建议（按优先级）**：

_立即（数小时至数天）_：

1. 隔离受影响的系统（限制传播）
2. 确定勒索软件变种并检查是否有解密工具
3. 如无内部能力，则聘请事件响应公司
4. 立即不要支付赎金（先评估替代方案）
5. 通知法律、保险，可能通知执法部门

_短期（数天至数周）_：

1. 如有可用且未受损的备份，则从备份恢复
2. 在所有端点上部署 EDR
3. 为所有远程访问实施 MFA
4. 进行取证调查以确定根本原因和范围
5. 制定和测试 IR 手册

_中期（数周至数月）_：

1. 网络分段（防止横向移动）
2. 邮件安全网关（阻止钓鱼）
3. 高级访问管理（限制凭证盗窃）
4. 安全意识培训（减少钓鱼成功率）
5. 备份加固（离线或不可变备份）

_长期（数月至一年）_：

1. 安全成熟度评估和路线图
2. 24/7 SOC 或 MDR 服务
3. 渗透测试和红队演练
4. 综合漏洞管理计划

**第 10 步 - 合规性**：

- 监管通知要求（GDPR、州泄露法律等）
- 车载保险索赔
- 为审计员记录事件

**第 11 步 - 综合**：

- 根本原因：钓鱼/RDP 利用 + 检测不足 + 分段不足 + 备份漏洞的组合
- 关键教训：纵深防御失败——多个控制措施失败导致攻击成功
- 优先级：立即控制和恢复，然后建立探测性和预防性控制
- 成本：赎金要求 + 停机时间 + 恢复 + 修复 + 声誉损害（可能达数百万）

### 示例 2：漏洞评估 - 新 Web 应用程序发布

**事件**：组织计划发布面向客户的 Web 应用程序；要求进行发布前安全审查

**分析**：

**第 1 步 - 范围**：

- 应用程序：电子商务 Web 应用程序
- 用户：外部客户
- 数据：个人身份信息（PII）、支付信息、订单历史
- 关键性：高（创收、客户信任）

**第 2 步 - 资产**：

- 客户 PII 和支付数据（机密性、完整性关键）
- 库存和定价数据（完整性、可用性关键）
- 应用程序可用性（收入影响）

**第 3 步 - 攻击面**：

- Web 界面（面向公众）
- API（移动应用程序、第三方集成）
- 管理门户（内部用户）
- 支付处理程序集成
- 第三方库和依赖项

**第 4 步 - 威胁建模（STRIDE）**：

**欺骗**：

- 威胁：攻击者冒充用户或管理员
- 缓解措施：强身份验证、MFA、会话管理

**篡改**：

- 威胁：攻击者修改价格、订单或用户数据
- 缓解措施：输入验证、授权检查、完整性控制

**抵赖**：

- 威胁：用户否认下订单
- 缓解措施：审计日志、交易签名

**信息泄露**：

- 威胁：攻击者访问其他用户的 PII 或支付信息
- 缓解措施：授权检查、加密、安全会话管理

**拒绝服务**：

- 威胁：攻击者使应用程序过载
- 缓解措施：速率限制、DDoS 保护、可扩展基础设施

**权限提升**：

- 威胁：用户获得管理员访问权限
- 缓解措施：最小权限、安全授权、权限分离

**第 5 步 - 漏洞（OWASP Top 10 分析）**：

1. **破坏访问控制**：检查 IDOR 漏洞、水平/垂直权限提升
2. **加密失败**：验证静态和传输中的加密、密钥管理
3. **注入**：测试 SQL 注入、XSS、命令注入
4. **不安全设计**：检查安全设计缺陷、威胁模型差距
5. **安全配置错误**：检查默认凭证、不必要的功能、详细错误
6. **易受攻击的组件**：扫描依赖项中的已知 CVE
7. **身份验证失败**：测试密码策略、会话管理、MFA
8. **软件/数据完整性**：验证供应链安全、未签名的更新
9. **日志失败**：确保安全事件记录、防止日志篡改
10. **SSRF**：测试服务器端请求伪造漏洞

**第 6 步 - 控制评估**：

_正面发现_：

- 所有连接使用 TLS 1.3
- 密码使用 bcrypt 哈希
- 使用输入验证框架
- CI/CD 中使用依赖项扫描

_已识别的差距_：

- 客户账户无 MFA
- 管理门户不在单独的域/网络
- 详细错误消息暴露堆栈跟踪
- API 端点无速率限制
- 一些第三方依赖项有已知 CVE
- 授权检查不足（IDOR 漏洞）
- 无 Web 应用程序防火墙（WAF）

**第 7 步 - 风险分析**：

_关键风险_：

- **IDOR 漏洞**：高可能性、高影响（数据泄露）
- **易受攻击的依赖项**：中等可能性、高影响（RCE 潜力）

_高风险_：

- **无速率限制**：高可能性、中等影响（爬取、暴力破解）
- **管理门户在同一域**：低可能性、高影响（凭证盗窃）

_中等风险_：

- **详细错误**：中等可能性、中等影响（信息泄露）
- **无 MFA**：低可能性（目前）、高影响（账户接管）

**第 8 步 - 检测和响应**：

- 日志：足够用于身份验证和交易
- SIEM 集成：尚未配置
- IR 手册：通用，需要应用程序特定场景
- 建议：配置 SIEM、创建应用程序特定 IR 手册、实施可疑模式警报

**第 9 步 - 建议（按风险优先级）**：

_发布前必须修复（关键）_：

1. 修复 IDOR 漏洞（实施授权检查）
2. 更新易受攻击的依赖项
3. 生产环境中移除详细错误消息
4. 在所有端点上实施速率限制

_发布前应修复（高）_：

1. 部署 WAF 并使用 OWASP 核心规则集
2. 分离管理门户（不同域、VPN/IP 限制）
3. 配置 SIEM 集成和警报

_发布后（中等）_：

1. 为客户账户实施 MFA
2. 增强日志记录（捕获更多安全事件）
3. 进行渗透测试
4. 建立漏洞悬赏计划

**第 10 步 - 合规性**：

- **PCI-DSS**：要求使用支付卡数据（使用令牌化、最小化持卡人数据环境）
- **GDPR/CCPA**：客户数据隐私要求（同意、数据最小化、泄露通知）
- **SOC 2**：如果 B2B 客户需要保证

**第 11 步 - 综合**：

- 应用程序具有坚实的基础（现代加密、输入验证、依赖项扫描）
- 关键问题必须在发布前解决（IDOR、易受攻击的依赖项）
- WAF 为 Web 威胁提供纵深防御
- 发布后：继续测试、漏洞悬赏、安全监控
- 走/不走的决定：不通过，直到关键问题解决

### 示例 3：安全架构审查 - 云迁移

**事件**：组织计划将本地应用程序迁移到 AWS；要求进行安全架构审查

**分析**：

**第 1 步 - 范围**：

- 迁移：50 多个应用程序，包括 Web 应用程序、API、数据库
- 目标：AWS（IaaS 和 PaaS 服务）
- 时间表：12 个月迁移
- 关键性：混合（部分业务关键应用程序）

**第 2 步 - 资产**：

- 当前在受控本地环境中应用程序和数据
- 关注：数据主权、合规性、共同责任模型

**第 3 步 - 攻击面变化**：

- **增加**：面向公众的云服务、云管理界面、更广的攻击面
- **减少**：物理访问威胁
- **新增**：云配置错误、IAM 漏洞、API 安全

**第 4 步 - 威胁建模（云特定）**：

_云特定威胁_：

- 账户妥协（被盗凭证、钓鱼）
- 配置错误存储桶（公共 S3 存储桶）
- 过度宽松的 IAM 策略
- 网络分段不足（VPC 设计）
- 通过云 API 的数据泄露
- 内部人员威胁（云管理员滥用）
- 供应链（受感染的云服务或依赖项）

_MITRE ATT&CK for Cloud_：

- 初始访问：有效账户、利用面向公众的应用程序
- 持久化：账户操作、创建 IAM 用户
- 权限提升：IAM 策略操作
- 防御规避：禁用云日志
- 凭证访问：代码/配置中未安全存储的凭证
- 发现：云服务发现
- 横向移动：使用替代身份验证材料
- 数据泄露：将数据传输到云账户

**第 5 步 - 漏洞（云环境）**：

- 缺乏云安全专业知识
- 本地思维（边界导向，而非零信任）
- 不明确的云 IAM 策略
- 无云配置管理（未使用 IaC）
- 无云安全态势管理（CSPM）

**第 6 步 - 控制评估（共同责任模型）**：

_AWS 责任_（云安全）：

- 物理安全
- 虚拟机安全
- 网络基础设施

_客户责任_（云内安全）：

- IAM 和访问控制
- 数据加密
- 网络配置（VPC、安全组）
- 应用程序安全
- 合规性

_建议控制_：

**身份和访问管理**：

- 实施使用 SCP（服务控制策略）的 AWS Organizations
- 强制执行所有用户的 MFA
- 使用 IAM 角色而不是长期凭证
- 最小权限原则
- 定期访问审查

**网络安全**：

- 使用公共/私有子网的 VPC 设计
- 安全组（状态防火墙）
- NACL（状态防火墙）
- 使用 AWS WAF 保护 Web 应用程序
- VPC 流量日志用于监控

**数据保护**：

- 静态加密（S3、EBS、使用 KMS 的 RDS）
- 传输加密（TLS）
- S3 存储桶策略（阻止公共访问）
- 数据分类和处理

**监控和检测**：

- AWS CloudTrail（API 日志）
- AWS GuardDuty（威胁检测）
- AWS Security Hub（聚合发现）
- AWS Config（配置合规性）
- SIEM 集成

**事件响应**：

- 云特定 IR 手册
- 使用 Lambda 自动化响应
- 快照和取证程序
- AWS 支持参与计划

**合规性**：

- AWS Artifact（合规性报告）
- AWS Config 规则（持续合规性）
- 用于 HIPAA/PCI-DSS 的加密
- 数据驻留（区域选择）

**第 7 步 - 风险分析**：

_高风险_：

- 配置错误的 S3 存储桶（可能性：高，影响：高——数据泄露）
- 被盗 IAM 凭证（可能性：中等，影响：高）
- 监控不足（可能性：高，影响：中等——延迟检测）

_中等风险_：

- 网络分段不足（可能性：中等，影响：中等）
- 缺乏云专业知识（可能性：高，影响：中等——配置错误）

**第 8 步 - 检测和响应**：

- 在所有区域和账户中部署 GuardDuty
- 集中 CloudTrail 日志
- 配置 Security Hub 和 Config
- 创建云特定警报（异常 API 调用、IAM 更改、公共 S3 存储桶）
- 制定云事件响应手册

**第 9 步 - 建议（云迁移安全路线图）**：

_迁移前（第 1-2 个月）_：

1. 为团队提供云安全培训
2. 设计 AWS Organizations 结构和账户策略
3. 定义 IAM 策略和策略
4. 设计 VPC 架构和网络分段
5. 选择并实施 CSPM 工具
6. 建立云安全基线（CIS AWS 基础设施基准）

_迁移中（第 3-12 个月）_：

1. 使用基础设施即代码（Terraform/CloudFormation）为所有资源
2. 在 CI/CD 中自动化安全检查（SAST、DAST、IaC 扫描）
3. 强制执行静态和传输加密
4. 实施最小权限 IAM
5. 启用所有云原生安全服务（GuardDuty、Security Hub、Config、CloudTrail）
6. 在生产部署前进行安全测试

_迁移后（持续）_：

1. 持续合规性监控
2. 定期 IAM 访问审查
3. 云安全态势评估
4. 在云环境中进行渗透测试
5. 云事件响应场景桌面演练

**第 10 步 - 合规性**：

- 利用 AWS 合规性认证（SOC 2、ISO 27001、PCI-DSS）
- 使用 AWS Artifact 作为审计证据
- 实施AWS Config 规则以实现持续合规
- 记录共享责任矩阵

**第 11 步 - 综合分析**：

- 云安全需要不同的思维方式（零信任、以身份为中心、API 驱动）
- 共享责任模型至关重要——必须保护 AWS 未保护的资源
- 主要风险：配置错误、IAM 漏洞、监控不足
- 机遇：云原生安全服务、自动化、可扩展性
- 成功因素：培训、最小权限、纵深防御、监控、IaC
- 建议：继续进行迁移，但并行实施安全路线图

## 常见陷阱及规避方法

**陷阱 1：没有风险背景的合规性检查**

- **问题**：不理解实际风险而遵循合规要求
- **解决方案**：基于风险的解决方案——了解威胁和业务背景，而不仅仅是复选框

**陷阱 2：仅依赖边界安全**

- **问题**：假设网络边界保护内部所有内容
- **解决方案**：纵深防御和零信任——假设可能被入侵，直接保护资产本身

**陷阱 3：警报疲劳和误报**

- **问题**：大量低质量警报使响应者不堪重负
- **解决方案**：调整检测，优先处理高保真度警报，尽可能自动化响应

**陷阱 4：忽视人为因素**

- **问题**：只关注技术控制，忽视社会工程和内部威胁
- **解决方案**：包括安全意识、特权用户监控、内部威胁计划

**陷阱 5：一次性评估**

- **问题**：没有持续监控的一次性安全审查
- **解决方案**：持续安全——持续监控、漏洞管理、威胁情报

**陷阱 6：没有上下文的漏洞评分**

- **问题**：仅根据 CVSS 评分优先，不考虑可利用性或业务背景
- **解决方案**：基于风险的优先级——考虑威胁情报、可利用性、资产关键性

**陷阱 7：安全成为障碍**

- **问题**：将安全视为业务目标的障碍
- **解决方案**：安全地支持业务——平衡风险和业务价值，提供安全替代方案

**陷阱 8：忽视供应链和第三方**

- **问题**：只关注第一方系统，忽视依赖关系
- **解决方案**：供应链风险管理——评估第三方安全、依赖漏洞

## 成功标准

高质量的网络安全分析：

- [ ] 应用适当的安全框架和方法
- [ ] 使用威胁建模确定和优先排序风险
- [ ] 跨多个层次（纵深防御）评估安全控制
- [ ] 提供可操作、优先级分明的修复建议
- [ ] 基于威胁情报和行业最佳实践进行分析
- [ ] 考虑技术和人为因素
- [ ] 不仅要预防，还要考虑检测和响应
- [ ] 映射到公认标准（MITRE ATT&CK、NIST CSF 等）
- [ ] 平衡安全与业务目标
- [ ] 展示深厚的安全专业知识和批判性思维
- [ ] 对技术和非技术人员都能清晰沟通
- [ ] 精确使用安全概念和术语

- 合规性和标准
