# App Store 屏幕设计

使用品牌素材和真实产品屏幕，制作一套 iPhone 6.9 英寸（1290×2796）的 App Store 活动，共 5-6 屏。产品屏幕可来自原始导出文件、Figma/源文件，或通过 Pika MCP 获取的公开 App Store 列表。要求故事驱动、视觉冲击力强、严格遵循品牌规范。

这是 `build-a-brand` 技能的姊妹技能——它消耗该技能的 `brand.md` 规格文件，但同样适用于用户提供的任何品牌规格。

## 成本透明度门槛

在执行任何付费 MCP 调用之前，调用一次 `identity_balance({verbose: true})`。展示当前余额、近期消耗速率和剩余额度，并以以下精确信息进行运行控制：

> 预计成本：使用 GPT-image-2、PNG 渲染、渲染后 analyze_media QA 和全分辨率单独 PNG QA 的典型 5-6 屏设置，约需 150-300 信用点（~$1.50-$3.00）。此费用低于 $5，回复 `proceed` 继续或 `cancel` 取消。

在用户回复 `proceed` 之前，不要调用任何付费 MCP 工具。如果用户回复 `cancel`，则停止生成。对于非交互式 `--quick` 或 `--config` 调用者，要求配置中包含 `cost_ack=proceed`；如果缺失，则停止并显示估算信息，而不是消耗信用点。

## 交付物

5 或 6 个 PNG 文件，编号保存至 `~/Desktop/[app-name]-app-store-screens/`（或用户指定的其他位置）：

```
01_hook.png            ← 最大卖点，作为搜索结果缩略图
02_value.png           ← 应用最擅长的功能
03_feature_a.png       ← 具体功能
04_feature_b.png       ← 另一个具体功能
05_proof.png           ← 社会证明、奖项、用户喜爱、差异化
06_close.png           ← 可选第 6 屏——收尾/行动号召/品牌亮点
```

另附一个包含所有 6 屏的缩略图 `_preview.png`。

## 工作流程

### 第 0 步——输入和风格选择

如果以空参数调用且无可用品牌/截图/演示上下文，则打印以下菜单原文并停止。在所需输入出现之前，不要生成图像或渲染 HTML。

> **我应该制作什么样的 App Store 截图集？** 必须提供：
>
> - **品牌规格** — `brand.md` 或包含名称、调色板、字体、语调和图像方向的等效品牌笔记；或 App Store URL/应用名称，如果您希望我首先获取列表并草拟品牌
> - **原始产品截图** — 导出的 PNG、可导出截图的 Figma/源文件、截图文件夹，或我可通过 Pika MCP 获取的 App Store URL/应用名称
> - **或虚构应用演示简报** — 仅用于发布演示/概念，无真实产品存在时；说 `demo_mode: true` 并提供虚拟应用的功能说明
>
> 可选：参考 App Store 截图、情绪板、首选屏幕数量（5 或 6）、输出文件夹。

在交互模式下，如果用户已提供部分输入，则仅询问缺失的必要项并停止。如果适用非交互式快速通道，则使用第 0.5 步。必要输入：
- `brand.md` 或包含名称、调色板、字体、语调和图像方向的等效品牌规格；如果用户提供 App Store URL 并要求您“帮助创建”，则首先获取列表，并从列表/图标/截图推断品牌规格以供批准
- 一个产品源：原始产品截图、可导出截图的 Figma/源文件，或可通过 Pika MCP 获取的 App Store URL/应用名称
- 仅限虚构发布演示，`demo_mode: true` 与 `demo_brief` 是真实产品截图的替代方案；使用下方虚构应用演示模式路径
- 可选参考截图或情绪板，如果用户希望特定 App Store 风格

### 第 0.5 步——非交互式快速通道

在以下情况下使用此路径：调用者传递 `--quick` 或 `--config <路径>`，或调用者声明他们正在 CI、子代理、批处理作业或其他非交互式框架中运行。

此部分优先于下方的交互式询问/等待指令。适用时，使用此快速通道，除非所需品牌和产品截图或显式演示模式输入确实不可用，否则不进入多轮输入。

- `--config <路径>` 指向包含预定义选择的 JSON 文件：`brand_spec`、`product_screenshots`、`app_store_url`、`website_url`、`reference`、`style`、`screen_count`、`narrative_arc`、`demo_mode`、`demo_brief` 和 `output_folder`。
- `--quick` 意味着选择默认风格，除非提供参考，否则从提供的品牌规格或 App Store 列表推断品牌阅读，自己草拟 5-6 屏的叙事弧，然后继续。
- 对于 `--quick` 或 `--config`，在风格选择、品牌阅读回放、参考规则回放或 5-6 屏策略提案时，不要停止确认。直接记录假设并继续设计/渲染。
- 如果既无真实产品截图，也无显式 `demo_mode: true` 与 `demo_brief`，则停止并显示一个紧凑的缺失字段列表，而不是启动多轮问答循环。

#### 虚构应用演示模式

仅当调用者明确说明这是虚构应用、假应用、发布演示、概念演示或配置中传递 `demo_mode: true` 时使用。不要用于真实产品。

演示模式允许在没有真实产品截图时创建符合品牌语气的代表性 UI 模拟，但输出必须标记为仅限演示的概念作品，而非生产资源。将虚构屏幕视为故事板化的 QRT/演示工件，而非 App Store Connect 可用的真实产品证据。

- 需要一个 `demo_brief` 或足够的用户提供的虚拟产品概念细节来定义应用的核心功能、受众、3-5 个功能以及证明/行动号召角度。
- 生成与该简报内部一致的 UI 状态；除非提示明确提供，否则不要暗示真实客户、真实评论、真实指标或真实集成。
- 在交付说明和缩略图标签中添加演示仅限声明：“演示 UI 概念——非生产资源且非真实产品截图。”
- 在非交互模式下，仅当配置设置 `demo_mode: true` 并提供 `demo_brief` 时才继续；否则停止并显示紧凑的缺失字段列表。

在交互模式下，当所需输入存在时，以简短议程开头并直接询问一个风格问题。这是了解用户是否希望默认风格或特定参考的最佳时机。在非交互式快速通道中，除非提供 `reference` 或 `style`，否则选择默认风格，直接记录假设并继续。

```
这是如何工作的：
1. **读取品牌 + 截图** — 我吸收品牌语调、调色板、类型，并确定应用实际做什么
2. **策略** — 我提出一个 5-6 屏的叙事弧（钩子→价值→功能→证明→收尾），每个部分都有标题，在任何设计之前
3. **设计 + 生成** — 我设计每个布局，1290×2796 尺寸合成
4. **预览** — 我交付 PNG + 缩略图，以便您能一次性查看整个活动

开始前快速问题——**您希望默认风格还是特定风格？**

- **默认** — 干净、克制，屏幕未经修改显示。全屏设备，标题+副标题上方，品牌色背景，品牌语调文案。编码在 `references/default-layout.md` 中。这是我能做得很好的风格。
- **特定风格** — 分享一个清晰的参考：您喜爱的 App Store 页面截图（Notion、Calm、Things、Headspace、任何应用），Figma 文件，情绪板图片。我会研究它，提取构图规则（设备尺寸+位置、标题处理、背景、任何标志性装饰），回放我的理解后再设计，然后构建活动——**但会替换您的品牌调色板、字体、语调和摄影风格**。如果参考使用肩部照片，我会生成符合您品牌风格的 `gpt-image-2` 照片。参考决定构图；您的品牌决定外观。

如果您不告诉我，我会选择默认。
```

**为什么没有“炫酷”自动模式。** 做好丰富/多样/戏剧性构图需要视觉判断（透视、分层、字体层级、色彩平衡），这些没有程序化答案。当用户希望丰富性而没有参考时，我的近似值往往看起来很业余。要求具体参考让我能提取特定规则来复制，而不是自由创作——用户也有验证我是否朝着正确方向努力的方法。

基于答案的两个下游路径：
- **默认** → 严格遵循 `references/default-layout.md`。每个屏幕使用相同的构图骨架；通过颜色+内容实现多样性。这会产生一致、受品牌约束的作品。
- **复制参考** → 研究参考，提取规则，替换用户品牌。见下文“参考驱动路径”的完整过程。

如果用户无法或不愿提供参考，但仍希望比默认更多，请温和地提出——解释如果没有参考，将提供默认风格+品牌色，这比猜测式迭代循环更好。不要凭空创造“炫酷”风格。

### 第 1 步——读取品牌和产品

#### App Store 列表路径

如果用户提供 `apps.apple.com` URL、数字 App Store 应用 ID 或应用名称搜索词作为产品源，首先尝试 Pika MCP `fetch_appstore_screens`，因为它更快、更稳定，并返回可供后续渲染步骤使用的托管截图/图标资源：

```
fetch_appstore_screens(
  query: <app_store_url | numeric_app_id | search_term>,
  country: "us",
  max_screens: 10,
  include_icon: true
)
```

使用返回的 `metadata`、`icon` 和 `screenshots` 作为产品源。返回的截图 `url` 值已经是 Pika 托管的 HTTPS 资产，可直接用于后续 `html_to_png` 阶段。

如果用户提供了特定国家 App Store URL，在调用工具时尽可能保留该商店国家。如果国家不明确，默认为 `"us"`，除非用户要求其他商店。

如果 MCP 工具不可用、未认证或返回无截图，说明发生了什么，然后使用最不脆弱的回退方案：其他读取/获取工具、官方 App Store/iTunes 元数据端点或用户提供的截图。保持回退基于真实列表资源；不要虚构产品 UI。

预期结果形状：

```
{
  "app_url": "https://apps.apple.com/...",
  "metadata": { "name": "...", "subtitle": "...", "description": "...", "category": "...", "icon_url": "https://..." },
  "icon": { "url": "https://cdn.pika.art/...", "source_url": "https://is...mzstatic.com/...", "filename": "appstore-icon.png", "mime_type": "image/png", "width": 1024, "height": 1024 },
  "screenshots": [
    { "url": "https://cdn.pika.art/...", "source_url": "https://is...mzstatic.com/.../1290x2796bb.png", "filename": "appstore-screen-01.png", "mime_type": "image/png", "width": 1290, "height": 2796 }
  ],
  "count": 1
}
```

#### 源截图准备

在选择默认手机布局之前，对每个获取或用户提供的源截图进行分类，并记录您将使用的 `source_treatment`：

- `clean_ui_capture` - 纯洁的应用内 UI，适合设备模型。
- `composed_marketing` - 完成的 App Store 营销屏幕，非应用内干净截图。
- `legacy_footer_cleanup` - 需要列表品牌页脚或水印清理才能嵌入设备的干净 UI。

`composed_marketing` 源是一个预组合的营销屏幕。常见信号：标题或副标题已预先放置在手机上方，手机边缘出血或裁剪，背景已是活动艺术，源图像已是完成的 1290x2796 App Store 屏幕，而非干净产品 UI。2025 年 Notion 列表使用此模式。

当源为 `composed_marketing` 时，不要将其重新嵌入另一个设备模型中，也不要在预制的标题上添加、书写或生成第二个标题/副标题。优先使用 `clean_ui_capture`：在产品网站、引导流程或网络应用上存在可捕获的 UI 表面时，使用 `capture_website`，或请求模拟器/Figma/原始 UI 导出。如果无干净 UI 表面，使用 `source_treatment=composed_passthrough`：直接呈现组合源作为屏幕/背景，仅添加最小交付框架、编号或缩略图标签。不要依赖底部 6-8% 裁剪修复组合源；它会移除错误区域并保留双标题失败。

对于其他干净 UI 的源截图，检查它们是否有列表品牌页脚或页脚水印出血，这些将在生成的活动中造成杂乱。R4 Notion 列表暴露了这个问题：原始页脚显示 `NOTION · NOTES, TASKS, AI` 重叠底部内容。如果获取或用户提供的干净 UI 源截图有此类型页脚水印，裁剪或遮罩底部 6-8% 再嵌入；不要直接放置原始截图。

在 HTML 阶段使用准备好的截图包装器，并锚定源顶部。包装器必须定义自己的几何形状；不要依赖 `height:100%`，除非每个父级到设备都有明确高度。

```html
<div class="source-screen-crop source-screen-crop--phone" style="
  width:100%;
  aspect-ratio:1290 / 2796;
  overflow:hidden;
  position:relative;
">
  <img src="s://screen01" style="
    width:100%;
    height:calc(100% / 0.92);   /* 显示顶部 92% 同时裁剪底部 8% */
    object-fit:cover;
    object-position:top center;
    display:block;
  ">
</div>
```

如果 8% 裁剪会移除真实产品 UI，使用品牌色渐变覆盖底部页脚，但仍然在截图进入最终设备模型之前移除水印出血。

#### 处理 Mac-app 或混合应用截图

`fetch_appstore_screens` 可能返回适用于 Mac 的横向截图（例如 1290×806），而不是 iPhone 竖向截图（1290×2796）用于 Mac 独占或混合 iOS/Mac 应用，如 Things 3、Drafts、Numbers、Day One、OmniFocus 或 BBEdit。在选择默认 iPhone 竖向布局之前检测此情况：

方向规则是 `aspect_ratio_w > aspect_ratio_h`，或 `width > height` 当仅存在像素维度时。

```
mac_shots = [s for s in screenshots if s.aspect_ratio_w > s.aspect_ratio_h]
# 等价于当明确宽高比不存在时：
mac_shots = [s for s in screenshots if s.width > s.height]
```

如果 `mac_shots` 非空，使用 `references/mac-app-layout.md` 中的嵌入式卡片布局，而不是全屏设备拍摄。对于 Mac 独占或混合应用，将每个横向截图嵌入到 1290×2796 竖向画布中的圆角 UI 卡片中，而不是将其裁剪到 iPhone 框架中、添加边框、处理为全屏设备。Things 3 第二轮基准验证了此方法：Mac 截图保持可读，竖向活动仍适合 App Store Connect。

源截图准备仍适用于 Mac 卡片：在嵌入之前检查横向截图是否有列表品牌页脚或页脚水印出血。不要在 Mac UI 上使用手机竖向裁剪。使用专用卡片包装器（如 `source-screen-crop--mac`）；如果需要清理，优先使用窄底遮罩/渐变或卡片内的小型横向保留底裁剪。

#### 瘦 App Store 列表门槛

在 `fetch_appstore_screens` 之后，计算显示真实产品 UI 的可用截图数量。如果列表返回少于 3 张真实产品截图，将其视为瘦 App Store 列表。

- 不要通过臆想 UI 来创建一个 5-6 屏幕的推广活动。真实产品的 UI 是设备框架的默认要求。
- 交互模式：在策略之前停止，并提供两个选择：
  1. **网站捕获路径** — 使用 `capture_website` 或提供的网站/引导 URL 来捕获真实产品界面，然后继续将这些捕获作为产品截图。
  2. **真实截图路径** — 在继续之前，请求模拟器导出、Figma 框架或其他产品 UI 捕获。
  不要为真实产品提供合成的设备 UI。如果用户明确转向虚构的发布/概念演示，则路由到虚构应用演示模式，并要求 `demo_mode: true` 与 `demo_brief`。
- 非交互式快速通道：当 `website_url` 或明显的产品网站可用时，优先选择网站捕获路径。如果没有可捕获的产品界面，则一次性停止并提供紧凑的缺失字段列表，除非配置明确设置 `demo_mode: true` 并提供 `demo_brief`。

获取后，仅推断从列表和视觉中读取的草稿品牌：应用名称、类别、可见调色板、可能的类型方向、从字幕/描述中获取的语音以及值得注意的 UI 瞬间。在交互模式下，将其作为临时品牌规范读回，并要求用户在提出 5-6 屏幕弧之前进行更正。在非交互式快速通道中，将其记录为临时品牌规范并继续。

#### 参考驱动路径：如何将用户的品牌应用于参考的风格

参考描述了布局/样式的样子。品牌描述了要使用的颜色/字体/语音/摄影。技能的工作是将它们结合起来：复制参考的视觉结构，但使用用户的品牌进行渲染。从参考中提取两件事，从品牌中提取两件事：

**从参考中提取结构规则：**
- 设备尺寸（作为画布的百分比）和倾斜角度
- 标题处理（大小、位置、颜色逻辑——关键字上使用强调？着色背景药丸？）
- 背景处理（纯色、照片、渐变、抽象元素）
- 英雄图像模式（手持手机的手、过肩、真实主题突破手机、3D 物体漂浮等）
- 指示/拉出模式（带箭头的气泡、浮动卡片、宝丽来框架等）
- 重复规则：每屏相同的布局，还是每个插槽不同？

**从品牌中应用具体内容：**
- 调色板（在参考使用纯色块的地方替换品牌颜色）
- 字体（在参考使用类型的地方替换品牌显示+正文字体）
- 语音（用品牌语音重写所有标题/副标题——不要复制参考的词语）
- 摄影方向（任何生成的图像都遵循品牌的摄影规则——对于 DeltaStream 是纪实 35mm、黄金时刻、真实公寓、每帧都有黄油强调色、真实演员多样性）
- 氛围（温暖与临床、俏皮与专业等）

**对于生成的英雄图像：通过 `generate_image_edit` 将参考作为 `images` 传递给 `gpt-image-2`。** 该工具支持多达 16 张参考图像。当参考使用独特的照片构图（手持手机、过肩、人物突破屏幕、3D 角色出现）时使用此功能。将品牌的摄影规则与提示结合使用：

```
参考：[用户的参考照片——例如，昆虫应用的手持手机与蝴蝶]

提示："在参考图像的完全构图和照明风格中——手持手机的角度和比例相同——但根据 [BRAND] 摄影规则渲染主题和场景：纪实 35mm、黄金时刻窗户光、真实公寓、黄油色陶瓷杯可见、30 多岁混合种族演员、35mm 电影颗粒。垂直 9:16 竖屏构图。"
```

这就是你如何在不复制其内容的情况下获得参考的风格。手+手机构图会转移；照明/演员/场景来自品牌。

**在交互模式下，在交互模式下设计之前，将提取的规则反馈回去。** 将它们写成简短的要点列表（“设备 75% 画布倾斜 -8°，标题在黄色药丸上方的设备上，过肩英雄，墨水指示带弯曲箭头”），并确认用户是否正确理解了参考。在非交互式快速通道中，将提取的规则内联记录并继续。然后应用这些规则一致地构建所有 6 个屏幕。不要在活动中途偏离。

然后实际阅读：

- **`brand.md`** — 提取：品牌名称、标语、调色板（带十六进制）、显示字体+正文字体、语音形容词、语音示例、禁止的词语、摄影/插画方向、氛围词。如果文件是不同的格式（PDF、纯文本笔记），解析其中的内容，并在交互模式下询问差距。在非交互式快速通道中，记录非关键差距的合理假设——不要编造品牌。
- **产品截图** — 打开每一张，并形成诚实的心理模型：*这个应用实际上做什么？* 注意核心 UI 模式（信息流、聊天、画布、列表、地图等）、主要操作界面和任何“惊艳”屏幕（生成结果、美丽状态、独特交互）。
- 如果你可以使用 `analyze_media` 来在不加载它们为图像的情况下检查截图，那就这么做——对于快速扫描来说更快。

**然后阅读你找到的内容**（3-5 行，对话式）：

```
ok — 读取 [品牌名称]：[标语]。调色板：[颜色]。语音：[形容词]。应用看起来像 [X]——我看到 [特定 UI 指示 1] 和 [特定 UI 指示 2]。令人印象深刻的屏幕是 [屏幕 N]，因为 [原因]。纠正我的错误，否则我将提出 6 屏幕弧。
```

交互模式：在提出策略之前等待确认。廉价地捕获误读。在非交互式快速通道中，将品牌读取视为临时，内联记录假设，并继续到策略。

### 第 2 步——提出 6 屏幕策略

在设计任何东西之前，将叙事弧写成纯文本。每个屏幕都需要：

- **角色**（钩子/价值/功能/证明/收尾）
- **标题**（5-8 个字，在品牌语音中——见“文案”下文）
- **可选副标题**（一行短）
- **布局原型**（见下文——现在不要画它）
- **哪个原始截图它使用**（文件名）——或者“无，全出血文本”
- **证明工件**仅用于证明屏幕——至少一个可见的证明工件，例如星级行、编辑选择徽章、评论卡、评论计数芯片、奖项徽章或其他来源的视觉证明。证明屏幕不能是纯文本。

像这样呈现：

```
**屏幕 1 — 钩子**
标题："睡得像你打算的那样。"
副标题：（无——让标题发挥作用）
布局：全出血 UI 带粗体文本叠加
 featured 截图：home_screen.png

**屏幕 2 — 价值**
标题："一键。然后安静。"
...
```

交互模式：在生成或合成任何东西之前，要求用户批准弧。在这里迭代文案——这是修复它的最便宜时刻。在非交互式快速通道中，根据配置或推断的弧生成，而无需停止确认。

**证明屏幕规则：** 证明屏幕需要一个可见的证明工件，而不仅仅是声明。不要发布一个只说“受数百万喜爱……”或另一个纯文本社交证明行的证明屏幕。如果 App Store 列表或品牌规范提供真实证明，将其可见地渲染为星级行、编辑选择徽章、评论卡、评论计数芯片、奖项徽章或来源引言卡。如果没有真实证明，则让证明节拍成为一个视觉差异化，并由产品截图支持，而不是编造评论、奖项、评分或客户数量。

### 第 3 步——生成品牌世界图像

对于任何需要鲜艳背景/英雄图像的屏幕，使用 `generate_image`（或在上面的参考驱动路径中传递参考图像时使用 `generate_image_edit`）生成。

**适用于 App Store 全屏的默认值：**
- `provider: gpt-image-2`
- `质量：medium` 用于完成的截图；`低` 仅当用户明确要求快速迭代时
- `aspect_ratio: 9:16` 用于全出血背景（匹配 iPhone 画布）
- 1K 是默认值。如果一个屏幕确实需要更高分辨率（例如，一个超详细背景会被放大），将 `gpt-image-2` 提升到其 2K/4K 级别（9:16 背景支持两者）或升级到 `seedream`——先表面权衡并询问

**品牌世界图像的提示结构：**
1. 主题+构图（“一个宽电影镜头拍摄的单个陶瓷杯在风化的橡木上……”）
2. 品牌调色板作为命名颜色（“仅限于墨水黑 #0E0E10、燕麦 #F5F0E6 和一种锈色 #C84B2F 的强调色”）
3. 光+氛围（“柔和的阴天窗户光，轻微的胶片颗粒，纪实感”）
4. 负面提示（“无文本、无标志、无人物，除非指定，无库存照片光泽”）
5. 9:16 背景的构图：垂直构图，上三分之一留出空间用于标题

**为标题保留上三分之一。** 告诉图像模型文本将去哪里，以便它留出空间。

保持生成的图像 URL 为 HTTPS/CDN URL 以进行服务器端渲染。如果用户提供本地产品截图或背景图像，首先使用 `upload_asset` 上传它们，然后使用返回的 `public_url`；`html_to_png` 无法读取本地 `file://` 路径。当一个阶段重复长 CDN URL 时，在 HTML/CSS 中放置短标记，例如 `s://screen01`，并通过 `short_link_map` 传递完整 URL；带有空格或缺少 `https://` 的错误资产 URL 在渲染之前会被拒绝。

### 第 4 步——在 1290×2796 上合成每个屏幕

为每个屏幕写一个 HTML 阶段，然后通过 Pika MCP `html_to_png` 渲染为 PNG。参见 `references/render-pipeline.md` 以获取：
- `html_to_png` 请求的确切形状
- 服务器端资产/字体规则
- 安全区域指南
- 常见陷阱（字体加载、视网膜文本锐度、中曲线裁剪）

每个 HTML 阶段应正好为 1290×2796 像素。使用 `@font-face` 并使用直接 `fonts.gstatic.com` WOFF2 字体文件 URL 或内联 `data:font/...` 源。不要在渲染器 HTML 中使用 GitHub 原始 Google 字体链接；它们可能解析为 `text/html` 并失败字体 MIME 允许列表。本地品牌套件字体文件必须通过公共 HTTPS URL 或内联公开；`upload_asset` 不接受字体 MIME 类型。参见 `references/fonts.md` 以获取可复制粘贴的 Google 字体片段。

对于 CJK 或其他非拉丁应用名称、标题、评论或 UI 标签，每个 CSS `font-family` 堆栈都必须添加广泛脚本备用选项，例如 `"Noto Sans SC"`, `"Noto Sans TC"`, `"Noto Sans JP"`, `"Noto Sans KR"`, `"Noto Sans Arabic"`, system-ui, sans-serif。Chromium 将为支持的拉丁符号使用品牌字体，并为缺失的脚本使用每个符号的备用选项，而不是渲染豆腐盒。

对于暗背景，设置暗模式副标题标记，而不是重复中等灰色。使用 `--subhead-on-dark: #B5B4B0` 或品牌调色板中的等效浅中性色（不透明度 100%）；永远不要在接近黑色上使用 `#787774`-类灰色，也永远不要用浅背景的 `opacity: 0.7-0.75` 规则降低暗标记。`#787774`-类灰色仅用于浅色背景。标题可以变为奶油/白色，但副标题也必须变为可读的暗模式颜色。

渲染后，在接收 PNG 之前运行预交付 QA。使用 `analyze_media` 在渲染的图像上，并在可用时检查编写的 HTML 位置。拒绝并重新渲染任何文本块边界框将承重标题、眉毛、副标题、CTA 或产品 UI 放在 `references/render-pipeline.md` 中记录的安全内容区域之外的屏幕。

### 第 5 步——构建接触表并交付

一旦所有 6 个 PNG 清晰地渲染：

1. 使用 `html_to_png` 构建 `_preview.png` 接触表——3×2 网格中的 6 个缩略图，大小约为 25%，在中性背景上，按角色标记。
2. 提交接触表 URL 加上每个单独截图的 `file_url`。如果您还保存了本地副本，请单独包含这些本地路径。
3. 询问：有什么要修改的？常见的修改是文案调整（便宜）、布局交换（中等）或新图像（最昂贵）。

在 `_preview.png` 存在并包含在交付中之前，不要报告截图集完成。如果接触表渲染失败，先修复表 HTML 或重新渲染缺失的 PNG；不要只交付单个 PNG 并称活动完成。

## 事后质量门

在宣布成功之前，调用 `analyze_media` 在 `_preview.png` 接触表上检查活动级别的多样性，然后检查任何带有证明文案、暗背景或准备好的源截图的屏幕作为全分辨率单独 PNG。25% 的接触表太小，无法验证页脚水印出血、暗背景副标题对比度、细证明工件或复合营销源上的双标题失败。

在以下屏幕上运行全分辨率单独 PNG 检查：
- 证明屏幕
- 每个使用接近黑色/暗背景的屏幕
- 每个嵌入获取或用户提供的源截图并可能带有列表品牌页脚文本的屏幕
- 每个使用 `source_treatment=composed_passthrough` 或源分类为 `composed_marketing` 的屏幕
- 每个使用 `mac_shots` 的 Mac 横向卡片屏幕

对于接触表，请求结构化裁决：

```
仅返回 JSON：{
  "verdict": "clean" | "degraded" | "catastrophic",
  "observations": string[],
  "quality_warning": string | null,
  "re_roll_suggestion": string | null
}
检查接触表是否显示每个请求的截图，App Store 安全区域是否得到尊重，产品 UI 是否可读，标题在缩略图比例下是否可读，以及没有生成的文本损坏。
```

对于每个目标单独渲染的 PNG，请求：

```
仅返回 JSON：{
  "proof_artifact_visible": boolean | null,
  "dark_subhead_contrast_ok": boolean | null,
  "footer_watermark_bleed_visible": boolean,
  "composed_source_double_headline_visible": boolean | null,
  "mac_card_preserves_landscape_ui": boolean | null,
  "verdict": "clean" | "degraded" | "catastrophic",
  "observations": string[],
  "re_roll_suggestion": string | null
}
在可读分辨率下检查。证明屏幕必须包含一个可见的证明工件，例如星级行、编辑选择徽章、评论卡、评论计数芯片、奖项徽章或来源引言卡。暗背景副标题必须使用浅暗模式标记并保持可读。源截图和 Mac 卡不得显示页脚水印出血或列表品牌页脚杂乱。对于复合营销源，验证没有生成的标题堆叠在烘焙的标题之上，也没有额外的设备模型包装在源周围。
```

- 如果 `verdict` 是 `clean`，交付接触表加上单独的 PNG URL。
- 如果 `verdict` 是 `degraded`，交付 URL 并附带 `quality_warning`，以便用户在发布前查看。
- 如果 `verdict` 是 `catastrophic`，不要称活动完成；表面裁决和 `re_roll_suggestion` 而不是宣布成功。
- 如果证明屏幕缺少可见的证明工件，如果暗背景副标题对比度低，如果源截图页脚水印出血仍然可见，或者 `composed_source_double_headline_visible` 为真，则至少将裁决视为 `degraded` 并重新渲染受影响的屏幕，然后正常交付。在复合源同时具有烘焙标题和生成标题时，不要称活动完成。

## 5 布局原型

每个屏幕使用一个。**不要堆叠设备。** 每个屏幕一个大胆的想法。

参见 `references/layout-archetypes.md` 以获取完整的 CSS 骨架和视觉示例。快速参考：

1. **浮动设备** — 在水花背景上倾斜的手机。主力设备。最适合价值/功能屏幕。
2. **全出血UI** — 手机画布填满框架；字体叠加在顶部或底部。最适合钩子。
3. **并排** — 设备在一侧，生成的生活影像在另一侧。最适合情感功能。
4. **视差堆叠** — 手机在前，品牌形状/影像漂浮在后面。最适合“哇”时刻功能屏幕。
5. **引言卡片** — 大型引言，小设备隐藏在角落。最适合证明屏幕。

## 文本 — 非可协商

App Store标题在小窗口中测试。它们必须：

- **为5-8个词。** 任何更长的内容在6.1英寸手机上的搜索结果中都会死亡。
- **完全呼应品牌声音。** 如果`brand.md`说声音是“干燥、平板，从不感叹”，标题永远不会以`!`结尾。如果声音是“温暖且有点调侃”，标题就会有节奏。
- **提出主张，而不是描述。** “像你真正打算的那样睡觉” > “跟踪你的睡眠”。 “为一天中安静的一小时而设计” > “生产力应用”。
- **前两个屏幕作为独立的缩略图工作。** 更大的字体，最清晰的钩子。App Store搜索显示前2-3个展开；其余的只有在用户点击时才会渲染。

**禁止（这些是App Store的“充满爱心的制作”）：**
- “保持组织。”
- “你的日常伴侣。”
- “一站式[类别]。”
- “设计来帮助你[动词]。”
- “跟踪。计划。实现。”
- 任何带有“无缝衔接”、“毫不费力”、“强大”、“智能”、“智能”的内容。

如果标题可以出现在500个其他应用上而无人注意——重写。

## 视觉标准

- **设备是主角 — 字体是标题。** 在1290×2796的画布上，设备宽度应为1050-1150px（≈81-89%的画布）。任何更小的看起来都胆怯。标题支持屏幕内容；它们不与内容竞争。
- **字体层次结构。** 每个屏幕上有一件事占主导地位——通常是设备。标题100-140px Funnel-Display类；副标题36-44px；在重量和大小上有明显的差异。（超过150px后，标题开始与设备争夺眼球。）
- **跳过SVG描边的iPhone框架——它们与截图角不匹配。** 基于描边的SVG边框位于其路径的一半内部/外部，并且半径/Dynamic Island比例永远不会与真实的iPhone完全匹配。更喜欢来自Figma/模拟器的透明截图导出或带有透明切割的真实iPhone模型PNG。如果只有矩形源截图可用，请使用一致的CSS `border-radius` + `overflow:hidden`包装器，并视觉检查角落。旧的本地`clean_phone_uniform()` PIL配方现在是一个记录在案的MCP差距，不是一个默认依赖项。
- **选择一个：出血或全帧。永远不要中间裁剪底部的曲线。** 默认是全帧（设备顶部在y=580，宽度=1000，因此圆角底部角落完全位于画布内，底部约48px的呼吸空间）。出血变体（设备顶部≥819）将圆角底部角落完全推到y=2796之外——适用于希望有戏剧性的钩子屏幕。任何介于两者之间都会产生可见的半切割曲线，画布在圆角中弧的中间切割；这是规则防止的失败模式。
- **Apple安全区。** 严格的安全区规则：承重文本和产品UI必须保持在y=180..2616内。顶部和底部的100px带永远不会用于关键内容，额外的80px缓冲区可以防止App Store边框、搜索结果裁剪和文本 ascenders 侵占边缘。装饰是好的；关键主张和可读的应用UI不是。
- **每屏一个粗体设备。** 巨大的字体*或*生成的影像*或*一个引言——不是所有三个。花哨的≠混乱的。
- **颜色仅来自品牌调色板。** 不为截图发明新颜色。如果调色板感觉过于限制，那是品牌需要解决的问题，而不是你的问题。

## 获取屏幕

原始屏幕可以来自任何地方——通过Pika MCP获取的App Store列表、Figma框架、Sketch导出、模拟器截图或本地文件。如果源是App Store URL/应用ID/应用名称，请使用上面提到的App Store列表路径。如果你有Figma MCP访问权限，并且源是Figma：

- `get_screenshot(fileKey, nodeId)` 返回节点的渲染PNG。这不需要用户在Figma桌面应用中选择任何内容。
- 对于手机带状布局，更喜欢请求单个手机导出。如果只有带状可用，请从设计源手动裁剪或使用未来的服务器端裁剪/清理工具（当可用时）；不要将本地PIL裁剪作为此技能的默认依赖项。
- 自然渲染通常是逻辑像素大小（例如，每个iPhone 15 Pro手机393×852）。当你将其缩放到App Store画布上的默认1000px设备宽度时，上采样对于非像素关键内容是可接受的。对于更紧密的保真度，请询问是否有更高分辨率的导出。

## 质量标准

交付前进行眯眼测试：

1. **眯眼看接触表。** 你能一眼看出6个屏幕的区别吗？（不同的标题、不同的布局、不同的焦点权重。）如果它们看起来像是同一屏幕的6个版本——重新设计。
2. **前两屏幕缩略图测试。** 将屏幕1和2裁剪到25%大小。标题仍然可读吗？钩子仍然清晰吗？如果你不得不凑近看，字体太小。
3. **品牌测试。** 覆盖每个屏幕上的设备。周围的 设计仍然感觉像品牌吗？（颜色、字体、情绪、标题中的声音。）如果不是，截图很通用。
4. **反通用测试**（与构建品牌相同）：这些屏幕可以属于这个类别中的任何其他应用吗？如果是——重写文案并重新设计焦点层次结构。
5. **安全区审核。** 检查每个渲染的PNG，并拒绝和重新渲染任何屏幕，其承重文本或产品UI在安全内容区域之外。

## 承重短语

这些锚点使生成的活动保持可读性和品牌一致性：

| 短语 | 位置 | 为什么承重 |
|---|---|---|
| `垂直构图，在上三分之一处留出负空间用于标题` | 品牌世界图像提示 | 为真实的App Store标题字体留下可用空间，而不是强迫文本覆盖繁忙的图像。 |
| `设备是主角 — 字体是标题` | 视觉标准 | 防止海报式屏幕，其中文案压倒了产品UI。 |
| `Apple安全区` | 视觉标准/渲染QA | 使关键主张远离状态栏和App Store覆盖区域。 |
| `无文本，无标志` | 生成的背景提示 | 避免不可用的生成字体；真实文案在HTML中添加。 |
| `选择一个：出血或全帧` | 设备布局规则 | 防止半切割圆角裁剪，看起来像渲染错误。 |

## 引擎选择：HTML优先渲染，仅使用gpt-image-2生成品牌世界图像

最终截图应该是通过`html_to_png`渲染的确定性HTML/CSS合成，因为App Store文案、设备蒙版、安全区和品牌字体需要精确控制。仅使用`gpt-image-2`生成水花/背景/品牌世界图像，其中生成增加了视觉丰富性；保持真实产品UI为截图。仅在特定生成的背景确实需要比1K更高分辨率时，将`gpt-image-2`提升到2K/4K级别（或升级到`seedream`）。

## 运行时预期

典型运行时间为10-25分钟，具体取决于需要多少用户确认：

| 步骤 | 墙上时钟 | 备注 |
|---|---:|---|
| 摄入+风格选择 | 1-5 min | 如果需要参考，用户可以控制节奏 |
| 品牌截图读取 | 2-5 min | 包括视觉检查和功能映射 |
| 策略提案 | 2-5 min | 最好的地方是廉价地迭代文案 |
| 图像生成 | 2-8 min | 仅用于背景或参考驱动的英雄图像 |
| HTML合成+渲染 | 5-10 min | 六个1290x2796 PNG加上接触表 |
| QA修订 | 可变 | 文案调整很便宜；新的图像较慢 |

## 失败模式

| 症状 | 原因 | 修复 |
|---|---|---|
| 屏幕看起来像是同一布局的六个变体 | 默认骨架重复，没有足够的内容对比 | 重新分配布局原型，并旋转焦点权重、颜色和截图选择 |
| 标题在接触表中难以辨认 | 字体太小，无法用于App Store缩略图使用 | 增加标题大小，缩短文案到5-8个词，并重新渲染 |
| 生成的背景包含文本或假UI | 提示过度描述了品牌/产品具体细节 | 使用无文本/无标志的护栏重新生成，并将真实UI保留为截图 |
| App Store列表少于3个可用的截图 | 薄的App Store列表，通常是配套应用或早期列表 | 使用网站捕获路径，请求真实截图，或停止。对于虚构的发布演示概念，仅使用`demo_mode: true`、`demo_brief`和演示专用披露 |
| 虚构应用没有真实产品截图 | 发布演示概念需要代表性UI，但生产规则禁止幻觉UI | 仅在`demo_mode: true`、具体的`demo_brief`、代表性UI模型和演示专用披露的情况下使用虚构应用演示模式 |
| 承重文本出现在顶部或底部边缘太近 | 安全区QA被跳过，或者只检查渲染外观，而不是文本块边界框 | 拒绝并重新渲染，使文本块边界框在严格的安全区边缘内 |
| 设备角落看起来不均匀 | 源截图已经包含圆角区域中的背景，或者CSS半径与源不匹配 | 请求透明的/高分辨率源导出，使用真实的模型切割，或应用一致的CSS蒙版并视觉检查。仍然需要一个服务器端统一的角落清理工具。 |
| 隐藏截图后品牌感觉通用 | 周围的设计忽略了`brand.md`声音、调色板或图像规则 | 在重新渲染之前，从品牌规范中重建屏幕外壳 |
| 渲染模糊或缩放 | 阶段尺寸或光栅选项不正确 | 验证1290x2796阶段大小和`html_to_png` `viewport_px:1290x2796`，`device_scale:1` |

## 当对用户提出异议时

- 如果他们想要一个“装饰”版本而没有提供参考→提出异议。请求他们提供他们喜欢的App Store页面截图、figma文件或情绪板。解释如果没有参考，他们会交付默认的加上他们的品牌颜色，这比猜测“激动人心”要好。（这个规则来自实际的活动工作——自动装饰产生了业余作品。）
- 如果他们想要一个10屏活动→提出异议。5-6是甜蜜点；更多会导致疲劳。
- 如果`brand.md`中的品牌声音很通用（“现代、友好、直观”）→标记它。你仍然可以生成屏幕，但告诉他们标题将只有声音规范那么独特。建议他们首先锐化声音（它位于`brand.md`的“声音与语气”部分）。
- 如果他们没有真实产品截图并且没有明确请求虚构应用演示模式→不要发明UI。请求截图、网站/引导捕获目标，或明确的`demo_mode: true`和具体的`demo_brief`。
- 如果他们根本没有品牌→不要按感觉进行。将他们路由到`build-a-brand`，或者让他们至少写出：名称、调色板十六进制值、显示字体、正文字体、一行声音描述。
