# BMad Review

通过不同的视角（每种视角都有独特的方法和立场）审查内容，并以规范化的形式报告发现。报告真实情况——绝不为了显得全面而夸大。每个视角对其内容以及零发现都设定自己的立场：对于大多数视角，空结果就是有效的；对抗性视角至少需要十个具体发现，并将空列表视为需要重新检查的信号；编辑性视角则将内容视为神圣不可侵犯，只批评其组织和表达方式。

视角集是 `{workflow.lenses}` 解析的结果，而不是固定列表——覆盖可以添加新视角并替换已安装的视角。不要从这个文件中声称任何功能；读取解析后的视角并基于它们工作。

## 输入

- **content** — 要审查的内容：差异、分支、未提交的更改、文件、规范、故事或任何文档。参数：`[路径]`。
- **lenses** (可选) — 一个或多个镜头代码或名称，无论调用者如何表达：口头请求或形式为 `skill:bmad-review lenses=<code>[,<code>...]` 的指令（bmm 的 `doc_standards` 使用此形式）。默认：所有适用的视角（全面审查）。
- **also_consider** (可选) — 与每个视角的正常分析一起考虑的领域。
- **claims** (可选) — 变更自身的叙述：它覆盖的提交消息或调用者提供的任何描述。仅用于边缘情况视角。
- **pre-resolved customization** (可选) — 由转发调用者提供的 `[workflow]` 字段值。参见执行步骤 1。

## 规范

- 纯路径（例如 `references/lens-edge-case-hunter.md`）从 `{skill-root}` 解析——这是该技能的安装目录，其中包含 `customize.toml`。`{project-root}` 是包含 `_bmad/` 的最近文件夹，从项目工作目录开始，向上遍历其父目录。
- `{workflow.<name>}` 解析到 `customize.toml` 的 `[workflow]` 表中的字段（根据 BMad 合并规则覆盖每个条目）。
- 在 `style_guide`、`review_guidance` 和 `persistent_facts` 中，以 `file:` 开头的值是路径或通配符——加载该文件的内容。如果 `file:` 值无法读取，则在输出标题中命名失败的文件并继续：`style_guide` 的已安装基线，其余条目按其他方式处理。

## 执行

1. **解析自定义设置：** `uv run {project-root}/_bmad/scripts/resolve_customization.py --skill {skill-root} --project-root {project-root} --key workflow`。
   - 脚本未找到：此处未设置 BMad。提供运行 `bmad` 技能的设置，如果尚未安装则先安装 `bmad` (`npx skills add bmad-code-org/BMAD-METHOD --skill bmad`)，然后再次运行该命令。
   - 其他任何失败：直接读取 `{skill-root}/customize.toml` 并使用默认值。

   **转发激活：** 如果调用者使用预解析的自定义字段（例如 `bmad-editorial-review` 桥接器）调用了您，请逐字尊重这些命名字段——它们已经包含用户的覆盖——并仅从自己的 `customize.toml` 中解析剩余字段。然后按顺序执行每个 `{workflow.activation_steps_prepend}` 条目，将 `{workflow.persistent_facts}` 作为会话的持久上下文，并将 `{workflow.review_guidance}` 条目作为每个视角的持久审查指令。
2. **加载内容。** 一次将其作为文件进行暂存：当内容是分支、未提交的工作或提交范围时，使用存储库的版本控制工具将统一差异写入系统临时目录中的唯一命名的文件，并取该文件的绝对路径作为内容。分支意味着其与合并基线的差异；未提交的工作包括未跟踪的文件。按相同方式暂存 `claims`——它是单个视角的输入，单独暂存，以便其他视角不会看到它。如果内容为空或无法解码为文本：当调用者期望原始发现 JSON 数组（例如，遗留的边缘情况转发器）时，返回 `[{"location":"N/A","trigger_condition":"Input empty or undecodable","guard_snippet":"Provide valid content to review","potential_consequence":"Review skipped — no analysis performed"}]`（没有 `lens` 字段）并停止；否则说明问题并请求可审查的内容。分类内容——差异、源文件、函数或文档——以及它是 **代码** 还是 **文档**；范围规则和视角适用性都取决于它。定义行为（规范、需求、计划、故事）的文档是 `docs`，行为性视角可能仍然适用；根据 `when` 判断。
3. **从 `{workflow.lenses}` 选择视角**。具有空 `instruction` 的视角被禁用。如果用户或调用者指定了视角，则仅运行这些——`applies_to` 和 `when` 不会过滤显式请求。否则，运行所有启用的视角，其 `applies_to` 覆盖内容类别（`any` 总是覆盖）且 `when` 适用。
4. **在运行任何操作之前，以一行宣布计划**：内容类别、即将运行的视角——当任何视角具有 `after` 设置时——它将在命名的视角的发现之上运行。当调用者固定了确切的输出合同（要求原始 JSON 或确切一行线的遗留转发器）时，完全跳过宣布——他们的合同涵盖您发出的所有内容，而不仅仅是发现块。然后按顺序执行每个 `{workflow.activation_steps_append}` 条目。
5. **运行独立的视角**——每个没有 `after` 的选定的视角。每个视角都看到内容和 `also_consider`，永远不会看到另一个视角的发现。遵循每个视角的 `instruction`；已安装的视角按需加载参考文件，因此仅加载运行的视角。当子代理可用时，在处理任何视角的结果之前启动每个独立的视角。尝试同时运行它们：为每个视角生成一个；给它带有 `{skill-root}` 和路径解析为绝对值的视角 `instruction`、暂存的内容文件的绝对路径（视角提示包含路径，视角读取文件，而不是内容字节；仅在内容从未作为文件暂存时才内嵌内容）、任何 `also_consider` 区域、持久审查指令、仅传递给边缘情况视角的 `claims` 路径（标记为在边缘情况视角的指令调用之前不读取）、约束“仅返回您的发现——不输出其他内容。不要调用任何技能，也不要生成您自己的子代理——您是审查者。在您的最终消息中返回您的发现作为文本；不要通过主机可能提供的任何发现报告工具进行路由。”否则，您自己按顺序运行这些视角，完成一个后再开始下一个。
6. **运行依赖的视角**——每个具有 `after` 的选定的视角，一旦命名的视角完成，就传递该视角的发现。其 `after` 目标未选中或未产生任何发现的视角仍然运行，没有任何先前的发现。命名不同目标的依赖视角相互独立：在处理任何结果之前，启动所有准备就绪的视角。尝试同时运行它们。当子代理可用时，与独立视角使用相同的约束生成它们：“仅返回您的发现——不输出其他内容。不要调用任何技能，也不要生成您自己的子代理——您是审查者。在您的最终消息中返回您的发现作为文本；不要通过主机可能提供的任何发现报告工具进行路由。”
7. **组装并呈现** 如下输出。保留每个视角的发现——视角之间的重叠是信号而不是重复；在 Markdown 报告中注明，而不是去重。如果设置了 `{workflow.on_complete}`，则执行它。

## 输出

一个包含每个视角所有发现的 JSON 数组。每个发现包含：

- `lens` — 产生它的视角的代码
- `location` — 内容中的位置（代码的文件：行范围，文档的章节）
- `trigger_condition` — 问题或暴露它的条件，用一行表示
- `guard_snippet` — 具体的修复、保护或缺失检查
- `potential_consequence` — 如果按原样发布会发生什么

每个视角文件对其发现进行语义细化，并可能添加视角特定字段（例如，删除发现的 `kind`/`confidence`，验证间隙发现的 `gap_shape`/`consumer`/`evidence`）。视角文件也可以声明自己的发现形状和渲染——编辑性视角渲染发现表——该形状将适用于该视角的发现。`[]` 是未发现时的有效值。任何地方都没有严重性、优先级或排名。

按 `{workflow.output_format}` 呈现——`"json"`（在 fenced json 块中的原始数组）、`"markdown"` 或 `"both"`——除非调用者请求了特定形状；遗留转发器的输出合同始终获胜，并控制您发出的所有内容，而不仅仅是发现块。Markdown 报告按视角分组发现，每个视角按其声明的形状渲染：每个发现渲染字段加上任何值得展示的额外信息，为未发现任何内容的视角一行，以及当整个审查干净时一个干净的纯声明。按 `{workflow.output_preferences}` 形状报告。

当 `{workflow.report_path}` 设置时，将报告写入该路径；否则在聊天中呈现。
