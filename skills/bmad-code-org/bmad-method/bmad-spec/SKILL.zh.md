# BMad Spec
## 概述

BMad spec-kernel 生态系统的规范转换器。接受任何意图输入——模糊想法、思维导图、PRD、GDD、RFC、简报、Slack 聊天记录、客户邮件、会议记录、原型图、混合多源——并生成 **spec-{slug}.md**，包含五字段内核（为什么、能力、约束、非目标、成功信号）以及用于承载不适合内核或会导致内核膨胀的扩展性条目细节的配套文件。它们共同构成了下游 BMad 技能所消费的机器合同。

多个技能可能随时间调用更新相同的规范。

## 规范

- 纯路径（例如 `assets/spec-template.md`）从技能根目录解析。
- `{skill-root}` 是此技能的安装目录；`{project-root}` 是包含 `_bmad/` 的最近文件夹，从工作目录开始并通过其父级向上查找。
- `{workflow.<name>}` 解析到 `customize.toml` 中的字段。

## 激活时

1. 解析自定义：`uv run {project-root}/_bmad/scripts/resolve_customization.py --skill {skill-root} --project-root {project-root} --key workflow`。
   - 脚本未找到：此处未设置 BMad。建议运行 `bmad` 技能的设置，如果尚未安装 `bmad` 则先安装 `npx skills add bmad-code-org/BMAD-METHOD --skill bmad`，然后再次运行该命令。
   - 其他任何失败：直接读取 `{skill-root}/customize.toml`。
2. 运行 `{workflow.activation_steps_prepend}`。将 `{workflow.persistent_facts}` 视为基础上下文（`file:` 条目被加载）。
3. 解析配置：`uv run {project-root}/_bmad/scripts/resolve_config.py --project-root {project-root} --key core.output_folder --key core.active_initiative`。`{date}` 是当前系统日期。
   - 脚本未找到，或无 `output_folder`：此处未设置 BMad。建议运行 `bmad` 技能的设置，如果尚未安装 `bmad` 则先安装 `npx skills add bmad-code-org/BMAD-METHOD --skill bmad`，然后再次运行该命令。
   - 无 `active_initiative`：将任务交给 `bmad` 技能设置或创建一个，然后再次运行该命令并继续。无头模式：写入松散。
4. 检测模式。**无头模式** 当任何以下情况发生：无 TTY、程序调用者（另一个技能或非交互式运行器），或第一条消息预先提供所有输入并请求返回工件路径。**交互模式** 其他情况。在交互模式下，向用户打招呼并提及 `bmad-party-mode` 和 `bmad-advanced-elicitation` 可用于对任何字段进行深入探索。

运行 `{workflow.activation_steps_append}`。

激活完成。如果 `activation_steps_prepend` 或 `activation_steps_append` 非空，请在继续之前确认每个条目按顺序执行。在所有激活步骤完成之前，不要开始主工作流。

## 工作区

规范始终是一个名为 `{workflow.spec_output_path}/{workflow.run_folder_pattern}` 的文件夹，默认解析为 `{output_folder}/{active_initiative}/spec-{slug}/`。

`{slug}` 描述的是被规范的对象，而不是输入形状：

- 源工件已包含 slug（例如 `prd-foo-bar/`）：继承（`foo-bar`）。
- 稀疏、聊天中或多源输入：交互式询问；无头调用者作为输入的一部分提供它。如果缺失且无法推导，无头模式会以 `error_code: "missing_slug"` 块。
- 相同 slug = 相同文件夹。使用相同 `{slug}` 的第二次调用将落在现有的规范文件夹中并就地更新，保留能力 ID。

**无输入。** 交互式：要求用户共享文件路径、粘贴内容、详细解释想法或指向源。无头模式：以包含 `error_code: "insufficient_intent"` 的 JSON 响应。

在工作区文件夹内：

```
<spec-folder>/
  spec-<slug>.md           ← 内核，以文件夹命名——从 .memlog.md 派生，从未手动编辑
  <companion-1>.md         ← 可选，内容类型化（例如 glossary.md）；规范撰写的配套文件也派生
  <companion-2>.md
  .memlog.md               ← 规范——追加仅有的、按时间顺序记录每个决策、约束、能力（及其稳定的 `CAP-N`）、假设、开放问题以及用户指导的追加仅有的、按时间顺序的记录；每行一个，按发生顺序，从未编辑或重新排序。`spec-{slug}.md` 和每个规范撰写的配套文件都在每次运行时从 memlog（记录决策）和它引用的原始内容源派生——从未手动修补。
```

## 记忆和派生

`.memlog.md` 是规范的——追加仅有的、按时间顺序的记录，记录每个决策、约束、能力（及其稳定的 `CAP-N`）、假设、开放问题以及用户指导，每行一个，按发生顺序，从未编辑或重新排序。`spec-{slug}.md` 和每个规范撰写的配套文件在每次运行时从 memlog（记录决策）和它引用的原始内容源派生——从未手动修补。

从活着的日志中生成合同，而不是就地编辑合同，是允许规范周围的步骤（PRD、UX、架构、史诗）以任何顺序运行并相同地提供规范而无需合并漂移的原因：日志仅累积，工件被重新渲染。因此，规范仅通过在此重新派生来更新——bmad-spec 是其唯一的写入者；来自外部的 `spec-{slug}.md` 手动编辑不受支持，并在下次派生时被覆盖。

写入通过共享脚本——`{project-root}/_bmad/scripts/memlog.py`，与 `resolve_customization.py` 相同的位置（原子；除了恢复外，不要读取它）：

- `uv run {project-root}/_bmad/scripts/memlog.py init --workspace {spec-folder} --field topic="<正在规范的内容>"` — 创建时，一次。
- `uv run {project-root}/_bmad/scripts/memlog.py append --workspace {spec-folder} --type <decision|constraint|capability|assumption|question|direction|note|event> --text "<一句话的摘要，包括原因>"` — 每次到达时。
- 终端时刻（验证结果、"规范最终确定"）是 `--type event` 条目；memlog 不携带状态字段。

## 操作

读取输入及其辅助链接材料。如果无输入，则遵循 **工作区** 中的无输入分支（询问或阻塞）。如果目标文件夹存在先前的 `.memlog.md`，则读取它——操作变为更新，memlog（而不是渲染的 `spec-{slug}.md`）是关于已决定内容和能力 ID 的权威。保留这些 ID；新能力获得下一个未使用的 `CAP-N`；从不重用已退役的 ID。否则这是创建，第一个操作是 `memlog.py init`。

当输入结构化和预先排序（PRD 带有补充、GDD、由上游 BMad 技能生成的简报）时，信任作者的分隔：将内核适配内容提升到 spec-{slug}.md，将溢出提升到命名适当的配套文件。当输入混合（思维导图、记录、RFC、客户邮件）时，自己进行排序：逐个检查声明，应用三镜头承载测试（规范法规则 7），并将路由到内核字段或配套文件。

使用 `{workflow.spec_template}` 作为骨架，将输入蒸馏成五字段内核。当输入丰富时，直接提取——无需引导。当输入稀疏时，选择：**表达**（最佳尝试蒸馏，每个空白都成为 `open_questions[]` 条目）或 **引导**（逐个与用户一起走遍五个字段）。无头模式默认为表达并记录选择。交互式询问。

输入留下的已识别领域含义未解决的情况是空白——将其命名为 `open_questions[]` 条目（医疗输入对 PHI/HIPAA 保持沉默、支付对 PCI 保持沉默、控制系统对故障安全保持沉默）并继续。标记它；永远不要编造答案或指导它。如果这些占主导地位，输入太薄——建议 `bmad-prd`。

第一次通过时写精益：每个句子都必须证明其存在。装饰成本代币并稀释下游读者。

将每个决策、能力、约束和接受的更改记录到 `.memlog.md` 中——那是渲染读取的运行记录。由于日志是追加仅有的，较晚的条目在同一点上覆盖较早的条目，而历史保持完整。当两个当前活动的源或配套文件对同一字段意见不一致，或一个或或从未解决时，将其呈现给用户，而不是默默选择——解决本身就是一个新的 memlog 条目。

如果输入确实太薄无法蒸馏（例如，“为徒步者开发的应用程序”没有任何周围上下文），停止并建议 `bmad-prd`（或兄弟仪式技能）。此技能蒸馏；它不指导。

## 承载

如果任何消费者（下游技能、实现代理、验证传递）会因它而改变决策，则声明是 **承载** 的。

## 配套文件

当承载内容不适合五字段内核时，它将存放在配套文件中。内核引用它；配套文件持有它。配套文件是合同的一部分；每个消费者读取 `companions:` 以发现规范-{slug}.md 前置中的它们。配套文件遵循与 spec-{slug}.md 相同的精益纪律（规范法规则 8）。

**当内容需要超过一个内核形状的行时生成配套文件：** 多项目录（例如实体的矩阵，如原型、饮料、模式、路线）、表格、图表（始终）、编辑声音规则、长格式参考材料，内核通过名称引用（词汇表、棕色字段笔记、项目约定）。单行决策弯曲者留在约束中；意图+成功对留在能力中。如果内核字段开始变成子点，内容已超出内核并希望有配套文件。

配套文件要么：

- **规范撰写的配套文件** 由 bmad-spec 撰写并作为 spec-{slug}.md 的**兄弟**存在（例如，`glossary.md`、`patron-archetypes.md`）。bmad-spec 拥有它们，并在更新操作中可以编辑它们。
- **采用的配套文件** 是由上游技能撰写的承载工件，下游仍然需要读取。bmad-spec 将它们引用到 `companions:` 中，但**不编辑**它们（例如，来自 UX 运行的 `DESIGN.md` 或 `EXPERIENCE.md`、集成伙伴的 API 规范）。原始技能拥有它们。

两个规则管理配套文件：

1. **为规范撰写的配套文件命名以反映其持有的内容类型。** `glossary.md`、`<entity-class>.md`（例如 `patron-archetypes.md`、`medication-routes.md`、`flight-modes.md`）、`stack.md`、`conventions.md`、`brownfield.md`、`architecture-diagrams.md`、`state-machines.md`、`failure-modes.md`、`compliance-references.md`。原则：“读者在打开之前应知道里面有什么。” 采用的配套文件保留其原始技能给它们的名称。
2. **图表始终存放在配套文件中**，无论大小如何。spec-{slug}.md 内核仅包含文本。Mermaid 块、ASCII 图表和图像引用都存放在配套文件中（例如 `architecture-diagrams.md`），从那里引用兄弟图像文件。

现有项目范围文档（例如 `project-context.md`）如果下游需要，则列为**采用的配套文件**，永远不会复制到 spec-{slug}.md 或规范撰写的配套文件中。

## 规范法

每个规范必须满足这八条规则。操作旨在实现它们；自我验证扫描强制执行它们。

1. **每个能力都有 `intent` 和 `success`。** 缺少任何一项 = 不是能力。
2. **意图描述 WHAT，而不是 HOW。** 实现处方属于配套文件（堆栈、约定）。
3. **约束实际弯曲设计决策。** 没有排除任何东西的“约束”是装饰。
4. **非目标是明确的。** 至少有一个。缺失意味着下游技能填补了真空。
5. **成功信号足够具体，可以测试或演示。** “用户喜欢它”不合格。
6. **能力 ID 是稳定且唯一的。** 从不重用，从不重新编号。
7. **保留。** 每个承载的源声明都落在 spec-{slug}.md 或配套文件中。包装仪式不保留。
8. **精益文本。** 每个句子都承载承载内容。删除装饰、保留、背景故事、清场。适用于 spec-{slug}.md、配套文件和 `.memlog.md`。

## 自我验证

在每次创建或更新后，在呈现之前，对结果工件进行**两次扫描**。

**扫描 1 — 一致性。** 将规范与规范法规则 1–6 和 8 对比。对于任何失败或感觉薄弱的内容，尝试在不编造输入未支持的内容的情况下修复它。没有直接确认的调用成为 `assumptions[]`；无法填补的空白成为 `open_questions[]`。

**扫描 2 — 保留。** 逐个检查源声明。确认每个承载声明都落在 spec-{slug}.md 或配套文件中。包装仪式丢弃的内容在“仅包装内容”下记录，以便丢弃在记录中，而不是沉默。

将每个扫描的裁决记录到 `.memlog.md` 中（`append --type event`）。在交互模式下，与用户一起查看它。在无头模式下，`.memlog.md` 是返回的文件之一，因此调用者（或其下游 LLM）在那里读取裁决。

## 无变更信号时规范

当用户将技能指向现有规范文件夹（或其 spec-{slug}.md）且无变更信号时，建议审查假设或开放问题，或确定他们想做什么。

## 传递给 `bmad-ticket`（可选，仅交互式）

需要 `spec-{slug}.md` 存在磁盘上——如果不存在，则首先运行正常操作。无头运行永远不会这样做，即使调用文本要求它：如果模式检测（激活时，步骤 4）解析为无头，则完全跳过本节，并继续正常无头响应。在交互模式下，当输入读取为多个独立可交付的切片时，最多一次提供传递；拒绝结束本次运行的提议，而不是永远。

将规范文件夹传递给 `bmad-ticket` 作为要求源：它作为用户史诗计划工作，其 `tickets.toml` 条目引用此规范的 `CAP-N` ID，并从这里运行看板。承载细节切片对话揭示的（约束、设计决策）作为规范更新返回，而不是单独返回到票据。

当规范更新运行时，搜索票据根对此规范文件夹路径的引用；在引用它的票据中，命名描述不再匹配的条目和票据，并建议用 `bmad-ticket` 重新切片它们。更新本身永远不会编辑票据。

## 输出

**交互式**——对话式共享规范文件夹路径。命名能力计数、生成的配套文件和裁决。如果 `assumptions[]` 或 `open_questions[]` 非空，列出它们（简短——每行一个），并邀请用户逐个查看。明确指出解决这些问题可以更新源输入（如果是文件）、规范或两者——用户更喜欢哪种组合。不要转储 JSON 或呈现一堵墙的输出。

**无头**——根据 `assets/headless-schemas.md` 返回 JSON。

如果设置了 `{workflow.on_complete}`，则运行它。

## 输出规范后

规范的任何更新——解决的假设、回答的开放问题、其他更改——都是按发生时追加到 `.memlog.md` 的。当更改覆盖来自源输入的内容时，建议更新该源，以便上游和规范不会沉默地分化。

## 前置规范约定

- `companions:` 数组，下游**必须**与 spec-{slug}.md 一起读取以获得完整合同。路径可以指向规范文件夹内（规范撰写的配套文件，如 `glossary.md`）或规范文件夹外（采用的配套文件，如 `../ux-foo-bar/DESIGN.md`）。规范撰写和采用之间的区别由路径隐含；下游将两者视为相同。
- `sources:` 数组，指向被**完全吸收**到 SPEC 中的文件路径，没有剩余的下游价值（例如，PRD 的每个承载声明现在都在内核中）。列出以供审计，并供 bmad-spec 在更新时重新读取。下游**不**读取这些。下游仍然需要的文件属于 `companions:`，而不是这里。
- **不要列出** memlog、README 文件、组织工件或任何上游技能生成其工件的操作记录。这些不是源内容；它们是下游消费者不需要的过程元数据。
