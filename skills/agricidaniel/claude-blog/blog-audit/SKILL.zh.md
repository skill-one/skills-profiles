# 博客审核：全站健康评估

对项目中的所有博客文章进行全面健康评估。
扫描质量评分、孤立页面、主题竞争、过时内容以及 AI 引用准备情况。
使用规范分析器 JSON 作为评分来源，并生成优先级行动队列。

## 审核流程

### 第 1 步：发现博客文件

扫描项目中所有博客内容文件：

- 递归地在常见的博客目录和 CMS 导出文件夹中查找 `.md`、`.mdx`、`.html`、`.astro`、`.svelte`、`.vue`、`.tsx` 和 `.jsx` 文件
- 常见路径检查：
  - `content/`
  - `posts/`
  - `blog/`
  - `src/content/`
  - `_posts/`
  - `pages/blog/`
  - `articles/`
  - `content/blog/**`
  - 用户明确提供的 CMS 导出文件夹
  - `src/pages/blog/`
- 过滤隐藏、供应商、生成和与秘密相关的路径：`.git/`、点目录、`node_modules/`、`vendor/`、`dist/`、`build/`、`.next/`、`coverage/`、`reports/`、生成导出、README、CHANGELOG、LICENSE、配置文件、SKILL.md、包文件、`.env*`、密钥和私人笔记
- 报告："在 [目录] 中找到 N 个博客文件"

如果在标准位置未找到博客文件，则请求允许的根目录或仅搜索用户批准的内容目录。默认情况下，不要扫描整个项目根目录。

### 第 2 步：规范批量分析

首先运行规范分析器输出，并将其作为每篇文章评分的来源：

```bash
python3 scripts/analyze_blog.py <blog-root> --batch --format json
```

分块处理文件，限制并行后续工作为一个小固定数量，尊重上下文限制，并聚合确定性 JSON，包含 `file`、`score`、`categories`、`issues` 和 `metadata`。在以下的全站检查之上叠加分析器 JSON，而不是单独的评分标准。

#### 内容质量层
- 在 30 分内容质量量表上对每篇文章进行评分
- 检查段落长度（目标 40-80 个词，硬限制 150）
- 检查句子长度（目标 15-20 个词）
- 评估标题结构和使用问答格式标题
- 使用角色和内容类型评估可读性：消费者内容倾向于更简单的级别，专业内容可以是中等，技术内容在清晰度保持高的情况下可能更密集

#### SEO 优化层
- 按文章检查页面 SEO 元素：
  - 标题标签长度（40-60 个可接受，50-60 个理想，仅预览警告）
  - 元描述简洁且针对页面。统计数据是可选的，必须可见且来源可靠
  - H1 存在性和唯一性
  - 图片替代文本覆盖率
  - 内部和外部链接数量
  - URL 拼缀质量

#### 规范验证层
- 在所有文章中检测结构化数据
- 验证 Article/BlogPosting、Person、Organization 和 BreadcrumbList 规范的完整性
- 如果存在 FAQPage，则将其作为可选实体标记进行验证，而不是 Google 富结果
- 规范化 `dateModified`、`lastUpdated`、`updated` 和 `lastmod`，包括时区规范化的生成规范，然后要求新鲜度一致性
- 标记缺失或格式错误的规范

#### 链接健康层
- 映射所有文章中的内部链接
- 构建有向链接图
- 检测孤立页面（零内部入站链接）
- 检测死端页面（零内部出站链接）
- 检查损坏的内部链接目标
- 推荐双向链接机会

#### 新鲜度检查层
- 从每篇文章的前置代码中读取 `lastUpdated` 或 `dateModified`
- 计算自上次更新以来的天数
- 根据内容类型、来源或统计数据年龄和 GSC 衰减标记新鲜度，而不是通用天数计数
- 按刷新优先级分类

#### AI 准备层
- 对每篇文章的 AI 引用准备情况进行评分
- 检查段落级可引用性（120-180 个词的段落）
- 评估问答格式和实体清晰度
- 检查 TL;DR 盒子和引用胶囊
- 检查 robots.txt、llms.txt、SSR/SSG 输出、JS 隔离内容、阻止的资产、GPTBot、ClaudeBot、PerplexityBot、Googlebot 和 Google-Extended 政策

### 第 2.5 步：技术抓取和搜索性能

在最终建议之前添加全站技术检查：

- 验证站点地图覆盖率、robots.txt、noindex 指令、规范标签、重定向、HTTP 状态码、hreflang 和内部规范一致性
- 在可用时使用 `blog-google` 进行核心 Web 价值、GSC 查询、URL 检查、索引状态和 GA4 上下文
- 报告跳过可选检查的原因，例如 `SKIPPED: 凭据不可用`

### 第 3 步：主题竞争检测

分析所有文章中的关键词竞争：

1. 从每篇文章中提取主要关键词/主题：
   - 标题文本
   - H1 标题
   - 元描述
   - 第一段
2. 使用停用词处理、词元化、区域感知和意图修饰符规范化关键词
3. 使用分析器数据、嵌入或显式置信度、可用时的 GSC 查询到 URL 数据和可用时的 SERP 重叠进行意图聚类
4. 使用以下建议之一标记竞争文章：
   - **合并**：将两个弱文章合并成一个强文章
   - **重定向**：301 重定向较弱的文章到较强的文章，同时保留反向链接、验证重定向映射并更新内部链接
   - **区分**：调整焦点，使文章针对不同的意图

### 第 4 步：孤立页面检测

构建和分析内部链接图：

1. 对抗站点配置和站点地图规范化 URL，包括相对链接、同域绝对路径、尾随斜杠、生成路由、锚点、斜杠映射
2. 构建邻接图：`{ 页面 -> [它链接到的页面] }`
3. 构建反向图：`{ 页面 -> [链接到它的页面] }`
4. 识别孤立页面：具有零内部入站链接的文章
5. 识别死端页面：具有零内部出站链接的文章
6. 对于每个孤立页面，根据主题相关性推荐 2-3 个现有文章应链接到它

### 第 5 步：过时内容检测

审计所有文章的内容新鲜度：

1. 读取前置代码字段：`lastUpdated`、`dateModified`、`date`、`updated`
2. 计算每篇文章自上次更新以来的天数
3. 按刷新优先级分类：
   - **高**：易变主题、过时来源或统计数据或 GSC 衰减
   - **中**：常青主题，但示例、链接或截图正在老化
   - **低**：最近验证或稳定参考内容
4. 估计每篇文章的刷新工作量：
   - 轻度刷新：更新统计数据，检查链接（1-2 小时）
   - 中度刷新：重写部分，添加新数据（3-4 小时）
   - 重度刷新：建议全文重写（5+ 小时）

### 第 6 步：生成全站报告

将所有结果汇总到一个综合报告中：

#### 摘要仪表板
```
## 博客审核报告

**审核日期：** [日期]
**总文章数：** N
**平均分：** XX/100

### 健康概述
| 指标 | 数量 |
|------|-------|
| 评分 90+（优秀）的文章 | N |
| 评分 70-89（良好）的文章 | N |
| 评分 50-69（需要改进）的文章 | N |
| 评分 <50（差）的文章 | N |
| 孤立页面 | N |
| 死端页面 | N |
| 主题竞争问题 | N |
| 过时或衰减内容 | N |
```

#### 每篇文章表格
```
### 每篇文章评分
| 文件 | 分数 | 内容 | SEO | E-E-A-T | 技术 | AI 引用 | 问题 |
|------|-------|---------|-----|---------|-----------|-------------|--------|
| [文件名] | XX/100 | X/30 | X/25 | X/15 | X/15 | X/15 | [数量] |
```

#### 优先级行动队列
```
### 优先级行动队列（最低分优先）
| 优先级 | 文件 | 分数 | 主要问题 | 推荐行动 |
|----------|------|-------|-----------|--------------------|
| 1 | [文件] | XX | [问题] | [行动] |
| 2 | [文件] | XX | [问题] | [行动] |
```

#### 主题竞争报告
```
### 主题竞争
| 关键词 | 竞争文章 | 建议 |
|---------|----------------|----------------|
| [关键词] | post-a.md, post-b.md | 合并 / 重定向 / 区分 |
```

#### 孤立页面
```
### 孤立页面（无入站链接）
| 页面 | 入站链接 | 推荐链接来源 |
|------|---------------|--------------------------|
| [文件] | 0 | post-a.md, post-b.md, post-c.md |
```

#### 过时内容
```
### 过时内容
| 文件 | 最后更新 | 过时天数 | 优先级 | 刷新工作量 |
|------|-------------|------------|----------|----------------|
| [文件] | [日期] | [N] | 高/中/低 | 轻/中/重 |
```

### 第 7 步：保存报告

在 `reports/` 下保存带时间戳的 Markdown 和 JSON 导出，例如 `reports/blog-audit-YYYY-MM-DD.md` 和 `reports/blog-audit-YYYY-MM-DD.json`。不要覆盖以前的审核报告。

保存后，通知用户：
- 报告位置：`[项目根目录]/reports/blog-audit-YYYY-MM-DD.md` 和 `[项目根目录]/reports/blog-audit-YYYY-MM-DD.json`
- 发现摘要（总文章数、平均分、关键问题数量）
- 建议首先在最低分的文章上运行 `/blog analyze <文件>`
- 建议在关键文章上运行 `/blog flow optimize` 进行 AI 引用 SEO 检查
