## 清单目的：“需求单元测试”

**核心概念**：清单是**需求写作的单元测试**——它们验证给定领域内需求的**质量、清晰度和完整性**。

**不用于验证/测试**：

- ❌ 不是“验证按钮点击正确”
- ❌ 不是“测试错误处理工作”
- ❌ 不是“确认API返回200”
- ❌ 不是检查代码/实现是否与规范匹配

**用于需求质量验证**：

- ✅ “是否为所有卡片类型定义了视觉层级需求？”（完整性）
- ✅ “‘突出显示’是否用具体的尺寸/位置量化？”（清晰度）
- ✅ “所有交互元素上的悬停状态需求是否一致？”（一致性）
- ✅ “是否定义了键盘导航的可访问性需求？”（覆盖范围）
- ✅ “规范是否定义了徽标图像加载失败时的行为？”（边缘情况）

**比喻**：如果你的规范是用英语编写的代码，那么清单就是它的单元测试套件。你正在测试需求是否写得良好、完整、无歧义，并准备好实施——而不是测试实现是否工作。

**所有权和复选框生命周期**：

- 由此命令生成的自定义清单是需求质量审查的审查者拥有的工件。
- `[x]`表示审查者确定需求质量标准已满足。
- `[x]`不表示实现工作已完成。
- 此命令生成或追加清单项；它**必须**不标记生成的项为`[x]`。
- 当审查者明确要求时，代理可以协助评估项目。
- `checklists/requirements.md`是一个由`/speckit-specify`和`/speckit-clarify`维护的独立内置规范质量清单；不要将其视为适用于此处生成的自定义清单的例外。

## 用户输入

```text
$ARGUMENTS
```

在继续之前，你必须考虑用户输入（如果非空）。

## 执行前检查

**检查扩展钩子（在清单生成之前）**：

- 检查项目根目录中是否存在`.specify/extensions.yml`。
- 如果存在，读取它并查找`hooks.before_checklist`键下的条目。
- 如果YAML无法解析或无效，不要无声地跳过：告诉用户`.specify/extensions.yml`无法读取（包括解析错误），并且没有检查钩子，包括任何注册的强制（`optional: false`）钩子，然后正常继续。
- 过滤掉`enabled`显式为`false`的钩子。将没有`enabled`字段的钩子视为默认启用。
- 对于每个剩余的钩子，**不要**尝试解释或评估钩子`condition`表达式：
  - 如果钩子没有`condition`字段，或者它是空/空，将钩子视为可执行。
  - 如果钩子定义了非空的`condition`，则跳过钩子，并将条件评估留给HookExecutor实现。
- 在从钩子命令名称构建命令调用时，将点（`.`）替换为连字符（`-`）。例如，`speckit.git.commit` → `/speckit-git-commit`。
- 对于每个可执行钩子，根据其`optional`标志输出以下内容：
  - **可选钩子**（`optional: true`）：

    ```text
    ## 扩展钩子

    **可选预钩子**：{extension}
    命令：`/{command}`
    描述：{description}

    提示：{prompt}
    要执行：`/{command}`
    ```

  - **强制钩子**（`optional: false`）：

    ```text
    ## 扩展钩子

    **自动预钩子**：{extension}
    执行：`/{command}`
    EXECUTE_COMMAND：{command}

    在继续执行步骤之前，等待钩子命令的结果。
    ```

    在发出上述块后，你必须实际调用钩子并等待它完成才能继续。以与你在此代理/会话中自己运行命令相同的方式运行它（调用可能与上面显示的原始`{command}` ID不同，例如，技能模式代理作为`/skill:speckit-...`或`$speckit-...`运行）。仅发出块本身不会运行钩子。
- 如果没有注册钩子或`.specify/extensions.yml`不存在，则无声地跳过

## 执行步骤

1. **设置**：从仓库根目录运行`.specify/scripts/bash/check-prerequisites.sh --json --template checklist-template`并解析JSON以获取FEATURE_DIR、AVAILABLE_DOCS列表和TEMPLATE_CONTENT。
   - 所有文件路径必须是绝对路径。
   - 对于像"I'm Groot"这样的参数中的单引号，使用转义语法：例如 'I'\''m Groot'（如果可能，也可以使用双引号："I'm Groot"）。

2. **IF EXISTS**：加载`.specify/memory/constitution.md`以获取项目原则和治理约束。

3. **澄清意图（动态）**：导出最多**三个**初始上下文澄清问题（不要使用预构建的目录）。它们必须：
   - 从用户的措辞和从规范/计划/任务中提取的信号生成。
   - 仅询问对清单内容有实质性影响的信息。
   - 如果在`$ARGUMENTS`中已经明确，则单独跳过。
   - 优先考虑精确性而不是广度

   生成算法：
   1. 提取信号：功能领域关键词（例如，auth、延迟、UX、API）、风险指标（“关键”、“必须”、“合规”）、利益相关者提示（“QA”、“审查”、“安全团队”）、以及明确的交付成果（“a11y”、“回滚”、“合同”）。
   2. 将信号聚类为候选焦点区域（最多4个），按相关性排序。
   3. 如果未明确指定，则识别可能的受众和时机（作者、审查者、QA、发布）。
   4. 检测缺失的维度：范围广度、深度/严谨性、风险强调、排除边界、可衡量的验收标准。
   5. 从以下原型中制定问题：
      - 范围细化（例如，“此范围是否应包括与X和Y的集成触点，还是仅限于本地模块正确性？”）
      - 风险优先级（例如，“这些潜在风险区域中哪些应接收强制门控检查？”）
      - 深度校准（例如，“这是一个轻量级的预提交合理性列表，还是一个正式的发布门控？”）
      - 受众框架（例如，“这将仅由作者使用，还是在PR审查期间由同行使用？”）
      - 边界排除（例如，“这一轮是否应明确排除性能调优项？”）
      - 场景类差距（例如，“未检测到恢复流程——回滚/部分故障路径是否在范围内？”）

   问题格式规则：
   - 如果提供选项，生成一个紧凑的表格，列：选项 | 候选 | 它为什么重要
   - 最多限制为A-E选项；如果自由形式答案更清晰，则省略表格
   - 永远不要要求用户重述他们已经说过的话
   - 避免推测性类别（不要幻觉）。如果不确定，请明确询问：“确认X是否属于范围。”

   交互不可能时的默认值：
   - 深度：标准
   - 受众：如果与代码相关，则为审查者（PR）；否则为作者
   - 焦点：前两个相关性集群

   输出问题（标记Q1/Q2/Q3）。回答后：如果≥2场景类（替代/异常/恢复/非功能性领域）仍然不明确，你可以最多再问**两个**有针对性的后续问题（Q4/Q5），每个问题附带一条简短的理由（例如，“未解决的恢复路径风险”）。不要超过五个总问题数。如果用户明确拒绝更多，则跳过升级。

4. **理解用户请求**：结合`$ARGUMENTS` + 澄清答案：
   - 推导清单主题（例如，安全、审查、部署、UX）
   - 合并用户明确提到的必须包含的项
   - 将焦点选择映射到类别框架
   - 从规范/计划/任务中推断任何缺失的上下文（不要幻觉）

5. **加载功能上下文**：从FEATURE_DIR读取：
   - spec.md：功能需求和范围
   - plan.md（如果存在）：技术细节、依赖关系
   - tasks.md（如果存在）：实施任务

   **上下文加载策略**：
   - 仅加载与活动焦点区域相关的必要部分（避免全文转储）
   - 优先将长部分总结为简洁的场景/需求要点
   - 使用渐进式披露：只有在检测到差距时才添加后续检索
   - 如果源文档很大，生成中间总结项，而不是嵌入原始文本

6. **生成清单**——使用TEMPLATE_CONTENT作为结构模板，并创建“需求的单元测试”：
   - 如果`FEATURE_DIR/checklists/`目录不存在，则创建它
   - 生成唯一的清单文件名：
     - 使用基于领域的简短、描述性名称（例如，`ux.md`、`api.md`、`security.md`）
     - 格式：`[domain].md`
   - 文件处理行为：
     - 如果文件不存在：创建新文件并从CHK001开始编号项目
     - 如果文件存在：将新项追加到现有文件，从最后一个CHK ID继续（例如，如果最后一个项是CHK015，则从CHK016开始新项）
   - 永远不要删除或替换现有清单内容——始终保留并追加
   - 留下每个新生成项未选中（`[ ]`）；复选框状态属于审查者

   **核心原则——测试需求，而不是实现**：
   每个清单项必须评估需求本身，以检查：
   - **完整性**：所有必要的需求是否存在？
   - **清晰度**：需求是否无歧义且具体？
   - **一致性**：需求是否与其他需求一致？
   - **可衡量性**：需求是否可以客观验证？
   - **覆盖范围**：是否所有场景/边缘情况都已覆盖？

   **类别结构**——按需求质量维度分组：
   - **需求完整性**（所有必要需求是否记录在案？）
   - **需求清晰度**（需求是否具体且无歧义？）
   - **需求一致性**（需求是否没有冲突？）
   - **验收标准质量**（成功标准是否可衡量？）
   - **场景覆盖范围**（是否所有流程/案例都已覆盖？）
   - **边缘情况覆盖范围**（是否定义了边界条件？）
   - **非功能性需求**（性能、安全、可访问性等——是否指定？）
   - **依赖关系和假设**（是否记录并验证？）
   - **歧义和冲突**（需要澄清什么？）

   **如何编写清单项——“需求的单元测试”**：

   ❌ **错误**（测试实现）：
   - "验证首页显示3个剧集卡片"
   - "测试桌面上的悬停状态工作"
   - "确认徽标点击导航到首页"

   ✅ **正确**（测试需求质量）：
   - "是否指定了精确的 featured 剧集数量和布局？" [完整性]
   - "‘突出显示’是否用具体的尺寸/位置量化？" [清晰度]
   - "所有交互元素上的悬停状态需求是否一致？" [一致性]
   - "是否为所有交互UI定义了键盘导航需求？" [覆盖范围]
   - "徽标图像加载失败时的回退行为是否指定？" [边缘情况]
   - "是否为异步剧集数据定义了加载状态？" [完整性]
   - "规范是否定义了竞争UI元素的视觉层级？" [清晰度]

   **项结构**：
   每个项应遵循此模式：
   - 询问需求质量的问题格式
   - 关注规范/计划中**写有或未写有**的内容
   - 包括质量维度在括号中 [完整性/清晰度/一致性等]
   - 检查现有需求时引用规范部分 `[Spec §X.Y]`
   - 使用 `[Gap]` 标记检查缺失的需求

   **按质量维度分类的示例**：

   完整性：
   - "是否为所有API故障模式定义了错误处理需求？ [Gap]"
   - "是否为所有交互元素指定了可访问性需求？ [完整性]"
   - "是否定义了响应式布局的移动断点需求？ [Gap]"

   清晰度：
   - "‘快速加载’是否用具体的定时阈值量化？ [清晰度, Spec §NFR-2]"
   - "‘相关剧集’选择标准是否明确定义？ [清晰度, Spec §FR-5]"
   - "‘突出’是否用可测量的视觉属性定义？ [歧义, Spec §FR-4]"

   一致性：
   - "导航需求是否在所有页面上一致？ [一致性, Spec §FR-10]"
   - "卡片组件需求在首页和详情页之间是否一致？ [一致性]"

   覆盖范围：
   - "是否定义了零状态场景（无剧集）的需求？ [覆盖范围, 边缘情况]"
   - "是否处理了并发用户交互场景？ [覆盖范围, Gap]"
   - "是否指定了部分数据加载失败的需求？ [覆盖范围, 异常流程]"

   可衡量性：
   - "视觉层级需求是否可测量/可测试？ [验收标准, Spec §FR-1]"
   - "‘平衡视觉重量’是否可以客观验证？ [可衡量性, Spec §FR-2]"

   **场景分类和覆盖范围**（需求质量焦点）：
   - 检查是否存在针对：主要、替代、异常/错误、恢复、非功能性场景的需求
   - 对于每个场景类，询问：“[场景类型]需求是否完整、清晰且一致？”
   - 如果场景类缺失："[场景类型]需求是否有意排除或缺失？ [Gap]"
   - 包括状态变更时的弹性/回滚："是否为迁移故障定义了回滚需求？ [Gap]"

   **可追溯性需求**：
   - **最低要求**：≥80%的项必须至少包含一个可追溯性参考
   - 每个项应引用：规范部分 `[Spec §X.Y]`，或使用标记：`[Gap]`、`[歧义]`、`[冲突]`、`[假设]`
   - 如果没有ID系统："是否建立了需求和验收标准的ID方案？ [可追溯性]"

   **表面和解决问题**（需求质量问题）：
   询问需求本身：
   - 歧义： "术语'快速'是否用具体指标量化？ [歧义, Spec §NFR-1]"
   - 冲突： "导航需求在§FR-10和§FR-10a之间是否冲突？ [冲突]"
   - 假设： "假设'始终可用的播客API'是否已验证？ [假设]"
   - 依赖关系： "是否记录了外部播客API需求？ [依赖关系, Gap]"
   - 缺失定义： "‘视觉层级’是否用可测量的标准定义？ [Gap]"

   **内容整合**：
   - 硬性上限：如果原始候选项 > 40，按风险/影响优先级
   - 合并检查相同需求方面的近似重复项
   - 如果>5个低影响边缘情况，创建一个项： "是否在需求中解决了边缘情况X、Y、Z？ [覆盖范围]"

   **🚫 绝对禁止**——这些使其成为实施测试，而不是需求测试：
   - ❌ 任何以"Verify"、"Test"、"Confirm"、"Check"开头并加上实现行为的项
   - ❌ 参考代码执行、用户操作、系统行为
   - ❌ "显示正确"、"工作正常"、"按预期工作"
   - ❌ "点击"、"导航"、"渲染"、"加载"、"执行"
   - ❌ 测试用例、测试计划、QA流程
   - ❌ 实现细节（框架、API、算法）

   **✅ 必须模式**——这些测试需求质量：
   - ✅ "是否为[需求类型]定义/指定/记录了[场景]？"
   - ✅ "是否用具体标准量化/澄清了[模糊术语]？"
   - ✅ "需求在[部分A]和[部分B]之间是否一致？"
   - ✅ "[需求]是否可以客观测量/验证？"
   - ✅ "是否在需求中解决了[边缘情况/场景]？"
   - ✅ "规范是否定义了[缺失方面]？"

7. **结构参考**：按照`.specify/templates/checklist-template.md`中的规范模板生成清单，包括标题、元部分、类别标题、所有权说明、注释部分和ID格式化。如果模板不可用，使用：H1标题、目的/创建元行、解释`[x]`表示审查者批准需求质量的所有权说明、包含`- [ ] CHK### <需求项>`行的`##`类别部分，ID从CHK001开始全局递增，以及说明`/speckit-implement`读取清单状态但不会修改标记。

8. **报告**: 输出清单文件的完整路径、项目数量，并总结运行是创建新文件还是追加到现有文件。总结：
   - 选择的重点区域
   - 深度级别
   - 执行者/时间
   - 任何明确用户指定的必须包含的项目

**重要提示**：每个 `/speckit-checklist` 命令调用都使用一个简短、描述性的清单文件名，并创建新文件或追加到现有文件。这允许：

- 多种类型的多个清单（例如，`ux.md`、`test.md`、`security.md`）
- 简单、易记的文件名，表明清单用途
- 在 `checklists/` 文件夹中轻松识别和导航

为了避免杂乱，使用描述性类型，并在完成后清理过时的清单。

## 示例清单类型及示例项目

**UX 需求质量**：`ux.md`

示例项目（测试需求，不是实现）：

- "是否使用可衡量的标准定义了视觉层次结构需求？[清晰度、规范 §FR-1]"
- "是否明确指定了 UI 元素的数量和位置？[完整性、规范 §FR-1]"
- "是否一致定义了交互状态需求（悬停、焦点、激活）？[一致性]"
- "是否为所有交互元素指定了可访问性需求？[覆盖范围、差距]"
- "当图像加载失败时是否定义了回退行为？[边缘情况、差距]"
- "是否可以客观地衡量 '突出显示'？[可衡量性、规范 §FR-4]"

**API 需求质量**：`api.md`

示例项目：

- "是否为所有失败场景指定了错误响应格式？[完整性]"
- "是否使用特定阈值量化了速率限制需求？[清晰度]"
- "是否所有端点上的身份验证需求一致？[一致性]"
- "是否为外部依赖项定义了重试/超时需求？[覆盖范围、差距]"
- "是否在需求中记录了版本策略？[差距]"

**性能需求质量**：`performance.md`

示例项目：

- "是否使用特定指标量化了性能需求？[清晰度]"
- "是否为所有关键用户旅程定义了性能目标？[覆盖范围]"
- "是否指定了不同负载条件下的性能需求？[完整性]"
- "是否可以客观地衡量性能需求？[可衡量性]"

## 反例：什么不该做

**❌ 错误 - 这些测试实现，不是需求：**

```markdown
- [ ] CHK001 - 验证首页显示 3 个剧集卡片 [规范 §FR-001]
- [ ] CHK002 - 测试桌面上的悬停状态是否正常 [规范 §FR-003]
- [ ] CHK003 - 确认标志点击导航到主页 [规范 §FR-010]
- [ ] CHK004 - 检查相关剧集区域显示 3-5 个项目 [规范 §FR-005]
```

**✅ 正确 - 这些测试需求质量：**

```markdown
- [ ] CHK001 - 是否明确指定了特色剧集的数量和布局？[完整性、规范 §FR-001]
- [ ] CHK002 - 是否对所有交互元素一致定义了悬停状态需求？[一致性、规范 §FR-003]
- [ ] CHK003 - 是否所有可点击品牌元素的导航需求清晰？[清晰度、规范 §FR-010]
- [ ] CHK004 - 是否记录了相关剧集的选择标准？[差距、规范 §FR-005]
- [ ] CHK005 - 是否为异步剧集数据定义了加载状态需求？[差距]
- [ ] CHK006 - "视觉层次结构"需求是否可以客观衡量？[可衡量性、规范 §FR-001]
```

**主要区别：**

- 错误：测试系统是否正常工作
- 正确：测试需求是否编写正确
- 错误：验证行为
- 正确：验证需求质量
- 错误："它是否做 X？"
- 正确："X 是否清晰指定？"

## 执行后检查

**检查扩展钩子（清单生成后）**：
检查项目根目录中是否存在 `.specify/extensions.yml`。

- 如果存在，读取它并查找 `hooks.after_checklist` 键下的条目
- 如果 YAML 无法解析或无效，不要静默跳过：告知用户 `.specify/extensions.yml` 无法读取（包括解析错误），并且没有检查任何钩子，包括任何注册的强制（`optional: false`）钩子，然后正常继续
- 过滤掉 `enabled` 显式为 `false` 的钩子。将没有 `enabled` 字段的钩子视为默认启用
- 对于每个剩余的钩子，**不要**尝试解释或评估钩子 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或它为空/空，将钩子视为可执行
  - 如果钩子定义了非空的 `condition`，跳过钩子，并将条件评估留给 HookExecutor 实现来处理
- 在从钩子命令名构建命令调用时，将点（`.`）替换为连字符（`-`）。例如，`speckit.git.commit` → `/speckit-git-commit`。
- 对于每个可执行的钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子** (`optional: true`)：

    ```text
    ## 扩展钩子

    **可选钩子**：{extension}
    命令：`/{command}`
    描述：{description}

    提示：{prompt}
    执行：`/{command}`
    ```

  - **强制钩子** (`optional: false`)：

    ```text
    ## 扩展钩子

    **自动钩子**：{extension}
    执行：`/{command}`
    EXECUTE_COMMAND：{command}
    ```

    在发出上述块后，你**必须**实际调用钩子并等待它完成才能继续。以你在此代理/会话中自己运行命令的方式运行它（调用方式可能与上面显示的 `{command}` 字面量 ID 不同，例如，技能模式代理以 `/skill:speckit-...` 或 `$speckit-...` 的形式运行它）。仅发出块不会运行钩子。
- 如果没有注册钩子或不存在 `.specify/extensions.yml`，则静默跳过
