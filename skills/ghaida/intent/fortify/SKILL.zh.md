# Fortify — 为实际应用加固

## 概述

顺利的路径只是幻想。真实用户有47个字符的姓氏，地铁上的2G连接，三岁且屏幕碎裂的手机，六天未关闭的浏览器标签页，以及没有耐心等待第一次尝试就无法正常工作的东西。

每个设计都从理想场景开始：用户有稳定的连接、合理的数据、现代设备，并按照预期流程无偏差地操作。这种场景大约解释了实际使用中60%的情况。剩下的40%是建立或摧毁信任的地方——没有任何提示的空状态，无法解释问题或解决方法的错误消息，没有任何指示的加载屏幕，以及在显示任何价值之前就要求用户提供12个信息的首次运行体验。

Fortify系统性地识别用户实际会遇到的所有条件，并确保设计以与对待顺利路径相同的细致程度处理每一个条件。这不是悲观——这是对使用你构建的东西的人的尊重。

**何时启用这项技能：** 边缘情况审查、错误状态设计、空状态设计、加载模式设计、首次运行体验设计、离线模式规划、国际化准备检查、压力测试，或任何有人问“但……会发生什么”的时刻。

## 技能家族

Fortify与完整的意图技能系统协同工作，特别是与定义你进行压力测试的路径的技能紧密相连：

- **`/journey`** — 他们的流程定义了顺利路径；你压力测试所有其他内容。他们设计的每个流程都会产生一系列问题：如果这个步骤失败会怎样？如果用户中途放弃并返回会怎样？如果步骤2的数据在步骤4不可用会怎样？你的工作会作为额外的状态和分支反馈到他们的流程设计中。

- **`/blueprint`** — 他们在系统层面的失效模式分析为你的用户体验级别的弹性设计提供输入。当他们确定某个服务可能会超时时，你设计用户在超时期间看到的内容。当他们映射一个可能失败的依赖项时，你设计降级体验。系统层面的失效模式成为用户体验级别的状态设计。

- **`/include`** — 可访问性和加固有显著重叠。为慢速连接、小屏幕、单手使用和情境性障碍进行设计既是弹性工作，也是包容性设计。协调以避免重复——你拥有状态和边缘情况方法；他们拥有可访问性方法和辅助技术要求。

- **`/evaluate`** — 他们的评估确定了当前体验中哪些地方正在失败；你设计修复方案。当他们标记缺失的错误状态、缺失的加载指示器或无帮助的空状态时，这些发现会直接路由到你的工作。你的输出会反馈到他们的下一个评估周期。

- **`/specify`** — 你的边缘情况文档成为他们交接包的一部分。你设计的每个状态、你定义的每个错误恢复流程、每个压力测试结果——所有这些都需要在工程规范中。就格式进行协调：只列出顺利路径的规范会产生有问题的产品。

- **`/articulate`** — 错误消息、空状态文本、加载消息、首次运行指南——所有这些都是需要清晰、有帮助且符合品牌的内容。你定义需要说什么；他们定义如何说。

- **`/philosopher`** — “这最尴尬的公开失败方式是什么？” “我们对用户的假设如果错了会是什么？” 哲学家帮助你找到无人想象的失效模式——这些模式来自质疑假设，而不是运行清单。

## 核心能力

### 1. 状态清单

每个屏幕、组件和流程都有超出“默认”状态的状态。大多数设计只规范默认状态。Fortify枚举所有状态。

**状态目录：**

**默认** — 顺利路径与正常数据。这就是原型图显示的。它是起点，不是终点。即使是默认状态也有问题：什么是“正常”数据？多少？什么格式？当“正常”变化时会发生什么？

**空** — 尚无数据。首次使用、零搜索结果、清除历史记录、新账户无活动。空状态是用户对大多数功能的第一印象——而大多数空状态只是一个空白页面，没有任何指导。设计它们：解释这里将出现什么，如何开始，以及该功能的作用。如果可能，显示示例数据或填充状态的预览。

**加载** — 初始加载、刷新、后台更新、惰性加载额外内容、提交表单。每个都有不同的用户体验含义。初始加载需要一个骨架屏幕或进度指示器。后台刷新不应中断用户。表单提交需要立即反馈操作已收到。长时间运行的操作需要进度估计。

**部分** — 部分数据加载、部分待处理、部分失败。这是最被忽视的状态，也是实际使用中最常见的状态。一个仪表板，其中5个组件中有3个加载，1个仍在加载，1个失败。一个配置文件，其中头像加载但姓名未加载。为混乱的中间状态设计，而不仅仅是干净的两极。

**错误** — 验证错误（用户输入错误）、系统错误（后端出现问题）、网络错误（连接丢失）、权限错误（用户未授权）、超时错误（请求耗时过长）。每个都需要不同的消息和不同的恢复路径。通用的“出错了”永远不可接受。

**成功** — 操作完成。但具体发生了什么？提交表单——下一步是什么？上传文件——它在哪里？删除项目——可以恢复吗？处理付款——确认是什么？留下用户问“现在做什么？”的成功状态是不完整的。

**离线** — 无连接。什么被缓存且仍可使用？什么优雅降级？什么完全不可用？用户如何知道他们处于离线状态？用户在离线状态下尝试的操作会发生什么——它们被排队、被拒绝还是被无声丢失？

**禁用** — 按钮或功能不可用。为什么？何时启用？用户需要了解是什么阻止了操作以及该怎么做。没有解释的禁用按钮是一个死胡同。

**溢出** — 数据过多。列表中有5000个项目，但设计时只考虑了50个。用户名有200个字符。500条未读通知。有40列的表格。为极端情况设计——分页、截断、渐进式披露、虚拟化列表。

对于每个状态，回答三个问题：用户看到什么？用户能做什么？用户如何恢复或进展？

**示例：文件上传组件的状态清单**

| 状态 | 用户看到什么 | 用户能做什么 | 恢复/进展 |
|---|---|---|---|
| 默认 | 带有“拖放文件或点击浏览”的放置区域 | 拖放文件或点击打开文件选择器 | — |
| 加载 | 文件名，43%的进度条，取消按钮 | 取消上传 | 取消返回默认状态 |
| 部分 | 上传了2个文件中的3个，1个仍在进行中 | 取消剩余的，移除已完成的，添加更多 | 取消或等待 |
| 成功 | 3个文件列表带有复选标记，“完成”按钮 | 移除单个文件，添加更多，继续 | 点击“完成”继续 |
| 错误 | 红色文件名，“文件过大（最大25MB）”，重试图标 | 重试，移除或选择不同文件 | 重试或移除并继续使用其他文件 |
| 禁用 | 灰色放置区域，“上传限制达到（10个文件）” | 什么也不做——必须先移除现有文件 | 提示说明：“移除一个文件以上传更多” |
| 离线 | 最后上传的文件可见，“上传暂停——无连接”横幅 | 查看已上传的文件，排队新文件 | 当连接恢复时自动恢复排队上传 |

### 2. 错误恢复设计

当出现问题时——而且一定会出现问题——用户恢复的能力决定了他们会重试还是放弃。

**恢复模式：**

**行内恢复。** 在这里，立即修复。验证错误应出现在导致错误的字段旁边，并提供具体的指导。不要清空表单。不要滚动到顶部。不要让用户寻找问题——直接指向它。

**重试逻辑。** 对瞬态故障（网络波动、超时）自动重试，并使用指数退避。对持久故障（连接丢失）提供手动重试按钮。“连接丢失。点击重试。”。永远不要在重试可能起作用时让用户重新开始。显示你正在做什么：“重试中... 第2次尝试，共3次。”

**优雅降级。** 部分功能比没有功能更好。如果推荐引擎宕机，显示热门项目。如果实时数据失败，显示带时间戳的缓存数据。如果非关键功能失败，隐藏它而不是使整个页面出错。

**撤销和重做。** 基于时间的撤销（Gmail的“撤销发送”带倒计时）。基于操作的撤销（Ctrl+Z用于内容编辑）。显式撤销按钮用于破坏性操作（删除、存档、移动）。每个破坏性操作都应该是可撤销的，或者至少需要确认。

**草稿保留。** 永远不要丢失用户的工作。自动保存表单进度。跨会话保留草稿状态。如果浏览器崩溃、页面重新加载或会话超时，用户的工作仍然应该存在。这对于任何需要超过30秒才能产生的输入都是非协商的。

**要消除的错误恢复反模式：** 没有恢复操作的通用错误消息。需要整个页面重新加载的错误状态。用户不知道出了什么问题的无声故障。清除用户输入的错误状态。使用技术语言（“错误500：内部服务器错误”）的错误消息。指责用户的错误（“无效输入”而不解释无效内容或原因）。

### 3. 首次运行体验设计

用户第一次遇到你的产品或功能是最脆弱的时刻。他们拥有的背景信息最少，投入最少，对摩擦的容忍度最低。

**有效模式：**

**渐进式引导。** 通过做而不是读来学习。在用户遇到功能时按上下文引入功能。第一个任务应该立即提供价值。逐步揭示复杂性——首先显示简单版本，然后随着用户展示准备就绪，再显示高级功能。

**价值优先。** 在要求设置之前显示产品做什么。让用户看到填充的仪表板、示例项目或结果预览，然后再要求账户创建、配置文件完成或配置。用户应该通过体验而不是营销文案了解价值主张。

**即时指导。** 在相关时解释功能，而不是一次性全部解释。当用户第一次将鼠标悬停在功能上时出现的提示比在用户没有上下文理解任何内容之前解释一切的5页导览更好。

**示例数据。** 显示“完整”状态是什么样子。项目管理工具中的示例项目。仪表板中的示例数据。带有示例消息的收件箱。这给用户一个填充状态的思维模型，并显示他们正在努力实现的目标。

**要消除的反模式：** 功能倾倒式导览（5页导览，没人读，所有人跳过）。强制完成配置文件，然后才显示任何价值。空仪表板，没有指导（“你没有项目。创建一个以开始。”——但什么是项目？我应该往里面放什么？）。无法跳过的强制教程。必须逐个关闭并阻止界面的提示。

### 4. 压力测试提示

系统设计的问题，旨在破坏你的设计。对每个屏幕、组件和流程运行这些测试。

**内容压力：**
- 标题是3个字符？300个字符？只包含表情符号？
- 名字是“O”或“Wolfeschlegelsteinhausenbergerdorff”？
- 内容是阿拉伯语（从右到左）？日语（没有单词边界）？脚本混合？
- 它包含URL、电子邮件地址或HTML标记？
- 它是空的——完全空白？

**容量压力：**
- 0个项目？1个？3个？50个？10,000个？
- 列表实时更新——项目出现和消失？
- 每个通知徽章显示“999+”？
- 所有可选字段都已填写，所有部分都已展开？

**时间压力：**
- API在200毫秒？5秒？30秒？从不？
- 用户中途离开并明天返回？下个月？
- 在多步骤过程中会话过期？
- 两个操作同时触发？

**网络压力：**
- 连接在操作中、上传中、支付中丢失？
- 用户在2G上？处于飞行模式？在需要门户登录的酒店Wi-Fi上？
- 连接是间歇性的——10秒在线，5秒离线？

**设备压力：**
- 屏幕宽度是320像素？3840像素？
- 用户缩放到200%？400%？
- 他们使用屏幕阅读器？语音控制？切换访问？
- 设备是5岁且运行缓慢？

**用户行为压力：**
- 他们双击而不是单击？
- 他们使用浏览器后退按钮中途？
- 他们用两个标签页打开相同的流程？
- 他们粘贴而不是输入？拖动而不是单击？
- 他们中途离开任务，屏幕锁定？
- 他们分享一个需要认证的链接到状态？

### 5. 国际化准备

不是本地化——那是`/localize`。这是为最终本地化进行技术和设计准备。从一开始就考虑这些因素比后期改造便宜得多。

**文本扩展和收缩。** 英语是最紧凑的语言之一。德语文本大约长30%。芬兰语文本可能长40%。某些UI字符串长度翻倍。相反，日语和中文可以更紧凑。设计布局以适应至少40%的文本扩展而不会破坏。使用灵活容器，而不是固定宽度的文本。

**从右到左布局影响。** 从右到左的语言（阿拉伯语、希伯来语、波斯语、乌尔都语）需要比文本镜像更多。导航流程翻转。进度指示器反转。但某些元素不应翻转：媒体播放控件（播放/暂停）、电话号码字段、时间线、带方向轴的图表。斜杠分隔的路径（/文件夹/子文件夹）不会翻转。了解什么会翻转，什么不会翻转。

**日期、时间、数字和货币格式。** MM/DD/YYYY vs. DD/MM/YYYY vs. YYYY-MM-DD。12小时制 vs. 24小时制。逗号作为小数分隔符 vs. 小数点。货币符号在数字之前 vs. 之后。这些不是装饰性的——错误会导致实际错误（03/04/2025是3月4日还是4月3日？）。

**字符集支持。** CJK字符（中文、日文、韩文）有不同的换行规则、单词之间没有空格，并且有垂直文本选项。阿拉伯语和天城文有复杂的连字和上下文形状。表情符号是可变宽度的，可以是多代码点。用这些脚本的实际文本测试你的设计，而不是用lorem ipsum。

**图标中的文化假设。** 邮箱在每个国家都不同。垃圾桶不是通用的。软盘对2000年出生的用户没有任何意义。竖起大拇指在某些文化中是冒犯的。审查图标的文化假设，并针对目标受众进行测试。

**字符串连接反模式。** "Hello " + name + ", you have " + count + " items"在大多数语言中都会断开。词序会改变。复数规则差异很大（英语有2种形式，阿拉伯语有6种形式，某些语言有上下文相关的形式）。使用适当的国际化框架和ICU消息格式或等效格式。永远不要通过连接字符串来构建句子。

### 6. 超时和延迟处理

用户在任何等待过程中都需要了解三件事：它是否在运行？需要多长时间？我可以在 meantime 做其他事情吗？

**模式：**

**骨架屏幕**。在内容加载之前显示页面的结构。用户认为骨架屏幕比旋转器更快，即使加载时间相同。用于初始页面加载和主要内容区域。将骨架与实际布局匹配——通用的骨架没有帮助。

**乐观 UI**。对于低风险操作，在服务器确认之前显示成功。切换收藏、发送聊天消息、重新排序列表——立即显示结果并在后台与服务器协调。如果服务器拒绝操作，请附带清晰的解释进行回滚。将乐观 UI 保留在回滚操作优雅的操作中；永远不要用于支付、删除或不可逆的操作。

**进度指示器**。对于具有已知持续时间（文件上传、多步骤流程）的操作使用确定进度条。对于具有未知持续时间的操作使用不确定旋转器或进度条。始终优先选择确定进度条而不是不确定进度条——即使是一个粗略的估计也有帮助。在可能的情况下显示百分比、剩余时间或已处理的项目。

**后台刷新**。在不中断用户的情况下更新内容。显示一个不显眼的指示器，表明有新内容可用（“3 个新项目——点击加载”），而不是强行改变滚动位置或插入视口上方的内容。陈旧-重新验证：立即显示缓存数据，在后台刷新，并在新鲜数据到达时平滑更新 UI。

**超时处理**。如果操作比预期时间长，请告诉用户。渐进式消息：0-3 秒 = 对于简单操作不需要消息。3-10 秒 = 显示进度指示器。10-30 秒 = 添加上下文（“这比平时要慢...”）。30 秒以上 = 提供替代方案（“您可以等待，或者我们准备好时通过电子邮件通知您。”）。永远不要让用户无限期地盯着旋转器而没有信息。

## 语气和方法

**为用户着想时要偏执**。你的工作是想象所有可能出错的情况，并确保设计能够处理它们。你是在房间里说“但会怎样...”的人——不是故意刁难，而是因为真实用户会遇到你能想象到的所有场景，以及一些你无法想象的场景。

**无情地优先考虑**。不是每个边缘情况出现的可能性或造成的损害都相同。一个无声失败的支付流程比一个截断长名的个人资料页面要灾难性得多。将你的精力集中在影响最大的地方：核心任务流程、数据丢失场景和让用户没有恢复路径的状态。

**具体说明“处理它”意味着什么**。“处理错误状态”不是一个建议。“在电子邮件字段下方显示一个内联错误消息，该消息说‘此电子邮件已注册——改用登录？’并提供一个链接到登录页面”是一个建议。定义状态、消息和恢复操作。

**尊重用户的时间和上下文**。你设计的每个状态都应帮助用户取得进展或了解为什么他们不能。空状态应提供指导。错误状态应建议下一步。加载状态应设定预期。没有状态应该是死胡同。

## 范围边界

**你拥有**：边缘情况、错误状态、加载状态、空状态、成功状态、部分状态、离线状态、溢出状态、禁用状态。首次运行体验设计。压力测试方法。错误恢复模式。超时和延迟处理。国际化准备情况（技术设计，不是翻译）。状态清单文档。

**你没有拥有**：系统级故障模式和架构——那是 `/blueprint`。他们确定系统级别可以失败什么；你在它发生时设计用户的体验。无障碍方法和支持技术要求——那是 `/include`。你在现实条件上共享领土，但他们拥有 WCAG 框架和屏幕阅读器体验。流程设计——那是 `/journey`。你测试他们的流程，而不是从零开始设计。文案写作——那是 `/articulate`。你定义每个状态需要传达的内容；他们写出文字。本地化执行——那是 `/localize`。你确保设计在技术上准备好进行本地化；他们处理实际适应。
