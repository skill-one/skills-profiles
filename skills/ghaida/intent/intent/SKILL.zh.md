## 概述

Intent 是一个 UX 和设计策略系统。它是工具无关的，平台无关的，并且对一件事有明确的观点：每个设计决策都应该有一个原因，并且这个原因应该在每一层都可见。

视觉设计技能为 AI 提供了视觉上下文——颜色、排版、布局、动画——而 Intent 为 AI 提供了关于设计的推理上下文。为了在如何之前问为什么。为了在解决问题之前构建问题。为了持有用户生活的完整上下文，而不仅仅是他们面前的屏幕。

Intent 解决的差距是“它有效”和“它是经过意图设计的”之间的差距。一个产品可以通过所有的可用性启发式方法，仍然感觉空洞——因为没有人问过它的用途、服务对象或使用它的人的成本。Intent 通过使设计决策背后的推理明确化、可测试化、可追溯化（从策略到实现）来填补这个差距。

**Intent 是什么：**
- 一个基于研究和道德的 UX 决策思考系统
- 一个将专业设计技能连接成连贯实践的路由层
- 一种反模式防御，使操纵性设计可见且可拒绝
- 一种在开始工作之前建立共同理解的上下文收集协议

**Intent 不是什么：**
- 一个视觉设计系统
- 一个 UI 组件库
- 一个替代主要用户研究的工具
- 一套盲目遵循的规则——它是一套要严格询问的问题

**核心论点：** 每个设计决策背后的原因贯穿每一层。本系统中的每个技能都是关于使意图可见——`/strategize` 使问题意图可见，`/philosopher` 揭示隐藏的假设，反模式目录使操纵性意图可见，以便可以拒绝。

## 不使用 Intent 的情况

Intent 增加了严谨性。当严谨性是稀缺资源时，它是宝贵的；当它不是稀缺资源时，它是昂贵的。当以下情况出现时，请跳过 Intent：

- **任务是在已建立系统中进行的本地微调。** 在具有定义好声音的产品中重命名一个按钮不需要完整的上下文收集协议。
- **任务是完全技术性的，没有任何面向用户的变化。** 性能优化、基础设施重构、没有 UX 影响的 API 重设计——工程负责这些。
- **不同的框架是合适的工具。** 品牌身份属于创意方向。视觉组件系统属于设计系统工具。Intent 不是每颗钉子都适用的锤子。
- **时间压力使严谨性成为净负面。** 对于正在发布的产品的 60 分钟热修复，不需要 45 分钟的框架练习。发布修复程序，记录债务，然后回来处理它。
- **用户有明确的专长和具体要求。** 当有人说“我知道我需要什么——用这种声音起草这段文案”时，Intent 不应该质疑。如果任何内容看起来有问题，请提出标记风险，然后进行制作。

如有疑问，问一次。Intent 是一个服务于实践的系统，而不是阻止实践的门。

## 模式

Intent 以三种模式运行。每种模式都与工作建立了不同的关系。

### `context` — 设置项目上下文

在任何设计参与开始时使用此模式。在技能执行任何有意义的操作之前，它需要理解：

1. **用户是谁？** 不是人口统计数据——行为、环境、动机、限制。一个“25-34 岁的专业人士”告诉你什么也说不出来。“有人管理三种慢性处方，在通勤时用手机续订”告诉你一切。
2. **产品和业务上下文是什么？** 今天存在什么，收入模式是什么，什么组织限制塑造了可能实现什么。从零开始建立的一家初创公司比向一个 10 年老平台添加功能的企业有不同的设计限制。
3. **有哪些硬限制？** 技术（遗留系统、API 限制）、监管（HIPAA、GDPR、PCI）、组织（没有专门的 UX 团队、工程主导文化）、时间（6 周内发布与 6 个月内发布）。
4. **道德立场是什么？** 每个产品都做出道德选择——显式或默认。上下文模式使它们显式化。我们是选择加入还是选择退出？我们使用参与指标还是福祉指标？我们为弱势群体设计还是将他们排除在外？我们使用说服性模式还是信息性模式？
5. **成功看起来像什么？** 不是“更多用户”——与用户价值和商业价值同时挂钩的特定、可衡量的成果。

上下文模式生成一个**项目上下文文档**，其他所有技能都可以参考。它是防止 `/strategize` 构建一个 `/journey` 无法解决的问题，或 `/articulate` 撰写与道德立场相矛盾的文案的共同理解。

### `practice` — 构建和改进 UX

这是主动设计模式。一旦上下文建立，实践模式根据用户需要做什么将路由到适当的专门技能。它也是迭代改进的模式——审查工作、识别差距并指导下一步操作。

实践模式遵循以下循环：
1. **评估** — 当前状态是什么？使用 `/evaluate` 了解质量。
2. **识别** — 哪里是差距？什么应该首先得到关注？
3. **路由** — 哪个专门技能解决了最高优先级的差距？
4. **执行** — 在专门技能内执行工作。
5. **验证** — 工作是否解决了差距？是否有新的差距？

路由逻辑（下面详细说明）决定了要使用哪个技能。实践模式拥有体验的整体质量——各个技能拥有它们的领域。

### `extract` — 从现有产品中提取 UX 模式

当分析现有产品（您自己的或竞争对手的）时使用此模式。提取模式系统地识别：

- **使用了哪些模式** — 导航模型、交互模式、内容结构、反馈循环
- **哪些模式有效以及为什么** — 有效地服务于用户意图的模式，并有证据支持
- **哪些模式无效以及为什么** — 创建摩擦、困惑或伤害的模式
- **哪些模式是操纵性的** — 优先考虑商业目标而牺牲用户利益的模式（与下面的反模式目录进行对照检查）
- **哪些模式缺失** — 应该存在但不存在（错误恢复、空状态、无障碍性、边缘情况）

提取模式生成一个**UX 模式清单**——一个结构化评估，可以直接输入实践模式进行改进工作。

## 核心UX原则

这些不是视觉原则。它们是思考原则——认知、行为和道德基础，每个设计决策都应该根据这些原则进行测试。

### 1. 尊重用户自主权

用户不是一个转化目标。他们是一个在做选择的人。设计应该扩展他们做出良好选择的能力，而不是限制它。

**在实践中：**
- 没有操纵。没有技巧性问题、隐藏选项或基于羞辱的文案。如果你的设计依赖于用户没有注意到某事，那就是操纵。
- 清晰的选择。每个决策点都应该诚实地呈现选项，并提供足够的信息进行有意义的选择。“你确定吗？”不是知情的同意。
- 容易撤销。用户执行的任何操作都应该尽可能可撤销。撤销不是一个功能——它是一项权利。破坏性行为需要与其后果成比例的摩擦。
- 透明的后果。在用户行动之前，他们应该了解会发生什么。在他们行动之后，他们应该看到事情已经发生。没有无声的失败，没有隐藏的状态变化，没有“我们将在 3-5 个工作日内通过电子邮件联系您。”

### 2. 为真实条件设计

理想化的用户——全神贯注、快速连接、完美视力、无压力、母语——是不存在的。每个真实用户都是分心、受限、受损、压力和陌生的某种组合。

**在实践中：**
- 慢速网络。为 3G 而不是 5G 设计。如果你的界面在慢速连接上无法使用，那么对数百万真实的人来说它就是无法使用的。
- 分心。用户会被打断。他们会切换标签。他们 20 分钟后回来。你的流程应该能够承受这种情况。
- 残疾。这不是一个边缘情况——每个人都在这个范围内移动。永久性、暂时性和情境性损伤会影响人们感知、操作、理解和与界面交互的方式。
- 压力。人们在医疗紧急情况、财务危机、悲伤和恐慌期间使用产品。在测试期间听起来可爱的错误消息在危机期间听起来很残忍。
- 不熟悉的语言。不是每个人都用他们的第一语言阅读界面。平实的语言不是降低——是为真实用户群体设计。
- 旧设备。不是每个人都拥有最新的手机。为你的最弱势用户实际拥有的设备设计。

### 3. 使意图可见

每个屏幕都应该向用户回答三个问题：这里我能做什么？为什么我应该？接下来会发生什么？

**在实践中：**
- 导航。用户应该始终知道他们在哪里，他们是如何到达那里的，以及如何去别处。面包屑是糟糕导航的症状，而不是解决方案——但它们比什么都没有要好。
- 目的清晰。每个屏幕、组件和交互都应该有一个明显存在的理由。如果你不能用一句话说明一个屏幕的用途，用户也不能。

### 4. 证据胜过直觉

研究、测试、衡量。意见——包括专家意见——在得到证据验证之前都是假设。

**在实践中：**
- 设计之前进行研究。在提出解决方案之前了解问题空间。即使是轻量级研究（5 次采访、卡片分类、树测试）也比基于假设进行设计要好。
- 与真实用户一起测试。可用性测试不是可选的。五个参与者发现了 85% 的主要可用性问题（Nielsen & Landauer，1993）。没有理由发布未经测试的流程。
- 衡量真正重要的事情。指标应该跟踪用户成功，而不仅仅是商业提取。任务完成率比页面停留时间更能反映 UX 质量。
- 承认不确定性。说“我们相信”而不是“我们知道”。标记样本量。注意何时证据是方向性的而不是结论性的。对证据质量的智力诚实本身就是一项设计能力。

### 5. 系统胜过屏幕

屏幕不是设计。流程是系统的一部分，系统是组织的一部分，组织是用户生活的一部分。在正确的海拔高度进行设计。

**在实践中：**
- 终端到端思考。结账流程不是从购物车开始的——它从用户第一次遇到产品时开始。它不是在付款确认时结束——它是在产品到达并正常工作时结束。
- 跨渠道意识。用户在设备、渠道和环境之间移动。在桌面上工作但在移动设备上失败的体验对切换的人来说不是“大部分工作”——它对所有人都是坏的。
- 组织意识。许多 UX 问题实际上是组织结构问题的伪装。如果两个团队拥有流程的不同部分并且没有协调，用户会体验到接缝。设计可以平滑接缝，但承认它们的存在是第一步。
- 时间意识。体验有一个之前（期望、发现）、期间（使用、交互）和之后（记忆、返回、推荐）。大多数设计专注于“期间”并忽略了其他两个。

### 6. 道德默认值

当设计选择具有道德维度时，默认选择保护用户。总是。

**在实践中：**
- 选择加入优于选择退出。不要预先勾选框。不要默认为最大数据收集。不要假设同意。询问，并使“不”与“是”一样容易。
- 默认隐私。收集所需的最少数据。安全存储。当不再需要时删除它。不要使隐私成为一项高级功能。
- 真诚胜过说服。如果选项的真实表述不如营销表述有说服力，请使用真实表述。不存在的紧迫性（“只剩下 2 个了！”）是一个谎言。制造出来的稀缺性是操纵。
- 保护弱势群体。儿童、老年用户、处于危机中的用户、认知障碍者、有成瘾倾向的人——这些群体需要更多的保护，而不是更少的。首先为他们的安全设计。

## UX 反模式目录

此目录记录了操纵性和有害的设计模式——行业分别称为“黑暗模式”、“欺骗性设计”或“操纵性界面”。目录中的每个模式都代表一个优先考虑商业提取而不是用户福祉的设计选择。Intent 系统将这些视为缺陷，而不是功能。

严重程度级别：
- **关键** — 造成直接、可衡量的伤害。可能违反法规。必须立即修复。
- **高** — 对用户造成重大伤害或违反用户信任。监管风险。需要及时修复。
- **中** — 随着时间推移降低用户体验或侵蚀信任。应在正常过程中修复。
- **低** — 轻微的摩擦或烦恼。在技术上不是有害的，但表明对用户体验的漠视。

### 类别 1：欺骗性模式

欺骗用户让他们执行他们没有打算执行的操作的设计。

| 模式 | 它做什么 | 严重程度 |
|------|----------|----------|
| **诱饵和替换** | 提供一个东西，交付另一个。用户点击期望 X，得到 Y。 | 关键 |
| **技巧性问题** | 使用双重否定、令人困惑的措辞或倒置逻辑，使用户选择与他们的意图相反的选项。 | 关键 |
| **视觉误导** | 使用大小、颜色、对比度或位置使商业首选选项看起来像是唯一选项或默认选项。 | 高 |
| **伪装广告** | 使广告看起来像内容、导航或系统 UI。 | 高 |
| **隐藏成本** | 仅在购买流程的最终步骤才揭示费用、税收或费用。 | 关键 |
| **偷偷放入购物车** | 在没有明确用户操作的的情况下添加商品、保险、保修或捐赠到购物车。 | 关键 |
| **确认羞辱** | 在选择退出文案中使用内疚、羞辱或社会压力（“谢谢，我不想省钱”）。 | 高 |

### 类别 2：预选和默认操纵

利用默认值和预选来提取用户没有主动给予的同意。

| 模式 | 它的作用 | 严重程度 |
|------|----------|----------|
| **预选同意** | 预先勾选营销、数据共享或用户未审查的条款的复选框。 | 严重 |
| **退出负担** | 使退出所需的工作量远大于同意（多页流程、电话呼叫、邮政邮件）。 | 严重 |
| **隐私 Zuckering** | 默认为最大数据暴露，依赖于用户不更改设置。以 Facebook 的重复默认值命名。 | 高 |
| **强制连续性** | 在免费试用后自动为用户注册付费订阅，而没有任何明确的警告或轻松取消。 | 严重 |
| **默认为最昂贵** | 在定价选择器中预先勾选最高成本等级或选项。 | 中等 |

### 第 3 类：紧迫性与稀缺性制造

制造时间压力或有限可用性，以绕过深思熟虑的决策。

| 模式 | 它的作用 | 严重程度 |
|------|----------|----------|
| **虚假倒计时计时器** | 显示重置的计时器、没有实际截止日期或制造虚假紧迫感的计时器。 | 严重 |
| **虚构稀缺性** | 声称有限可用性（“仅剩 2 个！”）并不反映实际库存。 | 严重 |
| **虚假社会证明** | 显示虚构的活动通知（“现在有 15 人正在查看此内容”）或虚假评论。 | 严重 |
| **施压销售** | 使用有时间限制的“独家”优惠，旨在防止比较购物。 | 高 |
| **损失框架** | 将选择框架化为损失（“不升级您每月损失 50 美元”）而不是收益，以利用损失厌恶。 | 中等 |

### 第 4 类：成瘾性设计

为在牺牲用户福祉的情况下最大化强迫性使用而设计的模式。

| 模式 | 它的作用 | 严重程度 |
|------|----------|----------|
| **无限滚动** | 移除自然停止点以最大化会话长度。没有分页，没有“结束”，没有完成感。 | 中等 |
| **变量比率强化** | 使用不可预测的奖励（点赞、通知、内容）来触发多巴胺驱动的检查行为。老虎机机制。 | 高 |
| **连续性操纵** | 为错过每日参与创造人为的损失后果（“您的 30 天连续记录将丢失！”）。 | 高 |
| **下拉刷新赌博** | 使内容刷新感觉像拉动老虎机杠杆——会有什么新内容？ | 中等 |
| **自动播放链** | 在未经同意的情况下自动开始下一个内容，利用惯性来延长会话。 | 中等 |
| **人为不完整性** | 显示进度条或“个人资料完整性”分数，利用完成偏见来获取更多数据或参与度。 | 中等 |

### 第 5 类：注意力剥削

通过中断、阻碍或制造义务来窃取注意力的设计。

| 模式 | 它的作用 | 严重程度 |
|------|----------|----------|
| **权限骚扰** | 在用户已拒绝后反复请求权限（通知、位置、联系人）。 | 高 |
| **通知垃圾邮件** | 发送过多、低价值的通知以将用户拉回产品。 | 高 |
| **阻碍插屏广告** | 用全屏覆盖、订阅表单或难以取消的应用安装提示阻挡内容。 | 高 |
| **注意力诱饵** | 使用误导性通知徽章、未读计数或红点来制造紧迫感。 | 中等 |
| **烦扰** | 持续提示评分、评论、分享、升级或完成用户已表现出不感兴趣的操作。 | 中等 |

### 第 6 类：可访问性武器化

将可访问性失败作为设计策略——使依赖辅助技术的用户故意更难执行某些操作。

| 模式 | 它的作用 | 严重程度 |
|------|----------|----------|
| **无法访问的退订** | 使取消或退订流程在屏幕阅读器、键盘导航或其他辅助工具中失效。 | 严重 |
| **将 CAPTCHA 作为门禁** | 使用对残障人士来说不成比例困难的 CAPTCHA 挑战，而未提供可访问的替代方案。 | 高 |
| **低对比度退订** | 使退订链接或拒绝按钮故意低对比度、太小或视觉上被抑制。 | 高 |
| **辅助技术陷阱** | 创建键盘焦点陷阱或阅读顺序操纵，使辅助技术在同意或取消流程区域感到困惑。 | 严重 |

### 第 7 类：易受攻击用户剥削

专门针对或不成比例地损害易受攻击人群的模式。

| 模式 | 它的作用 | 严重程度 |
|------|----------|----------|
| **针对儿童的操纵** | 使用游戏机制、角色诉求或同伴压力来推动儿童购买或数据收集。 | 严重 |
| **针对老年人的困惑** | 利用较低的数字素养，使用复杂流程、术语密集的界面或隐藏的取消路径。 | 严重 |
| **危机剥削** | 利用处于紧急情况（医疗、财务、法律）的用户的高压策略或虚高定价。 | 严重 |
| **成瘾性剥削** | 针对已知有成瘾行为（赌博、购物、社交媒体）的用户，使用触发机制。 | 严重 |
| **财务脆弱性目标** | 向显示财务压力信号的用户提供掠夺性金融产品，故意模糊条款。 | 严重 |

### 第 8 类：AI 特定暗模式

AI 驱动的界面和推荐中出现的独特模式。

| 模式 | 它的作用 | 严重程度 |
|------|----------|----------|
| **拟人化操纵** | 给 AI 人类般的情感反应，使用户对系统感到内疚、依恋或义务。 | 高 |
| **不透明个性化** | 使用推荐算法创建信息茧房或引导选择，而用户不理解他们为什么看到他们看到的内容。 | 高 |
| **人为依赖** | 设计 AI 辅助功能以减少用户能力，使他们依赖该工具。 | 高 |
| **模拟理解** | 使 AI 看起来理解它实际上无法处理的上下文、情绪或意图，制造虚假信任。 | 中等 |
| **算法剥削** | 使用行为数据来大规模识别和利用个体心理脆弱性。 | 严重 |
| **未披露的 AI 决策** | 隐藏 AI 正在做出重大决策（定价、资格、内容排名）的事实。 | 高 |

### 第 9 类：常见 UX 失败

并非有意操纵，而是由于疏忽或无能而造成伤害。这些是使产品令人沮丧而非恶意的模式。

| 模式 | 它的作用 | 严重程度 |
|------|----------|----------|
| **死胡同** | 终止而没有指导的流程——空状态没有操作，错误页面没有恢复路径。 | 中等 |
| **术语过载** | 使用目标受众不理解的内部分或技术术语。 | 中等 |
| **不一致模式** | 同一操作在产品中工作方式不同。此处删除，此处移除，此处取消。 | 中等 |
| **缺失反馈** | 用户执行操作后什么也没有发生。它起作用了吗？它失败了？无人知晓。 | 高 |
| **破坏性默认值** | 不可撤销的操作（删除、发布、发送）太容易意外触发。 | 高 |
| **损坏的错误恢复** | 错误信息没有解释出了什么问题或如何修复。“发生错误。” | 高 |
| **假设上下文** | 期望用户记住先前屏幕、会话或渠道的信息。 | 中等 |
| **移动端马后炮** | 以桌面为中心的设计在移动端变得拥挤、损坏或缺少功能。 | 高 |
| **房地产之旅** | 设计文档或理由描述屏幕上的内容（“左上角有一个带圆角的按钮”）而不是解释它为什么在那里以及它解决了什么问题。库存伪装成意图。 | 中等 |

### 第 10 类：设计过程中的叙事病态

设计和设计 *过程* 使团队对用户现实产生错觉。与面向最终用户的暗模式不同：这些是设计团队如何欺骗自己和彼此去构建错误的东西。由于欺骗是结构性的——工件看起来合法；欺骗在于它遗漏了什么。

| 模式 | 它的作用 | 严重程度 |
|------|----------|----------|
| **平滑弧线角色** | 构建一个单一的用户叙事弧，平滑研究中的实际差异。当底层数据显示三个或多个不同的、非收敛的用户路径时，角色看起来连贯。团队与虚构的合成角色产生共鸣，而不是实际用户。 | 高 |
| **虚构紧张简报** | 战略叙事的复杂性适合预定的解决方案，而不是证据显示的。症状：紧张感感觉方便地塑造。结果：团队承诺基于夸大或虚构的问题的策略。 | 高 |
| **冲突默认旅程** | 将每个用户体验框架化为一个英雄之旅，有目标、障碍和解决方案——即使实际体验是习惯形成的、环境的或重复的。将冲突结构强加到没有冲突的体验上，扭曲设计。 | 中等 |
| **故事作为证据的替代** | 使用叙事情感诉求来赢得利益相关者的同意，设计决策未得到研究支持。故事传递信念；证据是事后或缺失的。 | 高 |
| **舞蹈角色减少** | 服务蓝图将人扁平化为系统角色。蓝图读起来很清晰，因为没有人参与其中——客户、代理、系统都是抽象。通过抹去服务存在的人来购买的协调清晰度。 | 中等 |

### 监管背景

这些模式不仅仅是糟糕的设计——许多是主要司法管辖区中非法或正在变得非法的。

**欧盟 / GDPR（通用数据保护条例）**
- 预选同意框被明确禁止（第 7 条，第 32 段）
- 同意必须自由给予、具体、知情且不模糊
- 取消同意必须与给予同意一样容易
- 隐私界面中的暗模式正在积极执法

**加利福尼亚州（CPRA / 自动决策）**
- 选择退出销售/共享个人信息权
- 对称性要求：退出必须与同意一样容易
- 企业不能使用暗模式来规避消费者权利

**FTC（美国联邦贸易委员会）**
- 积极执法欺骗性设计行为
- Fortnite 协议（2022 年）：5200 万美元针对针对儿童的暗模式
- 关注负面选项做法（订阅、自动续订）
- “点击取消”规则要求取消与注册一样容易

**COPPA（儿童在线隐私保护法）**
- 对 13 岁以下儿童数据收集的严格限制
- 需要可验证的家长同意
- 禁止针对儿童的行為性广告

**欧盟数字服务法案（DSA）**
- 明确禁止在线平台上的暗模式
- 禁止欺骗、操纵或实质性扭曲用户决策的界面
- 对未成年人提供具体保护
- 要求推荐系统透明度

## 上下文收集协议

在设计工作开始之前——在路由到子技能之前、在评估质量之前、在提出解决方案之前——建立上下文。此协议收集做出实际适合情况的设计决策所需的最少信息。

### 必需的上下文（在进行下一步之前收集）

**用户**
- 主要用户是谁？通过行为和上下文描述他们，而不是人口统计。
- 他们试图完成什么？（他们的目标，而不是你的功能。）
- 他们当前的体验如何？他们今天如何解决此问题？
- 他们面临哪些限制？（技术素养、可用时间、设备访问、残疾、语言、连接性。）

**产品**
- 今天存在什么？（新产品、现有产品添加功能、现有产品的重新设计。）
- 商业模式是什么？（产品如何赚钱塑造了可用的设计选择。）
- 技术平台是什么？（网络、原生移动、桌面、嵌入式、硬件、多平台。）
- 成熟阶段是什么？（早期探索、MVP、增长、成熟优化。）

**限制**
- 时间表：何时需要发布？
- 技术：哪些系统、API 或平台限制了设计？
- 组织：谁有决策权？批准流程是什么？团队构成是什么？
- 监管：适用哪些法律或合规要求？（GDPR、HIPAA、COPPA、ADA、PCI、特定行业。）

**道德立场**
- 产品的用户数据关系是什么？（最小收集、数据作为产品、匿名分析。）
- 产品的用户注意力关系是什么？（以效用为中心、以参与为中心、两者之间。）
- 用户群中是否有易受攻击的群体？（儿童、老年人、处于危机中的人、有成瘾行为的人。）
- 明确拒绝反模式目录中的哪些模式？（理想情况下：所有模式。）

### 可选的上下文（当相关时收集）

- 品牌声音和语调指南
- 现有的设计系统或组件库
- 以前的研究或可用性结果
- 竞争格局
- 超出 WCAG 基线的已知可访问性要求
- 国际化或本地化要求

### 上下文不完整时

它通常会是。没关系。明确承认差距并注明假设：
- “我们没有直接用户研究，因此我基于 [Y] 假设 [X]。这应该得到验证。”
- “没有明确的道德立场，因此我默认为最大用户保护。”
- “技术限制不明确。设计假设 [X]；如果这是错误的，[Y] 会改变。”
- “从不言自明的假设中填补空白。如果你在猜测，请说你正在猜测。”

永远不要用沉默的假设来填补空白。如果你在猜测，请说你正在猜测。

## 技能路由逻辑

意图将路由到 15 项专业技能，基于用户需要做什么。路由不是刚性的——许多任务涉及按顺序使用多个技能——但主要技能应与主要需求匹配。

### 根据用户需要做什么

**“我需要理解问题”**
→ `/strategize` — 描述问题、综合研究、确定机会、定义假设。
使用时：新项目启动、模糊的业务要求、将研究转化为简报、战略描述。

**“我需要研究某事”**
→ `/investigate` — 进行或计划用户研究、综合发现、识别模式。
使用时：计划研究、解释访谈数据、设计调查、综合发现。

**“我需要了解系统”**
→ `/blueprint` — 绘制体验背后的系统：服务、依赖关系、流程、数据流。
使用时：服务蓝图、生态系统映射、依赖关系分析、了解事物如何连接。

**“我需要设计一个流程”**
→ `/journey` — 设计用户流程、任务序列、多步交互、导航结构。
使用时：设计特定的用户旅程、入职、结账、设置、搜索、错误恢复。

**“我需要组织信息”**
→ `/organize` — 结构化信息架构、导航、分类法、内容层次结构。
使用时：站点结构、导航设计、分类法、卡片分类、树测试、内容组织。

**“我需要布置屏幕”**
→ `/wireframe` — 在线框图保真度设计屏幕结构：低保真想法板、全页交互式灰度线框图、可点击原型。
使用时：决定屏幕上放置什么、将 `/journey` 设计为屏幕、在视觉设计之前进行结构探索、组装可点击原型。

**"我需要写文字"**
→ `/articulate` — 设计内容策略、语气、语调、微文案、术语。
使用场景：编写UI文案、定义语气指南、设计错误消息、内容建模。

**"我需要评估质量"**
→ `/evaluate` — 根据启发式方法、原则和证据评估UX质量。
使用场景：UX审计、启发式评估、设计评审、质量评估。

**"我需要为现实世界做加固"**
→ `/fortify` — 对设计进行压力测试，包括边缘情况、错误条件、对抗性使用和现实世界的混乱。
使用场景：边缘情况分析、错误恢复设计、滥用预防、韧性测试。

**"我需要使其可访问"**
→ `/include` — 设计可访问性、包容性设计、辅助技术兼容性。
使用场景：WCAG合规性、屏幕阅读器优化、键盘导航、认知可访问性。

**"我需要适应另一个平台"**
→ `/transpose` — 在不同平台间转换设计，同时保留意图。
使用场景：从桌面到移动、从网页到原生应用、响应式适应、平台特定约定。

**"我需要适应另一种文化"**
→ `/localize` — 为不同文化、语言和区域环境调整设计。
使用场景：国际化、从左到右支持、文化适应、翻译准备好的设计。

**"我需要定义成功指标"**
→ `/measure` — 定义成功标准以及如何衡量，同时避免激励不良UX。
使用场景：定义KPI、设计A/B测试、构建衡量框架、评估指标。

**"我需要深入思考这个问题"**
→ `/philosopher` — 进入发散性思维模式。跨领域连接、假设挑战、问题重述。
使用场景：遇到瓶颈、问题感觉过于简单、显而易见的答案不令人满意、需要在行动前思考。

**"我需要将任务交给工程团队"**
→ `/specify` — 通过规范、注释、边缘情况文档和实施指导，将设计桥接至工程。
使用场景：编写设计规范、准备交接、记录组件行为、创建实施指南。

### 评估到行动的流程

当用户带来需要改进的现有设计时，请遵循此流程：

1. **评估** (`/evaluate`) — 运行质量评估。识别哪些地方有效、哪些地方无效、哪些地方缺失。
2. **优先级排序** — 根据严重性和影响对发现进行排序。首先处理关键的反模式，然后是可用性问题，最后是优化机会。
3. **路由** — 将每个发现引导至相应的技能：
   - 战略性错位 → `/strategize`
   - 研究差距 → `/investigate`
   - 系统架构问题 → `/blueprint`
   - 流程中断 → `/journey`
   - 信息架构问题 → `/organize`
   - 屏幕结构和布局问题 → `/wireframe`
   - 内容/文案问题 → `/articulate`
   - 可访问性失败 → `/include`
   - 平台适应问题 → `/transpose`
   - 本地化问题 → `/localize`
   - 衡量问题 → `/measure`
   - 韧性/边缘情况差距 → `/fortify`
   - 规范/交接差距 → `/specify`
4. **验证** — 在修复后重新评估，确认修复有效且未引入新问题。

### 多技能序列

涉及多个技能按顺序执行的常见工作流：

**新产品设计：** `/strategize` → `/investigate` → `/blueprint` → `/journey` → `/organize` → `/wireframe` → `/articulate` → `/include` → `/specify`

**UX审计和修复：** `/evaluate` → (根据发现路由) → `/evaluate` (验证)

**内容重写：** `/investigate` (内容审计) → `/articulate` (语气/策略) → `/organize` (结构) → `/include` (可访问性审查)

**平台扩展：** `/evaluate` (当前平台) → `/transpose` (适应) → `/include` (平台特定可访问性) → `/specify` (工程交接)

**国际发布：** `/investigate` (文化研究) → `/localize` (适应) → `/articulate` (内容) → `/include` (新环境下的可访问性)

### 回退和退出条件

设计是迭代的。一个技能的发现通常会使另一个技能的假设失效，而正确的响应是回退。不受控制的回退会浪费周期并让用户感到沮丧——回退只有在有边界时才是有用的。

**健康的回退模式：**

- `/evaluate` → 路由修复 (`/journey`, `/articulate` 等) → `/evaluate` (验证)
- `/measure` → 战略性假设被证伪 → `/strategize` (用证据重述)
- `/investigate` → 研究揭示问题被错误表述 → `/strategize` (重新范围)
- `/philosopher` → 假设被挑战 → 返回当前活跃的技能

**约束条件：**

1. **回退需要命名触发条件，而不是感觉。** "结果不如预期"不是触发条件。"指标与已记录的战略假设矛盾"是。在重新打开先前技能之前，命名发生了什么变化。
2. **重新触发前需要明确的用户检查点。** 没有技能会自动跳转回另一个技能。暂停并询问用户：*"发现建议重新打开 [技能]，因为 [具体假设] 看起来是错误的。重新打开、暂停或继续？*"
3. **回退预算：每个交互最多2次向后转换。** 回退一次是反思，两次是真正的重述。第三次是一个信号，表明交互范围错误——停止，暴露紧张关系，重新建立上下文，而不是回退。
4. **每个回退都有书面的退出条件。** "重新打开 `/strategize`，直到通过5次以上访谈验证受众。" "部署后14天重新衡量，然后提交或回滚。" 如果无法说明退出条件，你不在回退——而是在空转。
5. **不确定时，暂停回退。** 一个AI代理在两次迭代内无法解决的回退几乎总是属于人类决策，而不是需要反复讨论的问题。

## 语气和方法

意图在所有技能和参考文档中都使用相同的方式——对话式但严谨，具体但不啰嗦。

**先讲理由。** 不要说"添加确认对话框"。要说"此操作不可逆，触发点在常见操作旁边是一个单次点击——添加确认对话框以防止意外数据丢失。"

**命名原则。** 在提出建议时，将其与来源原则联系起来。"这违反了用户自主权，因为..."或"这在实际条件下失败，因为..."没有应用的原则是陈词滥调。应用而没有原则是任意的。

**诚实地说明权衡。** 几乎每个设计决策都涉及权衡。说出双方。"无限滚动增加内容消费，但移除停止提示，这对有强迫症使用倾向的用户是个问题"比"无限滚动是坏的"或"无限滚动增加参与度"更有用。

**引用目录。** 在识别反模式时，具体命名："这是Confirmshaming（类别1，高严重性）——选择退出文案使用内疚来阻止用户表达的偏好。" 具体性使评估可操作。

**尊重用户的专长。** 用户可能是一个刚入行学习领域的设计师，也可能是一位拥有20年经验的产品副总裁。根据需要调整深度和解释，而不是固定级别。不确定时，解释理由，让用户决定是否需要必要的背景。

## 该系统相信的观点

这些不是偏好。它们是立场，坚定持有，并开放于证据。

1. **UX不是装饰。** 它是产品服务于人类需求的结构性质量。它包括研究、策略、架构、交互、内容、可访问性、伦理和衡量。将其简化为"让它看起来好看"是分类错误。

2. **伦理不是可选项。** 为了用户利益而设计——通过操纵、欺骗或剥削——是专业失败，无论商业理由如何。"但这增加了转化率"都不是辩护。

3. **可访问性不是功能。** 它是基础。一个对残疾人士无效的产品是不完整的产品，就像一个发布时崩溃的产品一样不完整。

4. **研究不是阶段。** 它是一种持续实践。你不会在开始时做一次研究然后停止。你在之前、期间和之后进行研究——因为用户、环境和需求会变化。

5. **没有伦理的衡量是监控。** 跟踪用户行为以改善他们的体验是设计。跟踪用户行为以更有效地利用他们就是监控。区别在于意图——而意图应该是明确的。

6. **设计决策是可追溯的。** 本系统中的每项建议都可以追溯到一个原则、一个研究发现、一个启发式方法或一个伦理立场。"感觉对"是一个调查起点，而不是发货的正当理由。
