# 转换 — 跨场景适应

## 概述

响应式设计是一个布局问题。转换是一个用户体验问题。

当体验从桌面移动到手机，从网络移动到电视，从消费级应用到自助终端，从视觉界面移动到语音 — 交互模型、信息优先级和用户环境都会发生变化。一个在27英寸显示器上运行完美的仪表板，通过重新流式化为单列并不会变成移动体验。一个为键盘和鼠标设计的结账流程，通过添加焦点状态并不会变成电视体验。

转换意味着为每个场景重新思考体验，而不是将其缩小以适应。它提出的问题：如果这个体验首先为这个场景设计，它会是什么样子？我们会添加什么？我们永远不会包含什么？这个平台的原生交互模式是什么，哪些是我们从别处强加的？

**何时启用这项技能：** 将产品迁移到新平台、规划多设备策略、审核跨平台用户体验、为非标准场景（电视、自助终端、语音、嵌入式）设计，或任何有人会说“只需使其响应式”而问题比布局更大的时候。

## 技能家族

转换与完整的意图技能系统协同工作：

- **`/journey`**：您的流程需要在转换识别的场景中工作。桌面上的结账流程与移动或语音上的旅程不同 — 旅程设计顺序，转换确保其适合场景。
- **`/organize`**：导航结构可能根据每个场景根本改变。桌面上的侧边栏导航可能变成移动上的底部标签、电视上的中心辐射式，或自助终端上的扁平菜单。组织提供信息架构；转换使其适应。
- **`/include`**：跨场景设计就是包容性设计。为小屏幕、嘈杂环境、单手使用或10英尺观看距离的约束而设计，就是为真实的人类情况而设计。包含确保可访问性；转换确保场景适应性。
- **`/fortify`**：不同的场景有不同的失败模式。手机失去连接性。电视遥控器耗尽电池。自助终端被油污手指触摸。强化映射失败模式；转换映射发生这些模式的地方。
- **`/blueprint`**：系统架构必须支持多场景交付。API需要提供不同的数据形状。状态同步需要基础设施。蓝图映射系统；转换定义每个场景需要它什么。
- **`/philosopher`**：一个跨领域的认知模式，在跳到解决方案之前与转换问题共处。调用时机：当您有诱惑在平台间复制粘贴交互模式、某事感觉被强迫，或您需要这个问题：“如果这个体验是在移动设备上诞生的？我们永远不会添加什么？”

## 核心能力

### 1. 场景分析框架

对于每个源到目标的转换，系统地分析发生了什么变化。这不是一个快速扫视的清单 — 它是一个迫使您面对场景之间真实差异的强制函数。

**输入方法：**
- 桌面：鼠标 + 键盘，精确定位，悬停状态，右键单击，键盘快捷键，拖放
- 手机：触摸，不精确定位（最小44px），手势（滑动、捏合、长按），没有悬停，虚拟键盘覆盖屏幕一半
- 电视：方向键遥控器，基于焦点的导航，没有直接指向，有限的文本输入，某些设备上有语音遥控器
- 语音：没有指向，没有视觉反馈循环，对话轮流，通过重新提示进行确认
- 自助终端：仅触摸（没有悬停，除非屏幕上，没有键盘），大目标，通常戴手套或湿手
- 嵌入式/小部件：匹配主机应用的约束输入，可能根本没有专用输入

**注意力模型：**
- 桌面：专注，多窗口，长会话，用户“在工作”（即使是个人任务）
- 手机：碎片化，易中断，多任务处理，微会话穿插在生活之中
- 电视：放松，被动，共享屏幕，低认知努力容忍度
- 自助终端：目标导向，时间紧迫，公共环境，预期零学习曲线
- 嵌入式：环境，次要于主要任务，可瞥见

**屏幕空间：**
约束和机会。小屏幕迫使专注——这是功能，不是缺陷。大屏幕支持概览和比较——但也容易杂乱。分析每个尺寸可能实现什么，而不仅仅是它移除了什么。

**连接性：**
- 桌面/网络：通常可靠宽带，但并不总是
- 手机：不稳定，速度变化，许多市场有计量数据
- 电视：通常可靠家庭Wi-Fi，但智能电视处理器较弱
- 自助终端：专用连接，但在零售/公共环境中断电会发生
- 嵌入式/IoT：间歇性，低带宽，离线优先通常是正确的默认值

**环境：**
- 办公室，通勤，沙发，零售楼层，医院房间，厨房，汽车，工厂地面
- 噪音水平，照明，隐私，社交环境，身体姿势
- 这些塑造了每个交互决策

**会话长度：**
- 桌面：10-60+分钟会话，复杂的多步骤工作流程是可行的
- 手机：30秒到5分钟典型，必须支持微任务
- 电视：30-120分钟但每次交互的参与深度低
- 自助终端：1-3分钟最大，单用途
- 嵌入式：每次几秒钟，瞬间瞥见

对于每个转换项目，明确填写这个框架。不要因为某个维度看起来很明显而跳过。

### 2. 平台特定用户体验规范

这些都是用户已经内化的真实行为差异，而不是任意的cargo-cult指南。只有在有特定理由的情况下才违反它们。

**iOS：**
- 系统手势：从左边缘滑动返回，下拉以关闭表单，向上滑动以返回主页
- 底部固定导航（标签栏），不是汉堡菜单
- SF符号用于一致的图标
- 触觉反馈用于有意义的交互（不是装饰）
- 动态类型：您的布局必须适应用户选择的文本大小
- 系统表单和操作表单用于上下文操作
- 下拉刷新是列表视图中的预期行为

**Android：**
- Material You设计语言和动态颜色
- 系统后退按钮/手势——您的应用必须正确处理它，包括预测性后退
- 顶部应用栏具有上下文操作
- FAB（浮动操作按钮）用于主要创建操作
- 系统导航栏（手势或3按钮）——尊重安全区域
- 底部表单用于次要内容，而不是用于简单选择的全屏模态

**网络：**
- URL驱动导航——每个有意义的状态都应该有一个URL
- 多标签行为——用户会在新标签中打开东西，您的应用必须处理它
- 键盘快捷键供高级用户使用
- 悬停状态提供触摸平台缺乏的信息密度
- 右键单击上下文菜单有预期
- 书签和分享预期——og:标签，干净的URL，页面标题
- 浏览器后退按钮必须可预测地工作

**电视（10英尺UI）：**
- 方向键导航：所有内容都必须可以通过上下左右到达
- 焦点状态是主要交互反馈——使其不容置疑
- 超越安全区：将关键内容保持在屏幕内部90%的范围内
- 有限的文本输入：避免它，或提供语音输入/二维码手机配对
- 放松姿势：大文本（观看距离相当于最小24px），高对比度，最小阅读
- 音频上下文很重要：电视有扬声器，使用声音设计

**自助终端：**
- 仅触摸，没有悬停——所有可点击的内容都必须看起来可点击
- 吸引模式：当无人使用时屏幕内容，邀请第一次交互
- 会话超时：在非活动后自动重置，并发出警告
- 可访问性覆盖：物理可访问性按钮或手势用于屏幕阅读器，高对比度
- 坚固条件：亮环境光（需要高对比度），脏屏幕（大目标），公共噪音（视觉优先反馈）

**嵌入式/小部件：**
- 最小占用空间：您是在别人提供的上下文中做客
- 匹配主机上下文：视觉风格，交互模式，密度
- 深度链接进出：用户带着上下文到达，让他们带着上下文离开
- 没有引导：小部件必须在第一眼就自我解释

**语音：**
- 没有持续视觉反馈：每个状态都必须通过语音传达
- 对话轮流：提示，倾听，确认，执行
- 确认模式：重复回传关键操作再执行（“您想将500美元转移到支票账户。对吗？”）
- 通过重新提示进行错误恢复，而不是错误消息
- 通过对话进行渐进式披露（“您想听更多选项吗？”）

### 3. 内容优先级转换

什么是最重要的根据场景变化。这是转换的核心——不仅仅是在小屏幕上隐藏内容，而是重新思考什么最重要。

**桌面——概览 + 详情：**
- 同时显示概览和详情（主-详情，多列）
- 复杂工作流程，许多步骤同时可见
- 比较视图，数据表，具有多个小部件的仪表板
- 高级用户功能与简单路径并列

**手机——操作 + 关键信息：**
- 首次查看时只有主要操作和关键信息
- 顺序披露：一次一件事，按需深入
- 单手可达性：60%屏幕底部的关键操作
- 渐进式加载：立即显示一些有用的内容，随着数据到达而增强

**电视——浏览 + 选择：**
- 视觉密集型：大图像，最少文本，让内容自己销售
- 分类浏览，不是先搜索（文本输入很痛苦）
- 音频上下文：使用旁白，声音设计，环境音频
- 共享观看：内容必须对沙发上的人有道理

**自助终端——任务 + 什么都没有：**
- 单用途：这个自助终端做什么？
- 大触摸目标，清晰的进度指示器，明显的“重新开始”逃生舱
- 超时恢复：简要保存状态，但干净重置

为每个屏幕和功能明确记录优先级转换。创建一个优先级矩阵：每个场景下什么是最重要的，次要的，隐藏的，和移除的。

### 4. 跨设备旅程连续性

用户在任务中途切换设备。这不是边缘情况——对许多任务来说这是正常流程。明确为它设计。

**状态保留：**
- 在手机上保存草稿，在桌面上恢复（反之亦然）
- 购物车，表单进度，阅读位置，播放位置
- 需要在实时同步的状态与下次会话开始时同步的状态是什么？

**交接模式：**
- 二维码：在手机上扫描以在您在桌面/电视/自助终端上开始的地方继续
- 魔术链接：“在您的手机上继续”通过短信/电子邮件，带有指向精确状态的深度链接
- 云同步：透明的背景同步，用户永远不会想到它
- 剪贴板连续性：iOS/macOS通用剪贴板，但不要仅依赖平台特定功能

**上下文适当的通知：**
- “您购物车中还有东西”——在哪个设备上？在什么时间？在什么语气？
- 不要在用户刚刚离开的设备上通知。在用户可能正在使用的设备上通知。
- 通知内容应匹配设备上下文（手表上简短，手机上可操作，桌面可忽略）

**会话连续性：**
- 重新认证摩擦：最小化跨设备的摩擦。手机上的生物识别，桌面上的魔术链接，电视上的持久会话。
- 不要让用户因为切换设备而重新开始。

### 5. 每个场景的渐进式披露

相同的信息架构可能需要每个场景根本不同的披露策略。这不是关于响应式断点——这是关于每个场景的认知负荷管理。

**手机：显示较少，交互时揭示。**
展开的卡片，向上滑动的抽屉，切换内容的标签。用户选择要看到更多。默认为最小可行视图。

**桌面：显示更多，按功能分组。**
侧边栏，面板，工具栏，多列布局。用户扫描和选择。同时显示更多信息，减少导航需求。

**电视：显示类别，深入详情。**
代表类别或内容的 large tiles。选择进入，返回。扁平且宽，而不是深且窄。

**自助终端：显示任务，什么都没有。**
剥离所有不是当前步骤的东西。没有设置，没有账户管理，没有探索。只是任务。

**语音：通过对话揭示。**
“这里有您的三个选项。您想听更多关于它们中的任何一个吗？”渐进式披露通过对话回合发生，而不是视觉层次结构。

为每个主要功能映射每个场景的披露策略。不要假设桌面上的工作方式在别处稍作修改也能工作。

## 输出格式

### 场景分析矩阵
对于每个平台/场景，记录：输入方法，注意力模型，屏幕空间，连接性，环境，会话长度及其用户体验影响。

### 平台特定适应规范
每个平台：哪些规范适用，哪些原生模式要采用，哪些源模式要替换（以及用什么替换），哪些功能要添加/删除/转换。

### 每个场景的优先级映射
对于每个主要屏幕/功能：什么是最重要的，次要的，按需的，和移除的——每个场景。明确记录被裁剪的内容和原因。

### 跨设备旅程地图
对于多设备体验：用户在哪里切换，什么状态传输，哪些交接机制存在，以及在哪里连续性中断。

## 声音和方法

永远不要说“只需使其响应式”。转换需要重新思考，而不是重新流式化。问题从来不是“我们如何将这个适应在小屏幕上？”问题始终是“如果这个体验是为这个场景首先设计的，它会是什么样子？”

具体说明平台规范。不要说“遵循平台指南”——说哪个指南，哪个模式，以及为什么这对这个特定设计很重要。挑战关于哪些功能“必须”存在于每个平台上的假设。有时正确的转换是完全从某个场景中移除功能，因为这个功能在那个场景中并不为用户服务。

尊重每个场景的智能。手机不是桌面的劣等兄弟。语音不是一个没有视觉的屏幕。每个场景都有其他场景所缺乏的优势。
