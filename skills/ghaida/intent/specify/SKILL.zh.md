# 指定 — 桥接设计到工程

## 概述

这项技能将设计工作转化为可执行、准备就绪的文档。它生成结构化的规范、资源包、测试计划以及利益相关者演示文稿，确保设计意图能够顺利传递到生产阶段。当设计需要进入工程阶段、需要跨职能团队清晰理解或需要以防止返工的方式记录决策时，请使用此技能。

---

## 技能系列

Specify 与完整的 Intent 技能系统协同工作：

- **`/strategize`**：他们的简报和假设提供了所有指定内容的“为什么”。每个规范都应该追溯到战略意图——这个功能为什么存在、它测试了什么假设、它满足了什么用户需求。
- **`/investigate`**：他们的研究成果为你的用例提供了证据基础。真实用户引言、观察到的行为和验证的痛点使规范更具说服力和准确性，而不是假设性的。
- **`/blueprint`**：他们的系统架构约束并指导你的规范。服务依赖、数据流和技术约束塑造了可能性和需要工程讨论的内容。
- **`/journey`**：他们的流程是你正在指定的——屏幕序列、交互转换、状态变化。Journey 设计体验；spec 文档化它以供实施。
- **`/organize`**：他们的信息架构指导你的导航规范。组织中的分类法、层次结构和标签决策成为屏幕规范的结构性骨干。
- **`/articulate`**：他们的文案工作直接输入到你的文案矩阵中。声音、语气和内容策略决策成为规范中的具体字符串。
- **`/fortify`**：他们的边缘情况分析成为规范的一部分。错误状态、故障模式、边界条件和恢复模式——所有内容都逐屏记录。
- **`/include`**：他们的无障碍要求进入每个屏幕规范。ARIA 标签、键盘导航、颜色对比、屏幕阅读器行为——包含不是附录，而是编织到每个屏幕中。
- **`/evaluate`**：他们的评估确定了规范中的差距。启发式违规、可用性问题、反模式标志成为在交接前需要解决的问题。
- **`/measure`**：他们的成功指标定义了测试计划的准则。每个功能规范都应该包括成功看起来像什么、如何衡量它以及需要监控什么。
- **`/philosopher`**：一种跨切认知模式，当规范揭示更深层次的问题时使用。调用时机：边缘情况不断增多、设计在真实条件下感觉脆弱、待解决问题部分不断增长，或用户说“坐下来思考一下”、“头脑风暴”或“有什么问题是没有人想到的？”哲学家帮助思考无人考虑的失败场景，以及规范是否记录了正确的事情。

## 核心功能

### 1. 详细的设计规范

编写全面的、逐屏（或逐状态）规范，记录：

- 视觉设计：具体的测量值、颜色、排版、间距
- 交互逻辑：什么触发什么、按什么顺序、在什么条件下
- 文案：确切的文本、不同上下文/市场/边缘情况的变体
- 状态：默认、悬停、激活、错误、加载、空、成功——所有内容都视觉化和逻辑化地记录
- 约束：设备尺寸、性能要求、无障碍需求

输出应为可生存的规范文档（HTML 或 markdown），工程师在实施过程中可以参考，而无需猜测。

### 2. 结构化的工程交接包

组织交付成果，使工程人员确切知道要构建什么以及为什么：

- 明确的所有权：谁在何时决定什么
- 问题背景：这个问题解决了什么用户需求或业务问题
- 设计方法：考虑的约束、拒绝的替代方案及其原因
- 用例：具体的，而不是通用的——真实用户场景，暴露边缘情况
- 资源：所有文件组织、命名、版本控制，并附有使用说明
- 测试标准：成功指标和面向特定受众的测试计划

### 3. 文案和变体矩阵

将所有文案变体记录在一个地方：

- 主要文案与次要文案与微文案（标签、提示、错误、空状态）
- 市场变体：语气变化、文化考虑、监管语言
- 边缘情况：字符限制、长字符串、非常短的字符串、数字边缘情况
- A/B 测试变体：正在测试的明确文案变化，以及成功标准

### 4. 交互式 HTML 规范文档

在适当的情况下，生成交互式 HTML 规范，这些规范：

- 将设计 inline 显示在解释性文本旁边
- 链接相关屏幕和决策
- 包含可折叠的参考部分（组件规范、文案矩阵、测试计划）
- 是自包含的，可以在任何浏览器中查看，无需外部依赖

### 5. 用例和边缘情况文档

编写具体的，而不是通用的用例：

- “新用户创建账户”与“用户登录”
- “支付过程中网络超时”与“错误状态”
- “用户购物车中有 200+ 项”与“用户购物车中有商品”
- 记录每种情况下设计的行为、出现的文案以及下一步发生什么

### 6. 利益相关者演示文稿

构建使跨职能团队保持一致的演示文稿：

- 问题陈述（来自 `/strategize`）
- 设计方法和考虑的约束
- 关键决策以及有意不做什么
- 测试计划：我们在衡量什么以及为什么（来自 `/measure`）
- 待解决问题：我们还需要解决什么
- 时间表和依赖关系

### 7. 测试计划与成功标准

编写测试计划，将观察结果与决策者配对：

- 谁需要看到这项工作（PM、工程负责人、CEO？）
- 成功看起来像什么：具体的、可衡量的结果（与 `/measure` GSM 链接相关）
- 我们在学习和为什么学习
- 结果如何反馈到设计迭代中

## 质量检查清单

在标记交接为完成之前，请核实：

- [ ] 每个屏幕都有记录的意图——它为什么存在以及它满足了什么用户需求（没有房地产之旅）
- [ ] 所有屏幕和状态都进行了视觉记录
- [ ] 所有文案都已写明（没有像“TBD”这样的占位符）
- [ ] 所有变体（市场、边缘情况、A/B 测试）都已记录
- [ ] 边缘情况已解决（空状态、错误、长内容、网络延迟）
- [ ] 待解决问题已明确标记（设计+工程）
- [ ] 所有权已声明（谁，何时，状态）
- [ ] 包含测试计划，并具有具体的成功标准
- [ ] 资源已组织并命名；其位置已记录
- [ ] 开放问题不会阻止工程；它们被标记为并行解决
- [ ] 文案矩阵包括实施所需的全部变体
- [ ] 相关的地方指定了交互时间（例如，toast 持续时间、动画速度、防抖间隔）
- [ ] 对于 A/B 测试：两个变体并排记录，明确指出具体差异
- [ ] 伦理审查已完成：设计已与反模式目录检查
- [ ] 测量部分已完成：成功指标、反指标和监控需求已记录

## 声音和方法

**意图优先于清单。**
- 设计文档中最大的反模式是“房地产之旅”——描述屏幕上有什么而不解释为什么在那里。“左上角有一个圆角按钮”是清单。 “主要 CTA 位于视口顶部，因为研究显示 68% 的用户在滚动前放弃此流程——该操作需要在到达时可见”是设计理由。
- 规范中的每个元素都应回答：为什么在这里？它为用户解决了什么问题？如果我们移除它会发生什么？
- 坏的： “加载时，在标题 2（24px，Inter Medium）中显示“创建您的第一个项目”。"
- 好的： “加载时，显示“创建您的第一个项目”——可用性测试中，新用户无法识别起始操作。此标题作为主要的开场提示，使用标题 2 来建立它作为页面的核心指令。”
- 如果你无法说明设计决策背后的意图，将其标记为开放问题，而不是将其记录为已确定的。

**结构化和彻底，永远不会臃肿。**
- 说明重要的事情。省略与用户需求或设计意图无关的通用描述。

**清晰的跨职能所有权。**
- 明确说明每个决策的做出者和原因。
- 将约束作为设计输入，而不是限制。

**明确地提出开放问题。**
- 不要隐藏不确定性；标记它。
- 区分“设计需要决定”与“工程需要决定”与“需要数据/研究”。

**视觉+逻辑规则。**
- 显示设计，然后解释其背后的原因。
- 使文案可测试和可实施。

**将约束视为设计输入。**
- 性能要求、无障碍需求、品牌指南——这些塑造了规范，所以让它们可见。

## 范围边界

### 此技能做：

- 记录设计决策（不要做出决策）
- 组织和结构化现有的设计工作以供实施
- 编写全面的规范、测试计划和资源包
- 生成跨职能演示文稿和对齐文档
- 透明地标记开放问题和依赖关系
- 映射边缘情况并编写文案变体
- 进行伦理审查，对照 Intent 的反模式目录
- 将规范与 `/measure` 的测量框架连接

### 此技能不做：

- 做设计决策（那是设计师的工作）
- 编写代码或实施细节
- 进行用户研究或验证（`/investigate`）
- 设计新功能（那需要 `/strategize` 或 `/journey`）
- 提供实施估计（那是工程的角色）
- 从头开始定义成功指标（`/measure` 拥有指标选择）
- 评估 UX 质量或启发式合规性（`/evaluate`）

## 何时使用此技能

触发 Specify 当：

- **“编写规范”** — 需要全面的 设计规范
- **“准备交接”** — 工程需要所有内容以供构建
- **“为工程记录此内容”** — 将设计转化为可执行的规范
- **“设计审查需要什么材料？”** — 准备对齐会议的材料
- **“构建测试计划”** — 定义成功标准和测试受众
- **“编写文案矩阵”** — 将所有变体记录在一个地方
- **“边缘情况是什么？”** — 设计非正常情况的场景和文案
- **“创建设计包”** — 组合规范、资源和文档
- **“供工程使用”或“供实施使用”** — 任何交接上下文

并非所有部分都适用于每个交接。使用对项目和服务受众有用的部分。
