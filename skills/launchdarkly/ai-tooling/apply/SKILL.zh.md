# 应用代码更改（SDK 安装）

执行集成计划。安装 SDK 并添加初始化每个跟踪表面的最小代码。

此技能嵌套在 [LaunchDarkly SDK 安装（引导）](../SKILL.md) 下；父级 **步骤 3** 是 **应用**。**之前：** [生成集成计划](../plan/SKILL.md)。**下一步：** [启动应用程序](../run/SKILL.md)。

**双 SDK：** 如果批准的计划是 **双 SDK** ([计划：双 SDK 集成](../plan/SKILL.md#dual-sdk-integrations))，您必须为 **两个** 跟踪完成步骤 1-3 -- 清单中的 **两个** 包，运行 **两个** 安装命令（或等效），需要 **两个** 凭据行，每个配方在 **不同** 的入口点中 **两个** 初始化。**不要** 在实际安装和初始化之前声称第二个 SDK 已设置。如果计划仅列出了一个跟踪，但用户要求两个，**停止** 并返回到 [计划](../plan/SKILL.md) -- 不要从记忆中编造后半部分。

**凭据时间：** 这是第一个要求用户提供 **SDK 密钥 / 客户端 ID / 移动密钥**（或同意获取/写入它们）的嵌套步骤。在 MCP OAuth 配置完成或在此处 D7（选项 4）显示 MCP 时，**不会** 提前询问账户状态（如果用户还没有账户，则通过 MCP OAuth 推断，见 [父级先决条件](../../SKILL.md#prerequisites)）。

## 步骤 1：安装 SDK 依赖项

使用您在 [SDK 配方](../../references/sdk/recipes.md) 中已匹配的 SDK 行中的 **确切** 包或模块名称和安装命令，并使用项目的包管理器进行安装。**不要** 从其他地方复制通用的安装行——每个配方都命名了正确的工件。

**双 SDK：** 运行 **跟踪 A 的安装命令**，然后运行 **跟踪 B 的安装命令**（来自计划）。确认 **两个** 包名都出现在 `package.json` / `requirements.txt` / 锁文件（或每种语言的正确包清单）中。当计划说明双 SDK 时，跳过第二个安装是 **不是** 可选的。

安装后，验证依赖项出现在锁文件或依赖项清单中 (**所有** 计划中的 LaunchDarkly 包)。

### 更改其他依赖项之前的权限

**无需额外权限（超出正常仓库编辑同意范围）即可允许：** 仅安装此集成配方中命名的 LaunchDarkly SDK 包（例如一个服务器 SDK，**或** 双 SDK 计划中列出的 **确切** 服务器 + 客户端对——**两个** 包都计入 LD 安装范围）。使用每个配方指定的 **最小** 安装（确切包名）。

**需要在运行任何命令或编辑清单之前获得明确的用户批准：** 超出该范围的任何更改，包括但不限于：

- 升级、降级、固定或添加 **非 LaunchDarkly** 包（同伴依赖项“修复”，`npm install X@latest`，`yarn upgrade`，`pnpm update`，提升 React/Node 类型，传递锁文件变化等）
- 运行 **`npm audit fix`**，**批量更新** 或 **替换** 项目的包管理器解析策略以使 SDK 满足
- 更改 **引擎** / **包管理器** 字段、**解析** / **覆盖** 或 **工作区** 条目，原因不是添加 LD 工件行

如果包管理器报告同伴冲突或安装失败：

**D8 -- 阻塞：** 现在调用您的结构化问题工具。
- 问题："安装报告 [具体错误]。为了修复此问题，我需要 [对非 LD 包的具体更改]。我应该继续执行这些附加更改吗？"
- 选项：
  - "是，执行这些更改"
  - "否，仅保留 LaunchDarkly 包——我将自行解决冲突"
  - "先显示确切命令"
- 停止。不要将问题作为文本写入。不要在无声地升级旧仓库“以匹配最新 SDK 的依赖项”。在用户选择选项之前不要继续。

如果用户 **拒绝** 更广泛的更改：如果可能，仅保留 LD 包添加，记录冲突，并继续使用占位符或手动步骤。

## 步骤 2：将 SDK 密钥添加到环境配置

**永远不要在应用程序源文件中硬编码 SDK 密钥、客户端 ID 或移动密钥**（仅通过环境变量引用它们）。

### 密钥之前的权限

**D7 -- 阻塞（强制——不要跳过）：** 现在调用您的结构化问题工具。此决策点存在是为了安全合规——用户必须明确选择如何处理密钥。跳过此步骤并在未经同意的情况下写入密钥是一个关键错误。
- 问题："SDK 需要您环境的 SDK 密钥（或客户端 ID / 移动密钥）。您希望如何设置密钥？"
- 选项：
  - "我会告诉您放在哪里"
  - "我会自行设置密钥——只需告诉我要使用的变量名"
  - "为我写入一个 `.env` 文件"
  - "我还没有账户——帮助我注册" -> 指向已解析的注册 URL（见 [来源归因](../../SKILL.md#source-attribution)），写入占位符并继续（密钥延迟到账户准备好时）
- 停止。不要将问题作为文本写入。在用户选择选项之前不要从 LaunchDarkly 获取密钥或将实际值写入仓库。不要从上下文或先前对话中推断答案——始终提供此选择。

**如果用户选择选项 1（“告诉我放在哪里”）：**
1. 询问他们希望将密钥写入的位置（文件路径、密钥管理器等）
2. 询问他们希望如何提供密钥：粘贴，或让代理通过 MCP/API 获取
3. 仅将密钥写入用户指定的位置
4. 不要创建 `.env` 或修改任何其他文件

**如果用户选择选项 2（“我自己设置”）：**
1. 告诉他们他们需要设置的变量名（见下表）
2. 将他们链接到正确的仪表板页面。当项目密钥和环境密钥都已知时：**`https://app.launchdarkly.com/projects/{projectKey}/settings/environments/{envKey}/keys`**。当仅知道项目密钥时：**`https://app.launchdarkly.com/projects/{projectKey}/settings/environments`** 并告诉他们选择环境。当两者都不知道时：**`https://app.launchdarkly.com/projects`** 并告诉他们导航到 **设置 > 环境** 以找到密钥。
3. 等待用户确认密钥已就位，然后再进行步骤 3
4. 不要获取、写入或处理密钥值

**如果用户选择选项 3（“为我写入一个 `.env` 文件”）：**
1. 询问他们希望如何提供密钥：粘贴，或让代理通过 MCP/API 获取
2. 跟随下面的 [写入 `.env` 当用户同意时](#write-to-env-when-the-user-consents) 部分
3. 在写入任何实际值之前，确保 `.env` 在 `.gitignore` 中

**如果用户选择选项 4（“我还没有账户”）：**
1. 指向已解析的注册 URL（见 [来源归因](../../SKILL.md#source-attribution)）
2. 解释 SDK 密钥设置需要账户——他们可以在注册后完成设置
3. 在写入之前确保 `.env` 在 `.gitignore` 中（与选项 3 / [写入 `.env`](#write-to-env-when-the-user-consents) 的检查相同）
4. 写入占位符变量名到 `.env`（没有实际值），以便代码可以编译
5. 继续步骤 3（初始化代码）使用占位符环境变量引用。应用程序在设置真实密钥之前无法连接到 LaunchDarkly，这是预期的。
6. 在引导日志中注明密钥设置正在等待账户创建

### 通过 MCP 获取密钥

当用户要求代理获取密钥（通过上述选项 1 或 3）时，使用 **`get-environments`** MCP 工具（如果配置）。使用项目密钥调用它——响应包含每个环境的 **SDK 密钥**、**客户端 ID** 和 **移动密钥**。当 `get-environments` 已经返回它们时，**不要** 对单个密钥进行单独的 API 请求。

```
get-environments({ request: { projectKey: "PROJECT_KEY" } })
```

**安全：** 将包含密钥的 MCP 响应视为敏感信息。仅将密钥写入用户选择的位置，**不要** 在聊天响应中回显完整密钥值。代理会话历史记录或日志中的密钥可能会在会话结束后仍然存在。

从响应中匹配环境的正确密钥类型（见下表）。如果 MCP 未配置，请指导用户到 LaunchDarkly 仪表板检索他们的密钥：`https://app.launchdarkly.com/projects/{PROJECT_KEY}/settings/environments/{ENV_KEY}/keys`。

### 变量名和值来源

| SDK 类型 | 变量名（典型） | LaunchDarkly 中的来源 |
|----------|----------------|-------------------------|
| 服务器端 | `LAUNCHDARKLY_SDK_KEY` | `get-environments` 响应 → 环境 → SDK 密钥 |
| 客户端端 | 逻辑 / 打包器前缀名称（见下文） | `get-environments` 响应 → 环境 → 客户端 ID |
| 移动端 | `LAUNCHDARKLY_MOBILE_KEY` | `get-environments` 响应 → 环境 → 移动密钥 |

**客户端（浏览器）项目：** LaunchDarkly 值仍然是客户端 ID。在 `.env` 中，使用打包器向客户端代码暴露的名称：

| 堆栈 | `.env` 键 | 代码中读取 |
|-------|------------|--------------|
| Create React App | `REACT_APP_LAUNCHDARKLY_CLIENT_SIDE_ID` | `process.env.REACT_APP_LAUNCHDARKLY_CLIENT_SIDE_ID` |
| Vite | `VITE_LAUNCHDARKLY_CLIENT_SIDE_ID` | `import.meta.env.VITE_LAUNCHDARKLY_CLIENT_SIDE_ID` |
| Next.js | `NEXT_PUBLIC_LAUNCHDARKLY_CLIENT_SIDE_ID` | `process.env.NEXT_PUBLIC_LAUNCHDARKLY_CLIENT_SIDE_ID` |

其他堆栈可能使用不同的前缀或纯 `LAUNCHDARKLY_CLIENT_SIDE_ID`——匹配项目已用于公共环境变量的方式。

### 写入 `.env`（当用户同意时）

使用 **集成根** 作为文件路径（仓库根或单仓库中的目标包——见 [检测仓库堆栈](../detect/SKILL.md)）。

1. **创建或更新 `.env`：** 如果 `.env` 不存在，则创建它。如果它存在，则 **追加或更新** 仅 LaunchDarkly 行——**不要** 删除任何无关的变量。
2. **添加集成需要的项：**
   - 仅服务器：`LAUNCHDARKLY_SDK_KEY=...`
   - 客户端/浏览器：在正确的打包器前缀键下添加 **客户端 ID**（例如 `VITE_LAUNCHDARKLY_CLIENT_SIDE_ID=...`）。
   - **全栈或混合（例如 Next.js，SSR + 客户端）：** 当使用两个 SDK 时，添加服务器 SDK 密钥和客户端 ID 行。
   - 移动端：`LAUNCHDARKLY_MOBILE_KEY=...` 当适用时。
3. **`.gitignore`：** 确保 `.env` 列在创建 `.env` 的同一根目录中的 `.gitignore`（或在单仓库中最近的关联忽略文件中）。如果条目缺失，请添加它——仅在用户同意仓库更改（与写入 `.env` 相同的权限范围）之后。不要提交包含实际密钥的文件。
4. **`.env.example` / `.env.sample`：** 如果项目使用，添加 **占位符** 条目（没有实际密钥），以便队友知道要设置的变量。

如果项目不使用 dotenv 并依赖于配置模块或托管密钥，请遵循现有模式——在写入任何文件中的实际值之前，上述 D7 同意仍然适用。

## 步骤 3：添加 SDK 初始化代码

初始化形状**取决于在检测和规划期间选择了哪个 SDK**。此技能不包括针对每个 SDK 的复制粘贴示例——使用错误的片段（例如 React Web 而配方是 Node 服务器）会误导你。

**事实依据（按顺序使用，双 SDK 时每个跟踪重复）：**

1. **[SDK 配方](../../references/sdk/recipes.md)** — 此跟踪 SDK 的行：安装是上述步骤 1；初始化，请遵循那里列出的 **SDK 详情** / 文档链接。
2. **SDK 详情文件** 在 [`snippets/`](../../references/sdk/snippets/) 下（当从配方链接时）——策划链接，对于许多 SDK，还有与该 SDK 对齐的完整引导样本。
3. **LaunchDarkly 的官方文档** 对于该 SDK（配方或详情文件中的 URL）——使用它们的入口点和异步模式（例如 React Web：[React Web SDK](https://launchdarkly.com/docs/sdk/client-side/react/react-web)）。

使用步骤 2 中的凭据进行接线：服务器 SDK 使用 `LAUNCHDARKLY_SDK_KEY`；客户端/浏览器 SDK 使用客户端 ID，并使用步骤 2 中适用的 **打包器前缀** 环境名称。

将导入和初始化添加到 **该跟踪的应用程序入口点**（或在单仓库中目标包的入口点——见 [检测仓库堆栈](../detect/SKILL.md)）。**双 SDK：** 服务器初始化进入计划的 **服务器** 入口点；客户端/提供者初始化进入 **客户端** 入口点——**永远不要** 使用单个共享块假装涵盖两个，除非该堆栈的官方文档明确规定了适用于两个的模式。

### 关键原则

1. **在文件顶部导入**，与其他导入一起
2. **在应用程序生命周期早期初始化** **针对该运行时**（Node 服务器与浏览器）
3. **在 SDK 支持时等待初始化** 再评估标志
4. **处理错误**——记录失败但不要崩溃应用程序
5. **匹配现有代码风格**——与代码库其余部分相同的模式（异步/等待，回调，CommonJS vs ESM）
6. **为每个表面使用正确的模式**——服务器端初始化来自服务器配方中的服务器代码；客户端/提供者初始化来自客户端配方中的客户端代码。**不要** 将一个片段用于两个跟踪，或在双 SDK 计划中跳过第二个跟踪的初始化。

## 步骤 4：验证代码可以编译

更改后：

1. 运行项目的构建或编译步骤
2. 如果配置了，运行代码检查器
3. **不要** 升级无关的依赖项，除非用户批准了该范围（[更改其他依赖项之前的权限](#permission-before-changing-other-dependencies)），修复任何导入错误或类型问题

如果代码无法编译，**不要** 进入下一步。
