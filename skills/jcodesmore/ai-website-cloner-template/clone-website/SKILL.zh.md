# 克隆网站

你即将逆向工程并重建用户请求中的**目标 URL 或 URL**，以像素级完美的克隆形式。

当提供多个 URL 时，保留每个路径名作为独立路由，并隔离每个目标的研究、截图、组件和资源。仅查询字符串或片段不同的 URL 共享路径名，因此请在输出计划中明确解决它们的路由和状态行为。只有在共享基础和输出计划固定后，才能并行化页面工作，以便并发构建者不会互相覆盖。

这不是一个两阶段过程（检查然后构建）。你是一个**在现场巡视的工长**——当你检查页面的每个部分时，你会将详细规范写入文件，然后将该文件交给一个拥有所需所有内容的专家构建代理。提取和构建是并行发生的，但提取过程是细致的，并产生可审计的工件。

## 范围默认值

目标是用户请求的 URL 解析到的页面。精确克隆该 URL 下可见的内容。除非用户另有说明，否则使用这些默认值：

- **保真度级别：** 像素级完美——颜色、间距、排版、动画完全匹配
- **范围内：** 视觉布局和样式、组件结构和交互、响应式设计、用于演示目的的模拟数据
- **范围外：** 真实的后端/数据库、认证、实时功能、SEO 优化、无障碍性审核
- **自定义：** 无——纯粹的模拟

如果用户提供额外的说明（特定的保真度级别、自定义项、额外上下文），请优先考虑这些说明而不是默认值。

## 输出隔离和路由保留

将每个目标 URL 视为持久的项目输出，而不是替换先前构建内容的许可。

在提取之前选择 `<app-root>`。对于单个应用程序，`<app-root>` 是仓库根目录（`.`）。如果不同的源需要单独的应用程序，则需要用户提供或批准为每个源准备的 Next.js 项目根；验证每个根可以独立构建，并且永远不会将一个源的输出写入另一个根。

然后为每个目标分配：

- 一个抗冲突的 `<site-key>`：一个可读的源别名（包括非默认端口）加上规范化源上 SHA-256 的前 8 个小写十六进制字符。
- 一个抗冲突的 `<page-key>`：一个保留段的可读路径名别名加上规范化路径名和任何状态查询/片段上 SHA-256 的前 8 个小写十六进制字符；使用 `root-<hash>` 表示 `/`。永远不要单独依赖有损字符替换。
- 一个工件根：`<app-root>/docs/research/<site-key>/<page-key>/`。
- 一个截图根：`<app-root>/docs/design-references/<site-key>/<page-key>/`。
- 一个组件根：`<app-root>/src/components/sites/<site-key>/<page-key>/`，真正的同站共享组件在 `<app-root>/src/components/sites/<site-key>/shared/` 下。
- 一个资源根：`<app-root>/public/sites/<site-key>/<page-key>/`，真正的同站共享资源在 `<app-root>/public/sites/<site-key>/shared/` 下。
- 一个 Next.js 路由文件。

剩余阶段的路径都相对于该目标的 `<app-root>`。在写入之前，验证每个计划的路线、工件根、截图根、组件根、资源根和下载器文件名是唯一的，或者是明确批准的共享位置。

路由默认值：

- 对于未受影响的模板中的第一个单 URL 克隆，`src/app/page.tsx` 处的现有脚手架可能会被替换，以便克隆仍然可以在 `/` 下访问。
- 对于来自同一源的多个 URL，或任何添加到已包含克隆/用户编写页面的项目中的后续克隆，保留规范化源路径名作为其 App Router URL（例如，`/docs/intro` 变成 `<app-root>/src/app/docs/intro/page.tsx`）。对会触发 App Router 语法的文件系统段名进行编码：用百分号编码的文件夹拼写来转义开头的 `_` 或 `@`，以及字面括号或方括号，而不是创建私有文件夹、插槽、路由组或动态段。在完成前验证构建的路由是否解析到精确的规范化 URL。
- 在写入之前检查每个现有的 `src/app/**/page.tsx`。除非用户明确批准该确切替换，否则永远不要删除或替换非脚手架路线、组件树、研究文件夹、截图或资源命名空间。
- 如果计划的路线已存在，则停止并询问是否要更新该路线、选择另一条路线或跳过它。
- 来自不同源的 URL 可能需要不兼容的字体、全局 CSS、布局和元数据。在修改文件之前，询问用户是否想要单独准备的应用程序根（推荐）或有意合并的多站点应用程序，具有路由范围的样式。不要创建未经批准的 monorepo 或在静默中混合全局基础。

## 预飞行检查

1. **需要浏览器自动化。** 检查可用的浏览器 MCP 工具（Chrome MCP、Playwright MCP、Browserbase MCP、Puppeteer MCP 等）。使用可用的工具——如果存在多个，则优先使用 Chrome MCP。如果没有检测到，请询问用户他们拥有的浏览器工具以及如何连接它。没有浏览器自动化，这项技能无法工作。
2. 解析用户请求中的目标 URL 或 URL。规范化并验证每个 URL；如果任何 URL 无效，请在继续之前要求用户更正它们。对于每个有效的 URL，验证它是否可通过您的浏览器 MCP 工具访问。
3. 验证基础项目构建：`npm run build`。Next.js + shadcn/ui + Tailwind v4 脚手架应该已经就位。如果没有，请告诉用户先设置它。
4. 列出现有路线 (`src/app/**/page.tsx`)、站点组件命名空间、研究工件、截图和公共资源。区分未受影响的模板脚手架和现有的克隆或用户编写的工作。
5. 编写输出计划，列出每个目标 URL、`<app-root>`、`<site-key>`、`<page-key>`、目标路线、工件根，以及是否必须更改任何共享基础文件。在编辑之前，与用户解决跨所有计划输出的冲突、同路径查询/片段行为以及多源布局决策。
6. 仅创建计划的每个页面/每个站点的目录，如果需要，则创建 `scripts/`。使用唯一的资源下载脚本名称，例如 `scripts/download-assets-<site-key>-<page-key>.mjs`；不要覆盖另一个页面的下载器。
7. 对于来自一个源的多个页面，一次按顺序构建共享基础，然后再并行进行页面工作。可选地确认是否要并行运行页面构建器（如果资源允许）或按顺序运行以避免过载。

在检查通过之前，阅读 [references/inspection-guide.md](references/inspection-guide.md) 以获取可重复使用的视觉、组件、布局和技术审核清单。

## 指导原则

这些是区分成功的克隆和“差不多就行”的混乱的真理。内化它们——它们应该指导你做出的每一个决定。

### 1. 完整性胜过速度

每个构建代理必须接收到**做完美工作所需的一切**：截图、确切的 CSS 值、本地路径下载的资源、真实文本内容、组件结构。如果构建代理必须猜测任何内容——颜色、字体大小、填充值——你就失败了。花额外一分钟提取更多属性，而不是发送一个不完整的简报。

### 2. 小任务，完美结果

当代理得到“构建整个功能部分”时，它会忽略细节——它会估算间距、猜测字体大小，并生成一个“差不多就行”但明显错误的结果。当它得到一个具有确切 CSS 值的单个聚焦组件时，它会每次都做到完美。

查看每个部分并判断其复杂性。一个简单的横幅，带有标题和按钮？一个代理。一个复杂的部分，有 3 种不同的卡片变体，每种都有唯一的悬停状态和内部布局？每个卡片变体一个代理，加上一个部分包装器代理。如有疑问，请将其拆分。

**复杂度预算规则：** 如果构建提示超过 ~150 行规范内容，该部分对于单个代理来说太复杂了。将其拆分成更小的部分。这是一个机械检查——不要用“但它们都有关联”来覆盖它。

### 3. 真实内容，真实资源

从实时网站提取实际文本、图像、视频和 SVG。这是一个克隆，不是模拟。使用 `element.textContent`，下载每个 `<img>` 和 `<video>`，将内联 `<svg>` 元素提取为 React 组件。只有在某物明显是会话唯一的服务器生成内容时，你才生成内容。

**分层资源很重要。** 看起来像是一个图像的部分通常是多个层——背景水彩/渐变、前景 UI 模拟 PNG、覆盖图标。检查每个容器的完整 DOM 树并列出其中的所有 `<img>` 元素和背景图像，包括绝对定位的覆盖层。遗漏一个覆盖层图像会使克隆看起来空荡荡的，即使背景是正确的。

### 4. 先构建基础

在构建任何东西之前，基础必须存在：全局 CSS 和目标网站的设计令牌（颜色、字体、间距）、内容结构的 TypeScript 类型，以及全局资源（字体、favicon）。这是按顺序进行的，不可协商。这之后的所有内容都可以并行进行。

### 5. 提取外观和行为

网站不是一个截图——它是一个活生生的东西。元素会根据滚动、悬停、点击、调整大小和时间而移动、改变、出现和消失。如果你只提取每个元素的静态 CSS，你的克隆在截图上看起来是正确的，但在有人实际使用时感觉是死的。

对于每个元素，提取其**外观**（通过 `getComputedStyle()` 获取的确切计算 CSS）和其**行为**（什么会改变、什么触发改变、以及过渡如何发生）。不是“它看起来像 16px”——提取实际计算值。不是“导航在滚动时改变”——记录确切的触发器（滚动位置、IntersectionObserver 阈值、视口交集）、前后状态（两组 CSS 值）和过渡（持续时间、缓动、CSS 过渡与 JS 驱动或 CSS `animation-timeline`）。

需要注意的行为示例——这些是说明性的，不是详尽的。页面可能会做此列表中未列出的其他事情，你必须捕获这些：
- 滚动到某个阈值后，导航栏会收缩、更改背景或获得阴影
- 当元素进入视口时，会以淡入、滑入、交错延迟的方式动画进入视图的元素
- 滚动时自动对齐的部分 (`scroll-snap-type`)
- 滚动速度不同的视差层
- 悬停状态会动画（不只是改变——过渡持续时间和缓动很重要）
- 带有进入/退出动画的下拉菜单、模态框、手风琴
- 滚动驱动的进度指示器或不透明度过渡
- 自动播放的轮播或循环内容
- 页面部分之间的暗到亮（或任何主题）过渡
- **循环的标签/药丸内容**——按钮通过过渡切换可见的卡片集
- **滚动驱动的标签/手风琴切换**——侧边栏中，随着内容滚动，活动项会自动更改（IntersectionObserver，不是点击处理程序）
- **平滑滚动库**（Lenis、Locomotive Scroll）——检查 `.lenis` 类或滚动容器包装器

### 6. 在构建之前确定交互模型

这是克隆中最昂贵的错误：构建基于点击的 UI，而原始版本是基于滚动的，反之亦然。在为交互部分编写任何构建提示之前，你必须明确回答：**这个部分是由点击、滚动、悬停、时间还是它们的组合驱动的？**

如何确定：
1. **先不点击。** 缓慢滚动通过该部分，观察当您滚动时是否有任何内容会自行改变。
2. 如果它们会改变，它是基于滚动的。提取机制：`IntersectionObserver`、`scroll-snap`、`position: sticky`、`animation-timeline` 或 JS 滚动监听器。
3. 如果滚动时没有改变，那么点击/悬停以测试基于点击/悬停的交互。
4. 在组件规范中明确记录交互模型：“交互模型：基于滚动的，使用 IntersectionObserver”或“交互模型：点击切换，带不透明度过渡”。

一个带有粘性侧边栏和滚动内容面板的部分与一个点击切换内容的标签界面从根本上不同。做错了会导致完全重写，而不是 CSS 微调。

### 7. 提取每个状态，而不仅仅是默认状态

许多组件有多个视觉状态——标签栏根据每个标签显示不同的卡片，页眉在滚动位置 0 和 100 时看起来不同，卡片有悬停效果。你必须提取所有状态，而不仅仅是页面加载时可见的状态。

对于标签化/有状态的内容：
- 通过浏览器 MCP 点击每个标签/按钮
- 提取每个状态的内容、图像和卡片数据
- 记录哪些内容属于哪个状态
- 注意状态之间的过渡动画（不透明度、滑入、淡入等）

对于滚动依赖元素：
- 在滚动位置 0（初始状态）捕获计算样式
- 滚动到触发阈值后再次捕获计算样式（滚动状态）
- 比较两者以识别确切改变哪些 CSS 属性
- 记录过渡 CSS（持续时间、缓动、属性）
- 记录确切的触发阈值（以 px 为单位的滚动位置，或视口交集比率）

### 8. 规范文件是事实来源

在派发任何构建代理之前，每个组件都会在页面的工件根下（`docs/research/<site-key>/<page-key>/components/`）获得一个规范文件。该文件是提取工作和构建代理之间的合同。构建代理在其提示中接收规范文件的内容——该文件还作为可审计的工件持久存在，如果看起来有问题，用户（或你）可以审查它。

规范文件不是可选的。它不是锦上添花。如果你在写入规范文件之前派发构建代理，你正在基于你能从浏览器 MCP 会话中记住的内容发送不完整的指令，构建代理将猜测以填补空白。

### 9. 构建必须始终可以编译

每个构建代理必须在完成前验证 `npx tsc --noEmit` 通过。合并工作树后，你验证 `npm run build` 通过。一个损坏的构建即使是暂时性的也是不可接受的。

## 第一阶段：侦察

使用浏览器 MCP 导航到目标 URL。

### 截图
- 在桌面（1440px）和移动（390px）视口下**全页截图**
- 保存到该页面的截图根（`docs/design-references/<site-key>/<page-key>/`）并使用描述性名称
- 这些是您的参考——构建代理将稍后接收到特定部分的裁剪/截图

### 全局提取
在执行任何其他操作之前，从页面提取以下内容：

**字体**——检查 `<link>` 标签中的 Google 字体或自托管字体。检查关键元素（标题、正文、代码、标签）的计算 `font-family`。记录实际使用的每个字体、权重和样式。对于单站点应用程序，使用 `next/font/google` 或 `next/font/local` 在 `src/app/layout.tsx` 中配置共享字体。在批准的合并多站点应用程序中，保持不兼容的字体/布局问题按路由范围划分。

**颜色**——从页面计算样式中提取网站的颜色调色板。对于单站点应用程序，将目标颜色合并到 `src/app/globals.css` 中，而不要删除现有路线所需的令牌。将它们映射到 shadcn 的令牌名称（背景、前景、主要、柔和等），如果它们适用。在批准的合并多站点应用程序中，使用路由包装器或范围令牌命名空间，而不是替换另一个站点的全局调色板。

**Favicon & 元数据** — 下载页面/网站 SEO 资产在计划的网站资产命名空间下。将真正应用全局的元数据仅在它适用于每个路由时放在根布局中；否则从目标页面或路由布局导出路由特定的元数据。

**全局 UI 模式** — 确定任何全站 CSS 或 JS：自定义滚动条隐藏、页面容器上的 scroll-snap、全局关键帧动画、背景滤镜、用作叠加层的渐变、**平滑滚动库**（Lenis、Locomotive Scroll — 检查 `.lenis`、`.locomotive-scroll` 或自定义滚动容器类）。将真正共享的行为合并到 `globals.css` 中；将页面特定的行为限定在页面中，以便现有路由不会意外更改。

### 强制交互扫描

这是在截图之后、在执行任何其他操作之前的一个专用步骤。它的目的是发现页面上的每个行为——其中许多行为在静态截图中是看不见的。

**滚动扫描**：通过浏览器 MCP 缓慢地从上到下滚动页面。在每个区域，暂停并观察：
- 头部是否改变外观？记录触发滚动的位置。
- 元素是否动画进入视图？记录哪些元素和动画类型。
- 侧边栏或标签指示器是否随着滚动自动切换？记录机制。
- 是否有滚动 snap 点？记录哪些容器。
- 是否有平滑滚动库激活？检查非原生滚动行为。

**点击扫描**：点击看起来可交互的每个元素：
- 每个按钮、标签、药丸、链接、卡片
- 记录发生的事情：内容是否更改？是否打开模态框？是否出现下拉菜单？
- 对于标签/药丸：点击每一个并记录每个状态下的内容

**悬停扫描**：将鼠标悬停在可能具有悬停状态的每个元素上：
- 按钮、卡片、链接、图像、导航项
- 记录更改：颜色、缩放、阴影、下划线、不透明度

**响应式扫描**：通过浏览器 MCP 在 3 个视口宽度下进行测试：
- 桌面：1440px
- 平板：768px
- 手机：390px
- 在每个宽度下，注意哪些区域更改布局（列→堆叠、侧边栏消失等）以及大约在哪个断点发生更改。

将所有发现保存到 `<artifact-root>/BEHAVIORS.md`。这是你的行为圣经——在编写每个组件规范时参考它。

### 页面拓扑
从上到下绘制页面上的每个独立区域。给每个一个工作名称。记录：
- 它们的视觉顺序
- 哪些是固定/粘性覆盖层与流式内容
- 整体页面布局（滚动容器、列结构、z-index 层）
- 区域之间的依赖关系（例如，覆盖所有内容的浮动导航）
- **每个区域的交互模型**（静态、点击驱动、滚动驱动、时间驱动）

将其保存为 `<artifact-root>/PAGE_TOPOLOGY.md`——它成为你的组装蓝图。

## 第二阶段：基础构建

此阶段按来源顺序进行。自己做（不委托给代理），因为它涉及共享文件。重新阅读输出计划并保留编辑现有路由之前的一切：

1. **合并字体和共享布局行为**，而不删除现有路由的要求。当行为不是真正应用全局时使用路由布局。
2. **小心合并全局 CSS**；将页面/站点特定的标记、关键帧、滚动行为和实用工具限定在路由包装器下，当它们可能冲突时。
3. **创建命名空间的 TypeScript 接口**，用于你观察到的内容结构；仅当它们的契约匹配时才重用现有同站类型。
4. **提取 SVG 图标**——在同站图标下 `src/components/sites/<site-key>/shared/icons.tsx` 中去重相同的图标；将页面专用图标保留在页面组件命名空间中。按视觉功能命名它们（例如，`SearchIcon`、`ArrowRightIcon`、`LogoIcon`）。
5. **将资产下载到计划的命名空间**——使用页面唯一命名的下载脚本并写入 `public/sites/<site-key>/<page-key>/` 或批准的同站共享目录。永远不要用通用文件名覆盖另一个页面的资产。
6. 验证所有先前存在的路由仍然可以构建，然后运行 `npm run build`。

```javascript
// 通过浏览器 MCP 运行此脚本来发现所有资产
```

## 第三阶段：组件规范与分发

这是核心循环。对于页面拓扑中的每个区域（从上到下），你执行三个操作：**提取**、**编写规范文件**，然后**分发构建器**。

### 第一步：提取

对于每个区域，使用浏览器 MCP 提取所有内容：

1. **对区域进行截图**（滚动到它，截图视口）。保存到页面的截图根目录。

2. **提取 CSS**，用于区域中的每个元素。使用以下提取脚本——不要手动测量单个属性。对每个组件容器运行一次并捕获完整输出：

```javascript
// 每个组件提取——通过浏览器 MCP 运行
// 将 SELECTOR 替换为实际的 CSS 选择器
(function(selector) {
  const el = document.querySelector(selector);
  if (!el) return JSON.stringify({ error: 'Element not found: ' + selector });
  const props = [
    'fontSize','fontWeight','fontFamily','lineHeight','letterSpacing','color',
    'textTransform','textDecoration','backgroundColor','background',
    'padding','paddingTop','paddingRight','paddingBottom','paddingLeft',
    'margin','marginTop','marginRight','marginBottom','marginLeft',
    'width','height','maxWidth','minWidth','maxHeight','minHeight',
    'display','flexDirection','justifyContent','alignItems','gap',
    'gridTemplateColumns','gridTemplateRows',
    'borderRadius','border','borderTop','borderBottom','borderLeft','borderRight',
    'boxShadow','overflow','overflowX','overflowY',
    'position','top','right','bottom','left','zIndex',
    'opacity','transform','transition','cursor',
    'objectFit','objectPosition','mixBlendMode','filter','backdropFilter',
    'whiteSpace','textOverflow','WebkitLineClamp'
  ];
  function extractStyles(element) {
    const cs = getComputedStyle(element);
    const styles = {};
    props.forEach(p => { const v = cs[p]; if (v && v !== 'none' && v !== 'normal' && v !== 'auto' && v !== '0px' && v !== 'rgba(0, 0, 0, 0)') styles[p] = v; });
    return styles;
  }
  function walk(element, depth) {
    if (depth > 4) return null;
    const children = [...element.children];
    return {
      tag: element.tagName.toLowerCase(),
      classes: element.className?.toString().split(' ').slice(0, 5).join(' '),
      text: element.childNodes.length === 1 && element.childNodes[0].nodeType === 3 ? element.textContent.trim().slice(0, 200) : null,
      styles: extractStyles(element),
      images: element.tagName === 'IMG' ? { src: element.src, alt: element.alt, naturalWidth: element.naturalWidth, naturalHeight: element.naturalHeight } : null,
      childCount: children.length,
      children: children.slice(0, 20).map(c => walk(c, depth + 1)).filter(Boolean)
    };
  }
  return JSON.stringify(walk(el, 0), null, 2);
})('SELECTOR');
```

3. **提取多状态样式**——对于具有多个状态的任何元素（滚动触发、悬停、活动标签），捕获两个状态：

```javascript
// 状态 A：捕获当前状态的样式（例如，滚动位置 0）
// 然后触发状态更改（滚动、点击、通过浏览器 MCP 悬停）
// 状态 B：重新运行提取脚本在同一个元素上
// A 和 B 之间的差异就是行为规范
```

明确记录差异："属性 X 从 VALUE_A 变更到 VALUE_B，由 TRIGGER 触发，过渡：TRANSITION_CSS。"

4. **提取真实内容**——所有文本、alt 属性、aria 标签、占位符文本。使用 `element.textContent` 对每个文本节点。对于标签化/状态内容，**点击每个标签并按状态提取内容**。

5. **确定此区域使用的资产**——哪些命名空间下载的图像/视频以及哪些站点/页面图标组件。检查**分层图像**（同一容器中的多个 `<img>` 或 background-images 堆叠）。

6. **评估复杂性**——此区域包含多少个不同的子组件？一个独立的子组件是一个具有自己独特样式、结构和行为的元素（例如，卡片、导航项、搜索面板）。

### 第二步：编写组件规范文件

对于每个区域（如果拆分则为子组件），在页面的组件规范目录中创建一个规范文件。这不是可选的——每个构建器都必须有一个相应的规范文件。

**文件路径**：`docs/research/<site-key>/<page-key>/components/<component-name>.spec.md`

**模板**：


### 第三步：分发构建器

根据复杂性，在工作树中分发构建器代理：

**简单区域**（1-2 个子组件）：一个构建器代理获取整个区域。

**复杂区域**（3 个以上独立子组件）：拆分它。每个子组件一个代理，再加上一个导入它们的区域包装器代理。子组件构建器先开始，因为包装器依赖于它们。

**每个构建器代理接收的内容**：
- 它的组件规范文件的完整内容（直接在提示符中内联——不要说“去读规范文件”）
- 页面命名空间截图根目录中区域截图的路径
- 要导入的共享组件（计划的站点范围图标模块、`cn()`、shadcn 基本元素）
- 命名空间目标文件路径（例如，`src/components/sites/<site-key>/<page-key>/HeroSection.tsx`）
- 指令在完成前使用 `npx tsc --noEmit` 进行验证
- 对于响应式行为：特定的断点值以及更改内容

**不要等待**。一旦你分发了某个区域的构建器，就移动到提取下一个区域。构建器在其工作树中并行工作，而你继续提取。

### 第四步：合并

构建器代理完成工作后：
- 将它们的工作树分支合并到主分支
- 你对每个代理构建的内容有完全的上下文，因此可以智能地解决任何冲突
- 拒绝或修复任何合并删除或重写无关现有路由或另一个页面命名空间的合并
- 每次合并后，验证构建仍然通过：`npm run build`
- 如果合并引入了类型错误，立即修复它们

提取→规范→分发→合并循环持续进行，直到所有区域都构建完成。

## 第四阶段：页面组装

所有区域构建并合并后，将页面组装到批准输出计划中的确切目标路由中。仅使用 `src/app/page.tsx` 对第一个新鲜模板根克隆；否则使用计划的路径，例如 `src/app/docs/intro/page.tsx`：

- 导入所有区域组件
- 从你的拓扑文档中实现页面级布局（滚动容器、列结构、粘性定位、z-index 层级）
- 将真实内容连接到组件属性
- 实现页面级行为：滚动 snap、滚动驱动动画、暗到亮过渡、Intersection observers、平滑滚动（Lenis 等.）
- 确认在此运行之前存在的所有路由仍然存在并且没有被无意更改
- 验证：`npm run build` 通过干净

## 第五阶段：视觉 QA 差异

组装后，不要声明克隆完成。进行并排比较截图：

1. 在原始站点和克隆的计划的本地路由并排打开（或在同一视口宽度下截图）
2. 从上到下逐个区域比较，在桌面（1440px）
3. 再次在手机（390px）下比较

## 不应做的事情

这些是从之前的失败克隆中吸取的教训——每个克隆都耗费了数小时的返工：

- **不要在原始设计是滚动驱动时构建基于点击的选项卡（反之亦然）。** 在点击之前通过滚动首先确定交互模型。这是最昂贵的错误——它需要完全重写，而不仅仅是 CSS 修复。
- **不要仅提取默认状态。** 如果加载时显示“精选”的选项卡，点击“生产力”、“创意”、“生活方式”并提取每个的卡片/内容。如果页眉在滚动时变化，需在位置 0 和位置 100+ 处捕获样式。
- **不要遗漏叠加层/分层图像。** 背景水彩 + 前景 UI 模拟 = 2 张图像。检查每个容器的 DOM 树以查找多个 `<img>` 元素和定位叠加层。
- **不要为实际是视频/动画的内容构建模拟组件。** 在构建复杂的 HTML 模拟之前，检查该部分是否使用 `<video>`、Lottie 或 canvas。
- **不要估算 CSS 类。** 如果计算值是 `18px` 而 `text-lg` 是 `18px/28px` 但实际行高是 `24px`，则“看起来像 `text-lg`”是错误的。提取确切值。
- **不要在一个庞大的提交中构建所有内容。** 这个管道的整个目的是逐步验证的增量进度。
- **不要将新目标视为替换当前应用的许可。** 保留现有路由和命名空间工件；在更新已存在的路由前请先询问。
- **不要从构建提示中引用文档。** 每个构建器在其提示中直接获得 CSS 规范——不要“查看 DESIGN_TOKENS.md 获取颜色”。构建器不应需要阅读外部文档。
- **不要跳过资产提取。** 没有真实的图像、视频和字体，无论 CSS 多完美，克隆始终看起来不真实。
- **不要给构建器代理过多的权限。** 如果你在编写构建提示时它变得很长，因为该部分复杂，那是一个将其拆分为更小任务的信号。
- **不要将不相关的部分捆绑到一个代理中。** CTA 部分和页脚是具有不同设计的不同组件——不要将它们都交给一个代理并寄希望于最好的结果。
- **不要跳过响应式提取。** 如果你只在桌面宽度下检查，克隆将在平板和移动设备上崩溃。在提取期间在 1440、768 和 390 宽度下测试。
- **不要忘记平滑滚动库。** 检查 Lenis（`.lenis` 类）、Locomotive Scroll 或类似库。默认浏览器滚动感觉明显不同，用户会立即发现。
- **不要在没有规范文件的情况下派遣构建器。** 规范文件强制执行彻底提取并创建可审计的工件。跳过它意味着构建器会从记忆中尽可能多地提取提示中的内容。
