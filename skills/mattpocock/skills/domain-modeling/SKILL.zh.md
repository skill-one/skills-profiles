# 领域建模

在设计中积极构建和打磨项目的领域模型。这是一个*主动*的学科：挑战术语、发明边缘情况场景，并在术语和决策明确时立即记录下来。(仅仅*阅读* `CONTEXT.md` 获取词汇不是这项技能：那是一条任何技能都能做到的一行习惯。这项技能是在你改变模型时使用的，而不仅仅是消费它。)

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，则该仓库有多个上下文。该地图指向每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 全局决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 特定上下文决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

懒惰地创建文件：只有当你有东西要写时才创建。如果不存在 `CONTEXT.md`，则在第一个术语被解决时创建一个。如果不存在 `docs/adr/`，则在需要第一个 ADR 时创建它。

## 会话期间

### 与术语表进行挑战

当用户使用的术语与 `CONTEXT.md` 中的现有语言冲突时，立即指出。 "你的术语表将 'cancellation' 定义为 X，但你似乎意味着 Y。究竟是哪一个？"

### 锻炼模糊语言

当用户使用模糊或重载的术语时，建议一个精确的规范术语。 "你在说 'account'：你是指 Customer 还是 User？那不是同一回事。"

### 讨论具体场景

当讨论领域关系时，用具体场景进行压力测试。发明那些探测边缘情况并迫使用户精确说明概念之间边界的场景。

### 与代码交叉引用

当用户说明某项工作原理时，检查代码是否一致。如果你发现矛盾，将其暴露出来： "你的代码取消整个 Orders，但你刚才说部分取消是可能的。哪个是正确的？"

### 内联更新 CONTEXT.md

当术语被解决时，立即更新 `CONTEXT.md`。不要批量处理这些：实时捕获它们。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应该完全不含实现细节。不要将 `CONTEXT.md` 视为规范、草稿板或实现决策的存储库。它只是一个术语表，除此之外什么也不是。

### 有节制地提供 ADR

只有当以下三点都成立时才提出创建 ADR：

1. **难以撤销**：以后改变想法的成本是显著的
2. **没有上下文会令人惊讶**：未来的读者会想知道 "他们为什么要这样做？"
3. **是真实权衡的结果**：确实存在真正的替代方案，你选择了其中一个并给出了具体原因

如果其中任何一点缺失，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
