# 改进代码库架构

暴露架构上的摩擦并提出**深化机会**：将浅层模块重构为深层模块。目标是可测试性和AI可导航性。

此命令受项目领域模型指导，并基于共享的设计词汇构建：

- 使用 "codebase-design" 调用 Skill 工具以获取架构词汇（**模块**、**接口**、**深度**、**连接点**、**适配器**、**利用**、**局部性**）及其原则（删除测试，“接口即测试表面”，“一个适配器=假设的连接点，两个=真实的连接点”）。在每条建议中精确使用这些术语，不要偏离“组件”、“服务”、“API”或“边界”。

- `CONTEXT.md` 中的领域语言为良好的连接点命名；`docs/adr/` 中的 ADR 记录了此命令不应重新审议的决策。

## 流程

### 1. 探索

**在扫描前确定范围：YAGNI。** 深化模块的效果在于使未来对其的修改更简单，因此要额外关注代码库中最近发生变化的部分。在开始扫描前确定要查看的位置：

- 如果用户指定了方向（一个模块、一个子系统、一个痛点），则采纳它，并跳过以下推断。

- 否则，回溯一段较长的提交历史（`git log --oneline`）以找到代码库的热点，即反复出现的文件和区域，并让这些路径首先吸引你的注意力。如果变化分散且没有明显热点，则扩大范围。

阅读项目的领域词汇表（`CONTEXT.md`）以及你首先接触区域的任何 ADR。

然后生成一个子代理来遍历代码库。不要遵循僵化的启发式规则；有机地探索并记录你遇到的摩擦点：

- 理解一个概念需要跨多个小模块来回跳转的地方在哪里？
- 模块**浅层**，其接口几乎与实现一样复杂的地方？
- 纯函数仅为了可测试性而被提取出来，但真正的错误隐藏在它们被调用的方式中（没有**局部性**）？
- 紧密耦合的模块在其连接点处泄漏的地方？
- 代码库中哪些部分未测试或难以通过其当前接口进行测试？

对任何你怀疑是浅层的部分应用**删除测试**：删除它会使复杂性集中，还是会只是转移？一个“是，集中”是你要的信号。

### 2. 将候选方案作为 HTML 报告呈现

将一个自包含的 HTML 文件写入操作系统的临时目录，以避免任何内容进入代码库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（或在 Windows 上为 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，以便每次运行都获得一个新文件。为用户打开它（在 Linux 上使用 `xdg-open <path>`，在 macOS 上使用 `open <path>`，在 Windows 上使用 `start <path>`），并告诉他们绝对路径。

报告使用 **通过 CDN 的 Tailwind** 进行布局和样式，并使用 **通过 CDN 的 Mermaid** 绘制图表，其中图表/流程/序列可以可靠地传达结构。将 Mermaid 与手工制作的 CSS/SVG 视觉混合使用：当关系呈图形状（调用图、依赖关系、序列）时使用 Mermaid，当你想要更编辑式的视觉效果（大规模图表、横截面、折叠动画）时使用手工制作的 div/SVG。为每个候选方案提供**原始/改进的可视化**。要直观。

对于每个候选方案，渲染一个卡片，包含：

- **文件**：哪些文件/模块参与其中
- **问题**：当前架构为何导致摩擦
- **解决方案**：对将要发生变化的纯英文描述
- **收益**：以局部性和利用性为依据，以及如何改进测试
- **原始 / 改进图表**：并排显示，自定义绘制，说明浅层性和深化
- **建议强度**：`Strong`、`Worth exploring`、`Speculative` 之一，以徽章形式呈现

在报告末尾添加一个**首选建议**部分：你会首先处理哪个候选方案以及原因。

**使用 `CONTEXT.md` 中的领域词汇，以及 `/codebase-design` 中的架构词汇。** 如果 `CONTEXT.md` 定义了“订单”，则谈论“订单录入模块”，而不是“FooBarHandler”，也不是“订单服务”。

**ADR 冲突**：如果候选方案与现有 ADR 冲突，只有在摩擦足够值得重新审议 ADR 时才暴露它。在卡片中明确标记（例如，警告调用： _"与 ADR-0007 冲突，但值得重新打开因为…"_）。不要列出 ADR 禁止的每个理论上的重构。

参见 [HTML-REPORT.md](HTML-REPORT.md) 以获取完整的 HTML 框架、图表模式和样式指南。

**不要提议接口。** 写入文件后，询问用户：“你想探索这些中的哪一个？”

### 3. 审问循环

一旦用户选择了一个候选方案，使用 "grilling" 调用 Skill 工具与他们一起遍历决策树：约束、依赖关系、深化模块的形状、连接点后的内容、哪些测试得以保留。

副作用在决策明确时内联发生；使用 "domain-modeling" 调用 Skill 工具以保持领域模型当前：

- **在 `CONTEXT.md` 中命名一个深化模块，但该概念不存在？** 将术语添加到 `CONTEXT.md`。如果文件不存在，则懒惰地创建该文件。

- **在对话中使模糊术语清晰？** 直接更新 `CONTEXT.md`。

- **用户以承重理由拒绝候选方案？** 提供一个 ADR，表述为： _"我想记录这作为 ADR，以便未来的架构评审不会重新建议它吗？"_ 仅在未来的探索者实际需要该理由以避免重新建议相同事物时提供；跳过短暂的（“现在不值得”）和显而易见的理由。

- **想探索深化模块的替代接口？** 使用 "codebase-design" 调用 Skill 工具，并使用其设计两次的并行子代理模式。
