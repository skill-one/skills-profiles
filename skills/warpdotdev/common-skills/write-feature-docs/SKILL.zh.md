# 编写功能文档

为新的 Warp 功能起草完整的文档页面。你需要阅读该功能的规范，通过自己研究代码库来验证技术声明，确认内容设计计划并与工程师确认大纲，然后才能生成完整的 MDX 草稿并在 `warpdotdev/docs` 中打开草稿 PR — 并标记文档团队进行审核。

工程师的工作是确认你无法从规范和代码中验证的内容 — 不是进行全面的准确性审核，不是润色文字，也不是了解文档规范。

## 工作流程

1.  找到并阅读规范文件
2.  研究代码库以验证技术声明 — 尽量减少工程师需要检查的内容
3.  展示内容设计计划并等待确认 — 页面面向谁
4.  展示大纲并等待确认 — 页面将包含什么内容
5.  生成完整的 MDX 草稿
5.5. 尝试通过计算机使用进行截图（如果可用）
6.  在 `warpdotdev/docs` 中打开草稿 PR 并标记文档团队

步骤 3 和 4 是**两个独立的确认，按顺序进行。** 大纲是从计划中派生出来的 — 计划选择内容类型，内容类型决定了大纲包含哪些部分。将它们一起展示会给工程师一个基于他们尚未同意的受众的大纲，他们会锚定具体的大纲而不是重新考虑上面的问题。先确定页面面向谁，然后再决定里面包含什么内容。

---

## 步骤 1：找到并阅读规范

如果工程师没有提供规范 ID，请向他们询问规范 ID。规范 ID 是：

- 线性工单编号：`APP-1234`，`REMOTE-1234`，`QUALITY-408`
- GitHub 问题（以 `gh-` 开头）：`gh-4567`
- 短的 kebab-case 功能名称：`vertical-tabs-hover-sidecar`

在以下位置查找规范文件：

- `specs/<id>/PRODUCT.md` — 主要来源：用户界面行为，是什么和为什么
- `specs/<id>/TECH.md` — 次要来源：实现，数据模型

如果两个文件都存在，请阅读它们。`PRODUCT.md` 是文档内容的主要驱动因素。

**阅读 `TECH.md` 时：** 在结合它的任何内容之前，识别看起来像内部实现细节的内容 — 数据库模式，内部服务名称，私有 API 端点，机密服务器架构。将标记的项目展示给工程师，并询问他们哪些内容可以包含在公共文档中，哪些内容应该保持内部。不要在草稿中包含任何标记为机密的内容。

这个确认是为什么这项技能需要一个在场的工程师。没有无人照管的路径：如果没有有人说什么是安全的发布内容，`TECH.md` 的内容根本无法起草。

如果这两个文件都不存在，请跳转到 [无规范的备用方案](#no-spec-fallback)。

---

## 步骤 2：研究代码库

在展示计划或大纲之前，使用 GitHub CLI 验证尽可能多的技术内容 — 将工程师需要确认的内容减少到你确实无法从代码中确定的内容。

从代码中需要验证的内容：

- **功能标志名称**：从规范标题或工单中搜索一个安全的特征标记。在任何 shell 使用之前，将其减少为一个与 `^[A-Za-z0-9][A-Za-z0-9_-]*$` 匹配的允许标记，如果你无法安全地生成一个，则跳过 shell 搜索；然后运行 `FEATURE_TOKEN="<validated-token>" && gh search code "${FEATURE_TOKEN}" --repo warpdotdev/warp-internal`。
- **UI 字符串**：搜索规范中引用的用户可见按钮标签，菜单项名称或设置名称
- **设置路径**：确认确切的设置菜单路径（例如，`**设置** > **AI** > **知识**`）
- **规范中提到的 CLI 命令或键盘快捷键**
- **相关功能**：识别其他引用此功能的功能，用于“相关页面”
- **要标记的工程师**：识别拥有规范的工程师的 GitHub 处理名。
  - *交互模式*：运行 `gh api user --jq .login` 获取当前运行技能的人的标记 — 仅当技能由规范工程师直接调用时使用此方法。如果由文档团队成员或非作者运行技能，请使用下面的发现步骤代替。
  - *非作者运行（文档团队成员或未编写规范的任何人）*：在运行任何查找命令之前，验证规范 ID 只包含字母数字字符和连字符（匹配 `^[A-Za-z0-9][A-Za-z0-9-]*$`）。如果规范 ID 包含任何其他字符，则完全跳过查找并使用 `[TODO: 标记规范作者]` 作为占位符。如果规范 ID 有效，将其分配给 `SPEC_ID` 并按顺序处理这些步骤，找到标记后停止：
    1. **检查提交信息中的 `Co-authored-by:` 尾部** — 在从私有源镜像的存储库中（例如 `warp-internal`），同步机器人是提交作者，但真正的作者出现在 `Co-authored-by:` 尾部中。提取第一个非机器人条目：
       ```bash
       git log --follow -1 --format="%B" -- "specs/${SPEC_ID}/PRODUCT.md" \
         | grep -i "^Co-authored-by:" \
         | grep -v "\[bot\]" \
         | head -1 \
         | grep -oP '<[^>]+>' | tr -d '<>'
       ```
       这返回一个电子邮件（可能是 GitHub noreply 地址）。如果电子邮件匹配模式 `<userid>+<username>@users.noreply.github.com`，直接提取标记：`echo "$EMAIL" | grep -oP '\+\K[^@]+'`。如果是真实电子邮件，通过 `gh api "search/users?q=${EMAIL}+in:email" --jq '.items[0].login'` 解析它。
    2. **解析同步的 PR URL** — 一些同步机器人将原始 PR URL 嵌入提交正文（例如 `Synced from warp: https://github.com/warpdotdev/warp/pull/11901`）。提取它并获取 PR 作者：
       ```bash
       ORIG_PR=$(git log --follow -1 --format="%B" -- "specs/${SPEC_ID}/PRODUCT.md" \
         | grep -oP 'https://github\.com/[^/]+/[^/]+/pull/\d+' | head -1)
       # 提取所有者/存储库和 PR 号，然后：gh pr view <N> --repo <owner/repo> --json author --jq '.author.login'
       ```
    3. **搜索原始存储库的 PRs** — 尝试实际拥有代码的存储库（检查公共镜像和如果可以访问的私有源）：
       ```bash
       gh pr list --search "specs/${SPEC_ID}" --repo warpdotdev/warp-internal --state merged --json author --limit 1 --jq '.[0].author.login'
       # 也尝试：gh pr list --search "specs/${SPEC_ID}" --repo warpdotdev/warp --state merged --json author --limit 1 --jq '.[0].author.login'
       ```
       跳过登录包含 `[bot]` 的任何结果。
    4. **回退到提交作者电子邮件** — 只有当电子邮件不包含 `[bot]` 时：
       ```bash
       EMAIL=$(git log --follow -1 --pretty=format:"%ae" -- "specs/${SPEC_ID}/PRODUCT.md")
       ```
       如果 `${EMAIL}` 非空且无机器人，通过 `gh api "search/users?q=${EMAIL}+in:email" --jq '.items[0].login'` 解析它。
    5. 如果在所有步骤后都找不到标记，请在 PR 正文中使用 `[TODO: 标记规范作者]` 作为占位符。

对于你从代码中验证的每个声明，标记为已确认。对于你无法验证的声明（代码中未出现的 UI 行为，产品意图，未发布功能的行為），在大纲中标记为 `[UNVERIFIED]` — 那些是工程师需要关注的东西。

---

## 步骤 3：展示内容设计计划并等待

**这是两个确认中的第一个，并且在大纲之前。** 在决定里面包含什么内容之前，先确定页面面向谁。

填写 `.agents/templates/content-design-plan.md`，使用 `.agents/references/content-design-plan.md` 了解每个字段的要求：受众和 JTBD，问题，目标，目的和价值，内容类型，技能和模板，以及具有明确排除的高影响场景。

将其打印到终端，然后说：

> "在概述页面之前，请确认这是正确的读者和正确的工作。更正任何不正确的地方，或者说'看起来不错'，我将起草大纲。"

**等待工程师的回复。** 不要在同一消息中生成大纲。计划决定了内容类型，内容类型决定了大纲包含哪些部分 — 将大纲与未确认的计划一起展示会邀请工程师锚定他们面前的具体部分，而不是重新考虑上面的受众。

如果他们更改受众，内容类型或范围，请在继续之前修订计划并重新确认。将确认的计划带到步骤 6 的 PR 正文。

---

## 步骤 4：展示大纲并等待

根据**确认**的步骤 3 生成一个简洁的大纲 — 没有散文 — 基于已确认的计划。大纲显示了你已经从研究中确认的内容，以及确切需要工程师输入的内容。

以以下格式将大纲打印到终端：

```
📄 文档大纲 [功能名称]

建议放置
  部分： src/content/docs/<部分>/   （例如，agent-platform/cloud-agents/）
  文件： <功能名称>.mdx
  URL：  docs.warp.dev/<路径>/<功能名称>

内容部分
  标题： <功能名称>   （frontmatter；Starlight 将其渲染为 H1）
  开头段落： [1 句话描述你要写的内容]
  ## 关键功能 — [要突出显示的 2-4 个功能点]
  ## 工作原理 — [概念模型：是什么和为什么，没有步骤]
  ## <使用部分标题> — [例如，"创建环境"，"配置 X"]
      前置条件： [任何要列出的前置条件]
      步骤：
        1. [步骤描述]
        2. [步骤描述]
        3. [步骤描述]
        ...
  ## 相关页面 — [建议的跨链接]
```

> 上述部分是默认值。根据功能调整大纲：如果功能不需要概念解释，则省略 `## 工作原理`，如果功能有多个不同的工作流程，则添加多个使用部分，如果功能足够简单，则将 `## 关键功能` 折叠到开头段落中。

```
从代码库中已验证 ✅
  - [例如，"功能标志：`my_feature_flag` 在 warp-internal 中已确认"]
  - [例如，"设置路径：已确认为设置 > AI > 代理 > 权限"]

需要你的确认 ⚠️
  - [例如，"步骤 3 — 同步是否自动触发或需要手动操作？"]
  - [例如，"在功能标志启用之前，'导出' 按钮是否可见？"]
```

打印大纲后，说：

> "我已经从代码库中验证了可以验证的内容。请检查上面标记为 ⚠️ 的项目并回复任何更正，或者说'看起来不错'以继续。"

在继续之前等待工程师的回复。根据他们的反馈进行修订，然后起草。

如果他们的反馈与步骤 3 中确认的计划相矛盾 — 不同的读者，不同的内容类型 — 修订计划而不是让两者分道扬镳。计划会进入 PR 正文，所以一个过时的计划会误导审阅者。

---

## 步骤 5：生成 MDX 草稿

根据确认的大纲生成一个完整的 `.mdx` 文件。输出可以直接放入 `warpdotdev/docs`。

### 模板结构

**使用文档存储库中 `.agents/templates/` 的规范内容类型的标准模板** — `feature-doc.md`，`conceptual.md`，`procedural.md`，`reference.md`，`troubleshooting.md`，`quickstart.md` 或 `guide-page.md`。那些是事实来源，并且它们带有自己的字段指导。下面的草图显示了最常见的功能文档的形状，以便你知道要期待什么；它不是阅读真实模板的替代品。

模板强制执行的规则很容易从记忆中出错：页面标题放在**frontmatter**中，而不是正文 H1（Starlight 将 frontmatter 标题渲染为 H1，所以正文 H1 会重复它），并且每个括号内的指令在页面发布前必须删除。

```mdx
---
title: [功能名称 — 句子大小写]
description: >-
  [1-2 句话的独立摘要。以用户利益开头。包括功能名称和几个关键术语，以便它作为搜索结果片段工作。]
---

[开头段落：你将写的内容的描述。1-3 句话。以用户可以完成什么开头，而不是实现。]

:::note
[可选：读者需要 upfront 的关键上下文 — 前置条件，限制，或何时不使用此功能。如果没有任何内容适用，请删除此调用。]
:::

## 关键功能

* **功能 A** - 它做什么以及为什么它对用户很重要。
* **功能 B** - 它做什么以及为什么它对用户很重要。

## 工作原理

[概念部分：解释系统行为，数据流或架构。在"如何"之前回答"什么"和"为什么"。当它们第一次出现时定义任何新术语。不要在这个部分包含逐步程序 — 将概念和程序内容清晰分开。]

## [使用部分标题]

[程序部分：首先说明任务，然后给出编号步骤。在告诉用户如何做之前，简要解释他们为什么要这样做。]

### 前置条件

* **[前置条件]** - 它是什么以及在哪里获取。参见 [完整参考](链接此处)。

### [任务名称 — 句子大小写，例如，"使用 CLI 创建环境"]

1. 第一步。如果结果不明显，预期结果是什么。
2. 第二步。
3. 第三步。

## 相关页面

* [相关功能](../path/to/page.md)
* [更深入的指南](../path/to/guide.md)
```

### 风格规则 — 精确应用

这些约定来自 Warp 文档风格指南，并且必须遵循：

**标题**
- 所有标题使用句子大小写：仅首字母和正确的功能名称大写
- 正确的功能名称保持其大写："Agent Mode"，"Warp Drive"，"Oz"，"Command Palette"
- ✅ `## 工作原理` — ❌ `## How It Works`
- ✅ `## Agent Mode settings` — ❌ `## Agent mode settings`

**列表**
- 粗体术语 + 短横线 + 描述：`* **术语** - 描述`
- 不要使用冒号：❌ `* **术语**: 描述`

**UI 元素和路径**
- 粗体按钮，链接，菜单项：`点击 **保存**`，而不是 `` 点击 `保存` ``
- 粗体设置路径中的每个段：`**设置** > **AI** > **知识**`

**语气和语调**
- 第二人称： "你可以"，"允许你"
- 主动语气： "Warp 索引你的代码库" — 不是 "你的代码库被索引"
- 避免使用"简单"，"容易"，"只是" — 这些会贬低读者的体验
- 使用现在时态描述事物如何工作；使用祈使语气描述指令

**frontmatter 描述**
- 写作一个独立的摘要，它作为搜索结果片段工作
- 以用户利益开头，包括功能名称和关键术语
- ✅ `Environments ensure your cloud agents run with a consistent toolchain. Learn when to use environments and how to configure them.`
- ❌ `This page describes environments.`

**调用语法**（Astro Starlight）
- `:::note` — 补充上下文，提示
- `:::caution` — 委婉语，限制
- `:::danger` — 破坏性或不可逆的操作
- `:::tip` — 帮助提示和最佳实践

**要保留为 `[TODO: 文档审阅者 — ...]` 占位符的内容**
- 计算机使用失败质量门、不可用或功能尚未发布的截图
- 视频/GIF 嵌入
- 如果功能尚未发布，确切的设置路径
- 最终 URL 路径（文档团队确认放置）
- 任何在工程师确认后仍然未验证的行为

## 步骤 5.5：通过计算机使用捕获截图（如果可用）

生成草稿后，尝试使用计算机使用捕获任何 `[TODO: 文档审阅者 — 截图需要]` 占位符的截图。此步骤是**可选的** — 只有当 `computer_use` 工具可用时才运行它。如果计算机使用不可用，请将所有占位符保留为原样。

### 决定尝试哪些截图

只有当以下所有条件都为真时才尝试截图：

- 功能已经发布（不是在功能标志后或未发布的）
- UI 状态可以靠程序可靠地导航到
- 占位符指定了具体的 UI 表面（而不是模糊的，如“显示功能工作”）

跳过需要特定账户状态、特定数据或内容会暴露敏感信息的截图。

### 捕获前的设置

在进行任何截图之前：
1. 以一致窗口大小启动 Warp（使用 `warp-internal-computer-use` 技能获取启动指导）
2. 导航到相关的 UI 界面或触发相关功能状态
3. **等待** 所有动画完成且 UI 完全稳定
4. 关闭任何与文档功能无关的弹窗、通知或吐司
5. 关闭与本次截图无关的侧边栏面板或区域
6. **验证无敏感数据可见**：检查令牌、API 密钥、私有仓库名称、客户工作区数据、电子邮件地址或个人信息。如果可见，则不要进行截图。

### 捕获协议：预测 → 捕获 → 验证 → 重新尝试一次

这是一个结构化的自我验证循环。不要跳过它——它是防止状态错误、裁剪错误和框架错误捕获的主要防线。

**步骤 1：在捕获前说明预期**

在进行任何截图前，写明你期望看到的内容：

```
捕获预期
  主题：            [被文档化的特定 UI 元素或界面]
  预期元素：        [2-3 个必须可见的特定内容——例如面板标题、按钮、特定设置]
  预期状态：        [UI 状态——例如“设置面板打开”、“模态框可见”、“功能激活并显示输出"]
  禁止包含：        [任何必须不可见的内容——例如敏感数据、无关弹窗、加载旋转器]
```

**步骤 2：捕获**

进行截图。

**步骤 3：查看并与预期验证**

使用计算机使用功能查看捕获的图像，然后与预期进行验证：

- 声明的**主题**是否可见且是焦点？
- 所有**预期元素**是否都存在？
- UI 是否处于**预期状态**（非过渡状态或加载状态）？
- 是否有**禁止包含**的内容可见？
- 在目标显示宽度下文本是否**可读**？

如果全部通过 → 进入质量门。

如果任何一项失败 → **重新尝试一次**：重新导航到 UI 状态，等待更长时间让 UI 稳定，然后重新捕获和验证。

如果第二次尝试仍然失败 → **丢弃**该截图并留下 `[TODO: 文档审查者——截图]` 占位符。不要包含无法验证的截图。

**步骤 4：质量门——包含前的最终检查**

- [ ] 截图中的文本在目标显示尺寸下**可读**
- [ ] 文档化的 UI 元素**明显是焦点**——未被埋没、裁剪或遮挡
- [ ] **无敏感数据**可见（令牌、私有仓库、个人信息、客户数据）
- [ ] UI 处于**稳定、非加载状态**——无旋转器、骨架屏或过渡状态
- [ ] 截图**符合捕获前声明的预期**
- [ ] 截图在其目标渲染宽度下无模糊或过大

如果任何一项失败，丢弃截图并留下 `[TODO: 文档审查者——截图]` 占位符。

> **每个截图的最大尝试次数：2。** 如果都失败，则继续。

### 尺寸——选择最接近的标准宽度

- **全宽（默认）** — 全窗口捕获、宽泛的产品界面、周围上下文重要的布局
- **~375px** — 窄 UI 界面：弹出框、命令菜单、侧边面板、下拉菜单、聚焦交互流程
- **~300–350px** — 紧密裁剪的控制项、标签、按钮、工具提示、小型菜单

在调整尺寸前裁剪不必要的空白空间。保持同一部分中的截图序列宽度一致。

### 位置——在 MDX 中插入截图的位置

插入每个截图：
- **紧接**在介绍 UI 或其状态的段落之后
- **靠近配置说明**——展示用户进行选择的设置面板或菜单
- **靠近状态或结果说明**——展示帮助用户识别成功的完成状态或输出
- **在视觉功能页面的开头**——早期使用宽泛方向的截图

**不要**为每个步骤添加截图。仅在视觉上确实有助于理解时才添加。

### MDX 格式

```mdx
<figure>
  <img
    src="[相对于此 MDX 文件的路径到 src/assets/<section>/<feature-name>-<ui-state>.png —— 计算MDX文件的目录深度，使用相应数量的 ../ 级别；例如 3 级深度 → ../../../assets/<section>/...]"
    alt="[描述性 alt 文本：图像显示的内容，而不仅仅是“截图”]"
  />
  <figcaption>[标题：完整句子，≤10 个词，引导而非指示，无营销语言，句子大小写，以句号结尾。]</figcaption>
</figure>
```

**Alt 文本规则：**
- 描述图像显示的内容，而不仅仅是“截图”
- ✅ `alt="Agent 权限设置，'始终允许'选项被选中用于文件读取"`
- ❌ `alt="screenshot"` 或 `alt=""`

**标题规则：**
- 引导读者——描述显示的内容，而非指示操作
- 完整句子，理想情况下≤10 个词，不超过~20 个词
- 无营销语言（避免“轻松”、“快速”、“强大”、“一瞥）
- 不要重复正文——标题添加上下文，而非回声
- 不要列出所有可见内容——命名主题
- ✅ `<figcaption>Oz 网应用的 Environments 页面。</figcaption>`
- ❌ `<figcaption>点击吐司跳转到 agent 的会话。</figcaption>`（程序性——将此内容放在正文）

**文件命名：** 全小写、连字符、描述性——例如 `agent-mode-permissions-panel.png`

**文件位置：** 将 PNG 保存到 `src/assets/<section>/` 在 `warpdotdev/docs` 中（Astro 自动优化它们）。

## 步骤 6：打开草稿 PR

**在打开 PR 之前，确认文档仓库自身的需求是否已满足。** `warpdotdev/docs` 对传入页面有两个限制，跳过它们的 PR 将被退回：

1. **`.agents/references/docs-worthiness-criteria.md`** 在文档仓库中的 **门 0**：功能是否已发布且 GA，是否是公共界面？如果不是，不要打开 PR——告诉工程师原因并停止。即使工程师请求了页面，也要检查这一点，因为为尚未发布的功能起草是最常见的失败，而接近工作的工程师很容易比用户提前发布。

   该参考中的其余门是关于是否需要文档的判断。它们管理自动管道，而不是你——请求自己已发布功能的文档的工程师有管道无法看到的上下文。不要以此为由拒绝。

2. 工程师在步骤 3 中确认的内容设计计划，作为 PR 主体中的 `## 内容设计计划` 部分包含。

优先更新现有页面而不是创建新页面，如果页面已经涵盖了该界面。

生成草稿后，将其提交到 `warpdotdev/docs`：

1. 将 `warpdotdev/docs` 克隆到临时目录（或使用可用的本地克隆）
2. 将 MDX 文件写入 `src/content/docs/<proposed-section>/<filename>.mdx`
3. 在适当的部分向 `src/sidebar.ts` 添加占位符条目。示例：
   ```ts
   // [TODO: 文档审查者——确认位置]
   { label: '<Feature name>', link: '/<section>/<feature-name>/' },
   ```
4. 在新分支上提交和推送，分支名为 `docs/<spec-id>-feature-draft`
5. **将 PR 主体写入临时文件，然后使用 `--body-file` 打开草稿 PR。** PR 描述必须包括：
   - 功能名称和 spec ID
   - 原始 spec PR 的链接
   - 所有 `[UNVERIFIED]` 和 `[TODO]` 项目的列表，供审查者注意

   使用可用的任何文件写入方法（文件创建工具、Python `open()` 调用或 shell `cat` 带引号 heredoc）将主体写入 `/tmp/pr-body.md`，然后传递给 `gh`：
   ```bash
   gh pr create --draft --body-file /tmp/pr-body.md ...
   ```

   **永远不要直接传递 PR 主体**（通过 `--body "..."`、`echo` 或直接通过 shell `cat` 管接到 `gh`）。Shell 字符串插值在字符串到达 `gh` 之前会扩展反引号、`$vars` 和 `[ ]` 通配符模式，破坏包含这些字符的任何 Markdown。首先写入文件可避免所有 shell 对内容的解释。

   **在 PR 主体的“文档大纲”部分，使用普通项目符号** (`-`) 表示 agent 验证的项目，而不是 `- [x]` 复选框。仅将 `- [ ]` 复选框保留在“需要审查的项目”部分，以便审查者确切知道哪些项目需要他们的操作。

6. 在 PR 主体中，使用步骤 2 的句柄通知 spec 作者：
   - 如果找到有效的 GitHub 句柄：包括 `/cc @<engineer-handle>`
   - 如果生成了备用占位符：包括字面文本 `[TODO: 标记 spec 作者]`——不要用 `/cc @` 括起来，因为那样会产生格式错误的提及
   请求 `@rachaelrenk` 和 `@hongyi-chen` 审查。

## 无 spec 备用方案

如果 `specs/<id>/PRODUCT.md` 和 `specs/<id>/TECH.md` 不存在，先研究代码库，然后再采访工程师。

**研究步骤：**
1. 搜索 `warpdotdev/warp-internal`（或 `warp-server` 取决于上下文）中的功能名称和相关术语：`gh search code "<feature-name>" --repo warpdotdev/warp-internal`
2. 阅读最相关的源文件，了解功能的作用
3. 检查不同 ID 下是否有 spec 文件：`gh api repos/warpdotdev/warp-internal/contents/specs`
4. 审查与功能相关的最近合并的 PR：`gh pr list --search "<feature-name>" --state merged --repo warpdotdev/warp-internal --limit 10`

**研究后，** 尽可能完整地构建画面，然后仅使用 `ask_user_question` 填补代码中无法解决的特定空白——不要作为广泛的采访。具体提问：“我在 `app/src/ai/` 中找到了该功能。根据代码，我的理解是：[总结]。我无法确定这两件事：[具体问题]。”

从你的研究和工程师的针对性回答中构建计划和大纲，然后在起草前完成步骤 3（计划确认）和步骤 4（大纲确认）。

## 仅交互式——没有无人值守模式

此技能之前有一个“环境模式”，允许 `scan-new-specs` 无头运行，跳过步骤 3 和 4 中的确认，并将大纲嵌入 PR 描述中作为清单。**该模式已移除，`scan-new-specs` 已退役。**

它为尚未发布的功能生成草稿 PR，因为合并的 spec 不是已发布的功能，且没有无人值守运行能区分差异。跳过大纲确认还移除了人类可以在此之前重定向草稿的机会，在编写正文之前。

不要重新添加无人值守路径：

- **对于自动化的、发布触发的文档**，使用 `missing_docs` 在 `warpdotdev/docs` 仓库中。它在起草前对每个候选者进行 `.agents/references/docs-worthiness-criteria.md` 的限制，并且仅在新的稳定版本发布后运行。
- **对于希望为功能编写文档的工程师**，此技能是正确的工具——直接调用，工程师在场确认大纲和 `TECH.md` 边界。

如果你在没有交互式会话的情况下运行，停止并报告此技能需要交互式会话，而不是无论如何都起草。
