# 跨越批评

使用此技能在多个子代理独立就同一争议性问题提出提案或意见后，运行**第二轮**。与其自己整合他们的报告，不如将每个提案传送给*其他*作者，并要求他们对提案进行批评——优点和缺点——然后你整合由此产生的更丰富的分析集。

## 这为何重要

当你生成独立的提案（不同的模型，不同的角度），每个作者最终都会对问题有深入的了解——通常比你更深入，因为他们进行了调查。如果你直接单独整合他们的报告，你就是瓶颈：你只能看到你碰巧注意到的权衡。

要求作者互相批评是一个好领导在寻求建议时所做的事情：让几个持有不同观点的人聚在一起，让他们挑出彼此推理中的漏洞，然后你走出来的画面远比他们中的任何一个——或你——单独产生的要完整得多。作者将揭示失败模式、隐藏的假设和权衡，这些是你和原始提案者都没有注意到的。

## 何时使用它

当决策**存在争议**时使用跨越批评——即独立代理产生了真正不同的提案，或者问题主观到合理的方案存在分歧。良好的匹配：

- 架构和设计权衡。
- 代码审查，其中审查者得出了不同的结论。
- 有关错误原因的竞争性理论。
- 代码结构或 API 形状决策，没有单一的正确答案。

当提案已经强烈同意时，或者当问题有你可以直接验证的客观答案时，不必费心——批评会增加延迟和 token，它的价值专门来自于解决真正的分歧。在该范围内，自由使用它；你不需要高风险的理由，只需要真正值得解决的分歧。

## 先决条件：你需要先有独立的提案

这项技能是*第二轮*。它假设你已经手头有 N 个独立的提案。如果你还没有：

- 对于判断性强的决策，使用**委员会**技能生成（在相同问题上使用模型多样化的子代理）。
- 对于调查性强的疑问，通过生成并行子代理来生成（参见**研究**技能）。
- 或者使用你已经收集的任何一组独立的子代理提案。

关键在于第一轮必须是**独立的**——在第一轮中，不要让作者看到彼此的工作，否则你会失去使第二轮有价值的那种多样性。

## 如何操作

### 1. 汇集提案

收集每个作者的提案。保持它们简洁——核心建议及其推理，而不是完整记录。考虑用中性的标签（提案 A、B、C）标记它们，并在实际情况下，对作者身份进行匿名化以减少对哪个模型听起来最自信的从众偏见。

### 2. 传阅并要求结构化批评

重用**第一轮的相同子代理**而不是生成新的——它们保留了它们的上下文，并且可以从理解的位置进行批评。将每个作者的*其他*提案（不是自己的）发送给每个作者，并要求每个作者：

- 对于每个替代方案：它的**优点**（它做得对的地方，它比我的方法更强的地方）和它的**缺点**（风险、边缘情况、隐藏成本、错误假设）。
- 在看到替代方案后，他们是否会**修改自己的**建议——以及为什么或为什么不。
- 一个最终的排名或建议和信心。

坚持为每个替代方案提供*优点和缺点*。一个承认对手优势的诚实批评远比一个对自身提案的反射性辩护更有用。

### 3. 整合

现在自己把它整合起来。通过**证据质量而不是投票数**来比较批评。在你的最终答案中：

- 以建议开头。
- 注意作者在看到彼此的工作后在哪里达成了一致——第二轮中的共识是一个强烈的信号。
- 揭示针对每个选项提出的最尖锐的缺点。
- 解释为什么建议的选项在决策标准下经受住了批评。
- 指出剩余的分歧、信心和实质性未知数。

## 最终答案模板

除非任务要求不同，否则使用此结构：

```markdown
## 建议
[一个或两个关于决策的句子。]

## 批评如何改变了情况
- [作者在看到替代方案后在哪里达成了一致或改变了主意]
- [提出的最强反对意见，以及它是否具有决定性]

## 为什么这个选项胜出
- [基于批评的理由]

## 剩余风险和未知数
- [开放性问题或注意事项]
```

## 实用提示

- 除非底层任务明确涉及进行更改，否则将批评轮保持为只读。
- 除非用户询问，否则不要在用户界面的摘要中暴露内部子代理 ID。
- 如果批评薄弱或不支持，请向同一作者发送有针对性的后续，而不是丢弃它。
