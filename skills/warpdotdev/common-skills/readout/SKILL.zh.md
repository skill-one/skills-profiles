# 输出

输出将调查转化为一个耐久的HTML文档，让人可以在几周后阅读，而无需任何原始上下文。它以两种方式之一开始：

- **快照模式** — 在对话中途调用（“记录下来”）：对话积累的发现是源材料。
- **研究模式** — 刚刚调用（“/readout on how github webhook events are processed in the server”）：没有对话可供挖掘，因此调查本身是工作的一部分。

无论哪种方式，调用这个技能都是一个**辅助任务**。你作为主代理的工作是缩小范围，启动一个具有良好简报的子代理，然后让开——子代理负责挖掘/研究以及写作，将这项（通常很大）的工作从你的上下文窗口中排除。

## 协调器工作流程

### 1. 缩小范围——启动前询问

模糊的简报会产生模糊的文档。在启动之前，你应该能够列出文档将回答的具体问题；如果你不能，先采访用户：

- 提问2-4个有针对性的问题，提供具体的选项而不是开放式提示——先快速查看代码或主题，以便选项是真实的（子系统、入口点、竞争性关注点）。对于“/readout on how github webhook events are processed”：哪个方向更重要——传入触发器、回调或两者？当前状态参考还是陷阱搜索？哪个仓库？
- 始终确定**深度和受众**：高层概述与深度机制和行级基础；个人笔记与团队共享。
- 尊重耸肩。 “只是一个高层概述”是一个有效答案——在简报中记录它并继续前进，而不是审问。即使如此，也要尝试提取读者最需要回答的两个或三个问题；具体性使输出有用。
- 当范围已经明确时跳过采访——一个专注对话的快照或精确的研究请求不需要问题。在快照模式下，对话通常提供问题；只有在调用对包含哪些线程不明确时才询问。

### 2. 编写简报

编写一个简短的简报（大约10-20行），包含**指针而不是有效载荷**：

- 一个工作标题/主题，以及模式（快照或研究）
- 文档必须回答的具体问题（来自对话或采访），以及深度和受众
- 范围：要涵盖哪些线程/子系统，以及任何明确排除的内容
- 快照模式：值得将文档集中在其上的头条结论，每条一个——子代理从对话历史本身中提取完整内容，因此不要原样粘贴发现
- 研究模式：起始指针——你已知入口点文件、符号或目录
- 仓库/目录的绝对路径，这些路径为工作提供基础
- 每个仓库的主机URL以及已知的检查提交（例如 `github.com/org/repo @ abc123`），以便文档可以链接代码引用

### 3. 启动一个本地子代理

通过 `run_agents` 启动**本地**执行的一个子代理。本地很重要：文档会出现在用户的文件系统中，并在他们的浏览器中打开。将子代理命名为 `readout-<topic-slug>`。

从以下模板构建子代理的提示。它必须包括：

- 简报
- 与模式匹配的源材料块（快照模式还需要你的代理运行ID——`current_run_id` 从协调运行时上下文——以便子代理可以挖掘父对话使用 `search_conversation_history`）
- 在写作之前阅读此技能目录中的 `references/doc-guide.md` 的指令
- 输出路径约定和完成协议

### 4. 继续工作

启动后，继续你正在做的事情，或者结束你的回合——子代理的完成消息会自行到达；当它到达时，用一句话描述文件路径转发给用户。在研究模式下，一个全新的对话可能没有其他待办事项；只需结束回合。除非用户要求等待文档，否则不要坐在等待循环中。

## 子代理提示模板

调整这个；保持结构，并包括与模式匹配的源材料块。

```
你正在生成一个“输出”：一个自包含的HTML文档，回答关于 <主题> 的特定问题集，对于没有此上下文的读者。

简报：
<简报——包括要回答的问题、深度和受众>

源材料（快照模式）：
- 父对话：代理运行ID <current_run_id>。使用 search_conversation_history
  并将 agent_run_id 设置为该ID。进行多个有针对性的查询——每个简报中的一个问题——而不是一个广泛的查询；有针对性的查询会浮现出更多可用的细节。
- 代码库（<绝对路径>）。对话是你的起点，而不是牢笼：
  在断言文件引用之前验证它们，并且当一个部分需要更多深度才能独立存在时，去阅读代码并填补空白。

源材料（研究模式）：
- 直接在代码库（<绝对路径>）中调查。让简报的问题指导调查：跟踪实际的代码路径，阅读真实的实现，并将每个断言都基于文件:行引用进行基础。区分已验证和推断。不要用通用知识填充文档——它的价值在于这是这个代码库的真相。

- 仓库主机+提交，用于链接代码引用，如果已知：<github.com/org/repo @ commit>
  （否则从git中派生；参见文档指南的“链接代码引用”）。

从 <技能目录>/assets/template.html 中的规范模板开始——其 data-readout 浏览器块必须逐字复制，以便每个输出看起来都像其他输出。在写作之前，阅读 <技能目录>/references/doc-guide.md 并遵循它。

输出：
- 写一个自包含的HTML文件到 ~/.readouts/<YYYY-MM-DD>-<topic-slug>.html
  （如果不存在，则创建 ~/.readouts；如果名称被占用，则添加后缀 -2、-3、...；从 `date +%F` 获取日期）。
- 根据文档指南嵌入引用的源，当检出仓库时
  (<技能目录>/scripts/embed_snippets.py)。
- 刷新输出索引：python3 <技能目录>/scripts/update_index.py
  （完全重新生成 ~/.readouts/index.html 列出每个输出）。
- 文件写入后，用 `open <路径>` 打开它（如果环境是无头式，则跳过此步骤）。
- 向你的协调器报告：绝对文件路径、文档涵盖的2-3句话摘要，以及你无法验证的任何内容。
```

## 回退

- **子代理无法启动或被拒绝**：自己生成文档，遵循 `references/doc-guide.md`。如果有一个研究子代理可用，将对话挖掘或代码调查委托给它，以便你的上下文仍然保持精简。
- **子代理无法搜索对话历史**（快照模式；它将报告回）：用子代理回复一个提炼的发现快照，以便它可以继续——这是唯一一个提示中包含有效载荷是正确的情况。
- **用户提供的材料而不是对话**（转录、文件、链接）：将此材料视为源；工作流程中的其他内容保持不变。
