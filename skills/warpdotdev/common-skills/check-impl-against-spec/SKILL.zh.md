# 对照规范检查实现

仅在 PR 审查期间存在 `spec_context.md` 时使用此技能。

## 目标

确定已签出的 PR 中的实现是否在实质上与已批准的规范上下文相符。这是对正常代码审查的补充，而不是单独的输出。

## 输入

- `spec_context.md` 包含要与之比较的规范上下文。它可能包括产品规范内容（预期行为、验收标准）和技术规范内容（实现细节、文件变更）。
- `pr_diff.txt` 包含 PR 的注释差异。
- `pr_description.md` 可能包含额外的范围或理由。
- 工作区包含 PR 分支的内容。

## 流程

1. 读取 `spec_context.md` 并提取其做出的具体承诺：
   - 必须的行为（来自产品规范）
   - 必须变更的文件或子系统（来自技术规范）
   - 声明的约束
   - 必须的后续步骤、验证或迁移
2. 将这些承诺与 `pr_diff.txt` 中的实际实现以及签出的文件进行比较。
3. 当小规模的实现级调整保留了规范意图时，将其视为可接受。不要标记命名、结构或低级技术上的无害差异。
4. 仅在出现实质性差异时标记不匹配，例如：
   - 产品规范中要求的行为缺失
   - 实现与规范决策相矛盾
   - 变更引入了重大的未计划范围
   - 技术规范中要求的验证、迁移或兼容性步骤缺失

## 输出

- 不要创建单独的报告文件。
- 将规范一致性发现合并到 `review.json`。
- 将广泛的规范漂移问题放在审查摘要中。
- 仅在差异可以与 diff 中的更改行关联时添加内联评论。
- 将实质性的规范漂移视为至少是一个重要问题。
- 如果实现与规范足够接近，不要仅为了提及一致性而添加评论。

## 边界

- 当 PR 安全地实现了相同的结果时，不要要求规范的字面一一实现。
- 不要推测 `spec_context.md` 中实际上不存在的规范细节。
- 不要直接发布到 GitHub。
