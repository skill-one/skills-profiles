# spec-driven-implementation

在 Warp 中为重大功能采用以规范为先的工作流程。

## 概述

适用于重要功能，其中书面规范将提高实现质量、减少歧义或使审查更易于进行。要务实：并非每个变更都需要规范。

规范通常应位于：

- `specs/<线性工单编号>/PRODUCT.md`
- `specs/<线性工单编号>/TECH.md`

例如：

- `specs/APP-1234/PRODUCT.md`
- `specs/APP-1234/TECH.md`

`specs/` 应仅包含作为直接子项的以工单命名的目录。不要在那里创建以工程师命名的子目录或以功能缩写命名的目录。

如果尚未存在相关的 Linear 工单，则在编写规范之前创建一个。直接使用 Linear MCP 工具：

- `list_teams` 查找合适的团队
- `list_issue_labels` 检查预期的标签/标记
- `save_issue` 使用合适的团队和标签创建工单

如果从请求和周围上下文中无法明显看出正确的团队或标签，请使用 `ask_user_question` 来澄清，而不是猜测。

这些规范应主要由代理编写，而不是手动编写，并应提交到源代码控制中，以便进行审查并与代码保持最新状态。

## 需要规范的情况

在变更重大时强烈优先使用规范，例如：

- 产品或架构上的歧义
- 预期实现规模约为 1k+ 行代码
- 深入或跨领域的栈变更
- 风险行为变更，其中回归成本高昂
- 代理质量将通过更清晰的输入得到实质性改善的工作

规范通常不适用于：

- 小型、局部的错误修复
- 简单的重构
- 模糊不清的 UI 微调

对于纯 UI 变更，产品规范通常很有用，而技术规范可能不需要。

## 工作流程

### 1. 确定功能是否需要规范

评估功能的大小、歧义和风险。如果规范不会显著提高执行或审查，则跳过它们，并专注于验证。

### 2. 首先编写产品规范

在实现之前，创建 `PRODUCT.md` 描述期望的用户界面行为。

使用 `write-product-spec` 技能来生成它。产品规范应定义：

- 正在解决的问题
- 期望的用户体验
- 不变性和边缘情况
- 成功标准
- 将如何验证行为

如果功能具有 UI 或交互设计，如果存在，则要求提供 Figma 模板。如果没有模板，则继续进行，但在产品规范中明确指出这一点。

当存在 Linear 工单时，在规范中引用它。由于规范位于 `specs/<线性工单编号>/...` 下，这通常应该很简单。

### 3. 在适当时编写技术规范

使用 `write-tech-spec` 技能为重大或歧义的实现工作编写技术规范。

在以下情况下优先使用技术规范：

- 实现跨越多个子系统
- 架构或可扩展性很重要
- 有意义需要记录的权衡
- 审查者从审查计划中受益更多而不是原始代码

如果 e2e 原型导致更准确的实现计划，则可以编写技术规范。当实现细节仍然不确定时，不要强制编写过早的技术规范。

### 4. 实现批准的规范

批准规范后，使用 `implement-specs` 技能从批准的 `PRODUCT.md` 和 `TECH.md` 进行构建。

实现通常可以与产品和技术规范相同的 PR 推送。当工程师迭代时，保持 `PRODUCT.md`、`TECH.md`、代码更改和测试在同一 PR 中，以便审查反映实际要发布的特性。

对于大型功能，实现者可以可选地提供：

- `PROJECT_LOG.md` 以跟踪探索的路径、检查点和当前实现状态
- `DECISIONS.md` 以捕获设计和实现过程中做出的具体产品和技术决策

这些是可选的辅助工具，不是必需的输出。

### 5. 在实现过程中保持规范最新

如果实现与规范不一致，请更新规范而不是留下过时的规范。

更新 `PRODUCT.md` 时：

- 用户界面行为更改
- 成功标准更改
- UX 细节或边缘情况更改

更新 `TECH.md` 时：

- 实现方法更改
- 架构边界移动
- 风险、依赖项或发布细节更改
- 测试或验证计划更改

提交的规范应描述实际发布的特性，而不仅仅是初始意图。在实用的情况下，将规范更新与相关的代码更改保持在同一 PR 中。

### 6. 根据规范验证行为

在考虑工作完成之前，确保验证与规范对应。优先使用直接验证产品行为的测试和工件：

- 遵循仓库本地测试约定的单元测试和回归覆盖率
- 关键用户流程的集成测试
- 适当时使用 Loom 漫游或等效功能演示
- 对于 UI 为主的工作，当有用时使用截图或视频

## 最佳实践

- 首先要务实。
- 编写规范以提高代理的输入质量，而不是作为仪式。
- 保持产品规范行为导向和轻实现。
- 保持技术规范实现导向，并基于当前代码库模式。
- 当规范引用相关代码片段时，如果可能，在文件引用中包含检查的提交 SHA，并将引用链接到精确的 GitHub `blob/<sha>/...#Lx-Ly` 行。
- 使用审查时间来验证规范和行为，而不是过度关注代码风格的细微差别。
