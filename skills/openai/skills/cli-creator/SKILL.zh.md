# CLI 创建器

创建一个真实的 CLI，使未来的 Codex 线程可以从任意工作目录通过命令名运行。

此技能适用于持久化工具，而非一次性脚本。如果当前仓库中的简短脚本能解决该任务，请直接在该仓库中编写脚本。

## 开始

指定目标工具的名称、来源，以及它应执行的首批实际任务：

- 来源：API 文档、OpenAPI JSON、SDK 文档、curl 示例、浏览器应用、现有内部脚本、文章或可用的 shell 历史记录。
- 任务：字面上的读取/写入操作，例如 `list drafts`（列出草稿）、`download failed job logs`（下载失败任务的日志）、`search messages`（搜索消息）、`upload media`（上传媒体文件）、`read queue schedule`（读取队列调度）。
- 安装名称：简短的二进制文件名，例如 `ci-logs`、`slack-cli`、`sentry-cli` 或 `buildkite-logs`。

当用户希望创建个人工具且未指定仓库时，建议在 `~/code/clis/<tool-name>` 下创建新文件夹。

在生成脚手架代码之前，检查提议的命令是否已存在：

```bash
command -v <tool-name> || true
```

如果已存在，请选择更清晰的安装名称或询问用户。

## 选择运行时环境

在选择之前，请检查用户机器和源材料：

```bash
command -v cargo rustc node pnpm npm python3 uv || true
```

然后选择最不让人意外的工具链：

- 默认使用 **Rust** 构建 Codex 应从任意仓库运行的持久化 CLI：单一快速二进制文件，强大的参数解析，良好的 JSON 处理，易于复制/安装到 `~/.local/bin`。
- 当官方 SDK、认证助手、浏览器自动化库或现有仓库工具是使 CLI 更优的原因时，使用 **TypeScript/Node**。
- 当源涉及数据科学、本地文件转换、Jupyter 笔记本、SQLite/CSV/JSON 分析或可安装为持久化命令的 Python 密集型管理工具时，使用 **Python**。

除非实质性改进 CLI，否则不要选择增加设置摩擦的语言。如果最佳语言未安装，经用户批准安装缺失的工具链，或选择次优的已安装选项。

在生成脚手架代码之前，用一句话说明选择结果，包括原因和你找到的已安装工具链。

## 命令契约

在编码之前，在聊天中勾勒出命令界面。包括二进制文件名、发现命令、解析或 ID 查找命令、读取命令、写入命令、原始逃生舱、认证/配置选择以及 PATH/安装命令。

在设计命令界面时，请阅读 [references/agent-cli-patterns.md](references/agent-cli-patterns.md) 以了解预期的可组合 CLI 结构。

构建此界面：

- `tool-name --help` 显示所有主要功能。
- `tool-name --json doctor` 验证配置、认证、版本、端点可达性以及缺失的设置。
- `tool-name init ...` 在仅通过环境变量认证很麻烦时存储本地配置。
- 发现命令查找账户、项目、工作区、团队、队列、频道、仓库、仪表板或其他顶级容器。
- 解析命令将名称、URL、slug、永久链接、客户输入或构建链接转换为稳定的 ID，以便后续命令无需重复广泛搜索。
- 读取命令获取确切对象并列出/搜索集合。分页列表支持有限的 `--limit`、游标、偏移量或明确记录的默认值。
- 写入命令每个执行一个命定的操作：创建、更新、删除、上传、调度、重试、评论、草稿。它们接受最窄的稳定资源 ID，在服务允许的情况下支持先进行 `--dry-run`、`draft` 或 `preview`，并且不隐藏在不明确命令（如 `fix`、`debug` 或 `auto`）中。
- `--json` 返回稳定的机器可读输出。
- 存在原始逃生舱：`request`、`tool-call`、`api` 或最诚实的名称。

不要仅暴露通用的 `request` 命令。为重复性任务提供 Codex 的高级动词。

在 CLI README 或等效文档中记录 JSON 策略：API 直通还是 CLI 封装，成功形状，错误形状，以及每个命令家族的一个示例。在 `--json` 模式下，错误必须是机器可读的，且不得包含凭证。

## 认证和配置

首先支持常规路径，按以下优先级顺序：

1. 使用服务标准名称的环境变量，例如 `GITHUB_TOKEN`。
2. 位于 `~/.<tool-name>/config.toml` 或其他简单记录路径下的用户配置。
3. `--api-key` 或特定工具令牌标志仅用于明确的一次性测试。优先使用环境变量/配置进行正常使用，因为标志可能泄露到 shell 历史记录或进程列表中。

切勿打印完整令牌。`doctor --json` 应说明令牌是否可用，认证源类别（`flag`、`env`、`config`、提供商默认或缺失），以及缺失的设置步骤。

如果 CLI 可以无需网络或认证运行，请在 `doctor --json` 中明确说明：报告 fixture/离线模式、是否找到 fixture 数据，以及该模式是否不需要认证。

对于源自 DevTools curl 的内部 Web 应用程序，在实施之前创建净化后的端点笔记：资源名称、方法/路径、必需头、认证机制、CSRF 行为、请求体、响应 ID 字段、分页、错误，以及一个脱敏的示例响应。切勿提交复制的 cookie、bearer 令牌、客户机密或完整生产负载。

使用截图推断工作流程、UI 词汇、字段和确认点。除非截图与网络请求、导出、文档页面或 fixture 配对，否则不要将截图视为 API 证据。

## 构建工作流

1. 阅读来源以清点资源、认证、分页、ID、媒体/文件流程、速率限制和危险的写入操作。如果文档暴露 OpenAPI，在命名命令之前下载或检查它。
2. 在聊天中勾勒出命令列表。保持名称简短且对 shell 友好。
3. 使用 README 或等效的面向仓库的说明生成 CLI 脚手架。
4. 实现 `doctor`、发现、解析、读取命令，如果请求则实现一个狭窄的草稿或干运行写入路径，以及原始逃生舱。
5. 将 CLI 安装到 PATH，使 `tool-name ...` 在源文件夹外也能工作。
6. 从另一个仓库或 `/tmp` 进行冒烟测试，而不仅仅是使用 `cargo run` 或包管理器包装器。运行 `command -v <tool-name>`、`<tool-name> --help` 和 `<tool-name> --json doctor`。
7. 运行格式化、类型检查/构建、请求构建器、分页/请求体构建器、无认证 `doctor`、帮助输出以及至少一个 fixture、干运行或实时只读 API 调用的单元测试。

如果需要实时写入以获得信心，请先询问并确保它是可逆的或仅草稿。

当来源是现有脚本或 shell 历史记录时，将有效的调用拆分为实际阶段：设置、发现、下载/导出、转换/索引、草稿、上传、轮询、实时写入。保留用户已经依赖的标志、路径和环境变量，然后用稳定的 ID、有界的 JSON 和文件输出包装可重复阶段。

对于原始逃生舱，首先支持只读调用。除非用户请求特定的写入，否则不要对实时服务运行原始非 GET/HEAD 请求。

对于媒体、工件或预签名上传流程，单独测试每个阶段：创建上传、传输字节、轮询/读取处理状态，然后附加或引用生成的 ID。

对于基于 fixture 的原型，将 fixture 保留在可预测的项目路径中，并使 CLI 在安装后能定位它们。从 `/tmp` 进行冒烟测试，以捕获仅在源文件夹内工作的二进制文件。

对于面向日志的 CLI，将确定性片段提取与模型解释分开。优先选择发出文件名、行号或字节范围、匹配规则和简短摘录的命令。

## Rust 默认设置

在 Rust 中构建时，使用成熟的 crate 而非自定义解析器：

- `clap` 用于命令和帮助
- `reqwest` 用于 HTTP
- `serde` / `serde_json` 用于负载
- `toml` 用于小型配置文件
- `anyhow` 用于 CLI 风格的错误上下文

添加一个 `Makefile` 目标，例如 `make install-local`，它构建 release 并将二进制文件安装到 `~/.local/bin`。

## TypeScript/Node 默认设置

在 TypeScript/Node 中构建时，保持 CLI 可安装为普通命令：

- `commander` 或 `cac` 用于命令和帮助
- 原生 `fetch`、官方 SDK 或用户现有的 HTTP 助手用于 API 调用
- 仅在外部负载验证防止真实损坏时使用 `zod`
- `package.json` 中的 `bin` 条目用于安装命令
- 使用仓库现有惯例的 `tsup`、`tsx` 或 `tsc`

添加安装路径，例如 `pnpm install`、`pnpm build` 和 `pnpm link --global`，或者安装小包装器到 `~/.local/bin` 的 `Makefile` 目标。

## Python 默认设置

在 Python 中构建时，除非工作流需要更多，否则优先选择无聊的标准库组件：

- `argparse` 用于命令和帮助，或者当子命令会显得杂乱时使用 `typer`
- `urllib.request` / `urllib.parse`、`requests` 或 `httpx` 用于 HTTP，匹配已安装或附近已使用的
- `json`、`csv`、`sqlite3`、`pathlib` 和 `subprocess` 用于本地文件、导出、数据库和现有脚本
- `pyproject.toml` 控制台脚本或小可执行包装器用于安装命令
- 仅当确实需要依赖项时使用 `uv` 或 virtualenv

添加一个 `Makefile` 目标，例如 `make install-local`，它将命令安装到 PATH 并记录它是否依赖于 `uv`、virtualenv 或仅系统 Python。

## 伴随技能

在 CLI 工作后，为其创建或更新一个小技能。如果 `$skill-creator` 可用，则使用它。除非用户指定仓库本地的 `.codex/skills/...` 路径或其他技能仓库，否则为个人伴随技能使用 `$CODEX_HOME/skills/<tool-name>/SKILL.md`。

按照未来 Codex 线程使用 CLI 的顺序编写伴随技能，而不是作为所有功能的导览。解释：

- 如何验证安装命令存在。
- 首先运行哪个命令。
- 如何配置认证。
- 哪个发现命令查找常见 ID。
- 安全的读取路径。
- 预期的草稿/写入路径。
- 原始逃生舱。
- 未经明确用户批准不要做什么。
- 三个可复制粘贴的命令示例。

将 API 参考细节保留在 CLI 文档或技能参考文件中。将技能集中在顺序、安全性和未来 Codex 线程应实际运行的示例上。
