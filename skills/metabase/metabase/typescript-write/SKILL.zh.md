## 不使用 `any` — 严格规则

- **新代码不得引入 `any`，显式或隐式。** 没有 `any` 注解，没有 `as any` / `as unknown as`，没有推断为 `any` 的未类型化参数或返回值，没有隐式为 `any` 的解构或数组/对象字面量。
- **未类型化的第三方/边界值** 必须在边界处进行类型化（一个已声明的类型、`unknown` + 类型守卫，或一个小型类型化包装器）— 永远不要让 `any` 向内传播。
- **强制类型验证。** 在完成 TS/TSX 修改之前，运行 `bun run type-check-pure`。如果 TypeScript LSP 工具可用，也使用悬浮和转到定义检查更改的符号；否则跳过 LSP 检查。

## 类型收紧

- **避免类型转换和松散的 `unknown`** — 修复签名而不是转换。
- **如果一个函数只需要宽泛对象的一个字段，接受该字段** — 而不是宽泛对象。一旦签名正确，转换通常就会消失。
- **在需要类型转换之前，优先使用 `Partial<T>`、`Pick<T, K>`、`Record<K, V>` 和泛型。**
- **匹配字典键与数据。** 当键已知时，使用有限键联合。开放字典可以使用索引签名、`Record<string, T>` 或 `Map`；索引签名仍然约束值，并且将它们的拼写更改为 `Record<string, T>` 并不会使缺失键的访问变得安全。
- **在值不变且调用者知道类型时，优先使 props/组件泛型** (`<T>`)。
- **优先使用 `unknown` 而不是松散的类型化**，并在使用前进行窄化 — 一个 `unknown` 值在使用点强制一个守卫。
- **对象字面量的 `satisfies`**，必须符合而不扩展（配置对象、查找映射、区分联合字面量）— 比 `: T`（扩展）或 `as T`（不安全）更好。
- **避免非空断言 (`!`)**。优先使用守卫、提前返回或 `?.`。仅在非空性可证明为真且本地化时使用 `!`，并附带注释。
- **守卫可能缺失的索引查找。** 数组和字典即使推断类型省略了它，也可能返回 `undefined`。使用保留键/值关系的迭代形式，并且仅在运行时键已知属于声明类型时断言 `keyof`。
- **没有冗余的运行时强制转换** — 不要将已类型化的值包装在 `Number()` / `String()` / `Boolean()` 中。
- **类型守卫属于 `frontend/src/metabase-types/guards/`**。不要在本地重新定义它们。
- **你无法避免的转换需要一个真实的理由注释。** `metabase/no-unjustified-type-casts` 规则接受任何前置注释 — 说明转换为什么是安全的实际原因。永远不要写遗留的 `// Unjustified type cast. FIXME` 占位符；它只存在于预规则之前的转换中，复制它会让 linter 漏过不合理的转换。如果你无法说明为什么转换是正确的，转换就是错误的 — 修复类型。
- **保持不可避免的断言局部。** 当这使得其不变性更容易强制执行时，将重复或复杂的断言隔离在背后一个辅助函数中。测试非平凡的运行时假设，它证明了这一点；一个平凡的断言不需要自动需要一个新的辅助函数或测试。不要因为要消除实现错误而削弱公共签名。

## 类型建模

- **重用现有类型；不要重新声明它们。** 使用来自 `metabase-types/api` 的规范 ID 和领域实体类型（`FieldId`、`TableId`、`ConcreteTableId`、`SchemaName`、…）以及通过它们键入数据结构（`new Map<ConcreteTableId, …>()`）。不要复制生成的/API 类型 — 组合或派生（`Pick`、`Omit`、索引访问 `SomeType["field"]`、`ReturnType`）。
- **泛型必须使实现者能够保持承诺。** 调用者选择的 `get<T>(): T` 不得掩盖对外部数据的未检查断言。返回 `unknown` 并验证，或接受一个验证器来建立 `T`。例如 `function empty<T>(): T[] { return []; }` 是有效的；判断实现，而不是 `T` 在签名中出现的频率。
- **优先使用诚实的类型而不是虚假的精度。** 当泛型表达真实的关联时使用它们。如果一个复杂类型无法准确建模行为，选择一个更简单的类型或 `unknown` 与窄化，而不是断言一个不支持的保证。
- **建模实际的数据契约；保持类型狭窄。** 可选的 `field?: T` 用于可能缺失的键，`field: T | undefined` 仅当键始终存在但值可能为 `undefined` 时，`| null` 用于显式 API null。优先使用领域联合而不是宽泛的 `string` / `number` / 松散的 `Record`。
- **定义或细化类型时参考 API 实现** 确保它们与实际数据结构匹配。在考虑类型转换时，首先考虑类型是否应该细化以匹配实际数据结构。
- **选项性必须反映缺失。** 保持必需字段必需，可选字段可选。当应用程序有有意义的默认值时，正常化输入，而不仅仅是为了消除类型错误。在 API 类型中保留实际的线形形状。
- **在建模内部状态时，将相关的缺失表示在一起。** 如果几个字段一起存在或消失，考虑一个可空的包含对象或一个区分联合。除非数据实际上有该形状，否则不要重塑原始 API 声明。
- **在设计格式时优先使用显式的特殊状态。** 使用可空性或命名联合变体来表示如 `-1` 这样的哨兵值隐藏意义。除非行为被故意改变，否则保留已建立的协议哨兵值，或在显式边界处正常化它们。
- **区分联合用于变体状态，并进行穷尽检查。** 将“N 种形状之一”建模为一个带有字面量区分的联合，而不是一组可选字段，并使用 ts-pattern 的 `.exhaustive()` 穷尽它，以便添加一个变体成为编译错误：
  ```ts
  import { match } from "ts-pattern";

  const result = match(status)
    .with({ type: "loading" }, () => <Spinner />)
    .with({ type: "error", error: P.select() }, (error) => <Error message={error.message} />)
    .with({ type: "success", data: P.select() }, (data) => <Content data={data} />)
    .exhaustive(); // 编译时保证所有情况都处理了
  ```
- **从常量派生联合类型** (`as const` + `typeof`/`keyof`)，以便类型和值不会漂移。
- **`readonly` / 不可变性，在不需要变异时** — 组件 props、共享常量、导出配置和未变异参数。对于你不变异的输入，优先使用 `readonly T[]` / `ReadonlyArray<T>`。变异调用者拥有数据的函数应明确这种行为。
- **在实用情况下构建完整、良好类型的对象。** 当对象表达式可以避免部分初始化状态或断言时，优先使用对象表达式。增量构建是清晰的，并维护了类型的不变性时，是允许的。
- **将 `metabase-lib` 不透明类型视为黑盒。** 使用 `metabase-lib` 函数来处理类型，例如 `Lib.Query`，而不是将其转换为内部表示。
- **显式类型化异步和错误状态**（一个区分联合或数据层的类型化结果）— 永远不要让加载/错误/空隐式。

## 函数签名

- **在改进稳定性和清晰度时使公共契约显式。** 在共享边界处注释参数和返回类型，当有用时；让本地值推断。使用 `satisfies` 或注释，当一个声明需要显式形状检查时。
- **接受操作支持的输入并返回最精确诚实的结果。** 在函数内部窄化避免的不确定性，但保留有意义的可空性和联合变体在其返回类型中。
- **使用命名选项，当位置参数容易混淆时。** 具有相同类型的连续参数是一个有用的警告信号，而不是自动要求重写一个清晰的 API。
- **使用 `async`/`await`，当它澄清控制流或错误处理时。** 直接返回现有承诺也是有效的；单独的 Promise 返回类型并不需要添加 `async`。

## 可空和未定义

- **在源处窄化。** 如果一个值仅在边缘情况下是可选的，不要通过每一层传递 `undefined` — 在生产者处守卫。
- **可选值的合理默认值。** 使用 `?.` 和 `??` 在消费者处。
- **当操作需要存在值时，窄化可空列表元素。** 使用类型守卫过滤，当缺失条目应被丢弃时；保留它们，当它们的缺失或位置有意义时。
- **避免非严格的空比较** (`X != null`)，当 `X` 永远不可能为 `null` 时 — 使用严格的检查或窄化类型。在必要时使用 `checkNotNull`。
- **检查 API 实现的实际可空性。** 找到 API 端点实现并检查该字段是否实际上可以为空。

## 命名

- **名称描述实体，而不是机制。** 名称必须反映值的内容。
- **使用领域词汇，并在有用时包含单位** (`timeoutMs`、`widthPx`、`temperatureC`)。当 `Info`、`Data` 或 `Entity` 模糊意义时，优先使用更具体的名称，同时保持已建立的术语，当它清晰时。
- **对兄弟概念进行对齐**：在相关的 API 中保持动词约定一致。
- **不要使用编码实现历史的名称** 而不是当前意义。后缀如 `Base`、`New`、`Old`、`Initial` 需要有真实的语义区分，否则删除它们。
- **避免神秘的标识符** (`v`、`n`、`$n`) 用于领域值；只有在小型的传统上下文中短名称是合适的（循环索引 `i`、坐标 `x`/`y`、泛型参数 `T`/`K`/`V`）。

## 代码结构和组织

- **优先重用而不是重复**。代码库已经有许多实用函数 — 利用它们。如果你引入了重复的逻辑，将其提取到一个共享实用工具中。
- **泛型辅助函数不属于功能文件夹**。提升到一个共享实用工具。
- **保持函数小而单一目的**。一个 100+ 行的函数很难审查 — 分割成专注命名的辅助函数，每个函数有一个责任和最小的依赖表面。必要时，用单元测试覆盖。
- **将不同的复杂 JSX 提取到命名的组件中**。通过重用、耦合、可测试性和可读性选择同文件与分离文件。

## 注释

- **默认情况下没有注释**。命名良好的标识符承载了 `what`。
- **注释应该是简洁的**。只有在 `why` 不明显时才添加一个简短的、简洁的注释：一个工作绕过、一个隐藏的不变量、一个微妙的排序约束、一个巧妙的简化。永远不要记录实际实现，专注于意图和 `why`。
