# 技能评估

对照官方规范和从 17 个以上官方示例中推导出的模式，评估代理技能。

---

## 核心理念

### 什么是技能？

技能**不是**教程。技能是一种**知识外化机制**。

传统 AI 知识锁在模型参数中。要教授新功能：
```
传统方式：收集数据 → GPU 集群 → 训练 → 部署新版本
成本：$10,000 - $1,000,000+
时间：数周至数月
```

技能改变了这一切：
```
技能：编辑 SKILL.md → 保存 → 在下次调用时生效
成本：$0
时间：即时
```

这是从“训练 AI”到“教育 AI”的范式转变——就像一个无需训练的热插拔 LoRA 插件。你用自然语言编辑 Markdown 文件，模型的行为就会改变。

### 核心公式

> **好的技能 = 专家知识 − Claude 已知知识**

技能的价值由其**知识增量**衡量——即它提供的内容与模型已知内容之间的差距。

- **专家知识**：决策树、权衡、边缘情况、反模式、特定领域的思维框架——这些需要数年经验才能积累
- **Claude 已知知识**：基本概念、标准库使用、常见编程模式、一般最佳实践

当技能解释“PDF 是什么”或“如何编写 for 循环”时，它只是在压缩 Claude 已知的知识。这是**令牌浪费**——上下文窗口是一个公共资源，与系统提示、对话历史、其他技能和用户请求共享。

### 工具与技能的区别

| 概念 | 本质 | 功能 | 示例 |
|------|------|------|------|
| **工具** | 模型**能**做什么 | 执行操作 | bash, read_file, write_file, WebSearch |
| **技能** | 模型**知道**如何做 | 指导决策 | PDF 处理, MCP 构建, 前端设计 |

工具定义能力边界——没有 bash 工具，模型无法执行命令。
技能注入知识——没有前端设计技能，模型会产生通用 UI。

**公式**：
```
通用代理 + 优秀技能 = 领域专家代理
```

相同的 Claude 模型，加载不同的技能，就成为不同的专家。

### 技能中的三种知识类型

评估时，对每个部分进行分类：

| 类型 | 定义 | 处理方式 |
|------|------|----------|
| **专家** | Claude 真正不知道的知识 | 必须保留——这是技能的价值 |
| **激活** | Claude 知道但可能想不到的知识 | 如有必要保留——作为提醒 |
| **冗余** | Claude 肯定知道的知识 | 应删除——浪费令牌 |

技能设计的艺术在于最大化专家内容，谨慎使用激活内容，无情地消除冗余内容。

## 评估维度（总分 120 分）

### D1：知识增量（20 分）——核心维度

最重要的维度。技能是否添加了真正的专家知识？

| 分数 | 标准 |
|------|------|
| 0-5 | 解释 Claude 已知的基本知识（什么是 X，如何编写代码，标准库教程） |
| 6-10 | 混合：部分专家知识被明显内容稀释 |
| 11-15 | 大部分是专家知识，冗余最小 |
| 16-20 | 纯知识增量——每个段落都值得它的令牌 |

**红旗**（即时分数 ≤5）：
- “什么是[基本概念]”部分
- 标准操作的逐步教程
- 解释如何使用常用库
- 通用最佳实践（“编写干净的代码”，“处理错误”）
- 行业标准术语的定义

**绿旗**（高知识增量指标）：
- 非明显选择的决策树（“当 X 失败时，尝试 Y 因为 Z”）
- 只有专家才知道的权衡（“A 更快但 B 处理边缘情况 C”）
- 来自真实世界经验的边缘情况
- “永远不要做 X 因为[非明显原因]”
- 特定领域的思维框架

**评估问题**：
1. 对每个部分提问：“Claude 是否知道这个？”
2. 如果解释某事，提问：“这是在向 Claude 解释还是在为 Claude 解释？”
3. 统计专家、激活和冗余段落数量

---

### D2：思维模式 + 合适的流程（15 分）

技能是否传递了专家**思维模式**以及**必要的特定领域流程**？

专家和新手之间的区别不在于“知道如何操作”，而在于“如何思考问题”。但当 Claude 缺乏特定领域的流程知识时，仅靠思维模式是不够的。

**关键区别**：
| 类型 | 示例 | 价值 |
|------|------|------|
| **思维模式** | “设计之前，问：什么让它令人难忘？” | 高——塑造决策 |
| **特定领域流程** | “OOXML 工作流：解包 → 编辑 XML → 验证 → 打包” | 高——Claude 可能不知道 |
| **通用流程** | “步骤 1：打开文件，步骤 2：编辑，步骤 3：保存” | 低——Claude 已知 |

| 分数 | 标准 |
|------|------|
| 0-3 | 只有 Claude 已知的通用流程 |
| 4-7 | 有特定领域流程但缺乏思维框架 |
| 8-11 | 良好平衡：思维模式 + 特定领域工作流 |
| 12-15 | 专家级：塑造思维 AND 提供 Claude 不知道的知识 |

**有价值的流程**：
- Claude 未受训练的工作流（新工具、专有系统）
- 非明显的正确顺序（例如，“验证必须在打包之前，而不是之后”）
- 容易遗漏的关键步骤（例如，“编辑后必须重新计算公式”）
- 特定领域的序列（例如，MCP 服务器的四阶段开发流程）

**冗余流程**：
- 通用文件操作（打开、读取、写入、保存）
- 标准编程模式（循环、条件、错误处理）
- 文档化良好的常用库使用

**专家思维模式看起来像**：
```markdown
在[操作]之前，问自己：
- **目的**：这个问题解决了什么？谁使用它？
- **约束**：隐藏的有哪些要求？
- **差异化**：什么让这个解决方案令人难忘？
```

**有价值的特定领域流程看起来像**：
```markdown
### 审阅工作流（Claude 不知道这个顺序）
1. 转换为 Markdown：`pandoc --track-changes=all`
2. 将文本映射到 XML：grep 文档.xml 中的文本
3. 批量（3-10 条）实现更改
4. 打包并验证：检查所有更改是否已应用
```

**冗余通用流程看起来像**：
```markdown
步骤 1：打开文件
步骤 2：找到部分
步骤 3：进行更改
步骤 4：保存并测试
```

**测试**：
1. 它是否告诉 Claude 要思考什么？（思维模式）
2. 它是否告诉 Claude 如何做它不知道的事情？（特定领域流程）

一个好的技能在需要时提供两者。

### D3：反模式质量（15 分）

技能是否有有效的“永远不要”列表？

**为什么这很重要**：专家知识的一半是知道什么**绝对不能**做。高级设计师看到白色背景上的紫色渐变就会本能地皱眉——“太 AI 生成”。这种“绝对不要”的直觉来自踩过无数地雷。

Claude 还没有踩过这些地雷。它不知道 Inter 字体被过度使用，不知道紫色渐变是 AI 生成内容的标志。好的技能必须明确声明这些“绝对不要”。

| 分数 | 标准 |
|------|------|
| 0-3 | 未提及反模式 |
| 4-7 | 通用警告（“避免错误”，“小心”，“考虑边缘情况”） |
| 8-11 | 具体的“永远不要”列表，附带一些解释 |
| 12-15 | 专家级反模式，附带原因——只有经验才能教 |

**专家反模式**（具体 + 原因）：
```markdown
永远不要使用通用的 AI 生成美学，例如：
- 过度使用的字体家族（Inter, Roboto, Arial）
- 陈词滥调的配色方案（尤其是白色背景上的紫色渐变）
- 可预测的布局和组件模式
- 所有内容都设置默认边框半径
```

**薄弱的反模式**（模糊，无原因）：
```markdown
避免犯错误。
小心边缘情况。
不要编写糟糕的代码。
```

**测试**：专家会读反模式列表并说“是的，我惨痛地学到了这个”吗？还是会说“这很明显，每个人都知道”？

### D4：规范合规性——尤其是描述（15 分）

技能是否遵循官方格式要求？**特别关注描述质量。**

| 分数 | 标准 |
|------|------|
| 0-5 | 缺少 frontmatter 或格式无效 |
| 6-10 | 有 frontmatter 但描述模糊或不完整 |
| 11-13 | 有效 frontmatter，描述有 WHAT 但弱于 WHEN |
| 14-15 | 完美：全面的描述，包含 WHAT, WHEN 和触发关键词 |

**frontmatter 要求**：
- `name`：小写，字母数字 + 连字符，≤64 个字符
- `description`：**最关键的字段**——决定技能是否会被使用

---

**为什么描述是最重要的字段**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  技能激活流程                                                      │
│                                                                    │
│  用户请求 → 代理看到所有技能描述 → 决定哪个（只有描述，不是正文！） | 
│                 激活                                                   │
│                                                                    │
│  如果描述不匹配 → 技能永远不被加载                                  │
│  如果描述模糊 → 技能可能不会在应该时触发                          │
│  如果描述缺少关键词 → 技能对代理不可见                             │
└─────────────────────────────────────────────────────────────────────┘
```

**残酷的真相**：一个内容完美但描述糟糕的技能是**无用的**——它永远不会被激活。描述是**唯一的机会**告诉代理“在这种情况下使用我。”

---

**描述必须回答三个问题**：

1. **WHAT**：这个技能做什么？（功能）
2. **WHEN**：在什么情况下应该使用它？（触发场景）
3. **KEYWORDS**：什么术语应该触发这个技能？（可搜索术语）

**优秀的描述**（包含所有三个元素）：
```yaml
description: "全面的文档创建、编辑和分析，支持跟踪更改、评论、格式保留和文本提取。
当 Claude 需要处理专业文档（.docx 文件）时：
(1) 创建新文档，
(2) 修改或编辑内容，
(3) 处理跟踪更改，
(4) 添加评论，或任何其他文档任务"
```

分析：
- WHAT：创建、编辑、分析、跟踪更改、评论
- WHEN：当 Claude 需要处理...时：“(1)... (2)... (3)..."
- KEYWORDS：.docx 文件、跟踪更改、专业文档

**糟糕的描述**（缺少元素）：
```yaml
description: "处理文档相关功能"
```

问题：
- WHAT：模糊（“文档相关功能”——具体是什么？）
- WHEN：缺失（代理何时应该使用它？）
- KEYWORDS：缺失（没有“.docx”，没有特定场景）

**另一个糟糕的示例**：
```yaml
description: "一个对各种任务有帮助的技能"
```

这毫无用处——代理不知道何时激活它。

---

**描述质量检查清单**：
- [ ] 列出具体功能（不只是“帮助做 X”）
- [ ] 包含明确的触发场景（“使用时...”，“当用户请求...”）
- [ ] 包含可搜索关键词（文件扩展名、领域术语、动作动词）
- [ ] 具体到代理确切知道何时使用它
- [ ] 包含必须使用此技能的场景（而不仅仅是“可以”使用）

### D5：渐进式披露（15 分）

技能是否实现了适当的内容分层？

技能加载有三个层级：
```
层级 1：元数据（始终在内存中）
         只有名称 + 描述
         每个技能 ~100 令牌

层级 2：SKILL.md 正文（触发后加载）
         详细指南、代码示例、决策树
         理想：< 500 行

层级 3：资源（按需加载）
         scripts/, references/, assets/
         无限制
```

| 分数 | 标准 |
|------|------|
| 0-5 | 所有内容都堆在 SKILL.md (>500 行，无结构) |
| 6-10 | 有参考但加载时机不明确 |
| 11-13 | 良好分层，有 MANDATORY 触发器 |
| 14-15 | 完美：决策树 + 明确触发器 + “不要加载”指导 |

**对于有参考目录的技能**，检查加载触发器质量：

| 触发器质量 | 特征 |
|------------|------|
| 差 | 参考在末尾列出，无加载指导 |
| 一般 | 一些触发器但未嵌入工作流 |
| 良好 | 工作流步骤中的 MANDATORY 触发器 |
| 优秀 | 场景检测 + 条件触发器 + “不要加载” |

**加载问题**：
```
加载太少 ◄─────────────────────────────────► 加载太多
- 参考未使用                    - 浪费上下文空间
- 代理不知道何时加载          - 稀释关键内容的无关信息
- 知识存在但从未访问          - 不必要的令牌开销
```

**好的加载触发器**（嵌入在工作流中）：
```markdown
### 创建新文档

**MANDATORY - 读取整个文件**：在继续之前，你必须完全读取
[`docx-js.md`](docx-js.md) (~500 行) 从头到尾。
**永远不要设置任何范围限制**当读取此文件。

**不要加载** `ooxml.md` 或 `redlining.md` 用于此任务。
```

**糟糕的加载触发器**（只是列出）：
```markdown
## 参考
- docx-js.md - 用于创建文档
- ooxml.md - 用于编辑
- redlining.md - 用于跟踪更改
```

**对于简单技能**（无参考，<100 行）：根据简洁性和自包含性评分。

### D6：自由校准（15 分）

任务的脆弱性是否适合相应的具体程度？

不同的任务需要不同级别的约束。这是关于匹配自由度与脆弱性。

| 分数 | 标准 |
|------|------|
| 0-5 | 严重不匹配（对创意任务使用僵化脚本，对易碎操作使用模糊描述） |
| 6-10 | 部分适当，存在一些不匹配 |
| 11-13 | 大多数场景的良好校准 |
| 14-15 | 完美的自由校准 |

**自由度谱**：

| 任务类型 | 应该有 | 原因 | 示例技能 |
|-----------|--------|------|----------|
| 创意/设计 | 高自由度 | 多种有效方法，差异化是价值 | frontend-design |
| 代码审查 | 中等自由度 | 原则存在但需要判断 | code-review |
| 文件格式操作 | 低自由度 | 一个错误字节就会损坏文件，一致性至关重要 | docx, xlsx, pdf |

**高自由度**（基于文本的指令）：
```markdown
坚持大胆的美学方向。选择一个极端：残酷极简，
极繁混乱，复古未来，有机自然...
```

**中等自由度**（伪代码或参数化）：
```markdown
审查优先级：
1. 安全漏洞（必须修复）
2. 逻辑错误（必须修复）
3. 性能问题（应该修复）
4. 可维护性（可选）
```

**低自由度**（具体脚本，精确步骤）：
```markdown
**MANDATORY**：使用 `scripts/create-doc.py` 中的确切脚本
参数：--title "X" --author "Y"
不要修改脚本。
```

**测试**：如果代理犯错误，后果是什么？
- 高后果 → 低自由度
- 低后果 → 高自由度

### D7：模式识别（10 分）

技能是否遵循已建立的官方模式？

通过分析 17 个官方技能，我们确定了 5 个主要设计模式：

| 模式 | ~行数 | 主要特征 | 示例 | 使用场景 |
|------|-------|----------|------|----------|
| **思维模式** | ~50 | 思维 > 技术，强NEVER列表，高自由度 | frontend-design | 需要品味和创造力的任务 |
| **导航** | ~30 | 最小SKILL.md，路由到子文件 | internal-comms | 多个明确的场景 |
| **哲学** | ~150 | 两步：哲学 → 表达，强调工艺 | canvas-design | 艺术/创作需要原创性的任务 |
| **流程** | ~200 | 分阶段工作流，检查点，中等自由度 | mcp-builder | 复杂的多步骤项目 |
| **工具** | ~300 | 决策树，代码示例，低自由度 | docx, pdf, xlsx | 对特定格式进行精确操作 |

| 分数 | 标准 |
|------|------|
| 0-3 | 无明显模式，结构混乱 |
| 4-6 | 部分遵循模式但有显著偏差 |
| 7-8 | 模式清晰但有轻微偏差 |
| 9-10 | 精妙地应用了合适的模式 |

**模式选择指南**：

| 任务特征 | 推荐模式 |
|----------|----------|
| 需要品味和创造力 | 思维模式 (~50行) |
| 需要原创性和工艺质量 | 哲学 (~150行) |
| 有多个明确的子场景 | 导航 (~30行) |
| 复杂的多步骤项目 | 流程 (~200行) |
| 对特定格式进行精确操作 | 工具 (~300行) |

### D8: 实际可用性 (15分)

代理是否能够有效地使用这项技能？

| 分数 | 标准 |
|------|------|
| 0-5 | 混乱、不完整、矛盾或未经测试的指导 |
| 6-10 | 可用但有明显的缺失 |
| 11-13 | 对常见情况有清晰的指导 |
| 14-15 | 全面覆盖包括边缘情况和错误处理 |

**检查**：
- **决策树**：对于多路径场景，是否有清晰的指导说明选择哪条路径？
- **代码示例**：它们是否真的能工作？还是伪代码会出错？
- **错误处理**：如果主要方法失败怎么办？是否提供了备用方案？
- **边缘情况**：是否涵盖了不常见但现实的场景？
- **可操作性**：代理是否能立即行动，还是需要自己弄清楚？

**良好的可用性**（决策树 + 备用方案）：
```markdown
| 任务 | 主要工具 | 备用方案 | 使用备用方案的场景 |
|------|----------|----------|-------------------|
| 读取文本 | pdftotext | PyMuPDF | 需要布局信息 |
| 提取表格 | camelot-py | tabula-py | camelot失败 |

**常见问题**：
- 扫描的PDF：pdftotext返回空白 → 先使用OCR
- 加密的PDF：权限错误 → 使用PyMuPDF并输入密码
```

**较差的可用性**（模糊）：
```markdown
使用适当的工具进行PDF处理。
正确处理错误。
考虑边缘情况。
```

## 评估时绝对不要做

- **绝对不要**仅仅因为看起来专业或格式良好就给高分
- **绝对不要**忽视token浪费 — 每个冗余段落都应导致扣分
- **绝对不要**被长度所迷惑 — 43行的技能可能优于500行的技能
- **绝对不要**跳过在脑海中测试决策树 — 它们是否真的能引导到正确的选择？
- **绝对不要**原谅用“但它提供了有用的背景”来解释基础知识
- **绝对不要**忽略缺失的反模式 — 如果没有NEVER列表，那是一个重大缺陷
- **绝对不要**假设所有步骤都有价值 — 区分特定领域和通用步骤
- **绝对不要**低估描述字段 — 描述差=技能永远不会被使用
- **绝对不要**将“何时使用”信息只放在正文中 — 代理只会在加载前看到描述

## 评估协议

### 第一步：第一遍扫描 — 知识增量扫描

完整阅读SKILL.md，并对每个部分提问：
> “Claude是否已经知道这个？”

将每个部分标记为：
- **[E] 专家**：Claude确实不知道这个 — 增值
- **[A] 激活**：Claude知道但简短提醒有用 — 可接受
- **[R] 冗余**：Claude肯定知道这个 — 应该删除

计算大致比例：E:A:R
- 好的技能：>70% 专家，<20% 激活，<10% 冗余
- 一般的技能：40-70% 专家，高激活
- 差的技能：<40% 专家，高冗余

### 第二步：结构分析

```
[ ] 检查frontmatter的有效性
[ ] 统计SKILL.md的总行数
[ ] 列出所有参考文件及其大小
[ ] 确定技能遵循的模式
[ ] 检查加载触发器（如果有参考文件）
```

### 第三步：逐维度评分

对每个维度：
1. 找到具体证据（引用相关行）
2. 给出分数并附上一行解释
3. 如果分数低于最大值，记录具体改进建议

### 第四步：计算总分和等级

```
总分 = D1 + D2 + D3 + D4 + D5 + D6 + D7 + D8
最大值 = 120分
```

**等级标准**（百分比）：
| 等级 | 百分比 | 含义 |
|------|--------|------|
| A | 90%+ (108+) | 优秀 — 可投入生产的专家技能 |
| B | 80-89% (96-107) | 良好 — 需要少量改进 |
| C | 70-79% (84-95) | 合格 — 有明确的改进路径 |
| D | 60-69% (72-83) | 不及格 — 存在严重问题 |
| F | <60% (<72) | 差 — 需要根本性重新设计 |

## 常见失败模式

### 模式1：教程

```
症状：解释PDF是什么，Python如何工作，基本库使用
根本原因：作者假设技能应该“教”模型
修复：Claude已经知道这些。删除所有基本解释。
     专注于专家决策、权衡和反模式。
```

### 模式2：堆砌

```
症状：SKILL.md有800多行，包含所有内容
根本原因：没有渐进式披露设计
修复：核心路由和决策树在SKILL.md中（理想<300行）
     详细内容在references/中，按需加载
```

### 模式3：孤儿参考

```
症状：参考目录存在但文件从未加载
根本原因：没有明确的加载触发器
修复：在流程决策点添加“必须读取整个文件”
     添加“不要加载”以防止过载
```

### 模式4：复选框流程

```
症状：步骤1、步骤2、步骤3... 机械流程
根本原因：作者按流程思考，而不是思维框架
修复：转化为“在执行X之前，问自己...”框架
     专注于决策原则，而不是操作序列
```

### 模式5：模糊警告

```
症状：“小心”、“避免错误”、“考虑边缘情况”
根本原因：作者知道可能会出错但没有具体说明
修复：明确的NEVER列表，具体示例和非显而易见的理由
     “绝对不要使用X，因为[具体问题，需要经验才能了解]”
```

### 模式6：隐形技能

```
症状：内容很棒但技能很少被激活
根本原因：描述模糊，缺少关键词，或缺少触发场景
修复：描述必须回答：做什么？何时使用？
     包含触发关键词
     "使用场景..." + 具体场景 + 可搜索术语

示例修复：
BAD: "帮助处理文档任务"
GOOD: "创建、编辑和分析.docx文件。当处理Word文档、跟踪更改或专业文档格式时使用。"
```

### 模式7：错误位置

```
症状：“何时使用此技能”部分在正文中，不在描述中
根本原因：误解三层加载
修复：将所有触发信息移到描述字段
     正文只在触发决策后加载
```

### 模式8：过度设计

```
症状：README.md、CHANGELOG.md、INSTALLATION_GUIDE.md、CONTRIBUTING.md
根本原因：将技能视为软件项目
修复：删除所有辅助文件。只包含代理完成任务所需的内容。
     没有关于技能本身的文档。
```

### 模式9：自由度不匹配

```
症状：对创造性任务使用刚性脚本，对易碎操作使用模糊指导
根本原因：没有考虑任务易碎性
修复：创造性任务 → 高自由度（原则，不是步骤）
     易碎操作 → 低自由度（精确脚本，无参数）
```

## 元问题

在评估任何技能时，始终回到这个基本问题：

> **“该领域的专家看到这个技能，会说：**
> **‘是的，这个技能捕捉了我花了多年时间学到的知识’？”**

如果答案是“是” → 技能具有真正的价值。
如果答案是“否” → 它只是在压缩Claude已经知道的内容。

最好的技能是**压缩的专家大脑** — 它将设计师10年的审美积累压缩成43行，或将文档专家的操作经验压缩成一个200行的决策树。

被压缩的东西必须是Claude没有的。否则，那就是垃圾压缩。

## 自我评估笔记

这个技能（skill-judge）本身应该通过评估：

- **知识增量**：提供Claude自己不会生成的具体评估标准
- **思维模式**：塑造如何思考技能质量，而不仅仅是清单项
- **反模式**：“评估时绝对不要做”部分，包含具体的“绝对不要”
- **规范**：有效的frontmatter和全面的描述
- **逐步披露**：自包含，无需外部参考
- **自由度**：中等自由度适合评估任务
- **模式**：遵循工具模式，包含决策框架
- **可用性**：清晰的协议，报告模板，快速参考

将此技能与自身进行评估，作为校准练习。
