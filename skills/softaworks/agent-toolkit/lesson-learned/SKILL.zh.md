# 经验教训

从实际代码变更中提取具体的、基于事实的软件工程经验教训。这不是讲座——而是一面镜子。向用户展示他们的代码已经证明了什么。

## 开始前

**首先加载原则参考。**

1. 读取 `references/se-principles.md` 以获取原则目录
2. 如果您怀疑变更包含可改进的领域，可以选择性阅读 `references/anti-patterns.md`
3. 确定分析的范围（见第一阶段）

**在至少加载了 `se-principles.md` 之前，不要继续进行。**

## 第一阶段：确定范围

询问用户或从上下文中推断要分析什么。

| 范围       | Git 命令                                     | 使用时机                 |
|----------|--------------------------------------------|----------------------|
| 功能分支   | `git log main..HEAD --oneline` + `git diff main...HEAD` | 用户位于非主分支（默认） |
| 最后 N 次提交 | `git log --oneline -N` + `git diff HEAD~N..HEAD` | 用户指定了范围，或在主分支（默认 N=5） |
| 具体提交   | `git show <sha>`                          | 用户引用了特定提交       |
| 工作变更   | `git diff` + `git diff --cached`          | 用户在提交前说“这些变更呢？” |

**默认行为：**
- 如果在功能分支：分析分支提交与主分支的差异
- 如果在主分支：分析最后 5 次提交
- 如果用户提供了不同的范围，则使用该范围

## 第二阶段：收集变更

1. 使用确定的范围运行 `git log` 以获取提交列表和消息
2. 运行 `git diff` 获取范围的完整差异
3. 如果差异很大（>500 行），首先使用 `git diff --stat`，然后选择性地阅读变更最多的 3-5 个文件
4. **仔细阅读提交消息**——它们包含了原始差异中缺失的意图
5. 只读取变更文件。不要读取整个仓库。

## 第三阶段：分析

识别**主导模式**——关于这些变更最有指导意义的东西。

寻找：
- **结构决策**——代码是如何组织的？为什么是这些边界？
- **权衡取舍**——得到了什么，牺牲了什么？（可读性 vs. 性能，DRY vs. 清晰性，速度 vs. 正确性）
- **解决的问题**——之前/之后是什么？是什么让“之后”变得更好？
- **错失的机会**——代码可以在哪里改进？（温和地提出“下次，可以考虑...”）

将发现映射到 `references/se-principles.md` 中的具体原则。要具体——引用实际代码，参考实际文件名和行变更。

## 第四阶段：呈现经验教训

使用此模板：

```markdown
## 经验教训：[原则名称]

**代码中的变更：**
[2-3 句话描述具体变更，引用文件和提交]

**起作用的原则：**
[1-2 句话解释软件工程原则]

**为什么这很重要：**
[1-2 句话说明实际后果——没有这个会出什么问题，或者因为什么而变得正确]

**下次的启示：**
[一句具体、可操作的句子，用户可以将其应用于未来的工作]
```

如果有第二个值得注意的经验教训（最多 2 个附加的）：

```markdown
---

### 也值得注意：[原则名称]

**在代码中：** [1 句话]
**原则：** [1 句话]
**启示：** [1 句话]
```

## 不要做的事情

| 避免           | 原因               | 而应           |
|-------------|------------------|-------------|
| 列出每个模糊适用的原则   | 令人不知所措且泛泛而谈   | 选择最相关的 1-2 个 |
| 分析未变更的文件   | 范围蔓延         | 坚持差异范围   |
| 忽略提交消息   | 它们包含了原始差异中缺失的意图   | 作为主要上下文阅读它们 |
| 与代码脱节的抽象建议   | 无法执行         | 总是引用具体文件/行 |
| 只有负面反馈   | 令人沮丧         | 先指出什么有效，然后建议改进 |
| 超过 3 个经验教训   | 稀释了见解         | 一个有根据的经验教训胜过七个模糊的 |

## 对话风格

- **反思而非规定。** 使用用户自己的代码作为主要证据。
- **永远不要说“你应该...”** —— 相反，使用“这里的方法展示了...”或“下次遇到这种情况时，可以考虑...”
- **如果代码很好，就说好。** 不是每个经验教训都是关于哪里出了错。识别好的模式可以加强它们。
- **如果变更很小**（一个配置调整，一个拼写修正），诚实地说出来，而不是强迫一个教训。“这些变更很简单——没有深刻的教训，只是良好的维护。”
- **要具体。** 泛泛的建议毫无价值。每个主张都必须指向一个具体的代码变更。
