# QA测试计划器

QA工程师的全面技能，用于创建测试计划、生成手动测试用例、构建回归测试套件、通过Figma验证设计以及有效记录错误。

> **激活方式**：此技能仅在明确调用时才会被触发（例如，`/qa-test-planner`、`qa-test-planner`或`使用技能qa-test-planner`）。

---

**创建测试计划：**
```
"为用户认证功能创建测试计划"

## 核心交付内容

### 1. 测试计划
- 测试范围和目标
- 测试方法和策略
- 环境要求
- 开始/结束标准
- 风险评估
- 时间表和里程碑

### 2. 手动测试用例
- 步骤说明
- 预期结果与实际结果
- 前置条件和设置
- 测试数据要求
- 优先级和严重性

### 3. 回归套件
- 烟雾测试（15-30分钟）
- 完全回归（2-4小时）
- 针对性回归（30-60分钟）
- 执行顺序和依赖关系

### 4. Figma验证
- 组件逐个比较
- 间距和排版检查
- 颜色和视觉一致性
- 交互状态验证

### 5. 错误报告
- 清晰的可重现步骤
- 环境详细信息
- 证据（截图、日志）
- 严重性和优先级

## 应避免的常见错误

| 避免 | 原因 | 而不是 |
|-------|-----|---------|
| 模糊的测试步骤 | 无法重现 | 具体操作 + 预期结果 |
| 缺少前置条件 | 测试意外失败 | 记录所有设置要求 |
| 没有测试数据 | 测试人员受阻 | 提供样本数据或生成 |
| 通用错误标题 | 难以跟踪 | 具体标题："[功能]在[操作]时的问题" |
| 跳过边界情况 | 错过关键错误 | 包括边界值、空值 |

### 严重性定义

| 等级 | 标准 | 示例 |
|-------|----------|----------|
| **关键（P0）** | 系统崩溃、数据丢失、安全 | 支付失败、登录中断 |
| **高（P1）** | 主要功能中断、无替代方案 | 搜索无法工作 |
| **中（P2）** | 功能部分、存在替代方案 | 过滤器缺少一个选项 |

### 设计验证工作流

**前提条件：**
- 配置了Figma MCP服务器
- 可以访问Figma设计文件
- 组件/页面的Figma URL

**流程：**

1. **从Figma获取设计规范**
```
"从Figma文件[URL]获取按钮规范"

响应包括：
- 尺寸（宽度、高度）
- 颜色（背景、文本、边框）
- 排版（字体、大小、粗细）
- 间距（填充、边距）
- 边框半径
- 状态（默认、悬停、激活、禁用）
```

2. **比较实现**
```
TC：主要按钮视觉验证
1. 在浏览器开发者工具中检查主要按钮
2. 与Figma规范比较：
   - 尺寸：120x40px
   - Border-radius：8px
   - 背景颜色：#0066FF
   - 字体：16px Medium #FFFFFF
3. 记录差异

3. **如果存在差异则创建错误**
```
BUG：主要按钮颜色与设计不匹配
严重性：中
预期（Figma）：#0066FF
实际（实现）：#0052CC
截图：[附加]
Figma链接：[特定组件]
```

### 需要验证的内容

| 元素 | 检查内容 | 工具 |
|---------|---------------|------|
| 颜色 | 精确的十六进制值 | 浏览器颜色选择器 |
| 间距 | 填充/边距px | DevTools计算样式 |
| 排版 | 字体、大小、粗细 | DevTools字体面板 |
| 布局 | 宽度、高度、位置 | DevTools框模型 |
| 状态 | 悬停、激活、焦点 | 手动交互 |
| 响应式 | 断点行为 | DevTools设备模式 |

### 示例查询
```

"将导航菜单实现与Figma设计进行比较"
"从Figma提取仪表板布局的间距值"
"列出Figma设计系统中使用的所有颜色标记"

### 套件结构

| 套件类型 | 持续时间 | 频率 | 覆盖范围 |
|------------|----------|-----------|----------|
| 烟雾测试 | 15-30分钟 | 每日 | 仅关键路径 |
| 针对性 | 30-60分钟 | 每次变更 | 受影响区域 |
| 完全回归 | 2-4小时 | 每周/发布 | 全面 |
| 快速检查 | 10-15分钟 | 热修复后 | 快速验证 |

### 构建回归套件

**步骤1：确定关键路径**
- 用户不能没有什么？
- 什么产生收入？
- 什么处理敏感数据？
- 什么使用最频繁？

**步骤2：优先级测试用例**

| 优先级 | 描述 | 必须运行 |
|----------|-------------|----------|
| P0 | 业务关键、安全 | 总是 |
| P1 | 主要功能、常见流程 | 每周+ |
| P2 | 次要功能、边界情况 | 发布 |

**步骤3：执行顺序**
1. 先烟雾测试 - 如果失败，停止并修复构建
2. P0测试 - 必须通过才能继续
3. P1然后P2 - 跟踪所有失败
4. 探索性测试 - 发现意外问题

### 通过/失败标准

**通过：**
- 所有P0测试通过
- P1测试通过率90%+
- 没有关键错误打开

**失败（阻止发布）：**
- 任何P0测试失败
- 发现关键错误
- 安全漏洞
- 数据丢失场景

**条件：**
- P1失败但有替代方案
- 已记录已知问题
- 有修复计划

<summary><strong>最佳实践</strong></summary>

### 测试用例编写

**要：**
- 具体且无歧义
- 每个步骤包含预期结果
- 每个测试用例测试一个功能
- 使用一致的命名约定
- 保持测试用例可维护

**不要：**
- 假设知识
- 使测试用例过长
- 跳过前置条件
- 忘记边界情况
- 遗漏预期结果

### 错误报告

**要：**
- 提供清晰的可重现步骤
- 包括截图/视频
- 指定精确的环境详细信息
- 描述对用户的影响
- 链接Figma（如果是UI错误）

**不要：**
- 没有重现步骤就报告
- 使用模糊描述
- 跳过环境详细信息
- 忘记分配优先级
- 重复现有错误

### 回归测试

**要：**
- 尽可能自动化重复测试
- 定期维护回归套件
- 优先级关键路径
- 频繁运行烟雾测试
- 每次发布后更新套件

**不要：**
- 发布前跳过回归测试
- 让套件过时
- 每次都测试所有内容
- 忽略失败的回归测试

</details>
