# backprop — bug → spec

计划执行修复代码并遗忘。
静态缺陷设计修复代码并编辑规范，使再次发生成为不可能。
那次编辑就是反向传播。

## 何时进行反向传播

- 在 `/build` 验证时测试失败。
- 用户报告错误。
- 生产事故后的事后分析。
- `/check` 标记违反了已找到的根本原因。

## 六个步骤

### 1. 追踪
阅读失败输出/错误报告。
找到错误行为的精确文件：行。
用一句原始人的话命名根本原因。

### 2. 分析
提出三个问题：
- 新的 §V 不变量能否捕获这类错误？（最常见：能）
- §I 是否错误——规范是否声称代码无法实现？（有时）
- §T 是否错误——我们是否构建了错误的东西？（罕见但真实）

### 3. 提出
起草规范变更。永远不要跳过 §B；§V/§I/§T 因情况而异。

模板：
```
§B 行：B<下一个>|<日期>|<根本原因>|V<下一个>
§V 行：V<下一个>：<能捕获它的可测试规则>
```

示例：
```
§B 行：B3|2026-04-20|退款作业在重试时运行两次|V7
§V 行：V7：∀ 退款 → 在扣款撤销前检查幂等性键
```

### 4. 生成测试
没有测试的新不变量等于谎言。先添加失败的测试。
命名测试以便引用不变量：`TestV7_RefundIdempotent`。

### 5. 验证
修复代码。运行测试。必须通过。运行完整套件。不得回归。

### 6. 记录
将规范编辑+测试+代码修复一起提交。
提交信息：`backprop §B.<n> + §V.<N>：<一句话原因>`。

## 好的不变量是什么

- 可在代码中测试（可使用 grep 或断言）。
- 限定于一个行为，而不是文件。
- 尽可能用肯定形式陈述（`! hold` 而不是 `⊥ forbid`）。
- 引用适用处的 §I 表面。

**坏**：V8：代码应该是正确的。
**好**：V8：∀ pg_query ! 通过驱动程序插值参数，⊥ 字符串连接。

## 何时不添加 §V

- 错误完全是机械性拼写错误且没有类别（`i++` vs `i--` 在一次性代码中）。
- 修复是一次性迁移。
- 根本原因是外部依赖（升级依赖项，并在 §C 中记录）。

仍然追加 §B 条目——记录该失败模式已被考虑。具有相同气味的未来错误 → §B 搜索显示先例。

## 输出形状

每次反向传播运行都会产生：
1. §B 条目（总是）。
2. §V 条目（通常）。
3. 测试文件（当添加 §V 时）。
4. 代码修复。
5. 一个提交。

没有仪表板。没有日志文件。SPEC.md + git 是完整的历史。
