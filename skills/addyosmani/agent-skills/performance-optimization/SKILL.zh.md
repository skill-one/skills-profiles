# 性能优化

## 概述

优化前先进行测量。没有测量的性能工作就是猜测——而猜测会导致过早优化，这种优化会增加不必要的复杂性，却无法提升真正重要的性能。先进行性能分析，找出实际的瓶颈，修复它，然后再次测量。只优化那些测量证明重要的部分。

## 何时使用

- 技术规范中存在性能要求（加载时间预算、响应时间SLA）
- 用户或监控报告性能缓慢
- 核心网络指标得分低于阈值
- 你怀疑某个变更引入了回归
- 构建处理大型数据集或高流量的功能

**不使用的情况：** 在没有问题证据之前不要进行优化。过早优化会增加比它所获得的性能更多的复杂性。

## 核心网络指标目标

| 指标 | 优秀 | 需要改进 | 差 |
|------|------|----------|----|
| **LCP**（最大内容绘制） | ≤ 2.5秒 | ≤ 4.0秒 | > 4.0秒 |
| **INP**（首次输入延迟） | ≤ 200毫秒 | ≤ 500毫秒 | > 500毫秒 |
| **CLS**（累积布局偏移） | ≤ 0.1 | ≤ 0.25 | > 0.25 |

## 优化工作流程

```
1. 测量  → 使用真实数据建立基线
2. 识别  → 找到实际的瓶颈（而不是假设的）
3. 修复  → 解决特定的瓶颈
4. 验证  → 再次测量；保留或回滚
5. 防护  → 添加监控或测试以防止回归
```

### 第1步：测量

有两种互补的方法——使用两者：

- **合成（Lighthouse、DevTools 性能标签页）：** 控制条件，可重复。最适合CI回归检测和隔离特定问题。
- **RUM（web-vitals库、CrUX）：** 真实用户数据在真实条件下。必须验证修复是否真正改善了用户体验。

**前端：**
```bash
# 合成：Chrome DevTools中的Lighthouse（或CI）
# Chrome DevTools → 性能标签页 → 录制
# Chrome DevTools MCP → 性能跟踪

# RUM：代码中的Web Vitals库
import { onLCP, onINP, onCLS } from 'web-vitals';

onLCP(console.log);
onINP(console.log);
onCLS(console.log);
```

**后端：**
```bash
# 响应时间日志记录
# 应用性能监控（APM）
# 带时间戳的数据库查询日志

# 简单时间测量
console.time('db-query');
const result = await db.query(...);
console.timeEnd('db-query');
```

### 从何处开始测量

根据症状决定首先测量什么：

```
什么很慢？
├── 首次页面加载
│   ├── 大型包？ --> 测量包大小，检查代码拆分
│   ├── 服务器响应慢？ --> 在DevTools网络瀑布流中测量TTFB
│   │   ├── DNS长时间？ --> 为已知源添加dns-prefetch / preconnect
│   │   ├── TCP/TLS长时间？ --> 启用HTTP/2，检查边缘部署，keep-alive
│   │   └── 等待（服务器）长时间？ --> 分析后端，检查查询和缓存
│   └── 妨碍渲染的资源？ --> 检查网络瀑布流中的CSS/JS阻塞
├── 交互感觉迟缓
│   ├── 点击时UI冻结？ --> 分析主线程，查找长时间任务（>50毫秒）
│   ├── 表单输入延迟？ --> 检查重渲染，受控组件开销
│   └── 动画卡顿？ --> 检查布局抖动，强制重排
├── 导航后的页面
│   ├── 数据加载？ --> 测量API响应时间，检查瀑布流
│   └── 客户端渲染？ --> 分析组件渲染时间，检查是否存在N+1请求
└── 后端 / API
    ├── 单个端点慢？ --> 分析数据库查询，检查索引
    ├── 所有端点慢？ --> 检查连接池，内存，CPU
    └── 间歇性缓慢？ --> 检查锁争用，GC暂停，外部依赖
```

### 第2步：识别瓶颈

按类别常见的瓶颈：

**前端：**

| 症状 | 可能原因 | 调查 |
|------|---------|------|
| LCP慢 | 大型图片，妨碍渲染的资源，服务器慢 | 检查网络瀑布流，图片大小 |
| CLS高 | 没有尺寸的图片，加载内容晚，字体偏移 | 检查布局偏移归因 |
| INP差 | 主线程上的重型JavaScript，大型DOM更新 | 在性能跟踪中检查长时间任务 |
| 初始加载慢 | 大型包，许多网络请求 | 检查包大小，代码拆分 |

**后端：**

| 症状 | 可能原因 | 调查 |
|------|---------|------|
| API响应慢 | N+1查询，缺少索引，未优化的查询 | 检查数据库查询日志 |
| 内存增长 | 泄漏引用，无界缓存，大型有效负载 | 堆快照分析 |
| CPU峰值 | 同步重型计算，正则表达式回溯 | CPU分析 |
| 高延迟 | 缺少缓存，冗余计算，网络跳转 | 跟踪请求通过堆栈 |

### 第3步：修复常见反模式

#### N+1查询（后端）

```typescript
// BAD: N+1——每个任务一个查询以获取所有者
const tasks = await db.tasks.findMany();
for (const task of tasks) {
  task.owner = await db.users.findUnique({ where: { id: task.ownerId } });
}

// GOOD: 单个查询带连接/包含
const tasks = await db.tasks.findMany({
  include: { owner: true },
});
```

#### 无界数据获取

```typescript
// BAD: 获取所有记录
const allTasks = await db.tasks.findMany();

// GOOD: 分页带限制
const tasks = await db.tasks.findMany({
  take: 20,
  skip: (page - 1) * 20,
  orderBy: { createdAt: 'desc' },
});
```

#### 查询忽略其索引

"添加索引"是猜测。查询计划才是测量：

```sql
EXPLAIN ANALYZE
SELECT id, title FROM tasks
WHERE owner_id = 42 ORDER BY created_at DESC LIMIT 20;
```

输出中的三个决定修复：

| 你看到的内容 | 它意味着什么 |
|---|---|
| 在大型表上`Seq Scan`，而预期有索引 | 没有可用的索引用于此谓词 |
| 估计的`rows=`与实际相差一个数量级 | 统计信息过时；规划器基于错误信息选择 |
| 扫描上方的`Sort`节点 | 索引覆盖了过滤器，但没有`ORDER BY` |

索引针对的是查询的**形状**，而不是孤立列。在复合索引中，等值列优先，然后是范围或排序列：

```sql
CREATE INDEX idx_tasks_owner_created ON tasks (owner_id, created_at DESC);
```

**索引不会帮助的情况：**

| 情况 | 原因 |
|------|------|
| 选择性低，查询主导值（一个95%为`active`的`status`列，过滤`active`） | 序列扫描确实更便宜；规划器会忽略索引。过滤稀有值是相反的情况，部分索引效果很好 |
| 前导通配符（`LIKE '%term'`） | B树无法在无前缀的情况下搜索；需要trigram或全文搜索 |
| 列上的函数（`WHERE lower(email) = ?`） | 普通列索引不可用；索引表达式 |
| 写入密集型表 | 每个索引都是每个`INSERT`/`UPDATE`的税；测量写入成本，而不是读取收益 |

修复后重新运行`EXPLAIN ANALYZE`。如果索引没有改变计划，则回滚（第4步），而且它不是免费的：它仍然会在每次写入时产生成本。

#### 连接池耗尽

特征非常独特：**所有**端点同时变慢，慢时间用于等待连接而不是执行，数据库报告大部分空闲会话。

```typescript
// BAD：每个请求或每个模块一个池——在无服务器情况下，这会乘以实例数量并耗尽数据库的连接限制
// GOOD：每个进程一个池，相对于数据库的极限进行大小调整
const pool = new Pool({
  max: 10,                        // 实例数 × max必须保持在max_connections以下
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 5_000, // 快速失败而不是无限排队
});
```

**大不是快。** 大于数据库可以并发执行的池只会将队列从你的应用程序转移到数据库，在那里更难看到。当实例数量无界（无服务器，自动扩展）时，多路复用连接的代理（pgbouncer，RDS Proxy）是修复方法，而不是更高的`max`。

#### 不必要的重渲染（React）

```tsx

function TaskList() {

const TaskItem = React.memo(function TaskItem({ task }: Props) {
  return <div>{/* 昂贵渲染 */}</div>;

// 使用useMemo优化昂贵计算

  const stats = useMemo(() => calculateStats(tasks), [tasks]);
```

#### 缺少缓存（后端）

缓存那些生成昂贵且读取频率远高于其变化的内容。缓存一个已经很快的查询会增加网络跳转、陈旧性错误和需要维护的驱逐策略，而没有任何收益。

**故意选择层：**

| 层 | 对...可见 | 使用时 | 成本 |
|---|---|---|---|
| 进程内（`Map`、LRU） | 一个实例 | 小型、热、每个实例的陈旧性可以接受 | 每个实例独立漂移；无效化只影响一个 |
| 共享（Redis、Memcached） | 所有实例 | 实例必须同意，或者值需要重新计算 | 网络跳转，以及运行和监控的另一个服务 |
| CDN / 边缘 | 每个人，每个URL | 响应对给定键是公开且相同的 | 无效化是难题；假设你无法快速召回错误响应 |

```typescript
// 缓存频繁读取、很少更改的数据
const CACHE_TTL = 5 * 60 * 1000; // 5分钟
let cachedConfig: AppConfig | null = null;
let cacheExpiry = 0;

async function getAppConfig(): Promise<AppConfig> {
  if (cachedConfig && Date.now() < cacheExpiry) {
    return cachedConfig;
  }
  cachedConfig = await db.config.findFirst();
  cacheExpiry = Date.now() + CACHE_TTL;
  return cachedConfig;
}

// 静态资产的HTTP缓存头
app.use('/static', express.static('public', {
  maxAge: '1y',           // 缓存1年
  immutable: true,        // 永不重新验证（在文件名中使用内容哈希）
}));

// API响应的Cache-Control
res.set('Cache-Control', 'public, max-age=300'); // 5分钟
```

**关键设计决定正确性。** 每个更改响应的输入都属于键：租户、区域设置、权限、功能标志。省略观看者的键会导致一个用户的数据被提供给另一个用户，这会作为性能提升被发布。你保留的代码，你将永远维护。让它为自己买单。

**选择一种无效化策略，而不是三种：**

| 策略 | 交易 |
|---|---|
| TTL | 最简单。你接受最多TTL的陈旧性，因此明确说明可接受的窗口 |
| 基于事件或标签 | 写入时新鲜，但现在写入者必须知道缓存拓扑 |
| 版本化键（`user:42:profile:v7`） | 永不无效化，只是停止读取旧键。直到驱逐前成本内存 |

**防止羊群效应。** 热键过期，所有并发请求同时错过，然后源一次性承担全部负载，这就是缓存如何从防止故障变成故障的原因。在单个请求重新计算时提供陈旧内容（`stale-while-revalidate`），或者将并发错过合并到一个正在进行的承诺后面，以便N个等待者导致一次重新计算。

**不要缓存：** 任何陈旧性就是正确性错误的东西（余额、权限、结账时的库存），或者在无法识别用户的键下缓存的用户数据。参见`../../references/performance-checklist.md`以获取请求合并、写入策略、负缓存和缓存清单。

### 第4步：验证（保留或回滚）

修复是一个假设，直到你重新测量。这一步决定它是否存活。

**以你测量基线的方式重新测量：** 相同命令，相同条件，相同固定预算（墙时钟、样本数或请求数）。在冷缓存上获取的基线与在热缓存上获取的结果测量的是缓存，而不是你的变更。

**一次只改变一件事。** 三个优化一起发布产生一个数字，而你无法归因。如果它们必须一起发布，请先单独测量每个。

**超越噪音，而不仅仅是平均值。** 重复测量并比较增量与运行间方差。3%的增益在±5%方差内不是增益；它是不同的样本。

然后严格决定：

| 结果与基线对比 | 操作 |
|---|---|
| 超过阈值，测试绿色 | **保留。** 在提交信息中包含前后数字。 |
| 在噪音内（无测量变化） | **回滚。** |
| 变差 | **回滚。** |
| 改善，但测试变红 | **回滚。** 带着胜利外衣的回归。 |

**“中性”是回滚，而不是保留。** 这是团队跳过的一步：变更已经编写，扔掉它感觉浪费，所以它未经测量就发布，而代码库积累了永远不会买得起的复杂性。你保留的代码，你将永远维护。让它为自己买单。

**正确性控制指标。** 套件保持绿色*并且*数字移动。一个“优化”通过放弃产品需要的工作（跳过验证、缓存必须新鲜的东西、移除负载均衡的`await`）而获胜，这不是胜利，而是回归。

#### 记录每次尝试，包括回滚的尝试

回滚的工作在git历史记录中没有痕迹，这恰好是为什么同一个死想法在下个季度会被再次尝试。保留一个简短的账本，以便被丢弃的想法保持丢弃：

| 想法 | 基线 → 结果 | 判定 | 原因 |
|---|---|---|---|
| 缓存行组件 | INP 240ms → 235ms | 已撤销 | 内部噪声（±15ms）。行不是瓶颈。 |
| 虚拟化列表 | INP 240ms → 90ms | 保留 | 跟踪中不再有长任务。 |
| 预连接到 API 域名 | LCP 2.8s → 2.8s | 已撤销 | 已经同源。 |

PR 描述中的一个部分或仓库中的 `PERF.md` 都可以。重要的是，下一个人（或下一个代理）在提出实验之前阅读它，并且不会重新运行已经失败的实验。

### 第 5 步：防止回归

保护用户实际感受到的指标，而不是所有可用的数字。使用与修复方案相同的 LCP、INP、p95 延迟或其他主要指标。

当界面面向用户时，使用两个互补的层：

- **合成 CI 门禁：** 在合并前使用性能预算捕获可重复的回归。重复噪声测量或比较中位数/趋势，以便正常的运行间差异不会使门禁变成一个不可靠的检查。
- **现场监控：** 在 RUM 数据中检测到有意义的 p75 变动时发出警报。使用归因的 `web-vitals` 数据定位原因；将 CrUX 的滚动窗口视为确认而不是立即警报。

当任何一个门禁触发时，返回到第 1 步，在提出另一个修复方案之前建立一个新的基线。

**设置预算并执行：**

```
JavaScript 打包：< 200KB 压缩后（初始加载）
CSS：< 50KB 压缩后
图片：< 200KB 每张图片（首屏以上）
字体：< 100KB 总计
API 响应时间：< 200ms (p95)
交互时间：< 3.5s 在 4G 网络上
Lighthouse 性能分数：≥ 90
```

**在 CI 中执行：**
```bash
# 打包大小检查
npx bundlesize --config bundlesize.config.json

# Lighthouse CI
npx lhci autorun
```

## 常见理由

| 理由 | 现实 |
|---|---|
| "我们稍后会优化" | 性能债务会累积。现在修复明显的反模式，推迟微优化。 |
| "在我的机器上很快" | 你的机器不是用户的。在代表性硬件和网络上进行分析。 |
| "这个优化很明显" | 如果你没有测量，你就不知道。先分析。 |
| "用户不会注意到 100ms" | 研究表明 100ms 的延迟会影响转化率。用户比你想象的更能注意到。 |
| "框架处理性能" | 框架可以防止一些问题，但无法修复 N+1 查询或过大的打包。 |
| "查询很慢，添加索引" | 先查看计划。索引可能已经存在且无法使用，并且每个索引都会永久影响写入。 |
| "直接缓存" | 缓存一个已经很快的调用没有任何好处，并且会添加一个陈旧性错误。缓存昂贵的东西，并且重新读取远多于写入。 |
| "增加连接池大小，我们连接不足" | 大于数据库可以服务的连接池将队列移动到不太显眼的地方。找出什么在保持连接。 |
| "效果不明显，但无害" | 中性更改是撤销。你永远支付维护费用，但没有得到回报。 |
| "我们已经写了，不如保留" | 沉没成本。测量并不关心更改花费了多长时间来编写。 |
| "改进很明显，不需要重新测量" | 那么重新测量很便宜，并且可以证明它。未测量的胜利是如何导致中性复杂性的。 |

## 警示信号

- 没有分析数据来证明的优化
- 数据获取中的 N+1 查询模式
- 没有在添加索引前后查看查询计划来证明它
- 缓存键省略了响应依赖的输入（租户、区域、查看者）
- 没有声明陈旧性窗口和无效策略的缓存
- 连接池大小在响应耗尽时增加，但没有找出什么在保持连接
- 没有分页的列表端点
- 没有尺寸、懒加载或响应式尺寸的图片
- 打包大小增长而没有审查
- 生产中没有性能监控
- 到处使用 `React.memo` 和 `useMemo`（过度使用和不足用一样糟糕）
- 没有重新测量的优化被保留下来证明它们
- 多个优化捆绑在一个测量中，所以无法将单个更改归因
- 需要更改、跳过或删除测试的“胜利”
- 相同的失败优化尝试了多次，因为没有人记录第一次尝试

## 验证

在任何与性能相关的更改后：

- [ ] 存在前后测量（具体数字）
- [ ] 结果与基线以相同方式重新测量（相同命令，相同条件）
- [ ] 改进超过了运行间差异，而不仅仅是平均值
- [ ] 没有超过基线的更改被保留为中性
- [ ] 尝试被记录，保留和撤销一样，所以不会重新运行死亡的点子
- [ ] 特定的瓶颈被识别和解决
- [ ] 核心网络生命体征在“良好”阈值内
- [ ] 打包大小没有显著增加
- [ ] 新的数据获取代码中没有 N+1 查询
- [ ] 任何新索引都由添加前后查询计划证明，并且考虑了其写入成本
- [ ] 任何新缓存都说明它依赖什么以及如何陈旧
- [ ] 测量的用户界面指标有合成预算或现场监控可以检测回归
- [ ] 现有测试仍然通过（优化没有破坏行为）
