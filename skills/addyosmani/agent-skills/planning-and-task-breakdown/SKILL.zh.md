# 规划与任务分解

## 概述

将工作分解为小的、可验证的任务，并明确验收标准。良好的任务分解是区分可靠完成工作的代理和产生混乱结果的关键。每个任务都应该足够小，以便在一个专注的会话中实现、测试和验证。

## 何时使用

- 你有一个规范，需要将其分解为可实现的单元
- 一个任务感觉太大或太模糊，难以开始
- 工作需要在多个代理或会话中并行化
- 你需要向人类传达范围
- 实现顺序不明显

**不使用时：** 单文件更改且范围明显，或者规范中已经包含定义良好的任务。

## 规划流程

### 第1步：进入规划模式

在编写任何代码之前，以只读模式操作：

- 阅读规范和相关代码库部分
- 识别现有模式和约定
- 绘制组件之间的依赖关系
- 记录风险和未知因素

**规划期间不要编写代码。** 输出是一个保存到 `tasks/plan.md` 的规划文档，以及记录在任务列表目标中的任务列表（参见输出文件；默认 `tasks/todo.md`），而不是实现。

### 第2步：识别依赖关系图

绘制什么依赖于什么：

```
数据库模式
    │
    ├── API模型/类型
    │       │
    │       ├── API端点
    │       │       │
    │       │       └── 前端API客户端
    │       │               │
    │       │               └── UI组件
    │       │
    │       └── 验证逻辑
    │
    └── 种子数据/迁移
```

实现顺序遵循依赖关系图自下而上：先构建基础。

### 第3步：垂直切片

不是先构建所有数据库，然后所有API，再所有UI —— 一次构建一个完整的功能路径：

**不良（水平切片）：**
```
任务1：构建整个数据库模式
任务2：构建所有API端点
任务3：构建所有UI组件
任务4：连接所有内容
```

**良好（垂直切片）：**
```
任务1：用户可以创建账户（模式+API+注册的UI）
任务2：用户可以登录（认证模式+API+登录的UI）
任务3：用户可以创建任务（任务模式+API+创建的UI）
任务4：用户可以查看任务列表（查询+API+列表视图的UI）
```

每个垂直切片都交付可工作、可测试的功能。

### 第4步：编写任务

每个任务都遵循此结构，无论它落在Markdown任务列表中还是作为外部跟踪器中的项目（参见输出文件）：

```markdown
## 任务[N]：[简短的描述性标题]

**描述：** 一段话说明此任务完成什么。

**验收标准：**
- [ ] [具体、可测试的条件]
- [ ] [具体、可测试的条件]

**验证：**
- [ ] 测试通过：[仓库的聚焦测试命令]
- [ ] 构建成功：[仓库的构建命令]
- [ ] 手动检查：[要验证的内容描述]

**依赖：** [此任务依赖的任务编号，或“无”]

**可能修改的文件：**
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**估计范围：** [小：1-2个文件 | 中：3-5个文件 | 大：5个以上文件]
```

### 第5步：排序和检查点

排列任务，以便：

1. 依赖关系得到满足（先构建基础）
2. 每个任务都使系统处于工作状态
3. 验证检查点在每2-3个任务之后发生
4. 高风险任务靠前（快速失败）

在任务列表目标中添加明确的检查点：

```markdown
## 检查点：任务1-3之后
- [ ] 所有测试通过
- [ ] 应用程序构建无错误
- [ ] 核心用户流程端到端工作
- [ ] 在继续之前与人类进行审查
```

## 任务大小指南

| 大小 | 文件 | 范围 | 示例 |
|------|-------|-------|---------|
| **XS** | 1 | 单个函数或配置更改 | 添加一个验证规则 |
| **S** | 1-2 | 一个组件或端点 | 添加一个新的API端点 |
| **M** | 3-5 | 一个功能切片 | 用户注册流程 |
| **L** | 5-8 | 多个组件的功能 | 带过滤和分页的搜索 |
| **XL** | 8+ | **太大——进一步分解** | — |

如果一个任务是大或更大，它应该分解成更小的任务。代理在S和M任务上表现最佳。

**何时进一步分解任务：**
- 它需要超过一个专注的会话（大约2+小时的代理工作）
- 你不能用3个或更少的要点描述验收标准
- 它触及两个或多个独立的子系统（例如，认证和计费）
- 你发现自己写任务标题中的“和”（一个表示它是两个任务的迹象）

## 输出文件

- **规划文档：** 将实现计划保存到 `tasks/plan.md`。这始终是一个Markdown文件——设计决策、风险和开放问题无法直接映射到单个跟踪器问题。
- **任务列表：** 在**任务列表目标**（定义如下）中记录每个任务。

如果不存在，则创建 `tasks/` 目录。

**不要覆盖不完整的规划。** 在编写 `tasks/plan.md` 或 `tasks/todo.md` 之前，检查它们是否已经存在并仍然包含未检查的任务：

- 相同工作正在重新规划（用户要求修改或扩展此计划）→ 就地更新现有文件。
- 不同工作 → **停止并询问。** 未检查的任务可能在另一个会话中处于构建中。不要自行删除、覆盖或重命名现有文件；展示冲突，并让用户决定（先完成旧计划，明确丢弃它，或告诉你新计划应该放在哪里）。

对外部任务列表目标也适用相同规则：不要批量关闭或删除另一个计划的开放跟踪器项以腾出空间给新的。

### 任务列表目标

任务列表目标是指录任务和检查点的位置。它在这里定义一次；本技能中的其他引用都指向它。

- **默认：`tasks/todo.md` 位置的检查表样式Markdown文件。** 这是 `/build` 命令和其他下游工具期望的约定。除非项目另有说明，否则使用它。
- **外部跟踪器：** 如果项目的代理规则（`CLAUDE.md`、`AGENTS.md` 等）或用户指定一个问题跟踪器（例如 GitHub Issues、Jira、Linear、`bd`/beads），则每个任务创建一个跟踪器项，而不是编写 `tasks/todo.md`。将第4步的结构映射到跟踪器的字段：验收标准和验证步骤在项正文，依赖关系通过跟踪器的链接机制（`bd dep add`、"被阻塞"等）添加。也将第5步的检查点记录为跟踪器项，或者如果跟踪器没有自然的等价物，则记录为规划文档中的检查表。

使用外部跟踪器时，在 `tasks/plan.md` 中注明它（例如 "任务在Linear项目FOO中跟踪"），以便下游步骤和未来会话知道在哪里查找，并保持规划文档的任务列表部分作为跟踪器项ID或链接的有序索引，而不是重复的检查表。

## 规划文档模板

```markdown
# 实现计划：[功能/项目名称]

## 概述
[一个段落总结我们正在构建什么]

## 架构决策
- [关键决策1及其理由]
- [关键决策2及其理由]

## 任务列表

### 第一阶段：基础
- [ ] 任务1：...
- [ ] 任务2：...

### 检查点：基础
- [ ] 测试通过，构建干净

### 第二阶段：核心功能
- [ ] 任务3：...
- [ ] 任务4：...

### 检查点：核心功能
- [ ] 端到端流程工作

### 第三阶段：完善
- [ ] 任务5：...
- [ ] 任务6：...

### 检查点：完成
- [ ] 所有验收标准满足
- [ ] 准备审查

## 风险和缓解措施
| 风险 | 影响 | 缓解措施 |
|------|--------|------------|
| [风险] | [高/中/低] | [策略] |

## 开放问题
- [需要人类输入的问题]
```

当任务存在于外部跟踪器中时，保持上面的任务列表部分作为跟踪器项ID或链接的有序索引，而不是重复的检查表。

## 并行化机会

当有多个代理或会话可用时：

- **可以并行化：** 独立的功能切片、已实现功能的测试、文档
- **必须顺序执行：** 数据库迁移、共享状态更改、依赖链
- **需要协调：** 共享API合约的功能（先定义合约，然后并行化）

## 常见理由

| 理由 | 现实 |
|---|---|
| "我会边做边想" | 那样你会得到一团糟和返工。10分钟的规划可以节省数小时。 |
| "任务很明显" | 还是把它们写下来。明确的任务会暴露隐藏的依赖关系和被遗忘的边缘情况。 |
| "规划是开销" | 规划就是任务。没有计划的实现只是打字。 |
| "我可以在脑海中记住所有内容" | 上下文窗口是有限的。书面计划会跨会话边界和压缩而生存。 |
| "旧的 `tasks/plan.md` 已过时，我会直接替换它" | 未检查的任务可能在另一个会话中处于构建中。覆盖它们会销毁存在于任何地方的工 作状态。停止并询问。 |

## 警报

- 没有写任务列表就开始实现
- 没有询问就覆盖了仍然有不同工作未检查任务的 `tasks/plan.md` 或 `tasks/todo.md`
- 项目指定了外部跟踪器时编写 `tasks/todo.md`（或者将任务分散到两者之间）
- 说“实现功能”但没有验收标准的任务
- 规划中没有验证步骤
- 所有任务都是XL大小
- 任务之间没有检查点
- 没有考虑依赖关系顺序

## 验证

在开始实现之前，确认：

- [ ] 每个任务都有验收标准
- [ ] 每个任务都有一个验证步骤
- [ ] 任务依赖关系被识别并正确排序
- [ ] 任务记录在任务列表目标中（默认 `tasks/todo.md`）
- [ ] 没有在未明确用户确认的情况下覆盖现有不完整的规划
- [ ] 没有任务触及超过~5个文件
- [ ] 主要阶段之间存在检查点
- [ ] 人类已经审查并批准了计划

## 参见

验收标准是按任务划分的，并回答“我们是否构建了正确的东西？”。它们位于项目范围的完成定义之上，每个任务在计数为完成之前都必须满足。参见 `../../references/definition-of-done.md`。
