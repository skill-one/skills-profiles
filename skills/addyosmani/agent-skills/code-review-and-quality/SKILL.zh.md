# 代码审查与质量

## 概述

多维度代码审查，并设置质量门禁。每一次变更在合并前都需要经过审查——无一例外。审查涵盖五个维度：正确性、可读性、架构、安全性和性能。

**批准标准：** 当变更明确提升了整体代码健康度时，即使它并不完美，也应该批准。完美的代码不存在——目标是持续改进。不要因为变更与你期望的写法不完全一致而阻止它。如果它改进了代码库并且遵循了项目的规范，就批准它。

## 何时使用

- 合并任何 PR 或变更之前
- 完成一个功能实现之后
- 当你需要评估另一个代理或模型生成的代码时
- 当重构现有代码时
- 任何修复 Bug 之后（审查修复部分和回归测试）

## 五轴审查

每一次审查都会在这些维度上评估代码：

### 1. 正确性

代码是否做了它声称要做的？

- 它是否与规范或任务要求相匹配？
- 是否处理了边界情况（空值、空、边界值）？
- 是否处理了错误路径（不只是成功路径）？
- 它是否通过了所有测试？测试是否真的在测试正确的事情？
- 是否存在计算错误、竞态条件或状态不一致？

### 2. 可读性与简洁性

另一个工程师（或代理）能否在不解释的情况下理解这段代码？

- 名称是否描述性强并且与项目规范一致？（没有上下文的 `temp`、`data`、`result`）
- 控制流是否简单（避免嵌套三元运算符、深层回调）？
- 代码是否逻辑上组织合理（相关代码分组、清晰的模块边界）？
- 是否有任何“技巧”应该简化？
- **这能否用更少的行数完成？**（1000 行代码而 100 行就足够是失败）
- **抽象是否值得其复杂性？**（在第三个用例之前不要泛化）
- 是否需要注释来澄清非明显的意图？（但不要注释明显的代码）
- 是否存在死代码残留：无操作变量（`_unused`）、向后兼容的遮蔽层或 `// 移除` 注释？
- **是否在一个无关的流程上添加了新的条件？** 这是一种设计问题，而不是小问题——将逻辑推入它自己的辅助函数、状态或策略，而不是打乱现有的路径。
- **是否在同一个形状上重复出现条件？** 它表明缺少模型或调度器。“临时”分支通常是永久债务。

### 3. 架构

变更是否适合系统的设计？

- 它是否遵循现有的模式或引入了新的模式？如果是新的，是否有充分的理由？
- 它是否保持了清晰的模块边界？
- 是否有应该共享的代码重复？
- 依赖项是否流向正确的方向（没有循环依赖）？
- 抽象级别是否合适（不过度设计，也不过于耦合）？
- **这次重构是减少了复杂性还是仅仅转移了复杂性？** 计算读者必须持有的概念数量来遵循变更。如果“更干净”的版本没有改变这个数量，它就不是更干净——优先选择使整个分支、模式或层消失的重构，而不是重新集中相同的逻辑。优先删除抽象而不是优化它。
- **特定于功能的逻辑是否泄漏到共享或通用模块中？** 将逻辑保持在它所属的层，重用现有的标准辅助函数而不是近似的副本，并且不要规范化架构漂移。
- **类型边界是否明确？** 质疑无谓的 `any`/`unknown`/可选/强制转换和静默回退，这些回退掩盖了不明确的不变量——使边界明确通常会使周围的控制流更简单。

### 4. 安全性

有关详细的安全指南，请参阅 `security-and-hardening`。变更是否引入了漏洞？

- 用户输入是否经过验证和清理？
- 密钥是否保持在代码、日志和版本控制之外？
- 是否在需要的地方进行了身份验证/授权检查？
- SQL 查询是否参数化（没有字符串连接）？
- 输出是否编码以防止 XSS？
- 依赖项是否来自可信来源且没有已知漏洞？
- 来自外部来源（API、日志、用户内容、配置文件）的数据是否被视为不受信任？
- 在逻辑或渲染中使用之前，是否在系统边界处验证了外部数据流？

### 5. 性能

有关详细的性能分析和优化，请参阅 `performance-optimization`。变更是否引入了性能问题？

- 是否有任何 N+1 查询模式？
- 是否有任何无界循环或不受约束的数据获取？
- 是否有任何应该异步的同步操作？
- 是否有任何 UI 组件中的不必要重绘？
- 是否有任何列表端点的分页缺失？
- 是否有任何在热点路径中创建的大对象？

## 结构性补救措施

当你标记一个结构性问题时，建议移动——而不仅仅是问题。一个只说“这很复杂”的审查让作者猜测。寻找命名的重构：

- **用类型模型或显式调度器替换条件链**。
- **将重复的分支合并为更清晰的单一流程**。
- **将编排与业务逻辑分离**，使每个都能独立读取。
- **将特定于功能的逻辑**从共享模块移动到拥有该概念的包中。
- **重用标准辅助函数**而不是定制的近似副本。
- **使类型边界明确**，以便下游分支消失。
- **删除一个传递式包装器**，它增加了间接性而没有澄清 API。
- **提取一个辅助函数，或将一个大文件拆分为专注的模块**。

优先选择移除移动部件的补救措施，而不是将相同的复杂性分散。

## 变更大小

小而专注的变更更容易审查、更快合并，并且更安全部署。目标是这些大小：

```
~100 行变更   → 好。可以一次性审查。
~300 行变更   → 如果是单一逻辑变更，可以接受。
~1000 行变更  → 太大。拆分它。
```

**关注文件大小，而不仅仅是差异大小。** 一个小的差异仍然可能将文件推过健康的边界——单个文件中大约 1000 *总行数*（与上述 ~1000 *变更* 行阈值不同）是一个常见的检查信号，而不是硬性上限。当变更实质性增加了已经很大的文件时，询问是否应先提取辅助函数、子组件或模块，然后再添加更多内容。分解，然后添加。

**“一个变更”算什么：** 一个自包含的修改，解决一个问题，包括相关的测试，并在提交后保持系统功能。功能的一部分——而不是整个功能。

**当变更太大时的拆分策略：**

| 策略 | 如何 | 何时 |
|------|------|------|
| **堆叠** | 提交一个小变更，基于它开始下一个 | 顺序依赖 |
| **按文件组** | 为需要不同审查者审查的组分别提交变更 | 跨切关注点 |
| **水平** | 先创建共享代码/桩，然后是消费者 | 分层架构 |
| **垂直** | 分解为功能的较小全栈切片 | 功能工作 |

**当大变更可以接受时：** 完整的文件删除和自动重构，审查者只需要验证意图，而不需要审查每一行。

**将重构与功能工作分开。** 一个重构现有代码并添加新行为的变更是两个变更——分别提交它们。小的清理（变量重命名）可以根据审查者的意愿包含在内。

## 变更描述

每一次变更都需要一个在版本控制历史中可以独立存在的描述。

**第一行：** 短、祈使、独立。例如“删除 FizzBuzz RPC”而不是“删除 FizzBuzz RPC”。必须足够信息，以便在搜索历史时，有人可以理解变更，而无需阅读差异。

**正文：** 什么在改变以及为什么。包括上下文、决策和代码本身无法看到的推理。在相关的地方链接到 Bug 编号、基准结果或设计文档。当存在方法缺陷时，承认它们。

**反模式：** “修复 Bug”、“修复构建”、“添加补丁”、“将代码从 A 移动到 B”、“阶段 1”、“添加便利函数”。

## 审查流程

### 第一步：理解上下文

在查看代码之前，理解意图：

```
- 这个变更试图完成什么？
- 它实现了哪个规范或任务？
- 预期行为变化是什么？
```

### 第二步：先审查测试

测试揭示了意图和覆盖率：

```
- 变更是否存在测试？
- 它们是否测试行为（而不是实现细节）？
- 是否覆盖了边界情况？
- 测试名称是否描述性强？
- 如果代码改变，测试是否会捕获回归？
```

### 第三步：审查实现

以五个轴为参考，逐步审查代码：

```
对于每个已更改的文件：
1. 正确性：这段代码是否做了测试所说的？
2. 可读性：我能否在不帮助的情况下理解？
3. 架构：它是否符合系统？
4. 安全性：有任何漏洞吗？
5. 性能：有任何瓶颈吗？
```

### 第四步：分类发现

用严重性前缀标记每个评论，以便作者知道哪些是必须解决的，哪些是可选的：

| 前缀 | 含义 | 作者操作 |
|------|------|----------|
| *(无前缀)* | 必须变更 | 合并前必须解决 |
| **关键：** | 阻止合并 | 安全漏洞、数据丢失、功能损坏 |
| **小问题：** | 小的、可选的 | 作者可以忽略——格式、风格偏好 |
| **可选：** / **考虑：** | 建议 | 值得考虑但不是必须的 |
| **仅供参考** | 仅信息性 | 无需操作——用于未来参考 |

这可以防止作者将所有反馈都视为强制性，并浪费时间在可选建议上。

**优先考虑重要的事情。** 按杠杆顺序排列发现：正确性和安全性优先，然后是结构性回归和遗漏的简化，然后是其他所有内容。不要将一个真实问题埋在装饰性小问题下面——几个有说服力的评论比一个长列表更好。如果你有一个结构性问题，十个小问题，结构性问题就是审查。

### 第五步：验证验证

检查作者的验证故事：

```
- 运行了哪些测试？
- 构建是否通过？
- 是否进行了手动测试？
- 是否有 UI 变更的截图？
- 是否有前后比较？
```

## 多模型审查模式

使用不同的模型进行不同的审查视角：

```
模型 A 编写代码
    │
    ▼
模型 B 审查正确性和架构
    │
    ▼
模型 A 解决反馈
    │
    ▼
人类做出最终决定
```

这可以捕获单个模型可能遗漏的问题——不同的模型有不同的盲点。

**审查代理的示例提示：**
```
审查这个代码变更的正确性、安全性和遵循项目规范。规范说 [X]。变更应该 [Y]。标记任何问题为关键、必须、可选或小问题。
```

## 死代码卫生

在每次重构或实现变更之后，检查孤儿代码：

1. 确定现在无法访问或未使用的代码
2. 明确列出
3. **在删除之前询问：** “是否应该删除这些现在未使用的元素：[列表]？”

不要留下死代码——它会使未来的读者和代理感到困惑。但在不确定的情况下不要默默删除。当不确定时，询问。

```
识别死代码：
- src/utils/date.ts 中的 formatLegacyDate() — 被 formatDate() 替代
- src/components/ 中的 OldTaskCard 组件 — 被 TaskCard 替代
- src/config.ts 中的 LEGACY_API_URL 常量 — 没有剩余引用
→ 这些可以安全删除吗？
```

## 审查速度

慢速审查会阻塞整个团队。审查的上下文切换成本低于对其他人造成的等待成本。

- **在一天内回复**——这是最大值，不是目标
- **理想的节奏：** 审查请求到达后立即回复，除非深入专注编码。一个典型的变更应该在一天内完成多个审查轮次
- **优先考虑快速的个人回复**，而不是快速的最后批准。即使需要多个轮次，快速反馈也能减少挫败感
- **大变更：** 要求作者拆分它们，而不是审查一个巨大的变更集

## 处理分歧

在解决审查争议时，应用这个层次结构：

1. **技术事实和数据** 优先于意见和偏好
2. **风格指南** 是风格问题的绝对权威
3. **软件设计** 必须根据工程原则进行评估，而不是个人偏好
4. **代码库一致性** 如果它不会降低整体健康度，是可以接受的

**不要接受“我稍后会清理。”** 经验表明，延迟清理很少发生。除非是真正的紧急情况，否则在提交前要求清理。如果无法在这个变更中解决周围的问题，要求以自我分配的方式提交 Bug。

## 审查中的诚实

在审查代码时——无论是由你、另一个代理还是人类编写的：

- **不要走形式。** 没有证据的“LGTM”对任何人都没有帮助。
- **不要淡化真实问题。** “这可能是一个小问题”而它是一个会打到生产的 Bug 是不诚实的。
- **尽可能量化问题。** “这个 N+1 查询将为列表中的每个项目增加 ~50ms”比“这可能很慢”更好。
- **对有明显问题的方法提出反对。** 奉承是审查中的失败模式。如果实现有问题，直接说出来并提出替代方案。
- **如果作者有完整上下文并不同意，要优雅地接受。** 聚焦于代码，而不是人——将个人评论重新聚焦于代码本身。

## 依赖纪律

代码审查的一部分是依赖项审查：

**在添加任何依赖项之前：**
1. 现有堆栈是否解决了这个问题？（通常它已经解决了。）
2. 依赖项有多大？（检查捆绑包影响。）
3. 它是否在积极维护中？（检查最后提交、打开的问题。）
4. 它是否有已知漏洞？（`npm audit`）
5. 许可证是什么？（必须与项目兼容。）

**规则：** 优先选择标准库和现有工具，而不是新的依赖项。每个依赖项都是一种负债。

**升级现有依赖项** 是像任何其他代码变更一样的变更，而风险最大的升级是那些批量合并的，带有“更新依赖项”的消息。用同样的纪律审查它们：

1. **阅读变更日志，而不仅仅是版本号。** Semver 是维护者可能没有遵守的承诺——一个“补丁”可能包含行为变化。对于主要升级，阅读迁移说明并找出什么会破坏。
2. **每个变更一个依赖项。** 逐个升级和合并它们（或小相关的组）。当批量提升破坏构建时，你失去了哪个包做了它；单个包变更使原因明显，并且回滚干净。
3. **让测试做决定。** 升级在 *之前* 和 *之后* 都通过了绿色套件验证，而不是“它安装了”。如果依赖项行为周围的覆盖率很薄，那差距才是真正的发现——先添加测试。
4. **注意传递图。** 大多数安装的包都是没有人直接选择的。审查锁文件差异，而不仅仅是 `package.json`；一个直接的提升可能会引入几十个间接变更。
5. **保持锁文件诚实。** 提交它，审查其差异，并且永远不要手动编辑它。锁文件是实际固定要发布的东西。

对于 `npm audit` 查找的优先级和供应链风险（拼写攻击、受感染的维护者），遵循 `security-and-hardening` 技能——这一部分涵盖升级 *工作流*，那一部分涵盖安全结果。

## 常见理由

| 理由 | 现实情况 |
|---|---|
| "它可行，这就足够了" | 可行的代码如果难以阅读、不安全或架构错误，会产生累积的债务。 |
| "我编写了它，所以我了解它是正确的" | 作者对自己的假设存在盲点。每个变更都需要另一双眼睛。 |
| "我们稍后会清理它" | 后来永远不会到来。审核是质量门槛——利用它。在合并前要求清理，而不是合并后。 |
| "AI 生成的代码可能没问题" | AI 代码需要更多审查，而不是更少。它自信且看似合理，即使错误。 |
| "测试通过了，所以它没问题" | 测试是必要的，但不是充分的。它们不会发现架构问题、安全问题或可读性问题。 |
| "重构使其更清晰" | 将复杂性转移而不是减少。如果读者仍然需要掌握相同数量的概念，结构没有改进——寻找分支消失的版本。 |
| "这只是对文件的微小添加" | 小差异仍然会使文件超出合理大小，并将分支连接到不相关的流程。判断最终结构，而不是差异大小。 |
| "只是版本号更新" | 更新是一个你未编写的变更行为。阅读变更日志；semver 并不保证无破坏。 |
| "我会通过一个 PR 升级所有内容以节省时间" | 批量更新会隐藏导致构建失败的包。每个依赖项一个变更，使原因和还原保持清晰。 |

## 严重警告

- 无审核即合并的 PR
- 仅检查测试是否通过的审核（忽略其他维度）
- 无实际审核的 "LGTM"
- 无安全审核的安全敏感变更
- 太大无法正确审核的 PR（拆分它们）
- 修复 Bug 的 PR 没有回归测试
- 无严重性标签的审核评论——使要求与可选项不明确
- 接受 "我稍后会修复"——它永远不会发生
- 将代码移动位置但不减少读者必须掌握的概念数量的重构
- 使已大文件增大的变更，而不是分解它
- 新条件语句散布到不相关的代码路径中（缺少抽象）
- 定制辅助函数重复了现有的标准辅助函数，或功能逻辑放在共享模块中
- 无变更日志审查且无按包隔离的批量 "更新依赖" PR
- 手动编辑、未提交或未审查其差异的锁文件变更

## 验证

审核完成后：

- [ ] 所有关键问题已解决
- [ ] 所有必须（无前缀）变更已解决或附带理由地推迟
- [ ] 测试通过
- [ ] 构建成功
- [ ] 验证记录已记录（变更内容、如何验证）
- [ ] 依赖项升级已根据其变更日志进行审查，按包隔离，并通过了带有锁文件差异的绿色套件验证

**假定障碍：** 针对每个这些，提出更简单的设计方案；仅在变更主动使结构更糟时将其升级为必须：重构将复杂性转移而不是减少；变更使文件超出大小边界且无分解；将功能逻辑添加到共享模块；现有标准辅助函数的近似重复；隐藏不明确不变量的静默回退。
