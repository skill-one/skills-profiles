# 怀疑驱动开发

## 概述

自信的答案并非正确的答案。长时间的投入会累积背景信息，悄无声息地将假设变成"事实"，而无人察觉。怀疑驱动开发是一种在产生任何非平凡的输出之前，创造出一位以**证伪**而非**认可**为偏见的全新背景信息审查者的纪律。

这不是`/review`。`/review`是对一个已完成工件的评价。这是一种飞行中的姿态：非平凡的决策在课程纠正仍然廉价时受到交叉审查。

## 何时使用

当至少满足以下条件之一时，决策为**非平凡**：

- 它引入或修改了分支逻辑
- 它跨越了模块或服务边界
- 它断言了类型系统或编译器无法验证的属性（线程安全、幂等性、顺序、不变性）
- 它的正确性取决于未来读者无法看到的背景信息
- 它的破坏范围是不可逆的（生产部署、数据迁移、公共 API 更改）

在以下情况应用该技能：

- 即将做出不确定性下的架构决策
- 即将提交非平凡代码
- 即将声称一个非显而易见的事实（"这是安全的"、"这是可扩展的"、"这符合规范"）
- 正在处理自己不完全理解的代码

**何时不使用**：

- 机械操作（重命名、格式化、文件移动）
- 遵循一个清晰、无歧义的用户指令
- 阅读或总结现有代码
- 单行更改且正确性显而易见
- 纯粹的工具操作（运行测试、列出文件）
- 用户明确要求速度而非验证

如果你对每个按键都怀疑，你将什么也发不了。该技能仅适用于上述定义的非平凡决策。

## 加载约束

此技能设计用于**主会话协调者**，其中第 3 步（怀疑，详细说明见下文）可以生成一个全新背景信息审查者。

- **不要将此技能添加到角色的`skills:`前端字段。** 一个遵循第 3 步的角色将生成另一个角色——这是`../../references/orchestration-patterns.md`明确禁止的编排反模式（"角色不应调用其他角色"）。
- **如果你发现自己从子代理上下文中应用此技能**（在 Claude Code 防止嵌套子代理生成的情况下）：首选路径是向用户显示怀疑驱动无法运行嵌套，并让主会话处理。作为最后的手段，仅当存在降级的自我提问后备方案——将 ARTIFACT + CONTRACT 重新编写为带有与先前推理的硬心理分界的全新自我提示，并执行步骤 1–5。这**不是全新背景信息审查**（你随身携带自己的背景信息），因此将结果标记为降级，并在用户可联系时优先升级。

## 流程

应用该技能时复制此清单：

```
怀疑循环：
- [ ] 第 1 步：声明 — 写下声明 + 为什么重要
- [ ] 第 2 步：提取 — 隔离工件 + 合约，移除推理
- [ ] 第 3 步：怀疑 — 使用对抗性提示调用全新背景信息审查者
- [ ] 第 4 步：协调 — 将每个发现与工件文本分类
- [ ] 第 5 步：停止 — 满足停止条件（平凡发现、3 个循环或用户覆盖）
```

### 第 1 步：声明 — 揭示所持立场

用两到三行命名决策：

```
声明："新的缓存层在规范中描述的读重负载下是线程安全的。"
为什么重要：这里发生竞争会损坏用户数据，在 QA 中难以检测。
```

如果你无法如此简洁地写出声明，你有的只是一个感觉，而不是一个决策。在审查它之前先揭示它。

### 第 2 步：提取 — 最小的可审查单元

全新背景信息审查者需要**工件**和**合约**，而不是过程。

- 代码：差异或函数——不是整个文件
- 决策：3–5 句话的提议加上它必须满足的约束
- 断言：声明加上据称支持它的证据（与第 1 步的声明块区分开来，后者是审查者正在审查的协调者的假设）

移除你的推理。如果你传递结论，你将得到对你结论的验证。单元必须足够小，以便审查者可以在一次阅读中将其保持在脑海中——如果是一个 500 行的 PR，请先进行分解。

### 第 3 步：怀疑 — 调用全新背景信息审查者

审查者的提示**必须是对抗性的**。措辞决定答案。

```
对抗性审查。找出这个工件有什么问题。
假设作者是过于自信的。寻找：
- 未声明的假设
- 未处理的边缘情况
- 隐藏的耦合或共享状态
- 合约可能被违反的方式
- 可能会破坏现有约定的方式
- 意外输入下的故障模式

不要验证。不要总结。找出问题，或者在彻底检查后明确声明无法找到任何问题。

工件：<粘贴工件>
合约：<粘贴合约>
```

**仅传递工件 + 合约。不要传递声明。** 传递给审查者你的结论会使其倾向于同意。审查者必须独立确定工件是否满足合约。

在 Claude Code 中，`agents/` 中的基于角色的审查者设计上具有隔离的上下文，可用于此处——请参阅 `agents/` 获取花名册和按域匹配。

**上述对抗性提示优先于角色的默认响应形状。** 像 `code-reviewer` 这样的角色被编写为生成包含优缺点的平衡裁决；怀疑驱动需要仅输出问题的输出。将对抗性提示逐字粘贴到调用中以覆盖角色的默认值。如果角色的响应形状无法干净地覆盖，则回退到带有对抗性提示的通用子代理。

#### 跨模型升级

单个模型审查者与原始作者共享盲点——一个更冷、不同架构的模型可以捕捉到它们。怀疑驱动已经针对非平凡决策是自愿的，所以在该范围内提供跨模型是技能价值的一部分，而不是可选的摩擦。

**交互式会话：始终提供。永远不要无声地跳过。**

**第 1 步：询问用户**

在上述第 3 步的单模型审查完成后，但在协调之前，暂停并询问：

> *"单模型审查完成。需要跨模型第二意见吗？选项：Gemini CLI、Codex CLI、手动外部审查（你将其粘贴到其他地方），或跳过。"**

这个问题在每次交互式怀疑循环中都是强制性的——即使是感觉风险较低的工件也是如此。用户——而不是代理——决定成本是否值得。代理的工作是展示选择。

**第 2 步：如果用户选择 CLI —— 验证，然后调用**

1. 检查工具是否在 PATH 中（`which gemini`，`which codex`）。
2. 在传递完整提示之前测试它是否工作（`gemini --version` 或等效）——陈旧的或损坏的二进制文件可能通过 `which` 但在真实输入上失败。
3. 与用户确认确切调用，包括所需的标志、认证和环境变量（例如，API 密钥）。实现方式各不相同；永远不要假设。
4. 仅传递工件 + 合约 + 对抗性提示。没有会话上下文，没有声明。
5. 注意 shell 逃逸。如果工件包含引号、`$(...)` 或反引号，优先使用 stdin（`echo … | gemini`）或 heredoc 而不是内联 `-p "…"`。不确定时，请要求用户在运行之前确认调用。
6. 将输出输入到第 4 步（协调）。

**永远不要将工件插值到 shell 引号参数中。** 代码、Markdown 和审查提示通常包含反引号、`$(...)` 和引号字符，这些字符将要么截断提示，要么执行嵌入的 shell。将完整提示写入文件并通过 stdin 传递。

示例形状（验证标志与你的安装工具——语法在不同的实现和版本中有所不同）：

```bash
# 首先将对抗性提示 + 工件 + 合约写入临时文件。
# 然后通过 stdin 传递，以便工件中的 shell 逃逸字符保持惰性。

# Codex（只读沙盒阻止 CLI 写入你的工作区）：
codex exec --sandbox read-only -C <repo-path> - < /tmp/doubt-prompt.md

# Gemini ('--approval-mode plan' 是只读的；'-p ""' 触发非交互模式
# 并且提示从 stdin 读取）：
gemini --approval-mode plan -p "" < /tmp/doubt-prompt.md
```

只读沙盒是承重细节：怀疑工件本身可能包含指令（有意或无意的提示注入），否则跨模型 CLI 会执行它们针对你的工作区。

**第 3 步：如果 CLI 不可用或失败**

明确显示失败。提供：手动运行、尝试不同工具或跳过。不要无声地回退到单模型——用户应该知道跨模型没有发生。

**第 4 步：如果用户跳过**

在输出中确认跳过（*“仅使用单模型发现继续”*）并继续到协调。跳过是好的；无声跳过是不好的。

**非交互式上下文**（CI、`/loop`、自主循环、计划运行）：

- 跨模型**被跳过**，并且必须在输出中**宣布**：*"跨模型跳过：非交互式上下文。*
- **永远不要在未经明确用户授权的情况下调用外部 CLI**——这是承重安全属性。

跨模型增加了成本、延迟和工具脆弱性。代理在每次怀疑循环中展示选择；用户决定该工件是否值得。代理的工作是展示选择，而不是限制它。

### 第 4 步：协调 — 将发现反折

审查者的输出是数据，不是裁决。**你仍然是协调者。** 在对每个发现进行分类之前，重新阅读工件文本——盲目接受审查与忽略它是一样的失败模式。

对于每个发现，按此**优先级顺序**（第一个匹配的类别胜出）进行分类：

1. **合约误读**——审查者明确指出你提供的合约不明确或不完整。首先修复合约，然后在下一个循环中重新分类。
2. **有效且可操作**——真实问题需要更改工件。更改它，重新循环。
3. **有效权衡**——问题是真实的，但修复成本超过接受成本。明确记录权衡，以便用户看到。
4. **噪音**——审查者指出的是在审查者没有背景信息的情况下实际上是正确的东西。记录它，继续前进，并询问：将背景信息添加到合约是否可以防止虚假标志？

全新的审查者可能会因为缺乏背景信息而犯错。不要因为它是"全新的"就推迟。

### 第 5 步：停止 — 有界循环，不是递归

在以下情况下停止：

- 下一轮仅返回平凡或已考虑过的发现，**或**
- 3 个循环完成（升级到用户，不要独自进行第四轮），**或**
- 用户明确说"发它"

如果经过 3 个循环审查者仍然提出实质性问题，工件可能尚未准备好。向用户展示这一点——3 个未解决的循环是关于工件的信息，而不是继续循环的理由。

如果 3 个循环"明显不足"因为工件太大：工件太大——返回到第 2 步并分解。不要提高界限。

## 常见合理化

| 合理化 | 现实 |
|---|---|
| "我很自信，跳过怀疑步骤" | 对新问题的自信与正确性相关性差。确定性的时刻正是盲点隐藏的时刻。 |
| "生成审查者很昂贵" | 在生产中调试错误的提交更昂贵。检查是有界的；错误不是。 |
| "审查者只会吹毛求疵" | 只有在未限定的前提下。将提示限制为"会导致合约下失败的工件问题"。 |
| "我会在最后用`/review`进行怀疑" | `/review`是最终关卡。怀疑驱动在方向错误时早期捕获，此时纠正仍然廉价。到 PR 时已经太晚了。 |
| "如果我怀疑每一步我就永远不会发布" | 该技能适用于非平凡决策，而不是每个按键。重新阅读"何时不使用"。 |
| "两个意见总比一个好" | 不当。协调，而不是推迟。 |
| "审查者不同意所以我错了" | 审查者缺乏你的背景信息——分歧是信息，不是裁决。重新阅读工件，分类，然后决定。 |
| "跨模型总是更好的" | 跨模型捕获单个模型与自己共享的盲点，但它增加了成本和工具脆弱性。在每次交互式怀疑循环中提供它——用户决定该工件是否值得。代理的工作是展示选择，而不是限制它。 |
| "用户说了一次是，所以我可以继续调用 CLI" | 每次调用都是其自己的授权。工件、提示和标志在调用之间会改变——在每次运行之前与用户确认确切命令。 |
| "用户说了一次是，所以我可以继续调用 CLI" | 每次调用都是其自己的授权。工件、提示和标志在调用之间会改变——在每次运行之前与用户确认确切命令。 |

## 信号灯

- 为单行重命名或格式化更改生成全新背景信息审查者
- 在未重新阅读工件文本的情况下将审查者输出视为权威
- 循环 >3 个循环而未升级到用户
- 使用"这个好吗？"而不是"找出问题"提示审查者
- 在时间压力下对高风险决策跳过怀疑
- 在未更改的工件上重新生成全新背景信息（你会得到相同的发现；你在拖延）
- **怀疑剧场（可检查信号）**：在 2 个或更多循环中，审查者提出了实质性发现，零发现被分类为可操作。你在验证，而不是怀疑。停止并升级。
- 仅在提交后怀疑——那是`/review`，不是怀疑驱动开发
- 在未确认工具存在、配置正确且接受确切语法的情况下硬编码外部 CLI 调用
- **在交互式怀疑循环中无声地跳过跨模型。** 即使不推荐它，提议也必须是可见的。跳过是好的；无声跳过是不好的。
- 当外部 CLI 出错或缺失时无声回退——明确显示失败并让用户重定向
- 从审查者的输入中移除合约
- 将声明传递给审查者（会使其倾向于同意）

## 与其他技能的交互

- **`code-review-and-quality` / `/review`**：互补的。`/review`是事后 PR 裁决；怀疑驱动是每决策的飞行中状态。使用两者。
- **`source-driven-development`**：SDD 验证关于框架的*事实*与官方文档。怀疑驱动验证关于工件的*你的推理*。SDD 检查 API 是否存在；怀疑驱动检查你是否在合约下正确使用它。
- **`test-driven-development`**：TDD 的 RED 步骤是具体的怀疑——失败的测试是证伪尝试。当 TDD 适用时，失败的测试*就是*行为声明的怀疑步骤。
- **`debugging-and-error-recovery`**：当审查者提出真实故障模式时，进入调试技能定位并修复。
- 仓库编排规则（`../../references/orchestration-patterns.md`）：此技能从主会话编排。调用另一个角色是反模式 B——见加载约束上文。

## 验证

应用怀疑驱动开发后：

- [ ] 每个非平凡的决策（根据上述定义）在生效前都明确命名为 CLAIM
- [ ] 每个非平凡工件至少进行一次新上下文审查（TDD 的 RED 步骤产生的失败测试对行为性声明满足此要求，根据与其他技能的交互）
- [ ] 审查者收到的是 ARTIFACT + CONTRACT — 不是 CLAIM，也不是你的推理
- [ ] 审查者的提示是对抗性的（“查找问题”），而不是验证性的（“它好吗”）
- [ ] 发现的问题根据工件文本进行分类（不是盖章通过）使用优先级：合约误读 / 可行动 / 权衡 / 噪音
- [ ] 达到停止条件（平凡发现、3 个周期或用户覆盖）
- [ ] 在交互模式下，跨模型被**明确提供给用户**（无论工件影响如何），并且响应在输出中被确认
- [ ] 在非交互模式下，跨模型被跳过，并且跳过被宣布
- [ ] 任何外部 CLI 调用都先进行 PATH 检查、可工作二进制测试、与用户的语法确认，以及运行授权
