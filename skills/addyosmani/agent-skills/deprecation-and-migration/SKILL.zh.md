# 技术淘汰与迁移

## 概述

代码是一种负债，而非资产。每一行代码都存在持续的维护成本——需要修复错误、更新依赖、应用安全补丁，以及培训新工程师。技术淘汰是指移除那些不再创造价值的代码，而迁移则是将用户安全地从旧系统迁移到新系统的过程。

大多数工程组织擅长构建新事物，但很少擅长移除它们。这项技能正是为了弥补这一差距。

## 使用场景

- 用新系统、API 或库替换旧系统
- 停用不再需要的特性
- 合并重复的实现
- 移除无人拥有但所有人都依赖的废弃代码
- 规划新系统的生命周期（淘汰规划应从设计阶段开始）
- 决定是维护遗留系统还是投资迁移

## 核心原则

### 代码是负债

每一行代码都存在持续成本：需要测试、文档、安全补丁、依赖更新，以及对附近工作的人员造成的认知负担。代码的价值在于它提供的功能，而非代码本身。当相同的功能可以通过更少的代码、更低的复杂度或更好的抽象来实现时——旧代码就应该被移除。

### Hyrum 定律让移除变得困难

用户数量足够多时，任何可观察的行为都会被依赖——包括错误、时序问题和未文档化的副作用。这就是为什么淘汰需要主动迁移，而不仅仅是宣布。当用户依赖的行为被替代方案无法复制时，他们无法“直接切换”。

### 淘汰规划应从设计阶段开始

构建新系统时，要思考：“三年后我们如何移除它？”具有清晰接口、功能开关和最小暴露面的系统，比那些泄漏实现细节到各处的系统更容易被淘汰。

## 淘汰决策

在淘汰任何东西之前，回答以下问题：

```
1. 该系统是否仍然提供独特价值？
   → 如果是，则维护它。如果不是，则继续。

2. 有多少用户/消费者依赖它？
   → 量化迁移范围。

3. 是否存在替代方案？
   → 如果没有，则先构建替代方案。没有替代方案的情况下不要淘汰。

4. 每个消费者迁移的成本是多少？
   → 如果可以轻松自动化，则执行。如果需要手动且高成本，则权衡维护成本。

5. 不淘汰的持续维护成本是什么？
   → 安全风险、工程师时间、复杂性的机会成本。
```

## 强制性淘汰与建议性淘汰

| 类型 | 使用场景 | 机制 |
|------|-------------|-----------|
| **建议性** | 迁移是可选的，旧系统是稳定的 | 警告、文档、提示。用户按自己的时间表迁移。 |
| **强制性** | 旧系统存在安全问题、阻塞进展或维护成本不可持续 | 硬性截止日期。旧系统将在 X 日期前被移除。提供迁移工具。 |

**默认采用建议性。** 只有当维护成本或风险证明必须强制迁移时才使用强制性淘汰。强制性淘汰需要提供迁移工具、文档和支持——你不能只宣布一个截止日期。

## 迁移流程

### 第 1 步：构建替代方案

没有可用的替代方案不要淘汰。替代方案必须：

- 覆盖旧系统的所有关键用例
- 具有文档和迁移指南
- 在生产中得到验证（而不仅仅是“理论上更好”）

### 第 2 步：宣布和文档

```markdown
## 淘汰通知：OldService

**状态：** 自 2025-03-01 起已淘汰
**替代方案：** NewService（见迁移指南）
**移除日期：** 建议性——尚未设定硬性截止日期
**原因：** OldService 需要手动扩展且缺乏可观测性。
            NewService 自动处理这两个方面。

### 迁移指南
1. 将 `import { client } from 'old-service'` 替换为 `import { client } from 'new-service'`
2. 更新配置（见示例）
3. 运行迁移验证脚本：`npx migrate-check`
```

### 第 3 步：逐步迁移

逐个迁移消费者，而不是一次性全部迁移。对每个消费者：

```
1. 确定与淘汰系统所有交互点
2. 更新为使用替代方案
3. 验证行为是否匹配（测试、集成检查）
4. 移除对旧系统的引用
5. 确认无回归问题
```

**更替规则：** 如果你拥有被淘汰的基础设施，你有责任迁移你的用户——或者提供向后兼容的更新以避免迁移。不要宣布淘汰后让用户自行解决。

### 第 4 步：移除旧系统

只有所有消费者都已迁移后：

```
1. 验证零活跃使用（指标、日志、依赖分析）
2. 移除代码
3. 移除相关测试、文档和配置
4. 移除淘汰通知
5. 庆祝——移除代码是一种成就
```

## 迁移模式

### 更替模式

并行运行旧系统和新系统。逐步将流量从旧系统路由到新系统。当旧系统处理 0% 的流量时，移除它。

```
阶段 1：新系统处理 0%，旧系统处理 100%
阶段 2：新系统处理 10%（金丝雀）
阶段 3：新系统处理 50%
阶段 4：新系统处理 100%，旧系统空闲
阶段 5：移除旧系统
```

### 适配器模式

创建一个适配器，将旧接口的调用转换为对新实现的调用。消费者继续使用旧接口，同时你迁移后端。

```typescript
// 适配器：旧接口，新实现
class LegacyTaskService implements OldTaskAPI {
  constructor(private newService: NewTaskService) {}

  // 旧方法签名，委托给新实现
  getTask(id: number): OldTask {
    const task = this.newService.findById(String(id));
    return this.toOldFormat(task);
  }
}
```

### 功能标志迁移

使用功能标志逐个将消费者从旧系统切换到新系统：

```typescript
function getTaskService(userId: string): TaskService {
  if (featureFlags.isEnabled('new-task-service', { userId })) {
    return new NewTaskService();
  }
  return new LegacyTaskService();
}
```

### 数据库模式迁移（扩展/收缩）

模式变更是最危险的迁移，因为数据是无法通过回滚部署来撤销的唯一事物。失败模式是将模式变更与代码变更耦合：在同一发布中重命名列，并在发布窗口期间——当旧代码和新代码同时运行时——其中一个会查询一个不存在的列。解决方法是**永远不要就地更改列**。分阶段迁移，使旧代码和新代码在每一步都有效。

```
扩展 ──────────────→ 迁移 ──────────────→ 收缩
添加新列，    回填现有行，  一旦旧代码不再读取
可空的，并   双写旧+新，  旧列，在稍后的
与旧列并    从应用中，    部署中删除它
列一起
```

**示例——将 `name` 重命名为 `full_name`：**

1. **扩展。** 添加 `full_name` 作为可空列。部署。（旧代码忽略它；不会出问题。）
2. **双写。** 应用在每次插入/更新时写入 `name` 和 `full_name`。部署。
3. **回填。** 批量复制 `name → full_name`，避免锁定表。
4. **切换读取。** 将应用指向 `full_name`，继续双写。部署并固化。
5. **收缩。** 停止写入 `name`，然后在*稍后*的部署中删除列。

每一步都是独立可部署且可逆的：如果第 4 步出问题，回滚代码，`full_name` 仍在被填充。将每一步视为一个薄垂直切片——参考 `incremental-implementation` 技能。

**规则：**
- **先扩展，后收缩。** 扩展（添加新可空列、新表、新索引）在任何部署中都是安全的；删除和重命名需要自己的部署*在*旧形状不再被引用后。
- **每个迁移都有测试的回滚路径。** 无法回滚的迁移是无法回滚的部署。合并前编写并运行 `down`。
- **批量回填，避免热点路径。** 对数百万行进行单个 `UPDATE` 会锁定表；分块并限流。
- **在风险时通过功能标志解耦**，与功能标志迁移模式中完全一样。

## 行尸代码

行尸代码是指无人拥有但所有人都依赖的代码。它未被积极维护，没有明确的负责人，并积累了安全漏洞和兼容性问题。迹象：

- 6 个月以上无提交但存在活跃消费者
- 无分配维护者或团队
- 失败的测试无人修复
- 存在已知漏洞的依赖无人更新
- 文档引用了不再存在的系统

**应对：** 要么分配负责人并正确维护，要么用明确的迁移计划淘汰它。行尸代码不能留在悬停状态——要么获得投资，要么移除。

## 常见借口

| 借口 | 现实 |
|---|---|
| "它还能用，为什么要移除？" | 无人维护的运行代码会积累安全债务和复杂性。维护成本在无声中增长。 |
| "以后可能需要它" | 如果以后需要，可以重建。保留未使用的代码“以防万一”比重建成本更高。 |
| "迁移成本太高" | 比较迁移成本与未来 2-3 年的持续维护成本。迁移通常是长期成本更低。 |
| "完成新系统后我们会淘汰它" | 淘汰规划应从设计阶段开始。到新系统完成时，你会有新的优先事项。立即规划。 |
| "用户会自行迁移" | 他们不会。提供工具、文档和激励——或者自己完成迁移（更替规则）。 |
| "我们可以无限期维护两个系统" | 做同样事情的多个系统是双倍的维护、测试、文档和入职成本。 |
| "只需重命名列，只是一行代码" | 在发布期间，旧代码和新代码会同时运行——其中一个会查询一个不再存在的列。扩展/收缩，永远不要就地重命名。 |
| "我会在同一迁移中添加列并删除旧列" | 这将安全的添加与破坏性的删除耦合。删除需要自己的部署，*在*旧形状不再被引用后。 |
| "如果需要，我们会编写回滚" | 没有回滚路径的迁移是无法回滚的部署。合并前编写并运行 `down`。 |

## 警报

- 没有替代方案的淘汰系统
- 没有迁移工具或文档的淘汰公告
- 多年“软”淘汰但无进展
- 无负责人且活跃依赖的行尸代码
- 在淘汰系统中添加新特性（投资替代方案）
- 未测量当前使用量的淘汰
- 未验证零活跃依赖的代码移除
- 模式变更和依赖它的代码在同一部署中发布
- 就地重命名或删除列而非扩展/收缩
- 没有测试回滚路径的迁移，或锁定表的回填

## 验证

完成淘汰后：

- [ ] 替代方案在生产中得到验证并覆盖所有关键用例
- [ ] 存在迁移指南，包含具体步骤和示例
- [ ] 所有活跃消费者已迁移（通过指标/日志验证）
- [ ] 旧代码、测试、文档和配置已完全移除
- [ ] 代码库中不再存在对淘汰系统的引用
- [ ] 淘汰通知已移除（它们已发挥作用）

数据库模式迁移后：

- [ ] 变更分阶段实施（扩展 → 回填 → 收缩），而非单次就地编辑
- [ ] 旧代码和新代码在每一步都有效
- [ ] 每个迁移都有测试的回滚路径；回填分批限流
- [ ] 破坏性步骤（删除/重命名）在旧形状不再被引用后自己的部署中发布
