# Excalidraw 图表创建器

生成 `.excalidraw` JSON 文件，要求**视觉化论证**，而不仅仅是显示信息。

**设置：** 如果用户要求你设置此技能（渲染器、依赖项等），请参考 `README.md` 获取说明。

## 自定义

**所有颜色和品牌特定样式都位于一个文件中：** `references/color-palette.md`。 在生成任何图表之前阅读它，并将其用作所有颜色选择的唯一真实来源——形状填充、描边、文本颜色、证据工件背景等。

要使此技能以您自己的品牌风格生成图表，请编辑 `color-palette.md`。此文件中的其他内容是通用设计方法和 Excalidraw 最佳实践。

## 核心理念

**图表应该论证，而不是显示。**

图表不是格式化文本。它是一个视觉论证，展示关系、因果关系和流程，这些是文字本身无法表达的内容。形状应该是含义本身。

**同构性测试**：如果你删除所有文本，结构本身是否能够传达概念？如果不能，请重新设计。

**教育性测试**：人们能否从这个图表中学习具体内容，或者它只是标记框？一个好的图表是教学性的——它展示实际格式、真实事件名称、具体示例。

## 深度评估（首先执行此操作）

在设计之前，确定此图表需要什么级别的细节：

### 简单/概念性图表
使用抽象形状，当：
- 解释心智模型或哲学
- 观众不需要技术细节
- 概念本身就是抽象（例如，“关注点分离”）

### 全面/技术性图表
使用具体示例，当：
- 图表一个真实系统、协议或架构
- 图表将用于教学或解释（例如，YouTube 视频）
- 观众需要了解事物实际的样子
- 您正在展示多种技术的集成

**对于技术图表，您必须包含证据工件**（见下文）。

## 研究任务（用于技术图表）

**在绘制任何技术内容之前，研究实际规范。**

如果您正在图表一个协议、API 或框架：
1. 查找实际的 JSON/数据格式
2. 找到真实的事件名称、方法名称或 API 端点
3. 了解各个部分实际如何连接
4. 使用真实术语，而不是通用占位符

不好： "协议" → "前端"
好： "AG-UI 发送事件 (RUN_STARTED, STATE_DELTA, A2UI_UPDATE)" → "CopilotKit 通过 createA2UIMessageRenderer() 渲染"

**研究使图表准确且具有教育意义。**

## 证据工件

证据工件是具体的示例，可以证明您的图表是准确的，并帮助观众学习。在技术图表中包含它们。

**证据工件的类型**（根据您的图表选择相关内容）：

| 工件类型 | 使用时机 | 渲染方式 |
|----------|----------|----------|
| **代码片段** | API、集成、实现细节 | 深色矩形 + 语法着色文本（见颜色调板中的证据工件颜色） |
| **数据/JSON 示例** | 数据格式、模式、有效载荷 | 深色矩形 + 着色文本（见颜色调板） |
| **事件/步骤序列** | 协议、工作流、生命周期 | 时间线模式（线 + 点 + 标签） |
| **UI 模拟** | 展示实际输出/结果 | 嵌套矩形模拟真实 UI |
| **实际输入内容** | 展示输入到系统的内容 | 矩形显示样本内容 |
| **API/方法名称** | 真实函数调用、端点 | 使用文档中的实际名称，而不是占位符 |

**示例**：对于关于流式传输协议的图表，您可能需要显示：
- 规范中的实际事件名称（而不仅仅是“事件 1”、“事件 2”）
- 显示如何连接的代码片段
- 流式传输数据实际的样子

**示例**：对于关于数据转换管道的图表：
- 显示样本输入数据（实际格式，而不是“输入”）
- 显示样本输出数据（实际格式，而不是“输出”）
- 如果相关，显示中间状态

关键原则：**展示事物实际的样子**，而不仅仅是它们的名称。

## 多层次架构

全面图表同时操作多个缩放级别。将其视为同时显示国家边界和街道名称的地图。

### 层级 1：摘要流程
简化概述，显示整个管道或流程的概览。通常放置在图表的顶部或底部。

*示例*：`输入 → 处理 → 输出` 或 `客户端 → 服务器 → 数据库`

### 层级 2：部分边界
标记区域，将相关组件分组。这些区域创建视觉“房间”，帮助观众理解哪些内容属于一起。

*示例*：按责任分组（后端 / 前端）、按阶段（设置 / 执行 / 清理）、按团队（用户 / 系统 / 外部）

### 层级 3：部分内的细节
每个部分内的证据工件、代码片段和具体示例。这是教育价值所在。

*示例*：在“后端”部分，您可能显示实际的 API 响应格式，而不仅仅是标记为“API 响应”的框

**对于全面图表，请尽量包含所有三个层级。** 摘要提供上下文，部分组织，细节教学。

### 不好与好

| 不好（显示） | 好（论证） |
|--------------|------------|
| 5 个相等的框，带有标签 | 每个概念都有一个与其行为对应的形状 |
| 卡片网格布局 | 视觉结构匹配概念结构 |
| 装饰文本的图标 | 是含义的形状 |
| 所有内容都在同一个容器中 | 每个概念都有不同的视觉词汇 |
| 所有内容都在一个框中 | 带有选择性容器的自由浮动文本 |

### 简单与全面（了解您需要哪种）

| 简单图表 | 全面图表 |
|----------|----------|
| 通用标签：“输入” → “处理” → “输出” | 具体的：显示输入/输出的实际样子 |
| 命名框：“API”、“数据库”、“客户端” | 命名框 + 实际请求/响应的示例 |
| “事件”或“消息”标签 | 带有规范中实际事件/消息名称的时间线 |
| “UI”或“仪表板”矩形 | 显示实际 UI 元素和内容的模拟 |
| ~30 秒解释 | ~2-3 分钟的教学内容 |
| 观众学习结构 | 观众学习结构和细节 |

**简单图表**适用于抽象概念、快速概览，或者当观众已经了解细节时。**全面图表**对于技术架构、教程、教育内容，或者当您希望图表本身进行教学时是必需的。

## 容器与自由浮动文本

**并非每个文本片段都需要一个形状围绕它。** 默认使用自由浮动文本。仅在它们有目的时才添加容器。

| 当...使用容器 | 当...使用自由浮动文本 |
|--------------|----------------------|
| 它是部分的重点 | 它是标签或描述 |
| 它需要与其他元素进行视觉分组 | 它是支持性细节或元数据 |
| 箭头需要连接到它 | 它描述附近的内容 |
| 形状本身携带含义（决策菱形等） | 字体排印本身创建足够的层次结构 |
| 它在系统中代表一个独特的“事物” | 它是部分标题、副标题或注释 |

**字体排印作为层次结构**：使用字体大小、粗细和颜色来创建视觉层次结构，而无需框。28px 的标题不需要一个矩形围绕它。

**容器测试**：对于每个框内元素，询问“这能否作为自由浮动文本工作？” 如果可以，请移除容器。

## 设计流程（在生成 JSON 之前执行此操作）

### 步骤 0：评估所需深度
在其他任何事情之前，确定是否需要：
- **简单/概念性**：抽象形状、标签、关系（心智模型、哲学）
- **全面/技术性**：具体示例、代码片段、真实数据（系统、架构、教程）

**如果全面**：首先进行研究。查找实际规范、格式、事件名称、API。

### 步骤 1：深入理解
阅读内容。对于每个概念，询问：
- 这个概念**做什么**？（不是它是什么）
- 概念之间存在哪些关系？
- 核心转换或流程是什么？
- **某人需要看到什么才能理解这个概念？**（而不仅仅是阅读关于它的内容）

### 步骤 2：将概念映射到模式
对于每个概念，找到与其行为对应的视觉模式：

| 如果概念... | 使用此模式 |
|------------|------------|
| 产生多个输出 | **扇出**（从中心辐射的径向箭头） |
| 将输入组合为一个 | **收敛**（漏斗、箭头合并） |
| 具有层次结构/嵌套 | **树**（线 + 自由浮动文本） |
| 是一系列步骤 | **时间线**（线 + 点 + 自由浮动标签） |
| 循环或持续改进 | **螺旋/循环**（返回起始点的箭头） |
| 是抽象状态或上下文 | **云**（重叠的椭圆） |
| 将输入转换为输出 | **装配线**（之前 → 处理 → 之后） |
| 比较两个事物 | **并排**（平行对比） |
| 分离为阶段 | **间隙/断开**（部分之间的视觉分离） |

### 步骤 3：确保多样性
对于多概念图表：**每个主要概念都必须使用不同的视觉模式**。不要使用统一的卡片或网格。

### 步骤 4：勾勒流程
在生成 JSON 之前，在脑海中追踪眼睛在图表中的移动。应该有一个清晰的视觉故事。

### 步骤 5：生成 JSON
现在创建 Excalidraw 元素。**见下文关于如何处理大型图表。**

### 步骤 6：渲染和验证（强制执行）
生成 JSON 后，您必须运行渲染-视图-修复循环，直到图表看起来正确。这不是可选的——请参阅下文的**渲染和验证**部分以获取完整过程。

## 大型/全面图表策略

**对于全面或技术图表，您必须逐部分构建 JSON。** 不要尝试一次性生成整个文件。这是一个硬约束——Claude Code 每次响应的输出限制为 ~32,000 个标记，而全面图表很容易超过这个限制一次性。即使它没有，一次性生成所有内容也会导致质量下降。逐部分生成在各个方面都更好。

### 逐部分工作流程

**阶段 1：构建每个部分**

1. **创建基础文件**，包含 JSON 包装器（`type`、`version`、`appState`、`files`）和第一部分的元素。
2. **每次编辑添加一个部分。** 每个部分都得到自己的专有传递——花时间处理它。仔细考虑布局、间距以及此部分与已有内容如何连接。
3. **使用描述性字符串 ID**（例如，`"trigger_rect"`、`"arrow_fan_left"`），以便跨部分引用易于阅读。
4. **按部分命名种子**（例如，部分 1 使用 100xxx，部分 2 使用 200xxx），以避免冲突。
5. **边进行边更新跨部分绑定**。当新部分的元素需要绑定到先前部分的元素时（例如，连接部分的箭头），同时编辑早期元素的 `boundElements` 数组。

**阶段 2：整体审查**

所有部分都就位后，通读完整的 JSON 并检查：
- 跨部分箭头两端的绑定是否正确？
- 整体间距是否平衡，或者某些部分拥挤而其他部分有过多空白？
- ID 和绑定是否都引用实际存在的元素？

在渲染前修复任何对齐或绑定问题。

**阶段 3：渲染和验证**

现在运行渲染-视图-修复循环（见下文）。这是您会发现 JSON 中不明显但存在视觉问题的地方——重叠、裁剪、不平衡的构图。

### 部分边界

根据图表计划中的自然视觉分组规划您的部分。一个典型的大型图表可能分为：

- **部分 1**：入口点/触发器
- **部分 2**：第一个决策或路由
- **部分 3**：主要内容（英雄部分——可能是最大的单个部分）
- **部分 4-N**：其余阶段、输出等

每个部分都应该是独立可理解的：其元素、内部箭头以及与相邻部分的任何跨参考。

### 不要做的事情

- **不要一次性生成整个图表。** 您将遇到输出标记限制，并生成截断、损坏的 JSON。即使图表足够小以适应，分部分生成也会产生更好的结果。
- **不要使用编码代理**生成 JSON。代理不会具有足够的上下文来了解此技能的规则，并且协调开销抵消了任何好处。
- **不要编写 Python 生成器脚本。** 模板和坐标数学看起来有帮助，但引入了一层间接性，使调试更困难。手工制作的 JSON 与描述性 ID 更易于维护。

## 视觉模式库

### 扇出（一对多）
中心元素带有指向多个目标的箭头辐射。用于：来源、PRD、根本原因、中心枢纽。
```
        ○
       ↗
  □ → ○
       ↘
        ○
```

### 收敛（多对一）
多个输入通过箭头合并到一个输出。用于：聚合、漏斗、综合。
```
  ○ ↘
  ○ → □
  ○ ↗
```

### 树（层次结构）
父子分支，带有连接线和自由浮动文本（不需要框）。用于：文件系统、组织结构图、分类。
```
  label
  ├── label
  │   ├── label
  │   └── label
  └── label
```
使用 `line` 元素表示树干和分支，自由浮动文本表示标签。

### 螺旋/循环（连续循环）
按序列排列的元素，带有返回起始点的箭头。用于：反馈循环、迭代过程、演变。
```
  □ → □
  ↑     ↓
  □ ← □
```

### 云（抽象状态）
大小不同的重叠椭圆。用于：上下文、记忆、对话、心智状态。

### 装配线（转换）
输入 → 处理框 → 输出，具有清晰的之前/之后。用于：转换、处理、转换。
```
  ○○○ → [PROCESS] → □□□
  chaos              order
```

### 并排（比较）
两个平行的结构，具有视觉对比。用于：之前/之后、选项、权衡。

### 间隙/断开（分离）
部分之间的视觉空白或障碍。用于：阶段变化、上下文重置、边界。

### 线条作为结构
使用线条（类型：`line`，不是箭头）作为主要结构性元素，而不是框：
- **时间线**：垂直或水平线，间隔处带有小点（10-20px 椭圆），每个点旁边有自由浮动标签
- **树结构**：垂直树干线 + 水平分支线，带有自由浮动文本标签（不需要框）
- **分隔符**：细虚线分隔部分
- **流程脊柱**：中心线，元素与之相关，而不是连接框

```
时间线:           树:
  ●─── 标签 1        │
  │                   ├── 项目
  ●─── 标签 2        │   ├── 子项目
  │                   │   └── 子项目
  ●─── 标签 3        └── 项目
```

线条 + 自由浮动文本通常比框 + 包含文本产生更干净的结果。

## 形状含义

根据它代表的内容选择形状——或者根本不使用形状：

| 概念类型 | 形状 | 原因 |
|----------|------|------|
| 标签、描述、细节 | **无**（自由浮动文本） | 字体排印创建层次结构 |
| 部分标题、注释 | **无**（自由浮动文本） | 字体大小/粗细足够 |
| 时间线上的标记 | 小 `ellipse`（10-20px） | 视觉锚点，不是容器 |
| 开始、触发、输入 | `ellipse` | 柔和的、起点般的 |
| 结束、输出、结果 | `ellipse` | 完成、目的地 |
| 决策、条件 | `diamond` | 经典决策符号 |
| 处理、动作、步骤 | `rectangle` | 包含动作 |
| 抽象状态、上下文 | 重叠的 `ellipse` | 模糊的、云状的 |
| 层次结构节点 | 线条 + 文本（不需要框） | 通过线条创建结构 |

**规则**: 默认不使用容器。仅当形状具有意义时才添加形状。目标是将<30%的文本元素置于容器内。

## 颜色作为意义

颜色编码信息，而非装饰。每个颜色选择都应来自`references/color-palette.md`——语义形状颜色、文本层级颜色和证据工件颜色都在那里定义。

**关键原则**:
- 每个语义目的（开始、结束、决策、AI、错误等）都有特定的填充/描边组合
- 自由浮动的文本使用颜色表示层级（标题、副标题、详细信息——每个层级不同）
- 证据工件（代码片段、JSON示例）使用其自己的深色背景+彩色文本方案
- 始终将较深的描边与较浅的填充搭配以获得对比度

**不要发明新的颜色。** 如果一个概念不适合现有的语义类别，使用主要色/中性色或次要色。

## 现代美学

为了制作干净、专业的图表：

### 粗糙度
- `roughness: 0` — 干净、清晰的边缘。用于现代/技术图表。
- `roughness: 1` — 手绘、有机感。用于头脑风暴/非正式图表。

**默认为 0**，适用于大多数专业场景。

### 描边宽度
- `strokeWidth: 1` — 细腻、优雅。适用于线条、分隔符、微妙的连接。
- `strokeWidth: 2` — 标准。适用于形状和主要箭头。
- `strokeWidth: 3` — 粗体。谨慎使用以强调（主流程线、关键连接）。

### 不透明度
**始终使用 `opacity: 100` 对于所有元素。** 使用颜色、大小和描边宽度来创建层级，而不是透明度。

### 小标记代替形状
用小点（10-20px 椭圆）代替完整形状，作为：
- 时间线标记
- 项目符号
- 连接节点
- 自由浮动文本的视觉锚点

## 布局原则

### 通过规模建立层级
- **英雄**: 300×150 - 视觉锚点，最重要
- **主要**: 180×90
- **次要**: 120×60
- **小**: 60×40

### 间距 = 重要性
最重要的元素周围有最多的空白空间（200px+）。

### 流动方向
引导视线：通常从左→右或从上→下用于序列，径向用于中心辐射。

### 连接是必需的
仅靠位置无法显示关系。如果 A 与 B 相关，则必须有箭头。

## 文本规则

**关键**: JSON `text` 属性仅包含可读文字。

```json
{
  "id": "myElement1",
  "text": "开始",
  "originalText": "开始"
}
```

设置: `fontSize: 16`, `fontFamily: 3`, `textAlign: "center"`, `verticalAlign: "middle"`

## JSON 结构

```json
{
```

## 渲染与验证（强制）

仅凭 JSON 无法判断图表。生成或编辑 Excalidraw JSON 后，您**必须**将其渲染为 PNG，查看图像并修复所见——在一个循环中直到正确。这是工作流程的核心部分，而不是最终检查。

### 如何渲染

```bash
cd .claude/skills/excalidraw-diagram/references && uv run python render_excalidraw.py <path-to-file.excalidraw>
```

这会在 `.excalidraw` 文件旁边输出一个 PNG。然后使用 PNG 上的**阅读工具**实际查看它。

### 循环

生成初始 JSON 后，运行此循环：

**1. 渲染与查看** — 运行渲染脚本，然后阅读 PNG。

**2. 与原始愿景审计** — 在寻找错误之前，将渲染结果与您在步骤 1-4 中设计的进行比较。询问：
- 视觉结构是否与您计划的概念结构匹配？
- 每个部分是否使用了您打算的模式（发散、收敛、时间线等）？
- 视觉流是否按您设计的顺序通过图表？
- 视觉层级是否正确——英雄元素主导，支持元素较小？
- 对于技术图表：代码片段、数据示例等证据工件是否可读且放置得当？

**3. 检查视觉缺陷**:
- 文本被容器裁剪或溢出
- 文本或形状与其他元素重叠
- 箭头穿过元素而不是绕过它们
- 箭头落在错误的元素上或指向空白空间
- 标签模糊不清（未清晰锚定到其描述的对象）
- 元素之间间距不均（应均匀间距）
- 某些部分与过于拥挤的部分之间空白过多
- 文本在渲染尺寸下太小而无法阅读
- 整体构图感觉不平衡或不协调

**4. 修复** — 编辑 JSON 以解决您发现的所有问题。常见修复：
- 当文本被裁剪时加宽容器
- 调整 `x`/`y` 坐标以修复间距和对齐
- 向箭头的 `points` 数组添加中间路径点以绕过元素
- 将标签重新定位到其描述的元素附近
- 调整元素大小以平衡各部分的视觉权重

**5. 重新渲染与查看** — 再次运行渲染脚本并阅读新的 PNG。

**6. 重复** — 继续循环，直到图表通过愿景检查（步骤 2）和缺陷检查（步骤 3）。通常需要 2-4 次迭代。不要在第一次通过后停止，即使没有严重错误——如果构图可以更好，请改进它。

### 何时停止

循环完成时：
- 渲染的图表与您规划步骤中的概念设计匹配
- 没有文本被裁剪、重叠或无法阅读
- 箭头干净地路由并连接到正确的元素
- 间距一致且构图平衡
- 您会感到舒适地向他人展示它，没有任何保留

### 首次设置
如果渲染脚本尚未设置：
```bash
cd .claude/skills/excalidraw-diagram/references
uv sync
uv run playwright install chromium
```

## 质量检查清单

### 深度与证据（技术图表首先检查）
1. **研究完成**: 是否查看了实际规格、格式、事件名称？
2. **证据工件**: 是否有代码片段、JSON 示例或真实数据？
3. **多缩放**: 是否有摘要流程+部分边界+细节？
4. **具体而非抽象**: 展示真实内容，而不仅仅是标记的框？
5. **教育价值**: 他人能否从中学到具体内容？

### 概念
6. **同构**: 每个视觉结构是否与其概念的行为相匹配？
7. **论证**: 图表是否展示了仅凭文本无法展示的内容？
8. **多样性**: 每个主要概念是否使用不同的视觉模式？
9. **避免统一容器**: 避免卡片网格和相等框？

### 容器纪律
10. **最小容器**: 是否有任何框内元素可以用作自由浮动文本？
11. **线条作为结构**: 树/时间线模式是否使用线条+文本而不是框？
12. **字体层级**: 字体大小和颜色是否创建视觉层级（减少对容器的需求）？

### 结构
13. **连接**: 每个关系都有箭头或线条
14. **流动**: 清晰的视觉路径供眼睛跟随
15. **层级**: 重要元素更大/更孤立

### 技术
16. **文本干净**: `text` 仅包含可读文字
17. **字体**: `fontFamily: 3`
18. **粗糙度**: `roughness: 0` 用于干净/现代（除非要求手绘风格）
19. **不透明度**: `opacity: 100` 对于所有元素（无透明度）
20. **容器比例**: <30% 的文本元素应在容器内

### 视觉验证（渲染必需）
21. **渲染为 PNG**: 图表已被渲染并视觉检查
22. **无文本溢出**: 所有文本都适合其容器
23. **无重叠元素**: 形状和文本无意中重叠
24. **均匀间距**: 相似元素具有一致的间距
25. **箭头正确落地**: 箭头连接到预期元素而不与其他元素交叉
26. **在导出尺寸下可读**: 文本在渲染的 PNG 中可读
27. **平衡构图**: 无大的空白区域或拥挤区域
