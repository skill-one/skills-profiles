# 决策记录

该技能拥有名为 `decisions.py` 的注册工具，通过软链接链接到仓库中的 `scripts/decisions.py`。运行 `decisions.py install` 来设置软链接和 CI 检查。该工具通过从当前工作目录向上遍历来查找仓库的 `docs/` 目录，因此可以在仓库中的任何位置运行它：

```sh
python scripts/decisions.py build [--relink]            # 重新生成 INDEX.md (+ 刷新链接)
python scripts/decisions.py check                       # 验证 (CI 安全；如果过时则退出 1)
python scripts/decisions.py promote <name…> [--deref] [--allow-replace]   # 草稿 -> accepted/
python scripts/decisions.py rename-draft-id <name> <NEW>                  # 重新为草稿分配 ID
python scripts/decisions.py migrate-layout              # 单次操作：旧 accepted/<type>/ -> 扁平化
python scripts/decisions.py install [repo]              # 在仓库中采用：软链接 + pre-commit
```

## 布局

所有符合规范的内容都存放在 `docs/decisions/` 下：

```
docs/
  decisions/              # 规范的命名空间 (总称)
    INDEX.md              # 生成的注册表，覆盖 accepted/ + archived/
    README.md             # 人类指南，用于规范 (由 install 构建)
    AGENTS.md             # 代理规则：决策在此处具有约束力 (由 install 构建)
    accepted/             # 接受的编号记录 — 扁平化；`type` 存放在前文
    archived/             # 已退役的记录 (被取代 | 已弃用) — 扁平化
    drafts/               # WIP 候选记录 — 扁平化，4 个大写字母的 ID，不在 INDEX 中
  threat-model.md         # 其他仓库文档保持兄弟关系 — 仍然交叉引用决策
```

| 阶段           | 目录         | ID                                     | 状态                      |
| :-------------- | :---------- | :------------------------------------- | :-------------------------- |
| 候选 (WIP)     | `drafts/`   | 4 个大写字母，助记符 (`CONF`)          | `draft`                     |
| 决策        | `accepted/` | 全局计数器 (`0001`…)                  | `accepted`                  |
| 已退役         | `archived/` | (保留其计数器)                        | `superseded` / `deprecated` |

**类型是开放的** — `type` 是任何小写短链接 (软件：`architecture`，`product`，`security`；治理：`policy`，`legal`，`finance`，`people`，`compliance`，`operations`)。它只存在于前文 — 每个生命周期目录都是扁平的 — 并且当前使用的集合是接受记录所携带的；INDEX 按此分组。仍在旧 `accepted/<type>/` 布局上的仓库运行一次 `python scripts/decisions.py migrate-layout`：文件名 (身份) 在移动过程中保留，因此 `build --relink` 会自我修复每个引用，而 `check` 在找到嵌套记录时始终指向此处。

没有 `proposed` 状态 — "提议" 是打开一个 PR 来将草稿提升的行为。自己创建草稿 ID (主题的助记符)；`check` 强制格式 + 唯一性。通过将纯 ID 作为内联代码进行交叉引用 — `` `0006` `` (决策) 或 `` `CONF` `` (草稿)；永远不要手动编写路径 — `build --relink` 生成并自我修复每个 `docs/*.md` 的链接 (记录、草稿和其他文档如 `threat-model.md`)。

**与 `origin/main` 的冲突会发出警告，但不会阻止。** 唯一性检查针对一个树，所以两个分支可以各自生成 `0044` 并保持绿色，直到它们相遇。因此 `check` 还会读取磁盘上的 `origin/main` 并在 ID 指向不同文件时打印一条 `WARN` 行，以及下一个可用的计数器。它从不获取，从不使运行失败，当该引用不存在时什么也不说 — 刚克隆的仓库或离线机器不会发现问题。

**`promote` 会生成 `origin/main` 持有的内容之外的内容。** 生成是这一面的另一面：它是一个写入操作 — 记录被重命名，其 H1 被重写，每个入站链接被重新路径化 — 所以 `promote` 读取引用而不是在之后报告，并打印它跨越了哪些计数器。留下的空白不是缺口：`check` 读取 `origin/main` 持有的计数器作为持有而不是缺失，并且 rebase 闭合了序列。两个树都没有的数字仍然会失败，并且在没有磁盘引用的情况下两者都表现得与之前完全一样。

**引用已退役记录会发出警告，但不会阻止。** 取代会使记录退役，但以前不会重新读取引用它的文档：一本规则手册依赖于 `0007`，在 `0019` 取代它之后仍然依赖于它。`check` (以及 `build`) 会为每个活文档中的此类引用打印一个 `WARN`，命名后继者。它永远不会使运行失败，因为提及可以是故意的历史性的；已归档的记录冻结了历史并引用它们喜欢的任何内容，并且取代旧记录的记录当然可以命名它。

## 编写

复制 `drafts/_template.md` — 唯一的模板。记录生来就是草稿，`promote` 是进入 `accepted/` 的唯一门：它生成计数器，翻转状态，并重写 H1，所以接受记录模板除了提供绕过签名的途径外不会添加任何内容。

写裁决，而不是辩论：

- **引用，不要重述。** 完整的论点存在于链接的线程、备忘录或日志中；记录携带决策、实时理由以及参考资料下的指针。
- **删除没有内容的章节。** 重复决策的推理、未经论证的替代方案表、填充的后果列表 — 删除比填充更好，模板标记了哪些章节可以删除。`check` 读取相同的标记：缺少模板未标记为可删除章节的草稿会失败，因为一个吞噬整个章节的脚本编辑不会留下其他痕迹。模板是您仓库的副本，所以标记是您可以移动的。
- **每个句子都应证明其存在。** 一个陈述事实的扁平句子比一个执行它的段落更好；一个装饰就是声音，每个段落一个装饰就是线索。
- **每条记录只做一项决策。** 一个不断增长的记录通常是多个裁决共享一个文件 — 将它们分开。

故意没有长度规则。一个纯粹的裁决通常适合几十行；一个也携带规范的记录（在某些仓库中，接受的记录就是发布的规范）合法地可以运行几百行。长度是一个需要权衡的症状，而不是一个需要监管的数字；上述要点删除的是填充，这在每个长度上都表现出来。

## 提升草稿

**提升需要明确的个人签名。** 提升是一个最终化、半不可逆的行为 (接受的记录是固定的 — 改变方向需要取代，而不是重写；决策者批准的维护编辑，如清晰度、过时性和跨记录一致性是允许的)。自由地编写和验证草稿；但在当前轮次中，在没有用户的明确许可的情况下，永远不要运行 `promote` — 或其下游步骤 (替换命名占位符、解决线程、重新生成 `INDEX.md`))。不要从相邻的选择中推断出批准 (范围答案、清空的检查清单)；不确定时，请询问。

**接受的决策永远不会引用草稿。** `promote` 强制执行这一点：它拒绝会违反规则的集合，并打印出如何修复它的确切方法 (共同提升，`--deref`，或 `--allow-replace`)，并附带复制粘贴提示。在任何提升之前，工具拒绝 — 或任何取代 — 请阅读 **[references/promotion.md](references/promotion.md)** 了解机制。

提升会改变记录的 ID 和其目录，并且 `promote` 会将两者都传递到树中：H1、每个相对链接 (drafts/ 和 accepted/ 是兄弟)、文本中的助记符以及指向草稿文件的任何拼写路径。它停在 `docs/`，并且永远不会编辑代码 — 一个 4 字母的助记符也读作标识符。`docs/` 外部的提及在运行后列出，供您手动处理；保留任何仅共享名称的标识符。`mdformat` 在提交时重新格式化重写的段落。

## 在仓库中采用此功能

从目标仓库运行此技能的 `decisions.py install [repo]`。(`repo` 默认为当前目录；安装设置 *在那里* — 它不会向上搜索。) 它是幂等的：它填充缺失的内容并重新生成 `INDEX.md`。它执行的操作：

- **软链接** `<repo>/scripts/decisions.py` 到此技能的副本，并 **git 忽略** 该路径 (如果不存在则创建 `.gitignore`) — 软链接是特定于机器的，所以每个克隆都会用 `install` 重新创建它，而不是提交它。
- **构建** `docs/decisions/`：`accepted/`，`archived/`，`drafts/` 及其模板 (唯一的模板)，人类 `README.md`，以及面向代理的 `AGENTS.md`。
- **生成** `INDEX.md` (一个构建工件，不是启动器)。
- **连接根入口点** — 当仓库没有根 `README.md` 或 `AGENTS.md` (新仓库或空仓库) 时，创建每个作为占位符，链接到构建，以便人类和代理发现它。现有文件保持不变 (见下文)。
- 在 git 仓库中，添加一个运行 `decisions.py check` 的 `pre-commit` 钩子；在 CI 中运行相同的命令。

如果仓库已经具有这些入口点，安装会将其保留 — 在您自己中连接构建，以便人类和代理发现它：

- 从仓库的 **贡献者面向** 文档链接构建的 `docs/decisions/README.md` — `CONTRIBUTING.md`，或者如果它仅面向贡献者 (跳过用户面向的 README) — 并指向 `docs/decisions/INDEX.md` 以浏览接受的决策。
- 在仓库根的 `AGENTS.md`/`CLAUDE.md` 中，链接 `docs/decisions/AGENTS.md`，以便代理知道在此处决策是约束性的。

将每个链接保留为一行说明其内容。
