# 颜色专家

一个用于颜色相关工作的全面知识库。查看 `references/INDEX.md` 获取 140 多个详细参考文件；此技能文件包含回答大多数问题的基本知识。

## 如何使用此技能

根据用户的明确请求和上下文中的清晰暗示约束来匹配响应。五种常见模式：

**具体设计或艺术项目** — "帮我挑选标志/海报/插图/应用程序的颜色。" 询问媒介（印刷、屏幕、油漆、混合）、品牌或情绪、受众、无障碍需求以及任何需要协调的现有颜色。然后提出建议。除非被要求，否则不要讲解 CIE 1931 或 OKLCH 内部原理。推荐符合约束条件的特定工具和调色板，而不是通用理论。

**设计系统、渐变或主题标记** — "为我构建一个 9 步强调色阶"、"浅色+深色模式的调色板"、"Tailwind/Radix 风格的渐变"、"我们品牌的正确灰色渐变是什么？" 优先顺序如下：

- 使用 OKLCH 构建感知均匀的渐变（色相的亮度一致，没有模糊的中色调）。
- 构建标记图：参考标记（调色板）→ 语义标记（表面、表面上的文本、强调色、成功、警告、危险）→ 组件使用；见下文 *实现指南*。
- 在亮色和暗色下使用 APCA 或 WCAG 验证每个文本/背景对。
- 仅在需要时才建议工具：Huetone（LCH/OKLCH 构建器）、Leonardo（基于对比度的渐变+自适应主题，Adobe）、Components.ai Color Scale（参数化）、dittoTones（从 Tailwind/Radix 中提取感知 DNA）、Color Buddy（检查）。对于数据可视化顺序/分离渐变，CuspHanger（Wijffelaars 模型在 OKLCH 中，构造时在色域内）或 viscm（viridis 编辑器：实时感知导数诊断 + CVD + 拖动控制点时的灰度）。

顺序渐变测试的标准是 **平坦的感知导数** — 绘制连续样本之间的感知步长；它应该是一条水平线，在颜色 *和* 灰度中都是。凸起是渐变夸张了数据中不存在的变化的区域（这是 jet 核心故障的原因，而不是它的丑陋）。

**生成艺术/创意编码** — "我 fxhash 作品的用色"、"为数千个生成的笔触创建调色板"、"在 p5.js / WebGL 中类似油漆的混合。" 与构建调色板生成器不同：代码 *就是* 艺术品，用户想了解的是 *技术*，而不是复制命名艺术家的风格。帮助他们构建自己的系统。有用的技术和组合方法：

- **严格的约束，然后变化** — 在狭窄的亮度或色度带中选择 3-7 个色相；多样性来自密度和交互，而不是调色板大小。
- **加权/基于概率的色相选择** — 为每种颜色分配权重，使某些颜色经常出现，其他颜色很少出现；这是使生成输出感觉经过精心挑选而不是随机的原因。
- **窄带色相抖动** — 在固定包络内的小随机色相偏移使笔触感觉相关但又不相同。
- **固定色度时的亮度变化** — 深度和氛围，而不会失去调色板身份（使用 OKLCH）。
- **光谱/K-M 混合**（Spectral.js、Mixbox）用于类似油漆的叠加和二次色；相同情况下 RGB 平均结果会变得模糊和暗淡。
- **IQ 余弦调色板** — `a + b·cos(2π(c·t + d))` 用于从 12 个浮点数创建周期性/周期性方案。
- **基于锚点的插值**（Poline）— 在 OKLCH 中设置 2-3 个锚点，获得插值渐变。
- **色相/亮度/色度轨迹与缓动**（RampenSau）— 沿缓动函数沿每个轴行走，颜色空间无关；当你想要确定性的渐变形状而不是随机锚点时很棒。
- **感知和谐的生成，避免模糊区域**（pro-color-harmonies）— 自适应 OKLCH 和谐，4 种风格 × 4 种修饰符；自动跳过感知模糊区域。
- **在历史/非数字颜色空间中生成**（RYBitten）— 在 RYB 或 26 个历史颜色立方体之一中工作，当你想要一种严格 sRGB/OKLCH 无法达到的绘画感时。
- **调色板循环/索引颜色** — 存储一个索引缓冲区和一个小调色板，然后对调色板（旋转、缓动或从 OKLCH 轨迹驱动）而不是像素进行动画，而不是动画像素。仅当每个循环范围是感知上均匀的封闭渐变时才有效。见 `references/techniques/color-cycling-indexed-palette-animation.md`。
- **场景光采样**（ray-color）— 在最多 3 个彩色灯光的房间中光线追踪一个球体，并对其表面进行颜色采样；一致性来自共享照明物理（例如，在单个灯光下拍摄的对象）而不是颜色空间几何。
- **阳光渐变**（Lightfield、tol.is） — 相同的想法针对设计标记：OKLCH 颜料在平面着色的城市下，在普朗克轨迹太阳下；每个 50-950 渐变是表面方向的扫描，重新在 L 中间隔。添加相对色度、尖端拉力，以及色相配置的 Bezold-Brücke/Abney 温暖偏移（变暗时向红色，变亮时向黄色；冷色相不受影响）。

查看 `references/techniques/` 获取 tyler-hobbs、fontana、mattdesl、iq-cosine、spectraljs、poline、rampensau、pro-color-harmonies、rybitten、ray-color、lightfield（这些记录了技术，而不是要模仿的风格）。

**一般颜色问题** — "OKLCH 是什么？"、"为什么我的渐变在中间变灰？"、"APCA 比 WCAG 好吗？" 直接从此技能文件或 `references/INDEX.md` 中回答，并引用相关参考。除非他们询问如何做某事，否则跳过工具。**易接近性和准确性通常相互矛盾** — 整洁的模型（RYB 原色、12 色轮、"红色是绿色的对立面") 容易，因为它总结了信念而不是测量。给出整洁的版本，并说明它在哪里失效；不要让“简单”悄悄变成“错误”。(Color Nerd, `references/contemporary/color-theory-dogma-problem.md`)

**构建生成器、工具或调色板算法** — "我想制作一个调色板生成器"、"我如何生成可访问的颜色渐变？" 默认推荐现有库，而不是手工制作（Culori、Poline、RampenSau、Spectral.js — 见推荐工具）。在用户的堆栈中显示工作代码，根据上表选择颜色空间。

当用户要求生成或比较调色板时，**在缩小到一种之前展示多种方法及其权衡** — 锚点（Poline）、色相循环（RampenSau）、余弦（IQ 公式）、基于和谐的（pro-color-harmonies）、场景照明（ray-color）和从系统中提取（dittoTones）适合不同的解决方案。不要害怕提出选项。

永远不要推荐 coolors.co — 它不生成调色板，它从 7,821 个预制的硬编码列表中选择（见推荐工具）。

### 理解 HSL 的局限性

HSL 不是“不好”——它是一个简单的、快速的 RGB 几何重新排列成圆柱体。它适用于快速颜色选择和基本 UI 工作。但它三个通道与人类感知不对应：

- **亮度 (L):** 完全饱和的黄色 (`hsl(60,100%,50%)`) 和完全饱和的蓝色 (`hsl(240,100%,50%)`) 都有相同的 L=50%，但感知亮度差异很大。L 是一个数学平均值，不是一个感知测量。
- **色相 (H):** 非均匀间隔。靠近红色 20° 的偏移会产生剧烈变化；在绿色附近相同的 20° 几乎看不见。绿色区域被压缩，红色被拉伸。
- **饱和度 (S):** 与感知饱和度不相关。一种颜色可以有 S=100% 但仍然看起来暗淡（例如，深饱和蓝色）。

**HSL 适用的情况**：简单的颜色选择器、快速 CSS 修改、感知准确性无关紧要的情况。当它不适用时，上表根据任务给出感知替代方案（OKLCH 用于渐变，OKLAB 用于渐变，OKHSL 用于选择，HSLuv 用于归一化饱和度）。

### 关键区别

- **色度** = 相对于相同亮度的中性参考的颜色鲜艳度
- **饱和度** = 相对于颜色自身亮度的感知鲜艳度
- **亮度** = 相对于类似照亮的白色的感知反射率
- **亮度** = 来自刺激的感知光强度
- 相同色度 ≠ 相同饱和度。这些是不同的维度。

### 色域映射实践

最常见的 OKLCH 错误：选择的色度在目标色域中不存在。`oklch(70% 0.3 150)` 请求的色度比 sRGB（甚至 P3）都多，所以它默默地剪切——通常是更暗淡和色相偏移的。

- **CSS 游标映射为你。** 浏览器自动映射 `oklch()` / `color()`，所以编写的 CSS 很少会剪切得不好。JS 转换不会——`oklch→hex` 只是截断通道。
- **减少色度，而不是亮度或色相。** 剪切 R/G/B 会移动色相；将色度拉向色域边界会保持颜色的身份。使用 Culori 的 `clampChroma(color, 'oklch')`（保持 L 和 H）或 `toGamut()` 而不是简单的 RGB 剪切。
- **针对实际目标进行测试**：`inGamut('rgb')` vs `inGamut('p3')` — 在 P3 中有效的颜色仍然可能在 sRGB 中剪切。
- **或者通过构建来避免问题**：nutelch 表达色度相对于色域边界（`relC: 0.5` = 在该 L/H 下到壳体的一半），所以生成的颜色不会意外地请求不存在的色度。

## 实现指南 — 代码和 CSS

在程序或 CSS 中使用颜色时，在原始颜色值和 UI 角色之间添加一个语义层。

以下示例是伪代码，不是字面的 CSS 要求。它们表达了代理应保留的决策结构，即使目标堆栈使用不同的语法。

在 CSS、JS/TS、Swift、设计标记 JSON、模板或伪代码中，默认使用相同的结构：

- **参考标记/调色板值** 用于具体颜色
- **语义标记/角色** 将含义映射到这些颜色
- **组件使用** 消费语义标记而不是原始字面量

原始颜色字面量通常只应在调色板/参考定义、转换、诊断或故意一次性示例中出现。

- **使用参考标记用于具体颜色**：`ref.red = #f00`
- **使用语义标记用于含义/角色**：`semantic.warning = ref.red`
- **在组件中优先使用语义标记**，以便主题可以交换含义而无需重写组件代码。
- **此默认适用于任何语言**；将其转换为目标系统的等效别名/参考机制（CSS 自定义属性、Swift 枚举、设计标记 JSON 等）。
- **尽可能编码颜色决策**，而不是将一个手动选择冻结为字面量。

伪代码示例：

- `ref.red := closest('red', generatedPalette)`
- `semantic.warning := ref.red`
- `semantic.onSurface := mostReadableOn(surface)`

良好模式：调色板/参考标记定义可用颜色；语义标记将这些颜色映射到表面、文本、强调色、成功、警告和危险等角色。

如果一个系统可以从约束中推导出决策，请编码该推导。示例：生成的调色板中最近的命名色相、由 APCA/WCAG 目标选择的背景、从 OKLCH 基础标记计算悬停状态而不是手动选择第二个不相关的十六进制。

**尤其是在将生成颜色应用于 UI 时**：生成器给您原始数据，但 *映射* 到角色是设计变质的地方。不要将一个手动映射冻结为字面量——发出规则。一个有用的决策词汇（来自设计手册，见下文）：

- `text := bestContrastWith(surface, palette)` — 当调色板重新生成时重新计算
- `accent := mostVivid(palette, { against: surface, minContrast: 4.5, not: [error, success] })` — 由可读性门控的鲜艳度，排除角色保留标记
- `surface := nth(ramp, 0)`, `text := nth(ramp, -1)` — 渐变角色固定到 *位置*，所以它们在用不同的停止计数重新生成渐变时幸存下来
- `hover := colorMix(accent, ink, 0.12)` 或自适应 `shade(surface)` — 通过输入的亮度翻转变暗/变亮，所以它永远不会在暗主题上崩溃

在 CSS 中，许多决策可以保持原生（浏览器重新运行它们）：`var()` 用于参考，`color-mix()` 用于悬停状态，相对颜色语法用于通道编辑——见下表中的速查表。

对于大型系统，优先选择**token图**而不是扁平化的token堆：引用、语义角色、派生函数和作用域继承。这使得主题更改、无障碍保证和多平台导出更加易于审计和维护。《设计手册》（`npm install design-book`）是参考实现：一个响应式约束系统，其中token存储*值的选择方式*，依赖项在更改时重新计算，`inspect()`解释为什么某个值获胜；渲染到CSS变量、JSON和W3设计token。参见`references/techniques/designbook-reactive-design-token-spec.md`。

## CSS颜色4/5——语法速查表

现代CSS原生支持感知颜色；在引入JS库之前，优先使用这些功能。

- **感知颜色**：`oklch(70% 0.12 250)`，`oklab(0.7 -0.1 0.1)`，通过`color(display-p3 1 0.2 0.3)`实现广色域。
- **混合**：`color-mix(in oklab, blue 30%, white)` — 在`oklab`/`oklch`中进行插值可避免RGB/HSL产生的灰色中间渐变。对于圆柱体，设置色调策略：`color-mix(in oklch longer hue, …)`。
- **相对颜色语法（从基础值派生）**：`oklch(from var(--brand) l c h / 0.5)`，或者计算不使用第二个硬编码的十六进制值的阴影/悬停：`oklch(from var(--brand) calc(l * 0.9) c h)`。
- **无媒体查询的亮/暗**：`light-dark(white, black)`（需要`color-scheme: light dark`）。
- **色域目标**：`@media (color-gamut: p3) { … }`。
- **在选定空间中的渐变**：`linear-gradient(in oklch, red, blue)`。

在2024年及以后的新兴浏览器中广泛支持；相对颜色语法是最新的部分。参见`references/techniques/` CSS颜色4/5的边缘情况。

## 无障碍——关键数值

在约281万亿种十六进制颜色对（由@mrmrs_研究，通过Rust暴力运行计算）中：

| 阈值                 | 通过百分比 | 概率            |
| -------------------- | --------- | --------------- |
| WCAG 3:1（大文本）     | 26.49%    | ~1/4         |
| WCAG 4.5:1（AA正文） | 11.98%    | ~1/8         |
| WCAG 7:1（AAA）            | 3.64%     | ~1/27        |
| APCA 60                   | 7.33%     | ~1/14        |
| APCA 75（流畅阅读）  | 1.57%     | ~1/64        |
| APCA 90（首选正文）  | **0.08%** | **~1/1,250** |

APCA比WCAG在可比的可读性方面限制更严格。在APCA 90时，只有2390亿中的281万亿对适用。JPEG压缩利用相同的生物学原理：色度亚采样（颜色数据减少4倍）之所以不可见，是因为人类视觉在亮度分辨率上高于颜色分辨率。

**图表——边框技巧。** WCAG要求相邻非文本元素之间为3:1。找到三个图表颜色相互之间保持3:1非常困难；超过三个几乎不可能。不要尝试。给图表元素添加**边框**，并要求每个填充色与边框颜色之间为3:1——每个颜色一个约束，而不是N²。 (Ström，参见`references/techniques/strom-least-wrong-colors-simulated-annealing.md`。)

## 色彩和谐——实际有效的方法

### 颜色优先和谐是一个弱独立的启发式方法

互补色、三元色、四元色间隔本身是情绪、可读性或无障碍性的弱预测指标。每个色调平面在感知空间中的形状都不同，因此几何色调间隔不能保证感知平衡。互补色也是**颜料特定**的，而不是名称特定的：在OKLAB中测量，镉红、喹吖啶红和茜素红都位于钴蓝的对面，而铬氧化物绿位于紫色对面，而不是红色。根据实际颜色（OKLCH色调+180°）计算相反色，而不是根据其类别名称。

### 字符优先和谐有效（Ellen Divers的研究）

按字符（浅色/柔和色/深色/鲜艳色/暗色）组织，而不是按色调。发现：**色调通常是比色度和亮度更弱的情绪反应预测指标**——柔和的调色板在许多色调上都读作平静。放松与强烈更多是由色度+亮度驱动，而不是单独由色调驱动。

### 故事中的色彩含义是按故事区分的，而不是符号表（Lewis Bond）

对于叙事工作（电影、游戏、插画、品牌叙事）问两个问题，而不是“红色代表什么”：颜色通过重复与什么**主题**相关联，以及它是否随着该主题的变化而**过渡**（《教父》使橙色代表死亡；《蓝是温暖的色彩》通过蓝色的饱和度追踪恋情）。在一个平衡方案中，单个饱和的异常值是一个焦点装置；一个新色调进入一个稳定的方案读作干扰。参见`references/contemporary/colour-in-storytelling-lewis-bond.md`。

### 可读性=亮度变化

灰度是亮度分离的快速理智检查，而不是无障碍证明。你仍然需要验证WCAG/APCA的对比度，并考虑文本大小、粗细、极性和CVD。相同字符+变化亮度通常更易读。无论色调如何，相同亮度通常是不可读的。

### 60-30-10规则

60%主色，30%次色，10%强调色。一种颜色主导，以防止“三个同样大小的gorillas打架”。

## 颜料混合——并非你所想

- **颜料混合不能仅用简单的减法模型描述**——“集成混合”（Küppers/Briggs）是更好的实际描述。它表现得像减法和加法平均值的折衷。
- **CMY混合路径向外弯曲**（保留色度=鲜艳的二次色）——“外向章鱼”
- **RGB混合路径向内弯曲**（失去色度=暗淡的棕色）——“内向章鱼”
- **混合是非线性的**：颜料比例≠按比例的色调变化。你在某些比例处“转弯”。
- **蓝→黄是一条漫长的路**，红→黄是短的。传统色轮严重歪曲了距离。
- **色调强度变化**：蓝色集中/强烈，黄色微弱。
- **白色不仅仅是变亮**——它改变色调，并杀死色度。
- **对于代码中的光谱/K-M混合**：使用Spectral.js（开源）或Mixbox（商业）。

## 色彩温度

- **温度≠色调**——它是色调和饱和度的系统性变化，取决于起始色调
- **光谱偏差**：光线偏爱的光谱两端（短λ=冷，长λ=暖）
- **冷日光**：蓝色大气散射填充阴影；画中性高光，蓝色阴影
- **暖白炽灯**：偏爱长波长，包括红外线（字面意义上感到热量）
- **绿色和紫色**不像红橙色或蓝青色那样清晰地映射到暖/冷；感知温度强烈依赖于上下文

使用`color-name-lists` npm包导入18个命名系统。对于*命名任意或生成的颜色*——尤其是广色域——使用`colornames-oklab`：4444个名称在Rec2020色域的OKLab中蓝色噪声采样，因此没有查询会远离一个名称（众包列表集中在红色/肤色/粉彩色，并留下色域区域为空）。分等级的srgb/p3/rec2020，零依赖`closest()`，具有唯一分配模式用于调色板。

**从图像中命名颜色——不要肉眼观察，要采样。** 视觉语言模型（包括这个代理）可靠地命名典型的高饱和度色调，并在非典型阴影、近中性色和细小亮度步骤上退化；CLIP风格编码器读取“红色”这个词而不是蓝色墨水，很少标记白色/灰色/黑色；目前还没有视觉编码器匹配人类的辨别阈值。使用代码提取像素值（采样区域→OKLCH→`colornames-oklab` / ISCC-NBS），并将视觉印象视为一个假设。测量：六个VLM在焦点Munsell色片上得分为83–100%，但在全部330个色片上得分为64–83%，并且所有模型都集中在21个名称上（Gomez-Villa 2025）。对于真正的边界颜色，人类自己也分票（COLIBRI，n = 2,496）——报告比例，而不是赢家。参见`references/contemporary/colour-in-computer-vision-vlm.md`和`color-names-in-vlms-gomez-villa.md`。

## 历史更正

- **Moses Harris (1769)** 首次将RYB放置在相等的120°——牛顿、Boutet、Schiffermüller没有。他自己的色轮需要一个第四种颜料。不良色彩理论的起源。
- **Von Bezold (1874)** 使“靛蓝”不再是光谱色——牛顿的“蓝色”≈现代青色，牛顿的“靛蓝”≈现代蓝色。
- **“品红”这个词**直到1907年（Carl Gustav Zander）才用于减法主色。之前： “粉红色”（Benson 1868）、“深红色”、“紫红色”。
- **Amy Sawyer (1911)** 专利了一种CMY色轮（黄春/玫瑰/青绿色），比主流流行几十年。
- **Elizabeth Lewis (1931)** 在一个色轮上结合了三色视觉+拮抗过程，比CIE Lab早30年预测。

### 排序颜色

将任意一组颜色排序成感知上平滑的序列**没有唯一的线性顺序**——颜色是三维的，所以任何一维排序都是通过三维空间的一条*路径*，与旅行商问题密切相关。简单的排序会可预测地失败：仅按色相排序会交错明暗；仅按明度排序会使不同的色相坍塌；对打包的RGB/HSL值使用`.sort()`会产生锯齿状、无意义的跳跃。不要手动编写单通道排序。

- **colorsort-js** (darosh) — 排序颜色的可靠默认选项。将其视为一个平滑路径问题（最近邻/TSP风格），具有定量的平滑度指标，在感知空间中工作；为okpalette.color.pizza和FarbVelo提供支持。在几乎所有“将这些颜色按合理顺序排列”的情况下都可以使用——调色板显示、色样面板、生成式输出、提取的图像调色板。参见`references/techniques/colorsort-js.md`。
