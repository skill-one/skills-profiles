# n8n 子工作流

子工作流是可重用的函数。`执行工作流触发器` 声明输入参数，主体部分执行操作，最后一个节点返回输出。调用者像调用其他节点一样调用它。

这种框架打开了以函数形状为赢的方式：封装、重用、可测试性、可替换性。它是 n8n 中的主要重用机制，不幸的是使用率不高。

没有子工作流，相同的逻辑会在工作流中重复。错误修复发生在多个地方，一个被遗漏，"相同"的副本就会漂移。

## 不可协商项

1. **在构建之前搜索。** 在编写处理通用问题的逻辑之前，检查是否已经存在子工作流。按标签（`search_workflows({ tags: ['subworkflow'] })`，领域标签）和/或关键字（`query: '<keyword>'`）进行过滤。标签是发现机制（n8n 2.27.0+）。
2. **`执行工作流触发器` 使用 "定义下方" 并带有类型字段，而不是传递。** 定义下方是唯一允许代理工具（`fromAi`）和结构化调用者传递值的模式。两个例外：(a) 子工作流特别需要接收二进制（那么它不能直接作为代理工具连接），或者 (b) 子工作流根本不接收任何输入（定义下方至少需要一个字段）。见下文"子工作流输入和输出"。

## 强制性默认值

- **任何可重用的内容都成为子工作流。** 如果一个逻辑块可能在其他地方可能需要，请将其提取出来。例外：简单的包装器（一个 HTTP 调用，没有逻辑）和与这个调用者紧密耦合的块。
- **对于纯逻辑，默认为无状态**（输入→输出，没有外部状态）。对于操作状态的逻辑，构建*故意*有状态子工作流，将操作封装在干净的合同（ORM / 仓库模式）后面。要避免的是*意外的*状态：一个"验证"子工作流在安静地写入日志表。
- **按发现进行标签**：每个子工作流都获得 `subworkflow`，一个领域标签（`customer`），和/或 `tool`。标签是 `search_workflows({ tags })` 过滤的；名称保持简单和描述性（`解析 RFC2822 日期`）。见 `references/NAMING_AND_DISCOVERY.md`。
- **描述包含关键字。** 输入/输出形状 + 代表性术语，以便各种查询都能找到它。
- **当输入合同真正不同时拆分**（二进制与 JSON，同步与异步，不同的认证方案）。不要通过传递 + 内部分支将不同的合同合并到一个触发器下。见 `references/SUBWORKFLOW_PATTERNS.md` "按输入形状拆分"。

## 决策树：这个应该是一个子工作流吗？

```
即将编写一个逻辑块？
├── 这个逻辑块可能可能在另一个工作流中需要？
│   ├── 是 → 提取为子工作流
│   └── 否 → 保持内联
│
├── 这个逻辑块是否 >5 个节点并且概念上是一个东西？
│   └── 如果你想测试性、隔离性或重用，则提取；如果它只是为了更干净的画布，则内联分组（见下文）。
│
├── 这个逻辑块是否处理通用问题（认证、重试、解析、格式化）？
│   └── 几乎可以肯定地提取。这些都是标准的可重用子工作流。
│
└── 这个逻辑块是否执行一个没有逻辑围绕它的 HTTP 调用？
    └── 不要提取。没有子工作流边界是多余的。
```

当唯一的动机是更干净的画布（不是重用、隔离、测试性或代理工具）时，**画布节点组**是仅用于可读性分段的工具：更快（每个调用没有子执行）并且更简单（没有输入/输出合同），逻辑保持内联。将其分组到形成有效组的位置（连接，单个入口/出口）；将过于分支的部分拆分为较小的组或保持未分组（一个便签进行注释，它不分组）。只有在您确实需要重用、隔离、独立测试或代理工具时，才提取到子工作流。见 `n8n-workflow-lifecycle-official` 可读性。

## 无状态与有状态子工作流

两者都是第一类。选择取决于意图和封装。

### 无状态

接收输入，返回输出。输入/输出之外没有 I/O。纯逻辑的默认值。

示例：

- `解析 RFC2822 日期`（标签 `subworkflow`）。输入：日期字符串。输出：ISO 日期或错误。
- `从订阅计算 MRR`（标签 `subworkflow`）。输入：订阅对象。输出：MRR 数字。
- `将发票格式化为 HTML`（标签 `subworkflow`）。输入：发票数据。输出：HTML 字符串。

当您需要再次使用该逻辑时，调用它，而不用担心副作用发生。

### 有状态（故意）

在干净的输入/输出合同后面读取或写入外部状态。与仓库模式相当：子工作流抽象了状态操作，以便调用者以领域术语思考，而不是实现。

示例：

- `按 id 获取客户`（标签 `customer`）。输入：id。输出：客户对象或 `{ ok: false, error: 'not_found' }`。读取数据库。
- `写入客户账单记录`（标签 `customer`，`billing`）。输入：记录。输出：`{ ok: true, id }`。写入数据库。
- `追加审计事件`（标签 `audit`）。输入：事件。输出：`{ ok: true, eventId }`。写入日志存储。
- `发送给值班人员`（标签 `notification`）。输入：通道，消息。输出：`{ ok: true, messageId }`。调用 Slack/SMTP。

构建这些作为子工作流的目的：

- 调用者以领域术语思考（`按 id 获取客户`），而不是存储（`SELECT * FROM customers ...`）。
- 交换它背后的底层存储/API（Postgres → Supabase，原生节点 → HTTP）而无需触摸调用者。
- 幂等性、重试和验证成为子工作流的责任，集中在一个地方。

要避免的是*意外的*状态：一个命名为/描述为纯的子工作流在安静地写入日志表。这会欺骗调用者，他们合理地认为它安全可重试或组合。要么将副作用作为合同的一部分（重命名、记录、返回其结果），要么将其移出。

## 何时提取

两个主要信号：

### 1. 概念一致性

当一个节点块做一件逻辑上的事情，即使未重用，提取也可能值得：

- **可测试性。** 使用固定数据单独运行子工作流。
- **可替换性。** 交换实现不会波及调用者。

仅可读性不是提取的理由：节点组将五个节点压缩为一个标记的框更便宜（没有子执行，没有输入/输出合同）。当您还想测试性、可替换性或重用时，提取。

### 1.5 火并遗忘审计日志模式

> 此处使用审计日志作为具体说明故意有状态模式的火并遗忘模式。**除非用户要求，否则不要向工作流添加审计日志。** 该模式本身（异步发射子工作流，不阻塞它）可以推广到任何副作用：指标、通知等。

一个故意有状态的审计日志子工作流使用 `执行工作流` 的 `waitForSubWorkflow: false` 被调用，以便调用者不会在写入上阻塞。

```
调用者 ──→ [执行工作流：DB 审计日志]
              { title: '收到电子邮件确认',
                description: <序列化数据> }
              waitForSubWorkflow: false
              ↓ (调用者立即继续)
        ──→ [继续下一步]
```

子工作流接收标题和描述，写入日志表（或 Slack，或两者），返回。调用者不等待。审计日志是副作用，不是关键路径。

当用户要求时，在每次有意义的状态转换时发射一个（"收到电子邮件确认"、"用户已验证"、"处理开始"、"资格决定"），以便从日志中重建时间线。

为什么它有价值：

- **免费的观察性。** 每个执行的时间线，当出现问题时。
- **没有耦合。** 实现（DB、Slack、两者）可以改变而无需触摸调用者。
- **默认异步。** `waitForSubWorkflow: false` 意味着审计不会减慢主工作流。

审计日志工作流是正确类型的故意有状态子工作流。副作用是重点。

### 1.7 中间件模式

当 webhook 工作流是 API 形状的，将其视为一个。子工作流成为中间件：小的无状态函数，在主处理程序之前运行，要么传递通过，要么使用 4xx 短路。

```
Webhook
  → [验证 JWT]    # 解码 + 验证；失败时 401
  → [速率限制]    # 检查 + 累加计数；失败时 429
  → IF (所有中间件 ok)
    → 主处理程序逻辑
    → 返回 200
  → ELSE → 返回中间件返回的 4xx
```

规范示例：n8n 内部自定义 JWT 认证。`验证 JWT`（标签 `subworkflow`）接收原始 `Authorization` 标头，解码，验证签名和过期，返回 `{ ok: true, user_id }` 或 `{ ok: false, status: 401, message }`。调用者 IF `ok`，失败时提前响应，成功时继续。

为什么使用子工作流而不是内联：每个需要认证的 webhook 都调用同一个。交换库，旋转签名密钥，或添加刷新令牌逻辑在一个地方。重用目标是精确的，合同很小，并且每个 API 端点的失败响应形状是一致的。

与 `n8n-error-handling-official` 配合使用以获取 4xx/5xx 响应形状，与 `n8n-credentials-and-security-official` 配合使用以处理底层密钥。

### 2. 重复模式

您即将构建之前构建过的东西。停止。搜索。

```
search_workflows({ query: 'date' })
search_workflows({ tags: ['customer'] })
search_workflows({ tags: ['subworkflow'] })
```

如果有匹配项，请使用它。如果没有，请将其构建为子工作流并标记它（`subworkflow`，领域，`tool`），以便下一次搜索找到它。标签约定（`subworkflow`，领域标签，`tool`）是使其发挥作用的东西。

## 当工作流线性且长时，如果大部分工作都在子工作流中，这是可以的

一个工作流可以有 20+ 个节点，但如果它主要是子工作流调用和决策的线性编排，仍然可以阅读。形状（仅因为审计日志节点是"真实步骤之间副作用的有力示例"而显示，仅当用户要求审计日志时才包含它们）：

```
Webhook
  → 审计日志（子工作流）
  → 验证
  → 审计日志（子工作流）
  → IF 认证 ok
    → 查找用户（或子工作流）
    → 审计日志（子工作流）
    → 处理步骤 1（子工作流）
    → 审计日志（子工作流）
    → 处理步骤 2（子工作流）
    → 审计日志（子工作流）
    → 决定资格（子工作流）
    → 审计日志（子工作流）
    → 发送通知（子工作流）
    → 响应
```

每个"逻辑步骤"都是一个子工作流调用。调用者是一个长但线性的叙述，易于自上而下跟随。逻辑存在于子工作流中。

这不是具有 20 个节点的工作流与 20 个内联转换相同的情况。那很难阅读。上述模式是好的，因为：

- 每个节点只有一个目的（调用特定的子工作流）。
- 节点组标记部分，便签进行注释（每 `n8n-workflow-lifecycle-official` "可读性"）。
- 检查一个部分意味着打开它调用的子工作流。那是封装。
- 顶级编排逻辑可见，而无需阅读实现。

如果您的有 15+ 个节点的工作流不是主要由 `执行工作流` 调用和分支组成，则在重用或测试值得时提取更多，并将其余部分内联（节点组）。

## 何时不提取

- **一个 HTTP 调用，没有逻辑。** 一个子工作流只是 `执行工作流 → HTTP 请求 → 返回` 添加了多余的边界。内联它。
- **与调用者的特定形状紧密耦合。** 如果该块接收只有这个调用者产生的深度嵌套输入，提取它只是将耦合重新定位。首先修复数据形状。
- **性能关键的热路径。** 每个子工作流调用都会增加延迟（很小，但真实）。对于高吞吐量工作流，在添加边界之前进行 профилирование。

代理工具的接线在无输入的情况下仍然有效：`toolWorkflow` 接受一个输入映射没有字段的子工作流。代理的唯一决策是是否调用。`n8n-agents-official` `references/TOOLS.md` 中的模式（"零 `fromAi` 参数"）直接适用。

### 其他约定

- **在 `description` 中记录工作流的输入和输出。** 字段名、类型、目的。调用者（人类和代理）通过描述来了解契约。
- **返回一致的结构。** 对于预期的失败（例如，解析错误），返回 `{ success: false, error: '...' }` 而不是抛出异常。调用者可以无包装地分支错误输出。
- **一旦有调用者，将输入模式视为契约。** 添加可选字段是安全的。重命名或删除字段可以执行，但需要小心：枚举所有调用者（`search_workflows` 搜索子工作流的名称 + 手动扫描），在同一变更中迁移它们，并在发布前使用 `validate_workflow` + `get_workflow_details` 进行验证。这里的静默中断很难检测，因为 n8n 不会在未识别的输入字段上报错。子工作流只是看到 `undefined`，调用者一无所知。
- **使用最终的 Set / 编辑字段节点来塑造返回值。** 可选的，有时需要的（当最后一个计算节点包含噪声字段时），并且是子工作流的良好实践，即使不严格要求。它在边界处使返回契约明确，因此读者通过阅读一个节点就能看到 API。这是 `n8n-expressions-official` 中设置节点反模式的合法例外：子工作流最后一个节点的隐式消费者是*所有调用者*，因此设置节点作为显式 API 边界是合理的。将其命名为 `Return` 或 `Return <thing>`。
- **返回自然形状，而不是存储形状。** 拥有数据表、S3 中的文件或任何存储层的子工作流应隐藏该表示从调用者。数组作为数组返回，对象作为对象返回，日期作为 ISO 字符串返回，无论底层存储是 JSON 字符串化文本还是其他内部格式。返回契约是*接口*。存储布局是*实现细节*。

  常见错误：子工作流有一个“新鲜”路径（刚产生数据，自然形状）和一个“缓存”路径（刚从 `_object` 列读取，仍然是字符串化）。错误直觉：将新鲜路径字符串化“以匹配”缓存路径。正确直觉：解析缓存路径，以便两者都返回自然形状。调用者不应该知道他们得到了什么。

对于作为代理工具接线的子工作流，请参阅 `n8n-agents-official` `references/SUBWORKFLOW_AS_TOOL.md`。

## 调用子工作流：`Execute Workflow` 模式

调用方 `Execute Workflow` 节点除了输入/`workflowId` 之外还有两个设置：

- **`mode`** 默认为 `'all'`：子工作流运行**一次**，所有 N 个项目作为输入。项目仍然像其他工作流一样按项目流经节点。将 `mode: 'each'` 设置为运行 N 次子工作流，每次执行一个项目。对于体仅正常处理项目的子工作流，两者是等效的。当子工作流的体假设它看到恰好一个项目时（每次运行的聚合，“这是要操作的客户”逻辑，每次输入应触发一次的最终写入），分割很重要。`mode: 'each'` 匹配该假设，`mode: 'all'` 破坏它。当你确实需要按项目迭代时，优先选择 `mode: 'each'` 而不是子工作流内部的 Loop Over Items 节点。
- **`waitForSubWorkflow`** 默认为 `true`。设置 `options.waitForSubWorkflow: false` 将立即触发调用并继续，子工作流将在后台运行。调用方的下游看不到返回数据。

`mode: 'each'` + `waitForSubWorkflow: false` 是 n8n 提供的**唯一真正的并行化**：N 次子工作流执行分发而不等待，运行并发（仍然受每个实例并发限制和每次调用开销的限制）。适用于“启动 N 个独立任务，稍后轮询/聚合”。例如：为每个项目分发一个长时间运行的任务，在数据表中跟踪每个项目，然后循环直到所有行标记为完成或超时。

对于触发后遗忘的轮询模式，请参阅 `references/SUBWORKFLOW_PATTERNS.md` “触发后遗忘的并行化”。

## 反模式

| 反模式 | 问题所在 | 解决方法 |
|---|---|---|
| 在三个工作流中重复相同的日期解析节点 | 修复发生在两个地方，遗漏第三个 | 提取为单个 `Parse <format> date` 子工作流（标签 `subworkflow`）一次 |
| 在不搜索的情况下构建新的子工作流 | 库增长重复，未来的搜索会找到两者 | 始终先 `search_workflows` |
| 子工作流命名/描述为纯，但静默写入日志表 | 调用者无法推理重试或幂等性，副作用突然袭击他们 | 要么将副作用作为契约的一部分（重命名、记录、返回其结果），要么将其移出 |
| 没有描述的子工作流 | 未来搜索中找不到，没有人知道它做什么 | 设置 `description`，包含输入/输出形状和目的 |
| 命名 `Helper 3` 的子工作流 | 名称无法告诉任何人它做什么 | 动词优先的描述性名称（`Parse RFC2822 date`），请参阅 `n8n-workflow-lifecycle-official` `NAMING_CONVENTIONS.md` |
| 未标记的子工作流 | 不会在任何 `tags` 过滤器下显示，未来的你找不到它 | 通过 `create_workflow` `update_workflow` `addTags` 标记它（`subworkflow`，域，`tool`） |
