# n8n 工作流生命周期

## 六个阶段

1. **计划。** 收集需求，提出澄清问题，搜索现有的工作流/子工作流是否已实现此功能。
2. **构建。** 编写 SDK 代码（具备技能：子工作流、节点配置、表达式、代码节点；可读性部分下方）。使用 `validate_node_config` 作为迭代、调试或单个节点小修改的旁路：清理每个参数的错误，而无需完整图示的噪音。它不是 VALIDATE 中 `validate_workflow` 的替代品。
3. **验证。** `validate_workflow` + `get_workflow_details` 用于连接，然后让用户验证每个节点的凭证并创建任何您无法创建的内容（缺少凭证、文件夹等）。
4. **测试。** 使用 `prepare_workflow_pin_data` 的 `test_workflow`；迭代直到输出符合预期。
5. **发布。** 仅在阶段 3 和 4 清洁后使用 `publish_workflow`。
6. **交接。** 生产交接：如何触发它，它返回什么，需要关注什么，他们应该了解如何很好地使用它。

跳过阶段会产生看起来已完成但在生产中会出错的工作流，或者完全解决错误的问题。三个最常见的跳过情况：

- **计划前构建。** “用户要求 X，我将开始编码” 而不确认 X 的含义，是否已有相同的逻辑作为子工作流，或它属于哪个文件夹/项目。问一个澄清问题比重建更便宜。
- **用户端连接前测试。** 在用户验证每个节点的凭证之前运行 `test_workflow` 会击中错误的服务的 401。将用户端设置作为 VALIDATE 的一部分完成。
- **未测试即发布。** 验证通过意味着 SDK 形式良好；它不代表工作流是正确的。

## 必须遵守的规则

1. **发布前验证和验证。** 在 SDK 代码上运行 `validate_workflow`，然后在每次创建/更新后使用 `get_workflow_details` 检查 `connections` 对象。仅验证会无声地遗漏连接线。`validate_node_config` 是一个单独的每个节点迭代工具，不是此步骤的替代品。
2. **向用户展示已知限制。** 如果文件夹、MCP 访问权限或任何其他限制阻止请求，请明确说明并提出解决方案。不要在错误位置无声地丢弃工作流或报告无法完全满足请求的成功。
3. **在非自动固定下游存在副作用时不测试时询问。** `test_workflow` 自动固定触发器、有凭证的节点和 HTTP 请求节点。其他所有内容（代码、编辑字段、If、等待、执行命令、文件操作、子工作流调用、数据表）都会真实运行。如果其中任何一项会引发用户可见的副作用，请在运行前询问用户。参见 `references/TESTING.md`。

## 强制默认值

- **发布前测试** 使用 `test_workflow` + `prepare_workflow_pin_data`。有关通过触发类型模拟、固定单个节点和副作用表面的信息，请参阅 `references/TESTING.md`。对于您自己监控运行的内部一次性脚本，可以更松散。
- **始终在 `create_workflow_from_code` 上包含 `description`**。1-2 句话捕捉 *什么* 和 *为什么*。参见“可读性”部分下方。

## 验证并不足够

`validate_workflow` 运行模式和形状检查：缺少参数、类型错误、引用不存在节点。它不会捕获：

- `.to()`-inside-`.add()` 连接陷阱（无声丢失的连接线）
- 扇出合并为单个连接
- 合并索引偏移一位
- 没有 `onError: 'continueErrorOutput'` 的错误输出
- 语法上有效但语义上错误的参数（例如，错误的表格 ID、错误的列名）

验证是必要的，但不是充分的。真正的门是：

1. `validate_workflow` 通过。
2. `get_workflow_details` 返回的 `connections` 对象与您的意图匹配。
3. `test_workflow` 在代表性固定数据上产生正确的输出。

只有到那时才调用 `publish_workflow`。

有关完整的发布前检查清单，请参阅 `references/VALIDATION_CHECKLIST.md`。

## 执行模型

n8n 工作流**按顺序、从左到右、从上到下**执行。在画布上看起来并行分支（从一个源到多个下游的扇出）按画布上目标节点的 Y 位置顺序依次运行。没有自动并发。

实际后果：

- 扇出到三个慢速 HTTP 调用按顺序运行；总延迟是总和，而不是最大值。
- “并行”分支在执行顺序中共享工作流状态；下游消费者看到的是最后一个分支留下的内容。
- 对于真正的并发，使用 `mode: 'each'` 和 `waitForSubWorkflow: false` 分发子工作流。参见 `n8n-loops-official` 和 `n8n-subworkflows-official`。

这是平台行为，不是 SDK 奇怪之处。不要围绕假设的并行性设计扇出。

## 命名约定

糟糕的名称会累积：六个月后难以找到的工作流会被复制。

有关完整约定（动词-名词模式、大写字母、前缀），请阅读 `references/NAMING_CONVENTIONS.md`。简短版本：

- **工作流：** 动词优先，作用域。`发送每周客户报告` 而不是 `客户报告发送者`。
- **节点：** 描述它们在此工作流中做什么，而不是节点类型。`获取活跃客户` 而不是 `Postgres1`。
- **子工作流：** 纯描述性名称（`解析 RFC2822 日期`）；在标签中携带类别（`subworkflow`、一个域标签、`tool`），而不是名称前缀。`search_workflows({ tags })` 根据它们过滤。参见 `n8n-subworkflows-official` `references/NAMING_AND_DISCOVERY.md`。
- **标签：** AI 端发现机制（n8n 2.27.0+）。MCP 列表（`list_workflow_tags`）、过滤（`search_workflows({ tags })`）和附加它们（`update_workflow` `addTags`/`removeTags`，自动创建未知名称）。小写，每个工作流 2-4 个。参见 `references/NAMING_CONVENTIONS.md`。

## 可读性：描述、节点组、便签、约定

对于任何超过 5 个节点的 workflow，四个杠杆承载可读性负载：

- **Workflow `description`：** 捕获 *为什么*，包括 AI 衍生的上下文。两句话：它做什么和它为什么存在。最重要的是，捕获在对话期间拥有的上下文，这些上下文不会以其他方式保留到文件中（驱动设计的约束、为什么选择这种方法而不是替代方案、用户提出请求的原因）。否则它将随聊天而消亡。
- **节点组：** 分组的唯一方式。将画布划分为命名的组，每个逻辑步骤一个（`验证输入`、`丰富订单`、`通知`），通过 `update_workflow` `setNodeGroups`（n8n 2.28.0+）。超过 10 个节点的每个逻辑步骤分组。每个组必须是一个连接的、无触发器的运行，只有一个入口和一个出口（n8n 拒绝任何其他内容）；折叠后，workflow 按其步骤而不是其节点阅读。将一个分支太分支化无法形成一个组，将其拆分为每个都合格的较小组，或者保持未分组。仅用于组织，成员按行运行（重用/隔离是子工作流的工作）。

  每个组还接受一个可选的 **`description`** 字符串（当组折叠时显示）。使用它来添加一个关于组做什么的简短总结，特别是对于名称本身无法传达 *为什么* 的组。空白或仅包含空白的描述被忽略。保持描述简洁；它们出现在一个小型折叠标签中。

- **便签：** 注释而不是分组。分组的任务是节点组（上方）。便签是用于注释组无法携带的上下文的附加层：对复杂部分的注释、TODO、警告、触发器的便签。使用 `n8n-nodes-base.stickyNote` 节点，并使用 markdown `content`（`### 标题` 在第一行，1-3 句话的正文）和整数 `color` 1-7。选择一个小调色板并坚持使用（例如，灰色/黄色用于注释，红色用于警告，粉色用于 TODO）；随机颜色传达不了任何信息。
- **节点 `notes` 用于非明显配置。** 解释为什么存在 workaround 或代码节点做什么。不要注释明显的节点。

另外两个注意点：

- **在引入自己的约定之前匹配现有项目约定。** 通过 `search_workflows` + `get_workflow_details` 快速浏览附近几个 workflow，并镜像便签调色板、命名和描述风格。
- **布局在创建/更新时自动应用。** SDK `position` 值对于非便签节点被忽略。便签、节点组和命名是您的可读性杠杆。

## 文件夹管理

在注册实例上，MCP 创建和组织文件夹：`create_folder`、`update_folder`（重命名/移动）、`move_workflows_to_folder`，以及 `create_workflow_from_code` 上的 `folderId` 用于创建时放置。`search_folders` 将名称解析为 ID。

如果用户想要一个不存在的文件夹，请创建它，不要在根目录下构建并报告成功。如果文件夹工具不存在，实例未注册：在 UI 中也阻止文件夹，因此请让用户注册（免费，在设置中），而不是手动创建文件夹。没有工具删除文件夹，项目是只读的。

有关完整协议，请参阅 `references/FOLDER_LIMITATIONS.md`。

## 每个工作流的 MCP 访问权限

每个工作流都有一个 `availableInMCP` 标志。默认值取决于谁创建了它：

- **通过 MCP 创建的 workflow** (`create_workflow_from_code`) 默认为 **MCP 可访问**。无需切换步骤：您可以通过 `search_workflows` 找到它们，并立即对它们进行操作。
- **在 n8n UI 中创建的 workflow** 可以默认关闭。直到用户切换开关，workflow 对您不可见。

这种情况下的首要案例：**用户在 UI 中手动构建了一个 workflow，现在希望您检查或编辑它，但您看不到它。** 在假设它不存在或您在搜索错误的项目之前，请让用户确认 MCP 访问权限已启用。

通过 MCP 调用的子工作流：调用者可以像代码级子工作流一样使用它们，而无需切换。要作为 MCP 暴露 *工具* 调用，需要切换（并且对于 MCP 创建的子工作流默认开启）。

有关完整按情况指南和用户面消息，请参阅 `references/MCP_ACCESS_PER_WORKFLOW.md`。

## 用户端连接（部分为阶段 3）

有一些用户必须做而您不能做的事情，并且它们需要在测试之前完成，否则测试会针对错误的凭证、击中缺失的文件夹或 401。在 VALIDATE 期间作为简短列表展示这些内容，在 TEST 之前：

- **验证每个节点的凭证。** `newCredential('Label')` 仅用于装饰。n8n 自动分配最近编辑的合适类型的凭证，当用户有多个时（生产与暂存 Gmail、两个 API 密钥）会无声地选择错误的凭证。告诉他们：“打开每个使用凭证的节点并确认选择了正确的凭证。”参见 `n8n-credentials-and-security-official` 非谈判 #2。
- **创建缺失的凭证。** 如果用户在聊天中粘贴了秘密或 workflow 需要一个不存在的账户，请命名凭证类型，并让他们在 UI 中创建它。
- **注册文件夹（仅当工具缺失时）。** 文件夹工具需要一个注册实例。如果它们缺失，用户在您可以创建或放置文件夹之前注册（免费，在设置中）；否则您自己处理文件夹。参见 `references/FOLDER_LIMITATIONS.md`。
- **用户创建的 workflow 的 MCP 访问切换。** 通过 MCP 创建的 workflow 默认为 MCP 可访问。切换仅在测试依赖于 UI 创建的 workflow 可从 MCP 调用时才适用。参见 `references/MCP_ACCESS_PER_WORKFLOW.md`。

在确认这些完成后才进行 TEST。

## 交接：生产交接（阶段 6）

在 `publish_workflow` 和干净测试之后，workflow 技术上是活动的，但用户仍然需要足够的上下文才能在生产中实际使用它。将此视为自由职业者到客户的交接：简短、结构化，并面向他们从现在开始如何操作它。

应包括的内容：

- **如何触发。** Webhook URL（现在已发布，是活动的）、计划频率 + 时区、手动触发按钮、子工作流调用者，适用哪种。对于 webhook，将 URL 交给他们。
- **它返回什么/数据去哪里。** 一句话。 “将新行写入 `customers` 表格，” “向调用者返回 JSON，” “触发 on-call Slack 频道。”
- **如何实际调用它，并附带示例。** “使用 `curl -X POST <url> -d '{...}'` 触发 webhook，” “从 UI 手动触发，” “等待直到 09:00 UTC 进行第一次计划运行。”
- **需要关注什么。** 作为警报/错误显示的失败模式、上游服务的速率限制上限，以及当出现问题时首先查看的地方（执行选项卡、错误 workflow、审计日志等）。
- **MCP 访问状态。** 如果您通过 MCP 创建了 workflow，它已经是 MCP 可访问的。让用户知道他们可以在设置中撤销访问权限，如果他们想要将其锁定。如果他们在 UI 中构建了它，他们需要切换 MCP 访问权限，以便任何其他代理可以调用它。
- **他们这边还有任何待办事项。** 如果在聊天中粘贴了令牌，则进行密钥旋转，后续接线您无法触及，便签中留下的已知 TODO。

保持简洁：半打要点，而不是大段文字。用户不应该需要问“好了，接下来做什么？”。

## 反模式

| 反模式 | 问题所在 | 解决方法 |
|---|---|---|
| 在未验证的情况下调用 `publish_workflow` | 出现问题的流程被发布到生产环境 | 验证、确认连接，然后进行测试 |
| 因为请求的文件夹不存在而在根目录创建工作流 | 工作流丢失，用户需要手动拖动它们 | 在构建之前暴露限制 |
| 使用通用节点名称（`HTTP Request1`，`Set2`） | 一个月后工作流难以阅读 | 重命名为描述操作 |
| 在 `create_workflow_from_code` 中缺少 `description` | 工作流在搜索中不可见，维护者没有上下文 | 始终包含 1-2 句话 |
| 询问用户在通过 MCP 创建的工作流上切换 MCP 访问开关 | 浪费用户时间，代理创建的工作流默认为 MCP 可访问 | 仅针对 UI 创建的工作流提及开关，或在用户想要 *撤销* 代理创建工作流的 MCP 访问权限时提及 |
| 在未询问的情况下对具有副作用且未固定的下游工作流运行 `test_workflow` | 真实数据表写入、真实子工作流副作用、真实执行命令输出等。触发器 + 授权节点 + 固定的 HTTP 获取，其他都不行 | 先询问。参见 `references/TESTING.md`。 |
| 15 个节点的 15 节点工作流上没有节点组 | 阅读者必须阅读每个节点才能找到他们想要的内容 | 通过 `setNodeGroups` 按逻辑步骤分组。参见上文的“可读性” |
| 使用便利贴来模拟分组，或使用各种颜色的便利贴 | 分组是节点组的工作 / 颜色变成纯粹的噪音 | 使用 `setNodeGroups` 进行分组；保留便利贴用于标注，每个类别使用一种颜色 |
| `description: "发送 Slack。"` | 从触发器和 Slack 节点看不到任何可见内容 | 包含 *原因* + AI 推导的上下文：“发送每周摘要给创始人。替换了经常被忽略的手动报告。” |
| 将扇出分支设计为好像它们并发执行 | n8n 按照从上到下的 Y 位置顺序依次运行扇出分支。总运行时间是分支的总和，而不是最大值 | 对于真正的并发，通过 `Execute Workflow` 使用 `mode: 'each'` + `waitForSubWorkflow: false` 进行调度。参见 `n8n-subworkflows-official` “Fire-and-forget 并行化” |
