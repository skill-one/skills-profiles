# 验证 OpenSpec 文档

检查完成的文档文字是否与现实相符。新上下文的意义在于审阅者没有看过文字的编写过程，因此不会被说服接受作者的假设。

这项技能只有在用户要求时才会运行。草稿工作由 `write-openspec-docs` 负责；除非用户要求验证通过，否则不要在草稿会话中调用此技能。

## 定义运行范围

1. 确认目标：一个页面、一个 `##` 部分，或一组已更改的声明。如果没有指定目标，请询问。
2. 阅读目标文档树根目录下的 README；其不变量和页面映射是检查的一部分。
3. 每个单元（一个 `##` 部分，或声明的声明列表）一个子代理。一个完整页面由多个并行运行的子代理组成。

## 生成审阅者

通用型子代理。子代理不继承技能，因此提示信息通过路径传递所有内容。填充每个占位符，使每个路径绝对化，并发送：

```
你正在审阅 OpenSpec 的用户文档，在它到达文档所有者之前。成为它遇到的最严格的两个读者：一个持怀疑态度的开发者冷读，和一个打开仓库的事实核查者。

仓库根目录：<绝对仓库根目录>。使用每个工具的绝对路径。

首先阅读：
1. <文档树根目录>/README.md：页面映射和不变量。
2. <绝对仓库根目录>/.agents/skills/write-openspec-docs/writing.md：写作规则。
3. <页面路径>：仅审阅 <部分 "<标题>" | 这些更改的声明：<列表>>；为上下文阅读页面的其余部分。

然后按顺序检查：

1. 事实。每个命令、标志、路径、配置键、输出块、默认值和行为声明。重新运行显示的终端命令：任何只读命令，任何在草稿目录或根本不更改状态的命令。AI 聊天表面的命令（如 /opsx:propose）不能在 shell 中运行；验证其名称和行为与该仓库提供的技能源。检查名称与 src/ 和 CLI 的 --help。输出块必须与命令实际打印的内容匹配。
2. 示例。任何示例规范或更改都必须通过 `openspec validate`。当示例存在于磁盘上时运行它。
3. 结构。标记任何重新解释主题的内容，其规范位置是另一个页面，或破坏文档树 README 中声明的规则的内容。
4. 工作匹配。该单元是否服务于页面上声明的任务（如果标题下有一条简短声明，则为该任务）？到达的读者能否快速获得他们想要的内容？
5. 信任和随意性。标记：宣传或安慰形容词（容易、简单、强大、无缝）、没有显示证据的声明、模糊的概括，而具体事实应该属于的地方、二元对比（“不是 X，而是 Y”）、冒号揭示、重要性夸张、总结结尾、破折号、应该为散文的编号列表，以及连续三个平行有力的句子。

仅报告结果，最严重的问题优先。对于每个问题：引用行号，说明错误，并给出一条线的修复方案。对于每个验证的事实，说明如何验证（运行的命令，或检查的文件和行）。列出任何无法验证的声明及其原因。不要重写单元。如果单元干净，请说明并列出您验证的内容。
```

## 处理报告

- 默认是报告而不是重写：按最严重的问题优先顺序向用户显示结果，每个结果附带引用的行和一条线的修复方案，以及验证的内容和如何验证，以及审阅者无法验证的任何声明。
- 仅在用户要求验证和修复运行或批准结果时应用修复。验证者也可能出错：拒绝应包含您的理由，以便用户可以否决您。
- 如果应用的修复更改了事实声明，请再次验证，范围限定在更改的声明。拼写和措辞修复不需要第二次验证。
- 两次验证没有收敛意味着停止并交由用户处理。不要在循环中抛光。
