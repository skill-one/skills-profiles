# 草稿 OpenSpec 文档 (scratch-plan 工作流)

你正在制作一个用户参与其中的文档页面。该页面计划与审查都在页面内部进行，然后逐个部分进行草稿。在草稿任何内容之前，先加载 `write-openspec-docs`（样式权威）和 `no-ai-slop`。

## 1. 设置草稿部分

将页面剥离到标题和 `>` 目标行，然后在它们下方添加一个工作部分：

```md
## Scratch: 页面计划 (发布前删除)

### 目的

### 结构
```

- **目的**：3-5 个要点。读者是谁，他们来查找什么，页面涵盖什么，链接到什么。在编写之前，检查 `docs-lab/README.md`（页面的目标行）和 `docs-lab/message-map.md`（路由到这里的疑问）。
- **结构**：页面各部分的编号列表，每行一个，命名部分及其内容形状（表格、围栏、树形、项目符号）。
- 说明页面将做什么，而不是它不会做什么。使用平实的语言和简短的项目符号；用户在他们的编辑器中阅读这部分。

## 2. 反复迭代直到计划获得批准

- 计划编辑成本不高；页面编辑成本高。在草稿之前，根据用户的要求多次重塑计划。
- 在聊天中记录每个决策的同时，也在计划本身中记录。为属于其他页面和沿途发现的产品观察添加一个 `### 备注` 列表。
- 用户可以在回合之间直接编辑文件；他们的编辑是决策，而不是需要撤销的漂移。
- 一次只展示一个开放调用，并附带建议。

## 3. 添加草稿计划，然后逐步草稿

一旦结构确定，在备注下方添加一个 `### 草稿计划`：每个页面部分一个步骤，每个步骤都有 ID 和可读的标题（`**D1. 目标行和引言**`），最后是一个整合步骤（跨页面更新）和一个清理步骤。然后：

- 等待用户调用一个步骤 ID。将正好那个步骤草稿到页面上方草稿块的上方。
- 在写入之前，对照来源验证每个事实；廉价的 `grep` 比信任更有效。引用内容以围栏形式显示原始合同（模板、说明、配置），链接到 GitHub 上的文件，而不是进行释义。
- 保持兄弟部分在可重复的子结构上，以便页面扫描为一个系统。
- 在计划中标记步骤 `(done)`，报告已发布的内容，并命名下一个步骤。

## 4. 整合和清理

- **整合**：更新所有指向页面的内容。README 目标行（与页面的 `>` 行逐字匹配），消息映射，同步配置（`website/docs.sync.config.mjs`），以及通过 `grep` 树形找到的任何跨链接。运行 `node website/scripts/sync-docs.mjs` 进行验证。
- **清理**：删除草稿块，在桌面和窄宽度上运行 `write-openspec-docs` 中的可检索性和一瞥测试，如果其散文已发布，则将页面的消息映射行切换为 Answered。
