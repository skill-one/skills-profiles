# 数学奥林匹克解题器

## 影响结果变化的五件事

1. **验证前剥离思维** — 一个验证器如果看到推理就会倾向于认同。新鲜语境，清理证明。
2. **“这能证明黎曼猜想吗？”** — 如果你的定理对 ζ 的特殊化是一个著名的开放问题，你就有漏洞。最可靠的红旗。
3. **短证明→提取通用引理** — 尝试 2×2 反例。如果通用形式是错误的，找出这个实例的特殊之处。
4. **两次出现相同漏洞→退一步** — 情况拆分可能掩盖了一个统一的论证。三行有时能办成十二页做不到的事。
5. **说“没有自信的解”** — 错误且自信比诚实的放弃更糟。

---

**工具策略**：解题器和验证器在紧张的预算工作流程中仅使用思考。竞赛数学是推理。计算用于深度模式（§6c），即使如此也是有限的 — 一个双指数递归在 n~30 之后无法计算，工作模 2^m。

## 何时使用何种方法

| 问题类型                                      | 方法                                                                       | 验证              |
| -------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------- |
| AIME 数值答案                                  | 最佳 N → 多数投票                                                          | 仅答案检查         |
| 奥林匹克证明（IMO/Putnam/USAMO）                    | 完整工作流程见下文                                                            | 5 轮对抗        |
| “这个证明正确吗？”                             | 跳到验证（步骤 4）                                                  | 对抗 + 特性博弈 |
| **完整问题集**（例如，一个竞赛的所有 6 个问题） | 顺序：每个问题一个完整工作流程，收集结果，编译单个 PDF | 每个问题对抗   |

**批量在一个工作流程中**：在每个 `agent()` 调用上设置 `opts.label` 来包含问题 ID（例如，`label: "P3:solver:2"`）。没有标签，36 个结果会回来而没有问题关联。并行运行问题 — 标签是关键，不是顺序。

### 对于完整问题集

为每个问题启动一个解题工作流程（相同的 VERBATIM 提示，不同陈述）。并行运行。所有返回后，对每个问题进行对抗验证。通过验证的问题会将其证明放入 PDF；放弃的问题会得到“没有自信的解”和部分笔记。

不要试图在一个代理的上下文中解决所有 N 个问题 — 每个问题都需要自己的思考预算和自己的新鲜语境验证器。组合是机械的：收集每个问题的输出，填写 LaTeX 部分，编译一次。| “简化这个证明” | 跳到演示（步骤 8） | — |

## 工作流程

### 1. 解释检查（30 秒，捕获一类错误中的 50/63）

在解决任何问题之前，识别解释。

> 阅读问题陈述。列出 2-3 种可能的解释。对于每种：
> 这是一种阅读方式是平凡的吗？如果一个阅读方式让问题变得容易，另一个让问题变得困难，那么困难的方式几乎肯定是意图的。说明你正在解决哪种解释以及为什么你认为它是意图的。

Aletheia 案例研究发现了 63 个“技术上正确”的解中有 50 个是错误的解释。奥林匹克问题通常有一个容易的阅读陷阱。

### 2. 生成候选并内部细化（并行，仅思考）

并行启动 8-12 个尝试代理。**每个代理内部迭代** — 解决 → 自我改进 → 自我验证 → 修正 → 重复。这是 Yang-Huang 结构，在 IMO 上达到 85.7%：一次性解决不够；每次尝试的细化很重要。

**代理工具不能强制工具限制。** 子代理获得完整工具集。唯一的机制是提示。使用此提示 VERBATIM — 不要总结，不要合成你自己的：

```
NO COMPUTATION. 不要使用 Bash、Python、WebSearch、Read、Write 或任何运行代码或获取数据的工具。数值验证不是证明步骤。“我计算了 n=1..10 并且模式成立”不是一个证明。

（如果你的代理框架需要 StructuredOutput 或类似的返回机制工具调用，那不是一个计算工具 — 调用它来返回你的答案。限制是那些真正工作的工具，而不是那些报告工作的工具。）

你的内部过程（迭代直到完成）：
- 解决：完成严格的解决方案。
- 自我改进：重读。在评分者看到之前修复差距。
- 自我验证：严格评分者模式。每一步都有理由吗？
- 修正：修复并重新验证。最多 5 轮。
- 停止：自我验证两次干净，或 5 轮，或方法根本错误。

来自有缺陷推理的正确答案是一个失败。如果不完整，要诚实地说。永远不要隐藏差距。

PROBLEM: <插入问题陈述>
ANGLE: <插入一个起始角度>
```

前两个段落是承重段。一个会写自己的提示并省略它们的会话将产生会磨 Python 30 次并自信得到错误答案的子代理 — 一个模式适合 n≤10 但在 n=100 失败的模式不是证明。

起始角度（跨代理变化 — 见 `references/solver_heuristics.md`）：

- 搞清楚小情况（测试过去 n=3）
- 寻找一个不变量或单变量
- 考虑极值情况
- 尝试归纳法
- 有什么对称性？
- 从后往前工作
- 滑落一个条件 — 它在哪里变得明显错误？
- 一般化（发明者的悖论 — 有时更多结构更容易）

每个代理返回其最终状态（不是中间轮次）：

```
**Verdict**: complete solution | partial result | no progress
**Rounds**: [多少个验证→修正循环]
**Method**: [关键思想，一段话]
**Detailed Solution**: [完整步骤，每一步都有理由]
**Answer**: [如果适用]
**Self-verification notes**: [你捕捉和修复了什么；剩余的担忧]
```

**重试策略**：如果一个代理失败或超时，重试一次。瞬态故障会发生。

### 3. 清理解决方案（上下文隔离 — 第一个杠杆）

思考轨迹使验证器倾向于认同 — 一长串推理看起来像是支持证据，即使结论是错误的。在任何验证之前，剥离：

- 所有思考块内容
- 所有“让我试试…” / “实际上等一下…” / “嗯”散文
- 所有错误的开端和回溯

剩下的：问题陈述 + 干净的最终论证。

仅提取每个解题器输出的 **方法** + **证明** + **答案** 部分。验证器永远不会看到解题器是如何得到那里的。

### 4. 对抗验证（新鲜语境，模式武装）

对于每个清理后的解决方案，启动一个新鲜验证器代理。**新鲜语境**：它只看到（问题陈述 + 清理后的解决方案）。**没有工具。**

验证器的工作是攻击，而不是评分。加载 `references/adversarial_prompts.md` 获取提示。它运行的关键模式：

| 模式 | 检查                                                                                                                                                          |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **#4**  | 这个定理特殊化到一个著名对象（ζ、二次互反律等）并证明了一些关于它的开放问题吗？→ 漏洞                                          |
| **#18** | 将证明的自己的中间身份代入任何“剩余漏洞。” 恢复原始声明吗？→ 重言式                                            |
| **#40** | 任何步骤是一个“单行引理”？提取通用形式。找到一个 2×2 反例。如果通用形式是错误的，找出什么特殊结构挽救了这个实例 |
| **#5**  | 对于每个调用的定理：从头开始重新检查假设。“在 [0,1] 上连续” ≠ “在 ℝ 上连续”                                                              |
| **#6**  | 任何无限和“通过正规化值界定”？检查边界 — 如果在那里有一个极点，和发散                                                 |

完整模式列表：`references/verifier_patterns.md`

验证器返回：

```
**Verdict**: HOLDS | HOLE FOUND | UNCLEAR

**If HOLE FOUND**:
- Location: [引用有问题的步骤]
- Pattern: [哪个检查触发，或“其他”]
- Why it breaks: [具体]
- Fixable?: [是 X / 否，根本]
```

### 5. 排名和投票验证（非对称 + 提前退出）

按（验证结果，验证器置信度）对解决方案进行排名。取第一。运行最多 5 个新鲜验证器代理。

**非对称阈值**：4 HOLDS 确认，2 HOLE FOUND 否定。为什么非对称：一个不可靠的验证器不应该杀死一个正确的证明；但两个独立的异议是一个真正的信号。

**鸽巢提前退出**：一旦结果确定，停止启动验证器。

- 2 说 HOLE FOUND → 否定，停止（节省剩余 3 次调用）
- 4 说 HOLDS → 确认，停止（节省第 5 次）
- 在 3 个验证器之后：如果 2 HOLDS + 1 HOLE，启动 2 个更多（结果未确定）。如果 3 HOLDS + 0 HOLE，启动 1 个更多（仍然可能达到 4-1）。

**双重上下文隔离**：每个验证器对（a）解题器的思考轨迹 — 已经在步骤 3 中剥离 — 和（b）其他验证器的判断都盲目的。每个验证器认为自己是第一个。没有“3 个代理已经确认了这个”社会证明。

**一个解题器不能验证自己的解决方案。** 不同的代理，新鲜语境。

### 5b. 当一个案例无法解决时 — 在磨碎之前退一步

如果一个证明分成几个案例，一个案例很容易证明，另一个抵抗：
**在磨碎困难案例之前，问是否有让拆分消失的路线。**

救你的模式：困难案例的假设往往对中间对象暗示了很强的事情，而你没有看到。直接使用这个暗示，而不是原始链。

具体形状：证明 f(n) ≤ cn 对于一个受约束的函数 f，在除 f(n) 的素数 p 上拆分。一个分支通过 (ℤ/p^e)\* 中的索引论点关闭。另一个分支抵抗 — 相同的群结构，但算术不矛盾。修复：假设“p | f(n)”插入到控制方程中意味着 **f(p) = p 本身**。一旦你有了这个，一个费马+狄利克雷论证在三行内杀死两个分支。案例拆分是一个迂回 — 它是在一个在假设下取已知值的变量上拆分。

在卡住案例 B 时检查：

- 案例B的假设对 f 在_其他输入_上暗示了什么？
- 是否有插入控制方程的不同对 (a,b)？
- 你证明得太多吗？（一个更干净的矛盾需要更少的机制。）

这也是一个演示通过胜利：无案例证明更短，更通用。

### 6. 修订（如果需要）

如果验证器发现一个漏洞：启动一个修订器代理。它得到（清理后的解决方案 + 验证器的漏洞报告）。仍然没有访问原始思考 — 修订器从漏洞开始，而不是通过重读你如何得到那里。

```
一个验证器在证明中发现了这个问题：
[漏洞报告]

修复证明。如果漏洞是根本性的（方法不工作），说这样，并返回 **Verdict: no confident solution** 以及剩余的部分进展。

对于你无法完全关闭的任何步骤，内联标记：[GAP: 具体描述剩余的内容]。证明文本中的差距，而不是单独的列表 — 它们是可搜索的，下一个修订器确切地知道在哪里查找。
```

最多 3 次修订周期。然后重新运行修订证明的投票。

**如果模式 #40 触发**（单行证明太干净），修订器得到一个更强的简报 — 来自 `references/adversarial_prompts.md` §7 的对抗简报模板。它迫使二选一：“通用引理显然是错误的（这里有一个 2×2 反例） — 所以要么找出这个案例的特殊之处，要么找出证明在哪里破裂。” 不能返回“看起来很好。”

### 6c. 深度模式（当紧预算放弃时）

标准工作流程是紧预算：8 解题器，~15 分钟，纯推理。当它放弃时，问题可能需要更多时间，而不是更多能力。

**深度模式**是一个专注的代理，具有：

- **无限时间** — 没有时钟压力
- **允许有针对性的计算** — 模块化算术检查、小案例枚举、符号验证身份。不是探索性暴力或无界递归。
- **放弃的原因作为起点** — 如果验证器发现一个特定漏洞，从这里开始。如果解题器从未声称完整，从他们部分证明的地方开始。

原型：一个专注的代理，获得已证明状态加上“引理 5 中的一个案例是开放的” — 并找到一个三行论证，案例拆分掩盖了它。通常不到 10 分钟几乎没有计算。深度模式是关于给问题持续关注，而不是向它扔计算。

**深度模式不是**：开放式探索、文献搜索、查找解决方案、多天调查。那是不同的工作流程（`math-research`）。深度模式仍然是“自己解决这个问题的” — 只是没有任何时钟。

**NO WEB. NO LOOKUP.** 深度模式可以使用 Bash/Python 进行有界计算，但永远不要使用 WebFetch、WebSearch 或任何网络访问。在 AoPS 或博客上找到解决方案不是解决这个问题的 — 它是在奥林匹克上作弊，它对这个技能的实际能力什么也教不了。将此放在深度模式提示的顶部：

```
NO WEB ACCESS. 不要使用 WebFetch、WebSearch 或任何接触互联网的工具。不要查找这个问题、它的解决方案或相关问题。你自己在解决这个问题 — 唯一允许的计算是本地（Bash/Python 用于模 k 算术，小案例枚举 n≤10，符号身份检查）。如果你调用一个网络工具，证明是无效的。
```

**深度模式中的计算限制**（错误 #8 的教训）：A6 的 b\_{n+1}=2b_n²+b_n+1 是双指数的；b_99 有 ~10^{2^98} 位。永远不要精确计算这样的对象 — 在 ℤ/2^m 中工作，或者跟踪只有 v_p(·)，或者证明递归模你关心的量。如果一个计算运行时间超过 60 秒，它可能是无界的。杀死它并工作在符号上。

**步骤 6d（不是可选的）**：在任何验证阶段的放弃后，自动启动一个深度模式代理，在将放弃写入输出之前。给它：

- 问题陈述
- 紧预算解题器最好的部分证明
- 验证器漏洞描述（具体是什么没有关闭）
- 指令：“NO WEB ACCESS — 不要查找这个问题或它的解决方案。允许有界本地计算（模 2^k，小案例 n≤10，通过 Bash/Python 进行符号身份检查）。60 秒计算限制。如果 n≤10 暴力揭示了一个紧预算解题器遗漏的模式，这个模式就是证明结构。”

深度代理可能会找到纯推理解题器看不到的构造。如果它也放弃，那么写放弃。不要跳过这个步骤 — 有 √n 或 log n 答案的问题通常对纯推理不可见，因为最佳结构是不对称的。

**编排器自我克制**：编排器本身不能搜索问题“以帮助”深度代理。如果你有诱惑去 Fetch 一个 AoPS 论坛“只是检查答案”，不要 — 那会污染技能的输出并歪曲其能力。

### 7. 校准放弃

如果 3 次修订周期都失败：**停止并承认。**

```
**Verdict**: no confident solution

**What was tried**: [方法]
**What WAS proven**: [任何生存验证的引理或部分结果]
**Where it breaks**: [未修复的漏洞]
```

不要猜测。一个错误的自信答案比诚实的“无法解决它”更糟。重要的指标是条件准确性 — 当你说“解决了”时，你是对的吗？

### 8. 演示通过（正确性确定后）

一个经过验证的证明往往不是优美的证明。你发现它的顺序很少是呈现它的最佳顺序。启动一个新的演示代理，并使用已验证的证明。

加载 `references/presentation_prompts.md`。代理会询问：

- 最简单的方式是说清楚这个是什么？
- 哪些引理应该内联？哪些值得单独成段？
- 有什么过度设计的地方吗？（例如，当线性足够时构建双指数）
- 既然我们已经知道答案，有没有一个3行的后见之明证明？

输出：LaTeX格式的证明。如果 `pdflatex` 可用（`scripts/check_latex.sh` 返回 0），也通过 `scripts/compile_pdf.sh` 编译成PDF。

## 这与通用的验证和改进有什么不同

1. **双重上下文隔离**：验证器对（a）求解器的思考轨迹——这会偏向于同意——和（b）其他验证器的判断——社会证明也会产生偏见。每个验证器都认为自己是第一个。
2. **特定模式的攻击**：不是“这个是否正确？”而是“这个是否会导致#40错误？#4错误？”具体优于通用。7类反驳分类法为验证器提供了一个检查清单。
3. **非对称投票+鸽巢退出**：4票确认，2票否决。一个不可靠的验证器不会杀死一个正确的证明；两个反对则会。一旦结果已确定，就停止启动验证器——在明显情况下可节省约30%的验证成本。
4. **规范博弈检查优先**：在求解之前明确询问“这是预期的解释吗？”先前工作的第一个失败模式（63个“正确”答案中有50个求解了错误的阅读）。
5. **校准的放弃**：在部分结果的情况下会说“没有自信的解决方案”。优化条件准确性，而不是覆盖率。
6. **演示步骤**：正确性和优雅性是分开的步骤。演示代理得到已验证的证明，并找到最干净的方式来表达它。
