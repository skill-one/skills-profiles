# 技能创建器

一个用于创建新技能并迭代改进它们的技能。

从高层次来看，创建技能的过程如下：

- 决定你想让技能做什么以及大致应该如何做
- 撰写技能的草稿
- 创建一些测试提示，并在上面运行带有访问权限的 claude
- 帮助用户从定性和定量两个方面评估结果
  - 在后台运行时，如果还没有定量的评估（如果有，你可以直接使用或根据需要修改），起草一些定量的评估。然后向用户解释（或者如果它们已经存在，解释已经存在的评估）
  - 使用 `eval-viewer/generate_review.py` 脚本向用户展示结果供他们查看，并让他们查看定量指标
- 根据用户对结果的评估反馈（以及如果有任何明显的缺陷，这些缺陷从定量基准中变得明显），重写技能
- 重复直到你满意为止
- 扩展测试集并在更大规模上再次尝试

使用这个技能时，你的工作是弄清楚用户在这个过程中的位置，然后跳进来帮助他们完成这些阶段。例如，也许他们想：“我想创建一个用于 X 的技能”。你可以帮助他们缩小范围，撰写草稿，编写测试用例，确定他们想要如何评估，运行所有提示，并重复。

另一方面，也许他们已经有一个技能草稿。在这种情况下，你可以直接进入评估/迭代部分。

当然，你应该始终保持灵活，如果用户说“我不需要运行大量的评估，只需要和我一起感觉一下”，你可以那样做。

然后，在技能完成后（但顺序是灵活的），你还可以运行技能描述改进器，我们有一个完整的独立脚本来优化技能的触发。

酷？酷。

## 与用户沟通

技能创建器可能会被来自编码术语熟悉程度广泛的人群使用。如果你没听说过（而且你怎么会呢，它只是最近才开始），现在有一种趋势，Claude 的能力正在激励水管工打开他们的终端，父母和祖父母谷歌“如何安装 npm”。另一方面，大部分用户可能相当计算机化。

所以请注意上下文线索，以了解如何措辞你的沟通！在默认情况下，只是给你一些想法：

- “评估”和“基准”是边缘的，但可以
- 对于“JSON”和“断言”，你需要在用户明确知道这些术语是什么意思之前，看到他们提供的严肃线索才能使用它们而无需解释

如果你不确定，可以简要解释术语，如果你不确定用户是否理解，可以自由地用简短的定义来澄清术语。

## 创建技能

### 捕获意图

首先，了解用户的意图。当前的对话可能已经包含用户想要捕获的工作流程（例如，他们说“把它变成一个技能”。如果是这样，首先从对话历史中提取答案——使用的工具、步骤的顺序、用户进行的更正、观察到的输入/输出格式。用户可能需要填写空白，并在继续下一步之前确认。

1. 这个技能应该让 Claude 能够做什么？
2. 什么时候应该触发这个技能？（什么用户短语/上下文）
3. 预期的输出格式是什么？
4. 我们是否应该设置测试用例来验证技能是否正常工作？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流步骤）从测试用例中受益。具有主观输出的技能（写作风格、艺术）通常不需要它们。根据技能类型建议适当的默认值，但让用户决定。

### 访谈和研究

主动询问边缘情况、输入/输出格式、示例文件、成功标准以及依赖项。确定这部分内容后，再编写测试提示。

检查可用的 MCPs - 如果对研究有用（搜索文档、找到类似的技能、查找最佳实践），如果有可用的子代理，则并行进行研究，否则内联。做好准备，以减少对用户的负担。

### 编写 SKILL.md

根据用户访谈，填写这些组件：

- **name**：技能标识符
- **description**：何时触发，做什么。这是主要的触发机制——包括技能做什么以及何时使用它的具体上下文。所有“何时使用”的信息都放在这里，而不是在正文中。注意：目前 Claude 有一个趋势，即“技能触发不足”——在它们有用时不会使用它们。为了解决这个问题，请使技能描述稍微“强迫”。例如，不要写“如何构建一个简单的快速仪表板来显示内部 Anthropic 数据。”，你可以写“如何构建一个简单的快速仪表板来显示内部 Anthropic 数据。确保在用户提到仪表板、数据可视化、内部指标或想要显示任何类型的公司数据时使用此技能，即使他们没有明确要求“仪表板。””
- **兼容性**：必需的工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能的构成

```
skill-name/
├── SKILL.md (必需)
│   ├── YAML 前置（name, description 必需）
│   └── Markdown 说明
└── 嵌套资源（可选）
    ├── scripts/    - 用于确定性/重复性任务的执行代码
    ├── references/ - 需要时加载到上下文中的文档
    └── assets/     - 用于输出的文件（模板、图标、字体）
```

#### 逐步披露

技能使用三级加载系统：

1. **元数据**（名称 + 描述）- 始终在上下文中（约 100 字）
2. **SKILL.md 正文** - 技能触发时在上下文中（理想情况下少于 500 行）
3. **嵌套资源** - 按需（无限，脚本可以在不加载的情况下执行）

这些字数是大约的，如果你需要，可以自由地更长。

**关键模式：**
- 保持 SKILL.md 少于 500 行；如果你接近这个限制，请添加额外的层级，并提供清晰的指向，说明使用技能的模型应该去哪里继续跟进。
- 从 SKILL.md 中清晰地引用文件，并指导何时阅读它们
- 对于大于 300 行的大文件，包括目录

**域组织**：当技能支持多个域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md (工作流 + 选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 缺乏惊喜原则

不言而喻，技能不得包含恶意软件、利用代码或任何可能危及系统安全的内容。技能的内容不应在描述时让用户感到意外。不要配合创建误导性技能或设计为促进未经授权的访问、数据泄露或其他恶意活动的技能。像“扮演 XYZ 角色”这样的东西是可以的。

#### 编写模式

在说明中最好使用祈使句。

**定义输出格式** - 你可以这样做：
```markdown
## 报告结构
始终使用这个精确模板：
# [标题]
## 执行摘要
## 关键发现
## 建议
```

**示例模式** - 包括示例很有用。你可以这样格式化它们（但如果“输入”和“输出”在示例中，你可能需要稍微偏离一点）：
```markdown
## 提交信息格式
**示例 1：**
输入：添加用户身份验证，使用 JWT 令牌
输出：feat(auth)：实现基于 JWT 的身份验证
```

### 编写风格

尝试向模型解释为什么这些事情很重要，而不是使用强硬的“必须”。使用心智理论，并尝试使技能具有通用性，而不是针对特定示例。先写一个草稿，然后用新鲜的眼光审视它并改进它。

### 测试用例

在编写技能草稿后，构思 2-3 个现实的测试提示——真实用户实际会说的东西。将它们分享给用户：[你不必使用确切的语言] “这里有我想要尝试的几个测试用例。这些看起来对吗，还是你想添加更多？” 然后运行它们。

将测试用例保存到 `evals/evals.json`。现在还不需要编写断言——只是提示。你将在下一步中起草断言，同时运行正在进行中。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示",
      "expected_output": "预期结果的描述",
      "files": []
    }
  ]
}
```

参见 `references/schemas.md` 获取完整模式（包括 `assertions` 字段，你将在下一步中添加）。

## 运行和评估测试用例

这一部分是一个连续的序列——不要中途停止。不要使用 `/skill-test` 或任何其他测试技能。

将结果放在 `<skill-name>-workspace/` 中，作为技能目录的兄弟目录。在工作区中，按迭代组织结果（`iteration-1/`，`iteration-2/` 等），并在其中，每个测试用例都有一个目录（`eval-0/`，`eval-1/` 等）。不要事先创建所有这些——只是按需创建目录。

### 第一步：在同一轮中生成所有运行（带技能和基线）

对于每个测试用例，在同一轮中生成两个子代理——一个带技能，一个不带技能。这很重要：不要先生成带技能的运行，然后再回来生成基线。立即启动所有内容，以便它们在同一时间完成。

**带技能的运行：**

```
执行此任务：
- 技能路径：<技能路径>
- 任务：<评估提示>
- 输入文件：<如果有，或“无”>
- 保存输出到：<工作区>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 保存输出：<用户关心的——例如，“.docx 文件”，“最终 CSV”>
```

**基线运行**（相同的提示，但基线取决于上下文）：
- **创建新技能**：没有任何技能。相同的提示，没有技能路径，保存到 `without_skill/outputs/`。
- **改进现有技能**：旧版本。在编辑之前，快照技能（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后将基线子代理指向快照。保存到 `old_skill/outputs/`。

为每个测试用例编写 `eval_metadata.json`（断言现在可以为空）。给每个评估一个描述性的名称，基于它正在测试的内容——不仅仅是“eval-0”。也使用此名称作为目录。如果这一迭代使用新的或修改后的评估提示，为每个新的评估目录创建这些文件——不要假设它们从以前的迭代中继承过来。

```json
{
  "eval_id": 0,
  "eval_name": "在此处提供描述性名称",
  "prompt": "用户的任务提示",
  "assertions": []
}
```

### 第二步：在运行进行中，起草断言

不要只是等待运行完成——你可以利用这段时间。为每个测试用例起草定量的断言，并向用户解释。如果断言已经存在于 `evals/evals.json` 中，请审查它们并解释它们检查的内容。

好的断言是客观可验证的，并且具有描述性的名称——它们应该在基准查看器中清晰易读，以便有人快速查看结果时立即了解每个断言检查的内容。主观技能（写作风格、设计质量）最好进行定性评估——不要强迫断言用于需要人类判断的事情。

更新 `eval_metadata.json` 文件和 `evals/evals.json` 文件，添加断言。还向用户解释他们在查看器中会看到什么——包括定性输出和定量基准。

### 第三步：运行完成时，捕获时间数据

当每个子代理任务完成时，你会收到一个包含 `total_tokens` 和 `duration_ms` 的通知。立即将此数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是唯一的机会捕获这些数据——它通过任务通知提供，并且不会保存在其他地方。处理每个通知，而不是尝试批量处理它们。

### 第四步：评分、汇总并启动查看器

一旦所有运行完成：

1. **评分每个运行**——生成一个评分子代理（或内联评分），它读取 `agents/grader.md` 并将每个断言与输出进行比较。将结果保存到每个运行目录中的 `grading.json`。评分.json 期望数组必须使用 `text`、`passed` 和 `evidence` 字段（而不是 `name`/`met`/`details` 或其他变体）——查看器依赖于这些确切的字段名。对于可以编程检查的断言，编写并运行脚本，而不是目测——脚本更快、更可靠，并且可以在迭代中重复使用。

2. **汇总到基准**——运行技能创建器目录中的聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这将生成 `benchmark.json` 和 `benchmark.md`，其中包含每个配置的通过率、时间和令牌，以及均值 ± 标准差和差异。如果手动生成 benchmark.json，请参阅 `references/schemas.md` 以获取查看器期望的确切模式。
将每个带技能的版本放在其基线版本之前。

3. **进行分析师检查**——阅读基准数据并展示汇总统计数据可能隐藏的模式。参见 `agents/analyzer.md`（“分析基准结果”部分）了解要查找的内容——例如，始终通过而不管技能的断言（非区分性）、高变差的评估（可能不稳定）以及时间/令牌权衡。

4. **启动查看器**，同时提供定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于迭代 2+，还传递 `--previous-workspace <workspace>/iteration-<N-1>`。

   **Cowork / 无头环境**：如果 `webbrowser.open()` 不可用或环境没有显示器，使用 `--static <output_path>` 将其写入一个独立的 HTML 文件，而不是启动服务器。反馈将在用户点击“提交所有评论”时下载为 `feedback.json` 文件。下载后，将 `feedback.json` 复制到工作区目录，以便下一次迭代拾取。

注意：请使用 generate_review.py 创建查看器；不需要编写自定义 HTML。

5. **告诉用户**类似：“我已经在您的浏览器中打开了结果。有两个选项卡——“输出”让您可以逐个查看测试用例并留下反馈，“基准”显示定量比较。完成后，请回到这里并告诉我。”

### 用户在查看器中看到的内容

“输出”选项卡一次显示一个测试用例：
- **提示**：给定的任务
- **输出**：技能生成的文件，尽可能内联显示
- **上一个输出**（迭代 2+）：折叠部分显示上一次迭代的输出
- **正式评分**（如果进行了评分）：折叠部分显示断言通过/失败
- **反馈**：一个文本框，在键入时自动保存
- **上一个反馈**（迭代 2+）：他们上次评论，显示在文本框下方

“基准”选项卡显示统计摘要：每个配置的通过率、时间和令牌使用情况，以及每个评估的细分和分析员观察。

导航通过 prev/next 按钮或箭头键。完成时，他们点击“提交所有评论”，将所有反馈保存到 `feedback.json`。

### 第五步：读取反馈

当用户告诉你他们完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "图表缺少坐标轴标签", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "完美，喜欢这个", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈表示用户认为结果可以。请专注于用户提出具体意见的测试用例进行改进。

完成任务后关闭查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是循环的核心。你已经运行了测试用例，用户已经审查了结果，现在你需要根据他们的反馈来改进技能。

### 如何思考改进

1. **从反馈中泛化。** 这里发生的大事是我们试图创建可以在成千上万次（可能字面意义上的，甚至更多谁知道呢）不同提示中使用技能。在这里，你和用户只是在反复迭代几个例子，因为这样能更快地推进。用户对这些例子了如指掌，评估新输出对他们来说很快。但如果你和用户共同开发的技能只在这些例子中有效，那它就毫无用处。与其进行繁琐的过度调整，或施加严苛的限制，如果有些固执的问题，你可以尝试使用不同的隐喻，或推荐不同的工作模式。尝试的成本相对较低，也许你会找到一些很棒的东西。

2. **保持提示简洁。** 移除那些没有发挥作用的元素。确保阅读记录，而不仅仅是最终输出——如果看起来技能正在让模型浪费时间做一些无生产力的工作，你可以尝试移除导致模型这样做的技能部分，看看会发生什么。

3. **解释原因。** 努力解释你要求模型做的一切背后的**原因**。今天的LLM很*聪明*。它们有很好的心智理论，当给定一个良好的挽具时，可以超越死记硬背的指令并真正实现事情。即使用户的反馈简短或沮丧，也要尝试真正理解任务以及用户为什么写他们写的东西，他们实际写了什么，然后将这种理解转化为指令。如果你发现自己写满了ALL CAPS的ALWAYS或NEVER，或者使用非常严格的结构，这是一个黄牌——如果可能的话，重新构建并解释推理，以便模型理解你要求的东西为什么很重要。这是一种更有人性、更强大、更有效的方法。

4. **寻找测试用例中重复的工作。** 阅读测试运行的记录，注意子代理是否独立编写了类似的辅助脚本或采取了相同的多步骤方法来处理某事。如果所有3个测试用例都导致子代理编写了`create_docx.py`或`build_chart.py`，那这是一个强烈的信号，表明技能应该捆绑这个脚本。编写一次，放在`scripts/`中，并告诉技能使用它。这可以节省未来每次调用时重新发明轮子的时间。

这项任务非常重要（我们试图每年创造数十亿美元的经济价值！），你的思考时间不是瓶颈；花时间认真思考。

我建议写一个草稿修订版，然后重新审视它并做出改进。真的尽力进入用户的思维，了解他们想要什么和需要什么。

### 迭代循环

改进技能后：

1. 将你的改进应用到技能中
2. 将所有测试用例重新运行到新的`iteration-<N+1>/`目录中，包括基线运行。如果你在创建一个新技能，基线始终是`without_skill`（没有技能）——这在迭代中保持不变。如果你在改进一个现有技能，使用你的判断来决定什么作为基线：用户带来的原始版本，或上一个迭代。

3. 使用`--previous-workspace`指向上一个迭代启动审查者
4. 等待用户审查并告诉你他们完成了
5. 阅读新的反馈，再次改进，重复

继续进行，直到：

- 用户表示他们满意
- 反馈都是空的（一切看起来都很好）
- 你没有取得有意义的进展

## 高级：盲比较

在你想对两个技能版本进行更严格的比较时（例如，用户问“新版本实际上是否更好？”），有一个盲比较系统。阅读`agents/comparator.md`和`agents/analyzer.md`了解详细信息。基本思路是：给一个独立代理两个输出，不告诉它哪个是哪个，让它判断质量。然后分析胜者胜出的原因。

这是可选的，需要子代理，大多数用户不需要它。人工审查循环通常就足够了。

## 描述优化

SKILL.md frontmatter中的描述字段是决定Claude是否调用技能的主要机制。在创建或改进技能后，建议优化描述以提高触发准确性。

### 第一步：生成触发评估查询

创建20个评估查询——包括应触发和不应触发。保存为JSON：

```json
[
  {"query": "用户提示", "should_trigger": true},
  {"query": "另一个提示", "should_trigger": false}
]
```

查询必须是现实的，是Claude Code或Claude.ai用户实际会输入的。不是抽象请求，而是具体、特定且具有良好详细信息的请求。例如，文件路径、关于用户工作或情况的个人背景、列名和值、公司名称、URL。一些背景故事。有些可能是小写或包含缩写、拼写错误或口语。使用不同长度的混合，并专注于边缘情况，而不是使它们界限分明（用户将有机会签署它们）。

差：`"格式化这些数据"`，`"从PDF中提取文本"`，`"创建一个图表"`

好：`"好的，我的老板刚刚发给我这个xlsx文件（它在我的下载中，名为'Q4销售最终最终v2.xlsx'），她想让我添加一个显示利润率的列。收入在列C，成本我猜在列D"`

对于**应触发**的查询（8-10个），要考虑覆盖范围。你想对同一意图的不同表达方式——有些正式，有些随意。包括用户没有明确命名技能或文件类型但明显需要的情况。加入一些不常见的用例，以及这个技能与其他技能竞争但应该获胜的情况。

对于**不应触发**的查询（8-10个），最有价值的是那些几乎相似的查询——共享关键词或概念的查询，但实际上需要不同的东西。考虑相邻领域、模棱两可的表达方式，其中天真关键词匹配会触发但不应触发，以及查询涉及技能做的事情但在其他工具更合适的情况下。

要避免的关键点：不要使不应触发的查询明显无关。"写一个fibonacci函数"作为PDF技能的负面测试太容易了——它不测试任何东西。负面用例应该是真正棘手的。

### 第二步：用户审查

使用HTML模板向用户展示评估集：

1. 从`assets/eval_review.html`读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项的JSON数组（周围没有引号——它是一个JS变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能的当前描述
3. 写入临时文件（例如，`/tmp/eval_review_<skill-name>.html`）并打开它：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换应触发、添加/删除条目，然后点击“导出评估集”
5. 文件下载到`~/Downloads/eval_set.json`——检查下载文件夹以获取最新版本，以防有多个（例如，`eval_set (1).json`）

这一步很重要——差的评估查询会导致差的描述。

### 第三步：运行优化循环

告诉用户："这需要一些时间——我将后台运行优化循环，并定期检查它。"

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中的模型ID（当前会话驱动的那个），以便触发测试与用户实际体验匹配。

运行时，定期使用`tail`命令查看输出，向用户提供有关当前迭代和分数的更新。

这会自动处理完整的优化循环。它将评估集分成60%的训练和40%的保留测试，评估当前描述（对每个查询运行3次以获得可靠的触发率），然后调用Claude根据失败的内容提出改进。它重新评估每个新描述在训练和测试上的表现，最多迭代5次。完成后，它会在浏览器中打开一个HTML报告，显示每次迭代的分数，并返回JSON，其中包含`best_description`——由测试分数而不是训练分数选择，以避免过拟合。

### 技能触发机制的工作原理

理解触发机制有助于设计更好的评估查询。技能会以名称+描述的形式出现在Claude的`available_skills`列表中，Claude根据描述决定是否咨询技能。重要的是要知道Claude只会在它自己无法轻松处理的任务上咨询技能——像"读取这个PDF"这样的简单、单步查询，即使描述匹配完美，Claude也可能直接用基本工具处理，因此可能不会触发技能。复杂、多步骤或专门的查询在描述匹配时可靠地触发技能。

这意味着你的评估查询应该足够实质性，以至于Claude实际上会从咨询技能中受益。像"读取文件X"这样的简单查询是差的测试用例——无论描述质量如何，它们都不会触发技能。

### 第四步：应用结果

从JSON输出中获取`best_description`，并更新技能的SKILL.md frontmatter。显示用户在/之前的/之后，并报告分数。

---

### 打包和展示（仅当`present_files`工具可用时）

检查你是否可以访问`present_files`工具。如果不能，跳过这一步。如果可以，打包技能并将.skill文件展示给用户：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包后，引导用户到生成的`.skill`文件路径，以便他们可以安装它。

## Claude.ai特定说明

在Claude.ai中，核心工作流程相同（草稿→测试→审查→改进→重复），但由于Claude.ai没有子代理，一些机制会发生变化。以下是需要调整的地方：

**运行测试用例**：没有子代理意味着没有并行执行。对于每个测试用例，读取技能的SKILL.md，然后按照其说明来完成测试提示。一次做一次。这不如独立子代理严格（你写了技能，你也在运行它，所以你有完整的上下文），但它是一个有用的合理性检查——人工审查步骤可以弥补。跳过基线运行——只需按请求使用技能完成任务。

**审查结果**：如果你无法打开浏览器（例如，Claude.ai的VM没有显示器，或你在一个远程服务器上），则完全跳过浏览器审查者。相反，直接在对话中呈现结果。对于每个测试用例，显示提示和输出。如果输出是用户需要查看的文件（如.docx或.xlsx），将其保存到文件系统中并告诉他们位置，以便他们可以下载并检查。直接在行内请求反馈："这个看起来怎么样？有什么你会改变的吗？"

**基准测试**：跳过定量基准测试——它依赖于基线比较，而没有子代理则没有意义。专注于用户的定性反馈。

**迭代循环**：与之前相同——改进技能，重新运行测试用例，请求反馈——只是中间没有浏览器审查者。如果你有文件系统，仍然可以将结果组织到迭代目录中。

**描述优化**：这一部分需要`claude` CLI工具（特别是`claude -p`），它仅在Claude Code中可用。如果你在Claude.ai上，跳过它。

**盲比较**：需要子代理。跳过。

**打包**：`package_skill.py`脚本在任何有Python和文件系统的地方都可以工作。在Claude.ai上，你可以运行它，用户可以下载生成的`.skill`文件。

**更新现有技能**：用户可能要求你更新现有技能，而不是创建新技能。在这种情况下：
- **保留原始名称**。注意技能的目录名称和`name` frontmatter字段——使用它们不变。例如，如果已安装的技能是`research-helper`，输出`research-helper.skill`（不是`research-helper-v2`）。
- **在编辑之前将文件复制到可写位置**。已安装的技能路径可能是只读的。复制到`/tmp/skill-name/`，在那里编辑，并从副本打包。
- **如果手动打包，先在`/tmp/`中暂存**，然后复制到输出目录——直接写入可能由于权限问题而失败。

## Cowork特定说明

如果你在Cowork中，需要知道的主要事项是：

- 你有子代理，所以主要工作流程（并行生成测试用例、运行基线、评分等）都有效。（但是，如果你遇到严重的超时问题，运行测试提示按顺序而不是并行也是可以的。）
- 你没有浏览器或显示器，所以在生成评估查看器时，使用`--static <output_path>`将独立的HTML文件写入，而不是启动服务器。然后提供一个用户可以点击以在他们的浏览器中打开HTML的链接。
- 由于某种原因，Cowork设置似乎使Claude在运行测试后不愿意生成评估查看器，所以重申一下：无论你在Cowork中还是在Claude Code中，在运行测试后，你都应该始终为人类查看示例生成评估查看器，然后再自己修改技能并尝试进行纠正，使用`generate_review.py`（而不是编写你自己的定制HTML代码）。抱歉，但我打算全部大写：*在评估输入之前生成评估查看器*！你想尽快让人类看到它们！

- 反馈工作方式不同：由于没有运行服务器，查看器的“提交所有评论”按钮将`feedback.json`作为文件下载。然后你可以从那里读取它（你可能需要先请求访问权限）。
- 打包工作——`package_skill.py`只需要Python和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在Cowork中应该工作得很好，因为它使用`claude -p`通过子进程，而不是浏览器，但请等到你完全完成技能并且用户同意它处于良好状态后再进行。
- **更新现有技能**：用户可能要求你更新现有技能，而不是创建新技能。遵循上面Claude.ai部分中的更新指南。
