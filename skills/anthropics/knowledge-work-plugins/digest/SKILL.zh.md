# 摘要命令

> 如果您看到不熟悉的占位符或需要检查已连接哪些工具，请参阅 [CONNECTORS.md](../../CONNECTORS.md)。

扫描所有已连接来源的近期活动，并生成一个结构化的摘要，突出显示重要信息。

## 说明

### 1. 解析标志

根据用户输入确定时间窗口：

- `--daily` — 过去 24 小时（如果未指定标志，则为默认值）
- `--weekly` — 过去 7 天

用户还可以指定自定义范围：
- `--since yesterday`
- `--since Monday`
- `--since 2025-01-20`

### 2. 检查可用来源

识别哪些 MCP 来源已连接（与搜索命令相同的方法）：

- **~~chat** — 频道、私信、提及
- **~~email** — 收件箱、已发送、线程
- **~~云存储** — 用户最近修改并共享的文档
- **~~项目追踪器** — 分配的任务、完成的任务、评论的任务
- **~~CRM** — 机会更新、账户活动
- **~~知识库** — 最近更新的维基页面

如果没有连接任何来源，请引导用户：
```
要生成摘要，您至少需要一个来源已连接。
检查您的 MCP 设置以添加 ~~chat、~~email、~~云存储或其他工具。
```

### 3. 从每个来源收集活动

**~~chat:**
- 搜索提及用户的消息（`to:me`）
- 检查用户所在的频道以查找近期活动
- 查找用户参与过的线程
- 识别关键频道中的新消息

**~~email:**
- 搜索最近的收件箱消息
- 识别有新回复的线程
- 标记有行动项或直接问用户问题的邮件

**~~云存储:**
- 查找最近修改或与用户共享的文档
- 记录用户拥有或协作的文档上的新评论

**~~项目追踪器:**
- 分配给用户的新任务或更新任务
- 用户关注的其他人完成的任务
- 用户参与的任务上的评论

**~~CRM:**
- 机会阶段变化
- 用户拥有的账户上记录的新活动
- 更新的联系人或账户

**~~知识库:**
- 相关集合中最近更新的文档
- 在用户关注的区域创建的新文档

### 4. 识别关键事项

从所有收集到的活动中提取并分类：

**行动项：**
- 直接要求用户执行的任务（"你能..."、"请..."、"@用户"）
- 已分配或即将到期的任务
- 等待用户回复的问题
- 审查请求

**决策：**
- 线程或邮件中达成的结论
- 批准或拒绝
- 政策或方向变化

**提及：**
- 用户被提及或引用的次数
- 关于用户的项目或领域的讨论

**更新：**
- 用户关注的项目的状态变化
- 用户领域中的文档更新
- 用户等待完成的任务

### 5. 按主题分组

按主题、项目或主题组织摘要，而不是按来源。合并跨来源的相关活动：

```
## Project Aurora
- ~~chat: 设计评审线程结束 — 团队选择了选项 B (#design, 周二)
- ~~email: Sarah 发送了包含反馈的更新规范 (周三)
- ~~云存储: "Aurora API 规范 v3" 由 Sarah 更新 (周三)
- ~~项目追踪器: 3 个任务移至进行中，2 个任务完成

## 预算规划
- ~~email: 财务团队要求周五前提交第二季度预测
- ~~chat: Todd 在 #finance 分享了模板 (周一)
- ~~云存储: "第二季度预算模板" 与您共享 (周一)
```

### 6. 格式化摘要

清晰地组织输出：

```
# [每日/每周] 摘要 — [日期或日期范围]

扫描的来源: ~~chat、~~email、~~云存储、[其他]

## 行动项 (X 项)
- [ ] [行动项 1] — 来自 [人员], [来源] ([日期])
- [ ] [行动项 2] — 来自 [人员], [来源] ([日期])

## 已做出的决策
- [决策 1] — [背景] ([来源], [日期])
- [决策 2] — [背景] ([来源], [日期])

## [主题/项目组 1]
[活动摘要，注明来源]

## [主题/项目组 2]
[活动摘要，注明来源]

## 提及
- [提及背景] — [来源] ([日期])

## 文档更新
- [文档名称] — [谁修改了什么] ([日期])
```

### 7. 处理不可用来源

如果任何来源失败或无法访问：
```
注意：无法连接到 [来源名称] 以生成此摘要。
包含的来源如下：[成功来源列表]。
```

不要让一个失败的来源阻止摘要的生成。尽最大努力从可用来源生成最佳摘要。

### 8. 总结统计

最后附上快速总结：
```
---
[X] 行动项 · [Y] 决策 · [Z] 提及 · [W] 文档更新
跨 [N] 来源 · 涵盖 [时间范围]
```

## 注意事项

- 如果未指定标志，默认为 `--daily`
- 按主题/项目分组，而不是按来源 — 用户关心发生了什么，而不是在哪里发生
- 行动项应始终排在最前面 — 它们是摘要中最可操作的部分
- 去除跨来源的重复活动（~~chat 和邮件中的相同决策 = 一个条目）
- 对于每周摘要，优先考虑重要性而不是完整性 — 突出显示重要信息，忽略噪音
- 如果用户有记忆系统（CLAUDE.md），使用它来解码人名和项目引用
- 每个条目中包含足够的上下文，以便用户决定是否需要进一步查看，而无需点击跳转
