# /write-query - 编写优化 SQL

> 如果你看到陌生的占位符，或需要查看已连接的工具，请参阅 [CONNECTORS.md](../../CONNECTORS.md)。

根据自然语言描述编写 SQL 查询，针对你的特定 SQL 方言进行优化，并遵循最佳实践。

## 用法

```
/write-query <描述你所需数据的说明>
```

## 工作流

### 1. 理解请求

解析用户的描述，识别以下要素：

- **输出列**：结果应包含哪些字段？
- **过滤条件**：哪些条件限制数据（时间范围、细分、状态）？
- **聚合**：是否存在 GROUP BY 操作、计数、求和、平均值？
- **连接**：是否需要合并多个表？
- **排序**：结果应如何排序？
- **限制**：是否有前 N 条或抽样需求？

### 2. 确定 SQL 方言

如果尚未知悉用户的 SQL 方言，询问其使用的是哪一种：

- **PostgreSQL**（包括 Aurora、RDS、Supabase、Neon）
- **Snowflake**
- **BigQuery**（Google Cloud）
- **Redshift**（Amazon）
- **Databricks SQL**
- **MySQL**（包括 Aurora MySQL、PlanetScale）
- **SQL Server**（Microsoft）
- **DuckDB**
- **SQLite**
- **其他**（询问具体细节）

记住该方言，以便在同一会话中的后续查询中使用。

### 3. 发现架构（如果已连接数据仓库）

如果已连接数据仓库 MCP 服务器：

1. 根据用户的描述搜索相关表
2. 检查列名、数据类型和关系
3. 查看影响性能的分区或聚簇键
4. 寻找可能简化查询的预构建视图或物化视图

### 4. 编写查询

遵循以下最佳实践：

**结构：**
- 当查询包含多个逻辑步骤时，使用 CTE（WITH 子句）以提高可读性
- 每个逻辑转换或数据源对应一个 CTE
- 为 CTE 设置有描述性的名称（例如 `daily_signups`、`active_users`、`revenue_by_product`）

**性能：**
- 生产环境中切勿使用 `SELECT *` -- 仅指定所需列
- 尽早过滤（将 WHERE 子句尽可能靠近基础表）
- 当可用时使用分区过滤器（尤其是日期分区）
- 对于具有大型结果集的子查询，优先使用 `EXISTS` 而非 `IN`
- 使用适当的连接类型（当 INNER JOIN 正确时，不要使用 LEFT JOIN）
- 当连接或窗口函数可行时，避免相关子查询
- 注意膨胀连接（多对多关系）

**可读性：**
- 添加注释解释非显而易见的逻辑背后的“为什么”
- 使用一致的缩进和格式
- 为表设置有意义的简短别名（不仅仅是 `a`、`b`、`c`）
- 将每个主要子句放在独立行上

**方言特定优化：**
- 应用方言特定的语法和函数（详见 `sql-queries` 技能）
- 使用方言适用的日期函数、字符串函数和窗口语法
- 注明任何方言特定的性能特性（例如 Snowflake 聚簇、BigQuery 分区）

### 5. 呈现查询

提供以下内容：

1. **完整查询** 放在带语法高亮的 SQL 代码块中
2. **简要说明** 每个 CTE 或部分的作用
3. **性能说明**（如果相关：预期成本、分区使用情况、潜在瓶颈）
4. **修改建议** -- 如何调整以应对常见变体（不同时间范围、不同粒度、额外过滤条件）

### 6. 提供执行选项

如果已连接数据仓库，提供运行查询并分析结果的选项。如果用户希望自行运行，查询已准备好直接复制粘贴。

## 示例

**简单聚合：**
```
/write-query 过去 30 天按状态统计订单数量
```

**复杂分析：**
```
/write-query 队列留存分析 -- 按注册月份对用户分组，然后显示注册后 1、3、6 和 12 个月时仍活跃（至少有一个事件）的百分比
```

**性能关键型：**
```
/write-query 我们有一个按日期分区的 5 亿行事件表。找出过去 7 天事件数量最多的前 100 位用户，以及他们最近的事件类型。
```

## 提示

- 提前说明你的 SQL 方言，以立即获得正确的语法
- 如果知道表名，请包含它们 -- 否则 Claude 会帮助你查找
- 指定查询是否需要幂等性（可安全重复运行）或一次性执行
- 对于定期运行的查询，说明是否需要针对日期范围进行参数化
