# 领域建模

在设计中积极构建和打磨项目的领域模型。这是一个*主动*的学科——挑战术语、发明边缘情况场景，并在术语明确时立即记录术语表和决策。（仅仅*阅读*术语表来获取词汇不是这项技能——任何技能都可以做这一行习惯。这项技能是在你改变模型时使用，而不仅仅是消费它。）

领域模型存在于两个地方：

- **术语表** — `docs/glossary/`，每个术语一个 markdown 文件，格式符合 `uvx disambiguate` 的预期（见下文）。永远不会有一个根 `CONTEXT.md`。
- **决策** — 按照 `writing-adrs` 技能的 ADRs 存放在 `docs/adr/` 中。

术语表条目、ADR、文档：如果可用，使用 `writing-prose` 技能编写和检查，表面 `markdown`——精确性和可理解性绝不能受损。

懒惰地创建文件——只有当你有东西可写时才创建。如果 `docs/glossary/` 不存在，在第一个术语被解决时创建它。

## 会话期间

### 与术语表进行挑战

当用户使用的术语与 `docs/glossary/` 中的现有语言冲突时，立即指出。 "你的术语表将 'cancellation' 定义为 X，但你似乎意味着 Y——这是哪一个？"

### 锤炼模糊语言

当用户使用模糊或重载的术语时，建议一个精确的规范术语。 "你在说 'account'——你是指 Customer 还是 User？那些是不同的事物。"

### 讨论具体场景

当讨论领域关系时，用具体场景进行压力测试。发明场景来探测边缘情况，并迫使用户精确地说明概念之间的边界。

### 与代码交叉引用

当用户说明某项工作原理时，检查代码是否一致。如果你发现矛盾，将其呈现出来： "你的代码取消整个 Orders，但你刚才说部分取消是可能的——哪个是正确的？"

### 内联更新术语表

当术语被解决时，立即在那里编写其术语表文件。不要批量处理这些——实时捕获它们。

术语表条目必须完全不含实现细节。术语表不是规范、草稿板或实现决策的存储库。它只是一个术语表，除此之外什么也不是。

### 勤俭地提供 ADR

只有当 `writing-adrs` 技能中的三项标准都满足时（难以逆转、没有上下文会令人惊讶、是真实权衡的结果）才提供创建 ADR 的建议）。格式、编号和位置也来自 `writing-adrs`。

## 术语表条目格式

`docs/glossary/` 中每个术语一个文件，可被 `uvx disambiguate` 消费：

- **文件名是 slug**：小写字母、数字、单个连字符 (`order-line.md` → slug `order-line`)。Slug 必须唯一。
- **第一个 H2 是规范名称**（强制）：`## Order Line`。
- **正文是自由形式的 markdown**：一个或两个紧密的句子定义术语是什么，而不是它做什么。当同一个概念存在多个词语时，选择最好的一个，并在 `_Avoid_：` 下列出其他词语。
- **使用标准 markdown 链接交叉引用相关术语**，通过 basename (`[Customer](customer.md)`) 或 wiki 风格 (`[[customer]]`)。这些链接形成 `disambiguate` 渲染的依赖关系图，按拓扑顺序排列——依赖于另一个术语的术语必须链接它。

示例 `docs/glossary/invoice.md`：

```md
## Invoice

向 [Customer](customer.md) 在交付后发送的付款请求。

_Avoid_：Bill, payment request
```

规则：

- **要有主见。** 每个概念一个规范术语；竞争词语放在 `_Avoid_：` 下。
- **只包含此项目上下文中特定的术语。** 即使项目广泛使用，一般编程概念（超时、错误类型、实用模式）也不属于这里。
- 编辑后使用 `uvx disambiguate --lint` 进行验证。
