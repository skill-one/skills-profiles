# 编写 ADR

ADR 存放在 `docs/adr/` 目录中，并使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

懒加载地创建 `docs/adr/` 目录——仅在第一个 ADR 需要时创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么，我们做了什么决定，以及为什么。}
```

就是这样。一个 ADR 可以是一个段落。其价值在于记录“我们做了决定”和“为什么”——而不是填写各个部分。

如果可用，使用 `writing-prose` 技能编写和检查，显示 `markdown`。硬性限制：精确性和可理解性不能受损。

## 可选部分

仅在它们能增加真实价值时才包含这些内容。大多数 ADR 都不需要它们。

- **状态** 前置元数据 (`proposed | accepted | deprecated | superseded by ADR-NNNN`) —— 当决策被重新审视时有用
- **考虑过的选项** —— 仅当拒绝的替代方案值得记住时
- **后果** —— 仅当需要指出非明显的下游影响时

## 编号

扫描 `docs/adr/` 目录，找到现有的最高编号，然后加一。

## 审查门

ADR 记录承重决策。在对话中做出的决策，从未经过审查（`docs/glossary/grilling-session.md`）→ 询问用户：“决策未经审查——按原样记录？” 仅在明确确认后继续。用户已经明确陈述的决策的转录 → 审查门不适用。

## 何时编写 ADR

必须满足以下三个条件：

1. **难以逆转** — 改变主意后的成本是显著的
2. **没有背景就令人惊讶** — 未来的读者会看着代码想知道“他们为什么要这样干？”
3. **是真实权衡的结果** — 存在真正的替代方案，你出于特定原因选择了其中之一

如果决策容易逆转，就跳过它——你只是会逆转它。如果它不令人惊讶，没有人会想知道为什么。如果没有真正的替代方案，除了“我们做了明显的事情”之外，没有记录的必要。

### 符合资格的例子

- **架构形状**。“我们使用单体仓库。” “写模型是事件驱动的，读模型是投影到 Postgres 的。”
- **上下文之间的集成模式**。“订单和账单通过领域事件通信，而不是同步 HTTP。”
- **带有锁定效应的技术选择**。数据库、消息总线、认证提供者、部署目标。不是每个库——只是那些替换需要花费一个季度才能替换的库。
- **边界和范围决策**。“客户数据由客户上下文拥有；其他上下文仅通过 ID 引用它。” 明确的“不”和“是”一样有价值。
- **故意偏离明显路径**。“我们使用手动 SQL 而不是 ORM，因为 X。” 任何合理读者会假设相反的事情。这些阻止了下一个工程师“修复”一个有意为之的事情。
- **代码中不可见的约束**。“由于合规要求，我们不能使用 AWS。” “响应时间必须在 200ms 以下，因为合作伙伴 API 合同。”
- **当拒绝的替代方案不明显时，记录拒绝的替代方案**。如果你考虑了 GraphQL 并选择了 REST，因为微妙的原因，记录它——否则六个月后有人会再次建议 GraphQL。
