# Agent-Native 计划

Agent-Native 计划是一种用于编码代理的结构化可视化规划模式。构建你通常用 Markdown 编写的计划，但作为一个包含可编辑块的扫描文档：内联图表、代码片段、开放式问题，以及可选的顶部视觉审查区域（线框画画布、可交互原型或两者在选项卡中）。架构和后端计划保持为纯文档；UI 和产品计划从顶部画布/原型开始（视觉表面选择部分拥有该规则）。

`/visual-plan` 是打包命令和主要入口点。从任务中选择审查模式：UI 优先，当工作主要是产品 UI 且审查应从屏幕开始时；原型优先，当审查应从可交互原型开始时；设计优先，当审查需要全保真度的品牌屏幕时；或视觉输入，当用户明确希望在规划前进行问卷调查时。当存在 Codex、Claude Code、Markdown 或粘贴的计划时，`/visual-plan` 使用该源计划作为起点，并从它构建审查表面，而不是重新开始。

## 何时使用

每当计划作为可审查的工件比聊天段落更好时，创建或调整视觉计划。这包括适度的工作，例如单个具有状态的 UI 表面、小型工作流、产品变更前/后，或需要协调的组件/API/数据形状决策，以及较大的多文件、模糊、长时间运行、有风险或 UI 密集型工作。当架构/数据流/UI 方向/选项/开放式问题受益于内联图表或结构化块时使用它，当用户需要在实施前对方向做出反应时，或当现有文本计划需要一个更丰富的审查表面时使用它。

## 计划规范

- **谨慎设置门槛。** 视觉计划是一个更丰富的审查表面，而不仅仅是一个用于大型项目的工具。当用户需要在代码之前看到、比较、评论或批准方向时，即使对于适度的 UI/状态/工作流变更也要使用它。跳过真正琐碎、无歧义的工作——拼写错误、单行修复、单个明确定义的函数、任何您可以用一句话描述的差异——并直接进行更改。永远不要用填充内容来填充计划，也永远不要发布单步计划。
- **起草前先研究。** 首先阅读真实文件、操作、模式；命名实际文件、符号和数据形状，而不是凭空捏造。在提出端点之前检查现有的 `actions/`，并优先使用命名客户端帮助程序而不是原始获取。将广泛的探索委托给子代理。以重用为先：对于每个步骤，在添加之前命名它重用的内容——现有的操作、模式、组件、帮助程序——所以计划解释了真正的新差异，而不是重新描述已经存在的内容。
- **先决定难以逆转的赌注。** 对于非琐碎的后端、数据或 API 工作，勾勒出功能的方向，然后指出一旦数据或调用者依赖它们就难以撤销的决策——线格式、公共 ID、数据模型形状、认证和所有权边界——并在计划中正确地确定这些，即使大部分功能稍后才会发布。然后范围到最小的第一版，证明方法而不封锁它，说明包含的内容和明确推迟的内容。
- **在正确的层次上保留示例。** 当用户的想法是广泛的框架、产品或运营模式变更时，不要将其合并到他们提到的第一个具体示例、提供者或同步路径中。将核心抽象与激励示例和应用程序/提供者适配器分开。使用示例使计划易于理解，但除非它们是整个请求的范围，否则将它们标记为示例。
- **发布独立的计划。** 如果用户粘贴、引用或已经有了 Codex / Claude Code / Markdown 计划，将其视为源材料，但将发布的计划重写为干净的独立提案。保留源计划的有用意图和代码库事实，将推断的视觉内容标记为推断的，并避免修订语言，例如“保留先前的计划”、“不要丢弃旧想法”、“与之前的版本不同”或“此修订更改...”。一个从未见过聊天或早期草稿的读者应该理解计划。
- **使第一次阅读具体化。** 如果计划打算与聊天外的人共享，或者概念是抽象的，则在模式表格、架构或路线图之前，在顶部附近提供一个具体的产品示例。对于具有 UI 能力的概念，这通常意味着一个显示产品术语中真实用户工作流的顶部画布应用状态。不要依赖仅在对话中才有意义的短语，并且不要将计划表述为“不是旧想法”；直接陈述积极的模型。
- **规划是只读的。** 在构建或审查计划时不要进行源编辑。只有在用户批准方向后才开始编辑。
- **澄清而非假设。** 不要询问如何构建它——在计划中探索和展示方法和选项。只有在歧义会改变设计且您无法从代码中解决时才提出澄清问题；使用主机代理的正常问用户问题流程，并在最终确定之前分批提出 2-4 个高杠杆问题。不要为普通澄清或预飞行调用 `create-visual-questions`；将其保留为视觉输入模式，当用户明确要求视觉输入问卷时。否则明确说明假设并继续，并将任何未解决的问题保留在计划底部的 `question-form` 开放式问题块中。对于复杂的计划，在交接前进行最终开放式问题检查：如果决策会影响架构、范围、UX、数据形状或发布，则在计划中说明理由或将其放入该底部表单并推荐默认值。
- **计划是批准的门槛。** 揭示计划后，在编写代码之前要求用户审查和批准，并命名受影响的文件/区域。提出计划并请求确认是批准步骤——不要询问一个单独的“这个看起来怎么样？”问题。
- **文档是事实来源，不是聊天。** 当范围发生变化时，使用 `update-visual-plan` 更新计划，而不是仅在聊天中改变方向，并使更新后的文档保持独立。不要在计划本身内部描述更新为对早期草稿的修正。在执行重大步骤之前重新阅读批准的计划。

## 创建结构化 Agent-Native 计划——绝不内联

交付物始终是结构化的 Agent-Native 计划，而不是仅聊天计划。托管 Plan MCP 连接器（`plan` 服务器，或遗留 `agent-native-plans`）是默认的协作和评论表面；它不是拒绝规划模式作为外部依赖或租用层的理由。计划是可移植的源工件（`plan.mdx`，可选的 `canvas.mdx` / `prototype.mdx`，JSON 和 HTML 导出），所有权敏感的工作流可以使用本地文件模式或自托管/自定义 Plan 应用程序 URL 而不放弃技能的审查纪律。不要建议用户跳过 `/visual-plan`，因为默认表面是托管的；为用户的所有权、隐私、共享和品牌需求选择正确的 Plan 模式。

默认情况下，通过 Plan MCP 连接器创建计划，并且永远不要将其作为内联聊天内容移交——没有 Markdown 散文、ASCII 绘图、表格或围栏线框。如果 `plan`（或遗留 `agent-native-plans`）工具不可见，通过主机的 `tool_search` 首先发现它们；如果它们仍然丢失，停止并给用户提供特定于客户端的重新连接步骤，而不是临时制作内联计划。在发布之前，或每当出现连接器或身份验证错误时，阅读此技能目录中的 `references/connection.md`——它是永不内联规则、连接器发现和每个客户端重新连接步骤的唯一事实来源。本地文件隐私模式（在工具指导之后）是例外。

## 核心工作流

本节描述默认的托管 Plan MCP 工作流。如果 `AGENT_NATIVE_PLANS_MODE=local-files` 被设置，或者用户要求完全本地文件/无托管 Plan 写入，请使用 **本地文件隐私模式**；仅传递这里的代码研究和计划组合指导。

1. 遵循主机代理的正常规划流程：检查代码库，在有用时委托广泛的探索，收集所需信息，并在生成计划之前根据需要提出本地澄清问题。如果源计划已经存在，从用户的粘贴、引用文件或最近的可见代理上下文中收集其确切文本；不要凭空捏造源文本。
2. 调用 `get-plan-blocks` 获取权威的块目录——不要从记忆中的标签进行创作。然后调用匹配模式的创建工具：`create-visual-plan` 用于文档优先计划（架构、后端、数据、重构、API），`create-ui-plan` 用于 UI 优先计划，`create-prototype-plan` 用于原型优先计划，`create-plan-design` 用于设计优先计划，`create-visual-questions` 仅在用户明确要求视觉输入问卷时。当源计划已经存在时，将其作为 `planText` 传递，并在生成独立计划文档的同时保留原始计划的有用意图，而不是生成修订备忘录。
3. 对于 UI/产品计划，首先使用主要的线框和注释状态组合顶部画布，然后使用本地块编写文档（见 `references/canvas.md` 和 `references/document-quality.md`）。对于具有用户界面影响的产品架构计划，在抽象架构或模式表格之前添加一个具体的“在应用中看起来像什么”视觉。保持文档接近代理通常输出的独立 Markdown 计划。如果提供了现有计划，则在不引用先前草稿或解释此版本如何不同的前提下，继续正确的 факты 和决策。对于非视觉计划，跳过顶部视觉表面（视觉表面选择 below 拥有该规则），并将 `diagram`、`data-model`、`api-endpoint`、`diff`、`file-tree`、`code` 和 `annotated-code` 块直接放在相关的散文旁边。宽文档布局是渲染器拥有的，并且有意允许：只有字面代码审查表面（`diff`、`annotated-code`）和具有垂直方向或 diff 类似子元素的 `tabs` 块会比散文更宽。除非它们自己的渲染器另有说明，否则将 `api-endpoint`、`openapi-spec`、`data-model`、`json-explorer`、`wireframe`、问题 和 `custom-html` 块保持在正常文档流中。
4. 揭示返回的计划链接或内联 MCP 应用，并要求用户审查。始终在聊天中包含实际 URL，以便下一步是在 CLI 或其他纯文本主机中单击。当主机暴露嵌入式浏览器/预览面板并且工具可以自动打开任意 URL 时，自动打开返回的计划 URL 以便方便审查——这是一个便利和烟雾测试，绝不是唯一的移交或访问模型。计划应该为本地代理和本地浏览器会话开箱即用；如果登录的嵌入式浏览器无法读取匿名/工具检查可以读取的本地计划，请修复应用程序/操作所有权或访问路径，而不是手动修补一个计划。对于高风险计划（架构、后端、数据、多文件或有风险），同时用户阅读时，也启动 **移交前的自我审查**，而不是阻止移交。
5. 对于托管计划，在编辑之前、审查之后、任何长时间暂停之后以及最终响应之前调用 `get-plan-feedback`。将 `anchorDetails`、resolver 意图、最近的审查事件以及来自浏览器移交的任何聚焦截图视为事实来源，以了解确切发生了什么变化以及每个评论指向的确切内容。
6. 对于托管计划，使用 `update-visual-plan` 应用更改，优先使用有针对性的 `contentPatches`。将顶级 `content` 负载视为完整替换，而不是合并；不要发送部分 `content` 对象以添加画布或一个块。如果无法避免完整替换或 `replace-blocks`，请在写入前立即调用 `get-visual-plan`，将其 `plan.updatedAt` 作为 `expectedUpdatedAt` 传递，并继续每个现有块和视觉表面。永远不要重用来自早期阅读或反馈负载的修订。对于源控制友好的编辑，使用针对 MDX 文件的粒度 `patch-visual-plan-source` 操作，而不是重新生成计划；`replace-file` 也是破坏性的，并且需要相同的 `expectedUpdatedAt` 栅栏。
7. 在每个托管计划写入后，再次调用 `get-visual-plan` 并比较持久化的文本、块 ID/计数、画布框架和原型与预期结果。成功的突变响应不是无关内容幸存的证据。如果编辑解决了针对代理的反馈，只有在验证调用后，才为线程调用 `resolve-plan-comment` 并为它的评论调用 `consume-plan-feedback`；执行两者，以便解决的反馈既不公开可见也不作为待办工作返回。
8. 对于托管计划，仅在用户想要一个可共享的收据或仓库检查入工件时，使用 `export-visual-plan` 导出。

## 移交前的自我审查

这个对抗性的自我审查传递是可选的，不是默认的：仅针对高风险计划运行——不可逆的迁移、安全敏感的工作，或当用户明确要求额外的严格性时——否则跳过它。它大致将计划生成的成本翻倍，因此对于小型、仅 UI、单决策或普通计划，默认是跳过，而不是运行它。当它运行时，保持传递廉价且非阻塞：

- **首先揭示计划，同时审查。** 发布链接并让用户开始阅读，然后并行运行审查——永远不要让用户等待它。
- **审查编写的计划；不要重新研究。** 批评计划文本及其自己的块。基础工作已经在起草时完成，所以审查检查输出而不是重新探索代码库。
- **生成一个怀疑的审查者**，其唯一工作是找到薄弱、缺失或错误的地方——不是表扬。指向：隐式或根本没有做出的难以逆转的决策（线格式、公共 ID、数据模型形状、认证、所有权）；没有锚定在真实文件或符号上的步骤；计划应该承诺一个选项的菜单；明显的缺失决策（“当 X 发生时会发生什么？”、“为什么不是 Y？”）；以及填充或单步填充。
- **修复而非询问。** 使用 `update-visual-plan` `contentPatches` 自己应用明确的修复——模糊的非目标、无锚定的声明、一个明显的缺失决策。将真正的判断调用路由回用户：将它们添加到底部的 `question-form` Open Questions 块或批量到正常的 ask-user-question 流程。不要无声地决定它们。
- **在阅读中不要让用户感到意外。** 在大型计划中，在编辑器加载之前应用补丁；否则简要说明正在运行自我审查，以便他们知道计划正在下面更改是预期的。下次响应时，总结审查更改了什么以及它为用户要决定的内容揭示了什么。

## 视觉表面选择

在创建计划之前或阅读源计划之后选择表面。默认情况下，不要添加视觉铬：

对于 UI/产品计划，顶部画布通常是主要的审查表面。将第一个有意义的线框放在那里，而不是埋藏在文档体块中。当状态很重要时，使用多个画布画板，例如默认视图、溢出菜单或弹出框、侧面板、加载或错误。使用 `targetId` 加上 `placement` 在帧旁边放置简短注释；将实现细节、权衡、文件映射、数据合同、风险和验证保留在画布下方的文档体中。

当用户要求流程图、故事板、用户旅程、线框图、画布或“这个看起来像什么”时，将其视为以画布优先的请求。为每个用户可见状态创建一个画板，仅连接相邻的转换，并使用简短的画布注释来记录产品备注。不要因为HTML图表编写更快而用文档体的`diagram`块替代请求的故事板；图表应位于画布下方，用于后端机制、架构或数据流说明。

保持产品线框图和解释性/元图表分开。从纯屏幕开始，这些屏幕看起来像正在讨论的应用状态，不嵌入UI中的标注文本或架构笔记。将箭头、标签、契约、数据流和模式说明放在单独的注释、单独的画布图表或文档体中。

当计划涉及现有应用时，在绘制前检查当前的外壳/组件。第一个画板应看起来像真实应用在相同密度下的样子：现有的侧边栏、工具栏位置、溢出菜单、应用边框和框架代理边框保持在它们实际的位置。将次要表面建模为单独的状态，例如右上角的溢出弹出窗口、表单、面板、加载状态或单独的AgentSidebar，而不是发明一个永久性的检查器或将框架边框折叠到产品UI中。

- **没有视觉表面**用于仅架构、仅后端、数据迁移、复制仅或否则非视觉计划。不要使用顶部画布用于架构图表、依赖关系图、文件计划、API契约或仅数据流审查。当关系需要视觉解释时，使用具有本地内联图表的强文档，通常每个建议或决策使用一个空间图表。优先考虑分组区域、图层、象限、矩阵或前后面板，除非关系确实是顺序的。
- **仅画布**用于一个静态屏幕、前后比较、组件状态、小弹出窗口或不需要点击的视觉方向。将这些线框图放在`content.canvas`中，并省略`content.prototype`。
- **画布+原型**用于多步骤UI流程、引导、向导、审查/批准流程、导航更改或任何需要审阅者操作行为的地方。将静态线框图保留在`content.canvas`中，在`content.prototype`中添加对齐的功能原型，并依赖顶部的视觉选项卡在它们之间切换。当两个表面都存在时，默认打开线框图选项卡；原型作为交互式后续视图保持可用。
- **默认为线框图**。干净的、极简的UI、高UX标准或对Linear/Vercel的参考描述了内容和密度条；它们不请求全保真度设计模式。除非用户明确要求品牌化、像素精确、生产类似或全视觉设计，否则使用渲染器拥有的线框图。这使每个画布屏幕可检查，并显示其全部内容。
- **原型优先**当用户要求操作UI或交互是主要问题时。使用`create-prototype-plan`，它仍然保留有用的静态模拟。

对于混合画布+原型的计划，重用标签和ID；除非明确为单表面，否则将表面补丁在一起。对于输出审查，阅读可观察性技能：支持单应用和工作室表格，保留应用预览，并保持审查、综合、差异和应用更改管理员授权。

将“更高保真度”、“像素精确”、“抛光模拟”、“生产类似”、“真实设计”和“不是草图/线框图”视为设计优先语言，即使请求中也包含“模拟”。对于新计划，使用`create-plan-design`。对于现有计划，保持相同的计划ID，并调用`update-visual-plan`，使用`set-visual-render-mode`补丁，使用`renderMode: "design"`，并在同一更新中包含升级的屏幕HTML/CSS。将结果基于真实应用外壳、标记、排版、间距和状态，并添加稳定的`data-design-id`目标。将作用域样式放在每个屏幕的`css`字段中，永远不会在`<style>`标签中。查看器本地干净的切换仅更改一个浏览器的线框图偏好；它不是保真度升级。不要创建一个重复的计划来处理保真度后续处理。

## 线框图质量 — 阅读`references/wireframe.md`

UI回顾/计划线框图必须满足严格的品质标准——全宽边框、固定底部栏、真实产品内容、前后可比较性、正确的`surface`预设、`--wf-*`标记而不是十六进制，以及没有`<html>`/`<style>`/字体标签。在编写任何线框图`/<Screen>`/`WireframeBlock`之前，阅读此技能目录中的`references/wireframe.md`——它是HTML线框图质量的单一来源，与`/visual-plan`和`/visual-recap`逐字共享。不要凭记忆编写线框图。

## 画布 — 阅读`references/canvas.md`

画布是静态UI模拟的单一来源：`surface`锁定每个画板的占位符，混合表面按车道布局，注释是锚定在`targetId`/`placement`的纯文本设计师笔记，编辑是外科手术`contentPatches`。在编写或编辑任何画布、画板或注释之前，阅读此技能目录中的`references/canvas.md`——它是画布/画板机制的单一来源。不要凭记忆编写画布布局。画布画板使用与文档体`WireframeBlock`屏幕相同的HTML线框图路径：使用语义HTML片段编写`<Screen surface="..." html={...} />`。不要在画布`<Screen>`标签内编写新的kit-tree子项，例如`<FrameScreen>`、`<Card>`、`<Row>`或`<Btn>`；这些是旧计划的遗留兼容性标记，会产生脆弱的画布布局。

## 文档质量 — 阅读`references/document-quality.md`

文档是一个严肃的技术计划，不是营销：结果优先、文本优先、自包含、由正确的原生块构建，具有单个底部`question-form`中的开放性问题和一个预移交视觉检查。在编写计划文档之前，阅读此技能目录中的`references/document-quality.md`——它是文档品质标准的单一来源。不要凭记忆编写文档。

## 好与坏的示例 — 阅读`references/exemplar.md`

对于品质标准的工作示例——一个伟大的UI优先计划和`/visual-plan`，以及要避免的反模式——在编写计划之前，阅读此技能目录中的`references/exemplar.md`。

## 编写不变量

将它们视为数据完整性检查，而不是可选的润色：

- `content`是完全替换。传递`content`或模式的便利数组（`screens`/`transitions`或`states`/`components`），永远不要两者都传递。创建操作拒绝混合来源，因此第二个有效负载不能无声地丢弃CSS、框架或文档块。
- 设计屏幕的作用域`css`是工件的一部分。将其保留在原型屏幕和其匹配的画布框架中，并使用渲染器拥有的`--wf-*`标记来传输颜色和排版。
- 富文本`data.markdown`必须包含实际的运行时换行符。不要向计划传递一个包含字面`\n`转义文本的单行Markdown值，这将使整个部分作为一个标题呈现。转义的新行在代码示例中是允许的，当周围的Markdown仍然有真实的换行符时。
- 画布画板不滚动。保持线框图HTML在自然流程中，当屏幕超过表面预设时设置更大的框架`height`；保留表面宽度，并在默认缩放下检查底部边缘，然后移交。
- 每次托管写入后，重新阅读结构化内容并检查实时计划表面。有效的JSON有效负载不是CSS加载或Markdown渲染成预期标题、段落和列表结构的证明。

## 工具指导

- `create-visual-plan`：为每个代理任务/运行开始一个结构化的视觉计划，或通过传递`planText`导入现有文本计划；`content`可以包含没有视觉表面、仅画布或画布+原型。
- `create-ui-plan`：当工作主要是产品UI时，开始一个UI优先计划。
- `create-prototype-plan`：开始一个具有功能性顶部审查表面的原型优先计划。如果交互本身也必须是高保真度，请将每个屏幕的`renderMode`设置为`design`，并通过`css`传递作用域样式；否则使用`create-plan-design`进行设计优先审查。
- `create-plan-design`：开始一个全保真品牌化Design-tab计划，并可选地匹配Prototype tab。
- `convert-visual-plan-to-prototype`：将现有的HTML线框图画布转换为原型计划。
- `create-visual-questions`：仅当用户明确要求视觉摄入问卷时使用，不作为`/visual-plan`预检。
- `update-visual-plan`：使用有针对性的`contentPatches`（见核心工作流步骤6-7）修订内容、状态或评论。使用`set-visual-render-mode`与`renderMode: "design"`一起将现有计划提升为高保真度，并附带故意的屏幕HTML/CSS；仅移除草图处理的渲染模式。`replace-blocks`和完整`content`替换需要从新的`get-visual-plan`调用中获取`expectedUpdatedAt`。
- `read-visual-plan-source`：以`plan.mdx`、可选`canvas.mdx`、可选`.plan-state.json`和JSON格式读取标准化计划。
- `patch-visual-plan-source`：通过稳定的块、画板、注释、组件或线框图节点ID应用粒度MDX AST补丁。优先考虑这些目标操作；`replace-file`需要从新的`get-visual-plan`调用中获取`expectedUpdatedAt`。
- `import-visual-plan-source`：从MDX文件夹创建或替换计划。
- `get-visual-plan`：读取当前结构化计划、导出HTML、注释和`plan.updatedAt`；它还返回源工作流的MDX文件夹。在破坏性写入前立即重新读取，以获取其并发围栏，并在每次写入后再次读取以验证持久化状态。
- `get-plan-feedback`：读取未消耗的人类反馈。经常使用它；它返回分组线程、确切的锚点详细信息、预期的解析器以及最近的审查事件有效负载，以便代理仅对指向它们的评论采取行动。
- `get-plan-blocks`：在编写之前解析块标签——不要记忆标签；首先调用此操作以获取来自实时块注册中心的权威标签名称、必需字段和prop形状。
- `export-visual-plan`：导出HTML、Markdown回退、结构化JSON和MDX文件以供repo检查入。

当用户批评计划的看起来或结构时，修复渲染器或此技能——永远不要手动编辑存储的计划。将反馈转化为更好的指导。

## 本地文件隐私模式 — 阅读`references/local-files.md`

当用户不想有托管的计划数据库写入——没有DB写入、没有计划MCP发布、完全本地/离线/私有规划、repo拥有的源代码控制工件或`AGENT_NATIVE_PLANS_MODE=local-files`——不要调用任何托管的计划工具，除了仅限架构的`get-plan-blocks`目录查找。编写本地MDX文件夹，并使用`plan local check` / `plan local serve` / `plan local verify`预览它。在使用本地文件模式之前，阅读此技能目录中的`references/local-files.md`——它是完整合同（目录查找、MDX文件夹布局、本地桥接命令以及您必须不调用的托管工具）的单一来源。仅传递代码研究和计划组合指导；托管的所有内容都被本地桥接取代。

## 解释评论锚点

本节适用于带有`get-plan-feedback` / `update-visual-plan`的托管计划。在本地文件模式下，不要调用托管反馈或更新工具；直接解释文件/聊天反馈，编辑MDX文件，重新运行本地桥接检查/服务/验证命令，并报告新的本地URL。

`get-plan-feedback`返回丰富的锚点——在采取任何评论行动之前阅读它们。

- **坐标框架**。`targetX`/`targetY`是在由`targetSelector`/`targetKind`命名的元素内部的百分比。裸`x`/`y`是整个计划文档的百分比。`canvasX`/`canvasY`是设计画布上的原始板世界像素（当可用时给出板大小）。
- **线框图销钉**。线框图上的锚点包括`targetNodeId`和`targetNodePath`（例如`card > list > listItem "Acme Inc"`）以标识精确的套件节点。直接使用`targetNodeId`与线框图节点补丁操作；使用来自设计画板的`data-design-id`值与`update-design-element-style`。优先考虑节点ID/路径而不是原始坐标；仅在不存在节点ID时才回退到坐标加上聚焦的屏幕（红色圆圈标记了确切点）。
- **文本引用**。使用`contextBefore`/`contextAfter`根据当前文本解决`textQuote`以消除歧义。如果`ambiguous: true`，请询问用户——不要猜测哪个出现是所指的。
- **分离的评论**。`get-plan-feedback`将引用文本不再存在的线程标记为`detached`（在`detachedThreads`中）。将这些与重写的内容进行协调——永远不要无声地丢弃它们。
- **路由**。`resolutionTarget`是唯一的路由信号：对`agent`采取行动，将`human`视为上下文仅。`@mentions`是通知的人，永远不会是路由信号。
- **双轴状态**。将每个摄入的评论标记为已消耗（`consumedCommentIds`在`update-visual-plan`上）。仅在您实际解决的代理目标评论上设置`status=resolved`；保留人类目标评论为打开状态。当编辑解决反馈时，首先重新读取持久化计划并验证请求的更改。然后才调用`resolve-plan-comment`以解决已处理的线程，并调用`consume-plan-feedback`以解决其评论；永远不要仅在一个轴上标记已处理的反馈。

## 可见性与共享

使用`set-resource-visibility`更改谁可以看到计划（例如公共、登录或组织范围的）。使用`share-resource`通过电子邮件或角色授予特定用户或角色访问权限。在共享任何涵盖未发布或私有工作的计划之前设置可见性——默认为满足审查需求的狭窄范围。

## 设置与身份验证

进入计划的两种方式。

**编码代理（CLI）**。使用Agent-Native CLI安装一次。命令安装计划技能，注册托管的计划MCP连接器，并在同一步骤中运行所选本地客户端的auth/setup（设置时的一次性浏览器登录——这是预期的），因此该客户端中的第一个工具调用不会遇到OAuth墙：

```bash
npx @agent-native/core@latest skills add visual-plans
```

之后，`/visual-plan`、`/visual-recap`和`/visualize-repo`是安装的斜杠命令。如果您只需要一个命令，请使用`skills add visual-plan`、`skills add visual-recap`或`skills add visualize-repo`。其他规划模式（`create-ui-plan`、`create-prototype-plan`、`create-plan-design`、`create-visual-questions`）是从`/visual-plan`可达的MCP工具，而不是单独的斜杠命令。传递`--no-connect`以注册连接器而不进行身份验证，然后当您准备好时运行`npx @agent-native/core@latest connect https://plan.agent-native.com --client all`，或者选择更窄的`--client`。身份验证和MCP工具加载是按客户端配置/会话的。

**浏览器（与您共享的人）**。打开计划编辑器，无需注册即可创建和编辑——您作为访客工作。仅在您想要保存或共享时才登录；登录时才将您作为访客制作的计划声明为您的账户。

共享和评论需要帐户：公共/共享的计划可被任何拥有链接的人查看，但评论它们需要agent-native帐户。

对于完全离线、无帐户使用，请本地运行计划应用程序并将计划作为MDX同步到您的repo。此本地模式是单独的高级路径，不是默认的托管流程。

对于全仓库的视觉文档，运行
`npx @agent-native/core@latest visualize-repo --open` 来创建/更新
`agent-native.json`，初始化 `.agent-native/visual-docs/repo-overview`，并打开本地桥接器。

如果计划的工具返回 `needs auth`、`Unauthorized` 或 `Session terminated`，不要持续重试它 — 停止并给用户执行 `references/connection.md` 中的客户端重连步骤，然后在连接器可用时继续。

托管默认：连接 `https://plan.agent-native.com/mcp`。不要在技能文件中放置共享密钥。
