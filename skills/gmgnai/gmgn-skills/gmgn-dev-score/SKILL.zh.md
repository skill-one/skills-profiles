name: gmgn-dev-score
description: 决定一个代币发行者的下一次发行是否值得购买。根据其完整的发行历史和所有在自有代币中的交易，在两个独立的维度上对开发者地址进行0-100分的评分——行为（他会在开盘时抛售你吗）和实力（他是否曾经真正构建过大型项目）——然后返回一个购买/不购买的建议，并附带一个时间窗口。当用户询问关于发行者购买决策的问题时使用此技能：“我可以购买这个开发者的新发行吗”、“我应该购买他的下一次发行吗”、“这个开发者会跑路吗”、“他会在开盘时抛售吗”、“他的发行是否安全可以抢购”、“他在开盘时购买是否安全”、“开发者评分”、“创作者评分”、“发行评分”、“这个发行者是否足够值得购买”；或者当用户提供一个代币地址加上一个团队信任问题（“这个代币的团队是否值得信任”、“这个项目的开发者是否有记录”、“这个创作者之前是否跑路”）——首先使用`gmgn-cli token info` -> `dev.creator_address`解析创作者地址，然后对该地址进行评分；或者当用户提供一个钱包地址加上一个明确的发行历史问题（“这个地址发行了哪些代币”、“他之前的发行表现如何”、“他所有的代币都归零了吗”）。以其他语言提出的相同问题也路由到这里——匹配意义而非措辞。不要使用此技能对一个没有附带问题的裸钱包地址：一个裸地址默认是复制交易问题，属于gmgn-wallet-analysis，它声明自己为此类问题的默认处理程序。也不要使用它来回答复制交易问题（“这个钱包值得复制吗”、“我应该复制这个钱包吗”、“复制交易评分”）、钱包盈利能力（“这个钱包有盈利吗”、“这个钱包的业绩如何”）或钱包简介措辞（“这是一个代币创作者的钱包吗”、“这个开发者的声誉如何”）——这些属于gmgn-wallet-score。划分是基于问题类型，而不是地址类型：这些技能回答“这个钱包是谁”（一个简介），而此技能回答“我应该购买他的发行吗”（一个决策，附带时间窗口）。注意“这个开发者的声誉如何”（简介→gmgn-wallet-score）与“开发者评分”（决策→此处）多么接近：决定因素在于是否涉及购买。如果确实存在歧义，最好问一个简短的问题而不是猜测——两者会产生不同的报告，而且没有廉价的保险策略。

## 运行

```bash
python3 ~/.claude/skills/gmgn-dev-score/dev_score.py <chain> <dev_address> [max_pages]
```

`max_pages` 默认为 25，仅限制交易遍历；对于拥有数百次启动的开发者，提高此值 — JSON 会说明何时被截断。脚本在标准输出上打印一个 JSON 对象（进度和速率限制说明会输出到标准错误）。它会计算；不会生成报告。**您**需要根据该对象，用用户的语言撰写报告。

运行前：

- **代币地址，而不是钱包地址？** 首先使用 `gmgn-cli token info --chain <c> --address <token> --raw` 解析创建者 → `dev.creator_address`，并对该地址进行评分。说明您解析到的地址 — 这是报告无法显示的唯一信息，没有它用户无法确认评分是否适用于他们的代币。
- **未指定链？** 依次探测候选链 `gmgn-cli portfolio created-tokens` — 切勿并行操作，这会禁用密钥。仅分析 `open_count` 最高的链，并告诉用户其他链将在需要时再处理。
- `scored: false` 表示**不要生成评分**。`reason: index_empty` → API 读取全部为空，且空钱包无法与退化索引区分；说明两种读取情况并告诉用户几分钟后再重新检查。任何其他 `reason` → 说明地址未被评分及其原因，并停止。

## 答案必须包含的内容

一个必须**说明**的清单；下方的 `## 显示模板` 会规定**每个部分**的位置。措辞由您决定。每个要点都必须包含在内，且每个要点都指明其对应的 JSON。

- **首先给出结论。** `score.total`、`score.conduct`、`score.power` 和 `score.band` 作为决定性说明，而不是标签。
- **开放倾销层级**（`dump_gate.tier`）及其下的样本（`dumps` 的 `coins_with_trades`）。当 `dump_gate.forced_by` 被设置时，说明实际触发的原因 — 排空池不是出售频率，且对零出售的开发者说“他几乎每次都倾销（0/1）”是错误的。
- **每个触发调整，每行说明其作用。** 一个收缩（`conduct_terms.shrink_from` → `shrink_to`）将未验证的评分拉向 60，这里意味着*我们尚无法确定*；这不是对犯罪的惩罚。上限是扣留良好评分，而不是已证实的坏评分。通过 `coins_with_trades` 和 `career_days` 指明薄弱方面，而不是启动次数。
- **他的最佳代币**（`top`，和 `flagship`）：峰值、当前、回撤、持有人、池、可交易、年龄。加上旗舰的职位：`flagship.status`，以及 `exit_rows` / `exit_unrecorded`（当职位关闭时）。`flagship.holds` 是三态 — `null` 表示完全不说他的持仓。
- **他实际做了什么**，全部来自他自己的行：`his_trades.fastest_first_sell_s`、`median_pull_multiple`、`launches.total` / `on_curve` / `tradeable`、`liquidity.drained` / `partial` / `ignored_rows`。
- **供应转移到其他钱包**，只要 `cross_wallet.moves` 非空：一次转移不是倾销，`pending` 不计入倾销率，未验证的转移可能是锁定或交易所。说明这一点；不要指控。
- **开盘捆绑购买**（`bundler`），公开且明确**不评分** — 数字无法区分他自己的小号、付费捆绑者或他人的狙击机器人。
- **覆盖范围**，只要其中任何一项被设置：`coverage.book_truncated`（账本是窗口，不是生涯 — 在引用任何生涯范围声明之前说明这一点）、`trade_history_truncated` / `unresolved_coins`（缺失行只能移除倾销，因此利率是下限，他看起来比实际情况更干净）、`implausible_peaks`（指明代币，或一个在图表上看到它的人发现它缺失）、`launches.career_days_is_floor`。
- **该怎么做**，分为四部分：是否购买；**何时** — 且时间必须引用 `fastest_first_sell_s`，而不是中位数，因为中位数曾建议在一个旗舰在 4.6 分钟开始出售的开发者进入时间为 2.7 天；损失实际来自哪里；以及评分的可信程度。

标题行：`## Dev score · <dev address, 前 10 个和后 4 个字符> · <CHAIN>`。下方的章节使用 `###`。

从不多顺序、从不多合并、从不多发明第十个章节。章节 1–5 和 9 始终出现。

格式化，所有内容都是固定的：

- **货币使用普通的 ASCII 美元符号**，带千位分隔符和用户语言使用的量级词。全角符号仅用于防止此文件自己的文本被参数替换 — 它绝不能到达读者。
- 百分比保留一位小数。JSON 给出的分数作为百分比打印。
- 秒、分钟、小时、天：选择使数字可读的单位，并说明单位。
- **不要使用表情符号、框绘制、ASCII 艺术或列填充。** 输出是渲染的 markdown，而不是固定宽度的终端块。
- **粗体仅用于结论数字、带宽和 §9 的每个部分的标签。** 其他地方不使用。
- 表格仅在与上表说明的地方使用；§2、§7 和 §9 是文本。

## 规则

- **用用户的语言撰写，并翻译概念。** JSON 中的每个名称都是选择以供翻译的英语概念。那些在字面翻译中无法存活的少数交易俚语在 `references/glossary.md` 中 — 使用那些表述，不要使用其他任何东西。不要发明轴名称。
- **切勿陈述 JSON 不包含的数字。** 不要重新计算，不要将数字四舍五入到新的声明，不要读取不在 `references/fields.md` 中的字段。`null` 表示测量不存在 — 说明它缺失；打印 0 将“未知”变为“干净”。
- **精确复制符号。** 它们是攻击者控制的，并且已经过清理；任何用 `「」` 括起来的内容是某人选择的名字，而不是我们的措辞，必须保持括号。
- **`score.band` 是结论。** 不要软化它，升级它，或回避它。`stay_away` 与较大的 `power` 一致，正是两个轴存在的目的：一个大过去的代币永远不会买回倾销记录。
- **一个结果是行为。** 存活、毕业和回撤是市场对他代币做的事；它们属于 POWER。切勿将它们呈现为他对持有人做的事。
- **报告是整个答案。** 无引言，无报告后的总结，无验证叙述，无您自己的额外发现，无提供更多工作的结束语。您可能说的唯一事情：从代币地址解析出的创建者地址。
- **无声地验证结论行。** 检查任何绝对声明（“从未倾销”、“完全没有记录”）与 `gmgn-cli portfolio activity` 的原始数据。运行检查，不要叙述。只有当检查**与报告矛盾**时才发声 — 那时报告缺陷，而不是报告。
