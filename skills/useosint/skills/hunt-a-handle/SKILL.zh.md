# 搜索用户名

用户名重用是开源情报（OSINT）中最经济有效的强关联手段：一个字符串，几分钟内确认，可能将十几个平台与一个人关联起来。它也是最容易被过度信任的。枚举者不会验证身份——他们会执行HTTP存在性检查——而一个命中列表只是一个候选项列表，仅此而已。毁掉这些调查的错误是将工具的输出直接粘贴到报告中。枚举是简单的一半；确认才是工作。

## 第1步 — 授权范围

阅读 [../../ETHICS.md](../../ETHICS.md)，在进行任何查询之前，写下以下内容：
主题、目标、授权范围内的选择器、超出范围的行动（登录、联系、请求关注），以及管辖权。搜索用户名很容易偏离方向——一次运行可能给你三十个新的平台，并且很容易最终分析一个与该字符串相同但无关的人。

**完成标准**：当范围被记录下来，并且你能说出什么会使你超出范围时。

## 第2步 — 选择你的枚举工具

| 持有情况 | 选择 | 原因 |
|---|---|---|
| 一个用户名，需要快速广度 | `sherlock` | 最大的快速扫描，仅检查存在性 |
| 一个用户名，需要个人资料内容 | `maigret` | 解析页面：显示名称、简介、ID、链接，有时是国家和创建日期 |
| 需要查看为什么触发了命中 | `WhatsMyName` 数据 | 每次检查都是一个声明的URI加上你可以读取的匹配规则 |
| 在一个已知平台上有一个用户名 | 手动访问 | 没有什么比直接阅读实际个人资料更有效 |

```bash
sherlock jdoe_92 --timeout 10 --csv
maigret jdoe_92 --html
```

maigret 是用于关联的更高价值工具，因为它返回 *字段*，而不是布尔值。一个显示名称、头像URL、自我声明的位置、数字用户ID和一个“也被称为”列表为你提供了测试下一个平台的材料。Sherlock 只给你一个URL和一个声明。

`WhatsMyName` 是一个检测列表，不是扫描器：一个JSON文件，包含网站条目，每个条目都有一个URI模板和明确的匹配标准（预期的HTTP状态和预期在正文中的字符串，以及“缺失”的等效标准）。阅读你怀疑的任何网站的条目——它告诉你工具认为的证据是什么。许多包装器和网络前端消耗相同的列表，因此在一个不同的工具中命中通常是三次规则触发，而不是三次独立的确认。

**完成标准**：每个候选项都记录了平台、URL、找到它的工具以及实时/非实时状态。

## 第3步 — 生成变体

你被给出的用户名是一个人在命名习惯中的一个点。恢复这个习惯，你就能找到第一次扫描遗漏的账户。

- 分隔符替换：`john.doe`、`john_doe`、`john-doe`、`johndoe`
- 截断和首字母缩写：`jdoe`、`johnd`、`j_doe`、`doej`
- 数字后缀：出生年份、出生年份两位数、`1`、`99`、`007`
- 聚合语和字符替换：`j0hnd0e`、`johnd0e`
- 邮件本地部分作为用户名，以及用户名作为邮件本地部分
- 游戏标签形态：前缀、`xX…Xx`、公会标签、重复的字母

完整模式列表：[reference/variant-patterns.md](reference/variant-patterns.md)。

两个推理方向很重要。用户名→姓名：`jdoe_92` 暗示了一种首字母-姓氏模式和一个1992年出生年份，这是一个假设，而不是一个发现。姓名→用户名：如果你已经有了真实姓名，请生成该姓名可能产生的用户名并枚举这些用户名——它通常比从一个别人给你的用户名开始更有效。

**完成标准**：变体集被枚举，并且产生命中的变体被折叠回第2步。

## 第4步 — 确认，或拒绝

对于每个候选项，寻找能够经受住怀疑读者检验的证据。

强：

- 相同的头像。使用 `find-the-original-image` 验证——与库存照片或第三方图片的匹配是拒绝，而不是确认。
- 字节相同或几乎相同的简介文本，尤其是在有拼写错误或不寻常的措辞的情况下。
- 自我声明的跨链接：个人资料链接另一个个人资料。目前可用的最佳证据，仅次于承认。
- 两个平台都存在的联系选择器（相同的电子邮件、相同的个人域名）。

中等：

- 账户创建日期在多个平台上聚集在一个狭窄的时间窗口内——人们会成批注册。
- 关注者/被关注者重叠与相同的独特小账户。
- 写作风格：习语、标点习惯、发布时间所在时区。

单独弱：用户名匹配。那是你在测试的东西，而不是支持它的证据。

暴露**数字用户ID**的平台特别有用。当ID按注册顺序发放时，即使个人资料隐藏了它，ID也限制了账户的创建日期。GitHub的
`https://api.github.com/users/<login>` 返回一个数字 `id` 和 `created_at`；Discord的雪花ID直接编码创建时间。平台详细信息：[reference/platform-leakage.md](reference/platform-leakage.md)。

**完成标准**：每个候选项都被评定为确认、可能或拒绝，旁边记录了证据。

## 哪里会出错

存在性检查是HTTP启发式方法。这些中的每一个都会产生一个误报：

- **软404**。网站返回200和一个“用户未找到”页面。如果匹配规则基于状态码，那么一切都存在。
- **通用个人资料页面**。一些平台为任何字符串渲染一个通用外壳，并且仅在API上返回404。
- **速率限制和CAPTCHA中间页面**。挑战页面是200带有正文内容，因此它可以满足“找到”和“缺失”的规则——一旦你被速率限制，运行其余结果都是垃圾。单独重新运行失败，而不是信任一次扫描。
- **保留、被占用和冒充账户**。已注册、真实，但不是你的主题。
- **过时的条目**。网站改变了他们的404行为，检测列表滞后。没有命中不代表没有账户。

更深层次的问题是冲突。常见的用户名属于许多无关的人，一个在十个平台上短或字典词的用户名通常是十个人而不是一个人。信心应该随着用户名的独特性而增加：一个罕见的发明字符串本身是弱到中等证据，`mike` 是没有。

不要通过登录、发消息或请求关注来解决歧义。这是互动，默认情况下超出范围，并且它告诉主题你存在——见 `investigate-without-getting-made`。

## 信心评级

- **确认**——通过 `find-the-original-image` 验证的头像匹配加上另一个强项，或者两个个人资料之间的自我声明跨链接，或者共享的联系选择器。
- **可能**——独特的用户名加上一个中等项（创建日期集群、关注者重叠、一致的风格）并且没有矛盾的证据。
- **未确认**——用户名匹配，其他都不匹配。将其报告为枚举命中，而不是主题的账户。
- **拒绝**——内容、语言、时间线或头像来源与主题矛盾。记录拒绝；它们阻止下一个分析师重做工作。

## 实例分析

给定 `sunfish_ada`。Sherlock 返回14个命中。maigret 返回9个有内容，包括一个代码托管个人资料，显示名称为 "A. Okonkwo"，一个摄影网站有相同的头像，以及一个论坛有一个空壳个人资料。

论坛命中首先被丢弃：在同一个论坛上获取一个故意荒谬的用户名也返回200，并返回一个相同的空页面。通用，不是账户。

摄影网站的头像反向搜索（通过 `find-the-original-image`）到代码托管个人资料上的相同图片，并且无处可寻——好的。代码托管API返回一个数字ID和与摄影账户声明的加入日期在同一个月的创建日期。两个中等项加上头像匹配：两个都确认。

一个微博客命中有相同的用户名，使用不同的语言发布与不相关主题的内容，账户比其他账户早六年。不同的人，相同的字符串——拒绝，并明确说明，因为这是审查者首先会发现的东西。

## 法律和ToS注意事项

自动化枚举使用脚本请求平台，大多数服务条款禁止，无论数据是否公开。保持并发量低，不要破解CAPTCHA，当平台发出拒绝信号时停止。在欧盟和英国，将分散的公共账户汇编成一个活人的个人资料是处理个人数据，需要合法依据和数据最小化。

## 第5步 — 报告

运行 `write-the-intel-brief`。提供平台/URL/信心/证据表格，列出拒绝原因，并首先给出由用户名产生的真实姓名和联系选择器。

**完成标准**：表格中的每个候选项都带有等级和来源，并且没有枚举命中没有一个是。
