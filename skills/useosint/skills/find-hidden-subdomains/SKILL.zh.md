# 查找隐藏的子域名

组织遗忘的主机才是值得查找的，而大多数主机在有人请求TLS证书时都宣布了自己的存在。
证书透明度将这一点转化为一个可搜索、永久、历史性的索引——免费且完全被动。初学者的错误是将CT命中视为活动主机：你拉回的大部分内容都无法解析，而这些信息也是有价值的，不是噪音。

## 首先从哪个来源开始

| 你持有 | 从...开始 | 为什么 |
|---|---|---|
| 一个顶级域名 | crt.sh通配符查询 | 最广泛的免费覆盖范围，包括早已消亡的名称 |
| 一个在通配符证书后面的域名 | 被动DNS，然后是存档 | CT只会显示`*.example.com` |
| 对命名约定的猜测 | CT来学习约定，然后是单词列表 | 在暴力破解任何东西之前先学习模式 |
| 一个组织名称，而不是域名 | 按主题组织机构搜索证书 | 查找你不知道他们拥有的域名 |
| 你已经拥有的证书 | 其SANs，然后是其序列和发行者 | SANs提供兄弟证书；序列可以在其他地方找到确切的证书 |
| 只需要*当前*主机的需求 | 解析候选列表 | CT本质上是历史的；DNS是活跃性神谕 |

## CT实际上是如何工作的

CA将它们签发的每个证书提交到可验证的公共日志中。日志返回一个已签名的证书时间戳，主流浏览器拒绝信任不携带合格日志中SCTs的公开受信任证书。所以参与不是自愿的：如果证书在浏览器中有效，它就在日志中。

对你重要的三个后果：

- **没有任何内容被删除。** 日志是追加-only的。五年前出现在证书中的主机在主机消失后仍然存在。
- **你能看到预证书和证书。** CA首先记录预证书，然后是最终证书，所以大多数名称至少出现两次。去重。
- **只涵盖公开受信任的证书。** 私有/内部CA、自签名证书或Cloudflare源证书永远不会到达日志。CT完全无视这些主机。

## crt.sh

Web界面使用`?q=`，其中`%`是通配符，`output=json`提供机器可读的结果。

```bash
# 查找example.com或其子域名中出现的所有名称
curl -s 'https://crt.sh/?q=%25.example.com&output=json' \
  | jq -r '.[].name_value' | sed 's/^\*\.//' | sort -u

# 当你想偏向当前基础设施时，跳过过期证书
curl -s 'https://crt.sh/?q=%25.example.com&output=json&exclude=expired' | jq -r '.[].name_value'

# 对组织字符串进行身份搜索，这会找到未知的域名
curl -s 'https://crt.sh/?q=Example+Corporation&output=json' | jq -r '.[].name_value'
```

`q`参数是身份搜索：它匹配域名，它也匹配主题字段，如组织名称，这就是你找到那些在简介中未提及的域名的方式。

有用的JSON字段：`name_value`（证书上的所有名称，按换行符分隔）、`common_name`、`issuer_name`、`not_before` / `not_after`、`serial_number`、`entry_timestamp`和`id`（打开`https://crt.sh/?id=<id>`来读取证书）。

crt.sh还通过Postgres公开其数据库只读访问——主机`crt.sh`，端口5432，用户`guest`，数据库`certwatch`。这让你可以针对证书索引编写真实的SQL，而不是分页JSON。这是一个共享的免费服务：保持查询范围有限，如果你过度使用它，可能会被切断。

其他CT前端和替代方案及其覆盖范围和访问模型在[reference/subdomain-sources.md](reference/subdomain-sources.md)中。

## SAN字段是关键

浏览器忽略通用名称；`subjectAltName`扩展包含实际覆盖的主机名列表。将其视为一个团队一起部署的声明：

- 一个包含少量相关名称的证书是故意的分组——这些主机属于同一服务，并且可能由同一管理员管理。
- 一个包含几十个不相关名称的证书是托管提供商或CDN的捆绑证书。**这些名称是其他客户，而不是你的目标资产。** 这是基于CT的枚举中最大的误报来源。
- 一个证书上包含来自*不同可注册域名*的名称是好发现：这意味着一个运营商管理两者，这会暴露收购、品牌重塑和未公开的兄弟品牌。在得出结论之前进行验证——见上面的捆绑陷阱。
- 内部名称不断泄露：`jira`、`owa`、`vpn`、`*.corp.example.com`、带有机架或数据中心代码的主机名，以及从未公开发布的产品代码名称。

## 通配符隐藏，不会揭示

`*.example.com`覆盖每个子域名，并且不包含任何子域名。一个切换到通配符的组织（通常与DNS-01 ACME自动化一起使用）从那时起在CT中实际上变得暗淡。当你看到一个通配符时：

- 在通配符之前挖掘CT，当时存在每个主机的证书。
- 转向被动DNS，它记录答案而不是证书。
- 检查存档和搜索索引以查找主机名（`read-deleted-pages`、`google-like-a-spy`）。
- 寻找由于技术原因必须保留自己证书的主机：通配符覆盖更深层的标签（`a.b.example.com`需要自己的），以及位于不同顶级域名上的任何内容。

## 结合来源，然后解析

CT给你历史。被动DNS给你观察到的现实。单词列表给你未发布的名称。使用所有三个，并按来源标记它们，因为你可以分配的置信度取决于名称来自哪里。

```bash
subfinder -d example.com -all -silent -o passive.txt   # 聚合许多被动来源
amass enum -passive -d example.com                     # 不同的来源组合，更慢
dnsx -l passive.txt -a -resp -silent                   # 将候选者解析为A记录
```

解析将候选者分为三个桶：解析到地址、解析到CNAME（读取目标——它命名了供应商，并且悬空的CNAME是报告的接管候选者），或者根本无法解析。死名称仍然是发现：它们标记了基础设施，揭示了命名约定，并且有时会再次解析。

**在你信任任何暴力破解结果之前，先检测通配符DNS。** 解析一个不可能存在的随机名称，例如`zzq7x-nonexistent.example.com`。如果它回答了，该区域解析一切，并且你的整个暴力破解列表都是误报。

明确划清界限：查询CT、被动DNS、搜索引擎和存档永远不会接触目标。通过公共递归解析器解析候选名称实际上是不可见的，但确实会生成查询。单词列表暴力破解是高容量的DNS流量，目标DNS提供商会看到，并且有时会因流量过大或被限制而阻止。使用`httpx`等工具对结果进行HTTP探测**是主动的**——你正在连接到目标的服务器。在你的范围笔记中标记暴力破解和探测，如果参与是被动-only的，则跳过它们。

## 名称模式意味着什么

不要将所有发现的托管主机视为平等。`dev`、`staging`、`uat`、`vpn`、`legacy`、`old`和admin面板与`www`承担非常不同的风险和后续工作。分类表在[reference/name-pattern-triage.md](reference/name-pattern-triage.md)中。

## 哪里会出错

- **捆绑和多租户证书。** 共享主机和CDN证书将不相关的客户放在一个证书上。始终检查证书上的其他名称是否可能属于你的目标，然后再采用它们。
- **CT不是资产清单。** 它是证书请求的记录。由内部CA、自签名证书、源证书或纯HTTP支持的主机不存在。永远不要将基于CT的列表报告为完整。
- **名称比主机存活。** 大多数历史CT名称都是死的。一个包含400个子域但无法解析的列表是400个未经验证的声明。
- **名称比所有权存活。** 当域名属于前一个所有者时签发的证书仍然会显示在当前所有者的查询下。通过`who-owns-this-domain`检查`not_before`与域的注册和转让历史。
