# 渐进式领域结晶（PDC）技能

## 此技能的作用

此技能使任何AI助手都能为任何业务应用构建和使用一个**动态领域知识库**，通过人机协作协议在会话中逐步积累。

AI默认情况下并不“知道”该领域。但有了此技能，它可以：
- 在每个会话开始时读取结构化的 `.tasks/domain.md` 文件
- 按照业务定义的精确方式使用内部术语和实体名称
- 在工作时内联标记领域理解的空白处
- 提出结构化的领域文件补充项供人工审核
- 从不破坏知识库——所有更新都是提议的，而不是自动应用的
- 通过渐进式披露管理领域知识增长——仅加载与当前会话相关的部分

---

## 核心协议

### 会话开始时

1. 在项目根目录中**查找 `.tasks/domain.md`**
2. 如果找到 → 检查文件结构：
   - **单个文件**（约200行以内）：在执行任何工作前完整读取它。
   - **索引+详细文件**（分结构）：读取根 `.tasks/domain.md` 索引（第一级——核心上下文）。然后确定哪些第二级详细文件与当前任务相关并仅加载那些。参见 § 渐进式披露。
3. 如果未找到 → 提议使用 `.tasks/domain.md` 中的模板初始化一个
4. 向用户确认：“我已经加载了 [项目名称] 的领域上下文。我熟悉 [N] 个实体和 [N] 个流程。” 如果在分模式中，也注明：“我已经加载了核心上下文。我将根据我们正在处理的内容按需加载详细文件。”

### 工作期间

- 按照在 `.tasks/domain.md` 中定义的**精确方式**使用实体名称、术语和缩写
- 当遇到未定义的术语或实体时，内联标记：`[UNKNOWN: <术语>]`
- 当实体之间的关系不明确时，标记：`[RELATIONSHIP UNCLEAR: <实体-a> → <实体-b>]`
- 当业务规则看似隐含但未记录时：`[RULE INFERRED: <描述>]`
- 不要编造领域事实——仅使用已记录的内容或在会话中用户确认的内容
- 在处理特定实体或流程时，如果存在且尚未加载，则加载其第二级详细文件

### 会话结束时

始终在最终响应的底部生成一个 `## 📋 提议的领域更新` 部分。

格式化为：

```markdown
## 📋 提议的领域更新

> 审核这些内容，并将确认的项目复制到您的 .tasks/domain.md

### 新发现的实体
- **[实体名称]**：[从本次会话中理解的定义]
  - 属性：[列表]
  - 相关于：[其他实体]

### 术语澄清
- `[术语]` → [纯定义]

### 确定的关系
- [实体 A] → [动词] → [实体 B]：[描述]

### 观察到的业务规则
- [规则描述]

### 开放性问题
- [ ] [关于模糊或不明确事项的问题]

### 建议的 .tasks/domain.md 部分添加/更新
- [ ] [具体的部分或条目更新]

```

人工审核此内容，按需编辑，并手动更新 `.tasks/domain.md`。这使人工成为领域权威。

## 渐进式披露

领域知识文件会随时间增长。一个在80行时工作良好的 .tasks/domain.md 在400行时会变得难以管理。渐进式披露使AI专注于当前会话相关的内容，同时保持对完整知识库的访问。

### 三级领域知识

| 级别 | 包含内容 | 加载时间 | 典型大小 |
|------|----------|----------|----------|
| **第一级——核心** | 项目概述、术语词汇表、实体名称（仅单行）、业务规则表、用户角色表 | **始终**，会话开始时 | 80–120行 |
| **第二级——工作上下文** | 实体完整描述（生命周期、注释、边缘情况）、流程步骤详解、关系图、集成点 | **按需**，会话涉及该实体或流程时 | 每个文件30–80行 |
| **第三级——存档** | 变更日志、已解决的问题、数据迁移笔记、供应商特定细节 | **明确请求**时，或在审查项目历史时 | 可变 |

### 每个级别包含的内容

**第一级——核心（根 .tasks/domain.md，始终加载）：**
- `## 项目概述` — 应用是什么、谁使用它、业务目标（5行）
- `## 领域边界` — 范围内内容、支持内容、明确排除内容。防止过度构建。
- `## 术语词汇表` — 内部行话映射到纯定义
- `## 实体注册表` — **名称和单行描述**（不是完整属性列表，不是生命周期细节，不是注释）。将其视为实体的目录。
- `## 状态模型` — 实体状态或生命周期阶段的命名枚举和有效状态转换。AI必须将这些视为唯一有效值。
- `## 业务规则` — 硬规则表（BR-001、BR-002等）。这些是AI必须始终知道的绝对真理。
- `## 用户角色` — 角色表
- `## 利益相关者地图` — 命名人员、他们与系统的关系、关键关注点、何时涉及他们。对采用和认可至关重要。
- `## 开放性问题` — 当前未解决的问题
- `## 详细文件` — 第二级文件的索引，带有一行摘要（见文件布局）

**第二级——工作上下文（单独文件，按任务加载）：**
- 实体完整规范——属性、生命周期、关系、注释、边缘情况（每个主要实体一个文件）
- 完整流程描述——步骤详解（每个流程一个文件）
- 关系图——实体到实体的完整表格
- 集成点——外部系统细节

**第三级——存档（单独文件，按请求加载）：**
- 变更日志——会话历史记录学到的内容
- 已解决的问题——已关闭的开放性问题历史记录
- 数据迁移笔记——供应商目录细节、导入程序
- 供应商特定细节——价格表结构、门户访问笔记

### 何时拆分：~200行规则

单个 .tasks/domain.md 适用于早期阶段项目。触发拆分很简单：

**当 .tasks/domain.md 超过~200行时，提议拆分。**

对用户说：“领域文件正在增长——[N]行，包含[N]个实体和[N]个流程。要我将它拆分为索引文件和详细文件吗？这样每个会话都会专注于相关内容，且不会丢失任何信息。”

如果用户同意：
1. 将第一级内容提取到精简的根 .tasks/domain.md（~80–120行）
2. 将每个实体的完整描述移动到 `docs/domain/entities/[name].md`
3. 将每个流程的完整描述移动到 `docs/domain/flows/[name].md`
4. 将关系图和集成点移动到它们各自的第二级文件
5. 将变更日志移动到 `docs/domain/archive/changelog.md`
6. 在根 .tasks/domain.md 中添加 `## 详细文件` 索引，并指向每个第二级文件带有一行摘要
7. 在保存前审核新结构

随着时间的推移，.tasks/domain.md 成为：
- 新开发人员的入职单源
- 未来AI会话（任何模型、任何工具）
- 文档和规格
- 测试用例基础
