# 前端设计

这是一种视觉设计护栏技能，而不是领域工作流技能。领域技能拥有所需的产品结构、术语、工作流和输出视图。这种技能拥有视觉质量，必须在那种结构内部应用。

## 强制性参考

在进行视觉规划或实施之前，请阅读这两个文件。跳过任何一个文件都是技能违规。

- `.agents/skills/frontend-design/references/visual-style-references.md`
- `.agents/skills/frontend-design/references/shadcn-setup-and-theming.md`

## 必需工作流

1. 阅读当前任务、领域上下文和选定的领域技能。
2. 当存在 `.tasks/domain.md` 时，请阅读它。提取品牌颜色、公司名称、领域语气、术语、工作流、实体、状态、角色和约束。
3. 阅读两个前端设计参考。
4. 在编码之前产出设计版本：
   - **愿景**：特定于领域的产品和视觉方向。拒绝通用的 SaaS 紫色、以卡片为主的仪表板和通用的管理员外壳。
   - **第一版功能**：可工作的屏幕、控件、路由、对话框和基于 localStorage 的状态。
   - **设计令牌**：主要、次要/强调色、背景、画布、焦点对比处理、文本、边框、半径、联系人阴影、状态颜色、排版、充足的间距和无需卡片的计划。
   - **设计方向**：强制使用品牌颜色、实际使用标志、轻盈的间距、轻盈的内部密度、圆角控件、强烈的输入对比、柔和/紧凑的阴影、最小的视觉噪音、无需卡片的默认值和授权的构图。如果选定的领域技能没有指定结构，则使用更强的视觉想法，如不对称性、故意的负空间、鲜明的强调色层级、动感和大气背景细节。
5. 通过设计合规性门。
6. 在构建屏幕细节之前配置 CSS 变量、Tailwind/shadcn 主题令牌以及相关的 shadcn 组件样式。
7. 使用这些令牌构建 UI。在 Tailwind 有用的地方使用 Tailwind，当 Tailwind 有限制时编写自定义 CSS 类；自定义 CSS 必须重用全局 CSS 变量、半径、颜色和阴影令牌。
8. 运行预完成审计并在完成前修改。

## 非协商项

- **品牌优先**：如果 `.tasks/domain.md` 提供了品牌颜色，请使用它们。将主要品牌/强调色映射到主要操作、活动导航、选中状态、焦点和链接。从兼容的色调中导出中性表面、边框、柔和文本和状态。不要默认使用通用的紫色/蓝色。
- **始终可读的前景**：使用品牌颜色作为主要、次要、强调色、活动和焦点角色，但单独选择前景/文本颜色以确保可读性。品牌调色板通常不提供所有文本颜色。每个文本、图标、标签、占位符、徽章、按钮、禁用状态和数据值都必须与其实际背景具有高对比度。当品牌颜色是背景时，为其导出一个可读的前景颜色，而不是重复使用另一个品牌颜色。优先考虑 WCAG AA 作为最低标准：正常文本为 `4.5:1`，大文本/图标为 `3:1`。
- **领域技能兼容性**：如果应用程序符合选定的商业/领域技能，如 CPQ、CRM、贸易或类似技能，请遵循该技能所需的工作流、术语和布局结构。对于领域技能没有指定的任何内容，请使用此技能的视觉规则和构图指导，而不是退回到通用的管理员外壳。
- **授权的构图**：每个应用程序都应该感觉是经过有意设计的。致力于一个连贯的审美，始终如一地使用 CSS 变量，优先选择主导颜色和锐利强调色，而不是胆怯的均匀分布调色板，在不会与工作流清晰度冲突的地方使用运动，在不会与工作流清晰度冲突的地方偏爱不对称或意想不到的构图，并通过与品牌兼容的背景和视觉细节营造氛围。
- **使用真实标志**：首先查看 `public/brand/logos/`。如果该文件夹包含可用的标志文件，请在标题或主要应用程序外壳中使用该文件夹中的正确实际标志。只有在 `public/brand/logos/` 不存在或没有可用的标志文件时，才创建或发明标志。
- **默认无需卡片**：目标是零卡片。如果 UI 可以无需卡片工作，则不允许使用卡片。即使没有导入 `Card`，占据页面主要区域的带边框圆角表面也是卡片。仅在对话框/弹出/表单容器、简洁通知或当行、分隔符或色调分离失败时真正重复的项时才允许卡片。
- **默认无需顶级卡片**：永远不要用大型兄弟卡片、圆角面板的堆栈/网格或大型框架式英雄/详情容器组成主页面。顶级结构必须是开放式部分、色调带、行、分隔符、工作区或一个开放式焦点工作区。
- **默认无需侧边栏**：只有在用户明确要求或选定的领域技能明确要求时才使用侧边栏。不要因为应用程序是可操作的、商业的、管理员式的、多步骤的或具有多个部分而添加侧边栏。
- **轻盈的间距**：使用充足的间隙、间距、行节奏和部分间距。稍微过多的间距是可以接受的；拥挤、密集或压缩的 UI 是失败的。
- **轻盈的内部密度**：轻盈必须在行、表格、列表、卡片和复合组件内部继续。当更清爽的堆叠或更丰富的行布局会呼吸更好时，不要将太多列压缩到一行中。内部内容应在子元素、元数据、操作和标签之间使用充足的间隙。
- **表格节奏**：当使用表面化表格时，给表格 `shadow-xs` 并使用充足的表头填充、行填充和更高的行节奏。表格不应感觉被压缩、扁平或像电子表格一样紧凑。
- **默认圆角**：如果选定的领域技能没有明确要求更尖锐或特定的半径语言，则优先选择一个清晰圆角的现代系统。默认情况下避免胆怯的 4px/6px/8px 管理员半径。控件、芯片、选项卡和关键表面通常应该感觉明显圆角或像药丸一样。
- **具有个性的排版**：选择美观、独特和有趣的字体。避免通用的默认字体，如 Arial 和 Inter。当产品可以支持时，优先选择一个具有个性的显示字体与一个精致的正文字体搭配。排版应该提升 UI，而不是像默认的启动应用程序一样阅读。
- **一个主导的工作表面**：第一个屏幕应该专注于一个清晰的操作对象或工作部分。不要试图一次显示整个产品。
- **无需主要区域框架化表面**：不要将主要工作区域、英雄、检查器或详情车道变成一个大的带边框圆角面板。优先选择开放式布局、分割行、色调带、分隔符或抽屉/表单。
- **令牌优先的 shadcn 和 CSS**：在组件工作之前配置 `app.css`/全局 CSS 变量、Tailwind 主题值和相关的 shadcn 组件样式。不要接受默认的 shadcn 颜色或组件样式作为设计。shadcn 组件只是基础原语；始终自定义它们的类/样式以适应应用程序的令牌、间距、对比度、半径、阴影和交互规则。Tailwind 不是每个视觉决策的必需品；当自定义 CSS 创建更独特、更简洁、更精致的 UI 时，编写自定义 CSS，同时重用相同的 CSS 变量和主题令牌。
- **强烈的柔和对比**：如果表面存在，它必须首先通过色调与画布分离，其次通过边框，最后通过阴影。相同白色或接近白色的表面带有微弱边框会失败。
- **交互表面对比**：每个可编辑控件都必须明显。常规文本输入、选择、文本区域、组合框、日期字段、搜索字段、命令栏控件和 shadcn 表单控件在浅色模式下必须使用接近白色或非常浅色调的背景，在暗色模式下使用接近黑色的背景。不要只修复选择器而将普通输入保留为页面颜色。控件不能使用 `bg-transparent`、`bg-background`、`bg-muted` 或与页面/面板相同的填充。`--input` 在浅色模式下必须比 `--background` 明亮，在暗色模式下必须比画布暗。搜索/过滤控件必须是屏幕上最清晰的输入表面之一。
- **不可避免时的面板/卡片对比**：如果卡片状表面确实是不可避免的，包括摘要面板、实时摘要卡片、检查器、通知和重复项容器，它必须在浅色模式下使用明显对比的接近白色或非常浅色调的背景，在暗色模式下使用接近黑色。即使在边框可见的情况下，色调相同的面板在色调页面上也会失败。
- **存在时的标题处理**：如果应用程序有标题/顶部栏，则优先选择浅色模式下透明的接近白色或非常浅色调的表面，暗色模式下接近黑色，带有 `backdrop-blur-md` 和大约 `70-80%` 的不透明度。标题仍然必须与页面有足够的对比度，并且在有可用时必须使用真实标志。
- **需要时的侧边栏色调和空间**：如果选定的领域技能需要侧边栏，请使用从主要颜色派生出的非常深的色调作为侧边栏背景或关键侧边栏表面。侧边栏必须有足够的宽度以容纳其标签、徽章和活动状态；不要剪裁文本或将操作挤压到边缘。使用充足的项填充、清晰的垂直节奏，并且仅在次要描述中才故意截断。
- **仅联系人深度**：避免将 `shadow-sm`、`shadow-md` 和 `shadow-lg` 作为正常布局表面的默认值。优先为按钮和其他小型交互元素使用 `shadow-2xs`，为卡片/表格/类似容器表面使用 `shadow-xs`，为弹出和横幅使用 `shadow-xl`，为对话框使用 `shadow-2xl`。仅在需要时使用柔和的、紧凑的、联系人边缘深度。柔和意味着没有硬边，不是几乎看不见；阴影仍然可以是清晰的灰色，如果需要对比度的话。深度应该读作边缘接触，而不是提升。
- **领域特定性**：UI 在领域名称和标签交换后不应感觉没有变化。

## 设计合规性门

在所有答案都接受之前不要编码。

- 我是否阅读了 `.tasks/domain.md` 并在存在时总结了品牌颜色？
- 我是否检查了 `public/brand/logos/` 并计划如果存在，则使用该文件夹中的实际标志文件？
- 我是否阅读了两个前端设计参考？
- 我是否定义了精确的全局 CSS 变量、Tailwind/shadcn 令牌和 shadcn 组件样式更新？
- 我是否在领域技能使用授权视觉构图的空间内遵循了必需的领域技能结构？
- 我是否为颜色、运动、空间构图和背景氛围选择了明确的指导方向，而不是通用的外壳？
- 这个 UI 是否可以零卡片构建？如果不能，是否每个剩余卡片都在狭窄的允许情况下不可避免？
- 是否没有顶级卡片？
- 我是否避免使用侧边栏，除非明确要求或选定的领域技能明确要求？
- 第一个屏幕是否专注于一个主导的工作表面，而不是标题 + 过滤器 + KPI 条带 + 卡片网格 + 表格？
- 我是否避免使用大型框架化的英雄/详情/检查器表面？
- 布局是否轻盈，具有充足的间距，而不是密集？
- 内部密度是否也轻盈：行、表格、卡片和元数据块是否没有拥挤或过度列？
- 如果没有领域技能覆盖半径语言，UI 是否明显倾向于圆角，而不是模糊的企业 4/6/8 半径？
- 排版是否感觉独特且有意，而不是默认/通用？
- 页面背景、画布、导航外壳和任何焦点表面在缩略图比例下是否清晰分离？
- 所有前景颜色是否与其背景可读，包括品牌颜色区域、禁用状态、标签、占位符、徽章、按钮、图标和柔和文本？
- 输入、搜索/过滤控件、表格和标题/导航外壳是否与页面背景有足够的色调分离？
- 在浅色模式下，所有可编辑控件，包括普通文本输入和选择器，是否实际使用接近白色或非常浅色调的背景，而不是页面颜色填充？
- 可编辑控件是否没有 `bg-transparent`、`bg-background`、`bg-muted` 和相同令牌的页面/面板填充？
- 摘要/检查器/实时摘要面板是否使用清晰的接近白色/浅色调表面，而不是与页面融合？
- 如果存在标题/顶部栏，它是否使用清晰的半透明处理、模糊背景和足够的对比度？
- 如果表面化表格，它是否使用 `shadow-xs` 加上充足的表头和行填充？
- 如果需要侧边栏，它是否使用更深的派生色调，并具有足够的宽度、填充、行高度和溢出处理？
- 阴影是否仅限于联系人边缘深度？
- 设计是否对此领域和任务有特定的感觉？

## 实施规则

- 优先选择顶部栏、选项卡、分段控件、面包屑、命令行、分步流程、抽屉、表单、对话框或详情路由，而不是侧边栏。
- 在添加任何卡片状包装器之前，尝试开放式间距、排版、分隔符、行、色调带、表格、抽屉、表单、对话框或详情路由。
- 在表格和基于行的视图中，优先选择较少的列、更丰富的行、更高的行节奏和更清晰的垂直堆叠，这样 UI 会感觉更轻盈和可读。
- 表面化表格通常应使用 `shadow-xs`、充足的表头填充和充足的主体行填充，而不是仅依赖边框。
- 详情视图应优先选择内联分割布局、选中行、分隔符、色调部分、抽屉或表单，然后再使用任何框架化面板。
- 如果导入 `Card` 组件或卡片状包装器仍然存在，请添加附近的内联说明，解释为什么它在允许的情况下不可避免。
- 使用良好的可读 UI 字体。除非领域明确要求，否则避免打字机/博客字体。
- 在不会与必需的工作流结构或操作清晰度冲突的地方，使用更富表现力的构图、更强的强调色层级和更大气背景。
- 通过色调、间距和层次结构而不是围绕所有内容的边框和框来使表面区分开来。
- 首先为对比度选择前景/文本颜色。除非它们在确切表面上明显可读，否则不要将品牌主要/次要/强调色视为正文文本颜色。
- 为输入/选择/文本区域/搜索字段提供明确的对比填充；不要让它们保持透明或页面颜色。
- 当不可避免时，为摘要/检查器/实时摘要面板提供明确的对比填充。
- 如果存在标题/顶部栏，请使用令牌驱动的半透明背景、`backdrop-blur-md` 和清晰对比度，而不是扁平的相同颜色条。
- 对于必需的侧边栏，请使用足够的宽度和项高度，以便可读的标签、可见的活动状态和非剪裁的徽章/操作。
- 如果卡片确实不可避免，请为其提供与画布有意色调对比的可见但柔和的边框。薄弱的相同白色卡片会失败。
- 仅添加实际工作流所需的 shadcn 组件。
- 始终自定义 shadcn 组件类/样式，以便输入、按钮、表格、选项卡、对话框、表单、导航遵循此应用程序的视觉规则，而不是默认的组件样式。
- 当 Tailwind 通用工具变得有限制时，使用自定义 CSS 类来增强布局、背景、间距和组件处理；通过全局主题的 `var(...)` 颜色、半径、边框和阴影，使这些类令牌驱动。
- 保持所有按钮、链接、菜单、对话框、选项卡、表单、路由和基于 localStorage 的状态功能。

- 任何顶级卡片都存在。
- 任何可避免的卡片仍然存在。
- 任何大型圆角边框区域都被视为英雄卡片、检查器卡片或详情卡片。
- 侧边栏在没有明确用户请求或选定领域技能需求的情况下存在。
- 第一屏主要是面板、卡片、KPI模块、辅助框或等权重模块。
- 表面分离主要依赖于边框而非色调。
- 同色或近白色的面板化使主要表面相互融合。
- 任何文本、图标、标签、占位符、禁用文本、徽章、按钮文本、表格文本或数据值在其背景上都难以阅读。
- 品牌颜色被使用，但没有为实际背景导出高对比度的前景/文本颜色。
- 输入、搜索/筛选控件、数据行或头部/导航铬合金融入页面背景。
- 浅色模式下的可编辑控件不是近白色或非常浅的色调，因此难以清晰阅读。
- 选择控件有对比度，但普通文本输入仍然保持页面颜色或被淡化。
- 可编辑控件使用 `bg-transparent`、`bg-background`、`bg-muted` 或与页面或面板相同的标记/填充。
- 摘要/检查器/实时摘要卡片或面板使用与页面相同的填充，而不是近白色/浅色调对比表面。
- 头部/顶部栏存在，但缺乏清晰的半透明 `backdrop-blur-md` 风格或与页面融合。
- 行/表格内容拥挤、列过多或第一列和元数据块内过于紧凑。
- 表面化的表格缺少 `shadow-xs` 或其头部/行填充过于紧密。
- `public/brand/logos/` 包含可用的标志文件，但头部仍然使用占位符标志或无理由不使用标志。
- 来自 `.tasks/domain.md` 的品牌颜色未反映在主要/激活/焦点处理上。
- UI 默认为通用管理外壳，而不是在允许的情况下使用授权组合。
