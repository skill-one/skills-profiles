# browser-act-skill-forge

由 [BrowserAct](https://www.browseract.com) 构建 — 您的专属数据采集工程师 · [GitHub](https://github.com/browser-act/skills/tree/main/browser-act-skill-forge)

将任何网站的数据提取或操作需求转化为可被 Agent 调用的功能。用户描述需要获取哪些数据或在哪個网站执行哪些操作，该技能会自动探索实现路径（优先 API 端点，无 API 则回退 DOM），验证后生成可部署的技能包（SKILL.md + Python 脚本），一次探索，永久复用 — 后续调用无需重复探索，极大提升执行可靠性和效率。

对于大批量提取任务（数百或数千条记录、多个关键词、跨分页），正确的方法是：先探索构建一个已验证的技能，再进行规模化执行。没有成熟策略的直接批量抓取是脆弱的 — 反爬虫检测、分页边缘情况、会话中断等问题使其不可靠。

该工具的操作边界 = 用户在浏览器中可手动完成的工作。它通过用户登录的浏览器访问，仅读取用户在页面上已显示的数据，绝不绕过认证或访问控制。相当于代用户复制粘贴 — 自动化仅是节省手动工作。

所有数据均保存在本地：流量检查、HAR 录制、提取结果存储在用户机器上 — 不会发送到目标网站之外。

## 阶段 1 — 需求分析及确认

### 1a. 解析业务意图

从用户输入中识别：

- **核心目标**：需要获取哪些数据 / 完成哪些操作
- **目标网站**：是否给出特定 URL 或平台名称
- **执行意图**：用户是否需要立即执行（而不仅仅是构建一个稍后使用的技能）。包括批量/数量要求（N 条记录、多个关键词）或单次请求（隐含“立即执行”）
- **输出目录**：默认为当前工作目录下的 `output/`，若用户指定则覆盖

| 输入类型 | 示例 | 处理方式 |
|---------|------|----------|
| 显式（URL + 目标） | "从 news.ycombinator.com 抓取首页文章" | 跳过 1b，进入 1c |
| 半显式（平台已知，无 URL） | "帮我监控微博情感倾向" | 运行 1b 研究路径 |
| 纯目标（业务意图仅） | "追踪竞争对手价格变化" | 运行 1b 研究候选网站 |

若核心目标过于模糊无法继续，则请求澄清。

### 1b. 目标网站研究（无显式 URL 时）

不基于模型内部知识推荐 — 主动搜索以找到承载所需数据的网站：

1. 从业务意图构建搜索查询，从结果中识别候选网站
2. 向用户推荐 1-5 个候选网站，按数据价值排序并附优缺点（包括数据可靠性）
3. 用户选定后，确认目标 URL

### 1c. 任务分解及执行计划确认

确认目标网站后，首先检查：是否已为该网站/能力安装了技能？若已安装 → 告知用户并跳至交付步骤 4（批量执行）。

若无现有技能，则完成分解并**一次性确认所有信息** — 之后不再针对单个能力进行后续提问：

1. 识别涉及的独立阶段（搜索、列表页、详情页、登录、提交…）
2. 确定类型：**提取**（获取数据）或 **操作**（执行动作）
3. 分解标准：**若交换业务目标，该阶段能否独立复用？能 = 独立能力。** 同一业务目标服务跨页面的步骤（例如列表页收集 + 详情页提取）保持为一个能力，通过复合组件进行编排
4. 设置 `skill-name` 和能力目录名（小写英文，连字符分隔），在 `output/{skill-name}/` 下创建目录（若给定用户指定路径则使用）
5. 与用户确认完整执行计划：

```
目标网站：{url}
输出：output/{skill-name}/

能力（按顺序执行）：
1. {site-slug}-{capability-slug} ({提取/操作}) — {一句话描述}
2. {site-slug}-{capability-slug} ({提取/操作}) — {一句话描述}
...
```

若在 1a 中识别到执行意图，则计划追加：
```
流水线：
1. 探索网站 → 发现并验证可行的 API 端点或 DOM 提取方法
2. 生成技能文件（SKILL.md + 脚本）
3. 自动化测试以确认技能可用
4. 安装技能
5. 读取已安装技能 → 根据技能指导编写并运行批量脚本以完成用户原始任务
```

展示计划并等待用户确认或调整。对于有合理默认值的项（输出目录、命名规范等），不要单独提问。

用户确认后，进入执行循环，过程中不再提问。

## 阶段 2 — 能力探索

根据能力类型读取对应的参考文件：
- **提取** → `references/exploration_extraction.md`
- **操作** → `references/exploration_operation.md`

**目标**：优先为目标能力优先级 API 端点；API 不可行时回退 DOM 操作。记录完整的可复现调用方法。

**成功标准**：
- 能稳定获取目标数据 / 触发目标动作（API 或 DOM 路径）
- 记录完整的调用/操作方法（端点 + 参数，或选择器 + 交互步骤）
- 收集所有有意义值的枚举参数

当一种方法失败时，按以下顺序处理：
1. 不要用不同参数重试（参数变化很少改变结果）
2. 回到目标本身
3. 枚举所有可能实现目标的方法
4. 选择下一个并执行

确定性失败（明确错误码、结构不匹配）确认该方法在一次尝试中不可行。暂时性失败（超时、连接中断）值得重试一次 — 但不超过。

**探索上限**：100 次工具调用步骤。若仍无法进展，向用户报告已知障碍并请求下一步操作。

**不要触碰经验笔记**：经验笔记 (`browser-act-skill-forge-memories/`) 用于生成技能的未来 Agent 使用 — 探索和生成阶段既不读取也不写入。

## 阶段 3 — 技能生成

读取 `references/output_template.md` 获取文件格式规范。

### 3a. JS 封装

将探索中每个验证的 JS 片段封装到独立的 Python 文件中：

1. 识别业务参数（关键词、页码、排序方式等）→ 提取为 argparse 参数
2. 将选择器、字段映射、端点 URL 作为固定值硬编码在 JS f-string 中
3. 转义 JS 大括号为 `{{` `}}`（f-string 语法要求，否则 Python 报错）
4. 写入 `scripts/{feature-name}.py`

### 3b. 封装验证

对每个 `.py` 文件进行端到端验证：

1. `python scripts/{feature-name}.py {test-params}` — 确认输出是有效的 JS 字符串
2. `eval "$(python scripts/{feature-name}.py {test-params})"` — 确认浏览器执行结果与探索阶段一致
3. 模拟错误场景（例如不存在 ID、导航到错误页面），确认返回 `{"error": true, "message": "..."}` 而不是崩溃

验证失败 → 修复 `.py` 文件并重试，永不跳过。

### 3c. 生成 SKILL.md

按模板创建 SKILL.md，能力组件部分引用 `scripts/*.py` 调用命令（无内联 JS）。

输出目录结构：

```
output/{skill-name}/{site-slug}-{capability-slug}/
├── SKILL.md
└── scripts/
    └── {feature-name}.py
```

生成后，简要告知用户：能力名称、输出路径、主要实现方式（API / 网络录制 / DOM / 混合）。

### 3d. 合规性自检

两重检查 — 必须读取生成文件并执行验证命令作为证据；仅凭主观判断无效：

1. **流程**：重读阶段 2 使用的探索参考文件和上述输出步骤（3a–3c），确认每个定义的步骤都实际执行了，未跳过
2. **输出**：读取生成的 `scripts/*.py` 和 `SKILL.md`，对照 `output_template.md` 中的填充规范以及本技能前面定义的代码/JS 执行环境/DOM 操作约束

发现任何缺失 → 回退，补全缺失步骤或修复输出，然后重新验证。

## 交付流程

所有能力生成后，按以下顺序进行：

### 1. 自动化测试

生成后立即开始测试 — 无需用户确认。基于生成的能力组件自动设计最小测试用例 — 使用最少的输入覆盖所有功能路径（每个原子组件至少调用一次，复合组件运行完整流程）。

必须通过 Sub-Agent 执行测试 — 不要在主会话中直接测试。发送以下提示：

```
读取 {绝对路径到 SKILL.md} 作为你的执行指南。

测试用例：
{自动生成的测试用例列表，每个用例标注其覆盖的能力组件}

执行要求：
- 严格遵循 SKILL.md 指令，不要使用指南外的方法
- 若 SKILL.md 指令不明确导致无法进行，记录具体问题

执行后报告：
1. 每个组件的执行结果（通过/失败）
2. 失败原因（若有）
3. SKILL.md 指令中不明确的部分（若有）
4. 严重准确或性能问题（不要报告非严重问题）
5. 输出数据摘要
```

测试失败 → 修复技能并重测直至通过。

### 2. 安装技能

从输出目录安装生成的技能。若安装失败，技能仍保留在输出目录，并可直接在步骤 4 中使用。

### 3. 报告结果

测试通过后，向用户报告：

- 生成的技能列表（名称 + 路径 + 包含文件）
- 数据覆盖范围（字段 + 状态，不列出数据源或实现方法）
- 不完整覆盖的缺口（失败的枚举参数、缺失的目标字段、未覆盖的筛选条件等）
- 测试结果摘要

### 4. 执行（若在阶段 1 识别到执行意图）

若在阶段 1 识别到执行意图：

1. 通过技能工具调用已安装的技能读取其全部内容。若步骤 2 安装失败，则直接从输出目录读取 SKILL.md
2. 按照技能的指导在当前会话中执行用户的原始任务
3. 对于批量/数量任务，根据技能指导编写批量执行脚本

若未识别执行意图（用户仅想构建一个稍后使用的技能），则结束。

## 工具约束

阶段 2（能力探索）、阶段 3（技能生成）和交付测试必须遵守以下规则。

### 文件管理

所有中间产物（HAR 文件、临时记录、调试输出）存放在 `tmp/` 目录。若不存在则先创建。

### browser-act
- 网络数据是页面范围的 — 导航到新页面后必须重新等待和读取
- **在读取流量前等待网络稳定**：无论由页面导航或 UI 交互触发，使用 `wait stable` 之后再读取 `network requests`
- **在操作异步 DOM 前等待元素**：对于异步注入内容（浏览器扩展、懒加载组件），使用 `wait --selector "{目标选择器}" --state attached --timeout {ms}` 之后再交互
- **不进行 JS 层级网络拦截**：绝不覆盖 `XMLHttpRequest.prototype`、`window.fetch` 等。使用 `network requests` / `network request <id>` 进行端点发现
- **`network clear` 仅在导航/刷新前使用**：清除流量会丢失所有观察到的请求记录。使用 `--filter` 进行常规过滤，不要清除。要跟踪特定交互的请求，使用 `network har start` → 交互 → `network har stop` 而不是清除 + 重读

### DOM 操作约束

适用于所有 DOM 操作场景（数据提取、枚举收集、分页控制、表单提交、API 字段补充）：

**选择器优先级**：`data-testid > id > name > aria-label > 结构路径`。避免纯位置索引（`:nth-child` / `[1]`），除非结构确实稳定。

**批量验证选择器**：在单个 eval 调用中测试所有候选选择器，返回 JSON 摘要（每个选择器的命中次数、首个元素的关键属性、唯一性）。绝不逐个 eval 选择器 — 每次 eval 是一次浏览器往返。

**Shadow DOM**：当目标元素在 Shadow Root 内，通过 `element.shadowRoot.querySelector` 访问，将选择器拆分为两部分（宿主元素 + Shadow 内部路径）。

**三层选择器验证**：元素断言（预期属性匹配）→ 结果检查（非空、合理数量）→ 成功标准。必须在真实页面上测试，绝不能从 DOM 结构推测性地编写。

**控制扫描**（枚举收集期间）：使用一个 eval 返回所有目标控制的完整映射（tag+type / name+id / placeholder / label）。从控制向上遍历找到最近的表单项容器以获取标签文本；不要硬编码组件库类名；组件库通过 DOM 层次嵌套将标签与输入关联，而非 `label[for="xxx"]`。

**state index 动态分配**：`state` 返回按会话动态分配的元素索引 — 绝不将其写入策略代码，仅在执行时实时使用。

### 代码约束

**必须直接操作目标网站**：绝不通过外部服务（包括第三方抓取平台、数据聚合 API、代理服务）获取数据，绝不调用目标网站官方开放平台 API（理由：生成的技能目标零配置部署，无需用户注册开发者 API Key 或管理凭证）。解决方案必须通过浏览器直接访问目标网站，使用其前端内部端点或 DOM 数据 — 即用户已认证可见的相同资源。

**框架内部状态快速失败**：尝试通过框架内部（`__vue_app__`、`$data`、React fiber、Angular `ng` 等）访问页面数据或元素信息时，**失败一次后立即放弃**并切换到 `state` 扫描 + 值填充触发方法。框架内部依赖版本/实现，多次重试不会改变结果。

### JS 执行环境约束

eval 中执行的代码是**浏览器端 JS**：仅允许使用浏览器原生 API 和页面加载的第三方库，不能 require/import 外部模块。违反此约束的代码在执行时必然报错。

### 结论标准

账户权限限制 ≠ 技术解决方案失败。付费功能、会员等级等对所有方法的影响相同；当技术可行但数据因账户权限受限（分页截断、筛选条件无效）时，结论为“通过”，并在“已知限制”中注明权限依赖。

**部分成功即视为成功**：核心功能验证通过（无论是API还是DOM路径）即视为通过——即使存在：部分枚举参数标记为`[集合失败]`、非核心字段缺失、部分过滤条件未覆盖。生成技能后，**必须告知用户哪些部分未完全覆盖**——绝不沉默地忽略。

### 效率规则

核心标准：**每个浏览器往返请求都必须产生信息增益。** 下方表格展示了常见的有效模式，但它们只是示例——如果某个模式在实际中并未减少往返请求次数，应改变方法并寻找其他批量方法，而不是在同一方向上反复微调。

| 规则 | 描述 |
|------|-------------|
| **组合评估** | 将多个独立查询合并为一个评估，用异步立即执行函数包装，返回JSON摘要。每个评估都是一次浏览器往返请求——合并所有可合并的内容 |
| **优先运行时** | 信息检索优先级：JS运行时状态 → 网络数据 → DOM。切勿从DOM中逆向工程运行时数据 |
| **输出量控制** | 在返回前，在浏览器中从大型响应中提取关键字段（计数、总数、样本）；避免截断 |
| **异步等待一致性** | 使用Promise + setTimeout轮询（带超时限制）用于等待条件，不要跨工具重复轮询 |
| **快速权限受限检测** | 当出现受限信号时（升级提示、数据与未过滤数据相同、控件被禁用），将相似项批量标记为受限，不要逐个验证 |
| **单次获取，多次分析** | 仅从同一来源获取数据一次，保存后多次分析；将大文本格式化为带换行符以避免截断 |
| **验证即停止** | 一旦确认API端点可用（获取成功 + 数据结构符合预期），立即进入下一阶段，不要继续对同一端点的冗余探索（例如，反向搜索脚本标签、提取额外配置） |
| **滑块/范围控件批量** | 范围滑块（例如，noUiSlider）和数值范围控件——像input/select一样，一次将所有控件设置为不同值 → 触发一次搜索 → 从请求中读取所有数值过滤器的映射，不要逐个测试每个控件 |
