# Autoresearch：自主迭代实验

一个用于任何编程任务的自主实验循环。您定义目标以及如何衡量它；代理将自主迭代——修改代码、运行实验、测量结果并保留或丢弃更改——直到被中断。

这项技能受 [Karpathy 的 autoresearch](https://github.com/karpathy/autoresearch) 启发，从机器学习训练推广到**任何具有可衡量结果的编程任务**。

---

## 代理行为规则

1. **必须** 在开始循环之前，通过交互式方式引导用户完成设置阶段。
2. **必须** 在进行任何更改之前，建立基线测量。
3. **必须** 在运行实验之前提交每个实验尝试（以便可以干净地回滚）。
4. **必须** 保留一个结果日志（TSV），跟踪每个实验。
5. **必须** 回滚未提高指标的更改（git reset 到最后一个已知良好状态）。
6. **必须** 一旦循环开始就自主运行——永远不要暂停询问“是否继续？”。
7. **不得** 修改用户标记为超出范围的文件。
8. **不得** 跳过测量步骤——每个实验都必须被测量。
9. **不得** 保留使指标恶化的更改，除非用户明确允许权衡。
10. **不得** 安装新的依赖项或进行环境更改，除非用户批准。

---

## 第一阶段：设置（交互式）

在进行任何实验之前，与用户一起建立这些参数。
直接询问用户每个项目。不要假设或跳过任何。

### 1.1 定义目标

询问用户：

> **您试图改进或优化什么？**
>
> 示例：执行时间、内存使用、二进制文件大小、测试通过率、代码覆盖率，
> API 响应延迟、吞吐量、错误率、基准分数、构建时间、捆绑包大小，
> 代码行数、圈复杂度等。

将用户的答案记录为**目标**。

### 1.2 定义指标

询问用户：

> **我们如何衡量成功？确切地运行什么命令来产生指标？**
>
> 我需要：
> 1. **运行命令**（例如，`dotnet test`、`npm run benchmark`、`time ./build.sh`、`pytest --tb=short`）
> 2. **如何从输出中提取指标**（例如，正则表达式模式、特定行、JSON 字段）
> 3. **方向**：是低更好还是高更好？
>
> 示例：“运行 `dotnet test --logger trx`，计算通过测试的数量。高更好。”
> 示例：“运行 `hyperfine './my-program'`，提取平均时间。低更好。”

记录：
- `METRIC_COMMAND`：运行命令
- `METRIC_EXTRACTION`：如何从输出中提取数值指标
- `METRIC_DIRECTION`：`lower_is_better` 或 `higher_is_better`

### 1.3 定义范围

询问用户：

> **我可以修改哪些文件或目录？**
>
> 哪些文件是禁止修改的（只读）？

记录：
- `IN_SCOPE_FILES`：代理可以编辑的文件/目录
- `OUT_OF_SCOPE_FILES`：不得修改的文件/目录

### 1.4 定义约束

询问用户：

> **我应该尊重任何约束吗？**
>
> 示例：
> - 每个实验的时间预算（例如，“每次运行应少于 2 分钟”）
> - 不引入新依赖项
> - 必须保持所有现有测试通过
> - 不得更改公共 API
> - 必须保持向后兼容性
> - VRAM/内存限制
> - 代码复杂度限制（优先选择更简单的解决方案）

记录为 `CONSTRAINTS`。

### 1.5 定义实验预算（可选）

询问用户：

> **我应该运行多少个实验，或者我应该一直运行直到您阻止我？**
>
> 您可以说一个数字（例如，“尝试 20 个实验”），或者“无限”（我将运行直到您中断）。

记录为 `MAX_EXPERIMENTS`（数字或 `unlimited`）。

### 1.6 简易性标准

告知用户默认的简易性策略：

> **简易性策略（默认）**：在其他条件相同的情况下，简单更好。一个小改进带来的丑陋复杂性不值得。在保持或提高指标的同时删除代码是一个很好的结果。我将权衡复杂性的成本与改进幅度。这个策略对您有效吗，还是您想调整它？

将任何调整记录为 `SIMPLICITY_POLICY`。

### 1.7 确认设置

将所有参数清晰地总结回用户，以表格形式：

| 参数          | 值                        |
| ------------- | ------------------------- |
| 目标          | ...                       |
| 指标命令     | ...                       |
| 指标提取     | ...                       |
| 方向          | 低更好 / 高...           |
| 在范围内文件 | ...                       |
| 超出范围文件 | ...                       |
| 约束          | ...                       |
| 最大实验    | ...                       |
| 简易性策略  | ...                       |

询问用户确认。在确认之前不要继续。

## 第二阶段：分支和基线

一旦用户确认：

1. **创建分支**：基于今天的日期建议一个标签（例如，`autoresearch/mar17`）。
   创建分支：`git checkout -b autoresearch/<tag>`。

2. **读取在范围内文件**：读取所有在范围内的文件，以构建当前状态的完整上下文。

3. **初始化 results.tsv**：在仓库根目录创建 `results.tsv`，带有标题行：
   ```
   experiment	commit	metric	status	description
   ```
   将 `results.tsv` 和 `run.log` 添加到 `.git/info/exclude`（如果尚未存在，则追加），以便它们保持未跟踪，而不会修改任何已跟踪文件。

4. **运行基线**：在当前未修改的代码上执行指标命令。
   将结果记录为实验 `0`，状态为 `baseline` 在 `results.tsv` 中。

5. **向用户报告基线**：
   > 基线建立：**[metric_name] = [value]**
   > 开始自主实验循环。

---

## 第三阶段：实验循环

连续运行此循环。不要停止询问用户。运行直到：
- `MAX_EXPERIMENTS` 达到，或
- 用户手动中断

### 对每个实验：

```
LOOP:
  1. 思考   - 分析先前的结果和当前代码。
              生成实验假设。
              考虑：什么有效，什么无效，什么还没有尝试过。

  2. 编辑   - 修改在范围内的文件以实现想法。
              每个实验的更改应保持专注和最小化。

  3. 提交   - git add + git commit 带有简短的描述性消息。
              格式：`"experiment: <简短描述更改的内容>"`

  4. 运行   - 执行指标命令。
              将输出重定向到 run.log，以免淹没上下文窗口。
              使用适当的 shell 重定向：
              - Bash/Zsh: `<command> > run.log 2>&1`
              - PowerShell: `<command> *> run.log`

  5. 测量   - 从 run.log 中提取指标。
              如果提取失败（崩溃/错误），读取 run.log 的最后 50 行以获取错误。

  6. 决策   - 将指标与当前最佳值进行比较：
               - 改善：保留提交。更新“最佳”基线。
                 记录状态 = "keep"。
               - 相同或更差：回滚。`git reset --hard HEAD~1`。
                 记录状态 = "discard"。
               - 崩溃：尝试快速修复（拼写错误、导入、简单错误）。
                 使用 `git commit --amend` 修复实验提交，并重新运行。
                 实验保留其原始编号。
                 如果在 2 次尝试后无法修复，回滚整个实验
                 (`git reset --hard HEAD~1`) 并记录状态 = "crash"。

  7. 记录   - 将一行追加到 results.tsv：
               experiment_number  commit_hash  metric_value  status  description

  8. 继续   - 跳转到步骤 1。
```

### 实验策略

生成实验想法时，请按此优先级顺序：

1. **先易后难**：简单的参数调整、明显的低效之处。
2. **根据结果进行指导**：如果一个方向显示出希望，在该方向进一步探索。
3. **在平台期后多样化**：如果最近 3-5 个实验都失败了，尝试完全不同的方法。
4. **组合赢家**：如果实验 A 和 B 各自独立地改进了，尝试将它们组合起来。
5. **简化传递**：定期尝试删除代码/复杂性，看看指标是否保持。
6. **重大更改**：在用尽增量想法后，尝试更大的架构更改。

### 处理约束

- **时间预算**：如果一个运行超过预期持续时间的 2 倍，就终止它并视为崩溃。
- **现有测试**：如果约束要求测试通过，在之前/之后运行它们，并在它们损坏时回滚。
- **内存/资源**：监控并回滚，如果资源使用超过声明的限制。

---

## 第四阶段：报告

当循环结束（预算达到或用户中断）时：

1. **打印完整的 results.tsv** 作为格式化表格。
2. **总结**：
   - 运行的总实验次数
   - 保留的实验 / 删除的实验 / 崩溃的实验
   - 起始指标（基线）与最终指标
   - 改进百分比
   - 最具影响力的前 3 个更改
3. **显示保留实验的累积 git 日志**：
   `git log --oneline <start_commit>..HEAD`
4. **建议下一步**：根据结果，建议人类研究人员可能会尝试的下一步（对于自动实验来说风险过高/太复杂的想法）。

## 快速参考

### Results TSV 格式

制表符分隔，5 列：

```
experiment	commit	metric	status	description
0	a1b2c3d	0.997900	baseline	unmodified code
1	b2c3d4e	0.993200	keep	increase learning rate to 0.04
2	c3d4e5f	1.005000	discard	switch to GeLU activation
3	d4e5f6g	0.000000	crash	double model width (OOM)
```

### Git 工作流程

- 所有实验都在 `autoresearch/<tag>` 分支上发生
- 每个实验在运行之前都会提交
- 失败的实验使用 `git reset --hard HEAD~1` 回滚
- 成功的实验推进分支
- `results.tsv` 和 `run.log` 保持未跟踪（添加到 `.git/info/exclude`）

### 关键原则

1. **测量一切**：没有测量就没有实验。
2. **回滚失败**：分支只在改进时推进。
3. **保持自主**：永远不要停止询问。如果卡住，请更深入地思考。
4. **保持简单**：复杂性是一种成本。权衡它以获得收益。
5. **记录一切**：TSV 是研究日志。
