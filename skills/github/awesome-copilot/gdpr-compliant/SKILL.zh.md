# GDPR工程技能

为工程师、架构师、DevOps和科技领导者提供可操作的GDPR参考指南。
灵感来源于CNIL开发者指南以及GDPR第5、25、32、33、35条。

> **黄金法则**：收集更少。存储更少。暴露更少。保留更少。

如需深入探讨，请阅读`references/`目录中的参考文件：
- `references/data-rights.md` — 用户权利端点、DSR工作流、RoPA
- `references/security.md` — 加密、哈希、密钥、匿名化
- `references/operations.md` — 云、CI/CD、事件响应、架构模式

## 1. 核心GDPR原则（第5条）

| 原则 | 工程责任 |
|---|---|
| 合法性、公平性、透明性 | 在RoPA中记录每项处理活动的法律依据 |
| 目的限定 | 为目的A收集的数据**必须**未经新的法律依据不得用于目的B |
| 数据最小化 | 仅收集具有明确业务需求的字段 |
| 准确性 | 提供更新端点；将更正传播到下游存储 |
| 存储限定 | 在模式设计时定义TTL — 永远不在之后定义 |
| 完整性 & 机密性 | 静态存储和传输加密；限制和审计访问权限 |
| 可问责性 | 维护合规证据；RoPA随时准备好接受DPA检查 |

## 2. 默认隐私设计 & 默认隐私保护

**必须**
- 在创建时为每个存储个人数据的表添加`CreatedAt`、`RetentionExpiresAt`。
- 将所有可选数据收集默认设置为**关闭**。用户选择启用；他们永远不会选择关闭默认设置。
- 在构建高风险处理（生物识别、健康数据、大规模画像、系统性监控）之前进行**DPIA**。
- 每当引入新的处理活动功能时，更新**RoPA**。
- 在数据流向子处理商之前，与每个子处理商签署**DPA**。

**必须不**
- 未经记录的法律依据就发布新的数据收集功能。
- 默认启用分析、跟踪或遥测，而未经明确同意。
- 在RoPA未列出的系统中存储个人数据。

---

## 3. 数据最小化

**必须**
- 将每个DTO/模型字段映射到具体业务需求。移除未记录的字段。
- 使用**独立的DTO**用于创建、读取和更新 — 永远不重用同一对象。
- 仅返回调用者有权查看的内容 — 使用响应投影。
- 在边缘掩码敏感值：返回`****1234`用于卡号，永远不返回完整值。
- 从默认列表/搜索投影中排除敏感字段（出生日期、国籍ID、健康数据）。

**必须不**
- 如果请求/响应体可能包含个人数据，则记录完整请求/响应体。
- 将个人数据包含在URL路径段或查询参数中（CDN日志、浏览器历史记录）。
- 未经明确法律依据收集`dateOfBirth`、国籍ID或健康数据。

---

## 4. 目的限定

**必须**
- 在代码注释和RoPA中记录每项处理活动的目的。
- 在将数据用于次要目的之前，获取新的法律依据或进行兼容性分析。

**必须不**
- 未经明确同意，将用于服务交付收集的个人数据共享给广告网络。
- 未经单独法律依据和用户通知，使用支持工单内容训练ML模型。

---

## 5. 存储限定 & 保留

**必须**
- 每个存储个人数据的表**必须**有定义的保留期。
- 通过计划任务（Hangfire、cron）自动执行保留 — 永远不手动执行。
- 保留期到期时匿名化或删除数据 — 永远不将过期数据无声地保留在生产环境中。

**推荐默认值**

| 数据类型 | 最大保留期 |
|---|---|
| 认证/审计日志 | 12-24个月 |
| 会话/刷新令牌 | 30-90天 |
| 邮件/通知日志 | 6个月 |
| 非活跃用户账户 | 最后登录后12个月 → 通知 → 删除 |
| 支付记录 | 符合税法要求（7-10年），最小化 |
| 分析事件 | 13个月 |

**应该**
- 添加`RetentionExpiresAt`列 — 在插入时计算。
- 使用软删除（`DeletedAt`），在擦除请求窗口（30天）后执行计划硬删除。

**必须不**
- 无限期保留个人数据“以防将来有用”。

## 6. API设计规则

**必须**
- **必须不**将个人数据包含在URL路径或查询参数中。
  - `GET /users/{userId}`
- 所有返回或接受个人数据的端点都需要认证。
- 从JWT中提取操作用户的身份 — 永远不从中提取请求体。
- 在每个资源上验证所有权：`if (resource.OwnerId != currentUserId) return 403`。
- 使用UUID或模糊标识符 — 永远不使用序列整数作为公开资源ID。

**应该**
- 对敏感端点（登录、数据导出、密码重置）进行速率限制。
- 设置`Referrer-Policy: no-referrer`和明确的`CORS`允许列表。

**必须不**
- 在API响应中返回堆栈跟踪、内部路径或数据库错误。
- 在认证API上使用`Access-Control-Allow-Origin: *`。

---

## 7. 日志规则

**必须**
- 在应用程序日志中匿名化IP — 掩码最后八位（IPv4）或最后80位（IPv6）。
  - `192.168.1.xxx`
- **必须不**记录：密码、令牌、会话ID、凭证、卡号、国籍ID、健康数据。
- **必须不**在可能包含个人数据的请求/响应体中记录完整请求/响应体。
- 执行日志保留 — 在定义的周期后自动清除。

**应该**
- 记录**事件**而不是数据：`"User {UserId} updated email"`而不是`"Email changed from a@b.com to c@d.com"`。
- 使用结构化日志（JSON）将`userId`作为内部标识符，而不是电子邮件地址。
- 将审计日志（敏感访问、管理员操作）与应用程序日志分开 — 不同的保留和ACL。

---

## 8. 错误处理

**必须**
- 返回通用错误消息 — 永远不暴露堆栈跟踪、内部路径或数据库错误。
  - `"Column 'email' violates unique constraint on table 'users'"`
  - `"A user with this email address already exists.""`
- 使用**Problem Details (RFC 7807)** 对所有错误响应。
- 在服务器端记录完整错误，并附带关联ID；仅向客户端返回关联ID。

**必须不**
- 在错误响应中包含文件路径、类名或行号。
- 在错误消息中包含个人数据（例如，“User john@example.com not found”）。

## 9. 加密（摘要 — 请参阅`references/security.md`获取完整细节）

| 范围 | 最低标准 |
|---|---|
| 标准个人数据 | AES-256磁盘/卷加密 |
| 敏感数据（健康、金融、生物识别） | AES-256 **列级别** + 通过KMS的封装加密 |
| 传输中 | TLS 1.2+（优先1.3）；强制执行HSTS |
| 密钥 | HSM支持的KMS；每年轮换DEK |

**必须不**允许TLS 1.0/1.1、空加密套件或硬编码的加密密钥。

---

## 10. 密码哈希

**必须**
- 使用**Argon2id**（推荐）或**bcrypt**（成本≥12）。永远不使用MD5、SHA-1或SHA-256。
- 每个密码使用唯一盐。仅存储哈希值。

**必须不**
- 以任何形式记录密码。在URL中传输密码。以明文存储重置令牌。

---

## 11. 密钥管理

**必须**
- 将所有密钥存储在KMS中：Azure Key Vault、AWS Secrets Manager、GCP Secret Manager或HashiCorp Vault。
- 使用预提交钩子（`gitleaks`、`detect-secrets`）防止密钥提交。
- 在员工离职、年度计划或怀疑泄露时轮换密钥。

**`.gitignore`必须包含**：`.env`、`.env.*`、`*.pem`、`*.key`、`*.pfx`、`*.p12`、`secrets/`

**必须不**
- 将密钥提交到源代码。将密钥存储为明文环境变量默认值。

---

## 12. 匿名化 & 假名化（摘要 — 请参阅`references/security.md`）

- **匿名化** = 不可逆 → 超出GDPR范围。用于擦除后保留的记录。
- **假名化** = 可逆（使用密钥）→ 仍然是个人数据，风险降低。
- 删除用户时，对必须保留的记录（财务、审计）进行匿名化，而不是删除它们。
- 将假名化密钥存储在KMS中 — 永远不与假名化数据存储在同一数据库中。

**必须不**在通过链接攻击可能重新识别的情况下称数据为“匿名化”。

---

## 13. 使用假数据进行测试

**必须**
- **必须不**在开发、测试或CI环境中使用生产个人数据。
- **必须不**在未先清除PII的情况下将生产数据库备份恢复到非生产环境。
- 使用合成数据生成器：`Bogus`（.NET）、`Faker`（JS/Python/Ruby）。
- 使用`@example.com`作为所有测试电子邮件地址。

## 14. 反模式

| 反模式 | 正确方法 |
|---|---|
| PII在URL中 | 使用模糊UUID作为公开标识符 |
| 记录完整请求体 | 仅记录结构化事件元数据 |
| “永久保留”模式 | 在设计时定义TTL |
| 开发/测试中的生产数据 | 合成数据 + 清除管道 |
| 跨团队共享凭证 | 单独账户 + RBAC |
| 硬编码密钥 | KMS + 密钥管理器 |
| 认证API上的`Access-Control-Allow-Origin: *` | 显式CORS允许列表 |
| 将同意与配置文件数据存储在一起 | 专用同意存储 |
| GET查询参数中的PII | POST正文或认证会话 |
| 公开URL中的序列整数ID | UUID |
| “匿名化”数据与准标识符 | 应用k-匿名性，测试链接抗性 |
| 在EEA外混合备份区域 | 备份作业上的明确区域锁定 |

## 15. PR审查清单

### 数据模型
- 每个新的PII列都有记录的目的和保留期。
- 敏感字段（健康、金融、国籍ID）使用列级别加密。
- 不使用序列整数作为公开标识符的PK。

### API
- URL路径或查询参数中**没有**PII。
- 所有返回个人数据的端点都需要认证。
- 存在所有权检查 — 用户不能访问其他用户的资源。
- 对敏感端点应用速率限制。

### 日志
- 不记录密码、令牌或凭证。
- 匿名化IP（掩码IPv4的最后八位或IPv6的最后80位）。
- 在可能包含PII的请求/响应体中**不**记录完整请求/响应体。

### 基础设施
- **没有**公共存储桶或公共IP数据库。
- 新云资源标记为`DataClassification`。
- 新存储资源启用静态加密。
- 新数据存储区域符合EEA或受SCC覆盖。

### 密钥 & CI/CD
- 源代码或提交的配置文件中**没有**密钥。
- 新密钥添加到KMS和密钥清单文档。
- CI/CD密钥在管道日志中掩码。

### 保留 & 擦除
- 保留执行作业或策略覆盖新数据存储或字段。
- 擦除管道更新以覆盖新数据存储。

### 用户权利 & 治理
- 数据导出端点包括任何新的个人数据字段。
- 如果引入新的处理活动，则更新RoPA。
- 新子处理商有签署的DPA和RoPA条目。
- 如果更改涉及高风险处理，则触发DPIA。

---

> **黄金法则**：收集更少。存储更少。暴露更少。保留更少。
>
> 你不收集的每字节个人数据都是你不会丢失、不会泄露、不会承担责任的字节。
