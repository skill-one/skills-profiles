# 企业客户入职

从合同到价值实现的四阶段框架，用于企业客户的入职。目标不仅仅是上线——而是实现可持续采用，避免在第12周出现采用率断崖。

## 使用场景

**触发条件：**
- "我们如何入职这位企业客户？"
- "客户已上线但采用率较弱"
- "我们在上线后3个月持续流失客户"
- "POC到生产环境的过渡"
- "如何防止第4周客户消失？"
- "客户成功入职框架"

**背景：**
- 企业或中市场交易
- 复杂的技术需求
- 多方利益相关者参与
- 30-90天的实施时间表
- 首年流失风险

---

## 核心框架

### 1. 第4周客户消失问题（及如何预防）

**模式：**

第1周：启动会议很成功。大家都很兴奋。
第2-3周：技术发现，需求收集。仍然顺利。
第4周：客户停止回应。会议被取消。"太忙了。"

**发生了什么？**

在对方内部未达成一致的情况下，你开始了客户入职。

**内部项目负责人是谁？**
- 销售代表？（已经转移到下一个交易）
- 技术负责人？（日常工作占用了时间）
- 高管支持者？（授权，但不推动）
- 没人？（**这就是他们消失的原因**）

**内部负责人验证框架**

在启动会议之前，回答以下问题：

**客户方谁会：**
- 参加每周项目会议？（不是"被邀请"——会实际出席）
- 解除采购/法律/安全的障碍？（拥有权限）
- 推动最终用户的采用？（拥有影响力）
- 在停滞时升级问题？（拥有高管访问权限）

**如果你无法为每项指定具体人员，你就没有项目负责人。你只有一个没人推动的合同。**

**如何解决：**

**在销售→客户成功交接期间（在客户启动会议之前）：**

销售代表必须确定：
- 主要项目负责人（姓名，而不是角色）
- 他们的能力（专职还是兼职项目？）
- 他们的权限（他们能解除障碍吗？）
- 他们的动机（什么对他们有好处？）

**如果没有明确的负责人：**

不要开始入职。让销售介绍给你经济购买者：

"在启动实施之前，我们想确保我们这边有合适的项目负责人。根据我们的经验，实施成功需要有人每周推动这件事。你们团队中谁应该与我们合作？"

**常见错误：**

假设会有人负责。明确询问。如果他们无法说出具体人选，交易就有风险。

### 2. 采用率断崖（第12周问题）

**模式：**

第6周：上线成功。使用率激增。你庆祝。
第8周：使用率停滞。
第10周：使用率下降。
第12周：使用率较峰值下降50%。

**为什么会这样发生：**

你将上线视为终点。**上线是起点。**

**推动可持续采用的因素：**

**不是：** 功能完整性，技术集成，培训课程

**是：** 持续的价值展示，用户成功案例，扩展用例

**超越上线的采用阶段框架**

**第1-6周（实施）：** 让它运行起来
- 衡量指标：技术设置完成百分比
- 负责人：技术负责人

**第6-12周（初始采用）：** 让人们开始使用
- 衡量指标：活跃用户数，使用频率
- 负责人：赋能/开发者关系团队

**第12-26周（可持续采用）：** 证明持续价值
- 衡量指标：用例扩展，团队扩散
- 负责人：客户成功团队

**第26周后（扩展）：** 在账户内增长
- 衡量指标：新团队，新用例，升级触发器
- 负责人：客户经理+客户成功团队

**大多数团队错过的交接：**

第6周（上线）→ 第12周（可持续采用）

大多数客户成功团队庆祝上线并转向下一个客户。**这时流失的种子开始萌芽。**

**第6-12周该做什么：**

**第7周：** 首次价值报告
"这是你们团队第一周完成的工作：[具体指标]。第12周的良好状态看起来像这样：[目标]。"

**第9周：** 用户成功案例
"[用户姓名]在[团队名称]本周节省了[X小时/减少了Y错误]。他们这样使用我们的产品。"

**第11周：** 用例扩展对话
"你们正在使用我们进行[主要用例]。像你们这样的团队还使用我们进行[相邻用例]。想探索吗？"

**常见错误：**

衡量"上线完成度"而不是"可持续活跃使用"。上线不是成功。第26周保留的采用率才是成功。

### 3. 入职前：成功是在第一个客户电话之前建立的

**模式：**

大多数入职失败可追溯到启动会议前的差距。

**被遗漏的内容：**

**销售没有正确介绍客户成功：**
- 交易驱动因素未知
- 利益相关者动态不明确
- 技术需求被假设

**没有确定内部项目负责人：**
- 客户成功团队联系后无人回应
- 会议安排给了错误的人
- 决策无法坚持

**客户时间表不现实：**
- 他们想在2周内上线
- 技术设置至少需要6周
- 从第一天起期望值就不一致

**入职前检查框架**

在安排启动会议之前，验证：

**账户信息：**
- [ ] 销售交接完成（交易驱动因素，利益相关者，技术需求）
- [ ] 过去互动回顾（演示笔记，提案，邮件）
- [ ] 组织结构映射（团队规模，汇报关系）
- [ ] 用例记录（主要+未来）

**内部设置：**
- [ ] 创建内部Slack频道（#account-[客户名称]）
- [ ] CRM中更新账户计划
- [ ] 准备项目计划模板
- [ ] 角色分配（客户成功经理负责人，技术负责人，高管支持者）

**客户准备情况：**
- [ ] 项目负责人由姓名确定（不仅仅是"他们的开发者关系团队"）
- [ ] 双方确认高管支持者
- [ ] 时间表现实（他们的目标与典型时间表相比）
- [ ] 记录已知障碍（采购，安全，法律）

**时间表验证：**
- [ ] 客户上线日期考虑到技术需求是现实的
- [ ] 内部能力可用（没有超负荷）
- [ ] 依赖关系确定（SSO，集成，数据迁移）

**决策标准：**

只有当所有四个部分都验证后，才安排启动会议。如果存在差距，在接触客户之前向销售或高管支持者暴露。

**常见错误：**

在没有内部清晰的情况下开始入职。这会造成混乱，错过截止日期，并侵蚀客户信心。

### 4. 四阶段入职流程

**阶段1：启动（第1周）**

**目标：** 对齐目标，时间表，成功指标

**参会人员：** 高管支持者+项目负责人+技术负责人

**议程：**
1. 介绍和角色（5分钟）
2. 高管对战略目标的对齐（5分钟）
3. 成功定义："3/6/12个月的成功看起来像什么？"（10分钟）
4. 时间表和里程碑（5分钟）
5. 会议节奏（每周项目团队，每月高管回顾）（5分钟）
6. 下一步（技术发现会议，成功计划审查）（5分钟）

**交付物：** 在24小时内发送启动会议回顾，包含成功指标，时间表，下一步会议

**阶段2：发现与规划（第2-3周）**

**目标：** 了解技术环境，映射用例，规划推广

**三个并行工作流：**

**工作流1：技术发现**
- 当前基础设施（本地，云，混合）
- 现有工具和集成
- 安全/合规要求
- 时间限制

**工作流2：成功规划**
- 用例优先级（从最高价值开始）
- 成功指标定义（如何衡量采用率）
- 培训需求确定（谁需要什么）

**工作流3：技术设置**
- SSO/身份配置
- 集成需求
- 数据迁移（如适用）
- 确定试点组

**交付物：** 客户成功计划文档，包含用例，指标，时间表，里程碑

**阶段3：实施（第4-6周）**

**目标：** 部署到试点组，验证用例，为更广泛的推广做准备

**三个并行轨道：**

**轨道1：管理设置**
- SSO配置完成
- 集成可用
- 数据迁移（如适用）

**轨道2：用户赋能**
- 试点组培训课程
- 文档共享
- 安排办公时间

**轨道3：试点和反馈**
- 试点组使用产品
- 每周收集反馈
- 问题分类和解决

**交付物：** 上线准备清单完成，试点组验证

**阶段4：上线和持续成功（第6周后）**

**目标：** 广泛推广，持续采用，扩展用例

**第6-8周（推广）：**
- 推广到所有团队
- 安排培训课程
- 提供支持（Slack，邮件，办公时间）

**第8-12周（价值展示）：**
- 首次价值报告（第7周）
- 分享用户成功案例（第9周）
- 用例扩展对话（第11周）

**第12-26周（可持续采用）：**
- 月度业务回顾
- 采用跟踪（活跃用户，频率，用例）
- 扩展机会识别

**常见错误：**

将上线视为完成。阶段4是赢得或失去留存的地方。

---

### 5. 并行轨道反模式

**模式：**

大多数入职团队按顺序运行工作流：
1. 技术设置（第1-2周）
2. 然后培训（第3-4周）
3. 然后试点（第5-6周）

**总时间：6周**

**更好的方法是并行轨道**

同时运行技术设置，培训和试点：
- 第1周：技术发现+确定试点组+安排培训
- 第2周：SSO配置+试点组培训+试点开始
- 第3周：集成+更广泛的培训+试点反馈

**总时间：3周**

**为什么并行有效：**

1. 缩短价值实现时间
2. 保持客户参与（每周都有进展）
3. 早期识别障碍（试点组在广泛推广前暴露问题）

**如何执行：**

为每个轨道分配明确的负责人：
- 轨道1（管理）：技术负责人
- 轨道2（赋能）：培训/开发者关系负责人
- 轨道3（试点）：客户成功经理+试点组负责人

跨轨道每周同步，暴露依赖关系和障碍。

**常见错误：**

在"完美的技术设置"之前才开始试点。尽早让试点组使用它，即使设置不完美。他们的反馈会让更广泛的推广更好。

## 决策树

### 我是否应该开始客户入职？

```
销售是否已确定项目负责人姓名？
├─ 否 → 在启动前确定项目负责人
└─ 是 → 继续...
    │
    客户的时间表是否现实，考虑到典型的部署？
    ├─ 否 → 在启动前重置期望
    └─ 是 → 继续...
        │
        是否有内部能力？
        ├─ 否 → 延迟启动或获取更多资源
        └─ 是 → 进入启动
```

### 入职是否处于风险中？

```
客户是否回应会议邀请？
├─ 否 → 第4周客户消失，升级给高管支持者
└─ 是 → 继续...
    │
    他们是否完成行动项？
    ├─ 否 → 没有项目负责人，确定谁推动这件事
    └─ 是 → 继续...
        │
        试点组是否使用产品？
        ├─ 否 → 试点组错误或产品未解决痛点
        └─ 是 → 正常进行
```

### 上线后采用率是否持续？

```
活跃用户是否在第6周到第12周增长？
├─ 是 → 健康的采用率
└─ 否 → 继续...
    │
    活跃用户是否下降？
    ├─ 是 → 采用率断崖，立即干预
    └─ 否（停滞）→ 风险，开始价值展示
```

## 常见错误

**1. 在内部未对齐之前开始客户入职**
   - 浪费前2-3周，造成混乱，损害信誉

**2. 未能提前确定真正的项目负责人**
   - 在第4周发现，必须重新开始或交易停滞

**3. 没有技术需求就过度承诺时间表**
   - 实施中途发现障碍，错过截止日期

**4. 没有内部沟通中心**
   - 决策无法在团队间传播，重复工作发生

**5. 将上线视为项目完成**
   - 第12周采用率断崖，账户面临风险

**6. 顺序轨道而不是并行**
   - 实施时间延长一倍，客户失去动力

**7. 上线后没有持续指标**
   - 过晚发现采用问题，无法挽救账户

## 快速参考

**入职前验证：**
- [ ] 销售交接完成（交易驱动因素，利益相关者，需求）
- [ ] 客户方已确定项目负责人姓名
- [ ] 时间表现实（他们的目标与典型部署相比）
- [ ] 内部角色分配（客户成功经理，技术，高管支持者）

**启动议程（30-45分钟）：**
1. 介绍（5分钟）
2. 高管对齐（5分钟）
3. 成功定义（10分钟）
4. 时间表和里程碑（5分钟）
5. 会议节奏（5分钟）
6. 下一步（5分钟）

**采用跟踪（第6-26周）：**
- 第7周：首次价值报告
- 第9周：用户成功案例
- 第11周：用例扩展对话
- 第13周：首次月度业务回顾
- 第26周：扩展准备评估

**四个阶段：**
1. 启动（第1周）：对齐
2. 发现（第2-3周）：规划
3. 实施（第4-6周）：部署到试点
4. 上线及持续（第6周后）：推广，价值展示，扩展

**危险信号：**
- 客户在第4周不回应 → 没有项目负责人
- 第5周试点组不使用产品 → 组错误或用例错误
- 第8-12周活跃用户下降 → 形成采用率断崖
