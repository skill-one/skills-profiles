### 多文档与分离容器决策框架

当实体有 30-70% 的访问相关性时，选择以下选项之一：

**多文档容器（同一容器，不同文档类型）：**
- ✅ 使用时：频繁联合查询、相关实体、可接受的运营耦合
- ✅ 优点：单次查询检索、减少延迟、成本节约、事务一致性
- ❌ 缺点：共享吞吐量、运营耦合、复杂索引

**分离容器：**
- ✅ 使用时：独立的扩展需求、不同的运营需求
- ✅ 优点：清晰分离、独立吞吐量、专业优化
- ❌ 缺点：跨分区查询、更高延迟、成本增加

**增强决策标准：**
- **>70% 相关性 + 有界大小 + 相关操作** → 多文档容器
- **50-70% 相关性** → 分析运营耦合：
  - 同样备份/恢复需求？ → 多文档容器
  - 不同扩展模式？ → 分离容器
  - 不同一致性需求？ → 分离容器
- **<50% 相关性** → 分离容器
- **存在关系识别** → 强多文档容器候选

## 重要 Azure Cosmos DB NoSQL 背景

### 理解面向聚合的设计

在面向聚合的设计中，Azure Cosmos DB NoSQL 提供多级聚合：

1. 多文档容器聚合

  多个相关实体按共享同一分区键分组，但作为具有不同 ID 的单独文档存储。这提供了：

   • 使用单个 SQL 查询高效查询相关数据
   • 使用存储过程/触发器在分区内部进行事务一致性
   • 访问单个文档的灵活性
   • 每个文档无大小限制 (每个文档限制为 2MB)

2. 单文档聚合

  多个实体组合成一个 Cosmos DB 文档。这提供了：

   • 跨聚合所有数据的原子更新
   • 所有数据的单点读取检索。确保通过 API 引用文档 ID 和分区键 (例如 `ReadItemAsync<Order>(id: "order0103", partitionKey: new PartitionKey("TimS1234"));`) 而不是使用查询 `SELECT * FROM c WHERE c.id = "order0103" AND c.partitionKey = "TimS1234"` 进行点读取示例)  
   • 受 2MB 文档大小限制

设计聚合时，根据您的需求考虑这两个级别。

### 参考常数

• **Cosmos DB 文档限制**: 2MB (硬限制)
• **自动扩展模式**: 自动在最大 RU/s 的 10% 和 100% 之间扩展
• **请求单元 (RU) 成本**:
  • 点读取 (1KB 文档): 1 RU
  • 查询 (1KB 文档): ~2-5 RUs 取决于复杂性
  • 写入 (1KB 文档): ~5 RUs
  • 更新 (1KB 文档): ~7 RUs (更新比创建操作更昂贵)
  • 删除 (1KB 文档): ~5 RUs
  • **关键**: 大文档 (>10KB) 具有按比例更高的 RU 成本
  • **跨分区查询开销**: 每扫描一个物理分区约 2.5 RU
  • **实际的 RU 估算**: 始终基于实际文档大小计算，而不是理论 1KB
• **存储**: $0.25/GB-月
• **吞吐量**: $0.008/RU 每小时 (手动), $0.012/RU 每小时 (自动扩展)
• **每月秒数**: 2,592,000

### 关键设计限制

• 文档大小限制: 2MB (硬限制影响聚合边界)
• 分区吞吐量: 每个物理分区高达 10,000 RU/s
• 分区键基数: 旨在避免热分区 (基数越高越好)
• **物理分区计算公式**: 总数据大小 ÷ 50GB = 物理分区数量
• 跨分区查询: 与单分区查询相比，具有更高的 RU 成本和延迟，RU 成本将随物理分区数量增加。避免为高频模式或非常大的数据集建模跨分区查询。
• **跨分区开销**: 每个物理分区为跨分区查询增加约 2.5 RU 基本成本
• **大规模扩展影响**: 100 个以上物理分区使跨分区查询变得极其昂贵且无法扩展。
• 索引开销: 每个索引属性都会消耗存储和写入 RU
• 更新模式: 频繁更新索引属性或完全替换文档会增加 RU 成本 (文档越大，更新 RU 增加的影响越大) 

## 核心设计理念

核心设计理念是开始时的默认思维方式。应用此默认模式后，您应该在设计模式部分应用相关的优化。

### 战略性共位置

使用多文档容器将经常一起访问的数据分组，只要它们在操作上可以耦合。Cosmos DB 提供容器级功能，如吞吐量配置、索引策略和变更流，这些功能在容器级别运行。将过多数据组合在一起会导致操作耦合，并可能限制优化机会。

**多文档容器优势**:

- **单个查询效率**: 使用一个 SQL 查询检索相关数据，而不是多次往返
- **成本优化**: 一个查询操作而不是多个点读取
- **延迟降低**: 消除多个数据库调用的网络开销
- **事务一致性**: 同一分区内的 ACID 事务
- **自然数据局部性**: 相关数据物理存储在一起以实现最佳性能

**何时使用多文档容器**:

- 用户及其订单: 分区键 = user_id，用户和订单的文档
- 产品及其评论: 分区键 = product_id，产品和评论的文档
- 课程及其课程: 分区键 = course_id，课程和课程的文档
- 团队及其成员: 分区键 = team_id，团队和成员的文档

#### 多容器与多文档容器：正确的平衡

虽然多文档容器很强大，但不要将不相关的数据强行组合在一起。当实体具有以下特征时，使用多个容器：

**不同的操作特征**:
- 独立的吞吐量需求
- 不同的扩展模式
- 不同的索引需求
- 不同的变更流处理需求

**多个容器的操作优势**:

- **较低的破坏范围**: 容器级问题只影响相关实体
- **细粒度吞吐量管理**: 按业务领域独立分配 RU/s
- **清晰的成本归因**: 了解每个业务领域的成本
- **干净的变更流**: 变更流包含逻辑相关的事件
- **自然的服务边界**: 微服务可以拥有特定领域的容器
- **简化的分析**: 每个容器的变更流只包含一种实体类型

#### 避免复杂的单容器模式

将不相关的实体混合在一起的复杂单容器设计模式对大多数应用程序没有实际意义，反而会产生操作开销：

**单容器反模式**:

- 所有容器 → 复杂过滤 → 难以分析
- 所有内容使用一个吞吐量分配
- 一个包含混合事件的变更流需要过滤
- 扩展影响所有实体
- 复杂索引策略
- 难以维护和让新开发者熟悉

### 保持关系简单和明确

一对一: 在两个文档中存储相关 ID

```json
// 用户容器
{ "id": "user_123", "partitionKey": "user_123", "profileId": "profile_456" }
// 配置文件容器  
{ "id": "profile_456", "partitionKey": "profile_456", "userId": "user_123" }
```

一对多: 使用相同的分区键表示父子关系

```json
// 订单容器使用 user_id 作为分区键
{ "id": "order_789", "partitionKey": "user_123", "type": "order" }
// 查询用户订单: SELECT * FROM c WHERE c.partitionKey = "user_123" AND c.type = "order"
```

多对多: 使用单独的关系容器

```json
// 用户课程容器
{ "id": "user_123_course_ABC", "partitionKey": "user_123", "userId": "user_123", "courseId": "ABC" }
{ "id": "course_ABC_user_123", "partitionKey": "course_ABC", "userId": "user_123", "courseId": "ABC" }
```

频繁访问的属性: 适度反规范化

```json
// 订单文档
{ 
  "id": "order_789", 
  "partitionKey": "user_123", 
  "customerId": "user_123", 
  "customerName": "John Doe" // 包含客户名称以避免查找
}
```

这些关系模式提供了初始基础。您的特定访问模式应影响每个容器中的实现细节。

### 从实体容器到面向聚合的设计

从一个容器每个实体开始是一个良好的思维模型，但您的访问模式应指导您如何使用面向聚合的设计原则进行优化。

面向聚合的设计认识到数据自然以组（聚合）的形式访问，这些访问模式应决定您的容器结构，而不是实体边界。Cosmos DB 提供多级聚合：

1. 多文档容器聚合: 相关实体共享分区键，但保持为单独的文档
2. 单文档聚合: 多个实体组合成一个文档以实现原子访问

关键洞察: 让您的访问模式揭示您的自然聚合，然后围绕这些聚合设计您的容器，而不是固化的实体结构。

现实检查: 如果完成用户的 PRIMARY 工作流 (例如 "浏览产品 → 添加到购物车 → 结账") 需要在多个容器之间进行跨分区查询，则您的实体实际上可能形成应一起重构的聚合。

### 基于访问模式的聚合边界

在确定聚合边界时，使用此决策框架：

步骤 1: 分析访问相关性

• 90% 一起访问 → 强大的单文档聚合候选
• 50-90% 一起访问 → 多文档容器聚合候选  
• <50% 一起访问 → 分离的聚合/容器

步骤 2: 检查限制

• 大小: 组合大小会超过 1MB 吗？→ 强制多文档或分离
• 更新: 更新频率不同吗？→ 考虑多文档
• 原子性: 需要事务性更新吗？→ 倾向于同一分区

步骤 3: 选择聚合类型
根据步骤 1 & 2 选择:

• **单文档聚合**: 将所有内容嵌入一个文档
• **多文档容器聚合**: 相同的分区键，不同的文档
• **分离的聚合**: 不同的容器或不同的分区键

#### 聚合分析示例

订单 + 订单项:

访问分析:
• 仅检查状态而无需订单项: 5% (只是检查状态)
• 带所有订单项获取订单: 95% (正常流程)
• 更新模式: 订单项很少独立更改
• 组合大小: ~50KB 平均，最大 200KB

决策: 单文档聚合
• 分区键: order_id，id: order_id
• 订单项嵌入为数组属性
• 优势: 原子更新，单个点读取操作

产品 + 评论:

访问分析:
• 不带评论查看产品: 70%
• 带评论查看产品: 30%
• 更新模式: 评论独立添加
• 大小: 产品 5KB，可能有数千条评论

决策: 多文档容器聚合
• 分区键: product_id，id: product_id (用于产品)
• 分区键: product_id，id: review_id (用于每条评论)
• 优势: 灵活访问，无限制的评论，事务一致性

客户 + 订单:

访问分析:
• 仅查看客户资料: 85%
• 查看客户与订单历史: 15%
• 更新模式: 完全独立
• 大小: 可能有数千个订单

决策: 分离的聚合 (不同容器)
• 客户容器: 分区键: customer_id
• 订单容器: 分区键: order_id，带有 customer_id 属性
• 优势: 独立扩展，清晰的边界

### 自然键优于通用标识符

您的键应描述它们标识的内容:
• ✅ user_id，order_id，product_sku - 清晰，有目的
• ❌ PK，SK，GSI1PK - 模糊，需要文档
• ✅ OrdersByCustomer，ProductsByCategory - 自描述查询
• ❌ Query1，Query2 - 无意义的名称

这种清晰性在应用程序增长和新开发者加入时变得至关重要。

### 针对您的查询优化索引

仅索引您的访问模式实际查询的属性，而不是所有方便的属性。使用选择性索引通过排除未使用的路径来减少 RU 消耗和存储成本。为复杂的 ORDER BY 和过滤操作使用复合索引。现实: 对所有属性自动索引会增加写入 RU 和存储成本，无论使用情况如何。验证: 列出每个访问模式过滤或排序的特定属性。如果大多数查询只使用 2-3 个属性，则使用选择性索引；如果使用大多数属性，请考虑自动索引。

### 为扩展而设计

#### 分区键设计

使用您最频繁查找的属性作为分区键 (例如用户查找的用户_id)。简单的选择有时会通过低多样性或访问不均等创建热分区。Cosmos DB 在分区之间分配负载，但每个逻辑分区都有一个 10,000 RU/s 的限制。热分区会过载单个分区，导致过多请求。

低基数在分区键具有太少不同值时创建热分区。subscription_tier (基本/高级/企业) 只创建三个分区，导致所有流量都集中在少数键上。使用高基数键，如 user_id 或 order_id。

流行度偏差在键具有多样性但某些值获得显着更多流量时创建热分区。user_id 提供数百万个值，但在病毒时刻有 10,000+ RU/s 的热门用户创建热分区。

选择分区键以在许多值之间均匀分配负载，同时与频繁查找保持一致。复合键通过在分区之间分配负载同时保持查询效率来解决这两个问题。device_id 单独可能使分区不堪重负，但 device_id#hour 将读取分散到基于时间的分区。

#### 考虑索引开销

索引开销会增加 RU 成本和存储。当文档具有许多索引属性或频繁更新索引属性时会发生这种情况。每个索引属性在写入时都会消耗额外的 RU 和存储空间。根据查询模式，这种开销对于读取密集型工作负载可能可以接受。

🔴 重要提示: 如果您可以接受增加的成本，请确保确认增加的 RU 消耗不会超过容器的配置吞吐量。为了安全起见，您应该进行粗略计算。

#### 工作负载驱动的成本优化

在做出聚合设计决策时:

• 计算读取成本 = 频率 × 每次操作的 RU
• 计算写入成本 = 频率 × 每次操作的 RU 
• 总成本 = Σ(读取成本) + Σ(写入成本)
• 选择总成本较低的设计

成本分析示例:

选项 1 - 反规范化订单+客户:
- 读取成本: 1000 RPS × 1 RU = 1000 RU/s
- 写入成本: 50 订单更新 × 5 RU + 10 客户更新 × 50 订单 × 5 RU = 2750 RU/s
- 总成本: 3750 RU/s

选项 2 - 正规化并使用单独查询:
- 读取成本: 1000 RPS × (1 RU + 3 RU) = 4000 RU/s
- 写入成本: 50 订单更新 × 5 RU + 10 客户更新 × 5 RU = 300 RU/s
- 总成本: 4300 RU/s

决策: 选项 1 在此情况下更好，因为 RU 消耗较低

## 设计模式

本节包括常见的优化。这些优化不应被视为默认值。相反，请确保基于核心设计理念创建初始设计，然后在设计模式部分应用相关的优化。

### 大规模数据分桶模式

🔴 **关键模式** 对于极高频量工作负载 (>50k 写入/秒 >100M 记录):

当面临大量写入量时，**数据分桶/分块** 可以通过 90%+ 减少写入操作，同时保持查询效率。

**问题**: 90M 个单独记录 × 80k 写入/秒将需要显著的 Cosmos DB 分区/大小和 RU 扩展，这将成为成本高昂。
**解决方案**: 将记录分组为块 (例如，每个文档 100 条记录) 以节省每个文档大小和写入 RU 成本，以保持相同的吞吐量/并发性，但成本更低。
**结果**: 90M 记录 → 900k 文档 (95.7% 减少)

**实现**：
```json
{
  "id": "chunk_001",
  "partitionKey": "account_test_chunk_001", 
  "chunkId": 1,
  "records": [
    { "recordId": 1, "data": "..." },
    { "recordId": 2, "data": "..." }
    // ... 98 more records
  ],
  "chunkSize": 100
}
```

**何时使用**：
- 写入量 >10k 操作/秒
- 单个记录较小 (<2KB 每个记录)
- 记录经常以组的形式访问
- 批处理场景

**查询模式**：
- 单个 chunk：点读（100 条记录 1 RU）
- 多个 chunk：`SELECT * FROM c WHERE STARTSWITH(c.partitionKey, "account_test_")`
- RU 效率：150KB chunk 每 43 RU vs 100 次单独读取 500 RU

**成本效益**：
- 写入 RU 减少 95%+
- 物理操作大幅减少
- 更好的分区分布
- 跨分区查询开销降低

### 多实体文档容器

当多个实体类型经常一起访问时，使用不同的文档类型将它们分组到同一个容器中：

**用户 + 最近订单示例**：
```json
[
  {
    "id": "user_123",
    "partitionKey": "user_123", 
    "type": "user",
    "name": "John Doe",
    "email": "john@example.com"
  },
  {
    "id": "order_456",
    "partitionKey": "user_123",
    "type": "order", 
    "userId": "user_123",
    "amount": 99.99
  }
]
```

**查询模式**：
- 仅获取用户：使用 id="user_123"、partitionKey="user_123" 的点读
- 获取用户 + 最近订单：`SELECT * FROM c WHERE c.partitionKey = "user_123"`
- 获取特定订单：使用 partitionKey="user_123" AND id="order_456" 的点读

**何时使用**：
- 实体之间 40-80% 的访问相关性
- 实体具有自然的父子关系
- 可接受的运营耦合（吞吐量、索引、变更流）
- 组合实体查询保持在合理的 RU 成本范围内

**优点**：
- 单个查询检索相关数据
- 联合访问模式降低延迟和 RU 成本
- 分区内的事务一致性
- 保持实体规范化（无数据重复）

**权衡**：
- 变更流中混合实体类型需要过滤
- 共享容器吞吐量影响所有实体类型
- 复杂的索引策略用于不同文档类型

### 优化聚合边界

初始聚合设计后，您可能需要根据更深入的分析调整边界：

提升为单个文档聚合
当多文档分析显示：

• 访问相关性高于预期 (>90%)
• 所有文档总是一起获取
• 组合大小保持有限
• 从原子更新中受益

降级为多文档容器
当单文档分析显示：

• 更新放大问题
• 大小增长问题
• 需要查询子集
• 不同的索引需求

拆分聚合
当成本分析显示：

• 索引开销超过读取收益
• 大型聚合的热点分区风险
• 需要独立扩展

示例分析：

产品 + 评论聚合分析：
- 访问模式：查看产品详情（无评论） - 70%
- 访问模式：查看带评论的产品 - 30%  
- 更新频率：产品每日，评论每小时
- 平均大小：产品 5KB，评论总计 200KB
- 决策：多文档容器 - 低访问相关性 + 大小问题 + 更新不匹配

### 短路反规范化

短路反规范化涉及将相关实体的属性复制到当前实体中，以避免读取期间的额外查找。此模式通过允许在单个查询中访问频繁需要的数据来提高读取效率。当出现以下情况时使用此方法：

1. 访问模式需要额外的跨分区查询
2. 复制的属性基本不可变或应用程序可以接受陈旧值
3. 属性足够小，不会显著影响 RU 消耗

示例：在电子商务应用程序中，您可以将 ProductName 从 Product 文档复制到每个 OrderItem 文档中，以便获取订单项时无需额外的查询来检索产品名称。

### 识别关系

识别关系使您能够使用 parent_id 作为分区键来消除跨分区查询并降低成本。当子实体不能与其父实体共存时，使用 parent_id 作为分区键，而不是创建需要跨分区查询的单独容器。

标准方法（更昂贵）：

• 子容器：partitionKey = child_id
• 需要跨分区查询：通过 parent_id 查找子实体需要跨分区查询
• 成本：跨分区查询的 RU 消耗更高

识别关系方法（成本优化）：

• 子文档：partitionKey = parent_id, id = child_id
• 无需跨分区查询：直接在父分区内查询
• 成本节省：通过避免跨分区查询显著降低 RU 消耗

出现以下情况时使用此方法：

1. 查找子实体时父实体 ID 总是可用
2. 需要查询给定父 ID 的所有子实体
3. 子实体没有父上下文就没有意义

示例：ProductReview 容器

• partition key = ProductId, id = ReviewId
• 查询产品的所有评论：`SELECT * FROM c WHERE c.partitionKey = "product123"`
• 获取特定评论：使用 partitionKey="product123" AND id="review456" 的点读
• 无需跨分区查询，节省大量 RU 成本

### 分层访问模式

复合分区键在数据具有自然层次结构且需要在多个级别上查询时很有用。例如，在学习管理系统中的常见查询是获取学生的所有课程、学生课程中的所有课程或特定课程。

StudentCourseLessons 容器：
- 分区键：student_id
- 具有分层 ID 的文档类型：

```json
[
  {
    "id": "student_123",
    "partitionKey": "student_123",
    "type": "student"
  },
  {
    "id": "course_456", 
    "partitionKey": "student_123",
    "type": "course",
    "courseId": "course_456"
  },
  {
    "id": "lesson_789",
    "partitionKey": "student_123", 
    "type": "lesson",
    "courseId": "course_456",
    "lessonId": "lesson_789"
  }
]
```

这可以启用：
- 获取所有数据：`SELECT * FROM c WHERE c.partitionKey = "student_123"`
- 获取课程：`SELECT * FROM c WHERE c.partitionKey = "student_123" AND c.courseId = "course_456"`
- 获取课程：使用 partitionKey="student_123" AND id="lesson_789" 的点读

### 具有自然边界的访问模式

复合分区键可用于建模自然查询边界。

TenantData 容器：
- 分区键：tenant_id + "_" + customer_id

```json
{
  "id": "record_123",
  "partitionKey": "tenant_456_customer_789", 
  "tenantId": "tenant_456",
  "customerId": "customer_789"
}
```

自然，因为查询始终是租户范围的，用户永远不会跨租户查询。

### 时间访问模式

Cosmos DB 支持在 SQL 查询中丰富的日期/时间操作。您可以使用 ISO 8601 字符串或 Unix 时间戳存储时间数据。根据查询模式、精度需求和人类可读性要求选择。

使用 ISO 8601 字符串：
- 人类可读的时间戳
- 自然按时间顺序排序（使用 ORDER BY）
- 商业应用程序中可读性很重要
- 内置日期函数，如 DATEPART、DATEDIFF

使用数字时间戳：
- 紧凑存储
- 时间值上的数学运算
- 高精度要求

创建包含日期属性的组合索引，以在维护时间顺序的同时高效查询时间数据。

### 使用稀疏索引优化查询

Cosmos DB 自动索引所有属性，但您可以通过使用选择性索引策略创建稀疏模式。通过排除不需要索引的路径，有效地查询文档的少数部分，从而减少存储和写入 RU 成本，同时提高查询性能。

当过滤掉 90% 以上的属性时使用选择性索引。

示例：Products 容器，其中仅销售项需要 sale_price 索引

```json
{
  "indexingPolicy": {
    "includedPaths": [
      { "path": "/name/*" },
      { "path": "/category/*" },
      { "path": "/sale_price/*" }
    ],
    "excludedPaths": [
      { "path": "/*" }
    ]
  }
}
```

这减少了很少查询的属性的索引开销。

### 具有唯一约束的访问模式

Azure Cosmos DB 除了 id+partitionKey 组合外不强制执行唯一约束。对于其他唯一属性，请使用条件操作或事务内的存储过程在应用程序级别实现唯一性。

```javascript
// 存储过程用于创建具有唯一电子邮件的用户
function createUserWithUniqueEmail(userData) {
    var context = getContext();
    var container = context.getCollection();
    
    // 检查电子邮件是否已存在
    var query = `SELECT * FROM c WHERE c.email = "${userData.email}"`;
    
    var isAccepted = container.queryDocuments(
        container.getSelfLink(),
        query,
        function(err, documents) {
            if (err) throw new Error('Error querying documents: ' + err.message);
            
            if (documents.length > 0) {
                throw new Error('Email already exists');
            }
            
            // 电子邮件唯一，创建用户
            var isAccepted = container.createDocument(
                container.getSelfLink(),
                userData,
                function(err, document) {
                    if (err) throw new Error('Error creating document: ' + err.message);
                    context.getResponse().setBody(document);
                }
            );
            
            if (!isAccepted) throw new Error('The query was not accepted by the server.');
        }
    );
    
    if (!isAccepted) throw new Error('The query was not accepted by the server.');
}
```

此模式确保唯一性约束，同时保持单分区内的性能。

### 分层分区键（HPK）用于自然查询边界

🔴 **新功能** - 仅在专用 Cosmos DB NoSQL API 中可用：

分层分区键（HPK）使用多个字段作为分区键级别，提供自然查询边界，消除合成键复杂性，同时优化查询性能。

**标准分区键**：
```json
{
  "partitionKey": "account_123_test_456_chunk_001" // 合成复合键
}
```

**分层分区键**：
```json
{
  "partitionKey": {
    "version": 2,
    "kind": "MultiHash", 
    "paths": ["/accountId", "/testId", "/chunkId"]
  }
}
```

**查询优势**：
- 单分区查询：`WHERE accountId = "123" AND testId = "456"`
- 前缀查询：`WHERE accountId = "123"`（高效的跨分区查询）
- 自然层次结构消除了合成键逻辑

**考虑 HPK 时**：
- 数据具有自然层次结构（租户 → 用户 → 文档）
- 常见前缀查询
- 想要消除合成分区键复杂性
- 仅适用于 Cosmos NoSQL API 

**权衡**：
- 需要专用层（无服务器可用）
- 较新的功能，生产历史较少
- 查询模式必须与层次结构级别一致

### 使用写入分片处理高写入工作负载

写入分片将高容量写入操作分布在多个分区键上，以克服 Cosmos DB 的每个分区 RU 限制。此技术将计算分片标识符添加到您的分区键中，将写入分散到多个分区，同时保持查询效率。

当需要写入分片时：仅在多个写入集中在相同的分区键值上时应用，从而创建瓶颈。大多数高写入工作负载自然分布在许多分区键上，并且不需要分片的复杂性。

实现：使用基于哈希或基于时间的计算添加分片后缀：

```javascript
// 基于哈希的分片
partitionKey = originalKey + "_" + (hash(identifier) % shardCount)

// 基于时间的分片  
partitionKey = originalKey + "_" + (currentHour % shardCount)
```

查询影响：分片数据需要查询所有分片并在应用程序中合并结果，以查询复杂性换取写入可扩展性。

#### 分片集中写入

当特定实体接收不成比例的写入活动时，例如病毒式社交媒体帖子每秒接收数千次交互，而典型帖子仅偶尔活动。

PostInteractions 容器（有问题）：
• 分区键：post_id
• 问题：病毒帖子超过每个分区的 10,000 RU/s 限制
• 结果：在高参与度期间请求速率限制

分片解决方案：
• 分区键：post_id + "_" + shard_id（例如，"post123_7"）
• 分片计算：shard_id = hash(user_id) % 20
• 结果：将交互分布在每个帖子的 20 个分区上

#### 分片单调递增键

像时间戳或自动递增 ID 这样的顺序写入集中在最近值上，创建最新分区的热点。

EventLog 容器（有问题）：
• 分区键：date（YYYY-MM-DD 格式）
• 问题：所有今天的活动都写入相同的日期分区
• 结果：限制为 10,000 RU/s，无论总容器吞吐量如何

分片解决方案：
• 分区键：date + "_" + shard_id（例如，"2024-07-09_4"）  
• 分片计算：shard_id = hash(event_id) % 15
• 结果：将每日事件分布在 15 个分区上

### 聚合边界和更新模式

当聚合边界与更新模式冲突时，根据 RU 成本影响优先级：

示例：订单处理系统
• 读取模式：始终获取包含所有项目的订单（1000 RPS）
• 更新模式：单个项目状态更新（100 RPS）

选项 1 - 组合聚合（单个文档）：
- 读取成本：1000 RPS × 1 RU = 1000 RU/s
- 写入成本：100 RPS × 10 RU（重写整个订单）= 1000 RU/s

选项 2 - 分离项目（多文档）：
- 读取成本：1000 RPS × 5 RU（查询多个项目）= 5000 RU/s  
- 写入成本：100 RPS × 10 RU（更新单个项目）= 1000 RU/s

决策：选项 1 由于读取成本显著较低而更好，尽管写入成本相同

### 使用 TTL 建模瞬时数据

TTL 以成本有效的方式管理具有自然过期时间的瞬时数据。用于自动清理会话令牌、缓存条目、临时文件或特定时间段后变得不相关的限时通知。

Cosmos DB 中的 TTL 提供即时清理——过期文档在几秒钟内被删除。用于安全敏感和清理场景。您可以在 TTL 过期之前更新或删除文档。更新过期文档会通过修改 TTL 属性来延长其生命周期。

TTL 需要Unix时间戳（自 1970 年 1 月 1 日 UTC 以来的秒数）或 ISO 8601 日期字符串。

示例：24 小时过期的会话令牌

```json
{
  "id": "sess_abc123",
  "partitionKey": "user_456",
  "userId": "user_456", 
  "createdAt": "2024-01-01T12:00:00Z",
  "ttl": 86400
}
```

容器级 TTL 配置：
```json
{
  "defaultTtl": -1,  // 启用 TTL，无默认过期
}
```

文档上的 `ttl` 属性覆盖容器默认值，为每种文档类型提供灵活的过期策略。
