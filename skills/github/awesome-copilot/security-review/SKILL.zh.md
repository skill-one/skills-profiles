# 安全审查

一款基于人工智能的安全扫描器，它能像人类安全研究员一样对您的代码库进行分析——追踪数据流、理解组件交互，并发现模式匹配工具遗漏的漏洞。

## 使用此技能的场景

当请求涉及以下情况时，请使用此技能：

- 扫描代码库或文件以查找安全漏洞
- 运行安全审查或漏洞检查
- 检查 SQL 注入、XSS、命令注入或其他注入漏洞
- 查找代码中暴露的 API 密钥、硬编码的密钥或凭证
- 审计依赖项以查找已知的 CVE
- 审查身份验证、授权或访问控制逻辑
- 检测不安全的加密或弱随机数生成
- 执行数据流分析以追踪用户输入到危险接收端
- 任何类似“我的代码安全吗？”、“扫描此文件”或“检查我的仓库以查找漏洞”的请求表述
- 运行 `/security-review` 或 `/security-review <路径>`

## 此技能的工作原理

与传统的模式匹配静态分析工具不同，此技能：
1. **像安全研究员一样阅读代码** — 理解上下文、意图和数据流
2. **跨文件追踪** — 跟踪用户输入如何在您的应用程序中移动
3. **自我验证结果** — 重新检查每个结果以过滤误报
4. **分配严重性评级** — 严重性：CRITICAL / HIGH / MEDIUM / LOW / INFO
5. **提出有针对性的补丁** — 每个发现都包含具体的修复方案
6. **需要人工批准** — 不会自动应用任何内容；您始终先进行审查

## 执行工作流程

每次都按以下步骤**顺序**执行：

### 第 1 步 — 范围解析
确定要扫描的内容：
- 如果提供了路径（`/security-review src/auth/`），则仅扫描该范围
- 如果未提供路径，则扫描**整个项目**，从根目录开始
- 确定使用的语言和框架（检查 `package.json`、`requirements.txt`、`go.mod`、`Cargo.toml`、`pom.xml`、`Gemfile`、`composer.json` 等）
- 阅读 `references/language-patterns.md` 以加载特定语言的漏洞模式

### 第 2 步 — 依赖项审计
在扫描源代码之前，先审计依赖项（快速见效）：
- **Node.js**：检查 `package.json` + `package-lock.json` 以查找已知漏洞包
- **Python**：检查 `requirements.txt` / `pyproject.toml` / `Pipfile`
- **Java**：检查 `pom.xml` / `build.gradle`
- **Ruby**：检查 `Gemfile.lock`
- **Rust**：检查 `Cargo.toml`
- **Go**：检查 `go.sum`
- 标记已知 CVE 的包、已弃用的加密库或可疑的固定版本
- 阅读 `references/vulnerable-packages.md` 以获取精选的漏洞包监视列表

### 第 3 步 — 密钥与暴露扫描
扫描所有文件（包括配置文件、环境文件、CI/CD、Dockerfile、IaC）以查找：
- 硬编码的 API 密钥、令牌、密码、私钥
- 意外提交的 `.env` 文件
- 代码中的注释或调试日志中的密钥
- 云凭证（AWS、GCP、Azure、Stripe、Twilio 等）
- 嵌入凭证的数据库连接字符串
- 阅读 `references/secret-patterns.md` 以应用正则表达式模式和熵启发式规则

### 第 4 步 — 深度漏洞扫描
这是核心扫描。对代码进行推理——不要只进行模式匹配。
阅读 `references/vuln-categories.md` 以获取每个类别的详细信息。

**注入漏洞**
- SQL 注入：使用字符串插值、ORM 误用、二次 SQL 注入的原始查询
- XSS：未转义输出、dangerouslySetInnerHTML、innerHTML、模板注入
- 命令注入：使用用户输入的 `exec/spawn/system`
- LDAP、XPath、Header、日志注入

**身份验证与访问控制**
- 敏感端点的身份验证缺失
- 分层对象级授权（BOLA/IDOR）失效
- JWT 弱点（alg:none、弱密钥、无过期验证）
- 会话固定、缺失 CSRF 保护
- 权限提升路径
- 大量赋值 / 参数污染

**数据处理**
- 日志、错误消息或 API 响应中的敏感数据
- 缺失静态加密或传输加密
- 不安全的反序列化
- 路径遍历 / 目录遍历
- XXE（XML 外部实体）处理
- SSRF（服务器端请求伪造）

**加密**
- 使用 MD5、SHA1、DES 进行安全目的
- 硬编码的 IV 或盐
- 弱随机数生成（使用 `Math.random()` 生成令牌）
- 缺失 TLS 证书验证

**业务逻辑**
- 竞态条件（TOCTOU）
- 财务计算中的整数溢出
- 敏感端点缺失速率限制
- 可预测的资源标识符

### 第 5 步 — 跨文件数据流分析
在文件级扫描后，执行**整体审查**：
- 从入口点（HTTP 参数、头部、正文、文件上传）追踪用户控制输入，直到接收端（数据库查询、`exec` 调用、HTML 输出、文件写入）
- 识别仅在查看多个文件时才出现的漏洞
- 检查服务或模块之间不安全的信任边界

### 第 6 步 — 自我验证轮次
对每个发现：
1. 用新鲜的眼光重新阅读相关代码
2. 询问：“这是否真的可利用，还是我遗漏了清理措施？”
3. 检查框架或中间件是否已在上游处理此问题
4. 降级或丢弃并非真实漏洞的发现
5. 分配最终严重性：CRITICAL / HIGH / MEDIUM / LOW / INFO

### 第 7 步 — 生成安全报告
以 `references/report-format.md` 中定义的格式输出完整报告。

### 第 8 步 — 提出补丁
对每个 CRITICAL 和 HIGH 发现，生成具体的补丁：
- 显示易受攻击的代码（之前）
- 显示修复后的代码（之后）
- 解释更改的内容和原因
- 保持原始代码风格、变量名和结构
- 添加内联注释解释修复方案

明确声明：**“在应用之前审查每个补丁。尚未进行任何更改。”**

## 严重性指南

| 严重性 | 含义 | 示例 |
|--------|------|------|
| 🔴 CRITICAL | 立即利用风险，可能发生数据泄露 | SQLi、RCE、身份验证绕过 |
| 🟠 HIGH | 严重漏洞，存在利用路径 | XSS、IDOR、硬编码的密钥 |
| 🟡 MEDIUM | 条件或链式利用的漏洞 | CSRF、开放重定向、弱加密 |
| 🔵 LOW | 违反最佳实践，直接风险低 | 详细错误、缺失头部 |
| ⚪ INFO | 值得注意的观察，不是漏洞 | 无 CVE 的过时依赖 |

## 输出规则

- **始终**首先生成发现摘要表（按严重性统计）
- **绝不**自动应用任何补丁——仅供人工审查
- **始终**为每个发现包含置信度评级（高 / 中 / 低）
- **按类别分组发现**，而不是按文件
- **具体说明**——包括文件路径、行号和具体的易受攻击代码片段
- **用普通英语解释风险**——攻击者可以利用此漏洞做什么？
- 如果代码库干净，请明确说明：“未发现漏洞”，并列出扫描的内容
