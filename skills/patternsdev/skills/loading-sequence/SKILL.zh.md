# 优化加载顺序

## 目录

- [何时使用](#何时使用)
- [说明](#说明)
- [详情](#详情)
- [来源](#来源)

在每一个成功的网页加载过程中，一些关键组件和资源在恰当的时间变得可用，从而为您提供一个流畅的加载体验。这确保用户感知到的应用性能是出色的。这种出色的用户体验通常也意味着能够通过[核心网页指标](https://web.dev/vitals/)。

## 何时使用

- 当您优化核心网页指标页面加载性能时使用
- 当您需要协调1P JS、3P JS、CSS、字体和图像的加载时
- 当第三方脚本影响您的加载性能时使用

## 说明

- 内联关键CSS和字体CSS；对外部字体使用预连接
- 资源排序，确保在LCP之前触发FCP，在FID之前触发LCP
- 在网络上的ATF图像之前开始获取第一方JS
- 对非关键脚本使用`async`或`defer`属性
- 懒加载折叠图像和非必要的第三方资源

## 详情

关键[指标](https://web.dev/metrics/)，如[首次内容绘制](https://web.dev/fcp/)、[最大内容绘制](https://web.dev/lcp/)、[首次输入延迟](https://web.dev/fid/)等，用于衡量性能，它们直接依赖于关键资源的加载顺序。例如，如果关键资源（如[英雄图像](https://en.wikipedia.org/wiki/Hero_image)）未加载，页面将无法拥有其LCP。本文讨论了资源加载顺序与网页指标之间的关系。我们的目标是提供清晰的指导，说明如何优化加载顺序以获得更好的网页指标。

在我们建立理想的加载顺序之前，让我们先尝试理解为什么正确的加载顺序如此难以实现。

### 为什么难以实现最佳加载？

我们有机会为许多合作伙伴的网站进行性能分析。我们识别了多个困扰不同合作伙伴网站页面高效加载的类似问题。

开发者对浏览器如何优先处理页面资源的期望之间往往存在关键差距。这通常导致性能得分不佳。我们进一步分析了造成这种差距的原因，以下要点总结了我们的分析精华。

**加载顺序不佳**

[网页指标](https://web.dev/vitals/)优化不仅需要对每个指标的含义有良好的理解，还需要了解它们的触发顺序以及它们与不同关键资源的关系。FCP发生在LCP之前，LCP发生在FID之前。因此，实现FCP所需的资源应优先于LCP所需的资源，然后是FID所需的资源。

资源通常没有被按正确的顺序进行排序和管道化。这可能是因为开发者不了解指标对资源加载的依赖性。结果，相关资源有时在对应指标触发时无法在正确的时间可用。

**示例**：

a) 当FCP触发时，英雄图像应准备好触发LCP。
b) 当LCP触发时，JavaScript (JS) 应已下载、解析并准备（或已执行）以取消阻止交互（FID）。

**网络/CPU利用率**

资源也没有适当地进行管道化，以确保CPU和网络充分利用。这导致CPU在处理网络绑定进程时出现“空闲时间”，反之亦然。

一个很好的例子是可能同时或按顺序下载的脚本。随着带宽在并发下载时被分配，无论是顺序下载还是并发下载，下载所有脚本的总时间都是相同的。如果您并发下载脚本，CPU在下载期间未充分利用。但是，如果您按顺序下载脚本，CPU可以在下载后立即开始处理第一个脚本。这导致更好的CPU和网络利用率。

**第三方(3P)产品**

3P库通常用于向网站添加常见功能和功能。第三方包括广告、分析、社交小部件、实时聊天和其他嵌入内容，这些内容为网站提供动力。3P库带有自己的JavaScript、图像、字体等。

3P产品通常没有动力去优化和支持消费者网站的加载性能。它们可能有沉重的JavaScript执行成本，这会延迟交互，或者妨碍其他关键资源被下载。

包含3P产品的开发者可能更关注它们在功能方面的价值，而不是性能影响。结果，3P资源有时会被随意添加，而没有充分考虑它们如何融入整体加载顺序。这使得它们难以控制和调度。

**平台怪癖**

浏览器在如何优先处理请求和实现提示方面可能有所不同。如果您对平台及其怪癖有深入的了解，优化会更容易。特定浏览器的特定行为使得实现所需的加载顺序变得困难。

一个例子是chromium平台上的[预加载错误](https://bugs.chromium.org/p/chromium/issues/detail?id=788757)。[预加载](https://medium.com/reloading/preload-prefetch-and-priorities-in-chrome-776165961bbf) (`<link rel=preload>`) 指令可用于告诉浏览器尽快下载关键资源。只有当您确定资源将在当前页面上使用时才应使用它。Chromium中的错误导致其行为，即通过`<link rel=preload>`发出的请求始终在预加载扫描器看到的其他请求之前开始，即使这些请求具有更高的优先级。此类问题会破坏优化计划。

**HTTP2优先级**

协议本身并没有提供许多选项或旋钮来调整资源的顺序和优先级。即使更好的优先级原语要提供，也存在HTTP2优先级[问题](https://github.com/andydavies/http2-prioritization-issues)，这使得最佳排序变得困难。主要是，我们无法预测服务器或CDN将按什么顺序优先处理单个资源的请求。一些CDN会重新优先处理请求，而其他CDN则实现了部分、有缺陷或不优先处理。

**资源级优化**

有效的排序需要被排序的资源以最佳方式提供服务，以便它们可以快速加载。关键CSS应内联，图像应正确设置大小，JavaScript应进行代码拆分并逐步交付。

框架本身缺乏允许代码拆分和逐步交付JavaScript和数据的结构。用户必须依赖以下方法之一来拆分1P JS的大块：

1. 现代React（Suspense / 并发模式 / 数据获取）- 这仍然仅限于实验
2. 使用动态导入进行懒加载 - 这不直观，开发者需要手动识别拆分代码的边界。

在代码拆分时，由于粒度与性能之间的权衡，开发者需要实现恰到好处的块粒度。

更高的粒度是理想的选择，因为它：

1. 最小化单个路由和后续用户交互所需的JavaScript
2. 允许缓存常见依赖项。这确保了库的更改不需要重新获取整个包。

同时，代码拆分时粒度过高也可能很糟糕，因为过多的较小块会降低单个块的压缩率并影响浏览器性能。

资源优化还需要消除死代码或未使用的代码。不必要的或过时的JavaScript可能会被运送到现代浏览器，从而对性能产生负面影响。现代浏览器转译为ES5并与polyfills捆绑的JavaScript是不必要的。库和npm包通常不以ES模块格式发布。这使得打包器难以进行摇树和优化。

如您所见，这些问题并不仅限于特定的一组资源或平台。为了解决这些问题，人们需要对整个技术堆栈有深入的了解，以及如何将不同资源结合起来以实现最佳指标。

### 更多关于资源 - 关系、约束和优先级

在上一节中，我们给出了几个示例，说明某些资源是如何被需要的，以便特定的触发事件（如FCP或LCP）可以触发。在我们讨论如何处理它们之前，让我们先了解所有这样的依赖关系。以下是我们在定义理想顺序之前需要考虑的资源级建议、约束和注意事项列表。

**关键CSS**

[关键CSS](https://web.dev/extract-critical-css/)是指实现FCP所需的最小CSS。最好将此类CSS内联在HTML中，而不是从另一个CSS文件中导入。在任何给定时间，应仅下载路由所需的CSS，并且所有关键CSS都应相应地进行拆分。

如果内联不可行，关键CSS应预加载，并从与文档相同的源提供服务。避免从多个域提供关键CSS，或直接使用第三方关键CSS，如Google Fonts。您的服务器可以作为第三方关键CSS的代理。

获取CSS的延迟或获取CSS的顺序不正确可能会影响FCP和LCP。为了避免这种情况，非内联CSS应优先级排序，并在网络上位于1P JS和ATF图像之上。

过多的内联CSS会导致HTML膨胀，并导致主线程上的样式解析时间过长。这可能会损害FCP。因此，识别什么是关键的以及代码拆分至关重要。

内联CSS无法缓存。一个解决方法是为CSS创建一个重复请求，该请求可以缓存。请注意，这可能导致多个全页布局，从而影响FID。

**字体**

与关键CSS类似，[关键字体](https://web.dev/font-best-practices/)的CSS也应内联。如果内联不可行，脚本应使用[预连接](https://web.dev/uses-rel-preconnect/)指定进行加载。获取字体的延迟（例如，Google Fonts或来自不同域的字体）会影响FCP。预连接告诉浏览器更早地建立到这些资源的连接。

内联字体会显著膨胀HTML，并延迟启动其他关键资源获取。[字体回退](https://css-tricks.com/css-basics-fallback-font-stacks-robust-web-typography/)可用于取消阻止FCP并使文本可用。然而，使用字体回退可能会由于字体跳转而影响[CLS](https://web.dev/cls/)。它还可能由于主线程上可能的大型样式和布局任务而导致实际字体到达时影响FID。

**折叠图像（ATF）**

这指的是在页面加载时最初对用户可见的图像，因为它们位于视口中。折叠图像的特殊情况是页面的英雄图像。所有折叠图像都应设置大小。未设置大小的图像会因它们完全渲染时发生的布局偏移而损害CLS指标。折叠图像的占位符应由服务器渲染。

延迟英雄图像或空白占位符会导致晚上的LCP。此外，如果占位符大小与实际英雄图像的固有大小不匹配，并且图像没有覆盖在替换上，LCP将重新触发。理想情况下，由于折叠图像不应影响FCP，但在实践中，图像可能会触发FCP。

**折叠图像（BTF）**

这些是在页面加载时对用户不立即可见的图像。因此，它们是懒加载的理想候选者。这确保它们不会与1P JS或页面上的重要3P资源竞争。如果BTF图像在1P JS或重要3P资源之前加载，FID将会延迟。

**第一方JavaScript（1P JavaScript）**

1P JS会影响应用程序的交互就绪性。它可能会在网络上的图像和3P JS之后延迟，并在主线程上的3P JS之后延迟。因此，它应在网络上位于ATF图像之前开始加载，并在主线程上位于3P JS之前执行。1P JS不会阻塞服务器端渲染页面的FCP和LCP。

**第三方JavaScript（3P JavaScript）**

HTML头部中的3P同步脚本可能会阻塞CSS和字体的解析，因此会阻塞FCP。头部中的同步脚本也会阻塞HTML主体解析。3P脚本在主线程上的执行可能会延迟1P脚本的执行，并推迟水合和FID。因此，需要更好地控制3P脚本的加载。

这些建议和约束通常适用于任何技术堆栈和浏览器。请注意，某些建议也可能成为约束。例如，内联字体和CSS很好，但过多的内联会导致膨胀。诀窍是在“太少太晚”和“太多太早”之间找到平衡。

以下是Chrome资源优先级表的关键要点：

- CSS和字体以最高优先级加载。这应该有助于我们优先考虑关键CSS和字体。
- 脚本根据它们在文档中的位置以及它们是否为异步、延迟或阻塞而获得不同的优先级。在第一个图像（或文档中的早期图像）之前请求的阻塞脚本比在第一个图像获取后请求的阻塞脚本具有更高的优先级。无论它们在文档中的位置如何，异步/延迟/注入脚本都具有最低优先级。因此，我们可以通过使用适当的[异步和延迟](https://javascript.info/script-async-defer)属性来优先考虑不同的脚本。
- 位于视口内且可见的图像具有比不在视口内的图像更高的优先级（网络：中）而不是（网络：最低）。这有助于我们优先考虑折叠图像而不是折叠图像。

现在，让我们看看如何将上述所有细节结合起来，以定义一个理想的加载顺序。

### 理想的加载顺序是什么

有了这些背景，我们现在可以提出一个加载顺序，该顺序应优化1P和3P资源的加载。建议的顺序使用[Next.js](https://nextjs.org/)服务器端渲染（SSR）作为优化的参考。

#### 当前状态

根据我们的经验，在优化之前，Next.js SSR应用程序的典型加载顺序如下所示。

| 资源 | 状态 |
|------|------|
| CSS | CSS在JS之前预加载，但未内联 |
| JavaScript | 1P JS预加载。3P JS未管理，并且仍然可以在文档的任何位置阻止渲染。 |
| 字体 | 字体既不内联也不使用预连接。字体通过外部样式表加载，这会延迟加载。字体可能或不可能显示阻塞。 |
| 图像 | 英雄图像未优先处理。折叠图像和折叠图像均未优化。 |

#### 无3P的建议顺序

以下是一个加载顺序，它考虑了之前讨论的所有约束。让我们首先处理没有3P的顺序。然后，我们将看看如何将3P资源插入此顺序中。请注意，在这里我们将Google Fonts视为1P。

| # (主线程) | 事件 | # (网络) | 请求 |
|---|---|---|---|
| 1 | 解析 HTML | 1 | 小型内联 1P 脚本 |
| 2 | 执行小型内联 1P 脚本 | 2 | 内联关键 CSS（外部则预加载） |
| | | 3 | 内联关键字体（外部则预连接） |
| 3 | 解析 FCP 资源（关键 CSS、字体） | 4 | LCP 图片（外部则预连接） |
| **FCP** | | 5 | 字体（由内联字体 CSS 触发，预连接） |
| 4 | 渲染 LCP 资源（英雄图片、文本） | 6 | 非关键（异步）CSS |
| | | 7 | 第一方 JS 用于交互 |
| | | 8 | 窗口上方图片（预连接） |
| **LCP** | | 9 | 窗口下方图片 |
| 5 | 渲染重要窗口上方图片 | | |
| **视觉完成** | | | |
| 6 | 解析非关键（异步）CSS | | |
| 7 | 执行 1P JS 并水合 | 10 | 懒加载 JS 块 |
| **FID** | | | |

虽然这个序列的某些部分可能很直观，但以下要点将有助于进一步证明其合理性。

1. 我们建议尽可能避免预加载，因为它会强制对每个前置资源进行手动预加载，并且还会导致手动排序。应特别避免对字体进行预加载，因为检测关键字体的过程很复杂。
2. 字体 CSS 应尽可能内联。来自其他源的字体应使用预连接进行获取。
3. 建议对所有来自其他源的资源使用预连接。这将确保在下载这些资源之前建立连接。
4. 非关键 CSS 应在用户交互开始之前获取（FID）。这将避免由于后续渲染此类 CSS 而导致的样式问题。
5. 在网络中开始获取第一方 JS，在窗口上方图片之前。下载和解析 JS 需要一些时间。
6. 在解析第一方 JS 期间，主线程上的 HTML 解析和窗口上方图片的下载可以并行进行。

#### 带有第三方资源的建议序列

最后，我们可以为现代 Web 应用中常见的所有关键资源提出一个序列。以下是主浏览器线程上的事件和网络请求序列，其中包含第三方资源。

| # | 主线程事件 | 网络请求 |
|---|---|---|
| 1 | 解析 HTML | FCP 阻塞第三方资源 |
| 2 | | |
| 3 | | 小型内联 1P 脚本 |
| 4 | 执行小型内联 1P 脚本 | 内联关键 CSS（外部则预加载） |
| 5 | 解析 FCP 阻塞第三方资源 | 内联关键字体（外部则预连接） |
| 6 | 解析 FCP 资源（关键 CSS、字体） | 第三方个性化窗口上方图片（用于 LCP） |
| 7 | **FCP** | LCP 图片（外部则预连接） |
| 8 | 渲染第三方个性化窗口上方图片（用于 LCP） | 字体（由内联字体 CSS 触发，预连接） |
| 9 | | 非关键（异步）CSS |
| 10 | 渲染 LCP 资源（英雄图片、文本） | 必须在第一次用户交互之前执行的第三方 |
| 11 | | 第一方 JS 用于交互 |
| 12 | **LCP** | |
| 13 | 渲染重要窗口上方图片 | 默认第三方 JS |
| 14 | 解析非关键（异步）CSS | |
| 15 | 执行第一次用户交互所需的第三方 | 窗口下方图片 |
| 16 | 执行 1P JS 并水合 | 懒加载 JS 块 |
| **FID** | | 较不重要的第三方 JS |

这里的主要问题是如何确保第三方脚本以最佳顺序下载。

由于脚本请求会发送到另一个域，建议对以下第三方请求使用预连接：

- #1 - FCP 阻塞第三方资源
- #5 - 第三方个性化窗口上方图片（用于 LCP）
- #9 - 必须在第一次用户交互之前执行的第三方
- #12 - 默认第三方 JS

为了实现所需的序列，我们建议使用 Next.js 的 ScriptLoader 组件。该组件的设计目的是“优化关键渲染路径并确保外部脚本不会成为影响页面加载速度的瓶颈”。与我们讨论最相关的功能是加载优先级。这允许我们在不同的时间点安排脚本，以支持不同的用例。以下是可用的加载优先级值：

**After-Interactive**：在下次水合之后加载特定的第三方脚本。这可用于加载 Tag-managers、Ads 或 Analytics 脚本，我们希望尽早执行，但在第一方脚本之后。

**Before-Interactive**：在 hydration 之前加载特定的第三方脚本。这可用于需要第三方脚本在第一方脚本之前执行的用例。例如，polyfill.io、bot 检测、安全和身份验证、用户同意管理（GDPR）等。

**Lazy-Onload**：优先级高于所有其他资源，并延迟加载指定的第三方脚本。这可用于 CRM 组件，如 Google Feedback 或特定于社交网络的脚本，如用于分享按钮、评论等。

因此，预连接、脚本属性和 Next.js 的 ScriptLoader 一起可以帮助我们获得所有脚本的所需序列。

### 结论

优化应用的责任落在平台的使用者和开发者身上。需要解决常见问题。我们旨在从内部到外部简化序列。针对不同用例的经过验证的建议和像 Script Loader 这样的倡议有助于 React-Next.js 堆栈实现这一点。下一步将是确保新应用符合上述建议。
