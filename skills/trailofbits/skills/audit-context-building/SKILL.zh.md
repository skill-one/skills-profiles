# 审计上下文构建

建立理解，而非结论。这运行在任何人寻找漏洞之前，并为后续工作提供支持。

## 使用场景

在审计、威胁模型或架构评审开始时，当代码不熟悉时使用。也用于早期阶段发现了无人能判断的发现，因为没有人绘制出系统如何组合的图景。

## 不使用场景

不要命名漏洞、建议修复方案、编写概念验证代码或评估严重性。这些属于寻找漏洞阶段，该阶段将在后续进行，并掌握整体情况。当代码依赖某事物且无人检查时，明确记录并继续前进——是否重要将在后续决定。

对于已经理解的代码，不值得使用这些标记。

## 在此上下文中不进行分析

分析过程很长，而此上下文需要保留以供使用。将其派发出去：

- **代码库或多个函数** — 运行 `/audit-context-building:audit-context <路径>`。它进行定向，在每个子代理中分析每个函数，并写入 `audit-context/DOSSIER.md` 以及在 `audit-context/functions/` 下每个函数的文件。只有紧凑记录会返回。
- **单个函数** — 将 `audit-context-building:function-analyzer` 代理派发到它。它将文本写入磁盘并返回记录。

然后从返回的内容中工作：索引、未执行的假设、开放性问题。需要函数的细节时，读取该函数的文件。

工作流程强制执行这一点，而不是此文本：绑定到返回模式的子代理不能返回文本。将此部分视为路由，并进行路由。

## 返回的内容及如何阅读

每条记录列出了必须始终为真的内容（以及显示该内容的行）、函数基于信仰接受的内容（以及建立该内容的任何内容）、它调用的函数及其所需内容，以及任何仍不明确的内容。档案添加了跨越多个函数的规则、谁可以访问什么，以及复杂部分聚集的地方。

比其他任何内容都重要的是两件事：

- **标记为 `nothing found` 的假设。** 代码依赖某事物为真，而没有任何地方使其为真。这是交给寻找漏洞阶段最有用的东西。
- **开放性问题。** 一份诚实的不明确清单胜过自信的答案，而该答案最终被证明是错误的。继续推进它们，而不是关闭它们。

当两条记录不一致时，会引用两者，而不是悄悄地协调。这是关于代码的事实，而不是分析中的缺陷。

## 格式

[ANALYSIS_FORMAT.md](resources/ANALYSIS_FORMAT.md) 定义了它，而
[FUNCTION_MICRO_ANALYSIS_EXAMPLE.md](resources/FUNCTION_MICRO_ANALYSIS_EXAMPLE.md) 通过 C 和 Solidity 中的示例进行说明。在扩展此插件或决定记录是否可信时，请阅读它们。

无论目标是什么，格式都是相同的。变化的是填充每个插槽的内容，以及什么被视为你无法在内部看到的调用。[DOMAIN_NOTES.md](resources/DOMAIN_NOTES.md) 跨智能合约、C 和 C++、反编译固件和 Web 服务进行映射——当目标不是普通源代码时，请阅读它。

**最重要的规则：跟随调用。** 函数是否正确通常取决于另一个函数的行为，而你不能仅从调用者那里看到这一点。一个限制看起来是强制执行的，因为值来自一个函数，其名称暗示它被检查了。因此，阅读被调用的函数，跟随通过它的每条路径，而不是只有成功的路径，并说明什么使每个假设为真。当没有任何东西这样做时，使用这些词：`nothing found`。每个声明都引用一行，或者成为开放性问题。
