# 规格到代码符合性

两个工件不一致，任务是找出不一致之处。文档说明系统应该做什么；代码决定它实际做了什么。它们之间的每一个差距要么是错误，要么是文档修正，而哪一个是取决于发现结果。

## 使用场景

你同时拥有描述预期行为的文档和应该实现该行为的代码。白皮书与协议，设计笔记与服务，README声明的保证与背后的函数。

当文档具有权威性时最有效——例如客户编写的、发布的或用于审计的文档——因为那时分歧是缺陷而不是过时的文字。

## 不适用场景

不适用于没有预期行为文档的代码。没有可以对照检查的东西，从代码中推断出的需求是自我检查的。首先使用`audit-context-building`构建系统模型。

不适用于查找一般错误。这仅发现一类问题：代码与文档不一致。两个工件都沉默不语的问题不在范围内，文档认可的错误是对文档的发现。

不适用于编写或改进文档，尽管它生成了需要修正的列表。

## 在这种情况下不要检查需求

运行`/spec-to-code-compliance:spec-compliance <路径>`。该命令行工具接受一个路径；要直接命名规范或扩大发散范围，请请求具有这些值的运行——"在`./contracts`上运行spec-compliance检查SPEC.md，检查20个需求"——它们将作为`{路径, 规范, 限制}`传递给脚本。在命令行工具后直接键入对象不工作；它作为字符串到达，并成为路径。

它查找文档，将它们拆分为可单独检查的需求，为每个需求分配自己的代理去追踪代码，让独立的代理在报告之前尝试反驳每一个分歧，并写入`spec-compliance/REPORT.md`以及`spec-compliance/requirements/`下的每个需求文件。这里只返回紧凑的记录。

对于单个需求，派遣`spec-to-code-compliance:spec-compliance-checker`代理去处理。

这不是关于输出放置位置的首选。如果诚实地进行检查，检查一个需求意味着阅读其执行、其调用者和其调用者，而检查30个需求意味着同时持有30个调用链。尝试内联，前几个会得到真正的检查，其余的会得到合理的检查——无论哪种方式，记录看起来都一样，因为基于有希望的功能名称的裁决与阅读函数的裁决完全一样。每个需求在其自己的上下文中，这就是可见的差异。

来自脚本的两种属性不是来自指令，这里无法获得：

- **发现者未执行的反驳。** Claude更倾向于在要求检查它们时产生的发现。工作流程将每个分歧发送给未产生它的代理——一个重新阅读代码，一个重新阅读文档——并丢弃任何一方推翻的内容。
- **无法用文字描述的记录。** 绑定到返回模式的子代理必须命名它读取的行和它运行的搜索。`absent`裁决会附带尝试的模式及其结果，这是区分真实缺失与早期停止搜索的唯一东西。

在`routes-not-inline`评估上测量：安装此插件后每次运行都会派遣工作，未安装则从不——Δ +1.00。删除此部分而保留工作流程不变不会改变任何东西，因为工作流程是一个真实命令，它自己被发现并派遣。将其理解为携带行为的机制而不是这段文字：本节在此是为了让人类知道运行什么以及为什么运行，而不是因为路由依赖于它。

## 返回的内容以及如何阅读

每个需求会得到六种裁决中的一种：`implemented`、`partial`、`contradicted`、`stronger-than-spec`、`absent`或`undecidable`。有趣的是中间四种。

- **`partial`** 通常是报告中最严重的问题。需求在任何人都会测试的路径上成立，但在没有人测试的路径上失败，这就是它存活足够长的时间被发现的原因。
- **`absent`** 完全取决于其`searched`记录。阅读它。执行通常存在于搜索没有去的地方——一个修饰符，一个基类，一个首先进行检查的调用者。
- **`undecidable`**，以及任何`documentProblem`，都是关于文档的发现。无法检查的过于模糊的需求是客户无法要求任何人遵守的。
- **`stronger-than-spec`** 是一个未文档化的约束。它今天有效，而且没有任何东西告诉下一个修改该代码的人有任何东西依赖于它。

报告还包含反向方向——代码具有而文档未提及的行为——这是按需检查需求无法构建发现的，因为它是由文档驱动的。

在处理报告为完整之前，先阅读`notChecked`、`unverified`和`unreadableDocuments`。被发散范围裁剪下的需求从未被检查过，而反驳代理双方都失败的分歧是未验证而不是确认的。

## 工作流程不会为你做的裁决

严重性是后果，而不是与文本的距离：[DIVERGENCE_RUBRIC.md](resources/DIVERGENCE_RUBRIC.md)。一个使池子外流的舍入步骤优先于以文档描述的不同方式满足的MUST，而没有任何行为后果的文档漂移是一个文档工单。

裁决不是发现。`absent`在强制需求上是发现；`absent`在一个描述路线图项目的句子上是发现。决定哪个是哪个是这个技能的目的，工作流程将证据交给你来决定。

## 目标不必是合同

问题到处都是相同的——这个需求要求什么，在哪里执行，是否在每条路径上执行——但什么构成规范以及执行隐藏在哪里都会改变。[DOMAIN_NOTES.md](resources/DOMAIN_NOTES.md)将它们映射到合同、C和C++、服务和反编译固件，并涵盖了规范是RFC或标准而不是项目文档的情况。在目标不是合同时以及在对大型标准进行范围检查时阅读它。
