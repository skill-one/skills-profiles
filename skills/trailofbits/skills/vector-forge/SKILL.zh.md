# 向量锻造

使用变异测试系统性地识别测试向量覆盖的空白，然后生成新的测试向量来填补这些空白。通过比较变异前后的杀灭率来衡量有效性。

## 使用场景

- 为密码学算法或协议生成测试向量
- 评估现有测试向量对实现的覆盖程度
- 找到没有测试向量执行的实现代码路径
- 创建类似 Wycheproof 的跨实现测试向量
- 测量测试向量套件的具象覆盖值

## 不适用场景

- 尚未存在实现（需要代码进行变异）
- 单个简单的实现，没有边界情况
- 测试应用逻辑而不是算法实现
- 算法没有公开的测试向量可供比较

## 前置条件

- **trailmark** 安装 — 如果 `uv run trailmark` 失败，请运行：
  ```bash
  uv tool install trailmark
# Python 代码片段：uv run --with trailmark python -   (一个工具环境不可导入)
  ```
- 至少有一个目标算法的实现，该实现使用支持变异测试的语言
- 一个消耗测试向量并执行实现的测试框架
- 目标语言的变异测试框架

## 拒绝理由

| 拒绝理由 | 为什么错误 | 必要操作 |
|----------|----------------|-----------------|
| "我们已经有足够的测试向量" | 变异测试证明并非如此 | 首先运行基线测试 |
| "实现的自身测试就足够了" | 自身测试通常与实现共享盲点 | 跨实现向量可以捕获不同的错误 |
| "FFI crate 可以在绑定层进行变异测试" | 对包装器的变异不会影响底层实现 | 变异实际的实现语言 |
| "超时意味着变异被捕获" | 超时是模糊的 — 可能被杀灭或存活 | 在得出结论之前解决超时 |
| "所有变异体都等效" | 大多数都不等效 — 通过阅读变异进行验证 | 逐个分类逃逸的变异体 |
| "检查有效向量就足够了" | 严格的变异在没有负断言的情况下存活 | 对每个无效向量断言拒绝 |
| "手动分析很好" | 手动分析遗漏了工具可以捕获的内容 | 安装并运行工具 |

## 工作流程概述

```
阶段 1：发现       → 找到要测试的实现
      ↓
阶段 2：测试框架   → 为每个实现编写/适配测试向量测试框架
      ↓
阶段 3：基线       → 使用现有向量运行变异测试
      ↓
阶段 4：逃逸分析   → 按代码路径对逃逸的变异体进行分类
      ↓
阶段 5：向量生成   → 创建针对逃逸的测试向量
      ↓
阶段 6：验证       → 重新运行变异测试，比较前后
      ↓
输出：覆盖报告 + 新的测试向量
```

---

## 阶段 1：发现

找到目标算法的实现。寻找：

1. **高级语言中的纯实现**（Go、Rust、Python） — 这些是最佳的变异测试目标
2. **FFI 包装器 crate** — 尽早识别这些，以免浪费时间变异包装器胶水代码
3. **参考实现** — 对于交叉验证很有用，但不一定是最佳的变异目标

对于每个实现，注意：
- 语言和变异测试框架
- 是否是纯代码还是 FFI 包装器
- 现有测试套件的大小和覆盖范围
- 测试向量将执行的 API 表面

### 实现类型分类

| 类型 | 变异值 | 示例 |
|------|---------------|---------|
| 纯实现 | 高 | zkcrypto/bls12_381 (Rust), gnark-crypto (Go) |
| FFI 绑定到 C/汇编 | 绑定层低 | blst Rust crate |
| C/C++ 实现 | 高（使用 Mull） | blst C 库 |
| 生成代码 | 中等（变异可能等效） | gnark-crypto 生成的字段算术 |

**关键洞察：** 如果一个实现通过 FFI 委托到另一种语言，你必须变异*底层的*实现，而不是绑定。对于 Rust/Go/Python 下面的 C/C++，使用 Mull 或类似工具。

---

## 阶段 2：测试框架

为每个实现创建一个测试框架，该框架：

1. 从 JSON 文件读取测试向量（推荐使用 Wycheproof 格式）
2. 为每个向量执行实现 API
3. 断言**接受和拒绝**：
   - 有效向量：反序列化成功，输出与预期匹配
   - 无效向量：反序列化失败或验证拒绝
4. 添加**往返断言**用于有效的反序列化向量：
   `serialize(deserialize(bytes)) == bytes`
5. 按向量报告通过/失败，并带有测试 ID

**关键：** 仅检查有效向量的测试框架将遗漏所有严格的变异（例如，`&` → `|` 在验证中）。参见
[references/lessons-learned.md](references/lessons-learned.md) §7。

测试框架必须可由变异测试框架运行。对于大多数框架，这意味着：
- **Go：** 同一包中的 `_test.go` 文件
- **Rust：** `tests/` 中的集成测试或内联 `#[test]` 函数
- **Python：** pytest 测试文件
- **C/C++：** 链接实现的可执行文件

### 测试框架位置

测试框架必须位于*实现的包内*，以便变异框架可以看到它。这通常意味着：

```bash
# Go: 将测试文件添加到正在变异的包
cp wycheproof_test.go /path/to/impl/package/

# Rust: 添加集成测试
cp wycheproof.rs /path/to/crate/tests/

# Python: 将测试添加到测试目录
cp test_wycheproof.py /path/to/package/tests/
```

### 处理现有向量

如果实现已经有测试向量：
1. 仅使用现有向量运行变异测试（基线）
2. 仅使用你的新向量运行变异测试
3. 合并两者一起运行变异测试
4. (1) 和 (3) 之间的差异显示了新向量的价值

## 阶段 3：基线

仅使用现有测试向量运行变异测试。

### 框架选择

参见 [references/mutation-frameworks.md](references/mutation-frameworks.md)
了解语言特定的设置。

| 语言 | 框架 | 命令 |
|----------|-----------|---------|
| Go | gremlins | `gremlins unleash ./path/to/package` |
| Rust | cargo-mutants | `cargo mutants -j N --timeout T` |
| Python | mutmut | `mutmut run --paths-to-mutate src/` |
| C/C++ | Mull | `mull-runner -test-framework=GoogleTest binary` |

### 并行处理

对于大型代码库始终使用并行执行：
- `cargo mutants -j 8` (Rust, 8 个并行工作线程)
- `gremlins unleash --timeout-coefficient 3` (Go, 增加超时)
- `mutmut run --runner "pytest -x -q"` (Python, 快速失败)

### 记录基线结果

捕获每个实现的以下指标：

| 指标 | 描述 |
|--------|-------------|
| 总变异体 | 生成的变异体数量 |
| 被杀灭 | 测试捕获的变异体 |
| 存活 | 未被捕获的变异体（这些是目标） |
| 未覆盖 | 测试完全无法触及的代码路径 |
| 超时 | 模糊的 — 在比较之前解决 |
| 效率 % | 被杀灭 / (被杀灭 + 存活) |
| 覆盖 % | (总 - 未覆盖) / 总 |

保存完整的变异日志以供阶段 4 分析。

## 阶段 4：逃逸分析（基于图的筛选）

使用 Trailmark 调用图进行可达性和爆炸半径分析，对每个逃逸的变异体（存活 + 未覆盖）进行分类。

**此阶段必须使用 genotoxic 技能的筛选方法。**
调用图将变异结果从存活变异体的扁平列表转换为可操作的、优先级的向量目标集。

### 步骤 1：构建调用图

在筛选变异之前，为每个实现构建 Trailmark 代码图：

```bash
# Go
uv run trailmark analyze --language go --summary {targetDir}

# Rust
uv run trailmark analyze --language rust --summary {targetDir}
```

图提供：
- **调用链** — 从公共 API 入口到变异函数的跟踪，以确定可达性
- **圈复杂度** — 优先级高 CC 函数
- **爆炸半径** — 调用者多的函数，如果它们的变异存活，影响更广

### 步骤 2：过滤到相关代码

变异框架测试整个包。将结果过滤到测试向量应该执行的文件/函数：

```bash
# Go (gremlins)
grep -E "(LIVED|NOT COVERED)" baseline.log \
  | grep -E " at (relevant|files)" \
  | sort

# Rust (cargo-mutants)
cat mutants.out/missed.txt | grep "src/relevant"
```

### 步骤 3：基于图的分类

对于每个逃逸的变异体，将其映射到调用图中的包含函数，并应用 genotoxic 筛选标准：

| 图信号 | 分类 | 操作 |
|--------------|----------------|--------|
| 图中没有调用者 | **假阳性** | 死代码，跳过 |
| 仅测试调用者 | **假阳性** | 测试基础设施 |
| 日志/显示/格式化 | **假阳性** | 修饰性 |
| 跨包调用但未覆盖 | **跨包空白** | 见下文 |
| 从公共 API 可达，低 CC | **缺失向量** | 设计定向向量 |
| 从公共 API 可达，高 CC (>10) | **模糊测试目标** | 向量 + 模糊测试框架 |
| 验证/错误处理路径 | **负向量** | 设计触发该路径的无效输入 |
| 优化路径（GLV、SIMD、批处理） | **边界情况向量** | 触发优化阈值的输入 |
| `\|`→`^` 左移后（例如 `(t<<1) \| carry`) | **等效变异体** | 跳过 — 位 0 总是 0，OR=XOR |
| ct_eq `&`→`\|` 在蒙哥马利肢体上 | **API 不可达** | 需要库内部测试，不是向量 |
| 等效变异（行为未改变） | **假阳性** | 跳过 |

### 步骤 4：识别跨包测试空白

**关键陷阱：** 变异框架通常只运行与变异相同的包中的测试。对于 Go (gremlins) 和 Rust (cargo-mutants)，这意味着：

- `hash_to_curve/g2.go` 中的变异只运行 `hash_to_curve` 包中的测试，*不*运行导入它的 `bls12381` 包中的测试
- 完全由跨包测试执行的函数将显示为**未覆盖** — 这些是**假阳性**
- 确认：检查是否从*不同*包中的测试（这些测试不会运行）调用被变异的函数

要解决跨包空白：
1. 在子包中添加一个薄测试，通过相同的代码路径调用
2. 或者使用 gremlins 运行 `--test-pkg ./...`（如果支持）
3. 或者将框架限制记录在报告中

### 步骤 5：按安全影响优先级排序

使用调用图按影响对存活变异体进行排序：

| 优先级 | 标准 | 示例 |
|----------|----------|---------|
| **P0 — 危急** | 变异体削弱验证/相等性/身份验证 | `ct_eq`: `&` → `\|` 使相等变得宽松 |
| **P1 — 高** | 变异体在反序列化标志解析中 | `from_compressed`: `&` → `\|` 接受无效标志 |
| **P2 — 中** | 变异体在字段算术内部 | `Fp::square`: `\|` → `^` 损坏计算 |
| **P3 — 低** | 变异体在优化路径中 | `phi` 内同态：仅影响性能路径 |
| **跳过** | 格式化、显示、等效变异 | `Debug::fmt` 返回值替换 |

### 步骤 6：按向量策略分组

按逃逸变异体代表的代码路径和所需的测试向量类型分组：

```
反序列化标志验证 (P1):
  - g1.rs:339,363-365,384 — from_compressed_unchecked flags
  → 需要：有效点-错误标志向量

字段算术 (P2):
  - fp.rs:371-376,406,635-643 — subtract_p, neg, square
  → 需要：字段算术 KATs，使用边缘值

优化阈值 (P3):
  - g1.go:68, g2.go:75 — GLV 与窗口乘法
  → 需要：使用大标量的标量乘法

跨包（框架限制）:
  - hash_to_curve/g2.go:242-278 — isogeny, sgn0
  → 记录为假阳性或添加子包测试
```

每个组都成为阶段 5 中新测试向量的目标。

## 阶段 5：向量生成

对于每个逃逸的代码路径组，设计测试向量以强制执行该路径。

### 向量设计模式

| 代码路径类型 | 向量策略 |
|----------------|----------------|
| 点反序列化 | 错误点：长度错误、无效字段元素、离曲线、错误的子群、单位点 |
| 签名验证 | 有效签名 + 签名、公钥、消息的所有单比特损坏 |
| 哈希到曲线 | 已知答案测试（KATs）和边缘情况输入：空、单字节、最大长度 |
| 聚合操作 | 1 签名者、多个签名者、重复签名者、有效/无效混合 |
| 错误处理 | 每个错误路径都应该有一个触发它的向量 |
| 算术边缘情况 | 零、一、字段模 - 1、无穷远点 |
| 序列化标志 | 每个有效标志组合 + 每个无效标志组合 |
| 往返完整性 | 对于每个有效的反序列化向量，断言 `serialize(deserialize(b)) == b` |
| 进位/减少故障 | 在减少的肢体宽度重新实现，注入故障，提取区分输入 |

### 单故障负向量

每个负向量应该有**恰好一个缺陷**，其他一切都有效 — 这可以隔离正在测试的验证检查。参见
[references/vector-patterns.md](references/vector-patterns.md)
了解每个标志的构造示例。

### 故障模拟（肢体宽度重新实现）

当变异测试仅适用于局部操作交换时，更深层次的结构性错误（进位传播、减少溢出）未被测试。为了弥补这个差距，在减少的肢体宽度（8、16、25、32 位）重新实现目标算法，并故意注入故障，然后生成捕获这些故障的向量。

参见 [references/fault-simulation.md](references/fault-simulation.md)
了解完整方法：肢体宽度选择、故障注入目录、向量提取和验证工作流。

### 跨实现验证

每个新测试向量**必须**在添加到套件之前与至少两个独立的实现进行验证：

1. 使用实现 A 生成向量
2. 使用实现 B 验证（不同代码库，理想情况下是不同语言）
3. 如果 B 不一致，请调查 — 一个实现有错误

### 向量格式

使用 Wycheproof JSON 格式 (`algorithm`, `testGroups[].tests[]`
带有 `tcId`, `comment`, `result`, `flags`)。参见
[references/vector-patterns.md](references/vector-patterns.md)
了解完整架构。

**Wycheproof 贡献：** 使用 Wycheproof 的 `vectorgen` 工具而不是直接格式化向量文件。提供生成的更改作为信封。`vectorgen` 工具可以添加、更新或替换向量，同时处理 `tcId` 分配、测试计数、规范格式化和架构验证。基于 Go 的生成器可以避免 `vectorgen` 命令行工具，而是调用 `github.com/c2sp/wycheproof/vectorgen` 程序化 API。

参见 [references/lessons-learned.md](references/lessons-learned.md)
§14 和上游
[vectorgen 指南](https://github.com/C2SP/wycheproof/blob/main/doc/vectorgen.md)
了解当前工作流程和命令。

## 阶段 6：验证

包含新测试向量后重新运行变异测试。

**提示：** 在向量开发期间使用按文件变异测试进行快速迭代
（参见 [references/lessons-learned.md](references/lessons-learned.md) §12）。
仅对最终比较运行完整包测试。

### 比较 前后

| 指标 | 基线 | 使用新向量 | 差值 |
|--------|----------|------------------|-------|
| 被杀灭 | X | Y | Y - X |
| 存活 | A | B | A - B (应该减少) |
| 未覆盖 | C | D | C - D (应该减少) |
| 效率 % | E% | F% | F - E |

### 成功标准

向量既有**回顾性**价值（杀死现有代码中的突变体），也有**前瞻性**价值（捕捉未来实现中的错误）。生成这两种类型的向量——边界条件向量可能不会提高成熟库的杀死率，但会捕捉新实现中的错误。参见
[references/lessons-learned.md](references/lessons-learned.md) §13。

**回顾性（可测量）：**先前幸存/未覆盖的突变体被杀死，没有回归。

**如果杀死率没有变化：**实现自身的测试很可能已经覆盖了那些路径。这些向量仍然具有跨实现验证的价值。记录哪种情况适用。

## 质量检查清单

交付前：

- [ ] 至少有一个纯实现突变测试（不仅仅是 FFI 包装器）
- [ ] 使用现有向量完成基线运行
- [ ] 为每个实现构建 Trailmark 调用图
- [ ] 使用图指导分类对所有逃逸的突变体进行分诊
- [ ] 识别并记录跨包的误报
- [ ] 安全关键突变（ct_eq、验证、认证）优先级为 P0/P1
- [ ] 故障模拟和突变派生的向量与 2 个以上实现交叉验证
- [ ] 使用新向量完成后运行
- [ ] 计算并解释前后差异
- [ ] 将报告写入 `VECTOR_FORGE_REPORT.md`
- [ ] 将新测试向量以标准格式（Wycheproof JSON）保存
