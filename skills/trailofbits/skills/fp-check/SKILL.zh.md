# 假阳性检查

## 使用场景

- "这个bug是真的吗？" 或 "这是否为真正的阳性？"
- "这是一个假阳性吗？" 或 "验证这个发现"
- "检查这个漏洞是否可利用"
- 任何要求验证或确认特定疑似bug的请求

## 不适用场景

- 寻找或追踪bug（"寻找bug"、"安全分析"、"审计代码"）
- 为风格、性能或可维护性进行的常规代码审查
- 功能开发、重构或非安全任务
- 当用户明确要求快速扫描而不进行验证时

## 拒绝的理由

如果你发现自己有这些想法，请停止。

| 拒绝的理由 | 为什么这是错误的 | 必须采取的行动 |
|---|---|---|
| "快速分析剩余的bug" | 每个bug都需要完整验证 | 返回任务列表，通过所有阶段验证下一个bug |
| "这个模式看起来很危险，所以它是一个漏洞" | 模式识别不是分析 | 在得出任何结论之前，完成数据流跟踪 |
| "为了效率而跳过完整验证" | 不允许部分分析 | 按照所选验证路径执行所有步骤 |
| "代码看起来不安全，不跟踪数据流就报告" | 看起来不安全的代码可能有上游验证 | 从源到汇跟踪完整路径 |
| "其他地方相似的代码是易受攻击的" | 每个上下文都有不同的验证、调用者和保护措施 | 独立地验证这个特定实例 |
| "这显然是关键的" | LLMs倾向于看到bug并高估严重性 | 完成魔鬼代言人审查；用证据证明 |

## 第0步：理解声明和上下文

在进行任何分析之前，用自己的话重述bug。如果你无法清晰地做到这一点，请向用户请求澄清。一半的假阳性都在这一步崩溃——当精确重述声明时，声明没有连贯的意义。

记录：

- **确切的漏洞声明是什么？**（例如，"在`parse_header()`中，当`content_length`超过4096时发生堆缓冲区溢出"）
- **所谓的根本原因是什么？**（例如，"在行142处的`memcpy`之前缺少边界检查"）
- **所谓的触发因素是什么？**（例如，"攻击者发送具有过大Content-Length头的HTTP请求"）
- **声称的影响是什么？**（例如，"通过受控的堆损坏进行远程代码执行"）
- **威胁模型是什么？**这段代码在什么权限级别运行？它是否在沙盒中？攻击者在触发此bug之前已经可以做什么？（例如，"未经身份验证的远程攻击者与特权本地用户"；"在Chrome渲染器沙盒内运行"与"作为root运行且没有沙盒"）
- **bug类别是什么？**对bug进行分类，并参考[bug-class-verification.md]({baseDir}/references/bug-class-verification.md)以获取补充通用阶段的类别特定验证要求。
- **执行上下文**：在正常执行期间何时以及如何到达此代码路径？
- **调用者分析**：哪些函数调用此代码以及它们施加的输入约束？
- **架构上下文**：这是否是具有多层保护的大型安全系统的一部分？
- **历史上下文**：此代码区域的任何最近更改、已知问题或以前的代码安全审查？

## 路径：标准验证与深度验证

完成第0步后，选择验证路径。

### 标准验证

当所有这些都成立时使用：

- 清晰、具体的漏洞声明（不是模糊或含糊的）
- 单个组件——bug路径中没有跨组件交互
- 被理解的bug类别（缓冲区溢出、SQL注入、XSS、整数溢出等）
- 触发中没有并发或异步
- 从源到汇的直观数据流

遵循[standard-verification.md]({baseDir}/references/standard-verification.md)。没有任务跟踪——按顺序线性地通过检查清单，直接记录发现结果。

### 深度验证

当任何这些成立时使用：

- 含糊的声明，可能有多种解释
- 跨组件的bug路径（数据流通过3个或更多模块或服务）
- 触发机制中的竞态条件、TOCTOU或并发
- 没有清晰规范的逻辑bug
- 标准验证结论不明确或升级
- 用户明确要求完整验证

遵循[deep-verification.md]({baseDir}/references/deep-verification.md)。将每个阶段作为具有明确依赖关系的任务进行跟踪，并使用插件的分析代理执行阶段。

### 默认

从标准开始。标准验证有两个内置升级检查点，当复杂性超过线性检查清单时，会路由到深度。

## 批量筛选

在一次性验证多个bug时：

1. 首先对所有bug运行第0步——重述每个声明通常会立即消除明显的假阳性
2. 独立路由每个bug（有些可能是标准的，有些是深度的）
3. 首先处理所有标准路由的bug，然后处理深度路由的bug
4. 验证所有bug后，检查**利用链**——单独未能通过门控审查的发现可能组合成一个可行的攻击

## 最终总结

在处理所有疑似bug后，提供：

1. **计数**：X 真阳性，Y 假阳性
2. **真阳性列表**：每个都有简短的漏洞描述
3. **假阳性列表**：每个都有拒绝的简要原因
