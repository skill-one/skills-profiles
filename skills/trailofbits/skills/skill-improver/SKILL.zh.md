# 技能改进器

通过运行 `/code-improver:improve` 来改进一个 Claude Code 技能 — 这是一个动态工作流，它会循环一个审阅者和一个修复者子代理，直到一个审阅报告零个严重/主要问题，然后清除自身的残留物。这个入口点将循环连接到 `plugin-dev:skill-reviewer` 代理，因此 **必须安装 plugin-dev 插件**（市场 `claude-plugins-official`）。循环、其账本及其守卫存在于工作流中；这个技能解析目标并中继结果。

## 启动循环

用户提供：`$ARGUMENTS`（如果为空，则从对话中获取目标技能）。

### 1. 解析技能路径

1. 如果输入以 `/SKILL.md` 结尾且文件存在，则使用其目录
2. 如果输入是一个包含 `SKILL.md` 的目录，则使用该路径
3. 否则 `Glob(pattern="**/SKILL.md")` 并按技能名称或路径子字符串过滤：
   - **多个匹配：** 询问用户选择
   - **无匹配：** 报告可用的技能
   - **单个匹配：** 继续

### 2. 解析循环脚本

循环是这个插件中的动态工作流 `workflows/improve.js`。通过路径启动它：`scriptPath` 接收解析后的绝对路径，而 Workflow 工具的 `name` 解析内置和项目工作流，因此市场安装的一个可能无法响应 `code-improver:improve`。按顺序尝试，第一个匹配的胜出 — 主目录优先于 `.`，所以安装的副本会胜过这个市场的检出：

1. `Bash: ls -d -- "${CLAUDE_PLUGIN_ROOT}/workflows/improve.js"`
2. `Bash: ls -d -- "${CODEX_PLUGIN_ROOT}/workflows/improve.js"`（如果该变量被设置）
3. `Bash: find ~/.claude ~/.codex . -maxdepth 7 -path '*/code-improver/workflows/improve.js' -print -quit 2>/dev/null`

按打印的路径使用。其插件目录 — 移除 `/workflows/improve.js` 的路径 — 是 `pluginRoot`。如果三个都为空，尝试 `{name: "code-improver:improve"}` 一次；如果也不可用，停止并说明循环无法定位。不要手动组装路径，不要临时修改循环。

### 3. 调用工作流

使用 Workflow 工具运行它，`{scriptPath: "<步骤 2 中的路径>", args: {...}}`：

```json
{
  "target": "<解析后的绝对路径>",
  "reviewer": {
    "kind": "agent",
    "name": "plugin-dev:skill-reviewer",
    "notes": "目标是 Claude Code 技能目录；将其作为技能（frontmatter、触发描述、渐进式披露、引用文件）进行审阅。"
  },
  "pluginRoot": "<步骤 2 中的插件目录>",
  "maxRounds": 5
}
```

- `maxRounds` 仅当用户请求不同的上限 (`--max-rounds N`) 时。
- `pluginRoot` 让运行找到其指标收集器；如果步骤 2 跳转到工作流名称，则省略该键 — 工作流会自行搜索。
- `scope`（相对仓库的通配符）仅当用户限制或扩展了循环可以触及的内容时；默认情况下，工作流限定于技能的插件目录。
- `decision` 仅在继续时（下方）。

工作流在后台运行，无需看管：它会审阅、修复、重新审阅，在每次修复轮后检查范围，并且只能在干净审阅时完成。它从不提交；所有更改都保留在工作树中。

**如果 Workflow 工具不可用或被拒绝，停止并说明。** 不要直接编辑中继循环 — 账本、范围守卫和升级保证都存在于工作流中，而内联模仿则没有（观察到的失败：内联回退通过削弱文档保证“修复”了问题，而循环正是为了防止这种情况）。

**如果结果是 `halted: "reviewer-unavailable"`，中继它并停止。** 这个技能指定的审阅器未安装；告诉用户从 `claude-plugins-official` 市场安装 `plugin-dev` 插件并重新运行。不要自己审阅技能。

**循环运行时不要结束你的回合。** Workflow 工具立即返回一个任务 ID；结果稍后到来。在交互式会话中，完成通知会重新调用你 — 等待它。在非交互式运行（脚本、CI、eval）中，没有后续回合：停止会中途放弃循环，所以启动后，轮询任务（带有返回的任务 ID 的 TaskOutput，或睡眠后重新检查）直到完成，然后中继结果。一个回答“循环正在运行，我稍后会报告”的会话已经丢失了运行。

## 中继结果

工作流返回一个结构化结果。诚实地报告它 — 区分很重要：

- **`converged: true`** — 最后一个动作是一个零个严重/主要问题的审阅。
  报告使用的轮次、剩余的次要问题 (`open_minor_count`) 以及工件路径 (`ledger_path`, `metrics`)。
- **`capped: true`** — 修复预算用尽，最终审阅仍然发现阻塞问题。直白地说：**capped, NOT converged**，并列出 `open_blocking`。不要将其呈现为成功。
- **`escalation`** — 循环检测到它没有收敛（反复出现的问题、计数不减少，或修复将问题重新定位）。向用户中继升级消息和问题 ID：这需要设计决策，而不是更多轮次。
- **`halted`** — 一个守卫被触发（范围违规、未注册的新文件、死或不可用的审阅器，或最终通过自己的编辑失败的检查）。中继 `violations`/`new_untracked_files` 中的路径、`finalize_regressions` 中的位置以及注释。
- **`notes`** 总是随结果一起传递 — 显示它们；它们包括响亮的警告，例如“初始化了一个 git 仓库”。

## 升级后继续

循环按设计停止。当用户决定（例如“保留黑名单并记录限制”）时，使用相同的 `target` 加上：

```json
{ "decision": "<用户的裁决，逐字>" }
```

新的运行会重新加载磁盘账本，所以每个发现、拒绝和裁决都会延续 — 轮次重新开始，重新推导不会。

要停止正在运行的循环，停止工作流任务（TaskStop）；磁盘上的账本是最后轮次的当前状态，重新运行会从中继续。

## 循环强制执行的内容（因此你不必）

- **修复验证** — 下一个审阅验证每个修复；对可执行行为的修复带有针对修复前代码的失败桩。
- **范围** — 每次修复轮后和最终通过后的机械 git-diff 检查，任何超出范围的更改都会停止；git 不跟踪的超出范围文件由内容哈希保护，因为没有 diff 会显示它们；完成也需要范围内没有未注册的新文件。
- **报告一切** — 审阅者报告所有问题及其严重性；过滤一次发生在账本裁决时，并且没有新证据时拒绝不会重新辩论。
- **最终化** — 在完成前，循环会剥离叙述评论，将版本变更缩减为恰好一个版本（在 `plugin.json` 和重复它的市场条目中），并运行文档匹配代码。这些编辑在最后一个审阅后落地，所以检查会读取它们：过激的叙述剥离或虚假的文档声明会导致 `finalize-regression` 而不是通过。

## 不应使用的情况

- **一次性审阅**：直接派遣 `plugin-dev:skill-reviewer` 代理
- **快速单个修复**：直接编辑文件
- **非技能目标**：使用 `code-improver` 技能配合适合目标的审阅器，或 `pr-improver` 用于分支
- **探索性起草**：手动迭代在形状尚不固定时提供更多控制
