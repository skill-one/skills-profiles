# 避免功能蔓延

请求设定了范围。diff 中的所有内容都应追溯到 ask 中的某一句话。否则，任何其他内容都是建议，而不是变更。

## 核心规则

构建请求中所述的内容。不是什么“会不错”，不是什么“高级工程师也会做的事”，也不是代码库“应该”有的。如果 diff 中的某一行不能由请求来证明，那么它就不属于 diff。

这适用于产品范围和代码范围。一个超出其问题陈述的 PRD 与一个带有重构一起发布的 bug fix 具有同样的疾病。

## 蔓延开始的信号

当你注意到以下任何一项时，请停止：

- 你的理由中出现了“既然在这里”或“不妨”的说法
- 为一个没人要求的情况添加了配置选项、标志或参数
- 因为旁边的代码看起来杂乱无章而重构代码
- 添加了第二个功能以使第一个功能感觉完整
- 为用户从未遇到过的边缘情况添加了错误处理
- 为变更之外的代码添加了测试、类型或文档
- 将一次性操作泛化为可重用的抽象
- 在没有声明用户需求的情况下复制竞争对手的功能
- PRD 中标题为“未来”或“值得拥有”的部分不断变长
- 变更触及了请求从未暗示的文件

其中每一项可能都是个好主意。除非用户表示同意，否则它们都不在范围内。

## 该怎么做

1. 完成请求。发布能够完全回答请求的最小变更。
2. 随着你进行，收集额外内容。不要采取行动。
3. 在最后将它们放在一个地方：
   - 在聊天或 PR 摘要中，在 `Suggestions` 标题下，每行一个
   - 在 PRD 中，在 `Out of scope` 下，每项附上一行理由
   - 在带有 `prds/` 文件的仓库中，追加到相关 PRD 的 `Out of scope` 部分
4. 让用户选择。“代理认为如此”不是批准。

建议写起来很便宜，被忽略也无所谓。未经请求的代码会耗费审查时间，增加错误，并模糊变更的目的。

## 利益相关者，包括代理

每个功能请求都有一个来源：一个产品经理、一个高管、一个用户、一个为了解决自己的问题而编码的开发者，或一个 AI 编码代理。以相同的方式对待他们。记录请求，将其与当前范围权衡，除非它解决了工作开始时的问题，否则推迟处理。

AI 代理现在是利益相关者。他们有意见，他们会推动。常见的代理驱动蔓延：

- “让我也添加你还没遇到的边缘情况的错误处理”
- “用重构会更干净”
- “你最好为这个添加测试”
- “我为这些附加场景添加了类型”

如果你是代理，注意自己不要这样做，并将其移至建议列表。如果你在和一个代理合作，在会话开始时说明范围，并将其额外内容视为任何其他利益相关者请求来处理。

在添加任何内容之前，问自己：

- 这是否解决了请求中命名的问题？
- 最小的可工作版本是什么？
- 如果我们从未构建它，会发生什么？

如果第一个答案是“否”，它就属于建议。

## 之前和之后

请求：“为任务添加 `deletedAt` 字段，并将已删除的任务从列表查询中隐藏。”

之前，蔓延的版本：

- 将 `deletedAt` 添加到模式
- 添加了 `by_user_and_deleted` 索引
- 重写了 `list` 以使用该索引
- 添加了 `softDelete`、`restore` 和 `purgeDeleted` 变更
- 添加了 30 天后清除的 cron
- 将 `list` 重命名为 `listActive` 并更新了三个调用点
- 添加了 `showDeleted` 参数“供以后的管理员视图使用”

之后，范围的版本：

- 将 `deletedAt: v.optional(v.number())` 添加到模式
- 添加了索引，并将 `list` 指向它，以便从未加载已删除的行

随变更发送的摘要：

```
完成：`deletedAt` 字段和列表查询现在会跳过已删除的任务。

建议
- 一个设置 `deletedAt` 的 softDelete 变更（目前还没有设置它）
- 一个 restore 变更
- 一个清除 30 天以上行的 cron
- 列表上的管理员标志以包含已删除的行
```

两行 diff 回答了请求。四行建议保留了每个想法。用户决定接下来会发生什么。

## PRD

PRD 通过指向其问题陈述来赢得每个部分。当一个 PRD 增长时：

- 重新阅读问题陈述。删除任何不为其服务的内容。
- 将删除的项目移至 `Out of scope`，每项附上一行理由。
- 如果删除的项目形成一个连贯的功能，那是一个第二 PRD，而不是一个更大的第一 PRD。

## 检查清单

- [ ] 每个更改的文件都是由请求暗示的
- [ ] 没有请求中未要求的新配置选项、标志或参数
- [ ] 没有重构相邻的代码
- [ ] 没有添加第二个功能以完善第一个
- [ ] 没有为变更之外的代码添加测试、类型或文档
- [ ] 额外内容列在摘要的 `Suggestions` 下或在 PRD 的 `Out of scope` 下
- [ ] 摘要在一行中说明已完成的操作，然后是建议
- [ ] 如果用户说“就做我要求的”，diff 中只包含那部分内容
