# Prisma Next — 反馈（问题报告、功能请求、团队问答）

> **编辑你的数据合约。Prisma 处理其余部分。**

这项技能是能力差距路由模式中的*终端*。当用户希望关闭差距时，其他 Prisma Next 技能的*Prisma Next 尚未实现的功能*条目会路由到这里；该技能也会在用户提出类似*"这是一个 Bug"*、*"提交问题"*、*"功能请求"*、*"我可以向团队咨询这个问题吗?"*、*"应该如何将 X 集成到 Prisma Next 中?"*等提示时直接触发。

该技能的任务是选择*正确的渠道*——GitHub 问题或 Discord——然后要么生成一个**结构化、公开安全的**问题正文（不包含秘密信息、不包含专有模式），供框架团队采取行动，要么将直接链接提供给 Prisma Discord 以进行同步问答。未经明确用户确认，绝不会提交到 GitHub。

规范渠道：

- **GitHub 问题**（Bug + 具体功能请求）：<https://github.com/prisma/prisma-next/issues/new/choose>
- **Prisma Discord**（问答、设计反馈、直接团队联系——包括扩展程序作者）：<https://pris.ly/discord>

## 使用时机

- 另一个 `prisma-next-*` 技能触发了能力差距条目，并且用户表示*"是的，提交功能请求"*。
- 用户说*"这是一个 Bug"*、*"提交这个"*、*"报告这个"*、*"针对 PN 提交问题"*、*"发送反馈"*、*"这应该是一个功能"*。
- 用户描述了意外行为——错误退出代码、与实际不符的错误消息、类型签名与运行时行为不匹配、规划器拒绝了一个看似安全的迁移——并希望将其置于框架团队的注意范围内。
- 用户询问*"我可以向 Prisma 团队咨询这个问题吗?"*、*"有哪里我可以与团队交谈吗?"*、*"做 X 的正确方式是这样做吗?"*、*"应该如何将 <我的扩展程序 / 我的应用程序> 与 PN 集成?"*，或任何其他开放式问答或设计反馈提示——包括扩展程序作者询问集成问题。

## 不应使用时机

- 用户希望在用户自己的代码中自行修复 Bug。修复方案存在于另一个技能（调试 / 合约 / 迁移 / 查询 / 运行时 / 构建）。首先链接到正确的技能；只有在用户明确希望框架以不同的方式执行时才回退到反馈。
- 用户希望升级 Prisma Next（Bug 可能已经修复）→ `prisma-next-upgrade` 技能（单独安装）；此技能将其作为预飞行检查提及。
- 用户的提问已由集群中的工作流技能覆盖（*"如何添加列?"* → `prisma-next-contract`；*"正确的查询接口是什么?"* → `prisma-next-queries"`）。路由到工作流技能，而不是团队——加载技能，回答问题，并且只有在代理无法回答时才升级到 Discord。

## 关键概念

- **三个渠道，一个决策。** GitHub 问题（Bug + 具体功能请求）、Prisma Discord（问答、设计反馈、直接团队联系），或集群中的另一个技能（当问题实际上是工作流问题，而不是需要转交给团队的问题时）。该技能的第一个动作是渠道决策；其余动作都跟随这个决策。
- **公开工件。** GitHub 问题*和*Discord 消息都是世界可读并存档的。正文/消息不得包含 `DATABASE_URL` 字符串、内部公司模式片段、示例行中的客户数据或任何其他用户不会公开分享的内容。代理在提交任何一种类型之前都会进行编辑。
- **Bug 与功能请求与问题的区别。** 一个 *Bug* 是"文档化表面行为异常"。一个 *功能请求* 是"我希望一个不存在的能力"。一个 *问题* 是"我希望与某人讨论 X，或者我不确定这到底是一个 Bug"。许多能力差距路由是功能请求；许多扩展程序作者的提示是问题。
- **框架团队需要复现（仅限问题）。** 没有复现步骤的 Bug 报告很难处理。在可能的情况下，代理会生成一个团队可以在本地重新运行的最小复现步骤——理想情况下是一个针对 [`examples/prisma-next-demo`](https://github.com/prisma/prisma-next/tree/main/examples/prisma-next-demo) 的小更改，团队已经检出该示例。Discord 问答不需要完整的复现——一个简短的代码片段加上问题通常就足够了。

## 工作流

### 1. 选择渠道

用户希望将问题转交给团队。选择哪个渠道？

**GitHub 问题** 如果满足以下任一条件：

- 用户描述了一个具体的 Bug（有关 Bug 与功能请求的划分，请参见*分类*部分）。
- 用户有一个具体的功能请求——一个命名的功能、一个特定的 API 形状、一个特定的 CLI 标志——他们希望在待办事项列表中看到。
- 另一个 `prisma-next-*` 技能将能力差距条目路由到这里以进行功能请求。

**Prisma Discord** (<https://pris.ly/discord>) 如果满足以下任一条件：

- 用户正在询问一个开放式问题——*"做 X 的正确方式是这样做吗?"*、*"你会如何处理 Y?"*、*"我看到了奇怪的行为，但我不确定这是否是一个 Bug。"*
- 用户希望在提交功能请求之前获得设计反馈——*"我们正在考虑构建一个自定义中间件来执行 X，这符合框架的方向吗?"*
- 用户是一个扩展程序作者，有一个需要与团队来回讨论的集成问题（依赖项协调、破坏性更改时间、新的扩展程序表面）。
- 用户明确要求团队——*"我可以向团队咨询这个问题吗?"*、*"有哪里我可以与 Prisma 交谈吗?"*、*"扩展程序作者如何与团队讨论事情?"*

**按顺序两者都使用** 如果满足以下任一条件：

- 用户有一个 Bug *和*一个相关功能请求——提交两个单独的 GitHub 问题，不要将它们混合在一个问题中。
- 用户希望在提交功能请求之前讨论设计——从 Discord 开始，一旦形状确定，再提交问题。

### 2. 分类（仅限问题路径）

用户正在提交一个 GitHub 问题。这是一个 Bug 还是功能请求？

**Bug** 如果满足以下任一条件：

- 一个文档化的 CLI 命令退出了错误的代码。
- 错误包的 `fix` 字段具有误导性或错误。
- 发布的 TypeScript 签名与运行时行为不匹配。
- 规划器拒绝了一个应该有效的迁移（或接受了一个不应该有效的迁移）。
- 合约发出产生的工件在运行时无法加载。
- 任何其他文档化表面做了错误的事情的情况。

**功能请求** 如果满足以下任一条件：

- 用户希望一个尚不存在的能力（大多数 *Prisma Next 尚未实现的功能*条目会落入这里）。
- 用户希望更好的错误消息、额外的 CLI 标志、新的中间件、额外的捆绑器插件等。

如果两者都有——一个 Bug *和*用户希望相关的功能——提交两个单独的问题。混合它们会使框架团队更难进行分类。

### 3. 收集最小正文（仅限问题路径）

对于**任何一种**：

- **Prisma Next 版本**：`pnpm ls @prisma-next/postgres`（或 `@prisma-next/mongo`）。如果项目使用目标包，该版本是规范的。
- **Node 版本**：`node -v`。
- **包管理器**：`pnpm` / `npm` / `yarn` / `bun` / `deno`。
- **操作系统**：`darwin` / `linux` / `win32` 和版本字符串就足够了。

对于**Bug 报告**，此外：

- **导致问题的确切命令**（例如 `prisma-next migration plan --name add-email`）。
- **完整输出**，如果涉及结构化错误包，请使用 `-v`。编辑 `DATABASE_URL` 和任何其他秘密。
- **最小的 `src/prisma/contract.prisma` / `src/prisma/contract.ts` 提取**，以重现问题。删除不相关的模型。在用户合约中保留原始模型和字段名称，当它们不会泄露任何妥协信息时——一个忠实的提取比一个重新主题化的提取更容易让框架团队（和未来阅读问题的读者）进行推理。只有在原始名称会泄露受保护域详细信息（产品名称、内部代码名称、客户标识符、受监管数据字段名称）时才将它们重命名为中性的占位符（`User`、`Post`、`Tag`）。
- **重现步骤**，作为编号列表。
- **预期行为**——一句话。
- **实际行为**——一句话加上相关输出行。
- **解决方法**，如果有——一句话。

对于**功能请求**，此外：

- **期望的 API 或行为**——一段话。尽可能提供具体的形状（CLI 标志、配置字段、中间件导出、插件 API）。
- **今天差距出现的位置**——哪个技能的 *Prisma Next 尚未实现的功能* 条目触发了请求，或者用户正在尝试完成的工作流。
- **当前的解决方法**，如果有——一句话（并且用户正在遵循的技能正文可能已经说明了这一点）。

### 4. 渲染正文

存储库提供了 GitHub 问题表单（`.github/ISSUE_TEMPLATE/bug_report.yml` 和 `feature_request.yml`）。当用户到达 <https://github.com/prisma/prisma-next/issues/new/choose> 时，他们会选择匹配的模板并填写表单字段；技能以相同的结构化形状生成正文，以便它与表单一一对应（即使表单未启用，`gh issue create --body-file` 也会生成可解析的工件）。

Bug 报告正文形状（字段名称与 `.github/ISSUE_TEMPLATE/bug_report.yml` 匹配）：

~~~markdown
## 包和版本

<例如 @prisma-next/postgres@0.5.2>

## 发生了什么？

<一句话总结加上相关输出行，编辑秘密>

## 你期望发生什么？

<一句话>

## 最小化重现

1. <步骤一>
2. <步骤二>
3. <步骤三>

```ts
// schema.psl 提取 + 失败的查询 / 命令
```

## 环境

- Node: <版本>
- OS: <darwin/linux/win32> <版本>
- 包管理器: <pnpm/npm/yarn/bun/deno> <版本>
- 数据库: <Postgres / Mongo> <版本>

## 额外上下文

<可选——链接到源技能的能力差距条目、相关问题编号、涉及的合作伙伴扩展程序>
~~~

功能请求正文形状（字段名称与 `.github/ISSUE_TEMPLATE/feature_request.yml` 匹配）：

~~~markdown
## 你试图解决什么问题？

<段落——这个用例或痛点这个问题将解决>

## 提议的解决方案

```ts
// 想象的 API 使用 / 行为
```

## 考虑过的替代方案

<一句话或两句——你尝试了当前 API 的内容以及为什么它不起作用>

## 范围和影响

<哪些包会被影响；特定目标的影响>
~~~

区域与技能集群对应：`cli`、`contract`、`migration`、`query`、`runtime`、`build`、`error`、`docs`。

### 5. 标题（仅限问题路径）

- **Bug**：`bug(<区域>): <一句话总结>`——例如 `bug(cli): migration plan exits 0 when there is no diff`。
- **功能请求**：`feat(<区域>): <一句话总结>`——例如 `feat(build): first-party Next.js plugin for contract emit`。

区域与技能集群对应：`cli`、`contract`、`migration`、`query`、`runtime`、`build`、`error`、`docs`。

### 6. 用于确认的界面（仅限问题路径）

**永远不要自动提交。** 代理将渲染的标题和正文展示给用户，并询问："这个看起来可以提交到 GitHub。您要提交吗？"。只有在用户明确批准后才会提交。

### 7. 提交（仅限问题路径）

首选。两步：

1. **将渲染的正文写入临时文件。** 使用您的文件写入工具（您在磁盘上创建任何其他文件时使用的工具）将正文写入例如 `wip/pn-issue-body.md` 或 `/tmp/pn-issue-body.md`。正文内容只是本工作流第 4 步生成的 Markdown——没有周围的 shell 引用，没有 heredoc。
2. **从 `gh` 引用该文件。** 运行：

   ~~~bash
   gh issue create \
     --repo prisma/prisma-next \
     --title "<标题>" \
     --body-file <步骤 1 的路径>
   ~~~

**反模式（不要这样做）：** 通过 `--body "$(cat <<EOF …)"` 或 `--body-file <(cat <<EOF …)` 插入正文。这些一行代码可靠地会在问题正文泄露 `cat <<'EOF'` / `EOF` 标记，当代理使用正文插值重复模板时。始终先将正文写入一个真实文件，然后再传递路径。

如果 `gh` 未安装：在浏览器中打开预填充的新问题 URL：

~~~text
https://github.com/prisma/prisma-next/issues/new/choose
~~~

以及指示用户粘贴渲染的正文。代理可以通过 `pbcopy`（macOS）、`xclip`（Linux），或简单地打印在聊天中供用户复制，将正文复制到剪贴板。

### 8. 路由到 Discord（问答 / 设计反馈 / 直接团队联系路径）

当步骤 1 选择 Discord 渠道时（步骤 2–7 不适用）：

1. **展示链接。** 给用户规范的邀请：<https://pris.ly/discord>。建议适合问题的频道：
   - 一般使用 / 问答 → 公开的 `#help` 或 `#prisma-next` 频道（频道名称会演变；邀请页面列出了当前频道）。
   - 扩展程序作者 / 合作伙伴集成 / 破坏性更改协调问题 → 公开的扩展程序作者频道，或者用户可以在服务器中直接@维护者。
2. **帮助起草开场消息。** Prisma 的 Discord 是可搜索的；一个结构良好的开场消息会得到更快、更有用的答案。代理起草一条简短的消息，包含：
   - 用户试图做什么的一个句子总结。
   - Prisma Next 版本（`pnpm ls @prisma-next/postgres` 或等效）。
   - 在相关的情况下，一个简短的代码片段（PSL 提取、查询、配置文件）——以与 GitHub 问题正文相同的方式编辑（没有 `DATABASE_URL`，没有客户模式名称）。
   - 用户想要回答的特定问题。
3. **不要自动发布。** 代理将起草的消息展示给用户——"这是一个您可以粘贴到 Discord 的开场消息；您想调整后再发送吗？"——并让用户决定是否要原样粘贴、编辑或选择不同的措辞。
4. **诚实地设定预期。** Discord 是同步的，尽力而为。Bug 和具体功能请求应始终提交到 GitHub（使用问题路径）；Discord 是用于得到*"是的，这是一个 Bug，请提交"*或*"是的，这应该是一个功能，请提交"*的对话。

### 9. 跟进

- **问题路径**：在用户的项目笔记中记录问题 URL（或如果项目有 `wip/`，则在项目中记录），以便以后的升级或相关工作可以引用它。如果 Bug 是 Prisma Next 旧版本的症状，建议用户运行 `prisma-next-upgrade`（单独安装的升级技能）——许多 Bug 都在新版本中修复了。
- **Discord 路径**：一旦 Discord 上的对话确定是一个具体的 Bug 或一个具体的功能请求，返回到此技能的第一步并提交问题（Discord 帖子成为问题正文中的*注释* / *差距出现的位置*参考）。

## 常见陷阱

1. **未经确认自动提交。** 首先展示正文。用户拥有公开面向的工件，而不是代理。
2. **将 `DATABASE_URL` 或其他秘密粘贴到正文。** 严厉编辑。用 `postgresql://USER:PASS@HOST/DB` 占位符替换。
3. **粘贴客户的机密域模式。** 当原始模型和字段名称会泄露机密信息（产品代码名称、客户标识符、受监管数据字段）时，在正文进入公共问题之前将其重命名为中性的占位符。否则，保留原始名称——一个忠实的提取比一个重新主题化的提取更容易让框架团队进行推理。过度重命名本身也是一种可读性成本。
4. **将文档问题作为 Bug 提交。** 文档问题应属于另一个技能或 GitHub 讨论中（如果存储库启用）。Bug 是关于表面行为异常。
5. **将 Bug 和功能混淆在一个问题中。** 提交两个。混合问题难以分类且难以关闭。
6. **没有版本就提交。** "我正在使用 Prisma Next，它坏了"而没有版本会使分类绝望。版本是最便宜的信息上下文；始终包含它。

## Prisma Next 尚未实现的功能

- **产品内反馈渠道。** 没有 `prisma-next feedback` 命令。GitHub 问题页面是官方渠道。如果您想要一个 CLI 端的反馈命令，请通过此功能请求提交。

## 检查清单

- [ ] 已分类为 Bug 或功能请求（一个问题中不能同时包含两者）。
- [ ] 存在环境块：PN 版本、Node、包管理器、操作系统。
- [ ] 可重复性最小，公开安全，无秘密信息。
- [ ] 模式片段在安全的情况下使用原始名称；仅在原始名称会泄露敏感域详细信息时重命名为中性占位符。
- [ ] 标题采用常规提交格式 (`bug(区域): …` / `feat(区域): …`)。
- [ ] 提交前向用户显示正文以确认。
- [ ] 通过 `gh issue create`（首选）或通过预填新问题 URL 提交。
- [ ] 捕获问题 URL 以供将来参考。
- [ ] 如果 Bug 可能已在较新版本中修复，建议 `prisma-next-upgrade`。
