# 代码质量指南

## 核心原则

生产数据库。正确性至上。崩溃 > 损坏。

## 正确性规则

1. **禁止使用变通方法或临时捷径。** 处理所有错误，检查不变量。
2. **频繁使用断言。** 绝不让静默失败或吞掉边界情况发生。
3. **在无效状态下崩溃**，如果存在数据完整性风险。不要在未定义状态下继续执行。
4. **考虑边界情况。** 在足够长的时间线上，所有可能的 bug 都会发生。

## Rust 模式

- 使非法状态不可表示
- 使用穷举模式匹配
- 优先使用枚举而非字符串/哨兵值
- 最小化堆内存分配
- 编写对 CPU 友好的代码（微秒 = 很长时间）

## 如果语句

错误示例：
```rust
if condition {
    // 正常路径
} else {
    // “不应该发生” - 被静默忽略
}
```

正确示例：
```rust
// 如果只有一个分支应该被触发：
assert!(condition, "不变量被破坏：...");
// 或者
return Err(LimboError::InternalError("unexpected state".into()));
// 或者
unreachable!("impossible state: ...");
```

仅当两个分支都是预期路径时才使用如果语句。

## 注释

- 不要添加代码注释，除非是 Rust `SAFETY` 注释。

## 避免过度工程

- 仅进行直接请求或明确必要的更改
- 不要添加超出要求的特性
- 不要为未更改的代码添加文档字符串/注释
- 不要为不可能发生的场景添加错误处理
- 不要为一次性操作创建抽象
- 三行相似代码 > 过早抽象

## 索引变更

当代码涉及索引插入、删除或冲突解决时，务必对照 SQLite 仔细检查顺序。错误的顺序会导致索引不一致，且容易被忽视。

## 确保理解 IO 模型

- [异步 IO 模型](../async-io-model/SKILL.md)

## 清理

- 完全删除未使用的代码
- 不添加向后兼容的变通方法（重命名的 `_vars`、重新导出、`// 已移除` 注释）

## 单次使用辅助函数

如果一个辅助函数在单一使用场景之外没有意义，请将其移动到使用它的函数内部：

```rust
fn do_something() {
    
    something_specific();

    fn something_specific() {
    }
}
```
