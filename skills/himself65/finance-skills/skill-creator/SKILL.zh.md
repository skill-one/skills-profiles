# 技能创建器

创建、评估和迭代高质量的代理技能。此技能涵盖整个生命周期：规划技能应执行的操作、编写 SKILL.md 和参考文件、根据评分标准进行质量评分，并迭代直到技能符合生产标准。

**理念：** 优秀的技能要精确，不必冗长。其描述将正确的请求路由到它。其主体为模型提供它无法从任何其他地方获得的上下文——环境、工具合约、默认值、领域判断以及每个约束背后的原因——并省略能够独立完成这些工作的强大模型所做的事情。当前的 Claude 模型严格且字面地遵循指令，因此每一行都会被执行：过度编写的或喊叫的技能会产生僵化、过度谨慎的输出，而清晰的目标和质量标准则让模型自行规划工作。`references/writing-guide.md` 详细介绍了这一点。

**运行时适配：** 与外部工具交互的技能应在运行时检测已安装、已认证和可访问的内容，并进行调整，而不是假设单一方法。在存在真实替代方案的地方提供回退路径。参见 `references/dynamic-calling.md` 获取模式目录。

## 第 1 步：了解用户需求

将请求分类为以下模式之一：

| 用户意图 | 模式 | 跳转到 |
|---|---|---|
| 创建一个全新的技能 | **创建** | 第 2 步 |
| 改进/修复现有技能 | **改进** | 第 6 步 |
| 评估/评分技能的质量 | **评估** | 第 7 步 |

如果模糊不清，请询问：“您是想创建新技能、改进现有技能还是评估技能？”

### 收集需求（创建模式）

在编写任何内容之前，回答以下问题（如果不清楚，请询问用户）：

| 问题 | 重要性 |
|---|---|
| 技能自动化的任务是什么？ | 定义核心工作流 |
| 目标用户是谁？ | 确定复杂性和术语级别 |
| 它使用哪些工具/API/CLI？ | 确定依赖项和平台限制 |
| 用户提供什么作为输入？ | 定义参数和默认值 |
| 输出应是什么样子的？ | 定义输出合约 |
| 它是否需要 API 密钥或凭证？ | 确定 `required_environment_variables` |
| 它应该在 Claude.ai 上运行还是仅在 CLI 上运行？ | 确定平台字段和动态命令 |

## 第 2 步：规划技能架构

在编写 SKILL.md 之前，规划结构。阅读 `references/architecture-patterns.md` 获取每种模式的详细指导。

### 选择结构模式

| 模式 | 使用场景 | 结构 | 示例 |
|---|---|---|---|
| **线性** | 单个工作流，无分支 | 设置 → 获取 → 分析 → 响应 | earnings-preview |
| **路由器** | 多个子任务在一个总标题下 | 设置 + 路由表 + 子技能 | stock-correlation (4 个子技能), etf-premium |
| **方法论** | 带有真实门禁的正式领域框架 | 顺序检查，每个检查都能停止分析 | sepa-strategy |
| **小部件** | 生成交互式 UI 输出 | 提取 → 计算 → 渲染 → 解释 | options-payoff |
| **API 封装器** | 封装具有许多端点的外部 API | 认证 + 端点映射 + 重大的参考 | fintel-data |

### 规划大纲

每个技能都有三个部分：

1. **设置/检测** — 检测可用工具、认证状态和运行时环境，并决定使用哪种方法。没有外部依赖项的技能可以跳过此步骤。
2. **工作** — 编号的步骤，顺序确实重要（获取在计算之前，可以结束分析的门禁），以及模型必须执行的判断，以目标、标准和领域启发式方法的形式陈述，而不是脚本。
3. **响应用户** — 输出合约：答案应如何开头，答案必须包含什么，哪些注意事项适用，以及任何评分或等级量表。

如果一个技能需要九个步骤以上，请将其拆分或使用路由器模式。

### 规划检测流程

与外部工具交互的技能应从运行时检测流程开始。阅读 `references/dynamic-calling.md` 获取所有模式。检测流程回答：

| 问题 | 检测方法 | 决策 |
|---|---|---|
| CLI 工具是否已安装？ | `command -v tool` | CLI 路径与 Python 回退 |
| 用户是否已认证？ | `tool auth status` / `echo $API_KEY` | 跳过认证设置或引导认证 |
| 哪个运行时有库？ | 终端中的 `import lib` 与 `execute_code` | 路由到正确的运行时 |
| 是否有更丰富的工具可用？ | `gh --version` 与 `git --version` | 丰富路径与最小路径 |
| 是否可以访问实时数据？ | `curl -s endpoint` | 实时数据与缓存/默认值 |

检测输出为技能的其余部分提供**决策树**——检查而不是假设。

### 规划参考文件

决定什么放入 SKILL.md 与 references/：

| SKILL.md（约 250 行） | references/ |
|---|---|
| 工作流和决策点 | 详细的 API 文档 |
| 路由/决策表 | 代码模板（>20 行） |
| 参数默认值表 | 公式和边缘情况 |
| 输出合约 | 故障排除数据库 |
| 快速示例（1-3 个） | 全面示例（4 个以上）和日期数据集 |

## 第 3 步：编写 SKILL.md

阅读 `references/writing-guide.md` 获取编写每个部分的详细说明。阅读 `references/frontmatter-guide.md` 获取完整的 YAML 字段参考。

### 关键规则

1. **首先编写 Frontmatter**：`name`（小写连字符，最多 64 个字符）和 `description`（最多 1024 个字符，无尖括号）是必需的。描述是路由文本，随每个请求一起传递：说明技能的作用，命名它服务的意图类别和用户将使用的独特词汇（方法、工具、数据类型、实体），并指向兄弟技能以处理相邻请求。命名意图类别，而不是列出近义短语。

2. **外部依赖项的检测流程**：使用 `!`command`` 探针和回退哨兵检测工具、认证状态和运行时，然后路由到方法。在存在真实替代方案的地方提供第二个路径（CLI 与 Python 库与内置工具）。参见 `references/dynamic-calling.md`。

3. **匹配具体性与脆弱性**：为脆弱操作提供确切命令、标志和代码——安装、认证、CLI 语法、API 合约、必须正确的计算。对于判断工作——分析、解释、写作——陈述目标、标准和领域启发式方法，并让模型规划。在每次失败检查确实结束分析的地方放置通过/失败门禁。

4. **默认值表**：为用户可能遗漏的每个参数提供明确的默认值，以便技能不会因等待输入而停滞。

5. **最终步骤中的输出合约**：答案应如何开头，答案必须包含什么，哪些注意事项适用，以及任何评分或等级量表。仅在格式本身重要的情况下（评分卡、小部件、清单）固定按部分划分的模板。定性描述长度，而不是用单词或句子计数，并将示例标记为说明性的，而不是用虚构的公司数据填充。

6. **平实语气**：一次陈述每个约束及其原因。省略大写的 MUST/NEVER/CRITICAL、重复的警告以及当前模型默认遵循的指令（“要彻底”、“逐步思考”、“检查答案”）——它们会导致过度触发和过度检查，而不是更好的工作。保留真实的政策约束（只读、不执行交易、隐私）在平实的文字中。

7. **保持易变事实的真实性**：尽可能获取实时数据，对将过期的任何内容进行日期标记，并将日期数据集保存在 `references/` 中。在发货前，对照当前库验证 API 名称和响应形状。

参见 `references/skill-examples.md` 获取每个模式的注释示例。

## 第 4 步：编写参考文件

阅读 `references/writing-guide.md` 获取完整的参考文件编写指南。

### 关键规则

1. **命名**：`lowercase-hyphenated.md`，每个概念集群一个文件
2. **大小**：快速查找 50-150 行，深度指南 150-400 行，目录 400-900 行
3. **结构**：H1 标题，H2 部分，代码块，表格，边缘情况部分在末尾
4. **链接**：在 SKILL.md 步骤中使用反引号路径，并在末尾的 `## Reference Files` 部分使用

## 第 5 步：交付前的质量检查

通过 `references/quality-rubric.md` 中的质量评分标准运行技能。评分每个维度。

### 快速检查清单

- [ ] Frontmatter 包含 `name` 和 `description`；描述不超过 1024 个字符且无尖括号
- [ ] 描述说明技能的作用、它服务的意图类别及其独特词汇——不是近义短语列表
- [ ] 描述指向相邻请求存在的兄弟技能
- [ ] SKILL.md 不到 300 行（理想情况下不到 250 行）
- [ ] 每个参数都有明确的默认值
- [ ] 编号的步骤中顺序很重要；判断工作以目标、标准和启发式方法的形式陈述
- [ ] 门禁仅在失败检查确实结束分析时停止
- [ ] 最终步骤陈述输出合约：答案应如何开头，必须包含的内容，注意事项，评分或等级量表
- [ ] 无数字长度限制；示例标记为说明性的
- [ ] 约束一次以平实的文字陈述，并附有原因——无大写的 MUST/NEVER，无“逐步思考”或“检查”的样板
- [ ] 复杂内容在参考文件中，而不是内联
- [ ] 参考文件指针使用反引号路径
- [ ] 外部依赖项在运行时通过 `!`command`` 检查和回退检测 (`|| echo "..."`)
- [ ] 将不同的运行时视为不同的环境（终端与 execute_code）
- [ ] 在适当的地方包含法律/道德免责声明
- [ ] 无硬编码的股票列表、工具路径或将过期的静态数据
- [ ] 技能中的 API 名称、字段和代码已与当前库核对

如果任何项目失败，请在交付给用户之前修复它。

## 第 6 步：改进现有技能

当用户要求改进技能时：

### 6a：阅读当前技能

阅读 SKILL.md 和所有参考文件（在 Hermes 上，`skill_view(name)` 加载它们）。

### 6b：根据评分标准评分

使用 `references/quality-rubric.md` 中的质量评分标准。向用户展示评分明细（说明性）：

| 维度 | 评分 | 问题 |
|---|---|---|
| 触发质量 | 6/10 | 二十个近义短语；遗漏了 ETF 用例 |
| 默认值覆盖 | 3/10 | 无默认值表 |
| 指令设计 | 5/10 | 判断工作的脚本步骤；大写警告 |
| 输出合约 | 4/10 | 僵化的 9 部分模板，带有虚构的示例数字 |
| 参考文件使用 | 7/10 | 良好的拆分，但缺少故障排除 |

### 6c：提出具体改进建议

按影响程度列出具体更改：

1. [最高影响] 添加覆盖每个参数的默认值表
2. [高影响] 围绕意图类别和独特词汇重写描述
3. [中等影响] 将固定报告模板替换为输出合约
4. ...

### 6d：应用更改

用户批准后，编辑技能文件（在 Hermes 上，使用 `skill_manage(action='patch', ...)` 进行有针对性的更改或 `skill_manage(action='edit', ...)` 进行完全重写）。

## 第 7 步：评估技能

当用户要求评估或评分技能时：

### 7a：加载和分析

阅读完整的 SKILL.md 和所有参考文件。计算行数、步骤、默认值和参考文件数量，并注意描述的长度和它涵盖的意图类别。

### 7b：根据评分标准评分

使用 `references/quality-rubric.md` 中的全面评分标准。在 1-10 的量表上为 10 个维度评分。

### 7c：展示评分卡

```
## 技能质量评分卡：[skill-name]

| # | 维度 | 评分 | 备注 |
|---|---|---|---|
| 1 | 触发质量 | 8/10 | 涵盖所有四个意图类别；一个兄弟边界缺失 |
| 2 | 默认值覆盖 | 9/10 | 所有 11 个参数都有默认值 |
| 3 | 指令设计 | 8/10 | 有序设置和计算；分析陈述为标准 |
| 4 | 参考文件策略 | 7/10 | 2 个文件，可以使用故障排除 |
| 5 | 动态内容 | 10/10 | 检测 + 实时数据注入 |
| 6 | 输出合约 | 9/10 | 以结论开头；必须包含的注意事项；量表定义 |
| 7 | 错误处理 | 6/10 | 缺少数据处理的说明不明确 |
| 8 | 代码/公式质量 | 8/10 | 可工作的 JS，可复制粘贴 |
| 9 | 简洁性与语气 | 7/10 | 196 行；两个大写警告需要重述 |
| 10 | 领域准确性 | 9/10 | BS 公式正确，边缘情况覆盖 |

**总体：81/100** —— 生产质量

### 前三改进建议
1. ...
2. ...
3. ...
```

### 参考技能

此存储库中展示每种模式良好的技能：

| 技能 | 它展示了什么 |
|---|---|
| sepa-strategy | 方法论模式：真实门禁，参考文件中的领域标准，一个评分量表 |
| options-payoff | 小部件模式：每个字段都有默认值，实时数据注入，精确的渲染规范 |
| stock-correlation | 路由器模式：意图路由表，自包含的子技能，代码中计算的指标 |
| earnings-preview | 输出合约：内容清单，一个判断部分，以头条新闻为首的指导 |

## 第 8 步：响应用户

### 创建模式

交付：
1. 完整的 SKILL.md 内容
2. 所有参考文件
3. 技能目录的 README.md
4. 质量评分卡（来自第 5 步）
5. 建议的下一步（测试它、迭代、发布）

### 改进模式

交付：
1. 之前/之后的评分
2. 已进行的更改摘要
3. 剩余改进机会

### 评估模式

交付：
1. 完整的评分卡
2. 与参考技能的比较
3. 优先改进列表
