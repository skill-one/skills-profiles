# GKE 升级与维护

生成清晰、可操作的文档——升级计划、运行手册或检查清单——以适应用户的环境。输出应针对其集群模式、发布渠道、版本和工作负载类型进行定制，而不是提供通用建议。

始终围绕自动升级模型提供指导：带维护窗口和排除项的自动升级是首选的控制机制。

## 信息收集

在生成任何升级工件之前，必须建立：

- **集群模式**——标准模式还是自动飞行模式？（自动飞行模式没有节点池管理、强制资源请求、没有 SSH）
- **当前和目标版本**——节点版本偏差必须在控制平面次要版本的两个版本范围内。
- **发布渠道**——快速、常规、稳定或扩展。
- **环境拓扑和发布顺序**——单集群与多集群、开发/测试/生产层级，以及是否使用发布顺序。
- **工作负载敏感性**——StatefulSets、数据库、GPU、长时间运行的批处理需要特殊处理。

如果用户提前提供这些信息，则直接跳转到交付物。如果他们含糊不清，则填写合理的默认值并标记假设。

## 核心原则

GKE 版本遵循 Kubernetes 版本术语：**主版本.次版本.补丁版本**（例如，1.30.1-gke.1187000）。一个**次版本**的版本号提升（例如，1.29 → 1.30）会引入新功能和 API。一个**补丁版本**的版本号提升（例如，1.30.1 → 1.30.2）会引入安全性和错误修复。确保用户理解这种区别。

1. **顺序控制平面、跳级节点池**——控制平面升级是顺序的（N → N+1 → N+2）。节点池支持跳级（N+2）升级。
2. **先升级控制平面**——控制平面必须先于节点池升级。节点可以落后多达两个次要版本。
3. **环境进展**——始终先升级开发/测试环境，再升级生产环境。使用**发布顺序**（首选）来自动化和强制跨环境（例如，开发 → 测试 → 生产）的进展，或者如果未使用发布顺序，则手动协调版本进展。
4. **感知工作负载**——升级策略取决于正在运行的内容（无状态、有状态、GPU、批处理）。
5. **发布渠道优先**——始终推荐发布渠道。请注意，“无渠道”（静态版本控制）已弃用，集群应迁移到发布渠道。
6. **回滚/降级**——控制平面补丁和节点池（次要版本和补丁）可以回滚（降级到目标版本）。GKE 支持两步控制平面次要版本升级，其中第一步是可回滚的。其他控制平面次要版本回滚**不是**客户可执行的，需要 GKE 支持。
7. **节点池升级顺序**——在升级多个节点池时，始终推荐顺序升级：首先升级非关键/无状态池（作为示警池）以验证集群健康，然后再升级关键有状态（数据库）或 GPU 池。

## 发布渠道

| 渠道 | 适用于 | SLA |
|------|--------|-----|
| **快速** | 开发/测试、早期功能访问 | 无升级稳定性 SLA |
| **常规**（默认） | 大多数生产环境 | 完整 SLA |
| **稳定** | 使命关键、优先稳定性 | 完整 SLA |
| **扩展** | 合规性、EoS 执行控制 | 完整 SLA |

### 支持生命周期
标准 GKE 版本在**常规**渠道可用后 14 个月内受支持。这意味着：

- **快速**渠道版本可能支持时间超过 14 个月（因为它们在常规渠道之前进入快速渠道）。
- **稳定**渠道版本可能支持时间少于 14 个月（因为它们在常规渠道之后进入稳定渠道）。
- **扩展**支持将此期限延长至 24 个月。请注意，额外费用仅适用于扩展支持期间（第 15-24 个月）。

### 当前功能

- **扩展渠道计算**：14 个月的标凈支持 + 约 10 个月的扩展支持 ≈ 每个次要版本 24 个月总支持时间。即使在扩展支持期间，强制升级仍然会发生：如果你不采取行动，GKE 会在支持到期时自动升级集群——平均每个次要版本升级间隔约 4 个月，与其他渠道的节奏相同（功能只是到达较晚）。
- **升级可靠性（KubeCon NA 2025）**：Google 报告 GKE 控制平面和节点的升级成功率高达 99.99%，安全的回滚和跳级版本升级支持使团队能够更少地升级（例如，每年一次而不是每季度一次）。首先在非生产集群中试点跳级版本升级。
- **自动扩展蓝绿节点升级**（预览）：一种蓝绿变体，按需扩展绿色池，而不是预先配置完整的副本池——适用于无法预留 2 倍容量的易受干扰工作负载。
- **计划集群升级通知**（预览）：选择接收关于计划次要版本升级的通知，并将通知连接到告警系统。
- **在排干期间进行优雅终止和 PDB**：蓝绿（包括自动扩展蓝绿，预览）是*唯一*尊重 `terminationGracePeriodSeconds` 的策略，长达 24 小时；浪涌升级尊重它长达 60 分钟。在节点排干期间，GKE 尊重 PDB 最长 60 分钟，之后会强制删除 Pod（会发送通知）。

## 维护窗口和排除项

配置维护窗口以控制自动升级时间。GKE 还支持节点池级别的维护排除项（除集群级别之外），以阻止特定工作负载的升级。

**排除项类型和限制：**

- **“无升级”**（范围：`no_upgrades`）：阻止所有升级（次要版本、补丁、节点）。
  - **限制**：每个排除项最多 **90 天**，并且集群最多可以有 **3** 个此类排除项。它们必须仍然在任何滚动 92 天窗口中至少允许 **48 小时的维护可用性**——因此你不能将它们链接成超过 90 天的连续冻结。GKE 建议将这些控制在 30 天以内。
- **“无次要版本或节点升级”**（范围：`no_minor_or_node_upgrades`）：阻止次要版本和节点升级，但允许控制平面补丁升级（低风险）。
  - **限制**：无固定天数上限——受次要版本的 **支持到期 (EoS)** 限制。建议：保持在 ~6 个月以内。
- **“无次要版本升级”**（范围：`no_minor_upgrades`）：阻止次要版本升级，但允许控制平面补丁和节点升级。
  - **限制**：无固定天数上限——受 EoS 限制。建议：保持在 ~6 个月以内。

**重要排除项规则（在推荐排除项时必须遵循，并在最终文本响应中包含）：**

1. **仅自动升级**：维护排除项**仅阻止自动升级**。用户发起的手动升级将绕过排除项。你必须向用户解释这一点。
2. **警告“无渠道”**：你必须明确警告禁用发布渠道（“无渠道”/静态版本控制）已弃用，不能用作排除项的替代方案。
3. **比较范围**：你必须解释“无升级”（限制、阻止补丁）和“无次要版本或节点升级”（允许补丁、更长时间）之间的区别。当用户希望允许安全补丁/修复同时阻止次要版本跳跃时，建议“无次要版本或节点升级”。
4. **处理 > 90 天的时期**：如果用户需要阻止升级超过 90 天，你必须解释“无升级”每个排除项限制为 90 天（每个集群最多 3 个，并且在任何滚动 92 天窗口中必须保持至少 48 小时的维护可用性，防止链接成更长的连续冻结）并建议使用范围排除项（“无次要版本或节点升级”/“无次要版本升级”），这些排除项没有固定天数上限，并且可以运行到次要版本的 EoS。
5. **版本偏差**：在使用排除项时要注意版本偏差（控制平面和节点池之间）。确保偏差不超过支持的 2 个次要版本。使用 `--add-maintenance-exclusion-until-end-of-support` 进行持久排除项。
6. **正确的 gcloud 语法**：在提供排除项的 gcloud 命令时，你必须使用单独的标志语法：`--add-maintenance-exclusion-name`、`--add-maintenance-exclusion-start`、`--add-maintenance-exclusion-end`（或 `--add-maintenance-exclusion-until-end-of-support`），以及 `--add-maintenance-exclusion-scope`（不要使用单个逗号分隔的 `--add-maintenance-exclusion` 标志）。

## 强制升级覆盖

GKE 保留在强制操作中覆盖用户定义的维护窗口和排除项的权利。这些覆盖不能被禁用或阻止。

**常见覆盖场景：**

- **关键安全补丁**：必须立即应用以保护基础设施的紧急漏洞修复。
- **支持到期 (EoS) / 结束生命 (EOL) 执行**：如果集群正在运行不受支持的版本，GKE 将强制将其升级到受支持的版本。
- **证书过期**：如果控制平面证书（CA）即将过期（在 30 天内）并且需要轮换以防止集群不可恢复。
- **维护饥饿**：GKE 要求在任何滚动 92 天窗口中至少有 48 小时的维护可用性。如果排除项阻止过多，GKE 可能会强制升级。

**指导（在讨论覆盖时必须遵循）：**

1. **与公告关联**：如果 GKE 执行意外升级，你必须明确建议检查 GKE 发布说明或安全公告以将事件与紧急补丁相关联（不要只是建议检查 Cloud Audit Logs）。
2. **设计弹性**：工作负载必须设计为能够承受意外的控制平面或节点轮换。你必须建议：
   - 区域集群（多主节点）以确保在控制平面升级期间 API 可用性。
   - 多区域工作负载部署。
   - 关键部署的副本 > 1。
   - 正确配置的 Pod 偏离预算 (PDB)，不要过于严格。

## 升级规划

在要求规划升级时，生成一个涵盖以下内容的结构化文档：

- 版本兼容性（破坏性更改、弃用 API）（仅限次要版本升级）
- 升级路径（顺序次要版本升级）（仅限次要版本升级）
- 节点池升级策略（仅标准模式）
- 工作负载就绪情况（PDB、资源请求）
- 回滚/应急程序（如何回滚节点池或与 GKE 支持协调主回滚）

**兼容性搜索规则：**

- 如果兼容性信息（例如，第三方运营商兼容性、GPU 驱动/CUDA 兼容性矩阵）在工作区或通过快速网络搜索中不可用，**不要循环或进行多次搜索尝试**。相反，将兼容性验证列为检查清单中的**关键预升级行动项**。

### 节点池策略（仅标准模式）

推荐**浪涌升级**作为默认和最常见的策略，并具有每个池设置：

- **无状态**：较高的 `maxSurge`（2-3）以加快速度，`maxUnavailable=0` 以确保安全。
- **有状态/数据库**：`maxSurge=1, maxUnavailable=0`（保守）。
- **GPU（固定预留）**：`maxSurge=0, maxUnavailable=1`（无浪涌容量）。
- **大型（50+ 节点）**：`maxSurge=20, maxUnavailable=0`（最大并行度）。

对于需要快速回滚或严格验证的使命关键工作负载，建议**标准蓝绿**升级。承认**自动扩展蓝绿**作为易受干扰工作负载的选项，但请注意它目前处于预览状态，可能需要容量要求。

**升级顺序（仅用户发起）**：在规划手动升级时，指定节点池升级的顺序。建议首先升级无状态池，验证集群稳定性，然后升级有状态/GPU 池。对于自动升级，GKE 会自动管理顺序节点池升级。

对于标准命令序列和运行手册模板，请参阅 [`references/runbook-template.md`](references/runbook-template.md)。

### 大规模 AI/ML 集群（GPU/TPU）

在建议 GPU/TPU 升级时，你必须涵盖以下所有内容：

- **无实时迁移**：GPU 虚拟机不支持实时迁移；GKE 升级将强制 Pod 重启。向用户解释这一点。
- **固定预留和配额**：H100/A100 通常使用固定预留，没有备用配额。建议滚动升级，带零浪涌（`maxSurge=0, maxUnavailable=1`），这会在升级节点之前释放该节点的预留，然后为其提供替代节点。解释为什么**蓝绿升级在此处不可行**，因为它们需要在过渡期间需要双倍（2x）GPU 资源（配额和预留）。
- **驱动程序耦合**：GPU 驱动程序与节点操作系统镜像紧密耦合，因此节点升级会引入新的 Linux 内核和 NVIDIA 驱动程序，可能会破坏 CUDA 兼容性。建议在开发/测试环境/集群中先升级并测试 CUDA 兼容性，然后更新工作负载依赖项（容器镜像中的 CUDA 版本）以匹配新驱动程序，然后再尝试升级。要诊断驱动程序回归，请比较旧（正常工作）节点和新（无法工作）节点的操作系统镜像、内核版本（`uname -r`）和驱动程序版本，并部署一个测试 Pod（例如，向量加法）以验证 GPU 访问。如果生产被阻止，将节点池回滚到以前的版本是最快的缓解措施。
- **操作安全性**：建议使用 GKE **维护排除项**在活动培训活动中阻止自动升级。在手动升级之前，对 GPU 节点进行隔离，并等待活动培训作业检查点/完成。
- **TPU 考虑**：TPU 切片原子重新创建（不是滚动）；维护在一个切片上会重新启动环境中的所有切片。

## 检查清单

生成可复制的 Markdown 检查清单。请参阅 [`references/checklists.md`](references/checklists.md) 以获取完整的预升级和后升级检查清单模板。根据用户的环境进行调整。

**有状态工作负载**：当存在有状态工作负载（数据库）时，始终在预升级检查清单中包含 PV 备份完成和 PV 回收策略（例如，保留 vs 删除）的检查。

**自动飞行检查清单**：对于自动飞行集群，请确保检查清单包括：

- 验证所有容器上的 `resources.requests`（自动飞行要求）。
- 你必须包含特定的 `kubectl` 命令以检查 API 弃用情况，特别是：`kubectl get --raw /metrics | grep apiserver_request_total | grep deprecated` 以检查任何活动工作负载是否使用弃用 API。
- 验证 PDB 以确保它们不会阻止节点排干（尽管 GKE 管理节点，但仍然尊重 PDB）。
- 识别并删除“裸 Pod”（未由 ReplicaSet/Deployment/StatefulSet 管理的 Pod），因为它们在节点重新创建期间不会被重新调度。
- 验证 `terminationGracePeriodSeconds` 以确保 Pod 有足够的时间在节点重新创建期间优雅地关闭。

## 维护运行手册

生成包含实际 `gcloud` 和 `kubectl` 命令的逐步运行手册。请参阅 `references/runbook-template.md` 以获取标准命令序列。

**任何放宽安全控制的运行手册都必须在同一运行手册中恢复它。** 这适用于所有情况，尤其是在节点池迁移或回滚期间的 PDB：在排干之前备份 PDB，并将重新应用它们作为编号步骤，并为其自己的验证，而不是结束语。一个将 `maxUnavailable: 100%` 修复为解除排干阻塞的运行手册，并且永远不会恢复它，将使集群失去干扰保护，并且差距在下次自愿驱逐之前是看不见的。相同的规则适用于维护排除项、隔离器和 autoscaler `minNodes` 覆盖，以通过程序。

- **静默暂停行为**：如果维护窗口在升级（自动或手动）完成之前关闭，GKE会故意暂停发布以防止在允许时间外造成中断。
- **混合版本状态**：集群会处于一个稳定的混合版本状态（部分节点已升级，部分未升级）。你必须明确声明这是一种受支持且安全的预期结果。
- **恢复**：升级将在下一个维护窗口开启时自动恢复。
- **立即完成的缓解措施**：如果用户希望立即完成升级，你必须建议**暂时扩大维护窗口**以包含当前时间（例如，使用 `gcloud container clusters update ... --maintenance-window-start ... --maintenance-window-duration ...`）。不要建议重新触发手动升级或绕过窗口。

## 故障排除

当用户报告升级卡住或失败时，你必须系统地分析和解决你最终回复中的所有5个潜在原因。即使你怀疑其中一个是主要原因，也**不要省略任何检查**：

1. **PDB阻止驱逐**：使用 `kubectl get pdb -A` 确认是否有任何PDB的 `ALLOWED DISRUPTIONS = 0`。
2. **资源限制**：检查Pod是否因容量限制卡在 `Pending` 状态。
3. **裸Pod**：识别没有所有者引用且阻止驱逐的Pod（建议删除它们）。
4. **准入webhook**：检查验证/修改webhook是否拒绝在新节点上创建Pod。
5. **PVC连接问题**：检查卷连接失败（尤其是区域限制）。

**缺货/配额耗尽规则**：

- 如果升级因 `ZONE_RESOURCE_POOL_EXHAUSTED`（缺货）或Compute Engine资源 `QUOTA_EXCEEDED` 而卡住：
  1. 建议将升级策略修改为 `maxSurge=0`（原地滚动）以绕过配额限制。
  2. 对于 `QUOTA_EXCEEDED`，建议向Google Cloud申请配额增加。
  3. 你必须建议**将工作负载迁移或在不同区域/区域创建新的节点池**，以缓解容量/配额不足的问题。

有关每个步骤的确切诊断命令和修复程序的详细信息，请参阅 [`references/troubleshooting.md`](references/troubleshooting.md)。
