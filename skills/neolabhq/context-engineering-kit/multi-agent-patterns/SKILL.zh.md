# Claude代码的多智能体架构模式

多智能体架构将工作分配给多个智能体调用，每个智能体都有自己专注的上下文。设计良好时，这种分配能够实现单个智能体限制之外的 capability；设计不良时，它会引入协调开销从而抵消收益。关键洞察在于：子智能体主要存在是为了隔离上下文，而不是拟人化角色划分。

## 核心概念

多智能体系统通过分布式方式解决单个智能体上下文限制问题。存在三种主导模式：监督者/协调者用于集中控制，点对点/群集用于灵活的交接，层次结构用于分层抽象。关键设计原则是上下文隔离——子智能体主要存在是为了划分上下文，而不是模拟组织角色。

有效的多智能体系统需要明确的协调协议、避免奉承的共识机制，以及对失败模式的仔细关注，包括瓶颈、分叉和错误传播。

## 为什么需要多智能体架构

### 上下文瓶颈

单个智能体在推理能力、上下文管理和工具协调方面面临固有的上限。随着任务变得更加复杂，上下文窗口会填满累积的历史记录、检索到的文档和工具输出。性能按照可预测的模式下降：丢失中间效果、注意力稀缺和上下文中毒。

多智能体架构通过将工作划分到多个上下文窗口来解决这些限制。每个智能体在一个干净的上下文中专注于其子任务。结果在协调层聚合，没有任何单个上下文承担全部负担。

### 并行化论点

许多任务包含需要单个智能体顺序执行的并行化子任务。一个研究任务可能需要搜索多个独立来源、分析不同文档或比较竞争方法。单个智能体按顺序处理这些任务，随着每一步累积上下文。

多智能体架构将每个子任务分配给具有新鲜上下文的专用智能体。所有智能体同时工作，然后返回结果给协调者。实际世界时间接近最长子任务的持续时间，而不是所有子任务的总和。

### 专业化论点

不同的任务受益于不同的智能体配置：不同的系统提示、不同的工具集、不同的上下文结构。通用智能体必须在上下文中携带所有可能的配置。专用智能体只携带它们需要的配置。

多智能体架构在不引起组合爆炸的情况下实现专业化。协调者路由到专用智能体；每个智能体都使用针对其领域的精简上下文进行操作。

## 架构模式

### 模式1：监督者/协调者

监督者模式将一个中央智能体置于控制地位，委派给专家并综合结果。监督者维护全局状态和轨迹，将用户目标分解为子任务，并路由到适当的工人。

```
用户请求 -> 监督者 -> [专家A、专家B、专家C] -> 聚合 -> 最终输出
```

**何时使用**：具有明确分解的复杂任务、需要跨领域协调的任务、需要人工监督的任务。

**优点**：严格控制工作流程、更容易实现人工干预、确保遵守预定义计划。

**缺点**：监督者上下文成为瓶颈、监督者故障级联到所有工人、"电话游戏"问题，即监督者错误地转述子智能体的响应。

**Claude代码实现**：创建一个主命令来协调，使用任务工具调用专用的子智能体。监督者命令包含协调逻辑，并调用子智能体进行专业工作。

```markdown
<!-- 示例监督者命令结构 -->
1. 分析用户请求并将其分解为子任务
2. 对于每个子任务，调度到适当的专家：
   - 使用任务工具生成具有专注上下文的子智能体
   - 只向每个子智能体传递相关的上下文
3. 从所有子智能体收集和综合结果
4. 返回统一响应给用户
```

**"电话游戏"问题**：当监督者错误地转述子智能体的响应时，监督者架构可能会表现更差，导致保真度下降。修复方法：当综合会丢失重要细节时，允许子智能体直接传递响应。在Claude代码中，这意味着让子智能体直接写入共享文件或原封不动地返回它们的输出，而不是让监督者重写所有内容。

### 模式2：点对点/群集

点对点模式移除中心控制，允许智能体根据预定义协议直接通信。任何智能体都可以通过显式交接机制将控制权转移给任何其他智能体。

**何时使用**：需要灵活探索的任务、僵化规划适得其反的任务、具有无法预先分解的涌现需求的任务。

**优点**：没有单点故障、有效扩展用于广度优先探索、支持涌现问题解决行为。

**缺点**：协调复杂性随智能体数量增加而增加、没有中央状态保持器时存在分叉风险、需要强大的收敛约束。

**Claude代码实现**：创建可以基于发现需求调用其他命令的命令。使用共享文件（如任务列表或状态文件）作为协调机制。

```markdown
<!-- 示例点对点交接结构 -->
1. 从共享上下文文件分析当前状态
2. 确定当前智能体是否可以完成任务
3. 如果需要专业帮助：
   - 将当前发现写入共享状态
   - 调用适当的智能体命令/技能
4. 继续直到任务完成或交接
```

### 模式3：层次结构

层次结构将智能体组织成抽象层：战略层、规划层和执行层。战略层智能体定义目标和约束；规划层智能体将目标分解为可执行计划；执行层智能体执行原子任务。

```
战略层（目标定义）-> 规划层（任务分解）-> 执行层（原子任务）
```

**何时使用**：具有清晰层次结构的大规模项目、具有管理层的企业工作流、需要高层规划和详细执行的任务。

**优点**：反映组织结构、明确分离关注点、在不同层级使用不同的上下文结构。

**缺点**：层间协调开销、战略与执行之间可能存在错位、错误传播复杂。

**Claude代码实现**：使用不同抽象层构建你的插件。高级命令专注于战略并调用中层规划命令，规划命令反过来调用原子执行命令。

## 上下文隔离作为设计原则

多智能体架构的主要目的是上下文隔离。每个子智能体在一个干净的上下文窗口中专注于其子任务，而不携带其他子任务的累积上下文。

### 隔离机制

**指令传递**：对于简单、明确定义的子任务，协调者创建专注的指令。子智能体只接收其特定任务所需的指令。在Claude代码中，这意味着通过任务工具向子智能体传递最小化、针对性的提示。

**文件系统内存**：对于需要共享状态复杂任务，智能体从持久存储读取和写入。文件系统作为协调机制，避免因共享状态传递导致的上下文膨胀。这是Claude代码最自然的模式——智能体通过markdown文件、JSON状态文件或结构化文档进行通信。

**完整上下文委托**：对于需要子智能体完全理解的复杂任务，协调者共享其整个上下文。子智能体拥有自己的工具和指令，但为决策接收完整上下文。谨慎使用，因为它会破坏上下文隔离的目的。

### 隔离权衡

完整上下文委托提供最大能力，但会破坏子智能体的目的。指令传递维护隔离，但限制子智能体的灵活性。文件系统内存支持共享状态而不传递上下文，但引入一致性挑战。

正确的选择取决于任务复杂性、协调需求和工作性质。

## 共识与协调

### 投票问题

简单多数投票将弱推理产生的幻觉视为与合理推理平等。如果没有干预，多智能体讨论可能会因为固有的一致性倾向而演变成基于错误前提的共识。

### 加权贡献

根据置信度或专业知识对智能体贡献进行加权。具有更高置信度或领域专业知识的智能体在最终决策中权重更大。

### 辩论协议

辩论协议要求智能体在多轮中互相批评输出。对抗性批评在复杂推理上通常比协作共识产生更高的准确性。

**Claude代码实现**：创建一个评审阶段，其中一个智能体批评另一个的输出。将此结构化为单独的命令：一个用于初始工作，一个用于批评，以及可选的一个基于批评进行修订。

### 触发式干预

监控多智能体交互以检测特定行为标记：
- **停滞触发器**：当讨论没有进展时激活
- **奉承触发器**：检测到智能体模仿其他答案而没有独特推理时
- **分叉触发器**：检测到智能体远离原始目标时

## 失效模式与缓解措施

### 失效：监督者瓶颈

监督者从所有工人累积上下文，容易饱和和退化。

**缓解措施**：实施输出约束，让工人只返回提炼的摘要。使用基于文件的检查点来持久化状态，而不是在上下文中携带完整历史。

### 失效：协调开销

智能体通信消耗 token 并引入延迟。复杂的协调可能会抵消并行化优势。

**缓解措施**：通过明确的交接协议最小化通信。使用结构化文件格式进行智能体间通信。尽可能批量结果。

### 失效：分叉

在没有中心协调的情况下追求不同目标的智能体可能会偏离预期目标。

**缓解措施**：为每个智能体定义清晰的目标边界。实施验证进度以验证向共同目标的进展。对智能体执行设置迭代限制。

### 失效：错误传播

一个智能体输出中的错误会传播到消费该输出的下游智能体。

**缓解措施**：在传递给消费者之前验证智能体输出。实施重试逻辑。设计组件故障时的优雅降级。

## 在Claude代码中应用模式

### 命令作为监督者

创建一个主命令，执行：
1. 分析任务并创建计划
2. 通过任务工具调度子智能体进行专业工作
3. 收集结果（通过返回值或共享文件）
4. 综合最终输出

### 子智能体作为专家

定义专用于特定领域的子智能体：
- 每个子智能体专注于一个专业领域
- 子智能体接收与其专业相关的专注上下文
- 子智能体返回结构化输出，协调者可以聚合

### 文件作为共享内存

使用文件系统进行智能体间协调：
- 状态文件跟踪跨智能体的进度
- 输出文件收集并行工作的结果
- 任务列表协调剩余工作

### 示例：代码评审多智能体

```
监督者命令：review-code
├── 子智能体：security-review（安全专家）
├── 子智能体：performance-review（性能专家）
├── 子智能体：style-review（风格/约定专家）
└── 聚合：合并发现，去重，优先级排序
```

每个子智能体只接收要评审的代码和其专业焦点。监督者将所有发现聚合为统一的评审。

## 指导原则

1. 将上下文隔离作为多智能体系统的首要优势进行设计
2. 根据协调需求选择架构模式，而不是组织隐喻
3. 将基于文件的通信作为Claude代码多智能体模式的默认选项
4. 实施明确的交接协议和清晰的状态传递
5. 使用辩论模式进行共识，而不是简单同意
6. 监控监督者瓶颈并实施基于文件的检查点
7. 在传递给智能体之前验证输出
8. 设置迭代限制以防止无限循环
9. 明确测试故障场景
10. 从简单开始——只有在单智能体方法失败时才添加多智能体复杂性

## 内存和状态管理

对于跨越多个会话或需要持久状态的任务，使用基于文件的内存：

### 工作内存

上下文窗口本身。提供即时访问，但会话结束时消失。只保留活动信息；总结已完成的工作。

### 会话内存

会话期间创建的文件，跟踪进度：
- 任务列表（已完成，剩余）
- 中间结果
- 决策日志

### 长期内存

跨会话持续存在的持久文件：
- CLAUDE.md用于项目级上下文
- 指定目录中的内存文件
- markdown或JSON中的结构化知识库

### 多智能体内存模式

- **交接文件**：智能体A写入状态，智能体B读取并继续
- **结果聚合**：多个智能体写入单独文件，监督者读取所有文件
- **进度跟踪**：所有智能体更新的共享任务列表
- **知识积累**：智能体追加发现到共享知识文件

选择满足你需求的 simplest 内存机制。基于文件的内存是透明的、可调试的，且不需要任何基础设施。

# 内存系统设计

内存提供持久化层，允许智能体在会话间保持连续性并基于累积知识进行推理。简单智能体完全依赖上下文进行内存，会话结束时失去所有状态。高级智能体实现分层内存架构，平衡即时上下文需求与长期知识保留。从向量存储到知识图谱再到时序知识图谱的演变代表了在结构化内存上的增加投资，以实现改进的检索和推理。

## 核心概念

内存存在于从即时上下文到永久存储的谱系上。一端，上下文窗口中的工作内存提供零延迟访问，但会话结束时消失。另一端，永久存储无限期存在，但需要检索才能进入上下文。

简单向量存储缺乏关系和时间结构。知识图谱保留推理所需的关系。时序知识图谱为时间感知查询添加有效期限。实施选择取决于查询复杂性、基础设施约束和准确性要求。

## 详细主题

### 内存架构基础

**上下文-内存谱系**
内存存在于从即时上下文到永久存储的谱系上。一端，上下文窗口中的工作内存提供零延迟访问，但会话结束时消失。另一端，永久存储无限期存在，但需要检索才能进入上下文。有效架构沿此谱系使用多个层级。

频谱包括工作记忆（上下文窗口、零延迟、易失性）、短期记忆（会话持久性、可搜索、易失性）、长期记忆（跨会话持久性、结构化、半永久性）和永久记忆（档案化、可查询、永久性）。每一层都具有不同的延迟、容量和持久性特征。

**简单向量存储的不足之处**
向量 RAG 通过将查询和文档嵌入共享的嵌入空间来提供语义检索。相似性搜索检索最语义相似的文档。这对于文档检索效果很好，但对于代理记忆缺乏结构。

向量存储会丢失关系信息。如果代理学习到“客户 X 在日期 Z 购买了产品 Y”，向量存储可以直接检索这一事实。但它无法回答“购买了产品 Y 的客户还购买了哪些产品？”因为它没有保留关系结构。

向量存储在时间有效性方面也存在困难。事实会随时间变化，但向量存储除了显式元数据和过滤外，没有机制来区分“当前事实”与“过时事实”。

**转向基于图的记忆**
知识图谱保存实体之间的关系。它不是孤立地存储文档片段，而是编码“实体 A 与实体 B 具有关系 R”。这使得查询可以遍历关系，而不仅仅是基于相似性。

时间知识图谱为事实添加了有效期。每个事实都有一个“有效起始”时间戳，可选的“有效截止”时间戳。这使得可以执行时间旅行查询，在特定时间点重建知识。

**基准性能比较**
深度记忆检索（DMR）基准提供了跨记忆架构的具体性能数据：

| 记忆系统 | DMR 准确率 | 检索延迟 | 备注 |
|---------------|--------------|-------------------|-------|
| Zep（时间知识图谱） | 94.8% | 2.58 秒 | 最佳准确率，快速检索 |
| MemGPT | 93.4% | 可变 | 良好的通用性能 |
| GraphRAG | ~75-85% | 可变 | 相比基线 RAG 提升 20-35% |
| 向量 RAG | ~60-70% | 快速 | 丢失关系结构 |
| 递归摘要 | 35.3% | 低 | 严重信息丢失 |

Zep 相比全上下文基线（2.58 秒 vs GPT-5.2 的 28.9 秒）检索延迟降低了 90%。这种效率来自于仅检索相关的子图，而不是整个上下文历史。

GraphRAG 在复杂推理任务中相比基线 RAG 提升了约 20-35% 的准确率，并通过社区式摘要将幻觉降低了高达 30%。

### 记忆层架构

**第一层：工作记忆**
工作记忆就是上下文窗口本身。它提供对当前正在处理的信息的即时访问，但容量有限，并且在会话结束时消失。

工作记忆的使用模式包括：代理跟踪中间结果的草稿计算、保留对话历史以供当前任务使用、跟踪活跃目标进度的当前任务状态、以及保存当前正在使用的信息的活跃检索文档。

通过仅保留活跃信息、在信息失去注意力之前对其进行摘要、以及使用注意力偏好的位置来优化关键信息，可以优化工作记忆。

**第二层：短期记忆**
短期记忆在当前会话中持久存在，但在会话之间不持久。它提供搜索和检索功能，而无需永久存储的延迟。

常见实现包括会话范围的数据库（在会话结束时持久存在）、指定会话目录中的文件系统存储、以及按会话 ID 键化的内存缓存。

短期记忆的使用案例包括：跨回合跟踪对话状态而不填充上下文、存储可能需要后续的工具调用中间结果、维护任务清单和进度跟踪、以及会话内缓存检索信息。

**第三层：长期记忆**
长期记忆无限期地跨会话持久存在。它使代理能够从过去的交互中学习，并随着时间的推移构建知识。

长期记忆的实现范围从简单的键值存储到复杂的图数据库。选择取决于要建模的关系的复杂性、所需的查询模式以及可接受的底层基础设施复杂性。

长期记忆的使用案例包括：跨会话学习用户偏好、构建随时间增长的领域知识库、维护具有关系历史的实体注册表、以及存储可重用的成功模式。

**第四层：实体记忆**
实体记忆专门跟踪有关实体（人、地点、概念、对象）的信息以保持一致性。这创建了一个原始的知识图谱，其中实体可以在多次交互中被识别。

实体记忆通过跟踪“约翰·多伊”在一个对话中提到的同一个人在另一个对话中是同一个人来维护实体身份。它通过存储随时间发现的有关实体的事实来维护实体属性。它通过跟踪实体之间的关系来维护实体关系。

**第五层：时间知识图谱**
时间知识图谱通过显式有效期扩展实体记忆。事实不仅为真或假，而且在特定时间范围内为真。

这可以通过检索在该日期范围内有效的信息来执行查询，例如“X 日期用户的地址是什么？”。它防止了过时信息与新数据冲突时的上下文冲突。它使能够进行关于实体随时间如何变化的时序推理。

### 记忆实现模式

**模式 1：文件系统作为记忆**
文件系统本身可以作为记忆层。这种模式简单，无需额外的基础设施，并支持即时加载，这使得基于文件系统的上下文有效。

实现使用文件系统层次结构进行组织。使用传达意义的命名约定。以结构化格式（JSON、YAML）存储事实。在文件名或元数据中使用时间戳进行时间跟踪。

优点：简单性、透明性、可移植性。
缺点：无语义搜索、无关系跟踪、需要手动组织。

**模式 2：带元数据的向量 RAG**
带丰富元数据的向量存储提供带过滤功能的语义搜索。

实现将事实或文档嵌入并存储，包括实体标签、时间有效性、来源归因和置信度分数。查询包括与语义搜索一起的元数据过滤器。

**模式 3：知识图谱**
知识图谱明确建模实体和关系。实现定义实体类型和关系类型，使用图数据库或属性图存储，并维护针对常见查询模式的索引。

**模式 4：时间知识图谱**
时间知识图谱为事实添加有效期，支持时间旅行查询并防止过时信息导致的上下文冲突。

### 记忆检索模式

**语义检索**
使用嵌入相似性搜索检索与当前查询语义相似的记忆。

**基于实体的检索**
通过遍历图关系检索与特定实体相关的所有记忆。

**时间检索**
使用有效期过滤器检索在特定时间或时间范围内有效的记忆。

### 记忆整合

记忆会随时间累积，需要整合以防止无限制增长并移除过时信息。

**整合触发器**
在显著累积记忆后触发、检索返回过多过时结果时、按计划周期性触发、或在请求显式整合时触发。

**整合过程**
识别过时事实、合并相关事实、更新有效期、存档或删除过时事实、并重建索引。
