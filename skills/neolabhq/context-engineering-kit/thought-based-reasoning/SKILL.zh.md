# 基于思维的推理技术用于大型语言模型

## 概述

思维链（CoT）提示及其变体鼓励大型语言模型在得出最终答案之前生成中间推理步骤，显著提高了它们在复杂推理任务上的性能。这些技术通过将隐式推理显式化，改变了模型解决问题的方式。

## 快速参考

| 技术 | 使用场景 | 复杂度 | 准确率提升 |
|------|----------|--------|-----------|
| 零样本CoT | 快速推理，没有示例可用 | 低 | +20-60% |
| 少样本CoT | 有良好示例，需要一致格式 | 中 | +30-70% |
| 自洽性 | 高风险决策，需要置信度 | 中 | 比CoT高+10-20% |
| 思维树 | 需要探索的复杂问题 | 高 | 在难题上+50-70% |
| 从少到多 | 带有子问题的多步骤问题 | 中 | +30-80% |
| ReAct | 需要外部信息的任务 | 中 | +15-35% |
| PAL | 数学/计算问题 | 中 | +10-15% |
| 反思 | 迭代改进，从错误中学习 | 高 | +10-20% |

## 核心技术

### 1. 思维链（CoT）提示

**论文**: "Chain of Thought Prompting Elicits Reasoning in Large Language Models" (Wei等人, 2022)
**引用次数**: 14,255+

#### 使用场景
- 多步骤算术或数学应用题
- 需要逻辑推理的常识推理
- 符号推理任务
- 当你有显示推理过程的良好示例时

#### 工作原理
提供包含中间推理步骤的少样本示例，而不仅仅是问答对。模型学习生成类似的逐步推理。

#### 提示模板

```
Q: 罗杰有5个网球。他买了2盒网球。每盒有3个网球。他现在有多少个网球？
A: 罗杰一开始有5个球。2盒3个网球的网球是6个网球。5 + 6 = 11。答案是11。

Q: 食堂原来有23个苹果。他们用了20个做午餐，又买了6个，现在有多少个苹果？
A: 食堂原来有23个苹果。他们用了20个做午餐。所以剩下23 - 20 = 3个。他们又买了6个苹果，所以现在有3 + 6 = 9个。答案是9。

Q: [你的问题在这里]
A:
```

#### 优势
- 显著提高推理任务的准确率
- 可解释的中间步骤
- 对大型模型（>100B参数）效果良好

#### 限制
- 需要精心设计示例
- 对小模型效果较差
- 仍然可能做出计算错误

### 2. 零样本CoT

**论文**: "Large Language Models are Zero-Shot Reasoners" (Kojima等人, 2022)
**引用次数**: 5,985+

#### 使用场景
- 没有示例可用
- 需要快速推理
- 跨任务通用推理
- 在创建少样本示例之前进行原型设计

#### 工作原理
只需在提示后附加"让我们逐步思考"（或类似短语）。这会触发模型生成推理步骤，而无需任何示例。

#### 提示模板

```
Q: 一个杂耍演员可以同时抛16个球。一半是高尔夫球，一半的高尔夫球是蓝色的。有多少个蓝色的高尔夫球？

让我们逐步思考。
```

**其他触发短语**:
- "让我们一步步计算以确保我们得到正确答案。"
- "让我们分解这个问题。"
- "让我们系统地处理这个问题。"
- "首先，让我理解这个问题..."

#### 两阶段方法（更稳健）

**阶段1 - 推理提取**:
```
Q: [问题]
A: 让我们逐步思考。
```

**阶段2 - 答案提取**:
```
[阶段1的推理]
因此，答案是
```

#### 优势
- 无需手动创建示例
- 跨任务泛化
- 易于实现

#### 限制
- 比少样本CoT效果差
- 可能产生冗长或不相关的推理
- 对精确措辞敏感

### 3. 自洽性

**论文**: "Self-Consistency Improves Chain of Thought Reasoning in Language Models" (Wang等人, 2022)
**引用次数**: 5,379+

#### 使用场景
- 需要置信度的高风险决策
- 具有多个有效推理路径的问题
- 需要减少输出方差时
- 推理正确性验证

#### 工作原理
采样多个不同的推理路径，然后通过多数投票选择最一致的答案。直觉：正确答案可以通过多个推理路径得出。

#### 提示模板

```
[使用任何CoT提示 - 零样本或少样本]

[生成N个温度>0的样本]

[从每个样本中提取最终答案]

[返回最频繁的答案（多数投票）]
```

#### 实现示例

```python
def self_consistency(prompt, n_samples=5, temperature=0.7):
    answers = []
    for _ in range(n_samples):
        response = llm.generate(prompt, temperature=temperature)
        answer = extract_answer(response)
        answers.append(answer)

    # 多数投票
    return Counter(answers).most_common(1)[0][0]
```

#### 优势
- 比单路径CoT显著提高准确率
- 提供置信度度量（协议水平）
- 任务无关的改进

#### 限制
- 计算成本更高（N倍生成）
- 需要可提取的离散答案
- 超过~10-20个样本后收益递减

### 4. 思维树（ToT）

**论文**: "Tree of Thoughts: Deliberate Problem Solving with Large Language Models" (Yao等人, 2023)
**引用次数**: 3,026+

#### 使用场景
- 需要探索/回溯的复杂问题
- 初始决策至关重要的问题
- 创意问题解决（写作、谜题）
- 当CoT单独达到<50%准确率时

#### 工作原理
将CoT推广为树结构，其中每个节点是一个“思维”（连贯的语言单元）。使用搜索算法（BFS/DFS）和自我评估来探索和选择有希望的推理路径。

#### 提示模板

**思维生成**:
```
给定当前状态：
[状态]

生成3-5个可能的下一步来解决这个问题。
```

**状态评估**:
```
评估以下部分解决方案是否：
- "确定"（肯定会导致解决方案）
- "可能"（可能有效）
- "不可能"（不可能导致解决方案）

部分解决方案：
[思维过程]
```

**BFS/DFS搜索**:
```python
def tree_of_thoughts(problem, max_depth=3, beam_width=3):
    queue = [(problem, [])]  # (状态, 思维路径)

    while queue:
        state, path = queue.pop(0)

        if is_solved(state):
            return path

        # 生成候选思维
        thoughts = generate_thoughts(state, k=5)

        # 评估并保留前k
        evaluated = [(t, evaluate(state, t)) for t in thoughts]
        top_k = sorted(evaluated, key=lambda x: x[1])[:beam_width]

        for thought, score in top_k:
            if score != "不可能":
                new_state = apply_thought(state, thought)
                queue.append((new_state, path + [thought]))

    return None
```

**示例：24点游戏**

```
问题：用4、9、10、13得到24（使用+、-、*、/且每个数字只用一次）

思维1：13 - 9 = 4（现在有：4、4、10）
评估："可能" - 有两个4和10，可能有效

思维2：10 - 4 = 6（现在有：4、6、13）
评估："可能" - 4 * 6 = 24，需要使用13

思维3：4 + 9 = 13（现在有：10、13、13）
评估："不可能" - 没有办法从这些得到24
```

#### 优势
- 显著提高难题的性能（4% → 74%在24点游戏上）
- 支持回溯和探索
- 早期捕获错误

#### 限制
- 计算成本显著更高
- 需要任务特定的思维分解
- 实现复杂

### 5. 从少到多提示

**论文**: "Least-to-Most Prompting Enables Complex Reasoning in Large Language Models" (Zhou等人, 2022)
**引用次数**: 1,466+

#### 使用场景
- 比你的示例更难的问题
- 组合泛化任务
- 带有清晰子问题的多步骤问题
- 符号操作和SCAN类任务

#### 工作原理
两阶段过程：
1. **分解**：将复杂问题分解为更简单的子问题
2. **顺序求解**：按顺序解决子问题，使用先前答案

#### 提示模板

**阶段1：分解**
```
Q: 四年前，科迪的年龄只有穆罕默德的一半。如果穆罕默德现在比30岁大两倍，科迪现在多少岁？

要解决"四年前，科迪的年龄只有穆罕默德的一半。如果穆罕默德现在比30岁大两倍，科迪现在多少岁？"，我们需要先解决：
- "如果穆罕默德现在比30岁大两倍，穆罕默德现在多少岁？"
然后我们需要解决：
- "四年前，科迪的年龄只有穆罕默德的一半。科迪现在多少岁？"
```

**阶段2：顺序求解**
```
Q: 如果穆罕默德现在比30岁大两倍，穆罕默德现在多少岁？
A: 穆罕默德比30岁大两倍，所以穆罕默德是30 * 2 = 60岁。

Q: 四年前，科迪的年龄只有穆罕默德的一半。穆罕默德是60岁。科迪现在多少岁？
A: 四年前，穆罕默德是60 - 4 = 56岁。科迪是56的一半，所以科迪是56 / 2 = 28岁。因此，科迪现在是28 + 4 = 32岁。

答案是32。
```

#### 优势
- 在更难的问题上表现优异
- 组合任务效果良好
- 明确的问题分解增强了可解释性

#### 限制
- 需要两阶段提示
- 分解步骤可能在新型结构上失败
- 比单阶段CoT更复杂的设置

### 6. ReAct（推理+行动）

**论文**: "ReAct: Synergizing Reasoning and Acting in Language Models" (Yao等人, 2022)
**引用次数**: 5,012+

#### 使用场景
- 需要外部信息（搜索、API）的任务
- 交互式决策环境
- 多跳问答
- 纯推理会导致幻觉时

#### 工作原理
交替推理痕迹（"思维"）与行动（"行动"）和观察（"观察"）。推理帮助规划行动；行动提供新的信息用于推理。

#### 提示模板

```
问题：科罗拉多山脉东部区域的海拔范围是多少？

思维1：我需要搜索科罗拉多山脉造山运动，找到东部区域延伸到的区域，然后找到该区域的海拔范围。
行动1：搜索[科罗拉多山脉造山运动]
观察1：科罗拉多山脉造山运动是在科罗拉多州和周边地区发生的一次造山运动（造山运动）。

思维2：没有提到东部区域。所以我要查找东部区域。
行动2：查找[东部区域]
观察2：东部区域延伸到高平原。

思维3：东部区域延伸到高平原。我需要搜索高平原并找到其海拔范围。
行动3：搜索[高平原]
观察3：高平原是指两个不同的陆地区域：高平原（美国）...

思维4：我需要搜索高平原（美国）。
行动4：搜索[高平原（美国）]
观察4：高平原是大平原的一个子区域... 海拔约为1,800至7,000英尺（550至2,130米）。

思维5：海拔范围是1,800至7,000英尺。
行动5：完成[1,800至7,000英尺]
```

#### 行动类型
- `Search[查询]` - 搜索信息
- `Lookup[关键词]` - 在当前上下文中查找关键词
- `Finish[答案]` - 返回最终答案

#### 优势
- 通过外部知识接地减少幻觉
- 可解释的行动痕迹
- 通过自适应推理处理异常

#### 限制
- 需要集成外部工具
- 更复杂的协调
- 行动空间必须定义

### 7. PAL（程序辅助语言模型）

**论文**: "PAL: Program-aided Language Models" (Gao等人, 2022)
**引用次数**: 608+

#### 使用场景
- 数学/算术推理
- 需要精确计算的问题
- 符号操作
- 当CoT导致计算错误时

#### 工作原理
生成代码（通常是Python）而不是自然语言推理。执行代码以获取答案。LLM处理分解；解释器处理计算。

#### 提示模板

```
Q: 罗杰有5个网球。他买了2盒网球。每盒有3个网球。他现在有多少个网球？

# Python解决方案:
def solution():
    """罗杰有5个网球。他买了2盒网球。每盒有3个网球。他现在有多少个网球?"""
    tennis_balls_initial = 5
    bought_cans = 2
    tennis_balls_per_can = 3
    tennis_balls_bought = bought_cans * tennis_balls_per_can
    tennis_balls_total = tennis_balls_initial + tennis_balls_bought
    return tennis_balls_total

Q: 比尔山庄面包店星期一早上烤了200条面包。他们早上卖了93条，下午卖了39条。一家杂货店退回了6条未售出的面包。他们剩下多少条面包？

# Python解决方案:
def solution():
    """面包师烤了200条。早上卖了93条，下午卖了39条。一家商店退回了6条。剩下多少?"""
    loaves_baked = 200
    loaves_sold_morning = 93
    loaves_sold_afternoon = 39
    loaves_returned = 6
    loaves_left = loaves_baked - loaves_sold_morning - loaves_sold_afternoon + loaves_returned
    return loaves_left
```

#### 优势
- 消除算术错误
- 清晰的变量命名增强了可解释性
- 利用代码执行进行验证

#### 限制
- 需要代码解释器
- 不适用于非计算推理
- 模型必须生成语法正确的代码

### 8. Auto-CoT

**论文**: "Automatic Chain of Thought Prompting in Large Language Models" (Zhang等人, 2022)
**引用次数**: 838+

#### 使用场景
- 没有手动创建的示例
- 想要自动化少样本CoT设置
- 扩展CoT到许多任务
- 当零样本CoT不够用时

#### 工作原理
1. 将问题按多样性聚类
2. 使用零样本CoT为代表性问题生成推理链
3. 使用这些自动生成的链作为少样本示例

#### 提示模板

**步骤1：生成多样化演示**
```python
# 聚类问题
clusters = cluster_questions(all_questions, k=8)

# 为每个聚类选择代表性问题并生成CoT
demonstrations = []
for cluster in clusters:
    question = select_representative(cluster)
    reasoning = zero_shot_cot(question)  # "让我们逐步思考"
    demonstrations.append((question, reasoning))
```

**步骤2：用作少样本示例**
```
Q: [演示问题1]
A: 让我们逐步思考。[生成的推理1]

Q: [演示问题2]
A: 让我们逐步思考。[生成的推理2]

...

Q: [新问题]
A: 让我们逐步思考。
```

#### 优势
- 无需手动创建示例
- 多样性采样提高鲁棒性
- 与手动CoT性能相当

#### 限制
- 质量取决于零样本CoT质量
- 聚类需要相似性度量
- 生成的链可能包含错误

### 9. 反思

**论文**: "Reflexion: Language Agents with Verbal Reinforcement Learning" (Shinn等人, 2023)
**引用次数**: 2,179+

#### 使用场景
- 多次尝试的迭代改进
- 无需微调即可从错误中学习
- 复杂编码或决策任务
- 当单次推理不足时

#### 工作原理
任务失败后，代理生成一个语言"反思"分析哪里出了错。这个反思被存储在内存中，并在后续尝试中用于避免重复错误。

#### 提示模板

**初始尝试**:
```
任务：[任务描述]

思维：[推理]
行动：[行动]
...
结果：[失败/部分成功]
```

**反思**:
```
之前的尝试失败是因为：
1. [具体错误分析]
2. [应该做什么]
3. [关键洞察]

反思：在下次尝试中，我应该...
```

**后续尝试（带有记忆）**：
```
任务：[任务描述]

之前的反思：
- [反思 1]
- [反思 2]

利用这些洞察，我现在将再次尝试该任务。

思考：[改进的推理]
行动：[更优的行动]
```

#### 示例：代码生成

```
任务：编写一个函数来查找最长的回文子串。

尝试 1：[存在 Bug 的代码]
测试结果：在 "babad" 上失败 - 预期结果为 "bab" 或 "aba"，但得到了 "b"

反思：我的解决方案只检查了单个字符。我需要：
1. 考虑所有长度的子串
2. 使用中心扩展法以提高效率
3. 同时记录起始位置和最大长度

尝试 2：[基于反思改进的代码]
测试结果：通过所有测试
```

#### 优点
- 无需更新权重即可从错误中学习
- 在 HumanEval 上达到 91%（超过 GPT-4 的 80%）
- 构建洞察的情景记忆

#### 局限性
- 需要多次尝试
- 长会话中的内存管理
- 反思的质量影响改进效果

## 最佳实践

### 1. 从简单开始
从零样本 CoT（“让我们一步一步地思考”）开始，如果需要再进阶到更复杂的技术。

### 2. 技术与任务匹配
- **数学/逻辑**：CoT, PAL, 自一致性
- **多跳问答**：ReAct, 最少到最多
- **创意/谜题**：思维树
- **迭代任务**：Reflexion

### 3. 组合技术
这些技术通常是互补的：
- ReAct + 自一致性以获得稳健的事实性答案
- ToT + PAL 用于复杂的计算探索
- 最少到最多 + Reflexion 用于困难的多步骤问题

### 4. 提示工程技巧
- 使用清晰的步骤标记（如“第 1 步：”、“首先，”等）
- 包含涵盖边缘情况的多样化示例
- 在示例之间保持一致的格式
- 添加验证步骤（“让我验证一下……”）

## 常见错误

| 错误 | 为什么错 | 修正方法 |
|---------|---------------|-----|
| 在简单查找中使用 CoT | 增加了不必要的令牌和延迟 | 仅保留用于多步骤推理 |
| 自一致性中样本太少 | 多数投票需要足够的样本 | 至少使用 5-10 个样本 |
| 通用的“一步步思考”但未检查输出 | 模型可能产生不相关的推理 | 验证推理质量，而不仅仅是其存在 |
| 在未理解权衡的情况下混合技术 | 计算成本高但无收益 | 理解每种技术在何时增加价值 |
| 使用 PAL 但没有代码解释器 | 没有执行环境，代码生成毫无用处 | 确保可用的执行环境 |
| 未在少样本 CoT 中测试示例质量 | 糟糕的示例导致糟糕的推理 | 验证示例是否正确解决了问题 |
| 将思维树应用于线性问题 | 巨大的开销但无收益 | 仅在需要探索时使用 ToT |
