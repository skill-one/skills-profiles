# 上下文工程基础

上下文是指语言模型在推理时可用的完整状态。它包括模型在生成响应时可以关注的一切内容：系统指令、工具定义、检索到的文档、消息历史记录和工具输出。理解上下文基础知识是有效进行上下文工程的前提。

## 核心概念

上下文由几个不同的组成部分构成，每个组成部分具有不同的特性和约束。注意力机制创建了一个有限的预算，限制了有效上下文的使用。渐进式披露通过按需加载信息来管理这种约束。工程学科是策划实现预期目标所需的最小高信号标记集。

## 详细主题

### 上下文的构成

**系统提示**
系统提示建立代理的核心身份、约束和行为指南。它们在会话开始时加载一次，并且在整个对话期间通常保持不变。系统提示应极其清晰，并使用适合代理的正确高度的简单直接语言。

正确的海拔平衡两种故障模式。在一极，工程师硬编码复杂易碎的逻辑，这会创建脆弱性和维护负担。在另一极，工程师提供模糊的高级指导，这未能为预期输出提供具体信号或错误地假设共享上下文。最佳海拔取得平衡：具体到足以有效指导行为，但又足够灵活以提供强大的启发式方法。

使用 XML 标签或 Markdown 标题将提示组织成不同的部分，以区分背景信息、指令、工具指导和输出描述。随着模型变得越来越强大，确切的格式不太重要，但结构清晰仍然很有价值。

**工具定义**
工具定义指定代理可以采取的操作。每个工具包括名称、描述、参数和返回格式。工具定义在序列化后位于上下文的靠前位置，通常位于系统提示之前或之后。

工具描述共同引导代理行为。描述不佳迫使代理猜测；优化的描述包括使用上下文、示例和默认值。合并原则指出，如果人类工程师不能明确地说在给定情况下应使用哪个工具，那么就不能期望代理能做得更好。

**检索到的文档**
检索到的文档提供特定领域的知识、参考材料或与任务相关的信息。代理使用检索增强生成将相关文档在运行时拉入上下文，而不是预先加载所有可能的信息。

即时方法维护轻量级标识符（文件路径、存储查询、网页链接），并使用这些引用动态地将数据加载到上下文中。这反映了人类认知：我们通常不会记忆整个语料库的信息，而是使用外部组织和索引系统按需检索相关信息。

**消息历史记录**
消息历史记录包含用户和代理之间的对话，包括以前的查询、响应和推理。对于长时间运行的任务，消息历史记录可能会增长并主导上下文使用。

消息历史记录作为临时内存，代理在其中跟踪进度、维护任务状态并在回合之间保留推理。有效管理消息历史记录对于长期任务完成至关重要。

**工具输出**
工具输出是代理操作的結果：文件内容、搜索结果、命令执行输出、API 响应和类似数据。工具输出组成典型代理轨迹中大部分标记，研究显示观察结果（工具输出）可以达到 83.9% 的总上下文使用。

无论工具输出是否与当前决策相关，它们都会消耗上下文。这为观察掩码、压缩和选择性工具结果保留等策略创造了压力。

### 上下文窗口和注意力机制

**注意力预算约束**
语言模型通过注意力机制处理标记，这些机制在上下文中的所有标记之间创建成对关系。对于 n 个标记，这会创建 n^2 个关系必须被计算和存储。随着上下文长度的增加，模型捕获这些关系的能力变得非常薄弱。

模型从以较短的序列为主的训练数据分布中发展出注意力模式。这意味着模型在上下文范围依赖关系方面经验不足，并且具有较少的专业参数。结果是“注意力预算”，随着上下文的增长而消耗。

**位置编码和上下文扩展**
位置编码插值允许模型通过将其适应最初训练的较小上下文来处理更长的序列。然而，这种适应引入了标记位置理解的退化。模型在较长上下文中仍然高度 capable，但在信息检索和长距离推理方面表现出比在较短上下文上的性能降低。

**渐进式披露原则**
渐进式披露通过按需加载信息来有效管理上下文。在启动时，代理仅加载技能名称和描述——足以知道技能何时可能相关。只有在技能针对特定任务激活时，才会加载完整内容。

这种方法使代理保持快速，同时在需要时提供更多上下文。该原则适用于多个级别：技能选择、文档加载，甚至工具结果检索。

### 上下文质量与上下文数量

假设更大的上下文窗口解决了内存问题的观点已被经验证伪。上下文工程意味着找到最大化预期结果可能性的最小高信号标记集。

几个因素造成了上下文效率的压力。处理成本随上下文长度不成比例地增长——不仅仅是双倍标记的成本翻倍，在时间和计算资源方面呈指数增长。即使技术上的窗口支持更多标记，模型性能也会在一定的上下文长度之外下降。即使使用前缀缓存，长输入仍然很昂贵。

指导原则是信息量而非详尽无遗。包括对当前决策有意义的部分，排除无关部分，并设计能够在需要时访问额外信息的系统。

### 上下文作为有限资源

上下文必须被视为具有递减边际收益的有限资源。与具有有限工作记忆的人类一样，语言模型在解析大量上下文时会消耗注意力预算。

引入的每个新标记都会以一定量消耗这种预算。这创造了仔细策划可用标记的需求。工程问题是在固有约束下优化效用。

上下文工程是迭代的，策划阶段发生在每次你决定将什么传递给模型时。它不是一次性的提示编写练习，而是一个持续的上下文管理学科。

## 实用指南

### 基于文件系统的访问

具有文件系统访问权限的代理可以自然地使用渐进式披露。将参考材料、文档和数据存储在外部。按需使用标准文件系统操作加载文件。这种模式避免了将上下文塞满可能不相关的信息。

文件系统本身提供了代理可以导航的结构。文件大小暗示复杂性；命名约定暗示用途；时间戳作为相关性的代理。文件引用的元数据提供了有效细化行为的机制。

### 混合策略

最有效的代理采用混合策略。为速度预加载一些上下文（如 CLAUDE.md 文件或项目规则），但启用自主探索以按需获取额外上下文。决策边界取决于任务特征和上下文动态。

对于内容动态性较低的上下文，预先加载更多是有意义的。对于快速变化或高度特定的信息，即时加载可避免陈旧上下文。

### 上下文预算

考虑到明确的上下文预算进行设计。了解您的模型和任务的上下文有效限制。在开发过程中监控上下文使用情况。在适当的阈值处实施压缩触发器。设计系统假设上下文会退化，而不是希望它不会。

有效的上下文预算需要理解不仅原始标记计数，还包括注意力分布模式。上下文的中间部分比开始和结束部分获得的注意力少。将关键信息放置在受注意力青睐的位置。

```markdown
<输出描述>
提供具有具体行引用的可操作反馈。
```

## 指导方针

1. 将上下文视为具有递减边际收益的有限资源
2. 将关键信息放置在受注意力青睐的位置（开始和结束）
3. 使用渐进式披露按需加载
4. 使用清晰的分节边界组织系统提示
5. 在开发过程中监控上下文使用情况
6. 在 70-80% 的利用率处实施压缩触发器
7. 设计以上下文退化而不是希望避免它为目标
8. 优先选择较小的信号上下文而不是较大的低信号上下文

# 上下文退化模式

语言模型在上下文长度增加时表现出可预测的退化模式。理解这些模式对于诊断故障和设计弹性系统至关重要。上下文退化不是一个二进制状态，而是一个性能退化的连续体，以几种不同的方式表现出来。

## 核心概念

上下文退化通过几种不同的模式表现出来。丢失在中间的现象导致上下文中心的信息获得较少的注意力。上下文中毒发生在错误通过重复引用而累积时。上下文干扰发生在不相关信息压倒相关内容时。上下文混淆发生在模型无法确定哪个上下文适用时。上下文冲突发生在累积信息直接冲突时。

这些模式是可预测的，并且可以通过压缩、掩码、分区和隔离等架构模式来缓解。

## 详细主题

### 丢失在中间的现象

最 well-documented 的退化模式是“丢失在中间”效应，其中模型表现出 U 形注意力曲线。上下文开始和结束处的信息获得可靠的注意力，而埋在中间的信息遭受召回准确率显著降低。

**经验证据**
研究表明，放置在上下文中间的相关信息与放置在开始或结束处的相同信息相比，召回准确率低 10-40%。这不是模型的失败，而是注意力机制和训练数据分布的后果。

模型将大量注意力分配给第一个标记（通常是 BOS 标记）以稳定内部状态。这创建了一个“注意力池”，吸收了注意力预算。随着上下文的增长，有限的预算被拉伸得更薄，中间标记无法获得足够的注意力权重以可靠地检索。

**实际影响**
设计上下文放置时考虑注意力模式。将关键信息放置在上下文的开始或结束处。考虑信息是否将直接查询或需要支持推理——如果是后者，放置不太重要，但整体信号质量更重要。

对于长文档或对话，使用摘要结构在受注意力青睐的位置突出关键信息。使用显式部分标题和过渡来帮助模型导航结构。

### 上下文中毒

上下文中毒发生在幻觉、错误或错误信息进入上下文并通过重复引用而累积时。一旦中毒，上下文就会创建反馈循环，强化不正确的信念。

**中毒如何发生**
中毒通常通过三种途径进入。首先，工具输出可能包含错误或意外格式，模型将其接受为绝对真理。其次，检索到的文档可能包含错误或过时的信息，模型将其纳入推理。第三，模型生成的摘要或中间输出可能引入幻觉，这些幻觉在上下文中持续存在。

累积效应非常严重。如果代理的目标部分中毒，它会发展出需要大量工作才能撤销的策略。每个后续决策都引用中毒内容，强化不正确的假设。

**检测和恢复**
注意症状，包括在之前成功的任务上输出质量下降、工具错位（代理调用错误的工具或参数）以及尽管纠正尝试但仍持续存在的幻觉。当出现这些症状时，请考虑上下文中毒。

恢复需要删除或替换中毒内容。这可能涉及截断上下文到中毒点之前，在上下文中明确指出中毒并请求重新评估，或使用已验证信息重新启动干净上下文。

### 上下文干扰

上下文干扰在上下文变得太长时出现，模型过度关注提供的信息，而牺牲了其训练知识。模型会关注上下文中的所有信息，无论其相关性如何，这造成了使用提供的信息的压力，即使内部知识更准确。

**干扰效应**
研究表明，即使上下文中有一个不相关的文档，也会降低涉及相关文档的任务的性能。多个干扰因素会加剧退化。效应不是关于绝对噪声，而是关于注意力分配——不相关信息与相关信息竞争有限的注意力预算。

模型没有“跳过”不相关上下文的机制。它们必须关注提供的一切，这种义务即使在明显不相关的信息的情况下也会造成干扰。

**缓解策略**
通过仔细策划进入上下文的内容来缓解干扰。在加载检索到的文档之前应用相关性过滤。使用命名空间和组织结构使不相关的部分易于忽略。考虑信息是否真的需要进入上下文，或者是否可以通过工具调用来访问。

当无关信息以降低质量的方式影响响应时，就会产生上下文混淆。这与分心有关，但又有区别——混淆关注的是上下文对模型行为的影响，而不是注意力分配。

如果你将某些内容置于上下文中，模型就必须关注它。模型可能会结合无关信息，使用不适当的工具定义，或应用来自不同上下文的约束。当上下文包含多种任务类型，或在同一会话中切换任务时，混淆问题尤其严重。

**混淆的迹象**
留意那些针对查询错误方面的响应、似乎适用于不同任务的工具调用，或混合了多个来源要求的输出。这些迹象表明模型对当前情况下应适用哪些上下文存在混淆。

**架构解决方案**
架构解决方案包括显式任务分割，其中不同任务获得不同的上下文窗口、任务上下文之间的清晰转换，以及隔离不同目标上下文的状态管理。

### 上下文冲突

当累积信息直接冲突，产生相互矛盾的指导，导致推理偏离时，就会产生上下文冲突。这与中毒不同，中毒是指单个信息错误——在冲突中，多个正确信息相互矛盾。

**冲突来源**
冲突通常源于多源检索，其中不同来源包含矛盾信息、版本冲突，其中过时和当前的信息都出现在上下文中，以及视角冲突，其中不同观点有效但不可兼容。

**解决方法**
解决方法包括显式冲突标记，以识别矛盾并请求澄清、优先规则，以确定哪个来源具有优先权，以及版本过滤，以从上下文中排除过时信息。

### 反直觉发现

研究表明存在几种反直觉模式，挑战了人们对上下文管理的假设。

**打乱干草堆比连贯干草堆表现更好**
研究发现，打乱（不连贯）的干草堆产生的性能优于逻辑连贯的干草堆。这表明连贯上下文可能会创建错误的关联，使检索变得混乱，而不连贯的上下文则迫使模型依赖精确匹配。

**单个干扰因素影响巨大**
即使单个无关文档也会显著降低性能。这种影响与噪声量不成比例，而是遵循阶跃函数，其中任何干扰因素的存在都会触发退化。

**针式问题与问题的相似性相关性**
针式问题与问题对的相似度较低，上下文长度增加时退化更快。需要跨不相似内容进行推理的任务尤其容易受到影响。

### 当更大的上下文损害性能时

更大的上下文窗口并不总是能提高性能。在许多情况下，更大的上下文会创建新的问题，这些问题超过了其带来的好处。

**性能退化曲线**
模型表现出与上下文长度非线性的退化。性能在达到阈值之前保持稳定，然后迅速退化。阈值因模型和任务复杂度而异。对于许多模型，即使上下文窗口支持更大的大小，有意义的退化也始于8,000-16,000个标记。

**成本影响**
处理成本随上下文长度不成比例地增长。处理400K标记上下文的成本不是200K的两倍——它在时间和计算资源上呈指数增长。对于许多应用，这使得大上下文处理在经济效益上不可行。

**认知负荷隐喻**
即使有无限的上下文，要求单个模型在几十个独立任务之间保持一致质量也会造成认知瓶颈。模型必须不断在项目之间切换上下文，保持比较框架，并确保风格一致性。这不是一个可以通过更多上下文解决的问题。

## 实用指南

### 四桶方法

四种策略针对上下文退化的不同方面：

**写入**：使用草稿板、文件系统或外部存储将上下文保存在窗口之外。这使活动上下文保持精简，同时保留信息访问。

**选择**：通过检索、过滤和优先级排序将相关上下文拉入窗口。这通过排除无关信息来解决分心问题。

**压缩**：通过摘要、抽象和观察掩码来减少标记，同时保留信息。这扩展了有效上下文容量。

**隔离**：将上下文分割到子代理或会话中，以防止任何单个上下文变得足够大而退化。这是最激进的策略，但通常也是最有效的。

### 架构模式

通过特定的架构模式实现这些策略。使用即时上下文加载来检索仅在需要时才获取的信息。使用观察掩码将冗长的工具输出替换为紧凑的引用。使用子代理架构隔离不同任务的上下文。使用压缩在超出限制之前总结不断增长的上下文。

## 示例

**示例 1：检测提示设计中的退化**
```markdown
# 你的命令/技能提示可能太大的迹象：

早期迹象（上下文利用率约50-70%）：
- 代理偶尔错过指令
- 响应变得不那么集中
- 一些指南被忽略

警告迹象（上下文利用率约70-85%）：
- 运行结果行为不一致
- 代理"忘记"之前的指令
- 质量变化显著

严重迹象（上下文利用率>85%）：
- 代理忽略关键约束
- 虚构增加
- 任务完成失败
```

**示例 2：缓解提示结构中的"丢失中间"问题**
```markdown
# 将关键信息组织在提示的边缘

<CRITICAL_CONSTRAINTS>                    # 在开头（高注意力）
- 不要直接修改生产文件
- 提交前始终运行测试
- 最大文件大小：500行
</CRITICAL_CONSTRAINTS>

<DETAILED_GUIDELINES>                     # 中间（低注意力）
- 代码风格偏好
- 文档模板
- 审查清单
- 示例模式
</DETAILED_GUIDELINES>

<KEY_REMINDERS>                           # 在结尾（高注意力）
- 运行测试：npm test
- 格式化代码：npm run format
- 创建带描述的PR
</KEY_REMINDERS>
```

**示例 3：子代理上下文隔离**
```markdown
# 不是由一个代理处理所有事情：

## 协调代理（精简上下文）
- 理解任务分解
- 委托给专业子代理
- 汇总结果

## 代码审查子代理（隔离上下文）
- 仅加载代码审查指南
- 仅专注于审查任务
- 返回结构化结果

## 测试编写子代理（隔离上下文）
- 仅加载测试模式
- 仅专注于测试创建
- 返回测试文件
```

## 指南

1. 在开发过程中监控上下文长度与性能的相关性
2. 将关键信息放在上下文的开始或结尾
3. 在严重退化之前实施压缩触发器
4. 在添加到上下文之前验证检索到的文档的准确性
5. 使用版本控制防止过时信息导致冲突
6. 分段任务以防止不同目标之间上下文混淆
7. 设计优雅退化而不是假设完美条件
8. 使用逐渐增大的上下文进行测试以找到退化阈值

# 上下文退化模式：多代理工作流

本节将上下文退化检测和缓解概念转化为Claude Code可执行的多代理工作流。在构建命令、技能或复杂代理管道时使用这些模式，以确保质量和可靠性。

## 虚构检测工作流

代理输出中的虚构会污染下游上下文，并通过多步工作流传播错误。此工作流在虚构复合之前检测它们。

### 使用场景

- 任何代理完成产生事实性声明的任务后
- 提交代理生成的代码或文档之前
- 输出将用作后续代理的输入时
- 在长时间运行的代理会话期间进行审查时

### 多代理验证模式

**步骤 1：生成输出**

让主要代理正常完成任务。

**步骤 2：提取声明**

使用此提示生成一个验证子代理：

```markdown
<TASK>
从以下输出中提取所有事实性声明。每条声明占一行。
</TASK>

<FOCUS_AREAS>
- 文件路径及其存在
- 引用的函数/类/方法名
- 代码行为断言（"此函数返回X"）
- 关于API、库或规范的对外事实
- 数值和指标
</FOCUS_AREAS>

<OUTPUT_TO_ANALYZE>
{agent_output}
</OUTPUT_TO_ANALYZE>

<OUTPUT_FORMAT>
一条声明占一行，前缀为类别：
[PATH] /src/auth/login.ts 存在
[CODE] validateCredentials() 返回布尔值
[FACT] JWT令牌默认24小时过期
[METRIC] 该函数具有O(n)复杂度
</OUTPUT_FORMAT>
```

**步骤 3：验证声明**

对于提取的声明组，生成一个验证代理：

```markdown
<TASK>
通过检查实际代码库和上下文来验证此声明。
</TASK>

<CLAIM>
{声明}
</CLAIM>

<VERIFICATION_APPROACH>
- 对于文件路径：使用文件工具检查存在性
- 对于代码声明：阅读实际代码并验证行为
- 对于对外事实：交叉引用文档或网络搜索
- 对于指标：分析代码结构
</VERIFICATION_APPROACH>

<RESPONSE_FORMAT>
状态：[已验证 | 错误 | 无法验证]
证据：[你发现的内容]
置信度：[高 | 中 | 低]
</RESPONSE_FORMAT>
```

**步骤 4：计算中毒风险**

汇总验证结果：

```
total_claims = 提取的声明数量
verified_count = 标记为已验证的声明数量
false_count = 标记为错误的声明数量
unverifiable_count = 标记为无法验证的声明数量

poisoning_risk = (false_count * 2 + unverifiable_count) / total_claims
```

**步骤 5：决策阈值**

- **风险 < 0.1**：输出可靠，正常继续
- **风险 0.1-0.3**：在继续之前手动审查标记的声明
- **风险 > 0.3**：使用更明确的接地指令重新生成输出：

```markdown
<REGENERATION_PROMPT>
之前的输出包含 {false_count} 个错误声明和 {unverifiable_count} 个无法验证的声明。

具体问题：
{列出FALSE和UNVERIFIABLE声明的证据}

请重新生成您的响应。对于每个事实性声明：
1. 在声明之前使用工具明确验证
2. 如果无法验证，则声明"我无法验证..."而不是断言
3. 为可验证的事实引用特定文件/行/来源
</REGENERATION_PROMPT>
```

## "丢失中间"检测工作流

长提示中埋藏的关键信息获得的关注较少。此工作流检测提示的哪些部分有被忽略的风险，方法是运行多个代理并验证它们的结果是否与原始指令一致。

### 使用场景

- 设计新的命令或技能时带有长提示
- 代理在不同运行中不一致地遵循指令
- 部署提示到生产环境之前
- 在提示优化期间

### 多运行验证模式

**步骤 1：识别关键指令**

从你的提示中提取代理必须遵循的所有关键指令：

```markdown
要验证的关键指令：
1. "不要修改/production中的文件"
2. "提交前始终运行测试"
3. "使用TypeScript严格模式"
4. "最大函数长度：50行"
5. "为公共API包含JSDoc"
6. "格式化输出为JSON"
7. "记录所有文件修改"
```

**步骤 2：使用相同提示运行多个代理**

使用相同的提示（要测试的命令/技能/代理）生成3-5个代理。每个代理独立运行，输入相同：

```markdown
<AGENT_RUN_CONFIG>
运行次数：5
提示：{你的完整待测试提示}
任务：{代表所有指令被执行的代表性任务}

为每个运行保存：
- run_id：唯一标识符
- agent_output：代理的完整响应
- timestamp：完成时间
</AGENT_RUN_CONFIG>
```

**步骤 3：将每个输出与原始提示验证**

对于每个代理的输出，生成一个新的验证代理来检查对每个关键指令的遵守情况：

```markdown
<VERIFICATION_AGENT_PROMPT>
<TASK>
你是一个合规性验证代理。分析代理输出是否遵循原始提示中的每个指令。
</TASK>

<ORIGINAL_PROMPT>
{要测试的完整提示}
</ORIGINAL_PROMPT>

<CRITICAL_INSTRUCTIONS>
{关键指令的编号列表}
</CRITICAL_INSTRUCTIONS>

<AGENT_OUTPUT>
{来自运行_N的输出}
</AGENT_OUTPUT>

<VERIFICATION_APPROACH>
对于每个关键指令：
1. 确定该指令是否适用于此任务
2. 如果适用，检查输出是否遵守
3. 查找显式违反和遗漏
4. 注意部分遵守
</VERIFICATION_APPROACH>

<OUTPUT_FORMAT>
RUN_ID：{run_id}

指令合规性：
- 指令 1："不要修改/production"
  状态：[遵守 | 违反 | 不适用]
  证据：{来自输出或解释的引用}

- 指令 2："提交前运行测试"
  状态：[遵守 | 违反 | 不适用]
  证据：{来自输出或解释的引用}

[...继续为所有指令...]

摘要：
- 遵守的指令：{计数}
- 违反的指令：{计数}
- 不适用：{计数}
</OUTPUT_FORMAT>
</VERIFICATION_AGENT_PROMPT>
```

**步骤 4：汇总结果并识别有风险的部分**

收集所有运行的验证结果，并识别不一致遵守的指令：

```markdown
<AGGREGATION_LOGIC>
对于每个指令：
  followed_count = 状态为FOLLOWED的运行数量
  violated_count = 状态为VIOLATED的运行数量
  applicable_runs = 总运行数 - (状态为NOT_APPLICABLE的运行数)

  compliance_rate = followed_count / applicable_runs

  分类：
  - compliance_rate == 1.0：RELIABLE（始终遵守）
  - compliance_rate >= 0.8：MOSTLY_RELIABLE（轻微不一致）
  - compliance_rate >= 0.5：AT_RISK（不一致 - 可能丢失中间）
  - compliance_rate < 0.5：FREQUENTLY_IGNORED（严重问题）
  - compliance_rate == 0.0：ALWAYS_IGNORED（关键失败）

AT_RISK指令是丢失中间问题的首要信号。
这些是工作有时但不一致的指令，表明它们位于注意力薄弱位置。
</AGGREGATION_LOGIC>

<AGGREGATION_OUTPUT_FORMAT>
指令合规性摘要：

| 指令 | 遵守 | 违反 | 合规率 | 状态 |
|------|------|------|--------|------|
| 1. 修改/production | 5/5 | 0/5 | 100% | RELIABLE |
| 2. 提交前运行测试 | 3/5 | 2/5 | 60% | AT_RISK |
| 3. TypeScript严格模式 | 4/5 | 1/5 | 80% | MOSTLY_RELIABLE |
| 4. 最大函数长度50 | 2/5 | 3/5 | 40% | FREQUENTLY_IGNORED |
| 5. 包含JSDoc | 5/5 | 0/5 | 100% | RELIABLE |
| 6. 格式化为JSON | 1/5 | 4/5 | 20% | ALWAYS_IGNORED |
| 7. 记录修改 | 3/5 | 2/5 | 60% | AT_RISK |

AT-RISK指令（可能位于丢失中间区域）：
- 指令 2："提交前运行测试"（60%合规）
- 指令 4："最大函数长度50"（40%合规）
- 指令 6："格式化为JSON"（20%合规）
- 指令 7："记录修改"（60%合规）
```

**步骤 5：输出建议**

根据识别的有风险部分，提供具体的缓解指导：

```markdown
<RECOMMENDATIONS_OUTPUT>
中间位置分析完成

检测到风险指令：{count}
这些指令执行不一致，表明它们可能位于注意力较弱的中间位置（提示的中间部分）。

具体建议：

1. 将关键信息移至注意力偏好的位置
   以下指令应移至提示的开头或结尾：
   - "提交前运行测试" -> 移至 <CRITICAL_CONSTRAINTS> 在提示开始处
   - "函数长度最大50" -> 移至 <KEY_REMINDERS> 在提示结尾处
   - "格式化为JSON" -> 移至 <OUTPUT_FORMAT> 在提示结尾处
   - "记录修改" -> 添加到开始和结束部分

2. 使用明确标记突出关键信息
   重组风险指令并强调：
   
   之前："提交前始终运行测试"
   之后："**关键：** 您必须提交前运行测试。切勿跳过此步骤。"

   之前："函数最大长度：50行"
   之后："3. [必需] 函数最大长度：50行"

   使用编号列表、粗体标记或明确标签如 [必需]、[关键]、[必须]。

3. 考虑拆分上下文以减少中间部分
   如果您的提示包含许多指令，请考虑：
   - 拆分为针对不同方面的专注子提示
   - 使用具有专业、较短上下文的子代理
   - 将详细指导移至仅在需要时加载的按需部分

   当前提示结构创建了一个大的中间部分，其中
   {count} 条指令正在丢失。通过以下方式减少中间部分：
   - 将2-3个最关键的项移至边缘
   - 将剩余的中间项转换为编号清单
   - 在结尾处添加明确的"验证这些项"提醒
</RECOMMENDATIONS_OUTPUT>
```

### 完整工作流示例

```markdown
# 示例：测试代码审查指令
```

## 错误传播分析工作流

在多代理链中，早期代理的错误会通过后续代理传播和放大。此工作流追踪错误到其来源。

### 使用场景

- 当最终输出包含错误，尽管中间步骤正确时
- 调试复杂的多个代理工作流
- 在代理链中建立错误边界
- 在失败的代理任务的事后分析期间

### 错误追踪模式

**步骤1：捕获代理链输出**

记录链中每个代理的输出：

```markdown
代理链记录：
- 代理1（分析器）：{output_1}
- 代理2（规划器）：{output_2}
- 代理3（实现器）：{output_3}
- 代理4（审查器）：{output_4}
```

**步骤2：识别错误症状**

启动错误识别代理：

```markdown
<TASK>
分析最终输出并识别所有错误、不一致或质量问题。
</TASK>

<FINAL_OUTPUT>
{output_from_last_agent}
</FINAL_OUTPUT>

<OUTPUT_FORMAT>
ERROR_ID: E1
描述：缺少空值检查的函数
位置：src/utils/parser.ts:45
严重性：高

ERROR_ID: E2
...
</OUTPUT_FORMAT>
```

**步骤3：向回追踪每个错误**

针对每个识别的错误，启动追踪代理：

```markdown
<TASK>
将此错误向回追踪通过代理链找到其来源。
</TASK>

<ERROR>
{error_description}
</ERROR>

<AGENT_CHAIN_OUTPUTS>
代理1输出：{output_1}
代理2输出：{output_2}
代理3输出：{output_3}
代理4输出：{output_4}
</AGENT_CHAIN_OUTPUTS>

<ANALYSIS_APPROACH>
针对每个代理输出（从最后一个开始）：
1. 此输出是否包含错误？
2. 如果是，错误是否存在于此代理的输入中？
3. 如果错误在输出中但不在输入中：此代理引入了错误
4. 如果错误在输出和输入中都存在：此代理传播了错误
</ANALYSIS_APPROACH>

<OUTPUT_FORMAT>
ERROR: {error_id}
来源代理：代理 {N}
来源类型：[引入的 | 从上下文传播的 | 从工具输出传播的]
根本原因：{解释}
导致它的上下文：{如果适用，相关上下文片段}
</OUTPUT_FORMAT>
```

**步骤4：计算传播指标**

```
针对链中的每个代理：
  引入的错误数 = 此代理创建的错误数
  传播的错误数 = 此代理传递的错误数
  捕获的错误数 = 此代理修复或标记的错误数

传播率 = 最终错误数 / 引入的总错误数
放大因子 = 最终错误数 / 起始错误数
```

**步骤5：建立错误边界**

根据分析，添加验证检查点：

```markdown
<ERROR_BOUNDARY_TEMPLATE>
代理 {N} 完成后：

1. 启动验证代理检查常见错误模式：
   - {代理 N 倾向于引入的错误模式1}
   - {代理 N 倾向于引入的错误模式2}

2. 如果检测到错误：
   - 记录错误以供分析
   - 要么：直接修复并继续
   - 要么：使用明确指导重新生成代理 N 输出

3. 只有验证通过时才继续到代理 {N+1}
</ERROR_BOUNDARY_TEMPLATE>
```

## 上下文相关性评分工作流

提示的所有部分对任务完成的贡献并不相等。此工作流识别提示中消耗注意力预算但不增加价值的干扰部分。

### 使用场景

- 优化提示长度和内容
- 决定在CLAUDE.md中包含什么
- 当提示感觉臃肿但不确定要删除什么时
- 调试忽略提供上下文的代理
- 部署新命令、技能或代理提示前

### 干扰识别模式

**步骤1：将提示拆分为部分**

将提示（命令/技能/代理）拆分为逻辑部分。每个部分应该是连贯的单位：

```markdown
<PROMPT_PARTS>
部分_1：
  ID：背景
  内容：|
    您是一位Python专家，正在帮助开发团队。
    当前项目：Python 3.9+数据处理管道

部分_2：
  ID：代码风格规则
  内容：|
    - 编写干净、规范的Python代码
    - 为函数签名添加类型提示
    - 为公共函数添加文档字符串
    - 遵循PEP 8风格指南

部分_3：
  ID：历史上下文
  内容：|
    项目于2019年从Python 2.7迁移。
    原团队使用camelCase命名，但我们现在使用snake_case。
    /legacy文件夹中的遗留模块已冻结。

部分_4：
  ID：输出格式
  内容：|
    提供可操作的反馈，并包含具体行引用。
    解释建议背后的原因。
</PROMPT_PARTS>
```

拆分指南：
- 每个XML部分或Markdown标题成为一个部分
- 将概念上不同的指令拆分为它们自己的部分
- 将相关的指令放在一起（不要在思考中途拆分）
- 根据提示长度，目标为3-15个部分

**步骤2：启动评分代理**

并行启动多个评分代理：

```markdown
<TASK>
评分此提示部分对完成指定任务的相关性。
</TASK>

<TASK_DESCRIPTION>
{description of what the agent should accomplish}
示例："审查拉取请求以发现代码质量问题并提出改进建议"
</TASK_DESCRIPTION>

<PROMPT_PARTS>
{正在评估的所有部分的内容}
</PROMPT_PARTS>

<SCORING_CRITERIA>
根据以下标准评分0-10：

必要的（8-10）：
- 部分直接使任务完成
- 删除此部分会导致任务失败
- 部分包含防止错误的关键约束
```

**步骤3：聚合相关性分数**

收集所有评分代理的分数：

```
部分分数 = [
  {id: "background", score: 8, usage: "始终"},
  {id: "code_style_rules", score: 9, usage: "始终"},
  {id: "historical_context", score: 3, usage: "很少"},
  {id: "output_format", score: 7, usage: "经常"}
]
```

计算聚合指标：

```
总部分数 = count(PART_SCORES)
高相关性部分 = count(分数 >= 5的部分)
干扰项 = count(分数 < 5的部分)

上下文效率 = 高相关性部分 / 总部分数
平均相关性 = sum(分数) / 总部分数
```

**步骤4：识别干扰项**

应用干扰阈值（分数 < 5）：

```markdown
干扰项分析：

识别干扰项：
1. 部分：历史上下文
   分数：3/10
   理由："从Python 2.7迁移的历史很少与审查当前代码相关。命名约定注释有用，但应放在代码风格规则中。"
   建议：删除或移动

总结：
- 总部分数：4
- 高相关性部分（>=5）：3
- 干扰项（<5）：1
- 上下文效率：75%
- 平均相关性：6.75

标记影响：
- 干扰项标记：~45（历史上下文）
- 潜在节省：45标记（提示的11%）
```

**步骤5：生成优化建议**

根据干扰项分析，提供可操作的建议：

```markdown
优化建议：

1. 删除：历史上下文
   原因：分数3/10，使用很少。迁移历史不会影响代码审查决策。

2. 移动："我们现在使用snake_case" 从历史上下文
   目标：代码风格规则部分
   原因：此特定规则相关，但埋在不相关的历史上下文中。

3. 考虑压缩：背景
   当前：2句话
   可压缩为：1句话 ("Python 3.9+数据管道专家")
   节省：~15标记

优化后的提示结构：
- 背景（压缩）：8标记
- 代码风格规则（添加snake_case）：52标记
- 输出格式：28标记
- 总计：88标记（从133标记减少）
- 效率提升：34%减少
```

### 干扰项阈值指南

默认阈值5在全面性与效率之间取得平衡：

| 阈值 | 用例 |
|------|------|
| < 3 | 在标记受限的上下文中进行激进修剪 |
| < 5 | 标准优化（推荐默认值） |
| < 7 | 保守修剪，用于关键提示 |

根据以下情况调整阈值：
- **上下文预算压力**：接近限制时降低阈值
- **任务关键性**：生产提示应提高阈值
- **提示稳定性**：实验提示可降低阈值

### 评分代理部署

为提高效率，并行化评分代理：

```markdown
# 并行执行模式
spawn_parallel([
  scoring_agent(part_1, task_description),
  scoring_agent(part_2, task_description),
  scoring_agent(part_3, task_description),
  ...
])

# 收集和聚合
scores = await_all(scoring_agents)
analysis = aggregate_scores(scores)
```

对于大于10个部分的提示，将评分代理分组为5-7组以管理编排开销。

## 上下文健康监控工作流

长时间运行的代理会话会积累上下文，随着时间的推移会退化。此工作流监控上下文健康并在需要时触发干预。

### 使用场景

- 在长时间运行的代理会话（>20轮）期间
- 当代理开始表现出退化症状时
- 作为代理编排系统中的定期健康检查
- 在代理工作流的关键决策点之前

### 健康检查模式

**步骤1：定期症状检测**

每N轮（建议：每10轮），启动健康检查代理：

```markdown
<TASK>
分析最近的对话历史以寻找上下文退化的迹象。
</TASK>

<RECENT_HISTORY>
{最后10轮对话}
</RECENT_HISTORY>

<症状检查清单>
检查以下退化症状：

中间位置丢失：
- [ ] 代理遗漏对话早期指令
- [ ] 关键约束被忽略
- [ ] 代理询问已提供的信息

上下文中毒：
- [ ] 重复出现相同错误
- [ ] 代理将错误信息作为事实引用
- [ ] 尽管纠正，但持续出现幻觉

上下文干扰：
- [ ] 响应变得不集中
- [ ] 代理不恰当地使用无关上下文
- [ ] 质量下降在之前成功的任务上

上下文混淆：
- [ ] 代理混淆不同的任务要求
- [ ] 对明显任务选择错误的工具
- [ ] 混合来自不同任务的输出要求

上下文冲突：
- [ ] 代理对冲突信息表达不确定性
- [ ] 轮次间行为不一致
- [ ] 代理询问已解决的澄清问题
</症状检查清单>

<OUTPUT_FORMAT>
健康状态：[健康的 | 退化的 | 危险的]
检测到的症状：[列出的症状]
建议操作：[继续 | 压缩 | 重新启动]
具体问题：[发现问题的详细描述]
</OUTPUT_FORMAT>
```

**步骤2：自动干预**

根据健康状态，触发适当的干预：

```markdown
IF 健康状态 == "退化" 或 健康状态 == "危险"：
  <重新启动干预>
  1. 提取保存必要状态并保存到文件
  2. 要求用户启动新会话，并在新会话开始后加载保存的状态文件
  </重新启动干预>
```

## 多代理验证指南

1. 使用专注单一目的提示启动验证代理
2. 使用结构化输出格式以供可靠解析
3. 设置明确的行动与继续决策阈值
4. 记录所有验证结果以供调试和优化
5. 平衡验证开销与错误预防价值
6. 在自然检查点实施验证，而不是每轮都实施
7. 对常规操作使用轻量级检查，对关键操作使用更严格的检查
8. 设计可跳过的时间关键场景中的验证

# 上下文优化技术

上下文优化通过战略压缩、掩码、缓存和分区扩展有限上下文窗口的有效容量。目标不是魔术般增加上下文窗口，而是更好地利用可用容量。有效的优化可以在不要求更大的模型或更长的上下文的情况下，将有效上下文容量提高一倍或三倍。

## 核心概念

上下文优化通过四种主要策略扩展有效容量：压缩（在接近限制的上下文中总结上下文）、观察掩码（用引用替换冗长输出）、KV缓存优化（重用缓存的计算）和上下文分区（将工作分配给隔离的上下文）。

关键在于：上下文的**质量**比**数量**更重要。优化的核心在于保留有效信号、降低噪声。其艺术在于权衡“保留什么”与“舍弃什么”，以及在不同场景下何时应用各项技术。

## 详细主题

### 压缩策略

**什么是压缩**
压缩是一种在上下文接近容量上限时对内容摘要化处理，随后用该摘要重新初始化新上下文窗口的实践。它能以高保真度提炼上下文窗口内容，使智能体（Agent）在性能损耗极小的情况下继续运行。

压缩通常是上下文优化的首要手段。其关键在于权衡“保留什么”与“舍弃什么”。

**压缩的实践方法**
压缩通过识别可压缩部分、生成保留核心要点的摘要，并用摘要替代完整内容来实现。压缩优先级如下：

1. **工具输出**：用关键发现替代冗长的输出
2. **较早的对话轮次**：对早期交互进行摘要
3. **检索到的文档**：若任务上下文已捕获，则进行摘要
4. **不可压缩**：系统提示词与关键约束条件

**摘要生成**
有效的摘要会根据内容类型保留不同要素：

- **工具输出**：保留关键发现、指标与结论，去除冗长的原始输出。
- **对话轮次**：保留关键决策、承诺与上下文转变，去除填充性内容和反复拉锯的交互。
- **检索到的文档**：保留关键事实与主张，去除支撑性证据与详尽阐述。

### 观察掩码

**观察的问题**
在智能体的执行轨迹中，工具输出可占据 80% 以上的 token 消耗。其中大部分是已经完成使命的冗余输出。一旦智能体利用工具输出做出决策，保留完整输出的价值便会边际递减，却仍持续占用大量上下文空间。

观察掩码用紧凑的引用替代冗长的工具输出。信息在需要时仍可访问，但不再持续占用上下文资源。

**掩码策略选择**
并非所有观察都应同等对待：

**切勿掩码：**
- 对当前任务至关重要的观察
- 最近一轮产生的观察
- 正在参与当前推理的观察

**考虑掩码：**
- 3 轮及以上之前的观察
- 可提取关键要点的冗长输出
- 已完成使命的观察

**始终掩码：**
- 重复的输出
- 模板化的页眉/页脚
- 已在对话中摘要过的输出

### 上下文分区

**子智能体分区**
上下文优化最激进的形式是将工作分区给具有隔离上下文的子智能体。每个子智能体在专注于其子任务的干净上下文中运行，不携带来自其他子任务的累积上下文。

这种方式实现了关注点分离——详细的搜索上下文保留在子智能体内相互隔离，而协调者专注于综合与分析。

**何时进行分区**
考虑在以下情况下进行分区：
- 任务可自然分解为相互独立的子任务
- 不同子任务需要不同的专门化上下文
- 上下文累积有超出限制的风险
- 不同子任务存在相互冲突的要求

**结果聚合**
通过以下方式为分区后的子任务聚合结果：
1. 验证所有分区均已完成
2. 合并兼容性结果
3. 若合并后结果仍过大，则进行摘要
4. 解决各分区输出间的冲突

## 实用指南

### 优化决策框架

**何时优化：**
- 随着对话延长，响应质量下降
- 长上下文导致成本上升
- 延迟随对话长度增加

**应用什么：**
- 工具输出占主导：采用观察掩码
- 检索文档占主导：采用摘要或分区
- 消息历史占主导：采用带摘要的压缩
- 多种成分并存：组合使用各项策略

### 将优化应用于 Claude Code 提示词

**命令优化**
命令按需加载，因此重点在于保持单个命令的聚焦：
```markdown
# 良好做法：范围明确的聚焦命令
---
name: review-security
description: Review code for security vulnerabilities
---
# 仅包含具体的安全审查指令

# 避免：试图包揽一切的过载命令
---
name: review-all
description: Review code for everything
---
# 将 50 个不同的审查检查清单硬塞在一起
```

**技能优化**
技能默认加载其描述，因此描述必须简洁：
```markdown
# 良好做法：简洁的描述
description: Analyze code architecture. Use for design reviews.

# 避免：浪费上下文章度的冗长描述
description: This skill provides comprehensive analysis of code
architecture including but not limited to class hierarchies,
dependency graphs, coupling metrics, cohesion analysis...
```

**子智能体上下文设计**
生成子智能体时，提供聚焦的上下文：
```markdown
# 协调者提供最简交接：
“审查认证模块的安全问题。
以结构化格式返回发现。”

# 而非这种冗长的交接：
“我需要你查看位于 src/auth/ 的认证模块，它包含
login.ts、session.ts、tokens.ts 等若干文件……[又多了 500 个 token 的上下文]”
```

## 准则

1. 优化前先测量——了解当前状态
2. 在可能的情况下，先应用压缩再应用掩码
3. 设计稳定的提示词以保障缓存稳定性
4. 在上下文问题出现之前进行分区
5. 持续监测优化的效果
6. 在节省 token 与保持质量之间取得平衡
7. 在生产规模下测试优化
8. 为边缘情况实现优雅的降级机制
