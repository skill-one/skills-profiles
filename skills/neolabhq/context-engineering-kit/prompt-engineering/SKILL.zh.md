# 提示工程模式

高级提示工程技术，以最大化大型语言模型的性能、可靠性和可控性。

## 核心功能

### 1. 少样本学习

通过展示示例来教授模型，而不是解释规则。包含 2-5 个输入-输出对来展示所需行为。当你需要一致的格式、特定的推理模式或处理边缘情况时使用。更多示例可以提高准确性，但会消耗 token——根据任务复杂度进行平衡。

**示例：**

```markdown
从支持工单中提取关键信息：

输入："我的登录不起作用，并且我不断收到错误 403"
输出：{"问题": "身份验证", "错误代码": "403", "优先级": "高"}

输入："功能请求：在设置中添加暗黑模式"
输出：{"问题": "功能请求", "错误代码": null, "优先级": "低"}

现在处理："无法上传大于 10MB 的文件，收到超时"
```

### 2. 思维链提示

在最终答案之前请求逐步推理。添加“让我们逐步思考”（零样本）或包含示例推理跟踪（少样本）。用于需要多步逻辑、数学推理或当你需要验证模型思维过程时。通过 30-50% 提高分析任务的准确性。

**示例：**

```markdown
分析此错误报告并确定根本原因。

逐步思考：
1. 预期行为是什么？
2. 实际行为是什么？
3. 最近发生了什么变化可能导致此问题？
4. 哪些组件涉及其中？
5. 最可能的原因是什么？

错误报告："用户在昨日部署的缓存更新后无法保存草稿"
```

### 3. 提示优化

通过测试和改进系统性地提高提示。从简单开始，测量性能（准确性、一致性、token 使用情况），然后迭代。在各种输入上测试，包括边缘情况。使用 A/B 测试来比较变体。对于生产提示至关重要，其中一致性和成本很重要。

**示例：**

```markdown
版本 1（简单）："总结这篇文章"
→ 结果：长度不一致，遗漏了关键点

版本 2（添加约束）："用 3 个要点总结"
→ 结果：结构更好，但仍然遗漏了细微差别

版本 3（添加推理）："确定 3 个主要发现，然后总结每个"
→ 结果：一致、准确、捕获了关键信息
```

### 4. 模板系统

使用变量、条件部分和模块化组件构建可重用的提示结构。用于多轮对话、基于角色的交互或当相同的模式适用于不同的输入时。减少重复并确保类似任务之间的一致性。

**示例：**

```python
# 可重用的代码审查模板
template = """
审查这个 {language} 代码，重点关注 {focus_area}。

代码：
{code_block}

提供以下方面的反馈：
{checklist}
"""

# 使用
prompt = template.format(
    language="Python",
    focus_area="安全漏洞",
    code_block=user_code,
    checklist="1. SQL 注入\n2. XSS 风险\n3. 身份验证"
)
```

### 5. 系统提示设计

设置跨对话持久的行为和约束。定义模型的角色、专业水平、输出格式和安全指南。使用系统提示用于稳定的指令，这些指令不应按回合更改，从而释放用户消息 token 以用于可变内容。

**示例：**

```markdown
系统：你是一位专注于 API 设计的高级后端工程师。

规则：
- 始终考虑可扩展性和性能
- 默认情况下建议使用 RESTful 模式
- 立即标记安全问题
- 用 Python 提供代码示例
- 使用早期返回模式

以以下格式响应：
1. 分析
2. 建议
3. 代码示例
4. 权衡
```

## 关键模式

### 逐步披露

从简单的提示开始，仅在需要时添加复杂性：

1. **级别 1**：直接指令
   - "总结这篇文章"

2. **级别 2**：添加约束
   - "用 3 个要点总结这篇文章，重点关注关键发现"

3. **级别 3**：添加推理
   - "阅读这篇文章，确定主要发现，然后用 3 个要点总结"

4. **级别 4**：添加示例
   - 包含 2-3 个输入-输出对的示例总结

### 指令层次结构

```
[系统上下文] → [任务指令] → [示例] → [输入数据] → [输出格式]
```

### 错误恢复

构建可以优雅处理失败的提示：

- 包含备用指令
- 请求置信度分数
- 在不确定时请求替代解释
- 指定如何指示缺失信息

## 最佳实践

1. **保持具体**：模糊的提示会产生不一致的结果
2. **展示而非告知**：示例比描述更有效
3. **广泛测试**：在各种代表性输入上评估
4. **快速迭代**：小的变化可能产生大的影响
5. **监控性能**：在生产中跟踪指标
6. **版本控制**：将提示视为具有适当版本控制的代码
7. **记录意图**：解释为什么提示结构如此

## 常见陷阱

- **过度工程**：在尝试简单提示之前从复杂的提示开始
- **示例污染**：使用与目标任务不匹配的示例
- **上下文溢出**：用过多的示例超出 token 限制
- **模糊指令**：留下多种解释的空间
- **忽略边缘情况**：不在不寻常或边界输入上测试

## 集成模式

### 与 RAG 系统

```python
# 结合检索到的上下文与提示工程
prompt = f"""给定以下上下文：
{retrieved_context}

{few_shot_examples}

问题：{user_question}

仅基于上述上下文提供详细答案。如果上下文包含足够的信息，请明确说明缺失的内容。"""
```

### 与验证

```python
# 添加自我验证步骤
prompt = f"""{main_task_prompt}

生成响应后，验证它是否满足以下标准：
1. 直接回答问题
2. 仅使用提供的上下文信息
3. 引用具体来源
4. 承认任何不确定性

如果验证失败，请修改你的响应。"""
```

## 性能优化

### Token 效率

- 删除冗余的单词和短语
- 在第一次定义后一致地使用缩写
- 合并类似的指令
- 将稳定内容移动到系统提示

### 延迟减少

- 在不牺牲质量的情况下最小化提示长度
- 使用流式传输进行长格式输出
- 缓存常见的提示前缀
- 在可能的情况下批量处理类似请求

# 代理提示最佳实践

基于 Anthropic 官方关于代理提示的最佳实践。

## 核心原则

### 上下文窗口

“上下文窗口”是指语言模型在生成新文本时可以回顾并参考的文本总量，包括它生成的新文本。这与语言模型训练时使用的大型数据集不同，而是代表了模型的“工作内存”。更大的上下文窗口允许模型理解和响应更复杂和较长的提示，而较小的上下文窗口可能会限制模型处理较长提示或在整个对话中保持连贯性的能力。

- 逐步 token 累积：随着对话通过回合进展，每个用户消息和助手响应都在上下文窗口中累积。以前的回合完全保留。
- 线性增长模式：上下文使用量随每个回合线性增长，以前的回合完全保留。
- 200K token 容量：总可用上下文窗口（200,000 个 token）代表了存储对话历史和从 Claude 生成新输出的最大容量。
- 输入-输出流程：每个回合包括：
  - 输入阶段：包含所有以前的对话历史加上当前的用户消息
  - 输出阶段：生成文本响应，成为未来输入的一部分

### 简洁是关键

上下文窗口是一种公共资源。你的提示、命令、技能共享上下文窗口，包括：

- 系统提示
- 对话历史
- 其他命令、技能、钩子、元数据
- 你的实际请求

**默认假设**：Claude 已经非常智能

仅添加 Claude 不具备的上下文。挑战每一条信息：

- "Claude 真的需要这个解释吗？"
- "我可以假设 Claude 知道这个吗？"
- "这段话是否值得其 token 成本？"

**良好示例：简洁**（大约 50 个 token）：

````markdown  theme={null}
## 提取 PDF 文本

使用 pdfplumber 进行文本提取：

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
````

**不良示例：过于冗长**（大约 150 个 token）：

```markdown  theme={null}
## 提取 PDF 文本

PDF（便携式文档格式）文件是一种常见的文件格式，包含文本、图像和其他内容。要从 PDF 中提取文本，您需要使用库。有许多可用于 PDF 处理的库，但我们推荐 pdfplumber，因为它易于使用并且可以很好地处理大多数情况。首先，您需要使用 pip 安装它。然后您可以使用以下代码...
```

简洁的版本假设 Claude 知道 PDF 是什么以及库是如何工作的。

### 设置适当的自由度

根据任务的易碎性和可变性匹配具体程度。

**高自由度**（基于文本的指令）：

用于：

- 多种方法都有效
- 决策取决于上下文
- 启发式方法指导方法

示例：

```markdown  theme={null}
## 代码审查过程

1. 分析代码结构和组织
2. 检查潜在的 bug 或边缘情况
3. 建议可读性和可维护性的改进
4. 验证是否遵循项目约定
```

**中等自由度**（伪代码或带参数的脚本）：

用于：

- 存在首选模式
- 允许一定程度的变体
- 配置影响行为

示例：

````markdown  theme={null}
## 生成报告

使用此模板并根据需要自定义：

```python
def generate_report(data, format="markdown", include_charts=True):
    # 处理数据
    # 按指定格式生成输出
    # 可选地包含可视化
```
````

**低自由度**（特定脚本、参数很少或没有）：

用于：

- 操作易碎且容易出错
- 一致性至关重要
- 必须遵循特定顺序

示例：

````markdown  theme={null}
## 数据库迁移

运行 exactly 这个脚本：

```bash
python scripts/migrate.py --verify --backup
```

不要修改命令或添加其他标志。
````

**类比**：将 Claude 视为探索路径的机器人：

- **两边都是悬崖的窄桥**：只有一种安全的方式前进。提供具体的护栏和精确指令（低自由度）。示例：必须按确切顺序运行的数据库迁移。
- **没有危险的开阔地带**：许多路径都能成功。给出一般性指导并信任 Claude 找到最佳路线（高自由度）。示例：代码审查，其中上下文决定最佳方法。

# 代理沟通的劝服原则

用于编写提示，包括但不限于：命令、钩子、Claude Code 的技能，或用于子代理或任何其他 LLM 交互的提示。

## 概述

LLM 对人类的劝服原则做出反应。理解这种心理学有助于你设计更有效的技能——不是为了操纵，而是为了确保即使在压力下也能执行关键实践。

**研究基础**：Meincke 等人（2025 年）测试了 7 种劝服原则，N=28,000 个 AI 对话。劝服技术使合规率翻了一番（33% → 72%，p < .001）。

## 七个原则

### 1. 权威

**是什么**：对专业知识、资格或官方来源的尊重。

**如何在提示中起作用**：

- 命令语言："你必须"、"从不"、"总是"
- 非协商框架："没有例外"
- 消除决策疲劳和合理化

**何时使用**：

- 执行纪律的技能（TDD、验证要求）
- 安全关键实践
- 既定最佳实践

**示例**：

```markdown
✅ 编写代码之前测试？删除它。重新开始。没有例外。
❌ 当可行时考虑先编写测试。
```

### 2. 承诺

**是什么**：与先前的行为、声明或公开声明的一致性。

**如何在提示中起作用**：

- 要求公告："宣布技能使用情况"
- 强制明确选择："选择 A、B 或 C"
- 使用跟踪：TodoWrite 用于清单

**何时使用**：

- 确保技能实际上被执行
- 多步骤流程
- 责任机制

**示例**：

```markdown
✅ 当你发现一个技能时，你必须宣布："我正在使用 [技能名称]"
❌ 考虑让你的合作伙伴知道你正在使用哪个技能。
```

### 3. 稀缺性

**是什么**：来自时间限制或有限可用性的紧迫性。

**如何在提示中起作用**：

- 时间限制要求："在继续之前"
- 顺序依赖："立即在 X 之后"
- 防止拖延

**何时使用**：

- 立即验证要求
- 时间敏感的工作流程
- 防止"我稍后做"

**示例**：

```markdown
✅ 完成任务后，立即请求代码审查，然后再继续。
❌ 你可以在方便的时候审查代码。
```

### 4. 社会证明

**是什么**：对他人做什么或被认为是正常的事的遵从。

**如何在提示中起作用**：

- 普遍模式："每次"、"总是"
- 失败模式："X 没有 Y = 失败"
- 建立规范

**何时使用**：

- 记录普遍实践
- 警告常见的失败
- 强化标准

**示例**：

```markdown
✅ 清单没有 TodoWrite 跟踪 = 步骤被跳过。每次。
❌ 有些人发现 TodoWrite 对清单很有帮助。
```

### 5. 团结

**是什么**：共享身份、"我们感"、群体归属感。

**如何在提示中起作用**：

- 协作语言："我们的代码库"、"我们是同事"
- 共同目标："我们都希望质量"

**何时使用**：

- 协作工作流程
- 建立团队文化
- 非等级实践

**示例**：

```markdown
✅ 我们是同事，一起工作。我需要你诚实的专业判断。
❌ 你应该告诉我如果你是错的。
```

### 6. 互惠

**是什么**：返回所获得利益的义务。

**如何起作用**：

- 有限使用——可能会感觉被操纵
- 几乎不需要在提示中

**何时避免**：

- 几乎总是（其他原则更有效）

### 7. 喜好

**是什么**：对与喜欢的人合作的一种偏好。

**如何起作用**：

- **绝对不要用于合规**
- 与诚实的反馈文化相冲突
- 导致谄媚

**何时避免**：

- 总是用于执行纪律

## 不同提示类型的原理解合

| 提示类型 | 使用 | 避免 |
|------------|-----|-------|
| 执行纪律 | 权威 + 承诺 + 社会证明 | 喜好、互惠 |
| 指导/技术 | 适度权威 + 团结 | 重权威 |
| 协作 | 团结 + 承诺 | 权威、喜好 |
| 参考 | 仅清晰 | 所有劝服 |

## 为什么有效：心理学原理

**明确的界限规则减少合理化**：

- "你必须"消除决策疲劳
- 绝对语言消除"这是一个例外吗？"的问题
- 明确的反合理化抵消特定的漏洞

**实施意图创造自动行为**：

- 清晰的触发器 + 必要动作 = 自动执行
- "当 X，做 Y"比"通常做 Y"更有效
- 减少合规的认知负荷

**LLM 是准人类**：

- 在包含这些模式的训练数据上训练
- 权威语言在训练数据中先于合规出现
- 承诺序列（声明→行动）频繁建模
- 社会证明模式（每个人做 X）建立规范

## 伦理使用

**合法的**：

- 确保关键实践得到遵循
- 创建有效的文档
- 防止可预测的失败

**不正当的：**

- 为个人利益操纵
- 制造虚假的紧迫感
- 基于内疚的合规

**测试：** 如果他们完全理解这项技术，它是否服务于用户的真实利益？

## 快速参考

设计提示时，请询问：

1. **它的类型是什么？**（纪律 vs. 指导 vs. 参考）
2. **我试图改变什么行为？**
3. **哪些原则适用？**（通常为纪律适用权威 + 承诺）
4. **我是否结合得太多？**（不要使用所有七个）
5. **这是否合乎道德？**（是否服务于用户的真实利益？）
