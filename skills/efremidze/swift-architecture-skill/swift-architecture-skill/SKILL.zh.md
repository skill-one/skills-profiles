# Swift 架构技能

## 概述

使用此技能为 SwiftUI/UIKit 代码库选择最佳 Swift 架构方案，并将其应用于用户的任务。

## 快速路径

在选择架构之前，始终捕获：
- 任务类型（新功能、重构、PR 审查、调试）
- UI 堆栈（SwiftUI、UIKit 或混合）
- 最小部署目标（iOS 17+ 支持 `@Observable`；iOS 16 需要 `ObservableObject`）
- 范围（单屏、多屏、全局应用）
- 状态和效果复杂度
- 团队熟悉度和依赖容忍度
- 现有约定以保留

然后：
- 如果用户明确指定了架构，将其视为初始候选方案并首先进行适配检查
- 如果未指定架构，加载 `references/selection-guide.md` 并根据声明的约束推断最佳适配方案
- 如果最佳适配方案结合了多种模式，为功能边界命名一个 **主要** 演练方案，为支持性关注点命名一个 **次要** 演练方案
- 选择 **快速推荐模式** 进行单功能指导，约束条件清晰
- 选择 **深度重构模式** 进行迁移、混合架构或模块边界变更

## 快速推荐模式

在以下情况下使用此模式：
- 范围是一个功能或屏幕
- 约束条件足够清晰，可以推荐一个主要模式
- 用户主要需要一个推荐、脚手架或审查清单

交付：
- 适配结果（`fit` 或 `mismatch`）
- 基于请求的 1-2 个理由
- 选择的参考文件
- 针对功能的具体结构、状态、依赖、异步和测试指导

## 深度重构模式

在以下情况下使用此模式：
- 请求跨越多个模块或屏幕
- 代码库已经混合了架构
- 用户正在从一种模式迁移到另一种模式

交付：
- 当前状态评估
- 目标架构推荐，包含适配或错配结果
- 带有边界变更的增量迁移路径
- 过渡过程中的风险、权衡和验证点

## 架构路由器

如果用户明确指定了架构，将其视为初始候选方案并在提交前进行适配检查：
- 验证 UI 堆栈适配（SwiftUI/UIKit/mixed）、最小部署目标、状态复杂度、效果编排需求、团队熟悉度和现有代码库约定
- 如果适配，继续使用请求的架构
- 如果与关键约束错配，明确解释错配并推荐 `references/selection-guide.md` 中的最接近适配替代方案
- 如果用户仍然坚持错配的架构，采取风险缓解计划并 upfront 说明风险

架构参考映射：
- MVVM（屏幕级状态与轻量级绑定）→ `references/mvvm.md`
- MVI（无框架依赖的 reducer 风格状态机）→ `references/mvi.md`
- TCA（可组合功能与严格的效果编排）→ `references/tca.md`
- Clean Architecture（严格的层和可替换的基础设施）→ `references/clean-architecture.md`
- VIPER（具有明确角色分离的大型 UIKit 模块）→ `references/viper.md`
- Reactive（Combine/RxSwift 流量密集型功能）→ `references/reactive.md`
- MVP（UIKit 被动视图与 presenter 驱动的渲染）→ `references/mvp.md`
- Coordinator（导航流和深度链接）→ `references/coordinator.md`

共享参考（在相关时与选定的演练方案一起加载）：
- `references/concurrency.md`：取消、过期响应防护以及演练方案片段使用的 `userMessage(for:)` 错误映射约定；在编写或审查异步代码时加载
- `references/observation.md`：`@Observable` 与 `ObservableObject` 根据部署目标；在连接 SwiftUI 状态时加载

当最佳适配结合多种模式时，遵循 `references/selection-guide.md` 中的 **组合架构**，阅读两个演练方案，并在提供文件结构或代码之前说明每个边界由哪种模式拥有。

## 分析现有代码库（适用时）

当代码已存在时：
- 检测当前架构和 DI 风格
- 记录并发模型（async/await、Combine、GCD、混合）
- 将推荐与本地约定对齐

## 安全边界

- 不要强制为小功能切换架构，当当前本地模式仍然合理时
- 除非错配严重到足以证明需要变更，否则保留现有约定
- 除非用户明确接受该权衡或代码库已经使用，否则不要引入新的框架依赖，如 TCA
- 优先选择最小的架构变更，以清晰解决请求
- 保持指导架构特定；除非模式之间的边界明确，否则不要混合演练方案
- 对于组合模式，避免合并职责：首先确定主要边界，然后仅将次要演练方案应用于其关注点

## 生成具体交付物

阅读选定的架构参考，将其指导转换为针对用户请求的交付物：

- **文件和模块结构**：特定于功能的目录布局和文件名
- **状态和依赖边界**：具体类型、协议和注入点
- **异步策略**：取消、actor 孤立和错误路径
- **测试策略**：要测试的内容、如何模拟依赖项和示例测试结构
- **迁移路径**（用于重构）：从当前架构迁移到目标架构的增量步骤
- **UI 堆栈适配**：为所选架构的 SwiftUI 和 UIKit 指导应如何不同

## 输出要求

- 将推荐范围限制在请求的功能或审查任务。
- 优先使用基于协议的依赖注入和显式状态建模。
- 标记现有代码中的反模式并提供直接修复。
- 在所有异步流中包含取消和错误处理。
- 对于明确的架构请求，包含一个简短的适配结果（`fit` 或 `mismatch`）和 1-2 个理由。
- 对于错配情况，包含一个最接近适配的替代方案、为什么它更好地匹配声明的约束，以及一个权衡。
- 在编写代码时，仅包含与任务相关的模式——不要倾倒整个演练方案。
- 将参考片段默认视为说明性；如果用户请求可运行代码，则仅添加完整的编译脚手架。
- 仅提出最低阻塞问题；否则， upfront 做出明确假设。
- 在审查 PR 时，使用架构特定的清单并指出具体的违规行为，附带行级修复。

## 验证清单

在最终确定前：

1. 确认选定的模式与用户的约束和堆栈匹配
2. 确认依赖注入、状态所有权、效果和测试策略已涵盖
3. 在推荐架构变更时，明确指出迁移风险
4. 以所选架构的 PR 审查清单结束，并根据用户的功能进行调整

## 文档 QA 清单

在更新参考时，验证：

1. 章节结构保持一致（默认路径、高级变体、迁移笔记、测试部分有最低标准、PR 审查清单）
2. 片段内部一致且编译可能
3. 跨演练方案链接指向正确的参考文件
4. 术语在选择指南和演练方案中保持一致
