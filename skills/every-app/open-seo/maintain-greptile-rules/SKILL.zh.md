# 维护 Greptile 规则

保持 `.greptile/` 高信号。一个评审发现是评估的证据，而不是自动成为新规则。

## 1. 验证发现

- 在当前代码库中复现或追踪发现，包括相关的调用路径、测试和有意引入的异常。
- 在提出变更前，阅读 `.greptile/config.json`、`.greptile/rules.md` 和 `.greptile/files.json`。
- 区分新引入的风险和相邻的遗留债务。不要编码未经验证的假设或一次性实现细节。
- 代码库的缺失不是政策证据。如果评审者仅因为当前没有示例就推断出偏好，除非所有者明确采纳政策，否则保持 Greptile、代码和 CI 不变。

## 2. 路由到正确的机制

- **一次性 Bug**：修复代码并添加一个聚焦的回归测试。不要添加 Greptile 规则。
- **已验证的确定性政策违规**：优先使用 TypeScript、Oxlint、Knip、聚焦测试或 CI。
- **可重复的、可通过 diff 强制的不变量**：在 `.greptile/config.json` 中添加或细化一个作用域结构化规则。
- **架构、偏好或误报校准**：更新 `.greptile/rules.md`。
- **Greptile 应参考的规范实现**：在 `.greptile/files.json` 中添加一个作用域狭窄的引用。
- **小工作流摩擦**：使用 `papercuts` 技巧并记录在 `.agents/PAPERCUTS.md` 中。

## 3. 应用晋升栏

只有在所有适用检查通过时才晋升发现：

- 它已针对当前代码进行验证。
- 未来的评审者可以通过 diff 和相关调用路径观察到它。
- 它是代码库特定的或显著改进了误报校准。
- 它很可能重复出现，或其影响足够高以证明预防的必要性：授权、安全、计费、数据丢失或跨数据库正确性。
- 现有的 Greptile 上下文和自动化检查已经充分覆盖它。
- 指令可以具体、可衡量、作用范围狭窄，并明确说明合法例外。

如果证据或政策不明确，保持配置和执行不变，并将候选者提交给人进行判断。

## 4. 保守编辑

- 每个结构化规则保持一个连贯的关切，具有稳定的低写字符 ID、严重性和最窄的未来安全作用范围。
- 不要因为当前代码库没有替代方案的零示例就推断永久政策。
- 优先缩小或替换一个嘈杂的规则，而不是叠加更多文本。
- 将代码库特定的规则保存在 `.greptile/` 中。验证并报告最小的 **org-enforced** 仪表板基线是否保护外部贡献、机密、认证、计费、CI 和削弱评审控制的努力。除非用户明确要求，否则不要创建或更改仪表板、MCP 或组织规则，并且不要在那里复制完整的代码库规则集。
- 将对 `.greptile/**`、`AGENTS.md`、`CLAUDE.md`、`.agents/skills/**` 和 `.github/**` 的更改视为需要显式维护者评审的评审控制更改。CODEOWNERS 请求评审；当可用时，分支保护或规则集必须单独要求代码所有者批准。
- 更新所需的最小配置文件集；不要在单独的文档中重复规则体。

## 5. 验证

运行：

```bash
jq empty .greptile/config.json .greptile/files.json
node_modules/.bin/prettier --check .greptile/config.json .greptile/files.json .greptile/rules.md
git diff --check
```

还验证规则 ID 是否唯一、严重性是否有效、每个 `files.json` 路径是否存在，以及独立评审者是否能在新措辞中找到一个明显的误报。

在合并就绪的工作期间，仅评估通过晋升栏的已验证发现。当没有持久性评审差距时，合并就绪的运行不需要更改 `.greptile/`。
