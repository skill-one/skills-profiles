# 纸割

在不影响当前任务的情况下，捕捉瞬间的微小摩擦。
聚合的条目显示了仓库需要清理的地方——因此标准是不同的贡献者会碰到同样的问题，并且仓库可以对此采取行动。

## 两个问题的测试

只有当**两个**都为真时才记录：

1. **对任何人都是可复现的。** 不同的用户在一个干净的检出中，在这个仓库中工作会碰到同样的摩擦。它不是特定于你的沙盒、shell配置、机器、网络或一次性故障。
2. **可以在仓库中修复。** 对仓库代码、配置、脚本或文档的更改可以防止或减少它。

如果任何一个答案是“否”，就继续进行并继续前进——不要记录它。

## 不要记录

- **你环境中的失败。** 沙盒 `EPERM` / `listen` / IPC-socket 错误，被阻塞的网络或 `fetch failed`，权限拒绝，缺少系统工具。那是执行者，不是仓库。
- **你自己的shell错误。** 保留或特殊变量名 (`status`，`path`)，未引用的glob，损坏的登录-shell钩子。修复命令——仓库中没有可以清理的东西。
- **暂时的波动性。** 一个在重试时成功且没有仓库侧原因的命令（网络抖动、挂起的推送、慢速镜像）。
- **你损坏的本地状态。** 切换分支后的部分 `node_modules`，陈旧的dev-server端口，脏缓存。重新运行安装或清理。
- **第三方或beta工具的限制，仓库无法更改**——除非修复是一个值得记录的仓库侧变通方法（那么记录那个变通方法）。
- 产品或代码正确性错误（现在修复或作为实际工作跟踪），以及你完成的工作（那属于任务摘要）。
- 密码、凭证、个人数据、原始客户有效负载或敏感路径。

当某件事失败时，首先问“这是仓库的问题，还是我的/我的环境的问题？” 只有前者是纸割。

## 主动记录

1. 在 `.agents/PAPERCUTS.md` 中搜索等效条目并避免重复。
2. 使用以下格式在 `## Open` 下添加一个未检查的项目：

   ```markdown
   - [ ] `YYYY-MM-DDTHH:MM:SSZ` — `agent` — <摩擦，以及最小的有用修复或变通方法>。
   ```

3. 保持一到两句话：当前示例（命令/错误或受影响的路径），它阻碍了谁或浪费了多长时间，以及最小的有用仓库侧修复。先说摩擦，而不是你正在做什么。
4. 继续原来的任务。不要把纸割扩展成无关的工作。

使用UTC时间戳和简短的代理标签 (`codex`，`claude`，`human`)。只有在它有助于未来的分派时才添加PR或任务标识符。

## 审查或解决

只有在我整个会话或用户明确要求时才进行挖掘或进行广泛审查。

对于审查或优先级请求，请检查并推荐；不要编辑日志或实施修复，除非用户也要求清理或实施。使用相同的分派进行授权清理：

1. 对每个打开的条目重新运行两个问题的测试；推荐删除失败的条目（环境/shell/波动性噪音滑入）。
2. 去重并分组相关条目。
3. 检查每个幸存的纸割是否仍然可复现。区分复现的失败、源检查和您无法验证的历史报告。
4. 优先考虑当前影响与审查和维护成本。优先考虑现有命令或简短的文档修复，而不是新的帮助程序、依赖项或设置钩子。将假设性改进推迟到具体需求出现时。
5. 对于授权清理，删除噪音，合并重复项，并实施约定的修复。将已修复的项目移至 `## Resolved`，检查它们，并附加解决日期或提交。将延迟报告与可操作的打开工作分开，并说明原因和具体触发条件。将真实错误路由到正常的issue/修复工作；将重复的审查政策差距通过 `maintain-greptile-rules` 路由。

为真正解决的纸割保留有用的历史记录；不要仅仅为了使文件更短而删除它们。（从不属于噪音——见步骤1——不同：删除它。）
