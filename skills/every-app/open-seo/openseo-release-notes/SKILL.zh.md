# OpenSEO 版本发布说明

为这个仓库端到端地发布一个版本。交付成果包括 `package.json` 中的版本号更新、一个新的 `release-notes/v<版本号>.md` 文件，以及对 `origin/main` 的一个标题为 `release: v<版本号>` 的拉取请求。

## 1. 更新版本号

- 查看 `package.json`。如果分支已经更新了 `version`，则将其视为真实来源，不要更改它。
- 否则，更新补丁版本（例如 `0.0.19` → `0.0.20`）。如果明确要求，才更新主版本号或次版本号。

## 2. 收集自上次发布以来的变更

- 查找最新标签：`git tag --sort=-creatordate | head -1`。验证分支是否与 `origin/main` 保持同步（`git fetch origin main && git log HEAD..origin/main --oneline` 应该为空；如果不为空，请标记它）。
- 列出提交记录：`git log <last-tag>..HEAD --oneline`。你也可以运行 `pnpm release:notes` 获取原始提交记录——仅将其用作候选变更的检查清单，绝不能作为草稿的结构（其 Improved/Changed/Docs 部分绝不能出现在说明中）。
- 对于每个提交，获取 PR 正文和作者（`gh pr view <num> --repo <repo> --json title,body,author`）——合并提交的主题可能已过时。提交主题中的 `(#NN)` 可以引用**任何**仓库：首先尝试 `bensenescu/open-seo`（源仓库），然后回退到 `every-app/open-seo`（公开仓库）——外部贡献者的 PR 和他们的用户名存在于公开仓库中。没有 `(#NN)` 的提交可能仍然是外部贡献者的公开 PR（`gh pr list --repo every-app/open-seo --state merged --author <login>`）；检查 `git log --format=%an` 获取作者。当 PR 正文和提交主题不一致时，验证声明（特性在合并前会被回滚）。
- 在每个变更旁边记录 PR 作者的 GitHub 用户名，以便在项目符号中感谢他们。

## 3. 起草说明

编写 `release-notes/v<版本号>.md`。**`release-notes/v0.0.24.md` 是标准的示例**——请参考它（v0.0.25 及以后的版本遵循相同风格）；v0.0.23 及之前的版本是旧的详细风格，永远不要模仿它们。说明是一个可扫描的摘要，不是文档：整个文件适合在一个屏幕上显示（包括标题大约 15 行），每一行都应有其存在的理由。

格式：

- 顶部行：一个片段命名发布的 2-3 个亮点（"GSC UI、改进的应用布局和应用代理的 Beta 版。"）。不是 "本次发布带来…" 的句子。
- 部分：`## 新增` 和 `## 修复` 仅此两项。没有 "改进" 部分——改进要么是标题级别的（新增），要么被删减。
- **新增项目符号命名特性；它们不推销它。** 每个项目符号一行短句（"重新设计了应用布局"，"在应用中获取 GSC Insights"）——没有破折号特性导览，没有 "所以你可以…" 的利益说明，没有列出特性影响的全部内容。如果名称本身不明确，最多有一句简单的上下文。
- 最多**每个特性一个子项目符号**，一行短句：最实用的细节、一个要求（"需要 `OPENROUTER_API_KEY`"）或一个预期设定者。
- **将初步特性标记为 "(Beta)"** 并诚实设定预期，包括指出当前的更好替代方案。预期设定者位于顶级行后的破折号之后（"(Beta) 应用代理 - MCP 仍然推荐，但我们将在夏季期间改进它。"），保留子项目符号的位置用于要求或细节。
- 修复：3-5 个项目符号，每个项目符号一个简单句，仅修复用户可能遇到并会识别的 Bug（"Claude 在 AI 搜索中回答工作正常。"）。没有错误代码、状态代码、模式/基础设施词汇或机制。如果有超过四个符合条件，保留核心流程（搜索、审计、跟踪、MCP 回答）中遇到的修复，优先删除用于恢复自造状态的修复（重新添加、取消存档、刷新）。
- **感谢贡献者。** 在项目符号末尾加上 `— thanks @handle` 仅用于外部贡献者——绝不要用于维护者自己的 PR（`bensenescu`）。感谢出现在顶级项目符号中，而不是子项目符号。多个贡献者：`— thanks @a, @b`。
- 结尾：`Full Changelog: https://github.com/every-app/open-seo/compare/v<prev>...v<version>`

筛选——这是核心工作。激进地删减；完整的 Changelog 链接涵盖了长尾：

- 仅产品本身的变更——应用、MCP 工具、运行 OpenSEO 的人实际使用的 SEO 数据/特性。每个项目符号的测试标准：**自托管者在使用产品时会注意到这个变更吗？** 抽象的关心（新的后端选项、提高的容量）是不够的。
- 不要提及：
  - **营销网站 (`web/`) 变更**——着陆页、文案、定位、博客。
  - **定价 / 计划 / 订阅 / 账单**——付费墙、免费试用/计划变更、Autumn 配置。托管商业问题，与自托管者无关。
  - **仅限引导流程的变更**——注册/引导聊天、配置步骤、升级轨道、电子邮件验证 UX。不是产品功能，即使规模很大。
  - **托管应用内部和元数据**——分析、规格/ADRs、CI、重构、依赖更新。
  - **对用户不可见的工作，即使与产品相关**——安全加固、提高的容量/限制、稳定性/内存/性能修复、数据库/后端选项和迁移。阅读说明的用户应该能从使用产品中识别每一行；如果他们只在配置文件或不再发生的故障中注意到，请删除它。
- 在包含和删除之间犹豫时，删除。一个可读的 4 个项目符号的新增比一个不可读的 10 个项目符号的新增更好。
- 绝不编造特性——每个声明都必须追溯到提交。
- 项目符号中的数字通常是推销——删除它们；如果有一个确实承载负载，引用保守的、典型的数字，绝不要 cherry-picked 的最佳情况。

## 4. 审查和验证

1. 使用以下内容生成一个审查子代理：草稿、上述指南、每个提交的详细信息以及仓库访问权限。它返回编号的审查评论，引用每个违反的指南。其职责包括**详细性**：标记任何推销而非命名的项目符号、任何第二个子项目符号、任何带有机制词汇的修复项目符号，以及任何将文件推过一屏的内容。
2. 对于每个实质性评论，并行生成一个验证子代理，对抗性地检查评论与实际提交/代码和裁决 APPLY / APPLY-MODIFIED / REJECT。
3. 仅应用已验证的评论。

## 5. 打开 PR

- 在名为 `claude/v<版本号>` 的分支上提交版本号更新、发布说明和任何技能变更（如果当前分支已经遵循此模式，则使用当前分支）。
- 推送到 `origin` 并对 `main` 打开一个标题为 `release: v<版本号>` 的拉取请求。PR 正文：发布说明内容。
- 不要标记或发布 GitHub 发布——合并后才会发生。合并后，运行 `pnpm release:publish`。它从 `package.json` 中读取版本号，并将匹配的 `release-notes/v<版本号>.md` 发布到 `every-app/open-seo`。
- 等效命令是：

  ```sh
  gh release create v<version> \
    --repo every-app/open-seo \
    --title v<version> \
    --notes-file release-notes/v<version>.md
  ```
