# 合并就绪

将当前工作推进到仅剩维护者自行审查和合并的步骤。交付成果是一个已推送的分支，包含干净的 `pnpm ci:check`，沿途的检查点提交，以及一个包含高层级描述和审查说明的已打开的 PR。

**永远不要合并 PR。维护者总是最后审查。**

## 0. 确定起点

这项技能与功能工作相结合——它不仅仅是审查通过：

- **与构建请求一起调用**（"构建 X，使其合并就绪"）：首先实现功能/修复，边提交边进行，然后继续下方步骤。审查阶段涵盖分支相对于 `origin/main` 的所有更改，而不仅仅是最后一次编辑。
- **在现有工作上调用**（"使此分支合并就绪"）：直接从步骤 1 开始。范围是 `git diff origin/main...HEAD` 以及任何未提交的内容。

## 1. 与主分支同步

- `git fetch origin main`。如果分支落后，合并 `origin/main` 并解决冲突（对于分支未有意更改的代码，优先采用主分支的版本）。
- **检查点**：在开始审查之前提交合并，以便冲突解决可以单独审计，与审查修复分开。

## 2. 多轴子代理审查

并行生成独立的审查子代理，每个轴一个，每个子代理都获得仓库访问权限和完整的分支范围：

- 已提交的更改：`git diff origin/main...HEAD`
- 已暂存的更改：`git diff --cached`
- 未暂存的更改：`git diff`
- 未跟踪的文件：`git status --short`，然后读取每个范围内的未跟踪文件

不要让未提交或新创建的文件仅仅因为不在 `origin/main...HEAD` 中而逃脱审查。

1. **不必要的复杂性**——薄包装器、无用的间接引用、单用途抽象、针对不可能状态的防御性保护、过时的配置。这个代码库故意保持简单。
2. **安全性**——新端点的授权（组织/项目范围）、SSRF、注入、密钥处理、任何用户输入形状的达到 D1/R2/外部 API 的内容。
3. **计费和计量**——用户可能在没有计费的情况下触发 DataForSEO/提供商支出、计费但失败的路径、重试/循环放大、每调用成本异常高的端点。信用通过 Autumn 计费；未计费支出是收入泄漏。
4. **库和项目惯用法**——TanStack（Router/Query/Start）按惯用法使用；模式与代码库其余部分已经这样做的模式匹配（共享应用程序/提供者错误边界、数据库/模式约定、现有组件模式）。在存在既定模式的情况下标记新颖模式。
5. **按感觉编码的冗余**——遗留的脚手架、记录编辑历史的过时评论、console.logs、无所有者的 TODO、附近复制粘贴的近似重复、未使用的文件/导出。

每个审查者返回包含文件:行号、严重性（`blocker` / `should-fix` / `nitpick`）和一句话理由的发现。明确告诉审查者：这是一个早期阶段的产品——不要追逐理论上的边缘情况；将任何有争议的内容标记为 `nitpick`。

## 3. 验证发现——永远不要盲目接受

对于每个 `blocker` 和 `should-fix` 发现，并行生成验证子代理，这些子代理以对抗性方式检查发现与实际代码的匹配情况，并给出 **APPLY / APPLY-MODIFIED / REJECT** 的理由。丢弃被拒绝的发现。Nitpicks 不需要验证——它们是报告的，不一定是修复的。

### 保留审查学习成果

验证后，路由持久性学习成果，而无需强迫每次审查都改变策略：

- 如果一个 **APPLY** 或 **APPLY-MODIFIED** 发现揭示了一个现有 `.greptile/` 上下文和 CI 没有捕获的反复出现或高风险仓库不变量，使用 `maintain-greptile-rules` 并应用其提升门槛。
- 将一次性错误作为代码修复和回归测试。将确定性机械检查放入 CI 或 lint 而不是 Greptile。
- 当出现小的工具、文档或工作流程挫败时，使用 `papercuts` 将其追加到 `.agents/PAPERCUTS.md`；不要因为修复它而偏离合并就绪工作。

## 4. 修复、检查、循环

- 应用已验证的 `blocker`/`should-fix` 修复。仅在微不足道且明显正确时应用 nitpicks；否则将它们列在 PR 中供维护者判断。
- **检查点**：将修复分组提交（例如，每个轴或每个问题一个提交），以便修复历史可以单独审查。
- 运行 `pnpm ci:check`（prettier、knip、tsc、oxlint）。修复失败并重新运行，直到干净。如果修复是重大的（不是格式化/lint），运行该更改的快速重新审查。
- 循环直到 ci:check 通过且所有已验证的发现都得到解决。

## 5. 推送并打开/更新 PR

- 推送分支。如果没有 PR，则打开一个针对 `main` 的 PR；否则更新现有 PR 的描述。
- PR 描述要求：
  - **高层级**——更改内容和原因，供人类快速浏览。没有文件路径，没有每个文件的变更日志。
  - **如何审查**——一个简短的有序指南：首先查看什么，哪些是风险/判断区域，哪些故意排除在范围之外。
  - **审查笔记**——未修复的 nitpicks 和任何值得第二次意见的 `REJECT` 裁决，清晰标记。
- 反馈：PR 链接、一段摘要，以及任何仍需要维护者判断的内容。不要合并。
