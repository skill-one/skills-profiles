# Diffity Tour 技能

您正在创建一个引导式代码巡游——这是一个逐步的、带有旁白的代码库漫游，用于回答用户的问题或解释功能的工作原理。巡游在浏览器中打开，侧边栏显示旁白和高亮代码部分。

## 参数

- `question` (必需): 用户的提问、主题、概念或 GitHub PR URL。示例：
  - `/diffity-tour 认证是如何工作的？`
  - `/diffity-tour 解释请求生命周期`
  - `/diffity-tour 评论是如何存储和检索的？`
  - `/diffity-tour 闭包`
  - `/diffity-tour React hooks`
  - `/diffity-tour 在我合并之前带我走一遍这个分支`
  - `/diffity-tour https://github.com/owner/repo/pull/123`

当参数是 **GitHub PR URL**（匹配 `github.com/owner/repo/pull/N`）时，巡游会自动锁定到 **Review 模式**——PR 的差异驱动范围，结论必须包含 PR-flags 列表。见下文的 **Review 巡游** 部分。

## CLI 参考

```
{{binary}} agent tour-start --topic "<text>" [--body "<text>"] --json
{{binary}} agent tour-step --tour <id> --file <path> --line <n> [--end-line <n>] --body "<text>" [--annotation "<text>"] --json
{{binary}} agent tour-done --tour <id> --json
{{binary}} list --json
```

## 前置条件

1. 检查 `{{binary}}` 是否可用：运行 `which {{binary}}`。如果未找到，{{install_hint}}。
2. **如果参数是 GitHub PR URL**:
   - 检查 `gh` 是否已安装并认证：运行 `gh auth status`。如果未认证，停止并要求用户运行 `gh auth login`。
   - 验证当前仓库是否与 PR 的仓库匹配：运行 `gh repo view --json nameWithOwner -q .nameWithOwner` 并确认它是否与 URL 中的 `owner/repo` 匹配。如果不匹配，停止并告诉用户他们需要位于 PR 的仓库克隆中——diffity 无法为未检出的仓库的 PR 进行巡游。
   - 使用 Bash 工具以 `run_in_background: true` 运行 `{{binary}} --no-open <pr-url>` 对 PR 启动 diffity。**`--no-open` 标志必须出现在 URL 之前**——commander 的 `passThroughOptions()` 会将位置 URL 之后的任何标志 slurp 到 refs 数组中，跳过 PR 处理并产生 "unknown ref" 错误。此命令将 PR 的分支本地检出并启动 diff 范围的会话。等待 2 秒钟，然后运行 `{{binary}} list --json` 获取端口。您**不需要**另一个 tree 实例——diff 会话支持 `agent tour-*` 命令。
3. **否则**，确保一个 tree 实例正在运行：运行 `{{binary}} list --json`。
   - 如果没有实例在运行，启动一个：使用 Bash 工具以 `run_in_background: true` 运行 `{{binary}} tree --no-open`，等待 2 秒钟，然后运行 `{{binary}} list --json` 获取端口。

## 说明

### 首先选择模式

在执行任何操作之前，决定此巡游属于哪种模式。技能的其余部分将基于此选择分支——范围、研究方法和输出形状都因模式而异。在调用任何工具之前完成此操作。

**快捷方式**：如果参数是 GitHub PR URL（匹配 `github.com/owner/repo/pull/N`），则跳过决策——它被锁定到 **Review 模式**。

| 模式 | 当用户询问...时使用 | 范围由...限定 | 目标步骤 |
|---|---|---|---|
| **Focused** | 一个狭窄的 "X 是如何工作的？" 问题 | 一个代码路径 | 3-6 |
| **Feature** | "这个功能是如何工作的？" | 一个功能边界 | 6-10 |
| **System** | "整个系统是如何工作的？" | 架构 | 8-15 |
| **Concept** | 关于一个编程概念 | 代码中的示例 | 3-8 |
| **Review** | 在合并前审计分支/PR/功能 | `git diff <base>..HEAD` | 可变——覆盖所有有意义的更改 |

引导用户进入每种模式的触发词：
- **Focused**: "X 如何验证", "带我走一遍 Y 端点"
- **Feature**: "认证是如何工作的", "解释评论系统"
- **System**: "应用程序是如何工作的", "给我架构概述"
- **Concept**: 单独的概念名称（`closures`, `React hooks`, `async/await`, `generics`）
- **Review**: "在我合并之前", "审查这个分支", "带我走一遍整个功能", "审计这个 PR", "我即将合并"

如果多种模式都适用，优先选择更具体的一种（Review > Concept > Focused > Feature > System）。如果您确实无法确定用户想要什么，请在研究之前询问——不要猜测并产生错误的巡游形状。

模式更改此技能适用的部分：
- **Concept 模式** → 阅读 **Concept 巡游** 部分下；研究不同（搜索示例，而不是跟随流程）并且步骤进展也不同。
- **Review 模式** → 阅读 **Review 巡游** 部分下；范围由 diff 驱动，线程逐个遍历，结论必须包含 PR-flags 列表。
- **Focused / Feature / System 模式** → 默认的 Phase 1-3 说明直接适用。

### Phase 1: 范围和研究

在创建任何巡游步骤之前，您必须深入理解用户问题的答案。

1. **确认范围**。您选择的模式设定了大致的步骤数量（见上文的 **选择模式**）。如果用户的问题过于宽泛，无法适应该大小（例如，"解释一切" 落入 System 模式），请在大脑中缩小到最重要的方面，并在引言中说明您涵盖的内容和排除的内容。

2. **确定受众**。考虑用户提问的方式：
   - "X 是如何工作的？" → 假设有人**不熟悉这个代码库**——解释架构决策，而不仅仅是代码机制
   - "X 为什么做 Y？" → 假设有人**正在调试或审查**——关注推理和边缘情况
   - "带我走一遍 X" → 假设有人想要**完整的画面**——要彻底，包括上下文

3. **研究代码库**。彻底阅读相关的源文件。从入口点跟随代码路径到完成。

   对于 Review 巡游尤其如此，还阅读 `git log --reverse <base>..HEAD` 并打开任何提交消息描述非明显修复、重构或防御性更改的提交。作者的自己的叙述通常是*为什么*的最佳来源——远比仅从代码中推断意图要好。在步骤体中引用或概述提交推理，如果它能阐明设计决策（例如，"提交 `abc1234` 在一次生产事件后引入了这个检查..."）。

   **巡游 GitHub PR 时，使用 `gh` 获取元数据和 diff:**
   - `gh pr view <url> --json title,body,baseRefName,headRefName,commits,files` — PR 标题、正文、基础/头分支、提交列表和更改文件列表。PR **正文**通常包含最丰富的 "为什么"（设计上下文、截图、作者考虑的权衡）——在引言中引用或总结它。
   - `gh pr diff <url>` — 定义巡游范围的统一 diff。使用此 diff 确认完整表面，而不仅仅是您在 `git diff` 中看到的。
   - 使用 PR 的 `baseRefName`（从上面的 JSON 中获取）作为 diff 基础——默认不是 `master`/`main`。命令如 `git log --reverse <baseRefName>..<headRefName>` 按作者顺序遍历 PR 的提交。
   - 源文件可以从工作区读取，因为 `{{binary}} <pr-url>` 已经将 PR 分支本地检出。

4. **确定讲述故事的关键位置**——需要某人看到的文件和行范围，以理解答案。

5. **注意配置依赖项**。如果行为基于环境变量、功能标志、配置文件或运行时条件而变化，请记录这些。它们必须在巡游中说明，以便读者了解 "当 X 配置时会发生这种情况，但如果 Y 设置，流程会在此处不同"。

6. **计划一个逻辑步骤序列**，逐步建立理解。每个步骤都应该自然地引导到下一个步骤。

**选择步骤的指南:**
- 从真实的入口点开始——外部输入到达的地方（HTTP 路由、CLI 命令、计划任务、webhook）。配置、模式、常量和辅助函数是**不是**入口点；它们是流程的依赖项。
- 刚好及时引入基础。当流程第一次读取模式时，巡游模式。当它第一次调用辅助函数时，巡游辅助函数。当它第一次引用配置值时，巡游配置。不要在流程开始之前预先加载一堆基础部分。
- 最多一个 "定向" 步骤（例如，显示所有端点的路由表）可以 precede 入口点。其他所有内容都应该由读者刚刚看到的东西驱动。
- 按照实际发生的顺序跟随执行路径。
- 只包括对理解必不可少的地点——跳过样板。
- 结束在最终结果（发送响应、持久化数据、渲染 UI）。
- 每个步骤应涵盖一个概念或代码部分。
- 尽可能包含具体示例（例如，"当用户运行 `{{binary}} main` 时，这将变成..."）。

**自上而下，而不是自下而上**。巡游反映了代码在运行时的行为，而不是它是如何构建的。**不要**按配置→模式→辅助函数→路由→动作的顺序巡游。按路由→动作→（查询读取它，因此模式出现）→（处理程序引用它，因此配置出现）→（调用它，因此辅助函数出现）的顺序巡游。读者在每次引入新内容时保持上下文更好。读者应该感觉他们坐在您旁边，您正在跟踪一个真实的请求，而不是在演示开始前坐下来听架构讲座。

**处理跨模块流程**：当代码路径进入库、实用模块或深度嵌套抽象时，决定是否跟随：
- **跟随它**，如果那里的逻辑对于理解答案至关重要（例如，一个转换请求的自定义中间件）
- **总结它**，如果模块做的是标准或众所周知的事情（例如，"这调用 Express 路由器，它匹配路径并调用我们的处理程序"）——在步骤体中提及它所做的工作，而无需为它创建单独的步骤
- **跳过它**，如果它是纯样板或管道（例如，重新导出、只有类型的文件）

**跨许多文件应用的模式**。当一个更改在 N 个相似的调用位置复制（例如，相同的守卫添加到 8 个处理程序、每个路由注册相同的中间件），**不要**创建 N 个步骤。在最具代表性的文件上创建一个步骤，并带有完整上下文，然后在步骤体中将其他调用位置作为 goto 链接列出（"相同的守卫也添加到 X、Y、Z"）。一个概念，一个步骤——巡游应该教读者一次模式，而不是 N 次。例外：如果一个应用与其他应用略有不同（例如，在传输流程中调用两次，或使用不同的参数），请为这一个单独的步骤花费一个步骤。

### Phase 2: 创建巡游

巡游 UI 有一个专用的解释面板。引言（来自 `tour-start --body`）显示为**步骤 0**——读者首先看到的，填充整个面板。每个后续步骤在其解释面板中显示其叙事，并附带高亮代码。由于面板有充足的空间，请编写丰富、详细的解释。

1. **开始巡游**，使用简短的标题和引言正文：
   ```
   {{binary}} agent tour-start --topic "<简短标题>" --body "<引言>" --json
   ```

   `--topic` 显示在巡游面板标题中——保持它为 **3–6 个词**（例如，"认证流程"，"路由是如何工作的"，"评论系统架构"）。**不要**使用用户的完整问题作为主题。

   **编写引言正文（步骤 0）:**
   这是读者首先看到的东西，并填充整个解释面板。使用此空间进行彻底的架构概述，在深入代码之前为读者设置一切。包括：
   - 涉及的关键组件/包/模块及其职责
   - 它们如何连接——数据流、调用链或依赖关系
   - 读者应该了解的关键抽象或模式
   - 使用粗体文本的摘要流程图（例如，**CLI 参数 → git diff → 解析器 → JSON API → React 渲染**）
   - **配置上下文**——如果功能的行为取决于配置、环境变量或功能标志，请在此处提及它们，以便读者知道巡游假设的模式/状态

   如果您缩小了广泛的问题，请说明您涵盖的内容："此巡游专注于 OAuth 登录流程。令牌刷新和会话管理是相关的，但分别涵盖。"

   使用丰富的 markdown 格式化——段落、粗体、`code`、表格、代码块。这不是一个涵盖巡游将涵盖的内容的目录；它是一个独立的概述，用于引导读者。

   从 JSON 输出中提取巡游 ID。

2. **按顺序添加步骤**。对于每个步骤：
   ```
   {{binary}} agent tour-step --tour <id> --file <path> --line <开始> --end-line <结束> --body "<叙述>" --annotation "<简短标签>" --json
   ```

   **编写步骤内容:**

   - `--file`: 相对于仓库根的路径（例如，`src/server.ts`）
   - `--line` / `--end-line`: 要高亮的精确行范围。保持它专注于相关部分。
   - `--annotation`: 一个简短标签（3-6 个词），显示为步骤标题。将其视为章节标题。
   - `--body`: 在解释面板中显示的叙事。这个空间很充足——使用它编写使用 markdown 的彻底解释：

   **在提交步骤目标之前进行验证**。在调用 `tour-step` 之前，验证 `--file` 路径是否可以从仓库根读取，并且您描述的函数或块确实位于宣布的 `--line`/`--end-line` 范围——读取范围，而不是依赖会话早期的内存。相同的规则适用于体中的每个 `goto:` 链接：一个损坏的 goto 链接比没有链接更糟，因为读者信任它，并且在没有错误信号的情况下被带到错误的地方。如果您不确定确切的行，请使用普通反引号代码，而不是 goto 链接。

   **步骤体结构**。每个步骤体应按以下顺序遵循这个弧：
   1. **过渡**（1 句话）：连接到前一个步骤——见下文的示例。
   2. **解释**（主体）：这个代码做什么以及*为什么*它这样结构——设计决策、权衡、具体示例。如果范围分成不同部分，使用子高亮 (`focus:X-Y`)。
   3. **要点**（1-2 句话）：一个陷阱、边缘情况或 "如果...会触摸..." 指针。

   没有过渡的步骤体感觉被抛入其中；没有要点的步骤体感觉不完整。每个步骤体大约为 **150-300 个字**——只有在逻辑真正要求时才更长。如果您的草稿超过 400 字，该步骤可能试图涵盖两件事；考虑将其拆分。

**执行：**
- 使用散文段落进行写作，并在有助于理解的地方补充结构化内容
- 使用 `code` 表示函数名、变量、引用、命令。当引用一个存在于**已知文件和行号**中的函数、类或代码符号时，将其制作成一个**跳转链接**，以便读者可以点击跳转。语法：`` [`symbolName`](goto:path/to/file.ts:startLine-endLine) `` 或 `` [`symbolName`](goto:path/to/file.ts:line) `` 用于单行。这些会渲染为可点击的内联代码，导航到文件并高亮目标行。示例：`` [`handleDragEnd`](goto:src/KanbanContent.jsx:42-58) ``。使用普通反引号代码表示通用术语、CLI 命令或未在代码库中定位的符号。
- 使用**粗体**强调引入的关键概念
- 解释代码存在的原因及其背后的设计决策，而不仅仅是它做了什么
- 使用具体示例："当你运行 `diffity main` 时，这行调用 `normalizeRef('main')`，它计算 `git merge-base main HEAD`"
- 使用表格表示映射（输入→输出、引用→git 命令）
- 使用代码块表示数据结构或命令输出
- 将每个步骤与引言中的整体图景联系起来
- **指出边缘情况和注意事项** — 如果存在非明显行为、已知限制或"看起来错误但故意如此"的时刻，请标记它。这些是在后期维护此代码时容易让人困惑的地方。
- 对于大范围高亮，使用**子高亮链接**来专注于步骤内的特定子部分。语法：`[label](focus:startLine-endLine)`。这些会渲染为可点击的芯片，将高亮移动到指定的行。示例：

  ```markdown
  首先，该函数验证其参数：
  [参数验证](focus:15-22)

  然后，核心转换处理每个条目：
  [核心转换](focus:25-40)

  最后，在返回之前缓存结果：
  [结果缓存](focus:42-48)
  ```

  当一个步骤涵盖 30+ 行，并且叙述自然地分解为不同部分时，使用子高亮。行范围必须在步骤的 `--line` / `--end-line` 范围内。

**Mermaid 图表：**
当概念通过视觉方式更容易理解时 — 架构关系、数据流、状态机、时序图 — 包括一个 mermaid 代码块。不要强迫每个步骤都使用图表；仅在它们确实澄清解释时使用。良好候选者：
- 引言（步骤 0）概述：一个显示组件如何连接的流程图
- 涉及多组件交互或请求流的步骤
- 状态机或生命周期转换

选择最合适的图表类型：
- `graph TD/LR` 用于架构、模块依赖、数据流
- `sequenceDiagram` 用于调用链、请求/响应流
- `stateDiagram-v2` 用于状态机、生命周期转换
- `classDiagram` 用于类型层次结构、结构关系
- `flowchart` 用于算法、决策树、控制流

保持图表简洁（少于 ~12 个节点）。它们在游览面板中内联渲染。

**不要：**
- 写一堵墙式的项目符号 — 使用带格式的散文段落
- 只描述语法 — 解释设计决策
- 重复高亮代码中可见的信息
- 在步骤主体中使用标题（注释作为标题）
- 强迫每个步骤都使用图表 — 仅在它们确实有帮助时才添加
- 在不将其与上一个步骤联系的情况下开始一个步骤

3. **添加一个结论步骤。** 游览的最后一个步骤应该总结一下。重用最后一个有意义的步骤的文件/行范围，并编写一个正文，其中包含：

   - **总结完整流程** 在 2-3 句话中 — 现在读者已经看到了每一部分，给他们一个可以继续前进的缩放后的心智模型
   - **突出关键设计决策** — 这个代码中有 2-3 个最重要的架构选择是什么？为什么做出这些选择？
   - **指出扩展点** — 如果有人想要修改或扩展此功能，他们会从哪里开始？他们会触摸哪些文件？
   - **注意相关区域** — 提及 1-2 个相关的功能或流程，这些与当前功能相关联，以便读者知道下一步去哪里探索

   使用注释 `"Putting It Together"` 为此步骤。

4. **完成游览：**
   ```
   {{binary}} agent tour-done --tour <id> --json
   ```

### 第三阶段：在浏览器中打开

1. 从 `{{binary}} list --json` 获取运行实例端口。
2. 打开游览：`open "http://localhost:<port>/tour/<tour-id>"`（或适用于用户操作系统的适当命令）。
3. 告诉用户游览已准备好：

   > 您的游览已准备好 — 检查您的浏览器。

## 概念游览

当用户询问的是**编程概念**而不是功能或流程（例如："闭包"、"泛型"、"错误处理模式"）时，游览成为一个教学工具。

**概念游览与功能游览的区别：**
- **研究阶段**：不是遵循执行路径，而是在代码库中搜索该概念的真实实例。使用 grep、glob 和文件读取来查找模式。广泛搜索 — 闭包可能作为回调、工厂函数或事件处理器出现。
- **示例选择**：选择 3-8 个涵盖不同方面的示例，从简单到复杂。不要展示 5 个相同的用法示例。
- **引言正文**：为可能从未遇到此概念的人编写。包括：无术语的定义、它存在的原因（它解决了什么问题）、心智模型或类比、以及要查找的句法线索。
- **步骤正文**：每个步骤通过一个真实示例教授一个方面。结构如下：引导读者在代码中定位 → 指出概念的实际应用 → 解释为什么在此处使用 → 关键要点。在第一次出现术语时内联定义术语。
- **进展**：第一个示例应该让读者想"哦，这就是全部？"最后一个示例应该是最复杂的用法。
- **总结步骤**：回顾 3-5 个关键规则，列出 2-3 个常见错误，建议学习下一个相关概念。
- **稀疏代码库**：如果少于 3 个真实示例存在，则创建临时的教学片段文件，将它们用作游览步骤（明确标记为独立示例），并在创建游览后删除它们。

所有其他游览指南（过渡、goto 链接、子高亮、mermaid 图表、结论）仍然适用。

## 审阅游览

当用户请求在合并前**审阅分支、PR 或功能**时，将游览组织为通过用户面流程的请求跟踪，而不是架构巡游。这是最有可能产生读者可以采取行动的审计的模式。

**审阅游览与功能游览的区别：**
- **从 diff 开始范围**：读者想要审计正在更改的内容。首先阅读 `git diff <base>...HEAD`（以及相关提交）以了解完整表面区域。每个有意义的更改都应该被访问；仅跳过纯样板文件。
- **引言结构**：用段落陈述功能，然后包括一个移动部件表（区域→在哪里→目的）、一个高级流程图和一个简短的配置上下文块（环境变量、新常量、行为默认值）。引言是读者构建他们将要导航的地图的地方。
- **允许一个定向步骤**：如果存在路由表、webhook 开关或其他端点目录，它可以作为步骤 1 作为将跟随的线程菜单。之后的一切必须由流程驱动。
- **一次一个线程**：选择最常见的用户旅程首先（通常是"创建→激活→持续管理"），端到端地走它，及时接触基础，然后重复每个剩余线程。不要交错线程。
- **跨切门禁在最后**：访问检查、速率限制、功能标志或跨许多操作应用的共享守卫应在主要流程之后，以便读者在看到*正在门禁的内容*之前看到*如何门禁*。
- **审阅者的结论**：除了通常的心智模型+扩展点外，还包括**"PR 对话中要标记的事项"**列表 — 非明显的权衡、防御性代码、竞争窗口、过时的默认值、非事务性写入。这通常是审阅游览中最有价值的部分。

所有其他游览指南（过渡、goto 链接、子高亮、mermaid 图表、结论）仍然适用。

## 质量检查清单

完成前请验证：

- [ ] 引言（步骤 0）提供全面的架构概述，而不是目录
- [ ] 如果问题被缩小范围，引言说明包含和不包含的内容
- [ ] 配置依赖项（环境变量、功能标志、配置）在相关位置被指出
- [ ] 第一个代码步骤是一个真实的入口点（路由、CLI 处理程序、事件处理程序） — 不是配置文件、模式或辅助程序
- [ ] 基础组件（模式、配置、常量、辅助程序）在流程首次引用它们的地方出现，而不是在序幕中
- [ ] 之前只有一个定向步骤
- [ ] 步骤遵循实际的执行/数据流，而不是按字母顺序排列的文件顺序
- [ ] 每个步骤都以一个将其与前一个步骤联系起来的过渡开始
- [ ] 解释了设计决策和"为什么"，而不仅仅是"代码做了什么"
- [ ] 标记了存在的边缘情况和注意事项
- [ ] 没有两个连续的步骤在同一文件中突出显示相同的行
- [ ] 跨模块跳转要么被跟踪，要么被总结，要么被跳过 — 不要留下未解释的
- [ ] 一个结论步骤将所有内容联系在一起，提供心智模型、设计决策和扩展点
- [ ] 每个具有已知文件位置的函数、类或符号引用都使用 goto 链接
- [ ] 每个 `goto:` 链接和每个 `--file` / `--line` 值都已与实际文件验证 — 没有猜测的行号
- [ ] 重复模式（跨 N 个文件相同的守卫/中间件）在一个步骤中覆盖，而不是 N 个步骤
- [ ] 步骤正文遵循过渡→解释→要点，并位于 150-300 字范围内
- [ ] 对于审阅游览：结论中包含"PR 对话中要标记的事项"列表
