# Diffity 审查技能

你正在审查一个 diff 并使用 `{{binary}} agent` CLI 留下内联评论。

## 参数

- `ref` (可选): 审查的 Git 引用 (例如 `main..feature`, `HEAD~3`)。默认为工作区更改。当同时提供 `ref` 和 `focus` 时，使用两者 (例如 `/diffity-review main..feature security`)。
- `focus` (可选): 将审查集中在特定区域。选项包括: `security`, `performance`, `naming`, `errors`, `types`, `logic`。如果省略，则审查所有内容。

## CLI 参考

```
{{binary}} agent diff
{{binary}} agent list [--status open|resolved|dismissed] [--json]
{{binary}} agent comment --file <path> --line <n> [--end-line <n>] [--side new|old] --body "<text>"
{{binary}} agent general-comment --body "<text>"
{{binary}} agent resolve <id> [--summary "<text>"]
{{binary}} agent dismiss <id> [--reason "<text>"]
{{binary}} agent reply <id> --body "<text>"
```

- `--file`, `--line`, `--body` 是 `comment` 所必需的
- `--end-line` 默认为 `--line` (单行评论)
- `--side` 默认为 `new`
- `general-comment` 创建一个不与任何文件或行绑定的 diff 级评论
- `<id>` 接受完整的 UUID 或 8 字符前缀

## 前置条件

1. 检查 `{{binary}}` 是否可用：运行 `which {{binary}}`。如果未找到，{{install_hint}}。

## 说明

### 第 1 步：确保 diffity 正在运行正确的引用 (无需打开浏览器)

审查需要一个运行中的会话，其引用与请求的引用匹配。引用不匹配会导致在添加评论时出现 "文件不在当前 diff 中" 的错误。

1. 运行 `{{binary}} list --json` 获取所有运行中的实例。解析 JSON 输出并找到 `repoRoot` 与当前仓库匹配的条目。
2. 如果存在匹配的条目，将其 `ref` 字段与请求的引用进行比较：
   - 注册表为工作区会话存储 `"work"`，为命名引用存储用户提供的引用字符串 (例如 `"main"`，`"HEAD~3"`)。
   - 如果引用 **匹配** → 重用会话，记下端口，并继续到第 2 步。
   - 如果引用 **不匹配** → 重新启动：运行 `{{binary}} <ref> --no-open --new` (如果没有引用，则运行 `{{binary}} --no-open --new`)。`--new` 标志会杀死旧会话并启动一个新的会话。使用 Bash 工具，设置 `run_in_background: true`。等待 2 秒，然后使用 `{{binary}} list --json` 进行验证并记下端口。
   - 如果 **没有请求引用** 且运行中的会话的引用不是 `"work"` → 使用 `{{binary}} --no-open --new` 重新启动 (运行中的会话是为命名引用，但我们需要工作区)。
3. 如果 **此仓库没有运行中的会话**，在后台启动一个：
   - 命令：`{{binary}} <ref> --no-open` (如果没有引用，则运行 `{{binary}} --no-open`)
   - 使用 Bash 工具，设置 `run_in_background: true`
   - 等待 2 秒，然后使用 `{{binary}} list --json` 进行验证并记下端口。

### 第 2 步：审查 diff

1. **直接从 diffity 获取统一 diff** — 这会自动处理合并基解析、未跟踪文件和所有引用类型：
   ```
   {{binary}} agent diff
   ```
   这会输出当前会话的完整统一 diff。行号位于 `@@` 段头中。
2. 查找并阅读所有相关的 CLAUDE.md 文件 — 根 CLAUDE.md 和任何包含已修改文件的目录中的 CLAUDE.md 文件。这些文件定义了项目特定的规则，diff 必须遵循。

#### 评估更改的大小并调整你的策略

3. **评估 diff 的大小** 并规划你的方法。无论 diff 的大小如何，每个文件都会得到彻底的审查 — 区别在于你如何组织工作：
   - **小** (少于 ~100 行更改，1-3 个文件)：直接 — 按顺序审查每个文件。
   - **中** (100-500 行更改，3-10 个文件)：按区域分组文件 (例如后端、前端、测试、配置)。首先审查核心逻辑文件，以便在审查涟漪效应之前理解意图。
   - **大** (500 行以上更改或 10 个以上文件)：按区域分组文件。首先审查核心逻辑，然后审查每个剩余文件。对于机械重复的更改 (例如对 20 个文件应用相同的重命名)，在几个实例上验证模式是否正确，然后检查每个剩余实例是否有偏离模式的错误 — 不要跳过任何，但一旦模式建立，你可以更快地检查它们。

   无论大小如何，**阅读并审查每个已更改的文件**。不要跳过或抽查文件。

#### 在审查之前理解更改

4. **首先总结更改**。在寻找问题之前，构建一个 diff 的心理模型：
   - 这个更改试图完成什么？(新功能、错误修复、重构、配置更改)
   - 哪些文件是结构更改，哪些是核心逻辑更改？
   - 作者的意图是什么？阅读提交信息 (`git log --oneline <args>`) 和任何链接的问题或 PR 描述以获取上下文。
   - 作者做出的关键决策是什么，以及他们是在什么约束下工作的？

   理解意图有助于你区分有意行为和真实错误。

5. 对于每个已更改的文件 (根据上述大小策略调整)，阅读整个文件 (而不仅仅是 diff 段)，以了解完整上下文。
6. **交叉引用调用者和依赖项**。对于任何已更改的函数签名、重命名导出、修改的返回类型或更改的行为：在整个代码库中 grep 使用情况。一个在隔离状态下看起来正确的函数可能会破坏每个调用者。检查：
   - 谁调用这个函数？他们会处理新的返回值 / 错误 / 空值情况吗？
   - 谁导入这个模块？更改后的导出名称能否解析？
   - 这个类型更改是否正确传播到消费者？
7. 使用以下技术分析代码更改。如果提供了 `focus` 参数，则集中在该区域。否则，应用所有分析过程和信号阈值。

#### 如何分析

diff 告诉你 *什么* 更改了；周围的代码告诉你更改是否 *正确*。应用这些分析过程：

**数据流分析** — 通过更改的代码跟踪值。每个变量来自哪里？它去哪里？检查：
- 值是否可能在更改的代码假设它不是的地方为空/未定义？
- 更改的代码是否处理了上游条件的所有分支？
- 如果函数的返回类型更改了，所有调用者是否处理了新的形状？
- 是否有缩窄检查 (例如 `if (x)`)，diff 意外移动到了外面？

**状态和生命周期分析** — 对于有状态代码 (React 状态、数据库事务、流、事件监听器)：
- 更改是否创建了一个无法达到或无法退出的状态？
- 资源 (监听器、订阅、文件句柄) 是否在所有路径上都被清理？
- 并发访问是否会破坏共享状态？
- 操作的顺序是否仍然满足不变式 (例如初始化在使用之前)？

**合同分析** — 检查更改的代码是否满足它必须满足的合同：
- 该函数是否仍然满足调用者期望的内容？ (阅读调用者，不要猜测。)
- 如果它实现了接口或覆盖了基方法，它是否仍然符合？
- 前提条件和后置条件是否得到保留？
- 对于 API 端点：响应形状是否与客户端发送/期望的匹配？

**边界分析** — 对于系统边界的代码 (用户输入、网络、文件 I/O、IPC)：
- 用户控制的输入在使用之前是否经过验证？
- 格式错误的外部数据是否会崩溃进程或损坏状态？
- 是否有注入向量 (SQL、shell、XSS、路径遍历)？

**边缘情况分析** — 仅适用于实际会发生的情况，而不是理论上的情况：
- 空数组/字符串、零、负数 — 代码是否处理它们？
- 循环、切片或索引算术中的 off-by-one
- 整数溢出、除以零 (除数来自输入)

#### 完整性检查

在分析代码正确性后，检查更改是否 **完整** — 不仅是正确的，而且是完成的：

**测试覆盖率**:
- 如果 diff 添加了新行为 (新函数、端点、UI 流程、分支)，是否有测试覆盖它？如果没有，将其标记为 `[suggestion]`。
- 如果 diff 修复了错误，是否有测试会捕获该错误？回归测试防止重新引入。
- 如果 diff 修改了现有行为，现有测试是否更新以匹配？过时的测试仍然通过比没有测试更糟 — 它们提供虚假的信心。
- 如果 diff 包括测试，请审查它们的质量：
  - 它们是否测试了 **正确的内容**？ (行为，而不是实现细节)
  - 它们是否覆盖了代码处理的 **边缘情况**？ (空输入、错误路径、边界值)
  - 它们是否 **隔离**？ (没有对测试顺序或全局状态的隐藏依赖)
  - 即使代码损坏，它们是否也能通过？ (自相矛盾的断言、模拟掉的逻辑)

**缺失部分**:
- 没有迁移的架构更改？
- 没有文档或默认值的新的环境变量？
- 没有更新锁定文件的依赖项？
- 更改的 API 响应没有客户端更新？
- 没有在调用点处理的新的错误类型？
- 没有清理相关代码的已移除功能 (死导入、未使用的配置、孤儿测试)？

仅标记那些 **明显需要** 的缺失部分，以便此更改正确工作。不要标记有抱负的改进。

#### 标记什么

标记会影响正确性、安全性或可靠性的真实问题：
- 将导致编译失败、解析失败或运行失败的代码 (语法错误、类型错误、缺失导入、未解析的引用)
- 会导致错误结果的逻辑错误 (明显的错误、off-by-one 错误、损坏的条件)
- 更改的代码中的安全漏洞 (注入、XSS、认证绕过、数据暴露)
- 你可以用具体场景证明的竞态条件或数据丢失风险
- CLAUDE.md 违规，你可以引用被违反的确切规则
- 损坏的合同 — 一个更改的函数不再满足其调用者期望的内容
- 新或更改行为的缺失测试 (作为 `[suggestion]`，而不是 `[must-fix]`，除非项目的 CLAUDE.md 要求测试)
- 不完整的更改 — 迁移、配置、客户端更新，这些对于此更改正常工作是明显需要的

跳过样式问题、linter 捕获的问题和未更改代码中的现有问题。专注于 diff，而不是整个文件。

#### 在评论之前验证

对于每个发现，在发布之前验证它是否真实：
- 重新阅读周围的代码 — 许多明显的错误在完整上下文中消失
- 对于 "缺失导入" 或 "未定义变量" 的声明，grep 确认
- 对于损坏的调用者，阅读实际的调用位置
- 对于 CLAUDE.md 违规，确认规则仅适用于此文件
- 对于缺失的测试，检查是否有其他文件中已经覆盖了此路径的测试

如果重复的模式出现在多个文件中，在第一个出现的地方评论，并在一般摘要中提及模式，而不是重复评论。

### 第 3 步：留下评论

1. **按严重性顺序评论**。首先发布所有 `[must-fix]` 评论，然后是 `[suggestion]`，然后是 `[question]`。在每个严重性内，按文件顺序排列。这确保了如果作者快速浏览，最重要的问题首先被看到。

2. 在评论正文中使用严重性前缀对每个发现进行分类：
   - `[must-fix]` — 错误、安全问题、数据丢失风险。会破坏或产生错误结果的代码。
   - `[suggestion]` — 具体的改进建议，有明确的理由。不是样式偏好 — 真实的改进。这包括缺失的测试、不完整的更改和更好的方法。
   - `[question]` — 需要从作者那里澄清的不明确内容。

3. 对于每个发现，使用以下方式留下内联评论：
   ```
   {{binary}} agent comment --file <path> --line <n> [--end-line <n>] [--side new] --body "<comment>"
   ```
   - 使用 `--side new` (默认) 对添加/修改的代码进行评论
   - 使用 `--side old` 对已删除的代码进行评论
   - 使用 `--end-line` 当问题跨越多行时
   - **以问题开头，而不是背景**。要具体和可操作的。
   - 对于小的、自包含的修复，包括一个显示修复的代码建议
   - 对于较大的修复 (结构更改、多位置)，描述问题和建议方法，而不使用完整的代码块
   - 如果标记 CLAUDE.md 违规，引用被违反的确切规则
4. 留下所有内联评论后，决定是否需要一般评论：
   - **没有发现 → 留下一个一般评论**："未发现问题。检查了错误和 CLAUDE.md 合规性。"
   - **1-2 个发现 → 跳过一般评论**，除非有内联评论未涵盖的跨领域问题。
   - **3 个以上发现 → 留下一个一般评论**，总结主题。
   - **大的 diff → 总是留下一个一般评论**，注明审查的范围，并按区域分组发现。
   - **不要在一般评论中使用严重性前缀** — 前缀仅用于内联发现。
   - 以结论开头，直接简洁 — 没有赞美，没有填充，没有描述代码做什么。
   ```
   {{binary}} agent general-comment --body "<整体审查摘要>"
   ```

### 第 4 步：打开浏览器

1. 现在评论准备好了，打开浏览器：
   ```
   {{binary}} open <ref>
   ```
   如果提供了引用参数 (例如 `{{binary}} open HEAD~3`)，请传递它。省略它以打开默认视图。
2. 告知用户审查已完成，他们可以检查浏览器。示例：

   > 审查完成 — 检查你的浏览器。
   >
   > 发现：2 个必须修复，1 个建议
   >
   > 准备好时，运行 **{{slash}}resolve** 来修复它们。
