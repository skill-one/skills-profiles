# 编写计划

## 概述

为一位未见过此代码库或此规范的工程师编写实现计划。假设一旦他们了解确切的接口和确切的测试，就会使用项目语言编写 idiomatic 代码，并且会在计划留下选择的地方做出合理的决定。他们无法知道的是你决定的内容：哪些文件、哪些名称和签名、规范中的哪些值、哪些测试证明了每个任务。记录这些内容。将整个计划作为可咬一口的任务提供给他们。DRY。YAGNI。TDD。频繁提交。

**开始时宣布：** "我正在使用编写计划技能来创建实现计划。"

**背景：** 如果在隔离的工作树中工作，它应该通过 `superpowers:using-git-worktrees` 技能在执行时创建。

**保存计划到：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- (用户对计划位置的偏好会覆盖此默认值)

## 范围检查

如果规范涵盖了多个独立的子系统，它应该在头脑风暴期间分解为子项目规范。如果没有，建议将其分解为单独的计划——每个子系统一个计划。每个计划都应该能够独立产生可工作、可测试的软件。

## 文件结构

在定义任务之前，规划将要创建或修改的文件以及每个文件的责任。这是分解决策被锁定的地方。

- 设计具有清晰边界和明确定义的接口的单元。每个文件应该有一个明确的责任。
- 你在能够一次性掌握上下文中的代码时推理最佳，并且当文件集中时，你的编辑更可靠。优先考虑较小的、集中的文件，而不是做太多事情的大型文件。
- 一起更改的文件应该放在一起。按责任分割，而不是按技术层分割。
- 在现有代码库中，遵循既定模式。如果代码库使用大型文件，不要单方面重构——但如果你要修改的文件变得难以处理，在计划中包含拆分是合理的。

这个结构指导任务分解。每个任务都应该产生自包含的更改，这些更改可以独立地有意义。

## 任务大小调整

任务是包含自己的测试周期并且值得一个新鲜审查者通过的 最小单元。在划分任务边界时：将设置、配置、脚手架和文档步骤折叠到需要它们的任务的交付物中；只有在审查者可以有意义地拒绝一个任务而批准其相邻任务的情况下才进行拆分。每个任务都以一个可独立测试的交付物结束。

## 步骤粒度

**每个步骤是一个具有可检查结果的动作：**
- "编写失败的测试" - 步骤
- "运行它以确保它失败" - 步骤
- "实现使测试通过的最小代码" - 步骤
- "运行测试并确保它们通过" - 步骤
- "提交" - 步骤

## 计划文档标题

**每个计划必须以这个标题开始：**

```markdown
# [功能名称] 实现计划

> **对于自主工作的员工：** 必须使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 来按任务实现此计划。步骤使用复选框（`- [ ]`）语法进行跟踪。

**目标：** [一句话描述这个构建的内容]

**架构：** [2-3句话关于方法]

**技术栈：** [关键技术/库]

**规范：** [指向此计划实现的规范/设计文档的路径——计划从规范出发，所以规范随计划一起移动；执行者阅读两者]

## 全局约束

[规范的跨项目要求——版本下限、依赖限制、命名和复制规则、平台要求——每行一条，并从规范中逐字复制确切的值。每个任务的要求隐式包含这一部分。]

## 审查重点

[规范暗示但没有任何任务的测试执行的最可能咬人的五个输入类别或失败模式——每行一条，命名输入或条件以及一个合理的人会期望的行为，最可能是第一个。规范是一份愿景文档：它说明软件必须做什么，而不是它将满足的所有内容，并且它对输入的沉默不是允许该输入破坏程序的许可。在规范面前写下这个列表，一次，然后，对于每一行，添加将之固定到拥有该代码的任务的测试，在该任务自己的步骤风格中。]

---
```

## 任务结构

````markdown
### 任务 N: [组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费：[此任务从早期任务使用的——确切的签名]
- 产生：[稍后任务依赖的——确切的函数名、参数和返回类型。一个任务的实现者只看到自己的任务；这个块是他们如何了解相邻任务使用的名称和类型的方式。]

- [ ] **步骤 1：编写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试以验证它失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：失败并显示 "function not defined"

- [ ] **步骤 3：在 `exact/path/to/file.py` 中实现 `function(input: InputType) -> ResultType`**

当签名和测试留下选择时的一行关于方法（哪个库调用、哪个数据结构）；只有当他们不确定的算法才提供代码块。

- [ ] **步骤 4：运行测试以验证它通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：通过

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: 添加特定功能"
```
````

## 步骤包含的内容

一个步骤完成时，实现者可以从中写出确切的一个合理的东西。这就是全部要求：无歧义，不完整。每种类型的步骤都包含使其无歧义的内容，并且不包含更多内容：

- **一个测试步骤：** 测试的名称及其断言，作为代码，其中包含规范的精确值。
- **一个代码步骤：** 确切的签名（名称、参数、返回类型）、它所在的文件以及规范固定了的具体值。实现者编写主体。主体仅用于签名和测试未确定的算法，或规范固定了的确切复制。
- **一个验证步骤：** 运行的命令和表示它通过的结果。
- **对另一个任务的引用：** 该任务的接口块说明了要使用的内容；计划不重复该任务的代码。

计划是实现者无法单独做出的决策的集合。比它描述的代码更长的计划是编写了代码。决定无事的行（"TBD"、"处理边缘情况"、"添加适当的验证"、"为上述内容编写测试"、"一个任务未定义的类型或函数"）是相反的失败，自我审查会捕捉到两者。

## 自我审查

在编写完整计划后，用新鲜的眼光查看规范，并对照计划进行检查。这是一个你自我运行的检查表——不是子代理派遣。

**1. 规范覆盖范围：** 快速浏览规范的每个部分/要求。你能指出一个实现了它的任务吗？列出任何差距。

**2. 步骤扫描：** 每个步骤必须让实现者写出一个合理的的东西，并且没有步骤可以包含更多内容：一个决定无事的行是一个差距，一个签名和测试已经确定的函数主体是一个记录。修复两者。

**3. 类型一致性：** 你在稍后任务中使用的类型、方法签名和属性名是否与你在早期任务中定义的匹配？在任务 3 中调用的 `clearLayers()` 但在任务 7 中调用的 `clearFullLayers()` 是一个错误。

**4. 审查重点：** 对于规范暗示的每个输入类别或失败模式，是否有任务的测试执行了它？最可能咬人的五个未覆盖的输入类别或失败模式放在审查重点部分，并且每行那里都将其测试添加到拥有该任务中。一个空白的部分意味着你检查了并且没有发现，而不是你跳过了检查。

**5. 比例：** 比较计划的长度与规范的长度。比它实现的规范长几个计划是一个程序记录，而不是一个计划。如果代码块是文档的大部分，请用签名、测试名称和断言替换主体，并检查每个步骤仍然是无歧义的。

如果你发现问题，请直接修复。不需要重新审查——只需修复并继续。如果你发现一个没有任务的规范要求，请添加任务。

## 执行交接

在保存和自我审查计划后，为你的人类合作伙伴提供链接以供阅读。如果他们已经明确提供了执行方法，请让他们审查计划并确认它捕获了他们想要的内容；等待该审查后再进行实现，然后使用保留的方法。否则，请让他们审查计划并在实现前选择执行方法。

**当还没有提供执行方法时：**

**"计划完成并保存到 `docs/superpowers/plans/<filename>.md`。请审查计划。您更喜欢哪种执行方法？**

- **子代理驱动** - 一个新的子代理实现每个任务，并在下一个任务开始之前由一个新的审查者检查它，然后在最后进行整个分支的审查。最彻底；每个任务和每个审查都花费一个新上下文。
- **本地** - 我在这个会话中自己实现每个任务，这个 harness 运行工作的方式，然后在最有能力的模型上对整个分支进行一次新的审查。最便宜和最快；直到最后都没有独立的审查。与中端会话模型运行良好，因为计划包含了设计。

**对于此计划我推荐 <其中一个>，因为 <从计划中的一句话：任务之间接口的依赖程度、任务的数量、一个发送错误会花费多少钱>。计划是否捕获了您想要的内容，我们应该使用哪种方法？**"

**当已经提供执行方法时：**

**"计划完成并保存到 `docs/superpowers/plans/<filename>.md`。请审查计划。它是否捕获了您想要的内容？**

**如果选择子代理驱动：**
- **必须使用子代理驱动开发技能：** `superpowers:subagent-driven-development`

**如果选择本地：**
- **必须使用执行计划技能：** `superpowers:executing-plans`
