# 完成前的验证

## 概述

**核心原则：** 证据先于主张，始终如一。

**违反此规则的字面要求，即是违反其精神。**

## 铁律

```
无新鲜验证证据不得声称完成
```

如果你没有在此消息中运行验证命令，你就不能声称它通过了。

## 门禁函数

```
在声称任何状态或表达满意之前：

1. 识别：什么命令能证明此主张？
2. 运行：执行完整的命令（新鲜、完整）
3. 阅读输出：检查退出码，统计失败次数
4. 验证：输出是否确认了主张？
   - 如果否：陈述实际状态并提供证据
   - 如果是：陈述主张并提供证据
5. 仅在此之后：才能做出主张

跳过任何步骤 = 撒谎，未验证
```

## 常见失败

| 主张 | 需要 | 不足 |
|------|------|------|
| 测试通过 | 测试命令输出：0 失败 | 之前的运行，“应该通过” |
| 代码检查器干净 | 代码检查器输出：0 错误 | 部分检查，推断 |
| 构建成功 | 构建命令：退出 0 | 代码检查器通过，日志看起来良好 |
| 修复了错误 | 原始症状测试：通过 | 代码已更改，假定已修复 |
| 回归测试通过 | 红绿循环已验证 | 测试通过一次 |
| 代理完成 | 版本控制系统差异显示更改 | 代理报告“成功” |
| 满足要求 | 逐行检查清单 | 测试通过 |

## 警示信号 - 停止

- 使用“应该”、“可能”、“看起来像”
- 在验证前表达满意（“太棒了！”、“完美！”、“完成了！”等）
- 准备提交/推送/PR 而未验证
- 信任代理成功报告
- 依赖部分验证
- 认为“就这一次”
- 疲惫并想尽快完成工作
- **任何暗示未运行验证就成功的措辞**

## 合理化预防

| 托词 | 现实 |
|------|------|
| “现在应该可以工作了” | 运行验证 |
| “我很自信” | 自信≠证据 |
| “就这一次” | 没有例外 |
| “代码检查器通过了” | 代码检查器≠编译器 |
| “代理说成功了” | 独立验证 |
| “我累了” | 疲惫≠借口 |
| “部分检查就足够了” | 部分证明不了任何东西 |
| “措辞不同，规则不适用” | 精神重于字面 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] “所有测试通过”
❌ “应该通过现在” / “看起来正确”
```

**回归测试（测试驱动开发红绿循环）：**
```
✅ 编写 → 运行（通过） → 回退修复 → 运行（必须失败） → 恢复 → 运行（通过）
❌ “我写了一个回归测试”（未进行红绿验证）
```

**构建：**
```
✅ [运行构建] [看到：退出 0] “构建通过”
❌ “代码检查器通过”（代码检查器不检查编译）
```

**要求：**
```
✅ 重新阅读计划 → 创建检查清单 → 验证每个 → 报告差距或完成情况
❌ “测试通过，阶段完成”
```

**代理委托：**
```
✅ 代理报告成功 → 检查版本控制系统差异 → 验证更改 → 报告实际状态
❌ 信任代理报告
```

## 适用时机

**始终在以下情况之前：**
- 任何成功/完成主张的变体
- 任何表达满意的方式
- 任何关于工作状态的正面陈述
- 提交、PR 创建、任务完成
- 进入下一个任务
- 委托给代理

**规则适用于：**
- 精确短语
- 概括和同义词
- 成功的暗示
- 任何暗示完成/正确性的沟通
