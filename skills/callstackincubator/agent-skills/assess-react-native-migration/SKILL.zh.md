# 评估 React Native 迁移

生成只读的迁移决策。诊断产品和交付系统；不要执行迁移。

## 确立产品范围

从一个能够暴露尽可能多的生产客户端代码库的工作区运行评估。当前的检出并不是证据，证明它包含整个产品。

在评估准备情况之前：

1.  检查当前存储库和代理可访问的每个工作区根目录。
2.  从产品文档、CI、发布配置、工作区清单、子模块以及指向兄弟存储库的引用中推断支持的客户端平台。
3.  定位每个生产客户端代码库，包括单独的 native iOS 和 Android 存储库、应用变体以及任何与人员配置或建议代码共享相关的 Web 客户端。
4.  记录一个平台清单，包括客户端、存储库或路径、产品成员资格的证据以及访问状态。

当 iOS 和 Android 都受支持时，在推荐路径之前检查两个原生代码库。如果一个代码库仍然不可用，将其证据标记为 `unknown`，声明评估仅涵盖可访问的平台，并相应降低置信度。不要仅仅因为其项目当前存储库中不存在就推断平台不受支持。

**范围门禁：** 每个受支持的生产客户端都列在清单中，并且每个代码库都是可访问的、明确不可用或确认不存在。

## 第一响应门禁

当范围门禁未通过时，第一次响应必须是：

```markdown
**问题：** 我可以在哪些地方访问此产品支持的所有客户端平台（包括 iOS 和 Android，如果都存在）的生产代码库？

**为什么重要：** 基于单个平台的迁移路径可能会遗漏原生依赖项、产品行为和交付约束，从而改变决策。
```

在范围门禁通过后，当存储库证据不可用时，应进行质询而不是调查。

如果可衡量的迁移驱动因素未知，第一次响应必须是：

```markdown
**问题：** React Native 迁移应该解决什么可衡量的交付或业务问题？

**为什么重要：** 这决定了迁移是否相关以及评估必须测试哪些结果。
```

如果驱动因素已知，只问下一个最高影响的未知因素，使用相同的两行格式。在提出问题和解释原因后立即结束回合。不要添加前言、问卷、建议或实施指导。

## 规则

- 将每个生产应用视为事实来源，包括未记录的行为。
- 在提问之前，检查可用的代码、CI、测试、发布配置、产品文档和运行时证据。
- 在 iOS 和 Android 之间明确比较它们的实现、行为、依赖项、交付或路线图差异。
- 仅基于所有支持平台的证据或限定其平台覆盖范围来支持产品范围的声明。
- 将材料声明标记为 `observed`、`measured`、`reported`、`assumed` 或 `unknown`。
- 基于证据提出建议，而不是基于综合准备就绪分数。
- 默认情况下收集证据，而不是到 brownfield、greenfield 或迁移本身。
- 掌握决策阶段。在 Path A 被接受之前，不要应用实施技能或选择 Expo 对比 bare React Native。
- 只计算 React Native 相对于当前原生系统的边际价值。
- 通过接受的、经过验证的工作来衡量代理，而不是通过代币、生成的代码或拉取请求。
- 不要对持续时间、成本、代码共享、代理生产力或 ROI 做出普遍性声明。

## 选择证据模式

当源代码或交付工件可用时，使用基于存储库的评估：

1.  完成平台清单并确定评估可以检查哪些存储库。
2.  对于每个可访问的移动代码库，定位应用变体、CI、测试、发布配置、架构记录和产品文档。
3.  在每个原生代码库中搜索 SDK、权限、应用扩展、存储、身份验证、推送、深度链接、分析、实验和平台特定行为。
4.  引用存储库名称加上文件路径和行号，以便在代码库分离时证据仍然可追溯。
5.  仅向利益相关者询问缺失代码库的位置或存储库无法确定的 产品、组织 和运营事实。

当存储库不可用或重要证据仍然缺失时，使用访谈评估：

1.  除非用户已经提供，否则从可衡量的交付或业务问题开始。
2.  每次回合只问一个改变决策的问题。
3.  用一句话解释答案如何影响路径、风险或假设。
4.  用更具体的后续问题挑战模糊或矛盾的答案，而不是接受它们作为证据。
5.  记录答案，更新证据状态，并选择下一个最高影响的未知因素。
6.  当另一个答案无法改变建议、置信度或检查点时，停止质询。

在证据门禁通过之前，每个响应必须只包含：

```markdown
**问题：** [一个问题]

**为什么重要：** [一句话]
```

在这些回合中不要包括问卷、路径建议、检查点或实施指导。如果用户暂停访谈，返回当前证据状态和单个最高影响的未知因素，不要假装评估已完成。

**访谈回合门禁：** 已请求一个答案，其决策影响是明确的，并且没有出现第二个问题。

## 1. 收集决策证据

声明决策、截止日期、当前替代方案和可衡量的驱动因素。框架偏好不是驱动因素。

检查这些维度：

| 维度 | 最小证据 |
| --- | --- |
| 产品 | 支持的平台、应用变体、共享与平台特定路线图的差异、关键流程、可访问性、分析器和边缘情况 |
| 原生表面 | SDK、模块、权限、后台工作、应用扩展、支付、硬件 API、自定义渲染和可行的 React Native 路径 |
| 连续性 | 身份验证和会话、安全和持久存储、推送令牌、深度链接、订阅、已安装用户更新、法律、安全和离线约束 |
| 验证 | 可重复构建、测试帐户、手动和自动化 QA、设备控制、原生参考证据、性能基线和独立审查 |
| 发布 | 当前节奏和恢复、内部分发、标志、实验、商店发布和期望的二进制以及可选的 OTA 轨道 |
| 所有权 | 决策权限和工件、基准、原生边界、共享基础、验证和发布的负责人 |
| 代理治理 | 批准的模型和源边界、受保护的密钥和测试数据、最小权限访问、证据保留、审计跟踪和人类架构和发布批准 |
| 交付基线 | 重复实现和审查、等待和交接、基准差距、两平台验证、发布指标、缺陷、返工和维护成本 |

对于依赖 OTA 的计划，需要负责人加上运行时兼容性、发布、可观察性、回滚或重新发布以及审计策略。OTA 可用性本身不是迁移收益。

使用一个结合现有产品和原生知识以及 React Native 迁移专业知识的迁移核心。只要求缺失的、可能改变决策的事实；将其他内容作为假设公开。

**门禁：** 每个维度都有证据或明确的未知因素，并且每个路径阻塞的未知因素都被命名。

## 2. 选择路径

选择一个结果并说明为什么其他替代方案会失败。

| 结果 | 推荐条件 |
| --- | --- |
| **Path A: brownfield** | 发布或已安装用户连续性占主导地位、原生耦合深度、流程可以独立移动，或者全应用切换风险不可接受。包括主机边界和双架构的成本。 |
| **Path B: greenfield** | 行为可以恢复、原生依赖项有可信的替代方案、连续性可以证明、验证强大，并且遗留范围可以控制直到替换。 |
| **Path C: greenfield-first checkpoint with brownfield fallback** | greenfield 提供了一个更简单的目标，但仍有实质性不确定性，并且可以证明在原生主机中完成的 React Native 工作可以在扩展之前进行。 |
| **Defer** | 商业案例合理，但证据、验证、所有权、预算或发布就绪状态缺失。命名最小的就绪工作和新开放条件。 |
| **Do not migrate** | 原生系统满足预期结果、重复移动交付不是实质性的、路线图不对称、平台特定工作占主导地位，或者风险调整后的回报不可信。 |

将 Path C 视为 Callstack 的 2025 年后新兴的运营模式，而不是行业基准。代理访问使行为移植更加可行；只有在这个产品上测量检查点才能确定速度和质量。

在 Path A 被接受后，将实施规划交给 [react-native-brownfield-migration](../react-native-brownfield-migration/SKILL.md)。不要重复其 Expo、XCFramework、AAR 或主机集成的指导。

**门禁：** 一个结果由决定性证据支持，被拒绝的替代方案有理由，并且置信度反映了证据质量。

## 3. 定义一个代表性检查点

使用检查点进行 Path C，并且在任何可能使推荐路径无效的不确定性时使用。设置由组织提供的固定日历和努力预算。选择两个或三个垂直流程：

1.  一个涵盖 UI、数据、分析器和导航的常见流程。
2.  一个经过身份验证的、有状态流程，涵盖持久性、错误和会话行为。
3.  最可能使计划失效的边界，例如原生 SDK、后台任务、硬件 API、离线行为、应用扩展、可访问性要求或低端 Android 约束。

将每个流程与原生源参考、运行时证据、负责人和基准场景相关联。不要只选择容易的屏幕。

针对现有产品定义可衡量的接受标准：

- 行为、状态、验证、错误、分析器、可访问性和视觉输出与原生参考匹配。
- 身份验证、存储、深度链接、推送和选定的原生边界在所需的设备和操作系统版本上工作。
- 启动、交互、内存和崩溃行为符合约定的基线或容差。
- CI、内部分发、可观察性和预期的发布轨道可靠到可以继续。
- 每个流程都有设备级证据和具有干净上下文的独立审查。
- Path C 打包并在每个所需的原生主机中至少打开一个代表性的 React Native 流程。

对至少一个流程运行两次：

1.  **Faithful pass：** 保留行为、分析器、可访问性、状态和边缘情况。记录保留原生形状架构以实现基准。
2.  **Idiomatic pass：** 引入 React 组件组合、清晰的状态边界、类型化导航、可重用的基元、合适的测试和测量的性能。重复基准和设备检查。

在扩展之前，为 `MIGRATION.md`、`SCREENS.tsv`、`STATE_AND_STORAGE.tsv`、`DEPENDENCIES.tsv`、`EVENTS.tsv` 和 `PARITY_CHECKS.md` 指定负责人。在评估期间，识别缺失的工件，而不是创建完整的清单，除非被要求。

以一个决策结束：继续 greenfield、继续 Path C、将已完成的工作移入 Path A、推迟或停止。不要仅仅因为检查点结果不方便而延长检查点。

**门禁：** 流程、预算、标准、证据、负责人和终端决策都是明确的。

## 4. 测试经济性

将一个代表性的变更从就绪实施映射到两个平台上的验证可用性。捕获两个时钟：

1.  **变更 lead time：** 承诺一个对生产队列可用的工件；分离二进制和 OTA 交付。
2.  **跨平台功能 lead time：** 就绪实施到 iOS 和 Android 上的验证可用性。

计算从删除重复实现和业务逻辑审查中获得的潜在回报，降低基准协调，工程师流动性，以及测量的发布或恢复改进。保留 iOS 和 Android 设备验证在模型中。除非单独资助和评估，否则将 Web 融合排除在基本情况之外。

计算全部投资：检查点、双维护、原生模块、培训、idiomatic 第二次通过、测试和设备自动化、可观察性、发布基础设施、平台所有权、切换和原生表面退役。

不要编造回报输入。在提供的数据不确定时使用范围。当验证和边界工作消耗预期节省、原生表面持续增长、双维护没有退役界限、代理增加返工而没有验证吞吐量、基准改善而没有交付改进，或者已发布的容量没有计划使用时，修订、推迟或停止。

**门禁：** 边际收益和全部投资可以在不将两平台验证视为删除工作的前提下进行比较。

## 输出合同

仅在证据门禁通过后或当用户结束访谈时使用此合同。

返回一个简洁的报告，按此顺序：

1.  **建议：** 结果、置信度、决定性原因和决策边界。
2.  **证据：** 平台清单、覆盖限制和材料发现，包括源状态和平台差异。
3.  **假设和阻塞：** 按决策影响排序的未知因素。
4.  **检查点：** 预算、流程、标准、负责人、证据和终端决策。
5.  **基线和 ROI：** 测量的输入、缺失的输入、计数的回报、全部投资和排除项。
6.  **下一个决策：** 谁决定什么，使用哪些证据，以及何时。

保持结论诊断。如果执行出现问题，只声明编排、任务合同、提示、重试规则和私有代理是特定于参与的。永远不要暴露或编造私有实施材料。
