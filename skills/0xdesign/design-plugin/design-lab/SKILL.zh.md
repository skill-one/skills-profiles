# 设计实验室技能

此技能实现了一个完整的设计探索工作流程：访谈、生成变体、收集反馈、优化、预览和最终确定。

## 关键：清理行为

**所有临时文件必须在流程结束时删除，无论是由以下哪种情况触发：**
- 用户确认最终设计 → 清理，然后生成计划
- 用户中止/取消 → 立即清理，不生成计划

**绝对不能留下 `.claude-design/` 或 `__design_lab` 路径。** 如果用户在任何时候说“取消”、“中止”、“停止”或“不管了”，请确认然后删除所有临时工件。

## 阶段 0：预检测

在开始访谈之前，自动检测：

### 包管理器
检查项目根目录中的锁文件：
- `pnpm-lock.yaml` → 使用 `pnpm`
- `yarn.lock` → 使用 `yarn`
- `package-lock.json` → 使用 `npm`
- `bun.lockb` → 使用 `bun`

### 框架检测
检查配置文件：
- `next.config.js` 或 `next.config.mjs` 或 `next.config.ts` → **Next.js**
  - 检查 `app/` 目录 → App 路由器
  - 检查 `pages/` 目录 → Pages 路由器
- `vite.config.js` 或 `vite.config.ts` → **Vite**
- `remix.config.js` → **Remix**
- `nuxt.config.js` 或 `nuxt.config.ts` → **Nuxt**
- `astro.config.mjs` → **Astro**

### 样式系统检测
检查 `package.json` 依赖项和配置文件：
- `tailwind.config.js` 或 `tailwind.config.ts` → **Tailwind CSS**
- `@mui/material` 在依赖项中 → **Material UI**
- `@chakra-ui/react` 在依赖项中 → **Chakra UI**
- `antd` 在依赖项中 → **Ant Design**
- `styled-components` 在依赖项中 → **styled-components**
- `@emotion/react` 在依赖项中 → **Emotion**
- `.css` 或 `.module.css` 文件 → **CSS Modules**

### 设计记忆检查
查找现有的设计记忆文件：
- `docs/design-memory.md`
- `DESIGN_MEMORY.md`
- `.claude-design/design-memory.md`

如果找到，读取它并使用它来预填默认值并跳过冗余问题。

### 视觉风格推断（关键）

**绝对不要使用通用/预定义的样式。从项目中提取视觉语言：**

**如果检测到 Tailwind**，读取 `tailwind.config.js` 或 `tailwind.config.ts`：
```javascript
// 提取并使用：
theme.colors      // 色彩调色板
theme.spacing     // 间距尺度
theme.borderRadius // 半径值
theme.fontFamily  // 字体排印
theme.boxShadow   // 提升系统
```

**如果存在 CSS 变量**，读取 `globals.css`、`variables.css` 或 `:root` 定义：
```css
:root {
  --color-*     /* 色彩标记 */
  --spacing-*   /* 间距标记 */
  --font-*      /* 字体排印标记 */
  --radius-*    /* 边框半径标记 */
}
```

**如果检测到 UI 库**（MUI、Chakra、Ant），读取主题配置：
- MUI: `theme.ts` 或 `createTheme()` 调用
- Chakra: `theme/index.ts` 或 `extendTheme()` 调用
- Ant: `ConfigProvider` 主题属性

**始终扫描现有组件**以了解模式：
- 找到 2-3 个现有按钮 → 记录它们的样式模式
- 找到 2-3 个现有卡片 → 记录填充、边框、阴影
- 找到现有表单 → 记录输入样式、标签位置
- 找到现有排版 → 记录标题大小、正文文本

**将推断的样式存储在设计简报中**，以便在所有变体中一致使用。

## 阶段 3：生成设计实验室

### 目录结构

在 `.claude-design/` 下创建所有文件：

```
.claude-design/
├── lab/
│   ├── page.tsx                 # 主要实验室页面（框架特定）
│   ├── variants/
│   │   ├── VariantA.tsx
│   │   ├── VariantB.tsx
│   │   ├── VariantC.tsx
│   │   ├── VariantD.tsx
│   │   └── VariantE.tsx
│   ├── components/
│   │   └── LabShell.tsx         # 实验室布局包装器
│   ├── feedback/                # 交互式反馈系统
│   │   ├── types.ts             # TypeScript 接口
│   │   ├── selector-utils.ts    # 元素识别
│   │   ├── format-utils.ts      # 反馈格式化
│   │   ├── FeedbackOverlay.tsx  # 主覆盖组件
│   │   └── index.ts             # 模块导出
│   └── data/
│       └── fixtures.ts          # 共享模拟数据
├── design-brief.json
└── run-log.md
```

### 反馈系统设置（关键 - 绝对不能跳过）

**FeedbackOverlay 是设计实验室的 PRIMARY 功能。** 没有它，用户无法提供交互式反馈。绝对不能在没有 FeedbackOverlay 的情况下生成设计实验室。

**可靠性策略：** 为避免不同项目配置的导入路径问题，将 FeedbackOverlay **直接在路由目录中创建**（例如，`app/design-lab/FeedbackOverlay.tsx`），而不是在 `.claude-design/` 中。这确保了简单的相对导入（`./FeedbackOverlay`）始终有效。

**路由目录中的必需文件：**
```
app/design-lab/           # 或 app/__design_lab/ 如果下划线有效
├── page.tsx              # 主要实验室页面包含变体
└── FeedbackOverlay.tsx   # 自包含覆盖组件（从模板复制）
```

**模板来源：** `design-and-refine/templates/feedback/FeedbackOverlay.tsx`

**为什么采用这种方法：**
- `.claude-design/` 路径可能因打包器配置失败
- 相对导入从同一目录始终有效
- 路由目录在清理时会被删除

### 路由集成

**Next.js App 路由器：**
创建 `app/__design_lab/page.tsx` 从 `.claude-design/lab/` 导入

**Next.js Pages 路由器：**
创建 `pages/__design_lab.tsx` 从 `.claude-design/lab/` 导入

**Vite React：**
- 如果存在 React Router：添加 `/__design_lab` 路由
- 如果没有路由器：在 `App.tsx` 中基于 `?design_lab=true` 查询参数进行条件渲染

**其他框架：**
为检测到的框架创建最合适的临时路由。

### 变体生成指南

**重要提示：** 阅读 `DESIGN_PRINCIPLES.md` 获取 UX、交互和动画的最佳实践。但 **绝对不要使用预定义的视觉样式**——从项目中推断。

**应用通用原则（来自 `DESIGN_PRINCIPLES.md`）：**
- **UX**：Nielsen 的启发式方法、认知负荷减少、渐进式披露
- **组件行为**：按钮状态、表单结构、卡片结构
- **交互**：反馈模式、状态处理、乐观更新
- **动画**：时间（150-300ms）、缓动（退出使用 ease-out，进入使用 ease-in）
- **可访问性**：焦点状态、ARIA 模式、触摸目标（最小 44px）

**从项目中推断视觉样式：**
- 颜色 → 从 Tailwind 配置、CSS 变量或现有组件
- 字体排印 → 从代码库中的现有标题、正文文本
- 间距 → 从项目的间距尺度或现有模式
- 边框半径 → 从现有卡片、按钮、输入
- 阴影 → 从现有提升组件

---

每个变体必须探索不同的设计轴。不要创建细微的变体——使它们有意义的区别。**使用项目的现有视觉语言为所有变体。**

**变体 A：信息层次结构重点**
- 重组内容层次结构（什么最重要？）
- 应用格式邻近性——将相关项目组合得更近
- 每个视图一个主要操作
- 使用现有字体排印尺度创建清晰的级别

**变体 B：布局模型探索**
- 尝试不同的布局方法（卡片 vs 列表 vs 表格 vs 分割面板）
- 应用卡片解剖或表格行为模式从 `DESIGN_PRINCIPLES`
- 考虑在每个断点处的响应式行为
- 使用项目的现有网格/布局系统

**变体 C：密度变化**
- 如果简报说“舒适”，尝试更紧凑的版本
- 如果简报说“紧凑”，尝试更宽敞的版本
- 使用项目的现有间距标记——只是以不同的方式应用
- 显示权衡：更多可见数据 vs 更易浏览

**变体 D：交互模型**
- 不同的交互模式（模态框 vs 行内 vs 面板 vs 抽屉）
- 应用反馈模式：即时 → 进度 → 完成
- 实现所有必需状态（加载中、错误、空、禁用）
- 考虑乐观更新非破坏性操作

**变体 E：表达方向**
- 推动用户在访谈中描述的品牌方向
- 探索项目现有设计标记的不同用法
- 更多或更少的阴影、边框、背景颜色
- 在添加意义的地方应用动画（悬停、焦点、过渡）

### 实验室页面要求

设计实验室页面必须包含：

1. **标题栏**，包含：
   - 设计简报摘要（目标、范围、关键要求）
   - 审查说明

2. **变体网格**，包含：
   - 清晰的标签（A、B、C、D、E）
   - 每个变体的简要说明（“为什么存在这个变体”）
   - 实际渲染的变体
   - 突出显示关键差异的笔记
   - **重要提示：** 每个变体容器必须有 `data-variant="X"` 属性（其中 X 是 A、B、C、D、E 或 F）。这是反馈系统识别哪些变体评论属于哪个变体的必要条件。

3. **响应式行为**：
   - 桌面：并排网格（2-3 列）
   - 移动：水平滚动或选项卡

4. **共享数据**：
   - 所有变体使用来自 `data/fixtures.ts` 的相同固定数据
   - 确保公平比较

5. **反馈覆盖层**（关键 - 绝对不能省略）：

   ⚠️ **这是最重要的要求** ⚠️

   FeedbackOverlay 允许用户点击元素并留下评论。没有它，设计实验室只是一个静态页面，无法收集结构化反馈。

   - 在与 `page.tsx` 相同的目录中创建 `FeedbackOverlay.tsx`
   - 使用相对路径导入：`import { FeedbackOverlay } from './FeedbackOverlay'`
   - 在页面末尾（所有变体之后）渲染
   - 传递 `targetName` 属性与组件/页面名称

   **示例集成：**

```tsx
import { FeedbackOverlay } from './FeedbackOverlay';  // 相对导入 - 始终有效

export default function DesignLabPage() {
  return (
    <div className="min-h-screen bg-background">
      <header>...</header>

      <main>
        <div className="grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-8">
          <div data-variant="A">
            <VariantA />
          </div>
          <div data-variant="B">
            <VariantB />
          </div>
          {/* ... 更多变体 */}
        </div>
      </main>

      {/* 关键：必须包含 FeedbackOverlay */}
      <FeedbackOverlay targetName="ComponentName" />
    </div>
  );
}
```

   **如果遗漏了 FeedbackOverlay，用户将无法提供反馈。** 这使设计实验室失去全部意义。

### 代码质量

**规范：**
- 遵循项目现有的代码规范（文件命名、导入等）
- 使用检测到的样式系统（Tailwind、CSS模块等）
- 在适当的地方使用项目现有的组件

**无障碍性（来自 DESIGN_PRINCIPLES）：**
- 语义化HTML：`<button>` 而不是 `<div onclick>`，`<nav>`、`<main>`、`<section>`
- 键盘导航：所有交互元素可聚焦且可操作
- 聚焦状态：可见的 `:focus-visible`，带有2px环和偏移
- 颜色对比度：文本为4.5:1，UI元素为3:1
- 触摸目标：最小44x44px
- 仅在HTML语义不足时使用ARIA

**状态（每个组件都需要）：**
- 默认、悬停、聚焦、激活、禁用、加载中、错误、空
- 参见 DESIGN_PRINCIPLES 中的“状态处理”部分

**动画：**
- 使用适当的时序：微交互150-200ms，过渡200-300ms
- 入场使用ease-out，出场使用ease-in
- 尊重 `prefers-reduced-motion`

   ```
   我已生成5个设计变体在 `.claude-design/lab/`

   查看它们：
   1. 确保您的开发服务器正在运行（如果没有，请运行 `pnpm dev`）
   2. 打开：http://localhost:3000/__design_lab

   花时间并并排查看变体，然后回来告诉我：
   - 哪个变体获胜（A-E）
   - 你喜欢它的哪些地方
   - 需要做什么改变
   ```

2. **立即进入第5阶段** - 请求反馈。不要等待用户说他们已打开浏览器。立即提出反馈问题，以便用户回来时做好准备。

### 为什么不启动服务器

运行 `pnpm dev` 或 `npm run dev` 会启动一个长时间运行的进程，它永远不会退出。如果你运行它，你会永远等待。用户可能已经运行了他们的开发服务器，或者可以在另一个终端中自行启动。

---

## 第5阶段：收集反馈

展示实验室URL后，用户可以通过以下两种方式提供反馈：
1. **交互式反馈**（推荐）：使用浏览器中的内置覆盖层
2. **手动反馈**：通过终端中的 AskUserQuestion

### 交互式反馈（主要方法）

设计实验室包含一个类似Figma的反馈覆盖层。展示实验室时，包括以下说明：

```
✅ 设计实验室已创建！

我已生成5个设计变体在 `.claude-design/lab/`

查看并提供反馈：
1. 确保您的开发服务器正在运行（如果没有，请运行 `pnpm dev`）
2. 打开：http://localhost:3000/__design_lab

**添加反馈：**
1. 点击“添加反馈”按钮（右下角）
2. 点击您要评论的任何元素
3. 输入您的反馈并点击“保存”
4. 对所有要评论的元素重复此操作
5. 填写“整体方向”字段（必填）
6. 点击“提交所有反馈”
7. 将复制的文本粘贴到终端中

或者直接在下方手动描述您的反馈！
```

**当用户粘贴反馈时**，它将采用以下格式：

```markdown
## 设计实验室反馈

**目标：** ComponentName
**评论：** 3

### 变体A
1. **按钮** (`[data-testid='submit']`, 带有“提交”的按钮)
   "使其更突出"

### 变体B
1. **卡片** (`.product-card`, 带有“产品名称”的div)
   "喜欢这个布局"

### 整体方向
采用变体B的结构。应用变体A的按钮样式。
```

**如何解析和执行此反馈：**

1. **首先阅读整体方向** - 这将指导您的综合分析
2. **对于每条评论**，使用以下方式定位元素：
   - 主要：反引号中的CSS选择器（例如，`[data-testid='submit']`）
   - 次要：元素描述（例如，“带有'提交'的按钮”）
3. **应用反馈**：编辑相应的变体文件

### 备用方案：通过 AskUserQuestion 手动反馈

如果用户不想使用交互式覆盖层（或粘贴手动反馈），请使用以下 AskUserQuestion 流程：

### 第1阶段：检查是否有获胜者

**问题1：准备好选择了吗？**
- 标题： "决策"
- 问题： "是否有您觉得无需修改的变体？"
- 选项：
  - "是 - 我找到了一个喜欢的" - 准备选择获胜者并进行优化
  - "否 - 我喜欢不同变体的部分" - 需要综合一个新的变体

### 第2A阶段：如果用户找到获胜者

如果用户说“是”，请询问：

**问题2a：哪个？**
- 标题： "获胜者"
- 问题： "您想采用哪个变体？"
- 选项：
  - "变体A" - [A的简要描述]
  - "变体B" - [B的简要描述]
  - "变体C" - [C的简要描述]
  - "变体D" - [D的简要描述]
  - "变体E" - [E的简要描述]

**问题3a：需要微调吗？**
- 标题： "微调"
- 问题： "需要做小的修改，还是可以直接使用？"
- 选项：
  - "可以直接使用" - 无需修改，进入最终预览
  - "需要微调" - 我将描述需要调整的内容

如果“需要微调”，请让用户通过文本输入描述更改。

然后进入 **第7阶段：最终预览**。

### 第2B阶段：如果用户想综合

如果用户说“否 - 我喜欢不同变体的部分”，请询问：

**问题2b：每个变体你喜欢什么？**
- 标题： "反馈"
- 问题： "你喜欢每个变体的哪些地方？（提及A、B、C、D、E中的具体元素）"
- （让用户通过“其他”文本输入提供详细反馈）

指导用户的示例响应格式：
```
- A：喜欢卡片布局和间距
- B：颜色方案感觉正确
- C：悬停交互很棒
- D：没有什么突出
- E：字体层级最清晰
```

然后进入 **第6阶段：综合新变体**。

---

## 第6阶段：综合新变体

根据用户对每个变体喜欢的内容提供反馈：

1. **创建一个新的混合变体**（变体F），结合：
   - 用户从每个变体中提到的具体元素
   - 所有变体中的最佳结构决策
   - 多个变体中出现的任何模式

2. **用比较视图替换设计实验室**：
   - 突出显示新的综合变体F
   - 保留1-2个与原始变体最接近的比较变体
   - 移除用户不喜欢任何变体的变体

3. **更新 `/__design_lab` 路由** 以显示新的排列

4. **再次请求反馈：**

**问题：新变体怎么样？**
- 标题： "评审"
- 问题： "综合变体（F）看起来如何？"
- 选项：
  - "就是这样！" - 进入最终预览
  - "越来越接近" - 需要再次迭代
  - "方向错误" - 让我澄清我的需求

如果“越来越接近”或“方向错误”，请收集更具体的反馈并进行迭代。支持多次综合，直到用户满意。

然后进入 **第7阶段：最终预览**。

---

## 第7阶段：最终预览

用户满意后：

1. 创建 `.claude-design/preview/` 目录：
   ```
   .claude-design/preview/
   ├── page.tsx                    # 预览页面
   └── FinalDesign.tsx             # 获胜设计
   ```

2. 在 `/__design_preview` 创建路由

3. 对于重新设计，包括前后对比：
   - 切换开关或分屏视图
   - 显示原始设计 alongside 提案

4. 请求最终确认：

**问题：确认最终设计？**
- 标题： "确认"
- 问题： "准备好最终确定这个设计了吗？"
- 选项：
  - "是，最终确定" - 进入清理和生成实施计划
  - "否，需要修改" - 告诉我需要调整的内容
  - "中止 - 取消所有操作" - 删除所有临时文件，不生成计划

如果“否，需要修改”：收集反馈并进行迭代。
如果“中止”：进入 **中止处理** 下面。

---

## 中止处理

如果用户在任何阶段想要取消/中止（不只是最终确认），他们可能会说：
- "取消"
- "中止"
- "停止"
- "算了"
- "忘掉它"
- "我改变了主意"

当检测到中止时：

1. **确认中止：**
   - "您确定要取消吗？这将删除我创建的所有设计实验室文件。"

2. **如果确认，立即清理：**
   - 删除 `.claude-design/` 目录完全
   - 删除临时路由文件 (`app/__design_lab/`，等）
   - 不要生成任何实施计划
   - 不要更新设计记忆

3. **确认：**
   - "设计探索已取消。所有临时文件已被清理。如果需要，请告诉我何时重新开始。"

---

## 第8阶段：最终确定

当用户确认（选择了“是，最终确定”）：

### 8.1：清理

删除所有临时文件：
- 删除 `.claude-design/` 目录完全
- 删除临时路由文件：
  - `app/__design_lab/`（Next.js App Router）
  - `pages/__design_lab.tsx`（Next.js Pages Router）
  - `app/__design_preview/`
  - `pages/__design_preview.tsx`
  - 还原任何 `App.tsx` 修改（Vite）

**安全规则：**
- 仅删除 `.claude-design/` 内的文件
- 仅删除插件创建的路由文件
- 永远不要删除用户编写的文件
- 删除前验证文件路径

## 错误处理

### 框架未检测到
如果无法确定框架：
- 询问用户： "我无法检测到您的框架。您使用的是什么？"
- 提供常见选项：Next.js、Vite、Create React App、Vue等

### 开发服务器失败
如果开发服务器无法启动：
- 检查端口冲突
- 提供手动说明
- 建议用户在另一个终端启动服务器

### 路由集成失败
如果无法创建临时路由：
- 回退到创建独立的HTML文件
- 提供手动预览说明

### 清理中断
如果清理中断：
- 记录已删除与剩余的内容
- 提供手动清理说明
- 永远不要留下部分状态而不通知用户

## 配置选项

插件支持以下可选配置（通过环境或项目配置）：

- `DESIGN_AUTO_IMPLEMENT`：如果为 `true`，确认后立即实施计划
- `DESIGN_KEEP_LAB`：如果为 `true`，不删除实验室，直到明确的清理命令
- `DESIGN_MEMORY_PATH`：设计记忆文件的自定义路径
