# n8n 工作流模式

构建 n8n 工作流的成熟架构模式。

---

## 6 个核心模式

基于真实工作流使用分析：

1. **[Webhook 处理](webhook_processing.md)** (最常见)
   - 接收 HTTP 请求 → 处理 → 输出
   - 模式：Webhook → 验证 → 转换 → 响应/通知

2. **[HTTP API 集成](http_api_integration.md)**
   - 从 REST API 获取数据 → 转换 → 存储/使用
   - 模式：触发器 → HTTP 请求 → 转换 → 操作 → 错误处理

3. **[数据库操作](database_operations.md)**
   - 读取/写入/同步数据库数据
   - 模式：计划 → 查询 → 转换 → 写入 → 验证

4. **[AI 代理工作流](ai_agent_workflow.md)**
   - 具有工具和记忆的 AI 代理
   - 模式：触发器 → AI 代理（模型 + 工具 + 记忆）→ 输出

5. **[计划任务](scheduled_tasks.md)**
   - 定期自动化工作流
   - 模式：计划 → 获取 → 处理 → 交付 → 记录

6. **批量处理** (下文)
   - 使用 API 带宽限制分批处理大型数据集
   - 模式：准备 → 分批 → 每批处理 → 累积 → 聚合

## 模式选择指南

### 何时使用每种模式：

**Webhook 处理** - 使用场景：
- 接收来自外部系统的数据
- 构建集成（Slack 命令、表单提交、GitHub webhooks）
- 需要即时响应事件
- 示例： "接收 Stripe 支付 webhook → 更新数据库 → 发送确认"

**HTTP API 集成** - 使用场景：
- 从外部 API 获取数据
- 与第三方服务同步
- 构建数据管道
- 示例： "获取 GitHub 问题 → 转换 → 创建 Jira 工单"

**数据库操作** - 使用场景：
- 在数据库之间同步
- 定时运行数据库查询
- ETL 工作流
- 示例： "读取 Postgres 记录 → 转换 → 写入 MySQL"

**AI 代理工作流** - 使用场景：
- 构建对话式 AI
- 需要 AI 具备工具访问权限
- 多步骤推理任务
- 示例： "与可以搜索文档、查询数据库、发送电子邮件的 AI 对话"

**计划任务** - 使用场景：
- 定期报告或摘要
- 定期数据获取
- 维护任务
- 示例： "每日：获取分析数据 → 生成报告 → 邮件团队"

**批量处理** - 使用场景：
- 处理超出 API 批量限制的大型数据集
- 需要在多个 API 调用中累积结果
- 嵌套循环（例如，多个类别 × 每个类别分页 API 调用）
- 示例： "为 4 个市场获取产品 × 每个市场 1000 个 → 聚合所有结果"

## 常见工作流组件

所有模式都共享这些构建块：

### 1. 触发器
- **Webhook** - HTTP 端点（即时）
- **计划** - Cron 基于定时（定期）
- **手动** - 点击执行（测试）
- **轮询** - 检查更改（间隔）

### 2. 数据源
- **HTTP 请求** - REST API
- **数据库节点** - Postgres、MySQL、MongoDB
- **服务节点** - Slack、Google Sheets 等
- **代码** - 自定义 JavaScript/Python

### 3. 转换
- **Set** - 映射/转换字段
- **代码** - 复杂逻辑
- **IF/Switch** - 条件路由
- **合并** - 合并数据流

读取嵌套 API 响应的过滤/投影切片以获取一个字段或有效负载？一个 `{{ $jmespath($json, "…") }}` 可以替代 Split Out → Filter → Aggregate 链（引用 n8n-expression-syntax 中的规则）。

### 4. 输出
- **HTTP 请求** - 调用 API
- **数据库** - 写入数据
- **通信** - 电子邮件、Slack、Discord
- **存储** - 文件、云存储

### 5. 错误处理
- **错误触发器** - 捕获工作流错误
- **IF** - 检查错误条件
- **停止和错误** - 显式失败
- **失败时继续** - 节点设置

## 工作流生命周期：在激活前验证、验证、测试

构建节点只是开始，不是结束。在工作流上线之前，通过四个关卡运行它——并记住标题规则：**验证通过是必要的，不是充分的。** 一个工作流可以验证干净，但仍可能丢失项目、选择错误的 Merge 输入或以纯文本形式发布 Slack 消息。干净的验证意味着形状是正确的，而不是逻辑正确。

1. **验证。** 在构建期间对完整 JSON 运行 `validate_workflow`，或在实例上存在工作流后运行 `n8n_validate_workflow({ id })`。修复每个错误并重新验证。这可以捕获架构、节点配置、表达式和引用错误——结构层。

2. **验证连接。** 使用 `n8n_get_workflow({ id })` 拉取工作流并直接读取 `connections` 对象。验证确认连接没有 *损坏*；它不确认它们是 *正确的*。这是捕获有效但错误的接线的地方：Merge 的 `useDataOfInput` 与连接槽不匹配、Switch 回退连接到空、分支分支从未连接、错误输出无处可去。（参见 n8n 节点配置技能的 NODE_FAMILY_GOTCHAS.md 以了解无声的陷阱。）

3. **测试。** 运行 `n8n_test_workflow` 并通过 `n8n_executions` 检查输出。确认输出形状与消费者期望匹配、分支都产生数据，以及（对于 webhook API）状态/正文/标头正确。**在测试期间触发真实副作用**——写入提交、消息发送、调用外部 API。如果任何节点具有用户可见的副作用，请在运行前与用户确认，或先使用安全数据测试。

4. **激活** 只有在通过前三个关卡后——使用 `n8n_update_partial_workflow` 与 `activateWorkflow` 操作。不要直接从干净的验证激活；一个丢失数据或重复发送的激活工作流比一个从未开始的工作流更糟。

跳过任何关卡都会用几分钟的代价换取在实时、可能具有状态、可能承载流量工作流中的调试。这种交易永远不值得。

## 数据流模式

### 线性流
```
触发器 → 转换 → 操作 → 结束
```
**使用场景**： 简单的工作流具有单一路径

### 分支流
```
触发器 → IF → [True 路径]
             └→ [False 路径]
```
**使用场景**： 基于条件执行不同操作

### 并行处理
```
触发器 → [分支 1] → 合并
       └→ [分支 2] ↗
```
**使用场景**： 可以同时运行的独立操作

### 循环模式
```
触发器 → 分批拆分 → 处理 → 循环（直到完成）
```
**使用场景**： 分批处理大型数据集

### 错误处理模式
```
主流程 → [成功路径]
         └→ [错误触发器 → 错误处理]
```
**使用场景**： 需要单独的错误处理工作流

## 批量处理模式

### SplitInBatches 循环

SplitInBatches 节点将大型数据集拆分为较小的块进行处理。理解其输出至关重要：

- `main[0]` = **完成** — 仅在所有批处理完成后触发一次
- `main[1]` = **每个批处理** — 每个批处理触发（这是循环体）

```
准备项目 → SplitInBatches → [main[1]: 处理批处理] → (循环返回)
                                  [main[0]: 完成] → Limit 1 → 聚合
```

始终在完成输出后添加 **Limit 1** 节点。

### 选择 batchSize（成本杠杆）

SplitInBatches 循环每次迭代重新运行其整个主体——约 0.8 ms/迭代引擎开销加上主体的成本——所以总计 ≈ `⌈items / batchSize⌉ × (overhead + body)`。batchSize 是直接的速度调节器：

- 选择**实际约束允许的最大批处理量**（API 页面大小、速率限制、内存）。较大的批处理 = 较少的迭代 = 较少的开销；主体仍然看到每个项目。
- `batchSize: 1` 是昂贵的极端——每个项目一个完整的引擎传递。仅在必须一次处理一个项目时使用（嵌套循环控制，或 API 恰好接受一个 id）。
- 如果你只是循环“遍历项目”而没有外部约束，你通常不需要循环——一个 All Items Code 节点以更低的成本处理整个集合。

### 跨迭代数据

循环后，`$('循环内的节点').all()` 返回**仅最后一个批次的项**。要跨所有迭代累积，请在循环内的代码节点中使用 `$getWorkflowStaticData('global')`。参见 n8n 代码 JavaScript 技能的完整模式。

### 嵌套循环

当处理 N 个类别 × 每个类别 M 个项目（其中 API 具有批量限制）时：

```
定义类别（N 项）
  → 外部循环（SplitInBatches，batchSize=1）
    → 准备类别数据
    → 内部循环（SplitInBatches，batchSize=1000）
      → API 调用 → 验证 → (通过 main[1] 循环回内部循环)
    → 内部 done[0] → 速率限制延迟 → 返回外部循环
  → 外部 done[0] → Limit 1 → 最终聚合
```

**接线陷阱**： 内部 done[0] 必须连接回外部循环输入，而不是聚合。外部 done[0] 输入最终聚合。

### API 分页

对于没有多 ID 过滤的 API，使用 `id_from` + 日期窗口进行高效分页：

```
计划 → Set 日期窗口 → Fetch 页面 → 处理
  → IF 还有更多？ → [true] 更新 id_from → Fetch 页面（循环）
                  → [false] → 聚合 → 输出
```

### Dry-Run / 验证容忍度

在禁用 API 写入节点进行干运行时，下游验证节点接收请求正文而不是响应。使验证容忍：

```javascript
// 在验证代码节点中
const body = $input.first().json;
const looksLikeRequest = body.method && body.parameters && !body.status;
if (looksLikeRequest) {
  return [{ json: { status: 'SKIPPED', message: '上游为测试禁用' }}];
}
// 正常响应验证如下...
```

## 热路径上的性能

当工作流处理 **数千个项目** 且 I/O 很少时，其速度由 n8n 跨越每个项目/迭代边界的次数决定——每次跨越设置执行上下文并复制项目。四个架构选择占主导地位：

1. **优先选择较少、较厚的 All-Items 节点而不是长转换链。** 每个节点→节点跳转重新复制所有项目（~0.05 ms/项目/跳转），所以六个串联的 Code/Set 节点成本是单个 All-Items Code 节点执行相同步骤的 ~7 倍。整合热路径。
2. **使用代码“为所有项目运行一次”，而不是“每个项目”** — ~0.02 ms/项目 vs ~0.6 ms/项目（≈25–30×）。串联的 *每个项目* 代码节点是最坏的情况；每个项目的税收会乘以节点数。
3. **最大化 SplitInBatches 循环中的 batchSize**（见上面的批量处理模式）——迭代是成本。
4. **不要微优化表达式** — 复杂性是免费的；节点和迭代计数是你支付的。

**但先进行 профилирование。** 大多数生产工作流是 I/O 约束的——顺序 HTTP / DB / Sheets 调用（每个调用数百毫秒）远远大于所有上述内容。这些规则在转换工作是你垫底，或者一个反模式（每个项目的代码、batchSize 1、长每个项目的链）将廉价操作变成慢操作时才有意义。少于几百个项目时，这一切都不重要。**n8n 代码 JavaScript** 技能提供了完整的测量模型。

## 集成特定陷阱

### Google Sheets

- **永远不要使用 `append`** 在具有公式列的工作表中——它会破坏公式。使用 Google Sheets API `values.update`（PUT）通过 HTTP Request 节点与 `googleApi` 凭证
- **为公式依赖列写入数字，而不是字符串** — 字符串 "4.98" 会破坏 `ADD()` 公式。使用 `parseFloat()` 在代码节点中
- **逐项执行陷阱**：Google Sheets 节点对每个输入项目执行一次。如果你需要单个批量写入，请在代码节点中首先将项目聚合为单个
- **UNFORMATTED_VALUE 返回数字**，而不是像 "N/A" 这样的文本——在代码节点中显式过滤

### Google Drive

- **`convertToGoogleDocument: true` 创建 Google 文档（文本）**，不是 Google 表格——要上传用于下载的 CSV，请完全省略此选项
- **CSV 下载链接格式**：`https://drive.google.com/uc?id={fileId}&export=download` — 而不是 `/view` 链接

### 双向阈值检查

当比较值（价格、数量、指标）时，始终双向检查：

```javascript
// ❌ 仅捕获增加
if (diff > threshold) { flag(); }

// ✅ 捕获峰值和暴跌——两者都是数据质量信号
if (Math.abs(diff) > threshold) { flag(); }
```

## 常见陷阱

### 1. Webhook 数据结构
**问题**：无法访问 webhook 有效负载数据

**解决方案**：数据嵌套在 `$json.body`
```javascript
❌ {{$json.email}}
✅ {{$json.body.email}}
```
参见：n8n 表达式语法技能

### 2. 多个输入项
**问题**：节点处理所有输入项，但我只想一个

**解决方案**：使用“执行一次”模式或仅处理第一个项目
```javascript
{{$json[0].field}}  // 第一个项目仅
```

### 3. 身份验证问题
**问题**：API 调用失败，显示 401/403

**解决方案**：
- 正确配置凭证
- 使用“凭证”部分，而不是参数
- 在工作流激活前测试凭证

### 4. 节点执行顺序
**问题**：节点执行顺序出乎意料

**解决方案**：检查工作流设置 → 执行顺序
- v0：自上而下（遗留）
- v1：基于连接（推荐）

### 5. 表达式错误
**问题**：表达式显示为文字

**解决方案**：在表达式周围使用 {{}}
- 参见 n8n 表达式语法技能的详细信息

## 快速启动示例

### 示例 1：简单的 Webhook → Slack
```
1. Webhook (路径: "form-submit", POST)
2. Set (映射表单字段)
3. Slack (向 #notifications 发送消息)
```

### 示例 2：计划报告
```
1. 计划 (每日 9 点)
2. HTTP 请求 (获取分析数据)
3. 代码 (聚合数据)
4. 电子邮件 (发送格式化报告)
5. 错误触发器 → Slack (失败时通知)
```

### 示例 3：数据库同步
```
1. 计划 (每 15 分钟)
2. Postgres (查询新记录)
3. IF (检查记录是否存在)
4. MySQL (插入记录)
5. Postgres (更新同步时间戳)
```

### 示例 4：AI 助手
```
1. Webhook (接收聊天消息)
2. AI 代理
   ├─ OpenAI 聊天模型 (ai_languageModel)
   ├─ HTTP 请求工具 (ai_tool)
   ├─ 数据库工具 (ai_tool)
   └─ 窗口缓冲记忆 (ai_memory)
3. Webhook 响应 (发送 AI 回复)
```

### 示例 5：API 集成
```
1. 手动触发 (用于测试)
2. HTTP 请求 (GET /api/users)
3. Split In Batches (每次处理 100 个)
4. Set (转换用户数据)
5. Postgres (插入用户)
6. 循环 (返回步骤 3 直到完成)
```

## 最佳实践

### ✅ 做

- 从解决你问题的最简单模式开始
- 在构建之前规划你的工作流结构

- 在激活前使用样本数据测试

- 忽略错误场景
- 当简单的模式就足够时使用复杂的模式
- 在参数中硬编码凭证
- 忘记处理空数据情况
- 混合多个模式而没有明确的边界
- 没有测试就部署
