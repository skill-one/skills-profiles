# n8n 子工作流

子工作流是一个可重用的函数。**执行工作流触发器**声明了类型化的输入，主体部分执行操作，最后一个节点返回输出。调用者通过**执行工作流**节点像其他步骤一样调用它。

这种框架为你提供了函数在世界各地提供的所有好处：封装、重用、可测试性、可替换性。它是 n8n 中主要的重用机制，而且使用得非常少。如果没有它，相同的逻辑会在工作流中到处被复制粘贴——然后在一个地方修复了错误，在第三个副本中遗漏了，你的“相同”副本会悄悄地分道扬镳。

这项技能是关于何时使用子工作流，如何定义其输入/输出合同以便调用者（和代理）实际上可以使用它，如何正确调用它（`all` vs `each`，阻塞 vs 一次性执行），以及如何命名它以便找到而不是重建。

---

## 两个不可协商的要点

其他一切都是判断力。这两点不是。

### 1. 在构建之前搜索

在为通用问题编写逻辑之前，检查是否已经有子工作流可以完成它。社区 MCP 无法按标签过滤工作流，因此**名称是发现表面**：

```
n8n_list_workflows()                          # 扫描库
n8n_get_workflow({ id: "<候选>" })       # 读取其输入/输出 + 主体
```

如果有什么适合的，使用它并告诉用户（“我找到了 `Subworkflow: Parse RFC2822 date` — 使用那个”）。如果没有适合的，使用可发现名称构建它，以便下一次搜索能找到它。发现约定（动词优先的前缀）生活在**NAMING_AND_DISCOVERY.md**中。

### 2. 执行工作流触发器使用“定义下方”与类型字段——不是透传

触发器有两种输入模式。**默认为“定义下方”**，带有明确的类型字段。定义下方是唯一一种为调用者提供填写模式的方式——这是让 AI 代理通过 `$fromAI` 传递值以及让结构化调用者干净地映射字段的原因。透传没有模式，所以触发器不能作为干净的代理工具连接，结构化调用者也没有东西可以绑定。

两个例外，而且只有两个：

- **二进制输入。** 类型字段仅限 JSON。如果子工作流必须接收图像/文件/PDF，你需要透传来让 `binary` 插槽流过。
- **零输入。** 定义下方至少需要一个字段。一个真正无参数的操作（“列出活动凭证”，“当前计数”）没有地方放置一个空的模式，所以透传是唯一的选择。

在两种情况下，透传是一个错误。见下文“输入和输出作为合同”。

## 这应该是子工作流吗？

你即将编写一段逻辑。通过这个：

```
这可能需要在另一个工作流中用到吗？
  └─ 是 → 提取。
是通用问题吗（认证、重试、解析、格式化、ID 生成）？
  └─ 几乎总是 → 提取。这些是标准的可重用子工作流。
是 >5 个节点并且概念上是一个东西吗？
  └─ 可能提取，即使重用不一定确定。它更好隔离。
是一个没有逻辑围绕它的 HTTP 调用吗？
  └─ 不要。一个只是触发 → HTTP → 返回的子工作流增加了无用的边界。
是紧密耦合到这个调用者的数据形状吗？
  └─ 不要现在提取——先修复数据形状，否则你只是将耦合重新定位。
```

提取的理由超出了重用：

- **可读性。** 调用者显示一个节点（“解析日期”）而不是五个。
- **可测试性。** 单独运行子工作流并使用固定的输入：`n8n_test_workflow({workflowId, method: "prepare"})` 命名需要数据的节点，然后 `method: "pinned"` 运行它使用你构建的内容（需要 `N8N_MCP_ACCESS_TOKEN` 和工作流的“MCP 中可用”设置——见 **n8n-mcp-tools-expert**）。子工作流没有 HTTP 触发器，所以默认 `method: "auto"` 无法运行它。
- **可替换性。** 交换实现而不影响调用者。

一个 20 节点的工作流是好的 *如果它主要是执行工作流调用和决策的线性序列*——每个节点只有一个目的，并且你通过打开它调用的子工作流来检查一个部分。一个 20 节点的工作流的行内转换不是好的。如果你有 15+ 个节点并且大部分不是子工作流调用和分支，请提取更多。

## 无状态 vs 有状态（故意）

两者都是第一类。选择取决于意图和合同承诺的内容。

**无状态**——输入输入，输出输出，没有超出 I/O 的其他内容。纯逻辑的默认值。当你需要它时，你调用它而不用担心副作用发生。

- `Subworkflow: Parse RFC2822 date` — 日期字符串 → ISO 日期或错误。
- `Subworkflow: Compute MRR from subscription` — 订阅对象 → 数字。
- `Subworkflow: Format invoice as HTML` — 发票数据 → HTML 字符串。

**有状态（故意）**——在干净的合同后面读取或写入外部状态。这是仓库模式：子工作流抽象了存储操作，以便调用者用领域术语思考，而不是 SQL。

- `Customer: get by id` — id → 客户对象或 `{ ok: false, error: "not_found" }`。读取数据库。
- `Customer: write billing record` — 记录 → `{ ok: true, id }`。写入数据库。
- `Notify: send to on-call` — 渠道，消息 → `{ ok: true, messageId }`。调用 Slack/SMTP。

为什么将这些构建为子工作流：调用者认为 `get customer by id` 而不是编写查询；你可以交换存储（Postgres → Supabase，原生节点 → HTTP）而不触动单个调用者；并且幂等性、重试和验证集中在一个地方。

要避免的是**意外的状态**——一个被命名/描述为纯的子工作流却悄悄地写入日志表。这会伏击每个调用者，他们合理地假设它是安全的可以重试或组合。要么让副作用成为合同的一部分（重命名它，记录它，返回它的结果），要么把它移出去。

## 输入和输出作为合同

触发器声明的字段和最后一个节点的输出形状*就是*子工作流的 API。将它们像一样对待。

### 声明类型化的输入（定义下方）

每个声明的输入都是一个调用者填充的类型化参数。故意选择类型（`string`，`number`，`boolean`，`array`，`object`）——代理使用这些作为填充工具参数的必需类型，人类依赖于它们来连接调用者。触发器节点参数看起来像这样：

```json
{
  "type": "n8n-nodes-base.executeWorkflowTrigger",
  "parameters": {
    "workflowInputs": {
      "values": [
        { "name": "list_of_ids",        "type": "array" },
        { "name": "include_transcript", "type": "boolean" },
        { "name": "session_id",          "type": "string" }
      ]
    }
  }
}
```

在工作流内部，将它们读取为 `$json.list_of_ids`，或者从任何下游读取为 `$('When Executed by Another Workflow').first().json.<field>`（见 **n8n-expression-syntax**）。

### 合同规则

- **在工作流 `description` 中记录输入和输出。** 字段名、类型、目的和一些代表性关键词。描述是调用者（人类和代理）阅读合同的地方，也是 `n8n_list_workflows` 匹配的内容。
- **返回一致、自然的形状——不是存储形状。** 一个拥有数据表或 S3 文件的子工作流隐藏了这种表示方式。数组返回为数组，对象返回为对象，日期返回为 ISO 字符串——无论底层存储是否为 JSON-字符串化的文本。返回合同是 *接口*；存储布局是 *实现细节*。常见错误：一个子工作流有一个“新鲜”路径（刚刚计算，自然形状）和一个“缓存”路径（刚刚从字符串化列读取）。错误直觉：将新鲜路径字符串化以匹配缓存一个。正确直觉：解析缓存路径，以便两者都返回自然形状。
- **返回错误，而不是总是抛出。** 对于 *预期的* 失败（解析错误，未找到），返回 `{ ok: false, error: "..." }`，以便调用者可以分支而无需连接错误输出。保留抛出用于 *真正意外的* 失败——见 **n8n-error-handling**。
- **合同一旦有调用者就冻结了。** 添加 *可选* 字段是安全的。重命名或删除字段是危险的：n8n 不会在无法识别的输入字段上出错——主体只看到 `undefined`，调用者不知道，并且你得到一个无声的合同破坏。要更改字段，请枚举每个调用者（`n8n_list_workflows` + 检查每个执行工作流节点），在同一更改中迁移它们，并在完成前使用 `validate_workflow` 和 `n8n_get_workflow` 进行验证。

### 最后一个返回节点——合法的 Set 异常

使用最后的 **Set / 编辑字段** 节点塑造输出，命名为 `Return` 或 `Return <东西>`。这是 Set 节点值得它违背 **n8n-expression-syntax** 中通常“不要添加一个尾随 Set 节点”建议的唯一地方：子工作流的最后一个节点的隐式消费者是 *每个调用者*，所以显式的 Set 使返回合同可见——一个读者通过阅读一个节点就能看到整个 API，并且你剥离了最后一个计算节点携带的任何噪声字段。

## 调用子工作流：`mode` 和 `waitForSubWorkflow`

调用者**执行工作流**节点的两个设置决定了子工作流如何运行。

### `mode`：`all` vs `each`

| `mode` | 子工作流运行 | 每次运行的项目 |
|---|---|---|
| `all` (默认) | 一次 | 所有 N 个项目（像往常一样按项目流过节点） |
| `each` | N 次 | 每次运行正好一个项目 |

对于只按常规方式处理项目的主体，两者是等效的——n8n 节点无论如何都是按项目迭代。**分裂只有在主体假设它看到 exactly 一个项目时才重要**：一次运行的聚合，“这是要采取行动的客户”逻辑，或一次性的最终写入应该每个输入一次。在 `all` 下，主体一次得到所有 N 个项目，并且假设被破坏（你聚合了所有人到一个结果而不是一个每个输入一个）。在 `each` 下，每次调用得到一个项目，并且假设成立。

所以：当你需要按项目迭代时，请优先选择 `mode: each` 而不是在工作流内部放置一个 Loop Over Items 节点。模式为你执行迭代，并且主体保持简单和单项目。

### `waitForSubWorkflow`：`true` vs `false`

`waitForSubWorkflow` 默认为 `true`——调用者阻塞直到子工作流返回，然后继续使用其输出。设置 `options.waitForSubWorkflow: false` 以实现一次性执行：调用器立即继续，子工作流在后台运行，下游看不到返回数据。

### n8n 提供的唯一并行化方式

`mode: each` + `waitForSubWorkflow: false` 是**获得真正并发子工作流执行的唯一方式**：N 个项目派发 N 次运行，并行执行（仍然受每个实例并发限制）。调用者不知道何时——或者是否——任何它们完成了，所以它只有在有单独的完成跟踪机制时才有用，通常是子工作流在它进行时更新数据表。完整的阶段 → 派发 → 轮询模式在 **SUBWORKFLOW_PATTERNS.md** 中（“一次性执行并行化”）。

## 按输入形状拆分（N+1 模式）

当子工作流有多个输入路径，其合同 *真正* 不同时——二进制 vs JSON，同步 vs 异步，不同的认证方案——不要把它们塞到一个触发器下，使用透传 + 内部 Switch。强迫函数是真实的：透传（用于二进制或零输入）和定义下方（用于类型化输入）在单个触发器上是互斥的。反射是“选择透传，因为它是最宽松的，然后在内部分支”的成本，你失去了类型化模式，增加了分支形状的杂项，并且每次新的输入形状都变成了更多的分支。

修复方法：对于 N 个不同的输入合同，构建 **N+1 个子工作流**——每个外部一个合同，每个都做其输入特定的准备（验证、获取、哈希、提取），并调用一个共享的下游子工作流，具有归一化的形状。共享核心有一个单一的类型化输入合同，并且不知道哪个外部调用了它。工作示例（从外部 ID 处理纸张 *或* 上传的 PDF）在 **SUBWORKFLOW_PATTERNS.md** 中。

## 子工作流作为代理工具

一个具有类型化定义下方触发器的子工作流可以作为 AI 代理工具：代理通过 `$fromAI` 填充声明的字段，主体运行，结果作为工具观察返回。这是默认使用定义下方的高价值原因——透传触发器无法暴露可填充的模式。

零输入的情况仍然可以作为工具工作：代理的唯一决定是是否调用。二进制情况无法干净地作为工具连接，因为代理不能直接传递二进制。

对于工具命名、描述和二进制输入的解决方案，见 **n8n-agents**；对于二进制处理本身，**n8n-binary-and-data**。

## 反模式

| 反模式 | 出现什么问题 | 修复 |
|---|---|---|
| 在三个工作流中重复相同的逻辑 | 一个错误在两个地方被修复，第三个地方漂移 | 一次提取到一个命名的子工作流 |
| 在不搜索的情况下构建一个新的子工作流 | 库中增长重复项；未来的搜索找到两者 | `n8n_list_workflows` / `n8n_get_workflow` 首先搜索 |
| 触发器设置为透传，但不处理二进制和不是零输入 | 没有模式 → 代理不能填充参数，结构化调用者不能绑定 | 使用定义下方与类型化的 `workflowInputs.values` |
| 零输入透传，没有清晰和记录 | 主体在调用者转发了什么的情况下悄悄读取随机字段 | 从一个“只保留 Set”Set 节点开始 + 一个粘性注释“预期无输入” |
| 被命名/描述为纯的子工作流，却悄悄地写入状态 | 调用者不能推理重试/幂等性；副作用伏击他们 | 让副作用成为合同的一部分，或者把它移出去 |
| 没有子工作流的 `description` | 不会在未来的搜索中找到；没有人知道它做什么 | 设置 `description`，记录输入/输出形状 + 关键词 |
| 名称像 `Helper 3` / 无前缀 | 没有说明它做什么，匹配不到前缀搜索 | 动词优先前缀（`Subworkflow:`，`<领域>`：，`Tool:`） |
| `mode: all` 在一个假设一个项目的主体上 | 将所有输入聚合到一个结果而不是一个每个输入一个 | `mode: each`（并且跳过内部的 Loop Over Items） |
| 在不迁移调用者的情况下重命名一个活动的输入字段 | 调用者发送旧名称 → 主体看到 `undefined`，任何地方都没有错误 | 在同一更改中迁移每个调用者；使用 `validate_workflow` 和 `n8n_get_workflow` 在完成前验证 |
| 30 节点的工作流，没有提取 | 难以阅读、测试和替换 | 将逻辑部分提取到子工作流中 |

## 社区 MCP 不提供的内容

| 想要做什么 | 现实 |
|---|---|
| 按 **标签** 过滤/发现工作流 | MCP 无法读取或按标签过滤（仅 UI）。发现是 *名称* —— 使用动词优先前缀和 `n8n_list_workflows`。 |
| 捕获 **未识别的输入字段** | n8n 不会在其中一个上出错。主体看到 `undefined`，调用者永远不会知道——一个无声的合同破坏。手动跨调用者验证字段重命名。 |
| 不使用类型化触发器设置输入模式/字段 | 触发器节点本身必须声明 `workflowInputs.values`。使用 `n8n_update_partial_workflow` (`updateNode` / `patchNodeField`) 配置它；使用 `get_node` / `validate_node` 验证。 |

MCP **可以**做：构建子工作流及其调用者（`n8n_update_partial_workflow` with `addNode` / `addConnection` / `updateNode` / `patchNodeField`），发现现有的（`n8n_list_workflows`，`n8n_get_workflow`），验证（`validate_workflow`，`n8n_validate_workflow`），孤立测试（`n8n_test_workflow`），检查运行（`n8n_executions`），用数据表支持有状态的子工作流（`n8n_manage_datatable`），并激活（`activateWorkflow`）。

## 与其他技能的集成

- **n8n-workflow-patterns** — 使用它来决定编排工作流的整体形状；使用这项技能来决定哪些部分成为子工作流。
- **n8n-mcp-tools-expert** — `n8n_list_workflows`，`n8n_get_workflow`，`n8n_update_partial_workflow` 和 `n8n_manage_datatable`（有状态子工作流和数据表以及“一次性执行并行化”的轮询）的参数格式。
- **n8n-node-configuration** — `workflowInputs` 和 `inputSource`（定义下方 vs 透传）是触发器上的显示选项驱动的配置。
- **n8n-expression-syntax** — 读取输入（`$json`，`$('When Executed by Another Workflow')`）和合法的最终 Set 异常都生活在这里。
- **n8n-error-handling** — 预期的失败返回 `{ ok: false, error }`；意外的失败抛出并通过错误输出路由。子工作流边界是一个定义那条线的自然地方。
- **n8n-validation-expert** — 验证子工作流及其调用者；一个未识别的输入字段不会在这里出现，所以手动验证字段更改。
- **n8n-code-javascript / n8n-code-python** — 当子工作流的身体是一个单个 Code 节点时，其合同仍然是触发器的类型化输入和返回形状，而不是 Code 节点的内部。
- **n8n-code-tool** — Custom Code Tool 是 *行内* 代理工具选项；子工作流工具是可重用的、多步骤选项。当逻辑在代理之间共享或需要完整的 Code 节点沙盒时，请选择子工作流。
- **n8n-agents** — 将类型化的子工作流连接为代理工具，包括零输入和二进制情况。
- **n8n-binary-and-data** — 用于二进制输入的透传触发器，以及为什么二进制不能直接通过代理工具传递。
- **using-n8n-mcp-skills** — 在构建过程中何时咨询哪些技能。
