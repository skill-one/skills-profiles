# 从 CI 更新组件截图

**截图** **图片** 并不存储在仓库中——它们存放在外部服务 (`hediet-screenshots.azurewebsites.net`) 中，以提交 SHA 为键。但一部分 fixtures 通过 **哈希** 在 [`test/componentFixtures/blocks-ci-screenshots.md`](../../../test/componentFixtures/blocks-ci-screenshots.md) 中被固定，并且该文件 **是** 提交的。当这些哈希值发生变化时，CI 会失败，你必须更新该文件。

## 两种不同的结果，只有一种会阻止

[`.github/workflows/component-fixtures.yml`](../../workflows/component-fixtures.yml) 中的 `Screenshots & Tests` 任务会产生两个独立的结果：

| 结果 | 阻止？ | 操作 |
| --- | --- | --- |
| 截图 **差异报告** (PR 评论中的前后图片) | 否——信息性 | 审查视觉效果。无需提交。 |
| **blocks-ci 哈希不匹配** | 是——失败检查 | 更新 `blocks-ci-screenshots.md` 并提交。 |

一个 fixture 通过 `labels: { kind: 'screenshot', blocksCi: true }` 选择进入阻止门。只有这些 fixture 会出现在 `blocks-ci-screenshots.md` 中。

失败看起来像这样：

```
##[error]blocks-ci 截图哈希与提交的文件不匹配。请查看 PR 评论或作业摘要以获取更新内容。
```

## 第 1 步：从 CI 获取预期的哈希值

> **切勿在本地重新生成哈希值。** 它们是渲染的 PNG 字节哈希值，在 `ubuntu-latest` 上生成。在 macOS 或 Windows 上渲染会产生不同的字节，因此哈希值不同，因此本地生成的值将导致 CI 失败。始终从 CI 作业中复制这些值。

三个表面包含相同的内容——使用任何方便的表面：

- 标题为 "blocks-ci screenshots changed" 的 **PR 评论**（仅限非分支 PR）——包含完整的更新文件和补丁。
- **作业摘要**，它获得相同的正文，并且是分支 PR 唯一收到的表面。
- **作业日志**，其最后一步打印统一差异：

```bash
gh api repos/microsoft/vscode/actions/jobs/<JOB_ID>/logs > "$TMPDIR/ci-job-log.txt"
grep -n '##\[error\]' "$TMPDIR/ci-job-log.txt"
```

使用以下命令找到失败的作业 ID：

```bash
gh pr checks <PR> --json name,link,bucket --jq '.[] | select(.name == "Screenshots & Tests")'
```

## 第 2 步：在接受更改之前验证其是否为有意为之

此门存在是为了捕获 **无意** 的布局回归，因此在不查看图片的情况下接受新哈希值会使其失去作用。图片可以通过哈希公开获取，因此拉取旧的（已提交的）和新的（来自 CI 的）版本并比较：

```bash
curl -sL -o old.png "https://hediet-screenshots.azurewebsites.net/images/<OLD_HASH>"
curl -sL -o new.png "https://hediet-screenshots.azurewebsites.net/images/<NEW_HASH>"
```

然后查看它们，并通过定位更改而不是目测完整截图来本地化更改——差异通常只有一两个像素：

```bash
python3 -c "
from PIL import Image, ImageChops
a = Image.open('old.png').convert('RGB'); b = Image.open('new.png').convert('RGB')
print('diff bbox:', ImageChops.difference(a, b).getbbox())
"
```

确认差异与 PR 的意图一致。如果 fixture 与更改无关，或者偏移量大于预期，则将其视为回归并修复代码而不是哈希值。

## 第 3 步：应用并提交

仅编辑 `test/componentFixtures/blocks-ci-screenshots.md` 中更改的行，将图像 URL 中的旧哈希值替换为新哈希值：

```md
#### editor/inlineChatZoneWidget/InlineChatZoneWidget/Dark
![screenshot](https://hediet-screenshots.azurewebsites.net/images/<NEW_HASH>)
```

该文件由 [`build/lib/screenshotBlocksCi.ts`](../../../build/lib/screenshotBlocksCi.ts) 生成，并按 **字节逐字节** 进行比较，因此请保留 `<!-- auto-generated by CI — do not edit manually -->` 头部、`#### <fixtureId>` / 图像链接配对、条目之间的空行以及 `fixtureId` 排序顺序。验证你的编辑与 CI 报告的差异完全相反：

```bash
git diff test/componentFixtures/blocks-ci-screenshots.md
```

然后提交并推送。检查将重新运行并通过；合并后 `main` 上的哈希值将成为新的基线。

## 进一步调查

原始捕获的图像和运行清单作为附件上传：

```bash
gh run download <RUN_ID> --name screenshots --dir .tmp/screenshots
```

`manifest.json` 将每个 `fixtureId` 映射到其 `imageHash` 和任何渲染错误。

## 来自同一作业的相关失败

如果 fixture **未能渲染** (`Fail if fixtures had errors`) 或 Playwright fixture 测试失败，检查也会失败。这些都是真正的错误——更新哈希值无济于事。查找日志中的 `::error::<fixtureId>:`，并下载 `playwright-test-results` 附件以获取测试失败。
