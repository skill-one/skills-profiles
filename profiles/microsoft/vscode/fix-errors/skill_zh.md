在修复遥测面板中的未处理错误时，问题通常包含错误消息、堆栈跟踪、命中次数和受影响用户数量。

## 方法

### 1. 不要在崩溃点修复

错误在堆栈跟踪中的特定行显示，但**修复几乎永远不会在那里**。在崩溃点修复（例如，在 `revive()` 函数中添加 `typeof` 守卫、用 try/catch 吞噬错误或返回回退值）只会掩盖真正的问题。无效数据仍然会通过系统并导致其他地方失败。

### 2. 通过调用栈向上追踪数据流

从下到上逐个阅读堆栈跟踪中的每个帧。对于每个帧，理解：
- 传递了什么数据以及期望什么数据
- 数据的来源（IPC 消息、扩展 API 调用、存储、用户输入等）
- 数据是否可能在那个点被损坏或格式错误

目标是找到**无效数据的产生者**，而不是在无效数据上崩溃的消费者。

### 3. 当无法从堆栈中识别产生者时

有时堆栈跟踪只显示接收/消费端（例如，IPC 服务器处理程序）。发送端在不同的进程中，不在堆栈中。在这种情况下：

- **在消费端丰富错误消息**，添加诊断上下文：无效数据的类型、其值的截断表示以及接收它的操作/命令。这些信息会自动通过未处理错误管道流入错误遥测面板。
- **不要无声地吞噬错误** — 让它仍然抛出，以便它在遥测中仍然可见，但带有足够的上下文以识别下一个遥测周期中的发送者。
- 考虑在抛出底层验证函数中添加相同的丰富信息（例如，在错误消息中包含无效值），以便遥测无论调用位置如何都能捕获它。

### 4. 当产生者可以识别时

直接修复产生者：
- 在通过 IPC 发送、存储或传递给 API 之前验证或清理数据
- 确保序列化/反序列化正确保留类型（例如，URI 对象应序列化为 `UriComponents` 对象，而不是字符串）

## 示例

给定一个堆栈跟踪，如下：
```
at _validateUri (uri.ts)       ← 验证抛出
at new Uri (uri.ts)            ← 构造函数
at URI.revive (uri.ts)         ← revive 假设有效的 UriComponents
at SomeChannel.call (ipc.ts)   ← IPC 处理程序从另一个进程接收参数
```

**错误的修复**：在 `URI.revive` 中添加 `typeof` 守卫，对于非对象输入返回 `undefined`。这会抑制错误，但调用者仍然期望一个有效的 URI，并且稍后会失败。

**正确的修复（当产生者未知时）**：在 IPC 处理程序级别和 `_validateUri` 本身中丰富错误，以包含实际无效值，以便遥测显示正在发送什么数据以及从哪里发送。示例：
```typescript
// 在 IPC 处理程序中 — 在 revive 之前验证
function reviveUri(data: UriComponents | URI | undefined | null, context: string): URI {
    if (data && typeof data !== 'object') {
        throw new Error(`[Channel] 无效的 URI 数据对于 '${context}': 类型=${typeof data}, 值=${String(data).substring(0, 100)}`);
    }
    // ...
}

// 在 _validateUri 中 — 包含方案值
throw new Error(`[UriError]: 方案包含非法字符。scheme:"${ret.scheme.substring(0, 50)}" (len:${ret.scheme.length})`);
```

**正确的修复（当产生者已知时）**：修复发送损坏数据的代码。例如，如果身份验证提供程序将 URI 字符串化而不是将 `UriComponents` 对象传递给日志创建调用，请修复该调用位置以传递正确的对象。

## 修复之前理解错误构造

在提出任何修复之前，**始终找到并阅读构造错误的代码**。在代码库中搜索错误类名或错误消息的唯一子字符串。构造代码揭示：

- **触发错误的条件** — 阈值、验证检查、状态断言
- **错误编码的分类或类别** — 错误可能有需要不同修复策略的子类型
- **错误参数的含义** — 消息中嵌入的数值、比率或标志通常编码诊断上下文
- **错误是否可操作** — 一些错误是基于阈值的警告，阈值可能按设计合法地超过

使用这些理解来确定正确的修复策略。构造代码是真相来源 — 不要仅从错误消息中假设错误含义。

### 示例：监听器泄漏错误

搜索 `ListenerLeakError` 导致 `src/vs/base/common/event.ts`，其中构造代码揭示：

```typescript
const kind = topCount / listenerCount > 0.3 ? 'dominated' : 'popular';
const error = new ListenerLeakError(kind, message, topStack);
```

阅读此代码告诉你：
- 错误基于比率有两个类别
- **被主导**（比率 > 30%）：一个代码路径解释了大多数监听器 → 该代码路径是问题所在，修复其释放
- **流行**（比率 ≤ 30%）：许多不同的代码路径每个贡献少量监听器 → 已识别的堆栈跟踪不是根本原因；它只是许多堆栈中最相似的。调查发射器和其聚合订阅者
- 对于流行泄漏：不要移除顶级堆栈中出现的缓存/池化/重用模式 — 它们存在是为了解决其他问题。如果聚合计数按设计（例如，许多菜单订阅共享上下文键服务），则关闭问题为“未计划”

这项分析来自阅读构造代码，而不是从记忆中的监听器泄漏规则。

## 指南

- 优先选择丰富错误消息而不是添加 try/catch 守卫
- 截断包含在错误消息中的任何用户控制值（以避免 PII 并保持消息长度有限）
- 不要以影响所有调用者的方式更改共享实用函数的行为（如 `URI.revive`） — 在特定的调用位置或产生者处修复
- 在做出更改后运行相关的单元测试
- 通过构建任务在声明工作完成前检查编译错误
