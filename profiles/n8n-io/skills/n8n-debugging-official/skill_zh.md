# n8n 调试

当出现问题时，原因几乎总是：

1. **参数配置错误**（值错误、类型错误、缺少字段）。
2. **过时的假设**（不同版本、行为与记忆中不同）。
3. **路径配置错误或连接错误**（输出索引错误、合并输入错误、缺少连线、IF/Switch 连接到错误分支）。
4. **上游数据被剥离**（某个中间节点将 `$json` 替换为其自己的输出，导致下游 `$json.x` 解析为 null，即使“它应该存在”）。修复方法：通过名称引用稳定的上游节点（`$('Earlier Node').item.json.x`）。
5. **项上下文丢失**（在 Aggregate、Execute Once 或 Split Out 流程之后，n8n 无法确定地匹配 `.item` 引用，错误信息类似“表达式引用...多个匹配项”）。修复方法：使用合并节点重新建立上下文，使用 `$input.all().find(...)` 进行显式查找，或重新设计以保持项对应关系稳定（例如，拆分为无状态子工作流）。
6. **逻辑错误**（连线正确且参数正确，但工作流执行了错误操作，与代码中的逻辑错误类似）。
7. **真实 Bug**（罕见但确实存在）。

系统性地诊断：先进行廉价检查，只有在这些检查失败时才进行更深入的调查。

## 非协商项

**相信用户**。“这不起作用”意味着某些行为不符合他们的预期，即使他们描述的症状不够精确。不要以“应该工作”或“你确定你在做 X 吗？”来驳回。先进行调查：用户是关于“应该发生什么”的真相，执行数据和源是关于“实际发生什么”的真相。当你找不到原因时，“我还不知道”比听起来合理的编造要好。

## 强制默认值（原因到廉价检查的匹配）

按可能性顺序匹配原因到廉价检查：

1. **参数配置错误** → 通过 `get_node_types` 重新获取，与 `get_workflow_details` 比较，查找类型/值/缺少字段的不匹配。在失败的节点上单独使用 `validate_node_config` 直接返回每个参数的错误；比手动检查具有深层/条件形状的节点的差异更快。
<!-- 临时：当实例元数据工具添加时，更改要求用户仅使用该工具 -->
2. **过时的假设** → 询问 n8n 版本，询问用户上次更新技能插件的时间，如果行为与技能矛盾，则怀疑漂移。
3. **路径配置错误或连接错误** → 通过 `get_workflow_details` 检查 `connections` 对象。对于合并输入不匹配，请参阅 `n8n-node-configuration-official` `references/MERGE_NODE.md`。
4. **上游数据被剥离** → 跟踪 `$json.x` 引用链，查找任何将 json 替换为其自己输出的节点。常见违规者：Aggregate、HTTP-binary、从文件提取、在“为所有项运行”模式下运行的代码、分支合并。不全面：任何节点都可以这样做，如果其输出形状不包括上游字段。
5. **项上下文丢失** → 检查任何 Aggregate / Execute Once / Split Out 下游的 `.item` 引用，切换到 `$input.all().find(...)` 或合并锚点。
6. **逻辑错误** → 通过 `get_workflow_execution` 逐步跟踪数据，比较每个节点的输出与预期。
7. **真实 Bug** → 转到阅读 n8n 源代码，然后是 GitHub 问题，然后是解决方案。

对于外部 API 问题，上游服务的 API 文档（不是 n8n 的包装器）才是真相。如果需要，获取 API 文档和 n8n 的源代码进行调试。

## 分步指南

当上述廉价检查不能立即确定原因时，按顺序执行这些步骤。

### 第 1 步：确认症状

询问：

- 他们期望什么？
- 实际发生了什么？
- 错误信息文本？
- 它最后一次工作是什么时候？自那时以来发生了什么变化？

模糊的（“它坏了”）在具体的情况下变得可行（“电子邮件发送到错误的地址”或“工作流返回 500 且正文为空”）。

### 第 2 步：检查执行

```
get_workflow_execution({ executionId: <execution_id>, workflowId: <workflow_id>, includeData: true })
```

查看：

- **哪个节点失败了？**
- **它有什么输入？**
- **什么错误信息？** 仔细阅读。通常指向原因。

没有执行 ID？要求用户重新运行。

### 第 3 步：重新获取工作流

```
get_workflow_details({ workflowId: <workflow_id> })
```

确认实际当前状态。用户可能正在查看不同的工作流或记住过时的版本。

比较：

- 节点与用户的 mental model。
- 连接与意图：通过 `get_workflow_details` 拉取并比较 `connections` 对象与 SDK 代码。
- 凭据与预期（根据 `n8n-credentials-and-security-official`）。
- **上游剥离风险：** 数据源和下游 `$json.x` 消费者之间的任何节点替换 json 为其自己的输出？常见违规者是 HTTP-binary、从文件提取、Aggregate、在“为所有项运行”模式下运行的代码和分支合并，但任何节点都可以这样做，如果其输出形状不包括上游字段。消费者应通过名称引用源节点（`$('Source Node').item.json.x`），而不是 `$json`。否则该字段将静默解析为 null。
- **项上下文风险：** 任何 Aggregate / Execute Once / Split Out 后跟下游 `.item` 引用？n8n 可能无法确定地匹配项。在过去的执行中查找“表达式引用...多个匹配项”。

### 第 4 步：重新获取节点类型

```
get_node_types([{ name: '<failed-node>', resource: '...', operation: '...' }])
```

比较实际参数形状与配置。常见不匹配：

- 缺少必需参数。
- 类型错误（字符串与数字等）。
- **`object` 和 `array` 在 n8n 的 UI 类型下拉菜单中是不同的**（Set、IF、Switch、Filter、任何要求您选择类型的 UI）。选择 `object` 不会接受数组值，反之亦然。在表达式本身中它是正常的 JS（数组*是*对象），所以这种区别只在那些 UI 类型选择表面出现。在 `={{ ... }}` 表达式返回类型槽的容器形状错误时要注意这一点。
- 依赖参数集没有其父级（例如，`credentials` 没有 `authentication !== 'none'`，或者 `query` 没有 `operation === 'executeQuery'`）。使用 `get_node_types` 传递正确的判别器重新获取。

如果手动形状与配置的差异很繁琐（深层参数、AI 工具子节点、许多条件分支），直接运行 `validate_node_config`。返回 `{ path, message }` 每个失败。对于工具子节点设置 `isToolNode: true`。

### 第 5 步：使用固定数据测试

```
prepare_workflow_pin_data({ workflowId: '<id>' })
test_workflow({ workflowId: '<id>' })
```

受控输入将“工作流损坏？”与“输入奇怪？”隔离。如果固定数据工作正常但真实输入失败，问题出在真实输入处理中。

如果固定数据也产生错误输出，那很可能是逻辑错误：跟踪每个节点的输出与您预期的内容。在测试运行上使用 `get_workflow_execution` 给您每一步实际发出的数据，这是每个节点所做操作的真相来源。

### 第 6 步：阅读 n8n 源代码

当一切检查合格但行为仍然似乎错误时：

```
github.com/n8n-io/n8n
```

- `packages/nodes-base/nodes/<NodeName>` 用于内置节点。
- `packages/cli/src/...` 用于执行逻辑。
- `packages/core/src/...` 用于工作流运行时。

代码的行为是真相。

参见 `references/FETCHING_N8N_SOURCE.md`。

### 第 7 步：怀疑双方漂移

如果步骤 1-6 都检查合格但行为仍然不符合预期，版本漂移是最可能剩余的原因。双方独立漂移：

<!-- 临时：当实例元数据工具添加时，更改要求用户仅使用该工具 -->
- **他们的 n8n 实例版本**。询问。（UI：`Settings → About`，或 `GET /rest/settings`。）在较旧的实例上，技能假设的参数和工具可能缺失；在非常新的实例上，参数形状或工具名称可能已移动。建议更新到最新的 n8n 发布版，或者如果据说有修复或问题是最近的，则更新到最新的 beta。
- **此技能插件的版本**。这些技能随时间相对于 n8n 漂移。如果用户安装了插件有一段时间，建议在技能仓库上执行 `git pull`（或插件管理器的更新命令）。参见 README 的“漂移”部分。

漂移表现为：`get_node_types` 中的参数形状不匹配、MCP 工具不存在或带有新参数、工具描述与技能教授的内容矛盾、行为与技能的声明相矛盾。当你发现任何这些情况时，明确向用户指出漂移：*"这可能是在您的 n8n 版本和这些技能之间的漂移。你能告诉我你的 n8n 版本，以及你上次更新技能的时间吗？"*

在更新双方后如果问题仍然存在，继续执行步骤 8。

### 第 8 步：报告或解决方案

对于确认的 Bug：

- 要求用户在 https://community.n8n.io 上发布问题。
- 向用户展示一个清晰的复现。
- 检查 n8n GitHub 问题。可能已经提交。
- 如果阻塞，则使用不同的节点/方法进行解决方案，并在工作流笔记中记录。
- 如果有修复正在进行中，则用 `<!-- TEMPORARY: ... -->` 标记解决方案。

## 反模式

| 反模式 | 出现什么问题 | 修复 |
|---|---|---|
| “它应该工作，你确定你在做 X 吗？” | 忽略用户的报告，错过真正的问题 | 相信用户。调查。 |
| 未经检查就重新运行 | 两次相同失败，没有新信息 | `get_workflow_execution` 在失败的运行上，阅读错误 |
| 假设文档准确当行为矛盾时 | 接受错误的 mental model | 阅读源代码。行为是真相 |
| 在配置节点失败时在 Code 节点中重新实现逻辑 | 隐藏 Bug，没有修复根本原因 | 先诊断，只有在确认 Bug 时才进行解决方案 |
| 随机删除节点进行二分 | 浪费时间 | 通过 `get_workflow_execution` 直接找到失败的节点 |
| 要求用户重新截图而不是通过 MCP 检查 | 慢，易出错 | 使用 `get_workflow_details` 和 `get_workflow_execution` |
| 在你只解决了 Bug 而没有理解它的情况下称其为“已修复” | Bug 以稍微不同的形式复发 | 记录原因。如果解决方案，用 `<!-- TEMPORARY: -->` 标记 |
| 在未询问用户的 n8n 版本或他们上次更新技能时称其为“Bug” | 真实原因是漂移，用户更新后“Bug”消失 | 在报告之前询问双方版本。参见步骤 7。 |
