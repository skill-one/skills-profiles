# n8n 循环

"循环"的三个含义对应三种机制：

1. **"为每个项目运行此节点。"** 默认。大多数节点会自动循环，所以无需操作。
2. **"用所有项目运行此节点*一次*，而不是每个项目运行一次。"** `executeOnce` 设置（单个布尔值）。
3. **"以显式批次处理项目，并在迭代之间控制流程。"** `Loop Over Items` 节点（以前称为 `Split In Batches`）。

对于分页 API，HTTP 请求节点具有内置的分页功能。几乎总是比手动构建的页码计数循环更可取。

## 模型：项目是一个数组

节点之间的数据流是一个项目数组，每个 `{ json: {...}, binary?: {...} }`。50 个项目 = 50 项数组。

默认：节点每个项目运行一次。具有 50 个输入项目的 HTTP 请求会发出 50 个请求并输出 50 个结果项目。这是大多数工作流依赖的隐式循环。

**输入数组就是循环。** 通过控制数组来控制迭代。

## 非协商事项

**`executeOnce: true` 始终用于节点应每次运行一次，而不是每个项目运行一次。** 包括通过 `$input.all()` / `$('Node').all()` 加上 `.map()` / `.filter()` / `.reduce()` 跨数据集聚合的表达式（没有它，聚合会为上游的每个项目计算 N 次，通常在下游产生 N 个重复项）。还包括单次通知、聚合写入、摘要消息。

**特例：** `.all()` 与另一个节点的 `.item`（每个项目的查找，例如 `$('Get Tags').all().filter(tag => $('Search Posts').item.json.tag_ids.includes(tag.json.id))`）是真正的每个项目工作，应该保持 `executeOnce` 关闭。有关完整区别，请参阅 `n8n-expressions-official` 技能的 `executeOnce` 部分。

## 强制默认值

- **当默认迭代足够时，不要构建循环。** 大多数节点（HTTP 请求、原生服务节点、Set、IF/Switch）会自动每个输入项目运行一次：N 个项目输入，N 次运行。要执行 N 个 HTTP 调用或创建 N 条记录，只需将源连接到该节点。除非需要每次迭代的控制，否则不要使用 `Loop Over Items`。（注意：`Execute Workflow` 是例外。它默认为单个所有项目批次。请参阅 `n8n-subworkflows-official` 的 `mode: 'each'`。）
- **对于分页 API，使用 HTTP 请求的内置分页。** 除非 API 真正奇怪，否则不要用 `Loop Over Items` + 手动 `$pageCount` 重新发明。请参阅 `references/HTTP_PAGINATION.md`。
- **`Loop Over Items` 用于显式分批或每次迭代的控制**（速率限制、每批错误恢复、状态块、轮询）。请参阅 `references/LOOP_OVER_ITEMS.md`。
- **每个项目的迭代是顺序的，不是并行的。** 每个项目完成之前下一个项目才会开始，即使在看似并行的分支上也是如此。对于真正的并发模式，请参阅 `n8n-subworkflows-official`。

## 决策树：我需要哪种机制？

```
需要为每个项目做些什么？
├── 默认每个项目的迭代就足够
│   └── 只需连接节点。完成。
│
├── 节点应该总共运行一次，而不是每个项目运行一次？
│   └── 在节点上设置 `executeOnce: true`
│
├── 分页 API（需要多个 HTTP 调用来获取所有页面）？
│   └── 使用 HTTP 请求的分页选项（请参阅 `references/HTTP_PAGINATION.md`）
│
├── 需要显式分批（速率限制、块大小、每批错误处理）？
│   └── 使用 Loop Over Items 节点（请参阅 `references/LOOP_OVER_ITEMS.md`）
│
└── 需要递归/重复直到条件满足？
    └── 使用带重置的 Loop Over Items，或一个调用自身的子工作流。
        两者都是高级模式；请参阅 `references/LOOP_OVER_ITEMS.md`。
```

## `executeOnce`：单次触发设置

每个节点的设置选项卡都有一个 **执行一次** 开关。打开时，节点使用第一个输入项目运行一次。在 SDK 代码中，设置 `executeOnce: true` 如所示；在现有工作流中，通过 `update_workflow` `setNodeSettings`（n8n 2.24.0+）应用它。

```ts
{
    name: 'Aggregate Slack',
    type: 'n8n-nodes-base.slack',
    parameters: { /* ... */ },
    executeOnce: true,
}
```

何时使用它：

- **通知和聚合写入。** "摘要消息" 不应因为 100 个项目输入而触发 100 次。
- **计数器、总计、报告。** 任何计算 `$input.all().length` 等内容都应该运行一次。
- **通过 `$input.all()` / `$('Node').all()` 跨整个数组聚合的表达式。** 否则，聚合会为上游的每个项目运行。（每个项目的*查找*使用 `.all()` 并通过另一个节点的 `.item` 过滤的是特例，请参阅 `n8n-expressions-official`。）

何时不使用它：

- **每个项目的操作。** 每个项目发送*一次*通知是默认的，通常正确。
- **每个项目分叉的 HTTP 请求。** 你想要每个项目一个调用。

最常见的错误：忘记在聚合节点上使用 `executeOnce`，然后在分叉后看到相同消息触发 50 次。

## 当隐式循环咬你

默认每个项目的迭代很好，直到它不好。常见的意外：

### 一个"单个"配置节点每个项目触发一次

一个 `Set` 节点在分叉之后每个项目运行一次，产生 N 个相同的常量。通常没问题，但昂贵的表达式（长的 `JSON.stringify`、Luxon 解析）会运行 N 次。将 Set 节点移到分叉之上，或设置 `executeOnce: true`。

### 一个聚合代码节点运行 N 次

一个读取 `$input.all()` 来计算总和的代码节点，如果没有 `executeOnce: true`，会为每个上游项目运行一次，产生 N 个相同的项。设置 `executeOnce: true`。

### 响应 webhook 触发两次

最痛苦的版本。响应 webhook 每个项目触发一次，并且两个没有合并的分支会触发两次：第一个响应获胜，其余的记录错误。先合并，或确保只有一个分支到达响应者。请参阅 `n8n-node-configuration-official` `references/MERGE_NODE.md`。

### LLM 调用触发 N 次时你想要一个摘要

与聚合代码节点形状相同。一个 LLM 节点在其提示中包含 `$input.all()` 会做出 N 个相同的调用，花费 N 个代币，返回 N 个相同的答案，如果没有 `executeOnce: true`。

## 何时使用 `Loop Over Items`

默认迭代处理大多数情况。使用 `Loop Over Items` 用于：

- **速率限制。** "一次处理 10 个，每批之间等待 1 秒。"
- **带数组体的分批 API 调用。** "将 50 项块发送到 /bulk。"
- **每批错误处理。** "如果一批失败，记录并继续。"
- **状态迭代。** "每次迭代都依赖于前一个输出。"
- **轮询长时间运行的工作。** "开始，每 30 秒检查状态，直到完成或达到上限。" 使用 `reset: true` 加上 `$runIndex` 天花板。
- **每个项目的多分支聚合。** "对于每个输入，并行运行转换，合并，然后聚合。" 完成输出（索引 0）携带结果。

有关连接细节、输出索引陷阱（输出 0 = **完成**，输出 1 = **循环**），以及工作示例，请参阅 `references/LOOP_OVER_ITEMS.md`。

## 何时不使用 `Loop Over Items`

最常见的合理化："我需要在所有项目完成之前才能进行下一步，所以我将添加 Loop Over Items 并使用 `done` 输出。" **你不需要 Loop Over Items 来实现这一点。** 默认每个项目的迭代已经等待：每个项目都通过完整的下游链，然后下一个项目开始，并且后循环节点永远不会"提前"触发。

纠正这个错误的补救措施几乎总是：**删除 Loop Over Items 节点，不做任何其他更改，发布**。这就是下面的场景 1，它涵盖了大多数情况。

这四个场景是独立的。将它们作为单独的决策来阅读，而不是所有"都替换" Loop Over Items 的替代方案。大多数构建都命中场景 1 并完成。场景 2 和 3 只有在其特定目标适用时才会进入。场景 4 是 Loop Over Items 真正值得其位置的狭窄情况。

### 场景 1：默认每个项目的迭代（默认，最常见）

源发出 N 个项目，每个项目处理器运行 N 次，下游链跟随。**没有 Loop Over Items，没有 `executeOnce`，没有聚合。** 只需连接节点。

```
[源：20 个项目]
  → [每个项目处理器]   # 默认迭代，运行 20 次
  → [下一步]            # 在每个项目之后运行，按顺序
```

如果在这里添加了 "Loop Over Items + done" 来"等待所有项目"或"使下一个节点为每个项目运行"，请删除 Loop Over Items 节点，并将源直接连接到处理器。**不要用它替换任何东西。** 默认迭代已经完成了这项工作。例外是 `Execute Workflow`（子工作流）：它默认为单个所有项目批次，因此每个项目的调用需要 `mode: 'each'` 在该节点上，而不是 Loop。请参阅 `n8n-subworkflows-official`。

### 场景 2：下游节点应总共触发一次（`executeOnce: true`）

独立于场景 1。仅当存在一个特定的下游节点，其任务是每次运行一次，而不是每个项目运行一次时才会触发：处理 20 篇论文后发送一封摘要邮件，循环后写入摘要，最后发送 Slack 通知。

在该节点上设置 `executeOnce: true`。该节点接收所有上游项目，但运行一次。这是一个每个节点设置，不是 Loop 替代方案：场景 1 中的每个项目处理器仍然运行 N 次，只有这一个下游节点会合并。

### 场景 3：节点需要项目为单个数组（聚合）

独立于场景 1。仅当下游节点的输入合同是列表，而不是每个项目调用（例如，一个接受 JSON 数组体的节点，一个需要整个列表的 LLM 提示）时才会触发。

使用聚合节点将每个项目流合并为一个包含数组的项。再次，这不是 Loop 替代方案。

### 场景 4：真正的分批（Loop Over Items 值得其位置的唯一时间）

速率限制（一次处理 N 个，每批之间等待），分块批量 API 调用（将 50 项数组发送到 `/bulk`），每批错误处理，带有 `reset: true` 和 `$runIndex` 天花板的长时间运行工作轮询，状态迭代，其中每个批次都依赖于前一个输出。

"等待项目完成"不符合条件。默认迭代已经做到了这一点。

### 快速消除歧义

如果你的唯一循环原因是"等待项目 / 为每个项目运行"，你处于场景 1。删除 Loop。不要添加 `executeOnce` 或聚合作为替代。它们解决不同的问题，并且只有在它们自己的场景适用时才会添加。

## 何时使用 HTTP 分页

三种常见的页形状：

- **响应中包含 Next-URL。** 每个响应都包含一个 `next` 链接。
- **页码/游标参数。** 每次调用都增加 `?page=N` 或 `?cursor=...`。
- **在空页上停止** 或特定状态。

HTTP 请求通过其 **分页** 选项原生处理所有这些：设置模式，给出下一页表达式，该节点内部循环，返回所有页面的项目组成的单个输出数组。

除非 API 做了内置模式无法表达的事情，否则不要用 `Loop Over Items` + 手动 `$pageCount` 重新发明。

请参阅 `references/HTTP_PAGINATION.md`。

## 子工作流递归

对于真正的递归工作（树遍历、重试带退避、"处理这个及其子项"），一个自调用的子工作流比带 `Reset` 的 `Loop Over Items` 更干净。输入参数携带递归状态。

```
子工作流：遍历树
  输入：{ node_id, depth }
  正文：处理节点，查找子项，对于每个子项调用自身，depth+1
```

注意递归深度。n8n 有嵌套执行限制。对于深度递归，队列+扁平循环比真正的递归更好。

## 反模式

| 反模式 | 出现什么问题 | 修复 |
|---|---|---|
| 向"使其循环"添加 Loop Over Items，而默认迭代已经足够 | 工作流更难阅读，没有好处，并且循环输出与 done 输出会错误连接 | 直接连接节点，让默认迭代处理它 |
| 没有 `executeOnce` 的聚合代码节点 | 相同聚合计算 N 次，输出有 N 个相同的项 | 设置 `executeOnce: true` |
| 使用 Loop Over Items + `$pageCount` 的手动分页循环 | 重新发明了 HTTP 请求原生做的事情，具有脆弱的停止条件 | 使用 HTTP 请求的 `Pagination` 选项 |
| 每个项目发送一个 Slack 消息，而你想得到一个摘要 | Slack 频道被淹没，速率限制被触发，尴尬 | Slack 节点的 `executeOnce: true`，上游构建摘要 |
| 两个分支都到达 `Respond to Webhook` | 响应两次，下游调用者看到错误 | 在响应者之前合并，或确保只有一个分支到达它 |
| 带有 `Reset` 和没有明确终止条件的 Loop Over Items | 无限循环，n8n 吃掉内存，直到执行被杀死 | 始终有一个明确的终止条件。对于分页 API，请使用 HTTP 分页 |
| 在同一工作流中嵌套一个 Loop Over Items 在另一个 Loop Over Items 内部 | 运行时出错，验证通过 | 将内部循环移入一个子工作流，每次外部迭代调用。请参阅 `n8n-subworkflows-official` `mode: 'each'` |
