# n8n 子工作流

子工作流是可重用的函数。`执行工作流触发器` 声明输入参数，主体部分执行操作，最后一个节点返回输出。调用者像调用其他节点一样调用它。

这种框架打开了以函数为形状的收益：封装、重用、可测试性、可替换性。它是 n8n 中的主要重用机制，但不幸的是使用率不高。

没有子工作流的情况下，相同的逻辑会在多个工作流中重复。在多个地方进行错误修复，可能会遗漏一个，"相同"的副本会逐渐偏离。

## 不可协商项

1. **在构建之前先搜索。** 在编写处理通用问题的逻辑之前，检查是否已经存在子工作流。按标签（`search_workflows({ tags: ['subworkflow'] })`，一个领域标签）和/或关键字（`query: '<keyword>'`）进行过滤。标签是发现机制（n8n 2.27.0+）。
2. **`执行工作流触发器` 使用 "定义下方" 并带有类型字段，而不是传递。** "定义下方" 是唯一允许代理工具（`fromAi`）和结构化调用者传递值的模式。两个例外：(a) 子工作流特别需要接收二进制（那么它不能直接作为代理工具连接），或者 (b) 子工作流根本不接收任何输入（"定义下方" 至少需要一个字段）。见下文"子工作流输入和输出"。

## 强制默认值

- **任何可重用的内容都成为子工作流。** 如果一个逻辑块可能在其他地方需要，请将其提取出来。例外：简单的包装器（一个 HTTP 调用，没有逻辑）和与这个调用者紧密耦合的块。
- **对于纯逻辑，默认为无状态**（输入→输出，没有外部状态）。对于涉及状态修改的逻辑，构建*故意*有状态的子工作流，将操作封装在一个干净的契约后面（ORM / 仓库模式）。要避免的是*意外的*状态：一个"验证"子工作流在安静地写入日志表。
- **按发现进行标记**：每个子工作流都获得 `subworkflow`，一个领域标签（`customer`），和/或 `tool`。标签是 `search_workflows({ tags })` 过滤的；名称保持简洁和描述性（`解析 RFC2822 日期`）。见 `references/NAMING_AND_DISCOVERY.md`。
- **描述包含关键字。** 输入/输出形状 + 代表性术语，以便各种查询都能找到它。
- **当输入契约真正不同时进行拆分**（二进制与 JSON，同步与异步，不同的认证方案）。不要通过传递+内部分支将不同的契约放在一个触发器下。见 `references/SUBWORKFLOW_PATTERNS.md` "按输入形状拆分"。

## 决策树：这个应该是一个子工作流吗？

```
即将编写一个逻辑块？
├── 这个逻辑块可能可能在另一个工作流中需要？
│   ├── 是 → 提取为子工作流
│   └── 否 → 保持内联
│
├── 这个块是否 >5 个节点并且概念上是一个整体？
│   └── 如果你想测试性、隔离性或重用，请提取；如果它只是为了更干净的画布，请内联分组（见下文）。
│
├── 这个块是否处理通用问题（认证、重试、解析、格式化）？
│   └── 几乎可以肯定需要提取。这些都是标准的可重用子工作流。
│
└── 这个块是否执行一个没有逻辑围绕的 HTTP 调用？
    └── 不要提取。没有意义地增加工作流边界。
```

当唯一动机是更干净的画布（不是重用、隔离、测试性或代理工具）时，**画布节点组**是仅用于可读性分区的工具：更快（每个调用没有子执行）且更简单（没有输入/输出契约），逻辑保持内联。在形成有效组的区域（连接、单个入口/出口）分组它；将过于分支的区域拆分为较小的组或保持未分组（用便签注释，它不分组）。只有当你确实需要重用、隔离、独立测试或代理工具时，才提取到子工作流。见 `n8n-workflow-lifecycle-official` 可读性。

## 无状态与有状态子工作流

两者都是第一类。选择取决于意图和封装。

### 无状态

接收输入，返回输出。输入/输出在输入/输出之外没有其他 I/O。纯逻辑的默认值。

示例：

- `解析 RFC2822 日期`（标签 `subworkflow`）。输入：日期字符串。输出：ISO 日期或错误。
- `从订阅计算 MRR`（标签 `subworkflow`）。输入：订阅对象。输出：MRR 数字。
- `将发票格式化为 HTML`（标签 `subworkflow`）。输入：发票数据。输出：HTML 字符串。

当你需要再次使用这个逻辑时，调用它，而不用担心会触发副作用。

### 有状态（故意）

在干净的输入/输出契约后面读取或写入外部状态。与仓库模式相当：子工作流抽象了状态操作，调用者以领域术语思考，而不是实现。

示例：

- `按 ID 获取客户`（标签 `customer`）。输入：ID。输出：客户对象或 `{ ok: false, error: 'not_found' }`。读取数据库。
- `写入客户账单记录`（标签 `customer`，`billing`）。输入：记录。输出：`{ ok: true, id }`。写入数据库。
- `追加审计事件`（标签 `audit`）。输入：事件。输出：`{ ok: true, eventId }`。写入日志存储。
- `发送给值班人员`（标签 `notification`）。输入：通道，消息。输出：`{ ok: true, messageId }`。调用 Slack/SMTP。

构建这些为子工作流的目的：

- 调用者以领域术语思考（`按 ID 获取客户`），而不是存储（`SELECT * FROM customers ...`）。
- 交换底层的存储/API（Postgres → Supabase，原生节点 → HTTP）而无需触摸调用者。
- idempotency、重试和验证成为子工作流的责任，集中在一个地方。

要避免的是*意外的*状态：一个命名为/描述为纯的子工作流在安静地写入日志表。这会突然袭击调用者，他们合理地认为它安全可重试或组合。要么将副作用作为契约的一部分（重命名、记录、返回其结果），要么将其移出。

## 何时提取

两个主要信号：

### 1. 概念一致性

当一个节点块执行一个逻辑操作，即使不被重用，提取也可能值得：

- **可测试性。** 使用固定的数据单独运行子工作流。
- **可替换性。** 交换实现不会波及调用者。

仅可读性不是提取的理由：节点组将五个节点压缩为一个带标签的框更便宜（没有子执行，没有输入/输出契约）。当你还想测试性、可替换性或重用时，请提取。

### 1.5 火并遗忘审计日志模式

> 审计日志在这里用作具体说明火并遗忘有状态模式的例子。**除非用户要求，否则不要在工作流中添加审计日志。** 该模式本身（异步发射子工作流，不阻塞）可以推广到任何副作用：指标、通知等。

一个故意有状态审计日志子工作流使用 `执行工作流` 的 `waitForSubWorkflow: false` 以便调用者不会在写入上阻塞。

```
调用者 ──→ [执行工作流：DB 审计日志]
              { title: '收到电子邮件确认',
                description: <序列化数据> }
              waitForSubWorkflow: false
              ↓ (调用者立即继续)
        ──→ [继续下一步]
```

子工作流接收标题和描述，写入日志表（或 Slack，或两者），返回。调用者不等待。审计日志是副作用，不是关键路径。

当用户要求时，在有意义的状态转换时（"收到电子邮件确认"、"用户已验证"、"处理开始"、"资格决定"）发射一个，以便从日志中重建时间线。

为什么它有价值：

- **免费的观察性。** 每个执行的时间线，当出现问题时。
- **无耦合。** 实现可以更改而无需触摸调用者。
- **默认异步。** `waitForSubWorkflow: false` 意味着审计不会减慢主工作流。

审计日志工作流是正确类型的子工作流。副作用是重点。

### 1.7 中间件模式

当 webhook 工作流是 API 形状时，将其视为一个 API。子工作流成为中间件：小的无状态函数，在主处理程序之前运行，要么传递通过，要么使用 4xx 短路。

```
Webhook
  → [验证 JWT]    # 解码 + 验证；失败时返回 401
  → [速率限制]    # 检查 + 增加计数器；失败时返回 429
  → IF (所有中间件 ok)
    → 主处理程序逻辑
    → 返回 200
  → ELSE → 返回中间件返回的 4xx
```

规范示例：n8n 内部自定义 JWT 认证。`验证 JWT`（标签 `subworkflow`）接收原始 `Authorization` 标头，解码，验证签名和过期，返回 `{ ok: true, user_id }` 或 `{ ok: false, status: 401, message }`。调用者根据 `ok` 进行 IF，失败时提前响应，成功时继续。

为什么使用子工作流而不是内联：每个需要认证的 webhook 都调用同一个。在单个位置交换库，旋转签名密钥，或添加刷新令牌逻辑。重用目标是精确的，契约很小，每个 API 端点的失败响应形状一致。

与 `n8n-error-handling-official` 配对用于 4xx/5xx 响应形状，与 `n8n-credentials-and-security-official` 配对用于底层密钥处理。

### 2. 重复模式

你即将构建一个你已经构建过的东西。停止。搜索。

```
search_workflows({ query: 'date' })
search_workflows({ tags: ['customer'] })
search_workflows({ tags: ['subworkflow'] })
```

如果匹配，请使用它。如果没有，请将其作为子工作流构建并标记它（`subworkflow`，领域，`tool`），以便下一次搜索能找到它。标签约定（`subworkflow`，领域标签，`tool`）是使其发挥作用的东西。

## 线性、长工作流在大多数工作都在子工作流中时是没问题的

一个工作流可以有 20+ 个节点，如果它主要是子工作流调用和决策的线性编排，仍然可以可读。形状（仅因为审计日志节点是一个生动的"真实步骤之间的副作用"示例而显示，仅当用户要求审计日志时才包含它们）：

```
Webhook
  → 审计日志（子工作流）
  → 验证
  → 审计日志（子工作流）
  → IF 认证 ok
    → 查找用户（或子工作流）
    → 审计日志（子工作流）
    → 处理步骤 1（子工作流）
    → 审计日志（子工作流）
    → 处理步骤 2（子工作流）
    → 审计日志（子工作流）
    → 决定资格（子工作流）
    → 审计日志（子工作流）
    → 发送通知（子工作流）
    → 响应
```

每个"逻辑步骤"都是一个子工作流调用。调用者是一个长但线性的叙述，易于从上到下跟随。逻辑存在于子工作流中。

这不是 20 个节点的工作流与 20 个内联转换相同的情况。那很难阅读。上面的模式是没问题的，因为：

- 每个节点都有一个目的（调用特定的子工作流）。
- 节点组标记区域，便签注释它们（每 `n8n-workflow-lifecycle-official` "可读性"）。
- 检查一个区域意味着打开它调用的子工作流。这就是封装。
- 顶级编排逻辑对可读性是可见的，而无需阅读实现。

如果你的工作流有 15+ 个节点并且不是主要由 `执行工作流` 调用和分支组成，请提取更多重用或测试值得的部分，并将其余部分内联分组（节点组）。

## 何时不提取

- **一个 HTTP 调用且没有逻辑。** 一个只是 `执行工作流 → HTTP 请求 → 返回` 的子工作流为无意义地增加了边界。内联它。
- **与调用者的特定形状紧密耦合。** 如果这个块接收一个只有这个调用者生成的深度嵌套输入，提取它只是将耦合重新定位。首先修复数据形状。
- **性能关键的热路径。** 每个子工作流调用都会增加延迟（很小，但真实）。对于高吞吐量工作流，在添加边界之前进行 профилирование。

## 先搜索再构建协议

当用户描述一个多步骤或听起来通用的东西时：

```
1. 使用相关的标签和/或查询搜索工作流（例如 `tags: ['subworkflow']`，一个领域标签，操作关键字）
2. 如果候选者出现，获取前 1-3 个 `get_workflow_details`
3. 通过阅读输入/输出（简要阅读主体）来确认匹配
4. 如果存在匹配 → 使用它。告诉用户 "我找到了 `<name>`。使用那个。"
5. 如果没有匹配 → 构建新的并标记它（`subworkflow`，领域，`tool`），以便下一次搜索能找到它
```

"告诉用户"这一步很重要。他们受益于知道他们的库中已经有了什么。

如果你期望找到的工作流没有出现，最常见的原因是每个工作流的 MCP 访问未启用。见 `n8n-workflow-lifecycle-official` `references/MCP_ACCESS_PER_WORKFLOW.md`。

## 子工作流输入和输出

子工作流由 `执行工作流触发器` 节点触发。触发器声明输入模式。调用者通过 `执行工作流` 传递数据，子工作流返回其最后一个节点输出的任何内容。

### 总是使用带有显式字段的 "定义下方"

`执行工作流触发器` 有两种输入模式。**默认使用 "定义下方"（类型字段）。** 这是唯一允许代理工具（通过 `fromAi()`）和任何结构化调用者传递值的模式。如果没有声明字段，代理没有模式来填充，子工作流不能干净地作为 `toolWorkflow` 连接。

形状：

```ts
const subTrigger = trigger({
    type: 'n8n-nodes-base.executeWorkflowTrigger',
    config: {
        parameters: {
            workflowInputs: {
                values: [
                    { name: 'list_of_ids', type: 'array' },
                    { name: 'include_transcript', type: 'boolean' },
                    { name: 'session_id', type: 'string' },
                ],
            },
        },
    },
})
```

每个声明的输入都成为调用者可以填充的类型参数。在工作流内部，通过 `$json.list_of_ids` 等访问，或从任何下游节点通过 `$('When Executed by Another Workflow').first().json.<field>` 访问。

故意选择类型（`string`，`number`，`boolean`，`array`，`object`）。模型使用这些作为填充代理工具参数时所需的类型，人类依赖它们来连接调用者。

### 例外 1：用于二进制的传递模式

如果子工作流需要接收二进制（图像、文件、PDF），"定义下方" 不起作用，因为类型字段仅限于 JSON。切换到传递：

```ts
const subTrigger = trigger({
    type: 'n8n-nodes-base.executeWorkflowTrigger',
    config: {
        parameters: {
            inputSource: 'passthrough',
        },
    },
})
```

在传递模式下，子工作流接收调用者的项目，包括 `binary` 插槽。成本：没有类型输入模式，因此代理工具无法通过 `fromAi()` 传递参数。使用此模式的原因是子工作流被其他工作流调用（而不是代理），需要二进制流通过。

对于需要二进制且由代理调用的子工作流，见 `n8n-binary-and-data-official` `AGENT_TOOL_BINARY.md`（代理工具不能直接传递二进制）。

### 例外 2：用于没有输入的传递

"定义下方" 要求至少有一个声明的字段。一个真诚地没有输入的子工作流（一个"列出活动凭证"工具，一个"当前计数"查找，任何零参数操作）无处放置空模式，因此传递是唯一的选择。

当专门使用传递来处理没有输入的情况时：

- **在主体开始处使用一个 `Set`（编辑字段）节点，在"仅保留设置"模式下没有字段。** 这会清除调用者的 JSON，以便下游节点不会意外读取调用者传递的字段。如果没有它，主体会安静地选择调用者转发的内容。
- **在触发器上添加一个便签，记录预期没有输入。** 未来阅读者（以及代理重新连接它作为工具）需要知道传递不是因为二进制，而是因为设计上没有模式。

代理工具连接在无输入的情况下仍然有效：`toolWorkflow` 接受一个输入映射没有字段的子工作流。代理的唯一决定是是否调用。`n8n-agents-official` `references/TOOLS.md`（"零 `fromAi` 参数"）的模式直接适用。

### 其他约定

- **在工作流 `description` 中记录输入和输出。** 字段名、类型、目的。描述是调用者（人类和代理）阅读合同的地方。
- **返回一致的形状。** 对于预期的失败（例如，解析错误），返回 `{ success: false, error: '...' }` 而不是抛出。调用者可以分支而无需包装错误输出。
- **一旦有调用者，将输入模式视为契约。** 添加可选字段是安全的。重命名或删除字段可以这样做，但必须小心：枚举每个调用者（`search_workflows` 对于子工作流的名称 + 手动扫描），在同一更改中迁移它们，并在发布之前使用 `validate_workflow` + `get_workflow_details` 进行验证。这里的沉默中断很难检测，因为 n8n 不会在无法识别的输入字段上出错。子工作流只看到 `undefined`，调用者不知道。
- **使用一个最终的 Set / 编辑字段节点来塑造返回。** 可选，有时需要（当最后一个计算节点携带噪声字段时），并且即使不严格要求，对于子工作流也是良好实践。这使返回合同在边界处明确，因此阅读者通过阅读一个节点看到 API。这是 `n8n-expressions-official` 中设置节点反模式的合法例外：子工作流的隐式消费者是*每个调用者*，所以设置配得上它作为明确的 API 边界。将其命名为 `返回` 或 `返回 <东西>`。
- **返回自然形状，而不是存储形状。** 一个拥有数据表、S3 中的文件或任何存储层的子工作流应将表示隐藏起来。数组返回为数组，对象返回为对象，日期返回为 ISO 字符串，无论底层存储是否为 JSON-字符串化文本或另一种内部格式。返回合同是*接口*。存储布局是*实现细节*。

  常见错误：一个子工作流有一个"新鲜"路径（刚产生的数据，自然形状）和一个"缓存"路径（刚从 `_object` 列读取的数据，仍然是字符串化）。错误的直觉：将新鲜路径字符串化"以匹配"缓存路径。正确的直觉：解析缓存路径，以便两者都返回自然形状。调用者不应该知道他们得到了什么。

对于作为代理工具连接的子工作流，见 `n8n-agents-official` `references/SUBWORKFLOW_AS_TOOL.md`。

## 调用子工作流：`执行工作流` 模式

调用者侧 `执行工作流` 节点除了输入/`workflowId` 之外还有两个设置：

- **`mode`** 默认为 `'all'`：子工作流运行**一次**，所有 N 个项目作为输入。项目仍然像其他工作流一样按项目流经节点。设置 `mode: 'each'` 以运行 N 次子工作流，每次一个项目。对于子工作流其主体正常处理项目的身体，两者是等效的。拆分很重要，当子工作流的身体假设它看到恰好一个项目（每次运行的聚合，"这是要操作的客户"逻辑，最终写入应该每次输入触发一次）时。`mode: 'each'` 匹配该假设，`mode: 'all'` 会破坏它。当你确实需要按项目迭代时，请优先选择 `mode: 'each'` 而不是子工作流内部使用 Loop Over Items 节点。
