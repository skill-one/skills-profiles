# n8n 扩展 MCP

任何启用了MCP访问的n8n工作流都成为编码代理可以按名称调用的工具。两种常见情况：

1. **包装MCP未暴露的n8n功能。** MCP涵盖了工作流CRUD、验证、执行、数据表、凭证列表、执行搜索、文件夹创建/重命名/移动以及文件夹/项目列表、标签列表和附加/分离。仍然缺失：文件夹删除、项目创建/重命名、标签重命名/删除、实例元数据、凭证创建。构建一个调用n8n API并将结果作为代理工具暴露的工作流。
2. **将通用工作流作为工具暴露。** 一个与n8n本身无关的工作流（调用第三方API、运行内部业务逻辑、在私有系统中查找信息）可以作为MCP调用。让代理在编码会话期间调用实际操作。

MCP将你的工作流调用为原生工具：输入来自`Execute Workflow Trigger`，输出来自工作流的最后一个节点。

## 何时使用此方法

情况1（包装n8n功能）：

- 文件夹删除和项目创建/重命名：没有MCP工具。文件夹创建/重命名/移动和在工作流之间移动工作流现在有MCP工具（`create_folder`、`update_folder`、`move_workflows_to_folder`），在注册的实例上；删除仍然需要REST API。
- 标签重命名/删除：MCP列出标签（`list_workflow_tags`）并附加/分离它们（`update_workflow` `addTags`/`removeTags`，自动创建未知名称），但不能重命名或删除标签实体。REST API存在用于这些操作。
- 实例元数据（限制、计划信息、配置的集成）：没有MCP工具。
- 凭证创建：REST API存在（`POST /credentials`），但目前还没有MCP工具。
- 任何n8n API操作MCP未原生暴露的操作。

情况2（通用代理工具）：

- 一个你宁愿编码而不是重新解释的重复代理任务（查找、格式化、发送）。
- 对代理没有直接访问权限的系统的操作（私有API、内部服务、第三方集成）。
- 任何你想在未来会话中调用而无需重新推导实现的内容。

不要为此方法：

- 一次性问题，直接询问用户。
- MCP已经原生暴露的内容。

## 必须遵守的规则

1. **在构建之前询问用户。** 这会在他们的实例上创建一个工作流，并带有凭证。他们需要明确同意。
2. **凭证通过凭证，而不是文本字段。** n8n中其他地方相同的规则。参见`n8n-credentials-and-security-official`。

## 协议

- **首先搜索现有的包装器。** `search_workflows({ tags: ['tool'] })`和一个功能关键字搜索。如果匹配，就使用它而不是重复。
- **对于情况1，作为无状态、可查询的工具构建。** 接收输入，调用n8n的API，返回结果。没有副作用。情况2可能有合法的副作用（发送、写入）；在工具描述中命名它们。
- **提出自己编辑代理的上下文文件**（CLAUDE.md、AGENTS.md、GEMINI.md、用户代理在会话开始时读取的任何文件）以添加新工具的条目。你有编辑/写入工具的权限，所以没有必要让用户手动粘贴片段。先询问，因为这是他们的配置文件，然后在他们同意时直接编辑它。

## 从头到尾的模式

```
1. 用户要求一个功能（缺失的MCP功能，或他们希望代理能够调用的工作流）。
2. 你："我可以构建一个工作流来将此功能作为MCP可以调用的工具暴露。
   要我创建它吗？"
3. 用户：是。
4. 你构建工作流：
   - 触发器：带有声明输入的`Execute Workflow Trigger`。
   - 主体：工具需要的任何逻辑（对n8n API的HTTP请求、第三方调用、内部计算）。
   - 输出：结构化响应。
5. 验证、测试、发布。
6. 询问用户是否可以为你添加一个条目到他们的代理上下文文件（CLAUDE.md / AGENTS.md / 等），
   这样未来的会话知道按名称搜索它。在他们同意时直接编辑文件。
7. 工作流立即可以调用：代理创建的工作流默认设置`availableInMCP: true`。
```

## 常见情况1包装器（缺失的MCP功能）

最常见的模式，按实用性排列。情况2（通用代理工具）是项目需要什么，没有规范示例。

> **n8n REST API参考：** https://docs.n8n.io/api/api-reference/。对于任何情况1包装，从这里开始。找到端点，然后用HTTP请求节点和`n8nApi`凭证包装它。自托管实例在`<instance-url>/api/v1/`暴露此API。

### 1. 文件夹删除和项目管理

MCP现在原生创建、重命名和移动文件夹（`create_folder`、`update_folder`、`move_workflows_to_folder`），所以这些不再需要包装。仍然缺失：**删除**文件夹和创建/重命名**项目**。n8n的REST API涵盖了两者（[文件夹端点](https://docs.n8n.io/api/api-reference/#tag/folders)），所以一个一次性包装就填补了空白。

```
工具：删除文件夹
输入：{ projectId: string, folderId: string }
输出：{ success: boolean }
```

### 2. 实例元数据

版本、配置的集成、环境信息。用于SessionStart漂移检查或根据实例功能调整工作流。

```
工具：获取实例信息
输入：{}
输出：{ version, edition, integrations: [...], limits: {...} }
```

## 代理如何调用工具工作流

MCP**不会将每个标记为工具的工作流注册为单独命名的MCP工具。** 发现和调用是两步：

1. **通过`search_workflows({ query: '<keyword>' })`发现**。返回`availableInMCP: true`的工作流在MCP访问上。筛选这些。
2. **通过`execute_workflow({ workflowId, inputs })`调用**。首先用`get_workflow_details`读取输入模式。`Execute Workflow Trigger`定义了类型字段。

输出是工作流最后一个节点返回的内容。

**MCP访问默认值：** 代理创建的工作流默认`availableInMCP: true`。UI创建的工作流可能默认关闭，在这种情况下，用户必须在工作流的设置中切换MCP访问才能在搜索结果中看到它。无论如何，用户可以稍后关闭它以限制访问。

**这就是为什么代理上下文文件片段（CLAUDE.md / AGENTS.md / 等）很重要。** 未来的会话不会自动枚举工具工作流。片段告诉它们工具存在，所以它们搜索它而不是重新推导实现。

## 反模式

| 反模式 | 出现什么问题 | 解决方法 |
|---|---|---|
| 在不询问用户的情况下构建MCP扩展工作流 | 在他们的实例上意外创建工作流并带有凭证 | 始终先询问权限 |
| 不在代理的上下文文件中记录新工具 | 未来的会话不会自动枚举工具工作流。如果没有提示，它们会重新推导实现。 | 询问用户，然后直接编辑CLAUDE.md / AGENTS.md / 它们代理读取的任何文件。不要让他们粘贴片段 |
| 在HTTP请求节点中硬编码n8n API令牌 | 当工作流导出或复制时令牌泄漏 | 使用类型为`n8nApi`的凭证或适当的头部认证 |
| 没有在工具的名称/描述中提及副作用的工具产生副作用 | 代理调用时认为它是只读的，结果发送了真实消息或写入真实数据 | 明确地在名称和描述中说明副作用（例如，`工具：发送Slack消息`）。对于情况1包装器，只读是更安全的默认值 |
| 执行批量或破坏性操作（归档、删除）的工具没有干运行 | 一个错误影响许多工作流 | 每次调用强制的明确选择进入，加上一个干运行模式，它列出目标而不执行 |
| 工具返回凭证*值* | 通过工具输出令牌泄漏 | 只返回ID、名称、类型。从不返回秘密 |
| 跳过包装的验证+验证+测试周期 | "工具"本身是坏的，表现为令人困惑的工具未找到或空响应错误 | 与任何工作流相同的生命周期：参见`n8n-workflow-lifecycle-official` |
