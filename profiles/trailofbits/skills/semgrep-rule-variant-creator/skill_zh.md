# Semgrep 规则变体创建器

将现有的 Semgrep 规则移植到其他语言，每个语言独立进行一次测试驱动的循环。

对于新规则而非移植，使用 `semgrep-rule-creator` — 它需要一个漏洞模式描述，而该技能需要一个完成的规则。该技能也是规则编写基础知识的参考：污染模式与模式匹配、为什么测试优先、以及如何在通过后缩小规则。移植应用相同的判断标准到新语言中，所以当规则结构本身是开放问题时，从这里开始。

## 作为工作流运行

移植是针对每种语言重复的四个阶段，所以编排作为动态工作流而不是每次运行都要重新遵循的指令：

```
/semgrep-rule-variant-creator:port-rule-to-languages
```

传递三个必需参数，以及 `outputDir` 除非工作目录是你想要变体存放的地方。每种语言一个条目：`"Go and Java"` 移植一个名为短语命名的单一语言，并且脚本会拒绝它。

`referencesDir` 必须是一个解析后的绝对路径。在这里解析它，因为没有任何工作流脚本可以展开变量。按顺序尝试，第一个匹配的胜出 — `-d` 是关键，因为一个裸的 `ls` 打印目录内的文件名而不是目录本身，并且什么也不复制：

1. **Claude 代码** — `ls -d -- "${CLAUDE_PLUGIN_ROOT}/skills/semgrep-rule-variant-creator/references"`
2. **Codex** — 如果该变量被设置，使用 `${CODEX_PLUGIN_ROOT}` 的相同命令
3. **两者都未设置** — `find ~/.claude ~/.codex . -type d -path '*/semgrep-rule-variant-creator/skills/*/references' -print -quit 2>/dev/null`

然后确认打印出的目录包含参考文件，使用 `ls -1 -- "<that path>"`。

传递完全打印的路径。如果所有三个都为空，停止并说明，而不是手工组装路径：脚本拒绝相对路径和未展开的标记，但一个手工构建的绝对路径如果不存在会清除所有防护，然后运行报告每个语言都通过而没有读取任何指导。

```json
{
  "rulePath": "<正在移植的规则路径>",
  "languages": ["Go", "Java"],
  "referencesDir": "<上面 ls 打印的绝对路径>",
  "outputDir": "<变体目录应该存放的地方>"
}
```

工作流脚本不能展开 `{baseDir}` 或 `${CLAUDE_PLUGIN_ROOT}`，并且没有文件系统访问权限来注意到它没有；已安装的插件也不在用户的项目中，所以 `referencesDir` 是参考文件以下到达阶段代理的唯一途径。脚本拒绝省略它的运行和传递标记而不是路径的运行，而不是没有它们进行移植，因为没有这些指导的移植仍然报告每个语言都通过。`outputDir` 是一个可选参数，默认为工作目录，在仓库中很少是你想要的。

它读取规则一次，然后独立运行每种语言通过完整循环，并报告哪些语言通过，哪些失败验证，哪些它判断不适用，哪些 Semgrep 完全无法分析，以及哪些它停止 — 一个它不认识的语言键，两个条目解析到一个目录，或一个从未报告回的反驳者。停止时命名要更改的内容，并且在重新运行时会发生，这就是它与一个死亡的代理的区别。规则作为路径而不是文本传输：每个阶段读取文件，因为一个要求逐字重复规则的代理不会 — 一个 HTML 转义 `<` 和 `>` 打破了 `<... ...>` 操作符，导致下游每个阶段都失效。

如果运行在会话仍然存活时中断 — 你停止了它，或者一个代理遇到终端错误 — 使用
`Workflow({scriptPath: "…", resumeFromRunId: "<runId>", args: {…}})` 重新启动它，传递相同的参数。参数不会与运行一起保存，所以省略它们的恢复在重播任何内容之前会失败预检检查；包含它们，完成从缓存中重播的语言和未完成的语言重新运行。

恢复仅限于同一会话，这使得它不适合移植可能遇到的中断：会话限制结束会话，并且运行存储在会话自己的目录下，所以下一个会话无法访问它们。一个它无法解析的运行 ID 也不是错误 — 它在 ID 下从零开始，并重新运行每个语言以全成本，没有任何说明。在依赖恢复之前检查 ID 是否仍然存在：

```
ls -d ~/.claude/projects/*/*/subagents/workflows/*
```

这就是运行今天存放的地方而不是一个记录的接口，所以一个空结果可能意味着布局移动而不是运行消失。无论如何安全的读取是相同的：如果你无法确认 ID，或者会话结束，使用相同的参数重新启动，并将 `outputDir` 指向一个新鲜的地方。脚本永远不会删除目录，所以一个在第二次运行时变为 `NOT_APPLICABLE` 的语言会留下第一次运行的变体。

脚本位于插件根目录的 `workflows/port-rule-to-languages.js`。它为每个阶段固定推理工作 — 读取规则很便宜，最高的是翻译和修复直到绿色的循环 — 并编码阶段顺序，所以规则不能在指定它的测试之前编写。它还把两个没有神谕的决定从任何单个代理手中移开：一个 `NOT_APPLICABLE` 判决在语言被放弃之前交给一个独立的反驳者，并且失败验证最多重试三次而不是信任一个代理迭代直到绿色。

当你移植到一个单一语言并想保持更新，或者移植已经完成了一半并且你只需要一个阶段时手动运行阶段。工作流是移植需要的唯一委托：一个代理读取规则，每种语言需要四个当移植首先变为绿色时 — 一个反驳判决加一个，每个验证重试也加一个。这里没有其他足够大或独立值得它自己的代理，所以手动运行阶段意味着你自己做而不是交给子代理。

## 四个阶段

每种语言在变体完成前运行所有四个。一个失败的验证的语言是未完成的；一个被判断不适用的语言不会生成目录。

**1. 适用性分析** — 决定模式是否完全属于目标语言：漏洞类别是否存在那里，每个源、汇点和净化器是否存在等效结构，以及移植的规则是否能检测真实风险而不是表面语法匹配。判决是 `APPLICABLE`、`APPLICABLE_WITH_ADAPTATION` 或 `NOT_APPLICABLE`。`NOT_APPLICABLE` 是唯一一个下游没有任何东西可以反驳的判决 — 它不生成测试、不生成规则、也不生成目录 — 所以在采取行动之前它需要第二意见。单独回答，通过运行 Semgrep：Semgrep 能否读取这种语言？Perl 没有前端，Elixir 的解析器是 Pro 专用的，在两种情况下漏洞类别存在而规则是不可评级的 — 这是与 `NOT_APPLICABLE` 的不同发现，后者声称漏洞类别不存在。参见
[applicability-analysis.md]({baseDir}/references/applicability-analysis.md)
了解每个判决的工作示例。

**2. 测试创建** — 首先以目标语言的惯用代码编写测试文件。至少两个 `ruleid:` 案例和两个 `ok:` 案例每个注释都在立即位于它评分的代码行上方。包括安全的变体，这是语言自己的惯用方式来正确执行该操作，因为这是移植最常引入的误报。

**3. 规则翻译** — 导出目标语言的 AST 并根据它显示的内容进行翻译，因为模式形状遵循 AST 形状而不是源相似性。保持原始的检测意图和模式；更改 ID 为 `<original-id>-<language>`、`languages` 键，并添加 `original-rule` 和 `ported-from` 元数据。参见
[language-syntax-guide.md]({baseDir}/references/language-syntax-guide.md)。

**4. 验证** — `semgrep --test` 是接受标准，并且它必须报告所有测试通过。遗漏的行意味着模式比漏洞更窄；错误的行意味着它更宽。测试文件是规范，所以修复规则以满足它。在测试仍然失败时停止会留下语言未完成而不是完成。参见
[workflow.md]({baseDir}/references/workflow.md) 了解如何读取测试失败以及在模式无法匹配或污染不会传播时进行故障排除。

接受标准是一个特定的 Semgrep：规则读取时记录的版本。切换二进制文件以获得绿色是它保护失败的 — 一个无法通过其 Elixir 测试的代理安装了最后一个 OSS 构建的 Elixir 解析器并报告了其真实的“所有测试通过”对于一个在这里是红色的移植。两个其他绿色意味着什么：一个 Semgrep *跳过* 的规则仍然以“所有测试通过”结束其运行，并且一个测试文件其扩展名 Semgrep 没有与规则的语言关联的也会这样，因为它无论哪种方式都评定了零个测试。

## 输出

每种适用语言一个目录，包含移植的规则及其测试文件：

```
python-command-injection-go/
├── python-command-injection-go.yaml
└── python-command-injection-go.go
```

`All tests passed` 意味着规则及其测试文件相互一致；它不是漏洞类别在目标语言中可利用的证据，因为相同的循环编写了两者，所以将完成的变体视为审查候选而不是验证的规则。

## 范围和报告

将你被交给的规则移植到你被要求的语言。不要修复原始规则，扩大它以捕获附近的漏洞类别，或添加一个没有人命名的语言；如果原始规则看起来错误或缺少明显的目标，用一句话说明并继续按要求进行移植。你得到的每种语言都会完成 — 移植在它的测试通过时完成，而不是当它的文件存在时。

保持文字简短，专注于结果。在工作流调用之前，用一句话说明你即将做什么。在移植运行时，当判决改变时、当目标需要原始规则没有的模式形状，或当测试不会变绿时发言 — 不是在每次 `semgrep --test` 迭代时。然后以结果领先：第一句话说明哪些语言通过，哪些失败验证，哪些不适用，哪些 Semgrep 无法分析，细节在之后。当错误改变规则、判决或下一步要做什么时纠正先前的陈述，然后继续；一个改变无事的错误不需要注意。

规则和测试文件是问题的规模。测试文件因其不同的结构和不同的安全形式而获得长度，而不是重复相同的案例，并且两个文件都不需要注释重复代码已经说明的内容。

## 拒绝的合理化

| 合理化 | 为什么它失败 | 正确方法 |
|-----------------|--------------|------------------|
| "模式结构相同" | 不同语言间 AST 不同 | 总是导出目标语言的 AST |
| "相同漏洞，相同检测" | 语言间数据流不同 | 分析目标语言惯用用法 |
| "规则不需要测试，因为原始规则有效" | 语言边缘情况不同 | 为目标编写新的测试用例 |
| "跳过适用性 — 它显然适用" | 某些模式是语言特定的 | 首先完成适用性分析 |
| "我将创建所有变体然后测试" | 错误累积，难以调试 | 在下一个语言之前完成每种语言 |
| "库等效足够接近" | 表面相似隐藏差异 | 验证 API 语义匹配 |
| "只需逐字翻译语法" | 语言有不同的惯用用法 | 研究目标语言模式 |
| "大多数测试通过" | 一个部分规则报告部分真相 | `All tests passed`，或者移植未完成 |
| "一个较旧的 semgrep 仍然解析这种语言" | 没有人能复现的绿色 | 报告失败的输出并说明解析器是 Pro 专用的 |
| "该类别存在那里，所以规则可以移植" | Semgrep 没有 Perl 前端，Elixir 的解析器是 Pro 专用的；污染无操作 | 在移植前确认 semgrep 能否读取语言 |
| "Semgrep 说所有测试通过" | 它对零个评定的测试说这个，对于一个它跳过或从未匹配的文件 | 检查规则运行并且测试文件的扩展名与语言匹配 |

## 快速参考

| 任务 | 命令 |
|------|---------|
| 运行测试 | `semgrep --test --config rule.yaml test-file` |
| 验证 YAML | `semgrep --validate --config rule.yaml` |
| 导出 AST | `semgrep --dump-ast -l <lang> <file>` |
| 调试污染流 | `semgrep --dataflow-traces -f rule.yaml file` |
