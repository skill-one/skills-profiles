# 如果需求不明确，请提问

## 使用场景

当请求存在多种可能的解释，或者关键细节（目标、范围、约束、环境或安全）不明确时，使用此技能。

## 不适用场景

当请求已经清晰，或者可以通过快速、低风险的探索性阅读来解答缺失的细节时，不要使用此技能。

## 目标

提出最少的澄清问题，以避免错误的工作；在必须回答的问题得到解答（或用户明确批准基于假设继续进行）之前，不要开始实施。

## 工作流程

### 1) 判断请求是否不明确

如果探索如何执行工作后，以下部分或全部内容不明确，则将请求视为不明确：
- 定义目标（应该改变什么 vs 什么保持不变）
- 定义“完成”（验收标准、示例、边缘情况）
- 定义范围（哪些文件/组件/用户在范围内/范围外）
- 定义约束（兼容性、性能、风格、依赖、时间）
- 确定环境（语言/运行时版本、操作系统、构建/测试运行器）
- 澄清安全/可逆性（数据迁移、发布/回滚、风险）

如果存在多种可能的解释，则假设它是不明确的。

### 2) 首先提出必须回答的问题（保持简短）

在第一次尝试中提出1-5个问题。优先提出能够排除整个工作分支的问题。

使问题易于回答：
- 优化可扫描性（简短、编号的问题；避免段落）
- 尽可能提供多选选项
- 在适当的情况下建议合理的默认值（将它们明确标记为默认/推荐选项；在列表中加粗推荐选项，或者如果你以代码块的形式呈现选项，在块上方立即添加加粗的“推荐”行，并在块内标记默认值）
- 包括快速路径响应（例如，回复`defaults`以接受所有推荐/默认选项）
- 在需要时包括低摩擦的“不确定”选项（例如，“不确定 - 使用默认值”）
- 如果有助于减少摩擦，请将“必须知道”与“最好知道”分开
- 结构化选项，以便用户可以用简洁的决策进行响应（例如，`1b 2a 3c`）；用 plain language 重述所选选项以确认

### 3) 在行动前暂停

在必须回答的问题到达之前：
- 不要运行命令、编辑文件或生成依赖于未知因素的详细计划
- 只要在不承诺某个方向的情况下，才执行明确标记的低风险探索步骤（例如，检查仓库结构、阅读相关配置文件）

如果用户明确要求你在没有答案的情况下继续：
- 将你的假设列成简短的编号列表
- 请求确认；只有在他们确认或更正后才能继续

### 4) 确认理解，然后开始工作

一旦你得到答案，用1-3句话重述需求（包括关键约束和成功标准），然后开始工作。

## 问题模板

- "在我开始之前，我需要：(1) ...，(2) ...，(3) .... 如果你不在乎(2)，我将假设 ...."
- "这些中哪一个应该是？A) ... B) ... C) ... (选择一个)"
- "你会认为‘完成’是什么？例如：..."
- "有任何我必须遵守的约束（版本、性能、风格、依赖）？如果没有，我将针对现有项目的默认值。"
- 使用编号问题和字母选项以及清晰的回复格式

```text
1) 范围？
a) 最小更改（默认）
b) 在接触该区域的同时重构
c) 不确定 - 使用默认值
2) 兼容性目标？
a) 当前项目默认值（默认）
b) 也支持旧版本：<指定>
c) 不确定 - 使用默认值

回复：defaults（或 1a 2a）
```

## 反模式

- 不要提出可以通过快速、低风险的探索性阅读来回答的问题（例如，配置、现有模式、文档）。
- 如果紧缩的多选或 yes/no 可以更快地消除歧义，则不要提出开放式问题。
