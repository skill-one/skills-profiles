# 差异化安全审查

针对 PR、提交和差异的安全聚焦代码审查。

## 核心原则

1. **风险优先**：关注认证、加密、价值传输、外部调用
2. **基于证据**：每个发现都有 git 历史记录、行号、攻击场景作为依据
3. **自适应**：根据代码库规模（SMALL/MEDIUM/LARGE）调整
4. **诚实**：明确说明覆盖范围限制和置信度
5. **结果驱动**：始终生成全面的 markdown 报告文件

---

## 理由说明（不可跳过）

| 理由说明 | 为什么这是错误的 | 必要行动 |
|----------|-----------------|----------|
| "小型 PR，快速审查" | Heartbleed 仅 2 行代码 | 按 风险 而非规模分类 |
| "我熟悉这个代码库" | 熟悉会导致盲点 | 构建 明确的基线上下文 |
| "git 历史太耗时" | 历史记录揭示回归问题 | 永不跳过第一阶段 |
| "影响范围很明显" | 你会遗漏传递调用者 | 定量计算 |
| "没有测试 = 不是我的问题" | 缺少测试 = 风险评级提升 | 在报告中标记，提升严重性 |
| "只是重构，没有安全影响" | 重构会破坏不变性 | 高风险分析，除非证明为低风险 |
| "我会口头解释" | 没有文档 = 发现会丢失 | 始终编写报告 |

## 快速参考

### 代码库规模策略

| 代码库规模 | 策略 | 方法 |
|-----------|------|------|
| SMALL (<20 个文件) | 深入 | 读取所有依赖项，完整 git blame |
| MEDIUM (20-200) | 聚焦 | 1 跳依赖项，优先文件 |
| LARGE (200+) | 外科手术 | 仅关键路径 |

### 风险等级触发器

| 风险等级 | 触发器 |
|---------|-------|
| 高 | 认证、加密、外部调用、价值传输、验证移除 |
| 中 | 业务逻辑、状态变更、新的公共 API |
| 低 | 注释、测试、UI、日志记录 |

## 工作流程概述

```
预分析 → 第一阶段：筛选 → 第一阶段：代码分析 → 第二阶段：测试覆盖
    ↓              ↓                    ↓                        ↓
第三阶段：影响范围 → 第四阶段：深层上下文 → 第五阶段：对抗性 → 第六阶段：报告
```

```
│  ├─ 阅读：adversarial.md
│  │  (第五阶段：攻击者建模、利用场景、可利用性评级)
│  └─ 或委托给：differential-review:adversarial-modeler agent

│
├─ 编写最终报告？
│  └─ 阅读：reporting.md
│     (第六阶段：报告结构、模板、格式指南)

│  └─ 阅读：patterns.md
│     (回归、重入、访问控制、溢出等)
│
└─ 仅快速筛选？
   └─ 使用上方快速参考，跳过分详细文档
```

## 代理

**`differential-review:adversarial-modeler`** — 建立攻击者视角并构建高风险代码变更的利用场景。遵循 5 步对抗性方法（攻击者模型、攻击向量、可利用性评级、利用场景、基线交叉引用）并生成结构化漏洞报告。当需要对高风险变更进行第五阶段分析时，委托给此代理，并将完整命名空间名称作为 `subagent_type` 传递——一个纯 `adversarial-modeler` 未注册，运行时调度会失败。

## 质量检查清单

交付前：

- [ ] 所有变更文件已分析
- [ ] 移除的安全代码的 git blame
- [ ] 高风险计算影响范围
- [ ] 攻击场景具体（非通用）
- [ ] 发现引用具体行号 + 提交
- [ ] 生成报告文件
- [ ] 通知用户摘要

## 集成

**audit-context-building 技能：**
- 预分析：构建基线上下文
- 第四阶段：高风险变更的深层上下文

**issue-writer 技能：**
- 将发现转化为正式审计报告
- 命令：`issue-writer --input DIFFERENTIAL_REVIEW_REPORT.md --format audit-report`

## 示例用法

### 快速筛选（小型 PR）
```
输入：5 个文件 PR，2 个高风险文件
策略：使用快速参考
1. 按文件分类风险等级（2 个高风险，3 个低风险）
2. 仅关注 2 个高风险文件
3. git blame 移除的代码
4. 生成最小报告
时间：约 30 分钟
```

### 标准审查（中等代码库）
```
输入：80 个文件，12 个高风险变更
策略：FOCUSED（见 methodology.md）
1. 对高风险文件进行完整工作流程
2. 对中等风险进行表面扫描
3. 跳过低风险文件
4. 完整报告包含所有部分
时间：约 3-4 小时
```

### 深度审计（大型、关键变更）
```
输入：450 个文件，认证系统重写
策略：SURGICAL + audit-context-building
1. 使用 audit-context-building 构建基线上下文
2. 仅分析认证变更
3. 影响范围分析
4. 对抗性建模
5. 全面报告
时间：约 6-8 小时
```

---

## 不应使用此技能的情况

- **绿野代码**（没有基线可比较）
- **仅文档变更**（无安全影响）
- **格式/代码检查**（装饰性变更）
- **用户明确要求仅快速摘要**（他们接受风险）

对于这些情况，使用标准代码审查。

---

## 严重警告（停止并调查）

**立即升级触发器：**
- 从 "安全"、"CVE" 或 "修复" 提交中移除代码
- 移除访问控制修饰符（onlyOwner, internal → external）
- 移除验证而不替换
- 添加外部调用而不检查
- 高影响范围（50+ 调用者）+ 高风险变更

这些模式即使在快速筛选时也需要对抗性分析。

---

## 获取最佳结果的技巧

**要：**
- 从 git blame 开始移除的代码
- 尽早计算影响范围以优先处理
- 生成具体的攻击场景
- 引用具体行号和提交
- 诚实说明覆盖限制
- 始终生成输出文件

**不要：**
- 跳过 git 历史分析
- 没有证据做出通用发现
- 时间有限时声称完整分析
- 忘记检查测试覆盖
- 错过高影响范围变更
- 仅向聊天输出报告（需要文件）
