# 设计接口

基于《软件设计哲学》中的“设计两次”：你的第一个想法很可能不是最好的。生成多个根本不同的设计方案，然后进行比较。

## 工作流程

### 1. 收集需求

设计前先理解：

- [ ] 这个模块解决什么问题？
- [ ] 调用者是谁？（其他模块、外部用户、测试）
- [ ] 关键操作是什么？
- [ ] 有哪些约束？（性能、兼容性、现有模式）
- [ ] 什么应该隐藏在内部，什么应该暴露？

询问：“这个模块需要做什么？谁会使用它？”

### 2. 生成设计方案（并行子代理）

使用任务工具同时生成 3+ 个子代理。每个都必须产出**根本不同**的方法。

```
每个子代理的提示模板：

为：[模块描述] 设计一个接口

需求：[收集到的需求]

此设计的约束：[为每个代理分配不同的约束]
- 代理 1："最小化方法数量 - 最多 1-3 个方法"
- 代理 2："最大化灵活性 - 支持多种用例"
- 代理 3："针对最常见的情况进行优化"
- 代理 4："从 [特定范式/库] 中获取灵感"

输出格式：
1. 接口签名（类型/方法）
2. 使用示例（调用者如何使用）
3. 此设计隐藏的内部细节
4. 此方法权衡的得失
```

### 3. 展示设计方案

每个设计方案展示：

1. **接口签名** — 类型、方法、参数
2. **使用示例** — 调用者在实践中如何使用
3. **隐藏的内容** — 保持在内部的复杂性

按顺序展示设计方案，让用户能在比较前吸收每个方法。

### 4. 比较设计方案

展示所有设计方案后，按以下维度比较：

- **接口简洁性**：更少的方法、更简单的参数
- **通用性 vs 专用性**：灵活性 vs 聚焦
- **实现效率**：接口形状是否允许高效的内部实现？
- **深度**：小接口隐藏大量复杂性（好）vs 大接口搭配薄弱实现（坏）
- **正确使用的便捷性** vs **误用的便捷性**

用散文讨论权衡，不用表格。突出设计方案分歧最大的地方。

### 5. 综合分析

最好的设计方案往往结合多个选项的见解。询问：

- “哪个设计方案最适合你的主要用例？”
- “其他设计方案中是否有值得合并的元素？”

## 评估标准

来自《软件设计哲学》：

**接口简洁性**：更少的方法、更简单的参数 = 更容易学习和正确使用。

**通用性**：能不改动就处理未来的用例。但要警惕过度泛化。

**实现效率**：接口形状是否允许高效的实现？还是迫使内部变得别扭？

**深度**：小接口隐藏大量复杂性 = 深度模块（好）。大接口搭配薄弱实现 = 浅度模块（避免）。

## 反模式

- 不要让子代理产出相似的设计方案；强制根本性的差异
- 不要跳过比较；价值在于对比
- 不要实现；这里只讨论接口形状
- 不要基于实现工作量进行评价
