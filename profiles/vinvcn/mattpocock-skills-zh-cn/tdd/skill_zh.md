# 测试驱动开发

TDD 是一个 red -> green 的循环。这个技能是让这个循环产出值得保留的测试的参考：什么是好的测试、测试应该放在哪里、反模式，以及循环的规则。每个周期前和周期中都要参考这些内容，而不是事后才看。

探索代码库时，读取 `CONTEXT.md`（如果存在），让测试名称和接口词汇与项目的领域语言对齐，并尊重你触碰区域的 ADRs。

## 好的测试是什么样的

测试应该通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应该随之改变。一个好的测试读起来像规范："用户可以用有效的购物车结账" 能清楚地说明存在什么能力；因为它不关心内部结构，所以能够承受重构。

示例见 [tests.md](tests.md)，mocking 规则见 [mocking.md](mocking.md)。

## 连接点 — 测试应该放在哪里

**连接点** 是你测试的公共边界：可以观察行为，但不伸手进入内部的接口。测试放在连接点上，绝不针对内部。

**只测试预先认可的连接点。** 写任何测试前，先写下要测试的连接点并与用户确认。未经确认的连接点不写测试。你无法测试所有东西；提前认可连接点，才能把测试精力放在关键路径和复杂逻辑上，而不是每个边缘情况。

询问："什么是公共接口，我们应该测试哪些连接点？"

当接口的形状本身就是问题所在时——模块应该有多深、连接点应该放在哪里、接口应该暴露什么——调用 Skill 工具并指定 `codebase-design` 获取词汇。它是模块、接口、深度、连接点、适配器、利用和局部性这些术语的共享来源，是供查阅的参考，而不是要运行的会话。

## 反模式

- **与实现耦合** — mock 内部协作者、测试 private methods，或通过 side channel 验证（例如不用接口而直接查询数据库）。特征是重构时测试失败，但行为没有变。
- **同义反复** — 断言以与代码相同的方式重新计算预期值（`expect(add(a, b)).toBe(a + b)`、手工按同一逻辑生成 snapshot、把 constant 断言等于它自己），因此天生通过，永远无法与代码 disagree。预期值必须来自独立的真实来源：已知良好的字面量、工作示例或规范。
- **水平切片** — 先写所有测试，再写所有实现。批量测试验证的是 _想象中的_ 行为：你测试的是东西的 _形状_，不是用户可见的行为；测试会对真实变化迟钝，并在理解实现前承诺测试结构。改用 **垂直切片**：一个测试 -> 一个实现 -> 重复，每个测试都是回应上一轮学习的 **tracer bullet**。

## 循环的规则

- **先 red 再 green。** 先写 failing test，再只写足够让它通过的代码。不要预判未来的测试，也不要添加推测性功能。
- **一次一个切片。** 每个周期只处理一个连接点、一个测试、一个 minimal implementation。
- **重构不是循环的一部分。** 重构属于 review 阶段（见 `code-review` 技能），不属于 red -> green 实现循环。
