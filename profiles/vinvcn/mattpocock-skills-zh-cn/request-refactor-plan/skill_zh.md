当用户想要创建重构请求时调用此技能。按以下步骤执行。你可以跳过你认为不必要的步骤。

1.  让用户详细描述他们想要解决的问题，以及可能的解决方案思路。

2.  探索代码库，验证他们的断言，并理解代码库当前状态。

3.  询问他们是否考虑过其他选项，并向他们展示其他选项。

4.  围绕实现与用户进行访谈。要非常详细、彻底。

5.  确定实现的精确范围。弄清你计划修改什么，以及不修改什么。

6.  在代码库中检查该区域的测试覆盖率。如果覆盖率不足，询问用户的测试计划。

7.  制定将实现拆分成微小提交的计划。记住马丁·福勒的建议：“让每个重构步骤尽可能小，以便你总能看到程序运行。”

8.  使用重构计划创建 GitHub issue。issue 描述使用下面模板：

<refactor-plan-template>

## 问题陈述

开发者面对的问题，从开发者视角描述。

## 解决方案

问题的解决方案，从开发者视角描述。

## 提交记录

一份很长、详细的实现计划。用 plain English 写，将实现拆到尽可能小的提交。每个提交都应让代码库保持可运行状态。

## 决策文档

已作出的实现决策列表。可以包括：

- 将构建/修改的模块
- 将修改的模块接口
- 来自开发者的技术澄清
- 架构决策
- 模式变更
- API 合约
- 特定交互

不要包含具体的文件路径或代码片段。它们可能很快过时。

## 测试决策

已作出的测试决策列表。包括：

- 好测试的描述（只测试外部行为，不测试实现细节）
- 哪些模块会被测试
- 测试的先例（即代码库中类似类型的测试）

## 超出范围

本重构范围外事项的描述。

## 其他备注（可选）

关于重构的其他备注。
