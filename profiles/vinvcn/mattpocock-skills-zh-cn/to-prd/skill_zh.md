这个 skill 使用当前的对话上下文和代码库理解来生成产品需求文档（PRD）。**不要**访谈用户，只需综合你已经知道的内容。

问题追踪器和筛选标签词汇应该已经提供给你；如果没有，运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果还没有探索代码库，先探索它以理解代码库的当前状态。在PRD中始终使用项目的领域术语表词汇，并遵守相关的架构决策记录（ADRs）。

2. 草拟你准备在哪些接口上测试这个功能。优先使用现有的接口，而不是新增接口。使用尽可能高层的接口。如果确实需要新增接口，尽可能在最高层提出。

与用户确认这些接口是否符合预期。

3. 使用下面模板编写PRD，并发布到项目的 问题追踪器。应用 `ready-for-agent` 筛选标签；不需要额外的筛选。

<prd-template>

## 问题陈述

用户面临的问题，从用户视角描述。

## 解决方案

问题的解决方案，从用户视角描述。

## 用户故事

一份很长的编号用户故事列表。每条用户故事使用以下格式：

1. As an <actor>, I want a <feature>, so that <benefit>

<user-story-example>
1. As a mobile bank customer, I want to see balance on my accounts, so that I can make better informed decisions about my spending
</user-story-example>

这份用户故事列表应该非常完整，覆盖功能的各个方面。

## 实现决策

已作出的实现决策列表。可以包括：

- 将构建/修改的模块
- 将修改的模块接口
- 来自开发者的技术澄清
- 架构决策
- 模式变更
- API 合约
- 特定交互

不要包含具体的文件路径或代码片段。它们可能很快过时。

例外：如果原型生成的片段比文字更精确地编码了某个决策（状态机、reducer、模式、类型形状），可以内联到相关决策中，并简短说明它来自原型。只保留决策密集部分，不要放完整的可运行演示。

## 测试决策

已作出的测试决策列表。包括：

- 什么是好测试的描述（只测试外部行为，不测试实现细节）
- 哪些模块会被测试
- 测试的先例（即代码库中类似类型的测试）

## 范围外

本PRD范围外事项的描述。

## 其他备注

关于功能的其他备注。

</prd-template>
