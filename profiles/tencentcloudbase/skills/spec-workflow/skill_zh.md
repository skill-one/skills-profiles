# 规范工作流

## 激活契约

### 首次使用时

- 请求涉及新功能、多步骤产品变更、跨模块集成或架构/设计任务。
- 接受标准不明确，需要在实现前明确。
- 工作涉及多个文件、用户流程、数据库设计或 UI 设计，需要分阶段确认。

### 编写代码前需阅读

- 不确定任务是否应直接编码或应先经过需求、设计和任务规划。
- 请求提及新页面、新系统、重新设计、工作流或多模块重构。

### 也要阅读

- 前端页面或视觉设计工作 -> `../ui-design/SKILL.md`
- 高级数据模型工作 -> `../data-model-creation/SKILL.md`

### 不适用于

- 范围明确的简单 Bug 修复。
- 单文件文档更新。
- 直观的配置变更。
- 用户已给出明确实现指令的微小重构。

### 常见错误/注意事项

- 在接受标准明确前跳转编码。
- 在需求、设计和任务之间缺少用户确认。
- 编写不明确的任务，无法映射回用户可见结果。
- 将 UI 工作视为纯技术实现，未明确设计意图。

### 最小清单

- 判断变更是否真的需要完整规范流程。
- 如需要，先停止并产出需求。
- 如变更小、低风险且接受标准已明确，允许直接执行，无需强制规范文档。
- 使用 EARS 风格接受标准。
- 在进入下一阶段前获取确认。

## 使用此技能的场景

使用此工作流进行结构化开发，当你需要：

- 定义或完善新功能
- 设计复杂架构
- 协调跨模块变更
- 规划数据库或 UI 密集型工作
- 提高需求质量和接受边界

## 决策规则

### 使用完整工作流时

- 任务中等到大
- 影响跨多个模块
- 接受边界模糊
- 用户希望在实现前进行严谨规划

### 跳过完整工作流时

- 任务小、低风险且已精确
- 目标、范围和接受标准足够清晰可直接执行
- 用户明确希望直接编码，无需规划阶段

## 核心工作流

### 阶段 1：需求

创建 `specs/<spec_name>/requirements.md`。

要做什么：

- 重述问题和范围
- 编写用户故事
- 使用 EARS 风格编写接受标准
- 明确业务规则、约束和非目标

EARS 模式：

```text
While <可选前提条件>, when <可选触发条件>, the <系统名称> shall <系统响应>
```

示例：

```text
When the user submits the form, the booking system shall validate required fields before creating the record.
```

### 阶段 2：设计

创建 `specs/<spec_name>/design.md`。

要做什么：

- 描述架构和模块边界
- 解释技术选择和权衡
- 根据需要定义数据模型、API、安全和测试策略
- 仅在图表显著提升清晰度时使用 Mermaid

### 阶段 3：任务

创建 `specs/<spec_name>/tasks.md`。

要做什么：

- 将设计拆分为可执行任务
- 保持任务具体且可审查
- 将每个任务链接回相关需求
- 随工作进展更新任务状态

任务格式：

```markdown
# 实施计划

- [ ] 1. 任务标题
  - 具体工作项
  - 另一个具体步骤
  - _需求：1
```

### 阶段 4：执行

在用户确认任务计划后才能开始实施。

执行期间：

- 保持任务状态更新
- 一次完成一个有意义的单元
- 保持从变更 -> 任务 -> 需求的可追溯性

## 代理工作规则

1. 请求不明确时提出追问；不要猜测核心产品行为。
2. 在需求、设计和任务分解之间要求确认。
3. 变更涉及最终用户页面或视觉决策时，尽早引入 `ui-design`。
4. 保持文档简洁但可测试。
5. 优先用户可见结果而非实现细节的任务名称。

## 输出预期

- `requirements.md` -> 问题、范围、用户故事、EARS 接受标准
- `design.md` -> 架构、技术方案、数据/API/安全/测试说明
- `tasks.md` -> 与需求绑定的可执行实施清单
