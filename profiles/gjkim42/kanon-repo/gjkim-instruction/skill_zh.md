# gjkim_instruction.md — 循环工程的根文档

## 该文档存在的原因

循环工程会针对一个长期存在的目标运行许多短期的代理迭代。每次迭代开始时背景信息很少，因此需要一个稳定的地方来说明必须满足的条件以及已经做出的决定。这个地方就是 `gjkim_instruction.md`，它保存在循环工程所处理的项目根目录下。

该文档防止的是早期决策锁定。根文档中写下的任何内容，后续的每次迭代都会将其视为需求来继承。如果未确认的细节被写下来——比如一个库的选择、一个模式、一个仅是初步猜测的文件布局——错误的猜测就会成为永久性的，循环工程就会失去寻找更好答案的自由。因此，该文档只记录两种类型的内容，并将其他所有内容都视为有意保持开放状态。

## 应包含的内容

- **目标**：一到两句话说明该工作必须达成的目标。
- **最低要求**：该工作成功所必须满足的最小结果集。必须是结果层面的，而不是实现层面的。
- **非目标**：该工作明确不追求的结果，以防止迭代偏离这些方向。非目标是确认的“我们不这样做”，而不仅仅是未决定的事项——未决定的事项属于“有意保持开放”类别。
- **已确认的决定**：只有用户明确确认的决定。每条记录都包含确认日期和一句话的说明，以便后续迭代判断原因是否仍然适用。
- **有意保持开放**（可选）：已知未决定的选择，列出这些选择以防止迭代无声地假设答案。在此列出选项并不代表认可它。

## 应排除的内容

- 未明确确认的实现细节：库、框架、模式、文件布局、API形状、部署目标。
- 任务列表、进度日志、迭代状态。这些属于问题、拉取请求或迭代笔记——根文档描述的是目的地，而不是过程。
- 推测性设计或正在考虑的选项。最多在“有意保持开放”下提及它们，绝不能作为需求或决定。
- 代码本身可推导出的任何内容。

需求与细节的区分测试：是否有两种有意义的实现都能满足它？如果只有一种实现可以，那么它是细节——直到用户将其确认为止，才将其排除。

## 模板

在项目根目录下创建文档，命名为 `gjkim_instruction.md`：

```markdown
# <工作名称>

循环工程的根文档。每次迭代开始时请先阅读此文档。此处未写明的任何内容都是有意的开放选择。

## 目标

<一到两句话>

## 最低要求

- <必须满足的结果>

## 非目标

- <明确不追求的结果>

## 已确认的决定

- <决定> — 确认于 <YYYY-MM-DD>。原因：<一句话>

## 有意保持开放

- <已知未决定的选择；不要假设答案>
```

当“非目标”或“有意保持开放”部分无任何警示价值时，可以省略。保持整个文档在一页左右；如果超出这一页，说明细节正在泄露——请修剪它们。

## 维护文档

- 只有在用户明确确认时才添加决定。“倾向于”、“可能”或“也许”不是确认。
- 只有在用户明确排除时才记录非目标。尚未有人决定的事项仍属于“有意保持开放”。
- 当迭代必须做出文档中未包含的选择时，做出最佳本地选择，在迭代对应的拉取请求或笔记中记录为未确认，并向用户提议确认。不要将其写入根文档。
- 当决定被撤销时，替换该条目。该文档描述的是当前状态；git 历史记录保存着旧状态。
- 更新时，除非用户明确更改，否则保留现有的需求和决定。
