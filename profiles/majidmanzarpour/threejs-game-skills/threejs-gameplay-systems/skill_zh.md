# Three.js 游戏系统

创建或演进一个具有明确所有权、响应式控制、确定性更新顺序以及能够塑造玩家决策空间的可玩浏览器游戏循环。

从实际加载的技能文件中解析 `<this-skill-dir>` 和本地引用；在使用运行时发现的替代方案之前，先解析其旁边的同级技能。

## 从这里开始

```bash
python3 <this-skill-dir>/scripts/create_threejs_game.py ./my-game
```

复制 `assets/threejs-vite-game/` 目录，重写项目名称，并为游戏提供独立的视觉测试和画布检查器。`--force` 参数会覆盖现有目录。

## 先设计

对于广泛的 game creation 或重大设计变更，编写三个简短的设计文档或更新现有文档。狭窄的机制修复使用现有设计并保留无关系统：

**设计简报。** 玩家承诺（一句话的幻想） · 目标手感 · 主要动词 · 次要动词 · 玩家每 5–30 秒重复的操作 · 1–5 分钟内变化的内容 · 玩家如何失败、学习并重新开始 · 获得奖励和产生风险的内容 · 更好的玩家会做不同的操作 · 下一个决策如何传达 · 本切片的非目标。

**核心循环契约。** `玩家通过 [动词] 实现 [目标]，同时 [压力] 产生风险；成功获得 [奖励]，失败导致 [成本/重试]。` 然后在代码中证明每个条款：动词映射到实际输入，目标在世界或 HUD 中可见，压力在第一个可玩分钟内存在，奖励改变状态而不仅仅是视觉效果，失败教会发生了什么，重启足够快以鼓励再次尝试。

**关卡或遭遇战计划。** 空间格式 · 摄像机能看到和看不到的内容 · 玩家起点、第一个决策、第一个威胁、第一个奖励 · 地标 · 每 20–60 秒或每个波次/洞/圈如何提升挑战 · 恢复点 · 如何预告危险区域 · 哪些部分是模块化或参数化的。

"探索一个酷炫的场景" 不是一个设计简报。简报需要决策、压力、反馈和后果。

## 构建

1. 检查现有结构、脚本、依赖项、循环、输入、摄像机、实体、状态、UI、诊断信息。
2. 保持小的所有权边界：`core`、`game`、`entities`、`systems`、`assets`、`ui`、`tests`。
3. 以可玩增量方式实现 —— 输入、状态、实体、碰撞、反馈、HUD 和音频钩子、诊断信息 —— 以确保每一步都有可玩内容。
   在扩展内容之前，在目标摄像机比例下使用实际英雄和反馈建立一个代表性遭遇战。敌人、奖励和道具的多样性应服务于游戏类型的决策，而不是通用的资源配额。
4. 调整手感：移动、加速度、摄像机跟随和 FOV、击打停顿、冲击力反馈、冷却时间、难度、重启。
5. 保持热点路径轻量级，并明确更新顺序。
6. 将所有游戏玩法随机性通过脚手架的种子随机数生成器路由，以便确定性测试钩子保持工作。

对于协同工作，在委托独立模块之前定义输入意图、实体/资源接口和事件。向负责人报告行为变更和本地检查，负责人拥有整合的浏览器流程。当用户变更需求时，更新现有简报和待办任务，而不是重启已完成的工作。

游戏玩法代码触发音频事件；`threejs-audio-generator` 生成实际资源，并提供运行时音频矩阵。

## 技术栈

TypeScript、Vite、Three.js 模块、`three/addons/...` 用于官方控制、加载器和后期处理。`lil-gui` 用于实时调整常量。Web Audio 用于运行时播放。物理引擎选择、时间步长和碰撞器策略遵循 `references/physics-engine-selection.md` — 默认使用 Rapier，当游戏需要真实模拟时。

## 常见问题

静态演示而不是可玩循环 · 机制附加到先构建的场景 · 描述了核心循环但从未通过实际输入、压力、奖励和失败/重试进行验证 · 赛道或竞技场装饰而非塑造决策 · 编译通过的机制但没有输入可以触发 · 摄像机和控制滞后或隐藏下一个决策 · 状态变更从未到达 UI、音频或 VFX · 在任何机制需要之前构建的抽象。

## 报告

行为和控制（广泛构建的三个设计文档）、架构选择和调整值、变更文件，以及你玩游戏时看到的内容。当涉及物理效果时，请注明物理引擎、时间步长和碰撞器策略。
