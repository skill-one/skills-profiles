# Three.js 游戏界面设计师

让游戏界面具有目的性、可读性、响应性，并符合游戏类型。

保留用户要求的范围和风格。对于狭窄的HUD修复，保留现有设计并检查更改状态和目标视口。对于完整的UI过审，请使用以下完整工作流程。当移动设备是目标时，需要移动输入，不是因为只有桌面版游戏有UI。

## 参考

`references/ui-patterns.md` — 层级结构和必需状态、HUD区域、菜单、触摸控制、响应式约束、风格一致性以及状态连接。在设计HUD、菜单、覆盖层、触摸控制或响应式布局之前，请先阅读它。

当标志、图标、GUI艺术、阵营标记、菜单背景或2D HUD资源会提升质量时，加载`threejs-image-generator`。`threejs-3d-generator`仅用于真实的3D菜单对象和情境道具，而不是平面HUD元素。

## 工作流程

1. 捕获现有内容的桌面和移动屏幕截图。
2. 列出UI状态：游戏进行中、暂停、设置、失败和重试、胜利或里程碑、加载、触摸控制。
3. 设置层级：生存和状态，然后是目标，接着是反馈，最后是风味。
4. 用定制的簇、计量器、徽章、图标、警报和模态状态替换工具状态卡。
5. 使用稳定尺寸、安全区域填充、文本适应约束以及悬停/按下/聚焦/禁用状态。
6. 将UI连接到游戏状态，而不是在UI代码中复制游戏规则。
7. 检查文本适应和重叠，最长可能值、安全区域、触摸目标以及两个视口上的实际状态变化。

## 可能出错的地方

通用的状态卡仪表盘 · UI遮挡玩家、威胁或下一个决策 · 在移动设备上移动和裁剪的文本 · 降低可读性的装饰面板 · 看起来正确但发出无意图的触摸控制。

## 报告

覆盖的UI意图和状态、更改的文件、目标视口屏幕截图、文本适应和重叠发现、适用时的安全区域和触摸目标证据，以及剩余风险。将这些结果输入到负责人的整合过审中，而不是重新运行未更改的全局检查。
