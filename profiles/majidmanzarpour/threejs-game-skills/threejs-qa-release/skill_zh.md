# Three.js 测试发布

验证游戏以玩家实际遇到的方式运行，然后准备一个包含已知风险的可发布版本。

从实际加载的技能文件中解析 `<this-skill-dir>` 和本地引用；在使用运行器发现的替代方案之前，先解析其旁边的同级技能。从已安装 npm 依赖的游戏项目运行检查器。

## 测试通过

对于完整游戏使用以下完整测试流程。对于狭窄的编辑，选择涵盖受影响行为、状态和目标视口的检查。重用同一代码修订中的有效专家证据；负责人拥有一个整合的测试流程。仅在相关更改、失败或未解决的关注点后重复测试。显式的仅限桌面范围不需要添加移动端游戏玩法。

1.  安装依赖项，运行构建和类型检查，启动开发或预览服务器。
2.  打开浏览器目标并捕获控制台、页面和网络错误。
3.  确认非空白、视觉多样化的画布像素。
4.  在每个目标视口上捕获活动游戏（默认情况下为桌面和移动端），而不仅仅是标题屏幕。
5.  执行主要输入、目标进度、失败和重试以及最近更改的内容。
6.  检查 HUD 文本适配、安全区域、触摸目标和对响应式布局。
7.  当音频更改时：用户手势解锁、SFX 触发、环境循环开始和停止、暂停和重启清理、静音和音量、解码错误。
8.  确定视觉测试框架。对于高级、发布就绪、UI 密集型或生成资产的工作，框架通常值得使用；无论哪种情况都要说明。
9.  运行机器人测试游戏 (`tests/bot-playtest.template.ts` 在框架游戏中) 以获取发布就绪的游戏玩法声明并报告其指标 JSON。
10. 当动画更改时，捕获一段未暂停的序列并使用 `references/visual-test-harness.md` 检查移动、剪辑过渡、脚步、 rig 变形和攻击/接触时间。

仅屏幕截图无法覆盖游戏玩法更改。

## 画布检查器

```bash
node <this-skill-dir>/scripts/inspect-threejs-canvas.mjs --url http://127.0.0.1:5188 --state active-play --run-id pass-1
```

`--mobile` 选择移动端模拟。`--state <name>`（可选 `--seed <n>`）在捕获前等待游戏的测试钩子。状态钩子必须确认 `{ state: name }`，而 `setPausedForScreenshot` 必须在渲染继续的情况下立即停止模拟。捕获冻结确认的状态，然后稳定；完整的准备阶段有一个超时。缺少钩子、无操作结果、未知状态和匹配错误会导致失败。报告保留 `state` 并添加 `requestedState`、`appliedState` 和 `runId`。框架游戏有自己的副本加上 `npm run inspect:canvas`。

为每次验证通过使用新的 `--run-id` 并使用单独的 `--out` 目录。在捕获前以导演的 `references/evidence-manifest.md` 格式声明预期的视口/状态对，然后使用 `--manifest` 运行其检查器。包含所有请求的状态；不要删除失败的槽位以使清单通过。省略 `--state` 仅执行当前视图的画布检查。

JSON 包含 `metrics` 块（颜色熵、边缘密度、亮度对比、主导色份额）和与等级预算的 `renderBudget` 比较。这些是 `threejs-aaa-graphics-builder/references/visual-scorecard.md` 中视觉评分卡的测量证据；超出预算的行需要一个记录的权衡，空白画布或错误条件会以非零退出。

## 发布测试

检查包脚本、Vite 配置、基本路径和公共资产 → 禁用调试 UI、日志记录和测试辅助工具 → 运行生产构建并在静态服务器上预览 → 在目标视口上检查构建输出 → 审查捆绑包和大型资产 → 记录部署命令、主机假设和残留风险。
