# Ralph TUI PRD 生成器

通过 ralph-tui 创建针对 AI 代理执行优化的详细产品需求文档。

---

## 工作任务

1.  接收用户提供的功能描述
2.  一次提出 3-5 个必要的澄清问题（使用字母选项） - 一次一组
3.  **始终询问质量门禁**（必须通过哪些命令）
4.  每次回答后，根据需要提出后续问题（自适应探索）
5.  当您拥有足够上下文时，生成结构化的 PRD
6.  将 PRD 用 `[PRD]...[/PRD]` 标记输出，以便 TUI 解析

**重要提示：** 不要开始实施。只需创建 PRD。

---

## 第一步：澄清问题（迭代式）

一次一组地提问。每个答案都应指导您接下来的问题。重点在于：

-  **问题/目标：** 这个功能解决了什么问题？
-  **核心功能：** 关键操作是什么？
-  **范围/边界：** 它不应该做什么？
-  **成功标准：** 我们如何知道它已完成？
-  **集成：** 它如何与现有功能配合？
-  **质量门禁：** 每个用户故事必须通过哪些命令？（必需）

### 像这样格式化问题：

```
1. 这个功能的主要目标是什么？
   A. 改善用户引导体验
   B. 提高用户留存率
   C. 减少支持负担
   D. 其他：[请指定]

2. 目标用户是谁？
   A. 仅限新用户
   B. 仅限现有用户
   C. 所有用户
   D. 仅限管理员用户
```

这允许用户以 "1A, 2C" 的形式快速迭代。

如果您在交互式会话中是 Claude Code，您可以使用 AskUserQuestion 工具来呈现这些问题 - 相同的问题和选项，仍然一次一组。当这个技能由 `ralph-tui create-prd` 驱动时，代理将非交互式运行，并且无法回答工具调用，因此像上面那样使用纯文本和字母选项提问。

### 质量门禁问题（必需）

始终询问质量门禁 - 这些是项目特定的：

```
每个用户故事必须通过哪些质量命令？
   A. pnpm typecheck && pnpm lint
   B. npm run typecheck && npm run lint
   C. bun run typecheck && bun run lint
   D. 其他：[指定您的命令]

对于 UI 故事，我们应该包含浏览器验证吗？
   A. 是的，使用 dev-browser 技能进行可视化验证
   B. 不，自动化测试就足够了
```

### 自适应提问

每次回答后，决定是否：

-  提出后续问题（如果答案揭示了复杂性）
-  提出新方面的内容（如果当前领域已清晰）
-  生成 PRD（如果您有足够的上下文）

通常需要 2-4 轮问题。

---

## 第二步：PRD 结构

使用以下部分生成 PRD：

### 1. 简介/概述

简要描述功能及其解决的问题。

### 2. 目标

具体的、可衡量的目标（项目符号列表）。

### 3. 质量门禁

**关键：** 列出每个用户故事必须通过的命令。

```markdown
## 质量门禁

每个用户故事必须通过以下命令：
- `pnpm typecheck` - 类型检查
- `pnpm lint` - 代码检查

对于 UI 故事，也包含：
- 使用 dev-browser 技能在浏览器中验证
```

这个部分由转换工具（ralph-tui-create-json, ralph-tui-create-beads）提取，并附加到每个故事的可接受标准中。

### 4. 用户故事

每个故事需要：

-  **标题：** 简短的描述性名称
-  **描述：** "作为一个 [用户]，我想要 [功能]，以便 [好处]"
-  **可接受标准：** 可验证的清单，说明“完成”意味着什么

每个故事应该足够小，以便在一个专注的 AI 代理会话中实现。

**格式：**
```markdown
### US-001: [标题]
**描述：** 作为一个 [用户]，我想要 [功能]，以便 [好处]。

**可接受标准：**
- [ ] 具体的可验证标准
- [ ] 另一个标准
```

**注意：** 不要在单个故事标准中包含质量门禁命令 - 它们在质量门禁部分中定义一次，并在转换过程中自动应用。

**重要提示：**
- 可接受标准必须是可验证的，而不是模糊的
- "工作正常" 是不好的
- "删除前按钮显示确认对话框" 是好的
- 每个故事应该是独立可完成的

### 5. 功能需求

编号的特定功能列表：
- "FR-1: 系统必须允许用户..."
- "FR-2: 当用户点击 X 时，系统必须..."

明确且无歧义。

### 6. 非目标（超出范围）

这个功能不包括的内容。对管理范围至关重要。

### 7. 技术考虑（可选）
- 已知的约束或依赖
- 与现有系统的集成点
- 性能要求

### 8. 成功指标
如何衡量成功？

### 9. 开放性问题
剩余问题或需要澄清的领域。

---

## 为 AI 代理编写

PRD 将通过 ralph-tui 由 AI 编码代理执行。因此：

-  明确且无歧义
-  用户故事应该小（可以在一个会话中完成）
-  可接受标准应尽可能机器可验证
-  如果您知道，请包含特定的文件路径
-  参考项目中的现有代码模式

---

## 输出格式

**关键：** 用 TUI 解析的标记包装最终的 PRD：

```
[PRD]
# PRD: 功能名称

## 概述
...

## 质量门禁
...

## 用户故事
...
[/PRD]
```

**文件命名：** TUI 将保存到 `./tasks/prd-[功能名称].md`

---

## 示例对话流程

**用户：** 为 TUI 添加暗黑模式创建 PRD

**助手：** 我将帮助您为暗黑模式创建 PRD。让我问几个问题：

1. 主要目标是什么？
   A. 减少长时间会话的眼睛疲劳
   B. 匹配系统主题偏好
   C. 提供视觉定制
   D. 其他

2. 设置是否应该持久化？
   A. 是的，保存到配置文件
   B. 不，仅限会话
   C. 遵循系统偏好

**用户：** 1A, 2A

**助手：** 太好了！再问几个问题：

3. 需要暗黑模式支持哪些组件？
   A. 所有 TUI 组件
   B. 仅主执行视图
   C. 主视图 + 设置
   D. 其他

4. 每个故事必须通过哪些质量命令？
   A. pnpm typecheck && pnpm lint
   B. npm run typecheck && npm run lint
   C. bun run typecheck
   D. 其他：[指定]

5. 对于 UI 故事，包含浏览器验证？
   A. 是的，使用 dev-browser 技能
   B. 不，自动化测试足够

**用户：** 3A, 4A, 5A

**助手：** 完美，我有足够的信息来生成 PRD。

[PRD]
# PRD: Ralph TUI 暗黑模式

## 概述
为 ralph-tui 添加暗黑模式支持，以减少长时间编排会话的眼睛疲劳。该功能将应用于所有 TUI 组件，并将用户的首选主题保存在配置文件中。

## 目标
- 提供在低光环境下的舒适观看体验
- 持久化主题偏好
- 将一致的样式应用于所有 TUI 组件

## 质量门禁

每个用户故事必须通过以下命令：
- `pnpm typecheck` - 类型检查
- `pnpm lint` - 代码检查

对于 UI 故事，也包含：
- 使用 dev-browser 技能进行浏览器验证

## 用户故事

### US-001: 添加主题配置
**描述：** 作为一个用户，我想要设置我的首选主题（亮色/暗色），以便跨会话持久化。

**可接受标准：**
- [ ] 向 `.ralph-tui.yaml` 模式添加 `theme` 字段
- [ ] 支持的值："light", "dark", "system"
- [ ] 默认为 "light"，以向后兼容

### US-002: 创建暗黑主题调色板
**描述：** 作为一个用户，我想要一个柔和对比的暗黑主题，易于眼睛观看。

**可接受标准：**
- [ ] 定义暗黑调色板，使用灰度（而不是纯黑色）
- [ ] 确保足够的对比率（WCAG AA）
- [ ] 颜色适用于所有 UI 状态（选中、悬停、禁用）

### US-003: 将主题应用于 TUI 组件
**描述：** 作为一个用户，我想要所有 TUI 组件尊重我的主题偏好。

**可接受标准：**
- [ ] 标题组件使用主题颜色
- [ ] 任务列表使用主题颜色
- [ ] 详情面板使用主题颜色
- [ ] 进度条使用主题颜色
- [ ] 对话框使用主题颜色

### US-004: 在设置中添加主题切换
**描述：** 作为一个用户，我想要从 TUI 设置中切换主题。

**可接受标准：**
- [ ] 设置视图中可见主题选项
- [ ] 更改立即生效，无需重启
- [ ] 更改保存在配置文件中

## 功能需求
- FR-1: 主题设置必须可从 `.ralph-tui.yaml` 读取
- FR-2: 主题必须在 TUI 启动时应用
- FR-3: 设置中的主题更改必须立即生效
- FR-4: 两种主题下所有文本都必须保持可读性

## 非目标
- 系统主题自动检测（未来增强）
- 超出亮色/暗色的自定义调色板
- 组件级主题覆盖

## 技术考虑
- 如果可用，使用现有的 OpenTUI 主题功能
- 考虑为 React 组件创建 ThemeContext
- 最小化主题更改时的重新渲染

## 成功指标
- 所有组件在暗黑模式下正确渲染
- 没有可访问性对比问题
- 主题跨会话持久化

## 开放性问题
- v2 是否应该自动检测系统主题偏好？

[/PRD]

---

## 检查清单

在输出 PRD 之前：

- [ ] 使用字母选项提出澄清问题
- [ ] 提出关于质量门禁的问题（必需）
- [ ] 根据需要提出后续问题
- [ ] 包含质量门禁部分，并具有项目特定的命令
- [ ] 用户故事足够小，可以独立完成
- [ ] 用户故事不包含质量门禁命令（它们在质量门禁部分中）
- [ ] 功能需求编号且无歧义
- [ ] 非目标部分定义了明确的边界
- [ ] PRD 用 `[PRD]...[/PRD]` 标记包装
