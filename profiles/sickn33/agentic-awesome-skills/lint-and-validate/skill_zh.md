# 代码风格检查与验证

## 使用场景

当仓库在行为或配置变更后存在相关的代码风格检查或类型检查时，应使用。首先阅读仓库说明和包脚本。开发过程中运行聚焦检查，完成前运行必要的检查。

## 操作步骤

1. 确定变更的语言、配置的命令和已安装的工具。执行前检查包脚本：名为 `lint` 的脚本可能修改文件或运行任意项目代码。
2. 运行项目的只读代码风格检查/类型检查命令。对于 Node 项目，优先使用声明的脚本，如 `npm run lint` 和 `npm run typecheck`。不要使用 `npx` 静默获取不存在的检查器。
3. 对于 Python，使用已配置且已安装的工具，如 `ruff check .` 或 `mypy .`。不要假设每个 `pyproject.toml` 都配置了两者。未经检查提议的变更和工作任务的授权，切勿添加 `--fix`。
4. 修复相关失败，但不要删除用户工作、削弱规则或提高超时时间只为通过。如果必要工具不可用，报告未运行的精确检查。
5. 报告命令、退出结果、范围和剩余限制。通过代码风格检查并不能证明不存在运行时或安全缺陷。

## 示例

修正 TypeScript 行为后，检查 `package.json`，运行配置的聚焦回归测试，如果存在这些脚本，再运行 `npm run lint` 和 `npm run typecheck`。如果 TypeScript 声明但未安装，报告缺失的本地检查器；不要用下载的包替代，也不要将结果称为通过。

## 预装辅助工具

- `python scripts/lint_runner.py /绝对的项目路径`：运行保守的候选检查集。Node 降级检查器必须存在于本地 `node_modules/.bin`；Python 候选者必须已安装。首先检查项目脚本。缺失命令或失败检查退出 1；未配置检查或无效项目元数据退出 2。退出 0 表示调用的检查通过，不代表发现了所有需要的检查。Python 检测是启发式的，可能建议未配置的 Ruff/MyPy 命令。
- `python scripts/type_coverage.py /绝对的项目路径`：只读注解清单，尽管其保留的兼容性文件名。每个语言最多采样 30 个文件，跳过链接和构建/依赖目录，并限制文件读取。Python 使用 AST 节点避免重复计数函数。TypeScript 报告词法 `: any` 出现，包括可能的注释和字符串。不推断质量百分比或通过/失败阈值。退出 2 表示没有适用文件；解析/读取错误退出 1。

## 限制

运行器执行受信任的项目命令，这些命令可能修改文件或访问网络。它不会安装依赖、检测所有单仓库配置或替代项目的 CI 合同。清单是有限的源采样，不是语义类型覆盖率；推断的类型、泛型、装饰器行为和正确性需要实际的类型检查器。不要将未运行的检查标记为成功。
