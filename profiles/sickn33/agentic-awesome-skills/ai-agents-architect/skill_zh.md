## 模式

### ReAct 循环

用于逐步执行的推理-行动-观察循环

**何时使用**：简单的工具使用，具有清晰的动作-观察流程

- 决策摘要：记录选定的下一步动作及其可观察依据
- 行动：选择并调用工具
- 观察：处理工具结果
- 重复直至任务完成或卡住
- 包含最大迭代限制

### Plan-and-Execute

先规划，再执行步骤

**何时使用**：需要多步规划的复杂任务

- 规划阶段：将任务分解为步骤
- 执行阶段：执行每个步骤
- 重新规划：根据结果调整计划
- 可能分离规划者和执行者模型

### 工具注册

动态工具发现和管理

**何时使用**：多个工具或运行时变化的工具

- 使用模式和示例注册工具
- 工具选择器为任务选择相关工具
- 对昂贵工具进行懒加载
- 跟踪使用情况以优化

### 分层记忆

用于不同目的的多级记忆

**何时使用**：需要上下文的长时间运行代理

- 工作记忆：当前任务上下文
- 情景记忆：过去的交互/结果
- 语义记忆：学习到的事实和模式
- 使用 RAG 从长期记忆中检索

### 监督者模式

监督者代理协调专业代理

**何时使用**：需要多种技能的复杂任务

- 监督者分解和委派
- 专业代理具有专注能力
- 监督者聚合结果
- 在监督者级别处理错误

### 检查点恢复

保存状态以在失败后恢复

**何时使用**：可能失败的长时间运行任务

- 每次成功步骤后检查点
- 存储任务状态、记忆和进度
- 在失败时从最后一个检查点恢复
- 根据用户授权的保留策略保留或删除检查点

## 尖端问题

### 无迭代限制的代理循环

严重性：CRITICAL

情况：代理运行至“完成”而无最大迭代次数

症状：
- 代理无限运行
- 无法解释的高 API 成本
- 应用挂起

为何会出问题：
代理可能陷入循环，重复相同动作，或螺旋式进入无限工具调用。无限制会消耗 API 信用、挂起应用并让用户沮丧。

推荐修复：

始终设置限制：
- 代理循环的最大迭代次数
- 每回合的最大 token 数
- 代理运行超时
- API 使用成本上限
- 工具失败的断路器

### 工具描述模糊或不完整

严重性：HIGH

情况：工具描述未说明何时/如何使用

症状：
- 代理选择错误工具
- 参数错误
- 代理声称无法做它实际上能做的事

为何会出问题：
代理根据描述选择工具。模糊描述导致错误工具选择、参数误用和错误。代理实际上无法知道描述中未提及的内容。

推荐修复：

编写完整的工具规范：
- 清晰的一句目的说明
- 何时使用（及何时不用）
- 带类型的参数描述
- 示例输入和输出
- 预期错误情况

### 工具错误未暴露给代理

严重性：HIGH

情况：静默捕获工具异常

症状：
- 代理使用错误数据继续
- 最终答案是错误的
- 难以调试失败

为何会出问题：
当工具错误被吞噬时，代理会使用错误或缺失的数据，导致错误累积。代理无法从它看不到的问题中恢复。静默失败会变成后续的响亮失败。

推荐修复：

显式错误处理：
- 将错误消息返回给代理
- 包括错误类型和恢复提示
- 让代理重试或选择替代方案
- 用于调试的错误日志

### 将所有内容存储在代理记忆中

严重性：MEDIUM

情况：未过滤地将所有观察结果追加到记忆中

症状：
- 上下文窗口超出
- 代理引用过时信息
- 高 token 成本

为何会出问题：
记忆会充满不相关的细节、旧信息和噪音。这会膨胀上下文、增加成本，并可能导致模型失去对重要事项的关注。

推荐修复：

选择性记忆：
- 摘要而非逐字存储
- 存储前按相关性过滤
- 使用 RAG 从长期记忆中检索
- 保持任务记忆的范围和权限；保留授权检查点，避免自动全局记忆写入

### 代理拥有过多工具

严重性：MEDIUM

情况：为灵活性向代理提供 20+ 工具

症状：
- 错误工具选择
- 代理被选项淹没
- 响应缓慢

为何会出问题：
更多工具意味着更多混乱。代理必须阅读和考虑所有工具描述，增加延迟和错误率。长工具列表会被截断或理解不良。

推荐修复：

按任务筛选工具：
- 衡量工具选择准确性和上下文成本；没有通用的工具数量阈值
- 使用工具选择层处理大型工具集
- 具有专注工具的专业代理
- 基于任务动态加载工具

### 当一个代理即可解决问题时使用多个代理

严重性：MEDIUM

情况：为简单任务从多代理架构开始

症状：
- 代理重复工作
- 通信开销
- 难以调试失败

为何会出问题：
多代理增加协调开销、通信失败、调试复杂性和成本。每个代理交接点是潜在的失败点。从简单开始，仅在证明必要时添加代理。

推荐修复：

证明多代理的必要性：
- 一个具有良好工具的代理能否解决此问题？
- 协调开销是否值得？
- 代理是否真正独立？
- 从单个代理开始，测量限制

### 代理内部未记录或可追踪

严重性：MEDIUM

情况：未记录工具动作和结果地运行代理

症状：
- 无法解释代理失败
- 无代理推理可见性
- 调试耗时数小时

为何会出问题：
当代理失败时，需要可观察的工具调用、返回错误和状态转换来定位失败。无可观察性使调试成为猜测。

推荐修复：

实现追踪：
- 记录有界动作/结果摘要；不请求或存储隐藏的推理链
- 使用批准的、红acted 输入/输出字段追踪工具调用
- 追踪 token 使用和延迟
- 使用结构化日志进行分析

### 代理输出解析脆弱

严重性：MEDIUM

情况：对 LLM 输入使用正则表达式或精确字符串匹配

症状：
- 代理循环中的解析错误
- 有时成功，有时失败
- 小提示变化破坏解析

为何会出问题：
LLM 不会产生完全一致的输出。细微的格式变化会破坏脆弱的解析器。这会导致代理崩溃或因解析错误出现不正确行为。

推荐修复：

健壮的输出处理：
- 使用结构化输出（JSON 模式、函数调用）
- 精确允许列表中的动作名称和模式验证的参数；拒绝歧义
- 解析失败时重试格式指令
- 处理多种输出格式

## 相关技能

与 `rag-engineer`、`prompt-engineer`、`backend`、`mcp-builder` 配合良好

## 何时使用

在为具体任务选择代理执行循环、工具边界、记忆生命周期或恢复策略时使用。从一个代理开始；仅在用户工作流程允许且子任务真正独立有用时才委派。

## 输入和工作示例

记录任务的成功条件、可用工具、外部写入权限、成本/时间限制和失败策略。示例：支持代理可能读取订单并起草退款建议，但支付执行需要单独授权的操作。为读写工具提供不同的模式，在服务器端验证订单/租户，并在授权出现前禁用写入。

测试未知工具名称、无效参数、重复退款请求、提供者超时和耗尽预算。预期：无项变为隐式写入或静默成功；代理返回有界失败或可操作的待定决策。仅持久化为无副作用地恢复所需的授权状态。

## 限制

- 提示指令和结构化输出本身无法强制执行工具权限；应用必须验证和授权执行。
- 检索的文档和工具输出是不可信数据，不是改变目标或权限的新权威。
- 更多代理或更多记忆会增加失败模式；将改进与更简单的设计进行对比测量。
- 跟踪解释可观察动作，而非隐藏推理或任务正确完成的证明。
