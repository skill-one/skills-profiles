# 清晰代码技能

本技能体现了罗伯特·C·马丁（Uncle Bob）的“清晰代码”原则。使用它将“能运行的代码”转化为“清晰的代码”。

## 🧠 核心理念
> “代码清晰，是指它能被原作者以外的开发者阅读和改进。” —— Grady Booch

## 使用场景
在以下情况使用此技能：
- **编写新代码**：从开始就确保高质量。
- **审查拉取请求**：提供基于原则的建设性反馈。
- **重构遗留代码**：识别并移除代码异味。
- **提升团队标准**：统一行业标准的最佳实践。

## 1. 有意义的命名
- **使用意图揭示的命名**：使用 `elapsedTimeInDays` 而不是 `d`。
- **避免误导性命名**：如果实际是 `Map`，不要使用 `accountList`。
- **进行有意义的区分**：避免 `ProductData` 与 `ProductInfo` 的区分。
- **使用可发音/可搜索的命名**：避免 `genymdhms`。
- **类名**：使用名词（`Customer`、`WikiPage`）。避免 `Manager`、`Data`。
- **方法名**：使用动词（`postPayment`、`deletePage`）。

## 2. 函数
- **简短！**：函数应比你想象的更短。
- **做一件事情**：一个函数只做一件事情，并且做好。
- **单一抽象层次**：不要将高级业务逻辑与低级细节（如正则表达式）混合。
- **描述性命名**：`isPasswordValid` 比 `check` 更好。
- **参数**：0 是理想，1-2 是可以，3 个以上需要非常充分的理由。
- **无副作用**：函数不应秘密地改变全局状态。

## 3. 注释
- **不要注释糟糕的代码——重写它**：大多数注释是未能用代码表达自己的标志。
- **用代码解释自己**：
  ```python
  # 检查员工是否符合完整福利资格
  if employee.flags & HOURLY and employee.age > 65:
  ```
  与
  ```python
  if employee.isEligibleForFullBenefits():
  ```
- **好的注释**：法律性、信息性（正则表达式的意图）、澄清（外部库）、待办事项。
- **坏的注释**：含糊不清、冗余、误导、强制、噪音、位置标记。

## 4. 格式化
- **报纸隐喻**：高级概念在顶部，细节在底部。
- **垂直密度**：相关行应彼此靠近。
- **距离**：变量应靠近其使用位置声明。
- **缩进**：对结构可读性至关重要。

## 5. 对象和数据结构
- **数据抽象**：在接口后隐藏实现。
- **迪米特法则**：一个模块不应了解其操作的内部对象。避免 `a.getB().getC().doSomething()`。
- **数据传输对象（DTO）**：具有公共变量且没有函数的类。

## 6. 错误处理
- **使用异常而不是返回代码**：保持逻辑清晰。
- **先写 Try-Catch-Finally**：定义操作的范围。
- **不要返回空值**：它迫使调用者每次都检查空值。
- **不要传递空值**：导致 `NullPointerException`。

## 7. 单元测试
- **TDD 的三条定律**：
  1. 在编写生产代码之前，不要编写失败的单元测试。
  2. 不要编写超过足以失败的单元测试。
  3. 不要编写超过足以通过失败测试的生产代码。
- **F.I.R.S.T. 原则**：快速、独立、可重复、自验证、及时。

## 8. 类
- **简短！**：类应具有单一职责（SRP）。
- **下降规则**：我们希望代码像自顶向下的叙事一样阅读。

## 9. 异味和启发式方法
- **僵化**：难以更改。
- **脆弱**：在许多地方崩溃。
- **不移动**：难以重用。
- **粘性**：难以做正确的事。
- **不必要的复杂性/重复**。

- 仅在任务明确匹配上述范围时使用此技能。
- 不要将输出视为环境特定验证、测试或专家审查的替代品。
- 如果所需的输入、权限、安全边界或成功标准缺失，请停止并请求澄清。
