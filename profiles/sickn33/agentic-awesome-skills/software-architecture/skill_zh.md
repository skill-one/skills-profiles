# 软件架构开发技能

本技能为注重质量的软件开发和架构提供指导。它基于 Clean Architecture 和领域驱动设计（Domain Driven Design）原则。

## 代码风格规范

### 一般原则

- **早期返回模式**：在可能的情况下，始终使用早期返回代替嵌套条件，以提高可读性
- 通过创建可重用的函数和模块来避免代码重复
- 将长（超过 80 行代码）的组件和函数分解成多个较小的组件和函数。如果它们不能在别处使用，请将其保留在同一个文件中。但如果文件超过 200 行代码，则应将其拆分成多个文件。
- 在可能的情况下，使用箭头函数代替函数声明

### 最佳实践

#### 先库后发（Library-First Approach）

- **始终在编写自定义代码之前搜索现有解决方案**
  - 检查 npm 以查找解决该问题的现有库
  - 评估现有的服务/SaaS 解决方案
  - 考虑用于常见功能的第三方 API
- 使用库而不是编写自己的工具或辅助函数。例如，使用 `cockatiel` 而不是编写自己的重试逻辑。
- **当自定义代码是合理时：**
  - 特定于领域的业务逻辑
  - 具有特殊要求的性能关键路径
  - 当外部依赖过于复杂时
  - 需要完全控制的敏感安全代码
  - 在彻底评估后，现有解决方案无法满足要求时

#### 架构和设计

- **Clean Architecture & DDD 原则：**
  - 遵循领域驱动设计和通用语言
  - 将领域实体与基础设施问题分离
  - 使业务逻辑独立于框架
  - 清晰地定义用例并保持其隔离
- **命名规范：**
  - **避免** 通用名称：`utils`、`helpers`、`common`、`shared`
  - **使用** 特定于领域的名称：`OrderCalculator`、`UserAuthenticator`、`InvoiceGenerator`
  - 遵循有界上下文命名模式
  - 每个模块应具有单一、清晰的目的
- **关注点分离：**
  - 不要将业务逻辑与 UI 组件混合
  - 将数据库查询从控制器中分离出来
  - 在上下文之间保持清晰的边界
  - 确保职责的适当分离

#### 需要避免的反模式

- **本地产出综合症（NIH Syndrome）：**
  - 当 Auth0/Supabase 存在时，不要构建自定义认证
  - 不要用 Redux/Zustand 代替使用自定义状态管理
  - 不要创建自定义表单验证，而应使用成熟的库
- **糟糕的架构选择：**
  - 将业务逻辑与 UI 组件混合
  - 在控制器中直接进行数据库查询
  - 缺乏清晰的关注点分离
- **通用命名反模式：**
  - 包含 50 个不相关函数的 `utils.js`
  - 作为垃圾场的 `helpers/misc.js`
  - 目的不明确的 `common/shared.js`
- 请记住：每一行自定义代码都是一个需要维护、测试和文档化的负债

#### 代码质量

- 使用带类型注解的 catch 块进行适当的错误处理
- 将复杂逻辑分解成更小、可重用的函数
- 避免深层嵌套（最大 3 层）
- 在可能的情况下，保持函数聚焦且不超过 50 行
- 在可能的情况下，保持文件聚焦且不超过 200 行代码

## 适用场景
本技能适用于执行概述中描述的工作流程或操作。
