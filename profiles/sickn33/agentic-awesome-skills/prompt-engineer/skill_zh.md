## 目的

这项技能将原始、无结构的用户提示转化为使用成熟提示框架的高度优化提示。它分析用户意图，识别任务复杂度，并智能选择最合适的框架，以最大化 Claude/ChatGPT 输出质量。

该技能在“魔法模式”下运行——它在后台默默工作，仅在需要澄清时才与用户交互。用户将收到经过润色、可直接使用的提示，而无需技术解释或框架术语。

这是一项**通用技能**，适用于任何终端环境，不仅限于 Obsidian 密室或特定项目结构。

## 何时使用

在以下情况下调用此技能：

- 用户提供的提示模糊或通用（例如，“帮我写 Python 代码”）
- 用户有复杂想法但难以清晰地表达
- 用户的提示缺乏结构、背景或具体要求
- 任务需要逐步推理（调试、分析、设计）
- 用户需要特定 AI 任务的提示但不知道提示框架
- 用户想提高现有提示的有效性
- 用户询问“如何向 AI 提问…”或“创建一个提示…”的变体

## 工作流程

### 第 1 步：分析意图

**目标：** 了解用户真正想完成什么。

**操作：**
1. 读取用户提供的原始提示
2. 检测任务特征：
   - **类型：** 编程、写作、分析、设计、学习、规划、决策、创意等
   - **复杂度：** 简单（一步）、中等（多步）、复杂（需要推理/设计）
   - **清晰度：** 明确意图 vs. 模糊/模糊
   - **领域：** 技术、商业、创意、学术、个人等
3. 识别隐含要求：
   - 用户是否需要示例？
   - 是否指定了输出格式？
   - 是否有约束（时间、资源、范围）？
   - 这是探索性还是执行导向？

**检测模式：**
- **简单任务：** 短提示（<50 字符），单个动词，无背景
- **复杂任务：** 长提示（>200 字符），多个要求，条件逻辑
- **模糊任务：** 通用动词（“帮助”、“改进”），缺少对象/背景
- **结构化任务：** 提及步骤、阶段、交付成果、利益相关者


### 第 2 步：询问澄清问题（有条件）

**目标：** 仅在框架选择或提示质量关键时收集缺失信息。

**触发条件**——仅当：
- 任务类型完全模糊（无法确定编程 vs. 写作 vs. 分析）
- 目标受众未知且实质性影响输出
- 范围未定义且选择错误范围会使提示无效
- 请求的输出格式冲突或缺失且无法推断

**问题限制：**
- 每次调用最多 3 个问题
- 尽可能将相关问题合并为一个
- 如果存在足够背景，完全跳过此步骤（大多数情况）

**示例澄清交流：**

```
用户: "帮我用 AI"

第 2 步（触发——任务类型模糊）：
“为了制作最佳提示，我需要快速澄清一点：
1. 你想用 AI 做什么——构建东西，了解它，还是使用 AI 工具完成任务？”
```

**关键规则：** 疑虑时，跳过澄清并使用现有背景生成最佳提示。过度提问会破坏“魔法模式”体验。


### 第 3 步：选择框架

**目标：** 将任务特征映射到最佳提示框架。

**框架映射逻辑：**

| 任务类型       | 推荐框架               | 理由         |
|---------------|-----------------------|-------------|
| **基于角色的任务**（扮演专家、顾问） | **RTF**（角色-任务-格式） | 清晰的角色定义 + 任务 + 输出格式 |
| **逐步推理**（调试、证明、逻辑）     | **思维链**             | 鼓励明确的推理步骤 |
| **结构化项目**（多阶段、交付成果）   | **RISEN**（角色、指令、步骤、最终目标、缩小范围） | 复杂工作的全面结构 |
| **复杂设计/分析**（系统、架构）     | **RODES**（角色、目标、细节、示例、确认） | 在细节和验证之间取得平衡 |
| **总结**（压缩、综合）             | **密度链**             | 迭代精炼到核心信息 |
| **沟通**（报告、演示、讲故事）     | **RACE**（角色、受众、背景、期望） | 受众感知信息传递 |
| **调查/分析**（研究、诊断）         | **RISE**（研究、调查、综合、评估） | 系统性分析方法 |
| **情境化情况**（问题解决带背景）     | **STAR**（情境、任务、行动、结果） | 丰富的背景问题框架 |
| **文档**（医疗、技术、记录）         | **SOAP**（主观、客观、评估、计划） | 结构化信息捕获 |
| **目标设定**（OKRs、目标、目标）     | **CLEAR**（协作、有限、情感、可感知、可调整） | 目标清晰度和可操作性 |
| **指导/发展**（指导、成长）         | **GROW**（目标、现实、选项、意愿） | 发展性对话结构 |

**混合策略：**
- **组合 2-3 个框架**，当任务跨越多种类型时
- 示例：复杂技术项目 → **RODES + 思维链**（结构 + 推理）
- 示例：领导力决策 → **CLEAR + GROW**（目标清晰度 + 发展）

**选择标准：**
- 主要框架 = 与核心任务类型最佳匹配
- 次要框架 = 解决额外的复杂度维度
- 避免过度设计：简单任务获得简单框架

**关键规则：** 此选择**无声**进行——不要向用户解释框架选择。


**角色：** 你是一位高级软件架构师。[RTF - 角色]

**目标：** 为 [系统] 设计微服务架构。[RODES - 目标]

逐步进行：[思维链]
1. 分析当前单体约束
2. 确定服务边界
3. 设计服务间通信
4. 规划数据一致性策略

细节：[RODES - 细节]
- 预期流量：[X]
- 数据量：[Y]
- 团队规模：[Z]

输出格式：[RTF - 格式]
提供架构图描述、服务定义和迁移路线图。

确认：[RODES - 确认]
验证服务是否松散耦合、可独立部署，并与业务领域一致。

**4.5. 语言适配**
- 如果原始提示是葡萄牙语，生成葡萄牙语提示
- 如果原始提示是英语，生成英语提示
- 如果混合，默认为英语（对 AI 模型更通用）

**4.6. 质量检查**
最终确定前，验证：
- [ ] 提示是自包含的（无需外部背景）
- [ ] 任务是具体且可衡量的
- [ ] 输出格式清晰
- [ ] 无模糊语言
- [ ] 任务复杂度适当详细


## 关键规则

### **绝不：**

- ❌ 假设未提供的信息——如果关键细节缺失，请始终询问
- ❌ 解释选择了哪个框架或为什么（魔法模式——保持其不可见）
- ❌ 生成通用、一刀切的提示——始终根据背景定制
- ❌ 在最终提示中使用技术术语（除非用户领域是技术的）
- ❌ 询问超过 3 个澄清问题（避免用户疲劳）
- ❌ 在输出中包含元评论（“此提示使用…”、“注意…”）
- ❌ 无代码块格式化地呈现输出
- ❌ 混合语言不一致（如果用户用 PT 写，用 PT 回应）

### **始终：**

- ✅ 生成前分析意图（第 1 步是强制性的）
- ✅ 如果关键信息模糊，有条件地询问澄清问题（第 2 步）
- ✅ 根据任务类型和复杂度选择框架（第 3 步映射）
- ✅ 当混合多个框架能提高提示质量时
- ✅ 根据原始输入复杂度调整提示长度（简单 → 短，复杂 → 详细）
- ✅ 在生成的提示中包含输出格式规范
- ✅ 以干净的 Markdown 代码块呈现最终提示
- ✅ 使提示自包含（不依赖外部背景）
- ✅ 在复杂提示中使用示例来说明预期输出
- ✅ 在呈现前验证提示完整性（第 4.6 步质量检查）


### **示例 2：复杂清晰提示 → RODES + 思维链（无需澄清）**

**用户输入：**
```
copilot> 创建提示：我需要构建一个考虑购买历史、用户偏好和市场趋势的产品推荐系统
```

**技能内部处理：**
1. **分析：** 明确意图，复杂任务（ML 系统设计），技术领域
2. **澄清：** 跳过（信息充足）
3. **选择：** RODES（复杂设计）+ 思维链（推理需要）

**技能输出：**

````markdown
```
角色：你是一位专注于推荐系统的资深机器学习工程师。

目标：设计一个结合用户购买历史、偏好和市场趋势的产品推荐系统。

细节：
- 输入数据源：用户交易记录、偏好调查、市场趋势 API
- 算法考虑：协同过滤、基于内容的过滤、混合方法
- 性能指标：精确度、召回率、多样性、新颖性
- 可扩展性：系统必须支持 10 万+ 用户
- 实时约束：推荐必须在 500 毫秒内更新

逐步进行：
1. 分析三个数据源及其关系
2. 提出至少 2-3 种算法方法并分析权衡
3. 设计数据管道架构（摄取、处理、服务）
4. 定义评估指标和 A/B 测试策略
5. 概述实施路线图，分阶段进行

示例：
- 显示核心推荐逻辑的伪代码
- 说明数据流图
- 提供样本 API 响应结构

确认：验证所提出的解决方案在个性化与发现之间取得平衡，可扩展到生产负载，并有效结合实时市场趋势。

输出格式：技术设计文档，包含架构图、算法论证和实施路线图。
```
````


### **示例 4：代码调试 → 思维链**

**用户输入：**
```
copilot> 优化提示：我的 Python 代码无法工作，需要调试
```

**技能内部处理：**
1. **分析：** 调试任务，需要逐步推理
2. **澄清：** 跳过（用户稍后会提供代码背景）
3. **选择：** 思维链

**技能输出：**

````markdown
```
你是一位 Python 专家调试器。

任务：通过逐步分析用户提供的 Python 代码进行调试。

调试方法：
1. 阅读并理解代码的预期目的
2. 识别错误或意外行为
3. 追踪每个执行步骤的变量状态
4. 找到问题的根本原因
5. 提出修复方案并解释
6. 建议预防措施以避免类似错误

逐步展示你的推理：
- 你在检查什么
- 你发现了什么
- 为什么这很重要

输出格式：
- **问题识别：** [描述错误]
- **根本原因：** [为什么会发生]
- **修复：** [带注释的修正代码]
- **预防：** [最佳实践以避免此类错误]
- **示例：** 包含一个工作示例以验证修复。
```
````


## 备注

这项技能是**平台无关**的，在任何 GitHub Copilot CLI 可用的终端环境中都能工作。它不依赖于：
- Obsidian 密室结构
- 特定项目配置
- 外部文件或模板

该技能完全自包含，仅基于用户输入和框架知识运行。

## 限制

- 仅在任务明确符合上述范围时使用此技能。
- 不要将输出视为环境特定验证、测试或专家审查的替代品。
- 如果缺少所需输入、权限、安全边界或成功标准，请停止并请求澄清。
