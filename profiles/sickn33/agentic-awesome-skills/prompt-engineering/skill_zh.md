# 提示工程模式

高级提示工程技术，以最大化大型语言模型的性能、可靠性和可控性。

## 核心能力

### 1. 少样本学习

通过展示示例来教授模型，而不是解释规则。包含 2-5 个输入-输出对来展示期望的行为。当你需要一致的格式、特定的推理模式或处理边缘情况时使用。更多示例可以提高准确性，但会消耗 token——根据任务复杂度进行平衡。

**示例：**

```markdown
从支持工单中提取关键信息：

输入："我的登录无法工作，并且一直收到错误 403"
输出：{"问题": "身份验证", "错误代码": "403", "优先级": "高"}

输入："功能请求：在设置中添加暗黑模式"
输出：{"问题": "功能请求", "错误代码": null, "优先级": "低"}

现在处理："无法上传大于 10MB 的文件，收到超时"
```

### 2. 思维链提示

在最终答案之前请求逐步推理。添加"让我们逐步思考"（零样本）或包含示例推理轨迹（少样本）。用于需要多步逻辑的复杂问题、数学推理，或当你需要验证模型的思考过程时。通过 30-50% 提高分析任务的准确性。

**示例：**

```markdown
分析这个错误报告并确定根本原因。

逐步思考：

1. 预期行为是什么？
2. 实际行为是什么？
3. 最近发生了什么变化可能导致这个问题？
4. 哪些组件涉及其中？
5. 最可能的原因是什么？

错误："用户在昨天部署缓存更新后无法保存草稿"
```

### 3. 提示优化

通过测试和改进系统性地提高提示。从简单开始，测量性能（准确性、一致性、token 使用量），然后迭代。在多样化的输入（包括边缘情况）上进行测试。使用 A/B 测试来比较变体。对于生产提示至关重要，其中一致性和成本很重要。

**示例：**

```markdown
版本 1（简单）："总结这篇文章"
→ 结果：长度不一致，遗漏关键点

版本 2（添加约束）："用 3 个要点总结这篇文章"
→ 结果：结构更好，但仍然遗漏细节

版本 3（添加推理）："识别 3 个主要发现，然后总结每个"
→ 结果：一致、准确、捕获关键信息
```

### 4. 模板系统

使用变量、条件部分和模块化组件构建可重用的提示结构。用于多轮对话、基于角色的交互，或当相同的模式适用于不同输入时。减少重复并确保相似任务之间的一致性。

**示例：**

```python
# 可重用的代码审查模板
template = """
审查这个 {language} 代码的 {focus_area}。

代码：
{code_block}

提供关于以下方面的反馈：
{checklist}
"""

# 使用
prompt = template.format(
    language="Python",
    focus_area="安全漏洞",
    code_block=user_code,
    checklist="1. SQL 注入\n2. XSS 风险\n3. 身份验证"
)
```

### 5. 系统提示设计

设置跨对话持久的行为和约束。定义模型的角色、专业水平、输出格式和安全指南。使用系统提示来稳定指令，这些指令不应逐轮变化，从而释放用户消息 token 用于可变内容。

**示例：**

```markdown
系统：你是一位高级后端工程师，专长于 API 设计。

规则：

- 始终考虑可扩展性和性能
- 默认情况下建议 RESTful 模式
- 立即标记安全问题
- 用 Python 提供代码示例
- 使用早期返回模式

以以下格式响应：

1. 分析
2. 建议
3. 代码示例
4. 权衡
```

## 关键模式

### 逐步披露

从简单的提示开始，仅在需要时增加复杂性：

1. **级别 1**：直接指令

   - "总结这篇文章"

2. **级别 2**：添加约束

   - "用 3 个要点总结这篇文章，重点关注关键发现"

3. **级别 3**：添加推理

   - "阅读这篇文章，识别主要发现，然后用 3 个要点总结"

4. **级别 4**：添加示例
   - 包含 2-3 个输入-输出对的示例总结

### 指令层次结构

```
[系统上下文] → [任务指令] → [示例] → [输入数据] → [输出格式]
```

### 错误恢复

构建能够优雅处理失败的提示：

- 包含备用指令
- 请求置信度分数
- 在不确定时请求替代解释
- 指定如何表示缺失信息

## 最佳实践

1. **具体**：模糊的提示会产生不一致的结果
2. **展示而非说明**：示例比描述更有效
3. **广泛测试**：在多样化的代表性输入上评估
4. **快速迭代**：小的改变可能产生大的影响
5. **监控性能**：在生产中跟踪指标
6. **版本控制**：将提示视为代码，并进行适当的版本控制
7. **记录意图**：解释为什么提示结构如此

## 常见陷阱

- **过度工程**：在尝试简单提示之前开始使用复杂的提示
- **示例污染**：使用与目标任务不匹配的示例
- **上下文溢出**：用过多的示例超出 token 限制
- **模糊指令**：留下多种解释的空间
- **忽略边缘情况**：不在不寻常或边界输入上测试

## 何时使用
这项技能适用于执行概述中描述的工作流程或操作。

## 限制
- 仅在任务明确匹配上述范围时使用此技能。
- 不要将输出视为环境特定验证、测试或专家审查的替代品。
- 如果缺少必需的输入、权限、安全边界或成功标准，请停止并请求澄清。
