# 上下文压缩策略

当代理会话生成数百万个对话历史记录时，压缩变得必不可少。朴素的方法是进行激进压缩以最小化每个请求的令牌数。正确的优化目标是每个任务的令牌数：完成任务所消耗的总令牌数，包括当压缩丢失关键信息时重新获取的成本。

## 何时使用
激活此技能当：
- 代理会话超出上下文窗口限制
- 代码库超出上下文窗口（5M+ 令牌系统）
- 设计对话摘要策略
- 调试代理"忘记"它们修改了哪些文件的情况
- 构建压缩质量的评估框架

## 核心概念

上下文压缩以令牌节省为代价来牺牲信息损失。三种可投入生产的方案存在：

1. **锚定迭代摘要**：维护结构化、持久的摘要，具有明确的会话意图、文件修改、决策和下一步行动的部分。当压缩触发时，仅摘要新截断的部分并与现有摘要合并。结构通过为特定信息类型分配专门部分来强制保留。

2. **不透明压缩**：生成针对重建保真度优化的压缩表示。实现最高的压缩率（99%+），但牺牲了可解释性。无法验证保存了什么。

3. **再生完整摘要**：在每次压缩时生成详细的结构化摘要。产生可读输出，但由于完整再生而非增量合并，可能会因重复压缩周期而丢失细节。

关键洞察：结构强制保留。专门部分充当摘要器必须填充的清单，防止无声的信息漂移。

## 详细主题

### 每个任务令牌数为何重要

传统压缩指标针对每个请求的令牌数。这是错误的优化。当压缩丢失关键细节（如文件路径或错误消息）时，代理必须重新获取信息、重新探索方法，并浪费令牌来恢复上下文。

正确的指标是每个任务的令牌数：从任务开始到完成所消耗的总令牌数。一种节省 0.5% 更多令牌但导致 20% 更多重新获取成本的压缩策略总体上更昂贵。

### 轨迹问题

轨迹完整性在所有压缩方法中是最弱的维度，在评估中得分 2.2-2.5（满分 5.0）。即使是具有明确文件部分的 结构化摘要 也难以在长时间会话中保持完整的文件跟踪。

编码代理需要知道：
- 哪些文件被创建
- 哪些文件被修改以及发生了什么变化
- 哪些文件被读取但未更改
- 函数名、变量名、错误消息

这个问题可能需要超出一般摘要的专门处理：一个单独的轨迹索引或在代理框架中明确跟踪文件状态。

### 结构化摘要部分

有效的结构化摘要包括明确的部分：

```markdown
## 会话意图
[用户试图完成什么]

## 修改的文件
- auth.controller.ts: 修复 JWT 令牌生成
- config/redis.ts: 更新连接池
- tests/auth.test.ts: 添加新配置的模拟设置

## 做出的决策
- 使用 Redis 连接池而不是每个请求的连接
- 持久故障的指数退避重试逻辑

## 当前状态
- 14 个测试通过，2 个失败
- 剩余：模拟设置会话服务测试

## 下一步行动
1. 修复剩余的测试失败
2. 运行完整测试套件
3. 更新文档
```

这种结构防止文件路径或决策的无声丢失，因为每个部分都必须明确处理。

### 压缩触发策略

何时触发压缩与如何压缩一样重要：

| 策略 | 触发点 | 交易 |
|------|--------|------|
| 固定阈值 | 70-80% 上下文利用率 | 简单但可能过早压缩 |
| 滑动窗口 | 保持最后 N 轮 + 摘要 | 可预测的上下文大小 |
| 基于重要性 | 首先压缩低相关部分 | 复杂但保留信号 |
| 任务边界 | 在逻辑任务完成时压缩 | 清晰的摘要但不可预测的时间 |

滑动窗口方法与结构化摘要相结合为大多数编码代理用例提供了可预测性和质量的最佳平衡。

### 基于探测的评估

传统的指标如 ROUGE 或嵌入相似度无法捕捉功能压缩质量。摘要可能在词汇重叠方面得分很高，但可能遗漏代理需要的那个文件路径。

基于探测的评估通过压缩后直接提问来直接衡量功能质量：

| 探测类型 | 它测试什么 | 示例问题 |
|--------|--------|--------|
| 检索 | 事实保留 | "原始错误消息是什么？" |
| 轨迹 | 文件跟踪 | "我们修改了哪些文件？" |
| 继续 | 任务规划 | "下一步该做什么？" |
| 决策 | 推理链 | "我们对 Redis 问题做了什么决定？" |

如果压缩保留了正确的信息，代理会正确回答。如果没有，它会猜测或幻觉。

### 评估维度

六个维度捕捉编码代理的压缩质量：

1. **准确性**：技术细节是否正确？文件路径、函数名、错误代码。
2. **上下文意识**：响应是否反映当前对话状态？
3. **轨迹**：代理是否知道哪些文件被读取或修改？
4. **完整性**：响应是否回答了问题的所有部分？
5. **连续性**：能否在不重新获取信息的情况下继续工作？
6. **指令遵循**：响应是否尊重声明的约束？

准确性在压缩方法之间表现出最大的差异（0.6 分差距）。轨迹普遍较弱（2.2-2.5 范围）。

## 实用指南

### 三阶段压缩工作流程

对于大型代码库或超出上下文窗口的代理系统，通过三个阶段应用压缩：

1. **研究阶段**：从架构图、文档和关键接口生成研究文档。将探索压缩为组件和依赖关系的结构化分析。输出：单个研究文档。

2. **规划阶段**：将研究转换为实施规范，包括函数签名、类型定义和数据流。5M 令牌的代码库压缩到大约 2,000 字的规范。

3. **实施阶段**：根据规范执行。上下文保持专注于规范而不是原始代码库探索。

### 使用示例轨迹作为种子

当提供手动迁移示例或参考 PR 时，将其用作理解目标模式的模板。示例揭示了静态分析无法揭示的约束：哪些不变量必须保持、哪些服务在更改时中断，以及干净的迁移是什么样子。

这在与代理无法区分基本复杂性（业务需求）和偶然复杂性（遗留解决方案）时特别重要。示例轨迹编码了这种区别。

### 实现锚定迭代摘要

1. 定义与您的代理需求匹配的明确摘要部分
2. 在第一次压缩触发时，将截断的历史记录摘要到部分
3. 在后续压缩中，仅摘要新的截断内容
4. 将新摘要合并到现有部分，而不是重新生成
5. 跟踪来自哪个压缩周期的信息以用于调试

### 何时使用每种方法

**使用锚定迭代摘要当：**
- 会话是长运行的（100+ 消息）
- 文件跟踪很重要（编码、调试）
- 您需要验证保存了什么

**使用不透明压缩当：**
- 需要最大令牌节省
- 会话相对较短
- 重新获取成本较低

**使用再生摘要当：**
- 摘要可解释性至关重要
- 会话有明确的阶段边界
- 每次压缩都接受完整上下文审查

### 压缩率考虑

| 方法 | 压缩率 | 质量分数 | 交易 |
|------|--------|--------|------|
| 锚定迭代 | 98.6% | 3.70 | 最佳质量，略微压缩较少 |
| 再生 | 98.7% | 3.44 | 良好质量，适度压缩 |
| 不透明 | 99.3% | 3.35 | 最佳压缩，质量损失 |

结构化摘要保留的 0.7% 额外令牌购买了 0.35 质量分。对于任何重新获取成本重要的任务，这种交易有利于结构化方法。

## 示例

**示例 1：调试会话压缩**

原始上下文（89,000 令牌，178 条消息）：
- /api/auth/login 端点 401 错误
- 跟踪通过 auth 控制器、中间件、会话存储
- 发现过时的 Redis 连接
- 修复连接池，添加重试逻辑
- 14 个测试通过，2 个失败

压缩后的结构化摘要：

```markdown
## 会话意图
调试 /api/auth/login 端点上的 401 未授权错误，尽管凭证有效。

## 根本原因
会话存储中的过时 Redis 连接。JWT 生成正确，但会话无法持久化。

## 修改的文件
- auth.controller.ts：未更改（仅读取）
- middleware/cors.ts：未更改（检查）
- config/redis.ts：修复连接池配置
- services/session.service.ts：添加重试逻辑以处理瞬态故障
- tests/auth.test.ts：更新模拟设置

## 测试状态
14 通过，2 失败（模拟设置问题）

## 下一步行动
1. 修复剩余的测试失败（模拟会话服务）
2. 运行完整测试套件
3. 部署到暂存
```

**示例 2：探测响应质量**

压缩后，询问"原始错误是什么？"

良好响应（结构化摘要）：
> "原始错误是从 /api/auth/login 端点返回的 401 未授权响应。用户在有效凭证的情况下收到此错误。根本原因是会话存储中的过时 Redis 连接。"

差响应（激进压缩）：
> "我们正在调试身份验证问题。登录失败。我们修复了一些配置问题。"

结构化响应保留了端点、错误代码和根本原因。激进响应丢失了所有技术细节。

## 指南

1. 优化每个任务的令牌数，而不是每个请求的令牌数
2. 使用具有明确部分的结构化摘要进行文件跟踪
3. 在 70-80% 上下文利用率时触发压缩
4. 实现增量合并而不是完整再生
5. 使用基于探测的评估测试压缩质量
6. 如果文件跟踪至关重要，则单独跟踪轨迹
7. 接受略低的压缩率以保留更好的质量
8. 监控重新获取频率作为压缩质量信号
