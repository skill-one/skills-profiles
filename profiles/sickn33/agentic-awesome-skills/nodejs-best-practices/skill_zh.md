# Node.js 最佳实践

> 2025年Node.js开发的原则与决策指南。
> **学会思考，而非死记硬背代码模式。**

## 何时使用
在做出Node.js架构决策、选择框架、设计异步模式或应用安全与部署最佳实践时，使用这项技能。

---

## ⚠️ 如何使用这项技能

这项技能教授的是**决策原则**，而非固定的可复制代码。

- 不明确时向用户询问偏好
- 基于上下文选择框架/模式
- 不要每次都默认使用相同解决方案

## 1. 框架选择 (2025)

### 决策树

```
你在构建什么？
│
├── 边缘/无服务器 (Cloudflare, Vercel)
│   └── Hono (零依赖、超快冷启动)
│
├── 高性能API
│   └── Fastify (比Express快2-3倍)
│
├── 企业/团队熟悉度
│   └── NestJS (结构化、依赖注入、装饰器)
│
├── 遗留/稳定/最大生态系统
│   └── Express (成熟、最多中间件)
│
└── 全栈带前端
    └── Next.js API Routes 或 tRPC
```

### 对比原则

| 因素 | Hono | Fastify | Express |
|------|------|---------|---------|
| **最适合** | 边缘、无服务器 | 性能 | 遗留、学习 |
| **冷启动** | 最快 | 快 | 中等 |
| **生态系统** | 正在增长 | 良好 | 最大的 |
| **TypeScript** | 原生支持 | 优秀 | 良好 |
| **学习曲线** | 低 | 中等 | 低 |

### 选择时需要询问的问题：
1. 部署目标是什么？
2. 冷启动时间是否关键？
3. 团队是否有现有经验？
4. 是否需要维护遗留代码？

## 2. 运行时考虑 (2025)

### 原生TypeScript

```
Node.js 22+: --experimental-strip-types
├── 直接运行.ts文件
├── 简单项目无需构建步骤
└── 适用于：脚本、简单API
```

### 模块系统决策

```
ESM (import/export)
├── 现代标准
├── 更好的树摇
├── 异步模块加载
└── 用于：新项目

CommonJS (require)
├── 遗留兼容性
├── 支持更多npm包
└── 用于：现有代码库、某些边缘情况
```

### 运行时选择

| 运行时 | 最适合 |
|-------|--------|
| **Node.js** | 通用、最大的生态系统 |
| **Bun** | 性能、内置打包器 |
| **Deno** | 安全优先、内置TypeScript |

## 3. 架构原则

### 分层结构概念

```
请求流程：
│
├── 控制器/路由层
│   ├── 处理HTTP特定内容
│   ├── 边界输入验证
│   └── 调用服务层
│
├── 服务层
│   ├── 业务逻辑
│   ├── 框架无关
│   └── 调用存储层
│
└── 存储层
    ├── 仅数据访问
    ├── 数据库查询
    └── ORM交互
```

### 为什么这很重要：
- **可测试性**：独立模拟各层
- **灵活性**：更换数据库无需触及业务逻辑
- **清晰性**：每层单一职责

### 何时简化：
- 小型脚本 → 单文件即可
- 原型 → 可接受较少结构
- 始终询问："这个会增长吗？"

## 4. 错误处理原则

### 集中式错误处理

```
模式：
├── 创建自定义错误类
├── 任何层抛出
├── 顶层（中间件）捕获
└── 格式化一致响应
```

### 错误响应理念

```
客户端收到：
├── 合适的HTTP状态码
├── 用于程序化处理的错误码
├── 用户友好消息
└── 绝不泄露内部细节（安全！）

日志记录：
├── 完整堆栈跟踪
├── 请求上下文
├── 用户ID（如适用）
└── 时间戳
```

### 状态码选择

| 情况 | 状态 | 何时 |
|------|------|------|
| 错误输入 | 400 | 客户端发送无效数据 |
| 无认证 | 401 | 缺失或无效凭证 |
| 无权限 | 403 | 有效认证但无权限 |
| 未找到 | 404 | 资源不存在 |
| 冲突 | 409 | 重复或状态冲突 |
| 验证 | 422 | 模式有效但业务规则失败 |
| 服务器错误 | 500 | 我们的问题，记录所有内容 |

## 5. 异步模式原则

### 何时使用每种模式

| 模式 | 何时使用 |
|------|----------|
| `async/await` | 顺序异步操作 |
| `Promise.all` | 并行独立操作 |
| `Promise.allSettled` | 并行但某些可能失败 |
| `Promise.race` | 超时或首个响应获胜 |

### 事件循环意识

```
I/O密集型（异步有帮助）：
├── 数据库查询
├── HTTP请求
├── 文件系统
└── 网络操作

CPU密集型（异步无帮助）：
├── 加密操作
├── 图像处理
├── 复杂计算
└── → 使用工作线程或卸载
```

### 避免阻塞事件循环

- 生产代码中绝不用同步方法（fs.readFileSync等）
- 卸载CPU密集型工作
- 使用流处理大数据

## 6. 验证原则

### 在边界验证

```
在哪里验证：
├── API入口点（请求体/参数）
├── 数据库操作前
├── 外部数据（API响应、文件上传）
└── 环境变量（启动时）
```

### 验证库选择

| 库 | 最适合 |
|------|----------|
| **Zod** | TypeScript优先，推断 |
| **Valibot** | 更小的打包体积（可树摇） |
| **ArkType** | 性能关键 |
| **Yup** | 现有React表单使用 |

### 验证理念

- 快速失败：早期验证
- 具体明确：清晰的错误消息
- 不信任：即使是"内部"数据

## 7. 安全原则

### 安全检查清单（非代码）

- [ ] **输入验证**：所有输入都经过验证
- [ ] **参数化查询**：无SQL字符串拼接
- [ ] **密码哈希**：bcrypt或argon2
- [ ] **JWT验证**：始终验证签名和过期时间
- [ ] **速率限制**：防止滥用
- [ ] **安全头部**：Helmet.js或等效
- [ ] **HTTPS**：生产环境全程使用
- [ ] **CORS**：正确配置
- [ ] **密钥**：仅环境变量
- [ ] **依赖项**：定期审计

### 安全思维

```
绝不信任：
├── 查询参数 → 验证
├── 请求体 → 验证
├── 头部 → 验证
├── Cookie → 验证
├── 文件上传 → 扫描
└── 外部API → 验证响应
```

## 8. 测试原则

### 测试策略选择

| 类型 | 目的 | 工具 |
|------|------|-------|
| **单元** | 业务逻辑 | node:test, Vitest |
| **集成** | API端点 | Supertest |
| **E2E** | 全流程 | Playwright |

### 要测试的内容（优先级）

1. **关键路径**：认证、支付、核心业务
2. **边缘情况**：空输入、边界值
3. **错误处理**：出问题时会发生什么？
4. **不值得测试**：框架代码、简单获取器

### 内置测试运行器（Node.js 22+）

```
node --test src/**/*.test.ts
├── 无外部依赖
├── 良好覆盖率报告
└── 支持监视模式
```

## 9. 应避免的反模式

### ❌ 不要：
- 新的边缘项目使用Express（使用Hono）
- 生产代码中使用同步方法
- 在控制器中放置业务逻辑
- 跳过输入验证
- 硬编码密钥
- 无验证信任外部数据
- 用CPU工作阻塞事件循环

### ✅ 要：
- 基于上下文选择框架
- 不明确时向用户询问偏好
- 为增长项目使用分层架构
- 验证所有输入
- 使用环境变量存储密钥
- 优化前先分析性能
