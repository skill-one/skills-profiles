## ❌ 反模式

**不要：**
- 对所有情况都默认使用 REST
- 在 REST 端点中使用动词 (/getUsers)
- 返回不一致的响应格式
- 向客户端暴露内部错误
- 跳过速率限制

**要：**
- 根据上下文选择 API 风格
- 询问客户端需求
- 彻底文档化
- 使用适当的状态码

## 何时使用

在定义新的端点契约、为已知消费者选择 REST/GraphQL/tRPC，或更改分页、错误、认证或兼容性行为时使用。对于现有契约中的错误，除非任务授权更改，否则保留该契约。

## 输入和流程

记录消费者和部署版本、预期有效负载大小、访问规则、兼容性义务和一个具体操作。阅读地图中的相关文件，比较实际选择，然后指定请求/响应示例和拒绝情况。在构建时共享的类型并不能保证独立部署的客户端保持兼容。

## 示例

输入：公开的订单列表在客户端分页时发生变化。选择一个有界的页面大小和稳定的 `(created_at, id)` 订单。定义下一游标格式、授权过滤器以及删除记录或无效游标的行为。测试两个相同的时间戳和页面之间的插入。预期：在承诺的快照语义内不会出现重复的 ID；记录新插入的行是否可以出现。

## 限制

- Python 助手最多使用正则表达式和浅层 JSON/YAML 检查匹配 15 个文件。其输出是一个分诊提示，不是 OpenAPI 验证、授权审计或部署批准。
- GraphQL 查询形状、tRPC 推理和 HTTP 方法名称不会强制执行资源授权或向后兼容性。
- 速率限制不能单独防止所有资源耗尽；大小、并发、时间和提供者成本边界取决于操作。
- 仅对授权的本地/测试目标进行安全检查，这些目标具有隔离的账户和定义的范围。
