# 代码审查清单

## 概述

提供一个系统化的清单，用于进行彻底的代码审查。这项技能有助于审查者确保代码质量、发现错误、识别安全问题，并在整个代码库中保持一致性。

## 何时使用这项技能

- 在审查拉取请求时使用
- 在进行代码审计时使用
- 在为团队建立代码审查标准时使用
- 在培训新开发人员代码审查实践时使用
- 在您希望确保审查中未遗漏任何内容时使用
- 在创建代码审查文档时使用

## 如何工作

### 第一步：理解背景

在审查代码之前，我将帮助您理解：

- 这段代码解决了什么问题？
- 需求是什么？
- 更改了哪些文件以及原因？
- 是否有相关的问题或工单？
- 测试策略是什么？

### 第二步：审查功能

检查代码是否正常工作：

- 它是否解决了声明的問題？
- 是否处理了边界情况？
- 错误处理是否适当？
- 是否有任何逻辑错误？
- 它是否符合需求？

### 第三步：审查代码质量

评估代码的可维护性：

- 代码是否易读且清晰？
- 名称是否描述性强？
- 结构是否正确？
- 函数/方法是否专注？
- 是否存在不必要的复杂性？

### 第四步：审查安全性

检查安全问题：

- 输入是否经过验证？
- 敏感数据是否受保护？
- 是否存在 SQL 注入风险？
- 身份验证/授权是否正确？
- 依赖项是否安全？

### 第五步：审查性能

查找性能问题：

- 是否有不必要的循环？
- 数据库访问是否优化？
- 是否存在内存泄漏？
- 缓存是否使用得当？
- 是否存在 N+1 查询问题？

### 第六步：审查测试

验证测试覆盖率：

- 新代码是否有测试？
- 测试是否覆盖了边界情况？
- 测试是否有意义？
- 所有测试是否通过？
- 测试覆盖率是否足够？

## 示例

### 示例 1：功能审查清单

```markdown
## 功能审查

### 需求
- [ ] 代码解决了声明的问题
- [ ] 所有验收标准都已满足
- [ ] 处理了边界情况
- [ ] 处理了错误情况
- [ ] 用户输入已验证

### 逻辑
- [ ] 没有逻辑错误或错误
- [ ] 条件正确（没有 off-by-one 错误）
- [ ] 循环正确终止
- [ ] 递归有正确的基准情况
- [ ] 状态管理正确

### 错误处理
- [ ] 错误被适当捕获
- [ ] 错误消息清晰且有帮助
- [ ] 错误不会暴露敏感信息
- [ ] 失败的操作被回滚
- [ ] 日志记录适当

### 示例问题：

**❌ 不好 - 缺少验证：**
\`\`\`javascript
function createUser(email, password) {
  // 没有验证！
  return db.users.create({ email, password });
}
\`\`\`

**✅ 好 - 正确验证：**
\`\`\`javascript
function createUser(email, password) {
  if (!email || !isValidEmail(email)) {
    throw new Error('无效的电子邮件地址');
  }
  if (!password || password.length < 8) {
    throw new Error('密码必须至少 8 个字符');
  }
  return db.users.create({ email, password });
}
\`\`\`
```

### 示例 2：安全审查清单

```markdown
## 安全审查

### 输入验证
- [ ] 所有用户输入都经过验证
- [ ] 防止 SQL 注入（使用参数化查询）
- [ ] 防止跨站脚本攻击（输出转义）
- [ ] 有 CSRF 保护
- [ ] 文件上传已验证（类型、大小、内容）

### 身份验证和授权
- [ ] 在需要的地方进行身份验证
- [ ] 存在授权检查
- [ ] 密码被哈希（从不存储明文）
- [ ] 会话管理安全
- [ ] 令牌适当过期

### 数据保护
- [ ] 敏感数据被加密
- [ ] API 密钥没有被硬编码
- [ ] 使用环境变量存储密钥
- [ ] 个人数据遵循隐私法规
- [ ] 数据库凭证安全

### 依赖项
- [ ] 没有已知的易受攻击的依赖项
- [ ] 依赖项是最新版本
- [ ] 移除不必要的依赖项
- [ ] 依赖项版本已固定

### 示例问题：

**❌ 不好 - SQL 注入风险：**
\`\`\`javascript
const query = \`SELECT * FROM users WHERE email = '\${email}'\`;
db.query(query);
\`\`\`

**✅ 好 - 参数化查询：**
\`\`\`javascript
const query = 'SELECT * FROM users WHERE email = $1';
db.query(query, [email]);
\`\`\`

**❌ 不好 - 硬编码密钥：**
\`\`\`javascript
const leakedToken = '[redacted live key]';
\`\`\`

**✅ 好 - 环境变量：**
\`\`\`javascript
const API_KEY = process.env.API_KEY;
if (!API_KEY) {
  throw new Error('需要 API_KEY 环境变量');
}
\`\`\`
```

### 示例 3：代码质量审查清单

```markdown
## 代码质量审查

### 可读性
- [ ] 代码易于理解
- [ ] 变量名称描述性强
- [ ] 函数名称解释其作用
- [ ] 复杂逻辑有注释
- [ ] 用常量替换魔法数字

### 结构
- [ ] 函数小而专注
- [ ] 代码遵循 DRY 原则（不要重复自己）
- [ ] 合理分离关注点
- [ ] 代码风格一致
- [ ] 没有死代码或注释掉的代码

### 可维护性
- [ ] 代码模块化和可重用
- [ ] 依赖项最少
- [ ] 修改是向后兼容的
- [ ] 不兼容更改有文档记录
- [ ] 记录技术债务

### 示例问题：

**❌ 不好 - 名称不清晰：**
\`\`\`javascript
function calc(a, b, c) {
  return a * b + c;
}
\`\`\`

**✅ 好 - 描述性名称：**
\`\`\`javascript
function calculateTotalPrice(quantity, unitPrice, tax) {
  return quantity * unitPrice + tax;
}
\`\`\`

**❌ 不好 - 函数做太多事：**
\`\`\`javascript
function processOrder(order) {
  // 验证订单
  if (!order.items) throw new Error('没有商品');
  
  // 计算总价
  let total = 0;
  for (let item of order.items) {
    total += item.price * item.quantity;
  }
  
  // 应用折扣
  if (order.coupon) {
    total *= 0.9;
  }
  
  // 处理支付
  const payment = stripe.charge(total);
  
  // 发送邮件
  sendEmail(order.email, '订单确认');
  
  // 更新库存
  updateInventory(order.items);
  
  return { orderId: order.id, total };
}
\`\`\`

**✅ 好 - 分离关注点：**
\`\`\`javascript
function processOrder(order) {
  validateOrder(order);
  const total = calculateOrderTotal(order);
  const payment = processPayment(total);
  sendOrderConfirmation(order.email);
  updateInventory(order.items);
  
  return { orderId: order.id, total };
}
\`\`\`
```

## 最佳实践

### ✅ 做这些

- **审查小更改** - 更小的 PR 更容易彻底审查
- **先检查测试** - 验证测试是否通过且覆盖新代码
- **运行代码** - 在可能的情况下在本地测试
- **提问** - 不要假设，请求澄清
- **提供建设性意见** - 建议改进，不要只是批评
- **关注重要问题** - 不要纠结于小的风格问题
- **使用自动化工具** - 代码检查器、格式化工具、安全扫描器
- **审查文档** - 检查文档是否更新
- **考虑性能** - 考虑扩展性和效率
- **检查回归** - 确保现有功能仍然正常

### ❌ 不要做这些

- **不要不阅读就批准** - 实际审查代码
- **不要含糊其辞** - 提供具体的反馈和示例
- **不要忽视安全** - 安全问题至关重要
- **不要跳过测试** - 未测试的代码会导致问题
- **不要粗鲁** - 保持尊重和专业
- **不要 rubber stamp** - 每次审查都应该增加价值
- **不要疲劳审查** - 你会错过重要问题
- **不要忘记背景** - 理解大局

## 常见陷阱

### 问题：缺少边界情况
**症状**：代码在快乐路径上工作，但在边界情况下失败
**解决方案**：问“如果...？”问题
- 输入是否为 null？
- 数组是否为空？
- 用户是否未通过身份验证？
- 网络请求是否失败？

### 问题：安全漏洞
**症状**：代码暴露安全风险
**解决方案**：使用安全清单
- 运行安全扫描器（npm audit, Snyk）
- 检查 OWASP Top 10
- 验证所有输入
- 使用参数化查询
- 不要信任用户输入

### 问题：测试覆盖率差
**症状**：新代码没有测试或不充分的测试
**解决方案**：要求所有新代码都有测试
- 函数的单元测试
- 功能的集成测试
- 边界情况测试
- 错误情况测试

### 问题：代码不清晰
**症状**：审查者无法理解代码的作用
**解决方案**：请求改进
- 更好的变量名称
- 解释性注释
- 更小的函数
- 清晰的结构
