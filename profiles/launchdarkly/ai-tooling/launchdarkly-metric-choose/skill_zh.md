# LaunchDarkly 指标选择

您正在使用一个帮助用户在设置实验、受保护发布或发布策略之前选择正确指标的功能。您的任务是理解功能上下文，展示将自动从现有项目策略中附加的内容，清点可用且健康的指标，并生成清晰的类型化建议。

此功能是建议性的。它不会创建指标、将它们附加到实验或配置发布。对于这些任务，请参阅本文件末尾的相关功能。

## 前置条件

此功能需要远程托管的 LaunchDarkly MCP 服务器在您的环境中进行配置。

**必需的 MCP 工具：**
- `list-metrics` — 列出可用指标及其类型和事件键
- `list-metric-events` — 检查哪些事件键有近期活动

**可选的 MCP 工具（增强工作流）：**
- `list-release-policies` — 获取项目级策略，这些策略配置哪些指标自动附加到受保护发布。用于受保护发布和发布策略路径。

## 工作流

### 第 1 步：确定上下文

提前问两个问题：

1. **这是用于什么目的？**
   - **(a) 实验** — 使用标志变体测试假设
   - **(b) 受保护发布** — 带自动回归检测逐步发布更改
   - **(c) 发布策略** — 创建或编辑一个项目级策略，该策略配置所有符合特定条件的受保护发布的默认指标

2. **更改是什么？**
   - 标志键（如果适用）
   - 平语描述："发布新的结账流程" / "测试新的推荐算法"

### 第 2 步：获取现有配置（仅受保护发布和发布策略）

**对于实验 — 跳过此步骤。** 没有预先存在的配置需要展示。

**对于受保护发布和发布策略工作**，首先调用 `list-release-policies`：

```
list-release-policies(projectKey)
```

在做出任何建议之前展示结果：

```
您的项目有 2 个发布策略：

策略："生产安全护栏"（适用于：environment=production）
  自动附加到受保护发布：
    ✓ api-error-rate  (count, LowerThanBaseline)
    ✓ p95-latency     (value, LowerThanBaseline)
    ✓ [指标组] 核心平台健康（3 个指标）

策略："默认"（适用于：所有环境）
  未配置指标。
```

这告诉用户在做出任何额外选择之前已经覆盖了哪些内容。对于受保护发布，这些指标将自动出现 — 建议是添加更多内容，而不是从头开始重建。

如果不存在策略或没有配置指标，请注意所有指标必须手动选择。

### 第 3 步：按事件健康清点可用指标

调用 `list-metrics` 查看项目中的所有指标，然后与 `list-metric-events` 进行交叉参考。

分为两组组织：

| 组别 | 标准 | 备注 |
|------|------|------|
| **健康** | 事件键出现在 `list-metric-events` 中 | 安全推荐 |
| **有风险** | 事件键未出现在 `list-metric-events` 中 | 警告：可能不会产生数据 |

在推荐之前展示此清点 — 它可能会揭示用户有意的指标没有事件流。

### 第 4 步：建议

根据上下文，推理有显著差异。

---

#### (a) 实验

**从假设开始，而不是指标列表。**

要求用户在查看可用指标之前完成这个句子：

> "如果此更改成功，[指标] 将 [增加 / 减少]。"

主要指标必须直接衡量该假设 — 不是代理，不是相关性。如果用户无法完成句子，请先帮助他们达到这个目标。

**建议一个主要指标。** 它必须：
- 直接衡量假设
- 有活跃的事件流
- 有明确的成功方向（`HigherThanBaseline` 或 `LowerThanBaseline`）

**建议类型化的次要指标。** 至少建议每种类型中的一个适用：

| 类型 | 目的 | 示例 |
|------|------|------|
| **护栏** | 更改是否破坏了任何内容？ | 错误率、崩溃率、延迟 p95 |
| **反指标** | A 的改进是否以 B 为代价？ | 如果主要指标是转化率，添加支持工单或会话长度 |
| **支持信号** | 相关行为是否确认了假设？ | 如果主要指标是注册，添加第 2 步引导完成 |

通常每种类型一个就足够了。更多次要指标会增加噪音和解释负担。

---

#### (b) 受保护发布

受保护发布是安全机制，而不是实验。您添加的每个指标都是一个潜在的自动回滚触发器 — 如果它在发布完成之前回归到其阈值之外，LaunchDarkly 可以停止并回滚发布。

**从自动附加的内容开始。** 在第 2 步中展示发布策略结果后，问："自动附加的指标是否足够，还是您希望为此特定发布添加更多？"

**建议附加指标时：**
- 偏好可靠性 — 工程指标（错误率、延迟、崩溃率）具有稳定、可预测的基线
- 避免在回归分析下嘈杂或难以解释的探索性产品指标
- **越少越好。** 两到三个高信号指标是合适的规模。超过五个会增加误报回滚风险。
- **只建议有活跃事件流的指标。** 在受保护发布中有风险的指标要么不产生信号，要么更糟，由于数据质量问题而不是真实回归而触发误报回滚。

任何受保护发布的建议起点（如果尚未由策略覆盖）：
1. 错误率 — 我们是否在新变体中看到更多错误？
2. 延迟 / 响应时间 — 新变体是否更慢？
3. 一个与受更改影响的核心用户动作相关的特定领域指标

---

#### (c) 发布策略

发布策略适用于项目中符合其条件的每个发布。这是最高标准。

**从当前状态开始。** 在第 2 步中展示现有策略后，问："您要编辑哪个策略，还是要创建一个新的策略？它将适用于哪些环境或标志条件？"

**为策略建议指标时：**
- **最多 2-3 个指标。** 超过这些会将策略变成对每个发布的负担，包括那些指标不适用很好的发布。
- **只建议具有长期稳定事件历史的指标。** 如果事件已经可靠地流动了数月，它是安全的全局默认值。偶尔的间隙在规模上会引发问题。
- **反对添加。** 如果用户提出超过 3 个，请问他们要移除哪些。选择的过程就是要点。
- **解释范围条件。** 限制为 `environment=production` 的策略仅适用于生产发布。帮助用户思考他们是否希望在 staging（基线可能不同）中具有相同的指标或创建单独的策略。

典型的强策略候选者：错误率、核心转化或参与指标、延迟。

### 第 5 步：提供建议

输出清晰的命名列表。明确说明每个指标的目的和已覆盖的内容：

```
新结账流程受保护发布（环境：生产）的推荐指标

自动附加（来自 "生产安全护栏" 策略）：
  ✓ api-error-rate    (count, LowerThanBaseline)
  ✓ p95-latency       (value, LowerThanBaseline)

附加 — 建议为此发布：
  ✓ checkout-conversion  (occurrence, HigherThanBaseline)
    → 确认发布没有降低目标功能的核心转化

⚠ page-load-time — 没有近期事件。在包含它之前instrument该事件，
  或将其从列表中移除以避免触发误报回滚。
```

然后以下一步行动结束：
- 如果用户需要的指标不存在 → 使用 **metric-create** 功能
- 如果事件没有流动 → 使用 **metric-instrument** 功能
- 确认列表后 → 配置受保护发布或实验（通过 LaunchDarkly UI 或 API）

## 重要上下文

- **实验中更改指标需要重启。** LaunchDarkly 在实验开始时快照指标配置。发布后添加、删除或更改指标需要停止实验并重新启动它 — 变更之前的歷史数据不可比较。如果用户提到他们正在实验中途，请立即提出这一点。
- **没有事件的 主要指标比没有主要指标更糟。** 实验不会产生统计输出。事件健康是主要指标的一个硬性要求。
- **CUPED 和百分位数分析不兼容。** 如果实验使用 CUPED 方差减少，基于百分位数的指标（例如 p95 延迟）会静默地降级到基于均值的分析。如果用户在启用 CUPED 的实验中选择百分位数指标，请指出这一点。
- **上下文类型不匹配会导致数据丢失。** 如果指标事件使用 `device` 上下文跟踪，但实验在 `user` 上随机化，事件不会被正确归因。确认 `track()` 调用中的上下文类型与实验的随机化单元匹配。
- **发布策略指标必须共享相同的上下文类型。** 受保护发布发布策略中的所有指标必须使用相同的随机化单元。如果用户建议具有不匹配上下文类型的指标，请在他们尝试配置策略之前指出。
