# LaunchDarkly 标志清理

你正在使用一个技能，它将指导你安全地从代码库中移除一个功能标志，同时保留生产环境行为。你的任务是探索代码库以了解标志的使用方式，查询 LaunchDarkly 以确定正确的转发值，干净地移除标志代码，并验证结果。

如果你还没有确定要清理哪个标志，请先使用 `[标志发现技能](../launchdarkly-flag-discovery/SKILL.md)` 来审计环境并找到候选标志。

## 前置条件

此技能需要将远程托管的 LaunchDarkly MCP 服务器配置到你的环境中。

**必需的 MCP 工具：**
- `check-removal-readiness`：详细的 safety 检查（并行协调标志配置、跨环境状态、依赖项、代码引用和过期目标）
- `get-flag`：获取特定环境的标志配置

**可选的 MCP 工具：**
- `archive-flag`：在代码移除后，在 LaunchDarkly 中归档标志
- `delete-flag`：永久删除标志（不可逆，优先归档）

## 核心原则

1. **安全第一**：始终保留当前生产环境行为。
2. **LaunchDarkly 作为事实来源**：不要猜测转发值。查询实际配置。
3. **遵循规范**：尊重现有代码风格和结构。
4. **最小化变更**：仅移除与标志相关的代码。不要进行无关的重构。

## 工作流程

### 第 1 步：探索代码库

在触摸 LaunchDarkly 或移除代码之前，了解此标志在代码库中的使用方式。

1. **查找所有标志键的引用**。在整个代码库中搜索标志键字符串（例如，`new-checkout-flow`）。检查：
   - 直接的 SDK 评估调用（`variation()`、`boolVariation()`、`useFlags()` 等）
   - 引用键的常量/枚举
   - 抽象 SDK 的包装器/服务模式
   - 配置文件、测试和文档
   - 参考 [SDK 模式](references/sdk-patterns.md) 获取所有语言/框架的模式列表

2. **理解分支**。对于每个引用，识别：
   - 标志为 `true`（或变体 A）时运行的代码？
   - 标志为 `false`（或变体 B）时运行的代码？
   - 是否有副作用、提前返回或嵌套条件？

3. **注意范围**。此标志影响多少文件、组件或模块？在一个 `if` 块中使用的标志比在多层中传递的标志更简单。

### 第 2 步：运行移除准备检查

使用 `check-removal-readiness` 获取详细的 safety 评估。此单一工具调用并行执行多个检查：
- 标志配置和目标状态
- 跨环境状态
- 依赖标志（先决条件）
- 过期目标
- 代码引用统计

该工具返回准备状态：

**`safe`**：没有 block 或警告。继续移除。

**`caution`**：没有硬 block 但存在警告（例如，其他仓库中的代码引用、计划过期的目标、标志标记为永久）。显示警告并让用户决定。

**`blocked`**：硬 block 阻止安全移除（例如，依赖标志、正在接收请求、目标处于活动规则下）。显示 block：用户必须先解决它们。

### 第 3 步：确定转发值

使用 `get-flag` 获取每个关键环境的标志配置。**转发值**是替换代码中标志的变体。

| 情景 | 转发值 |
|------|--------|
| 所有关键环境 ON，相同 fallthrough，无规则/目标 | 使用 `fallthrough.variation` |
| 所有关键环境 OFF，相同 offVariation | 使用 `offVariation` |
| 关键环境在 ON/OFF 状态上不同 | **不安全**：停止并通知用户 |
| 关键环境提供不同的变体 | **不安全**：停止并通知用户 |

### 第 4 步：展示清理计划

在修改任何代码之前，向用户展示摘要并等待确认：

1. **转发值**——哪个变体将被硬编码以及原因（基于标志的当前状态）。
2. **所有代码引用**——来自第 1 步的文件路径和行号。
3. **计划变更**——对于每个引用，描述将移除什么以及将保留什么。
4. **准备状态**——来自 `check-removal-readiness` 的结果（safe、caution 或 blocked）以及任何警告。
5. **LaunchDarkly 操作**——确认代码变更完成后将归档标志。

**在用户明确确认之前，不要进行代码变更。**

### 第 5 步：从代码中移除标志

现在使用你在第 1 步中学到的知识执行移除。

1. **用转发值替换标志评估**。
   - 保留匹配转发值的代码分支
   - 完全移除死分支
   - 如果标志值分配给变量，用字面值替换变量或内联它

2. **清理死代码**。
   - 移除仅用于标志的导入、常量和类型定义
   - 移除仅用于死分支的函数、组件或文件
   - 检查孤儿导出、钩子、辅助函数、样式和测试文件
   - 如果仓库使用未使用导出工具（Knip、ts-prune、lint 规则），运行它并移除任何与标志相关的孤儿

3. **不要过度清理**。
   - 仅移除与标志直接相关的代码
   - 不要重构、优化或“改进”周围代码
   - 不要更改未触及代码的格式或风格

**示例转换（布尔标志，转发值 = `true`）：**

```typescript
// Before
const showNewCheckout = await ldClient.variation('new-checkout-flow', user, false);
if (showNewCheckout) {
  return renderNewCheckout();
} else {
  return renderOldCheckout();
}

// After
return renderNewCheckout();
```

### 第 6 步：创建 Pull Request

使用 [references/pr-template.md](references/pr-template.md) 中的模板创建结构化的 PR 描述。PR 应该清晰地传达：
- 移除了什么标志以及为什么
- 转发值是什么以及为什么它是正确的
- 准备状态评估结果（来自 `check-removal-readiness`）
- 移除了什么代码以及保留了什么行为
- 其他仓库是否仍然引用此标志

### 第 7 步：验证

在认为工作完成之前：

1. **代码编译和 lint**。运行项目的构建和 lint 步骤。
2. **测试通过**。如果标志在测试中使用，测试应该更新以反映硬编码的行为。
3. **没有剩余引用**。再次搜索代码库中的标志键，确保没有遗漏。
4. **PR 完成**。描述涵盖了准备状态评估、转发值理由以及任何跨仓库协调需要。

## 边缘情况

| 情况 | 操作 |
|------|------|
| 在 LaunchDarkly 中找不到标志 | 通知用户，检查键中的拼写错误 |
| 标志已经归档 | 询问是否仍需代码清理（标志从 LD 中移除，但代码可能仍然引用它） |
| 代码库中有多个 SDK 模式 | 搜索所有模式：`variation()`、`boolVariation()`、`variationDetail()`、`allFlags()`、`useFlags()`，以及任何包装器 |
| 动态标志键（`flag-${id}`） | 警告自动化移除可能不完整：需要手动审查 |
| 代码与 LD 中的默认值不同 | 在 PR 描述中标记为不一致 |
| 移除后仍有孤儿导出/文件 | 运行未使用导出检查并移除死文件 |

## 不要做的事情

- 不要修改与标志清理无关的代码。
- 不要重构或优化超出标志移除的范围。
- 不要移除仍在积极发布的标志。
- 不要猜测转发值：始终查询 LaunchDarkly。

## 清理后

PR 合并并部署后：
1. **使用 `archive-flag` 在 LaunchDarkly 中归档标志**。归档是可逆的；删除是不可逆的。始终先归档。
2. **如果 `check-removal-readiness` 报告了其他仓库中的代码引用，通知其他团队**。
3. **如果标志有挂起的 targeting 变更**，可以忽略：标志正在被移除。
