# 应用代码更改（SDK 安装）

执行集成计划。安装 SDK 并添加初始化每个跟踪表面的最小代码。

此技能嵌套在 [LaunchDarkly SDK 安装（引导）](../SKILL.md) 下；父级 **步骤 3** 是 **应用**。**之前：** [生成集成计划](../plan/SKILL.md)。**下一步：** [启动应用程序](../run/SKILL.md)。

**双 SDK：** 如果批准的计划是 **双 SDK** ([计划：双 SDK 集成](../plan/SKILL.md#dual-sdk-integrations))，您必须为 **两个** 跟踪完成步骤 1-3 -- 清单中的 **两个** 包，运行 **两个** 安装命令（或等效），需要 **两个** 凭据行，每个配方在 **不同** 的入口点中 **两个** 初始化。**不要** 在没有执行其真实安装和初始化的情况下声称第二个 SDK 已设置。如果计划仅列出了一个跟踪，但用户要求两个，**停止** 并返回到 [计划](../plan/SKILL.md) -- 不要凭记忆编造后半部分。

**凭据时间：** 这是第一个要求用户输入 **SDK 密钥 / 客户端 ID / 移动密钥**（或同意获取/写入它们）的嵌套步骤。账户状态不会提前询问 -- 它是通过 MCP OAuth 推断的，当 MCP 已配置或在 D7（选项 4）处显示时，如果用户还没有账户（[父级先决条件](../../SKILL.md#prerequisites)）。

## 步骤 1：安装 SDK 依赖项

使用您在 [SDK 配方](../../references/sdk/recipes.md) 中已匹配的 SDK 行中的 **确切** 包或模块名称和安装命令，并使用项目的包管理器进行安装。不要从其他地方复制一个通用的安装行 -- 每个配方都命名了正确的工件。

**双 SDK：** 运行 **跟踪 A 的安装命令**，然后运行 **跟踪 B 的安装命令**（来自计划）。确认 **两个** 包名都出现在 `package.json` / `requirements.txt` / 锁文件（或每种语言的正确包清单）中。当计划说明双时，跳过第二个安装是 **不是** 可选的。

安装后，验证依赖项出现在锁文件或依赖项清单中 (**所有** 计划中的 LaunchDarkly 包)。

### 更改其他依赖项之前的权限

**无需请求额外权限（超出正常仓库编辑同意范围）：** 仅安装此集成配方中命名的 LaunchDarkly SDK 包（例如一个服务器 SDK，**或** 双 SDK 计划中列出的 **确切** 服务器 + 客户端对 -- **两个** 包都计入 LD 安装范围）。使用每个配方指定的 **最小** 安装（确切的包名）。

**需要您在运行任何命令或编辑清单之前获得明确的用户批准：** 超出该范围的任何更改，包括但不限于：

- 升级、降级、固定或添加 **非 LaunchDarkly** 包（同伴依赖项“修复”、“npm install X@latest”、“yarn upgrade”、“pnpm update”、提升 React/Node 类型、传递锁文件变化等）
- 运行 **`npm audit fix`**、**批量更新** 或 **替换** 项目的包管理器解析策略以使 SDK 满足
- 更改 **引擎** / **包管理器** 字段、**解析** / **覆盖** 或 **工作区** 条目，原因不是添加 LD 工件行

如果包管理器报告同伴冲突或安装失败：

**D8 -- 阻塞：** 现在调用您的结构化问题工具。
- 问题："安装报告 [具体错误]。为了修复此问题，我需要 [对非 LD 包的具体更改]。我应该继续执行这些附加更改吗？"
- 选项：
  - "是，执行这些更改"
  - "否，仅保留 LaunchDarkly 包 -- 我将自行解决冲突"
  - "先显示确切命令"
- 停止。不要将问题作为文本写入。不要在无声地升级旧仓库“以匹配最新 SDK 的依赖项”。在用户选择选项之前不要继续。

如果用户 **拒绝** 更广泛的更改：如果可能，保留仅 LD 包添加，记录冲突，并继续使用占位符或手动步骤。

## 步骤 2：将 SDK 密钥添加到环境配置

**永远不要在应用程序源文件中硬编码 SDK 密钥、客户端 ID 或移动密钥**（仅通过环境变量引用它们）。

### 密钥之前的权限

**D7 -- 阻塞（强制 -- 不要跳过）：** 现在调用您的结构化问题工具。此决策点存在是为了安全合规 -- 用户必须明确选择如何处理密钥。跳过此步骤并未经同意写入密钥是一个关键错误。
- 问题："SDK 需要您的环境的 SDK 密钥（或客户端 ID / 移动密钥）。您希望如何设置密钥？"
- 选项：
  - "我会告诉您放在哪里"
  - "我会自行设置密钥 -- 只告诉我要使用什么变量名"
  - "为我写入一个 `.env` 文件"
  - "我还没有账户 -- 帮我注册" -> 指向已解析的注册 URL（见 [来源归因](../../SKILL.md#source-attribution)），写入占位符并继续（密钥延迟到账户准备好时）
- 停止。不要将问题作为文本写入。不要在用户选择选项之前从 LaunchDarkly 获取密钥或将真实值写入仓库。不要从上下文或先前对话中推断答案 -- 始终提供此选择。

**如果用户选择选项 1（“告诉我放在哪里”）：**
1. 询问他们希望将密钥写入的位置（文件路径、密钥管理器等）
2. 询问他们希望如何提供密钥：粘贴它，或让代理通过 MCP/API 获取
3. 仅将密钥写入用户指定的位置
4. 不要创建 `.env` 或修改任何其他文件

**如果用户选择选项 2（“我会自行设置”）：**
1. 告诉他们需要设置的变量名（见下表）
2. 链接到正确的仪表板页面。当项目密钥和环境密钥都已知时：**`https://app.launchdarkly.com/projects/{projectKey}/settings/environments/{envKey}/keys`**。当仅知道项目密钥时：**`https://app.launchdarkly.com/projects/{projectKey}/settings/environments`** 并告诉他们选择环境。当两者都不知道时：**`https://app.launchdarkly.com/projects`** 并告诉他们导航到 **设置 > 环境** 以找到密钥。
3. 等待用户确认密钥已就位，然后再进行步骤 3
4. 不要获取、写入或处理密钥值

**如果用户选择选项 3（“为我写入一个 `.env` 文件”）：**
1. 询问他们希望如何提供密钥：粘贴它，或让代理通过 MCP/API 获取
2. 遵循下文中的 [写入 `.env`（当用户同意时）](#write-to-env-when-the-user-consents) 部分
3. 在写入任何真实值之前，确保 `.env` 在 `.gitignore` 中

**如果用户选择选项 4（“我还没有账户”）：**
1. 指向已解析的注册 URL（见 [来源归因](../../SKILL.md#source-attribution)）
2. 解释 SDK 密钥设置需要账户 -- 他们可以在注册后完成设置
3. 在写入之前确保 `.env` 在 `.gitignore` 中（与选项 3 / [写入 `.env`](#write-to-env-when-the-user-consents) 的检查相同）
4. 写入占位符变量名到 `.env`（没有真实值），以便代码可以编译
5. 继续步骤 3（初始化代码）使用占位符环境变量引用。应用程序在设置真实密钥之前无法连接到 LaunchDarkly，这是预期的。
6. 在引导日志中记录密钥设置正在等待账户创建

### 通过 MCP 获取密钥

当用户要求代理获取密钥（通过上述选项 1 或 3）时，使用 **`get-environments`** MCP 工具（如果已配置）。使用项目密钥调用它 — 响应包括每个环境的 **SDK 密钥**、**客户端 ID** 和 **移动密钥**。当 `get-environments` 已经返回它们时，**不要** 进行单独的 API 请求以获取单个密钥。

```
get-environments({ request: { projectKey: "PROJECT_KEY" } })
```

**安全：** 将包含密钥的 MCP 响应视为敏感信息。仅将密钥写入用户选择的位置，不要在聊天响应中回显完整密钥值。代理会话历史记录或日志中的密钥可能会在会话结束后持续存在。

从响应中匹配的环境中选择正确的密钥类型（见下表）。如果 MCP 未配置，请指导用户在 LaunchDarkly 仪表板中检索他们的密钥：`https://app.launchdarkly.com/projects/{PROJECT_KEY}/settings/environments/{ENV_KEY}/keys`。

### 变量名和值来源

| SDK 类型 | 变量名（典型） | LaunchDarkly 中的来源 |
|----------|----------------|-------------------------|
| 服务器端 | `LAUNCHDARKLY_SDK_KEY` | `get-environments` 响应 → 环境 → SDK 密钥 |
| 客户端端 | 逻辑 / 打包器前缀名称（见下文） | `get-environments` 响应 → 环境 → 客户端 ID |
| 移动端 | `LAUNCHDARKLY_MOBILE_KEY` | `get-environments` 响应 → 环境 → 移动密钥 |

**客户端（浏览器）项目：** LaunchDarkly 值仍然是客户端 ID。在 `.env` 中，使用打包器向客户端代码暴露的名称：

| 堆栈 | `.env` 键 | 代码中读取 |
|-------|------------|--------------|
| Create React App | `REACT_APP_LAUNCHDARKLY_CLIENT_SIDE_ID` | `process.env.REACT_APP_LAUNCHDARKLY_CLIENT_SIDE_ID` |
| Vite | `VITE_LAUNCHDARKLY_CLIENT_SIDE_ID` | `import.meta.env.VITE_LAUNCHDARKLY_CLIENT_SIDE_ID` |
| Next.js | `NEXT_PUBLIC_LAUNCHDARKLY_CLIENT_SIDE_ID` | `process.env.NEXT_PUBLIC_LAUNCHDARKLY_CLIENT_SIDE_ID` |

其他堆栈可能使用不同的前缀或纯 `LAUNCHDARKLY_CLIENT_SIDE_ID` -- 匹配项目已用于公共环境变量的方式。

### 写入 `.env`（当用户同意时）

使用 **集成根** 作为文件路径（仓库根或单体仓库中的目标包 -- 见 [检测仓库堆栈](../detect/SKILL.md)）。

1. **创建或更新 `.env`：** 如果 `.env` 不存在，则创建它。如果它存在，则 **追加或更新** 仅 LaunchDarkly 行 -- 不要删除不相关的变量。
2. **添加集成需要的项：**
   - 仅服务器：`LAUNCHDARKLY_SDK_KEY=...`
   - 客户端/浏览器：在正确的打包器前缀键下添加 **客户端 ID**（例如 `VITE_LAUNCHDARKLY_CLIENT_SIDE_ID=...`）。
   - **全栈或混合（例如 Next.js，SSR + 客户端）：** 当使用两个 SDK 时，添加 **服务器 SDK 密钥** 和 **客户端 ID** 行。
   - 移动端：`LAUNCHDARKLY_MOBILE_KEY=...` 当适用时。
3. **`.gitignore`：** 确保 `.env` 列在创建 `.env` 的同一根目录中的 `.gitignore` 中（或在单体仓库中最近的相关的忽略文件中）。如果条目缺失，请添加它 -- 仅在用户同意仓库更改（与写入 `.env` 相同的权限范围）之后。不要提交包含真实密钥的文件。
4. **`.env.example` / `.env.sample`：** 如果项目使用，添加 **占位符** 条目，不要添加真实密钥，以便队友知道要设置哪些变量。

如果项目不使用 dotenv 并依赖于配置模块或托管密钥，请遵循现有模式而不是 -- 上述 D7 同意仍然适用，在将真实值写入任何文件之前。
