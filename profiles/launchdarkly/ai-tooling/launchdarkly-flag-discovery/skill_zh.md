# LaunchDarkly 功能标志发现

您正在使用一项技能，它将指导您审计和理解 LaunchDarkly 项目中的功能标志环境。您的工作是探索项目、评估标志的健康状况、识别需要关注的事项，并提供可操作的推荐建议。

## 前置条件

此技能要求您的环境中配置了远程托管的 LaunchDarkly MCP 服务器。

**必需的 MCP 工具：**
- `list-flags`：搜索和浏览标志，可按状态、类型、标签进行过滤
- `get-flag`：获取特定环境中单个标志的完整配置
- `get-flag-status-across-envs`：检查标志在所有环境中的生命周期状态

**可选的 MCP 工具（增强深度）：**
- `find-stale-flags`：查找适合清理的标志，按陈旧程度排序
- `get-flag-health`：获取单个标志的综合健康视图（合并状态+配置）
- `check-removal-readiness`：对特定标志进行详细的安全检查

## 工作流程

### 第 1 步：理解项目

在深入标志数据之前，建立上下文：

1. **识别项目。** 与用户确认 `projectKey`。如果他们尚未指定，请询问。
2. **理解范围。** 询问用户他们试图完成什么：
   - 广泛审计？("我们的标志状态如何？")
   - 针对性调查？("这个特定标志是否仍然需要？")
   - 清理规划？("哪些标志可以移除？")

### 第 2 步：探索标志环境

根据用户的目标调整您的策略：

**对于广泛审计：**
- 使用 `list-flags`，范围限定于关键环境（默认为 `production`）。
- 注意总数：这告诉您标志表面的规模。
- 按 `state`（活跃、非活跃、已发布、新）进行过滤，以划分环境。
- 按 `type`（临时与永久）进行过滤：临时标志是主要的清理目标。

**对于清理规划：**
- 使用 `find-stale-flags`：这是最有效的入口点。它返回按陈旧程度排序的清理候选列表，分为：
  - `never_requested`：创建但从未评估（可能已废弃）
  - `inactive_30d`：在指定时间段内没有 SDK 评估
  - `launched_no_changes`：完全发布，最近没有变更
- 默认 `inactiveDays` 为 30。增加用于保守清理（60、90），或减少用于激进清理（7、14）。
- 默认 `includeOnly` 为 `temporary`。设置为 `all` 以包含永久标志。

**对于针对性调查：**
- 使用 `get-flag-health` 进行单标志深入分析。它在一个调用中合并状态数据与配置上下文，返回生命周期状态、上次请求时间戳、目标摘要、年龄以及是否为临时标志。
- 或使用 `get-flag` 获取完整配置，包括规则、目标和 fallback 详细信息。

### 第 3 步：评估标志健康

对于需要深入调查的标志，评估健康信号。参见 [标志健康信号](references/flag-health-signals.md) 获取完整解释指南。

需要评估的关键信号：

| 信号 | 它告诉您什么 |
|------|--------------|
| **生命周期状态** | 标志在其生命周期中的位置（新 -> 活跃 -> 已发布 -> 非活跃） |
| **上次请求** | SDK 上次评估此标志的时间：陈旧度指标 |
| **目标复杂性** | 规则和目标的数量：移除复杂度指标 |
| **跨环境一致性** | 标志是否在所有地方表现一致 |
| **标志年龄 + 临时状态** | 老的临时标志是强力的清理候选 |

使用 `get-flag-status-across-envs` 检查标志是否在所有环境中一致。一个在生产环境中非活跃但在预发布环境中活跃的标志，与在所有环境中都非活跃的标志所传达的信息不同。

### 第 4 步：分类和优先级排序

将标志分组到可操作的类别：

1. **准备移除**：在所有环境中非活跃、临时、无依赖。直接引导用户到 [标志清理技能](../launchdarkly-flag-cleanup/SKILL.md) 进行代码移除。
2. **可能安全，需要验证**：已发布（完全发布），最近没有规则变更。用户应确认发布已有意完成。
3. **需要调查**：在某些环境中活跃但在其他环境中不活跃，或具有复杂的目标。在没有更多上下文的情况下不建议采取行动。
4. **保持原样**：正在执行任务的活跃标志，或有意长期存在的永久标志。

### 第 5 步：评估移除准备情况（适用时）

如果用户想知道特定标志是否可以移除，使用 `check-removal-readiness`。此工具并行调用多个 API 并返回结构化结论：

- **`safe`**：无阻碍或警告。继续清理。
- **`caution`**：存在警告（代码引用、过期目标、永久标志类型）。展示并让用户决定。
- **`blocked`**：硬性阻碍（依赖标志、活跃请求、目标规则）。必须先解决。

参见 [移除准备情况检查清单](references/removal-readiness-checklist.md) 获取解释每个信号的完整细节。

### 第 6 步：呈现发现

根据用户的要求结构化您的响应：

**对于审计：** 先提供摘要（总数、按状态和类型划分），然后突出需要关注的事项，最后提供具体建议。

**对于特定标志：** 先提供结论（健康 / 需要关注 / 准备移除），然后用您发现的信号支持。

**对于清理规划：** 先提供清理候选数量，按信心排序（最安全的移除优先），并链接到清理工作流执行。

## 重要上下文

- **"已发布"意味着完全发布**：目标已启用，所有用户都接收单个变体，且最近没有变更。这不意味着“最近部署”。
- **"非活跃"并不总是意味着可以安全移除。** 标志可能用于尚未发布的代码，或作为另一个标志的先决条件被引用。
- **永久标志可以有意非活跃。** 某些标志设计为在需要时才激活（禁用开关、紧急切换）。不要自动将这些标志标记为清理。
- **权重在 API 中按 1000 缩放。** 权重为 `60000` 意味着 60%。始终转换为人类可读的百分比。
- **此技能用于发现，而非行动。** 如果用户想从代码中移除标志，引导他们到 [标志清理技能](../launchdarkly-flag-cleanup/SKILL.md)。如果他们想更改目标，引导他们到 [标志目标技能](../launchdarkly-flag-targeting/SKILL.md)。
