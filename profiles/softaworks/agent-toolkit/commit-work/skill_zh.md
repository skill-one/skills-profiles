# 提交工作

## 目标
提交易于审查且安全可发布的更改：
- 仅包含预期的更改
- 提交具有逻辑范围（需要时拆分）
- 提交信息描述了更改内容及其原因

## 需要询问的输入（如果缺失）
- 单个提交还是多个提交？（不确定时：默认为多个小提交，当存在不相关的更改时。）
- 提交风格：必须使用 Conventional Commits。
- 任何规则：主题最大长度、必需的范围。

## 工作流程（检查清单）
1) 提交前检查工作区
   - `git status`
   - `git diff`（未提交）
   - 如果更改很多：`git diff --stat`
2) 确定提交边界（需要时拆分）
   - 拆分依据：功能 vs 重构、后端 vs 前端、格式化 vs 逻辑、测试 vs 生产代码、依赖更新 vs 行为变更。
   - 如果一个文件中混合了更改，计划使用补丁提交。
3) 仅提交属于下一个提交的内容
   - 对于混合更改，优先使用补丁提交：`git add -p`
   - 要取消提交一个代码块/文件：`git restore --staged -p` 或 `git restore --staged <路径>`
4) 审查实际将要提交的内容
   - `git diff --cached`
   - 检查：
     - 无密钥或令牌
     - 无意外的调试日志
     - 无不相关的格式化变更
5) 在编写信息前用 1-2 句话描述已提交的更改
   - "发生了什么更改？" + "为什么？"
   - 如果无法清晰描述，提交可能太大或混合；回到步骤 2。
6) 编写提交信息
   - 使用 Conventional Commits（必需）：
     - `类型(范围): 简短摘要`
     - 空行
     - 正文（什么/为什么，非实现日记）
     - 脚注（BREAKING CHANGE）如果需要
   - 对于多行信息，优先使用编辑器：`git commit -v`
   - 如有帮助，使用 `references/commit-message-template.md`。
7) 运行最小的相关验证
   - 在继续之前运行仓库中最快的有效检查（单元测试、代码检查或构建）。
8) 对下一个提交重复，直到工作区干净

## 交付物
提供：
- 最终的提交信息（如果需要）
- 每个提交的简短摘要（什么/为什么）
- 用于提交/审查的命令（至少：`git diff --cached`，以及任何运行的测试）
