# 专业沟通

## 概述

这项技能提供了在软件开发环境中进行有效专业沟通的框架和指导。无论您是向利益相关者写邮件、撰写团队聊天消息，还是准备会议议程，这些原则都能帮助您清晰沟通并建立专业信誉。

**核心原则**：有效的沟通不在于展示您知道多少，而在于确保您的信息被接收和理解。

## 何时使用此技能

在以下情况下使用此技能：

- 向团队成员、经理或利益相关者写邮件
- 撰写团队聊天消息或异步沟通
- 准备会议议程或总结
- 向非技术人员解释技术概念
- 构建状态更新或报告
- 提高书面沟通的清晰度

**关键词**：邮件、聊天、团队、Slack、Discord、消息、写作、沟通、会议、议程、状态更新、报告

## 核心框架

### What-Why-How 结构

使用这个通用框架组织任何专业信息：

| 组成部分 | 目的 | 示例 |
| --- | --- | --- |
| **What** | 清晰陈述主题/请求 | "我们需要将发布推迟一周" |
| **Why** | 解释原因 | "发现支付处理中的关键错误" |
| **How** | 概述下一步行动/待办事项 | "QA将在周四重新测试；我将在周五更新利益相关者" |

**适用于**：邮件、状态更新、会议发言要点、技术解释

### 书面沟通的三大黄金法则

1. **以清晰的标题/目的开头** - 收件人应立即了解消息内容
2. **使用项目符号、标题和可扫描的格式** - 没人想要大段文字
3. **先说关键信息** - 忙碌的人欣赏效率；先陈述主要观点

### 受众校准

在沟通前，问自己：

1. **您在写给谁**？(技术同行、经理、利益相关者、客户)
2. **他们需要什么程度的细节**？(高层概述 vs 实施细节)
3. **这对他们有什么价值**？(如何影响他们的工作/决策)

## 邮件最佳实践

### 邮件标题公式

| 以前使用 | 尝试 |
| --- | --- |
| "项目更新" | "项目X：状态更新和下一步行动" |
| "问题" | "快速提问：API速率限制方法" |
| "仅供参考" | "仅供参考：周二下午3点部署安排" |

### 邮件结构模板

```markdown
**标题**：[项目/主题]：[具体目的]

Hi [姓名]，

[1-2句直接陈述关键点或请求]

**背景/上下文：**
- [要点1]
- [要点2]

**我需要您做什么：**
- [具体行动或决策需求]
- [适用时：时间线]

[可选：简短的下一步或跟进计划]

Best,
[您的姓名]
```

### 常见邮件类型

| 类型 | 关键要素 |
| --- | --- |
| **状态更新** | 进度总结、障碍、下一步行动、时间线 |
| **请求** | 清晰的请求、背景、截止日期、为什么重要 |
| **升级** | 问题总结、影响、尝试的解决方案、需要的决策 |
| **仅供参考/公告** | 发生了什么变化、谁受影响、任何必要的行动 |

**模板参考**：见 `references/email-templates.md`

## 团队消息礼仪

> **注意**：示例使用Slack术语，但这些原则同样适用于Microsoft Teams、Discord或任何团队消息平台。

### 何时使用聊天 vs 邮件

| 使用聊天 | 使用邮件 |
| --- | --- |
| 快速问题，简短回答 | 需要记录的详细文档 |
| 实时协调 | 向利益相关者发送正式沟通 |
| 非正式团队讨论 | 需要仔细审查的消息 |
| 时间敏感更新 | 具有多个部分的复杂解释 |

### 团队消息最佳实践

1. **使用线程** - 保持主频道可扫描；跟进信息放在线程中
2. **谨慎@提及** - 不要不必要地通知他人
3. **频道组织** - 合适的主题放在合适的频道
4. **直接表达** - "你能审核我的PR吗？" 比 "嘿，你忙吗？" 更好
5. **异步友好** - 写出不需要立即回复的消息

### "无需问候"原则

以前：

```text
你：嗨
你：在吗？
你：能问个问题吗？
[等待...]
```

尝试：

```text
你：嗨Sarah - 关于部署脚本有个快速问题。
     在第42行出现权限错误。你之前见过这种情况吗？
     错误信息：[粘贴错误]
```

## 技术沟通 vs 非技术沟通

### 何时使用技术性 vs 易懂性表达

| 受众 | 方法 |
| --- | --- |
| **工程同行** | 技术细节、代码示例、架构细节 |
| **技术经理** | 细节与高层影响的平衡 |
| **非技术利益相关者** | 商业影响、类比、结果重于实施 |
| **客户** | 简单语言、对他们意味着什么、避免术语 |

### 简化三大策略

1. **先讲大图景再细节** - 人们先理解"为什么"再理解"如何"
2. **简化但不失准确性** - 使用类比；用简单语言替换术语
3. **知道何时切换** - 观察现场；根据问题和参与度调整

### 术语翻译示例

| 技术 | 简单语言 |
| --- | --- |
| "微服务架构" | "我们的系统被拆分成可独立扩展的小块" |
| "异步消息处理" | "任务被排队并在后台处理" |
| "CI/CD流水线" | "自动测试和部署我们代码的过程" |
| "数据库迁移" | "更新我们的数据组织方式" |

**更多示例**：见 `references/jargon-simplification.md`

## 写作清晰度原则

### 主动语态优于被动语态

主动语态更清晰、直接，并传达权威：

| 被动（避免） | 主动（推荐） |
| --- | --- |
| "团队识别了一个错误" | "团队识别了一个错误" |
| "我们将实施该功能" | "我们将实施该功能" |
| "测试发现了错误" | "测试发现了错误" |

### 删除填充词

| 以前使用 | 使用 |
| --- | --- |
| "此时此刻" | "现在" |
| "如果" | "如果" |
| "由于" | "因为" |
| "为了" | "到" |
| "我只是想确认一下" | "你能" |

### "有什么意义？"测试

写作后问自己："有什么意义？这对读者有什么重要性？"

如果不能清晰回答，重新组织信息，先强调价值/影响。

## 会议沟通

### 会前：议程最佳实践

每个会议邀请应包含：

1. **清晰目标** - 将完成什么？
2. **议程项目** - 要讨论的主题和时间估计
3. **准备要求** - 参会者需要带什么/回顾什么？
4. **预期结果** - 需要决策？信息分享？头脑风暴？

### 会中：主持技巧

- **限制讨论时间** - "我们用5分钟讨论这个，然后继续"
- **实时记录行动项** - 谁做什么，何时完成
- **待办事项列表** - 记录离题内容以备后用

### 会后：总结格式

```markdown
**会议**：[主题] - [日期]

**参会者**：[姓名]

**关键决策：**
- [决策1]
- [决策2]

**行动项：**
- [ ] [姓名]：[任务] - 截止日期[日期]
- [ ] [姓名]：[任务] - 截止日期[日期]

**下一步行动：**
- [需要跟进的会议]
- [要分享的文档]
```

**按会议类型的结构**：见 `references/meeting-structures.md`

## 快速参考：沟通检查清单

发送任何专业沟通前：

- [ ] **清晰目的** - 收件人能否在5秒内理解意图？
- [ ] **合适受众** - 这是合适的人/频道吗？
- [ ] **关键信息优先** - 主要观点是否在前？
- [ ] **可扫描** - 是否有项目符号、标题、短段落？
- [ ] **行动明确** - 收件人是否知道（如果有的话）需要做什么？
- [ ] **术语检查** - 受众能否理解所有术语？
- [ ] **语气恰当** - 是否专业但不冷漠？
- [ ] **校对** - 任何错别字或模糊表达？
