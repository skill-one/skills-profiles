# 技能评估器

评估代理技能是否符合官方规范和从17个以上官方示例中推导出的模式。

---

## 核心理念

### 什么是技能？

技能**不是**教程。技能是一种**知识外化机制**。

传统AI知识锁在模型参数中。为了教授新功能：
```
传统方式：收集数据 → GPU集群 → 训练 → 部署新版本
成本：$10,000 - $1,000,000+
时间：数周至数月
```

技能改变了这一点：
```
技能：编辑SKILL.md → 保存 → 在下次调用时生效
成本：$0
时间：即时
```

这是从“训练AI”到“教育AI”的范式转变——就像一个无需训练的热插拔LoRA适配器。您用自然语言编辑Markdown文件，模型的 поведение 就会改变。

### 核心公式

> **好的技能 = 专家知识 - Claude已知内容**

技能的价值由其**知识增量**衡量——即它提供的内容与模型已知内容之间的差距。

- **专家知识**：决策树、权衡、边缘情况、反模式、特定领域的思维框架——这些需要数年经验才能积累的东西
- **Claude已知内容**：基本概念、标准库使用、常见编程模式、一般最佳实践

当技能解释“PDF是什么”或“如何编写for循环”时，它是在压缩Claude已经拥有的知识。这是**令牌浪费**——上下文窗口是一个公共资源，与系统提示、对话历史、其他技能和用户请求共享。

### 工具与技能

| 概念 | 本质 | 功能 | 示例 |
|------|------|------|------|
| **工具** | 模型能做什么 | 执行操作 | bash、read_file、write_file、WebSearch |
| **技能** | 模型知道如何做什么 | 指导决策 | PDF处理、MCP构建、前端设计 |

工具定义能力边界——没有bash工具，模型无法执行命令。
技能注入知识——没有前端设计技能，模型会产生通用的UI。

**方程式**：
```
通用代理 + 优秀的技能 = 领域专家代理
```

相同的Claude模型，加载不同的技能，成为不同的专家。

### 技能中的三种知识类型

评估时，对每个部分进行分类：

| 类型 | 定义 | 处理 |
|------|------|------|
| **专家** | Claude确实不知道这一点 | 必须保留——这是技能的价值 |
| **激活** | Claude知道但可能想不到 | 如果简短则保留——作为提醒 |
| **冗余** | Claude肯定知道这一点 | 应该删除——浪费令牌 |

技能设计的艺术在于最大化专家内容，谨慎使用激活内容，无情地消除冗余内容。

## 评估维度（总计120分）

### D1：知识增量（20分）——核心维度

最重要的维度。技能是否添加了真正的专家知识？

| 分数 | 标准 |
|------|------|
| 0-5 | 解释Claude已知的基本概念（什么是X，如何编写代码，标准库教程） |
| 6-10 | 混合：部分专家知识被明显内容稀释 |
| 11-15 | 大部分是专家知识，冗余最小 |
| 16-20 | 纯知识增量——每个段落都值得它的令牌 |

**红旗**（即时分数≤5）：
- “什么是[基本概念]”部分
- 标准操作的逐步教程
- 解释如何使用常用库
- 通用最佳实践（“编写干净的代码”、“处理错误”）
- 行业标准术语的定义

**绿旗**（高知识增量指标）：
- 非明显选择的决策树（“当X失败时，尝试Y，因为Z”）
- 只有专家才知道的权衡（“A更快，但B处理边缘情况C”）
- 来自真实世界经验的边缘情况
- “永远不要做X，因为[非明显原因]”
- 特定领域的思维框架

**评估问题**：
1. 对于每个部分，问：“Claude是否知道这一点？”
2. 如果解释某事，问：“这是在向Claude解释，还是在为Claude解释？”
3. 统计专家与激活与冗余的段落数量

---

### D2：思维模式+适当程序（15分）

技能是否传递了专家的**思维模式**以及**必要的特定领域程序**？

专家和新手之间的区别不是“知道如何操作”，而是“如何思考问题”。但当Claude缺乏特定领域的程序知识时，只有思维模式是不够的。

**关键区别**：
| 类型 | 示例 | 价值 |
|------|------|------|
| **思维模式** | “在设计中，问：什么使其令人难忘？” | 高——塑造决策 |
| **特定领域程序** | “OOXML工作流：解包 → 编辑XML → 验证 → 打包” | 高——Claude可能不知道 |
| **通用程序** | “步骤1：打开文件，步骤2：编辑，步骤3：保存” | 低——Claude已经知道 |

| 分数 | 标准 |
|------|------|
| 0-3 | 只有Claude已经知道的通用程序 |
| 4-7 | 有特定领域程序但缺乏思维框架 |
| 8-11 | 良好平衡：思维模式+特定领域工作流程 |
| 12-15 | 专家级：塑造思维并提供Claude不知道的程序 |

**有价值的程序**：
- Claude未训练过的工作流程（新工具、专有系统）
- 非明显的正确顺序（例如，“验证必须在打包之前，而不是之后”）
- 容易遗漏的关键步骤（例如，“编辑后必须重新计算公式”）
- 特定领域的序列（例如，MCP服务器的四阶段开发过程）

**冗余程序**：
- 通用文件操作（打开、读取、写入、保存）
- 标准编程模式（循环、条件语句、错误处理）
- 文档化良好的常用库使用

**专家思维模式看起来像**：
```markdown
在[操作]之前，问自己：
- **目的**：这个问题解决了什么？谁使用它？
- **约束**：隐藏的要求是什么？
- **差异化**：什么使这个解决方案令人难忘？
```

**有价值的特定领域程序看起来像**：
```markdown
### 审阅工作流（Claude不知道这个序列）
1. 转换为markdown：`pandoc --track-changes=all`
2. 映射文本到XML：在document.xml中grep文本
3. 批量实施更改：每次3-10行
4. 打包并验证：检查所有更改是否已应用
```

**冗余通用程序看起来像**：
```markdown
步骤1：打开文件
步骤2：找到该部分
步骤3：进行更改
步骤4：保存并测试
```

**测试**：
1. 它是否告诉Claude如何思考？（思维模式）
2. 它是否告诉Claude如何做它不知道的事情？（特定领域程序）

一个好的技能在需要时提供两者。

### D3：反模式质量（15分）

技能是否有有效的“永远不要”列表？

**为什么这很重要**：专家知识的一半是知道什么**不要**做。高级设计师看到白色背景上的紫色渐变就会本能地皱眉——“太AI化了”。这种对“绝对不要做什么”的直觉来自踩过无数地雷。

Claude没有踩过这些地雷。它不知道Inter字体被过度使用，不知道紫色渐变是AI生成内容的标志。好的技能必须明确声明这些“绝对不要”。

| 分数 | 标准 |
|------|------|
| 0-3 | 未提及反模式 |
| 4-7 | 通用警告（“避免错误”、“小心”、“考虑边缘情况”） |
| 8-11 | 具体的“永远不要”列表，附带一些解释 |
| 12-15 | 专家级反模式，附带解释——只有经验才能教 |

**专家反模式**（具体+原因）：
```markdown
永远不要使用通用的AI生成美学，例如：
- 过度使用的字体家族（Inter、Roboto、Arial）
- 陈腐的配色方案（尤其是白色背景上的紫色渐变）
- 可预测的布局和组件模式
- 所有东西都设置默认的border-radius
```

**薄弱的反模式**（模糊，无解释）：
```markdown
避免犯错误。
小心边缘情况。
编写糟糕的代码。
```

**测试**：一个专家在阅读反模式列表时会说“是的，我通过艰难的方式学到了这一点”？还是会说“这是显而易见的”？

### D4：规范合规性——尤其是描述（15分）

技能是否遵循官方格式要求？**特别关注描述质量。**

| 分数 | 标准 |
|------|------|
| 0-5 | 缺少frontmatter或格式无效 |
| 6-10 | 有frontmatter，但描述模糊或不完整 |
| 11-13 | 有效的frontmatter，描述有WHAT但有WEHN |
| 14-15 | 完美：全面的描述，包括WHAT、WHEN和触发关键字 |

**frontmatter要求**：
- `name`：小写，字母数字+连字符，≤64个字符
- `description`：**最关键的字段**——决定技能是否会被使用

---

**为什么描述是最重要的字段**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  技能激活流程                                                      │
│                                                                     │
│  用户请求 → 代理看到所有技能描述 → 决定哪个                      │
│                 （只有描述，不包括正文！）     要激活              │
│                                                                     │
│  如果描述不匹配 → 技能永远不会被加载                              │
│  如果描述模糊 → 技能可能不会在应该触发时触发                      │
│  如果描述缺少关键字 → 技能对代理不可见                           │
└─────────────────────────────────────────────────────────────────────┘
```

**残酷的真相**：一个内容完美但描述糟糕的技能是**无用的**——它永远不会被激活。描述是**唯一的机会**告诉代理“在这种情况下使用我”。

---

**描述必须回答三个问题**：

1. **WHAT**：这个技能做什么？（功能）
2. **WHEN**：在什么情况下应该使用它？（触发场景）
3. **KEYWORDS**：应该触发这个技能的哪些术语？（可搜索术语）

**优秀的描述**（所有三个元素）：
```yaml
description: "全面的文档创建、编辑和分析，支持跟踪更改、评论、格式保留和文本提取。
当Claude需要处理专业文档（.docx文件）时：
(1) 创建新文档，
(2) 修改或编辑内容，
(3) 处理跟踪更改，
(4) 添加评论，或任何其他文档任务"
```

分析：
- WHAT：创建、编辑、分析、跟踪更改、评论
- WHEN：当Claude需要处理...时
- KEYWORDS：.docx文件、跟踪更改、专业文档

**糟糕的描述**（缺少元素）：
```yaml
description: "处理文档相关功能"
```

问题：
- WHAT：模糊（“文档相关功能”——具体是什么？）
- WHEN：缺少（何时应该由代理使用？）
- KEYWORDS：缺少（没有“.docx”，没有特定场景）

**另一个糟糕的例子**：
```yaml
description: "一个对各种任务有帮助的有用技能"
```

这无济于事——代理不知道何时激活它。

---

**描述质量检查清单**：
- [ ] 列出具体的功能（不只是“帮助做X”）
- [ ] 包含明确的触发场景（“使用当...”， “当用户询问...”）
- [ ] 包含可搜索的关键字（文件扩展名、领域术语、动作动词）
- [ ] 具体到代理确切知道何时使用它
- [ ] 包括必须使用此技能的场景（而不仅仅是“可以”）
