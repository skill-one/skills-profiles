# 降低熵值

更多的代码产生更多的代码。熵值会累积。这项技能倾向于最小的代码库。

**核心问题：** "代码库在*之后*看起来会是什么样子？"

## 开始之前

**从 `references/` 目录至少加载一种思维方式**

1. 列出参考目录中的文件
2. 阅读前导描述以选择适用的方式
3. 至少加载一种
4. 说明你加载了哪种以及其核心原则

**在完成这些之前不要继续。**

## 目标

目标是**最终代码库中更少的总代码**——而不是现在需要编写的代码更少。

- 编写 50 行代码删除 200 行代码 = 净收益
- 保留 14 个函数以避免编写 2 个 = 净损失
- "没有变更"不是目标。更少的代码才是目标。

**衡量最终状态，而不是付出的努力。**

## 三个问题

### 1. 解决这个问题所需的最小代码库是什么？

不是"最小的变更"是什么——而是最小的*结果*是什么。

- 这可以是 2 个函数而不是 14 个吗？
- 这可以是 0 个函数（删除该功能）吗？
- 如果这样做，我们会删除什么？

### 2. 所提出的变更是否导致总代码减少？

计算变更前后的代码行数。如果变更后 > 变更前，则拒绝它。

- "组织得更好"但代码更多 = 更多熵值
- "更灵活"但代码更多 = 更多熵值
- "更清晰的关注点分离"但代码更多 = 更多熵值

### 3. 我们可以删除什么？

每个变更都是删除的机会。询问：

- 这使得什么变得过时？
- 只是因为我们正在替换的东西才需要的什么？
- 我们最多可以删除多少？

## 信号旗

- **"保留现有内容"** - 现状偏见。问题是总代码，而不是变更。
- **"这增加了灵活性"** - 为什么增加灵活性？YAGNI。
- **"更好的关注点分离"** - 更多的文件/函数 = 更多的代码。分离不是免费的。
- **"类型安全"** - 值得多少行代码？有时在更少的代码中运行时检查会赢。
- **"更容易理解"** - 14 件事情不比 2 件事情更容易。

## 不适用的情况

- 代码库已经针对其功能是最小的
- 你处于具有强规范的框架中（不要与之对抗）
- 监管/合规要求强制要求某些结构
