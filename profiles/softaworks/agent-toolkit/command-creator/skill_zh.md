# 命令创建器

此技能指导创建 Claude Code 剪辑命令——可重用的工作流，可在 Claude Code 对话中使用 `/command-name` 调用。

## 关于剪辑命令

剪辑命令是存储在 `.claude/commands/`（项目级）或 `~/.claude/commands/`（全局/用户级）中的 markdown 文件，在调用时会被展开为提示。它们非常适合：

- 重复性工作流（代码审查、PR 提交、CI 修复）
- 需要一致性的多步骤流程
- 代理委托模式
- 项目特定自动化

## 何时使用此技能

在以下情况下调用此技能：

- 用户要求“创建命令”或“制作剪辑命令”
- 想要自动化重复性工作流
- 需要为重用文档化一致流程
- 说“我不断重复 X，我们能为此创建一个命令吗？”
- 想要创建项目特定或全局命令

## 预装资源

此技能包含参考文档以提供详细指导：

- **references/patterns.md** - 命令模式（工作流自动化、迭代修复、代理委托、简单执行）
- **references/examples.md** - 带完整源码的真实命令示例（submit-stack、ensure-ci、create-implementation-plan）
- **references/best-practices.md** - 质量检查清单、常见陷阱、写作指南、模板结构

在创建命令时按需加载这些参考文档，以了解模式、查看示例或确保质量。

## 命令结构概述

每个剪辑命令都是一个 markdown 文件，包含：

```markdown
---
description: 在 /help 中显示的简要描述（必需）
argument-hint: <占位符>（如果命令接受参数，可选）
---

# 命令标题

[为代理执行自主操作的详细说明]
```

## 命令创建工作流

### 第 1 步：确定位置

**自动检测适当位置：**

1. 检查 git 仓库状态：`git rev-parse --is-inside-work-tree 2>/dev/null`
2. 默认位置：
   - 如果在 git 仓库中 → 项目级：`.claude/commands/`
   - 如果不在 git 仓库中 → 全局：`~/.claude/commands/`
3. 允许用户覆盖：
   - 如果用户明确提到“全局”或“用户级” → 使用 `~/.claude/commands/`
   - 如果用户明确提到“项目”或“项目级” → 使用 `.claude/commands/`

在继续之前向用户报告所选位置。

### 第 2 步：显示命令模式

帮助用户理解不同类型的命令。加载 **references/patterns.md** 查看可用模式：

- **工作流自动化** - 分析 → 执行 → 报告（例如 submit-stack）
- **迭代修复** - 运行 → 解析 → 修复 → 重复（例如 ensure-ci）
- **代理委托** - 上下文 → 委托 → 迭代（例如 create-implementation-plan）
- **简单执行** - 带参数运行命令（例如 codex-review）

询问用户：“哪个模式最接近您想创建的内容？” 这有助于构建对话。

### 第 3 步：收集命令信息

询问用户关键信息：

#### A. 命令名称和用途

询问：

- “命令的名称应该是什么？”（用于文件名）
- “这个命令做什么？”（用于描述字段）

指南：

- 命令名称必须使用连字符（非下划线）
  - ✅ 正确：`submit-stack`、`ensure-ci`、`create-from-plan`
  - ❌ 错误：`submit_stack`、`ensure_ci`、`create_from_plan`
- 文件名与命令名称匹配：`my-command.md` → 调用为 `/my-command`
- 描述应简洁、以行动为导向（出现在 `/help` 输出中）

#### B. 参数

询问：

- “这个命令需要任何参数吗？”
- “参数是必需的还是可选的？”
- “参数应该代表什么？”

如果命令需要参数：

- 在 frontmatter 中添加 `argument-hint: <占位符>`
- 使用 `<尖括号>` 表示必需参数
- 使用 `[方括号]` 表示可选参数

#### C. 工作流步骤

询问：

- “这个命令应该遵循哪些具体步骤？”
- “它们的顺序应该是怎样的？”
- “应该使用哪些工具或命令？”

收集以下详细信息：

- 执行初始分析或检查
- 主要操作
- 如何处理结果
- 成功标准
- 错误处理方法

#### D. 工具限制和指导

询问：

- “这个命令应该使用任何特定代理或工具吗？”
- “是否有任何工具或操作应避免？”
- “它应该读取任何特定文件以获取上下文吗？”

### 第 4 步：生成优化命令

创建带有代理优化指令的命令文件。加载 **references/best-practices.md** 获取：

- 模板结构
- 代理执行的最佳实践
- 写作风格指南
- 质量检查清单

关键原则：

- 使用祈使/不定式形式（动词优先指令）
- 明确具体
- 包含预期结果
- 提供具体示例
- 定义清晰的错误处理

### 第 5 步：创建命令文件

1. 确定完整文件路径：
   - 项目：`.claude/commands/[command-name].md`
   - 全局：`~/.claude/commands/[command-name].md`

2. 确保目录存在：

   ```bash
   mkdir -p [directory-path]
   ```

3. 使用 Write 工具编写命令文件

4. 确认用户：
   - 报告文件位置
   - 总结命令功能
   - 解释如何使用：`/command-name [参数]`

### 第 6 步：测试和迭代（可选）

如果用户想测试：

1. 建议测试：`您可以通过运行：/command-name [参数] 来测试此命令`
2. 准备根据反馈迭代
3. 根据需要更新文件以改进

## 快速提示

**对于详细指导，加载预装资源：**

- 设计命令工作流时加载 **references/patterns.md**
- 查看现有命令结构时加载 **references/examples.md**
- 最终确定前加载 **references/best-practices.md** 以确保质量

**记住常见模式：**

- 使用 Bash 工具执行 `pytest`、`pyright`、`ruff`、`prettier`、`make`、`gt` 命令
- 使用 Task 工具调用子代理执行专业任务
- 首先检查特定文件（例如 `.PLAN.md`）再继续
- 立即标记待办事项完成，不要批量处理
- 包含明确的错误处理指令
- 定义清晰的成功标准

## 总结

创建命令时：

1. **检测位置**（项目级 vs 全局级）
2. **显示模式**以构建对话
3. **收集信息**（名称、用途、参数、步骤、工具）
4. **生成优化命令**，包含代理可执行的指令
5. **在适当位置创建文件**
6. **确认并根据需要迭代**

专注于创建代理可自主执行的命令，包含清晰步骤、明确工具使用和适当的错误处理。
