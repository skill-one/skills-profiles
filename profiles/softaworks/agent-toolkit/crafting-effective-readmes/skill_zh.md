# 编写有效的 README

## 概述

README 用于解答你的受众会提出的问题。不同的受众需要不同的信息 - 开源项目的贡献者需要不同于未来你打开配置文件夹时的背景信息。

**始终思考：** 谁会阅读这份文档，他们需要了解什么？

## 流程

### 第一步：确定任务

**思考：** "你正在处理什么 README 任务？"

| 任务 | 时间 |
|------|------|
| **创建** | 新项目，还没有 README |
| **添加** | 需要记录新内容 |
| **更新** | 功能变更，内容过时 |
| **审查** | 检查 README 是否仍然准确 |

### 第二步：任务特定问题

**创建初始 README：**
1. 项目类型是什么？（见下文项目类型）
2. 这解决了什么问题？（用一句话描述）
3. 什么是最快能让它运行起来的方法？
4. 有什么值得强调的？

**添加一个章节：**
1. 需要记录什么？
2. 它应该放在现有结构中的什么位置？
3. 谁最需要这些信息？

**更新现有内容：**
1. 有什么变化？
2. 阅读当前的 README，识别过时的章节
3. 提出具体的修改建议

**审查/刷新：**
1. 阅读当前的 README
2. 对照实际的项目状态（package.json、主文件等）
3. 标记过时的章节
4. 如果有，更新“上次审查”日期

### 第三步：始终思考

起草后，思考：**“还有什么需要强调或包含，但我可能遗漏了？”**

## 项目类型

| 类型 | 受众 | 关键章节 | 模板 |
|------|------|----------|------|
| **开源** | 贡献者、全球用户 | 安装、使用、贡献、许可 | `templates/oss.md` |
| **个人** | 未来你、作品集观众 | 它的作用、技术栈、学习心得 | `templates/personal.md` |
| **内部** | 同事、新员工 | 设置、架构、操作手册 | `templates/internal.md` |
| **配置** | 未来你（困惑的） | 这里有什么、为什么、如何扩展、注意事项 | `templates/xdg-config.md` |

**如果不确定，请询问用户**。不要假设所有内容都使用开源默认设置。

## 必备章节（所有类型）

每个 README 至少需要包含：

1. **名称** - 自解释的标题
2. **描述** - 用 1-2 句话说明是什么和为什么
3. **使用方法** - 如何使用它（示例有帮助）
