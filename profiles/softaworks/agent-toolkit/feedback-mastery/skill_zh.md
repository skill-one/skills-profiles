# 反馈对话

## 概述

这项技能提供了处理困难职场对话和有效反馈的框架。无论是处理绩效问题、解决冲突还是给予建设性反馈，这些结构化方法都能带来更好的结果。

**核心洞察：** 研究表明，那些带着准备和清晰框架处理困难对话的员工，比那些没有计划就介入的员工**更有60%的可能性达成积极解决方案**。

## 何时使用此技能

在以下情况下使用此技能：

- 准备向同事或直接下属提供反馈
- 处理绩效问题或未达预期
- 处理团队成员之间的冲突
- 就敏感话题进行一对一对话
- 接收反馈并希望做出建设性回应
- 管理利益相关者的期望

**关键词**：反馈、困难对话、一对一、绩效、冲突、期望、行为、对抗

## 核心框架

### 准备-执行-跟进模型

困难对话的三部分结构：

| 阶段 | 重点 | 关键问题 |
| --- | --- | --- |
| **准备** | 理解问题、定义目标、管理情绪 | 问题是什麼？我希望达到什麼结果？我是否冷静？ |
| **执行** | 中性开场、用事实而非指责、鼓励对话 | 我如何开始？我有什么证据？我如何让他们参与？ |
| **跟进** | 记录行动、设置检查点、提供支持 | 我们达成了什麼共识？何时检查？我如何支持？ |

### SBI反馈模型

**情境-行为-影响（SBI）**结构化反馈使其具体、客观且可执行：

| 组成部分 | 描述 | 示例 |
| --- | --- | --- |
| **情境** | 描述具体背景 | "在昨天代码审查中..." |
| **行为** | 陈述可观察的行动（非解读） | "...你在莎拉解释她的方法时三次打断了她..." |
| **影响** | 解释对团队/项目/个人的影响 | "...这让她犹豫是否分享想法，并减缓了我们的讨论。" |

**为什么有效：** SBI消除假设，专注于可观察的事实，减少防御性。

## 准备阶段

### 第1步：理解问题

问自己：

- **问题到底是什么？**（具体，不要模糊）
- **它如何影响团队、项目或公司？**
- **我是否收集了所有相关事实？**
- **这是模式还是一次性事件？**

### 第2步：定义你的目标

在对话前，明确你寻求的目标：

| 目标类型 | 示例 |
| --- | --- |
| 行为改变 | "我希望他们按时提交代码审查" |
| 相互理解 | "我希望理解是什么阻碍了他们" |
| 期望设定 | "我希望澄清功能'完成'的含义" |
| 问题解决 | "我希望一起找到解决方案" |

**技巧：** 使用if-then语句澄清利害关系：
> "如果这种行为继续，那么项目时间表将受到影响，导致错过交付物。"

### 第3步：管理你的情绪

高情绪强度会降低认知处理能力30%。在对话前：

- [ ] 我是否冷静且在控制中？
- [ ] 我是否将事实与个人挫败感分开？
- [ ] 我是否考虑过他们的观点？
- [ ] 我能否不指责地呈现？

**重构技巧：**

| 指责性 | 建设性 |
| --- | --- |
| "你总是错过截止日期，这拖慢了所有人" | "我注意到最近有些延误，想了解你是否面临任何挑战" |
| "你从不正确地测试你的代码" | "我最近看到几个错误逃过了测试。让我们谈谈我们的测试流程" |

## 执行阶段

### 三步执行公式

1. **用中性和意图开场**
2. **用事实而非指责陈述问题**
3. **鼓励对话和解决方案**

### 有效开场白

| 背景 | 开场白 |
| --- | --- |
| 一般 | "我想谈谈对我们团队成功很重要的事情，我很想听听你的看法。" |
| 绩效 | "我注意到一些模式我想讨论。我的目标是支持你，而不是批评。" |
| 冲突 | "我感觉可能有些紧张，我想了解你这一方的发生了什麼。" |
| 期望 | "我想确保我们对期望是一致的。我们可以谈谈这个项目进行得如何吗？" |

### 事实而非指责

| 指责 | 事实 |
| --- | --- |
| "你不对这个项目投入" | "我注意到你最近三次会议的更新都很简短。是不是有什么影响你的工作量？" |
| "你不在乎代码质量" | "这个PR在QA中发现了12个错误。让我们谈谈发生了什麼，以及我们如何改进" |
| "你总是迟到" | "站立会议9:00开始，你过去三天都9:15才加入。是什麼情况？" |

**关键原则：**

- 使用具体示例而非概括（"总是"、"从不"）
- 坚持可观察的行为，而非对动机的假设
- 关注影响，而非性格

### 鼓励对话

在陈述你的观察后，转向合作：

| 情况 | 对话提示 |
| --- | --- |
| 理解障碍 | "这有什麼挑战？" |
| 寻求他们的观点 | "你怎么看待情况？" |
| 寻找解决方案 | "什麼能帮助你成功？" |
| 检查一致性 | "这和你对发生的事情的理解一致吗？" |

## 跟进阶段

即使成功的对话也需要跟进以创造持久改变。

### 跟进清单

- [ ] **记录达成的行动项** - 具体将改变什麼？
- [ ] **设置检查日期** - 何时会再次讨论？
- [ ] **提供持续支持** - 你将如何帮助他们成功？
- [ ] **庆祝进步** - 当他们取得进步时认可

### 示例跟进消息

```markdown
Hi [姓名],

感谢你昨天的对话。我欣赏你的坦诚。

**我们达成的共识：**
- [行动项1] - [时间表]
- [行动项2] - [时间表]

**检查：** 让我们在[日期]重新联系，看看进展如何。

如果你需要任何支持，我都在这里。感谢你和我一起处理这件事。

最好的，
[你的名字]
```

## 软件团队的SBI示例

### 积极反馈

**代码审查：**
> **情境：** "在周二对认证模块的代码审查中..."
> **行为：** "...你提供了关于潜在安全漏洞的详细评论，并建议了高效的修复方法..."
> **影响：** "...这加强了我们的安全态势，并节省了团队后期的调试时间。"

**协作：**
> **情境：** "在昨天的架构讨论中..."
> **行为：** "...你提出了澄清问题，并在其他人提出想法的基础上构建，而不是推动自己的解决方案..."
> **影响：** "...这帮助我们更快地达成共识，并让每个人感到被听到。"

### 建设性反馈

**错过截止日期：**
> **情境：** "当我们上周四最终确定API部署时..."
> **行为：** "...你的测试结果在约定的截止时间后两小时才提交..."
> **影响：** "...这延迟了发布，风险了我们的SLA，并导致QA团队加班。"

**会议行为：**
> **情境：** "在我们昨天的冲刺计划中..."
> **行为：** "...你在讨论的大部分时间都在看手机，在我们要求估算时没有贡献..."
> **影响：** "...这使团队无法获得你在后端故事方面的专业知识，并让其他人觉得他们的时间不被重视。"

## 常见困难场景

### 场景：绩效问题

**情境：** 一位开发人员持续交付有bug的代码。

**方法：**

1. **准备：** 收集具体示例（PR、bug数量、时间表）
2. **执行：** "我注意到[最近Y个PR中有X个bug]。我想了解发生了什麼，以及我如何能支持你。"
3. **探索：** 询问工作量、需求清晰度、测试信心
4. **合作：** "什麼能帮助你更有信心地提高代码质量？"
5. **跟进：** 检查达成改变后的情况，认可改进

### 场景：团队成员之间冲突

**情境：** 两位工程师在技术方法上存在分歧，这影响了团队。

**方法：**

1. **先分别会面：** 了解每个观点
2. **寻找共同点：** 他们都想什麼？（工作产品、好代码等）
3. **共同调解：** 专注于事实和权衡，而非个性
4. **建立决策流程：** 当存在分歧时，团队如何决定？
5. **跟进：** 检查解决方案是否有效

### 场景：不切实际的期望

**情境：** 领导希望功能在需要一半的时间内完成。

**方法：**

1. **准备：** 过去类似工作的数据、所需任务分解
2. **执行：** "我想确保我们对现实是一致的。这里是我看到的..."
3. **呈现权衡：** "如果我们[缩小范围/增加人员/接受风险]，我们可以按时完成"
4. **合作：** "这里最重要的是日期还是完整的功能集？"
5. **记录：** 以书面形式达成共识，避免未来不一致

**详细脚本：** 查看`references/difficult-conversation-scripts.md`

## 好地接收反馈

当你处于接收端时：

### 对话期间

1. **充分倾听** - 在他们说话时不要准备你的辩护
2. **提出澄清问题** - "你能给我一个具体示例吗？"
3. **复述以确认** - "所以你说的意思是..."
4. **承认影响** - 即使意图不同： "我能看出这对你有什麼影响"
5. **不要防御** - 感谢他们提出

### 对话后

1. **诚实反思** - 反馈中是否有真理？
2. **确定行动** - 你将如何改变？
3. **跟进** - 告诉他们你将改变什麼
4. **请求持续反馈** - 表明你致力于成长
