# 创建 DESIGN.md

为单个产品或连贯的网站创建一个 `DESIGN.md`。记录其主导的设计语言，而不是偶然存在的一切值。

## 边界

- 仅修改 `DESIGN.md`。不要更改产品源代码、依赖项、配置或生成的文件。
- 使用下述的 DESIGN.md 格式合同。不要发明一个竞争性的模式。
- 不要将每个发现的标记或组件复制到文档中。
- 不要将重复、本地样式或视觉偏好转换为产品意图。

## 1. 选择模式

### 仓库模式

当本地产品仓库可用时使用。在选定产品的根目录下创建或更新 `DESIGN.md`。

如果仓库包含多个可部署的产品，选择用户命名的那个。如果请求没有指定一个且所有权不明确，则在写入前询问。

仓库证据可以建立规范值、标记名称、组件所有权和记录的理由。

### URL 模式

当用户提供一个没有源代码仓库的公共 URL 时使用。在当前工作区创建一个重建的 `DESIGN.md` 草稿。

URL 模式需要渲染的浏览器访问。检查桌面和移动宽度下的 DOM、计算样式和公开加载的样式表。屏幕截图可以支持解释，但不能单独建立确切值。

检查提供的页面和共享的浏览器界面。对于全局请求，采样最多三个同源的页面，这些页面代表不同的模板。

URL 证据只能建立可观察的视觉模式和计算值。它不能建立内部标记名称、组件所有权、未记录的理由或模式是否有意成为规范。

如果渲染检查不可用，请要求屏幕截图或源文件。不要仅从复制、元数据或 HTML 结构创建 `DESIGN.md`。

在源可用时始终选择仓库模式。提供的 URL 可以验证渲染的呈现效果，但不能替代仓库证据。

## 共享证据管道

两种模式的区别仅在于收集证据的方式。它们必须使用相同的记录和输出管道：

```text
角色 → 值 → 源 → 范围 → 频率 → 置信度
```

1. 使用选定的模式收集证据。
2. 记录每个候选的源、范围和频率。
3. 将候选标准化为 DESIGN.md 模式。
4. 忽略不确定、没有合同的本地或与实现无关的候选。
5. 验证前文的结构和导出兼容性。
6. 只有在标准化后的前文通过后，才写入 Markdown。

永远不要让仓库或 URL 证据引入第二个标记模式。相同的扁平标记名称、映射形状的排版、省略规则和导出门适用于两种模式。

生成的文档在验证通过之前是私有的。在 lint 和导出成功之前，永远不要返回、显示或总结 `DESIGN.md` 草稿。如果验证报告无效形状或缺少导出类别，请重写前文并重新运行；如果类别无法修复，请删除它并报告为省略。

## 2. 追踪证据

在仓库模式下，按此顺序检查：

1. 现有的 `DESIGN.md` 和显式的仓库指导
2. 标记、主题、变量和全局样式
3. 共享的基础组件及其变体
4. 典型的路由和渲染的消费者
5. 表面本地实现

当选定的产品导入、引用、继承或渲染它时，源才会参与。排除提议、迁移、示例、生成输出、遗留实现和类似命名的包，除非选定的产品使用它们。

在 URL 模式下，为以下内容采样代表性元素：

- 颜色和表面角色
- 排版角色
- 间距和布局
- 边框、半径和高度
- 导航、按钮、输入、卡片和重复的内容结构
- 桌面和移动呈现

优先使用计算值和加载的 CSS 声明，而不是视觉估计。

在起草 URL 模式的文本或 YAML 之前，为每个采样的页面和视口构建一个私有的证据账本。对于每个候选，记录：页面、视口、元素角色、计算属性/值，以及当可用时匹配的加载的 CSS 声明或自定义属性。

检查页面加载的公共样式表，包括自定义属性和媒体查询规则；只有当样式表值连接到渲染的元素或跨采样的页面重复时，才可用。

当渲染的计算值和加载的声明/自定义属性一致，或相同的计算值在所需样本中针对相同的角色重复时，将 URL 值提升到 DESIGN.md。如果这两个条件都不成立，请省略该值。只有当其声明和渲染使用直接可观察时，您才可能保留暴露的自定义属性名称；不要从原始值发明语义别名。

对于每个 URL 模式的声明，在写入之前需要所有三个证据：

1. 观察：模式或值在渲染的页面上可见或计算。
2. 基础：它被测量，或跨所需采样的页面/视口重复。
3. 后果：它改变了 DESIGN.md 中的具体实现选择。

如果任何证据缺失，请省略该声明。不要将视觉印象转换为标记，将单次发生转换为全局规则，或将猜测值转换为 YAML。确切值需要计算样式或加载的 CSS；否则，在不提供值的情况下描述角色或省略它。

## 3. 决定属于什么

在仓库模式下，在描述产品特征之前找到显式的产品意图或设计参考。在 URL 模式下，不要发明产品特征；概述可能仅声明网站的可见目的和呈现，并必须将文档标识为重建的。

仅从治理源中的命名共享标记和角色写入 YAML。不要将实用类、重复的文本字面量或组件值转换为标记尺度。

将前文形状视为硬门，而不是风格选择：值是标记组必须是映射，其子项是模式的字段。永远不要发出标量排版条目（`sans: Geist`）、任意嵌套的源对象（`font-family: { mono: ... }`）或从 CSS 变量名称复制的圆角键（`radius-sm`、`radius-md` 等）。

使用映射，而不是序列，来表示标记组。当治理源定义一个组级标记（例如 `--radius`）时，将其标准化为 `base`；否则保留源标记名称。

将源值映射到 DESIGN.md 模式字段。保留语义标记名称，而不是源对象嵌套。例如，写 `typography.mono.fontFamily: Geist Mono`，而不是 `typography.mono: Geist Mono`；当源只有 `--radius` 时，写 `rounded.base: 0.625rem`，而不是 `rounded.radius` 或派生的半径步长。

在写入确切值之前，通过活动的主题或配置解决框架实用程序。

在写入前文之前，确定仓库的导出目标：`css-tailwind` 用于 Tailwind v4，`json-tailwind` 用于 Tailwind v3，否则为 `dtcg`。标记名称必须适用于该目标。

在编码主题模式之前，检查已安装的 DESIGN.md 规范：

```bash
npx @google/design.md spec
```

如果规范支持 `themes` 和 `default-theme`，请使用其主题感知标记语法。否则，将默认主题值放在每个规范语义标记下，并在 `## Themes` 表中保留确切的备用主题值。不要创建平行的 `-light` 和 `-dark` 标记名称，丢弃备用主题值，或使用未发布的语法。备用主题表仅是文档；不要假装它使前文具有主题感知。

在仓库模式下，每个文本规则必须由显式指导、命名的共享标记或变体或至少由两个经过审计的表面使用的共享所有者支持。否则省略它。

在 URL 模式下，每个文本规则必须直接可见。全局规则必须在至少两个采样的模板中重复；否则将其限制为检查的页面。使用重建的角色名称，并将文档标记为草稿。

URL 模式的 YAML 故意是稀疏的，但在存在测量证据时不是空的。当至少有一个支持值或角色通过三重证据门时，请添加一个类别。颜色可以使用计算值或验证的公共自定义属性，但必须保持扁平且导出安全；排版必须使用规范字段，例如 `fontFamily`、`fontSize`、`lineHeight` 和 `fontWeight`；圆角和间距值必须来自计算样式或加载的声明。不要创建别名，例如 `primary`、`elevated` 或 `display`，仅仅是为了组织观察结果。组件部分需要相同的交互或表面处理在至少两个采样的页面中重复，并改变具体的实现选择。

URL 重建不会改变前文模式。仅使用以下排版属性名称：`fontFamily`、`fontSize`、`lineHeight`、`fontWeight` 和 `letterSpacing`。例如：

```yaml
typography:
  sans:
    fontFamily: Inter Variable
  display:
    fontFamily: Inter Variable
    fontSize: 64px
    lineHeight: 64px
    fontWeight: 510
```

永远不要发出 URL 特定的别名，例如 `family`、`size`、`weight`、`mobile-display` 或嵌套的 `sans`/`mono` 值在排版尺度内。重建的角色名称可能不同；模式字段名称可能不会。

对于 URL 输出，除非用户指定其他目标，否则使用 `css-tailwind` 作为兼容性导出目标。将重建的颜色角色扁平化为有效的标记名称。使用 `background-primary`、`foreground-secondary` 或 `border-muted`，而不是嵌套键，例如 `background.primary` 或 `foreground.secondary`。每个发出的标记名称必须匹配 `^[a-zA-Z0-9][a-zA-Z0-9-]*$`；拒绝并重写任何会失败此测试的键。

在写入任何 Markdown 之前，先标准化 URL 前文。顺序是：收集证据，选择导出目标，将证据映射到规范模式，拒绝无效形状，然后写入文档。永远不要先起草文本，然后再调整 YAML。

URL 前文必须满足这些形状规则：

- `colors` 是有效标记名称到值的扁平映射。
- `typography` 是命名尺度的映射；每个尺度是一个仅使用规范字段的映射。
- `rounded` 和 `spacing` 是有效标记名称到值的扁平映射。
- `components` 可以引用规范标记路径，但不能引入第二个标记模式。

如果标准化需要发明标记名称、字段、尺度或语义关系，请省略候选。

在前文之外，每个 Markdown 句子必须改变实现选择。删除组件清单、通用设计建议和仅重述 YAML 的文本。

保留每个规则的范围和方向。当实现与显式指导冲突时，记录指导并在 `DESIGN.md` 外报告冲突。

## 4. 编写文档

从最小的有效前文开始：

```yaml
---
version: alpha
name: <string>
description: <string>
---
```

仅 `name` 是必需的。仅在治理源已经定义了命名系统或合同时，才添加 `colors`、`typography`、`rounded`、`spacing` 或 `components`。不要创建标记名称来组织实现值。标记引用使用 `{path.to.token}`。

使用模式形状的映射，而不是复制的源嵌套。排版尺度始终命名，并映射其属性在其下方：

```yaml
typography:
  sans:
    fontFamily: Geist
  mono:
    fontFamily: Geist Mono
```

如果源仅定义了 `--radius`，写 `rounded.base`，而不是 `rounded.radius`；不要从实用类或重复值派生 `sm`、`md`、`lg` 或 `xl`。在保存之前，检查解析的前文，如果任何 `typography` 子项是标量或 `rounded` 包含治理源中不存在的键，请自行拒绝它。

从 `## Overview` 开始。仅声明产品的目的和证据设计方向。不要总结页面、组件、标记或实现。仅添加此顺序中支持的部分：

1. 颜色
2. 主题
3. 排版
4. 布局
5. 高度与深度
6. 形状
7. 组件
8. 该做与不该做

仅因为格式中存在才创建一个部分。不要重新排序或复制包含的部分。仅当支持指导无法适应标准部分时，才添加未知部分。

Markdown 记录设计意图和应用指导。除了备用 `## Themes` 表，不要将标记清单、组件配置、源语法或文档方法放在 Markdown 中。

仅当治理源声明了明确的禁止时，才包含一个“不该做”。

- 将确切的规范值放在 YAML 前文中，除了备用主题值，当安装的规范无法表示模式时。
- 将支持的理由和应用指导放在 Markdown 中。
- 保留来自现有 `DESIGN.md` 的接受决策，除非用户或当前治理证据替换了它们。
- 不要发明品牌个性、受众或情感理由。
- 不要包括引用、审计笔记、被拒绝的候选、冲突或未解决的问题在 `DESIGN.md` 中。

在保存之前，删除：

- 任何 YAML 标记未由治理源命名
- 任何页面本地行为作为全局规则呈现
- 任何与显式指导冲突的实现模式
- 任何未明确声明的禁止
- 任何 YAML 前文或备用 `## Themes` 表之外的精确实现值
- 任何 Markdown 中的组件配置或文档方法
- 任何不改变最终 DESIGN.md 的句子

运行一次最终的无操作传递：删除模糊建议，例如“彻底”、“保持精致”或“使用良好判断”。仅保留证据门、模式约束或改变文档的应用规则。

## 5. 验证

运行结构 linting：

```bash
npx @google/design.md lint DESIGN.md
```

然后运行一个兼容性导出，使用上述选定的目标：

```bash
npx @google/design.md export --format <format> DESIGN.md
```

检查输出。每个由目标支持并填充的前文类别必须发出其对应的标记类别；即使命令成功退出，空或缺失的类别也是模式失败。重写前文并重新运行验证，直到类别发出，除非目标确实无法表示它。不要在导出中缺少任何填充类别的情况下报告成功。不要在 lint 或导出失败时返回文档。不要仅为了满足导出器限制而删除支持的设计信息；报告该限制而不是。不要创建或保留导出文件。

对于 `css-tailwind`，验证这些输出家族：`colors` → `--color-*`，`typography.<name>.fontFamily` → `--font-*`，`typography.<name>.fontSize` → `--text-*`，`rounded` → `--radius-*`，和 `spacing` → `--spacing-*`。排版条目是命名尺度；将 `fontFamily`、`fontSize` 和 `lineHeight` 放在每个尺度内，而不是任意源嵌套，例如 `font-family`。如果 `typography` 填充但导出不包含 `--font-*` 或 `--text-*`，文档无效，必须重写后报告。

在更新现有文档时，暂时保留其原始内容并运行：

```bash
npx @google/design.md diff <previous-file> DESIGN.md
```

除非当前治理证据或用户明确替换，否则恢复任何删除的接受决策。

## 6. 报告

返回：

- 模式和经过审计的产品或 URL
- 创建或更新的 `DESIGN.md`
- 使用的治理源
- 从文档中省略的冲突或不支持的区域
- 最终 lint 和导出结果

在 URL 模式下，将输出标记为重建的草稿。
