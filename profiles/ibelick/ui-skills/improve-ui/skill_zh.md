# 改进 UI

对实际控制该产品的统一产品界面进行审计。保留产品的身份，重用现有所有者，并优先选择不支持的发现。仅编写用户选择更改的计划；由另一个代理执行这些更改。

## 边界

- 永远不要修改产品源代码。仅在 `design-plans/` 下创建或编辑文件。
- 不要安装依赖项，运行格式化程序，提交，推送或以其他方式突变工作树。
- 不要更新设计文档。在执行者的计划中记录接受的文档更改。
- 仅在用户提供或明确要求视觉检查时使用渲染证据。
- 使每个计划自包含；其执行者没有来自审计或对话的上下文。

## 1. 选择界面

尊重用户的范围。如果请求很广泛，选择一个可部署的应用程序和一个代表主要产品任务的统一界面系列。说明选择；不要将整个存储库综合为一个产品。

从界面的路由和布局开始。通过组合、共享组件、变体、解析的标记和样式跟踪渲染路径。不要从存储库范围的搜索开始寻找不一致性。

只有在通过渲染、导入、属性、解析的配置、CSS 继承或由界面加载的生成项证明时，才存在连接。共享名称、相似标记、存储库邻近性和概念关系不能建立连接。除非它们参与跟踪的路径，否则排除其他应用程序、预览、配置器、生成注册表、遗留系统和企业变体。

## 2. 重建本地系统

检查 `DESIGN.md`、存储库指南和界面本地设计文档。仅在证明它是当前且控制所选界面的情况下使用源；除非明确接受且当前，否则草稿、提议、迁移和任务列表描述未来的意图。缺少设计文档不是发现。

仅检查与跟踪路径相关的标记、变量、主题、原语、变体和组合。解析别名和变体到它们的定义。仅在存储库说明的情况下将实现分类为本地或遗留。

记录：

```markdown
## 设计语言
- 审计的界面：
- 设计来源：
- 记录的决策：
- 控制所有者和消费者：
- 明确的例外：
```

在 `明确的例外` 下，除非引用的来源明确标识了例外，否则写入 `无文档记录`。

## 3. 证明发现

在应用证明门之前，检查每个跟踪界面的用户界面标签、活动状态呈现、响应分支和兄弟变体是否存在内部矛盾。将结果仅视为候选者。

只有在更正主要改变视觉呈现、界面副本、布局、组件样式或符合记录的设计规则时，发现才在范围内。如果更正主要改变产品行为是否正常工作，则拒绝它。

搜索结果、重复和实现差异产生候选者，而不是发现。仅在存在所有三个证明时保留候选者：

1. **合同** — 引用适用于此属性和范围的约束性设计决策，或在同一任务中用户界面呈现或内容中存在直接矛盾。 “优先选择”、“通常”、“名称”、“遗漏”、“重复”和“例外不存在”不能建立合同。
2. **运行时** — 证明引用的所有者、值或行为通过跟踪的运行时路径到达受影响的界面。不要比较单独的所有者层或生命周期状态。
3. **更正** — 说明证据要求的更改。如果它依赖于现有的标记、变体、原语或示例，请准确命名。如果证据无法确定正确的选择，预期的条件是模糊的，提议包含替代方案，或更正需要发明产品意图，则拒绝候选者。

源可以证明标记、排版、颜色、间距、布局、副本、组件变体、响应式呈现和明确的设计合同违规。它不能将功能行为、状态管理或交互正确性转换为设计发现。层次结构、突出显示、密度、清晰度、可发现性、可用性和感知一致性需要渲染或用户证据。

除非用户明确要求，否则丢弃无障碍性和 HTML/ARIA 语义发现。除非用户请求或产品特定的设计合同控制，否则丢弃损坏的路由、重定向、数据布线、操作失败、元数据、包 API、性能、架构和代码质量发现。

仅在所有证明通过后分配置信度。当证据支持时重用现有所有者；不要仅凭重复创建共享原语。

## 4. 审查发现

在报告之前，重新打开每个引用的来源，并尝试证伪每个候选者。当出现以下情况时删除它：

- 问题与引用的实现不完全匹配。
- 规则不控制该属性和界面。
- 对抗证据表明差异是有效的或故意的。
- 证据支持多个更正。
- 更正发明了产品意图。
- 另一个发现描述了相同的根本问题。

只有通过此过程幸存的发现才能进入表格。

## 5. 报告

按置信度、用户影响、范围和更正成本对幸存的发现进行排序。停止在三个。

使用此结构：

```markdown
## 设计语言
- 审计的界面：
- 设计来源：
- 记录的决策：
- 控制所有者和消费者：
- 明确的例外：

## 发现
| # | 问题 | 证据 | 建议的更改 | 范围 | 置信度 |
| --- | --- | --- | --- | --- | --- |

## 首先改进
<最高杠杆发现及其原因，或无支持的推荐。>
```

证据必须建立合同、运行时关系和确定的界面后果。建议的更改必须包含一个更正。在返回之前删除不支持的或重叠的行。

删除不包含所有必需列（包括置信度）的任何发现。

在 `首先改进` 下，选择一个具有最强证据和最高杠杆的幸存发现。永远不要组合发现。

如果没有任何候选者幸存，在 `## 发现` 下写入 `未找到支持的发现。`，在 `## 首先改进` 下写入 `无支持的推荐。`。

如果发现幸存，停止并询问要将其转换为计划的是哪一个。如果用户已经选择了一个发现或明确请求了描述的改进的计划，则继续使用该范围。如果要求直接修复或改进，提供计划；永远不要实施它。

## 6. 指定选定的更改

阅读 [references/plan-template.md](references/plan-template.md)。为每个选定的更改编写一个计划，而不是为每个症状编写一个。

在编写之前，重新打开每个引用的来源，记录当前提交（如果可用），识别确切的可用原语和示例，并跟踪受影响的界面。用现有的计划进行协调，而不是重复它。

当存储库提供标记或组件合同时，不要发明值。仅在证明现有系统无法表达决策的原因以及哪些消费者应共享它之后，才引入原语。

如果要求协调，重新检查现有计划与当前源和记录的决策，更新过时的证据、受影响的界面和状态。
