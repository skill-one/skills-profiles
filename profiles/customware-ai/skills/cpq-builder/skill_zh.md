# CPQ 构建技能

## 此技能的作用

此技能定义了构建**配置-报价-配置**（Configure-Price-Quote）形工具的模式——即用户配置输入，系统应用规则计算结果，输出为需要审核/批准的格式化交付成果。

CPQ 并非仅限于产品定价。相同的结构模式涵盖：

| 领域 | "配置" | "计算" | "输出" |
|---|---|---|---|
| **设备销售** | 选择产品，选择选项 | 应用加价，计算总额 | 销售报价 PDF |
| **法律计算器** | 输入案例详情（收入，持续时间） | 应用指南公式 | 估算摘要报告 |
| **保险估算器** | 输入保障详情 | 应用费率表 | 保费估算文档 |
| **贷款资格** | 输入财务详情 | 应用贷款标准 | 资格证明信 |
| **福利资格** | 输入个人详情 | 应用资格规则 | 福利摘要 |
| **服务提案** | 选择服务，设定范围 | 应用工时费率 | 服务提案 |

构建器读取此技能，读取特定领域的 `DOMAIN.md` 以获取术语和规则，并生成可工作的原型。`DOMAIN.md` 确定工具是关于起重机报价还是离婚计算；此技能提供适合的结构模式。

**此技能中的模式是默认值，而非强制要求。** 当实际工作流偏离标准的 CPQ 形状——阶段较少，布局不同，输出不同时——请调整模式。每个主要部分都明确命名了偏离情况。

## 客户背景

Customware 的 CPQ 客户涵盖多个领域：工业设备经销商、定制服装和标识店、食品/饮料批发商、专业服务公司（法律、咨询、设计）、IT 和托管服务提供商、建筑和手工业企业、制造商、分销商。CPQ 模式适合所有这些客户。

**此技能中的示例跨多个领域轮换**——工业设备、服务、消费品、软件、定制商品。这是有意为之的。模式是领域无关的；示例通过类比说明。应用此技能时，忽略任何示例中的特定领域，并提取结构模式。您的 `DOMAIN.md` 确定构建的具体词汇、产品、规则和角色。

“单梁起重机需要电机”的规则与“定制连帽衫需要印刷方法”或“托管服务合同需要等级”或“狗粮订单需要包装尺寸”具有相同的形状。规则是“父产品需要子组件选择”。构建该模式；让 `DOMAIN.md` 填充词汇。

### 客户画像

Customware 的 CPQ 客户通常是 **中小企业（5-50 名员工）** 正经历成长烦恼。他们不是从另一个 CPQ 系统迁移。他们从：

- 变得难以管理的 Excel 电子表格（多个选项卡、复制粘贴错误、损坏的公式）
- 需要手动编辑每个客户的 Word 文档报价模板
- 基于电子邮件的审批工作流，老板在一个回复所有线程中批准报价
- 关于哪些产品需要哪些配件的“部落知识”，存在于高级代表的大脑中
- 手动输入定价，由于不一致的折扣而侵蚀利润

原型的任务是感觉**远好于电子表格**，同时又感觉**没有企业过度复杂**。一个使用 Excel 报价 5 年的小团队应该看到原型并立即想到“这快得多”——而不是“这看起来很复杂。”

这种定位塑造了此技能的每个设计决策：

- 内联行编辑是**比较点**。Excel 用户期望可以直接编辑的网格。
- 实时总计很重要。客户一直在公式中做数学；他们期望在更改输入时看到数字更新。
- 角色门控很令人印象深刻。客户从未有过“只有所有者才能批准超过 50K”的软件强制执行——这是一个被打破的口头规则。
- 品牌化报价文档很令人印象深刻。客户一直在手动格式化 Word 文档。
- 客户端门户、AI 建议和电子签名集成**在此阶段并不令人印象深刻**。它们是解决客户尚未遇到的企业复杂性。

为那些厌倦了损坏的 Excel 公式的客户构建，而不是从 Salesforce 迁移的客户。

## 这甚至算是 CPQ 吗？

在应用此技能中的任何模式之前，请确认工作流实际上是 CPQ 形状的。当以下**全部四个**条件都满足时，CPQ 模式适用：

1. **用户收集结构化输入**，这些输入决定了结果（配置选择、客户详情、需求、财务数据、案例详情）。
2. **业务规则或计算逻辑将输入转换为交付成果**（加价公式、指南计算、费率表、资格规则）。
3. **在输入和最终确定之间存在审核或批准关卡**，或者交付成果经过某种利益相关者审核（准备者/审核者模式）。
4. **工作成果感觉像是要交接**——交给客户、内部利益相关者、监管机构、下游系统。

如果标准 1 缺失 → 它是仪表板或显示工具，不是 CPQ。放弃。
如果标准 2 缺失 → 它是数据输入表单，不是 CPQ。放弃。
如果标准 3 缺失 → 它是“收集和交付”——应用 CPQ 模式但跳过批准部分。
如果标准 4 缺失 → 它是个人计算器/实用工具，不是 CPQ。放弃。

**常见误判：**
- “股票报价查看器” — 有“报价”一词但显示工具（标准 1 缺失）
- 没有审核步骤的“税务计算器”——实用工具，不是 CPQ（标准 3 + 4 缺失）
- “产品目录”带价格——显示，不是 CPQ（标准 2 + 3 缺失）
- “反馈表单”——数据输入，不是 CPQ（标准 2 缺失）

如果四个标准不满足，不要强行适配以下模式。使用任务描述和 `DOMAIN.md` 以及前端设计的原则构建。

## 领域类型

大多数 CPQ 形状的工作流属于以下两种领域类型之一。在应用模式之前确定构建的类型：

**产品领域。** 用户配置可销售的产品/服务。定价是核心计算。输出是带行项目、总计、税和条款的报价文档。示例：设备销售、定制服装订单、食品/CPG 批发、服务提案（咨询标书、托管服务）、软件许可、定制包装。

**计算/输入领域。** 用户输入案例/申请人详情。计算应用指南/规则/费率表。输出是带输入、计算值和免责声明的摘要报告。示例：Clarity Legal 的配偶支持计算器、保险估算器、贷款资格、福利资格。

此技能的模式适用于两者。当一个部分或规则是领域特定的，此技能会明确说明。

## 最低标准

每个 CPQ 构建**必须**满足 Tier 1 标准。当 `DOMAIN.md` 指示需要时，构建 Tier 2 标准。Tier 3 功能在完成摘要中提及作为未来工作，但在原型中不构建。

### Tier 1 — 非协商（每个 CPQ 构建）

这些是使原型感觉**远好于 Excel + Word** 的功能。如果任何功能缺失，无论 UI 多干净，构建都是不完整的。

**1. 直接内联行项目编辑。** 电子表格风格的表格，用户可以添加行、编辑任何单元格，并实时更新总计。**不是**“配置表单 → 添加到报价 → 构建报价表 → 编辑”的往返流程。行项目表格就是工作区。见“部分模式”下标准的实现。

**2. 包裹/必需子产品使用适当的配置器模式。** 当父产品需要子组件（例如，“工业单元需要电机选择”、“定制连帽衫需要印刷方法”、“托管服务合同需要等级”、“狗粮订单需要包装尺寸”）时，子选择是配置父产品的一部分。行项目显示父项 + 选定的子项作为一个连贯的条目。**永远不要**两个独立的行项目，用户可能会忘记子项。对于具有 4 个以上配置属性或级联依赖的产品（典型的工业设备、定制商品和通常 3-4 级深的分层服务），使用适当的配置器模式——见“产品配置器模式”下内联展开 vs 侧边栏 vs 全页决策。

**3. 可见地显示约束规则。** 从 `DOMAIN.md` 中来的需要/排除/推荐规则必须对用户可见——而不仅仅是沉默地执行。当用户添加起重机时，UI 显示“电机选择需要（BR-001）”在他们保存之前。当他们尝试添加排除的组合时，UI 显示规则和理由。习惯于 Excel 的客户**从未**有过规则执行——使规则可见是价值的一半。

**4. 折扣堆栈带可见数学。** 当应用折扣时，显示分层计算：
```
列表价格：                  $15,000.00
数量折扣（5%）：           -$750.00
促销折扣（3%）：            -$427.50
─────────────────────────────────────
净价格：                   $13,822.50
```
每个折扣是一行；数学是透明的。习惯于在电子邮件线程中协商折扣但没有审计轨迹的客户需要确切地看到价格是如何确定的。

**5. 实时报价摘要。** 运行总计（小计、税、总计）在用户编辑行项目时实时更新。没有“点击计算”按钮。这是 Excel 来的客户最大的“哇”时刻——总计只是更新。

**6. 品牌化报价文档。** 生成的 PDF/打印视图带有客户的标志、行项目表格、总计、条款和任何必需的免责声明。这个质量标准：它应该看起来像一家真正的企业会发送的报价。

**7. 多级审批路由。** 大多数 SMB 工作流有 2 个以上的审批级别（代表配置 → 经理审核 → 所有者批准）。即使是简单案例也至少有一个审批者和最终签字角色。原型必须显示基于角色的路由，尊重 `DOMAIN.md` 的利益相关者地图。路由通常按请求类型分支——例如，一家公司可能将“定制配置通过高级审核员、检查通过服务经理、维护通过运营经理，所有路径最终由所有者批准。”这种条件多级路由是基本要求。

**8. 多报价管理。** 用户同时有多个报价在处理中。原型必须显示带状态指示器的报价列表，支持过滤/排序，并允许用户点击任何报价进行编辑。**不是**仅单个报价工作区，带“已保存报价”侧边栏列表。

**9. 保存/加载/克隆报价。** 基于 localStorage。用户可以创建新报价、保存它、加载已保存的报价，并克隆现有报价作为类似请求的起点。Excel 用户通过复制选项卡执行此操作；原型提供克隆按钮。

**10. 基于角色的视图和操作门控。** 不同角色看到不同内容。审批者看到批准按钮；准备者不显示。敏感数字（利润、成本）对非审批者角色隐藏。这是客户直观了解的“只有老板才能看到利润”模式，但从未被强制执行。

### Tier 2 — 当 `DOMAIN.md` 说明需要时构建

这些是有价值的功能，但只有在 `DOMAIN.md` 提供明确信号时才值得构建。

- **引导销售**（用于复杂配置的逐步问答）——当 `DOMAIN.md` 描述与客户的发现流程时
- **数量/分层定价**——当 `DOMAIN.md` 提及数量折扣、数量层级或批量折扣时
- **客户端只读报价链接**——当 `DOMAIN.md` 提及通过电子邮件/共享报价给客户时
- **订阅/续订处理**——当领域是 SaaS 类型的具有经常性收入时
- **一个构建中包含多种定价模型**（成本加成 + 目录 + 定制）——当 `DOMAIN.md` 描述混合定价策略时
- **按客户类型区分的报价文档模板**——当 `DOMAIN.md` 描述针对不同受众的不同输出格式时

### Tier 3 — 未来工作（在完成摘要中提及，不构建）

这些属于生产构建，而不是原型。完成摘要应命名它们，以便客户知道接下来会发生什么。

- 从 CRM/电子邮件/电话上下文生成 AI 建议的报价
- 报价版本控制和修订跟踪
- 订阅计费逻辑和按比例分配
- CRM/ERP 集成（在完整栈阶段处理）
- 电子签名集成（DocuSign、HelloSign 等）
- 税引擎集成（Avalara、Vertex）
- 多货币与动态汇率
- 自助服务客户配置门户
- Deal Rooms / 品牌化提案微站点
- 原生移动应用

### 完成摘要模板

每个 CPQ 构建的完成摘要必须包括：

```markdown
## 此原型包含的内容

**Tier 1（始终构建）：**
- [确认每个 Tier 1 功能是否存在，或注明为何遗漏特定功能]

**Tier 2（为此领域构建）：**
- [列出构建的任何 Tier 2 功能及其原因]

## 此原型不包含的内容

这是一个前端原型，演示核心 CPQ 工作流。以下功能将在生产中提供：
- [列出相关的 Tier 3 项目，基于客户可能未来的需求]

要从原型过渡到生产，添加：真实身份验证、CRM/ERP 集成、电子签名、真实 PDF 生成以及上述列出的任何 Tier 3 功能。
```

这设定了诚实的预期，表明更多内容即将到来，同时清楚地说明了交付内容。

## 何时使用此技能

当“是否是 CPQ？”中的四个标准都满足**且**客户的 `DOMAIN.md` 包含：

**经典的 CPQ 信号：**
- 供客户报价/定价的产品或服务
- 配置选项（尺寸、型号、变体、材料）
- 产品之间的依赖关系（需要、推荐、排除）
- 基于加价或利润的定价（成本加成、供应商列表 + 百分比）
- 报价或提案工作流（草稿 → 审核 → 批准 → 发送）

**更广泛的“配置-计算-输出”信号：**
- 带有审核/交接步骤的计算器、估算器或评估工具
- 引导式输入表单，输入驱动计算输出
- 多步骤数据收集，应用规则产生结果
- 输出文档（报告、摘要、估算、提案）
- 准备者/审核者工作流（客户填写 → 专业人士审核）

**不要使用此技能当**领域主要是库存跟踪（使用 ERP 技能）、带有现场跟踪和支付的不断进行的项目执行（使用 trades-builder）、在线产品销售（使用电子商务技能）或客户关系管理（使用 CRM 技能）。

## 模板合同

在开始构建之前，了解模板为您提供了什么以及此技能添加了什么：

**模板 (`app/layouts/MainLayout.tsx`) 随附：**
- `SidebarProvider`, `Sidebar`, `SidebarContent`, `SidebarInset`, `SidebarTrigger` — 已连接
- `SidebarContent` 是**空的**——这是您的着陆区
- 头部中的一个品牌槽位（标志占位符 + 公司名称）
- `ModeToggle` 和用户菜单在头部的右侧集群

**此技能填充：**
- `SidebarContent` — 使用适合所选布局的部分导航填充
- 品牌槽位 — 使用来自 `DOMAIN.md` 的客户标志和公司名称
- 头部的右侧集群 — 在具有多个角色的工作流中，在现有用户菜单之前添加一个角色切换器 `DropdownMenu`
- `<Outlet />` 在 `<main>` 中 — 通过每个部分的路线组件填充

**此功能不执行：**
- 添加第二个 `Sidebar` 组件。只有一个侧边栏。
- 将品牌瓦片放入 `SidebarContent` 中。品牌仅存在于页眉中。
- 在路由组件内部挂载 MainLayout。路由在 `<Outlet />` 中渲染；布局是父级。在路由内部挂载 MainLayout 会导致重复的侧边栏/页眉。
- 重新连接 `SidebarProvider` 或替换可折叠行为。

如果工作流不适合侧边栏布局（请参阅下方的布局模式替代方案），构建可能会使用不同的外壳。在完成摘要中记录偏差。

## 区段模式

默认的 CPQ 工作流具有 **三个逻辑阶段**：配置输入、审核/批准、交付文档。默认 UI 根据用户是否受益于单独的“审核/编辑行”阶段，将这些映射到三个或四个区段。

### 默认区段结构（SMB 直接编辑模型）

对于 SMB CPQ，其中一名角色从创建到批准都负责报价（最常见的情况），默认值是 **三个区段**：

1. **编辑报价** — 所有行项目 + 客户详情的直接内联编辑。这是用户花费 90% 时间的主要工作区。行项目内联添加、编辑、删除。客户信息、条款和备注是内联的。右侧或下方显示实时总计。
2. **批准** — 审核和批准操作。显示最终状态，运行门禁检查，并生成批准操作。如果报价之前已批准/修订，可能会显示更改历史记录。
3. **报价文档** — 交付物。只读、可打印、品牌格式化。

这合并了 v4.3 的“配置 → 构建报价”往返流程到一个直接编辑表面。**大多数 SMB CPQ 构建 应该使用此三个区段模型。**

### 四个区段结构（当角色之间存在交接时）

当配置和行项目组装由不同的人完成时（例如，工程师配置 → 销售代表定价 → 经理批准），四个区段是合适的：

1. **配置** — 工程师或技术角色指定产品
2. **构建报价** — 销售角色添加定价、条款、客户信息
3. **批准** — 经理角色批准
4. **报价文档** — 交付物

仅当 DOMAIN.md 描述了每个阶段角色之间真实的交接时，才使用此结构。大多数 SMB CPQ 不需要此功能 — 一个人可以配置、构建和批准。使用三个区段。

### 计算器域区段结构

对于计算器/输入域（Clarity Legal 模式）：

1. **提交详情** — 输入表单（面向客户）
2. **计算** — 计算结果（自动生成自输入）
3. **律师审核** — 审核者面向的批准（面向律师）
4. **最终报告** — 交付输出

结构模式相同；标签和组件适应该域。

### 偏差

**跳过“批准”** — 当工作流没有审核门禁（自助流程）时。编辑报价 → 文档。
**跳过“报价文档”** — 当交付物不是文档时（推送到系统、内联结果、确认页面）。
**在编辑报价之前添加“发现/输入”** — 当工作流在配置之前有一个发现阶段时。
**选择与实际工作流匹配的区段数量。** 不要填充到四个。不要缩减以适应。

### 编辑报价区段 — 直接内联编辑（Tier 1 必须的）

编辑报价区段使用 **类似 Excel 的行项目表格** 作为主要工作区。这对于产品 CPQ 是非协商的。

**必须行为：**

- 每个行项目是表格的一行
- 单元格是内联可编辑的 — 点击单元格，编辑值，总计更新
- 通过表格下方的“+ 添加行”按钮添加新行（或用户点击空占位符行时自动添加）
- 通过行操作菜单删除行（垃圾桶图标、“删除”选项）
- 通过行操作菜单克隆行（“复制”选项）
- 每行计算总计（数量 × 单价 - 折扣）
- 脚部行跨所有行计算小计
- 折扣堆栈出现在小计下方（如果适用）
- 税行出现在折扣下方（如果 DOMAIN.md 提及税）
- 总计在底部加粗显示

**必须的列（产品域）：**

| # | 描述 | 配置 | 数量 | 列出价格 | 折扣 | 净价格 | 行总计 | 操作 |
|---|---|---|---|---|---|---|---|---|

描述列显示产品名称。配置列显示所选选项（例如，“高级层 — 50 用户”或“三重混纺，DTG 打印”）。对于具有必需配置的产品（捆绑/必需子模式），点击行会打开配置器抽屉/弹出窗口，用户在其中选择选项，然后才会提交行。配置选择后内联显示，并且可以通过再次点击它进行编辑。

**捆绑/必需子产品必须行为：**

当 DOMAIN.md 描述了需要子组件的父产品时 — 例如，“工业单元需要电机选择”、“定制连帽衫需要打印方法”、“管理服务合同需要层”或“狗粮订单需要包装尺寸”：

- 添加父产品会自动提示输入必需的子产品
- 行项目显示为一个连贯的条目："[父产品] — [必需子产品] — [变体]"
- 价格汇总：父产品基础价格 + 子产品附加费
- 用户在未选择必需子产品之前无法保存行
- 显示可见规则指示器："[组件名称] 选择必需 (BR-001)"

**约束规则必须行为：**

当 DOMAIN.md 有需要/排除/推荐规则时：

- “需要”规则在满足之前会阻止保存；内联显示“需要：[解释]”
- “排除”规则会阻止无效组合；内联显示“不能将 X 与 Y 组合，因为 [理由]”
- “推荐”规则作为软提示显示；显示“客户通常与此添加 Z。添加？”
- 每个规则显示其规则 ID（BR-001、BR-002），以便用户可以追溯到来源

这种可见规则执行是来自 Excel 的客户最大的“哇”时刻之一。使其突出显示。

### 产品配置器模式

当产品有多个配置属性（3+ 决策）或配置级联（第 1 级选择决定第 2 级选项，第 2 级选项决定第 3 级等）时，单元格内的下拉列表模式不够用。用户需要一个真正的配置器。

实际产品配置通常深入 3-4 级，跨越许多域：

- **工业设备**：类型 → 容量 → 电机 → 起重机 → 控制
- **定制服装**：服装样式 → 面料 → 尺寸集 → 打印/刺绣方法 → 完成
- **IT 服务**：服务层 → 用户数量 → 模块 → SLA 层级 → 集成
- **食品/CPG 批发**：产品系列 → 风味或变体 → 包装尺寸 → 箱数量 → 冷/常温运输
- **专业服务**：参与类型 → 范围层 → 团队组成 → 持续时间 → 交付格式
- **定制标志/包装**：基材 → 尺寸 → 完成工艺 → 打印方法 → 安装硬件

每一级都限制下一级。选择一个 5 吨工业单元 → 只有某些电机适用 → 只有某些控制器匹配。选择三重混纺连帽衫面料 → 只有某些打印方法兼容 → 只有某些完成选项。选择高级服务层 → 解锁某些模块 → 需要更高的 SLA。形状是相同的。DOMAIN.md 告诉代理实际配置了什么。

对于这种深度的配置，三种模式是合适的，根据配置复杂性选择：

#### 模式 A — 内联可展开行（2-4 属性，无级联）

当产品有少量独立属性（例如，数量、颜色、尺寸或一个配置选择）时，行项目内联展开以显示它们。点击行 → 展开显示属性选择器 → 填写它们 → 行折叠，配置在配置列中总结。

```
┌─────────────────────────────────────────────────────────────┐
│ 1  [产品名称]    [变体 ▾]    1   $X,XXX.XX  ...     │  ← 折叠
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ 1  [产品名称]    [变体 ▾]    1   $X,XXX.XX  ...     │
│    ┌───────────────────────────────────────────────────┐    │  ← 展开
│    │ 变体:      ( ) 选项 A    ( ) 选项 B        │    │
│    │ 数量:     [  1  ]                             │    │
│    │ 描述:     [                              ]    │    │
│    └───────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

使用条件：

- 总计 2-4 个属性
- 属性是独立的（无级联依赖）
- 展开时，所有属性在约 200px 的垂直空间内视觉上适合

符合模式 A 的产品示例：一件带有尺寸和颜色的 T 恤，一个服务附加项带有小时和费率，一个软件许可证座位数，一个批发箱数量选择，一个带有一种完成工艺的印刷横幅。

#### 模式 B — 带垂直步骤器的侧边抽屉（4-7 属性，允许级联）

当配置有级联依赖或 4-7 个属性时，点击行 → 从右侧滑入覆盖约 40% 屏幕的侧边抽屉。抽屉在其左侧有一个垂直步骤器，显示每个配置级别。

```
                           ┌────────────────────────────────┐
                           │ 配置 [产品]                    │
                           │                                │
                           │ ●━━━ 第 1 步：基础             │
                           │ │    [所选值]                   │
                           │ │                              │
                           │ ●━━━ 第 2 步：尺寸             │
                           │ │    [所选值]                   │
                           │ │                              │
                           │ ◉━━━ 第 3 步：核心组件         │
                           │ │    [ 选项 A ]  [ 选项 B ]   │
                           │ │                              │
                           │ ○━━━ 第 4 步：依赖选择         │
                           │ │    (先完成第 3 步)            │
                           │ │                              │
                           │ ○━━━ 第 5 步：完成工艺         │
                           │                                │
                           │           [取消]  [保存]     │
                           └────────────────────────────────┘
```

抽屉行为：

- 抽屉内的垂直步骤器（不在主应用侧边栏内）
- 步骤在其依赖满足时是可点击的；未满足时灰色显示
- 每个步骤的内容出现在抽屉内的步骤器右侧
- 级联依赖：更改上游选择会使下游选择无效并清除（带确认吐司：“更改 [上游] 将重置 [下游] 选择”）
- “保存”将配置提交到行项目；“取消”放弃
- 行项目在配置列中显示组装的配置摘要

这是真正级联配置的模式。符合模式 B 的示例：带有类型/容量/电机/控制的工业设备，带有服装/面料/打印方法/完成的定制服装，带有层/用户/模块/SLA 的 IT 服务，带有基材/尺寸/结构设计/打印/完成/数量/运输的定制标志。抽屉为配置器提供空间，同时不将用户从报价工作区上下文中移除。抽屉内的垂直步骤器使级联可见，而不会消耗应用级导航。

为什么使用抽屉而不是模态框：

- 抽屉比模态框感觉不那么中断
- 用户仍然可以看到左侧的行项目表格作为上下文
- 抽屉可以通过点击外部关闭（避免了模态框风格的“关闭前保存”摩擦）
- 抽屉与 React Router 很好地组合 — 作为路由打开，关闭返回父级

#### 模式 C — 全页配置器（8+ 属性，复杂级联）

当配置确实复杂时 — 8+ 属性，多阶段级联，需要图表或可视化 — 配置器值得它自己的页面。点击“配置” → 导航到 `/quotes/{id}/lines/{lineId}/configure` → 全页，顶部有水平步骤指示器，中间是配置主体，右侧是摘要/预览轨道。

```
┌──────────────────────────────────────────────────────────────────┐
│ ← 返回报价                                                  │
│                                                                  │
│ ●━━━━━━●━━━━━━●━━━━━━◉━━━━━━○━━━━━━○                            │
│ 第 1 步  第 2 步  第 3 步  第 4 步  第 5 步  审核中                   │
│                                                                  │
│ ┌─────────────────────────────────────┬──────────────────────┐  │
│ │                                     │ 已选择：             │  │
│ │  配置内容当前步骤                       │ 第 1 步：[值]      │  │
│ │                                     │ 第 2 步：[值]      │  │
│ │                                     │ 第 3 步：[值]      │  │
│ │                                     │ 第 4 步：(选择中)  │  │
│ │                                     │                      │  │
│ │                                     │ 运行价格：           │  │
│ │                                     │ $X,XXX.XX            │  │
│ └─────────────────────────────────────┴──────────────────────┘  │
│                                                                  │
│                          [返回]  [继续 →]                    │
└──────────────────────────────────────────────────────────────────┘
```

全页是唯一适用于真正复杂配置的模式。顶部水平步骤指示器在这里工作（在类似向导的流程中），而在报价详情级别是错误的 — 因为在这里用户确实是在一次一步地做，然后才移动到下一步。

使用条件：

- 8+ 属性
- 配置涉及视觉元素（图表、尺寸、照片、颜色样本、布局预览）
- 配置超过 30 秒 — 足够值得一个专门的关注表面
- 配置结果足够重要，值得“确认前审核”步骤

符合模式 C 的示例：带有几十个柜子、表面、电器和完成工艺决策的定制厨房；带有车架、传动系统、车轮、刹车、配件、颜色的可配置自行车；带有模块、用户层、集成、支持级别、期限长度的企业软件合同；带有基材、尺寸、结构设计、打印、完成、数量、运输的定制包装订单。

#### 选择模式

```
IF 产品有 2-4 个独立属性，无级联：
  → 模式 A：内联可展开行

IF 产品有 4-7 个属性，级联依赖，配置 <30 秒：
  → 模式 B：带垂直步骤器的侧边抽屉

IF 产品有 8+ 属性，视觉/图表组件，>30 秒：
  → 模式 C：带水平步骤指示器的全页配置器

WHEN IN DOUBT:
  → 模式 A 对于看起来简单的产品
  → 模式 B 对于工业设备、带选项的服务
  → 模式 C 保留给真正复杂的配置器
```

#### 级联依赖规则

对于模式 B 和 C，当配置级联时：

1. **在未选择上游选项之前，将下游步骤显示为禁用状态**。如果步骤2为空，则不允许用户点击步骤4。
2. **当上游选择发生变化时**，清除下游选择并显示确认信息：“将容量从5吨更改为10吨将重置电机和起重机的选择。继续？”
3. **在每个步骤中显示规则依据**：“根据您选择的5吨容量（BR-007）过滤可用电机。”使过滤规则可见。
4. **当只有一个选项时自动选择**：如果级联缩小为一个有效选项，则预先选择它并注明“(仅基于先前选择的可选选项)”。

这使得级联感觉更智能，而不是令人困惑。习惯使用Excel的客户通常在脑海中都有这些规则——“如果尺寸较大，则不能使用基本组件”、“如果是高级服务层级，则包含嵌入式支持”、“如果是食品级基材，则仅适用水性油墨”——明确显示规则比默默执行更令人印象深刻。

#### 项目中的配置摘要

在配置器提交（抽屉保存、全页确认）后，项目行显示组装的配置在配置列中。对于3-4层深的配置，这可能变得很长：

```
[工业设备示例]
工业起重机 — 5吨，40英尺跨度
└─ 标准电机，类型2起重机，480V控制， festoon系统

[定制服装示例]
高级连帽衫 — 三重混纺，M-XL尺码
└─ DTG印刷，4色正面，袖口刺绣，聚乙烯袋

[IT服务示例]
管理服务 — 高级层级，50用户
└─ 安全模块，备份模块，4小时SLA，Slack集成
```

将其显示为紧凑的摘要文本，并提供“编辑配置”链接以重新打开配置器。不要尝试在项目行表格中将每个属性作为单独的列显示——这无法扩展到2-3个属性之外。

## 折扣堆栈模式（应用折扣时必须强制执行层级1）

当DOMAIN.md提到任何形式的折扣（数量、促销、手动、协商）时，构建必须将折扣显示为分层、透明的计算。

**必须显示的数学计算：**

```
列表价格（5 × $15,000）：       $75,000.00
─────────────────────────────────────────
数量折扣（5%）：              -$3,750.00
促销折扣（3%）：             -$2,137.50
手动折扣（$1,000）：           -$1,000.00
─────────────────────────────────────────
净价格：                       $68,112.50
HST（13%）：                         $8,854.63
─────────────────────────────────────────
总计：                           $76,967.13 加元
```

**必须的行为：**

- 每个折扣是总计堆栈中的单独一行
- 每一行显示：折扣类型、百分比或金额、删除的金额
- 折扣按堆栈顺序应用（数量 → 促销 → 手动）
- 手动折扣如果超过DOMAIN.md的阈值，则触发审批路由
- 用户可以看到被删除的内容和原因；公式中没有任何隐藏的内容

**折扣审批阈值：**

当DOMAIN.md描述折扣审批规则（“折扣超过15%需要经理审批”）时，原型必须执行这些规则：

- 折扣低于阈值 → 用户可以无需审批即可应用
- 折扣在/高于阈值 → 用户可以应用，但报价进入“待审批”状态
- 审批路由路由到在该折扣级别授权的角色

这是SMB企业最常见的“我们失去利润”的投诉。在UI中显示规则具有高价值。

## 多层级审批链模式（必须强制执行层级1）

大多数SMB CPQ工作流有2个以上的审批层级。原型必须反映这一点。

### 审批链定义

DOMAIN.md在利益相关者地图中描述审批人。原型从此地图派生审批链：

- **单一审批人** → 简单门禁（“待审批来自[所有者]”）
- **顺序审批人** → 链（“待审批来自[销售经理]，然后[所有者]”）
- **条件审批人** → 基于报价属性的路由（“路由到[审阅者A]用于标准配置，[审阅者B]用于服务请求，[审阅者C]用于维护”）

### 审批链UI

显式显示链，以便用户了解报价的位置和下一步是什么：

```
报价状态：待审批
─────────────────────────────────────────
✓ 提交人[销售代表]              (May 5, 2:30 PM)
✓ 审批人[销售经理]            (May 5, 3:15 PM)
○ 待审批来自[财务主管]
○ 待最终确认来自[所有者]
```

每个审批人：
- 在他们的队列中看到报价（过滤列表视图：“等待我的审批”）
- 可以批准、拒绝或请求更改
- 他们的操作推进或中断链
- 被拒绝/更改的报价返回到前一个审批人并附有备注

**构建必须满足的要求：**

- 审批链自动从DOMAIN.md的利益相关者地图派生
- 角色切换器允许用户以任何审批人的身份查看队列外观
- 多报价列表中的“等待我的审批”过滤器显示待审批的活跃角色报价
- 审批操作更新链状态并触发toast确认
- 拒绝/更改捕获的评论对下一个/前一个角色可见

### 审批路由规则

当DOMAIN.md描述路由规则时——例如，“维护请求路由到服务经理，检查请求路由到现场主管”——原型实现路由。示例逻辑（使用DOMAIN.md替换的占位符名称）：

```javascript
// 从DOMAIN.md利益相关者地图派生的示例路由逻辑：
// - 标准报价：路由到[销售经理]
// - 检查请求：路由到[现场主管]
// - 维护请求：路由到[服务经理]
// - 所有报价最终由[所有者]确认

function getApprovalChain(quote) {
  const chain = [];
  
  if (quote.requestType === 'inspection') {
    chain.push({ role: 'inspection-reviewer', name: '[现场主管]' });
  } else if (quote.requestType === 'maintenance') {
    chain.push({ role: 'maintenance-reviewer', name: '[服务经理]' });
  } else {
    chain.push({ role: 'sales-reviewer', name: '[销售经理]' });
  }
  
  chain.push({ role: 'final-approver', name: '[所有者]' }); // 最后总是最终确认
  return chain;
}
```

在实际构建中，用DOMAIN.md利益相关者地图中的真实名称替换占位符名称。原型在批准部分明确显示链，以便用户可以看到路由逻辑。这是SMB客户中最有价值的特性之一——他们以前从未有过自动路由。

## 布局模式

默认布局是**列表/详细信息**，因为SMB CPQ用户总是有多个报价在处理中。他们需要查看他们的队列并深入单个报价。

### 默认：列表/详细信息布局

```
+----------+--------------------------------+
|          | [报价列表]                     |
| 筛选器  | 行（状态徽章）                 |
| 快速    | 行                            |
| 筛选器  | 行                            |
|          |                                 |
|          | + 新报价                       |
+----------+--------------------------------+
```

当用户点击一个报价时，他们导航到详细信息路由：

```
+--------------------------------------------------------------+
| 标题：[公司名称] | Q-2026-0001 | 状态：草稿         |
| ← 所有报价                                                  |
+--------------------------------------------------------------+
| [编辑报价] [批准] [报价文档] 标签                           |
| ──────────────────────────────────────────────────────────── |
|                                                               |
| [活动部分内容——默认为项目行表格]                            |
|                                                               |
| [实时总计在右侧或下方——可折叠]                            |
+--------------------------------------------------------------+
```

**为什么列表/详细信息是默认的：**

- 客户来自Excel，他们在不同的报价中使用多个选项卡/文件
- 他们需要一目了然地查看所有在处理中的报价（队列视图）
- 他们需要筛选器：按状态、按客户、按审批人、按日期
- 深入一个报价不应丢失队列上下文（后退按钮始终有效）
- 审批队列本质上呈列表形状（“显示我等待我审批的所有内容”）

**列表视图中的侧边栏**：筛选器、角色切换器、“+ 新报价”按钮，可选保存的筛选器快捷方式。

**详细信息视图中的侧边栏**：四部分/三部分导航（编辑报价 / 批准 / 报价文档）。或者使用详细信息视图中的顶部标签代替侧边栏——两者都接受；根据视觉密度选择。

**右侧轨道/实时摘要**：可折叠。默认展开在“编辑报价”（总计是基本上下文）。默认折叠在“报价文档”（文档就是摘要）。

### 替代方案：单个报价布局

当DOMAIN.md描述用户一次只处理一个报价的工作流程（CPQ中很少见，但某些计算器有效）时，使用不带列表视图的单页布局。报价就是页面。

### 替代方案：计算器样式布局（计算器域）

对于计算器/输入域，其中计算是主要功能：

```
+--------------------------------------------------------------+
|  [单列表单]                                                   |
|                                                               |
|  个人详细信息                                               |
|    [字段行]                                                  |
|                                                               |
|  财务详细信息                                               |
|    [字段行]                                                  |
|                                                               |
|  ─────────────────────────────────────                       |
|                                                               |
|  计算结果                                                  |
|    [内联输出面板——用户输入时更新]                           |
|                                                               |
|  [提交以供审查]                                              |
+--------------------------------------------------------------+
```

Clarity Legal面向客户的流程使用此布局。律师面向的审查流程使用列表/详细信息。

### 布局决策规则

```
IF用户并行管理多个在处理中的工作流（几乎所有CPQ）:
  → 列表/详细信息布局（默认）

IF计算是主要功能并且可以与输入内联显示:
  → 计算器样式布局

IF用户一次只处理一个项目（罕见）:
  → 单页布局

IF不确定:
  → 列表/详细信息布局
```

### 侧边栏行为

使用列表/详细信息时，侧边栏根据用户是否在列表视图或详细信息视图中而变化：

**列表视图**：筛选器、角色切换器、“+ 新报价”按钮、可选保存的筛选器快捷方式。

**详细信息视图**：部分导航（编辑报价 → 批准 → 报价文档）、顶部返回列表链接。

使用`SidebarContent`进行两者——根据路由交换内容，不要添加第二个侧边栏。这是一个常见的实现错误：代理在详细信息路由中挂载MainLayout，导致出现重复的侧边栏。不要这样做。

### 右侧轨道可折叠

报价摘要面板是一个**可折叠的右侧侧边栏**，而不是固定面板。使用shadcn的`Sidebar`组件，`side="right"`，或`Sheet`用于离屏行为。

默认状态按部分：
- 编辑报价：展开（总计是基本）
- 批准：展开（最终审查需要上下文）
- 报价文档：折叠（文档就是摘要）

用户可以通过标题触发按钮随时切换。

## 报价生命周期指示器

一旦用户进入报价的详细信息视图，他们需要定位自己：这个报价在其生命周期中处于什么位置，以及如何在其不同视图（编辑、文档、审批）之间导航？

这两个是不同的关注点，需要不同的表示形式。

### 关注点1 — 工作流状态（“这个报价在其生命周期中处于什么位置？”）

报价通过状态移动：草稿 → 等待审批 → 已批准 → 已发送（或已拒绝）。用户需要随时看到当前状态。

**默认模式：页面标题附近的状态徽章。**

在报价参考编号旁边放置一个`Badge`，显示当前状态。按状态颜色编码：
- 草稿 → 轮廓/灰色
- 等待审批 → 默认/琥珀色
- 已批准 → 次要/绿色
- 已拒绝 → 破坏性/红色
- 已发送/已最终确定 → 次要/蓝色

这是最低要求。它已经在v4.5构建中存在并且有效。

**可选增强：水平状态流。**

对于生命周期有4个以上可见状态且客户受益于一目了然进度的工作流程，在页面标题下方添加一个水平状态行：

```
●━━━━━━━━━━━━━●━━━━━━━━━━━━━◉━━━━━━━━━━━━━○━━━━━━━━━━━━━○
草稿         [审阅者]     [审批人]     已批准      已发送
（完成）    （完成）     （当前）
```

使用填充圆圈表示已完成状态，轮廓圆圈带填充表示当前，空圆圈表示未来。在审批等待阶段显示审批人姓名，以便用户看到谁正在持有报价。

当生命周期简单（3个状态或更少）时，可以跳过——单独的状态徽章就足够了。添加3步状态流程只是装饰，不是信息。

### 关注点2——视图导航（“如何切换编辑和文档视图？”）

用户需要在可编辑的工作区、只读的客户面文档以及其他视图（审批队列、历史记录）之间切换。这些是同一报价的*同级视图*，而不是顺序阶段。

**默认模式：详情页顶部的标签页。**

将`标签页`放在页面标题下方、主内容区域上方：

```
[编辑报价]  [文档]  [审批]  [历史记录]
═══════════
```

活动标签页下方有下划线或填充。非活动标签页可点击。这是正确的模式，因为：

- 标签页表示“同级视图”——没有隐含的顺序
- 切换只需一键，无需模态或页面过渡
- 每个标签页可以显示计数或状态徽章（“审批（1个待处理）”、“历史记录（5个）”）
- 禁用状态有意义——“文档”可以禁用，直到存在行项目
- 它可以舒适地扩展到6个标签页；超过这个数量，工作流可能阶段太多

**标签页可用性规则：**

- **编辑**——始终可用
- **文档**——至少存在一个行项目时才可用（否则文档为空）
- **审批**——仅在报价处于审批状态或具有审批历史时可见
- **历史记录**——当报价有任何状态变更（编辑、审批、拒绝）时可见

不要显示空标签页。不要显示“即将推出”的标签页。

### 不使用标签页的情况——使用垂直步骤条

当出现以下情况时，应使用垂直步骤条（左侧轨道中的编号步骤，如v4.3构建）：

- 工作流有**4个或更多真正的顺序步骤**，且不能乱序执行
- 用户需要**按顺序执行每个步骤**再进入下一步（向导，而不是工作区）
- 有**自然的结束**——用户完成第N步后报价即完成

大多数CPQ不满足这些条件。报价是工作区——用户会重新访问、编辑、稍后返回。标签页符合这种心智模型。应用级别的垂直步骤条强制将向导心智模型应用于工作区工作流，并产生视觉问题（步骤标签被挤压、侧边栏空间使用不当）作为副作用。此技能的早期版本犯了这种错误；当前模式将垂直步骤条保留在配置器抽屉中，而不是应用外壳。

将垂直步骤条保留为真正的向导：入职流程、一次性设置、企业多阶段交易（每个阶段由不同人员负责）。

### 不使用标签页或步骤条的情况——仅使用面包屑

面包屑显示层级/位置，而不是工作流阶段。当用户在*树状结构*下导航（报价 › Q-2026-0007 › 行项目）时使用面包屑，但不要将其作为阶段导航的替代品。

实际上，两者可以共存：顶部显示位置的面包屑，下方显示当前项目的同级视图标签页。

### 工作流过于简单的情况

某些工作流只有一个表面（计算器式单页面布局）。不需要标签页。页面就是工作。状态徽章本身传达状态。报价文档在请求时以单独的路由或模态打开。

不要仅为了填充布局而添加标签条。如果只有一个标签，那就没有标签。

### 总结

| 工作流形状 | 模式 |
|---|---|
| 多视图工作区（编辑/文档/审批） | **标签页**在详情页顶部 + 标题附近的状态徽章 |
| 多视图工作区 + 复杂生命周期（4个或更多状态） | **标签页** + 状态徽章 + 水平状态流程行 |
| 真向导（顺序步骤） | **垂直步骤条**在左侧轨道 |
| 层级导航 | **面包屑**（如果存在同级视图也与之配对） |
| 单页面工作流 | **状态徽章**仅 |

大多数产品CPQ使用第1行模式——多视图工作区。编辑/文档/审批的标签页，标题附近的状态徽章。

## 报价文档（最终输出）

交付物。对于产品域，这是面向客户的报价PDF。对于计算器域，这是摘要报告。

将其视为真实文档，而不是摘要卡片。**质量标准：**如果你不希望将此内容作为“报价/报告”通过邮件发送给客户而感到尴尬，那么它就没有完成。

### 布局（从上到下）

**1. 文档标题栏**——两列：
- 左侧：品牌标志（带onError回退到带色标的姓名方块——绝不能是裸img标签）。公司名称。公司地址。
- 右侧：文档标题（“报价”、“估算”、“摘要报告”等）。参考编号（自动生成，例如“Q-2026-0001”）。文档日期。如适用，有效期。

**2. 准备接收方信息**——接收方姓名、联系邮箱、客户公司。视觉权重。

**3. 内容块：**

对于产品域：行项目表格。
| # | 描述 | 配置 | 数量 | 单价 | 行总价 |

对于计算器域：输入表格 + 结果表格。（见Clarity Legal模式。）

**4. 总计/摘要块：**

产品域——右侧对齐的总计堆栈，包含完整折扣计算：
```
小计：                         $75,000.00
数量折扣（5%）：              -$3,750.00
促销折扣（3%）：               -$2,137.50
─────────────────────────────────────
净小计：                     $69,112.50
HST（13%）：                   $8,984.63
─────────────────────────────────────
总计：                        $78,097.13 加元
```

计算器域——突出显示主要计算值或值范围。三卡布局（低/中/高）突出显示主要值，适用于范围。

**5. 条款 / 免责声明块：**

产品：付款条款、货币、有效期。
计算器：来自DOMAIN.md的强制性法律/监管免责声明。

**6. 审批链块**——显示审批历史：
```
已批准：
  ✓ [审阅者姓名]（销售经理）——2026年5月5日
  ✓ [审阅者姓名]（财务）——2026年5月6日
  ✓ [审阅者姓名]（所有者）——2026年5月6日
```

这对客户来说很印象深刻——证明报价经过了正常渠道。

**7. 状态徽章**——草稿 / 等待审核 / 已批准 / 已最终确定。可见。

**8. 页脚**——小字打印、联系信息、如域要求的签名行。

### 只读

文档视图上没有编辑控件。仅有的可用操作：“返回编辑报价”、“打印”、“下载PDF”（原型中为占位符操作，显示toast）。

## RBAC行为

当工作流有多个角色时：

- 使用DOMAIN.md用户角色或利益相关者地图中的角色种子localStorage
- 角色切换器是头部的一个`DropdownMenu`。触发器中显示活动角色 + 徽章
- **视图门控：**不同角色默认看到不同的列表过滤器（审批者“等待我的审批”；准备者“我的草稿”）
- **操作门控：**只有被授权批准的角色才显示批准按钮
- **字段门控：**敏感数字（成本、利润率）对非审批者角色隐藏
- **路由可见性：**当角色处理特定工作类型时，在活动时显示相关路由信息

当DOMAIN.md只描述一个角色或没有角色时，省略角色切换器。不要凭空编造角色来填充UI。

当角色缺乏权限时，操作导向的提示信息：

- ❌ 禁用按钮（神秘——用户不知道原因）
- ✓ “切换到[审批者角色]角色以[操作]”（用于带角色切换器的原型）
- ✓ “此操作需要[审批者角色]。请联系[name]获取批准。”（用于生产）

## 确定性映射规则

### 域类型检测

```
INSPECT DOMAIN.md:
  IF 实体注册表中有带价格/选项/配件的产品：
    → 域类型：产品
  ELSE IF 实体注册表中有带规则的输入字段且DOMAIN.md有指南/公式：
    → 域类型：计算器
  ELSE IF 两者都有：
    → 混合（罕见——选择主导的）
  ELSE：
    → 模糊——在完成摘要中记录，默认为产品
```

### 部分计数决策

```
EVALUATE工作流转接：
  IF同一角色执行配置 + 行管理 + 审批：
    → 3个部分：编辑报价、审批、报价文档（SMB默认）
  IF配置与行管理由不同角色执行：
    → 4个部分：配置、构建报价、审批、报价文档
  IF不存在审批门控：
    → 跳过审批部分
  IF交付物不是文档：
    → 用适当的输出替换报价文档（确认、推送到系统、内联结果）
```

### 布局决策

```
基于工作流选择：
  IF用户并行管理多个报价（几乎所有CPQ）：
    → 列表/详情布局（默认）
  IF计算是主要功能，简单输入/输出：
    → 计算器式布局
  IF单项目工作流（罕见）：
    → 单页面布局
```

### 实体→可配置项映射

```
FOR每个DOMAIN.md实体注册表中的实体：

  产品域：
  WHERE实体是可销售的产品/服务/零件：
    → 创建config.data.products[]条目
    → 设置id、name、category、basePrice、pricingSource
    → 从实体的“可变属性”设置options[]
    → 从“必须包含”关系设置requiredChildren[]（例如，起重机需要电机）
    → 从“可以包含”关系设置optionalChildren[]

  计算器域：
  WHERE实体是输入字段/参数：
    → 创建config.data.inputSections[]条目
    → 将相关输入分组到部分
    → 设置field id、label、type、required、validation
```

### 关系→规则映射

```
FOR每个关系：
  "requires" → config.rules[] (类型：requires，严重性：error，表面可见)
  "recommends" → config.rules[] (类型：recommends，严重性：info，作为建议显示)
  "excludes" → config.rules[] (类型：excludes，严重性：error，阻止无效组合)
  "includes child" → config.products[].requiredChildren[] (捆绑模式)
```

### 折扣堆栈映射

```
FOR每个DOMAIN.md中的折扣类型：
  → 创建config.data.discountTypes[]条目
  → 设置id、label、type（百分比|金额）、rate、条件
  → IF折扣有审批阈值：
      → 创建config.rules[]条目 (类型：approval-required，阈值：X)

示例：
  "10个以上数量折扣5%" → 百分比折扣带数量条件
  "第四季度促销3%" → 百分比折扣带日期条件  
  "超过15%的折扣需要经理批准" → approval-required规则，阈值0.15
```

### 审批链映射

```
FROM DOMAIN.md利益相关者地图和路由规则：
  → 为每个报价类型创建config.approvalChain条目
  → IF存在路由规则（例如，“检查到Dre，维护到Manish”）：
      → 在approvalChain中创建条件路由
  → ALWAYS在DOMAIN.md描述最终审批者时追加
  → 在审批部分可视化显示链
```

### 状态模型→工作流映射

```
IF DOMAIN.md状态模型包含工作流状态：
  → 映射到quote.status枚举（草稿、等待批准、已批准、已拒绝、已最终确定）
  → 映射转换到操作可用性
```

### 品牌化→主题映射

```
→ 从DOMAIN.md项目概述设置config.app.companyName
→ 从brandfetch设置config.app.theme.primaryColor
→ 从brandfetch设置config.app.theme.accentColor
→ 从brandfetch设置config.app.theme.logoUrl（BrandMark中带onError回退）
→ 设置config.app.theme.mode = "light"
```

### 报价设置映射

```
产品域：
→ 设置currency、taxEnabled（仅如果DOMAIN.md提及税）、taxLabel、taxRate
→ 设置defaultTerms、markup、quoteFormat

计算器域：
→ 从DOMAIN.md指南设置formulas
→ 按交付物类型设置outputFormat
→ 从DOMAIN.md设置disclaimers
```

### 角色映射

```
FOR每个DOMAIN.md用户角色中的角色：
  → 创建config.roles[]条目
  → 设置id、label、permissions、viewFilters、fieldVisibility
  → IF角色出现在审批链中 → 标记为审批者
  → IF只有一个角色或没有角色 → 在UI中省略角色切换器
```

### 边缘情况

```
→ IF实体没有价格 → SET pricingSource = "tbd", ADD到openQuestions
→ IF关系理由缺失 → SET message = "[source] [rel] [target] — 未捕获理由"
→ IF实体不可分类 → SKIP, ADD到openQuestions
→ IF DOMAIN.md有Open Questions → COPY到config.metadata.openQuestions
→ IF只有一个角色 → 创建默认角色，省略角色切换器
→ IF没有定价AND域是产品 → SET markup = 0, ADD到openQuestions
→ IF没有计算公式AND域是计算器 → 带占位符公式构建，ADD到openQuestions
→ IF DOMAIN.md提及折扣但没有审批阈值 → 使用15%默认值用于"需要批准"
```

## 业务规则模板

### 产品依赖（硬性要求）
```json
{
  "id": "BR-XXX",
  "type": "requires",
  "trigger": "addItem",
  "condition": { "item.category": "[source_category]" },
  "action": { "suggest": "[target_product_id]", "matchField": "[matching_attribute]" },
  "message": "[来自DOMAIN.md的理由]",
  "severity": "error",
  "surfaceVisibly": true
}
```

### 产品推荐（软性）
```json
{
  "id": "BR-XXX",
  "type": "recommends",
  "trigger": "addItem",
  "condition": { "item.category": "[source_category]" },
  "action": { "suggest": "[target_product_id]" },
  "message": "[来自DOMAIN.md的理由]",
  "severity": "info",
  "surfaceVisibly": true
}
```

### 产品排除
```json
{
  "id": "BR-XXX",
  "type": "excludes",
  "trigger": "addItem",
  "condition": { "item.category": "[source_category]" },
  "action": { "block": "[target_product_id]" },
  "message": "[来自 DOMAIN.md 的理由]",
  "severity": "error",
  "surfaceVisibly": true
}
```

### 组合 / 必选子项
```json
{
  "id": "BR-XXX",
  "type": "requires-child",
  "parent": "[parent_product_id]",
  "child": "[child_product_id_or_category]",
  "selectionMode": "required-one-of",
  "message": "[理由]",
  "severity": "error"
}
```

### 折扣阈值审批门
```json
{
  "id": "BR-XXX",
  "type": "approval-required",
  "trigger": "discountApplied",
  "condition": { "discount.percentage": { "$gte": 0.15 } },
  "action": { "requireApproval": "[approver_role_id]" },
  "message": "超过15%的折扣需要 [approver name] 审批",
  "severity": "warning"
}
```

### 多级审批链
```json
{
  "id": "BR-XXX",
  "type": "approval-chain",
  "trigger": "submitForApproval",
  "chain": [
    { "role": "sales-reviewer", "name": "[Sales Manager]", "condition": { "quote.requestType": "standard" } },
    { "role": "inspection-reviewer", "name": "[Field Supervisor]", "condition": { "quote.requestType": "inspection" } },
    { "role": "maintenance-reviewer", "name": "[Service Manager]", "condition": { "quote.requestType": "maintenance" } },
    { "role": "final-approver", "name": "[Owner]" }
  ],
  "message": "根据请求类型路由至审批人，最终由 [Owner] 审批"
}
```

在实际配置中，将占位符名称替换为来自 DOMAIN.md 的利益相关者映射中的真实名称。

## 垂直预设

| 垂直 | 域类型 | 常用布局 | 关键一级功能 |
|---|---|---|---|
| **制造 / BOM** | 产品 | 列表/详情 | 组合（父项+配件）、折扣叠加、多级审批 |
| **批发 / 分销** | 产品 | 列表/详情 | 数量级（二级）、折扣叠加、客户定价 |
| **服务 / 集成商** | 产品 | 列表/详情 | 设备+人工+材料组合、审批链 |
| **法律 / 合规** | 计算器 | 计算器样式+列表/详情 | 公式计算、强制免责声明、律师审批队列 |
| **金融 / 保险** | 计算器 | 计算器样式+列表/详情 | 利率表、资格规则、范围输出 |
| **评估 / 资格** | 计算器 | 计算器样式 | 评分模型、阈值规则、推荐输出 |

## 完成前的验证

在完成构建前，验证所有一级标准是否满足：

```
[ ] 直接内联编辑 — 可编辑单元格的行项表，无配置后构建的往返流程
[ ] 组合 / 必选子项 — 带有必选子项的父项在单行中处理；配置器模式匹配复杂性（内联/抽屉/全页）
[ ] 约束规则可见 — 需要/排除/推荐以理由和规则ID呈现
[ ] 折扣叠加 — 可见数学计算、分层计算、无隐藏公式
[ ] 实时报价摘要 — 用户编辑时总计实时更新
[ ] 品牌报价文档 — Logo、行项、总计、条款、审批链、专业打印布局
[ ] 多级审批路由 — 链接来自 DOMAIN.md，可视化呈现
[ ] 多报价管理 — 带过滤器的列表视图，可深入详情
[ ] 保存 / 加载 / 复制 — 所有内容持久化到 localStorage
[ ] 基于角色的门控 — 视图过滤、操作门控、敏感字段隐藏
[ ] 报价生命周期指示器 — 导航标签+状态徽章；当状态4+时水平状态流
```

如果任何一级标准缺失，构建不完整。修复后再完成。

```
[ ] 无重复侧边栏 — 通过路由至详情视图验证，计数 Sidebar 组件（应为1）
[ ] 无挂载的 MainLayout 在路由中 — 路由在 <Outlet /> 中渲染
[ ] 在 app.css 和 ThemeProvider 默认中都设置亮模式
[ ] 品牌Mark组件在所有Logo出现的地方使用（无裸 <img>）
[ ] 货币使用 Intl.NumberFormat 并带千位分隔符
[ ] 页脚文本出现一次，不被布局嵌套重复
```

这些是常见的实现问题，会通过 `npm run build` 但会破坏用户体验。
