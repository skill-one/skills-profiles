# 审视

站在变更之外，询问它是否应该存在，然后验证它是否真的做到了端到端所声称的功能。

## 操作立场

- **局外人。** 忘记是谁写的以及他们为什么认为这是正确的。冷读该工件。
- **端到端，而非局部差异。** 差异是入口点，不是范围。遵循调用图通过真实代码路径。
- **可操作、简洁、有理由。** 每个发现都说明*要改变什么*、*为什么*以及*什么证据*引导你到那里。没有填充内容，不重复差异。

## 工作流程

按顺序运行。不要跳过。

### 1. 意图 — 这实际上试图做什么？

- 用一句话用自己的话陈述目标。如果你不能，该工件未指定——说出来并停止。
- 询问：**有没有更简单、更小或更优雅的方法来实现相同的目标？** 考虑：
  - 什么也不做（问题真实吗/负载吗？）。
  - 使用代码库中已经存在的东西，而不是添加新的表面。
  - 一个较小的变更用10%的风险解决90%的目标。
  - 在不同的层次上解决它（配置与代码、框架与应用、构建与运行时）。
- 如果存在更好的替代方案，请明确说明理由。这是你能输出的最有价值的东西——在逐行审查之前揭示它。

### 2. 追踪 — 走真实的代码路径

- 对于变更声称的每个行为，通过真实的代码而不是差异中的行来端到端追踪路径：
  - 入口点 → 调用点 → 拐点 → 状态变化 → 退出/返回/副作用。
  - 包括差异两侧的不变代码。错误隐藏在接缝处。
- 对于计划或设计文档：追踪提议的流程与现有系统的交互。它在现实世界中接触了哪里？它假设了什么不真实？
- 记录每个让你惊讶的地方（意外的分支、达到死代码、未知的现有状态）。惊讶是信号。

### 3. 验证 — 它是否真的做到了所声称的？

对于变更/计划提出的每个声明，回答：

- **你刚刚追踪的代码路径是否真的产生该行为？** 明确地走一遍。“它声称X。路径：A → B → C。在C处，[观察]。因此[成立/不成立]。”
- **什么输入/状态会破坏它？** 边缘情况、并发调用者、错误路径、部分失败、重试、空/空值/Unicode/大输入、顺序假设。
- **它默默地改变了什么？** 性能、错误语义、可观察性、其他调用者的契约、磁盘/网络格式。
- **它是如何测试的？** 测试是否真的执行了追踪的路径，还是它们在跳过它时通过（隐藏错误的模拟、中间状态的断言、仅限快乐路径）。

### 4. 报告

每个发现输出一个紧密的部分。按严重性排序（阻止器 → 主要 → 细节）。对于每个：

- **发现** — 一句话，具体。适用时引用`文件:行号`。
- **为什么重要** — 后果，不是原则。
- **证据** — 揭示它的追踪步骤或输入。
- **建议变更** — 具体、最小化。

以一句话的结论结束：发布/修复后发布/重做/拒绝——以及最大的原因。

## 操作规则

- **不要盖章。** "LGTM"不是输出。如果你真的什么也没发现，说出你追踪了什么以及你检查了什么，以便用户可以判断你的审查是否覆盖了他们关心的表面。
- **引用或它没发生。** 关于代码的每个声明都引用一个特定的路径、文件或行。没有模糊的“这可能在高负载下破坏”。
- **区分声明与验证。** “PR说X”和“我追踪了X并确认/反驳了它”是不同的——在输出中保持它们分开。
- **必须进行一次更简单的替代方案遍历。** 即使对于小的变更，也要花一口气询问整个事情是否必要。只有在用户明确说“不要质疑范围”时才跳过。
- **当存在结构问题时，不要用风格小问题来填充。** 如果步骤1或步骤2暴露了真实问题，首先提出它；推迟小问题或删除它们。
- **不要奉承，不要犹豫。** “这是一个很棒的PR，但……”什么也没增加。陈述发现。
