# 管理层沟通

与书面状态报告具有相同的受众和翻译规则，但**针对渠道**进行了调整——JIRA评论、Slack帖子、异步站会、电子邮件或会议讨论要点。受众了解代码名称，但不了解代码。渠道决定了长度、格式以及页面保留的结构程度。

当工程内容需要向上流动至组织、横向进入产品/发布团队或进入非工程会议时，使用此方法——无论目的地如何。

## 调用时机

- "为管理层/高管/副总裁/总监/产品经理/发布经理写一些内容"
- "为[非技术受众]重写这部分内容"
- "使其非技术化" / "减少技术术语" / "减少行话"
- "发送一个Slack更新/站会笔记/电子邮件" *关于一项工程工作*
- "执行摘要" / "执行摘要" / "领导层更新" / "状态更新"
- "基于工程更新的[会议]讨论要点"

如果渠道不明确，请问一个简短的问题——*"JIRA、Slack、站会还是电子邮件?"*——然后停止。

## 受众——"工程组织领导层"的含义

具有工程知识的非工程师：副总裁、总监、产品经理、发布经理、在提供技术产品的公司中的高管。他们了解产品/框架名称，并交叉引用JIRA键和PR。他们不阅读代码。

他们想要：*现状如何，对客户意味着什么，谁负责，下一步是什么.* 他们不想要：函数级别的错误工作原理。

这不适用于市场营销、财务、面向客户或真正的ELI5受众——他们需要不同的重写。在生成之前标记并确认。

## 语气

**保留。** 产品名称、框架名称、团队拥有的组件名称、JIRA键、PR编号、客户/工作负载标识符（`Tada`、`DeepSpeed`、`PyTorch`、`Llama-2-70B`、`vLLM`、`JIRA-12345`、`PR #5751`）。这些是工程与领导层跟踪之间的桥梁。

**删除。** 函数名称、文件路径、结构字段、提交SHA、代码表达式、环境变量名称、行号、内部数据结构术语（`tadaLaunchPrepare`、`tada/prim.h::syncWaitPeer`、`scratchBuf`、`0e0a6bac`）。这些对受众来说都不是可操作的。

**翻译。** 机制用一到两句话的平实英语因果关系来描述。不是*"内核从`scratchBuf == NULL`读取"*，而是*"GPU最终从未初始化的缓冲区读取，并永远等待一个永远不会到达的信号。"* 翻译时不撒谎——竞争条件仍然是竞争条件；回归仍然是回归。

**不要过度删除。** 工程组织领导层能够流利地阅读概念级的技术词汇——*竞争条件、同步、未初始化的缓冲区、快速路径、解决方案、注册、队列、驱动程序、内核*（在GPU的意义上）。界限在于*概念存在且在此处重要*（保留）和*这是函数/结构/文件/SHA*（删除）。将"竞争"替换为"时间问题"是对读者的轻视。

**偏向**主动语态、具体的主题、简短的段落。*"我们发现了一个错误。Alex编写了修复程序。PR正在审核中。"* 比起*"根本原因已被确定，并已编写修复程序并提交审核。"*

**避免：**

- 不是真正犹豫的犹豫（*"我们相信"、"似乎"、"可能存在"*）。要么陈述，要么不陈述。
- 为了全面性而重复显而易见的内容（*"这个错误在Tada中，Tada用于GPU通信，这对分布式训练很重要，..."*）。
- 告诉领导层如何做他们的工作（*"你应该优先处理"、"这需要在X之前完成"*）。给他们事实；他们决定。
- 工程流程细节：二分法运行、调试迭代、GDB会话。他们关心你发现了它，而不是如何发现它。（例外：当*流程本身*是故事时——*"我们在意识到二分法误导之前浪费了三周"*——然后作为一条学习记录，而不是逐场播放。）

## 渠道形状

相同的内容，不同的外壳。选择与目的地匹配的形状。

### JIRA评论/书面状态报告

完整的结构块。加粗的章节标签。从票证页面轻松扫描。

构建块（根据需要使用尽可能多的）：

- **状态/TL;DR。** 一行加粗。读者可以在这里停止并得到正确的答案。*"修复程序待合并。"* / *"根本原因未知——正在调查。"* / *"阻塞供应商。"* / *"客户可见回归在7.2中；正在回滚。"*
- **影响。** 谁受到影响，程度如何，他们看到什么。客户/工作负载/产品术语，不是测试套件术语。*"Llama-2-70B微调在8个GPU上每次评估步骤都会挂起"* > *"测试失败。"*
- **出错原因。** 短段落。平实英语机制，一个级别的为什么，没有代码标识符。
- **何时发生/如何疏忽。** 可选。当领导层无论如何都会询问时，包括：潜在回归、CI差距、先前的未完成修复、冻结期间发生的更改。
- **负责人。** 人 + 团队 + 他们的PR/分支/JIRA工件。一个链接，而不是五个。
- **下一步。** 具体、近期、有序。*"代码审查 → 合并 → 回滚到7.2。"*
- **解决方案/缓解措施。** 如果客户现在遇到这个问题，他们今天能做什么？一句话。
- **风险。** 可选。只有真实风险——*"修复程序触及了热路径；性能回归可能直到基准测试后才会出现。"* 不要制造风险以显得全面。

按*此项目最重要的*顺序排序。

### Slack——频道帖子或DM

单条消息，没有大段文字。加粗的章节标签被读取为"我从JIRA中逃脱了"——不要这样。

- 一个**加粗的TL;DR**作为第一行。
- 2-4个简短的要点：影响、负责人+链接、下一步。丢弃不相关的块。
- 一个链接，内联嵌入（`JIRA-12345` / `PR #5751`）。不是一个链接墙。
- 没有问候语，没有结束语。频道是上下文。
- 如果这是一个**线程回复**而不是新帖子，则失去TL;DR——直接以答案开头。

长度目标：顶级帖子少于~80个字；线程回复少于~40个字。

### 异步站会笔记

受众在30秒内扫描10个这样的内容。优先考虑动词。

- 1-3行，最多。
- 模式：*"\<状态\> \<事物\>。\<如果不是我，则负责人\>。\<下一步\>。"*
- 示例：
  - *"修复Tada挂起影响dumbModel LLM-7B (JIRA-12345)。Alex的PR #5751正在审核中。下一步回滚到v7.2。"*
  - *"仍在追查LLM-7B评估步骤挂起。可重复的触发器现在可靠；正在二分法。尚未提供时间。"*
- 没有要点，没有加粗的标签。格式**就是**句子。

### 电子邮件——内部高管/跨团队

主题行是价值的一半。

- **主题：** 将TL;DR重写为名词短语。*"Tada挂起在dumbModel中：修复程序正在审核 (JIRA-12345)."*
- **问候语：** 匹配接收者的身份（*Hi Sam,* / *Hi all,*）。
- **正文：** JIRA评论形状，但作为由空行分隔的流动段落。两到三个段落就足够了。
- **结束语** 需要接收者注意的下一个决策点，如果有。如果没有，一个简单的 *"——[姓名]"* 就可以了。

### 会议讨论要点

你要*说*这个，而不是展示它。

- 要点列表，每个要点最多一个短从句。
- 顺序是你将说话的顺序。
- 包括你希望在口头参考时引用的编号/键，以便你不会结结巴巴。
- 跳过散文。*"dumbModel LLM-7B微调在8个GPU上每次评估步骤都会挂起。"* / *"根本原因：Tada快速路径中跳过了同步。"* / *"Alex的修复程序正在审核，PR #5751。"* / *"一旦合并，就回滚到v7.2。"*

## 源材料

输入是以下之一：

1. **一个JIRA票证键**（例如 `JIRA-12345`）→ 通过 `GET /rest/api/3/issue/<KEY>?fields=summary,status,priority,assignee,comment` 获取，加上你的实例用于技术评估的任何自定义字段——通常是当前状态最干净的来源。最新的实质性评论是重新构建的内容；不要倾倒整个线程。
2. **粘贴的技术文本** → 直接使用。
3. **当前对话** → 如果你（或用户）刚刚生成了工程内容，并且用户现在说 *"现在在Slack中"* / *"现在为副总裁"*，重用上下文中的内容。

如果源材料不明确，请问一个问题并停止。

## 输出流程

1. **确认渠道**，如果未说明。
2. **生成草稿**作为单个聊天块，格式化为渠道将渲染的格式。
3. **询问去向：**
   - 默认：打印——用户复制。
   - JIRA回帖：只有在用户明确说明的情况下。显示确切的ADF负载，等待明确的 *"发布它"* / *"继续"* / *"是"*，然后 `POST /rest/api/3/issue/<KEY>/comment`。
   - **从不从此技能发布到Slack、电子邮件或任何非JIRA渠道。** 将草稿交给用户；他们发布。
4. **一个迭代是正常的，三个迭代是一个迹象。** 如果用户处于第三次修订，请询问你遗漏了哪些特定的框架/受众假设——不要盲目不断调整。

## 工作示例——同一个错误，三个渠道

**源（工程JIRA评论）：**

> **机制：** `tadaLaunchPrepare` / `tadaLaunchKernel` / `tadaLaunchFinish` 中的单流快速路径（在 `scheduler->numStreams == 1 && !plan->persistent` 上触发）跳过了 `launchStream` 和 `handle->shared->deviceStream` 之间的跨流事件。dumbModel 正好命中这个门。内核启动之前，设备流的IPC发布/scratch缓冲区写入（填充 `scratchBuf`）对启动流可见——`scratchBuf == NULL` 在内核中——悬空指针引用——从垃圾中读取环准备标志——线程无限期旋转。

### 作为JIRA评论

> **状态：待合并修复。** 发现了错误，修复程序已验证，PR正在审核。
>
> **影响：** LLM-7B微调在8个GPU上每次尝试评估模型时都会挂起——阻止整个工作负载。影响使用dumbModel（一个用于训练不适合单个GPU的大型模型的流行框架）的客户，这意味着平台上的大多数大型模型微调运行都受到影响。
>
> **出错原因：** 我们的GPU通信库（Tada）在特定配置下跳过了一个内部同步步骤，dumbModel恰好触发了这个配置。GPU最终从未初始化的缓冲区读取，并永远等待一个永远不会到达的信号。这个不安全的快捷方式已经在代码中存在几个月了，但直到现在才被任何真实工作负载触发。
>
> **之前的修复尝试** 添加了一个防御性检查，在某些路径上隐藏了症状，但留下了底层的竞争条件。此新修复程序完全移除了不安全的快捷方式，并加强了设备侧的安全检查。
>
> **负责人：** Alex（Tada团队）。PR org/platform#5751。
>
> **下一步：** 代码审查 → 合并。今天遇到此问题的客户可以暂时禁用IPC注册。

### 作为Slack帖子

> **Tada挂起影响dumbModel LLM-7B已修复，待合并。** (JIRA-12345)
>
> - 跳过通信快速路径中的同步 → GPU读取未初始化的内存 → 挂起。潜伏了数月；dumbModel是第一个触发它的工作负载。
> - 负责人：Alex，PR #5751正在审核。
> - 解决方案直到合并：禁用IPC注册。

### 作为站会笔记

> 修复Tada挂起影响dumbModel LLM-7B (JIRA-12345)。Alex的PR #5751正在审核。解决方案已发布在票证中；下一步回滚到v7.2。

渠道之间的变化：相同的诊断，相同的负责人，相同的下一步。JIRA获得每个块。Slack丢弃"何时发生"和"之前的修复尝试"——对渠道来说太多。站会只保留状态+键+负责人+下一步。它们都不提`scratchBuf`或`tadaLaunchPrepare`。

## 规则

- **从不编造事实**来使重写更干净。如果工程源说"根本原因未知"，重写说"根本原因未知"——不要将猜测提升为发现，以使叙述整洁。
- **从不删除JIRA键、PR编号或客户/工作负载名称**在去技术化过程中。它们是交叉引用的桥梁——丢失它们会破坏跟踪。
- **从不编造负责人。** 如果源没有命名，请询问用户——不要从`git blame`或最近的提交中猜测。
- **在发布到JIRA之前获取批准。** 重用jira-check批准流程。打印输出不需要批准。
- **从不从此技能发布到Slack、电子邮件或任何非JIRA渠道。** 将草稿交给用户；他们发布。
- **远离倡导。** 此技能生成状态更新，而不是建议。如果用户想要建议备忘录，确认后再重新构建。
