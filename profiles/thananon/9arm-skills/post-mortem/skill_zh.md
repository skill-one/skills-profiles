# 原因分析报告

一份关于错误修复的规范工程记录。在调试成功后，**为其他工程师（以及六个月后忘记一切的未来你）**编写，欢迎在此处使用代码标识符——这是让下一个人能够快速恢复心智模型的工件。

对于组织内部的版本，将完成的报告交给 [`management-talk`](../../productivity/management-talk/SKILL.md)。他们负责：原因分析报告掌握工程事实，管理报告为领导层重新诠释。

## 调用时机

- "/reason-analysis"
- "编写原因分析报告 / reason-analysis / RCA / 根本原因分析"
- "记录此修复" / "编写根本原因" / "用报告关闭此错误"
- 在调试会话明确成功修复后，主动提出草拟报告。

## 不适用场景

- **错误未修复或修复未验证。** 假设的错误分析报告具有误导性。拒绝并告知用户缺失的内容。
- **客户可见的停机/事件。** 这些需要单独的事件报告（时间线、影响范围、调度历史、通讯记录）。此技能范围是错误修复。在生成前确认并标记。
- **琐碎的修复**（拼写错误、明显的单行代码）。PR 描述是记录。不要制造仪式。

## 必须输入项——没有这些就拒绝草拟

在编写单行之前，确认所有四项。如果有任何缺失，列出缺失项并停止：

- [ ] **存在可靠的复现方式**（不是“有时发生”——一个确定性或高频率偶发复现方式，下一个人可以运行）。
- [ ] **已知根本原因**（机制已被识别，不是假设）。
- [ ] **已确定修复方案**（PR / 提交 / 分支指针）。
- [ ] **已验证修复**（原始复现方式现在通过；客户工作负载/失败测试现在成功）。

这些直接对应于 `debug-mantra` 步骤 1-4。如果你通过 `debug-mantra` 进入，步骤 4 的面包屑账本就是你的原始材料——从中提取。

## 结构

按此顺序使用这些模块。**摘要、根本原因、修复和验证是强制性的。** 其余是可选的但通常存在。

### 1. 摘要 _(强制性)_
一段话。用用户/工作负载术语描述什么出错了。用一句话描述修复了什么。JIRA 关键字、PR 编号、负责人。一个停止在此处的读者应该得到正确答案。

### 2. 症状
实际观察到的内容。测试输出、错误消息、日志行、性能数字、客户报告。具体标识符——不要转述失败模式。

### 3. 根本原因 _(强制性)_
实际的错误机制。**欢迎使用代码标识符**——函数名、文件路径、结构字段、分支条件、错误变更的提交 SHA。端到端地追踪原因链。这是最昂贵的部分，也是原因分析报告存在的原因。未来你会根据你写得多清晰而生死存亡。

### 4. 为什么产生症状
将根本原因与症状联系起来。通常不明显——错误在 `tadaLaunchPrepare` 中，但可见的失败是客户培训运行数小时后挂起。端到端地追踪链，以便一个只了解症状的读者可以将其与原因联系起来，而无需重新推导。

### 5. 修复 _(强制性)_
发生了什么变化，以及**为什么这个变化解决了根本原因而不是隐藏症状**。链接到 PR / 提交。如果之前的修复尝试掩盖了症状，命名它并解释它有什么问题——这段历史是原因的一部分。

### 6. 如何发现
简短。调试路径：
- 使其确定性的复现方式。
- 破解它的工具（调试器、源代码跟踪、旋钮枚举、代码内仪器——`debug-mantra` 步骤 2 级联）。
- 尝试和拒绝的假设，以及每个被拒绝的原因（一行）。（从面包屑账本中提取）。
- 确认原因的唯一实验。

这个部分是给下一个调试者——使其可学习。

### 7. 为什么疏忽了
是什么允许这个错误达到分支/发布/客户。选择真实原因：
- CI 缺口（没有测试执行此路径/配置）。
- 潜在代码（编写时正确，后来不同文件中的变更破坏了它）。
- 工作负载缺口（直到现在才实际工作负载达到此代码路径）。
- 之前的修复不完整（防御性检查掩盖了症状；根本原因未触及）。
- 审查遗漏（变更可审查；含义未被注意到）。

如果诚实的答案是“没有好理由——我们应该发现它”，就说出来。**无责备**——描述缺口，而不是人。

### 8. 验证 _(强制性)_
我们如何知道修复有效。具体：
- 原始失败测试现在通过（测试名称、链接）。
- 客户工作负载现在完成（工作负载标识符、运行链接）。
- 性能回归已解决（修复前数字、修复后数字）。
- 压力/浸泡/模糊运行完成无错误（持续时间、规模）。
- 其他受影响的配置/工作负载也已测试。

如果你只验证了一个配置，明确说明——*"在 Llama-2-70B / 8 个 GPU / DeepSpeed 上验证；未在其他工作负载上重新测试。"* 不要暗示比实际更广泛的覆盖范围。

### 9. 行动项/后续
不在修复 PR 本身中的具体下一步。每个项目：什么 + 负责人 + 跟踪工件。

- 在 <seam> 处添加回归测试。（负责人，测试名称。）
- 重构以防止此类错误。（负责人，票证。）
- CI 缺口关闭：<新检查>。（负责人，PR。）
- 文档/运行手册更新。（负责人，链接。）
- 为 <相邻问题> 提交相关票证。（负责人，关键字。）

如果没有行动项，写 *"无——修复足够且无需此类错误后续跟进。"* 不要为了看起来全面而制造行动项。

## 语气

这是工程师对工程师的。不同于 `management-talk`：

- **代码标识符是一流。** `tadaLaunchPrepare`、`tada/prim.h::syncWaitPeer`、`scratchBuf`、提交 SHA、行号——保留它们。目的是让未来的工程师可以通过 grep 回到变更。
- **机制优于叙事。** 走实际的因果链。不要将其软化成“同步问题”——说哪个函数跳过了哪个事件在哪个门下。
- **主动语态、具体主语、短段落。** 别处同样规则。
- **无犹豫。** “我们相信” / “似乎” / “可能” —— 删除。陈述它或不要写它。
- **无责备。** 描述错误、缺口和修复。永远不会“X 应该发现它”。CI 缺口是失败模式，不是人。
- **无倡导。** 原因分析报告记录了发生了什么和下一步。如果你想为重构辩护，那是单独的提案——从行动项中链接它。

## 输出流程

1. **确认所有四个必须输入项已满足。** 如果有任何缺失，列出它们并停止。不要草拟。
2. **确认去向**（默认：源票证上的 JIRA 评论）。其他有效目的地：PR 描述、`docs/postmortems/<ticket>.md`、内部维基页面。形状相同——只有包装不同。
3. **生成草稿**作为单个聊天块。
4. **发布前确认。** 如果发布回 JIRA，显示确切的 ADF 负载，等待明确的 *"发布"* / *"继续"* / *"是"*，然后 `POST /rest/api/3/issue/<KEY>/comment`。纯打印输出无需批准。
5. **提供管理报告移交选项：** *"需要领导层风格的版本吗？我可以将这个交给 `management-talk`。"* 不要自动执行。

## 示例——Tada 在 dumbModel 中挂起 (JIRA-12345)

> **摘要。** Tada 的单流快速路径跳过了一个必要的跨流同步，导致内核在可见的 scratch 缓冲区写入之前启动。由 dumbModel 在 LLM-7B 微调中可靠触发，导致工作负载在每次评估步骤中挂起。通过移除不安全的快速路径并加强设备端检查修复。JIRA-12345，PR org/platform#5751，负责人 Alex (Tada 团队)。
>
> **症状。** 8 个 GPU LLM-7B 微调在 dumbModel 下在第一个评估步骤无限挂起。无错误，无超时——在 `tadaKernel_AllReduce_f32_RING` 中忙等待。每次运行都可复现。
>
> **根本原因。** `tadaLaunchPrepare` / `tadaLaunchKernel` / `tadaLaunchFinish` 中的单流快速路径（基于 `scheduler->numStreams == 1 && !plan->persistent`）跳过了 `launchStream` 和 `handle->shared->deviceStream` 之间的跨流事件。dumbModel 精确命中此门。内核在 IPC 发布/scratch 缓冲区写入（填充 `scratchBuf`）在 `deviceStream` 上对 `launchStream` 可见之前启动。在内核中：`scratchBuf == NULL` → 漏指针引用 → 从垃圾内存读取准备标志 → 线程永远等待永远不会到达的准备信号。
>
> **为什么产生症状。** 挂起发生在所有归约环等待循环中，这是调用栈中最后一个可见的东西——但实际错误在几个帧之前的启动准备中。跳过的同步直到工作负载触发精确的门（单流、非持久）才无声，dumbModel 的归约散布模式在每次评估步骤中命中它。
>
> **修复。** PR #5751 完全移除了单流快速路径（与它绕过的安全性相比，节省微不足道），并在解引用之前在设备端添加了对 `scratchBuf` 的空检查，以便同一类错误失败时大声而不是无声地旋转。之前的尝试（PR #5612）在 IPC 发布后在主机端添加了防御性检查，在某些路径上掩盖了症状，但留下了底层竞争，该变更也被回滚。
>
> **如何发现。** 复现器从“8 个 GPU LLM-7B 挂起有时”缩小到通过将单流固定在 2 个 GPU 子集上的单个评估步骤上 30 秒的确定性复现。初始假设：`launchStream` 上的内核启动顺序。调试器证伪——内核正确入队。第二个假设：scratch 缓冲区初始化竞争。通过在 `tadaLaunchPrepare` 中添加 `[DBG-7af3]` 仪器，打印 `scratchBuf` 和 `deviceStream` 事件记录时间戳；启动发生在发布完成之前。唯一锁定原因的实验：强制 `numStreams = 2` 使错误消失，隔离了门。
>
> **为什么疏忽了。** 潜在代码路径。单流快速路径是在 3 月份添加的，当时假设 dumbModel 路径始终采用多流路线。该假设当时是正确的。5 月份对 dumbModel 启动器的更改开始将评估步骤折叠为单流——此时门翻转。Tada 的 CI 没有执行单流 + IPC + scratch 缓冲区的组合；客户工作负载是第一个遇到它的。
>
> **验证。** 原始 LLM-7B / 8 个 GPU / dumbModel 工作负载现在可以干净地完成整个评估周期（3 个连续 2 小时运行）。`tada-tests` `all_reduce_perf` 回归套件变绿。浸泡运行：8 个 GPU 上 6 小时，无挂起。未在其他模型大小或非 dumbModel 工作负载上重新测试——两者都通过多流路径，从未受到影响。
>
> **行动项。**
> - 回归测试添加：`tests/single_stream_ipc_publish_test.cpp` 练习之前未覆盖的门。（Alex，合并到 PR #5751 中。）
> - CI 缺口：在夜间添加单流 + IPC 矩阵条目。（Alex，JIRA-12346。）
> - 文档更新：Tada 启动快速路径不变量在 `docs/launch_synchronization.md` 中记录。（Alex，PR #5752。）
> - 相关：审计其他 `numStreams == 1` 快速路径以防止同一类错误。（已提交为 JIRA-12347。）

这份原因分析报告与管理报告版本的不同之处在于：

- 每个代码标识符都命名了 (`tadaLaunchPrepare`、`scratchBuf`、`numStreams`、`handle->shared->deviceStream`)。
- 端到端地追踪因果链，以便读者可以 grep 回到错误行。
- 命名了 *之前的修复尝试* (PR #5612) 以及它有什么问题。
- 记录了 *确切的实验* 锁定原因 (`numStreams = 2` 使其消失)。
- 诚实地陈述验证覆盖范围——"未在其他模型大小上重新测试" 是信息，不是漏洞。
- 行动项有负责人和跟踪工件。

## 规则

- **没有所有四个必须输入项就拒绝草拟。** 假设的原因分析报告比没有更糟。
- **永远不要编造根本原因、负责人、验证运行或行动项。** 如果一个部分的事实不存在，询问。不要用合理的散文填补空白。
- **永远不要删除工程记录中的代码标识符。** 它们是索引。领导层重新诠释是 `management-talk` 的工作，不是你的。
- **无责备。** 描述缺口和错误，从不描述人。
- **诚实地陈述验证覆盖范围。** 如果你只测试了一个配置，说明。暗示更广泛的覆盖范围是导致重复回归的失败模式。
- **发布到 JIRA 前获取确认。** 纯打印输出无需批准。永远不要从这个技能发布到非 JIRA 目的地。
- **一次迭代是正常的，三次是可疑的。** 如果用户在第三次传递仍在修订，询问哪个部分有问题——不要盲目地不断调整。
