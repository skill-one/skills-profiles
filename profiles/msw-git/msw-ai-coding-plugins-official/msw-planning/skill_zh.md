# MSW 新游戏规划模式 (msw-planning)

## 目的
当用户处于“我想制作一个像这样的游戏”阶段时，将其转化为 **MSW 中要构建的内容 + 如何构建**：引导式会话产生 **GDD/路线图**，然后技能指导分阶段构建——详细的阶段计划、进度跟踪和计划修订——**直到每个里程碑的构建准备进入完整实施**。对于不熟悉游戏设计的人来说，只需按照问题进行；对于熟悉的人来说，它可以快速记录决策。

## 核心原则（为什么这样工作）
- **目录基础**：MSW 是 2D · mLua（一种 Lua 扩展脚本语言）· 跨平台，因此“你可以构建的内容”的空间是有限的。将模糊的想法映射到 [`references/genre-catalog.md`](references/genre-catalog.md) 中的真实类型/地图类型/机制，以获得一个 *可行的* 计划。仅从通用游戏知识出发进行规划会导致 MSW 无法实现的方案。
- **适当规模的构建**：目录为每个类型提供 **构建工作量提示**（低 / 中 / 高）——这是一个信号，而不是一个裁决（基线 1–5 个地图 · 10–20 个单位/物品 · 基础到中级 mLua；**塔防位于舒适单人模式的顶部**）。使用它来设定预期，而不是拒绝一个类型。根据 **构建工作量 + 范围（地图/内容）** 来调整第一个构建，而不是根据日历/开发时间估计——技能无法知道用户的技能水平或可用时间，因此它不会承诺“这需要 N 天/周。”**当用户的雄心很大**（一个高工作量类型，或者许多系统/地图，或者“我想拥有所有东西”）时，不要一次性规划全部内容——**将第一个构建的范围缩小到一个小型可玩核心（MVP）**，并将其余部分推迟到后续阶段。这适用于任何类型。
- **单次通过（无来回）+ 单向检查**：将用户触点限制为 **步骤 1（批量问题）** 和 **步骤 3（方向检查）**——不要在中间反复询问。但 **在编写 GDD 之前，永远不要跳过步骤 3（方向检查）**：不要只是展示基础结果，然后直接跳到 GDD。一旦方向确定，立即生成可交付成果。
- **标准化交付物**：将结果放入固定的 GDD 结构 ([`references/gdd-template.md`](references/gdd-template.md)) 作为 Markdown，以便实施技能可以拾取它并将其带到 MVP。
- **“后来”的单一归宿**：GDD 仅涵盖其自身的里程碑。它之外的所有内容——削减功能、后续里程碑的想法、在讨论中出现的“我们以后再做”的请求——在它出现的那一刻记录在 **站立里程碑路线图** (`Docs/<game>-Roadmap.md`：一个未来里程碑的槽位，或其 Backlog，当时间未知时）中，并且 **永远不会停放在 GDD 中**。一个归宿，没有重复：路线图拥有当前里程碑之外的所有内容；GDD 拥有其内部的所有内容。
- **推动项目前进**：每次交付后，**首先提出下一步**（例如，“我接下来写阶段 1 详细计划吗？”）。如果用户同意，就继续；如果他们说不，就停止——这是一个建议，而不是强迫。（这与无尽的文档中来回询问不同——它连接了交付物之间的流程。）
- **决策门 = 可选选择，而不是自由文本**：在每个用户决策点——**步骤 3 方向检查**、**阶段交接**（立即实施 vs 写下一个阶段的计划）和**软阶段门**——通过代理的多项选择 UI（当可用时，例如 Claude Code 的 `AskUserQuestion`）以结构化可选选择的形式呈现选项，以便用户点击选项而不是输入自由文本回复。标记推荐选项，但不要强迫；如果代理没有这样的 UI，则回退到清晰的枚举文本选择。

## 启动时——检查现有 GDD（恢复 / 新建 / 阻止）
一个构建跨越多个会话和 **里程碑——每个里程碑是一个 GDD**。事物存放的位置（所有项目根目录，RootDesk 外部，以防止 `refresh_workspace` 刷新）：
- **活动** GDD + 阶段计划 → `Docs/`.
- **`Docs/<game>-Roadmap.md`** → 游戏的 **站立里程碑路线图**（愿景 · 发布标准 · 每个里程碑一个槽位 · Backlog）：跨里程碑方向，与 M1 GDD 一起创建，永久（从未存档）。它 **不是** GDD——当前里程碑的合同保留在其 `-M<n>-GDD.md` 中。
- **已完成** GDD → `Archive/`（在里程碑完成时）。
- **`Archive/As-built.md`** → 世界的运行实施记录：由技能维护的当前状态地图，是一个 **AI / 交接参考，而不是面向用户的规划文档**（由 [`references/build-management.md`](references/build-management.md) 清理维护；通过 *Brownfield* 下面种子）。

**在运行以下流程之前，检测计划文件**——检查 **`Docs/`** 和 **`Archive/`** 中是否存在 `<game>-M<n>-GDD.md`：
- **列出这些目录的完整内容**（大写 `Docs/` / `Archive/`）——一个目录级列表，返回其中 *所有* 内容（例如，代理的文件列表器 / `Glob` 与 `Docs/*`）——然后 **你自己** 从该列表中匹配以 `-GDD.md` / `-Phase<N>.md` 结尾的名称。**不要** 通过缩窄的模式或内容搜索检测（`*-GDD.md` 的 glob 或 grep 案敏度 + 范围脆弱：`*.md` 仅限顶层，`docs/` ≠ `Docs/`——一个无声地读取为“没有 GDD”），并且不要从内存中检测。
- 仅当 `Docs/` 和 `Archive/` 列表**真正为空**时，才得出 **“任何地方都没有 GDD”** 的结论。
- 如果 **`Archive/As-built.md`** 存在，**首先读取它** 以获取当前状态地图；如果 **`Docs/<game>-Roadmap.md`** 存在，与它一起读取以获取跨里程碑方向（切勿将其误认为是活动 GDD）。
- 通常最多只有一个活动 GDD；**如果存在多个，首先询问这是关于哪个游戏**，然后应用以下规则。

**门控规则——只有当 `Docs/` 或 `Archive/` 中存在计划时，“继续” / “下一个任务” / 恢复请求才起作用**（一个 `<game>-M<n>-GDD.md` / `<game>-M<n>-Phase<k>.md`，或先前里程碑 + `Archive/As-built.md`）。如果 **两者中都没有** 存在，则必须**不将其视为恢复，并且不得自动启动 STEP 1 问卷**——相反：如果请求是 **继续 / “下一步”意图**，或者用户说他们正在自己的现有工作基础上构建**（不是从新鲜模板开始），则转到 *Brownfield* 下面；否则（新建游戏或意图不明确）告诉用户没有保存的计划，并询问是否要开始一个新游戏（然后 STEP 1）。**不要从工作区文件中推断 Brownfield——模板附带样本，因此非空工作区不是先前工作的证据。

**如果存在 GDD，请判断 GDD / 阶段文档任务状态（`⬜/🟡/✅`）实际上完成了多少——**不是从工作区文件中**（模板附带 `.mlua`/`.model`/`.ui`，因此文件存在不是可靠的进度信号）。然后分支：
- **用户明确要求继续/恢复** → **恢复**（以下步骤），无论状态如何。
- **每个路线图和阶段项目都是 `⬜`**（一个零进度的计划）**并且它是游戏的第一个里程碑**——`Archive/` 中没有相同的 `<game>` GDD **并且** GDD 的编号是 `M1`。（在提供之前检查此点：存档的先前里程碑，或者当前 GDD 上的 `M2+` 编号本身就是证明这个世界已经包含构建工作的证据——零进度的计划仅仅是*构建在其之上* → 那是以下 `🟡/✅` 案例中，**不是**这个案例。）→ 提供一个 **可选选择**（见核心原则）：**① 继续此计划 (*[game]*)** / **② 放弃它并规划一个新游戏**。如果他们选择放弃，**首先明确哪些文件将被删除**——`Docs/<game>-M<n>-GDD.md`，该游戏的 `Docs/<game>-M<n>-Phase<k>.md`，**以及该游戏的 `Docs/<game>-Roadmap.md`**（它是与 M1 GDD 一起创建的，因此它随着它一起被删除——留下它会将已删除游戏的指导输入到下一个规划会话）——仅这些——删除它们，然后重新开始。
- **任何项目都是 `🟡` 或 `✅`——或者 GDD 全部为 `⬜` 但此游戏的先前里程碑存在**（相同的 `<game>` GDD 在 `Archive/` 中，或者 `M2+` 编号）——即，在这个世界中存在进行中的或已构建的实施 → **不要**放弃，**不要**规划一个新游戏在这里。**通知**用户这个世界已经有一个原型正在进行中，并且必须在一个**新的世界**中构建一个**真正的新游戏**——这个技能**无法创建一个世界**，因此用户创建一个世界并在这个世界运行技能——然后**停止**。（如果他们实际上想要继续这一个，则恢复。重新设计一个零进度的下一个里程碑 *计划* 是在 `Archive/As-built.md` 上的计划修订——仍然是这个游戏，永远不会是新的。）

**恢复现有计划**：
1. **首先读取现有文档**——`Docs/<game>-M<n>-GDD.md`（+ **每个** `Docs/<game>-M<n>-Phase<k>.md` 当前存在——几个可以共存，因为早期的阶段等待用户的测试，并且它们的清单可能包含 §6 还没有的状态；+ `Docs/<game>-Roadmap.md` 用于跨里程碑上下文）。**不要**重新运行 STEP 1–4；计划已经存在。
2. **重建状态**：GDD 的 `Stage` 行 + 路线图 `⬜/🟡/✅`，任何 `🟡 已实现（未测试）` 项目（标记这些以重新测试 / 用户确认），以及最近的 `§9 计划变更`。
3. **如果恢复的工作将触及实施或任何清单状态，现在阅读 [`references/build-management.md`](references/build-management.md) 的全部内容**（见 STEP 6 下的硬门）——恢复是一个读取链最薄弱的点，因为文档是由过去的会话编写的。在阅读文档时，还**更新陈旧的 AI 笔记**：如果 `Docs/` GDD/阶段文档的标题 AI 笔记早于当前模板（例如，它缺少 [`references/gdd-template.md`](references/gdd-template.md) 现在嵌入的建设管理指针），请更新该笔记行为为当前模板文本作为协调的一部分——旧文档不得继续引导未来的会话到一个过时的读取链。
4. **简要重申现状**——已完成的工作 / 当前阶段 / 仍有未测试的内容 / 下一步——然后从那里继续。
- 如果 `Docs/` 没有 GDD，但 `Archive/` 有一个完成的 GDD（+ `Archive/As-built.md`），则之前的里程碑完成。**确认**是否要开始一个 **下一个里程碑**——在 `Docs/` 中创建一个新的 GDD (`<game>-M<n+1>-GDD.md`，下一个编号按 STEP 5），计划 **在里程碑路线图的下一个槽位 (+ 其 Backlog) 和 `Archive/As-built.md`** 上——而不是假设一个全新的游戏。（在编写它之前，**与工作区记录进行协调——见 *在下一个里程碑之前协调* 下面**。编写新的 GDD **将**该路线图槽位提升：它的单行主题扩展为 GDD；路线图只保留单行。）
- **阶段文档生命周期**：仅当该阶段 **全部为 `✅`**（其阶段清理）时才删除阶段文档——GDD 路线图是它的记录。因此，`Docs/` 中仍然存在的文档是 **当前** 阶段以及任何早期阶段停放在 **`⏳ 用户测试边界`**（项目仍然 `🟡`，等待用户的测试），并且几个可以合法共存。一个遗留文档，其项目全部为 `✅`，是唯一一个表明遗漏清理的情况。
- `Docs/` 文件是 **跨会话的真实来源**：前一个会话的聊天上下文不会传递，因此任何未写入 GDD/阶段文档的内容都会丢失（这就是为什么决策和状态被记录在那里）。

**`Docs/` 中没有 GDD，也没有 `Archive/` → 在做任何其他事情之前，*分类工作区，然后决定*——强制性的，包括对明确的“新建游戏”请求：永远不要在没有首先检查这里已经构建了什么的情况下直接跳转到 STEP 1。**（*Brownfield* = 继续用户自己的已经构建的世界；它 **由用户驱动，永远不会从原始文件存在中推断**——但分类本身**不是**可选的。）当存在真实工作时，显示它；如何突出显示 Brownfield 取决于用户的 *意图*（下面），而不是工作区。

非空工作区**不是** Brownfield 信号——一个新鲜模板已经附带脚手架。**将已知的启动项视为 *零进度***（一个已知的集合，**不是详尽的**——模板版本会变化，其他模板不同；这是“已知为脚手架的东西”，而不是一个完整的清单）：瓦片数据集 `RectTileData_Henesys`；`@Logic` `UIPopup`，`UIToast`；`@Component` `Monster`，`MonsterAttack`，`PlayerAttack`，`PlayerHit`；**模板怪物-AI FSM 样本**——`StateComponent` 脚本 `StateChaseMonster` / `StateMoveMonster` / `StateTypeChase` / `StateTypeWander`，条件脚本 `ConditionHasTarget` / `ConditionIsAlive` / `ConditionIsDead` / `ConditionNoTarget`，`.stateset`s `StateSetChaseMonsterAI` / `StateSetMoveMonsterAI`，以及 `Global/` 怪物模型 `ChaseMonster` / `MoveMonster`（所有由模板导入到 `RootDesk/MyDesk/` + `Global/` 并连接到 `*Template` 地图中——它们的存在**不是**用户构建的怪物 AI）；加上始终存在的 `Global/` 默认值——DefaultPlayer，WorldConfig，起始地图。
- **工作区 ≈ 仅启动项（或更少）** → 新项目 → **直接进行 STEP 1，没有 Brownfield 提示。**
- **工作明显超出启动项**（自定义名称的系统 / 地图 / 数据集 / 脚本建议真正的实施）→ 可能正在进行中的真实游戏。**如何突出显示 Brownfield 取决于用户的 *意图*，而不是工作区：**
  - **继续 / “下一步”意图**（“我应该做什么下一步？”，“继续”，“我们在哪里？”）→ 继续现有工作是自然的阅读 → 提供 **Brownfield 作为推荐选项**（以及：开始一个单独的新游戏；或者只是重新检查 / 改进一个特定系统）。
  - **明确的新建游戏意图**（“我想制作一个新游戏”）→ **尊重它：新建游戏是默认 / 推荐选项。** 仅将 Brownfield 作为**最后的、非推荐的**选项（*“…或者你实际上在继续你已经构建的世界？”*）——一个安全网，永远不会推荐，永远不会是一个强制性的分支，覆盖用户要求的内容。
  - 一个明确的“在我的现有工作基础上构建”请求 → 直接到调查。
  Brownfield 仅在用户实际选择它时运行。

当选择 Brownfield 时，不要在真空中规划——**进行结构调查** (`map/` + `RootDesk/MyDesk/` — 系统 · 模型 · 数据集 · UI；*仅限结构，不进行逐行代码阅读*；深度检查是 msw-general 的工作），显示 *"我已经看到已经构建的内容——正确?"* 并使用 `⚠️confirm`，然后 **初始化 `Archive/As-built.md`** 并在现有世界之上规划第一个里程碑（里程碑路线图按通常方式与该里程碑的 GDD 一起创建——STEP 5）。

**在规划下一个里程碑之前协调**——当在 `Archive/` 记录上规划新的里程碑时（从启动时到达，或者完成一个之后）：`Archive/As-built.md`（或一个遗留交接笔记）是一个**起始提示，而不是事实依据**——其他会话中可能发生的工作 / 手动编辑而未更新它。**在编写新的 GDD 之前，运行与 *Brownfield* 上面的相同轻量级结构调查，但用于**验证**记录（而不是从头开始发现）：检查新里程碑将触及的区域——快速扫描明显未跟踪的主要系统——与记录声称的内容进行对比。如果它已经**漂移**，**首先与用户协调**，**更新 `Archive/As-built.md`** 以匹配现实，*然后* 在其上规划。这可以防止整个 GDD 基于陈旧的假设编写，并且只有在中实施时才会出现漂移。

## 流程

### STEP 1 — 引导问题（批量）
不要重复用户已经给出的内容；仅批量询问差距：
1. **类型 / 参考** — 感觉如何？有任何类似的游戏？（如果不确定，从“你想获得什么样的乐趣？”开始？）
2. **核心乐趣 / 核心循环** — 你在一个会话中重复什么？（例如，杀死敌人 → 增长 → 更强的敌人）
3. **目标 · 平台** — PC/移动？单人/多人？
4. **范围（第一个构建）** — 快速原型还是更大的东西？大约有多少张地图 / 多少内容？
5. **必须有的 / 可削减的**

批量到约 5 个问题。如果用户说“你决定”，则使用合理的默认值，但**声明假设**。

### STEP 2 — 目录基础 + 可行性检查
读取 [`references/genre-catalog.md`](references/genre-catalog.md) 并：
- 找到与用户想法最接近的 **类型(s)**。
- 拉取该类型的 **推荐地图类型** 和 **核心机制标签**。
- 拉取该类型的 **`MVP:` 切片提示**（最小可玩切片——为范围缩小后的第一个构建和 STEP 4 的阶段 1 种子）和 **`Growth:` 轴**（完成的核通常添加的内容——为后续阶段和未来里程碑提供输入）。将它们调整为用户的想法；它们是提示，而不是固定规范。
- **读取 `build-effort` 提示**（低 / 中 / 高）并判断用户的雄心。如果它是高工作量或用户一次请求很多，请直言不讳，并**建议一个范围缩小后的第一个构建**（一张地图 · 核心循环仅限）——从类型的 `MVP:` 提示开始，其 `Growth:` 轴建议后续阶段。跟踪每个路线图项目，使用三种状态——`⬜ 未开始` / `🟡 已实现（未测试）` / `✅ 已测试`（所有开始 ⬜；状态规则 → [`references/build-management.md`](references/build-management.md)）。
- **路线图清单仅包含一个手交就绪原型所需的项**——并且所有这些都必须达到 `✅`。抛光 / 好的 / 后续工作转到 **里程碑路线图** (`Docs/<game>-Roadmap.md` — 一个未来里程碑的槽位，或其 Backlog）**在规划时间**，永远不会作为清单项，也永远不会停放在 GDD 中（见 *“后来”的单一归宿*）。区分器：*丢弃它会让完整实施团队的基础更不完整吗？* → 需要（清单）；*生产会抛光它吗？* → 里程碑路线图。
- 对于数据密集型游戏，在路线图中声明“数据驱动（UserDataSet/CSV 是真实来源）”。早期阶段可能为速度硬编码值，但一旦值集增长或稳定，**计划硬编码→数据集（UserDataSet/CSV）迁移**：在此里程碑内 → 后续阶段的任务在 GDD §6 中；超出它 → 一个 **里程碑路线图条目**（槽位或 Backlog；§7 仅保留一个指针——一个仅以 GDD 文本形式写入的意图在存档时被埋葬）——所以平衡/内容不再需要代码编辑。仅在**值得**（许多可调节数值 · 预期的平衡迭代 · 内容扩展）时包含此内容，而不是少数常数。数据集本身由 `msw-general` 编写（见其 `references/dataset.md`）。
- **保存 GDD 前的覆盖检查**：§6 阶段必须 *集体交付* §1 的一线概念（并且，对于 M2+，路线图槽位行）——将每个能力那些行声称的与将实现它的清单项跟踪。没有项目的声明是一个规划漏洞，没有后续规则可以捕获（未计划的任务不会留下 `⬜` 在后面）。**验证限制不会缩小范围**：AI 无法单独验证的流程（真实多人匹配，设备上的感觉，商业）仍然按计划记录为任务——它们将简单地结束 `🟡 需要用户测试`——永远不会因为无法自动验证而默默地遗漏。如果用户同意排除一个声明的功能，请重新编写 §1 / 路线图槽位，以便文档停止承诺它。
- **如果项目发送占位符/样本实体**：包括一个任务来**在原型转交给完整实施之前删除它们**，这样它们不会带入真实构建。**范围 = 整个项目，而不仅仅是所选构建地图**——**任何**项目都可能携带自己的样本（模板派生的地图经常这样做；一些不发送任何样本），所以任务的完成标准是 "**检查所有地图并清理**": 首先列出**所有地图**（完整的 `map/` 列表），然后检查每个；一个地图扫描干净**不是**证据，其他地图的清洁。**不要假设固定名称——通过检查识别每个地图的样本**（通常 `*Template`-命名的空闲/移动/追逐怪物样本，但名称因模板而异）——它们在早期作为 AI 模式参考很有用；实际删除发生在实施过程中，通过 MapBuilder 从 `.map` 中删除它们。**未使用的模板地图也是交接残留物**：在交接时，**询问用户是否要删除或保留**每个游戏不使用的模板地图（永远不要未经确认删除）——并且决定**在样本清理之前**（不要在即将被删除的地图上清理样本）；“所有地图干净”适用于剩余的地图。

### STEP 5 — 保存 + 下一步
- 将生成的 markdown 保存到项目根目录的 `Docs/` 下，作为 **`Docs/<game>-M<n>-GDD.md`**——**`<game>`** 是一个简短的 ASCII（英语/罗马化）缩写（**永远不会是原始的非英语标题**；CJK/非 ASCII 文件名会破坏 globbing 和跨平台路径——例如 `MapleIdle-M1-GDD.md`，而不是原始的 CJK 标题）并且 **`<n>` 是里程碑编号。**里程碑编号：第一个里程碑是 **M1**；后续里程碑采用 **(Docs/ 中现有的 `-M<n>-GDD.md` 的最高数字) + 1**——*解析数字，不要按字母顺序排序*（所以 M9 → M10，不是 M2）。文档的内容保留在用户的语言中；只有文件名是 ASCII。阶段文档继承相同的 **`<game>-M<n>-` 前缀**（STEP 6）。收集所有规划交付物（GDD · 阶段详细计划）到这里。如果缺少，则创建文件夹。保留为文件，实施技能可以拾取它并将其带到 MVP。
- ⚠️ **不要** 保存到 `RootDesk/`。Maker 的 `refresh_workspace` 清理（删除）`RootDesk/` 下的非 MSW 文件 (.md 等.)，因此这些文件在刷新运行期间实施/测试时**会消失**。始终将它们保留在 RootDesk 外部（项目根目录 `Docs/`）。
- **与 M1 GDD 一起创建里程碑路线图**——`Docs/<game>-Roadmap.md`（名称中不带 `M<n>`；每个游戏一个；永久，从未存档）。遵循 [`references/gdd-template.md`](references/gdd-template.md) 中的“里程碑路线图模板”：**一线愿景** + **发布标准**（必须为游戏可发布的内容——标准，而不是功能清单），**每个里程碑一个槽位**（M1 = 指向活动 GDD；未来的 M 的一个行主题 + 指定功能），以及 **Backlog**，用于想要但未分配的项目。**将 STEP 2–3 从第一个构建中删除的所有内容**（Growth 轴 · 削减功能 · 用户的“以后”愿望）放入未来槽位或 Backlog。**根据游戏进行缩放**：单里程碑游戏的路线图只有几行（M1 = 发布）。对于后续里程碑 (M2+)，不要重新创建——**更新**现有的路线图（提升该槽位）。
- 当基础 GDD 完成时，自然地首先提出：“我接下来写 **阶段 1 详细计划** 吗？” → 如果用户同意，直接进入 STEP 1。
- 其他分支要提供的：如果数字/数据密集型，转到数据集设计；如果屏幕密集型，使用 `msw-ui-system` 编写 UI；要立即构建，使用 `msw-general` 开始实施。
- 默认推荐流程是 '详细阶段 1 → 实施。'
- **应用地图类型**——如果存在匹配的地图，则在其中构建原型，否则用户在 Maker 中设置它**：原型必须构建在 `TileMapMode` 已经等于决定类型的地图中。在设置时，检查现有地图的 `MapBuilder.read().getTileMapMode()`，然后：
  - **如果有一个地图已经匹配**——例如，项目保留 **每个地图类型模板地图**（一个 TileMap / RectTile / SideView 每个）——**在不需要切换的情况下构建原型**，不需要切换（破坏性切换是避免的）。*此快捷方式仅当存在匹配的地图/模板时适用。*
  - **如果没有地图匹配**——没有按类型模板，或者从零开始——回退到标准策略：**用户在 Maker 中切换地图的类型**（msw-general `tile.md`；代理随后使用 `getTileMapMode()` 验证）。
  - **如果构建的地图很早命名**（如果原型将存在于一个 `*Template` 命名的地图中），请计划一个 **阶段 1 任务**将其重命名为一个游戏合适的 ASCII 名称**，在真正的构建开始之前**——地图引用（区域注册 · 站点 · `GetEntityByPath` 路径 · 活动地图）随着阶段的进展而累积，所以改名在阶段 1 非常便宜，在交接时昂贵；并且一个生活在 `*Template` 命名的地图会污染技能自己依赖的模板与游戏分类。完成标准：文件已重命名 + 每个引用已更新 + 刷新 + 条目已验证。机制属于实施技能；**如果引用存在于只读配置 (`Global/`) 中，则该部分是用户的 Maker 操作**——与 `TileMapMode` 切换相同的策略。
