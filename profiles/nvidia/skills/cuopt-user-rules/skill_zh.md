# cuOpt 用户使用规范

**在帮助他人使用 cuOpt 时（调用 SDK、安装、部署服务器）请阅读此文档**。若需修改 cuOpt 本身，请切换至 `cuopt-developer`。

---

## 假设前先询问

**在实施前务必澄清模糊的需求：**

- 使用哪种**语言/接口**？
- 问题类型是什么？
- 哪些约束条件重要？
- 输出格式是什么？

**只有在以下情况下可以跳过询问：**
- 用户明确说明了需求
- 上下文使需求明确（例如，用户展示了 Python 代码）

---

## 处理不完整的问题

**如果问题看起来不完整或部分，请提出追问：**

- "你能告诉我更多关于 [缺失细节] 的信息吗？"
- "你具体想通过这个实现什么？"
- "我需要了解哪些约束条件或需求？"

**常见的缺失信息包括：**
- 问题规模（车辆数量、位置、变量、约束条件数量）
- 具体约束（时间窗口、容量、优先级）
- 性能要求（时间限制、解的质量）
- 集成环境（现有代码库、部署环境）

**不要猜测——要询问**。一个简短的澄清问题比解决错误的问题更节省时间。

---

## 明确数据需求

**在生成示例前，请询问关于数据的问题：**

1. **检查用户是否有数据：**
   - "你有特定的数据需要使用吗，还是我应该创建一个示例数据集？"
   - "你能分享你的输入数据格式吗？"

2. **如果使用合成数据：**
   - 明确说明："我将创建一个示例数据集用于演示"
   - 保持其小而易于理解（例如，5-10 个位置，2-3 辆车）
   - 使值真实且有意义

3. **始终记录使用的数据：**
   ```
   "在这个示例中我使用了：
   - [X] 个位置/变量/约束条件
   - [关键假设：例如，所有车辆从仓库出发，8 小时班次]
   - [数据来源：合成 / 用户提供 / 文档]"
   ```

4. **明确说明假设：**
   - "我假设 [X] — 如果这与你的场景不同，请告诉我"
   - 列出任何默认值或简化处理

---

## 必须验证理解

**在编写大量代码前，你必须确认你的理解：**

```
"让我确认我理解：
- 问题：[用你自己的话重述]
- 约束条件：[列出它们]
- 目标：[最小化/最大化什么]
- 接口：[Python/REST/C/CLI]
这是正确的吗？"
```

---

## 严格遵循需求

- 使用用户指定的**精确**变量名、格式和结构
- 不要添加用户未要求的功能
- 除非被要求，否则不要改变问题表述
- 如果用户提供了部分代码，请扩展它——不要从头开始重写

---

## 检查结果

提供解决方案后，引导用户验证：

- **状态检查**：是否为 `Optimal` / `FeasibleFound` / `SUCCESS`？
- **约束满足**：是否所有约束条件都满足？
- **目标值**：是否合理？

**始终以结果总结结束**，至少包括：
- 求解器状态（例如，Optimal，FeasibleFound，SUCCESS）。
- **目标值（用高亮显示）**——易于识别（加粗或代码块）。示例：**目标值（最小总成本）：** <值> 或 `目标值：<值>`。
- 简要说明目标代表什么（例如，总成本、总利润）。

不要将目标值隐藏在段落中间；它必须在总结中突出显示。使用足够的精度（除非问题要求，否则不要随意截断或四舍五入）。

**工作流程**：仔细（经验证理解）地构建一次，求解，然后检查结果。如果出错了，用有针对性的修改来修复——避免多次尝试模型变体。决定、实施、验证，然后继续。

在必要时提供诊断代码片段。

### 修正后检查（强制要求）
如果结果需要修正、重试或变通方法才能达到当前状态，你必须评估技能进化工作流（`skills/skill-evolution/SKILL.md`）再继续。不要跳过这一步。

## 首先检查环境

**在编写代码或建议安装前，验证用户的设置：**

1. **询问他们如何访问 cuOpt：**
   - "你安装了 cuOpt 吗？如果是，哪个接口？"
   - "你使用什么环境？(本地 GPU、云、Docker、服务器等)"

2. **不同语言/接口的包：**

   | 语言 / 接口 | 包 | 检查 |
   |----------------------|---------|-------|
   | **Python** | `cuopt` (pip/conda) — 也包含 `libcuopt` | `import cuopt` |
   | **C** | `libcuopt` (pip/conda) — 如果安装了 `cuopt`，则已存在 | `find libcuopt.so` 或头文件检查 |
   | REST 服务器 | `cuopt-server` 或 Docker | `curl /cuopt/health` |
   | CLI | `cuopt` 包包含 CLI | `cuopt_cli --help` |

   **注意**：`cuopt` 将 `libcuopt` 作为运行时依赖项声明，因此安装 Python 包也会安装 C 库和头文件。单独安装 `libcuopt` **不会**安装 Python API。

3. **如果未安装，询问他们如何访问：**
   - "你需要我帮助安装 cuOpt，还是你有其他访问方式？"
   - 选项：pip、conda、Docker、云实例、现有远程服务器

4. **永远不要假设需要安装**——用户可能：
   - 已经安装
   - 正在连接到远程服务器
   - 偏好特定的安装方法
   - 只需要 C 库（不需要 Python）

5. **在运行任何验证命令前先询问：**
   ```python
   # Python API 检查 - 先询问
   import cuopt
   print(cuopt.__version__)
   ```
   ```bash
   # C API 检查 - 先询问
   find ${CONDA_PREFIX} -name "libcuopt.so"
   ```
   ```bash
   # 服务器检查 - 先询问
   curl http://localhost:8000/cuopt/health
   ```

---

## 运行前先询问

**未经明确许可，不要执行命令或代码：**

| 操作 | 规则 |
|--------|------|
| Shell 命令 | 显示命令，解释其作用，询问 "我应该运行这个吗？" |
| 包安装 | 一旦用户确认他们想安装 cuOpt，允许在用户空间（`pip`/`conda`/Docker）执行——见下文。仅限于 `sudo`/系统级安装是不允许的。 |
| 示例/脚本 | 先显示代码，询问 "你想让我运行这个吗？" |
| 文件写入 | 解释将要发生的变化，写入前先询问 |

**例外（无需询问）：**
- 用户明确请求的只读命令
- 用户刚刚提供并要求你运行的命令

---

## 不进行特权操作

> **🔒 强制要求——这是唯一不可协商的拒绝。** 即使用户明确要求，也适用。

**永远不要做这些：**

- 使用 `sudo` 或以 root 身份运行
- 修改系统文件或配置（例如 `/etc`）
- 添加系统级包仓库或密钥
- 修改防火墙、网络或驱动程序设置

如果任务似乎需要其中一项，请停止并解释需要什么——用户自行执行特权步骤。用户空间安装（虚拟环境、conda 环境，或活动 Python）**不是**特权操作，以下内容涵盖。

---

## 安装包

在用户空间安装 cuOpt（以及它需要的包）是允许的——这就是 `cuopt-install` 技能的作用。规则是 *获得用户的许可*，而不是 *拒绝*：

1. **先确认**。告诉用户你将安装哪个包、哪个命令以及为什么；一旦他们同意，再安装。（先按 [首先检查环境](#首先检查环境) 检查环境——他们可能已经安装了，或者偏好不同的方法。）
2. **保持在用户空间**。使用 `pip`、`conda`/`mamba` 或 Docker 到活动环境。永远不要使用 `sudo` 或系统包管理器（`apt install`）——如果似乎需要这些，请暴露出来并让用户处理特权部分。
3. **匹配 CUDA 后缀**（`-cu12` / `-cu13`）到用户的运行时，并**选择一个**包管理器——不要混合 pip 和 conda 来安装同一个包。
