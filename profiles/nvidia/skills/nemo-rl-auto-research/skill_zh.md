# 自动研究

在本仓库中针对用户声明的目标（如准确率、奖励、吞吐量、延迟、稳定性或其他特定指标）运行迭代 NeMo-RL 实验，使用 git 作为研究账本。

将依赖项视为就绪，但需审慎选择运行时。使用食谱的权威指标作为事实来源。保持变更小、可重复且简单。保留无关的用户工作。

**安全提示**：此技能会创建 git 分支、将文件写入磁盘，并执行包括训练作业在内的 shell 命令，这些作业可能会消耗 GPU 资源。在创建分支或启动作业前，务必与用户确认活动计划。未经明确用户批准，不要执行破坏性 git 操作（重置、强制推送）或启动计算密集型作业。

为每个自动研究活动使用 `nemo-rl-session-memory` 技能。在分支前开始或恢复会话记录，在形成计划后、有意义编辑或长时间运行启动前后、用户改变方向前以及交接或最终总结前进行检查点。

在上下文压缩、交接、断开连接或长时间间隔后，重新加载此技能和任何已使用的配套技能，读取最新的 `nemo-rl-session-memory` 交接内容，并在继续前重申总体目标、停止规则、当前分支和最新结果。除非用户明确更改主要目标，否则将后续指导视为附加项。

## 工作流程

1. 在分支前检查当前 git 状态并识别无关的用户更改。
2. 使用共享分支前缀。优先使用用户提供的；否则创建一个提示性的默认前缀，例如 `autoresearch/2026-03-24-dapo-qwen2p5`。
3. 读取目标食谱、其父项以及 `examples/run_grpo.py`、`nemo_rl/models/`、`nemo_rl/algorithms/`、`nemo_rl/environments/` 和 `docs/` 中的相关代码路径。对于 NeMo-gym 食谱，还检查 `examples/nemo_gym/` 入口点、配置和启动脚本。
4. 将任何用户停止规则翻译为可监控的显式值，例如请求的实验数量作为 `target_experiment_count`、`campaign_deadline`、`per_experiment_timeout` 或 `target_metric`。
5. 验证所需数据、检查点、运行时输入和启动器。
6. 创建一个未跟踪的 TSV 日志和每个实验日志目录。
7. 如果不存在，在 `<prefix>/baseline` 上运行基线。

对于 GPU、CPU 密集型、分布式或长时间运行的工作，审慎选择执行环境。当当前机器具有合适的 GPU 和容量时本地运行；否则遵循用户请求的环境，使用 `launch-nemo-rl` 用于 nrl-k8s/Kubernetes，使用 Slurm 的原生启动器用于 Slurm，或在启动前与用户澄清。仅使用 CPU 本地运行进行轻量级检查、干运行和短时非 GPU 检查。

如果用户提到 Brev，或者 `/home/ubuntu/RL` 存在且 `/ephemeral` 可作为卷使用，将机器视为 Brev 实例，并在创建实验目录、缓存、日志、检查点或认证运行状态前使用 `nemo-rl-brev-etiquette`。

## 分支

- 将每个实验放在共享前缀下的独立分支上。
- 保留每个分支，即使对于失败或效果不佳的想法。
- 每个分支至少提交一个关于假设的提交。
- 当重新运行合理时，在同一分支上添加后续修复提交。
- 从不无声地 stash、重置或覆盖无关的用户更改。如果脏文件与实验重叠，使用单独的工作树或在进行下一步前询问。

参见 `references/git-workflow.md` 获取确切模式。

## 循环

1. 选择一个具体的假设。
2. 创建一个分支，例如 `autoresearch/2026-03-24-dapo-qwen2p5/prompt-compact-schema`。
3. 编辑所需的最小文件集。
4. 提交假设。
5. 在启动运行前，检查监控的停止条件。除非某个条件已明显满足，否则不要提前停止。
6. 从食谱或日志代码中识别权威指标源，然后使用唯一日志路径运行：

```bash
LOG_DIR=reports/auto_research/<campaign>/<experiment>
mkdir -p "$LOG_DIR"
uv run <entrypoint> > "$LOG_DIR/run.log" 2>&1
```

7. 如果用户提供了每个实验的墙上时钟限制，明确执行它。优先使用食谱级超时；否则用外部超时包装命令。如果两者都存在，则尊重更严格的限制。
8. 使用适合实际日志格式的命令提取主要指标。如果提取为空，则在标记运行前检查最后几行日志和食谱的日志路径。
9. 在 TSV 中记录索引、分支、父提交、提交、食谱、指标名称、指标值、内存（GB）、经过时间（分钟）、启动器、作业 ID、命令、日志路径、状态和描述，以及足够的定时或计数信息以评估停止规则。
10. 在活动中定期打印面向用户的进度更新。包括当前分支、最新已知结果、尝试的实验数量、如果适用则剩余实验数量、如果适用则剩余活动时间，以及是否已满足任何停止条件。
11. 实验完成后重新检查监控的停止条件，并明确说明结果，例如 `stop condition not yet met: 17/24 attempted, 6h12m remaining` 或 `stop condition met: 24/24 attempted`。
12. 将结果标记为 `keep`、`discard` 或 `crash`，然后转移到下一个分支，除非用户指定的停止条件已明确满足。

对于基于计数的停止规则，计算尝试的想法数量，而不仅仅是成功或完全完成的运行。

对于活动时间预算，在活动开始时将用户限制转换为绝对截止日期，并持续检查剩余时间。

对于每个实验预算，对每个运行执行超时，并将超时视为失败。

示例：
- `do 50 experiments`：仅在 TSV 中存在 50 行尝试的实验后才停止
- `10h total, 1h each`：对每个运行执行 1 小时限制，并在达到 10 小时活动预算时停止，或当剩余预算不足以启动另一个 1 小时运行时停止
- `50 experiments or 10h total, 1h each`：监控所有三个值，从不超出每次运行的限制，并在一个活动级停止触发器明确达到时停止

## 优先级

优先考虑预期目标增益高且复杂度成本低的想法：
- 正确性和后端兼容性
- 提示和滚动格式
- 批次、序列和精度布局
- 优化器和调度器调整
- 奖励塑形、裁剪或缩放
- 数据集混合或验证更改
- 基于硬件的同步与异步执行

其他条件相同，优先考虑简单的胜利并避免易碎的硬件特定技巧。

## 避免

- 不要从配置不足的冒烟运行得出训练想法失败的结论。如果运行使用极小的批次大小、极少的优化器步骤或其他非代表性设置，将其视为管道验证；在标记为 `discard` 之前，扩展到有意义的批次大小并长时间训练以测试假设。
- 不要在紧密的编辑-运行-调试循环中重复支付批次调度器设置成本。如果 Slurm 批次作业有较大的启动成本，并且失败需要快速迭代，使用文档中记录的交互式 Slurm 模式或在进行更多批次作业前询问用户。
- 不要让上下文压缩或后续指导问题抹去原始活动目标。刷新 `nemo-rl-session-memory`，重新加载活动技能，并在用户明确更改它之前保留主要目标。

## 停止

如果用户给出明确的停止条件，它们将覆盖通用规则。不要因为搜索感觉足够而停止；仅在请求的计数、截止日期、预算或目标条件已明确满足时才停止。

在活动中，明确告知用户是否已满足停止条件。如果没有，以具体术语报告剩余计数、剩余时间或其他剩余阈值。

如果用户没有给出明确的停止条件，运行基线以及最多三个低风险实验，然后总结最佳结果并在继续前询问。
