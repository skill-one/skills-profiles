# 按CODEOWNERS分组拆分PR

将一个大的pull request拆分成多个较小的PR，每个PR尽量只涉及最少的CODEOWNERS审查组。目标是减少审查负担：仅涉及`megatron/core/`的PR只需要核心审查者，而同时涉及`examples/`、`tools/`和`megatron/training/`的PR则会引入许多额外的组。

## 先回答约束条件

对于拆分规划问题，在完整工作流程之前，应先提出以下约束条件：

- 每个PR的CODEOWNERS审查组数量应最小化，但每个生成的PR仍必须能够独立合并和审查。
- 测试代码应与它们验证的生产代码一起移动；不要为了减少审查组而将测试拆分到单独的PR中。
- 如果PR B依赖于PR A中重命名的符号，应指明依赖关系，并在需要时在PR A中添加向后兼容的别名、重新导出或shim。
- 在执行前等待用户批准。
- 执行会从正确的基线创建草稿PR，应用文件范围的diff（使用`git diff upstream/main..<source-branch> -- <paths> | git apply`），推送到用户的分支，并且永远不会直接推送到上游。

## 工作流程

### 1. 分析PR

1. 获取PR详细信息：`gh pr view <number> --repo NVIDIA/Megatron-LM --json title,body,headRefName,author` 和 `gh pr diff <number> --repo NVIDIA/Megatron-LM --stat`。同时确定当前的GitHub用户（使用`gh api user --jq .login`）。
2. 解析`.github/CODEOWNERS`文件，构建文件路径模式到所有者组的映射。
3. 对于PR中的每个已更改文件，确定需要审查它的CODEOWNERS组。
4. 构建按CODEOWNERS组分组的摘要表，显示哪些文件引入了哪些组。
5. 统计PR当前需要的不同审查组的总数。

### 2. 提出最小化每个PR审查组的拆分方案

主要优化目标：**最小化每个生成的PR所需的CODEOWNERS审查组数量**。

策略：
1. 按CODEOWNERS组对文件进行聚类。属于同一组审查者的文件自然应该放在一起。
2. 确定最大的聚类——这将成为第一个（通常是最大的）PR。
3. 剩余的文件形成一个或多个额外的PR，每个PR理想情况下只需要一个或两个审查组。
4. 如果拆分创建依赖关系（例如，PR B使用了PR A中重命名的符号），依赖的PR必须在第一个PR合并后合并。明确注明这一点。
5. 每个PR必须能够独立合并到main——没有损坏的导入，没有缺失的符号。第一个PR中的向后兼容别名和重新导出存根可以使这一点成为可能。

以表格形式呈现建议的拆分方案：
- PR名称/描述
- 包含的文件
- 所需的CODEOWNERS组
- 对其他PR的依赖（如有）

在继续之前等待用户批准。

### 3. 执行拆分（用户批准后）

对于每个新的PR：
1. 从适当的基线（`main`或依赖PR的分支）创建新分支。
2. 提取相关更改：`git diff upstream/main..<source-branch> -- <file paths> | git apply`。
3. 暂存、提交清晰的提交信息，并推送到用户的分支。
4. 将PR作为**草稿**创建（根据仓库贡献指南）。
5. 如果原始PR需要缩小范围，在强制推送前与用户确认。
6. 完成后报告所有PR链接。

## 重要指南

- 始终将PR作为**草稿**推送到用户的分支，永远不会直接推送到上游。
- 向后兼容的更改（别名、重新导出、弃用shim）应放在第一个PR中，以便后续PR可以依赖它们。
- 测试文件应与它们测试的生产代码一起移动，不应在单独的PR中。
- 倾向于每个拆分PR使用单个干净的提交，而不是重放原始提交历史。
- 如果文件难以分类（例如，它同时涉及两个组），应询问用户该文件应放入哪个PR。
- 如果当前的GitHub用户不是原始PR的作者，每个新的PR的描述必须明确归功于原始作者（例如，“原始更改由@<author>在#<number>中提出”）。
