# Xcode 构建修复工具

使用此技能来实施已批准的构建优化更改，并使用基准测试进行验证。

## 核心规则

- 仅应用已获得明确开发者批准的更改。
- 一次应用一个逻辑修复，以便更改可审查且可逆。
- 应用更改后重新基准测试，以验证改进。
- 准确报告发生了什么变化，哪些文件被修改，以及测量的增量。
- 如果更改没有带来改进或导致回归，请立即标记。

## 输入

修复工具期望以下之一：

- `.build-benchmark/optimization-plan.md` 中的已批准优化计划，带有勾选的批准框。
- 描述要应用的修复的明确开发者指令（例如，“将 `DEBUG_INFORMATION_FORMAT` 设置为 `dwarf` 用于调试”）。

当从优化计划工作時，请阅读批准检查清单，并仅实施勾选的项目。

## 修复类别

### 构建设置

将 `project.pbxproj` 值更改为与 [build-settings-best-practices.md](references/build-settings-best-practices.md) 中的建议匹配。

典型的修复：

- 将 `DEBUG_INFORMATION_FORMAT = dwarf` 设置为用于调试
- 将 `SWIFT_COMPILATION_MODE = singlefile` 设置为用于调试
- 启用 `COMPILATION_CACHE_ENABLE_CACHING = YES`
- 启用 `EAGER_LINKING = YES` 用于调试
- 对齐跨目标设置以消除模块变体

在编辑 `project.pbxproj` 時，通过匹配目标名称和配置名称定位正确的 `buildSettings` 块。应用更改后，使用 `xcodebuild -showBuildSettings` 进行验证。

### 脚本阶段

修复在增量或调试构建期间浪费时间的运行脚本阶段。

典型的修复：

- 添加输入和输出文件声明，以便 Xcode 可以跳过未更改的脚本。
- 添加配置守卫：`[[ "$CONFIGURATION" != "Release" ]] && exit 0` 用于仅限发布的脚本。
- 当列表很长時，将输入/输出列表移动到 `.xcfilelist` 文件中。
- 当声明了输入和输出時，启用 `Based on dependency analysis`。

### 源级编译修复

应用减少类型检查器和编译器开销的代码更改。有关前后模式的详细信息，请参阅 [references/fix-patterns.md](references/fix-patterns.md)。

典型的修复：

- 为复杂表达式添加显式类型注解。
- 将长链式或嵌套表达式分解为中间类型的变量。
- 当类没有被继承時，将其标记为 `final`。
- 为仅限内部的符号收紧访问控制 (`private`/`fileprivate`)。
- 将庞大的 SwiftUI `body` 属性提取为更小的组合子视图。
- 将深层嵌套的结果构建器代码替换为单独的 typed 辅助程序。
- 为传递给泛型函数的闭包添加显式返回类型。

### SPM 重组

重组 Swift 包以提高构建并行性并减少重建范围。

典型的修复：

- 将共享类型移动到较低层级的模块以消除循环或向上依赖。
- 按功能区域拆分过大的模块（200+ 文件）。
- 将协议定义提取到轻量级的接口模块中。
- 移除不必要的 `@_exported import` 使用。
- 对导入相同包的目标对齐构建选项，以防止模块变体重复。
- 将分支跟踪依赖项固定到标记版本或提交哈希，以进行确定性解析。

在应用版本固定更改之前：

- 运行 `git ls-remote --tags <url>` 确认标签存在。如果上游没有标签，则固定到特定的修订哈希。
- 在继续之前，使用 `xcodebuild -resolvePackageDependencies` 验证固定版本是否成功解析。

## 执行工作流

1. 读取已批准的优化计划或开发者指令。
2. 对于每个已批准的项目，确定要更改的确切文件和位置。
3. 应用更改。
4. 验证更改可以编译：运行快速 `xcodebuild build` 以确认没有引入错误。
5. 应用所有已批准的更改后，使用原始基线相同的输入重新基准测试：
   ```bash
   python3 scripts/benchmark_builds.py \
     --project App.xcodeproj \
     --scheme MyApp \
     --configuration Debug \
     --destination "platform=iOS Simulator,name=iPhone 16" \
     --output-dir .build-benchmark
   ```
6. 将更改后的中位数与基线进行比较并报告增量。

## 评估回归

并非每个较慢的数字都是真正的回归。修复工具必须在建议还原之前评估全局情况。

### 编译缓存权衡

像 `COMPILATION_CACHE_ENABLE_CACHING = YES` 这样的更改可能会使标准清理构建稍微变慢（缓存填充开销），同时使缓存清理构建显著变快。由于缓存清理构建反映了现实的开发者工作流程（分支切换、拉取更改、清理构建文件夹带有温暖的缓存），因此标准清理构建变慢而缓存清理构建变快是一种净改进，而不是回归。相同的逻辑适用于任何首次成本较高但后续构建受益的更改。

### 比较所有构建类型

一起评估标准清理、缓存清理（当可用時）和增量构建。只有当它使对开发者日常工作流程很重要的指标变得更差時，更改才是一个明确的回归。如果只有冷启动清理构建变慢，但开发者很少进行真正的冷启动，那么这可能是可以接受的。

### 单个更改与累积

单个更改如果自身导致回归，但如果它能够实现更大的累积改进（例如，启用编译缓存使一种构建类型变慢，但为其他所有内容解锁缓存优势），则仍然值得保留。

### 最佳实践设置不是还原候选

某些构建设置是苹果推荐的现代默认值。这些应该被应用并保留，无论立即基准测试是否显示可衡量的改进。它们不是投机性的优化——它们使项目与苹果的工具链方向保持一致，并且将在未来的 Xcode 版本中累积价值。修复工具绝不能根据单个基准测试结果建议还原这些设置。

应始终保留的最佳实践设置：

- `COMPILATION_CACHE_ENABLE_CACHING = YES` -- 苹果正在积极投资于此；缓存随着每个 Xcode 版本而改进，并在真实开发者工作流程中累积
- `EAGER_LINKING = YES` (Debug) -- 允许链接器与编译重叠
- `SWIFT_USE_INTEGRATED_DRIVER = YES` -- 消除进程间调度开销
- `DEBUG_INFORMATION_FORMAT = dwarf` (Debug) -- 避免不必要的 dSYM 生成
- `SWIFT_COMPILATION_MODE = singlefile` (Debug) -- 增量重新编译
- `ONLY_ACTIVE_ARCH = YES` (Debug) -- 没有必要在本地构建所有架构

在报告这些设置時，使用类似的语言：“应用了推荐的构建设置。未立即测量基准测试改进，但此设置与苹果推荐配置一致，并使项目为未来的 Xcode 改进做好了准备。”

### 建议还原時机（仅限投机性更改）

对于不是最佳实践设置的更改（例如，源代码重构、链接实验、脚本阶段修改、依赖项重组）：

- 如果累积通过显示所有测量构建类型（标准清理、缓存清理和增量）的墙上时钟回归，建议还原所有投机性更改，除非开发者明确要求为非性能原因保留特定项目。
- 对于每个单独的投机性更改：如果它没有显示中位数改进，也没有缓存/增量收益，请标记为 `Recommend revert` 并报告测量的增量。
- 区分“仅减少异常值”（改善了最坏情况但未改善中位数）和“中位数改进”（改善了典型开发者的等待时间）。
- 当更改在一种构建类型上权衡另一种构建类型時（例如，标准清理变慢但缓存清理变快），请清晰地呈现两个数字，并让开发者决定。将其表述为：“标准清理构建慢了 X.X 秒，但缓存清理构建（现实的日常工作流程）快了 Y.Y 秒。”

## 报告

以纯文本语言开头，报告墙上时钟结果：

> “您的清理构建现在需要 X.X 秒（之前是 Y.Y 秒）—— Z.Z 秒更快。”
> “您的增量构建现在需要 X.X 秒（之前是 Y.Y 秒）—— Z.Z 秒更快。”

然后包括：

- 更改后的清理构建墙上时钟中位数
- 更改后的增量构建墙上时钟中位数
- 两种构建类型的绝对和百分比墙上时钟增量
- 如果基准测试噪声很高，则包含置信度说明
- 每个修复修改的文件列表
- 与原始建议的任何偏差

如果累积任务指标有所改善但墙上时钟没有，请明确说明：“编译器工作负载减少但构建等待时间没有改善。当 Xcode 与其他同样长的任务并行运行这些任务時，这是预期的。”

如果修复没有产生可衡量的墙上时间改进，请注明 `No measurable wall-time improvement` 并建议保留（例如，出于代码质量原因）或还原。

对于因非基准测试原因（确定性包解析、分支切换缓存）很有价值的更改，请标记为：“此更改不会带来等待时间改进。好处是 [确定性构建 / 更快的分支切换 / 降低 CI 成本]。”

注意：`COMPILATION_CACHE_ENABLE_CACHING` 在测试的项目中已被测量为清理构建快 5-14%（87 到 1,991 Swift 文件）。在真实开发者工作流程中，缓存在构建之间持续存在，因此这种好处会累积——分支切换、拉取更改和具有持久 DerivedData 的 CI。基准测试脚本会自动检测此设置，并运行缓存清理阶段进行验证。

## 执行报告

优化通过完成后，生成一个结构化的执行报告。这为开发者提供了一个清晰的摘要，说明了尝试了什么，什么有效，以及最终状态是什么。

结构：

```markdown
## 执行报告

### 基线
- 清理构建中位数：X.X 秒
- 缓存清理构建中位数：X.X 秒（如果适用）
- 增量构建中位数：X.X 秒

### 已应用的更改

| # | 更改 | 可操作性 | 测量结果 | 状态 |
|---|------|----------|----------|------|
| 1 | 描述 | repo-local | 清理：X.X→Y.Y，增量：X.X→Y.Y | 保留 / 还原 / 阻止 |
| 2 | ... | ... | ... | ... |

### 最终累积结果
- 清理构建中位数：X.X 秒（之前是 Y.Y 秒）—— Z.Z 秒更快/更慢
- 缓存清理构建中位数：X.X 秒（之前是 Y.Y 秒）—— Z.Z 秒更快/更慢
- 增量构建中位数：X.X 秒（之前是 Y.Y 秒）—— Z.Z 秒更快/更慢
- **净结果**：更快 / 更慢 / 不变

### 被阻止或不可操作的发现
- 发现：无法从代码库中解决的原因
```

状态值：

- `保留` -- 更改改善了或维持了构建时间，并且被保留。
- `保留（最佳实践）` -- 更改是推荐的构建设置；无论立即基准测试结果如何，都保留。
- `还原` -- 更改使构建时间变差，并且被还原。
- `阻止` -- 由于项目结构、Xcode 行为或外部约束，无法应用更改。
- `无改进` -- 更改编译，但没有可衡量的墙上时间收益。包括是否保留（出于非性能原因）或还原。
