# Sentry 博客写作技巧

这项技巧旨在确保每篇 Sentry 博客都符合我们的写作标准——无论你是帮助工程师撰写他们的第一篇博客，还是让市场人员起草产品公告。

**标准：** 每篇 Sentry 博客都应该是资深工程师会在团队 Slack 中分享的内容，或者是在技术决策中参考的内容。

以下是需要内化和应用于每一篇内容的核心理念。

## Sentry 的声音

**我们听起来像：** 在会议后的派对上，一位资深开发者正兴奋地解释某个他们真正感兴趣的东西——聪明、具体、略带不羁、知识渊博。

**我们听起来不像：** 公司博客、新闻稿、销售演示或 AI 生成的摘要。

保持技术精确性、有观点、直接明了。幽默是受欢迎的，但应该服务于内容，而不是取代内容。讽刺有效。每篇博文一个笑话就足够了。

使用“我们”（Sentry）和“你”（读者）。这是一场对话，不是一篇论文。

## 禁止使用的语言

永远不要使用这些语言。它们是自动的红旗：

- “我们很兴奋/激动地宣布”——直接宣布即可
- “顶级”、“行业领先”、“尖端”——展示，不要说教
- “无缝的”/“无缝地”——没有什么是无缝的
- “赋能”/“利用”/“解锁”——说出你实际的意思
- “稳健的”——描述是什么让它稳健
- “在 [公司]，我们相信……”——直接陈述信念
- “简化”——每个人都在简化，停止
- 填充性过渡：“话虽如此”、“值得注意的是”、“归根结底”、“毫不迟疑”、“你可能知道”
- “在本篇博客中，我们将探讨……”——直接切入，直接开始

## 开头（前 2-3 句）

开头必须做两件事中的一个：**陈述问题**或**陈述结论**。永远不要以背景、公司历史或炒作开头。

**好：** “发布前两周，我们砍掉了整个指标产品。这是为什么预聚合时间序列指标在调试时会失效，以及我们如何从头开始重建系统的原因。”

**差：** “在 Sentry，我们一直在寻找改善开发者体验的方法。今天，我们很激动地分享一些我们认为你会喜欢的指标产品的更新。”

## 结构：遵循读者的疑问

围绕读者实际想知道的内容来组织每一篇博文，而不是你的内部叙述：

1. **这个问题解决了什么？**（最多 1-2 段）
2. **它实际上是如何工作的？** 不是按钮，而是底层技术。（文章主体——要具体）
3. **有哪些权衡或替代方案？**（这区分了优秀与卓越）
4. **我该如何使用/尝试/实现这个？**（具体的下一步）

对于工程深度解析，还需要解决：

5. **我们尝试了哪些行不通的方法？**（建立信任）
6. **已知的局限性是什么？**（展现智力诚实）

## 易于浏览的格式

人们会滚动。更短的段落几乎总是更好的阅读体验。

**在对比点处断开段落。** 当一个句子引入“但是”、“然而”或转换视角时，开始一个新段落。不要把转折埋在一段文字中。

**差：**
> 传统监控跟踪请求和延迟。这对无状态 HTTP 服务有效。AI 代理不同。单个运行可能涉及多个 LLM 调用、工具执行和交接。

**好：**
> 传统监控跟踪请求和延迟。这对无状态 HTTP 服务有效。
>
> AI 代理不同。单个运行可能涉及多个 LLM 调用、工具执行和交接。

对比点前的换行会创造视觉强调。这在网络写作中是标准的，即使它打破了传统的段落规则。

**每个段落一个想法。** 如果一个段落涵盖两个不同的点，就把它分开。三个句子的段落是好的。一个句子的段落也是好的，用于强调。

**不要使用破折号。** 使用逗号、句号或换行代替。破折号在印刷品中是好的，但在博客格式中会造成视觉杂乱。

## 开发者内容的 SEO

当针对一个有竞争力的搜索查询时：

**通用的在前，具体的在后。** 博文的头 50-60% 应该是工具无关的教育内容（定义、概念、指标、最佳实践）。在第二部分引入你的产品作为实现示例。Google 对信息查询的指南排名高于产品页面。

**将关键词放在 H2 中。** 通用标题对搜索不可见。“AI 代理监控的关键指标”优于“要测量什么”。（见下文**章节标题**的示例）

**包含定义性部分。** 对于任何头术语（“代理可观察性”、“错误监控”），排名靠前的页面几乎总是有一个“什么是 X？”部分。即使感觉基础，也要包含一个。

**添加 FAQ。** 在博文底部添加 3-4 个针对长尾关键词的问题。这些问题可以赢得特色片段和“人们也在问”框。

## 避免的 AI 写作模式

LLM 生成的文本有特征。标记并重写这些模式：

**顿挫式的戏剧性片段。**
- 差：没有错误。没有警告。一切正常。
- 好：没有错误，没有警告，一切看起来都很好。

**标语式的格言。**
- 差：你无法修复你看不到的问题。
- 好：没有对完整请求周期的可见性，你只是在猜测。

**三拍式揭示。**
- 差：不是配置问题。不是代码错误。部署是陈旧的。
- 好：不是配置问题或代码错误。部署是陈旧的。

**自以为是的简单。**
- 差：[代码块] “就是这样。你需要的一切。”
- 好：[代码块] 然后解释代码的作用，或者直接继续。

**平行结构的广告文案。**
- 差：指标告诉你哪里出了问题。跟踪记录告诉你为什么。
- 好：指标显示哪里出了问题，但跟踪记录才是你实际找出原因的地方。

**只在书签处有个性。** AI 草稿以个人轶事开头，在 80% 的文章中变得客观，然后在结尾处加上 CTA。作者的声音应该贯穿始终。
- 差：个人介绍 → 临床中间 → “免费试用 Sentry。”
- 好：第一人称作为旁注贯穿全文：“这部分让我卡住了” / “我会责怪错误的服务。”

## 章节标题必须传达信息

**弱：** “背景”、“架构”、“结果”、“结论”

**强：** “为什么时间序列预聚合破坏了调试上下文”、“分布式 GROUP BY 的散集方法”、“哪里会出问题：基数墙”

## 技术质量标准

**数字胜于形容词。** 如果你做出性能声明，请包含数字。
- 差：这显著减少了我们的错误处理时间。
- 好：这将我们的 p99 错误处理时间从 340 毫秒减少到 45 毫秒——提高了 7.5 倍。

**代码必须能工作。** 如果博文包含代码，请测试它。包含导入、配置和上下文。注释应解释*为什么*，而不是*什么*。

**系统图。** 如果你描述一个包含两个以上交互组件的系统，请包含一个图。用真实的服务名称标记，而不是通用的框。

**诚实胜于炒作。** 永远不要夸大功能的作用。承认局限性。如果某项功能处于 Beta 版本，请说明。如果竞争对手做得好，指出这一点是可以的。不要声称 AI 功能比实际更强大——“Seer 建议一个可能的根本原因”≠“Seer 找到了根本原因。”

## 标题指南

标题是博文中最具杠杆作用的句子。它必须阻止开发者在 RSS 订阅或 Twitter 上滚动。

**好的标题**做出具体声明、讲述故事或承诺具体回报：
- “我们构建的指标产品工作正常。但我们还是砍掉它并重新开始”
- “我们通过修复 Salt 将发布延迟减少了 5%”
- “你的 JavaScript 包含 47% 的死代码。这里是如何找到它”

**差的标题**是模糊的公告：
- “推出我们的新指标产品”
- “Sentry 中的性能改进”
- “使用 Seer 进行 AI 驱动的调试”

## 结尾

以有用的内容结束：指向文档、源代码、试用方法或提供反馈的方式。永远不要以通用的炒作（“我们迫不及待想看到你构建什么！”）、重述你刚刚说过的话或产品页面的 CTA（“免费试用 Sentry。所有计划都包含在内”）结束。与开头的故事联系起来，或者给读者一个具体的下一步行动。

## 博文类型

以下是按博文类型划分的快速指南：

| 类型 | 目标 | 作者署名 |
|------|------|--------|
| 工程深度解析 | 解释技术系统/决策，让其他工程师学习 | 构建它的工程师。总是。 |
| 产品发布 | 解释已发布的内容、为什么它很重要、如何使用它 | 产品经理、工程师或开发者体验。除非是市场人员构建的，否则不是产品营销经理。 |
| 事后分析 | 透明的失败分析，包含时间线和修复方案 | 工程领导层 |
| 数据/研究 | Sentry 独特数据位置的原始见解 | 数据团队、工程或研究 |
| 教程/指南 | 帮助开发者完成特定任务 | 开发者体验、工程师或社区贡献者 |

## “我会分享这篇博文吗？”测试

在发布之前，问：开发者会分享这篇博文吗？它有希望在 Hacker News 上获得一席之地吗？如果答案是否定的，这篇博文要么需要更多深度，要么需要更多原创见解，要么它应该放在版本更新日志中。

值得分享的博文至少包含以下一项：

- 解释了技术决策及其权衡
- 原始数据或研究，其他地方找不到
- 具有具体细节的现实世界调试故事
- 对某事出错的诚实记录
- 节省读者实际时间的操作指南

## 非协商事项（快速参考）

1. 没有真实人物的署名，不要发布。不要“Sentry 团队”的署名。
2. 不要发布无法工作的代码。
3. 不要说“我们很兴奋地宣布”。直接宣布即可。
4. 如果你描述一个系统，请包含一个图。
5. 如果你做出性能声明，请包含数字。
6. 如果你讨论一个决策，解释你为什么没有选择其他方案。
7. 每篇博文在写作前，作者必须清楚“这是为谁写的”。
8. 版本更新日志属于版本更新日志。博客文章应该提供更多价值。
9. 疑虑时，深入挖掘。过于肤浅的风险远大于过于详细。
10. 写出你试图解决这个问题时希望存在的博文。

## 在审阅或编辑草稿时

运行两个清单：

**技术审阅：**
- 所有技术声明准确
- 代码示例可以工作
- 架构描述与现实相符
- 数字和基准正确
- 没有过于简化的内容会让专家感到不适

**编辑审阅：**
- 开头在 2 句内吸引读者
- 通过“我会分享这篇博文吗？”测试
- 没有企业语言、填充或废话
- 章节标题传达信息
- 合适的长度（不填充，不单薄）
- 标题具体且引人入胜

**最终检查：**
- 作者署名正确（真实人物的名字）
- 包含指向文档/入门的链接
- 博文没有重复版本更新日志中的内容

在提供反馈时，要具体和建设性。引用薄弱的部分，解释为什么它薄弱，并重写它以符合标准。
