# 创建 Sentry SDK 技能包

生成一个完整、基于研究的 SDK 技能包——一个主向导 SKILL.md，以及针对 SDK 支持的每个功能支柱的深入参考文件。

## 在何时调用此技能

- 请求为新的平台“创建 Sentry SDK 技能”
- 请求为 sentry-agent-skills 添加对 “[语言/框架]” 的支持
- 构建新的 `sentry-<平台>-sdk` 技能包
- 将 SDK 技能模式移植到新的 Sentry SDK

> 首先阅读 `${SKILL_ROOT}/references/philosophy.md`——它定义了此技能实现的包架构、向导流程和设计原则。

---

## 第一阶段：确定 SDK

确定你要为哪个平台创建技能：

```bash
# 什么 SDK？包名是什么？
# 示例：sentry-go, @sentry/sveltekit, sentry-python, sentry-ruby, sentry-cocoa
```

建立**功能矩阵**——这个 SDK 支持哪些 Sentry 支柱？

| 支柱 | 检查文档 | 备注 |
|------|---------|------|
| 错误监控 | 始终可用 | 不可协商的基线 |
| 跟踪/性能 | 通常可用 | 检查是否有 span API |
| 分析 | 变化 | 可能被移除或处于实验阶段 |
| 日志记录 | 新功能 | 检查最低版本 |
| 指标 | 新功能 | 检查最低版本 |
| 定时任务 | 后端仅限 | 前端 SDK 不适用 |
| 会话回放 | 前端仅限 | 后端 SDK 不适用 |
| AI 监控 | 某些 SDK | 通常仅限 JS + Python |

**参考现有的 SDK 技能**以了解目标质量水平：

```bash
ls skills/sentry-*-sdk/ 2>/dev/null
# 阅读 1-2 个现有的 SDK 技能作为模式参考
```

## 第二阶段：研究

**这是最关键的阶段。** 技能质量完全取决于准确、最新的 API 知识。不要凭记忆编写技能——根据官方文档研究每个功能。

### 研究策略

使用 `claude` 工具（带 `outputFile` 参数）**分叉并行研究任务**——每个功能区域一个任务。每个任务应：

1. 访问该功能的官方 Sentry 文档页面
2. 访问 SDK 的 GitHub 仓库以验证源级 API
3. 将详细的研究结果写入专门的研究文件

阅读 `${SKILL_ROOT}/references/research-playbook.md` 获取详细的研究执行计划，包括提示模板和文件命名约定。

### 研究 Sentry 向导

在深入研究功能之前，检查 Sentry 向导 CLI 是否支持此框架：

```bash
# 检查 SDK 的文档着陆页以获取向导说明
# 访问：https://docs.sentry.io/platforms/<平台>/
# 查找：“npx @sentry/wizard@latest -i <集成>”
```

如果存在向导集成：

1. 记录确切的向导命令和 `-i` 标志
2. 记录向导创建/修改的内容（文件、配置、构建插件）
3. 注意向导**交互式处理认证**——登录、组织/项目选择和认证令牌创建/下载都自动发生
4. 注意向导是否设置**源映射上传**——这对前端 SDK 至关重要
5. 这将成为生成技能第三阶段中的“选项 1：向导（推荐）”

> **为什么这很重要：** 向导自动处理整个认证流程（登录、组织/项目选择、认证令牌）和源映射上传配置。没有源映射，生产堆栈跟踪显示的是压缩代码——这使得 Sentry 对于前端调试几乎毫无用处。而且没有认证令牌，源映射根本无法上传。向导是唯一能在一步中正确处理这两者的方法。

### 研究批量处理

按主题区域批量研究任务。尽可能并行运行它们：

| 批量 | 主题 | 输出文件 |
|------|------|---------|
| 1 | 设置、配置、所有初始化选项、框架检测 | `research/<sdk>-setup-config.md` |
| 2 | 错误监控、恐慌/异常捕获、作用域、增强 | `research/<sdk>-error-monitoring.md` |
| 3 | 跟踪、分析（如果支持） | `research/<sdk>-tracing-profiling.md` |
| 4 | 日志记录、指标、定时任务（如果支持） | `research/<sdk>-logging-metrics-crons.md` |
| 5 | 会话回放（前端仅限）、AI 监控（如果支持） | `research/<sdk>-replay-ai.md` |

**重要：** 告知每个研究任务将其输出写入文件（`outputFile` 参数）。不要内联消耗研究结果——它们很大（每个 500–1200 行）。工作器将稍后从磁盘读取它们。

### 研究质量门禁

在继续之前，验证每个研究文件：

- 包含实际内容（不仅仅是 Claude 的过程笔记）
- 包含带有真实 API 名称的代码示例
- 包括最低 SDK 版本
- 涵盖框架特定变体

```bash
# 快速验证
for f in research/<sdk>-*.md; do
  echo "=== $(basename $f) ==="
  wc -l "$f"
  grep -c "^#" "$f"  # 应该有多个标题
done
```

**重新运行任何产生少于 100 行的研究任务**——它很可能无声失败。

## 第三阶段：创建主 SKILL.md

主 SKILL.md 实现了哲学文档中的**四阶段向导**。保持其专注——主文件应涵盖向导流程、快速启动配置、框架表格和参考调度；单个功能的深入细节应放在 `references/` 文件中，而不是这里。要全面但不要重复。

### 首先收集上下文

在编写之前，运行一个 scout 或阅读现有技能以了解约定：

- 前置模式（名称、描述、许可证）
- “调用此技能时”触发短语
- 表格格式和代码示例样式
- 故障排除表格约定

### SKILL.md 结构

```markdown
---
name: sentry-<platform>-sdk
description: <平台> 的完整 Sentry SDK 设置。在请求“为 <平台> 添加 Sentry”、“安装 <包>”或配置错误监控、跟踪、[功能] 对于 <平台> 应用时使用。支持 [框架]。
license: Apache-2.0
---

# Sentry <平台> SDK
```

### 主 SKILL.md 的关键原则

1. **保持简洁**——深入细节放在参考中，不在这里
2. **框架 SDK 首选向导**——如果 Sentry 向导支持此框架，在任何手动设置之前将其呈现为“选项 1：向导（推荐）”。**向导需要交互式浏览器登录，并且不能由代理运行**——在块引用中告诉用户将命令复制粘贴到自己的终端中，完成后回来。如果用户跳过向导，代理将进行完整的手动设置。参见 `${SKILL_ROOT}/references/philosophy.md` 获取完整模式。
3. **源映射对前端/移动不可协商**——手动设置路径必须包括源映射上传配置（构建工具插件 + 环境变量）。没有源映射，生产堆栈跟踪是不可读的压缩代码。
4. **检测命令必须是真实的**——对实际项目进行测试
5. **推荐逻辑必须是意见性的**——“始终”、“当 X 检测到”，而不是“可以考虑”
6. **快速启动配置应使用合理的默认值启用最多功能**
7. **框架中间件表格**——确切的导入路径、中间件调用和怪癖
8. **积极交叉链接**——如果 Go 后端，建议前端。如果 Svelte 前端，建议后端。

## 第四阶段：创建参考文件

每个 SDK 支持的功能支柱一个参考文件。这些是深入分析——它们可以比主 SKILL.md 更长。

### 参考文件结构

```markdown
# <功能> — Sentry <平台> SDK

> 最低 SDK: `<包>` vX.Y.Z+
## 配置

## 代码示例
### 基本用法
### 高级模式
### 框架特定说明（如果适用）

## 最佳实践

## 故障排除
| 问题 | 解决方案 |
|------|---------|
```

### 什么构成一个良好的参考

阅读 `${SKILL_ROOT}/references/quality-checklist.md` 获取完整的质量标准。

要点：

- **可工作的代码示例**——不是伪代码，不是截断的片段
- **配置选项表格**——类型、默认值、最低版本
- **每个模式一个完整示例**——不要展示同一事物的 5 个变体
- **框架特定说明**——指出框架行为差异时
- **顶部最低 SDK 版本**——始终
- **诚实地说明限制**——如果功能被移除（如 Go 分析），请说明

### 特定功能的指导

| 功能 | 关键要点 |
|------|---------|
| 错误监控 | 捕获 API、恐慌/异常恢复、作用域、增强（标签/用户/面包屑）、错误链、BeforeSend、指纹识别 |
| 跟踪 | 样本率、自定义 span、分布式跟踪、框架中间件、操作类型 |
| 分析 | 样本率配置、如何附加到跟踪，或诚实地“移除/不可用” |
| 日志记录 | 启用标志、日志记录器 API、与流行日志记录库的集成、过滤 |
| 指标 | 计数器/仪表/分布 API、单位、属性、基数最佳实践 |
| 定时任务 | 检查 API、监控配置、计划类型、心跳模式 |
| 会话回放 | 回放集成、样本率、隐私掩码、画布/网络录制 |

> **前端/移动 SDK 的注意**：源映射上传配置属于主 SKILL.md（第三阶段：指导），而不是参考文件。它是核心设置流程的一部分——每个前端生产部署都需要它。涵盖构建工具插件、所需环境变量（`SENTRY_AUTH_TOKEN`、`SENTRY_ORG`、`SENTRY_PROJECT`），并将 `.env` 添加到 `.gitignore` 中。

## 第五阶段：验证所有内容

**绝对不要跳过此阶段。** SDK API 经常变化。研究可能会产生幻觉。工作器可能会编造配置键。

### API 验证

针对 SDK 的实际源代码运行专门的验证过程：

```
研究提示：“针对 <SDK> GitHub 仓库源代码验证这些特定的 API 名称和签名：[列出技能文件中的每个 API]”
```

常见错误：

- 配置选项名称大小写错误（`SendDefaultPii` vs `SendDefaultPII`）
- 编造的不存在的配置键（`experimental.tracing`——验证它是否真实）
- 使用过时的 API 而不是现代替代品（`configureScope` → `getIsolationScope`）
- 将已移除的功能列为可用（Go SDK 中的分析）
- 最低版本号错误

### 审查过程

对完整的技能包运行审查器：

- 代码示例的技术准确性
- 主 SKILL.md 和参考文件之间的一致性
- 与仓库中现有 SDK 技能的一致性
- 代理技能规范合规性（前置、命名）

### 修复审查发现

按优先级分类：

- **P0**：误导性声明（宣传已移除的功能）——立即修复
- **P1**：不正确的 API、已弃用的方法——合并前修复
- **P2**：样式不一致、版本细节——如果快速则修复
- **P3**：跳过

## 第六阶段：注册和更新文档

技能通过审查后：

1. **更新 README.md** — 添加到 SDK 技能表格
2. **更新 AGENTS.md** — 如果哲学文档或技能类别部分需要
3. **添加使用示例** — 使用部分中的触发短语
4. **记录包模式** — 如果这是新的 SDK，注意 references/ 结构

### 提交策略

每个主要部分都有自己的提交：

1. `feat(<平台>-sdk): 添加 sentry-<平台>-sdk 主 SKILL.md 向导`
2. `feat(<平台>-sdk): 为所有功能支柱添加参考深入分析`
3. `docs(readme): 将 sentry-<平台>-sdk 添加到可用技能`
4. `fix(skills): 解决审查发现`（如果有）
