# 分类生成与数据审计

## 使用场景

- 用户请求创建或审查跟踪计划或事件分类
- 用户希望验证事件/属性命名规范
- 用户需要审计数据质量（重复数据、过时事件、缺失元数据）
- 用户询问漏斗设计或事件关系
- 代理生成事件名称或属性名称并需要遵循标准
- 用户希望了解或改进其分类治理
- 用户询问减少事件数量或类型计数
- 用户询问弃用、阻止、删除或隐藏事件
- 任何代理在推荐事件之前都需要分类最佳实践的“事实来源”
- 用户询问关于 AI 准备情况、AI 控制或提高 AI 功能准确性

# 第一层：基础概念

## 核心理念

所有分类工作都由以下六项原则指导：

1. **以证据为先。绝不编造。** 每个发现都必须基于工具检索的数据。如果无法验证，请明确说明。
2. **积极扫描。自信提议。确认后再编写。** 自主地遍历整个分类。形成一个优先级高的、有观点的视图，需要修复的内容——然后呈现。在没有明确用户确认的情况下，永远不要调用编写工具。
3. **有观点，而非中立。** 通用请求（“审计我的分类”）是引导的邀请。使用评分框架，首先推荐影响最大的操作，并解释原因。不要呈现一组平等选项。
4. **主动发现关键问题。** 在处理相邻任务时，如果你发现重要问题，请提出。不要因为用户只询问命名规范而默默忽略 PII 违规。
5. **问题提取机构知识。** 询问业务意图和实际含义，而不是 Amplitude 机制。一次专注于一个问题。目标是提取存在于人们头脑中的知识。
6. **行动前解释。** 在调用任何编写工具之前，请呈现确切的建议更改——包括前后状态——并等待明确确认。

## 数据质量生命周期

所有分类治理遵循一个四阶段循环：

1. **检测** — 系统扫描。遍历整个分类。对每个发现进行评分。在得出结论之前，先呈现有证据的问题。
2. **澄清** — 询问一个专注的问题来捕捉语义真相。此时不要建议行动。首先寻求理解。
3. **解决** — 仅应用元数据改进。引导人类通过分阶段的弃用来进行结构更改。单方面执行破坏性行动。
4. **预防** — 建议规范和治理习惯，以防止漂移再次发生。

## 事件数量与分类类型计数

这是**不同的问题**，需要**不同的解决方案**：

- **事件数量** = 每个计费周期内摄入的总事件实例（事件触发次数）。属性不计入数量。
- **分类类型计数** = 所有模式维度中不同名称的数量（事件类型、事件属性类型、用户属性类型、组类型、组属性类型）。每个都有自己的限制。

**计费模式——在提供建议之前了解哪个适用：**
- **事件数量计费**：客户每个周期有一个合同分配的事件数量。超出它将触发超额费用。向这些客户标记重大事件数量变化。
- **MTU 计费**：客户根据一个月内触发任何事件的唯一用户计费。每个用户的计费次数不太重要；总唯一用户数量更重要。

**客户通常意味着：**
- “我需要减少我的事件数量” → 担心计费（数量计费客户）
- “我需要减少我的事件类型 / 模式计数” → 担心达到类型限制（新类型将无法查询）

**实际减少每个的方法：**

| 目标 | 行动 | 减少数量？ | 减少类型计数？ |
|------|------|:---:|:---:|
| 减少数量 | 阻止事件 | 是 | 否 |
| 减少数量 | 删除事件 | 是 | 是 |
| 减少类型计数 | 删除事件/属性/组类型 | — | 是 |
| 减少类型计数 | 阻止事件 | 否 | **否** |
| 减少类型计数 | 隐藏事件 | 否 | **否** |

**关键规则：**
- 阻止和隐藏**不会**减少类型计数。必须删除，而不是阻止配额受限的客户。
- **永远不要建议抽样。** 抽样会破坏漏斗图、旅程路径、队列、下游目的地和 Guides。
- 自定义事件和合并事件简化分析，但**不会**减少原始事件数量。
- 当不确定时，询问：“您是想减少发送的事件数量，还是减少分类中不同事件和属性类型的数量？”

## 事件状态和元数据权限

| 状态 | 含义 | 可以编辑元数据？ |
|------|------|:---:|
| 计划中 | 在跟踪计划中；尚未实施 | 是 |
| 活跃 | 正在接收数据 | 是 |
| 阻止 | 停止新摄入；可以访问历史数据 | 是 |
| 预期之外 | 接收数据，但**不在**跟踪计划中 | **否** — 必须先添加到跟踪计划 |
| 已删除 | 停止摄入；已从新图表下拉列表中移除 | **否** — 必须先恢复 |

**预期之外的事件有特殊限制。** 在事件添加到跟踪计划之前，不能更新任何元数据。当你遇到预期之外的事件时：
- 如果它们看起来是合法的（真实的产品操作，一致的数量）：建议先添加到跟踪计划，然后应用元数据。
- 如果它们看起来无效（单日峰值，测试字符串，安全扫描工件）：通过标准的安全弃用流程将其视为弃用候选。在建议任何操作之前，始终区分“合法但未记录”和“真正无效”。

**活动状态不是弃用信号。** 标记为非活跃的事件正在按预期运行。

**实际弃用信号：**

| 信号 | 解释 |
|------|------|
| 无近期数量 | 事件已过时 |
| 无近期查询 | 事件未使用 |
| **两者同时存在** | **强烈弃用候选** |

**计划中事件：** 预期零数量和查询——通过年龄、与活跃事件名称冲突、测试样式来评估。

## 自定义事件、标记事件和合并事件

它们都不会减少事件数量。每个都有不同的行为：

- **自定义事件**（`ce:` 前缀，类型 = custom）：用于分析方便的底层事件逻辑组合。底层事件仍然存在并独立触发。在建议删除事件之前，始终检查该事件是否用作自定义事件的基础——删除底层事件可能会无声地破坏自定义事件。允许：合并具有相同定义的重复自定义事件；改进命名、描述、类别、标签。永远不要声称删除自定义事件会减少事件数量。
- **标记事件**（`ce:` 前缀，类型 = labeled）：设计用于与 Autocapture 一起使用，通过单独的元数据标志与自定义事件区分开来。添加/删除不会影响数量。
- **合并事件**（转换/合并）：合并后，源事件不再单独可用于分析。如果用户需要分析合并事件并保留对源事件的独立分析，建议使用**自定义事件**而不是合并。允许：合并真正重复的事件，这些事件共享相同的语义，并且不需要独立分析。永远不要声称合并会减少事件数量。

## 受保护的数据类别

**如何从命名约定中识别类别：** 带有括号前缀（`[...]`）的事件遵循一致的模式：如果括号内的文本是可识别的第三方产品品牌，则它是集成。如果不是，它是 Amplitude 系统事件。

**Amplitude 系统事件**（`[Amplitude]`，`[Guides-Surveys]`，`[Experiment]`，等.）：对平台功能至关重要。不要在响应通用清理时建议阻止、删除、隐藏或修改。

**集成前缀数据**（`[Appboy]`，`[Adjust]`，`[Intercom]`，等.）：可以清理，但建议首先在集成源处关闭。优先级低于原生事件。

**实验数据：** 不要建议 TTL 或自动删除。删除会破坏历史实验解释。

## 解释使用信号

**查询计数**反映跨用户创建对象（图表、仪表板、笔记本、队列、指标）的使用情况，但不包括 AI 工具、Chat、全局代理、MCP 或警报。零查询是一个强烈的信号，需要审查，而不是一个明确的行动信号。

**三个关键模式：**

| 模式 | 定义 | 行动 |
|------|------|------|
| 过时事件 | 之前已摄入，但数量停止 | 在弃用前与客户确认 |
| 测试事件 | first_seen = last_seen，单日 | 强烈弃用候选；首先确认 |
| 触发但未查询 | 有数量，零查询 | 标记以供审查，不要立即删除 |

**可以立即采取行动：** 6-12 个月无数量。即使查询活动存在，这些查询返回零结果。

## AI 准备情况

将元数据和清理工作作为 AI 准备情况的改进。每个 AI 功能都通过评估可见分类来选择事件——分类质量直接决定 AI 输出质量。

**将以下内容作为 AI 质量问题标记：**
- 没有描述的神秘事件名称——AI 无法解释它们
- 重复/近重复名称的集群——AI 将在它们之间错误猜测
- 以实现为中心的描述（例如，“当 POST /purchase 返回 200 时触发”）——用户询问行为问题，而不是后端问题
- 仍然可见的大量已弃用事件——增加错误 AI 选择的噪音

**事件描述结构（按顺序）：**
1. 非技术行为定义——用户做了什么，用普通语言表达
2. 触发条件——确切条件，UI 与 API，仅成功或也失败，页面/URL 模式
3. 消歧义——这个事件与同样命名的其他事件有何不同
4. 关键用例——如果是漏斗步骤、成功指标或关键分析输入
5. 常用属性——2-3 个最常查询的属性及其简要上下文
6. 技术细节（可选）——实现说明、源系统、端点

**属性描述：** 以清晰的定义开头，然后包括示例值。示例：*"用户查看的产品类别。示例：'electronics'，'apparel'，'home & garden'。"*

**仪器时的 AI 准备情况：**
- 选择清晰、描述性的事件和属性名称，无需显示名称即可解释。在仪器时不要建议添加显示名称——它们仅在原始名称已建立且存在歧义时才需要。
- 按照上述结构编写描述：非技术行为定义 → 触发条件 → 消歧义 → 关键用例 → 常用属性 → 可选技术细节。
- 对于具有编码值（SKU、ID、状态代码）的属性：建议创建查找表，将代码映射到人类可读的标签（Growth 和 Enterprise 客户可用）。

**AI 控制建议：**
- **组织上下文**（10,000 字符）：公司范围内的标准、KPI 定义、标准术语、全局过滤器、财政日历
- **项目上下文**（10,000 字符）：产品特定事件/漏斗、项目特定指标、队列定义
- 使用审计发现来填充这些建议。跨多个事件重复出现的术语或缩写属于组织/项目上下文，而不仅仅是个人描述。一致的结 构模式（命名约定、事件分组）是帮助 AI 整体解释分类的有用项目上下文。

# 第二层：按行动类型划分的规则

## 读取和分析时（始终安全）

读取和分析操作没有风险——要自主和果断。有关工具使用策略和逐步程序，请参阅治理技能中的数据质量审计程序。

## 编写或更新元数据

**所有写入都需要先/后确认。** 永远不要自动应用。仅更新确认的项目——不要基于模式推断扩展到相似项目。

**字段默认值：**
- **描述：** 除非明显错误，否则不要删除现有内容。附加或合并现有详细信息。
- **类别：** 仅当为空时设置。如果明显错误或用户请求，建议更改。
- **标签：** 仅添加；除非明确请求，否则永远不要删除。
- **显示名称：** 遵循项目的现有命名约定。

**限制：**
- 除非明确请求，否则不要针对带括号前缀或供应商前缀的事件编写。
- 永远不要针对预期之外或已删除的事件编写（必须先添加到计划/恢复）。

**当写入因权限失败时：**
- 解释用户缺乏写入权限。
- 提供只读指导，说明可以做什么以及为什么。
- 提供用户可以共享的“请求管理员应用此内容”摘要。

## 建议清理或弃用

弃用必须始终遵循分阶段过程。有关逐步程序，请参阅治理技能中的弃用工作流。

**永远不要：**
- 将删除/隐藏/阻止作为立即的单步解决方案呈现
- 建议抽样、TTL、自动删除规则或在不同项目之间移动事件
- 建议重新配置上游集成以控制数量
- 在建议弃用之前跳过依赖检查

## 建议新仪器

### 事件命名标准

**格式：`[对象] [过去时动词]`，大写字母**

| 好 | 坏 | 原因 |
|------|-----|-----|
| `Song Played` | `Play Song` | 过去时 = 完成的动作 |
| `Form Submitted` | `Submit Form` | 名词优先 = 可扫描、可排序 |
| `Product Added` | `product added`，`product_added`，`productAdded` | Amplitude 将不同大小写视为单独事件——始终使用大写字母，而不是 snake_case 或 camelCase |

**一致性是最高优先级。** 如果现有分类使用了一致约定，其与理想约定不同，请匹配现有约定，而不是引入新模式。

**用户视角，而非系统视角：**
- `Message Sent`（用户发送）而不是 `Message Delivered`（系统发送）
- `Purchase Completed`（用户完成）而不是 `Payment Processed`（系统处理）

**具体性平衡——一个事件 + 属性，而不是多个事件：**
- **好**：`Order Completed` with property `payment_method`
- **坏**：`Credit Card Order Completed`，`Apple Pay Order Completed`

**跨平台一致性：** 相同用户操作 = 相同事件名称，跨 Web、iOS、Android。平台差异放在 `platform` 属性中。

**一个动作 = 一个事件名称。** 代码库中没有重复。

**Autocapture 优先：** 不要建议自定义事件用于 Autocapture 已捕获的内容：`Page Viewed`，`Element Clicked`，`Element Changed`，`Form Started`，等。

### 属性命名标准

- **`snake_case`** 用于所有属性名称
- **描述性且具体：** `payment_type` 而不是 `type`，`error_message` 而不是 `message`
- **当歧义时包含单位：** `video_duration_seconds`，`file_size_mb`，`price_usd`
- **时间戳约定：** `[event_name]_at`（例如，`product_added_at`）
- **跨事件一致：** 相同概念使用相同的属性名称。`product_name` 必须在所有事件上是 `product_name`——不是 `name`，`prod_name`，等。
- **不同概念使用不同名称：** `login_method` 和 `payment_method`，而不是通用的 `method` 用于两者
- **点表示法：** 表示嵌套对象已传递（Amplitude 自动创建）。除非打算嵌套对象，否则不要在属性名称中直接使用点表示法。在审计期间，点表示法属性的集群是一个清理信号——检查哪些实际上正在被查询。如果很大一部分未使用，建议在源处修剪对象以减少分类噪音。

### 属性类型标准

| 类型 | 格式 | 示例 |
|------|------|------|
| IDs | 始终为字符串 | `"user_id": "12345"` 不是 `12345` |
| 计数/金额 | 数字 | `"order_total": 59.99` |
| 标志 | 布尔值 | `"is_premium": true` |
| 时间戳 | ISO 8601 字符串 | `"2024-03-10T14:30:00Z"` |
| 枚举/状态 | 字符串 | `"status": "In Progress"` |
| 空值处理 | 每个属性选择一种方法 | 删除、`null` 或哨兵字符串（如 `"Unknown"`）——永远不要混合。使用显式哨兵字符串可以让您区分有意不可用值和仪器错误。不一致的空值处理是最常见的导致属性过滤器错误和漏斗中断的原因。 |

### 用户识别标准

- **匿名用户：** 仅设置 `device_id`。**不要**设置 `user_id`。
- **已认证用户：** 为每个经过验证的用户设置唯一的、稳定的 `user_id`。登录/验证之前永远不要设置。
- **服务器端事件：** 每个事件包括唯一的 `insert_id` 以进行去重（7 天窗口）。
- **会话：** 在会话内使用一致的 `session_id`；对于服务器端，使用第一个会话事件的时间戳。

### 结构模式

- **A/B 实验：** 作为列表用户属性，而不是事件
- **错误：** 一个 `Error Encountered` 事件，带有 `error_type`/`error_category` 属性
- **电子商务：** 使用 `product_engagement`（此操作中的项目）+ `cart_contents`（完整购物车快照）数组
- **B2B：** 至少一个组类型（`org_id`，`account_id`）仪器
- **漏斗的属性一致性：** 在漏斗中的所有事件上捕获相同的属性（例如，`product_id`）

### 类别分配

使用 Amplitude 类别元数据字段——不要在事件名称中嵌入前缀。常见类别：

| 类别 | 目的 | 示例 |
|------|------|------|
| 生命周期 | 用户旅程里程碑 | Signup Completed，Trial Started，Subscription Cancelled |
| 功能 | 核心产品功能 | Task Created，Document Edited，Report Generated |
| 参与度 | 导航和 UI 交互 | Page Viewed，Button Clicked，Search Performed |
| 交易 | 收入事件 | Purchase Completed，Checkout Started，Refund Requested |
| 系统 | 技术健康 | Error Occurred，API Request Completed，Timeout Occurred |
| 增长 | 获取和推荐 | Invite Sent，Share Completed，Referral Reward Earned |

**分配启发式：**
- 如果事件表示首次或里程碑用户操作（signup、首次购买、首次邀请），请优先考虑 **生命周期** 而不是功能或交易。
- 如果事件记录的点击或查看不是核心产品操作，请优先考虑 **参与度** 而不是功能。
- 集成源事件（`[Appboy]`，`[Adjust]`，等.）可能无法整齐排列——根据集成的目的分配系统或增长，或者留空。
- 当正确的类别不明确时，询问客户，而不是猜测。

## 评分和优先级排序问题

三个维度：

### 1. 问题影响

| 级别 | 分数 | 定义 | 示例 |
|------|------|------|------|
| 高 | 3 | 名称是模糊的——分析师无法可靠地解释它 | 行话、首字母缩写词、块状词、易混淆的名称 |
| 中 | 2 | 名称可以解释，但分类更混乱 | 约定异常值，计划中未出现的事件 |
| 低 | 1 | 名称清晰；问题缺少完善 | 当名称自我解释时缺少描述 |

### 2. 事件重要性

- **查询频率：** 30/60/90/180 天计数——高查询事件影响更多分析
- **数量：** 高数量 = 更多成本和风险
- **首次出现：** 非常近 = 早期验证，以免问题累积
- **最后出现：** 很久 = 陈旧信号

### 3. 工作量

- **低：** 仅元数据更改（描述、显示名称、类别、标签、隐藏）
- **中：** 需要利益相关者验证或依赖检查
- **高：** 需要代码库更改或集成重新配置

**优先级：** 首先处理高影响问题上的高重要性事件。陈旧/测试事件是快速获胜——在真实数据质量问题下方呈现它们。

**健康评级：** （获得的总分数 / 可能的总分数）x 100%
- 0-49%：需要改进
- 50-79%：符合预期
- 80-100%：超出预期

## 权威边界（仅元数据）

**允许（非破坏性、仅元数据、经用户批准）：**
- 更新显示名称、描述、类别、标签
- 设置官方状态
- 隐藏事件（**不**阻止或删除）
- 设置自动任务
- 向项目设置添加 AI 上下文

**不允许：**
- 阻止、删除、合并或转换事件
- Block/Drop 过滤器
- 修改摄入管道或上游集成
- 任何形式的抽样策略

# 第三层：检测参考

## 检测信号和阈值

默认回溯：**180 天**。

| 信号 | 优先级 | 行动 |
|------|------|------|
| 语义上不明确的名称 | 高 | 添加显示名称 + 描述 |
| 缺少描述（不明确的名称） | 高 | 添加描述，遵循 AI 准备公式 |
| 语义重复（真正——相同含义，不同大小写） | 高 | 合并或消歧义 |
| 语义重复（相似——不同名称，相同操作） | 高 | 调查；合并或消歧义 |
| 180 天无数量 | 中 | 在行动前调查 |
| 180 天无查询 | 中 | 首先检查资产依赖关系 |
| 跨事件 + 用户范围的重复属性 | 中 | 澄清正确的“真实来源” |
| 缺少描述（清晰的名称） | 低 | 添加描述；降低优先级 |
| 缺少类别 | 低 | 添加类别 |
| 命名约定异常值 | 低 | 标记以供将来重新对齐 |
| 预期之外的事件/属性 | 低 | 审查后添加到计划或阻止 |
| 陈旧（最后出现超出回溯） | 低 | 快速获胜——安排弃用 |
| 单日（first_seen = last_seen） | 低 | 快速获胜——可能是测试；首先验证 |
| 测试/QA 工件（`test_`，`debug_`，`tmp_`，`_qa`） | 低 | 快速获胜——标准弃用流程 |

**例外：** 当客户接近配额时，陈旧/单日/测试信号成为提高优先级。

## 关键审计指标

| 指标 | 影响 |
|------|------|
| 类型配额限制的百分比 | 高当 >90% |
| 最近 7 天添加的新类型（峰值 = 可能的动态值泄漏） | 高如果峰值 |
| 最近 7 天总事件数量变化 | 高如果意外 |
| 通过名称的重复类型数量 | 高 |
| 未仪器化的组类型（B2B 产品） | 高 |
| 将 A/B 实验作为事件而不是用户属性跟踪 | 中 |
| 180 天内无查询的事件 | 中 |
| 180 天内无数量的事件 | 中 |
| 单日事件 | 中 |
| 活跃事件描述的百分比 | 低 |
| 活跃事件类别的百分比 | 低 |
| 预期之外的事件/属性数量 | 低 |
| 命名约定不一致 | 低 |

# Amplitude MCP 能力选择

在运行时检查连接的公共 Amplitude MCP 目录。工具名称和包装器在推出期间可能会改变或以不同的方式暴露，因此从其宣传的描述和模式中选择能力，而不是依赖记录在此技能中的名称。

## 上下文和发现

- 使用项目上下文能力发现可访问的项目 ID 并读取选定项目的设置。当有多个项目可用时，请要求用户选择；永远不要从项目名称中推断 ID。
- 当暴露时，使用分类搜索进行事件和属性发现；否则，过滤和分页活动分类读取器。使用实体搜索进行图表、仪表板、笔记本、实验、队列和保存内容的发现。
- 在任何编写之前，使用工作区或分支能力检查批准要求、分支保护、权限和当前分支。

## 分类读取

- 当目录暴露一个整合分类读取器时，优先使用它。使用其宣传的区分符选择原始事件、自定义/标记事件、事件属性、用户属性、组属性、派生属性、查找表、渠道或持久化属性。
- 如果目录暴露单独的事件或属性读取器，仅使用其记录的过滤器和分页字段。不要发明别名或从另一个读取器复制参数。
- 从返回的分类行中解析事件和属性名称。名称区分大小写；不要用显示名称替换。
- 通过每个游标分页 exhaustive 读取。当响应报告总数时，将其与累积的行进行核对；否则，需要读取器记录的终端游标条件。失败或部分页面不是完成。
- 使用可用的转换读取器审计事件/属性合并、值映射或其他清理规则。

## 元数据更新

- 仅在选择其当前模式支持请求的对象类型、元数据字段、分支选择器和范围的编辑能力后，选择事件或属性变异能力。
- 首先读取确切的当前对象。仅更新明确确认的字段，保留现有描述，除非用户要求替换它们，并且不要从旧工具版本推断不受支持的参数。
- 事件-属性元数据可以是全局的或针对单个事件的。使用模式明确的范围控制；永远不要假设省略意味着全局，除非当前模式记录了它。
- 自定义/标记事件定义是完整替换，而不是合并。传递完整的已验证定义，并警告重命名会破坏引用。
- 永远不要更新带括号前缀或供应商前缀的系统事件，除非用户明确请求。
- 在任何写入之前都需要明确确认，并尊重跟踪计划写入权限和分支保护。
