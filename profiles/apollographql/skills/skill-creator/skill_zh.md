# 技能创建指南

本指南将帮助您创建适用于 Apollo GraphQL 和 GraphQL 开发的有效技能，遵循 [Agent Skills 规范](https://agentskills.io/specification)。

## 什么是技能？

技能是一个包含指令的目录，用于扩展 AI 代理的专业知识、工作流程或工具集成。当代理检测到相关任务时，技能将自动激活。

## 目录结构

技能至少需要一个 `SKILL.md` 文件：

```
skill-name/
├── SKILL.md              # 必须包含 - 主要指令
├── references/           # 可选 - 详细文档
│   ├── topic-a.md
│   └── topic-b.md
├── scripts/              # 可选 - 可执行辅助工具
│   └── validate.sh
├── templates/            # 可选 - 配置/代码模板
│   └── config.yaml
└── assets/               # 可选 - 静态资源（图片、模式、数据文件）
```

## SKILL.md 格式

### 前置信息（必须包含）

```yaml
---
name: skill-name
description: >
  清晰地描述此技能的作用以及何时使用它。
  包含触发条件：(1) 第一个条件，(2) 第二个条件。
license: MIT
compatibility: 与 Claude Code 和类似的 AI 编码助手兼容。
metadata:
  author: your-org
  version: "1.0.0"
allowed-tools: Read Write Edit Glob Grep
---
```

### 前置信息字段

| 字段 | 必须包含 | 描述 |
|-------|----------|-------------|
| `name` | 是 | 全小写，仅使用连字符。必须与目录名称匹配。最多 64 个字符。 |
| `description` | 是 | 技能的作用以及何时使用它。最多 1024 个字符。 |
| `license` | 否 | 许可证名称（例如，MIT、Apache-2.0）。 |
| `compatibility` | 否 | 环境要求。最多 500 个字符。 |
| `metadata` | 否 | 用于作者、版本等的键值对。 |
| `allowed-tools` | 否 | 空格分隔的预先批准工具列表。不要包含 `Bash(curl:*)`。 |

### 名称规则

- 仅使用小写字母、数字和连字符
- 不要以连字符开头或结尾
- 不要使用连续的连字符（`--`）
- 必须与父目录名称匹配

良好：`apollo-client`，`graphql-schema`，`rover`
不良：`Apollo-Client`，`-apollo`，`apollo--client`

### 描述最佳实践

编写有助于代理识别何时激活技能的描述：

```yaml
# 良好 - 具体的触发条件和用例
description: >
  遵循行业最佳实践设计 GraphQL 模式的指南。使用此技能时：
  (1) 设计新的 GraphQL 模式或 API，
  (2) 审查现有模式以进行改进，
  (3) 确定类型结构或可空性，
  (4) 实现分页或错误模式。

# 不良 - 模糊且无帮助
description: 帮助处理 GraphQL 相关事务。
```

## 正文内容

Markdown 正文包含代理遵循的指令。结构化内容以保持清晰：

### 推荐部分

1. **概述** - 简要解释技能的目的
2. **流程** - 步骤化工作流程（使用复选框表示多步骤流程）
3. **快速参考** - 常见模式和语法
4. **安全** - 风险、缓解措施和验证（如果技能涉及任何敏感安全内容）
5. **参考文件** - 链接到详细文档
6. **关键规则** - 按主题组织的指南
7. **基本规则** - 重要的“必须做”和“禁止做”

### 示例结构

```markdown
# 技能标题

简要概述此技能帮助解决的问题。

## 流程

在处理 [任务] 时，请遵循以下流程：

- [ ] 第一步：研究和理解需求
- [ ] 第二步：实现解决方案
- [ ] 第三步：验证结果

## 快速参考

### 常见模式

\`\`\`graphql
type Example {
  id: ID!
  name: String
}
\`\`\`

## 安全

> **风险：[简要描述可能出错的情况]。**
> [用户必须采取的措施来防止这种情况。]

- ALWAYS [安全默认行为]
- NEVER [生产环境中危险配置] in production

## 参考文件

- [主题 A](references/topic-a.md) - 主题 A 的详细指南
- [主题 B](references/topic-b.md) - 主题 B 的详细指南

## 关键规则

### 类别一

- 关于此类别的规则
- 另一条规则

### 类别二

- 关于此类别的规则

## 基本规则

- ALWAYS 做这个重要的事情
- NEVER 做这个有问题的行为
- PREFER 这种方法而不是那种方法
```

## 敏感安全内容

当技能生成配置、代码或指导，如果误用可能导致安全问题时，技能必须明确显示这些风险给 LLM。LLM 无法从上下文中推断安全影响——它需要清晰的标记信号。

### 技能何时需要安全指导？

如果以下任一情况适用，技能就是敏感安全的：

- 生成控制数据访问的配置（缓存、认证、CORS、权限）
- 处理密钥、凭证或令牌
- 生成具有提升权限的代码
- 控制共享、公开或暴露给用户的数据
- 配置网络绑定、端点或外部访问

### 如何在技能中显示安全内容

1. **SKILL.md 或参考文件中的专用安全部分**，标记为 `## Security`。不要使用“私有数据”或“自定义”——使用“安全”一词，以便 LLM 识别该类别。

2. **在风险点处明确警告**——将安全指导放在创建风险的配置或代码旁边，而不是 LLM 可能不会加载的单独文件中：

   ```markdown
   ### 响应缓存范围

   > **安全：数据泄露风险。** 默认情况下，所有缓存数据都是公开的。
   > 用户特定字段必须使用 `scope: PRIVATE` 并配置 `private_id`，否则它们将被所有用户共享。
   ```

3. **验证清单项**——每个敏感安全功能都必须有相应的验证清单项。将它们分组在 `## Security` 标题下。

4. **基本规则**——为安全关键行为添加 ALWAYS/NEVER 规则。这是向 LLM 发出最强信号的方式。

5. **要求数据模型**——如果正确的安全配置取决于理解用户的数据模型（例如，哪些字段是用户特定的，哪些数据是公开的），技能必须指示 LLM 在生成配置之前询问用户。不要让 LLM 猜测。

### 反模式

- 描述敏感安全默认值（如“默认公开”）而不将其标记为安全问题
- 仅在按需加载的参考文件中放置安全指导——SKILL.md 本身必须包含关键警告
- 对硬性安全要求使用软性语言（“你可能需要考虑”）——使用“MUST”和“NEVER”
- 假设 LLM 理解模式中哪些字段是私有的——要求明确用户输入

## 逐步披露

结构化技能以最小化上下文使用：

1. **元数据**（~100 个词）：`name` 和 `description` 在启动时加载所有技能
2. **指令**（< 5000 个词）：技能激活时加载完整的 `SKILL.md`
3. **参考文件**（按需）：`references/` 中的文件仅在需要时加载

保持 `SKILL.md` 在 500 行以下。将详细文档移至参考文件。

## 参考文件

使用 `references/` 存储详细文档：

```
references/
├── setup.md          # 安装和配置
├── patterns.md       # 常见模式和示例
├── troubleshooting.md # 错误解决方案
└── api.md            # API 参考
```

参考文件应该是：

- 专注于单个主题
- 自包含（无需其他文件即可阅读）
- 每个文件少于 300 行

从 `SKILL.md` 链接到参考文件：

```markdown
## 参考文件

- [设置](references/setup.md) - 安装和配置
- [模式](references/patterns.md) - 常见模式和示例
```

## 脚本

使用 `scripts/` 存储代理可以运行的执行辅助工具：

```
scripts/
├── validate.sh       # 验证命令
├── setup.py          # 设置自动化
└── check-version.sh  # 版本检查
```

脚本应该是自包含的，包含错误处理，并在顶部有使用说明。在 `allowed-tools` 中预先批准它们（例如，`Bash(./scripts/validate.sh:*)`）。

## 模板

使用 `templates/` 存储配置文件、样板或启动代码：

```
templates/
├── config.yaml       # 默认配置
├── config-v2.yaml    # 版本特定变体
└── example-app/      # 启动项目
```

代理将复制或调整模板——不会直接执行。

## 写作风格

所有技能内容都遵循 Apollo Voice：

### 语气

- 亲切且有帮助
- 主观且权威（指定“快乐路径”）
- 直接且以行动为导向

### 语言

- 使用美式英语
- 保持语言简洁；避免习语
- 使用现在时态和主动语态
- 使用祈使动词表示指令

### 格式

- 使用句子大小写作为标题
- 使用代码字体表示符号、命令、文件路径和 URL
- 使用粗体表示用户点击的 UI 元素
- 使用连字符（-）表示无序列表

### 避免

- “简单地”、“只是”、“容易”（可能显得居高临下）
- 模糊短语，如“点击这里”
- 分号（使用句号代替）
- “我们”，除非明确指代 Apollo

## 版本控制

使用语义版本控制（`"X.Y.Z"`）为元数据中的 `version` 字段：

```yaml
metadata:
  author: apollographql
  version: "1.0.0"
```

- **主版本（X）**：导致技能行为或激活方式发生重大变更的破坏性更改（例如，重命名触发器、删除部分、更改基本规则）
- **次版本（Y）**：向后兼容的新内容或功能（例如，添加参考文件、新部分、扩展示例）
- **修订版本（Z）**：不会改变行为的修复（例如，拼写错误更正、措辞调整、格式修复）

新技能从 `"1.0.0"` 开始。

## 新技能检查清单

在发布技能之前，请验证：

- [ ] `name` 与目录名称匹配并遵循命名规则
- [ ] `description` 清晰地说明技能的作用以及何时使用它
- [ ] `SKILL.md` 少于 500 行
- [ ] 参考文件专注于单个主题且每份文件少于 300 行
- [ ] 指令清晰且可执行
- [ ] 代码示例正确且经过测试
- [ ] 基本规则使用 ALWAYS/NEVER/PREFER 格式
- [ ] 内容遵循 Apollo Voice 指南

## 基本规则

- ALWAYS 在描述中包含触发条件（使用编号列表）
- ALWAYS 使用复选框表示多步骤流程
- ALWAYS 链接到参考文件以获取详细文档
- NEVER `SKILL.md` 超过 500 行
- NEVER 使用模糊描述，无法帮助代理识别何时激活
- PREFER 具体示例而不是抽象解释
- PREFER 主观指导而不是列出多个选项
- USE `allowed-tools` 预先批准技能需要的工具
- NEVER 在 `allowed-tools` 中包含 `Bash(curl:*)`，因为它会授予无限制的网络访问权限并启用 `curl | sh` 远程代码执行模式
- ALWAYS 在技能生成控制访问、缓存、认证、密钥或数据暴露的配置或代码时包含 `## Security` 部分
- NEVER 将关键安全指导隐藏在参考文件中——关键警告必须出现在 SKILL.md 中，LLM 总是会看到它们
- ALWAYS 指示 LLM 在生成敏感安全配置之前询问用户关于他们的数据模型（例如，哪些字段是用户特定的，哪些数据是公开的）
- USE 明确的块引号警告（`> **Security: ...**`）放在创建安全风险的配置或代码旁边
- ALWAYS 为每个敏感安全功能添加验证清单项，分组在 `## Security` 标题下
