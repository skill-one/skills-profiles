# 打包拆分

在构建现代 Web 应用时，[Webpack](https://webpack.js.org/) 或 [Rollup](https://rollupjs.org/guide/en/) 这类打包工具会将应用的源代码打包成一个或多个包。当用户访问网站时，会请求并加载这些包，以便在用户的屏幕上显示数据。

JavaScript 引擎（如 [V8](https://v8.dev/docs)）能够在用户请求的数据加载过程中解析并编译它们。尽管现代浏览器已经进化到尽可能快速且高效地解析和编译代码，但开发者仍然负责优化两个步骤：请求数据的加载时间和执行时间。我们希望尽可能缩短执行时间，以防止阻塞主线程。

## 何时使用

- 当应用存在一个影响加载时间的庞大 JavaScript 包时，请使用此方法
- 当您希望减少首次内容绘制（FCP）和最大内容绘制（LCP）时，这很有帮助
- 当您的代码部分仅用于特定用户交互或路由时，请使用此方法

## 操作步骤

- 使用 Webpack 或 Rollup 等打包工具将代码拆分为多个较小的包
- 将不需要用于初始渲染的代码拆分到自己的包中
- 考虑对交互响应时间（TTI）的影响，并优先处理关键渲染代码

## 详细说明

尽管现代浏览器能够流式传输正在到达的包，但在用户设备上绘制第一个像素之前，仍然可能需要相当长的时间。包越大，引擎到达首次渲染调用所在的代码行所需的时间就越长。在此期间，用户只能看到空白屏幕。

我们希望尽可能快地向用户显示数据。较大的包会导致加载时间、处理时间和执行时间增加。如果能减小包的大小，从而加快速度，那就太好了。

与其请求一个包含不必要代码的巨大包，不如将包拆分为多个较小的包！

通过拆分应用包，我们可以减少加载、处理和执行包所需的时间！通过减少加载和执行时间，我们可以减少首次内容绘制（FCP）之前的时间，即用户屏幕上首次绘制内容的时间，以及最大内容绘制（LCP）之前的时间，即最大组件渲染到屏幕上的时间。

虽然能在屏幕上看到数据很棒，但我们不仅想“看到”内容。为了使应用完全可用，我们希望用户能够与之“交互”！只有在包加载和执行后，UI 才会变得可交互。所有内容绘制到屏幕上并变为可交互所需的时间称为交互响应时间（TTI）。

较大的包不一定意味着更长的执行时间。可能我们加载了大量用户根本不会使用的代码！包的某些部分可能仅在特定用户交互时才会执行，而用户可能根本不会进行这些交互！

引擎仍然需要在用户看到任何内容之前加载、解析和编译初始渲染未使用的代码。尽管由于浏览器高效处理这两个步骤，解析和编译的成本可以忽略不计，但获取比必要更大的包可能会损害应用的性能。在低端设备或较慢网络上，用户在获取包之前会看到加载时间显著增加。

与其最初请求当前导航中优先级不高的代码部分，不如将这些代码与需要渲染初始页面的代码分开。

通过将大包拆分为两个较小的包 `main.bundle.js` 和 `emoji-picker.bundle.js`，我们通过获取更少的数据来减少初始加载时间。
