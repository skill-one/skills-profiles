# 代码库文档生成器

## 概述

这项技能能够为代码库创建全面且适合初学者的文档。它提供结构化的模板和最佳实践，用于编写 README、架构指南、代码注释和 API 文档，帮助新用户快速理解和参与项目。

## 适合初学者的文档核心原则

为新手文档化代码时，请遵循以下基本原则：

1. **先说明"为什么"** - 在深入实现细节之前解释目的
2. **逐步披露** - 从简单到复杂分层呈现信息
3. **提供背景** - 不仅解释代码做什么，还要说明它为什么存在
4. **包含示例** - 为每个概念提供具体使用示例
5. **假设无先验知识** - 在可能的情况下定义术语，避免行话
6. **视觉辅助** - 使用图表、流程图和文件树结构
7. **快速见效** - 帮助用户在 5 分钟内让项目运行起来

## 文档类型及使用场景

### 1. README 文档

**创建时机：** 项目根目录、主要功能模块或独立组件。

**遵循结构：**
```markdown
# 项目名称

## 项目做什么
[1-2 句简体中文解释]

## 快速入门
[在 5 分钟内让用户运行项目]

## 项目结构
[带解释的可视化文件树]

## 核心概念
[用户需要理解的核心概念]

## 常见任务
[频繁操作的逐步指南]

## 故障排除
[常见问题和解决方案]
```

**最佳实践：**
- 首先突出项目的价值主张
- 包含实际可用的设置说明（测试过！）
- 提供项目结构的可视化概述
- 链接到更深入的文档以了解高级主题
- 根目录 README 应专注于入门

### 2. 架构文档

**创建时机：** 项目包含多个模块、复杂数据流或非显而易见的架构决策时。

**遵循结构：**
```markdown
# 架构概述

## 系统设计
[高级图表和解释]

## 目录结构
[每个目录用途的详细分解]

## 数据流
[数据如何通过系统流动]

## 关键设计决策
[为什么做出某些架构选择]

## 模块依赖
[不同部分如何交互]

## 扩展点
[添加新功能的位置和方式]
```

**最佳实践：**
- 使用图表展示系统组件和关系
- 解释架构决策背后的"为什么"
- 文档化既成功路径也错误处理
- 确定模块之间的边界
- 包含带注释的可视化文件树结构

### 3. 代码注释

**创建时机：** 复杂逻辑、非显而易见的算法或需要上下文的代码。

**注释模式：**

**函数/方法文档：**
```javascript
/**
 * 计算部分计费周期内的订阅费用。
 *
 * 存在原因：用户可以中途订阅，因此我们需要只收取当前计费周期剩余天数的费用。
 *
 * @param {number} fullPrice - 普通月度订阅价格
 * @param {Date} startDate - 用户订阅开始时间
 * @param {Date} periodEnd - 当前计费周期结束时间
 * @returns {number} 应收取的部分金额
 *
 * @example
 * // 用户 1 月 15 日订阅，周期结束 1 月 31 日
 * calculateProratedCost(30, new Date('2024-01-15'), new Date('2024-01-31'))
 * // 返回：16.13 (31 天中的 17 天)
 */
```

**复杂逻辑文档：**
```python
# 存在原因：API 对已删除用户返回 null，对从未设置名称的用户返回空字符串。我们需要区分这两种情况以用于审计日志。
if user_name is None:
    # 用户被删除 - 记录安全事件
    log_deletion_event(user_id)
elif user_name == "":
    # 用户从未完成入职 - 安全跳过
    continue
```

**最佳实践：**
- 解释"为什么"而不是"什么" - 代码展示了它做什么
- 文档化边缘情况和业务逻辑
- 为复杂函数添加示例
- 解释不直观的参数
- 注明任何陷阱或反直觉行为

### 4. API 文档

**创建时机：** 任何 HTTP 端点、SDK 方法或公共接口。

**遵循结构：**

```markdown
## 端点名称

### 端点做什么
[端点目的的简体中文解释]

### 端点
`POST /api/v1/resource`

### 认证
[需要的认证方式及如何提供]

### 请求格式
[JSON 架构或示例请求]

### 响应格式
[JSON 架构或示例响应]

### 示例用法
[带 curl/代码的具体示例]

### 常见错误
[错误代码及其含义]

### 相关端点
[链接到相关操作]
```

**最佳实践：**
- 提供可工作的 curl 示例
- 展示成功和错误响应
- 清晰解释认证方式
- 文档化速率限制和约束
- 包含常见问题的故障排除

## 文档工作流程

### 第 1 步：分析代码库

在编写文档之前：

1. **识别入口点** - 主文件、索引文件、应用初始化
2. **映射依赖关系** - 模块如何相互关联
3. **找到核心概念** - 用户需要理解的关键抽象
4. **定位配置** - 环境设置、配置文件
5. **审查现有文档** - 在已有基础上构建，不要重复

### 第 2 步：选择文档类型

根据用户请求和代码库分析：

- **新项目或缺失 README** → 从 README 文档开始
- **复杂架构或多个模块** → 创建架构文档
- **令人困惑的代码段** → 添加行内代码注释
- **HTTP/API 端点** → 编写 API 文档
- **需要多种类型** → 按顺序处理：README → 架构 → API → 注释

### 第 3 步：生成文档

使用 `assets/templates/` 中的模板作为起点：

- `assets/templates/README.template.md` - 用于项目 README
- `assets/templates/ARCHITECTURE.template.md` - 用于架构文档
- `assets/templates/API.template.md` - 用于 API 文档

根据特定代码库自定义模板：

1. **填写项目特定信息** - 用实际内容替换占位符
2. **添加具体示例** - 使用项目中的真实代码
3. **包含视觉辅助** - 创建文件树、图表、流程图
4. **测试说明** - 验证设置步骤确实可行
5. **链接相关文档** - 将文档部分连接起来

### 第 4 步：审查清晰度

在最终确定文档之前：

1. **像新手一样阅读** - 在没有项目背景的情况下是否易懂
2. **检查完整性** - 解释是否有遗漏
3. **验证示例** - 代码示例是否真的可行
4. **测试说明** - 是否有人能按步骤操作
5. **改进结构** - 信息是否易于查找

## 文档模板

这项技能包含 `assets/templates/` 中的多个模板，提供起始结构：

### 可用模板

- **README.template.md** - 带有快速入门、项目结构和常见任务部分的全面 README 结构
- **ARCHITECTURE.template.md** - 架构文档模板，包含系统设计、数据流和设计决策
- **API.template.md** - API 端点文档，包含请求/响应格式和示例
- **CODE_COMMENTS.template.md** - 有效行内文档的示例和模式

### 使用模板

1. **从 `assets/templates/` 读取相应的模板**
2. **为特定项目自定义** - 用实际信息替换占位符
3. **添加项目特定部分** - 根据需要扩展模板
4. **包含真实示例** - 使用代码库中的实际代码
5. **删除无关部分** - 删除不适用部分

## 常见模式

### 创建文件树结构

文件树帮助新手理解项目组织：

```
project-root/
├── src/                    # 源代码
│   ├── components/        # 可重用 UI 组件
│   ├── pages/             # 页面级组件（路由）
│   ├── services/          # 业务逻辑和 API 调用
│   ├── utils/             # 辅助函数
│   └── types/             # TypeScript 类型定义
├── public/                # 静态资源（图片、字体）
├── tests/                 # 与 src 结构镜像的测试文件
└── package.json           # 依赖关系和脚本
```

### 解释复杂数据流

使用编号步骤和图表：

```
用户请求流程：
1. 用户提交表单 → 2. 验证 → 3. API 调用 → 4. 数据库 → 5. 响应

[1] components/UserForm.tsx
    ↓ 验证输入
[2] services/validation.ts
    ↓ 发送到 API
[3] services/api.ts
    ↓ 查询数据库
[4] 数据库 (PostgreSQL)
    ↓ 返回数据
[5] components/UserForm.tsx (更新 UI)
```

### 文档化设计决策

捕获架构选择的"为什么"：

```markdown
## 为什么使用 Redux

**决策：** 使用 Redux 而不是 Context API 进行状态管理

**背景：** 我们的 App 有 50+ 个需要访问用户认证状态、购物车和 UI 偏好的组件。

**理由：**
- Context API 在这么多组件中导致不必要的重新渲染
- Redux DevTools 帮助调试复杂的状态变化
- 团队有现有的 Redux 经验

**权衡：**
- 更多的样板代码
- 新开发者的学习曲线更陡峭
- 值得：性能、调试、团队熟悉度
```

## 输出指南

生成文档时：

1. **为目标受众编写** - 根据文档是面向初学者、中级还是高级用户调整复杂度
2. **使用一致的格式** - 遵循 markdown 规范，保持标题层级一致
3. **提供可工作的示例** - 测试所有代码片段和命令
4. **文档间链接** - 创建文档导航结构
5. **保持可维护性** - 文档应易于更新以适应代码变化
6. **添加日期和版本** - 注明文档最后更新时间
