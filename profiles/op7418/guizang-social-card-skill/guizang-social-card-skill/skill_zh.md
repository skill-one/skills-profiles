# 贵州社交卡技能

为小红书/红点、微信公众号、文章封面和平台缩略图创建精美的社交卡套餐。

此技能是自包含的。它借鉴了贵州PPT风格系统的视觉原则，但不得编辑原始PPT技能、其模板或其引用。如果原始PPT技能可用，您可以仅作参考阅读。

生成的工作必须位于任务文件夹中，而不是技能根目录。默认情况下，位于此仓库内的 `local-tests/<slug>/` 中，或使用用户请求的明确输出文件夹。不要创建根级任务文件夹，如 `social-card-*`、`livephoto-*`、`wechat-*`、`output/`，或在 `SKILL.md` 旁边放置松散的渲染资源。

## 要产出什么

使用此技能：

- 社交卡/轮播图集：封面加内容页，尤其是小红书/红点3:4。
- 短Live Photo动图卡，当用户要求Live Photo/实况照片并提供视频证据或屏幕录制时。
- 材质优先的Live Photo拼图布局，当用户拥有高质量视频资产并希望创建单视频、两网格、三网格或四网格动图卡且几乎不加或少量添加文字时。
- 三联Live Photo拼贴，当用户有三个短视频、三个结果、三个视角或应保持在一张图像卡单元内的高信息比较时。
- Live Photo长视频摄入：诊断是否需要修剪、加速、拆分为三联拼贴，或在渲染前请求用户指定特定时间范围。
- 微信公众号封面对：一个 `21:9` 主封面加一个 `1:1` 方形封面，在同一个HTML中组合在一起以进行视觉检查。
- 重截图的产品帖子、文章封面、教程轮播、户外/生活方式笔记、AI/产品更新说明。
- 需要贵州风格瑞士或编辑杂志布局的社交图像。

不要使用此技能：

- 全部幻灯片或水平PPT网站。使用PPT技能。
- 长视频生成。使用视频技能。此技能仅支持短布局约束的Live Photo卡，用视频替换静态图像位置。
- 纯图像编辑，无布局或文章提取要求。

### 红点分类能力（能力圆圈）

最常见的11个红点（小红书）分类分为三类。有关按菜谱逐个路由，请参阅 `references/category-cookbook.md`。

**端到端强**（文本、结构和图像故事都在范围内）：

- 旅行 (Travel), 职场 (Workplace), 推荐 (Recommended, 指定子类型后)。

**文本和结构强；图像需要来自用户或来源库**：

- 游戏 (Game), 影视 (Film/TV), 美食 食谱方向 (Food — 仅食谱), 彩妆 教程方向 (Makeup — 仅教程), 健身 (Fitness), 家居 (Home), 穿搭 精选方向 (Outfit — 模块/文章仅)。

**超出范围——诚实地拒绝，而不是承诺结果**：

- 美食 菜品大片摆盘 (food-photography showcase).
- 穿搭 日常 OOTD 全身 (日常OOTD全身；我们无法生成或模拟).
- 情感 梦核 / 氛围感装饰风 (dreamcore / 美学装饰风格 — 与编辑和瑞士风格都冲突).
- Y2K / 千禧辣妹 / 哥特萝莉 / kawaii装饰美学.
- 纯摄影展示帖子，图像是整个交付物。

当请求属于第三类时，在摄入时命名我们无法做的事情——不要无声地调整布局以错过用户的意图。

## 核心原则

表达优先。目标不是把文本塞进海报；而是把源材料变成清晰的可视化论点。

对于每一页，决定：

- 观众应该一眼就能理解什么？
- 哪些证据、截图或图像支持它？
- 哪些字必须大，哪些可以成为标题或元数据？
- 什么可以删除，因为它属于帖子正文，而不是图像？

## 工作流程

### 1. 摄入

仅收集会改变输出的缺失信息：

- 目标平台和宽高比。
- 源文本、字幕、文章或标题。
- **红点分类**——如果用户指定了11种常见类型中的任何一种（旅行 / 职场 / 游戏 / 影视 / 美食 / 彩妆 / 穿搭 / 家居 / 健身 / 情感 / 推荐），通过 `references/category-cookbook.md` 路由以找到正确的菜谱并确认请求在能力圆圈内（见上文的“红点分类能力”）。如果请求落在超出范围的桶中，在设计之前向用户表面，不要无声地调整。
- 提供的图像/截图及其应出现的位置。**对于新闻 / 教程 / 数据 / 评论内容，主动提示提供截图或照片**——它们是证据层。没有真实实物的海报往往看起来像填充物。
- 提供的视频资产，如果用户要求Live Photo。将用户提供的视频视为正常路径；网络来源免费视频仅用于演示/推广情况或当用户明确要求来源材料时。确认目标平台，因为持续时间不同：小红书支持 `5s`；微信公众号Live Photo应保持在 `3s`，必须从iPhone上传。在剪切之前，阅读 `references/live-photo-production.md` 并将请求分类为单Live Photo、三联拼贴或长视频摄入。如果源太长或包含多个可用时刻，先进行低成本诊断，然后询问一次是否要修剪、加速、拆分为多个井或使用用户指定的时间范围。如果源比目标持续时间短，询问是否提供更长的片段、接受更短的Live Photo或明确允许保持/减速。如果重要的焦点不明确，建议可能的裁剪/放大选项，但让用户在执行前决定。
- **如果用户仅提供文本（没有任何图像），在设计之前询问一次**：

  ```
  我需要1-2张图。三种走法：
  A. 你自己有照片 / 截图，传给我（推荐——最不"AI感"）
  B. 我去 Pexels / Unsplash / Flickr 帮你找
  C. 用 AI 生成
  ```

  一行内推荐A——你自己的照片能让海报看起来不像是AI生成的。接受用户选择的任何选项（包括“都行你看着办”）并继续。**不要重新提示，不要在多轮中不断推动A。**这个问题是一次性的。
  接受用户选择（包括“都行你看着办”）并继续。**不要重新提示，不要在多轮中不断推动A。**这个问题是一次性的。
- 如果指定了首选样式：瑞士风格、杂志/编辑、科技、户外等。
- 硬性约束：标题文本、1:1封面上不能有图像、必须包含硬件照片、保持截图可读，等等。

如果用户已经提供了足够的上下文，请进行合理的假设。

如果内容涉及当前产品发布、政策、价格、声明或新闻，请通过浏览验证不稳定的事实，并在最终响应中引用来源。

### 2. 提取故事

在设计之前，将源材料变成页面计划。

对于红点：

- 第1页是封面钩子。
- 第2-N页每页只承载一个想法。
- 对于大多数帖子，使用5-9页。当较低区域变得空时，压缩或合并页面。
- 保持帖子正文以供细微差别；图像应承载钩子、比较、清单和尖锐的要点。

对于微信公众号：

- 始终生成一个配对系统：`21:9` 主封面加一个 `1:1` 方形封面。
- 在同一个HTML文件中构建两个封面，并添加一个组合预览部分，以便可以一起检查它们的视觉关系。
- `21:9` 保留完整或接近完整的标题、副标题和一个强烈的视觉关系。
- `1:1` 使用从长标题简化而来的短标题：大居中类型，默认情况下没有图像，没有拥挤的副标题。

### 3. 选择样式模式

每个套餐选择一个模式。**这两个系统不是绑定到特定内容类型的**——变化的是视觉立场，而不是可以谈论的主题。职场文章可以是编辑；旅行日记可以是瑞士。根据你想要的感觉选择，而不是根据类别查找。

**编辑杂志 x E-ink** 带来：

- 宋体/思源黑体显示 + 安静的无衬线体正文，纸张+墨水调色板。
- 氛围层（纸张纹理 / 墨水洗 / WebGL画布）覆盖温暖的纸张基座。
- 账簿行、页边注、引文、大型照片井——杂志特写感。
- 当你希望页面感觉缓慢、深思熟虑、手工设置时最佳。

**瑞士国际** 带来：

- 中等/思源黑体感觉，大尺寸时非常轻的显示，小尺寸时单色标签。
- 严格的左对齐网格，细线规则，一个高饱和度强调。
- 卡片填充矩阵、KPI塔、水平条形图、编号声明——系统/数据感。
- 当你希望页面感觉经过工程、量化、果断时最佳。

如果两种视觉系统对某个内容都可行，问题就变成了编辑意图：“这是一个特写故事还是发布说明？”这决定了模式，而不是主题本身。

不要在同一个图像集中混合这两种视觉系统，除非用户明确要求混合。

然后选择一个主题：

- 编辑杂志 x E-ink 使用6种杂志调色板之一：墨水经典、靛蓝瓷、森林墨水、牛皮纸、沙丘或午夜墨水（唯一深色变体；保留游戏海报/夜间摄影/电影封面）。
- 瑞士国际使用4种强调调色板之一：IKB蓝色、柠檬黄色、柠檬绿色或安全橙色。

阅读 `references/theme-presets.md` 以获取确切的CSS标记。不要发明任意的颜色，除非用户有严格的品牌要求。

### 4. 规划页面

创建简洁的内部计划：

```text
Page 01 / cover / hook / image source / layout intent
Page 02 / point / key copy / visual evidence / layout intent
...
```

当用户要求批准时，在设计之前显示此计划。否则使用它内部并继续。

使用 `references/layout-recipes.md` 选择页面结构。避免让每一页都成为重复的标题加卡片布局。

对于3:4图像，在编码之前检查 `references/portrait-fill.md`。一个短表格或账簿必须扩展为完整的肖像构图，带有一个引文列、图像证据、页边注、较大的行或一个背景英雄区域。

面向观众的副本必须描述用户实际场景，而不是生产方法。内部术语，如 `3s`、`5s`、`Live Photo`、`triple collage`、`information budget`、`long-video intake`、`speed-up`、`highlight detection`、`one action point` 或 `layout template`，可以指导计划、文件名、QA笔记和交付摘要，但它们不能成为H1、钩子或主正文副本，除非用户正在制作关于这些概念的教学帖子。在渲染之前，像真实观众一样阅读每个可见的标题一次：如果听起来像任务要求，请用场景特定副本替换它。

不要为了满足自动化的密度警告而添加非模板装饰。额外的标尺、侧边栏、伪时间轴、装饰性标签或虚构徽章必须来自现有的布局菜谱或用户请求。如果出现密度警告，通过选择更好的菜谱、调整真实内容大小或接受建议性警告和视觉理由来修复它；不要在卡片上放置无意义的UI。

对于Live Photo卡，像正常社交卡一样规划它们，然后决定运动角色：一个动作点、一个小过程、一个前后变化、三个并行结果或氛围/证据。唯一的结构变化是一个或多个图像井变成视频井。保持相同的比例、裁剪、安全区域、排版和样式模式规则；将静态图像裁剪逻辑应用于视频流。第一帧必须通过与静态图像相同的检查：不要过度裁剪，关键UI/内容保持可读，并且卡片仍然遵循所选的布局菜谱。在渲染之前，阅读 `references/live-photo-production.md`。

对于材质优先的Live Photo拼图卡，让视频资产引导。使用少量或没有副本：单视频封面只需要一个简短标题，而两网格/三网格/四网格版本通常不需要添加文字。当单视频封面在素材上添加文字时，使用M16 Image-Led Cover / 文本在图像上的规则：首先进行主体映射，仅在需要时才添加局部、图像色调的渐变。不要默认使用全画布渐变。

然后选择一个主题：

- Editorial Magazine x E-ink 使用6种杂志调色板之一：墨水经典、靛蓝瓷、森林墨水、牛皮纸、沙丘或午夜墨水（唯一深色变体；保留游戏海报/夜间摄影/电影封面）。
- Swiss International 使用4种强调调色板之一：IKB蓝色、柠檬黄色、柠檬绿色或安全橙色。

阅读 `references/theme-presets.md` 以获取确切的CSS标记。不要发明任意的颜色，除非用户有严格的品牌要求。

### 4.5. 复制种子模板

不要从零开始编写HTML。根据第3步选择的样式模式选择一个种子模板：

- Editorial Magazine × E-ink → 将 `assets/template-editorial-card.html` 复制到任务文件夹作为 `index.html`。
- Swiss International → 将 `assets/template-swiss-card.html` 复制到任务文件夹作为 `index.html`。

种子已经连接：字体加载、主题标记、所有三种海报尺寸（`.poster.xhs` / `.poster.square` / `.poster.wide`）、配对预览框架、纹理/背景层和所有布局菜谱引用的类定义。

在 `<html>` 元素上设置主题/强调：

- Editorial: `<html data-theme="ink-classic | indigo-porcelain | forest-ink | kraft-paper | dune | midnight-ink">`.
- Swiss: `<html data-accent="ikb | lemon-yellow | lemon-green | safety-orange">`.

用 `<section class="poster ...">` 块替换 `<!-- POSTERS_HERE -->` 之后的单个占位符海报，每个块携带从所选布局菜谱（Editorial的M01-M16，Swiss的S01-S12）的HTML骨架。永远不要加载错误模板的类系统：Editorial菜谱假设宋体显示 + 账簿/页边注/管道；Swiss菜谱假设中等/思源黑体 + 卡片填充 + 矩阵/水平条形图/KPI塔。无声地混合它们会破坏布局。

### 5. 构建和渲染

默认实现模式：

- 默认情况下，在 `local-tests/<slug>/` 下创建任务文件夹，或在使用用户请求的输出文件夹内。永远不要在技能根目录中放置生成的任务文件夹、渲染的图像、MOV文件、`.pvt`包或下载的源。
- 将源图像放在 `assets/` 中。
- 从第4.5步复制的种子模板开始，而不是空白文件。优先更改 `<!-- POSTERS_HERE -->` 区域页面到页面。如果任务需要自定义布局CSS，在复制的文件中添加一个清晰命名的任务作用域块，并保持语义默认值重置 (`figure { margin:0; }`, 不要有浏览器默认的间距意外)。
- 使用Playwright或浏览器截图工具导出每个 `.poster` 或 `.cover` 节点。
- 将渲染的图像保存在 `output/` 中。
- 验证尺寸并检查渲染的PNG。
- 保持 `node validate-social-deck.mjs <task-dir>` 可用以进行自动检查通过。它检查溢出（R1）、页脚碰撞（R2）、Swiss粗体显示（R3）、最小字体大小（R4）、4带密度（R5）、`.h-xl` 行帽（R6）、浏览器默认的figure边距漂移（R7）、视觉边界/底部空白（R8）和标题到内容差距（R9）。任何FAIL都使用退出代码1——在自动检查请求最终交付之前修复。WARN是建议性的，但请阅读它。

Live Photo分支：

- 在渲染之前决定信息预算：`3s` 适合一个动作点；`5s` 适合一个小过程；三联拼贴适合三个并行片段，但不适合复杂的 故事；长视频需要诊断后编辑。
- 对于长源，避免声称精确的自动高亮检测。探测持续时间/分辨率，制作稀疏接触表，并在渲染前选择在剪切、加速、拆分为三联拼贴或请求用户指定特定时间范围。
- 从每个视频井中提取第一帧，将其放置在最终静态卡片布局中，并在制作 `.pvt` 之前显示/检查预览。这可以以较低的令牌和渲染成本捕获裁剪和层次结构问题。
- 在平台持续时间下渲染配对MOV：`5s` 用于小红书，`3s` 用于微信公众号官方账号。
- 从可读的代表性帧中提取关键的JPG。
- 将 `JPG + MOV` 打包到 `.pvt` 中，使用 `makelive`；将 `.pvt` 作为单个项目通过AirDrop传输到iPhone进行测试。
- 验证尺寸、持续时间、帧数、包内容以及运动质量。优先使用接触表帧条进行视觉检查，这样只需要最终平铺图像进行人工/模型检查。使用 `references/live-photo-production.md` 以获取确切的命令和失败模式检查。

不要在图像中放置可见的指令、键盘快捷键或使用说明。

对于 Editorial Magazine x E-ink，使用分层背景系统。优先使用微妙的WebGL墨水画布或冻结的程序化画布加上纸张纹理。阅读 `references/background-systems.md`；不要依赖平坦的米色背景，不要添加页面范围的网格/点背景。

### 6. 图像和截图处理

当用户提供截图时：

- 保留截图内容，除非用户要求重新设计。
- 优先程序化框架：目标比例画布，安全填充，干净背景，可读截图。
- 不要拉伸截图。
- 如果截图清晰度很重要，请扩大截图区域并减少附近文本。

#### 图文组合

每当海报在照片上放置文本时（全出血封面，大型图像井，生成的图像覆盖层），请遵循 `references/image-overlay.md`：

- **选择优先，仅在需要时才使用渐变。** 覆盖 ≥60% 画布的图像必须首先通过 `image-overlay.md` 中的安静区域和光线测试。先不使用蒙版进行组合；如果缩略图检查失败，请在标题区域周围添加局部、图像色调的渐变。不要默认使用全画布渐变。
- **主体映射是强制的。** 在放置标题之前，使用读取工具读取图像，用 plain language 描述主体的面部/焦点特征的位置，并将主体映射记录为英雄块旁边的HTML注释。仅在记录的安全区域内放置文本。
- **裁剪纪律——在每张图片上内联设置 `object-position`。** 模板默认 (`center 50%`) 是后备，不是推荐。对于每个 `<img>`，根据主体位置决定并内联写入：例如 `style="object-position:center 62%"` 对于身体主体的中点，`center 30%` 对于天空为主的风景，以地平线主体的前景设备为 `center 70%`。参见 `references/components.md` 中的表格和 `image-overlay.md` 中的面部照片具体细节。无声地裁剪主体会从高比例（`r-3x4`，`r-21x9`）中裁剪出画面。

编辑暗封面（例如游戏期刊在关键艺术上）和带有英雄照片的瑞士封面都需要这些检查。跳过它们是一个已知的失败模式（见 `style-system.md` 反模式D）。

当用户没有图像时：

- 这个分支仅在使用第1步“三选一”门进入B（网络来源）或C（AI生成）时运行。永远不要无声地进入B或C——用户选择了其中之一。
- 对于C（AI生成）：仅在它们为社交卡添加真实价值的地方使用生成的位图，通常1-2页。生成与页面视觉角色匹配的图像，而不是通用的装饰图像。保持生成的图像免受嵌入标题、页面编号、标志或假UI标签的影响，除非明确需要。
- 对于B（网络来源）：见下文的“网络来源图像”部分。

#### 网络来源图像（当用户没有截图/照片时回退）

当用户没有截图/照片，且生成的位图不适合页面的角色（例如编辑氛围照片，户外/生活方式背景，游戏封面艺术，真实世界产品拍摄）时，从网络获取，而不是留下页面空白。

政策：**先抓取，后披露，让用户决定是否可归因。** 不要预先过滤来源的许可证——用户是最终组合的权利所有者，决定什么可以接受。

推荐来源，按优先级顺序。**以下五个都是免费层级的库，无需许可证费用**；我们不会从付费股票网站（视觉中国 / Getty / 站酷海洛等）获取。

1. **Unsplash** — `https://unsplash.com/s/photos/<keyword>`。非常适合户外 / 生活方式 / 氛围背景。英文关键词效果最佳。许可证是宽容的，但按情况验证。
2. **Pexels** — `https://www.pexels.com/search/<keyword>/` 或 `https://www.pexels.com/zh-cn/search/<keyword>/`。**原生支持中文关键词搜索**——填补了Unsplash在“国内场景”（中文街景 / 国风物品 / 本地地名）的差距。当主题是中国特定或关键词是中文时，首先使用此选项。根据Pexels许可证免费使用。
3. **Flickr CC许可池** — `https://www.flickr.com/search/?text=<keyword>&license=2%2C3%2C4%2C5%2C6%2C9`。许可证过滤器 (`license=2,3,4,5,6,9`) 限制为Creative Commons照片。填补了“纪录片真实性”差距：街头摄影，场景中的人物，真实室内，非风格化场景，Unsplash/Pexels缺乏。如果用户选择归因，请始终保留CC归因。
4. **Wallhaven** — `https://wallhaven.cc/search?q=<keyword>`。非常适合游戏 / 动漫 / 壁纸主题。内容是用户上传的，权利未经核实。
5. **直接网络搜索** — 当需要一个特定主题时（产品渲染，游戏静止图像，历史照片）。使用WebFetch / WebSearch找到候选URL。

编辑模式选择顺序：**Pexels（如果关键词是中文 / 中国特定）→ Unsplash → Flickr CC（如果您需要真实感）→ 直接搜索**。瑞士模式很少需要任何这些——产品渲染，UI截图和关键截图风格的图像应该是用户提供的或AI生成的，而不是股票。

如何获取：

- 使用WebFetch或 `curl` 将图像下载到任务文件夹的 `assets/` 目录。
- 以目的命名文件，而不是哈希：`assets/hero-mountain.jpg`, `assets/ui-pulse-card.png`。
- 在旁边的 `assets/SOURCES.md` 文件中记录源URL（每行一个文件：`hero-mountain.jpg ← <url>`）。即使用户在最终图像中拒绝归因，也必须这样做——它保留了人类作者的来源记录。

获取后，在最终确定设计之前向用户展示来源：

```
我从 <site> 取了这些图：
- assets/hero-mountain.jpg — <url>
- assets/ui-pulse-card.png — <url>

⚠️ 版权未经核实。请你判断是否可用。
是否需要在图文中标注来源？
- 要：我把 "Photo · <site> · @<author>" 加到对应页脚 / 角标。
- 不要：原样使用,不加注释。
```

如果用户选择“标注”——添加一个小 `mono` 标题（Swiss: `.t-meta` 18-20px 在角落；编辑: `.label` 接近图像井）。永远不要将标题挤进布局的焦点区域。

如果用户选择“不标注”——无声地继续。来源仍然存在于 `assets/SOURCES.md` 以供用户记录。

如果一个图像只是复合中的许多元素之一（例如九张照片中的其中一张），用户可以合理地跳过归因。不要强制添加会破坏布局的信用标签。

### 7. 交付

**先给用户看，请求时再验证。** 在渲染完成后立即显示用户渲染的图像（绝对路径）以及一个简短的摘要，说明构建了什么。

2. 询问一个问题：**"先你自己看，还是我先自动核查一遍？"** (Do you want to review first, or should I run the auto-check?)

如果用户说 "我自己看" / "先给我" / "no need" — 停在这里，让他们检查，并回应他们提出的任何问题。

如果用户说 "你查吧" / "auto-check" / "yes" — 只有在此时运行 `node validate-social-deck.mjs <task-dir>`, 修复任何FAIL，然后重新渲染以进行最终交付。提及密度/cap WARNs。

永远不要在向用户展示之前无声地运行验证器——它每轮的成本很高，用户通常比自动检查更快地发现问题。

最终响应（在用户审查或请求自动检查之后）应包括：

- 输出文件夹路径。
- 渲染的图像显示为绝对路径，当有用时。
- 关于尺寸和验证的简短说明（或“尚未验证，等待您的审查”）。
- 对于从网络获取的任何图像：源URL + 网站 + 用户做出的归因决定。
- 对于Live Photo：`.pvt` 包路径，调试 `JPG + MOV` 对，目标平台持续时间，验证摘要。
- 对于Live Photo发布：提醒用户两件事：平台限制 (`5s` 小红书, `3s` 微信公众号官方账号) 和发布路径（将 `.pvt` 包作为单个项目通过AirDrop传输到iPhone，然后从匹配的移动应用程序路径发布；桌面/网页上传路径通常无法识别 `.pvt` 作为可发布的Live Photo）。
- 如果用户无法使用iPhone/AirDrop发布路径（例如仅限桌面的工作流程，Android，或不支持Live Photo的平台），提供降级交付：从同一MOV源导出短循环GIF或无声MP4片段。GIF/MP4保留了运动证据，但失去了Live Photo点击播放体验。在切换到此回退之前与用户确认。
- 任何未解决的任何风险，例如源图像分辨率低。

## 非协商项

- 永远不要编辑原始贵州PPT技能或从其他地方复制的任何上游技能。
- 永远不要在技能根目录中创建生成的作品。所有任务工件必须默认位于 `local-tests/<slug>/` 中，或位于用户请求的输出文件夹内。禁止在根级创建任务文件夹，如 `social-card-*`、`livephoto-*`、`wechat-*`、`output/` 或 `SKILL.md` 旁边的松散渲染资源。

- 不要创建随机的装饰性SVG椭圆、blob、雨滴、贴纸或无意义的圆圈。
- 不要使用嵌套卡片或通用SaaS卡片布局作为默认值。
- 不要让文本溢出、触摸边缘或与页脚带冲突。使用 `margin-top: auto` 将 `.foot` 钉在flex列中，永远不要使用 `position: absolute` 覆盖增长的内容。
- 当内容溢出时，在编辑之前测量溢出量。小溢出应得到小的修复：`1-40px` 意味着推/紧缩，`40-90px` 意味着局部紧凑，`90-160px` 意味着轻微的标题或段落压缩，只有 `160px+` 才会触发菜谱更改或内容删除。修复后，检查R8底部空白，以防止页面从溢出变成一个巨大的空下带。
- 不要让标题与下一个内容块接触。主要显示标题通常应至少保持 `28px` 下方；本地标题应至少保持 `16px`。使用验证器R9，在依赖视觉检查之前使用视觉检查。
- 不要让文本在移动设备上变得太小而无法阅读。
- 不要在Swiss中为显示标题使用内联 `font-size` + `font-weight`。使用输入的类（`.h-hero` / `.h-statement` / `.h-xl` / `.num-mega`）。80-120px 标题在重量700-900不是Swiss；"越大越轻"是一个硬规则。
- 不要交付带有平面纸张背景的编辑海报、每行都有单色标签，没有氛围层的海报。
- 运行 `references/style-system.md` 中的编辑身份测试——单独的宋体标题并不能让海报看起来像编辑。

- 不要伪造数据、发布细节或百分比。
- 不要裁剪面部、关键UI文本或硬件/产品细节，除非用户明确接受。
- 不要把视频卡片变成假的静态序列，不说明。如果源比目标持续时间短，请请求一个更长的源，使用平台安全的较短持续时间，或明确记录任何保持/减速。如果重要的焦点不明确，建议可能的裁剪/放大选项，但让用户在执行前决定。

- 不要跳过Live Photo的第一帧预览。视频是一个带有运动的图像井；它的第一帧必须通过静态图像的相同检查：不要过度裁剪，关键UI/内容保持可读，并且卡片仍然遵循所选的布局菜谱。在渲染之前，阅读 `references/live-photo-production.md`。

- 不要让结果视频在浅裁剪中滚动通过章节边界；这会创建“重叠视频”失败。检查接触表并选择一个稳定的时间窗口，然后再打包。

- 不要猜测用户在放大/裁剪视频以进行可读性时的视觉优先级。提供裁剪/放大权衡，并在用户确认后应用它，除非请求已经使焦点区域明确。

- 不要盲目地将21:9封面裁剪成1:1。分别构建每个比例。

- **3:4 卡必须吃满画布**。内容（文本 + 图像 + 数据）必须覆盖 ≥75% 画布高度。任何 >15% 画布高度的纯空白带都需要“留白理由”：(a) 英雄图像自带呼吸、(b) 单句宣言式英雄statement、(c) 段落顶/底leading & trailing whitespace（前后总和 ≤15%）。**禁止使用 `<div style="flex: 1"></div>` 上下夹击把内容塞到中段**——杂志页留白逻辑不适用于社交卡（杂志靠对开页吸收留白，社交卡逐张独立刷，欠填看着像 PPT漏排）。

- Recipe-by-recipe 最小密度见 `references/layout-recipes.md` 每条recipe的「Minimum density」段。Render 后必须跑 `qa-checklist.md` 的 4 横带密度检查。
