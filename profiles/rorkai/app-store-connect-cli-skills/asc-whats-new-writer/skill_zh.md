# asc 新功能 Writer

从灵活的输入中生成引人入胜的本地化版本说明。可选地与促销文本更新配对。

## 前置条件

- 通过 `asc metadata pull --app "APP_ID" --version "1.2.3" --dir "./metadata"` 将元数据本地拉取到规范文件中。OR：用户手动提供关键词。
- 配置上传认证 (`asc auth login` 或 `ASC_*` 环境变量)。
- **主要语言环境**为 `en-US`，除非用户指定其他语言环境。

## 开始前

1. 阅读 `references/release_notes_guidelines.md` 了解语气、结构和示例。
2. 确定在 `metadata/version/` 下**最新版本目录**（最高 semver）。使用此目录进行所有元数据读取。
3. 通过列出该版本目录中的 JSON 文件来枚举**现有语言环境**。

## 第一阶段：收集输入

接受三种输入模式之一（自动检测）：

### Git 日志

解析自上次标签以来的提交：

```bash
# 查找最新标签
git describe --tags --abbrev=0

# 列出自该标签以来的提交
git log $(git describe --tags --abbrev=0)..HEAD --oneline --no-merges
```

过滤掉噪音：合并提交、依赖项更新、CI 更改、仅格式化的提交。提取面向用户的更改。

### 项目符号

用户提供大致的项目符号，例如：
- "改进了搜索"
- "修复了启动时的崩溃"
- "添加了睡眠计时器"

### 自由文本

用户以对话方式描述更改：
> "我们使搜索更快了，修复了打开应用时那个烦人的崩溃，并添加了睡眠计时器功能"

该技能从文本中提取和结构化更改。

### 未提供输入

提示用户："此版本中有哪些更改？您可以粘贴 git 日志输出、项目符号，或仅描述更改。"

## 第二阶段：草拟说明（主要语言环境）

### 第 1 步：分类更改

根据指南将更改分组到各个部分：
- **新增** — 新功能或能力
- **改进** — 现有功能的增强
- **修复** — 用户会注意到的错误修复

省略空的部分。如果所有更改都是修复，则仅显示"修复"。

### 第 2 步：编写以用户利益为导向的文本

遵循 `references/release_notes_guidelines.md` 中的语气规则：
- 描述用户影响，而不是实现细节
- 使用直接称呼（"你"）和动作动词
- 要具体——提及具体的改进

### 第 3 步：前置钩子

前 ~170 个字符是"更多"之前唯一可见的部分。以一个完整、有吸引力的句子开头，突出最重大的更改。

### 第 4 步：回应用户关键词以供转换

1. 从 `metadata/version/{latest}/{primary-locale}.json` 读取 `keywords`
   - 这些规范文件也是 `asc metadata keywords ...` 读取和写入的。
2. 如果该字段为空或缺失，跳过此步骤
3. 确定与所描述更改相关的关键词
4. 自然地将它们编织到说明中——切勿强行或堆砌

### 第 5 步：尊重字符限制

- 主要语言环境的总长度保持在 500-1500 个字符
- 这为本地化扩展留出空间（某些语言扩展 30-40%）
- 硬限制：4,000 个字符

### 第 6 步：可选地草拟促销文本

如果用户需要，草拟一个 170 字符的促销文本，该文本：
- 用一句有力的句子总结更新的主题
- 可以参考季节性活动
- 可以在不提交新内容的情况下更新

### 展示草稿

向用户展示草稿并显示字符计数。在本地化之前等待批准。

## 第三阶段：本地化

将批准的说明翻译到所有现有语言环境。

### 翻译规则

- 使用正式语体和正式的"你"形式（俄语：вы，德语：Sie，法语：vous，西班牙语：usted，荷兰语：u，意大利语：Lei）
- 根据当地市场调整语气——英语的俏皮话可能需要调整正式市场（ja，de-DE）
- **切勿逐字翻译**习语——将其调整为当地等效词
- 英语中的俏皮语气在其他文化中可能需要更尊重或更正式

### 语言环境特定关键词回应用户

对于每个语言环境：
1. 从 `metadata/version/{latest}/{locale}.json` 读取 `keywords`
2. 在翻译的说明中自然地回应用户特定的关键词
3. 如果关键词字段为空，则跳过该语言环境的回应用户

### 验证

- 所有翻译必须 ≤ 4,000 个字符
- 促销文本必须每语言环境 ≤ 170 个字符
- 如果翻译超出限制，请缩短它——切勿在句子中间截断

## 第四阶段：审核和上传

### 第 1 步：展示摘要

显示一个包含所有语言环境及其说明和字符计数的表格：

```
| 语言环境 | 新功能（前 80 个字符...） | 字符数 | 促销文本 | 字符数 |
|----------|--------------------------|--------|----------|--------|
| en-US    | 搜索更快了——...          | 847    | 新睡眠… | 142    |
| ar-SA    | البحث أصبح أسرع — ...    | 923    | نوم جديد… | 138    |
| ...      | ...                      | ...    | ...      | ...    |
```

### 第 2 步：等待批准

未经用户确认，不要上传。

### 第 3 步：上传

通过 `asc` 上传（请与 `asc --help` 核对确切语法）：

```bash
# 单个语言环境直接更新
asc apps info edit --app "APP_ID" --version-id "VERSION_ID" --locale "en-US" --whats-new "Your release notes here"

# 写入 ./metadata/version/<version>/<locale>.json 后批量规范元数据推送
asc metadata push --app "APP_ID" --version "1.2.3" --dir "./metadata" --dry-run
asc metadata push --app "APP_ID" --version "1.2.3" --dir "./metadata"
```

如果草拟了促销文本，请在直接更新命令中包含 `--promotional-text "..."`，或在 `asc metadata push` 之前将 `promotionalText` 写入规范 JSON。

### 第 4 步：处理失败

在部分上传失败时：
- 报告哪些语言环境成功，哪些失败
- 提供重试失败语言环境的选项

## 元数据文件路径

- **关键词**：`metadata/version/{latest-version}/{locale}.json` → `keywords` 字段
- **当前新功能**：`metadata/version/{latest-version}/{locale}.json` → `whatsNew` 字段
- **最新版本**：`metadata/version/` 下最高 semver 目录
- 规范的 `./metadata` 树是 `asc metadata pull`、`asc metadata push` 和 `asc metadata keywords ...` 操作的。
- 遵循与 `asc-aso-audit` 相同的元数据解析约定

## 注意事项

- 新功能**不会**为 App Store 搜索索引——为人类而写，而不是算法。
- 促销文本是唯一无需新提交即可更新的元数据字段。
- 170 字符的可见窗口是您版本说明的最重要部分。
- 每次应用更新都会触发算法重新评估——更新行为很重要，即使文本不影响排名。
- 理想的更新频率：每 2-4 周。
- 对于完整元数据翻译（所有字段），请使用 `asc-localize-metadata`。
- 对于关键词研究和优化，请先使用 `asc-aso-audit`。
- 如果本地关键词字段在草拟前已过时，请使用 `asc metadata pull` 刷新，或使用 `asc metadata keywords diff` 检查计划的关
