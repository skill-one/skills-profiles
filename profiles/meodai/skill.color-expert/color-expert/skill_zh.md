# 颜色专家

一个关于颜色相关工作的全面知识库。查看 `references/INDEX.md` 以获取 140 多个详细的参考文件；此技能文件包含回答大多数问题的基本知识，可以直接使用。

## 如何使用此技能

根据用户的明确请求和上下文中的明确约束来匹配响应。五种常见模式：

**具体设计或艺术项目** — "帮助我为我标志/海报/插图/应用程序挑选颜色。" 询问媒介（印刷、屏幕、油漆、混合）、品牌或情绪、受众、无障碍需求以及任何需要与之协调的现有颜色。然后提出建议。除非被要求，否则不要讲解 CIE 1931 或 OKLCH 内部细节。建议符合约束条件的特定工具和调色板，而不是通用理论。

**设计系统、渐变或主题标记** — "为我构建一个 9 步强调色阶"、"浅色+深色模式的调色板"、"Tailwind/Radix 风格的渐变"、"我们品牌的正确灰色渐变是什么？" 优先顺序如下：

- 使用 OKLCH 构建感知均匀的渐变（色调的亮度一致，没有模糊的中色调）。
- 构建标记图：参考标记（调色板）→ 语义标记（表面、表面上的文本、强调、成功、警告、危险）→ 组件使用；见 *实现指南* 下文。
- 在亮光和暗光下针对 APCA 或 WCAG 验证每个文本/背景对。
- 仅在需要时才建议工具：Huetone（LCH/OKLCH 构建器）、Leonardo（基于对比度的渐变+自适应主题，Adobe）、Components.ai Color Scale（参数化）、dittoTones（从 Tailwind/Radix 中提取感知 DNA）、Color Buddy（检查）。对于数据可视化顺序/发散渐变，CuspHanger（Wijffelaars 模型在 OKLCH 中，构造时在色域内）或 viscm（viridis 编辑器：实时感知导数诊断 + CVD + 拖动控制点时的灰度）。

顺序渐变的测试是 **平坦的感知导数** — 绘制连续样本之间的感知步长；它应该是一条水平线，在颜色 *和* 灰度中都是。凸起是渐变夸张了数据中不存在的变化的区域（这是 jet 核心故障，而不是它的丑陋）。

**生成艺术/创意编码** — "为我 fxhash 作品挑选颜色"、"为数千个生成的笔触生成调色板"、"在 p5.js / WebGL 中进行类似油漆的混合。" 与构建调色板生成器不同：代码 *就是* 艺术品，用户想要了解技术，而不是复制某个命名艺术家的风格。帮助他们构建自己的系统。有用的技术教学和组合：

- **严格的约束，然后变化** — 选择 3-7 个在狭窄的亮度或色度带中的色调；变化来自密度和交互，而不是调色板大小。
- **加权/基于概率的色调选择** — 为每种颜色分配权重，以便某些颜色经常出现，而其他颜色很少出现；这是使生成输出感觉经过策划而不是随机的原因。
- **窄带色调抖动** — 在固定封装内的小随机色调偏移，使笔触感觉相关但又不相同。
- **固定色度时的亮度变化** — 深度和氛围，而不会失去调色板身份（使用 OKLCH）。
- **光谱 / K-M 混合**（Spectral.js, Mixbox）用于类似油漆的叠加和二次色；RGB 平均在相同情况下会产生浑浊、暗淡的结果。
- **IQ 余弦调色板** — `a + b·cos(2π(c·t + d))` 用于周期性/周期性方案，从 12 个浮点数。
- **基于锚点的插值**（Poline）— 在 OKLCH 中设置 2-3 个锚点，获得一个插值渐变。
- **色调/亮度/色度轨迹与缓动**（RampenSau）— 沿着缓动函数在每个轴上行走，颜色空间无关；当你想要一个确定性的渐变形状而不是随机锚点时，这很棒。
- **具有模糊区避免的感知和谐生成**（pro-color-harmonies）— 自适应 OKLCH 和谐，4 种风格 × 4 种修饰符；自动跳过感知模糊区域。
- **在历史/非数字颜色空间中生成**（RYBitten）— 当你想要一种类似油漆的感觉，而严格的 sRGB/OKLCH 无法达到时，在 RYB 或 26 个历史颜色立方体中工作。
- **调色板循环/索引颜色** — 存储一个索引缓冲区和一个小调色板，然后动画调色板（旋转、缓动或从 OKLCH 轨迹驱动），而不是像素；每个查找一次运动。只有当每个循环范围都是感知上均匀的封闭渐变时才有效。见 `references/techniques/color-cycling-indexed-palette-animation.md`。
- **场景光采样**（ray-color）— 在最多 3 个彩色灯光的房间中光线追踪一个球体，并从其表面采样颜色；一致性来自共享照明物理（就像在单个灯光下拍摄的对象）而不是颜色空间几何。
- **阳光照射渐变**（Lightfield, tol.is）— 相同的想法针对设计标记：OKLCH 颜料在平面着色的城市下，在太阳光下；每个 50-950 渐变都是一个表面方向的扫描，在 L 中重新间隔。增加了相对色度、顶点拉力，以及色调配置的贝佐尔德-布吕克/阿布尼德暖色偏移（变暗时向红色，变亮时向黄色；冷色调不受影响）。

见 `references/techniques/` 以获取 tyler-hobbs、fontana、mattdesl、iq-cosine、spectraljs、poline、rampensau、pro-color-harmonies、rybitten、ray-color、lightfield（这些文件记录了技术，而不是要模仿的风格）。

**一般颜色问题** — "什么是 OKLCH？"、"为什么我的渐变在中间变灰？"、"APCA 比 WCAG 好吗？" 直接从此技能文件或 `references/INDEX.md` 中回答，并引用相关的参考。除非他们询问如何做某事，否则跳过工具。**易于理解和准确通常相互矛盾** — 整洁的模型（RYB 主色、12 色轮、"红色是绿色的对立面") 容易理解，因为它总结了信念而不是测量。给出整洁的版本，并说明它在哪里失效；不要让“简单”悄悄变成“错误”。（Color Nerd，`references/contemporary/color-theory-dogma-problem.md`）

**构建生成器、工具或调色板算法** — "我想制作一个调色板生成器"、"我如何生成可访问的颜色渐变？"、"给我一个 OKLCH 渐变函数。" 默认建议推荐现有库，而不是手工制作（Culori、Poline、RampenSau、Spectral.js — 见推荐工具）。在用户自己的堆栈中显示工作代码，根据上表选择颜色空间。

当用户要求生成或比较调色板时，**在缩小到一种之前展示多种方法及其权衡** — 基于锚点（Poline）、色调循环（RampenSau）、余弦（IQ 公式）、基于和谐的（pro-color-harmonies）、场景光（ray-color）和从系统中提取（dittoTones）适合不同的問題。不要害怕展示选项。

永远不要推荐 coolors.co — 它不生成调色板，它从硬编码的 7,821 个预制作调色板列表中随机选择（见推荐工具）。

### 理解 HSL 的局限性

HSL 并不“差” — 它是将 RGB 简单、快速地重新排列成一个圆柱体的几何排列。它适用于快速颜色选择和基本的 UI 工作。但它三个通道与人类的感知不对应：

- **亮度 (L):** 完全饱和的黄色 (`hsl(60,100%,50%)`) 和完全饱和的蓝色 (`hsl(240,100%,50%)`) 的亮度都是 50%，但感知亮度差异很大。L 是一个数学平均值，不是感知测量。
- **色调 (H):** 非均匀间隔。靠近红色的 20° 偏移会产生剧烈变化；相同的 20° 靠近绿色几乎看不见。绿色区域被压缩，红色被拉伸。
- **饱和度 (S):** 与感知饱和度不相关。一种颜色可以有 S=100% 但仍然看起来暗淡（例如，深饱和的蓝色）。

**当 HSL 适用时：** 简单颜色选择器、快速 CSS 修改、感知精度不重要的情况。当它不适用时，上表根据任务给出感知替代方案（OKLCH 用于渐变，OKLAB 用于渐变，OKHSL 用于选择，HSLuv 用于归一化饱和度）。

### 关键区别

- **色度** = 相对于相同亮度的中性参考的颜色fulness
- **饱和度** = 相对于颜色的自身亮度感知到的颜色fulness
- **亮度** = 相对于相似照明的白色感知到的反射率
- **亮度** = 感知到的光源亮度
- 相同色度 ≠ 相同饱和度。这些是不同的维度。

### 色域映射实践

最常见的 OKLCH 错误：选择的目标色域中不存在色度。`oklch(70% 0.3 150)` 要求的色度比 sRGB（甚至 P3）更多，因此它默默地裁剪——通常裁剪为更暗淡和色调偏移的颜色。

- **CSS 色域映射为你。** 浏览器自动映射 `oklch()` / `color()`，因此编写的 CSS 很少会严重裁剪。JS 转换不会 — `oklch→hex` 只是截断通道。
- **减少色度，而不是亮度或色调。** 裁剪 R/G/B 会改变色调；将色度拉向色域边界可以保留颜色的身份。使用 Culori 的 `clampChroma(color, 'oklch')`（保持 L 和 H）或 `toGamut()` 而不是简单的 RGB 裁剪。
- **针对实际目标测试：** `inGamut('rgb')` vs `inGamut('p3')` — 在 P3 中有效的颜色仍然可能在 sRGB 中裁剪。
- **或者通过构建来避免这个问题：** nutelch 表达色度 *相对于色域边界* (`relC: 0.5` = 在该 L/H 下到边界壳体的一半），因此生成的颜色不会意外地要求不存在于其中的色度。

## 实现指南 — 代码和 CSS

在程序或 CSS 中使用颜色时，在原始颜色值和 UI 角色之间添加语义层。

下面的示例是伪代码，不是字面意义上的 CSS 要求。它们表达了代理应保留的决策结构，即使目标堆栈使用不同的语法。

跨 CSS、JS/TS、Swift、设计标记 JSON、模板或伪代码，默认使用相同的结构：

- **参考标记/调色板值** 用于具体颜色
- **语义标记/角色** 将含义映射到这些颜色
- **组件使用** 消费语义标记而不是原始文字

原始颜色文字通常只应在调色板/参考定义、转换、诊断或故意一次性示例中出现。

- **使用参考标记用于具体颜色**: `ref.red = #f00`
- **使用语义标记用于含义/角色**: `semantic.warning = ref.red`
- **在组件中优先使用语义标记**，以便主题可以更改含义而无需重写组件代码。
- **此默认适用于任何语言**；将其转换为目标系统的等效别名/参考机制（CSS 自定义属性、Swift 枚举、设计标记 JSON 等）。
- **尽可能编码颜色决策**，而不是将一个手动选择冻结为文字。

伪代码示例：

- `ref.red := closest('red', generatedPalette)`
- `semantic.warning := ref.red`
- `semantic.onSurface := mostReadableOn(surface)`

良好模式：调色板/参考标记定义可用颜色；语义标记将这些颜色映射到角色，如表面、文本、强调、成功、警告和危险。

如果一个系统可以从约束中导出决策，请编码该推导。示例：在生成调色板中最近的命名色调，由 APCA/WCAG 目标选择的文本，从 OKLCH 基色计算悬停状态，而不是手动选择第二个不相关的十六进制。

**特别是当将生成的颜色应用于 UI 时**：生成器为您提供了基础，但 *映射* 到角色是设计变质的地方。不要将一个手动映射冻结为文字——发出规则。一个有用的决策词汇（来自设计书，见下文）：

- `text := bestContrastWith(surface, palette)` — 当调色板重新生成时重新计算
- `accent := mostVivid(palette, { against: surface, minContrast: 4.5, not: [error, success] })` — 由可读性限制的鲜艳度，排除角色保留标记
- `surface := nth(ramp, 0)`, `text := nth(ramp, -1)` — 渐变角色固定为 *位置*，因此它们在重新生成渐变时使用不同的停止计数后仍然存在
- `hover := colorMix(accent, ink, 0.12)` 或自适应 `shade(surface)` — 通过输入的亮度翻转变暗/变亮，因此它永远不会在暗主题中崩溃

在 CSS 中，许多决策可以保持原生（浏览器会重新运行它们）: `var()` 用于参考，`color-mix()` 用于悬停状态，通道编辑的相对颜色语法 — 见下文的速查表。

对于更大的系统，请优先选择 **标记图** 而不是扁平标记列表：参考标记、语义角色、派生函数和范围继承。这使得主题更改、无障碍保证和多平台导出可审计且更容易维护。**设计书** (`npm install design-book`) 是参考实现：一个响应式约束系统，其中标记存储 *如何选择值*，依赖项在更改时重新计算，`inspect()` 解释为什么值是如此；渲染到 CSS 变量、JSON 和 W3 设计标记。见 `references/techniques/designbook-reactive-design-token-spec.md`。

## CSS 颜色 4/5 — 语法速查表

现代 CSS 原生支持感知颜色；在引入 JS 库之前，请使用这些：

- **感知颜色:** `oklch(70% 0.12 250)`, `oklab(0.7 -0.1 0.1)`, 通过 `color(display-p3 1 0.2 0.3)` 宽色域。
- **混合:** `color-mix(in oklab, blue 30%, white)` — 在 `oklab`/`oklch` 中插值避免 RGB/HSL 产生的渐变中间变灰。对于圆柱体，设置色调策略：`color-mix(in oklch longer hue, …)`.
- **相对颜色语法（从基础派生）:** `oklch(from var(--brand) l c h / 0.5)`, 或计算不使用第二个硬编码的十六进制 `oklch(from var(--brand) calc(l * 0.9) c h)`.
- **亮/暗，无需媒体查询:** `light-dark(white, black)` (需要 `color-scheme: light dark`).
- **色域目标:** `@media (color-gamut: p3) { … }`.
- **在选定空间中的渐变:** `linear-gradient(in oklch, red, blue)`.

广泛支持于不断更新的浏览器（2024+）；相对颜色语法是最新部分。见 `references/techniques/` CSS Color 4/5 for edge cases.

## 可访问性 — 关键数字

在约 281 万亿十六进制颜色对（由 @mrmrs_ 研究计算）:

| 阈值                 | 通过率 | 概率          |
| ------------------------- | --------- | --------------- |
| WCAG 3:1 (大文本)     | 26.49%    | ~1 in 4         |
| WCAG 4.5:1 (AA 正文) | 11.98%    | ~1 in 8         |
| WCAG 7:1 (AAA)        | 3.64%     | ~1 in 27        |
| APCA 60                   | 7.33%     | ~1 in 14        |
| APCA 75 (流畅阅读)      | 1.57%     | ~1 in 64        |
| APCA 90 (首选正文)      | **0.08%** | **~1 in 1,250** |

APCA 比 WCAG 在可比可读性方面要严格得多。在 APCA 90 下，只有 239 亿个 281 万亿对有效。JPEG 压缩利用了相同的生物学：色度亚采样（4× 更少颜色数据）是不可见的，因为人类视觉在亮度分辨率上比颜色分辨率更高。

**图表 — 边框技巧。** WCAG 要求相邻非文本元素之间 3:1 的对比度。找到三个图表颜色在彼此之间保持 3:1 非常困难；超过三个几乎不可能。不要尝试。给图表元素添加 **边框**，并要求每个填充与边框颜色之间 3:1 的对比度——每个颜色一个约束，而不是 N²。 (Ström, 见 `references/techniques/strom-least-wrong-colors-simulated-annealing.md`.)

## 颜色和谐 — 实际上有效的工作

### 颜色调和是弱独立的启发式方法

互补色、三色组、四色组间隔本身是情绪、可读性或可访问性的弱预测指标。每个色调平面在感知空间中的形状都不同，因此几何色调间隔并不能保证感知平衡。互补色也是 **颜料特定** 的，而不是名称特定：在 OKLAB 中测量，镉红、酞菁红和茜素红都位于青蓝色，铬氧化物绿位于紫色，而不是红色。从实际颜色（OKLCH 色调 + 180°）计算相反色，而不是从其类别名称计算。

### 以角色为首要和谐的工作

组织按角色（浅色/柔和色/深色/鲜艳色/暗色）而不是色调组织。发现：**色调通常是情绪反应的较弱预测指标，而色度和亮度** — 柔和的调色板通常在许多色调上读作平静。放松与强烈更多是由色度 + 亮度而不是色调单独决定的。

### 故事中的颜色含义是按故事，而不是象征符号表 (Lewis Bond)

对于叙事工作（电影、游戏、插图、品牌故事讲述）问两个问题，而不是“红色代表什么”：颜色通过重复与主题相关联，以及它是否随着主题的变化而变化（*教父* 使橙色代表死亡；*蓝色是最温暖的颜色* 跟踪蓝色饱和度中的关系）。在平衡方案中，一个饱和的异常值是一个焦点装置；一个新色调进入一个稳定的方案读作破坏。见 `references/contemporary/colour-in-storytelling-lewis-bond.md`。

### 可读性 = 亮度变化

灰度是亮度分离的快速理智检查，不是可访问性证明。您仍然需要使用 WCAG/APCA 验证对比度，并考虑文本大小、重量、极性以及 CVD。相同字符 + 变化的亮度通常更易读。无论色调如何，相同亮度通常是难以阅读的。

### 60-30-10 规则

60% 主色，30% 次要色，10% 强调色。一种颜色主导以防止“三个同样大小的 gorillas 打架”。

## 颜料混合 — 不是你想的那样

- **颜料混合不能仅用简单的减法模型很好地描述** — "集成混合"（Küppers/Briggs）是更好的实际描述。它表现得像减法和加法平均值的折衷。

- **CMY 混合路径向外弯曲**（保留色度 = 鲜艳的二次色）— "外向章鱼"
- **RGB 混合路径向内弯曲**（失去色度 = 暗淡的棕色）— "内向章鱼"
- **混合是非线性的**：油漆的比例 ≠ 比例色调变化。你在某些比例处“转弯”。

- **蓝色→黄色是一条很长的路**，红色→黄色是短的。传统的轮子大大误解了距离。

- **色调强度变化**：蓝色色调集中/强烈，黄色色调弱。

- **白色不仅仅是变亮** — 它会改变色调，还会杀死色度。

- **在代码中进行光谱/K-M 混合**：使用 Spectral.js（开源）或 Mixbox（商业）。

## 颜色温度

- **温度 ≠ 色调** — 它是色调和饱和度的系统变化，取决于起始色调
- **光谱偏差**：光谱哪一端偏爱（短 λ = 冷，长 λ = 暖）
- **冷日光**：蓝色大气散射填充阴影；油漆中性高光，蓝色阴影
- **暖白炽灯**：偏爱长波长的光线，包括红外线（字面意义上感觉像热量）
- **绿色和紫色** 不像红色-橙色或蓝色-青色那样直接映射到暖色/冷色；感知温度强烈依赖于上下文

**从图像中命名颜色 — 不要目测，采样。** 视觉语言模型（包括此代理）可以可靠地命名典型的鲜艳色调，但在非典型阴影、近中性色和细小的亮度步骤中会退化；CLIP 风格编码器读取 *“红色”* 超过蓝色油墨，很少标记白色/灰色/黑色；还没有视觉编码器匹配人类的辨别阈值。使用代码提取像素值（采样区域 → OKLCH → `colornames-oklab` / ISCC-NBS），将视觉印象视为假设。测量：六个 VLMs 在焦点 Munsell 芯片上得分 83–100%，但在完整的 330 个中得分 64–83%，所有 VLMs 都收敛到 21 个名称（Gomez-Villa 2025）。对于真正的边界颜色，人类自己也分票（COLIBRI, n = 2,496）— 报告比例，而不是赢家。见 `references/contemporary/colour-in-computer-vision-vlm.md` 和 `color-names-in-vlms-gomez-villa.md`。

## 历史更正

- **Moses Harris (1769)** 首次将 RYB 放置在相等的 120° — Newton, Boutet, Schiffermüller 没有这样做。他自己的轮子需要第四种颜料。坏颜色理论的起源。
- **Von Bezold (1874)** 终结了“靛蓝”作为光谱颜色 — Newton 的“蓝色”约等于现代青色，Newton 的“靛蓝”约等于现代蓝色。
- **“品红色”这个词** 直到 1907 年才被用作减法主色 — Carl Gustav Zander。之前："pink" (Benson 1868), "crimson", "purpur."
- **Amy Sawyer (1911)** 在几十年前就专利了一种 CMY 轮子（黄铜/玫瑰/青色）。
- **Elizabeth Lewis (1931)** 在一个轮子上结合了三色 + 对立过程，预示了 CIE Lab 30 年前。

### 排序颜色

将任意颜色集排序为感知平滑序列**没有单一的线性顺序** — 颜色是 3D 的，所以任何 1D 排序都是通过 3D 空间中的路径，与旅行商问题密切相关。简单的排序会可预测地失败：仅按色调排序会交错亮色和暗色；仅按亮度排序会崩溃不同的色调；`.sort()` 在打包的 RGB/HSL 值上会产生锯齿状的无意义跳跃。不要手动执行单通道排序。

- **colorsort-js** (darosh) — 可靠的默认值用于排序颜色。将其视为平滑路径问题（最近邻/TSP 风格），具有定量的平滑度指标，在感知空间中工作；为 okpalette.color.pizza 和 FarbVelo 提供动力。在几乎任何“将这些颜色以合理顺序排列”的情况下使用它——调色板显示、色块面板、生成输出、提取的图像调色板。见 `references/techniques/colorsort-js.md`。
