# 创建 QA 回归流程

将 `argent-create-flow` 作为创作引擎加载。遵循其要求的引用，包括记录器语法、选择器、优化、平台异常和修复。这项技能添加了 QA 合同和完成门禁。

**Vega** 支持以下所有项目：`launch: { vega: ... }`、`await:`/`assert:` 选择器、`snapshot:` 和 `idle` 都在其中运行。只有触摸指令缺失，因为 Vega 是远程驱动的。使用记录的 `tool: tv-remote` 步骤进行导航，使用 `tool: keyboard` 进行输入，这使得第 5 个项目没有可控制的内容。D-pad 路径相对于当前焦点位置是相对的，因此用项目 4 的身份检查来门禁每个移动，而不是假设光标落位。阅读 `argent-tv-interact` 以获取焦点读取和远程导航。

**Apple TV 和 Android TV 不在范围内。** 运行器不会拒绝那里的触摸指令，因此它们在手势层失败，而不是在创作指导层。使用 `argent-tv-interact` 并报告该限制。

**物理 iPhone** 运行 QA 流程，有三个硬件限制：重播不会自动绑定手机，因此将它的 udid 作为 `device`（CLI `--device`）并保持其 `connected`；`pinch`/`rotate` 步骤在那里和实时工具一样失败，因此驱动应用程序自己的缩放 UI；流程树是 `describe` 树（相同的 id 和角色），因此在一个模拟器上编写的选择器可能在那里丢失。在录制之前，阅读 `argent-ios-device-interact` 以获取应用程序范围的合同。

## 完成 QA 流程的定义

只有当满足以下条件时，QA 流程才算完成：

1. 第一个不是 `echo:` 或 `script:` 的步骤是 `launch:`。流程内的设置证明了确定性的数据基线。重复运行不会累积工件或需要手动清理。
2. 第一个演练记录了每个操作和实时结构检查。只有三个文档中记录的优化插入是未记录的。
3. 每个需求都映射到一个硬 `await:`、`assert:` 或审查过的 `snapshot:`。回声和截图不是判决。一个负检查需要与之前可见时相同的稳定选择器。
4. 每个屏幕更改都有目标身份，然后是 `idle` 准备就绪。
5. 目标满足稳定选择器和坐标回退规则。QA 仅保留坐标用于真正未标记的目标。Vega 上为空，因为它没有坐标目标。
6. 未更改的 YAML 使用相同的运行器通过两次。第 1 次运行从新鲜的移动 Argent 服务开始，第 2 次运行立即跟随。

## 1. 定义测试合同

在触摸应用程序之前，编写一个紧凑的表格。在最终报告中重申它。包括：

- 应用程序、平台和命名的初始状态。
- 有序的用户操作。
- 每个预期结果、持久性规则或缺失声明占一行。
- 每行稳定的可执行证据。
- 需要的数据和副作用。

使用结构检查进行语义状态，使用截图进行像素，并用于混合需求。一个行为场景变成一个 `qa-<区域>-<行为>` 流程。

不要发明一个材料值或削弱歧义。选择最强的 UI 可验证阅读并报告它。当选择改变测试含义时询问。

使重复运行确定性的：

1. 检查所需的基线而不进行修改。
2. 如果账户是脏的，记录一个安全的重置或种子流程。或者，在设置中包含安全的规范化。
3. 设置导航后，回声命名基线并在第一个场景突变之前硬检查它。使用 `assert:` 或一个目标 `await:` 完全证明基线。
4. 优先在结束时恢复基线。

流程有两个固定装置机制：

- `run:` 重放单独记录的重置或种子流程。
- `script:` 运行请求的本地设置或清理。使用 `flow-add-script` 在演练中记录它。

在清理之前询问创建或删除请求范围之外的有意义用户数据的操作。

### 紧凑示例

工单：在设置中选择暗色。验证暗色被选中，亮色不存在，并且屏幕以暗色模式渲染。

| 合同行          | 操作                   | 证据                                                                    | 状态效果          |
| ---------------- | ------------------------ | --------------------------------------------------------------------------- | --------------------- |
| 登录后的主页     | 启动                   | `await: { visible: { id: home-screen } }`，然后 `await: { idle: true }`     | 现有账户      |
| 打开设置         | 点击 `settings-tab`       | `await: { visible: { id: settings-screen } }`，然后 `await: { idle: true }` | 无                  |
| 证明亮色被选中  | 检查设置         | `assert: { visible: { id: theme-light-selected } }`                         | 如果已经是暗色则失败 |
| 证明暗色被选中   | 点击 `theme-dark-option`  | `await: { visible: { id: theme-dark-selected } }`                           | 主题变为暗色    |
| 证明亮色不存在    | 检查稳定的屏幕   | `assert: { hidden: { id: theme-light-selected } }`                          | 无                  |
| 验证暗色渲染 | 检查稳定的屏幕   | `snapshot: settings-dark`                                                   | 无                  |
| 恢复基线      | 点击 `theme-light-option` | `await: { visible: { id: theme-light-selected } }`                          | 下一次运行开始干净 |

初始的亮色检查建立了后来 `hidden` 检查使用的选择器。最终恢复使第 2 次运行独立。

## 2. 记录场景

遵循 `argent-create-flow` 的启动顺序和实时创作周期。在结构合同检查出现其状态时记录每个结构合同检查。

截图没有记录器形式。在演练期间检查其稳定状态，然后在优化期间添加计划的截图。如果直接恢复改变了状态，请重新录制受影响的行为。一个恢复的演练不是证明。

## 3. 使证据具有区分性

- **状态变化：** 证明新状态和旧状态的缺失，当两者都可能匹配时。
- **取消/持久性：** 跨越提交边界。取消或保存后离开，重新进入，然后验证存储的状态：取消后不变，保存后更新。
- **缺失：** 证明包含屏幕并记录与 `visible` 相同的稳定选择器，然后是操作，然后是 `hidden`。不要仅为了加强正面基线而添加一个未建立好的 `hidden` 检查。在一个集合中，视口缺失不是全局缺失。使用固定的种子位置、计数、空状态或其他集合范围的证据。
- **覆盖层：** 使用 create-flow [隐藏目标程序](../argent-create-flow/references/reliability-and-recovery.md#obscured-targets-and-persistent-overlays)。
- **重复控制：** 优先使用 id。否则使用仅流程的 `within` 与一个稳定的容器。使用 `text.in` 证明在容器内渲染的成员资格。
- **动态内容：** 断言受控状态或稳定的应用程序铬。使用锚定结构来避免不可避免的动态值并披露依赖关系。
- **视觉状态：** 仅对正确、稳定、确定性的屏幕进行截图。使用全屏进行全局更改，使用 `cropOn` 进行一个组件。

永远不要将验收证据放在 `when:` 内。仅使用 `when:` 用于可选设置，该设置重新汇聚到所需路径。

## 4. 完成 和 审计

完成 create-flow 优化和阻塞审计。然后：

1. 将每个合同行映射到执行的操作或硬检查。
2. 构建一个导航表，每行对应一个屏幕更改，命名身份门禁和准备门禁。缺少其中之一的行是阻塞缺陷。
3. 确认设置和结束状态允许立即第 2 次运行。

| 操作             | 目标 | 身份                  | 准备 |
| ------------------ | ----------- | ------------------------- | --------- |
| 点击 `settings-tab` | 设置    | `settings-screen` visible | `idle`    |

这两者修复方式不同。一个缺失的身份检查必须在恢复屏幕上实时记录。一个缺失的 `idle` 检查在 YAML 中添加，因为 `await: { idle: true }` 没有记录器形式，并且是 `argent-create-flow` 的三个允许的优化插入之一。重新录制任何缺失的操作或其他结构检查。

## 5. 证明两次连续的通过

在最后编辑和审计后，将连续设置为零：

1. 为两次通过选择一个运行器。使用 `flow-execute` 本地运行或 `argent flow run <name> --platform <platform>` 用于 CI。切换运行器会重置连续性。
2. 种子、审查和冻结截图基线。基线更新不计为通过。
3. 在第 1 次移动通过之前，为该流程的设备重新循环 Argent 服务：两次热通过是相关证据，因为固定的定时边距可能两次通过仅仅因为环境速度没有改变。将 `stop-all-simulator-servers` 的范围限制为 `devices: [<device>]`。永远不要省略范围——一个空调用是机器范围的扫描，步骤 7 重启此证明足够频繁以反复获取其他代理的设备。使用 MCP 调用 `flow-execute`，或从独立运行器的安装中 `argent run stop-all-simulator-servers --devices <device>`。重置不得改变应用程序或账户数据。对于 Chromium，让运行器启动声明的应用程序并省略 `device`。Vega 没有可回收的 Argent 服务，因此拆除是一个空操作，两次通过都是热的。
4. 从流程的启动和设置运行，不要使用基线更新模式。只有在 `ok: true` 且每个验收检查执行时才计算通过。一个假的 `when:` 可以仅跳过可选设置。一个出错的步骤不会推进连续性，并且计数混合了两种类型——阅读每个原因。一个无法运行的原因（在 `idle` 下不可读的树、无法解析的 `run:` 目标）是环境：修复它并重新运行。**一个失败的 `launch:` 也计为 `errored`，并且它是关于应用程序的判决**——一个不再安装或启动的应用程序是此测试存在的回归，因此报告它而不是重新运行。
5. 在完成之前解决每个通过步骤的警告。还解决来自 `flow-finish-recording` 的记录等待警告。遵循 [实时等待和检查](../argent-create-flow/references/live-authoring.md#live-waits-and-checks)。对于运行器警告，`await: { idle: true }` 引起 [六个不同的警告](../argent-create-flow/references/flow-yaml.md#idle-readiness)，所以首先阅读它是哪一个。两个说屏幕正在移动。一个说等待在保持中中途超时，需要更大的 `timeout:`。一个说树保持为空。一个——**仅在 UI 树上稳定**——说层次结构确实保持静止，并且只有截图对丢失，因此检查捕获路径而不是应用程序的渲染。一个说步骤以没有证据结束。检查屏幕，披露原因，并验证周围验收检查使用稳定元素而不是静止。一个 [无选择器的手势](../argent-create-flow/references/flow-yaml.md#directives)——一个坐标 `tap`/`long-press`/`swipe`，或一个没有 `on:` 的 `pinch`/`rotate`——以不同的形状发出警告：树源中断使其未稳定，因此它盲目地发送了手势，绿色表示仅发送了手势。恢复树源，通常通过重新启动应用程序以使仪器加载，并重新运行。接受该警告需要一个不提供树的应用程序，这无法满足此合同。
6. 立即使用相同的 YAML 和相同的运行器再次运行。不要手动重置应用程序或账户数据。
7. 在任何失败、编辑、重新录制、基线更新或状态变更的手动恢复后重置连续性。通过 `argent-create-flow` 修复，再次审计，并使用新鲜服务重新启动。

只有在连续性达到两次时才完成。如果预期的运行器不可用，报告证明被阻塞。如果产品行为失败，保留强检查并报告回归。永远不要削弱它以获得绿色输出。

记录运行器和新鲜服务设置。

## 6. 报告

报告：

- 流程名称、路径、平台和独立命令。
- 合同行映射到操作和检查。
- 导航表。
- 基线设置、结束状态恢复和接受的依赖关系。
- 两次通过结果、运行器、新鲜服务设置和已解决的警告。
- 截图范围、审查的基线状态和失配容忍度。
- 坐标或原始手势例外。
- 剩余的手动判断或阻塞。
