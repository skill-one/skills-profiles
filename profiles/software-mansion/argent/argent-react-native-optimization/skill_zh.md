## 规则

- 不要应用霰弹式优化。先测量，定义“足够好”的标准（目标指标+阈值），修复主要问题，再诚实地重新测量。
- **快速扫描** — 使用 `react-profiler-renders` 获取实时渲染计数表。立即识别热组件。
- **深度测量** — 加载 `argent-react-native-profiler` 技能。`react-profiler-start` → 交互 → `react-profiler-stop` → `react-profiler-analyze`。
- **检查** — 每个发现使用 `react-profiler-component-source`。使用 `react-profiler-fiber-tree` 追踪组件谱系和渲染成本。
- **验证正确性** — 在修复前，从上述步骤重新收集信息，并逻辑判断该方法是否值得实施。
- **修复** — 应用一个修复。在提交前使用 `debugger-evaluate` 进行验证。
- **重新测量** — 报告目标指标是否改善、退化或保持不变。检查其他区域的退化。如果没有净收益或不可接受的权衡，则回滚。
- **为发现而分析，而不仅为验证。** 使用分析器查找静态分析遗漏的问题，而不仅用于确认修复。
- **每个周期一次架构变更修复。** 机械批量修复（内联样式、索引键）可以分组——批量后重新分析一次。当测量涉及设备交互时，在第一次运行前记录为流程 (`argent-create-flow` 技能)，以便所有后续周期重放相同步骤。
- **React 编译器**：如果 `react-profiler-analyze` 报告 `reactCompilerEnabled: true`，除非你通过 `react-profiler-fiber-tree` 确认了编译器退出（缺少 `useMemoCache`），否则不要提议 `useCallback`/`useMemo`/`React.memo`。
- **子代理**：阶段 1-2 派遣子代理——每个文件一个用于代码检查结果，每个清单项一个用于语义分析。子代理——不能接触设备——所有分析和 E2E 验证必须在主代理中完成。

## 管道

**代码检查和语义扫描以低成本捕获确定性问题。分析器发现静态分析遗漏的运行时瓶颈。两者都要做。**

将此清单复制到你的待办事项列表：

```
优化进度：
- [ ] 阶段 1：代码检查扫描（确定性——无需运行应用即可捕获机械问题）
- [ ] 阶段 2：语义扫描（判断——记忆化、列表、动画等）
- [ ] 阶段 3：基线分析（发现真实瓶颈，修复主要问题）
- [ ] 阶段 4：验证无退化（崩溃、错误、红色屏幕）
```

### 阶段 1：代码检查扫描

在项目根目录一次性运行 ESLint，使用全面的 RN 性能规则集。派遣子代理修复结果——每个文件一个。
有关规则集和流程，请参阅 [references/lint-rules.md](references/lint-rules.md)。

### 阶段 2：语义扫描

审查每个需要判断的领域——记忆化、列表渲染、动画、异步模式、效果清理、状态卫生、上下文架构。每个清单项派遣一个子代理。
有关完整清单，请参阅 [references/semantic-checklist.md](references/semantic-checklist.md)。

### 阶段 3：可视化分析

1. 加载 `argent-react-native-profiler` 技能，启动双重分析
2. 执行关键用户流程（导航用户指定的屏幕，或所有主要流程）
3. 使用 `react-profiler-analyze` + `native-profiler-analyze` + `profiler-combined-report` 分析
4. 将分析结果与阶段 1-2 的发现进行交叉引用
5. 修复影响最大的问题。架构变更后重新分析；批量机械修复。如果记录的流程在修复后中断（例如，UI 布局更改），请遵循 `argent-create-flow` 技能修复流程，而不是默默丢弃它。

### 阶段 4：验证无退化

在范围内导航每个屏幕和 UI 流程，确认每个都无错误渲染。如果没有指定范围，请验证整个应用——通过 `argent-device-interact` 覆盖所有可访问屏幕。使用 `debugger-log-registry` 检查运行时错误（如果它返回 `status: "not_connected"`，则没有日志文件——请先遵循其 `guidance` 重新连接），并拍摄屏幕截图以检查红色/黄色错误屏幕。检查修复引入的退化（例如，渲染次数减少但 CPU 升高，或不同屏幕出现新的卡顿）。仅主代理。

## 全应用优化

1. **阶段 1**：中央运行代码检查（一个命令），并行派遣子代理按文件修复
2. **阶段 2**：每个清单项一个子代理进行语义扫描
3. **阶段 3**：主代理分析主要问题屏幕；自上而下修复架构问题
4. **阶段 4**：主代理导航所有屏幕以验证无崩溃

整个运行后，再次运行代码检查以验证你的更改是否引入了新问题。
这也有助于确保你没有遗漏任何可以修复的问题。
