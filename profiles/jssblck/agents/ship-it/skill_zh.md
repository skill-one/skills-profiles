# 发货

一个完整的发货请求，需要完成提交、推送、以准备状态打开的拉取请求，并且 CI 状态为绿色。打开一个新的非草稿 PR，然后在 CI 运行时完成仓库的必要审核和本地验证。

一个更窄的请求保持其范围。仅用于 CI 修复时，修复受影响的分支和检查，而无需创建 PR 或更改其草稿/准备状态、基础分支、标题或不相关的內容。仅用于监控时，报告结果而无需进行修复。一个明确要求保持草稿的请求优先于完整的工作流。

除非被要求，否则不要合并 PR。仅在存在实质性歧义、需要批准或存在无法使用现有权限解决的阻塞时才暂停。

## 提交请求的工作

在特性分支上工作，而不是默认分支。当当前特性分支拥有变更时，保持在当前特性分支上；否则遵循仓库的命名规范，或者当不存在规范时使用 `agent/`。

检查 diff 和工作树。保留不相关的用户变更并标记明确路径。将相关文件组合成逻辑提交。

使用祈使主语。当变更的原因不明显时，在主题中解释变更的原因。遵循主动归属和标点符号说明。将提交正文包裹在 80 列内，但不要硬换行 PR 段落。

## 打开或重用 PR

对于完整的发货请求，推送并检查是否存在现有的 PR：

```sh
gh pr list --state open --head <branch> --json number,title,url,isDraft,baseRefName,headRefName
```

重用现有的 PR。如果它是草稿，除非用户要求保持草稿，否则使用 `gh pr ready` 标记它为准备状态。如果不存在 PR，使用 `gh pr create` 创建一个非草稿 PR。仅在用户明确要求草稿时使用 `--draft`。除非这是一个现有堆栈中的依赖层或用户指定了另一个基础分支，否则使用默认分支作为基础。

解释变更的原因和变更的内容。当适用时，使用 `Fixes #<n>` 引用原始问题。在编辑正文时保留现有上下文。除非被要求，否则不要添加标签或审查者。

## 运行配置的审核并按比例验证

对于完整的发货请求，在打开或重用 PR 并设置其预期准备状态后，如果项目定义了签收工作流，则运行该工作流。使用仓库当前的审核策略；当不存在时，不要凭空设置关卡。

阅读仓库的检查命令。运行必要的本地检查和覆盖变更行为的测试。在构建之前生成必要的代码。

- 当变更达到该边界时，包含集成测试。确认相关测试运行而不是静默跳过。
- 现有的自动化端到端测试可以提供运行时证据。除非存在独特的风险需要检查，否则不要手动重复它们的覆盖范围。
- 使用手动交互来处理未覆盖的集成或视觉风险。执行代表性受影响的流程，而不是共享组件的每个路径。当变更影响它们时，检查响应式布局。
- 对于 CLI 或 API 行为，一个专注的测试或真实命令/请求可以提供证据。选择捕获风险的方法。
- 对于没有运行时表面的变更，说明不需要运行时捕获。
- 报告本地环境差距，并让 CI 覆盖需要其平台的检查。

通过检查后，仅对新编辑、失败或未解决的风险重复或扩展验证。不要重构不相关的代码以改进验证过程。提交并推送任何必要的修复。

## 添加证据

对于完整的发货请求，添加一个测试部分，包含精确的命令、结果和相关信息差距。当足够时使用现有的自动化输出。

在语言标记的围栏中内联简洁的文本证据：`console` 用于命令转档，`json` 用于 JSON，或 `text` 用于其他输出。在发布证据之前，从证明中删除密钥和私有数据。

使用 `gh --attach` 而不是 `gh-image` 附加有用的截图或录制视频。遵循 [github-image-upload](../github-image-upload/SKILL.md) 以支持媒体、附件语法和验证。当文本证据覆盖变更时，不需要媒体。不要提交证明文件。

调用此完整工作流授权将其证明添加到 PR。将证据保留在 PR 正文，保留其现有解释，并将任何必要的归属页脚保留在最后。

使用 `gh pr view` 验证预期的 PR 基础分支、头分支、状态和证据。

## 照看发布的 PR

发布并验证 PR 后，使用 [babysit](../babysit/SKILL.md) 在等待前检查合并冲突，并监视 CI 直至完成。监视完整的检查集，以便过滤视图不会隐藏失败。对于仅用于监控的请求，报告冲突而无需解决它们。

对于请求中的失败，诊断、修复、运行受影响的检查、提交、推送并再次监视。当行为所记录的内容发生变化时，刷新证明。保留必要的检查；不要绕过它们或在检查失败、被取消或未按预期运行时声称成功。

报告不相关的失败，而不是在没有方向的情况下扩展工作。如果访问权限或基础设施阻塞进展，识别阻塞者和未解决的检查。
