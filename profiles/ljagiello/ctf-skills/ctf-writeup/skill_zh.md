# CTF 写入文件生成器

为已解决的挑战生成标准格式的提交风格 CTF 写入文件。

默认行为：

- 在活跃的比赛中，优化速度、清晰度和可重复性
- 保持写入文件简短，以便队友或组织者可以快速验证解决方案
- 始终生成 `submission`-风格的写入文件
- 优先从挑战数据中选择一个完整的解决方案脚本到最终旗帜

## 工作流程

### 第 1 步：收集信息

从当前会话、挑战文件和用户输入中收集以下信息：

1. **挑战元数据** — 名称、CTF 活动、类别、难度、积分、旗帜格式
2. **解决方案工件** — 利用脚本、有效载荷、屏幕截图、命令输出
3. **时间线** — 采取的关键步骤、死胡同、转折点

```bash
# 扫描利用脚本和工件
find . -name '*.py' -o -name '*.sh' -o -name 'exploit*' -o -name 'solve*' | head -20
# 检查输出文件中的旗帜
grep -rniE '(flag|ctf|eno|htb|pico)\{' . 2>/dev/null
```

### 第 2 步：生成写入文件

将写入文件作为 `writeup.md`（或 `writeup-<challenge-name>.md`）使用以下提交模板生成。

```markdown
<用 3-8 行简短解释关键观察。保持直接。>

\`\`\`python
<从提供的挑战数据到打印最终旗帜的一个完整解决脚本>
\`\`\`

### 第 2 步：<Action>（可选）

<仅在第二个简短步骤真正有助于可读性时添加，例如将核心观察与最终验证分开。>

### 第 3 步：<Action>（可选）

<仅在挑战确实需要时使用。保持步骤总数较小。>

## 旗帜

\`\`\`
flag{example_flag_here}
\`\`\`
```

指导：

- 优先选择 1-3 个简短步骤
- 代码应保持最小的完整解决脚本
- 不要将“恢复秘密”、“推导密钥”和“解密旗帜”拆分为单独的部分片段
- 脚本应从挑战数据开始，并以打印旗帜结束
- 避免长背景部分
- 避免死胡同，除非它们解释了关键的转折点
- 避免多个替代解决方案；选择一个干净的路径
- 仅在用户明确要求的情况下才编辑旗帜

## 最佳实践检查清单

在最终确定写入文件之前，请验证：

- [ ] **元数据完整** — 标题、CTF、日期、类别、难度、积分、作者均已填写
- [ ] **旗帜处理符合请求** — 除非用户要求编辑，否则保留真实旗帜
- [ ] **可重复的步骤** — 读者可以按照您的写入文件重现解决方案
- [ ] **代码可运行** — 利用脚本包含所有导入、正确的变量名和注释
- [ ] **无敏感数据** — 无真实凭证、API 密钥或私有基础设施详细信息
- [ ] **长度保持简洁** — 写入文件足够简短，以便快速审查
- [ ] **工具和版本注明** — 如果行为取决于它们，请提及特定工具版本
- [ ] **正确归因** — 归功于队友、参考写入文件或必不可少的工具
- [ ] **语法和格式** — 统一标题级别，代码块有语言标签

## 质量指南

**要：**
- 解释足够快以验证
- 包含一个完整的解决路径，而不是多个替代路线
- 包含一个完整的脚本，一直到最后一个旗帜
- 显示实际输出（如果非常长，则截断）以证明方法有效
- 为代码块添加语言标签（`python`、`bash`、`sql` 等）
- 保持主路径靠前，以便读者可以快速验证

**不要：**
- 不加解释地复制粘贴原始终端转储
- 粘贴多个部分片段，迫使读者重建最终解决方案
- 在最终写入文件中留下占位符文本
- 包含与解决方案无关的无关信息
- 假设读者知道特定的挑战设置
