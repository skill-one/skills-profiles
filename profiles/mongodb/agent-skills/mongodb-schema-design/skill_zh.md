# MongoDB Schema Design

MongoDB 的数据模型模式和反模式，由 MongoDB 维护。糟糕的模式是大多数 MongoDB 性能和成本问题的根本原因——查询和索引无法修复一个从根本上错误的模型。

## 何时应用

在以下情况下参考这些指南：
- 从零开始设计新的 MongoDB 模式
- 从 SQL/关系型数据库迁移到 MongoDB
- 审查现有数据模型以解决性能问题
- 解决慢查询或文档大小增长问题
- 决定嵌入和引用之间的选择
- 建模关系（一对一、一对多、多对多）
- 实现树/层次结构
- 看到 Atlas 模式建议或性能顾问警告
- 达到 16MB 文档限制
- 向现有集合添加模式验证

### 访问模式分析

在理解更广泛的上下文之前，不要立即推荐模式或模式更改。与用户一起分析访问模式，以识别痛点并寻找优化机会。

#### 工作流程

**步骤 1：评估环境**
向用户询问：
  - 这是一个新设计还是有一个具有现有访问模式的生成交互式数据库？
  - 如果有生产数据，它是否在 Atlas 上？如果是，是什么级别？（M0/M2/M5 对比 M10+）

**步骤 2：确定工作负载类型**
工作负载是读密集型、写密集型还是平衡？这将影响哪些诊断源最相关。
向用户询问：
- 这些集合的主要工作负载是什么——读密集型（分析、报告、搜索）、写密集型（日志、物联网摄取、频繁更新）还是平衡？

使用 `db.serverStatus().opcounters` 进行验证。

**步骤 3：与用户一起选择最佳源**
根据情况推荐最佳源，并解释权衡。对于模式设计决策，我们通常需要结合多个源以获得完整图景。

**步骤 4：继续分析**
只有在选择源之后，才获取数据或指导用户进行分析。

#### 源

- [查询统计](references/source-query-stats.md) - 返回记录查询的运行时统计信息，显示查询形状和频率。**限制**：目前仅捕获读操作（与写模式配对使用）。需要 Atlas M10+ 级别。
- [Atlas 慢查询日志](references/source-slow-query-logs.md) - 审阅慢查询（实际查询，不是形状）以识别性能瓶颈。捕获所有读操作和写操作。需要 Atlas M10+ 级别。
- 代码库 - 检查应用程序代码中的实际查询，以了解访问模式，特别是对于新应用程序或工作负载变化时。可与查询统计结合使用以获得更完整的图景。
- 自然语言输入 - 要求用户用自然语言描述他们的典型查询和访问模式。可作为唯一源或补充和验证其他源——用户可能有数据或代码库中未反映的背景知识。

**结合查询统计和慢查询日志：**

将两者结合使用进行综合分析：
1. 查询统计 → 识别频繁访问模式（哪些查询运行最频繁）
2. 慢查询日志 → 识别性能瓶颈（哪些查询很慢）
3. 专注于模式优化那些既频繁又慢的查询（最高影响）

## 关键原则

> **“一起访问的数据应该一起存储。”**

这是 MongoDB 的核心哲学。嵌入相关数据可以消除连接，减少往返次数，并支持原子更新。仅在必须时才引用。

实现这一哲学的核心方式是 MongoDB 提供了**灵活的模式**。这意味着不同文档中可以有不同字段，甚至不同结构。这允许您根据访问模式以最佳方式建模数据，而不会被僵化的模式所限制。例如，如果不同文档具有不同的字段集，只要它满足您的应用程序需求，那就完全可以。您还可以使用模式验证来强制执行某些规则，同时仍然允许灵活性。

关键原则的另一个含义是，关于预期读/写工作负载的信息对模式设计非常重要。如果来自不同实体的信息块经常一起查询或更新，这意味着将数据块存储在同一文档中可以带来显著的性能优势。另一方面，如果某些信息块很少一起访问，则可能需要将它们分开存储，以避免加载不必要的数据。

#### 模式基础总结

- **嵌入与引用**：根据访问模式选择嵌入或引用：当数据总是一起访问（1:1、1:少数、有界数组、需要原子更新）时嵌入；当数据独立访问、关系是多对多，或数组可以无限制增长时引用。
- **一起访问的数据存储在一起**：MongoDB 的核心原则：围绕查询设计模式，而不是实体。嵌入相关数据以消除跨集合连接并减少往返次数。识别您的 API 端点/页面，列出每个返回的数据，然后调整文档以匹配这些查询。
- **拥抱文档模型**：不要一对一地重新创建 SQL 表为 MongoDB 集合。相反，将连接的表非规范化为丰富的文档，以实现单查询读取和原子更新。当从 SQL 迁移时，识别总是连接在一起的表并将它们合并为单个文档。
- **模式验证**：使用 MongoDB 的内置 `$jsonSchema` 验证器在数据库级别捕获无效数据（类型检查、必需字段、枚举约束、数组大小限制）。对现有集合从 `validationLevel: "moderate"` 和 `validationAction: "warn"` 开始，然后收紧到 `strict`/`error`。
- **16MB 文档限制**：MongoDB 文档不能超过 16MB——这是一个硬限制，不是指导方针。常见原因：无界数组、大型嵌入二进制文件、深度嵌套对象。缓解方法：将无界数据移动到单独的集合，并使用 `$bsonSize` 监控文档大小。

## 嵌入/引用决策框架

| 关系 | 基数 | 访问模式 | 建议 |
|-------------|-------------|----------------|----------------|
| 一对一 | 1:1 | 总是在一起 | 嵌入 |
| 一对少 | 1:N (N < 100) | 通常在一起 | 嵌入数组 |
| 一对多 | 1:N (N > 100) | 通常分开 | 引用 |
| 多对多 | M:N | 变化 | 双向引用 |

这是一个**粗略**的指南，嵌入或引用是否取决于您的具体访问模式、数据大小和读/写频率。始终使用实际工作负载进行验证。

## 这些规则如何工作

### MongoDB MCP 集成

对于自动验证，连接到 [MongoDB MCP 服务器](https://github.com/mongodb-js/mongodb-mcp-server)。

如果 MCP 服务器正在运行并连接，我可以自动运行验证命令来检查您的实际模式、文档大小、数组长度、索引使用情况、慢查询日志等。这使我能够根据您的真实数据提供定制建议，而不仅仅是代码模式。

**⚠️ 安全**：使用 `--readOnly` 以确保安全。仅在需要写操作时才移除。

连接后，我可以自动：
- 通过 `mcp__mongodb__collection-schema` 推断模式
- 通过 `mcp__mongodb__aggregate` 测量文档/数组大小
- 通过 `mcp__mongodb__db-stats` 检查集合统计信息

### ⚠️ 行动策略

**我永远不会未经您明确批准就执行写操作。**

在通过 MCP 执行任何写或破坏性操作之前，我将： (1) 总结精确操作（集合、索引/验证器、受影响的文档估计数量），以及 (2) 要求明确确认（是/否）。我不会在部分或模糊的批准上继续进行。

| 操作类型 | MCP 工具 | 行动 |
|---------------|-----------|--------|
| **读（安全）** | `find`, `aggregate`, `collection-schema`, `db-stats`, `count` | 我可能会自动运行以进行验证 |
| **写（需要批准）** | `update-many`, `insert-many`, `create-collection` | 我将显示命令并等待您的“是” |
| **破坏性（需要批准）** | `delete-many`, `drop-collection`, `drop-database` | 我会警告您并要求明确确认 |

当推荐模式更改或数据修改时：
1. 我会解释**我要做什么**以及**为什么**
2. 我会向您展示**精确命令**
3. 我会**等待您的批准**再执行
4. 如果您说“继续”或“是”，只有那时我才会运行它

**您的数据库，您的决定。** 我在这里提供建议，而不是单方面行动。

3. 我会根据您的实际数据调整我的建议
