# Prisma Next — 反馈（问题报告、功能请求、团队问答）

> **编辑你的数据合约。Prisma 处理其余部分。**

这项技能是能力差距路由模式中的*终端*。当用户希望关闭差距时，其他 Prisma Next 技能的*Prisma Next 尚未实现的功能*条目会路由到这里；该技能也会在用户提出类似*"这是一个 Bug"*、*"提交问题"*、*"功能请求"*、*"我可以向团队询问这个问题吗?"*、*"应该如何将 X 集成到 Prisma Next 中?"*等提示时直接触发。

该技能的任务是选择*正确的渠道*——GitHub 问题或 Discord——然后要么生成一个**结构化、公开安全的**问题正文（不包含秘密信息、不包含专有模式），供框架团队采取行动，要么将用户直接链接到 Prisma Discord 进行同步问答。除非用户明确确认，否则永远不会直接提交到 GitHub。

规范渠道：

- **GitHub 问题**（Bug + 具体的功能请求）：<https://github.com/prisma/prisma-next/issues/new/choose>
- **Prisma Discord**（问答、设计反馈、直接团队联系——包括扩展程序作者）：<https://pris.ly/discord>

## 使用场景

- 另一个 `prisma-next-*` 技能触发了能力差距条目，并且用户表示*"是的，提交功能请求"*。
- 用户说*"这是一个 Bug"*、*"提交这个"*、*"报告这个"*、*"针对 PN 提交问题"*、*"发送反馈"*、*"这应该是一个功能"*。
- 用户描述了意外行为——错误退出代码、与实际不符的错误消息、类型签名与运行时行为不匹配、规划器拒绝了一个看似安全的迁移——并希望将其放在框架团队的注意范围内。
- 用户询问*"我可以向 Prisma 团队询问这个问题吗?"*、*"我可以在哪里与团队交流?"*、*"这是执行 X 的预期方式吗?"*、*"应该如何将我的扩展程序/我的工具与 PN 集成?"*，或任何其他开放式问答或设计反馈提示——包括扩展程序作者询问集成问题。

## 不使用场景

- 用户希望在用户自己的代码中自行修复 Bug。修复方案存在于另一个技能中（调试 / 合约 / 迁移 / 查询 / 运行时 / 构建）。首先链接到正确的技能；只有在用户明确希望框架采取不同行动时才回退到反馈。
- 用户希望升级 Prisma Next（Bug 可能已经修复）→ `prisma-next-upgrade` 技能（单独安装）；此技能将其作为预飞行检查提及。
- 用户的提问已经由集群中的工作流技能覆盖（*"如何添加列?"* → `prisma-next-contract`；*"正确的查询接口是什么?"* → `prisma-next-queries`）。路由到工作流技能，而不是团队——加载技能，回答问题，并且只有在代理无法处理时才升级到 Discord。

## 关键概念

- **三个渠道，一个决策。** GitHub 问题（Bug + 具体的功能请求）、Prisma Discord（问答、设计反馈、直接团队联系），或集群中的另一个技能（当问题被确定为工作流问题而不是需要转交给团队的问题时）。该技能的第一个动作是渠道决策；其余部分都跟随这个决策。
- **公开工件。** GitHub 问题和 Discord 消息都是可读的并已存档。正文/消息不得包含 `DATABASE_URL` 字符串、内部公司模式片段、示例行中的客户数据或任何用户不会公开分享的内容。代理在提交任何一种类型的内容之前都会进行编辑。
- **Bug 与功能请求与问题的区别。** 一个 *Bug* 是“文档化表面行为异常”。一个 *功能请求* 是“我想要一个不存在的功能”。一个 *问题* 是“我想与某人讨论 X，或者我不确定这到底是一个 Bug”。许多能力差距路由都是功能请求；许多扩展程序作者的提示都是问题。
- **框架团队需要复现（仅限问题）。** 没有复现步骤的 Bug 报告很难处理。在可能的情况下，代理会生成一个团队可以在本地重新运行的最小复现步骤——理想情况下是一个针对 [`examples/prisma-next-demo`](https://github.com/prisma/prisma-next/tree/main/examples/prisma-next-demo) 的小改动，团队已经将其检出。Discord 问答不需要完整的复现——一个简短的代码片段加上问题通常就足够了。

## 工作流程

### 1. 选择渠道

用户希望将问题转交给团队。哪个渠道？

**GitHub 问题** 如果满足以下任一条件：

- 用户描述了一个具体的 Bug（有关 Bug 与功能请求的区分，请参见下面的 *分类*）。
- 用户有一个具体的功能请求——一个命名的功能、一个特定的 API 形状、一个特定的 CLI 标志——他们希望在待办事项列表中看到。
- 另一个 `prisma-next-*` 技能路由他们到这里进行功能请求。

**Prisma Discord** (<https://pris.ly/discord>) 如果满足以下任一条件：

- 用户正在提出一个开放式问题——*"这是执行 X 的预期方式吗?"*、*"你会如何处理 Y?"*、*"我看到了奇怪的行为，但我不确定这是否是一个 Bug。"*
- 用户希望在提交功能请求之前获得设计反馈——*"我们正在考虑构建一个自定义中间件来执行 X，这符合框架的方向吗?"*
- 用户是一个扩展程序作者，有一个需要与团队来回讨论的集成问题（依赖关系协调、破坏性变更时间、新的扩展程序表面）。
- 用户明确要求团队——*"我可以向团队询问这个问题吗?"*、*"我可以在哪里与 Prisma 交流?"*、*"扩展程序作者如何与团队讨论事情?"*

**按顺序两者都使用** 如果满足以下任一条件：

- 用户有一个 Bug *并且* 有一个相关功能请求——提交两个单独的 GitHub 问题，不要将它们混合在一个问题中。
- 用户希望在提交功能请求之前讨论设计——从 Discord 开始，一旦形状确定，再提交问题。

### 2. 分类（仅限问题路径）

用户正在提交一个 GitHub 问题。这是一个 Bug 还是功能请求？

**Bug** 如果满足以下任一条件：

- 一个文档化的 CLI 命令退出了错误的代码。
- 错误包的 `fix` 字段具有误导性或错误。
- 发布的 TypeScript 签名与运行时行为不匹配。
- 规划器拒绝了一个应该有效的迁移（或接受了一个不应该有效的迁移）。
- 合约发出产生了一个在运行时无法加载的工件。
- 任何其他文档化表面做了错误的事情的情况。

**功能请求** 如果满足以下任一条件：

- 用户想要一个目前不存在的功能（大多数 *Prisma Next 尚未实现的功能*条目会落入这里）。
- 用户想要更好的错误消息、额外的 CLI 标志、新的中间件、额外的捆绑器插件等。

如果两者都有——一个 Bug *并且* 用户希望有一个相关功能——提交两个单独的问题。混合它们会使框架团队的分类更加困难。

### 3. 收集最小正文（仅限问题路径）

对于**任何一种**：

- **Prisma Next 版本**：`pnpm ls @prisma-next/postgres`（或 `@prisma-next/mongo`）。如果项目使用目标包，则该版本是规范的。
- **Node 版本**：`node -v`。
- **包管理器**：`pnpm` / `npm` / `yarn` / `bun` / `deno`。
- **操作系统**：`darwin` / `linux` / `win32` 和版本字符串就足够了。

对于**Bug 报告**，此外：

- **导致问题的确切命令**（例如 `prisma-next migration plan --name add-email`）。
- **完整输出**，如果涉及结构化错误包，请使用 `-v`。编辑 `DATABASE_URL` 和任何其他秘密。
- **最小的 `src/prisma/contract.prisma` / `src/prisma/contract.ts` 提取**，以重现问题。删除不相关的模型。在用户不暴露任何泄露信息的情况下保留原始模型和字段名称——一个忠实的提取比一个重新主题化的提取更容易让框架团队（和未来阅读问题的读者）进行推理。只有在原始名称会泄露受保护领域详细信息（产品名称、内部代码名称、客户标识符、受监管数据字段名称）时才重命名为中性的占位符（`User`、`Post`、`Tag`））。
- **重现步骤**，作为编号列表。
- **预期行为**——一句话。
- **实际行为**——一句话加上相关输出行。
- **解决方法**，如果有——一句话。

对于**功能请求**，此外：

- **期望的 API 或行为**——一段话。尽可能提供具体的形状（CLI 标志、配置字段、中间件导出、插件 API）。
- **今天差距出现的位置**——哪个技能的 *Prisma Next 尚未实现的功能* 条目触发了请求，或者用户正在尝试完成的工作流。
- **当前的解决方法**，如果有——一句话（并且用户正在遵循的技能正文可能已经说明了这一点）。

### 4. 渲染正文

存储库提供了 GitHub 问题表单（`.github/ISSUE_TEMPLATE/bug_report.yml` 和 `feature_request.yml`）。当用户到达 <https://github.com/prisma/prisma-next/issues/new/choose> 时，他们会选择匹配的模板并填写表单字段；该技能会生成正文，使其与表单一一对应（即使表单未使用，`gh issue create --body-file` 也会生成可解析的工件）。

Bug 报告正文形状（字段名称与 `.github/ISSUE_TEMPLATE/bug_report.yml` 匹配）：

~~~markdown
## 包和版本

<例如 @prisma-next/postgres@0.5.2>

## 发生了什么？

<一句话总结加上相关输出行，编辑了秘密>

## 我期望发生什么？

<一句话>

## 最小化重现

1. <步骤一>
2. <步骤二>
3. <步骤三>

```ts
// schema.psl 提取 + 失败的查询 / 命令
```

## 环境

- Node: <版本>
- OS: <darwin/linux/win32> <版本>
- 包管理器: <pnpm/npm/yarn/bun/deno> <版本>
- 数据库: <Postgres / Mongo> <版本>

## 其他上下文

<可选——链接到源技能的能力差距条目、相关问题编号、涉及的合作伙伴扩展程序>
~~~

功能请求正文形状（字段名称与 `.github/ISSUE_TEMPLATE/feature_request.yml` 匹配）：

~~~markdown
## 你试图解决什么问题？

<段落——这个用例或痛点会解决什么>

## 提议的解决方案

```ts
// 想象的 API 使用 / 行为
```

## 考虑过的替代方案

<一句话或两句——你尝试了当前 API 的什么，以及为什么它不起作用>

## 范围和影响

<哪些包会被影响；特定目标的影响>
~~~

### 5. 标题（仅限问题路径）

- **Bug**：`bug(<领域>): <一句话总结>` — 例如 `bug(cli): migration plan exits 0 when there is no diff`。
- **功能请求**：`feat(<领域>): <一句话总结>` — 例如 `feat(build): first-party Next.js plugin for contract emit`。

领域与技能集群相同：`cli`、`contract`、`migration`、`query`、`runtime`、`build`、`error`、`docs`。

### 6. 用于确认的界面（仅限问题路径）

**永远不要自动提交。** 代理向用户展示渲染的标题和正文，并询问：*"这个看起来可以提交到 GitHub。是否要提交?"*。只有在用户明确批准后才会提交。

### 7. 提交（仅限问题路径）

首选。两步：

1. **将渲染的正文写入临时文件。** 使用您的文件写入工具（您在磁盘上创建任何其他文件时使用的相同工具）将正文写入例如 `wip/pn-issue-body.md` 或 `/tmp/pn-issue-body.md`。正文内容只是在此工作流第 4 步生成的 Markdown——没有周围的 Shell 引用，没有 Here 文档。
2. **从 `gh` 引用该文件。** 运行：

   ~~~bash
   gh issue create \
     --repo prisma/prisma-next \
     --title "<标题>" \
     --body-file <步骤 1 的路径>
   ~~~

**反模式（不要这样做）：** 通过 `--body "$(cat <<EOF …)"` 或 `--body-file <(cat <<EOF …)` 插入正文。这些一行代码可靠地会在问题正文泄露 `cat <<'EOF'` / `EOF` 标记，当代理使用正文插值重复模板时。始终先将正文写入真实文件，然后传递路径。

如果 `gh` 未安装：在浏览器中打开预填充的新问题 URL：

~~~text
https://github.com/prisa
