# 发送消息

使用 `messages.send`、`messages.get` 和 `messages.activities.list` 操作直接消息工作流。

## 建立连接和范围

1. 让 MCP 客户端执行 OAuth 2.1/PKCE 授权。不要请求、接受、打印或存储令牌、API 密钥、授权标头、客户端 ID 或密钥。
2. 在进行变更之前，显示当前连接选择的组织和发送者资料。如果客户端上下文没有暴露两者，使用 `sent-account-readiness` 检查授权范围后再继续。
3. 当请求的组织或发送者资料与当前授权的授权不同时，在客户端重新授权。不要用负载字段模拟范围切换。
4. 最小化敏感输出。在实用的情况下遮盖电话号码，并且在操作员审查消息后不要重复消息正文。

如果 MCP 不受支持或授权失败，保持技能可用于负载规划。解释执行需要兼容的客户端或重新授权；不要要求用户粘贴凭证。

## 检查消息

- 当知道消息标识符时，使用 `messages.get` 获取当前记录。
- 使用 `messages.activities.list` 获取生命周期事件和交付证据。
- 声明接受的或排队的发送不是交付的证明。只有在返回的状态或活动建立交付时才报告已交付。
- 返回回答问题所需的标识符、时间戳和状态证据，遮盖接收者数据，除非有必要才包含消息正文。

对于跨多个交付记录的聚合趋势、漏斗或根本原因分析，转交给 `messaging-performance-analyzer`。

## 准备发送

1. 解析预期通道、发送者资料、接收者、模板或内容、变量、调度输入以及工具支持的任何幂等字段。不要编造缺失的值。
2. 对于高容量发送，使用 `sent-account-readiness` 在准备变更前检查 `balance.get`。如果可用余额或账户就绪状态不足或不确定，则停止。
3. 在调用工具之前构建确切的 `messages.send` 参数。
4. 显示包含所选组织、发送者资料、通道、确切目的地、内容或模板标识符、变量以及调度/幂等输入的负载预览。仅显示一次敏感内容；在操作员仍能验证目标的情况下遮盖它。
5. 请求对此确切负载的明确确认。对话中早先给出的通用批准是不够的。
6. 在确认后立即调用 `messages.send`。如果任何负载值、范围或经过的上下文发生变化，则丢弃确认并重新预览。

在没有预览和调用之前的明确确认的情况下，永远不要调用 `messages.send`。

## 处理结果和重试

- 报告消息标识符和返回的接受状态。当响应仅建立接受或排队时，说“接受”或“排队”；不要说“已交付”。
- 当用户询问后续交付状态时，使用 `messages.get` 或 `messages.activities.list`。
- 将每次重试视为新的变更：重建负载，显示新的预览，并在重试之前立即获得新的明确确认。
- 不要盲目重试模糊的发送。如果第一次调用超时或其结果未知，当存在标识符时，检查 `messages.get` 和 `messages.activities.list`。在没有确凿证据的情况下，报告未知结果和重复风险。只有在操作员选择这样做并完成新的预览和确认后，才尝试再次发送。
