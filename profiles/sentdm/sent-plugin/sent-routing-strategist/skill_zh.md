# 发送路由策略师

路由是 Sent 最昂贵的误解所在之处。几乎每个决策都受以下两个事实支配：

1. **`channel` 数组是一个广播列表，而不是偏好顺序。** `["whatsapp", "sms"]` 对两个收件人创建四个消息和四个费用。没有 `fallback` 字段，也没有有序偏好语法。
2. **自动路由是后备机制。** 省略 `channel`，或发送 `["sent"]`，平台将选择路由，然后在路由级失败时重新路由至最多三个不同的渠道和提供商组合。

## 确定渠道值

| 意图 | 正确值 | 原因 |
| --- | --- | --- |
| 尽可能以最佳方式触达收件人 | 省略 `channel` 或 `["sent"]` | 启用路由选择和重新路由 |
| 保证一个特定渠道 | `["sms"]`、`["whatsapp"]` 或 `["rcs"]` | 固定会限制匹配到该渠道，且不会跨渠道 |
| 故意在不同渠道上发送相同内容 | `["whatsapp", "sms"]` | 广播；预期每对渠道一个消息和一个费用 |
| "尝试 RCS，回退到 SMS" | 省略 `channel` 或 `["sent"]` | 有序数组会广播；自动路由执行后备 |

任何不在 `sent`、`sms`、`whatsapp` 和 `rcs` 之外的值会返回 `400`。当用户要求有序后备时，在编写代码前明确命名误解，因为失败模式是重复交付和重复费用，而不是错误。

## 固定渠道放弃的内容

固定会限制路由匹配到指定渠道。没有渠道约束的规则仍然匹配并解析到固定渠道，因此固定不需要特定渠道的规则存在。固定发送永远不会跨到不同渠道，尽管当规则允许时同渠道提供商跳转仍然是可能的。如果固定渠道上没有路由，消息会以 `FAILED` 状态结束且没有匹配路由——它不会静默回退。

当合规性、合同或内容约束要求特定渠道时固定。否则优先选择自动路由。

## 读取结果

`POST /v3/messages` 返回 `202` 并包含每个收件人的 `message_id` 值。对于自动路由，回显的每个收件人渠道不是解析路由，且之后不会更新。从证据中解析真相：

| 问题 | 证据 |
| --- | --- |
| 实际尝试了哪个路由 | `message.routed` 事件，或路由后的 `GET /v3/messages/{id}` 上的 `channel` |
| 收件人的设备是否接收 | `message.delivered` |
| 尝试了哪些路由序列 | `GET /v3/messages/{id}/activities` |
| 为什么停止 | 终端状态加上渠道值 |

## 终端状态解释

| 状态 | 含义 | 正确响应 |
| --- | --- | --- |
| `FAILED` | 路由尝试失败；自动路由可能仍会排队另一个尝试 | 在将其视为最终状态前检查最新的消息状态和活动 |
| `FILTERED` | 政策门禁——同意阻止或路由拒绝 | 永不重试；同意阻止是合规性停止 |
| `BLOCKED` | 账户前置条件——余额、入职配额、未批准模板 | 修复账户条件，然后再次发送 |
| `SCHEDULED` | 由静音时段策略暂停 | 等待；它会自动重新进入管道 |

`channel` 为 `auto` 的结果意味着消息在任何路由尝试前就已结束。原因是无匹配路由、无效模板参数、同意阻止或账户前置条件。账户前置条件不会拒绝发送请求：它会以 `202` 接受，受影响的消息会显示为 `BLOCKED`。

Sent 在这些情况下在消息上内部记录发送时原因代码，但不会在 API 响应或 webhook 中返回它们，因此诊断依赖于状态和渠道组合加上活动历史。从可观察证据到根本原因的映射在 [references/routing-diagnosis.md](references/routing-diagnosis.md) 中表列。

## 重新路由行为

只有在终端失败表明路由或运营商问题可能被其他路由克服时才重试失败路由：此路由无法投递、提供商服务不可用、提供商超时或传输错误。其他所有失败保持 `FAILED`。

重新路由会重用相同的 **`message_id`** 并重新运行管道，因此 `message.queued` 和 `message.routed` 再次触发，同意门禁在每次尝试时重新应用，已尝试的路由会被排除。上限是初始发送和所有重新路由中最多三个不同的渠道和提供商组合。

客户询问的 WhatsApp 到 SMS 行为是这种情况的一个特定案例：一个被接受但因收件人侧原因失败的 WhatsApp 消息会重新路由并记录一个收件人范围的规则，即 WhatsApp 对该号码不可投递，因此后续自动发送会跳过该收件人的 WhatsApp。它需要自动路由；固定 WhatsApp 发送无法产生它。

## 自动路由如何选择路由

路由来自平台维护的规则，在发送时根据收件人属性（国家、号码前缀、确切号码、运营商、号码类型、转网状态）、发送者、模板属性、渠道以及目的地是否为国际进行评估。顺序是：先匹配确切收件人规则，然后是账户范围的，再是全局的，接着是匹配特定性，然后是规则优先级，然后是更长的号码前缀，然后是最旧的规则。排除不活跃、已删除、过期和低于阈值的规则。模板有明确非批准审核状态的候选者会被丢弃，而没有任何记录审核的渠道不会被阻止。第一个存活的候选者获胜，其余的作为后备路由保留。

没有固定的渠道偏好顺序，因此永远不要承诺"RCS 优先，然后 WhatsApp，然后 SMS"。在做出任何关于特定路由选择原因的声明前，请阅读 [references/routing-model.md](references/routing-model.md)。

## 成本和数量后果

由于广播会根据收件人数乘以消息，因此在发送前审查任何多渠道数组以符合预期支出。1,000 个收件人的发送使用两个渠道会产生 2,000 条消息。每请求收件人上限为 1,000，并记录的节流将完整批次与大约每秒一个请求配对以保持在每分钟 200 个请求的预算内。

今天的 RCS 包含文本加上最多四个建议芯片，映射自模板按钮，并且每个外发的 RCS 消息都会接收附加的 STOP 芯片。不要设计依赖富卡片、轮播或媒体的固定 RCS 流程。

## 边界

使用 `sent-messaging` 执行带确认的单次发送，`sent-two-way-messaging` 用于同意和入站关键字语义，`messaging-performance-analyzer` 用于聚合投递率回归，以及 `sent-webhook-engineer` 用于接收和去重该技能教您读取的事件。
