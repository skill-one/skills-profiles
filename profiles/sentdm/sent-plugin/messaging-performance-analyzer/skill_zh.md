# 消息性能分析器  

## 概述  

使用此技能将原始 Sent 消息证据转化为简洁的诊断，说明发生了什么变化、在哪里出现漏斗问题以及首先需要修复什么。在解释运营商、WhatsApp 或 RCS 提供商代码之前，将每个分析都锚定到 **Sent 消息 ID**、**消息状态**、**消息活动** 和 **webhook 事件**。  

Sent 的 v3 发送端点接受基于模板的请求，并返回用于异步跟踪的每个接收者的 `message_id` 值。状态通过 `GET /v3/messages/{id}` 获取，详细的生命周期证据通过 `GET /v3/messages/{id}/activities` 获取。Webhook 端点支持事件摄取、事件类型发现、事件历史记录、测试交付和密钥轮换。  

## 何时使用  

当用户询问消息失败的原因、交付或阅读率下降的原因、回退是否正常工作、提供商是否在过滤流量，或活动表现如何时，使用此技能。在诸如“MDR”、“交付报告”、“webhook 事件”、“活动”、“状态”、“失败”、“未交付”、“阅读率”、“回退”、“过滤”、“限流”或“运营商拒绝”等词语触发时使用。  

不要使用此技能来注册 10DLC、设计发送者配置文件、上线 RCS 或编写 WhatsApp 模板。在隔离性能症状后，将这些工作流程交给相关技能处理。  

## 证据层级  

从 Sent 拥有的证据开始，然后用提供商的上下文进行丰富。这可以防止过度拟合可能缺失、过时或在不同渠道中标准化不同的运营商代码。  

| 证据 | Sent 验证路径 | 用于分析 |
|---|---|---|  
| 发送响应 | `POST /v3/messages` | 识别请求 ID、接受的接收者、渠道扩散和 Sent `message_id` 值。 |
| 当前状态 | `GET /v3/messages/{id}` | 确认最新的已知生命周期状态和 API 暴露的任何错误详情。 |
| 活动时间线 | `GET /v3/messages/{id}/activities` | 重建接受、路由、发送、交付、阅读和错误转换。 |
| webhook 配置 | `GET /v3/webhooks`, `GET /v3/webhooks/event-types` | 确认客户是否订阅了分析所需的事件。 |
| webhook 事件历史记录 | `GET /v3/webhooks/{id}/events` | 将交付的事件与 API 状态和客户摄取日志进行比较。 |
| webhook 连接性 | `POST /v3/webhooks/{id}/test` | 在归咎交付基础设施之前验证端点可达性。 |  

## 流程  

### 1. 在分析漏斗之前固定问题  

将用户的确切问题表述为可衡量的比较。“WhatsApp 不行”变成“周一至周三从配置文件 A 发送订单模板的 WhatsApp `DELIVERED` 率是否下降？”精确的问题可以保持队列稳定，防止混合渠道的平均值隐藏失败模式。  

在计算任何内容之前，捕获这些维度：配置文件或发送者身份、模板 ID/名称、渠道、国家、发送窗口、接收者分段以及是否请求回退或多渠道广播。  

**示例。** 如果用户说“RCS 回退停止工作了”，将队列定义为省略 `channel` 或使用 `channel: ["sent"]` 的发送，然后比较选定的 `payload.channel` 和消息活动。将任何显式的多渠道数组作为广播单独分析。  

### 2. 从 Sent 消息 ID 构建队列  

使用 Sent `message_id` 作为主要单位。当指定多个渠道时，v3 发送可以为每个接收者和渠道对创建单独的消息。在终端结果汇总中，每个 Sent 消息只计算一次，然后在去重后，才添加接收者级或活动级汇总。  

区分活动历史记录和最新状态快照。历史记录可以证明其包含的转换。快照（如 `status=DELIVERED`）只能证明观察到的当前结果；它不能证明导出也观察到了 `QUEUED`、`ROUTED` 或 `SENT`。将不可用的转换分母报告为 `N/A`，而不是零，并且永远不要合成缺失的转换。  

除非导出的证据缺少 Sent ID，否则不要使用提供商 ID（如 WhatsApp `wamid`、SMS 运营商 ID 或 RCS 消息 ID）作为主要连接键。提供商 ID 对于升级很有用，但 Sent API 和仪表板通过 Sent 消息 ID 跟踪状态。  

### 3. 将生命周期阶段标准化为 Sent 文档的状态  

使用 Sent 文档的交付生命周期作为第一轮漏斗：`QUEUED`、`ROUTED`、`SENT` 和 `DELIVERED`。将 `READ` 视为 WhatsApp 和 RCS 的单独参与指标，永远不要将其视为 SMS 交付要求。使用仅存在于证据中的字段将终端失败、延迟/在途消息、接收的入站消息和格式错误/未知记录分到不同的桶中。  

| 阶段 | 解释 | 常见的诊断问题 |
|---|---|---|  
| `QUEUED` | Sent 接受了处理请求。 | 队列是否在增长或请求从未路由？ |
| `ROUTED` | Sent 选择了一个渠道/提供商路径。 | 路由是否选择了预期的渠道或回退路径？ |
| `SENT` | 消息离开了 Sent/提供商处理，前往目标网络。 | 提供商接受率高，但下游交付低吗？ |
| `DELIVERED` | 在支持的情况下确认了交付。 | 目标网络是否确认了接收？ |
| `READ` | 在可用的情况下观察到 WhatsApp/RCS 参与接收。 | 用户在交付后是否打开了消息？ |
| 错误/失败 | 发生了终端或可恢复错误。 | 根本原因是合规性、有效负载、吞吐量、退订还是提供商中断？ |  

### 4. 在诊断交付之前检查 webhook 健康状况  

仪表板活动下降或客户侧事件下降可能是 webhook 摄取问题，而不是交付问题。确认 webhook 存在性、活动状态、事件订阅、最近的事件历史记录和测试交付。只有在用户明确要求或怀疑凭证泄露时才轮换密钥，因为轮换会立即使旧密钥失效。  

**示例。** 如果 Sent 状态显示 `DELIVERED`，但客户数据库显示“无交付回调”，请检查 `/v3/webhooks/{id}/events` 和客户的端点日志。如果 Sent 有事件，但端点返回失败，则修复是 webhook 处理，而不是活动路由。  

### 5. 在命名根本原因之前按渠道拆分  

SMS、WhatsApp 和 RCS 失败的方式不同。除非用户明确要求混合 KPI，否则不要将它们平均起来。比较每个渠道的漏斗，然后比较汇总结果。  

| 渠道 | 首次拆分 | 典型后续证据 |
|---|---|---|  
| SMS | 国家、发送者/配置文件、10DLC 活动、退订、运营商系列 | 合规性状态、品牌/活动准备情况、退订日志、吞吐量模式。 |
| WhatsApp | 模板、语言、类别、接收者国家、质量/层级症状 | 模板状态、阅读回执、对话窗口、Meta 端的错误（如果存在）。 |
| RCS | 代理准备情况、自动路由、固定渠道失败、文本/建议芯片渲染 | Sent RCS 设置状态、选定路由和精确的活动/错误详情。 |  

### 6. 在建议修复之前量化影响  

一起报告原始计数和比率。在 15 条消息中 40% 的失败率与在 150,000 条消息中 4% 的失败率是不同的决策。将全球总数与每个渠道×方向组进行核对，保留显式的 `unknown` 组而不是无声地丢弃不完整的维度。包括排除项，如待处理消息、测试流量、沙盒发送、重试和重复渠道扩散。  

一个实用的分析表格应包括：发送计数、最新状态分布、失败计数、与基线的失败率差异、最精确的错误字符串/代码、首次观察时间戳、受影响的模板、受影响的国家和受影响的配置文件。  

### 7. 将诊断转换为下一步行动  

以一个主要诊断、一个置信度级别和下一步验证步骤结束。避免长列表的通用修复建议。将每个建议都与观察到的证据挂钩。  

**示例。** “最大的漏斗出现在 SMS 流量在配置文件 `support-us` 的 `ROUTED` 阶段，从 UTC 14:10 开始。WhatsApp 和 RCS 队列稳定。受影响的流量使用相同的订单更新模板和 US A2P 路由。下一步验证 Sent 品牌活动状态和退订处理；如果合规，则升级精确的消息 ID 和活动时间戳。”  

## 要避免的常见合理化  

在检查 Sent webhook 事件历史记录和端点响应之前，不要从客户侧 webhook 缺失推断交付失败。webhook 摄取失败经常与交付失败相似。  

在比较基线、国家、发送者/配置文件和模板之前，不要将活动标记为“运营商过滤”的小样本。过滤是一个隔离队列后的结论，而不是“失败”的同义词。  

不要将 `READ` 视为通用阶段。Sent 记录 WhatsApp 和 RCS 的阅读回执；SMS 通常不支持阅读回执。  

不要将广播误认为回退。省略 `channel` 或 `["sent"]` 启用自动路由；一个显式渠道固定交付；多个显式值创建单独的消息。每个返回的 `message_id` 只计算一次，并报告选定的渠道。  

## 验证清单  

- [ ] 分析使用 Sent `message_id` 值作为主要单位。  
- [ ] 队列由时间窗口、配置文件/发送者身份、模板、渠道和接收者分段固定。  
- [ ] 状态计算使用每个 Sent 消息 ID 的最新已知状态。  
- [ ] 转换计算使用观察到的活动历史记录，并且永远不会从最新状态填充阶段。  
- [ ] 待处理或在途消息要么被排除，要么被单独报告。  
- [ ] SMS 交付分析在 `DELIVERED` 处停止；WhatsApp/RCS `READ` 被标记为参与。  
- [ ] 全球和渠道×方向总数相互核对，包括格式错误和显式的 `unknown` 桶。  
- [ ] 当症状缺少回调时，检查 webhook 配置、事件历史记录和端点测试结果。  
- [ ] 渠道特定失败在报告汇总比率之前拆分。  
- [ ] 提供商或运营商代码被精确引用为观察到的，而不是从查找表发明。  
- [ ] 最终建议命名一个下一步验证步骤和证明该建议的证据。  

## 相关技能  

使用 `sms-10dlc-registration` 当漏斗指向美国 A2P SMS 合规性、品牌注册、活动注册或退订/选择入证据时。  

使用 `rcs-agent-onboarding` 当症状指向 RCS 代理批准、启动准备情况、能力差距或回退设计，而不是实时交付分析时。  

使用 `sender-profile-architect` 当问题是租户/配置文件隔离、webhook 路由、凭证作用域或多品牌发送设计时。  

使用 `waba-template-author` 或 `template-builder-ui` 当根本原因是 WhatsApp 模板类别、审核状态、模板有效负载结构或编写工作流时。  

使用 `sent` 技能用于共享 Sent 术语和路由。
