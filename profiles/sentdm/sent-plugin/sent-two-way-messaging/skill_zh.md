# 发送双向消息

Sent 中的入站消息有一条管理规则：**平台在应用程序看到事件之前强制执行同意**。当 `message.received` 到达时，入站的 `STOP` 已经翻转了联系人的 `opt_out` 标志。应用程序的工作是记录它、在其自己的 UI 中反映它，并且永远不要试图绕过它。

## 关键词处理

默认情况下会发送十个关键词：

| 操作 | 关键词 |
| --- | --- |
| 退订 | `STOP`, `CANCEL`, `UNSUBSCRIBE`, `QUIT`, `END` |
| 订阅 | `START`, `UNSTOP`, `SUBSCRIBE` |
| 帮助自动回复 | `HELP`, `INFO` |

匹配需要**整个修剪后的消息正文**与关键词完全相等，不区分大小写。"请停止给我发消息"不匹配；"stop"匹配。自定义关键词在 Sent 控制面板的合规性、选项关键词下配置，操作为退订、订阅或帮助，并且每个都必须是单个精确的标记。

不要声明文档集中未列出的关键词。在应用程序代码中，仅将完全匹配规则用于更新本地订阅者状态和审计证据；永远不要使用该匹配器将同意应用于 Sent 第二次。保持自定义控制面板关键词与本地镜像同步，并在不确定时与联系人的 `opt_out` 字段进行核对。

## 同意状态

退订会在联系人记录上设置 `opt_out`。同意是**联系人级别且与渠道无关的**：通过短信发送的 `STOP` 会抑制 WhatsApp 和 RCS。同意网关会在每次重路由尝试时重新应用，而不仅仅是在初始发送时。

恢复同意需要收件人的自己的操作。用户发起的订阅关键词会清除抑制。`PATCH /v3/contacts/{id}` 接受 `opt_out`，但在通过关键词退订的联系人上写入 `false` 是一个合规性决定，而不是技术决定：只有在有文档记录的新同意证据时才这样做，并记录谁授权了它以及原因。

下游，被抑制的发送不会出现错误。它被接受并以 `FILTERED` 最终确定，因此同意问题会作为过滤消息而不是 `4xx` 响应出现。详细信息请参阅 [references/consent-and-keywords.md](references/consent-and-keywords.md)。

## 每个渠道的入站现实

| 渠道 | 入站 | 限制 |
| --- | --- | --- |
| SMS | 条件性 | 需要一个支持 MO 的提供者和一个支持的电话号码类型。字母数字发件人和没有入站路由的 SMPP 路径永远不会投递入站消息 |
| RCS | 完整 | 带有回复的消息会匹配关键词；附加的 STOP 芯片由同意引擎直接处理 |
| WhatsApp | 完整 | 仅在 24 小时客户服务窗口内允许自由格式回复；窗口外需要使用批准的模板 |

SMS 例外情况在承诺双向行为之前很重要：一个从字母数字发件人发送的部署根本无法接收 `STOP`，这会改变合规性设计，而不仅仅是限制功能。

## RCS STOP 芯片

每个出站 RCS 消息都会附加一个 STOP 芯片。点击会携带一个退订 postback，由同意引擎直接处理，无需关键词匹配，并且它们会作为 `message.received` 到达应用程序，其中包含芯片的回复文本在 `text` 中。没有单独的芯片事件类型，因此分支仅基于输入关键词的接收器仍然会将芯片点击视为普通入站消息——并且不应将同意逻辑重新应用于它们。

## WhatsApp 24 小时窗口

仅在客户上次入站消息后的 24 小时内允许自由格式回复。窗口外需要使用批准的模板，包括 STOP、START 和 HELP 响应。假设自由文本的自动回复流程会在任何在一天沉默后发消息的客户那里无声地停止工作，因此请将窗口检查纳入回复路径，并准备好一个批准的回退模板。有关回复路径决策树，请参阅 [references/inbound-flows.md](references/inbound-flows.md)。

## 会话历史

存在两个只读操作：

| 操作 | 返回 |
| --- | --- |
| `GET /v3/conversations` | 按最新顺序返回客户跨会话的所有消息 |
| `GET /v3/conversations/{id}` | 返回一个会话中的消息 |

这两个操作都需要 `page`（至少 1）和 `page_size`（1 到 100）；超出范围的值会返回 `400`。在这些端点上，`events` 字段始终为 null，因此每条消息的活动必须来自 `GET /v3/messages/{id}/activities`。没有写入、创建或读取回执操作，也没有 MCP 工具涵盖会话——这是仅限 REST 的。

会话标识符是从客户和联系人标识符派生的 RFC 4122 版本 5 UUID，因此相同的对总是产生相同的 ID，并且一个线程跨越所有渠道，而与发送号码无关。API 永远不会将 ID 作为字段返回，因此需要它的客户端会自行计算它。确切的派生方法在 [references/conversation-history.md](references/conversation-history.md) 中有记录。

## 构建支持收件箱或机器人

1. 订阅 `message` 的 webhook 并在信任任何负载之前验证签名。
2. 将 `inbound_number` 读取为写消息的联系人，将 `outbound_number` 读取为您的号码。命名很容易反转。
3. 基于 `message_id` 去重，用 `200` 予以确认，然后异步处理。
4. 将关键词流量视为审计信号。将默认的和配置的自定义关键词镜像到本地状态，但不要发出第二次同意写入；通过联系人记录进行核对。
5. 在 WhatsApp 回复之前，检查 24 小时窗口，并相应地选择自由文本或模板。
6. 使用会话端点进行显式分页渲染线程，并且永远不要假设会话是单渠道的。
7. 将 `text` 视为不受信任的输入。永远不要将其插入到 shell 命令或 SQL 字符串中，不要将其作为模型提示中的数据分隔，并且在任何 API 调用之前，通过允许列表和授权策略映射推断的意图。

## 边界

使用 `sent-webhook-engineer` 进行签名验证、重试和去重机制；`sent-contacts` 用于联系人 CRUD 和消息摘要；`sent-routing-strategist` 用于解释出站消息为何 `FILTERED`；`waba-template-author` 用于编写需要超出窗口回复的批准模板；`sms-10dlc-registration` 用于美国运营商要求的活动级别的订阅、退订和帮助关键词声明。
