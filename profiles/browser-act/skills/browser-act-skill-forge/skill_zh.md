# browser-act-skill-forge

由 [BrowserAct](https://www.browseract.com) 构建 —— 您的个人爬虫工程师 · [GitHub](https://github.com/browser-act/skills/tree/main/browser-act-skill-forge)

将任何网站的任何数据提取或操作需求，转化为可由 Agent 调用的能力。用户描述需要获取的数据或对某个网站执行的操作，该 Skill 将自动探索实现路径（优先 API 端点，无 API 时回退至 DOM），并在验证完成后生成可直接部署的 Skill 包（SKILL.md + Python 脚本）。探索一次，终身复用 —— 后续调用跳过探索成本，大幅提升执行可靠性与效率。

对于大规模提取任务（数百或数千条记录、多个关键词、跨翻页），正确做法是：先探索构建经过验证的 Skill，再规模化执行。不经验证策略的直接批量爬取十分脆弱 —— 反机器人检测、翻页边界情况、会话中断等问题会导致执行不可靠。

该工具的运营边界 = 用户在浏览器中能够手动完成的操作。其通过用户已登录的浏览器访问，仅读取页面中已展示给用户的已显示数据，绝不绕过认证或访问控制。相当于代用户复制粘贴 —— 自动化仅节省手动操作的工作量。

所有数据均在本地存储：流量检查、HAR 录制及提取结果均存储在用户本机 —— 不向目标站点之外传输任何数据。

## 语言

面向用户的所有流程输出（计划确认、进度更新、流程通知）均遵循用户的语言。生成的 Skill 文件内容遵循本 Skill 的语言。

```
阶段 0（工具检测）→ 阶段 1（需求分析与确认）→ [循环：阶段 2（能力探索）→ 阶段 3（技能生成）] → 交付
```

## 阶段 0 — 工具检测

当前会话中已完成 → 跳过。

通过 Skill 工具调用 `browser-act` 加载使用说明。若加载过程中出现安装或配置问题，按其指引解决后重试。

成功加载后，确认 API Key 已配置（若未配置 → 引导用户完成注册与配置，然后重试）。

## 阶段 1 — 需求分析与确认

### 1a. 解析业务意图

从用户输入中识别：

- **核心目标**：需要获取的数据 / 需要完成的动作
- **目标站点**：是否给出了具体 URL 或平台名称
- **执行意图**：用户是否希望立即执行（而非仅为构建 Skill 供后续使用）。包含批量/规模要求（N 条记录、多个关键词）或隐含"立即执行"的单次请求
- **输出目录**：默认为当前工作目录下的 `output/`，若用户指定则覆盖

| 输入类型 | 示例 | 处理方式 |
|-----------|---------|----------|
| 明确（URL + 目标） | "Scrape front page articles from news.ycombinator.com" | 跳过 1b，直接进入 1c |
| 半明确（已知平台，无 URL） | "Help me monitor Weibo sentiment" | 执行 1b 调研路径 |
| 纯目标（仅业务意图） | "Track competitor price changes" | 执行 1b 调研候选站点 |

若核心目标过于模糊无法继续，需向用户询问以澄清。

### 1b. 目标站点调研（无明确 URL 时）

不基于模型内部知识推荐 —— 主动搜索以查找承载所需数据的站点：

1. 基于业务意图构建搜索查询，从结果中识别候选站点
2. 向用户推荐 1–5 个候选站点，按数据价值排序，并说明优缺点（含数据可靠性）
3. 用户选择后，确认目标 URL

### 1c. 任务分解与执行计划确认

确认目标站点后，首先检查：该站点/能力是否已有已安装的 Skill？若有 → 告知用户并跳过至交付步骤 4（批量执行）。

若无已有 Skill，则完成分解，并**一次性向用户确认全部信息** —— 不再针对各能力进行后续追问：

1. 识别涉及的自独立阶段（搜索、列表页、详情页、登录、提交等）
2. 确定类型：**提取**（获取数据）vs **操作**（执行动作）
3. 拆分标准：**若更换业务目标，该阶段能否独立复用？是 = 独立能力。** 服务于同一业务目标、跨页面的步骤（如列表页采集 + 详情页提取）合并为一个能力，通过复合组件编排
4. 设定 `skill-name` 与能力目录名（小写英文、连字符分隔），在 `output/{skill-name}/` 下创建目录（用户指定路径则使用）
5. 与用户确认完整执行计划：

```
目标站点：{url}
输出：output/{skill-name}/

能力（按顺序执行）：
1. {site-slug}-{capability-slug}（{extraction/operation}）— {一句话描述}
2. {site-slug}-{capability-slug}（{extraction/operation}）— {一句话描述}
...
```

若在 1a 中识别到执行意图，在计划末尾追加：

```
流水线：
1. 探索站点 → 发现并验证可行的 API 端点或 DOM 提取方式
2. 生成 Skill 文件（SKILL.md + 脚本）
3. 自动化测试确认 Skill 可用
4. 安装 Skill
5. 读取已安装 Skill → 编写并运行批量脚本以完成用户原始任务
```

展示计划后，等待用户确认或调整。对于有合理默认值的项目（如输出目录、命名规范等）不单独提问。

用户确认后，进入执行循环，过程中不再提问。

> **阶段 2 与阶段 3 在每一个能力单元下循环执行 —— 完成一个再开始下一个。**

## 阶段 2 — 能力探索

根据能力类型读取对应的参考文件：
- **提取** → `references/exploration_extraction.md`
- **操作** → `references/exploration_operation.md`

**目标**：优先为能力探索目标 API 端点；API 不可行时回退至 DOM 操作。记录完整可复现的调用方式。

**成功标准**：
- 能稳定获取目标数据 / 触发目标动作（API 或 DOM 路径）
- 完整记录调用/操作方式（端点 + 参数，或选择器 + 交互步骤）
- 枚举全部有意义的参数取值

**当某方式失败时，按以下顺序处理：**
1. 不以不同参数重试（调整参数通常不会改变结果）
2. 回到目标本身
3. 枚举所有可实现目标的替代方式
4. 选择下一个并执行

确定性失败（明确错误码、结构不匹配）表明该方式一次尝试即不可行。瞬时失败（超时、连接中断）需重试一次 —— 但仅此一次。

**探索上限**：100 次工具调用步骤。若仍无法推进，向用户报告已知障碍并询问下一步。

**不查看经验笔记**：经验笔记（`browser-act-skill-forge-memories/`）为生成的 Skill 未来 Agent 使用而设 —— 探索与生成阶段既不读取也不写入。

## 阶段 3 — 技能生成

阅读 `references/output_template.md` 获取文件格式规范。

### 3a. JS 封装

将探索中验证的每个 JS 片段封装为独立的 Python 文件：

1. 识别业务参数（关键词、页码、排序方式等）→ 提取为 argparse 参数
2. 将选择器、字段映射、端点 URL 作为固定值硬编码于 JS f-string 中
3. 将 JS 花括号转义为 `{{` `}}`（f-string 语法要求，否则 Python 报错）
4. 写入 `scripts/{feature-name}.py`

### 3b. 封装验证

对每个 `.py` 文件执行端到端验证：

1. `python scripts/{feature-name}.py {test-params}` — 确认输出为有效的 JS 字符串
2. `eval "$(python scripts/{feature-name}.py {test-params})"` — 确认浏览器执行结果与探索阶段一致
3. 模拟错误场景（如不存在的 ID、访问错误页面），确认返回 `{"error": true, "message": "..."}` 而非崩溃

验证失败 → 修复 `.py` 文件后重试，不可跳过。

### 3c. 生成 SKILL.md

按模板生成 SKILL.md，能力组件章节引用 `scripts/*.py` 的调用命令（不使用内联 JS）。

输出目录结构：

```
output/{skill-name}/{site-slug}-{capability-slug}/
├── SKILL.md
└── scripts/
    └── {feature-name}.py
```

生成后简要告知用户：能力名称、输出路径、主要实现方式（API / 网络捕获 / DOM / 混合）。

### 3d. 合规自查

两项检查 —— 必须读取生成的文件并执行验证命令作为证据；仅靠心理判断不算数：

1. **流程**：重新阅读阶段 2 中使用的探索参考文件及上述 3a–3c 输出步骤，确认每一步均已实际执行，而非跳过
2. **输出**：读取生成的 `scripts/*.py` 与 `SKILL.md`，对照 `output_template.md` 中的填写规范及本 Skill 前期定义的代码 / JS 执行环境 / DOM 操作约束

发现任何缺口 → 返回补齐缺失步骤或修复输出，然后重新验证。

## 交付流程

所有能力生成完成后，按以下顺序执行：

### 1. 自动化测试

生成后立即开始测试 —— 无需用户确认。基于生成的能力组件自动设计最小测试用例 —— 以最少输入覆盖所有功能路径（每个原子组件至少调用一次，复合组件运行完整流程）。

必须通过 Sub-Agent 执行测试 —— 不在主会话中直接测试。下发如下提示词：

```
以 `{SKILL.md 的绝对路径}` 作为你的执行指南。

测试用例：
{根据生成的能力组件自动生成的测试用例列表，每个标注其覆盖的组件}

执行要求：
- 严格遵循 SKILL.md 中的指令，不使用指南之外的方法
- 若 SKILL.md 指令存在阻碍推进的不明确之处，记录具体问题

执行后报告：
1. 各组件执行结果（通过/失败）
2. 失败原因（如有）
3. SKILL.md 指令中不明确的部分（如有）
4. 严重的准确性或性能问题（不报告非严重问题）
5. 输出数据摘要
```

测试失败 → 修复 Skill 后重新测试，直至通过。

### 2. 安装 Skill

从输出目录安装生成的 Skill。若安装失败，Skill 仍保留在输出目录中，可在步骤 4 中直接使用。

### 3. 报告结果

测试通过后，向用户报告：

- 生成的 Skill 列表（名称 + 路径 + 包含文件）
- 数据覆盖（字段 + 状态，不列出数据来源或实现方式）
- 未完整覆盖的缺口（未枚举的参数、缺失的目标字段、未覆盖的筛选条件等）
- 测试结果摘要

### 4. 执行（若阶段 1 中识别到执行意图）

若在阶段 1 中识别到执行意图：

1. 通过 Skill 工具调用已安装的 Skill，读取其完整内容。若步骤 2 安装失败，则从输出目录读取 SKILL.md 代替
2. 按照 Skill 指令，在当前会话中执行用户原始任务
3. 对于批量/规模任务，根据 Skill 指引编写批量执行脚本

若未识别到执行意图（用户仅为构建 Skill 供后续使用），在此结束。

## 工具约束

阶段 2（能力探索）、阶段 3（技能生成）与交付测试必须遵循以下规则。

### 文件管理

所有中间产物（HAR 文件、临时记录、调试输出）存放于 `tmp/` 目录。如不存在则先创建。

### browser-act
- 网络数据与页面绑定 —— 导航至新页面后必须重新等待并重新读取
- **在读取流量前等待网络稳定**：无论由页面导航还是 UI 交互触发，读取 `network requests` 前须使用 `wait stable`
- **操作异步 DOM 元素前等待元素加载**：针对异步注入内容（浏览器扩展、懒加载组件），使用 `wait --selector "{target selector}" --state attached --timeout {ms}` 等待后再进行交互
- **不进行 JS 层面的网络拦截**：永不覆盖 `XMLHttpRequest.prototype`、`window.fetch` 等。通过 `network requests` / `network request <id>` 发现端点
- `network clear` 仅用于导航/刷新之前：清除流量会丢失所有已观察的请求记录。常规过滤使用 `--filter`，而非 clear。追踪特定交互产生的请求，使用 `network har start` → 交互 → `network har stop`，而非 clear + 重新读取

### DOM 操作约束

适用于所有 DOM 操作场景（数据提取、枚举采集、分页控件、表单提交、API 字段补全）：

**选择器优先级**：`data-testid > id > name > aria-label > 结构路径`。除非结构确属稳定，否则避免使用纯位置索引（`:nth-child` / `[1]`）。

**批量校验选择器**：在单个 eval 调用中测试所有候选选择器，返回 JSON 摘要（各选择器命中数、首元素关键属性、唯一性）。切勿逐一 eval 选择器 —— 每次 eval 都是一次浏览器往返。

**Shadow DOM**：当目标元素位于 Shadow Root 内时，通过 `element.shadowRoot.querySelector` 访问，将选择器拆分为两部分（宿主元素 + Shadow 内部路径）。

**三层选择器校验**：元素断言（预期属性匹配）→ 结果检查（非空、数量合理）→ 成功标准。必须在真实页面测试，切勿凭 DOM 结构推测编写。

**控件扫描**（枚举采集时）：使用一次 eval 返回全部目标控件的完整映射（标签+类型 / name+id / placeholder / label）。自控件向上追溯至最近的表单项容器以获取标签文本；不硬编码组件库类名；组件库通过 DOM 层级嵌套将标签与输入关联，而非使用 `label[for="xxx"]`。

**state 索引动态分配**：`state` 返回每会话动态分配的元素索引 —— 不可写入策略代码，仅在执行时实时使用。

### 代码约束

**必须直接操作目标站点**：绝不通过外部服务获取数据（含第三方爬虫平台、数据聚合 API、代理服务），也绝不调用目标站点的官方开放平台 API（理由：生成的 Skill 面向零配置部署，无需用户注册开发者 API Key 或管理凭据）。方案必须通过浏览器直接访问目标站点，使用其前端内部端点或 DOM 数据 —— 即已认证用户可见的资源。

**框架内部状态快速失败**：尝试通过框架内部（`__vue_app__`、`$data`、React fiber、Angular `ng` 等）访问页面数据或元素信息时，**一旦失败即放弃**，立即切换至 `state` 扫描 + 值填充触发方式。框架内部与版本/实现相关，多次重试不会改变结果。

### JS 执行环境约束

eval 中执行的代码为 **浏览器侧 JS**：仅可使用浏览器原生 API 与页面已加载的第三方库，不允许 require/import 外部模块。违反此约束的代码必然在执行时报错。

### 结论标准

账户权限限制 ≠ 技术方案失败。付费功能、会员等级等同样影响所有方案；当 API 在技术层面可行但数据受账户权限限制（分页截断、筛选条件无效）时，结论为"通过"，并将权限依赖标注于"已知限制"中。

**部分成功即视为成功**：核心能力验证可用（无论 API 或 DOM 路径）即视为通过 —— 即使存在：部分枚举参数标记为 `[采集失败]`、非核心字段缺失、部分筛选条件未覆盖。生成 Skill 后，**必须告知用户哪些部分未完全覆盖** —— 不可静默省略。

### 效率规则

核心准则：**每一次浏览器往返都必须带来信息增益。** 下表列示常见高效模式，仅为示例 —— 若该模式在实际中并未减少往返次数，则改变方案并寻找其他批量方法，而非在同一方向上反复微调。

| 规则 | 说明 |
|------|-------------|
| **复合 eval** | 将多个独立查询合并为一次 eval，包裹于 async IIFE，返回 JSON 摘要。每次 eval 均为一次浏览器往返 —— 能合并则全部合并 |
| **运行时优先** | 信息获取优先级：JS 运行时状态 → 网络数据 → DOM。切勿从 DOM 反推运行时数据 |
| **输出量控制** | 在浏览器中从大响应中提取关键字段（数量、总数、样本），返回前避免截断 |
| **异步等待协同** | 使用 Promise + setTimeout 轮询（设超时上限）等待条件，不要跨工具反复轮询 |
| **受限权限快速检测** | 当出现受限信号（升级提示、数据与未过滤时一致、控件禁用）时，批量将同类项标记为受限，而非逐一验证 |
| **一次获取，多次分析** | 仅从同一来源获取数据一次，保存后多次分析；格式化大文本时添加换行，避免截断 |
| **止于验证** | API 端点确认可用（fetch 成功 + 数据结构符合预期）后，立即进入下一阶段，不再继续对同一端点做冗余探索（如反查脚本标签、提取额外配置） |
| **滑块/范围控件批量处理** | 范围滑块（如 noUiSlider）与数值范围控件 —— 如同输入/select 控件，一次性将全部控件设为不同值 → 触发一次查询 → 从请求中读取全部 numericFilters 映射，而非逐个控件测试 |
