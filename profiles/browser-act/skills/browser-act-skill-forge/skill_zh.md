# browser-act-skill-forge

由 [BrowserAct](https://www.browseract.com) 构建 — 您的专属数据抓取工程师 · [GitHub](https://github.com/browser-act/skills/tree/main/browser-act-skill-forge)

将任何网站的数据提取或操作需求转化为可被 Agent 调用的功能。用户描述需要获取哪些数据或要在哪个网站执行什么操作，该技能会自动探索实现路径（优先检查 API 端点，若无 API 则回退至 DOM 操作），验证后生成可部署的技能包（SKILL.md + Python 脚本）。探索一次，重复使用 — 后续调用将跳过探索成本，极大提升执行可靠性和效率。

对于大批量提取任务（数百或数千条记录、多个关键词、跨分页），正确的方法是：先探索构建一个经过验证的技能，然后大规模执行。没有经过验证的策略直接进行批量抓取是脆弱的 — 反爬虫检测、分页边缘情况、会话中断等问题使其不可靠。

此工具的操作边界 = 用户在浏览器中可以手动完成的工作。它通过用户登录的浏览器访问，仅读取用户在页面上已显示的数据，绝不绕过认证或访问控制。相当于代用户复制粘贴 — 自动化只是节省手动工作。

所有数据均保存在本地：流量检查、HAR 录制、提取结果存储在用户机器上 — 不会发送超出目标网站本身的信息。

## 语言

## 阶段 1 — 需求分析及确认

### 1a. 解析业务意图

从用户输入中识别：

- **核心目标**：要获取哪些数据 / 要完成什么操作
- **目标网站**：是否给出特定 URL 或平台名称
- **执行意图**：用户是否希望立即执行（而不仅仅是构建一个稍后使用的技能）。包括批量/数量要求（N 条记录、多个关键词）或暗示“立即执行”的单次请求
- **输出目录**：默认为当前工作目录下的 `output/`，如果用户指定则会被覆盖

| 输入类型 | 示例 | 处理方式 |
|---------|------|----------|
| 显式（URL + 目标） | "从 news.ycombinator.com 抓取首页文章" | 跳过 1b，进入 1c |
| 半显式（平台已知，无 URL） | "帮助我监控微博情绪" | 运行 1b 研究路径 |
| 纯目标（仅业务意图） | "跟踪竞争对手价格变化" | 运行 1b 研究候选网站 |

如果核心目标过于模糊无法继续，请要求用户澄清。

### 1b. 目标网站研究（当无显式 URL 时）

不要基于模型内部知识推荐 — 主动搜索以找到托管所需数据的网站：

1. 从业务意图构建搜索查询，从结果中识别候选网站
2. 向用户推荐 1-5 个候选网站，按数据价值排序，包括优缺点（包括数据可靠性）
3. 用户选择后，确认目标 URL

### 1c. 任务分解及执行计划确认

确认目标网站后，首先检查：是否已为该网站/功能安装了技能？如果已安装 → 告知用户并跳至交付步骤 4（批量执行）。

如果没有现有技能，完成分解并**一次性确认所有信息** — 之后不再针对每个功能进行后续提问：

1. 识别涉及的独立阶段（搜索、列表页、详情页、登录、提交…）
2. 确定类型：**提取**（获取数据）或 **操作**（执行操作）
3. 分割标准：**如果交换业务目标，此阶段能否独立复用？能 = 独立能力。** 为同一业务目标服务的跨页面步骤（例如，列表页收集 + 详情页提取）保持为一个能力，通过复合组件进行编排
4. 设置 `skill-name` 和能力目录名称（小写英文，连字符分隔），在 `output/{skill-name}/` 下创建目录（如果给定则使用用户指定路径）
5. 与用户确认完整的执行计划：

```
目标网站：{url}
输出：output/{skill-name}/

能力（按顺序执行）：
1. {site-slug}-{capability-slug} ({提取/操作}) — {一句话描述}
2. {site-slug}-{capability-slug} ({提取/操作}) — {一句话描述}
...
```

如果执行意图在 1a 中被识别，则追加到计划中：
```
流程：
1. 探索网站 → 发现并验证可行的 API 端点或 DOM 提取方法
2. 生成技能文件（SKILL.md + 脚本）
3. 自动化测试以确认技能可用
4. 安装技能
5. 读取已安装的技能 → 根据技能指导编写并运行批量脚本以完成用户的原始任务
```

展示计划并等待用户确认或调整。不要针对具有合理默认值的项目（输出目录、命名约定等）进行单独提问。

用户确认后，进入执行循环，过程中不再提问。

## 阶段 2 — 能力探索

根据能力类型读取相应的参考文件：
- **提取** → `references/exploration_extraction.md`
- **操作** → `references/exploration_operation.md`

**目标**：优先为目标能力排序 API 端点；当 API 不可行时回退至 DOM 操作。记录完整的可复现调用方法。

**成功标准**：
- 可以稳定获取目标数据 / 触发目标操作（API 或 DOM 路径）
- 记录完整的调用/操作方法（端点 + 参数，或选择器 + 交互步骤）
- 收集所有有意义值的枚举参数

当一种方法失败时，请按以下顺序操作：
1. 不要用不同参数重试（参数变化很少改变结果）
2. 回到目标本身
3. 枚举所有可能实现目标的替代方法
4. 选择下一个并执行

确定性失败（明确错误代码、结构不匹配）确认该方法在一次尝试中不可行。暂时性失败（超时、连接中断）值得重试一次 — 但不能更多。

**探索上限**：100 次工具调用步骤。如果仍然无法进展，向用户报告已知障碍并询问下一步。

**不要触碰经验笔记**：经验笔记 (`browser-act-skill-forge-memories/`) 用于生成技能的未来 Agent 使用 — 在探索和生成阶段既不读取也不写入。

## 阶段 3 — 技能生成

读取 `references/output_template.md` 获取文件格式规范。

### 3a. JS 封装

将探索中每个验证过的 JS 片段封装到独立的 Python 文件中：

1. 识别业务参数（关键词、页码、排序顺序等）→ 提取为 argparse 参数
2. 将选择器、字段映射、端点 URL 作为固定值硬编码在 JS f-string 中
3. 转义 JS 大括号为 `{{` `}}`（f-string 语法要求，否则 Python 报错）
4. 写入到 `scripts/{feature-name}.py`

### 3b. 封装验证

对每个 `.py` 文件进行端到端验证：

1. `python scripts/{feature-name}.py {test-params}` — 确认输出是有效的 JS 字符串
2. `eval "$(python scripts/{feature-name}.py {test-params})"` — 确认浏览器执行结果与探索阶段一致
3. 模拟错误场景（例如，不存在的 ID、导航到错误页面），确认返回 `{"error": true, "message": "..."}` 而不是崩溃

验证失败 → 修复 `.py` 文件并重试，永不跳过。

### 3c. 生成 SKILL.md

根据模板创建 SKILL.md，能力组件部分引用 `scripts/*.py` 调用命令（无内联 JS）。

输出目录结构：

```
output/{skill-name}/{site-slug}-{capability-slug}/
├── SKILL.md
└── scripts/
    └── {feature-name}.py
```

生成后，简要告知用户：能力名称、输出路径、主要实现方式（API / 网络捕获 / DOM / 混合）。

### 3d. 合规性自检

两个检查 — 必须读取生成文件并执行验证命令作为证据；仅凭主观断言无效：

1. **流程**：重读阶段 2 中使用的探索参考文件和上述输出步骤（3a–3c），确认每个定义的步骤都实际执行了，没有跳过
2. **输出**：读取生成的 `scripts/*.py` 和 `SKILL.md`，对照 `output_template.md` 中的填充规范以及本技能前面定义的代码 / JS 执行环境 / DOM 操作约束

发现任何缺失 → 回退，完成缺失步骤或修复输出，然后重新验证。

## 交付流程

所有能力生成后，按以下顺序进行：

### 1. 自动化测试

生成后立即开始测试 — 无需用户确认。根据生成的能力组件自动设计最小测试用例 — 使用最少的输入覆盖所有功能路径（每个原子组件至少调用一次，复合组件运行完整流程）。

必须通过 Sub-Agent 执行测试 — 不要在主会话中直接测试。发送以下提示：

```
读取 {绝对路径到 SKILL.md} 作为你的执行指南。

测试用例：
{自动生成的测试用例列表，每个用例标注它覆盖哪个组件}

执行要求：
- 严格遵循 SKILL.md 指令，不要使用指南外的方法
- 如果 SKILL.md 指令不明确导致无法进行，记录具体问题

执行后报告：
1. 每个组件的执行结果（通过/失败）
2. 失败原因（如有）
3. SKILL.md 指令中不明确的部分（如有）
4. 严重准确度或性能问题（不要报告非严重问题）
5. 输出数据摘要
```

测试失败 → 修复技能并重测直至通过。

### 2. 安装技能

从输出目录安装生成的技能。如果安装失败，技能仍保留在输出目录中，并且可以直接在步骤 4 中使用。

### 3. 报告结果

测试通过后，向用户报告：

- 生成的技能列表（名称 + 路径 + 包含的文件）
- 数据覆盖率（字段 + 状态，不要列出数据源或实现方法）
- 不完整覆盖率差距（失败的枚举参数、缺失的目标字段、未覆盖的过滤条件等）
- 测试结果摘要

### 4. 执行（如果阶段 1 中识别了执行意图）

如果阶段 1 中识别了执行意图：

1. 通过技能工具调用已安装的技能以读取其全部内容。如果在步骤 2 中安装失败，则直接从输出目录读取 SKILL.md
2. 按照技能的指导在当前会话中执行用户的原始任务
3. 对于批量/数量任务，根据技能的指导编写批量执行脚本

如果未识别执行意图（用户只是想稍后构建一个技能使用），则到此结束。

## 工具约束

阶段 2（能力探索）、阶段 3（技能生成）和交付测试必须遵循以下规则。

### 文件管理

所有中间产物（HAR 文件、临时记录、调试输出）存放在 `tmp/` 目录。如果不存在则先创建它。

### browser-act
- 网络数据是页面范围的 — 导航到新页面后必须重新等待和读取
- **在读取流量前等待网络稳定性**：无论是页面导航还是 UI 交互触发，使用 `wait stable` 之后再读取 `network requests`
- **在操作异步 DOM 前等待元素**：对于异步注入的内容（浏览器扩展、懒加载组件），使用 `wait --selector "{目标选择器}" --state attached --timeout {ms}` 之后再交互
- **无 JS 级别的网络拦截**：绝不覆盖 `XMLHttpRequest.prototype`、`window.fetch` 等。使用 `network requests` / `network request <id>` 进行端点发现
- **`network clear` 仅在导航/重载前使用**：清除流量会丢失所有观察到的请求记录。使用 `--filter` 进行常规过滤，不要清除。要跟踪特定交互的请求，使用 `network har start` → 交互 → `network har stop` 而不是清除 + 重新读取

### DOM 操作约束

适用于所有 DOM 操作场景（数据提取、枚举收集、分页控制、表单提交、API 字段补充）：

**选择器优先级**：`data-testid > id > name > aria-label > 结构路径`。避免纯位置索引（`:nth-child` / `[1]`），除非结构确实稳定。

**批量验证选择器**：在单个 eval 调用中测试所有候选选择器，返回 JSON 摘要（每个选择器的命中次数、键属性第一个元素、唯一性）。永不逐个 eval 选择器 — 每个 eval 是一次浏览器往返。

**Shadow DOM**：当目标元素在 Shadow Root 内，通过 `element.shadowRoot.querySelector` 访问，将选择器拆分为两部分（宿主元素 + Shadow 内部路径）。

**三层选择器验证**：元素断言（预期属性匹配）→ 结果检查（非空、合理数量）→ 成功标准。必须在真实页面上测试，绝不能从 DOM 结构推测性地编写。

**控制扫描**（在枚举收集期间）：使用一个 eval 返回所有目标控制的完整映射（tag+type / name+id / placeholder / label）。从控制向上遍历找到最近的表单项容器以获取标签文本；不要硬编码组件库类名；组件库通过 DOM 层次嵌套将标签与输入关联，而不是 `label[for="xxx"]`。

**state index 动态分配**：`state` 返回会话动态分配的元素索引 — 不要将其写入策略代码，仅在执行时间实时使用。

### 代码约束

**必须直接操作目标网站**：绝不通过外部服务（包括第三方抓取平台、数据聚合 API、代理服务）获取数据，也绝不调用目标网站官方开放平台 API（理由：生成的技能目标零配置部署，无需用户注册开发者 API 密钥或管理凭证）。解决方案必须通过浏览器直接访问目标网站，使用其前端内部端点或 DOM 数据 — 这些是已认证用户可见的资源。

**框架内部状态快速失败**：当尝试通过框架内部（`__vue_app__`、`$data`、React fiber、Angular `ng` 等）访问页面数据或元素信息时，**失败一次后立即放弃**并立即切换到 `state` 扫描 + 值填充触发方法。框架内部依赖于版本/实现，多次重试不会改变结果。

### JS 执行环境约束

在 eval 中执行的代码是**浏览器端 JS**：仅使用浏览器原生 API 和页面加载的第三方库，不能 require/import 外部模块。违反此约束的代码在执行时必然出错。

### 结论标准

账户权限限制 ≠ 技术解决方案失败。付费功能、会员等级等对所有方法的影响相同；当技术可行但数据因账户权限受限（分页截断、过滤条件无效）时，结论为“通过”，并在“已知限制”中注明权限依赖。

**部分成功算作成功**：核心能力验证工作（无论 API 或 DOM 路径）算作通过 — 即使有：部分枚举参数标记 `[collection failed]`、非核心字段缺失、部分过滤条件未覆盖。生成技能后，**必须告知用户哪些部分未完全覆盖** — 绝不沉默忽略。

### 效率规则

核心标准：**每个浏览器往返必须产生信息增益。** 下方表格展示了常见高效模式，但它们只是示例 — 如果某个模式在实际中不能减少往返次数，改变方法并寻找其他批量方法，而不是在同一方向上反复微调。

| 规则 | 描述 |
|------|------|
| **复合 eval** | 将多个独立查询合并到一个 eval 中，用 async IIFE 包裹，返回 JSON 摘要。每个 eval 是一次浏览器往返 — 合并所有可合并的内容 |
| **运行时优先** | 信息检索优先级：JS 运行时状态 → 网络数据 → DOM。绝不从 DOM 反向工程运行时数据 |
| **输出量控制** | 从大型响应中在浏览器内提取关键字段（计数、总数、样本）再返回；避免截断 |
| **异步等待凝聚力** | 使用 Promise + setTimeout 轮询（带超时限制）进行等待条件，不要跨工具重复轮询 |
| **快速权限限制检测** | 当出现限制信号（升级提示、数据与未过滤相同、控件禁用）时，批量标记相似项为受限，不要逐个验证 |
| **一次获取多次分析** | 从同一来源只获取数据一次，保存后多次分析；将大文本格式化为带换行符以避免截断 |
| **验证即停止** | 一旦 API 端点确认工作（获取成功 + 数据结构符合预期），立即进入下一阶段，不要继续对同一端点进行冗余探索（例如，反向搜索脚本标签、提取额外配置） |
| **滑块/范围控件批量** | 范围滑块（例如，noUiSlider）和数字范围控件 — 像输入/选择一样，一次设置所有控件为不同值 → 触发一次搜索 → 从请求中读取所有数字过滤器映射，不要逐个测试控件 |
