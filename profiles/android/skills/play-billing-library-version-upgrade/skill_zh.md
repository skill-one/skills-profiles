## 第 0 阶段：意图信息

**报告操作**：在进行下一步之前，立即告知用户："我将升级 Play Billing Library 到最新版本。"

## 第 1 阶段：发现与情境感知

1. **主要检查（构建版本）**：在 `build.gradle`、`build.gradle.kts` 或 `libs.versions.toml` 中定位项目的计费依赖项（例如，`com.android.billingclient:billing`）。
2. **初始编译测试**：立即尝试同步和构建项目。
3. **后备发现（有效版本）**：
   - **触发条件**：仅在构建立即失败时，扫描源代码以查找已弃用的组件。
   - **逻辑**：已弃用 API 的存在表明**"有效版本"**——定义为这些特定 API 最后可用时的版本，而不是它们被引入时的版本。
   - **示例**：如果存在 `SkuDetails`，则将基线视为 **PBL v7** 或更早版本（无论 `build.gradle` 中的版本字符串如何）。
4. **确定目标与路径**：访问版本工具或发布说明以查找最新稳定版本，并根据**有效版本**基线计算 **[直接/分步]** 迁移路径。

- **计算迁移路径**：
  - 如果**有效版本**与目标版本相差不超过 2 个主版本：计划**直接迁移**。
  - 如果它落后于目标版本超过 2 个主版本：计划**分步迁移**。每次以两个主版本为单位进行迁移（例如，v4 → v6 → v8），直到你达到目标版本的前两个版本内。
- **报告操作**：在进行下一步之前，告知用户："我检测到你实际上使用的是 PBL \[当前版本\]，最新版本是 \[目标版本\]。我正在计划一个 **[直接/分步]** 迁移路径。"

## 第 2 阶段：上下文文档映射与规划

对于路径中识别出的每个主版本跳跃，你必须综合以下来源的说明：

- **[迁移指南](https://developer.android.com/google/play/billing/migrate-gpblv%5BX%5D)**（其中 `[X]` 是目标主版本）。
- **发布亮点**：相关 [发布说明](references/android/google/play/billing/release-notes.md) 的"弃用"和"破坏性变更"部分。
- **开发者文档**：参考你关于 Google Play 计费文档的知识，了解本应用中使用的相关功能（例如，订阅、一次性产品）。
- **制定计划**：识别出每个具体的代码更改需求（API 移除、类替换、逻辑变更），并将其打印为清单。
