# 拉取变更并解决合并冲突

在将另一个分支（通常是 `main`）集成到当前功能分支时，或者在执行合并或变基操作后 `git status` 显示未合并路径时，使用此技巧。适用于任何基于 Git 的团队工作流程；Flows/React 应用程序是冲突常见出现在应用程序外壳和共享库中的常见案例。

## 目标

- 保留当前分支上的有意工作；**不要假设**“main 赢”或“我们赢”而未经分析。
- 在任何冲突解决编辑之前，将权衡取舍**对用户可见**。
- 按**影响**排序讨论：结构/功能/API/数据模型变更优先于样式、文本或间距。

## 硬性规则

1. **禁止静默解决** — 在用户同意计划（或明确表示“使用您的建议”）之前，不要删除 `<<<<<<<` / `=======` / `>>>>>>>` 或对冲突文件运行 `git add`。
2. **在冲突处停止** — 如果合并或变基引入冲突，**暂停**并报告；不要通过全盘选择一边来强行通过大文件，除非用户明确要求这样做。
3. **优先考虑影响** — 在呈现冲突时，大致按以下方式分组和排序：
   - **P0 — 结构/产品：** 删除路由、删除模块、移除功能、更改数据或 API 合约、SDK 或模式变更、认证或路由外壳。
   - **P1 — 行为：** 逻辑、钩子、查询、过滤器、错误处理、加载状态。
   - **P2 — UI 结构：** 布局区域、新增或删除的部分、导航。
   - **P3 — 表现：** 标记、间距、类名、文本微调。

## 工作流程

### 1. 获取并集成（或诊断）

- 除非用户要求变基，否则优先使用 `git fetch` 然后执行 `git merge origin/main`（或命名分支）。
- 如果合并已经在进行中，运行 `git status` 并列出**所有**未合并的文件。

### 2. 向用户报告冲突（明确）

输出清晰的列表：

- **分支状态：** 当前分支、目标分支（例如 `origin/main`）、合并与变基。
- **未合并文件：** 仅路径，然后可选地 `git diff --name-only --diff-filter=U`。
- **每个文件（简短）：** 一行说明*什么*发生了分歧（例如“`AlertsPage` — 布局 + 新数据范围”），如果从路径和 `git diff` 推断**未解决**。

### 3. 编辑前分析

使用**所有**：

- **对话历史** — 用户或团队在此分支上试图发布什么？
- **仓库信号** — 如果存在产品或架构文档（例如 `PRD.md`）、当前分支上的最近提交、文件所有权（例如大功能模块与共享 `lib/`）。
- **冲突块** — 合并期间 `git show :2:path`（我们）与 `git show :3:path`（他们），或读取冲突标记；识别重复与正交变更。

将每个冲突区域分类为：

- **正交** — 安全合并（例如导入排序 + 新属性）。
- **重叠** — 必须选择或手动合并（相同行）。
- **损坏风险** — 重复块（在不良合并后常见）；标记并建议从一边重建然后手动应用另一边的意图。

### 4. 建议 + 问题（必需）

向用户呈现：

1. **摘要表格或要点** — 文件 → 推荐的一边*或*“手动合并”→ 一行**原因**。
2. **按 P0 → P3 排序** — 首先指出任何**移除**功能或**更改**公共行为的。
3. **明确问题** — 任何模糊不清的地方（例如“保留 main 的全局行为还是分支的局部变体？”）。
4. **请求指导** — 例如“回复：(a) 跟随建议，(b) 保留分支以文件 X，(c) 保留 main 以文件 Y，(d) 中止合并。”

**只有在**用户确认（或给出精确映射）后，才应用解决方案：

- 优先进行小手术编辑；尽可能保留两边的意图。
- 重新运行 `git status`；确保没有冲突标记剩余；运行测试或对用户关心的修改区域进行代码检查。

### 5. 如果用户想中止

- 适当使用 `git merge --abort` 或 `git rebase --abort`；确认他们失去该操作的进行中集成状态。

## 反模式（不要做）

- 在未经用户批准的情况下对整个仓库使用 `--ours` / `--theirs`。
- 因为 main 涉及相同文件而“解决”删除功能分支的工作。
- 在没有简短执行摘要的情况下，将冲突列表隐藏在长代码转储中。
- 优先解决低影响的样式冲突，而 P0 决策是隐含的。

## 快速参考

- **我们 vs 他们（合并）：** 阶段 2 = 当前分支 (`HEAD`)，阶段 3 = 进入 (`MERGE_HEAD`)。如有必要，使用 `git checkout --conflict=merge <file>` 验证。
- **全栈或 Flows 应用程序中的典型高接触路径：** 根应用程序外壳、顶部导航、路由模块，以及共享 `lib/` 或 `hooks/`。

有关可选命令片段和合并消息模板，请参阅 [reference.md](reference.md)。
