## 此技能的作用

`/check`是合并前的关卡。两种模式，分开任务，通常都需要，先验证：

- **`verify`**（运行时证明）：运行真实的应用程序并观察更改的行为。证明它工作并符合规范（满足每个验收标准，构建每个规范表面），绿色测试永远不会揭示这一点。仅对代码进行读取，不创建持久文件，主线程。通常在`/develop`之后。
- **`review`**（新鲜模型代码审查）：在一个**不同的模型**上对差异进行高级阅读（编写代码的模型对其自己的输出进行审查会共享其盲点）。将按严重程度排序的发现写入`docs/reviews/`。仅对代码进行读取。通常在PR之前。

两种模式都不编辑代码。`verify`将失败指向`/debug`或`/develop`；`review`报告需要修复的发现。

## 选择模式（在执行任何操作之前进行路由）

第一步，在阅读任何模式文件或触摸存储库之前。查看`/check`之后的内容：

- **以`verify`（或`run`）开头** → 阅读`modes/verify.md`，完全遵循它。将剩余的参数（功能名称、范围）传递给它。
- **以`review`开头** → 阅读`modes/review.md`，完全遵循它。将方向保持不变传递（例如`/check review with opus`，`/check review uncommitted`）。
- **没有模式词，或模糊**（裸`/check`，或没有模式的特征名称如`/check auth`）→ 不要猜测，不要默认。以纯文本面板显示两个选项，并**停止等待**工程师的选择。

**如何呈现选择（纯文本，适用于每个代理，无交互式模态）：**

打印确切的这个内容，然后停止等待。不要假设`verify`，直到他们回答。根据他们输入的词进行路由（`verify` / `review` / `both`）。

```
你想运行哪种检查？输入一个：
  • verify  运行真实的应用程序并证明更改符合其规范（通常在/develop之后）
  • review  新鲜模型高级阅读差异，按严重程度排序（通常在PR之前）
  • both    先验证，然后审查
```

无交互式选择器或模态：在行内键入的选择在所有AI工具中表现相同。（`argument-hint` frontmatter也将`verify | review`显示在Claude Code自动补全中；其他工具忽略它，这就是为什么此行内面板是可移植的路径。）

如果特征名称没有模式（`/check auth`），在他们选择后将其作为目标携带；仍然询问模式。

不要在单个运行中混合模式。在**两者**中，先做`verify`，然后提供`review`。

## 可移植性（任何操作系统，任何代理）

macOS、Linux或Windows上的任何Agent Skills客户端。`git`是唯一需要的CLI。其他shell片段是POSIX参考，而不是字面的脚本：使用你代理自己的跨平台文件、进程和浏览器工具。每个模式文件都添加自己的可移植性说明。没有子代理支持会回退到行内，并在每个模式中注明。

捆绑文件：`modes/verify.md`，`modes/review.md`，以及`review-agent-prompt.md`和`review-guide.md`用于审查。仅读取你路由到的模式文件；在生成审查者时将审查捆绑文件解析为绝对路径。
