## 输出风格（纯文字，无连字符，无破折号）

## 此技能的作用

将一个想法转换为一个有序的、粗略的、动态的计划，并在产品发布时保持其真实性。回答要构建什么，按什么顺序构建，有多重，哪些需要首先做出决策，而不是如何构建一个东西（那是 `/architect` 和 `/develop` 的工作）。

范围塑造，粗略且小：一个简洁的概览表格（`# · 功能 · 阶段 · 状态`）+ 按阶段分组的功能部分（参见 `scope-template.md`）。每个部分：标题 `### N. 名称`，只有在重要的时候才使用简短标签（`需要决策`、方法覆盖、工作流层覆盖如 `· GA`），1 到 2 行的意图，一个 `Done when:` 行（验收标准种子，即 `WHAT`），复选框步骤。

功能形状生命周期：尚未设计 → 一个框，其入口命令。在规范捕获时，`/architect` 填充已构建好的形状：`设计它（规范）` 被勾选，规范被链接，`构建它：/develop <功能>`，从规范的 `## 构建计划` 中展开 2 到 5 个里程碑子项，然后是 `验证它：/check verify <功能>` 和 `测试它：/test <功能>`。原子构建任务保留在规范的 `## 构建计划` 中，永远不会在这里；每个框都是一个命令或跟踪的里程碑。状态：在表格中和标题旁边；规范和代码指针一旦存在就会显示。

一个命令，推断意图（`/scope [什么]`，永远不会是子命令）：
- **plan**（默认）：没有范围 + 一个产品规模的构想，或者请求下一个切片。完整流程：询问 → 将其分解为粗略的功能部分 → 排序 + 阶段 → 写作。
- **replan**：范围存在 + 没有参数。以一个简短的现状读出开始（git 分支和远程的 ahead/behind，按状态统计的功能数量，以及每个进行中功能的恢复点），以便一个空的 `/scope` 可以作为“我在哪里，什么安全可以捡起”的导向，然后协调已发布的内容，揭示计划与现实之间的偏差（没有范围行的代码或规范），注册在构建期间出现的需求，重新排序，并排队下一个切片。正常的动态节奏，不是罕见的：再次运行空的 `/scope`。
- **add**：范围存在 + 参数名称一个功能。注册一个粗略的行（意图 + 排序 + 层级 + 需要 spec），不再重新规划：`/scope <一个功能>`。

## 询问与执行

高级产品工程师。与 `/architect` 相同的推断/询问/推荐纪律：推断想法陈述的内容（类别、明显的功能）；询问无法推断的内容，分批进行（每轮最多 4 个问题；参见决策面板）；推荐构建方法、构建顺序、工作流层级（项目默认和每个功能的覆盖），哪些需要规范（专家调用：向工程师展示，让工程师覆盖）。

永远不要选择工具：不选择提供者、库、ORM、主机或 BaaS；那是 `/architect` 按功能在规范中的工作。一个暗示工具选择的功能正好是 `Needs spec: yes`。保持范围工具中立，以免它过时。

## 决策面板（每个面向用户的选择）

每个选择都是一个选项面板，而不是一个中性的菜单：2 到 4 个针对此产品的具体选项；正好有一个标记为 `(推荐)`，并附有一行原因（让用户做出决定，让他们覆盖）。永远不要添加你自己的其他选项，选择器会自动追加一个自由文本的其他选项；只在纯文本回退中提供自由文本，不提供选择器。首先考虑功能：使用代理的选择器（`AskUserQuestion` on Claude Code），否则使用与纯文本相同的选项；分批进行同样规则，每轮最多 4 个。

## 资产所有权

`docs/scope/` 是功能范围，由此技能拥有；`/architect` 拥有 `docs/specs/`。其他技能通过扫描 `docs/scope/` 找到其行来查找功能。动态文档：`plan`、`replan`、`add` 都就地编辑（协调和追加，永远不会创建新的带日期的文件）。不写入其他内容：不写规范、代码或 `AGENTS.md`。`docs/scope/` 只保留范围文件；清单、分析、研究文档与规范一起存在于其 `rationale.md` 中（由 `/architect` 拥有）。

文件形状：
- 小产品：一个文件，`docs/scope/scope.md`（概览表格 + 按阶段分组的部分 + 图例）。
- 大产品：史诗分割：`docs/scope/index.md`（跨史诗的概览表格 + 每个史诗的行状态汇总，每个都链接到其史诗文件）+ 每个史诗一个文件，按区域命名（`docs/scope/auth.md`，…）。
- 按需推广：从一个文件开始；当 `scope.md` 超出舒适的扫描范围（大约十几个功能跨明显的不同区域）时，重命名为 `index.md`（保留表格 + 每个史诗的汇总），将每个区域的部分移动到它自己的 `<epic>.md`。永远不会过早分割它。名称语义（`scope.md` / `index.md` / `<epic>.md`），永远不会编号。
- 保持每个文件粗略且小；一个长的史诗文件需要更细的功能和更紧密的意图，而不是构建任务转储。

状态生命周期（`/scope` 设置初始状态；管道推进它）：
- 新功能开始 `planned`。老代码：也将现有的功能作为 `existing`（完成）或 `in-progress`（部分）注册，这是 `/scope` 写入的唯一其他状态。
- `/develop` 推进管道构建工作（`planned` → `in-progress` → `done`）；`/sync` 与差异进行协调。在一个**假设的决策**上构建的功能（其治理规范是 `Assumed`，由 `/develop` 记录，当工程师在决定之前选择构建时）带有 `assumed decision (spec NNNN)` 注释，直到 `/architect` 批准该决策；注释不会阻止 `done`，它是一个决策债务，会一直显示直到被批准。
- `done` ≠ `existing`：`done` = 此管道构建并验证了它；`existing` 日期早于工作流；`/develop` 和 `/sync` 从不触摸 `existing` 行。
- `replan` 可能将范围之外的功能设置为 `dropped`，永远不会删除行；`dropped` 保留历史记录，排除在活动计数和工作之外；`/develop` 和 `/sync` 跳过它。

工作流层级（每个功能一个严格的旋钮，`Prototype` · `Alpha` · `Beta` · `GA`）：功能应得的流程量。ONE 项目默认（推荐一次，计划步骤 5b，记录在范围标题 `**Workflow:**` 行）和每个功能的覆盖（标题旁边的标签，例如 `· GA`，只有在功能与默认不同时；无标签 = 继承）。层级驱动的内容：
- **设计时间**：更高的层级 → 更可能 `Needs spec: yes`，并且规范的跨模型决策评论运行（在 `GA`/`Beta` 时自动运行）。`Prototype`/`Alpha` 功能通常是 `Needs spec: no`。
- **`/develop` 之后**（验证尾随）：`Prototype` = 无（依赖 `/develop` 自身的构建时自我检查）；`Alpha` = `/check verify`；`Beta` = `/check verify` + `/test`；`GA` = 添加一个全新的模型 `/check review` + `/document`。
- **关闭 `done`**（最后一个必需的阶段标记它）：`Prototype` → `/develop`（构建 + 自我检查）；`Alpha` → `/check verify`；`Beta`/`GA` → `/test`。一个 `Assumed` 规范永远不会阻止 `done`；它会一直标记为需要批准（`/architect`）在每个层级。

`/scope` 推荐项目默认值，基于功能组合的风险和大小（步骤 5b），这是 `/architect` 和 `/develop` 读取的相同信号；`/develop` 读取有效层级（功能覆盖，否则项目默认，否则推断）来调整它推荐的下一步，所以一个 `Prototype` 项目不会被指示运行验证，一个 `Alpha` 项目不会被指示运行完整的审查链。

资产基础：默认为 `docs/`；如果 `docs/` 是一个发布的文档站点（`docusaurus.config.*`、`.vitepress/`、`mkdocs.yml`、Astro Starlight 或 Nextra 检测到），使用 `.workflow/`（`.workflow/scope/…`）。始终遵循已存在的哪个基础（这里的路径假设 `docs/`）。

并发性：跨会话和团队成员共享。在写入前立即重新阅读；仅进行手术编辑（按顺序追加行，协调更改的单元格，永远不会重写文件）；标记而不是覆盖意外的状态；追加使用下一个自由编号，以便添加者不会冲突。

## 执行

### 步骤 0：推断意图 & 想法检查

没有子命令。首先检查 `docs/scope/` 下是否存在范围（或如果那是资产基础，则存在 `.workflow/scope/`），然后推断：
- 范围存在 + 没有参数（或再次运行，描述为“协调 / 下一步是什么”）→ replan 行为（`modes/replan.md`）。
- 范围存在 + 参数名称一个功能 → add 行为（`modes/add.md`）。
- 没有范围 + 一个产品规模的构想，或规划下一个切片（包括老代码）→ plan 行为，如下。

模糊（一个新的切片 vs 一个单独的功能）：从范围推断最可能的阅读，在报告中说明你选择的行为；真正不清楚 → 一个简短的澄清问题。

plan 行为，没有想法给出（没有参数，没有范围要扩展）：在执行任何其他操作之前停止并询问：

“你在构建什么？描述你想要计划的产品的切片（关于它做什么和为谁的一两句话）。”

等待答案；将其用作产品想法。

### 步骤 1：加载推断的行为

在步骤 0 推断行为后，读取一个模式文件并遵循它：

- `modes/plan.md` 用于 plan 行为（新范围，产品规模的构想，或下一个切片规划）。
- `modes/replan.md` 用于 replan 行为（范围存在且没有参数）。
- `modes/add.md` 用于 add 行为（范围存在且参数名称一个功能）。

除非推断的行为改变，否则不要读取其他模式文件。所有上述常见规则仍然适用，`scope-template.md` 仍然是任何写入/报告的格式参考。
