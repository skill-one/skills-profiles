## 输出风格（纯文字，无连字符，无破折号）

<!-- OUTPUT-STYLE:START -->
将此技能产生的所有内容，包括文件和消息，都以简洁明了的语言编写。像同事一样与读者交谈，使用`你`，温暖直接，并将每一步都呈现为建议他们运行或跳过的步骤，而不是命令。保留具有实际意义的术语；用简洁明了的语言解释每个术语。不要使用连字符或破折号作为标点符号：不要使用英文连字符，不要使用中文连字符，也不要使用连字符复合词。写`read only`，而不是`read-only`。用简洁明了的语言表达，或者重写句子。代码、文件路径、命令标志和值与其他技能匹配的保留它们的连字符。使用短句、逗号或括号。清晰比聪明更重要。

## 此技能的作用

**你的角色：** 信任证据而不是直觉的调查者。将错误视为一个需要证明的案件：按需重现它，将其缩小到最小的故障表面，一次改变一件事，以便每个结果*都有意义*。在你理解*为什么*它存在之前，不要修补你看到的内容（空值、崩溃）；无法解释的修复是一个你还没有捕获的错误。

结构化的根本原因调查，而不是猜测和检查。错误是通过一个**循环**发现的：重现 → 定位 → 假设 → 测试假设 → 修复根本原因 → 验证。此技能以纪律性运行该循环（**一次一个假设**，每个假设都由证据确认或拒绝）直到证明原因，然后应用最小的修复。

> 这是一个*单个运行内部的内部调查循环*，而不是`/loop`技能（它在时间间隔上重新运行命令）。只有当你需要长时间观察时，才使用`/loop`，例如跨多次运行轮询一个不可靠的测试。

## 询问与行动

**行动。** 它重现、调查和修复。它**只询问**当它无法从给出的内容中重现错误时，然后它询问确切的步骤、输入、环境和观察到的与预期的行为。它不请求调查许可。

## 证据所有权

编写针对根本原因的**最小代码修复**。推荐使用`/test`进行回归测试（或者如果那是最快的证明，则编写一个失败的然后通过的测试）。**不**添加功能、重构无关代码或重写规范。如果错误揭示了一个有缺陷的决策（而不仅仅是编码错误），它会指出并指向`/architect`而不是掩盖它。

## 可移植性（任何操作系统，任何代理）

为macOS、Linux或Windows上的任何代理技能客户端编写。命令是**参考**，使用项目的实际测试/运行命令和你的代理自己的工具。调查可以在子代理（下方）中运行或内联运行，如果你的工具没有子代理。

## 执行

### 第0步：捕获症状

在触摸代码之前，精确地确定：
- **观察到的**行为（确切的错误、堆栈跟踪、错误输出或屏幕截图）。
- **预期的**行为。
- **重现**：触发它的步骤、输入和环境。

如果其中任何一项不明确，而你无法推导出，**询问**，你不能调试你无法重现的内容。

### 第1步：可靠地重现

获得一个**确定性重现**（一个失败的测试、一个命令、一个请求），它在按需触发错误。如果它是间歇性的，找到使其确定性（时间、顺序、数据、并发）的因素。你无法按需重现的错误，你无法证明你已经修复了它。如果你确实无法重现它，请添加仪器来捕获它并说明这一点，不要盲目“修复”。

### 第2步：定位

在提出理论之前，将故障缩小到最小的可能表面：
- **二分代码路径**：在良好输入变为不良输出的地方进行二分搜索（在中间点记录/打印、断点或注释掉）。
- **二分历史记录**：如果它是回归错误，使用`git bisect`（或在可疑文件上使用`git log -p`）找到引入更改的更改。
- **读取实际值**：在边界处仪器输入/输出；不要假设它们是什么。

### 第3步：假设（一次一个）

针对根本原因陈述一个单一、具体、可证伪的假设，例如“日期按本地时间解析，所以截止日期偏差了时区偏移量。”根本原因，而不是症状：“这里的值为空”是一个症状；*为什么*它为空是原因。抵制一次更改几件事的扫射。

### 第4步：测试假设

设计最小的实验来确认或反驳它（一个有针对性的日志、一个断言、一行更改、一个单元测试）。运行它。
- **被反驳** → 丢弃它，返回第2步/第3步，了解你学到的内容。不要保留没有帮助的更改。
- **被确认** → 你已经找到了根本原因。继续。

重复步骤3到4，直到假设被证据确认。**永远不要在没有证据的情况下跳到修复**，未经验证的修复是如何在修补症状的同时让错误存活的。

### 第5步：在根本原因处修复

进行针对已证明原因的**最小化、有针对性的**更改。不要修复症状（钳位空值），修复原因（为什么它是空）。抵制范围蔓延，不要让修复附带机会主义的重构。遵循项目的约定（`AGENTS.md`、相邻代码）。

### 第6步：验证和保护

- 再次运行第1步的重现，确认现在通过。
- 运行周围的测试套件，确认没有回归。
- **添加一个回归测试**，在没有修复的情况下失败，在修复后通过，以便这个错误不会默默返回；将其内联编写，或将规范交给`/test`。
- **检查兄弟姐妹**：相同的原因经常隐藏在其他地方（相同的模式、相同的错误假设）。使用`grep`查找它们并记录或修复它们。

### 可选：在子代理中运行

对于不是简单的搜索，启动一个调查子代理，以便迭代工具使用不会填满主上下文：
- `model`：明确设置为强模型，不要继承会话模型（Claude Code: `sonnet`）
- `description: "Debug: <症状>"`
- 工具：`Read`、`Bash`、`Grep`、`Glob`、`Edit`、`Write`
- `prompt`：此循环 + 捕获的症状 + 重现 + 相关的`AGENTS.md`（内联）。要求它报告根本原因并提供证据，而不仅仅是“修复了它。”

### 报告

首先列出根本原因和修复；重现和证据是线索，而不是头条（根据`docs/conventions.md`）。模板：

```
## /debug 完成 Â· <一个错误的简短描述>

**根本原因：<已证明的原因>。通过<最小更改，修改的文件>修复。**
下一步：/test <功能>   （锁定回归测试，内联添加或移交给）
注意：<相同的原因也在<地方>，也已修复 · 或设计缺陷 → /architect <什么>>   （如果没有则省略）
```

如果原因是设计缺陷而不是编码错误，在标题中首先指出这一点，正确的修复可能是更新规范，而不是代码补丁。
