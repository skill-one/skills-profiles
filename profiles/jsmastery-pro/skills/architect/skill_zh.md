## 输出风格（纯文字，无连字符，无破折号）

<!-- OUTPUT-STYLE:START -->
将此技能产生的所有内容，包括文件和消息，都以简单语言编写。像同事一样与读者交谈，使用 `you`，热情直接，并将每个步骤作为他们可以运行或跳过的建议，而不是命令。保留具有实际意义的术语；用简单语言解释每个术语。不要使用连字符或破折号作为标点符号：不要使用英文破折号，不要使用中文破折号，不要使用连字符复合词。写 `read only`，而不是 `read-only`。用简单语言表达，或者重写句子。代码、文件路径、命令标志和值与其他技能匹配的保持其连字符。使用短句、逗号或括号。清晰比聪明更重要。

## 此技能的作用

运行结构化发现，权衡选项，并在 `docs/specs/` 中编写或更新构建规范。主线程编写；它仅将读取代码库或获取网络的任务卸载给廉价的子代理（见 *子代理*）。四种模式：

| 模式 | 使用场景 | 设计行为 |
|---|---|---|
| `FEATURE` | 从头开始设计新功能，无论是否有现有代码 | 基本原理设计，最佳实践，最小化代码阅读 |
| `ARCHITECTURE` | 为新项目选择技术堆栈或基础架构 | 全面堆栈评估，行业模式，不读取代码 |
| `ENHANCEMENT` | 改进、替换或扩展现有内容 | 读取现有代码 + 规范，专注选项比较 |
| `CROSS-CUTTING` | 在整个代码库中标准化模式（错误处理、日志记录、认证、命名） | 样本当前状态，精确定义标准，建议执行 |

- **创建**：新决策 → 新规范，状态为 `Proposed`
- **更新**：发展现有决策 → 就地编辑现有规范
- **替代**：替换过去决策 → 新规范 + 更新旧规范的状态行
- **确认**：商讨 `Assumed` 规范，`/develop` 在工程师选择构建之前记录时（见 *确认假设决策*）

规范状态有两种行为，由是否存在可构建的范围功能链接规范（一个指向它的 `docs/scope/` 行的 `spec` 单元格）决定：

- **功能链接规范**（典型的 FEATURE/ENHANCEMENT，或具有范围行的 ARCHITECTURE 基础）的状态反映功能生命周期。`/architect` 创建它为 `Proposed` 并拥有其内容，但从不推进状态；`/develop` 在功能进入进行中时将其推进到 `In Progress`，然后在构建和验证后（范围 `done`）将其推进到 `Accepted`。工程师确认仅确认内容；`Accepted` 表示已发布。
- **独立决策规范**（基础/堆栈或跨切标准，没有范围行链接它）的决策状态。写入时为 `Proposed`，工程师在确认时（决策已生效）为 `Accepted` 确认。`/develop` 不推进它。

记录已发布工作的规范（“已构建路径”或已链接的功能已 `existing`）出生为 `Accepted`。

**`Assumed` 状态。** `/develop` 可能在工程师选择在负载决策商讨之前构建时创建状态为 `Assumed` 的规范。它记录构建使用的假设，而不是商讨的决策。功能仍然可以标记为 `done`；`Assumed` 规范保持标记为有待确认，并且不会阻止它。只有 `/architect` 通过确认（见下文）清除 `Assumed` 状态。`/architect` 从不创建 `Assumed` 规范；它仅商讨已存在的规范。

不编写代码。从不更新 `AGENTS.md`/`CLAUDE.md`（`/sync` 拥有这些）。

## 子代理（主线程编写；子代理仅读取、获取或交叉检查）

主线程运行对话并编写规范；它从不将编写或任何修复交给子代理。它生成的每个子代理都是只读的，并且永远不会继承会话模型：

- **读取代码库**（最便宜的模型，Claude Code `haiku`）：当存储库很大时（ENHANCEMENT/CROSS-CUTTING）对现有代码进行只读扫描。Claude Code：`scout` 类型。返回紧凑的映射，从不文件转储。
- **从网络获取**（最便宜的模型，Claude Code `haiku`）：当前工具景观检查和 Agent Skill / MCP 发现，都在设计对话（阶段 c）期间，当需要当前事实时。Claude Code：`researcher` 类型。返回紧凑的摘要，从不原始页面。
- **交叉检查草拟的规范**（其主要工作是决策完整性：找到规范未命名的行为必须产生的值，以及构建者会自行发明的决策）：一个只读传递，读取完成的规范并返回评论，不写入任何内容。`/architect` **总是询问**是否运行它（从不代表工程师运行或跳过它），强烈建议在 `GA`/`Beta`（这些错误存在的层）使用 `Another model`，在 `Alpha` 提供它，并建议 `Skip` 在 `Prototype`；它发现的任何差距都向工程师展示推荐的修复方案，让他们决定，而不是自动解决。见 *规范编写后*。

网络获取只发生一次，当需要它时（阶段 (c) 景观和工具发现检查）。它返回的链接将进入规范的参考文献，供人类跟随；人工智能永远不会再次获取它们（在交叉检查、`/develop` 或 `/audit` 期间）。

## 询问与行动

在编写规范之前（和生成任何读取/获取辅助工具之前）针对性地提问；将预算用于实质内容。对每个问题进行分类：

- **INFER**：任何提示或代码库揭示的内容（功能与架构，堆栈，范围内的 UI，已选择的提供者）。推导，不要询问。
- **ASK**：只有工程师单独知道的内容（需求，偏好，业务规则，合规范围）。
- **RECOMMEND**：任何专业知识确定的（哪个提供者/库/模式适合）。声明选择，简短说明原因，以及备选方案；他们可以覆盖。从不提供中性菜单，从不沉默决策。

不要将完整数据模型、完整堆栈或现成的验收标准集捆绑到一个接受或更改面板中，并且不要为他们默默地决定工具、提供者或设置选择。

建议与当前使用的堆栈一致（在 BaaS 上，优先考虑其认证/存储而不是新的外部工具；重用优于蔓延）。无论是网络还是移动：推断平台，不要假设网络。

这就是意图，不是程序。如何运行提问生活在于 `internal/design-conversation.md`，执行将在下面让你在问一个设计问题之前完整阅读。

## 资产所有权

此技能仅创建或更新的 `docs/specs/` 中的规范文件，以及它产生的任何支持证据（清单、审计），这些证据生活在规范的 `rationale.md`（目录规范）或内联（单个文件规范），永远不会在范围文件夹中（`docs/scope/` 由 `/scope` 拥有，而不是规范）。

两个独立选择，位置（仓库形状）和形状（决策大小）：

- **位置 = 仓库形状。** 单个仓库 → `docs/specs/`。单仓库 → `docs/specs/<workspace>/` 用于工作空间决策，`docs/specs/_root/` 用于仓库范围的决策（镜像范围）。编号是按位置（扫描该目录以查找下一个 `NNNN`）。称解析的位置为 `$SPEC_DIR`。
- **形状 = 决策大小**，在任何仓库形状中都相同。简单决策：一个文件 `$SPEC_DIR/NNNN-title.md`（所有内容内联，编写紧凑）。一个伞形（相关的子决策），一个重型或基础决策，或一个值得 `verify.md` 的使用目录形状：`$SPEC_DIR/NNNN-title/`，其顶部文件为 `index.md` 加上 `rationale.md`（以及子规范 `NNNN-<child>.md` 用于伞形）。从不重复名称（`NNNN-title/NNNN-title.md`）；目录携带编号，顶部文件是 `index.md`。默认为单个文件。

  目录规范始终有两个核心文件（加上可选的 `verify.md` 和子规范）：
  - **`index.md`**：构建规范 `/develop` 读取：`## Summary`，`## Requirements`，`## Decision`，设计/规范部分，`## Build plan`，`## Consequences`，`## Follow-up`，以及指向 `rationale.md` 的一行 `## Rationale` 指针。对于伞形，它还以列表形式开头 `## Structure` 清单并链接每个子规范（每行一条：它是什么以及它支持哪个决策），并包含任何跨子合同。
  - **`rationale.md`**：决策记录 `/develop` 跳过：`## Context`，`## Options considered`，`## Rationale`，`## References` 部分，以及在其子标题下任何庞大的证据（清单、审计）。没有 `research/` 文件夹；所有证据都生活在这里。
  - 子规范（伞形仅限）是扁平的 `NNNN-<child>.md` 文件，每个文件足够完整，可以独立构建，并带有简短的内联理由（没有自己的 `rationale.md`）；只有当子规范变得沉重时才将其提升为其自己的目录。跨子合同生活在伞形 `index.md` 中。
- **一个狭窄的例外进入范围**：确认规范后，更新匹配的功能为准备构建的形状（*规范编写后*，步骤 3 中的确切编辑）。不要将原子任务列表倒入范围。没有匹配的功能：提供注册一个（见推导任务步骤）。

**资产基础。** 规范默认生活在 `docs/` 下。如果 `docs/` 是一个发布的文档站点（`docusaurus.config.*`，`.vitepress/`，`mkdocs.yml`，Astro Starlight 或 Nextra 检测到），则使用 `.workflow/` 而不是（`.workflow/specs/`）。始终遵循已存在的基（这里假设 `docs/`）。

## 可移植性（任何操作系统，任何代理）

- **命令**：`git` 是唯一需要的 CLI，在所有操作系统上都是相同的。其他 shell 片段（`mkdir -p`，`date`，`find`，`ls`，`cat`，`wc`）是 POSIX 参考，不是字面脚本；使用您的代理的跨平台文件工具（读取、搜索/glob、写入、创建目录）以及您对今天日期的了解。使用您的写入工具创建 `docs/specs/`，而不是 `mkdir`。
- **捆绑文件**：`agent-prompt.md`，`agent-modes/*.md`，和 `spec-template.md` 生活在此技能文件夹的相对路径下。主线程在编写规范之前自己读取这些（见 *编写规范*）：`agent-prompt.md`（角色、规则和报告格式），匹配的 `agent-modes/<mode>.md`，和 `spec-template.md`（规范部分结构）。仅在写入时读取它们，不要在预飞行期间读取，这样它们就不会在整个面试中坐在上下文中。
- **没有交互式问题支持？** 使用您的代理提供的任何选项选择器，并且仅在缺少时回退：作为纯文本提问轮次，具有相同的选项，代理没有选择器；选择器会自动添加其他选项；询问问题。

## 执行

### 步骤 0：主题检查（预飞行之前）

如果未提供设计主题（`/architect` 无参数或空描述），则在做任何其他事情之前停止并询问：

“你想处理哪个设计决策？用一到两句话描述你需要设计的功能、系统或选择。”

等待答案；将其用作预飞行前的设计主题。

---

### 预飞行（主模型）

运行这些步骤（`git` 命令是字面的；其他使用您的代理的文件工具）：

- **新鲜度（团队）**：`git fetch` 静默地，选择基础分支（如果 `git rev-parse --verify main` 成功，则 `main`，否则 `master`），计算与原点的提交计数 `git rev-list --count HEAD..origin/<base>`。如果 >0，在决策之前警告“先拉取” （队友可能已添加规范或更改此功能）。
- **解析规范位置** (`SPEC_DIR`) = 范围工作空间镜像到 `docs/specs/`：单个仓库 → `docs/specs/`；单仓库工作空间 → `docs/specs/<workspace>/`；仓库范围 → `docs/specs/_root/`。确定 `<workspace>` 如范围所做（主题/路径/范围行）。如果缺失，则创建目录。
- **今天的日期**：使用今天的日期（将其注入规范）。
- **列出此位置的现有规范**：文件名 `NNNN-*.md` 加上 `$SPEC_DIR` 中的任何 `index.md`，用于编号（按位置）和相关的决策检测。
- **计算源文件**（例如 `.ts`，`.tsx`，`.js`，`.py`，`.go`，`.rs`，`.java`），排除 `node_modules/`，`.git/`，`dist/`。这提供了要读取的代码量，并决定是否将读取卸载给 `scout` 子代理。
- **读取项目上下文**，堆栈和社区技能的来源：根 `AGENTS.md`（回退到 `CLAUDE.md`，否则缺失），以及此功能区域的嵌套 `<area>/AGENTS.md` 如果存在（例如 `src/auth/AGENTS.md` 对于 auth 功能）。
- **读取此功能的构建方法**：管理规范 `## Build plan` 排序和切片的交付策略。优先级：此功能的范围行 `Approach` 覆盖如果声明，否则项目默认（根 `AGENTS.md` 首先否则 `docs/scope/` 中的范围标题）。具有自己的方法的功能按其方法构建；其他使用项目默认方法。四个意味着实质上不同的 `## Build plan` 排序，而不是相同的顺序重新标记：**Tracer Bullet** 首先建立通过每一层的薄端到端线程，然后变厚；**Skateboard** 首先构建最薄的可用整体，然后增长；**Facade** 首先使用占位符数据的 UI 外壳，并推迟迁移（原型路径）；**Journey** 在下一个用户路径的任务完全完成之前完成。可能存在特定于项目的变体。如果两者都不记录一个，则假设默认并通过员工/主管判断设置默认值（为生产工作优先考虑端到端 Tracer Bullet 切片）。让记录的方法明显地塑造排序。
- **定位链接的范围功能（如果有）**：廉价扫描 `docs/scope/` 文件名/标题（包括每个工作空间子目录），寻找匹配此主题的功能；仅打开包含它的单个范围文件（`scope.md`，或匹配的 `<epic>.md` 在拆分中）。如果找到，读取该行的意图加上任何验收标准种子（它们为阶段 (a) 种子），并记住文件/行以供推导任务和链接步骤使用；这也确定了功能链接与独立决策状态。如果没有行匹配，则注意独立决策路径，现在不要创建一个。
- **（可选）** 列出安装的技能目录以供仅用于可用性（`.claude/skills/`，`.agents/skills/`，`skills/`）。相关性由 AGENTS.md 加上功能决定，而不是名称匹配。

从规范列表（相对于 `$SPEC_DIR` 的路径）：
- **下一个编号**：最高现有 + 1，零填充到 4 位数字；如果没有（伞形目录计为一个编号），则为 `0001`。冲突保护（团队）：立即再次列出 `$SPEC_DIR` 在您编写之前；如果选择的 `NNNN` 存在，则增加到下一个空闲编号。从不覆盖现有规范；写入后，确认没有并发运行使用了相同的编号。
- **文件名 / 形状**：从主题生成的 `kebab-case` slugs，最多 5 个词，不带冠词，全部小写。
  - 简单决策 → `$SPEC_DIR/NNNN-kebab-title.md`。
  - 伞形（拆分为 ≥2 个相关的子决策）→ 目录 `$SPEC_DIR/NNNN-kebab-title/`，其中 `index.md`（伞形决策列出其子项），`rationale.md`（推理 + 任何清单/审计），以及其内部的子规范 `NNNN-child.md`。在编写时确定主题的广度，并记住形状。
- **相关规范**：分两轮进行，这样随着规范的积累保持廉价。首先只读取每个现有规范的标题行（即使有几十个它们也很便宜）；然后只读取标题可能重叠此主题的少数规范的标题、状态和上下文开头 20 行，以确认。标记匹配。
- **伞形子检测**：如果主题是现有伞形（`$SPEC_DIR/NNNN-<伞形>/`），例如在构建它时出现的，将新规范放在该目录中作为下一个子规范（`NNNN-child.md`），并将其添加到伞形的 `index.md` 列表中，而不是新的顶级规范。在 `/develop` 遇到构建过程中的决策部分时，也这样做。告诉工程师它将去哪里。
- **更新/替代检测**：如果现有规范明显与主题重叠（相同的域、系统、决策），在阶段对话中之前呈现决策面板（代理没有选择器；选择器会自动添加 Other 自动选项）：“我发现了一个可能重叠的现有规范：`[path]`，[标题]。我应该如何处理？”，选项：**新决策（创建新规范）** · **就地更新现有规范** · **替代它（新规范替换它）**。默认为重叠强度（几乎相同 → 更新或替代；相邻 → 新）。在更新/替代中：设置 `OPERATION`，读取现有规范全文，并跳过就地更新阶段对话。
  - **找到重叠的规范**：如果重叠规范的 `**Status**:` 是 `Assumed`，这是一个确认，而不是上面的面板。遵循 *确认假设决策*（运行设计对话，然后要么填写真实内容并清除 `Assumed`，要么如果假设是错误的则替代）。

**社区技能** 来自项目的 `AGENTS.md`，永远不会使用硬编码的名称表（名称和堆栈会变化）。项目范围的技能/约定生活在根 `AGENTS.md` 中，区域特定的技能生活在嵌套 `<area>/AGENTS.md`（由 `/audit` 和 `/sync` 维护）：

1. 读取根 `AGENTS.md` 和此功能区域的嵌套 `AGENTS.md`；它们的 `## Agent skills` 部分列出了每个安装的技能作为带有其位置和对其管辖范围的简短说明的圆点，以便您可以挑选出相关的技能及其路径直接。
2. 仅识别与 *此* 功能相关的技能。取每个相关技能的路径，并从该 `## Agent skills` 圆点处记下，并在编写时按需打开它，只有当它实质上塑造了决策时才这样做（见 *编写规范*，项目 12）。跳过功能不接触的技能。
3. 可用 ≠ 相关。您可能列出了安装的技能目录以查看存在的内容，但相关性来自功能加上 `AGENTS.md`。如果有一个明显相关的技能已安装但尚未在 `AGENTS.md` 中引用，则使用它，并标记（规范 Follow-up）它属于正确的上下文文件：根如果项目范围的，嵌套 `<area>/AGENTS.md` 如果区域特定的。
4. 上下文文件显示项目已经使用的任何内容（一个 BaaS、一个 ORM、一个支付提供者、一个认证库）是您的库/提供者建议必须构建在或优先考虑，而不是不相关的外部工具。如果一个真正更好的选项没有安装，则将其标记为规范 Follow-up 而不是默默地假设它。

### 编写规范（主线程）

在分阶段对话之后，您自己编写规范。不要生成任何人来起草、研究或评论它。解析此技能的文件夹到绝对路径（您已经解析了这些相对路径，所以您知道文件夹）并现在读取三个文件（仅在现在，所以它们不会在整个面试中坐在上下文中）：`agent-prompt.md`，`spec-template.md`，和匹配的推断模式文件：
- `FEATURE` → `agent-modes/feature.md`
- `ARCHITECTURE` → `agent-modes/architecture.md`
- `ENHANCEMENT` → `agent-modes/enhancement.md`
- `CROSS-CUTTING` → `agent-modes/cross-cutting.md`

然后编写规范，应用：
- **从 `agent-prompt.md`**：采用角色（“你是谁 / 你如何思考 / 你不做什么”）并遵循常见指令，步骤 0，步骤 0b，`## 专家规则适用于所有模式`，和 `## 报告格式`。在 `## 模式特定指令` 中，仅作为唯一的模式特定块跟随上述模式文件；忽略其他模式文件。`agent-prompt.md` 写作为一个子代理简报，所有大写占位符；将您在对话中已经收集的输入（列在下面），并将规则应用于自己。
- **从 `spec-template.md`**：仅使用 `=== SPEC TEMPLATE START ===` 和 `=== SPEC TEMPLATE END ===` 之间的部分（规范部分结构和字段指导）。尾随参考/元部分（`## 文件名约定`，`## 状态值` 表，伞形结构 / 子状态注释，`## 编写规则`）是您自己的指导：您在预飞行中解析了文件名、形状和初始 `**Status**:`；根据 `## 专家规则适用于所有模式` 中的“初始 `**Status**:` 行”规则编写 `**Status**:` 行。不要编辑 `spec-template.md`。

**参考文献和链接**：重用 Stage (c) `REFERENCES_LEVEL`；不要现在获取。根据 *关于来源和引用* 在 `agent-prompt.md` 中编写 `## References` 部分和 `(basis: ...)` 引用，按该级别引用，根据 *关于来源和引用* 在 `agent-prompt.md` 中。Stage (c) 检查只运行一次；仅重用它们确认的链接，并按名称引用任何未验证的来源，不带 URL。只有如果 Stage (c) 从未运行（例如，文档路径），才现在呈现参考文献同意面板（建议选择 `No references, keep it clean`）并设置 `REFERENCES_LEVEL` 为 `none` 或 `sources` (`sources+links` 不提供，在编写时没有获取可用）。仅如果 Stage (c) 从未运行（例如，文档路径），才现在呈现参考文献同意面板（建议选择 `No references, keep it clean`）并设置 `REFERENCES_LEVEL` 为 `none` 或 `sources` (`sources+links` 不提供，在编写时没有获取可用）。

推断的模式（从框架推断）已经是 `FEATURE` / `ARCHITECTURE` / `ENHANCEMENT` / `CROSS-CUTTING`。

应用输入（您已经从设计对话和预飞行收集到）：
1. 设计主题（来自用户的原始消息）
2. 推断框架：模式、平台（网络/移动/API），堆栈和约定（来自 `AGENTS.md`），以及任何推断或确认的约束/合规性
2a. 功能的构建方法（预飞行优先级：范围行 `Approach` 覆盖如果声明，否则项目默认来自 `AGENTS.md`/范围标题，否则记录的默认值）→ `BUILD_APPROACH`；根据此功能隐含的顺序和切片 `## Build plan`。

3a. `RECOMMEND` 项目 → `RECOMMEND_ITEMS_OR_NONE`：您必须做出并说明的决定（与堆栈对齐的工具/提供者，会话模型等）；不要重复它作为开放式问题。如果没有任何，将其视为 `"none"`
3b. 参考文献级别 → `REFERENCES_LEVEL` (`none` | `sources` | `sources+links`，按上述规则）。如果 Stage (c) 从未运行，并且您尚未提问，则默认为 `none`
4. 上下文文件内容：`AGENTS.md`（根 + 此功能区域的嵌套），或 `CLAUDE.md` 作为回退，或 "MISSING"

6. 相关规范路径（在预飞行中标记）

10. 今天的日期（来自预飞行）
11. 文档上下文（如果“已构建”路径运行：工程师关于为什么选择此功能的自由文本答案，替代方案，以及权衡）
12. 与此功能相关的社区技能（从 `AGENTS.md` 推断，按预飞行）：按需打开技能文件，仅当它实质上塑造了决策时才这样做；它的约定在咨询时具有权威性。命名每个在 `## Decision` **Implementation skills** 字段中。

### 确认假设决策

当主题解析为现有 `Assumed` 规范时（工程师通过 `/develop` 的逃避通道首先构建，现在正在确认，通常表述为 `/architect <feature>: ratify …`），预飞行将找到该规范。完整阅读它：其 `## Owed decision`，`## Assumption built on`，和 `## Code area` 告诉您临时决定的假设和代码的位置。然后运行正常设计对话，以实际构建为锚点，并商讨决策。两种结果：

- **假设成立。** 填充真实决策内容（上下文，选项考虑，决策，推理，设计部分，后果）以便规范成为真实的商讨记录，并清除 `Assumed`：设置 `**Status**:` 行为为功能的生命周期状态（如果功能已构建但尚未 `done`，则为 `In Progress`，如果功能已验证和测试，则为 `Accepted`）。`/develop` 然后在 `done` 时将其关闭为 `Accepted`，如通常一样。决策不再具有临时性。
- **假设错误。** 编写纠正规范 (`create` 或 `supersede`)，其中包含真实决策，标记假设规范 `Superseded by [NNNN](…)`，并告诉工程师构建基于一个错误的假设，应该根据纠正的规范重新构建。

无论如何，确认是为什么 `Assumed` 规范可以离开该状态：`/develop` 记录假设，`/architect` 确认或纠正它并提供推理。不要在确认运行后留下规范 `Assumed`。
