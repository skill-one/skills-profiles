# scan-new-specs (已弃用)

**已于 2026-08-20 停用。请勿调用此技能，也请勿安排其运行。**

其计划代理 (`0ITuF9vNJ1RiO00Szlm1fW`) 已暂停，并将保持暂停状态。

## 已停用的原因

该技能在 **spec 合并** 时触发，而 spec 合并发生在功能发布之前。单此设计选择导致了两个失败：

- **它为未发布甚至已废弃的工作起草文档。** 合并的 spec 并非已发布的功能。代理没有证据证明用户实际接收了什么，因此写出的页面是为尚未落地、落地方式不同或根本未落地的行为准备的。
- **它将每个 spec 都视为文档任务。** 没有任何内容判断变更是否需要文档。纯 UI 变更、小的直观添加以及后台工作都变成了草稿 PR，文档仓库积累了未经审核的内容债务，速度比任何人都能审核的速度更快。

## 取代它的方案

`warpdotdev/docs` 中的 `missing_docs` 技能，以 drift-watch 模式运行。它在两个重要方面有所不同：

- **发布触发。** `scripts/check_new_release.py` 对每个新稳定发布运行进行限制，因此流水线看到的是实际发布的内容，而不是计划的内容。每日计划会执行每发布一次的工作。
- **基于价值进行限制。** 每个候选内容在起草任何文档之前，都会根据 `.agents/references/docs-worthiness-criteria.md` 进行评估，默认不提供文档，并要求提供具体证据。判决结果，包括拒绝，都会记录在 `references/changelog_decisions.md` 中，因此不会重新进行争论。

真正值得记录的内容一旦发布，就会在那里重新出现。

## 如果你正要运行这个

- **寻找文档缺失？** 从 `warpdotdev/docs` 仓库以 drift-watch 模式运行 `missing_docs`。
- **你是希望为你的功能编写文档的工程师？** 直接交互式调用 `write-feature-docs`。它仍然有效，并且仍然会引导你进行 spec 研究和提纲确认。它不再以无头模式运行。
- **设置计划文档代理？** 使用 `missing_docs`，而不是这个。计划此技能会重新引入它被停用时的泛滥问题。

## 相关技能

- `missing_docs` (在 `warpdotdev/docs`) — 发布触发、基于价值限制的替代方案
- `write-feature-docs` — 仍然支持工程师直接交互式使用
