# 复现错误报告

在当前上下文是 GitHub 问题、支持报告、Linear 工单或描述可通过可见应用程序行为复现的具体错误的用户提示时使用此技能。它主要用于 UI、渲染、窗口管理、设置、编辑器、终端显示、引导或其他交互式错误，其中屏幕录制（或截图）使结果更具可操作性。

父代理不应尝试在本地手动复现 UI 错误，除非用户明确要求。启动一个或多个启用计算机使用的 Oz 云代理，以便它们可以运行相关应用程序、与其交互并捕获视觉证据。

## 父工作流

1. 仔细阅读错误报告并提取：
   - 报告的行为
   - 预期行为
   - 如果提供，则复现步骤
   - 当相关时，操作系统、应用程序版本/构建/频道、外壳、功能标志、账户状态或其他环境限制
   - 附加的截图、视频、日志或注释，这些可以缩小复现路径
2. 判断此技能是否适用：
   - 用于 UI 可见错误、交互错误、渲染/布局错误、引导错误以及屏幕录制（或截图）有用的错误。
   - 除非提示明确要求视觉复现，否则不要用于纯后端、CI、构建、依赖项或纯文本代码问题。
   - 如果报告需要凭证、私有账户状态或复现环境不可用的其他功能，请清楚报告该限制，而不是猜测。
3. 如果复现路径很简单，启动一个启用计算机使用的 Oz 云代理。
4. 如果有多个可能的复现路径，在一个 `run_agents` 批次中启动多个 Oz 云代理。给每个子代理一个独特的假设或环境变体，例如：
   - 不同的操作系统或桌面环境
   - 初始运行状态与已初始化的本地状态
   - 稳定版本与开发版本
   - 新设置与现有设置
   - 不同的外壳、提示、面板布局或设置切换
5. 如果步骤不完整，使用代码库知识提出可能的应用程序状态，并将子代理分配给调查这些状态。不要编造关于原始报告者环境的假设。
6. 等待所有子代理报告后再总结。区分确认复现、部分复现、未复现、障碍和未测试的假设。

## 版本和应用程序设置

- 当存在合适的可运行工件时，优先针对用户报告的确切应用程序版本/构建/频道进行复现。
- 当可以安装更接近报告者匹配的工件时，不要在沉默中替换最新的可用构建。
- 优先考虑已发布或打包的可运行工件，前提是该工件更好地匹配报告者的环境，并且仓库特定指南允许这样做。
- 如果无法找到或安装确切版本/构建，请清楚报告，解释尝试了什么，并且仅在继续调查有用时使用最接近的合理回退。
- 在清单和最终报告中记录请求的报告者版本、安装的测试版本、工件来源和任何回退决定。

## 仓库特定指南

消费仓库可能会提供一个名为 `reproduce-bug-report-local` 的配套技能。当该配套技能可用或在提示中引用时，请阅读并应用其仓库特定的范围、应用程序设置、环境和工作流指南作为补充说明。本地配套技能可能会缩小范围或专门设置，但它不应重新定义此核心技能中的证据、工件、报告或安全预期。

使用如下格式的 `run_agents` 调用：

```text
summary: 启动 Oz 云计算机使用代理以复现报告的 UI 错误并捕获屏幕录制。
remote.computer_use_enabled: true
agent_run_configs:
- name: "repro-primary"
  prompt: 主要复现提示
- name: "repro-variant"
  prompt: 当有用时的可选变体提示
base_prompt: 下面的共享子代理提示
```

当它们会重复相同的步骤时，省略额外的子代理。除非用户请求特定模型，否则省略 `model_id`。

## 共享子代理提示

给每个子代理这些共享指令，然后附加子代理特定的复现路径或假设。

```text
你正在使用 Oz 云计算机使用来复现报告的 UI 错误。

目标：
- 尽可能忠实地复现报告的行为。
- 默认情况下捕获屏幕录制；大多数 UI 错误涉及运动、过渡或多步骤交互，因此视频比静态图像更有说服力。作为补充捕获截图，或仅在确实为静态渲染时作为主要工件捕获。
- 如果提供的步骤不清晰或不完整，使用代码库和产品知识来识别可能产生报告行为的可能应用程序状态，然后测试分配的假设。
- 报告清晰的复现证据，而不仅仅是意见。

输入：
- 错误报告上下文：<粘贴或总结问题正文、评论、截图/视频描述、标签和相关元数据>
- 分配的复现路径或假设：<具体的步骤、环境、应用程序状态、设置、功能标志或代码路径要测试>
- 报告者应用程序版本/构建/频道：<报告中的确切值，或未知>
- 构建应用程序目标：<要安装的确切可运行工件，或如果确切工件不可用时的合理回退>

安全和隐私：
- 不要向公共报告者索要凭证、令牌、私有存储库、私有工作区名称或私有账户标识符。
- 不要在录制、截图、日志、清单或最终报告中包含密钥、认证令牌、私有 URL、Authorization 头、刷新令牌或其他私有账户详细信息。
- 除非提示和仓库特定指南明确授权安全的测试认证工作流，否则不要创建或登录账户。
- 如果分配的报告无法在允许的认证/状态限制内执行，请停止并报告障碍。
- 除非明确指示，否则不要向 GitHub、Linear 或外部服务发布评论。当提供 Slack 线程上下文（一个频道 ID 和线程）时，将复现证据（录制）发布回该线程，以便请求者看到它；不要发布到任何其他频道或服务。
- 避免破坏性行动。如果复现需要删除应用程序状态，请仅删除当前复现环境的测试状态，并准确报告重置了什么。

工件工作流：
- 创建一个以你的变体命名的专用工件目录，例如 `~/bug-repro-primary`。
- 默认情况下记录复现的屏幕录制并保存到工件目录中，使用描述性名称，例如 `repro.mp4`。
- 作为补充捕获截图（或仅在确实为静态渲染时作为主要工件捕获），使用有序文件名，例如 `01-initial-state.png`、`02-before-click-settings.png` 和 `03-after-click-settings.png`。
- 在工件目录中维护一个简短的清单，包括：
  - 录制或截图文件名
  - 时间戳
  - 可见应用程序状态
  - 执行或即将执行的操作
  - 截图是否显示报告的错误
- 如果 harness 支持内置截图或工件上传，请使用它。否则将工件保留在目录中并报告路径。

复现工作流：
1. 确认你正在测试的环境：操作系统、架构、显示/会话类型、如果相关则外壳，以及可见的应用程序/构建/版本。
2. 当可用时，从报告中识别确切的报告者应用程序版本/构建/频道，然后使用最接近的仓库批准的可运行工件。
3. 如果没有确切的报告者版本可用，记录版本未知并选择报告的最合理安装目标；明确说明回退。
4. 从与报告最匹配的最干净状态开始。如果错误取决于现有设置或持久化的本地状态，则不要重置应用程序状态。
5. 在尝试特定错误复现之前，达到报告所需的基线应用程序状态。
6. 在尝试特定错误复现之前，开始屏幕录制并捕获基线截图。
7. 首先按照可用的确切步骤进行。
8. 如果确切步骤无法复现，测试分配的假设并记录它与报告的偏差。
9. 如果错误出现，停止更改变量并捕获足够的证据使复现具有可操作性。
10. 如果错误未出现，最多进行两个有针对性的变化，这些变化直接受报告或代码路径假设的支持。
11. 如果应用程序崩溃、挂起或阻止进度，请捕获截图并收集非敏感日志或终端输出以解释障碍。

代码路径调查对于不清晰的步骤：
- 在代码库中搜索 UI 字符串、标签、功能名称、设置键、遥测名称、路由名称和报告中提到的组件。
- 识别可能产生报告行为的可能组件、模型、功能标志或状态转换。
- 使用该调查选择有针对性的 UI 操作，而不是广泛的探索性点击。
- 报告使你形成假设的文件或符号，但最终报告应专注于复现证据。

报告回来：
- 在结论之前，简要的错误摘要，包括问题/报告标识符（如果可用）、报告的行为和预期行为。
- 复现状态：确认、部分确认、未复现或受阻。
- 你执行的确切步骤。
- 环境和应用程序/构建信息。
- 报告者请求的应用程序版本/构建/频道、安装的测试版本/构建/频道，以及工件来源或回退解释。
- 观察到的行为是否与报告匹配，以及匹配程度。
- 屏幕录制（以及任何补充截图）与简短描述和工件路径或附件名称。
- 收集的任何日志、崩溃输出或诊断，并删除密钥。
- 最可能的代码路径或状态，如果调查过。
- 建议的下一步调试步骤或后续问题，仅当它将实质性改变下一步行动时。

## 子代理提示模式

### 主要复现子代理

用于具有清晰步骤的报告：

```text
你拥有主要的复现尝试。

在尝试变体之前，严格按照错误报告的步骤进行。优先匹配报告者的操作系统、应用程序频道、允许的应用程序状态、设置、外壳和布局。如果这些详细信息缺失，选择最常见的路径并明确列出假设。
```

### 变体子代理

当存在一个值得测试的特定替代条件时使用：

```text
你拥有这个复现变体：<变体名称>。

仅测试分配的环境或状态。不要复制主要子代理的完整搜索空间。报告这个变体是否改变了结果，并包括任何差异的截图。
```

### 代码路径假设子代理

当复现步骤缺失或模糊时使用：

```text
你拥有代码路径指导的复现。

首先从报告中的字符串、UI 标签、设置名称、功能名称或截图中跟踪可能的代码路径。然后选择一个有针对性的 UI 路径来执行可疑状态。报告你用来形成假设的代码路径以及测试它的视觉结果。
```

## 成功标准

使用此技能成功将产生：

- 带有屏幕录制（以及有用的截图）和确切步骤的确认复现，或范围明确且测试了假设的非复现。
- 可视证据的清晰工件路径或附件。
- 简要总结测试了哪些变体和哪些未测试。
- 足够的环境详细信息，以便工程师可以重复测试。
- 没有泄露密钥、凭证、私有账户详细信息或不必要的公共评论。

## 总结格式

当子代理完成时，按此结构总结：

```text
错误摘要：
- 问题/报告：<标识符或来源>
- 报告的行为：<子代理尝试复现的错误是什么>
- 预期行为：<应该发生什么而不是>
复现状态：<确认 | 部分确认 | 未复现 | 阻塞>

测试了什么：
- <变体/子代理>：<步骤和环境>

证据：
- <截图/工件路径>：<它显示什么>

发现：
- <观察到的行为与报告的行为>
- <可能的 state/代码路径，如果已知>

下一步：
- <一个具体的调试动作或后续问题>
```
