# 交叉评审

使用此技能在多个子代理独立就同一争议性问题提出提案或意见后，运行**第二轮**。与其自己整合他们的报告，你应将每个提案分发给*其他*作者，并要求他们对其进行评审——优缺点——然后你整合由此产生的更丰富的分析结果。

## 重要性何在

当你生成独立提案（不同模型、不同角度），每位作者最终都会对问题有深入的了解——通常比你更深入，因为他们进行了调查。如果你直接单独整合他们的报告，你就是瓶颈：你只能看到你恰好注意到的权衡。

要求作者互相评审是寻求建议时好领导的做法：让几个持有不同观点的人聚在一起，让他们挑出彼此推理中的漏洞，然后你得到的整体图景将远比他们中的任何一人——或你——单独产生的要完整得多。作者们将揭示失败模式、隐藏假设和权衡，这些是你和原始提案者都未注意到的。

## 使用时机

当决策**存在争议**时使用交叉评审——即独立代理产生了真正不同的提案，或问题主观到合理的方案存在分歧。良好匹配：

- 架构和设计权衡。
- 审查代码时审查者得出不同结论。
- 有关错误根本原因的竞争性理论。
- 代码结构或 API 形状决策，没有唯一正确答案。

提案已强烈同意时或当问题有客观答案可直接验证时不要费心——评审会增加延迟和 token，其价值专门来自于解决真实分歧。在此范围内，自由使用；你不需要高风险的正当理由，只需要真正值得解决的分歧。

## 先决条件：你需要先有独立的提案

此技能是*第二轮*。它假设你已手头有 N 个独立的提案。如果你还没有：

- 对于判断性强的决策，使用**委员会**技能生成（模型多样化的子代理就同一问题）。
- 对于调查性强的疑问，通过生成并行子代理生成（参见**研究**技能）。
- 或使用你已经收集的任何一组独立的子代理提案。

关键在于第一轮必须是**独立的**——在第一轮中不要让作者互相看到彼此的工作，否则你会失去使第二轮有价值的那种多样性。

## 如何执行

### 1. 收集提案

收集每位作者的提案。保持简洁——核心建议及其理由，而不是完整记录。考虑用中性的标签（提案 A、B、C）标记，并在实际情况下，对作者身份进行匿名化以减少对听起来最自信的模型的风向偏误。

### 2. 分发并要求结构化评审

重用**第一轮的相同子代理**而不是生成新的——它们保留了上下文，并能从理解的角度进行评审。将每个作者的*其他*提案（不是自己的）发送给每位作者，并要求每位作者：

- 对于每个替代方案：其**优点**（它正确的地方，它比我的方法更强的地方）和其**缺点**（风险、边缘情况、隐藏成本、错误假设）。
- 在看到替代方案后，他们是否会**修改自己的**建议——以及原因或原因。
- 一个最终排名或建议及信心。

坚持为每个替代方案提供*优缺点*。一个承认对手优势的诚实评审远比一个对自身提案的反射性辩护更有用。

### 3. 整合

现在由你自己整合。通过**证据质量而不是投票数**比较评审。在你的最终答案中：

- 以建议开头。
- 注明作者在看到彼此的工作后达成共识的地方——第二轮的共识是一个强烈的信号。
- 揭示针对每个选项提出的最尖锐的缺点。
- 解释为什么建议的选项在决策标准下经受住了评审。
- 指出剩余的分歧、信心和实质性未知因素。

## 最终答案模板

除非任务要求不同，否则使用此结构：

```markdown
## 建议
[一个或两个关于决策的句子。]

## 评审如何改变了局势
- [作者在看到替代方案后达成共识或改变想法的地方]
- [提出的最强反对意见，以及它是否具有决定性]

## 为什么这个选项胜出
- [基于评审的理由]

## 剩余风险和未知因素
- [开放性问题或注意事项]
```

## 实用提示

- 除非底层任务明确涉及进行更改，否则保持评审轮只读。
- 除非用户询问，否则不要在用户界面摘要中暴露内部子代理 ID。
- 如果评审薄弱或不支持，向同一作者发送有针对性的后续信息，而不是丢弃它。
