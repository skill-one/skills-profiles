# PR 演示文稿
创建一个本地静态的 HTML/CSS/JavaScript 演示文稿，引导审阅者了解当前分支的拉取请求（PR），将其呈现为四个独立的交互式 D3 视图。该演示文稿应帮助审阅者从四个不同的视图理解受影响的代码和 PR：
- **系统概览视图**：针对受 PR 影响的子系统的简洁独立代码概览。它不应感觉像图表。将其呈现为一系列展开的组件卡片，为审阅者在审阅 PR 之前提供足够的架构上下文以获得方向。在此视图中不要提及 PR、更改的文件、审阅评论、差异链接、截图、规范或实现差异。
- **数据流图**：状态、数据、事件、请求、文件、资源或渲染输出如何在更改的系统中移动。
- **代码依赖图**：哪些更改的组件相互依赖，主要的接口在哪里，哪些文件是入口点而不是叶子依赖项。
- **用户操作图**：用户做什么，他们与什么界面交互，以及该操作如何通过实现流动。

这项技能是对基于画布的 PR 理解的实验。不要重现幻灯片格式。不要将所有视角放在一个图表上。生成四个独立的画布视图，用户可以在它们之间切换，并在每个视图中提供引导式游览，以便该网站从开始到结束教授 PR。根据 PR 的大小进行扩展：一个小的 PR 应该感觉像紧凑的审阅辅助工具，而不是全面的结构文档。

这项技能不是代码审阅技能。不要生成新的审阅发现、批准/请求更改建议或详尽的评论。使用 PR/head 提交的完整代码库、PR 差异、PR 描述、PR 更改的规范以及来自人类或代理的现有审阅评论来生成帮助审阅者快速理解更改的定向地图。

## 输出
在以下位置创建一个自包含的网站：
- `.warp/pr-walkthrough/index.html`
该网站必须可以直接从本地文件系统通过 `file://` URL 加载。不要需要开发服务器、安装包、打包器或构建步骤。
优先选择一个自包含的 HTML 文件，带有内联 CSS、内联 JavaScript 和内联数据。如果不可避免地要拆分文件，请只使用相对本地文件，并避免使用 `fetch()`，因为浏览器限制可能会阻止本地文件读取。
D3 应从信誉良好的 CDN 上的固定官方版本加载。除非有明确的原因要更改它，否则使用辅助脚本的默认设置：
- `https://cdn.jsdelivr.net/npm/d3@7.9.0/dist/d3.min.js`
不要使用未固定的 `latest` URL、非官方构建或动态包范围。不要在 UI 中显示重复的 D3 实现免责声明。仅在相关时将 CDN/运行时细节保留在验证日志或最终免责声明中。
对于可重用确定的 D3 渲染，优先选择 `scripts/d3_canvas_runtime.py` 中的辅助脚本。它发出 Brandalf 对齐的 CSS、一个内联运行时加载器，它在注入固定的 D3 脚本之前定义渲染器，以及一个具有缩放、平移、图切换、搜索、节点详细信息、适应视图和引导式游览控制的图渲染器。使用此辅助脚本而不是在每个生成的演示文稿中编写一次性 D3 设置代码。
生成的画布必须被视为需要验证的生成代码。在报告演示文稿已准备好之前，运行 `scripts/validate_d3_canvas.py` 对生成的 HTML。如果画布无法初始化、D3 无法加载、缺少所需的图、游览控制无法工作、节点/边无法渲染，或在应该可用的情况下浏览器验证无法执行，请调试并重新生成，然后再说演示文稿已准备好。如果确实没有支持浏览器的环境，请报告画布渲染为未验证，而不是已准备好。

## 品牌样式
在生成或修订演示文稿视觉设计时使用 `brandalf` 技能。Brandalf 指向托管的 Warp 品牌源；在编写演示文稿的 HTML/CSS 之前获取并应用它。如果托管的品牌源不可用，请继续使用以下回退标记并在最终响应中报告免责声明。
除非获取的品牌源另有说明，否则应用这些 Brandalf 衍生的默认值：
- 使用 Warp 深色表面：页面背景为 `#121212`，面板为 `#1e1e1d`/`#292929`，文本为 `#faf9f6` 或 `#ffffff`。
- 故意使用 Warp 粉色强调 `#a43787` 用于活动状态、关键链接、焦点环、选定的游览步骤和高强调标签。使用次要绿色 `#34895c`、蓝色 `#2e5d9e` 和紫色 `#754dac` 作为图颜色。
- 使用 Matter 为 UI/正文文本，带有 `DM Sans, system-ui, sans-serif` 回退。使用 Matter Mono 为代码、元数据、画布标签、坐标、文件路径和面向机器的片段，带有 `Roboto Mono, ui-monospace, monospace` 回退。
- 保持副本真实求索、技术、简洁和可验证。避免营销超级形容词和通用 Buzzword。
- 优先选择锐利、类似文档的容器，带有微妙的边框。仅在卡片、节点调用、工具提示和按钮可读性提高的情况下使用圆角。
推荐图颜色：
- 系统概览视图：黄色 `#c0872a`
- 数据流图：绿色 `#34895c`
- 代码依赖图：蓝色 `#2e5d9e`
- 用户操作图：紫色 `#754dac`
- 活动/焦点/选定节点：粉色 `#a43787`

## 工作流程
### 1. 建立 PR 上下文
确定存储库根目录、当前分支和比较基础。
如果当前分支已经有一个 GitHub PR，则使用 PR 基础分支，并记录 PR URL 以用于 GitHub 差异链接：
```bash
gh pr view --json baseRefName,headRefName,title,body,url,state,reviewRequests,reviews,files
```
如果没有 PR，则根据本地存储库约定或远程默认分支推断基础分支：
```bash
git symbolic-ref --short refs/remotes/origin/HEAD
```
然后收集审阅输入：
```bash
git --no-pager diff --stat <base>...HEAD
git --no-pager diff --name-status <base>...HEAD
git --no-pager log --oneline <base>..HEAD
git --no-pager diff <base>...HEAD
```
在构建视图之前估计 PR 的大小，根据更改的行数、更改的文件和概念范围。默认使用最小的有用演示文稿：
- **微小的 PR**：大约 1 个更改的文件或不到 75 行更改。每个视图使用 2-3 个节点/卡片，每个视图使用 1-2 个游览步骤，除非它们实质上澄清了行为，否则省略截图/审阅讨论节点。
- **小的 PR**：大约不到 250 行更改或 1-3 个更改的文件。每个视图使用 3-4 个节点/卡片，每个视图使用 2-4 个游览步骤，并将每个节点摘要限制为 1 句话加上最多 1 个简短细节。
- **中等的 PR**：大约 250-800 行更改或几个相关的文件。仅在每个节点教授一个独特概念时，每个视图使用 4-7 个节点。
- **大的 PR**：仅在 PR 跨越多个子系统、引入新架构或具有大量审阅/规范上下文时，才使用之前更丰富的 5-12 个节点范围。
不要将小的 PR 膨胀以填充画布。如果两个节点会向审阅者传达相同的事实，请将它们合并。如果一个视图会重复另一个视图，请有意使其稀疏，而不是添加填充。
不要仅从差异中构建演示文稿内容。该技能通常在可以访问 PR/head 提交时完整存储库的检出到中调用。使用该检出作为架构上下文：
- 阅读重要更改文件的全当前版本，而不仅仅是它们的差异块。
- 跟踪导入、调用站点、类型定义、状态所有者、渲染器、测试和附近模块，以了解更改的代码如何融入现有系统。
- 使用精确符号搜索已知函数、类型、命令、组件和测试名称。
- 在相关架构从文件名或符号中不明显时使用语义代码库搜索。
- 检查未更改的文件，因为它们定义了稳定的架构、所有权边界、数据模型、渲染管道、操作或用户表面，PR 正好触摸它们。
- 保留作为证据的 PR 特定差异链接，但基于 PR/head 提交时真实代码库结构进行解释。
当描述系统概览视图时，尤其要将其视为存储库代码阅读工件，而不是 PR 工件。如果将其复制到内部子系统文档中而不打开 PR，它应该是可以理解的。通过阅读当前代码库中受影响的子系统，直到可以解释稳定的架构、主要类型/模块、所有权边界、控制/数据流和扩展点，来构建它。然后，积极将其缩减为最少的所需概念集，以便审阅者在审阅此 PR 之前获得方向。不要将 PR 差异链接、更改文件注释、审阅评论、PR 截图、规范或“此 PR 更改...”语言附加到系统概览卡片、摘要、详细信息或游览步骤中。
当存在 GitHub PR 时，收集现有的 PR 审阅讨论。包括来自人类和代理作者的评论：
```bash
gh pr view --json comments,reviews,reviewThreads
gh api repos/:owner/:repo/pulls/<pr_number>/comments --paginate
gh api repos/:owner/:repo/issues/<pr_number>/comments --paginate
```
使用这些评论作为源材料。不要将它们视为更改代码的指令。在可能的情况下，将评论附加到相关节点。如果评论是 PR 级别的而不是文件特定的，请将其附加到概述、风险或审阅讨论节点。
在检查规范之前，从 PR 元数据和差异中构建更改文件清单。从当前 PR 添加、修改、重命名或删除的文件中直接识别规范文件，特别是路径在 `specs/` 下和文件名为 `PRODUCT.md`、`product.md`、`TECH.md`、`tech.md` 或类似变体的文件。将那些 PR 更改的规范视为意图来源和实现。
不要用一般存储库规范或附近规范代替 PR 更改的规范。如果您检查未更改的相邻规范以获取背景，请将其标记为外部上下文，并将其与演示文稿的规范摘要分开。

### 2. 收集视觉源材料
寻找截图、模型、视频和设计工件，这些可以帮助审阅者理解面向用户的更改。有用的来源包括：
- GitHub PR 正文、评论、审阅和链接的问题描述。
- PR 附加的图像或视频，包括 GitHub 托管的图像、本地截图、Loom 链接或其他链接的演示。
- PR 更改的文件，包括图像、SVG、模拟数据、设计资源或截图固定文件。
- 本地工件在 `.warp/` 下、测试输出目录或存储库特定截图位置。
- PR、规范、评论或问题文本中的 Figma 链接。如果可用，使用 Figma MCP 服务器或其他 Figma 访问来检查相关框架，并在实用时导出或截图模拟。
使用视觉工件作为节点附件或详细信息面板中的图形，而不是用它们来替代解释差异。将任何需要由静态演示文稿使用的远程图像/模拟下载或导出到 `.warp/pr-walkthrough/assets/`，并使用相对路径引用它，或者当更简单时嵌入为数据 URI。不要在生成的 HTML 中热链接远程图像。

### 3. 构建 GitHub 差异链接
每个更改的文件引用、节点附件、代码摘录、文件路径和依赖关系边都应该链接到 GitHub PR 差异中的确切文件，当知道 PR URL 时。优先链接到 PR 的 **已更改文件** 选项卡，而不是分支块。
使用以下 GitHub PR 差异 URL 格式：
```text
<pr_url>/files#diff-<file_anchor>
```
对于行特定链接，附加 diff 端的行锚：
```text
<pr_url>/files#diff-<file_anchor>R<new_line>
<pr_url>/files#diff-<file_anchor>L<old_line>
```
其中：
- `<pr_url>` 是从 `gh pr view --json url` 获取的规范 PR URL。
- `<file_anchor>` 是 PR 文件列表中更改的文件路径的小写十六进制 SHA-256 摘要，或 diff 的 `b/<path>` 侧。
- `R<new_line>` 链接到 diff 的右侧/新侧的行。
- `L<old_line>` 链接到 diff 的左侧/旧侧的行。
生成锚点时使用确定性辅助脚本，而不是手工编写。

### 4. 作为四个引导视图分析 PR
在编写 HTML 之前构建四个视图模型。每个视图应包含要点，而不是每个更改的文件。
对于每个图，决定：
- 审阅者应该首先理解什么节点？
- 哪个节点序列最好地从开始到结束教授 PR？
- 对于图视图，哪些边连接这些节点，以及每个边解释什么关系？
- 哪些更改的文件、规范、测试、视觉和现有的审阅评论附加到每个节点？
- 审阅者如果点击该节点应该检查什么？
在最终确定内容之前，将每个重要节点与 PR/head 提交时的实际源文件进行交叉检查。对于系统概览视图，首先检查现有的所有者模块和相邻未更改的模块，然后使用差异仅确定要研究的子系统。对于其他图，使用差异附加证据并描述 PR 特定的路径。
每个视图需要一个游览：一系列节点 ID 和解释性文本。游览应引导审阅者在 deliberate 顺序。它不应仅仅是任意文件顺序选择节点。
有向图必须使方向在视觉上明确。数据流、代码依赖和用户操作边必须使用箭头头渲染，明显地落在目标节点边界而不是消失在节点下方。边标签应描述从源到目标的关系方向。系统概览视图通常应具有零边；如果需要边，则该视图可能正在退回到图表领域，应简化。
使用这些视图角色：
- **系统概览视图**：作为独立的代码概览教授 PR 触摸的子系统的架构。不要将其结构化为 PR 更改列表、差异摘要、实现路径、依赖图、审阅者清单或全面的子系统文档。不要将 PR 差异链接、更改文件注释、审阅评论、PR 截图或规范/问题意图附加到此视图。对于小的 PR，优先选择 2-3 个稳定的组件概念；对于较大的 PR，仅在每张卡片都是必要时使用 4-7 张卡片。每张卡片应比图节点更大，并且应在画布上显示一个简短的段落，而不仅仅是标签。段落应定义组件及其重要性，以便审阅者在审阅 PR 之前获得方向，同时严格限制为审阅者获得方向所需的上下文。卡片标题、摘要、详细信息和游览步骤应描述系统如何工作，并且应保持对 PR 无关。
- **数据流图**：强调信息或状态如何移动。从意图/规范输入开始，然后是源/默认/状态，然后是布局/渲染输出，然后是异步资产或验证循环。
- **代码依赖图**：强调所有权和依赖方向。从规范/入口点开始，然后是模型/视图/命令接口，然后是编辑器渲染元素，然后是测试。
- **用户操作图**：强调用户路径。从界面开始，然后是操作，然后是可见反馈和错误/加载状态。
一个有用的非概览图通常对小的 PR 有 3-5 个节点，对较大的 PR 有 5-12 个节点。对于相同的概念点出现在多个图中，具有图特定的坐标和图特定的解释性文本是可以的，但避免在视图之间重复相同的解释。

### 5. 创建画布数据模型
将图数据内联存储在 HTML 中，作为分配给 `window.PR_WALKTHROUGH_D3_DATA` 的 JSON。不要使用 `fetch()` 加载 JSON。
使用此形状：
```json
{
  "meta": {
    "title": "PR 标题",
    "prUrl": "https://github.com/owner/repo/pull/123",
    "baseRef": "master",
    "headRef": "feature-branch",
    "summary": "PR 试图完成的目标是什么。"
  },
  "graphs": [
    {
      "id": "system-overview",
      "label": "System overview",
      "color": "#c0872a",
      "summary": "受影响子系统的简洁组件概览。",
      "nodes": [],
      "edges": [],
      "tour": []
    },
    {
      "id": "data-flow",
      "label": "Data flow graph",
      "color": "#34895c",
      "summary": "状态和渲染输出如何通过更改。",
      "nodes": [
        {
          "id": "intent",
          "title": "Intent",
          "kind": "overview",
          "x": 0,
          "y": 0,
          "summary": "PR 试图使其可理解的更改。",
          "details": ["简洁的证据基础解释。"],
          "files": [{ "path": "specs/example/product.md", "url": "<github_diff_url>" }],
          "comments": [{ "author": "reviewer", "body": "现有的审阅讨论.", "url": "<comment_url>" }],
          "links": [{ "label": "PR", "url": "<pr_url>" }]
        }
      ],
      "edges": [
        { "source": "intent", "target": "surface", "label": "default flows into" }
      ],
      "tour": [
        { "nodeId": "intent", "title": "从意图开始", "body": "教授这个点为什么很重要。" }
      ]
    }
  ]
}
```
坐标和比例指导：
- 将起始节点放在左/顶部。
- 在实际情况下，将游览路径左到右或上到下放置。
- 保持相关节点足够近，以便游览步骤和边在视觉上明显。
- 将较低级别的依赖项放在调用者的右/下方。
- 对于系统概览视图，将比例从图节点更改为展开的参考卡片。使用较少的卡片、更大的卡片尺寸、段落长度的摘要和一个简单的可读布局。将同级架构组件放置在一个紧凑的参考地图中，围绕中央子系统概念，而不是围绕 PR 意图。在此视图中不要包含 PR 特定的证据和注释。
- 对于小的 PR，保持图坐标紧凑，以便每个视图在不平移的情况下可读。优先选择短左到右链，而不是广泛的地图。

### 6. 构建静态网站
该网站必须适用于人类和浏览器自动化代理。
所需 UI 行为：
- 一个由 D3 缩放驱动的可缩放、可平移的 SVG 画布，渲染当前活动的图。
- 可见的视图切换器：`System overview`、`Data flow graph`、`Code dependency graph` 和 `User action graph`。
- 可见的游览控制：`Previous tour step`、`Next tour step`、`Restart tour` 和一个指示器，例如 `Step 2 / 7`。
- 用于在活动图中搜索节点标题、文件路径和附加评论文本的搜索输入。
- 可点击的节点，它们会打开或更新一个持久详细信息面板，并在它出现在游览中时同步游览到该节点。
- 边标签用于关系含义。
- 键盘支持：
  - 右箭头或 `n`：下一个游览步骤。
  - 左箭头或 `p`：上一个游览步骤。
  - `1`：系统概览视图。
  - `2`：数据流图。
  - `3`：代码依赖图。
  - `4`：用户操作图。
  - `+` 或 `=`：放大。
  - `-`：缩小。
  - `0`：重置缩放。
  - `f`：适应视图。
  - `/`：聚焦搜索。
  - `Escape`：清除搜索或选择。
- 稳定的标题、按钮标签、`data-graph-id`、`data-node-id`、`data-edge-id` 和 `data-tour-index` 属性，以便计算机使用代理可以可靠地点击并通过截图。
所需内容行为：
- 在画布上方或旁边显示 PR 标题、基础/头引用和简短意图摘要。
- 包含正好四个视图定义：`system-overview`、`data-flow`、`code-dependency` 和 `user-action`。
- 每个视图必须有自己的节点和游览。数据流、代码依赖和用户操作图必须具有有向边。系统概览视图通常应具有零边，并使用较大的卡片，带有可见的段落文本，以便它读作概览，而不是图表。
- 在有向图中，每个渲染的边必须在其目标节点处使用可见的箭头头和一个读取源到目标的标签。
- 系统概览内容必须与 PR 无关，并且范围紧密。它应该只教育审阅者关于审阅 PR 所需的架构，而不要参考 PR、更改的文件、审阅评论、截图、规范或实现差异。将 PR 特定的证据和注释放在数据流、代码依赖或用户操作图中。
- 每个游览步骤必须指向一个节点，并解释在该游览中为什么这个节点很重要。
- 每个节点必须在详细信息面板中具有解释性文本。系统概览卡片还必须在画布本身上显示一个完整的段落，并解释稳定的代码概念，而不是 PR 更改。
- 每个更改文件引用应该链接到 GitHub PR 差异 URL。
- PR 更改的规范必须表示为节点或节点附件。如果 PR 没有更改规范，请包含一个明确的“未找到 PR 更改的规范”节点或注释。
- 现有的来自人类和代理的审阅评论必须附加到相关节点或总结在审阅讨论节点中。
- 视觉工件应作为节点附件出现在详细信息面板中。
- 对于微小的和小的 PR，将缺少的规范、审阅讨论和视觉表示为现有节点上的简短详细信息面板注释，除非它们实质上改变了审阅者如何阅读 PR。
- 使用 Brandalf 对齐的 Warp 样式：深色 `#121212` 表面、浅白色文本、Matter/Matter Mono 字体、粉色活动强调 `#a43787`，以及来自品牌调色板的图颜色。
使用辅助输出：
```bash
python3 .agents/skills/pr-walkthrough/scripts/d3_canvas_runtime.py --css
python3 .agents/skills/pr-walkthrough/scripts/d3_canvas_runtime.py --runtime
python3 .agents/skills/pr-walkthrough/scripts/d3_canvas_runtime.py --template --data graph.json > .warp/pr-walkthrough/index.html
```
### 7. 验证演示文稿
在完成之前：
1. 打开生成的 `index.html` 路径或打印确切的 `file://` URL。
2. 验证 HTML 不需要除明确记录的、固定的官方 D3 CDN 运行时之外的网络访问。
3. 确认 D3 使用一个具体的固定 URL，并且没有 `latest` 包引用。
4. 确认不使用 `fetch()` 加载本地 JSON/数据。
5. 确认图数据包含正好所需的图 ID：`system-overview`、`data-flow`、`code-dependency` 和 `user-action`。
6. 确认所有必需的控制项都存在：`Fit to view`、`Reset zoom`、`System overview`、`Data flow graph`、`Code dependency graph`、`User action graph`、`Previous tour step`、`Next tour step` 和 `Restart tour`。
7. 确认每个视图在浏览器中渲染节点/卡片，确认系统概览渲染展开的段落卡片，其中没有 PR 特定的附件，并确认所有非概览图渲染具有可见箭头头的有向边。
8. 确认图切换、游览导航、键盘快捷键、缩放、平移、适应视图、搜索和节点详细信息选择工作。
9. 确认每个图都有一个非空的游览，并且每个游览步骤都指向一个现有节点。
10. 确认每个节点都有解释性文本，并且适用的情况下有相关的更改文件链接，系统概览卡片除外，它不应包含 PR 差异链接、更改文件注释、审阅评论、截图、规范或实现差异。
11. 确认 PR 更改的规范和现有的 PR 审阅评论是否已获取，或者是否明确报告为缺失/不可用。
12. 确认截图、模型、Figma 导出、更改的图像和视频缩略图是否为本地相对资源或数据 URI，而不是远程热链接。
13. 确认该网站使用 Brandalf/Warp 样式。
14. 运行可重用的验证器：
```bash
python3 .agents/skills/pr-walkthrough/scripts/validate_d3_canvas.py --html .warp/pr-walkthrough/index.html --require-browser
```
如果验证失败或无法在支持浏览器的环境中执行，则不要报告演示文稿已准备好；修复图或报告渲染为未验证。
### 8. 可选的 Cloudflare Pages 公共发布
默认情况下，将演示文稿工件保留在 `.warp/pr-walkthrough/` 下，不要版本控制。如果用户要求公共访问 URL 或可重复的 CLI 发布工作流程，请优先选择 Cloudflare Pages Direct Upload 在演示文稿通过验证后。
先决条件：
- 用户需要一个 Cloudflare 账户。
- 对于本地交互式使用，运行 Wrangler login 一次：
```bash
npx wrangler login
```
- 一次创建 Pages 项目，除非它已经存在：
```bash
npx wrangler pages project create warp-pr-walkthrough --production-branch main
```
使用生成的演示文稿目录作为上传根：
```bash
npx wrangler pages deploy .warp/pr-walkthrough \
  --project-name warp-pr-walkthroughs \
  --branch pr-<pr-number>-$(git rev-parse --short HEAD) \
  --commit-dirty=true
```
对于稳定的“最新演示文稿” URL，部署到生产分支：
```bash
npx wrangler pages deploy .warp/pr-walkthrough \
  --project-name warp-pr-walkthroughs \
  --branch main \
  --commit-dirty=true
```
Wrangler 会打印部署 URL，对于非生产分支上传，还会打印部署别名 URL。从 stdout 捕获 URL 并报告给用户。生产分支 URL 通常为：
```text
https://warp-pr-walkthroughs.pages.dev
```
分支预览 URL 通常使用以下形状：
```text
https://pr-<pr-number>-<sha>.warp-pr-walkthroughs.pages.dev
```
重要发布注意事项：
- 新创建的 Cloudflare Pages 项目可能在生产 URL 上服务，直到预览子域名 TLS 完成配置。如果预览 URL 在 Chrome 中因 `ERR_SSL_VERSION_OR_CIPHER_MISMATCH` 而失败，请等待并重试，或者部署到 `--branch main` 并使用生产 URL 立即共享。
- 如果 `wrangler` 警告工作目录中有未提交的更改，请为生成的 `.warp/` 工件传递 `--commit-dirty=true`，这些工件不应提交。
- 对于私有代码或敏感 PR 上下文，除非用户明确接受暴露，否则不要发布到公共 URL。使用受保护的托管、Cloudflare Access 或本地 `file://` URL 代替。
- 仅在 PR 评论中报告短公共 URL；不要提交或嵌入生成的 HTML 工件到存储库中，除非用户明确要求。
## 定向启发式
在决定要突出显示什么时：
- 强调审阅者需要理解 PR 的目的、设计、架构和用户影响的最小兴趣点。
- 优先选择较少、更好的节点。一个 100-200 行的 PR 通常应该产生一个紧凑的演示文稿，其中所有视图总共大约有 10-16 个节点/卡片，而不是 30+。
- 使用 PR/head 提交时的完整代码库作为架构真相的来源。差异显示更改了什么，但现有代码解释了更改的部分是什么意思。系统概览视图应基于代码库探索，而不是差异。
- 对于系统概览，在读者有足够的基础来审阅 PR 之前停止；不要包含间接触摸的每个子系统或每个实现依赖项。
- 优先选择节点表示概念、子系统、状态所有者、用户界面、重要规范和审阅讨论热点。
- 优先选择边表示因果关系、数据移动、调用/依赖方向和用户操作进程。
- 优先选择游览教授顺序。图可以显示关系，但游览应引导理解。
- 减少对生成文件、机械重命名、格式化仅更改和重复的样板。
- 解释每个高级点为什么需要每个较低级别的依赖项。
- 将行为或架构风险作为定向笔记表面，尤其是当它们在规范、PR 描述、测试或现有审阅评论中记录时。
- 将测试连接回它们验证的节点或边。
- 如果规范和代码不一致，将差异表示为节点或注释，而不是隐藏它。
- 不要尝试执行全新的代码审阅。如果您在定向审阅者时注意到某些内容，请将其框定为要检查的区域，而不是发现，除非它已经存在于 PR 审阅讨论中。
