# 实现规范

实现 `PRODUCT.md` 和 `TECH.md` 中批准的功能。

## 概述

在产品和技术规范获得批准后使用此技能。目标是构建规范中描述的功能，同时在工作中保持已提交的规范和实现的一致性，随着工作的进展。

批准的规范应直接位于 `specs/` 下的以工单命名的目录中，例如 `specs/APP-1234/PRODUCT.md` 和 `specs/APP-1234/TECH.md`。

在许多情况下，实现应与产品和技术规范一起推送到同一个 PR 中。随着工程师的迭代，对 `PRODUCT.md`、`TECH.md` 和代码的更改都应推送到同一个 PR 中，以便评审始终锚定实际发布的功能。

## 前置条件

在使用此技能之前：

- 确认 `PRODUCT.md` 存在
- 确认功能需要时 `TECH.md` 存在
- 确认相关规范已经过评审和批准到足以开始实现的程度

## 工作流程

### 1. 首先阅读批准的规范

将：

- `PRODUCT.md` 视为用户界面行为的权威来源
- `TECH.md` 视为架构、顺序和实现形状的权威来源

在编写代码之前，确保您理解预期的行为、约束、风险和验证计划。

### 2. 为大型功能提供可选的实现辅助工具

对于大型或长期运行的功能，在实现开始之前，可选地提供给用户以下辅助工具之一：

- `PROJECT_LOG.md` 用于跟踪检查点、探索路径、部分发现和当前实现状态
- `DECISIONS.md` 用于捕获在 PRD 和技术设计过程中做出的具体产品和技术决策

这些是可选的辅助工具，不是必须交付的成果。当它们可以减少混淆或帮助未来的代理避免重新探索相同的路径时，提供它们。

### 3. 根据规范进行计划和实现

将工作分解为具体的实现步骤，然后根据批准的规范实现功能。

在实现过程中：

- 保持行为与 `PRODUCT.md` 一致
- 保持架构和顺序与 `TECH.md` 一致
- 随着工作的完成，添加或更新测试和验证工件

在实用的情况下，使用同一个 PR 进行规范和实现，以便可以在一个地方审查完整的功能演变。

### 4. 随着实现的演变更新规范

如果实现表明预期的行为或设计应该改变，请更新已提交的规范，而不是让它们过时。

特别是：

- 当用户界面行为、UX、边缘情况或成功标准发生变化时，更新 `PRODUCT.md`
- 当架构、顺序、模块边界或验证策略发生变化时，更新 `TECH.md`
- 将这些更新保持在与相应代码更改相同的 PR 中

PR 应描述实际发布的功能，而不仅仅是规范的初始草案。

### 5. 根据规范进行验证

在考虑工作完成之前，验证代码是否与当前规范匹配。

优先：

- 遵循存储库本地测试约定的单元测试和回归覆盖
- 对于重要的用户流程，进行集成或端到端测试

## 最佳实践

- 在整个实现过程中保持规范和代码同步。
- 当决策发生变化时，优先立即更新规范，而不是将规范清理工作批量到末尾。
- 仅当它们为复杂功能增加了实际价值时，使用可选的跟踪文档。
- 保持同一个 PR 一致：规范更新、代码更改、测试和可选的跟踪文档都应支持相同的功能叙述。
