# Saga

Saga 是一种自主的、由规范驱动的开发工作流，适用于**中大型功能**，这些功能应尽可能无需人工干预即可实现，只在少数离散的触点需要人工参与。你扮演**协调者**的角色：你将一个粗略的提示转化为严密的规范，然后将实现工作委托给一批**工作子代理**，同时保持你自己的上下文窗口干净。

整个方法基于一个赌注：如果规范为每个任务定义了足够严格的验证标准，以形成一个*合同*，那么工作者可以并行执行并自我验证，Saga 几乎无需人工看管即可成功。因此，Saga 的质量在第一阶段就已经决定了，在编写任何代码之前就已经确定。

## 核心原则

- **严密的合同优于良好的意图。** 只有当任务的验证标准足够明确，满足这些标准几乎不可能出错时，任务才准备好委托。歧义是敌人；在规划阶段解决它，而不是在实施阶段。
- **不允许空白。** 在规划阶段，使每个要求都明确。除非用户明确授予了这种自由裁量权，否则不要将决策留给工作者。工作者不应该需要猜测“完成”意味着什么。
- **保护协调者的上下文。** 你是一个长生命周期的协调者。将繁重的阅读、研究和实施工作推给工作者；接收紧凑的报告。将状态保存在磁盘上（在 Saga 目录的规范树和 `PROGRESS.md` 中），以便你的理解能够经受压缩，你可以重新阅读而不是重新记忆。这最大限度地提高了压缩时间，并使你在整个运行过程中保持连贯。
- **验证是一流的。** 每个任务和整个 Saga 都带有预先定义的验证标准，以及检查这些标准的具体方法（计算机使用、交互式 CLI 或测试）。参见 `references/validation-strategies.md`。
- **少数人工触点，而不是零。** 人工批准规范（第一阶段结束），只有在规范确实无法解决障碍时（第二阶段）才咨询人工，并执行最终的手动验收（第三阶段）。

## Saga 目录

每个 Saga 都位于其自己的目录中，**位于仓库之外**，在 `~/.sagas/` 下，以便它在协调者会话之间持续存在，并由新代理恢复。以功能的缩写加上时间戳为其命名，例如 `~/.sagas/dark-mode-20260609-0028/`。与用户确认确切路径并记录它——这是 Saga 的稳定身份。

该目录包含一个规范文件的*树*以及一个进度日志。每个级别都携带自己的验证标准，因此细节随着 Saga 的大小而扩展，而不是使一个文件膨胀：

```
~/.sagas/<saga-name>/
├── SAGA.md                      # 概述、环境、Saga 级别的退出标准、里程碑索引
├── PROGRESS.md                  # 活动的、持续更新的执行日志和当前状态
└── milestones/
    ├── 01-<slug>/
    │   ├── MILESTONE.md          # 里程碑规范 + 里程碑级别的验证标准
    │   └── tasks/
    │       ├── 01-<slug>.md      # 任务规范 + 任务级别的验证标准
    │       └── 02-<slug>.md
    └── 02-<slug>/
        ├── MILESTONE.md
        └── tasks/ ...
```

`SAGA.md` 保持小巧——它索引里程碑并只包含 Saga 级别的内容。里程碑和任务规范包含详细信息。这就是保持你的上下文干净的方法：只阅读你当前正在协调的里程碑或任务的规范，并依赖 `PROGRESS.md` 而不是重新推导状态。

使用 `references/saga-spec-template.md` 中的模板和字段定义逐字复制。在起草规范之前阅读它。

## 第一阶段——规划与规范生成（协调者 + 用户）

目标：生成一个全面、无歧义的 Saga 规范树。这个阶段是**完全协作**的，与用户一起进行。只有在用户批准规范时才结束。

在这个阶段向用户询问任何问题时，**始终使用 `ask_user_question` 工具并提供具体的选项**（单选或多选），而不是开放式问题。当有一个合理的默认值时，设置 `recommended_option_index`。开放式散文问题会减慢用户的速度并邀请模糊的答案；选项会迫使清晰的决策。

### 1. 摄入和框架

将请求重述为一个段落问题陈述和功能的粗略形状。确定你将需要关闭的主要未知因素。选择一个独特的 Saga 目录路径，位于 `~/.sagas/` 下（功能缩写 + 时间戳），与用户确认并创建它；所有以下内容都写在里面。

### 2. 建立机器和运行时能力

在不知道这个机器上实际可以测试什么以及针对这个程序可以测试什么的情况下，你无法定义现实的验证标准。通过首先检查仓库和环境，然后只为无法发现的内容向用户询问来确定：

- **这是什么类型的程序？** Web 应用、原生 GUI、TUI、CLI/库、后端服务等。这决定了验证方法（参见 `references/validation-strategies.md`）。
- **是否可以使用计算机？** 检查是否有计算机使用/浏览器自动化功能可供你或云工作者使用。如果需要 GUI/网页验证，但计算机使用仅在远程可用，计划通过远程工作者进行该验证。
- **测试/构建工具链是什么？** 发现测试运行器、构建、代码检查和类型检查命令（例如，从 README、CI 配置、包清单、项目规则中）。确认它们可以运行。
- **程序如何运行/启动** 以进行手动或交互式验证？

将这些发现记录在 `SAGA.md` 的环境部分下——工作者和任何未来的协调者都依赖它们。

### 3. 关闭每个模糊的间隙

通过 `ask_user_question` 与用户迭代，直到要求中没有空白：行为、范围边界、边缘情况、数据形状、错误处理、非目标以及验收标准。批量相关问题（每次最多 4 个）。只有在剩余的决策要么得到解决，要么由用户明确委托给你自己的自由裁量权时才停止。

### 4. 定义 Saga 退出标准

在分解之前，编写 Saga 级别的**退出标准**：表示整个功能已完成且正确的具体、可检查的条件。这是整个 Saga 的合同，也是第三阶段的基础。

### 5. 分解为里程碑和任务

将工作分解为**里程碑**（连贯的、独立有意义的块，按依赖顺序排列）和每个里程碑内的**任务**，这些任务的范围使得*单个工作者代理*可以集中精力完成一个。为每个任务指定：范围、拥有的文件/表面、对其他任务的依赖，以及**验证标准 + 验证方法**。围绕功能的真实依赖进行实用拓扑——最大化可以在里程碑内并行运行的任务，并按顺序排列里程碑，其中后续工作依赖于早期工作。

将此内容作为规范树写入 Saga 目录：里程碑索引和 Saga 退出标准在 `SAGA.md` 中，每个里程碑的详细信息和里程碑级别的验证标准在其 `MILESTONE.md` 中，每个任务的详细信息和验证标准在其自己的任务规范文件中。每个任务的验证标准必须根据 `references/validation-strategies.md` 严格。如果你无法为一个任务编写严格的验证标准，该任务定义不明确——将其拆分或返回用户。

### 6. 获得批准

展示 Saga 规范——引导用户浏览 `SAGA.md` 和里程碑/任务规范——并请求他们批准或请求更改（通过 `ask_user_question`）。**在用户批准之前不要开始第二阶段。** 这是主要的人工检查点。

## 第二阶段——实施与验证（工作者舰队，循环）

目标：执行每个任务到其验证标准，里程碑按里程碑，委托给工作者并保持你精简。用户在此阶段仅当规范无法解决障碍时才参与。

### 协调机制

- **委托，不要实施。** 使用 `run_agents` 启动工作者。你协调；你自己不编写功能代码。这就是保护你上下文的方法。
- **按并行性批量处理。** 在一个里程碑内，将所有独立任务作为一次 `run_agents` 批量启动（共享 `base_prompt`，每个任务的 `prompt`）。按顺序运行依赖的里程碑。使用任务依赖的 Mermaid/DAG 心理模型。
- **隔离本地工作者。** 当工作者修改同一个仓库时，给每个工作者一个自己的 git 工作树和分支。遵循**Saga 分支命名约定**，以便每个分支都可以追溯到其 Saga 目录、里程碑和任务，而无需咨询 `PROGRESS.md`：
  ```
  saga/<saga-name>/m<M>t<T>-<task-slug>
  ```
  示例：`saga/dark-mode-20260609-0028/m1t2-setup-tokens`。使用以下命令创建：
  ```
  git worktree add ../saga-<saga-name>-m<M>t<T> -b saga/<saga-name>/m<M>t<T>-<task-slug> <base>
  ```
  如果你的团队或仓库有一个分支前缀约定（例如，一个按用户前缀，如 `<username>/`，或 CI 强制执行的要求前缀），一致地添加它，同时保持 `saga/<saga-name>/...` 结构完整，以便分支保持可过滤。工作者永远不会共享一个检出或在工作者的当前分支上工作。提前决定合并策略（通常：在每个里程碑边界集成每个里程碑的分支）。工作者更改必须在使用树之前提交、推送或以其他方式持久传递。

  要列出 Saga 的所有分支：`git branch --list '*saga/<saga-name>/*'`
- **用于计算机使用的远程工作者。** 如果一个任务的验证需要计算机使用，并且它仅在远程可用，则使用计算机启用功能远程启动该工作者（或其验证步骤），并让它返回一个持久性工件（推送的分支、草稿 PR 或紧凑的补丁/差异），而不是只在远程环境中留下工作。

### 给每个工作者提供的每个任务的合同

将共享规则放在 `base_prompt`（仓库路径、基础分支、工具链命令、编码标准、验证方法、如何报告）和每个工作者的特定任务放在每个工作者的 `prompt` 中。指示每个工作者：

1. 只实现分配的任务和拥有的文件。
2. **在循环中自我验证** 使用规定的验证标准（计算机使用 / 交互式 CLI 子代理 / 单元测试 + 集成测试）。迭代修复→验证，直到所有标准都通过或它确实受阻。
3. **在清理之前创建持久性传递。** 对于本地 git 工作树任务，将验证后的更改提交到任务分支，并确保该分支对协调者可见。对于远程任务，推送分支、打开草稿 PR 或返回完整的补丁/差异；不要在远程检出中留下工作的唯一副本。如果受阻但有部分有用的工作，将其作为 WIP 提交或补丁保留；如果没有值得保留的部分工作，请明确说明。
4. **只有在存在持久性传递后才能删除工作树**：`git worktree remove <worktree-path> --force`。分支或补丁仍然存在；工作树不存在。过时的工作树是不可接受的，但清理绝不能丢弃验证或有用部分工作的唯一副本。
5. 紧凑地报告：分支名、提交哈希或补丁/推送分支工件、更改文件、验证证据（测试输出、截图、CLI 转录），以及清晰的通过/受阻状态。保持发现简短——你在保护上下文。

参见 `references/validation-strategies.md` 以选择和应用验证方法，以及什么构成足够的证据。

### 协调循环

对于每个里程碑，按顺序：

1. 启动里程碑的可并行任务作为工作者。立即在 `PROGRESS.md` 中记录每个工作者的可寻址代理/运行 ID、其任务、分支和工作树。显示名称不足以恢复；一个新协调者需要一个运行 ID 来向正在进行的工作者发送消息。
2. 收集报告（读取工作者的消息内容；不要依赖生命周期成功）。在 Saga 目录中更新 `PROGRESS.md` 的每个任务状态和证据指针。
3. **处理受阻的任务。** 如果工作者无法满足其标准，决定：重新范围并重新委托给同一个工作者（它保留上下文），调整其任务规范文件中的任务，或者——只有在障碍是规范的真正差距或外部决策时——才升级给用户并提供选项。尽量不升级；规范通常应该有答案。
4. **集成并运行里程碑级验证。** 将里程碑的分支合并到集成分支，解决冲突，并验证里程碑是否完整（在集成结果中运行相关测试/验证）。如果任何工作者留下了工作树，尽管有指示，现在删除它 (`git worktree remove <path> --force`)，然后再继续。
5. 移动到下一个里程碑。

每当需要状态而不是在上下文中持有状态时，从磁盘重新阅读相关的规范文件和 `PROGRESS.md`。随着进展更新 `PROGRESS.md`——一个新协调者使用它来安全地恢复 Saga，因此过时的日志意味着失去 Saga。如果你感觉到你的上下文正在填满，首先将简洁的进度检查点写入 `PROGRESS.md`。

## 第三阶段——最终验证（协调者 + 用户）

目标：确认 Saga 的退出标准是否满足，然后交给用户进行手动验收。

1. 使用可用的最强方法运行完整的 Saga 级别退出标准（对于 GUI/网页使用计算机，对于 TUI 使用交互式 CLI，否则使用完整的测试/集成套件）。总结针对每个退出标准的证据。
2. 向用户展示简洁的完成报告：构建了什么，如何验证每个退出标准，以及他们手动验证的确切步骤（如何运行/启动，要查找什么）。
3. **通过 `ask_user_question` 循环用户进行手动验收**：接受，或报告特定问题。如果他们报告问题，将它们捕获为新的任务，运行一个集中的第二阶段迷你循环（委托→自我验证→集成），并重新展示。重复直到用户接受。

只有在用户确认验收后，才考虑 Saga 完成。

---

## 恢复 Saga

由于 Saga 目录和 `PROGRESS.md` 位于仓库之外并捕获完整状态，因此 Saga 可以在任何时候（在压缩后、新会话或移交后）被新协调者拾取。当被要求继续、恢复或拾取 Saga 时，**阅读 `references/continuing-a-saga.md` 并遵循它。**

## 实用提示

- 除非用户要求，否则不要提交或打开 PR；当你这样做时，遵循仓库的版本控制规则。
- 保持规范树当前——如果实施迫使范围或标准发生变化，请更新相关的规范文件，而不是让它漂移。
- 对于非常大的 Saga（≈10+ 并行工作者），请优先使用远程执行，以免耗尽用户的机器。
- 除非被要求，否则不要在用户面前总结中的人工代理 ID。
