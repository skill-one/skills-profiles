# write-tech-spec

为 Warp 中的一个重要功能编写 `TECH.md` 规格文档。

## 概述

技术规格文档应将产品意图转化为符合现有代码库的实施计划，记录架构决策，并使执行人员更容易执行和审查人员更容易评估工作。

将规格文档写入 `specs/<id>/TECH.md`，其中 `<id>` 是以下之一：

- 一个 Linear 工单号（例如 `specs/APP-1234/TECH.md`）
- 一个 GitHub 问题 ID，以 `gh-` 开头（例如 `specs/gh-4567/TECH.md`）
- 一个短小的 kebab-case 功能名称（例如 `specs/vertical-tabs-hover-sidecar/TECH.md`）

当存在同名的 `PRODUCT.md` 时，应匹配其使用的 ID。`specs/` 目录应仅包含以 ID 命名的直接子目录。

工单/问题引用是可选的。如果用户有 Linear 工单或 GitHub 问题，请使用其 ID。如果没有，请要求他们提供一个功能名称作为目录。仅在用户明确要求创建新的 Linear 工单或 GitHub 问题时，才创建新的工单或问题；在这种情况下，分别使用 Linear MCP 工具或 `gh` CLI（如果团队、标签或存储库不明确，则使用 `ask_user_question`）。

## 使用场景

当实现跨越多个模块、具有有意义的架构权衡，或审查人员从在代码之前或 alongside 代码中看到计划将受益时，使用此技能。对于纯 UI 变更或简单的修复，通常不需要技术规格。

最好先有 `PRODUCT.md`，以便技术计划与约定的行为相关联。如果实现仍然不确定，请先构建一个 e2e 原型，然后根据所学内容编写技术规格。

## 写作前的调研

在起草之前，阅读产品规格（如果有），检查相关代码，并确定主要文件、类型、数据流和所有权边界。当可以直接检查代码时，不要猜测当前架构。
在规格文档中引用相关代码片段时，最好使用提交固定引用，以便未来的读者可以检查您研究的确切代码。捕获您检查的每个存储库的当前提交 SHA（例如 `git rev-parse HEAD`），并在可能的情况下，将文件引用作为 Markdown 链接到相应的 GitHub `blob/<sha>/...#Lx-Ly` URL。使用链接文本以保持规格中路径的可读性。

## 结构

必需部分：

1. **背景** — 正在构建的内容、当前系统在更改区域的工作方式以及最相关的文件和行引用。将“问题”、“当前状态”和“相关代码”合并为一个基于现实的章节。示例引用：
   - [`app/src/workspace/mod.rs:42 @ <commit-sha>`](https://github.com/warpdotdev/warp/blob/<commit-sha>/app/src/workspace/mod.rs#L42) — 用户流程的入口点
   - [`app/src/workspace/workspace.rs (120-220) @ <commit-sha>`](https://github.com/warpdotdev/warp/blob/<commit-sha>/app/src/workspace/workspace.rs#L120-L220) — 可能会更改的状态和事件处理
   参考 `PRODUCT.md` 以获取用户可见的行为，而不是重新陈述它。
2. **建议变更** — 实施计划：哪些模块会更改、引入的新类型/API/状态、数据流、所有权边界以及设计如何遵循现有模式。当有多个合理路径时，指出权衡。
3. **测试和验证** — 实现将如何通过产品行为进行验证。负责证明功能工作的所有内容：单元测试、集成测试、手动步骤、截图、视频和任何其他验证。直接引用 `PRODUCT.md` 中的编号行为不变式，而不是重新陈述它们；每个重要的不变式都应映射到一个具体的测试或验证步骤。这一部分是验证所在的地方——`PRODUCT.md` 故意没有验证部分。
4. **并行化** — 积极评估是否通过 `run_agents` 启动的并行子代理会显著减少墙上时间或隔离工作。如果 `run_agents` 不可用，则跳过此部分。当规格建议使用子代理时，应包括每个建议代理：
   - 短名称/角色和它拥有的子任务。
   - 执行模式（`local` 或 `remote`）及其简要理由。
   - 对于本地代理：它应使用的工作目录或 git 工作树，以便并行代理不会在相同的检出或文件上发生冲突。
   - 对于远程代理：使用哪个环境或明确说明代理将在空环境中运行。
   - 分支和 PR 策略：每个代理在哪个分支上工作、每个代理将使用的工作树路径以及它们的工作如何落地（每个代理一个 PR、一个合并的 PR 等）。
   - 协调边界：每个代理拥有的文件/服务以及它如何与兄弟代理同步（消息传递、合并点、验证所有权）。

   区分哪些步骤可以并行运行，哪些必须按顺序运行。当依赖图不简单时，考虑使用简短的 Mermaid 图表（`graph TD` 或 `flowchart LR`），以便读者可以一目了然地看到发散点和合并点。

   当不提出并行化时，简要说明为什么它没有益处（例如，任务很小，或子任务紧密耦合），以便审查人员可以质疑这一判断。

   为工作树、分支名称和执行模式提出具体的默认值，而不是留有开放性。

可选部分——仅在它们增加信号时包含；如果为空，则省略标题；不要将“无”作为占位符写入。

- **端到端流程** — 仅在跟踪系统路径告诉您的内容与建议变更列表不同时包含。
- **图表** — 仅在视觉说明比文字更快地解释设计时包含 Mermaid 图表（数据流、状态转换、跨层序列）。优先考虑一个或两个专注的图表，而不是装饰性的图表。
- **风险和缓解措施** — 当存在真实的故障模式、回归、迁移问题或发布风险值得指出时包含。
- **后续工作** — 当存在延迟清理或值得命名的未来工作时包含。

## 长度启发式

根据功能调整规格文档的长度：

- 单文件更改且方法清晰：跳过技术规格或保持在约 40 行以内。
- 多模块更改且存在一些不确定性：目标约 80–150 行。
- 大型跨切或架构新颖的更改：当每个部分都值得其位置时，可以更长。

如果背景和建议变更最终从不同角度描述了相同的文件和状态，则合并它们。

## 写作指导

- 将计划基于实际代码库结构和模式。
- 将重要代码引用固定到提交 SHA，并在存储库有可访问远程时链接到相应的 GitHub 行。
- 优先考虑具体的实施指导，而不是通用的架构语言。
- 解释为什么建议的设计适合此存储库。
- 参考 `PRODUCT.md` 以获取行为，而不是重新陈述它。
- 每个部分都应值得其位置——如果部分会重复另一个或只包含样板，则省略它。

## 保持规格文档的更新

批准的规格文档可能与实现一起发布在同一个 PR 中。当模块边界、实施顺序、风险、验证策略或发布假设发生变化时，在同一 PR 中更新 `TECH.md`。检查入的规格文档应描述实际发布的实现。

对于大型功能，实现者可以可选地保留一个 `DECISIONS.md` 文件，总结具体决策。当它有助于未来代理时提供它；否则跳过它。
