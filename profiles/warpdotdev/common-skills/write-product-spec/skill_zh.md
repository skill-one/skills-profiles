# write-product-spec

编写 Warp 中一个重要功能的 `PRODUCT.md` 规格说明。

## 概述

产品规格说明应清晰明确地描述所需行为，以便代理能够正确实现并避免回归。应纯粹从用户的角度描述功能——用户看到的内容、执行的操作和体验，以及必须为用户保持的不变量。不要包含实现细节（内部类型、状态布局、模块边界、数据流、算法）。

"用户" 并非仅限于 Warp 应用的最终用户。它指的是任何消费所设计界面的对象：

- 对于 UI / UX 功能：使用 Warp 的人类。
- 对于数据模型：读取和写入该模型的代码。
- 对于 API、协议或库：该 API 的调用者——其他服务、客户端代码、插件或代理。
- 对于 CLI 工具或面向开发者的界面：调用它的开发者。

规格说明应从该消费者的角度描述行为：界面的形状、可执行的操作、返回的内容、可依赖的不变量以及必须处理的边缘情况——而不规定界面底层的实现方式。

实现细节、验证和测试计划存在于由 `write-tech-spec` 技能生成的配套 `TECH.md` 文件中。编写产品规格说明通常是两步过程的第一步：一旦 `PRODUCT.md` 获得一致同意，就调用 `write-tech-spec` 为同一功能生成 `TECH.md`（或者让用户知道这是预期的下一步）。产品规格说明应编写得足够清晰，以便可以直接从它编写技术规格说明。

将规格说明写入 `specs/<id>/PRODUCT.md`，其中 `<id>` 是以下之一：

- 线性工单编号（例如 `specs/APP-1234/PRODUCT.md`）
- 前缀为 `gh-` 的 GitHub 问题编号（例如 `specs/gh-4567/PRODUCT.md`）
- 短的 kebab-case 功能名称（例如 `specs/vertical-tabs-hover-sidecar/PRODUCT.md`）

`specs/` 应仅包含以编号命名的目录作为直接子目录——不应包含以工程师命名的子目录。

工单/问题引用是可选的。如果用户有线性工单或 GitHub 问题，使用其编号。如果没有，请他们提供一个功能名称用作目录。仅在用户明确要求时才创建新的线性工单或 GitHub 问题；在这种情况下，分别使用线性 MCP 工具或 `gh` CLI（如果团队、标签或存储库不明确，则使用 `ask_user_question`）。

## 编写前

仅收集所需的上下文：目录编号（线性工单、GitHub 问题或功能名称）、功能摘要、目标用户、关键行为、边缘情况以及功能将如何被验证。对于缺失的上下文，使用 `ask_user_question` 而不是猜测。

### Figma 模拟

如果功能有任何 UI 或交互设计，在起草行为部分之前，请用户确认是否存在 Figma 模拟，并在提供时在规格说明中包含链接。模拟通常是视觉状态、间距和边缘情况布局最可靠的来源——不询问可能会导致行为部分猜测设计师已经确定下来的意图。

- 如果用户提供了一个链接，请在简短的 `## Figma` 部分下（或行为顶部附近内联）包含它，作为 `Figma: <链接>`。
- 如果用户确认没有模拟，请记下 `Figma: none provided`，以便明确而不是模糊地表示不存在。
- 如果功能是纯后端（数据模型、API、没有视觉界面的 CLI 工具），请跳过这个问题并省略该部分。

不要无声地丢弃设计上下文；明确的“无”比完全不提及更可取，尤其是在通常预期会有设计的地方。

## 结构

必需部分：

1. **摘要**——用 1-3 句话描述功能和预期结果。
2. **行为**——规格说明的核心。对功能如何工作的详尽英文描述，以编号的、可测试的不变量形式编写。参见“行为部分”下文——这是规格说明获得长度的部分，其他部分应保持简洁，以避免重复。

可选部分——仅在它们能提供额外信息时才包含；如果为空，请省略标题；不要写“None”作为占位符。

- **问题**——仅在动机不明显于摘要时包含。
- **目标 / 非目标**——在范围不明确或有争议时包含。
- **Figma**——存在时包含链接，或存在设计但无模拟时包含明确的 `Figma: none provided` 注释。对于非视觉功能，完全省略。参见“Figma 模拟”上文中。
- **开放问题**——优先在相关行为旁边使用内联 `**开放问题：** …`。仅在存在多个未解决的问题值得收集时包含一个专门的部分。

不要包含验证、成功标准或测试部分。验证和测试计划存在于配套的 `TECH.md`（由 `write-tech-spec` 生成）。将行为以编号形式编写为可单独测试的不变量——技术规格说明可以直接引用它们。

## 行为部分

行为就是规格说明。其他都是框架。

行为的目标是完整地用英文描述功能如何工作，详细到技术规格说明可以直接从它编写，而作者不必猜测或重新推导产品意图。如果读者在行为部分结束后对功能在某些情况下的行为仍有疑问，该部分就不完整。

至少描述：

- 默认行为和快乐路径的用户流程。
- 每个用户可见的状态及其之间的转换。
- 用户可以提供的所有输入以及功能如何响应。
- 空状态、错误状态、加载/等待状态和取消。
- 合理的实现者不会想到的边缘情况——权限被拒绝、离线、超时、状态变化之间的竞争、多个并发实例、陈旧或缺失的数据、交互中途失去焦点、与相邻功能的交互。
- 相关的键盘、无障碍和焦点预期。
- 必须始终保持的不变量以及不得回归的行为。

行为长度应与功能匹配。简单的功能可能需要几条不变量；复杂的功能可能需要许多不变量，每个流程或状态可能需要子部分。其余的规格说明应保持简洁，以便行为可以根据功能的要求尽可能详尽，而不会使文档整体变得臃肿。倾向于列举一个更多的边缘情况，而不是一个更少。

## 长度启发式

行为应长到功能所需——不要为了达到行目标而截断边缘情况。以下启发式适用于行为周围的内容（摘要、可选部分）：保持框架简洁，以便规格说明的总长度反映功能的实际复杂性，而不是结构开销。

- 简单的修复或狭窄的 UI 调整：不需要规格说明。
- 小功能（单个模块、少量边缘情况）：框架加行为通常总计约 30-60 行。
- 中等功能（跨模块、多个状态）：通常总计约 80-150 行。
- 大型或行为丰富的功能：可以更长，并且大部分长度应存在于行为中。

如果你发现自己同时在摘要、问题、目标和行为中写同一个想法，请合并框架——而不是行为内容。

## 编写指南

- 优先考虑具体的、可观察的行为，而不是有抱负的措辞。
- 在可能的情况下，将行为写为不变量列表，而不是散文。
- 捕获不得回归的不变量和容易遗漏的边缘情况。
- 除非对 UX 不可行，否则避免实现细节。
- 每个部分都应有其存在的理由——如果一个部分会重复另一个部分或只包含样板，请省略它。

## 保持规格说明最新

批准的规格说明可能与实现相同的 PR 一起发布。随着实现的演变，在用户界面或 UX 细节发生变化时，在同一 PR 中更新 `PRODUCT.md`。已提交的规格说明应描述实际发布的功能。

对于大型功能，实现者可以可选地保留一个 `DECISIONS.md` 文件，总结设计和实现过程中做出的具体决策。在它有助于未来代理时提供它；否则跳过它。

## 示例行为部分

一个假设功能的示例行为部分：在 Warp 块列表中渲染 GitHub 风格的 Markdown 表格。它展示了预期的形状——编号的、可测试的、从用户角度出发的不变量，它们枚举了默认值、边缘情况、格式错误的输入、流式传输、选择/复制、搜索、共享、主题和跨界面一致性，并有一个内联开放问题。

````markdown
## 行为

1. 当终端输出块包含一个 GitHub 风格的 Markdown 表格（一个标题行、一个由一个或多个 `---` 段组成的分隔行，以及一个或多个主体行，所有行都由 `|` 分隔），该表格在块中渲染为视觉格式化的表格——而不是原始的管道分隔文本。

2. 表格渲染为：
   - 视觉上独特的标题行。
   - 基于分隔行对齐的列：`|:---|` 左对齐，`|:---:|` 居中，`|---:|` 右对齐。`|---|` 没有冒号时回退到默认对齐（文本左对齐，数字看起来右对齐）。
   - 与活动主题一致的可见行分隔符（或等效间距）。

3. 单元格内的内联 Markdown 渲染为内联：粗体、斜体、内联代码、删除线和链接都以与周围块输出相同的方式渲染。单元格内的换行符（`<br>` 或转义的 `\n`）渲染为单元格内换行。

4. 列宽选择为适应表格的自然内容，当它适合块内时。如果单个单元格的内容非常长，该单元格在其列内换行，而不是强制列宽度变得不合理。
   - **开放问题：** 当换行的单元格会导致行高度不合理时，我们是使用“展开”功能来裁剪，还是让行无限制地增长？

5. 水平滚动：当表格的总宽度超过块宽度时——许多列，或无法合理缩窄的宽列——表格在块内变为水平可滚动的。水平滚动会显示屏幕外的列，而不会裁剪或截断它们。块的垂直滚动仍然独立于表格滚动工作。

6. 当块被调整大小（终端调整大小、窗格拆分、侧边栏打开/关闭）时，表格重新流式传输到新宽度，而不会丢失行或列的顺序。

7. 空单元格渲染为视觉上为空（与周围单元格相同的行高，没有占位符文本）。所有单元格都为空的行仍然渲染为行。

8. 只有标题和分隔符的表格（零主体行）渲染为标题-only 表格，而不是原始文本。

9. 单列表格渲染为单列表格（不会折叠为项目符号列表或类似内容）。

10. 格式错误的表格优雅地回退：
    - 缺少分隔行 → 渲染为预格式文本，而不是表格。
    - 拉伸行（某些行比标题少或多的单元格）→ 缺失的单元格渲染为空；额外的单元格会显示，如果可能，视觉上扩展标题行。块永远不会无声地丢失数据。
    - 未关闭的表格（最后一行在流中截断）→ 渲染为部分表格；参见 (11)。

11. 流式输出：当命令仍在生成行时，表格逐步渲染。新行按到达顺序追加。标题行在收到分隔线后立即锁定；分隔线之前的行渲染为普通文本，直到表格被识别。

12. 选择和复制：
    - 使用鼠标或键盘跨单元格选择它们的可见文本内容。
    - 复制选择默认产生制表符分隔的纯文本（每行一个，单元格由制表符分隔）。一个功能（上下文菜单、快捷键）允许用户复制原始 Markdown 源代码。
    - 复制整个块保留原始 Markdown 源代码的逐字副本。

13. 在块内搜索（块内查找）匹配单元格文本内容。匹配项在渲染的单元格内原位高亮显示；导航匹配项会滚动表格到视图内，包括水平滚动，如果匹配项在屏幕外的列中。

14. 共享或导出块（Warp Drive、共享链接、保存为文件）保留原始 Markdown 源代码，而不是渲染形式。

15. 主题：表格边框、标题背景、交替行阴影（如果有）、以及链接/代码样式都来自当前的 Warp 主题。没有硬编码的颜色。

16. Markdown 表格在块列表 Markdown 已经渲染的任何地方都一致地渲染——命令输出、代理响应以及任何支持内联 Markdown 的其他块类型。相同的输入在每个界面中产生相同的表格。

17. 非表格管道内容不会被错误渲染为表格。包含 `|` 字符但没有有效标题-分隔行的文本仍然是纯文本，即使它视觉上类似于表格。
````
