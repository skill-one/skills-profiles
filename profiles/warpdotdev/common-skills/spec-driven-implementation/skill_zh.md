# spec-driven-implementation

在 Warp 中为重大功能采用以规范为先的工作流程。

## 概述

适用于需要书面规范来提高实现质量、减少歧义或简化审查的重大功能。保持务实：并非所有变更都需要规范。

规范通常应位于：

- `specs/<线性工单编号>/PRODUCT.md`
- `specs/<线性工单编号>/TECH.md`

例如：

- `specs/APP-1234/PRODUCT.md`
- `specs/APP-1234/TECH.md`

`specs/` 目录应仅包含以工单命名的直接子目录。不要在那里创建以工程师命名的子目录或以功能缩写命名的目录。

如果尚未存在相关的 Linear 工单，请在编写规范之前创建一个。直接使用 Linear MCP 工具：

- `list_teams` 查找合适的团队
- `list_issue_labels` 检查预期的标签/标记
- `save_issue` 使用合适的团队和标签创建工单

如果从请求和上下文中无法明显看出正确的团队或标签，请使用 `ask_user_question` 来澄清，而不是猜测。

这些规范应主要由代理编写，而不是手动编写，并应提交到源代码控制中，以便进行审查并与代码保持同步。

## 需要规范的情况

在变更重大时强烈优先使用规范，例如：

- 产品或架构上的歧义
- 预期实现规模约为 1k+ LOC
- 深入或跨切面的栈变更
- 风险行为变更，其中回归测试成本高昂
- 代理质量将通过更清晰的输入得到实质性改善的工作

规范通常不适用于：

- 小型、局部的错误修复
- 简单的重构
- 模糊性很小的窄 UI 调整

对于纯 UI 变更，产品规范通常很有用，而技术规范可能不需要。

## 工作流程

### 1. 判断功能是否需要规范

评估功能的大小、歧义和风险。如果规范不会显著改善执行或审查，则跳过它们，并专注于验证。

### 2. 首先编写产品规范

在实现之前，创建 `PRODUCT.md` 描述期望的用户界面行为。

使用 `write-product-spec` 技能来生成它。产品规范应定义：

- 解决什么问题
- 期望的用户体验
- 不变性和边界情况
- 成功标准
- 如何验证行为

如果功能具有 UI 或交互设计，如果存在 Figma 模板，请请求一个。如果没有模板，请继续但应在产品规范中明确指出。

当存在 Linear 工单时，在规范中引用它。由于规范位于 `specs/<线性工单编号>/...` 下，这通常应该很简单。

### 3. 在需要时编写技术规范

使用 `write-tech-spec` 技能进行重大或模糊的实现工作。

在以下情况下优先使用技术规范：

- 实现跨越多个子系统
- 架构或可扩展性很重要
- 有意义需要记录的权衡
- 审查者从审查计划中受益更多而不是原始代码

如果 e2e 原型导致更准确的实现计划，可以编写技术规范。当实现细节仍然不确定时，不要强制过早的技术规范。

### 4. 实现批准的规范

规范批准后，使用 `implement-specs` 技能从批准的 `PRODUCT.md` 和 `TECH.md` 构建。

实现通常可以与产品和技术规范相同的 PR 推送。当工程师迭代时，保持 `PRODUCT.md`、`TECH.md`、代码更改和测试在同一 PR 中，以便审查反映实际发布的特性。

对于大型功能，实现者可以可选地提供：

- `PROJECT_LOG.md` 跟踪探索路径、检查点和当前实现状态
- `DECISIONS.md` 捕获设计和实现过程中做出的具体产品和技术决策

这些是可选的辅助工具，不是必需的输出。

### 5. 在实现过程中保持规范最新

如果实现与规范不符，请更新规范而不是留下过时的规范。

更新 `PRODUCT.md` 时：

- 用户界面行为变化
- 成功标准变化
- UX 细节或边界情况变化

更新 `TECH.md` 时：

- 实现方法变化
- 架构边界移动
- 风险、依赖项或发布细节变化
- 测试或验证计划变化

提交的规范应描述实际发布的特性，而不仅仅是初始意图。在实用的情况下，将规范更新与相关的代码更改保持在同一 PR 中。

### 6. 根据规范验证行为

在考虑工作完成之前，确保验证与规范对应。优先使用直接验证产品行为的测试和工件：

- 遵循仓库本地测试约定的单元测试和回归覆盖
- 关键用户流程的集成测试
- 适当的 loom 演示或等效功能演示
- 对于 UI 为主的工作，当有用时，截图或视频

## 最佳实践

- 优先考虑务实。
- 编写规范以提高代理的输入质量，而不是作为仪式。
- 保持产品规范行为导向和轻实现。
- 保持技术规范实现导向，并基于当前代码库模式。
- 当规范引用相关代码块时，如果可能，在文件引用中包含检查的提交 SHA，并将引用链接到 GitHub `blob/<sha>/...#Lx-Ly` 的确切行。
- 使用审查时间来验证规范和行为，而不是过度关注代码风格的细微问题。
