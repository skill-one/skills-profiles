# write-pr-description

一个 pull request 的描述只有一个任务：提供 diff 无法说明的内容。

diff 已经说明了发生了什么变更。描述则说明了为什么发生变更、变更的影响、过程中做出的决策以及作者希望引起关注的点。以下内容都由此衍生。当这里的规则与特定审查者的需求冲突时，优先满足审查者的需求。

`create-pr` 覆盖了打开 PR 的机制。这项技能涵盖 PR 主体内容应包含的内容。

## 1. 撰写前收集事实

通常你已经完成了工作，并且已经了解大部分内容。当你描述一个你没有编写的分支，或者刚刚接手的 PR 时，从这里开始。

```bash
# 从分支检出
git --no-pager log <base>..HEAD            # 首先查看提交信息，它们包含变更的原因
git --no-pager diff <base>...HEAD --stat

# 从 PR 编号，没有本地分支
gh pr view <n> --repo <owner/repo> --json title,commits,files,baseRefName
gh pr diff <n> --repo <owner/repo>
```

在查看 diff 之前先阅读提交信息。它们通常是动机最丰富的来源。然后验证它们所声称的内容：一个提交信息说“与该文件中的现有模式匹配”是对代码的断言，并且通常是不正确的。不要转发你没有检查过的断言。

通过查看而不是推理来验证。值得做的检查是廉价且具体的：

- 阅读变更删除的内容。当一个变更存在以修复某个问题，缺陷通常在删除的代码中可见。
- 让系统说明某个事物的含义，而不是推断：`gcloud iam roles describe` 用于角色的权限集，资源的提供者或 API 模式用于资源的字段，解析器用于标记的作用。
- 在声称某个标志是开启或关闭之前，在环境文件中全局搜索该标志。
- 打开评论或提交信息指向的文件，并确认它是否如指针所述。

这类检查通常能写出描述中最好的句子。

收集 diff 无法告诉审查者的内容：

- 动机。没有这个变更，什么会破坏、成本或保持不可能。
- 链接的问题、规范或设计文档，以及分支上提交的任何规范文件。
- 有真实替代方案的决策，以及为什么替代方案被放弃。
- 爆炸半径：这个变更可能破坏的内容，超出它所触及的文件。
- 你运行验证的内容，以及它显示的结果。
- 你不确定的任何内容。

## 2. 遵循仓库的模板

检查仓库是否有 PR 模板。如果有多个，选择与变更匹配的模板。模板因仓库而异，因此每次都要检查，而不是重复使用上次 PR 的形状。

**模板自身的说明优先于这项技能。** 一个模板说“如果与此无关，请删除此部分”，它是在告诉你这个仓库的审查者想要什么。遵循它。以下指导适用于模板没有说明的情况。

- 保持标题、措辞和顺序。审查者和工具都会扫描它们。
- 在标题下用自己的话回答每个部分，不要重复模板的问题文本、解释性链接或示例。一个有四个门禁部分的模板可能需要用 200 个字来四次说“不”。
- 如果一个部分不适用，用表明你考虑过的从句说明，而不是删除它或让它空着（例如“没有新表”）。
- 只有当其陈述为真时才勾选框。否则在同一行上不勾选并附上简短原因。不要删除框，不要带保留意见勾选，也不要将框的文本重述给读者。
- 保留机器可读内容：changelog 标记、工件或媒体标记、问题链接键。检查模板放置标记的位置是否有效。有些模板在 HTML 注释中显示标记，而解析器会删除该注释，这意味着留在原位的标记会被静默忽略。与解析器或合并后的 PR 对比确认。
- 指导性 HTML 注释可以在回答它们后添加。

当没有模板时，使用以下形状，这是模板会给出的相同形状：

1. 第 3 步的引言段落，上面没有标题。它包含“什么”和“为什么”，因此没有单独的 `Why` 部分。
2. `## Review guide`，当第 4 步需要时。
3. `## What changed`
4. `## Validation`

这种形状在小变更时会合并。一个标题下只有一行是第 4 步警告的仪式步骤，因此删除任何会包含一行的部分，让引言来承载它。

## 3. 撰写主体

用一到三句话概括变更的内容和原因。一个只读第一段的审查者应该能够判断他们是否是正确的审查者。

如果仓库有模板，这个段落放在模板的第一个内容部分，无论该部分叫什么。不要在模板的第一个标题上添加引言，也不要在内部重复。

然后给出实质内容：

- 只有在代码不明显时才解释机制。新的抽象、非局部不变量或不寻常的控制流需要一个段落。重命名的字段不需要。
- 明确命名行为变更，包括主要变更的副作用。这些是会破坏其他人的内容。对于权限变更，说明方向：现在允许而以前不允许的内容，以及现在拒绝而以前允许的内容。
- 记录决策及其被拒绝的替代方案。这是大多数描述中最有价值的内容，并且无法从 diff 中恢复。如果没有真实替代方案，直接陈述决策。不要编造一个替代方案来填充空位。
- 包括用户可见变更的视觉证据：截图，或变更的修改前后的对比。只引用存在的捕获。
- 一次链接问题、规范或对话。如果没有，只有在仓库要求时才说明（通过模板部分或贡献指南）。在一个不使用它们的仓库中宣布“没有链接的问题”是代码风格合规，而不是信息。永远不要编造一个看似合理的工单 ID 来填充空位。

### 验证

通常你运行了工作，所以报告它：命令和它显示的结果。

你没有运行，或者只部分运行时，这些是诚实的形状。可以同时适用多个：你可能自己验证了事实，但仍在等待 CI 的其余部分。

- **没有运行。** 平静地说明，并命名审查者或 CI 应该运行的命令。
- **CI 产生结果**，因为检查需要凭证或你不应该使用的环境。命名作业，并说明你期望它显示的内容，将其标记为期望而不是观察。例如“期望一个销毁和一个创建，其他什么都没有”让审查者有东西可以对照运行，这比沉默更有用。措辞要使其无法被误解为你看过的输出。
- **分支添加了测试但没有记录运行。** 说明测试已添加但未运行，以免有人将测试列表视为证据它们已通过。
- **你不能运行**，因为缺少设备、凭证或环境。说明情况，并命名它为审查者需要进行的检查。这不涵盖你跳过的内容；如果你本可以运行，就运行它。
- **其他人记录了结果**，例如在早期提交中注明的验证。归因或省略它。永远不要将其重述为自己的观察。

无论哪些适用，一次说明每个。在三个部分中重复“没有运行”读作搪塞，并且掩盖了说明应该运行什么的那一行。

永远不要将意图写成像结果是那样。

### 文风

以 ASD-STE100 为基准：主动语态、每句一个主题、句子长度不超过 25 个字、简单时态、每个概念一个术语，整个描述中保持一致。代码标识符、命令行和已建立的仓库术语是技术名称；保持原样。参见 [references/plain-language.md](references/plain-language.md) 了解规则和豁免。

## 4. 在必要时添加审查者指导

当阅读顺序不明显、你希望特别关注某个位置，或者变更可能破坏文件之外的内容时，添加审查者指导。当有能力的审查者会知道去哪里查看而不需要被告知时，跳过它。

放在顶部，直接在摘要之后。审查者不应该需要滚动过合规性检查列表才能找到开始的地方。`## Review guide` 是一个合理的默认标题，当模板没有提供时。

在小 PR 中，指导是一两句话，而不是一个部分。将其合并到引言中，而不是在它上面添加标题。两段文字的标题是仪式，六份文件的阅读顺序也是。

审查者指导包含以下部分或全部：

- 推荐的阅读顺序，适用于 PR 大到顺序重要的情况。
- 关注区域：你不确定的内容、与安全相关的表面、有实际替代方案的决策、真正的单向门。

为有能力的工程师撰写。指向代码和开放的问题；永远不要解释如何审查代码。参见 [references/review-guide.md](references/review-guide.md)，它以一个简短的地图开头，说明你需要哪些部分。

## 5. 删除

草稿通常过长，而多余的部分几乎从不包含思考。它们收集在感觉是义务的部分：检查清单答案、测试清单、你已经说过的内容的第二次陈述。这些部分也最容易删除，这使得这一步廉价且值得每次都做。

在开始删除之前，整个主体的粗略锚点：

- 只有测试、配置或机械变更，没有行为变更：简短段落。
- 小变更但有真实风险表面：几百字，几乎都是关于风险而不是 diff。
- 聚焦的修复或功能：四五百字。
- 新机制有消费者：不到一千字。
- 非常大或基础变更：大约一千字，大部分额外内容用于阅读顺序和关注区域。

这些是锚点，不是限制。超过一个意味着仔细查看下面的列表；它永远不意味着删除一个决策。

然后查看每个段落，并命名它帮助审查者做出的决策。如果你无法命名一个，就删除它。通常发现的内容：

- 任何 diff 一眼就能看到的内容。“哈希滚动逻辑被泛化”，“字段被重命名”，每行变更一个要点，锁文件的陈述。例外是看起来是意外的，例如名称与它绑定的内容不一致。审查者能看到它但无法知道它是错误的，所以它保留。
- 对 diff 添加的评论的释义。审查者在原地阅读它们，滚动一次之遥。
- 你添加的测试清单。说明什么*没有*被覆盖，以及变更的大致测试比例。测试函数名称的列表读作填充，尤其是没有结果与之关联时。
- 标准工具行为的解释。Terraform 替换重命名的资源，测试宏如何轮询，React 效果何时触发，库如何生成子进程。解释这个变更，而不是审查者的工具。
- 事实的第二次陈述。数一下：“没有链接的问题”和“没有运行”每个只能出现在一个地方，一个值得陈述两次的事实通常是第一次陈述得不好。
- 只有关联到另一部分描述的句子的唯一工作。单页内的交叉引用意味着内容放在了错误的位置。
- 关于描述本身的句子。“因为这次变更的爆炸半径很大，所以包含审查者指导。”写指导；不要解释它。
- 提交后缀。`Co-Authored-By` 属于提交，而不是 PR 主体。

即使删除困难也要保留：动机、行为变更、决策及其被拒绝的替代方案、开放问题、爆炸半径。这些是描述存在的原因。当必须删除时，先删除机制，再删除决策。

## 6. 自我检查

- 第一段是否让审查者决定 PR 是否是他们的？
- 关于测试的每个声明是否描述了运行的内容，或者明确说明没有运行？
- 你是否验证了从提交信息继承的每个事实性声明？
- 删除是否删除了一个决策、被拒绝的替代方案或开放问题？这些是在压缩时最先消失的，也是最后应该丢失的。将它们放回去。
- 描述是否与分支的当前状态匹配，而不是你到达那里的路径？
- 如果有审查者指导，它是否在顶部？

## 反模式

**叙述分支自己的历史。** 最常见的失败。像“这个 PR 之前包含单元测试，在审查反馈后删除了”，或者“上面的描述高估了这一点并已更正”这样的句子描述了 diff 中不存在的过渡。审查者看到的是当前状态与基础状态。描述那个状态。

注意哪些内容通过了规则：推理通常仍然重要，只有过渡被删除。“测试被删除是因为它们只重新断言匹配臂”变成“这里没有单元测试，因为这一层的测试只会重新断言匹配臂”。

无论分支有多长，它仍然以一个状态到达审查者手中，与基础状态对比。

**重述 diff。** 文件按文件清单是编写长内容的标准方式，而这些内容不携带信息。

**未经验证的声明，关于任何内容。** 膨胀的测试声明是熟悉的案例（“完全测试”，“无回归”），但关于机制的自信错误声明更危险，因为审查者不太可能检查它。在断言角色允许什么、标志控制什么、函数保证什么之前，验证它。

**评价自己的工作。** “全面”，“稳健”，“干净”，“正确”。填充内容会损害信誉。

**教训审查者。** “请检查边缘情况并确保错误处理正确。”一个有能力的审查者已经在做这件事，并且它取代了你只能给出的具体指导。

**留下过时的描述。** 在重做或强制推送后，重写主体以描述当前分支。不要在底部附加修订日志。
