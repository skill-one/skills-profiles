# 对 PR 评论进行回复（黑名单模式）

使用此技能对当前分支上的 PR 评论进行回复。如果评论已经在对话中可见（通常来自内置的 `/pr-comments` 技能），则从该上下文继续。如果评论尚未可见，则先获取并显示它们，然后引导用户逐个处理可操作的评论，收集明确的决定，执行请求的代码更改，然后才请求批准，最后才发布 GitHub 回复或解决评审线程。

## 不应使用此技能的情况

当用户只想获取或显示 PR 评论（使用 `pr-comments`）或只想执行底层代码更改，而无意在 GitHub 上发布回复或解决线程时，请跳过此技能。只有在用户确认要发布回复或解决线程后，才应读取此技能。

## 前置条件

- 在 PR 分支的仓库签出中工作。
- 除非加载的上下文缺少评论正文、作者、URL、路径或行元数据等必要字段，否则不要重新获取评论。
- 在用户最终批准预览之前，不要发布 GitHub 回复、提交评审或解决线程。

如果上下文中没有 PR 评论，则在继续之前获取并显示它们。如果可用，优先调用内置的 `/pr-comments` 工作流。否则使用等效的 GitHub CLI 备用方案：识别当前 PR，获取 PR 级评论，评审评论和评论正文，然后使用 `insert_code_review_comments` 显示它们。显示获取的评论后，在执行更改之前，询问用户是否要继续此回复工作流。

## 评论过滤

在请求回复模式之前，将加载的评论过滤到仍需用户关注的可操作评论。

跳过以下评论，而无需询问用户：

- 来自 Warp/Oz/code-review 机器人的自动 PR 级概述或状态评论，特别是那些没有附加文件位置的评论，这些评论总结了评审状态、检查进度或表示未请求代码更改。
- 已经由当前 GitHub 用户回复的评论。

要识别当前 GitHub 用户，请优先使用：

```sh
GH_PAGER="" gh api user --jq .login
```

对于评审线程，使用 `reply_metadata.parent_comment_id`、线程元数据、解决状态和加载上下文中的评论排序（如果可用）。仅在线程已解决或该线程中最新相关的回复由当前 GitHub 用户编写时，才跳过原始评论和线程。如果审阅者在当前用户的回复后添加了更新的后续评论，请保留该线程在逐步引导中。对于没有明确线程元数据的 PR 级评论，仅在加载的上下文明确显示当前用户已对此特定评论做出回复时才跳过，例如直接回复、引用、链接或立即后续回复引用它。

如果跳过自动或已回复的评论，请保留一个简短的内部分类列表，其中包含评论 URL 和原因。不要为跳过的评论创建决策记录，不要将其包含在每条评论的逐步引导中，除非作为简短的跳过计数摘要包含在最终 GitHub 回复/解决预览中。

当不确定评论是否为自动的、已回复的或仍可操作时，请将其保留在逐步引导中，而不是跳过它。

## 询问用户问题要求

此技能中的每个 `ask_user_question` 调用都必须包含一个使用工具的自由格式“其他...”选项。使用该选项允许用户输入自定义模式、回复、理由、发布说明或下一步操作，而无需在正常聊天中仅为了收集自定义文本而将控制权返回给用户。

## 初始模式选择

在讨论单个评论之前，调用 `ask_user_question` 并仅提出一个模式问题：

- 逐个回复
- 收集所有决定，然后批量处理
- 其他...

使用选定的模式进行其余工作流。

### 逐个模式

对于每个评论，收集用户的决定并立即执行任何请求的代码更改，然后再移动到下一个评论。每次更改后，记录：

- 正在处理的评论
- 更改的代码或文档
- 运行或仍需运行的验证
- 草稿 GitHub 回复以及是否应解决线程

### 批量模式

对于每个评论，交互式地收集用户的决定，但尚未编辑代码。批量模式不会批量或跳过信息收集阶段：用户必须能够请求更多上下文、请求解释、检查引用的代码或为任何单个评论提供自定义方法，然后再做决定。在所有评论都有决定后，批量应用请求的代码更改，然后验证并准备最终的 GitHub 回复预览。

## 每条评论的逐步引导

按显示顺序处理评论。对于每个评论：

1. 简要重述相关上下文：
   - 作者
   - 文件和行或 PR 级位置
   - 当位置元数据可用时，为单行评论格式化为 `path:line` 或为范围评论格式化为 `path:start-end` 的可点击文件引用
   - 评论的简短摘要
   - 任何理解评论所需的明显代码上下文
2. 如果从加载的上下文中不明显，则在呈现选项之前检查相关文件。
3. 使用针对特定评论量身定制的选项调用 `ask_user_question`。

当评论附加到代码时，在询问问题之前打印文件引用，以便用户可以快速打开相关部分。使用仓库相对路径，例如 `src/lib.rs:42` 或 `src/lib.rs:40-48`。对于没有文件位置的 PR 级评论，说明没有附加的代码位置。

始终包含具有以下含义的选项：

- 应用代理为该评论推荐的修复
- 在做决定之前解释该评论的含义
- 承认该评论但不进行代码更改
- 其他...

使用“其他...”选项的自由格式字段进行自定义回复或方法。不要在正常聊天中仅为了收集自定义自由格式文本而将控制权返回给用户。

当用户选择“解释”时，提供关于评论的简洁上下文、审阅者可能提出它的原因以及涉及权衡的信息。然后再次询问相同的评论，并使用更新的选项；不要跳过决定。

此解释循环适用于逐个模式和批量模式。在批量模式中，只有最终的代码编辑和 GitHub 评论更新被延迟；每条评论的信息收集仍然是交互式的。

当用户选择“承认但不更改”时，给他们提供更多关于为何不进行代码更改的信息的机会。保留提供的理由，用于最终 GitHub 回复草稿。

## 决策记录

为每条评论维护一个内部决策记录。每条记录应包括：

- 评论标识符或 URL
- 评论类型：评审线程评论、线程回复、PR 级评论或评审正文
- 选定的处理方式：修复、解释后修复、承认但不更改、自定义或无操作
- 计划的代码更改（如果有）
- 需要的验证
- 草稿回复正文
- 是否应解决评审线程

对于草稿回复，应简洁具体。优先使用说明更改了什么或为何故意不回复评论的回复。为可能发布到 GitHub 的每个草稿回复前缀 `[Warp Agent]`，以便审阅者可以清楚地看到回复是由代理编写的。如果修复已提交并推送，但在发布回复之前，请包含一个链接到已解决评论的提交，以便回复可审计。

## 应用修复

遵循用户选定的模式：

- 在逐个模式中，编辑和验证每个接受的修复，然后再继续到下一个评论。
- 在批量模式中，等待收集所有评论决定后，再一起执行所有接受的编辑。

在执行更改时：

- 仅应用与选定的 PR 评论相关的更改。
- 保留无关的本地更改。
- 遵循仓库特定的编码、测试和样式规则。
- 在每次逐个修复后运行最窄的有用验证，并在所有修复应用后运行最终验证。
- 如果请求的修复不安全、不明确或与另一条评论冲突，请在编辑之前停止并询问用户。

## 最终验证

应用所有接受的修复后：

1. 查看 `git diff` 以确认更改与收集的决定一致。
2. 根据仓库的约定和更改的文件运行相关的格式化、代码检查、类型检查、构建或测试。
3. 如果无法运行验证，请在最终摘要中解释原因，并在预览中包含该例外情况。

除非用户明确要求，否则不要提交更改。

## 提交和推送到 origin 之前发布 GitHub 回复

在验证之后，在发布任何 GitHub 回复或解决评审线程之前，询问用户是否要提交更改并将它们推送到 `origin`。此顺序确保审阅者在看到代理编写的评论回复之前看到推送的代码。

如果处理评论时没有工作区更改，请跳过提交/推送问题，并继续到 GitHub 回复预览。

使用类似以下选项调用 `ask_user_question`：

- 在发布回复之前将这些更改提交并推送到 origin
- 不提交或推送；继续到 GitHub 回复预览
- 在发布 GitHub 回复之前停止
- 其他...

如果用户选择提交和推送：

1. 查看 `git status` 和最终差异，以确保仅包含预期的评论回复更改。
2. 如果尚未明确，请求或建议一个简洁的提交消息；保留“其他...”选项以用于自定义提交说明。
3. 阶段预期的更改，以非交互式命令提交，并将当前分支推送到 `origin`。
4. 在提交消息中包含 `Co-Authored-By: Warp Agent <agent@warp.dev>`（永远不会在 PR 描述中添加它），如果提交已经有一个，则不要再次添加它。
5. 如果提交或推送失败，请在发布 GitHub 回复之前停止并报告失败。

## GitHub 回复和解决预览

在提交/推送决策完成后，在发布任何内容到 GitHub 之前，按评论分组显示预览。对于每个评论包括：

- 评论 URL 或简短标识符
- 操作：仅回复、仅解决、回复和解决或无 GitHub 操作
- 回复正文
- 修复的推送提交链接（当存在时）
- 与该评论相关的验证

然后调用 `ask_user_question` 询问是否要继续：

- 发布回复并解决批准的线程
- 先编辑草稿回复
- 不发布任何内容
- 其他...

如果用户选择编辑，收集他们的编辑，更新预览，并再次询问批准。不要发布，直到用户选择批准选项。

## 使用 GitHub CLI 发布

仅在批准后使用 GitHub CLI。清除所有 `gh` 命令的分页器。

在运行任何发布回复或 PR 评论的 GitHub CLI 命令之前，验证传出正文是否以 `[Warp Agent]` 开头。如果不是，请在发布之前添加前缀。

对于评审评论，使用 REST API 端点发布回复。将回复正文写入临时 JSON 文件，并使用 `--input` 传递它，而不是将响应文本直接放在命令行参数中：

```sh
REPLY_BODY_FILE="$(mktemp)"
cat > "$REPLY_BODY_FILE"
REPLY_PAYLOAD_FILE="$(mktemp)"
python3 - "$REPLY_BODY_FILE" "$REPLY_PAYLOAD_FILE" <<'PY'
import json
import sys
from pathlib import Path

body_file = Path(sys.argv[1])
payload_file = Path(sys.argv[2])
payload_file.write_text(json.dumps({"body": body_file.read_text()}))
PY
GH_PAGER="" gh api \
  --method POST \
  /repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies \
  --input "$REPLY_PAYLOAD_FILE"
rm -f "$REPLY_BODY_FILE" "$REPLY_PAYLOAD_FILE"
```

对于无法直接线程的 PR 级评论或评审正文评论，发布一个正常的 PR 评论，并引用或链接到原始评论：

```sh
REPLY_BODY_FILE="$(mktemp)"
cat > "$REPLY_BODY_FILE"
GH_PAGER="" gh pr comment {pull_number} --body-file "$REPLY_BODY_FILE"
rm -f "$REPLY_BODY_FILE"
```

要解决评审线程，使用 GraphQL。如果线程节点 ID 尚未已知，则查询 PR 的所有评审线程，并将加载的评论 ID 映射到其包含的线程。使用分页，以便第一个 100 个之外的线程仍然可以解决：

```sh
GH_PAGER="" gh api graphql --paginate \
  -f owner="{owner}" \
  -f repo="{repo}" \
  -F number={pull_number} \
  -f query='
    query($owner: String!, $repo: String!, $number: Int!, $endCursor: String) {
      repository(owner: $owner, name: $repo) {
        pullRequest(number: $number) {
          reviewThreads(first: 100, after: $endCursor) {
            pageInfo {
              hasNextPage
              endCursor
            }
            nodes {
              id
              isResolved
              comments(first: 100) {
                nodes {
                  databaseId
                  url
                }
              }
            }
          }
        }
      }
    }'
```

使用以下方式解决批准的线程：

```sh
GH_PAGER="" gh api graphql \
  -f threadId="$THREAD_ID" \
  -f query='mutation($threadId: ID!) { resolveReviewThread(input: { threadId: $threadId }) { thread { id isResolved } } }'
```

如果评论无法通过可用元数据回复或解决，请报告限制并建议手动 GitHub 操作，而不是猜测。

## 最终回复

在发布批准的回复并解决批准的线程后，总结：

- 处理的评论
- 更改的文件
- 验证结果
- 是否将更改提交并推送到 `origin`
- 发布的 GitHub 回复或解决
- 用户需要处理的任何剩余事项
