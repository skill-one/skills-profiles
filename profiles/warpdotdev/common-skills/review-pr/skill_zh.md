# 审核PR技能

审核当前的pull request，并将输出写入`review.json`。

## 背景

- 工作目录是PR分支的检出。
- 工作流程通常会在`pr_diff.txt`中提供注释过的diff。
- 工作流程通常会在`pr_description.txt`中提供PR描述。
- 如果存在`spec_context.md`，则其中包含实现与规范验证的上下文信息。
- 当提示引用`.agents/skills/review-pr/scripts/resolve_spec_context.py`时，使用该脚本按需将`spec_context.md`具体化，而不是期望规范内容嵌入在提示中。
- 关注此PR更改的文件和行。
- 不要直接向GitHub发布评论或审核。

## 审核范围

- 优先考虑正确性、安全性、错误处理和有意义的性能问题。
- 将评论质量和测试质量视为与这些同等的一流审核优先级——不是仅在有时间的情况下才提及的可选小问题；在最终确定你的结论之前，请根据存储库自己的规范检查两者。
- 如果消费存储库提供本地`security-review-pr`辅助技能或提示请求安全检查，则将其作为代码PR的补充指导，并将任何安全发现合并到相同的`review.json`中，而不是发出单独的输出。
- 当存在`spec_context.md`时，如果可用，使用存储库本地的`check-impl-against-spec`技能，并将具体的规范漂移视为审核问题。
- 仅在你可以提供具体的建议块时才包含样式或小问题评论。
- 如果问题涉及未更改的代码，请在顶层`body`中提及，而不是内联评论。
- 不要建议添加仅更改构造函数输入或结构字段的测试用例，当现有测试已经涵盖有意义的行为了。仅在它们执行不同的代码路径或边缘情况时才建议新测试。
- 当PR明显是V0或初始实现时，将稳健性建议（超时、重试、生命周期管理）作为可选的未来工作，而不是阻止性问题，除非它们有风险影响正确性、安全性或数据丢失。

## 存储库特定指导

在审核之前，主动检查消费存储库是否提供专门针对其自身规范的`review-pr-local`辅助技能：如果提示命名了一个，则在其中读取；否则在存储库中查找（例如，在`.agents/skills/review-pr-local/SKILL.md`，尽管存储库可能以不同的方式放置或命名其专门化）。如果存在辅助技能，请读取它并将其指导作为此审核的一部分应用。无论如何都没有找到，则仅依赖核心契约。

辅助技能预期会用存储库自己的规范专门化此技能的评论和测试指导。它永远不会更改输出JSON模式、严重性标签、安全规则、证据规则、建议块约束或在此技能中描述的其他diff行注释契约。

## Diff行注释

diff文件使用这些前缀：

- `[OLD:n]`表示旧侧的删除行。使用`"LEFT"`。
- `[NEW:n]`表示新侧的添加行。使用`"RIGHT"`。
- `[OLD:n,NEW:m]`表示未更改的上下文。使用`"RIGHT"`与行`m`。

将这些注释视为内联评论位置的唯一来源。对于你发出的每个内联评论，首先在`pr_diff.txt`（或内联PR diff）中识别确切的注释行，并将其路径、侧和行号复制到`review.json`中。不要从散文、渲染的GitHub视图、文件长度、周围的规范文本或未注释的片段中推断行号。如果你无法在注释diff中指向特定的`[NEW:n]`、`[OLD:n]`或`[OLD:n,NEW:m]`行，请将反馈放在顶层`body`中，而不是`comments`。

## 评论要求

每个评论正文必须以以下标签之一开头：

- `🚨 [CRITICAL]`用于错误、安全问题、崩溃或数据丢失。
- `⚠️ [IMPORTANT]`用于逻辑问题、边缘情况或缺失的错误处理。
- `💡 [SUGGESTION]`用于值得改进或更好的模式。
- `🧹 [NIT]`仅当评论包含建议块时用于清理。

对存储库评论或测试指南的确认违规可以单独获得`⚠️ [IMPORTANT]`——无论PR的其余部分有多干净。不要因为周围的代码看起来不错就默认这些为`🧹 [NIT]`/`💡 [SUGGESTION]`。

使用这些约束编写评论：

- 保持简洁、直接和可操作。
- 不要添加赞美或含糊其辞。
- 优先使用单行评论。
- 保持范围最多10行。
- 限制内联评论仅限于在注释PR diff中明确出现的行。
- 仅对PR diff中存在的文件创建文件级或内联评论。
- 如果相关文件或行不是diff的一部分，请将反馈放在顶层`body`中，而不是`comments`。
- 在添加每个评论对象之前，验证其`path`、`side`、`line`和可选的`start_line`/`start_side`是否与同一文件的diff部分中的真实注释对应。

## 建议块

当提议代码更改时，使用：

```suggestion
<在此处替换代码>
```

规则：

- 匹配原始文件的完全缩进。
- 仅包含替换代码。
- 块内容替换**正好**行`start_line`–`line`（含）。块内的每一行都成为该范围内的新文件内容，GitHub将保留所有其他行不变。
- **不要**包含该范围之外的行。行`start_line`以上和行`line`以下保持不变；在建议提交后，在块内重复它们会导致它们出现两次。
- 永远不要以立即出现在`start_line`上方的行开头块，也永远不要以立即出现在`line`下方的行结束块。如果你需要这些行作为锚点，请扩大`start_line`或`line`，以便它们实际上是替换范围的一部分。
- 计算原始替换行中的大括号、方括号、括号和块分隔符深度（`{`、`[`、`(`、`end`等），并确保替换在相同的深度结束。不要发出幽灵关闭标记，也不要遗漏必需的标记。
- 当不确定周围上下文时，扩大`start_line`/`line`以包含足够的真实行，而不是猜测周围的标记。
- 对于多行建议，将`start_line`和`start_side`设置为第一行，将`line`和`side`设置为最后一行。

## 输出格式

创建具有此结构的`review.json`：

```json
{
  "verdict": "REJECT",
  "body": "## 概述\n...\n\n## 关注点\n- ...\n\n## 结论\n发现：1个严重问题，2个重要问题，3个建议\n\n**请求更改**",
  "comments": [
    {
      "path": "path/to/file",
      "line": 42,
      "side": "RIGHT",
      "start_line": 40,
      "start_side": "RIGHT",
      "body": "⚠️ [IMPORTANT] 简短解释\n\n```suggestion\n替换\n```"
    }
  ]
}
```

字段规则：

- `verdict`是必需的，必须完全是大写的字符串`"APPROVE"`或`"REJECT"`。将你的最终建议映射为：`Approve`或`Approve with nits` → `"APPROVE"`；`Request changes` → `"REJECT"`。`verdict`和顶层`body`中的人类可读建议必须一致。
- 顶层`body`是GitHub评论正文，是必需的。使用`body`而不是`summary`进行评论概述和最终建议。
- `comments`是必需的，必须是一个数组。在没有内联评论时使用空数组。
- `path`必须相对于存储库根目录。
- `line`是必需的，必须针对正确的侧。
- `start_line`是可选的，仅用于多行范围。当`start_line`存在时，`start_side`是必需的，必须是`"LEFT"`或`"RIGHT"`。
- `side`必须是`"LEFT"`或`"RIGHT"`。

## body要求

顶层`body`必须包括：

- PR的高级概述。
- 重要关注点以及无法内联评论的未更改代码关注点。
- 格式为`发现：X个严重问题，Y个重要问题，Z个建议`的问题计数。
- 最终建议为`Approve`、`Approve with nits`或`Request changes`。此建议必须与顶层的`verdict`字段（`Approve` / `Approve with nits` → `"APPROVE"`；`Request changes` → `"REJECT"`）匹配。

## 预审核审计

在起草顶层`body`或选择`verdict`之前，完成此审计——全面的diff阅读是不充分的。

- **评论**：逐个列出diff添加或更改的每个评论（文档评论或内联），并附带其文件：行。对于每个评论，单独检查它是否符合存储库自己的评论指南，无论其形式如何——或者，如果存储库未定义任何指南，则根据项目现有代码的评论分布（密度、语气、现有评论解释的内容与省略的内容）进行判断。独立评估是否符合适用指南的违规，或与代码库自己的规范明显不匹配：这些品质都不能解释适用指南的违规或与代码库自己的规范明显不匹配。

- **测试**：检查diff添加或更改的每个测试是否符合存储库自己的测试指南，无论其形式如何。

## 最终检查

在返回或上传`review.json`之前：

- 如果验证失败，修复无效的JSON。
- 确认行号与注释diff匹配。
- 运行捆绑的验证器针对你审核的确切注释diff：
    ```sh
    python3 .agents/skills/review-pr/scripts/validate_review_json.py --review-json review.json --diff pr_diff.txt
    ```
  如果脚本报告任何无效评论，请修复`review.json`并重新运行它。在脚本通过验证之前，不要返回或上传`review.json`。如果脚本路径不在该确切位置，请在加载的`review-pr`技能目录下找到`validate_review_json.py`副本，并使用相同的参数运行它。
- 不要运行`gh pr review`、`gh pr comment`、`gh api`或任何其他向GitHub发布的命令。

你的唯一输出是最终的`review.json`。
