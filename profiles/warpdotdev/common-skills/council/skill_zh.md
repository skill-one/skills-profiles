# 理事会

使用此技能协调多个子代理调查同一问题，优先考虑不同模型，其次考虑不同的分配视角，然后将他们的报告综合成一个建议。

此技能最适合判断性强的任务：架构权衡、有风险的错误修复、代码评审红队演练、发布决策、事件分析以及“这个替代方案是否值得追求？”等问题。

## 工作流程

### 1. 设定理事会问题

用一句话陈述理事会需要回答的决策。确定：

- 审查中的竞争选项或假设；
- 要检查的代码库、分支、PR、问题、设计或工件；
- 代理是否应该是只读的或可以修改代码；
- 最终决策标准，如正确性、风险、实施成本、可测试性、发布安全性或产品行为。

如果用户的请求不明确，只问最少的澄清所需。否则选择合理的默认值并继续。

### 2. 选择理事会成员

优先考虑模型多样性。理事会不应默认使用同一模型上的三个代理，而应使用不同角度；仅在可用启动配置无法提供多个有用模型时，或用户明确要求一个模型时才使用。如果模型多样性不可用，则简短说明后再回退到仅视角多样性。

三个成员理事会的首选默认阵容：

- Opus 4.7 或最强的可用 Claude/Opus 推理模型：架构、正确性和边缘情况分析。
- GPT 5.5 或最强的可用 GPT/Codex 模型：基于实现的评审、可行性和测试策略。
- Kimi 2.6、GLM 5.1 或最强的可用 OSS/本地模型：反方批评、隐藏假设和替代框架。

如果这些确切模型在活动 harness 中不可用，则使用该系列的最近可用模型并注明替代。如果没有开源模型可用，如果可能，则使用第三个不同的前沿模型；否则使用最强的剩余模型，并带有故意对抗或专业角度。

为每个成员分配模型和角度。避免使角度与模型重复；例如，不要要求所有成员进行一般架构评审。有用的角度组合包括：

- 架构师/正确性评审员；
- 实现/可测试性评审员；
- 红队、安全、性能或产品风险评审员；
- 反方“反对明显解决方案”评审员。

当不同的子代理需要不同的模型时，在单独的 `run_agents` 调用中启动它们，因为模型选择是全局范围的。如果请求的模型与预期不同，则将解析的启动设置视为权威，除非它们使任务不可行。

在使用非默认 harness 时，为该 harness 选择有效的模型 ID。例如，Claude Code 可能会暴露 `claude-opus-4-7`，Codex 可能会暴露 `gpt-5.5`，而开源模型取决于当前配置的本地或远程提供者。不要编造不支持的模型 ID；如果所需的模型不可用，则选择最接近的受支持替代品并保留预期的角度多样性。

对于只读调查，将所有子代理保持在同一 checkout 中，并明确告诉它们不要修改文件。对于实施或原型设计理事会，为每个本地子代理提供自己的 git 工作树和分支，以便它们不会冲突。

### 3. 启动前简报

对于明确的编排请求，在调用 `run_agents` 之前，简要告诉用户您计划启动哪些理事会成员以及每个成员将调查什么，然后等待批准。

共享简报应包括：

- 仓库路径或工件位置；
- 当前分支或基础上下文；
- 要回答的确切问题；
- 相关背景和已知问题；
- 需要检查的文件/符号，如果已知；
- 限制，尤其是只读/不提交/不打开 PR；
- 预期报告格式。

保持启动提示足够简短，以便任务标题保持紧凑。如果长简报导致启动验证问题，则使用最小提示启动，并在之后立即将完整简报发送给子代理。

### 4. 要求结构化报告

要求每个理事会成员返回：

1. 检查的确切文件路径、符号、文档或证据；
2. 当前行为或当前实现；
3. 正在评估的替代方案；
4. 正确性风险和边缘情况；
5. 实施和测试成本；
6. 建议：保持当前方法、追求替代方案或使用混合方案；
7. 置信度水平和未知因素。

鼓励独立性。除非您有意进行第二轮批评，否则不要将一个子代理的发现与其他成员共享。

### 5. 收集报告

在完成消息到达时阅读。不要仅依赖生命周期成功；有用输出在子代理的报告。

如果报告缺少关键证据或做出了不受支持的声明，则向同一子代理发送有针对性的后续问题，而不是启动替代方案。因为它们保留了上下文，所以重用现有子代理进行后续问题。

### 6. 综合建议

通过证据质量而不是投票数来比较报告。在最终答案中：

- 首先提出建议；
- 指出共识和分歧；
- 解释为什么建议的选项在决策标准中胜出；
- 明确解决用户提出的关注点；
- 包括相关文件路径/符号，但不要使答案过载；
- 区分“立即执行”与可选的未来加固；
- 提及置信度和大额未知因素。

优先选择简洁的决策备忘录而不是转录摘要。用户需要提炼的建议，而不是每个中间细节。

## 最终答案模板

除非任务要求不同，否则使用此格式：

```markdown
## 建议

[一个或两个句子的决策。]

## 原因

- [关键原因 1]
- [关键原因 2]
- [关键原因 3]

## 权衡和风险

- [风险或注意事项]
- [测试/发布影响]

## 最终决定

[具体的下一步：合并当前更改、追求替代方案、混合方案、运行测试等。]
```

## 实用提示

- 如果理事会是只读的，告诉子代理不要修改文件、提交、创建分支或打开 PR。
- 如果理事会涉及 PR 或分支工作，请遵循仓库的正常版本控制规则，并使用隔离的工作树进行并行本地编辑。
- 如果理事会是关于代码评审反馈，只有在底层问题实际解决后，才标记评审评论为已解决。
- 除非用户明确要求，否则不要在用户界面摘要中暴露内部子代理 ID。
