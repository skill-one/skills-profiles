# write-feature-docs

为新的 Warp 功能起草完整的文档页面。您需要阅读该功能的规范，通过自己研究代码库来验证技术声明，确认内容设计计划并与工程师确认大纲，然后才能生成完整的 MDX 草稿并在 `warpdotdev/docs` 中打开草稿 PR——并标记文档团队进行审核。

工程师的工作是确认您无法从规范和代码中验证的内容——不是进行全面的准确性审核，不是润色文字，也不是了解文档规范。

## 工作流程

1.  找到并阅读规范文件
2.  研究代码库以验证技术声明——尽量减少工程师需要检查的内容
3.  展示内容设计计划并等待确认——页面是面向谁的
4.  展示大纲并等待确认——页面将包含什么内容
5.  生成完整的 MDX 草稿
5.5. 尝试通过计算机使用进行屏幕截图（如果可用）
6.  在 `warpdotdev/docs` 中打开草稿 PR 并标记文档团队

步骤 3 和 4 是**两个独立的确认，按顺序进行**。大纲是从计划中派生的——计划选择内容类型，内容类型决定了大纲包含哪些部分。将它们一起展示会给工程师一个基于他们尚未同意的受众构建的大纲，他们会锚定具体的大纲而不是重新考虑上面的问题。先确定页面面向谁，然后再决定里面包含什么内容。

---

## 步骤 1：找到并阅读规范

如果工程师没有提供规范 ID，请向工程师询问规范 ID。规范 ID 是：

- 线性工单号：`APP-1234`、`REMOTE-1234`、`QUALITY-408`
- GitHub 问题（以 `gh-` 开头）：`gh-4567`
- 短的 kebab-case 功能名称：`vertical-tabs-hover-sidecar`

在以下位置查找规范文件：

- `specs/<id>/PRODUCT.md`——主要来源：用户界面行为，是什么以及为什么
- `specs/<id>/TECH.md`——次要来源：实现，数据模型

如果两个文件都存在，请阅读它们。`PRODUCT.md` 是文档内容的主要驱动因素。

**阅读 `TECH.md` 时：** 在将其中的任何内容纳入文档之前，识别看起来像内部实现细节的内容——数据库模式、内部服务名称、私有 API 端点、机密服务器架构。将标记的项目展示给工程师并询问他们哪些内容可以安全地包含在公共文档中，哪些内容应保持内部。不要包含任何标记为机密的内容在草稿中。

这个确认是为什么这项技能需要一位在场的工程师。没有无人看管的路径：如果没有某人来说明哪些内容可以发布，`TECH.md` 的内容根本无法起草。

如果这两个文件都不存在，请跳转到 [No-spec fallback](#no-spec-fallback)。

---

## 步骤 2：研究代码库

在展示计划或大纲之前，使用 GitHub CLI 尽可能自己验证尽可能多的技术内容——将工程师需要确认的内容减少到您确实无法从代码中确定的那些。

从代码中需要验证的内容：

- **功能标志名称**：从规范标题或工单中搜索一个安全的特征标记。在进行任何 shell 使用之前，将其减少为一个匹配 `^[A-Za-z0-9][A-Za-z0-9_-]*$` 的允许标记，如果您无法安全地生成一个，则跳过 shell 搜索；然后运行 `FEATURE_TOKEN="<validated-token>" && gh search code "${FEATURE_TOKEN}" --repo warpdotdev/warp-internal`。
- **UI 字符串**：搜索规范中引用的用户可见按钮标签、菜单项名称或设置名称
- **设置路径**：确认确切的设置菜单路径（例如，`**设置** > **AI** > **知识**`）
- **规范中提到的 CLI 命令或键盘快捷键**
- **相关功能**：识别其他与该功能交叉引用的功能以用于“相关页面”
- **需要标记的工程师**：识别拥有规范的 GitHub 处理器的工程师。
  - *交互模式*：运行 `gh api user --jq .login` 获取当前运行该技能的人的处理器——仅在规范工程师直接调用该技能时使用此方法。如果由文档团队成员或非作者运行该技能，请使用下面的发现步骤代替。
  - *非作者运行（文档团队成员或未编写规范的任何人）*：在运行任何查找命令之前，验证规范 ID 仅包含字母数字字符和连字符（匹配 `^[A-Za-z0-9][A-Za-z0-9-]*$`）。如果规范 ID 包含任何其他字符，则完全跳过查找并使用 `[TODO: tag spec author]` 作为占位符。如果规范 ID 有效，请将其分配给 `SPEC_ID` 并按顺序处理这些步骤，找到处理器后停止：
    1. **检查提交消息中的 `Co-authored-by:` 尾部**——在从私有源镜像的存储库（如 `warp-internal`）中，同步机器人是提交作者，但真正的作者出现在 `Co-authored-by:` 尾部中。提取第一个非机器人条目：
       ```bash
       git log --follow -1 --format="%B" -- "specs/${SPEC_ID}/PRODUCT.md" \
         | grep -i "^Co-authored-by:" \
         | grep -v "\[bot\]" \
         | head -1 \
         | grep -oP '<[^>]+>' | tr -d '<>'
       ```
       这返回一个电子邮件（可能是 GitHub 的 noreply 地址）。如果电子邮件匹配模式 `<userid>+<username>@users.noreply.github.com`，则直接提取处理器：`echo "$EMAIL" | grep -oP '\+\K[^@]+'`。如果是真实电子邮件，则通过 `gh api "search/users?q=${EMAIL}+in:email" --jq '.items[0].login'` 解析它。
    2. **解析同步的 PR URL**——某些同步机器人将原始 PR URL 嵌入提交正文（例如 `Synced from warp: https://github.com/warpdotdev/warp/pull/11901`）。提取它并获取 PR 作者：
       ```bash
       ORIG_PR=$(git log --follow -1 --format="%B" -- "specs/${SPEC_ID}/PRODUCT.md" \
         | grep -oP 'https://github\.com/[^/]+/[^/]+/pull/\d+' | head -1)
       # 提取所有者/存储库和 PR 号，然后：gh pr view <N> --repo <owner/repo> --json author --jq '.author.login'
       ```
    3. **搜索原始存储库的 PR**——尝试实际拥有代码的存储库（检查公共镜像和如果可访问的私有源）：
       ```bash
       gh pr list --search "specs/${SPEC_ID}" --repo warpdotdev/warp-internal --state merged --json author --limit 1 --jq '.[0].author.login'
       # 也尝试：gh pr list --search "specs/${SPEC_ID}" --repo warpdotdev/warp --state merged --json author --limit 1 --jq '.[0].author.login'
       ```
       跳过登录名包含 `[bot]` 的任何结果。
    4. **回退到提交作者电子邮件**——仅在电子邮件不包含 `[bot]` 时：
       ```bash
       EMAIL=$(git log --follow -1 --pretty=format:"%ae" -- "specs/${SPEC_ID}/PRODUCT.md")
       ```
       如果 `${EMAIL}` 非空且无机器人，则通过 `gh api "search/users?q=${EMAIL}+in:email" --jq '.items[0].login'` 解析它。
    5. 如果在所有步骤后都没有找到处理器，请在 PR 正文中使用 `[TODO: tag spec author]` 作为占位符。

对于您从代码中验证的每个声明，请标记为已确认。对于您无法验证的声明（代码中未出现的 UI 行为、产品意图、未发布功能的行為），请在大纲中标记为 `[UNVERIFIED]`——这些是工程师需要关注的东西。

## 步骤 3：展示内容设计计划并等待

**这是两个确认中的第一个，并且在大纲之前。** 在决定里面包含什么内容之前，先确定页面面向谁。

填写 `.agents/templates/content-design-plan.md` 从文档存储库，使用 `.agents/references/content-design-plan.md` 来了解每个字段的要求：受众和 JTBD、问题、目标、目的和价值、内容类型、技能和模板，以及具有明确排除的高影响场景。

将其打印到终端，然后说：

> "在我想概述页面之前，请确认这是正确的读者和正确的工作。更正任何不正确的地方，或者说'看起来不错'，我将起草大纲。"

**等待工程师的回复。** 不要在同一个消息中生成大纲。计划决定了内容类型，内容类型决定了大纲包含哪些部分——将大纲与未经确认的计划一起展示会邀请工程师锚定他们面前的具体部分，而不是重新考虑上面的受众。

如果他们更改受众、内容类型或范围，请在继续之前修订计划并重新确认。将确认的计划带到 PR 正文中的步骤 6。

---

## 步骤 4：展示大纲并等待

根据步骤 3 确认的计划生成简洁的大纲——没有散文——基于已确认的计划。大纲显示了您从研究中确认的内容以及确切需要工程师输入的内容。

以以下格式将大纲打印到终端：

```
📄 用于 [Feature name] 的文档大纲

建议放置
  部分： src/content/docs/<section>/   （例如，agent-platform/cloud-agents/）
  文件： <feature-name>.mdx
  URL： docs.warp.dev/<path>/<feature-name>

内容部分
  标题： <Feature name>   （frontmatter；Starlight 将其渲染为 H1）
  开头段落： [1 句话描述您将写的内容]
  ## 关键功能 — [突出显示 2-4 个功能的要点]
  ## 工作原理 — [概念模型：是什么和为什么，没有步骤]
  ## <使用部分标题> — [例如，“创建环境”，“配置 X”]
      前提条件： [列出任何前提条件]
      步骤：
        1. [步骤描述]
        2. [步骤描述]
        3. [步骤描述]
        ...
  ## 相关页面 — [建议的交叉链接]
```

> 上述部分是默认值。根据功能调整大纲：如果功能不需要概念解释，请省略 `## 工作原理`；如果功能具有不同的工作流程，请添加多个使用部分；如果功能足够简单，请将 `## 关键功能` 折叠到开头段落中。

```
从代码库中确认 ✅
  - [例如，“在 warp-internal 中确认功能标志：`my_feature_flag`”]
  - [例如，“设置路径：确认为设置 > AI > 代理 > 权限”]

需要您的确认 ⚠️
  - [例如，“步骤 3——同步是自动触发还是需要手动操作？”]
  - [例如，“在功能标志启用之前，'导出'按钮是否可见？”]
```

打印大纲后，说：

> "我已经从代码库中验证了尽可能多的内容。请检查上面标记为 ⚠️ 的项目并回复任何更正，或者说'看起来不错'以继续。"

在继续之前等待工程师的回复。根据他们的反馈进行修订，然后起草。

如果他们的反馈与步骤 3 中确认的计划相矛盾——不同的读者、不同的内容类型——请修订计划，而不是让两者分道扬镳。计划将进入 PR 正文，因此过时的计划会误导审阅者。

---

## 步骤 5：生成 MDX 草稿

根据确认的大纲生成完整的 `.mdx` 文件。输出可以直接放入 `warpdotdev/docs`。

### 模板结构

**使用文档存储库中 `.agents/templates/` 的规范模板**——`feature-doc.md`、`conceptual.md`、`procedural.md`、`reference.md`、`troubleshooting.md`、`quickstart.md` 或 `guide-page.md`。这些是事实来源，并且它们带有自己的字段指导。下面的草图显示了最常见的功能文档的形状，以便您知道要期待什么；它不是阅读真实模板的替代品。

模板强制执行的规则很容易从记忆中出错：页面标题放在 **frontmatter** 中，而不是正文 H1（Starlight 将 frontmatter 标题渲染为 H1，因此正文 H1 会重复它），并且每个括号指令在页面发布前必须删除。

```mdx
---
title: [Feature name — 句子大小写]
description: >-
  [1-2 句话的独立摘要。以用户利益开头。包括功能名称和几个关键术语，以便它作为搜索结果片段工作。]
---

[开头段落：您将写的内容的 1-3 句话。以用户可以完成的事情开头，而不是实现。]

:::note
[可选：读者需要 upfront 的关键上下文——前提条件、限制或何时不使用此功能。如果没有适用，请删除此调用。]
:::

## 关键功能

* **功能 A** - 它做什么以及为什么对用户很重要。
* **功能 B** - 它做什么以及为什么对用户很重要。

## 工作原理

[概念部分：解释系统行为、数据流或架构。在“如何”之前回答“什么”和“为什么”。当它们第一次出现时定义任何新术语。不要在此部分包含分步程序——将概念和程序内容清晰分开。]

## [使用部分标题]

[程序部分：首先说明任务，然后给出编号步骤。在告诉用户如何做之前，简要解释用户为什么要做这个任务。]

### 前提条件

* **[前提条件]** - 它是什么以及在哪里获取。参见 [完整参考](link-here).

### [任务名称 — 句子大小写，例如，“使用 CLI 创建环境”]

1. 第一步。如果结果不明显，则预期结果。
2. 第二步。
3. 第三步。

## 相关页面

* [相关功能](../path/to/page.md)
* [更深入的指南](../path/to/guide.md)
```

### 样式规则——准确应用

这些约定来自 Warp 文档样式指南，并且必须遵循：

**标题**
- 所有标题使用句子大小写：仅首字母大写和专有功能名称
- 专有功能名称保留其大小写："Agent Mode"、"Warp Drive"、"Oz"、"Command Palette"
- ✅ `## 工作原理` — ❌ `## How It Works`
- ✅ `## Agent Mode settings` — ❌ `## Agent mode settings`

**列表**
- 粗体术语 + 短横线 + 描述：`* **术语** - 描述`
- 不要使用冒号：❌ `* **术语**: 描述`

**UI 元素和路径**
- 粗体按钮、链接、菜单项：`点击 **保存**`，而不是 `` 点击 `保存` ``
- 粗体设置路径中的每个部分，`>` 保持简单：`**设置** > **AI** > **知识**`

**声音和语气**
- 第二人称： "你可以," "允许你"
- 主动语气： "Warp 索引你的代码库" — 不是 "你的代码库被索引"
- 避免使用 "简单"、"容易"、"只是" —— 这些会轻视读者的体验
- 使用现在时态描述事物如何工作；使用祈使语气描述指令

**frontmatter 描述**
- 写作一个独立的摘要，它可以用作搜索结果片段
- 以用户利益开头，包括功能名称和几个关键术语
- ✅ `Environments 确保您的云代理使用一致的工具链。学习何时使用环境以及如何配置它们。`
- ❌ `此页面描述环境。`

**调用语法**（Astro Starlight）
- `:::note` — 补充上下文、提示
- `:::caution` — 备注和限制
- `:::danger` — 具有破坏性或不可逆的操作
- `:::tip` — 有用的提示和最佳实践

**要作为 `[TODO: docs reviewer — ...]` 占位符保留的内容**
- 计算机使用失败质量门、不可用或功能尚未发布的屏幕截图
- 视频/GIF 嵌入
- 最终设置路径（文档团队确认位置）
- 任何在工程师确认后仍然未经验证的行为

## 步骤 5.5：通过计算机使用捕获屏幕截图（如果可用）

生成草稿后，尝试使用计算机使用捕获任何 `[TODO: docs reviewer — screenshot needed]` 占位符的屏幕截图。此步骤是**可选的**——仅在 `computer_use` 工具可用时才运行。如果计算机使用不可用，请将所有占位符保留为原样。

### 决定尝试哪些屏幕截图

仅尝试屏幕截图，其中**所有**以下情况都为真：

- 功能已经发布（不是在功能标志或未发布）
- UI 状态可以靠程序可靠地导航
- 占位符指定了具体的 UI 表面（而不是像“显示功能工作”这样模糊）

跳过需要特定帐户状态、特定数据或可能暴露敏感信息的内容的屏幕截图。

### 捕获前的设置

在捕获任何屏幕截图之前：

1. 以一致窗口大小启动 Warp（使用 `warp-internal-computer-use` 技能获取启动指导）
2. 导航到相关的 UI 表面或触发相关的功能状态
3. **等待** 所有动画完成并且 UI 完全稳定
4. 关闭任何与功能无关的弹出窗口、通知或提示，这些不是功能文档的一部分
5. 关闭任何与此屏幕截图不相关的侧边栏面板或窗格
6. **验证没有显示敏感数据**：检查是否有令牌、API 密钥、私有存储库名称、客户工作区数据、电子邮件地址或个人信息。如果任何内容可见，请不要捕获屏幕截图。

### 捕获协议：预测 → 捕获 → 验证 → 重试一次

这是一个结构化的自我验证循环。不要跳过它——它是防止错误状态、错误裁剪和错误框架捕获的主要保护。

**步骤 1：在捕获之前陈述预期结果**

在捕获任何屏幕截图之前，写出您预期的内容：

```
捕获预期
  主题：            [正在文档中记录的特定 UI 元素或表面]
  预期元素：  [2-3 个必须可见的特定内容 — 例如，面板标题、按钮、特定设置]
  预期状态：     [UI 状态 — 例如，“设置面板打开”、“模态可见”、“功能激活并显示输出"]
  必须不包含：   [任何必须不显示的内容 — 例如，敏感数据、不相关的弹出窗口、加载旋转器]
```

**步骤 2：捕获**

捕获屏幕截图。

**步骤 3：查看并对照预期结果**

使用计算机使用查看捕获的图像，然后将其与预期结果进行对照：

- 是否**主题**可见且清晰是焦点？
- 是否所有**预期元素**都存在？
- UI 是否处于**预期状态**（不是过渡状态或加载状态）？
- 是否有任何**必须不包含**的内容可见？
- 文本在目标显示宽度下是否**可读**？

如果所有内容都通过 → 进入质量门。

如果任何内容失败 → **尝试一次更多**：重新导航到 UI 状态，等待更长时间让 UI 稳定，然后重新捕获和重新验证。

如果第二次尝试也失败 → **丢弃**屏幕截图并保留 `[TODO: docs reviewer — screenshot]` 占位符。不要包含您无法验证的屏幕截图。

**步骤 4：质量门——包含在包含之前进行最终检查**

- [ ] 屏幕截图中的文本在目标显示大小下是**可读**的
- [ ] 文档的 UI 元素是**清晰地焦点** — 不是埋藏、裁剪或遮挡
- [ ] **没有敏感数据**可见（令牌、私有存储库、个人信息、客户数据）

- [ ] 屏幕截图在其目标渲染宽度下看起来不会模糊或过大

> **每个屏幕截图的最大尝试次数：2。如果两次都失败，请继续。**

### 尺寸——选择最接近的标准宽度

- **全宽（默认）** — 全窗口捕获，广泛的 产品表面，周围上下文很重要的布局
- **~375px** — 窄 UI 表面：弹出窗口、命令菜单、侧窗格、下拉菜单、专注于交互流程
- **~300–350px** — 紧密裁剪的控件、芯片、按钮、工具提示、小型菜单

在调整尺寸之前裁剪不必要的空白空间。将同一部分中的屏幕截图保持在相同的宽度。

### 位置——在哪里在 MDX 中插入屏幕截图

将每个屏幕截图：
- **立即在**介绍 UI 或状态的段落之后
- **在配置说明附近** — 显示设置面板或菜单，用户在其中做出选择
- **在状态或结果解释附近** — 显示完成状态或输出，帮助用户识别成功
- **在视觉功能页面的开头** — 使用宽定向屏幕截图

**不要**为每个步骤添加屏幕截图。仅在视觉确实有助于理解时才添加。
