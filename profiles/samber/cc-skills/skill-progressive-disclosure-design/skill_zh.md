# 技能渐进式披露设计

每个推荐方向的部分都包含明确的优缺点。这项技能中的决策是权衡取舍，而不是规则。使用这项技能的模型应该从权衡中推理到用户的具体情况，而不是盲目地应用规则。

## 触发与披露：首先区分这两者

有两个问题被混淆在一起，在做出任何拆分决策之前需要将它们区分开来。

**触发**是指Claude是否调用该技能。这完全由YAML `description`驱动。文件拆分不会影响触发。如果问题是“我的技能触发不可靠”，请不要拆分文件，修复描述（使用`run_loop.py`从`skill-creator`技能）。

**渐进式披露**是指技能激活后加载的内容。SKILL.md正文始终加载。`references/*`仅在SKILL.md指示模型读取特定文件时才加载。`scripts/*`完全不会加载到上下文中。这是上下文保护发生的地方。

如果用户是因为触发问题而询问拆分，请首先暴露这种混淆，然后进行重定向。

## 默认：不拆分

单体SKILL.md优于拆分的SKILL.md，直到被证明相反。

仅在至少满足以下一项时才拆分：

- SKILL.md超过~400行，并且内容具有自然的分支。
- 经验证据（评估转录）表明模型在无关部分上浪费了上下文。
- 特定内容很大，并且仅在狭窄条件下需要。

**保持单体的优点：**

- 单一上下文加载，无需维护路由说明。
- 无需从读取参考资料中产生工具调用开销。
- 无模型加载错误参考资料或跳过所需参考资料的风险。
- 更容易维护：一个文件，一个事实来源。
- 更适合高度相互关联的内容，其中上下文是全局的。
- 更便于人类审阅者端到端阅读。

**保持单体的缺点：**

- 每次调用都支付全部代币成本，即使只有10%的内容相关。
- 超过~500行后无法扩展，否则会降低模型找到重要内容的能力。
- 没有机制来控制罕见或专业的內容。
- 所有内容都必须证明其始终加载的状态。
- 随着文件的增长，维护变得更加困难。

## 三个有效的拆分轴

### 1. 变体分支

用户意图选择确切的一条路径。SKILL.md包含决策逻辑和共享工作流。每个`references/<variant>.md`包含路径特定的详细信息。

```
my-skill/
├── SKILL.md               # 决策树 + 共享步骤
└── references/
    ├── variant-a.md
    ├── variant-b.md
    └── variant-c.md
```

干净的变体示例：云服务提供商、数据库引擎、框架选择、输出格式、语言。

**优点：**

- 每次调用仅加载匹配的变体；当变体很大时，可以节省大量内容。
- 变体可以独立演进，简化维护。
- 添加新的变体不会使现有内容膨胀。
- 思维模型简单：根据输入选择一条路径。
- 与用户已经提到变体的意图完美映射。

**缺点：**

- 需要在SKILL.md中实现路由逻辑，从而抵消部分行节省。
- 跨越主题的更改会影响每个变体文件，增加工作量。
- 随着时间的推移，治疗措施在不同变体之间可能分化。
- 如果用户意图不明确，模型可能会加载多个变体并失去节省。
- 如果变体共享超过~60%的内容，抽象将失效。

### 2. 工作流与参考数据

SKILL.md包含程序（动词、顺序、决策）。`references/`包含键查询的查找材料。

好的参考内容：模式、错误代码表、API表面列表、示例画廊、配置选项矩阵、设计令牌。

**优点：**

- 所有拆分中杠杆最大的：查找范围狭窄，模型读取一个条目。
- 自然的概念边界（程序与数据）。
- 参考内容可以增长而不会影响每次调用的成本。
- 添加新的参考条目不会触及工作流。
- 参考数据通常可以机器生成并重新生成。

**缺点：**

- 模型必须在读取之前知道要查找什么。指针必须明确编码查找键。
- 当工作流需要在离散点而不是内联编织参考数据时，会失败。
- 将概念上统一的内容拆分，对人类读者更困难。
- 模型可能会错过仅存在于参考中的更广泛上下文。
- 查找数据很小（总计少于~50行）通常不值得拆分。

### 3. 深度层级（公共路径与边缘情况）

SKILL.md涵盖80%的情况。`references/edge-cases.md`涵盖其余部分。

指针必须像这样读取：

> 如果您看到X、Y或Z，请停止并继续阅读`references/edge-cases.md`。

**优点：**

- 公共路径保持最小、快速、便宜。
- 边缘情况可以详尽无遗，而不会污染每次调用。
- 扩展边缘情况覆盖范围而不触及公共路径很容易。
- 反映了专家的工作方式：默认值优先，按需处理异常。

**缺点：**

- 加载条件必须清晰且可从用户输入中观察到。大多数边缘情况都不满足这一点。
- 模糊条件会导致要么始终加载（浪费），要么始终不加载（死重）。
- 边缘情况因为评估自然集中在常见查询上而得到较少测试。
- 模型可能会跟随公共路径，而它本应升级。
- 80/20的估计通常是错误的；看起来像边缘情况的东西实际上是常见的。

## 不起作用的拆分

对于每个反模式，“为什么它看起来有吸引力”显示了设计者为什么会选择它；“为什么它不起作用”显示了实践中会发生什么。

### 基于主题的拆分，但调用不按主题聚集

一个测试技能拆分为`unit.md`、`integration.md`、`mocks.md`是一个典型的例子。

**为什么它看起来有吸引力：**

- 概念上干净，反映了人类组织文档的方式。
- 作为维护者易于导航。
- 可能减少每次调用的上下文成本。

**为什么它不起作用：**

- 真实任务跨越2-3个主题，迫使每次调用加载多个。
- 跨主题的关切点被重复或碎片化。
- 节省是理论上的，而不是实证的。

### 没有实际分支条件就拆分以命中行目标

**为什么它看起来有吸引力：**

- 一个启发式方法（“保持SKILL.md少于400行”）感觉像一条干净的规则来满足。
- 拆分感觉像进展。

**为什么它不起作用：**

- 没有分支条件，参考资料并行加载或始终加载，不会提供节省。
- 向SKILL.md添加路由说明，通常使总内容更长。

### 参考资料中的罕见但关键内容

**为什么它看起来有吸引力：**

- 内容很大或专业化。
- 将其从SKILL.md中移出感觉像良好的卫生习惯。

**为什么它不起作用：**

- 参考资料（按设计）是可选的；模型可能会跳过它们。
- 如果内容是关键的，它必须可靠地加载，这意味着SKILL.md。
- “罕见”和“关键”放在一起通常是技能正在做两份工作的迹象，应该分成两个技能。

### 修饰性拆分（示例、注释、提示文件）

**为什么它看起来有吸引力：**

- 减少SKILL.md中的视觉杂乱。
- 感觉像良好的组织。

**为什么它不起作用：**

- 没有加载条件：要么始终加载（浪费工具调用），要么始终不加载（死内容）。
- 暗示了在运行时不存在的重要性层次结构。
- 经常隐藏模型需要的内容。

## 指针卫生

当SKILL.md指向一个参考资料时，指针是整个加载合同。规则：

- 命名触发加载的用户可见信号。“如果用户提到快照测试”而不是“对于测试问题”。
- 每个指针一个句子。不要在SKILL.md中总结参考资料内容。
- 在文件名中编码加载条件。`go126-simd.md`而不是`advanced.md`。
- 任何超过300行的参考资料在文件顶部提供目录。
- 如果两个参考资料在大多数运行中一起加载，请将它们合并。

**严格指针卫生的优点：**

- 错误加载率急剧下降。
- 文件名编码加载条件，对未来的维护者具有自我说明性。
- 强迫事先明确每个参考资料何时需要。
- 使架构评估更容易解释。

**严格指针卫生的缺点：**

- 某些内容没有清晰的触发器；规则强制使用笨拙的表述。
- 文件名变得很长且笨拙。
- 需要纪律；随着时间的推移很容易偏离。
- 当触发条件确实模糊时，可能会过度限制有用的加载。

## 在`references/`之前使用`scripts/`

对于任何确定性内容（格式化、验证、模式生成、文件转换、正则表达式密集型解析），`scripts/`中的脚本优于`references/`中的说明。

**脚本优于参考说明的优点：**

- 执行零上下文成本。
- 确定性、可重复的输出。
- 跨调用可重用，无需重新读取。
- 可以独立进行单元测试。
- 通常比模型驱动的说明生成更快。

**脚本的缺点：**

- 需要运行时支持脚本执行；并非所有环境都支持。
- 比让模型对说明进行推理灵活度低。
- 处理未预料的边缘情况而无需代码更改更困难。
- 增加了维护负担：技能中的代码需要保持正常工作。
- 用户无法在不编辑脚本的情况下轻松自定义行为。
- 失效模式更尖锐：脚本错误会停止工作流。

## 决策清单

在将任何内容从SKILL.md拆分出来之前，回答：

1. 这部分内容是否有模型可以从用户输入中检测到的清晰、可观察的加载条件？
2. 拆分是否真的会减少上下文，考虑到添加到SKILL.md中的路由说明？
3. 这是参考资料数据（查找）还是程序（顺序）？程序内容通常保持不变。
4. 脚本是否可以确定性地处理这个问题？
5. 在现实世界的调用中，有多少比例的运行会加载此文件？低于20%，内联或删除——很少加载的参考资料很少证明路由开销是合理的。20-80%是拆分甜点区。超过80%，将其提升到SKILL.md——路由成本超过了加载节省。

如果问题1的答案不明确，请不要拆分。

## 评估技能架构

架构评估与输出评估不同。输出评估问“技能是否产生了正确的结果？”；架构评估问“技能是否加载了正确的文件，出于正确的理由，在可接受的成本下？”相同的套件，不同的指标——运行两者：输出质量是底线，架构是优化。

**运行架构评估的优点：**

- 捕获死参考资料、死SKILL.md部分和错误路由的内容。
- 量化拆分是否真的节省了代币，而不仅仅是看起来整洁。
- 揭示直觉遗漏的真实加载模式。
- 强制评估集覆盖所有声明的路径，暴露死路径。
- 与输出评估结合，可以在两个维度上捕获回归。

**运行架构评估的缺点：**

- 需要超出标准输出评估的套件设置。
- 路径覆盖的评估集设计需要工作。
- 指标需要根据每个技能进行校准（阈值因成本配置文件而异）。
- 输出评估仍然是必需的；这增加了总迭代成本。
- 容易过度优化代币成本，以牺牲输出质量为代价。

### 架构评估的评估集设计

输出评估针对现实世界的查询优化输出质量。架构评估针对路径覆盖进行优化。评估集必须执行技能声明的每个代码路径，否则指标将是噪声。

至少构建：

- 每个声明的变体一个查询（如果技能使用变体分支拆分）。
- 每个深度层级分支一个查询（如果存在深度层级拆分）。
- 每个主要查找类别一个查询（如果存在参考资料数据拆分）。
- 一个查询应该只命中公共路径并加载零参考资料。
- 2-3个离主题查询，这些查询不应触发技能（也测试描述）。

如果没有任何现实世界的查询触发某个参考资料文件，该文件就是死的。将其内联或删除，然后再运行任何东西。

### 仪器

每次评估运行都由加载了技能的子代理执行。捕获每个运行的：

1. 包含每个工具调用的完整转录。
2. 哪些`references/*`文件被读取（解析技能目录内路径上的`view`调用）。
3. 是否调用了`scripts/*`。
4. 总代币数和墙时间。
5. 输出（用于并行输出质量评估）。

作为每个运行的`transcript.json`和`loads.json`与标准输出一起持久化。技能创建者套件已经记录了`timing.json`中的代币和时间；扩展其评分步骤以从转录中提取参考资料加载。

### 每个参考资料文件的指标

在所有评估运行中，对于每个`references/*.md`：

- **加载率**：加载它的运行比例。
- **共现**：对于每个其他参考资料，加载两者的运行比例。
- **加载时的使用率**：加载它的运行中，内容是否明显地影响了输出（引用内容、应用程序序、使用模式）？检查转录。
- **重读率**：加载同一文件两次的运行比例。

### 技能整体的指标

- **中位数和p95每次调用的代币**，包括和不包括参考资料。
- **SKILL.md利用率**：读取转录并识别模型在任何运行中从未引用的SKILL.md部分。强烈候选删除。
- **路径覆盖率**：是否每个声明的路径至少被一个查询命中？

### 决策规则

| 观察 | 动作 |
| --- | --- |
| 参考资料在<20%的运行中加载 | 内联到SKILL.md或删除——路由开销不值得 |
| 参考资料在20–80%的运行中加载 | 保持拆分——甜点区；路由有效 |
| 参考资料在>80%的运行中加载 | 提升到SKILL.md——始终加载成本超过了路由成本 |
| 两个参考资料在>70%的运行中一起加载 | 合并到一个文件 |
| 参考资料加载但未在输出中使用 | 修复或删除SKILL.md中的指针 |
| 参考资料在同一运行中重读 | SKILL.md路由不明确；澄清 |
| 没有查询触发参考资料 | 删除参考资料 |
| SKILL.md部分在任何运行中从未引用 | 删除该部分 |

这些阈值只是起点。根据成本配置文件调整它们：小参考资料与廉价加载相比，可以容忍较低的加载率，而不是大参考资料。

### 比较两个架构

在单体与拆分（或拆分A与拆分B）之间选择架构时：

1. 对两个版本运行相同的评估集。
2. 对两者运行输出质量评估。确认没有回归。如果质量下降，无论代币节省如何，架构更改都是损失。
3. 比较中位数代币、p95代币和中位数每次调用时间。
4. 比较路径覆盖率：每个版本是否都通过预期路径可靠地达到相同的输出？

节省15%代币但输出质量变异性增加的拆分比单体更差。可靠性优于效率。

### 指标将不会告诉你的

- SKILL.md说明是否清晰。阅读转录以查找困惑的工具调用和死胡同尝试。
- 描述是否正确触发。这是一个单独的评估（使用`run_loop.py`从`skill-creator`技能）。
- 内容放置是否与用户心智模型匹配。主观的；与人类一起审查。

设计时看起来干净的拆分很少与实际加载模式匹配。相信转录而不是你的直觉。

## 提供建议时的输出

当被问及对特定技能组织的建议时：

1. 首先诊断。这是触发问题还是披露问题？
2. 在建议之前引用现有SKILL.md的相关内容（或用户对其的描述）。
3. 提出最小可行拆分。抵制拆分比必要更多的文件。
4. 为每个建议的参考资料文件，编写将放入SKILL.md的精确指针句子。
5. 明确展示权衡。使用此技能中的优缺点作为模型如何呈现建议的范例。
6. 如果不确定拆分是否有助于，建议先进行仪器（评估技能，读取转录）再提交。
