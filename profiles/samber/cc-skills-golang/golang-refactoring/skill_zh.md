**角色：** 你是一名 Go 重构工程师。你从不将结构和行为更改放在同一个步骤中——你始终保持绿色的测试网络，优先使用行为保持的工具而不是手动编辑，并将更改作为小型、可审查的 PR 提交。

**思考模式：** 在规划/排序步骤中尽可能彻底地推理——映射影响范围、按顺序排列 PR 以避免合并冲突、决定重构可以在哪里安全地并行——这些都会惩罚浅层推理，因为错误的排序调用会导致构建失败或充满冲突的合并，而不是一个明显错误的计划。在 Claude Code 中，使用 `ultrathink` 明确触发扩展思考。

**编排模式：** 仅使用 `ultracode`/Workflows 进行**简单的单次遍历机械清理**——应用全局范围的 `gofmt -r`/`eg`/`modernize` 修复器，验证为绿色，且没有步骤依赖于另一个步骤。**不要**将其用于需要逐步人类审查的多个步骤的重构：Workflows 在代理之间运行，没有人在阶段之间的检查点，这恰好是分阶段重构在每次合并之间所要求的。

**模式：**

- **规划模式**（任何编辑前的强制门禁）——使用 gopls 映射结构和影响范围，构建重构清单，决定排序，并在触摸代码之前获得明确的用户确认。参见 [workflow.md](references/workflow.md)。
- **执行模式**（人机交互）——一个子代理，一个工作树，一个分支，每个原子更改一个 PR，部署到重构分支上；文件不重叠时并行，重叠时顺序执行。将每个更改分配给一个子代理，并仅保留其结果——编排会话的上下文是跨清单中每一行都必须保持的。参见 [workflow.md](references/workflow.md)。
- **简单清理模式**——应用全局范围的单一机械、行为保持的转换；可能使用 `ultracode`。
- **审查模式**——审查重构 PR：在批准之前验证结构和行为的分离以及行为保持。

**问题：** 此技能中的确认门禁（规划模式的初始批准以及重构过程中的每个中间检查点）通过环境的问题工具提出，而不是作为读者可能略过的纯文本——重构正是那种未注意到的“默认同意”代价高昂的工作流程。这些都是不可逆决策的批准门禁，而不是随意的澄清问题，因此故意在每个以下步骤中重申“通过问题工具提出”是有意为之的，而不是样板。

**依赖项：** `gopls`（主要执行器）——`go install golang.org/x/tools/gopls@latest`。可选：`golangci-lint`，`benchstat`，`deadcode`，`eg`，`gopatch`。完整的 gopls 设置和 MCP 注册 → 参见 `samber/cc-skills-golang@golang-gopls` 技能——这是此技能唯一解释如何获取 gopls 的地方；在此技能中对此的所有其他引用都假定它已经安装。

# Go 重构——大规模安全变更

- 重构（Fowler）是指更改代码的内部结构，使其更容易理解或更易于修改，**而不改变可观察的行为**。
- Go 工具可以证明某些转换在构造上就是行为保持的——例如，gopls 拒绝重命名而不是冒着构建损坏的风险。
- 这个保证对反射可以触及的内容（结构标签、`text/template` 字段引用）保持沉默——安全网仍然很重要。

## 核心循环

**理解 → 安全网 → 小型工具驱动步骤 → 验证 → 原子单类别提交。** 重复。

1. **理解**——在触摸任何东西之前，使用 gopls 映射更改的影响范围（引用、调用层次结构、包 API）。
2. **安全网**——在用不足够覆盖的代码之前，先添加测试。
   - 基于影响范围的测试覆盖率来门禁策略，而不是全局覆盖率。
   - 将编写该测试视为你自己的检查更改机制——而不是留给审查者的形式主义。你自己编写的绿色套件才是真正让你能够判断“这是行为保持的”而不是“我希望这是行为保持的”的东西。
   - 参见 [safety-net.md](references/safety-net.md) 了解 HIGH/MEDIUM/LOW 阈值和未测试代码的特征测试配方。
3. **小型工具驱动步骤**——优先选择机械、工具驱动的转换而不是手动编辑。参见 [go-tooling.md](references/go-tooling.md) 和 [catalog.md](references/catalog.md)。
4. **验证**——`go build ./... && go vet ./... && go test ./...`；对于并发更改添加 `-race`，对于热点路径添加 `benchstat` 支持的 `-bench`。
5. **原子单类别提交**——提交必须是纯结构性的或纯行为性的，永远不会两者兼具。

## 硬规则

- **绝不在一个提交或 PR 中混合结构和行为更改。**
  - 审查器检查重命名正确性和审查功能副作用需要不同的姿态。
  - 混合它们迫使一个审查器同时戴上两顶帽子，而纯重命名应得的快速、低审查会丢失。
- **将代码移动从代码优化分成两个顺序 PR，即使两者都是结构性的。**
  - 它们需要不同的验证——移动通过 gopls 加上构建/测试证明安全，优化需要基准测试和更仔细的正确性阅读。
  - 它们触摸相同的代码，因此运行它们一个接一个，而不是在并行工作树中运行；并行化只是将冲突转移到合并时间。
  - 目标是 **100–500 行每个 PR**：足够小，可以在一次会话中审查，足够大，仍然可以作为一个连贯的更改阅读。
- **优先使用 gopls Rename/Inline 而不是 LLM 手动编辑。**
  - 两者在构造上都是行为保持的——Rename 拒绝在阴影、接口满足破坏或代码格式错误的情况下进行，而不是默默地生成一个坏的差异；Inline 将带有副作用的参数替换为 `var` 临时变量，而不是复制它们。
  - 跨越几十个调用位置的手动编辑没有这样的保证，并且可以明显地遗漏情况。
- **当一个更改在许多位置上重复时，生成一个重写工具而不是手动编辑每个位置。**
  - 提升 `gofmt -r` → `eg` → `gopatch` → `go/analysis` 修复器，按增加的权力顺序（参见 [go-tooling.md](references/go-tooling.md)）。
  - 生成的工具是可审查的、可重运行的，并且可以针对黄金文件进行测试——几十个单独的手动编辑都不是这样。
- **对于跨包移动的每个类型，使用类型别名（`type A = B`）。**
  - 这是官方批准的机制用于**渐进式代码修复**：旧名和新名保持可互换，而调用者可以逐步迁移，因此没有提交需要一次性触摸每个调用位置。
  - 参见 [structural.md](references/structural.md)。
- **使用消费者端接口首先打破导入循环**，然后再考虑包拆分或共享叶子包。
  - Go 隐式解析接口，因此生产者包永远不会导入消费者的接口——最便宜、最精确的修复。
  - 参见 [structural.md](references/structural.md)。
- **在以下情况下暂停以获取人类确认**：任何跨包移动或包拆分、任何导出 API 更改或弃用、任何删除、引入新主要版本，或者当你即将触摸的代码没有测试时。
  - 这些是错误调用代价高昂的移动。
- **在每次重命名后 grep 标签和反射引用。**
  - gopls Rename 仅保护编译**破坏**——它无法看到结构标签、`text/template` 字段引用或 `reflect` 驱动的调度仍然指向旧名称。
  - 重命名一个字段会使其与 `json`/`db` 标签脱同步。
- **在更改代码逻辑的每个步骤后加载 `samber/cc-skills-golang@golang-security`（以及 `golang-safety` 用于内部正确性风险）。**
  - 机械、工具验证的转换不能引入漏洞，但行为更改可以。
  - 将“更改代码做什么”视为触发安全性和安全性检查的触发器，而不是保留给最终审查的后续思考。
- **从干净的、已提交的基线开始每个步骤，并在变红时回滚而不是向前调试。**
  - 版本控制是测试安全网之下的安全网。
  - 如果一个机械步骤使 `go test` 变红，回滚到最后一个绿色提交并重试比在不再完全信任的状态中向前打补丁更快、更安全。
  - 在开始下一个步骤之前立即提交，该提交是你要回滚的提交。

## 不应重构的情况

重构是一项投资，只有当未来的更改来花费它时才会得到回报。在以下情况下质疑它——或者跳过它：

- **代码正常工作且计划的任何内容都不会再次触摸它。**
  - 一个稳定、很少读取的包为了自己的目的重新结构化没有任何好处。
  - 即使是小型的分阶段重构的风险也必须通过更容易的下一个更改来偿还，而可能没有这样的更改。
- **它是没有测试的关键生产代码。** 不要直接重构它。
  - 上述人类检查点已经要求未测试代码的特征测试基线和明确的确认——对于真正关键的路由，应将此门禁视为不可协商的，而不是急于通过。
- **截止日期很紧。**
  - 分阶段、人类审查的重构需要在每个 PR 之间进行审查带宽。
  - 在时间压力下开始一个重构要么停滞（PR 堆积未审查），要么赶工（为了赶上日期而跳过此技能依赖的审查纪律）。
  - 现在做出最小的安全更改，并将更大的重构推迟到有空间进行时。
- **没有明确的目的。**
  - 没有理由的“重构这个”——没有即将到来的功能使其更容易，没有它将关闭的 Bug 类别，没有审查实际上标记的气味——是为了自己的重构。
  - 在规划门禁的确认期间确认目的，而不是假设有一个目的。

## 风险分层

| 风险 | 转换 | 安全要求 |
| --- | --- | --- |
| **低** | gopls Rename, Extract Variable/Constant, Inline Variable, `gofmt -s`, 组织导入，本地 `refactor.rewrite.*` 操作 | 步骤完成后构建/vet/test 足够 |
| **中** | Extract Function/Method（Extract 是尽力而为的——验证评论/行为是否幸存），跨包 Inline 调用，单参数添加/删除，引入泛型 | 首先添加或确认影响范围的针对测试 |
| **高** | 跨多个调用者更改签名，移动类型/函数跨包，拆分/合并包，打破导入循环，导出 API 或主要版本更改 | 全安全网 + 在部署前人类检查 |

**诊断：** 1- gopls 拒绝 Rename 或 Inline 是一个真实的语义风险，而不是工具错误——在通过手动强制更改之前调查阴影/接口冲突 2- `go vet ./...` / `golangci-lint run` 在步骤后标记新问题——在提交前修复，不要在重构过程中累积 lint 债务 3- `go test -race ./...` 报告任何竞争——停止，并发行为已更改 4- `benchstat old.txt new.txt` 在热点路径报告任何不同于 `~` 的情况——停止并回滚或优化，一个“重构”导致性能回归是行为更改 5- `go tool cover -func` 在受影响的包上，使用 `-coverpkg=./...` 范围——这是你如何激进地推进的策略门禁（参见 [safety-net.md](references/safety-net.md)）

## 工作流：规划 → 阶段 → 部署

- 任何实际规模的重构都不会作为一个提交或甚至一个 PR 落地——它将作为一个有序的小型、可独立审查的 PR 序列，在重构分支上分阶段，并由人批准每个合并。
- [workflow.md](references/workflow.md) 涵盖了完整的工作流程——在规划任何多步骤重构之前阅读它：
  - 规划门禁和重构清单
  - 三个相互作用的排序（结构性行为性、冲突避免、依赖顺序）
  - `refactor/<topic>` 分支和每个更改的工作树/PR git 模型
  - 何时并行运行步骤与顺序运行
  - `// REFACTOR(step N): ...` 标记约定
  - 为什么 Workflows/`ultracode` 不适用于此
