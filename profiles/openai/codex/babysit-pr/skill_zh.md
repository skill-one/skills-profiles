# PR Babysitter

## 目标
持续地照看一个PR，直到出现以下其中一个终止结果：

- PR被合并或关闭。
- 需要用户帮助的情况（例如CI基础设施问题、重试预算耗尽后的重复不稳定失败、权限问题或无法安全解决的不明确性）。
- 可选的交接里程碑：PR目前为绿色 + 可合并 + 审查干净。将其视为一个进行状态，而不是观察者停止，因此即使PR仍然打开，晚到的审查评论也会被及时显示。

即使单个快照返回`idle`而检查仍在等待时，也不要停止。

## 输入
接受以下任何一种：

- 没有PR参数：从当前分支推断PR（`--pr auto`）
- PR编号
- PR URL

## 核心工作流程

1. 当用户要求“监控”/“观察”/“照看”一个PR时，除非有意进行一次性诊断快照，否则从观察者的连续模式（`--watch`）开始。
2. 运行观察者脚本以快照PR/审查/CI状态（或消费从`--watch`流式传输的每个快照）。
3. 检查JSON响应中的`actions`列表。
4. 如果`diagnose_ci_failure`存在，检查失败的运行日志并对故障进行分类。
5. 如果故障可能是由于当前分支引起的，请本地修补代码、提交并推送。不要修补随机的易失性测试、CI基础设施、依赖项中断、运行器问题或其他与分支无关的故障。
6. 如果`process_review_comment`存在，检查显示的已发布的审查项并决定是否处理它们。
7. 如果审查项是可操作的且正确的，请本地修补代码、提交、推送，然后仅在GitHub状态变更策略允许时才解决相关的审查线程。
8. 除非用户明确确认确切回复，否则不要向人类编写的审查评论/线程发布回复。如果人类审查项是不可操作的、已解决的或无效的，请向用户显示该项目和建议回复，而不是在GitHub上回复。
9. 如果故障可能是易失性/无关的并且`retry_failed_checks`存在，请使用`--retry-failed-now`重新运行失败的作业。
10. 如果同时存在可操作的审查反馈和`retry_failed_checks`，请优先处理审查反馈；新的提交将重新触发CI，因此避免在旧SHA上重新运行易失性检查，除非您有意推迟审查更改。
11. 在每个循环中，在处理CI故障或合并状态之前，查找新显示的审查反馈，然后与CI一起验证合并性/合并冲突状态（例如通过`gh pr view`）。
12. 在任何推送或重新运行操作后，立即返回步骤1并在更新的SHA/状态上继续轮询。
13. 如果您在暂停以修补/提交/推送之前使用`--watch`，请在推送后立即在同一个回合中重新启动`--watch`（不要等待用户重新调用技能）。
14. 重复轮询，直到`stop_pr_closed`出现或达到需要用户帮助的障碍。绿色 + 审查干净 + 可合并的PR是一个进展里程碑，而不是在PR仍然打开时停止观察者的原因。
15. 维护终端/会话所有权：在照看活动期间，请在同一个回合中继续消耗观察者输出；不要让脱离的`--watch`进程运行，然后像监控完成一样结束回合。

## CI故障分类
在使用`gh`命令检查失败运行以决定重新运行之前，使用`gh`命令检查失败运行。

- `gh run view <run-id> --json jobs,name,workflowName,conclusion,status,url,headSha`
- `gh api repos/<owner>/<repo>/actions/runs/<run-id>/jobs -X GET -f per_page=100`
- `gh api repos/<owner>/<repo>/actions/jobs/<job-id>/logs > /tmp/codex-gh-job-<job-id>-logs.zip`
- `gh run view <run-id> --log-failed`作为整体工作流运行完成后的一种后备方案

`gh run view --log-failed`是工作流运行范围的，并且可能直到整体运行完成才不会显示失败作业的日志。为了更快地诊断，首先轮询运行的作业，并且一旦特定作业失败，直接从动作作业日志端点获取该作业的日志。观察者包括一个`failed_jobs`列表，其中包含每个失败作业的`job_id`和`logs_endpoint`，当GitHub显示一个时。

当失败作业的日志指向已更改的代码（编译/测试/检查/类型检查/快照/静态分析在触及的区域）时，优先将故障视为与分支相关。

当日志显示瞬态基础设施/外部问题（超时、运行器配置失败、注册表/网络中断、GitHub Actions基础设施错误）时，优先将故障视为易失性/无关。

除非日志明确将故障与PR分支连接起来，否则不要尝试通过更改测试、构建脚本、CI配置、依赖项固定或基础设施相邻代码来修复易失性/无关的故障。对于易失性/无关的故障，仅在观察者建议`retry_failed_checks`时重新运行；否则等待或请求用户帮助。

如果分类不明确，请在选择重新运行之前执行一次手动诊断尝试。

阅读`.codex/skills/babysit-pr/references/heuristics.md`以获取简洁的清单。

## 审查评论处理
观察者从以下地方显示审查项：

- PR问题评论
- 内联审查评论
- 审查提交（COMMENT / APPROVED / CHANGES_REQUESTED）

仅对已发布的反馈采取行动。忽略GitHub的`PENDING`状态中的审查提交和附加到那些待处理评论的内联评论。不要将待处理的审查反馈标记为已查看；它应在审查者提交审查后仍然有资格显示。

有意显示Codex审查器机器人反馈（例如来自`chatgpt-codex-connector[bot]`的评论/审查），以及人类审查者反馈。大多数无关的机器人噪音仍然会被忽略。
出于安全考虑，观察者仅自动显示受信任的人类审查者（例如仓库所有者/MEMBER/COLLABORATOR，以及经过身份验证的操作员）和批准的审查机器人（例如Codex）。

在一个新的观察者状态文件中，现有的未解决的已发布审查反馈可能会立即显示（而不仅仅是监控开始后到达的评论）。这是有意为之的，以便不会错过已经打开的审查评论。

当您同意评论并且它是可操作的时：

1. 本地修补代码。
2. 使用`codex: address PR review feedback (#<n>)`提交。
3. 推送到PR头分支。
4. 推送成功后，仅在GitHub状态变更策略允许时才解决相关的GitHub审查线程。
5. 立即在新SHA上重新开始观察（不要在报告推送后停止）。
6. 如果监控在`--watch`模式下运行，请在推送后立即在同一个回合中重新启动`--watch`；不要等待用户再次要求。

不要自动向人类编写的GitHub审查评论/线程发布回复。如果您不同意人类评论，认为它是不可操作的/已经解决，或者需要回答问题，请向用户报告该项目并建议回复，然后在发布任何内容到GitHub之前等待明确确认。如果用户批准回复，请将其前缀为`[codex]`，以便清楚地知道回复是自动化的，而不是来自人类用户。
如果观察者后来显示您自己的批准回复，因为经过身份验证的操作员被视为受信任的审查者，请将其视为已处理，不要再次回复。
如果代码审查评论/线程已经在GitHub中标记为已解决，请将其视为不可操作的，并安全地忽略它，除非出现新的未解决的后续反馈。

## GitHub状态变更策略

您可以读取任何用于监控的PR状态。写入必须遵守此策略。

您可以推送PR以更新正在审查的代码或强制CI重新运行，如上所述。

您可以解决由请求照看的人或Codex审查机器人发起的审查评论线程。解决时，请留下以`[from Codex]: `为前缀的评论，并解释您所做的更改以及包含这些更改的提交。如果其他人类（除请求照看的人外）参与了审查线程，请不要触摸审查线程。

在做出任何更改之前，请自行获取PR状态，而不是依赖PR观察者脚本的输出。

除非明确要求，否则不要：

* 评论其他人类的审查线程，通过聊天与用户交流
* 解决除请求照看的人以外的其他人类的审查线程
* 与除用户以外的其他人互动
* 将PR标记为草稿或准备好审查
* 关闭或重新打开PR

通常，永远不要以难以区分您或用户是否做了对其他人可见的事情的方式在GitHub上采取行动。如有疑问，请在聊天中向用户请求澄清。

## Git安全规则

- 仅在PR头分支上工作。
- 避免使用破坏性git命令。
- 除非需要恢复上下文，否则不要切换分支。
- 在编辑之前，检查是否存在无关的未提交更改。如果存在，请停止并询问用户。
- 每次成功修复后，提交并`git push`，然后重新运行观察者。
- 如果您中断了实时的`--watch`会话以进行修复，请在推送后立即在同一个回合中重新启动`--watch`。
- 不要为同一个PR/状态文件运行多个并发`--watch`进程；保持一个观察者会话活动并重复使用它，直到它停止或您有意重新启动它。
- 推送不是终止结果；继续监控循环，除非遇到严格的停止条件。

提交消息默认：

- `codex: fix CI failure on PR #<n>`
- `codex: address PR review feedback (#<n>)`

## 监控循环模式
在实时Codex会话中使用此循环：

1. 运行`--once`。
2. 读取`actions`。
3. 首先检查PR是否现在已合并或以其他方式关闭；如果是，请报告该终止状态并立即停止轮询。
4. 检查CI摘要、新的审查项和合并性/冲突状态。
5. 诊断CI故障并将分支相关性与易失性/无关性分类。如果整体运行仍然挂起，但`failed_jobs`已经包含一个失败的作业，请立即获取该作业的日志并立即诊断，而不是等待整个工作流运行完成。仅在故障与分支相关时才修补。
6. 对于来自其他作者的每个显示的审查项，如果它是可操作的，请修补/提交/推送，然后仅在GitHub状态变更策略允许时才解决它。如果它是不可操作的、已经解决或需要书面回答，请向用户显示该项目并建议回复，而不是自动发布。如果稍后快照显示您自己的批准回复，请将其视为信息性，并继续而不再回复。
7. 当同时存在可操作的审查评论和易失性重新运行时，优先处理审查评论；如果审查修复需要提交，请推送它并跳过在旧SHA上重新运行失败的检查。
8. 仅当`retry_failed_checks`存在并且您即将用审查/CI修复提交替换当前SHA时，才重新运行失败的检查。不要为了使CI变绿而更改与分支无关的易失性或基础设施故障。
9. 如果您推送了提交、解决了符合条件的审查线程或触发了重新运行，请简要报告操作并继续轮询（不要停止）。如果需要书面GitHub回复的人类审查评论，请停止并要求确认后再发布。
10. 在审查修复推送后，除非已经达到严格的停止条件，否则在同一回合中主动重新启动连续监控（`--watch`）。
11. 如果一切通过、可合并、未阻塞所需审查批准，并且没有未解决的审查项，请报告PR目前可以合并，但请保持观察者运行，以便在PR仍然打开时快速显示新的审查评论。
12. 如果阻塞在需要用户帮助的问题上（基础设施中断、耗尽易失性重试、不明确的审查者请求、权限），请报告障碍并停止。
13. 否则，根据以下轮询节奏睡眠并重复。

当用户明确要求监控/观察/照看一个PR时，优先使用`--watch`，以便在一个命令中自主轮询继续。仅用于调试、本地测试或当用户明确要求一次性检查时，才使用重复的`--once`快照。

不要停止以询问用户是否要继续轮询；自主继续，直到达到严格的停止条件或用户明确中断。
在审查修复推送后，不要因为创建了新的SHA而将控制权交还给用户；重新启动观察者并重新进入轮询循环是照看任务的一部分。
如果`--watch`进程仍在运行并且没有达到严格的停止条件，照看任务仍在进行中；继续流式传输/消耗观察者输出，而不是结束回合。

## 轮询节奏
保持审查轮询积极，即使在CI变为绿色后继续监控：

- 当CI不是绿色（挂起/运行/排队或失败）：每分钟轮询一次。
- 在CI变为绿色后：在PR保持打开时保持基本节奏轮询，以便新发布的审查评论能够及时显示，而不是等待长时间的绿色状态回退。
- 每当有任何更改（新的提交/SHA、检查状态更改、新的审查评论、合并性更改、审查决策更改）时，立即重置节奏。
- 如果CI再次变为绿色（新的提交、重新运行或回归）：保持基本轮询节奏。
- 如果任何轮询显示PR已合并或以其他方式关闭：立即停止轮询并报告终止状态。

## 停止条件（严格）
仅在以下任一情况为真时停止：

- PR合并或关闭（一旦轮询/快照确认即可停止）。
- 需要用户干预且Codex无法单独安全进行。

保持轮询：

- `actions`仅包含`idle`但检查仍在等待。
- CI仍在运行/排队。
- 审查状态安静但CI不是终止状态。
- CI为绿色但合并性未知/挂起。
- CI为绿色且可合并，但PR仍然打开，您正在等待可能的新审查评论或合并冲突更改。
- PR为绿色但阻塞在审查批准上（`REVIEW_REQUIRED` / 类似）；继续以基本节奏轮询并显示任何新的审查评论，而无需请求确认以继续观察。

## 输出预期
在监控期间提供简洁的进度更新，并提供最终总结，包括：

- 在长时间未更改的监控期间，避免在每次轮询时发出完整更新；仅总结状态更改，并偶尔进行心跳更新。
- 将推送确认、中间CI快照、准备合并快照和审查操作更新视为进度更新；不要发出最终总结或结束照看会话，除非达到严格的停止条件。
- 用户请求“监控”不会通过几次样本轮询满足；请保持在循环中，直到达到严格的停止条件或用户明确中断。
- 审查修复提交+推送不是完成事件；立即在同一回合中重新启动实时监控（`--watch`）并继续报告进度更新。
- 当CI首次为当前SHA变为所有绿色时，发出一次庆祝性进度更新（不要在每次绿色轮询时重复）。首选风格：`🚀 CI is all green! 33/33 passed. Still on watch for review approval.`
- 不要在观察者终端仍在运行时发送最终总结，除非观察者已发出/确认严格的停止条件；否则继续提供进度更新。

- 最终PR SHA
- CI状态摘要
- 合并性/冲突状态
- 推送修复
- 易失性重试周期使用
- 剩余未解决的故障或审查评论
