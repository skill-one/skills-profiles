# 威胁模型源代码仓库

交付一个可操作的、针对特定仓库或项目路径的应用安全威胁模型，而不是通用的清单。将每个架构声明与仓库中的证据挂钩，并保持假设明确。优先考虑现实的攻击者目标和具体影响，而不是通用的清单。

## 快速入门

1) 收集（或推断）输入：
- 仓库根路径和任何在范围内的路径。
- 预期用途、部署模型、互联网暴露和身份验证预期（如果已知）。
- 任何现有的仓库摘要或架构规范。
- 使用 `references/prompt-template.md` 中的提示模板生成仓库摘要。
- 遵循 `references/prompt-template.md` 中要求的输出合同。在可能的情况下，直接使用其原文。

## 工作流程

### 1) 范围和提取系统模型
- 从仓库摘要中识别主要组件、数据存储和外部集成。
- 识别系统如何运行（服务器、CLI、库、工作进程）及其入口点。
- 将运行时行为与 CI/构建/开发工具和测试/示例分开。
- 将范围内的位置映射到这些组件，并明确排除范围外的项目。
- 没有证据不要声称组件、流程或控制措施。

### 2) 推导边界、资产和入口点
- 列出作为组件之间具体边界的信任边界，并注明协议、身份验证、加密、验证和速率限制。
- 列出驱动风险的资产（数据、凭证、模型、配置、计算资源、审计日志）。
- 识别入口点（端点、上传表面、解析器/解码器、作业触发器、管理工具、日志/错误接收器）。

### 3) 校准资产和攻击者能力
- 列出驱动风险的资产（凭证、个人身份信息、完整性关键状态、可用性关键组件、构建工件）。
- 基于暴露和预期用途描述现实的攻击者能力。
- 明确注明无能力，以避免夸大的严重性。

### 4) 将威胁枚举为滥用路径
- 优先考虑映射到资产和边界的攻击者目标（数据泄露、权限提升、完整性破坏、拒绝服务）。
- 对每个威胁进行分类并将其与受影响的资产挂钩。
- 保持威胁数量少但高质量。

### 5) 使用明确的可能性和影响推理进行优先级排序
- 使用定性可能性和影响（低/中/高）并附简短的理由。
- 使用可能性 x 影响，并根据现有控制措施进行调整，设置总体优先级（关键/高/中/低）。
- 说明哪些假设对排名影响最大。

### 6) 与用户验证服务上下文和假设
- 总结对威胁排名或范围有实质性影响的键假设，然后要求用户确认或更正。
- 提出最多 3 个有针对性的问题以解决缺失的上下文（服务所有者和环境、规模/用户、部署模型、身份验证/授权、互联网暴露、数据敏感性、多租户）。
- 在生成最终报告之前暂停并等待用户反馈。
- 如果用户拒绝或无法回答，说明哪些假设仍然存在以及它们如何影响优先级。

### 7) 推荐缓解措施和关注路径
- 将现有缓解措施（附带证据）与推荐的缓解措施区分开来。
- 将缓解措施与具体位置（组件、边界或入口点）和控制类型（授权检查、输入验证、模式强制、沙箱、速率限制、密钥隔离、审计日志）挂钩。
- 优先考虑具体的实施提示而不是通用建议（例如，“在网关处强制上传有效载荷模式”而不是“验证输入”）。
- 基于验证的用户上下文提出建议；如果假设仍然未解决，将建议标记为有条件的。

### 8) 在最终确定之前运行质量检查
- 确认所有发现的入口点都已被覆盖。
- 确认每个信任边界都在威胁中体现。
- 确认运行时与 CI/开发分离。
- 确认用户澄清（或明确的无响应）已反映。
- 确认假设和开放问题已明确。
- 确认报告的格式与 `references/prompt-template.md` 中定义的所需输出格式密切匹配。
- 将最终 Markdown 写入文件 `<repo-or-dir-name>-threat-model.md`（使用仓库根的 basename，或如果您被要求对子路径建模，则使用范围内的目录）。

## 风险优先级指导（说明性，非详尽）

- 高：预身份验证远程代码执行、身份验证绕过、跨租户访问、敏感数据泄露、密钥或令牌盗窃、模型或配置完整性破坏、沙箱逃逸。
- 中：针对关键组件的定向拒绝服务、部分数据泄露、有可衡量影响的速率限制绕过、影响检测的日志/指标中毒。
- 低：低敏感性信息泄露、易于缓解的噪声拒绝服务、需要不太可能的前提条件的问题。
