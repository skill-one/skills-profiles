# 安全最佳实践

## 概述

此技能提供了一种描述如何识别当前上下文中使用的语言和框架，然后从该技能的参考目录中加载有关此语言和/或框架的安全最佳实践信息的说明。

如果存在这些信息，则可用于编写默认安全的代码，或被动检测现有代码中的重大问题，或（如果用户请求）提供漏洞报告并建议修复方案。

## 工作流程

此技能的初始步骤是识别您被要求使用或项目中已存在的所有语言和所有框架。重点关注主要的核心理念。通常您需要识别前端和后端的语言和框架。

然后检查此技能的参考目录，查看是否有与语言和/或框架相关的任何相关文档。确保您阅读所有与特定框架或语言相关的参考文件。文件名的格式为 `<语言>-<框架>-<堆栈>-security.md`。您还应该检查是否存在 `<语言>-general-<堆栈>-security.md`，该文件与您可能使用的框架无关。

如果正在开发包含前端和后端的 Web 应用程序，请确保您已检查前端和后端的前端和后端参考文档！

如果您被要求制作一个将包含前端和后端的 Web 应用程序，但前端框架未指定，也请查看 `javascript-general-web-frontend-security.md`。了解如何保护前端和后端非常重要。

如果您在技能的参考目录中找不到相关信息，请稍微思考一下您对语言、框架以及所有众所周知的针对该语言的安全最佳实践的了解。如果您不确定，可以尝试在线搜索有关安全最佳实践的相关文档。

从那时起，它可以以几种方式运行。

1. 主要模式是仅使用信息从现在开始编写默认安全的代码。这对于启动新项目或在编写新代码时非常有用。

2. 次要模式是在项目中工作并编写代码时被动检测漏洞。关键或非常重要的漏洞或违反安全指南的重大问题可以被标记，并告知用户。这种被动模式应专注于影响最大的漏洞和默认安全设置。

3. 用户可以要求安全报告或提高代码库的安全性。在这种情况下，应生成完整的报告，描述项目如何未能遵循安全最佳实践指南。报告应按优先级排序，并具有清晰的严重性和紧急性部分。然后提供开始修复这些问题的服务。见 #fixes 部分。

## 工作流程决策树

- 如果语言/框架不明确，请检查存储库以确定它并列出您的证据。
- 如果在 `references/` 中存在匹配的指导，则仅加载相关文件并遵循其说明。
- 如果没有匹配的指导，请考虑您是否了解针对所选语言和/或框架的任何众所周知的安全最佳实践，但如果要求生成报告，请告知用户没有具体的指导（您仍然可以生成报告或确定关键漏洞）

# 覆盖

虽然这些参考包含了语言和框架的安全最佳实践，但客户可能有一些需要绕过或覆盖这些实践的情况。注意项目文档和提示文件中的特定规则和说明，这些规则和说明可能要求您覆盖某些最佳实践。当覆盖最佳实践时，您可能会向用户报告，但不要与他们争论。如果出于某些项目特定原因需要绕过/忽略安全最佳实践，您也可以建议向项目添加文档，以说明为什么不遵循最佳实践，并在未来遵循绕过。

# 报告格式

在生成报告时，您应该将报告作为 `security_best_practices_report.md` 或用户提供的其他位置中的 Markdown 文件编写。您可以询问用户他们希望报告写入的位置。

报告应在顶部有一个简短的执行摘要。

报告应清晰地划分为基于漏洞严重性的多个部分。报告应专注于最关键的调查结果，因为这些对用户的影响最大。所有调查结果都应带有数字 ID，以便更容易参考。

对于关键调查结果，应包括一句影响声明。

一旦报告编写完成，也直接向用户报告，尽管您可能不那么详细。您可以提供解释任何调查结果或安全最佳实践指导背后的原因，如果用户需要有关任何调查结果的更多信息。

重要提示：在报告中引用代码时，请确保找到并包含您正在引用的代码的行号。

在编写报告文件后，向用户总结调查结果。

还告诉用户最终报告写入的位置

# 修复

如果您生成了报告，请让用户阅读报告并要求开始执行修复。

如果您被动发现了一个关键调查结果，请通知用户并询问他们是否希望您修复此调查结果。

在生成修复时，应专注于一次修复一个调查结果。修复应具有简洁清晰的注释，解释新代码基于特定的安全最佳实践，并可能简要说明不这样做会有多危险。

始终考虑您想要做的更改是否会影响用户代码的功能。考虑这些更改是否可能导致项目当前工作方式的回归。通常情况下，不安全的代码是出于其他原因而依赖的（这也是不安全代码存在这么长时间的原因）。避免破坏用户的项目，因为这可能会使他们在未来不希望应用安全修复。最好编写一个经过深思熟虑的、由整个项目充分支持的修复，而不是仓促的更改。

始终遵循用户配置的任何正常更改或提交流程。如果进行 git 提交，请提供清晰的提交信息，解释这是为了与安全最佳实践保持一致。尽量避免将多个不相关的调查结果合并到一个提交中。

始终遵循用户配置的任何正常测试流程（如果有）以确认您的更改没有引入回归。考虑更改可能产生的二阶影响，并在做出更改之前通知用户如果有任何影响。

# 一般安全建议

以下是适用于几乎所有语言或框架的几个安全编码建议。

### 避免使用递增 ID 作为资源的公共 ID

在为某些资源分配 ID 时，该 ID 将被用于暴露在互联网上，避免使用小的自动递增 ID。使用更长的随机 UUID4 或随机十六进制字符串。这将防止用户了解资源数量并能够猜测资源 ID。

### 关于 TLS 的说明

虽然 TLS 对生产部署很重要，但大多数开发工作将是 TLS 禁用或由某些范围外的 TLS 代理提供。由于这种情况，请非常小心地不要将缺少 TLS 报告为安全问题。还请非常小心地使用“安全” Cookie。它们只有在应用程序实际上将在 TLS 上运行时才应设置。如果它们在非 TLS 应用程序上设置（例如，在本地开发或测试时部署），则会破坏应用程序。您可以提供一个 env 或其他标志来覆盖设置安全，以便在 TLS 生产部署之前保持关闭。此外，避免推荐 HSTS。在没有完全理解其持久性影响（可能导致重大中断和用户锁定）的情况下使用它是危险的，并且通常不建议用于 codex 审查的项目范围。
