# 定义目标

## 概述

将用户的意图转化为一个代理可以诚实地追求的目标。优先考虑可衡量的结果、明确的证据和有限的范围，而不是活动描述。

这项技能仅涵盖目标定义和目标工具创建。不要从这项技能中创建中间规划工件、持久的快照、账本、决策日志或恢复文件。

## 工作流程

1. 确认确实需要定义目标。
   - 当用户要求 `$define-goal`、要求创建或设置目标、要求目标工具，或者希望帮助将意图转化为明确目标时，使用此技能。
   - 如果用户仅要求普通实施工作，直接执行工作，而不是强迫创建目标。

2. 将可能的目标以具体术语重新表述。
   可用的目标命名：
   - 将会为真的具体结果
   - 涉及的主要工件、系统、代码库、环境或用户界面行为
   - 如何验证完成情况
   - 范围内包含的内容
   - 当存在歧义时，范围外排除的内容
   - 询问用户的停止条件，而不是持续处理

3. 当领域支持时，使其量化。
   优先考虑代表真实成功的数字，而不是装饰性的精确度：
   - 通过/失败验证器：精确测试、检查、CI 作业、评估、命令或验收标准
   - 质量阈值：延迟、错误率、成本、准确率、召回率、精确率、覆盖率、失败率、包大小、内存、正常运行时间、完成率或人工审查标准
   - 工件约束：文件路径、受影响的模块、允许的命令、输出格式、目标环境、截止日期或最大影响范围
   - 证据数量：重复失败的次数、成功重跑次数、已审查示例、已迁移记录、已处理的评论或已验证案例

4. 在设置目标之前修复弱目标。
   - 当本地上下文允许时，将模糊目标重写为可衡量的目标。
   - 当缺失的细节改变预期结果或验证时，问一个简洁的澄清问题。
   - 除非将模糊的活动目标（如“取得进展”、“继续调查”、“改进事情”或“处理 X”）转化为可验证的结果，否则拒绝纯活动目标。

5. 在创建目标之前检查活动目标状态。
   - 调用 `get_goal`。
   - 如果没有活动目标且目标符合质量标准，调用 `create_goal`。
   - 如果存在与用户意图仍然匹配的活动目标，继续使用它而不是创建重复的目标。
   - 如果存在与新请求冲突的活动目标，询问是否完成当前目标、完成后再标记为完成，或启动一个由目标支持的独立线程。

6. 只有在目标通过质量标准后才能创建目标。
   - 使用一个简洁的目标字符串。
   - 将验证证据包含在目标本身中。
   - 当它们限制工作时，包含范围边界。
   - 只有当用户明确要求时，才包含令牌预算。
   - 除非用户明确要求基于目标的工作，否则不要为普通的多步任务调用 `create_goal`。

## 目标质量标准

在调用 `create_goal` 之前，目标应该回答：

- 完成时具体什么会为真？
- 什么证据会证明？
- 什么定量或二元阈值定义成功？
- 什么范围边界重要？
- 什么应该导致代理停止并询问？

良好：

> 通过进行最小的安全服务器端更改，将 checkout API p95 延迟降低到 250 毫秒以下，然后使用 `npm run test:checkout` 和现有的本地延迟基准验证，确保连续 3 次运行 p95 低于 250 毫秒。

良好：

> 解决 PR 123 上的开放审查评论，这些评论要求代码更改，仅更新受影响的认证文件和测试，并使用目标认证测试命令加上 `gh pr view 123` 验证，显示没有未解决的更改请求线程。

弱：

> 使 checkout 更快。

弱：

> 继续调查 PR 评论。

## 量化启发式方法

- 对于错误，将成功定义为首先可复现，其次修复，并在可能的情况下使用失败后通过的验证器。
- 对于测试，命名确切的命令和所需的通过条件。
- 对于性能，命名指标、目标阈值、测量方法和运行次数。
- 对于质量工作，定义一个可观察的验收标准，如已审查示例、代码检查/类型检查/测试通过或用户批准的工件。
- 对于研究，定义研究必须支持的决定、范围内的来源或系统以及证据标准。
- 对于操作，定义健康状态、监控窗口、失败阈值和回滚或升级触发器。

## 澄清问题

只有在合理的重写可能风险追求错误结果时才提问。保持问题简短，并围绕缺失的验证器或范围边界。

有用的提问形状：

- “在这里，什么指标应定义成功：延迟、成本、准确率或用户可见行为？”
- “我应该针对哪个环境进行验证：本地、测试或生产？”
- “在我标记此目标为完成之前，您希望我提供哪些最低证据？”

如果用户无法提供指标，请提议最诚实的二元验证器并请求确认。
