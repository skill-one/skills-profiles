# 图像生成技能

为当前项目生成或编辑图像（例如网站资源、游戏资源、UI 模板、产品模板、线框图、标志设计、照片级真实图像或信息图表）。

## 顶层模式和规则

此技能有两个顶层模式：

- **默认内置工具模式（首选）**：内置 `image_gen` 工具用于常规图像生成和编辑。不需要 `OPENAI_API_KEY`。
- **后备 CLI 模式（仅显式）**：`scripts/image_gen.py` CLI。仅在用户显式要求 CLI 路径时使用。需要 `OPENAI_API_KEY`。

在显式 CLI 后备模式中，CLI 暴露三个子命令：

- `generate`
- `edit`
- `generate-batch`

规则：
- 默认使用内置 `image_gen` 工具处理所有常规图像生成和编辑请求。
- 自动切换到 CLI 后备模式。
- 如果内置工具失败或不可用，告知用户存在 CLI 后备模式，并且它需要 `OPENAI_API_KEY`。仅在用户显式要求该后备模式时继续。
- 如果用户显式要求 CLI 模式，使用捆绑的 `scripts/image_gen.py` 工作流。不要创建一次性 SDK 运行器。
- 不要修改 `scripts/image_gen.py`。如果缺少某些内容，先询问用户再采取其他措施。

内置保存路径策略：
- 在内置工具模式下，Codex 默认将生成的图像保存在 `$CODEX_HOME/*` 下。
- 不要描述或依赖 OS 临时文件夹作为默认内置目标。
- 不要描述或依赖内置 `image_gen` 工具的路径参数（如果有）。如果需要特定位置，先生成后再将选定的输出从 `$CODEX_HOME/generated_images/...` 移动或复制到该位置。
- 内置模式下的保存路径优先级：
  1. 如果用户指定了目标，将选定的输出移动或复制到该位置。
  2. 如果图像用于当前项目，在完成前将最终选定的图像移动或复制到工作区。
  3. 如果图像仅用于预览或头脑风暴，直接内联渲染；底层文件可以保留在默认的 `$CODEX_HOME/*` 路径。
- 不要仅将项目引用的资源保留在默认的 `$CODEX_HOME/*` 路径。
- 除非用户明确要求替换，否则不要覆盖现有资源；否则创建一个带版本号的同名文件，例如 `hero-v2.png` 或 `item-icon-edited.png`。

两种模式的共享提示指导文档位于 `references/prompting.md` 和 `references/sample-prompts.md`。

仅 CLI 模式的后备文档/资源：
- `references/cli.md`
- `references/image-api.md`
- `references/codex-network.md`
- `scripts/image_gen.py`

## 何时使用
- 生成新图像（概念艺术、产品拍摄、封面、网站英雄）
- 使用一个或多个参考图像生成新图像，用于风格、构图或情绪
- 编辑现有图像（修复、光照或天气转换、背景替换、对象移除、合成、透明背景）
- 为一项任务生成多个资源或变体

## 何时不用
- 扩展或匹配存储在仓库中的现有 SVG/矢量图标集、标志系统或插图库
- 创建简单的形状、图表、线框图或图标，这些内容更适合直接在 SVG、HTML/CSS 或画布中生成
- 当源文件已存在于可编辑的原生格式中时，进行小型的项目本地资源编辑
- 任何用户明确要求确定性代码原生输出而不是生成位图的任务

## 决策树

思考两个独立的问题：

1. **意图**：这是一个新图像还是现有图像的编辑？
2. **执行策略**：这是一个单一资源还是多个资源/变体？

意图：
- 如果用户希望在保留部分内容的同时修改现有图像，将请求视为 **edit**。
- 如果用户仅将图像作为风格、构图、情绪或主题指导的参考，将请求视为 **generate**。
- 如果用户未提供图像，将请求视为 **generate**。

内置编辑语义：
- 内置编辑模式适用于对话上下文中已可见的图像，例如附加图像或线程中先前生成的图像。
- 如果用户希望使用内置工具编辑本地图像文件，首先使用内置 `view_image` 工具加载它，以便图像在对话上下文中可见，然后继续内置编辑流程。
- 不要承诺通过内置工具进行任意文件系统路径编辑。
- 如果本地文件仍需要直接文件路径控制、掩码或其他显式 CLI 参数，仅在用户要求时使用显式 CLI 后备模式。
- 对于编辑，应积极保留不变量，并默认进行无损保存。

执行策略：
- 在内置默认路径中，通过为每个请求的资源或变体发出一个 `image_gen` 调用来生成多个资源或变体。
- 在显式 CLI 后备路径中，仅在用户显式选择 CLI 模式并需要多个提示/资源时，使用 CLI `generate-batch` 子命令。

除非用户明确要求更改现有图像，否则假设用户希望生成新图像。

## 工作流
1. 确定顶层模式：默认为内置，仅在显式要求时为后备 CLI。
2. 确定意图：`generate` 或 `edit`。
3. 确定输出是仅预览还是用于当前项目。
4. 确定执行策略：单个资源、重复内置调用还是 CLI `generate-batch`。
5. 提前收集输入：提示、确切文本（逐字）、约束/避免列表和任何输入图像。
6. 对于每个输入图像，明确标注其角色：
   - 参考图像
   - 编辑目标
   - 支持插入/样式/合成输入
7. 如果编辑目标仅位于本地文件系统且保持在内置路径上，首先使用 `view_image` 检查它，以便图像在对话上下文中可用。
8. 如果用户要求照片、插图、精灵、产品图像、横幅或其他显式光栅风格资源，使用 `image_gen` 而不是替换 SVG/HTML/CSS 占位符。如果请求是图标、标志或应与现有仓库原生 SVG/矢量/代码资源匹配的 UI 图形，优先直接编辑这些资源。
9. 根据具体性增强提示：
   - 如果用户的提示已经具体且详细，将其规范化为清晰的规范，而不添加创意要求。
   - 如果用户的提示是通用的，仅在实质性提高输出质量时才添加得体的增强。
10. 默认使用内置 `image_gen` 工具。
11. 如果用户显式选择 CLI 后备模式，则仅在此情况下使用仅 CLI 文档进行质量、`input_fidelity`、掩码、输出格式、输出路径和网络设置。
12. 检查输出并验证：主题、风格、构图、文本准确性以及不变量/避免项。
13. 进行单次有针对性的更改，然后重新检查。
14. 对于仅预览的工作，直接内联渲染图像；底层文件可以保留在默认的 `$CODEX_HOME/generated_images/...` 路径。
15. 对于项目相关的工作，将选定的资源移动或复制到工作区，并更新任何消耗代码或引用。不要将项目引用的资源仅保留在默认的 `$CODEX_HOME/generated_images/...` 路径。
16. 对于批量处理，除非用户明确要求保留丢弃的变体，否则仅在工作区中持久化选定的最终结果。
17. 始终报告任何工作区相关资源的最终保存路径，以及最终提示和是否使用内置工具或后备 CLI 模式。

## 提示增强

将用户提示重新格式化为结构化、面向生产的规范。使用户的目标更清晰、更具可操作性，但不要盲目添加细节。

将其视为提示塑造指导，而不是封闭模式。仅使用有帮助的行，并在实质性提高清晰度时添加简短的额外标注行。

### 具体性策略

使用用户的提示具体性来决定适当的增强程度：

- 如果提示已经具体且详细，保留其具体性并仅进行规范化和结构化。
- 如果提示是通用的，当它将实质性提高结果时，可以添加得体的增强。

允许的增强：
- 构图或框架提示
- 精细程度或预期用途提示
- 实用布局指导
- 合理的场景具体性，以支持声明的请求

不允许的增强：
- 请求未暗示的额外字符或对象
- 未暗示的品牌名称、口号、调色板或叙事高潮
- 除非周围布局支持，否则不要进行任意特定位置的放置

## 用例分类（确切 slugs）

将每个请求分类到以下其中一个类别，并在提示和参考中保持 slugs 一致。

生成：
- photorealistic-natural — 真实纹理和自然光照的随性/编辑式生活方式场景。
- product-mockup — 产品/包装拍摄、目录图像、商品概念。
- ui-mockup — 应用/网页界面模板和线框图；指定所需的精细程度。
- infographic-diagram — 结构化布局和文本的图表/信息图表。
- logo-brand — 标志/品牌探索，适合矢量。
- illustration-story — 漫画、儿童书籍艺术、叙事场景。
- stylized-concept — 风格驱动的概念艺术、3D/风格化渲染。
- historical-scene — 时期准确/世界知识场景。

编辑：
- text-localization — 翻译/替换图像中的文本，保留布局。
- identity-preserve — 试穿、场景中的人物；锁定面部/身体/姿势。
- precise-object-edit — 移除/替换特定元素（包括内部交换）。
- lighting-weather — 一天中的时间/季节/大气变化。
- background-extraction — 透明背景/干净抠图。
- style-transfer — 应用参考风格，同时更改主题/场景。
- compositing — 多图像插入/合并，匹配光照/透视。
- sketch-to-render — 绘图/线稿到照片级渲染。

## 共享提示模式

使用以下标注规范作为两种顶层模式的共享提示框架：

```text
Use case: <taxonomy slug>
Asset type: <资源将用于何处>
Primary request: <用户的主要提示>
Input images: <Image 1: 角色; Image 2: 角色>（可选）
Scene/backdrop: <环境>
Subject: <主要主题>
Style/medium: <照片/插图/3D 等>
Composition/framing: <广角/近景/俯视; 位置>
Lighting/mood: <光照 + 情绪>
Color palette: <调色板笔记>
Materials/textures: <表面细节>
Text (verbatim): "<确切文本>"
Constraints: <必须保留/必须避免>
Avoid: <负面约束>
```

注释：
- `Asset type` 和 `Input images` 是提示框架，不是专用的 CLI 标志。
- `Scene/backdrop` 指的是视觉环境。它不是后备 CLI `background` 参数，后者控制输出透明度行为。
- 仅 CLI 路径的后备执行注释，如 `Quality:`, `Input fidelity:`, 掩码、输出格式和输出路径，仅适用于显式 CLI 路径。不要将它们视为内置 `image_gen` 工具参数。

增强规则：
- 保持简短。
- 仅添加实质性提高提示所需的细节。
- 对于编辑，明确列出不变量（`仅更改 X; 保留 Y 不变`）。
- 如果任何关键细节缺失且阻止成功，请提问；否则继续。

## 示例

### 生成示例（英雄图像）
```text
Use case: product-mockup
Asset type: landing page hero
Primary request: 一个简约的陶瓷咖啡杯英雄图像
Style/medium: 干净的产品摄影
Composition/framing: 广角构图，如有必要，页面复制有可用负空间
Lighting/mood: 柔和的影棚光照
Constraints: 无标志、无文本、无水印
```

### 编辑示例（不变量）
```text
Use case: precise-object-edit
Asset type: 产品照片背景替换
Primary request: 仅替换背景为温暖的日落渐变
Constraints: 仅更改背景；保留产品和其边缘不变；无文本；无水印
```

## 提示最佳实践
- 将提示按场景/背景 -> 主题 -> 细节 -> 约束的结构化。
- 包括预期用途（广告、UI 模板、信息图表）以设置模式和精细程度。
- 使用相机/构图语言以实现照片级真实感。
- 仅在用户明确要求矢量输出或非图像占位符时使用 SVG/矢量占位符。
- 引用确切文本并指定字体 + 位置。
- 对于难词，逐字母拼写并要求逐字渲染。
- 对于多图像输入，通过索引引用图像并描述其应如何使用。
- 对于编辑，每次迭代重复不变量以减少漂移。
- 进行单次更改的后续迭代。
- 如果提示是通用的，仅添加将实质性帮助的额外细节。
- 如果提示已经详细，则规范化它而不是扩展它。
- 对于显式 CLI 后备模式，请参阅 `references/cli.md` 和 `references/image-api.md` 以获取 `quality`、`input_fidelity`、掩码、输出格式和输出路径指导。

两种模式共享的原则：`references/prompting.md`。
共享的规范/占位符：`references/sample-prompts.md`。

## 仅后备 CLI 模式

### 临时和输出约定
这些约定仅适用于显式 CLI 后备。它们不描述内置 `image_gen` 输出行为。
- 使用 `tmp/imagegen/` 存储中间文件（例如 JSONL 批次）；完成后删除它们。
- 将最终资源写入 `output/imagegen/`。
- 使用 `--out` 或 `--out-dir` 控制输出路径；保持文件名稳定且描述性。

### 依赖项
在此仓库中优先使用 `uv` 进行依赖项管理。

必需的 Python 包：
```bash
uv pip install openai
```

仅用于缩小尺寸的选项：
```bash
uv pip install pillow
```

可移植性说明：
- 如果您在仓库外使用安装的技能，请使用其包管理器将依赖项安装到该环境。
- 在 `uv` 管理的环境中，`uv pip install ...` 仍然是首选路径。

### 环境
- `OPENAI_API_KEY` 必须设置以进行实时 API 调用。
- 使用内置 `image_gen` 工具时，不要要求用户提供 `OPENAI_API_KEY`。
- 永远不要要求用户在聊天中粘贴完整密钥。请他们本地设置密钥并在准备好时确认。

如果密钥缺失，请向用户提供以下步骤：
1. 在 OpenAI 平台 UI 中创建 API 密钥：https://platform.openai.com/api-keys
2. 在其系统中将 `OPENAI_API_KEY` 设置为环境变量。
3. 如果需要，提供指导以帮助他们为操作系统/外壳设置环境变量。

如果在此环境中无法安装，请告知用户缺少哪个依赖项以及如何将其安装到活动环境。
