# 命令行界面创建器

通过命令名在任何工作目录中运行，为未来的 Codex 线程创建一个真实的命令行界面。

这项技能适用于持久化工具，而不是一次性脚本。如果当前仓库中的简短脚本可以解决任务，请直接在那里编写脚本。

## 开始

命名目标工具、其来源以及它应该首先执行的真实任务：

- 来源：API 文档、OpenAPI JSON、SDK 文档、curl 示例、浏览器应用程序、现有的内部脚本、文章或工作 shell 历史记录。
- 任务：字面读取/写入，例如 `list drafts`、`download failed job logs`、`search messages`、`upload media`、`read queue schedule`。
- 安装名称：一个简短的二进制名称，例如 `ci-logs`、`slack-cli`、`sentry-cli` 或 `buildkite-logs`。

当用户想要一个个人工具并且尚未命名仓库时，优先在 `~/code/clis/<tool-name>` 下创建一个新文件夹。

在搭建之前，检查提议的命令是否已经存在：

```bash
command -v <tool-name> || true
```

如果存在，选择一个更清晰的安装名称或询问用户。

## 选择运行时

在做出选择之前，检查用户的机器和来源材料：

```bash
command -v cargo rustc node pnpm npm python3 uv || true
```

然后选择最不令人意外的工具链：

- 默认使用 **Rust** 为任何仓库中 Codex 应运行的持久化命令：一个快速的二进制文件、强大的参数解析、良好的 JSON 处理、易于复制/安装到 `~/.local/bin`。
- 当官方 SDK、认证辅助工具、浏览器自动化库或现有仓库工具是 CLI 可以更好的原因时，使用 **TypeScript/Node**。
- 当来源是数据科学、本地文件转换、笔记本、SQLite/CSV/JSON 分析或仍然可以作为持久化命令安装的 Python 重度管理工具时，使用 **Python**。

除非它实质性地改进了 CLI，否则不要选择增加设置摩擦的语言。如果最佳语言未安装，则要么在获得用户同意的情况下安装缺失的工具链，要么选择下一个最佳已安装选项。

在搭建之前，用一句话说明选择，包括原因和找到的已安装工具链。

## 命令契约

在编码之前，在聊天中勾勒出命令界面。包括二进制名称、发现命令、解析或 ID 查找命令、读取命令、写入命令、原始逃生通道、认证/配置选择和 PATH/安装命令。

在设计命令界面时，阅读 [references/agent-cli-patterns.md](references/agent-cli-patterns.md) 以获取预期的可组合 CLI 形状。

朝着这个界面构建：

- `tool-name --help` 显示所有主要功能。
- `tool-name --json doctor` 验证配置、认证、版本、端点可达性和缺失设置。
- `tool-name init ...` 在环境认证令人痛苦时存储本地配置。
- 发现命令查找账户、项目、工作区、团队、队列、频道、仓库、仪表板或其他顶级容器。
- 解析命令将名称、URL、缩写、永久链接、客户输入或构建链接转换为稳定 ID，以便未来的命令不会重复广泛的搜索。
- 读取命令获取确切对象并列出/搜索集合。分页列表支持有界的 `--limit`、游标、偏移量或明确记录的默认值。
- 写入命令执行每个命名的操作：创建、更新、删除、上传、调度、重试、评论、草稿。它们接受最窄的稳定资源 ID，支持在服务允许的情况下首先使用 `--dry-run`、`draft` 或 `preview`，并且不会将写入隐藏在 `fix`、`debug` 或 `auto` 等广泛命令中。
- `--json` 返回稳定的机器可读输出。
- 存在一个原始逃生通道：`request`、`tool-call`、`api` 或最诚实的名称。

不要只暴露一个通用的 `request` 命令。给 Codex 高级动词以重复的作业。

在 CLI README 或等效文档中记录 JSON 策略：API 透传与 CLI 信封、成功形状、错误形状以及每个命令家族的一个示例。在 `--json` 下，错误必须是机器可读的，并且不能包含凭证。

## 认证和配置

首先支持无聊的路径，按此优先级顺序：

1. 使用服务的标准名称的环境变量，例如 `GITHUB_TOKEN`。
2. 用户配置在 `~/.<tool-name>/config.toml` 或另一个简单的记录路径下。
3. 仅用于显式一次性测试的 `--api-key` 或特定于工具的令牌标志。对于正常使用，优先选择环境/配置，因为标志可能会泄漏到 shell 历史记录或进程列表中。

永远不要打印完整的令牌。`doctor --json` 应该说明令牌是否可用、认证来源类别（`flag`、`env`、`config`、提供程序默认值或缺失），以及缺失的设置步骤。

如果 CLI 可以在没有网络或认证的情况下运行，请在 `doctor --json` 中明确说明：报告固定/离线模式、是否找到固定数据以及该模式下是否不需要认证。

对于从 DevTools curl 源的自定义 Web 应用程序，在实现之前创建清理的端点笔记：资源名称、方法/路径、必需的标头、认证机制、CSRF 行为、请求正文、响应 ID 字段、分页、错误和一个脱敏的示例响应。永远不要提交复制的 cookie、bearer 令牌、客户机密或完整的生产有效负载。

使用截图来推断工作流、UI 词汇、字段和确认点。除非它们与网络请求、导出、文档页面或固定配对，否则不要将截图视为 API 证据。

## 构建工作流

1. 读取来源，仅足以列出资源、认证、分页、ID、媒体/文件流、速率限制和危险写入操作。如果文档暴露 OpenAPI，则在命名命令之前下载或检查它。
2. 在聊天中勾勒出命令列表。保持名称简短且适合 shell。
3. 使用 README 或等效的面向仓库说明搭建 CLI。
4. 实现 `doctor`、发现、解析、读取命令，如果请求，则一个狭窄的草稿或干运行写入路径，以及原始逃生通道。
5. 在 PATH 上安装 CLI，以便 `tool-name ...` 在来源文件夹外工作。
6. 从另一个仓库或 `/tmp` 进行冒烟测试，而不仅仅是使用 `cargo run` 或包管理器包装器。运行 `command -v <tool-name>`、`<tool-name> --help` 和 `<tool-name> --json doctor`。
7. 运行格式、类型检查/构建、请求构建器、分页/请求正文构建器、无认证 `doctor`、帮助输出，以及至少一个固定、干运行或实时只读 API 调用。

如果需要实时写入以获得信心，请先询问，并使其可逆或仅限草稿。

当来源是现有脚本或 shell 历史记录时，将工作调用分解为真实阶段：设置、发现、下载/导出、转换/索引、草稿、上传、轮询、实时写入。保留用户已经依赖的标志、路径和环境变量，然后将可重复的阶段用稳定 ID、有界 JSON 和文件输出包装。

对于原始逃生通道，首先支持只读调用。除非用户请求了特定的写入，否则不要对实时服务运行原始非 GET/HEAD 请求。

对于媒体、工件或预签名上传流，分别测试每个阶段：创建上传、传输字节、轮询/读取处理状态，然后附加或引用生成的 ID。

对于基于固定的原型，将固定保存在可预测的项目路径中，并在安装后让 CLI 定位它们。从 `/tmp` 进行冒烟测试，以捕获仅在来源文件夹内工作的二进制文件。

对于面向日志的 CLI，将确定性片段提取与模型解释分开。优先选择一个发出文件名、行号或字节范围、匹配规则和简短摘录的命令。

## Rust 默认值

在 Rust 中构建时，使用已建立的 crate 而不是自定义解析器：

- `clap` 用于命令和帮助
- `reqwest` 用于 HTTP
- `serde` / `serde_json` 用于有效负载
- `toml` 用于小型配置文件
- `anyhow` 用于 CLI 形状的错误上下文

添加一个 `Makefile` 目标，例如 `make install-local`，构建发布版本并将二进制文件安装到 `~/.local/bin`。

## TypeScript/Node 默认值

在 TypeScript/Node 中构建时，保持 CLI 可作为正常命令安装：

- `commander` 或 `cac` 用于命令和帮助
- 原生 `fetch`、官方 SDK 或用户现有的 HTTP 辅助工具用于 API 调用
- 仅在防止实际损坏的外部有效负载验证的情况下使用 `zod`
- `package.json` `bin` 条目用于安装的命令
- `tsup`、`tsx` 或 `tsc` 使用仓库现有的约定

添加安装路径，例如 `pnpm install`、`pnpm build` 和 `pnpm link --global`，或一个将小型包装器安装到 `~/.local/bin` 的 `Makefile` 目标。

## Python 默认值

在 Python 中构建时，除非工作流需要更多，否则优先选择无聊的标准库组件：

- `argparse` 用于命令和帮助，或在子命令否则会变得杂乱时使用 `typer`
- `urllib.request` / `urllib.parse`、`requests` 或 `httpx` 用于 HTTP，匹配已安装的或附近已使用的
- `json`、`csv`、`sqlite3`、`pathlib` 和 `subprocess` 用于本地文件、导出、数据库和现有脚本
- `pyproject.toml` 控制台脚本或一个小型可执行包装器用于安装的命令
- `uv` 或虚拟环境仅在依赖项确实需要时

添加一个 `Makefile` 目标，例如 `make install-local`，将命令安装到 PATH，并记录它是否依赖于 `uv`、虚拟环境或仅系统 Python。

## 伴侣技能

CLI 工作后，为其创建或更新一个小型技能。当 `$skill-creator` 可用时使用它。使用 `$CODEX_HOME/skills/<tool-name>/SKILL.md` 为个人伴侣技能，除非用户命名了仓库本地 `.codex/skills/...` 路径或另一个技能仓库。

按照未来 Codex 线程应使用 CLI 的顺序编写伴侣技能，而不是作为每个功能的巡游。解释：

- 如何验证已安装的命令是否存在。
- 首先运行哪个命令。
- 认证如何配置。
- 哪个发现命令查找常见 ID。
- 安全的读取路径。
- 意图草稿/写入路径。
- 原始逃生通道。
- 没有明确用户批准不要做什么。
- 三个可复制粘贴的命令示例。

将 API 参考细节保留在 CLI 文档或技能参考文件中。保持技能专注于顺序、安全性和未来 Codex 线程应实际运行的示例。
