# 安全漏洞验证

判断一个安全漏洞是否为真实阳性或假阳性，并提供支持性证据进行判定。

## 输入

用户通过文件路径或粘贴文本提供漏洞信息。如果未提供任何信息，则提示用户输入。

提取：漏洞类别、具体声明、受影响端点、代码位置以及任何现有的验证证据。

## 验证工作流程

### 第一步：理解漏洞信息

识别：
- 漏洞类别（BFLA、BOLA、XSS、SQLi、SSRF 等）
- 具体声明（缺少何种授权检查、何种输入未进行清理等）
- 受影响的端点和 HTTP 方法
- 代码位置

### 第二步：分析源代码

1. 读取指定行号的有缺陷的文件以及所有支持文件
2. 从路由注册开始，跟踪请求流程通过中间件到处理程序
3. 验证具体声明——代码是否确实缺少所描述的检查？
4. 查找扫描器可能遗漏的间接保护措施（中间件、辅助函数、ORM 约束）
5. 确认在所描述条件下，有缺陷的代码路径是可访问的

### 第三步：实时验证（当可用时）

如果可以访问应用程序的实时实例，并且可以通过实时交互确认漏洞，则使用 `proxy` 技能确认可利用性：

1. 启动针对目标域的 reaper 代理
2. 以合法用户身份进行身份验证（或让用户进行身份验证），捕获对有缺陷端点的有效请求
3. 重放或修改请求以尝试在漏洞信息中描述的漏洞利用
4. 将响应与预期行为进行比较：
   - 未授权操作是否成功？（真实阳性）
   - 服务器是否用 401/403/404 拒绝？（假阳性）
5. 使用 `reaper get <id>` 捕获请求/响应对作为证据

### 第四步：做出判定

将漏洞信息归类为以下之一：

- **真实阳性**：漏洞存在且可利用。代码缺少所描述的保护措施，且端点是可访问的。
- **真实阳性（已确认）**：与上述情况相同，并且实时测试显示了成功的漏洞利用。
- **假阳性**：漏洞不存在。提供具体原因（发现间接保护措施、代码路径不可访问等）。
- **无法确定**：无法确定，需要更多信息。指定需要什么信息。

### 第五步：报告

以以下格式输出摘要：

1. **判定**：真实阳性、假阳性或无法确定
2. **置信度**：高、中或低
3. **证据摘要**：代码审查和/或实时测试的关键发现
4. **代码分析**：支持判定特定行和逻辑
5. **实时测试结果**（如果执行）：显示行为的请求/响应对
6. **建议**：如果是真实阳性则修复，如果是假阳性则关闭，如果是无法确定则收集更多信息

示例：

```
## 验证结果
- **判定**：真实阳性
- **置信度**：高
- **证据**：在 routes/transfers.go:142 的处理程序查询 ID 而未检查所有权。没有中间件或 ORM 级别的约束强制执行用户范围。
- **建议**：添加所有权检查——在 WHERE 子句中包含 user_id。
```

### 第六步：持久化结果

如果漏洞信息是以文件路径提供的，则询问用户是否希望将验证详细信息追加到原始漏洞文件中。如果他们同意，则将包含判定、置信度、证据摘要和建议的 `## 验证` 部分追加到文件中。
