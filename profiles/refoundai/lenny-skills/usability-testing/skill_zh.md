# 可用性测试

帮助用户使用来自11位产品领导者的框架和见解进行有效的可用性测试。

## 如何提供帮助

当用户需要关于可用性测试的帮助时：

1. **明确目标** - 确定他们是在验证概念、寻找摩擦点还是优化转化
2. **选择合适的保真度** - 帮助他们选择在魔术师测试、虚假门、原型或生产测试之间进行选择
3. **设计测试** - 指导他们进行用户招募、场景创建以及需要观察的内容
4. **规划迭代** - 讨论如何将发现结果反馈到产品开发过程中

## 核心原则

### 在构建前先伪造它
Itamar Gilad：“最初你需要伪造它——进行虚假门测试、烟雾测试、魔术师测试。我们向人们展示了标签式收件箱的工作情况，但它并不是真正的Gmail，只是一个外壳。” 在编写生产代码之前，使用伪造版本来验证核心价值主张，其中人类在幕后执行自动任务。

### 小样本揭示大摩擦
Melanie Perkins：“你简直难以置信，只需在互联网上找到10个随机的人，他们就能给出如此敏锐的反馈，这些反馈对于如此多的人来说是如此具有代表性。” 使用尽可能少的10个随机人员进行测试，以识别核心产品问题。

### 观察用户，而不仅仅是询问他们
Uri Levine：“只需观察用户正在做什么。如果他们没有做你期望的事情，那么就问他们为什么。” 直接观察揭示了调查遗漏的行为和需求。当用户偏离预期路径时，询问“为什么”。

### 测试多个选项，而不是一个
Kristen Berman：“我们从不进行只向人们展示一件事的UX研究。我们总是展示多个选项，并相对地寻找哪个能驱动预期的行为。” 单一设计测试对于预测行为是无效的。

### 克服创造者偏见
Guillermo Rauch：“你倾向于高估你的产品的工作效果。将你的产品交给另一个人并观察他们如何与之互动非常重要。” 直接观察用户有助于克服认为你的产品比实际更直观的倾向。

### 微观层面的测试驱动百万
Judd Antin：“我们更改了七个字符，使Airbnb获得了数百万美元，因为我们发现按钮让人感到害怕。” 不要将可用性测试视为初级工作；找到令人害怕或令人困惑的CTA可能会极大地影响转化。

### 通过测试阶段进行进展
Itamar Gilad：“中级测试是构建一个粗略版本——早期采用者计划、阿尔法测试、纵向用户研究以及鱼食（在你的团队中测试）。” 使用从鱼食到狗食再到阿尔法的逐步过程来迭代增加信心。

### 使测试成为团队运动
Noah Weiss：“我们所有的产品经理、工程师、设计师和用户研究员都在同一个Slack线程中实时参与，并对可用性测试做出反应。” 通过让跨职能团队在共享聊天线程中实时对测试做出反应来增加参与度。

## 帮助用户的提问

- “你试图观察或验证的具体行为是什么？”
- “你需要验证概念（使用虚假门）还是优化执行（使用真实产品）？”
- “你将如何招募对产品没有利害关系、能够提供诚实反馈的用户？”
- “你是在测试一个选项还是多个选项进行比较？”
- “你将如何处理发现结果——它们将如何反馈到开发中？”
- “团队中还有谁应该观察这些测试会话？”

## 常见错误提示

- **只测试一个设计** - 展示多个选项来衡量相对性能
- **在验证前构建** - 在编写生产代码之前使用魔术师测试或虚假门测试
- **依赖内部直觉** - 员工对产品过于熟悉，无法发现真正的用户摩擦
- **忽略微观层面的问题** - 小的文案更改和按钮标签可能对业务产生巨大影响
- **孤立测试** - 将工程师和设计师带入会话中，以建立共同的理解
