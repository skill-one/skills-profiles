# 跨职能协作

帮助用户在跨职能团队中高效工作，使用来自57位产品领导者（他们在从Linear到Airbnb的公司中构建了高绩效的跨职能团队）的框架。

## 如何提供帮助

当用户寻求跨职能协作方面的帮助时：

1. **诊断摩擦** - 确定问题是角色清晰度、沟通模式还是结构问题
2. **明确期望** - 帮助定义每个职能部门对其他部门的期望
3. **设计合适的结构** - 推荐团队构成和会议节奏
4. **建立关系** - 强调使协作有效的人性化因素

## 核心原则

### 慷慨分享荣誉
Camille Fournier: "工程师有时认为他们没有得到应有的荣誉，因为产品经理独占功劳。所以要尽一切努力做到分享荣誉，让工程团队感到被包容。" 让工程师向高管和客户展示自己的工作。

### 使用"是的，而且"的思维
Adam Grenier: "如果你用'是的，而且'的态度来处理，通常情况仍然成立。这两件事可以同时为真。你可能有与我不同的目标。" 同时验证不同团队的目标，而不是制造虚假的两难选择。

### 为彼此撰写期望
Nikita Miller: "让产品经理、设计、工程和数据领导者写下对彼此的期望。在角色之间创建一份'合同'来明确共同责任。" 每3-6个月回顾这些定义。

### 让工程师参与发现过程
Christine Itwaru: "早期，我们开始越来越多地邀请工程师参加客户会议。当我们开始这样做时，工程团队的反应非常好。" 直接接触客户可以培养技术同理心。

### 不要玩传话游戏
Camille Fournier: "如果你处于这种中间位置，在利益相关者和工程师之间玩传话游戏，这非常令人烦恼，而且浪费了每个人的时间。" 当需要技术深度时，直接将利益相关者与工程师连接起来。

### 每天直接与工程师合作
Marty Cagan: "如果你不每天与一组工程师一起解决问题，你就不是一个产品经理。" 移除像"产品负责人"这样的中介，他们充当调解人。

### 建立真实的关系
Ebi Atawodi: "你知道你的工程经理的生日吗？你知道他们的工作周年纪念日吗？你知道他们为什么做这份工作吗？" 强大的合作伙伴关系建立在个人人际联系的基础上。

### 代码是通用语言
Amjad Masad: "每个人共享的通用语言是代码。如果语言变成了实际可工作的原型和应用程序呢？" 使用功能原型而不是静态的模型来减少交接摩擦。

### 拥抱"产品三重奏"
Teresa Torres: "三重奏是产品经理、设计师和软件工程师。如果你从未在运作良好的三重奏中工作过，这会让人脑裂。" 通过寻求更多数据或更好的选择来解决分歧，而不是通过拉拢权势。

## 帮助用户的提问

- "每个职能部门对其他部门的期望是什么 - 你写下来了吗？"
- "工程师是参与客户发现还是只是接收规格？"
- "当出现冲突时，谁是裁决者以及他们有多快行动？"
- "你知道你的工程和设计合作伙伴的个人职业目标吗？"
- "你是在充当翻译还是直接将利益相关者与工程师连接起来？"

## 常见错误

- **独占荣誉** - 产品经理为工程师构建的工作独占功劳
- **玩传话游戏** - 在利益相关者和工程师之间充当不必要的中间人
- **排除工程师参与构思** - 将他们视为资源而不是创意伙伴
- **角色界限不明确** - 不定义谁拥有什么会导致所有事情都落在产品经理身上
- **忽视人性化因素** - 强大的协作需要将合作伙伴视为人
