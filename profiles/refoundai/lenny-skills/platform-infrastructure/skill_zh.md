# 平台基础设施

利用来自5位产品及工程领导者的见解，帮助用户设计和扩展内部平台和共享技术基础设施。

## 如何提供帮助

当用户需要平台基础设施方面的帮助时：

1. **理解平台的目的** - 询问他们是为内部开发者、外部合作伙伴还是两者同时构建
2. **评估组织准备情况** - 确定他们是否具备支持平台采用和治理结构
3. **识别杠杆点** - 帮助他们找到平台投资能创造最大价值乘数的点
4. **为采用设计** - 确保平台解决的是真实开发者的问题，而非理论问题

## 核心原则

### 将通用能力抽象为共享基础设施
Daniel Lereya: "我们第一次停下来思考，'什么是列？' 我们还围绕它组织了所有产品架构... 添加新列的工作只是思考特定内容。" 扩展功能速度需要将重复组件抽象为共享基础设施，以便开发者只关注独特逻辑。

### 隐形基础设施往往最重要
Asha Sharma: "不是数百个功能，而是基础设施和平台... 性能、可靠性、隐私、安全，所有这些。" 大型平台的成功往往取决于可靠性、速度等"隐形"品质，而非可见功能。

### 在需要之前就为扩展做规划
Ivan Zhao: "在COVID期间，我们无法扩展基础设施。很长一段时间里，西蒙真的很擅长不做过早优化... 我们甚至在使用最大的Postgres实例。" 虽然避免过早优化是好事，但基础设施必须提前规划足够远，以避免使用激增时的"末日"场景。

### 在架构中构建可发现性
Eli Schwartz: "如果你创建一个分类的站点地图，你可以说，'这些都是关于健康的所有问题，来自站点地图... 然后，搜索引擎可以浏览整个网站，所有的问题和答案都是可发现的.'" 对于大规模平台，HTML站点地图和内部链接等结构决策对于搜索引擎可发现性至关重要。

### 默认采用服务器端跟踪
Vijay: "最大的错误是使用客户端SDK设置分析... 从服务器而不是从客户端开始跟踪事件。" 服务器端跟踪比客户端SDK在数据可靠性、跨平台一致性和开发者维护方面更优越。

## 帮助用户的问题

- "这个平台的'用户'是谁，他们今天试图解决什么问题？"
- "当前导致生产力损失最多的开发者体验痛点是什么？"
- "你将如何衡量这个平台是否真的被采用？"
- "这是构建还是购买的决定，还是应该暂时保持手动流程？"
- "你的'末日时钟'是什么 - 当前基础设施何时会达到极限？"

## 常见错误

- **为抽象的未来构建** - 基于预期需求而非当前开发者痛点创建能力
- **没有产品所有权的平台** - 将基础设施视为没有专门产品管理的技术项目
- **直到太晚才避免过早优化** - 不监控基础设施限制以触发在失败前进行扩展项目
- **默认采用客户端跟踪** - 使用浏览器SDK而不是服务器端事件跟踪
- **忽略迁移成本** - 在不考虑将团队从现有解决方案迁移的努力的情况下构建新平台
