# 编写 OpenSpec 文档

你现在正在编写 OpenSpec 的用户文档。阅读 [writing.md](writing.md)；它是此处所有草稿的风格指南。立即生效的简要版本：

- 一页是一个检索表面，而不是一篇散文。结构决定读者是否找到答案；散文只决定它如何阅读。每个部分都以答案开头，而不是一个连续的故事。
- 在制定提纲之前选择页面类型。指南跟随读者的任务；参考反映产品的结构，并使用确切的字段、命令和文件名作为扫描锚点。参考需要完整覆盖，不要将多个事实压缩成一句、一个单元格或一个段落。
- 起草能回答问题的最短版本；扩展一个空白的页面很便宜，缩减一个臃肿的页面是重写。用简单的词语，尽量少用：一个能在一行中表达的想法占用一行。大多数读者跳过的深度内容放在链接后面，有效载荷（命令、实际输出、失败和修复）保持完整。
- 愚蠢的句子，智能的结构。写出显而易见的句子（行动者、动词、宾语、陈述字面事件）；不要压缩额外的事实或采取角度。没有夸张的形容词，没有开场白，没有破折号。
- 每个插槽只做一项工作：每句话一个事实，列表介绍只宣布列表，每个部分只有一个读者问题或查找目标。相关的事实得到自己的插槽，永远不会搭便车。
- 将项目基于读者可以验证的内容：路径或文件夹首先，概念作为术语，真实输出诚实展示。
- 没有房屋模板。清单以列出每个项目的列表开头，然后在列表后在各自的单元中扩展每个项目，永远不会内联。序列使用编号步骤（数字表示顺序；清单使用项目符号）。单个想法和推理保持在简短的散文中。
- 每个承重事实都位于扫描锚点上：代码围栏、编号粗体引言、`**术语**：事实`项目符号、表格、文件树。永远不会只在段落中间。
- 完成之前，运行两个后备测试。可检索性：是否可以通过扫描单独找到每个问题或确切的产品名称？一瞥：检查渲染页面的形状；它看起来可以完成，还是像工作？检查表格密集更改在桌面和窄宽度。失败意味着没有获得报酬就写了插槽；现在修复它，不要留待审核。

## 基本规则

- 在起草之前加载 `no-ai-slop` 技能；它拥有通用杂乱模式，而 [writing.md](writing.md) 拥有 OpenSpec 文档具体看起来和听起来的样子。
- 编辑之前完整阅读目标页面。
- 只有真实事实：标志、路径和源中存在的输出。如果一个声明不能廉价地检查，仍然写它，但在展示工作时将其命名为未检查；永远不会用一个听起来合理的句子来弥补差距。
- 一个事实存在于一个页面上；其他地方链接到它。文档树的 README 拥有页面映射和结构不变量；在重构或添加页面之前检查它。
- 对于参考页面，在起草散文之前从源中列出合同。遵循 [writing.md](writing.md#reference-pages) 中的参考页面过程。
- 当不确定某件事应该扫描或听起来如何时，匹配示例：`docs-lab/start/setup.md` 用于部分形状和清单，`docs-lab/start/installation.md`（卸载）用于多步骤任务。

## 完成时

向用户展示更改并命名任何未检查的声明。

如果用户要求深入的、以证据为先的起草会话（运行每个命令，每节一个会话，正式检查点），请遵循 [full-process.md](full-process.md)。
