实现来自 OpenSpec 变更的任务。

**商店选择**：如果用户指定了一个商店（商店是一个独立于 OpenSpec 仓库的注册在本机上的商店）或工作存在于其中，运行 `openspec store list --json` 来发现注册的商店 ID，然后在读取或写入规范的命令（`new change`、`status`、`instructions`、`list`、`show`、`validate`、`archive`、`doctor`、`context`、`schemas`、`view`）上传递 `--store <id>`。一旦选定，将 `--store <id>` 视为整个工作流程中的粘性选项。下面未限定范围的示例命令是简写：在运行它之前，附加该标志。例如，运行 `openspec status --change "<name>" --json --store "<id>"`，而不是下面显示的无限定范围形式。其他命令不接受该标志。命令打印的提示信息已经包含该标志；在后续操作中保持它。没有商店时，命令作用于最近的本地 `openspec/` 根目录。

**项目检查**：这些步骤期望一个已经使用 OpenSpec 的项目。在第一个写入任何内容的步骤（`new change`、`archive`、`sync specs` 或编写工件文件）之前，确认项目有一个根：运行 `openspec list --json`（如果选择了商店，则使用 `--store <id>`，因为商店是根）并读取 `root`。根对象表示项目已设置。`"root": null` 表示未设置 - 这里没有 `openspec/` 目录，并且写入操作（如 `openspec new change`）会作为副作用创建一个。该命令退出非零状态，这是答案而不是损坏的 CLI，因此请读取 JSON 而不是重试或绕过它。

一个 `"root": null` 并不是关于设置：当 `status` 错误消息以 `Declared in` 或 `Invalid store declaration in` 开头并命名为此项目的 `openspec/config.yaml`（或 `config.yml`）时，该项目通过它声明的商店使用 OpenSpec，但此机器无法解析（商店未注册，或 `store:` 行格式不正确）。不要将其视为未初始化并跳过下面的分支：在写入之前停止并显示该错误的 `message` 和 `fix`。

否则，没有根时，接下来会发生什么取决于如何进入此工作流程：

- **自动选择**：您自己选择了此工作流程，而未指定 OpenSpec、指定此技能或运行其斜杠命令。停止使用 OpenSpec 并像未安装 OpenSpec 时一样正常回答请求。不要要求他们设置任何内容，也不要提及 OpenSpec 设置。
- **明确的 OpenSpec 请求**：用户指定了 OpenSpec、指定了此技能或运行了其斜杠命令。在写入之前停止并询问如何进行：设置此项目（`openspec init`）、目标他们已有的商店（`--store <id>`）或继续不使用 OpenSpec 处理此请求。等待他们的回答。

在这两个分支中，永远不要作为副作用创建根：在用户要求之前不要运行 `openspec init`，不要手动创建 `openspec/` 文件，也不要让命令创建它。

**输入**：可选地指定变更名称（例如，`/openspec-apply-change add-auth`）。如果省略，则检查是否可以从对话上下文中推断。如果模糊或歧义，您必须提示可用的变更。

**步骤**

1. **选择变更**

   如果提供了名称，则使用它。否则：
   - 如果用户在对话中提到了变更，则从对话上下文中推断
   - 如果只有一个活动变更，则自动选择
   - 如果不明确，则运行 `openspec list --json` 获取可用变更并要求用户选择一个

   始终宣布：`"使用变更: <name>"` 以及如何覆盖（例如，`/openspec-apply-change <other>`）。

2. **检查状态以了解架构**
   ```bash
   openspec status --change "<name>" --json
   ```
   解析 JSON 以了解：
   - `schemaName`：使用的工作流程（例如，"spec-driven"）
   - `planningHome`、`changeRoot` 和 `actionContext`：规划范围和编辑约束
   - 哪个工件包含任务（通常对于 spec-driven 是 "tasks"，对于其他架构检查状态）

3. **获取应用说明**

   ```bash
   openspec instructions apply --change "<name>" --json
   ```

   这返回：
   - `contextFiles`：工件 ID -> 具体文件路径数组（因架构而异 - 可能是提案/规范/设计/任务或规范/测试/实现/文档）
   - 进度（总数、完成数、剩余数）
   - 带有状态的任务列表
   - 基于当前状态的动态说明
   - 可选的 `context`：从选定的根当前需要的项目说明输入
   - 可选的 `operationGuidance`：当前用于应用的建议指导
   - `missingArtifacts`（当存在时）：没有输出的所需工件 ID

   **处理状态：**
   - 如果 `state: "blocked"`：显示消息并暂停实现。
     - 如果 `missingArtifacts` 非空：建议使用 `/openspec-continue-change` 创建它们。
     - 否则，按照 CLI 说明从现有的规划工件创建或修复架构配置的跟踪文件。不要假设另一个工件已准备好或在阻塞时开始实现。
   - 如果 `state: "all_done"`：祝贺并建议存档
   - 否则：继续实现

   将 `context` 视为提示级别的必需输入。读取并考虑它，并在实现时应用相关的项目事实、约定和约束。
   将 `operationGuidance` 视为可选的附加建议。读取并考虑每个条目，并遵循适用且与内置工作流程兼容的条目。

   将这两个字段与 CLI 返回的状态、缺失工件、任务、进度、`contextFiles` 和内置 `instruction` 分开。它们不是任务完成的证据，不会取代内置说明，也不会允许绕过阻塞状态。如果上下文与内置说明、明确的用户选择或 CLI 控制的值冲突，请报告冲突并保留控制值。如果指导不适用或与这些控制输入冲突，请不要遵循它并解释原因。这些是提示级别的行为合同，不是强制性的检查。

4. **读取上下文文件**

   从应用说明输出中读取 `contextFiles` 下列出的每个文件路径。这些文件取决于使用的架构：
   - **spec-driven**：提案、规范、设计、任务
   - 其他架构：遵循 CLI 输出的 `contextFiles`

   除非用户单独要求，否则不要将 `context` 或 `operationGuidance` 原封不动地复制到实现文件或规划工件中。

5. **显示当前进度**

   显示：
   - 使用的架构
   - 进度："N/M 任务完成"
   - 剩余任务概述
   - 来自 CLI 的动态说明

6. **实现任务（循环直到完成或阻塞）**

   对于每个待处理的任务：
   - 显示正在处理的任务
   - 进行所需的代码更改
   - 保持更改最小且专注于每个任务
   - 在任务文件中标记完成：`- [ ]` → `- [x]`
   - 继续下一个任务

   **暂停如果：**
   - 任务不明确 → 请求澄清
   - 实现揭示设计问题 → 建议更新工件
   - 一个任务需要超出规范和任务描述的工作，或者您有动力放弃、缩小、推迟或接受指定行为的例外以使其适应 → 揭示增加的范围并暂停；不要无声地缩小、推迟或简化指定行为
   - 遇到错误或阻塞 → 报告并等待指导
   - 用户中断

7. **完成或暂停时显示状态**

   显示：
   - 本会话完成的任务
   - 总体进度："N/M 任务完成"
   - 如果全部完成：建议存档
   - 如果暂停：解释原因并等待指导

**实现期间输出**

```
## 正在实现: <change-name> (架构: <schema-name>)

正在处理任务 3/7: <任务描述>
[...实现正在进行中...]
✓ 任务完成

正在处理任务 4/7: <任务描述>
[...实现正在进行中...]
✓ 任务完成
```

```
- [x] 任务 2
```


**约束条件**
- 一直通过任务直到完成或阻塞
- 始终在开始之前读取上下文文件（来自应用说明输出）
- 如果任务不明确，在实现之前暂停并请求澄清
- 如果实现揭示问题，暂停并建议更新工件
- 保持代码更改最小且限定于每个任务
- 完成每个任务后立即更新任务复选框
- 遇到错误、阻塞或不明确的要求时暂停 - 不要猜测
- 当一个任务需要超出规范描述的工作时，揭示增加的范围并暂停 - 永远不要无声地缩小、推迟或简化指定行为
- 只有当指定行为完全实现时才将任务标记为 `- [x]`，而不是部分完成或推迟时
- 使用来自 CLI 输出的 `contextFiles`，不要假设特定的文件名
- 不要将 `context` 或 `operation guidance` 作为任务完成的证据
- 应用相关的项目上下文；报告与控制工作流程输入的冲突
- 考虑每个指导条目；解释任何不适用或冲突的建议
- 不要将运行时上下文或 `operation guidance` 复制到实现文件或规划工件中
- 保留 CLI 控制的阻塞/就绪/all-done 行为和完成标准

**流式工作流程集成**

此技能支持 "对变更采取行动" 模型：

- **可以随时调用**：在所有工件完成之前（如果存在任务），在部分实现之后，与其他操作交错
- **允许工件更新**：如果实现揭示设计问题，建议更新工件 - 不是阶段锁定，流畅工作
