# 验证 OpenSpec 文档

检查完成的文档文字与实际情况是否相符。新上下文的意义在于审阅者没有目睹这些文字的编写过程，因此不会被说服接受作者的假设。

这项技能只有在用户要求时才会运行。草稿工作由 `write-openspec-docs` 负责；除非用户要求进行验证，否则不要在草稿会话中调用此功能。

## 定义运行范围

1. 确认目标：一个页面、一个 `##` 部分，或一组已更改的声明。如果没有指定目标，则询问。
2. 阅读目标文档树根目录下的 README；其不变量和页面映射是检查的一部分。
3. 每个单元（一个 `##` 部分，或声明的声明列表）一个子代理。一个完整页面由多个并行运行的子代理组成。

## 生成审阅者

通用型子代理。子代理不会继承技能，因此提示信息通过路径传递所有内容。填充每个占位符，使每个路径绝对化，并发送：

```
你正在审阅 OpenSpec 的用户文档，在它到达文档所有者之前。成为它遇到的最严格的两位读者：一位怀疑的开发者冷读，以及一位打开仓库进行事实核查的人。

仓库根目录：<绝对仓库根目录>。使用绝对路径与每个工具。

首先阅读：
1. <文档树根目录>/README.md：页面映射和不变量。
2. <绝对仓库根目录>/.agents/skills/write-openspec-docs/writing.md：写作规则。
3. <页面路径>：仅审阅 <部分 "<标题>" | 这些更改的声明：<列表>>；为获取上下文，阅读页面的其余部分。

然后按顺序检查：

1. 事实。每个命令、标志、路径、配置键、输出块、默认值和行为声明。重新运行显示的终端命令：任何只读命令，任何在草稿目录中或根本不更改状态的命令。AI 聊天界面的命令（如 /opsx:propose）不能在 shell 中运行；根据此仓库提供的技能源验证其名称和行为。检查名称与 src/ 和 CLI 的 --help。输出块必须与命令实际打印的内容匹配。
2. 示例。任何示例规范或更改都必须通过 `openspec validate`。当示例存在于磁盘上时运行它。
3. 结构。标记任何重新解释主题的内容，其规范位置是另一个页面，或破坏文档树 README 中声明的规则的内容。
4. 工作匹配度。该单元是否服务于页面的声明工作（如果标题下有一行声明，则为该声明）？到达的读者是否能快速获得他们想要的内容？
5. 信任和随意性。标记：宣传或安慰形容词（容易、简单、强大、无缝）、没有显示证据的声明、模糊的概括而具体事实应属于、二元对比（"不是 X，而是 Y"）、冒号揭示、重要性夸张、总结结尾、破折号、应作为散文的编号列表，以及连续三个平行有力的句子。

仅报告结果，最严重的问题优先。对于每个问题：引用行号，说明错误，并给出一条修正建议。对于每个验证的事实，说明如何验证（运行的命令或检查的文件和行）。列出任何无法验证的声明及其原因。不要重写单元。如果单元干净，请说明并列出已验证的内容。
```

## 处理报告

- 默认是报告而不是重写：按最严重问题优先顺序向用户展示结果，每个问题附带引用的行号和一条修正建议，以及已验证的内容和验证方式，以及审阅者无法验证的声明。
- 仅在用户要求验证和修正运行或批准结果时应用修正。验证者也可能出错：拒绝意见将随你的理由一起报告，以便用户可以否决。
- 如果应用的修正更改了事实声明，则再次验证，范围限定在更改的声明。拼写和措辞修正不需要第二次验证。
- 两次验证未收敛则停止并交由用户处理。不要在循环中抛光。
