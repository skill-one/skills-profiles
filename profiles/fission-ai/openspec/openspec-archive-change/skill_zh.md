归档实验工作流中的一个已完成变更。

**商店选择：** 如果用户指定了一个商店（商店是一个独立注册在当前机器上的 OpenSpec 仓库）或工作流存在于其中，运行 `openspec store list --json` 来发现已注册的商店 ID，然后在读取或写入规范的命令（`new change`、`status`、`instructions`、`list`、`show`、`validate`、`archive`、`doctor`、`context`、`schemas`、`view`）中传递 `--store <id>`。一旦选定，将 `--store <id>` 视为工作流其余部分的粘性选项。以下命令的未限定示例是简写：在运行它之前，附加该标志。例如，运行 `openspec status --change "<name>" --json --store "<id>"`，而不是下面显示的未限定形式。其他命令不接受该标志。命令已打印的提示信息已经包含该标志；在后续操作中保持它。没有商店时，命令作用于最近的本地 `openspec/` 根目录。

**项目检查：** 这些步骤期望一个已经使用 OpenSpec 的项目。在第一个写入任何内容的步骤（`new change`、`archive`、`sync specs` 或创建工件文件）之前，确认项目有一个根：运行 `openspec list --json`（如果选择了商店，则使用 `--store <id>`，因为商店是根）并读取 `root`。根对象表示项目已设置。`"root": null` 表示未设置 - 这里没有 `openspec/` 目录，并且 `openspec new change` 会作为副作用创建一个。该命令退出非零状态，这是答案而不是损坏的 CLI，因此请读取 JSON 而不是重试或绕过它。

一个 `"root": null` 不是关于设置：当 `status` 错误消息以 `Declared in` 或 `Invalid store declaration in` 开头并命名为此项目的 `openspec/config.yaml`（或 `config.yml`）时，项目通过它声明的商店使用 OpenSpec，而此机器无法解析（商店未注册，或 `store:` 行格式不正确）。不要将其视为未初始化并跳过以下分支：在写入之前停止并显示该错误的 `message` 和 `fix`。

否则，没有根时，接下来会发生什么取决于如何进入此工作流：

- **自动选择**：您自己选择了此工作流，而用户没有指定 OpenSpec、指定此技能或运行其斜杠命令。停止使用 OpenSpec 并像没有安装 OpenSpec 时一样正常回答请求。不要让他们设置任何内容，也不要提及 OpenSpec 设置。
- **显式 OpenSpec 请求**：用户指定了 OpenSpec、指定了此技能或运行了其斜杠命令。在写入之前停止并询问如何进行：设置此项目（`openspec init`）、目标他们已有的商店（`--store <id>`）或为此请求不使用 OpenSpec。等待他们的回答。

在这两种分支中，永远不要作为副作用创建根：直到用户要求它之前，不要运行 `openspec init`，不要手动创建 `openspec/` 文件，也不要让命令创建它。

`<capability-path>` 是相对于 `specs/` 的规范目录（例如，`user-auth` 或 `identity/user-auth`）。在解析其主规范时保留从每个增量规范中获取的完整路径。

**输入**：可选地指定变更名称。如果省略，则检查是否可以从对话上下文中推断。如果模糊或歧义，您必须提示可用的变更。

**步骤**

1. **选择变更**

   如果提供了名称，则使用它。否则：
   - 如果用户在对话中提到了变更，则从对话上下文中推断
   - 如果只有一个活动变更，则自动选择
   - 如果不明确，运行 `openspec list --json` 获取可用变更并要求用户选择一个

   提示时，仅显示活动变更（未已归档的）。
   如果可用，则包含每个变更使用的架构。

   总是宣布：“使用变更：<name>” 以及如何覆盖（例如，`/openspec-archive-change <other>`）。

   **在现有归档检查之前加载当前归档输入：**

   在解析选定变更并规划根之后，运行：
   ```bash
   openspec instructions archive --change "<name>" --json
   ```
   在此命令上保持相同的选定根标志。此查找是建议性的且可选的：它仅提供额外的提示输入，因此绝不能阻止归档。
   如果它退出非零或返回无效 JSON——例如在还不支持此命令的旧 CLI 上——则继续归档工作流，没有任何上下文和操作指导。不要报告错误并停止。

   成功的响应可能会省略两个可选字段。将 `context` 视为必需的提示级输入：读取并考虑它，并应用相关的项目事实、约定和约束。将 `operationGuidance` 视为可选的附加建议：读取并考虑每个条目，并遵循适用且与内置归档工作流兼容的条目。

   将这两个字段与内置步骤、显式用户选择、解析路径、CLI 检查和命令契约分开。如果上下文与其中一个控制输入冲突，请报告冲突并保留控制值。如果指导不适用或与控制输入冲突，请不要遵循它并解释原因。不要从其中推断替换路径、跳过提示或标志，并且除非用户单独要求，否则不要将它们的文本逐字复制到规范、变更工件或归档摘要中。这些是提示级行为契约，不是强制检查。

2. **检查工件完成状态**

   运行 `openspec status --change "<name>" --json` 来检查工件完成状态。

   解析 JSON 以了解：
   - `schemaName`：正在使用的工作流
   - `planningHome`、`changeRoot`、`artifactPaths` 和 `actionContext`：路径和范围上下文
   - `artifacts`：具有其状态（`done`、`skipped` 或其他）的工件列表

   **如果任何工件既不是 `done` 也不是 `skipped**`（已跳过的工件满足要求——变更声明跳过规范）：
   - 列出未完成工件的警告
   - 询问用户是否希望继续
   - 如果用户确认，则继续

3. **检查任务完成状态**

   使用与选定根标志相同的 `openspec list --json` 找到 `changes` 中名称与选定变更完全匹配的条目。
   要求恰好一个匹配且非负整数的 `totalTasks` 和 `completedTasks`，且 `completedTasks <= totalTasks`。CLI 解析架构的跟踪任务文件，包括自定义工件名称、输出路径和通配符。
   不完整的任务 = `totalTasks - completedTasks`。

   不要从工件状态或缺少顶层 `tasks.md` 推断任务完成。如果查找失败、返回无效 JSON、省略或重复选定的变更，或返回无效计数，请报告问题并在同步或归档之前停止。
   CLI 仅计算 `x`/`X` 复选标记为完成；其他标记（包括不熟悉的标记）保持未完成。

   **如果发现未完成的任务：**
   - 显示未完成任务计数的警告
   - 询问用户是否希望继续
   - 如果用户确认，则继续

   **如果 `totalTasks` 为零：** 不显示与任务相关的警告即可继续。

4. **评估增量规范同步状态**

   使用状态 JSON 中的 `artifactPaths.specs.existingOutputPaths` 作为唯一的增量规范源。如果 `specs` 条目缺失或 `existingOutputPaths` 为空，则不提示同步并不要从其他工件推断增量规范。

   **如果存在增量规范：**
   - 将每个增量规范与其对应的主规范（`<planningHome.root>/openspec/specs/<capability-path>/spec.md`）进行比较（使用步骤 2 中的商店感知 `planningHome.root`，而不是硬编码的仓库路径）
   - 缺失主规范**不是自动**“已同步”。对于新功能，主规范是同步的*输出*，而不是输入：
     - 如果增量有 MODIFIED 或 RENAMED 要求，报告只有 ADDED 要求可以创建新主规范并将该功能标记为同步阻塞。永远不要编造没有当前版本的 requirement。
     - 否则，如果增量只有 REMOVED 要求且变更的 `.openspec.yaml` 声明 `retire_capabilities: true`，该功能已退役：将其计为已同步，警告没有剩余内容可移除，并且不要重新创建主规范。现在和验证完成同步时都应用此规则。
     - 否则，如果增量没有 ADDED 要求，报告无法同步并将该功能标记为同步阻塞。对于 REMOVED-仅增量，警告没有主规范可从其移除并保持主规范树不变。`openspec archive` 拒绝未标记的 REMOVED-仅情况，带有 `Spec must have at least one requirement`。
     - 否则，如果增量没有 ADDED 要求，报告无法同步并将该功能标记为同步阻塞。对于 REMOVED-仅增量，警告没有主规范可移除并保持主规范树不变。`openspec archive` 拒绝未标记的 REMOVED-仅情况，带有 `Spec must have at least one requirement`。
     - 否则，将功能计为需要同步并在摘要中命名（`<capability-path>: 将创建新的主规范`）。如果增量也有 REMOVED 要求，警告因为没有主规范可移除而将被忽略。同步仅从增量的 ADDED 要求创建主规范，与 `openspec archive` 做法完全相同。
   - 确定将应用哪些更改（添加、修改、移除、重命名）
   - 即使一个功能同步阻塞，也要继续评估其余功能。在提示之前显示综合摘要。

   **提示选项：**
   - 如果任何功能同步阻塞：解释原因并提供“不同步归档”、“取消”
   - 否则，如果需要更改：”立即同步（推荐）”、“不同步归档”
   - 否则，如果已同步：”立即归档”、“无论如何同步”、“取消”

   根据回答进行路由：
   - “取消”——停止，不归档
   - “不同步归档”或“立即归档”——继续归档
   - “立即同步”或“无论如何同步”——同步，然后验证（下方）。在功能同步阻塞时不要开始任何同步；解释阻塞原因并重复可用选项。
   - 任何其他内容——再次询问而不是归档

   在选定的同步写入任何主规范之前，使用与选定根标志相同的 `openspec instructions specs --change "<name>" --json` 运行一次。要求零退出状态和有效的工件指令 JSON。如果查找失败或返回无效 JSON，请报告错误并在写入任何主规范或移动变更之前停止。有效响应中省略 `rules` 是无规则的情况。仅将返回的 `rules` 应用于此合并产生的主规范的内容和形式；不要将其用作归档指导、更改 CLI 行为或将其规则文本复制到任何输出文件。

   然后，运行 `openspec-sync-specs` 工作流内联（代理驱动智能合并）用于变更 '<name>'，传递增量规范分析和上面获取的规范规则快照，并等待它完成。内联同步必须重用该快照而不再次获取 `specs` 指令。不要将其委托给后台任务——步骤 5 会将 `changeRoot` 从仍在读取它的同步中移除，导致变更已归档而主规范从未更新。如果您的代理只能通过委托运行它，请同步委托并等待结果。

   然后，重新运行此步骤顶部的比较，包括明确退役的、缺失规范的案例，针对 `artifactPaths.specs.existingOutputPaths` 中的每个具有增量规范的 capability——而不仅仅是同步报告它触及的那些。成功的同步不会留下任何剩余内容要应用，因此每个 capability 现在必须读取为已同步：
   - ADDED 要求存在
   - MODIFIED 要求携带增量中命名的场景和描述更改，其其他场景保持完整
   - REMOVED 要求消失——并且如果此同步退役了 capability（移除了其最后一个要求，留下 `## Requirements` 为空），则其主规范被删除而不是留空；同步故意保留并报告的规范也是匹配的
   - RENAMED 要求在新名称下存在并在旧名称下不存在

   如果同步失败，或者任何 capability 不匹配，请报告差异并停止——不要归档。没有任何内容移动，`changeRoot` 保持完整，因此用户可以修复不匹配或重新运行同步并再次开始归档。

5. **执行归档**

   如果 `planningHome.changesDir` 下不存在 `archive` 目录，则创建它：
   ```bash
   mkdir -p "<planningHome.changesDir>/archive"
   ```

   生成目标名称：如果变更名称已经以 `YYYY-MM-DD-` 前缀开头，则使用变更名称本身；否则，将当前日期作为 `YYYY-MM-DD-<change-name>` 前缀。永远不要堆叠第二个日期（与 `openspec archive` 的规则相同）。

   **检查目标是否已存在：**
   - 如果是：使用错误失败，建议重命名现有归档或使用不同日期
   - 如果不是：将 `changeRoot` 移动到归档目录

   ```bash
   mv "<changeRoot>" "<planningHome.changesDir>/archive/<target-name>"
   ```

6. **显示摘要**

   显示归档完成摘要，包括：
   - 变更名称
   - 使用过的架构
   - 归档位置
   - 是否同步了规范（如果适用）
   - 任何警告的说明（未完成的工件/任务）

**成功输出**

```markdown
## 归档完成

**变更：** <change-name>
**架构：** <schema-name>
**归档到：** 从 `planningHome.changesDir`/<target-name>/ 导出的归档路径
**规范：** <"✓ 同步到主规范" 仅当步骤 4 验证通过时；否则 "无增量规范" 或 "跳过同步">

<"所有工件完成。所有任务完成。" — 或，如果带警告归档，则列出它们（例如 "归档时带有 2 个未完成的任务"）>
```

**约束条件**
- 宣布选定的变更；当不明确时提示选择
- 使用工件图（openspec status --json）进行完成检查
- 不要因警告而阻塞归档——只需告知并确认
- 移动到归档时保留 .openspec.yaml（它随目录移动）
- 显示发生的事情的清晰摘要
- 如果请求同步，请内联运行 `openspec-sync-specs` 工作流（代理驱动）
- 归档时不要同步仍在进行中的规范同步——内联运行同步并在移动 `changeRoot` 之前验证主规范
- 如果存在增量规范，始终运行同步评估并在提示之前显示综合摘要
- 应用相关运行时上下文并报告冲突；操作指导仍然是建议性的
- 考虑每个指导条目并解释任何不适用或冲突的建议
- 现有的 CLI 检查、解析路径、提示和命令契约保持不变
- 工件规则仅约束正在写入的规范，并且永远不会是操作指导
- 永远不要将运行时上下文、操作指导或工件规则文本逐字复制到输出文件
