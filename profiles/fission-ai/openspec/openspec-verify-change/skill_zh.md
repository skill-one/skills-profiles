验证实现是否与变更工件（规范、任务、设计）匹配。

**存储选择**：如果用户指定了商店（商店是注册在此机器上的独立 OpenSpec 仓库）或工作存在于其中，运行 `openspec store list --json` 以发现注册的商店 ID，然后在读取或写入规范的命令（`new change`、`status`、`instructions`、`list`、`show`、`validate`、`archive`、`doctor`、`context`、`schemas`、`view`）中传递 `--store <id>`。选择后，将 `--store <id>` 视为工作流程其余部分的粘性选项。以下命令的每个无作用域示例都是简称：在运行它之前，附加该标志。例如，运行 `openspec status --change "<name>" --json --store "<id>"`，而不是下面显示的无作用域形式。其他命令不接受该标志。命令打印的提示信息已经包含该标志；在后续操作中保持它。没有商店时，命令作用于最近的本地 `openspec/` 根目录。

**项目检查**：这些步骤期望一个已经使用 OpenSpec 的项目。在第一个写入任何内容的步骤（`new change`、`archive`、`sync specs` 或创建工件文件）之前，确认项目具有根目录：运行 `openspec list --json`（选择商店时使用 `--store <id>`，因为商店是根目录）并读取 `root`。根对象表示项目已设置。`"root": null` 表示未设置 - 这里没有 `openspec/` 目录，并且 `openspec new change` 会作为副作用创建一个。该命令退出非零，这是答案而不是损坏的 CLI，因此读取 JSON 而不是重试或绕过它。

一个 `"root": null` 不是关于设置：当 `status` 错误消息以 `Declared in` 或 `Invalid store declaration in` 开头并命名此项目的 `openspec/config.yaml`（或 `config.yml`）时，该项目通过它声明的商店使用 OpenSpec，而此机器无法解析（商店未注册，或 `store:` 行格式不正确）。不要将其视为未初始化并跳过以下分支：在写入之前停止并显示该错误的 `message` 和 `fix`。

否则，没有根目录时，接下来会发生什么取决于如何进入此工作流程：

- **自动选择**：您自己选择了此工作流程，而用户没有指定 OpenSpec、指定此技能或运行其斜杠命令。停止使用 OpenSpec 并像没有安装 OpenSpec 时一样正常回答请求。不要让他们设置任何内容，也不要提及 OpenSpec 设置。
- **显式 OpenSpec 请求**：用户指定了 OpenSpec、指定了此技能或运行了其斜杠命令。在写入之前停止并询问如何进行：设置此项目（`openspec init`）、目标他们已有的商店（`--store <id>`）或为此请求不使用 OpenSpec。等待他们的回答。

在这两个分支中，永远不要作为副作用创建根目录：直到用户要求它之前，不要运行 `openspec init`，不要手动创建 `openspec/` 文件，也不要让命令创建它。

**输入**：可选地指定变更名称。如果省略，则检查是否可以从对话上下文中推断。如果模糊或歧义，您必须提示可用的变更。

**步骤**

1. **选择变更**

   如果提供了名称，则使用它。否则：
   - 如果用户在对话中提到了变更，则从对话上下文中推断
   - 如果只有一个活动变更，则自动选择
   - 如果不明确，运行 `openspec list --json` 获取可用变更并要求用户选择一个

   提示时，显示列表返回的所有活动变更，包括状态为 `"no-tasks"` 的变更。
   如果可用，则包含每个变更使用的架构。
   将具有不完整任务的变更标记为 "(进行中)"。

   总是宣布："使用变更：<name>" 以及如何覆盖（例如，`/openspec-verify-change <other>`）。

2. **检查状态以了解架构**
   ```bash
   openspec status --change "<name>" --json
   ```
   解析 JSON 以了解：
   - `schemaName`：正在使用的工作流（例如，"spec-driven"）
   - `planningHome`、`changeRoot`、`artifactPaths` 和 `actionContext`：路径和作用域上下文
   - 此变更的哪些工件存在

3. **获取规划上下文并加载工件**

   ```bash
   openspec instructions apply --change "<name>" --json
   ```

   这返回变更目录、`contextFiles`（工件 ID -> 具体文件路径数组）、`taskTrackingConfigured` 以及从每个由架构的 `apply.tracks` 配置匹配并可以读取的具体文件聚合的顶级 `tasks` 和 `progress`。从 `contextFiles` 读取所有可用工件。

   将 apply `state` 和 `instruction` 视为上下文，而不是验证结果。验证期间不要实现任务或存档变更。

4. **初始化验证报告结构**

   创建一个具有三个维度的报告结构：
   - **完整性**：跟踪任务和规范覆盖范围
   - **正确性**：跟踪需求实现和场景覆盖范围
   - **一致性**：跟踪设计遵循和模式一致性

   每个维度可以有 CRITICAL、WARNING 或 SUGGESTION 问题。

   验证是建议性的。尊重有意省略的情况，例如 `skip_specs: true`、可选的设计文档和没有任务跟踪的架构。不要要求或发明可选或有意省略的工件以获得干净的报告。`Not verified` 描述的是此报告的限制，而不是新的存档先决条件。存档保留其自己的检查和用户确认行为。

   将 schema 未定义的检查或状态报告为有意跳过的工件标记为 **不适用**。变更的可读 delta 规范包含 REMOVED 或 RENAMED 需求但没有 ADDED 或 MODIFIED 需求的正确性检查也是 **不适用**（见步骤 6）。将它们从跳过检查计数和存档就绪评估中排除。为适用检查中证据缺失或不可用的情况保留 **未验证**。

   如果仅适用于检查的任务证据可用，则仅验证任务完成情况，并将其余适用检查（包括 **代码模式一致性**）标记为未验证，原因为此。

   如果工件无法读取或包含无可用需求、场景或设计决策，则将受影响的检查标记为未验证，并给出具体原因。继续由剩余证据支持的检查，但部分检查的输入集不是完全验证的检查。缺失需求影响规范覆盖范围和需求实现映射；缺失场景影响场景覆盖范围；缺失设计决策影响设计遵循。

5. **验证完整性**

   **任务完成情况**：
   - 如果 `taskTrackingConfigured` 为 false，将 **任务完成情况** 报告为不适用。不要将空的 `tasks` 视为缺失证据。
   - 否则，使用顶级的 `tasks` 和 `progress` 字段。它们已经聚合了由 `apply.tracks` 匹配的每个可读的具体文件，无论跟踪工件的 ID 如何；不要从 `contextFiles` 键推断跟踪。
   - 如果 `unavailableTrackingFiles` 非空，将 **任务完成情况** 标记为未验证，并包含每个不可用路径和原因。继续使用任何可读的任务证据，但不要从部分 `tasks` 和 `progress` 字段推断完成情况。
   - 如果 `taskTrackingConfigured` 为 true 且 `tasks` 为空，将 **任务完成情况** 标记为未验证，并记录来自 apply `state` 和 `instruction` 的原因。非零总计本身不能建立可评估的任务描述。
   - 报告完成与总任务数 `progress`。
   - 如果 `progress.remaining` 大于 0：
     - 为每个列出的未完成任务添加 CRITICAL 问题。如果剩余计数超过列出的未完成任务，还报告未描述的未完成复选框，并建议添加描述并完成它们。不要从列出的任务中单独推断完成情况。
     - 建议："完成任务：<description>" 或 "如果已实现，标记为完成"

   **规范覆盖范围**：
   - 如果状态将规范工件跳过 `skip_specs: true`，或者 schema 未定义规范工件，将规范的依赖检查报告为不适用。
   - 否则，`contextFiles` 由工件 ID 键控，工件 ID 来自活动架构。如果 `contextFiles.specs` 缺失或为空，将 **规范覆盖范围**、**需求实现映射** 和 **场景覆盖范围** 标记为未验证；不要将它们视为干净。
   - 如果 `contextFiles.specs` 中存在 delta 规范：
     - 提取所有需求（标记为 "### Requirement：" 或列为 `FROM:`/`TO:` 对的 `## RENAMED Requirements`）并注意每个需求位于 delta 部分的每个部分：`## ADDED`、`## MODIFIED`、`## REMOVED` 或 `## RENAMED Requirements`。该部分决定检查的内容。
     - 对于每个 ADDED 或 MODIFIED 需求（对于 MODIFIED，检查 delta 中的文本，而不是旧的措辞）：
       - 在代码库中搜索与需求相关的关键字
       - 评估是否可能存在实现
     - 如果 ADDED 或 MODIFIED 需求未实现：
       - 添加 CRITICAL 问题：`"需求未找到：<需求名称>"`
       - 建议："实现需求 X：<描述>"
     - 对于每个 REMOVED 需求，变更要求行为消失，因此反转检查：
       - 在代码库中搜索已移除的行为。在 `openspec/` 工件或文档中的匹配项，或仅服务于迁移说明或 ADDED 需求的代码，本身不能作为证据。报告任何仍然交付已移除行为的代码路径，包括与 ADDED 需求共享的路径。
       - 未找到实现是预期结果。永远不要将 REMOVED 需求报告为 "需求未找到" 或建议实现它。
       - 如果行为仍然存在：
         - 添加 CRITICAL 问题：`"已移除的需求仍然实现：<需求名称>"`
         - 建议："在 <文件>:<行号> 移除剩余实现，如果需求有迁移说明，请遵循它"
     - 对于每个 RENAMED 条目（`FROM:`/`TO:`），名称更改但行为保持不变，因此检查 `TO` 需求的该不变行为：
       - 不要报告 FROM 名称缺失，也不要要求代码符号、标识符或文件名重命名。
       - 如果 `TO` 名称也出现在 MODIFIED 下，则将其行为在那里与 MODIFIED 文本检查；在此跳过。
       - 否则，在 `<planningHome.root>/openspec/specs/<capability-path>/spec.md` 读取基线需求，使用与 delta 规范相同的 capability path：在 FROM 名称下，或在 FROM 名称因主规范已同步而缺失时仅在 TO 名称下。其正文和场景是 TO 需求保留的行为的证据。
       - 在代码库中搜索该行为并评估是否仍然实现。
       - 如果它似乎未实现：
         - 添加 CRITICAL 问题：`"重命名需求未找到：<TO 名称>"`
         - 建议："恢复 <TO 名称> 的行为（从 <FROM 名称> 重命名）；重命名不得改变行为"
       - 如果基线需求无法找到或读取，将 **规范覆盖范围** 对于该条目标记为未验证，并给出原因。永远不要将未检查的重命名计为通过。

6. **验证正确性**

   如果 delta 规范可读且至少包含一个 REMOVED 或 RENAMED 需求但没有 ADDED 或 MODIFIED 需求（变更仅删除或重命名需求），报告 **需求实现映射** 和 **场景覆盖范围** 为 **不适用**。Spec Coverage 下的 REMOVED 和 RENAMED 检查是此类变更的证据（每个 RENAMED 条目在那里与其基线行为检查），因此不要将这两个检查标记为未验证。没有任何可解析需求的 delta 规范是无用证据，不是删除-only 变更：将这两个检查标记为未验证。

   **需求实现映射**：
   - 对于 delta 规范中的每个 ADDED 或 MODIFIED 需求（REMOVED 条目，以及没有 MODIFIED 块的 RENAMED 条目在 Spec Coverage 下已解决）：
     - 在代码库中搜索实现证据
     - 如果找到，则记录文件路径和行号范围
     - 评估实现是否与需求意图一致
     - 如果检测到差异：
       - 添加 WARNING：`"实现可能与规范不一致：<详细信息>"`
       - 建议："对比需求 X 检查 <文件>:<行号>"

   **场景覆盖范围**：
   - 对于 delta 规范中 ADDED 或 MODIFIED 需求下的每个场景（标记为 "#### Scenario："）：
     - 检查代码中是否处理了条件
     - 检查是否存在覆盖场景的测试
     - 如果场景似乎未覆盖：
       - 添加 WARNING：`"场景未覆盖：<场景名称>"`
       - 建议："为场景添加测试或实现：<描述>"
   - 跳过 REMOVED 需求下的场景；该行为意味着要消失。

7. **验证一致性**

   **设计遵循**：
   - 如果 schema 未定义设计工件，将 **设计遵循** 报告为不适用。
   - 如果 `contextFiles.design` 存在：
     - 提取关键决策（查找类似 "Decision："、"Approach："、"Architecture：" 的部分）
     - 验证实现是否遵循这些决策
     - 如果检测到矛盾：
       - 添加 WARNING：`"未遵循设计决策：<决策>"`
       - 建议："更新实现或修订 design.md 以匹配现实"
   - 否则，如果 `contextFiles.design` 缺失或为空：将 **设计遵循** 标记为未验证。在其他支持工件的情况下，**代码模式一致性** 仍然运行；任务-only 情况仍然有限。

   **代码模式一致性**：
   - 如果无法识别实现更改，将 **代码模式一致性** 标记为未验证并解释缺失证据。
   - 否则，检查新代码是否与项目模式一致
   - 检查文件命名、目录结构、编码风格
   - 如果发现显著偏差：
     - 添加 SUGGESTION：`"代码模式偏差：<详细信息>"`
     - 建议："考虑遵循项目模式：<示例>"

8. **生成验证报告**

   **摘要评分卡**：
   ```markdown
   ## 验证报告：<变更名称>

   ### 摘要
   | 维度    | 状态           |
   |--------------|------------------|
   | 完整性    | X/Y 任务，N 需求|
   | 正确性    | M/N 需求覆盖   |
   | 一致性    | 遵循/问题      |
   ```

   在每个状态单元格中，报告运行检查的结果，并为每个跳过的检查报告 `Not verified (<reason>)`。如果某个维度中的所有检查都跳过，则从单元格开始 `Not verified`。永远不要将跳过的检查评分视为通过。将每个未验证或部分验证的检查在最终评估中视为跳过。仅计算 ADDED 和 MODIFIED 需求的 N，并单独报告 REMOVED 和 RENAMED 需求（例如，"1 个移除确认，1 个重命名验证"）。对于仅删除或重命名需求的变更，正确性单元格读取 `Not applicable (没有 ADDED 或 MODIFIED 需求)`。

   **按优先级划分的问题**：

   1. **CRITICAL**（存档前必须修复）：
      - 未完成的任务
      - 缺失需求实现
      - 仍然实现的移除需求
      - 行为不再实现的重命名需求
      - 每个都有具体的、可操作的推荐

   2. **WARNING**（应该修复）：
      - 规范/设计差异
      - 缺失场景覆盖
      - 每个都有具体的推荐

   3. **SUGGESTION**（最好修复）：
      - 模式不一致
      - 小改进
      - 每个都有具体的推荐

   **最终评估**：
   - 如果 CRITICAL 问题：`"发现 X 个 critical 问题。修复后再存档。"` 如果任何检查被跳过，还命名每个跳过的检查及其原因。
   - 如果没有 CRITICAL 问题，一个或多个警告，并且没有跳过检查：`"没有 critical 问题。Y 个警告需要考虑。准备存档（注意改进）。"`
   - 如果只有建议并且没有跳过检查：`"没有 critical 问题或警告。Z 个建议需要考虑。准备存档（注意改进）。"`
   - 如果没有问题和没有跳过检查：`"所有检查通过。准备存档。"`
   - 如果任何检查被跳过并且没有 CRITICAL 问题：不要声称就绪。说 `"在运行的检查中未发现 critical 问题。<检查(s)> 未验证：<原因>"`。当非零时，包含警告计数。
   - 在每个最终评估中，当非零时，包含建议计数。

**验证启发式方法**

- **完整性**：专注于客观清单项（复选框、需求列表）
- **正确性**：使用关键字搜索、文件路径分析、合理推断 - 不要要求绝对确定性
- **一致性**：寻找明显的矛盾，不要抠细节
- **误报**：当不确定时，优先选择 SUGGESTION 而不是 WARNING，WARNING 而不是 CRITICAL
- **可操作性**：每个问题都必须有一个具体的推荐，其中适用的话包含文件/行引用

**输出格式**

使用清晰的 markdown，包括：
- 摘要评分卡表格
- 按优先级分组的问题列表（CRITICAL/WARNING/SUGGESTION）
- 格式为 `file.ts:123` 的代码引用
- 具体的、可操作的推荐
- 不要包含模糊的建议，如 "考虑审查"
