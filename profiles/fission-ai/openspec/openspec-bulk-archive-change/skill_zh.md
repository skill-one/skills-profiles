批量归档多个已完成变更的单次操作。

这项技能允许您批量归档变更，通过检查代码库智能处理规范冲突，以确定实际已实现的内容。

**存储库选择**：如果用户命名了存储库（存储库是此机器上注册的独立OpenSpec仓库）或工作存在于其中，运行 `openspec store list --json` 以发现注册的存储库ID，然后在读取或写入规范的命令（`new change`、`status`、`instructions`、`list`、`show`、`validate`、`archive`、`doctor`、`context`、`schemas`、`view`）中传递 `--store <id>`。选择后，将 `--store <id>` 视为工作流程其余部分的粘性选项。以下命令的每个无作用域示例都是简称：在运行它之前，附加该标志。例如，运行 `openspec status --change "<name>" --json --store "<id>"`，而不是下面显示的无作用域形式。其他命令不接受该标志。命令打印的提示信息已经包含该标志；在后续操作中保持它。如果没有存储库，命令将作用于最近的本地 `openspec/` 根目录。

**项目检查**：这些步骤期望一个已经使用OpenSpec的项目。在第一个写入任何内容的步骤（`new change`、`archive`、`sync specs` 或创建工件文件）之前，确认项目具有根目录：运行 `openspec list --json`（选择存储库时使用 `--store <id>`，因为存储库是根目录）并读取 `root`。根对象表示项目已设置。`"root": null` 表示未设置——这里没有 `openspec/` 目录，并且 `openspec new change` 会作为副作用创建一个。该命令退出非零，这是答案而不是损坏的CLI，因此请读取JSON而不是重试或绕过它。

一个 `"root": null` 不是关于设置：当 `status` 错误消息以 `Declared in` 或 `Invalid store declaration in` 开头并命名此项目的 `openspec/config.yaml`（或 `config.yml`）时，该项目通过它声明的存储库使用OpenSpec，而此机器无法解析（存储库未注册，或 `store:` 行格式不正确）。不要将其视为未初始化并跳过以下分支：在写入之前停止并显示该错误的 `message` 和 `fix`。

否则，没有根目录时，接下来会发生什么取决于如何到达此工作流程：

- **自动选择**：您自己选择了此工作流程，而用户没有命名OpenSpec、命名此技能或运行其斜杠命令。停止使用OpenSpec并像没有安装OpenSpec一样正常回答请求。不要要求他们设置任何内容，也不要提及OpenSpec设置。
- **明确的OpenSpec请求**：用户命名了OpenSpec、命名了此技能或运行了其斜杠命令。在写入之前停止并询问如何进行：设置此项目（`openspec init`）、目标他们已有的存储库（`--store <id>`）或为此请求不使用OpenSpec。等待他们的回答。

在这两个分支中，永远不要作为副作用创建根目录：直到用户要求它之前，不要运行 `openspec init`，不要手动创建 `openspec/` 文件，也不要让命令创建它。

`<capability-path>` 是相对于 `specs/` 的规范目录（例如，`user-auth` 或 `identity/user-auth`）。在解析其主规范时保留从每个增量规范获取的完整路径。

**输入**：无需（提示选择）

**步骤**

1. **获取活动变更**

   运行 `openspec list --json` 获取所有活动变更。

   如果没有活动变更，通知用户并停止。

2. **提示选择变更**

   要求用户选择变更（多选）：
   - 显示每个变更名称和任务状态列表输出
   - 包括“所有变更”选项
   - 允许选择任意数量的变更（1+ 有效，2+ 是典型用例）

   **重要**：不要自动选择。始终让用户选择。

   **在批量验证之前，为选定的根目录加载当前归档输入一次**：

   从此根目录选择一个选定的变更，并运行
   `openspec instructions archive --change "<selected-change>" --json` 并使用相同的选定的根目录标志。此查找是建议性的且可选的：它仅提供额外的提示输入，因此绝不能阻塞批量。如果它失败或返回无效的JSON——例如在还不支持此命令的旧CLI上——继续批量，无上下文和操作指导。不要报告错误并不要停止。

   有效响应可能省略 `context` 和 `operationGuidance`。将 `context` 视为跨批量的必需提示级输入：读取并考虑它，并应用相关的项目事实、约定和约束。将 `operationGuidance` 视为可选的附加建议：读取并考虑每个条目，并遵循适用且与内置批量工作流程兼容的条目。

   将这两个字段与冲突分析、显式用户选择、解析路径、CLI检查和命令合同分开。如果上下文与其中一个控制输入冲突，请报告冲突并保留控制值。如果指导不适用或与控制输入冲突，不要遵循它并解释原因。不要从这两个字段推断跳过的提示、替换路径或标志，也不要将它们的文本逐字复制到输出文件中。这些是提示级行为合同，不是强制检查。

3. **批量验证 - 为所有选定的变更收集状态**

   使用与步骤3相同的选定的根目录标志一次运行 `openspec list --json` 以获取任务进度。如果查找失败、返回无效的JSON或省略任何选定的变更、包含重复的选定变更或返回无效计数，请报告问题并在同步或归档批量之前停止。

   对于每个选定的变更，收集：

   a. **工件状态** - 运行 `openspec status --change "<name>" --json`
      - 解析 `schemaName`、`artifacts`、`planningHome`、`changeRoot`、`artifactPaths` 和 `actionContext`
      - 注意哪些工件是 `done` 而其他状态

   b. **任务完成** - 查找列表响应中的 `changes` 条目，其 `name` 与此变更完全匹配
      - 要求非负整数 `totalTasks` 和 `completedTasks`，且 `completedTasks <= totalTasks`
      - 不完整的任务 = `totalTasks - completedTasks`
      - CLI 解析规范的跟踪任务文件，包括自定义工件名称、输出路径和通配符
      - 不要从工件状态、工件ID为 `tasks` 或缺少顶层 `tasks.md` 推断任务完成
      - CLI 仅计算 `x`/`X` 复选标记为完成；其他标记保持不完整
      - 如果 `totalTasks` 为零，记为“无任务”

   c. **增量规范** - 检查状态JSON中的 `artifactPaths.specs.existingOutputPaths`
      - 列出哪些能力规范存在
      - 对于每个，提取要求名称（匹配 `### Requirement: <name>` 的行）
      - 将此列表视为唯一的增量规范源。如果 `specs` 条目缺失或列表为空，则对此变更不执行规范同步或规范指令查找；不要从无关工件推断增量。
      - 独立地为每个变更评估此内容，包括混合模式的批量，其中某些模式没有 `specs` 工件。

   d. **归档目标** - 一次计算每个变更的目标名称并记录为该变更的 `<target-name>`
      - 当变更名称以 `YYYY-MM-DD-` 前缀开头时，使用变更名称本身；否则，将当前日期作为 `YYYY-MM-DD-<name>` 前缀（与 `openspec archive` 的规则相同）
      - 检查 `<planningHome.changesDir>/archive/<target-name>` 是否已存在
      - 如果它存在，或另一个选定的变更解析到相同的目标名称，请将每个此类变更标记为 `Blocked` 并显示 `归档目录已存在`
      - 被阻止的变更永远不会同步或移动：在步骤6的表中显示为 `Blocked`，将其排除在冲突解决之外（仅使用其他变更解决其冲突），并在步骤8d中记录为失败
      - 在写入任何主规范之前检查这里，与 `openspec archive` 匹配：在同步后发现的冲突会留下未发生的归档的主规范

4. **检测规范冲突**

   构建一个以 `<capability-path>` 为键的映射：

   ```text
   identity/user-auth -> [change-a, change-b]  <- 冲突（2+ 变更）
   billing/user-auth  -> [change-c]            <- 正常（不同的完整路径）
   ```

   当2个或更多选定的变更具有相同 `<capability-path>` 的增量规范时，存在冲突。

5. **代理解决冲突**

   **对于每个冲突**，调查代码库：

   a. **从每个冲突的变更中读取增量规范** 以了解每个声称添加/修改的内容

   b. **搜索代码库** 以查找实现证据：
      - 查找实现每个增量规范要求的代码
      - 检查相关文件、函数或测试

   c. **确定解决方案**：
      - 如果只有一个变更实际实现 -> 同步该变更的规范
      - 如果两个都实现 -> 按时间顺序应用（旧的优先，新的覆盖）
      - 如果都没有实现 -> 跳过规范同步，警告用户

   d. **记录解决方案** 对于每个冲突：
      - 每个增量规范的包含或排除决策，按变更和 `<capability-path>` 键
      - 要应用和按什么顺序应用的包含的增量规范
      - 因为它们的实现缺失而从同步中排除的增量规范
      - 理由（代码库中找到的内容）

6. **显示合并状态表**

   显示总结所有变更的表：

   ```markdown
   | 变更              | 工件 | 任务 | 规范   | 冲突 | 状态 |
   |---------------------|-------|-------|---------|-----------|--------|
   | schema-management   | 完成  | 5/5   | 2 delta | 无      | 准备  |
   | project-config      | 完成  | 3/3   | 1 delta | 无      | 准备  |
   | add-oauth           | 完成  | 4/4   | 1 delta | identity/user-auth (!) | 准备* |
   | add-verify-skill    | 1 剩余 | 2/5   | 无    | 无      | 警告   |
   ```

   对于冲突，显示解决方案：
   ```text
   * 冲突解决方案:
     - identity/user-auth 规范：将先应用 add-oauth，然后应用 add-jwt（两者都实现，按时间顺序）
   ```

   对于不完整的变更，显示警告：
   ```text
   警告:
   - add-verify-skill: 1 个不完整的工件，3 个不完整的任务
   ```

7. **确认批量操作**

   向用户提出一个确认问题：

   - "归档 N 个变更？" 选项基于状态
   - 选项可能包括：
     - "归档所有 N 个变更"
     - "仅归档 N 个准备好的变更（跳过不完整）"
     - "取消"

   如果有不完整的变更，请明确它们将带有警告归档。

   根据意图而不是确切标签进行路由——您编写了这些标签，因此请匹配用户的选择而不是上面的措辞：
   - "取消" — 停止，不要归档。报告未归档任何内容并跳过其余步骤。
   - 归档所有选项 — 继续处理所有选定的变更，不包括 `Blocked` 的变更
   - 仅准备选项 — 仅处理步骤6表格标记为 `Ready` 或 `Ready*` 的变更，并将其余变更在步骤8d中记录为跳过，除了 `Blocked` 变更，它们保持失败并带有 `归档目录已存在`。如果 `Ready*` 变更的冲突伙伴被跳过，请使用仅要归档的变更重新推导该冲突的解决方案。
   - 其他任何内容 — 询问而不是归档

   在步骤8写入第一个主规范或移动任何变更之前，获取确认批量所需的所有必需的规范规则快照。对于将要同步具体 `artifactPaths.specs.existingOutputPaths` 的每个变更，使用相同的选定的根目录标志一次运行
   `openspec instructions specs --change "<name>" --json`。在第一个写入或移动之前获取所有快照。如果任何查找退出非零或返回无效的工件指令JSON，请识别受影响的变更，报告错误，并在任何主规范写入或变更移动之前停止整个批量。不要将查找失败视为省略的规则。有效的响应没有 `rules` 是无规则的情况。

8. **为每个确认的变更执行归档**

   在处理之前，将步骤5记录的决策（在步骤7的任何重新推导之后）输入到两个每个增量集：
   - `includedDeltas`: 从确认的变更中所有非冲突的增量规范加上为同步选择的冲突增量规范
   - `excludedDeltas`: 从确认的变更中因为其实现缺失而被排除的冲突增量规范
   - 一个变更可以同时具有包含和排除的增量规范。保持每个增量的决策；不要将其合并为每个变更的同步标志。

   按确定的顺序处理变更（尊重冲突解决）：

   a. **同步包含的增量规范**：
      - 仅对 `includedDeltas` 中的变更运行 `openspec-sync-specs` 工作流（代理驱动的智能合并），传递仅包含的增量路径，并明确指示它忽略该变更的 `excludedDeltas`。等待它完成。
      - 对于冲突，按解决顺序应用。
      - 将该变更获取的规范规则快照传递到内联同步；内联同步必须重用它而不再次获取指令
      - 仅将工件规则应用于该变更生成的主规范。它们不会改变冲突解决、归档行为或CLI合同，并且它们的文本不会逐字复制到输出文件中
      - 不要委托给后台任务——步骤8c会将 `changeRoot` 从仍在读取它的同步中移除。
      - 如果一个变更没有包含的增量规范，不要为其运行同步工作流。

   b. **在移动变更根之前验证包含的增量规范**：
      - 仅对 `includedDeltas` 中的增量规范重新运行比较，与 `<planningHome.root>/openspec/specs/<capability-path>/spec.md`（使用步骤3状态JSON中的存储库感知 `planningHome.root`，而不是硬编码的仓库路径）中的主规范进行比较。
      - 验证主规范已更新：
        - 添加的要求存在
        - 修改的要求携带场景和描述更改，其其他场景完整
        - 删除的要求消失——并且当此同步退役了能力（删除了其最后一个要求，留下 `## Requirements` 为空）时，其主规范被删除而不是留下空白；同步故意保留并报告的规范也是一个匹配
        - 重命名的要求在新名称下存在，在旧名称下不存在
      - 不要验证 `excludedDeltas` 中的增量规范；它们有意不被同步。
      - 如果同步失败或任何能力不匹配验证，报告差异并失败/跳过移动该变更的 `changeRoot`——不要归档该变更。`changeRoot` 保持完整。

   c. **执行归档**：

      目标名称：使用步骤3d为该变更记录的 `<target-name>`，不变。在这里永远不要重新计算它：运行到午夜后的批量会在步骤3检查一个日期，然后移动到另一个日期。

      **检查目标是否已存在**：
      - 在移动之前立即检查，即使步骤3已经检查：目标可以在批量中出现在
      - 如果是：将该变更记录为失败并带有 `归档目录已存在`，将 `changeRoot` 保留在原地，报告为它已经同步的任何主规范，并继续处理剩余的变更
      - 如果不是：将 `changeRoot` 移动到归档目录

      ```bash
      mkdir -p "<planningHome.changesDir>/archive"
      mv "<changeRoot>" "<planningHome.changesDir>/archive/<target-name>"
      ```

      **确认移动没有嵌套**：`mv` 即使目标在检查后出现也会退出0，将变更移动到它里面。如果 `<planningHome.changesDir>/archive/<target-name>/<change-directory-name>` 现在存在（`changeRoot` 的最后一个路径段），将该目录移回 `changeRoot` 并将该变更记录为失败并带有 `归档目录已存在`。永远不要报告它为已归档。

   d. **为每个变更跟踪结果**：
      - 成功：归档成功
      - 失败：归档期间或规范验证出错（记录错误）
      - 跳过：用户选择不归档（如果适用）
      - 同步跳过：对于 `excludedDeltas` 中的每个增量，报告 `sync skipped` 与变更、`<capability-path>` 和记录的原因。这与跳过归档不同。

9. **显示总结**

   显示最终结果：

   ```markdown
   ## 批量归档完成

   归档了 3 个变更：
   - schema-management-cli -> archive/2026-01-19-schema-management-cli/
   - project-config -> archive/2026-01-19-project-config/
   - add-oauth -> archive/2026-01-19-add-oauth/

   跳过了 1 个变更：
   - add-verify-skill (用户选择不归档不完整的)

   规范同步总结：
   - 4 个增量规范同步到主规范
   - 1 个增量规范同步跳过（add-jwt, identity/user-auth: 实现未找到）
   - 1 个冲突已解决（identity/user-auth: 同步了 add-oauth，跳过了 add-jwt）
   ```

   如果有任何失败：
   ```text
   失败了 1 个变更：
   - some-change: 归档目录已存在
   ```
