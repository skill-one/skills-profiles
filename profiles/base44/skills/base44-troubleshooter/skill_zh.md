# 解决生产问题

## 前置条件

在获取日志前验证身份：

```bash
npx base44 whoami
```

如果未认证或令牌过期，指导用户运行 `npx base44 login`。

通过以下方式之一解析应用上下文：

```bash
# 从链接的本地项目
cat base44/.app.jsonc

# 或显式指定
npx base44 logs --app-id app_123
```

## 可用命令

| 命令 | 描述 | 参考 |
|------|------|------|
| `base44 logs` | 获取此应用的函数日志 | [project-logs.md](references/project-logs.md) |
| `base44 workflows runs` | 列出工作流运行，按最新排序；失败的运行会包含失败的任务和底层错误 | [workflows-runs.md](../base44-cli/references/workflows-runs.md) |
| `base44 workflows list` | 列出此应用的工作流及其状态和运行摘要 | [workflows-list.md](../base44-cli/references/workflows-list.md) |

## 日志不会读后写

**单次获取失败并不能证明任何问题。** 一次性 `base44 logs` 读取的是滞后于调用的索引，因此触发函数后立即获取空结果才是预期结果，而不是问题的证据。

- **实时调试：使用 `--follow`。** 当实时流可用时，它会在**不到一秒**内传递行。当不可用时，CLI 会告知并轮询（`警告：此应用的实时日志不可用——回退到轮询（行可能滞后 ~20-30 秒）。`）。无论哪种情况，`--follow` 都是正确的工具——你永远不需要选择。
- **一次性获取会滞后 ~20-30 秒。** 这是摄入时间，不是过滤器问题。
- **当输出为空时，需要改变的是时间，而不是标志。** 等待并重新运行相同的命令。扩大 `--limit`、丢弃 `--level` 或切换 `--order` 都不会改变尚未摄入的行的状态，重新滚动标志是代理自我误导到错误诊断的方式。

## 排错流程

### 1. 观察发生——`--follow`

如果你可以触发失败（或它正在发生），从获取历史记录开始，而不是事后获取：

```bash
npx base44 logs --follow
npx base44 logs --follow --function <function_name>
```

然后调用函数并读取到达的内容。避免误读健康流的规则：

- **不要基于计时器做决定。** 打开流，触发函数，直到看到行——不要读取固定窗口，打印并得出“损坏”的结论。安静的流是安静的，因为没有任何调用。
- **交付是按调用，不是按行。** 长时间运行的函数的行会在调用结束时一起到达。调用期间的中途安静是正常的。
- **在中途重新部署是安全的。** 部署会在几秒钟内旋转脚本，相同的打开流会在下一次调用时传递新代码的行。不要在每次部署后拆解流并重建。
- **`--since` 与 `--follow` 一起被拒绝**（流从现在开始），`--until` 和 `--order` 也被拒绝。对于任何历史记录，使用一次性获取。
- **模式在启动时决定一次。** 如果第一个连接被拒绝或无法到达，运行将一直轮询。如果流打开，就没有轮询回退了。
- **运行中途丢失的流会结束命令**，显示 `Error: The realtime log stream stopped and could not be re-established`，退出码 1。这个退出是流放弃，而不是日志损坏的证据——重新运行相同的命令，而不是改变标志。

### 2. 确认是否为计划运行，而非请求

工作流是自动化系统——cron 定时任务、实体触发、连接器事件、应用内代理操作。**当抱怨是“我的计划任务未运行”或“自动化停止工作”时，函数日志是错误的工具。** 它们显示函数打印了什么；它们无法告诉你是否派发了运行，里面哪个任务失败，或为什么工作流停止触发。

```bash
npx base44 workflows runs --status failed
npx base44 workflows list
```

失败的运行会包含失败的任务和底层错误，因此从那里开始，只有在知道失败任务调用了哪个函数后，才进入 `base44 logs`。`workflows list` 报告 `consecutiveFailures`——任何大于零的都是需要关注的工作流。

这里容易误导的两个点：

- **触发列中的 `manual` 并不意味着有人点击了什么。** 它是当运行在没有触发类型的情况下派发时被附加到运行上的标记。
- **测试运行是包含的**，作为触发类型的旁边标记为 `(scheduled, test)`。你自己运行来检查某事的运行会出现在列表中。

### 3. 检查最近错误

首先获取所有函数的最新错误：

```bash
npx base44 logs --level error
```

### 4. 深入特定函数

如果你知道哪个函数失败：

```bash
npx base44 logs --function <function_name> --level error
```

如果你不在项目目录外，请显式传递应用：

```bash
npx base44 logs --app-id app_123 --function <function_name> --level error
```

`--function` 过滤器是对*标记*行的过滤。仍在使用传统按函数部署的应用会发出未标记的行，因此过滤视图可能会隐藏它们；这会在应用的下次部署时自我修复。如果过滤的运行返回为空，请在得出没有日志的结论前，不使用 `--function` 重新运行。

### 5. 检查时间范围

与用户报告的问题时间戳关联：

```bash
npx base44 logs --function <function_name> --since <start_time> --until <end_time>
```

### 6. 分析日志

- 在输出中查找堆栈跟踪和错误消息
- 检查时间戳以与用户报告的问题关联
- 显式传递 `--limit` 以追溯到更远——没有默认页面大小，超过 500 的值会被钳制到 500

## 读取空结果

`未找到匹配过滤器的日志。` 是模糊的——永远不要将其解释为“健康”。它意味着以下之一：

- 运行尚未摄入（最常见——等待并重新运行，见上文）
- 没有该名称的函数，或过滤器丢弃了未标记的行（见步骤 3）
- 应用未发布时读取 `--env prod`
  (`未找到生产日志。` —— 尝试 `--env preview` 获取草稿日志)
