# 系统设计框架

一种结构化的方法来设计大规模分布式系统。在构建新服务、评审设计、估算容量或准备系统设计讨论时，请应用这些原则。

## 核心原则

**从需求开始，而非解决方案。** 在理解约束之前就跳到架构设计会导致系统过度或不足度设计。可扩展的系统是由经过充分理解的构建模块（负载均衡器、缓存、队列、数据库、CDN）组装而成的——关键在于选择正确的模块、用估算值来调整大小，并承担每个选择带来的权衡。

## 评分

**目标：10/10。** 通过设计满足的八个快速诊断行数来评分——`score = round(passed / 8 × 10)`：9-10 = 全部/几乎全部行通过——明确的需求、实际估算值、冗余、声明的数据库扩展和缓存策略、通过队列的异步处理、监控和部署计划，并命名权衡；5-6 = 设计可以工作，但跳过了估算值、冗余或运维；<=3 = 在需求或估算值存在之前就提出了架构。始终声明当前分数，命名失败的诊断行，并为每个提供具体的修复方案。

## 系统设计框架

构建可靠、可扩展分布式系统的六个领域：

### 1. 四步流程

**核心概念：** 每个设计都遵循四个阶段：(1) 理解问题并确定范围，(2) 提出高级设计并获取认可，(3) 深入关键组件，(4) 以权衡和未来改进收尾。

**为什么有效：** 没有结构，设计要么过于抽象，要么过早陷入细节。四步法按比例分配时间——先勾勒轮廓，再在关键处深入。

**关键洞察：**
- 第一步 (~5-10分钟)：澄清问题、功能和非功能性需求、约定的规模（DAU、QPS、存储）
- 第二步 (~15-20分钟)：包含API、服务、数据存储、数据流箭头的高级图表
- 第三步 (~15-20分钟)：详细设计2-3个最困难或最关键的组件
- 第四步 (~5分钟)：权衡、瓶颈、未来改进
- 永远不要跳过第一步——模糊的范围会浪费所有下游工作；明确同意假设

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **新服务启动** | 在编码前用一页设计文档涵盖所有四个步骤 | 需求、API合约、数据模型、容量估算，然后实现 |
| **架构评审** | 按顺序引导评审者 | 范围、图表、对风险最高组件的深入分析、开放问题 |
| **事件复盘** | 通过四步法追踪故障 | 哪个需求被遗漏？哪个模块失败？哪个权衡带来了问题？ |

在端到端运行设计时，请参阅 [references/four-step-process.md](references/four-step-process.md) —— 每个阶段的分配时间、示例澄清问题以及四个步骤的每个步骤的提示。

### 2. 粗略估算

**核心概念：** 使用2的幂、延迟数字和简单算术来估算QPS、存储、带宽和服务器数量，然后再提交架构。

**为什么有效：** 估算可以防止过度配置（浪费金钱）和配置不足（负载下的宕机）。2分钟的计算可以节省数周的返工。

**关键洞察：**
- 2的幂：2^10 ≈ 1千，2^20 ≈ 1百万，2^30 ≈ 1十亿，2^40 ≈ 1万亿
- 延迟：内存读取 ~100纳秒，SSD读取 ~100微秒，磁盘寻道 ~10毫秒，同数据中心往返 ~0.5毫秒，跨大陆 ~150毫秒
- 可用性九：99.9% = 每年8.77小时停机；99.99% = 每年52.6分钟
- QPS：DAU x 每日操作数 / 86,400秒；峰值通常是平均值的2-5倍
- 存储：每日记录数 x 记录大小 x 保留期
- 大胆估算——目标是数量级，而非精度

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **容量规划** | 估算QPS，乘以增长因子 | 100M DAU x 5操作 / 86400 = ~5,800 QPS平均，~30K峰值 |
| **存储预算** | 每条记录大小 x 数量 x 保留期 | 500M推文/天 x 300字节 x 365天 = ~55 TB/年 |
| **SLA定义** | 将九转换为允许的停机时间 | 四个九 = 每年~52分钟停机 |

在调整系统大小时，请参阅 [references/estimation-numbers.md](references/estimation-numbers.md) —— 完整延迟表、可用性九表和已计算的QPS/存储/带宽。

### 3. 构建模块

**核心概念：** 可扩展的系统是由标准工具包组装的：DNS、CDN、负载均衡器、反向代理、应用服务器、缓存、消息队列和一致性哈希。

**为什么有效：** 每个模块都权衡了一种成本以换取另一种成本（缓存权衡新鲜度以换取读取速度；队列权衡延迟以实现解耦），因此只有在特定瓶颈出现时才引入模块——一开始就引入所有模块只会增加故障模式。

**关键洞察：**
- 负载均衡器：L4（传输层——快速、简单）vs L7（应用层——内容感知路由）
- 缓存层：客户端、CDN、Web服务器、应用（Redis/Memcached）、数据库查询缓存
- 缓存策略：缓存旁路（应用管理）、读取通过、写入通过（同步）、写入后（异步）
- 消息队列（Kafka、RabbitMQ、SQS）：将生产者与消费者解耦、吸收峰值、实现异步处理
- 一致性哈希：在节点变化时以最小重分配将键分布在节点上

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **读密集型工作负载** | 数据库前方的缓存旁路Redis | 缓存用户配置文件并设置TTL；写入时使缓存失效 |
| **流量峰值** | API和工作者之间的消息队列 | 将图像调整任务入队；工作者按自己的节奏拉取 |
| **全球用户** | 静态资源的CDN | 从边缘提供JS/CSS/图像；源服务器仅提供API |
| **负载不均** | 一致性哈希用于分片分配 | 添加节点时仅移动 ~1/n 的键 |

在选择组件时，请参阅 [references/building-blocks.md](references/building-blocks.md) —— DNS、CDN、负载均衡器、缓存策略、消息队列和一致性哈希的工作原理以及何时引入它们。

### 4. 数据库设计和扩展

**核心概念：** 根据数据形状和访问模式选择SQL vs NoSQL；首先垂直扩展，然后在达到垂直极限时水平扩展（复制和分片）。

**为什么有效：** 数据库通常是第一个瓶颈。理解复制、分片和反规范化权衡可以延迟昂贵的重构，并使增长变得有目的。

**关键洞察：**
- 垂直扩展更简单但有上限；水平扩展更复杂但几乎无限
- 复制：主从（一个写入者，多个读取者）用于读密集型；多主用于多区域写入
- 分片：基于哈希（均匀分布，范围查询困难）、基于范围（范围查询简单，热点风险）、基于目录（灵活，额外查找）
- SQL用于ACID事务、连接、定义模式；NoSQL用于灵活模式、水平扩展、非常高的写入吞吐量
- 反规范化权衡存储和写入复杂性以换取读取速度——当读取主导且数据变化很少时使用
- 明星/热点问题：一个热点分片需要二级分片或缓存层

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **读密集型API** | 带读取副本的主从 | 读取到副本，写入到主节点；接受轻微延迟 |
| **大规模用户数据** | 基于user_id的哈希分片 | hash(user_id) % num_shards；均匀、独立的分片 |
| **分析仪表板** | 反规范化物化视图 | 预先连接和聚合夜间；从物化表提供 |

在数据库成为瓶颈时，请参阅 [references/database-scaling.md](references/database-scaling.md) —— 复制拓扑、三种分片策略的比较、反规范化权衡以及SQL vs NoSQL选择指南。

### 5. 常见系统设计

**核心概念：** 大多数系统都是少量著名设计的变体：URL缩短器、速率限制器、通知系统、新闻源、聊天、搜索自动完成、网络爬虫、唯一ID生成器。

**为什么有效：** 一套已知设计的心理库让你能够识别新问题与哪个模式相似并对其进行调整，而不是从头开始发明。

**关键洞察：**
- URL缩短器：base62编码、键值存储、301 vs 302重定向权衡（缓存 vs 分析）
- 速率限制器：网关处的令牌桶或滑动窗口；返回429并附带Retry-After
- 新闻源：写入时发散（发布时推送）vs 读取时发散（读取时拉取）；混合用于明星
- 聊天：WebSocket用于实时双向消息，队列用于交付保证，心跳存在服务
- 自动完成：top-k频繁查询的Trie；预先计算并缓存常用前缀
- 网络爬虫：使用URL前沿的BFS，礼貌（robots.txt、每域名速率限制），通过内容哈希去重
- 唯一ID：UUID（简单，无需协调）vs Snowflake（64位，时间排序，数据中心感知）

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **短链接服务** | base62编码自增ID或哈希 | `https://short.ly/a1B2c3` 映射到一个键值行 |
| **API保护** | 网关处的令牌桶 | 每个键每分钟100个令牌；稳定补充；拒绝并附带429 |
| **社交源** | 混合发散 | 预先计算<10K粉丝账户的源；合并明星帖子在读取时 |

在问题类似于已知设计时，请参阅 [references/common-designs.md](references/common-designs.md) —— URL缩短器、速率限制器、新闻源、聊天、自动完成、网络爬虫和唯一ID生成器的完整演练。

### 6. 可靠性和运维

**核心概念：** 系统的好坏取决于其保持运行、恢复和可观察的能力。健康检查、监控、日志记录和部署策略是第一流的系统设计考虑，而不是事后想法。

**为什么有效：** 生产系统以图表无法预测的方式失败。运维就绪性——指标、警报、回滚计划、冗余——决定了故障是短暂中断还是全面宕机。

**关键洞察：**
- 健康检查：活性（进程是否存活？）和就绪性（能否服务流量？）——Kubernetes都使用
- 可观察性的三个支柱：指标（Prometheus、Datadog）、日志（ELK、CloudWatch）、跟踪（Jaeger、Zipkin）
- 部署：滚动（渐进式）、蓝绿（即时切换相同环境）、金丝雀（先对一小部分）
- 灾难恢复：RPO（可接受的数据丢失）和RTO（可接受的恢复时间）驱动备份和故障转移策略
- 多数据中心：主动-被动（故障转移）或主动-主动（需要数据同步和冲突解决）
- 自动扩展：基于CPU、内存、队列深度或自定义指标；始终设置最小和最大计数

**代码应用：**

| 环境 | 模式 | 示例 |
|------|------|------|
| **零停机部署** | 带健康检查门的蓝绿 | 检查通过后切换到绿色；保留蓝色作为即时回滚 |
| **渐进式发布** | 带指标比较的金丝雀 | 5%流量到新版本；比较错误和延迟；提升或回滚 |
| **数据安全** | 定义RPO/RTO，相应实施 | RPO 1小时 = 每小时备份；RTO 5分钟 = 自动故障转移 |

在为生产环境加固时，请参阅 [references/reliability-operations.md](references/reliability-operations.md) —— 健康检查模式、可观察性支柱、部署策略、灾难恢复（RPO/RTO）和自动扩展。

## 常见错误

| 错误 | 为什么失败 | 修复 |
|------|----------|------|
| **需求之前架构** | 解决了错误的问题，错过了约束 | 花费5-10分钟确定范围：功能、规模、SLA |
| **无估算** | 配置偏差数量级 | 在选择组件前估算QPS、存储、带宽 |
| **单点故障** | 一个组件导致系统宕机 | 每层冗余：多服务器、多AZ、多区域 |
| **过早分片** | 在需要之前巨大的运维复杂性 | 首先垂直扩展，读取副本，缓存积极，最后分片 |
| **无失效的缓存** | 过期数据导致错误和混乱 | 定义TTL；缓存旁路带写入时的显式失效 |
| **到处同步调用** | 一个慢服务级联延迟到所有调用者 | 非延迟关键路径使用队列；同步调用超时 |
| **忽略热点** | 一个热点分片或键被猛击，其他空闲 | 检测热点键；添加二级分片或本地缓存 |
| **无监控或警报** | 用户在您之前发现故障 | 从第一天开始就监控指标、日志和跟踪 |

## 快速诊断

| 问题 | 如果没有 | 操作 |
|------|----------|------|
| 是否列出了功能和非功能性需求？ | 设计基于假设 | 写下功能、DAU、QPS、存储、延迟和可用性SLA |
| 是否有QPS和存储估算？ | 容量是猜测 | DAU x 操作数 / 86400 for QPS；记录 x 大小 x 保留期 for 存储 |
| 每个组件都是冗余的吗？ | 单点故障 | 添加副本、故障转移或多AZ每个组件 |
| 是否定义了数据库扩展策略？ | 在增长下遇到墙壁 | 首先垂直扩展，然后读取副本，然后分片，并具有明确的分片键 |
| 是否有读密集型路径的缓存？ | 数据库承受不必要的负载 | Redis/Memcached缓存旁路带定义的TTL |
| 异步路径是否使用队列？ | 紧密耦合、级联故障 | 使用Kafka/SQS解耦任务、通知、分析 |
| 是否有监控和警报计划？ | 盲目于生产故障 | 定义指标、日志聚合、跟踪、警报阈值 |
| 是否定义了部署策略？ | 风险性一次性发布 | 滚动、蓝绿或金丝雀带自动回滚 |
