# 设计日常事物框架

创建直观、可发现且易于理解产品的设计基础原则。"用户体验圣经"——适用于物理产品、软件及任何人类设计系统。

## 核心原则

**好的设计实际上比糟糕的设计更难被注意到，部分原因在于好的设计如此契合我们的需求，以至于设计本身变得隐形。** 当某事失败时，用户会责怪自己——但错误几乎总是出在设计上。优秀的设计弥合了人们想要做什么与产品允许做什么之间的差距：它是可发现的（你可以弄清楚该做什么）且易于理解的（你可以弄清楚发生了什么）。

## 评分

**目标：10/10。** 每个满足的快速诊断行得2分（5行=可发现性、评估、错误恢复、映射、约束）。等级：**9-10** = 用户无需指令即可操作、理解所有结果并从任何错误中恢复；**5-6** = 至少有一个鸿沟或错误路径被打破；**<=3** = 用户必须查阅手册或例行责怪自己。报告当前分数及失败的诊断行。

## 两个鸿沟

与产品的每一次交互都需要跨越两个鸿沟：

```
用户                                    产品
  │                                        │
  ├──── 执行鸿沟 ────────────────→│
  │     "我该如何做我想做的事？"         │
  │                                        │
  │←──── 评估鸿沟 ──────────────┤
  │     "发生了什么？它起作用了吗？"      │
```

### 执行鸿沟

**用户想要做什么与产品允许他们做什么之间的差距。** 用户会问：这里我能做什么？我应该使用哪个控件？

**通过以下方式跨越：** 清晰的指示器、自然映射、约束、熟悉的概念模型。

### 评估鸿沟

**产品做了什么与用户理解的发生了什么之间的差距。** 用户会问：发生了什么？它起作用了吗？系统处于什么状态？

**通过以下方式跨越：** 即时可见的反馈、清晰的状态指示器、有意义的错误消息、进度指示器。

**设计目标：** 使两个鸿沟尽可能窄——行动和理解应该是即时的。

参见：[参考资料/两个鸿沟.md](参考资料/两个鸿沟.md) 获取鸿沟分析练习。

## 七项基本设计原则

### 1. 可发现性

**定义：** 用户能否弄清楚哪些操作是可能的以及如何执行它们？其五个组成部分——可供性、指示器、约束、映射、反馈——将在下文中详细说明。

**测试：** 将新用户置于你的产品前。如果他们在10秒内无法弄清楚该做什么，可发现性就破坏了。

**反模式：** "用户手册解释了它。" 如果用户需要手册，设计就失败了。

### 2. 可供性

**定义：** 物体的属性与用户能力之间的关系，该关系决定了物体如何被使用。

**关键洞察：** 可供性无论是否被感知都存在——对设计而言重要的是*被感知*的可供性。

| 类型 | 定义 | 示例 |
|------|------------|---------|
| **真实** | 物理能力存在 | 按钮可供按压 |
| **感知** | 用户认为能力存在 | 抬高的区域看起来可点击 |
| **隐藏** | 存在但并不明显 | 右键单击上下文菜单 |
| **虚假** | 看起来可供操作但实际上不可 | 看起来可点击的装饰元素 |
| **反可供性** | 阻止操作 | 阻挡移动的障碍物 |

**数字应用：**

| 元素 | 可供性 | 如何表示 |
|---------|------------|---------------|
| **按钮** | 点击/轻点 | 抬高、颜色、阴影、悬停状态 |
| **文本字段** | 文本输入 | 边框、占位符文本、标签 |
| **滚动区域** | 滚动 | 滚动条、边缘渐变、部分内容 |

**常见错误：** 平面设计抹去感知可供性（按钮或标签？）、触摸目标太小、看起来相同的交互和装饰元素。

参见：[参考资料/可供性.md](参考资料/可供性.md) 获取可供性设计模式。

### 3. 指示器

**定义：** 传达操作应发生位置的信号。**可供性决定你能做什么；指示器告诉你在哪里以及如何做。**

| 类型 | 定义 | 示例 |
|------|------------|---------|
| **有意** | 设计用于传达 | 门上的"按"标签、占位符文本 |
| **偶然** | 无意但信息量丰富 | 草地中的磨损小径（人们从这里走） |
| **社会** | 其他人的行为 | 人行道表明入口 |

**数字指示器：**

| 指示器 | 它传达什么 | 示例 |
|-----------|---------------------|---------|
| **光标变化+悬停状态** | 这是交互的 | 链接上的指针→手形；按钮颜色变化 |
| **图标+标签** | 元素的函数 | 放大镜=搜索；"提交"、"取消" |
| **颜色+位置** | 状态、类别、层次结构 | 红色=错误、绿色=成功；关闭按钮右上角 |

**设计规则：** 不确定时，添加一个指示器——宁可过度传达也不让用户猜测。

参见：[参考资料/指示器.md](参考资料/指示器.md) 当决定为不明确的控件添加哪个指示器时。

### 4. 映射

**定义：** 控件与其效果之间的关系。**自然映射**意味着控件的物理布局与其控制的布局相匹配。

| 映射质量 | 示例 | 为什么有效/无效 |
|-----------------|---------|-------------------|
| **自然** | 音量滑块（向上=更响） | 与心智模型匹配 |
| **差** | 灯光开关面板 | 没有与灯光的空间对应关系 |
| **差** | 炉灶旋钮排成一行 | 布局与燃烧器位置不匹配 |

**数字原则：** 控件靠近其影响的对象、布局镜像内容、方向匹配预期（向下滚动=内容向上移动）、相关控件分组。

| 技巧 | 如何工作 | 示例 |
|-----------|-------------|---------|
| **邻近** | 控件靠近目标 | 编辑按钮紧邻内容 |
| **空间** | 布局镜像现实世界 | 地图控件匹配指南针方向 |
| **文化** | 遵循惯例 | 红色=停止/危险、绿色=前进/安全 |
| **顺序** | 遵循自然顺序 | 步骤1、2、3从左到右（或从上到下） |

参见：[参考资料/映射.md](参考资料/映射.md) 获取映射分析练习。

### 5. 约束

**定义：** 限制可能的操作以防止错误。

| 类型 | 机制 | 示例 |
|------|-----------|---------|
| **物理** | 形状/尺寸防止错误操作 | USB插头只能以一种方式插入 |
| **文化** | 社会规范引导行为 | 红色=停止、绿色=前进 |
| **语义** | 含义限制选项 | 后视镜只能面向后部才有意义 |
| **逻辑** | 逻辑限制选择 | 最后一个螺丝只剩一个孔 |

**数字约束：**

| 约束 | 实现 | 示例 |
|------------|---------------|---------|
| **输入验证** | 限制可以输入的内容 | 日期选择器与自由文本 |
| **禁用状态** | 灰度显示不可用选项 | "提交"在表单有效前禁用 |
| **强制顺序+撤销** | 按顺序执行；允许撤销 | 带锁定步骤的向导；Gmail"撤销发送" |

**设计规则：** 你添加的每个约束都是用户可以少犯的一个错误——使错误操作不可能，而不是惩罚他们。

参见：[参考资料/约束.md](参考资料/约束.md) 获取约束设计模式。

### 6. 反馈

**定义：** 将操作结果传达给用户的反馈。反馈必须即时（直接操作在0.1秒内）、信息量充足、适度且不侵入。

| 类型 | 何时使用 | 示例 |
|------|-------------|---------|
| **视觉** | 大多数操作 | 按钮按压动画、颜色变化、对勾 |
| **听觉** | 重要事件、确认 | 成功提示音、错误声音 |
| **触觉** | 触摸设备、确认 | 按键时振动 |
| **进度** | 长操作 | 进度条、旋转器、骨架屏幕 |

**数字反馈模式：**

| 情况 | 需要反馈 | 示例 |
|-----------|----------------|---------|
| **表单提交** | 成功/错误消息 | "已保存！"提示或内联错误 |
| **加载** | 进度指示器 | 旋转器、骨架屏幕、百分比 |
| **错误** | 出了什么问题+如何修复 | "无效电子邮件。请检查格式。" |

**响应时间：** 0.1秒感觉即时；1秒是可察觉的延迟（改变光标）；10秒失去注意力（显示进度条）；超过10秒用户离开（显示百分比，允许后台处理）。

**常见错误：** 无反馈（我的点击注册了吗？）、延迟反馈（感觉出错了）、反馈不明确、警报过载。

参见：[参考资料/反馈.md](参考资料/反馈.md) 当一个操作没有明确结果时，你需要正确的反馈类型和时机。

### 7. 概念模型

**定义：** 用户对产品如何工作的心智模型。

| 模型 | 由谁持有 | 描述 |
|-------|---------|-------------|
| **设计模型** | 设计师 | 设计师认为它如何工作 |
| **用户模型** | 用户 | 用户认为它如何工作 |
| **系统图像** | 产品 | 产品实际传达的内容 |

**目标：** 用户的模型应与设计模型匹配；系统图像是唯一的桥梁。匹配的模型让用户预测结果并从错误中恢复；不匹配会导致困惑、自责和支持请求。

**示例（恒温器）：** 设计模型——设置温度，系统保持它；常见用户模型——更高的设置加热更快（错误），所以用户会将它调到90°F。

**使用以下方式构建正确模型：** 熟悉的隐喻（桌面、垃圾箱）、可见的系统状态、清晰的反馈、一致的行为、渐进式披露。

参见：[参考资料/概念模型.md](参考资料/概念模型.md) 当用户的模型与产品实际工作方式不符时。对于完全拆解的案例研究（门把手、恒温器、数字产品），参见[参考资料/案例研究.md](参考资料/案例研究.md)。

## 人类错误

**诺曼的关键洞察：不存在"人类错误"——只有糟糕的设计。** 当有人犯错时，寻找设计缺陷，而不是人的缺陷。

### 错误类型

**失误**——正确意图，错误操作：

| 失误类型 | 原因 | 示例 | 设计修复 |
|-----------|-------|---------|------------|
| **操作失误** | 在正确目标上执行错误操作 | 点击"删除"而不是"编辑" | 将破坏性操作分开 |
| **记忆衰退** | 忘记序列中的步骤 | 写完"已附加"后忘记附件 | Gmail的附件提醒 |
| **模式错误** | 正确操作，错误模式 | 大小写锁定下输入 | 清晰显示模式状态 |
| **捕获错误** | 习惯覆盖意图 | 自动驾驶到旧办公室 | 在决策点中断 |

**错误**——错误意图，正确执行：

| 错误类型 | 原因 | 示例 | 设计修复 |
|-------------|-------|---------|------------|
| **基于规则** | 应用错误规则 | 在错误情况下使用公式 | 提供上下文，确认 |
| **基于知识** | 不完整/错误的心智模型 | 误解系统如何工作 | 更好的概念模型 |
| **记忆衰退** | 忘记目标或计划 | 忘记为什么打开冰箱 | 提醒，历史记录 |

### 针对错误设计

**预防：** 使错误不可能的约束、无处不在的撤销/重做、破坏性操作的确认、合理的默认值、宽容的输入。
**恢复：** 清晰的错误消息、永远不删除用户的工作、部分保存、轻松重置到已知良好状态。

**错误消息清单：**
- [ ] 说明出了什么问题（用人类语言）
- [ ] 说明如何修复
- [ ] 不要责怪用户
- [ ] 保留用户的工作
- [ ] 提供替代路径

参见：[参考资料/人类错误.md](参考资料/人类错误.md) 获取错误预防模式。

## 行动的七个阶段

**诺曼的人类与产品交互模型：**

```
1. 目标      → "我想调整温度"
2. 计划      → "我将使用恒温器"
3. 指定   → "我将按下上箭头"
4. 执行   → (按下按钮)
   ─── 执行鸿沟 ───
5. 感知  → (看到显示变化)
6. 解释 → "数字变大了"
7. 比较   → "这是我所想要的吗?"
   ─── 评估鸿沟 ───
```

**设计启示：** 用指示器、映射和约束支持阶段1-3；阶段4用好的可供性；阶段5-7用反馈和可见状态。通过每个阶段检查任何交互，以发现用户在哪里卡住。

参见：[参考资料/七个阶段.md](参考资料/七个阶段.md) 获取分阶段分析。

## 以人为本设计（HCD）流程

```
观察 → 想法生成 → 原型制作 → 测试 → (迭代)
```

改变你运行此循环的两个具体细节：在**观察**中，不要问用户他们想要什么（他们不知道）——在真实环境中观察他们的替代方案和挫败感。在**测试**中，使用真实用户而不是设计师——5个真实用户可揭示约85%的问题，所以观察行为而非意见并迭代。

## 常见错误

| 错误 | 为什么失败 | 修复 |
|---------|-------------|------|
| **无指示器** | 用户找不到功能 | 为每个交互元素添加视觉提示 |
| **无反馈** | 用户不知道操作是否成功 | 在0.1秒内对每个操作做出响应 |
| **责怪用户** | 忽略设计缺陷 | 寻找每个"用户错误"的设计原因 |
| **功能蔓延** | 复杂性压倒用户 | 应用约束，渐进式披露 |
| **不一致** | 破坏概念模型 | 相同操作=相同结果 |
| **忽略上下文** | 设计用于理想条件 | 观察真实使用环境 |

## 快速诊断

审核任何设计：

| 问题 | 如果没有 | 操作 |
|-------|-------|--------|
| 用户能否弄清楚该做什么？ | 可发现性差 | 添加指示器，改进可供性 |
| 用户是否理解发生了什么？ | 评估鸿沟太宽 | 添加反馈，显示系统状态 |
| 用户能否从错误中恢复？ | 没有错误容忍度 | 添加撤销，确认，清晰消息 |
| 控件布局是否与输出匹配？ | 映射差 | 重新组织控件以匹配空间布局 |
| 是否隐藏了不可能/不相关的选项？ | 缺少约束 | 禁用、隐藏或删除无效选项 |

## 关于作者

**Don Norman，博士** 是尼尔森诺曼集团的联合创始人，是加州大学圣地亚哥分校设计实验室的主任，也是苹果公司高级技术的前任副总裁，他创造了"用户体验"一词。"日常事物的设计"（1988年，2013年修订版）被广泛认为是史上最有影响力的设计书籍，并在全球设计课程中作为必读材料。
