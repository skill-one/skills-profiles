# 创建应用

将一个原始的应用想法转化为一个经过验证、架构清晰的第一版，并在可持续的节奏下发布——而不会为了尚未挣得的规模而过度构建，或者编写一个最终会变成重写的原型。这段旅程分为十个阶段：它在每个决策之前都会进行询问，并将每个选择记录在 `docs/` 中，以便您可以在不同会话中暂停和继续。早期的阶段通常不会产生任何代码；一旦实验批准构建，工程阶段就会构建出真正的东西。

## 核心原则

**快速验证同时保持选择开放：将昂贵且难以逆转的决策提前做出，并将所有廉价的事项推迟。** 将稀缺的早期精力投入到少数几个复合因素上——最冒险的假设、依赖边界、领域语言——并积极避免浪费。

这项技能排序阶段、提出问题并记录决策；构成技能承载着方法。调用它们，而不是自己构建它们的框架。

## 运营规则

1. **首先恢复。** 在做任何事之前，请阅读 `docs/CREATE-APP-PLAN.md` 和旅程地图中的每个产出物。如果存在跟踪器，请用3-5行总结旅程状态，并询问进入哪个阶段。当用户确认入口点时完成。带有跟踪器的旅程是恢复的，而不是重新开始的。
2. **仅在第一次运行时进行信息输入。** 没有跟踪器：运行下面的信息输入，然后创建 `docs/CREATE-APP-PLAN.md`，将每个阶段的状态标记为 `pending | in-progress | awaiting-evidence | done | deferred: reason | skipped: reason`。当跟踪器存在并且用户确认了阶段计划时完成。
3. **阶段入口。** 宣布：阶段的作用、它强制的决策、它产生的产出物、粗略的工作量。提供继续 / 跳过 / 推迟——标记为 GATE 的阶段可以推迟，但不能跳过。在继续时将阶段标记为 `in-progress`。当用户做出选择时完成。
4. **技能调用和回退。** 加载阶段的技能并使用它：每个阶段的调用行通过slug命名技能——使用该技能来运行阶段。如果不可用，提供：`npx skills add wondelai/skills/<slug> --global`。如果用户拒绝，则从其简要信息运行阶段——最低可用的方法。说明您处于何种模式。
5. **阶段内的决策。** 询问“与用户共同决策”下的每个问题——提供具体的选项和您的建议。在跟踪器的关键决策中记录选择。无声做出的决策是缺陷。
6. **阶段退出。** 在写入之前，展示草稿产出物内容以供批准。在批准后：写入或扩展 `docs/` 文件，更新跟踪器（状态、关键决策、下一步行动）。当文件写入并且阶段行显示 `done` 时完成。
7. **产出物纪律。** 写作前阅读；如果文件不存在，则创建它，否则扩展——添加或更新您的部分，保留其他人的部分。文件在 `docs/` 中是大写的。每个建议都作为一个复选框或一个带有所有者和优先级的表格行出现。在创建 `docs/` 文件时，请参阅 [references/artifact-templates.md](references/artifact-templates.md)——从完整骨架（所有部分标题）创建它，然后填写您的阶段命名的部分。
8. **代理准备和处理；只有人类与客户和测试用户交谈。** 起草冲刺脚本和访谈指南并评分结果，然后暂停状态为 `awaiting-evidence`，直到用户返回笔记。ios-hig-design 阶段仅适用于发布原生 iOS 应用；否则在信息输入时跳过它。

## 信息输入

在创建跟踪器之前询问以下问题：

1. 应用想法用一句话是什么，以及它背后的最冒险的信念是什么？（Gates 阶段 1；如果应用所做的工作不明确，请添加工作要做的可选阶段。）
2. 基本想法是否已经通过行为证据得到验证，还是仍然是一个猜测？（未验证且风险高会使阶段 1 成为强制性；如果已经存在付费客户，您可能处于错误的旅程——改进应用或增长应用。）
3. 它处于什么阶段——周末原型、资助构建以发布，还是围绕它组建的团队？（原型依赖于阶段 1-3 和 10；组建团队的可能会添加灵感产品。）
4. 您是否会发布原生 iOS 客户端？（是会保留阶段 8；否则会跳过它。）
5. 您是否有客户可以交谈，还是必须找到他们？（Gates 阶段 1-2 中的人类证据循环和可选 mom-test / 持续发现。）
6. 您期望前几个月的负载是多少——每日活跃用户和每日操作？ （为阶段 7 容量数学提供信息，并停止过早的扩展。）
7. 独立构建还是团队，以及谁拥有发布节奏？ （Gates 阶段 9 的塑造。）

阶段跳过启发式规则：当核心流程已经测试或简单时跳过阶段 2；除非发布原生 iOS，否则跳过阶段 8；仅当负载明显很小时才跳过阶段 7——但仍然记录估计；对于周末原型，将阶段 3-6 作为一次通过运行，但永远不要跳过依赖规则。

然后从模板创建 `docs/CREATE-APP-PLAN.md`，将每个阶段的状态标记，并将阶段 8 标记为 iOS 条件性。当 `docs/CREATE-APP-PLAN.md` 存在并且每个阶段都被标记并且用户确认了计划时完成。

## 阶段

### 阶段 1 — 验证最冒险的假设（lean-startup）

**目的：** 在编写生产代码之前，证明如果假设为假，会杀死应用。

**简要信息（回退）：** 向后规划构建-衡量-学习：您必须学习什么，您将如何知道，什么是最小的构建可以找出。按什么致命而不是容易测试来对跳跃假设进行排序。MVP 是一个学习工具，通常很粗糙（Dropbox 是用视频而不是同步引擎验证的）。爬上验证阶梯——注册弱，付费存款强，活跃使用最强；目标是行为级别 4-5，永远不要“你会使用这个吗？”的意见。

**调用：** 使用 `lean-startup` 技能，并使用想法，如果存在 CUSTOMER.md，则使用工作声明。询问排序的跳跃假设，最简单的可以推翻最冒险的实验，以及预先承诺的行为成功阈值。

**与用户共同决策：** 哪个假设如果为假是致命的？哪种实验类型——烟雾测试（需求），concierge（价值），奥兹巫师（自动化）？什么 go/pivot 阈值，在运行之前固定？只有用户与真人一起运行它；然后暂停 `awaiting-evidence`。

**产出物：** 创建 docs/PRODUCT.md，带有 `## Vision` 和 `## MVP Definition`；创建 docs/EXPERIMENTS.md，带有 `## Experiment Cards`（EXP-001 带有假设、指标、决策规则）和 `## Experiment Backlog`。更新跟踪器。

**完成时：** 最致命的假设被命名，EXP-001 具有预先承诺的阈值，PRODUCT.md 声明了 MVP 范围，并且用户有实验可以运行。

### 阶段 2 — 降低核心体验的风险（design-sprint）

**目的：** 使用测试过的外观来固定核心流程应该是什么，然后再投入工程时间。

**简要信息（回退）：** 五天：星期一映射问题，星期二草图，星期三决定，星期四原型，星期五与五个真实用户测试。输出是一个高保真外观加上证据，而不是代码。最危险的时刻是一个陌生人第一次的十分钟——测试他们是否理解并完成核心任务，而不需要解释。五个用户会显示出模式；您需要模式，而不是显著性。永远不要解释原型；观察他们在哪里卡住。

**调用：** 使用 `design-sprint` 技能，并使用 PRODUCT.md 中的 MVP 范围。询问星期一的映射和 How Might We 重构，一个获胜的概念故事板，以及一个带有笔记网格的五幕访谈脚本（每个参与者检查标记 / 交叉 / 波浪号）。在暂停时，在 docs/EXPERIMENTS.md 的冲刺卡片下记录批准的脚本，以便它可以在会话中断期间存活。

**与用户共同决策（返回时）：** 测试过的流程是否按原样工作，需要重塑，还是暴露了一个循环回阶段 1 的需求问题？哪些困惑成为修复？

**产出物：** 创建 docs/DESIGN.md，带有 `## Design Direction`；扩展 docs/EXPERIMENTS.md `## Experiment Cards`，带有冲刺测试及其裁决。更新跟踪器。

**完成时：** DESIGN.md 记录了方向，冲刺结果和裁决在 EXPERIMENTS.md 中，并且用户选择了继续 / 重塑 / 循环。

### 阶段 3 — 绘制边界（clean-architecture）

**目的：** 隔离业务规则，使数据库、框架和提供者保持可交换的细节。

**简要信息（回退）：** 源代码依赖指向内部——框架指向用例指向实体。业务规则不能导入框架或 ORM。用例定义接口（例如 InvoiceRepository）；基础设施实现它们；控制器将 HTTP 请求转换为纯请求对象并接收纯响应——不要跨越边界传递框架类型。诊断：您能否在没有数据库、Web 服务器或框架运行的情况下测试业务规则？四个圆圈是典型的，而不是神圣的——仅在波动点绘制边界。

**调用：** 使用 `clean-architecture` 技能，并使用 PRODUCT.md 中验证的 MVP 范围。询问层映射、核心用例及其请求/响应模型，以及它依赖的存储库接口。

**与用户共同决策：** 真实的波动边界在哪里（数据库、第三方 API、交付机制）？完整的四层，或者对于小型应用合并适配器和框架？

**产出物：** 创建 docs/ARCHITECTURE.md，带有 `## System Context` 和 `## Layer Map & Dependency Rule`（层、什么依赖于什么、违规表格）。更新跟踪器。

**完成时：** ARCHITECTURE.md 命名了层，依赖规则方向是明确的，并且核心业务规则可以在没有基础设施的情况下进行测试。

### 阶段 4 — 域建模（domain-driven-design）

**目的：** 使代码说出业务，以便领域专家可以阅读并发现错误。

**简要信息（回退）：** 模型就是代码。构建一个通用语言——根据领域概念命名事物，而不是技术角色（InvoiceDraft.finalize() 比起 DataProcessor.process() 更好）；难以命名是一个设计信号。边界上下文：一个词在一个边界内意味着一个东西（账单中的“Customer”不必等于支持中的“Customer”）。聚合：一个具有一个根的集群，它强制不变性——保持它们小，通过 ID 参考其他聚合。避免贫血模型；将行为推入实体和值对象。

**调用：** 使用 `domain-driven-design` 技能，并使用 ARCHITECTURE.md 的层映射。询问通用语言、边界上下文和上下文映射，以及核心聚合及其根强制的不变性。

**与用户共同决策：** 核心域（您的竞争优势）与通用子域（认证、电子邮件、支付）的区别在哪里（购买或使用开源）？同一个词在不同的上下文中是否合法地意味着不同的事情？

**产出物：** 扩展 docs/ARCHITECTURE.md：添加 `## Bounded Contexts & Context Map` 和 `## Domain Glossary (Ubiquitous Language)`（术语 | 含义 | 代码名称）。更新跟踪器。

**完成时：** 涵盖表命名了核心概念，上下文和关系被映射，并且存储库接口按照阶段 3 位于领域层。

### 阶段 5 — 编写可读的代码（clean-code）

**目的：** 随着代码库的增长，保持每个函数可读且经过测试。

**简要信息（回退）：** 代码比编写更常被阅读。小函数做一件事情，在单个抽象级别；意图揭示的名称；没有标志参数（一个迹象——函数做两件事）；命令与查询分离；一个命名良好的提取函数比注释更好。测试是一流的——脏测试比没有好。按照 F.I.R.S.T.（快速、独立、可重复、自我验证、及时）编写它们，使用基于行为的名称，如 shouldRejectNegativeTotal。

**调用：** 使用 `clean-code` 技能，并使用阶段 3-4 的核心模块。询问针对规则的评分和修复，以及核心用例的干净单元测试（安排-执行-断言、描述性名称、构建器帮助程序）。

**与用户共同决策：** 什么质量标准控制提交——函数大小、名称清晰度、没有吞没的异常？哪些 happy-path 和失败情况必须第一个测试覆盖？

**产出物：** 创建 docs/TESTING.md，带有 `## Test Strategy`（金字塔、工具、什么绿色门）和 `## Safety Net Map`（模块 | 固定的行为 | 测试文件 | 空白）。更新跟踪器。

**完成时：** TESTING.md 声明了策略，核心用例具有通过的行为命名测试，不需要数据库，并且提交质量标准被记录。

### 阶段 6 — 安装元学科（pragmatic-programmer）

**目的：** 采用保持代码库多年易于更改的习惯。

**简要信息（回退）：** 发射一个示波器——每个层（UI 到用例到数据库和返回）的一个薄的真正切片，保持它，以在第二天发现集成错误。DRY 仅适用于知识，而不是偶然的相似性。正交性：更改数据库不得触及 UI。可逆性：将第三方 SDK 封装在您自己的接口后面，以便 Stripe 或模型提供者可以交换，而不会触及业务逻辑。破损的窗户：修复第一个黑客或用跟踪的票证将其封存——永远不要留下无声的腐烂。

**调用：** 使用 `pragmatic-programmer` 技能，并使用 ARCHITECTURE.md 和核心用例。询问最薄的端到端示波器设计和每个第三方依赖的适配器接口。

**与用户共同决策：** 示波器是什么？破损的窗户政策是零容忍并带有跟踪的票证吗？哪些依赖项现在获得适配器接口，哪些以后获得？

**产出物：** 扩展 docs/TESTING.md (`## CI Gates`) 和 docs/TECH-DEBT.md (`## Debt Budget & Broken-Windows Policy` 和 `## Adopted Conventions`)。更新跟踪器。

**完成时：** 示波器端到端指定，为每个提供者命名适配器接口，并且破损的窗户政策被记录下来。

### 阶段 7 — 诚实地确定大小（system-design）

**目的：** 估计真实的负载，并证明您不需要构建什么。

**简要信息（回退）：** 从需求开始，而不是解决方案。QPS = 每日活跃用户 x 每日操作 / 86,400，峰值 2-5 倍平均；存储 = 每天记录数 x 记录大小 x 保留。对于几百个用户，数学几乎总是说一个索引良好的数据库加上一个缓存。按顺序扩展：首先垂直，然后读取副本，然后缓存，最后分片。只有在估计或真实瓶颈证明它值得时，才使用队列来吸收峰值并将慢速工作（例如照片 OCR）与请求路径解耦。

**调用：** 使用 `system-design` 技能，并使用信息输入中的负载数字。询问后计算的 QPS 和存储估计，以及明确列出您现在不需要的技术。

**与用户共同决策：** 给定估计，您故意推迟哪些扩展？如果有任何真实瓶颈，它现在证明需要缓存或队列吗？

**产出物：** 扩展 docs/ARCHITECTURE.md：添加 `## Data & Storage Decisions` 和 `## Decision Log`（日期 | 决策 | 原因 | 被拒绝的替代方案），将每个“不”记录为决策。更新跟踪器。

**完成时：** 容量估计被记录，推迟的扩展技术被明确列出，任何缓存或队列都被数字证明。

### 阶段 8 — 让它感觉原生（ios-hig-design）— 仅限 iOS

**目的：** 让 iPhone 客户端感觉原生——这是 iOS 用户信任的基础。仅在发布原生 iOS 客户端时运行（在信息输入中决定）；否则跳过。

**简要信息（回退）：** 三个支柱——清晰度、委婉、深度。尊重安全区域（动态岛屿、主指示器）；每个触摸目标至少 44x44 pt；语义颜色（Color(.label), Color(.systemBackground)）以便 Dark Mode 自动化；语义文本样式用于动态类型；原生导航——主要目的地使用标签栏，NavigationStack 用于下钻，sheet 用于专注任务，永远不要使用汉堡菜单。无障碍是第一流的：每个控件都有一个标签，并且 VoiceOver 可以完成每个任务。

**调用：** 使用 `ios-hig-design` 技能，并使用应用的关键屏幕。询问安全区域、44pt 目标、语义颜色和类型、原生导航和可访问性标签的 HIG 审计。

**与用户共同决策：** 哪些屏幕在第一次审查范围内？任何故意偏离平台，它们是否合理？

**产出物：** 扩展 docs/DESIGN.md：添加 `## Components`（组件 | 决策 | 状态）和 `## UX Audit Findings`（问题 | 启发式 | 严重性 0-4 | 修复 | 状态）。更新跟踪器。

**完成时：** 每个在范围内的屏幕都被审查，发现被记录为严重性，并且可访问性差距被捕获为修复。

### 阶段 9 — 按节奏发布（37signals-way）

**目的：** 在固定时间内发布一个专注的 v1，以对抗功能蔓延。

**简要信息（回退）：** 构建半个产品，而不是半个不情愿的产品。在下注之前塑造工作：足够粗糙以获得设计自由，解决足够的问题以消除大的未知数，由食欲界定（“这值得两周”）——而不是估计。固定时间并裁剪范围以适应，永远不要反过来。将塑造的提议下注到固定周期中；一个断路器会在截止日期时杀死任何未完成的任何东西。有偏见的软件：每个提供的偏好都是一个拒绝的决策；选择合理的默认值；对功能的默认答案是尊重的“现在不”。

**调用：** 使用 `37signals-way` 技能，并使用 PRODUCT.md 中的 MVP 范围。询问下一个功能塑造为提案（问题、食欲、面包板、兔子洞、不做什么），以及 v1 裁剪列表。

**与用户共同决策：** 下一个功能的食欲是什么？哪些 v1 功能被裁剪，哪些用户界面偏好成为有偏见的默认值？

**产出物：** 扩展 docs/PRODUCT.md (`## Outcome Roadmap`) 和 docs/STRATEGY.md (`## No-List` — 我们明确不会做的事情）。更新跟踪器。

**完成时：** 下一个功能具有带有食欲的塑造提案，v1 裁剪列表在 STRATEGY.md 的 No-List 中，路线图反映了固定时间 / 灵活范围。

### 阶段 10 — 将复杂性视为敌人（software-design-philosophy）

**目的：** 在每个模块中控制复杂性——所有其他阶段的透镜。

**简要信息（回退）：** 复杂性是任何使系统难以理解和更改的结构。优先考虑深度模块——强大的功能背后有一个简单的接口——而不是浅层模块；根据功能除以接口复杂性来评估模块，而不是行数。这纠正了 Clean Code 的“小”和 DDD 的许多概念滑入类itis（一群只有一个方法的浅层类）。战略优先于战术：在设计中投入稳定的 10-20% 额外时间，因为早期的捷径在团队和代码库增长时会成倍增加。

**调用：** 使用 `software-design-philosophy` 技能，并使用阶段 3-6 的模块。询问深度与浅层的评估，标记浅层类、传递方法、边界跨边界的信息泄漏，以及合并位置。

**与用户共同决策：** 哪些浅层模块应该合并到更深的模块中？战术捷径在哪里累积的债务值得现在战略的 10-20%？

**产出物：** 扩展 docs/TECH-DEBT.md (`## Smell Inventory`: 嗅觉 | 位置 | 重构 | 状态) 和 docs/ARCHITECTURE.md (`## Decision Log`)。更新跟踪器。

**完成时：** 浅层模块和泄漏被记录在 Smell Inventory 中，合并决策被记录，并且战略与战术的立场已达成一致。

## 常见错误

| 错误 | 修复 |
|---|---|
| 在验证想法之前构建架构 | 首先运行阶段 1——验证是廉价的，重写不是 (`lean-startup`)。 |
| 将“MVP”视为编写垃圾的许可 | 发布最小的东西来学习，然后在批准后构建真正的东西——最小不是低质量 (`lean-startup`)。 |
| 让框架决定架构 | 将框架保留在外围作为插件；没有 ORM 类型跨越用例边界 (`clean-architecture`)。 |
| 贫血领域模型 | 将行为推入实体和值对象，而不是脂肪服务类 (`domain-driven-design`)。 |
| 类itis——过度应用“小” | 根据深度（每个单位接口的功能）而不是行数来评估模块 (`software-design-philosophy`)。 |
| 过早扩展 | 做出估计；一个数据库加上一个缓存可以承载大多数应用很远——最后分片 (`system-design`)。 |
