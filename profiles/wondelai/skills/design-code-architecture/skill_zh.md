# 设计代码架构

设计新应用的架构：正确把握少数难以逆转的关键决策，并在其他地方保持激进简化。这是一个包含八个阶段的交互式、可中断的旅程——代理在做出每个决策前都会询问并记录结果在你的项目的 `docs/` 文件夹中，因此你可以在任何阶段停止并稍后继续。它从最基础且难以逆转的部分（边界、领域）开始，经过可调优的部分（数据、弹性），到贯穿始终的跨领域原则（复杂性、可逆转性、范围）。一个周末项目只需轻量级使用三个阶段；一个为发布而建设的资助团队则需要整个技术栈。

## 核心原则

**架构是一组难以逆转的决策集合：刻意做出这些决策，并将所有廉价决策推迟。**这项技能按阶段顺序排列问题，记录每个选择在 `docs/` 中。构成技能的方法是调用它们而不是临时构建它们的框架。整个策略是通过在它们前面设置边界，将昂贵决策转化为廉价决策，从而保持不可削减的昂贵决策集足够小，以便仔细处理。

## 操作规则

1. **首先中断。** 在做任何事之前，阅读 `docs/DESIGN-CODE-ARCHITECTURE-PLAN.md` 和旅程地图中的每个产出物。如果存在追踪器，用 3-5 行总结旅程状态并询问进入哪个阶段。当用户确认入口点时完成。带有追踪器的旅程是中断的，而不是重新开始的。
2. **仅在第一次运行时输入。** 没有追踪器：运行下面的输入，然后创建 `docs/DESIGN-CODE-ARCHITECTURE-PLAN.md`，将每个阶段状态为 `pending | in-progress | awaiting-evidence | done | deferred: reason | skipped: reason`。当追踪器存在且用户确认阶段计划时完成。
3. **阶段入口。** 宣布：阶段的作用、它强制的决策、它产生的产出物、粗略的工作量。提供继续 / 跳过 / 推迟——标记为 GATE 的阶段可以推迟，但不能跳过。在继续时将阶段标记为 `in-progress`。当用户选择时完成。
4. **技能调用和回退。** 加载阶段的技能并使用它：每个阶段的调用行命名技能的缩写——使用该技能运行阶段。如果不可用，提供：`npx skills add wondelai/skills/<slug> --global`。如果用户拒绝，从其简要运行阶段——最小可行方法。说明你处于哪种模式。
5. **阶段内决策。** 询问“与用户共同决策”下的每个问题——提供具体选项和你的建议。在追踪器的关键决策中记录选择。无声做出的决策是缺陷。
6. **阶段退出。** 在写入之前，展示草稿产出物内容以供批准。批准后：写入或扩展 docs/ 文件，更新追踪器（状态、关键决策、下一步行动）。当文件写入且阶段行显示 `done` 时完成。
7. **产出物纪律。** 写之前阅读；如果文件不存在则创建，否则扩展——添加或更新你的部分，保留其他人的部分。文件在 `docs/` 中为大写。每个建议都作为带所有者和优先级的复选框或表格行出现。创建 docs/ 文件时查看 [references/artifact-templates.md](references/artifact-templates.md)——从完整骨架（所有部分标题）创建，然后填充你的阶段名称的部分。
8. **每个难以逆转的决策在代码假设它之前都有一个决策日志行（决策、原因、拒绝的替代方案）。** 默认为模块化单体：服务仅在已证明的边界上下文中分割。

## 输入

在创建追踪器之前询问以下问题：

1. 应用将做什么，以及哪个功能是你们真正的竞争优势？（在阶段 2 中框定核心子域——在哪里进行深度建模与购买现成产品）
2. 你们倾向于哪个技术栈——语言、网络框架、ORM、数据库？（阶段 1 边界和阶段 4 数据决策的门槛；被视为细节，而不是骨架）
3. 第一年的实际负载是多少——粗略的日活跃用户和每个用户采取的主要操作？ （阶段 3 尺寸的门槛：需求在解决方案之前）
4. 它将调用哪些出站依赖项——支付、电子邮件、LLM API、运输、队列？ （阶段 6 集成点审计的门槛）
5. 哪个数据是系统的记录，以及是否存在第二读取模式，如搜索、分析或信息流？ （阶段 4 一致性和派生数据决策的门槛）
6. 是否有人验证了人们确实想要这个应用？（如果没有，请先路由到创建业务 / 创建应用——不要架构一个未经验证的想法）
7. 多少团队将拥有这个系统，以及你们现在想要多少旅程？ （门槛团队拓扑的可选阶段和阶段 8 的需求）

阶段跳过启发式：当第一年负载远低于任何阈值时跳过阶段 3 的扩展机械和阶段 4 的大部分复制（单个索引数据库是答案——记录它并继续）；对于单团队应用跳过团队拓扑的可选阶段。永远不要跳过阶段 1 或阶段 2——边界和领域模型是使每个后续决策廉价的加性工作；一旦存在真实用户和出站调用，阶段 6 的弹性不是可选的。然后从模板创建追踪器并确认计划。

当 `docs/DESIGN-CODE-ARCHITECTURE-PLAN.md` 存在且每个阶段都被状态，并且用户确认了计划时完成。

## 阶段

阶段按列表顺序运行，从最难逆转到可调优再到跨领域——每个阶段都假设前一个阶段的产出物存在。根据操作规则，任何阶段都可以进入、跳过或推迟；阶段 1-2 是使它们之后的所有决策廉价更改的加性工作。

阶段形成一个依赖链，与系统镜像：领域驱动设计说边界在哪里属于（上下文和聚合接缝）；干净架构说依赖项如何跨越它们；数据密集型应用决定持久化层中哪些内容存在于其中；系统设计说实际需要多少基础设施——通常远少于恐惧。软件设计保持模块深度而不是乘以浅层仪式，Release It! 硬化集成点，务实程序员提供跨领域习惯以保持结构随时间推移，而 37signals 方式通过固定时间和削减范围来管理整个事情。

### 阶段 1 — 绘制边界（clean-architecture）

**目的：** 保持业务规则独立于框架、数据库和供应商，以便每个后续决策保持可交换——这是买回所有其他决策的举动。

**简要（回退）：** 依赖规则——源代码依赖指向内部：框架 → 接口适配器 → 用例 → 实体；内部不命名任何外部内容。数据库、网络和供应商是细节，是规则的插件。用依赖反转强制执行：用例拥有仓库接口；Postgres/Stripe 实现存在于外部适配器中。只在真实波动点（数据库、外部服务、交付）绘制完整边界；在其他地方折叠层——方向很重要，不是文件夹数量。

**调用：** 使用 `clean-architecture` 技能，用输入中的具体第一个功能和技术栈。要求它为该功能分层（实体、带有请求/响应模型的用例、仓库 + 网关接口、HTTP 控制器和数据库适配器在外部环），并标记哪些边界是仪式而不是在真实波动点赚取成本。

**与用户共同决策：** (1) 模块化单体与服务——默认为具有干净内部边界的模块化单体；具有共享数据模型的微服务是分布式单体，严格更差。 (2) 哪些波动点现在获得完整边界接口，而不是折叠层。

**产出物：** 创建 docs/ARCHITECTURE.md，包含 `## 系统上下文`（做什么，集成）、`## 层级图 & 依赖规则`（层级，什么依赖于什么；违规 | 位置 | 修复 | 状态）、以及模块化单体与服务的选择在 `## 决策日志`（日期 | 决策 | 原因 | 拒绝的替代方案）。更新追踪器。

**完成时：** 层级图存在，第一个功能使用框架/ORM 类型限制在外部环，核心设计为在没有数据库/网络/框架的情况下可测试，模块化单体与服务的决策是决策日志行，阶段 1 显示 `done`。

### 阶段 2 — 建模领域（domain-driven-design）

**目的：** 在业务实际分割的地方设置边界，并使代码说出领域——现在最便宜，从空白页发明词汇。

**简要（回退）：** 模型是代码——构建通用语言，使团队词汇成为代码词汇。根据领域概念命名（`Order.place()`，而不是 `OrderManager.process()`）；一个抵制名称是设计信号，而不是烦恼。边界上下文：一个区域，一个词在这里精确地意味着一件事（“Customer”在计费与支持中不同）——这些是你们未来的服务接缝。聚合：一个小型根集群强制执行不变性，内部立即一致，外部最终一致；通过 ID 引用其他聚合。将行为推入实体——没有贫血数据包。

**调用：** 使用 `domain-driven-design` 技能，用领域词汇和阶段 1 层级图。要求构建从团队实际使用的词汇构建的边界上下文映射，核心聚合及其不变性，以及子域分类（核心 / 支持 / 通用）。

**与用户共同决策：** (1) 同一个词在上下文中真正意味着不同的事情——不要统一成一个全知的模型。 (2) 哪个子域是核心（深入建模）与通用（购买或使用 OSS——认证、电子邮件、支付）。

**产出物：** 扩展 docs/ARCHITECTURE.md：`## 边界上下文 & 上下文映射`（上下文、关系、反腐败层）和 `## 领域词汇（通用语言）`（术语 | 含义 | 代码名称）；记录聚合和核心领域选择在 `## 决策日志`。更新追踪器。

**完成时：** 上下文映射了它们的关系，词汇命名了核心术语，每个聚合都声明了它的不变性和通过 ID 引用，核心子域被选择，上下文边界与阶段 1 层级图对齐。

### 阶段 3 — 诚实地调整系统大小（system-design）

**目的：** 用数字证明系统可以有多小，以便跳过你无法证明需要机械。

**简要（回退）：** 从需求开始，而不是解决方案。草稿估算：QPS = 日活跃用户 × 每天操作 ÷ 86,400，峰值 2-5× 平均；存储 = 记录/天 × 大小 × 保留期。对于数百到数千用户，单个索引数据库加上读取路径缓存可以带很长时间。按顺序扩展：首先垂直，然后缓存旁路（TTL + 显式失效），然后读取副本，最后分片，只有有证据。为慢/尖峰工作解耦使用消息队列，为全球静态资源使用 CDN。过早分片和过早服务分割是命名错误。

**调用：** 使用 `system-design` 技能，用输入中的负载现实。要求平均和峰值 QPS，年度存储，哪个组件首先瓶颈，以及一个不需要的列表技术（分片、副本、CDN、队列、多区域）。

**与用户共同决策：** 哪些扩展动作现在要做与推迟——与数字绑定（不要为 50k 用户构建 50），如果有任何慢速工作要移到消息队列后面。

**产出物：** 扩展 docs/ARCHITECTURE.md `## 系统上下文` 与负载现实和草稿估算数字；记录每个扩展动作（现在采用 / 推迟触发器）在 `## 决策日志`。更新追踪器。

**完成时：** 平均/峰值 QPS 和年度存储被写下来，第一个瓶颈被命名，并且每个扩展技术要么有理由采用，要么有触发器推迟。

### 阶段 4 — 做出明确的数据决策（ddia-systems）

**目的：** 获得比代码更长的层——数据模型、存储引擎和一致性由访问模式选择，而不是习惯。

**简要（回退）：** 数据比代码更持久。根据访问模式匹配模型——关系型用于多对多和即席查询，文档用于自包含聚合和局部性，图用于递归遍历；存储引擎在读取和写入之间权衡（LSM 写吞吐量与 B-tree 读取延迟）。大多数数据库默认为读已提交或快照，而不是序列化——简单的读后写触发写偏差（两个买家抢最后一个单位）。显式锁定（`SELECT ... FOR UPDATE`）或使用序列化事务，在不变性要求下。单领导者 + 读取副本是读取密集型默认值；复制延迟迫使明确的读取你的写。

**调用：** 使用 `ddia-systems` 技能，用阶段 2 聚合暗示的工作负载和阶段 3 副本计划。要求每个工作负载的模型 + 存储引擎匹配，实际默认隔离级别及其异常，以及哪些读取后写路径需要锁定。

**与用户共同决策：** (1) 一个数据存储与多态持久化，按工作负载匹配。 (2) 哪些路径获得锁定或序列化事务，而不是容忍最终一致性；是否第二个读取模式（搜索、分析）证明派生数据通过 CDC 与之同步。

**产出物：** 扩展 docs/ARCHITECTURE.md `## 数据 & 存储决策`（模型、引擎、隔离级别、锁定路径、系统记录与派生数据）并记录推理在 `## 决策日志`。更新追踪器。

**完成时：** 每个工作负载都有根据匹配的模型 + 引擎，默认隔离级别被记录，每个写偏差易感路径都被锁定或序列化，任何派生数据都有定义的同步机制。

### 阶段 5 — 保持模块深度（software-design-philosophy）

**目的：** 停止结构成为自己的疾病——在简单接口后面隐藏机械，而不是分裂成浅层类。

**简要（回退）：** 复杂性是敌人；每个决策的测试是它是否使整个系统更简单。模块深度 = 功能 ÷ 接口复杂性——深度模块在小的接口后面隐藏力量；浅层模块（类病）在不隐藏复杂性的情况下增加接口成本。干净分层和深度模块是盟友；干净分层和类病不是。信息泄漏——一个设计决策反映在许多模块中——是顶级红灯；封装每个知识片段一次。战略优先于战术：投资 10-20% 来保持设计干净；创业捷径随着团队增长而累积债务。

**调用：** 使用 `software-design-philosophy` 技能，用阶段 1-2 提出的模块集。询问哪些模块是浅层传递的，在哪里知识跨越边界，以及是否有任何计划边界是仪式而不是深度。

**与用户共同决策：** 哪些浅层模块要合并成更深的模块现在，防止过度合并真正无关的关心；团队采用的设计约定（命名、行为在哪里、每个文件一个知识片段）。

**产出物：** 扩展 docs/TECH-DEBT.md `## 嗅觉清单`（浅层模块 / 信息泄漏条目，应用了合并）并记录团队同意的规则在 `## 采用的约定`。更新追踪器。

**完成时：** 每个浅层模块集群被合并或记录有修复，没有单个设计决策在模块中重复，并且设计约定被写下来。

### 阶段 6 — 设计失败（release-it）

**目的：** 使系统在依赖项缓慢或宕机时优雅降级，而不是崩溃——现在设计最便宜，不是在凌晨 2 点。

**简要（回退）：** 通过 QA 的软件不是能在生产中生存的软件。集成点是第一杀手，缓慢响应比没有更糟——悬挂依赖项耗尽线程和池，而没有任何日志。非谈判：每个出站调用连接 + 读取超时；关键一个的断路器（跳转开，快速失败，半开恢复）；隔离每个依赖项的池的舱壁；带退避 + 振动的重试。每个列表端点分页（无界结果集在真实数据下崩溃）；安排稳态清理。用功能标志和向后兼容的扩展-收缩迁移将部署与发布解耦。

**调用：** 使用 `release-it` 技能，用输入中的出站依赖项。要求每个依赖项的超时值和断路器阈值，舱壁位置，每个集成点的优雅降级路径，以及深度健康检查 + RED 指标 + 扩展-收缩迁移 + 可信赖的回滚。

**与用户共同决策：** 断路器阈值，哪些依赖项获得专用池，当非关键依赖项宕机时核心流程如何降级，以及你信任的回滚路径。抵制混沌工程 / 多区域故障转移，对于第一个千名用户。

**产出物：** 创建 docs/RELIABILITY.md，包含 `## 集成点审计`（依赖项 | 超时 | 断路器 | 舱壁 | 重试策略 | 状态）、`## 查询 & 资源发现`、`## 健康检查 & 指标`，以及 `## 部署 vs 发布`。更新追踪器。

**完成时：** 每个计划出站调用都有一个超时，关键依赖项有断路器和舱壁，每个列表端点都被分页，深度健康检查 + RED 指标 + 扩展-收缩迁移 + 可信赖的回滚被指定，审计没有对关键路径的开放行。

### 阶段 7 — 证明接线并锁定习惯（pragmatic-programmer）

**目的：** 构建一个通过每个层薄的真正切片，以证明边界连接，并设置保持架构可逆转的习惯。

**简要（回退）：** 追踪子弹——构建一个薄但完全真实的垂直切片（HTTP → 用例 → 仓库 → DB → 回），作为生产代码保留，以便第二天进行端到端反馈，并在充实它们之前证明边界链接。可逆转性：在你们自己的接口后面抽象每个供应商（开源道路测试——你能在一周内交换数据库或 LLM 提供商吗？）。正交性：对单个需求的一个戏剧性改变只影响一个模块。知识 DRY，而不是巧合——合并重复的规则，让看起来像的单独保留。破损窗户：修复第一个黑客或用跟踪票板将其封存。

**调用：** 使用 `pragmatic-programmer` 技能，用阶段 1 边界。询问最薄的端到端追踪子弹，每个供应商的适配器接口，以及一个审计，在哪里一个改变会触及许多模块，或者供应商 API 会泄漏到业务逻辑中。

**与用户共同决策：** 哪个切片是追踪子弹（一个经过认证的核心操作，最小功能）；破损窗户政策和每个迭代的债务预算；哪些供应商首先获得拥有的接口。

**产出物：** 扩展 docs/TESTING.md `## 测试策略`，`## 安全网映射`（追踪子弹路径作为第一个端到端测试），和 `## CI 门禁`; 扩展 docs/TECH-DEBT.md `## 债务预算 & 破损窗户政策` 和 `## 采用的约定`（可逆转性、正交性）。更新追踪器。

**完成时：** 追踪子弹切片通过每个层端到端运行，并被固定为第一个 CI 门禁，每个供应商都坐拥一个拥有的接口，破损窗户政策和债务预算被写下来。

### 阶段 8 — 切割范围到本质（37signals-way）

**目的：** 决定是否任何东西都会发货——固定时间，灵活范围，并在它成为你携带的复杂性之前删除推测性抽象。

**简要（回退）：** 建设更少——最好的产品做更少的事情做得好；半成品胜过敷衍了事的产品。固定一个食欲（这项工作真正值得的时间）并削减范围以适应，而不是估算一个无限制的架构，它会膨胀。YAGNI：每个推测性抽象（通用插件系统、事件源、为零用户配置的多租户）都是推迟到想象中的未来的决策，代价是当前的复杂性。做出微小的可逆转决策；默认说不，以便伟大的决策可以呼吸。永远不要削减难以逆转的小决策集。

**调用：** 使用 `37signals-way` 技能，用阶段 1-7 的完整架构计划。要求它将工作塑造成固定的食欲，将本质与发布分离，命名兔子洞，并列出要删除或用最简单的东西替换的推测性抽象。

**与用户共同决策：** v1 架构工作的食欲；要删除、推迟到重新审视触发器或替换为最简单的东西的抽象；确认没有难以逆转的决策被削减只是为了节省时间。

**产出物：** 扩展 docs/ARCHITECTURE.md `## 决策日志` 什么被故意不构建为 v1；扩展 docs/TECH-DEBT.md `## 债务账本`（推迟的抽象作为故意采取的债务，每个都有重新审视它的触发器）。更新追踪器。

**完成时：** v1 范围固定为食欲，每个切割或推迟的抽象都是决策日志或债务账本行，带有重新审视触发器，并且没有难以逆转的决策因时间而削减。
