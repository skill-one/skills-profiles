# 软件设计框架哲学

一个用于管理软件工程基本挑战——复杂性的实用框架。在设计模块、审查 API、重构代码或提供架构决策建议时，请应用这些原则。

## 核心原则

**编写软件的最大限制是我们理解正在创建的系统的能力。** 复杂性是敌人：它使系统难以理解、难以修改，并是错误的来源。通过问“这会增加还是减少系统的整体复杂性？”来评估每个设计决策——目标不是零复杂性，而是最小化不必要的复杂性，并将必要的复杂性集中在可以管理的地方。

## 评分

**目标：10/10。** 在审查或创建设计时，通过计算它满足的八个快速诊断行的数量（≈1.25分每个），然后检查范围：

- **9-10** — 深度模块，接口远比实现简单；没有信息泄漏（实现可以更改而不影响调用者）；接口注释捕获设计意图；常规设计改进。所有八个诊断通过。
- **6-8** — 大部分深度，但有一个或两个泄漏、浅类或未记录的抽象。5-6个诊断通过。
- **3-5** — 类itis或时间分解，反复泄漏，注释仅重述代码。2-4个诊断通过。
- **≤2** — 战术龙卷风代码：浅模块、普遍泄漏、未记录设计意图。0-1个诊断通过。

始终说明当前分数、失败的诊断行以及每个诊断需要哪些具体更改才能达到10/10。

## 软件设计框架

管理复杂性和生成易于理解和修改的系统的六个原则：

### 1. 复杂性及其原因

**核心概念：** 复杂性是系统结构中任何使其难以理解和修改的内容。它表现出三种症状——变更放大、认知负荷和未知未知——并具有两个原因：依赖关系和晦涩。

**关键洞察：**
- 变更放大：一个简单变更需要在许多地方进行修改
- 认知负荷：开发人员必须记住太多内容才能进行变更
- 未知未知：不明显必须更改的内容或相关信息——最严重的症状
- 复杂性是累积的——它从数百个小的决策中累积起来（“千刀万剐”），因此每个决策都很重要

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 变更放大 | 集中共享知识 | 提取颜色常量，而不是在20个文件中硬编码`#ff0000` |
| 认知负荷 | 减少开发人员必须知道的内容 | `open(path)`而不是要求缓冲区大小、编码、锁定模式 |
| 未知未知 | 使依赖关系明确 | 类型系统和接口揭示受变更影响的内容 |
| 晦涩 | 精确命名 | `numBytesReceived`而不是`n`；`retryDelayMs`而不是`delay` |

当你需要命名代码库具有*哪种*症状并在修复之前查看它时，请参阅[参考资料/complexity-symptoms.md](references/complexity-symptoms.md)——按症状识别测试、依赖关系分类（句法/语义/时间/隐藏）、成本公式C = Σ(cp·tp)以及10行红旗表。

### 2. 深度与浅度模块

**核心概念：** 最好的模块是深度模块：简单接口背后的强大功能。浅模块的接口相对于它们提供的功能很复杂——它们增加了复杂性而不是隐藏它。

**为什么有效：** 接口是模块对系统其余部分的*成本*；实现是收益。因此，一个比重新实现自己更难学习的更难的方法是净负的——深度，而不是行数，决定了模块是否值得其位置。

**关键洞察：**
- 深度 = 提供的功能 / 附加的接口复杂性（Unix文件I/O是深度的；薄的Java I/O包装器是浅度的）
- “类itis”：创建太多小、浅类——每个接口增加认知负荷
- 小方法不一定好；深度比大小更重要
- 最好的抽象隐藏了大量的复杂性在少数几个简单概念后面

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 深度模块 | 在简单API后面隐藏复杂性 | `file.read(path)`隐藏磁盘块、缓存、缓冲、编码 |
| 类itis治疗 | 合并相关的浅类 | `RequestParser` + `RequestValidator` + `RequestProcessor` → 一个`RequestHandler` |
| 接口简单性 | 更少的参数，更少的方法 | `config.get(key)`具有合理的默认值，而不是15个构造函数参数 |

当你判断抽象是否有效时，请参阅[参考资料/deep-modules.md](references/deep-modules.md)——深度比率的前后代码、类itis治疗结果和案例研究（Unix I/O、GC、TCP/IP）。

### 3. 信息隐藏和泄漏

**核心概念：** 每个模块都应该封装其他模块不需要的知识。信息泄漏——一个设计决策在多个模块中反映——是软件设计中最重要的红旗之一。

**为什么有效：** 一个位于一个模块中的决策可以在那里更改而不会在别处；同一个泄漏到N个模块的决策将一个编辑变成N个编辑，编译器不会提醒你进行这些编辑。隐藏是将变更放大转换回局部变更。

**关键洞察：**
- 时间分解导致泄漏：按*何时*发生的事情拆分代码会强制跨阶段共享知识——按知识组织而不是时间
- 通过数据格式、协议或共享假设的后门泄漏是最微妙的形式
- 装饰器经常泄漏——它们暴露了装饰的接口
- 如果两个模块共享知识，则合并它们或创建一个封装它的新模块

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 格式泄漏 | 集中序列化 | 一个模块拥有JSON编码/解码，而不是`json.dumps`到处 |
| 时间分解 | 按知识组织，而不是时间 | 将“读取配置”和“应用配置”合并为一个配置模块 |
| 协议泄漏 | 抽象传输细节 | `MessageBus.send(event)`隐藏HTTP与gRPC与队列 |

当你需要编辑两个模块时，请参阅[参考资料/information-hiding.md](references/information-hiding.md)——四种泄漏形式与代码（接口、后门、时间、装饰器）、五种减少策略、HTTP处理案例研究以及检测表。

### 4. 通用模块与专用模块

**核心概念：** 设计“有点通用”的模块：接口足够通用以支持多种用途，实现可以处理当前需求。问：“最简单的接口可以覆盖我所有当前需求是什么？”

**为什么有效：** 反直觉地，通用接口通常*更简单*——特殊案例方法随着需求增长而增加，而一个通用方法吸收它们。陷阱是另一个方向：当前需求不需要的通用性是投机复杂性，现在支付了可能永远不会到来的用例的费用。

**关键洞察：**
- “有点通用”是在过于具体和过于通用之间的甜点
- 向下推动复杂性：低级模块应处理硬案例，以便高级模块保持简单
- 配置参数通常代表未能做出决定——每个参数是将复杂性推给调用者的决策
- 不确定时，首先实现更简单、更通用的方法

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| API通用性 | 为概念设计，而不是一个用例 | `text.insert(position, string)`而不是`text.addBulletPoint()` |
| 减少配置 | 自动确定行为 | 自动检测文件编码，而不是`encoding`参数 |
| 避免过度专门化 | 一个通用方法而不是许多特定方法 | `store(key, value, options)`而不是`storeUser()`、`storeProduct()`、`storeOrder()` |

当你选择接口应该有多通用时，请参阅[参考资料/general-vs-special.md](references/general-vs-special.md)——“所有当前需求的简单接口”测试、配置参数反模式以及向下推动复杂性如何解决。

### 5. 注释作为设计文档

**核心概念：** 注释应该描述代码中不明显的内容：设计意图、抽象理由、不变量和假设。“好代码是自文档化的”对于任何超出低级实现细节的内容都是神话。

**为什么有效：** 代码只能记录*它做什么*——永远不会为什么选择这种方法而不是其他方法，或者它无声地假设的内容。这种推理是系统中最易失的信息：它只存在于作者的大脑中，一旦他们离开就会消失，因此注释是唯一的机会来捕捉它。

**关键洞察：**
- 四种类型：接口注释（最重要——它们定义了抽象）、数据结构成员注释、实现注释、跨模块注释
- 先写注释（注释驱动设计）以在编写代码之前理清思路
- 不要重复代码已经清楚的内容；将注释保持在它们描述的代码旁边并一起更新
- 如果很难写注释，设计可能太复杂了

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 接口注释 | 描述抽象，而不是实现 | “返回最接近位置的部件，如果没有在阈值内则为null” |
| 数据结构注释 | 解释不变量 | “列表按优先级降序排序；平局按插入顺序打破” |
| 实现注释 | 解释原因，而不是什么 | "// 二分搜索：列表始终排序，可以容纳100k+项” |
| 跨模块注释 | 链接相关决策 | "// 此超时必须与RetryPolicy.java中的重试间隔匹配" |

当你编写或审查注释并不确定哪些内容属于其中之一时，请参阅[参考资料/comments-as-design.md](references/comments-as-design.md)——四种注释类型与示例、注释驱动设计程序以及自文档化代码神话的反驳。

### 6. 战略编程与战术编程

**核心概念：** 战术编程快速使功能工作并随着每个捷径累积复杂性。战略编程在良好设计上投资10-20%的额外精力，将每个变更视为改进结构的机遇。

**为什么有效：** 战术速度是借来的：每个捷径都使未来的变更更难，而战略投资会复合——战略设计的系统在几个月内使用起来更快。

**关键洞察：**
- 战术龙卷风：一个快速交付但留下废墟的开发人员——短期内受到称赞，长期内具有破坏性
- 你的主要工作是一个好设计，它恰好能工作，而不是一个恰好有设计的代码
- 初创公司最需要战略编程——早期捷径随着团队的增长会累积成压倒性的债务
- 每个变更都是一个投资机会：让代码稍微更好；重构是每个功能的一部分，而不是一个特殊事件

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 战术陷阱 | 抵制快速且肮脏的修复 | 不要为“只是这个特殊情况”添加一个布尔参数 |
| 战略投资 | 在添加功能期间改进结构 | 在添加功能时重构一个尴尬的模块接口 |
| 设计审查 | 评估结构，而不仅仅是正确性 | 问“这使系统更简单了吗？”而不是“它工作了吗？” |

当你决定变更值得多少设计努力，或为其辩护时，请参阅[参考资料/strategic-programming.md](references/strategic-programming.md)——10-20%的投资数学、战术龙卷风模式以及为什么初创公司最需要战略编程。

## 常见错误

| 错误 | 为什么失败 | 修复 |
|------|-----------|------|
| **创建太多小类** | 类itis增加了接口而没有深度；每个边界是认知负担 | 合并相关的浅类到更深的模块 |
| **按时间顺序拆分模块** | “读取，然后处理，然后写入”强制跨模块共享知识 | 将共享知识的代码组合到一个模块中 |
| **在接口中暴露实现** | 调用者依赖于内部；变更传播 | 围绕抽象设计接口；隐藏格式和协议 |
| **将注释视为可选** | 设计意图和假设丢失；新人猜测错误 | 先写接口注释；与代码一起维护 |
| **所有东西都用配置参数** | 推给调用者的参数是你没有做出的决策（见§4） | 自动确定行为；提供合理的默认值 |
| **快速且肮脏的战术修复** | 快捷方式累积直到系统无法工作 | 投资10-20%的额外精力；将每个变更视为设计机会 |
| **传递方法** | 只将参数转发到另一个方法的方法增加了接口但没有功能 | 将传递方法合并到调用者或被调用者 |
| **为特定用例设计** | 专用接口累积特殊案例 | 问：最简单的接口覆盖所有当前需求？ |

## 快速诊断

| 问题 | 如果没有 | 动作 |
|------|--------|------|
| 你能用一句话描述每个模块吗？ | 模块做太多或缺乏目的 | 分割成连贯、可描述的责任 |
| 接口比实现简单吗？ | 模块是浅的——复杂性向外泄漏 | 隐藏更多；将浅类合并到更深的模块中 |
| 你可以在不影响调用者的情况下更改实现吗？ | 信息跨边界泄漏 | 在一个模块中封装泄漏的知识 |
| 接口注释描述抽象吗？ | 设计意图丢失；模块将被误用 | 记录模块承诺的内容，而不是它如何工作 |
| 设计讨论是否是代码审查的一部分？ | 审查捕获错误但不是复杂性增长 | 将“这会减少复杂性吗？”添加到审查标准中 |
| 每个模块是否隐藏了一个重要的设计决策？ | 模块围绕代码组织，而不是信息 | 重新组织，使每个模块拥有特定知识 |
| 新手能否在不阅读实现的情况下理解模块边界？ | 抽象未记录或泄漏 | 改进接口注释；简化接口 |
| 你是否在10-20%的时间内进行设计改进？ | 债务随着每个功能累积 | 将设计改进包含在每次PR中 |
