# 提升代码质量

将一个可用但未经测试的快速原型转变为可以发布和运营的产品。这是一个包含九个阶段的交互式、可中断的旅程：代理在做出每个决策前都会询问，并将结果记录在您的项目的 `docs/` 文件夹中，因此您可以在任何阶段停止并稍后继续。一周前的原型已经是遗留代码——因此第一步是一个安全网，之后的每个阶段都因为有了这个安全网而可以进行验证。

## 核心原则

**一周未经过测试的原型已经是遗留代码：从战术转向战略——首先设置安全网，然后依次进行可读性、结构和生产环境加固。** 这项技能按顺序排列阶段，提出决策问题，并将每个选择记录在 `docs/` 中。组成技能承载着方法——调用它们而不是临时构建它们的框架。跳过步骤（在测试前重构，在确定规模前扩展）正是这种排序存在的目的，以防止这种失败模式。

## 运营规则

1. **首先恢复。** 在做任何事之前，阅读 `docs/IMPROVE-CODE-QUALITY-PLAN.md` 和旅程地图中的每个产出物。如果存在跟踪器，请用3-5行总结旅程状态并询问要进入哪个阶段。当用户确认了入口点时完成。带有跟踪器的旅程是恢复的，而不是重新开始的。
2. **仅在第一次运行时进行摄入。** 没有跟踪器：运行下面的摄入，然后创建 `docs/IMPROVE-CODE-QUALITY-PLAN.md`，将每个阶段的状态标记为 `pending | in-progress | awaiting-evidence | done | deferred: reason | skipped: reason`。当跟踪器存在并且用户确认了阶段计划时完成。
3. **阶段入口。** 宣布：阶段的作用、它强制的决策、它产生的产出物、粗略的工作量。提供继续 / 跳过 / 推迟——标记为 GATE 的阶段可以推迟，但不能跳过。在继续时将阶段标记为 `in-progress`。当用户做出选择时完成。
4. **技能调用和回退。** 加载阶段的技能并使用它：每个阶段的调用行通过slug命名技能——使用该技能来运行阶段。如果不可用，提供：`npx skills add wondelai/skills/<slug> --global`。如果用户拒绝，从它的简要说明中运行阶段——这是最小的可行方法。说明你处于什么模式。
5. **阶段内的决策。** 询问“与用户一起决策”下的每个问题——提供具体的选项和你的建议。将选择记录在跟踪器的关键决策中。无声做出的决策是缺陷。
6. **阶段退出。** 在写入之前，展示草稿产出物内容以供批准。在批准后：写入或扩展 `docs/` 文件，更新跟踪器（状态、关键决策、下一步行动）。当文件写入并且阶段行显示 `done` 时完成。
7. **产出物纪律。** 写之前先阅读；如果文件不存在则创建，否则扩展——添加或更新你的部分，保留其他人的部分。文件在 `docs/` 中是大写的。每个建议都作为一个复选框或带有所有者和优先级的表格行出现。在第一次创建 `docs/` 文件时查看 [references/artifact-templates.md](references/artifact-templates.md)——从完整骨架（所有部分标题）创建它，然后填写你的阶段命名的部分。
8. **阶段1是一个门控；提交保持单一目的。** 没有阶段会触及安全网地图中未包含的代码——首先固定它（不存在意味着未列在Pinned behaviors下；Gaps列中的条目也是禁止的）。结构和行为更改永远不会共享一个提交：在只有结构的提交中用测试为绿色进行重构，然后在它自己的提交中更改行为。在重构过程中变红的测试意味着回退并重试更小的步骤，而不是调试。安全网测试添加和 `docs/` 更新是它们自己的单一目的提交。

## 摄入

在创建跟踪器之前询问这些问题：

1. 应用程序做什么，如果它崩溃了最坏的情况是什么？（定义风险并设置阶段优先级）
2. 你接下来要更改哪个模块，哪个的变更率最高（`git log`）或属于核心领域？（选择阶段1开始的模块——三维轴启发式）
3. 今天是否存在任何自动化测试，并且测试命令运行为绿色？（范围阶段1的安全网）
4. 堆栈是什么——框架、ORM、数据库？（门控阶段5和9——边界和数据决策）
5. 这是否在生产中带有真实用户数据，以及大致有多少活跃用户或请求？（门控阶段7-9——弹性是需求驱动的）
6. 它调用哪些外部依赖——第三方API、支付、电子邮件、队列？（门控阶段7——集成点审计）
7. 你想要旅程中的多少——在真实用户之前进行阶段1-3；在发布之前进行阶段7；阶段8-9跟踪实际增长）

阶段跳过启发式：当真实负载远低于任何扩展阈值时跳过阶段8-9（从需求开始，而不是解决方案——在50个用户时不要为50个用户构建）。一旦有真实用户存在，阶段7不是可选的——即使流量很低，超时和断路器也是基本要求（它可能保持 `deferred: reason`，永远不会 `skipped`）。永远不要跳过阶段1；它是门控。然后根据模板创建跟踪器并确认计划。

当 `docs/IMPROVE-CODE-QUALITY-PLAN.md` 存在并且每个阶段都标记了状态，并且用户确认了计划时完成。

## 阶段

阶段按列表顺序运行——每个阶段都假设前一个阶段的产出物存在。根据运营规则，任何阶段都可以进入、跳过或推迟，但阶段1是所有阶段的门控：下游不能触及未固定的代码。

### 阶段1 — 建立安全网（与遗留代码一起工作）— GATE

**目的：** 在变更点固定当前行为，以便每个后续阶段都可以验证。没有阶段可以触及安全网地图中未包含的代码。

**简要（回退）：** 遗留代码是没有测试的代码，因此一周前的原型符合条件。覆盖和修改，而不是编辑和祈祷：识别变更点，用最侵入性的接缝打破内联依赖（用生产默认值参数化构造函数；提取和覆盖一个隐藏的调用），然后编写特征化测试来拍摄实际行为——断言一些错误，读取失败，固定真实值。当在有限时间内无法实现完整覆盖时，对新代码进行Sprout/Wrap，并将未测试的主机跟踪为债务。

**调用：** 使用 `working-with-legacy-code` 技能，并在摄入时选择的起始模块。请求入口方法的效应草图、接缝和固定当前注册/计费/核心行为的最小特征化测试集。

**与用户一起决策：** (1) 通过三维轴启发式确认起始模块——接下来要更改的、高变更率的、核心领域的。 (2) 在特征化过程中发现的错误：固定错误行为并将其记录在债务登记册中，永远不要无声地修复——调用者可能依赖于这种怪癖。确认用户接受这一点。

**产出物：** 创建 docs/TESTING.md，包含 `## 测试策略`、`## 安全网地图`（模块 | 固定的行为 | 测试文件 | 间隙），以及 `## 特征化待办事项列表`；创建 docs/TECH-DEBT.md，包含 `## 债务登记册`（项目 | 位置 | 类型 | 风险 | 工作量 | 优先级 | 状态）和 `## Sprout / Wrap 注册表`。更新跟踪器。

**完成时：** 目标模块的行为被固定，套件运行为绿色，两个文件都存在，并且阶段1显示 `done`——只有到那时，后续阶段才会解锁。

### 阶段2 — 使代码可读（清晰的代码）

**目的：** 优化以供阅读——命名、小型的单一目的函数、安全的错误处理——现在更改是可验证的。

**简要（回退）：** 代码的阅读远多于编写。命名揭示了意图（`elapsedTimeInDays`，而不是 `d`）；布尔值作为谓词读取；函数在一个抽象级别上做一件事，带有0-2个参数（标志参数是两个函数）。命令查询分离：更改状态或返回值，永远不要两者都做。错误处理：优先使用异常而不是返回代码，捕获特定类型，永远不要返回或传递空值（使用空集合、Optional或空对象），并将操作+状态上下文放在每个抛出的错误中。

**调用：** 使用 `clean-code` 技能，并针对目标模块。请求跨越六个学科的0-10评分，以及按优先级排序的前十个修复，以及错误处理审计（裸捕获、空值返回、无上下文的错误）。

**与用户一起决策：** 应用哪些修复现在进行，哪些记录为债务，团队采用的命名/错误处理约定，以及是否将清晰的代码评分作为CI门控。

**产出物：** 扩展 docs/TECH-DEBT.md：为每个命名/函数/错误异味添加行到 `## 异味清单`（异味 | 位置 | 重构 | 状态），并记录商定的规则在 `## 采纳的约定` 下。更新跟踪器。

**完成时：** 模块评分8+，或者每个低于8的间隙都是一个带有修复的异味清单行，约定被记录，并且阶段1的测试仍然通过。

### 阶段3 — 应用命名的重构（重构模式）

**目的：** 将“清理它”转换为命名、行为保持的转换，并在小步骤中执行。

**简要（回退）：** 每个异味都对应一个命名的重构。提取方法是主力——如果你会写一个注释来解释一个块，提取它并以注释命名。还替换魔法数字为符号常量，替换嵌套条件为保护子句，替换条件为多态，引入参数对象。工作流程：测试为绿色，一个转换，测试为绿色，提交；变红的测试意味着回退，而不是调试。准备性重构（使更改变得容易，然后使容易的更改）和三条规则防止过早抽象。

**调用：** 使用 `refactoring-patterns` 技能，并针对有异味的函数和阶段1的测试。请求它为每个异味命名，引用转换，并一次应用一个，每次应用后运行测试。

**与用户一起决策：** 范围——这一轮要解决哪些异味，是否即将到来的功能值得在插入点首先进行准备性重构，以及重构的模块是否加入 TESTING.md 中的CI门控列表。

**产出物：** 扩展 docs/TECH-DEBT.md `## 异味清单`：对于每个异味，记录应用的命名重构及其状态。更新跟踪器。

**完成时：** 目标异味显示命名的重构和 `done` / `ticketed` 状态，测试为绿色，结构更改以只有结构的提交 landed。

### 阶段4 — 用深层模块减少复杂性（软件设计哲学）

**目的：** 战斗无监督代理创建的类itis——在简单的接口后面隐藏真实机制，而不是增加浅层类。

**简要（回退）：** 复杂性是敌人；最小化模块对整个系统施加的影响。模块深度 = 功能 ÷ 接口复杂性；深层模块在小型接口后面隐藏机制，浅层模块则不（类itis）。合并总是一起出现并共享状态的浅层类。注意信息泄漏（一个决策在多个模块中反映）和时间分解（按执行顺序组织，而不是按知识）。这是战术→战略的转换：投资10-20%来保持设计清洁。

**调用：** 使用 `software-design-philosophy` 技能，并针对到目前为止触摸的模块集。询问哪些类是浅层的，在哪里信息跨边界泄漏，以及如何合并成具有更简单接口的深层模块。

**与用户一起决策：** 哪些合并现在进行，而不是推迟，防止合并不相关的关注点。

**产出物：** 扩展 docs/TECH-DEBT.md `## 异味清单`，添加类itis / 浅层模块 / 信息泄漏条目，以及应用的合并。更新跟踪器。

**完成时：** 每个浅层模块集群都被合并或记录为有修复，接口数量没有为了“模块化”而增加，并且测试为绿色。

### 阶段5 — 绘制架构边界（清晰的架构）

**目的：** 使框架和数据库依赖于业务规则，而不是相反。

**简要（回退）：** 依赖规则：源依赖指向内部——实体，然后用例，然后接口适配器，然后框架/驱动；内部不命名任何外部。数据库和Web是细节，是您规则的插件。通过依赖反转强制执行：用例拥有存储库接口；Postgres/Stripe实现存在于外部的适配器中。SOLID是中级工具。共享一个数据模型的微服务是一个分布式单体——首先在服务内部应用该规则。

**调用：** 使用 `clean-architecture` 技能，并针对当前的模块映射和摄入的堆栈。请求它映射依赖图，列出业务逻辑导入ORM或框架的每个违规行为，并显示提取到无框架的用例背后的拥有接口。

**与用户一起决策：** 推边界这一轮有多远，哪些供应商（支付、存储）首先在拥有的接口后面进行包装，以及是否任何计划的服务拆分要等到服务内边界保持（避免分布式单体）。

**产出物：** 扩展 docs/ARCHITECTURE.md：记录层和当前违规行为在 `## 层映射 & 依赖规则`（违规 | 位置 | 修复 | 状态），以及边界选择在 `## 决策日志` 下。更新跟踪器。

**完成时：** 每个依赖规则违规行为都是一个带有修复的跟踪行，至少最高风险的供应商被包装，业务规则测试在没有数据库或框架的情况下运行，并且测试为绿色。

### 阶段6 — 锁定习惯（实用主义程序员）

**目的：** 设置保持代码库在这次旅程结束后可变的元原则。

**简要（回退）：** DRY是关于知识，而不是文本——在两个地方重复相同的规则（客户端和服务器上的验证），留下偶然相似的东西。正交性：更改一个组件不应该影响另一个组件。破损窗户理论：立即修复黑客或用跟踪的票证将其围起来——永远不要未跟踪的 `// TODO`。可逆性：将第三方供应商包装在您自己的接口后面。子弹列车：将下一个功能作为一个非常薄的端到端切片构建，而不是逐层构建。

**调用：** 使用 `pragmatic-programmer` 技能，跨整个代码库。请求它标记重复的知识（忽略偶然的重复）以及任何需要用跟踪票证围起来的破损窗户或未跟踪的TODO。

**与用户一起决策：** 每次迭代的债务预算和破损窗户政策——什么现在修复，什么记录为债务。

**产出物：** 扩展 docs/TECH-DEBT.md：记录重复知识和破损窗户项目在 `## 债务登记册` 中，以及商定的政策在 `## 债务预算 & 破损窗户政策` 和 `## 采纳的约定` 下。更新跟踪器。

**完成时：** 重复知识命中被登记或修复，没有未跟踪的黑客，并且债务预算政策被写下来。

### 阶段7 — 使其能够生存生产（发布它）

**目的：** 使每个集成点硬化，以便慢速或失败的依赖项可以优雅地降级，而不是导致整个应用程序崩溃。

**简要（回退）：** 通过QA通过软件不是在生产的软件。集成点是第一杀手——慢速响应比没有更糟。不可协商的：每个出站调用都有连接+读取超时；在失败依赖项上有一个断路器（打开时跳转，快速失败，半开恢复）；隔离资源池的舱壁；指数退避+抖动重试；稳态清理累积的杂项。使用功能标志和扩展收缩迁移将部署与发布解耦。添加深度健康检查、RED指标、基于症状的警报。

**调用：** 使用 `release-it` 技能，并针对摄入的外部依赖项。请求对没有超时的调用进行审计，断路器+舱壁放置，以及深度健康检查+RED指标+警报设计的审计。

**与用户一起决策：** 断路器阈值，哪些依赖项获得专用池，以及警报症状和阈值（错误率、延迟）。

**产出物：** 创建 docs/RELIABILITY.md，包含 `## 集成点审计`（依赖项 | 超时 | 断路器 | 舱壁 | 重试策略 | 状态），`## 健康检查 & 指标`，以及 `## 部署 vs 发布`。更新跟踪器。

**完成时：** 每个出站调用都有超时，关键依赖项有断路器和舱壁，深度健康检查+RED指标+基于症状的警报存在，稳态清理被安排用于累积的杂项，可以无重新部署地回滚发布，并且审计表没有对关键路径的开放行。

### 阶段8 — 按实际负载进行规模（系统设计）

**目的：** 从需求和国家进行有意扩展，而不是被动反应——只有在估计证明它合理时才添加机制。

**简要（回退）：** 从需求开始，而不是解决方案。粗略估算：QPS = 每日活跃用户 × 每天操作 ÷ 86,400，峰值2-5倍平均；存储 = 记录/天 × 大小 × 保留期。按顺序扩展：首先垂直，然后缓存（带TTL和显式失效的缓存旁路）用于读重路径，然后是读副本，最后才分片。使用消息队列将慢速工作与请求路径解耦。寻求已知设计（速率限制器→令牌桶返回 `429 Retry-After`）。

**调用：** 使用 `system-design` 技能，并针对摄入的负载现实。请求平均和峰值QPS，年度存储，哪个组件首先出现瓶颈，以及按优先级排序的缓存/队列/副本移动列表，不要过度设计。

**与用户一起决策：** 哪些扩展步骤现在进行，而不是推迟，与实际数字挂钩（在50个用户时不要在50个用户时构建），以及命名第一个慢速工作要移动到消息队列后的名称，如果有。

**产出物：** 扩展 docs/ARCHITECTURE.md `## 系统上下文`，包含负载现实和粗略估算数字；扩展 docs/RELIABILITY.md `## 查询 & 资源发现`，包含无界查询和瓶颈。更新跟踪器。

**完成时：** QPS和存储数字被记录，第一个瓶颈被命名，每个扩展步骤要么应用，要么推迟，并写下触发数字。

### 阶段9 — 使数据层正确（DDIA系统）

**目的：** 保护数据，使其比代码更持久——并发下的正确性，以及数据存储选择由需求决定，而不是习惯。

**简要（回退）：** 数据比代码更持久。大多数数据库默认为可读已提交或快照，而不是序列化——简单的读后写会触发写偏差（两个请求都卖掉了最后一个项目）。明确使用 `SELECT ... FOR UPDATE` 或序列化事务修复它；了解您的实际默认值。复制延迟意味着读您的写和单调读必须是故意的，一旦副本存在。匹配数据模型与访问模式；多语言持久化通常是正确的；将系统记录与派生数据（CDC / 事件源）分开，而不是双重写入。

**调用：** 使用 `ddia-systems` 技能，并针对摄入的数据库和阶段8的副本计划。请求找到易受写偏差影响的读后写路径，声明实际默认隔离级别及其异常，并修复有风险的路径。

**与用户一起决策：** 哪些路径需要锁定，而不是序列化事务，以及新的工作负载（搜索、信息流）是否值得一个新的数据存储通过CDC保持同步。

**产出物：** 扩展 docs/ARCHITECTURE.md `## 数据 & 存储决策`，包含隔离级别、锁定路径，以及任何多语言/派生数据选择；记录推理在 `## 决策日志` 中。更新跟踪器。

**完成时：** 默认隔离级别被记录，每个易受写偏差的路径都被锁定或变为序列化，并且任何新的数据存储都有定义的同步机制。
