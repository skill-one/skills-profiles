# 37signals 产品开发框架

一个用于构建盈利软件的系统，无需臃肿、官僚主义或过度劳累，其精髓源自三本书：《真实世界》(少做)、《重做》(默认拒绝)和《搞定》(固定时间、灵活范围)。使用它来塑造工作、押注六周周期、运行小型自主团队，并按可预测的节奏发布。

## 核心原则

**少做。** 最好的产品做更少的事情但做得更好——简单是目的地，不是起点。传统开发是增加，而37signals的方式是减少：做半个产品（而不是半途而废的产品），默认拒绝，固定时间并灵活范围。限制是伟大工作的前提——六周、三人、定制的提案迫使你找到核心版本。

## 评分

**目标：10/10。** 根据这些原则对产品计划、功能范围和团队流程进行0-10评分。报告当前分数以及达到10/10所需的特定变更。

- **9-10：** 固定时间周期、定制提案、小型团队、无积压、明确默认值、清晰文案
- **7-8：** 大部分是定制工作和小型团队，但存在范围蔓延或流程开销
- **5-6：** 部分定制，但积压持续存在，团队规模过大，或偏好取代决策
- **3-4：** 重流程（站会、冲刺、故事点）偶尔进行简单性工作
- **0-2：** 功能工厂：长期路线图、大型团队、估算仪式、无定制

### 1. 少做，超越竞争对手

**核心概念：** 通过刻意省略赢得——更少的功能、更少的偏好、更少的移动部件，每个都做得比竞争对手更好。开发你自己需要的软件，解决你深刻理解的问题。

**为什么有效：** 每个功能都会永远带来维护、认知和机会成本，通常只服务于部分用户。少做能让产品聚焦，代码库易于管理，团队规模较小。

**关键洞察：**
- 半个产品胜过半途而废的产品——做几件事做好，而不是做许多事做差
- 做策展人，不做囤积者：拒绝好想法，让伟大的想法呼吸空间
- 做小决定——大决定难以做出且难以撤销；小决定能积累动力
- 超越竞争对手：让他们做瑞士军刀，而你做牛排刀
- 聚焦不会改变的东西——速度、简单性、可靠性、易用性

**产品应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| **功能优先级** | 默认拒绝 | 请求报告仪表板→发布覆盖90%用例的CSV导出 |
| **MVP范围** | 切到痛处再切更多 | v1放弃用户账户；使用邮箱魔法链接 |
| **竞争策略** | 超越，不做超越 | 竞争对手有50个集成；发布3个完美运行 |

在决定删减什么时查看 [参考资料/build-less.md](references/build-less.md) —— 策展策略、限制作为功能论点、实际范围删减示例。

### 2. 塑造工作

**核心概念：** 在工作到达团队之前，一位连接产品和技术世界的资深人士使其粗略（有操作空间）、解决（主要元素已确定）、界定（范围由需求决定）。

**为什么有效：** 原始想法浪费团队时间；详细规格使团队变成工单处理者。塑造消除了最大的未知数，同时保留了设计自由，需求（“这个问题值多少时间？”）取代估算（“这需要多长时间？”）——界定投资而非无限承诺。

**关键洞察：**
- 定制提案包含五个元素：问题、需求、解决方案、陷阱、禁区
- 原型流程作为地点、可供性和连接——结构化而不需要视觉设计
- 粗笔画保持抽象度高；线框图在概念验证前邀请像素级反馈
- 陷阱（范围爆炸风险）在提案中解决，不在构建中
- 禁区使边界可见，防止范围蔓延

**产品应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| **功能设计** | 原型优于模型 | “邀请队友”：设置→邀请表单→发送邮件→接受链接→仪表板 |
| **范围定义** | 先定需求 | “2周需求问题，不是6周”塑造适合的解决方案 |
| **风险管理** | 提前指出陷阱 | “权限可能很复杂——v1仅限所有者/成员” |

**道德边界：** 设定反映问题真实价值的需求数——永远不要人为缩小以施压团队。

查看 [参考资料/shaping-work.md](references/shaping-work.md) 时起草提案——五元素提案格式、实际原型、粗笔画规则、陷阱模式表、好/坏禁区示例、六步塑造流程。

### 3. 押注和周期

**核心概念：** 用押注表取代积压和路线图：资深利益相关者将定制提案押注到六周周期中，周期之间有两周冷却期。未完成的工作触发断路器——不会自动继续。

**为什么有效：** 积压会无限增长，制造虚假进展，分散焦点；有限周期强制真正优先级。断路器终结僵尸项目，冷却期防止持续冲刺的过度劳累。

**关键洞察：**
- 废除积压——重要想法会回来
- 六周足够有意义的工作，短到能感受到截止日期
- 变动范围：团队为固定截止日期删减非必要范围，反之则不
- 一次计划一个周期——长期路线图是过时的承诺
- 大多数提案不会被押注，这是健康的

**产品应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| **路线图替代** | 每周期押注 | 每6周3-4个定制提案，而非12个月路线图 |
| **风险管理** | 断路器终结僵尸 | 6周完成70%？不发布——如果仍重要，重新塑造并押注 |
| **容量规划** | 周期间冷却 | 两周用于错误、技术债务、探索、恢复 |

**道德边界：** 诚实地使用断路器——消除僵尸项目，而非政治不便项目；重点是专注，而非不可持续的施压。

查看 [参考资料/betting-cycles.md](references/betting-cycles.md) 时运行押注表或计划周期——表如何决定、六周/两周节奏结构、应用断路器、反对积压的案例。

### 4. 小团队和执行

**核心概念：** 三人团队（一名设计师，一到两名程序员）自主工作定制提案——无站会，无项目经理徘徊。他们自行发现任务，并在山形图上跟踪进度。

**为什么有效：** 三个人可以交谈，十个人需要会议。团队从定制提案中发现任务，能真正理解问题，山形图说真话：上坡=仍在探索，下坡=执行已知工作。

**关键洞察：**
- 范围取代任务——将相关工作分组为独立移动的山形图切片
- 会议是有毒的：写下来
- 真实：第2天有工作HTML和真实数据，胜过第5天的Figma模型
- 现在发布，以后迭代——用户手中的软件胜过演示文稿中的计划
- 设计和编程从第一天开始整合——无交接阶段

**产品应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| **团队结构** | 最多三人，无项目经理 | 每6周押注一名设计师+两名程序员 |
| **进度跟踪** | 山形图，非燃尽图 | “邀请”（权限不明确）上坡； “邮件模板”（执行）下坡 |
| **沟通** | 异步优先，写下来 | 书面更新或5分钟视频，而非30分钟会议 |

**道德边界：** 自主需要真正可管理的范围——如果团队持续加班才能在六周内完成，修复塑造，而非团队。

查看 [参考资料/small-teams-execution.md](references/small-teams-execution.md) 时团队处于构建中——阅读和更新山形图、切片范围、异步沟通规范、用真实HTML做真实工作。

### 5. 有偏见的软件和清晰沟通

**核心概念：** 伟大软件做选择，而不是让用户陷入偏好——每个偏好都是团队无法或不愿做的决定。同样的诚实适用于文案：直白表达，避免营销术语，公开传授知识。

**为什么有效：** 每个偏好都会将产品分割成更多状态需要设计、测试和支持，并将决策推给缺乏背景的用户；合理默认减少认知负担并创造凝聚力。清晰文案建立信任，而营销术语侵蚀信任，公开教学吸引与你有相同价值观的客户。

**关键洞察：**
- 选择最佳默认值并发布——只有数据表明它失败时才重审
- 循环（为早期功能创造的问题而修补的功能）增加复杂性
- “现在不”是对好功能请求的有效、健康的回答
- 超越竞争对手；销售你的副产品（书籍、文章、工具）
- 界面文案是最好的营销——每个标签和错误消息都在建立或破坏信任

**产品应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| **功能请求** | 默认拒绝，无虚假承诺 | “感谢建议。我们目前不计划这个。” |
| **UI文案** | 平白语言 | “已保存”而非“已成功将资源持久化到云端” |
| **错误消息** | 诚实且有帮助 | “无法发送邮件。检查地址并重试。” |
| **偏好** | 消除；选择默认值 | 从浏览器检测时区；发布一个好的主题 |
| **营销** | 诚实定位 | “Basecamp并非适合所有人。这里是谁适合，谁不适合。” |

查看 [参考资料/opinionated-software.md](references/opinionated-software.md) 时拒绝功能请求或删除设置，以及 [参考资料/ux-ui-copy.md](references/ux-ui-copy.md) 时编写界面文案、空状态或错误消息。

## 常见错误

| 错误 | 失败原因 | 修复 |
|------|----------|------|
| 维护积压 | 无限增长；虚假进展；分散焦点 | 废除它；每个周期押注定制提案 |
| 估算而非设定需求 | 估算填满时间并邀请谈判 | 询问“这个问题值多少时间？” |
| 塑形前像素级模型 | 太早具体；邀请争论 | 先原型和粗笔画 |
| 延长六周周期 | 僵尸项目教团队截止日期是假的 | 断路器：未完成即不发布 |
| 添加偏好而非决策 | 为少数人服务而增加所有用户的复杂性 | 选择最佳默认值并发布 |
| 每日站会和状态会议 | 中断制作流程；报告开销 | 山形图提供可见性；异步更新 |
| 对好功能请求说“是” | 好功能仍增加非必要复杂性 | 默认拒绝；只押注本周期重要的事 |
| 提前计划多个周期 | 过时的承诺降低响应性 | 一次计划一个周期 |

## 快速诊断

| 问题 | 否 | 行动 |
|------|----|------|
| 这项工作有固定时间限制吗？ | 范围无限扩展 | 首先设定六周（或更短）的需求 |
| 工作是否定制（粗略、解决、界定）？ | 建设中范围问题出现 | 定义问题、需求、解决方案、陷阱、禁区 |
| 2-3人团队能完成吗？ | 太大 | 分解为独立的六周押注 |
| 本周期拒绝至少5件事？ | 做太多 | 在押注表中无情删减 |
| 团队自行发现任务？ | 微管理；团队未授权 | 交接定制提案，而非任务清单 |
| 用山形图跟踪进度？ | 虚假精确掩盖不确定性 | 切换为上坡（探索）vs. 下坡（执行） |
| 周期后有冷却期吗？ | 过度劳累；无清理时间 | 安排两周无结构时间 |
| 软件在此处有明确偏见吗？ | 决策推迟给用户偏好 | 选择最佳默认值；移除设置 |

查看 [参考资料/case-studies.md](references/case-studies.md) 获取端到端实际案例——采用Shape Up、抵制功能蔓延、用山形图取代状态会议。
