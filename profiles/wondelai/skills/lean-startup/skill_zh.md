# 精益创业方法论

一种系统化的方法，用于构建初创企业和推出新产品，它缩短了开发周期，并快速发现商业模式是否可行。

## 核心原则

**创业是一种管理形式。** 成功不需要完美的计划或卓越的洞察力——它需要一个系统化的过程来验证假设、从客户那里学习，并快速迭代。大多数初创企业失败不是因为他们无法构建计划中的东西，而是因为他们构建了错误的东西：将每个计划视为一组可证伪的假设，并投入精力消除浪费和加速**验证学习**，而不是执行固定的路线图。

## 评分

**目标：10/10。** 通过五个快速诊断行对计划、实验或指标集进行评分——**回答“是”得1分，如果同时在验证阶梯上（第3级及以上）得到证据得2分**：

- **9-10：** 列出并按风险排序的每一个信念假设，风险最高的通过真实MVP进行测试，定义可操作的指标，并在构建之前设定明确的转向标准。
- **5-6：** 存在假设和一些MVP，但指标是虚荣的或转向标准未定义——无法从数据中做出决策。
- **≤3：** 水平化思维——首先构建完整产品，询问客户他们想要什么，或在产品/市场契合度之前进行扩展。

说明当前分数和最低分诊断行，以便下一步修复。

## 构建-衡量-学习循环

基本循环：**想法 → 构建（产品）→ 衡量（数据）→ 学习（知识）→ 回到想法。**

**关键洞察：** 逆向规划循环：
1. **我们想学习什么？**（要测试的假设）
2. **我们将如何知道我们学到了？**（指标）
3. **我们能构建的最小化是什么？**（MVP）

**目标：** 最小化通过循环的总时间。

在规划实验时查看 [references/build-measure-learn.md](references/build-measure-learn.md)——逆向规划顺序、实验设计模板、按产品类型划分的循环示例，以及构建/虚荣指标循环陷阱。

## 验证学习

通过关于真实行为的实验学习客户真正想要什么——而不是功能请求、调查或焦点小组（人们会误判自己的行为）。衡量客户*做了什么*，而不是他们*说什么*，并运行可能证伪你假设的实验。虚荣的胜利（下载量、无参与的注册）不是学习。

**验证阶梯：**

| 级别 | 证据 | 强度 |
|------|------|------|
| 1 | “我认为客户想要这个” | 最弱（观点） |
| 2 | “客户说他们想要这个” | 弱（陈述偏好） |
| 3 | “客户注册了早期访问” | 中等（低承诺） |
| 4 | “客户支付了定金” | 强（真实承诺） |
| 5 | “客户在积极使用它” | 最强（显露偏好） |

**目标：** 在大规模构建之前达到第4-5级。

## 最小可行产品（MVP）

允许以最少努力进行最大验证学习的新产品的版本。不是原型（技术可行性），不是Beta（质量），不是最小可市场产品——一个学习工具，通常令人尴尬的小且质量低，并且通常比你想象的要小得多。

**MVP类型：**

| 类型 | 它是什么 | 何时使用 | 示例 |
|------|----------|----------|------|
| **礼宾员** | 伪装成自动化的手动服务 | 测试解决方案是否有价值 | Food on the Table（手动餐点计划） |
| **奥兹巫师** | 假自动化，手动后端 | 测试是否需要自动化 | Zappos（无库存，零售购买鞋子） |
| **烟雾测试** | 登录页面+注册，无产品 | 在构建之前测试需求 | Dropbox视频（解释概念，衡量注册） |
| **单个功能** | 只有核心功能 | 测试哪个功能最有价值 | Twitter（仅状态更新） |
| **零碎** | 组合现有工具 | 在定制构建之前测试工作流程 | Groupon（WordPress + 电子邮件） |

**设计问题：** 最危险的假设是什么？测试它的最小化是什么？我们如何衡量它是否得到验证？

在选择和调整MVP时查看 [references/mvp-design.md](references/mvp-design.md)——七种类型的深入分析、类型选择决策矩阵、下限/上限调整范围，以及MVP设计画布。

## 信念假设

如果错误，将导致你的业务失败的假设。识别它们，按风险（哪个失败将是致命的？）进行优先排序，并首先测试最危险的假设——永远不要按容易程度顺序测试。

| 假设类型 | 问题 | 测试方法 |
|----------|------|----------|
| **价值假设** | 客户是否关心这个问题？ | 烟雾测试，礼宾员MVP |
| **增长假设** | 客户将如何发现我们？ | 渠道测试，推荐实验 |
| **保留假设** | 客户会回来吗？ | 群组分析，参与指标 |
| **变现假设** | 客户会付费吗？ | 预订单，价格测试 |

**示例—Dropbox：** 信念假设：“人们会下载和使用文件同步工具。” 测试：在构建大规模基础设施之前制作解释视频。结果：Beta列表从5,000个增长到75,000个，一夜之间——需求得到验证。

在映射和排名假设时查看 [references/assumptions.md](references/assumptions.md)——影响-不确定性矩阵、优先级评分模板、每种假设类型的测试方法，以及特定行业的假设列表。

## 创新会计

当传统指标失败时的进度衡量：收入和客户从零开始，虚荣指标看起来不错，但不会推动决策。

### 1. 建立基线

精确衡量当前现实，即使它是零或令人尴尬：转化漏斗（注册 → 活跃 → 保留 → 付费），参与度（DAU/MAU，会话长度，使用功能），经济（CAC，LTV，流失率）。

### 2. 调整引擎

运行实验以提高基线指标：A/B测试定价（$9 vs. $19/月），入职完成率，获取渠道（SEO vs. 付费 vs. 推荐）。每个实验都通过验证学习针对可衡量的改进。

### 3. 转向或坚持

当调整停滞时，做出基于证据的判断（以下在**转向或坚持**中列出的标准和转向类型）。

在构建基线仪表板时查看 [references/innovation-accounting.md](references/innovation-accounting.md)——漏斗、群组和经济学指标框架。

## 可操作指标与虚荣指标

虚荣指标让你感觉良好，但不会改变行为；可操作指标推动决策并阐明因果关系。

| 虚荣指标 | 为什么它不好 | 可操作替代方案 |
|----------|--------------|----------------|
| **总注册量** | 总是上升，无背景 | **注册→活跃%**（转化率） |
| **页面浏览量** | 不指示价值 | **页面停留时间**，**跳出率** |
| **总用户数** | 包括不活跃/流失用户 | **活跃用户**（DAU，WAU，MAU） |
| **下载量** | 不表示使用 | **DAU/下载量**（激活率） |
| **收入** | 无背景 | **每群组收入**，**LTV/CAC** |

**可操作指标的三种特征：** 可操作的（清晰的因果关系，可重复），可访问的（简单，每个人都能理解），可审计的（底层数据可以检查）。

**示例：** 虚荣指标：“我们拥有100,000用户！” 可操作指标：“X渠道用户保留率是Y渠道的两倍——加倍投入X。”

**群组分析：** 按注册日期分组用户，并跟踪随时间推移的行为——这是唯一能看到产品是否真正改进的方法。

在构建群组表格或选择要跟踪的内容时查看 [references/metrics.md](references/metrics.md)——五步群组演练和与精益创业阶段对齐的AARRR（海盗指标）。

## 转向或坚持

转向是一个结构化的课程纠正，旨在测试关于产品、战略或增长引擎的新假设。

**转向时：** 实验反复无法验证假设，指标尽管迭代但保持平稳，客户反馈与愿景相矛盾，或进展对跑道来说太慢。**坚持时：** 指标在改进（即使很慢），清晰的 学习正在发生，并且调整朝着正确的方向移动。

**转向类型：**

| 转向类型 | 更改内容 | 示例 |
|----------|----------|------|
| **放大** | 单个功能成为整个产品 | Instagram（照片滤镜来自Burbn） |
| **缩小** | 产品成为单个功能 | Flickr（照片分享来自Game Neverending） |
| **客户群组** | 同一个问题，不同客户 | Groupon（行动主义平台→本地交易） |
| **客户需求** | 同一客户，不同问题 | Potbelly（古董店→三明治） |
| **平台** | 应用程序 ↔ 平台 | YouTube（约会网站→视频平台） |
| **商业架构** | 高利润/低销量 ↔ 低利润/高销量 | Salesforce（软件→SaaS） |
| **价值捕获** | 变现模式变更 | Android（付费→免费+应用收入） |
| **增长引擎** | 病毒，粘性或付费模式 | Facebook（大学病毒→付费广告） |
| **渠道** | 你如何接触客户 | Salesforce（直销→自助服务） |
| **技术** | 不同技术，相同解决方案 | Apple（英特尔→ARM芯片） |

**节奏：** 成功的初创企业通常在产品/市场契合度之前转向1-5次。**反模式：** “转向”而没有验证新方向是否解决了核心问题。

在数据表明需要转向时查看 [references/pivots.md](references/pivots.md)——数据驱动的转向信号，结构化的转向会议议程，领先指标，以及Instagram/Slack/YouTube的转向故事。

## 三个增长引擎

初创企业可持续获取和保留客户的方式。**选择一个引擎，优化它，然后考虑添加其他引擎**——同时运行多个引擎会分散注意力和学习。

### 1. 粘性增长引擎

以保留为驱动：`增长率 = 新客户获取率 - 流失率`。跟踪流失率，保留群组（30/60/90天），DAU/MAU。适用于SaaS、订阅、社交网络。策略：改进产品，直到自然增长率超过流失率。

### 2. 病毒增长引擎

客户带来客户：`病毒系数 = (%邀请) × (发送邀请) × (%加入)`；大于1.0表示指数增长，自我维持增长。跟踪系数，病毒周期时间，推荐归因。适用于Dropbox，Hotmail，WhatsApp。策略：将病毒性构建到产品本身。

### 3. 付费增长引擎

花费以获取：需要 `LTV > CAC`（目标LTV/CAC > 3x）。跟踪CAC，LTV，和回收期。适用于电子商务和传统企业。策略：优化，直到每个客户的利润为获取更多客户提供资金。

在挑选或调整引擎时查看 [references/growth-engines.md](references/growth-engines.md)——流失率降低策略，K因子和病毒循环设计，LTV/CAC优化，渠道经济表，以及产品与引擎匹配框架。

## 五个为什么

根本原因分析：当问题发生时，问“为什么？”五次，然后在每个级别上按比例投资——不仅仅是症状。

**示例—网站宕机：**
1. **为什么？** 服务器内存耗尽
2. **为什么？** 新功能中的内存泄漏
3. **为什么？** 代码未进行内存管理审查
4. **为什么？** 基础设施变更没有代码审查流程
5. **为什么？** 团队移动太快，没有创建流程

**按比例投资：** 修复错误（1），添加内存监控（2），实施代码审查（3-4），放慢速度以建立质量流程（5）。**反模式：** 停在级别1。

在促进会议时查看 [references/five-whys.md](references/five-whys.md)——三个工作示例（宕机，流失率激增，发布失败）以及如何处理分歧链，指责蔓延，以及你无法控制的根本原因。

## 小批量

以小批量工作，以实现更快的反馈循环，更容易转向，当你犯错时减少浪费，并更快地推向市场。

| 大批量 | 小批量 |
|--------|--------|
| 构建整个产品，然后发布 | 发布登录页面，然后构建 |
| 每季度发布 | 每周或每天发布 |
| 规划12个月路线图 | 规划6周周期 |
| 大爆炸重写 | 增量重构 |

**持续部署** 是终极小批量：每次提交都部署，立即发现错误，持续学习，减少每个发布的风险。

在设置更快发布节奏时查看 [references/small-batches.md](references/small-batches.md)——持续部署管道和先决条件，功能标志类型，渐进式发布清单，和工作分解技术。

## 精益创业应用：从想法到规模

**阶段1—问题/解决方案契合：** 通过客户发现、烟雾测试和礼宾员MVP验证问题是否存在，客户是否关心。指标：愿意付费或承诺的客户。

**阶段2—产品/市场契合：** 构建MVP并迭代使用数据。指标：高保留率，有机增长，强参与度。

**阶段3—扩展：** 优化增长引擎和单位经济。指标：可持续、盈利增长。**反模式：** 跳过阶段1-2，直接跳到扩展。

**按背景：**
- **SaaS初创企业：** 烟雾测试（登录页面+邮件列表）→ 10个客户的礼宾员MVP → 单个功能MVP → 衡量保留率，NPS，功能使用率 → 基于群组数据转向或扩展
- **企业创新：** 将创新会计与核心业务指标分开，保护团队免受季度收入压力，在验证学习里程碑上解锁计量资金
- **产品功能：** 背后部署功能标志 → A/B测试核心指标 → 基于数据放弃、迭代或扩展

在需要特定上下文剧本（SaaS，企业创新，功能）时查看 [references/applications.md](references/applications.md)，以及 [references/case-studies.md](references/case-studies.md) 以获取完整的Dropbox，IMVU，Zappos，Groupon故事——包括失败——当你需要你面前赌注的完整工作先例时。

## 常见错误

| 错误 | 为什么它失败 | 修复 |
|------|--------------|------|
| **构建太多** | 验证之前浪费 | 首先使用烟雾测试或礼宾员测试 |
| **询问客户** | 人们不知道/误判 | 观察行为，而不是观点 |
| **虚荣指标** | 感觉良好的数字，没有决策 | 跟踪群组，转化率，保留率 |
| **没有假设** | 如果你不预测，就无法学习 | 在每个实验之前写下假设 |
| **转向太慢** | 浪费跑道 | 提前设定明确的转向标准 |
| **跳过创新会计** | 无法判断你是否在改进 | 建立基线，衡量调整工作 |
| **过早扩展优化** | 在产品/市场契合度之前抛光 | 首先验证学习；质量遵循证据 |

## 快速诊断

审计任何产品开发计划：

| 问题 | 如果没有 | 行动 |
|------|----------|------|
| 最危险的假设是什么？ | 在不稳定的土地上构建 | 绘制信念假设 |
| 你将如何测试它？ | 你在猜测 | 设计MVP来测试假设 |
| 哪个指标将验证/证伪？ | 你不会学习 | 定义可操作指标 |
| 你可以用更少的东西测试吗？ | 过度构建 | 进一步缩小MVP |
| 如果实验失败，你会做什么？ | 没有转向标准 | 提前定义转向触发器 |
