# 精简用户体验框架

一种以实践为导向的体验设计方法，用快速实验、跨职能协作和持续学习来取代繁重的交付成果。精简用户体验将问题从"我们应该设计什么？"转变为"我们需要学习什么？"

## 核心原则

**结果重于产出。** 体验设计的价值不是由交付成果的保真度来衡量，而是由它带来的用户行为变化来衡量。

**基础：** 传统的用户体验瀑布式流程将需求转化为线框图、模型、规范和代码，在每次交接中丢失上下文并隐藏未经测试的假设。精简用户体验压缩了想法与证据之间的距离：声明假设，形成假设，运行最小规模的实验，让真实用户行为来决定结果。共享理解取代了文档；学习速度取代了像素完美。

## 评分

**目标：10/10。** 通过下方的八行快速诊断来评估用户体验流程、设计计划或团队工作流程：每行回答"是"约得1.25分（8个"是"=10）。等级：

- **9-10** — 声明假设，具有预先承诺的成功标准的假设，最低保真度的实验，整个团队参与设计，每周进行研究，结果（而非产出）指标，双轨敏捷，以及最近被证伪的假设。
- **5-6** — 存在假设，但标准模糊或保真度过高；设计和研究仍然部分隔离。
- **<=3** — 繁重的交付成果，未经测试的假设，产出计数，没有实验日志。

始终说明当前分数，失败的诊断行，以及每个具体修复措施。

## 框架

### 1. 声明假设

**核心概念：** 每个设计都始于假设。精简用户体验使它们显式化，以便可以优先考虑和测试，而不是在规范中无形地嵌入。

**为什么有效：** 未言明的假设意味着团队在 shaky 的基础上构建，只有在发布后才发现问题；早期揭示它们可以集中精力在最危险的假设上，并降低出错成本。

**关键洞察：**
- 商业假设定义了必须为业务成立的条件（收入模式、市场规模、支付意愿）；用户假设定义了用户是谁以及他们如何行为
- 按两个轴进行优先级排序：风险（如果错误会造成多大损害）和不确定性（我们了解多少）
- 首先测试高风险、高不确定性的假设
- 作为团队协作地编写假设，而不是孤立地编写

**产品应用：**

| 上下文 | 应用 | 示例 |
|--------|------|------|
| **新功能启动** | 假设映射工作坊 | "我们假设用户想要与队友分享报告" |
| **路线图规划** | 按假设风险排序功能 | 优先考虑其成功取决于未经测试信念的功能 |
| **利益相关者对齐** | 跨角色暴露隐藏的假设 | PM 假设定价有效；工程师假设可扩展性；设计师假设流程 |

**道德边界：** 假设必须是诚实的评估，而不是事后解释——如果领导层已经决定了一个方向，承认约束，而不是假装它可以向证伪开放。

在运行假设工作坊或编写假设时查看 [参考资料/hypothesis-canvas.md](references/hypothesis-canvas.md) — 风险/不确定性优先级矩阵，商业与用户假设的区分，以及可填写的假设和子假设模板。

### 2. 假设陈述

**核心概念：** 假设将假设转化为可测试的预测，将建议的更改与特定用户群的可衡量结果联系起来。

**为什么有效：** 假设迫使精确——而不是"改善引导"，团队承诺一个可以被证明或证伪的预测，这可以防止范围蔓延，并使学习步骤不明确。

**关键洞察：**
- 标准格式："我们相信如果[用户画像]通过[操作]使用[功能]，[结果]会发生"
- 每个假设都指定用户画像、操作、结果和可衡量的信号
- 子假设将一个大赌注分解为可独立测试的部分
- 在运行实验之前，就"验证"和"证伪"的外观达成一致

**产品应用：**

| 上下文 | 应用 | 示例 |
|--------|------|------|
| **功能设计** | 在线框图之前编写假设 | "我们相信如果新用户完成引导设置向导，试用到付费的转化率将提高10%" |
| **A/B测试** | 正式化测试理由 | "如果我们把行动号召按钮移到页眉上方，点击率将提高15%" |
| **冲刺计划** | 将假设附加到每个故事 | 故事："按日期筛选"。假设："任务完成时间缩短30%" |

**道德边界：** 不要在事后挑选指标来宣布假设验证——预先承诺成功标准。

在挑选假设的可衡量信号或定义团队成功时查看 [参考资料/outcome-metrics.md](references/outcome-metrics.md) — 结果与产出，领先指标与滞后指标对，用户体验 OKRs，以及要避免的虚荣指标。

### 3. MVP 和实验

**核心概念：** 在精简用户体验中，MVP 是可以测试假设的真实用户的最小设计工件——一个学习工具，而不是产品发布。

**为什么有效：** 用五位用户在走廊中测试的纸质原型可以证伪原本会消耗整个工程冲刺的假设；将实验保真度与假设风险相匹配，可以最大化每单位努力的学习量。

**关键洞察：**
- 实验范围从低保真度（纸质原型、concierge 测试）到高保真度（编码 A/B 测试、Wizard of Oz）
- 选择能回答问题的最低保真度实验
- 一个好的实验有明确的假设、定义的受众、可衡量的信号和时间限制
- 原型用户画像可以在需要速度时代替完整研究，但必须在之后验证

**产品应用：**

| 上下文 | 应用 | 示例 |
|--------|------|------|
| **早期概念验证** | 纸质原型或可点击模型 | 同一天绘制3个概念，测试5位用户 |
| **需求验证** | 登录页面烟雾测试 | "注册获取早期访问"衡量真实兴趣 |
| **可用性验证** | 可点击原型测试 | Figma 原型测试5-8位用户 |
| **定价验证** | 油漆门测试 | 显示定价页面，在构建计费之前测量点击率 |

**道德边界：** 烟雾测试和假门不得误导用户认为产品存在——披露测试状态并提供退出选项。

在挑选或设计实验时查看 [参考资料/experiment-patterns.md](references/experiment-patterns.md) — 实验类型的完整目录，包括何时/何时不应运行的说明，实验选择矩阵和保真度阶梯，以及设计模板。

### 4. 协作设计

**核心概念：** 设计是一项团队运动。精简用户体验用跨职能会议取代了设计师-然后-交接的孤立模型，在这些会议中，开发人员、产品经理和设计师一起绘制解决方案。

**为什么有效：** 帮助绘制解决方案的开发人员不需要40页的规范来构建它——共享理解取代了文档，不同角度产生了更具创造性的解决方案，交接浪费大幅下降。

**关键洞察：**
- 设计工作室方法：发散（个人绘制），展示，评论，收敛（改进的绘制），迭代
- 目标是知情的承诺，而不是共识：团队同意要测试什么，而不是什么是"正确"的
- 跨职能意味着工程师、QA、数据分析师和利益相关者也绘制
- 风格指南和模式库是活文档；将交付成果减少到仅用于共享理解所需的最小量（通常是白板照片）

**产品应用：**

| 上下文 | 应用 | 示例 |
|--------|------|------|
| **冲刺启动** | 设计工作室会议（90分钟） | 整个团队绘制与冲刺假设相关的解决方案 |
| **功能探索** | 协作绘制工作坊 | 6-up 绘制：每人5分钟绘制6个想法 |
| **远程团队** | 虚拟白板会议 | FigJam 或 Miro 白板，有时间限制的绘制回合 |

**道德边界：** 协作不得成为委员会式设计——指定的设计师综合输入；团队不会对像素进行投票。

在促进设计工作室时查看 [参考资料/collaborative-design.md](references/collaborative-design.md) — 工作坊协议的逐步说明（时间、材料、远程变体）以及如何将风格指南作为活文档。

### 5. 反馈和研究

**核心概念：** 持续的轻量级研究取代了大型可用性研究——每个冲刺中嵌入的小型研究，而不是季度报告。

**为什么有效：** 发现只有在决策仍然可以逆转时才会改变，因此研究的价值随着学习与它所通知的决策之间的冲刺数而衰减；每周的小型研究将这个差距保持在接近零，而季度报告永远无法做到。

**关键洞察：**
- 研究类型：可用性测试，客户访谈，A/B 测试，分析审查，调查，日记研究
- 五位用户可以揭示大约85%的可用性问题（尼尔森）
- 持续节奏：每周招募，每周测试，每周综合
- 整个团队应该至少观察一些会议以建立同理心
- 原型用户画像在需要速度时可以代替基于证据的用户画像，但必须在之后验证

**产品应用：**

| 上下文 | 应用 | 示例 |
|--------|------|------|
| **每周可用性测试** | 每周四测试原型3-5位用户 | "测试星期四"仪式，轮换主持人 |
| **发布后学习** | 监控分析+3个后续访谈 | 找到流失点，访谈流失用户 |
| **用户画像验证** | 比较原型用户画像假设与访谈数据 | "我们假设高级用户是市场营销人员；数据显示运营经理" |

**道德边界：** 以知情同意进行研究——参与者应了解其数据如何使用，并有权撤回。

### 6. 与敏捷集成

**核心概念：** 精简用户体验通过双轨开发在敏捷中工作：发现（学习要构建什么）和交付（构建它）并行运行。

**为什么有效：** 设计工作无法整齐地放入交付冲刺中；提前一个冲刺运行发现意味着验证的设计在交付冲刺开始时准备好了，而不是设计永远落后。

**关键洞察：**
- 发现轨道（研究+设计）为交付轨道（工程+QA）提供输入，交错一个冲刺
- 用户故事获得假设和成功指标，而不是验收标准
- 用户体验的"完成定义"包括验证的学习，而不仅仅是交付的像素
- 来自证伪假设的待办事项项被移除，而不是推迟

**产品应用：**

| 上下文 | 应用 | 示例 |
|--------|------|------|
| **冲刺计划** | 将假设验证纳入冲刺目标 | "冲刺目标：验证如果新用户完成引导设置向导，任务完成时间缩短30%" |
| **待办事项项细化** | 将实验结果附加到故事 | 故事仅在假设验证后移至交付 |
| **回顾会议** | 与交付速度一起回顾学习速度 | "本冲刺验证了4个假设，证伪了2个" |

**道德边界：** 不要用精简用户体验作为跳过可访问性、安全性或合规性的借口——这些是非协商的质量标准，而不是要测试的假设。

在将发现拟合到交付节奏时查看 [参考资料/agile-integration.md](references/agile-integration.md) — 交错双轨冲刺机制，故事如何携带假设，以及用户体验完成定义。

在您想要一个端到端示例以建模参与时查看 [参考资料/case-studies.md](references/case-studies.md) — 四个复合场景（企业、初创公司、代理、内部工具）显示假设、实验和结果/产出指标。

## 常见错误

| 错误 | 为什么失败 | 修复 |
|------|----------|------|
| **将 MVP 视为发布** | 通过将 MVP 与首次发布混淆而过度构建 | 重构：MVP = 学习工具，而不是产品发布 |
| **跳过假设声明** | 隐藏的假设成为昂贵的惊喜 | 在启动时运行30分钟的假设映射会议 |
| **没有成功标准的假设** | 无法判断实验是否通过 | 预先承诺指标、阈值和样本量 |
| **设计师唯一的设计** | 交接浪费、错位、迭代缓慢 | 与整个团队运行设计工作室会议 |
| **研究作为阶段** | 反馈太晚才重要 | 将轻量级研究嵌入每个冲刺 |
| **忽略证伪的假设** | 构建了未通过测试的功能 | 从待办事项项中移除证伪项；转向或放弃 |
| **文档化而不是协作** | 没有人阅读的40页规范 | 用共享理解取代规范，来自协作设计 |
| **衡量产出而非结果** | 交付了不会改变行为的功能 | 将成功定义为行为改变，而不是交付 |

## 快速诊断

审计任何用户体验流程或设计计划：

| 问题 | 如果没有 | 行动 |
|------|----------|------|
| 假设是否明确声明？ | 隐藏的假设驱动决策 | 运行假设映射工作坊 |
| 是否有可测试的假设？ | 基于意见构建 | 在设计之前以标准格式编写假设 |
| 实验是否是回答问题的最低保真度？ | 在学习前过度投资 | 降级为纸质原型或烟雾测试 |
| 整个团队是否参与设计？ | 交接浪费和错位 | 安排设计工作室会议 |
| 是否每个冲刺都在进行研究？ | 反馈循环太慢 | 建立每周测试节奏 |
| 是否跟踪结果而非产出？ | 交付了不会学习 | 按功能定义行为改变指标 |
| 用户体验是否顺畅地输入敏捷？ | 设计瓶颈或冲刺零陷阱 | 实施双轨敏捷，交错冲刺 |
| 是否可以指出一个最近证伪的假设？ | 没有学习；确认偏差 | 审查实验日志并庆祝转向 |
