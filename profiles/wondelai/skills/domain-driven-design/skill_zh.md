# 领域驱动设计框架

通过围绕业务领域建模代码来应对软件复杂性的框架。软件中最大的风险不是技术故障——而是构建的模型无法反映业务的实际运作方式。

## 核心原则

**模型即代码；代码即模型。** 软件应当体现对业务领域深刻的、共享的理解。当领域专家和开发人员使用同一种语言，并且这种语言直接体现在代码库中时，复杂性就变得可控，系统会随着业务的变化优雅地演进。

## 评分

**目标：10/10。** 通过为满足快速诊断的每一行（7行）**每行1分**，再加上高达3分的深度分数来评分领域模型：如果核心领域具有真正丰富的模型（而不仅仅是CRUD），则加1分；如果不变量存在于聚合内部而不是服务中，则加1分；如果通用语言在对话、代码和测试中保持一致，则加1分。等级：**9-10** = 专家可读的名称、具有ACL的明确上下文边界、小聚合、行为丰富的实体、跨聚合流的事件、已识别的核心领域；**5-6** = 某些领域语言但有漏洞的边界或贫血对象；**<=3** = 技术命名、所有内容使用一个模型、逻辑散布在服务中。报告分数和失败的特定诊断行。

## 框架

### 1. 通用语言

**核心概念：** 开发人员和领域专家之间共享的、严格的语言，在对话、文档和代码中始终如一地使用。当语言变化时，代码也会变化——而代码中的笨拙命名会反过来促进语言的完善。

**为什么有效：** 含糊不清是大多数建模失败的根本原因。当开发人员说“订单”而专家意味着“购买请求”时，错误是不可避免的；通用语言强制代码中的每个名称都映射到业务认可并验证的概念。

**关键洞察：**
- 语言源于深入的协作，而不是事后附加的词汇表
- 如果一个概念很难命名，模型可能就是错误的——命名难度是一个设计信号
- 技术术语（`DataProcessor`与`ClaimAdjudicator`）将领域逻辑隐藏在能够纠正它的专家面前
- 不同的边界上下文可能使用相同的词语表示不同的含义——而这完全可以接受

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 类/方法命名 | 使用领域概念和动词命名 | `LoanApplication`，`policy.underwrite()`——而不是`RequestHandler`，`process()` |
| 模块结构 | 按领域概念组织 | `shipping/`，`billing/`——而不是`controllers/`，`services/` |
| 代码审查 | 拒绝纯技术名称 | 将`Manager`，`Helper`，`Processor`，`Utils`标记为命名异味 |

在运行建模会话或维护词汇表时查看：[references/ubiquitous-language.md](references/ubiquitous-language.md)——涵盖语言如何演变并反馈到代码中。

### 2. 边界上下文和上下文映射

**核心概念：** 边界上下文是在其中特定领域模型适用的明确边界。相同的词语（“Customer”）在不同的上下文中可以表示不同的含义；上下文映射定义了它们之间的关系和翻译策略。

**为什么有效：** 尝试维护单一统一模型的大型系统不可避免地会陷入不一致。边界上下文接受业务的不同部分需要不同的模型；上下文映射管理它们之间的集成。

**关键洞察：**
- 边界上下文不是微服务——它是一个语言和模型边界，可能包含多个服务
- 上下文边界通常与团队边界一致（康威定律）
- 九种上下文映射模式描述了团队之间的政治和技术关系
- 反腐层是最重要的防御模式——永远不要让外部模型泄漏到你的核心领域
- 共享内核将两个团队连接起来；保持它小而明确管理
- 从映射现有内容（一团糟）开始，然后定义目标边界

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 服务集成 | 反腐层 | 在边界处将外部API响应翻译成你的领域对象 |
| 遗留系统迁移 | 顺应者/ACL | 在适配器后面包装遗留系统，该适配器说你的领域语言 |
| API设计 | 开放主机服务+发布语言 | 暴露具有规范模式的良好文档的REST API |

查看：[references/bounded-contexts.md](references/bounded-contexts.md)以了解九种映射模式和集成策略。

### 3. 实体、值对象和聚合

**核心概念：** 实体具有跨状态变化的持久身份。值对象完全由其属性定义，并且是不可变的。聚合是实体和值对象的集群，具有单个根，该根强制执行一致性边界。

**为什么有效：** 没有这些区别，所有内容都变成了可变的、具有身份的对象——混乱的状态、不一致的更新、脆弱的并发。聚合划定了界限：聚合内部的所有内容都保证一致；外部内容最终一致。

**关键洞察：**
- 实体测试：“即使所有我的属性都改变，我还是同一个人吗？”（一个人改变姓名和地址——仍然是同一个人）
- 值对象测试：“我是否仅由我的属性定义？”（任何10美元的钞票都可以与另一个可互换）
- 大多数东西应该是值对象，而不是实体——优先考虑不可变性
- 保持聚合小（一个根加上最小的集群）；通过ID而不是对象引用引用其他聚合
- 聚合内部立即一致性；为聚合之间的最终一致性进行设计

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 身份跟踪 | 带有ID的实体 | `Order`由`orderId`标识，可以跨状态变化 |
| 不可变属性 | 值对象 | `Address(street, city, zip)`——替换，而不是突变 |
| 一致性边界 | 聚合根 | `Order`是根；`OrderLine`项目仅通过它存在 |
| 并发控制 | 根上乐观锁定 | `Order`上的版本字段；如果两个编辑竞争则发生冲突 |

查看：[references/building-blocks.md](references/building-blocks.md)以了解聚合设计规则和一致性边界。

### 4. 领域事件

**核心概念：** 领域事件捕获领域内发生的、专家关心的事情，以过去时命名（`OrderPlaced`，`PaymentReceived`）——已经发生的事实。

**为什么有效：** 领域事件将原因与结果解耦。当`OrderPlaced`发布时，运输、计费和通知各自独立地反应，而订单上下文不知道它们——耦合减少，最终一致性，一个自然的审计跟踪。

**关键洞察：**
- 事件是不可变的事实——一旦发布，就不能更改或撤回
- 领域事件是边界上下文内部的；跨边界的是集成事件
- 事件实现时间上的解耦：生产者不等待消费者
- 事件溯源将完整的事件历史作为真实来源存储，通过重播派生当前状态
- 不是每个状态变化都值得发布事件——只发布领域关心的事件

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 状态转换 | 在领域操作上引发事件 | `order.place()`引发`OrderPlaced` |
| 跨上下文集成 | 发布集成事件 | `OrderPlaced`触发运输上下文中的`ShippingLabelRequested` |
| 最终一致性 | 异步事件处理程序 | 库存处理程序在`OrderPlaced`后异步更新库存 |

查看：[references/domain-events.md](references/domain-events.md)以了解事件命名、事件溯源和集成事件。

### 5. 仓库和工厂

**核心概念：** 仓库提供领域对象内存集合的幻觉，隐藏持久性。工厂封装复杂的创建逻辑，以便聚合始终处于有效状态。

**为什么有效：** 当持久性和组装细节泄漏到领域代码中时，每次存储更改都会波及业务规则和聚合可能处于半有效状态。仓库将SQL/ORM关注点限制在基础设施中，以便领域可以在内存中保持可测试性；工厂确保到达聚合的唯一路径强制执行其不变量，因此无效实例无法表示。

**关键洞察：**
- 仓库接口属于领域层；其实现属于基础设施
- 仓库方法使用通用语言：`findPendingOrders()`，而不是`getByStatusCode(3)`
- 集合导向的仓库模仿`add`/`remove`；持久化导向的仓库使用`save`
- 对于复杂规则或多部分组装，才需要工厂；一个两字段的值对象只需要一个构造函数
- 规范模式将查询标准封装为领域对象：`OverdueInvoiceSpecification`

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 数据访问抽象 | 仓库接口 | `OrderRepository.findByCustomer(customerId)`在领域；`PostgresOrderRepository`在基础设施 |
| 复杂创建 | 工厂方法 | `Order.createFromQuote(quote)`验证并从`Quote`聚合组装 |
| 查询封装 | 规范 | `spec = OverdueBy(days=30); repo.findMatching(spec)` |

查看：[references/repositories-factories.md](references/repositories-factories.md)以了解仓库、工厂和规范模式。

### 6. 战略设计和提纯

**核心概念：** 系统的所有部分并非同等重要。战略设计识别核心领域——竞争优势所在——并将其与支持子领域（必要而非差异化）和通用子领域（商品）区分开来。

**为什么有效：** 在所有地方应用同样的严谨性会分散你的最佳人才，并过度设计商品功能。识别核心领域将最佳开发人员和最深建模集中在最关键的地方。

**关键洞察：**
- 核心领域：投资你的最佳人员和最深建模；支持：构建，但不要过度设计；通用（认证、电子邮件、支付）：购买或使用开源
- 提纯从周围的复杂性中提取并突出核心领域
- 领域愿景声明是对核心领域价值主张的一页描述
- 随着业务发展，重新审视“核心”——今天的差异化可能成为明天的商品

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 构建与购买 | 分类子领域类型 | 构建 定制定价引擎（核心）；使用Stripe支付（通用） |
| 团队分配 | 最佳开发人员专注于核心领域 | 资深人员建模承保规则；初级人员集成电子邮件服务 |
| 代码组织 | 将核心与通用分开 | `domain/pricing/`（深度模型）与`infrastructure/email/`（薄适配器） |

查看：[references/strategic-design.md](references/strategic-design.md)时决定在哪里投资工程工作——子领域分类和提纯技术。

## 常见错误

| 错误 | 为什么失败 | 修复 |
|------|-----------|------|
| 技术名称而不是领域语言 | 逻辑隐藏在`DataManager`后面；专家无法验证模型 | 重命名为领域术语（`ClaimAdjudicator`）；如果不存在领域术语，则概念可能错误 |
| 一个模型统治一切 | 一个用于计费、运输和营销的`Customer`类变得臃肿和自相矛盾 | 边界上下文：每个都有自己的`Customer`，并且只有它需要的属性 |
| 巨大的聚合 | 并发冲突、加载缓慢、事务瓶颈 | 保持聚合小；通过ID引用；聚合之间最终一致性 |
| 贫血领域模型 | 对象是数据包；规则散布在服务和重复 | 将行为移入实体和值对象；服务仅协调 |
| 没有反腐层 | 外部模型泄漏；代码耦合到外部模式 | 每个外部系统后面都有一个翻译层 |
| 边界上下文=微服务 | 过早提取；没有分布式复杂性的好处 | 上下文是一个模型边界，不是一个部署单元；从单体中的模块开始 |
| 忽略领域专家 | 开发人员发明了一个与现实不符的模型；昂贵的返工 | 定期建模会话，直到专家说“是的，这就是它的工作方式” |

## 快速诊断

| 问题 | 如果没有 | 操作 |
|------|---------|------|
| 领域专家能否读懂你的类名并理解它们？ | 技术术语隐藏了模型 | 重命名类、方法、事件为通用语言 |
| 边界上下文边界是否明确定义？ | 模型泄漏；相同的词语在不同上下文中表示不同的含义 | 绘制上下文映射；定义边界和翻译 |
| 聚合是否小（一个根+最小集群）？ | 加载缓慢，并发问题 | 分割聚合；通过ID引用；接受最终一致性 |
| 领域对象是否包含行为，而不仅仅是数据？ | 贫血模型；逻辑散布在服务中 | 将业务规则移入实体和值对象 |
| 是否使用领域事件进行跨聚合通信？ | 紧耦合，同步链 | 引入事件；让聚合异步反应 |
| 每个外部集成是否都有反腐层？ | 外部模型污染你的领域 | 在每个边界处添加翻译层 |
| 你是否已经确定了哪个子领域是核心？ | 最佳人才分散 | 分类子领域；专注于核心领域的深度建模 |
