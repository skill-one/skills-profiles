# 高效处理遗留代码

一份关于修改无测试代码的指南，源自 Michael C. Feathers 的著作《高效处理遗留代码》。使用它将无法测试的类放入测试框架中，通过特征化测试锁定当前行为，并逐步安全地做出更改——而无需进行重构。

## 核心原则

**遗留代码就是没有测试的代码。** 不是旧代码，也不是丑代码——未经测试的代码：没有测试，你无法知道更改是否保留了行为，因此每次编辑都像是在赌博。这门技艺在于打破足够的依赖关系，在更改任何东西之前引入测试——覆盖并修改，而不是编辑和祈祷。

## 评分

**目标：10/10。** 根据以下原则对未测试代码的更改进行 0-10 评分。报告当前分数以及达到 10/10 所需的具体步骤。

- **9-10：** 在任何编辑之前，更改特征化测试所覆盖的更改点；行为更改和重构作为单独的验证步骤交付；使用最侵入性的技术打破依赖关系
- **7-8：** 测试最多在更改点，但偶尔会出现混合重构加行为提交或比需要更重的依赖关系手术
- **5-6：** 某些特征化测试，但关键路径仍然基于信任更改；无回报计划的新生代码不断累积
- **3-4：** 编辑和祈祷，手动验证；更改后编写测试，断言新代码所做的任何事
- **0-2：** 直接将未测试的更改放入混乱的代码中，重构和行为更改混合在一个提交中，提议重构而不是测试

## 框架

### 1. 遗留代码困境和更改算法

**核心概念：** 困境：要安全地更改代码，我们需要测试，但要引入测试，必须更改代码。出路是一个固定序列——识别更改点，寻找测试点，打破依赖关系，编写测试，然后进行更改和重构——其中预测试编辑是保守和机械的，真正的更改只在安全网内发生。

**为什么有效：** 编辑和祈祷用反馈代替了谨慎，而谨慎无法扩展到你不完全理解的代码。覆盖并修改用测试的夹钳夹住了现有行为，因此任何意外的更改都会立即在你的机器上显示出来，而不是在生产环境中稍后显示。

**关键洞察：**
- 更改代码有两个原因——更改行为（功能、错误修复）和改进结构（重构）——将它们混合在一步中会使故障无法诊断
- 测试点很少是更改点：效果会传播，所以你通常在更改效果出现的地方测试，而不是在编辑的地方测试
- 在测试存在之前进行的依赖关系打破编辑必须精确保留签名，并依赖编译器找到每个受影响的位置
- 覆盖范围沿着你实际更改的路径增长——这比任何专门的“测试项目”更有优势，后者永远无法获得资金
- “编程是一门一次做一件事的艺术”：算法的每一步都是单独可验证的

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 未测试模块中的错误修复 | 在触摸错误之前运行五个步骤 | 用测试固定 `parseInvoice()`，然后修复舍入错误 |
| 混合清理和功能的 PR | 分成仅结构化和仅行为的提交 | 首先提取和重命名，测试变绿，然后添加折扣规则 |
| “只是一个单行更改” | 首先找到最近的测试点 | 在调用你要编辑的私有方法的公共方法上有一个固定测试 |

在运行五个步骤对实际更改进行操作时查看 [references/change-algorithm.md](references/change-algorithm.md)——作为一个工作程序，包含更改点/测试点检查表和“没有时间”情况的分诊。

### 2. 接缝：在哪里拆分代码

**核心概念：** 接缝是在你的程序中可以更改行为而无需在该位置编辑的地方。每个接缝都有一个启用点——你决定运行哪个行为的地方。将遗留代码置于测试之下很大程度上是在寻找接缝：测试可以替代慢速、全局或外部依赖关系，而生产源保持不变。

**为什么有效：** 如果你必须编辑代码来测试它，你可能会更改你正在试图固定的行为。接缝将替换移动到远处——一个子类、一个导入、一个构建标志——因此被测试的代码与生产环境完全一样运行，而测试从启用点控制其依赖关系。

**关键洞察：**
- 对象接缝是面向对象代码中的默认设置：每个可重写调用都是一个接缝，其启用点是对象创建或传递的位置
- 链接和导入接缝在构建或加载时交换实现——`jest.mock` 和 `unittest.mock.patch` 是现代服装中的链接接缝
- 预处理接缝（C/C++ 宏）是最粗糙的工具；最后再使用它们
- `new Database()` 在方法体内是一个从未构建过的接缝——执行实际工作的构造函数、全局变量、静态变量和硬编码的 I/O 是接缝死亡的地方
- 没有可到达的启用点的接缝是无用的：如果测试无法做出决定，请继续寻找
- 动态语言使几乎每个名称查找都成为接缝——便宜，但修补内部将测试与文件布局耦合

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 类构建自己的 DB 客户端 | 通过构造函数参数的对象接缝 | `constructor(db: Db = new ProdDb())` — 测试传递一个假 |
| 模块调用顶层 `send_email()` | 导入/链接接缝 | `mocker.patch("billing.send_email")` 或 `jest.mock("./mailer")` |
| 逻辑直接读取墙时钟 | 时钟处的接缝 | 注入 `now()` 提供程序；测试冻结时间 |

在在特定堆栈中寻找接缝时查看 [references/seams.md](references/seams.md)——接缝目录，包含代码、启用点和现代工具中的接缝（依赖注入容器、jest.mock、pytest monkeypatch、时钟和配置接缝）。

### 3. 特征化测试

**核心概念：** 特征化测试记录代码当前实际做什么——不是规范、注释或任何人的记忆所说的应该做什么。编写一个你知道会失败的探针，让失败消息揭示真实行为，然后更改断言以固定该行为。

**为什么有效：** 在遗留系统中，实际行为是事实规范：调用者、报告和客户可能依赖它，包括怪癖。从想象中的需求编写的测试会大声失败，而特征化测试会在重构期间精确地失败——就在你更改现有行为的时候。

**关键洞察：**
- 配方：在测试框架中调用代码，断言一些荒谬的事情（`expect(total).toBe(-1)`），读取失败，固定观察到的值
- 感知和分离是打破依赖关系的两个原因：分离将代码放入测试框架，感知让断言看到它计算了什么
- 对于复杂输出（报告、生成文件、大型 JSON），使用黄金主文件：一次捕获完整输出，永远与它进行比较
- 快照测试是黄金主文件——像代码一样审查第一个快照，并规范化易变数据，否则你正在固定噪声
- 在特征化过程中发现错误？用注释和工单固定它——下游代码可能依赖错误的行为；稍后作为有意、单独的更改修复它
- 特征化你的更改将触及的分支，而不是整个系统——覆盖范围跟随更改

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 重构税务计算器 | 针对代表性输入固定输出 | 运行 20 个案例，断言每个记录的结果 |
| 遗留报告生成器 | 黄金主文件差异 | 生成报告，与检查入的 主文件比较 |
| 在固定过程中发现溢出 | 固定错误的值，记录它 | `assert days == 30  # BUG? expected 31 — TICKET-482` |

在编写你的第一个探针到固定套件时查看 [references/characterization-tests.md](references/characterization-tests.md)——黄金主文件，正确执行的快照测试，以及工作前后重构。

### 4. 发芽和包装：首先没有测试进行更改

**核心概念：** 当你真诚地无法今天将区域置于测试之下时，不要将新逻辑编织到未测试的混乱中。发芽方法或发芽类：将新行为作为新鲜、完全测试的代码编写，并从遗留位置调用它。包装方法或包装类：将旧代码放在一边并重命名，在调用它的前面或后面添加行为，装饰器样式。

**为什么有效：** 即使其主机无法在测试框架中实例化，新代码在新鲜的方法或类中也可以是测试驱动的——测试性不再等待将主机放入测试框架。未测试的主机通过恰好一个调用位置更改，因此未验证的爆炸半径是一行而不是整个方法。

**关键洞察：**
- 当新逻辑在一个点插入时使用发芽方法；当主机类甚至无法在测试框架中实例化时使用发芽类
- 包装方法适用于围绕旧代码的行为（日志记录、通知、计量），而不是混合：将 `pay()` 重命名为 `rawPay()`，重新创建 `pay()` 作为包装器
- 包装类是装饰器模式——当几个调用位置需要添加行为或类已经臃肿时使用它
- 对权衡要诚实：主机保持未测试；你将良好的代码添加到了一个糟糕的区域
- 将发芽作为债务跟踪，并偿还它——下次更改到达那里时覆盖热点
- 发芽是更改算法中的一个战术移动，而不是永久替代获取代码进行测试

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 400 行的 `process()` 中的滞纳金规则 | 发芽方法，一个调用行 | `total += lateFee(order)` — `lateFee()` 先测试编写 |
| 遗留 `pay()` 周围的审计日志 | 包装方法 | 新的 `pay()` 记录，调用 `rawPay()`，再次记录 |
| 新验证，类无法实例化 | 发芽类 | `new OrderValidator().validate(data)` 从遗留代码调用 |

### 5. 依赖关系打破技术

**核心概念：** 一个机械、低风险的移动目录，切断所有阻止实例化或感知的东西：提取接口、构造函数参数化、方法参数化、提取并重写工厂方法或获取器、引入实例委托、适应参数、拆分方法对象、子类和重写方法。因为它们在测试存在之前运行，所以始终选择最侵入性的技术来解除阻塞。

**为什么有效：** 代码抵制测试的原因有一小集反复出现——构造函数执行实际工作、静态变量和单例、无法构造的参数、怪物方法。每个障碍都有一个命名的、实践的反向移动，因此你执行一个已知的动作，而不是对没有安全网的代码进行即兴手术。

**关键洞察：**
- 带有生产默认值的构造函数参数化是主力：现有调用者未经更改即可编译，而测试注入假
- 提取接口是书中最安全的移动——引入接口不能改变行为，只能放松类型
- 子类和重写方法构成了目录的一半：一个测试子类可以Stub 危险的部分，这是一个合法的工具，而不是黑客
- 对于静态变量和单例，引入实例委托向调用者提供了一个他们可以交换的实例；静态设置可以在测试中覆盖单例
- 适应参数击败了无法伪造的框架类型——将 `HttpServletRequest` 包装在你的窄接口中并针对该接口进行测试
- 动态语言有更便宜的接缝：`unittest.mock.patch` 或 `jest.mock` 可以代替几种技术，但参数化留下了更好的设计

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| 构造函数打开 DB 连接 | 构造函数参数化 | `def __init__(self, conn=None): self.conn = conn or connect()` |
| 每处都调用静态 `Billing.charge()` | 引入实例委托 | 实例 `charge()` 委托给静态；测试覆盖它 |
| 900 行的方法窃取本地变量 | 拆分方法对象 | `new RateCalculation(order, rates).run()` — 本地变量成为字段 |

在特定障碍阻止实例化或感知时查看 [references/dependency-breaking.md](references/dependency-breaking.md)——每个技术的 before/after 代码以及将障碍映射到正确移动的决策表。

### 6. 拆解和理解

**核心概念：** 在更改你不理解的代码之前，投资于廉价的 comprehension：效果草图跟踪更改可以影响什么，功能草图显示方法和字段如何在神类中聚集，抓挠重构意味着不顾一切地重构以学习和然后丢弃编辑，讲述系统的故事迫使简化摘要。回报是找到瓶颈——狭窄的地方，几个测试覆盖了广泛的行为。

**为什么有效：** 在遗留代码中，瓶颈是理解，而不是打字。效果草图将“这可能破坏什么？”从焦虑变为一个有限列表，并且瓶颈让一小部分测试作为夹钳覆盖整个方法集群——通常揭示隐藏的类边界想要在哪里绘制。

**关键洞察：**
- 效果草图：每个变量或方法一个气泡，每个“影响”一个箭头——从你的更改点向前跟踪行为可以泄漏到每个地方
- 瓶颈是效果草图中的狭窄处；在那里测试并覆盖它上游的一切
- 抓挠重构是将重构作为阅读技术：提取、重命名并简化一个小时，然后还原——洞察力在检出时幸存
- 怪物方法策略：在瓶颈处黄金主文件它，拆分方法对象，然后在新的类内部重构
- 神类策略：功能草图集群，然后沿着它们之间的自然边界提取
- 当没有时间时进行分诊：更改一次的地点获得发芽或包装；相同地点更改两次已经值得它的测试

**应用：**

| 环境 | 应用 | 示例 |
|------|------|------|
| “更改这个字段会破坏什么？” | 从字段向外的效果草图 | 三个读者找到；两个瓶颈测试覆盖它们 |
| 5,000 行类中的功能 | 瓶颈测试，然后发芽 | 覆盖 `postInvoice()`，发芽新规则作为类 |
| 团队中没有人理解代码 | 在分支上进行抓挠重构 | 提取和重命名以学习，还原，计划真正的移动 |

在想要一个完整的 worked walkthrough 时查看 [references/case-studies.md](references/case-studies.md)——三个场景：未测试的 800 行服务中的功能，被单例困扰的模块置于测试之下，以及在错误修复之前驯服怪物方法。

## 常见错误

| 错误 | 为什么失败 | 修复 |
|------|----------|------|
| 在一步中重构和更改行为 | 当某事破坏时，你无法知道是哪个编辑做的 | 分开提交；每一步之间测试变绿 |
| 在遗留代码上编写“应该”测试 | 想象中的规范会大声失败，而你“修复”了承重行为 | 特征化代码实际上做什么；单独提交错误 |
| 模拟一切可见的东西 | 测试固定了实现，所以每个重构都会破坏它们 | 仅伪造阻止实例化或感知的东西 |
| 大爆炸重构而不是增量覆盖 | 老系统一直在移动；重构交付晚，错过了多年的边缘案例 | 逐步覆盖并修改 |
| 沉默地修复在特征化过程中发现的错误 | 调用者和报告可能依赖错误的行为 | 固定它，记录它，作为单独的故意更改修复它 |
| 在任何测试存在之前进行侵入性清理 | 每个手动编辑都冒着没有净底下的行为风险 | 最侵入性的技术；保留签名；依赖编译器 |
| 无偿发芽 | 主机保持未测试，发芽会硬化成下一个遗留层 | 跟踪发芽债务；在下次接触时覆盖热点 |
| 等待专门的“测试项目” | 那个项目永远不会获得资金；覆盖范围永远不会出现 | 沿着每个你交付的更改增长覆盖范围 |

## 快速诊断

| 问题 | 如果没有 | 行动 |
|------|----------|------|
| 测试是否覆盖你即将更改的代码？ | 你在编辑和祈祷 | 运行更改算法；在编辑之前固定行为 |
| 你能在测试框架中构造这个类吗？ | 依赖关系阻止分离 | 构造函数参数化，提取接口，或发芽类 |
| 测试能否感知你更改的效果？ | 效果对断言不可见 | 找到一个感知点；提取并重写获取器 |
| 这个提交是行为仅还是结构仅？ | 混合的 | 分开它；在两个测试之间运行测试 |
| 你是否知道这次更改会影响什么？ | 未知爆炸半径 | 绘制效果草图；在瓶颈点测试 |
| 你的断言是否声明了观察到的行为？ | 测试愿望 | 探针，读取失败，固定实际值 |
| 你选择的接缝是否是最便宜的可用接缝？ | 不必要的手术 | 首先偏好构造函数参数和导入接缝 |
| 这次更改后代码的覆盖范围会更好吗？ | 下一次更改的成本与这次一样 | 在最近的测试点至少保留一个固定测试 |
