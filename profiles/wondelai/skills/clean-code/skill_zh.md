# 清晰代码框架

一种有纪律的编写代码的方法，能够传达意图，最小化意外，并乐于接受变更。在编写新代码、审查拉取请求、重构遗留系统或提供代码质量建议时，请应用这些原则。

## 核心原则

**代码被阅读的频率远高于被编写的频率——为读者优化。** 读写比例远超过10:1，因此每个命名选择、函数边界和格式化决策要么增加清晰度，要么增加成本。清晰代码读起来像精心撰写的散文：名称揭示意图，函数逐步讲述故事，并且适用童子军法则——始终保持代码比发现时更整洁。

## 评分

**目标：10/10。** 根据以下原则对任何代码进行0-10分的评分。报告当前分数以及达到10/10所需的特定改进。

- **9-10：** 名称揭示意图，函数小巧且专注，错误处理一致，测试清晰且全面
- **7-8：** 基本清晰，但有轻微的命名歧义或几个长函数；测试可能缺乏边界情况
- **5-6：** 混合——良好的模式与不清晰的名称、重复的逻辑或不一致的错误处理并存
- **3-4：** 长的多用途函数、误导性的名称、糟糕或缺失的测试
- **1-2：** 几乎无法阅读——魔法数字、神秘的缩写、没有结构、没有测试

## 清晰代码框架

编写清晰传达意图并能适应变更的代码的六个纪律：

### 1. 有意义的名称

**核心概念：** 名称应揭示意图，避免误导信息，并使代码读起来像散文。如果名称需要注释来解释，那么名称就是错误的。

**为什么有效：** 名称是最普遍的文档形式——一个精心选择的名称可以消除阅读实现的需求；一个糟糕的名称则迫使每个读者逆向工程意图。

**关键洞察：**
- 名称应回答其存在的原因、做什么以及如何使用
- 没有编码、前缀或类型信息（不使用匈牙利命名法）；只有对于小范围的循环计数才使用单个字母
- 类是名词；方法是动词
- 每个概念一个词：不要混合 `fetch`、`retrieve` 和 `get`
- 更大的作用域需要更长的、更描述性的名称
- 自由重命名——IDE使其变得非常简单

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **变量** | 揭示意图 | `elapsedTimeInDays` 而不是 `d` |
| **布尔值** | 谓词短语 | `isActive`、`hasPermission`、`canEdit` |
| **函数** | 动词 + 名词 | `calculateMonthlyRevenue()` 而不是 `calc()` |
| **类** | 命名责任 | `InvoiceGenerator` 而不是 `InvoiceManager` |

重命名或审查名称时，请参考 [references/naming-conventions.md](references/naming-conventions.md) —— 按语言约定的命名规范、可发音/可搜索的表格以及前后示例。

### 2. 函数

**核心概念：** 函数应该是小的、做一件事情并把它做好——理想情况下4-6行、零到两个参数、一个抽象级别。

**为什么有效：** 小的单用途函数易于命名、理解、测试和重用；长函数隐藏错误、抵制测试并积累责任。

**关键洞察：**
- 步降规则：代码自上而下读取，每个函数调用下一级别的抽象
- 参数数量：零最佳，一个可以，两个可以接受，三个以上需要说明理由
- 标志参数是有问题的——该函数做了两件事；把它拆分
- 命令-查询分离：改变状态或返回值，从不两者兼有
- 提取直到你放弃：如果你可以提取一个命名的函数，那就这么做
- 没有隐藏的副作用——名称必须说出全部真相

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **长函数** | 提取命名的步骤 | `validateInput(); transformData(); saveRecord();` |
| **标志参数** | 拆分为两个函数 | `renderForPrint()` / `renderForScreen()` 而不是 `render(isPrint)` |
| **错误情况** | 在顶部使用保护子句 | 早期返回错误，单一路径 |
| **多个参数** | 引入参数对象 | `new DateRange(start, end)` 而不是 `report(start, end, format, locale)` |
| **副作用** | 使效果显式化 | `checkPassword()` 启动会话 → 重命名或分离 |

拆分长函数时，请参考 [references/functions-and-methods.md](references/functions-and-methods.md) —— 参数数量规则、命令-查询分离和步降工作示例。

### 3. 注释和格式化

**核心概念：** 注释是未能用代码表达自己的失败。当注释是必要的时，它们解释的是*为什么*，而不是*什么*。格式化创建视觉结构，使代码可扫描。

**为什么有效：** 注释会腐烂——代码会变，但注释往往不会变，导致比没有更好的文档。清晰的格式化使开发人员能够像阅读报纸一样扫描代码：先看标题，按需查看细节。

**关键洞察：**
- 最好的注释是一个精心提取的函数
- 可以接受的：法律标题、TODO、公共API文档、真实的“为什么”解释
- 注释掉的代码和日记注释：删除——版本控制会记住
- 概念之间的垂直开放；概念内部的垂直密度；在用法附近声明变量
- 报纸隐喻：高级函数在文件顶部，细节在下面

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **解释“什么”** | 用更好的名称替换 | `// 检查是否符合资格` → `isEligible()` |
| **解释“为什么”** | 保留为注释 | `// RFC 7231 要求代理使用此标题` |
| **注释掉的代码** | 删除它 | 信任版本控制 |
| **团队格式化** | 一致后自动化 | Prettier、Black、gofmt |

决定是否需要注释时，请参考 [references/comments-formatting.md](references/comments-formatting.md) —— 好与坏的注释目录和垂直格式化规则。

### 4. 错误处理

**核心概念：** 错误处理与业务逻辑是分开的关注点。使用异常而不是返回代码，每次异常都提供上下文，并且永远不要返回或传递null。

**为什么有效：** 返回代码使快乐路径布满检查；异常清晰地分离了两者。返回null迫使每个调用者进行null检查，并且一个缺失的检查会在远离源头的位置崩溃。

**关键洞察：**
- 首先编写try-catch——它定义了一个事务边界
- 优先使用未检查的异常——检查的异常违反了开闭原则
- 根据调用者的需求定义异常类，而不是失败类型
- 不要返回null（使用空集合、Optional或抛出异常）；也不要传递null
- 特殊情况/空对象模式：返回具有默认行为的对象，而不是null

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **Null返回** | 空集合或Optional | `return Collections.emptyList()` 而不是 `return null` |
| **错误代码** | 替换为异常 | `throw new InsufficientFundsException(balance, amount)` |
| **第三方API** | 使用适配器包装 | `PortfolioService` 包装供应商API，转换其异常 |
| **特殊情况** | 空对象模式 | `GuestUser` 具有默认行为，而不是null检查 |
| **错误中的上下文** | 包括操作 + 状态 | `"Failed to save invoice #1234 for customer 'Acme'"` |

设计异常或null策略时，请参考 [references/error-handling.md](references/error-handling.md) —— 特殊情况模式和第三方API包装示例。

### 5. 单元测试

**核心概念：** 测试是一流代码，与生产代码使用相同的纪律来保持干净。脏测试比没有测试更糟糕——它们成为阻碍每次变更的负债。

**为什么有效：** 清晰的测试是可执行的文档和重构的安全网；脏测试使每次修改都变成通过难以理解的测试代码的战斗。

**关键洞察：**
- TDD的三大法则：首先编写一个失败的测试；只编写足够的测试来失败；只编写足够的代码来通过
- 每个测试一个概念——一个逻辑断言，不一定是每个断言
- F.I.R.S.T：快速、独立、可重复、自验证、及时
- 建立特定领域的测试语言：像DSL一样可读的帮助程序
- 像生产代码一样轻松重构测试代码

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **测试结构** | 安排-执行-断言 | 设置、执行、验证——清晰分离 |
| **测试命名** | 场景 + 预期行为 | `shouldRejectExpiredToken` 而不是 `test1` |
| **共享设置** | 构建器/工厂帮助程序 | `aUser().withRole(ADMIN).build()` |
| **易出错的测试** | 移除外部依赖 | 模拟时间、网络、文件系统 |

编写或清理测试时，请参考 [references/testing-principles.md](references/testing-principles.md) —— TDD法则、F.I.R.S.T扩展和清晰测试模式。

### 6. 代码异味和启发式方法

**核心概念：** 异味是更深层次设计问题的表面指示器——快速学会识别它们，并应用有针对性的重构，而不是模糊的“清理”。

**为什么有效：** 异味是启发式方法，它们指向可能的问题，而无需深入分析，将代码审查直觉转化为具体、可重复的操作。

**关键洞察：**
- 函数异味：太多参数、输出参数、标志参数、死函数
- 通用异味：重复、抽象层次不当、特征嫉妒、魔法数字
- 测试异味：覆盖率不足、跳过测试、未测试的边界条件和失败路径
- 小步、测试重构——永远不要同时重构和添加功能
- 童子军法则：保持代码比发现时更整洁

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| **重复** | 提取共享逻辑 | 常见验证 → `validateEmail()` 帮助程序 |
| **特征嫉妒** | 将方法移动到数据类中 | `order.calculateTotal()` 而不是 `calculator.total(order)` |
| **死代码** | 删除它 | 删除未使用的函数、不可达的分支 |
| **魔法数字** | 命名常量 | `MAX_LOGIN_ATTEMPTS = 5` 而不是裸 `5` |
| **散弹手术** | 合并相关变更 | 将分散的逻辑分组到一个模块 |

当异味难以命名时，请参考 [references/code-smells.md](references/code-smells.md) —— 按类别完整目录，每个都与其目标重构配对。

## 常见错误

| 错误 | 为什么失败 | 修复 |
|------|-----------|------|
| **缩写名称** | 编写时节省几秒钟，阅读时花费几小时 | 完整描述性名称；IDE自动完成 |
| **“聪明”的一行** | 写起来令人印象深刻，但难以调试 | 扩展为可读的命名步骤 |
| **用注释代替重构** | 注释会腐烂；代码是真相 | 提取一个命名的函数 |
| **捕获通用异常** | 沿着预期错误一起吞噬错误 | 捕获特定异常；让其余的传播 |
| **没有为错误路径编写测试** | 快乐路径工作，边界情况崩溃 | 测试每个分支、边界和失败模式 |
| **过早优化** | 隐藏意图以获得边际收益 | 先清理；优化测量的瓶颈 |
| **上帝类** | 一个2000行的类做所有事情 | 应用SRP——按责任拆分 |
| **没有测试的重构** | 没有回归的安全网 | 首先编写特征化测试 |
| **不一致的约定** | 每个文件都像不同的代码库 | 确定风格；使用linter和格式化器强制执行 |
| **到处返回null** | null检查像病毒一样传播 | Optional、空集合或空对象 |

## 快速诊断

| 问题 | 如果没有 | 操作 |
|------|---------|------|
| 能否在不阅读主体的情况下理解每个函数？ | 名称不揭示意图 | 重命名为描述它做什么 |
| 所有函数都在20行以下吗？ | 函数做了太多事情 | 将子操作提取为命名的帮助程序 |
| 没有注释掉的代码块吗？ | 死代码造成混乱 | 删除——版本控制有历史记录 |
| 错误处理与业务逻辑分开吗？ | try-catch使主流程混乱 | 提取处理程序；异常优于返回代码 |
| 每个类都有一个单一的责任吗？ | 类积累不相关的职责 | 拆分为专注、命名的类 |
| 每个公共方法都有一个测试吗？ | 没有变更的安全网 | 在进一步更改之前添加测试 |
| 测试名称是否描述了行为？ | 失败难以解释 | 重命名为 `shouldDoXWhenY` |
| 重复是否少于3次？ | 复制粘贴传播错误 | 提取共享逻辑 (§6) |
| 魔法数字是否为命名常量？ | 意图隐藏在原始值后面 | 命名常量 (§6) |
| 所有测试是否在10秒内运行？ | 慢测试不会运行 | 模拟外部依赖；拆分集成测试 |
