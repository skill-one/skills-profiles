# 重构模式框架

一种有纪律的方法，用于在不改变代码可观察行为的情况下改进现有代码的内部结构。每次重构都遵循相同的循环：验证测试通过，应用一个小的结构变化，验证测试仍然通过。

## 核心原则

**重构不是重写。它是一系列保持行为不变的小型行为保持转换，每个转换都有测试支持。** 你永远不会改变代码的功能——只会改变它的组织方式。大爆炸式重写失败是因为它们将结构变化与行为变化结合起来，使得无法知道哪些地方出了问题。

**基础：** 差劲的代码是在时间压力下交付的自然结果，而不是性格缺陷。代码异味是结构退化的客观信号；异味目录告诉你*在哪里*查找，重构目录告诉你*该做什么*。

## 评分

**目标：10/10。** 通过有多少个[快速诊断](#快速诊断)行通过来评估结构质量——`score = round(passed / 8 × 10)`，当单个异味严重时向下调整。等级：
- **9-10**：没有明显的异味，每个函数只做一件事，名称揭示意图，消除重复，条件语句在适当的地方使用多态，并且测试覆盖了重构的路径。
- **5-6**：还有一些异味（一个长方法，一些重复）但结构基本健全。
- **≤3**：普遍的异味——缠绕的条件语句，上帝类，到处都是重复——或者没有测试来安全地重构。

始终说明当前分数，命名导致分数下降的异味，并列出达到10/10所需的特定重构。

## 重构模式框架

六个系统地改进代码结构的重点领域：

### 1. 代码异味作为触发器

**核心概念：** 代码异味是更深层次结构问题的表面指示器——不是错误，而是设计使代码更难理解、扩展或维护的信号。每种异味都映射到命名重构来修复它。

**为什么有效：** 命名的异味为团队提供了客观标准，而不是主观的“我不喜欢这个”——“这是特征依赖”直接指向修复。

**关键洞察：**
- 异味分为五个家族：膨胀者、面向对象滥用者、变更阻止者、可省略者、耦合者
- 长方法是常见的异味；重复代码是最昂贵的
- 一个需要注释来解释它*做什么*的方法是一种异味——提取并命名这个块
- 霰弹手术（一个变更，许多类）和发散变更（一个类，许多变更原因）是责任错位的相反信号
- 原始数据狂热——原始字符串/整数而不是小的领域对象——会传播错误和重复

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 方法超过10行 | 提取方法 | 将循环体拉入`calculateLineTotal()` |
| 一个变更影响许多类（霰弹手术） | 移动方法/字段 | 将分散的行为集中到一个类中 |
| 许多方法使用相同的参数 | 引入参数对象 | `startDate, endDate` → `DateRange` |
| 复制粘贴的逻辑 | 提取方法 + 提取方法 | 通过公共方法或基类共享 |

当你需要命名一个异味及其修复时，查看[参考资料/异味目录.md](references/smell-catalog.md)——所有五个家族（膨胀者、OO滥用者、变更阻止者、可省略者、耦合者）及其检测启发式方法和每个重构映射。

### 2. 组合方法

**核心概念：** 大多数重构从这里开始：将长方法分解为更小、命名良好的部分，这些部分读起来像散文——高级步骤委托给命名清晰的助手。

**为什么有效：** 短方法具有揭示意图的名称，消除了注释，使错误一目了然，并支持重用；当名称说明一切时，方法调用读取成本为零。

**关键洞察：**
- 提取方法是唯一最重要的重构——首先掌握它
- 写注释的冲动？提取块并使用注释作为方法名
- 当方法体和名称一样清晰时，内联方法——没有价值的间接性就是噪音
- 使用查询替换临时变量来替换在多个地方使用的计算值；当一个临时变量服务于两个目的时，拆分临时变量
- 当局部变量太混乱无法提取时，使用方法对象替换方法——它们成为字段

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 带有注释的块 | 提取方法 | `// 检查资格` → `isEligible()` |
| 临时变量使用一次 | 内联变量 | 删除`const price = order.getPrice()` |
| 简单的委托方法 | 内联方法 | 如果使用一次，内联`return deliveries > 5` |
| 方法有许多缠绕的局部变量 | 使用方法对象替换方法 | 局部变量成为新类中的字段 |

当你应用任何方法级转换时，查看[参考资料/组合方法.md](references/composing-methods.md)——提取/内联方法的步骤和代码示例、提取/内联变量、使用查询替换临时变量、拆分临时变量和使用方法对象替换方法的代码示例。

### 3. 在对象之间移动功能

**核心概念：** 关键的面向对象设计决策是责任在哪里。当特征依赖、过度耦合或不平衡的类大小显示方法或字段在错误的类中时，将其移动到它应该去的地方。

**为什么有效：** 将方法放置在它使用的数据之外会创建看不见的跨类依赖，所以一个逻辑变更会波及许多文件——霰弹手术。将方法和数据放在一起将变更限制在一个类中。

**关键洞察：**
- 当一个方法使用另一个类的特性比它自己的更多时，移动方法；同样适用于移动字段
- 当一个类做两件事时，提取类沿着变更轴拆分；当类做得太少时，内联类
- 隐藏委托执行迪米特法则；当转发成为整个类时，移除中间人
- 按情况解决这个紧张问题：当链不稳定时隐藏委托，当它是纯转发时移除中间人

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 方法依赖另一个类 | 移动方法 | `calculateShipping()` 从 `Order` 移动到 `ShippingPolicy` |
| 上帝类500+行 | 提取类 | 将 `Address` 字段/方法拉入自己的类 |
| 客户调用 `a.getB().getC()` | 隐藏委托 | 添加 `a.getCThroughB()` |
| 类只转发调用 | 移除中间人 | 让客户直接调用委托 |

当你决定责任属于哪里时，查看[参考资料/移动功能.md](references/moving-features.md)——移动方法/字段、提取/内联类、隐藏委托和移除中间人的机制。

### 4. 组织数据

**核心概念：** 原始数据——魔法数字、暴露的字段、整型代码——会创建微妙错误并分散领域知识。用封装行为并强制不变的对象替换原始值。

**为什么有效：** 整数金额没有四舍五入规则或货币代码；`Money` 对象封装了所有这些，因此业务规则存在于一个地方，类型系统在编译时捕获错误。

**关键洞察：**
- 用符号常量替换魔法数字——最简单的数据重构；它命名意图
- 用对象替换数据值治愈原始数据狂热（`EmailAddress`、`Money`、`Temperature`）
- 封装字段和封装集合——永远不要暴露原始字段或可变的内部列表
- 当代码影响行为时用子类替换类型代码；用策略替换时子类化不切实际
- 当你需要身份语义时（一个共享的 `Customer`，而不是副本）将值改为引用

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| `if (status == 2)` | 替换魔法数字 | `if (status == ORDER_SHIPPED)` |
| `String email` 每处传递 | 用对象替换数据值 | `EmailAddress` 类带有验证 |
| 获取器返回可变列表 | 封装集合 | 返回 `Collections.unmodifiableList(items)` |
| `int typeCode` 带有 switch | 用子类替换类型代码 | `Employee` → `Engineer`、`Manager` |

当你用对象替换原始值时，查看[参考资料/组织数据.md](references/organizing-data.md)——用对象替换数据值、将值改为引用、替换魔法数字、封装字段/集合和替换类型代码的变体。

### 5. 简化条件逻辑

**核心概念：** 深度嵌套的 if/else 树、长 switch 和分散的空检查是最难阅读和最容易出错的代码。命名重构分解、合并并用更清晰的结构替换条件语句。

**为什么有效：** 六分支条件语句迫使读者在脑海中模拟每条路径；命名提取的分支是自我说明的，多态消除了“遗漏这个案例”的整个类别错误。

**关键洞察：**
- 分解条件：提取条件、then 分支和 else 分支到命名方法
- 合并条件表达式：将具有相同结果的相同条件合并为一个命名检查
- 用保护子句替换嵌套条件：提前处理边缘情况并返回，保持主路径不缩进
- 用多态替换条件是基于类型的条件黄金标准
- 引入特殊案例（空对象）消除了分散的 `if (x == null)` 检查；引入断言使假设快速失败

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 长的 `if` 带有复杂条件 | 分解条件 | 提取 `isSummer(date)` 和 `summerCharge()` |
| 深度嵌套的 `if/else` | 用保护子句替换 | 边缘情况首先，提前返回，扁平主路径 |
| 对象类型 switch | 用多态替换条件 | 每个类型实现自己的 `calculatePay()` |
| 到处都是 `if (customer == null)` | 引入特殊案例 | `NullCustomer` 带有安全默认行为 |

当你解开分支时，查看[参考资料/简化条件.md](references/simplifying-conditionals.md)——分解/合并条件的示例、保护子句、用多态替换条件、特殊案例和断言。

### 6. 安全重构工作流

**核心概念：** 重构只有在被测试包裹时才是安全的。工作流是机械的：运行测试（绿色），应用一个小变换，运行测试（绿色），提交。如果测试变红，则回滚——不要调试一个破败的重构。

**为什么有效：** 小步骤使失败显而易见（它是你最后做的事情），回滚成本几秒钟；调试失败的大爆炸式重写成本数天。

**关键洞察：**
- 三重规则：容忍重复一次，记录两次，第三次重构
- 准备性重构：重构以在添加功能*之前*使其容易；理解和捡拾垃圾重构在你阅读和触摸代码时保持代码改进
- 不重构的情况：重写更容易，没有测试并且添加测试不可行，或者代码将很快被删除
- 首先为清晰重构，然后分析并优化测量的瓶颈——清晰的代码更容易调整
- 通过抽象分支和平行变更实现生产中大型重构，无需长期分支

**代码应用：**

| 上下文 | 模式 | 示例 |
|--------|------|------|
| 即将添加功能 | 准备性重构 | 首先清理插入点 |
| 第三次相同逻辑的副本 | 三重规则 | 现在提取共享逻辑 |
| 生产中大型 API 变更 | 通过抽象分支 | 添加抽象层，迁移调用者，移除旧路径 |
| 重命名广泛使用的方法 | 平行变更 | 添加新的，弃用旧的，迁移，移除 |

在大型或风险重构之前，查看[参考资料/重构工作流.md](references/refactoring-workflow.md)——完整的绿色到绿色循环，何时（不）重构，性能，通过抽象分支和平行变更。

## 常见错误

| 错误 | 为什么失败 | 修复 |
|------|-----------|------|
| 没有测试的重构 | 没有安全网来检测行为变化 | 首先编写特征化测试 |
| 大爆炸式重写 | 混合结构和行为变化；无法调试 | 最小的可能步骤，每次步骤后都有测试 |
| 添加功能时重构 | 同时戴两顶帽子——两者都无法验证 | 首先重构（提交），然后添加功能（提交） |
| 没有更新调用者就重命名 | 构建中断或死代码 | 使用 IDE 重命名；搜索所有引用 |
| 提取太多微小的方法 | 当名称很差时，间接性没有清晰度 | 每个名称都必须消除阅读主体的需要 |
| 忽略异味目录 | 重新发明修复而不是应用经过验证的配方 | 学习命名异味；每个异味都映射到重构 |
| 重构注定失败的代码 | 在受诅咒的代码上抛光是无用的 | 检查代码的寿命是否值得投资 |
| 重构时优化 | 混合清晰度与性能 | 首先清晰，然后分析，然后优化热点路径 |

## 快速诊断

| 问题 | 如果没有 | 操作 |
|------|---------|------|
| 在你开始之前测试是否通过？ | 没有安全网 | 首先编写或修复测试——永远不会重构红色 |
| 你能命名你正在修复的异味吗？ | 直觉式重构，而不是目录 | 确定异味，应用其规定的重构 |
| 每个方法是否在 ~10 行以内？ | 长方法可能 | 提取方法到命名步骤 |
| 每个类是否只有一个变更原因？ | 分发变更或大型类 | 提取类以分离责任 |
| 是否有重复的代码块？ | 最昂贵的异味 | 将共享逻辑提取到公共方法/基类 |
| 条件语句是否在适当的地方使用多态？ | 仍然有 switch 语句 | 用多态替换条件 |
| 你是否在每一步后提交？ | 风险丢失工作，混合变更 | 每次绿色到绿色转换后提交 |
| 你的变更后代码是否更容易阅读？ | 重构增加了复杂性 | 回滚并尝试不同的方法 |
