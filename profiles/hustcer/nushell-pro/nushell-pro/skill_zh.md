# Nushell Pro

编写安全、规范、可移植且可测试的 Nushell 代码。将主要工作流保留在这个文件中；仅在任务需要时加载详细的参考。

## 操作工作流

1. 确定任务：新脚本、调试、审查、重构、模块设计、迁移、性能工作、安全审计或 Bash 转换。
2. 在更改代码之前，先阅读目标 `.nu` 文件、附近的测试、`AGENTS.md` 和现有项目约定。
3. 确定项目的 Nu 支持范围（从 CI、文档或项目配置获取）和活动的本地版本。不要假设本地二进制文件定义了兼容性目标。优先使用官方英文文档；翻译可能会滞后。当本地文档/源代码检出可用时，检查它们并将它们的修订版本与安装的 Nu 版本分开记录。从任何 shell 中，优先使用：

   ```console
   nu --version
   ```

   当已经进入 Nushell 或需要结构化版本数据时，使用：

   ```nu
   version | get version
   ```

4. 加载最小的相关参考集：

6. 在生成脚本首次实际运行之前，在预期范围内使用 `nu-check --debug`。对复杂的字符串/序列化负载断言精确输出，然后运行相关测试；仅解析无法检测到意外但有效的插值。使用 `--ide-check` 时需要结构化诊断。
7. 在样式和性能备注之前，报告安全/正确性发现。

## 跨领域约束

这些规则适用于所有任务类型。在依赖 Nushell 版本之间更改的语法或行为之前，加载路由的参考。

### 类型和管道契约

- 在 I/O 签名中声明管道输入，而不是作为位置参数。当必须重用 `$in` 时捕获它，因为流可以是单次通过的。
- 类型导出命令参数和输入/输出签名。
- 将外部/配置记录视为不可信的；使用可选访问，例如 `$record.field?` 并验证结果类型/值。
- 记住 `default` 会立即评估其后备参数。当它可能失败或成本高昂时，使后备参数 null 安全或显式分支。
- 保持返回类型一致。除非函数确实多态，否则避免使用 `any`。
- 仅当 CLI 必须保留调用者的标记拼写而不是应用 Nushell 字面量强制时，在 `main` 参数上使用 `external_arg`。它在 Nu 0.115 中产生 `glob`/`list<glob>` 值，因此在使用它们作为结构化应用程序数据之前进行验证或转换。
- 优先使用 `match` 对一个值进行多个分支；使用 `if` 对一次性布尔谓词。

### 外部命令和错误

- 将外部参数作为单独的值传递，而不是作为插值的命令字符串。当状态重要时，使用 `complete` 并检查 `exit_code`。
- 优先使用 `try/catch` 和 `$err.details` 进行结构化进程内错误。
- 在 Nu 0.115 中，跨度的 `error make` 标签具有形状 `{text: ..., span: {start: ..., end: ...}}`。不要使用过时的扁平 `{text, start, end}` 形式。
- 在 Nu 0.115.0 中，直接嵌套在具有 `catch` 处理程序的外部 `try` 内部的 `try/finally` 会静默跳过内部 `finally`。给外部块添加 `finally`，或将内部一个放在 `do`/命令边界后面，并断言拥有的状态已消失。
- 将渲染的嵌套-Nu 诊断视为呈现文本，而不是稳定协议。对于 CLI 测试，在匹配长而特定领域的短语之前，规范化 ANSI 样式、缩进和 PTY 包装。

### 安全停止检查点

在批准执行命令、删除文件、读取凭证或接受路径/模式之前，确认这些边界：

- 不要将不受信任的字符串传递给 `nu -c`、`source`、`run`、`^sh -c`、`^bash -c` 或 `^cmd.exe /C`。
- 将外部命令参数作为单独的值传递，而不是插值的 shell 命令字符串。
- 对于现有路径限制在基本目录的情况，展开路径并使用 `path relative-to` 证明包含。字符串 `starts-with` 检查是不安全的，因为 `/safe/base2` 以 `/safe/base` 开头。
- 优先使用 Nu 的内置 `mktemp`/`mktemp --directory`；它是可移植的，并直接返回路径。不要使用可预测的临时名称。
- 使用 `with-env` 范围化密钥；当存在 stdin/配置文件机制时，不要记录它们或将它们传递在 argv 中。
- 保护破坏性路径免受 root、`$nu.home-dir`、意外类型和不受信任的通配符的影响。考虑 TOCTOU 和部分成功行为。

对于尚不存在的输出路径，使用相同的包含规则验证现有父目录，然后仅连接验证的叶名称。

### 字符串和格式化

- 优先使用简单的字面量和原始正则表达式字符串；仅在需要实际转义时使用双引号。
- 记住 `$'...'` 会插值但不会处理转义序列。
- **在插值中直接内嵌的 `(` 需要使用 `$"..."`。** 由于 `$'...'` 不进行转义处理，它内部的每个 `(` 都会打开一个插值表达式，`\(` 无法阻止这一点。编写 `$"\(abc)($var)"`，而不是 `$'\(abc)($var)'`。失败通常是静默的而不是错误：`$'(1 + 1) items'` 评估为 `2 items`。参见 [字符串格式](references/string-formats.md)。对于具有许多分隔符的生成代码，连接纯字面量片段和序列化数据。
- 在解释器之间保持代码和数据分离：将 argv/stdin/JSON 传递给固定程序。如果 API 仅接受源，使用固定、受信任的模板并使用目标语言序列化；单个 argv 字符串在接收工具评估时仍然是代码。不要将原始值连接到源。
- 使用 kebab-case 命令/标志，snake_case 变量/参数，SCREAMING_SNAKE_CASE 环境变量。

### 数据格式和分组

- `from xml` 丢失 XML 命名空间身份（在 Nu 0.115.1 中重现）：它仅存储元素和属性的本地名称，结果中没有命名空间 URI 或声明。例如，`<x xmlns:r="urn:r" id="plain" r:id="rel"/>` 变为一个仅包含 `id: rel` 的 `attributes` 记录；反向两个属性会导致 `id: plain`。当本地名称冲突时，后续属性会覆盖先前的属性。不要使用此记录进行命名空间敏感的 XML 查找、编辑或往返。使用命名空间感知的 XML 解析器，或者当 `query xml` 插件可用时，使用带有 `--namespaces` 的 XPath（当名称重要时使用 `--output-names`）。匹配命名空间 URI 加上本地名称，而不是前缀拼写。
- Nu 0.115 使 `from yaml` 默认为 YAML 1.2，具有严格的非字符串键和标签。当输入契约由其他系统控制而不是继承默认值时，固定 `--spec`、`--multiple`、标签处理和键解析。
- 让 `to yaml` 默认拒绝不可逆的值。只有在数据丢失是文档合同的一部分时才退出，并引用值：`--non-roundtrip 'null'`。裸 `null` 是解析错误，`--non-roundtrip 'lossy'` 在 0.115.0 上被 `to yaml` 拒绝，因此当确实需要损毁编码时使用 `--serialize`。
- `group-by` 记录输出不能表示空键，并在 Nu 0.115 中省略该组。使用 `group-by --to-table` 当必须保留或区分空字符串的空组时。

### 数据流和性能

- 优先使用管道和不可变的 `let` 绑定。
- 使用 `where`、`select`、`update`、`insert`、`items`、`transpose`、`reduce` 和 `enumerate` 而不是手动解析和可变累积。
- 不要在闭包中捕获 `mut` 变量。
- `for` 适用于顺序副作用，但不是转换表达式；当需要列表结果时使用 `each`。
- 仅当并发安全且有益时使用 `par-each`；当顺序或顺序副作用重要时保留 `each`。
- 在预期逐行流解析时，在 `parse` 之前添加 `lines`。
- 优先使用直接行条件对 Nu 0.115 上的简单 `any`/`all` 谓词；当谓词需要设置、解构或重用时保留闭包。
- 使用原生表格处理小型交互式数据，使用 Polars 处理大型列式分组/连接/聚合工作负载。

### 模块和脚本

- 仅导出预期的 API；保持帮助程序为私有。
- 当命令应与模块名称匹配时，使用 `export def main`。
- 使用 `def --env`/`export def --env` 进行调用者可见的环境更改。
- 不要以解析器关键字命名命令、别名、模块或导出。还将 `$ans` 视为 Nu 0.115 中的保留；重命名旧的 `ans` 绑定。
- `source`、`use` 和 `run` 目标必须是受信任的，并且在解析时可用。
- 在正确的接缝处进行测试：直接函数用于稳定的结构化错误，CLI 子进程用于参数解析/过程边界，当需要时两者都使用。

## 审查顺序

在审查代码时，按以下顺序报告发现：

1. 安全：注入、遍历、凭证、破坏性操作、临时文件、环境中毒。
2. 正确性：类型、空值处理、解析时约束、退出代码、清理/回滚、数据格式合同、平台/版本行为、稳定测试。
3. 可维护性：命名、模块边界、重复、文档。
4. 性能：流式传输、不必要的集合、安全并行性、Polars。

除非工具输出显示它们当前失败，否则跳过项目格式化器/检查器已强制执行的问题。

## 验证

对于普通脚本/模块验证，优先使用 `nu-check --debug`。它在不运行目标顶层命令的情况下解析，并报告解析时类型错误以及语法错误。使用匹配的解析模式：

```bash
nu --no-config-file -c 'nu-check --debug path/to/script.nu'
nu --no-config-file -c 'nu-check --debug --as-module path/to/module.nu'
nu --no-config-file path/to/test-script.nu
```

- 没有 `--debug`，无效内容返回 `false`，周围的 `nu` 进程仍然可以退出 `0`；显式消费布尔值。使用 `--debug` 时，解析错误会抛出，因此未捕获的失败会退出非零。缺失文件是错误。这两种模式都无法证明运行时正确性或提供沙盒。
- 在检查具有相对导入的保存脚本时，直接传递文件路径。将其文本管道到 `nu-check` 检查匿名源；可选路径在管道输入存在时无法恢复文件的导入上下文。
- 对于需要跨度和诊断记录的编辑器/CI 集成，使用 `nu --no-config-file --ide-check 100 path/to/script.nu`。
- `--ide-check` 在 stdout 上发出 JSON Lines，并且当记录具有 `type: "diagnostic"` 和 `severity: "Error"` 时可能仍然退出代码 `0`。它还在目标文件不存在时以空输出退出 `0`，因此在将空结果视为通过之前验证路径是否存在。使用 `from json` 解析每一行非空；不要单独使用进程退出代码。
- 将 `severity: "Error"` 诊断视为阻止器，表面其他严重性（如 `Warning`）而不阻止，忽略 `type: "hint"` 记录。将非零退出代码或 stderr 作为 CLI 启动或 I/O 失败单独处理。
- 优先使用 `--no-config-file` 进行可重复的独立检查。当脚本有意依赖于用户配置中的命令或环境时，省略它，并记录该依赖性。
- `source` 执行顶层代码；它不是语法检查。仅当有意加载经过审计的定义/设置时使用它。使用 `nu-check`/`--ide-check` 验证有副作用的脚本，然后在拥有的临时固定装置中执行。在保存结构化值时，使用公认的数据扩展名或在 `save` 之前显式序列化（`to json`、`to yaml`、`to nuon` 等）。
- 在 Nu 0.115+ 中不要使用 `nu --testbin`。使用 Nushell 本身或目的构建的测试固定装置重新创建所需行为。
- 在涉及诊断或表格的情况下，在窄 PTY 下重现终端敏感测试，例如 `stty cols 24 && nu tests/example.nu`。
- 在完成之前检查调试标记和意外更改。
- 如果验证失败，修复最小的可重复问题，并在扩展测试套件之前重新运行确切的失败命令。
