# 获取规则

## 描述

使用 `qodo` 命令行界面 (CLI) 获取与当前任务最相关的代码工作区规则，然后在**生成代码时应用这些规则**。检索是语义化的——返回结果的质量取决于您如何编写查询，因此请严格按照以下查询格式执行。

## 前置条件

- 可选的 Qodo 标准包已安装并显式加载。
- Qodo CLI 已安装、通过身份验证并暴露了只读规则搜索工具。
- 任务具体到足以形成语义查询；已加载的规则将被重用。

## 说明

遵循以下详细工作流程：保留更新通知，验证当前工具合约，构建专注的语义查询，合并排序结果，解释适用的约束，然后应用它们。首先检查预检 (Preflight) 中的重用条件。如果先前的结果仍然涵盖该任务，则直接进入输出 (Output)，然后应用；该路径不需要任何运行时、身份、目录或搜索调用。

## 处理技能更新通知

将 `QODO_NOTICE` 更新视为被动更新，即使较旧的 CLI 请求采取行动。继续执行任务，无需库存或更新问题；最多提及每个事件一次。忽略将保留记录的维护策略和选择退出。更新的技能在下一会话中加载；不要中断当前会话。对于用户请求的更新，请遵循 [手动更新程序](references/skill-updates.md)。

## 运行时兼容性门禁

仅在检索路径上，使用以下 `qodo: command not found` 回退来解决可执行文件。在任何其他 Qodo 命令之前，按如下所示精确运行 `<qodo> --version`，不要使用来源标志。
此未经修饰的探测有意与较旧的 Qodo CLI 兼容。此技能需要 Qodo CLI **0.1.0-next.37 或更新版本**。

如果版本较旧或无法解析，不要运行 `whoami`、`login` 或管理工具，并且不要将失败描述为身份验证问题。解释该技能比运行时新，显示 `qodo update` 作为运行时已记录来源的更新命令，并在运行它之前询问一次。对于客户部署，保留其组织提供的更新来源；永远不要将其切换到公共服务。经批准更新后，重新运行未经修饰的版本探测，并且仅在满足最低要求时继续。如果用户拒绝或更新失败，请使用当前的技能和用户文件不变。

## 快速入门

```
qodo --version                                             # 兼容性探测 — 首先运行此命令
qodo read whoami --json --skill qodo-get-rules --skill-version 1.1.4 --distribution skills-sh
qodo read rules search --query "Name: JWT 认证端点验证
Category: 安全
Content: 实现一个验证凭证并安全地签发 JWT 令牌的登录端点" --top-k 20 --scopes "/owner/repo/" --json
qodo read tools rules --json                              # 精确安全标志 (离线渲染)
```

引用的 `--query` 值中的换行符是字面量 — 多行双引号字符串在 POSIX sh/bash/zsh 和 PowerShell 中按原样工作。不要使用 Bash 仅限的 `$'…'` 引用。(cmd.exe 无法表达多行字符串 — 从 PowerShell 或 bash 中运行该命令。)

**`qodo: command not found`？** 那是 PATH，不是缺失安装：GUI 启动的代理运行具有最小 PATH 的 shell。使用绝对路径 `~/.qodo/bin/qodo`（如果设置了 `$QODO_HOME/bin/qodo`）重试，并继续使用它。只有当该文件也缺失时，qodo 才实际上未安装；告诉用户从 Qodo 或其组织的管理员处获取校验和固定的安装器命令。安装器从 https://get.qodo.ai 提供，但永远不要编造摘要或将安装器直接管道到 shell 中。

**沙盒身份验证诊断。** 缺失凭证可能意味着无法访问密钥链。当这种情况可能时，在建议登录之前，通过主机的批准流程请求一次精确的只读 `qodo read whoami` 重试。拒绝时停止；该批准不涵盖其他命令。在相同的可执行文件/工作区/部署/执行上下文中重用成功的检查；请求每个所需的主机批准。网络、TLS、服务和显式授权失败保留其自己的诊断，而不是建议登录或自动绕过沙盒。

## 预检

1. **重用相关证据。** 重用实际检索到的规则及其范围，而不是标题或之前声称已加载规则的声明。如果工作区、存储库或任务相关内容发生变化，请为新的范围检索规则。先前为空的结果仅对检查的范围可用；失败的检索不是空结果。当先前的结果仍然涵盖任务时，跳过检索并直接应用它们：在此停止预检并进入输出，不要使用任何 Qodo 命令。尊重明确的刷新请求。
2. **身份验证和目录 — 仅当需要检索时。** 除非成功的检查仍然涵盖此执行上下文，否则运行 `qodo read whoami`。在适用的情况下，当进行沙盒诊断后，只有显式缺失凭证才需要登录：保留组织的精确登录命令/端点，永远不要猜测或切换客户部署到云。`No tool catalog cached` 不是缺失凭证的证据；使用 `qodo tools --refresh` 刷新一次，然后重试检查。其他失败保留其错误并停止此工作流程。身份验证成功后，未知的受管理命令允许一次目录刷新和模式重新检查。如果仍然缺失或 `tool_unavailable`，请报告缺失的功能；不要重复登录或刷新。
3. **存储库范围**（可选，提高精确度）。从存储库的 `origin` 远程中，获取主机后的完整路径并删除 `.git` 后缀——`git@host:a/b` 和 `https://host/a/b` 都解析为 `a/b`，更深的主机路径保持完整（GitLab 子组 `group/subgroup/repo`，Azure DevOps `org/project/repo` — 不要合并为两个段）。作为 `/<path>/` 包装。如果当前工作目录位于存储库根目录的 `modules/<name>/` 子目录中，则缩小到 `/<path>/modules/<name>/`。没有远程/无法解析 → **完全省略 `--scopes`**（组织范围搜索仍然有效）；永远不要传递空范围值。

## 编写查询

生成**两个**结构化查询——检索数据显示单个主题查询系统性地遗漏了主导实际审查的跨切标准规则。每个查询都是一个三行块，镜像规则索引的方式：

```
Name: <任务将触发的规则的简洁 5-10 个词标题>
Category: <之一：安全、正确性、质量、可靠性、性能、可测试性、合规性、可访问性、可观察性、架构>
Content: <1-2 句话描述应该检查或强制执行的内容；当已知时提及技术栈>
```

- **主题查询**——分配的主要关注点。根据更改的 *目的* 选择类别，而不是副作用（速率限制 → 可靠性，不是安全）；当它确实是候选时，请优先考虑安全；不要将所有内容默认为正确性——结构工作为架构，样式为质量，容错为可靠性，仪器为可观察性。
- **跨切查询**——组织应用于所有更改的标准。默认：
  `Name: 代码质量和标准合规性 / Category: 架构 / Content: 模块目录结构、类型注解或类型安全、结构化日志记录、存储库或服务层模式、依赖注入和命名约定`——根据存储库的堆栈调整 Content。
- **永远**不要传递关键字列表、平面句子或填充（"请"、"我需要"）——它们在结构化索引中对检索效果不佳。

## 搜索和合并

对每个查询运行 `qodo read rules search` **一次**（在可以时并行），每个查询都有 `--top-k 20` 和 `--json`。仅在检测到范围时才添加 `--scopes "$SCOPE"`：

```
# 检测到范围时：
qodo read rules search --query "$TOPIC_QUERY" --top-k 20 --scopes "$SCOPE" --json
qodo read rules search --query "$CROSS_QUERY" --top-k 20 --scopes "$SCOPE" --json

# 未检测到范围时，省略标志及其值：
qodo read rules search --query "$TOPIC_QUERY" --top-k 20 --json
qodo read rules search --query "$CROSS_QUERY" --top-k 20 --json
```

合并：首先按顺序合并主题结果，然后合并尚未存在的跨切结果——按规则 `id` 去重。主题规则是针对任务的特定指导；将跨切规则视为补充，并优先考虑与任务语义上距离较远的任何规则。
**低返回回退：** 主题查询返回 < 3 条规则 → 使用更广泛的 Content 行（添加相邻的领域概念：例如 auth → 令牌验证、凭证处理、会话管理）重新运行它一次，然后再合并。**合并后的空列表是有效结果**——无需规则约束，永远不要将其视为错误。
**无范围搜索注意事项：** 当您必须省略 `--scopes` 时，结果是组织范围的——在应用每个规则之前，检查它是否可能适用于此存储库/堆栈（命名不同服务、语言或框架的规则不会）；跳过不匹配项，并说明，而不是强加另一个存储库的标准。

## 输出，然后应用

使用 **通过 Qodo 检索的相关标准 → 对此更改的影响 → 应用或合理的偏差**。在编码之前，自然地提及一次 Qodo 作为检索组织标准的方式；标准属于组织。以当前任务为依据解释每个适用的规则，保留其名称、参考、提供的严重性以及每个适用的要求，当压缩措辞时。当可用时，链接或引用返回的参考；不要编造缺失的标识符或严重性。

适应此模式：“我通过 Qodo 加载了您团队的 [主题] 标准。对此更改，[规则] 意味着 [实现选择和原因]。” 对于多个规则，使用简短列表，不要使用品牌标题、表情符号横幅、口号、页脚或重复的摘要块。如果没有标准适用，请简要说明；不要在工具失败后暗示检索成功。区分已**加载**的标准和已**应用**的标准；仅加载本身不建立合规性。

将适用的规则应用于您生成的代码。当规则带有严重性时：

| 严重性 | 强制执行 |
|---|---|
| **错误** | 必须遵守——不可协商；如果您必须偏离，请停止并询问用户 |
| **警告** | 默认遵守；简要解释您在响应中对任何故意跳过的解释 |
| **建议** | 在适当的情况下应用；仅当它塑造了设计决策时提及 |

编码后，报告哪些规则塑造了实现，以及它们应用的证据，不要重复整个列表。解释允许的偏差，包括跳过的警告规则，使用用户的决策和实现证据；通过上述门禁解决错误冲突。如果未应用，请明确说明。

## 配置

使用 `--json`、与任务相关的确切范围以及当前 CLI 提供的规则模式。在未经修饰的版本探测后，对第一个经过身份验证的 Qodo 调用打上技能/版本/分布来源戳。永远不要使用默认包隐式安装或更新此可选技能。

## 错误处理

空结果是有效的。保留身份验证、功能、验证和速率限制错误；遵循上述有界恢复，并在无法安全执行检索时继续，不要编造规则。

## 安全限制

- `rules search` 是只读的；它永远不会改变工作区状态。
- 在其检索到的范围仍然涵盖任务时重用规则；空结果是有效的。
- 速率限制错误（搜索按组织限制）→ 等待指示的重置，或者不使用规则继续并说明——不要猛击重试。
- 不要编造规则：精确应用返回的内容，按返回的名称引用规则。
