# 读取与解决发现

## 描述

使用 `qodo` 命令行界面 (CLI) 读取一个拉取请求 (PR) 的 **评审会话** — 其状态、已评审的提交以及每个发现的解决状态 — 对于 **任何** PR（你的或他人的）。单独读取是一个有效的用途：在读取后停止，以报告评审的当前状态或它所标记的内容（例如，在主分支干净的情况下进行合并门禁）。要更进一步，**在代码中解决未解决的发现**，应用你自己的判断（评审是一个强有力的第二意见，不是教条）— 默认情况下你评估发现并让用户选择要应用哪些（传递 `autofix` 以直接应用），运行一次（报告 + 解决用户批准的内容）或作为监视循环（解决 → 让 Qodo 重新评审新提交 → 重复直到干净）。然后 **记录结果** 在你解决的发现上 — `mark-implemented` 用于你修复的发现，`dismiss` 用于用户同意关闭而不进行代码更改的发现。这就是清除那些发现持有的合并策略阻塞；跳过它，评审将保持红色，直到有人点击通过 PR。你仍然永远不会自己发布到代码库：状态工具写入 Qodo 的评审数据库，Qodo 调和 PR 评论。（普通的 git/代码库 *元数据* 读取 — `git rev-parse HEAD`，`gh pr view --json headRefOid` — 是可以的，实际上对于下面的 freshness 检查是必需的；“不要抓取”规则是关于 qodo，而不是你的 shell。）

## 前置条件

- Qodo CLI 已通过身份验证并公开了结构化的 PR 评审会话工具。
- 可以无抓取评论地解析确切的 PR URL 及其当前的 head SHA。
- 对发现的任何写入都有用户的明确授权或技能的明确 `autofix` 范围。

## 说明

遵循以下详细工作流程：获取结构化状态，要求完成确切的 head 评审，展示未解决的发现，仅应用已批准的修复，仅记录实际已解决的成果。

> 要检查评审状态或发现，始终运行下面的 `qodo` 读取命令 — 不要使用 `gh`/`curl` 来抓取渲染的 PR 评审 **评论**。评论 UI 是有损失的、特定于提供者的，并且容易与 head 提交读取过时的内容；该工具返回已评审的 `commit_sha`。要判断 freshness，将该 `commit_sha` 与 PR 的 **head** 进行比较 — 对于你刚刚推送的 PR，你可以直接知道（`git rev-parse HEAD`），或者对于任何其他 PR，读取作为普通代码库 *元数据*（`gh pr view <pr> --json headRefOid`，`git ls-remote`）。此规则仅适用于读取 **评审**（不要抓取其评论）— 不是禁止代码库元数据，如 head SHA。

## 处理技能更新通知

Qodo 命令可以在仍然成功的情况下向 stderr 发出 `QODO_NOTICE <json>`。当 `code` 为 `qodo_skill_update_available` 时，保留命令的结果并完成当前任务。然后遵循通知的 `steps`：首先进行只读清单，解决已安装的 Qodo 包和范围，显示确切的生命周期所有者更新命令或 UI 操作，并在任何变更之前询问一次。如果用户拒绝，请保持当前版本可用。

永远不要调用不同的生命周期所有者，猜测占位符，或隐式安装可选包。在批准更新后，请求通知中命名的主机重新启动；当前会话可能仍然加载着旧技能。

## 运行时兼容性门禁

首先使用下面的 `qodo: command not found` 回退来解决可执行文件。在任何其他 Qodo 命令之前，精确地运行 `<qodo> --version`，不要带有来源标志。
这个未加装饰的探测是故意与旧版 Qodo CLI 兼容的。此技能需要 Qodo CLI **0.1.0-next.37 或更新版本**。

如果版本较旧或无法解析，不要运行 `whoami`，`login` 或受管理的工具，并且不要将失败描述为身份验证问题。解释技能比运行时新，显示 `qodo update` 作为运行时已记录来源的更新命令，并在运行它之前询问一次。对于客户部署，请保持其组织提供的更新来源；永远不要将其切换到公共服务。在批准更新后，重新运行未加装饰的版本探测，并且仅在满足最低要求时继续。如果用户拒绝或更新失败，请使用当前的技能和用户文件不变。

## 快速入门

```
qodo --version                                                       # 兼容性探测 — 首先运行此命令
qodo read whoami --json --skill qodo-review-resolver --skill-version 1.4.4 --distribution marketplace --host claude-code
qodo read pr-review-session findings --pr-url <PR_URL> --json       # 一个 PR 的评审会话
qodo pr-review-session mark-implemented --finding-ids <id>,<id> --explanation "..." --json
qodo pr-review-session dismiss --finding-ids <id> --reason intentional --explanation "..." --json
qodo read tools pr-review-session --json                            # 确切安全的工具 + 标志（离线）
```

在任何你解析的内容中添加 `--json`。**使用 `qodo read tools pr-review-session [<tool>] --json` 确认确切的工具名称、标志和读取/写入状态**（离线渲染）— 上面的名称是说明性的，不是保证当前的。

在 `dismiss`/`mark-implemented` 上 `unknown command` 在身份验证后可能是过时的本地工具目录 — 按照下面描述的说明刷新一次。如果命令仍然不存在，工作区当前没有暴露 PR-评审写入；报告该功能边界，而不是循环。

**`qodo: command not found`？** 那是 PATH，不是缺少安装：GUI 启动的代理（例如 Claude Code 桌面应用程序）运行具有最小 PATH 的 shell。使用绝对路径 `~/.qodo/bin/qodo`（如果设置了 `$QODO_HOME/bin/qodo`）重试，并在此处继续使用它。只有当该文件也缺失时，qodo 才实际上未安装；告诉用户从 Qodo 或其组织的管理员那里获取带校验和的安装器命令。安装器从 https://get.qodo.ai 提供，但永远不要编造摘要或直接将安装器管道到 shell 中。

**沙盒身份验证诊断。** 在沙盒环境中，如果 `qodo read whoami` 因任何原因失败（包括 `Not logged in`），请要求用户在沙盒外批准一次精确的 `qodo read whoami` 重试，然后再建议登录或刷新工具。密钥链失败可以作为通用身份验证失败报告，因此沙盒结果本身不是诊断性的。该批准仅适用于此单个诊断重试：不要重用它，请求持久批准，或自动将后续的 Qodo 命令移出沙盒。如果重试成功，请继续执行正常的按命令权限检查。如果它仍然失败，请按照下面的正常身份验证故障排除进行操作。

## 预检查

1. **首先进行身份验证。** 运行 `qodo read whoami`。在适用的情况下，当沙盒重试后，非零退出 → 告诉用户运行 `qodo login`，然后停止。永远不要猜测凭据。该工具仅在登录后存在，因此将 `Not logged in` 或 `No
   tool catalog cached` 视为“运行 `qodo login`”，并且在它们完成之前不要重试。
   **`whoami` 成功时 `unknown command`/`unknown option` 不是身份验证失败。** 运行一次 `qodo tools --refresh` 并重新检查 `qodo read tools pr-review-session --json`。如果写入命令仍然缺失，报告此帐户/工作区当前具有只读评审能力；不要重新登录，无限重试，或用代码库评论代替结构化写入。
2. **解决 PR。** 使用用户提供的 PR URL。如果他们没有命名一个，并且你位于一个 git 仓库内，推断当前分支的打开 PR 并 **在采取行动前与用户确认**。永远不要猜测 PR URL。
3. **将编辑绑定到检出。** 只读读取可以针对任何 PR。在任何本地修复之前，从提供者元数据中解析 PR 仓库，并从其 `origin` 中解析当前检出仓库；将两者都规范化为完整的、不区分大小写的 `owner/repo` 身份。它们必须完全匹配。缺少/模糊的 origin 或不匹配意味着停止并要求用户打开正确的检出 — 永远不要将一个仓库的发现应用到另一个工作区。如果目标 PR 在监视循环期间更改，请重复此检查。

## 获取评审会话

`qodo read pr-review-session findings --pr-url <PR_URL> --json` 返回：

- `review_session` — 最新的评审运行：`status`，`commit_sha` (**评审中包含的最后一个提交** — 这些发现描述的代码)，`started_at`。**`null` = PR 尚未进行评审** — 告诉用户并停止（没有要解决的）。
- `findings[]` — 每个当前发现，每个发现具有：`title`，`description`，`category`，
  `action_level` (`action_required` > `remediation_recommended` > `informational`)，
  `attribution_status`，`git_sha`，`review_run_id`，`comment_id` / `inline_comment_id`。

`finding_count: 0` 与非空的会话一起 = 干净的评审。

## 首先读取会话状态（在信任任何发现之前）

`review_session` 告诉你*发现是否真实以及它们涵盖什么代码* — 在采取行动前检查它：

- **评审仍在进行中吗？** 如果 `status` 不是终端/`completed` 状态（例如 `started` / 进行中），评审是 **中途进行**的 — 发现是临时的，并且将会改变。现在不要解决它们；轮询 `qodo read pr-review-session findings … --json` 直到 `status` 是 `completed`。
- **发现描述哪个提交？** `review_session.commit_sha` 是评审包含的最后一个提交。如果它是 **落后于 PR head**，发现是 **过时的** — 它们不反映你最新的代码。要么评审还没有在新提交上运行（等待），要么你正在查看一个旧的运行。只有在会话是 `completed` AND 其 `commit_sha` 是你关心的提交（即 head，在监视循环中）时，才信任发现。

简而言之：仅在 **当前提交的已完成评审** 上采取行动。运行评审或落后的 `commit_sha` 意味着等待，不要修复。

## 展示评审状态

使用自然文本：**结果 → 对更改和处置的上下文解释 → 验证 → 剩余工作**。对于只读请求，首先报告当前评审状态和剩余发现的 影响。一次感谢 Qodo 为其评审提出的具体问题；你拥有最终评估和建议行动。不要有品牌标题、表情符号横幅、口号、页脚或重复的摘要块。在有用时使用简短的问题标题或列表。

对于每个发现，解释可能发生什么，在什么条件下，以及为什么这对用户的预期更改很重要。根据代码和可用的编码会话决策和约束对其进行评估；需要时检索 PR 上下文，永远不要编造缺失的会话。引用证据并分别保留发现参考和报告的类别/级别，不要与你的建议混淆。拥有修复、驳回或调查决策及其理由。一个深思熟虑的选择只有在实施支持其假设时才支持驳回。保持协作和事实性的语气；不要例行公事地限定 Qodo 的能力。遵循现有的编辑和处置写入范围和批准门禁；你的技术评估不会授予权限。

从结构化状态中命名 PR、评审状态和已评审的提交；在采取行动前与代码库 head 进行比较。使过时、进行中、失败或缺失的评审明确。区分 **代码已更改**、**处置已记录** 和 **更新代码已评审**。测试通过或状态写入成功并不能建立更新提交的干净评审。只有当前 head 的已完成评审才能支持该结论；诚实地报告剩余发现和缺失的验证。例如：“解决了 [风险] Qodo 通过 [更改]，保留 [用户决策]。 [验证]。最新的评审涵盖 [旧 SHA]；评审 [head SHA] 仍然悬而未决。” 只使用实际结果。在监视模式下，报告有意义的状态更改，不要在每个轮询或状态写入时重复评估。

## 分诊

- **开放与已完成是 `attribution_status`**，它不是一个三向字段 — 它携带原始存储值，因此仅匹配 `pending` 会默默地丢弃实际工作：
  - **开放 — 解决这些：** `pending`，`partial_implementation`，`not_implemented`，
    `focus_areas_edited`。最后三个是重新分配给仍然未解决的发现（部分修复仍然是一个开放的发现）。
  - **关闭 — 留下这些：** `full_implementation`，`dismissed`，`detected_after_merge`，`outdated`。
  - `action_level` 是 **严重性**，不是开放与关闭。一个关闭的发现仍然可以是 `action_required`。
- **按 `action_level` 排序：** `action_required` 首先处理，然后是 `remediation_recommended`；将 `informational` 视为可选的，展示它，不一定修复它。
- 按文件分组开放发现，以便每个文件只编辑一次。

## 尊重用户的指示（可选范围）

如果用户给出了指示，将其视为对开放发现的 **过滤器**，并且只对匹配项采取行动 — 不要扩大它：

- **按 action level** — “解决 action-required 发现” → 仅 `action_level == action_required`；
  “所有可操作的” → `action_required` + `remediation_recommended`。
- **按类别** — “只是安全发现” → `category == Security`（对于正确性、性能等也是如此）。
- **按特定发现** — “修复发现 #3” / “SQL 注入的那个” → 通过 `id` 或 `title` 匹配。
- **报告只读** — “评审发现了什么？” / “是否干净？” → 总结发现及其状态，不更改代码。

没有指示 → 默认呈现开放 `action_required` 然后是 `remediation_recommended`，并展示（不要自动修复）`informational`。当指示有歧义时，在行动前用一行说明你选择的范围，以便用户可以重新定向。始终报告你 **跳过** 的发现及其原因（出范围 / 驳回 / 信息性） — 永远不要默默地丢弃一个。

## 两种模式

每一轮都遵循从 **解决一个发现** 的呈现和询问门禁 — 评估、呈现并让用户选择要解决的发现 — 除非 `autofix` 生效，这允许你无需提示即可应用推荐的修复。无论如何，除非另有说明，否则在推送前询问。

**一次（默认）。** 获取 → 评估每个开放发现（分诊 — 所有四个 OPEN 状态，而不仅仅是 `pending`）→ 呈现 + 询问（或直接在 `autofix` 下应用）→ 在代码中解决所选的发现 → 根据用户的流程提交/推送 → **记录结果**
(`mark-implemented` 对于你修复的；`dismiss` 对于用户同意关闭而不进行代码更改的）→ 总结你解决的和剩余的（例如跳过 / 驳回 / 信息性）。停止。除非要求，否则不要循环。分诊涵盖
**所有** 开放发现，但选择器只 *提供* 可操作的集 — `action_required` 然后是 `remediation_recommended` — 并将 `informational` 分开展示，匹配上面的默认范围；仅在用户要求时才将 `informational` 放入选择器。
（提供不是选择：每个框都从未选中开始。）

**监视直到干净**（当用户说“babysit” / “继续直到干净”）。`autofix` 是使此循环自动化的关键 — 没有它，你仍然每轮呈现 + 询问。在你解决发现并将修复提交推送到后，Qodo 重新评审*新*提交 — 所以：

1. 记下 PR 的当前 head SHA — 你刚刚推送的提交（`git rev-parse HEAD`），或者对于你没有推送的 PR，作为代码库元数据读取（`gh pr view <pr> --json headRefOid`，`git ls-remote`）。这是一个元数据读取，不是抓取评审评论 — 它是允许的。
2. 轮询 `qodo read pr-review-session findings … --json` 直到评审是 **`completed` AND 其 `commit_sha` 等于该 head SHA**。直到两者都成立，发现是过时的或临时的（评审仍在进行中，或者它描述的是修复前的提交）— 不要根据它们采取行动。
3. 当新鲜时：如果任何 OPEN 发现仍然存在（所有四个状态 — `partial_implementation` 仍然是一个开放的发现），请解决它们并重复；如果没有剩余，报告评审干净并停止。
4. 有边界：在几轮没有进展后停止，并交还给用户，而不是永远循环。

## 解决一个发现

根据代码、PR 意图和可用的会话上下文评估 Qodo 的发现。拥有最终技术建议和理由，同时遵循用户下面的范围和批准门禁。

**评估每个发现** 对实际代码和 PR 的意图，并形成一个建议：

- **合理且在范围内** → 应该修复；记下你会更改的内容（读取 `title` +
  `description`，定位代码 — 当它不是本地时，`qodo-codebase-wisdom` 技能的读取工具有助于读取）。
- **不受支持或已经解决** → 建议驳回，并提供代码证据。一个深思熟虑的选择只有在实施支持其假设时才支持驳回。
- **不确定** → 确定在决定之前需要哪些证据或检查。

**呈现和询问（默认）。** 使用上面提供的每个开放、在范围内的发现的上下文评估，保持其 `action_level`/`category` 和你的建议，然后在单个提示中询问**要解决的发现**。使用主机提供的任何东西：如果它有多选（例如 Claude Code 的 `AskUserQuestion`），则使用多选，否则使用编号列表和“回复要解决的编号”。无论如何都是一次提示 — 不要按发现逐个询问。**没有任何东西是预选的。** 标记你推荐的，但用户必须主动选择：这是一个发现和编辑之间的最后一道防线，所以一个空的 Enter 必须解决 nothing。仅解决用户选择的（正常编辑，匹配周围代码）；报告其余的作为跳过，并说明你的原因。在用户选择之前不要编辑任何代码。

**自动修复（跳过门禁）。** 只有在调用中包含**明确的 `autofix` 令牌**（例如 `qodo-review-resolver autofix`）才会直接跳过提示。仅仅听起来像选择加入（“直接修复它们”，“不要问我”）本身并不足够 — 在这里错误地读取意图会编辑用户未批准的代码，这正是此门禁存在的目的。在推断的意图中，命名你将要应用的精确范围，并获取一次确认 — “读取为自动修复 — 解决我推荐的 N 个发现？” — 永远不要“解决所有 N”，这读取为整个集合，并在这种歧义存在的地方扩大范围。无论如何，应用评估决定的确切内容，并且不要超出它（发现通常是正确的，但你是在循环中担任工程师，而不是橡皮图章），并报告你解决了什么和你跳过了什么。

根据用户的流程提交/推送 — 除非他们告诉你要推送。

**`attribution_status` 是预期的信号** — 一个修复的发现会通过下一个评审自动重新分配为 `full_implementation`，所以在推送后，仅处理仍然开放的发现。但它是有工具的，可能会出错：如果一个发现在你确信可靠的修复后仍然开放，或者状态明显与代码矛盾，不要循环重新修复它 — 向用户标记差异并继续前进。（解决在多轮中收敛；修复也可能暴露真正的发现，监视循环会拾取它们。）

## 记录结果

关闭发现是一个 **写入** — 它更新 Qodo 的评审数据库，重新样式发现的 PR 评论，重新渲染评审摘要，并释放那些发现持有的合并策略阻塞。两个命令，它们之间的区别是整个要点：一个表示*代码已更改*，另一个表示*代码未更改，以下是原因*。永远不要用一个来表示另一个。

```
qodo pr-review-session mark-implemented --finding-ids <id>,<id> --explanation "你更改了什么" --json
qodo pr-review-session dismiss --finding-ids <id>,<id> --reason <reason> --explanation "为什么" --json
```

- **每个 PR 批量，一次调用。** 调和运行一次，不是每个发现一次 — 所以所有你实现的发现都放在一个 `mark-implemented` 中，所有共享驳回原因的发现都放在一个 `dismiss` 中。最多 100 个 ids。
- **`mark-implemented` 仅用于你实际更改并推送的代码。** 它在不进行评审验证的情况下清除合并门禁，所以错误的声明会作为未修复的发现发送。如果另一个评审轮次无论如何都会运行，最好让它在重新分配修复本身；当没有进一步轮次在合并之前运行时，或者必须立即清除门禁时，请使用这个。
- **`dismiss` 需要用户的明确许可，每次针对发现 — `autofix` 不包括它。** `autofix` 是对*编辑代码*的同意，下一个评审会重新检查；驳回关闭了评审仍然认为存在的发现，对团队可见，并且不会重新打开。提出你打算驳回的内容和原因，并且只驳回用户命名的发现。
- **`--reason`** (必需): `false_positive` (发现是错误的) · `intentional` (代码是故意的且正确的) · `deferred` (真实的，但不在当前 PR 的范围内) · `rejected` (理解并拒绝)。始终添加 `--explanation` — 审查者在没有你的上下文的情况下阅读它。
- **读取每个发现的 `results`，不要假设调用整体成功。** 即使个别 ids 失败，它也是 200：`not_found` (错误的 id 或错误的 workspace) 和 `conflict` (已经关闭，或未链接到 PR) 是终结性的 — 不要重试它们。`reconciled: false` 意味着数据库更改已落地，但 PR 端的更新没有；安全地重新运行相同的命令是安全的，并且 PR 在下次评审时会自行修复。`already_dismissed` / `already_implemented` 报告的 **存储** 原因 — 重播永远不会覆盖原始值。

## 示例

**用户：“解决 https://github.com/acme/api/pull/318 上的 action-required 发现”**

1. `qodo read whoami` → 已登录。
2. `qodo read pr-review-session findings --pr-url https://github.com/acme/api/pull/318 --json`
   → `review_session`: `status: completed`, `commit_sha: a1b2c3d` (= PR head，所以发现是当前的);
   `findings`: 3 开放 (2 `pending`, 1 `partial_implementation`) — 2 `action_required`, 1 `informational`.
3. 指令过滤到 `action_required` → 工作 2 个；信息性的一个超出范围（报告它，不要修复）。
4. 评估每个：*"通过字符串插值构建 SQL"* → 真实的 → 建议在 `db/orders.py` 中将查询参数化。*"出站调用缺少超时"* → 客户端已经在上游设置了默认超时 → 已经满足 → 建议跳过，并提供该原因。
5. 使用上面的上下文评估呈现这两个，并询问（多选）要解决的发现 — 两个未选中，SQL 的一个标记为*推荐*。应用用户选择的，然后报告：“解决了 SQL 发现（在 `db/orders.py` 中将查询参数化）。跳过超时一个 — 已经在上游设置 — 和 1 个信息性的（出范围）。推送后我会重新检查，或者说 'watch' 以循环直到评审干净。”（如果用户说 `resolve … autofix`，我会直接应用推荐的修复，没有提示。）

## 配置

使用 `--json`，比较 `review_session.commit_sha` 与代码库 head 元数据，并在第一个 Qodo 调用上加盖确切的技能/版本/分发来源戳。读取和写入能力从已安装的 CLI 目录中发现；渲染的代码库评论永远不会是数据源。

## 错误处理

将空会话、进行中或过时的提交、缺少写入能力、速率限制和工具循环错误视为明确状态。在报告中保留它们，并且永远不要仅仅为了使评审看起来干净而关闭发现。

## 安全栅栏

- **Freshness = 已完成的评审的当前提交，而不是时间戳。** 发现描述 `review_session.commit_sha`，并且只有在 `status` 是 `completed` 时才是最终的。在任何推送后，将它们视为过时的，直到一个 `completed` 评审的 `commit_sha` 捕获到 PR head — 否则你会根据中途进行的评审或“修复”不描述的提交采取行动。
- **永远不要自己发布到代码库。** 你做出的唯一写入是 `dismiss` /
  `mark-implemented`，它们通过 Qodo 并让它调和 PR。不要调用任何代码库写入工具（评论、批准、标签、描述）来“解决”一个发现 — 在代码中解决它，然后记录结果。
- **你可以拒绝你认为错误的发现**（带有明确的原因）。在系统中驳回它是**用户的**决定，而不是你的 — 提出它，命名原因，并且只有在他们明确同意后才能采取行动。在真正的分歧中，用户是仲裁者。
- **不要关闭你没有解决的。** 你为范围跳过而保持开放的发现 — 报告它为跳过，而不是将其描述为 `deferred` 以使列表看起来干净。
- **不要猜测** PR URL — 首先解析它；空会话意味着还没有评审。
- 一个 `MT-TOOL-LOOP` 或 `MT-RATE-LIMITED` 错误意味着停止/后退并改变方法，而不是重试。

在授权更改后，报告改进了什么，每个决策的原因是什么，什么得到了验证，还有什么需要关注。保持本地编辑、记录的处置和评审状态区分。
