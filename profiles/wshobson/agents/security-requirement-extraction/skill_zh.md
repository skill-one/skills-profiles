# 安全需求提取

将威胁分析转化为可执行的安全需求。

## 使用此技能的场景

- 将威胁模型转换为需求
- 编写安全用户故事
- 创建安全测试用例
- 构建安全验收标准
- 合规性需求映射
- 安全架构文档

## 核心概念

### 1. 需求类别

```
业务需求 → 安全需求 → 技术控制
         ↓                       ↓                      ↓
  "保护客户数据"    "静态PII加密"    "使用KMS密钥轮换的AES-256加密"
```

### 2. 安全需求类型

| 类型               | 重点                   | 示例                               |
| ------------------ | ----------------------- | ------------------------------------- |
| **功能性**     | 系统必须做什么     | "系统必须验证用户"      |
| **非功能性**     | 系统如何执行     | "验证必须在<2秒内完成" |
| **约束**     | 施加的限制     | "必须使用批准的加密库"  |

### 3. 需求属性

| 属性        | 描述                 |
| ---------------- | --------------------------- |
| **可追溯性** | 链接到威胁/合规性 |
| **可测试性**  | 可以验证             |
| **优先级**     | 业务重要性         |
| **风险等级**   | 未满足时的影响           |

## 最佳实践

### 应该做

- **追溯到威胁** - 每个需求都应该映射到威胁
- **保持具体** - 模糊的需求无法测试
- **包含验收标准** - 定义"完成"
- **考虑合规性** - 早期映射到框架
- **定期审查** - 需求随威胁演变

### 不应该做

- **不要泛泛而谈** - "要安全"不是需求
- **不要省略理由** - 解释其重要性
- **不要忽视优先级** - 并非所有需求都同等重要
- **不要忘记可测试性** - 如果你无法测试它，就无法验证它
- **不要孤立工作** - 邀请利益相关者
