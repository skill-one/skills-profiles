# 检查点推广

整个插件的第5阶段门：一个干净训练且超越任务指标的检查点，仍然需要在通过以下四个阶段后才能发布。
`eval-harness-first`构建了在此处重新运行的套件——这项技能取决于该套件的基线来决定某些事情。

**输入：** 一个训练好的检查点，来自`eval-harness-first`的`eval/baseline-<model>.json`，以及冻结的`eval/drift-suite.yaml`。
**输出格式：**
`promotion-report.md`——四个阶段的证据，以及一个终端的`PROMOTE`或`REJECT`裁决，`/finetune`第5阶段和`/promote-checkpoint`直接使用。

## 四阶段门

每个阶段控制下一个阶段——第2阶段的失败意味着第3阶段不会运行。第2阶段和第3阶段共享一次昂贵的推理过程，因此并发运行它们并在裁决时间应用门顺序是在**确定性**的竞技场（通过序列化不会保存任何东西）；基于裁判的竞技场仍然应该先等待第2阶段——这才是真正的节省之处。

1. **数据质量门。** 在任何评估接触检查点之前：去重训练集，检查评估黄金数据泄漏（`trace-to-training-data`的Hygiene部分存在的确切失败是为了防止这种情况），并扫描标签噪声。在泄露的黄金数据上训练的检查点使所有后续阶段无效。
2. **保留+冻结的能力漂移套件。**
   重新运行`eval-harness-first`的`eval/drift-suite.yaml`——MMLU/GSM8K/IFEval加上200-500个领域相邻的项目——针对检查点，并与`baseline-<model>.json`根据以下漂移预算表进行差异比较。
3. **配对竞技场与基准。**
   位置随机化的裁判，检查点与基准模型，相同的提示——或者当竞技场中的所有评分器都是确定性时（没有LLM裁判；位置随机化在那里不适用）的`references/gate-templates.md`中的确定性配对比较变体。
   **一个保留阶段的胜利如果在实时竞技场中失败则不会发布**——第2阶段的数字和第3阶段的判断必须一致；在冻结的黄金数据上获胜而在配对比较中失败是一个真实的信号，而不是一个需要解释的差异。
4. **金丝雀测试。** 5-10%的分层发布，对任何达到生产流量的检查点进行自动回滚。**仅限本地用户在第3阶段停止**——为本地部署跳过第4阶段是正确的停止点，而不是捷径。

### 漂移预算

| 漂移（分） | 裁决 |
|---|---|
| ≤1 | 噪声——继续 |
| 2-5 | 在决定之前使用种子变化重新运行 |
| >5 | **硬失败**——任务收益没有例外 |

>5分行不受其他行的影响：一个检查点在目标任务上获得了8分，但在一般能力上失去了6分，仍然在这里失败——任务改进永远不会弥补漂移预算的违规行为。

**项目数量来自预算，而不是便利性：** 对于半宽低于5分硬失败阈值的一半的严格n在典型精度下（p≈0.7）约为1300；n=200是一个务实的底线（在该相同p下±6分半宽，n=50 ±13分）——报告半宽，并将小于它的余量视为`REJECT (不确定)`，而不是PASS/HARD FAIL。完整的数学和5次运行的警告示例：
`references/gate-templates.md`。

**RERUN不是裁决。** 一个2-5分的漂移只有在种子变化重新运行完成后才会产生`PROMOTE`或`REJECT`——`PROMOTE`要求回到≤1分（噪声）；任何重新运行仍然>1分——2-5分范围或>5分违规一样——都将第2阶段解决为硬`REJECT`。没有报告可以到达裁决部分而第2阶段仍然显示`RERUN`。

## 灾难性遗忘

未管理的LoRA微调会失去真正的通用能力，而第2阶段会捕获它：

- **~43%的无管理知识损失**——没有重放，没有正则化。
- **基本管理下~10%**——一些重放或保守的LR。
- **重放+EWC下~3%**——自律的情况。
- **10-30%的通用数据重放混合是标准的缓解措施**——将通用域数据混合到训练中，而不是仅针对目标任务数据。

如果一个检查点在第2阶段遇到>5分的硬失败，请按顺序处理这个升级楼梯——这是这项技能和`references/gate-templates.md`都指向的唯一规范顺序：

1. **调整重放混合比例——交换行，不要添加它们**（添加会使比例与总优化器步数混淆）。在小规模运行（<~100步）下，剂量不是单调的——交换后重新检查漂移。
2. **降低学习率。**
3. **更少的周期。**
4. **一个更小的LoRA秩**——相同的秩/LR杠杆`lora-qlora-recipes`和`preference-optimization`在训练运行中调整，这里反向应用。

这个顺序是一个默认值，不是一个法律：**来自单个前后运行对的补救指导是一个假设**——一旦任何杠杆产生逆转，就将其标记为低置信度，并优先选择种子变化重复而不是盲目信任下一个环节。
一个杠杆清除了漂移违规，但将成功标准指标降至目标以下，对人类来说是一个两面的权衡，而不是继续下降楼梯的理由。完整的推理和两个警告背后的5次运行轨迹：
`references/gate-templates.md`。

**披露漂移套件指令重用。** 一个重放行复制了漂移竞技场的确切指令措辞（而不仅仅是分离的源项目），使得该基准的后重放分数是一个上限——在将其视为干净之前，将其标记为指令熟悉，或用释义重新探测。

## 裁决

`promotion-report.md`作为部分涵盖所有四个阶段，**必须以终端裁决结束：`PROMOTE`或`REJECT`**，产生它的证据，以及当裁决为`REJECT`时，恰好一个顶级补救措施。
模板：`references/gate-templates.md`。
终端合同其他技能解析：

```
## 裁决

REJECT

证据：领域相邻的漂移套件下降了6.2分（阈值：>5分硬失败），尽管目标任务上获得了8分。

顶级补救措施：将重放混合比例从10%调整到20%，保持步数恒定。
```

- **REJECT是一个结果，不是一个错误。** 一个在第2阶段的漂移预算或第3阶段的竞技场比较中失败的检查点完成了它的任务。不要将REJECT视为一个需要重新运行此技能的失败运行；它是工作门的正确输出。
- **一个补救措施，不是一个菜单。** 证据部分可以列出所有观察到的内容；裁决部分根据上述升级楼梯命名每个最高杠杆的修复。一个跨三个可能修复的报告中没有完成这项技能存在的优先级。
- **没有自动重新训练。** 此技能产生一个裁决和一个报告，而不是重新触发的训练运行。一个`REJECT`将补救措施交还给`finetuning-method-selection`或相关训练技能的人类决策。

## 相关技能

- `eval-harness-first` — 拥有漂移套件和基线，此技能重新运行并与它们差异比较；没有`baseline-<model>.json`意味着没有要门控的东西。
- `quantized-export` — 在`PROMOTE`裁决之后唯一的合法下一步。
- `preference-optimization`和`lora-qlora-recipes` — 拥有在灾难性遗忘升级路径中的LR和秩杠杆；此技能诊断违规行为，这些技能拥有导致它的配置。
- `dataset-curation` — 拥有重放混合构建配方，升级楼梯的第一步应用。

完成`promotion-report.md`模板，包含所有四个阶段，漂移套件评分表，配对竞技场协议（项目数量，位置随机化，获胜率阈值），以及重放混合配置示例：
`references/gate-templates.md`。
