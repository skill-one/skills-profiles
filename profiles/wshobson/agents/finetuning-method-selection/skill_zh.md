# 微调方法选择

这是微调生命周期中的路由技能：它决定是否微调是合适的工具，如果是，则选择哪种方法和哪种基础模型大小类别。本插件中的其他所有技能都假设路由已经完成——在打开 `lora-qlora-recipes`、`preference-optimization` 或 `grpo-rlvr-training` 之前，请从这里开始。

## 何时使用此技能

- 在选择框架或基础模型之前开始任何微调工作。
- 不确定 RAG 或提示工程是否比训练更经济地解决问题。
- 在同一底层任务中，选择偏好优化（DPO 系列）和强化方法（GRPO/RLVR）之间的方法。
- 在提交运行之前确定候选模型/方法组合的大小。

## 快速参考

| 情况 | 路由 |
|---|---|
| 事实经常变化（价格、文档、新闻） | RAG，不是微调 |
| 期望行为仍在确定中 | 提示工程 |
| 稳定的领域知识，≥500MB 文本 | CPT 然后是 SFT — 见 Off-Ramps First |
| 有输入/输出演示 | SFT — 见 `lora-qlora-recipes` |
| 有偏好对或点赞/点踩 | DPO/ORPO/KTO — 见 `preference-optimization` |
| 有可验证的成功/失败信号 | GRPO+RLVR — 见 `grpo-rlvr-training` |
| 尚未准备评估工具 | 停止 — 见 `eval-harness-first` |

## Off-Ramps First

大多数听起来像“微调这个”的请求在其他地方服务得更好、更便宜。在开始训练运行之前，请检查这些 Off-Ramps：

- **知识绑定且易变**（差距是变化的事实——价格、文档、时事）：路由到 RAG，而不是微调。微调模型固化了一个快照；易变的事实会立即过时。
- **行为绑定且变化**（期望行为仍在确定中，或按请求变化）：路由到提示工程。微调锁定了一个行为；不要锁定一个尚未稳定的行为。
- **稳定、密集的领域知识**：这是持续预训练（CPT）进入的地方，其大小由存在的领域文本量决定：

| 领域文本量 | 路由 |
|---|---|
| <10MB | 仅 RAG |
| 10MB–500MB | RAG + 微调 |
| 500MB–10GB | CPT，然后是 SFT |
| >10GB | 需要 CPT |

CPT 学习率 ≈ **预训练 LR 的 10%**。在本插件中，CPT 仅作为指导——大小和 LR 指导位于此处，但本插件不执行 CPT 运行。

## 方法路由器

一旦排除了 Off-Ramps，这就是完整的决策树（逐字逐句来自构建此插件的研究）：

```
新 FACTS?  易变 → RAG | 稳定+密集 → CPT (LR ~预训练的 10%) → SFT
新 BEHAVIOR? 变化 → 提示工程 | 稳定:
  演示 → SFT (LoRA/QLoRA, 所有线性, α=2r)
  偏好对 → DPO (如果长度偏差则为 SimPO，如果内存绑定则为 ORPO)
  未配对 👍/👎 → KTO
  可验证的成功 → RLVR + GRPO (按失败模式为 DAPO/GSPO/Dr.GRPO)
部署：FP8 (Hopper+) | NVFP4 (Blackwell 规模) | AWQ (旧版) | GGUF+imatrix (边缘)
在任何这些之前：评估工具必须先存在。
```

自上而下阅读这棵树：回答“新事实或新行为”，然后跟随与手中数据形状匹配的分支（演示、偏好对、点赞/点踩，或可验证的成功/失败）。数据形状选择方法——而不是反过来。

### 已路由示例

- *"用户希望助手完全遵循我们的支持宏。"* 行为是稳定的，并且可以从转录中演示 → 演示 → **SFT**。
- *"我们有一对好的/坏的回复，来自评审员的点赞/点踩，未配对。"* → 未配对信号 → **KTO**，而不是 DPO（DPO 需要配对的偏好）。
- *"模型已经可以解决其中的一些数学问题，我们可以自动评分正确性。"* → 可验证的成功信号 → **GRPO+RLVR**，并且只有在确认模型至少有时成功后（见下文关键路由事实）。
- *"我们希望模型知道本周的定价页面。"* → 易变的事实 → **RAG**，根本不进行训练运行。

## 关键路由事实

- **损失函数选择是低杠杆的**。一项 240-H100 运行研究发现，方法选择值约 1 个百分点，而模型规模值约 50 个百分点，并且 20 个 DPO 变体中没有一种优于原味 DPO。不要在路由决策中纠结于 DPO 变体选择——将精力放在确保数据形状和规模正确上。
- **DPO 是为了口味，GRPO+RLVR 是为了推理**。编码主观判断（语气、风格、“哪个答案更好”）的偏好对路由到 DPO。具有可验证的成功/失败信号的任务（数学、代码、工具调用）路由到 GRPO+RLVR。
- **RL 不是解决从未成功的模型的修复方法**。GRPO 和其他 RL 方法磨利了现有能力——它们不会从零开始教一个。如果模型还不理解任务或输出格式，请先运行 SFT；只有在模型至少有时成功后，才引入 RL。

### 常见路由错误

- 使用微调来修复每周变化的事实——这是一个 RAG 问题，微调会比源数据更快过时。
- 在检查实际瓶颈是数据质量还是模型规模之前选择 DPO 变体——变体选择是 ~1pp 杠杆，而不是 ~50pp 杠杆。
- 在模型每次运行都失败的情况下开始 RL 运行——首先路由到 SFT，以便 RL 有东西可以磨利。
- 将 CPT 视为“模型不知道我们的领域”的默认选项——首先检查数据量阈值；低于 500MB，RAG 或 RAG+微调的迭代比 CPT 运行更快。

## 模型选择

基础模型选择首先是大小类别，其次是系列，并且很快就会过时——因此它只存在于一个地方：`references/model-catalog.md`。该文件是本插件（以及 DGX Spark ops 插件）中唯一命名基础模型系列的文件。此技能和 `references/memory-math.md` 都不命名一个；两者都仅按大小类别描述模型（例如，“8B 类别的 LoRA”，而不是模型名称）。

目录故意有日期——模型排名每季度都会变化。它包含一个“最后验证”日期和刷新检查清单。在信任一行之前，请检查该日期；如果过时，请在推荐其模型之前在目录中执行刷新检查清单。

**当目录和方法技能不一致时的优先级**：目录的每行注释列声明硬件/大小类别的可行性，而不是方法建议——`lora-qlora-recipes` 的 LoRA 与 QLoRA 与全 FT 表（按任务形状路由）控制实际方法选择。

## 内存可行性

在提交方法之前，请调整大小：总内存 ≈ **params × dtype 字节 + 优化器状态 + 梯度 + 激活**。为所选 dtype 和方法（全微调、LoRA 或 QLoRA）计算每个项——工作表格和大小类别示例位于 `references/memory-math.md`。

在 DGX Spark 特定情况下，统一内存行为会破坏简单估计（瞬态负载峰值、`nvidia-smi` 低报、长时间运行的热量节流）。一旦安装了 `dgx-spark-ops` 插件，将 Spark 特定可行性调用推迟到其 `spark-memory-thermal-ops` 技能，而不是在这里重新推导。

## 相关技能

一旦此技能选择了方法，就将其交给执行该方法的技能：

- `lora-qlora-recipes` — 通过 LoRA/QLoRA 进行 SFT
- `preference-optimization` — DPO、ORPO、KTO
- `grpo-rlvr-training` — 具有可验证奖励的 GRPO

在任何方法被选中之前，评估工具必须存在——见 `eval-harness-first`。
