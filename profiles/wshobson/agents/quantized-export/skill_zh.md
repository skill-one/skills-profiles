# 量化导出

`checkpoint-promotion` 的最后一步会给出一个 `PROMOTE` 的判定：一个通过了四阶段门槛的检查点仍然需要在其目标运行时所需正确格式的导出中才能部署，并且需要证明导出后仍然可以正常工作。`REJECT` 判定永远不会到达这一步——导出只从被提升的检查点开始。

**输入：** 一个被提升的检查点（或 LoRA 适配器）以及目标部署表面——GPU 等级、服务堆栈，以及是否包含长上下文/代码/数学工作负载。

**输出格式：** 在选定格式的导出工件加上一个比较导出前 3-5 个黄金输出与导出后的烟雾测试差异报告。

## 格式映射

根据硬件和部署形状选择格式，而不是根据习惯——错误的选择要么浪费吞吐量余量，要么在特定工作负载上静默地崩溃（参见 Workload Overrides）。

- **Hopper 系列 GPU 及更新型号默认使用 FP8。** 它在约一半的内存下保留了接近 bf16 的质量，并且当目标 GPU 支持它且没有边缘设备约束时，它是安全的首选。
- **AWQ INT4 针对 FP8 硬件支持之前的旧 GPU。** **GPTQ 对于新部署已被取代**——不要在全新的导出中使用它；AWQ 在相同的位宽下具有更好的精度保持，并且当前的工具支持更广泛。
- **GGUF 使用 Q4_K_M 量化，从 imatrix 构建，是边缘/llama.cpp 格式。** 用于本地或 CPU 邻近的部署，而不是 GPU 服务吞吐量——它优化的是占用空间，而不是数据中心 GPU 上的 tokens/秒。
- **NVFP4 仅限于 Blackwell 大规模部署——并且明确不适用于 GB10。** SM121 (GB10) 上的 NVFP4 运行 **~32% 慢于 FP8**，因为硬件缺少原生 `cvt.e2m1x2` 路径，除非内核编译为 `sm_121a`。在 GB10 目标上选择 NVFP4 是倒退，而不是升级——在那里选择 FP8。
- **合并与 LoRA 仅限是量化格式的独立轴。** 合并导出将适配器折叠到基础权重中：更大的工件，服务时没有基础模型依赖。LoRA 仅限将适配器保持分离：工件更小，但服务堆栈必须与服务它一起加载完全相同的基模型——不匹配或错误版本的基模型会静默地改变输出。当工件可移植性比存储更重要时选择合并；当磁盘占用空间或多适配器服务更重要时选择 LoRA 仅限。

### 推荐选择

核心格式选择权衡，作为常见场景的查找表：

| 目标 | 工作负载 | 格式 |
|---|---|---|
| 数据中心 GPU | 通用聊天 | FP8 |
| 数据中心 GPU | 长上下文/代码/数学 | FP8 或 W8A8 —— 永远不要使用 INT4 |
| 旧 GPU 世代 | 通用 | AWQ INT4 |
| 边缘设备/笔记本电脑 | llama.cpp 服务 | GGUF Q4_K_M + imatrix |
| GB10 | 任何工作负载 | FP8 通过 vLLM 夜间构建，或 GGUF 通过 llama.cpp 本地构建——跳过 NVFP4 |

```yaml
# 快速决策片段——请参考上表中的完整映射
hopper_or_newer: fp8
older_gpu: awq-int4
edge_llama_cpp: gguf-q4_k_m+imatrix
gb10_any_workload: fp8-vllm-nightly   # GB10 上永远不要使用 nvfp4
```

## 工作负载覆盖

上述格式映射是默认值，而不是适用于所有工作负载的规则。**长上下文、代码和数学工作负载在 INT4 下会崩溃**——量化误差会在长序列和精确的 token 级推理中累积，而这些不会在短、通用的提示中显示出来。对于这三种工作负载类别中的任何一种，**即使目标硬件在其他情况下会证明 INT4 的成本效益，也要保持在 FP8 或 W8A8 上**。

- 不要用 MMLU 或类似的广知识基准来验证此覆盖——它们不会施加这种失败模式。**使用实际任务评估**——来自 `eval-harness-first` 的黄金输出和评分器，通过导出的工件运行——因为长上下文、代码或数学上的 INT4 退化会作为特定任务的失败（丢失上下文、破坏语法、算术错误）在它移动知识基准之前就出现。
- 如果在上述三种工作负载类别中的一种上，任务评估在 INT4 导出后退化，那么修复方法是切换格式，而不是重新调整量化配方——在相同的位宽下，AWQ 和 GPTQ 变体在这类工作负载上共享累积误差的失败模式。

## 烟雾测试

导出错误在文件级别是静默的——一个格式错误的导出仍然会产生可加载的工件，所以文件存在检查证明不了什么。**烟雾测试对每个导出都是强制性的，即使格式“应该只是工作”也不例外：**

1. **在其实际目标运行时加载导出的工件**——vLLM 用于 FP8/AWQ，llama.cpp 用于 GGUF，而不是在不同的框架中快速检查其将在生产中服务的内容。
2. **运行 3-5 个黄金提示**——从 `eval/goldens.jsonl` 中获取这些，`eval-harness-first` 维护的相同 `eval` 中，而不是一个全新的临时集。
3. **将每个输出与相同提示的导出前生成进行比较**，相同的确定性采样设置——贪婪解码（温度 0）和固定种子，在导出前和导出后持久化并重用，而不仅仅是名义上相同的配置。**对于无损导出，字节匹配是门槛——任何差异都是错误。** 对于**有损**（量化）导出，字节匹配预期会失败；门槛是任务评分器判定的同意——参见 `references/export-commands.md` 的 Smoke-Test Script Skeleton。

将其作为门槛运行，而不是手动检查：

```bash
python smoke_test.py "$EXPORT_PATH" \
    eval/goldens.jsonl pre-export-outputs.jsonl
# 任何预/后不匹配都会导致非零退出
```

### 失败特征

导出错误实际看起来像什么，而不仅仅是干净的通过/失败标志：

- **模板不匹配** 表现为混乱或连绵输出——导出中嵌入的聊天模板与检查点训练和评估时使用的模板不匹配，所以转折边界或特殊标记会落在错误的位置。
- **将错误的量化应用于 `lm_head`** 表现为离模板或语义上无意义的输出，但仍然看起来流畅——输出头丢失了它即使在网络其他部分干净量化的情况下也需要的精度。

永远不要发布跳过此步骤的导出——检查点的 `PROMOTE` 判定表明未导出的检查点是好的；它对导出管道什么也说不出来。在任何量化方法或运行时版本升级后重新运行，而不仅仅是第一次导出后。每个格式加上烟雾测试脚本骨架的可运行命令序列：
`references/export-commands.md`。

## 相关技能

- `checkpoint-promotion` — 这是此技能的唯一有效上游来源。没有 `PROMOTE` 判定的检查点不会到达导出。
- `eval-harness-first` — 拥有此技能的烟雾测试从中获取其 3-5 个提示的 `eval/goldens.jsonl`，以及 Workload Overrides 部分要求用于长上下文/代码/数学验证的任务评估。
- `finetuning-method-selection` — 其 `references/model-catalog.md` 是在从上述格式映射选择格式之前检查硬件类别假设（基础模型针对哪些 GPU 世代）的地方。

**Spark 用户：** 在 GB10 上，通过 llama.cpp 的 GGUF 对于本地服务效果很好，并且通过 vLLM 夜间构建的 FP8 服务是另一条已证明的路径——NVFP4 是那里要避免的唯一格式（参见上述格式映射例外）。一旦安装了 `dgx-spark-ops` 插件，将 Spark 特定的服务和热问题推迟到其技能，而不是在这里重新推导。
