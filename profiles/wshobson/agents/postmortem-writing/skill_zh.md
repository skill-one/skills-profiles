# 停机复盘撰写

撰写有效且无责备的停机复盘指南，推动组织学习并防止事件再次发生。

## 使用此技能的场景

- 进行事件后复盘
- 撰写复盘文档
- 主持无责备复盘会议
- 识别根本原因和促成因素
- 制定可执行的后续事项
- 建立组织学习文化

## 核心概念

### 1. 无责备文化

| 责备导向            | 无责备                         |
| ------------------ | ---------------------------- |
| "谁造成的？"       | "哪些条件允许这种情况发生？"   |
| "有人犯了错误"     | "系统允许这种错误发生"         |
| 惩罚个人            | 改进系统                      |
| 隐藏信息            | 分享学习成果                  |
| 恐惧发言            | 心理安全感                    |

### 2. 复盘触发条件

- SEV1 或 SEV2 事件
- 面向客户的停机 > 15 分钟
- 数据丢失或安全事件
- 可能造成严重后果的未遂事件
- 新的故障模式
- 需要异常干预的事件

## 快速入门

### 复盘时间线

```
第 0 天：事件发生
第 1-2 天：起草复盘文档
第 3-5 天：复盘会议
第 5-7 天：最终确定文档，创建工单
第 2 周后：行动项完成
每季度：跨事件模式回顾
```

### 模板 2：5Why 分析

```markdown
# 5Why 分析：[事件]

## 问题陈述

支付服务因数据库连接耗尽导致 47 分钟停机。

## 分析

### Why #1：为什么服务失败？

**答案**：数据库连接耗尽，导致所有新请求失败。

**证据**：指标显示连接数达到 100/100（最大值），有 500+ 挂起请求。

---

### Why #2：为什么数据库连接耗尽？

**答案**：每个入站请求都打开新的数据库连接，而不是使用连接池。

**证据**：代码差异显示直接使用 `DriverManager.getConnection()` 而不是池化 `DataSource`。

---

### Why #3：为什么代码绕过连接池？

**答案**：一名开发人员重构了仓库类，并无意中更改了连接获取方法。

**证据**：PR #1234 显示了该变更，当时正在修复其他 Bug。

---

### Why #4：为什么代码审查没有发现？

**答案**：审查者专注于功能变更（Bug 修复），没有注意到基础设施变更。

**证据**：审查评论仅讨论业务逻辑。

---

### Why #5：为什么没有针对此类变更设置安全网？

**答案**：我们缺乏验证连接池行为的自动化测试，且缺乏关于连接模式的文档。

**证据**：测试套件没有连接处理的测试；维基没有关于数据库连接的文章。

## 识别的根本原因

1. **主要**：缺少基础设施行为的自动化测试
2. **次要**：架构模式文档不足
3. **三级**：代码审查清单未包含基础设施考虑

## 系统性改进

| 根本原因    | 改进措施                       | 类型       |
| ---------- | ---------------------------- | ---------- |
| 缺少测试   | 添加基础设施行为测试           | 预防       |
| 缺少文档   | 记录连接模式                  | 预防       |
| 审查缺陷   | 更新审查清单                   | 检测       |
| 无金丝雀发布 | 实施金丝雀发布                | 缓解       |
```

### 模板 3：快速复盘（轻微事件）

```markdown
# 快速复盘：[简短标题]

**日期**：2024-01-15 | **时长**：12 分钟 | **严重性**：SEV3

## 发生了什么

API 延迟因缓存失效风暴飙升至 5 秒，缓存刷新后触发。

## 时间线

- 10:00 - 启动缓存刷新以更新配置
- 10:02 - 触发延迟警报
- 10:05 - 确定为缓存失效风暴
- 10:08 - 启用缓存预热
- 10:12 - 延迟恢复正常

## 根本原因

配置更新全量缓存刷新导致雷声效应。

## 修复措施

- 立即：启用缓存预热
- 长期：实施部分缓存失效（ENG-999）

## 经验教训

生产环境不要全量刷新缓存；使用目标失效。
```

## 主持指南

### 主持复盘会议

```markdown
## 会议结构（60 分钟）

### 1. 开场（5 分钟）

- 提醒所有人无责备文化
- "我们在此是为了学习，而不是追究责任"
- 回顾会议规范

### 2. 时间线回顾（15 分钟）

- 按时间顺序回顾事件
- 提出澄清问题
- 识别时间线中的空白

### 3. 分析讨论（20 分钟）

- 什么失败？
- 为什么失败？
- 哪些条件允许这种情况发生？
- 什么可以预防？

### 4. 行动项（15 分钟）

- 头脑风暴改进措施
- 按影响和努力程度排序
- 分配负责人和截止日期

### 5. 结束（5 分钟）

- 总结关键学习成果
- 确认行动项负责人
- 如有需要，安排后续会议

## 主持技巧

- 保持讨论聚焦
- 将责备转向系统
- 鼓励沉默参与者
- 记录不同意见
- 限制离题讨论时间
```

## 需避免的反模式

| 反模式            | 问题                    | 更好方法                 |
| ---------------- | ---------------------- | ---------------------- |
| **责备游戏**      | 关闭学习                | 专注于系统                |
| **浅层分析**      | 无法防止再次发生        | 重复问"为什么"5 次       |
| **无行动项**      | 浪费时间                | 始终有具体下一步         |
| **不切实际的行动** | 从未完成                | 范围到可完成的任务       |
| **无跟进**        | 行动项被遗忘            | 在工单系统中跟踪         |

## 最佳实践

### 应做

- **立即开始** - 记忆会很快模糊
- **具体** - 精确时间，精确错误
- **包含图表** - 视觉证据
- **分配负责人** - 无孤立的行动项
- **广泛分享** - 组织学习

### 不应做

- **不要点名批评** - 永远不要
- **不要忽略小事件** - 它们揭示模式
- **不要让复盘变成责备文档** - 那会扼杀学习
- **不要制造忙乱工作** - 行动项应有意义
- **不要忽略跟进** - 确认行动项已完成
