# WCAG 审计模式

全面指南，用于根据 WCAG 2.2 指南审计网页内容，并提供可操作的修复策略。

## 使用此技能的场景

- 进行无障碍审计
- 修复 WCAG 违规
- 实现无障碍组件
- 准备应对无障碍诉讼
- 满足 ADA/第 508 条要求
- 达到 VPAT 合规

## 核心概念

### 1. WCAG 合规级别

| 级别   | 描述            | 适用对象      |
| ------ | --------------- | ------------- |
| **A**  | 基本无障碍      | 法律基准      |
| **AA** | 标准合规        | 大多数法规    |
| **AAA** | 增强无障碍      | 特殊需求      |

### 2. POUR 原则

```
Perceivable（可感知）：用户能否感知内容？
Operable（可操作）：用户能否操作界面？
Understandable（可理解）：用户能否理解内容？
Robust（稳定）：是否与辅助技术兼容？
```

### 3. 按影响分类的常见违规

```
严重（阻断性）：
├── 功能性图像缺少替代文本
├── 交互元素无键盘访问
├── 表单缺少标签
└── 无控制的自动播放媒体

较严重：
├── 色彩对比度不足
├── 缺少跳过链接
├── 无障碍的自定义组件
└── 缺少页面标题

中等：
├── 缺少语言属性
├── 链接文本不清晰
├── 缺少地标
└── 标题层级不当
```

## 最佳实践

### 应做事项

- **尽早开始** - 从设计阶段就考虑无障碍
- **使用真实用户测试** - 残疾人提供最佳反馈
- **尽可能自动化** - 30-50% 的问题可被检测
- **使用语义化 HTML** - 减少对 ARIA 的依赖
- **记录模式** - 构建无障碍组件库

### 不应做事项

- **不要仅依赖自动化测试** - 需要人工测试
- **不要将 ARIA 作为首选方案** - 优先使用原生 HTML
- **不要隐藏焦点轮廓** - 键盘用户需要它们
- **不要禁用缩放** - 用户需要调整大小
- **不要仅使用颜色** - 需要多种指示
