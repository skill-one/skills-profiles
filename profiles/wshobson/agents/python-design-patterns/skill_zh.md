# Python 设计模式

使用基本设计原则编写可维护的 Python 代码。这些模式帮助你构建易于理解、测试和修改的系统。

## 何时使用这项技能

- 设计新的组件或服务
- 重构复杂或缠绕的代码
- 决定是否创建抽象
- 在继承和组合之间进行选择
- 评估代码复杂性和耦合度
- 规划模块化架构

## 核心概念

### 1. KISS（保持简单）

选择最简单的解决方案。复杂性必须由具体需求来证明。

### 2. 单一职责（SRP）

每个单元应该只有一个变化的原因。将关注点分离到专注的组件中。

### 3. 组合优于继承

通过组合对象来构建行为，而不是扩展类。

### 4. 三法则

在抽象之前，等待你有三个实例。重复通常比过早抽象更好。

## 快速入门

```python
# 简单优于聪明
# 取代工厂/注册模式：
```

## 最佳实践总结

1. **保持简单** - 选择最简单的解决方案
2. **单一职责** - 每个单元只有一个变化的原因
3. **分离关注点** - 具有明确目的的独立层
4. **组合而非继承** - 通过组合对象实现灵活性
5. **三法则** - 在抽象之前等待
6. **保持函数简短** - 20-50 行（因复杂度而异），一个目的
7. **注入依赖** - 通过构造器注入实现可测试性
8. **在抽象之前删除** - 删除死代码，然后考虑模式
9. **逐层测试** - 每个关注点的隔离测试
10. **明确优于聪明** - 可读代码优于优雅代码

## 故障排除

**一个类正在增长，似乎有多个职责，但拆分感觉不对。**
应用“变化原因”测试：列出所有可能需要编辑这个类的变化。如果列表包含来自不同领域（例如，HTTP 解析 AND 业务规则 AND 格式化）的项目，请拆分它。如果所有变化都来自同一个领域关注点，则该类可能尺寸合适。

**通过构造器注入所有依赖项产生了具有 7+ 参数的构造器。**
这表明一个类中包含太多职责，而不是依赖注入的问题。首先将类拆分为更小的单元，然后每个构造器自然会变得更小。

**组合产生了难以追踪的深层嵌套包装对象。**
保持组合浅（2-3 层）。如果包装是唯一的机制，请考虑基于协议的方法或简单的函数组合是否比装饰器对象链更清晰。

**三法则说不应抽象，但重复会导致一个副本更新而另一个副本未更新时出现错误。**
当重复项以危险的方式发散时，应尽早抽象。三法则是启发式方法，不是法律。如果副本已经错误地发散，请立即提取并添加一个测试来执行共享行为。

**服务层正在从 API 层导入，破坏了依赖方向。**
这是分层违规。服务层不能从处理器导入。引入一个共享类型/模型层，两者都可以从中导入，保持依赖箭头指向下方（API → 服务 → 仓库）。
