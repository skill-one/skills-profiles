# 团队构成模式

构建多智能体团队的最佳实践，包括选择团队规模、选择智能体类型以及配置Claude Code的智能体团队功能的显示模式。

## 使用此技能的场景

- 决定为一个任务生成多少队友
- 在预设团队配置之间进行选择
- 为每个角色选择合适的智能体类型（subagent_type）
- 配置队友显示模式（tmux、iTerm2、进程内）
- 为非标准工作流程构建自定义团队构成

## 团队规模启发式方法

| 复杂度   | 团队规模 | 使用场景                                       |
| -------- | -------- | --------------------------------------------- |
| 简单     | 1-2      | 单维度审查、孤立错误、小型功能                 |
| 中等     | 2-3      | 多文件更改、2-3个关注点、中型功能             |
| 复杂     | 3-4      | 跨领域关注点、大型功能、深度调试             |
| 非常复杂 | 4-5      | 全栈功能、综合审查、系统性问题               |

**经验法则**：从能覆盖所有必要维度的最小团队开始。增加队友会增加协调开销。

## 预设团队构成

### 审查团队

- **规模**：3名审查者
- **智能体**：3x `team-reviewer`
- **默认维度**：安全性、性能、架构
- **使用场景**：代码更改需要多维度质量评估

### 调试团队

- **规模**：3名调查者
- **智能体**：3x `team-debugger`
- **默认假设**：3个竞争性假设
- **使用场景**：错误具有多个可能的根本原因

### 功能团队

- **规模**：3名（1名领导 + 2名实现者）
- **智能体**：1x `team-lead` + 2x `team-implementer`
- **使用场景**：功能可以分解为并行工作流

### 全栈团队

- **规模**：4名（1名领导 + 3名实现者）
- **智能体**：1x `team-lead` + 1名前端 `team-implementer` + 1名后端 `team-implementer` + 1名测试 `team-implementer`
- **使用场景**：功能跨越前端、后端和测试层

### 研究团队

- **规模**：3名研究人员
- **智能体**：3x `general-purpose`
- **默认领域**：每个分配一个不同的研究问题、模块或主题
- **功能**：代码库搜索（Grep、Glob、Read）、网络搜索（WebSearch、WebFetch）
- **使用场景**：需要理解代码库、研究库、比较方法或并行从代码和网络源收集信息

### 安全团队

- **规模**：4名审查者
- **智能体**：4x `team-reviewer`
- **默认维度**：OWASP/漏洞、认证/访问控制、依赖项/供应链、密钥/配置
- **使用场景**：覆盖多个攻击面的综合安全审计

### 迁移团队

- **规模**：4名（1名领导 + 2名实现者 + 1名审查者）
- **智能体**：1x `team-lead` + 2x `team-implementer` + 1x `team-reviewer`
- **使用场景**：大型代码库迁移（框架升级、语言移植、API版本提升）需要并行工作并验证正确性

## 智能体类型选择

在使用 `Agent` 工具生成队友时，根据队友需要的工具选择 `subagent_type`：

| 智能体类型                     | 可用工具                                      | 使用场景                                                    |
| ------------------------------ | -------------------------------------------- | ---------------------------------------------------------- |
| `general-purpose`              | 所有工具（Read、Write、Edit、Bash等）            | 实现、调试、任何需要文件更改的任务                         |
| `Explore`                      | 只读工具（Read、Grep、Glob）                   | 研究、代码探索、分析                                       |
| `Plan`                         | 只读工具                                      | 架构规划、任务分解                                          |
| `agent-teams:team-reviewer`    | Read/search/Bash plus TaskList/TaskGet/TaskUpdate/SendMessage | 具有结构化发现的代码审查                             |
| `agent-teams:team-debugger`    | Read/search/Bash plus TaskList/TaskGet/TaskUpdate/SendMessage | 假设驱动的调查                    |
| `agent-teams:team-implementer` | Read/Write/Edit/search/Bash plus TaskList/TaskGet/TaskUpdate/SendMessage | 在文件所有权边界内构建功能 |
| `agent-teams:team-lead`        | Read/search/Bash plus Agent Teams 协调工具 | 团队协调和协调                        |

**关键区别**：只读智能体（Explore、Plan）不能修改文件。永远不要将实现任务分配给只读智能体。

## 显示模式配置

在 `~/.claude/settings.json` 中配置：

```json
{
  "teammateMode": "tmux"
}
```

| 模式           | 行为                       | 最佳适用场景                                          |
| -------------- | -------------------------- | ----------------------------------------------------- |
| `"tmux"`       | 每个队友在一个 tmux 选项卡中   | 开发工作流、监控多个智能体                         |
| `"iterm2"`     | 每个队友在一个 iTerm2 选项卡中 | 偏好 iTerm2 的 macOS 用户                           |
| `"in-process"` | 所有队友在同一进程中       | 简单任务、CI/CD 环境                                |

## 自定义团队指南

构建自定义团队时：

1. **每个团队需要一个协调者** — 要么指定一个 `team-lead`，要么让用户直接协调
2. **将角色与智能体类型匹配** — 当可用时，使用专用智能体（审查者、调试者、实现者）
3. **避免重复角色** — 两个智能体做同样的事情会浪费资源
4. **提前定义边界** — 每个队友需要明确的文件或责任归属
5. **保持小规模** — 2-4 名队友是最佳点；5 名以上需要显著的协调开销

## 故障排除

**一个队友被生成为了 `Explore` 但需要写入文件。**
`Explore` 和 `Plan` 是只读智能体。将 `subagent_type` 更改为 `general-purpose` 或适当的专用智能体类型。永远不要将实现任务分配给只读智能体。

**团队规模过大，协调导致一切变慢。**
每个额外的队友会增加沟通开销。整合角色：一个智能体可以覆盖两个维度吗？一个 4 人团队执行 6 个独立任务通常比 3 个智能体每个覆盖 2 个任务更好。

**tmux 模式没有显示选项卡。**
确保在生成队友之前已安装并运行了 tmux 会话。`in-process` 模式无需 tmux，适合 CI 或脚本环境。

**两个审查者标记了相同的问题。**
审查维度重叠。重新定义每个审查者的关注领域：一个关注正确性/逻辑，一个关注安全性，一个关注性能/可扩展性。重叠的覆盖会浪费 token 并产生重复的发现。

**一个 `team-lead` 正在生成队友，但队友没有收到任务。**
验证领导是否使用 `Agent` 工具生成队友，并在提示中传递完整的上下文。队友以全新的状态开始，没有先前的对话历史——他们需要在初始提示中包含所有相关信息。
