# 数据集管理

此技能假定 `finetuning-method-selection`
已路由至此处——下一步是准备数据，而非选择方法。以下内容：根据目标方法选择格式、最常见静默训练失败的模板/打包机制、混合合成数据而不崩溃的规则，以及关闭第 2 阶段并在运行开始前的数据集卡。

**输入：** 原始示例（演示、偏好判断或任务提示）加上来自 `finetuning-method-selection` 的路由决策。
**输出格式：** 一个格式化、打包、验证的 JSONL 数据集以及一个完整的数据集卡——第 2 阶段工件 `/finetune` 在启动训练前会进行检查。

## 格式选择

| 方法 | 形状 | 行数 |
|---|---|---|
| SFT, 单轮 | 指令 (`instruction`/`response` 或 `prompt`/`completion`) | ~1,000+ 地板 |
| SFT, 多轮 | 对话 / ChatML `messages` 列表 | ~1,000+ 地板 |
| DPO / ORPO | 偏好对 (`prompt`, `chosen`, `rejected`) | 方法相关，参见 `preference-optimization` |
| KTO | 无配对 (`prompt`, `completion`, `label`) | 方法相关，参见 `preference-optimization` |
| GRPO / RLVR | 仅提示 (`prompt` + 验证器元数据) | 方法相关，参见 `grpo-rlvr-training` |

- **~1,000+ 行是 SFT 的推荐地板，而非目标。** 低于它，少量低质量或重复的示例会主导梯度；高于它，**质量胜于数量**——一个较小的验证、去重集胜过一个更大的噪声集。
- ChatML 形状用于定位；其他四种格式加上 ShareGPT 转换说明位于 `references/formats-and-templates.md`：

  ```json
  {"messages": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ]}
  ```

## 聊天模板和损失掩码

在任何连接或打包之前应用目标模型的聊天模板——**绝不**在之后应用——打包原始文本并在之后对打包的块进行模板化会破坏回合边界，导致角色标记相对于每个示例的位置错误。

- **仅训练助手响应。** 掩码损失（标签张量中的 `-100`）在系统/用户回合和模板自身的角色标记上——仅助手回合内容标记对损失有贡献。
- **模板/分词器不匹配是主要的静默失败模式。** 一个针对一个聊天模板训练但用于服务或评估的不同模板的模型会退化而不会报错。验证训练中使用的相同模板字符串在推理和评估时是否被应用。
- **保持数据集在 `messages` 形状** 并让训练器对其进行模板化和掩码（当前 TRL 中的 `assistant_only_loss=True`）——预先渲染到扁平文本字段会破坏掩码需要的回合边界。完整代码草图：`references/formats-and-templates.md`。训练前进行合理性检查——仅解码未掩码的位置；预期只有助手文本：

  ```python
  keep = batch["labels"][0] != -100
  print(tokenizer.decode(batch["input_ids"][0][keep]))
  ```

## 打包

**没有打包，40–70% 的计算资源将用于填充**——可变长度的示例在固定序列长度处批量处理会浪费每个示例长度与批次最大值之间的间隙。打包将多个示例连接成一个最大长度序列，从而消除了大部分浪费。

- **打包会改变批次语义。** 一个打包序列可以包含多个原始示例，因此“每轮步数”和任何基于示例计数的 LR 调度在启用打包后都会改变——重新计算基于打包序列计数的调度里程碑。
- **强制要求：在扩展到完整运行之前解码并手动检查 5–10 个打包序列。** 确认示例边界落在预期位置，每个子示例的模板标记完整，并且每个打包序列内的损失掩码仍然是仅助手。这不是可选的——打包错误是静默的（损失曲线看起来正常），并且只有在评估质量中数小时后才会暴露：

  ```python
  for seq in packed_dataset.select(range(10)):
      print(tokenizer.decode(seq["input_ids"]))
  ```

## 合成数据规则

- **将 ≥25% 的真实数据作为崩溃防护。** 在模型生成的数据不断增长而没有真实数据地板的情况下进行训练会导致连续几代后可衡量的质量崩溃——25% 的真实数据是维持现状的最低限度。**通用领域重放行**
  计入此地板——**“真实”意味着“不是为这个任务从这个学生生成的”，而不是“人类创作的”。** 一个在构建上全部合成的数据集可以通过重放 alone 来满足 ≥25% 的地板（参见
  `references/synthetic-data.md` 的 Replay-Mix Construction 配方）；在数据集卡中说明哪些行计为“真实”，而不是让地板在结构上无法满足。
- **Magpie 和拒绝采样是主力。** Magpie 从模型自己的模板中提取提示；拒绝采样为每个提示生成多个候选并仅保留通过过滤器的那部分。两者都比简单的单次生成更优。
- **针对学生、有意识的生成比静态生成效率高 1.3–2x**——瞄准学生的实际失败模式可以用更少的过滤示例达到质量标准。
- **过滤后的典型接受率运行 10–30%。** 相应地规划数量——一个 10,000 行的目标在 15% 接受率下需要 ~65,000+ 原始生成。
- 生成方法排名、过滤器漏斗、重放混合构建和蒸馏模式：
  `references/synthetic-data.md`。

## 数据集卡

每个达到训练的数据集都会获得一张卡——第 2 阶段 `/finetune` 在启动前会进行检查。卡片不是自由形式的文档；它**必须**包含以下字段：

- **来源** — 每一行来自哪里（真实来源、合成方法或两者），可追溯到 `trace-to-training-data` 输出。
- **计数** — 总行数，以及如果拆分则按拆分（训练/评估/保留）的行数。
- **合成/真实比例** — 测量比例，检查是否符合上述 ≥25% 的真实地板。
- **去重方法** — 精确匹配、语义（嵌入阈值）或两者；参见 `references/synthetic-data.md` 中的过滤器漏斗。
- **使用的模板** — 精确的聊天模板字符串/标识符，在推理和评估期间保持一致——这是将 `eval-harness-first` 运行与检查点联系起来的东西。
- **打包配置** — 是否使用打包、最大序列长度，以及确认上述 5–10 个序列的手动检查已完成。

缺少这六个字段中的任何一个的数据集都不准备好进行 `/finetune`——卡片是一个关卡，而不是事后编写的摘要。

### 第 2 阶段退出检查清单

在移交给 `/finetune` 之前，请确认：

1. 格式与方法匹配（上表）。
2. 在连接之前应用模板。
3. 损失仅掩码到助手回合。
4. 解码并阅读 5–10 个打包序列。
5. 最终混合中 ≥25% 的真实数据。
6. 数据集卡完整——所有六个字段。
