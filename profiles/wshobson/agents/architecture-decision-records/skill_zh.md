# 架构决策记录

创建、维护和管理架构决策记录（ADRs）的全面模式，这些记录捕获了重大技术决策的背景和理由。

## 何时使用此技能

- 做出重大架构决策
- 记录技术选择
- 记录设计权衡
- 新成员入职
- 审查历史决策
- 建立决策流程

## 核心概念

### 1. 什么是ADR？

架构决策记录（ADR）捕获：

- **背景**：我们为什么需要做决策
- **决策**：我们决定的内容
- **后果**：结果如何

### 2. 何时编写ADR

| 编写ADR                  | 跳过ADR               |
| -------------------------- | ---------------------- |
| 新框架采用     | 小版本升级            |
| 数据库技术选择 | 修复错误              |
| API设计模式        | 实现细节              |
| 安全架构      | 例行维护              |
| 集成模式       | 配置更改              |

### 3. ADR生命周期

```
提议 → 接受 → 废弃 → 取代
              ↓
           拒绝
```

## 模板

### 模板1：标准ADR（MADR格式）

```markdown
# ADR-0001：使用PostgreSQL作为主数据库

## 状态

接受

## 背景

我们需要为新电子商务平台选择一个主数据库。系统将处理：

- ~10,000个并发用户
- 复杂的产品目录，具有分层类别
- 订单和支付的交易处理
- 产品的全文搜索
- 商店定位器的地理空间查询

团队有MySQL、PostgreSQL和MongoDB的使用经验。我们需要ACID合规性来处理金融交易。

## 决策驱动因素

- **必须具有ACID合规性**用于支付处理
- **必须支持复杂查询**用于报告
- **应该支持全文搜索**以减少基础设施复杂性
- **应该具有良好的JSON支持**用于灵活的产品属性
- **团队熟悉**减少了入职时间

## 考虑的选项

### 选项1：PostgreSQL

- **优点**：ACID合规，优秀的JSON支持（JSONB），内置全文搜索，PostGIS用于地理空间，团队有使用经验
- **缺点**：比MySQL的复制设置稍复杂

### 选项2：MySQL

- **优点**：团队非常熟悉，复制简单，社区庞大
- **缺点**：JSON支持较弱，没有内置全文搜索（需要Elasticsearch），没有扩展的地理空间

### 选项3：MongoDB

- **优点**：灵活的架构，原生JSON，水平扩展
- **缺点**：多文档事务没有ACID（决策时），团队使用经验有限，需要架构设计纪律

## 决策

我们将使用**PostgreSQL 15**作为我们的主数据库。

## 理由

PostgreSQL提供了以下最佳平衡：

1. **ACID合规性**对于电子商务交易至关重要
2. **内置功能**（全文搜索、JSONB、PostGIS）减少了基础设施复杂性
3. **团队熟悉SQL数据库**减少了学习曲线
4. **成熟的生态系统**具有出色的工具和社区支持

复制的轻微复杂性被减少额外服务（不需要单独的Elasticsearch）所抵消。

## 后果

### 积极

- 单一数据库处理事务、搜索和地理空间查询
- 减少操作复杂性（要管理的服务更少）
- 强一致性保证用于金融数据
- 团队可以利用现有的SQL专业知识

### 消极

- 需要学习PostgreSQL特定功能（JSONB、全文搜索语法）
- 垂直扩展限制可能需要更早使用读副本
- 一些团队成员需要PostgreSQL特定培训

### 风险

- 全文搜索可能不如专用搜索引擎扩展得那么好
- 缓解措施：如果需要，设计潜在的Elasticsearch添加

## 实施说明

- 使用JSONB进行灵活的产品属性
- 使用PgBouncer实现连接池
- 设置流式复制用于读副本
- 使用pg_trgm扩展进行模糊搜索

## 相关决策

- ADR-0002：缓存策略（Redis）- 补充数据库选择
- ADR-0005：搜索架构 - 如果需要Elasticsearch可能会取代

## 参考

- [PostgreSQL JSON文档](https://www.postgresql.org/docs/current/datatype-json.html)
- [PostgreSQL全文搜索](https://www.postgresql.org/docs/current/textsearch.html)
- 内部：性能基准在`/docs/benchmarks/database-comparison.md`中的数据库比较

```

### 模板2：轻量级ADR

```markdown
# ADR-0012：采用TypeScript进行前端开发

**状态**：接受
**日期**：2024-01-15
**决策者**：@alice, @bob, @charlie

## 背景

我们的React代码库已增长到50多个组件，与属性类型不匹配和未定义错误相关的错误报告越来越多。PropTypes提供仅运行时的检查。

## 决策

为所有新前端代码采用TypeScript。逐步迁移现有代码。

## 后果

**好**：在编译时捕获类型错误，更好的IDE支持，代码自文档化。

**坏**：团队学习曲线，初始速度减慢，构建复杂性增加。

**缓解措施**：TypeScript培训课程，允许使用`allowJs: true`逐步采用。
```

### 模板4：用于废弃的ADR

```markdown
# ADR-0020：废弃MongoDB，采用PostgreSQL

## 状态

接受（取代ADR-0003）

## 背景

ADR-0003（2021）由于架构灵活性需求选择了MongoDB用于用户资料存储。自那时以来：

- MongoDB的多文档事务仍然不适合我们的用例
- 我们的架构已经稳定，很少更改
- 我们现在从其他服务获得了PostgreSQL专业知识
- 维护两个数据库增加了操作负担

## 决策

废弃MongoDB并将用户资料迁移到PostgreSQL。

## 迁移计划

1. **阶段1**（第1-2周）：创建PostgreSQL架构，启用双写
2. **阶段2**（第3-4周）：填充历史数据，验证一致性
3. **阶段3**（第5周）：将读切换到PostgreSQL，监控
4. **阶段4**（第6周）：移除MongoDB写入，退役

## 后果

### 积极

- 单一数据库技术减少了操作复杂性
- 用户数据的ACID事务
- 团队可以专注于PostgreSQL专业知识

### 消极

- 迁移工作（约4周）
- 迁移期间数据问题的风险
- 失去一些架构灵活性

## 经验教训

从ADR-0003的经验中记录：

- 架构灵活性带来的好处被高估
- 多个数据库的操作成本被低估
- 在技术决策中考虑长期维护
```

### 模板5：请求评论（RFC）风格

```markdown
# RFC-0025：为订单管理采用事件溯源

## 摘要

提议为订单管理域采用事件溯源模式，以提高可审计性、支持时间查询并支持业务分析。

## 动机

当前挑战：

1. 审计需求需要完整的订单历史
2. "X时刻订单状态是什么？"查询不可能
3. 分析团队需要事件流用于实时仪表板
4. 客户支持需要手动重建订单状态

## 详细设计

### 事件存储

```

OrderCreated { orderId, customerId, items[], timestamp }
OrderItemAdded { orderId, item, timestamp }
OrderItemRemoved { orderId, itemId, timestamp }
PaymentReceived { orderId, amount, paymentId, timestamp }
OrderShipped { orderId, trackingNumber, timestamp }

```

### 投影

- **当前订单状态**：用于查询的物质化视图
- **订单历史**：用于审计的完整时间线
- **每日订单指标**：分析聚合

### 技术

- 事件存储：EventStoreDB（专为目的设计，处理投影）
- 考虑的替代方案：Kafka + 自定义投影服务

## 缺点

- 团队学习曲线
- 与CRUD相比复杂性增加
- 需要仔细设计事件（存储后不可变）
- 存储增长（事件永远不会删除）

## 替代方案

1. **审计表**：更简单，但不能支持时间查询
2. **现有数据库的CDC**：复杂，不改变数据模型
3. **混合**：仅对订单状态更改进行事件溯源

## 未解决的问题

- [ ] 事件模式版本策略
- [ ] 事件保留策略
- [ ] 快照频率以优化性能

## 实施计划

1. 使用单个订单类型进行原型设计（2周）
2. 团队接受事件溯源培训（1周）
3. 完整实施和迁移（4周）
4. 监控和优化（持续进行）

## 参考

- [Martin Fowler的事件溯源](https://martinfowler.com/eaaDev/EventSourcing.html)
- [EventStoreDB文档](https://www.eventstore.com/docs)
```

```markdown
此目录包含[项目名称]的架构决策记录（ADRs）。

## 索引

| ADR                                   | 标题                              | 状态     | 日期       |
| ------------------------------------- | ---------------------------------- | ---------- | ---------- |
| [0001](0001-use-postgresql.md)        | 使用PostgreSQL作为主数据库        | 接受     | 2024-01-10 |
| [0002](0002-caching-strategy.md)      | 使用Redis的缓存策略              | 接受     | 2024-01-12 |

## 创建新ADR

1. 复制`template.md`到`NNNN-title-with-dashes.md`
2. 填写模板
3. 提交PR进行审查
4. 审批后更新此索引

## ADR状态

- **提议**：正在讨论
- **接受**：已做出决策，正在实施
- **废弃**：不再相关
- **取代**：被另一个ADR取代
- **拒绝**：考虑但未采用
```

### 自动化（adr-tools）

```bash
# 安装adr-tools
brew install adr-tools

# 初始化ADR目录
adr init docs/adr

# 创建新ADR
adr new "使用PostgreSQL作为主数据库"

# 取代一个ADR
adr new -s 3 "废弃MongoDB，采用PostgreSQL"

# 生成目录
adr generate toc > docs/adr/README.md

# 链接相关ADR
adr link 2 "补充" 1 "被补充"
```

## 审查流程

```markdown
## ADR审查清单

### 提交前

- [ ] 背景清楚地解释了问题
- [ ] 考虑了所有可行的选项
- [ ] 优缺点平衡且诚实
- [ ] 记录了后果（正面和负面）
- [ ] 链接了相关ADR

### 审查期间

- [ ] 至少有2位高级工程师审查
- [ ] 咨询了受影响的团队
- [ ] 考虑了安全影响
- [ ] 记录了成本影响
- [ ] 评估了可逆性

### 接受后

- [ ] 更新ADR索引
- [ ] 通知团队
- [ ] 创建实施工单
- [ ] 更新相关文档
```

## 最佳实践

### 应该做

- **尽早编写ADR** - 在实施开始前
- **保持简短** - 最多1-2页
- **诚实地记录权衡** - 包括真实的缺点
- **链接相关决策** - 建立决策图
- **更新状态** - 当被取代时废弃

### 不应该做

- **不要更改已接受的ADR** - 写新的来取代
- **不要跳过背景** - 未来读者需要背景
- **不要隐藏失败** - 被拒绝的决策很有价值
- **不要含糊其辞** - 具体的决策，具体的后果
- **不要忘记实施** - 没有行动的ADR是浪费
