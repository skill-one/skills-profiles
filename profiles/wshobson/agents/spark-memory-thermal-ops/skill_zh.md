# Spark 内存与热管理

DGX Spark 的 GB10 芯片拥有一个 128GB 的统一内存 (UMA) 池，由 CPU 和 GPU 共享，并且其持续功耗上限远低于额定值。这两点都打破了独立 GPU 的假设：可用空间并非 `nvidia-smi` 报告的数值，并且一个启动迅速的任务会在执行过程中变慢，而没有任何配置错误。这项技能涵盖了规划内存可用空间、处理实际内存不足 (OOM) 情况以及跨长时间任务监控热量的内容。对于启动时失败的模式（ABI 不匹配、flash-attn、playbook 故障），请参阅 `spark-training-gotchas` — 这项技能假设任务已启动。

## 常见问题快速参考

| 情况 | 应采取的操作 |
|---|---|
| 启动前规划可用空间 | 根据 `free -g` 预算，而不是 `nvidia-smi` — 请参阅 UMA 内存模型 |
| 统一内存上的任务 OOM | 按顺序处理 OOM 梯度：先刷新，然后批量/打包，最后方法降级 |
| 运行过程中吞吐量下降 | 在假设配置错误之前，检查功耗/温度日志 — 请参阅热监控 |
| 同时需要训练器和推理服务器 | 一次运行一个 — 请参阅并发工作负载 |

## 何时使用此技能

- 在启动前，根据 128GB 池对训练运行进行规模调整 — 这个模型、方法和批量/打包组合是否适合。
- 任务在负载或步骤中途 OOM，且补救顺序很重要 — 首先尝试什么，其次尝试什么，再次尝试什么。
- 在多小时任务期间监控温度和功耗，判断减速是热节流还是其他原因。
- 计划在同一台机器上同时运行训练器和推理服务器（vLLM、Ollama）。

## UMA 内存模型

Spark 没有独立的 GPU VRAM — GPU 和 CPU 共享一个 128GB 的内存池。有两个后果：

- **`nvidia-smi` 和 `cudaMemGetInfo` 严重低估压力 — 或者根本报告为零。** 两者都报告 CUDA 分配器可见的内存，而不是池的实际状态 — 一台机器可能在 `nvidia-smi` 中显示有可用空间，但仍会 OOM，因为页面缓存和 mmap 的页面消耗了相同的池。在某些驱动程序/设置下，内存查询会直接返回 `[N/A], [N/A]` 而不是数值 — 在那里搜索数值的脚本会一无所获，而不是误导性的低估（请参阅 `spark-training-gotchas` 的 G3 错误）。

- **模型加载是一个瞬态峰值，而不是稳态。** 加载 safetensors 权重时，会 mmap 文件，然后复制到 CUDA 张量 — 在加载期间的一段时间内，mmap 的页面和 CUDA 复制都会同时消耗池。一个在训练时适合的模型，在加载期间仍可能 OOM，如果可用空间是根据加载后的占用空间而不是这个双倍的瞬态峰值来调整的。

使用 `free -g` 而不是 `nvidia-smi` 进行规划和诊断：

```bash
free -g | awk 'NR==2 {print "free:", $4, "GB"}'
```

经验法则：取那个空闲数值，减去几 GB 的操作系统/驱动程序开销，然后根据结果预算 — 不是 128GB 的规格数字。
`references/uma-accounting.md` 中的工作表接受参数计数、数据类型和方法作为输入，并返回一个内存估计值以与已知锚点进行比较。

### 规划顺序

在启动前，按顺序处理这些内容：

1. 阅读 `free -g`；为预算减去操作系统/驱动程序开销。
2. 根据 `references/uma-accounting.md` 估计权重 + 优化器 + 梯度 + 激活。
3. 与最接近的锚点（70B QLoRA、27B LoRA、9B 完整 FT）进行比较，而不是单独的估计值。
4. 如果估计值接近预算，则从较短的打包或较小的批量开始 — 比在运行中遇到 OOM 梯度更便宜。

### 示例：调整 70B QLoRA 运行的大小

检查工作表公式对约 40GB 锚点的合理性：

```python
params = 70e9
weights_gb = params * 0.5 / 1e9      # NF4，步骤 1
adapter_gb = 0.5                     # 步骤 5，可忽略不计
total_gb = weights_gb + adapter_gb   # + 激活
print(f"{total_gb:.0f}GB 在激活之前")
```

权重单独计算接近约 40GB 锚点 — 对同一模型类别，估计值远高于该数值是一个重新检查数据类型和方法的信号。

## OOM 梯度

当任务在统一内存上 OOM 时，按顺序处理这个梯度。每一步都比上一步更具破坏性 — 不要跳过：

**减少批量大小永远不是第一步。**

1. **刷新缓冲区缓存。** 先前运行或大型数据集读取的页面缓存通常占用了“丢失”可用空间中的 GB。这不需要任何成本，只需重新运行，并且不会触及任务的配置：

   ```bash
   sync; echo 3 > /proc/sys/vm/drop_caches
   ```

   需要 root 权限；是一个运行间重置，而不是训练中途步骤。请参阅 `spark-training-gotchas`（G3 错误）了解此步骤背后的完整诊断。

2. **减少批量大小或打包长度。** 只有在刷新未能释放足够的可用空间后，才减少批量大小或打包长度 — 这是第一个改变任务执行步骤的步骤。优先考虑打包长度；它更直接地驱动长上下文中的激活占用空间。

3. **降级方法：bf16 LoRA 优先于 QLoRA。** 如果刷新和缩小批量/打包后仍 OOM，则降级方法一个级别 — 接下来是 bf16 LoRA，而不是相反。QLoRA 的 bitsandbytes 解量化缓冲区是瞬态的 CUDA 端分配，可能在等效 bf16 LoRA 运行之前 OOM，尽管 QLoRA 的稳态占用空间更小。QLoRA 的 OOM 并不证明模型不适合。

只有在所有三个步骤之后，任务仍然不适合时，才进一步降级（更小的模型、多 Spark）。

## 热监控

多小时运行会推入 Spark 的持续功耗上限，远低于额定值 — 这是预期平台行为，而不是需要解释的症状：

- 与训练日志一起采样温度和功耗，而不是在注意到减速后 — 每 30-60 秒将吞吐量下降与热事件相关联。保持 `assets/thermal-sample.sh` 写入的 CSV 输出格式，以便时间戳与日志对齐：

  ```bash
  bash assets/thermal-sample.sh 30 thermal.log
  ```
