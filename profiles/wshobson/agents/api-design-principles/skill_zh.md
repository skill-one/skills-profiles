# API 设计原则

掌握 REST 和 GraphQL API 设计原则，以构建直观、可扩展且易于维护的 API，让开发者愉悦并经得起时间的考验。

## 何时使用这项技能

- 设计新的 REST 或 GraphQL API
- 为提高可用性重构现有 API
- 为团队建立 API 设计标准
- 在实现前评审 API 规范
- 在 API 模式之间迁移（如 REST 到 GraphQL）
- 创建开发者友好的 API 文档
- 为特定场景（移动端、第三方集成）优化 API

## 核心概念

### 1. RESTful 设计原则

**面向资源架构**

- 资源是名词（用户、订单、产品），而非动词
- 使用 HTTP 方法表示操作（GET、POST、PUT、PATCH、DELETE）
- URL 表示资源层级
- 保持一致的命名规范

**HTTP 方法语义：**

- `GET`：获取资源（幂等、安全）
- `POST`：创建新资源
- `PUT`：替换整个资源（幂等）
- `PATCH`：部分资源更新
- `DELETE`：删除资源（幂等）

### 2. GraphQL 设计原则

**先定义模式开发**

- 类型定义领域模型
- 查询用于读取数据
- 变更用于修改数据
- 订阅用于实时更新

**查询结构：**

- 客户端请求他们需要的精确数据
- 单一端点，支持多个操作
- 强类型模式
- 内建自省功能

### 3. API 版本化策略

**URL 版本化：**

```
/api/v1/users
/api/v2/users
```

**请求头版本化：**

```
Accept: application/vnd.api+json; version=1
```

**查询参数版本化：**

```
/api/users?version=1
```

## 最佳实践

### REST API

1. **命名一致**：集合使用复数名词（`/users`，而非 `/user`）
2. **无状态**：每个请求包含所有必要信息
3. **正确使用 HTTP 状态码**：2xx 成功，4xx 客户端错误，5xx 服务器错误
4. **API 版本化**：从一开始就计划可能产生破坏性变更
5. **分页**：始终对大型集合进行分页
6. **速率限制**：使用速率限制保护 API
7. **文档**：使用 OpenAPI/Swagger 创建交互式文档

### GraphQL API

1. **先定义模式**：在编写解析器前设计模式
2. **避免 N+1 问题**：使用 DataLoaders 进行高效数据获取
3. **输入验证**：在模式和解析器层级进行验证
4. **错误处理**：在变更有效负载中返回结构化错误
5. **分页**：使用基于游标的分页（Relay 规范）
6. **弃用**：使用 `@deprecated` 指令进行渐进式迁移
7. **监控**：跟踪查询复杂度和执行时间

## 常见陷阱

- **REST 的过度获取/获取不足**：GraphQL 中已解决，但需要 DataLoaders
- **破坏性变更**：API 版本化或使用弃用策略
- **不一致的错误格式**：标准化错误响应
- **缺少速率限制**：无限制的 API 易受滥用
- **文档质量差**：未文档化的 API 让开发者沮丧
- **忽视 HTTP 语义**：对幂等操作使用 POST 会打破预期
- **耦合过紧**：API 结构不应与数据库模式镜像
