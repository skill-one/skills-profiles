# 代码审查卓越

通过建设性反馈、系统分析和协作改进，将代码审查从守门转变为知识共享。

## 使用此技能的场景

- 审查拉取请求和代码变更
- 为团队建立代码审查标准
- 通过审查指导初级开发人员
- 进行架构审查
- 创建审查清单和指南
- 提升团队协作
- 缩短代码审查周期时间
- 维护代码质量标准

## 核心原则

### 1. 审查心态

**代码审查的目标：**

- 发现错误和边界情况
- 确保代码可维护性
- 跨团队共享知识
- 强制执行编码标准
- 改进设计和架构
- 建立团队文化

**不是目标：**

- 展示知识
- 吝啬格式化（使用代码格式化工具）
- 不必要地阻塞进度
- 按照个人偏好重写

### 2. 有效反馈

**好的反馈是：**

- 具体且可操作的
- 教育性的，而不是评判性的
- 关注代码，而不是个人
- 平衡的（也要表扬好的工作）
- 优先级（关键与锦上添花）

```markdown
❌ 坏的："这是错误的。"
✅ 好的："当多个用户同时访问时，这可能导致竞态条件。这里考虑使用互斥锁。"

❌ 坏的："你为什么不用X模式？"
✅ 好的："你考虑过仓库模式吗？这将使测试更容易。这里有一个示例：[链接]"

❌ 坏的："重命名这个变量。"
✅ 好的："[小问题] 考虑使用`userCount`而不是`uc`以提高清晰度。如果你愿意保持原样，不阻塞。"
```

### 3. 审查范围

**需要审查的内容：**

- 逻辑正确性和边界情况
- 安全漏洞
- 性能影响
- 测试覆盖和质量
- 错误处理
- 文档和注释
- API设计和命名
- 架构适配

**不需要手动审查的内容：**

- 代码格式化（使用Prettier、Black等）
- 导入组织
- 代码检查违规
- 简单拼写错误

## 审查流程

### 第一阶段：收集背景信息（2-3分钟）

```markdown
在深入代码之前，了解：

1. 阅读拉取请求描述和链接的问题
2. 检查拉取请求的大小（>400行？要求拆分）
3. 审查CI/CD状态（测试通过吗？）
4. 了解业务需求
5. 记录任何相关的架构决策
```

### 第二阶段：高级审查（5-10分钟）

```markdown
1. **架构和设计**
   - 解决方案是否适合问题？
   - 是否有更简单的方法？
   - 是否与现有模式一致？
   - 是否可扩展？

2. **文件组织**
   - 新文件是否在正确的位置？
   - 代码是否逻辑分组？
   - 是否有重复文件？

3. **测试策略**
   - 是否有测试？
   - 测试是否覆盖边界情况？
   - 测试是否可读？
```

### 第三阶段：逐行审查（10-20分钟）

```markdown
对于每个文件：

1. **逻辑和正确性**
   - 是否处理了边界情况？
   - 是否有计算错误？
   - 是否有空/未定义检查？
   - 是否有竞态条件？

2. **安全性**
   - 是否有输入验证？
   - 是否有SQL注入风险？
   - 是否有XSS漏洞？
   - 是否有敏感数据暴露？

3. **性能**
   - 是否有N+1查询？
   - 是否有不必要的循环？
   - 是否有内存泄漏？
   - 是否有阻塞操作？

4. **可维护性**
   - 变量名是否清晰？
   - 函数是否只做一件事？
   - 复杂代码是否有注释？
   - 是否提取了魔法数字？
```

### 第四阶段：总结和决策（2-3分钟）

```markdown
1. 总结主要问题
2. 突出你喜欢的部分
3. 做出明确决定：
   - ✅ 批准
   - 💬 评论（小建议）
   - 🔄 要求修改（必须解决）
4. 如果复杂，提供结对编程
```

## 审查技巧

### 技巧1：清单方法

```markdown
## 安全性清单

- [ ] 用户输入已验证和清理
- [ ] SQL查询使用参数化
- [ ] 检查身份验证/授权
- [ ] 密钥未硬编码
- [ ] 错误消息不泄露信息

## 性能清单

- [ ] 无N+1查询
- [ ] 数据库查询已索引
- [ ] 大列表分页
- [ ] 昂贵操作已缓存
- [ ] 热路径无阻塞I/O

## 测试清单

- [ ] 测试了正常路径
- [ ] 覆盖了边界情况
- [ ] 测试了错误情况
- [ ] 测试名称描述清晰
- [ ] 测试是确定性的
```

### 技巧2：提问方法

不要陈述问题，而是提出问题来鼓励思考：

```markdown
❌ "如果列表为空，这将失败。"
✅ "如果`items`是空数组会怎样？"

❌ "这里需要错误处理。"
✅ "如果API调用失败，应该如何表现？"

❌ "这效率低下。"
✅ "我看到这个循环遍历所有用户。我们有100,000个用户时，性能影响考虑过吗？"
```

### 技巧3：建议而非命令

````markdown
## 使用协作性语言

❌ "你必须将这个改为使用async/await"
✅ "建议：async/await可能会使这个更易读：
`typescript
    async function fetchUser(id: string) {
        const user = await db.query('SELECT * FROM users WHERE id = ?', id);
        return user;
    }
    `
你觉得呢？"

❌ "提取这个到一个函数"
✅ "这个逻辑出现在3个地方。提取它到一个共享的工具函数有意义吗？"
````

### 技巧4：区分严重性

使用标签指示优先级：

```markdown
🔴 [阻塞] - 必须在合并前修复
🟡 [重要] - 应该修复，如果不同意请讨论
🟢 [小问题] - 锦上添花，不阻塞
💡 [建议] - 考虑替代方法
📚 [学习] - 教育性评论，无需行动
🎉 [表扬] - 做得好，继续加油！

示例：
"🔴 [阻塞] 这个SQL查询容易受到注入攻击。请使用参数化查询。"

"🟢 [小问题] 考虑将`data`重命名为`userData`以提高清晰度。"

"🎉 [表扬] 优秀的测试覆盖率！这将捕获边界情况。"
```

## 语言特定模式

### Python代码审查

```python
# 检查Python特定问题

# ❌ 可变默认参数
def add_item(item, items=[]):  # 错误！跨调用共享
    items.append(item)
    return items

# ✅ 使用None作为默认值
def add_item(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items

# ❌ 捕获太宽泛
try:
    result = risky_operation()
except:  # 捕获所有内容，甚至KeyboardInterrupt！
    pass

# ✅ 捕获特定异常
try:
    result = risky_operation()
except ValueError as e:
    logger.error(f"无效值: {e}")
    raise

# ❌ 使用可变类属性
class User:
    permissions = []  # 所有实例共享！

# ✅ 在__init__中初始化
class User:
    def __init__(self):
        self.permissions = []
```

### TypeScript/JavaScript代码审查

```typescript
// 检查TypeScript特定问题

// ❌ 使用any会破坏类型安全
function processData(data: any) {  // 避免any
    return data.value;
}

// ✅ 使用正确的类型
interface DataPayload {
    value: string;
}
function processData(data: DataPayload) {
    return data.value;
}

// ❌ 未处理异步错误
async function fetchUser(id: string) {
    const response = await fetch(`/api/users/${id}`);
    return response.json();  // 如果网络失败会怎样？
}

// ✅ 正确处理错误
async function fetchUser(id: string): Promise<User> {
    try {
        const response = await fetch(`/api/users/${id}`);
        if (!response.ok) {
            throw new Error(`HTTP ${response.status}`);
        }
        return await response.json();
    } catch (error) {
        console.error('获取用户失败:', error);
        throw error;
    }
}

// ❌ 属性的修改
function UserProfile({ user }: Props) {
    user.lastViewed = new Date();  // 修改属性！
    return <div>{user.name}</div>;
}

// ✅ 不要修改属性
function UserProfile({ user, onView }: Props) {
    useEffect(() => {
        onView(user.id);  // 通知父级更新
    }, [user.id]);
    return <div>{user.name}</div>;
}
```

## 高级审查模式

### 模式1：架构审查

```markdown
当审查重大变更时：

1. **先设计文档**
   - 对于大型功能，在代码实现前请求设计文档
   - 在实现前与团队一起审查设计
   - 确定方法以避免返工

2. **分阶段审查**
   - 第一个拉取请求：核心抽象和接口
   - 第二个拉取请求：实现
   - 第三个拉取请求：集成和测试
   - 审查更容易，迭代更快

3. **考虑替代方案**
   - "我们考虑过使用[模式/库]吗？"
   - "与简单方法相比，权衡是什么？"
   - "当需求变化时，这将如何演变？"
```

### 模式2：测试质量审查

```typescript
// ❌ 差的测试：实现细节测试
test('increments counter variable', () => {
    const component = render(<Counter />);
    const button = component.getByRole('button');
    fireEvent.click(button);
    expect(component.state.counter).toBe(1);  // 测试内部状态
});

// ✅ 好的测试：行为测试
test('displays incremented count when clicked', () => {
    render(<Counter />);
    const button = screen.getByRole('button', { name: /increment/i });
    fireEvent.click(button);
    expect(screen.getByText('Count: 1')).toBeInTheDocument();
});

// 测试审查问题：
// - 测试描述行为还是实现？
// - 测试名称是否清晰描述？
// - 是否覆盖边界情况？
// - 测试是否独立（无共享状态）？
// - 是否可以任意顺序运行？
```

### 模式3：安全审查

```markdown
## 安全审查清单

### 身份验证和授权

- [ ] 是否需要身份验证？
- [ ] 每个操作前是否检查授权？
- [ ] JWT验证是否正确（签名、过期）？
- [ ] API密钥/密钥是否安全？

### 输入验证

- [ ] 所有用户输入是否已验证？
- [ ] 文件上传是否限制（大小、类型）？
- [ ] SQL查询是否参数化？
- [ ] 是否有XSS保护（输出转义）？

### 数据保护

- [ ] 密码是否哈希（bcrypt/argon2）？
- [ ] 敏感数据是否加密存储？
- [ ] 是否强制使用HTTPS传输敏感数据？
- [ ] 是否根据法规处理PII？

### 常见漏洞

- [ ] 无eval()或类似动态执行？
- [ ] 无硬编码密钥？
- [ ] 状态改变操作是否有CSRF保护？
- [ ] 公共端点是否有速率限制？
```

## 给出困难反馈

### 模式：改良三明治方法

```markdown
传统：表扬+批评+表扬（感觉不真实）

更好的：背景+具体问题+解决方案

示例：
"我注意到支付处理逻辑在控制器中是内联的。这使得它更难测试和重用。

[具体问题]
calculateTotal()函数混合了税计算、折扣逻辑和数据库查询，使其难以单元测试和理解。

[解决方案]
我们可以将其提取到一个PaymentService类中吗？这将使其可测试和可重用。如果需要，我可以与你结对完成。"
```

### 处理分歧

```markdown
当作者不同意你的反馈时：

1. **寻求理解**
   "请帮助我理解你的方法。是什么让你选择这个模式？"

2. **承认有效点**
   "关于X，这是一个很好的点。我没有考虑到。"

3. **提供数据**
   "我担心性能。我们可以添加基准测试来验证方法吗？"

4. **必要时升级**
   "让我们请[架构师/高级开发人员]对此发表意见。"

5. **知道何时放手**
   如果它有效且不是关键问题，批准它。完美是进步的敌人。
```

## 最佳实践

1. **及时审查**：24小时内，最好是当天
2. **限制拉取请求大小**：最多200-400行，以便有效审查
3. **分时段审查**：最多60分钟，休息一下
4. **使用审查工具**：GitHub、GitLab或专用工具
5. **自动化你能做的**：代码格式化工具、安全扫描
6. **建立关系**：表情符号、表扬和同理心很重要
7. **保持可用**：提供结对编程复杂问题的机会
8. **向他人学习**：审查他人的评论

## 常见陷阱

- **完美主义**：因小风格偏好而阻塞拉取请求
- **范围蔓延**："在修改的同时，你能再..."
- **不一致性**：对不同的人使用不同的标准
- **延迟审查**：让拉取请求闲置数天
- **幽灵**：请求修改后消失
- **橡皮图章**：未经实际审查就批准
- **争论细节**：过度争论琐碎的细节
