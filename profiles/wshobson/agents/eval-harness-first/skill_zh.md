# 评估工具集初探

整个插件的阶段0门禁：
`finetuning-method-selection`（微调方法选择）以及所有下游技能，都假定这个工具集在编写训练配置之前已经存在。这个工具集不是运行结束后的产物——它是数据管理引擎。用于构建黄金数据的标记轨迹，在去除显式保留集后，将作为训练数据。

**输入：** 如果存在，则为生产/代理轨迹；如果不存在，则为任务规范，外加愿意对≥100个示例进行评分的标记员。
**输出格式：** `eval/` 目录下——黄金数据、评分员、漂移套件以及后续阶段门禁的基础模型基线。

## 门禁

没有评估工具集，就无法微调。跳到训练配置，就没有可比较的基准，无法捕获回归，也没有标记数据进行训练。飞轮：

1. **收集轨迹** — 生产/代理跨度，或者如果还没有，则为合成任务。
2. **错误分析** — 对≥100个轨迹进行开放式编码，轴向编码到4-8个故障桶。
3. **每个桶分配一个评分员** — 首先确定性地分配；仅对真正主观的标准使用校准的大型语言模型（LLM）裁判。
4. **按频率×严重性×价值进行优先级排序**。
5. **标记轨迹用于数据集管理，去除显式保留集。** 每个`eval/goldens.jsonl` ID都通过ID从训练数据中排除。
6. **训练。**
7. **在检查点上重新运行相同的工具集** — 不是运行一个不同的、宽松的工具集。
8. **漂移检测将反馈到步骤2** — 新的生产故障模式重新打开错误分析。

步骤2-4构建工具集；步骤5-8是为什么它必须首先存在——它既是训练数据的来源，也是检查点的退出门禁。

## 构建黄金数据

- **当轨迹存在时：** 运行错误分析——对≥100个真实轨迹进行开放式编码（读取它们，用自己的话标记故障，还没有固定的分类法），然后轴向编码将那些标签压缩成4-8个命名的故障桶。少于4个意味着编码过程过于浅层；多于8个意味着需要合并桶。**例外：** 单故障表面的任务（例如严格模式提取）可能落在1-2个桶中，并在一个评分员内部对每个字段进行子度量——不要在没有证据的情况下凭空创建人工分割。
- **当轨迹不存在时：** 基于维度的生成——列举重要的轴（任务类型、难度、边缘情况、角色），并采样交叉积；自由生成的提示会聚集在最容易编写的内容周围。
- **黄金数据像代码一样进行版本控制** — 提交`eval/goldens.jsonl`，在评审中进行差异比较，按发布进行标记。它也充当CI回归套件。

## 评分员

错误分析每个故障桶分配一个评分员——不是为整个评估集分配一个。单个混合分数会隐藏哪个桶发生了回归。

- **首先确定性地分配。** 正则表达式、模式验证或执行检查更便宜、可重复且无需校准。
- **仅对真正主观的标准使用LLM裁判** — 语气、忠实度、“哪个响应更好”——在这些标准上没有确定性检查可以表达。
- **在Likert上二进制通过/失败。** 1-5或1-10的量表校准噪声更大且更难一致应用；压缩为通过/失败。
- **漂移套件MMLU风格的评分：优先使用logprob而不是生成并提取** — 紧凑的标记预算使得生成并提取对那些有前缀的模型解析脆弱，将格式合规性与被测量的知识混淆在一起。所有四种评分员形状的模板和此评分说明：
  `references/grader-templates.md`。

## 裁判校准是先决条件

任何路由到LLM裁判的桶都需要在校准其裁决对探索之外的所有内容都有意义之前进行校准——这是一个硬性先决条件，而不是一个可选项。**当没有桶路由到裁判时无效** — 一个全确定性工具集没有校准对象；明确说明这一点，而不是忽略本节。

- 标记≥100个项目，分割**训练**/**开发**/**密封测试**（报告一次，之后不再触摸）。
- 报告**TPR和TNR**，而不是一个混合的准确率数字——裁判可以通过在偏斜集上始终说“通过”来达到90%。
- **将裁判固定到固定的模型快照**，并在裁判模型更改时重新校准，每季度无论如何都进行。
- **裁判必须来自与被测模型不同的模型系列。**
- 一个错过约定的TPR/TNR标准的裁判将**仅提供咨询**——标记供人工审查，永远不会门禁升级。完整协议、偏差校正和重新校准清单：
  `references/judge-calibration.md`。

## 基线

在阶段1（方法选择）开始之前，运行完整的工具集——黄金数据加上能力漂移套件——对未修改的基础模型。这是每个后续检查点进行比较的数字。

`eval/baseline-<model>.json`是门禁令牌。没有基线文件，就没有`checkpoint-promotion`（检查点升级）的比较基准——一个在未测量内容上“看起来更好”的检查点不是发现。

## 目录契约

```
eval/
├── goldens.jsonl          # 标记轨迹+合成黄金数据，版本控制
├── graders/                # 每个故障桶一个模块
│   ├── schema_compliance.py
│   ├── exact_match.py
│   └── rubric_judge.py
├── drift-suite.yaml        # 固定的基准+200-500个领域相邻的项目
└── baseline-<model>.json   # 门禁令牌：工具集+漂移套件与基础模型对比
runs/
└── <run-id>/
    └── results.json         # 每个运行的工具集输出，每个检查点一个
```

`eval/`跨运行持久存在，并位于`runs/`之外——固定的测量标准，而不是运行工件。`runs/`是可丢弃的；`eval/`不是。永远不要让运行脚本写入`eval/`。**规范位置：** 每个轨迹的`results.json`——包括阶段0基线——位于`runs/<run-id>/results.json`，永远不会在`eval/runs/...`下；要求后者的指令是错误的，而不是这个契约。

### 阶段0退出检查清单

在`finetuning-method-selection`之前，确认：

1. ≥100个轨迹进行开放式编码；4-8个故障桶（对于单一故障表面的合成黄金数据，没有最低限度——见构建黄金数据的例外；桶计数然后来自基线后的错误分析）。
2. `eval/goldens.jsonl`已提交并版本控制。
3. 每个桶一个评分员，首先确定性地分配。
4. 裁判已校准——TPR/TNR，快照已固定，不同系列（**当没有桶路由到LLM裁判时无效**；明确说明）。
5. `eval/drift-suite.yaml`已冻结。
6. `eval/baseline-<model>.json`已写入。

缺少这六项中的任何一项（或其声明的无效情况）？阶段0未完成——`/finetune`在运行前检查基线文件。

## 相关技能

通用评估指南（仪表板、A/B测试、非微调工具集）位于`llm-application-dev`插件的`llm-evaluation`技能中——此技能仅涵盖微调耦合：黄金数据充当训练数据，以及门禁基线。

- `finetuning-method-selection` — 首先路由到这里。
- `dataset-curation` — 将这些轨迹格式化为训练行。
- `trace-to-training-data` — 将评分轨迹转换为训练示例。
- `checkpoint-promotion` — 消耗`baseline-<model>.json`，对每个候选检查点重新运行此工具集。
