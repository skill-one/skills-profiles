# 事件存储设计

为事件溯源应用程序设计事件存储的全面指南。

## 何时使用此技能

- 设计事件溯源基础设施
- 在事件存储技术之间进行选择
- 实现自定义事件存储
- 优化事件存储和检索
- 设置事件存储模式
- 规划事件存储扩展

## 核心概念

### 1. 事件存储架构

```
┌─────────────────────────────────────────────────────┐
│                    事件存储                       │
├─────────────────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐ │
│  │   流 1     │  │   流 2     │  │   流 3     │ │
│  │ (聚合)     │  │ (聚合)     │  │ (聚合)     │ │
│  ├─────────────┤  ├─────────────┤  ├─────────────┤ │
│  │ 事件 1     │  │ 事件 1     │  │ 事件 1     │ │
│  │ 事件 2     │  │ 事件 2     │  │ 事件 2     │ │
│  │ 事件 3     │  │ ...       │  │ 事件 3     │ │
│  │ ...       │  │             │  │ 事件 4     │ │
│  └─────────────┘  └─────────────┘  └─────────────┘ │
├─────────────────────────────────────────────────────┤
│  全局位置：1 → 2 → 3 → 4 → 5 → 6 → ...             │
└─────────────────────────────────────────────────────┘
```

### 2. 事件存储要求

| 要求       | 描述                          |
| ---------- | ----------------------------- |
| **仅追加** | 事件不可变，仅追加操作       |
| **有序**   | 每个流和全局有序             |
| **版本控制** | 乐观并发控制                 |
| **订阅**   | 实时事件通知                 |
| **幂等性** | 安全处理重复写入             |

## 技术对比

| 技术       | 适用于                     | 限制                       |
| ---------- | -------------------------- | -------------------------- |
| **EventStoreDB** | 纯事件溯源                 | 单用途                     |
| **PostgreSQL** | 现有 Postgres 堆栈         | 手动实现                   |
| **Kafka**    | 高吞吐量流式传输           | 不适合每个流的查询         |
| **DynamoDB** | 无服务器，AWS 本地         | 查询限制                   |
| **Marten**   | .NET 生态系统               | .NET 特定                 |

## 最佳实践

### 应该做

- **使用包含聚合类型的流 ID** - `Order-{uuid}`
- **包含关联/因果关系 ID** - 用于追踪
- **从一开始就版本化事件** - 规划模式演进
- **实现幂等性** - 使用事件 ID 进行去重
- **适当索引** - 针对你的查询模式

### 不应该做

- **不要更新或删除事件** - 它们是不可变的事实
- **不要存储大型有效负载** - 保持事件小巧
- **不要跳过乐观并发控制** - 防止数据损坏
- **不要忽视背压** - 处理慢速消费者
