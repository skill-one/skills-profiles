# 领域建模

在设计中积极构建和打磨项目的领域模型。这是一个*主动*的学科——挑战术语、发明边界场景，并在术语明确时立即记录下词汇表和决策。（仅仅*阅读*词汇表来获取词汇不是这项技能——任何技能都可以养成这种单行习惯。这项技能是在你改变模型时使用，而不是仅仅消费它。）

领域模型存在于两个地方：

- **词汇表** — `docs/glossary/`，每个术语一个 markdown 文件，格式符合 `uvx disambiguate` 的要求（见下文）。永远不会有一个根 `CONTEXT.md`。
- **决策** — `docs/adr/` 中的 ADRs，遵循 `writing-adrs` 技能。

词汇表条目、ADR、文档：尽可能简短，偏好原始模式（`caveman` 技能）——精确性和可理解性不能受损。

懒惰地创建文件——只有当你有东西可写时才创建。如果 `docs/glossary/` 不存在，则在第一个术语解析时创建它。

## 会话期间

### 与词汇表进行挑战

当用户使用的术语与 `docs/glossary/` 中的现有语言冲突时，立即指出。 "你的词汇表将 'cancellation' 定义为 X，但你似乎意味着 Y——究竟是哪一个？"

### 锤炼模糊语言

当用户使用模糊或重载的术语时，建议一个精确的规范术语。 "你在说 'account'——你是指 Customer 还是 User？那不是同一回事。"

### 讨论具体场景

当讨论领域关系时，用具体场景进行压力测试。发明场景来探测边界情况，并迫使用户精确地描述概念之间的界限。

### 与代码交叉引用

当用户说明某项工作原理时，检查代码是否一致。如果你发现矛盾，请暴露它： "你的代码取消整个 Orders，但你刚才说部分取消是可能的——哪个是正确的？"

### 内联更新词汇表

当术语解析时，立即在那里编写其词汇表文件。不要批量处理这些——实时捕获它们。

词汇表条目必须完全不含实现细节。词汇表不是规范、草稿板或实现决策的存储库。它只是一个词汇表，除此之外什么都不是。

### 勤俭地提供 ADR

只有在满足 `writing-adrs` 技能中的三项标准时才提供创建 ADR 的建议（难以逆转、没有上下文就令人惊讶、是真实权衡的结果）。格式、编号和位置也来自 `writing-adrs`。

## 词汇表条目格式

`docs/glossary/` 中每个术语一个文件，可被 `uvx disambiguate` 消费：

- **文件名是别名**：小写字母、数字、单个连字符（`order-line.md` → 别名 `order-line`）。别名必须唯一。
- **第一个 H2 是规范名称**（强制）：`## Order Line`。
- **正文是自由形式的 markdown**：一个或两个紧密的句子定义术语是什么，而不是它做什么。当同一个概念存在多个词语时，选择最好的一个，并在 `_Avoid_：` 下列出其他词语。
- **使用标准 markdown 链接交叉引用相关术语**，通过别名（`[Customer](customer.md)`）或维基风格（`[[customer]]`）。这些链接形成 `disambiguate` 以拓扑顺序渲染的依赖图——依赖于另一个术语的术语必须链接它。

示例 `docs/glossary/invoice.md`：

```md
## Invoice

向 [Customer](customer.md) 发送付款请求。

_Avoid_：Bill, payment request
```

规则：

- **要有主见。** 每个概念一个规范术语；竞争性词语放在 `_Avoid_：` 下。
- **只包含此项目上下文中特定的术语。** 即使项目广泛使用，一般编程概念（超时、错误类型、实用模式）也不属于这里。
- 编辑后使用 `uvx disambiguate --lint` 进行验证。
