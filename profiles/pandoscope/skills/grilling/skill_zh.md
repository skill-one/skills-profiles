# 烤箱

与用户进行访谈直至达成共识。逐一走遍决策树的每个分支，处理依赖关系。一次只问一个问题——在问下一个问题前等待答案。*事实*可以在环境中找到：查找，不要询问。*决策*由用户做出——将每个决策都交给用户，等待。未经用户确认，不要采取行动。

命名：问题 `S«s»Q«q»`，答案 `S«s»Q«q»A«n»`。

## 步骤

1. `resolve-store.sh path` — 定位已克隆的商店框架。解析，不要克隆。当商店未命名、未解析或不存在时，以非零状态退出并自行修复其命名；未命名 → 大声说明并记录为空（静默跳过与成功记录无法区分）。商店 URL 仅存在于环境中——不要硬编码，不要将其回显到工件中。
2. `resolve-store.sh unmerged` — 任何记录 → 拒绝打开会话，直到主要用户合并之前的会话，根据 [recording.md](recording.md)。
3. `resolve-store.sh preferences` — 以 JSON 数组的形式发出活动设置，用于会话的 `preferences`：复制，不要重新输入。仅注入该设置，不要注入决策历史。
4. 将每个决策点作为会话 JSON 进行记录——迄今为止的整个会话，包括答案。合同：`render/decision-context.ts` 位于此文件旁边；语义：[format.md](format.md)。永远不要手动格式化问题；渲染器会自行添加自由文本槽位。
5. 渲染面向用户的形式——验证失败会命名违规字段；修复 JSON，重新运行：

   ```bash
   node --experimental-strip-types <skill-dir>/render/render.ts <session.json> --out <dir>
   ```

6. 发布 `session.html` 作为工件，随着会话的增长重新部署相同的 URL；不可用 → 将 `session.md` 原文打印到聊天中——不要作为文件附件，不要作为定时对话框（对话框在用户仍在输入时会关闭）。
7. 答案以页面的复制 JSON 的形式粘贴到聊天中，或作为聊天回复：答案 ID（"S1Q2A1" 或 "1"），通过 "N，但实际上是因为..." 进行更正——简称 "N，BAB..."。目前还没有实时页面到代理的通道（pandoscope/skills#139）。答案的含义：[reading.md](reading.md)。后续：追加新问题以及收到的答案，重新渲染；用户可以重新访问之前的答案。
8. 会话结束：将每个裁决记录到商店中，根据 [recording.md](recording.md) 将拒绝原因嵌入会话的目标工件中。
9. `check.sh <session.json>` — 重新验证会话，验证引用是否为商店原文，当记录未合并时失败，并打印残留内容以供手动验证。

## 问题规则

- 槽位 1 包含预测：当活动规则匹配时（在 `matches` 中命名），偏好驱动，否则冷选择。当槽位 2 的条件语句胜过槽位 1 时，分歧建议位于槽位 2。
- 仅当确实存在未探索的合理分支时使用通配符。
- 如果条件语句 = 当选项胜过推荐。仅当它与否定条件语句不同时，才添加 "为什么没有推荐"。
- 必须标记接近的竞争；对于接近的竞争，永远不要编造弱点，也不要将它们评分为客户流失。
- 更正（"N，但实际上是因为..."，简称 "N，BAB..."）接受选项，覆盖其声明的理由——最高信号事件；在记录中标记。
- 仅当自由文本答案未说明拒绝原因时，才使用一个后续问题（2-3 个排名猜测 + 自由文本）。猜测被视为预测。

## 非目标

不自动接受偏好规则——始终需要人工介入。不使用嵌入/RAG 工具。不进行上游同步。
