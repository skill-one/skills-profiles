# 测试驱动开发

先写测试。提交时是红色。编写最少的代码使其通过。提交变绿。重构。

**核心原则：** 测试通过公共接口验证行为，而不是实现。代码可以完全改变；测试不应该改变。当你重命名一个内部函数时测试就中断了——没有行为变化——那么这个测试就是在测试实现。删除它。

没有监控到的失败 = 没有证据证明测试测试的是正确的东西。提交历史记录是证据；钩子检查其结构。

有关示例，请参阅 [tests.md](tests.md)；有关模拟指南，请参阅 [mocking.md](mocking.md)。

## 铁律

没有先提交失败的测试，就没有生产代码。

在测试之前写了代码？删除它。从测试中重新实现。删除意味着删除。例外情况（一次性原型、生成代码、配置）需要人工批准。想“这次只是跳过 TDD”？那就是合理化。

## 1. 规划（在编写任何代码之前）

使用项目的领域词汇表，以便测试名称和接口词汇与代码库匹配；尊重你触及区域的 ADR。

- 列出要测试的 *行为*，而不是实现步骤。优先考虑关键路径和复杂逻辑——你不能测试所有东西。
- 设计接口以实现 [可测试性](interface-design.md)；识别 [深度模块](deep-modules.md) 的机会（小接口，深实现）
- 与用户确认公共接口和优先行为，然后继续进行。

## 2. 垂直切片，而不是水平

不要先写所有测试，然后写所有实现。那是水平切片，它会产生糟糕的测试：批量编写时，它们测试 *想象的* 行为和事物的 *形状*（签名、数据结构），对实际变化不敏感，并让你在理解代码之前就提交了测试结构。

垂直切片工作——一个测试 → 一个实现 → 重复。每个测试都响应上一周期所教你的内容。

```text
错误（水平）：RED: t1 t2 t3 t4   GREEN: i1 i2 i3 i4
正确（垂直）：t1→i1  t2→i2  t3→i3 ...
```

第一个切片是一个追踪器子弹：它证明了端到端的路径是可行的。

## 3. 提交协议

一个行为 = 一个红色提交 + 一个绿色提交。每个分支可以有多轮；在 Go/Rust 仓库中，更喜欢一次一个周期（见标记）。

**每个提交——包括红色提交——都使树保持无 lint 错误。** 在每次提交后，运行仓库的完整钩子套件在整个树（例如 `prek run --all-files`）：退出码为 0 且没有文件被修改。自动修复器修改文件就是失败——应用修复并将其作为引入问题的提交进行修改，然后再开始下一个周期。CI 仅评估 PR 头部从不原谅脏的中间提交；每次提交的卫生检查在这里，在提交时，或者根本不检查。

### STUB 提交（仅在红色测试需要缺失的 API 表面时）

一个红色提交在 **测试上** 是红色的：lint、格式化和类型检查仍然通过。当新的测试调用一个函数、方法或参数，而它还不存在时，类型检查会失败——所以首先提交一个仅包含最小签名作为其自己的提交，前缀 `chore(stub):`。签名 + 文档字符串，零行为：新的可调用项引发 `NotImplementedError`；新的参数被接受并忽略。这是对铁律的唯一特许例外：stub 定义 *接口*，并且必须不包含 *实现*——stub 提交中的任何逻辑都是没有失败测试的生产代码。当表面已经存在时，完全跳过此步骤。

### 红色提交

- 写一个失败的测试。一个行为，清晰的名称，真实代码——除非不可避免，否则不要使用模拟。
- 运行它 *未标记*；观察它以 **正确的原因** 失败（功能缺失——行为错误，断言失败，或 stub 的 `NotImplementedError`——永远不会是拼写错误、导入错误或缺失符号）。立即通过？它测试了现有行为——修复测试。
- 添加标记（下方），套件变绿，提交。仅测试，前缀 `test(red):`。

| 语言 | 标记 | 严格？ |
| --- | --- | --- |
| Python (pytest) | `@pytest.mark.xfail(strict=True)` | 是——XPASS 使套件失败 |
| TS/JS (vitest) | `test.fails(...)` / `it.fails(...)` | 是 |
| TS/JS (jest) | `it.failing(...)` | 是 |
| Go | `//go:build red` + `TestRed` 前缀 + `red-tests` 任务 | 仅聚合 |
| Rust | `#[ignore = "red"]` + `red_` 前缀 + `red-tests` 任务 | 仅聚合 |
| 其他 | 找到一个严格的预期失败机制；没有这样的机制存在 → 未标记提交，告诉人仓库缺乏红色执行 | n/a |

Go/Rust 构建标签/忽略标记 *排除* 测试的正常套件，因此一个 `red-tests` CI 任务必须仅运行标记的测试并期望失败（当不存在时为空操作）。其退出码是聚合的：两个红色测试正在进行中，一个错误地通过 → 任务仍然通过。严格标记捕获每个测试；任务不捕获。

### 绿色提交

- 通过的最简单代码。YAGNI——不要进行推测性的一般化。
- 移除此周期的红色标记。此提交中没有其他测试更改。
- 套件变绿，输出纯净。失败？修复代码，而不是测试。前缀 `feat:`/`fix:`。

### 重构（仅在绿色之后）

删除重复项，改进名称，提取辅助函数，深化模块。测试保持绿色，没有新行为，单独提交。**永远不要在红色时重构。** 然后开始下一个周期。

## 执行及其限制

`lint-red.sh`（随 skill 提供；连接到 prek + CI）：`staged`/`commit` 模式检查 `test(red):` 提交仅触及测试文件并添加标记，其他添加无标记；`merge` 模式拒绝树中的任何标记；如果存在 Go/Rust 标记，则必须存在 `red-tests` 任务。

钩子验证提交 *结构* 和标记卫生。它们不验证你是否运行了未标记的测试并观察它以正确的原因失败——那仍然是你。对于每次提交的 lint 也是如此：安装的预提交钩子阻止脏提交在提交时阻止，但在没有安装钩子（新的远程环境）的情况下，每次提交后的 `--all-files` 运行是手动纪律——无论如何都要做。严格标记部分补偿（XPASS 捕获测试现有行为的测试）。“Lint 通过”≠“TDD 验证”。

## 好的测试

| 质量 | 规则 |
| --- | --- |
| 行为性 | 执行公共 API 的真实路径；在重构中存活 |
| 最小化 | 一个东西。名称中有“和”？拆分它。 |
| 清晰 | 名称声明行为，而不是 `test1` |
| 诚实 | 测试代码，而不是模拟 |

```ts
// 好——测试真实行为（vitest；jest: it.failing）
test.fails('retries failed operations 3 times', async () => {
  let attempts = 0;
  const op = () => { attempts++; if (attempts < 3) throw new Error('fail'); return 'ok'; };
  expect(await retryOperation(op)).toBe('ok');
  expect(attempts).toBe(3);
});
```

## 红色警告——停止，删除，重启

未标记的测试在实现存在之前通过 · 无法解释为什么测试失败 · 在绿色中减弱断言以使其通过 · 测试模拟 · “只是这一次” · “我正在务实地做，TDD 是教条的。”

阅读 [testing-anti-patterns.md](testing-anti-patterns.md) 以避免常见陷阱。

## 合理化表格

| 找借口 | 现实 |
| --- | --- |
| “太简单，不需要测试” | 简单代码会崩溃。测试需要 30 秒。 |
| “我之后会测试” | 之后的测试受到实现的偏差影响：“这个做什么？”而不是“这个应该做什么？” |
| “删除数小时的代码是浪费” | 沉没成本。未验证的代码是债务。 |
| “写测试很困难” | 难以测试 = 难以使用。倾听它；简化接口。 |
| “必须模拟所有东西” | 太耦合。注入依赖项。 |
| “Lint 通过，TDD 完成” | 钩子检查结构，而不是你观察失败。 |

## 当卡住/调试时

不知道如何测试 → 先写期望的 API 和断言。发现了一个错误 → 写一个失败的测试来重现它，然后运行完整协议。永远不要在没有测试的情况下修复错误。
