## 步骤

### 第 1 步：准备工作

调用 `/impeccable`，其中包含设计原则、反模式以及**情境收集协议**。在进行下一步之前，请遵循该协议。如果还没有设计情境，你必须先运行 `/impeccable teach`。此外，收集：界面试图实现的目标。

### 第 2 步：收集评估

启动两个独立的评估。**两者都不能看到对方的输出**，以避免偏见。

你应该将每个评估委托给一个单独的子代理，以确保独立性。使用你环境中的代理生成机制（例如，Claude Code 的 `Agent` 工具，或 Codex 的子代理生成）。子代理应以结构化文本的形式返回他们的发现。目前不要将发现输出给用户。

如果当前环境中没有子代理可用，请按顺序完成每个评估，在继续之前将发现写入内部笔记。

**标签隔离**：当浏览器自动化可用时，每个评估都必须创建一个新标签页。即使有一个已经打开在正确的 URL 上，也绝对不要重用现有标签页。这可以防止两个评估相互干扰页面状态。

#### 评估 A：LLM 设计审查

阅读相关的源文件（HTML、CSS、JS/TS），如果浏览器自动化可用，请视觉检查活动页面。**为这个创建一个新标签页**；不要重用现有标签页。导航后，通过设置文档标题来标记标签页：
```javascript
document.title = '[LLM] ' + document.title;
```
像设计总监一样思考。评估：

**AI 滑稽检测（关键）**：这看起来像其他所有 AI 生成的界面吗？对照 impeccable 技能中所有 **DON'T** 指南进行审查。检查 AI 色彩调板、渐变文本、暗光晕、玻璃态设计、英雄指标布局、相同的卡片网格、通用字体以及所有其他迹象。**测试**：如果有人说是 AI 制作的，你会立即相信他们吗？

**整体设计审查**：视觉层次结构（视线流、主要操作清晰度）、信息架构（结构、分组、认知负荷）、情感共鸣（是否与品牌和受众匹配）、可发现性（交互元素是否明显）、构图（平衡、空白、节奏）、排版（层次结构、可读性、字体选择）、色彩（有目的的使用、一致性、可访问性）、状态和边缘情况（空、加载、错误、成功）、微文案（清晰度、语气、帮助性）。

**认知负荷**（参考 [cognitive-load](reference/cognitive-load.md)）：
- 运行 8 项认知负荷检查清单。报告失败次数：0-1 = 低（好），2-3 = 中等，4+ = 关键。
- 计算每个决策点的可见选项。如果 >4，请标记它。
- 检查渐进式披露：复杂性是否仅在需要时才显示？

**情感旅程**：
- 这个界面唤起什么情感？这是有意为之的吗？
- **峰终定律**：最强烈的时刻是积极的吗？体验是否结束良好？
- **情感低谷**：检查在高风险时刻（支付、删除、提交）的焦虑峰值。是否有设计干预（进度指示器、安抚文案、撤销选项）？

**Nielsen 的启发式方法**（参考 [heuristics-scoring](reference/heuristics-scoring.md)）：
为 10 个启发式方法中的每一个评分 0-4。这些评分将在报告中呈现。

返回结构化发现，包括：AI 滑稽裁决、启发式方法评分、认知负荷评估、哪些方面做得好（2-3 项）、优先问题（3-5 项，包括什么/为什么/修复）、轻微观察结果和启发性问题。

#### 评估 B：自动检测

运行捆绑的确定性检测器，该检测器标记 25 个特定模式（AI 滑稽迹象 + 一般设计质量）。

**CLI 扫描**：
```bash
npx impeccable --json [--fast] [目标]
```

- 将 HTML/JSX/TSX/Vue/Svelte 文件或目录作为 `[目标]` 传递（任何带有标记的内容）。不要传递纯 CSS 文件。
- 对于 URL，跳过 CLI 扫描（它需要 Puppeteer）。使用浏览器可视化代替。
- 对于大型目录（200+ 可扫描文件），使用 `--fast`（仅正则表达式，跳过 jsdom）
- 对于 500+ 文件，缩小范围或询问用户
- 退出码 0 = 清洁，2 = 发现

**浏览器可视化**（当浏览器自动化工具可用并且目标是可查看页面时）：

覆盖层是**为用户提供的视觉辅助工具**。它直接在用户的浏览器中突出显示问题。不要滚动页面来截图覆盖层。相反，请通过控制台输出以编程方式获取结果。

1. **启动实时检测服务器**：
   ```bash
   npx impeccable live &
   ```
   注意 stdout 打印的端口（自动分配）。使用 `--port=PORT` 来固定它。
2. **创建一个新标签页**并导航到页面（对于本地文件，使用开发服务器 URL，或直接 URL）。不要重用现有标签页。
3. **通过 `javascript_tool` 标记标签页**，以便用户可以区分它：
   ```javascript
   document.title = '[Human] ' + document.title;
   ```
4. **滚动到顶部**以确保页面滚动到最顶部后再注入
5. **通过 `javascript_tool` 注入**（将 PORT 替换为步骤 1 中的端口）：
   ```javascript
   const s = document.createElement('script'); s.src = 'http://localhost:PORT/detect.js'; document.head.appendChild(s);
   ```
6. 等待 2-3 秒，让检测器渲染覆盖层
7. **从控制台读取结果**，使用 `read_console_messages` 并使用模式 `impeccable`。检测器使用 `[impeccable]` 前缀记录所有发现。不要滚动页面来截图覆盖层。
8. **清理**：完成时停止实时服务器：
   ```bash
   npx impeccable live stop
   ```

对于多视图目标，在 3-5 个代表性页面上注入。如果注入失败，请仅使用 CLI 结果继续。

返回：CLI 发现（JSON）、浏览器控制台发现（如果适用）以及任何标记的误报。

### 第 3 步：生成综合批评报告

将两个评估综合成一个报告。不要简单地连接。将发现结合起来，注明 LLM 审查和检测器在哪里达成一致，检测器在哪里发现了 LLM 遗漏的问题，以及检测器发现是误报的地方。

以设计总监的方式组织你的反馈：

#### 设计健康评分
> *参考 [heuristics-scoring](reference/heuristics-scoring.md)*

以表格形式呈现 Nielsen 的 10 个启发式方法评分：

| # | 启发式方法 | 评分 | 关键问题 |
|---|-----------|-------|-----------|
| 1 | 系统状态的可见性 | ? | [具体发现或“n/a”如果稳固] |
| 2 | 系统与现实世界的匹配 | ? | |
| 3 | 用户控制和自由 | ? | |
| 4 | 一致性和标准 | ? | |
| 5 | 错误预防 | ? | |
| 6 | 识别而非记忆 | ? | |
| 7 | 灵活性和效率 | ? | |
| 8 | 美学和极简设计 | ? | |
| 9 | 错误恢复 | ? | |
| 10 | 帮助和文档 | ? | |
| **总计** | | **??/40** | **[评级范围]** |

对分数要诚实。4 分意味着真正优秀。大多数真实界面得分在 20-32 之间。

#### 反模式裁决

**从这里开始。** 这看起来像 AI 生成的吗？

**LLM 评估**：你自己的 AI 滑稽迹象评估。涵盖整体美学感觉、布局相同性、通用构图、错失的个性机会。

**确定性扫描**：总结自动检测器发现的内容，包括计数和文件位置。注意检测器捕捉到你遗漏的任何额外问题，并标记任何误报。

**视觉覆盖层**（如果使用了浏览器）：告诉用户他们的浏览器中 **[Human]** 标签页现在可见，突出了检测到的问题。总结控制台输出报告的内容。

#### 整体印象
一个简短的直觉反应：什么有效，什么无效，以及最大的机会是什么。

#### 做得好的地方
突出 2-3 件做得好的事情。具体说明为什么它们有效。

#### 优先问题
最有影响力的 3-5 个设计问题，按重要性排序。

对于每个问题，标记 **P0-P3 严重性**（参考 [heuristics-scoring](reference/heuristics-scoring.md) 获取严重性定义）：
- **[P?] 什么**：清晰地命名问题
- 为什么它很重要：这对用户有什么伤害或如何破坏目标
- 修复：要做什么（要具体）
- 建议的命令：哪个命令可以解决这个问题（来自：/animate, /quieter, /shape, /optimize, /adapt, /clarify, /layout, /distill, /delight, /audit, /harden, /polish, /bolder, /typeset, /critique, /colorize, /overdrive)

#### 人设警告
> *参考 [personas](reference/personas.md)*

自动选择 2-3 个与这种界面类型最相关的人设（使用参考中的选择表）。如果 `.github/copilot-instructions.md` 包含来自 `impeccable teach` 的 `## 设计情境` 部分，则根据受众/品牌信息生成 1-2 个项目特定的人设。

对于每个选择的人设，走过主要用户操作并列出发现的特定警告：

**Alex（高级用户）**：没有检测到键盘快捷键。表单需要 8 次点击才能执行主要操作。强制模态引导。高放弃风险。

**Jordan（初学者）**：侧边栏中的图标导航。错误消息中使用技术术语（“404 未找到”）。没有可见的帮助。会在第 2 步放弃。

要具体。命名导致每个人设失败的确切元素和交互。不要写通用的人设描述；写出了什么对他们造成了破坏。

#### 轻微观察结果
关于值得解决的问题的小快注。

#### 值得思考的问题
可能解锁更好解决方案的启发性问题：
- “如果主要操作更突出，会怎样？”
- “这需要感觉这么复杂吗？”
- “自信的版本会是什么样子？”

**记住**：
- 要直接。模糊的反馈浪费大家的时间。
- 要具体。“提交按钮”，而不是“一些元素”。
- 说出问题所在，以及为什么这对用户很重要。
- 给出具体的建议，而不仅仅是“考虑探索……”
- 残酷地优先排序。如果所有事情都很重要，那么什么都不重要。
- 不要软化批评。开发者需要诚实的反馈来发布出色的设计。

### 第 4 步：询问用户

**在展示发现之后**，使用基于实际发现的目标问题。直接询问用户澄清你不能推断的内容。这些答案将塑造行动计划。

提出类似以下问题（根据具体发现进行调整；绝对不要问通用问题）：

1. **优先方向**：根据发现的问题，询问用户现在哪个类别对用户最重要。例如：“我发现视觉层次结构、色彩使用和信息过载有问题。我们应该首先解决哪个领域？”提供前 2-3 个问题类别作为选项。

2. **设计意图**：如果批评发现了一个语调不匹配，询问这是否是故意的。例如：“界面感觉临床和公司化。这是预期的语调，还是应该感觉更温暖/更有力/更活泼？”根据发现的问题提供 2-3 个语调方向作为选项。

3. **范围**：询问用户希望承担多少工作。例如：“我发现 N 个问题。要解决所有问题，还是专注于前 3 个？”提供范围选项，如“仅前 3 个”，“所有问题”，“仅关键问题”。

4. **限制**（可选；只有当相关时才询问）：如果发现涉及许多领域，询问是否有任何禁区。例如：“是否应保持某些部分不变？”这可以防止计划触及用户认为已完成的内容。

**问题的规则**：
- 每个问题都必须参考报告中的具体发现。永远不要问通用的“你的受众是谁？”类型的问题。
- 最多保持 2-4 个问题。尊重用户的时间。
- 提供具体的选项，而不是开放式提示。
- 如果发现是明确的（例如，只有 1-2 个明确的问题），请跳过问题并直接进入第 5 步。

### 第 5 步：推荐行动

**在收到用户的答案之后**，呈现一个反映用户在第 4 步中优先级和范围的优先行动摘要。

#### 行动摘要

按优先级列出推荐的命令，基于用户的答案：

1. **`/command-name`**：简要说明要修复的内容（具体批评发现中的上下文）
2. **`/command-name`**：简要说明（具体上下文）
...

**推荐规则**：
- 仅推荐来自：/animate, /quieter, /shape, /optimize, /adapt, /clarify, /layout, /distill, /delight, /audit, /harden, /polish, /bolder, /typeset, /critique, /colorize, /overdrive 的命令
- 按用户声明的优先级排序，然后按影响排序
- 每个项目的描述应包含足够的上下文，以便命令知道要关注什么
- 将每个优先问题映射到适当的命令
- 跳过不会解决任何问题的命令
- 如果用户选择了有限范围，则仅包括该范围内的项目
- 如果用户标记了禁区，则排除会触及这些区域的命令
- 如果建议了修复，则以 `/polish` 作为最后一步结束
- 告诉用户：
>
> 你可以问我一次运行这些，一次运行所有，或按你喜欢的任何顺序运行。
>
> 修复后重新运行 `/critique` 以查看你的分数提高。
