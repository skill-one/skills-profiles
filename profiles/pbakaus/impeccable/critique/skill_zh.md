## STEPS

### Step 1: Preparation

调用 `/imineeble`，其中包含设计原则、反模式以及 **Context Gathering Protocol**（情境收集协议）。在继续之前，请遵循该协议。如果目前尚无设计情境，你**必须**先运行 `/imineeble teach`。此外，请收集以下信息：界面试图实现什么目标。

### Step 2: Gather Assessments

启动两项独立的评估。**两项评估均不得查看对方的输出**，以避免产生偏差。

你**应当**将每项评估分别委托给独立的子代理进行，以确保独立性。使用当前环境的代理生成机制（例如 Claude Code 的 `Agent` 工具，或 Codex 的子代理生成方式）。子代理应以结构化文本返回其发现结果。**暂时不要向用户输出这些发现结果**。

如果当前环境中不可用子代理，则依次完成每项评估，并在继续之前将发现结果写入内部笔记。

**标签隔离**：当可浏览器自动化时，每项评估**必须**创建自己的新标签页。即使存在已打开的正确 URL 的标签页，也**绝不**复用现有标签页。这样可以防止两项评估相互干扰页面的状态。

#### Assessment A: LLM Design Review

阅读相关源文件（HTML、CSS、JS/TS），如果可浏览器自动化，请对实时页面进行视觉检查。**为该评估创建新标签页**；不得复用现有标签页。导航后，通过设置文档标题对标签页进行标记：
```javascript
document.title = '[LLM] ' + document.title;
```
以设计总监的思维进行评估：

**AI 劣质内容检测（关键）**：这是否看起来像所有其他 AI 生成的界面？对照 impeccable 技能中**所有的** **DON'T**（禁用）准则进行审查。检查 AI 色板、渐变文字、暗色光晕、玻璃拟态、首屏指标布局、相同卡片网格、通用字体以及其他一切特征。**测试标准**：如果有人说"AI 生成了这个"，你是否会立刻相信？

**整体设计评审**：视觉层级（视线流动、主要操作清晰度）、信息架构（结构、分组、认知负荷）、情感共鸣（是否匹配品牌和受众）、可发现性（交互元素是否明显）、构图（平衡、留白、节奏）、排版（层级、可读性、字体选择）、色彩（使用目的性、一致性、可访问性）、状态与边界情况（空、加载、错误、成功）、微观文案（清晰度、语调、有用性）。

**认知负荷**（参考 [cognitive-load](reference/cognitive-load.md)）：
- 执行 8 项认知负荷检查清单。报告失败项数量：0-1 为低（良好），2-3 为中等，4+ 为严重。
- 统计每个决策点可见的选项数量。若超过 4 个，需标记。
- 检查是否有渐进式披露：是否仅在需要时才揭示复杂性？

**情感旅程**：
- 该界面唤起何种情感？这是有意的吗？
- **峰终定律**：最强烈的时刻是正向的吗？体验以良好的结局收尾吗？
- **情感低谷**：检查高 stakes（高利害）时刻（支付、删除、提交）是否存在焦虑激增（是否出现问题）。是否存在设计干预（进度指示、安抚文案、撤销选项）？

**Nielsen 启发式原则**（参考 [heuristics-scoring](reference/heuristics-scoring.md)）：
为每一项启发式原则打分 0-4 分。该评分将呈现在报告中。

返回结构化发现结果，涵盖：AI 劣质内容判定、启发式评分、认知负荷评估、有效之处（2-3 项）、优先问题（3-5 项，含问题/原因/修复方法）、次要观察，以及有启发性的问题。

#### Assessment B: Automated Detection

运行捆绑的确定性检测器，该检测器可标记 25 个特定模式（AI 劣质内容特征 + 通用设计质量）。

**CLI 扫描**：
```bash
npx impeccable --json [--fast] [target]
```

- 将 HTML/JSX/TSX/Vue/Svelte 文件或目录作为 `[target]`（任何具有标记文件的）传入。**不得传入仅含 CSS 的文件**。
- 对于 URL，跳过 CLI 扫描（其需要 Puppeteer）。使用浏览器可视化检查。
- 对于 200+ 的可扫描文件的大型目录，使用 `--fast`（仅正则表达式，跳过 jsdom）
- 对于 500+ 文件，缩小范围或询问用户
- 退出码 0 = 干净，2 = 有发现

**浏览器可视化**（当可浏览器自动化工具且目标为可查看页面时）：

覆盖层是**面向用户的辅助工具**。它在浏览器中直接高亮问题。**不要**通过滚动页面以截图覆盖层。相反，通过读取控制台输出来以编程方式获取结果。

1. **启动实时检测服务器**：
   ```bash
   npx impeccable live &
   ```
   注意打印到标准输出的端口（自动分配）。使用 `--port=PORT` 固定端口。
2. **创建新标签页**并导航到页面（本地文件使用开发服务器 URL，或使用直接 URL）。不得复用现有标签页。
3. 通过 `javascript_tool` **标记标签页**，以便用户可以区分：
   ```javascript
   document.title = '[Human] ' + document.title;
   ```
4. **滚动到顶部**，确保在注入之前页面已滚动至最顶部
5. 通过 `javascript_tool` **注入**（将 PORT 替换为第 1 步中获取的端口）：
   ```javascript
   const s = document.createElement('script'); s.src = 'http://localhost:PORT/detect.js'; document.head.appendChild(s);
   ```
6. 等待 2-3 秒，让检测器渲染覆盖层
7. **使用 `read_console_messages` 以模式 `impeccable` 从控制台读取结果**。检测器以 `[impeccable]` 前缀记录所有发现结果。**不要**通过滚动页面以覆盖层的截图。
8. **清理**：完成后停止实时服务器：
   ```bash
   npx impeccable live stop
   ```

对于多视图目标，在 3-5 个代表性页面上进行注入。如果注入失败，仅继续使用 CLI 结果。

返回：CLI 发现结果（JSON）、浏览器控制台发现结果（如适用），以及任何标记的误报。

### Step 3: Generate Combined Critique Report

将两项评估综合为单一报告。**不要**简单拼接。将发现结果交织在一起，指出 LLM 评审与检测器一致之处、检测器发现 LLM 遗漏的问题之处，以及检测器发现的误报之处。

以设计总监的视角组织反馈：

#### 设计健康评分
> *参考 [heuristics-scoring](reference/heuristics-scoring.md)*

将 Nielsen 的 10 项启发式原则评分以表格形式呈现：

| # | Heuristic | Score | Key Issue |
|---|-----------|-------|-----------|
| 1 | Visibility of System Status | ? | [具体发现或"n/a"，若健全则填写] |
| 2 | Match System / Real World | ? | |
| 3 | User Control and Freedom | ? | |
| 4 | Consistency and Standards | ? | |
| 5 | Error Prevention | ? | |
| 6 | Recognition Rather Than Recall | ? | |
| 7 | Flexibility and Efficiency | ? | |
| 8 | Aesthetic and Minimalist Design | ? | |
| 9 | Error Recovery | ? | |
| 10 | Help and Documentation | ? | |
| **Total** | | **??/40** | **[评分区间]** |

对评分要诚实。4 分表示 genuinely excellent（真正出色）。大多数真实界面评分为 20-32 分。

#### 反模式判定

**从此处开始。** 这是否看起来是 AI 生成的？

**LLM 评估**：你对 AI 劣质内容特征的自身评估。涵盖整体审美感受、布局同质化、通用构图、被忽视的个人化机会。

**确定性扫描**：总结自动化检测器发现的内容，含数量和文件位置。注明检测器还发现哪些你遗漏的问题，并标记任何误报。

**视觉覆盖层**（如使用浏览器）：告知用户覆盖层现在显示在浏览器的 **[Human]** 标签页中，高亮检测到的问题。总结控制台输出报告的内容。

#### 总体印象
简短的直观感受：什么做得好，什么没做好，以及最大的改进机会。

#### 做得好的地方
突出 2-3 项做得好的地方。具体说明为何有效。

#### 优先问题
按重要程度排序的 3-5 个最具影响力的设计问题。

对每个问题，用 **P0-P3 严重度** 进行标记（参考 [heuristics-scoring](reference/heuristics-scoring.md) 了解严重度定义）：
- **[P?] 问题是什么**：清晰命名问题
- **为何重要**：这如何损害用户或削弱目标
- **修复**：应如何处理（具体）
- **建议命令**：哪个命令可解决此问题（来自：/animate, /quieter, /shape, /optimize, /adapt, /clarify, /layout, /distill, /delight, /audit, /harden, /polish, /bolder, /typeset, /critique, /colorize, /overdrive）

#### 角色标志
> *参考 [personas](reference/personas.md)*

自动选择与该界面类型最相关的 2-3 个角色（使用参考中的选择表格）。如果 `.github/copilot-instructions.md` 包含来自 `impeccable teach` 的 `## Design Context` 章节，也根据受众/品牌信息生成 1-2 个项目特定角色。

对每个选定的角色，走一遍该角色的主要用户操作，列出发现的具体标志：

**Alex（高级用户）**：未检测到键盘快捷键。主要操作需 8 次点击。对新手设置强制弹窗。放弃风险高。

**Jordan（新手）**：侧边栏仅用图标导航。错误消息使用技术术语（"404 Not Found"）。无可见帮助。在第二步就会放弃。

具体说明。指明每个角色受阻的具体元素和交互。不要写通用的角色描述；要写针对该角色的具体问题。

#### 次要观察
对较小但值得解决的问题的快速备注。

#### 需要考虑的问题
可能开启更佳解决方案的有启发性的问题：
- "如果主要操作更突出一些会如何？"
- "它是否需要这么复杂？"
- "自信的版本会是什么样子？"

**记得**：
- 直接。模糊的反馈浪费所有人时间。
- 具体。"提交按钮"，而非"某些元素"。
- 说明问题**以及**为何对用户重要。
- 给出具体建议，而非仅"考虑探索……"。
- 无情地优先排序。如果所有事项都重要，则都没有。
- 不要软化批评。开发者需要诚实反馈才能打造出色的设计。

### Step 4: Ask the User

**呈现发现结果后**，基于实际发现的内容，使用针对性问题询问用户。直接询问用户以澄清无法推断的内容。这些答案将塑造行动计划。

沿着以下思路提问（根据具体发现进行调整；**不要**问通用问题）：

1. **优先方向**：根据发现的问题，询问用户当前最看重哪类问题。例如："我发现了视觉层级、色彩使用和信息过载的问题。我们应该优先解决哪个领域？"提供前 2-3 个问题类别作为选项。

2. **设计意图**：如果评审发现语调不匹配，询问这是否有意的。例如："该界面感觉临床且企业化。这是预期的语调，还是应该更温暖/更醒目/更有趣？"根据发现的问题能解决的方向，提供 2-3 个语调方向作为选项。

3. **范围**：询问用户希望承担多少工作。例如："我发现了 N 个问题。想处理全部，还是仅关注前 3 个？"提供范围选项，如"仅前 3 个"、"全部问题"、"仅关键问题"。

4. **约束**（可选；仅当相关时询问）：如果发现触及多个方面，询问是否有哪些事项不允许改动。例如："是否有任何板块应保持原样？"这防止计划改动用户认为已完成的区域。

**问题规则**：
- 每个问题都必须参考报告中具体的发现。**不要**问通用的"你的受众是谁？"这类问题。
- 最多 2-4 个问题。尊重用户时间。
- 提供具体选项，而非开放式的提示。
- 如果发现结果直接（例如仅 1-2 个明确问题），跳过问题，直接进入 Step 5。

### Step 5: Recommended Actions

**收到用户答案后**，呈现反映 Step 4 中用户优先级和范围的优先行动摘要。

#### 行动摘要

根据用户答案，按优先级列出建议命令：

1. **`/命令名称`**：说明要修复的内容（基于评审发现的具体背景）
2. **`/命令名称`**：说明（基于具体背景）
...

**推荐规则**：
- 仅推荐来自以下命令：/animate, /quieter, /shape, /optimize, /adapt, /clarify, /layout, /distill, /delight, /audit, /harden, /polish, /bolder, /typeset, /critique, /colorize, /overdrive
- 按用户声明的优先级排序，然后按影响排序
- 每个条目的描述应包含足够上下文，使命令知道应关注什么
- 将每个优先问题映射到适当的命令
- 跳过可能解决零问题的命令
- 如果用户选择了有限范围，仅包含范围内的项目
- 如果用户标记了某些区域为禁区，排除会触及这些区域的命令
- 如果推荐了任何修复，以 `/polish` 作为最终步骤结束

呈现摘要后，告知用户：

> 我可以让你逐一执行这些命令、一次性执行，或按你偏好的任何顺序执行。
>
> 修复后重新运行 `/critique` 以查看分数提升。
