推动界面突破常规界限。这不仅仅是视觉效果的问题——而是利用浏览器的全部能力，让界面中的任何部分都呈现出非凡的体验：能够处理百万行数据的表格、随触发按钮变形的对话框、带有流式反馈的实时验证表单、带有电影感的页面过渡。

## 强制准备

调用 /Impeccable —— 其中包含设计原则、反模式以及 **Context Gathering Protocol**（上下文收集协议）。在进行操作前，必须遵循该协议——如果目前尚不存在设计上下文，您必须先执行 /Impeccable teach。

**针对本技能的额外重要提示**：上下文决定了"非凡"的含义。创意作品集上的粒子系统令人印象深刻；但同一套粒子系统放在设置页上则会显得尴尬。而带有即时乐观保存和动画状态过渡的设置页？那同样是非凡的。在决定什么是合适的之前，必须理解项目的个性和目标。

### 构建前先提案

本技能发生失误的可能性最高。切勿直接跳入实现阶段。您必须：

1. **梳理 2-3 种不同的方向** —— 考虑不同的技术、不同的 ambition（雄心）以及美学思路。针对每个方向，简要描述其结果会呈现什么样的视觉效果和体验。
2. **直接询问用户澄清无法推断的内容。** 在编写任何代码之前，向用户展示这些方向并征求其选择。说明其中的权衡（浏览器支持、性能成本、复杂度）。
3. 仅选择用户确认的方向继续推进。

跳过此步骤，存在构建出尴尬且需要丢弃的界面的风险。

### 使用浏览器自动化迭代

技术上具有雄心的效果几乎不可能一上来就成功。您必须积极使用浏览器自动化工具预览作品、视觉上验证结果并进行迭代。不要 assumption（假设）效果看起来正确——要进行检查。需要期待多轮精细调整。"技术上可行"与"看起来非凡"之间的差距，是通过视觉迭代而非仅靠代码来填补的。

## 评估此处"非凡"的含义

合适的技术雄心完全取决于你正在处理的内容。在选定技术之前，问自己：**会让 THIS 特定界面的用户说出"哇，真不错"的是什么？**

### 针对视觉/营销界面
页面、首屏区域、落地页、作品集——这里的"wow"往往是感官层面的：由滚动驱动的展示、着色器背景、电影感的页面过渡、响应鼠标指针的生成艺术。

### 针对功能性界面
表格、表单、对话框、导航——"wow"在于它给人的感受：通过 View Transitions 从触发它的按钮变形而来的对话框、通过虚拟滚动以 60fps 渲染十万行数据的表格、带有流式验证且感觉即时响应的表单、带有弹簧物理效果的拖放功能。

### 针对性能关键界面
"wow"虽不可见但可感知：搜索能够无闪烁地筛选 5 万条数据、复杂的表单从不阻塞主线程、图像编辑器在近实时状态下进行处理。界面始终不犹豫。

### 针对数据密集型界面
图表和仪表盘——"wow"在于流畅感：通过 Canvas/WebGL 为海量数据集进行 GPU 加速渲染，数据状态之间的动画过渡，自然收敛的力导向图布局。

**共同点**：实现方式在某种层面超越了用户对 Web 界面所期待的水平。技术的运用服务于体验，而非反过来。

## 工具包

按你想要实现的目标分类，而非按技术名称分类。

### 让过渡带有电影感
- **View Transitions API**（同文档：所有浏览器；跨文档：Firefox 不支持）——状态之间共享元素的变形。列表项展开为详情页。按钮变形为对话框。这是最接近原生 FLIP 动画的东西。
- **`@starting-style`**（所有浏览器）——仅用 CSS 将元素的 `display: none` 动画到可见状态，包含入场关键帧
- **弹簧物理** —— 使用质量、张力、阻尼实现自然运动，而非 cubic-bezier。可用的库：motion（原名 Framer Motion）、GSAP，或自行实现弹簧求解器。

### 将动画与滚动位置绑定
- **Scroll-driven animations**（`animation-timeline: scroll()`）——纯 CSS，无需 JS。视差、进度条、展示序列均由滚动位置驱动。（Chrome/Edge/Safari；Firefox：仅 flag 可用——始终提供静态回退方案）

### 超越 CSS 渲染
- **WebGL**（所有浏览器）——着色器效果、后期处理、粒子系统。可用的库：Three.js、OGL（轻量级）、regl。用于 CSS 无法表达的视觉效果。
- **WebGPU**（Chrome/Edge；Safari 部分支持；Firefox：仅 flag 可用）——新一代 GPU 计算。比 WebGL 更强大，但浏览器支持有限。始终回退到 WebGL2。
- **Canvas 2D / OffscreenCanvas** —— 自定义渲染、像素操作，或通过 Web Workers + OffscreenCanvas 将大量渲染完全移出主线程。
- **SVG filter chains** —— 位移图、湍流、形态学，用于有机扭曲效果。可通过 CSS 动画。

### 让数据充满生命力
- **虚拟滚动** —— 仅渲染表格/列表中可见的行数，适用于数万条数据的场景。简单场景无需库；复杂场景使用 TanStack Virtual。
- **GPU 加速图表** —— 针对超出 SVG/DOM 承载能力的超大规模数据集，使用 Canvas 或 WebGL 渲染数据可视化。可用的库：deck.gl、基于 regl 的自定义渲染器。
- **动画数据过渡** —— 在图表状态之间变形过渡，而非替换。使用 D3 的 `transition()` 或 View Transitions 处理基于 DOM 的图表。

### 动画复杂属性
- **`@property`**（所有浏览器）——注册具有类型的自定义 CSS 属性，从而能够对 CSS 通常无法插值的渐变、颜色和复杂值进行动画。
- **Web Animations API**（所有浏览器）——基于 JavaScript 的动画，具备 CSS 的性能。可组合、可取消、可逆转。复杂编排的基础。

### 突破性能边界
- **Web Workers** —— 将计算移出主线程。大量数据处理、图像操作、搜索索引——任何可能导致卡顿的工作。
- **OffscreenCanvas** —— 在 Worker 线程中进行渲染。主线程保持空闲，而复杂的视觉效果在后台渲染。
- **WASM** —— 为计算密集型功能提供接近原生的性能。图像处理、物理模拟、编解码器。

### 与设备交互
- **Web Audio API** —— 空间音频、音频响应可视化、音效反馈。需要用户手势才能启动。
- **Device APIs** —— 方向、环境光、地理定位。应谨慎使用，且始终需要用户授权。

**注意**：本技能旨在增强界面给人的感受，而非改变产品本身的功能。添加实时协作、离线支持或新的后端能力属于产品决策，而非 UI 增强。重点在于让现有功能呈现出非凡的体验。

## 以纪律实施

### 渐进增强是必须的

每种技术都必须能够优雅降级。不应用增强时，体验也必须仍然良好。

```css
@supports (animation-timeline: scroll()) {
  .hero { animation-timeline: scroll(); }
}
```

```javascript
if ('gpu' in navigator) { /* WebGPU */ }
else if (canvas.getContext('webgl2')) { /* WebGL2 fallback */ }
/* CSS-only fallback must still look good */
```

### 性能规则

- 目标为 60fps。若低于 50fps，则简化。
- 始终遵守 `prefers-reduced-motion` —— 这是无障碍要求，而非建议。提供精美的静态替代方案。
- 仅在靠近视口时，懒加载重型资源（WebGL 上下文、WASM 模块）。
- 暂停离屏渲染。销毁不可见的部分。
- 在实际的中端设备上测试，而不仅仅是你的开发电脑。

### 打磨是差异所在

"酷"与"非凡"之间的差距，在于最后 20% 的精细打磨：弹簧动画的缓动曲线、错落展示中的时间偏移、让过渡感觉具有物理质感的微妙二次运动。不要交付第一个能运行的版本——交付那个感觉必然的版本。

**绝不**：
- 忽略 `prefers-reduced-motion` —— 这是无障碍要求，而非建议
- 交付在中端设备上导致卡顿的效果
- 在不具备可用回退方案的情况下使用前沿 API
- 未经明确用户许可添加声音
- 用技术雄心掩盖薄弱的设计基础——应首先使用其他技能修复这些问题
- 叠加多个相互竞争的非凡瞬间——聚焦才能产生影响力，多余只会制造噪音

## 验证结果

- **"Wow" 测试**：向从未见过它的人展示。他们有反应吗？
- **移除测试**：将其拿走。体验是否显得减弱，还是没人注意到？
- **设备测试**：在手机、平板、Chromebook 上运行。是否仍然流畅？
- **无障碍测试**：启用 reduced motion。是否仍然美观？
- **上下文测试**：这对 THIS 品牌和受众来说是否合理？

请记住："技术上非凡"并非指使用最新的 API。而是让界面做到用户没想到一个网站能够做到的事情。
