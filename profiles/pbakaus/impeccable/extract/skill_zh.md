识别可复用的模式、组件和设计令牌，然后将它们提取并整合到设计系统中，以实现系统化复用。

## 发现

分析目标区域以识别提取机会：

1. **找到设计系统**：定位你的设计系统、组件库或共享 UI 目录（使用 grep 搜索“设计系统”、“ui”、“components”等）。了解其结构：
   - 组件组织方式及命名规范
   - 设计令牌结构（如果存在）
   - 文档模式
   - 导入/导出规范
   
   **关键**：如果不存在设计系统，在创建前先询问。先了解首选位置和结构。

2. **识别模式**：寻找：
   - **重复使用的组件**：多次使用的相似 UI 模式（按钮、卡片、输入等）
   - **硬编码值**：应作为令牌的颜色、间距、排版、阴影等
   - **不一致的变体**：同一概念的多种实现（3种不同的按钮样式）
   - **可复用模式**：值得系统化的布局模式、组合模式、交互模式

3. **评估价值**：并非所有内容都应提取。考虑：
   - 是否使用3次以上或可能被复用？
   - 系统化是否提高一致性？
   - 这是通用模式还是特定上下文？
   - 维护成本与收益如何？

## 规划提取

创建系统化提取计划：

- **要提取的组件**：哪些 UI 元素将成为可复用组件？
- **要创建的令牌**：哪些硬编码值将成为设计令牌？
- **要支持的变体**：每个组件需要哪些变体？
- **命名规范**：组件名、令牌名、属性名需与现有模式匹配
- **迁移路径**：如何重构现有使用以消费新的共享版本

**重要**：设计系统逐步发展。现在明确可复用的内容进行提取，而非所有可能未来可复用的内容。

## 提取与丰富

构建改进的可复用版本：

- **组件**：创建设计良好的组件，具备：
  - 清晰的属性 API 及合理默认值
  - 适用于不同场景的适当变体
  - 内置可访问性（ARIA、键盘导航、焦点管理）
  - 文档和用法示例
  
- **设计令牌**：创建令牌，具备：
  - 清晰命名（原始 vs 语义）
  - 合适的层级和组织
  - 每个令牌使用场景的文档
  
- **模式**：文档化模式，包含：
  - 使用该模式的场景
  - 代码示例
  - 变体和组合

**绝不**：
- 未泛化就提取特定上下文的单次实现
- 创建过于通用以致无用的组件
- 未考虑现有设计系统规范就提取
- 跳过 TypeScript 类型或属性文档
- 为每个单一值创建令牌（令牌应有语义意义）

## 迁移

用新的共享版本替换现有使用：

- **查找所有实例**：搜索已提取的模式
- **系统化替换**：更新每个使用以消费共享版本
- **彻底测试**：确保视觉和功能一致性
- **删除冗余代码**：移除旧实现

## 文档

更新设计系统文档：

- 将新组件添加到组件库
- 文档化令牌使用和值
- 添加示例和指南
- 更新 Storybook 或组件目录

记住：良好的设计系统是动态系统。随着模式出现就提取，深思熟虑地丰富它们，并保持一致维护。
