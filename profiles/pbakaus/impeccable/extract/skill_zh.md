识别可复用的模式、组件和设计令牌，然后将它们提取并整合到设计系统中，以便进行系统性复用。

## 发现

分析目标区域，识别提取机会：

1. **定位设计系统**：查找你的设计系统、组件库或共享 UI 目录（grep for "design system", "ui", "components", etc.）。了解其结构：
   - 组件组织与命名规范
   - 设计令牌结构（如有）
   - 文档编写模式
   - 导入/导出规范
   
   **关键提示**：如果没有现成设计系统，在创建之前应先确认。先了解首选位置与结构。

2. **识别模式**：查找：
   - **重复组件**：多次使用的相似 UI 模式（按钮、卡片、输入框等）
   - **硬编码值**：应作为令牌的颜色、间距、排版、阴影等
   - **不一致的变体**：同一概念的多种实现（3 种不同按钮样式）
   - **可复用模式**：值得系统化的布局模式、组合模式、交互模式

3. **评估价值**：并非所有内容都应提取。需考虑：
   - 该内容使用次数是否达到 3 次以上，或是否可能复用？
   - 系统化整理是否提升了一致性？
   - 这是通用模式还是特定场景模式？
   - 维护成本与收益如何？

## 规划提取

制定系统化的提取计划：

- **需提取的组件**：哪些 UI 元素将变成可复用组件？
- **需创建的设计令牌**：哪些硬编码值将转化为设计令牌？
- **需支持的变体**：每个组件需要哪些变体？
- **命名规范**：与现有模式匹配的组件名称、令牌名称、属性名称
- **迁移路径**：如何重构现有使用方式，以消费新的共享版本

**重要提示**：设计系统应逐步成长。提取当前明确可复用的内容，而非日后可能可复用的所有内容。

## 提取与丰富

构建改进、可复用的版本：

- **组件**：创建设计精良的组件，包含：
   - 清晰的属性 API 与合理的默认值
   - 针对不同使用场景的合适变体
   - 内置可访问性（ARIA、键盘导航、焦点管理）
   - 文档与使用示例

- **设计令牌**：创建令牌时需注意：
   - 清晰命名（原始令牌 vs 语义令牌）
   - 合理的层级与组织
   - 说明每个令牌的适用场景

- **模式**：记录模式时需包含：
   - 何时使用此模式
   - 代码示例
   - 变体与组合

**切勿**：
- 提取未经过抽象化的、仅针对特定场景的一次性实现
- 创建过度通用的组件以至于变得无意义
- 不考虑现有设计系统规范就进行提取
- 跳过正确的 TypeScript 类型或属性文档
- 为每一个值创建令牌（令牌应带有语义含义）

## 迁移

用新的共享版本替换现有使用方式：

- **查找所有实例**：搜索已提取的模式
- **系统性地替换**：更新每个使用处，使其消费共享版本
- **充分测试**：确保视觉与功能上的一致性
- **删除无效代码**：移除旧的实现

## 文档

更新设计系统文档：

- 将新组件添加到组件库
- 记录令牌使用与值
- 添加示例与指南
- 更新任何 Storybook 或组件目录

记得：一个优秀的设计系统是活的系统。随着模式的出现而提取模式，审慎地丰富它们，并保持它们的一致性。
