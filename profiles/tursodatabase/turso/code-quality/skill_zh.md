# 代码质量指南

## 核心原则

生产数据库。正确性至上。崩溃 > 损坏。

## 正确性规则

1. **不允许使用临时解决方案或快速修复。** 处理所有错误，检查不变式
2. **频繁使用断言。** 不要静默失败或吞掉边界情况
3. **在可能破坏数据完整性的无效状态下崩溃。** 不要在未定义的状态下继续执行
4. **考虑边界情况。** 在足够长的时间线内，所有可能的错误都会发生

## Rust 模式

- 使非法状态无法表示
- 使用穷尽的模式匹配
- 优先使用枚举而不是字符串/哨兵
- 最小化堆分配
- 编写对 CPU 友好的代码（微秒 = 长时间）

## if 语句

错误：
```rust
if condition {
    // 正常路径
} else {
    // "不应该发生" - 被静默忽略
}
```

正确：
```rust
// 如果只有一个分支应该被触发：
assert!(condition, "违反了不变式：...");
// 或者
return Err(LimboError::InternalError("意外状态".into()));
// 或者
unreachable!("不可能的状态：...");
```

只有当两个分支都是预期路径时，才使用 if 语句。

## 注释

**应该做：**
- 记录为什么，而不是记录什么
- 记录函数、结构体、枚举、变体
- 关注为什么需要这样做

**不应该做：**
- 重复代码的注释
- 引用 AI 对话（"这个测试应该触发错误"）
- 时间标记（"添加的"、"现有代码"、"第一阶段"）

## 避免过度设计

- 仅进行直接请求或明显必要的更改
- 不要添加超出所请求的功能
- 不要向未更改的代码添加文档字符串/注释
- 不要为不可能的情况添加错误处理
- 不要为一次性操作创建抽象
- 三个相似的行 > 过早的抽象

## 索引变更

当代码涉及索引插入、删除或冲突解决时，请再次检查与 SQLite 的顺序。错误的顺序会导致索引不一致，并且很容易被忽略。

## 确保理解 IO 模型

- [异步 IO 模型](../async-io-model/SKILL.md)

## 清理

- 完全删除未使用的代码
- 没有向后兼容的修复（重命名的 `_vars`、重新导出、`// 删除` 注释）
