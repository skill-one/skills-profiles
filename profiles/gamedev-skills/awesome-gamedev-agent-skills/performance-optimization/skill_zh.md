# 性能优化

性能工作是一项衡量纪律，而非一堆技巧。方法始终相同：**分析 → 找到瓶颈点 → 修复它 → 再次衡量**。这项技能教你这个循环以及最高杠杆的修复方法（对象池化、批量处理、分配控制、资源预算），并指引你使用每个引擎的分析器。它与 `physics-tuning` 配合使用，用于模拟成本。

## 何时使用

- 当帧率低或不稳定、游戏卡顿/顿挫，或者需要达到目标（桌面 60 FPS、移动端 30/60 FPS）但目前未达标时使用。
- 用于决定优化什么：分析、读取帧预算，并在更改任何代码之前确定 CPU 还是 GPU 是瓶颈。
- 用于应用特定修复：对象池化、绘制调用/批量减少、移除每帧分配和垃圾回收峰值，以及设置资源预算。

**何时*不*使用**：针对物理抖动/隧道效应/时间步长问题，使用 `physics-tuning`。对于引擎的具体分析器 UI 和渲染设置，使用相应引擎的技能（`godot-export` 覆盖部分构建设置；引擎核心涵盖其余部分）。这项技能是跨引擎方法，以及共享修复方法。

## 金科玉律：先衡量，绝不猜测

大多数未经分析就应用的性能“修复”会针对错误的目标，并带来无益的复杂性。**不要优化未经过衡量的代码**。打开分析器，在代表性硬件上的代表性场景中找到最大的单次成本，并修复它。在继续之前重新衡量以确认修复是否有效。在**发布/优化构建**中进行分析——编辑器和调试构建会撒谎（编辑器开销、无编译器优化）。

## 核心工作流程

1. **定义目标和重现**。陈述目标（例如 60 FPS = 16.67 ms/帧），并找到一个可重复的最差场景。“有时慢”是无法修复的；可重复的峰值是可以修复的。
2. **在触碰代码前进行分析**。运行引擎分析器并读取帧：总帧时间，以及 CPU（游戏逻辑、物理、脚本）和 GPU（渲染）之间的时间分配。
3. **找到瓶颈——CPU 或 GPU**。如果 GPU 时间 ≫ CPU，则攻击绘制调用/过度绘制/着色器/分辨率。如果 CPU 时间占主导，则攻击脚本/物理/分配。修复错误的一侧毫无作用。
4. **修复最大的单次成本**。优先考虑**算法**上的胜利（减少工作量、缓存、空间划分、减少运行频率），而不是微调热点行。应用匹配的共享修复（池化、批量处理、移除分配）。
5. **在相同的场景/硬件上重新衡量**。确认数字是否移动。根据数据而不是直觉决定保留或还原。
6. **设置预算以保持稳定**。每个子系统的每帧 ms 预算，以及资源预算（纹理大小、三角形数量、绘制调用上限）；在验证中添加性能检查。
7. **报告衡量数据**。陈述前后帧时间、找到的瓶颈以及修复措施——绝不“应该更快”。如果你只能编辑器中衡量，请说明。

## 模式

### 1. 帧预算计算（将“感觉慢”转化为数字）

```text
目标 FPS → 帧预算：   60 FPS = 16.67 ms   |   30 FPS = 33.3 ms   |   120 FPS = 8.33 ms
整个帧（CPU 模拟 + 渲染提交 + GPU）必须符合预算；GPU 并行运行，因此 CPU 帧和 GPU 帧较慢者决定 FPS。分配子预算，例如 @60 FPS：
  游戏脚本 ~5 ms · 物理 ~3 ms · 渲染（CPU 提交）~4 ms · UI/其他 ~2 ms · 空闲。
如果某个子系统超出其分配，那就是你的目标——不是你假设的任何值。
```

### 2. 使用引擎分析器衡量（在任何修复之前执行此操作）

```text
Godot 4.7 : 调试器 ▸ 分析器（脚本/物理时间）和监视器选项卡（FPS、绘制调用、内存）。
            代码中：Performance.get_monitor(Performance.TIME_PROCESS) 和
            Performance.get_monitor(Performance.RENDER_TOTAL_DRAW_CALLS_IN_FRAME)。
Unity 6.3 LTS   : 分析器窗口（CPU/GPU/内存/渲染模块）+ 帧调试器用于绘制调用。
            代码中：一个跟踪“CPU 主线程帧时间”用于 HUD/日志的 ProfilerRecorder。
Unreal 5  : `stat unit`（帧/游戏/绘制/GPU ms）、`stat fps`、`stat scenerendering`（绘制调用）；
            Unreal Insights 用于深度跟踪。
# 读取分配：是绘制/GPU 行最大，还是游戏/CPU 行最大？这决定了修复方法。
```

### 3. 对象池化（停止在热点循环中分配/释放）

```gdscript
# 子弹、粒子、敌人、伤害数字：重复使用固定集，而不是每帧使用 instantiate()/free() —
# 这会消耗内存，并在 C# 中为垃圾回收器提供数据。
var _pool: Array[Node] = []
func acquire() -> Node:
    var n: Node = _pool.pop_back() if not _pool.is_empty() else bullet_scene.instantiate()
    n.set_process(true); n.visible = true
    return n
func release(n: Node) -> void:
    n.set_process(false); n.visible = false       # 禁用 + 隐藏；不要 free
    _pool.append(n)                                # 回到池中以供重复使用
# 正确：在加载时预热池；重复使用。错误：每发子弹使用 instantiate()/queue_free()。
```

### 4. 减少绘制调用（最常见的 GPU 端胜利）

```text
每个唯一的材质/纹理/状态更改大致是一个绘制调用；成千上万个它们会阻塞 GPU。
- 使用图集纹理并共享材质，使精灵/网格批量处理为一个调用。
- 相同的网格 → GPU 实例化（Unity）、MultiMesh / MultiMeshInstance（Godot）、实例化静态网格（Unreal）。
- 静态几何体 → 静态批量处理/烘焙；将非移动对象标记为静态。
- 减少过度绘制：限制大型重叠的透明/粒子层（它们会重新着色像素）。
- 更少的实时灯光/阴影；在不会移动的地方烘焙光照。
衡量绘制调用前后的情况——调用次数应该减少，GPU 帧时间也应该减少。
```

### 5. 停止每帧分配（垃圾回收峰值 = 卡顿）

```csharp
// Unity 6.3 LTS (C#)。每帧分配会填满托管堆；垃圾回收器会因此卡住一帧。
// 错误（每次调用分配）：foreach (var e in FindObjectsOfType<Enemy>()) ...  // + LINQ, new[]
// 正确：缓存引用一次，重用缓冲区，避免在 Update 中使用 LINQ/装箱。
void Update() {
    _hits = Physics.RaycastNonAlloc(ray, _hitBuffer);   // 重用预分配的数组
    for (int i = 0; i < _hits; i++) { /* ... */ }       // 无每帧分配
}
// Godot/GDScript：避免在 _process 中每帧构建新的数组/字典；重用它们。
```

## 陷阱

- **未经分析优化**。直观的罪魁祸首通常是错误的。每次都要先衡量。
- **分析编辑器/调试构建**。编辑器开销和非优化代码会误导。在目标硬件上分析发布构建以获取真实数据。
- **修复错误的一侧**。当 GPU 是瓶颈时微调 CPU 代码（反之亦然）毫无作用。首先检查 CPU 与 GPU 的分配。
- **过度优化算法**。当 O(n²) 循环或每帧全场景查询是真正成本时，削减一个函数。减少工作量，而不是打磨它。
- **热点循环中分配/释放**。每帧生成和销毁子弹/粒子会导致碎片化和垃圾回收峰值。池化它们。
- **Update 中每帧分配/LINQ/装箱**（C#）会为垃圾回收器提供数据→周期性卡顿。缓存并重用。
- **绘制调用爆炸**来自唯一材质和未批量处理的精灵/网格。图集，共享材质，实例化，批量处理。
- **过度绘制**来自堆叠的透明/粒子/全屏效果重新着色像素。
- **无预算**。没有每个子系统的 ms 和资源上限，性能会无声退化；在构建/CI 检查中强制执行它们。
- **过早优化**。在原型有趣或衡量之前，不要扭曲原型以进行性能优化。

## 相关技能

- `physics-tuning` — 模拟成本、固定步长预算、睡眠物体、广域相位层。
- `godot-export` — 影响衡量性能的发布/构建设置。
- `procedural-gen`, `game-ai` — 常见的 CPU 热点（生成、路径查找）以预算和延迟。
- `roguelike`, `tower-defense`, `survival-crafting` — 需要池化/预算的实体密集型类型。
