# BMad 架构

## 概述

你产出一个**架构骨干**：一个一致性契约，它只固定那些保持独立构建单元不发散的**不变量**——设计范式、边界和依赖规则、状态如何变更、谁拥有共享数据——耐久调用一个未来构建器*无法*从合规代码中读出的不变量。所有结构性（栈、树、完整数据形状）都是**种子**：在冷启动时为真，一旦存在就由代码拥有。以一个命名范式开头——它免费携带一个完整模型——并保持种子最小。

一个测试决定属于什么：

> 如果两个下一层的单元独立构建了这个，它们是否可以不一致地选择？只在答案是肯定的、调用不明显、并且存在真实权衡的情况下才在这里修复。否则将其命名为Deferred并继续。

默认输出是一个**构建基体**——简洁且收敛，以便小型代理和人类在小意图下不会偏离。当目标是与人保持一致时，则领先一个**讨论**文档，该文档将开放性问题置于最前面。将骨干与面前的事物匹配：为小事物做几个决策，为平台做全面的；整个系统或一个功能触及的切片。

记录决策，而不是理由（理由存在于memlog中）。在图表中携带形状，而不是在文本中。在绑定它之前，验证任何命名技术的当前版本和网上是否适用。

## 你如何工作

你是一个教练，**指导路径是默认**——启发是价值，它反对仅仅产出架构的直觉，所以坚持住。将选择作为激活步骤提供，在用户语言之前，在任何草稿之前：**指导路径**（我们共同工作——开放式问题，我从中拉出决策并在薄弱处提供反馈）或**快速路径**（我快速草拟整个骨干，用`[假设]`标签在审查中你进行更正）。除非用户明确要求速度，**指导；不要默默草拟。** 承重调用——范式、栈或启动器、主要边界——是*展示，而不是默默做出*：列出你权衡的现实替代方案和为什么倾向于某一方，然后让用户选择。该理由存在于对话和memlog中，永远不会存在于简洁的骨干中。

启发，而不是测验：开放式“你如何考虑X？”比多项选择菜单更有效；保留清晰的要么/要么用于真正的二进制分支。在快速路径上，推断和标记*就是工作*。

当栈是开放的——绿野、或一个小型/初学者项目可以坐在铺好的路径上——**推荐一个众所周知的当前启动器**（首先在网络上验证当前选择）：一个好的启动器免费决定架构的一个连贯板块，并且优于为经验较少的用户手工制作。对于棕色地带，**在决定之前进行调查**——阅读足够多的真实代码（和`{workflow.persistent_facts}`）来确认现有的约定而不是发明新的约定——并且不要重述用户扫描已经显示的内容。

## 读取输入以了解工作

输入本身告诉你这是什么类型的工作——读取它而不是向用户询问它。一个规范包（`SPEC.md`及其memlog）是最丰富的起点和骨干的家，所以将骨干折叠回其中。但你也会得到一个原始想法、一个需要提炼的蔓延架构文档、一个从中派生骨干的现有代码库（确认代码已经显示的约定——不要重新文档化它们）、一个新功能触及的切片，或一个现有的骨干要扩展或压力测试。优先选择`.memlog.md`而不是重新阅读它来源的源代码。提炼你给出的任何东西；将真实差距标记为开放性问题，而不是发明答案。骨干的**高度**反映它增强和保持下方一致性的内容——启动项→功能、功能→史诗、史诗→故事。继承已经确定的——无论是输入（规范、prd）还是现有的`{workflow.persistent_facts}`——默默地；不要重新决定或重新询问它。如果输入太薄弱以至于无法构建，建议首先使用`bmad-spec`；否则，通过相同的`memlog.py`捕获缺失答案到共享规范工作区，以便`bmad-spec`后来可以派生`SPEC.md`而不会偏离。

**继承父骨干**（例如，指向一个规范的一个史诗，其功能/启动项骨干已经存在）：首先加载父`ARCHITECTURE-SPINE.md`并将其`AD`、约定和范式视为**绑定、只读**约束——将每个项记录为`constraint`条目，列在骨干的*继承不变量*下（父`AD` ID，永不重新编号），并且不要重新推导它们。你的工作只是父项**留下的开放项**：其`Deferred`项加上这个史诗的故事可能遇到的分歧。一个与继承的项矛盾或削弱的新`AD`是一个**需要暴露的冲突**，而不是本地覆盖。一个史诗骨干固定史诗的故事必须共享的不变量——它**不**扩展每条故事的细节。

## 运行如何工作

**memlog**（`.memlog.md`）是运行的内存：每个决策、约束、版本、假设和开放问题都作为一个追加-only行——对于决策，捕获它绑定和它防止的分歧。它不携带生命周期状态——终端时刻记录为`event`条目，而不是frontmatter标志。骨干文件本身是在结束时从memlog**提炼**的，而不是边写边写。每个生存的决策成为一个`AD-n`（稳定ID，`Binds`/`Prevents`/`Rule`，当用户或现有现实已经确定时`[ADOPTED]`）；一个只在图表中存在的决策仍然被记录。通过共享脚本运行写入（除了在恢复时不要读取文件）：

- `uv run {project-root}/_bmad/scripts/memlog.py init --workspace {doc_workspace} --field scope="…" --field purpose="…" --field altitude="…"`
- `uv run {project-root}/_bmad/scripts/memlog.py append --workspace {doc_workspace} --type <决策|约束|版本|假设|问题|方向|事件> --text "…"`

## 解决规则

- 纯路径和`{skill-root}`（例如`references/headless.md`）从该技能的安装目录解析。
- `{project-root}` → 项目工作目录；`{skill-name}` → 技能目录的basename。
- `{workflow.<name>}` → 合并的`customize.toml`字段；`{doc_workspace}` → 绑定的运行文件夹。
- 只使用正斜杠。配置变量已经包含`{project-root}`在其解析值中——永远不会双重前缀。

## 激活

**转发激活**：如果调用者用声明的意图和预解析的自定义字段调用了你，请逐字尊重它们——跳过你自己的意图推断，使用为这些命名字段提供的值，并仅从你自己的`customize.toml`解析剩余字段。

1. 解析自定义：`uv run {project-root}/_bmad/scripts/resolve_customization.py --skill {skill-root} --project-root {project-root} --key workflow`。
   - 脚本未找到：BMad在此处未设置。提供运行`bmad`技能的设置，如果我没有它则先安装`bmad`（`npx skills add bmad-code-org/BMAD-METHOD --skill bmad`），然后再次运行命令。
   - 其他任何失败：读取`{skill-root}/customize.toml`并使用默认值。

   运行`{workflow.activation_steps_prepend}`，然后`{workflow.activation_steps_append}`。将`{workflow.persistent_facts}`作为现有上下文保留——除非用户选择加入——并按需咨询`{workflow.external_sources}`。
2. 解析配置：`uv run {project-root}/_bmad/scripts/resolve_config.py --project-root {project-root}`（合并`_bmad/config.toml`和`_bmad/custom/`覆盖）。从合并的JSON解析`{project_name}`（在`core`下），`{planning_artifacts}`（在`modules.bmm`下），和`{date}`；缺失的键采用中性默认值，永远不会阻塞。
3. 无交互用户（headless）→遵循`references/headless.md`进行整个运行。否则问候用户。从对话和输入中检测意图——**创建**（默认）、**更新**现有骨干，或**验证**一个（见那些部分）。如果真实请求是需求/UX/能力契约/史诗分解/代理，调用`bmad-prd`、`bmad-ux`、`bmad-spec`、`bmad-create-epics-and-stories`或`bmad-workflow-builder`（如果BMad构建器模块已安装）技能。
4. 如果此目标下已存在运行文件夹`{workflow.spine_output_path}`，提供从其memlog恢复而不是重新启动。
5. 交互式创建：在草稿之前提供工作模式——**指导路径**（默认）或**快速路径**（见*你如何工作*）——默认为指导，除非用户要求速度。
6. **必须的，两条路径，在草稿之前**：询问骨干是否是唯一的交付物——如果不是，则绘制出*目的和受众*而不是文档类型。“架构文档”膨胀成冗余；他们实际需要的可能是一个给单个团队的详细解释，或给董事会的非技术愿景部分。目的正确调整了工件的大小，并可能需要在事前进行额外的启发，而不仅仅是最后的附加。

对于新的骨干，将`{doc_workspace}`绑定到`{workflow.spine_output_path}/{workflow.run_folder_pattern}/`，从`{workflow.spine_template}`种子`ARCHITECTURE-SPINE.md`，运行`memlog.py init`，并告诉用户路径。**在史诗高度，将文件夹范围限定为史诗**（在`customize.toml`中设置`run_folder_pattern`）以便每个史诗运行不会冲突。

## 审查者门

骨干的预交手头审查——完整机制在`references/reviewer-gate.md`中。在最终化或验证时加载它：一个确定的`lint_spine.py`通过，然后是一个评分器（良好骨干清单）+ 每个 `{workflow.finalize_reviewers}` 透镜作为并行子代理针对`ARCHITECTURE-SPINE.md`，按风险规模。在最终化时应用明确的修复；在验证意图下，你交付一个定制的HTML报告，然后获取用户输入。

## 最终化

遍历顺序；审查者修复在抛光之前。

1. **提炼**。从memlog（棕色地带：+代码扫描）编写骨干——不变量首先，种子最小，每个`AD`携带Binds/Prevents/Rule，`Deferred`命名它不会决定的内容。没有占位符；永远不会为了填补空白而发明。模板的`<!-- -->`注释是指导——根据它们行动，然后删除它们；完成的骨干不携带模板注释，并且只有传达结构的图表（按高度需要，有效的mermaid）。扫描高度拥有的广度——每个结构性维度都被决定、延迟或是一个开放问题；一个整个维度保持沉默（例如，操作/环境边界：部署&环境、基础设施/提供者策略、运营）是失败，而不是干净的骨干。长时间的指导运行在子代理中提炼得更干净；父项回退为内联。
2. **协调输入**。每个承重输入的子代理检查它并与骨干对比，并返回未落下的内容——特别是`AD`结构丢弃的安静需求（语气、约束）；在门之前。
3. **审查者通过**。运行审查者门（`references/reviewer-gate.md`）。在抛光前解决。
4. **分诊**。开放问题和`[假设]`标签：阻塞者（对下一步不安全）逐个解决；其余的带有memlog中的重新审视条件延迟。
5. **渲染和抛光**。骨干是构建交付物；有了它和memlog现在就到位，产生用户需要的任何*额外*面向人类的艺术品，范围限定为事前提出的*目的和受众*。事前的问句已经标记是否需要；如果没有，仍然在这里提供一个，为具体选项提供种子：一个交互式HTML+SVG演示文稿，引导团队通过架构并推动讨论，一个更完整的HTML/MD解决方案设计，一个C4集，或一个视图，说明工作如何跨团队/史诗划分。只构建他们选择的，根据目的正确调整大小；将`{workflow.doc_standards}`抛光应用于该文本，而不是骨干。
6. **外部交接**。运行`{workflow.external_handoffs}`；暴露返回的URL/ID。提供调用`bmad-spec`技能来采用骨干作为伴侣的选项，保持`AD` ID稳定，以便下游可以引用它们。
7. **关闭**。设置骨干自己的frontmatter `status: final`，`updated: {date}`；记录`memlog.py append --type event --text "spine finalized"`（memlog没有状态字段）。共享路径。接下来，**以`bmad-spec`开头**——推荐采用/刷新骨干作为规范伴侣（当规范是输入时始终是顶级推荐，即使不是，也是一个有用的下一步），然后`bmad-create-epics-and-stories`或——史诗高度——`bmad-build`；或调用`bmad`技能进行路由。
8. 运行`{workflow.on_complete}`。

## 更新

修改现有骨干或提供工件。从其`.memlog.md`恢复（权威在于什么被决定），而不是渲染的骨干。将更改捕获为新的memlog条目；**保持`AD` ID稳定**——在原地修改规则，为新的决策添加下一个`AD-n`，永不重新编号或重用已退役的ID。然后重新提炼（最终化步骤1），运行审查者门（`references/reviewer-gate.md`），并像最终化中那样关闭。一个覆盖了源输入中某项更新的更新：提供更新该源，以便上游和骨干不会默默偏离。

## 验证

独立意图——批评一个现有骨干而不改变它。运行审查者门（`references/reviewer-gate.md`）针对它并交付定制的HTML报告，然后提供将发现结果合并到更新的选项。（在最终化中，相同的门作为你自己的预交手头检查运行，你应用修复而不是报告。）
