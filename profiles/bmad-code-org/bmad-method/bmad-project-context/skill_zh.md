# 概述

一个生成仓库代理指令的对话：`AGENTS.md` 内一个小的已验证代码块。用户带来他们想要遵循的规则——治理、安全、标准——而仓库提供其余部分，并验证其内容。

始终是对话式；用户批准每个写入操作。

**参数：** 意图（`setup` | `adopt` | `refresh` | `record` | `audit`）；目标仓库或路径；额外的源路径或 URL。

## 解析规则

- 纯路径和 `{skill-root}`（例如 `references/best-practices.md`）从该技能的安装目录解析。
- `{project-root}` → 项目工作目录。
- **目标** → 被描述的仓库，默认为 `{project-root}`。如果它解析到多个工作树，或用户无法在其中提交，则在写入前询问。

## 激活时

1.  解析自定义：`uv run {project-root}/_bmad/scripts/resolve_customization.py --skill {skill-root} --project-root {project-root} --key workflow`。
   - 脚本未找到：BMad 在此未设置。建议运行 `bmad` 技能的设置，如果尚未安装 `bmad` 则先安装 `bmad`（`npx skills add bmad-code-org/BMAD-METHOD --skill bmad`），然后再次运行该命令。
   - 其他任何失败：直接读取 `{skill-root}/customize.toml` 并使用默认值。

   执行 `{workflow.activation_steps_prepend}`；将 `{workflow.persistent_facts}` 条目视为持久上下文（`file:` = 路径/通配符以加载，其他为纯文本）。
2.  配置：如果存在 `{project-root}/_bmad`，则 `uv run {project-root}/_bmad/scripts/resolve_config.py --project-root {project-root}` 并读取 `{output_folder}`。独立运行：跳过。
3.  **在其他任何操作之前加载 `references/best-practices.md` 和 `references/template.md`。** 以下每个决策都是基于它们做出的。
4.  检测意图并向用户打招呼：**setup**（目标中的指令文件不包含有意义的内容——仅脚手架、空标题、注释、单独的导入行不是有意义的；不确定时，采用，因为采用一个近乎空的文件会花费一个小账本，而设置一个有意义的文件会丢失指令）、**adopt**（指令文件包含内容但没有管理块，无论其状态和谁编写它——迁移形式为 refresh；该文件是基线，其中每条指令都进入步骤 1 的账本）、**refresh**（存在管理块）、**record**（用户报告代理犯的错误）、**audit**（重新验证并修剪）。提供的意图与检测到的内容矛盾——例如 `setup` 对一个包含内容的文件——会暴露并确认，永远不会默默服从。将 `{workflow.external_sources}` 合并到源列表中。执行 `{workflow.activation_steps_append}`。

## 设置、采用和刷新步骤

直到第 5 步之前不进行写入！

### 1. 评估和报告

读取 `AGENTS.md`、特定于 harness 或代理的规则文件、文档文件夹以及任何包含经验教训的笔记。报告存在的内容及其符合 `best-practices.md` 的程度。

现有指令是正在改进的基线，而不是要丢弃的原始材料。打开一个 **账本**：每条现有部分和每个独立有意义的指令各一个条目，在 `retain` 或 `rewrite` 下打开，包含代理在没有它的情况下会出错的内容。条目随着步骤 2–4 中出现的证据而结算——`retain | rewrite | relocate | automate | delete`，每项都有其理由、证据、如果删除的风险、重新定位的目的地以及批准标志。删除需要 `best-practices.md` 中的四个理由之一，并且重新定位目的地必须本身被加载或位于一个可观察的触发器之后——移动到一个没有任何内容读取的文件是删除，需要其理由。设置没有要映射的内容，也不会打开账本；刷新为它提议更改或删除的行或块本身打开条目。在指令文件之外发现的教训——README 中的警告、笔记文件——是普通候选者，不是账本条目。

如果目标包含可分离的单元——一个列出成员的工作区清单，或包含自己的构建清单的目录——命名它们并询问此运行是否仅覆盖根目录、全部、或哪些。没有该证据，不要询问。兄弟仓库不是子代；每个都是自己的目标，依次提供。

### 2. 询问他们带来的内容

无论仓库做什么都要遵循的规则：治理、安全和合规、编码标准、风格指南、冻结区域。也询问外部文档——手册、维基、架构文档、MCP 知识库。记录路径；不要立即读取它们。

绿色字段：这是全部内容。棕色字段：扫描无法触及的是一半。

### 3. 发现和验证

使用并行子代理针对各部分的需求展开——可执行配置和 CI 以用于政策和它们已经声明的内容、跟踪源以用于规范和边界、有针对性的历史记录以用于其理由仍需保留的约束。

`package.json`、`Makefile`、`pyproject.toml`、贡献指南、拉取请求模板和 CI 配置被读取，以了解块不应重复的内容。它们的注意事项来自步骤 4 中的用户。路径检查命名文件的每个声明。对于块将要声明的关于命令的内容的每个声明，读取运行它的目标或脚本并验证该声明。

步骤 1 中同意的每个子项都作为其自己的范围进行扫描，针对其自己的清单。

### 4. 访谈差距

只有扫描无法触及的内容：代理在此处持续出错的内容、禁止区域、领域术语的含义、约束存在的原因。

- 永远不要询问扫描可以回答的内容。要求用户确认路径检查的声明，或配置文件已经声明的声明，是缺陷。
- 询问回忆问题，而不是审查列表。永远不要将用户交给扫描创建的选择问题。
- 本会话发现的错误并被捕获是观察证据——提供它。
- 在本会话读取的任何内容中发现的重复命令——日志、文档、其自身的运行——其正确形式不是显而易见的猜测是候选行：提供它。例如 `uv run pytest`，其中 `pytest` 看起来正确但在项目环境中运行。
- 最多八个批次；更少更好。一个批次产生无新内容意味着写入。
- 当仓库与用户矛盾时，显示证据并询问。永远不会给出所提供的声明，也永远不会默默丢弃。

### 5. 显示块，然后写入它

针对 `template.md` 进行编写。对于每个候选项，首先询问是否有钩子、lint 规则或 CI 检查比文字更好地执行它；如果是，则提议检查，并且如果他们拒绝，则该行成为后备。标记为 `automate` 的账本条目会保留其指令，直到其检查到位（稍后运行在检查启动后根据第 2 条地删除该行）。

**在写入它之前显示完整的块**，以及所有子块——一个批准涵盖整个集合。**显示已解决的账本**：仅替换文本是不完整的提案，因为它显示了用户获得的内容并隐藏了他们失去的内容。每条现有指令都显示其决策和理由。保留和重写的规则保持完整可能被分组。如果重写削弱、缩小或丢弃了规则的一部分，则将丢失的部分视为删除并单独列出。保留规则本身；示例可以解释它但不能替代它。每个重新定位、自动化和删除都被列出来。基于前三个理由之一的删除被保留用于逐行批准——批准块永远不会批准它——并且拒绝的删除、重新定位或自动化会恢复为保留。批准后，在标记之间拼接——拼接本身不触及它们之外的任何内容。标记之外的文本仅通过已解决的账本条目或用户已看到的建议修复，永远不会作为拼接的副作用更改。用今天的日期和验证的 SHA 填充每个来源行。

在指令文件中的内容与块在行为上矛盾的方式——过时的 `CLAUDE.md` 行、已退役的命令——建议修复该文件。两个活着的矛盾指令是缺陷。

永远不会提交。

### 6. 结束

- 放入的内容、遗漏的内容及其原因，以及在采用或刷新之后每个现有指令的位置。
- 用用户的术语从 `best-practices.md` 解释原因——为什么它很小，为什么仓库已经声明的会保留在外，为什么陷阱会保留直到其原因是空的。
- 它的加载方式，以及其他 harness 文件可以指向它。
- 用户提交这些指令更改时适用的任何分支、票证、提交或拉取请求规则。
- 维护：在重大更改后重新运行，`record` 代理出错的时刻，优先使用检查而不是新行。
- 跨项目重复的规则，或个人而不是团队的规则，应放在它们的全局代理配置中。

### 刷新

相同的步骤，步骤 1 作为差异。读取来源行，重新验证每个路径和每个注意事项，并运行 `git log --diff-filter=DR --name-only` 自记录的 SHA 以针对每行——更新或删除其证据已消失的行。每个建议的删除都是一个在步骤 5 中显示的账本条目，永远不会是静默编辑，并且块外的手写指令按采用处理——任何接触它们的建议都会进入账本。永远不会重新询问先前运行解决的内容；访谈缩小到团队工作方式的变化。块仅在出现新证据时增长。

### 采用

针对此技能从未接触过的指令刷新。没有先前运行设置的任何内容，因此完整的访谈适用——并且文件本身是维护者证词，因此账本是运行的主要输出：用户应该能够阅读它并看到他们每个指令的位置。

建议声明指令被移出文件的剩余内容——通常是将 `CLAUDE.md` 减少到 `@AGENTS.md`，一旦为使用中的每个 harness 验证了该导入，就像任何加载机制一样。没有指令会存在于两个加载的文件中，它在其中被支付两次；一个副本，逐字或重写，保留一次——块保留幸存者——这解决了两个条目。

### 绿色字段

从规范或计划文档中获取，或仅通过访谈。不存在的命令作为明确 TODO 写入，命名决定的堆栈，永远不会将猜测的调用声明为事实，并在代码存在后的第一次刷新后验证。一个真正的有争议的设计决策——真实的权衡、多种可行的形状——会转到 `bmad-architecture`。

### 迁移

如果目标有一个来自已退役技能的 `project-context.md`，通常在 `{output_folder}` 下，则在步骤 1 中读取它并提议吸收其内容。未经同意不要删除它，也不要默默使其成为孤儿。

## 记录

捕获代理在出错时发生的一个错误——唯一的陷阱证据来源。

获取任务、错误、纠正及其证据。检查块是否已有行涵盖它。一次发生被记录；一个反复或昂贵的错误现在会获得一行——在 **运行和验证** 时为命令错误，否则为陷阱。写入它并显示差异。如果它是机械可防止的，则提议钩子、lint 规则或 CI 检查。

## 审计

重新检查每个注意事项，路径检查每个文件，跟随每个指针，并询问每行删除它是否会影响代理行为。验证每个命令声明针对运行它的目标或脚本。检查与其他指令文件的矛盾。

失败的行被修复，移到可观察的触发器之后，或成为账本条目：删除需要 `best-practices.md` 中的四个理由之一，在删除任何内容之前按步骤 5 呈现并解决。**政策或陷阱只有在它保护的东⻅消失或用户退役它时才会消失；最近失败的任何内容都不是理由。** 审计结束更小或相等。

## 子项

组件、嵌套仓库或提取的规则文件在以下条件满足时在其相同形状下获得自己的文件：其规则是子树专用的，它们是实质性的（几条规则不是文件），分割实质上减少了父块，加载机制对所有使用的 harness 都经过验证——检查，永不假设——并且用户批准分割。即使加载已验证，当必须在会话进入该目录之前应用规则，或打破它会影响目录外的工作时，在根处保留规则。否则规则作为路径限定行（“在 `src/importer/`：...”）保留在父块中，这比无人加载的文件成本更低。为什么加载检查：`best-practices.md`。

仅在触发器不是路径时使用链接文件。

选择的子项如果以父项不已经说的一切结束，则不会获得文件。说明并继续。

在父项的 **Where things are** 中列出每个子项，一行及其路径。发现永远不会依赖于 harness 发现它。
