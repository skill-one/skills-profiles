## 何时使用

当您需要根据 Diátaxis 框架创建、审阅或改进技术文档时，请使用此技能。例如：
- 创建用户指南
- API 文档
- 教程内容
- 重组现有文档以更好地满足不同用户的需求和场景

## 说明

将文档组织为四种不同的类型——教程、操作指南、参考材料和解释——每种类型服务于不同的用户需求和场景。

在创建文档之前，始终询问有关用户场景、受众和目标的澄清问题。

---

### 第 1 步——确定文档类型

使用以下基于用户信号的决策清单：

| 用户信号 | 文档类型 |
|---|---|
| "我是 X 的新手，想学习它" / "带我走一遍" | **教程** |
| "如何...?" / "我需要完成 X" | **操作指南** |
| "X 的参数/选项/语法是什么?" | **参考** |
| "为什么 X 会这样工作?" / "帮我理解 X" | **解释** |

快速决策树：
- 用户是否**通过实践学习**第一次？→ 教程
- 他们是否需要**解决一个特定问题**，并且已经理解？→ 操作指南
- 他们是否需要**技术事实**来查找？→ 参考
- 他们是否想要**概念背景**？→ 解释

---

### 第 2 步——应用类型特定模式

#### 教程（以学习为导向）
- **标题模式**：以动词开头——*"构建您的第一个 X"*，*"从零开始创建 Y"*
- 结构：目标 → 前置条件 → 编号步骤 → 每个步骤立即验证的结果 → 最终结果
- 最小化解释；最大化实践
- 每个步骤必须产生可见的、可测试的结果
- **验证**：初学者必须能够在没有外部帮助的情况下完成教程

**示例引言：**
> *"在本教程中，您将使用 Express 构建一个简单的 REST API。到结束时，您将拥有一个能够响应 GET 请求的运行服务器。无需先前的 Express 经验。"**

---

#### 操作指南（以问题为导向）
- **标题模式**：将任务表述出来——*"如何配置 X"*，*"如何将 Y 部署到 Z"**
- 结构：目标陈述 → 假设/前置条件 → 编号步骤 → 预期结果
- 假设基础知识；跳过概念解释
- 允许变化；注明存在的替代方案
- **验证**：有经验的用户可以在不困惑或倒退的情况下完成任务

**示例引言：**
> *"本指南展示了如何向现有的 Express 应用添加 JWT 认证。它假设您有一个可运行的 Express 服务器和基本的中间件熟悉度。"**

---

#### 参考（以信息为导向）
- **标题模式**：命名事物——*"配置选项"*，*"API 端点"*，*"CLI 标志"*
- 结构：每个条目使用一致的重复格式（名称 → 类型 → 默认值 → 描述 → 示例）
- 陈述事实；避免超出最小使用示例的指令
- 保持最新；如有必要，版本戳
- **验证**：用户可以在不到 30 秒内查找特定事实，而无需阅读周围内容

**示例条目：**
> **`timeout`** *(整数，默认值：`5000`)*
> 请求在超时前等待响应的最大毫秒数。
> *示例：* `{ timeout: 3000 }`

---

#### 解释（以理解为导向）
- **标题模式**：将概念表述出来——*"X 是如何工作的"*，*"理解 Y"*，*"为什么 Z 的设计是这样的"**
- 结构：背景 → 核心概念 → 替代方案/权衡 → 更高层次的视角
- 避免分步指令或技术规范
- **验证**：阅读后，用户可以用自己的话解释概念，并理解设计决策背后的原因

**示例引言：**
> *"认证和授权经常被混淆。本页面解释了它们的区别，为什么两者都重要，以及常见的模式（会话、令牌、OAuth）如何以不同的方式处理每个问题。"**

---

### 第 3 步——保持分离和集成

- 保持每个文档为单一类型——不要将教程步骤与参考表格或概念性离题内容混合
- 在不同类型之间交叉链接：教程可以链接到相关的参考页面；操作指南可以链接到背景解释
- 在所有类型中使用一致的标题和术语，以便用户可以导航整个文档系统

---

### 第 4 步——交付前验证

| 类型 | 验证检查 |
|---|---|
| 教程 | 初学者能否在不寻求外部帮助的情况下从头到尾完成？ |
| 操作指南 | 它是否解决了有经验的用户提出的陈述问题？ |
| 参考 | 用户是否可以在 30 秒内找到特定事实？ |
| 解释 | 用户是否理解*为什么*，而不仅仅是*什么*？ |
