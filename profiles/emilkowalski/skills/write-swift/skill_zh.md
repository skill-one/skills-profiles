# Swift 编写指南

## 初始响应

当这个技能首次被调用而没有具体问题时，仅响应：

> 我已准备好帮助你以现代 Swift 的方式编写代码，这也是 Swift 语言期望的方式。

在用户提问之前，不要提供任何其他信息。

如何以 Swift 6.4 为当前版本的方式编写 Swift。

**工具链基线：Swift 6.3**（截至 2026 年 8 月的当前版本）。这里的一切都在 6.3 上编译，除非标记为 ⚠，否则标记为未发布的 Swift 6.4 功能。并发指南假设 Swift 6.2 模型——如果项目在 6.1 或更早版本上，§3 中关于 `async` 和 `@concurrent` 的规则不适用。

主线：**Swift 是一种渐进式披露语言。从最简单、最静态、最单线程的东西开始，只有在你可以指出原因的地方购买动态性——并发、引用语义、存在性、不安全指针。** 以下每条规则都是该原则的应用。

建模这个默认层次结构。只有当你有理由时，才向下移动一个级别：

| 需求         | 寻求               | 只有在...时才向下移动      |
| ------------ | ----------------------- | -------------------------- |
| 数据         | `struct` / `enum`       | 你需要身份、共享或继承     |
| 抽象         | 具体类型           | 你在类型之间有重复代码    |
| 多态         | `some P`（泛型）      | 你需要异构存储 → `any P` |
| 执行         | 主 actor，同步       | 分析显示挂起 → `async` → `@concurrent` → `actor` |
| 内存         | `Array`, `String`       | 分析显示成本 → `InlineArray`, `Span` |
| 安全性       | 安全 API                | C 互操作或测量的热路径 → `Unsafe*`               |

## 1. 使用值类型建模数据

值类型是 Swift 中的默认值，而不是特殊情况。

- **默认使用 `struct` 和 `enum`。仅在需要身份、共享可变状态、继承或资源生命周期时使用 `class`。** 窗口、数据库连接、渲染引擎中存储的实体——这些都有身份。一个点、一杯饮料、一种材料——这些没有。
- **默认使用 `let`；仅在需要变异时使用 `var`。** 这是 `some` 在 `any` 之前和值在引用之前的相同纪律：从狭窄开始，随着原因而扩展。
- **一个具有可变引用类型属性的 `struct` 既不是值也不是引用。** 复制共享对象；变异会泄漏到复制中。要么保持引用类型不可变，要么只暴露转发到它的计算属性，要么将其作为 `private` 存储属性在写时复制。
- **写时复制是如何获得在线存储和值语义的。** 将一个最终类包装在 `struct` 中，并在变异之前检查 `isKnownUniquelyReferenced(&storage)`；如果没有，则首先复制。这正是 `Array`、`String` 和 `Dictionary` 的工作原理。
- **枚举是“一组固定事物”和互斥状态的工具。** 用一个 `enum State` 替换一堆可选存储属性（`isSharing`、`selectedRows`、`shareTarget`）使无效组合无法表示，并使状态变化变为原子操作，而不是一系列你可能会忘记完成的属性写入。
- **组合值会产生值。** 一个所有存储属性都是值类型的 `struct` 具有值语义——这是使撤消、差异化和状态恢复成为单个代码路径而不是每个属性一个代码路径的原因。

```swift
struct Material {                       // 保留值语义
  var roughness: Double
  private var _texture: Texture         // 一个类

  var color: Color {
    get { _texture.color }
    set {
      if !isKnownUniquelyReferenced(&_texture) { _texture = Texture(copying: _texture) }
      _texture.color = newValue
    }
  }
}
```

**不可复制类型** (`~Copyable`) 表达唯一的所有权：文件描述符、银行转账、打开的资源。抑制复制将“你不应该运行两次”从断言转换为编译错误，并使 `struct` 上的 `deinit` 有意义。将完成方法标记为 `consuming` 以便编译器证明它是最后一次使用。参数所有权变得明确：`borrowing`（只读，默认）、`consuming`（拿走它）、`inout`/`mutating`（临时写入访问）。

## 2. 错误和可选值——使失败路径可见

Swift 错误处理基于三点：错误源被标记，所以它们不能让你感到意外；错误包含足够的上下文来采取行动；**可恢复的错误与程序员错误不同**。

- **可恢复的 → `throw`。程序员错误 → `precondition`/`fatalError`。** 失败的网络调用保持程序运行。越界的索引意味着代码是错误的，必须在出现漏洞之前停止。
- **带有相关值的枚举是最佳错误类型。** `case duplicateFriend(String)` 比 `case duplicateFriend` 更好——上下文是整个重点。
- **使用 `guard` 进行错误条件**，因为它强制退出路径。`if let` 用于普通的解包。
- **带类型 `throws` (`throws(MyError)`) 是用于内部函数、错误转发泛型代码和受约束的环境**，在这些环境中装箱 `any Error` 太昂贵。对于公共 API，未装箱 `throws` 保留你以后更改错误类型的自由。注意统一：`throws` 是 `throws(any Error)`，非抛出是 `throws(Never)`——这是让 `map` 抽象于两者的原因。
- **强制解包仅在你可以声明不变式**的地方，并且最好使用带有消息的失败 `#require`/`precondition` 而不是裸 `!`。

## 3. 并发：直到分析表明否则保持单线程

这是代理最常犯错的领域，因为 Swift 6.2 中模型发生了变化。

每个应用程序都完全在主线程上启动。单线程代码可以走得很远，大多数应用程序永远不需要离开它。

**顺序，按顺序。不要跳过步骤。**

1. **主 actor 上的单线程。** 完全没有并发。对大多数应用程序来说都很好。
2. **`async`/`await`** 来隐藏延迟（网络、磁盘）。仍然没有你自己的并发——SDK API 如 `URLSession.data(from:)` 代表你。
3. **`@concurrent`** 将你的昂贵工作移出主线程——只有在 Instruments 显示挂起后。4. **`actor`** 将状态移出主 actor——只有在太多主 actor 状态迫使任务不断跳回时。

**首先打开正确的构建设置。** 在每个项目中启用 **可接近的并发**。对于应用程序模块和面向 UI 的模块，还将 **默认 actor 隔离** 设置为 **MainActor**——它是 Xcode 26 中新应用程序项目的默认值，并且它删除了大多数 `@MainActor` 注释。在包中：`swiftSettings: [.defaultIsolation(MainActor.self)]`。**不要为通用库设置默认主 actor**——库应该提供 `nonisolated` API，并让客户端决定工作运行的位置。

### 规则已更改

**在 Swift 6.2 中，将函数标记为 `async` 并不移动它到当前 actor。** 它从调用它的地方运行。这是使“最自然的代码”默认无数据竞争的原因。

- **`@concurrent`** — 总是切换到并发线程池。在它上面使用你的 CPU 重型工作。
- **`nonisolated`** — 在它被调用的地方运行。**这是库 API 的正确默认值**，因为调用者决定。`nonisolated` 在类型上使所有成员都非隔离（Swift 6.1+）。
- 既不是——保持在调用者的 actor 上。

```swift
nonisolated struct PhotoProcessor {          // 与主 actor 解耦
  @concurrent                                // 保证在后台运行
  func process(_ data: Data) async -> ProcessedPhoto {
    async let sticker = extractSticker(data)  // 两个独立的工作，并行执行
    async let colors  = extractColors(data)
    return await ProcessedPhoto(sticker: sticker, colors: colors)
  }
}
```

- **在卸载之前进行分析。** 使用 Instruments（时间分析器、挂起）。如果代码可以在不使用并发的情况下变得更快，则始终首先这样做。并发有真正的成本——任务分配、调度和推理。
- **不要为琐碎的工作创建任务。** 一个用于读取 `UserDefaults` 值的子任务比它节省的成本更多。
- **每个端到端操作一个任务。** 必须按顺序发生的工作放在一个任务中；独立的操作获得单独的任务，以便运行时可以交错它们。
- **`await` 是一个挂起点，它打破了原子性。** 状态可以在你挂起时改变，并且你可能会在不同的线程上恢复。在每次 `await` 之后重新检查假设。永远不要跨一个持有锁，永远不要依赖线程本地存储跨一个。

### Actor 递归

Actors 保证互斥，而不是事务。在同一个 actor 上两个 `await` 之间，其他工作会运行。

- **在同步方法中修改 actor 状态。** 在 actor 上的同步代码不间断地运行——那是你的事务边界。
- **保持异步 actor 方法精简**，由同步事务性操作组成，并在每个 `await` 时将 actor 置于一致状态。
- 经典错误：检查缓存 → `await` 下载 → 写入缓存。两个任务都错过了，都下载了，第二个覆盖了第一个。在 `await` 之后重新检查，或者消除正在进行的负载。
- **Actors 不是 FIFO。** 它们首先运行最高优先级的工作，精确地避免优先级反转。如果你需要排序，请使用任务（它从开始到结束运行）或 `AsyncStream`，而不是 actor。

## 4. Sendable 和共享数据

`Sendable` 标记一个类型可以在隔离域之间安全共享。编译器在每个任务和 actor 边界进行检查。

- **值类型在其存储上是 `Sendable`**——非公共类型自动推断。**公共类型永远不会推断可发送性**：标记公共类型 `Sendable` 是对客户端的承诺，因此 Swift 要求你写它。
- **Actors 和 `@MainActor` 类型的隐式 `Sendable`**，因为它们的状态是隔离的。
- **大多数模型类既不是 `@MainActor` 也不是 `Sendable`。** 故意使它们非 `Sendable`——这可以防止一半模型在主线程上被修改，而另一半模型在后台被修改。如果它们需要离开主 actor，请使它们为 `nonisolated`，而不是 `Sendable`。
- **你仍然可以在域之间发送非 `Sendable` 对象** 只要发送者停止使用它。在转交之前进行所有变异；之后触摸它是错误。
- 闭包捕获状态太多。只有当函数类型 `@Sendable` 真正跨域时才标记。

**`@unchecked Sendable` 是编译器无法检查的承诺。** 将它保留给具有真实内部同步的类型（一个 `Mutex`、一个锁）。对于全局上的 `nonisolated(unsafe)` 也是这样——最后手段，不是警告静音器。

**当你遇到数据竞争错误时，按此列表进行处理：**

1. **不要共享它。** 将共享对象移入本地，以便每个并发作业都获得自己的实例。（这是大多数真实错误的修复方法。）
2. **将其作为 `Sendable` 值类型**，这样“共享”实际上是复制。
3. **将其隔离到一个 actor**——主 actor 或你自己的。
4. 只有到那时才使用 `Mutex`/`Atomic` 从 `Synchronization` 模块（将它们存储在 `let` 属性中），或者 `@unchecked Sendable`。

**全局和静态变量是最常见的错误来源。** 按优先级顺序：使其为 `let`；将其放在 `@MainActor` 上；将其包装在 `Mutex` 中；`nonisolated(unsafe)`。注意 Swift 中的全局变量是懒惰初始化和原子化的——与 C 不同。

**桥接旧的回调 API：** 如果您拥有代理协议，请用 `@MainActor` 注释它。如果您不拥有，请将方法标记为 `nonisolated` 并使用 `MainActor.assumeIsolated { }`——它断言而不是跳转，所以它比静默竞争更响亮。`@preconcurrency` 在协议上是一个简写，用于做同样的事情。使用 `@preconcurrency import` 来暂时抑制来自尚未迁移的模块的可发送性警告；一旦它迁移，警告就会正确地回来。

## 5. 结构化并发

始终优先选择结构化任务。

结构化任务 (`async let`, task groups) 像局部变量一样作用域：它们不能存活超过块，它们自动等待，并且它们通过任务树继承取消、优先级和任务本地值。非结构化任务 (`Task { }`, `Task.detached`) 自动为你提供所有这些。

- **`async let`** 用于固定、静态已知的并发子任务数量。
- **`withTaskGroup`** 当数量是动态时。任务组符合 `AsyncSequence`——按结果落地迭代。使用 **`withDiscardingTaskGroup`** 当子任务返回无任何内容时：它立即释放每个子任务资源并取消兄弟任务在第一个错误时。

**`Task { }`** 仅当工作生命周期不适合作用域时使用——反应委托回调、按钮点击、视图出现。它继承 actor 隔离和优先级；您必须自己管理取消。
- **`Task.detached`** 几乎从不使用。它继承不到任何东西——不是隔离，不是优先级，不是任务本地值。如果您需要一个分离的根，请将任务组放在其中，而不是多次分离。

**取消是协作的。** 取消设置一个标志；它不会停止任何东西。在开始昂贵的工作之前检查 `Task.isCancelled` 或 `try Task.checkCancellation()`，并且在同步辅助程序中也这样做。对于被挂起而不是运行的工作（`AsyncSequence` 的 `next()`），使用 `withTaskCancellationHandler`——记住，处理程序立即运行并与正文并发执行，因此它所触及的状态需要真正的同步（原子或锁，而不是 actor——你无法在 actor 上保证顺序）。

**限制你的并发。** 不要为无界列表中的每个项目生成一个子任务。启动 N 个子任务，然后每当一个完成时添加一个新的。

**任务本地值** (`@TaskLocal`) 在任务树中传播上下文——请求 ID、跟踪跨度——而不需要通过每个签名传递参数。使它们可选，以便未绑定的读取具有合理的默认值。

**桥接回调：** `withCheckedContinuation` / `withCheckedThrowingContinuation`。合同是 **在每个路径上精确地恢复一次**——永远不会恢复挂起调用者永远挂起；恢复两次是致命错误。对于在回调中触发 N 次的回调，请使用 `confirmation`；对于没有异步重载的单一回调，请使用 `withCheckedContinuation`。

**`AsyncSequence`:** 使用 `for await` / `for try await` 迭代。使用 `AsyncStream` / `AsyncThrowingStream` 适应现有的基于处理程序或基于委托的 API——在闭包内构造源，从处理程序中 `yield`，并在 `onTermination` 中清理。

## 6. SwiftUI 中的并发

- **`View` 是 `@MainActor` 隔离的**，它包含的一切也是，包括你的 `@State`。你几乎永远不需要在视图或视图模型上写 `@MainActor`——并且随着主 actor 默认，你可以删除你拥有的那些。
- **SwiftUI 故意将一些你的代码运行在主线程之外** 以保持帧廉价。API 签名中的信号是 `@Sendable`：`visualEffect`、`Shape.path(in:)`、`Layout` 要求、`onGeometryChange`。当你在其中一个闭包中遇到隔离错误时，**不要发送 `self`——将你需要的一个值复制到闭包的捕获列表中。**

```swift
.visualEffect { [pulse] effect, proxy in    // 复制布尔值，不要捕获 self
  effect.blur(radius: pulse ? 2 : 0)
}
```

- **SwiftUI 的动作回调是故意同步的。** 时间敏感的 UI 更新——响应手势或滚动事件启动动画——必须在同一帧发生。将 `withAnimation` 状态变化放在同步回调中；为后续的长时间运行工作打开一个 `Task`。
- **在 UI 和异步工作之间放置一个状态。** 视图启动任务；异步层在完成时执行同步变异；UI 响应。这保持了视图逻辑的同步，并使异步逻辑可以在不导入 SwiftUI 的情况下进行测试。

## 7. 协议和泛型

不要从类开始。**也不要从协议开始。**

工作流程：**编写具体类型 → 注意它们之间的重复代码 → 将共享功能提取到协议中 → 编写针对它的泛型代码。** 具有几乎相同体的重载是泛型化的时候的信号。

- **没有任何类型定制的协议是浪费的协议。** 如果每个一致性都会使用相同的默认实现，请在一个现有协议上编写约束扩展。复杂的协议层次结构（“类型动物学”）成本高昂，编译时间和二进制大小没有购买任何东西。
- **优先选择 has-a 考虑 is-a。** 如果协议的一些操作对你的类型有意义，不要细化它——将它在通用结构中包装起来，并暴露你想要的 API。 (`GeometricVector<Storage: SIMD>` 考虑而不是 `GeometricVector: SIMD`.)
- **协议要求是一个定制点**——它是动态调度的，并且一致性的实现获胜。**仅在扩展中仅存在的方法是静态调度的**，所以一致性的版本会隐藏而不是覆盖它，并且只有知道 `any P` 的代码会调用扩展的。如果一个类型应该能够定制某些内容，请将其作为要求。
- **组合优于继承。** 类继承是整体的（一个超类）、侵入性的（你继承存储属性和初始化器复杂性），并且留下了关于可以覆盖的内容和何时调用超类的未写入合同。组合小的值而不是。

### `some` vs `any`

- **默认编写 `some P`。当您需要存储任意类型时更改到 `any P`。** 与 `let` 在 `var` 之前的相同纪律。
- `some P` — 每个作用域一个固定的底层类型。您保留每个类型关系，包括关联类型，并且编译器可以进行专业化。
- `any P` — 类型擦除的框，运行时动态类型变化。需要异构集合、底层类型的可选性和完全隐藏抽象。您为此付费：关联类型关系被擦除到它们的上界，并且调用对优化器不透明。
- **您不能在 `any P` 上调用接受关联类型的方法。** 擦除在产生位置工作，但在消耗位置不起作用。修复方法是：将存在性传递到接受 `some P` 的函数——编译器在作用域内取消它，在该作用域内类型是固定的。
- **约束存在性和不透明类型** — `some Collection<Element>`，`any Collection<any Animal>`——让您隐藏 `LazyFilterSequence<[Animal]>`，同时仍然暴露元素类型。在您自己的协议上声明主要关联类型（例如 `protocol Container<Item>`）以供调用者实际提供，而不是实现细节，如 `Iterator`。
- **`where` 子句中的相同类型要求是如何在协议之间固定关系的。** (`where Self.CropType.FeedType == Self`) 没有它们，“种植然后收获”无法通过类型检查，错误的从属会编译。

## 8. API 设计——使用处的清晰度

使用处的清晰度是这里排名最高的目标。

- **Swift-only API 中没有类型前缀。** 模块消除歧义。只保留前缀，仅当 API 与 Objective-C API 镜像时才保留。但避免从特定框架中非常通用的名称——它们在上下文中读起来很糟糕，并强制手动消除歧义。
- **从异步替代中删除 `get` 的前缀** 和任何直接返回其结果的任何内容。`persistentPosts`，而不是 `getPersistentPosts`。
- **访问控制是文档。** `private`（文件），`internal`（模块，并且是默认值），`package`, `public`。在边界处明确是强制性的，这就是强制发送性和 API 进化决策的原因。
- **设计模型以防止可以拼写的非法状态**。私有设置加上一个验证的 mutating 方法；枚举用于封闭集；一个强类型的 `UUID` 考虑而不是 `String`。
- **属性包装器** 将访问策略（`@Argument`, `@Published`, 防御性复制, 懒加载, 线程本地）提取出来，以便声明位置在单个词中声明策略。与 `@dynamicMemberLookup` 在键路径上使用以投影通过包装器（这就是 `$binding.title` 的工作原理）。
- **结果构建器** 用于声明性 DSL。**宏** 当宏样板是编译器可以编写代码时（§12）。

## 9. 性能——测量，然后选择

低级 Swift 性能由四个成本主导。知道您正在支付哪个。

1. **函数调用** — 参数复制，静态与动态调度，调用帧分配和阻塞优化。
2. **内存布局** — 内联与离线存储；动态大小类型。
3. **分配** — 全局（释放），栈（便宜：一个减法），堆（昂贵：搜索加上锁定）。
4. **复制** — retains/releases 和递归结构复制。

**但首先进行算法工作。** 每次你写一个循环，尝试用算法的调用替换它。最大的胜利几乎都不是微观优化：

- **了解你调用的复杂性。** `Array.remove(at:)` 是 O(n)；在循环中调用它是 O(n²)。`removeAll(where:)` 总共是 O(n)。通过重新切片每个字节构建 `Data` 是 O(n²)；`popFirst()` 是 O(1)。这两项都是隐藏在干净代码背后的 100 倍以上的回归。
- **链接的 `map`/`flatMap`/`filter` 为每个阶段分配一个数组。** 优雅不等于快。如果一个管道在热循环中按像素或按元素运行，请一次设置输出大小，并写入其中。
- **然后进行分析。** Instruments 的时间分析器和内存分析器，针对你要测量的代码运行（在测试的运行按钮上单击 Profile）以便你正在测量你关心的代码。`platform_memmove` 在火焰图中主导一个火焰图意味着意外的复制；一百万个瞬态分配意味着中间数组；`swift_beginAccess` 意味着运行时排他性检查；`swift_retain`/`swift_release` 意味着引用计数的流量。

**具体杠杆，大致按它们买的东西的顺序：**

- **在您不打算子类的类上使用 `final`** 转换动态调度为静态并解锁内联。整个模块优化让您在许多情况下可以证明这一点——并启用泛型专业化，这是泛型停止有任何成本的地方。
- **结构存储是内联的；类存储是离线的。** 小结构是免费的；具有三个引用类型字段的大结构每复制一次成本是三个 retains，而类一次只保留一个。如果你复制它很多，请使用写时复制。
- **`any P` 存在性有一个 3 字节的内联缓冲区。** 值适合内联；较大的值每个复制一次都分配到堆上。相同的技巧适用于：给大型类型间接存储使用写时复制，它再次适合缓冲区。
- **同构 `[MyModel]` 击败 `[any Model]`** — 密集打包，一次传递类型信息，可专业化。`[any Model]` 是灵活但隐藏的选项；当你需要它时才使用。
- **将泛型参数约束为类** (`T: AnyObject`) 给编译器一个已知的表示，即使没有专业化。
- **`InlineArray<N, T>`**（Swift 6.2）用于固定大小存储：元素内联存储，通过值泛型在类型中指定大小，没有堆分配，没有引用计数，没有唯一性或排他性检查。如果它被复制或共享，这是错误的选择。

**Swift 6.3 中已发货，当您测量了需要：** `@inline(always)`（与 `final` 方法配对）和 `@specialized(where T == ...)`（SE-0460）以预专门化热具体类型。 landing in Swift 6.4 (**未发布**——见 §15 的注释) 的 `borrow`/`mutate` 访问器而不是 `get`/`set` 用于大型存储值，`UniqueArray`/`UniqueBox`，以及 `Ref`/`MutableRef` 将重复的查找从循环中提升出来。

**异步函数** 将其状态保留在每个任务的 slab 分配器上，而不是 C 栈，并且在每个挂起点分裂成部分函数。成本分析类似于同步函数，但调用开销略高——这是不制作需要等待的东西成为 `async` 的另一个原因。

**到主 actor 的跳转和返回的成本是真实的上下文切换。** 批量：将循环推入 `_loadArticles`/`updateUI` 以便它们接受数组，而不是每次迭代两次跳转。

## 10. ARC 和对象生命周期

- **对象的保证生命周期在最后使用结束，而不是在关闭大括号时结束。** 观察到的生命周期是优化器的一个涌现属性，它将会改变。依赖 `deinit` 运行时间的代码是一个潜在的漏洞。
- **`weak`/`unowned` 仅用于打破引用循环——别无他用。** 在强所有者使用后读取 `weak` 引用可能会合法地给出 `nil`。可选绑定比强制解包更糟：它将一个响亮的崩溃变成了一个无声的错误答案。
- **比 `weak` 更好的做法：不要构建循环。** 将共享数据分解为双方都引用的第三类型，将循环转换为树。
- **最好的做法：重新设计 API** 以便对象只能通过强引用访问。`withExtendedLifetime` 工作但将正确性放在你的身上，并扩散到代码库——将其视为补丁，而不是设计。
- **保持 `deinit` 侧效应局部。** 从 `deinit` 中发布指标或触发全局效果会与优化决策冲突。使用 `defer` 在调用站点，并留 `deinit` 用于验证。

**Xcode 的** **Optimize Object Lifetimes** 构建设置缩短观察到的生命周期，使其接近保证的最小值，并将会暴露这些错误。
