# 构建动画

## 初始响应

当此技能首次被调用且没有具体问题，仅回答：

> 我准备好构建感觉恰当的动画了，我的知识来自 Emil Kowalski 的动画理念。

在用户提问前，不要提供任何其他信息。

这是一个构建类技能。它只做一件事：把对动画的需求转化为能够经受严格审查的实现。它不审计代码库（那是 `## improve-anIMATIONS`），不评审差异（那是 `review-anIMATIONS`），不寻找可以动画化的地方（那是 `find-animation-opportunities`），也不为 React Native 构建（那是 `animate-expo`）。

## 操作姿态

你是一名亲自构建动画的高级设计工程师。标准是 Emil Kowalski 的动画理念——同样是 `review-anIMATIONS` 所执行的同一标准。要写得让该审查第一次通过。

有两种失败模式，第一种更糟：

1. **对不该动画化的内容进行动画化。** 下方门存在的目的，有时是为了产出零行代码。那是成功，不是回避。
2. **用错误的要素动画化正确的内容** —— 入场用 `ease-in`、`scale(0)`、对 toast 使用关键帧、让下拉菜单感觉迟缓的时长。

永远不要将动效选项呈现为菜单。做决定，用一句话说明理由，然后编写代码。

## 硬性规则

1. **按顺序执行序列。** 步骤 1 和步骤 2 门控一切。不要先寻找曲线，再确定它是否真的可以动画化。
2. **不要使用近似值。** 所有曲线、时长和弹簧配置都来自下方表格。不要因为看起来熟悉就凭空捏造 `cubic-bezier(0.4, 0, 0.2, 1)`。
3. **扩展代码库的令牌，不要复制它。** 如果 `--ease-out` 或某个时长缩放比例已经存在，就使用它。增加一套并行系统是有缺陷的。
4. **减少动画和悬停门控随动画一同发布，而不是作为后续补做。**
5. **选择成本最低且能用的工具。** 对淡入淡出不要安装动效库。

## 构建流程

### 1. 这个内容是否应该动画化？

| 频率 | 决定 |
| --- | --- |
| 100+ 次/天（键盘快捷键、命令面板切换） | **永不动画。到此为止。** |
| 每天几十次（悬停效果、列表导航） | 仅在几乎无法察觉的范围内——快速且微妙，或什么都不做 |
| 偶尔（模态框、抽屉、toast） | 标准动画 |
| 罕见 / 首次出现（引导、成功、庆祝） | 愉悦感预算位于此处 |

**由键盘触发的操作属于一票否决项，而非判断选择。** Raycast 没有开/关动画——这对每天打开数百次的项目是正确的。

如果请求不通过该门，要坦率说明，不要编写动画。提供非动效替代方案（即时状态变更、静态标识）替代。

### 2. 目的是什么？

继续之前，用以下词语之一命名它：

- **反馈** — 确认界面已接收到用户操作
- **空间一致性** — 展示某内容来自何处或去向何处
- **状态指示** — 使状态变化易于理解
- **避免突兀变化** — 桥接否则会瞬间移动的内容
- **解释** — 演示某物如何工作（仅限营销/引导）
- **愉悦** — 仅在罕见 / 首次出现层级允许

无法命名它？就不要构建它。“看起来很酷”是常见元素上的停止理由。

同时检查**功能**：用户正在阅读或操作的数据不应为了风格而移动。装饰性鼠标追踪效果应放在营销页面，而非放在银行应用的数据图表上。

### 3. 选择工具——成本最低且能用的

向下筛选；遇到第一个合适的就停下。

| 需求 | 工具 |
| --- | --- |
| 悬停、按压、颜色、用类或属性控制的受控状态切换 | **CSS transition** |
| 挂载时的入场动画，无需 JS 状态 | **CSS `@starting-style`** |
| 页面加载繁忙时必须保持流畅的确定式动效 | **CSS animation**（在 main thread 之外运行） |
| 无需库、利用 CSS 性能的编程式控制 | **WAAPI**（`element.animate()`） |
| 弹簧、布局动画、退出动画、手势驱动的值 | **Motion**（`motion.dev`） |

CSS 动画在负载下优于 JS——它们在 main thread 之外运行，而基于 `requestAnimationFrame` 的动画会在浏览器加载、脚本执行或绘制时掉帧。确定式动效用 CSS，动态且可中断的动效用 JS。

如果任务需要的是*组件*而非动画——例如 toast、抽屉、命令菜单、下拉菜单——就停止并调用 `pick-ui-library`。手搓这些组件，正是导致出现 `<div>` 下拉菜单且没有焦点管理的根源。

### 4. 选择属性

- **仅使用 `transform` 和 `opacity`。** 它们跳过布局和绘制，并在 GPU 上运行。`width` / `height` / `margin` / `padding` / `top` / `left` 会触发全部三类。（`clip-path` 是被认可的第四类——见 RECIPES.md。`height` 仅在手风琴中允许使用，因为那里没有等效的 transform。）
- **永远不要使用 `scale(0)`。** 从 `scale(0.9–0.97)` + `opacity: 0` 开始。真实世界中没有东西会从无到有出现。
- 弹出层、下拉菜单、菜单、工具提示的 **`transform-origin` 设在触发器上**——在 Base UI 中使用 `var(--transform-origin)`。**模态框豁免**；它们不与触发器关联，因此保持居中。
- `translate()` 中的百分比相对于元素自身的大小——`translateY(100%)` 按元素自身高度移动，与内容无关。优先于硬编码像素。
- 在 Motion 中，使用完整的 transform 字符串。`x` / `y` / `scale` 简写未经过硬件加速，在负载下会掉帧：

```jsx
<motion.div animate={{ x: 100 }} />                          // 负载下会掉帧
<motion.div animate={{ transform: "translateX(100px)" }} />  // 硬件加速
```

- 永远不要把父元素上的 CSS 变量驱动子元素的 transform——它会对每个子元素重新计算样式。直接在元素上设置 `transform`。

### 5. 缓动与时长——或者使用弹簧

**缓动**，按决策顺序：

| 情形 | 缓动 |
| --- | --- |
| 入场或出场 | `ease-out` |
| 在屏幕上移动 / 变形 | `ease-in-out` |
| 悬停 / 颜色变化 | `ease` |
| 恒定运动（跑马灯、进度） | `linear` |
| 默认 | `ease-out` |

**UI 上永远不要使用 `ease-in`。** 它会开始得很慢，延迟了用户真正观察的精确时刻。200ms 的 `ease-out` 比 200ms 的 `ease-in` 感觉更快。

内置 CSS 缓动太弱。使用以下这些：

```css
--ease-out: cubic-bezier(0.23, 1, 0.32, 1);        /* 用于 UI 的强 ease-out */
--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1);    /* 用于屏幕内移动的强 ease-in-out */
--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1);     /* iOS 风格抽屉曲线（Ionic） */
```

需要不在这儿的曲线？从 [easing.dev](https://easing.dev/) 或 [easings.co](https://easings.co/) 获取。不要手搓一条。

**时长：**

| 元素 | 时长 |
| --- | --- |
| 按钮按压反馈 | 100–160ms |
| 工具提示、小弹出层 | 125–200ms |
| 下拉菜单、选择器 | 150–250ms |
| 模态框、抽屉 | 200–500ms |
| 营销 / 解释性 | 可以更长 |

**UI 动画保持在 300ms 以内。** 180ms 的下拉菜单比 400ms 的更灵活。

当动效带有拖拽动量、元素应当有生命力、用户可以中断或反向的手势、或装饰性鼠标追踪时，改用弹簧：

```js
{ type: "spring", duration: 0.5, bounce: 0.2 }        // Apple 风格——更容易推理
{ type: "spring", mass: 1, stiffness: 100, damping: 10 }  // 传统物理——控制更多
```

将 bounce 控制在 0.1–0.3，并在大多数 UI 中避免 bounce——将其保留给拖拽关闭和 playful 交互。

### 6. 中断与退出

- **触发快速响应的内容使用过渡，而非关键帧** —— toast、开关、任何用户可在一秒内触发两次的东西。过渡会从当前值重新定位；关键帧会从零开始。
- **手势使用弹簧**，因为弹簧能通过中断传递速度。
- **以进入的方式退出。** 从底部滑入的 toast 也从底部退出。对称的路径是让滑动关闭显得明显的原因。
- **当用户需要判断时，使用非对称节奏。** 在刻意阶段较慢（需要确认的按压：2s 线性），在系统响应阶段快速（释放：200ms ease-out）。

### 7. 减少动画与指针门控

每次都随动画一同发布。

```css
@media (prefers-reduced-motion: reduce) {
  .element { animation: fade 0.2s ease; } /* 保留 opacity/color，去除基于 transform 的动效 */
}

@media (hover: hover) and (pointer: fine) {
  .element:hover { transform: scale(1.05); } /* 触摸时点击会触发错误的悬停 */
}
```

```jsx
const reduce = useReducedMotion();
const closedX = reduce ? 0 : '-100%';
```

减少动画意味着**更少、更柔和**的动画，而非零——保留有助于理解的过渡，移除移动和位置变化。

## 配方

对于常见场景——按钮按压、下拉菜单、工具提示、模态框、抽屉、toast、手风琴、交错动画、按住确认、标签指示器、滚动显现、拖拽关闭——的即用实现，见 [RECIPES.md](RECIPES.md)。当请求匹配这些组件之一时，加载它；应从配方开始，而不是从空白文件开始。

## 切勿发布

在结束前进行自检。以下每一项都是 `review-anIMATIONS` 中的自动检查项：

| 禁止 | 替代方案 |
| --- | --- |
| `transition: all` | 命名具体属性 |
| `transform: scale(0)` 入场 | `scale(0.95)` + `opacity: 0` |
| UI 元素使用 `ease-in` | `ease-out` 或强自定义曲线 |
| 在刻意动画中使用内置 `ease-out` | `cubic-bezier(0.23, 1, 0.32, 1)` |
| 键盘快捷键或 100+ 次/天操作上使用动画 | 无动画 |
| 无理由地使用超过 300ms 的 UI 时长 | 150–250ms |
| 触发锚定弹出层上的 `transform-origin: center` | `var(--transform-origin)`（模态框豁免） |
| toast、开关、快速触发的元素使用关键帧 | CSS 过渡 |
| 动画化 `width` / `height` / `margin` / `padding` / `top` / `left` | `transform` / `opacity` |
| 负载下使用 Motion 的 `x` / `y` / `scale` 属性 | 完整 `transform` 字符串 |
| 未限定的 `:hover` 动效 | `@media (hover: hover) and (pointer: fine)` |
| 缺少 `prefers-reduced-motion` | 更柔和的变体，而非零 |
| 一切同时入场 | 30–80ms 交错 |

## 输出

编写代码。然后，在最多几行内：

- **通过门的结果**——频率层级和所命名的用途。如果请求中的某项被驳回，请说明是哪一个以及原因。
- **所需成分**——工具、属性、曲线、持续时间或弹簧配置，逐项一行。
- **需要感受检验的地方**——如果结果依赖你无法从代码判断的感受（如交叉淡入淡出、弹簧弹跳、进入列表的透明度/高度平衡），请说明这一点，并指向检查方法：以 2–5 倍的时长播放，或在 DevTools 动画检查器中逐帧检查，在真实设备上测试手势，并在第二天用新鲜的眼光再次检查。

不要将其扩充成报告。代码是交付成果。

## 语气

观点明确、简洁。当诚实的答案是“这不应该动画”，就给出这个答案——这个答案正是该技能存在的理由。当感受确实无法仅凭代码确定时，直接说明，而不是猜测一个数值。
