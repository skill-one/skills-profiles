# 千问支付

千问AI平台（QianWenAI）余额查询和固定金额支付宝充值。仅使用此技能进行千问AI账户操作。不要从低余额、通用配额错误、HTTP状态码或不相关的模型故障中推断充值意图或过期账户。

## 兼容性和资源

此技能的每条路由都需要Node.js 18.18+。使用`scripts/preflight.mjs`来强制执行运行时基线，确定千问CLI兼容性，并选择可用的支付宝支付路径；不要在文本中复制或覆盖其版本和能力决策。

| 位置 | 权威责任 |
| --- | --- |
| `scripts/preflight.mjs` | 路由依赖探测、金额规范化以及交易关键响应验证 |
| `scripts/recharge-result-contract.mjs` | 充值结果身份和状态分类 |
| `scripts/poll-recharge.mjs` | 前端支付后结果轮询 |
| `references/recharge-flow.md` | 确认订单业务序列、分支、停止和恢复 |
| `references/cli-contracts.md` | 命令、参数、JSON形状、脚本接口和退出代码 |
| `references/sources.md` | 仅限手动溯源查找 |

仅在当前路由需要其权威详细信息时加载参考。对于固定金额充值，仅在用户确认订单创建后，才读取`recharge-flow.md`。当用户明确报告当前订单的二维码未显示且当前订单的支付宝材料仍保留时，也读取其恢复部分。

## 路由

| 请求 | 路由 | 业务边界 |
| --- | --- | --- |
| 余额 | `balance-summary` | 只读 |
| 确认过期或明确模型调用余额错误 | 询问是否充值 | 不授权金额或交易 |
| 固定金额支付宝充值 | `recharge-order` | 每次尝试一次创建确认，然后支付和条件性前端结果轮询 |
| 当前订单二维码未显示 | `missing-qr-recovery` | 用户触发的从保留的支付宝材料中恢复呈现；无命令或新订单 |
| 现有订单结果 | `recharge-result` | 一次只读快照；永远不会启动轮询循环 |
| 充值历史 | `recharge-history` | 只读，默认30天 |
| 充值页面引导 | `recharge-page` | 在打开浏览器前确认 |
| 代币计划购买 | 无 | 重定向到`sources.md`中列出的代币计划页面 |

## 核心规则

1. **仅本地化千问拥有的输出。** 跟随用户最新实质性消息的语言。AI风险通知可以全部翻译。仅用户面支付宝内容直接传递；路由特定控制数据永远不会面向用户。
2. **一次确认，一次创建尝试。** 确认精确的掩码账户、规范化金额、支付宝方式和操作范围。一次确认授权创建命令的精确一次调用，并在调用前消耗。它不能授权另一个订单，包括在同一对话中使用相同账户和金额或为重试、替换或附加订单。状态查询、二维码恢复、支付继续或声明支付已完成永远不会授权创建。永远不会自动重试中断的、格式错误的、超时的、非零或其他未确认的创建尝试。
3. **一个外部充值生命周期内一个支付所有者。** 此技能拥有订单创建、支付移交和查询千问结果的决策。预检在订单创建前选择`direct`或`alipay-payment-skill`。`alipay-payment-skill`仅在其委派支付侧步骤内拥有安全、命令、重试、输出和停止决策。在直接支付宝命令开始后，永远不会切换路径，因为其副作用可能未知。
4. **无支付即兴创作。** 仅使用当前创建响应中未更改、验证的`paymentUrl`。永远不会接受、重写、重建、规范化、解码/重新编码或替代来自用户、历史记录、日志或另一个订单的链接。
5. **一次信用证明。** 只有共享充值结果分类器返回`category=credited`才能证明充值已成功。支付宝结果、二维码扫描、用户声明、余额变化或历史记录条目都不能。
6. **保护凭证和交易数据。** 永远不要请求支付宝密码、银行卡号、短信验证码、API密钥、cookie或粘贴的令牌。将完整账户标识符、订单ID、支付链接和原始有效载荷仅保留在当前流程内存中。不要将它们复制到文件、日志、长期内存或子代理消息。
7. **在轮询前交付。** 在任何结果查询或`poll-recharge.mjs`之前完成Progress节点2。仅对代理可见的命令结果、文件读取、预览、草稿或计划最终回复不是交付。
8. **轮询路由。** 使用[recharge-flow.md](references/recharge-flow.md)进行轮询资格和业务序列。
9. **一致的执行上下文。** 将[cli-contracts.md](references/cli-contracts.md)中的执行上下文和身份验证恢复合同应用于千问命令。

## 直接路径sessionId解析

本节仅适用于直接路径。委派路径遵循`alipay-payment-skill`。`sessionId`是可选的，仅适用于`alipay-bot submit-payment`；`trigger-payment-signal`永远不会接收它。使用此订单中的第一个非空值：

| 优先级 | 来源 |
| --- | --- |
| 1 | 运行时元数据：`sessionId` / `session_id` |
| 2 | 当前对话：`threadId` / `thread_id` / `conversationId` / `conversation_id` / `agentContextId`；对于Codex：`CODEX_THREAD_ID` |
| 3 | 环境变量`AIPAY_SESSION_ID` |

使用该值原样。不要生成一个，询问用户一个，或替换另一个业务ID。如果所有来源都为空，省略`--session-id`。

## 预确认快速路径

### 1. 金额

仅使用当前充值有意提供的金额。

- 准确地将元、角/毛和分转换为十进制字符串或整数运算。
- 仅当金额明确、正数、以人民币计价且精确表示为分时继续。
- 当金额缺失、近似、范围、包含多个候选、使用其他货币或具有分以下精度时，请求一个精确的金额。
- 永远不要猜测、四舍五入、截断或重用来自另一个请求的金额。

与路由依赖一起验证规范化金额：

```bash
node <skill-dir>/scripts/preflight.mjs --route recharge-order --amount <normalized>
```

对于每个`recharge-order`尝试，兼容的Alipay CLI和`alipay-payment-skill`是独立的阻塞依赖项。预检验证CLI合同；分别验证`alipay-payment-skill`是否存在于主机可用技能注册表中并可加载。两个依赖项都不能相互替代，即使预检选择`payment_path=direct`。在身份验证、确认或订单创建之前完成这两个检查。

在两个依赖项门都通过后，保留返回的`payment_path`。`direct`表示可选的预移交信号功能可用；`alipay-payment-skill`表示支付提交必须使用已验证的`alipay-payment-skill`。如果任何依赖项不可用，停止并使用[cli-contracts.md § 依赖项设置](references/cli-contracts.md)仅在需要安装指导时。

### 2. 身份验证和账户快照

使用[cli-contracts.md](references/cli-contracts.md)中的身份验证合同验证服务器认证的千问CLI账户。仅使用CLI OAuth设备流程；仅显示其返回的验证URL，并永远不会要求凭证或令牌。

仅保留完整账户标识符用于当前流程一致性检查，并仅显示其掩码形式。在创建之前，重新读取已认证的账户并与确认的快照进行比较。任何账户、金额、货币、支付方式或操作范围的更改都会使确认无效。

在创建之前，不要查询余额、充值历史或先前的订单。它们增加了延迟，而不会保护此交易。

### 3. 确认

对于每个新的固定金额创建确认，第一条可见行必须是此完整的AI风险通知，在适当的时候本地化：

```text
AI风险通知：此充值请求由AI准备，可能无法反映您的实际意图。请检查金额、账户和操作范围；如果任何内容不正确，请不要确认。
```

然后显示掩码账户、规范化金额、支付宝方式，并确认创建一个充值订单并进入支付流程。以一个自然的确认问题结束。不要使用机械的确认/取消选项列表。

- 肯定：重新检查账户和规范化金额，消耗确认，然后读取并执行[recharge-flow.md](references/recharge-flow.md)。
- 否定：运行无操作并输出本地化的`Recharge canceled`。
- 材料变更：显示一个新的确认块，包含风险通知。

## 用户可见进度

仅传达这些业务转换。不要暴露CLI命令、参数、技能路由、验证器、服务名称、轮询内部、`sessionId`、内部轮询截止日期或原始千问侧错误，除非用户明确要求故障排除信息。

### 进度节点1：订单创建

在确认后和调用创建命令之前：

```text
正在创建充值订单…
```

### 进度节点2：支付宝输出交付

- **直接路径：** 仅使用用户面stdout，由[cli-contracts.md § 直接支付宝命令](references/cli-contracts.md)标识。交付它一次并直接作为用户面响应。正常渲染其Markdown；不要添加前缀、标题、代码块或状态摘要。逐字节保留所有非媒体文本；不要翻译、总结、包装或过滤其业务内容。仅应用此传输适配：
  - 如果stdout包含`MEDIA: <路径或URL>`行，提取每个引用并删除这些行。发送剩余文本不变，然后通过图像/媒体通道按原始顺序发送引用的图像。
  - 如果没有图像/媒体通道可用，将引用作为Markdown图像附加到单个文本响应中，按原始顺序。
  - 如果stdout已经包含Markdown图像，保留它们不变，不要发送重复图像。永远不会打开、分析或修改引用的图像。除非在用户报告当前订单的二维码未显示时重新呈现保留的当前订单二维码，否则不要重用它。
- **支付宝技能路径：** 遵循内容、格式和媒体规则，无需在此处重述它们。其在此外部流程中生命周期终结者的范围在[recharge-flow.md](references/recharge-flow.md)中定义。如果它已经通过用户可见通道发出内容，不要重复它。

对于直接路径，`MEDIA:`处理仅改变传输表示，不是支付宝结果验证。对于任何路径，进度节点2仅在选定路径的内容对用户可见后完成。如果运行时无法在不结束外部回合的情况下发布该文本，则使用它作为最终回复，该回合内不轮询，并在用户下一条消息后使用一个现有订单快照。永远不会将支付宝内容推迟到轮询后的计划最终回复中。传递规则覆盖千问侧本地化、隐藏和错误重写规则。

如果确认流程请求无输出恢复，因为支付步骤未产生任何用户可见内容，显示本地化的等效内容：`支付步骤未返回任何可显示的结果，因此其结果未知。已保留现有充值订单。不要创建另一个订单或再次支付；在重试前请问我检查此订单。` 这是一个千问拥有的恢复通知，不是支付宝输出或充值结果的证明。

精确一次规则有一个例外：当用户报告当前支付二维码未显示时，遵循[recharge-flow.md § 4](references/recharge-flow.md)重新呈现二维码和支付宝数据返回的支付链接。

### 进度节点3：千问充值结果

使用共享结果分类器返回的类别：

- `credited`：`充值成功。¥<金额>已添加到您的千问AI余额。` 然后附加`充值记录可能延迟约10秒。`
- `failed`：`充值未成功。请先检查支付宝交易状态再尝试。`
- `processing` 或 `unconfirmed`：`充值结果尚未确认。如果您已经支付，请不要再次支付——告诉我支付已完成，我将为您检查最终结果。`

当确认流程合同请求终端后余额查询时，在验证的回复后附加`当前可用余额：¥<余额>`。如果该查询失败，附加`最新余额暂时不可用。` 永远不要根据余额响应更改或替换充值结果。

永远不会说您将自动或稍后报告结果。用户必须发送另一条消息，然后才能查询稍后快照。

## 其他路由

### 余额

使用[cli-contracts.md § 余额](references/cli-contracts.md)。显示验证的人民币金额。低余额或零余额单独不能证明过期状态或授权充值。

### 充值资格

- 明确的千问AI充值请求直接进入金额流程。
- 用户确认过期账户或明确的模型调用余额不足错误可以提供一次本地化充值选择；选择加入仍然不会授权金额或订单。
- 不要为通用失败、HTTP 403、免费套餐耗尽、代币计划配额或消费限额建议充值。

### 现有订单结果

使用[cli-contracts.md § 现有订单结果](references/cli-contracts.md)中的一个快照。不要查询支付宝状态或启动`poll-recharge.mjs`。使用进度节点3呈现结果。

### 充值历史

使用[cli-contracts.md § 充值历史](references/cli-contracts.md)。在退出`0`时，将CLI结果转换为人类可读的响应。历史记录是信息性的，永远不会证明特定订单结果。

### 充值页面引导

解释该命令将打开验证的千问AI充值页面，并在使用[cli-contracts.md § 充值页面引导](references/cli-contracts.md)之前询问是否继续。显示返回的验证URL；永远不要构建一个。

### 代币计划

不要购买、续订、升级或添加代币计划配额。将购买请求直接引导到`sources.md`中列出的代币计划页面。将现有计划状态、配额和计费问题路由到`qianwen-usage`。

## 更新检查

对于更新请求，当可用时使用兄弟`qianwen-update-check`技能；否则运行`qianwen version --check`。在未解决的充值流程期间，永远不会运行更新检查。
