# Mapbox 搜索集成技能

提供实现应用程序中 Mapbox 搜索功能的专家指导。涵盖从提出正确的发现问题、选择合适的搜索产品，到遵循 Mapbox 搜索团队最佳实践实现生产就绪集成的完整工作流程。

## 使用此技能的场景

当用户说以下内容时使用：

- "我需要给我的地图添加搜索功能"
- "我需要为我的地图应用添加搜索栏"
- "我该如何实现位置搜索？"
- "我想让用户搜索地点/地址"
- "我需要在应用程序中实现地理编码"

**此技能与 `mapbox-search-patterns` 相辅相成：**

- `mapbox-search-patterns` = 工具和参数选择
- `mapbox-search-integration` = 完整的实现工作流程

## 发现阶段：提出正确的问题

在编写代码之前，请提出以下问题以了解需求：

### 问题 1：用户在搜索什么？

**问：** "你想让用户搜索什么？"

**常见答案及其影响：**

- **"地址"** → **使用搜索框 API**（交互式地址搜索的默认选项，包括地理编码）。如果用例是批量/服务器端地理编码或维护现有集成，则仅使用地理编码 API。
- **"兴趣点/商家"** → 兴趣点搜索，使用带有分类搜索的搜索框 API
- **"地址和兴趣点"** → 搜索框 API
- **"特定类型的兴趣点"**（餐厅、酒店等）→ 搜索框 API
- **"国家、城市、邮政编码或社区"** → 交互式搜索使用搜索框 API；仅对批量/服务器端地理编码使用地理编码 API
- **"自定义位置"**（用户创建的地点）→ 可能需要自定义数据 + 搜索集成

**如果初始未说明，请进行后续提问：** "您的用户在搜索兴趣点数据吗？餐厅、商店、商业类别？"

**影响：**

- **"是，包括兴趣点"** → 使用搜索框 API
- **"否，用户不需要兴趣点搜索"** → **仍然默认使用搜索框 API**，用于交互式/自动完成用例。搜索框 API 处理地址、地名和所有位置类型，采用基于会话的定价。仅在以下情况下推荐地理编码 API：批量地理编码、服务器端永久地理编码或维护现有的地理编码 API 集成。

### 问题 2：地理范围是什么？

**问：** "用户将在哪里进行搜索？"

**常见答案及其影响：**

- **"单个国家"**（例如，"仅限美国"）→ 使用 `country` 参数，结果更佳，成本更低
- **"特定区域"** → 使用 `bbox` 参数进行边界框约束
- **"全球"** → 无国家限制，但可能需要语言参数
- **"多个特定国家"** → 使用 `country` 数组参数

**后续提问：** "您是否需要将结果限制在特定区域内？"（配送区域、服务区域等）

### 问题 3：搜索交互模式是什么？

**问：** "用户将如何与搜索交互？"

**常见答案及其影响：**

- **"边输入边搜索/自动完成"** → **使用搜索框 API**，设置 `auto_complete: true` 并采用基于会话的定价（对自动完成最经济）。实现防抖。
- **"搜索按钮/最终查询"** → 可以使用任一 API，无需自动完成
- **"两者都有"**（自动完成 + 精细调整）→ 两阶段搜索，先自动完成，然后显示详细结果
- **"语音输入"** → 考虑语音到文本集成，处理更长的查询

### 问题 4：使用平台是什么？

**问：** "这是为哪个平台设计的？"

**常见答案及其影响：**

- **"Web 应用"** → Mapbox Search JS（最简单），或直接 API 调用用于高级用例
- **"iOS 应用"** → iOS 搜索 SDK（推荐），或直接 API 集成用于高级用例
- **"Android 应用"** → Android 搜索 SDK（推荐），或直接 API 集成用于高级用例
- **"多个平台"** → 平台特定 SDK（推荐），或直接 API 方法以保持一致性
- **"React 应用"** → Mapbox Search JS React（使用 UI 最简单），或 Search JS Core 用于自定义 UI。避免直接 API 调用——它们需要手动防抖、会话令牌管理和竞态条件处理。
- **"Vue / Angular / 其他框架"** → Mapbox Search JS Core 或 Web。如果使用直接 API 调用，需要会话令牌以进行正确的计费（每个搜索会话一个令牌，作为 `session_token` 在每个 `suggest/retrieve` 请求中传递）。

### 问题 5：结果将如何使用？

**问：** "当用户选择一个结果时会发生什么？"

**常见答案及其影响：**

- **"在地图上飞往位置"** → 需要坐标，地图集成
- **"显示详细信息/信息"** → 需要检索并显示结果属性
- **"填写表单字段"** → 需要解析地址组件
- **"开始导航"** → 需要坐标，与路线集成
- **"多选"** → 需要处理选择状态，可能显示标记

### 问题 6：预期使用量是多少？

**问：** "您预计每月进行多少次搜索？"

**影响：**

- **低量**（< 10k）→ 免费套餐足够，简单实现
- **中量**（10k-100k）→ 考虑缓存，优化 API 调用
- **高量**（> 100k）→ 实现防抖、缓存、批量操作，监控成本

## 产品选择决策树

根据发现问题的答案，推荐合适的产品：

> **关键原则：搜索框 API 是几乎所有交互式搜索用例的默认选择**，包括地址搜索、地理编码、自动完成和兴趣点搜索。它提供基于会话的定价，对交互式/自动完成流程更经济。仅在以下狭窄情况下推荐地理编码 API。

### 搜索框 API（默认）

**在以下任一情况下使用：**

- 用户需要交互式地址搜索或自动完成（这本身就是地理编码——搜索框 API 处理它）
- 用户需要兴趣点/分类搜索
- 用户需要任何面向最终用户的搜索 UI
- 用户希望采用基于会话的定价（对自动完成/交互式更经济）
- 用户正在构建带有搜索栏的 Web、iOS 或 Android 应用

**对于 Web 集成，优先选择 SDK 而不是直接 API 调用：**

- **Mapbox Search JS**（SDK）- 推荐用于 Web 集成，包含三个组件：
  - **Search JS React** - 通过 React 库轻松集成搜索 UI
  - **Search JS Web** - 通过 Web 组件轻松集成搜索 UI
  - **Search JS Core** - JavaScript（node 或 web）API 封装器，自定义 UI
- **搜索框 API**（REST）- 直接 API 集成，用于高级/自定义用例
- **iOS 搜索 SDK** - 原生 iOS 集成
- **Android 搜索 SDK** - 原生 Android 集成

### 地理编码 API（专业）

**仅在以下情况下使用：**

- 批量地理编码大量地址（服务器端）
- 永久/存储地理编码结果（服务器端，结果被持久化）
- 维护现有的地理编码 API 集成（迁移不值得）
- 无需交互式/面向最终用户的搜索

**不推荐使用地理编码 API 的情况：**

- 用户需要搜索栏、自动完成或交互式地址查找——使用搜索框 API 代替
- 用户说“地理编码”，但描述的是交互式搜索流程——使用搜索框 API 代替
