# HTML 计划

将源材料转化为可供检查和行动的计划。保留用户范围、顺序、承诺和术语，除非他们要求更广泛的综合。

## 围绕工作构建文档

在设计之前，阅读对话、项目指令和提供的计划。当存在现有设计语言时，匹配该设计语言。否则，从受众和主题中推导出一种安静、务实方向。

当 [`design-artifact`](../design-artifact/SKILL.md) 可用时，阅读其基础知识，以使该方向有意为之。保持此技能的可追溯性和源保留规则为权威；创意方向不得将计划膨胀为仪表板或活动页面。

决定计划实际需要什么：

- 阶段或顺序；
- 状态和决策点；
- 所有者和协作者；
- 依赖关系和风险；
- 接受检查；
- 未解决的问题。

除非源材料支持，否则不要添加时间线、进度百分比、状态徽章或仪表板摘要。在不将实施计划膨胀为战略文件的情况下，改进语法和结构。

## 保留可追溯性

- 保持源承诺的可识别性。
- 将接受的决策与假设和开放问题分开。
- 仅在它们真实存在的地方显示顺序和依赖关系。
- 使用表格进行精确映射、比较或重复字段。
- 仅当它使顺序实质上更容易理解时，使用流程或时间线。
- 保持长篇文本可读，而不是强迫每个段落都进入卡片。

## 构建和验证

交付一个响应式、可访问、自包含的 HTML 文件。使用语义标题、列表、表格和地标。保留必要的 CSS 和 JavaScript 在行内，避免外部服务，并使任何导航或披露都可通过键盘操作。

在宽度和窄宽度下检查结果。检查没有承诺消失，阶段是否保持在预期顺序中，所有权和依赖关系是否清晰，以及长内容是否不会溢出。

返回绝对路径，并注明你引入的任何结构解释。
