# HTML 原型

构建一个可信的产品决策模型。将产物与用户的上下文相匹配，而不是应用一套固定的风格。目标不是制作所有可能的屏幕。目标是使重要的视觉或行为问题可测试。

## 选择保真度模式

使用以下两种模式之一：

- **Mockup（模型图）**：当开放问题是视觉层次结构、布局、排版、颜色或产品契合度时，创建一个精致、响应式、基本静态的产物。
- **Prototype（原型）**：当开放问题是导航、输入、状态变化、反馈、恢复或过渡时，创建一个可工作的流程。

不要创建单独的 `html-mockup` 技能。不要仅仅为了使模型图看起来更完整而添加行为。如果用户要求两种模式，请保留相同的内容和结构，以便保真度变化易于比较。

## 从上下文推导方向

在设计和之前，检查对话、提供的参考和项目。寻找设计系统文档、标记、现有组件、产品截图和附近的产物。

权威按以下顺序运行：

1. 用户的明确视觉和功能指令。
2. 项目已建立的设计语言和交互约定。
3. 产品、受众、内容和场景。
4. 你自己的设计判断。

在编码之前，确定：

- 用户和关键任务；
- 审查的边界场景；
- 模型图或原型模式；
- 视觉方向的来源；
- 相关的状态模型；
- 真实产品接管的位置。

当不存在设计系统时，从主题和用例创建一个特定的方向。不要默认使用渐变、暗色仪表板、可互换的卡片或装饰性指标。用于现场工具、编辑工作流和财务审批的原型不应感觉像同一个产品。

当 [`design-artifact`](../design-artifact/SKILL.md) 可用时，如果视觉方向仍然开放，请阅读并使用此技能进行组合。使用它来选择语域、调色板、类型和构图；将此技能保留为保真度、状态和交互完整性的权威。

## 范围一个可信的体验

选择可以回答审查问题的最小流程。使用真实、内部一致的名称、日期、状态、数量和文本。

- 使导航对所建模的范围有效。
- 实现带有标签、验证、提交反馈和合理默认值的表单。
- 仅在场景中包含中断或确认时使用对话框。
- 使用过渡来澄清连续性或状态变化，而不是作为装饰。
- 删除死按钮。如果操作属于真实系统，请解释边界，而不是假装它已完成。

## 建模相关状态

在构建之前列出状态。包括所选场景实际上可以到达的状态：

- 加载中；
- 空的；
- 错误；
- 成功；
- 禁用；
- 移动端；
- 简报中的特定领域状态。

看起来像异步的原型操作通常应显示加载中、成功和失败或恢复。集合通常应考虑空状态。受限制的操作应显示其禁用的原因。不要强迫不相关的状态进入主流程，仅仅为了满足清单。在交接中使省略的状态明确。

## 使交互完整

- 当原生元素提供正确的语义时，使用原生元素。
- 使用键盘支持整个建模的流程。
- 保持焦点可见，并在有意义转换后有意放置它。
- 给对话框一个可访问的名称，包含焦点，在 `Escape` 上关闭，并将焦点恢复到触发器。
- 将表单错误与其控件相关联，并宣布重要的状态变化。
- 不要将基本行为隐藏在悬停后面。
- 在保留状态反馈的同时尊重 `prefers-reduced-motion`。
- 使触摸目标可用，并防止意外的页面级水平溢出。

在模型图模式下，即使控件未连接，也要保留语义结构和可见的焦点样式。使静态审查边界清晰。

## 建立合同

- 提供一个包含基本 CSS 和 JavaScript 的自包含 `.html` 文件。
- 不需要构建工具、身份验证、实时 API 或外部服务。
- 使用响应式构图，而不是缩小桌面画布。
- 保持设计标记小，并针对所选方向特定。
- 使用可访问的对比度，并不仅仅是颜色来传达状态。
- 优先考虑一个流程的深度和正确性，而不是在假产品上跨越广度。

## 验证和交接

在宽屏和窄屏移动宽度上测试产物。执行每个建模的状态和控制。在适当的地方测试 `Tab`、`Shift+Tab`、`Enter`、`Space`、箭头键，以及 `Escape` 用于对话框。检查控制台、页面溢出、长内容、禁用行为、焦点恢复和减少运动模式。

检查每个不同表面的计算前景色和背景色，特别是可能继承主体颜色在暗色或染色区域内的文本。如果浏览器工具不可用，请说明哪些视觉和交互检查未验证，而不是将源检查视为替代品。

返回绝对文件路径、保真度模式、建模的场景、实现的状态以及故意省略的生产行为。
