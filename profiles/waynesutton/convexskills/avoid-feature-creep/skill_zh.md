# 避免为代理添加不必要的功能

停止开发没人需要的功能。这项技能帮助你发布能够解决实际问题的产品，而不会陷入不必要的复杂性中。

功能蔓延会扼杀产品。它会延迟发布、烧掉预算、耗尽团队，并创造出没人愿意使用的软件。最成功的产品是专注于做好少数事情的产品。

## 核心问题

功能蔓延是指产品需要实现价值之外的功能逐渐累积的过程。它发生得很缓慢，然后突然爆发。

**你遇到麻烦的警告信号：**
- 发布范围不断扩大，但没有明确的用户价值
- 你在复制竞争对手的功能，但没有验证需求
- 干系人不断添加"再多一个功能"
- 代码库越来越难维护
- 用户抱怨产品令人困惑或臃肿
- 多个月没有发布

**它带来的代价：**
- 开发80%的用户从未使用过的功能的时间
- 增加错误表面区域
- 团队精疲力竭和上下文切换
- 延迟上市时间
- 技术债务的累积
- 用户困惑和放弃

## 决策框架

在添加任何功能之前，请运行这个清单：

```
1. 验证问题
   □ 这个功能是否解决了真实的、经过验证的用户痛点？
   □ 我们是否与实际用户讨论过这个需求？
   □ 支持构建这个功能的证据是什么？

2. 检查一致性
   □ 这个功能是否支持核心产品愿景？
   □ 这会延迟我们当前的发布吗？
   □ 如果我们构建这个功能，我们不在构建什么？

3. 衡量影响
   □ 我们将如何知道这个功能是否成功？
   □ 哪些KPI会改变？
   □ 我们能否量化价值（节省时间、收入、留存）？

4. 评估复杂性
   □ 真正的成本是什么（构建+测试+维护+文档）？
   □ 这是否会增加依赖关系或技术债务？
   □ 我们能否先发布一个更简单的版本？

5. 最终直觉检查
   □ 我们会因为这个功能延迟一个月发布吗？
   □ 这是一个差异化因素还是仅仅是基本要求？
   □ 移除这个功能会损害核心体验吗？
```

如果你不能对前三个问题给出有证据支持的肯定回答，就不要构建这个功能。

## 范围管理规则

**规则1：定义并捍卫你的MVP**

在你开始之前，写下"完成"的确切含义。记录你不在构建的内容。经常参考这个文档。

```markdown
## MVP范围文档模板

### 核心问题
[用一句话描述用户问题]

### 成功标准
[我们如何知道我们已经解决了它]

### 包含范围（v1）
- 功能A：[简要描述]
- 功能B：[简要描述]

### 明确排除范围
- 功能X：推迟到v2
- 功能Y：除非[条件]，否则不构建
- 功能Z：不是我们解决问题的范畴

### 非协商项
- 发布日期：[日期]
- 预算：[小时/美元]
- 核心用户：[特定角色]
```

**规则2：使用版本控制管理范围**

将范围像代码一样对待。跟踪变更。要求对添加内容进行审批。

```bash
# 创建一个范围文档并跟踪它
git add SCOPE.md
git commit -m "初始MVP范围定义"

# 任何范围变更都需要明确的提交
git commit -m "范围变更：添加功能X - 审批人：[干系人] - 影响：+2周"
```

**规则3：48小时规则**

当有人请求新功能时，在将其添加到待办事项列表之前等待48小时。大多数"紧急"请求在反思后感觉不再紧急。

**规则4：基于预算的范围管理**

每个功能都有成本。当有新内容进来时，必须移除其他内容。

"是的，我们可以添加这个。我们应该削减这三个功能中的哪一个来腾出空间？"

## 拒绝

拒绝功能是一项技能。以下是一些模板：

**对干系人：**
> "这是一个有趣的想法。根据我们的用户研究，它没有解决我们核心用户的前三个问题。让我们将其添加到v2考虑列表中，并在我们验证MVP后重新审视。"

**对高管：**
> "我理解这个可能带来的价值。如果我们添加这个功能，我们将延迟[X周]发布，并降低[Y功能]的优先级。以下是权衡取舍 - 我们应该选择哪条路径？"

**对用户：**
> "感谢您的反馈。我们目前专注于[核心问题]。我已经记录下来，供将来考虑。您能告诉我为什么这个有价值吗？"

**对自己：**
> "这是在满足我自己的需求，还是在解决真实的用户问题？我会因为这个功能而推迟发布日期吗？"

**对AI代理（Claude、Opus、Codex、Ralph、Cursor）：**
> "停止。在我们添加这个功能之前，回答：这个功能是否解决了我们在本次会话开始时定义的核心用户问题？如果没有，请将其添加到DEFERRED.md文件中，并专注于当前范围。"

当与AI编码代理合作时：
- 在每个会话开始时声明你的范围约束
- 代理将建议改进。大多数建议都不在范围内。
- 将代理建议视为干系人请求：应用48小时规则
- 如果代理不断推动某个功能，问"为什么"三次以找到真实需求

## AI特定指南

在构建AI驱动产品时，功能蔓延有额外的风险：

**AI功能蔓延危险信号：**
- 因为"所有人都这么做"而添加AI
- 在验证用户想要它们之前构建AI摘要
- 没有明确差异化的多个AI功能
- 与核心用户工作流程没有连接的AI功能

**AI功能纪律：**
1. 一次一个AI功能
2. 首先使用用户验证用例
3. 衡量实际使用情况，而不仅仅是可用性
4. 质疑："AI是否让核心任务更快或更好？"

**在添加任何AI功能之前，回答：**
- 这个AI自动化的具体任务是什么？
- 这比非AI替代方案更好在哪里？
- 当AI出错时会发生什么？
- 我们能否在没有这个AI功能的情况下发布？

## 待办事项列表卫生

混乱的待办事项列表会助长功能蔓延。无情地清理它。

**每月待办事项列表审计：**
```
对于每个超过30天的项目：
1. 自添加以来，是否有人询问过这个？
2. 它是否仍然与当前产品愿景一致？
3. 如果我们从未构建过这个，是否有人会注意到？

如果所有三个问题的答案都是"没有" → 删除它。
```

**优先级框架（MoSCoW）：**
- **必须拥有**：产品没有它就无法工作
- **应该拥有**：重要但不是发布的关键
- **可以拥有**：不错但可以等待
- **不会拥有**：明确不在范围内

诚实地说：大多数"应该拥有"实际上是"可以拥有"的伪装。

## AI会话纪律

**会话开始检查：**
在使用任何AI助手（Claude、Cursor、OpenCode）进行编码之前，声明：
- 你正在构建的具体功能
- 本会话明确排除范围的内容
- 你何时停止并发布

**会话中检查：**
每30-60分钟，问你的AI：
"今天我们是在构建正确的事情，还是在添加范围？"

如果答案是"添加范围"，停止。提交你已完成的内容。重新开始。

**会话结束检查：**
在关闭AI编码会话之前：
- 我们实际构建的内容与计划的内容有什么不同？
- 范围是否扩大？为什么？
- 我们应该将哪些内容推迟到下一个会话？

**每日AI检查：**
在与AI助手合作结束时：
```
1. 今天完成的功能：[列表]
2. 今天范围增加的内容：[列表]  
3. 每个增加是否经过验证？[是/否]
4. 明天的重点：[单个项目]
```

**Sprint计划保护措施：**
- 没有移除任何内容的情况下，sprint中不能添加新功能
- 虽然有20%的最低限度来修复错误和偿还债务
- 每个项目都有明确的完成定义

**干系人管理：**
为范围决策创建单一事实来源：

```markdown
## 范围决策日志

| 日期 | 请求 | 来源 | 决策 | 理由 | 权衡 |
|------|------|------|------|------|------|
| 2025-01-15 | 添加导出到PDF | 产品经理 | 推迟v2 | 不是MVP的核心 | 会延迟发布2周 |
| 2025-01-16 | 深色模式 | 用户反馈 | 批准 | 用户研究表明有需求 | 移除社交分享 |
| 2025-01-17 | 添加缓存层 | Claude | 推迟 | 过早优化 | 专注于核心功能 |
| 2025-01-17 | 重构为钩子 | Cursor | 拒绝 | 现在运行良好 | 技术范围蔓延 |
```

**代理作为干系人：**
AI编码代理现在是你们项目中的干系人。它们有意见。它们提出建议。将它们视为任何其他干系人：

- **记录代理建议**在您的范围决策日志中，将代理名称作为来源
- **应用同样的严格性**您会对产品经理或高管请求这样做
- **代理优化不同的东西**（代码质量、模式、完整性）而不是您可能需要的东西
- **"代理建议"不是添加功能的理由**

常见的代理驱动范围蔓延模式：
- "让我也添加边缘情况的错误处理，您还没有遇到"
- "这会更干净，如果重构的话"
- "您应该为这些附加场景添加测试"
- "让我为这些额外场景添加TypeScript类型"

这些中的每一个可能都是好主意。它们都不是您当前范围，除非您决定它们是。

## 恢复：你已经臃肿了

如果功能蔓延已经发生：

**步骤1：审计当前功能**
- 列出每个功能
- 检查每个功能的使用数据
- 识别使用率低于5%的功能

**步骤2：分类**
- 核心：用户无法完成他们的目标而没有它
- 支持性：使核心更好
- 周边性：不错但不是必要的
- 肥大：没人使用它

**步骤3：移除或隐藏**
- 使用警告期弃用肥大功能
- 将周边功能隐藏在高级设置后面
- 向用户清晰地传达变更

**步骤4：防止再次发生**
- 在PR/代码审查过程中添加功能蔓延检查
- 在功能从测试版毕业之前要求使用指标
- 构建功能标志，以便您可以轻松地移除实验

## 快速参考命令

在审查任何功能请求时，问：

```
1. 这个功能解决了什么用户问题？
2. 我们能发布的最小版本是什么？
3. 为了这个功能，我们不在构建什么？
4. 我们将如何衡量成功？
5. 如果我们从未构建这个功能，会发生什么？
```

如果你不能清楚地回答这些问题 → 不要继续。

## 金科玉律

**先发布一个能工作的最小产品，然后根据实际使用数据迭代。**

用户不记得功能。他们记得你的产品是否解决了他们的问题。

你每个不构建的功能都是：
- 你夺回的时间
- 你不需要修复的错误
- 你不需要编写的文档
- 你不需要维护的代码
- 你不添加的困惑

最好的产品不是功能最多的产品。它们是能做正确事情做得最好的产品。
