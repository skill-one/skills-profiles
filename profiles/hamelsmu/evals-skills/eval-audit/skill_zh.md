# 评估审计

检查LLM评估流程并生成问题清单及具体后续步骤。

## 概述

1. 收集评估工件：跟踪记录、评估器配置、裁判提示、标记数据、指标仪表板
2. 在六个方面进行诊断检查
3. 生成按影响排序的发现报告，每个发现链接到修复方案

## 前置条件

通过可观察性MCP服务器或本地文件访问评估工件（跟踪记录、评估器配置、裁判提示、标记数据）。如果不存在，则跳转到“无评估基础设施”。

## 连接到评估基础设施

检查用户是否连接了可观察性MCP服务器（如Phoenix、Braintrust、LangSmith、Truesight或类似系统）。如果可用，使用它来拉取跟踪记录、评估器定义和实验结果。如果没有，请要求提供本地文件：CSV文件、JSON跟踪导出、笔记本或评估脚本。

## 诊断检查

逐个检查下方区域。检查可用工件，确定是否存在问题，如果存在则记录发现。

按对用户产品的影响对发现进行优先级排序。首先呈现影响最大的发现。

### 1. 错误分析

**检查：** 用户是否对真实或合成跟踪记录进行了系统性的错误分析？

查找：标记的跟踪数据集、失败类别定义、跟踪审查笔记。如果存在评估器但没有记录的失败类别，则可能跳过了错误分析。

**发现（如果缺失）：** 评估器在没有错误分析的情况下构建，评估通用质量（“有用性”、“连贯性”）而不是实际失败模式。首先使用`error-analysis`，或者如果不存在跟踪记录，则首先使用`generate-synthetic-data`。

参见：[您的AI产品需要评估](https://hamel.dev/blog/posts/evals/index.html)、[LLM评估常见问题解答](https://hamel.dev/blog/posts/evals-faq/)

**检查：** 失败类别是进行头脑风暴还是观察到的？

从研究中借用的通用标签（“幻觉分数”、“毒性”、“连贯性”）表明进行了头脑风暴。基于应用的类别（“缺少查询约束”、“错误的客户语气”、“编造的属性特征”）表明进行了观察。

**发现（如果进行头脑风暴）：** 通用类别遗漏了特定于应用的失败，并产生在纸面上得分良好但在实际中遗漏了真实问题的评估器。使用`error-analysis`重新进行，从跟踪记录开始。

参见：[谁验证了验证者？](https://arxiv.org/abs/2404.12272)

### 2. 评估器设计

**检查：** 评估器是二进制通过/失败吗？

标记使用李克特量表（1-5）、字母等级（A-F）或没有明确通过/失败阈值的数值分数的任何评估器。

**发现（如果不是二进制）：** 李克特量表难以校准。标注者对3和4之间的差异意见不一，裁判继承了这种噪声。考虑转换为二进制通过/失败，并使用明确的定义，使用`write-judge-prompt`。

参见：[创建一个推动业务结果的LLM裁判](https://hamel.dev/blog/posts/llm-judge/)

**检查：** LLM裁判提示是否针对特定的失败模式？

标记评估整体（“这个响应有帮助吗？”、“评估此输出的质量”）的任何评估器。

**发现（如果模糊）：** 整体裁判产生不可操作的结论。每个裁判应检查一个特定的失败模式，具有明确的通过/失败定义和少量示例。使用`write-judge-prompt`。

**检查：** 是否尽可能使用基于代码的检查？

标记用于客观检查的LLM裁判：格式验证、约束满足、关键词存在、模式一致性。

**发现（如果过度依赖裁判）：** 用代码替换客观检查（正则表达式、解析、模式验证、执行测试）。将LLM裁判保留用于需要解释的标准。

**检查：** 是否将相似度指标作为主要评估？

标记ROUGE、BERTScore、余弦相似度或嵌入距离作为生成质量的主要评估器。

**发现（如果存在）：** 这些指标测量表面级别的重叠，而不是正确性。它们适用于检索排序，但不适用于生成评估。用基于特定失败模式的二进制评估器替换它们。

参见：[LLM评估常见问题解答](https://hamel.dev/blog/posts/evals-faq/)

### 3. 裁判验证

**检查：** LLM裁判是否通过人类标签进行验证？

查找：混淆矩阵、TPR/TNR测量值、对齐分数。在生产中未验证数据的裁判是一个关键发现。

**发现（如果未验证）：** 未验证的裁判可能会持续遗漏失败或标记通过跟踪记录。使用TPR和TNR在保留的测试集上测量对齐度。使用`validate-evaluator`。

参见：[创建一个推动业务结果的LLM裁判](https://hamel.dev/blog/posts/llm-judge/)

**检查：** 是否使用TPR/TNR或原始准确率来测量对齐度？

标记“准确率”、“百分比同意”或Cohen's Kappa作为主要对齐指标。

**发现（如果使用准确率）：** 在类别不平衡的情况下，原始准确率具有误导性：一个总是说“Pass”的裁判在90%的跟踪记录通过但未捕获任何失败时得到90%的准确率。使用TPR和TNR，它们直接映射到偏差校正。使用`validate-evaluator`。

**检查：** 是否有适当的训练/开发/测试分割？

检查裁判提示中的少量示例是否来自用于测量裁判性能的数据。

**发现（如果泄露）：** 将评估数据用作少量示例会夸大对齐分数并隐藏真实的裁判失败。分割为训练（少量示例来源）、开发（迭代）和测试（最终测量）。使用`validate-evaluator`。

### 4. 人工审查流程

**检查：** 谁在审查跟踪记录？

确定是领域专家还是外包标注者在标记数据。

**发现（如果没有领域专业知识进行外包）：** 通用标注者捕获格式错误但遗漏特定于领域的失败（错误的医疗剂量、不正确的法律引用、不匹配的属性特征）。聘请领域专家。

参见：[改进AI产品的领域指南](https://hamel.dev/blog/posts/field-guide/)

**检查：** 审查者是否看到完整的跟踪记录还是只有最终输出？

**发现（如果仅输出）：** 仅审查最终输出会隐藏流程中断的位置。显示完整跟踪记录：输入、中间步骤、工具调用、检索的上下文和最终输出。

**检查：** 如何向审查者显示数据？

标记原始JSON、未格式化文本或包含跟踪数据的电子表格单元格。

**发现（如果原始格式）：** 审查者花费精力解析数据而不是评估质量。使用自然表示格式化：渲染Markdown、语法高亮代码、将表格显示为表格。使用`build-review-interface`。

参见：[LLM评估常见问题解答](https://hamel.dev/blog/posts/evals-faq/)

### 5. 标记数据

**检查：** 是否有足够的标记数据？

对于错误分析，~100个跟踪记录是饱和的粗略目标。对于裁判验证，需要~50个通过和~50个失败的示例以获得可靠的TPR/TNR。如果标记数据稀疏，通过更有效地采样跟踪记录来收集更多：

- **随机：** 始终包括其他策略旁边的随机样本，以发现未知问题。
- **聚类：** 按语义相似性对跟踪记录进行分组，并审查每个聚类的代表。
- **数据分析：** 分析延迟、回合、工具调用和token的统计数据以查找异常值。
- **分类：** 使用现有的评估、预测模型或LLM来提取有问题的跟踪记录。谨慎使用。
- **反馈：** 使用明确的客户反馈（投诉、否定信号）来过滤跟踪记录。

**发现（如果不足）：** 小数据集产生不可靠的失败率和宽置信区间。使用上述采样策略收集更多标记数据，或使用`generate-synthetic-data`补充。

### 6. 流水线卫生

**检查：** 在重大更改后是否重新运行错误分析？

检查错误分析上次运行的时间与模型切换、提示重写、新功能或生产事件相比。

**发现（如果过时）：** 流水线更改后，失败模式会发生变化，为旧流水线构建的评估器会遗漏新的失败类型。每次重大更改后重新运行错误分析。

**检查：** 评估器是否得到维护？

查找定期重新验证裁判或刷新评估数据集。

**发现（如果设置后忘记）：** 评估器随着流水线的发展而退化。重新验证裁判，使用新鲜的人类标签，并更新评估数据集以反映当前使用情况。

## 无评估基础设施

如果用户没有评估工件（没有跟踪记录、没有评估器、没有标记数据）：

1. 对真实跟踪记录样本运行`error-analysis`。
2. 如果不存在生产数据，使用`generate-synthetic-data`创建测试输入，通过流水线，然后对生成的跟踪记录运行`error-analysis`。
3. 在完成错误分析之前，不要建议构建评估器、裁判或仪表板。

## 报告格式

按影响排序呈现发现。对于每个：

```
### [问题标题]
**状态：** [问题存在 / 良好 / 无法确定]
[1-2句对发现的具体问题的解释]
**修复：** [具体操作，参考技能或文章]
```

按六个诊断区域分组。省略未发现问题的区域。

## 反模式

- 作为清单运行审计而不检查实际工件。
- 报告与用户流水线中发现的内容脱节的通用建议。
- 在完成错误分析之前建议评估器。
- 建议使用LLM裁判来处理代码检查可以处理的失败。
- 将此审计视为一次性事件。在重大流水线更改后重新审计。
