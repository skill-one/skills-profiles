# natural-japanese

为了使工作日语易于阅读和理解而撰写的技能。从会议记录、调查报告、内部指南、研究笔记、幻灯片等工作文件，到笔记、博客、散文。AI气味去除是作为流程的一部分整合进来的。

## 设计理念

有两个核心。第一是“检测由机器，判断由AI”。因为AI很难认识自己的习惯，所以可疑检测由机器决定性地执行，是否修改由AI（你）根据上下文判断。第二是“事后修正不如生成时约束”。在写完后消除AI气味，不如在写之前的设计和写的时候的约束来防止其发生更有效。流程按“设计 → 撰写 → 检查 → 收敛”的顺序进行。

## 执行模式 — 快速和完整

使用两种不同工作量模式的相同流程。预计所需时间——快速模式适用于短文（会议记录程度）约30秒左右，稍长（1万字级别）约3分钟。完整模式适用于短文约7分钟，1万字级别约15-20分钟。开始完整模式时，应先向用户传达此参考时间后再开始。

**快速（默认）**: 日常文件使用此模式。不使用子代理，在此处完成。只需阅读相应的doctype的type1文件即可（文体宪法是§2的摘要就足够了。其他references只在lint的finding导致判断犹豫时才打开）。设计（§1）是在脑海中完成读者、主信息、标题的确认。检查是执行一次lint，并进行自己的骨架通读。lint即使对于短文也不省略（对于短文，统计检测器会沉默，但禁止语和翻译感即使是一句话也能检测到。这是几秒钟的保险，如果跳过它，快速模式的品质保证就不成立）。收敛循环如果没有新的finding则在一周内结束，进行最终通读后结束。预计由技能引起的额外时间应在几十秒内，如果超出这个范围开始加载references，那么你正在执行完整模式的工作。

**完整**: 当用户说“认真”、“仔细”、“可以花时间”时，对外部、管理层等失败成本较高的文件，或长文件（参考1万字以上）时。一旦决定完整模式（或者用户指定完整模式），即使文件很小，也不省略流程。除了lint之外，还执行outline / terms，并必须使用三个子代理并行执行检查（§4）——结构审查、易读性审查、doctype对照（各自返回意见，判断记录到父代理，必须由父代理进行“修改/保留”的判断。写作本身不分割——浓度、比喻的一致性、章节之间的连接需要查看整个文件才能保持）。收敛是满足状态条件（§5）为止。即使感觉“这篇文章过于冗长”，也不要自行缩短流程，而是向用户建议切换到快速模式。另外，实测中，低思考预算(effort)的执行可以合理化地削减完整流程。在可以选择effort的环境中执行完整模式时，推荐使用high（快速模式使用low就足够了）。

如果犹豫不决，最好先用快速模式完成，然后向用户补充一句“也可以用完整模式润色”。

## 调用方式 — write / score / 模式指定

当技能作为带参数的命令调用时，解释以下形式。

- `/natural-japanese [quick|full] <目标>` — 写作/修改（默认）。新创建还是重写是根据目标判断的
- `/natural-japanese write [quick|full] <主题或素材>` — **明确新建**。从没有原始文章的状态开始，按照§1的设计（读者、主信息、骨架、浓度、素材收集）→§2的写作→检查→收敛的整个流程来撰写。如果素材不足，则先在§1-4中收集，或者向用户索取
- `/natural-japanese score [quick|full|exp] <文件>` — **仅诊断**。不更改文件，返回自然度分数（0〜100，分数越高越自然=AI气味越淡）和原因。quick=lint 仅（30秒），full=包含结构、易读性审查，exp=包含semantic.py的深层检测（首次约1GB下载）。**必须首先阅读 `references/diagnose.md`**。分数的计算公式、阈值、输出格式的定义都在那里，如果不阅读lint findings的转记就返回，那么你就没有执行诊断模式的工作。诊断后可以建议重写，但在要求之前不要直接修改

如果没有模式指定，则根据执行模式的基准自行选择。自然语言也是一样（“关于〇〇写作”→ write 相当，“这篇文章AI味浓吗？”、“AI气味评分”→ score 相当）。

## 1. 设计 — 写之前决定

### 1-1. 读者、目的、文档类型

确定谁阅读，阅读后希望发生什么文档（不清楚则询问用户）。一旦确定了文档类型，就阅读相应的型:

- 会议记录 → `references/doctypes/minutes.md`
- 调查报告、分析报告 → `references/doctypes/report.md`
- 内部指南、手册 → `references/doctypes/guide.md`
- 研究笔记、讨论文件、企划书 → `references/doctypes/memo.md`
- 幻灯片结构 → `references/doctypes/slide.md`

不适用型的文档（笔记、博客、散文等）可以跳过本节。

### 1-2. 主信息和骨架

在写正文之前，用一句话写主信息。写不出来就是素材不足，而不是写作方法的问题（→ 1-4）。接下来制作标题骨架。每个标题都是“背景”、“总结”之类的标签，而不是包含结论的消息。只读标题，确认论点通顺后再进入正文。

### 1-3. 浓度设计

如果所有节都使用相同的温度、相同的厚度，这本身就会产生“过度整齐的不自然”。设计重要的节要厚，轻的节要诚实地轻，有意设计差异。步骤参考 `references/revision-guide.md` 的“浓度设计”。

### 1-4. 素材收集 — 非强制、新写作时

如果固有名词、数字、实例缺乏，开始写作后，即使意识到“只有一般论”，也无法修改。通过推理和搜索的往返收集素材的步骤、判断是否充足的基准、Web搜索不可用环境下的用户素材提供请求参考 `references/revision-guide.md` 的“素材收集”。

### 1-5. 文体配置文件 — 非强制

如果 `style-profile.md`（项目根目录或用户指定的位置）已经存在，则读取它，以视角、词汇、节奏的癖为模板。如果没有，则使用通用模式进行。只有在用户要求“学习自己的文体”时，才按照 `assets/style-profile-template.md` 沿着过去文章3〜5本提取特征，并输出配置文件（不要过度断言，保留“趋势”）。如果用户明确指出“不使用某些词汇或组合”、“不自然”，则不将其扩展到一般规则，而是添加来源和适用范围，记录在同配置文件的“避免表达”中。不禁止整个单词，而是将指出的组合作为最小单位处理。

## 2. 撰写 — 在文体宪法下撰写

以 `references/writing-constitution.md` 的12条为约束撰写正文。要点仅举几例——不从前置结论开始写，标题是消息，说明用地文书写，列表是压缩的真正并行，专业术语按“功能→名称”的顺序在文中说明，固有名词、数字接地，文中核1处加粗，添加浓度，不重复相同的铸型，“〜而不是”只用于真正的误解更正，极限和估计使用明确标签公开，事实和意见分开，结尾是再统一，报告是So What。

在此阶段不必过于担心禁止语或节奏，在宪法范围内充分表达内容即可。细节将在下一个检查阶段处理。

## 3. 检查(1) — 静态检测

```
uv run scripts/lint.py --json <file>
```

检测禁止语、翻译感、否定肯定对比的重复、文本长度的均匀性、体言止め率、段落头的连接词率、词汇多样性、英语句法的怀疑等。检测结果无论数量如何都是exit code 0（lint，所以不会因为数量停止CI）。只有输入错误时才exit code 1。

如果目标文档类型明确，则指定 `--genre essay|tech|business`。切换到校正好的语料库阈值配置文件，减少误检。不同类型之间的判断标准差异参考 `references/genre-notes.md`。

在收敛循环（4〜5）中，将前一个 `--json` 输出作为 `--baseline` 传递，会自动分类为resolved / new / persisting。在 `uv` 不可用环境（Claude.ai 等）中，参考 `references/manual-checklist.md` 以相同观点手动模拟。

还有 `scripts/semantic.py` 这个 EXPERIMENTAL 的语义检测器。它通过文本嵌入测量相邻文本的相似度起伏（话题的平板度），但由于torch + sentence-transformers依赖和首次~1GB的模型下载，作为重量级，没有整合到lint.py本体中，而是作为独立的opt-in入口。只有在完整流程或环境允许时，才添加运行 `uv run scripts/semantic.py --json <file>`，并将findings与lint一样放入判断记录中处理。

## 4. 检查(2) — 判断记录和两个审查

lint的findings只是可疑的提示，不是指示机器全部修改。重读本次命中类别的节，根据上下文判断“修改/不修改”。判断是逐个记录“修改了”还是“保留（理由）”同时进行（记录的格式参考同文件“判断记录”）。

如果需要术语目录: 禁止语 → `references/forbidden-patterns.md`、翻译感 → `references/translationese.md`。确认专业术语是否首次出现并说明的材料使用 `uv run scripts/terms.py <file>`。以初出行、出现次数、说明标记的有无列出假名复合词、ASCII缩写、看似固有名词的词（是否说明由机器判断，AI/人判断）。

### 结构审查 — 骨架通读

lint只能看到文本层面的表层。特别是以列表为主的会议记录、幻灯片，lint几乎会直接通过，因此结构审查成为主角。从完成的文本中提取标题和每个段落的起始句，阅读并确认（`uv run scripts/outline.py <file>` 可以以行号附加的方式机械提取标题、每个段落的起始句、列表占位符）:

1. 论点是否通顺（骨架上就能追上话题）
2. 每个标题是否是消息
3. 是否有重复相同的铸型（定义文的型、节的内部结构、写作的文型）
4. 是否有浓度（所有节是否都是相同的厚度）
5. 结尾是否连接到So What（报告类）
6. business、tech的解释、案例研究、报告是否在最后等待主要回答。此外，是否在事实说明之外多次追查预告、异常、揭示、回收。

如果文档类型确定，也会对照doctype的“必需元素”和“AI容易犯的错误”。

### 易读性审查

`uv run skills/natural-japanese/scripts/lint.py --reading-load <文件>` 可以指出易读性高的地方（一句长、隐藏的列表、连续汉字、双重否定、“の”连锁）。**这是与AI气味检测不同目的的推敲用轨道，自然度分数也不包含 `--baseline` 比较**。输出是“看看这个句子”，而不是“修改它”。指摘是起点，如何修改参考下文目录。

语序、标点位置、一文一义、主语谓语距离、助词的过度使用、冗长表达是机器阈值化无法判断的领域。参考 `references/readability-principles.md`（一般原则）和 `references/readability-antipatterns.md`（按易读性负载顺序A→J分类的27种坏文模式目录）每周参考，目视判断。**目录从前面开始应用**——A（否定嵌套）・B（关联距离）・C（词与词形重量）是一文中迫使读者计算的高负载层，H・I・J是跨越文档、书写、读者知识的层。短不是目标函数，而是在确认事实保持和主谓、关联后，在同等候选之间才使用平分。短文分割或列表展开导致字数增加是正确的结果，不应作为不合格理由。

结构审查、易读性审查中发现的问题也与lint的findings一样记录到判断记录中。

如果段落只说了一般论（没有固有名词、数字、实例），则可能是写作方法的问题，而不是素材问题。参考 `references/revision-guide.md` 的“素材不足分支”判断是否应返回信息收集。

## 5. 收敛

反映记录中“修改了”的项目后，重新运行lint，确认是否没有新的finding。重复3〜4，直到记录上的所有finding都被分类，修正不会产生新的finding。如果相同的finding连续两周复发，参考 `references/revision-guide.md` 的“发散保护”。

对于现有文档的重写，如果对所有项目统一应用相同类型的修改（标题的结论化、列表的地文化等），会消除原始文档的自然浓度，反而增加AI气味。只选择有价值的部分修改的原则参考 `references/revision-guide.md` 的“不要一律适用改稿”。

## 6. 最终阶段 — 自我检查循环和评估锁

即使lint和记录收敛，这也只是消除了既知的表层模式。从这里开始，容易残留lint检测不到的“无菌室般的冷漠”、“冗长拖沓”。

在完整模式（以及重要文件）中，使用 `references/eval-rubric.md` 的 **6轴推敲Rubric** 进行客观评估。

1. **消除AI气味、文体的自然性**: 没有演讲式的数字声明、煽动共鸣、翻译感短划线、决定性句子
2. **信息密度、简洁性（排除冗长拖沓）**: 删除了占用读者时间的不必要的开场白、解释、言辞水增
3. **功能性、可扫描性**: 能否最短距离、不迷路地找到所需信息
4. **逻辑的清晰性和说服力**: 因果关系是否令人信服，是否有实测、具体实例接地
5. **人性、诚实性（体温、动机）**: 不患无菌病，是否宿有作者的真实感受、问题意识（Why）
6. **自我证明力**: 这份文件本身是否成为没有虚假标牌的最佳范例

**合格标准是全轴90分以上、综合平均92分以上**。未达标的轴需要确定瓶颈进行改稿，直到达到合格标准为止（详细步骤参考 `references/eval-rubric.md` 以及 `references/revision-guide.md`）。快速模式则在此6点中在脑海中通读检查后结束。发现不协调感时直接修改完成。

## 7. 清理

完成后，删除所有中间文件（记录、lint的JSON、草稿备份等）。用户项目中只保留完成的文档和用户明确要求保留的 `style-profile.md`。详细参考 `references/revision-guide.md` 的“处理作业文件”。
