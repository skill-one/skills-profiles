# Paper-to-PPTX — 路由器

## 路由协议

对于现有演示文稿的编辑，重用其论文来源、叙述、术语和资源。
更改请求的幻灯片以及任何受影响的跨幻灯片引用；除非请求需要，否则不要重新运行论文摄入或重建演示文稿的故事。在交付前检查更改后的幻灯片并运行现有的最终 PPTX 审计。单独请求的大纲或解释不需要创建演示文稿。

对于新任务，加载以下核心和匹配资源。重用已加载的后续指导；仅在任务需要时才加载更多。

### 1. 加载清单和核心层

读取 `[manifest.yaml](manifest.yaml)`。它声明了 `paper_type` 轴、允许的值以及每个值映射到的文件路径。

还要读取 `always_load` 下列出的每个文件。这些文件包含目的和核心原则、精简操作模式和工具链策略、9 步工作流骨干以及适用于每个演示文稿的输出/质量规则，以及用于在幻灯片之间保持技术术语一致的共享术语账本。

### 2. 对论文类型进行分类

使用清单的 `detect:` 提示和来源决定 `paper_type` 值：

- `discovery` — 发现/机制论文（问题到证据的弧线）。默认。
- `methods` — 方法/AI/工具/算法论文（问题到解决方案的弧线）。
- `resource` — 资源/数据集/图谱/组学/基准论文（工作流到验证的弧线）。
- `clinical` — 临床/人群/干预研究（设计到推断的弧线）。
- `materials` — 材料/化学/物理/工程论文（属性到机制/设计到性能的弧线）。
- `review` — 综述/观点/评论/荟萃分析（证据地图的弧线）。

在设计幻灯片之前，向用户声明检测到的值，以便他们可以廉价地纠正你。

### 3. 加载匹配的片段

读取为检测到的 `paper_type` 映射的文件。它提供了演示文稿的弧线以及如何调整此类型的默认幻灯片结构。**不要**读取 `static/` 中的每个片段。

### 4. 使用加载的材料构建演示文稿

按此优先级顺序应用加载的片段：

1. 核心原则 (`core/principles.md`) — 论点是骨干；精简操作模式；接受的输入；默认为中文的语言规则。
2. 工具链策略和快速路径 (`core/toolchain.md`) — 跨平台 Python 优先的堆栈，默认快速路径。
3. 论文类型的弧线（加载的 `paper_type` 片段）— 此论文的叙述顺序和幻灯片结构。
4. 工作流 (`core/workflow.md`) — 依次运行 9 步。
5. 输出和质量规则 (`core/output-and-quality.md`) — 交付成果、质量门禁、回退。

在读取源文件时构建术语账本 (`../nature-shared/core/terminology-ledger.md`)，以便模型名称、基因/蛋白质名称、数据集、指标和缩写在每个幻灯片和演讲者笔记中保持一致。

当请求演示文稿时，最终产品是真实的 `.pptx`，而不仅仅是大纲或脚本。不要编造结果、数字或图形细节。

### 5. 仅在需要时才查找参考文献

`references/` 下的文件是深度参考文献，不是默认值。根据清单中 `references.on_demand` 表格的需求打开它们：

- 组合/审计幻灯片布局、视觉节奏、排版、反模板设计、原型、幻灯片上的文本预算 → `references/design-and-layout.md`。
- 选择、提取、裁剪和检查图形/表格资源 → `references/figure-assets.md`。
- 运行自我审查/纠正修订循环、严重性分级、程序化 PPTX 检查、渲染预览策略和最终验证 → `references/self-review.md`。

当生成了真实的 PPTX 时，除非文件不可用，否则运行 `scripts/audit_pptx_quality.py`。将高严重性发现视为阻塞项，修订演示文稿，然后重新运行审计并将最终结果记录在 `output/qa_report.md` 中。
