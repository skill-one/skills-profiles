# 增量式实现

## 概述

以细小的垂直切片构建——实现一个部分，测试它，验证它，然后扩展。避免一次性实现整个功能。每个增量都应该让系统处于可工作、可测试的状态。这是使大型功能可管理的执行纪律。

## 何时使用

- 实现任何多文件变更
- 从任务分解中构建新功能
- 重构现有代码
- 任何当你想在不测试的情况下写超过~100行代码时

**不使用时：** 单文件、单函数的变更，其范围已经很小。

## 增量循环

```
┌──────────────────────────────────────┐
│                                      │
│   实现 ──→ 测试 ──→ 验证 ──┐  │
│       ▲                           │  │
│       └───── 提交 ◄─────────────┘  │
│              │                       │
│              ▼                       │
│          下一个切片                  │
│                                      │
└──────────────────────────────────────┘
```

对于每个切片：

1. **实现** 最小的完整功能部分
2. **测试** — 运行测试套件（如果不存在，则编写测试）
3. **验证** — 确认切片按预期工作（测试通过，构建成功，手动检查）
4. **提交** -- 使用描述性信息保存进度（参见 `git-workflow-and-versioning` 获取原子提交指导）
5. **移至下一个切片** — 继续前进，不要重启

## 切片策略

### 垂直切片（首选）

构建通过整个堆栈的一个完整路径：

```
切片 1：创建任务（数据库 + API + 基础 UI）
    → 测试通过，用户可以通过 UI 创建任务

切片 2：列出任务（查询 + API + UI）
    → 测试通过，用户可以看到他们的任务

切片 3：编辑任务（更新 + API + UI）
    → 测试通过，用户可以修改任务

切片 4：删除任务（删除 + API + UI + 确认）
    → 测试通过，完整的 CRUD 完成
```

每个切片都交付可工作的端到端功能。

### 合约优先切片

当后端和前端需要并行开发时：

```
切片 0：定义 API 合约（类型、接口、OpenAPI 规范）
切片 1a：根据合约实现后端 + API 测试
切片 1b：根据匹配合约的模拟数据实现前端
切片 2：集成并测试端到端
```

### 风险优先切片

首先解决风险最高或最不确定的部分：

```
切片 1：证明 WebSocket 连接工作（最高风险）
切片 2：在已证明的连接上构建实时任务更新
切片 3：添加离线支持和重连
```

如果切片 1 失败，你会在投资切片 2 和 3 之前发现它。

## 实现规则

### 规则 0：优先简洁

在编写任何代码之前，问：“能工作的最简单的事情是什么？”

编写代码后，根据以下检查进行审查：
- 能否用更少的行数完成？
- 这些抽象是否值得它们的复杂性？
- 一个资深工程师看到这个会说“你为什么不直接...”？
- 我是在为假设的未来需求构建，还是为当前任务构建？

```
简洁检查：
✗ 带有中间件管道的通用 EventBus 用于一个通知
✓ 简单的函数调用

✗ 用于两个相似组件的抽象工厂模式
✓ 两个直接的组件，带有共享工具

✗ 配置驱动的表单构建器用于三个表单
✓ 三个表单组件
```

三行相似的代码比过早的抽象更好。首先实现简单、明显正确的版本。只有在测试证明正确性后才能优化。

### 规则 0.5：范围纪律

只接触任务要求的内容。

不要：
- “清理”你变更旁边的代码
- 重构你未修改文件的导入
- 删除你不完全理解的注释
- 添加规范中未包含的功能，因为它们“看起来有用”
- 在你只读的文件中现代化语法

如果你注意到任务范围之外有值得改进的地方，记下来——不要修复：

```
注意到但未触碰：
- src/utils/format.ts 有一个未使用的导入（与这个任务无关）
- 认证中间件可以使用更好的错误消息（单独的任务）
→ 想让我为这些创建任务吗？
```

### 规则 1：一次一件事

每个增量改变一个逻辑事物。不要混合关注点：

**不好：** 一个提交，添加了一个新组件，重构了一个现有组件，并更新了构建配置。

**好：** 三个单独的提交——每个变更一个。

### 规则 2：保持可编译

每次增量后，项目必须可以构建，现有测试必须通过。不要在切片之间将代码库置于损坏状态。

### 规则 3：为不完整功能使用功能标志

如果功能尚未准备好供用户使用，但你需要合并增量：

```typescript
// 进行中的功能标志
const ENABLE_TASK_SHARING = process.env.FEATURE_TASK_SHARING === 'true';

if (ENABLE_TASK_SHARING) {
  // 新的共享 UI
}
```

这让你可以合并小的增量到主分支，而不会暴露不完整的工作。

### 规则 4：安全默认值

新代码应默认为安全、保守的行为：

```typescript
// 安全：默认禁用，选择启用
export function createTask(data: TaskInput, options?: { notify?: boolean }) {
  const shouldNotify = options?.notify ?? false;
  // ...
}
```

### 规则 5：易于回滚

每个增量应该是独立可回滚的：

- 添加性变更（新文件、新函数）易于回滚
- 对现有代码的修改应该是最小化和专注的
- 数据库迁移应有相应的回滚迁移
- 避免在一个提交中删除某物，在同一提交中替换它——分开它们

## 与代理合作

当指导代理增量实现时：

```
“让我们实现计划中的任务 3。

从数据库模式变更和 API 端点开始。
暂时不要触碰 UI——我们将在下一个增量中处理。

实现后，运行存储库的测试和构建命令来
验证没有东西损坏。”
```

明确每个增量中包含的范围和不包含的范围。

## 增量检查清单

每次增量后，使用存储库自己的命令（参见测试驱动开发技能的“首先发现堆栈”部分）进行验证：

- [ ] 变更只做一件事，并且完整地做了它
- [ ] 所有现有测试仍然通过（存储库的测试命令：`npm test`，`./gradlew test`，`pytest`，...)
- [ ] 构建成功（存储库的构建命令）
- [ ] 类型检查通过，其中堆栈有一个（`npx tsc --noEmit`，`mypy`，...)
- [ ] 格式化检查通过（存储库的格式化命令）
- [ ] 新功能按预期工作
- [ ] 变更已使用描述性信息提交

**注意：** 在可能影响它的变更后运行每个验证命令。成功运行后，除非代码已更改，否则不要重复相同的命令——在未更改的代码上重新运行不会提供任何信息。

## 常见借口

| 借口 | 现实 |
|---|---|
| "我会在最后测试所有内容" | 错误会累积。切片 1 中的错误会使切片 2-5 错误。测试每个切片。 |
| "一次性完成更快" | 它 *感觉* 更快，直到某事出错，而你找不到是 500 行更改中的哪一行导致的。 |
| "这些变更太小，无法单独提交" | 小提交是免费的。大提交隐藏了错误，并使回滚变得痛苦。 |
| "我稍后会添加功能标志" | 如果功能不完整，就不应该对用户可见。现在添加标志。 |
| "这个重构足够小，可以包含在内" | 重构与功能混合使两者都更难审查和调试。分开它们。 |
| "让我再运行一次构建命令以确保安全" | 成功运行后，重复相同的命令不会提供任何信息，除非代码自那以后已更改。在后续编辑后再次运行它，而不是作为 reassurance。 |

## 信号灯

- 未经运行测试编写超过 100 行代码
- 单个增量中包含多个不相关的变更
- "让我快速添加这个" 范围扩展
- 跳过测试/验证步骤以加快速度
- 增量之间构建或测试损坏
- 积累的大型未提交变更
- 在第三个用例要求之前构建抽象
- “我在这里”时触碰任务范围之外的文件
- 为一次性操作创建新的工具文件
- 连续两次运行相同的构建/测试命令而没有任何中间代码更改

## 验证

完成一个任务的所有增量后：

- [ ] 每个增量都被单独测试并提交
- [ ] 完整的测试套件通过
- [ ] 构建干净
- [ ] 功能按指定端到端工作
- [ ] 没有未提交的变更剩余

## 参见

每次增量的验证是本地检查。在声明任务完成之前，应用项目范围的“完成定义”作为最终门禁，无论任务如何，每个增量都必须清除这个标准。参见 `../../references/definition-of-done.md`。
