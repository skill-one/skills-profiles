# 可观察性与指标化

## 概述

无法观察的代码就是无法操作的代码。可观察性是指从外部使用代码发出的遥测数据来回答“系统正在做什么以及为什么”的能力。指标化不是发布后才添加的功能——它和功能一起编写，就像测试一样。如果一个功能没有遥测数据，那么第一个用户报告的错误就变成了考古学而不是查询。

## 何时使用

- 构建将在生产环境中运行的任何功能
- 添加新服务、端点、后台作业或外部集成
- 生产事件诊断时间过长（“我们不知道发生了什么”）
- 设置或审查告警规则
- 审查添加 I/O、重试、队列或跨服务调用的 PR

**不适用于：**
- 诊断当前发生的故障——使用 `debugging-and-error-recovery` 技能（可观察性是使该技能下次快速的原因）
- 分析和优化测量到的延迟——使用 `performance-optimization` 技能
- 发布日监控清单和回滚触发器——参见 `shipping-and-launch` 技能；该技能涵盖为其提供指标的指标化

## 流程

### 1. 在指标化之前定义“工作”

没有问题的遥测数据就是噪音。在添加任何指标化之前，写下 2-4 个值班工程师将针对此功能提出的问题：

```
功能：结账支付重试
值班工程师将提出的问题：
1. 多少比例的支付在第一次尝试时成功，在重试后才成功？
2. 支付永久失败时为什么？（提供者错误？超时？验证？）
3. 支付提供者是否比平时慢？
→ 以下每个信号都必须有助于回答这些问题。
```

如果你无法命名问题，你就不准备进行指标化——你会记录所有内容而一无所获。

### 2. 为每个问题选择正确的信号

| 信号 | 回答 | 成本分析 | 示例 |
|---|---|---|---|
| **结构化日志** | “这个特定情况下发生了什么？” | 每个事件；随流量增长 | `payment_failed` 带有提供者错误代码 |
| **指标** | “整体频率/速度？” | 每个序列固定；查询成本低 | 提供者调用的 p99 延迟 |
| **跟踪** | “时间如何在服务之间流逝？” | 每个请求；通常采样 | 一个慢速结账，按跳段分解 |

经验法则：指标告诉你**什么**地方出错了，跟踪告诉你**哪里**出错了，日志告诉你**为什么**出错了。

### 3. 结构化日志记录

记录事件，而不是散文。每行日志都是一个具有稳定事件名和机器可读字段的 JSON 对象：

```typescript
// BAD：字符串插值——不可查询、不一致
logger.info(`Payment ${id} failed for user ${userId} after ${n} retries`);

// GOOD：稳定事件名 + 结构化字段
logger.warn({
  event: 'payment_failed',
  paymentId: id,
  provider: 'stripe',
  errorCode: err.code,
  attempt: n,
}, 'payment failed');
```

**日志级别——始终一致地使用：**

| 级别 | 含义 | 值班工程师操作 |
|---|---|---|
| `error` | 违约条件被破坏；可能需要采取行动 | 调查 |
| `warn` | 退化但已处理（重试成功，使用回退） | 关注趋势 |
| `info` | 重要业务事件（订单已放置，作业已完成） | 无 |
| `debug` | 诊断详细信息 | 默认情况下在生产环境中关闭 |

**关联 ID 是强制性的。** 在系统边界处生成（或接受）请求 ID 并将其附加到每行日志、跟踪和出站调用。没有它，你无法从交错日志中重建单个请求：

```typescript
// Express：每个请求的子日志器，ID 下游传播
app.use((req, res, next) => {
  req.id = req.headers['x-request-id'] ?? crypto.randomUUID();
  req.log = logger.child({ requestId: req.id });
  res.setHeader('x-request-id', req.id);
  next();
});
```

**当多个入口点写入一个日志时，命名入口点。** 关联 ID 识别运行；它不会说哪个代码路径启动了它。通过调度器、重放端点和手动 CLI 运行到达的相同作业产生可互换的行到一个接收器，因此将一行归因于消除——交叉阅读调度器的历史记录、进程表、部署日志——并且该论点仅当这些外部记录仍然存在时才有效。在运行开始处标记入口点，放在关联 ID 旁边，并以相同的方式传播：

```typescript
// 每个入口点一个助手：运行自己的日志器携带两个字段。
// `entryPoint`，不是 `source`——ECS 保留 `source.*` 用于网络字段。
export const runLog = (entryPoint: 'scheduler' | 'replay_endpoint' | 'cli', runId: string) =>
  logger.child({ entryPoint, requestId: runId });

// 调度器滴答        -> runLog('scheduler', crypto.randomUUID())
// POST /jobs/:id/replay -> runLog('replay_endpoint', req.id)
// CLI 调用        -> runLog('cli', process.env.RUN_ID ?? crypto.randomUUID())
```

两个字段必须与关联 ID 跨越相同的边界——队列元数据、HTTP 标头——或者工作重新推导入口点并猜测。一个仅与入口点相关的字段是一个提示，而不是归因：任何可以调用作业的内容都可以重现它。

**永远不要记录秘密、令牌、密码或完整的 PII。** 这是 `security-and-hardening` 技能的一个硬规则——遥测管道是经典的数据泄露路径。白名单字段；不要记录整个请求正文。

### 4. 指标

对于请求驱动型服务，在每个端点和每个外部依赖项上指标化**RED**：**R**ate（每秒请求数）、**E**rrors（失败率）、**D**uration（延迟直方图，不是平均值）。对于资源（队列、池、主机），使用**USE**：**U**tilization（利用率）、**S**aturation（饱和度）、**E**rrors（错误）。

与跟踪一样，供应商中立的路径是 OpenTelemetry 指标 API（与步骤 5 使用相同的 SDK 和上下文）。以下示例使用 Prometheus 的 `prom-client`——一个常见的后端选择，不是唯一的选择；RED/USE 和基数规则无论哪种方式都相同。

```typescript
import { Histogram } from 'prom-client';

const httpDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration',
  labelNames: ['method', 'route', 'status_class'],  // '2xx', 不是 '200'
  buckets: [0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});
```

**基数是故障模式。** 每个唯一标签组合都是一个单独的时间序列。标签必须来自小而固定的集合（路由模板、状态类、提供者名称）。永远不要将用户 ID、原始 URL、错误消息或其他无界值用作标签——那属于日志和跟踪。

```
作为标签可以：    route="/api/tasks/:id"   status_class="5xx"   provider="stripe"
永远不是标签：  user_id, email, request_id, 完整 URL, 错误消息文本
```

永远跟踪平均值，永远跟踪百分位数：平均值隐藏了 1% 的用户体验很糟糕。使用直方图并读取 p50/p95/p99。

### 5. 分布式跟踪

使用 OpenTelemetry——它是供应商中立的规范，并且自动指标化涵盖了 HTTP、gRPC 和常见数据库客户端，几乎零代码：

```typescript
// tracing.ts — 必须在其他任何内容之前导入
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';

const sdk = new NodeSDK({
  serviceName: 'checkout-service',
  instrumentations: [getNodeAutoInstrumentations()],
});
sdk.start();
```

仅在有意义内部工作单元（例如，`applyDiscounts`、`chargeProvider`）周围添加手动跟踪，并附加值班工程师将按其过滤的属性。跨每个异步边界传播上下文——HTTP 标头、队列消息元数据——否则跟踪将在间隙处中断。默认情况下以低比率基于头部采样；如果您的后端支持尾部采样，请保留 100% 的错误。

### 6. 告警

基于**用户感受到的症状**进行告警，而不是基于原因：

```
症状（值得在页面上显示的）：           原因（仪表板，不是页面）：
错误率 > 1% 持续 5 分钟        CPU 达到 85%
p99 延迟 > 2s                 一个 Pod 已重启
队列年龄 > 10 分钟             磁盘达到 70%
```

基于原因的告警在什么都没出错时触发，并且会错过您未预测到的故障。基于症状的告警在用户受到伤害时触发，无论原因如何。

您创建的每个告警的规则：

1. **它必须是可操作的。** 如果响应是“忽略它，它会自我修复”，则删除该告警。
2. **它链接到一个运行手册**——即使只有三行：是什么意思，第一个要运行的查询，升级路径。
3. **它有阈值和持续时间**，由 SLO 或历史数据证明，而不是猜测。
4. 只使用两种严重性：**页面**（面向用户，立即行动）和**工单**（退化，本周采取行动）。第三级变成噪音，训练人们忽略一切。

#### 编写运行手册

上述规则 2 要求每个告警链接到运行手册。运行手册的工作是回答三个问题，而无需读者思考：正在发生什么，首先检查什么，如果那不解决，该联系谁。存储在 `docs/runbooks/` 中，命名为告警。

**最小可行运行手册（三行）：**

```markdown
# 运行手册：/api/tasks 高错误率
**含义：** 数据库连接池可能已耗尽，或者是一个糟糕的部署。
**首先检查：** `SELECT count(*) FROM pg_stat_activity WHERE backend_type = 'client backend';`
  — 如果计数 > 池限制，请查看步骤 2。（将您的数据库的等效内容替换进去。）
**升级到：** #db-oncall 或工程值班轮换。
```

**何时扩展到三行之外：** 仅当第一个检查本身不足以决定时才添加步骤。一个涵盖三个最常见原因的五步运行手册比一个涵盖每个边缘案例并被快速浏览的二十步文档更好。

**保持运行手册最新。** 作为关闭其被使用的每个事件的一部分更新运行手册——一个过时的运行手册会建立虚假的信心。如果一步是错误的或缺失的，请在标记事件解决之前修复它。

### 7. 验证遥测本身

指标化是代码；它可能是错误的。在调用工作完成之前，触发路径并查看实际输出：

- 在暂存环境中强制错误 → 通过 `requestId` 在日志中找到它，确认字段是结构化的（不是 `[object Object]`）
- 发送测试流量 → 确认指标序列出现，带有预期的标签和合理的值
- 在跟踪 UI 中跟随一个请求跨服务 → 没有损坏的跟踪
- 每次触发新告警一次（暂时降低阈值）→ 确认它到达正确的频道，并且运行手册链接有效
- 在暂存中诱导故障 → 仅通过遥测定位，无需阅读源代码

## 常见借口

| 借口 | 现实 |
|---|---|
| “我会稍后添加日志” | “稍后”变成“在第一个事件之后”，这是发现您失明时最昂贵的时刻。在构建时进行指标化。 |
| “更多日志 = 更多可观察性” | 非结构化噪音使事件变慢，而不是更快。三个可查询的事件比三百行散文更好。 |
| “console.log 现在足够了” | 非结构化输出无法过滤、关联或告警。结构化日志器一次花费五分钟额外时间。 |
| “我们可以只是在出现问题时查看仪表板” | 没有定义问题的仪表板显示您所有的一切，除了答案。从值班工程师的问题开始。 |
| “告警所有重要的事情，我们稍后调整” | 噪音的传呼机训练人们忽略它。调整永远不会发生；错过的真实页面会。 |
| “用户 ID 作为指标标签使调试更容易” | 它也使您的指标后端崩溃。高基数查找属于日志和跟踪。 |
| “跟踪对我们的两个服务来说太夸张了” | 两个服务已经意味着跨服务延迟问题日志无法回答。自动指标化使成本微不足道。 |

## 信号灯

- 一个包含重试、队列或外部调用的功能 PR，但没有新的遥测数据
- 通过字符串插值而不是结构化字段构建的日志行
- 没有关联/请求 ID——每行日志都是一个孤儿
- 一个日志流由调度器、webhook 和手动运行提供，但没有字段命名哪个产生了该行
- 指标标记有用户 ID、原始 URL 或错误消息文本（基数炸弹）
- 延迟跟踪为平均值，没有百分位数
- 每天触发并得到确认而没有采取行动的告警
- 告警在原因（CPU、内存）上触发人类传呼，而用户面错误率未监控
- 日志中出现的秘密、令牌或完整请求正文
- “在我的机器上可以工作”作为生产功能健康的唯一证据

## 验证

在指标化一个功能后，确认：

- [ ] 此功能的值班工程师问题被记录下来，并且每个信号都映射到一个
- [ ] 所有日志输出都是结构化的（JSON），每个行都有一个稳定的日志名和关联 ID
- [ ] 每个由多个入口点写入的日志接收器都携带一个入口点字段，在运行开始处设置，并以与关联 ID 相同的方式传播，而不是下游推断
- [ ] 任何日志行中都没有秘密、令牌或未脱敏的 PII（抽查实际输出）
- [ ] 每个新端点和每个外部依赖项都存在 RED 指标，带有有界标签集
- [ ] 延迟是一个直方图；p95/p99 是可查询的
- [ ] 可以在跟踪 UI 中端到端跟随一个请求，没有损坏的跟踪
- [ ] 每个新告警都是基于症状的，有运行手册链接，并且已经测试触发一次
- [ ] 在暂存中诱导的故障仅通过遥测定位，无需阅读源代码
