# 约束驱动开发

## 概述

这个技能包中的其他技能描述了什么是好的标准。`code-review-and-quality` 给你五个维度。`test-driven-development` 给你一个循环。`security-and-hardening` 给你一个威胁列表。所有这些都存在于代理可以阅读但可能不会遵循的文本中，并且都不会在会话结束时存活。

这个技能产生的是不同的东西：一个书面记录，记录了**这个项目**的标准，用数字表示，可以存活于对话之外，并且可以机械地检查。

原因很重要。当你编写代码时，阅读它告诉你它是否足够好。代理在一个下午写的东西比你一周内要读的多得多，所以判断从你的头脑中移出，并进入循环运行的检查中。这些检查需要存在，它们需要你实际选择的数字，并且它们需要在工作的附近触发，以便代理可以自行修正其输出。

规范驱动开发说要构建什么。测试驱动开发证明它是否有效。约束驱动开发在任何人就“是否足够好可以发布”进行拉取请求争论之前，定义了“足够好可以发布”的含义。

## 何时使用

在以下情况下应用此技能：

- 开始一个项目或一个重要功能，并且没有写下的质量标准
- 用户要求“设置约束”、“添加质量门”、“定义我们的标准”或“阻止代理发布垃圾”
- 代理正在产生无人逐行阅读的卷
- CI 有检查，但没有人可以说哪些检查阻止合并，哪些只是装饰
- 覆盖率、性能或可访问性数字在每个 PR 上都有争议，而不是一次性决定
- 你即将运行 `/build auto` 或任何自主循环，并且唯一介于它和主分支之间的测试套件也是代理编写的

**不使用时：**

- 项目已经有一个 `CONSTRAINTS.md`，并且用户没有更改它——阅读它并遵循它
- 一次性脚本、尖峰、可丢弃的原型
- 用户现在需要代码审查 (`code-review-and-quality`) 或构建 CI 管道 (`ci-cd-and-automation`)
- 预产品市场契合度的代码，预期寿命为两周——下限仍然值得，其余部分则不值得

## 加载约束

面试需要一个活跃的用户。**不要在非交互式环境中运行它**（CI、`/loop`、自主运行）。如果约束缺失，并且你处于这些环境中，请应用下限，并记录你已这样做，然后将其余部分标记为供人类处理。

## 流程

### 第 1 步：在提问之前先检测

永远不要问你能阅读的东西。在第一个问题之前，收集：

| 内容 | 查找位置 |
|------|---------------|
| 语言和堆栈 | `package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml` |
| 测试运行器 | 开发依赖项、`test` 脚本、现有的测试文件 |
| 现有的代码检查器 | `eslint.config.*`、`biome.json`、`.ruff.toml` |
| 当天的覆盖率 | `coverage/` 输出，或者运行一次测试套件 |
| CI | `.github/workflows/`、`.gitlab-ci.yml` |
| 代理套件 | `.claude/`、`.codex/`、`AGENTS.md` |

用两行报告你发现的内容，然后只问剩下的。

### 第 2 步：四个问题，每个问题都有一个默认值

遵循 `interview-me` 的一问一答纪律，但有一个变化：这里每个问题都有一个默认值，所以“我不知道”是一个完整的答案，仍然可以生成一个工作的配置。

```
Q1: 除了下限之外，你想强制执行以下哪项？
    (a) 新代码的测试覆盖率
    (b) 安全扫描
    (c) 性能预算
    (d) 可访问性
    (e) 架构边界
GUESS: (a) 和 (b) —— 你已经有一个测试运行器，并且你正在处理用户输入。
DEFAULT if unsure: (a) 和 (b).
说明每个选择的开销： (c) 和 (d) 需要一个运行中的 URL，(e) 需要一个编写的规则文件。
```

```
Q2: 当代理在执行任务时检查失败，应该阻止还是警告？
GUESS: 阻止。你正在无人看管的代理上运行，一个无人阅读的警告就是一个警告。
DEFAULT if unsure: 在下限上阻止，在其余部分上警告，为期两周。
```

```
Q3: 你有目标数字，还是应该测量你今天的现状并保持该水平？
GUESS: 测量。大多数团队没有数字，虚构的数字会被忽略。
DEFAULT if unsure: 测量并保持。见下文“Ratchets”。
```

```
Q4: 代理在交回工作之前，你能忍受的最慢检查是什么？
GUESS: 大约 90 秒。更长的话你会停止运行它。
DEFAULT if unsure: 任务结束时 90 秒，CI 中无限。
```

在四个问题上停止。一个包含十二个问题的摄入会产生一个用户无法理解的配置，并且用户会后悔开始。

### 第 3 步：编写 `CONSTRAINTS.md`

在仓库根目录下创建一个文件。任何套件上的代理都可以读取它，并且对它的更改会在它所属的审查中显示。

```markdown
# 约束

上次审查：2026-08-08 由 @addy

## 下限（始终强制执行，无需设置）

- 没有新的抑制评论：`@ts-ignore`、`eslint-disable`、`# noqa`、`# type: ignore`
- 没有未实现的存根：`throw new Error("Not implemented")`、空的 `catch {}`
- 没有跳过或删除的测试，没有提交信息中的原因
- 源代码中没有密钥
- 这个文件不会减弱以使更改通过

## 带数字的强制执行

| 维度 | 规则 | 由谁检查 | 在何时运行 |
|-----------|------|-----------|---------|
| 类型 | 零类型错误 | `tsc --noEmit` | 每次编辑 |
| 代码检查器 | 我们配置中的零错误 | `biome check` | 每次编辑 |
| 密钥 | 源代码中没有密钥 | `gitleaks detect --redact` | 每次编辑 |
| 覆盖率 | 更改的行 ≥ 80% 被覆盖 | `vitest run --coverage` + git diff | 任务结束、CI |
| 安全：代码 | 没有高发现 | `semgrep scan --config p/default` | CI |
| 安全：依赖项 | 高或以上没有任何东西 | `osv-scanner scan source -r .` | CI |
| 可访问性 | 零关键或严重 | `axe $PREVIEW_URL --tags wcag2a,wcag2aa,wcag21aa` | 预览部署 |
| 性能 | LCP ≤ 2500ms，CLS ≤ 0.1 | `lighthouse $PREVIEW_URL --output=json` | 预览部署 |

每一行都命名了产生裁决的命令。一个带有数字但没有本列命令的维度是一个愿望，而不是一个约束。

## 测量，尚未强制执行

| 指标 | 今天 | 方向 |
|-------|-------|-----------|
| 项目覆盖率 | 62.4% | 必须不下降 |
| 打包大小（主） | 184 kB | 必须不增长 |

## 例外

| ID | 规则 | 路径 | 原因 | 所有者 | 到期日 |
|----|------|------|--------|-------|---------|
| W1 | `no-explicit-any` | `src/legacy/**` | 在 ENG-441 中跟踪的重写 | @addy | 2026-11-01 |

然后向 `AGENTS.md` 和 `CLAUDE.md` 添加一行：`在编写代码之前读取 `CONSTRAINTS.md`。不要减弱它以使更改通过。`

### 第 4 步：安装每个维度所需的内容

选择一个维度意味着安装一些东西。不要让用户有一个数字但没有机制，并且不要在存在事实上的检查器时发明自己的检查器——这些工具被列出，因为它们的规则格式和阈值是生态系统中其他一切的目标，所以团队的现有配置仍然可以正常工作。

| 维度 | 工具 | 安装 | 运行 | 在...上设置门 |
|------|------|---------|-----|---------|
| 类型（TS） | tsc | 已经存在 | `tsc --noEmit` | 任何错误 |
| 类型（Python） | mypy | `pip install mypy` | `mypy .` | 任何错误 |
| 代码检查器 | 你现有的配置 | 已经存在 | `eslint .` / `biome check` / `ruff check` | 任何错误 |
| 覆盖率（JS） | 你现有的测试运行器 | 已经存在 | `vitest run --coverage`（或 `jest --coverage`） | 更改的行覆盖率 |
| 覆盖率（Python） | pytest-cov | `pip install pytest-cov` | `pytest --cov --cov-report=lcov` | 相同 |
| 安全：代码 | Semgrep | `pipx install semgrep` | `semgrep scan --config p/default --config p/owasp-top-ten` | 任何高发现 |
| 安全：密钥 | gitleaks | `brew install gitleaks` | `gitleaks detect --redact --no-banner` | 任何发现 |
| 安全：依赖项 | osv-scanner | `brew install osv-scanner` | `osv-scanner scan source -r .` | 高或以上 |
| 性能：页面 | Lighthouse | `npm i -D lighthouse` | `lighthouse $URL --output=json --quiet` | LCP、CLS、性能分数 |
| 性能：打包 | size-limit | `npm i -D size-limit` | `size-limit --json` | 每个条目的字节预算 |
| 可访问性 | axe-core | `npm i -D @axe-core/cli` | `axe $URL --tags wcag2a,wcag2aa,wcag21aa` | 零关键或严重 |
| 架构 | dependency-cruiser | `npm i -D dependency-cruiser` | `depcruise --validate src` | 任何违规 |
| 断言质量 | Stryker | `npm i -D @stryker-mutator/core` | `stryker run --mutate <更改的文件>` | 变异分数 |

如果你跳过这五件事，你会受到惩罚：

1. **`--redact` 在 gitleaks 不是可选的。** 没有它，匹配的密钥会出现在代理的文本记录中，这就是泄露的密钥如何出现在日志、摘要或提交信息中的。报告规则和位置，而不是值。
2. **Lighthouse 和 axe 需要一个 URL。** 它们只针对运行中的应用程序工作，所以它们属于在预览部署或你首先启动的本地服务器上针对运行时阶段的运行。如果项目没有要访问的 URL——一个 CLI、一个库、一个桌面应用程序——就说出来，并放弃这个维度，而不是发明一个无法运行的检查。
3. **将昂贵的检查范围限制为差异。** 在整个仓库上运行 `stryker run --mutate` 要花几个小时，并且会被关闭；在更改的文件上运行它不到一分钟。Semgrep 也是如此，它需要一个路径列表。
4. **覆盖率不需要第二次测试运行。** 读取你的套件已经写入的 lcov，并将其与 `git diff` 相交。两次运行套件以获得一个数字是让人们对这个最快的最快方式产生厌恶。
5. **Semgrep 的注册表规则可以免费运行；在重新分发它们之前检查许可证。** `opengrep` 是一个具有相同规则格式和 JSON 输出的即插即用分支，如果这对你的法律团队很重要。

将每个一个添加到项目的自己的脚本中，以便在没有代理的情况下可以重现：

```json
{
  "scripts": {
    "check:fast": "tsc --noEmit && eslint . && gitleaks detect --redact --no-banner",
    "check:task": "npm run check:fast && vitest run --coverage",
    "check:full": "npm run check:task && semgrep scan --config p/default && osv-scanner scan source -r ."
  }
}
```

这个映射比工具更重要。`check:fast` 是在编辑之后运行的，`check:task` 是当代理认为它已完成时运行的，`check:full` 是在 CI 中运行的。

命令现在存在于两个地方——`CONSTRAINTS.md` 中的 `Checked by` 列和这些脚本。`CONSTRAINTS.md` 是权威来源：它附带每个命令的理由，并且它出现在审查中。脚本只是方便的包装器，必须镜像它，而不是第二个真相来源；如果它们漂移，文件会获胜。

### 第 5 步：将其连接到生命周期

最大的错误是在每个地方运行所有东西。一个阻止代理的检查会被关闭，而一个被关闭的门比没有门更糟，因为标准看起来仍然存在。

| 阶段 | 命令 | 运行什么 | 预算 |
|-------|---------|-----------|--------|
| 构建 | `/build` | 类型、代码检查器、密钥、下限 | 5 秒以下，仅更改的文件 |
| 验证 | `/test` | 相关测试、更改行的覆盖率 | 90 秒以下 |
| 审查 | `/review` | 一切，以及下限下的守门人 | 分钟 |
| 发布 | `/ship` | 方向检查，没有回归 | CI |

两个规则使这变得可以忍受：

1. **范围限制为差异。** 检查这个更改触及的行，而不是整个仓库。更改行的覆盖率是一个代理可以移动的数字；项目覆盖率是一个它继承的数字。
2. **成本决定位置。** 任何超过几秒钟的东西都会离开编辑循环。在整个仓库上进行变异测试要花几个小时；在更改的文件上进行它不到一分钟，这是人们运行检查和人们不运行检查之间的区别。

### 第 6 步：保护标准本身

有人会指出，如果代理编写代码和检查，检查就证明不了任何东西。一半正确，值得围绕它进行工程设计。

代理不会设计巧妙的漏洞。它们遇到一个红色的检查，并走最便宜的路到绿色。在审查时，注意 diff 中的这五个动作：

1. **阈值移动了。** 预算降低，严重性降低，从快速阶段移除了检查。将 `CONSTRAINTS.md` 与其在分支点的状态进行比较。
2. **一个测试变得容易了。** 添加了 `.skip`，删除了测试文件，从保持的测试中移除了断言。
3. **一个检查器被沉默了。** 新的 `@ts-ignore` 或 `eslint-disable`。四个抑制值得特别关注，因为它们关闭了你依赖的检查：`istanbul ignore` 从覆盖率中丢弃代码而不是测试它，`Stryker disable` 隐藏了一个幸存的变异，`nosemgrep` 和 `gitleaks:allow` 为安全发现做了同样的事情。
4. **工作未完成。** 一个抛出异常的存根，一个空的 `catch` 将失败转换为沉默，一个 `TODO` 站在实现应该的位置。
5. **出现了一个例外。** `Exceptions` 表中的新行，没有人讨论过。

所有这些都不需要超出 `git diff` 的工具。收紧标准应该是无声的；放宽标准应该是响亮的。

与带数字的维度不同，下限没有自己的事实上的工具，所以被要求执行下限的代理倾向于从头开始编写检查器，两个代理会写两个不同的检查器。这个技能随附的 [references/floor-guard.md](references/floor-guard.md)（差异范围、退出 `0`/`1`/`2`、每个生态系统可适应的模式）是这五个检查的参考实现。适应它，而不是重新发明它，原因与每个维度命名事实上的工具相同：以便机制在运行和堆栈之间保持一致。

**并非所有检查都是同样循环的。** 通过一个问题对它们进行排序：代理能否通过编写不工作的代码使这个通过？

- **外部** — axe-core 编码 WCAG，`osv-scanner` 读取漏洞数据库，Lighthouse 测量一个真实的浏览器。代理不能与这些争论。
- **项目** — 你的代码检查器，你的层边界。人类拥有文件。
- **套件** — 你自己的测试。最有用，并且是唯一真正循环的。

一个完全由第三种类型组成的标准不如包含外部意见的标准有价值。检查至少有一个外部约束存在。

### 第 7 步：Ratchets，当你没有数字时

在一个 62% 覆盖率的代码库上设置 80% 覆盖率，你会得到一个永远红色的构建，然后是一个学会忽略红色构建的团队。

替代方案要求没有决定：记录你现在的位置，然后拒绝变得更差。将它放在“测量，尚未强制执行”表中，并记录今天的数字和方向。每个检查都与记录的值进行比较，而不是一个愿望。当数字提高时，更新它；当它下降时，那就是发现。

这也回答了一个关于培训的合理反对意见。模型因为通过测试而受到奖励，你可以用几秒钟来评估它们。架构陈旧会在几个月后出现，永远不会达到权重。Ratchet 是缺失的惩罚，写在工作可以看到的构建中。

## 合理的默认值

当用户没有意见时，使用这些。它们被选择为大多数代码库在第一天就能达到。

| 约束 | 默认 | 为什么是这个数字 |
|------------|---------|-----------------|
| 更改行的覆盖率 | ≥ 80% | 足够高以强制测试，足够低以允许配置行 |
| 项目覆盖率 | 今天的值，必须不下降 | 没有必要采用 |
| 变异分数（如果使用） | 开始时 ≥ 60% | 一个从未变异过的套件的典型值；80% 是成熟的 |
| 依赖项漏洞 | 高或以上没有任何东西 | 低于那个大多是噪音 |
| LCP | ≤ 2500 ms | 核心网络生命体征“良好”阈值 |
| CLS | ≤ 0.1 | 相同 |
| 可访问性 | 零关键或严重的 axe 违规 | 中等和轻微通常是可商榷的 |
| 例外有效期 | 90 天 | 足够计划修复，足够短以记住 |
| Ratchet 容忍度 | 0.5% | 当一个无关的文件移动数字时吸收漂移 |

一起说明数字和原因。没有理由的阈值会被下一个遇到它的人删除。

## 升级路径

约束在三个牙齿级别上起作用。从第一个开始。

1. **仅书面。** `CONSTRAINTS.md` 存在，代理会读取它。不花钱，捕获诚实的错误，依赖于代理的遵守。
2. **脚本化。** 一个运行快速检查的 `npm run check`（或 `make check`），连接到你的代理的编辑后挂钩和你的 CI。确定性，没有新的依赖项。
3. **工具支持。** 一个专用的运行器，处理差异范围、预算、Ratchets 和守门人检查。当配置超出 shell 脚本时使用。守门人参考在 [references/floor-guard.md](references/floor-guard.md) 中是这半个技能的起点。

大多数项目应该停留在 2。当维护的检查运行 shell 超过大约三十行时，移动到 3。

**第一次运行可以是仅下限。** 守门人检查是差异范围的，不需要安装，所以你可以在第一天就执行下限，并随着安装每个工具，而不是在第一个提交受保护之前建立每个检查，而添加带数字的维度。可以安装机器范围的密钥（gitleaks、osv-scanner）也可以运行 CI 仅有的，如果你宁愿保持笔记本电脑干净；声明每个维度在 `Runs at` 列中运行的位置。

## 常见的合理化

| 推诿 | 真实情况 |
|--------|---------|
| “一旦代码稳定下来，我们就会添加约束” | 代码会在允许它在移动时出现的东西周围稳定下来 |
| “测试就是约束” | 你编写的测试证明你同意自己；它们对新的代码覆盖率、依赖项风险或打包增长什么也说不出来 |
| “我们无法达到 80% 覆盖率” | 那么就不要设置 80%。设置今天的数字并保持它 |
| “这会减慢代理的速度” | 只有当你把慢检查放在快速循环中时才会减慢代理。这是一个放置错误，而不是反对约束的论点 |
| “我会记住我们的标准” | 代理不会，并且它正在编写大部分代码 |
| “约束会阻止我们发布” | 一个有所有者和国期的例外会为你解冻。删除约束将永远解冻所有人 |

## 信号旗

如果你注意到以下情况，请停止并重新考虑：

- 面试运行了四个问题，或者产生了一个用户无法解释的配置
- 设置了一个今天代码库就失败的预算，没有计划达到它
- 在 `CONSTRAINTS.md` 中写入了一个带有数字但没有工具的维度
- 手工编写了一个检查器，而存在一个事实上的检查器，因此忽略了团队的现有配置
- 每个约束都由项目自己的测试套件检查，没有外部意见
- `CONSTRAINTS.md` 与失败的特性提交在同一提交中更改
- 例外没有所有者，或者到期日超过一年
- 代理建议放宽阈值而不是修复代码
- 慢检查落入了编辑循环，并且有人开始传递 `--no-verify`
- 自从编写以来，没有人打开过 `CONSTRAINTS.md`

## 验证

当技能被正确应用时：

- [ ] `CONSTRAINTS.md` 存在，并且其中每个数字都有一个说明理由
- [ ] 下限被强制执行，并且在当前代码库上无需更改即可通过
- [ ] 用户选择的每个维度都安装了工具，并且今天有一个可以运行的命令
- [ ] 每个约束都说明它在哪里运行，并且快速阶段保持在几秒钟以内
- [ ] 至少有一个约束是外部的（不是由这个项目自己的测试判断）
- [ ] 测量指标记录今天的值和方向
- [ ] 例外有一个所有者和一个到期日
- [ ] `AGENTS.md` 或 `CLAUDE.md` 指向该文件
- [ ] 在当前分支上进行试验运行不会产生用户不同意失败的任何错误
