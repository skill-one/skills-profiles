# 安全与加固

## 概述

面向 Web 应用的安全优先开发实践。将所有外部输入视为敌意，将所有秘密视为神圣，将所有授权检查视为强制执行。安全不是一个阶段——它是对接触用户数据、身份验证或外部系统的每一行代码的限制。

## 使用场景

- 构建任何接受用户输入的应用
- 实现身份验证或授权
- 存储或传输敏感数据
- 集成外部 API 或服务
- 添加文件上传、Webhook 或回调
- 处理支付或个人身份信息 (PII) 数据

## 流程：威胁模型优先

没有威胁模型的控制是猜测。在加固之前，花五分钟像攻击者一样思考：

1. **绘制信任边界**。未受信任的数据在哪里进入您的系统？HTTP 请求、表单字段、文件上传、Webhook、第三方 API、消息队列，以及 **LLM 输出**——加上看起来内部因为操作系统将它们交给您的本地值：另一个进程的命令行或环境、共享卷上的文件名、作业负载中的路径。信任遵循谁 *编写* 了值的规则，而不是哪个通道传递了它。每个边界都是攻击面。
2. **命名资产**。什么值得窃取或破坏？凭证、PII、支付数据、管理员操作、资金流动。
3. **对每个边界运行 STRIDE**——这是一个快速镜头，不是一种仪式：

| 威胁 | 提问 | 典型缓解措施 |
|---|---|---|
| **S**poofing | 有人能冒充用户/服务吗？ | 身份验证、签名验证 |
| **T**ampering | 数据能在传输或静止时被篡改吗？ | 完整性检查、参数化查询、HTTPS |
| **R**epudiation | 后来能否认操作吗？ | 安全事件审计日志 |
| **I**nformation disclosure | 数据会泄露吗？ | 加密、字段白名单、通用错误 |
| **D**enial of service | 能被压垮吗？ | 速率限制、输入大小限制、超时 |
| **E**levation of privilege | 用户能获得他们不应有的权限吗？ | 授权检查、最小权限 |

4. **在使用案例旁边编写滥用案例**。对于每个功能，询问“我会如何滥用这个？”——然后将其作为您的第一个测试。

如果您无法命名一个功能的信任边界，您就没有准备好保护它。这是 OWASP **A04：不安全设计**——大多数漏洞始于设计，而不是代码。

## 三层边界系统

### 总是做（无例外）

- **在系统边界验证所有外部输入**（API 路由、表单处理程序）
- **参数化所有数据库查询**——永远不要将用户输入串联到 SQL
- **编码输出**以防止跨站脚本攻击 (XSS)（使用框架自动转义，不要绕过它）
- **对所有外部通信使用 HTTPS**
- **使用 bcrypt/scrypt/argon2 哈希密码**（永远不要存储明文）
- **设置安全头**（CSP、HSTS、X-Frame-Options、X-Content-Type-Options）
- **使用 httpOnly、secure、sameSite cookie** 进行会话
- **在每次发布前，在提交的锁文件上运行检测到的包管理器的原生审计**

### 需要先询问（需要人工批准）

- 添加新的身份验证流程或更改身份验证逻辑
- 存储新的敏感数据类别（PII、支付信息）
- 添加新的外部服务集成
- 更改 CORS 配置
- 添加文件上传处理程序
- 修改速率限制或节流
- 授予提升权限或角色

### 永远不要做

- **永远不要将秘密提交到版本控制**（API 密钥、密码、令牌）
- **永远不要记录敏感数据**（密码、令牌、完整的信用卡号）
- **永远不要将客户端验证视为安全边界**
- **永远不要为了方便而禁用安全头**
- **永远不要使用 `eval()` 或 `innerHTML`** 与用户提供的数據
- **永远不要将会话存储在客户端可访问的存储**（用于身份验证令牌的 localStorage）
- **永远不要向用户暴露堆栈跟踪**或内部错误详细信息

## 加固控制

以下规则是工作流程；每个具体实现都存在于 [references/hardening-patterns.md](references/hardening-patterns.md) 中。当您到达该代码时，打开您需要的部分，而不是之前。

### 注入、XSS 和访问控制

- 参数化每个查询。永远不要从输入字符串构建 SQL、NoSQL 或 shell 命令。
- 通过框架的自动转义编码输出。如果原始 HTML 不可避免，请先用允许列表清理器进行清理。
- 在每个请求上检查 **授权**，而不仅仅是身份验证：经过身份验证的用户必须拥有或被允许在特定资源上（A01、IDOR）。

模式：[注入](references/hardening-patterns.md#injection)、[XSS](references/hardening-patterns.md#cross-site-scripting-xss)、[访问控制](references/hardening-patterns.md#broken-access-control)。

### 身份验证和会话

- 使用 bcrypt（≥12 轮）、scrypt 或 argon2 哈希密码。会话密钥来自环境，而不是来自代码。
- 会话 cookie 是 `httpOnly`、`secure`，并且 `sameSite: 'lax'` 或 `'strict'`（CSRF 防御；`'none'` 在跨站请求中发送 cookie），具有有界的 `maxAge`。

模式：[身份验证](references/hardening-patterns.md#broken-authentication)。

### 头部、CORS 和响应

- 每个响应都有安全头（helmet 或框架等效项）；CSP 从 `default-src 'self'` 开始，并收紧，而不是放宽。
- CORS 限制为从配置中明确的原点列表。永远不要带凭证的 `*`。
- 在任何响应之前剥离敏感字段（`passwordHash`、重置令牌）。错误正文是通用的；内部信息仅发送到服务器日志。

模式：[配置错误](references/hardening-patterns.md#security-misconfiguration)、[敏感数据暴露](references/hardening-patterns.md#sensitive-data-exposure)。

### 输入验证和上传

- 在边界处使用模式验证：允许的形状、长度、枚举、格式。使用 422 和结构化详细信息拒绝；下游代码仅使用解析的、类型的值。
- 上传：允许列出 MIME 类型，限制大小，在重要情况下验证内容（魔术字节）。扩展名证明不了什么。

模式：[边界处的模式验证](references/hardening-patterns.md#schema-validation-at-boundaries)、[文件上传](references/hardening-patterns.md#file-upload-safety)。

### 服务器端获取（SSRF）

任何用户影响的 URL——Webhook、从 URL 导入、图像代理、链接预览——都可以指向内部服务。允许列出方案和主机，解析 **所有** DNS 记录并拒绝任何私有或保留地址（回环、链路本地 `169.254.169.254`、私有、唯一本地、IPv4 和 IPv6），并禁止重定向。该检查仍然有 DNS 重绑定 TOCTOU 间隙：对于高风险表面，请固定解析的 IP 或在前面放置一个过滤代理。

模式：[服务器端请求伪造 (SSRF)](references/hardening-patterns.md#server-side-request-forgery-ssrf)。

### 基于派生路径的破坏性操作

删除、移动或覆盖仅与命名目标的值一样安全，并且信任遵循谁 *编写* 了该值，而不是哪个通道传递了它：另一个进程的命令行与表单字段一样受攻击者控制。形状检查证明良好格式，而不是授权。在调用之前，要求所有三个：解析的目标（符号链接已解析）位于 **允许的根** 下；它至少在根下 **至少一个级别**；并且它携带 **在操作之前读取的所有权证据**。在拒绝时，记录拒绝的目标并停止；永远不要回退到更广泛的默认路径。

为什么检查比它读的弱（标记自我证明、检查/使用竞争）：[破坏性路径](references/hardening-patterns.md#destructive-operations-on-derived-paths)。工作代码：`../../references/security-checklist.md`。

### 速率限制

一般限制 API，严格限制身份验证端点（大约每 15 分钟 10 次尝试）。一旦有多个进程服务流量，内存计数器会无声地变成 `max × 实例`，或在服务器less 上永远不会触发：使用共享存储支持限制器。

模式：[速率限制](references/hardening-patterns.md#rate-limiting)。

### 秘密

秘密来自环境。`.env.example` 与占位符一起提交；真实的 `.env*` 文件和密钥材料被 git 忽略；在提交之前搜索暂存的差异。**一旦秘密到达远程位置，它就会在着陆时被泄露：首先旋转它，然后清除历史记录。**

模式：[秘密管理](references/hardening-patterns.md#secrets-management)。

### 依赖项和供应链

1. **找到安装边界和经理**。使用拥有锁文件的工件根，或者仅在它不在该工作区之外时使用独立的嵌套项目。核实 `packageManager`（当存在时）、锁文件和 CI；在出现分歧或竞争锁文件时停止。固定经理版本。
2. **在第一次执行之前阻止依赖项脚本**。使用禁用脚本或记录的关闭策略启动，检查挂起的脚本源，仅批准最小值，提交策略，然后用干净的冻结/不可变安装进行验证。永远不要一揽子批准。
3. **在每次发布前，对提交的锁文件运行原生审计**。通过 **可达性**（运行时、构建、测试、部署路径）和修复可用性对关键/高进行分类。永远不要自动应用强制修复（`npm audit fix --force` 或等效），因为强制修复可能会跨越声明的依赖项范围；预览、阅读变更日志、测试每个升级。用原因和审查日期记录每个推迟。
4. **审计仅匹配已知公告**。它们不会捕获新恶意或拼写劫持的包（`cross-env` vs `crossenv`）。一起审查新依赖项、锁文件差异和脚本策略更改：所有权、维护、发布年龄、来源、传递图。在支持的地方验证注册表签名（`npm audit signatures`、`pnpm audit signatures`）并将其缺失视为调查信号，而不是自动证明妥协（A06、LLM03）。

分类决策树：[依赖项审计分类](references/hardening-patterns.md#dependency-audit-triage)。经理矩阵和安装脚本门：`../../references/security-checklist.md`。

### 个人数据和隐私

加固询问“攻击者能读取它吗？”隐私询问“我们应该保留它吗？保留多久？”要保护、泄露和合规的最便宜数据是你从未收集的数据；将个人数据视为要最小化的负债。

- **在添加时将字段分类为**（非个人、PII、敏感），并相应处理每个类别。您无法保护或尊重您无法找到的数据的删除请求。
- **仅针对声明目的收集**。“以后可能有用”是潜伏的泄露范围，不是目的。将 PII 从遥测中排除（`observability-and-instrumentation` 技能从运维方面做出了相同的观点）。
- **事先设置保留期，然后实际删除**。每个个人数据存储都需要一个 TTL 和一个工作的删除路径，包括备份、缓存、搜索索引和 analytics 复本。
- **支持您管辖区要求的数据主体权利**（GDPR、CCPA 和同类）：导出、更正、删除。设计模式，以便用户的数据是可查找和可擦除的，而不是不可逆转地涂抹在系统中。
- **同意门收集和第三方共享，并且是可审计的**。将 PII 发送到分析、广告或 LLM 供应商是共享；供应商需要一个数据处理协议。将区域设置为可配置策略，而不是硬编码假设。

分类表：[数据分类](references/hardening-patterns.md#data-classification)。隐私事件启动泄露通知时钟；使用 `debugging-and-error-recovery` 技能运行事后分析。

### AI / LLM 功能

调用 LLM——聊天机器人、摘要器、代理、RAG——添加了新的攻击面；将其映射到 [OWASP LLM 应用程序 Top 10 (2025)](https://genai.owasp.org/llm-top-10/)：

- **模型输出是不可信的输入**（LLM05）。永远不会进入 `eval`、SQL、shell、`innerHTML` 或文件路径；防御性解析，根据模式验证，然后编码。
- **提示可以被劫持**（LLM01）。未受信任的文本在上下文中——用户消息、获取的页面、PDF——可以携带指令。系统提示不是安全边界；在代码中执行权限。
- **将秘密、其他租户的数据和完整系统提示保持在上下文窗口之外**（LLM02、LLM07）；范围工具权限，验证每个工具参数，并确认破坏性行动（LLM06）；限制 token、请求速率和递归深度（LLM10）；为每个租户分区 RAG 嵌入，并在索引之前验证文档（LLM08）。

模式：[LLM 输出处理](references/hardening-patterns.md#llm-output-handling)。

## 常见理由

| 理由 | 现实 |
|---|---|
| "这是一个内部工具，安全不重要" | 内部工具也会被攻破。攻击者针对最薄弱的环节。 |
| "我们会稍后添加安全" | 安全改造比构建它难 10 倍。现在添加它。 |
| "没有人会尝试利用这个" | 自动扫描器会发现它。安全靠隐藏不是安全。 |
| "框架处理安全" | 框架提供工具，而不是保证。您仍然需要正确使用它们。 |
| "只是一个原型" | 原型会变成生产。从第一天开始培养安全习惯。 |
| "威胁模型在这里过于复杂" | 五分钟的“我会如何攻击这个？”可以防止后来无法通过控制修补的设计缺陷。 |
| "只是 LLM 输出，只是文本" | 这“文本”可以是 SQL 语句、脚本标签或 shell 命令。将其视为任何未受信任的输入。 |
| "审计通过了，所以依赖项是安全的" | 审计匹配已知公告。它们不会检测到新恶意的包或使未审查的安装脚本安全。 |
| "现在收集，以后可能需要" | 您不持有的数据不会被泄露、传票或错误删除。“可能需要”是泄露范围，不是目的。 |
| "我们会手动处理删除请求" | 手动擦除会遗漏备份、缓存和 analytics 复本。如果模式无法找到用户的数据，您无法执行请求——设计它。 |
| "合规是法务部门的问题，不是我们" | 导出、删除、保留和同意是模式和代码。法务部门不能在您将 PII 污染到十个系统之后添加它们。 |

## 信号

- 用户输入直接传递到数据库查询、shell 命令或 HTML 渲染
- 删除、移动或覆盖的目标来自有效负载、配置值或另一个进程的命令行，仅通过路径的形状检查进行保护
- 秘密在源代码或提交历史中
- 没有身份验证或授权检查的 API 端点
- 缺少 CORS 配置或通配符（`*`）原点
- 身份验证端点没有速率限制，或内存限制器在多个实例前面
- 堆栈跟踪或内部错误暴露给用户
- 具有已知关键漏洞的依赖项、一个安装边界上的竞争锁文件、不可重现的安装或一揽子批准的脚本
- 用户提供的 URL 服务器获取没有允许列表（SSRF）
- LLM/模型输出传递到查询、DOM、shell 或 `eval`
- 秘密、PII 或完整系统提示放置在 LLM 上下文窗口内
- 没有声明目的、保留限制或删除路径收集的个人数据
- 将 PII 发送到没有同意或数据处理协议的分析/广告/LLM 供应商
- “删除我的账户”仅翻转一个标志，而个人数据仍然存在于存储和备份中

## 验证

在实现与安全相关的代码后：

- [ ] 原生审计没有未缓解的可达关键/高发现；CI 保留权威锁文件并阻止未审查的依赖项脚本
- [ ] 源代码或 git 历史中没有秘密
- [ ] 所有用户输入都在系统边界处验证
- [ ] 破坏性文件系统操作解析符号链接，然后验证允许的根、最小深度和所有权，然后运行
- [ ] 每个受保护端点都检查身份验证和授权
- [ ] 响应中存在安全头（使用浏览器开发者工具检查）
- [ ] 错误响应不暴露内部详细信息
- [ ] 身份验证端点有速率限制，当多个实例服务流量时，使用共享存储支持限制器
- [ ] 服务器端 URL 获取验证通过允许列表（无 SSRF）
- [ ] 如果存在 AI 功能，则验证和编码 LLM/模型输出
- [ ] 个人数据分类，最小化为声明目的，并具有保留限制
- [ ] 删除和导出请求端到端工作（包括备份、缓存和 analytics 复本）
