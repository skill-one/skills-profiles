# 运输与发布

## 概述

有信心地运输。目标不仅仅是部署——而是安全部署，部署时要有监控机制，准备好回滚计划，并清晰地了解成功标准是什么。每次发布都应该可逆、可观察、逐步进行。

## 何时使用

- 首次将功能部署到生产环境
- 向用户发布重大变更
- 迁移数据或基础设施
- 开启测试版或早期访问计划
- 任何带有风险的部署（所有部署）

## 发布前检查清单

### 代码质量

- [ ] 所有测试通过（单元测试、集成测试、端到端测试）
- [ ] 构建成功且无警告
- [ ] 代码风格检查和类型检查通过
- [ ] 代码已审查并获得批准
- [ ] 没有应在发布前解决的 TODO 注释
- [ ] 生产代码中没有 `console.log` 调试语句
- [ ] 错误处理涵盖了预期的失败模式

### 安全性

- [ ] 代码或版本控制中没有密钥
- [ ] 生态系统的依赖项审计（`npm audit`、`pip-audit`、`cargo audit`、...）显示没有严重或高漏洞
- [ ] 所有面向用户的端点都有输入验证
- [ ] 已实施身份验证和授权检查
- [ ] 已配置安全头（CSP、HSTS 等）
- [ ] 身份验证端点已配置速率限制
- [ ] CORS 配置为特定来源（非通配符）

### 性能

- [ ] 核心网络生命体征指标在“良好”阈值范围内
- [ ] 关键路径中没有 N+1 查询
- [ ] 图片已优化（压缩、响应式尺寸、懒加载）
- [ ] 打包大小在预算范围内
- [ ] 数据库查询具有适当的索引
- [ ] 已为静态资源和重复查询配置缓存

### 可访问性

- [ ] 所有交互元素都支持键盘导航
- [ ] 屏幕阅读器可以传达页面内容和结构
- [ ] 颜色对比度符合 WCAG 2.1 AA 标准（文本为 4.5:1）
- [ ] 模态和动态内容的焦点管理正确
- [ ] 错误消息具有描述性并关联到表单字段
- [ ] axe-core 或 Lighthouse 中没有可访问性警告

### 基础设施

- [ ] 生产环境中已设置环境变量
- [ ] 已应用数据库迁移（或准备应用）
- [ ] 已配置 DNS 和 SSL
- [ ] 已为静态资源配置 CDN
- [ ] 已配置日志记录和错误报告
- [ ] 存在健康检查端点并返回响应

### 文档

- [ ] README 已更新任何新的设置要求
- [ ] API 文档是最新的
- [ ] 已为任何架构决策编写 ADR
- [ ] 已更新版本日志
- [ ] 已更新面向用户的文档（如果适用）

## 功能标志策略

使用功能标志来将部署与发布解耦：

```typescript
// 功能标志检查
const flags = await getFeatureFlags(userId);

if (flags.taskSharing) {
  // 新功能：任务共享
  return <TaskSharingPanel task={task} />;
}

// 默认：现有行为
return null;
```

**功能标志生命周期：**

```
1. DEPLOY with flag OFF     → 代码已部署到生产环境但处于非活动状态
2. ENABLE for team/beta     → 在生产环境中进行内部测试
3. 逐步发布          → 5% → 25% → 50% → 100% 的用户
4. 每个阶段监控    → 观察错误率、性能、用户反馈
5. 清理             → 完全发布后删除标志和死代码路径
```

**规则：**
- 每个功能标志都有一个所有者和过期日期
- 在完全发布后的 2 周内清理标志
- 不要嵌套功能标志（会创建指数级组合）
- 在 CI 中测试标志的两种状态（开启和关闭）

## 分阶段发布

### 发布顺序

```
1. DEPLOY to staging
   └── 在 staging 环境中运行完整测试套件
   └── 对关键流程进行手动冒烟测试

2. DEPLOY to production (feature flag OFF)
   └── 验证部署成功（健康检查）
   └── 检查错误监控（无新错误）

3. ENABLE for team (flag ON for internal users)
   └── 团队在生产环境中使用该功能
   └── 24 小时监控窗口

4. CANARY 发布 (flag ON for 5% of users)
   └── 监控错误率、延迟、用户行为
   └── 比较指标：canary 与基线
   └── 24-48 小时监控窗口
   └── 只有当所有阈值都通过时才推进（见下表）

5. 逐步增加 (25% -> 50% -> 100%)
   └── 每个步骤都进行相同的监控
   └── 可以随时回滚到之前的百分比

6. 完全发布 (flag ON for all users)
   └── 监控 1 周
   └── 清理功能标志
```

### 发布决策阈值

使用这些阈值来决定在每个阶段是否推进、暂停或回滚：

| 指标 | 推进（绿色） | 暂停并调查（黄色） | 回滚（红色） |
|------|--------------|---------------------|--------------|
| 错误率 | 基线 10% 以内 | 基线 10-100% 以上 | 基线 2 倍以上 |
| P95 延迟 | 基线 20% 以内 | 基线 20-50% 以上 | 基线 50% 以上 |
| 客户端 JS 错误 | 无新错误类型 | 新错误占会话 <0.1% | 新错误占会话 >0.1% |
| 业务指标 | 中性或积极 | 下降 <5%（可能是噪音） | 下降 >5% |

### 何时回滚

如果以下情况立即回滚：
- 错误率增加超过基线 2 倍
- P95 延迟增加超过 50%
- 用户报告的问题激增
- 检测到数据完整性问题
- 发现安全漏洞

## 监控和可观察性

### 需要监控的内容

```
应用指标：
├── 错误率（总数和按端点）
├── 响应时间（p50、p95、p99）
├── 请求量
├── 活跃用户
└── 关键业务指标（转化率、参与度）

基础设施指标：
├── CPU 和内存利用率
├── 数据库连接池使用情况
├── 磁盘空间
├── 网络延迟
└── 队列深度（如果适用）

客户端指标：
├── 核心网络生命体征指标（LCP、INP、CLS）
├── JavaScript 错误
├── 从客户端角度看的 API 错误率
└── 页面加载时间
```

### 错误报告

```typescript
// 设置带报告的错误边界
class ErrorBoundary extends React.Component {
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    // 向错误跟踪服务报告
    reportError(error, {
      componentStack: info.componentStack,
      userId: getCurrentUser()?.id,
      page: window.location.pathname,
    });
  }

  render() {
    if (this.state.hasError) {
      return <ErrorFallback onRetry={() => this.setState({ hasError: false })} />;
    }
    return this.props.children;
  }
}

// 服务器端错误报告
app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  reportError(err, {
    method: req.method,
    url: req.url,
    userId: req.user?.id,
  });

  // 不要向用户暴露内部细节
  res.status(500).json({
    error: { code: 'INTERNAL_ERROR', message: 'Something went wrong' },
  });
});
```

### 发布后验证

发布后的第一个小时内：

```
1. 检查健康端点返回 200
2. 检查错误监控仪表板（无新错误类型）
3. 检查延迟仪表板（无回归）
4. 手动测试关键用户流程
5. 验证日志是否正在流动且可读
6. 确认回滚机制工作（如果可能进行干运行）
```

## 错误预算发布门禁

您服务的错误预算——SLO 允许失败的请求或时间的比例——决定了是否可以安全发布。将其用作目标门禁——而不是谈判：

```
剩余预算 > 20%  →  正常发布；密切监控
剩余预算 0–20%  →  仅限逐步发布；无高风险变更
预算耗尽        →  暂停功能工作；完全专注于可靠性
预算重置           →  恢复正常速度；加入恢复它的修复
```

在金丝雀发布期间的高消耗率（比基线速度更快地消耗预算）是上述发布决策阈值表中的**暂停**信号——将其视为错误率升高的情况。

## 回滚策略

每次部署在发生之前都需要一个回滚计划：

```markdown
## [功能/发布] 的回滚计划

### 触发条件
- 错误率 > 基线 2 倍
- P95 延迟 > [X]ms
- 用户报告 [特定问题]

### 回滚步骤
1. 禁用功能标志（如果适用）
   OR
1. 部署先前版本：`git revert <commit> && git push`
2. 验证回滚：健康检查、错误监控
3. 沟通：通知团队回滚

### 数据库考虑
- 迁移 [X] 有回滚：`npx prisma migrate rollback`
- 新功能插入的数据：[保留 / 清理]

### 回滚时间
- 功能标志：< 1 分钟
- 重新部署先前版本：< 5 分钟
- 数据库回滚：< 15 分钟
```

## 常见理由

| 理由 | 现实 |
|------|------|
| "在 staging 环境中可以运行，在生产环境中也会运行" | 生产环境具有不同的数据、流量模式和边缘情况。部署后监控。 |
| "我们不需要功能标志" | 每个功能都受益于一个关闭开关。即使是“简单”的变更也可能导致问题。 |
| "监控是开销" | 没有监控意味着您从用户投诉中发现问题，而不是从仪表板中发现。 |
| "我们稍后会添加监控" | 在发布前添加。您无法调试看不到的内容。 |
| "回滚是承认失败" | 回滚是负责任的工程。发布有问题的功能是失败。 |
| "错误率看起来很好，让我们继续发布" | 检查消耗率，而不仅仅是当前错误率。比基线速度更快地消耗预算即使在单个阈值都是绿色的情况下也是暂停信号。 |

## 警报

- 没有回滚计划就部署
- 生产环境中没有监控或错误报告
- 大爆炸发布（一次全部，没有 staging）
- 没有过期日期或所有者的功能标志
- 没有人监控第一个小时的发布
- 生产环境配置由记忆而不是代码完成
- “周五下午，让我们发布”
- 错误预算耗尽但功能工作未更改

## 验证

发布前：

- [ ] 发布前检查清单已完成（所有部分为绿色）
- [ ] 功能标志已配置（如果适用）
- [ ] 回滚计划已记录
- [ ] 监控仪表板已设置
- [ ] 已通知团队发布

发布后：

- [ ] 健康检查返回 200
- [ ] 错误率正常
- [ ] 延迟正常
- [ ] 关键用户流程正常
- [ ] 日志正在流动
- [ ] 已测试或验证回滚准备就绪

对于每个已发布的服务：

- [ ] 已实施错误预算政策：知道当预算低于 20% 和耗尽时采取什么行动
