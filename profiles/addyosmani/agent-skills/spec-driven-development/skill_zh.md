# 需求驱动开发

## 概述

在编写任何代码之前，先编写一个结构化的规范。规范是你和人类工程师之间的共享真理来源——它定义了我们正在构建什么、为什么以及我们如何知道它已完成。没有规范的代码是在猜测。

## 使用场景

- 开始一个新项目或功能
- 需求模糊或不完整
- 变更涉及多个文件或模块
- 即将做出架构决策
- 任务实施将花费超过30分钟

**不使用场景：** 单行修复、拼写错误更正或要求明确且自包含的变更。

## 受控工作流程

需求驱动开发有四个阶段，由范围检查（阶段0）先行，仅当单个请求包含多个可独立测试的功能时才激活。在当前阶段验证通过之前，不要进入下一阶段。

```
规范制定 ──→ 规划 ──→ 任务 ──→ 实现
   │          │        │          │
   ▼          ▼        ▼          ▼
  人类审查    人类审查  人类审查    人类审查
```

### 阶段0：范围检查

大多数请求描述一个功能。如果这个请求只有一个功能，则跳过此阶段直接进入规范制定——阶段0是例外而非规则，它对单功能特性不设层级。

**检测。** 在规范制定前分解单个请求包含多个可独立测试的功能：

- 请求名称不同的功能，各自有消费者或数据（例如身份、计费、通知、报告）
- 可接受标准聚类成可单独发布和验证的组
- 一个功能可以删除或替换，而无需重写其他功能的需求

**在编写任何规范前提出功能映射。** 简洁且可审查——一个模块表加上构建顺序，而不是项目计划：

```markdown
# 功能映射：[计划名称]

| 模块id | 责任 | 依赖 |
|---|---|---|
| identity | 账户、会话、SSO | — |
| billing | 计划、发票、支付 | identity |
| notifications | 邮件和webhook分派 | identity |
| reporting | 使用情况仪表板 | billing, notifications |

构建顺序：identity → billing, notifications → reporting
```

- **稳定的模块id。** 蛇形命名法，一旦选定，在计划期间永不重命名。规范、计划和下游命令通过这些id选择工作，而不是猜测哪个规范是活动的。
- **依赖方向，无循环。** 箭头指向一个方向。如果两个模块各自需要对方，它们就是一个模块。
- **接口位于边界。** 映射记录`billing`依赖于`identity`；它们之间的合同属于提供模块的规范（参见`api-and-interface-design`设计它）。

**映射像每个阶段一样受控。** 人类审查模块边界、依赖方向和构建顺序，在编写任何模块规范之前。映射错误代价高昂；审查十行并不贵。

**然后按模块递归。** 按依赖顺序运行规范制定 → 规划 → 任务 → 实现，为每个模块。每个模块都有自己的规范，范围限于该模块的目标、边界和成功标准。将批准的映射保存在项目根目录，并将每个模块的规范与它一起保存，按模块id命名（`SPEC-identity.md`，`SPEC-billing.md`）——映射，而不是文件名猜测，是现有内容的索引。

### 阶段1：规范制定

从高层愿景开始。向人类提出澄清问题，直到需求具体化。

**立即暴露假设。** 在编写任何规范内容之前，列出你的假设：

```
我正在做的假设：
1. 这是一个Web应用程序（不是原生移动应用）
2. 身份验证使用基于会话的cookie（不是JWT）
3. 数据库是PostgreSQL（基于现有的Prisma架构）
4. 我们只针对现代浏览器（没有IE11）
→ 现在纠正我，否则我将使用这些假设继续。
```

不要默默填充模糊的需求。规范的全部目的是在编写代码之前暴露误解——假设是最危险的误解形式。

**编写涵盖以下六个核心领域的规范文档：**

1. **目标** — 我们在构建什么，为什么？用户是谁？成功标准是什么？

2. **命令** — 完整的可执行命令，包括标志，而不仅仅是工具名称。
   ```
   构建：npm run build
   测试：npm test -- --coverage
   格式化：npm run lint --fix
   开发：npm run dev
   ```

3. **项目结构** — 源代码存放位置，测试存放位置，文档存放位置。
   ```
   src/           → 应用程序源代码
   src/components → React组件
   src/lib        → 共享工具
   tests/         → 单元和集成测试
   e2e/           → 端到端测试
   docs/          → 文档
   ```

4. **代码风格** — 一个真实的代码片段展示你的风格胜过三段描述。包括命名约定、格式化规则和良好输出的示例。

5. **测试策略** — 框架、测试存放位置、覆盖率预期、不同关注点对应不同测试级别。

6. **边界** — 三层系统：
   - **始终执行：** 提交前运行测试，遵循命名约定，验证输入
   - **先询问：** 数据库模式更改，添加依赖项，更改CI配置
   - **永不执行：** 提交密钥，编辑供应商目录，未经批准删除失败的测试

**规范模板：**

```markdown
# 规范：[项目/功能名称]

## 目标
[我们在构建什么，为什么。用户故事或可接受标准。]

## 技术栈
[框架、语言、关键依赖项及其版本]

## 命令
[构建、测试、格式化、开发——完整命令]

## 项目结构
[带描述的目录布局]

## 代码风格
[示例片段+关键约定]

## 测试策略
[框架、测试位置、覆盖率要求、测试级别]

## 边界
- 始终：[...]
- 先询问：[...]
- 永不：[...]

## 成功标准
[我们如何知道它已完成——具体的、可测试的条件]

## 未解决的问题
[任何需要人类输入的未解决的问题]
```

**外部规范工具：** 此工作流程与格式无关。如果项目已经使用OpenSpec或另一个规范系统，请保留该系统的工件格式和存储约定，而不是创建一个重复的`SPEC.md`。这项技能拥有澄清、内容和批准门；外部工具拥有如何表示已批准的规范。

**将指令重新定义为成功标准。** 当收到模糊的需求时，将它们翻译成具体条件：

```
需求："使仪表板更快"

重新定义的成功标准：
- 仪表板LCP < 2.5秒在4G连接上
- 初始数据加载完成时间 < 500毫秒
- 加载期间无布局偏移（CLS < 0.1）
→ 这些是正确的目标吗？
```

这让你能够循环、重试和解决问题，以明确的目标为目标，而不是猜测“更快”是什么意思。

### 阶段2：规划

使用已验证的规范生成技术实施计划：

1. 确定主要组件及其依赖关系
2. 确定实施顺序（什么必须首先构建）
3. 记录风险和缓解策略
4. 确定可以并行构建什么，必须顺序构建什么
5. 定义阶段之间的验证检查点

> 跟随`planning-and-task-breakdown`了解这些步骤背后的依赖图映射和垂直切片机制；它是规范来源。上面的要点是一个轻量级摘要；如果它们有分歧，`planning-and-task-breakdown`将优先。
>
> **输出约定：** 将计划保存到`tasks/plan.md`，并在`planning-and-task-breakdown`定义的任务列表目标中记录任务列表（默认`tasks/todo.md`；项目可以指定外部跟踪器）。如果不存在`tasks/`，则创建它。下游命令（`/build`等）期望这些默认值。

计划应该是可审查的：人类应该能够阅读它并说“是的，这是正确的做法”或“不，更改X。”

### 阶段3：任务

将计划分解为离散的、可实施的任务：

- 每个任务应该可以在一次专注的会话中完成
- 每个任务都有明确的可接受标准
- 每个任务包括验证步骤（测试、构建、手动检查）
- 任务按依赖关系排序，而不是按感知的重要性排序
- 没有任务应该需要更改超过~5个文件

> 跟随`planning-and-task-breakdown`了解完整的任务尺寸和依赖排序机制；它是规范来源。下面的模板是一个轻量级内联形式；如果它们有分歧，`planning-and-task-breakdown`将优先。

**任务模板：**
```markdown
- [ ] 任务：[描述]
  - 可接受：[完成后必须为真]
  - 验证：[如何确认——测试命令、构建、手动检查]
  - 文件：[将触及哪些文件]
```

### 阶段4：实现

按照`skills/incremental-implementation/SKILL.md`（`incremental-implementation`）和`skills/test-driven-development/SKILL.md`（`test-driven-development`）执行任务。使用`skills/context-engineering/SKILL.md`（`context-engineering`）在每个步骤加载正确的规范部分和源文件，而不是向代理发送整个规范。

## 保持规范活跃

规范是一个活生生的文档，而不是一次性工件：

- **决策更改时更新** — 如果发现数据模型需要更改，请先更新规范，然后实施。
- **范围更改时更新** — 添加或删除的功能应在规范中反映。
- **提交规范** — 规范应与代码一起存放在版本控制中。
- **在PR中引用规范** — 链接到每个PR实现的规范部分。

## 常见理由

| 理由 | 现实 |
|---|---|
| "这很简单，我不需要规范" | 简单任务不需要*长*规范，但它们仍然需要可接受标准。两行规范就足够了。 |
| "我会编写规范后再编码" | 那是文档，不是规范。规范的价值在于在编写代码之前强制清晰。 |
| "规范会拖慢我们" | 15分钟的规范可以防止数小时的返工。在15分钟内进行瀑布式处理胜过在15小时内调试。 |
| "需求会改变" | 这就是为什么规范是一个活生生的文档。过时的规范仍然比没有规范更好。 |
| "用户知道他们想要什么" | 即使是明确的需求也有隐含的假设。规范暴露了这些假设。 |
| "这是一个大功能；分割它是有开销的" | 如果可接受标准聚类成可独立测试的组，一个整体的规范迫使下游任务推理整个合同。一个十行的功能映射是廉价的替代方案。 |
| "我会在规划期间分解" | 规划在规范内切片任务。到那时，过大的工件已经存在——模块边界和依赖方向必须在编写规范之前，而不是之后决定。 |

## 警报

- 没有任何书面需求就开始编写代码
- 在澄清“完成”的含义之前问“我应该直接开始构建吗？”
- 实现规范或任务列表中未提及的功能
- 没有记录就做出架构决策
- 因为没有预先批准功能映射而跳过规范，因为“很明显要构建什么”
- 一个需求跨越多个可独立测试的功能的规范
- 在实施期间隐式决定模块边界或构建顺序，因为没有预先批准功能映射

## 验证

在继续实施之前确认：

- [ ] 规范涵盖了所有六个核心领域
- [ ] 人类已经审查并批准了规范
- [ ] 成功标准是具体且可测试的
- [ ] 边界（始终/先询问/永不）已定义
- [ ] 规范已保存到存储库中的文件
- [ ] 如果请求包含多个可独立测试的功能，则在编写任何模块规范之前已批准功能映射（模块id、依赖方向、构建顺序）
- [ ] 每个模块规范都追溯到已批准映射中的模块id
