# 面试我

## 概述

人们所要求的东西和他们真正想要的东西是不同的。他们要求“一个仪表盘”，只是因为这是人们通常会要求的东西，而不是因为仪表盘能解决他们的问题。他们说“让它更快”，但没有一个具体的目标数字。

发现这种差距最便宜的时刻是在任何计划、规范或代码存在之前。一旦你开始构建，转换成本就是真实的，用户会合理地将错误的事情合理化为“足够好”的事情。不匹配会被锁定。

这项技能是在付出任何代价之前缩小差距。其他定义阶段的技能假设你已经大致知道你想要什么：`idea-refine` 从一个想法中生成各种变体，`spec-driven-development` 将需求写下来，`doubt-driven-development` 在你草拟计划后对计划进行压力测试。面试我是在所有这些之前，一次问一个问题，并附上你的最佳猜测，直到你能预测用户在说出之前会说什么。

## 何时使用

在以下情况下使用这项技能：

- 要求中至少缺少一个：**用户是谁**、**他们为什么想要**它、**成功**看起来像什么、**约束条件**是什么
- 请求是常规的而不是具体的（“给我构建 X”、“让它更快”），并且你无法在不猜测的情况下理解常规
- 你想从你还没有揭示的假设开始
- 当两个合理的选项之间存在冲突时，用户还没有说出他们正在优化的值（简单性 vs. 灵活性、成本 vs. 速度）
- 用户明确调用： “面试我”、“拷问我”、“在我们开始之前，我们确定吗？”、“压力测试我的思维”

**何时不使用：**

- 要求是明确的、自包含的（“重命名这个变量”、“修复这个错误”）
- 用户已经明确要求速度而不是验证
- 纯粹的信息请求（“X 是如何工作的？”、“这段代码做什么？”）
- 机械操作（重命名、格式化、文件移动）
- 你已经拥有 ≥95% 的信心；在假设你不需要之前，请重新阅读以下停止条件

## 加载约束

这项技能需要一个活跃的、响应迅速的用户。**不要在非交互式环境中调用**，例如 CI 管道、计划运行、`/loop` 或自主循环。如果你处于这些状态之一，并且要求不明确，请将此标记为用户的障碍，而不是猜测。

## 流程

### 第 1 步：假设，并附上信心数字

在问任何问题之前，用**一句话**写下你对用户想要的当前最佳理解，并附上一个诚实的信心数字（0–100%）：

```
假设：你想在站会中回答“我们做得怎么样？”的方法，而“仪表盘”是想到的惯例。
信心：~30% — 缺失：为谁、上下文中“指标”的含义以及成功看起来像什么
```

这个数字强迫你诚实。如果你写下了高数字，但实际上无法预测用户对接下来你要问的三个问题的反应，那么这个数字就是错误的。从你可以辩护的信心水平开始。

当信心低于 ~70% 时，在同一行附加一个简短的理由——什么仍然悬而未决或缺失。这告诉用户面试需要揭示什么，并防止数字成为一个模糊的信号。

### 第 2 步：一次问一个问题，每个问题都附上猜测

格式：

```
Q: <一个专注的问题>
GUESS: <你对答案的假设，以及产生它的推理>
```

等待用户反应后再问下一个问题。

**为什么一次一个，而不是一批：**

- 用户无法在你把它们淹没在列表中时对你的假设做出反应
- 批次鼓励快速浏览和表面答案
- 第三个问题通常取决于第一个问题的答案；一次问所有问题会锁定错误的框架
- 用户仔细思考的能量是有限的；一次一个问题地花它

**为什么附上猜测：**

- 用户对错误的猜测反应比从零开始生成答案更快
- 它让你对一个明显错误的假设做出承诺，这能让你保持诚实
- 它揭示了你自己的假设，这是面试要暴露的东西

这里的风险是礼貌的用户同意你的猜测以表示友好。通过表现出你愿意犯错，并偶尔在用户预期会反对的方向上猜测来缓解这种情况。

### 第 3 步：倾听“想要 vs. 应该想要”

最危险的答案是用户说一个深思熟虑的答案听起来像什么，而不是他们实际上想要什么。注意：

- 答案匹配最佳实践谈话（“我想让它可扩展”、“干净的架构”），但没有具体细节
- 委托给惯例（“大多数应用程序都是这样做的”、“标准方法”）
- 诸如“我应该……”、“我认为我应该……”、“良好的工程实践说……”之类的短语
- 用 Buzzwords 作为目标——当“现代”、“可扩展”、“健壮”是答案，而不是具体结果时

当你听到这些时，要问的问题是：

> *“如果你不必向任何人解释，你实际上想要什么？”*

这个问题通常比之前的五个问题做得更多。

### 第 4 步：用用户自己的话重申意图

当你的信心很高时，写回你认为用户想要的东西。保持简洁（5–8 行），尽可能使用用户的语言，并按用户可以逐行确认或纠正的结构进行组织：

```
我现在认为你想要的是：

- 结果：      <一行>
- 用户：      <一行——谁受益>
- 为什么现在： <一行——什么发生了变化>
- 成功：      <一行——我们如何知道它有效>
- 约束：      <一行——绑定限制>
- 超出范围： <一行——我们明确不做什么>

是/否/改进？
```

包括“超出范围”是强制性的。一半的错位是关于我们*不*构建的东西的沉默分歧。

### 第 5 步：确认——明确的“是”，而不是“随便你”

门是一个明确的“是”。以下**不是**“是”：

- “随便你认为是最好的。” → 用户在委托，这意味着他们也不有 95% 的信心。重新提问，并提供两个具体的选项作为选择。
- “听起来不错。” → 模糊不清。问：“有什么需要改进的吗？”沉默不是确认。
- “好的，我们开始吧。” → 通常是礼貌地退出，而不是认可。相同的后续操作。
- 沉默后跟着“好的，我们开始吧。” → 用户已经放弃了面试，而不是收敛。停止并问你是否错过了什么。

如果他们纠正你，将更正包含在内并重申。循环直到你得到一个明确的“是”。

### 第 6 步：终端回合和停止规则（关键）

当用户用明确的“是”确认意图陈述时：

1. **交付确认的意图陈述。**
2. **提供下游路径**（提供将其保存到 `docs/intent/[主题].md`、使用 `spec-driven-development` 起草规范或计划后进行任务规划）。
3. **立即停止你的回合**。不要在这次回合中调用工具或开始下游工作。将控制权交还给用户，让他们选择下一步。

### 95% 信心停止规则

当你能回答“我能预测用户对接下来我要问的三个问题的反应吗？”时，你就完成了。

如果回答是“是”，你就有共享的理解。停止面试并生成重述。如果回答不是“是”，你还没完成；问下一个问题。

这是一个可检查的测试，而不是一种感觉。它也有一个底线：如果你已经问了好几个问题，仍然无法预测，那不是关于要求的信息，而是一个停止继续打磨的理由。停止并告诉用户：“我问了 X 个问题，我仍然无法预测你的反应。基础缺失。想后退吗？”

## 输出

这项技能的输出是一个**确认的意图陈述**：来自第 4 步的重述，以及来自第 5 步的明确的“是”。这就是交付物。规范、计划和任务列表是下游；它们消耗这项技能产生的意图。

如果用户希望意图持续存在（一个多会话项目、转交给另一个协作者），提供将其保存到 `docs/intent/[主题].md`。只有在他们确认时才保存。

## 示例

一个简短的“之前”和“之后”。

**没有 `interview-me`：**

```
用户：给我构建一个用于我们指标的仪表盘
代理：<开始建议图表库和布局>
```

代理已经假设：为谁、指标是什么、“为我们的团队”是什么意思、成功看起来像什么。这些都没有被说明。每一个假设都是用户后来可以说“那不是我想要的”的地方。

**使用 `interview-me`：**

```
用户：给我构建一个用于我们指标的仪表盘

代理：
假设：你想在站会中回答“我们做得怎么样？”的方法，而“仪表盘”是想到的惯例。
信心：~30% — 缺失：为谁、什么是“指标”、成功看起来像什么

Q:     当你说“我们做得怎么样？”时，是谁在问——你一个人、站会中的工程团队，还是向上（例如，你的经理、高管、董事会）？
GUESS：站会中的工程团队，因为“我们”通常这样范围，站会是这个问题被问到的地方。如果是为高管，指标和框架会改变很多。

用户：实际上是给我。我一直在失去跟踪哪些实验正在运行以及它们的早期信号。

代理：
更新阅读：根本不是团队仪表盘。它是一个个人实验跟踪器。信心：~60% — 仍然缺失：“早期信号”是什么意思以及完成看起来像什么。

Q:     缺失的是你不知道哪些实验存在，还是你无法在一个地方看到它们的结果？
GUESS：第二个。你 somewhere 有一个实验列表，但它们的结果存在于五个不同的工具中，手动协调它们让你感到厌烦。

用户：第一个实际上是。我字面上没有列表。它们分散在不同的文档中。

代理：<继续>
```

两个问题之后，代理已经发现实际的请求不是“一个仪表盘”。它是“一个列表”。不同的工件、不同的范围、不同的工作。仪表盘将是错误的。

## 与其他技能的交互

- **`idea-refine`**：下游。如果确认的意图是“我想 X，但我不知道如何范围它”，将 `idea-refine` 转交给生成针对现在明确的意图的各种变体。
- **`spec-driven-development`**：下游。如果确认的意图是具体的（“我想 X 用于 Y 用户，具有 Z 成功标准”），将 `spec-driven-development` 转交给将其写下来。
- **`planning-and-task-breakdown`**：这个技能的两个跳下游（在规范之后）。
- **`doubt-driven-development`**：时间线上的另一端。面试我是在决策意图提取之前；doubt-driven 是在决策工件审查之后。两者都捕获了偏差，但处于不同的时刻。
- **`source-driven-development`**：正交的。面试我澄清用户想要什么；SDD 验证框架事实。它们不竞争。

## 常见合理化

| 合理化 | 现实 |
|---|---|
| “要求足够清晰” | 如果你现在无法用一句话写出用户期望的结果，要求就不明确。在决定之前运行步骤 1。 |
| “问太多问题浪费了他们的时间” | 4–6 个有针对性的问题的时间浪费很小。构建错误东西的时间浪费巨大，用户是承担这个成本的人。 |
| “在构建时我会弄清楚” | 代码存在后的转换成本是现在的 10 倍。在实施过程中的发现是返工。 |
| “他们说了‘随便你’，所以我应该决定” | “随便你”是委托，不是决策。重新提问，并提供两个具体的选项作为选择。 |
| “我应该给他们几个选项让他们选择” | 选项在用户知道他们想要什么并在权衡之间选择时才有效。他们还没有知道他们想要什么。列出选项会扩大搜索范围；提问会缩小搜索范围。 |
| “如果我附上我的猜测，我就是在引导他们” | 引导是重点。反应比从零开始生成更快。风险是奉承，而不是引导；通过表现出你愿意犯错来缓解。 |
| “我们谈得足够多了，我明白了” | 测试它：你能预测他们对接下来你要问的三个问题的反应吗？如果不能，你还没有完全理解。 |
| “用户说了‘是’，我们完成了” | 如果“是”是在一个模糊的重述之后或一个开放式回答“听起来不错”之后，这个“是”是空洞的。具体地重述并重新确认。 |

## 信号灯

- 一个消息中三个或更多问题：这是批量处理，不是面试
- 没有附上你假设的问题：这是调查，而不是承诺
- 接受“随便你认为是最好的”作为最终答案
- 在用户没有明确确认你的重述之前产生规范、计划或任务列表
- 在意图确认后立即调用工具或开始下游工作，而不是停止回合
- 问题被表述为“最佳实践会是什么？”而不是“你实际上想要什么？”
- 用户给出了一个表明复杂性的答案（可扩展的、干净的、现代的），而你接受它而没有探查它是否是他们真正想要的
- 三个或更多轮而你的信心没有明显上升：你问的问题不对，后退并重新框架
- 一个信心数字低于 ~70% 而没有附加一条简短的理由（什么仍然悬而未决或缺失）
- 在用户确认之前保存意图文档（文档本身暗示了用户没有给出的“是”）
- 在重述中跳过“超出范围”行（非目标上的沉默分歧是错位的一半）

## 验证

应用面试我之后：

- [ ] 在第一个回合中陈述了一个明确的假设和信心数字
- [ ] 每个低于 ~70% 的信心数字都附带了一条简短的理由（什么仍然悬而未决或缺失）
- [ ] 问题一次一个，每个问题都附上了代理的猜测
- [ ] 至少运行了一个“如果你不必向任何人解释，你实际上想要什么？”探测，当用户给出了一个表明复杂性的或惯例的答案时
- [ ] 写回了一个具体的重述（结果 / 用户 / 为什么现在 / 成功 / 约束 / 超出范围）给用户
- [ ] 用户用明确的“是”确认了重述（不是“随便你”，不是“听起来不错”，不是沉默）
- [ ] 在停止点，代理能够预测它将要问的下一个三个问题的反应
- [ ] 在收到明确的确认后，立即停止回合，没有调用工具或开始下游工作
- [ ] 任何转交给下游技能（`idea-refine`、`spec-driven-development`）都是基于确认的意图，而不是原始不明确的要求
