# Git 工作流与版本控制

## 概述

Git 是你的安全网。将提交视为保存点，将分支视为沙盒，将历史记录视为文档。随着 AI 代理高速生成代码，规范的版本控制是保持变更可管理、可审查、可撤销的机制。

## 何时使用

始终使用。所有代码变更都应通过 git 流程。

## 核心原则

### 主干式开发（推荐）

保持 `main` 始终可部署。在 1-3 天内合并回的短期特性分支上工作。长期开发分支是隐藏的成本——它们会分叉、产生合并冲突并延迟集成。DORA 研究持续表明，主干式开发与高性能工程团队相关。

```
main ──●──●──●──●──●──●──●──●──●──  (始终可部署)
        ╲      ╱  ╲    ╱
         ●──●─╱    ●──╱    ← 短期特性分支 (1-3 天)
```

这是推荐的默认设置。使用 gitflow 或长期分支的团队可以调整这些原则（原子提交、小变更、描述性信息）到他们的分支模型——提交纪律比具体的分支策略更重要。

- **开发分支是成本。** 每个分支存活一天，就会累积合并风险。
- **发布分支是可接受的。** 当你需要稳定发布，而 main 分支继续向前推进时。
- **特性标志 > 长分支。** 优先使用标志部署不完整的工作，而不是将工作保留在分支上几周。

### 1. 早期提交，频繁提交

每个成功的增量都有自己的提交。不要累积大量未提交的变更。

```
工作模式：
  实现切片 → 测试 → 验证 → 提交 → 下一个切片

不是这样：
  实现所有功能 → 希望它工作 → 巨大提交
```

提交是保存点。如果下一个变更破坏了某些东西，你可以立即回滚到最后一个已知良好状态。

### 2. 原子提交

每个提交做一件逻辑上的事情：

```
# 好：每个提交都是自包含的
git log --oneline
a1b2c3d 添加任务创建端点并带验证
d4e5f6g 添加任务创建表单组件
h7i8j9k 将表单连接到 API 并添加加载状态
m1n2o3p 添加任务创建测试 (单元测试 + 集成测试)

# 不好：所有东西混在一起
git log --oneline
x1y2z3a 添加任务功能，修复侧边栏，更新依赖，重构工具
```

### 3. 描述性信息

提交信息解释 *为什么*，而不仅仅是 *是什么*：

```
# 好：解释意图
feat: 为注册端点添加电子邮件验证

防止无效的电子邮件格式到达数据库。
在路由处理器级别使用 Zod 模式验证，
与 auth.ts 中现有的验证模式保持一致。

# 不好：描述从差异中显而易见的内容
update auth.ts
```

**格式：**
```
<类型>: <简短描述>

<可选的正文解释原因，而不是是什么>
```

**类型：**
- `feat` — 新功能
- `fix` — 修复 Bug
- `refactor` — 既不修复 Bug 也不添加功能的代码变更
- `test` — 添加或更新测试
- `docs` — 仅文档
- `chore` — 工具、依赖、配置

### 4. 分离关注点

不要将格式化变更与行为变更结合。不要将重构与功能结合。每种类型的变更都应该是单独的提交——理想情况下是单独的 PR：

```
# 好：分离关注点
git commit -m "refactor: 将验证逻辑提取到共享工具"
git commit -m "feat: 为注册添加电话号码验证"

# 不好：混合关注点
git commit -m "refactor 验证并添加电话号码字段"
```

**将重构与功能工作分开。** 重构变更与功能变更是两种不同的变更——分别提交。这使得每个变更更容易审查、回滚和理解历史记录。小的清理工作（重命名一个变量）可以在审查者决定的情况下包含在功能提交中。

### 5. 控制变更大小

目标每个提交/PR 约 100 行。超过 1000 行的变更应拆分。参见 `code-review-and-quality` 中的拆分策略，了解如何将大变更拆分。

```
~100 行  → 易于审查，易于回滚
~300 行  → 单个逻辑变更可以接受
~1000 行 → 拆分成更小的变更
```

## 分支策略

### 特性分支

```
main (始终可部署)
  │
  ├── feature/task-creation    ← 每个特性一个分支
  ├── feature/user-settings    ← 并行工作
  └── fix/duplicate-tasks      ← Bug 修复
```

- 从 `main`（或团队的默认分支）分支
- 保持分支短生命周期（1-3 天内合并）——长期分支是隐藏的成本
- 合并后删除分支
- 优先使用特性标志而不是长期分支来处理不完整的特性

### 分支命名

```
feature/<简短描述>   → feature/task-creation
fix/<简短描述>       → fix/duplicate-tasks
chore/<简短描述>     → chore/update-deps
refactor/<简短描述>  → refactor/auth-module
```

## 使用 Worktree

对于并行 AI 代理工作，使用 git worktrees 同时运行多个分支：

```bash
# 为特性分支创建一个 worktree
git worktree add ../project-feature-a feature/task-creation
git worktree add ../project-feature-b feature/user-settings

# 每个工作树是一个包含自己分支的独立目录
# 代理可以并行工作而不互相干扰
ls ../
  project/              ← main 分支
  project-feature-a/    ← task-creation 分支
  project-feature-b/    ← user-settings 分支

# 完成后，合并并清理
git worktree remove ../project-feature-a
```

优点：
- 多个代理可以同时处理不同的特性
- 无需切换分支（每个目录有自己的分支）
- 如果一个实验失败，删除工作树——不会丢失任何东西
- 变更隔离，直到显式合并

## 保存点模式

```
代理开始工作
    │
    ├── 做出变更
    │   ├── 测试通过？→ 提交 → 继续
    │   └── 测试失败？→ 回滚到最后一个提交 → 调查
    │
    ├── 做出另一个变更
    │   ├── 测试通过？→ 提交 → 继续
    │   └── 测试失败？→ 回滚到最后一个提交 → 调查
    │
    └── 特性完成 → 所有提交形成干净的提交历史
```

这种模式意味着你永远不会丢失超过一个增量的工作。如果代理跑偏了，`git reset --hard HEAD` 可以让你回到最后一个成功状态。

## 变更摘要

任何修改后，提供结构化摘要。这使得审查更容易，记录范围纪律，并暴露意外变更：

```
所做的变更：
- src/routes/tasks.ts: 为 POST 端点添加验证中间件
- src/lib/validation.ts: 使用 Zod 添加 TaskCreateSchema

我故意没有触碰的内容：
- src/routes/auth.ts: 有类似的验证差距但超出范围
- src/middleware/error.ts: 错误格式可以改进（单独处理任务）

潜在问题：
- Zod 模式是严格的——拒绝额外字段。确认这是期望的。
- 添加了 zod 依赖（72KB 压缩后）——已经在 package.json 中
```

这种模式可以早期捕获错误假设，并为审查者提供清晰的变更地图。"未触碰"部分尤其重要——它表明你遵守了范围纪律，没有进行不请自来的翻新。

## 提交前卫生

每次提交前：

```bash
# 1. 检查你要提交的内容
git diff --staged

# 2. 确保没有秘密
git diff --staged | grep -i "password\|secret\|api_key\|token"

# 3. 运行测试
npm test

# 4. 运行代码风格检查
npm run lint

# 5. 运行类型检查
npx tsc --noEmit
```

使用 git hooks 自动化这个过程：

```json
// package.json (使用 lint-staged + husky)
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{json,md}": ["prettier --write"]
  }
}
```

## 处理生成文件

- **仅当项目期望它们时才提交生成文件**（例如 `package-lock.json`、Prisma 迁移文件）
- **不要提交** 构建输出 (`dist/`, `.next/`)、环境文件 (`.env`) 或 IDE 配置 (`.vscode/settings.json` 除非共享)
- **有一个 `.gitignore`** 覆盖：`node_modules/`、`dist/`、`.env`、`.env.local`、`*.pem`

## 使用 Git 进行调试

```bash
# 找出引入 Bug 的提交
git bisect start
git bisect bad HEAD
git bisect good <已知良好提交>
# Git 在中间点检出；在每个点运行你的测试以缩小范围

# 查看最近的变化
git log --oneline -20
git diff HEAD~5..HEAD -- src/

# 查找最后修改特定行的用户
git blame src/services/task.ts

# 搜索提交信息中的关键字
git log --grep="validation" --oneline
```

## 发布与版本控制

提交是你自己跟踪变更的方式；**版本**是你的消费者跟踪变更的方式。一旦有其他东西依赖你的代码——另一个团队、发布的包、部署的客户端——"main 上的最新版本"就不再是"我在运行什么，以及是否可以安全升级"的充分答案。版本号和变更日志是回答这个问题的合同。

### 语义化版本控制

对于任何有消费者的东西，使用 `MAJOR.MINOR.PATCH` 版本号，并让数字传达意义：

```
  MAJOR  破坏性变更——消费者必须更改他们的代码来升级
  MINOR  新功能，向后兼容——可以安全升级
  PATCH  修复 Bug，向后兼容——可以安全升级
```

数字是一个承诺，所以让代码匹配它。一个"补丁"如果改变了消费者依赖的行为，就是一个穿着伪装的重大变更（Hyrum's Law——参见 `api-and-interface-design` 技能）。当不确定一个变更是否破坏性时，假设它是破坏性的；一个意外的重大变更远比破坏消费者便宜。

### 标记发布，让标签成为真相的来源

发布是一个不可变的历史点，而不是一个移动的分支。标记它，以便它总是可以重现：

```bash
git tag -a v1.4.0 -m "发布 1.4.0"
git push origin v1.4.0
```

从标签而不是分散在文件中手动编辑版本号，这样工件、标签和变更日志永远不会不一致。

### 保持一个面向人类的变更日志

变更日志不是 `git log`。它是经过筛选的、面向消费者的答案"发生了什么，我是否关心？"——按 `添加 / 修改 / 修复 / 已弃用 / 删除 / 安全` 分组，最新在最上面，每个条目围绕用户影响而不是内部机制来表述。

```markdown
## [1.4.0] - 2025-06-12
### 添加
- 通过 CSV 批量导入任务
### 修复
- 循环任务截止日期的时区漂移
### 已弃用
- `GET /v1/tasks/all` — 使用分页的 `GET /v1/tasks`（将在 2.0 中移除）
```

在变更做出变更的同时记录条目，而影响是新鲜的——不是在发布时从提交考古中重建。破坏性变更会获得迁移说明和弃用窗口（遵循 `deprecation-and-migration` 技能）；实际发布是 `shipping-and-launch` 技能的工作——这一部分是版本控制合同，它为它提供输入。

## 常见借口

| 借口       | 现实       |
|---|---|
| "我会在特性完成后提交" | 一个巨大的提交无法审查、调试或回滚。每次切片都提交。 |
| "信息不重要" | 信息是文档。未来的你（和未来的代理）需要理解发生了什么以及为什么。 |
| "我稍后会合并" | 合并会破坏开发叙事。从一开始就保持干净的增量提交。 |
| "分支会增加开销" | 短期分支是免费的，可以防止冲突工作碰撞。长期分支是问题——1-3 天内合并。 |
| "我会稍后拆分这个变更" | 大变更更难审查、风险更高、更难部署、更难回滚。在提交前拆分，而不是提交后。 |
| "我不需要 .gitignore" | 直到 `.env` 包含生产秘密被提交。立即设置。 |
| "只是一个小的修复，增加补丁版本" | 检查消费者可以观察到什么。他们依赖的行为变更是一个重大变更，无论差异大小如何。 |
| "变更日志只是提交日志" | 提交是为你；变更日志是面向消费者的，按影响筛选。从原始提交生成一个会埋葬重要内容。 |
| "我们会在发布时写变更日志" | 到那时影响是凭记忆重建的，其中一半已经丢失。在变更时记录条目。 |

## 信号灯

- 大量未提交的变更累积
- 提交信息像 "fix"、"update"、"misc"
- 格式化变更与行为变更混合
- 项目中没有 `.gitignore`
- 提交 `node_modules/`、`.env` 或构建工件
- 与 main 分叉差异很大的长期分支
- 强制推送共享分支
- 在小版本或补丁版本提升中发布破坏性变更
- 没有标签的发布，或者版本号与标签不一致的手动编辑
- 面向用户的发布没有变更日志条目，或者变更日志只是简单地倾倒提交信息

## 验证

对于每个提交：

- [ ] 提交做一件逻辑上的事情
- [ ] 信息解释原因，遵循类型规范
- [ ] 提交前测试通过
- [ ] 差异中没有秘密
- [ ] 没有将格式化变更与行为变更混合
- [ ] `.gitignore` 覆盖标准排除项

对于每个发布（任何有消费者的东西）：

- [ ] 版本提升与变更匹配：破坏性 → 主版本，添加性 → 次版本，修复 → 补丁
- [ ] 发布被标记，版本是从标签派生的，而不是手动编辑的不一致
- [ ] 变更日志有一个按影响分组的、面向人类的、针对此版本的条目
