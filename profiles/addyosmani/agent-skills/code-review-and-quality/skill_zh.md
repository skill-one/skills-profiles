# 代码审查与质量

## 概述

多维度代码审查，并设置质量门禁。每一次变更在合并前都需要经过审查——没有例外。审查涵盖五个维度：正确性、可读性、架构、安全性和性能。

**批准标准：** 当一个变更明确提升了整体代码健康度时，即使它不完美，也应该批准。完美的代码不存在——目标是持续改进。不要因为一个变更不是你本会写的样子就阻止它。如果它改进了代码库并遵循了项目的规范，就批准它。

## 使用时机

- 合并任何 PR 或变更之前
- 完成一个功能实现之后
- 当你需要评估另一个代理或模型生成的代码时
- 当重构现有代码时
- 任何修复 Bug 之后（审查修复和回归测试）

## 五轴审查

每一次审查都在这些维度上评估代码：

### 1. 正确性

代码是否做了它声称要做的？

- 它是否与规范或任务要求匹配？
- 是否处理了边缘情况（空值、边界值）？
- 是否处理了错误路径（不只是成功路径）？
- 是否通过了所有测试？测试是否真的在测试正确的事情？
- 是否有计算错误、竞态条件或状态不一致？

### 2. 可读性与简洁性

另一个工程师（或代理）能否在不解释的情况下理解这段代码？

- 名称是否描述性强且与项目规范一致？（没有上下文的 `temp`、`data`、`result`）
- 控制流是否简单（避免嵌套三元运算符、深层回调）？
- 代码是否逻辑组织（相关代码分组、清晰的模块边界）？
- 是否有任何“技巧”应该简化？
- **这能否用更少的行数完成？**（1000 行代码而 100 行足够就是失败）
- **抽象是否值得其复杂性？**（在第三个用例之前不要泛化）
- 是否需要注释来澄清非明显的意图？（但不要注释明显的代码）
- 是否有死代码残留：无操作变量（`_unused`）、向后兼容的遮蔽层或 `// 移除` 注释？
- **是否在无关的流程上添加了新的条件语句？** 这是一种设计气味，而不是小问题——将逻辑推入它自己的辅助函数、状态或策略，而不是缠绕现有的路径。
- **是否在同一形状上出现重复的条件语句？** 它们表明缺少模型或调度器。“临时”分支通常是永久债务。

### 3. 架构

变更是否适合系统的设计？

- 它是否遵循现有的模式或引入了新的模式？如果是新的，是否有正当理由？
- 它是否保持了干净的模块边界？
- 是否有应该共享的代码重复？
- 依赖项是否按正确的方向流动（没有循环依赖）？
- 抽象级别是否合适（没有过度设计，没有过度耦合）？
- **这次重构是减少了复杂性还是仅仅转移了它？** 计算读者必须持有的概念数量以遵循变更。如果“更干净”的版本保持这个数量不变，它就不干净——优先选择使整个分支、模式或层消失的重构，而不是重新集中相同的逻辑。优先删除抽象而不是润色它。
- **特定功能的逻辑是否泄漏到共享或通用模块中？** 将逻辑保留在其所属层，重用现有的规范辅助函数而不是近似的副本，并且不要规范化架构漂移。
- **类型边界是否明确？** 质疑无谓的 `any`/`unknown`/可选/强制转换和静默回退，这些回退掩盖了不明确的不变量——使边界明确通常会使周围的控制流更简单。

### 4. 安全性

有关详细的安全指南，请参阅 `security-and-hardening`。变更是否引入了漏洞？

- 用户输入是否经过验证和清理？
- 密钥是否保持在代码、日志和版本控制之外？
- 是否在需要的地方进行了身份验证/授权检查？
- SQL 查询是否参数化（没有字符串连接）？
- 输出是否编码以防止 XSS？
- 依赖项是否来自可信来源且没有已知漏洞？
- 来自外部来源（API、日志、用户内容、配置文件）的数据是否被视为不受信任？
- 在逻辑或渲染中使用之前，是否在系统边界处验证了外部数据流？

### 5. 性能

有关详细的性能分析和优化，请参阅 `performance-optimization`。变更是否引入了性能问题？

- 任何 N+1 查询模式？
- 任何无界循环或不约束的数据获取？
- 任何应该异步的同步操作？
- 任何 UI 组件中的不必要重绘？
- 任何列表端点缺少分页？

## 结构性补救措施

当你标记一个结构性问题时，建议移动——而不仅仅是问题。一个只说“这很复杂”的审查让作者猜测。寻求命名的重构：

- **用类型模型或显式调度器替换条件语句链**。
- **将重复的分支合并为更清晰的单一流程**。
- **将编排与业务逻辑分离**，以便每个都能独立读取。
- **将特定功能的逻辑从共享模块移出到拥有该概念的包中**。
- **重用规范辅助函数**而不是定制的近似副本。
- **使类型边界明确**，以便下游分支消失。
- **删除一个传递式包装器**，它增加了间接性而没有澄清 API。
- **提取一个辅助函数，或将一个大文件拆分为专注的模块**。

优先选择移除移动部件的补救措施，而不是将相同的复杂性分散到周围。

## 变更大小

小而专注的变更更容易审查、更快合并、更安全部署。目标是这些大小：

```
~100 行变更   → 好。可以一次性审查。
~300 行变更   → 如果是单一逻辑变更，可以接受。
~1000 行变更  → 太大。拆分它。
```

**关注文件大小，而不仅仅是差异大小。** 一个小的差异仍然可能将文件推过健康的边界——单个文件中大约 1000 *总行数*（与上面 ~1000 *变更* 行阈值不同）是一个常见的检查信号，而不是硬性上限。当一个变更实质性增长了一个已经很大的文件时，询问是否应该先提取辅助函数、子组件或模块，然后再添加更多。分解，然后添加。

**“一个变更”算什么：** 一个自包含的修改，解决一个问题，包括相关的测试，并在提交后保持系统功能。功能的一部分——不是整个功能。

**当变更太大时的拆分策略：**

| 策略   | 如何   | 何时   |
|------|------|------|
| **堆叠** | 提交一个小变更，基于它开始下一个 | 顺序依赖关系 |
| **按文件组** | 为需要不同审查者审查的组提交单独的变更 | 跨切关注点 |
| **水平** | 先创建共享代码/桩，然后是消费者 | 分层架构 |
| **垂直** | 拆分为功能更小的全栈切片 | 功能工作 |

**当大变更可以接受时：** 完整的文件删除和自动重构，审查者只需要验证意图，不需要每一行。

**将重构与功能工作分开。** 一个重构现有代码并添加新行为的变更就是两个变更——分别提交它们。小的清理（变量重命名）可以由审查者酌情包含。

## 变更描述

每一次变更都需要一个在版本控制历史中独立的描述。

**第一行：** 短、祈使、独立。“删除 FizzBuzz RPC”而不是“删除 FizzBuzz RPC”。必须足够信息，以便在搜索历史时，有人可以理解变更，而无需阅读差异。

**正文：** 变更的内容和原因。包括上下文、决策和代码本身无法看到的推理。在相关的地方链接到 Bug 编号、基准结果或设计文档。当存在方法缺陷时，承认它们。

**反模式：** “修复 Bug”、“修复构建”、“添加补丁”、“将代码从 A 移动到 B”、“阶段 1”、“添加便利函数”。

## 审查过程

### 第一步：理解上下文

在查看代码之前，理解意图：

```
- 这个变更试图完成什么？
- 它实现了哪个规范或任务？
- 预期的行为变化是什么？
```

### 第二步：先审查测试

测试揭示意图和覆盖率：

```
- 变更是否存在测试？
- 它们是否测试行为（而不是实现细节）？
- 是否覆盖了边缘情况？
- 测试名称是否描述性强？
- 如果代码改变，测试是否会捕获回归？
```

### 第三步：审查实现

以五个轴为参考，逐步审查代码：

```
对于每个已更改的文件：
1. 正确性：这段代码是否做了测试所说的？
2. 可读性：我能否在不帮助的情况下理解？
3. 架构：它是否符合系统？
4. 安全性：有任何漏洞吗？
5. 性能：有任何瓶颈吗？
```

### 第四步：分类发现

用严重性标记每个评论，以便作者知道什么是必须的，什么是可选的：

| 前缀   | 含义   | 作者操作   |
|------|------|------|
| *(无前缀)* | 必须变更 | 合并前必须解决 |
| **关键：** | 阻止合并 | 安全漏洞、数据丢失、功能损坏 |
| **小问题：** | 小的、可选的 | 作者可以忽略——格式、风格偏好 |
| **可选：** / **考虑：** | 建议   | 值得考虑但不是必须的 |
| **仅供参考** | 仅信息性 | 无需操作——仅用于未来参考 |

这可以防止作者将所有反馈视为强制性，并浪费时间在可选建议上。

**优先考虑重要的事情。** 按杠杆顺序排列发现：正确性和安全性优先，然后是结构性回归和遗漏的简化，然后是其他所有内容。不要将一个真实问题埋在装饰性小问题下面——几个有说服力的评论比一个长列表更好。如果你有一个结构性问题，十个小问题，结构性问题就是审查。

### 第五步：验证验证

检查作者的验证故事：

```
- 运行了哪些测试？
- 构建是否通过？
- 是否进行了手动测试？
- 是否有 UI 变更的屏幕截图？
- 是否有前后比较？
```

## 多模型审查模式

使用不同的模型进行不同的审查视角：

```
模型 A 编写代码
    │
    ▼
模型 B 审查正确性和架构
    │
    ▼
模型 A 解决反馈
    │
    ▼
人类做出最终决定
```

这可以捕获单个模型可能遗漏的问题——不同的模型有不同的盲点。

**审查代理的示例提示：**
```
审查这个代码变更的正确性、安全性和遵循项目规范。规范说 [X]。变更应该 [Y]。标记任何问题为关键、必须、可选或小问题。
```

## 死代码卫生

在任何重构或实现变更之后，检查孤儿代码：

1. 确定现在无法访问或未使用的代码
2. 明确列出
3. **在删除之前询问：** “我应该删除这些现在未使用的元素：[列表]？”？

不要留下死代码——它会使未来的读者和代理困惑。但不要在不确定的情况下默默删除。当不确定时，询问。

```
识别死代码：
- src/utils/date.ts 中的 formatLegacyDate() — 被 formatDate() 替代
- src/components/ 中的 OldTaskCard 组件 — 被 TaskCard 替代
- src/config.ts 中的 LEGACY_API_URL 常量 — 没有剩余引用
→ 这些可以安全删除吗？
```

## 审查速度

慢速审查阻止整个团队。审查的上下文切换成本低于对其他人造成的等待成本。

- **一天内回复** — 这是最大值，不是目标
- **理想节奏：** 审查请求到达后立即回复，除非深入专注编码。一个典型的变更应该在一天内完成多个审查轮次
- **优先考虑快速的个人回复** 而不是快速的最后批准。即使需要多个轮次，快速反馈也能减少挫败感
- **大变更：** 要求作者拆分它们，而不是审查一个巨大的变更集

## 处理分歧

在解决审查争议时，应用这个层次结构：

1. **技术事实和数据** 覆盖意见和偏好
2. **风格指南** 是风格问题的绝对权威
3. **软件设计** 必须根据工程原则进行评估，而不是个人偏好
4. **代码库一致性** 如果它不会降低整体健康度，是可以接受的

**不要接受“我稍后会清理它”。** 经验表明，延迟清理很少发生。在提交前要求清理，除非是真正的紧急情况。如果周围的无法在这个变更中解决，要求以自我分配的方式提交 Bug。

## 审查中的诚实

在审查代码时——无论是由你、另一个代理还是人类编写的：

- **不要 rubber-stamp。** 没有证据的“LGTM”对任何人都没有帮助。
- **不要淡化真实问题。** “这可能是一个小问题”而它是一个会打到生产的 Bug 是不诚实的。
- **尽可能量化问题。** “这个 N+1 查询将为列表中的每个项目增加 ~50ms”比“这可能很慢”更好。
- **反对有明显问题的方法。** 奉承是审查中的失败模式。如果实现有问题，直接说并提出替代方案。
- **优雅地接受覆盖。** 如果作者有完整上下文并不同意，请尊重他们的判断。评论代码，而不是人们——将个人评论重新聚焦于代码本身。

## 依赖纪律

代码审查的一部分是依赖审查：

**在添加任何依赖项之前：**
1. 现有堆栈是否解决这个问题？（通常它已经解决了。）
2. 依赖项有多大？（检查捆绑包影响。）
3. 它是否积极维护？（检查最后提交、打开的问题。）
4. 它是否有已知漏洞？（`npm audit`）
5. 许可证是什么？（必须与项目兼容。）

**规则：** 优先选择标准库和现有实用工具，而不是新的依赖项。每个依赖项都是一种负债。

**升级现有依赖项** 像任何其他代码变更一样，风险最大的升级是那些批量合并并带有消息“更新依赖项”的。用同样的纪律审查它们：

1. **阅读变更日志，而不仅仅是版本号。** Semver 是维护者可能没有遵守的承诺——一个“补丁”可能包含行为变化。对于主要升级，阅读迁移说明并找出什么会中断。
2. **每个变更一个依赖项。** 分别升级和合并它们（或小相关的组）。当批量提升破坏构建时，你失去了哪个包做了它；单个包变更使原因明显，并且还原干净。
3. **让测试决定。** 升级在 *和* 之后都由绿色套件验证，而不是“它安装了”。如果依赖项行为周围的覆盖率很薄，那差距是真正的发现——先添加测试。
4. **注意传递图。** 大多数安装的包都是没有人直接选择的。审查锁文件差异，而不仅仅是 `package.json`；一个直接的提升可能会引入几十个间接变化。
5. **保持锁文件诚实。** 提交它，审查其差异，并且永远不要手动编辑它。锁文件是实际固定要发布的东西。

对于 `npm audit` 查找的优先级和供应链风险（拼写攻击、受感染的维护者），请遵循 `security-and-hardening` 技能——这一部分涵盖升级 *工作流*，那一部分涵盖安全裁决。

```markdown

- [ ] 处理了边缘情况
- [ ] 处理了错误路径

### 可读性

- [ ] 逻辑简单

### 架构
- [ ] 遵循现有模式
- [ ] 没有不必要的耦合或依赖
- [ ] 抽象级别合适
- [ ] 重构减少了复杂性而不是转移它
- [ ] 没有特定功能的逻辑在共享模块中；文件保持在健康大小内

### 安全性
- [ ] 代码中没有密钥
- [ ] 在边界处验证了输入
- [ ] 没有注入漏洞
- [ ] 有身份验证/授权检查
- [ ] 来自外部来源的数据被视为不受信任

### 性能
- [ ] 没有 N+1 查询模式
- [ ] 没有无界操作
- [ ] 列表端点有分页

### 验证
- [ ] 测试通过
- [ ] 构建成功
- [ ] 进行了手动验证（如果适用）

### 裁决
- [ ] **批准** — 准备合并
- [ ] **请求变更** — 必须解决问题
```

## 常见理由

| 理由   | 现实   |
|------|------|
| "它工作，这足够好了" | 工作代码如果不可读、不安全或架构错误会创建复合债务。 |
| "我写了它，所以我知道它是正确的" | 作者对自己的假设视而不见。每一次变更都受益于另一双眼睛。 |
| "我们会稍后清理它" | 从不发生。审查是质量门禁——使用它。在合并前要求清理，而不是之后。 |
| "AI 生成的代码可能没问题" | AI 代码需要更多审查，而不是更少。它自信且看似合理，即使错误。 |
| "测试通过，所以它很好" | 测试是必要的，但不是充分的。它们不会捕获架构问题、安全问题或可读性问题。 |
| "重构让它更干净" | 将复杂性重新定位而不是减少它。如果读者仍然持有相同数量的概念，结构没有改进——寻找使整个分支、模式或层消失的重构，而不是重新集中相同的逻辑。 |
| "这只是添加到这个文件的一小部分" | 小差异仍然可能将文件推过健康的边界——将分支拧到无关的流程上。判断结果结构，而不是差异大小。 |
| "只是版本升级" | 升级是行为变化，你没有写。阅读变更日志；semver 不保证没有中断。 |
| "我会一次性提交所有内容来节省时间" | 批量升级破坏构建隐藏了哪个包做了它。每个依赖项一个变更使原因和还原干净。 |

## 信号旗

- 没有审查就合并的 PR
- 只检查测试是否通过的审查（忽略其他轴）
- 没有实际审查的“LGTM”
- 没有安全审查的安全敏感变更
- 太大无法正确审查的 PR（拆分它们）
- Bug 修复 PR 没有回归测试
- 审查评论没有严重性标签——不清楚什么是必须的，什么是可选的
- 接受“我稍后会修复它”——它永远不会发生
- 重构将代码移动到不减少读者必须持有的概念数量的地方
- 变更增长了一个已经很大的文件，而不是分解它
- 新的条件语句散布到无关的代码路径中（缺少抽象）
- 定制的辅助函数复制了现有的规范一个，或者功能逻辑放在了共享模块中
- 批量“升级依赖项”PR 没有变更日志审查，也没有按包隔离
- 锁文件更改被手动编辑、未提交或未经审查其差异合并
