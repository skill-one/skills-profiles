# 怀疑驱动开发

## 概述

自信的答案并非正确的答案。长时间的投入会积累背景信息，悄无声息地将假设转化为“事实”，而无人察觉。怀疑驱动开发是一种在产生任何非平凡的输出之前，创造出一位以**证伪**而非**证实**为偏见的全新背景信息审查者的纪律。

这不是`/review`。`/review`是对一个已完成工件的评价。这是一种飞行中的姿态：非平凡的决策在课程纠正仍然廉价时接受交叉审查。

## 何时使用

当至少符合以下条件之一时，决策为**非平凡**：

- 引入或修改分支逻辑
- 跨越模块或服务边界
- 声明类型系统或编译器无法验证的属性（线程安全、幂等性、顺序、不变性）
- 其正确性取决于未来读者无法看到的背景信息
- 其影响范围是不可逆的（生产部署、数据迁移、公共 API 更改）

在以下情况应用该技能：

- 即将做出不确定性下的架构决策
- 即将提交非平凡代码
- 即将声称一个非显而易见的事实（“这是安全的”、“这是可扩展的”、“这符合规范”）
- 正在处理自己不完全理解的代码

**何时不使用**：

- 机械操作（重命名、格式化、文件移动）
- 遵循一个清晰、无歧义的用户指令
- 阅读或总结现有代码
- 单行更改且正确性显而易见
- 纯工具操作（运行测试、列出文件）
- 用户明确要求速度而非验证

如果你对每个按键都怀疑，你将什么也发不出。该技能仅适用于上述定义的非平凡决策。

## 加载约束

此技能设计用于**主会话协调者**，其中步骤 3（怀疑，详细说明如下）可以生成一个全新背景信息审查者。

- **不要将此技能添加到角色的`skills:`前端字段。** 一个遵循步骤 3 的角色会生成另一个角色——这是`../../references/orchestration-patterns.md`明确禁止的编排反模式（“角色不应调用其他角色”）。
- **如果你发现自己从子代理上下文中应用此技能**（在 Claude Code 中，子代理无法生成嵌套子代理）：首选路径是向用户显示怀疑驱动开发无法运行嵌套，并让主会话处理。作为最后的手段，仅存在降级的自我提问回退——将工件 + 合同重写为带有与先前推理的硬心理分界符的新自我提示，并执行步骤 1-5。这**不是全新背景信息审查**（你带着自己的背景信息），因此将结果标记为降级，并在用户可联系时优先升级。

## 流程

应用该技能时复制此清单：

```
怀疑周期：
- [ ] 步骤 1：声明 — 写下声明 + 为什么重要
- [ ] 步骤 2：提取 — 隔离工件 + 合同，去除推理
- [ ] 步骤 3：怀疑 — 使用对抗性提示调用全新背景信息审查者
- [ ] 步骤 4：协调 — 将每个发现与工件文本分类
- [ ] 步骤 5：停止 — 满足停止条件（平凡发现、3 个周期或用户覆盖）
```

### 步骤 1：声明 — 揭示所持立场

用两到三行命名决策：

```
声明："新的缓存层在规范中描述的读重负载下是线程安全的。"
为什么重要：这里发生竞争会损坏用户数据，在 QA 中难以检测。
```

如果你无法如此简洁地写出声明，你只有感觉，没有决策。在审查它之前先揭示它。

### 步骤 2：提取 — 最小的可审查单元

全新背景信息审查者需要**工件**和**合同**，而不是过程。

- 代码：差异或函数——不是整个文件
- 决策：3-5 句话的提议加上它必须满足的约束条件
- 断言：声明加上据称支持它的证据（与步骤 1 的声明块区分开来，该块是审查者正在审查的协调者的假设）

去除你的推理。如果你传递结论，你将得到对你结论的验证。单元必须足够小，以便审查者可以在一次阅读中将其保持在脑海中——如果是一个 500 行的 PR，请先进行分解。

### 步骤 3：怀疑 — 调用全新背景信息审查者

审查者的提示**必须是对抗性的**。措辞决定答案。

```
对抗性审查。找出此工件的问题所在。
假设作者是过于自信的。寻找：
- 未声明的假设
- 未处理的边缘情况
- 隐藏的耦合或共享状态
- 合同可能被违反的方式
- 可能会破坏现有约定的方式
- 意外输入下的故障模式

不要验证。不要总结。找出问题，或者在彻底检查后明确声明无法找到任何问题。

工件：<粘贴工件>
合同：<粘贴合同>
```

**仅传递工件 + 合同。不要传递声明。** 将审查者传递你的结论会使其倾向于同意。审查者必须独立确定工件是否满足合同。

在 Claude Code 中，`agents/` 中的基于角色的审查者设计上具有隔离的上下文，并且可用于此处——请参阅 `agents/` 获取花名册和按域匹配。

**上述对抗性提示优先于角色的默认响应形状。** 像 `code-reviewer` 这样的角色被编写为生成包含优缺点的平衡裁决；怀疑驱动需要仅输出问题的输出。将对抗性提示逐字粘贴到调用中以覆盖角色的默认值。如果角色的响应形状无法干净地覆盖，则回退到带有对抗性提示的通用子代理。

#### 跨模型升级

单个模型审查者与原始作者共享盲点——一个更冷、不同架构的模型可以捕捉它们。怀疑驱动已经针对非平凡决策是自愿的，所以在该范围内提供跨模型是技能价值的一部分，而不是可选的摩擦。

**交互式会话：始终提供。永远不要无声地跳过。**

**步骤 1：询问用户**

在上述步骤 3 的单模型审查完成后，但在协调之前，暂停并询问：

> *"单模型审查完成。需要跨模型第二意见吗？选项：Gemini CLI、Codex CLI、手动外部审查（你将其粘贴到其他地方）、或跳过。"**

这个问题在每次交互式怀疑周期中都是强制性的——即使对于感觉风险较低的工件也是如此。用户——而不是代理——决定成本是否值得。代理的工作是展示选择。

**步骤 2：如果用户选择 CLI —— 验证，然后调用**

1. 检查工具是否在 PATH 中（`which gemini`，`which codex`）。
2. 在传递完整提示之前测试它是否工作（`gemini --version` 或等效）——一个过时的或损坏的二进制文件可能会通过 `which` 但在真实输入上失败。
3. 与用户确认确切的调用，包括所需的标志、认证和环境变量（例如，API 密钥）。实现方式不同；永远不要假设。
4. 仅传递工件 + 合同 + 对抗性提示。没有会话上下文，没有声明。
5. 注意 shell 逃逸。如果工件包含引号、`$(...)` 或反引号，请优先使用 stdin（`echo … | gemini`）或 heredoc 而不是内联 `-p "…"`。如有疑问，请要求用户在运行之前确认调用。
6. 将输出输入到步骤 4（协调）。

**永远不要将工件插入到 shell 引号参数中。** 代码、Markdown 和审查提示通常包含反引号、`$(...)` 和引号字符，这些字符要么会截断提示，要么会执行嵌入的 shell。将完整提示写入文件并通过 stdin 传递。

示例形状（验证你的安装工具的标志——语法在不同的实现和版本中不同）：

```bash
# 首先将对抗性提示 + 工件 + 合同写入临时文件。
# 然后通过 stdin 管道，以便工件中的 shell 保留字符保持惰性。

# Codex（只读沙盒阻止 CLI 写入你的工作区）：
codex exec --sandbox read-only -C <repo-path> - < /tmp/doubt-prompt.md

# Gemini ('--approval-mode plan' 是只读的；'-p ""' 触发非交互模式
# 并且提示从 stdin 读取）：
gemini --approval-mode plan -p "" < /tmp/doubt-prompt.md
```

只读沙盒是承重细节：怀疑工件本身可能包含指令（有意或无意的提示注入），否则跨模型 CLI 会执行它们针对你的工作区。

**步骤 3：如果 CLI 不可用或失败**

明确展示失败。提供：手动运行、尝试不同工具或跳过。不要无声地回退到单模型——用户应该知道跨模型没有发生。

**步骤 4：如果用户跳过**

在输出中确认跳过（*“仅使用单模型发现继续进行”*）并继续协调。跳过是好的；无声跳过是不好的。

**非交互式上下文**（CI、`/loop`、自主循环、计划运行）：

- 跨模型被**跳过**，并且跳过必须在输出中**宣布**：*"跨模型跳过：非交互式上下文。*"
- **永远不要在未经明确用户授权的情况下调用外部 CLI**——这是一个承重安全属性。

跨模型增加了成本、延迟和工具脆弱性。代理在每次交互式怀疑周期中展示选择；用户决定此工件是否值得。代理的工作是展示选择，而不是限制它。

### 步骤 4：协调 — 将发现回折

审查者的输出是数据，不是裁决。**你仍然是协调者。** 在对每个发现进行分类之前，重新阅读工件文本—— rubber-stamping 审查者是忽略它的相同失败模式。

对于每个发现，按此**优先级顺序**（第一个匹配的类别胜出）进行分类：

1. **合同误读**——审查者特别指出你提供的合同不明确或不完整。首先修复合同，然后在下一个周期重新分类。
2. **有效且可操作**——真实问题需要更改工件。更改它，重新循环。
3. **有效权衡**——问题是真实的，但修复成本超过接受成本。明确记录权衡，以便用户看到。
4. **噪音**——审查者指出的是在审查者没有背景信息的情况下实际上是正确的东西。记录它，继续前进，并询问：将此背景信息添加到合同是否可以防止虚假标志？

全新的审查者可能会因为缺乏背景信息而错误。不要因为它是“全新的”就推迟。

### 步骤 5：停止 — 有界循环，非递归

在以下情况下停止：

- 下一个周期只返回平凡或已考虑过的发现，**或**
- 3 个周期完成（升级到用户，不要独自进行第四个），**或**
- 用户明确说“发布它”

如果在 3 个周期后审查者仍然提出实质性问题，工件可能尚未准备好。向用户展示这一点——3 个未解决的周期是关于工件的信息，而不是继续循环的理由。

如果 3 个周期“明显不足”，因为工件很大：工件太大——返回步骤 2 并分解。不要提高界限。

## 常见合理化

| 合理化 | 现实 |
|---|---|
| “我自信，跳过怀疑步骤” | 对新问题的正确性，自信与正确性相关性差。确定性的时刻正是盲点隐藏的时刻。 |
| “生成审查者很昂贵” | 在生产中调试一个错误的提交更昂贵。检查是有界的；错误不是。 |
| “审查者只会吹毛求疵” | 只有在未限定的前提下。将提示限制为“会导致此工件在合同下失败的发现”。 |
| “我会在最后用`/review`进行怀疑” | `/review` 是事后 PR 裁决；怀疑驱动是每项决策的飞行中状态。两者都使用。 |
| “如果我怀疑每一步，我永远也发不出” | 该技能仅适用于非平凡决策，而不是每个按键。重新阅读“何时不使用”。 |
| “两个意见总是比一个更好” | 不当。当第二个具有较少背景信息并产生噪音时。协调，而不是推迟。 |
| “审查者不同意所以我错了” | 审查者缺乏你的背景信息——不同意是信息，不是裁决。重新阅读工件，分类，然后决定。 |
| “跨模型总是更好” | 跨模型捕捉单个模型与自己共享的盲点，但它增加了成本和工具脆弱性。在每次交互式怀疑周期中都提供它——用户决定此工件是否值得。代理的工作是展示选择，而不是限制它。 |
| “用户说了一次是，所以我可以继续调用 CLI” | 每个调用都是其自己的授权。工件、提示和标志在调用之间会改变——在每次运行之前都与用户确认确切的命令。实现方式不同；永远不要假设。 |

## 信号灯

- 为单行重命名或格式化更改生成全新背景信息审查者
- 在未重新阅读工件文本的情况下将审查者输出视为权威
- 超过 3 个周期而未升级到用户
- 使用“这个好吗？”而不是“找出问题”提示审查者
- 在时间压力下对高风险决策跳过怀疑
- 在未更改的工件上重新生成全新背景信息（你会得到相同的发现；你在拖延）
- **怀疑剧场（可检查信号）**：在两个或多个周期中，审查者提出了实质性发现，零发现被分类为可操作。你在验证，而不是怀疑。停止并升级。
- 仅在提交后怀疑——那是 `/review`，不是怀疑驱动开发
- 在未经确认工具存在、配置正确且接受确切语法的用户的情况下硬编码外部 CLI 调用
- **在交互式怀疑周期中无声地跳过跨模型。** 即使不推荐它，也必须向用户展示提议。跳过是好的；无声跳过是不好的。
- 当外部 CLI 出错或缺失时无声回退——明确展示失败并让用户重定向
- 从审查者的输入中去除合同
- 将声明传递给审查者（会使其倾向于同意）

## 与其他技能的交互

- **`code-review-and-quality` / `/review`**：互补的。`/review` 是事后 PR 裁决；怀疑驱动是飞行中每项决策。两者都使用。
- **`source-driven-development`**：SDD 验证关于框架的*事实*与官方文档。怀疑驱动验证*你对工件的推理*。SDD 检查 API 是否存在；怀疑驱动检查你是否正确使用它符合合同。
- **`test-driven-development`**：TDD 的 RED 步骤是具体的怀疑——失败的测试是证伪尝试。当 TDD 适用时，那个失败的测试*就是行为声明的怀疑步骤*。
- **`debugging-and-error-recovery`**：当审查者提出真实故障模式时，进入调试技能定位并修复。
- 仓库编排规则（`../../references/orchestration-patterns.md`）：此技能从主会话编排。调用另一个角色的角色是反模式 B——见加载约束上述。

## 验证

应用怀疑驱动开发后：

- [ ] 每个非平凡决策（根据上述定义）在生效前都明确声明为 CLAIM
- [ ] 每个非平凡工件至少进行一次全新背景信息审查（由 TDD 的 RED 步骤产生的失败测试满足此条件，根据与其他技能的交互）
- [ ] 审查者收到了工件 + 合同——不是声明，不是你的推理
- [ ] 审查者的提示是对抗性的（“找出问题”），而不是验证性的（“它好吗”）
- [ ] 发现与工件文本分类（不是 rubber-stamping）使用优先级：合同误读 / 可操作 / 权衡 / 噪音
- [ ] 满足停止条件（平凡发现、3 个周期或用户覆盖）
- [ ] 在交互模式下，跨模型被**明确提供给用户**（无论工件风险如何）并且响应在输出中确认
- [ ] 在非交互模式下，跨模型被跳过并且跳过被宣布
- [ ] 任何外部 CLI 调用都由 PATH 检查、工作二进制测试、与用户的语法确认和明确授权precede
