# 代码调试

通过结构化的错误分类和修复策略，系统性地调试实验代码。

## 输入

- `$0` — 错误信息、stderr输出或包含问题的代码文件
- `$1` — 可选：产生错误的代码

## 参考文献

- 调试模式和状态机：`~/.claude/skills/code-debugging/references/debug-patterns.md`

## 工作流程

### 第1步：分类错误

| 分类 | 示例 | 严重程度 |
|------|------|----------|
| SyntaxError | 无效语法、缩进错误 | 低 |
| ImportError | 缺少模块、名称错误 | 低 |
| RuntimeError | 除零错误、形状不匹配 | 中 |
| TimeoutError | 死循环、运行过慢 | 中 |
| OutputError | 缺少文件、格式错误 | 中 |
| LogicError | 结果错误、0%准确率 | 高 |

### 第2步：分析根本原因
1. 阅读错误回溯信息（如果截断，则读取最后1500个字符）
2. 确定导致错误的精确行和变量
3. 检查常见模式：
   - 设备不匹配（CPU与GPU张量）
   - 矩阵运算中的形状不匹配
   - 缺少数据归一化
   - 索引中的"Off-by-one"错误
   - 任务类型不匹配的损失函数

### 第3步：应用修复策略

**对于语法/导入错误**：直接修复，单次尝试
**对于运行时错误**：修复后重跑，最多4次重试
**对于逻辑错误**：反思方法，考虑替代方案
**对于超时**：减小数据集大小、优化瓶颈、添加提前停止

### 第4步：反思和预防
修复后：
1. 解释错误发生的原因
2. 确定导致错误的行
3. 按行描述修复方法
4. 记录未来代码中应避免的模式

## 修复策略状态机

```
阶段0（首次尝试）→ 将代码作为新问题重新提交
阶段1（第二次尝试）→ 根据严重程度决定是重新提交还是保留
阶段2（第三次尝试）→ 如果仍然失败，则从零开始重新生成
```

## 规则

- 优先选择最小化的针对性修改，而非全文重写
- 最多4-5次修复尝试后，再改变方法
- 始终将长错误输出截断为最后1500个字符
- 修复后，验证修复是否引入新错误
- 保留错误历史，避免重复犯错
- 如果准确率为0%：首先检查准确率计算，然后检查数据管道
