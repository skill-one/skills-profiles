# 令牌效率专家

这项技能为所有项目中的 Claude 代码使用提供令牌优化策略，以实现成本效益。这些指南有助于在保持高质量协助的同时最小化令牌消耗。

## 核心原则

**除非用户明确要求详细输出或完整文件内容，否则始终默认遵循这些优化指南。**

默认假设：**用户更喜欢高效、经济实惠的协助。**

---

## 模型选择策略

**为优化成本和性能而选择合适的模型：**

### Opus - 用于学习和深入理解

**在以下情况下使用 Opus：**
- 学习新的代码库 - 理解架构、代码结构、设计模式
- 广泛探索 - 识别关键文件、理解仓库组织
- 深入分析 - 分析复杂算法、性能优化
- 阅读和理解 - 在进行更改之前需要理解现有代码时
- 非常复杂的调试 - 只有当 Sonnet 无法解决时或问题是架构性问题时

### Sonnet - 用于常规开发任务（默认）

**使用 Sonnet（默认）用于：**
- 编写代码、编辑和修复、调试、测试、文档、部署、一般性问题

**典型会话模式：**
1. **先用 Opus** - 花费 10-15 分钟理解代码库（一次性投资）
2. **切换到 Sonnet** - 用于所有实现、调试和常规工作
3. **再回到 Opus** - 只有在明确需要深入架构理解时

**节省：相对于全部使用 Opus 的成本节省约 50%。**

## 技能和令牌效率

**误区：** 在 `.claude/skills/` 中拥有许多技能会增加令牌使用。

**现实：** 技能使用**渐进式披露** - Claude 在会话开始时只看到技能描述（4 个技能约 155 个令牌）。只有在激活时才会加载完整技能内容。

**安全地将多个技能链接到项目中。** 令牌浪费来自于不必要地读取大文件，而不是拥有可用的技能。

## 令牌优化规则（快速参考）

### 1. 使用安静/最小输出模式
默认使用 `--quiet`, `-q`, `--silent` 标志。只有在用户明确要求时才使用详细输出。

### 2. 绝不读取整个日志文件
始终在读取前进行过滤：`tail -100`, `grep -i "error"`, 特定时间范围。

### 3. 首先检查轻量级来源
在读取大文件之前，检查 `git status --short`, `package.json`, `requirements.txt`。

### 4. 使用 Grep 而不是读取文件
使用 Grep 工具搜索特定内容，而不是读取整个文件。

### 5. 限制文件读取
使用偏移量和限制参数。首先使用 `wc -l` 检查文件大小。

### 6. 使用 Bash 命令而不是读取文件
**关键优化**用于纯转换和检查。读取文件消耗令牌；Bash 命令不消耗。

| 操作 | 低效 | 高效 |
|-------|------|------|
| 复制文件 | 读取 + 写入 | `cp source dest` |
| 替换文本 | 读取 + 编辑 | `sed -i '' 's/old/new/g' file` |
| 追加 | 读取 + 写入 | `echo "text" >> file` |
| 删除行 | 读取 + 写入 | `sed -i '' '/pattern/d' file` |
| 合并文件 | 读取 + 读取 + 写入 | `cat file1 file2 > combined` |
| 计算行数 | 读取文件 | `wc -l file` |
| 检查内容 | 读取文件 | `grep -q "term" file` |
| 检查 JSON | 读取 + 解析 | `python3 -c "import json; ..."` 或 `jq` |

**何时打破此规则 — 优先选择读取 + 编辑：**
- **代码编辑**（`.py`, `.js`, `.xml`, `.ga`, `.tsx` 等） — 用户受益于可审查的 diff。读取小文件的成本值得审查。
- **验证重要** — 当语法错误会破坏文件（工作流 JSON、配置模式）。
- **交互式审查** — 用户明确希望看到更改内容。

正确的框架是**基于范围**（见下一节），而不是“始终使用 Bash”或“始终读取 + 编辑”。有关更详细的策略和模式，请参阅 [strategies.md](strategies.md)。

### 7. 过滤命令输出
限制范围：`head -50`, `find . -maxdepth 2`, `tree -L 2`。

### 8. 提供结构化摘要，而不是直接输出
提供目录内容、代码结构、命令输出的结构化摘要。

### 9. 使用 Head/Tail 处理大输出
`head -100`, `tail -50`, 从中间采样 `head -500 | tail -100`。

### 10. 高效使用 JSON/数据工具
提取特定字段：`jq '.metadata'`, `jq 'keys'`。对于 CSV：`head -20`, `wc -l`。

### 11. 优化代码阅读
先获取概览（查找、grep 类/函数），只读取结构，搜索特定代码，只读取相关部分。

### 12. 使用任务工具进行探索性搜索
使用 Task/Explore 子代理进行广泛的代码库探索。与直接多文件探索相比，节省 70-80% 的令牌。

### 13. 高效的科学文献搜索
并行批量 3-5 个相关搜索。立即保存结果。记录“未找到”的项目。

有关详细策略、Bash 模式和大量示例，请参阅 [strategies.md](strategies.md)。

## 基于范围的工具选择

在 Bash 和读取 + 编辑之间的选择不是仅关于令牌成本 — 它是关于用户是否受益于看到更改。将工具与工作范围匹配：

| 范围 | 优先工具 | 原因 |
|------|----------|------|
| 只读结构化数据检查（JSON、YAML、JSONL、大日志） | `python3 -c`, `jq`, `grep`, `awk` | Bash 输出可过滤；没有误编辑源文件的风险。内联 `python3 -c` 用于 JSON 检查比读取 + 解析更快、更便宜。 |
| 代码的本地编辑（`.py`, `.js`, `.xml`, `.ga`, `.tsx`） | 读取 + 编辑 | 用户看到可审查的 diff；早期捕获语法错误。 |
| 大数据文件转换（CSV、大 JSON、BAM 衍生的 TSV） | `sed`, `awk`, `python3` 脚本 | 读取整个文件将消耗数千个令牌。 |
| 从头开始创建新文件 | 写入工具 | 单次往返；Bash heredocs 添加不了价值且不可审查。 |

**何时打破此规则 — 优先选择读取 + 编辑：**

## 文件操作决策树

**问自己：**
1. **创建新文件？** -> 写入工具
2. **低成本操作**（< 100 行输出）？ -> 直接使用 Claude 上下文
3. **修改代码文件**（.py, .js, .xml）？ -> 读取 + 编辑（始终）
4. **修改小数据文件**（< 100 行）？ -> 读取 + 编辑是合适的
5. **修改关键数据**（基因组统计、丰富表格）？ -> bash + 日志文件
6. **修改大数据文件？** -> sed/awk
7. **复制/移动文件？** -> cp/mv

## 何时覆盖这些指南

**在以下情况下覆盖效率规则：**

1. **用户明确要求完整输出**（“显示整个日志文件”）
2. **过滤输出缺少必要上下文**（错误引用缺少行号）
3. **文件已知很小**（< 200 行）
4. **学习代码结构和架构** - 优先考虑理解而不是效率

**在学习模式下：**
- 完全读取 2-5 个关键文件以建立理解
- 使用 grep 查找其他相关示例
- 摘要跨多个文件发现的模式
- 学习阶段后，返回高效模式进行实现
- 有关详细学习模式策略，请参阅 [learning-mode.md](learning-mode.md)

**在 1-3 的情况下，向用户解释令牌成本并首先提供过滤视图。**

## 总结

**核心格言：正确的模型。正确的工具。先过滤。有选择地读取。智能地摘要。**

**模型选择（最高影响）：**
- **学习/理解** -> 使用 Opus
- **开发/调试/实现** -> 使用 Sonnet（默认）

**工具选择（主要优化）：**
- **创建新文件** -> 直接使用写入工具
- **低成本操作**（< 100 行） -> 直接使用 Claude 上下文
- **修改代码文件** -> 读取 + 编辑（始终）
- **修改小数据文件**（< 100 行） -> 读取 + 编辑是合适的
- **修改大数据文件** -> bash 命令（99%+ 节省）
- **修改关键数据** -> bash 命令 + 日志文件
- **复杂编辑** -> 读取 + 编辑工具

**次要规则：**
- 在读取前过滤（grep、head、tail）
- 需要时限制读取
- 摘要而不是显示原始输出
- 使用安静模式命令
- 策略性文件选择用于学习

通过遵循这些指南，用户可以从他们的 Claude 订阅中获得 5-10 倍的价值，同时保持高质量的协助。
