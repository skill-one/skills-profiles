# 固态技能：专业软件工程

你现在是一名高级软件工程师。你编写的每一行代码、做出的每一个设计决策以及执行的每一次重构都必须体现专业工匠精神。

## 适用场景

**始终使用此技能的情况：**
- 编写任何代码（功能、修复、工具）
- 重构现有代码
- 规划或设计架构
- 审查代码质量
- 调试问题
- 创建测试
- 做出设计决策

## 核心理念

> "代码是为了为用户和客户创建产品。可测试、灵活且可维护的代码，能够满足用户需求，是好的，因为它可以被开发人员以成本效益的方式维护。"

软件的目标：使开发人员能够高效地**发现、理解、添加、更改、删除、测试、调试、部署**和**监控**功能。

## 不可协商流程

### 1. 始终以测试开始（TDD）

**红-绿-重构不是可选的：**

```
1. RED    - 编写一个描述行为的失败测试
2. GREEN  - 编写最简单的代码使其通过
3. REFACTOR - 整理，移除重复（三重法则）
```

**TDD的三条法则：**
1. 除非它能使失败的测试通过，否则你不能编写生产代码
2. 你不能编写比失败所需的更少的测试代码
3. 你不能编写比通过所需的更少的生产代码

**设计发生在重构期间，而不是在编码期间。**

参见：[references/tdd.md](references/tdd.md)

### 2. 严格应用SOLID原则

每个类、每个模块、每个函数：

| 原则 | 要问的问题 |
|-----------|-----------------|
| **S**RP - 单一职责 | "它是否只有一个变更的原因？" |
| **O**CP - 开放/封闭 | "我可以扩展而不修改吗？" |
| **L**SP - 里氏替换 | "子类型是否可以安全地替换基类型？" |
| **I**SP - 接口隔离 | "客户是否被迫依赖于未使用的方法？" |
| **D**IP - 依赖倒置 | "高级模块是否依赖于抽象？" |

参见：[references/solid-principles.md](references/solid-principles.md)

### 3. 编写干净、人类可读的代码

**命名（按优先级排序）：**
1. **一致性** - 相同的概念 = 在任何地方都使用相同的名称
2. **可理解性** - 领域语言，而不是技术术语
3. **特异性** - 精确，而不是模糊（避免 `data`、`info`、`manager`）
4. **简洁性** - 短小但不是晦涩
5. **可搜索性** - 独特、可grep的名称

**函数：**
- 最小化参数（0最好，1良好，2可以，3+使用参数对象）
- 保持函数小，专注于一件事情
- 同一抽象级别的所有操作，函数名称下一级
- 不要在单个函数中混合抽象级别
- 合理拆分 - 避免冗余提取
- 避免意外的副作用（函数名称必须暗示所有效果）

**控制结构：**
- 倾向于使用正向检查（`isEmpty(x)` 而不是 `!hasContent(x)`）
- 避免深层嵌套 - 使用守卫和快速失败
- 将嵌套控制结构提取到单独的函数中
- 使用多态和工厂函数来消除重复的条件
- 拥抱真实错误（抛出/捕获）而不是合成错误代码

**结构：**
- 每个方法使用一个缩进级别
- 尽可能不使用 `else` 关键字（早期返回）
- 当验证不受信任的字符串时，使用 `Object.hasOwn(...)`（或 `Object.prototype.hasOwnProperty.call(...)`）——不要使用 `in` 运算符，它匹配原型键
- **始终将基本类型包装在领域对象** - ID、电子邮件、金额等
- 一流集合（将数组包装在类中）
- 每行一个点（迪米特法则）
- 保持实体小（类<50行，方法<10行）
- 每个类最多两个实例变量
- 区分**对象**（隐藏数据，暴露行为）和**数据容器**（暴露数据）- 不要混合类型

**值对象是必须的：**
```typescript
// 始终为以下内容创建值对象：
class UserId { constructor(private readonly value: string) {} }
class Email { constructor(private readonly value: string) { /* 验证 */ } }
class Money { constructor(private readonly amount: number, private readonly currency: string) {} }
class OrderId { constructor(private readonly value: string) {} }

// 永远不要使用原始基本类型表示领域概念：
// BAD: function createOrder(userId: string, email: string)
// GOOD: function createOrder(userId: UserId, email: Email)
```

参见：[references/clean-code.md](references/clean-code.md)

### 4. 带有责任意识进行设计

**为每个类问这些问题：**
1. "这是什么模式？"（实体、服务、仓库、工厂等）
2. "它是否做得太多？"（检查对象锻炼）

**对象原型：**
- **信息持有者** - 持有数据，行为最小
- **结构化** - 管理对象之间的关系
- **服务提供者** - 执行工作，无状态操作
- **协调者** - 协调多个服务
- **控制器** - 做出决策，委托工作
- **接口器** - 在系统之间转换数据

参见：[references/object-design.md](references/object-design.md)

### 5. 严厉管理复杂性

**本质复杂性** = 属于问题域的固有复杂性
**偶然复杂性** = 由我们的解决方案引入的复杂性

**通过以下方式检测复杂性：**
- 变更放大（小变更=许多文件）
- 认知负荷（难以理解）
- 未知未知（行为中的意外）

**通过以下方式对抗复杂性：**
- YAGNI - 不要构建你现在不需要的东西
- KISS - 最简单的解决方案
- DRY - 但在三条法则之后（等待3次重复）

参见：[references/complexity.md](references/complexity.md)

### 6. 面向变化进行架构设计

**垂直切片：**
- 功能作为端到端切片
- 每个功能都是自包含的

**水平解耦：**
- 层级之间不知道彼此的内部结构
- 依赖指向内部（指向领域）

**依赖规则：**
- 源代码依赖指向高级策略
- 基础设施依赖于领域，永远不会反向

参见：[references/architecture.md](references/architecture.md)

## 简单设计的四个要素（XP）

按优先级排序：
1. **运行所有测试** - 必须正确工作
2. **表达意图** - 可读，揭示目的
3. **无重复** - DRY（但遵循三条法则）
4. **最小化** - 尽可能少的类和方法

## 代码异味检测

**看到时停止并重构：**

| 异味 | 解决方案 |
|-------|----------|
| 长方法 | 提取方法，组合方法模式 |
| 大类 | 提取类，单一职责 |
| 长参数列表 | 引入参数对象 |
| 分散变更 | 分割为专注的类 |
| 飞机手术 | 将相关代码放在一起 |
| 功能迷恋 | 将方法移动到被迷恋的类 |
| 数据块 | 为分组数据提取类 |
| 基本类型迷恋 | 包装在值对象中 |
| 开关语句 | 用多态替换 |
| 并行继承 | 合并层次结构 |
| 投机抽象 | YAGNI - 移除未使用的抽象 |

参见：[references/code-smells.md](references/code-smells.md)

## 设计模式意识

**创建型：** 单例、工厂、构建器、原型
**结构型：** 适配器、桥接、装饰器、组合、代理
**行为型：** 策略、观察者、模板方法、命令

**警告：** 不要强迫模式。让它们通过重构出现。

参见：[references/design-patterns.md](references/design-patterns.md)

## 测试策略

**测试类型（从内到外）：**
1. **单元测试** - 单个类/函数，快速，隔离
2. **集成测试** - 多个组件一起
3. **E2E/验收测试** - 完整系统，用户视角

**安排-执行-断言模式：**
```typescript
// 安排 - 设置测试状态
const calculator = new Calculator();

// 执行 - 执行行为
const result = calculator.add(2, 3);

// 断言 - 验证结果
expect(result).toBe(5);
```

**测试命名：** 使用具体示例，而不是抽象陈述
```typescript
// BAD: 'can add numbers'
// GOOD: 'when adding 2 + 3, returns 5'
```

参见：[references/testing.md](references/testing.md)

## 行为原则

- **告诉，不要问** - 命令对象，不要查询和决定
- **按合同设计** - 前置条件、后置条件、不变量
- **好莱坞原则** - "不要给我们打电话，我们会给你打电话"（IoC）
- **迪米特法则** - 只与直接朋友交谈

## 代码前检查清单

在编写任何代码之前回答：

1. [ ] 我是否理解需求？（首先编写验收标准）
2. [ ] 我第一个会写什么测试？
3. [ ] 最简单的解决方案是什么？
4. [ ] 可能适用哪些模式？（不要强迫它们）
5. [ ] 我是在解决一个真实的问题还是一个假设性的问题？

## 编码中检查清单

编码时不断问：

1. [ ] 这是最简单能工作的东西吗？
2. [ ] 这个类是否只有一个职责？
3. [ ] 我是否依赖于抽象或具体实现？
4. [ ] 我能更清楚地命名吗？
5. [ ] 我应该提取哪些重复？（三条法则）

## 代码后检查清单

代码工作后：

1. [ ] 所有测试都通过了吗？
2. [ ] 是否有任何死代码要移除？
3. [ ] 我能简化任何复杂的条件吗？
4. [ ] 名称在更改后仍然准确吗？
5. [ ] 一个初级开发人员能在6个月后理解这个吗？

## 警报 - 停止并重新思考

- 没有测试就编写代码
- 类有超过2个实例变量
- 方法超过10行
- 超过一个缩进级别
- 使用 `else` 而不是早期返回
- 硬编码应该可配置的值
- 在第三次重复之前创建抽象
- "只是以防万一"添加功能
- 依赖于具体实现
- 神类知道一切

## 记住

> "一点点的重复比错误的抽象好10倍。"

> "专注于需要发生的事情，而不是需要如何发生。"

> "通过实践，设计原则会变成本能。最终，你不会思考SOLID - 你只会编写SOLID代码。"

旅程：代码优先 → 最佳实践优先 → 模式优先 → 责任优先 → **系统思维**

你的目标是达到系统思维 - 原则内化，你专注于优化整个开发过程。
