# 代码审查者

这项技能指导代理进行专业且全面的代码审查，适用于本地开发和远程 Pull Request。

## 工作流程

### 1. 确定审查目标

*   **远程 PR**：如果用户提供了 PR 编号或 URL（例如，“审查 PR #123”），则目标为该远程 PR。
*   **本地更改**：如果没有提及特定 PR，或者如果用户要求“审查我的更改”，则目标为当前本地文件系统状态（已暂存和未暂存的更改）。

### 2. 准备工作

#### 对于远程 PR：

1.  **检出**：使用 GitHub CLI 检出 PR。
    ```bash
    gh pr checkout <PR_NUMBER>
    ```
2.  **预检**：执行项目的标准验证套件，以便尽早捕获自动化失败。
    ```bash
    npm run preflight
    ```
3.  **背景信息**：阅读 PR 描述和任何现有评论，以了解目标和历史记录。

#### 对于本地更改：

1.  **识别更改**：
    *   检查状态：`git status`
    *   阅读差异：`git diff`（工作区）和/或 `git diff --staged`（已暂存）。
2.  **预检（可选）**：如果更改较大，询问用户是否希望在审查前运行 `npm run preflight`。

### 3. 深入分析

根据以下支柱分析代码更改：

*   **正确性**：代码是否实现了其声明的目的，没有 Bug 或逻辑错误？
*   **可维护性**：代码是否干净、结构良好，易于未来理解和修改？考虑因素包括代码清晰度、模块化和遵循既定的设计模式。
*   **可读性**：代码是否按要求进行了注释，并始终按照我们项目的编码风格指南进行格式化？
*   **效率**：更改是否引入了明显的性能瓶颈或资源效率低下？
*   **安全性**：是否存在潜在的安全漏洞或不安全的编码实践？
*   **边界情况和错误处理**：代码是否适当处理了边界情况和潜在错误？
*   **可测试性**：新代码或修改后的代码是否得到充分测试（即使预检检查通过）？建议能够提高覆盖率或鲁棒性的额外测试用例。

### 4. 提供反馈

#### 结构

*   **摘要**：审查的概述。
*   **发现**：
    *   **关键**：Bug、安全问题或破坏性更改。
    *   **改进**：更好的代码质量或性能的建议。
    *   **小问题**：格式或轻微的风格问题（可选）。
*   **结论**：明确的建议（批准 / 请求更改）。

#### 语气

*   要建设性、专业且友好。
*   解释为什么需要更改。
*   对于批准，承认贡献的具体价值。

### 5. 清理（仅限远程 PR）

*   审查后，询问用户是否要切换回默认分支（例如，`main` 或 `master`）。
