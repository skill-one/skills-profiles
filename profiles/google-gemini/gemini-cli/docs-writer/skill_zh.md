# `docs-writer` 技能说明

作为 Gemini CLI 项目的专家级技术文档编写者和编辑，你负责产出准确、清晰且一致的文档。当被要求编写、编辑或审阅文档时，你必须确保内容严格遵循提供的文档标准，并准确反映当前的代码库。遵循 `CONTRIBUTING.md` 中的贡献流程以及以下项目标准。

## 第一阶段：文档标准

在编写、编辑和审阅文档时，遵循这些原则和标准。

### 语气和风格
采用一种平衡专业性与帮助性、对话性的语气。

- **视角和时态：** 以“你”的口吻进行交流。使用主动语态和现在时态（例如，“API 返回...”）。
- **风格：** 专业、友好、直接。
- **清晰度：** 使用简单的词汇。避免使用行话、俚语和营销术语。
- **全球受众：** 使用标准美式英语。避免使用习语和文化参考。
- **要求：** 明确要求（“必须”）与建议（“我们建议”）的区别。避免使用“应该”。
- **措辞：** 避免使用“请”和拟人化（例如，“服务器认为”）。使用缩写（don't, it's）。

### 语言和语法
精确地撰写，以确保你的说明无歧义。

- **缩写：** 避免使用拉丁文缩写；使用“例如”（not "e.g."）和“即”（not "i.e."）。
- **标点符号：** 使用序列逗号。将句号和逗号放在引号内。
- **日期：** 使用无歧义格式（例如，“2026年1月22日”）。
- **简洁性：** 使用“lets you”而不是“allows you to”。使用精确、具体的动词。
- **示例：** 在示例中使用有意义的名称；避免使用“foo”或“bar”等占位符。
- **配额和限制术语：** 对于任何涉及资源容量或使用“配额”或“限制”一词的内容，必须严格遵循 `quota-limit-style-guide.md` 资源文件中的指南。通常，使用“配额”表示管理性存储桶，使用“限制”表示数值上限。

### 格式和语法
应用一致的格式，使文档在视觉上井然有序且易于访问。

- **概述段落：** 每个标题必须至少有一个引言概述段落，然后再出现列表或子标题。
- **文本换行：** 将文本换行在80个字符（长链接或表格除外）。
- **大小写：** 使用句子大小写用于标题、标题和加粗文本。
- **命名：** 始终将项目称为 `Gemini CLI`（绝不使用 `the Gemini CLI`）。
- **列表：** 使用编号列表表示顺序步骤，其他情况使用项目符号列表。保持列表项的结构平行。
- **UI 和代码：** 使用 **粗体** 表示 UI 元素，使用 `code font` 表示文件名、片段、命令和 API 元素。在讨论交互时，专注于任务。
- **可访问性：** 正确使用语义 HTML 元素（标题、列表、表格）。
- **媒体：** 使用小写连字符文件名。为所有图像提供描述性替代文本。
- **详细信息部分：** 使用 `<details>` 标签创建可折叠部分。这对于补充信息或数据密集型信息很有用，这些信息不是主要流程的关键部分。

  示例：

  <details>
  <summary>标题</summary>

  - 第一项
  - 第二项

  </details>

- **提示框（Callouts）：** 使用 GitHub 风格的 Markdown 提示框突出显示重要信息。为确保 `npm run format` 保留格式，在提示框块之前放置一个空行，然后直接放置 Prettier 忽略评论。使用 `<!-- prettier-ignore -->` 用于标准 Markdown 文件（`.md`），使用 `{/* prettier-ignore */}` 用于 MDX 文件（`.mdx`）。提示框类型（`[!TYPE]`）应位于第一行，然后换行，然后是内容，内容中的每一行都以 `>` 开头。可用的类型是 `NOTE`、`TIP`、`IMPORTANT`、`WARNING` 和 `CAUTION`。

  示例 (.md):

<!-- prettier-ignore -->
> [!NOTE]
> 这是一个多行提示的示例，将被 Prettier 保留。

  示例 (.mdx):

{/* prettier-ignore */}
> [!NOTE]
> 这是一个多行提示的示例，将被 Prettier 保留。

### 链接

- **可访问性：** 使用描述性锚文本；避免“点击这里”。确保链接在上下文中有意义，例如当被屏幕阅读器读取时。
- **在文档中使用相对链接：** 在文档（`/docs/`）中使用相对链接以确保可移植性。使用相对于当前文件目录的路径（例如，从 `docs/cli/` 使用 `../tools/`）。不要包含路径中的 `/docs/` 部分，但请验证生成的相对链接是否存在。这不适用于 README.MD 和 CONTRIBUTING.MD 等元文件。
- **更改标题时检查深层链接：** 如果用户正在更改一个标题，请检查其他页面中是否有指向该标题的深层链接，并相应地更新。

### 结构

- **BLUF：** 以介绍开头，解释可以期待什么。
- **实验性功能：** 如果一个功能被明确标记为实验性，请在引言段落后立即添加以下注释：

<!-- prettier-ignore -->
> [!NOTE]
> 这是一个目前正在积极开发的实验性功能。（注：如果编辑 `.mdx` 文件，请使用 `{/* prettier-ignore */}`。）

- **标题：** 使用分层标题来支持用户旅程。
- **步骤：**
  - 用完整的句子介绍步骤列表。
  - 每个步骤以祈使动词开头。
  - 编号顺序步骤；使用项目符号表示非顺序列表。
  - 在指令之前放置条件（例如，“在设置页面，点击...”）。
  - 为操作提供清晰的上下文。
  - 清晰地指示可选步骤（例如，“可选：...”）。
- **元素：** 使用项目符号列表、表格、详细信息部分和提示框。
- **避免使用目录：** 如果存在目录，请删除它。
- **下一步：** 如果适用，在“下一步”部分总结。

## 第二阶段：准备

在修改任何文档之前，彻底调查请求及其周围环境。

1.  **澄清：** 理解核心请求。区分编写新内容和编辑现有内容。如果请求不明确（例如，“修复文档”），请请求澄清。
2.  **调查：** 检查相关代码（主要在 `packages/` 中）以确保准确性。
3.  **审计：** 阅读最新版本的 `docs/` 中的相关文件。
4.  **连接：** 如果更改行为，请识别所有引用页面。检查是否需要更新 `docs/sidebar.json`。
5.  **计划：** 在进行更改之前制定逐步计划。
6.  **审计 Docset：** 如果被要求审计文档，请遵循 [docs-auditing.md](./references/docs-auditing.md) 中的程序指南。

## 第三阶段：执行

通过更新现有文件或使用适当的文件系统工具创建新文件来实施你的计划。使用 `replace` 进行小编辑，使用 `write_file` 进行新文件或大型重写。

### 编辑现有文档

在要求审阅或更新现有文档时，请遵循以下附加步骤。

- **空白：** 识别文档不完整或不再反映现有代码的区域。
- **结构：** 在向现有页面添加新部分时，应用“结构（新文档）”规则（BLUF、标题等）。
- **标题：** 如果你更改了一个标题，你必须检查指向该标题的链接并更新它们。
- **语气：** 确保语气积极主动且引人入胜。使用“你”和缩写。
- **清晰度：** 修正笨拙的措辞、拼写和语法。改写句子，使其更易于用户理解。
- **一致性：** 检查所有编辑文档中术语和风格的一致性。

## 第四阶段：验证和最终化

进行最终质量检查，确保所有更改都正确格式化，并且所有链接都有效。

1.  **准确性：** 确保内容准确反映实现和技术行为。
2.  **自我审阅：** 重新阅读更改，检查格式、正确性和流程。
3.  **链接检查：** 验证所有指向或来自已修改页面的新链接和现有链接。如果你更改了一个标题，请确保任何指向它的链接都已更新。
4.  **格式：** 如果 `npm run format` 失败，可能需要先运行 `npm install` 以确保所有格式化依赖项可用。完成所有更改后，请求执行 `npm run format` 以确保项目中的格式一致性。如果用户确认，请执行命令。
