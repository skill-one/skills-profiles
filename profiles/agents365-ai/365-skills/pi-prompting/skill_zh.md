# Pi Prompting

当 `pi:pi-companion-forwarder` 需要就非平凡的编码或调查任务向 Pi 寻求帮助时，使用此技能。

Pi 会运行用户配置的任何模型。默认情况下，此插件针对 DeepSeek V4（用于评审的 Pro 版，用于日常任务的 Flash 版）。以下指南假设提示可能会在非推理模型（Flash）或推理模型（Pro）上运行。倾向于具体、编号的检查清单，而不是抽象的指令——这两种模型类型都能可靠地遵循这些规则。

核心规则：

- 每次向 Pi 运行时优先处理一个清晰的任务。将不相关的请求拆分为单独的运行。
- 告知 Pi 完成的样子。不要假设它会推断出期望的最终状态。
- 每当不支持的猜测会降低质量时，声明明确的根基规则。
- 使用稳定的 XML 风格标签块，以便提示具有明显的内部结构。
- 保持文本简短。对于程序性工作，优先选择编号的检查清单而不是段落。

默认提示配方：

- `<task>`：具体的任务以及相关的存储库或失败上下文。包括文件路径。
- `<output_contract>`（或 `<structured_output_contract>` 用于 JSON）：确切的形状、顺序和简洁性要求。
- `<grounding_rules>`：用于评审、研究或任何可能漂移到不受支持的主张的任务。
- `<action_safety>`：用于可写任务——命名 Pi 可能接触的目录和文件类型。

何时添加额外块：

- 编码或调试：添加 `<completeness_contract>` 列出什么才算“完成”（测试通过、代码风格检查、文件已修改）。
- 评审或对抗性评审：依赖提供的 `prompts/adversarial-review.md` 和 `prompts/review.md`。不要手工制作另一个评审提示。
- 研究或推荐任务：添加一个简短的 `<sources>` 块，列出 Pi 允许咨询的内容。

如何选择提示形状：

- 当任务是评审本地 git 变更时，使用内置的 `/pi:review` 或 `/pi:adversarial-review` 命令。这些提示已经包含评审合同。
- 当任务是诊断、规划、研究或实施，并且你需要更直接地控制提示时，使用 `task`。
- 使用 `task --resume-last` 用于同一 Pi 会话的后续指令。除非方向发生了实质性变化，否则只发送增量指令，而不是重述整个提示。

工作规则：

- 优先选择明确的提示合同，而不是模糊的提示。
- 默认情况下不要提高推理级别（`--effort high`）——DeepSeek Flash 将不会受益，而 DeepSeek Pro 需要更长时间。在升级努力之前收紧提示。
- 对于工具密集型或长时间运行的任务，在 Pi 的工作笔记中请求简短的基于结果的进度更新。
- 将主张与观察到的证据锚定。如果某件事是假设，请将其标记为假设。

提示组装清单：

1. 在 `<task>` 中定义确切的任务和范围。
2. 声明输出合同——JSON、项目符号列表、普通文本——以及最大长度。
3. 决定 Pi 是否应根据自己的判断继续进行，还是因遗漏高风险细节而停止。
4. 只有在任务需要时才添加 `<grounding_rules>` 和 `<action_safety>`。
5. 在发送提示之前删除冗余指令。

## 具备子代理意识的提示

当安装 pi-subagents 时：

- 对于具有并行工作流的任务，在 `<task>` 之前添加 `<available_pi_subagents>` 块。
- 建议的代理路由：侦察员用于探索，研究员用于网络/文档，规划师用于设计，工作者用于实施，评审员用于代码评审。
- 永远不要在对抗性评审或停止评审门提示中建议子代理（这些需要确定性行为）。
- 该块是建议而不是命令——Pi 决定是否委派。
- 对于专用的多任务并行执行，使用 `/pi:parallel-rescue "task1" "task2" ...` 而不是手动提示构建。
