# agent-native-design

## 目的

这项技能有助于分析、设计和重构命令行工具，使其能够同时可靠地为**人类**、**AI代理**和**编排系统**提供服务。

它不是一项仅仅用于*使用*CLI的技能。它是一项将CLI作为**代理原生界面**进行设计和评审的技能。

这项技能专注于四个目标：

1. 使CLI的行为对AI代理可预测。
2. 使CLI的输出对人可读且可恢复。
3. 使CLI的执行对系统和编排器可管理。
4. 定义从身份验证到错误路由的完整交互循环。

---

## 何时使用此技能

当用户希望执行以下操作时，请使用此技能：

* 评估现有CLI是否对代理友好
* 重新设计CLI以更好地支持AI代理
* 将API或SDK转换为代理原生CLI
* 审查帮助输出、模式设计、退出代码或JSON合约
* 设计干运行、身份验证委托或安全边界
* 从模式生成CLI技能、文档或接口约定
* 将面向人类的CLI重构为面向机器的CLI
* 定义CLI应如何与代理运行时交互

典型的提示包括：

* "评审这个CLI，并告诉我它是否是代理原生的。"
* "为这个API设计一个AI代理可以可靠使用的CLI。"
* "重构这个工具，使stdout对机器可读，对代理更安全。"
* "帮助我定义模式内省、干运行和退出代码语义。"

## 何时不使用此技能

当用户只想执行以下操作时，请不要使用此技能：

* 帮助运行特定命令
* CLI的安装帮助
* 与界面设计无关的shell故障排除
* 通用Linux或终端教程
* 与工具无关的代理规划或内存设计
* 无任何CLI/工具层API业务逻辑评审

## 核心模型

一个代理原生CLI必须同时服务于三个受众。

### 1. 人类

需求：可读的输出、友好的错误消息、入门指导。
渠道：`stderr`、可选的`--format table`、在适当情况下使用交互式TUI。

### 2. AI代理

需求：结构化数据、稳定合约、自我描述。
渠道：`stdout`作为JSON、稳定的退出代码、模式内省、干运行预览、生成的技能/文档。

### 3. 系统/编排器

需求：委托身份验证、进程管理、确定性错误路由。
渠道：环境变量、退出代码、干运行模式、稳定的命令语义。

### 基础合约

| 渠道 | 主要受众 |
| --------- | ----------------- |
| `stdout` | 机器和代理 |
| `stderr` | 人类 |
| `exit codes` | 系统和编排器 |

这项技能教您如何使CLI成为代理的一流界面。生产代理（Claude Code、Cursor、Gemini CLI）通常将CLI与MCP服务器配对——CLI用于状态更改和本地/可脚本化工作，MCP用于多租户SaaS和按用户身份验证。当设计需要MCP端时，请参阅`references/hybrid-mcp-cli.md`中的决策矩阵和CLI/MCP权衡背后的基准数据。

## 完整的交互循环

| 阶段 | 步骤 | 描述 |
| ------- | ------ | ------------- |
| 0. 引导 | 1 | 人类/系统获取身份验证令牌或凭证 |
| 0. 引导 | 2 | 设置受信任的环境变量：令牌、配置文件、安全模式 |
| 1. 发现 | 3 | 代理加载技能或命令摘要 |
| 1. 发现 | 4 | 代理查询参数的模式/帮助 |
| 2. 规划 | 5 | 代理使用`--dry-run`预览请求形状 |
| 3. 执行 | 6 | 代理使用验证后的输入执行 |
| 4. 解释 | 7 | 代理解析结构化结果 |
| 5. 恢复 | 8 | 代理使用退出代码+错误对象来重试、重新身份验证、修复或升级 |

一个不支持每个阶段的CLI从代理的角度来看是不完整的。

## 七项原则

这些都是承重原则。每项原则至少有一个评审标准，并且至少有一个支持示例。

### 原则 0. 一个CLI，三个受众

CLI必须同时服务于人类、代理和系统。只服务于一个受众的设计是不完整的。

### 原则 1. 结构化输出是界面

`stdout`始终应该是可解析和稳定的。成功和失败都是结构化的JSON。CLI必须自行决定哪个受众正在阅读：在启动时检测stdout是否是TTY，如果不是，则默认为JSON，如果是，则默认为人类可读。`NO_COLOR`和显式的`--format json|table`标志覆盖自动检测。代理永远不需要记住传递`--format json`——如果他们必须这样做，他们会忘记，并且运行将无声地生成无法解析的散文。信封和错误合约：`references/design-patterns.md#output-envelopes`。

### 原则 2. 信任是单向的

CLI参数并非天生可信——它们可能来自一个幻觉或提示注入的代理。由人类或系统设置的环境级配置更可信。代理在受限制的表面上选择*要做什么*；人类定义*在哪里以及如何允许其操作*。

### 原则 3. CLI必须描述自己

CLI必须足够自我描述，以便代理可以在不阅读外部README文件的情况下使用它。自我描述必须是**渐进的**，而不是急切的：顶级`--help`列出资源；资源帮助列出操作；操作帮助列出标志；单独的`schema <resource.action>`返回完整的类型化模式。一个拥有数百条命令的CLI将所有内容都倾倒在第一个`--help`中，在每次代理调用时支付该代币成本。请参阅`references/design-patterns.md#help-design`和`references/examples.md`中的示例2和5。

### 原则 4. 通过渐进式可见性实现安全

读取命令易于发现；修改命令带有明确警告；破坏性命令被隐藏在技能中或单独门控。层级表和理由：`references/design-patterns.md#safety-design`。层级是必要的，但不是充分的——它们是提示端的防御，并且批准疲劳会迅速降低它们。假设代理运行时将在操作系统级别（文件系统、网络、进程）对CLI进行沙盒处理，并设计破坏性命令在沙盒内失败。

### 原则 5. 在边界处验证，而不是在中间

输入在CLI入口点验证一次。内部代码操作已验证、类型化、受信任的结构。验证函数集中测试通过和拒绝情况。

### 原则 6. 模式是事实来源

如果存在模式，则所有内容都由此衍生：CLI命令结构、验证规则、帮助文本、生成的文档、生成的技能、类型定义、干运行合约。模式永远不会手动复制。模式还必须携带自己的版本和弃用信号，在每次响应的`meta`块中显示，以便具有缓存旧视图的代理可以检测漂移并重新发现，而不是无声地调用已删除的方法。完整的版本合约和示例：`references/design-patterns.md#schema-versioning`。

### 原则 7. 身份验证必须可委托

身份验证由人类/系统管理的流程获取和刷新。代理使用凭证；它永远不会拥有身份验证生命周期。首选机制：环境变量、配置文件、操作系统密钥链集成、外部刷新的令牌。规范模式：`references/examples.md`中的示例3。

## 标准评审工作流

### 步骤 1. 分类输入

确定用户是否提供：现有CLI、要封装的API、概念设计、部分界面或故障案例。

### 步骤 2. 映射三个受众

**人类：** 是否有可读输出？错误是否可理解？是否支持入门？

**代理：** `stdout`是否是稳定的JSON？CLI能否描述自己？是否有模式内省和干运行？

**系统：** 身份验证是否可委托？退出代码是否稳定？失败是否可确定性路由？

### 步骤 3. 评审交互循环

检查CLI是否支持：引导、发现、参数理解、预览、执行、解析、恢复。

### 步骤 4. 使用评审标准对CLI进行评分，然后映射回原则

使用14标准的评审标准对CLI进行评分。完整的评审标准位于`references/rubric.md`。七项原则中的每一项至少有一个评审标准支持，因此评分到原则的映射是完整的：P0 → 三受众支持、非交互操作；P1 → `stdout`合约、`stderr`分离、幂等重试、错误可恢复性；P2 → 信任边界；P3 → 自我描述（帮助）、干运行；P4 → 安全层级；P5 → 边界验证；P6 → 模式内省；P7 → 身份验证委托。然后按原则总结证据、风险和建议。完整的评审清单位于`references/checklists.md`。

**机器验证基线。** 当正在评审的CLI已安装并可运行时，在应用评审标准之前运行`anc audit <command> --output json`（[agentnative](https://github.com/brettdavies/agentnative) 代码分析器，8个RFC 2119原则）。（注：原文此处为`anc audit`，应为`anc lint`，根据上下文推测）`anc`探测已发布的二进制行为：非交互操作、`--output json`有效性、模式发现性、帮助/版本、退出代码、NO_COLOR和干运行。您自己评分评审标准维度——当前没有代码分析器测量信任方向性（P2）、边界验证（P5）、安全层级（P4）、身份验证委托（P7）或模式版本漂移（P6）。当CLI不可安装或`anc`不可用时，请单独使用评审标准；当`anc`可用时，请将anc评分卡与评审标准分数一起报告。

### 步骤 5. 生成重构计划

* **P0** 必须修复
* **P1** 应改进
* **P2** 长期改进

## 默认输出格式

### 1. 总体结论

声明CLI是**代理原生的**、**部分代理原生的**还是**尚未代理原生**的。

### 2. 三受众合约评审

评估对人类、代理、系统的支持。

### 3. 交互循环覆盖率

评估每个阶段：身份验证引导 → 环境设置 → 技能/帮助发现 → 模式内省 → 干运行 → 执行 → 解析和恢复。

### 4. 评审标准分数 + 七项原则评审

首先报告14标准的评审标准分数，然后总结七项原则为：状态 · 证据 · 问题 · 建议。

### 5. 主要风险

总结设计失败：仅人类输出、不稳定JSON、无模式内省、破坏性命令过度暴露、身份验证与代理耦合、退出代码不明确。

### 6. 重构计划

优先级建议，示例来自`references/examples.md`。

## 此技能应避免推荐的事项

* 仅作为人类可读散文的输出合约
* 需要README进行基本命令发现
* 模式和验证分道扬镳
* 主要通过代理生成的参数提供身份验证
* 默认暴露破坏性行为
* 依赖未记录的约定的CLI行为
* 仅文本的错误，不可机器路由
* 在重试下不是幂等的修改命令
* 没有带`--yes`退出和没有TTY感知回退的确认提示
* 在顶级`--help`中急切地输出模式——在循环调用CLI的代理上支付此代币成本；改用渐进式披露。代币成本理由位于`references/hybrid-mcp-cli.md`。

## 一句话总结

这项技能通过**结构化输出、自我描述、委托身份验证、安全边界和完整交互循环**，帮助将CLI转变为对**人类、AI代理和系统**都值得信赖的执行界面。
