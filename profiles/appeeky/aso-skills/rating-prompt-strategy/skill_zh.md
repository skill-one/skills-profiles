# 评分提示策略

您优化应用何时、如何以及向谁展示评分提示——最大化高评分同时最小化负面评分。评分是应用商店排名信号，也是产品页面的转化因素。

## 评分对应用商店优化（ASO）的重要性

- **搜索排名** — 评分更高的应用在竞争性关键词中排名更优
- **转化率** — 评分星级在搜索结果中可见；4.8分一眼胜过4.2分
- **iOS**：评分按版本重置（您可以在App Store Connect中请求重置）
- **Android**：评分永久累积——一个糟糕的时期很难恢复

## 核心规则

**仅提示那些体验过价值的用户。** 过早提示会导致低评分。在成功时刻提示会产生4-5星评分。

## iOS — SKStoreReviewRequest

苹果原生提示。规则：
- 每年最多显示**3次**，无论您调用多少次
- 苹果控制显示逻辑——调用它并不保证会显示
- 出错、崩溃或令人沮丧的时刻后**永不**提示
- 无法自定义提示UI

```swift
import StoreKit

// 在合适的时刻调用
if let scene = UIApplication.shared.connectedScenes.first as? UIWindowScene {
    SKStoreReviewController.requestReview(in: scene)
}
```

## Android — Play In-App Review API

谷歌原生提示。规则：
- 没有硬性限制，但谷歌会频繁调用时进行限流
- 在明确的积极时刻显示
- 无法确定用户是否实际评分（隐私）

```kotlin
val manager = ReviewManagerFactory.create(context)
val request = manager.requestReviewFlow()
request.addOnCompleteListener { task ->
    if (task.isSuccessful) {
        val reviewInfo = task.result
        val flow = manager.launchReviewFlow(activity, reviewInfo)
        flow.addOnCompleteListener { /* proceed */ }
    }
}
```

## 时间框架

### 成功时刻触发器

在您的应用中定义1-3个用户最满意的"成功时刻"：

| 应用类型 | 良好提示时刻 | 不良提示时刻 |
|----------|--------------------|--------------------|
| 健身 | 完成锻炼后 | 跳过锻炼后 |
| 生产力 | 完成项目/任务后 | 失败保存或同步错误后 |
| 游戏 | 赢得关卡或击败Boss后 | 输掉或失败后 |
| 金融 | 第一次成功交易后 | 出现令人困惑的错误后 |
| 冥想 | 完成会话后 | 冷启动时 |
| 购物 | 成功购买/交付后 | 结账失败后 |

### 基于会话的规则

仅提示符合所有条件的用户：

```
提示条件：
✓ 会话数 >= 3（不是首次用户）
✓ 安装后时间 >= 3天
✓ 至少完成过[激活事件]
✓ 上一会话无崩溃
✓ 当前会话无负面信号（错误、取消）
✓ 未评价此版本
```

## 提示前调查（推荐）

在触发原生提示前，显示一个应用内问题：

```
您喜欢[应用名称]吗？
  [是，非常喜欢!]   [不太喜欢]
```

- **"是"** → 触发`SKStoreReviewRequest` / Play In-App Review
- **"不太喜欢"** → 显示反馈表单（邮件或应用内），**不**触发原生提示

这能过滤出不满意的用户，避免他们给出1-2星评价。

**预期提升**：使用提示前过滤平均提升0.3-0.8星。

## 版本控制（iOS）

iOS允许您在App Store Connect中按版本重置评分。策略性使用：

- **重大改进后重置**——如果您修复了最常被投诉的问题
- **争议性变更后不重置**——用户不喜欢的变更
- 重置后，在头7天内运行积极（但经过过滤）的提示活动
- 首先针对最活跃的用户（最长的会话历史）

## 从评分下降中恢复

### 诊断

1. 检查导致下降的版本——与发布日期关联
2. 阅读该时期的1星评价——找出常见投诉
3. 在下一个版本中修复问题
4. 回复所有1-3星评价（见`review-management`技能）

### 恢复活动

修复发布后：
1. 回复负面评价："已在版本X.X修复——请更新并告知我们"
2. 部分用户在回复后会更新评分
3. 运行针对最忠诚用户的提示活动（最高会话数）
4. 不要提示留下负面评价的用户

### 时间线

```
第0天：   问题识别——进行热修复或补丁
第1-3天：回复所有负面评价，承认问题
第7天：   修复发布——回复之前的负面评价"已在X.X修复"
第8天+：  对会话数>=5且过去7天无崩溃的用户启用提示
第3周：   监控评分趋势——应在2-4周内恢复0.2-0.5星
```

## 提示频率

| 平台 | 最大值 | 推荐 |
|----------|---------|-------------|
| iOS | 365天内3次（苹果强制执行） | 每版本1-2次 |
| Android | 无硬性限制（谷歌限流） | 每用户每月1次 |

同一会话**永不**显示两次提示。

## 输出格式

### 评分策略计划

```
当前评分：[X.X] ★  ([N]个评分)
平台：iOS / Android / 两者

识别的成功时刻：
1. [事件名称] — 当[条件]时触发
2. [事件名称] — 当[条件]时触发

提示前调查：是 / 否
  如果是："您喜欢[应用名称]吗？" → 是 / 不太喜欢

提示触发逻辑：
  会话数 >= [N]
  安装后时间 >= [N]天
  过去[N]会话无崩溃
  [激活事件]完成：是
  已评价此版本：否

预期结果：在[N]周内提升[X]星

恢复计划（如果评分<4.0）：
  1. [修复] — [日期]前发布
  2. [回复策略] — [N]条评价需处理
  3. [提示活动] — [日期]开始，针对[群体]
```

## 相关技能

- `review-management` — 回复评价以恢复评分
- `onboarding-optimization` — 修复导致1星评价的激活问题
- `android-aso` — Play In-App Review API上下文
- `retention-optimization` — 活跃用户给出更好的评分
