# 博客撰写器：新文章生成

根据主题、简报或提纲撰写完整的博客文章。每篇文章都遵循双重优化（谷歌排名+人工智能引用）的六大支柱。

**关键参考资料**（相对于仓库根目录；参考资料位于主 `blog` 技能的参考资料目录中，而不是 `blog-write/` 中）：

- `skills/blog/references/synthesis-contract.md`：合成输出的 6 LAWs（v1.8.0；每当文章嵌入研究合成文本时适用）
- `skills/blog/references/content-templates.md`：模板选择指南和使用方法
- `skills/blog/references/quality-scoring.md`：5 类评分（内容 30，SEO 25，E-E-A-T 15，技术 15，人工智能引用 15）
- `skills/blog/references/eeat-signals.md`：经验、专业、权威、信任标志
- `skills/blog/references/internal-linking.md`：链接策略和锚文本规则
- `skills/blog/references/visual-media.md`：图片来源和图表样式
- `skills/blog-write/references/delivery.md`：此子技能的交付合同步骤和摘要模板

## 工作流程

### 阶段 0：表面目标定位（在研究之前执行）

确定此帖子旨在赢得哪些 FLOW 5 表面。选择会塑造结构、长度、引用密度和行动号召。2026 年的 5 个表面：

1. 自有网站（有机谷歌排名）
2. 搜索结果页面（包括人工智能概述）
3. 人工智能助手引用（ChatGPT、Perplexity、Claude、Gemini、Copilot、You.com）
4. 本地包（博客内容不在此范围内；使用 claude-seo 用于本地）
5. 社区和视频（Reddit、YouTube、LinkedIn、Quora、专业论坛）

默认情况下，大多数帖子针对表面 1、2 和 3。如果同一查询也出现在社区（Reddit 帖子、YouTube 评论）中，请应用双重表面思维：优化帖子以供提取，并计划社区回响（在 `/blog repurpose` 中涵盖）。

要了解更深入的逐表面工作流程，请参阅 `skills/blog/references/flow-alignment.md` 和 `/blog flow find`。

### 阶段 1：主题理解

1. **明确主题** - 如果用户只提供主题，请询问：
   - 目标受众（这是为谁准备的？）
   - 主要关键词/搜索意图
   - 期望的字数（默认：2,000-2,500 字）
   - 平台/格式（MDX、markdown、HTML - 如果在项目中则自动检测）
2. **如果存在简报** - 加载它并跳到阶段 1.5

### 阶段 1.5：模板选择

从 `skills/blog/templates/` 中的 12 个模板中选择适当的内容模板（主 `blog` 技能拥有模板目录）。

1. **根据主题和搜索意图自动检测内容类型**：
   | 信号 | 模板 |
   |------|------|
   | "如何..."、过程、步骤 | `how-to-guide` |
   | "最佳 X"、"前 N 名"、列表格式 | `listicle` |
   | 客户成果、前后对比、指标 | `case-study` |
   | "X 与 Y 对比"、比较、替代方案 | `comparison` |
   | 广泛主题、综合指南 | `pillar-page` |
   | "X 值得吗"、产品评估 | `product-review` |
   | 意见、预测、行业观点 | `thought-leadership` |
   | 专家引言、多来源收集 | `roundup` |
   | 代码演示、工具演示、技术 | `tutorial` |
   | 突发新闻、算法更新、事件 | `news-analysis` |
   | 调查结果、实验、原始数据 | `data-research` |
   | 问答、知识库、"X 是什么" | `faq-knowledge` |

2. **加载匹配的模板**：从 `skills/blog/templates/<type>.md` 读取
3. **调整提纲** - 使用模板的章节结构、标题模式和建议的字数来塑造阶段 3 的提纲
4. **备用** - 如果没有模板完全匹配，则使用阶段 3 下面的通用提纲结构。通知用户选择的模板（或没有匹配的模板）。

有关详细选择标准和意图映射，请参阅 `skills/blog/references/content-templates.md`。

### 阶段 2：研究

生成 `blog-researcher` 代理（或使用 WebSearch 进行内联研究）：

1. **找到 8-12 个当前统计数据**（优先考虑 2025-2026 年数据）
   - 搜索：`[主题] study 2025 2026 data statistics`
   - 优先考虑 Tier 1-3 来源（参见 `skills/blog/references/quality-scoring.md`）
   - 记录：统计数据、来源名称、URL、日期、方法
2. **找到封面图片**（宽、高质量、主题相关）：
   - 优先使用原始截图、产品视觉效果、图表或数据图形（如果可用）
   - 对于库存图片，使用官方 API，如 Openverse、Unsplash、Pexels 或 Pixabay，以便捕获许可证、创作者、来源 URL 和下载 URL
   - 将批准的资产下载到草稿文件夹，存储归属，并且永远不要热链接任意的 CDN URL
   - 拒绝 `javascript:`, `data:`, 和 `file:` 图片 URL
   - 目标尺寸：1200x630（OG 兼容）或 1920x1080
   - 或者通过 `blog-chart` 生成自定义 SVG 封面（带有关键统计数据）
   - 或者通过 `blog-image` 生成自定义 AI 图片；优先使用 `gemini-3.1-flash-image`，然后是 `gemini-3.1-flash-lite-image` 或 `gemini-3-pro-image`（当可用时），并记录模型 ID
   - 有关封面图片尺寸详情，请参阅 `skills/blog/references/visual-media.md`
3. **从开源平台找到 3-5 个内联图片**：
   - 使用官方 API 或 Openverse 搜索；保留每个资产的许可证、创作者、来源 URL 和检索日期
   - 将图片本地下载并使用草稿中的本地路径引用
   - 在下载前，使用交付合同的 SSRF 规则验证最终 URL
4. **计划 2-4 个数据可视化** 从研究统计数据
   - 选择多样化的图表类型（参见 `skills/blog/references/visual-media.md`）
   - 将数据点映射到图表格式
5. **AI 图片生成**（可选，如果 `blog-image` 可用）：
   - 如果库存照片结果不足（少于 3 个良好匹配）或主题过于专业
   - 通过 `blog-image` 子技能生成自定义英雄图片和/或内联插图
   - 记录提示、提供者和模型 ID；库存照片仍然可用，但当它们更好地服务于主题时，原始图片和数据可视化更受青睐
6. **NotebookLM 研究**（可选，如果用户有相关笔记本）：
   - 如果用户提到 NotebookLM 笔记本或主题与配置的笔记本对齐
   - 通过 `blog-notebooklm` 查询用户上传文档中的来源数据
   - 继承底层文档来源的来源 Tier；用户自己的主要文档可以是 Tier 1，而复制的二级来源保留其原始 Tier
   - 如果未配置或未认证，则静默回退
7. **找到相关的 YouTube 视频**（每篇文章 2-3 个）：
   - 使用 `blog-google` youtube 命令或 WebSearch `site:youtube.com [主题] [年份]`
   - 应用 `skills/blog/references/video-embeds.md` 中的质量标准（最低分数 50/100）
   - 选择 2-3 个最佳视频。如果没有找到，则静默回退。

### 阶段 3：提纲生成

在撰写之前创建结构化提纲。如果阶段 1.5 加载了模板，请根据模板的章节结构调整此骨架：

```
# [将标题作为问题 - 包含主要关键词]

## 简介（100-150 字）
- 以读者的问题、有用的发现、具体示例或可选的已验证统计数据开头（当证据使这成为最强的钩子时）
- 问题/机会声明
- 读者将学到什么

> **关键要点**
> - [带有统计和来源的核心发现]
> - [第二关键见解或建议]
> - [第三个可操作的要点]
> (3-5 个简洁的要点，当摘要有助于此内容类型时)

## H2：[意图匹配的标题]
- 清晰的章节要点，在需要时提供已验证支持
- 支持证据
- [图片位置]
- 实用建议
- [EVIDENCE-BACKED EXPLANATION 占位符]
- [INTERNAL-LINK: 锚文本 → 目标描述]

## H2：[意图匹配的标题]
- 首先回答段落
- [图表：类型 + 数据描述]
- 分析和启示
- [EVIDENCE-BACKED EXPLANATION 占位符]
- [INTERNAL-LINK: 锚文本 → 目标描述]

## H2：[意图匹配的标题]
- 首先回答段落
- 真实世界示例或案例研究
- [图片位置]
- [EVIDENCE-BACKED EXPLANATION 占位符]

## H2：[意图匹配的标题]
- 首先回答段落
- [图表：类型 + 数据描述]
- 分步指导
- [EVIDENCE-BACKED EXPLANATION 占位符]
- [INTERNAL-LINK: 锚文本 → 目标描述]

## H2：[意图匹配的标题]
- 首先回答段落
- 前瞻性分析

## [行动号召部分或内联放置]
- 有关内容类型按放置规则的行动号召，请参阅 `skills/blog/references/cta-placement.md`
- 在提供价值后放置行动号召，而不是在任意位置
- 每篇文章一个专注的行动号召（266% 的转化率更高）
- [行动号召：与文章主题匹配的上下文行动号召]

## 可选的 FAQ 部分（仅当真实的读者问题值得时）
- [INTERNAL-LINK: 锚文本 → 详细内容]

## 结论（100-150 字）
- 关键要点（项目符号）
- 行动号召
- [INTERNAL-LINK: 锚文本 → 下一逻辑内容]
```

在撰写之前向用户展示提纲以供批准。

**视觉元素节奏**：每隔 300-500 字插入 `[IMAGE]`、`[CHART]`、`[VIDEO]` 或 `[CALLOUT]` 标记。交替类型（不要连续相同类型）。有关视觉节奏部分和 `skills/blog/references/cta-placement.md` 中的行动号召定位，请参阅 `skills/blog/references/content-rules.md`。

### 阶段 4：图表生成（内置）

当研究人员识别出值得制作图表的数据（3 个以上可比较指标、趋势数据、前后对比）：

1. 使用多样性规则选择图表类型（每篇文章不要重复相同类型）
2. 调用 `blog-chart` 子技能，提供：图表类型、标题、数据值、来源、平台格式
3. 将返回的 SVG 直接嵌入文章中，使用 `<figure>` 包装器
4. 每篇 2,000 字的文章目标 2-4 个图表
5. 均匀分布图表 - 不要将它们聚集在一起

有关图表类型选择和样式规则的详细信息，请参阅 `skills/blog/references/visual-media.md`。

### 阶段 5：内容撰写

遵循以下规则撰写完整文章：

#### 5a. 前置元数据
```yaml
---
title: "[清晰的标题，可识别页面并匹配搜索意图]"
description: "[准确、页面特定的可见内容摘要]"
coverImage: "[来自 Pixabay/Unsplash/Pexels 或生成的 SVG 路径的 URL]"
coverImageAlt: "[关于封面图片的描述性句子]"
ogImage: "[与 coverImage 相同，或自定义 OG 图片 URL]"
date: "YYYY-MM-DD"
lastUpdated: "YYYY-MM-DD"
author: "[作者姓名]"
tags: ["keyword1", "keyword2", "keyword3"]
---
```

如果平台使用不同的字段名（例如，`image`、`hero`、`thumbnail`），请调整以匹配项目的现有前置元数据约定。

#### 5b. 摘要框（关键要点）

在介绍之后（在第一个 H2 主体部分之前）添加摘要框：

```markdown
> **关键要点**
> - [带有已验证支持的核心发现]
> - [第二关键见解或建议]
> - [第三个可操作的要点]
```

要求：
- 3-5 个简洁的要点，尺寸适合材料
- 必须是自包含的 - 不需要阅读文章即可理解
- 仅在摘要与材料相关且已验证时使用统计数据
- 陈述关键发现、建议或答案
- 默认标签："关键要点"。如果活动角色处于活动状态，请使用角色的 summary_label
- 向后兼容：接受在重写期间现有的 TL;DR 盒子

#### 5c. 目的优先格式化（关键）

在重要部分的开头陈述其目的，然后提供该声明所需的上下文和已验证证据。不要强迫统计数据或固定长度。

模式：
```markdown
## 如何在 2026 年 X 影响 Y？

[来自来源的统计数据] ([来源名称](url), 年份)。[用 1-2 句话直接回答标题问题，解释其启示以及这对读者意味着什么。]
```

**公共统计数据材料的来源记录**：

记录足够的来源信息，以便读者或编辑可以验证该声明。使用出版物的引用样式，而不是强迫一种句子模式。

1. **相关日期或研究期间**。在时效性或测量期间改变声明含义时，包括它。
2. **可识别的来源**。在需要区分来源并将引用靠近声明时，命名出版商和文档标题。
3. **可检索的支持**。保留稳定的 URL。为可变或未标记的来源添加检索日期，并记录方法或限制，当它们影响解释时。

**FLOW 质量标准（放弃或替换）**：
公共声明必须使用已验证来源，或保持定性。如果统计数据无法验证，则放弃它。如果它被更新的来源反驳，则用已验证的替代方案替换它。不要软化模糊语言以保留无法验证的数字。

有关证据引导优化提示（CTR 审计、质量后续处理、模式、PAA 重写、ChatGPT 可见性），请参阅 `/blog flow optimize`。

#### 5d. 信息增益标记

在文章包含真正原创数据、透明的第一手证据或独特的来源合成时，使用信息增益标记作为可选的起草注释。证据本身有助于读者；标记不是搜索引擎信号，并且其存在不会获得任何分数。

用评论或可见标记标记每个标记：

- `[原创数据]` - 作者亲自收集的专有调查、实验、A/B 测试结果、案例研究指标
- `[个人经验]` - 第一手观察、直接参与的经验教训、"当我们尝试 X，Y 发生了" 叙述
- `[独特见解]` - 别人没有做的分析、有数据支持的逆向观点、现有研究之间的新联系

放置：
- 自然地编织到正文文本中
- 作为内联评论使用：`<!-- [原创数据] -->` 在相关段落之前
- 或如果格式支持，作为可见引言：
  ```markdown
  > **我们的发现**：[有特定数据支持的原创观察]
  ```
- 仅当支持的原创材料值得时使用。

#### 5e. 已验证支持的说明

对于重要的可重用声明，创建一个自包含的、已验证支持的说明，尺寸适合材料。

指导：
- 自包含且可独立理解
- 包含特定声明以及需要时已验证的支持
- 使用声明式、可引用的写作风格
- 放在 H2 章节主体中（不是单独的块）

示例：
```markdown
[已验证来源标题]，一项 [方法或样本描述] 在 [日期] 发布的研究发现，对于 [受众或市场] 的 [具体指标] 为 [来源名称](https://example.com/full-report)，检索日期 YYYY-MM-DD。从实际角度将证据与读者应采取的行动联系起来，在做出声明或更改工作流程之前。
```

不要为了达到固定长度而填充说明，或者仅仅为了获得准备就绪分数而添加它们。

#### 5f. 内部链接区域

使用占位符符号在整个文章中标记内部链接机会。用户（或后续步骤）将解决这些到实际 URL。

区域放置：
- **简介** - 链接到相关的支柱内容或主题中心
- **每个 H2 部分** - 链接到支持文章、深入探讨、相关工具
- **FAQ 部分** - 将答案链接到扩展答案的详细内容
- **结论** - 链接到读者应该消费的下一逻辑内容

格式：
```markdown
[INTERNAL-LINK: 锚文本 → 目标描述]
```

示例：
```markdown
有关关键词分组的深入探讨，请参阅我们的
[INTERNAL-LINK: 完整关键词分组指南 → 关于关键词研究方法论的支柱页面].
```

每篇 2,000 字的文章目标 5-10 个内部链接区域。使用描述性锚文本（永远不要 "点击这里" 或 "阅读更多"）。有关锚文本规则和链接策略，请参阅 `skills/blog/references/internal-linking.md`。

#### 5g. 段落规则
- 使用适合受众和材料的段落和句子长度
- 当这样做提高理解时拆分段落，而不是为了满足配额
- 每个段落以最重要的信息开头
- 目标 Flesch 阅读易度：60-70

#### 5h. 标题规则
- 一个 H1（仅标题）
- H2 用于主要部分；根据意图使用疑问或声明形式
- H3 仅用于子部分 - 永远不要跳过级别
- 保持标题术语与页面主题自然一致；不要强制执行精确匹配关键词配额

#### 5i. 图片嵌入

标准 markdown：
```markdown
![描述性替代文本 - 主题关键词自然](https://cdn.pixabay.com/photo/...)
```

MDX 使用 Next.js Image（如果检测到）：
```mdx
![描述性替代文本 - 主题关键词自然](https://cdn.pixabay.com/photo/...)
```

- 在 H2 标题之后、正文文本之前放置图片
- 均匀分布在整个帖子中（不要聚集）
- 替代文本应该是完整的描述性句子

#### 5j. 图表嵌入

标准 markdown/HTML：
```html
<figure>
  <svg viewBox="0 0 560 380" ...>...</svg>
  <figcaption>来源：[来源名称]，[年份]</figcaption>
</figure>
```

MDX 格式：
```mdx
<figure className="chart-container" style={{margin: '2.5rem 0', textAlign: 'center', padding: '1.5rem', borderRadius: '12px'}}>
  <svg viewBox="0 0 560 380" ...>...</svg>
</figure>
```

#### 5k. 视频嵌入
使用 `skills/blog/references/video-embeds.md` 中的 srcdoc 懒加载模式嵌入 YouTube 视频。包括 aria-label、noscript 回退以供 AI 爬虫使用。在相关 H2 之后、500+ 字之后放置。

#### 5l. 引用格式
内联归因（始终）：
```markdown
2026 年 2 月，Seer Interactive 的 AI 概述 CTR 追踪器报告了 AI 概述搜索结果页面的 2.4% 有机 CTR ([Seer Interactive](https://www.seerinteractive.com/), 检索日期 YYYY-MM-DD).
```

#### 5m. FAQ 部分
仅当用户问题值得时才添加 FAQ 项目。答案应该是完整且简洁的；仅在相关时包含已验证统计数据。

FAQPage 是可选的实体标记。Google FAQ 丰富结果已于 2026 年 5 月 7 日完全停止，因此不要将 FAQ 模式作为核心 Google 丰富结果输出或引用杠杆。优先考虑 Article/BlogPosting + Person + Organization + BreadcrumbList；仅在平台已经支持它且问题确实帮助用户时才发出 FAQPage。

对于使用可选 FAQSchema 组件的 MDX：

### 阶段 6：质量检查

在交付之前验证：

#### 结构和内容
1. 重要声明清晰地陈述其要点，并在需要时包含已验证支持
2. 段落和句子节奏适合受众；仅长度不能阻止交付
3. 所有统计数据都有命名的 Tier 1-3 来源
4. 2-4 个类型多样化的图表
5. 3-5 个带有描述性替代文本的内联图片
6. 封面图片在前置元数据中存在（coverImage + ogImage）
7. FAQ 部分存在，当用户问题时包含 3-5 个项目
8. 标题层次结构清晰（H1 -> H2 -> H3）
9. 元描述准确且具体地总结了可见内容

#### 新元素验证
10. 可选的摘要有助于读者，并且不包含任何未支持的声明
11. 任何信息增益标记都指向支持的原创材料
12. 重要的可重用声明是自包含的，并且有已验证支持
13. 内部链接区域在简介、H2 部分、FAQ 和结论中标记
14. 审查项目语音偏好，以改善清晰度和匹配度

#### 可选的编辑语音审查
15. **句子节奏** - 仅在提高清晰度、强调或流畅性时才改变句子结构。不要从句子模式推断作者身份或强制执行固定句子长度范围。
16. **配置的短语审查** - 在上下文中审查这些项目样式列表术语，并在更清晰的替代方案适合时替换它们：
    - "在当今的数字景观中"、"重要的是要注意"、"深入探讨"
    - "游戏改变者"、"导航景观"、"革命化"、"无缝"
    - "尖端"、"利用"、"的力量"（作为动词）
    - "深入挖掘"、"关键"、"提升"、"培养"、"景观"（过度使用）
    - "多方面的"、"强大的"、"织锦"、"启程"
    - 完整列表在 `agents/blog-writer.md`
17. **缩写** - 在它们适合所选语音时使用缩写。它们的存在或缺失与作者身份或 Google 性能无关。
18. **修辞问题** - 仅在它们有助于读者推理决策时使用它们。没有配额。
19. **YouTube 视频** - 2-3 个嵌入，带有懒加载、aria-labels 和 noscript 回退（参见 `skills/blog/references/video-embeds.md`）
