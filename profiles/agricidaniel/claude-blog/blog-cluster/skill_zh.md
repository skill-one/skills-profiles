# 博客集群（语义主题集群引擎）

从单个种子关键词开始，规划和执行整个相互关联的内容生态系统。分为三个层级：语义集群（大脑）、集群架构（结构）和执行引擎（机器）。

> 改编自 Lutfiya Miller 的 **semantic-cluster-engine** 提交（AI 营销中心专业挑战赛获奖者，2026年3月，95/100 标杆）。原始存储库：https://github.com/Drfiya/semantic-cluster-engine
> 此版本保留了计划 + 执行的架构和集群上下文创新，移除了特定品牌（ScienceExperts.ai）的样式和图像提示，并通过 claude-blog 现有的子技能进行路由。

## 命令

| 命令 | 功能 |
|------|------|
| `/blog cluster` | 交互式。询问是否要计划或执行。 |
| `/blog cluster plan <种子关键词>` | 基于 SERP 的语义分析。输出集群计划 + 地图。 |
| `/blog cluster plan --from strategy [路径]` | 导入现有的 `blog-strategy` 集群构建计划，并与 SERP 数据进行验证。 |
| `/blog cluster execute [计划路径]` | 顺序调用 `blog-write`，附带集群上下文和自动互链。 |

## 与现有 claude-blog 技能的交叉引用

| 技能 | 此技能调用它的时间 |
|------|------------------|
| `/blog strategy` | 上游规划。`plan --from strategy` 消耗其集群构建计划表格。 |
| `/blog write` | 每篇帖子执行。每个分支和中心都由 `blog-write` 生成，并带有前置的集群上下文块。 |
| `/blog chart` | 由 `blog-write` 内部调用以生成内联 SVG 图表。此技能没有直接调用。 |
| `/blog image` | 每篇帖子可选生成英雄图像。模型选择委托给 `blog-image`；当可用时，优先使用当前的 Gemini 图像模型。 |
| `/blog seo-check` | 执行后推荐进行每篇帖子的页面级验证。 |
| `/blog cannibalization` | 执行后推荐确认集群内零关键词重叠。 |
| `/blog schema` | 执行后推荐添加 `BreadcrumbList`、`ItemList` 和 `Article` 模式。 |

此技能永远不会修改其他技能所属的文件。它通过任务工具或作为编排的子技能调用它们。

## 命令路由

1. 解析用户命令以确定子命令。
2. 如果用户只输入了 `/blog cluster`，询问：“您想要**计划**新的集群还是**执行**现有的计划？”
3. 路由：
   - `plan <关键词>` 到计划阶段（下方）
   - `plan --from strategy [路径]` 到策略导入流程（下方）
   - `execute [路径]`、`build` 或 `run` 到执行阶段（下方）

## 计划阶段：`/blog cluster plan <种子关键词>`

参考：`references/semantic-clustering.md`

### 第 1 步。种子关键词扩展

使用 WebSearch 将种子扩展为 30 到 50 个短语的关键词宇宙：

1. 直接搜索 `<种子>` 以捕获相关搜索和“人们还问”。
2. 长尾扩展：`<种子> 指南`、`<种子> 小贴士`、`<种子> 工具`、`<种子> 示例`、`<种子> vs`、`最佳 <种子>`、`如何 <种子>`。
3. 问题挖掘：`什么是 <种子>`、`<种子> 如何工作`、`为什么 <种子>`、`<种子> 初学者`。
4. 意图变体：添加商业修饰符（最佳、顶级、评论、比较、价格）、信息修饰符（指南、教程、解释、示例）和交易修饰符（购买、下载、工具、软件、服务）。
5. 年度新鲜度：`<种子> 2026`。

### 第 2 步。语义集群

使用 `references/semantic-clustering.md` 中的优先级规则对扩展的关键词进行分组：

1. **SERP 重叠分析** 是主要信号。两个关键词在 Top-10 结果中有 4 个或更多共享时，通常针对相同意图，应考虑为同一篇帖子。
2. **意图分类** 将每个关键词分配到信息性、商业性、交易性或导航性。
3. **实体映射** 识别 Google 关联于主题的人、产品、框架和组织。
4. **分组** 将具有相同意图和主题邻近性的关键词组合在一起。每个组成为中心辐射结构的一个分支。

### 第 3 步。集群架构设计

参考：`references/cluster-architecture.md`

构建中心辐射结构：

- **中心（hub）**：针对最广泛的关键词。字数 2,500 到 4,000。模板 `pillar-page`。链接到每个辐射。
- **辐射**：每个针对长尾集群。字数 1,200 到 1,800。模板自动选择意图。链接到中心和其他兄弟。

集群形成规则：

- 正常模式：每个中心 2 到 5 个集群，每个集群 2 到 4 个辐射，总共 1 个中心加上 5 到 15 个辐射。
- 小集群模式：对于狭窄的种子，在警告用户并要求确认后，允许 1 个中心加上 2 到 4 个辐射。
- 每个辐射针对一个独特的首要关键词（零重复）。

### 第 4 步。内部链接矩阵

对于每个辐射 `S`：

- `S` 到中心（始终；锚文本使用中心的唯一关键词）。
- 中心到 `S`（始终；锚文本使用 `S` 的唯一关键词）。
- `S` 到同一集群中的其他辐射（每个 2 到 3 个链接，上下文锚文本）。
- `S` 到相邻集群中的辐射（0 到 1 个链接，仅在语义相关时）。

验证每个辐射至少有 2 个入站链接。计算计划的总互链数。

### 第 5 步。生成输出文件

所有计划和执行工件都放入当前工作目录的单个子目录中。规范输出目录，拒绝符号链接，拒绝集群目录外的写入。斜杠必须仅匹配小写字母、数字和连字符；拒绝绝对路径、`..`、斜杠内的路径分隔符和隐藏控制字符。

```
<cwd>/
└── cluster-<种子关键词斜杠>/
    ├── cluster-plan.json
    ├── cluster-map.html
    ├── pillar-<斜杠>.md       （执行阶段）
    ├── <辐射斜杠>.md         （执行阶段，每个辐射一个）
    └── cluster-scorecard.md   （执行阶段）
```

#### `cluster-plan.json` 模式

```json
{
  "seed_keyword": "<种子>",
  "generated_at": "YYYY-MM-DDTHH:MM:SSZ",
  "pillar": {
    "id": "P",
    "title": "中心的标题",
    "primary_keyword": "最广泛的关键词",
    "secondary_keywords": ["..."],
    "search_volume_estimate": "高|中|低",
    "template": "pillar-page",
    "word_count_target": 3000,
    "cluster": "pillar"
  },
  "clusters": [
    {
      "name": "集群 A：主题",
      "intent": "信息性|商业性|交易性",
      "color": "#2563eb",
      "posts": [
        {
          "id": "A1",
          "title": "帖子标题",
          "primary_keyword": "长尾关键词",
          "secondary_keywords": ["..."],
          "search_volume_estimate": "高|中|低",
          "template": "如何指南",
          "word_count_target": 1500,
          "links_to": ["P", "A2"],
          "links_from": ["P", "A2"]
        }
      ]
    }
  ],
  "total_posts": 9,
  "total_interlinks": 23,
  "estimated_total_words": 18000
}
```

注意：量级估计是相对指标（高、中、低），源自 SERP 信号，不是绝对搜索量。要获取精确数据，用户应咨询 Ahrefs、SEMrush 或 DataForSEO（claude-blog 提供的 `seo-dataforseo` 伴生子技能）。

#### `cluster-map.html`（XSS 安全）

一个静态的、自包含的 HTML 文件，带有嵌入式 SVG 可视化。作者必须遵守以下硬性规则：

- 无内联 `<script>` 块。无 `onclick`、`onmouseover` 或任何 `on*` 事件属性。
- 无外部脚本 `<src>` 引用。
- 插入到 SVG 中的每个文本标签必须转义：将 `&` 替换为 `&amp;`，`<` 替换为 `&lt;`，`>` 替换为 `&gt;`，`"` 替换为 `&quot;`，`'` 替换为 `&#39;`。
- 悬停效果使用 CSS `:hover` 仅。无 JavaScript。
- 使用 SVG 节点内的 `<title>` 子元素为可访问的提示（浏览器原生，无脚本）。

地图显示：一个中心节点、颜色编码的集群组向外辐射、每个集群内的辐射节点，以及连接相关节点的链接线。

### 第 6 步。向用户展示计划

显示集群和帖子的摘要表格、总互链数、估计字数和文件路径。在继续执行前询问确认。等待明确的用户批准。不要自动执行。

## 策略导入：`/blog cluster plan --from strategy [路径]`

将 `blog-strategy` 输出桥接为集群计划。

1. 定位策略输出。扫描当前目录（或用户指定路径）以查找包含 `Cluster Build Plan` 表格的文件，该表格具有列 `# | 辐射主题 | 模板 | 目标关键词 | 字数 | 内部链接`（由 `/blog strategy` 产生的格式）。
2. 解析表格。提取中心行（标记为 `P`）、辐射行、模板分配、目标关键词、字数和链接关系。
3. 验证和丰富。对每个关键词运行 SERP 重叠验证（计划阶段第 2 步）。添加量级估计并验证语义集群分组。
4. 如果 SERP 数据与策略表格矛盾，标记冲突；不要无声地覆盖用户的战略意图。
5. 使用与标准计划阶段相同的输出生成 `cluster-plan.json` 和 `cluster-map.html`。
6. 展示转换后的计划，突出显示基于 SERP 的任何调整，并等待用户确认。

## 执行阶段：`/blog cluster execute [计划路径]`

参考：`references/execution-workflow.md`

### 第 1 步。加载计划

从用户指定路径或工作目录中最新的 `cluster-*/cluster-plan.json` 读取 `cluster-plan.json`。验证 JSON 结构。如果不存在计划，返回：“未找到集群计划。请先运行 `/blog cluster plan <种子关键词>`。”

在读取用户提供的计划路径之前，将其相对于当前工作目录进行规范化。拒绝绝对路径、`..`、符号链接、非 `cluster-plan.json` 文件名以及任何选定的集群目录外的路径。将所有生成的帖子、图像、地图和评分卡输出约束到该集群目录。

### 第 2 步。确定执行顺序

1. 首先生成中心页面（以便辐射可以链接到已知的文件名）。
2. 然后生成辐射，按 `(集群优先级, 搜索量估计降序, 帖子 ID 字母顺序)` 排序。集群优先级是集群内估计量的总和（最高优先级）。
3. 当存在多个集群时，交替生成以使早期内容分布多样化。

### 第 3 步。对于每个帖子：构建集群上下文并调用 `blog-write`

构建集群上下文块（完整模式在 `references/execution-workflow.md` 中）并作为主题提示传递给调用 `blog-write` 的任务工具。上下文告诉 `blog-write` 集群名称、帖子的角色（中心或辐射）、主要和次要关键词、选择的模板、字数目标、已写帖子列表（链接到这些帖子）、即将到来的帖子列表（使用 `[INTERNAL-LINK]` 占位符）、以及此帖子的链接要求。

**证据来源传播。** 集群上下文包括此指令，用于每个辐射和中心：“保持材料声明可追溯到支持它们的来源。记录日期、发布者/标题详细信息、检索笔记、方法和局限性，当它们有助于识别或解释来源时。使用出版物的引用样式。删除无法验证的统计数据，并用被反驳的统计数据替换。”

此级联在批量执行中保留了证据纪律，而不会将固定的来源记录格式变成评分或门禁。参见 `skills/blog/references/flow-alignment.md`。

上下文还指示 `blog-write` 自主运行：跳过主题澄清、跳过大纲批准、不要自动检测模板、不要暂停。

输出格式：默认为标准 Markdown（`.md`），匹配 `blog-write` 的默认设置。如果用户明确请求 HTML，则相应设置平台目标。不要强加任何特定品牌的 CSS 或标志；那是用户的责任。

### 第 4 步。每篇帖子的可选英雄图像

如果 `blog-image` 可用，通过任务工具调用 `/blog image generate` 生成 16:9 英雄图像，并将其放置在 `cluster-<斜杠>/images/<帖子斜杠>-hero.png`。将提供商选择委托给 `blog-image`；当可用时，优先使用当前的 Gemini 图像模型，并在评分卡中记录模型 ID。如果图像生成不可用或失败，记录警告并继续，不生成图像。图像生成是非阻塞的。

### 第 5 步。反向链接注入

在每篇帖子写入后：

1. 扫描集群目录中所有先前写入的帖子，查找引用刚刚写入的帖子的 `[INTERNAL-LINK: 关键词 -> 文件名.md]` 标记。
2. 将每个匹配项替换为实际的 Markdown 链接：`[关键词](文件名.md)`。
3. 在第一次通过中在帖子的 frontmatter 中添加集群元数据块（`cluster:`、`cluster_role:`、`cluster_group:`）。

### 第 6 步。故障处理

如果 `blog-write` 返回任何帖子的质量门禁失败，立即停止批处理。保存进度，将失败的帖子和所有剩余帖子标记为跳过，并告诉用户在继续之前手动检查或重试失败的帖子。不要在质量失败后继续生成 5 到 15 篇帖子，因为那可能创建扩展内容滥用风险。

如果 `blog-write` 由于超时或运行时错误在生成内容前失败，在评分卡中记录失败，除非用户明确在检查原因后继续，否则停止。

如果用户在执行中途取消，保存进度并记录已完成的帖子。在下一个 `/blog cluster execute` 中，检测已写入文件并从下一个未写入的帖子处恢复。

### 第 7 步。生成 `cluster-scorecard.md`

在所有尝试的帖子完成后，生成一个涵盖以下内容的 Markdown 评分卡：

- 每篇帖子的状态（已写、失败、跳过）与文件路径和字数。
- 每篇帖子的质量评分（并行调用 `/blog analyze` 对每个帖子）和集群平均值。
- 集群凝聚力评分：0 到 100 的综合评分，包括链接互惠性、意图多样性、模板多样性以及关键词覆盖率（公式在 `references/execution-workflow.md` 中）。
- 内部链接审计：每篇帖子的出站和入站链接计数、孤儿标记、未解决的 `[INTERNAL-LINK]` 标记。
- 重复检查：任何两篇帖子共享主要关键词，或任何一对超过 70% 的关键词重叠。建议运行 `/blog cannibalization` 进行更深入的检查。
- 图像生成摘要：生成的英雄图像与跳过的图像。
- 推荐的后续操作：模式生成（`/blog schema`）、每篇帖子的 SEO 验证（`/blog seo-check`）、再利用（`/blog repurpose`）。

### 第 8 步。最终报告

向用户返回简洁的摘要，包括总计、评分卡路径和后续操作命令。

## 质量门禁

| 门禁 | 检查 | 失败时的操作 |
|------|------|--------------|
| 集群最小值 | 至少 2 个集群，每个集群至少 2 篇帖子 | 在计划期间警告；建议扩展 |
| 重复 | 没有两篇帖子共享主要关键词 | 阻止执行；要求调整计划 |
| 链接完整性 | 每篇帖子至少有 2 个或更多入站内部链接 | 在评分卡中警告 |
| 量级估计 | 中心通常比辐射需要更多深度 | 作为可选规划上下文传递给 `blog-write`；从不强制执行原始字数最小值 |
| 意图多样性 | 集群中至少有 2 个不同的意图 | 在评分卡中警告 |
| 模板多样性 | 集群中至少有 3 个不同的模板 | 在评分卡中警告 |

## 错误处理

| 情景 | 操作 |
|------|------|
| 种子关键词太宽泛（超过 50 个关键词变体） | 建议在集群之前缩小焦点。 |
| 种子关键词太狭窄（少于 5 个关键词变体） | 提供较小的集群（中心加上 2 到 3 个辐射）或建议放宽。 |
| WebSearch 不可用 | 仅生成草稿计划，并在执行前需要用户确认、导入的关键词数据或 SERP 数据。 |
| `blog-write` 失败质量门禁或内容生成 | 停止批处理，保存进度，将失败的帖子和所有剩余帖子标记为跳过，并要求用户在继续前手动检查或明确恢复。 |
| `blog-write` 未安装 | 返回：“blog-cluster 需要 claude-blog。在运行此技能前安装它。” |
| `cluster-plan.json` 格式错误 | 验证 JSON 并报告带有行号的解析错误。 |
| 用户取消执行 | 保存进度；在下次调用时自动检测已完成的帖子，并从中恢复。 |
| 可选图像生成不可用或失败 | 跳过英雄图像生成；在执行开始时仅警告一次，而不是每篇帖子。 |

## 与相关 claude-blog 技能的区别

| 技能 | 角色 | blog-cluster 增加的内容 |
|------|------|------------------------|
| `blog-strategy` | 规划 3 到 5 个内容中心，并作为战略练习绘制中心辐射结构图 | 执行基于 SERP 的语义集群，然后执行计划生成真实、互链的帖子。 |
| `blog-calendar` | 围绕主题集群安排发布日期 | 不构建集群或撰写帖子；此技能执行这两项操作。 |
| `blog-cannibalization` | 检测现有内容中的关键词重叠 | 诊断性。blog-cluster 在规划阶段防止重复。 |
| `blog-write` | 一次撰写一篇帖子 | blog-cluster 协调多个 `blog-write` 调用，附带共享集群上下文和双向链接。 |
| `blog-outline` | 生成单个 SERP 指导的提纲 | blog-cluster 生成整个集群的提纲等效物，然后撰写帖子。 |

blog-cluster 是总包商：它分析主题，绘制数据驱动的计划，并从单个种子关键词构建整个结构。
