# 博客品牌：持久化编辑上下文

生成两个项目根文件，当博客协调器存在时，会自动加载以支持写作和规划命令：

- `BRAND.md`：目标受众是谁，品牌代表什么，永远不该说什么
- `VOICE.md`：品牌的声音如何，结构和词汇上如何体现

这些是编辑界的完美产品.md / 设计.md模式：持久化的上下文，跨会话持续存在，并传播到每个命令。

## 存在的原因

目前，角色JSON（来自`blog-persona`）被某些技能加载，而其他技能则不加载。主题集群上下文存在于集群保险库中。竞争对手定位则无处可寻。每个博客命令都从其拥有的上下文中重新推导“品牌是什么”。

`BRAND.md`和`VOICE.md`解决了这个问题：一个权威来源，由`blog`协调器在每个命令开始时加载。

当两个文件都不存在时，行为与v1.7.1相同。向后兼容。

## 命令

| 命令 | 目的 |
|---|---|
| `/blog brand init` | 交互式访谈，将BRAND.md和VOICE.md写入项目根目录 |
| `/blog brand show` | 显示当前内容（或报告缺失） |
| `/blog brand update` | 使用当前值作为默认值重新运行访谈 |

## 初始化流程

运行5步交互式访谈。询问每一步，等待响应，然后继续。如果`blog-persona` JSON已存在，则从其中预填声音答案。

### 第1步：受众

询问：
- **主要受众角色**（例如“50-500人B2B SaaS的市场负责人”）
- **次要受众**（可选）
- **读者专业水平**：初学者 / 中级 / 高级 / 混合
- **读者正在积极尝试解决的问题**（3到5个要点）
- **受众持有的常见误解**（用于锚定信息获取）

### 第2步：定位和规范实体

询问：
- **官方实体名称**（法律或公共品牌名称）
- **主页URL**（规范品牌入口）
- **标志URL或文件路径**（首选方形或SVG资源）
- **sameAs资料**（LinkedIn、X、YouTube、Crunchbase、GitHub或其他官方资料）
- **Wikidata Q-ID**（如果存在；如果无足轻重，则留空）
- **一句品牌使命**（品牌帮助人们做什么）
- **独特的观点**（塑造内容的反传统或非显而易见的信念）
- **这个品牌不是什么**（反定位，永远不该与之混淆）
- **前3个直接竞争对手**，以及与每个竞争对手的一线差异化

### 第3步：编辑规则

询问：
- **必须做列表**（3到7个博客将永远做的事情；例如“只引用主要来源”、“提及从业者而非产品”）
- **禁止做列表**（3到7个博客永远不会做的事情；例如“没有标题党”、“没有列表填充”）
- **禁忌短语**（这个品牌永远不使用的特定词语或短语；与仓库的可选项目样式列表分开）
- **必须披露**（例如关联披露、AI内容披露、利益冲突模式）

### 第4步：主题边界

询问：
- **完全在范围内的主题**（核心内容支柱）
- **部分在范围内的主题**（相邻；仅以原创角度覆盖）
- **超出范围的主题**（不会覆盖；将重定向到合作伙伴内容）
- **重复格式 / 列名**（如果有；例如“每月现场笔记”、“读者问答”）

### 第5步：声音（如果存在，则自动从blog-persona中填充）

询问：
- **代词立场**：第一人称（我们 / 我）、第二人称（你）、第三人称（团队）或混合
- **可接受的缩写**：完整 / 部分无 / 无
- **句子上限**：每句最多单词数作为硬性上限
- **段落上限**：每段最多单词数（默认150）
- **偏爱的标题模式**：编号 / 提问 / 承诺 / 陈述
- **要避免的标题模式**：任何被这个品牌禁止的模式
- **摘要框标签**：来自blog-persona，或选择一个

- **避免**：[列表]

- 尊重 vs 无礼：[0.0到1.0]
- 热情 vs 事实：[0.0到1.0]

- Flesch易读性：[范围]

## 参考样本
- [URL 1]（提取的模式：[摘要])

## 显示流程

1. 检查项目根目录是否存在`BRAND.md`和`VOICE.md`。
2. 如果两个文件都存在，打印摘要表（仅关键部分）和文件路径。
3. 如果一个或两个文件缺失，打印缺失的文件并建议`/blog brand init`。

## 更新流程

与初始化相同，但用当前值预填每个答案。用户可以按Enter接受或输入新值。收集所有答案后，用新内容覆盖两个文件并更新`最后更新：`行。

## 与博客协调器的集成

当运行`/blog write`、`/blog rewrite`、`/blog brief`、`/blog outline`、`/blog calendar`或`/blog strategy`时，协调器（`skills/blog/SKILL.md`）检查项目根目录是否存在`BRAND.md`和`VOICE.md`。如果存在，则内容将被注入系统提示，供下游代理（`blog-researcher`、`blog-writer`、`blog-seo`、`blog-reviewer`）使用。

如果不存在，行为不变。协调器不会提示用户创建它们；它们是可选上下文。

## 与blog-persona的关系

| 关注点 | blog-persona | blog-brand |
|---|---|---|
| 结构化角色JSON用于程序化使用 | 是 | 否 |
| 可读的品牌上下文用于跨技能提示 | 否 | 是 |
| 受众和定位 | 否 | 是 |
| 禁忌短语和编辑禁止 | 部分（禁止列表） | 全部（禁忌 + 披露 + 范围） |
| 竞争对手差异化 | 否 | 是 |
| 主题边界 | 否 | 是 |
| 声音指纹（语气滑块） | 是（规范） | 镜像（只读） |

`blog-brand`不会取代`blog-persona`；它使用它。角色JSON仍然是语气维度、句子长度分布和缩写频率的来源。`VOICE.md`镜像可读部分，以便提示自包含。

如果`/blog brand init`运行时没有角色，声音问题仍然会生成`VOICE.md`。想要程序化强制执行的用户可以在之后运行`/blog persona create`。

## 错误处理

- **项目根目录不明确**：询问用户在哪里写入文件。默认是当前工作目录。
- **初始化时文件已存在**：询问是否覆盖或运行更新。
- **引用了但缺失了角色**：询问是否将角色引用留空或创建一个。
- **读者提供最小答案**：提示至少提供2个受众要点和3个编辑规则；拒绝写入骨架。
