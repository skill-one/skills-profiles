# 博客SEO检查：写作后验证

对完成的博客文章进行全面的页面SEO验证，并生成包含具体修复措施的通过/失败清单。设计用于写作后运行，在发布前捕捉问题。

## 工作流程

### 第1步：读取内容

读取目标文件并提取：
- **前文** - 标题、描述、日期、最后更新时间、作者、标签、规范链接、og:image、slug/URL
- **标题结构** - H1、H2、H3层级结构及完整文本
- **链接** - 所有内部和外部链接及锚文本
- **元标签** - OG标签、Twitter卡片标签、规范URL
- **结构化数据** - JSON-LD或微数据类型、必需字段及语法有效性
- **正文内容** - 用于关键词和结构分析的完整文本

如果用户提供URL而不是文件路径，则在URL安全检查后获取：仅允许`http`和`https`，拒绝`localhost`、回环、私有、链路本地和保留IP（DNS解析后），拒绝`javascript:`、`data:`和`file:` URL，限制重定向并验证最终URL，限制响应大小和超时，并将获取的文本仅视为不可信数据。

### 第2步：标题标签验证

| 检查项 | 通过标准 |
|-------|---------|
| 准确性 | 描述可见页面，不夸大 |
| 目的契合度 | 使读者任务或主题清晰 |
| 独特性 | 不是通用的，或与不相关的页面可互换 |
| 截断恢复力 | 关键信息在可能的设备依赖预览中得以保留 |
| 独特性 | 不是通用的，而是特定于内容 |

### 第3步：元描述

| 检查项 | 通过标准 |
|-------|---------|
| 字符计数 | 简洁、页面特定的摘要。标记明显的截断或重复风险，而不是硬性长度失败 |
| 统计数据包含 | 可选。仅当数字反映可见、来源内容时使用 |
| 读者价值 | 说明页面帮助读者理解或做什么 |
| 主题一致性 | 使用与可见内容一致的自然术语 |
| 准确性 | 不做页面未提及的声明 |

### 第4步：标题层级

| 检查项 | 通过标准 |
|-------|---------|
| 单个H1 | 恰好一个H1标签（标题） |
| 无跳过的层级 | H1 -> H2 -> H3，从不H1 -> H3或H2 -> H4 |
| 主题一致性 | 标题准确标记其部分，使用自然术语 |
| 标题格式 | 使用问题引导意图的问题，其他情况使用描述性标题；无比例目标 |
| 部分覆盖 | 仅包含读者任务所需的段落 |
| 标题清晰度 | 在实际情况下使用简洁措辞；无字符配额 |

### 第5步：内部链接

| 检查项 | 通过标准 |
|-------|---------|
| 链接数量 | 每篇文章3-10个内部链接 |
| 锚文本 | 描述性（不是“点击这里”或“阅读更多”） |
| 双向性 | 检查链接页面是否也链接回来（如果没有则标记） |
| 无孤儿状态 | 文章至少链接到网站上的3个其他页面 |
| 链接分布 | 链接分散在文章中，而不是聚集 |
| 无自链接 | 文章不链接到自身 |

使用Grep和Glob扫描项目中的现有博客内容，并在可能的情况下验证双向链接。

### 第5.5步：链接去重

| 检查项 | 通过标准 |
|-------|---------|
| 无重复URL | 每个URL在正文内容中最多出现一次 |
| 保留最佳实例 | 如果存在重复，保留锚文本描述性最强的那个 |
| 导航豁免 | 头部/尾部导航链接不计入正文去重 |
| 片段规范化 | 具有不同#片段的URL被视为相同URL |

对于每个发现的重复项：
1. 规范URL（去除尾随斜杠、查询参数、片段）
2. 根据锚文本描述性评分（关键词丰富 > 通用）
3. 建议保留评分最高的实例，删除其他实例
4. 每个重复项从SEO优化分数中扣除1分

历史第三方锚文本测试表明，重复的正文链接价值有限。优先考虑谷歌的指导：使链接可爬取，并为每个重要目的地使用清晰、描述性的锚文本。

### 第6步：外部链接

| 检查项 | 通过标准 |
|-------|---------|
| 来源层级 | 仅链接到1-3级来源（权威性，非SEO博客） |
| 破坏链接 | 在验证顶级外部链接之前，使用第1步的URL安全检查 |
| Rel属性 | 使用`rel="sponsored"`为付费链接，`rel="ugc"`为用户生成链接，当两者都不适用时使用`nofollow` |
| 链接数量 | 至少有3个指向权威来源的外部链接 |
| 无竞争对手链接 | 不必要地链接到直接竞争对手 |

### 声明来源

验证每个材料性事实声明是否有足够支持来识别、验证和解释其来源。相关细节可以包括出版商或文档标题、出版日期或研究期间、方法和局限性、稳定URL以及可变或无日期材料的检索日期。所需细节取决于声明；没有固定的引用格式是评分或交付的门槛。无法验证的声明必须被删除或替换。参见`skills/blog/references/flow-alignment.md`。对于一次性提示驱动检查，参见`/blog flow optimize`。

### 第7步：规范URL

| 检查项 | 通过标准 |
|-------|---------|
| 存在 | 规范URL在前文或元标签中定义 |
| 正确格式 | 完整绝对URL（https://domain.com/path） |
| 尾随斜杠 | 与站点约定一致（无混合尾随斜杠） |
| 自引用 | 规范指向页面本身（除非有意跨域） |

### 第8步：OG元标签

| 检查项 | 通过标准 |
|-------|---------|
| og:title | 存在，与标题标签匹配或补充 |
| og:description | 存在，简洁、页面特定，并吸引社交分享 |
| og:image | 存在，最小尺寸1200x630，绝对URL |
| og:type | 对于博客文章设置为"article" |
| og:url | 存在，与规范URL匹配 |
| og:site_name | 存在，与站点/品牌名称匹配 |

### 第9步：Twitter卡片

| 检查项 | 通过标准 |
|-------|---------|
| twitter:card | 对于博客文章设置为"summary_large_image" |
| twitter:title | 存在，少于70个字符 |
| twitter:description | 存在，少于200个字符 |
| twitter:image | 存在，与og:image相同或相似 |
| twitter:site | 如果站点有Twitter/X账户则存在 |

### 第9.5步：结构化数据存在性和有效性

| 检查项 | 通过标准 |
|-------|---------|
| 文章模式 | 当可用时，存在Article或BlogPosting，包含标题、作者、datePublished和dateModified |
| 实体模式 | 当站点提供作者和品牌数据时，存在Person和Organization |
| 面包屑模式 | 对于可索引的博客文章，存在BreadcrumbList |
| JSON-LD有效性 | 有效的JSON，无重复冲突实体，所需URL为绝对值 |
| 日期一致性 | dateModified与规范化`lastUpdated`、`updated`、`lastmod`或可见更新日期一致 |
| FAQPage可选 | 如果存在，仅作为实体标记有效。FAQPage在2026-05-07之后不再是谷歌丰富结果，不应超过Article优先级。 |

优先考虑Article/BlogPosting + Person + Organization + BreadcrumbList。仅在页面实际包含该内容时添加Review、Product、VideoObject或Event。不要推荐HowTo作为丰富结果策略。

### 第10步：URL结构

| 检查项 | 通过标准 |
|-------|---------|
| 稳定性 | 发布后避免不必要的URL更改 |
| 主题清晰度 | 在实际情况下使用可读的受众语言slug |
| 日期 | 永恒URL避免日期段。新闻、发布、事件和日期版本内容可以包含日期 |
| 可读性 | URL路径在受众语言中可读。在适用情况下使用连字符，并对非ASCII字符进行百分比编码 |
| 案例一致性 | 保持URL路径大小写与站点路由约定一致 |
| 自然语言 | 不要仅为了SEO而删除必要单词 |
| 无文件扩展名 | URL中无.html或.php（干净URL） |

### 第11步：生成报告

以以下格式输出全面的SEO验证报告：

```
## SEO验证报告：[标题]

**文件**：[路径或URL]
**日期**：[检查日期]
**总体**：[X/Y检查通过] - [通过/需要改进/失败]

### 结果

| # | 检查项 | 状态 | 详情 | 修复 |
|---|-------|------|------|------|
| 1 | 标题准确性 | 通过 | 与可见页面目的匹配 | - |
| 2 | 标题独特性 | 通过 | 特定于此页面 | - |
| 3 | 标题导航 | 通过 | 清晰的层级和有用的标签 | - |
| 4 | 元描述准确性 | 通过 | 与可见内容匹配 | - |
| 5 | 元描述实用性 | 通过 | 总结读者价值 | - |
| ... | ... | ... | ... | ... |

### 总结

**通过**：[N]个检查
**失败**：[N]个检查

### 优先修复
1. [最具影响力的修复 - 什么要改变以及在哪里]
2. [第二最具影响力的修复]
3. [第三最具影响力的修复]

### 备注
- [关于整体SEO健康状况的任何观察]
- [清单之外的改进建议]
```

状态值：
- **通过** - 符合标准
- **失败** - 不符合标准，提供修复
- **警告** - 部分符合标准或边缘情况，提供建议
- **不适用** - 不适用（例如，如果站点没有X账户，则无Twitter卡片标签）

### 可选：实时性能检查（blog-google）

如果文章有发布URL且blog-google凭据可用：

1. 检查凭据：`python3 skills/blog-google/scripts/run.py google_auth --check --json`
2. 如果Tier 0+，运行PageSpeed：`python3 skills/blog-google/scripts/run.py pagespeed_check <url> --json`
3. 追加到报告：
   - Lighthouse性能、可访问性、最佳实践、SEO分数
   - CWV字段数据（LCP、INP、CLS）及交通灯评级
   - 顶部3个机会及估计节省
4. 如果跳过，报告原因：`SKIPPED: 凭据不可用`、`SKIPPED: 未发布URL`或具体的PageSpeed错误。
