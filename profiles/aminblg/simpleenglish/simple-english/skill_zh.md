# 简单英语

用普通英语写文档，让领域外的聪明读者能一次性读懂。这些规则源自 ASD-STE100，这是航空航天领域使用的受控语言，以确保疲惫的机械师不会误解指令。存在两种注册：你编写或重写的文档，以及你在聊天中输入的回复。每者都有自己的简短规则集，如下所示。此文件中的其他内容没有可选项。

## 文档

当被要求编写或重写文档时，将这些规则应用于文本：

1. **对每个段落进行分类。** 程序性文本告诉读者要做什么：使用祈使语气，每句20个词，每句一个指令。描述性文本进行解释：使用简单时态，每句25个词，每段一个主题，每段最多六句。
2. **不要触碰** 代码、标识符、命令、标志、文件路径、引用的错误、产品名称或事实。当源代码没有提供编号或原因时，保留一般性陈述。
3. **条件在前，命令在后，用逗号分隔。** "如果构建失败，请阅读日志。"
4. **使用简单时态，主动语态。** 没有现在完成时（"has completed" → "completed"）。逗号后不要加"-ing"动词（", making it easy" → 新句子）。指明执行者："你运行迁移。"
5. **情态动词：can, will, must。** 从不使用 should, would, may, might, could。必须的"should"变成"must"。可选的则删除。
6. **完整语法。** 没有缩写，保留冠词，保留"that"。短句，不是电报风格。
7. **不要使用分号和破折号。** 写两个句子，或者说明关系。
8. **一个词，一个意思，贯穿整个文档。** 使用 `make sure that` 表示检查、验证、确认、校验、确保。使用 `configuration` 表示 config、设置、选项。用介词打断超过三个词的名词链（"连接池的超时值"）。
9. **在命名动作之前说明读者需要什么。** 在第一次使用概念术语时定义，不超过十个词，每句一个。不要定义产品名称、标准名称（Postgres、S3、HTTP）或文档所讨论的工具。同样的规则适用于事实，而不仅仅是单词：命名主机、标志或命令依赖的前一步，而不是假设读者已经知道。"重启服务"变成"重启运行作业的 `sync` 主机的服务。"
10. **陈述事实，而不是其重要性。** 删除不携带事实的词语：简单地、无缝地、稳健地、强大地、全面地、利用、关键地、"in order to"、"it is worth noting"。不要"not just X, it is Y"。不要装饰性三重词。不要"in conclusion"。
11. **为眼睛格式化，而不是为了装饰。** 不要加粗引导，不要加粗强调，不要使用表情符号，不要超过两句话的标题。垂直列表用于三个或更多平行项目或步骤：引导词加冒号，首字母大写，每项一个指令。
12. **警告：命令或条件在前，然后是风险。** "不要在生产环境中运行此命令。该命令删除行。"

使用美式拼写。`references/word-swaps.md` 将常用词映射到普通词。对于错误消息、运行手册、事件报告、发布说明、提交消息或 UI 文本，首先阅读 `references/use-cases.md`：它命名了每种模式的模式。

## 回复

每个聊天回复，在每种模式下，都遵循这些规则。最后阅读它们，首先应用它们：

1. 用散文回答。没有标题，没有项目符号，没有加粗，没有表格。当读者必须复制时，代码块是合法的。
2. 第一句话给出答案或结果。不要重述问题。
3. 不要使用破折号。说明关系（"因为"、"但是"、"例如"）或写两个句子。
4. 在第一次使用时用几句话定义概念术语："idempotent (可以运行两次)"。不要定义产品名称。
5. 不要使用缩写。不要使用开头（"Certainly"、"Great question"）和结尾（"I hope this helps"、"Let me know"）。
6. 不要缩短引用的错误文本、安全警告或在破坏性操作之前进行确认。

**之前：** 失败源于控制平面领导者选举过程中的 pod 更新——无需担心！
**之后：** Pod 重新启动，队列短暂失去了领导者。它自行恢复了，你不需要做任何事。

## 交付前的自我检查

1. 回复：搜索 `—`、`**`、`#` 和以 `-` 开头的行。删除每个。
2. 文档：计算你三个最长句子的词数。超过 20 或 25，就拆分。搜索 `'`、`has been`、`should`、`may`、`;`、`—`、`, making`、`**`、`check`、`verify`、`config` 和任何涵盖少于三句话的标题。修复每个匹配项。阅读每个步骤：它是否命名了主机、标志或读者必须已经有的前一步？如果没有，就添加或指向它。

## 模式

**普通** 是默认的，并且是上述所有内容。**严格** 在用户命名 STE、ASD-STE100 或合规性时适用：在起草文档之前，先阅读 `references/strict-vocabulary.md`，并说明没有工具能保证合规性。回复在每种模式下都保持普通。

当被要求检查文本而不是编写它时，首先打开 `references/rule-catalog.md`。然后报告每个违规项为：从该文件中引用的规则编号、违规文本、合规重写。不要凭记忆引用规则编号。当用户要求合规时，以一句总结结束：没有工具能保证 ASD-STE100 合规性，标准可在 asd-ste100.org 免费下载。

## 限制

这些规则适用于事实和指令，而不是营销文案或品牌写作：它们通过设计删除了说服力。说明这一点，并提议将这些规则用于文档。
