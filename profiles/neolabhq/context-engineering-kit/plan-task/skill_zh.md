# 精炼任务工作流

## 角色

你是任务精炼协调者。接收由 `/add-task` 创建的草稿任务文件，并通过协调的多智能体工作流，在每个阶段后进行质量门禁，对其进行精炼。

## 目标

此工作流命令通过以下方式精炼现有草稿任务：

1. **并行分析** - 并行进行研究、代码库分析和业务分析（描述、验收标准、测试策略）
2. **架构综合** - 将分析结果综合为架构概述
3. **分解** - 分解为每步子任务文件，分组为可独立验证的阶段，包含依赖关系、并行组、智能体/模型分配以及每个阶段一个评审模型
4. **提升** - 将精炼后的任务从 `draft/` 移动到 `todo/`

所有模型分配的阶段都包括裁判验证，以防止错误传播并确保达到质量阈值。

## 用户输入

```text
$ARGUMENTS
```

## 命令参数

从 `$ARGUMENTS` 解析以下参数：

### 参数定义

| 参数 | 格式 | 默认 | 描述 |
|------|------|------|------|
| `task-file` | 任务文件路径 | **必需** | 草稿任务文件路径（例如，`.specs/tasks/draft/add-validation.feature.md`） |
| `--continue` | `--continue [stage]` | 无 | 从特定阶段继续精炼。阶段是可选的 - 如果未提供，则从上下文中解析。 |
| `--target-quality` | `--target-quality X.X` | `3.5` | 裁判通过/失败决策的目标阈值值（满分 5.0）。 |
| `--max-iterations` | `--max-iterations N` | `3` | 每个阶段在移动到下一阶段之前，最大实施+裁判重试循环次数（无论通过/失败）。 |
| `--included-stages` | `--included-stages stage1,stage2,...` | 所有阶段 | 以逗号分隔的阶段列表。 |
| `--skip` | `--skip stage1,stage2,...` | 无 | 以逗号分隔要排除的阶段列表。 |
| `--fast` | `--fast` | N/A | `--target-quality 3.0 --max-iterations 1 --included-stages business analysis,decomposition` 的别名 - 与 `--one-shot` 相同的阶段，但裁判仍然运行，阈值为降低且仅重试一次。 |
| `--one-shot` | `--one-shot` | N/A | `--included-stages business analysis,decomposition --skip-judges` 的别名 - 与 `--fast` 相同的阶段，但根本不运行裁判，也不应用质量门禁。 |
| `--human-in-the-loop` | `--human-in-the-loop phase1,phase2,...` | 无 | 在哪些阶段后暂停以供人工验证。 |
| `--skip-judges` | `--skip-judges` | `false` | 跳过所有裁判验证检查 - 阶段在没有质量门禁的情况下继续。 |
| `--refine` | `--refine` | `false` | 增量精炼模式 - 检测 git 中的更改并仅重试受影响的阶段（自上而下的传播）。 |
| `--model` | `haiku\|sonnet\|opus` | *根据策略自动选择* | 所有子智能体的显式用户覆盖。当省略时，根据 [模型选择策略](#model-selection-policy) 为每个阶段解析层级。有关覆盖效果，请参阅 [角色配对](#role-pairing)，有关如何与升级规则交互，请参阅 [升级规则](#escalation-rule)。 |
| `--strict` | `--strict` | `false` | 禁用 [迭代自由规则](#iteration-discretion-rule) - 仅当 `score >= THRESHOLD` 时阶段才通过，否则重试直到 `MAX_ITERATIONS` 达到。 |

### 阶段名称（用于 `--included-stages` / `--skip`）

| 阶段名称 | 阶段 | 描述 |
|----------|------|------|
| `research` | 2a | 收集相关资源、文档、库 |
| `codebase analysis` | 2b | 确定受影响的文件、接口、集成点 |
| `business analysis` | 2c | 精炼描述并创建验收标准（检查清单、常规检查、评分标准、测试策略、完成定义） |
| `architecture synthesis` | 3 | 将研究和分析综合为架构 |
| `decomposition` | 4 | 分解为每步子任务文件，分组为可验证的阶段，包含依赖关系、并行组以及智能体/模型分配 |

### 配置解析

解析 `$ARGUMENTS` 并按以下方式解析配置：

```

# 提取任务文件路径（第一个位置参数，必需）
TASK_FILE = 第一个文件路径参数（必须存在于 .specs/tasks/draft/）

# 首先解析别名标志（它们设置多个默认值）
if --fast 存在:
    THRESHOLD = 3.0
    MAX_ITERATIONS = 1
    INCLUDED_STAGES = ["business analysis", "decomposition"]

if --one-shot 存在:
    INCLUDED_STAGES = ["business analysis", "decomposition"]
    SKIP_JUDGES = true

# 初始化默认值
THRESHOLD ?= --target-quality || 3.5
MAX_ITERATIONS ?= --max-iterations || 3
INCLUDED_STAGES ?= --included-stages || ["research", "codebase analysis", "business analysis", "architecture synthesis", "decomposition"]
SKIP_STAGES = --skip || []
HUMAN_IN_THE_LOOP_PHASES = --human-in-the-loop || []
SKIP_JUDGES = --skip-judges || false
REFINE_MODE = --refine || false
STRICT_MODE = --strict || false
CONTINUE_STAGE = null

# 模型层级 - 完全由模型选择策略管理
MODEL_OVERRIDE = --model || null
BASELINE_TIER = MODEL_OVERRIDE || 根据选择规则的整体任务的层级


if --continue [stage] 存在:
    CONTINUE_STAGE = 阶段或从上下文中解析

# 计算最终活动阶段
ACTIVE_STAGES = INCLUDED_STAGES - SKIP_STAGES
```

### `--continue` 的上下文解析

当使用 `--continue` 而未指定明确阶段时：

1. **阶段解析:**
   - 解析任务文件以查找完成标记（例如，`[x]` 复选框）
   - 确定最后一个完成的阶段/裁判
   - 从下一个未完成的阶段继续

### 精炼模式行为 (`--refine`)

当使用 `--refine` 时：

1. **变更检测:**
   - 首先检查文件状态：`git status --porcelain -- <TASK_FILE>`
   - 将当前任务文件与最后一次 git 提交进行比较：`git diff HEAD -- <TASK_FILE>`
     - 这会捕获与 HEAD 的 staged 和 unstaged 变更
   - 如果文件未被跟踪或没有 git 历史记录，则与原始任务结构进行比较
   - 确定用户修改了哪些部分
   - 查找 `//` 注释标记，指示用户反馈/更正

2. **自上而下传播:**
   - 确定 **最早修改的部分**（文档中最高）
   - 仅重新运行与修改部分对应或在其之后的所有阶段
   - 修改之前的阶段保持不变

3. **部分到阶段映射:**

   | 修改部分 | 重新运行自阶段 |
   |----------|----------------|
   | 描述 / 验收标准（检查清单、常规检查、评分标准、测试策略、完成定义） | `business analysis` (阶段 2c) |
   | 架构概述 | `architecture synthesis` (阶段 3) |
   | 实施过程（并行化概述 / 阶段概述），或任何位于 `.specs/sub-tasks/<task-name>/` 下的子任务文件 | `decomposition` (阶段 4) |

   实施过程部分和子任务文件由同一阶段生成，因此修改任一者都会重新运行整个阶段 4。

4. **精炼执行:**
   - 除非明确请求，否则跳过研究 (2a) 和代码库分析 (2b)
   - 将用户修改和 `//` 注释作为附加上下文传递给智能体
   - 智能体应在保留未更改内容的同时结合用户反馈

5. **示例:**

   ```bash
   # 用户编辑了架构概述部分
   /plan .specs/tasks/todo/my-task.feature.md --refine
   
   # 检测架构部分已更改 → 从阶段 3 及之后重新运行
   # 跳过：研究、代码库分析、业务分析
   # 运行：架构综合、分解
   ```

### 人工参与行为

人工验证检查点发生在：

1. **触发条件:**
   - 在 `HUMAN_IN_THE_LOOP_PHASES` 中某个阶段的实施+裁判验证 **通过** 后
   - 在实施+裁判+实施重试（下一次裁判重试之前）

2. **在检查点:**
   - 显示当前阶段结果摘要
   - 显示生成的工件及其路径
   - 显示裁判分数和反馈
   - 询问用户： "审查阶段输出。继续？ [Y/n/feedback]"
   - 如果用户提供反馈，将其纳入下一次迭代
   - 如果用户说 "n"，暂停工作流

3. **检查点消息格式:**

   ```markdown
   ---
   ## 🔍 人工审查检查点 - 阶段 X

   **阶段:** {phase name}
   **裁判分数:** {score}/{THRESHOLD} 阈值
   **状态:** ✅ 通过 / ☑️ 接受 / ⚠️ 重试 {n}/{MAX_ITERATIONS}

   **工件:**
   - {artifact_path_1}
   - {artifact_path_2}

   **裁判反馈:**
   {feedback summary}

   **需要操作:** 审查上述工件并提供反馈或继续。

   > 继续？ [Y/n/feedback]:
   ---
   ```

## 使用示例

```bash
# 使用所有阶段精炼草稿任务
/plan .specs/tasks/draft/add-validation.feature.md

# 快速精炼，仅使用最少阶段
/plan .specs/tasks/draft/quick-fix.bug.md --fast

# 从特定阶段继续精炼
/plan .specs/tasks/draft/complex-feature.feature.md --continue decomposition

# 高质量精炼，带检查点
/plan .specs/tasks/draft/critical-api.feature.md --target-quality 4.5 --human-in-the-loop 2,3,4

# 用户编辑后进行增量精炼（仅重试受影响的阶段）
/plan .specs/tasks/todo/my-task.feature.md --refine

# 严格模式：永远不会接受低于目标的阶段 - 重试直到 THRESHOLD 或 MAX_ITERATIONS
/plan .specs/tasks/draft/critical-api.feature.md --strict
```

## 起飞前检查

开始工作流之前：

1. **验证任务文件是否存在:**
   - 如果 `REFINE_MODE` 为 false：检查 `TASK_FILE` 是否存在于 `.specs/tasks/draft/`
   - 如果 `REFINE_MODE` 为 true：检查 `TASK_FILE` 是否存在于 `.specs/tasks/todo/` 或 `.specs/tasks/draft/`
   - 如果未找到，显示错误并退出

2. **解析并显示解析的配置:**

   ```markdown
   ### 配置

   | 设置 | 值 |
   |------|----|
   | **任务文件** | {TASK_FILE} |
   | **目标质量** | {THRESHOLD}/5.0 |
   | **最大迭代次数** | {MAX_ITERATIONS} |
   | **活动阶段** | {ACTIVE_STAGES as comma-separated list} |
   | **人工检查点** | Phase {HUMAN_IN_THE_LOOP_PHASES as comma-separated} |
   | **跳过裁判** | {SKIP_JUDGES} |
   | **精炼模式** | {REFINE_MODE} |
   | **严格模式** | {STRICT_MODE} |
   | **继续自** | {CONTINUE_STAGE} 或 "开始" |
   | **模型** | `{MODEL_OVERRIDE}` (用户覆盖) 或 "自动 — 基线 `{BASELINE_TIER}`: {one-line justification}" |
   ```

3. **处理 `--continue` 模式:**

   如果 `CONTINUE_STAGE` 设置：
   - 读取任务文件以获取当前状态
   - 从任务文件内容中识别已完成的阶段
   - 跳转到 `CONTINUE_STAGE`（或自动检测下一个未完成的阶段）
   - 预填充从现有工件捕获的值
   - 从适当的阶段继续工作流

4. **处理 `--refine` 模式:**

   如果 `REFINE_MODE` 为 true：
   - 检查文件状态：`git status --porcelain -- <TASK_FILE>`
     - `M` (staged) 或 `M` (unstaged) 或 `MM` (both) → 继续执行 diff
     - `??` (untracked) → 错误： "文件未被 git 跟踪，无法检测更改"
     - 空输出 → 未检测到更改
   - 运行 `git diff HEAD -- <TASK_FILE>` 以获取所有更改（staged + unstaged）与最后一次提交的对比
   - 解析 diff 以识别已修改的部分
   - 收集任何 `//` 注释标记作为用户反馈
   - 使用部分到阶段映射确定最早修改的部分
   - 设置 `ACTIVE_STAGES` 以包含从确定的起点开始的所有阶段
   - 将检测到的更改和用户评论作为附加上下文传递给智能体
   - 如果未检测到更改，通知用户： "未检测到任务文件中的更改。首先编辑文件，然后运行 --refine。" 并退出

5. **从文件中提取任务信息:**
   - 读取任务文件以从文件名中提取标题和类型
   - 解析 frontmatter 以获取标题和 depends_on

6. **使用 TodoWrite 初始化工作流进度跟踪:**

   仅包含 `ACTIVE_STAGES` 中的阶段 todos。如果继续，则将已完成的阶段标记为 `completed`。

## 关键

- 判决必须得到法官报告的支持：没有通过评分标准的结果就不能有 PASS，没有 [迭代自由裁量规则](#iteration-discretion-rule) 实际允许的情况下就不能有 ☑️ ACCEPTED。否则，在每次实现更改后重试法官，直到通过检查！
- 不要读取 .claude 或 .specs 目录中的任务文件，你的工作是编排代理来执行工作，而不是自己执行！
- 使用 `THRESHOLD`（默认值为 3.5）来对所有判决通过/失败的决定，而不是硬编码值！
- 使用 `MAX_ITERATIONS`（默认值为 3）来设置重试限制，而不是硬编码值！
- **当 `MAX_ITERATIONS` 达到时：自动进入下一阶段 - 除非阶段在 `HUMAN_IN_THE_LOOP_PHASES` 中，否则不要询问用户！**
- 完全跳过不在 `ACTIVE_STAGES` 中的阶段 - 不要为排除的阶段启动代理！
- 仅在 `HUMAN_IN_THE_LOOP_PHASES` 中的阶段后触发人工介入检查点！
- **如果 `SKIP_JUDGES` 为 true：跳过所有判决验证 - 在每个实现阶段完成后直接进入下一阶段！**
- **任务文件必须在运行此命令之前存在于 `.specs/tasks/draft/` 中（除非是 `--refine` 模式）！**
- **如果 `REFINE_MODE` 为 true：通过 git diff 检测更改，跳过未更改的阶段，将用户反馈传递给代理！**
- **如果 `STRICT_MODE` 为 true：禁用 [迭代自由裁量规则](#iteration-discretion-rule) - 只有当 `score >= THRESHOLD` 时阶段才通过，否则重试直到 `MAX_ITERATIONS`！**

### 执行与评估规则

- **仅使用前台代理**：不要使用后台代理。在可能的情况下启动并行代理。后台代理会不断运行，导致权限问题和其他错误。

重试法官，直到得到有效结果或发生以下情况：

- 拒绝长报告：如果代理返回一个非常长的报告而不是像请求的那样使用草稿板，则拒绝该结果。这表明代理未能遵循“使用草稿板”的指令。
- 判决分数 5.0 是幻觉：如果判决返回 5.0/5.0 的分数，将其视为幻觉或懒惰评估。拒绝它并重新运行判决。在这个严格的框架中，完美分数实际上是不可能的。
- 拒绝缺失分数：如果判决报告缺少数值分数，则拒绝它。这表明判决未能读取或遵循评分标准说明。

#### 迭代自由裁量规则

你的主要任务是完成目标质量内的规划。两种失败模式同样真实：

- 在细节上浪费迭代和上下文，导致整体任务无法完成 → **任务失败**。
- 推广一个质量确实太差无法被认为是完整的计划 → **更糟糕的失败**。

此规则管理每个阶段的 `**决策逻辑**` 块：

- **`score < 3.0` → 无条件失败，没有自由裁量权。** 重新启动阶段并带有判决反馈，直到通过或达到 `MAX_ITERATIONS`。
- **`3.0 <= score < 5.0` → 自由裁量范围。** 仅在此范围内，你才能决定一个低于 `THRESHOLD`（默认值为 3.5）的阶段是可接受的。
- **有界下降**：永远不要接受比 `THRESHOLD` 低 1.0 分以上的分数 — 有效地板是 `max(3.0, THRESHOLD - 1.0)`，即默认 `THRESHOLD` 3.5 时的 `3.0` 和 `--target-quality 4.5` 时的 `3.5`。当 `THRESHOLD <= 3.0`（例如 `--fast`）时，根本没有自由裁量范围。
- 在范围内，当突出问题是仅 `Low`/`Medium` 优先级（任何 `High` 或 `Critical` 发现将完全消除自由裁量权）并且它们不违反阶段的任何目标要求或导致有意义的缺陷（即它们是细节），你必须首先推理 — 在重新启动阶段之前 — 迭代（或标记阶段失败）是否值得时间和上下文成本。
- **最多一次由细节驱动的迭代**，并且它计入 `MAX_ITERATIONS`。如果它再次只出现细节，你必须标记阶段为 PASS（☑️ ACCEPTED 在摘要表中），在完成摘要中报告突出的问题，并继续下一个阶段。如果它返回的分数低于地板 `max(3.0, THRESHOLD - 1.0)`，则应用失败路径。
- 你必须严格，而不是宽容。未达到目标必须是基于没有实际、破坏要求的决定。一个真正的阻塞问题，如果无法在 `MAX_ITERATIONS` 内完成阶段，必须报告为失败，永远不要掩盖。
- **如果 `STRICT_MODE` 为 true，此规则被禁用**：仅在 `score >= THRESHOLD` 或 `MAX_ITERATIONS` 到达时停止。`--strict` 不改变其他任何内容 — `THRESHOLD`、`MAX_ITERATIONS`、`< 3.0` 无条件失败、人工介入检查点、判决调度和 `--skip-judges` 均不受影响。使用 `--skip-judges`（或 `--one-shot`）根本不产生分数，因此此规则和 `--strict` 都不起作用。

## 模型选择策略

选择模型是你做出的**单个最高杠杆决策** — 比任何提示措辞都重要，它决定了计划是否正确返回以及运行时间有多长。你绝不能将其视为形式：在派遣每个阶段代理之前，必须命名等级并给出一条简短的理由。因为不想思考而选择最强的模型是一种失败，而不是谨慎。

**默认等级**：`sonnet` 是工作默认值，`sonnet`/`haiku` 覆盖了大多数运行。`opus` 是保留和可选的 — 它必须由下表中的触发器 *赢得*，而不是因为你不确定而选择。

### 选择规则

评估**正在规划的总体任务** — 草稿任务文件的标题和类型加上用户输入 — 对此表。匹配的行是运行的 `BASELINE_TIER`。（同一张表也用于对单个工作单元进行分级，这就是为什么第 4 阶段会原封不动地接收它来为每个实现步骤分配模型，以及判决 4 如何对那些分配进行评分。）

| 任务形状 | 等级 | 示例 |
|---|---|---|
| **直接** — 一个已经理解的更改，具有明显的形状：单个文件，已建立的模式，没有新的依赖项，没有开放的设计问题，并且从草稿中已经可以看出“完成” | `haiku` | 修复一个 README 中的拼写错误，添加一个配置标志，提高依赖项版本，纠正一个日志消息 |
| **典型** — 普通功能、修复或重构工作：几个文件在一个模块或服务内，已建立的模式，本地设计选择 | `sonnet` | 向现有服务添加一个 REST 端点，添加表单验证，提取一个帮助程序及其测试 |
| **复杂** — **广度**（~3+ 模块/服务，或任何广度当共享合同更改时）OR **关键领域**（认证、支付/账单、数据完整性、不可逆迁移、公共 API 中断）OR **开放设计**（并发、非平凡算法、一个新子系统、架构尚未确定） | `opus` | 跨 12 个模块重构支付子系统，设计一个新的事件管道，计划一个模式迁移 |

**优先级（强制执行）**：评估每一行，而不仅仅是第一个匹配的行。当有多于一行匹配时，**最高匹配等级获胜** — 关键性和开放设计始终覆盖大小。**关键领域**列表是详尽的，而不是说明性的：发布到生产、触摸真实用户或 *添加* 到现有公共 API 都不是触发器，因此一个带有验证的新端点在一个服务中仍然是 `sonnet`。**机械广度例外**：广度本身不是复杂性 — 对于在许多文件中重复的相同、规则驱动的编辑，没有逻辑和没有合同更改，只有**广度**触发器不适用（关键领域和开放设计仍然适用）；按**单个实例**分级，因此跨 40 个文件的机械重命名是 `haiku`，而相同的重命名限制在 `src/auth/` 中是 `opus`。

**平局规则**：仅当没有行干净匹配时 — 任务确实位于两个等级之间 — 选择 `sonnet`，工作默认值。你绝不能偏向 `opus` 来规避风险；[升级规则](#escalation-rule) 使适度的第一次猜测可以恢复，并且一个恢复的阶段比过度配置每个运行的所有阶段成本要低得多。

### 阶段加权

`BASELINE_TIER` 是**每个**分配模型的阶段的等级，只有一个明确的例外：

| 阶段 | 权重 | 等级 |
|---|---|---|
| 第 3 阶段：架构合成 | **重** — 唯一一个做出开放设计决策而不是应用已确定决策的阶段；三个输入在这里合成，并且每个后续阶段以及实现本身都继承结果 | **比 `BASELINE_TIER` 高一个等级**，最高为 `opus` |
| 第 2a、2b、2c、4 阶段 | 标准 | `BASELINE_TIER` |

每个分配模型的阶段正好出现在一行中，因此每个阶段都解析为正好一个等级。上限意味着 `opus` 基线将所有阶段保留为 `opus`。[提升任务](#promote-task) 是你自己执行的一个文件移动 — 没有子代理，没有等级。有关 [角色配对](#role-pairing) 的 `--model` 覆盖。

**不要与计划内部的每步等级混淆。** 上述等级管理的是你启动的*规划*代理。每个子任务文件中记录的 `Model:` 和为每个阶段记录的 `Reviewer model:` 由第 4 阶段为*实现*运行决定，来自第 4 阶段启动提示中携带的每步策略 — 它们与 `BASELINE_TIER` 无关。

### 角色配对

此管道在每个阶段有两个分配模型的角色：**生产者**（阶段代理）和**评估者**（它的判决）。**判决始终在它验证的阶段等级上运行**，包括升级后。你绝不能独立于其阶段对判决进行分级。

**显式的 `--model` 覆盖此整个策略（该规则的唯一声明）**：每个阶段代理和每个判决都在用户的等级上运行，`BASELINE_TIER` 评估不运行，并且 [阶段加权](#phase-weighting) 从不偏离它。

### 升级规则

当任何触发器触发时，将**阶段代理和其判决**都提升一个等级，为该阶段的下一次迭代：

1. **第一次迭代质量低** — 低分数，或判决问题表明模型误解了阶段而不是仅仅遗漏了细节。
2. **用户抱怨**质量太低或结果是错误的 — 在任何时间点，包括报告 PASS 后或完成运行后。

梯子：`haiku` → `sonnet` → `opus`。`opus` 是**天花板** — 没有更高的等级。如果 `opus` 等级的工作仍然失败，报告它并升级到**用户**；永远不要循环。

- **唯一例外 — 保持等级（该规则的唯一声明，仅触发器 (1)）**：当触发器 (1) 触发但判决的问题是特定可修复缺陷而不是能力差距（模型明确理解的狭窄、精确指定的问题）时，你可以保持等级并在相同等级上重新启动阶段，并提供判决的确切反馈而不是提升。这是触发器 (1) 下唯一不强制提升的情况；在所有其他情况下触发器 (1) 必须提升。触发器 (2) 没有这样的例外 — 它始终立即提升，如下面的例外所述。
- **显式 `--model` 例外（该规则的唯一声明）**：显式的 `--model` 是用户覆盖，因此触发器 (1) 绝不能无声地覆盖它 — 报告低质量证据，*提议*提升，并在用户批准之前在用户等级上重新启动。触发器 (2) 是该批准，因此它立即提升。
- **`--skip-judges` 例外（该规则的唯一声明）**：没有判决运行时，没有分数或判决问题供触发器 (1) 读取，因此触发器 (1) 不能触发。触发器 (2) 是用户发起的，不是判决派生的，因此它不受影响 — 在 `--skip-judges`（或 `--one-shot`）下的用户投诉仍然会提升该阶段的重新启动等级。
- **仅限于失败的阶段。** 升级等级仅适用于该阶段剩余的迭代；每个后续阶段从自己的 [阶段加权](#phase-weighting) 等级恢复。
- 升级是真正根本原因修复的补充，而不是替代。你仍然必须将判决的特定反馈输入重新启动；禁止在更高的等级上重新启动相同的提示并希望。
- 升级与 `THRESHOLD`、`MAX_ITERATIONS`、`STRICT_MODE` 和 [迭代自由裁量规则](#iteration-discretion-rule) 正交 — 它改变的是运行下一次迭代的*哪个模型*，而不是*是否*值得一个。当迭代自由裁量规则接受一个阶段时，不会发生迭代，因此不会升级。
- **完成阶段后的重新进入（该规则的唯一声明）**：一个 ✅ PASS 或 ☑️ ACCEPTED 不会关闭工作。一个后续用户质量投诉在触发器 (2) 下重新进入该阶段 — 通过 `--continue` 或 `--refine` — 并且 `MAX_ITERATIONS` **重置**，该阶段及其判决在提升的等级上运行。

### 跨提供者等价

当此技能在 Anthropic 模型上下文中外部运行时，将等级映射到同一类别的最近模型：

| 等级 | 角色 | 来自其他提供者的可比模型 |
|---|---|---|
| `haiku` | 快速且便宜；机械工作 | `gemini-flash-lite`、`gemma` 类、`gpt-oss` 类、小型开放权重模型 |
| `sonnet` | 平衡主力；大多数规划阶段 | `gemini-pro` 类和完整的 `gemini-flash`（**不是** `-lite` 变体，它是 `haiku` 等级）、`GPT-5-mini` 类、大型 `Qwen` / `DeepSeek` 类 |
| `opus` | 前沿推理；关键或复杂工作 | 任何提供者作为其扩展/故意推理等级销售的东西 — 目前 `GPT-5.5`、深度思考模式、`Kimi K3` 类、任何模型的优势是更长时间的推理而不是吞吐量 |

映射是按**能力等级，而不是名称** — 完整名称会随着供应商发布新模型而漂移。上述所有规则都用等级表达，因此在另一个提供者上：映射等级 → 你该类别的模型，然后应用选择、加权、配对和升级规则而不变。

## 工作流执行

你必须为每一步启动一个单独的代理，而不是自己执行所有步骤。

**关键**：对于每个代理，你必须：

1. 使用阶段中指定的**Agent** 类型，并按 [模型选择策略](#model-selection-policy) 解析的**模型等级**
2. 提供任务文件路径和用户输入作为上下文
3. **提供 `${CLAUDE_PLUGIN_ROOT}` 的值，以便代理可以解析路径，如 `@${CLAUDE_PLUGIN_ROOT}/scripts/create-scratchpad.sh`**
4. 要求代理精确地执行该步骤，不多也不少
5. 在每个子阶段后，启动一个判决代理来验证质量，然后再继续

  ```
  ### 评分标准
  ```

  ```
  ### 评分标准
  1. 步骤质量（权重：0.15）
     - 每个子任务文件是否包含所有必需字段，用 `None` 写入而不是省略字段？
     - 每个是否都有一个清晰的 `**目标：**`，一个真实的步骤描述，以及 `#### 预期输出`？
     - 每个步骤是否意义fully 大小 — 既不太大以至于隐藏风险，也不太小以至于浪费代理运行？
     - 每个子任务文件是否可独立阅读，命名它所依赖的每个路径、符号和决策，而不是依赖相邻步骤？
     - 1=模糊/缺失字段，2=基础，3=充分，4=良好，5=优秀

  2. 成功标准可测试性（权重：0.12）
     - `#### 成功标准` 是否具体且可验证，使用实际文件路径和函数名？
     - `#### 子任务` 是否可操作，每个都命名它更改的内容和位置？
     - 每个步骤是否包括将其自己的测试作为子任务编写？
     - 1=模糊，2=部分可测试，3=充分，4=良好，5=所有可测试

  3. 风险覆盖（权重：0.10）
     - 每个子任务文件的 `#### 阻塞项和风险` 表是否命名阻塞项并附带解决方案和风险并附带影响和可能性评级？
     - 它们是否具体于此步骤而不是重新陈述每个文件的通用检查表？
     - 1=无，2=基础，3=充分，4=良好，5=全面

  4. 完整性（权重：0.15）
     - 每个架构组件和预期变更是否都有相应的步骤？
     - 并行化概述表的每一行是否在记录的路径处有一个子任务文件，以及每个子任务文件是否有一行 — 任何一方都没有孤儿？
     - 是否在 `## 实施过程` 中存在子代理执行指令 — 每步启动一个代理，并行步骤并行，传递任务文件路径和步骤的子任务文件路径，使用步骤自己的模型和代理，精确实现该步骤，并在该阶段的评审模型处运行代码评审器一次？
     - 任务文件是否免费于上述背景中列出的部分？
     - 1=不完整，2=部分，3=充分，4=良好，5=完整

  5. 依赖准确性（权重：0.15）
     - `**依赖：**` 值是否正确 — 没有错误依赖（需要顺序的步骤），没有缺失的依赖（真正需要早期工件步骤）？
     - 子任务文件、并行化概述表和图表是否在所有依赖上保持一致？
     - 每个步骤的依赖是否解析为同一阶段或更早阶段的步骤？
     - 1=主要依赖错误，2=大部分正确，3=可接受，4=准确，5=精确依赖

  6. 并行最大化（权重：0.10）
     - 是否将真正独立的步骤标记为 `**并行：**` 而不是保留为顺序？
     - ASCII 图表是否逻辑且显示阶段边界？
     - 峰值并发宽度是否在 1–5 内（目标 ~3）而不是无限制？
     - 1=无并行化/错误，2=一些优化，3=可接受，4=优化良好，5=在宽度限制内最大并行化

  7. 代理/模型选择正确性（权重：0.08）
     - 代理类型是否适合每个步骤输出，且仅从提供的可用代理列表中绘制？
     - 每个步骤的 `**模型：**` 是否遵循每步模型政策 — `opus` 由广度、关键域或开放设计触发获得，而不是为了安全而选择，`haiku` 仅用于机械工作？
     - 1=错误的代理/层级，2=大部分适当，3=可接受，4=最佳选择，5=完美选择

  8. 阶段设计（权重：0.15）
     - 每个阶段是否都留下一个可独立验证的里程碑 — 一个可提交和运行的应用程序/服务/解决方案，以及允许评审者根据该阶段列出的标准对其进行判断的测试或其他验证工件？
     - 每个阶段的 `Reviewer model:` 是否适当 — 从未低于该阶段使用的最高实施层级，除非阶段较小、统一和机械？
     - 阶段大小是否合理 — 每个阶段一步（评审波动），步骤数量不多以至于评审者的发现迫使重写整个阶段？当没有更早点提供可工作、可验证状态时，整个任务只有一个阶段是可接受的。
     - 每个检查表项和 `## 验收标准` 中的每个评分标准是否至少出现在一个阶段，并且每个阶段仅列出在该检查点真正应出现的标准而不是任务结束标准？
     - 任务文件是否免费于阈值值、分数和评审配置，这些属于编排器？
     - 1=阶段是任意切割或留下破损状态，2=里程碑部分保持或评审层级错误，3=可接受，4=设计良好的里程碑，评审层级合理，5=每个阶段都是一个干净、自包含、正确评审的里程碑
  ```

关键：**必须按提示使用，不要添加任何其他内容。包括实现代理的输出！！！**

## 推广任务

**目的：** 将精炼的任务从草稿文件夹移动到待办文件夹。这是一个您自己执行的文件移动 — 没有子代理，没有模型层级，没有判定。

所有阶段完成后：

1. **将任务文件从草稿移动到待办：**

   ```bash
   git mv <TASK_FILE> .specs/tasks/todo/
   # 如果 git 不可用：mv <TASK_FILE> .specs/tasks/todo/
   ```

2. **不要移动 `.specs/sub-tasks/<task-name>/`。** 子任务文件夹在规划时间创建，并在任务文件从 `草稿/` → `待办/` → `进行中/` → `完成/` 移动时保持不变，因此并行化概述中记录的路径永远不会过时。

3. **如有必要，更新任何参考** 在研究和分析文件中

## 错误处理

### 阶段代理失败 (异常/崩溃)

如果任何阶段代理意外失败:

1. 报告失败并附带代理输出
2. 向用户提出澄清问题以帮助解决问题
3. 使用问题和答案列表重新启动阶段代理以解决问题

### 评审员返回 FAIL

如果任何评审员返回 FAIL (分数 < `THRESHOLD`):

0. **首先应用 [迭代自由裁量规则](#iteration-discretion-rule)**: 如果 `分数 < 3.0` (或 `STRICT_MODE` 为 true), 总是重试。如果 `max(3.0, THRESHOLD - 1.0) <= 分数 < THRESHOLD` 且仅剩突出问题, 故意决定是否值得重试 — 如果您接受, 标记阶段 ☑️ 接受, 在摘要中列出其突出问题, 并进入下一阶段而不是步骤 1-4; 否则继续步骤 1
1. **自动重试**: 使用评审员反馈重新启动阶段代理, 按照决定 [升级规则](#escalation-rule) 的层级 — 它全面管理, 包括其唯一的例外情况和 `--model` 例外。重试特定锚点在其之上: 触发 (1) 锚定在此处 `分数 < 3.0` (或显示模型误解了阶段的评审员问题); 在重新启动的阶段相同层级重新评审; 在阶段摘要中说明层级决定
2. **人工检查点**: 如果阶段在 `HUMAN_IN_THE_LOOP_PHASES` 中, 在下一个评审员重试之前触发人工检查点 (在实施重试之后但在重新评审之前)
3. **达到 `MAX_ITERATIONS`**: **自动进入下一阶段** (除非 `--human-in-the-loop` 包括此阶段, 否则不要询问用户)
4. 在完成摘要中记录警告: `⚠️ 阶段 X 在 MAX_ITERATIONS 迭代后未通过质量阈值 (X.X/THRESHOLD)`

### 重试流程

```
实施 → 评审员 FAIL → 实施重试 → 评审员重试
                                                    ↓
          通过 → 继续进入下一阶段
          FAIL → 重复直到 MAX_ITERATIONS
                  ↓
          MAX_ITERATIONS 达到 → 进入下一阶段 (带警告)
```

### 带人工检查点重试流程

当阶段在 `HUMAN_IN_THE_LOOP_PHASES` 中:

```
实施 → 评审员 FAIL → 实施重试
                                    ↓
                🔍 人工检查点 (可选反馈)
                                    ↓
                              评审员重试
                                    ↓
                通过 → 继续 | FAIL → 重复直到 MAX_ITERATIONS
                                      ↓
                MAX_ITERATIONS → 🔍 最终人工检查点
                                      ↓
                        用户确认 → 进入下一阶段
```
