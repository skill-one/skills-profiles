# 上下文工程基础

上下文是指语言模型在推理时可用的完整状态。它包括模型在生成响应时可以关注的一切：系统指令、工具定义、检索到的文档、消息历史和工具输出。理解上下文基础知识是有效上下文工程的前提。

## 核心概念

上下文由几个不同的组件组成，每个组件具有不同的特性和约束。注意力机制创建了一个有限的预算，限制了有效上下文的使用。渐进式披露通过按需加载信息来管理这种约束。工程学科是策划实现预期结果的最小高信号标记集。

## 详细主题

### 上下文的解剖结构

**系统提示**
系统提示建立代理的核心身份、约束和行为指南。它们在会话开始时加载一次，并且通常在整个对话期间持续存在。系统提示应极其清晰，并使用简单直接的语言，在正确的“高度”为代理提供指导。

正确的“高度”平衡了两种故障模式。在一极，工程师硬编码复杂易碎的逻辑，这会创造脆弱性和维护负担。在另一极，工程师提供模糊的高级指导，未能给出预期输出的具体信号或错误地假设共享上下文。最佳“高度”在有效指导行为的同时，又足够灵活以提供强大的启发式方法。

使用 XML 标签或 Markdown 标题将提示组织成不同的部分，以区分背景信息、指令、工具指导和输出描述。随着模型变得越来越强大，确切的格式不太重要，但结构清晰仍然很有价值。

**工具定义**
工具定义指定代理可以采取的操作。每个工具都包括名称、描述、参数和返回格式。工具定义在序列化后靠近上下文的开始处，通常在系统提示之前或之后。

工具描述共同引导代理行为。糟糕的描述迫使代理猜测；优化的描述包括使用上下文、示例和默认值。合并原则指出，如果人类工程师无法明确地说出在特定情况下应该使用哪个工具，那么代理也不太可能做得更好。

**检索到的文档**
检索到的文档提供特定领域的知识、参考材料或与任务相关的信息。代理使用检索增强生成将相关文档在运行时拉入上下文，而不是预先加载所有可能的信息。

“即时”方法维护轻量级标识符（文件路径、存储查询、网络链接），并使用这些引用动态地将数据加载到上下文中。这反映了人类认知：我们通常不会记忆整个语料库的信息，而是使用外部组织和索引系统按需检索相关信息。

**消息历史**
消息历史包含用户和代理之间的对话，包括以前的查询、响应和推理。对于长时间运行的任务，消息历史可能会增长到主导上下文使用。

消息历史作为便笺内存，代理可以跟踪进度、维护任务状态并在回合之间保留推理。有效管理消息历史对于长时间跨度的任务完成至关重要。

**工具输出**
工具输出是代理操作的結果：文件内容、搜索结果、命令执行输出、API 响应和类似数据。工具输出通常占典型代理轨迹中标记的大部分，研究显示观察结果（工具输出）可达到总上下文使用的 83.9%。

无论工具输出是否与当前决策相关，都会消耗上下文。这为观察掩码、压缩和选择性工具结果保留等策略创造了压力。

### 上下文窗口和注意力机制

**注意力预算约束**
语言模型通过注意力机制处理标记，在上下文中的所有标记之间创建成对关系。对于 n 个标记，这会创建 n^2 个关系必须被计算和存储。随着上下文长度的增加，模型捕获这些关系的能力变得很薄。

模型从以较短的序列为主的训练数据分布中发展注意力模式。这意味着模型在处理上下文范围依赖关系方面经验不足，参数较少。结果是“注意力预算”，随着上下文的增长而消耗。

**位置编码和上下文扩展**
位置编码插值允许模型处理更长的序列，通过调整它们以适应原来训练的较小上下文。然而，这种调整引入了标记位置理解的退化。模型在较长的上下文中仍然高度 capable，但与在较短的上下文中的性能相比，信息检索和长距离推理的精度有所降低。

**渐进式披露原则**
渐进式披露通过按需加载信息来有效管理上下文。在启动时，代理仅加载技能名称和描述——足够知道技能何时可能相关。仅在技能被激活以执行特定任务时才加载完整内容。

这种方法使代理保持快速，同时按需提供更多上下文。该原则适用于多个级别：技能选择、文档加载，甚至工具结果检索。

### 上下文质量与上下文数量

假设更大的上下文窗口解决了内存问题已被经验证地推翻。上下文工程意味着找到能够最大化预期结果的最小高信号标记集。

几个因素造成了上下文效率的压力。处理成本随上下文长度不成比例地增长——不仅仅是双倍的标记成本翻倍，但在时间和计算资源方面呈指数增长。即使技术支持更多标记，模型性能也会在某些上下文长度之外下降，即使技术窗口在技术上支持更多标记。

指导原则是信息量而不是详尽无遗。包括对当前决策有意义的，排除对决策无关的，并设计能够按需访问额外信息的系统。

### 上下文作为有限资源

上下文必须被视为具有递减边际收益的有限资源。像具有有限工作内存的人类一样，语言模型有一个注意力预算，在解析大量上下文时使用。

每个引入的新标记都会以某种程度消耗这个预算。这创造了仔细策划可用标记的需求。工程问题是在固有约束下优化效用。

上下文工程是迭代的，策划阶段发生在每次你决定将内容传递给模型时。它不是一个一次性的提示编写练习，而是一个持续的上下文管理学科。

## 实用指南

### 基于文件系统的访问

具有文件系统访问权限的代理可以自然地使用渐进式披露。将参考材料、文档和数据存储在外部。仅在需要时使用标准文件系统操作加载文件。这种模式避免了将信息填充到上下文中，这些信息可能不相关。

文件系统本身提供了代理可以导航的结构。文件大小暗示了复杂性；命名约定暗示了目的；时间戳作为相关性的代理。文件引用的元数据提供了有效细化行为的一种机制。

### 混合策略

最有效的代理采用混合策略。预加载一些上下文以加快速度（如 CLAUDE.md 文件或项目规则），但启用自主探索以按需加载额外的上下文。决策边界取决于任务特征和上下文动态。

对于内容动态性较低的上下文，预先加载更多内容是有意义的。对于快速变化或高度特定的信息，即时加载可以避免陈旧的上下文。

### 上下文预算

设计时考虑明确的上下文预算。了解您的模型和任务的实际上下文限制。开发过程中监控上下文使用情况。在适当的阈值处实施压缩触发器。设计系统，假设上下文会退化，而不是希望它不会退化。

有效的上下文预算管理需要理解不仅只是原始标记计数，还包括注意力分布模式。上下文的中部比开始和结束部分接收到的注意力要少。将关键信息放置在注意力偏好的位置。

## 示例

**示例 1：组织系统提示**
```markdown
<背景信息>
你是一位帮助开发团队的 Python 专家。
当前项目：用 Python 3.9+ 进行数据处理管道。
</背景信息>

<指令>
- 编写干净的、符合 idiomatic 的 Python 代码
- 为函数签名包含类型提示
- 为公共函数添加文档字符串
- 遵循 PEP 8 代码风格指南
</指令>

<工具指导>
使用 bash 执行 shell 操作，使用 python 执行代码任务。
文件操作应使用 pathlib 以跨平台兼容性为目标。
</工具指导>

<输出描述>
提供可操作的反馈，并包含具体的行引用。
解释建议背后的推理。
</输出描述>
```

**示例 2：渐进式文档加载**
```markdown
# 不需要一次加载所有文档：

# 第 1 步：加载摘要
docs/architecture_overview.md     # 轻量级概述

# 第 2 步：按需加载特定部分
docs/api/endpoints.md             # 仅当需要 API 工作时
docs/database/schemas.md          # 仅当需要数据层工作时
```

**示例 3：技能描述设计**
```markdown
# 糟糕：模糊的描述，加载到上下文中但提供的信号很少
description: 帮助处理代码事物

# 好：特定的描述，有助于模型决定何时激活
description: 分析代码质量并建议重构模式。在审查拉取请求或改进现有代码结构时使用。
```

## 指南

1. 将上下文视为具有递减边际收益的有限资源
2. 将关键信息放置在注意力偏好的位置（开始和结束）
3. 使用渐进式披露将加载推迟到需要时
4. 使用清晰的部分边界组织系统提示
5. 开发过程中监控上下文使用情况
6. 在 70-80% 利用率处实施压缩触发器
7. 设计以上下文退化而不是希望避免退化
8. 优先选择较小的信号上下文而不是较大的低信号上下文

# 上下文退化模式

语言模型在上下文长度增加时表现出可预测的退化模式。理解这些模式对于诊断故障和设计弹性系统至关重要。上下文退化不是二进制状态，而是一系列性能退化的连续体，以几种不同的方式表现出来。

## 核心概念

上下文退化通过几种不同的模式表现出来。丢失在中间的现象导致上下文中心的信息接收到的注意力减少。上下文中毒发生在错误通过重复引用而累积时。上下文干扰发生在不相关信息淹没相关内容时。上下文混淆发生在模型无法确定哪个上下文适用时。上下文冲突发生在累积信息直接冲突时。

这些模式是可预测的，可以通过架构模式（如压缩、掩码、分区和隔离）来缓解。

## 详细主题

### 丢失在中间的现象

最 well-documented 的退化模式是“丢失在中间”效应，模型表现出 U 形注意力曲线。上下文开始和结束处的信息接收到的注意力是可靠的，而埋在中间的信息遭受召回精度显著降低。

**经验证据**
研究表明，放置在上下文中间的相关信息与放置在开始或结束处的相同信息相比，召回精度降低了 10-40%。这不是模型的失败，而是注意力机制和训练数据分布的后果。

模型将大量注意力分配给第一个标记（通常是 BOS 标记）以稳定内部状态。这创建了一个“注意力汇点”，吸收了注意力预算。随着上下文的增长，有限的预算被拉伸得更薄，中间的标记无法获得足够的注意力权重以可靠地检索。

**实际影响**
设计上下文放置时，请考虑注意力模式。将关键信息放置在上下文的开始或结束处。考虑信息将直接查询还是需要支持推理——如果是后者，放置位置不太重要，但整体信号质量更重要。

对于长文档或对话，使用摘要结构将关键信息置于注意力偏好的位置。使用显式部分标题和过渡帮助模型导航结构。

### 上下文中毒

上下文中毒发生在幻觉、错误或错误信息进入上下文并通过重复引用而累积时。一旦中毒，上下文就会创建反馈循环，强化错误的信念。

**中毒如何发生**
中毒通常通过三种途径进入。首先，工具输出可能包含错误或意外的格式，模型将其接受为事实。其次，检索到的文档可能包含错误或过时的信息，模型将其纳入推理。第三，模型生成的摘要或中间输出可能引入幻觉，这些幻觉在上下文中持续存在。

累积效应非常严重。如果代理的 goals 部分被中毒，它就会发展出需要大量工作才能撤销的策略。每个后续决策都引用中毒内容，强化错误的假设。

**检测和恢复**
注意以下症状，包括在之前成功的任务上输出质量下降，工具错配（代理调用错误的工具或参数），以及尽管纠正尝试，但持续存在的幻觉。当出现这些症状时，请考虑上下文中毒。

恢复需要删除或替换中毒内容。这可能涉及截断上下文到中毒点之前，在上下文中明确指出中毒并要求重新评估，或者使用干净的上下文重新启动并仅保留已验证的信息。

### 上下文干扰

上下文干扰在上下文变得太长时会出现，模型过度关注提供的上下文，而忽略其训练知识。模型通过注意力机制处理标记，创建上下文中所有标记之间的成对关系。对于 n 个标记，这会创建 n^2 个关系必须被计算和存储。随着上下文长度的增加，模型捕获这些关系的能力变得很薄。

模型从以较短的序列为主的训练数据分布中发展注意力模式。这意味着模型在处理上下文范围依赖关系方面经验不足，参数较少。结果是“注意力预算”，随着上下文的增长而消耗。

**干扰效应**
研究表明，即使一个不相关的文档在上下文中，也会降低涉及相关文档的任务的性能。多个干扰因素会累积退化。效应不是关于噪声的绝对值，而是关于注意力分配——不相关信息与相关信息竞争有限的注意力预算。

模型没有“跳过”不相关上下文的机制。它们必须关注提供的所有内容，这会产生干扰，即使不相关信息明显不是有用的。

**缓解策略**
通过仔细策划进入上下文的内容来缓解干扰。在加载检索到的文档之前应用相关性过滤。使用命名空间和组织结构，使不相关的部分在结构上容易忽略。考虑信息是否真的需要进入上下文，或者是否可以通过工具调用来访问。

### 上下文混淆

上下文混淆发生在不相关信息以方式降低质量的方式影响响应时。这与干扰有关，但不同之处在于混淆涉及上下文对模型行为的影响，而不是注意力分配。

如果你将某些内容放入上下文，模型必须关注它。模型可能将不相关信息纳入推理，使用不适当的工具定义，或应用来自不同上下文的约束。混淆在包含多个任务或在同一会话内切换任务时尤其有问题。

**混淆的迹象**
注意响应错误地处理了查询的各个方面，工具调用似乎适用于不同的任务，或输出混合来自多个来源的要求。这表明对当前情况适用的上下文感到困惑。

**架构解决方案**
架构解决方案包括显式任务分割，不同的任务具有不同的上下文窗口，清晰的任务上下文过渡，以及隔离不同目标的上下文的状态管理。

### 上下文冲突

上下文冲突发生在累积信息直接冲突时，导致推理的矛盾指导。这与中毒不同，在冲突中，多个正确的信息直接冲突。

**冲突来源**
冲突通常由多源检索引起，其中不同的来源包含矛盾的信息，版本冲突导致过时的和当前的信息都出现在上下文中，以及视角冲突，其中不同的观点是有效的但不可兼容的。

**解决方案方法**
解决方案包括显式冲突标记，识别矛盾并请求澄清，优先规则，确定哪个来源优先，以及版本过滤，从上下文中排除过时的信息。

### 反直觉的发现

研究表明，有几个反直觉的模式挑战了上下文管理的假设。

**打乱的干草堆比连贯的干草堆表现更好**
研究发现，打乱（不连贯）的干草堆产生的性能优于逻辑连贯的干草堆。这表明连贯的上下文可能会产生虚假关联，使检索变得混乱，而混乱的上下文强制模型依赖精确匹配。

**单个干扰因素具有不成比例的影响**
即使一个不相关的文档也会显著降低性能。效应不是与噪声成正比，而是遵循阶跃函数，其中任何干扰因素都会触发退化。

**针尖问题相似性相关性**
针尖和问题对之间的相似性较低，上下文长度增加时退化更快。需要跨不相似内容进行推理的任务特别容易受到损害。

### 当更大的上下文窗口有害时

更大的上下文窗口并不总是提高性能。在许多情况下，更大的上下文窗口会产生新的问题，其好处被抵消了。

**性能退化曲线**
模型表现出随上下文长度非线性的退化。性能在阈值之前保持稳定，然后迅速下降。阈值因模型和任务复杂性而异。对于许多模型，即使上下文窗口支持更大的大小，有意义退化在 8,000-16,000 个标记左右开始。

**成本影响**
处理成本随上下文长度不成比例地增长。处理 400K 标记的上下文的成本不是 200K 的两倍——在时间和计算资源方面呈指数增长。对于许多应用程序，这使得大上下文处理在经济效益上是不切实际的。

**认知负荷隐喻**
即使有无限的上下文，要求单个模型在多个独立任务之间保持一致质量也会产生认知瓶颈。模型必须不断在项目之间切换上下文，维护比较框架，并确保风格一致性。这不是一个可以通过更多上下文解决的问题。

## 实用指南

### 优化决策框架

**何时优化**
- 随着对话的延长，响应质量下降
- 由于上下文过长，成本增加
- 随着对话长度增加，延迟增加

**应用什么**
- 工具输出占主导地位：观察掩码
- 检索到的文档占主导地位：摘要或分区
- 消息历史占主导地位：使用摘要进行压缩
- 多个组件：结合策略

### 应用于 Claude Code 提示的优化

**命令优化**
命令按需加载，因此重点关注保持单个命令的焦点：
```markdown
# 好的：具有清晰范围的专注命令
---
name: review-security
description: 审查代码中的安全漏洞
---
# 仅包含特定的安全审查指令

# 避免：试图做所有事情的过载命令
---
name: review-all
description: 审查代码中的所有内容
---
# 50 个不同的审查检查清单被塞在一起
```

**技能优化**
技能默认加载其描述，因此描述必须简洁：
```markdown
# 好的：简洁的描述
description: 分析代码架构。用于设计审查。

# 避免：浪费上下文预算的冗长描述
description: 该技能提供全面的代码架构分析
架构包括但不限于类层次结构、依赖图、耦合指标、内聚分析...
```

**子代理上下文设计**
在生成子代理时，提供专注的上下文：
```markdown
# 协调器提供的最小传递：
"审查身份验证模块中的安全问题。
以结构化格式返回发现结果。"

# 不应这样冗长的传递：
"我需要查看身份验证模块，它位于 src/auth/，包含几个文件，包括 login.ts、session.ts、tokens.ts... [500 个更多标记的上下文]"
```

## 指南

1. 优化之前测量——了解您当前的状态
2. 在可能的情况下，在掩码之前应用压缩
3. 设计以一致的提示为缓存稳定性而设计
4. 在上下文变得有问题之前进行分区
5. 监控优化效果随时间推移
6. 平衡标记节省与质量保留
7. 在生产规模上测试优化
8. 为边缘情况实现优雅的退化
