# 评估 Claude 代码代理的方法

评估代理系统需要不同于传统软件甚至标准语言模型应用的方法。代理会做出动态决策，在不同运行之间是非确定性的，并且通常没有单一的正确答案。有效的评估必须考虑到这些特点，同时提供可操作的反馈。一个强大的评估框架能够实现持续改进，捕获回归，并验证上下文工程选择是否实现了预期效果。

## 核心概念

代理评估需要以结果为导向的方法，考虑到非确定性和多个有效路径。多维评估标准可以捕捉各种质量方面：事实准确性、完整性、引用准确性、来源质量和工具效率。LLM 作为法官提供可扩展的评估，而人工评估可以捕捉边缘情况。

关键洞察在于代理可能会找到实现目标的不同路径——评估应该判断它们是否在遵循合理过程的同时实现了正确的结果。

**性能驱动因素：95% 的发现**
对 BrowseComp 评估（测试浏览代理定位难以找到的信息的能力）的研究发现，三个因素解释了 95% 的性能差异：

| 因素 | 解释的差异 | 含义 |
|------|-------------|-------|
| 令牌使用 | 80% | 令牌越多，性能越好 |
| 工具调用次数 | ~10% | 更多探索有助于 |
| 模型选择 | ~5% | 更好的模型可以倍增效率 |

Claude 代码开发的启示：

- **令牌预算很重要**：在现实的令牌限制下进行评估
- **模型升级胜过令牌增加**：升级模型比增加令牌预算提供更大的收益
- **多代理验证**：验证在具有单独上下文窗口的子代理之间分配工作的架构

## 评估挑战

### 非确定性和多个有效路径

代理可能会以完全不同的有效路径来达到目标。一个代理可能会搜索三个来源，而另一个可能会搜索十个。他们可能会使用不同的工具来找到相同的答案。传统的评估方法检查特定步骤，在这种情况下会失败。

**解决方案**：解决方案是结果而不是精确的执行路径。判断代理是否通过合理的流程实现了正确的结果。

### 上下文相关的失败

代理的失败通常以微妙的方式取决于上下文。代理可能在复杂查询中成功，但在简单查询中失败。它可能在某个工具集上运行良好，但在另一个工具集上失败。失败可能只在长时间交互后才会出现，此时上下文会累积。

**解决方案**：评估必须涵盖一系列复杂程度级别，并测试长时间交互，而不仅仅是孤立的查询。

### 复合质量维度

代理质量不是单一维度。它包括事实准确性、完整性、连贯性、工具效率和流程质量。代理可能在准确性方面得分很高，但在效率方面得分很低，反之亦然。

**解决方案**：评估标准必须捕捉多个维度，并根据用例适当加权。

## 评估标准设计

### 多维评估标准

有效的标准涵盖关键维度，并具有描述性级别：

**指令遵循**（权重：0.30）

- 优秀 (1.0)：所有指令都精确遵循
- 良好 (0.8)：轻微偏差不影响结果
- 可接受 (0.6)：主要指令遵循，次要指令遗漏
- 差 (0.3)：忽略重要指令
- 失败 (0.0)：根本性地误解了任务

**输出完整性**（权重：0.25）

- 优秀：所有请求的方面都彻底涵盖
- 良好：大多数方面涵盖，有轻微差距
- 可接受：关键方面涵盖，有些差距
- 差：主要方面缺失
- 失败：基本方面未解决

**工具效率**（权重：0.20）

- 优秀：最佳工具选择和最少的调用
- 良好：良好的工具选择，有轻微低效
- 可接受：适当的工具，有些冗余
- 差：使用错误的工具或过多的调用
- 失败：严重的工具误用或极多的调用

**推理质量**（权重：0.15）

- 优秀：整个推理清晰、逻辑
- 良好：通常合理的推理，有轻微差距
- 可接受：有基本的推理
- 差：推理不清晰或有缺陷
- 失败：没有明显的推理

**响应连贯性**（权重：0.10）

- 优秀：结构良好，易于理解
- 良好：通常连贯，有轻微问题
- 可接受：易于理解但可以更清晰
- 差：难以跟随
- 失败：不连贯

### 评分方法

将维度评估转换为数值分数（0.0 到 1.0），并使用适当的加权。计算加权总分。根据用例要求设置通过阈值（通常为一般用途 0.7，关键操作 0.85）。

提供清晰的任务描述、代理输出、真实情况（如果可用）、评估量表（带有级别描述），并请求结构化判断。

**思维链要求**：始终在分数之前提供理由。研究表明，这通过 15-25% 的可靠性提高了思维链提示。

### 人工评估

人工评估捕捉自动化遗漏的内容：

- 不寻常查询中的幻觉答案
- 微妙的上下文理解错误
- 自动评估遗漏的边缘情况
- 定性问题，如语气或方法

对于 Claude 代码开发，请要求用户：

- 手动检查代理输出以捕获边缘情况
- 系统地抽样复杂性级别
- 跟踪失败模式以指导提示改进

### 最终状态评估

对于生成工件（文件、配置、代码）的命令，评估最终输出而不是过程：

- 生成的代码是否工作？
- 配置是否有效？
- 输出是否满足要求？

## 测试集设计

**样本选择**
开发期间从小的样本开始。在代理开发早期，由于有丰富的低垂果实，变化的影响非常显著。小的测试集揭示了巨大的影响。

从真实使用模式中抽样。添加已知的边缘情况。确保覆盖不同复杂性级别。

**复杂性分层**
测试集应跨越复杂性级别：简单（单个工具调用），中等（多个工具调用），复杂（许多工具调用，显著的歧义），以及非常复杂（扩展交互，深度推理）。

## 上下文工程评估

### 测试提示变化

在迭代 Claude 代码提示时，系统地评估：

1. **基线**：在测试用例上运行当前提示
2. **变化**：在相同的用例上运行修改后的提示
3. **比较**：测量质量分数、令牌使用量、效率
4. **分析**：确定哪些变化改进了哪些维度

### 测试上下文策略

上下文工程选择应通过系统评估进行验证。在相同的测试集上运行具有不同上下文策略的代理。比较质量分数、令牌使用量和效率指标。

### 退化测试

通过在上下文大小不同的地方运行代理来测试上下文退化如何影响性能。识别性能悬崖，此时上下文成为问题。建立安全操作限制。

## 高级评估：LLM 作为法官

**关键洞察**：LLM 作为法官不是单一技术，而是一系列适用于不同评估上下文的方法。选择正确的方法和减轻已知偏差是这项技能的核心能力。

### 评估分类法

评估方法分为两类，具有不同的可靠性特征：

**直接评分**：单个 LLM 评估一个响应在定义的量表上。

- 适用于：客观标准（事实准确性、指令遵循、毒性）
- 可靠性：对于定义明确的标准，中等到高
- 失效模式：分数校准漂移，不一致的量表解释

**成对比较**：LLM 比较两个响应，选择更好的一个。

- 适用于：主观偏好（语气、风格、说服力）
- 可靠性：对于偏好高于直接评分
- 失效模式：位置偏差，长度偏差

MT-Bench 论文（Zheng 等人，2023 年）的研究表明，成对比较比直接评分在基于偏好的评估中实现了与人工法官更高的协议，而直接评分仍然适用于具有明确真实情况的客观标准。

### 偏见景观

LLM 法官表现出系统偏差，必须主动减轻：

**位置偏差**：在成对比较中，第一个位置的响应受到优待。缓解：使用交换位置的评估两次，使用多数投票或一致性检查。

**长度偏差**：无论质量如何，较长的响应都会被评分较高。缓解：明确提示忽略长度，长度归一化评分。

**自我增强偏差**：模型对其自己的输出评分较高。缓解：使用生成器和评估器使用不同的模型，或者承认限制。

**冗余偏差**：详细的解释即使不必要也会获得更高的分数。缓解：针对特定标准的评估标准，惩罚不相关的细节。

**权威偏差**：自信的语气无论准确性如何都会被评分较高。缓解：要求证据引用，事实核查层。

### 指标选择框架

根据评估任务结构选择指标：

| 任务类型 | 主要指标 | 次要指标 |
|-----------|----------|-----------|
| 二元分类（通过/失败） | 召回率、精确率、F1 | Cohen's κ |
| 顺序量表 (1-5 评分) | Spearman's ρ, Kendall's τ | 加权 Cohen's κ |
| 成对偏好 | 一致性率、位置一致性 | 置信度校准 |
| 多标签 | Macro-F1, Micro-F1 | 每个标签的精确率/召回率 |

关键洞察：绝对一致性比系统性的不一致模式更重要。一个与人类在特定标准上持续不一致的判断者比随机噪声更成问题。

## 评估指标参考

### 分类指标（通过/失败任务）

**精确率**：所有标记为通过的响应中，有多少比例真正通过？

- 使用时：错误阳性代价高昂

**召回率**：所有实际通过的响应中，有多少比例我们识别？

- 使用时：错误阴性代价高昂

**F1 分数**：精确率和召回率的调和平均值

- 使用时：平衡的单一数字摘要

### 一致性指标（与人工判断比较）

**Cohen's Kappa**：调整机会的一致性

>
> > 0.8：几乎完美的一致性
> > 0.6-0.8： substantial 一致性
> > 0.4-0.6： moderate 一致性
> > 0.4：公平到差的一致性

### 相关性指标（顺序分数）

**Spearman's Rank Correlation**：排名之间的相关性

>
> > 0.9：非常强的相关性
> > 0.7-0.9： strong 相关性
> > 0.5-0.7： moderate 相关性
> > 0.5： weak 相关性

### 好评估系统指标

| 指标 | 好 | 可接受 | 令人担忧 |
|------|----|--------|----------|
| Spearman's ρ | > 0.8 | 0.6-0.8 | < 0.6 |
| Cohen's Kappa | > 0.7 | 0.5-0.7 | < 0.5 |
| 位置一致性 | > 0.9 | 0.8-0.9 | < 0.8 |
| 长度-分数相关性 | < 0.2 | 0.2-0.4 | > 0.4 |

## 评估方法

### 直接评分实现

直接评分需要三个组件：清晰的标准、校准的量表和结构化输出格式。

**标准定义模式**：

```
标准：[名称]
描述：[这个标准衡量什么]
权重：[相对重要性，0-1]
```

**量表校准**：

- 1-3 量表：二元，包含中性选项，认知负荷最低
- 1-5 量表：标准的 Likert，粒度和可靠性之间的良好平衡
- 1-10 量表：高粒度，但校准更难，仅在使用详细评估标准时使用

**直接评分提示结构**：

```
你正在评估 Claude Code 命令的输出。

## 原始任务
{任务描述}

## 命令输出
{命令输出}

## 评估标准
{每个标准：名称、描述、权重}

## 指令
对于每个标准：
1. 在响应中找到具体证据
2. 根据量表评分 (1-{最大} 量表)
3. 用证据证明你的分数
4. 建议一个具体的改进

**重要提示**：在分数之前提供理由。研究表明，这通过 15-25% 的可靠性提高了思维链提示。

### 成对比较实现

成对比较本质上更可靠，但需要减轻偏见。

**位置偏差缓解协议**：

1. 第一次通过（A 第一）：响应 A 在第一个位置，响应 B 在第二个位置
2. 第二次通过（B 第一）：响应 B 在第一个位置，响应 A 在第二个位置
3. 一致性检查：如果通过不一致，则返回 TIE 并降低置信度
4. 最终结论：一致的赢家，平均置信度

**成对比较提示结构**：

```
你正在比较来自不同提示变体的两个输出。

## 原始任务
{任务描述}

## 输出 A（第一个变体）
{来自提示变体 A 的输出}

## 输出 B（第二个变体）
{来自相同输出文本的输出}

## 比较标准
- 指令遵循
- 输出完整性
- 工具效率

## 关键指令
- 不要因为响应更长而偏好响应
- 不要因为位置（第一 vs 第二）而偏好响应
- 只关注质量差异
- 当响应真正等价时，接受 TIE

## 分析过程
1. 独立分析输出 A：[优点，缺点]
2. 独立分析输出 B：[优点，缺点]
3. 在每个标准上比较
4. 确定赢家并给出置信度 (0-1)

## 输出
推理：[解释为什么]
赢家：[A/B/TIE]
置信度：[0.0-1.0]
```

**置信度校准**：置信度分数应校准到实际可靠性：

### 置信度因素

| 因素 | 高置信度 | 低置信度 |
|------|----------|----------|
| 位置一致性 | 两个通过都同意 | 通过不一致 |
| 证据数量 | 3+ 具体引用 | 模糊或无引用 |
| 标准一致性 | 所有标准一致 | 标准分数差异很大 |
| 边缘情况匹配 | 与已知情况相似 | 新情况 |

### 校准提示添加

将此添加到评估提示中：

```markdown
## 置信度评估

评分后，评估你的置信度：

1. **证据强度**：你引用的证据有多具体？
   - 强：引用精确的段落，精确的观察
   - 中等：一般观察，合理的推断
   - 弱：模糊的印象，假设

2. **标准清晰度**：标准的界限有多清晰？
   - 清晰：容易将输出映射到评估标准
   - 模糊：输出落在级别之间
   - 不清楚：标准不适合这个案例

3. **整体置信度**：[0.0-1.0]
   - 0.9+: 非常自信，清晰的证据，明显的评估匹配
   - 0.7-0.9: 自信，良好的证据，轻微的模糊性
   - 0.5-0.7: 中等置信度，一些模糊性
   - <0.5: 低置信度，显著的不确定性

置信度：[分数]
置信度理由：[解释哪些因素影响了置信度]
```

## 评估工作流程

### 工作流程：测试新命令

1. **编写 5-10 个测试用例**，涵盖复杂性级别
2. **在每个测试用例上运行命令**，捕获完整输出
3. **快速筛选**所有输出使用 Tier 1 评估
4. **详细评估**失败和边缘情况
5. **识别模式**在失败中，以指导提示改进
6. **迭代提示**基于发现的特定弱点
7. **重新评估**相同的测试用例以衡量改进

### 工作流程：比较提示变体

1. **创建变体提示**（例如，不同的指令短语）
2. **运行两个变体**在相同的测试用例上
3. **成对比较**使用位置交换
4. **计算每个变体的胜率**
5. **分析**每个变体在哪些情况下表现更好
6. **决定**选择赢家或创建混合体

### 工作流程：回归测试

1. **维护测试套件**代表案例
2. **更改前**：运行评估，记录基线分数
3. **更改后**：重新运行评估
4. **比较**：标记回归（分数下降 > 0.5）
5. **调查**为什么特定案例回归？
6. **接受或还原**基于整体影响

### 工作流程：持续质量监控

1. **抽样生产使用**（如果可用）
2. **对样本运行轻量级评估**
3. **跟踪指标随时间变化**：
   - 每个标准的平均分数
   - 失败率
   - 低置信度率
4. **退化警告**：分数从基线下降 > 10%
5. **定期深度分析**：每月对随机样本进行详细评估

## 应避免的反模式

### ❌ 没有理由的评分
**问题**：分数缺乏依据，难以调试
**解决方案**：始终要求在分数之前提供证据

### ❌ 单次通过成对比较
**问题**：位置偏差破坏了结果
**解决方案**：始终交换位置并检查一致性

### ❌ 过载的标准
**问题**：测量多个事物的标准是不可靠的
**解决方案**：一个标准 = 一个可衡量的方面

### ❌ 缺少边缘情况指导
**问题**：评估者在模糊情况下处理不一致
**解决方案**：在标准中包含边缘情况，提供明确的指导

### ❌ 忽略低置信度
**问题**：对不确定的评估采取行动会导致错误结论
**解决方案**：将低置信度案例升级为人工审查

### ❌ 通用标准
**问题**：通用标准产生模糊、无用的评估
**解决方案**：创建特定于领域的标准（代码命令 vs 文档命令 vs 分析命令）

## 处理评估失败

当评估失败或产生不可靠的结果时，使用这些恢复策略：

### 无格式输出忽略

当评估器产生无法解析或不完整的输出时：

1. **标记为无效并忽略分析** - 错误输出，通常表示思考过程中的幻觉

2. **在没有更改的情况下重试初始提示** - 多次重试通常比单次提示更一致
3. **如果仍然产生错误输出，则标记为人工审查**：标记为“评估失败，需要人工检查”并排队以供后续处理

### 验证检查表

在信任评估结果之前，验证：

- [ ] 所有标准都在有效范围内（1-5）
- [ ] 每个分数都有引用具体证据
- [ ] 提供了置信度分数且合理
- [ ] 理由和分配的分数之间没有矛盾
- [ ] 加权总分计算正确

## 验证评估提示（元评估）

在使用评估提示生产之前，将其与已知案例测试：

### 校准测试用例

创建一小组具有已知质量级别的输出：

| 测试类型 | 描述 | 预期分数 |
|-----------|-------------|----------------|
| 已知良好 | 明显优秀的输出 | 4.5+ / 5.0 |
| 已知不良 | 明显差的输出 | < 2.5 / 5.0 |
| 边缘情况 | 边缘案例 | 3.0-3.5，具有细致的解释 |

### 验证工作流程

1. **已知良好测试**：评估一个明显优秀的输出
   - 如果分数 < 4.0 → 标准过于严格或证据要求不明确

2. **已知不良测试**：评估一个明显差的输出
   - 如果分数 > 3.0 → 标准过于宽松或标准不明确

3. **边缘测试**：评估一个边缘案例
   - 应产生中等分数 (3.0-3.5) 并具有详细的解释
   - 如果自信高分/低分 → 标准缺乏细微差别

4. **一致性测试**：运行相同评估 3 次
   - 分数方差应 < 0.5
   - 如果方差较高 → 标准需要更清晰的定义

### 位置偏差验证

在使用成对比较之前测试位置偏差：

```markdown
## 位置偏差测试

使用相同的测试用例在两个位置运行：

Test Case: [相同的输出文本]
位置 A: [粘贴输出]
位置 B: [粘贴相同的输出]

预期结果：TIE with high confidence (>0.9)

如果结果显示赢家：
- 位置偏差检测到
- 添加更强的反偏见指令到提示
- 一致地重新测试以获得 TIE
```

### 评估提示迭代

当校准测试失败：

1. **识别失败模式**：过于严格？过于宽松？不一致？
2. **调整特定标准级别**：添加示例，澄清界限
3. **重新运行校准测试**：所有 4 个测试都必须通过
4. **记录更改**：跟踪改进了可靠性的更改

# 指标选择指南

## 指标类别

### 分类指标

用于二元或多元分类评估任务（通过/失败，正确/错误）。

#### 精确率

```
Precision = True Positives / (True Positives + False Positives)
```

**解释**：所有法官说好的响应中，有多少比例真正好？

**使用时**：错误阳性代价高昂

#### 召回率

```
Recall = True Positives / (True Positives + False Negatives)
```

**解释**：所有实际好的响应中，有多少比例我们识别？

**使用时**：错误阴性代价高昂

#### F1 分数

```
F1 = 2 * (Precision * Recall) / (Precision + Recall)
```

**解释**：精确率和召回率的调和平均值

**使用时**：平衡的单一数字摘要

### 一致性指标

用于比较自动化评估与人工判断。

#### Cohen's Kappa (κ)

```
κ = (Observed Agreement - Expected Agreement) / (1 - Expected Agreement)
```

**解释**：调整机会的一致性
>
> > 0.8：几乎完美的一致性
> > 0.6-0.8： substantial 一致性
> > 0.4-0.6： moderate 一致性
> > 0.4：公平到差的一致性

### 相关性指标

用于顺序/连续分数。

#### Spearman's Rank Correlation (ρ)

**解释**：排名之间的相关性
>
> > 0.9：非常强的相关性
> > 0.7-0.9： strong 相关性
> > 0.5-0.7： moderate 相关性
> > 0.5： weak 相关性

**使用时**：顺序比绝对值更重要

#### Kendall's Tau (τ)

**解释**：与 Spearman 类似，基于成对一致性

**使用时**：您有大量 tied 值

#### Pearson Correlation (r)

**解释**：线性相关性

**使用时**：分数的绝对值很重要，而不仅仅是顺序

### 成对比较指标

#### 一致性率

```
Agreement = (Matching Decisions) / (Total Comparisons)
```

**解释**：简单的百分比同意

#### 位置一致性

```
Consistency = (Consistent across position swaps) / (Total comparisons)
```

**解释**：交换位置改变决策有多频繁？

## 指标选择按用例

### 用例 1：验证自动评估

**目标**：确保自动化评估与人工判断相关

**推荐指标**：
1. 主要：Spearman's ρ（用于顺序量表）或 Cohen's κ（用于分类）
2. 次要：每个标准的一致性
3. 诊断：混淆矩阵以发现系统性错误

### 用例 2：比较两个模型

**目标**：确定哪个模型产生更好的输出

**推荐指标**：
1. 主要：成对比较的胜率
2. 次要：位置一致性（偏差检查）
3. 诊断：每个标准的分数分解

### 用例 3：质量监控

**目标**：跟踪评估质量随时间变化

**推荐指标**：
1. 主要：与人类的一致性（滚动一致性，人工抽样检查）
2. 次要：分数分布稳定性
3. 诊断：偏差指标（位置，长度）

## 解释指标结果

### 好评估系统指标

| 指标 | 好 | 可接受 | 令人担忧 |
|------|----|--------|----------|
| Spearman's ρ | > 0.8 | 0.6-0.8 | < 0.6 |
| Cohen's κ | > 0.7 | 0.5-0.7 | < 0.5 |
| 位置一致性 | > 0.9 | 0.8-0.9 | < 0.8 |
| 长度-分数相关性 | < 0.2 | 0.2-0.4 | > 0.4 |

### 警示信号

1. **高一致性但低相关性**：可能表示校准问题
2. **低位置一致性**：位置偏差影响结果
3. **高长度相关性**：长度偏差使分数膨胀
4. **每个标准的方差**：某些标准可能定义不佳
