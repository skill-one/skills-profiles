# judge-with-debate

<任务>
通过多智能体辩论评估解决方案，其中独立的评委分析、相互挑战彼此的评估，并迭代地完善他们的评价，直到达成共识或达到最大轮次。
</任务>

<上下文>
该命令实现了多智能体辩论模式，用于高质量的评估，其中多个视角和严格的论证提高了评估的准确性。与单次评估不同，辩论迫使评委用证据来捍卫他们的立场，并考虑反方论点。

主要优势：

- **结构化评估** - 元评委在评估开始前产生定制的评分标准和标准
- **多视角** - 三个独立的评委减少个人偏见
- **基于证据的辩论** - 评委用解决方案和评估规范中的具体证据来捍卫立场
- **迭代完善** - 最多3轮辩论推动准确分数的收敛
- **共享规范** - 元评委运行一次；所有评委在所有轮次中共享相同的评估规范
</上下文>

## 模式：基于辩论的评估

该命令实现了迭代的多评委辩论：

```
阶段 0：设置
         mkdir -p .specs/reports
                  |
阶段 0.5：派遣元评委
         元评委 (Opus)
              |
         评估规范 YAML
              |
阶段 1：独立分析 (3 个评委并行)
         +- 评委 1 -> {name}.1.md -+
解决方案 +- 评委 2 -> {name}.2.md -+-+
         +- 评委 3 -> {name}.3.md -+ |
                                      |
阶段 2：辩论轮 (迭代)     |
    每个评委阅读其他人的报告  |
         |                            |
    辩论 + 捍卫 + 挑战        |
    (基于评估规范)  |
         |                            |
    如果被说服则修订 --------------+
         |                            |
    检查共识                   |
         +- 是 -> 最终报告       |
         +- 否 -> 下一个轮 ---------+
```

## 流程

### 设置：创建报告目录

在开始评估之前，确保报告目录存在：

```bash
mkdir -p .specs/reports
```

**报告命名约定：** `.specs/reports/{solution-name}-{YYYY-MM-DD}.[1|2|3].md`

其中：

- `{solution-name}` - 从解决方案文件名派生（例如，`users-api` 从 `src/api/users.ts`）
- `{YYYY-MM-DD}` - 当前日期
- `[1|2|3]` - 评委编号

### 阶段 0.5：派遣元评委

在独立分析之前，派遣一个元评委代理来生成定制的评估规范。元评委运行一次，并产生所有评委在所有辩论轮次中都将使用的评分标准、检查清单和评分标准。

**元评委提示模板：**

```markdown
## 任务

为以下评估任务生成评估规范 YAML。您将产生评分标准、检查清单和评分标准，多个评委代理将使用它们通过独立分析和多轮辩论来评估解决方案。

CLAUDE_PLUGIN_ROOT=`${CLAUDE_PLUGIN_ROOT}`

## 用户提示
{任务描述 - 解决方案 supposed 要完成的任务}

## 上下文
{任何与被评估解决方案相关的上下文}

## 文件类型
{代码 | 文档 | 配置 | 等.}

## 评估模式
多评委辩论，在轮次中寻求共识

## 指示
仅返回最终评估规范 YAML 在您的响应中。
规范应支持独立分析和基于辩论的完善。
```

**派遣：**

```
使用任务工具：
  - 描述: "元评委: 为 {solution-name} 生成评估规范"
  - 提示: {元评委提示}
  - 模型: opus
  - subagent_type: "sadd:meta-judge"
```

等待元评委完成，并从其输出中提取评估规范 YAML，然后继续阶段 1。

### 阶段 1：独立分析

启动 **3 个独立评委代理并行**（Opus 用于严谨性）：

1. 每个评委接收：
   - 路径到被评估的解决方案
   - 元评委的评估规范 YAML
   - 任务描述
2. 每个产生 **独立评估** 并保存到 `.specs/reports/{solution-name}-{date}.[1|2|3].md`
3. 报告必须包括：
   - 每个标准的分数和证据
   - 支持评分的特定引用/示例
   - 总体加权分数
   - 主要的强项和弱点

**主要原则：** 初始分析的独立性防止群体思维。

**提示模板用于初始评委：**

```markdown
您是评委 {N}，独立地根据元评委产生的评估规范评估解决方案。

CLAUDE_PLUGIN_ROOT=`${CLAUDE_PLUGIN_ROOT}`

## 解决方案
{解决方案文件的路径}

## 任务描述
{解决方案 supposed 要完成的任务}

## 评估规范

```yaml
{元评委的评估规范 YAML}
```

## 输出文件
.specs/reports/{solution-name}-{date}.{N}.md

## 指示

遵循您在代理指示中定义的完整评委过程！

附加指示：
1. 彻底阅读解决方案
2. 对于评估规范中的每个标准：
   - 找到具体证据（引用确切文本）
   - 在定义的量表上评分
   - 用具体的示例进行辩护
3. 计算加权总体分数
4. 写入全面的报告到 {output_file}

添加到报告开头 `Done by Judge {N}`
```

**派遣每个评委：**

```
使用任务工具：
  - 描述: "评委 {N}: {solution-name} 的独立分析"
  - 提示: {带有评估规范 YAML 的评委提示}
  - 模型: opus
  - subagent_type: "sadd:judge"
```

### 阶段 2：辩论轮 (迭代)

对于每轮辩论（最多 3 轮）：

启动 **3 个辩论代理并行**：

1. 每个评委代理接收：
   - 他们自己的先前报告路径 (`.specs/reports/{solution-name}-{date}.[1|2|3].md`)
   - 其他评委报告的路径 (`.specs/reports/{solution-name}-{date}.[1|2|3].md`)
   - 原始解决方案
   - 元评委的评估规范 YAML
2. 每个评委：
   - 识别与其他评委的分歧（在任何标准上分数差距大于 1 分）
   - 用解决方案和评估规范中的证据捍卫自己的评分
   - 挑战他们不同意其他评委的评分
   - 考虑反方论点
   - 如果被说服则修订他们的评估
3. 更新他们的报告文件，添加新部分：`## 辩论轮 {R}`
4. 在他们回复后，如果他们达成共识，则进入阶段 3：共识报告

**主要原则：** 评委仅通过文件系统通信 - 总管不调解，也不自己读取报告文件，这可能导致上下文溢出。

**辩论评委的提示模板：**

```markdown
您是辩论轮 {R} 中的评委 {N}。

CLAUDE_PLUGIN_ROOT=`${CLAUDE_PLUGIN_ROOT}`

## 您的先前报告
{路径到 .specs/reports/{solution-name}-{date}.{N}.md}

## 其他评委的报告
评委 1: .specs/reports/{solution-name}-{date}.1.md
...

## 任务描述
{解决方案 supposed 要完成的任务}

## 解决方案
{解决方案的路径}

## 评估规范

```yaml
{元评委的评估规范 YAML}
```

## 输出文件
.specs/reports/{solution-name}-{date}.{N}.md (追加到现有文件)

## 指示

遵循您在代理指示中定义的完整评委过程！

附加辩论指示：
1. 阅读您的先前评估 {your_previous_report}
2. 阅读所有其他评委的报告
3. 识别分歧（您的分数与其他评委的分数差距大于 1 分）
4. 对于每个主要分歧：
   - 清晰地陈述分歧
   - 用解决方案和评估规范中的证据捍卫您的立场
   - 用反方证据挑战其他评委的立场
   - 考虑他们的证据是否改变了您的看法
5. 通过追加辩论轮部分来更新您的报告文件
6. 回复您是否达成共识，以及与哪个评委达成共识。包括重新评估的分数和标准分数。

关键：
- 基于评估规范标准进行论证
- 只有在找到他们证据有说服力时才修订
- 如果您仍然相信它们，请捍卫您的原始分数
- 引用解决方案中的具体证据
```

**派遣每个辩论评委：**

```
使用任务工具：
  - 描述: "评委 {N}: {solution-name} 的辩论轮 {R}"
  - 提示: {带有评估规范 YAML 的辩论评委提示}
  - 模型: opus
  - subagent_type: "sadd:judge"
```

### 共识检查

每轮辩论后检查共识：

**如果达成共识：**
- 所有评委的总体分数彼此相差 0.5 分以内
- 没有任何标准在任何两个评委之间存在大于 1 分的分歧
- 所有评委明确表示他们接受共识

**如果在 3 轮后没有共识：**
- 报告持续的分歧
- 提供所有评委报告供人工审查
- 标记自动评估无法达成共识

**总管指示：**

**步骤 1：派遣元评委（阶段 0.5）**

1. 启动元评委代理
2. 等待元评委完成
3. 从元评委输出中提取评估规范 YAML

**步骤 2：运行独立分析（阶段 1）**

1. 并行启动 3 个评委代理（评委 1、2、3）以及评估规范 YAML
2. 每个将他们的独立评估写入 `.specs/reports/{solution-name}-{date}.[1|2|3].md`
3. 等待所有 3 个代理完成

**步骤 3：检查共识**

让我们系统地处理这个问题，以确保准确检测共识。

读取所有三个报告并提取：
- 每个评委的总体加权分数
- 每个评委的每个标准的分数

逐步检查共识：
1. 首先，从每个报告中提取所有总体分数并明确列出
2. 计算最高分和最低分之间的差异
   - 如果差异 <= 0.5 分 -> 总体共识达成
   - 如果差异 > 0.5 分 -> 尚未达成共识
3. 接下来，对于每个标准，并列显示三个评委的分数
4. 对于每个标准，计算最高分和最低分之间的差异
   - 如果任何标准有差异 > 1.0 分 -> 该标准尚未达成共识
5. 最后，验证只有在以下两个条件都满足时才达成共识：
   - 总体分数在 0.5 分以内
   - 所有标准分数在 1.0 分以内

**步骤 4：决策点**

- **如果共识达成**：进入步骤 6（生成共识报告）
- **如果未达成共识 AND 轮次 < 3**：进入步骤 5（运行辩论轮）
- **如果未达成共识 AND 轮次 = 3**：进入步骤 7（报告未达成共识）

**步骤 5：运行辩论轮**

1. 增加轮次计数器（轮次 = 轮次 + 1）
2. 并行启动 3 个评委代理以及相同的评估规范 YAML
3. 每个代理读取：
   - 他们自己的先前报告从文件系统
   - 其他评委的报告从文件系统
   - 原始解决方案
4. 每个代理追加 "辩论轮 {R}" 部分到他们自己的报告文件
5. 等待所有 3 个代理完成
6. 返回步骤 3（检查共识）

**步骤 6：回复报告**

逐步综合评估结果。

1. 小心阅读所有最终报告
2. 在生成报告之前，分析以下内容：
   - 共识状态（达成或未达成）
   - 所有评委之间的主要同意点
   - 如果有的话，主要分歧点
   - 辩论轮如何改变了评估
3. 向用户回复包含以下内容的报告：
   - 如果有共识：
     - 共识分数（所有评委的平均值）
     - 共识强项/弱点
     - 达成共识的轮次数
     - 带有清晰辩护的最终建议
   - 如果没有共识：
       - 所有评委的最终分数显示分歧
       - 未达成共识的特定标准
       - 无法达成共识的原因分析
       - 标记供人工审查
4. 命令完成

**步骤 7：报告未达成共识**

- 报告持续的分歧
- 提供所有评委报告供人工审查
- 标记自动评估无法达成共识

## 最佳实践

### 元评委 + 评委验证

- **从不跳过元评委** - 定制的评估标准产生更好的判断和更基于证据的辩论
- **元评委运行一次** - 所有 3 个评委在所有辩论轮次中使用相同的规范
- **包含 CLAUDE_PLUGIN_ROOT** - 元评委和评委都需要解析的插件根路径
- **元评委 YAML** - 仅将 YAML 传递给评委，不要修改它
- **辩论基础** - 评委在捍卫立场时应参考评估规范标准

### 常见陷阱

- **评委创建新的报告而不是追加** - 丢失辩论历史
- **总管在评委之间传递报告** - 违反文件系统通信原则
- **薄弱的初始评估** - 垃圾进，垃圾出
- **过多的辩论轮次** - 3 轮后收益递减
- **辩论中的奉承** - 评委太容易同意而没有真正的证据
- **修改元评委 YAML** - 规范必须原封不动地传递给所有评委
- **在轮次之间重新运行元评委** - 规范一次生成并共享

### 应该做

- **评委追加到他们自己的报告文件**
- **评委直接从文件系统读取其他报告**
- **基于证据的强初始评估**
- **最多 3 轮辩论**
- **要求用证据来改变立场**
- **基于评估规范标准进行辩论论证**
- **在所有轮次中使用相同的评估规范**

## 示例用法

### 评估 API 实现

```bash
/judge-with-debate Implement REST API for user management --solution "src/api/users.ts" 
```

**阶段 0.5 - 元评委**（假设日期 2025-01-15）：
- 元评委生成评估规范 YAML，其中包含标准：
  - 正确性 (30%)、设计 (25%)、安全性 (20%)、性能 (15%)、文档 (10%)
  - 每个标准的评分标准、检查清单和定义

**阶段 1 - 独立分析**（3 个评委接收规范）：
- `.specs/reports/users-api-2025-01-15.1.md` - 评委 1 评分正确性 4/5，安全性 3/5
- `.specs/reports/users-api-2025-01-15.2.md` - 评委 2 评分正确性 4/5，安全性 5/5
- `.specs/reports/users-api-2025-01-15.3.md` - 评委 3 评分正确性 5/5，安全性 4/5

**分歧检测：** 安全性分数范围从 3-5

**阶段 2 - 辩论轮 1**（评委参考评估规范）：
- 评委 1 辩护 3/5: "缺少速率限制，输入验证不完整根据规范检查清单项目 4"
- 评委 2 挑战: "速率限制存在于中间件（第 45 行），满足规范评分标准"
- 评委 1 修订为 4/5: "错过了中间件，但输入验证根据规范仍然薄弱"
- 评委 3 辩护 4/5: "输入验证根据规范要求足够"

**辩论轮 1 输出：**
- 所有评委现在 4-5/5 在安全性上（差距在 1 分以内）
- 输入验证的分歧仍然存在

**辩论轮 2**（使用相同的评估规范）：
- 评委检查特定验证代码与规范标准
- 评委 2 修订为 4/5: "重新审查后，电子邮件验证正则表达式根据规范检查清单薄弱"
- 共识：安全性 = 4/5

**最终共识：**
```
正确性: 4.3/5
设计: 4.5/5
安全性: 4.0/5 (2 辩论轮达成共识)
性能: 4.7/5
文档: 4.0/5

总体: 4.3/5 - 通过
```

</输出>
