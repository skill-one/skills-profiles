# 基于子代理的开发

通过为每个任务或问题分派新的子代理来创建和执行计划，并在每个或每批任务后进行代码和输出审查。

**核心原则：** 每个任务使用新的子代理 + 任务之间或任务之后的审查 = 高质量、快速迭代。

通过代理执行计划：

- 相同会话（无上下文切换）
- 每个任务使用新的子代理（无上下文污染）
- 每个或每批任务后进行代码审查（及早发现问题）
- 更快的迭代（任务之间无需人工介入）

## 支持的执行类型

### 顺序执行

当你有相互关联的任务或问题，并且需要按顺序执行时，依次调查或修改是最佳方式。

为每个任务或问题分派一个代理，让它按顺序工作。任务或问题完成后，审查输出和代码。

**使用场景：**

- 任务紧密耦合
- 任务需要按顺序执行

### 并行执行

当你有多个无关的任务或问题（不同的文件、不同的子系统、不同的错误），依次调查或修改浪费时间。每个任务或调查都是独立的，可以并行进行。

为每个独立的问题域分派一个代理，让它们并行工作。

**使用场景：**

- 任务基本独立
- 整体审查可以在所有任务完成后进行

## 顺序执行流程

### 1. 加载计划

读取计划文件，创建包含所有任务的 TodoWrite。

### 2. 使用子代理执行任务

对于每个任务：

**分派新的子代理：**

```
任务工具（通用）：
  描述："实现任务 N：[任务名称]"
  提示：|
    你正在实现来自 [计划文件] 的任务 N。

    仔细阅读该任务。你的工作是：
    1. 按任务指定精确实现
    2. 编写测试（如果任务要求遵循 TDD）
    3. 验证实现
    4. 提交你的工作
    5. 汇报

    工作目录：[目录]

    汇报：你实现了什么，你测试了什么，测试结果，修改的文件，任何问题
```

**子代理汇报** 工作摘要。

### 3. 审查子代理的工作

**分派代码审查者子代理：**

```
任务工具（超级能力：代码审查者）：
  使用 requesting-code-review/code-reviewer.md 中的模板

  WHAT_WAS_IMPLEMENTED：[来自子代理的汇报]
  PLAN_OR_REQUIREMENTS：来自 [计划文件] 的任务 N
  BASE_SHA：[任务前的提交]
  HEAD_SHA：[当前提交]
  描述：[任务摘要]
```

**代码审查者返回：** 优势、问题（关键/重要/次要）、评估

### 4. 应用审查反馈

**如果发现问题：**

- 立即修复关键问题
- 在下一个任务前修复重要问题
- 记录次要问题

**如果需要，分派后续子代理：**

```
"修复代码审查中发现的问题：[列出问题]"
```

### 5. 标记完成，下一个任务

- 在 TodoWrite 中将任务标记为已完成
- 移动到下一个任务
- 重复步骤 2-5

### 6. 最终审查

所有任务完成后，分派最终代码审查者：

- 审查整个实现
- 检查是否满足所有计划要求
- 验证整体架构

### 7. 完成开发

最终审查通过后：

- 宣布："我正在使用完成开发分支的技能来完成这项工作。"
- **必需子技能：** 使用 superpowers:finishing-a-development-branch
- 按该技能验证测试、展示选项、执行选择

### 示例工作流程

```
你：我正在使用基于子代理的开发来执行这个计划。

[加载计划，创建 TodoWrite]

任务 1：安装脚本钩子

[分派实现子代理]
子代理：实现了 install-hook 并带测试，5/5 通过

[获取 git SHA，分派代码审查者]
审查者：优势：良好的测试覆盖率。问题：无。准备就绪。

[标记任务 1 完成]

任务 2：恢复模式

[分派实现子代理]
子代理：添加了 verify/repair，8/8 测试通过

[分派代码审查者]
审查者：优势：稳固。问题（重要）：缺少进度报告

[分派修复子代理]
修复子代理：每 100 次对话添加进度

[验证修复，标记任务 2 完成]

...

[所有任务完成后]
[分派最终代码审查者]
最终审查者：所有要求已满足，可以合并

完成！
```

### 警示信号

**永远不要：**

- 任务之间跳过代码审查
- 继续处理未修复的关键问题
- 并行分派多个实现子代理（冲突）
- 未阅读计划任务就实现

**如果子代理任务失败：**

- 分派修复子代理并给出具体指示
- 不要尝试手动修复（上下文污染）

## 并行执行流程

加载计划，严格审查，分批执行任务，批次之间报告审查。

**核心原则：** 分批执行，架构审查的检查点。

**开始时宣布：** "我正在使用执行计划技能来实现这个计划。"

### 第 1 步：加载和审查计划

1. 读取计划文件
2. 严格审查 - 确定对计划是否有任何疑问或担忧
3. 如果有担忧：在开始前与你的人类伙伴提出
4. 如果没有担忧：创建 TodoWrite 并继续

### 第 2 步：执行批次

**默认：前 3 个任务**

对于每个任务：

1. 标记为 in_progress
2. 按计划中的每个步骤精确执行（计划有适口大小的步骤）
3. 按指定运行验证
4. 标记为 completed

### 第 3 步：报告

批次完成后：

- 展示已实现的内容
- 展示验证输出
- 说："准备好获取反馈。"

### 第 4 步：继续

根据反馈：

- 如有必要应用更改
- 执行下一个批次
- 重复直到完成

### 第 5 步：完成开发

所有任务完成后并验证：

- 宣布："我正在使用完成开发分支的技能来完成这项工作。"
- **必需子技能：** 使用 superpowers:finishing-a-development-branch
- 按该技能验证测试、展示选项、执行选择

### 何时停止并寻求帮助

**立即停止执行：**

- 批次中途遇到障碍（缺少依赖、测试失败、指令不明确）
- 计划存在关键差距无法开始
- 你不理解指令
- 验证反复失败

**寻求澄清，而不是猜测。**

### 何时重新审视早期步骤

**返回审查（步骤 1）时：**

- 伙伴根据你的反馈更新计划
- 基本方法需要重新思考

**不要强行通过障碍** - 停止并询问。

### 注意事项

- 首先严格审查计划
- 精确遵循计划步骤
- 不要跳过验证
- 计划要求时参考技能
- 批次之间：只需报告并等待
- 遇到障碍时停止，不要猜测

## 并行调查流程

并行执行的特例，当你有多个无关的失败可以调查，而无需共享状态或依赖时。

### 1. 确定独立域

按损坏的内容分组失败：

- 文件 A 测试：工具审批流程
- 文件 B 测试：批量完成行为
- 文件 C 测试：中止功能

每个域都是独立的 - 修复工具审批不会影响中止测试。

### 2. 创建专注的代理任务

每个代理获得：

- **特定范围：** 一个测试文件或子系统
- **明确目标：** 使这些测试通过
- **约束：** 不要更改其他代码
- **预期输出：** 你发现和修复的内容摘要

### 3. 并行分派

```typescript
// 在 Claude Code / AI 环境中
Task("修复 agent-tool-abort.test.ts 失败")
Task("修复 batch-completion-behavior.test.ts 失败")
Task("修复 tool-approval-race-conditions.test.ts 失败")
// 三个同时运行
```

### 4. 审查和集成

代理返回时：

- 阅读每个摘要
- 验证修复是否存在冲突
- 运行完整测试套件
- 集成所有更改

### 代理提示结构

好的代理提示应：

1. **专注** - 一个清晰的问题域
2. **自包含** - 理解问题所需的所有上下文
3. **明确输出** - 代理应该返回什么？

```markdown
修复 src/agents/agent-tool-abort.test.ts 中的 3 个失败测试：

1. "应该使用部分输出捕获中止工具" - 期望消息中包含 'interrupted at'
2. "应该处理已完成和已中止工具的混合" - 快速工具中止而不是完成
3. "应该正确跟踪 pendingToolCount" - 期望 3 个结果但得到 0

这些是时序/竞争条件问题。你的任务：

1. 读取测试文件并理解每个测试验证的内容
2. 确定根本原因 - 时序问题还是实际错误？
3. 通过：
   - 将任意超时替换为基于事件的等待
   - 如果发现，修复中止实现中的错误
   - 如果行为测试已更改，调整测试预期

不要只是增加超时 - 找到真正的问题。

返回：你发现的内容和修复的摘要。
```

### 常见错误

**❌ 太宽泛：** "修复所有测试" - 代理会迷失方向
**✅ 具体化：** "修复 agent-tool-abort.test.ts" - 专注范围

**❌ 无上下文：** "修复竞争条件" - 代理不知道在哪里
**✅ 上下文：** 粘贴错误消息和测试名称

**❌ 无约束：** 代理可能会重构所有内容
**✅ 约束：** "不要更改生产代码" 或 "仅修复测试"

**❌ 模糊输出：** "修复它" - 你不知道发生了什么变化
**✅ 具体化：** "返回根本原因和更改的摘要"

### 何时不要使用

**相关失败：** 修复一个可能会修复其他 - 首先一起调查
**需要完整上下文：** 理解需要看到整个系统
**探索性调试：** 你还不确定什么已损坏
**共享状态：** 代理会相互干扰（编辑相同文件、使用相同资源）

### 实际会话中的示例

**场景：** 大型重构后，3 个文件中有 6 个测试失败

**失败：**

- agent-tool-abort.test.ts：3 个失败（时序问题）
- batch-completion-behavior.test.ts：2 个失败（工具未执行）
- tool-approval-race-conditions.test.ts：1 个失败（执行计数 = 0）

**决策：** 独立域 - 中止逻辑与批量完成分离，与竞争条件分离

**分派：**

```
代理 1 → 修复 agent-tool-abort.test.ts
代理 2 → 修复 batch-completion-behavior.test.ts
代理 3 → 修复 tool-approval-race-conditions.test.ts
```

**结果：**

- 代理 1：将超时替换为基于事件的等待
- 代理 2：修复了事件结构错误（threadId 在错误位置）
- 代理 3：添加了等待异步工具执行完成的等待

**集成：** 所有修复独立，无冲突，完整套件变绿

**节省时间：** 3 个问题并行解决 vs 顺序解决

### #验证

代理返回后：

1. **审查每个摘要** - 了解发生了什么变化
2. **检查冲突** - 代理是否编辑了相同代码？
3. **运行完整套件** - 验证所有修复是否一起工作
4. **抽查** - 代理可能会犯系统性错误
