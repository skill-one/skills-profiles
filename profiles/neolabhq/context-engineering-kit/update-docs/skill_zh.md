## 用户参数

用户可以提供特定的关注领域或文档类型：

```text
$ARGUMENTS
```

如果未提供任何内容，则专注于未提交更改的所有文档需求。如果所有内容都已提交，则涵盖最新的提交。

## 上下文

在实现新功能或重构现有代码后，必须更新文档以反映更改。此命令使用专门的技术写手代理和并行分析协调自动文档更新。

## 目标

确保所有代码更改都得到适当的文档记录，具有清晰、可维护的文档，帮助用户完成实际任务。

## 重要约束

- **关注用户影响** - 不是每个代码更改都需要文档
- **保留现有文档风格** - 遵循既定模式
- **分析更改的复杂性**：
  - 如果有3个或更多更改的文件影响文档，或重大API更改 → **使用多代理工作流**
  - 如果有1-2个简单更改 → **自己编写文档**
- **文档必须证明其存在的合理性** - 避免膨胀和维护开销

## 工作流步骤

### 准备

1. **如果可用，阅读SADD技能**
   - 如果可用，阅读SADD技能以了解管理代理的最佳实践

2. **发现文档基础设施**
   - 关键：你必须阅读根README.md和项目配置（package.json、pyproject.toml等）
   - 确定现有的文档结构（docs/、README文件、JSDoc）
   - 理解项目约定和文档模式
   - 检查文档生成工具（OpenAPI、JSDoc、TypeDoc）

3. **清点现有文档**

```bash
# 查找所有文档文件
find . -name "*.md" -o -name "*.rst" | grep -E "(README|CHANGELOG|CONTRIBUTING|docs/)"

# 检查生成的文档
find . -name "openapi.*" -o -name "*.graphql" -o -name "swagger.*"
```

### 分析

并行使用haiku代理执行步骤4-5：

4. **分析文档结构**
   - 启动haiku代理以映射现有文档：
     - 确定docs/文件夹结构和组织
     - 查找所有README.md文件及其目的
     - 定位API文档（生成的或手动的）
     - 记录代码库中的JSDoc/TSDoc模式
   - 输出：文档映射，包含位置和类型

5. **分析本地更改**
   - 运行`git status -u`以识别所有已更改的文件（包括未跟踪的）
     - 如果没有未提交的更改，运行`git show --name-status`以获取最新提交
   - 过滤以识别影响文档的更改：
     - 新增/修改的公共API
     - 更改的模块结构
     - 更新的配置选项
     - 新功能或工作流
   - 启动每个已更改文件的单独haiku代理以：
     - 分析文件及其文档影响
     - 确定需要创建/更新的文档
     - 确定需要更新的索引文档（见索引文档部分）
     - 准备文档需求的简短摘要
   - 提取文档任务列表

### 文档规划

6. **按文档区域分组更改**
   - 聚合haiku代理的分析结果
   - 将可以由相同的文档更新覆盖的更改分组：
     - **API文档**：所有API更改 → 单个代理
     - **模块README**：同一模块中的更改 → 单个代理
     - **用户指南**：相关功能更改 → 单个代理
     - **JSDoc/代码注释**：复杂逻辑更改 → 每个文件代理
     - **索引文档**：导航和发现文档的更新 → 单个代理
   - 确定需要更新的索引文档：
     - 根`README.md` - 如果新模块/功能影响项目概述，高概率需要更新。
     - 模块`README.md` - 如果模块的目的、导出或用法已更改
     - `docs/`索引文件 - 如果文档结构已更改
   - 创建文档任务分配

### 文档编写

#### 简单更改流程（1-2个文件，小规模更新）

如果更改简单，请按照此指南自己编写文档：

1. 阅读技术写手代理指南从 @/plugins/sdd/agents/tech-writer.md
2. 审查已更改的文件并理解其影响
3. 确定哪些文档需要更新
4. 遵循项目约定进行有针对性的更新
5. 验证所有链接和示例是否正常工作
6. 确保文档服务于真实用户需求

确保文档：

- 遵循项目风格和约定
- 包括可工作的代码示例
- 避免与现有文档重复
- 帮助用户完成任务

#### 多代理流程（3个或更多文件或重大更改）

如果有多个已更改的文件或重大的文档需求，请使用专门的代理：

7. **启动`doc-analysis`代理（并行）**（Haiku模型）
   - 为每个识别的文档区域启动一个分析代理
   - 为每个代理提供：
     - **上下文**：相关文件中发生了什么更改（git diff）
     - **目标**：要分析的文档区域
     - **资源**：该区域现有的文档
     - **目标**：创建详细的文档需求
     - **输出**：具体的文档任务及其优先级：
       - **关键**：用户面API更改、破坏性更改
       - **重要**：新功能、配置选项
       - **锦上添花**：代码注释、小规模澄清
   - 收集所有文档需求报告

8. **启动`sdd:tech-writer`代理进行文档编写（并行）**（Sonnet或Opus模型）
   - 为每个文档区域启动一个技术写手代理
   - 为每个代理提供：
     - **上下文**：分析代理的文档需求
     - **目标**：要创建/更新的特定文档文件
     - **文档任务**：来自分析代理的任务列表
     - **指导**：阅读技术写手代理 @/plugins/sdd/agents/tech-writer.md 以获取最佳实践
     - **资源**：用于风格参考的现有文档
     - **目标**：创建/更新全面的文档
     - **约束**：
       - 遵循现有的文档模式
       - 包括可工作的代码示例
       - 避免文档膨胀
       - 关注用户任务，而不是实现细节

9. **启动质量审查代理（并行）**（Sonnet或Opus模型）
   - 再次启动`sdd:tech-writer`代理进行质量审查
   - 提供：
     - **上下文**：原始更改 + 新创建的文档
     - **目标**：验证文档质量和完整性
     - **审查标准**：
       - 所有用户面更改都有文档记录
       - 代码示例准确且可工作
       - 链接和引用有效
       - 文档遵循项目约定
       - 没有不必要的文档膨胀
     - **输出**：通过确认或需要修复的问题列表

10. **如有必要，进行迭代**
    - 如果任何文档区域存在质量问题：返回步骤8
    - 仅针对有差距的区域启动新的技术写手代理
    - 提供具体的修复说明
    - 继续进行，直到所有文档通过质量审查

11. **最终验证**
    - 整体审查所有文档更改
    - 验证文档之间的交叉引用是否正常工作
    - 确保没有冲突信息
    - 确认文档结构是可导航的

## 成功标准

- 所有用户面更改都有适当的文档 ✅
- 代码示例准确且已测试 ✅
- 文档遵循项目约定 ✅
- 没有损坏的链接或引用 ✅
- 由审查代理验证质量 ✅

## 核心文档理念

### 文档层次结构

```text
关键：文档必须证明其存在的合理性
├── 它是否帮助用户完成实际任务？→ 保留
├── 它是否在需要时可发现？→ 改进或删除  
├── 它是否会被维护？→ 保持简单或自动化
└── 它是否重复现有文档？→ 删除或合并
```

### 需要记录的内容 ✅

**用户面文档：**

- **入门指南**：快速设置，5分钟内获得首次成功
- **操作指南**：面向任务、解决问题的文档  
- **API参考**：当手动文档比生成文档更有价值时
- **故障排除**：常见真实问题及其解决方案
- **架构决策**：当它们影响用户体验时

**开发者文档：**

- **贡献指南**：实际工作流程，而不是理想化的
- **模块README**：导航辅助，简要说明目的
- **复杂业务逻辑**：代码库中的JSDoc
- **集成模式**：常见任务的可用示例

### 不需要记录的内容 ❌

**产生文档债务的内容：**

- 没有特定任务的通用“入门指南”
- 重复生成/模式文档的API文档  
- 解释代码明显功能的代码注释
- 不存在的流程的流程文档
- 简单、自解释结构的架构文档
- 重复git历史的变更日志
- 临时解决方案的文档
- 说同样内容的多个README

**警告标志 - 停止并重新考虑：**

- “此文档解释...” → 它帮助用户完成什么任务？
- “如您所见...” → 如果它很明显，为什么需要记录它？
- “TODO：更新此内容...” → 它真的会被更新吗？
- “有关更多详细信息，请参阅...” → 信息是否在用户期望的地方？

### 用户旅程映射

确定关键用户路径：

- **开发者入职**：克隆 → 设置 → 首次贡献
- **API消费**：发现 → 身份验证 → 集成
- **功能使用**：问题 → 解决方案 → 实现
- **故障排除**：错误 → 诊断 → 解决

### 文档差距分析

**高影响差距**（优先处理）：

- 缺少主要用例的设置说明
- 没有示例的API端点
- 没有解决方案的错误消息
- 没有目的陈述的复杂模块

**低影响差距**（通常跳过）：

- 没有注释的小规模实用函数
- 单个模块使用的内部API
- 临时实现
- 自解释的配置

## 智能文档策略

### 何时生成 vs. 编写

**用于自动生成：**

- **OpenAPI/Swagger**：从代码注释生成的API文档
- **GraphQL模式**：类型定义和查询
- **JSDoc**：函数签名和基本参数文档
- **数据库模式**：Prisma、TypeORM、Sequelize模型
- **CLI帮助**：来自参数解析库

**手动编写文档：**

- **集成示例**：真实世界的使用模式
- **业务逻辑解释**：决策的原因
- **故障排除指南**：实际问题的解决方案
- **入门工作流**：精心策划的快车道
- **架构决策**：当它们影响API设计时

### 文档工具及其优势

**OpenAPI/Swagger：**

- ✅ 完美用于：REST API参考、请求/响应示例
- ❌ 不适用于：集成指南、身份验证流程
- **限制**：需要纪律性保持注释当前

**GraphQL introspection：**

- ✅ 完美用于：模式探索、类型定义
- ❌ 不适用于：查询示例、业务上下文
- **限制**：没有使用模式或业务逻辑

**Prisma Schema：**

- ✅ 完美用于：数据库关系、模型定义  
- ❌ 不适用于：查询模式、性能考虑
- **限制**：不捕获业务规则

**JSDoc/TSDoc：**

- ✅ 完美用于：函数合同、参数类型
- ❌ 不适用于：模块架构、集成示例  
- **限制**：没有强制执行而不容易过时

## 文档审计指南

### 质量评估

对于每个现有文档，询问：

1. 此内容上次更新是什么时候？ (>6个月 = 可疑)
2. 此信息是否在别处可用？ (重复检查)
3. 此内容是否帮助完成实际任务？ (效用检查)  
4. 是否在需要时可以找到？ (可发现性检查)
5. 移除此内容是否会破坏某人的工作流程？ (影响检查)

### 战略更新

**高影响、低努力更新：**

- 修复损坏的链接和过时的代码示例
- 添加导致常见失败的缺失设置步骤
- 创建模块级README导航辅助
- 记录身份验证/配置模式

**尽可能自动化：**

- 设置从代码生成API文档
- 配置JSDoc构建  
- 添加模式文档生成
- 创建文档检查/新鲜度检查

## 文档模式参考

### README.md最佳实践

**项目根README：**

```markdown
# 项目名称

简要描述（最多1-2句话）。

## 快速入门
[最快成功路径 - 必须在<5分钟内工作]

## 文档
- [API参考](./docs/api/) - 如果复杂API
- [指南](./docs/guides/) - 如果复杂工作流  
- [贡献](./CONTRIBUTING.md) - 如果接受贡献

## 状态
[当前状态、已知限制]
```

**模块README模式：**

```markdown
# 模块名称

**目的**：用一句话描述此模块存在的原因。

**主要导出**：用户需要的主要函数/类。

**用法**：一个最小的示例。

参见：[主文档](../docs/)以获取详细指南。
```

### 索引文档

索引文档作为导航辅助和文档的入口点。更新文档时，始终检查相关索引文档是否需要更新。

**常见的需要更新的索引文档：**

| 文档 | 位置 | 更新时 |
|------|------|-------|
| `README.md` | 项目根 | 新功能、模块或重大更改 |
| `README.md` | 模块目录 | 模块API、导出或目的更改 |
| `index.md` | `docs/`根 | 新文档页面或结构更改 |
| `getting-started.md` | `docs/` | 设置步骤、先决条件或快速启动更改 |
| `guides.md` | `docs/` | 添加新指南或指南类别更改 |
| `reference.md` | `docs/` | 添加新的API参考或参考结构 |
| `resources.md` | `docs/` | 添加新工具、链接或资源 |
| `SUMMARY.md` | `docs/`（GitBook） | 任何文档结构更改 |
| `_sidebar.md` | `docs/`（Docsify） | 导航结构更改 |
| `mkdocs.yml` | 项目根（MkDocs） | 文档导航更改 |

**索引文档更新检查清单：**

当文档更改影响模块或功能时：

1. **模块级索引** - 更新模块的`README.md`：
   - 添加/移除导出的函数或类
   - 如果API更改，更新用法示例
   - 如果范围更改，更新目的陈述

2. **部分级索引** - 更新相关的`docs/`索引文件：
   - `docs/guides.md` - 如果添加了新指南
   - `docs/reference.md` - 如果添加了新的API文档
   - `docs/tutorials.md` - 如果添加了新教程

3. **项目级索引** - 更新根`README.md`：
   - 将新功能添加到功能列表
   - 如果入口点更改，更新快速启动
   - 更新项目结构中的新模块

   - `SUMMARY.md`对于GitBook项目
   - `_sidebar.md`对于Docsify项目
   - `mkdocs.yml` nav部分对于MkDocs项目

### JSDoc最佳实践

**记录这些：**

```typescript  
/**
 * 使用重试逻辑和欺诈检测处理支付。
 * 
 * @param payment - 包括金额和方法在内的支付详情
 * @param options - 重试和验证的配置  
 * @returns 解决方案为交易结果ID的Promise
 * @throws PaymentError - 当重试后支付失败时
 * 
 * @示例
 * ```typescript
 * const result = await processPayment({
 *   amount: 100,
 *   currency: 'USD', 
 *   method: 'card'
 * });
 * ```
 */
async function processPayment(payment: PaymentRequest, options?: PaymentOptions): Promise<PaymentResult>
```

**不要记录这些：**

```typescript
// ❌ 显然的功能
getName(): string

// ❌ 简单的CRUD
save(user: User): Promise<void>

// ❌ 自解释的实用工具  
toLowerCase(str: string): string
```
