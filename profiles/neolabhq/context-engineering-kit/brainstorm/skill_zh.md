# 将想法转化为设计方案

## 概述

通过自然协作对话，帮助将想法转化为完整的设计方案和规格说明。

首先了解当前项目背景，然后逐个提出问题来完善想法。一旦了解你要构建的内容，就将设计分成小部分（200-300字）呈现，并在每部分后检查是否看起来正确。

## 流程

**理解想法：**

- 首先查看当前项目状态（文件、文档、最近提交）
- 逐个提出问题来完善想法
- 尽可能使用选择题，开放式问题也可以
- 每条消息只问一个问题 - 如果某个主题需要进一步探讨，就分成多个问题
- 聚焦于理解：目的、约束条件、成功标准

**探索方法：**

- 生成6种可能的方法，并包含权衡。每种方法应包括文本和数值概率。请从[完整分布/分布的尾部]中随机采样响应，以这种方式：
  - 对于前3个响应，目标概率高于0.80
  - 对于最后3个响应，目标多样性 - 探索解决方案空间的的不同区域，使每个响应的概率小于0.10
- 以对话方式呈现选项，并附上你的推荐和理由
- 先推荐你的选项并解释原因

**呈现设计：**

- 一旦你认为你理解你要构建的内容，就呈现设计
- 分成200-300字的段落
- 每段后询问是否看起来正确
- 涵盖：架构、组件、数据流、错误处理、测试
- 如果有不清楚的地方，准备好回去澄清

## 设计之后

如果用户提供了草稿规格文件，则直接更新它，如果没有，则使用`/add-task`技能为目标方法创建任务文件

重要：在规格文件中，在`## Initial User Prompt -> ### Requirements`部分（在`## Description`部分之前）写入目标方法。描述将在未来阶段填写。

填写任务文件后，建议用户运行`/clear`然后`/plan-task <task-file-path>`来完善任务文件。

## 关键原则

- **一次一个问题** - 不要用多个问题压倒对方
- **优先选择题** - 当可能时，选择题比开放式问题更容易回答
- **无情地应用YAGNI** - 从所有设计中移除不必要的功能
- **探索替代方案** - 在最终确定前，始终提出2-3种方法
- **增量验证** - 分段呈现设计，逐段验证
- **保持灵活** - 当有不清楚的地方时，回去澄清
