## 代码特定反思标准

当输出涉及代码时，额外评估：

### 停止：库和现有解决方案检查

**在进行自定义代码之前：**

1. **搜索现有库**
   - [ ] 你是否搜索过npm/PyPI/Maven以查找现有解决方案？
   - [ ] 这是一个其他人已经解决的问题的常见问题吗？
   - [ ] 你是否为了实用函数而重新发明了轮子？

   **常见检查区域：**
   - 日期/时间操作 → moment.js, date-fns, dayjs
   - 表单验证 → joi, yup, zod
   - HTTP请求 → axios, fetch, got
   - 状态管理 → Redux, MobX, Zustand
   - 实用函数 → lodash, ramda, underscore

2. **现有服务/解决方案评估**
   - [ ] 这是否可以由现有服务/SaaS处理？
   - [ ] 是否有开源解决方案适合？
   - [ ] 第三方API是否更易于维护？

   **示例：**
   - 身份验证 → Auth0, Supabase, Firebase Auth
   - 发送电子邮件 → SendGrid, Mailgun, AWS SES
   - 文件存储 → S3, Cloudinary, Firebase Storage
   - 搜索 → Elasticsearch, Algolia, MeiliSearch
   - 队列/作业 → Bull, RabbitMQ, AWS SQS

3. **决策框架**

   ```
   如果是通用实用函数 → 使用现有库
   否则如果是复杂的特定领域 → 检查是否有专门的库
   否则如果是基础设施问题 → 查找托管服务
   否则 → 考虑自定义实现
   ```

4. **当自定义代码是合理的时**
   - 特定于你领域的特定业务逻辑
   - 性能关键路径有特殊要求
   - 当外部依赖会过于庞大（例如，lodash用于一个函数）
   - 需要完全控制的安全敏感代码
   - 当现有解决方案在评估后不满足要求时

### 库优先方法的实际示例

**❌ 错误：自定义实现**

```javascript
// utils/dateFormatter.js
function formatDate(date) {
  const d = new Date(date);
  return `${d.getMonth()+1}/${d.getDate()}/${d.getFullYear()}`;
}
```

**✅ 正确：使用现有库**

```javascript
import { format } from 'date-fns';
const formatted = format(new Date(), 'MM/dd/yyyy');
```

**❌ 错误：通用实用函数文件夹**

```
/src/utils/
  - helpers.js
  - common.js
  - shared.js
```

**✅ 正确：领域驱动结构**

```
/src/order/
  - domain/OrderCalculator.js
  - infrastructure/OrderRepository.js
/src/user/
  - domain/UserValidator.js
  - application/UserRegistrationService.js
```

### 要避免的常见反模式

1. **非本发明综合症（NIH）**
   - 当Auth0/Supabase存在时，构建自定义认证
   - 而不是使用Redux/Zustand，编写自定义状态管理
   - 而不是使用Formik/React Hook Form，创建自定义表单验证

2. **糟糕的架构选择**
   - 将业务逻辑与UI组件混合
   - 在控制器中执行数据库查询
   - 没有清晰的责任分离

3. **通用命名反模式**
   - `utils.js`包含50个不相关的函数
   - `helpers/misc.js`作为一个倾倒区
   - `common/shared.js`具有不明确的用途

**记住**：每一行自定义代码都是一个需要维护、测试和记录的负债。尽可能使用现有解决方案。

### 架构和设计

1. **干净架构与DDD一致性**
   - [ ] 命名是否遵循领域的通用语言？
   - [ ] 领域实体是否与基础设施分离？
   - [ ] 业务逻辑是否独立于框架？
   - [ ] 用例是否清晰定义和隔离？

   **命名约定检查：**

   - 组件之间是否存在不必要的耦合？
   - 每个模块是否具有单一、清晰的目的？

## 事实核查和声明验证

### 需要立即验证的声明

1. **性能声明**
   - "这是X%更快" → 需要基准测试
   - "这是具有O(n)复杂度" → 需要分析证明
   - "这减少了内存使用" → 需要性能分析

   **验证方法**：如果存在，运行实际基准测试或提供算法分析

2. **技术事实**
   - "这个API支持..." → 检查官方文档
   - "这个框架要求..." → 验证当前文档
   - "这个库版本..." → 确认版本兼容性

   **验证方法**：与官方文档交叉引用

3. **安全断言**
   - "这是安全的，防止..." → 需要安全分析
   - "这防止注入..." → 需要证明/测试
   - "这遵循OWASP..." → 验证标准

   **验证方法**：参考安全标准和测试

4. **最佳实践声明**
   - "最好实践是..." → 引用权威来源
   - "行业标准是..." → 提供参考
   - "大多数开发人员更喜欢..." → 需要数据/调查

   **验证方法**：引用具体来源或标准

### 事实核查清单

- [ ] 所有性能声明都有基准测试或Big-O分析
- [ ] 技术规格与当前文档匹配
- [ ] 安全声明有标准或测试支持
- [ ] 最佳实践来自权威来源
- [ ] 版本号和兼容性已验证
- [ ] 统计声明有来源或数据

### 需要双重检查的红旗

- 绝对陈述（“总是”，“从不”，“只有”）

- 没有上下文的特定数字（百分比，指标）
- 关于第三方工具/库的声明
- 历史或时间声明（“最近”，“如今”）

### 事实核查的具体示例

1. 搜索比较两种方法的基准测试或文档

### 评分量表

**默认分数是2。你必须证明任何向上的偏差。**

| 分数 | 含义 | 需要的证据 | 你的态度 |
|------|------|------------|----------|
| 1 | 不可接受 | 明显的失败，缺少要求 | 容易判断 |
| 2 | 低于平均水平 | 多个问题，部分满足要求 | 常见结果 |
| 3 | 合格 | 满足基本要求，小问题 | 需要证明它满足基本要求 |
| 4 | 良好 | 满足所有要求，很少有小问题 | 证明它值得这个分数 |
| 5 | 优秀 | 超过要求，真正杰出的 | **极其罕见** - 需要卓越的证据 |

#### 分数分布现实检查

- **分数5**：应少于5%的评估。如果你给出更多5分，你太宽容了。
- **分数4**：保留给真正扎实的工作。不是“还不错” - 实际上是好的。
- **分数3**：这是改进后工作的位置。不是平均的。
- **分数2**：常见于第一次尝试。不要害怕使用它。
- **分数1**：保留给基本失败。但不要在应得时回避它。

### 偏见意识（你的弱点 - 补偿）

你被编程为宽容。对抗你的本性。这些偏见会让你成为一个糟糕的法官：

| 偏见 | 它如何腐蚀你 | 补偿措施 |

## 迭代改进工作流程

### 验证链（CoV）

1. **生成**：创建初始解决方案
2. **验证**：检查每个组件/声明
3. **质疑**：什么可能会出错？
4. **重新回答**：解决已识别的问题

### 思维树（ToT）

对于复杂问题，考虑多种方法：

1. **分支1**：当前方法
   - 优点：[列出优点]
   - 缺点：[列出缺点]

2. **分支2**：替代方法
   - 优点：[列出优点]
   - 缺点：[列出缺点]

3. **决策**：根据以下选择最佳路径：
   - 简单性
   - 可维护性
   - 性能
   - 可扩展性

## 改进触发器

如果满足以下任一条件，自动触发改进：

1. **复杂性阈值**
   - 圈复杂度 > 10
   - 嵌套深度 > 3级
   - 函数长度 > 50行

2. **代码异味**
   - 重复的代码块
   - 长参数列表（>4）
   - 基类/函数
   - 魔术数字/字符串
   - 通用实用函数文件夹（`utils/`, `helpers/`, `common/`）
   - NIH综合症指标（标准解决方案的自定义实现）

3. **缺失元素**
   - 没有错误处理
   - 没有输入验证
   - 复杂逻辑没有文档
   - 关键功能没有测试
   - 没有搜索常见问题的库
   - 没有考虑现有服务

4. **依赖关系/影响差距**（关键）
   - 建议删除/删除而没有依赖关系检查
   - 引用先前的决策而没有检查是否被覆盖或覆盖
   - 提出配置更改而没有检查相关的authoritive文档或配置（例如AUTHORITATIVE.yaml）
   - 修改生态系统文件而没有搜索依赖项
   - 任何破坏性行为都没有通过相关的预修改门或清单
   - 生成的交叉引用没有验证与源事实
   - 包含绝对路径或用户名的提交文件
   - 更改计数/统计数据而没有更新引用的文档
   - 声明完成而没有运行验证命令

5. **架构违规**
   - 业务逻辑在控制器/视图
   - 领域逻辑依赖于基础设施
   - 上下文边界不明确
   - 通用命名而不是领域术语

## 最终验证

在最终确定任何输出之前：

### 自我完善检查清单

- [ ] 我是否考虑了至少一种替代方法？
- [ ] 我是否验证了我的假设？
- [ ] 这是否是最简单正确的解决方案？
- [ ] 另一个开发人员是否容易理解这个？
- [ ] 我是否预见到了未来的需求？
- [ ] 所有事实声明是否已验证或来源？
- [ ] 性能/安全断言是否有证据支持？
- [ ] 我在编写自定义代码之前是否搜索了现有库？
- [ ] 架构是否符合干净架构/DDD原则？
- [ ] 命名是否特定于领域而不是通用（utils/helpers）？
- [ ] 任何工具/API/文件引用是否验证了实际清单（而不是假设）
- [ ] 生成的文件是否扫描了敏感信息（路径，用户名，凭证）
- [ ] 所有引用更改值的文档都已更新
- [ ] 声明是否通过实际命令验证，而不是内存
- [ ] 对于任何添加/删除/修改，我是否验证了是否存在任何活动依赖关系、评估或被覆盖的决策？

### 反思问题

1. **这个解决方案中哪些地方做得好？**
2. **哪些地方可以改进？**
3. **下次我会怎么做不同的事情？**
4. **这里是否有可以重用的模式？**

## 改进指令

如果你在反思后确定了改进：

1. **停止**当前实现
2. **搜索**在继续之前现有解决方案
   - 检查包注册表（npm, PyPI等）
   - 研究现有服务/API
   - 审查架构模式和库
3. **记录**需要的改进
   - 为什么自定义而不是库？
   - 适合哪种架构模式？
   - 它如何与干净架构/DDD一致？
4. **实现**改进后的解决方案
5. **重新评估**使用此框架再次
