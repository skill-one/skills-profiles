# /em:postmortem — 对错误的坦诚分析

**命令：** `/em:postmortem <事件>`

不是追究责任。而是理解。失败的交易、错失的季度、表现不佳的功能、不成功的招聘。实际发生了什么，为什么发生，以及因此发生了哪些改变。

---

## 大多数复盘失败的原因

它们要么变成以下两种情况之一：

**指责会议** — 有人被推卸责任，防御性心理增强，真正的原因没有得到审视，同样的问题以不同的形式再次发生。

**粉饰太平** — “我们学到了很多，我们会做得更好，这里有12个模糊的行动项。” 什么都没改变。同样的问题，不同的季度。

真正的复盘既不是前者，也不是后者。它是对系统失败的严格调查。不是“谁的错”，而是“哪些条件使得这个结果事后看来是可预测的？”

**目的：** 从失败中提取最大的学习价值，以便防止再次发生并改进系统。

---

## 框架

### 第1步：精确定义事件

在分析之前：准确描述发生了什么。

- 预期结果是什么？
- 实际结果是什么？
- 何时首次出现差距？
- 有什么影响（财务、运营、声誉）？

精确性很重要。“我们错过了第三季度的收入”不够精确。“我们关闭了420K的新ARR，与680K的目标相比，少了260K，主要是由三个交易滑到第四季度，以及一个交易输给了竞争对手”才是精确的。

### 第2步：正确执行的“五个为什么”

目标：从**发生了什么**（症状）到**为什么发生**（根本原因）。

标准的错误“五个为什么”：
- 为什么我们错过了收入？因为交易滑了。
- 为什么交易滑了？因为销售周期比预期的长。
- 为什么？因为客户购买流程很复杂。
- 为什么？因为我们面向企业客户。
- 为什么？企业销售就是如此。

→ 结论：没什么可做的。企业销售就是这样。

真正的“五个为什么”：
- 为什么我们错过了收入？三个交易从季度中滑了出去。
- 为什么那些交易滑了？它们都没有识别出具有预算授权的负责人。
- 为什么我们没有在负责人推进交易？我们的资格标准没有要求这一点。
- 为什么我们的资格标准没有要求这一点？八个月前我们建立标准时，我们还在中小企业市场，而不是企业市场。
- 为什么我们没有随着ICP的变化更新资格标准？没有负责人，没有标准审查流程。

→ 根本原因：资格标准过时，没有负责人，没有审查流程。
→ 修复措施：更新标准，分配负责人，增加季度审查。

**好的根本原因的测试：** 你可以通过具体的、具体的改变来防止再次发生吗？如果是，你就找到了真正的问题。

### 第3步：区分贡献因素和根本原因

大多数事件都有多个贡献因素。并非所有因素都是根本原因。

**贡献因素：** 使情况恶化，但不是核心原因。如果移除，结果可能会有所不同——但同样的问题会再次发生。

**根本原因：** 使结果可能性的基本条件。修复这个问题，这类问题就不会再次发生。

示例——失败的招聘：
- 贡献因素：流程仓促，背景调查被跳过，团队压力很大需要人员补充
- 根本原因：没有定义能力框架，所以面试流程因谁负责而异

**这种区分很重要。** 如果你只解决贡献因素，下次你会遇到一个看起来不同但结构上相同的失败。

### 第4步：识别被忽视的警告信号

每个失败都有前兆。事后看来很明显。这个步骤的价值在于让它们事前就明显。

询问：
- 在什么时间点负面结果可以预测？
- 在那个时间点可见的信号是什么？
- 谁看到了它们？当它们提出时发生了什么？
- 为什么没有被采取行动？

**常见模式：**
- 信号被高级人员驳回
- 没人觉得安全说出来，所以没有提出信号
- 看到了信号，但没有明确的所有权来采取行动
- 数据可用，但没人看
- 团队过于乐观，没有认真对待负面信号

这个步骤对于系统性问题尤其重要——“我们没有觉得安全提出这个担忧”是一个比“交易资格有问题”更深的根本原因。

### 第5步：区分可控与不可控因素

一些失败发生在正确决策的情况下。一些失败是因为错误决策。知道区别可以防止过度纠正和纠正不足。

- **可控：** 流程、标准、团队能力、资源分配、做出的决策
- **不可控：** 市场条件、客户决策、竞争对手行为、宏观事件

对于不可控因素：可以做些什么来提高对类似事件的抵御能力？
对于可控因素：具体需要改变什么？

**警告：** “这是在我们控制范围之外的”有时被用来逃避责任。要严格。

### 第6步：建立变更登记表

每个复盘都以变更登记表结束——具体的承诺、负责人和日期。

**糟糕的行动项：**
- “我们将改进我们的资格流程”
- “沟通会更好”
- “我们将更严格地预测”

**好的行动项：**
- “Ravi负责在3月15日之前重写资格标准，将负责人识别为硬性要求。新标准从3月22日开始在每周销售会议上审查。”
- “在3月10日之前，Elena为任何超过60天没有产品演示的开放机会在CRM中添加交易滑落风险标志”
- “Maria从4月1日开始每6周运行一次30分钟的回顾，与企业销售团队一起，审查输赢数据”

**对于每个行动项：**
- 具体是什么在改变？
- 谁负责？
- 何时？
- 如何验证它有效？

### 第7步：验证日期

最常被跳过的步骤。如果没人检查变更是否真的发生并且真的有效，复盘就毫无用处。

设定验证日期：“我们将在6月的董事会会议上审查资格标准是否已更新，以及交易滑落率是否有所改善。”

没有这个，复盘就是一场表演。

## 复盘输出格式

```
事件：[名称和日期]
预期：[应该发生什么]
实际：[发生了什么]
影响：[量化]

时间线
[日期]：[发生了什么或可见的]
[日期]：...

五个为什么
1. [为什么X发生?] → 因为[Y]
2. [为什么Y发生?] → 因为[Z]
3. [为什么Z发生?] → 因为[A]
4. [为什么A发生?] → 因为[B]
5. [为什么B发生?] → 因为[根本原因]

根本原因：[一句话清晰说明]

贡献因素
• [因素] — 如何贡献
• [因素] — 如何贡献

被忽视的警告信号
• [信号在什么日期可见] — 为什么没有被采取行动

可控因素：[列表]
不可控因素：[列表]

变更登记表
| 行动项 | 负责人 | 截止日期 | 验证方式 |
|--------|-------|----------|-------------|
| [具体变更] | [姓名] | [日期] | [如何验证] |

验证日期：[检查日期]
```

## 好的复盘的语气

指责廉价。理解困难。

目标不是证明有人犯了错误。目标是理解系统为什么产生了这个结果——以便改进系统。

“销售人员没有正确资格交易”是指责。
“我们的资格框架在我们转向高端市场时没有更新，而且没有人负责保持其最新状态”是理解。

第一个版本会解雇或羞辱某人。第二个版本会建立更具弹性的组织。

两者可能同时为真。区别在于：哪一个实际上防止了再次发生？
