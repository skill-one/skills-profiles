# 运行 Nx 生成器

Nx 生成器是强大的工具，用于创建项目骨架、执行自动代码迁移或在单一代码库中自动化重复任务。它们确保代码库的一致性，并减少样板工作。

当用户想要执行以下操作时，适用此技能：

- 创建新的项目，如库或应用程序
- 创建功能或样板代码的骨架
- 运行特定于工作区或自定义生成器
- 执行任何 Nx 生成器可完成的操作

## 关键原则

1. **始终使用 `--no-interactive`** - 防止挂起执行的提示
2. **阅读生成器的源代码** - 仅凭模式是不够的；了解生成器实际做什么
3. **匹配现有仓库模式** - 研究仓库中类似的工件并遵循其约定
4. **通过 lint/test/build/typecheck 等进行验证** - 生成的代码必须通过验证。列出的目标只是示例，使用适合此工作区的内容。

## 步骤

### 1. 发现可用生成器

使用 Nx CLI 发现可用生成器：

- 列出插件的生成器：`npx nx list @nx/react`
- 查看可用插件：`npx nx list`

这包括插件生成器（例如，`@nx/react:library`）和本地工作区生成器。

### 2. 将生成器与用户请求匹配

确定哪些生成器（或生成器）可以满足用户的需求。考虑他们想要什么类型的工件、相关的框架以及任何提到的特定生成器名称。

**重要提示**：当本地工作区生成器和外部插件生成器都可以满足请求时，**始终优先选择本地工作区生成器**。本地生成器针对特定仓库的模式进行了定制。

如果没有合适的生成器，你可以停止使用此技能。然而，证明责任很高——在决定没有适用生成器之前，仔细考虑所有可用的生成器。

### 3. 获取生成器选项

使用 `--help` 标志了解可用选项：

```bash
npx nx g @nx/react:library --help
```

注意必需选项、可能需要覆盖的默认值以及与用户请求相关的选项。

### 库可构建性

**默认使用不可构建的库**，除非有特定原因需要构建。

| 类型                        | 使用场景                                                       | 生成器标志                     |
| --------------------------- | ----------------------------------------------------------------- | ----------------------------------- |
| **不可构建**（默认）        | 内部单一代码库库被应用程序消费                           | 无 `--bundler` 标志                 |
| **可构建**               | 发布到 npm、跨仓库共享、用于缓存命中的稳定库             | `--bundler=vite` 或 `--bundler=swc` |

不可构建的库：

- 直接导出 `.ts`/`.tsx` 源代码
- 消费者的打包器编译它们
- 更快的开发体验，配置更少

可构建的库：

- 有自己的构建目标
- 适用于很少变化的稳定库（缓存命中）
- 发布到 npm 所需

**如果不确定，请询问用户**：“这个库应该是可构建的（自己的构建步骤，更好的缓存）还是不可构建的（直接消费源代码，更简单的设置）？”

### 4. 阅读生成器源代码

**这一步至关重要**。仅凭模式无法告诉你所有信息。阅读源代码可以帮助你：

- 知道将创建/修改哪些文件以及位置
- 了解副作用（更新配置、安装依赖等）
- 识别从模式中不明显的行为和选项
- 了解选项如何相互作用

要找到生成器源代码：

- 对于插件生成器：使用 `node -e "console.log(require.resolve('@nx/<plugin>/generators.json'));"` 找到 generators.json，然后从那里定位源代码
- 如果失败，直接从 `node_modules/<plugin>/generators.json` 读取
- 对于本地生成器：通常在 `tools/generators/` 或本地插件目录中。在仓库中搜索生成器名称。

阅读源代码后，重新考虑：这是正确的生成器吗？如果不是，回到步骤 2。

> **⚠️ `--directory` 标志的行为可能具有误导性。**
> 它应指定生成库或组件的完整路径，而不是它将生成的父路径。
>
> ```bash
> # ✅ 正确 - 目录是库的完整路径
> nx g @nx/react:library --directory=libs/my-lib
> # 生成 libs/my-lib/package.json 和更多
>
> # ❌ 错误 - 这将在 libs 和 libs/src/... 处创建文件
> nx g @nx/react:library --name=my-lib --directory=libs
> # 生成 libs/package.json 和更多
> ```

### 5. 检查现有模式

在生成之前，检查代码库的目标区域：

- 查看类似的现有工件（其他库、应用程序等）
- 确定命名约定、文件结构和配置模式
- 注意使用的测试运行器、构建工具和 linter
- 配置生成器以匹配这些模式

### 6. 干运行以验证文件位置

**始终首先使用 `--dry-run` 运行**以验证文件将创建在正确的位置：

```bash
npx nx g @nx/react:library --name=my-lib --dry-run --no-interactive
```

仔细查看输出。如果文件将创建在错误的位置，根据从生成器源代码中学到的知识调整选项。

注意：某些生成器不支持干运行（例如，如果它们安装 npm 包）。如果由于此原因干运行失败，请继续实际运行生成器。

### 7. 运行生成器

执行生成器：

```bash
nx generate <generator-name> <options> --no-interactive
```

> **提示**：新包通常需要正确配置工作区依赖（例如，导入共享类型、被应用程序消费）。`link-workspace-packages` 技能可以帮助正确添加这些依赖。

### 8. 修改生成的代码（如果需要）

生成器提供了一个起点。根据需要修改输出：

- 添加或修改功能
- 调整导入、导出或配置
- 与现有代码模式集成

**重要提示**：如果你替换或删除生成的测试文件（例如，`*.spec.ts`），请要么编写有意义的替换测试，要么从项目配置中删除 `test` 目标。空的测试套件会导致 `nx test` 失败。

### 9. 格式化和验证

格式化所有生成的/修改的文件：

```bash
nx format --fix
```

此示例是内置的 nx 格式化，使用 prettier。可能有其他格式化工具适用于此工作区，在适当的时候使用这些工具。

然后验证生成的代码是否正常工作。请记住，你使用生成器或后续修改所做的更改可能会影响各种项目，因此通常不足以仅运行你刚刚创建的工件的构建目标。

```bash
# 这些目标只是示例！
nx run-many -t build,lint,test,typecheck
```

这些目标是在许多工作区中常用的示例。你应该研究此工作区及其项目可用的其他目标。CI 配置通常是指导必须通过的关键目标的良好指南。

如果验证失败且问题可管理（几个 lint 错误、轻微的类型问题），请修复它们。如果问题很广泛，请首先尝试明显的修复，然后向用户提供有关已生成的内容、失败内容以及你所尝试的内容的详细信息。
