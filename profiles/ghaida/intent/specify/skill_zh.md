# Specify — 桥接设计到工程

## 概述

这项技能将设计工作转化为可执行、准备就绪的文档。它生成结构化的规格说明、资源包、测试计划以及利益相关者演示文稿，确保设计意图能够顺利传递到生产阶段。当设计需要进入工程阶段、需要跨职能团队清晰理解或需要以防止返工的方式记录决策时，请使用此技能。

---

## 技能系列

Specify 与完整的 Intent 技能系统协同工作：

- **`/strategize`**：他们的简报和假设为所有 Specify 内容提供“为何”。每个规格说明都应追溯到战略意图——这个功能为何存在、它测试了什么假设、它满足了什么用户需求。
- **`/investigate`**：他们的研究成果为你的用例提供证据基础。真实用户引言、观察到的行为和验证的痛点使规格说明更具说服力和准确性，而非假设性。
- **`/blueprint`**：他们的系统架构限制并指导你的规格说明。服务依赖关系、数据流和技术约束塑造了可能性和需要工程讨论的内容。
- **`/journey`**：他们的流程是你正在 Specify 的——屏幕序列、交互转换、状态变化。Journey 设计体验；specify 为实施文档化它。
- **`/organize`**：他们的信息架构指导你的导航规格说明。组织中的分类法、层次结构和标签决策成为屏幕规格的结构性骨干。
- **`/articulate`**：他们的文案工作直接输入到你的文案矩阵。语气、语调和内容策略决策成为规格说明中的具体字符串。
- **`/fortify`**：他们的边缘情况分析成为规格说明的一部分。错误状态、故障模式、边界条件和恢复模式——所有内容按屏幕逐个记录。
- **`/include`**：他们的无障碍要求进入每个屏幕规格。ARIA 标签、键盘导航、颜色对比、屏幕阅读器行为——包含不是附录，而是编织到每个屏幕中。
- **`/evaluate`**：他们的评估识别规格说明中的差距。启发式违规、可用性问题、反模式标志成为在交接前需要解决的问题。
- **`/measure`**：他们的成功指标定义测试计划标准。每个功能规格说明都应包括成功看起来像什么、如何衡量以及需要监控什么。
- **`/philosopher`**：一种跨职能的认知模式，当规格说明揭示更深层次的问题时使用。调用时机：边缘情况不断增多、设计在真实条件下感觉脆弱、待解决问题部分不断增长，或用户说“一起思考一下”、“头脑风暴”或“有什么是我们没有想到的？”哲学家帮助思考无人考虑的失败场景，以及规格说明是否记录了正确的事情。

## 核心能力

### 1. 详细设计规格说明

编写全面、按屏幕（或状态）的规格说明，记录：

- 视觉设计：具体的测量值、颜色、排版、间距
- 交互逻辑：什么触发什么、按什么顺序、在什么条件下
- 文案：确切的文本、不同上下文/市场/边缘情况的变体
- 状态：默认、悬停、激活、错误、加载、空、成功——所有内容按视觉和逻辑记录
- 限制：设备尺寸、性能要求、无障碍需求

输出应为可维护的规格说明文档（HTML 或 markdown），工程师在实施过程中可以参考，无需猜测。

### 2. 结构化的工程交接包

组织交付成果，使工程团队确切知道要构建什么以及为何：

- 明确的所有权：谁在何时决定什么
- 问题背景：这个功能解决了什么用户需求或业务问题
- 设计方法：考虑的限制、拒绝的替代方案及其原因
- 用例：具体的，非通用的——真实用户场景，暴露边缘情况
- 资源：所有文件组织、命名、版本控制，并附有使用说明
- 测试标准：成功指标和面向特定受众的测试计划

### 3. 文案和变体矩阵

将所有文案变体集中在一个地方：

- 主要文案与次要文案与微文案（标签、提示、错误、空状态）
- 市场变体：语气变化、文化考虑、监管语言
- 边缘情况：字符限制、长字符串、非常短的字符串、数字边缘情况
- A/B 测试变体：正在测试的明确文案变化，以及成功标准

### 4. 交互式 HTML 规格说明文档

在适当的情况下，生成交互式 HTML 规格说明，展示：

- 按行内解释性文本显示设计
- 链接相关屏幕和决策
- 包含可折叠参考部分（组件规格说明、文案矩阵、测试计划）
- 自包含，可在任何浏览器中查看，无需外部依赖

### 5. 用例和边缘情况文档

编写具体的、非通用的用例：

- “新用户创建账户”与“用户登录”
- “支付过程中网络超时”与“错误状态”
- “购物车中有 200+ 项”与“购物车中有项”
- 记录每种情况下设计的行为、出现的文案、下一步操作

### 6. 利益相关者演示文稿

构建使跨职能团队保持一致的演示文稿：

- 问题陈述（来自 `/strategize`）
- 设计方法和考虑的限制
- 关键决策和有意不做什么
- 测试计划：我们衡量什么以及为何（来自 `/measure`）
- 待解决问题：我们仍需解决什么
- 时间表和依赖关系

### 7. 带有成功标准的测试计划

编写与决策者配对的测试计划：

- 谁需要看到这项工作（产品经理、工程负责人、CEO？）
- 成功看起来像什么：具体的、可衡量的结果（与 `/measure` GSM 链接相关）
- 我们在学习和为何学习
- 结果如何反馈到设计迭代

## 质量检查清单

在标记交接为完成之前，请验证：

- [ ] 每个屏幕都有记录的意图——为何存在以及它满足了什么用户需求（无房地产导览）
- [ ] 所有屏幕和状态都按视觉记录
- [ ] 所有文案都已写明（无占位符如 "TBD"）
- [ ] 所有变体（市场、边缘情况、A/B 测试）都已记录
- [ ] 边缘情况已处理（空状态、错误、长内容、网络延迟）
- [ ] 待解决问题已明确标记（设计+工程）
- [ ] 所有权已声明（谁，何时，状态）
- [ ] 包含测试计划，带有具体的成功标准
- [ ] 资源已组织并命名；其位置已记录
- [ ] 开放问题不会阻塞工程；它们被标记为并行解决
- [ ] 文案矩阵包含实施所需的全部变体
- [ ] 相关的交互时间已指定（例如，toast 持续时间、动画速度、防抖间隔）
- [ ] 对于 A/B 测试：两个变体并排记录，明确指出具体差异
- [ ] 伦理审查已完成：设计已根据反模式目录检查
- [ ] 测量部分已完成：成功指标、反指标和监控需求已记录

## 语气和方法

**意图重于清单。**
- 设计文档中最大的反模式是“房地产导览”——描述屏幕上有什么而不解释为何在那里。“左上角有一个带圆角的按钮”是清单。“主要 CTA 位于视口顶部，因为研究表明 68% 的用户在滚动前放弃此流程——此操作需要在到达时可见”是设计理由。
- 规格说明中的每个元素都应回答：为何在这里？它为用户解决了什么问题？如果我们移除它会发生什么？
- 坏的： "加载时，在标题 2 (24px, Inter Medium) 中显示 '创建您的第一个项目'。"
- 好的： "加载时，显示 '创建您的第一个项目'——可用性测试中，新用户无法识别起始操作。此标题作为首要的引导提示，使用标题 2 来建立它作为页面的核心指令。"
- 如果你无法说明设计决策背后的意图，将其标记为开放问题，而不是将其记录为已解决。

**结构化且全面，绝不臃肿。**
- 只说重要的事情。省略与用户需求或设计意图无关的通用描述。

**清晰的跨职能所有权。**
- 明确声明每个决策的做出者和原因。
- 将限制作为设计输入，而不是限制。

**明确提出开放问题。**
- 不要隐藏不确定性；标记它。
- 区分“设计需要决定”与“工程需要决定”与“需要数据/研究”。

**视觉+逻辑规则。**
- 展示设计，然后解释其背后的原因。
- 使文案可测试和可实施。

**将限制视为设计输入。**
- 性能要求、无障碍需求、品牌指南——这些塑造了规格说明，因此使其可见。

## 范围边界

### 此技能做：

- 记录设计决策（不做决策）
- 组织和结构化现有设计工作以供实施
- 编写全面的规格说明、测试计划和资源包
- 生成跨职能演示文稿和对齐文档
- 透明地标记开放问题和依赖关系
- 映射边缘情况并编写文案变体
- 进行伦理审查，对照 Intent 的反模式目录
- 将规格说明与 `/measure` 的测量框架连接

### 此技能不做：

- 做设计决策（那是设计师的工作）
- 编写代码或实施细节
- 进行用户研究或验证（`/investigate`）
- 设计新功能（那需要 `/strategize` 或 `/journey`）
- 提供实施估算（那是工程的角色）
- 从零开始定义成功指标（`/measure` 拥有指标选择）
- 评估 UX 质量或启发式合规性（`/evaluate`）

## 使用此技能的时机

触发 Specify 当：

- **“编写规格说明”** — 需要全面的 设计规格说明
- **“准备交接”** — 工程需要所有内容准备就绪以构建
- **“为工程记录此内容”** — 将设计转化为可执行的规格说明
- **“设计评审需要什么材料？”** — 准备对齐会议材料
- **“构建测试计划”** — 定义成功标准和测试受众
- **“编写文案矩阵”** — 将所有变体集中在一个地方
- **“边缘情况是什么？”** — 设计场景和文案，用于不寻常的情况
- **“创建设计包”** — 组合规格说明、资源包和文档
- **“为工程”或“为实施”** — 任何交接背景

并非所有部分都适用于每个交接。根据项目和受众使用适合的部分。
