# 平台：GitHub

GitHub指南用于寄生虫SEO、GEO（AI引用）和精选列表创建。GitHub是一个二级技术权威平台——域名权威高、索引速度快、AI引用概率非常高。用于存储库、README、GitHub Pages、gists和Awesome风格的导航列表。

**调用时**：在**首次使用**时，如果有帮助，先用1-2句话说明这项技能涵盖的内容及其重要性，然后提供主要输出。在**后续使用**或当用户要求跳过时，直接进入主要输出。

## 为什么选择GitHub进行SEO

| 因素 | 影响 |
|------|------|
| **域名权威** | 高DA；存储库、gists、Pages排名良好 |
| **快速索引** | 搜索引擎频繁抓取GitHub |
| **AI引用** | ChatGPT、Perplexity在技术查询中引用GitHub；在GEO框架中为二级 |
| **技术专长** | 强大的专长信号；结构化文档成为AI参考材料 |
| **跨平台** | 跨Dev.to、Stack Overflow、论坛分享；扩大可见性 |

## 应用场景

| 应用场景 | 格式 | 目的 |
|----------|------|---------|
| **寄生虫SEO** | 存储库、README、Pages、gists | 利用GitHub权威进行排名和反向链接 |
| **GEO** | 文档、教程、精选列表 | AI工具在技术答案中引用GitHub |
| **精选/导航列表** | Awesome风格的存储库 | 主题资源目录；反向链接、发现 |

## 表面：个人资料与存储库

| 表面 | 它是什么 | 优化重点 |
|---------|------------|---------------------|
| **个人资料README** | 同用户名命名的公共存储库；根`README.md`在个人资料上渲染 | 个人品牌、旗舰链接、社交证明 |
| **置顶** | 个人资料上最多**6**个存储库或gists | 展示顶级项目；与实体信号（**entity-seo**）保持一致 |
| **每个存储库README** | 每个存储库的**代码**选项卡上的根`README.md` | 产品着陆页；安装、证明、CTA |

更改普通存储库README不会更改个人资料横幅，除非该内容是**个人资料README**存储库或从它链接。

### 个人资料README (`username/username`)

**不等于产品存储库README。** 优化**身份+导航**，在约15-40行的渲染内容中，除非用户明确要求长篇简历。官方设置：[管理您的个人资料README](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-github-profile/customizing-your-profile/managing-your-profile-readme)。

| 原则 | 做 | 避免 |
|-----------|-----|--------|
| **长度** | 短、可扫描的章节；**省略目录**，除非文件确实很长 | 应用“产品存储库典型500-1500字”在这里 |
| **标题** | `###`块（例如*我做什么·开源·找到我*）用于快速浏览 | 许多嵌套`##` + 长篇叙述没有中断 |
| **链接** | 每个主要URL在**找到我/连接**行中**一次**（或徽章**或**瘦表格——不是所有三个都重复相同的目的地） | 在徽章、表格和散文中重复网站/LinkedIn/电子邮件 |
| **存储库块** | **粗体存储库名称** + **≤2**短行 + 最多**一个**复制粘贴命令（例如`npx skills add …`）——使用流行个人资料的“旗舰OSS”扫描模式，无需克隆存储库的完整README | 完整的功能矩阵、变更日志或安装文档粘贴到个人资料文件 |
| **布局** | 可选**居中**标题（`<div align="center">`）仅用于**姓名+标语+徽章**；正文保持左对齐Markdown以提高可读性 | 居中缠绕整个README |
| **可选小部件** | 紧凑的Shields（平面样式）；可选[github-readme-stats](https://github.com/anuraghazra/github-readme-stats) / [star-history](https://star-history.com) — **第三方**，视为**转换/社交证明**，不是核心SEO | 当文本中重复相同的CTA时，显示`for-the-badge`徽章墙 |

**最小轮廓（典型个人资料）：**

1. 标题 + 首先回答的标语（+ 瘦徽章行）。
2. `### 我做什么` — 身份、证明链接（**不**重复后面相同的URL）。
3. `### 开源` — 粗体存储库链接 + 提案 + 可选一个代码分隔符。
4. `### 找到我` — 单行去重的链接（网站 · 传记 · 案例 · 社交 · 电子邮件）。
5. `### 活动`（可选）— 小**github-readme-stats** + **star-history**；`<img>`上的**替代文本**。

参考模式（高信号、低噪音）：扫描优先的个人资料，例如[alchaincyf](https://github.com/alchaincyf) — 短`###`块，粗体产品/存储库名称，一个“找到我”集群。

**实体信号**：清晰的项目名称、作者、维护者；一致的标识。见**entity-seo**。

### 个人资料README清单（短）

- [ ] H1 + **一个**首先回答的标语（关键词：角色、技术栈、领域）
- [ ] 官方**外部**链接（网站、社交、电子邮件）**去重**
- [ ] **置顶**存储库（≤6）与README中讲述的故事相匹配
- [ ] 可选：**活动**部分 — 在一个标题下分组统计/星标历史，而不是分散小部件
- [ ] **最后更新**脚注以保持新鲜度（GEO信号）

## 存储库主页：布局地图

| 区域 | 典型内容 | SEO/操作笔记 |
|------|------------------|----------------|
| **主列** | 文件列表；渲染的**根README**在下方 | 第一个屏幕和H2/H3承载大部分叙述 |
| **关于侧边栏** | **描述**、**网站**、**主题**、发布快捷方式、许可证、语言 | 保持描述和README第一段一致；**网站**应与主要外部CTA匹配 |
| **其他选项卡** | 问题、PR、操作等。 | 参与度和新鲜度信号 |

**网站字段**：通过存储库**设置**/**关于**编辑维护；优先考虑与README链接一致的规范文档或产品URL。

## 站内发现（高级别）

| 条目 | 角色 | 注意事项 |
|-------|------|--------|
| **趋势** | 时间窗口内的可见性 | 公式**不**公开；永远不要承诺排名 |
| **探索** | 集合、主题、计划 | 对于模式和季节性活动很有用 |
| **主题** | 与存储库主题绑定的主题页面 | 与主题元数据（见下文主题部分）一致 |
| **搜索** | 跨存储库和用户查询 | README + 关于 + 主题驱动匹配质量 |

UI和URL随时间演变；在[github.com](https://github.com/)上验证。

## 存储库名称、关于和README（SEO/GEO优先级）

**排名权重**（GitHub + Google）：存储库名称 & 关于 ≈ 最高；主题 ≈ 高；README ≈ 高。

### 存储库名称

| 实践 | 指南 |
|----------|-----------|
| **描述性** | 暗示项目做什么 |
| **关键词丰富** | 包含主要关键词（`markdown-editor`而不是`my-project`） |
| **连字符** | 分隔单词（`react-component-library`） |
| **简洁** | 较短 = 易于记忆、可分享 |

### 关于部分（描述）

| 限制 | 指南 |
|----------|-----------|
| **350个字符** | 硬限制；GitHub强制执行 |
| **~128个字符** | 最佳简洁性；通常完全显示 |
| **内容** | 主要关键词 + 自然变化；它做什么，为谁；如果空间允许，链接到网站或文档 |

**示例**： "一个快速、轻量级的Markdown编辑器，用于React，具有实时预览、语法高亮和导出到PDF。使用TypeScript构建。"

### 主题

| 限制 | 指南 |
|----------|-----------|
| **6-20个主题** | 最大20个；6-10个推荐 |
| **~50个字符**每个 | 每个主题 |
| **格式** | 小写、连字符、数字 |
| **混合** | 技术（react、python）、目的（cli、库）、类别（seo、ai-tools）、社区（hacktoberfest） |

**未充分利用**但非常有效的发现性和GEO。

### README结构和组件

针对**存储库（项目）README**，除非另有说明。**个人资料README**覆盖：较短，较少部分——见**个人资料README (`username/username`)** 以上。

| 部分 | 目的 | SEO/GEO |
|---------|---------|---------|
| **标题 + 标语** | H1 + 1-2句摘要；第一段包含关键词 | 关键；前100个字加权 |
| **目录** | 链接到H2/H3；**用于长存储库README**（通常>500字）。**通常在个人资料README上跳过** | 导航；可爬性 |
| **安装/快速入门** | 前提条件；确切命令；准备好复制粘贴 | 用例清晰 |
| **使用示例** | 代码块；常见场景 | 可引用；可提取 |
| **截图/GIF** | 演示、输出；需要替代文本 | 参与度；可访问性 |
| **徽章** | 构建、版本、许可证 | 信任信号 |
| **贡献** | 链接到CONTRIBUTING.md | 社区信号 |
| **许可证** | 链接到LICENSE | 完整性 |

**字数**：没有硬限制；**500-1500字**典型用于**产品/库**存储库。首先提供价值；稍后扩展。**个人资料README**：优先考虑**密集简洁**——长篇属于规范网站或在置顶存储库自己的README中。

### README GEO / AI引用

| 实践 | 指南 |
|----------|-----------|
| **首先回答** | 在前1-2句中直接回答（40-60字）；**个人资料README**可以压缩到**H1下一条响亮的标语**，如果外部链接承载其余部分 |
| **短段落** | 最大2-3句；可提取的清晰度 |
| **问题式标题** | H2/H3作为问题，在相关的地方（**存储库README**）；在**个人资料README**中，可选——**部分的清晰度**比问题措辞更重要 |
| **数据包含** | 统计、数字；引用内容约40%更可能包含数据 |
| **新鲜度** | 定期更新；~76%的引用内容在30天内更新 |

**实体信号**：清晰的项目名称、作者、维护者；一致的标识。见**entity-seo**。

### README清单——**存储库（默认）**

- [ ] 项目标题带关键词
- [ ] 第一段简洁描述
- [ ] H2/H3结构；图像的替代文本
- [ ] 安装+使用示例
- [ ] 截图或演示
- [ ] 徽章；贡献；许可证
- [ ] 内部链接到相关文档/存储库
- [ ] 6-20个主题在存储库

*(对于**个人资料** `username/username`，使用较短的**个人资料README清单**——以上每一行都不适用。)*

## GitHub上的寄生虫SEO

### 关键表面

| 表面 | 使用 |
|---------|-----|
| **README** | 存储库的着陆页；关键词优化的摘要、标题、链接 |
| **GitHub Pages** | 静态网站；博客、FAQ、文档；额外的排名机会 |
| **Gists** | 微内容；长尾关键词；链接到存储库或外部资源 |
| **Wiki** | 关键词丰富的文档 |
| **问题** | 问答、讨论；可索引 |

### GitHub Pages与README

| 表面 | 角色 |
|---------|------|
| **README** | 第一印象；星标/分支；简短提案和深度链接 |
| **Pages** | 多页**静态**网站：长文档、博客、变更日志 |

**默认URL模式**：用户或组织网站通常使用`username.github.io`存储库，并在`https://username.github.io`上提供。项目网站是从给定存储库发布的，通常出现在`https://username.github.io/repository/`（路径可能因设置而异）。见[关于GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages)。

**限制**：构建大小、带宽和构建频率限制随时间变化——当用户需要数字时，引用[GitHub Pages限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)，而不是这个技能的硬编码数字。

### 优化

| 元素 | 实践 |
|---------|----------|
| **存储库标题** | 主要关键词；描述性；连字符 |
| **关于** | 350个字符最大；关键词丰富；主要关键词+自然变化 |
| **描述** | 次要关键词；链接到网站或资源 |
| **README** | 关键词优化的摘要首先；标题、项目符号；截图；链接到文档、教程 |
| **主题/标签** | 6-20个相关主题；每个50个字符 |
| **GitHub Pages** | 移动友好；元数据；博客/FAQ以获得额外关键词 |

### Gists用于微内容

- 针对特定长尾关键词
- 链接到更大的存储库或外部资源
- 分享代码片段、小工具

### 社区参与

- 回应问题和PR；建立信任
- 为热门项目做贡献；反向链接、可见性
- 保持存储库更新；过时 = 较低可信度

## GitHub上的GEO

| 因素 | 实践 |
|--------|----------|
| **README清晰度** | 清晰、可引用的段落；直接答案 |
| **文档** | 结构化；AI工具解析良好 |
| **实体信号** | 清晰的项目、作者身份；见**entity-seo** |
| **一致性** | 积极维护；参与（星标、分支、观察者） |

## 存储库原型

| 原型 | 意图 | 首屏重点 |
|-----------|--------|------------------------|
| **产品/库** | 可安装的软件、SDK、CLI、服务 | 安装、快速入门、证明（CI、许可证）、支持路径 |
| **精选/资源** | Awesome风格的列表、索引 | 范围、策展条、贡献规则 |
| **个人资料中心** | 个人资料上公共**`username/username`** README | 身份+官方链接+**置顶**旗舰存储库；**不**重复完整产品README |

匹配指标到类型：精选列表优化信任和反向链接；产品存储库优化采用和问题质量。

## 精选/导航列表（Awesome风格）

**Awesome列表** = GitHub上的精选、主题特定资源列表。功能类似于导航目录；高流量、反向链接、发现。 sindresorhus/awesome（441K+星标）是主列表；6,500多个精选列表存在于各个主题中。

### 按类别示例

| 类别 | 示例 |
|----------|----------|
| **主列表** | sindresorhus/awesome — 所有awesome列表的中心 |
| **SEO/营销** | awesome-seo, awesome-ai-seo, bmpi-dev/awesome-seo |
| **AI/ML** | awesome-ai-tools, AITreasureBox, awesome-ai |
| **开发工具** | awesome-tools, awesome-cli, awesome-nodejs |
| **语言** | awesome-python, awesome-javascript, awesome-go |
| **前端/后端** | awesome-react, awesome-vue, awesome-django |
| **其他** | awesome-security, awesome-gaming, awesome-databases |

### 创建时机

- 您有一个具有许多高质量资源可以策展的领域
- 现有列表缺乏您主题的覆盖
- 您想获得反向链接资产和主题权威

### 列表结构（sindresorhus/awesome指南）

| 元素 | 实践 |
|---------|----------|
| **标题** | 清晰、专注（例如，"Awesome SEO"、"Awesome AI Tools"） |
| **描述** | 简洁；范围清晰 |
| **部分** | 分类（例如，教程、工具、文章） |
| **项目** | 策展，不是收集；只包括您推荐的内容 |
| **项目格式** | `- [名称](URL) - 简要描述为什么它很棒` |
| **许可证** | CC0或类似 |
| **贡献** | contributing.md用于PR流程 |

### 被列入与创建

| 行动 | 使用 |
|--------|-----|
| **提交到现有列表** | PR到awesome-*存储库；遵循列表格式；联系维护者 |
| **创建新列表** | 当您的细分领域不存在列表时；遵循awesome指南 |
| **列表之间链接** | 链接到其他覆盖主题更好的awesome列表 |

### 发现

- **sindresorhus/awesome** — awesome列表的主列表
- **AwesomeSearch** — 跨awesome列表搜索
- **more-awesome** — awesome列表目录

## 常见错误

| 错误 | 避免 |
|---------|-------|
| **忽视参与** | 不回应问题/PR会降低信任 |
| **不规则更新** | 过时的存储库表示不活跃 |
| **不完整的文档** | 缺乏清晰的描述会让用户感到沮丧 |
| **通用标题** | 缺少关键词会降低可发现性 |
| **薄弱的awesome列表** | 低质量或未策展的项目会损害信誉 |
| **个人资料README = 产品README** | 将安装/贡献/截图密集的模板粘贴到`username/username`——使用**个人资料**清单 |
| **个人资料上的链接蔓延** | 相同的网站/LinkedIn/电子邮件在徽章、表格和长文本中重复——整合 |

## 输出格式

- **用例**（寄生虫SEO / GEO / 精选列表）
- **表面范围**（个人资料与特定存储库；README与Pages）
- **存储库名称、关于、主题**（如果优化元数据）
- **表面**（README、Pages、gist、awesome存储库）
- **README结构**（部分、字数、GEO实践（如果适用））——**如果个人资料README**，引用**短**轮廓+去重链接+可选小部件按**个人资料README**部分以上
- **优化**（关键词、结构、链接）
- **可立即使用的**副本或结构，如果适用
