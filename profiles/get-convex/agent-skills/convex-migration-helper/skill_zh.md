# 凸显迁移助手

在执行破坏性变更时，安全迁移凸显模式和数据。

## 使用场景

- 向现有表添加新的必填字段
- 修改字段类型或结构
- 分割或合并表
- 重命名或删除字段
- 从嵌套数据迁移到关系型数据

## 不适用场景

- 绿地模式，生产环境或开发环境中无现有数据
- 添加无需回填的可选字段
- 添加无现有数据需迁移的新表
- 添加或删除无正确性问题的索引
- 无需迁移的凸显模式设计问题

## 核心概念

### 模式验证驱动工作流

凸显不会允许部署与静态数据不匹配的方案。
这是塑造每次迁移的基本约束：

- 如果现有文档不存在该字段，则不能添加必填字段
- 如果现有文档具有旧类型，则不能修改字段类型
- 如果现有文档仍包含该字段，则不能从方案中删除字段

这意味着迁移遵循可预测的模式：**扩展方案，迁移数据，收缩方案**。

### 在线迁移

凸显迁移在线运行，这意味着应用程序在数据异步批量更新时继续处理请求。
在迁移窗口期间，您的代码必须处理旧和新两种数据格式。

### 优先添加新字段而非修改类型

在修改数据形状时，创建新字段而不是修改现有字段。
这使过渡更安全，更容易回滚。

### 不要删除数据

除非您确定，否则优先将字段标记为弃用，而不是删除。
将字段标记为 `v.optional` 并添加代码注释，说明其已弃用及其存在的原因。

## 安全变更（无需迁移）

### 添加可选字段

```typescript
// 之前
users: defineTable({
  name: v.string(),
});

// 之后 - 安全，新字段为可选
users: defineTable({
  name: v.string(),
  bio: v.optional(v.string()),
});
```

### 添加新表

```typescript
posts: defineTable({
  userId: v.id("users"),
  title: v.string(),
}).index("by_user", ["userId"]);
```

### 添加索引

```typescript
users: defineTable({
  name: v.string(),
  email: v.string(),
}).index("by_email", ["email"]);
```

## 破坏性变更：部署工作流

每个破坏性迁移都遵循相同的多部署模式：

**部署 1 - 扩展方案：**

1. 更新方案以允许旧格式和新格式（例如，添加可选新字段）
2. 更新代码以在读取时处理两种格式
3. 更新代码以对新文档写入新格式
4. 部署

**部署之间 - 迁移数据：**

5. 运行迁移以回填现有文档
6. 验证所有文档已迁移

**部署 2 - 收缩方案：**

7. 更新方案仅要求新格式
8. 删除处理旧格式的代码
9. 部署

## 使用迁移组件

对于任何非平凡的迁移，使用
[`@convex-dev/migrations`](https://www.convex.dev/components/migrations)
组件。它处理批量处理、基于游标的分页、状态跟踪、从失败中恢复、干运行和进度监控。

参考 `references/migrations-component.md` 了解安装、设置、直接使用 `npx convex run migrations:myMigration` 定义和运行迁移、干运行、状态监控和配置选项。

## 常见迁移模式

参考 `references/migration-patterns.md` 了解完整模式及代码示例，涵盖：

- 添加必填字段
- 删除字段
- 修改字段类型
- 将嵌套数据分割到单独表
- 清理孤儿文档
- 零停机策略（双重写入、双重读取）
- 小表快捷方式（无组件的单个内部Mutation）
- 验证迁移是否完成

## 常见陷阱

1. **在迁移数据前将字段设为必填**：凸显会拒绝部署，因为现有文档缺少该字段。
   始终先扩展方案。
2. **在大型表上使用 `.collect()`**：触发事务限制或超时。使用迁移组件进行正确的批量分页。
   `.collect()` 仅适用于您知道是小型表的场景。
3. **在迁移前未写入新格式**：迁移窗口期间创建的文档将被遗漏，导致迁移“完成”后仍有未迁移数据。
4. **跳过干运行**：使用 `dryRun: true` 在提交生产数据更改前验证迁移逻辑。
   在真实文档接触前捕获错误。
5. **过早删除字段**：优先使用 `v.optional` 标记弃用并添加注释。
   仅在确定数据不再需要且无代码引用时删除。
6. **使用cron进行迁移批量处理**：迁移组件通过内部递归调度处理批量处理。
   cron需要手动清理和额外部署以删除。
