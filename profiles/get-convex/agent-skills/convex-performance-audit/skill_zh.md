# Convex 性能审计

逐个问题类别诊断和修复 Convex 应用中的性能问题。

## 使用场景

- Convex 页面或功能感觉缓慢或昂贵
- `npx convex insights --details` 报告读取字节数、读取文档数或 OCC 冲突高
- 低新鲜度读取路径使用响应式功能，而点时读取即可
- OCC 冲突错误或过多的 mutation 重试
- 订阅数量高或 UI 更新缓慢
- 函数接近执行或事务限制
- 同级函数存在相同的性能模式需要修复

## 不适用场景

- 初始 Convex 设置、认证设置或组件提取
- 没有性能目标的纯模式迁移
- 没有用户可见或部署可见问题的单次微优化

## 指导原则

- 当规模较小、流量适中或可用信号较弱时，优先使用更简单的代码
- 除非有明确测量信号、无界路径或已知的热读取/写入路径，否则不建议推荐摘要表、文档拆分、获取策略更改或迁移密集型发布
- 在 Convex 中，对小型表进行简单扫描通常是可接受的。不要因为模式在大规模下不理想就发明结构性工作

## 第一步：收集信号

从可用的最强信号开始：

1. 如果部署健康洞察已从用户或当前上下文提供，将其视为性能信号的一流来源
2. 如果 CLI 洞察可用，运行 `npx convex insights --details`。在需要时使用 `--prod`、`--preview-name` 或 `--deployment-name`。
   - 如果本地仓库的 Convex CLI 版本太旧不支持 `insights`，在放弃之前尝试 `npx -y convex@latest insights --details`。
3. 如果仓库已使用 `convex-doctor`，您可以将其发现视为提示。不要要求它，也不要将其视为事实依据
4. 如果运行时信号不可用，无论如何从代码进行审计，但请记住上述指导原则。缺乏洞察不是健康的证明，但它也不是大规模重构的证明。

## 信号路由

收集信号后，识别问题类别并阅读匹配的参考文件。

| 信号                                                         | 参考                                 |
| -------------------------------------------------------------- | ----------------------------------------- |
| 高读取字节数或文档数、JS 过滤、不必要的连接  | `references/hot-path-rules.md`            |
| OCC 冲突错误、写入争用、mutation 重试        | `references/occ-conflicts.md`             |
| 高订阅数量、慢 UI 更新、过度重新渲染 | `references/subscription-cost.md`         |
| 函数超时、事务大小错误、大有效负载     | `references/function-budget.md`           |
| 没有具体信号的“它很慢” | 从 `references/hot-path-rules.md` 开始 |

多个问题类别可能重叠。首先阅读最相关的参考，如果症状仍然存在，则检查其他参考。

## 升级较大修复

如果可能的修复是侵入性的、跨领域的或迁移密集型的，请在编辑前停止并呈现选项。

示例：

- 在多个流程中引入摘要或汇总表
- 拆分文档以隔离经常更新的字段
- 跨多个屏幕重做分页或获取策略
- 切换到需要迁移安全发布的新的索引或反规范化字段

当正确性取决于在发布过程中处理旧状态和新状态时，请咨询 `convex-migration-helper` 技能的迁移工作流程。

## 工作流程

### 1. 确定问题范围

从实际项目中挑选一个具体的用户流程。查看代码库、客户端页面和 API 表面，找到与症状匹配的流程。

记录：

- 入口函数
- 使用 `useQuery`、`usePaginatedQuery` 或 `useMutation` 的客户端调用点
- 读取的表
- 写入的表
- 路径是高读取、高写入还是两者兼有

### 2. 追踪完整的读取和写入集

对于路径中的每个函数：

1. 追踪每个 `ctx.db.get()` 和 `ctx.db.query()`
2. 追踪每个 `ctx.db.patch()`、`ctx.db.replace()` 和 `ctx.db.insert()`
3. 注意外键查找、JS 端过滤和完整文档读取
4. 识别所有触摸相同表的兄弟函数
5. 识别在同一页上渲染的响应式统计信息、聚合或小部件

在 Convex 中，每个额外的读取都会增加事务工作，每个写入都可能使响应式订阅者失效。将读取放大和失效放大视为一级问题。

### 3. 应用相关参考的修复

阅读与您的问题类别匹配的参考文件。每个参考包括特定的模式、代码示例和推荐的修复顺序。

不要停留在洞察命名的单个函数上。追踪触摸相同表的兄弟读取者和写入者。

### 4. 一起修复兄弟函数

当一个触摸表的函数存在性能错误时，审计具有相同模式的兄弟函数。

找到一个问题后，检查相同表族的兄弟读取者和兄弟写入者，包括伴随的摘要或汇总表。

示例：

- 如果一个列表查询从完整文档切换到摘要表，请检查该表的 其他列表查询
- 如果一个 mutation 隔离了经常更新的字段或拆分了热文档，请检查写入相同表的 其他写入者
- 如果一个读取路径需要对未填充的字段进行迁移安全的发布，请检查具有相同发布风险的兄弟读取

除非有明确的产品原因，否则不要将一个路径修复并保留另一个路径在旧模式上。

### 5. 完成前验证

确认所有这些：

1. 结果与之前相同，没有丢失记录
2. 预期不再路径中的消除读取或写入
3. 当反规范化或索引字段缺失时，回退行为正常工作
4. 需要时，经常更新的字段与广泛读取的文档隔离
5. 检查了所有相关的兄弟读取者和写入者，而不仅仅是原始函数

## 参考文件

- `references/hot-path-rules.md` - 读取放大、失效、反规范化、索引、摘要表

- `references/subscription-cost.md` - 响应式查询成本、订阅粒度、点时读取
