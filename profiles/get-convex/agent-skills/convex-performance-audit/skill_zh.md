# Convex 性能审计

针对 Convex 应用中的性能问题进行诊断与修复，逐一解决不同的问题类别。

## 何时使用

- Convex 页面或功能感觉迟缓或成本过高
- `npx convex insights --details` 报告高字节读取、文档读取或 OCC 冲突
- 低时效性读取路径在点查本可满足的场景中使用了响应式机制
- OCC 冲突错误或过度的变更重试
- 订阅数量过高或 UI 更新缓慢
- 函数接近执行或事务限制
- 同一性能模式需在同级函数中一并修复

## 何时不使用

- 初始 Convex 配置、认证配置或组件提取
- 纯模式迁移且无性能目标
- 未发现用户可见或部署可见问题的单次微优化

## 防护准则

- 在规模较小、流量适中或可用信号较弱时，优先采用更简单的代码
- 除非存在可量化的信号、明确无界路径或已知的热读取/写入路径，否则不推荐使用摘要表、文档拆分、获取策略变更或以迁移为主的部署
- 在 Convex 中，对小型表进行简单扫描通常是可接受的。不要仅因某模式在大规模下不理想就凭空增加结构性工作

## 第一步：收集信号

从可用的最强信号入手：

1. 如果用户或当前上下文已提供部署健康（Health）洞察，将其视为一级性能信号来源。
2. 如果可用 CLI 洞察，运行 `npx convex insights --details`。按需使用 `--prod`、`--preview-name` 或 `--deployment-name`。
   - 如果本地仓库的 Convex CLI 版本过低，不支持 `insights`，则在放弃前尝试 `npx -y convex@latest insights --details`。
3. 如果仓库已使用 `convex-doctor`，可将其发现结果视为提示。无需强制使用，也不应将其视为事实来源。
4. 如果运行时信号不可用，仍可从代码层面进行审计，但需牢记上述防护准则。缺乏洞察并非健康的证明，但也并非必须开展大规模重构的证明。

## 信号路由

收集信号后，识别问题类别并阅读对应的参考文件。

| 信号                                                         | 参考文件                                 |
| -------------------------------------------------------------- | ----------------------------------------- |
| 高字节读取或文档读取、JS 过滤、不必要的连接（joins）           | `references/hot-path-rules.md`            |
| OCC 冲突错误、写入竞争、变更重试                                  | `references/occ-conflicts.md`             |
| 订阅数量过高、UI 更新缓慢、过度重渲染                              | `references/subscription-cost.md`         |
| 函数超时、事务大小错误、大载荷                                     | `references/function-budget.md`           |
| 通用“执行缓慢”且无特定信号                                      | 从 `references/hot-path-rules.md` 开始   |

多种问题类别可能存在重叠。先阅读最相关的参考文件，若症状依然存在，再查阅其他文件。

## 升级并处理更大的修复方案

若预期的修复可能具有侵入性、跨领域影响或以迁移为主的，应在编辑前停止，先提供方案选项。

示例：

- 在多个流程中引入摘要或汇总表
- 拆分文档以隔离高频更新的字段
- 在多个屏幕中重构分页或获取策略
- 切换至需要安全迁移部署的新索引或反范式字段

若在部署过程中正确性取决于处理新旧状态，请咨询 `convex-migration-helper` 技能的迁移流程。

## 工作流程

### 1. 界定问题范围

从实际项目中挑选一个具体的用户流程，分析代码库、客户端页面与 API 接口，找到与症状相匹配的流程。

记录以下内容：

- 入口函数
- 使用 `useQuery`、`usePaginatedQuery` 或 `useMutation` 的客户端调用点
- 读取的表
- 写入的表
- 该路径是高读取、高写入，还是两者兼有

### 2. 追踪完整的读写集合

针对路径中的每个函数：

1. 追踪每个 `ctx.db.get()` 和 `ctx.db.query()`
2. 追踪每个 `ctx.db.patch()`、`ctx.db.replace()` 和 `ctx.db.insert()`
3. 记录外键查询、JS 端过滤及全文档读取
4. 识别所有操作相同表的同级函数
5. 识别同一页面渲染的响应式统计、聚合或组件（widgets）

在 Convex 中，每多一次读取都会增加事务工作量，每次写入都可能使响应式订阅者失效。将读取放大与失效放大视为一级问题。

### 3. 应用相关参考文件中的修复方案

阅读与您问题类别匹配的参考文件。每个参考文件均包含具体模式、代码示例与推荐的修复顺序。

不要止步于洞察中指出的单一函数。追踪所有操作相同表的同级读取者与写入者。

### 4. 一并修复同级函数

当某个涉及某张表的函数存在性能问题时，需审计同级函数是否存在相同模式。

发现一个问题后，需检查该表家族的所有同级读取者与写入者，包括配套的摘要或汇总表。

示例：

- 若某个列表查询从全文档切换至摘要表，需检查该表的其它列表查询
- 若某个变更隔离了高频更新字段或拆分了热点文档，需检查写入同一张表的其它变更
- 若某条读取路径需对未回填字段进行安全迁移部署，需检查同级读取以排查相同部署风险

除非有明确的业务原因，否则不应只修复某条路径，而让另一条路径仍保留旧模式。

### 5. 完成前验证

确认以下所有事项：

1. 结果与之前一致，无记录丢失
2. 已消除的读取或写入不再出现在预期的路径中
3. 当反范式字段或索引字段缺失时，回退行为正常
4. 在需要时，将高频更新字段与广泛读取的文档隔离
5. 所有相关的同级读取者与写入者均已检查，并非仅检查原始函数

## 参考文件

- `references/hot-path-rules.md` - 读取放大、失效、反范式化、索引、摘要表
- `references/occ-conflicts.md` - 写入竞争、OCC 解决、热点文档拆分
- `references/subscription-cost.md` - 响应式查询成本、订阅粒度、点查
- `references/function-budget.md` - 执行限制、事务大小、大文档、载荷大小

同时，请查阅官方
[Convex Best Practices](https://docs.convex.dev/understanding/best-practices/)
页面，该页面涵盖参数校验、访问控制及代码组织等方面的额外模式，在审计过程中可能会遇到这些问题。
