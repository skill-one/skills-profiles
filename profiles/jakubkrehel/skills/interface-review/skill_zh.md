# 变更评审

这项技能评审的是一个变更而非一个界面。它确定范围，将变更的文件扩展到它们影响的表面，读取差异的两边并将每个发现分类。

范围属于它自身。领域规则属于 `better-*` 技能。严重性、合并、覆盖率、上限和结论属于 `better-interface`，这项技能将评审交给它。

正确性、测试、安全和性能属于项目的通用代码评审。一次命名关注点并继续进行。

## 变更是不是代码库

作者在问“我让这个变得更糟了吗？”。报告变更造成的影响，并尽量少地谈论它仅仅触及的内容。三个现有的发现是一种礼貌；三十个是不同的评审，而且没有人要求。

在形成对变更的看法之前先阅读变更。声明的意图决定了什么被视为不完整，而浏览过的差异会产生关于下一块已经修复的代码的发现。

## 核心原则

### 1. 首先解决变更范围

整个调用是目标，所以 `/interface-review pr 482` 评审拉取请求 482。[范围解析](scope-resolution.md) 包含接受的靶标以及每个如何解析。

在没有提供目标的情况下，按以下顺序解析并停止在第一个匹配处：

1. `HEAD` 在 `git merge-base origin/<default-branch> HEAD` 之前：该范围**加上**任何未提交的更改，并分别说明提交计数和未提交文件计数。
2. 工作区是脏的：未提交的更改。
3. 都不是：没有要评审的变更。停止并询问，根据 **没有变更，问而不是编造一个**。

顺序很重要。先检查工作区，一个随机的格式化编辑会掩盖一个十二个提交的分支，报告仍然声称完整覆盖。

排除锁文件、快照、生成输出、源代码代码和二进制文件，并说明你排除了什么。排除后为空的范围通过不同的路线到达相同的地方。

### 2. 没有变更，问而不是编造一个

一个干净的树与合并基没有 ahead 的任何内容意味着用户要求评审一个不存在的变更。不要自行回退到 `HEAD~1..HEAD`。最后一个提交是无论发生了什么来完成的，通常是合并，通常是别人的工作，关于它的报告与关于用户意图的报告无法区分。

陈述你发现的存储库事实，然后提供路线并等待。[没有要评审的内容](scope-resolution.md#nothing-to-review) 包含收集的事实：

- **最后一个提交**，`HEAD~1..HEAD`，以短 SHA 和主题命名，以便用户在选择之前看到他们将要得到的内容。
- **用户命名的目标**：`pr <n>`、一个分支、一个引用或一个范围，根据 **首先解决变更范围** 解析。
- **整个存储库的界面审计**，这不是一个变更评审。将其作为存储库范围的评审交给 `better-interface`，而不带这个技能的范围块、状态或现有部分。没有变更，每个发现都是现有的，分类什么也不说。

在询问之前检查当前分支上是否有打开的拉取请求，并首先提供它。一个其提交已经合并的分支解析为没有变更，而它的拉取请求仍然是用户意图的准确内容。

在排除后范围变为空的地方，说明哪些文件被排除了，并以同样的方式询问。不要将空的评审报告为 `Approve`。

### 3. 差异不是一个表面

一个变更的文件是证据，而不是评审主题。它的**爆炸半径**是它渲染的表面集；评审那些。

默认情况下默认扩展爆炸半径一步：直接导入者和调用者。仅对设计令牌、主题值和共享原语扩展第二步，其中一行代码可以到达整个产品。

最多评审五个消费者，按 [范围解析](scope-resolution.md#expanding-to-consumers) 中的规则排序，然后说明你没有扩展多少。没有界限的扫描无法支持它声称的覆盖范围，而未声明的截止点被视为完整性。

### 4. 阅读删除的行

回归在变更后的状态下是看不见的。针对每个块的 `-` 侧与 [删除信号](removed-signals.md) 读取。

一个信号是一个线索，而不是一个发现。一个删除只有在变更中没有替换它的内容时才是回归，而领域技能拥有这个判断。将每个不匹配的删除路由到它的所有者，只报告该技能确认的内容并标记状态为 `Regression`。这告诉作者他们破坏了某个工作正常的东西，而不是犯了一个新错误。

### 5. 对每个发现进行分类

给每个发现一个状态：

- `Introduced`：变更创建它。
- `Regression`：变更削弱了之前正确的东西。
- `Pre-existing`：存在于接触的代码中，但不是由这个变更引起的。

根据差异接触的内容而不是它所在的文件来标记状态：变更从未接触的行是 `Pre-existing`，即使它靠近一个块三行。在需要时与基础引用确认：

```bash
git blame -L <line>,<line> "$BASE" -- path/to/file
```

将每个发现与其状态一起上交，并让 `better-interface` 应用其上限和结论规则。

### 6. 将变更保持在它的声明意图上

阅读拉取请求标题和正文、链接的问题和提交消息，然后评审界面是否交付了它们声称的内容。

这是暴露**不完整**变更的原因。表面评审看不到它，因为它检查现有的状态，而这里的关键是缺失的状态：

- 对某些状态应用了新的变体、大小或主题，但没有全部应用：悬停、焦点、活动、禁用、加载、选中。
- 一个新的用户界面字符串没有项目维护的翻译目录中的条目。
- 一个新的组件没有空、加载、错误、禁用或窄宽度状态。
- 一个控件添加到一个表面，但没有添加到已经携带其同伴的兄弟表面。

不要报告范围蔓延。变更是否做太多是一个流程问题，而不是界面问题。

### 7. 将评审交给 `better-interface`

将范围块、受影响的表面以及每个发现的状况交给 `better-interface`。它路由到领域技能，应用严重性，合并，执行上限并发布结论。

如果 `better-interface` 不可用，报告解析的范围和文件清单，将其命名为缺失的技能并停止。不要编造严重性等级、上限或结论。

### 8. 永远不要修改工作区

变更评审是只读的，包括检出。获取拉取请求引用；永远不要检出它们。`git fetch` 只写入 `.git` 并被允许。`gh pr checkout`、`git checkout`、`git switch` 和 `git stash` 会重写作者打开的文件。它们会失败在本地编辑或丢弃它们，所以它们永远不被允许。

渲染验证是可选的。除非项目暴露了一个廉价的预览或用户请求渲染评审，否则标记视觉和运行时声明 **未验证**。当它们这样做时，使用隔离的工作区 (`git worktree add /tmp/review-<n> refs/remotes/pr/<n>`) 并完成时删除它。

## 完成前

| 错误 | 修复 |
| --- | --- |
| 一个随机的编辑而不是分支被评审 | 在工作区之前检查 `merge-base`，并报告两个计数 |
| 因为没有变更而评审了最后一个提交 | 陈述事实并提供最后一个提交、命名目标或存储库审计 |
| 没有消费者地评审块 | 扩展一步，对令牌和原语扩展两步，并命名你跳过了什么 |
| 只读取了差异的 `+` 侧 | 搜索 `-` 侧以查找删除的可访问性、焦点、运动和文本信号 |
| 一个等效的替换报告为回归 | 将删除路由到它的所有者；只报告它确认的内容 |
| 一个删除报告为一个新的错误 | 将其标记为 `Regression`，以便作者知道它以前可以工作 |
| 一个靠近块的行标记为 `Introduced` | 根据差异接触的内容，与基础引用的 `git blame` 确认 |
| 拉取请求被检出到评审它 | 获取引用并在原地评审它 |
| 引用的行号在评审的引用上不存在 | 对范围块中命名的头引用引用 |
| 严重性等级或发现上限在这里重申 | 委托给 `better-interface` |
| 报告中存在正确性、测试或安全发现 | 一次命名关注点，指向项目的代码评审并放下它 |

## 评审输出格式

以范围块开头：

| 字段 | 值 |
| --- | --- |
| 目标 | `branch`、`working`、`staged`、`pr 482` 或输入的范围 |
| 基础引用 | `origin/main` 在 `a1b2c3d` |
| 头引用 | `refs/remotes/pr/482` 在 `e4f5g6h` |
| 提交 | 7 次提交，2 个文件未提交 |
| 范围内的文件 | 排除后 12 个 |
| 排除 | `pnpm-lock.yaml`、`src/__snapshots__`：锁文件和快照 |
| 扩展的表面 | `CheckoutPage`、`SettingsPanel`；3 个未扩展的 `Button` 消费者 |

覆盖表保持不变。没有证据在变更范围内没有证据的领域是 `Not reviewed: no evidence in the change scope`，这是一个覆盖声明而不是一个差距。

然后是发现，每个 **分类每个发现** 都有一个 `状态` 列：

| 严重性 | 领域 | 状态 | 位置 | 之前 | 之后 | 原因 |
| --- | --- | --- | --- | --- | --- | --- |
| HIGH | 可访问性 | Regression | `src/Dialog.tsx:42` | `aria-label="Close"` 在这个变更中删除 | 在仅图标控件上恢复 `aria-label="Close"` | 关闭控件在这个变更之前有一个可访问的名称，现在不再有 |

如果没有 `Introduced` 或 `Regression` 发现，省略表格并说明“此变更中没有可操作的界面发现。”

然后是 `Pre-existing` 发现，最多三个，最高严重性优先，平铺为不是这个变更的责任。当没有时省略该部分。

| 严重性 | 领域 | 位置 | 问题 |
| --- | --- | --- | --- |
| MEDIUM | 字体排印 | `src/Toolbar.tsx:7` | 数字徽章使用比例数字；早于这个变更 |

上限和结论只涵盖 `Introduced` 和 `Regression`。`Pre-existing` 发现位于上限之外，所以触摸一个旧文件不能变成一个全文件审计。它们也位于结论之外，所以一个只有预存在发现的变更是一个 `Approve`。

以 `Block` 结尾，当任何 `HIGH` 剩余时，否则为 `Approve`，将剩余的发现保留在表格中作为要做的功课。当 `better-interface` 可用时，严重性等级和上限来自它。
