# 接口评审

这项技能运行跨学科评审。它将接口路由到每个 `better-*` 技能，收集它们的证据并整合一个排名的裁决。

它只拥有编排功能。可访问性规则属于 `better-accessibility`，结构属于 `better-layout`，文案属于 `better-writing`，类型属于 `better-typography`，颜色属于 `better-colors`，视觉润色和动效属于 `better-ui`。在这里不要重复或覆盖它们的规则。

未提交的工作、分支和拉取请求的变更范围评审属于 `interface-review`，它解决范围并对发现进行分类，然后将评审结果返回。

## 证据而非品味

用力按压升级触发器，而不要干涉项目中的有意选择。它们会以相同的方式行事。无论风格指南怎么说，触发器就是一个失败；你仅仅不同意的高密度、半径或语音并不是一个发现。

因此，报告的标准是证据而非品味。`Approve` 的标准是你检查了你声称检查的内容。来自真实检查的简短报告胜过填充到看起来全面的冗长报告。

## 核心原则

### 1. 首先确定范围

从请求和当前工作区推断屏幕、流程、功能或存储库范围。在输出中声明已确定的范围。

在 **使用领域技能作为事实来源** 下列出的每个领域技能中覆盖所有内容，包括它们存在的空、加载、错误和窄宽度状态。最多报告 15 个发现。

当范围太大而无法可信地检查时，将其缩小到一个完整的流程：请求所关注的流程，或者如果没有，则是每个用户都必须通过的入口路径。声明边界和排除的内容。永远不要暗示未检查的表面被评审了。

### 2. 将变更发送到 `interface-review`

命名分支、拉取请求、提交范围或未提交变更的请求是变更评审，而不是屏幕评审。请用户运行 `interface-review`，这是一个用户触发的操作，不能从这里启动。

在这里不要解决变更范围。读取差异、分类发现并将更改文件扩展到受影响的表面属于 `interface-review`。猜测它们，报告的范围将无人能检查。

当 `interface-review` 返回评审时，它会提供变更范围、每个发现的状况以及变更范围报告格式。严重性、排名、上限和裁决留在这里，并且这三个都涵盖 `Introduced` 和 `Regression` 仅。

### 3. 判断前重构

识别框架、样式系统、组件库、设计令牌、支持的视口以及任何预览或测试命令。使用项目自己的语言编写每个修复，这样没有发现会要求采用不同的堆栈。这决定了修复的形式，而不是代码是否足够好。

然后阅读项目自己关于其接口的描述：`CONTRIBUTING.md`、`CODING_STANDARDS.md`、`AGENTS.md`、`CLAUDE.md`、设计系统文档、Storybook 文档、接口 ADR。声明你找到了哪些，或者没有。

阅读它们以找到发现所属的位置，而不是为了获得删除它的许可。一个记录的约定并不是约定好的证据，而“它在风格指南中”不会使发现失效。它们更改的是 **在哪里** 你报告。当一个指南或共享令牌是原因时，针对该来源报告一次，并将组件作为其位置。

### 4. 使用领域技能作为事实来源

在评审之前，确认以下每个拥有技能都可用。加载并应用每个可用的所有者，并在整合之前完成每个领域评审。

按此顺序评审，以便基础性失败不会被润色隐藏：

1. `better-accessibility`
2. `better-layout`
3. `better-writing`
4. `better-typography`
5. `better-colors`
6. `better-ui`

从一个在此加载的领域技能中，获取其原则、其参考和其验证检查。它的严重性等级和它的格式是用于独立使用；此文件中的整合格式、共享严重性和发现上限取代它们。

如果一个拥有技能不可用，将该领域标记为 `Not reviewed`，并命名它，然后继续处理其余部分。不要从记忆中重新创建它的规则，用邻居替换，或声称整体覆盖。

当两个技能似乎涵盖一个问题时，将其分配给底层规则的拥有者，并在 **Why** 单元中注明次要影响。只报告一次。

### 5. 需要证据

每个发现都引用 `path/to/file:line` 并显示当前实现。不要仅凭视觉外观报告代码级发现，或仅凭源代码报告视觉发现，当运行时行为决定结果时。

### 6. 按用户影响排名

使用一个共享的严重性量表：

- `HIGH`：阻止任务、误导用户、隐藏内容或控件、造成数据丢失风险，或创建重复的系统故障。
- `MEDIUM`：有意义地损害理解、效率、适应性或一致性。
- `LOW`：孤立的润色，对任务影响有限。

在严重性内，按发现到达的位置数量和一个修复能买到的程度排名。令牌或共享组件修复优先于一个叶节点中的相同症状。

**升级触发器。** 一旦拥有技能确认其中之一，它在眼前就是 `HIGH`，永远不会因为表面微小而被平均降低：

- 一个没有可访问名称的交互式控件。
- 一个可以通过键盘访问的控件，但没有可见的焦点指示器。
- 一个可以通过指针访问但无法通过键盘访问的控件或路径。
- 忽略 `prefers-reduced-motion` 的动效或自动播放内容。
- 在 320px 宽度或 200% 放大时被裁剪、重叠或无法访问的内容或控件。
- 身体或控件文本的渲染对比对未能通过其所需比率。
- 仅由颜色携带的状态或含义。
- 没有确认、撤销或不同处理的破坏性行动。
- 没有办法访问完整值的截断内容。
- 只能在滚动边缘之后或在一个没有可见提示的披露之后才能访问的内容或控件。
- 一个没有说明如何从中恢复的错误。
- 一个与其含义相反的语义颜色，例如在非破坏性行动上的危险色调。
- 仅由动效携带的状态变化，当动画不运行时没有颜色、图标或标签留下。

触发器排名高于所有其他发现。当触发器数量超过上限允许时，首先列出它们，并说明上限排除了多少。上限可能会缩短报告；它永远不会是为什么阻止项未被报告的原因。

这些设定严重性，而不是新规则。拥有技能决定症状是否存在；这个列表决定它的成本。在变更评审中，对触发器的确认 `Regression` 即使在相同症状作为现有存在时也是 `HIGH`。

### 7. 优先选择更便宜的修复

严重性说明发现有多糟糕；这说明了要提议哪个修复。当有多个可以工作时，选择最早可以工作的那个：

1. **删除。** 一个空间会携带的隔离符，一个在高频交互上的动画，一个原生元素使冗余的 ARIA 属性，一个什么也不导入的斜坡。
2. **使用平台。** 原生元素，原生控件，浏览器的自己的焦点环，而不是自定义重建。
3. **重用项目已有的。** 现有的令牌、间距步骤或动效曲线，在任何新值之前。
4. **修正值。** 错误的缓动、半径、间隙或对比对，使用拥有技能给出的确切值。
5. **添加。** 一个新的令牌，一个包装器，一个媒体查询，平台无法提供的 ARIA 属性。

在步骤 5 中编写的修复，而步骤 1 是可用的，它自己的发现。报告删除。

### 8. 整合系统性发现

一个根本原因是 一个发现。在相同行中列出每个确认的位置，而不是每行一个发生。永远不要填充以达到上限；简短的评审或没有发现是有效的结果。

### 9. 验证可以验证的内容

运行项目提供的安全、相关的检查。当运行时行为或视觉判断很重要时，检查渲染的接口，并报告确切的命令或交互及其结果。你无法运行的检查是 **Not verified**，永远不会是一个发现。

### 10. 默认情况下不通过修改进行评审

将评审请求视为只读。除非用户也要求你实施发现，否则不要编辑源代码。当他们这样做时，将整合报告作为变更范围，并在之后重新运行相关的验证。

## 完成前

| 错误 | 修复 |
| --- | --- |
| 六个断开的领域报告 | 一个排名的发现表 |
| 仅从源代码推断的视觉主张 | 检查渲染状态，或将其标记为未验证 |
| 静默的覆盖范围差距 | 显示实际检查了哪些领域和状态 |
| 处理为覆盖的缺失拥有技能 | 将领域标记为 `Not reviewed` 并命名技能 |
| 触摸的文件中的每个遗留问题都报告 | 三个现有发现，在自己的部分 |
| 阻止变更评审的现有问题 | 将现有发现排除在上限和裁决之外 |
| 当变更从未触及它时领域标记为 `Clear` | 将其标记为 `Not reviewed: 变更范围内没有证据` |

## 评审输出格式

格式位于 [review-format.md](review-format.md)：范围和覆盖范围，发现表，验证和裁决。评审在发现报告在那里之前未完成。
