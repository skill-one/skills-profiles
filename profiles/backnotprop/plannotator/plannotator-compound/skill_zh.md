# 复合规划分析

您正在进行一项全面的用户 Plannotator 计划存档研究分析。目标：从其被拒绝的计划中提取模式，将其缩减为可操作的见解，并生成一份优雅的 HTML 仪表板报告。

这是一个多阶段的过程。每个阶段必须完全完成后才能开始下一个阶段。研究诚信至关重要——每个文件都必须读取，不能跳过。

## 源选择

在开始分析之前，确定哪个数据源可用。

1. **Plannotator 模式（首选）** — 确定 Plannotator 数据目录：
   如果设置了 `$PLANNOTATOR_DATA_DIR`，则使用它，否则使用 `~/.plannotator`。检查那里的 `plans/` 子目录。如果它存在并包含 `*-denied.md` 文件，则使用此模式。下面整个工作流程都是为 Plannotator 数据编写的。

2. **Claude Code 降级模式** — 如果 Plannotator 存档不存在或其中不包含被拒绝的计划，请检查 `~/.claude/projects/`。如果存在，请在继续之前阅读 [参考资料/claude-code-fallback.md](references/claude-code-fallback.md)。该参考资料解释了如何使用捆绑的解析器 [脚本/extract_exit_plan_mode_outcomes.py](scripts/extract_exit_plan_mode_outcomes.py) 从 Claude Code JSONL 转录中提取拒绝原因。下面每个阶段都有一个简短说明解释降级模式下的变化——参考资料文件包含详细信息。

3. **两者都不可用** — 请求用户提供他们的 Plannotator 计划目录或 Claude Code 项目目录。不要猜测。

## 阶段 0：定位计划并检查之前的报告

使用源选择中选择的模式。

**Plannotator 模式：** 验证计划目录包含 `*-denied.md` 文件。如果不存在，则在停止之前降级到 Claude Code 模式。

**Claude Code 降级模式：** 运行捆绑的解析器，根据降级参考资料构建拒绝原因数据集。如果需要，创建 `/tmp/compound-planning/`。

在任何模式下，继续进行下面的“之前的报告检测”。

### 之前的报告检测

定位计划目录后，检查现有报告：

```
ls ${PLANNOTATOR_DATA_DIR:-~/.plannotator}/plans/compound-planning-report*.html
```

报告遵循版本化的命名方案：
- 首个报告：`compound-planning-report.html`
- 后续报告：`compound-planning-report-v2.html`，`compound-planning-report-v3.html`，等等。

如果存在一个或多个报告，请确定**最新**的一个（最高版本号）。使用 `stat` 获取其文件系统修改日期（macOS：`stat -f %Sm -t %Y-%m-%d`，Linux：`stat -c %y | cut -d' ' -f1）。这是**截止日期**。

向用户显示一个选择：

> "我找到了一个之前的报告（`compound-planning-report-v{N}.html`），最后更新于 {CUTOFF_DATE}。我可以：
>
> 1. **增量** — 仅分析日期在 {CUTOFF_DATE} 之后的文件，节省代币并建立之前的发现
> 2. **完整** — 从头重新分析整个存档
>
> 您希望选择哪个？"

在继续之前等待用户的响应。

**如果增量：** 将所有后续阶段过滤为仅处理截止日期之后的文件日期。新的报告版本将在其标题叙述中注明它涵盖了从 {CUTOFF_DATE} 到现在的时期，并参考之前的报告以获取早期发现。清单（阶段 1）仍然应计算所有文件以获取整体统计数据，但应明确区分“自上次报告以来新增”计数。

**如果完整：** 正常进行所有文件，但仍然使用下一个版本号作为输出文件名。

**如果不存在之前的报告：** 正常进行。输出文件名将使用 `compound-planning-report.html`（第一个报告没有版本后缀）。

## 阶段 1：清单

计数并报告数据集。**始终计数所有文件**以获取整体统计数据，无论这是增量运行还是完整运行：

```
- *-approved.md 文件（计数）
- *-denied.md 文件（计数）
- 日期范围（文件名中找到的最早日期到最新日期）
- 总天数跨度
- 修订率：拒绝 / （批准 + 拒绝）——这是仪表板部分 1 中使用的“X% 的计划在编码前被修订”统计数据
```

**注意：** 完全忽略 `*.annotations.md` 文件。拒绝文件已经包含完整的计划文本以及所有审阅者反馈，这些反馈在 `---` 分隔符之后追加。注释文件是此内容冗余的子集——读取两者将导致反馈重复计数。

**如果增量模式：** 在总计数之后，单独报告仅日期在截止日期之后的文件计数：

```
自 {CUTOFF_DATE} 以来：
- *-denied.md 文件：X（共 Y 个总）
- 新日期范围：{CUTOFF_DATE} 到 {LATEST_DATE}
- 新天数跨度：N
```

如果自截止日期以来少于 3 个新的拒绝文件存在，请警告用户：
> "自上次报告以来只有 {N} 个新的拒绝计划。增量分析可能很薄弱。您想继续还是切换到完整分析吗？"

还运行 `wc -l` 跨越所有 `*-approved.md` 文件以获取每个批准计划的平均行数。这告诉用户他们的计划是保持轻量级还是随着时间的推移而膨胀。您不需要读取批准计划的内容——只需读取它们的行数即可。如果可能，按时间段（例如，每月）进行分解，以显示计划大小是否发生变化。

日期以 YYYY-MM-DD 格式出现在文件名中，有时作为前缀（2026-01-07-name-approved.md），有时嵌入其中（name-2026-03-15-approved.md）。从所有文件名中提取日期。

告诉用户您发现了什么，并且您开始提取。

**Claude Code 降级模式：** 上面提到的 Plannotator 清单字段不适用。请按照 [参考资料/claude-code-fallback.md](references/claude-code-fallback.md) 中的清单说明进行操作——报告解析器组装的拒绝原因数据集。

## 阶段 2：映射——并行提取

这是最耗时的阶段。您必须读取**范围内**的每个 `*-denied.md` 文件。不要跳过文件。不要提前总结。

**范围内**意味着：如果运行完整分析，则所有拒绝文件；如果运行增量模式，则仅日期在截止日期之后的拒绝文件。在增量模式下，仅处理嵌入的 YYYY-MM-DD 日期严格在截止日期之后的文件。

**Claude Code 降级模式：** 解析器输出是干净的源数据集。阅读降级参考资料以获取针对 JSON 部分文件的提取提示和批处理策略。除非解析器失败或用户要求审计级验证，否则不要回到原始 `.jsonl` 日志。

**重要：** 仅读取 `*-denied.md` 文件。不要读取批准计划、注释文件或差异文件。每个拒绝文件包含完整的计划文本，后跟一个 `---` 分隔符和审阅者的反馈——分析所需的一切都在一个文件中。

### 批处理策略

所有提取代理应使用 `model: "haiku"`——它们正在进行简单的文件读取和结构化提取，而不是推理。Haiku 对于这项工作更快、更便宜。

方法取决于数据集大小：

**小型数据集（≤ 10 个总文件）：** 直接在主代理中读取所有文件——不需要子代理。只需按顺序读取它们并继续到阶段 3。

**中型数据集（11-30 个文件）：** 启动 2-3 个并行 Haiku 代理，大致均匀分配文件。

**大型数据集（31-80 个文件）：** 启动 4-6 个并行 Haiku 代理（每个约 10-15 个文件）。按文件类型和/或时间段进行拆分。

**大型数据集（80+ 个文件）：** 启动所需数量的并行 Haiku 代理，以保持每个批次的文件数在 10-15 个左右。按数据中的自然时间边界（月份、季度或产生平衡批次的任何分组）进行拆分。如果一个时间段占主导地位（例如，最近一个月的文件有 3 倍），请将该时间段拆分为多个批次。

使用 Agent 工具以 `run_in_background: true` 和 `model: "haiku"` 并行启动所有提取代理。

### 输出文件

每个提取代理必须将其结果写入一个干净的输出文件，而不是依赖代理任务输出（其中包含难以解析的交错 JSONL 框架日志）。指示每个代理写入：

```
/tmp/compound-planning/extraction-{batch-name}.md
```

在启动代理之前创建 `/tmp/compound-planning/` 目录。阶段 3 中的缩减代理将直接读取这些干净的文件。

### 提取提示

每个代理接收此指令（调整时间段、文件列表和输出路径）：

```
您正在从拒绝计划文件中提取结构化数据，用于模式分析。

目录：[PLANS DIRECTORY]
要读取的文件：[特定的 *-denied.md 文件列表]
输出：将您的完整结果写入 [OUTPUT FILE PATH]

每个拒绝文件包含两个由 --- 行分隔的部分：
1. 计划文本（--- 之前）
2. 审阅者的反馈和注释（--- 以下）

读取您列表中的每个文件。对于每个文件，提取：
- 计划名称/主题（来自 --- 之前的计划文本）
- 给出的拒绝原因或反馈（来自 --- 以下——捕获实际使用的词语）
- 具体要求更改的内容
- 反馈类型（让内容决定类别——不要强行套入预定义类型。常见的类型包括：范围问题、方法分歧、信息缺失、流程要求、质量问题、UX/设计问题、命名争议、澄清请求、测试/程序拒绝——但用户的实际模式可能不同）
- 审阅者使用的任何特定短语或重复语言
- 如果有的话，单独的注释（编号的反馈项，带引文和审阅者评论）
- 日期（从文件名中提取）

不要跳过任何文件。每个文件一个条目。

将每个条目格式化为：
**[filename]**
- 日期：...
- 主题：...
- 拒绝原因：...
- 反馈类型：...
- 具体要求：...
- 显著短语：...
- 注释：[数量，每个的简要摘要]
---

处理所有文件后，将完整结果写入 [OUTPUT FILE PATH]。
在文件末尾说明文件总数。
```

### 在代理运行时

跟踪完成情况。每当一个代理完成时，请记录它处理的文件数量。验证总数是否与阶段 1 的清单匹配。如果任何代理的计数不足，请标记它并考虑重新启动以处理缺失的文件。

如果代理超时（对于大型批次可能发生——128 个文件的批次可能需要 8 分钟以上），请仅重新启动它以处理未处理的文件。检查输出文件以查看它在超时前处理到了哪里。

## 阶段 3：缩减——模式分析

一旦所有提取代理完成（对于小型数据集，所有文件都已读取），请继续缩减。缩减代理应使用 `model: "sonnet"`——这个阶段需要真正的分析推理，而不仅仅是文件读取。

### 缩减策略

方法取决于生成的提取文件数量：

**标准（≤ 20 个提取文件）：** 启动单个 Sonnet 代理读取所有提取文件并生成完整分析。这涵盖了大多数数据集。

**大型（21+ 个提取文件）：** 使用两阶段缩减：

1. **阶段 1——部分缩减：** 将提取文件分成 4-6 组。启动并行 Sonnet 代理，每个代理读取一组并生成与下面列出的相同部分的部分分析。每个写入 `/tmp/compound-planning/partial-reduce-{N}.md`。

2. **阶段 2——最终缩减：** 单个 Sonnet 代理读取所有部分缩减文件，并将它们综合成最终的综合分析。该代理合并分类，组合计数，去重模式，并解决部分之间的任何冲突分类。

**Claude Code 降级模式：** 缩减阶段与相同。唯一的上游差异是提取文件是从归一化的拒绝原因 JSON 而不是 Plannotator Markdown 文件中提取的。

### 缩减提示

给每个缩减代理此提示（根据单阶段和多阶段调整文件路径）：

```
您正在进行一项跨用户拒绝计划存档的 map-reduce 分析的缩减阶段。

读取所有提取文件在 [FILE PATHS]

这些文件包含从每个拒绝计划文件中提取的结构化数据。每个提取包括计划主题、拒绝反馈、注释和审阅者语言。您的任务：汇总所有内容，发现模式，聚类成一个分类，并生成综合分析。

要彻底。使用真实计数。引用真实数据中的真实短语。这是研究——不要含糊其辞，不要编造。

将您的完整结果写入 [OUTPUT FILE PATH]。

生成以下部分：
[... 下面列出的部分 ...]
```

缩减代理的任务是让数据说话。不要强加预定的框架——发现实际存在的内容。分析必须产生：

### 1. 拒绝原因分类
将每个拒绝分类到从数据中出现的有限类型集中。计数出现次数。显示百分比。包括每个类型的真实示例引言。目标为 8-15 个类别——足够具体，足够少以供扫描。让用户的实际反馈决定分类是什么。

### 2. 顶级反馈模式（按频率排名）
最常出现的 5-10 个模式。对于每个：审阅者一致要求的内容、来自不同文件的第 3 个或更多个示例引言，以及模式是否随时间变化。

### 3. 重复短语
审阅者反复使用的确切短语，以及它们表示的含义。这些是审阅者的词汇——他们对什么最关心的简写。

### 4. 审阅者重视什么（隐含偏好）
从模式中推导出来——这个特定的人最关心什么？质量？速度？叙事？架构？流程？简单性？按证据强度排名。这个部分应该感觉像审阅者标准的个人简介。

### 5. 代理经常出错的地方
另一方面——导致拒绝的经常性错误是什么？代理应该停止为这个审阅者做什么？

### 6. 结构性要求
审阅者一致要求什么样的计划结构？必需的部分、顺序、格式偏好、期望的详细程度。

### 7. 随时间演变
反馈模式在时间跨度内如何变化。按数据中存在的任何自然时间边界分组（短跨度为周，长跨度为月）。期望是否成熟？是否出现了新的模式？什么发生了变化？如果数据集跨度小于一个月，请说明演变分析有限，但仍要寻找早期文件到晚期文件之间的任何进展。

### 8. 可操作的提示指令
最重要的输出。基于所有模式：可以嵌入在规划提示中的具体编号指令，以防止最常见的拒绝原因。将这些写入代理可以遵循的实际指令。针对此用户的模式要具体——像“写好计划”这样的通用建议是无用的。每个指令应追溯到真实的、频繁的拒绝模式。

在编写指令后，计算它们将解决多少拒绝（计算落入指令覆盖的分类的拒绝数量与总拒绝数量）。报告此百分比——每个用户的百分比都不同。

## 阶段 4：生成 HTML 仪表板

构建一个单一、自包含的 HTML 文件作为最终交付物。将其保存到用户的计划目录中，使用版本化文件名：

- 首次报告：`compound-planning-report.html`
- 第二个报告：`compound-planning-report-v2.html`
- 第三个报告：`compound-planning-report-v3.html`
- 以此类推。

版本号是在阶段 0 基于找到的现有报告确定的。

**如果这是一个增量报告**，标题应指示分析期间（例如，“2026 年 3 月 15 日 – 2026 年 3 月 31 日”），并包括副标题，注明“增量分析——请参阅 v{N-1} 以获取早期发现。”标题中的叙述应将发现表述为自上次报告以来是什么新内容或发生了什么变化，而不是完整的画面。标题中的整体统计数据（文件计数、修订率）应仍然反映完整存档以提供上下文。

读取 `assets/report-template.html` 中的模板，仅用于**设计语言**。模板包含来自先前分析的示例数据——忽略模板中的所有数据值、引言和百分比。仅使用其视觉设计：颜色、排版、间距、组件样式和布局模式。

### 设计语言（来自模板）

- **调色板：** 浅色模式，温暖的浅米色 (#FDFCFB)，文本为 slate 色调，高亮/强调为琥珀色，积极为翡翠色，负面为玫瑰色，操作元素为靛蓝色
- **排版：** Playfair Display（衬线，用于叙述标题），Inter（无衬线，用于正文/数据），JetBrains Mono（等宽，用于代码/短语）——Google Fonts CDN
- **布局：** 单列，最大宽度 1024px，垂直间距宽（主要部分之间 128px），编辑/叙述优先美学
- **语气：** 平静、反思、权威。像个人回顾日记，而不是监控仪表板。

### 页面框架（标题 + 页脚）

在 7 个部分之前，页面有：

- **标题：** 左侧报告标题（Playfair Display，约 36px），下方是项目名称 + 日期范围，使用浅元文。右侧：文件计数，使用等宽（例如，“223 拒绝 · 71 天”）。与内容由底部边框分隔。在内容之前有足够的底部填充。

- **页脚：** 在第 7 个部分之后。顶部边框，居中斜体 Playfair Display 标签，总结语料库（例如，“分析 Plannotator 存档中的 X 个拒绝计划。”）。

### 仪表板部分顺序（7 个部分）

报告遵循此确切部分顺序。每个部分都建立在之前的部分之上——流程从“发生了什么”到“为什么”再到“如何解决”：

1. **数据中的故事** — 一个叙述性段落（Playfair Display 衬线，约 26px），用散文讲述头条发现。不是项目符号——一个像文章开头一样读起来像真实段落的真实段落。旁边是一个 KPI 侧边栏，包含 3 个关键指标（顶级拒绝百分比、整体修订率和发现的拒绝类别数量）。在叙述中最显眼的数字上使用琥珀色内联高亮。

2. **计划为何被拒绝** — 分类作为一个排名列表。每行：排名数字（等宽），类别标签，一个薄 4px 进度条（第一项为琥珀色-500，其余为 slate-300），百分比（等宽），对于顶级条目，在标签下方提供来自数据的斜体引言。显示前 10 个类别或数据支持的其他数量（至少 5 个）。

3. **期望如何演变** — 每个自然时间段一个卡片。每个卡片都有：时间段名称（衬线），主题短语（彩色大写），描述段落，和底部的统计行（例如，“X 拒绝 · Y 叙事请求”）。如果数据跨度少于 3 个不同的时间段，使用 2 个卡片或甚至一个卡片，内部进展注明。

4. **有效与无效** — 两个并排的卡片。左侧：绿色调（emerald-50/50 背景，emerald-100 边框）包含此审阅者对成功计划的特征。右侧：红色调（rose-50/50 背景，rose-100 边框）包含代理持续犯的错误。两者都来自缩减分析。项目符号，带小彩色圆点。每张卡片 5-8 个项目。

5. **可操作的输出** — 诊断回报。以 Playfair Display 叙述句开头，说明导出了多少提示指令，以及估计的拒绝百分比它们将解决（使用来自阶段 3 的真实计算百分比，而不是通用数字）。然后是前 3 个最有影响力的改进，编号项目，每个项目带有琥珀色数字、粗标题和一行描述。这一部分连接了分析和后面将跟随的完整提示。

6. **您最常用的短语** — 网格芯片（移动端 2 列，桌面端 3 列）。每个芯片：等宽引文短语在左侧，频率计数在右侧。白色背景，slate-200 边框，rounded-12px。显示 9-12 个最常用的短语。这些应该是审阅者的实际词语——他们的口头指纹。

7. **纠正性提示** — 深色面板（slate-900 背景，白色文本，rounded-3xl，shadow-xl）。以 Playfair 介绍句开头，说明指令。然后是一个深色代码块（slate-800/80 背景，amber-200 等宽文本）包含来自阶段 3 的完整编号提示指令。包括一个可以工作的复制到剪贴板按钮（包含 JS）。代码块下方是一个渐变辉光卡片（indigo-to-purple 模糊光晕在白色卡片后面）包含一条结束语，说明这些指令是个人化的——它们来自用户自己的反馈，用户自己的语言，用户自己的标准。

### 适应规则

- 如果用户的 < 3 个月数据，将演变部分减少到较少卡片
- 如果大多数拒绝文件缺少 `---` 以下的反馈（没有注释的裸拒绝），请在叙述中注明这一点——分析将更薄弱
- **Claude Code 降级模式：** 明确将报告源标记为 Claude Code `ExitPlanMode` 拒绝原因。不要编造 Plannotator 仅有的字段，例如注释计数或批准计划行计数。请参阅降级参考资料以获取 KPI 替代方案和页脚/来源指导。
- 如果少于 5 个拒绝类别出现，请将分类和模式部分合并为一个
- 如果数据集非常小（< 20 个文件），叙述应承认样本量有限，并将发现表述为初步的
- 提示指令的数量将因用户而异——可能是 8 个或 20 个。不要强制正好 17 个。让数据决定数量。
- 第 5 部分中的前 3 个可操作项目必须是覆盖最大拒绝份额的 3 个，而不是听起来最令人印象深刻的 3 个

### 关键规则

1. 每个数字必须来自真实分析——不要编造数据
2. 每个引言必须是来自真实文件的真正引言
3. 分类百分比必须根据真实计数计算
4. 提示指令必须追溯到实际的拒绝模式
5. 提示块上的复制按钮必须有效（包含 JS）

生成后，在用户的浏览器中打开该文件。

## 阶段 5：总结

告诉用户：
- 分析了多少个拒绝文件
- 如果增量：自上次报告以来有多少个是新的
- 找到的顶级 3 个拒绝模式
- 估计的提示指令将解决多少拒绝的百分比
- 最有影响力的提示改进
- 报告保存的位置（包括版本号）
- 如果增量：提醒用户之前的发现在之前的报告中

## 阶段 6：改进挂钩

在显示摘要后，询问用户是否要启用**改进挂钩**——这将纠正提示指令从报告的第 7 部分写入一个文件，Plannotator 的 `EnterPlanMode` 挂钩可以自动将其注入到未来的每个规划会话中。

> "您想启用改进挂钩吗？这将保存纠正提示指令到一个文件中，该文件会自动注入到所有未来的规划会话中——所以 Claude 在编写任何计划之前都能看到您的反馈模式。"

**如果同意：**

挂钩文件位于：

```
${PLANNOTATOR_DATA_DIR:-~/.plannotator}/hooks/compound/enterplanmode-improve-hook.txt
```

如果数据目录中不存在 `hooks/compound/` 目录，请在其中创建。

文件内容应包含来自阶段 3 的纠正提示指令——HTML 报告第 7 部分中出现的相同编号列表。将它们作为纯文本写入，每条指令每行前缀编号。没有 HTML，没有 markdown 管理符，没有前言——只有指令本身。挂钩系统将注入该文件的内容。

**如果文件已存在：**

读取现有文件，并让用户选择：

> "从之前的分析已经存在改进挂钩。我可以：
>
> 1. **替换** — 用新的指令覆盖（旧的不再存在）
> 2. **合并** — 合并两者，删除重复的指令并保留每个指令的最佳版本
> 3. **保留现有** — 保持当前挂钩不变，跳过此步骤
>
> 您希望选择哪个？"

- **替换：** 用新的指令覆盖文件。
- **合并：** 读取现有指令，与新指令比较，并生成合并集。删除重复项（即使措辞不同，意图相同）。当两个指令覆盖相同的模式时，保留更具体或更可操作的版本。对最终列表按顺序重新编号。将合并结果写入文件。向用户显示发生了什么变化（添加 N 个新，删除 N 个冗余，保留 N 个现有）。
- **保留现有：** 什么也不做，继续。

**如果不存在：** 完全跳过此阶段。

## 重要说明

- **数据源优先级：** Plannotator 是首选路径。Claude Code 日志分析是用户没有 Plannotator 存档的次要路径。
- **研究诚信：** 每个文件都必须读取。这项分析的价值来自完整性。抽样或跳过会损害结果。
- **仅真实数据：** 永远不要编造引言、百分比或模式。如果数据没有显示明显的模式，请诚实地说，而不是发明一个。
- **让数据引导：** 分类、模式和指令应从实际文件中得出。不同的用户将拥有完全不同的拒绝模式。构建移动应用的用户的反馈与构建 API 的用户不同。不要假设模式会是什么。
- **代理并行化：** 对于大型数据集，最大限度地使用并行代理以减少墙上时间。瓶颈是最大的批次——将其拆分。
- **结构化提取格式：** 要求提取代理返回具有一致分隔符的结构化文本，以便缩减代理可以可靠地解析。
- **报告是工件：** HTML 仪表板是用户保留的。它应该是美丽的、诚实的、有用的。每个部分都应感觉像是专门为用户编写的，因为确实如此。
