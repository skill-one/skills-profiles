# 简单问题描述

编写一个维护者能在一分钟内理解的问题。专注于用户遇到的情况以及应该发生的情况。

## 工作流程

1. 读取提供的笔记、对话、问题、PR 描述或差异。在 PR 中，还要检查规范、设计文档或 README 的变更——它们通常比描述更能说明意图。
2. 确定具体问题。当源代码清楚说明受影响者时，说明谁或什么受到了影响。
3. 描述期望的行为，而不是规定实现方式。
4. 仅保留有助于他人理解或重现问题的上下文。
5. 如果源代码是 PR 或差异，描述变更试图解决的问题，而不是它更改的文件或代码。
6. 立即起草问题，除非问题和期望行为无法确定。在这种情况下，问一个简短的澄清问题。

一个问题对应一个问题。如果源代码捆绑了无关的问题，起草最严重问题的描述，将其他问题每行一条列出，并告诉贡献者将它们拆分为单独的问题和拉取请求。

如果源代码添加了功能而不是修复了错误行为，不要将缺失作为错误进行记录。描述用户今天无法做的事情以及功能的完整用户体验：谁使用它、从哪里使用以及他们看到的内容。

不要编造用户影响、重现步骤或源代码不支持的确定性。如果源代码只显示清理、重构或可能的代码异味，说明没有明确的具体问题，而不是制造一个问题——这条规则优先于第 6 步。回复两到三句话：源代码显示的内容，以及使其成为问题值得的证据。

如果源代码修复了未公开的安全漏洞，不要起草描述它的公开问题。建议私下向维护者报告。

## 写作规则

- 使用平实语言和短句。
- 除非需要描述重现步骤或大型功能，否则将问题控制在 200 字以内。
- 以行为先，而不是代码、架构或建议的修复。当症状无法理解时，一个简单的平实语言原因也可以。
- 仅在必要时保留技术细节。使症状有意义的限制和默认值（批处理大小、配额、上限）都算必要。
- 保留有用的证据，如错误消息、截图、链接和文档引用。
- 不要提及 AI 撰写或审查了问题。
- 避免填充内容、赞美、路线图语言和详尽的边缘情况。
- 使用贡献者的确定性。不要将猜测呈现为确认的错误；当源代码描述风险而不是观察到的失败时，写“可以”或“似乎”。

## 输出格式

第一行是问题标题——在 GitHub 上提交时，将其放在标题字段中，而不是在正文中重复。对于缺失的功能，以结果命名（“标记没有结构化数据的页面”）而不是虚构的错误（“审核从未提及结构化数据”）。

当没有有用的内容可添加时，省略**附加上下文**部分。约束和范围说明属于该部分，包括当维护者合理担心受影响时，哪些内容不受影响。

```markdown
# <用简短的标题描述问题或期望结果>

## TL;DR

<用一到两句话说明现在发生的情况和应该发生的情况。>

## 发生了什么？

<用平实语言描述当前行为。如有，包括具体示例。>

## 应该发生什么？

<描述期望的行为，不提出如何构建它。>

## 附加上下文

<可选的重现步骤、错误文本、截图、链接或约束。>
```

## 示例

```markdown
# 聊天记录会跳离我正在阅读的消息

## TL;DR

当我向上滚动阅读旧消息时，新的回复将我移回聊天的底部。聊天应该保持在我离开的位置，直到我选择返回最新消息。

## 发生了什么？

新的回复自动将聊天滚动到底部，即使我正在阅读较早的消息。

## 应该发生什么？

保持我的当前滚动位置，并显示有新消息可用。
```
