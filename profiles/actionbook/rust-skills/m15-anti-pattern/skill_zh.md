# 反模式

> **第 2 层：设计选择**

## 核心问题

**这个模式是否隐藏了设计问题？**

在审查代码时：
- 这是在解决症状还是根本原因？
- 是否有更地道的方法？
- 这与 Rust 是否冲突？

---

## 反模式 → 更好的模式

| 反模式 | 为什么不好 | 更好的方法 |
|--------|-----------|-----------|
| 处处使用 `.clone()` | 隐藏所有权问题 | 正确的引用或所有权 |
| 生产环境中使用 `.unwrap()` | 运行时恐慌 | `?`、`expect` 或处理 |
| 单一所有者时使用 `Rc` | 不必要的开销 | 简单的所有权 |
| 为便利使用 `unsafe` | 可能导致未定义行为 | 寻找安全的模式 |
| 通过 `Deref` 实现面向对象 | 指令 API | 组合、特征 |
| 巨大的 match 分支 | 难以维护 | 提取到方法 |
| 处处使用 `String` | 分配浪费 | `&str`、`Cow<str>` |
| 忽略 `#[must_use]` | 错过错误 | 处理或 `let _ =` |

---

## 思考提示

看到可疑代码时：

1. **这是症状还是根本原因？**
   - 为避免借用而克隆？→ 所有权设计问题
   - 因为不会失败而使用 `unwrap`？→ 未处理的案例

2. **地道代码会是什么样子？**
   - 引用而不是克隆
   - 迭代器而不是索引循环
   - 模式匹配而不是标志

3. **这是否与 Rust 冲突？**
   - 与借用检查器冲突 → 重新结构化
   - 过度使用 `unsafe` → 寻找安全模式

## 初学者前 5 大错误

| 排名 | 错误 | 修复 |
|------|------|------|
| 1 | 用克隆逃避借用检查器 | 使用引用 |
| 2 | 生产环境中使用 `unwrap` | 用 `?` 传播 |
| 3 | 事事使用 `String` | 使用 `&str` |
| 4 | 索引循环 | 使用迭代器 |
| 5 | 与生命周期冲突 | 重新结构化以拥有数据 |

## 代码异味 → 重构

| 异味 | 指示 | 重构 |
|------|------|------|
| 许多 `.clone()` | 所有权不明确 | 明确数据流 |
| 许多 `.unwrap()` | 缺少错误处理 | 添加正确处理 |
| 许多 `pub` 字段 | 封装被破坏 | 私有 + 访问器 |
| 深层嵌套 | 复杂逻辑 | 提取方法 |
| 长函数 | 多重职责 | 分割 |
| 巨大的枚举 | 缺少抽象 | 特征 + 类型 |

---

## 常见错误模式

| 错误 | 反模式原因 | 修复 |
|------|------------|------|
| E0382 使用后移动 | 克隆与所有权的冲突 | 正确的引用 |
| 生产环境中恐慌 | 处处使用 `unwrap` | `?`、匹配 |
| 性能慢 | 所有文本使用 `String` | `&str`、`Cow` |
| 借用检查器冲突 | 结构错误 | 重新结构化 |
| 内存膨胀 | 处处使用 `Rc`/`Arc` | 简单的所有权 |

---

## 已弃用 → 更好的方法

| 已弃用 | 更好的方法 |
|--------|-----------|
| 基于索引的循环 | `.iter()`、`.enumerate()` |
| 收集到 `Vec<_>()` 然后迭代 | 链接迭代器 |
| 手动 `unsafe` 细胞 | `Cell`、`RefCell` |
| 用 `mem::transmute` 进行类型转换 | `as` 或 `TryFrom` |
| 自定义链表 | `Vec`、`VecDeque` |
| `lazy_static!` | `std::sync::OnceLock` |

## 快速审查清单

- [ ] 没有 `.clone()` 而没有正当理由
- [ ] 库代码中没有 `.unwrap()` 
- [ ] 没有 `pub` 字段且存在不变性
- [ ] 没有迭代器可用时不用索引循环
- [ ] 没有 `String` 而用 `&str` 足够
- [ ] 没有忽略 `#[must_use]` 警告
- [ ] 没有 `unsafe` 而没有 SAFETY 注释
- [ ] 没有巨大的函数（>50 行）
