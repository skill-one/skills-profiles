# 生态集成

> **第二层：设计选择**

## 核心问题

**这个任务应该使用哪个 crate，以及如何集成？**

在添加依赖之前：
- 是否有标准解决方案？
- 维护状态如何？
- API 稳定性如何？

---

## 集成决策 → 实现

| 需求 | 选择 | crates |
|------|--------|--------|
| 序列化 | 基于派生的 | serde, serde_json |
| 异步运行时 | tokio 或 async-std | tokio（最受欢迎） |
| HTTP 客户端 | 简便易用 | reqwest |
| HTTP 服务器 | 现代 | axum, actix-web |
| 数据库 | SQL 或 ORM | sqlx, diesel |
| CLI 解析 | 基于派生的 | clap |
| 错误处理 | 应用 vs 库 | anyhow, thiserror |
| 日志记录 | 外观层 | tracing, log |

---

## 思考提示

在添加依赖之前：

1. **维护得是否良好？**
   - 最近是否有提交？
   - 是否积极响应问题？
   - 是否频繁出现破坏性变更？

2. **范围是什么？**
   - 需要整个 crate 还是仅某个特性？
   - 特性标志能否减少冗余？

3. **如何集成？**
   - 基于特质还是具体类型？
   - 同步还是异步？
   - 需要哪些约束？

## 快速参考

### 语言互操作

| 集成 | Crate/工具 | 用例 |
|-------------|------------|----------|
| C/C++ → Rust | `bindgen` | 自动生成绑定 |
| Rust → C | `cbindgen` | 导出 C 头文件 |
| Python ↔ Rust | `pyo3` | Python 扩展 |
| Node.js ↔ Rust | `napi-rs` | Node 拓展 |
| WebAssembly | `wasm-bindgen` | 浏览器/WASI |

### Cargo 特性

| 特性 | 目的 |
|---------|---------|
| `[features]` | 可选功能 |
| `default = [...]` | 默认特性 |
| `feature = "serde"` | 条件依赖 |
| `[workspace]` | 多 crate 项目 |

## 错误代码参考

| 错误 | 原因 | 修复 |
|-------|-------|-----|
| E0433 | 找不到 crate | 添加到 Cargo.toml |
| E0603 | 私有项 | 检查 crate 文档 |
| 特性未启用 | 可选特性 | 在 `features` 中启用 |
| 版本冲突 | 不兼容的依赖 | `cargo update` 或固定版本 |
| 重复类型 | 不同 crate 版本 | 在工作区中统一 |

## crate 选择标准

| 标准 | 良好迹象 | 警告迹象 |
|-----------|-----------|--------------|
| 维护 | 最近提交 | 多年未活跃 |
| 社区 | 积极的问题/PR | 无响应 |
| 文档 | 示例、API 文档 | 最少文档 |
| 稳定性 | 语义版本控制 | 频繁破坏性变更 |
| 依赖 | 最少、知名 | 重量级、晦涩 |

---

## 反模式

| 反模式 | 为什么不好 | 更好 |
|--------------|---------|--------|
| `extern crate` | 过时（2018+之后） | 直接 `use` |
| `#[macro_use]` | 全局污染 | 显式导入 |
| 通配符依赖 `*` | 预测性差 | 特定版本 |
| 依赖过多 | 供应链风险 | 评估必要性 |
| 一切封装 | 维护负担 | 信任 crates.io |
