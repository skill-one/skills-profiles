# 元认知并行分析（实验性）

> **状态：** 实验性 | **版本：** 0.2.0 | **最后更新：** 2025-01-27
>
> 此技能测试三层并行认知分析。

## 概念

与顺序分析不同，此技能启动三个并行分析器——每个认知层一个——然后综合其结果。

```
用户问题
     │
     ▼
┌─────────────────────────────────────────────────────┐
│            元认知并行                   │
│                  (协调器)                       │
└─────────────────────────────────────────────────────┘
     │
     ├─── 第一层 ──► 语言机制 ──► L1 结果
     │
     ├─── 第二层 ──► 设计选择     ──► L2 结果
     │                                            ├── 并行（代理模式）
     │                                            │   或顺序（内联）
     └─── 第三层 ──► 领域约束 ──► L3 结果
     │
     ▼
┌─────────────────────────────────────────────────────┐
│              跨层综合                   │
│         (在主上下文中结合所有结果)          │
└─────────────────────────────────────────────────────┘
     │
     ▼
领域正确的架构解决方案
```

## 使用方法

```
/meta-parallel <你的 Rust 问题>
```

**示例：**
```
/meta-parallel 我的交易系统报 E0382 错误，应该用 clone 吗？
```

## 执行模式检测

**关键：** 首先检查代理文件是否存在，以确定执行模式。

尝试读取层分析器文件：
- `../../agents/layer1-analyzer.md`
- `../../agents/layer2-analyzer.md`
- `../../agents/layer3-analyzer.md`

---

## 代理模式（插件安装）- 并行执行

**当 `../../agents/` 目录下所有层分析器文件都存在时：**

### 第一步：解析用户查询

从 `$ARGUMENTS` 中提取：
- 原始问题
- 任何代码片段
- 领域提示（交易、Web、嵌入式等）

### 第二步：启动三个并行代理

**关键：** 在单个消息中启动所有三个任务以启用并行执行。

```
读取代理文件，然后并行启动：

Task(
  subagent_type: "通用",
  run_in_background: true,
  prompt: <../../agents/layer1-analyzer.md 的内容>
          + "\n\n## 用户查询\n" + $ARGUMENTS
)

Task(
  subagent_type: "通用",
  run_in_background: true,
  prompt: <../../agents/layer2-analyzer.md 的内容>
          + "\n\n## 用户查询\n" + $ARGUMENTS
)

Task(
  subagent_type: "通用",
  run_in_background: true,
  prompt: <../../agents/layer3-analyzer.md 的内容>
          + "\n\n## 用户查询\n" + $ARGUMENTS
)
```

### 第三步：收集结果

等待所有三个代理完成。每个代理返回结构化分析结果。

### 第四步：跨层综合

使用所有三个结果，按照以下模板执行综合。

---

## 内联模式（仅技能安装）- 顺序执行

**当层分析器文件不存在时，直接执行分析：**

### 第一步：解析用户查询

与代理模式相同——从 `$ARGUMENTS` 中提取问题、代码和领域提示。

### 第二步：执行第一层 - 语言机制

分析涉及的 Rust 语言机制：

```markdown
## 第一层：语言机制

**识别的错误/模式：**
- 错误代码：E0XXX（如果适用）
- 模式：所有权/借用/生命周期等

**根本原因：**
[解释此错误在 Rust 所有权模型中的原因]

**语言级解决方案：**
1. [解决方案 1]：描述
2. [解决方案 2]：描述

**置信度：** 高 | 中 | 低
**推理：** [为什么是这个置信度]
```

**关注领域：**
- 所有权规则（移动、复制、借用）
- 生命周期注解
- 借用规则（共享 vs 可变）
- 错误代码及其含义

### 第三步：执行第二层 - 设计选择

分析设计模式和权衡：

```markdown
## 第二层：设计选择

**设计模式上下文：**
- 当前方法：[使用什么模式]
- 问题：[为什么它与 Rust 规则冲突]

**设计替代方案：**
| 模式 | 优点 | 缺点 | 何时使用 |
|------|------|------|---------|
| 模式 A | ... | ... | ... |
| 模式 B | ... | ... | ... |

**推荐模式：**
[哪个模式最合适及其原因]

**置信度：** 高 | 中 | 低
**推理：** [为什么是这个置信度]
```

**关注领域：**
- 智能指针选择（Box、Rc、Arc）
- 内部可变模式（Cell、RefCell、Mutex）
- 所有权转移 vs 共享
- 克隆 vs 引用

### 第四步：执行第三层 - 领域约束

分析领域特定要求：

```markdown
## 第三层：领域约束

**识别的领域：** [交易/金融科技 | Web | CLI | 嵌入式 | 等]

**领域特定要求：**
- [ ] 性能：[要求]
- [ ] 安全性：[要求]
- [ ] 并发：[要求]
- [ ] 可审计性：[要求]

**领域最佳实践：**
1. [最佳实践 1]
2. [最佳实践 2]

**解决方案的约束：**
- 必须：[硬性要求]
- 应该：[软性要求]
- 避免：[该领域的反模式]

**置信度：** 高 | 中 | 低
**推理：** [为什么是这个置信度]
```

**关注领域：**
- 行业要求（金融科技法规、Web 可扩展性等）
- 性能约束
- 安全性和正确性要求
- 该领域常见模式

### 第五步：跨层综合

结合所有三个层：

```markdown
## 跨层综合

### 层结果摘要

| 层 | 关键发现 | 置信度 |
|---|----------|--------|
| L1（机制） | [摘要] | [级别] |
| L2（设计） | [摘要] | [级别] |
| L3（领域） | [摘要] | [级别] |

### 跨层推理

1. **L3 → L2：** [领域约束如何影响设计选择]
2. **L2 → L1：** [设计选择如何决定机制]
3. **L1 ← L3：** [直接领域对语言特性的影响]

### 综合建议

**问题：** [结合完整上下文重述]

**解决方案：** [领域正确的架构解决方案]

**理由：**
- 领域要求：[L3 约束]
- 设计模式：[L2 模式]
- 机制：[L1 实现]

### 置信度评估

- **总体：** 高 | 中 | 低
- **限制因素：** [哪个层置信度最低]
```

## 测试场景

### 测试 1：交易系统 E0382
```
/meta-parallel 交易系统报 E0382，trade record 被 move 了
```

预期：L3 识别金融科技约束 → L2 建议共享不可变 → L1 推荐Arc<T>

### 测试 2：Web API 并发
```
/meta-parallel Web API 中多个 handler 需要共享数据库连接池
```

预期：L3 识别 Web 约束 → L2 建议连接池 → L1 推荐Arc<Pool>

### 测试 3：CLI 工具配置
```
/meta-parallel CLI 工具如何处理配置文件和命令行参数的优先级
```

预期：L3 识别 CLI 约束 → L2 建议配置优先级模式 → L1 推荐构建者模式

## 错误处理

| 错误 | 原因 | 解决方案 |
|------|------|---------|
| 代理文件未找到 | 仅技能安装 | 使用内联模式（顺序） |
| 代理超时 | 复杂分析 | 等待更长时间或使用内联模式 |
| 层结果不完整 | 代理问题 | 使用内联分析填充 |

## 限制

- **代理模式：** 并行执行，更快但需要插件安装
- **内联模式：** 顺序执行，较慢但任何地方都可用
- 跨层综合质量取决于结果结构
- 可能比简单单层分析有更高的延迟
