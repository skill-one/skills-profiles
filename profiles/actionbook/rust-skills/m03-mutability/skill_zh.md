# 可变性

> **第一层：语言机制**

## 核心问题

**为什么这些数据需要改变，谁可以改变它们？**

在添加内部可变性之前，请理解：
- 变更是必要的还是偶然的复杂性？
- 谁应该控制变更？
- 变更模式是否安全？

---

## 思考提示

在添加可变性之前：

1. **变更是否必要？**
   - 可能通过转换 → 返回新值
   - 可能使用构建器 → 不可变地构建

2. **谁控制变更？**
   - 外部调用者 → `&mut T`
   - 内部逻辑 → 内部可变性
   - 并发访问 → 同步可变性

3. **线程上下文是什么？**
   - 单线程 → Cell/RefCell
   - 多线程 → Mutex/RwLock/Atomic

## 向下追溯 ↓

从设计到实现：

```
"需要从 &self 获取可变访问"
    ↓ T: Copy → Cell<T>
    ↓ T: !Copy → RefCell<T>

"需要线程安全的可变"
    ↓ 简单计数器 → AtomicXxx
    ↓ 复杂数据 → Mutex<T> 或 RwLock<T>

"需要共享的可变状态"
    ↓ 单线程：Rc<RefCell<T>>
    ↓ 多线程：Arc<Mutex<T>>
```

---

## 借用规则

```
任何时候，你只能拥有以下之一：
├─ 多个 &T (不可变借用)
└─ 或一个 &mut T (可变借用)

不能同时两者。
```

## 快速参考

| 模式 | 线程安全 | 运行时成本 | 使用场景 |
|------|----------|------------|----------|
| `&mut T` | N/A | 零 | 独占可变访问 |
| `Cell<T>` | 否 | 零 | 复制类型，无需引用 |
| `RefCell<T>` | 否 | 运行时检查 | 非复制类型，需要运行时借用 |
| `Mutex<T>` | 是 | 锁竞争 | 线程安全变更 |
| `RwLock<T>` | 是 | 锁竞争 | 多读者，少写者 |
| `Atomic*` | 是 | 最小 | 简单类型 (bool, usize) |

## 内部可变性决策

| 场景 | 选择 |
|------|------|
| T: Copy, 单线程 | `Cell<T>` |
| T: !Copy, 单线程 | `RefCell<T>` |
| T: Copy, 多线程 | `AtomicXxx` |
| T: !Copy, 多线程 | `Mutex<T>` 或 `RwLock<T>` |
| 读取密集型，多线程 | `RwLock<T>` |
| 简单标志/计数器 | `AtomicBool`, `AtomicUsize` |

---

## 反模式

| 反模式 | 为什么不好 | 更好的方式 |
|--------|------------|------------|
| 所处 RefCell | 运行时恐慌 | 清晰的所有权设计 |
| 单线程使用 Mutex | 不必要的开销 | RefCell |
| 忽略 RefCell 恐慌 | 难以调试 | 处理或重构 |
| 热循环内加锁 | 性能杀手 | 批量操作 |
