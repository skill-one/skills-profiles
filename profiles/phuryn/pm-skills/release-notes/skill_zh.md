## 版本说明生成器

将技术工单、产品需求文档（PRD）或内部变更日志转换为精炼、面向用户的产品版本说明。

### 背景

您正在为 **$ARGUMENTS** 编写版本说明。

如果用户提供了文件（JIRA 导出、Linear 工单、PRD、Git 日志或内部变更日志），请先阅读它们。如果他们提到产品 URL，请使用网络搜索来了解产品和目标受众。

### 指导步骤

1. **收集原始材料**：阅读所有提供的工单、变更日志或描述。提取：
   - 发生了什么变更（功能、改进或修复）
   - 影响哪些用户群体
   - 为什么这很重要（用户收益）

2. **对变更进行分类**：
   - **新功能**：全新的功能
   - **改进**：现有功能的增强
   - **错误修复**：已解决的问题
   - **不兼容变更**：需要用户操作的任何内容（迁移、API 变更）
   - **弃用**：即将停止支持的功能

3. **按照以下原则编写每个条目**：
   - 以用户收益为开头，而不是技术变更
   - 使用平实语言——避免行话、内部代号或工单编号
   - 每个条目保持 1-3 句话
   - 如果用户提供了，包含视觉元素或截图

   **示例转换**：
   - 技术："为仪表板 API 端点实现了 Redis 缓存层"
   - 用户界面："仪表板现在加载速度提升 3 倍，让您花更少时间等待，花更多时间分析。"

   - 技术："修复了并发结账流程中的竞态条件"
   - 用户界面："修复了在高流量期间某些订单可能失败的问题。"

4. **组织版本说明结构**：

   ```
   # [产品名称] — [版本 / 日期]

   ## 新功能
   - **[功能名称]**：[1-2 句话描述其作用和重要性]

   ## 改进
   - **[领域]**：[哪些方面得到了改善以及如何帮助用户]

   ## 错误修复
   - 修复了 [用用户术语描述的问题]

   ## 不兼容变更（如有）
   - **需要操作**：[用户需要做什么]
   ```

5. **调整语气**以匹配产品的声音——B2B 产品适合专业语气，消费级产品适合友好语气，API 产品适合开发者焦点。

保存为 Markdown 文档。如果用户希望 HTML 或其他格式，相应转换。
