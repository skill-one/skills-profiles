# 运输文物：使 AI 构建的代码可审查的文档

## 目的

AI 代理编写代码速度快，但它们不会留下关于*意图*的持久记录——系统应该做什么、谁被允许做什么、秘密在哪里、哪些规则实际上得到了验证。没有这些记录，任何人类（以及任何审计代理）都无法判断代码是否安全可运。这项技能定义了恢复审查性的少量文档。

这些文档位于仓库根目录下的 `documentation/` 中，它们是为两个读者编写的：人类审查者和下一个 AI 编码代理。它们是每个后续审计的**预期状态**的一半——安全或性能审查的效果取决于其能够与代码进行比较的意图。

## 该文档集的组织方式

该文档集**不是**一个固定列表——它是一个小的**核心**加上**条件性**文档，只有在功能存在时才添加。

- **核心文档**——每个可审查的应用程序都有这些界面，因此始终生成它们。
- **条件性文档**——只有当应用程序实际具有该功能时才包含一个。如果没有，请在 `architecture.md` 中写一行（“没有计划的工作——没有 `cron.md`。”），而不是编造一个空文档。审查性来自于诚实的地图，而“我们不做 X”是地图的一部分。
- 大多数文档是通过 `/document-app` 从代码反向工程得到的。唯一的例外是 `tests.md`，它是由 `/derive-tests` 从其他文档*派生*的——它是验证地图，而不是子系统描述。

在不过分恐慌的情况下，诚实地描述当前状态。这项工作的目标是准确的地图，而不是清洁的健康证明。每个文档都很简短，以表格和项目符号为主，并跳过通用理论。

## 核心文档

每个条目：文件 · 一行目的 · 它必须捕获的内容 · 审查者如何使用它。

1. **`architecture.md`** — 系统是什么以及它是如何组合在一起的。
   - 必须捕获：产品概述 + 关键假设；技术栈；认证/会话/声明端到端的流程；信任边界（例如服务角色与客户端）；一个简短的**已知风险/假设**列表（每个条目都有代码中显示的位置作为依据，而不是通用的检查表）；一个“相关文档”索引，列出所有生成的其他文档。
   - 审查者使用：根文档——其他所有内容都从此处交叉引用。

2. **`flows.md`** — 权限和副作用实际被执行的旅程。
   - 必须捕获：每个承重流程作为角色 + 前置条件 + 成功结果；跨 UI → 服务器 → 数据 → 任务 → 提供商 → 代理的逐步序列；每个受保护步骤的**认证检查**（哪个声明/角色/范围，在哪个资源上，以及预期的*拒绝*情况）；**信任边界跨越**（浏览器→服务器，服务器→提供商，任务→应用程序，代理→工具，webhook→应用程序）；每个步骤引起的状态变化和副作用（写入，邮件排队，任务触发，出站调用）。
   - 审查者使用：静态 `permissions.md` 矩阵无法显示的运行时视图——*在哪里*以及*按什么顺序*执行认证，以及可以跳过的地方。
   - **反 PRD 规则**：不接触权限、数据完整性、外部副作用、金钱、隐私或操作安全的流程不属于这里。这是一个安全/操作地图，而不是功能规范。

3. **`permissions.md`** — 谁被允许做什么。
   - 必须捕获：角色/声明；范围如何派生（令牌与数据库）；资源 × 操作 × 角色矩阵；哪些表具有行级安全，哪些依赖于代码强制检查。
   - 审查者使用：访问控制审计与代码进行比较的基线。`flows.md` 显示它在运行中；这是静态参考。

4. **`variables.md`** — 配置和秘密，映射到风险。
   - 必须捕获：一个名称 · 使用者 · 范围（服务器/客户端） · 来源 · 旋转 · 风险的表格；明确确认没有秘密捆绑在客户端；预上线检查清单。
   - 审查者使用：秘密/PII 泄露表面和事件响应期间的旋转计划。

5. **`tests.md`** — 验证地图：哪些记录的规则实际上被检查，哪些只是提议的，哪些没有被检查。
   - 必须捕获，分为三个清晰分隔的部分，以防止地图错误地显示绿色：
     - **现有覆盖率** — 仓库中*今天*的测试，每个都与它固定的规则相关联（因此地图反映现实，而不是愿望清单）。
     - **提议的测试** — 尚未编写的推荐案例，标记为**测试类型**（自动化的单元/集成 · 受保护的实时 · 手动审查）。
     - **差距** — 没有任何验证的记录，按跨越它们暴露的内容进行排名。
   - 每行包含：用例 → 规则 → 预期行为（包括拒绝/负面情况） → 证据来源（文档 + 代码） → 状态（现有 / 提议 / 无）。它还注明哪些检查需要 CI 并阻止合并到 `main`。
   - 审查者使用： “记录 == 实现” 的操作形式——它显示其他文档声称的每个规则是否今天实际上由一个测试固定，只是提议的，还是未验证的。
   - 由 `/derive-tests` 生成（不是 `/document-app`），因为它是从其他文档和现有的测试套件派生出来的，而不是从子系统读取的。

## 条件性文档（只有在功能存在时才包含）

6. **`emails.md`** — 系统发送的每个通知。*只有在应用程序发送事务性或自动邮件时才包含。*
   - 必须捕获：队列 → 处理器 → 提供商路径；模板及其接受的变量；重试/退避行为；发送失败时在哪里查找。
   - 审查者使用：发现未验证的模板输入和 PII 暴露边界。

7. **`cron.md`** — 所有计划工作和如何安全地操作它。*只有在存在计划或后台任务时才包含。*
   - 必须捕获：一个清单表（任务 → 计划 → 函数 → 秘密 → 限制 → 重试）；每个任务如何保持幂等性；内部调用如何认证；在哪里查看最后运行。
   - 审查者使用：发现可伪造的触发器和无界后台任务。

8. **`seo.md`** — 单页应用程序如何处理 SEO 和社交预览。*只有在存在公共/可索引或机器人面对的路由时才包含。*
   - 必须捕获：预览方法（静态元数据 / 预渲染 / 边缘 HTML）；路由 → 需要 SEO → 公共数据仅表格；如何清理动态元数据；机器人 vs 人类路由。
   - 审查者使用：捕获公共数据仅违规和机器人路由上的元数据注入。

9. **`automation.md`** — 嵌入代理和其他自动化路径。*只有在应用程序嵌入 AI 代理、LLM 工作流、工具调用、webhook 或外部自动化时才包含。*
   - 必须捕获，每个自动化/代理：触发 + 所有者 + 它是否自动运行或仅在批准后运行；它可以读取的输入以及它可能调用的**确切工具/API**（工具表面本身就是一个硬护栏）；**转向**在哪里（提示）与**非提示硬护栏**在哪里；回到应用程序的**输出合同**（模式、验证、失败处理）；**应用程序拥有的副作用 vs 代理拥有的建议**；以及控制——批准门、审计/时间线日志记录、速率限制、重试、关闭开关。
   - 审查者使用：使隐藏的自动化路径可见，并划清代理*提议*与应用程序*强制*之间的界限——现代 AI 构建应用程序中风险最高的表面。

## 注意事项

- 每个生成的文档都在 `architecture.md` 下的“相关文档”部分添加了对自身的引用，以便该文档集保持可发现性。
- 跳过任何不相关的条件性文档，并在一行中说明，而不是编造内容。
- 不要在这些文档中包含示例和完成的模板——它们描述的是*此系统*，而不是通用方法。
- 代理操作上下文文件（`CLAUDE.md` / `AGENTS.md`）是一个*不同的*工件——从这些文档派生的指令，而不是系统文档。它在交接步骤由 `/ship-check` 生成，而不是在这里。
- `tests.md` 由 `/derive-tests` 生成；其余文档由 `/document-app` 生成。
- 不要包含“更新日期”行；文件的版本历史记录是真相来源。
