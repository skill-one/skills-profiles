# antislop-code

> Anti Slop: AI 编码代理的规则。代码注释技能

> antislop 系统的一部分。与 `antislop.md`（核心）一起阅读。此技能过滤掉那些读起来像通用 AI（装饰性、重复显而易见的内容、生硬、大声）的注释，同时保留那些包含真实信息的注释。它通过编号引用核心规则，并且从不重复或重新编号它们。当任务编写或编辑代码注释时加载它。

## 如何使用此技能

- 每当任务涉及代码注释时，都与 `antislop.md` 一起加载。核心包含机制（目的测试、三个层级、交付门）；此技能包含注释特定的深度。
- 每个条目都有相同的结构：**说明**（模式）、**原因**（为什么它看起来像废话）、**修复**（应该怎么做），并引用作为 R-XX 的管理核心规则。
- **范围护栏**：此技能仅修改注释。永远不要修改可执行代码、标识符、导入、格式、缩进、空白、控制流或逻辑。如有疑问，请保持代码不变。
- 核心中的交付门仍然是门。此文件末尾的“代码注释检查清单”是作为其补充运行的注释特定补充。

## 添加无信息的注释

### 装饰性分隔符

- **说明**：由重复字符、ALL CAPS 标签或围绕部分名称的框绘制构建的横幅注释：`// =======================` 围绕 `Authentication`、`// -------- WORKFLOW --------` 或 `/* ---- ROUTES ---- */` 标头。
- **原因**：装饰就是信息。用 `=` 或 `-` 包裹的标签表示“AI 制作了这个”，而没有添加信息，ALL CAPS 读起来像喊叫。
- **修复**：用单行替换，如果标签无信息则完全删除（R-31）。

### 重复显而易见的内容

- **说明**：重复下一行或声明已经显示的内容的注释，例如 `// 初始化变量` 在 `let count = 0` 之上、`// 用户类` 在 `class User {}` 之上、`// 验证用户` 在 `function validateUser()` 之上，或 `const userAge = 25; // 用户年龄是 25`。
- **原因**：它使阅读负担加倍而不添加任何信息。代码已经说明了；注释只是重复它。
- **修复**：删除并保留代码行。

### 工作流叙述

- **说明**：逐步叙述流程的注释，例如 `// 第一步：验证输入`、`// 第二步：处理请求`、`// 第三步：返回响应`，或 `// 首先...`、`// 下一步...`、`// 最后...`。
- **原因**：控制流本身在代码中可见。编号它像清单而不是解释。
- **修复**：删除。如果流程确实难以理解，那是一个结构问题，而不是缺少注释的问题。

### 空标签

- **说明**：没有信息在后面的通用标签：`// 主逻辑`、`// 核心逻辑`、`// 业务逻辑`、`// 辅助函数`、`// 入口点`、`// 错误处理`，或 `// 注意：这很重要。` / `// 重要：请阅读。`
- **原因**：标签命名一个类别，而不是一个事实。“主逻辑”告诉读者他们无法从代码中推断出的任何信息。
- **修复**：除非标签包含特定信息，否则删除。`"Note: retries happen only on 5xx"` 值得保留；`"Note: this is important"` 不值得。

### 模糊占位符

- **说明**：承诺未来工作但不说明什么的注释：`// TODO: Improve this`、`// Future improvements`、`// Additional optimization can be added here`、`// Add more validation`。
- **原因**：模糊的 TODO 是噪音。它命名一种感觉（这可以更好），而不是一个任务（做什么，为什么）。
- **修复**：删除。只有当它命名一个特定任务并具有足够的上下文来执行时，才保留 TODO。

### 签名回声

- **说明**：只重复签名的文档，例如一个 JSDoc 块重复 `@param price The price.` 和 `@returns Total price.` 对于一个其名称和参数已经说明了一切的函数。
- **原因**：回声签名增加长度，而不是理解。读者不会学到任何新东西。
- **修复**：简化或删除回声。保留解释业务规则、边缘情况、假设、算法、限制、副作用、API 行为或安全影响的文档。永远不要删除真实的文档。

### 装饰性 Emoji

- **说明**：在注释中用作装饰的 Emoji，例如 `// ✅ Validation` 或 `// 🚀 Performance`。
- **原因**：Emoji 是代码中的视觉噪音，特定的 Emoji 集（✅、🚀、🔒）是 AI 默认词汇表。
- **修复**：用 plain English 替换，如果标签无信息则删除。

### 结束标记

- **说明**：仅标记块结束的注释，例如 `} // end if`、`# End of function` 或 `// End processOrder`。
- **原因**：关闭大括号已经结束块。标记是出于习惯而不是需要。
- **修复**：删除。在罕见的情况下，结束标记确实有助于长文件，仅在其防止混淆时保留，而不是作为习惯。

## 它应该读起来像什么

### 过度解释的注释

- **说明**：一个运行多行的注释，围绕一个适合一行的事实堆叠原因、上下文和历史：一个四行块解释一个桩位于 PATH 上，哪个发布引入了工作区，以及之前什么被破坏了。每一句话都是真的。长度是关键。
- **原因**：一个人留下笔记，一个生成器写案例。将一个一行的事实填充到一个段落中，构建一个“因为 X，所以 Y，因此 Z”链，或引用问题编号和修复它的版本，与任何其他 AI 模式一样，它们埋葬了重要的一行在那些不重要的行下面。
- **修复**：仅保留约束：一行，最多两行，永远不会三行。保留平台陷阱、静默失败、协议规则、性能成本。丢弃问题编号、版本历史和推理链。

### 行行解释

- **说明**：每个琐碎声明上的注释，逐行解释：`// 初始化 count`，然后 `// 循环项目`，然后 `// 获取项目`，然后 `// 增加`，然后 `// 返回结果`。
- **原因**：当每行都注释时，没有注释有意义。读者必须检查每一行才能找到包含意义的注释。
- **修复**：用一行注释每个逻辑块，而不是每行一个注释。如果块不需要注释，就不写注释。

### 生硬或大声的措辞

- **说明**：听起来正式、长或喊叫的注释：“这个函数负责在继续进行身份验证过程之前验证提供的凭证是否有效”，或 `// MAIN LOGIC` 在大写中。
- **原因**：正式和大声的措辞读起来像生成，而不是像工程师为下一个人留下的笔记。
- **修复**：用自然开发者的声音写短、句尾的行：`// 验证凭证后再发放令牌。` 好的注释解释原因，而不是什么，并且保持简短。

## 不是禁止（保留这些）

永远不要删除解释：

- 业务逻辑和意图
- 架构决策
- 安全考虑
- 性能权衡
- 并发行为
- 协议细节
- API 合同
- 工作区
- 边缘情况和假设
- 许可证和法律声明

必须保留的示例：

```js
// Stripe 可能会重试最多三天的 webhook 交付。
// 使用事件 ID 忽略重复事件。
```

注释只有在它解释代码已经显示的内容之外的东西时才值得保留：原因、约束、非明显行为。

保留意味着什么可能保留，而不是多长时间可能运行。一个工作区注释是一行关于工作区，而不是关于它的段落。上面的示例是两行，因为两个事实是真的，不是因为两行是一个目标。这个列表是最常见的评论在它不应该通过审查的原因：内容确实有价值，所以长度不受审查。价值不是长度。

## 代码注释检查清单

当任务涉及注释时，与核心交付门一起运行。所有答案必须是 **是**：

- [ ] 每个注释都添加代码已经显示的信息之外的信息吗？(R-31)
- [ ] 注释避免装饰性分隔符、ALL CAPS 横幅和框绘制的标题？
- [ ] 注释避免重复明显的行、声明或签名？
- [ ] 注释避免逐步工作流叙述？
- [ ] 注释避免空标签和命名无任务的模糊 TODO？
- [ ] 注释避免装饰性 Emoji 和结束标记？
- [ ] 注释密度是一行每个逻辑块，而不是每行一个？
- [ ] 每个注释是一行，只有当第二行携带新事实时才是两行？
- [ ] 剩余的注释读起来简短、自然、句尾？
- [ ] 范围护栏是否遵守：仅修改注释，代码未修改？
