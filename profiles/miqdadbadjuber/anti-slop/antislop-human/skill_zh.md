# antislop-human

> Anti Slop: AI 编码代理的规则。人类技能

> antislop 系统的一部分。与 `antislop.md`（核心）一起阅读。此技能深入探讨人类关注的问题：界面必须对不同视力、双手和设置的人保持可用性。对比度、键盘、焦点、状态以及排除人的移动细节。

## 如何使用此技能

- 在构建或编辑界面时，与 `antislop.md` 一起加载。核心包含机制（目的测试、三个层级、交付门）；此技能包含人类方面的深度：排除不同视力、双手和设置的人的界面部分。
- 每个条目都具有相同的结构：**说明**（模式）、**原因**（谁被排除，以及为什么它看起来不完整）、**修复**（应该做什么），核心规则作为 R-XX 引用。
- 可访问性不是一个在最后附加的额外清单。它是“界面保持稳定”的核心承诺的一部分（C-4）。核心中的交付门仍然是门；此文件末尾的“人类技能清单”是与其一起运行的补充。
- 对比度检查器（公式 + 参考表 + 脚本）位于此技能中。用于您无法通过肉眼验证的每个颜色组合。
- 此技能仅保留排除人的移动细节：缩放和屏幕键盘。

## 颜色与对比度

### 低对比度文本

- **说明：** 浅灰色文本在白色或接近白色的背景上，细正文，选择看起来“优雅”但难以阅读的柔和标签。
- **原因：** 它排除了低视力用户和所有在明亮光线下的用户。这是一个没有检查标准的视觉选择，这正是过滤器存在的原因来捕获这种默认值。
- **修复：** 满足 WCAG AA 最小值（R-25）：普通文本 4.5:1，大文本（18px+） 3:1。计算比率；不要凭肉眼判断。

### 文本在照片或渐变上

- **说明：** 白色文本直接放置在光线较亮区域的图像或渐变上，仅在明亮点进行检查。
- **原因：** 对比度是局部的。如果图像较亮，即使英雄仍然“看起来”不错，文本也会低于 4.5:1。R-25 要求测试文本覆盖的整个区域，而不是单个点。
- **修复：** 在文本后面添加遮罩或实色块，然后验证最差位置，而不是最佳位置。如果文本区域的任何部分失败，则处理失败。

### 灰色幻觉

- **说明：** “深灰色在黑色上”或“浅灰色在白色上”声称通过 AA 而无需计算。
- **原因：** 这是最常见的可访问性幻觉。眼睛高估了灰色对的对比度，代理重复这一说法是因为它听起来合理。#555555 在黑色上是 2.8:1。它失败了。
- **修复：** 不要断言配对通过。运行对比度检查器（下方）或应用公式。当两者都不可能时，使用参考表。

### 非文本对比度

- **说明：** 交互式组件（按钮、图标、输入边框、焦点指示器、图表段）与其背景的对比度小于 3:1。
- **原因：** 非文本 UI 通过形状和边缘传递信息。当边缘是一丝色调时，低视力用户无法找到控制。相同的条适用于悬停和选中等状态。
- **修复：** 每个组件边界和每个状态指示器与其相邻颜色具有 3:1 的比率（WCAG 1.4.11）。将图标与满足 4.5:1 的文本标签配对。

### 对比度检查器

对比度检查器的所在地。从最到最少方便的三层：

**脚本。** 当脚本运行时可用且文件存在时，运行它而不是手动计算。脚本随此技能的文件夹一起提供（`contrast-check.py`，与此 `SKILL.md` 在同一位置）。在 macOS 和 Linux 上使用 `python3`，在 Windows 上使用 `python` 运行它：

```bash
python3 "${CLAUDE_SKILL_DIR}/contrast-check.py" "#FFFFFF" "#777777"
# 普通文本：失败（4.48 < 4.5）
# 大文本：通过（4.48 >= 3.0）
```

如果 `${CLAUDE_SKILL_DIR}` 变量在此代理中不可用，请直接将脚本路径指向此技能的文件夹。脚本的存在是为了让代理停止幻觉 AA。它接受两个十六进制颜色并打印出两种文本大小的比率和判断。如果文件丢失，公式和下面的表是完整的。不要阻塞脚本。

**公式（WCAG 2.x）。**

1. 对比度比率 = (L1 + 0.05) / (L2 + 0.05)，其中 L1 是较亮的相对亮度，L2 是较暗的。
2. 一种颜色的相对亮度 L：将每个通道转换为 0-1（`c = hex / 255`），然后线性化：如果 `c <= 0.03928`，`c_lin = c / 12.92`；否则 `c_lin = ((c + 0.055) / 1.055)^2.4`。
3. `L = 0.2126*R + 0.7152*G + 0.0722*B`。
4. 将比率四舍五入为两位小数并比较：普通文本 4.5:1，大文本（18px+，根据 R-25）。最大比率是 21.0（黑色在白色上）。

**参考表**（常见组合，使用公式计算）：

| 组合（文本在背景上） | 比率 | 普通文本（4.5） | 大文本（3.0） |
|----------------------|------|-----------------|----------------|
| 黑色在白色上 | 21.00 | 通过 | 通过 |
| 白色在黑色上 | 21.00 | 通过 | 通过 |
| 白色在 #333333 上 | 12.63 | 通过 | 通过 |
| 白色在 #666666 上 | 5.74 | 通过 | 通过 |
| #777777 在白色上 | 4.48 | 失败 | 通过 |
| 白色在 #888888 上 | 3.54 | 失败 | 通过 |
| 白色在 #999999 上 | 2.85 | 失败 | 失败 |
| #555555 在黑色上 | 2.82 | 失败 | 失败 |

将表作为合理性检查阅读，而不是替代品。任何未列出的组合，或接近阈值的内容，都通过公式或脚本。

## 键盘

### 移除焦点轮廓

- **说明：** `outline: none` 或 `outline: 0`，没有替换焦点样式。
- **原因：** 键盘用户无法看到他们所在的位置。这是在不使用鼠标的情况下使界面无法使用的最快方法，并且 R-32 禁止这样做。
- **修复：** 保留或用满足相同对比度条（与其邻居 3:1）的可见 `:focus-visible` 样式替换轮廓。永远不要设置 `outline: none` 而没有替换。

### 仅鼠标模式

- **说明：** 仅在悬停时打开的菜单，点击打开但无法键盘打开的下拉菜单，没有键盘回退的拖放。
- **原因：** 每一个都排除了键盘和辅助技术用户（R-32）。如果控制无法通过 Tab、Enter 或 Space 访问和操作，它对很多人来说就不存在了。
- **修复：** 每个交互式元素都可以通过键盘访问和操作（R-32）：逻辑 Tab 顺序遵循视觉顺序，使用 Enter 或 Space 激活，并且对话框可通过 Escape 关闭（R-26）。

### 错误的 Tab 顺序

- **说明：** 焦点在页面上跳转，跳过内容，或落在隐藏元素上，因为 DOM 顺序与视觉顺序不匹配。
- **原因：** 读取代码顺序而不是视觉顺序的 Tab 顺序使导航不可预测（R-32）。用户会失去他们的位置，页面感觉是损坏的。
- **修复：** 保持源顺序与视觉顺序匹配，为长页面添加跳过链接，并且永远不要给真实内容 `tabindex="-1"`，除非它是受控焦点陷阱（如对话框）的一部分。

## 焦点与状态

### 弱或不可见的焦点指示器

- **说明：** 与背景相同颜色的焦点环，仅在悬停时出现，或比 1px 边框更薄的指示器。
- **原因：** 焦点指示器是键盘用户知道他们所在位置的方式。如果它未通过对比度条或仅在悬停时显示，则仅使用键盘的访问会中断（R-32, R-34）。
- **修复：** 每个交互式元素上都有可见的焦点指示器，与相邻颜色 3:1 的对比度，在您提供的每个主题中。在暗模式和亮模式下检查它。

### 仅颜色反馈

- **说明：** 仅通过颜色传达成功、错误和状态：红色错误文本，绿色成功边框，色调芯片，没有图标、标签或文本。
- **原因：** 它排除了色盲和低视力用户，并且在强制颜色模式下完全消失。依赖于看到色调的状态不是状态（C-4）。
- **修复：** 每个颜色信号都与文本、图标或图案配对。错误状态首先为文本：“密码必须至少 8 个字符”，而不是仅仅一个红色边框。

### 缺失 UI 状态

- **说明：** 数据视图没有空、加载或错误状态，或者存在但不可见：没有文本的旋转器，空屏幕没有解释。
- **原因：** R-27 要求三个状态；可访问性角度是每个都必须可感知和提供信息，而不是装饰性的。没有上下文的加载旋转器对屏幕阅读器用户来说像是一个冻结的页面。
- **修复：** 每个数据视图都有三个状态（R-27），每个都被宣布或可见：明确的空消息，带文本的加载状态，以及说明发生了什么以及如何操作的错误状态。

## 缩放与移动使用

移动（断点、缩放、网格、溢出、点击目标）的布局机制是 `antislop-layoutmobile` 的关注点。本节仅保留排除人的移动细节：缩放和屏幕键盘。

### 无法缩放的文本

- **说明：** 固定像素字体大小，或具有 `overflow: hidden` 的容器在 200% 缩放时剪切文本。
- **原因：** 用户必须能够调整文本大小（WCAG 1.4.4）。如果缩放到 200% 剪切内容或强制水平滚动，则文本实际上不可调整。
- **修复：** 流体类型随缩放重新流，文本上没有剪切容器，并在窄视口上验证 200% 缩放时的布局（R-35）。

### 移动键盘覆盖表单

- **说明：** 视口底部的输入被屏幕键盘隐藏，没有滚动到视图，也没有为输入留出空间。
- **原因：** 用户无法看到或达到的表单是他们无法完成的表单。这是一个移动唯一的排除（R-03）。
- **修复：** 当输入获得焦点时，它滚动到键盘上方，并留出足够的底部填充，以便焦点字段永远不会被覆盖。使用真实设备或模拟键盘进行测试。

## 人类技能清单

在涉及界面的任务中，与核心交付门一起运行这些。所有答案必须为 **是**：

- [ ] 每个文本和背景组合是否通过对比度检查器（公式、表或脚本）验证，包括文本在图像和渐变上？（R-25）
- [ ] 每个交互式组件边界和状态指示器是否满足其背景 3:1？（非文本对比度）
- [ ] 每个交互式元素是否都有可见、高对比度且在每个主题中都存在的焦点指示器？（R-32, R-34）
- [ ] 每个交互式元素是否都可以通过键盘访问和操作，对话框可通过 Escape 关闭，且没有 `outline: none` 而没有替换？（R-32, R-26）
- [ ] 每个数据视图的空、加载和错误状态是否存在且可感知，而不是仅通过颜色？（R-27, C-4）
- [ ] 文本是否可以缩放到 200% 而不被剪切，并且移动键盘是否永远不会覆盖焦点输入？（R-35）
