# 完成一个开发分支

## 概述

**核心原则：** 验证测试 → 检测环境 → 提供选项 → 执行选择 → 清理。

**开始时宣布：** "我正在使用完成开发分支的技巧来完成这项工作。"

## 第1步：验证测试

运行项目的完整测试套件（`npm test` / `cargo test` / `pytest` / `go test ./...`）。

**如果测试失败**，报告失败情况并停止——绿色套件后会出现菜单：

```
测试失败（<N>个失败）。必须修复才能完成：

[显示失败]
```

**如果测试通过：** 继续第2步。

## 第2步：检测环境

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# 现在捕获，仍然在工作区内部——第5步在清理（第6步）之前会改变目录
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

这决定了要显示哪个菜单以及清理方式：

| 状态 | 菜单 | 清理 |
|------|------|------|
| `GIT_DIR == GIT_COMMON`（普通仓库） | 标准3个选项 | 无需清理工作树 |
| `GIT_DIR != GIT_COMMON`，命名分支 | 标准3个选项 | 基于来源（见第6步） |
| `GIT_DIR != GIT_COMMON`，分离HEAD | 减少2个选项（无合并） | 外部管理——保留原样 |

## 第3步：确定基础分支

基础分支是这项工作分叉自的分支——通常在计划、对话或分支的上游中命名。如果尚未知道，询问："这个分支分叉自<你的最佳猜测>——这是正确的吗？" 在合并前确认：合并到错误的基础分支是昂贵的撤销操作。

## 第4步：提供选项

**普通仓库和命名分支工作树——提供正好这些3个选项：**

```
实现完成。你想做什么？

1. 本地合并到<基础分支>
2. 推送并创建拉取请求
3. 保持分支原样（我稍后会处理）

选择哪个选项？
```

**分离HEAD——提供正好这些2个选项：**

```
实现完成。你处于分离HEAD（外部管理的工作区）。

1. 推送为新分支并创建拉取请求
2. 保持原样（我稍后会处理）

选择哪个选项？
```

提供菜单时必须完全按照原文——简洁，且每个选项都来自上面的列表。丢弃工作只有在你的合作者明确要求时才会发生（见"如果你的合作者要求丢弃工作"）。等待他们的回答；集成决策是他们的。

## 第5步：执行选择

### 选项1：本地合并

```bash
# 获取主仓库根目录以确保当前目录安全
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# 首先合并——在移除任何东西之前验证成功
git checkout <基础分支>
git pull
git merge <功能分支>

# 验证合并结果的测试
<测试命令>
```

如果合并结果的测试失败：停止，保留工作树和分支原样，并调查——尚未推送，所以合并是本地的且可恢复。

一旦合并结果为绿色：清理工作树（第6步），然后删除分支：

```bash
git branch -d <功能分支>
```

### 选项2：推送并创建PR

```bash
git push -u origin <功能分支>
# 从分离HEAD开始，在远程上命名新分支：
# git push origin HEAD:refs/heads/<新分支>
```

然后使用Forge的工具创建针对<基础分支>的拉取/合并请求——如果提供CLI，则使用CLI，否则使用Forge在推送时打印的创建URL——遵循仓库的PR模板和约定（如果存在），并将URL报告给你的合作者。

保留工作树——你的合作者在其中迭代PR反馈。

### 选项3：保持原样

报告："保留分支<名称>。工作树保存在<路径>。"

### 如果你的合作者要求丢弃工作

这条路径仅作为响应明确要求丢弃工作而存在。首先确认：

```
这将永久删除：
- 分支 <名称>
- 所有提交：<提交列表>
- 工作树在 <路径>

输入'discard'以确认。
```

等待确切的确认。收到后：

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

然后清理工作树（第6步）并强制删除分支：

```bash
git branch -D <功能分支>
```

## 第6步：清理工作区

**适用于选项1和确认丢弃。** 选项2和3始终保留工作树。两个调用者已经切换到主仓库根目录——工作树移除必须从工作树外部运行——并使用在第2步捕获的`GIT_DIR`/`GIT_COMMON`/`WORKTREE_PATH`值，在改变目录之前。

**如果`GIT_DIR == GIT_COMMON`：** 普通仓库，无需清理工作树。完成。

**如果`WORKTREE_PATH`在`.worktrees/`或`worktrees/`下：** Superpowers创建了工作树——我们拥有清理权：

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # 自愈：清理任何过时的注册
```

**如果移除被拒绝**（`contains modified or untracked files`）：工作树包含其他地方不存在的文件——未提交的计划、笔记或草稿工作。切勿自行`--force`。向你的合作者展示风险并询问：

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
工作树移除被拒绝——这些文件从未提交：

<文件列表>

1. 在清理前将它们提交到<分支>
2. 将它们移到<主仓库根目录>
3. 删除它们（不可恢复）

选择？
```

执行选择，然后移除工作树。

**否则：** 主机环境拥有此工作区——保留原样。如果你的平台提供工作区退出工具，使用它。

## 快速参考

| 选项 | 合并 | 推送 | 保留工作树 | 清理分支 |
|------|------|------|------------|----------|
| 1. 本地合并 | 是 | - | - | 是 |
| 2. 创建PR | - | 是 | 是 | - |
| 3. 保持原样 | - | - | 是 | - |
| 丢弃（仅限明确请求） | - | - | - | 是（强制） |

## 常见理由

| 找借口 | 现实 |
|------|------|
| "测试会话开始时通过了" | 在你即将集成的树上运行测试套件。绿色运行仅证明它运行的树。 |
| "他们显然想合并" | 集成是你的合作者的决定。提供菜单并等待。 |
| "他们似乎对这个功能完成了——我提议丢弃它" | 菜单按原文编写。丢弃只有在你的合作者明确要求时才会发生。 |
| "'是的，丢弃它'算作确认" | 只有输入的单词`discard`才授权删除。 |
| "PR已经上传，所以工作树现在是杂乱的" | PR反馈会在该工作树中修复。它保留到工作完成。 |
| "这个其他工作树看起来过时了——我也会清理它" | 清理仅限于`.worktrees/`或`worktrees/`下的工作树。其他所有东西都属于主机。 |
| "移除被拒绝——`--force`只是完成清理" | 拒绝意味着该工作树中存在文件。`--force`永久销毁它们。向你的合作者展示并询问。 |
| "合并结果的失败可能是临时的" | 合并失败的测试会停止一切。分支和工作树保持原样，以便你调查。 |
| "基础分支显然是main" | 确认分叉点或询问。合并到错误的基础分支是昂贵的撤销操作。 |
| "推送被拒绝——强制推送会修复它" | 推送被拒绝意味着远程发生了变化。调查；仅在合作者明确请求时强制推送。 |
