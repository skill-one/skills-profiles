# 使用 Git Worktrees

## 概述

确保工作在隔离的工作空间中进行。优先使用平台的原生工作空间工具。仅在原生工具不可用时才回退到手动 git 工作空间。

**核心原则：** 首先检测现有隔离状态。然后使用原生工具。然后回退到 git。永远不要与沙盒对抗。

**在开始时宣布：** "我正在使用使用 git 工作空间技能来设置一个隔离的工作空间。"

## 第 0 步：检测现有隔离状态

**在创建任何东西之前，检查您是否已经在隔离的工作空间中。**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

**子模块保护：** `GIT_DIR != GIT_COMMON` 在 git 子模块中也成立。在得出"已经在工作空间"的结论之前，请验证您不在子模块中：

```bash
# 如果这返回一个路径，您在子模块中，而不是在工作空间 — 治理为普通仓库
git rev-parse --show-superproject-working-tree 2>/dev/null
```

**如果 `GIT_DIR != GIT_COMMON`（且不是子模块）：** 您已经在链接的工作空间中。跳到第 2 步（项目设置）。不要创建另一个工作空间。

报告分支状态：
- 在一个分支上： "已经在隔离工作空间中 `<路径>` 在分支 `<名称>`。"
- Detached HEAD： "已经在隔离工作空间中 `<路径>` (detached HEAD, 外部管理)。需要在完成时创建分支。"

**如果 `GIT_DIR == GIT_COMMON`（或在子模块中）：** 您在普通仓库检出到的目录。

用户是否已经在您的说明中指示了他们的工作空间偏好？如果没有，请在创建工作空间之前征求同意：

> "您希望我设置一个隔离的工作空间吗？它将保护您当前的分支免受更改。"

尊重任何现有的声明偏好，无需询问。如果用户拒绝同意，请就地工作并跳到第 2 步。

## 第 1 步：创建隔离工作空间

**您有两个机制。按此顺序尝试。**

### 1a. 原生工作空间工具（首选）

用户已经要求隔离工作空间（第 0 步同意）。您是否已经有创建工作空间的方法？它可能是一个名为 `EnterWorktree`、`WorktreeCreate` 的工具，一个 `/worktree` 命令，或一个 `--worktree` 标志。如果您有，请使用它并跳到第 2 步。

原生工具自动处理目录放置、分支创建和清理。当您有原生工具时使用 `git worktree add` 会导致您的沙盒无法看到或管理的幻影状态。

只有在您没有原生工作空间工具时才继续到第 1b 步。

### 1b. Git 工作空间回退

**仅在 1a 步不适用时使用** — 您没有原生工作空间工具。使用 git 手动创建工作空间。

#### 目录选择

按此优先级顺序操作。显式的用户偏好总是优先于观察到的文件系统状态。

1. **检查您的说明文件中是否有声明的偏好工作空间目录。** 如果用户已经指定了一个，请使用它而无需询问。

2. **检查是否存在现有的项目本地工作空间目录：**
   ```bash
   ls -d .worktrees 2>/dev/null     # 首选（隐藏）
   ls -d worktrees 2>/dev/null      # 替代方案
   ```
   如果找到，请使用它。如果两者都存在，`.worktrees` 优先。

3. **如果没有其他指导可用**，默认为项目根目录下的 `.worktrees/`。

#### 安全验证（仅限项目本地目录）

**必须验证目录被忽略后才能创建工作空间：**

```bash
git check-ignore -q .worktrees 2>/dev/null || git check-ignore -q worktrees 2>/dev/null
```

**如果不被忽略：** 添加到 .gitignore，提交更改，然后继续。

**为什么关键：** 防止意外将工作空间内容提交到仓库。

#### 创建工作空间

```bash
# 根据选择的位置确定路径
path="$LOCATION/$BRANCH_NAME"

git worktree add "$path" -b "$BRANCH_NAME"
cd "$path"
```

**沙盒回退：** 如果 `git worktree add` 因权限错误（沙盒拒绝）而失败，请告诉用户沙盒阻止了工作空间创建，您正在当前目录中工作。然后就地运行设置和基线测试。

## 第 2 步：项目设置

自动检测并运行适当的设置：

```bash
# Node.js
if [ -f package.json ]; then npm install; fi

# Rust
if [ -f Cargo.toml ]; then cargo build; fi

# Python
if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
if [ -f pyproject.toml ]; then poetry install; fi

# Go
if [ -f go.mod ]; then go mod download; fi
```

## 第 3 步：验证干净基线

运行测试以确保工作空间从干净状态开始：

```bash
# 使用项目适用的命令
npm test / cargo test / pytest / go test ./...
```

**如果测试失败：** 报告失败，询问是否继续或调查。

**如果测试通过：** 报告就绪。

### 报告

```
工作空间就绪于 <完整路径>
测试通过 (<N> 个测试，0 个失败)
准备实现 <功能名称>
```

## 快速参考

| 情况 | 操作 |
|------|------|
| 已经在链接工作空间中 | 跳过创建（第 0 步） |
| 在子模块中 | 治理为普通仓库（第 0 步保护） |
| 可用原生工作空间工具 | 使用它（第 1a 步） |
| 没有原生工具 | Git 工作空间回退（第 1b 步） |
| `.worktrees/` 存在 | 使用它（验证忽略） |
| `worktrees/` 存在 | 使用它（验证忽略） |
| 两者都存在 | 使用 `.worktrees/` |
| 两者都不存在 | 检查指令文件，然后默认 `.worktrees/` |
| 目录未被忽略 | 添加到 .gitignore + 提交 |
| 创建时权限错误 | 沙盒回退，就地工作 |
| 基线测试期间测试失败 | 报告失败 + 询问 |
| 没有 package.json/Cargo.toml | 跳过依赖安装 |

## 常见理由

| 找借口 | 真实情况 |
|--------|---------|
| "我显然不在工作空间中 — 无需检查" | 运行第 0 步。沙盒创建的隔离和子模块都会让肉眼判断产生误导；检测命令可以解决。 |
| "`git worktree add` 比寻找原生工具更快" | 原生工具（例如 `EnterWorktree`）拥有放置、分支和清理。绕过它是第 1 大错误 — 它会创建沙盒无法看到或管理的幻影状态。 |
| "工作空间目录肯定已经被忽略了" | 运行 `git check-ignore`。未被忽略的工作空间目录会将整个树提交到仓库。 |
| "任何目录名都可以" | 显式指令优先于现有的项目本地目录，其次是 `.worktrees/` 默认。 |
| "工作空间是干净的 — 基线测试可以稍后进行" | 污染的基线会使每个后续失败变得模糊。现在运行测试；通过失败是您人类合作伙伴的决定。 |
