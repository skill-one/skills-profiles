# 系统化调试

## 概述

**核心原则：** 在尝试修复之前，始终先找到根因。症状修复是失败。

**违反本流程的字面要求，就是违反调试的本质。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果尚未完成第一阶段，则不能提出修复方案。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产环境 Bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其是以下情况时：**
- 时间紧迫（紧急情况会让猜测变得诱人）
- “只需快速修一下”显得很明确
- 已经尝试过多次修复
- 之前的修复无效
- 并不完全理解问题

**不要跳过以下情况：**
- 问题看似简单（简单 Bug 也有根因）
- 你着急（匆忙行事必然导致返工）
- 经理要求立即修复（系统化调试比反复试错更快）

## 四个阶段

在进入下一阶段之前，你必须完成每一个阶段。

### 阶段一：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含精确解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **稳定复现**
   - 能否稳定触发？
   - 具体步骤是什么？
   - 是否每次都会发生？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查近期变更**
   - 什么变更可能导致此问题？
   - Git diff、最近提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统具有多个组件（CI → 构建 → 签名，API → 服务 → 数据库）时：**

   **在提出修复方案之前，添加诊断插桩：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪个层失败（密钥 → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误位于调用栈深处时：**

   请在本目录中查看 `root-cause-tracing.md` 以了解完整的回溯追踪技术。

   **快速版本：**
   - 坏值从何而来？
   - 什么以坏值调用了这个？
   - 一直向上追踪，直到找到源头
   - 在源头修复，而非在症状处修复

### 阶段二：模式分析

**在修复之前，先找到模式：**

1. **寻找有效示例**
   - 在相同代码库中定位类似的正常代码
   - 什么与问题代码类似且正常工作？

2. **与参考对比**
   - 如果正在实现模式，完整阅读参考实现
   - 不要粗略浏览，逐行阅读
   - 在应用之前充分理解模式

3. **识别差异**
   - 正常与异常代码之间有什么不同？
   - 列出每一个差异，无论大小
   - 不要假设“那没什么影响”

4. **理解依赖关系**
   - 此功能需要其他哪些组件？
   - 需要什么设置、配置、环境？
   - 它有哪些假设？

### 阶段三：假设与测试

**科学方法：**

1. **形成单一假设**
   - 明确陈述：“我认为 X 是根因，因为 Y”
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 为测试假设做出尽可能小的改动
   - 一次只改变一个变量
   - 不要同时修复多个问题

3. **验证后再继续**
   - 是否有效？是 → 进入阶段四
   - 无效？形成新假设
   - 不要在之上叠加更多修复

4. **当你不了解时**
   - 说“我不理解 X”
   - 不要假装懂
   - 寻求帮助
   - 进一步研究

### 阶段四：实施

**修复根因，而非症状：**

1. **创建失败测试用例**
   - 最简单的可能复现
   - 如可能则自动化测试
   - 如无框架则使用一次性测试脚本
   - 修复前必须存在
   - 使用 `superpowers:test-driven-development` 技能编写规范的失败测试

2. **实施单一修复**
   - 针对已识别的根因进行修复
   - 一次只做一项修改
   - 不要有“趁此机会”的改进
   - 不要捆绑重构

3. **验证修复**
   - 现在测试通过了吗？
   - 没有其他测试被破坏吗？
   - 问题是否确实已解决？
   - 在声称成功之前使用 `superpowers:verification-before-completion` 技能

4. **如果修复无效**
   - 停止
   - 计数：你尝试了多少次修复？
   - 如果 < 3：返回阶段一，用新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见下方第 5 步）**
   - 未经架构讨论，不要尝试第 4 次修复

5. **如果 3 次以上修复失败：质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都揭示不同位置处的新共享状态/耦合/问题
   - 实现修复需要“大规模重构”
   - 每次修复都在别处产生新的症状

   **停止并质疑基本原理：**
   - 这种模式在根本上是否合理？
   - 我们是否“因惯性坚持到底”？
   - 应该重构架构还是继续修复症状？

   **在与人合作者讨论后，再尝试更多修复**

   这不是假设失败，而是架构错误。

## 危险信号 - 停止并遵循流程

如果你发现自己想到以下想法：
- “先快速修一下，稍后再调查”
- “只需尝试改变 X 看看是否有效”
- “添加多个改动，运行测试”
- “跳过测试，我手动验证”
- “可能是 X，我来修复那个”
- “我不完全理解，但应该可以”
- “模式说 X，但我会不同地应用它”
- “主要问题是：[列出修复方案而未调查]”
- 在追踪数据流之前提出解决方案
- **“再试一次修复”（已经尝试过 2 次及以上时）**
- **每次修复都揭示不同位置的新问题**

**所有这些都意味着：停止。返回阶段一。**

**如果 3 次以上修复失败：质疑架构（见阶段四.5）**

## 你的合作者的信号表明你在做错了

**留意以下转向：**
- “那不是发生吗？”——你未验证就做了假设
- “这会让我们看到……？”——你本应收集证据
- “别猜测”——你在未理解的情况下提出修复
- “彻底思考这个问题”——质疑基本原理，而不仅仅是症状
- “我们卡住了？”（沮丧）——你的方法行不通

**当看到这些时：停止。返回阶段一。**

## 常见的合理化谬误

| 借口 | 现实 |
|------|------|
| “问题很简单，不需要流程” | “简单问题也有根因。对简单 Bug，流程更快。” |
| “紧急情况，没时间走流程” | “系统化调试比反复试错更快。” |
| “先试试这个，之后再调查” | “第一次修复会确立模式。从一开始就正确执行。” |
| “我先确认修复有效，再写测试” | “未经测试的修复无法坚持。先测试才能证明有效。” |
| “一次性修复多个问题节省时间” | “无法隔离哪些有效。会导致新 Bug 产生。” |
| “参考文档太长，我会适应模式” | “部分理解必然导致 Bug。必须完整阅读。” |
| “我看到问题，我来修复” | “看到症状 ≠ 理解根因。” |
| “再试一次修复”（失败 2 次及以上后） | “3 次以上失败 = 架构问题。质疑模式，不要再次修复。” |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|------------|------------------|
| **1. 根因** | 阅读错误、复现、检查变更、收集证据 | 理解是什么以及为什么 |
| **2. 模式** | 寻找有效示例、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 已确认或产生新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 已解决、测试通过 |

## 当流程揭示“无根因”时

如果系统化调查揭示问题确实是环境相关的、与时间相关或外部的：

1. 你已经完成了流程
2. 记录你调查的内容
3. 实施适当的处理（重试、超时、错误信息）
4. 为未来的调查添加监控/日志

**但是：** 95% 的“无根因”情况都是调查不完整。
