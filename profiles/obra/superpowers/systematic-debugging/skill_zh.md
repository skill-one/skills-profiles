# 系统化调试

## 概述

**核心原则：** 在尝试修复之前，必须始终找到根本原因。症状修复是失败的。

**违反此流程的字面意思就是违反调试的精神。**

## 铁律

```
先调查根本原因，再进行修复
```

如果你还没有完成第一阶段，你就不能提出修复建议。

## 使用场景

适用于任何技术问题：
- 测试失败
- 生产环境中的错误
- 预期外行为
- 性能问题
- 构建失败
- 集成问题

**尤其适用于以下情况：**
- 时间紧迫（紧急情况会让人想猜测）
- “快速修复一下”看起来很明显
- 你已经尝试过多个修复
- 之前的修复没有起作用
- 你不完全理解问题

**不要跳过的情况：**
- 问题看起来很简单（简单的错误也有根本原因）
- 你很匆忙（赶工保证会返工）
- 经理要求立即修复（系统化比反复试更快）

## 四个阶段

你必须完成每个阶段才能进入下一个阶段。

### 第一阶段：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们通常包含确切解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **一致地重现**
   - 你能可靠地触发它吗？
   - 具体的步骤是什么？
   - 它是否每次都发生？
   - 如果无法重现 → 收集更多数据，不要猜测

3. **检查最近的变化**
   - 什么变化可能导致这个问题？
   - Git diff，最近的提交
   - 新的依赖项，配置更改
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件（CI → 构建 → 签名，API → 服务 → 数据库）时：**

   **在提出修复建议之前，添加诊断工具：**
   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每层的状态

   运行一次以收集证据显示在哪里出问题
   然后分析证据以识别失败的组件
   然后调查该特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第一层：工作流
   echo "=== 工作流中可用的密钥： ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第二层：构建脚本
   echo "=== 构建脚本中的环境变量： ==="
   env | grep IDENTITY || echo "IDENTITY 不在环境中"

   # 第三层：签名脚本
   echo "=== 密钥链状态： ==="
   security list-keychains
   security find-identity -v

   # 第四层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这揭示了：** 哪一层失败（密钥 → 工作流 ✓，工作流 → 构建 ✗）

5. **跟踪数据流**

   **当错误在调用堆栈深处时：**

   查看 `root-cause-tracing.md` 在此目录中的完整反向跟踪技术。

   **快速版本：**
   - 坏值从哪里起源？
   - 什么调用了这个坏值？
   - 一直跟踪直到找到源头
   - 在源头修复，而不是在症状处修复

### 第二阶段：模式分析

**在修复之前找到模式：**

1. **找到工作示例**
   - 在同一代码库中定位类似的正常代码
   - 什么与损坏的类似的工作内容？

2. **与参考进行比较**
   - 如果实现模式，完全阅读参考实现
   - 不要略读 - 每行都读
   - 完全理解模式后再应用

3. **识别差异**
   - 工作和损坏的区别是什么？
   - 列出每个差异，无论多么小
   - 不要假设“那不重要”

4. **理解依赖关系**
   - 这个需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 第三阶段：假设和测试

**科学方法：**

1. **形成单一假设**
   - 清晰说明：“我认为 X 是根本原因，因为 Y”
   - 写下来
   - 具体而不是模糊

2. **最小化测试**
   - 做最小的可能更改来测试假设
   - 一个变量一次
   - 不要同时修复多个东西

3. **继续前验证**
   - 它起作用了吗？是 → 第四阶段
   - 没有起作用？形成新的假设
   - **不要在顶部添加更多修复**

4. **当你不知道时**
   - 说“我不懂 X”
   - 不要假装知道
   - 请求帮助
   - 研究更多

### 第四阶段：实施

**修复根本原因，而不是症状：**

1. **创建失败的测试用例**
   - 最简单的可能的重现
   - 如果可能，自动化测试
   - 如果没有框架，使用一次性测试脚本
   - 修复前必须有的
   - 使用 `superpowers:test-driven-development` 技巧编写正确的失败测试

2. **实施单个修复**
   - 解决已确定的根本原因
   - 一次一个更改
   - 没有临时改进
   - 没有捆绑重构

3. **验证修复**
   - 现在测试通过了吗？
   - 没有其他测试被破坏吗？
   - 问题真的解决了吗？
   - 使用 `superpowers:verification-before-completion` 技巧在声明成功之前验证

4. **如果修复不起作用**
   - 停止
   - 计算：你已经尝试了多少个修复？
   - 如果 < 3：返回第一阶段，用新信息重新分析
   - **如果 ≥ 3：停止并质疑架构（见第 5 步）**
   - **不要在没有架构讨论的情况下尝试第 4 次修复**

5. **如果 3 次以上的修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每个修复都揭示不同位置的新共享状态/耦合/问题
   - 修复需要“大规模重构”才能实现
   - 每个修复都会在其他地方产生新症状

   **停止并质疑基本原理：**
   - 这个模式从根本上来说是合理的吗？
   - 我们是“纯粹因为惯性而坚持”吗？
   - 我们应该重构架构还是继续修复症状？

   **在尝试更多修复之前与你的“人类伙伴”讨论**

   这不是失败的假设 - 这是错误的架构。

## 警示标志 - 停止并遵循流程

如果你发现自己想：
- “先快速修复，以后再调查”
- “试着改变 X 看看是否起作用”
- “添加多个更改，运行测试”
- “跳过测试，我会手动验证”
- “很可能 X，让我修复它”
- “我不完全理解，但这可能有效”
- “模式说 X，但我会稍作修改”
- “以下是主要问题：[列出修复而没有调查]”
- 在跟踪数据流之前提出解决方案
- **“再试一次修复”（当已经尝试了 2 次以上时）**
- **每个修复都在不同地方揭示新问题**

**所有这些都意味着：停止。返回第一阶段。**

**如果 3 次以上的修复失败：** 质疑架构（见第 4.5 步）

## 你的“人类伙伴”的信号 - 你正在做错

**注意这些重定向：**
- “那不是发生的吗？” - 你在没有验证的情况下假设了
- “它会显示我们...吗？” - 你应该添加证据收集
- “停止猜测” - 你在没有理解的情况下提出了修复
- “超思考这个” - 质疑基本原理，而不是症状
- “我们卡住了？”（沮丧） - 你的方法不起作用

**当你看到这些时：** 停止。返回第一阶段。

## 常见的借口

| 借口 | 现实 |
|------|------|
| “问题很简单，不需要流程” | 简单的问题也有根本原因。流程对简单错误很快速。 |
| “紧急情况，没有时间进行流程” | 系统化调试比猜测和反复试更快。 |
| “先试这个，然后调查” | 第一个修复设定了模式。从一开始就正确做。 |
| “修复确认工作后再写测试” | 未测试的修复不会坚持。先测试证明它。 |
| “一次修复多个，节省时间” | 无法隔离什么起作用了。会导致新错误。 |
| “参考太长，我会稍作修改” | 部分理解保证会出错误。完全阅读它。 |
| “我看到问题，让我修复它” | 看到症状 ≠ 理解根本原因。 |
| “再试一次修复”（在 2 次以上失败后） | 3 次以上的修复 = 架构问题。质疑模式，不要再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|----------|----------|
| **1. 根本原因** | 阅读错误、重现、检查更改、收集证据 | 理解什么和为什么 |
| **2. 模式** | 找到工作示例、比较 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或新假设 |
| **4. 实施** | 创建测试、修复、验证 | 错误已解决，测试通过 |

## 当流程揭示“没有根本原因”时

如果系统化调查揭示问题是真正环境依赖的、时间相关的或外部的：

1. 你已经完成了流程
2. 记录你调查了什么
3. 实施适当的处理（重试、超时、错误消息）
4. 添加监控/日志记录以供将来调查

**但是：** 95% 的“没有根本原因”的情况是调查不完整。

## 支持技术

这些技术是系统化调试的一部分，并在此目录中可用：

- **`root-cause-tracing.md`** - 通过调用堆栈反向跟踪以找到原始触发器
- **`defense-in-depth.md`** - 在找到根本原因后，在多个层添加验证
- **`condition-based-waiting.md`** - 用条件轮询替换任意超时
