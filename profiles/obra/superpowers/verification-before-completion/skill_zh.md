# 完成前验证

## 概述

**核心原则：** 证据优先于断言，始终如此。

**违反本规则的字面含义，即违反本规则的精神。**

## 铁律

```
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
```

如果在当前消息中尚未运行验证命令，则无法声称其通过。

## 门控机制

```
在声称任何状态或表达满意之前：

1. IDENTIFY：什么命令能够证明该声明？
2. RUN：执行完整的命令（全新、完整）
3. READ：查看完整输出，检查退出代码，统计失败次数
4. VERIFY：输出是否证实了该声明？
   - 如果 NO：以证据说明实际状态
   - 如果 YES：以证据说明该声明
5. ONLY THEN：做出该声明

跳过任何一步 = 撒谎，而非验证
```

## 常见失误

表格：

```
声称 | 必需 | 不充分
-------|------|----------------
测试通过 | 测试命令输出：0 失败 | 之前运行结果，"应该通过"
代码检查干净 | 代码检查器输出：0 错误 | 部分检查，推断
构建成功 | 构建命令：退出码为 0 | 代码检查通过，日志看起来良好
Bug 已修复 | 原始症状测试：通过 | 代码已改动，假定已修复
回归测试有效 | 红-绿循环已验证 | 测试仅通过一次
Agent 已完成 | VCS 差异显示有改动 | Agent 报告"成功"
需求已满足 | 逐项核对清单 | 测试通过
```

## 红色警示 - 停止

- 使用 "应该"、"可能"、"似乎" 等措辞
- 在验证前表达满意（"太棒！"、"完美！"、"已完成！" 等）
- 在未经验证的情况下即将提交/推送/创建 PR
- 信赖 Agent 的成功报告
- 依赖部分验证
- 认为"就这一次"
- 疲惫且想以工作为先
- **任何在未运行验证的情况下暗示成功的措辞**

## 防止自我合理化

表格：

```
借口 | 现实
-------|------
"现在应该能行" | 运行验证
"我有信心" | 信心 ≠ 证据
"就这一次" | 没有例外
"代码检查通过了" | 代码检查器 ≠ 编译器
"Agent 说成功了" | 独立验证
"我累了" | 疲惫 ≠ 借口
"部分检查足够了" | 部分检查不能证明任何事
"措辞不同，规则不适用" | 精神优于字面
```

## 关键模式

**测试：**
```
✅ [运行测试命令] [查看：34/34 通过] "所有测试通过"
❌ "现在应该通过" / "看起来正确"
```

**回归测试（TDD 红-绿）：**
```
✅ 编写 → 运行（通过） → 撤销修复 → 运行（必须失败） → 恢复 → 运行（通过）
❌ "我已经编写了回归测试"（未经红-绿验证）
```

**构建：**
```
✅ [运行构建] [查看：退出码为 0] "构建通过"
❌ "代码检查通过了"（代码检查器不检查编译）
```

**需求：**
```
✅ 重新阅读方案 → 创建清单 → 逐项验证 → 报告差距或完成情况
❌ "测试通过，阶段完成"
```

**Agent 委托：**
```
✅ Agent 报告成功 → 检查 VCS 差异 → 验证改动 → 报告实际状态
❌ 信赖 Agent 报告
```

## 何时应用

**始终在以下之前：**
- 任何成功/完成声明的变体
- 任何满意表达
- 关于工作状态的任何积极陈述
- 提交、创建 PR、完成任务
- 切换到下一个任务
- 委托给 Agent

**规则适用于：**
- 确切的短语
- 改写和同义词
- 成功暗示
- 任何表明完成/正确的沟通
