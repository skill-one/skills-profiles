# 编写计划

## 概述

假设工程师对我们代码库一无所知且品味可疑，编写全面的实施计划。记录他们需要了解的所有信息：每个任务需要修改哪些文件、代码、测试、可能需要检查的文档，以及如何进行测试。将整个计划分解为可管理的任务。保持代码复用（DRY）、避免过早优化（YAGNI）、测试驱动开发（TDD），并频繁提交代码。

假设他们是经验丰富的开发者，但几乎不了解我们的工具集或问题领域。假设他们对良好的测试设计了解不多。

**开始时宣布：** "我正在使用编写计划技能来创建实施计划。"

**背景：** 如果在隔离的工作树中工作，它应该通过 `superpowers:using-git-worktrees` 技能在执行时创建。

**保存计划到：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- （用户对计划位置的偏好会覆盖此默认值）

## 范围检查

如果规范涵盖了多个独立的子系统，它应该在头脑风暴阶段分解为子项目规范。如果没有，建议将其分解为单独的计划——每个子系统一个。每个计划都应该能够独立产生可工作、可测试的软件。

## 文件结构

在定义任务之前，规划将要创建或修改的文件以及每个文件的责任。这是分解决策固定下来的地方。

- 设计具有清晰边界和明确定义的接口的单元。每个文件应该只有一个明确的责任。
- 你对一次能hold在上下文中的代码进行推理最好，而且当文件专注于某事时，你的修改更可靠。优先考虑较小的、专注的文件，而不是做太多事情的大的文件。
- 一起改变的文件应该放在一起。按责任分割，而不是按技术层分割。
- 在现有代码库中，遵循既定模式。如果代码库使用大文件，不要单方面重构——但如果你要修改的文件变得难以管理，在计划中包含拆分是合理的。

这种结构指导任务分解。每个任务都应该产生自包含的更改，这些更改可以独立地有意义。

## 任务大小调整

任务是包含自己的测试周期并且值得一个新鲜审查者通过的单元。在划分任务边界时：将设置、配置、脚手架和文档步骤合并到需要它们的任务的交付物中；只有在审查者可以有意义地拒绝一个任务而批准其相邻任务的情况下才进行拆分。每个任务都以一个可独立测试的交付物结束。

## 任务粒度细化

**每个步骤是一个操作（2-5分钟）：**
- "编写失败的测试" - 步骤
- "运行它以确保它失败" - 步骤
- "实现使测试通过的最小代码" - 步骤
- "运行测试并确保它们通过" - 步骤
- "提交" - 步骤

## 计划文档头部

**每个计划必须以这个头部开始：**

```markdown
# [功能名称] 实施计划

> **对于自主工作的工人：** 必须使用子代理驱动开发（推荐）或执行计划来按任务实施此计划。步骤使用复选框（`- [ ]`）语法进行跟踪。

**目标：** [用一句话描述这个计划构建的内容]

**架构：** [2-3句话描述方法]

**技术栈：** [关键技术/库]

**规范：** [规范/设计文档的路径，此计划实现它——计划从规范出发，所以规范随计划一起移动；执行者阅读两者]

## 全局约束

[规范的跨项目要求——版本下限、依赖限制、命名和复制规则、平台要求——每行一条，并从规范中逐字复制确切的值。每个任务的要求隐式包含这一部分。]

## 审查重点

[规范暗示但任务的测试没有执行的五个输入类别或失败模式，最有可能咬使用此软件的人——每行一条，命名输入或条件以及合理的人期望的行为，最可能是第一个。规范是愿景文档：它说明软件必须做什么，而不是它将满足的所有内容，并且它对输入的沉默不是允许该输入破坏程序的许可。在规范面前，写下这个列表，一次，然后，对于每一行，添加将它们固定到拥有代码的任务的测试，在该任务自己的步骤风格中。]

---
```

## 任务结构

````markdown
### 任务 N：[组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费：[此任务从早期任务使用的——确切的签名]
- 产生：[稍后任务依赖的——确切的函数名、参数和返回类型。任务的实现者只看到自己的任务；这个块是他们了解相邻任务使用的名称和类型的方式。]

- [ ] **步骤 1：编写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试以验证它失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：失败并显示 "function not defined"

- [ ] **步骤 3：编写最小实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试以验证它通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：通过

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: 添加特定功能"
```
````

## 无占位符

每个步骤必须包含工程师实际需要的内容。这些都是**计划失败**——永远不要写它们：
- "TBD"、"TODO"、"稍后实现"、"填写详细信息"
- "添加适当的错误处理" / "添加验证" / "处理边界情况"
- "为上述内容编写测试"（没有实际测试代码）
- "与任务 N 类似"（重复代码——工程师可能以任意顺序阅读任务）
- 描述要做什么而不显示如何做的步骤（代码步骤需要代码块）
- 引用未在任何任务中定义的类型、函数或方法

## 自我审查

在编写完整计划后，用新鲜的眼睛查看规范，并对照计划进行检查。这是一个你运行自己的检查表——不是子代理调度。

**1. 规范覆盖：** 快速浏览规范的每个部分/要求。你能指出一个实现它的任务吗？列出任何差距。

**2. 占位符扫描：** 在你的计划中搜索红旗——上述“无占位符”部分中的任何模式。修复它们。

**3. 类型一致性：** 你在稍后任务中使用的类型、方法签名和属性名称是否与你在早期任务中定义的匹配？任务 3 中调用的 `clearLayers()` 但任务 7 中调用的 `clearFullLayers()` 是一个错误。

**4. 审查重点：** 对于规范暗示的每个输入类别或失败模式，是否有任务的测试执行了它？最有可能咬人的五个未覆盖的输入放在审查重点部分，并且每行那里都将其测试添加到拥有代码的任务中。一个空的部分意味着你检查了并且没有发现，而不是你跳过了检查。

如果你发现问题，请直接修复。不需要重新审查——只需修复并继续。如果你发现一个没有任务的规范要求，请添加任务。

## 执行交接

在保存并自我审查计划后，链接它供你的人类合作伙伴阅读。如果他们已经明确提供了执行方法，请让他们审查计划并确认它捕获了他们想要的内容；在实施之前等待该审查，然后使用保留的方法。否则，请让他们审查计划并在实施之前选择执行方法。

**当还没有提供执行方法时：**

**"计划完成并保存到 `docs/superpowers/plans/<filename>.md`。请审查计划。您更喜欢哪种执行方法？**

- **子代理驱动** - 一个新的子代理实现每个任务，并在下一个任务开始之前由一个新的审查者检查它，然后在最后进行整个分支的审查。最彻底；每个任务和每个审查都花费一个新上下文。
- **原生** - 我在这个会话中自己实现每个任务，这个 harness 运行工作的方式，然后最强大的模型在最后对整个分支进行一次新鲜审查。最便宜和最快；直到最后都没有独立的审查。与中端会话模型运行良好，因为计划包含了设计。

**对于这个计划我推荐 <其中一个>，因为 <计划中的一句：任务接口之间的依赖程度、任务数量、 shipped 错误的成本>。计划是否捕获了您想要的内容，我们应该使用哪种方法？**"

**当已经提供执行方法时：**

**"计划完成并保存到 `docs/superpowers/plans/<filename>.md`。请审查计划。它是否捕获了您想要的内容？**"

**如果选择子代理驱动：**
- **必须使用子代理驱动开发：** `superpowers:subagent-driven-development`

**如果选择原生：**
- **必须使用执行计划：** `superpowers:executing-plans`
