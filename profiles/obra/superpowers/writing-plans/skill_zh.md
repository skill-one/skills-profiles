# 编写计划

## 概述

编写全面的实现计划，假设工程师对我们的代码库毫无上下文了解，且品味存疑。记录他们需要知道的一切：每个任务需要触碰哪些文件、可能需要检查的代码、测试和文档，以及如何进行测试。以小块任务的形式给出完整计划。坚持 DRY（不做重复）、YAGNI（不做未需求功能）、TDD（测试驱动开发）、频繁提交。

假设他们是熟练的开发者，但对我们的工具集或问题领域几乎一无所知。假设他们不熟悉良好的测试设计。

**在开始时宣布：** "我正在使用 writing-plans 技能来创建实现计划。"

**上下文：** 如果是在独立工作区（worktree）中工作，它应该在执行时通过 `superpowers:using-git-worktrees` 技能创建。

**将计划保存到：** `docs/superpowers/plans/YYYY-MM-DD-<-feature-name>.md`
- （用户对计划位置的偏好会覆盖此默认值）

## 范围检查

如果规格涵盖多个相互独立的分系统，应在头脑风暴阶段将其拆分为子项目规格。如果未拆分，建议将其拆分为单独的计划——每个分系统一个。每个计划都应独立产出可运行、可测试的软件。

## 文件结构

在定义任务之前，梳理将创建或修改哪些文件，以及每个文件负责什么。这是确定分解决策的地方。

- 以清晰边界和明确定义的接口设计单元。每个文件应只承担一项明确的职责。
- 我们最能理解同时存在于上下文中的代码，且文件聚焦时修改更可靠。优先选择较小、聚焦的文件，而非处理过多内容的过大文件。
- 一起变更的文件应放在一起。按职责拆分，而非按技术层级拆分。
- 在现有代码库中，遵循既定模式。如果代码库使用大文件，不要擅自重构——但如果你修改的文件变得过于庞大，在计划中包含拆分是合理的。

该结构为任务分解提供依据。每个任务应产出自包含的变更，且能独立理解其意义。

## 任务合理划分

任务是承载自身测试周期且值得新审核者把关的最小单元。在划分任务边界时：将设置、配置、脚手架搭建和文档步骤合并到交付成果需要它们的任务中；仅在审核者可能有意义地拒绝一个任务而批准其相邻任务时才进行拆分。每个任务以可独立测试的交付成果结尾。

## 小块任务粒度

**每一步只是一项操作（2-5分钟）：**
- “编写失败测试” - 步骤
- “运行它以确保其失败” - 步骤
- “编写使测试通过的极简代码” - 步骤
- “运行测试并确保通过” - 步骤
- “提交” - 步骤

## 计划文档头部

**每个计划必须以下方头部开头：**

```markdown
# [Feature Name] Implementation Plan

> **为智能体工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 按任务实现本计划。步骤使用复选框（`- [ ]`）语法进行跟踪。

**目标：** [一句话描述构建的内容]

**架构：** [2-3句话说明方法]

**技术栈：** [关键技术/库]

**规格：** [本计划所实现的规格/设计文档的路径——计划基于规格论述，因此规格会随计划一同传递；执行者会同时阅读两者]

## 全局约束

[规格中的项目级要求——版本下限、依赖限制、命名和复制规则、平台要求——每项一行，且原样复制自规格。每个任务的准则均隐含包含该部分内容。]

## 审核重点

[规格隐含但任何任务的测试均未覆盖的、最可能让使用该软件的个人受损的五个输入类别或故障模式——每行指出输入或条件，以及合理的人预期其具备的行为，通常优先列出。规格是一份愿景文档：它说明软件必须做什么，而非将做到的一切；其对某输入的沉默并不等于允许该输入破坏程序。此处一次性列出该清单，届时请将规格置于面前。然后，针对每一行，为该代码所属的任务添加锁定该条件的测试，使用该任务的自身步骤格式。]

## 任务结构

````markdown
### 任务 N：[组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 使用：[本任务使用的先前任务的内容——精确签名]
- 产出：[后续任务依赖的内容——精确函数名、参数和返回类型。任务的实现者仅能看到自身任务；该部分区块是它们了解邻近任务所使用名称和类型的方式。]

- [ ] **步骤 1：编写失败测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试以验证其失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：失败，报错 "function not defined"

- [ ] **步骤 3：编写极简实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试以验证其通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：通过

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 无占位符

每一步必须包含工程师所需的确切内容。这些属于**计划失败**——绝不编写它们：
- “TBD”、“TODO”、“稍后实现”、“填充细节”
- “添加适当的错误处理” / “添加校验” / “处理边界情况”
- “为上述内容编写测试”（不包含实际测试代码）
- “与任务 N 类似”（重复代码——工程师可能按顺序之外阅读任务）
- 仅描述做什么而未展示如何（代码步骤必须包含代码块）的步骤
- 引用任何任务均未定义的类型、函数或方法的步骤

## 自检

编写完整计划后，从全新的视角审视规格，对照规格检查计划。这是你自行运行的检查清单——而非派发子代理。

**1. 规格覆盖：** 通读规格中的每一节/每一项要求。能否指出实现它的任务？列出任何缺失。

**2. 占位符扫描：** 在计划中搜索警示信号——包含上述“无占位符”部分中列出的任何模式。进行修正。

**3. 类型一致性：** 后续任务中使用的类型、方法签名和属性名是否与你在前置任务中定义的一致？任务 3 中调用 `clearLayers()`，而任务 7 中调用 `clearFullLayers()` 即为错误。

**4. 审核重点：** 对于规格隐含的每个输入类别或故障模式，是否存在任务中的测试覆盖了它？最可能让使用该软件的个人受损的五个未覆盖项将列入审核重点部分，且该部分每一行都会为所属任务添加对应的测试。该部分为空意味着你已检查且未发现，而非跳过检查。

如果发现问题，请内联修正。无需重新审查——直接修正并继续。如果发现规格要求无对应任务，则添加任务。

## 执行交接

在保存计划并完成自检后，将计划链接给人工合作伙伴阅读。如果他们已明确提供了执行方法，请他们审查计划并确认其涵盖了他们想要的；在等待该确认后实施，然后使用保留的方法。否则，请他们审查计划并选择执行方法后再实施。

**当尚未提供执行方法时：**

**“计划已完成并保存到 `docs/superpowers/plans/<filename>.md`。请审查计划。您倾向于哪种执行方式？**

- **Subagent 驱动** - 一个全新的子代理实现每个任务，并在下一个任务开始前由全新的审核者进行检查，最后对整个分支进行整体审查。最为彻底；每个任务和每次审查均消耗全新的上下文。
- **原生** - 我在本会话中自行实现每个任务，方式与本框架运行工作的方式一致，然后由最强大的模型中的一个全新审核者对整个分支进行检查。最经济且最快；在结束前无独立审查。由于计划包含设计，因此与中配会话模型配合运行良好。

**对于本计划，我推荐 <两者之一之一者（二选一）中的一个，因为 <根据计划的一句话：任务之间接口的依赖程度、任务数量、若出现已发布错误将造成的代价>. 本计划是否涵盖了您想要的，我们应该采用哪种方式？**

**当已提供执行方法时：**

**“计划已完成并保存到 `docs/superpowers/plans/<filename>.md`。请审查计划。它是否涵盖了您想要的？”**

**若选择 Subagent 驱动：**
- **必需技能：** 使用 superpowers:subagent-driven-development

**若选择原生：**
- **必需技能：** 使用 superpowers:executing-plans
