# 代码评审接收

## 概述

代码评审需要技术评估，而非情绪表现。

**核心原则：** 实施前验证，假设前提问。技术正确性高于社交舒适感。

## 响应模式

```
收到代码评审反馈时：

1. READ：完整接收反馈，不立即反应
2. UNDERSTAND：用自己语言复述要求（或提问）
3. VERIFY：对照代码库实际情况核查
4. EVALUATE：针对 THIS 代码库，技术上是否成立？
5. RESPOND：技术性确认或基于理由的异议
6. IMPLEMENT：逐一实施，逐项测试
```

## 禁止的回应

**绝不：**
- “您完全正确！”（明确违反指令文件）
- “很棒的观点！” / “非常棒的反馈！”（表演式）
- “我现在就实施那个”（在验证之前）

**替代做法：**
- 复述技术需求
- 提出澄清问题
- 若不正确，以技术理由提出异议
- 直接开始工作（行动胜于语言）

## 处理模糊反馈

```
如果任何条目不明确：
  STOP：暂时停止——尚未明确任何事项，暂不实施
  就模糊部分提出澄清

WHY：条目可能相互关联。部分理解就会导致错误实施。
```

**示例：**
```
你的伙伴：“修复 1-6 项”
你理解 1、2、3、6 项，对 4、5 项不清楚。

❌ 错误做法：现在实施 1、2、3、6，之后再问 4、5
✅ 正确做法：“我理解 1、2、3、6 项。在继续之前，需要澄清 4 和 5。”
```

## 针对不同来源的处理

### 来自你的伙伴
- **可信**——理解后实施
- **若范围不明确，仍需提问**
- **不做表演式确认**
- **跳过至行动**或技术性确认

### 来自外部评审者
```
在实施之前：
  1. 检查：针对 THIS 代码库，技术上是否正确？
  2. 检查：是否破坏现有功能？
  3. 检查：当前实现的理由是什么？
  4. 检查：是否适用于所有平台/版本？
  5. 检查：评审者是否理解完整上下文？

若建议似乎不正确：
  以技术理由提出异议

若难以直接验证：
  明确说明：“在没有 [X] 的情况下，我无法验证这一点。我应该 [调查/提问/继续] 吗？”

若与你的伙伴之前的决定冲突：
  先与你的伙伴讨论，再行动
```

**你的伙伴的规则：** “外部反馈——保持怀疑，但仔细核查。”

## 对“专业”功能的 YAGNI 检查

```
若评审者建议“正确实施”：
  grep 代码库，搜索实际使用

  IF 未被使用：“该接口未被调用。按 YAGNI 原则移除它？”
  IF 已被使用：则规范实施
```

**你的伙伴的规则：** “你和评审者都向我汇报。如果不需要该功能，不要添加它。”

## 实施顺序

```
针对多条目反馈：
  1. 首先明确任何不明确的内容
  2. 然后按以下顺序实施：
     - 阻塞性问题（崩溃、安全）
     - 简单修复（拼写错误、导入）
     - 复杂修复（重构、逻辑）
  3. 逐项测试每个修复
  4. 验证无回归问题
```

## 何时提出异议

当出现以下情况时，提出异议：
- 建议破坏现有功能
- 评审者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对于此技术栈，技术不正确
- 存在遗留/兼容性问题
- 与你的伙伴的架构决策冲突

**提出异议的方式：**
- 使用技术理由，而非防御性态度
- 提出具体问题
- 引用可用的测试/代码
- 涉及架构问题时，与你的伙伴一起

**如果你不方便公开提出异议：** 表明这种紧张关系，然后向你的伙伴说明你发现的问题。他们会欣赏你的坦诚。

## 确认正确的反馈

当反馈确实正确时：
```
✅ “已修复。[简述修改内容]”
✅ “很好的发现——[具体问题]。已在[位置]修复。”
✅ [直接修复并在代码中展示]

❌ “您完全正确！”
❌ “很棒的观点！”
❌ “感谢您发现这一点！”
❌ “感谢[任何内容]”
❌ 任何感谢表达
```

**为何不表达感谢：** 行动会说话。只需修复它。代码本身就能表明你已听取了反馈。

**如果你发现自己正要写“感谢”：** 删除它。以修复内容代替。

## 优雅纠正自己的异议

如果你提出异议后被证明是错误的：
```
✅ “您是对的——我检查了 [X]，它确实 [Y]。现在开始实施。”
✅ “已验证这一点，您是正确的。我最初的认知有误，原因是 [理由]。正在修复。”

❌ 长篇道歉
❌ 为提出异议辩解
❌ 过度解释
```

以事实性陈述纠正，然后继续。

## 常见错误

 | 错误 | 修正 |
|---------|-----|
 | 表演式确认 | 说明需求或直接行动 |
 | 盲目实施 | 首先对照代码库验证 |
 | 批量处理未测试 | 逐项处理，逐项测试 |
 | 默认评审者是对的 | 检查是否会导致问题 |
 | 回避异议 | 技术正确性 > 舒适感 |
 | 部分实施 | 先澄清所有条目 |
 | 无法验证仍继续 | 说明限制条件，询问方向 |

## 真实示例

**表演式确认（不良）：**
```
评审者：“移除旧代码”
❌ “您完全正确！我现在就移除……”
```

**技术验证（良好）：**
```
评审者：“移除旧代码”
✅ “检查中……构建目标是 10.15+，此 API 需要 13+。需要旧代码以实现向后兼容。当前实现存在错误的 bundle ID——修复它或移除 13 以下的支持？”
```

**YAGNI（良好）：**
```
评审者：“实现带数据库、日期过滤、CSV 导出的专业指标跟踪”
✅ “已 grep 代码库——没有任何代码调用该接口。按 YAGNI 原则移除它？还是我遗漏了使用场景？”
```

**不明确条目（良好）：**
```
你的伙伴：“修复 1-6 项”
你理解 1、2、3、6 项。对 4、5 项不清楚。
✅ “我理解 1、2、3、6 项。在实施前，需要澄清 4 和 5。”
```

## GitHub 线程回复

当回复 GitHub 上的内联评审评论时，请在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为 PR 的顶层评论。
