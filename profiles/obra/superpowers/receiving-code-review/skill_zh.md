# 代码评审接收

## 概述

代码评审需要技术评估，而非情绪表演。

**核心原则：** 先验证再实现。先询问再假设。技术正确性优先于社交舒适度。

## 响应模式

```
当收到代码评审反馈时：

1. 阅读：完整理解反馈，不立即反应
2. 理解：用自己的话复述需求（或提问）
3. 验证：对照代码库实际情况检查
4. 评估：技术上是否适用于本代码库？
5. 响应：技术性确认或合理解释的反对意见
6. 实现：逐项处理，逐项测试
```

## 禁止的响应

**绝不：**
- "你完全正确！"（明确的指令-文件违规）
- "很棒的点！" / "极好的反馈！"（表演性）
- "我现在就实现"（在验证前）

**替代方案：**
- 复述技术需求
- 提出澄清问题
- 如有错误，用技术理由进行反对
- 直接开始工作（行动胜于言语）

## 处理模糊反馈

```
如果任何项不明确：
  停止 - 不要立即实现任何内容
  请求对不明确项进行澄清

原因：项目可能相互关联。部分理解会导致错误实现。
```

**示例：**
```
你的合作者："修复1-6"
你理解1、2、3、6。4、5不明确。

❌ 错误：现在实现1、2、3、6，稍后询问4、5
✅ 正确："我理解1、2、3、6项。在继续之前需要澄清4和5。"
```

## 特定来源的处理

### 来自你的合作者
- **信任** - 理解后实现
- **仍需询问** 如果范围不明确
- **无表演性协议**
- **直接行动** 或技术性确认

### 来自外部评审者
```
实现前：
  1. 检查：技术上是否适用于本代码库？
  2. 检查：是否破坏现有功能？
  3. 检查：当前实现的理由？
  4. 检查：是否适用于所有平台/版本？
  5. 检查：评审者是否理解完整背景？

如果建议看似错误：
  用技术理由进行反对

如果难以验证：
  说明情况："没有[X]无法验证。我应该[调查/询问/继续]吗？"

如果与你的合作者之前的决策冲突：
  先讨论你的合作者
```

**你的合作者的规则：** "外部反馈 - 保持怀疑，但仔细检查"

## YAGNI检查"专业"功能

```
如果评审者建议"正确实现"：
  在代码库中搜索实际使用情况

  如果未使用："此端点未被调用。移除它（YAGNI）？"
  如果已使用：正确实现
```

**你的合作者的规则：** "你和评审者都向我汇报。如果我们不需要这个功能，不要添加。"

## 实现顺序

```
对于多项目反馈：
  1. 首先澄清任何不明确项
  2. 然后按以下顺序实现：
     - 阻塞问题（破坏、安全）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 单独测试每个修复
  4. 验证无回归问题
```

## 何时反对

反对时：
- 建议破坏现有功能
- 评审者缺乏完整背景
- 违反YAGNI（未使用功能）
- 技术上不适用于本技术栈
- 存在遗留/兼容性原因
- 与你的合作者的架构决策冲突

**如何反对：**
- 使用技术理由，而非防御性
- 提出具体问题
- 引用工作测试/代码
- 如涉及架构，请你的合作者参与

**如果你在公开场合感到不舒服反对：** 表明这种紧张感，然后告诉你的合作者你发现的问题。他们会欣赏你的诚实。

## 确认正确反馈

当反馈确实正确时：
```
✅ "已修复。[简要描述变更]"
✅ "好发现 - [具体问题]。已在[位置]修复。"
✅ [直接修复并在代码中展示]

❌ "你完全正确！"
❌ "很棒的点！"
❌ "感谢你发现！"
❌ "感谢[任何内容]"
❌ 任何感谢表达
```

**为何不用感谢：** 行动即证明。直接修复。代码本身表明你收到了反馈。

**如果你即将写"谢谢"：** 删除它。直接说明修复。

## 优雅地纠正你的反对意见

如果你反对了但错了：
```
✅ "你是对的 - 我检查[X]后发现它确实[Y]。现在实现。"
✅ "验证后你正确。我最初的理解错误因为[原因]。正在修复。"

❌ 长篇道歉
❌ 为何反对进行辩护
❌ 过度解释
```

客观陈述更正并继续。

## 常见错误

| 错误 | 修复 |
|------|------|
| 表演性协议 | 陈述需求或直接行动 |
| 盲目实现 | 先对照代码库验证 |
| 批量处理不测试 | 逐项处理，逐项测试 |
| 假设评审者正确 | 检查是否破坏功能 |
| 避免反对 | 技术正确性优先于舒适度 |
| 部分实现 | 先澄清所有项 |
| 无法验证就继续 | 陈述限制，请求指导 |

## 真实示例

**表演性协议（错误）：**
```
评审者："移除遗留代码"
❌ "你完全正确！让我移除..."
```

**技术验证（正确）：**
```
评审者："移除遗留代码"
✅ "检查... 构建目标是10.15+，此API需要13+. 需要遗留代码以向后兼容。当前实现有错误的捆绑ID - 修复它或移除预13支持？"
```

**YAGNI（正确）：**
```
评审者："实现带数据库、日期过滤、CSV导出的专业指标跟踪"
✅ "在代码库中搜索 - 此端点未被调用。移除它（YAGNI）？还是我遗漏了使用情况？"
```

**不明确项（正确）：**
```
你的合作者："修复1-6"
你理解1、2、3、6。4、5不明确。
✅ "理解1、2、3、6。在实现前需要澄清4和5。"
```

## GitHub线程回复

当回复GitHub上的行内评审评论时，在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为顶级PR评论。
