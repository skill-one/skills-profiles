# Diffity Tour 技能

您正在创建一个引导式代码巡游——这是一个逐步的、带有旁白的代码库漫游，用于回答用户的问题或解释功能的工作原理。巡游在浏览器中打开，侧边栏显示旁白和高亮代码部分。

## 参数

- `question` (必需): 用户的提问、主题、概念或 GitHub PR URL。示例：
  - `/diffity-tour 认证是如何工作的？`
  - `/diffity-tour 解释请求生命周期`
  - `/diffity-tour 评论是如何存储和检索的？`
  - `/diffity-tour 闭包`
  - `/diffity-tour React hooks`
  - `/diffity-tour 在我合并之前带我走一遍这个分支`
  - `/diffity-tour https://github.com/owner/repo/pull/123`

当参数是 **GitHub PR URL** (匹配 `github.com/owner/repo/pull/N`) 时，巡游会自动锁定到 **Review 模式** — PR 的差异驱动范围，结论必须包含 PR-flags 列表。见下文的 **Review 巡游** 部分。

## CLI 参考

```
diffity agent tour-start --topic "<text>" [--body "<text>"] --json
diffity agent tour-step --tour <id> --file <path> --line <n> [--end-line <n>] --body "<text>" [--annotation "<text>"] --json
diffity agent tour-done --tour <id> --json
diffity list --json
```

## 前置条件

1. 确认 `diffity` 可用：运行 `which diffity`。如果未找到，使用 `npm install -g diffity` 安装它。
2. **如果参数是 GitHub PR URL**:
   - 检查 `gh` 是否已安装并认证：运行 `gh auth status`。如果未认证，停止并要求用户运行 `gh auth login`。
   - 验证当前仓库是否与 PR 的仓库匹配：运行 `gh repo view --json nameWithOwner -q .nameWithOwner` 并确认它是否与 URL 中的 `owner/repo` 匹配。如果不匹配，停止并告诉用户他们需要进入 PR 的仓库克隆——diffity 无法为未检出的仓库的 PR 进行巡游。
   - 对 PR 启动 diffity：使用 Bash 工具并设置 `run_in_background: true` 运行 `diffity --no-open <pr-url>`。**`--no-open` 标志必须位于位置 URL 之前** — commander 的 `passThroughOptions()` 会将位置 URL 之后的任何标志都混入 refs 数组，跳过 PR 处理并产生 "unknown ref" 错误。此命令将 PR 的分支检出到本地并启动一个 diff 范围的会话。等待 2 秒钟，然后运行 `diffity list --json` 获取端口。您不需要另一个 tree 实例——diff 会话支持 `agent tour-*` 命令。
3. **否则**，确保一个 tree 实例正在运行：运行 `diffity list --json`。
   - 如果没有实例在运行，启动一个：使用 Bash 工具并设置 `run_in_background: true` 运行 `diffity tree --no-open`，等待 2 秒钟，然后运行 `diffity list --json` 获取端口。

## 说明

### 首先选择模式

在执行任何其他操作之前，决定此巡游属于哪种模式。技能的其余部分将根据此选择分支——范围、研究方法和输出形状都因模式而异。在调用任何工具之前完成此操作。

**快捷方式**：如果参数是 GitHub PR URL (匹配 `github.com/owner/repo/pull/N`)，则跳过决策——它被锁定到 **Review 模式**。

| 模式 | 当用户询问... | 范围由...定义 | 目标步骤 |
|---|---|---|---|
| **聚焦** | 一个狭窄的 "X 是如何工作的?" 问题 | 单个代码路径 | 3-6 |
| **功能** | "这个功能是如何工作的?" | 功能边界 | 6-10 |
| **系统** | "整个东西是如何工作的?" | 架构 | 8-15 |
| **概念** | 关于编程概念 | 代码中的示例 | 3-8 |
| **Review** | 在合并前审计分支/PR/功能 | `git diff <base>..HEAD` | 可变——涵盖所有有意义的变化 |

引导用户选择模式的触发词：
- **聚焦**： "X 如何验证", "带我走遍 Y 端点"
- **功能**： "认证是如何工作的", "解释评论系统"
- **系统**： "应用程序是如何工作的", "给我架构概述"
- **概念**： 单独的概念名称 (`closures`, `React hooks`, `async/await`, `generics`)
- **Review**： "在我合并之前", "审查这个分支", "带我走遍整个功能", "审计这个 PR", "我即将合并"

如果多个模式适用，优先选择更具体的一个（Review > 概念 > 聚焦 > 功能 > 系统）。如果您确实无法确定用户想要什么，请在研究之前询问——不要猜测并产生错误的巡游形状。

模式会改变此技能适用的部分：
- **概念模式** → 阅读 **概念巡游** 部分下文；研究方式不同（搜索示例，而不是跟随流程）并且步骤进展也不同。
- **Review 模式** → 阅读 **Review 巡游** 部分下文；范围由 diff 驱动，线程逐个遍历，结论必须包含 PR-flags 列表。
- **聚焦 / 功能 / 系统模式** → 默认的 Phase 1-3 说明直接适用。

### Phase 1: 范围和研究

在创建任何巡游步骤之前，您必须深入理解用户问题的答案。

1. **确认范围**。您选择的模式设定了大致的步骤数量（见上文的 **选择模式**）。如果用户的问题过于宽泛，无法适应该大小（例如 "解释一切" 落在 System 模式），请在大脑中将范围缩小到最重要的方面，并在引言中说明您涵盖的内容和排除的内容。

2. **确定受众**。考虑问题是如何表述的：
   - "X 是如何工作的?" → 假设有人 **不熟悉这个代码库** — 解释架构决策，而不仅仅是代码机制
   - "X 为什么做 Y?" → 假设有人正在调试或审查 — 侧重于推理和边缘情况
   - "带我走遍 X" → 假设有人想要完整的画面 — 要彻底，包括上下文

3. **研究代码库**。彻底阅读相关源文件。从入口点跟随代码路径到完成。

   对于 Review 巡游尤其如此，还请阅读 `git log --reverse <base>..HEAD` 并打开任何提交信息描述非明显的修复、重构或防御性更改。作者的自己的叙述通常是 *为什么* 的最佳来源——远比单独从代码中推断意图要好。在步骤正文中引用或概述提交推理，如果它能阐明设计决策（例如 "提交 `abc1234` 在一次生产事件后引入了这个检查，当时..."）。

   **巡游 GitHub PR 时使用 `gh` 获取元数据和 diff:**
   - `gh pr view <url> --json title,body,baseRefName,headRefName,commits,files` — PR 标题、正文、基础/头分支、提交列表和已更改文件列表。PR **正文** 通常包含最丰富的 "为什么"（设计上下文、截图、作者考虑的权衡）——在引言中引用或总结它。
   - `gh pr diff <url>` — 定义巡游范围的统一 diff。使用此 diff 确认完整表面区域，而不仅仅是您在 `git diff` 中看到的。
   - 使用 PR 的 `baseRefName`（从上面的 JSON 中获取）作为 diff 基础——默认不是 `master`/`main`。像 `git log --reverse <baseRefName>..<headRefName>` 这样的命令按作者顺序遍历 PR 的提交。
   - 源文件可以从工作树中读取，因为 `diffity <pr-url>` 已经将 PR 分支检出本地。

4. **确定讲述故事的关键位置** — 那些文件和行范围，有人需要看到才能理解答案。

5. **注意配置依赖项**。如果行为基于环境变量、功能标志、配置文件或运行时条件而变化，请记录这些。它们必须在巡游中指明，以便读者了解 "当 X 配置时会发生这种情况，但如果 Y 被设置，流程会在此处不同"。

6. **规划逻辑步骤序列**，逐步构建理解。每个步骤都应该自然地引导到下一个步骤。

**选择步骤的指南:**
- 从真实的入口点开始——外部输入到达的地方（HTTP 路由、CLI 命令、计划任务、webhook）。配置、模式、常量和辅助函数是 **不是** 入口点；它们是流程的依赖项。
- 刚刚引入基础时介绍基础。当流程第一次读取模式时，巡游模式。当它第一次调用辅助函数时，巡游辅助函数。当它第一次引用配置值时，巡游配置。不要在流程开始之前预先加载大量基础部分。
- 至多允许一个 "定向" 步骤（例如显示所有端点的路由表）可以 precede 入口点。其他所有内容都应该由读者刚刚看到的内容驱动。
- 按照实际发生的顺序跟随执行路径。
- 只包括对理解必不可少的位置——跳过样板。
- 结束在最终结果（发送响应、持久化数据、渲染 UI）。
- 每个步骤应涵盖单个概念或代码部分。
- 尽可能包含具体示例（例如 "当用户运行 `diffity main` 时，这将变成..."）。

**自上而下，而不是自下而上**。巡游反映了代码在运行时的行为，而不是它是如何构建的。**不要** 走配置 → 模式 → 辅助函数 → 路由 → 动作。走路由 → 动作 → （查询读取它，因此出现模式）→ （处理程序引用它，因此出现配置）→ （调用它，因此出现辅助函数）。读者在引入每个新内容时保持上下文更好。读者应该感觉他们坐在你旁边，你正在跟踪一个真实的请求，而不是在演示开始之前坐下来听关于架构的讲座。

**处理跨模块流程**：当代码路径进入库、实用程序模块或深度嵌套的抽象时，决定是否跟随它：
- **跟随它** 如果那里的逻辑对于理解答案至关重要（例如一个转换请求的自定义中间件）
- **总结它** 如果模块执行标准或众所周知的功能（例如 "这调用 Express 路由器，它匹配路径并调用我们的处理程序"）——在步骤正文中提及它，而无需为它创建单独的步骤
- **跳过它** 如果它是纯样板或管道（例如重新导出、仅类型文件）

**跨多个文件应用的模式**。当一个更改在 N 个相似的调用位置上重复（例如，相同的守卫添加到 8 个处理程序，每个路由上都注册了相同的中介），**不要** 创建 N 个步骤。在最具代表性的文件上创建一个步骤，并使用完整上下文，然后在正文中将其他调用位置列为 goto 链接（"相同的守卫也添加到 X、Y、Z"）。一个概念，一个步骤——巡游应该教读者一次模式，而不是 N 次。例外：如果其中一个应用与 others 不同（例如在传输流程中调用两次，或使用不同的参数），请为这一个单独的步骤花费时间。

### Phase 2: 创建巡游

巡游 UI 有一个专门的解释面板。引言（来自 `tour-start --body`）显示为 **步骤 0** — 读者看到的第一个东西，填充整个面板。每个后续步骤在其旁边显示叙事内容，并高亮代码。由于面板空间充足，请编写丰富、详细的解释。

1. **开始巡游**，使用简短的主题标题和引言正文：
   ```
   diffity agent tour-start --topic "<short title>" --body "<intro>" --json
   ```

   `--topic` 显示在巡游面板标题中——将其限制为 **3-6 个词**（例如 "认证流程", "路由是如何工作的", "评论系统架构"）。**不要** 使用用户的完整问题作为主题。

   **编写引言正文（步骤 0）:**
   这是读者看到的第一个东西，并填充整个解释面板。使用此空间进行彻底的架构概述，以便在深入代码之前为读者设置所有必要内容。包括：
   - 涉及的关键组件/包/模块及其职责
   - 它们如何连接——数据流、调用链或依赖关系
   - 读者应该知道的键抽象或模式
   - 使用粗体文本的摘要流程图（例如 **CLI args → git diff → parser → JSON API → React render**）
   - **配置上下文** — 如果功能的行為取决于配置、环境变量或功能标志，请在此处提及它们，以便读者知道巡游假设的模式/状态

   如果您将一个宽泛的问题范围缩小，请说明您涵盖的内容："此巡游专注于 OAuth 登录流程。令牌刷新和会话管理是相关的，但分别涵盖。"

   使用丰富的 markdown 格式化——段落、粗体、`code`、表格、代码块。这不是一个将涵盖内容的目录；它是一个独立的概述，用于引导读者。

   从 JSON 输出中提取巡游 ID。

2. **按顺序添加步骤**。对于每个步骤：
   ```
   diffity agent tour-step --tour <id> --file <path> --line <start> --end-line <end> --body "<narrative>" --annotation "<short label>" --json
   ```

   **编写步骤内容:**

   - `--file`: 相对于仓库根的路径（例如 `src/server.ts`）
   - `--line` / `--end-line`: 要高亮的精确行范围。将其集中在相关部分。
   - `--annotation`: 一个简短标签（3-6 个词），显示为步骤标题。将其视为章节标题。
   - `--body`: 在解释面板中显示的叙事。它有充足的空间——使用它来编写详细的解释，使用 markdown：

   **在提交到步骤之前验证目标**。在调用 `tour-step` 之前，验证 `--file` 路径是否可以从仓库根读取，并且您描述的函数或代码块确实位于宣传的 `--line`/`--end-line` 范围内——读取该范围，而不是依赖会话早期的记忆。这同样适用于正文中的每个 `goto:` 链接：一个损坏的 goto 链接比没有链接更糟，因为读者信任它，并且在没有任何信号的情况下被带到错误的位置。如果您不确定确切的行，请使用普通反引号代码，而不是 goto 链接。

   **步骤正文结构**。每个步骤正文应按以下顺序遵循这个弧：
   1. **过渡**（1 句话）：连接到前一个步骤——见下文的示例。
   2. **解释**（主体）：这个代码做什么以及为什么它这样结构——设计决策、权衡、具体示例。如果范围被分成不同的部分，请使用子高亮 (`focus:X-Y`)。
   3. **要点**（1-2 句话）：一个陷阱、边缘情况或 "如果你要修改或扩展这个功能，可以从哪里开始?" 指针。

   没有过渡的步骤感觉被掉入；没有要点的步骤感觉不完整。每个步骤正文大约为 **150-300 个字**——只有在逻辑确实要求时才更长。如果您的草稿超过 400 字，该步骤可能试图涵盖两件事；考虑将其拆分。

   **步骤过渡——连接叙事:**
   每个步骤都应该感觉是前一个步骤的自然延续。以一个**过渡句子**开始每个步骤正文，将其连接到之前的内容：
   - "现在我们已经看到了请求是如何解析的，让我们看看它在哪里被验证..."
   - "我们刚刚看到的处理程序委托给这个服务，其中包含实际的业务逻辑..."
   - "此时数据已被转换并准备好持久化——这里是它如何发生的..."

   永远不要像读者突然从上下文中出现一样开始一个步骤。巡游是一个故事——每个步骤是一个章节，而不是一个孤立的段落。

   **要:**
   - 使用散文段落，在需要时补充结构化内容
   - 使用 `code` 表示函数名、变量、引用、命令。当引用一个存在于**已知文件和行**中的函数、类或代码符号时，将其制作成一个 **goto 链接**，以便读者可以点击跳转到那里。语法：`` [`symbolName`](goto:path/to/file.ts:startLine-endLine) `` 或 `` [`symbolName`](goto:path/to/file.ts:line) `` 用于单行。这些渲染为可点击的内联代码，可以导航到文件并高亮目标行。示例：`` [`handleDragEnd`](goto:src/KanbanContent.jsx:42-58) ``。使用普通反引号代码表示通用术语、CLI 命令或您尚未在代码库中定位的符号。
   - 使用 **粗体** 表示正在介绍的关键概念
   - 解释代码存在的原因和背后的设计决策，而不仅仅是代码做什么
   - 使用具体示例： "当您运行 `diffity main` 时，这一行调用 `normalizeRef('main')`，它计算 `git merge-base main HEAD`"
   - 使用表格表示映射（输入 → 输出，引用 → git 命令）
   - 使用代码块表示数据结构或命令输出
   - 将每个步骤与引言中的更大的图景联系起来
   - **指出边缘情况和陷阱** — 如果存在非明显行为、已知限制或 "看起来错误但实际上是故意" 的时刻，请标记它。这些是人们在稍后在此代码库工作时容易出错的东西。
   - 对于大型高亮范围，使用 **子高亮链接** 聚焦于步骤内的特定子部分。语法：`[label](focus:startLine-endLine)`。这些渲染为可点击的芯片，将高亮移动到指定的行。示例：

     ```markdown
     首先，该函数验证其参数：
     [参数验证](focus:15-22)

     然后核心转换处理每个条目：
     [核心转换](focus:25-40)

     最后，在返回之前缓存结果：
     [结果缓存](focus:42-48)
     ```

     当步骤涵盖 30+ 行时，使用子高亮。行范围必须在步骤的 `--line` / `--end-line` 范围内。

   **Mermaid 图表:**
   当一个概念更容易通过视觉理解时——架构关系、数据流、状态机、序列图——包括一个 mermaid 代码块。不要强迫每个步骤都使用图表；仅在它们确实有助于解释时使用它们。良好候选者：
   - 引言（步骤 0）概述：显示组件如何连接的流程图
   - 涉及多组件交互或请求流程的步骤
   - 状态机或生命周期转换
   - 类图，用于类型层次结构、结构关系
   - 流程图，用于算法、决策树、控制流

   选择最合适的图表类型：
   - `graph TD/LR` 用于架构、模块依赖、数据流
   - `sequenceDiagram` 用于调用链、请求/响应流
   - `stateDiagram-v2` 用于状态机、生命周期转换
   - `classDiagram` 用于类型层次结构、结构关系
   - `flowchart` 用于算法、决策树、控制流

   保持图表简洁（节点少于 ~12 个）。它们在巡游面板中内联渲染。

   **不要:**
   - 写一个墙上的项目符号——使用散文段落和格式化
   - 只描述语法——解释设计决策
   - 重复可见的代码信息
   - 在步骤正文中使用标题（注释充当标题）
   - 强迫每个步骤都使用图表——仅在它确实有助于时才添加一个
   - 没有过渡地开始一个步骤

### Phase 3: 在浏览器中打开

1. 从 `diffity list --json` 获取运行实例端口。
2. 打开巡游：`open "http://localhost:<port>/tour/<tour-id>"`（或用户 OS 的适当命令）。
3. 告诉用户巡游已准备好：

   > 您的巡游已准备好——检查您的浏览器。
