# Diffity 审查技能

你正在审查一个 diff 并使用 `diffity agent` CLI 留下内联评论。

## 参数

- `ref` (可选): 审查的 Git 引用 (例如 `main..feature`, `HEAD~3`)。默认为工作区变更。当同时提供 `ref` 和 `focus` 时，将两者都使用 (例如 `/diffity-review main..feature security`)。
- `focus` (可选): 将审查集中在特定区域。可选值: `security`, `performance`, `naming`, `errors`, `types`, `logic`。如果省略，则审查所有内容。

## CLI 参考

```
diffity agent diff
diffity agent list [--status open|resolved|dismissed] [--json]
diffity agent comment --file <path> --line <n> [--end-line <n>] [--side new|old] --body "<text>"
diffity agent general-comment --body "<text>"
diffity agent resolve <id> [--summary "<text>"]
diffity agent dismiss <id> [--reason "<text>"]
diffity agent reply <id> --body "<text>"
```

- `--file`, `--line`, `--body` 是 `comment` 所必需的
- `--end-line` 默认为 `--line` (单行评论)
- `--side` 默认为 `new`
- `general-comment` 创建一个 diff 级别的评论，不与任何文件或行关联
- `<id>` 接受完整的 UUID 或 8 字符前缀

## 前置条件

1. 检查 `diffity` 是否可用：运行 `which diffity`。如果未找到，使用 `npm install -g diffity` 安装它。

## 说明

### 第 1 步：确保 diffity 正在运行正确的引用 (不打开浏览器)

审查需要一个运行会话，其引用与请求的引用匹配。引用不匹配会导致在添加评论时出现 "文件不在当前 diff 中" 的错误。

1. 运行 `diffity list --json` 获取所有运行中的实例。解析 JSON 输出并找到 `repoRoot` 与当前仓库匹配的条目。
2. 如果存在匹配的条目，将其 `ref` 字段与请求的引用进行比较：
   - 注册表为工作区会话存储 `"work"`，为命名引用存储用户提供的引用字符串 (例如 `"main"`，`"HEAD~3"`)。
   - 如果引用 **匹配** → 重用会话，记下端口，然后继续到第 2 步。
   - 如果引用 **不匹配** → 重新启动：运行 `diffity <ref> --no-open --new` (如果没有引用，则运行 `diffity --no-open --new`)。`--new` 标志会杀死旧会话并启动一个新的。使用 Bash 工具，设置 `run_in_background: true`。等待 2 秒，然后使用 `diffity list --json` 验证并记下端口。
   - 如果 **没有请求引用** 且运行会话的引用不是 `"work"` → 使用 `diffity --no-open --new` 重新启动 (运行会话是为命名引用，但我们需要工作区)。
3. 如果 **此仓库没有运行会话**，在后台启动一个：
   - 命令：`diffity <ref> --no-open` (如果没有引用，则运行 `diffity --no-open`)
   - 使用 Bash 工具，设置 `run_in_background: true`
   - 等待 2 秒，然后使用 `diffity list --json` 验证并记下端口。

### 第 2 步：审查 diff

1. **直接从 diffity 获取统一 diff** — 这会自动处理合并基解析、未跟踪文件和所有引用类型：
   ```
   diffity agent diff
   ```
   这会输出当前会话的完整统一 diff。行号在 `@@` 段头中。
2. 查找并阅读所有相关的 CLAUDE.md 文件 — 根 CLAUDE.md 和任何包含已修改文件的目录中的 CLAUDE.md 文件。这些文件定义了项目特定的规则，diff 必须遵循。

#### 评估变更大小并调整你的策略

3. **评估 diff 大小** 并规划你的方法。无论 diff 大小如何，每个文件都会得到彻底审查 — 区别在于你如何组织工作：
   - **小** (少于 ~100 行变更，1-3 个文件)：直接 — 按顺序审查每个文件。
   - **中** (100-500 行变更，3-10 个文件)：按区域分组文件 (例如后端、前端、测试、配置)。首先审查核心逻辑文件，以便在审查涟漪效应之前理解意图。
   - **大** (500 行以上变更或 10 个以上文件)：按区域分组文件。先从核心逻辑开始，然后审查每个剩余文件。对于机械重复的变更 (例如对 20 个文件应用相同的重命名)，在第一个几个实例上验证模式是否正确，然后检查每个剩余实例是否有偏离模式的异常 — 不要跳过任何，但一旦模式建立，你可以更快地检查它们。

   无论大小如何，**阅读并审查每个变更的文件**。不要跳过或抽查文件。

#### 在审查之前理解变更

4. **首先总结变更**。在寻找问题之前，构建一个 diff 的心理模型：
   - 这个变更试图完成什么？(新功能、错误修复、重构、配置变更)
   - 哪些文件是结构性变更，哪些是核心逻辑变更？
   - 作者的意图是什么？阅读提交信息 (`git log --oneline <args>`) 和任何链接的问题或 PR 描述以获取上下文。
   - 作者做出的关键决策是什么，以及他们是在什么约束下工作的？

   理解意图有助于你区分有意行为和真实错误。

5. 对于每个变更的文件 (根据上述大小策略调整)，阅读整个文件 (而不仅仅是 diff 段)，以了解完整上下文。
6. **交叉引用调用者和依赖项**。对于任何变更的函数签名、重命名导出、修改的返回类型或行为更改：在整个代码库中 grep 使用情况。一个在隔离状态下看起来正确的函数可能会破坏每个调用者。检查：
   - 谁调用这个函数？他们会处理新的返回值/错误/空值情况吗？
   - 谁导入这个模块？更改的导出名称会解析吗？
   - 这个类型更改是否正确传播到消费者？
7. 使用以下技术分析代码变更。如果提供了 `focus` 参数，则专注于该区域。否则，应用所有分析过程和信号阈值。

#### 如何分析

diff 告诉你 *什么* 变更了；周围的代码告诉你变更是否 *正确*。应用这些分析过程：

**数据流分析** — 通过变更的代码跟踪值。每个变量来自哪里？它去哪里？检查：
- 值是否可能在变更的代码假设它不存在的位置为空/未定义？
- 变更的代码是否处理了上游条件的所有分支？
- 如果函数的返回类型更改，所有调用者是否处理了新的形状？
- 是否有缩窄检查 (例如 `if (x)`)，diff 意外移动到了外面？

**状态和生命周期分析** — 对于有状态代码 (React 状态、数据库事务、流、事件监听器)：
- 变更是否创建了一个无法达到或无法退出的状态？
- 资源 (监听器、订阅、文件句柄) 是否在所有路径上都被清理？
- 并发访问是否会破坏共享状态？
- 操作的顺序是否仍然满足不变式 (例如初始化在使用之前)？

**契约分析** — 检查变更的代码是否满足它必须满足的契约：
- 该函数是否仍然满足调用者期望的内容？(阅读调用者，不要猜测)
- 如果它实现了接口或重写了基方法，它是否仍然符合？
- 前提条件和后置条件是否保留？
- 对于 API 端点：响应形状是否与客户端发送/期望的匹配？

**边界分析** — 对于系统边界的代码 (用户输入、网络、文件 I/O、IPC)：
- 用户控制的输入在使用前是否经过验证？
- 格式不正确的外部数据是否会崩溃进程或损坏状态？
- 是否有注入向量 (SQL、shell、XSS、路径遍历)？

**边缘情况分析** — 仅适用于实际会发生的情况，而不是理论上的情况：
- 空数组/字符串、零、负数 — 代码是否处理它们？
- 循环、切片或索引算术中的 off-by-one
- 整数溢出、除以零 (除数来自输入)

#### 完整性检查

在分析代码正确性后，检查变更是否 **完整** — 不仅是正确的，而且是完成的：

**测试覆盖率**:
- 如果 diff 添加了新行为 (新函数、端点、UI 流程、分支)，是否有测试覆盖它？如果没有，将其标记为 `[建议]`。
- 如果 diff 修复了错误，是否有测试会捕获该错误？回归测试防止重新引入。
- 如果 diff 修改了现有行为，现有测试是否更新以匹配？过时的测试仍然通过比没有测试更糟 — 它们提供虚假的信心。
- 如果 diff 包括测试，请审查它们的质量：
  - 它们是否测试了 **正确的内容**？(行为，而不是实现细节)
  - 它们是否覆盖了代码处理的 **边缘情况**？(空输入、错误路径、边界值)
  - 它们是否 **隔离**？(没有对测试顺序或全局状态的隐藏依赖)
  - 即使代码损坏，它们是否也能通过？(自反断言、模拟掉的逻辑)

**缺失部分**:
- 没有迁移的架构变更？
- 没有文档或默认值的新的环境变量？
- 没有更新锁定文件的依赖项？
- 没有客户端端更新的变更 API 响应？
- 没有在调用位置处理的新的错误类型？
- 没有清理相关代码的移除功能 (死导入、未使用的配置、孤儿测试)？

仅标记那些 **明显需要** 此变更才能正确工作的缺失部分。不要标记有抱负的改进。

#### 要标记的内容

标记会影响正确性、安全性或可靠性的真实问题：
- 将导致编译失败、解析失败或运行失败的代码 (语法错误、类型错误、缺失导入、未解析的引用)
- 会导致错误结果的逻辑错误 (明显的错误、off-by-one 错误、损坏的条件)
- 变更代码中的安全漏洞 (注入、XSS、认证绕过、数据暴露)
- 你可以用具体场景证明的竞态条件或数据丢失风险
- CLAUDE.md 违规，你可以引用被违反的确切规则
- 破坏的契约 — 一个变更的函数不再满足其调用者期望的内容
- 新或变更行为的缺失测试 (作为 `[建议]`，而不是 `[必须修复]`，除非项目的 CLAUDE.md 要求测试)
- 不完整的变更 — 迁移、配置、客户端端更新，这些显然需要此变更才能工作

跳过样式问题、linter 捕获的问题和未更改代码中的现有问题。专注于 diff，而不是整个文件。

#### 在评论之前验证

对于每个发现，验证它是真实的再发布：
- 重新阅读周围的代码 — 许多明显的错误在完整上下文中消失
- 对于 "缺失导入" 或 "未定义变量" 的声明，grep 确认
- 对于损坏的调用者，阅读实际的调用位置
- 对于 CLAUDE.md 违规，确认规则仅适用于此文件
- 对于缺失的测试，检查是否有其他文件中已经有一个测试覆盖了此路径

如果重复的模式出现在多个文件中，在第一个出现的地方评论，并在一般摘要中提及模式，而不是重复评论。

### 第 3 步：留下评论

1. **按严重性顺序评论**。首先发布所有 `[必须修复]` 评论，然后是 `[建议]`，然后是 `[问题]`。在每个严重性内，按文件顺序排列。这确保了如果作者快速浏览，最重要的问题会被首先看到。

2. 在评论正文中使用严重性前缀对每个发现进行分类：
   - `[必须修复]` — 错误、安全问题、数据丢失风险。会破坏或产生错误结果的代码。
   - `[建议]` — 具体改进，有明确的理由。不是样式偏好 — 真实的改进。这包括缺失的测试、不完整的变更和更好的方法。
   - `[问题]` — 不明确的内容，需要作者澄清。

3. 对于每个发现，使用以下方式留下内联评论：
   ```
   diffity agent comment --file <path> --line <n> [--end-line <n>] [--side new] --body "<comment>"
   ```
   - 使用 `--side new` (默认) 对添加/修改的代码评论
   - 使用 `--side old` 对删除的代码评论
   - 使用 `--end-line` 当问题跨越多行时
   - **以问题开头**，而不是背景。具体且可操作。
   - 对于小、自包含的修复，包括一个显示修复的代码建议
   - 对于较大的修复 (结构性变更、多位置)，描述问题和建议方法，而不使用完整的代码块
   - 如果标记 CLAUDE.md 违规，引用被违反的确切规则
4. 留下所有内联评论后，决定是否需要一般评论：
   - **无发现 → 留下一个一般评论**："未发现问题。检查了错误和 CLAUDE.md 合规性。"
   - **1-2 个发现 → 跳过一般评论**，除非存在内联评论未涵盖的跨领域问题。
   - **3 个以上发现 → 留下一个一般评论**，总结主题。
   - **大 diff → 总是留下一个一般评论**，注明审查范围并按区域分组发现。
   - **不要在一般评论中使用严重性前缀** — 前缀仅用于内联发现。
   - 以结论开头，直接简洁 — 没有赞美，没有填充，没有描述代码做什么。
   ```
   diffity agent general-comment --body "<整体审查摘要>"
   ```

### 第 4 步：打开浏览器

1. 现在评论已准备好，打开浏览器：
   ```
   diffity open <ref>
   ```
   如果提供了引用 (例如 `diffity open HEAD~3`)，请传递引用参数。省略它以打开默认视图。
2. 告知用户审查已完成，他们可以检查浏览器。示例：

   > 审查完成 — 检查你的浏览器。
   >
   > 发现：2 个必须修复，1 个建议
   >
   > 准备好时，运行 **/diffity-resolve** 修复它们。
