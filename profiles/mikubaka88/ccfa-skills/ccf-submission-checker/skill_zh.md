# CCF 提交检查器

## 家庭文件合同

在编写前，确定每个任务/成果的规范输出和一个稳定的可工作目录。重用明确的或已建立的路径；否则使用项目根目录 `ccfa-workfiles/<用途>/<成果ID>/`，仅在需要时使用 `source/`、`assets/`、`cache/` 和 `build/`。就地更新当前文件；不要分散中间文件或创建迭代副本。保留输入和所需证据；仅清理由此任务创建的已验证的可丢弃文件。使用 UTF-8 文本 I/O，并在保存或渲染后检查中文文本。对于文件工作，应用 [artifact-contracts.md](../ccf-common/references/artifact-contracts.md) 并在技能转换时重用相同的路径。

## 协作合同

在专家执行前，先阅读并应用 [ccf-humanization](../ccf-humanization/SKILL.md)，然后应用 [ccf-common](../ccf-common/SKILL.md)。在每次交接时，重用其适用的活跃规则或刷新缺失/更改的规则。即使没有文本，这两个预检也是必需的；详细的编辑、实验和维护模式仅在相关时运行。

保留一个集成的负责人，并积极使用其他技能来解决缺失的先决条件或检查材料发现。重用适用的证据；不要跳过必要的准备工作以节省代币。在最终确定前，集成贡献并验证受影响的成果。遵循条件性的 [合作路线](../ccf-common/references/routing.md)；避免不相关的阶段和重复报告。

## 核心规则

将提交视为一个构建、场地政策、页面预算和成果就绪的关卡。使用本地场地指南获取预期规则，然后要求官方政策的最新性以做出最终决定。不要重写论文内容。

## 模式

- `venue-format`：模板、页面限制、匿名性、作者块、补充和最终版规则。
- `package-check`：LaTeX/PDF 构建、元数据、字体、页数、文件结构和提交清单。
- `artifact`：代码/数据/模型发布计划、环境、种子、硬件、许可证、成果 README 和可复现性附录。
- `full`：场地 + 包裹 + 成果。

## 工作流

1. 确定场地/年份/赛道、提交模式、项目目录、TeX/PDF 文件、补充/成果文件和截止日期压力。
2. 当可用时，读取 `ccfa.yaml`。如果缺失，使用提供的文件并说明项目状态跟踪不可用。
3. 对于场地问题，在检查官方新鲜性之前，先阅读 `../ccf-paper-writer/references/venue-guides/index.md` 和特定的场地指南。
4. 对于包裹检查，检查实际的 TeX/PDF/构建输出，为确切的场地/年份/赛道计算页面，匿名性，字体，元数据，参考文献和适用的所需表格。对于 ICLR 2027，应用匹配指南的年份特定模板、阶段特定页面预算和 AI 使用声明/表格检查；未确认的使用事实保持未验证。阅读日志和受影响的页面；不要从文件存在推断构建成功。
5. 对于成果检查，构建可复现性清单：代码、数据、模型、环境、种子、硬件、许可证、访问限制和 README。
6. 交由 `ccf-paper-writer` 进行文本/页面重写：超出限制时压缩，实际解释缺失时实质性扩展，预算内时正常润色。交由 `ccf-experiment-designer` 处理缺失的可复现性实验，交由 `ccf-visual-composer` 处理图形/表格浮动顺序、标题位置、字体、裁剪、调色板或视觉可读性修复，交由 `ccf-rebuttal-writer` 处理审阅后响应的打包。

## 输出合同


## 检查范围

遵循 `../ccf-common/references/handoff-modes.md` 和 `../ccf-common/references/task-modes.md`。运行与请求模式相关的实际成果相关的检查。区分通过、失败、不适用和未验证；缺失的工具不表示通过或失败。记录官方规则 URL 和检查日期。重用项目构建配置，并将生成的日志/预览放置在已建立的或共享的任务构建目录中。就地更新规范就绪报告，并区分旧的 PDF 和成功的当前构建。修复后仅重新检查受影响的构建表面。单独页数预算不足不是场地违规。不要仅仅因为请求了就绪检查而上传或提交文件。
