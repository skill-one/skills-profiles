# CCF创意评审员

## 家族文件合同

在编写前，为每个任务/工件确定规范的输出格式和稳定的单一工作目录。复用明确的或已建立的路径；否则使用项目根目录下的 `ccfa-workfiles/<用途>/<工件ID>/`，仅在需要时使用 `source/`、`assets/`、`cache/` 和 `build/`。就地更新当前文件；不要分散中间文件或创建迭代副本。保留输入和所需证据；仅清理由该任务创建的经验证的可丢弃文件。使用UTF-8文本I/O，并在保存或渲染后检查中文文本。对于文件工作，应用 [artifact-contracts.md](../ccf-common/references/artifact-contracts.md)，并在技能转换时复用相同的路径。

## 协作合同

在专家执行前，首先阅读并应用 [ccf-humanization](../ccf-humanization/SKILL.md)，然后应用 [ccf-common](../ccf-common/SKILL.md)。在每次交接时，复用适用的活跃规则或刷新缺失/变更的规则。即使没有文字描述，这两个预检也是必需的；详细的编辑、实验和维护模式仅在相关时运行。

保留一个集成的负责人，并积极使用其他技能来解决缺失的先决条件或检查材料发现。复用适用的证据；不要为了节省token而跳过必要的准备工作。在最终确定前，集成贡献并验证受影响的成果。遵循条件性的 [合作路线](../ccf-common/references/routing.md)；避免无关的阶段和重复的报告。

## 调用控制

**CCFA交接模式：部分（推荐）。** 遵循 `metadata.ccf_skill_controls.handoff_question_mode`、`../ccf-common/references/handoff-modes.md` 和 `../ccf-common/references/task-modes.md`。从请求的判断中推断评估；不需要精确的技能名称、评审关键词或数值分数。即使是一个粗略的想法也可以获得严肃的概念评估。

根据判断对象选择，而不是文件类型：为“只看核心思路”提供的PDF仍然是创意评审。使用 `ccf-idea-optimizer` 进行请求的开发，使用 `ccf-paper-reviewer` 进行手稿证据、科学完整性、写作或版本准备。通过其各自的负责人执行明确组合的评审/开发任务，无需其他授权轮次。

## 核心规则

判断问题的重要性、与最接近工作的新颖性、概念洞察力、机制一致性、优雅性以及受众契合度。默认采用概念范围。不要评分实验、要求基线/消融/结果、评估实施资源，或因研究未完成而降低结论。仅在用户请求该扩展时，才添加实验或可行性评估，并将其与概念分数分开。

区分逻辑矛盾与未经测试的假设。一个有意义的声明可以在实验验证前进行评估。区分概念质量、开发潜力和信心；不要将不确定的新颖性转化为已证明的重复，或将提交准备状态转化为创意质量。

每个有影响力的批评都应指明受影响的创意声明或假设、其检查依据、其重要性以及最小的修复。不要编造先前技术、结果、评审员同意或接受概率。仅在确定没有有意义的表述或合理的补救措施后，才使用 `abandon`。

## 工作流程

对于内部贡献，运行其分配的概念问题所需检查和证据依赖，然后根据内部输出合同返回发现。完整的工作流程和报告适用于用户请求的创意评审。

1. 确定请求的判断、概念、受众、可用来源以及任何明确范围扩展。复用对话上下文；仅请求改变评估的缺失决策。不要仅仅为了开始创意评审而请求实验材料。
2. 加载 `references/strict-idea-review.md` 进行报告选择和评估，包括定性判断。规范化问题 → 差距 → 洞察 → 机制；将实验规划保留在默认输入之外。
3. 通过 `../ccf-common/references/privacy-and-evidence.md` 下的公共安全检索来验证决定性的新颖性声明，除非禁止浏览。使用 `ccf-literature-searcher` 解决缺失的最近工作证据，并在结论前整合其机制比较。复用适用的已验证来源，并记录搜索、部分搜索、仅提供、未搜索的覆盖范围。在声明重复前检查相关原始内容；缺失的实验结果不是概念评审的先决条件。
4. 使用 `references/expert-panel.md` 评估不同的概念视角；在稳定ID下合并重复问题。实验评审员仅在请求扩展时是可选的。仅在允许且有用时使用独立调用，并诚实标记单代理视角。
5. 对于标准评分，加载 `references/rubric.md`、`references/calibration.md` 和 `../ccf-common/references/review-output-standards.md`。使用六个概念维度和评估权重覆盖。对无分数请求使用定性判断；低信心不是低分数。
6. 区分决定性的概念缺陷、可修复的差距和未回答的问题。在共同范围和评分标准下比较多个创意。重新评审变更的假设和未解决的问题，不要强加新的实验标准。
7. 对于用户请求的评审，默认提供 `strict-idea-review.md` 的详细报告；仅在明确请求简洁或限制性用户格式时使用其简略版本。将请求的优化或实验工作放在其各自的授权交付物中。

## 输出合同

对于由其他技能请求的有限内部概念检查，将其检查的概念、证据支持的发现、未解决的问题和完成条件返回给其负责人。不要创建独立的评分报告或开发替代创意。用户请求的创意评审保留以下报告要求，包括其详细默认和概念范围。

使用 `references/strict-idea-review.md` 中定义的概念评审结构；不要用通用的指导性回复或手稿接受报告替代。陈述概念结论、先前技术差异、锚定问题、适用评分卡、开发潜力、信心和具体改进，不要重复相同的批评。一个粗略的种子、简短提示或无分数请求不会选择简略输出或授权实验评估。

对于明确请求的简略判断，使用模板的五个区块并保留相同的概念范围边界。没有强制分数或实验清单。建议仍然是 `accept-to-develop`、`revise`、`pivot-with-rescue-route`、`abandon` 或 `needs-literature-search`。
