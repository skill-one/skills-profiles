# 从前端代码中提取设计系统

分析前端源代码，提取一个全面的文档（DESIGN.md），捕捉项目的视觉语言——颜色、排版、间距、组件模式和布局原则——直接从源文件中提取，无需构建或渲染应用程序。

## 存在的原因

`design-md` 技术基于渲染后的 HTML 工作。但通常你有一个代码库，并且在你甚至可以运行应用程序之前就想了解其设计系统——也许依赖项缺失、构建损坏，或者你只是想进行快速审计。此技术读取源文件本身：样式表、组件文件、主题配置和 Tailwind 设置。它更快，并且可以在任何地方工作。

## 使用场景

- 用户有一个前端代码库，并希望提取或记录其设计系统
- 用户希望将项目的视觉身份迁移到 Stitch
- 用户要求“审计样式”或“了解仓库的设计语言”
- 用户希望从现有源代码创建 DESIGN.md
- 应用程序无法构建/渲染，但源代码可用
- 用户希望统一或协调代码库中不一致的样式

## 前置条件

- 可以访问前端项目的源目录
- 无需构建或运行时依赖项——此技术仅读取源文件

## 工作流程

### 第一阶段：项目发现

首先了解你要处理的内容。这决定了要使用哪些提取模式。

#### 1. 检测框架和堆栈

扫描项目根目录以查找线索文件：

| 信号文件 | 框架/工具 |
|:---|:---|
| `package.json` 包含 `react` | React / Next.js |
| `package.json` 包含 `vue` | Vue / Nuxt |
| `package.json` 包含 `svelte` | Svelte / SvelteKit |
| `package.json` 包含 `@angular/core` | Angular |
| `tailwind.config.js/ts` | Tailwind CSS |
| `postcss.config.js` | PostCSS 管道 |
| `styled-components` 或 `@emotion` 在依赖项中 | CSS-in-JS |
| `.css` / `.scss` / `.less` 文件仅 | 纯 CSS / SASS |
| `theme.js` / `theme.ts` / `tokens.js` | 设计令牌文件 |

首先读取 `package.json`——它揭示了框架、CSS 工具以及任何设计令牌库（例如，`style-dictionary`、`@chakra-ui/react`、`@mui/material`、`ant-design`）。这种上下文告诉你要在哪里查找样式信息。

#### 2. 映射源树

识别你要分析的键目录和文件：

```
src/
├── components/     ← 组件级样式
├── styles/         ← 全局样式表
├── theme/          ← 主题定义、令牌
├── assets/         ← 字体、图像
├── app.css         ← 根样式
└── index.css       ← 入口 CSS
```

还要检查：
- `tailwind.config.js` / `tailwind.config.ts` — 自定义颜色、字体、间距
- `globals.css` / `global.css` — CSS 自定义属性（变量）
- 任何 `theme.*` 或 `tokens.*` 文件
- 组件库配置（例如，`chakra-theme.ts`、`vuetify.config.ts`）

#### 3. 阅读框架特定指南

查阅适当的参考以获取提取模式：

- **React / Next.js / Tailwind** → [references/react-tailwind.md](references/react-tailwind.md)
- **Vue / Nuxt** → [references/vue.md](references/vue.md)
- **Svelte / SvelteKit** → [references/svelte.md](references/svelte.md)
- **Angular** → [references/angular.md](references/angular.md)
- **纯 CSS / SASS / Less** → [references/plain-css.md](references/plain-css.md)

这些参考包含特定于框架的模式，用于定位颜色、排版、间距和组件样式。在进行下一步之前，请阅读与你的框架匹配的参考。

### 第二阶段：深度提取

系统地处理每个设计维度。对于每个维度，从源文件中收集原始数据，然后将其综合成描述性语言。

目标不是列出每个 CSS 属性——而是理解样式选择背后的意图，并用人类、编辑性语言描述它们，以便另一位设计师（或 Stitch）可以使用它们来重现相同的视觉效果。

#### 1. 视觉主题和氛围

首先读取最广泛的样式，以了解整体情绪：

- **根背景**：`body` 或根元素的背景是什么？浅奶油色（#f-range）表示轻盈/干净；深色（#0-#2 范围）表示情绪化/戏剧性。
- **空白处哲学**：间距值是慷慨（32px+）还是紧凑？检查根容器、部分包装器和卡片组件上的填充/边距值。
- **密度**：计算每页/部分的组件数量。少且有空间 = 极简；密集打包 = 信息密集。
- **色温**：中性色是温暖的（奶油、棕色）还是凉爽的（蓝灰色、板岩）？
- **整体感觉**：综合成 1-2 句丰富的句子来捕捉情绪。

在源中查找这些信号：

| 源位置 | 它告诉你什么 |
|:---|:---|
| 根 `background-color` 或 Tailwind `bg-*` 在布局上 | 整体明暗度 |
| Tailwind 配置中的间距比例或 CSS 变量 | 空白处哲学 |
| 组件数量与包装器填充的比较 | 密度 |
| 自定义属性命名（`--warm-*` vs `--cool-*`） | 色温意图 |
| 主题文件中的注释 | 开发人员自己话中的设计意图 |

#### 2. 色彩调色板和角色

从代码库中提取每个唯一颜色，并分配功能角色。跨所有层搜索：

**在哪里查找颜色：**

| 层 | 搜索内容 |
|:---|:---|
| CSS 自定义属性 | `--color-*`、`--primary`、`--bg-*` |
| Tailwind 配置 | `theme.extend.colors` |
| 主题/令牌文件 | 颜色对象、调色板 |
| 组件样式 | `background-color`、`color`、`border-color` |
| 内联/作用域样式 | 模板中的 `bg-*`、`text-*` 类 |
| CSS-in-JS 主题对象 | `colors`、`palette` 键 |

**如何组织**：按功能而不是按色调分组颜色：

1. **主要基础**——背景和表面颜色
2. **强调和交互**——CTA 按钮和活动状态、链接
3. **排版和文本层次结构**——主要、次要、次要文本
4. **功能状态**——成功、错误、警告、信息

为每个颜色创建一个描述性名称，唤起颜色的个性，而不是其原始十六进制值：

- ❌ `#294056` → "蓝色"
- ✅ `#294056` → **"深淡青色-海军蓝"** → 主要 CTA、活动导航

**去重很重要**。代码库中经常有近乎重复的颜色（例如，`#333` 和 `#2C2C2C`）。将它们合并到最能代表预期颜色的一个名称下。

#### 3. 排版规则

提取完整的排版系统：

**字体家族：**
- 检查 CSS `font-family`、Tailwind `fontFamily`、Google 字体链接或本地 `@font-face` 声明。
- 注意每个字体的**个性**：几何形状与人文主义、衬线与无衬线、它唤起的感受。

**类型比例（层次结构）：**
- 查找每个标题级别（H1-H6）和正文文本，注意：
  - `font-size`（以 rem 或 px 为单位）
  - `font-weight`（数值 + 描述性名称）
  - `letter-spacing`（以及原因——优雅？紧凑？）
  - `line-height`（宽松用于可读性？紧凑用于显示？）
- 映射组件使用情况：产品卡片使用哪个标题级别？英雄部分呢？

**间距原则：**
- 文本间距如何与整体间距比例相关？
- 标题与正文之间的字母间距模式
- 行高哲学（正文宽松/放松？显示紧凑？）

#### 4. 组件样式

分析 4-5 个最重要的 UI 基本元素：

**按钮：**
- 圆角（以及它传达的信息——俏皮？专业？极简？）
- 主要、次要和幽灵变体的颜色方案
- 悬停/焦点/活动状态和过渡时间
- 填充比例（水平与垂直）

**卡片/容器：**
- 圆角（通常与按钮不同——稍微圆润）
- 阴影策略：平面、微妙的悬停阴影、始终突出？
- 边框处理：发丝边框、彩色强调、无？
- 内部填充（慷慨或紧凑？）
- 卡片内图像处理（全宽、填充、圆润？）

**导航：**
- 布局模式（水平条、垂直侧边栏、抽屉）
- 排版处理（大写字母、字母间距、重量）
- 活动悬停状态指示器（下划线、颜色、背景）
- 移动行为（汉堡包、底部导航、抽屉）

**输入和表单：**
- 边框样式和焦点状态行为
- 与按钮一致的圆角样式
- 填充和触摸目标尺寸

**特定域组件：**
- 识别 1-2 个此项目特有的组件（例如，产品卡片、仪表板小部件、聊天气泡），并描述其样式模式。

#### 5. 布局原则

提取结构系统：

**网格和结构：**
- 最大内容宽度（来自容器上的 `max-width`）
- 列系统（CSS 网格、Flexbox 模式、定义断点）
- 响应式断点（来自媒体查询或 Tailwind 配置）

**空白处策略：**
- 基础间距单位（8px 网格？4px？自定义？）
- 部分边距（主要部分之间有多少空间）
- 边缘填充（不同断点处的页面边距）

**对齐和视觉平衡：**
- 文本对齐模式（英雄部分居中、正文左对齐）
- 图像与文本比例
- 视觉重量分布

**响应式行为：**
- 移动优先还是桌面优先？
- 网格如何折叠？填充比例？
- 触摸目标尺寸

#### 6. Stitch 生成说明

将提取综合为 Stitch 的可操作提示：

- **氛围语言**：将情绪转化为自然描述
- **颜色参考**：按描述性名称 + 十六进制列出颜色
- **组件提示**：编写 2-3 个示例提示，可以重新创建 Stitch 中的关键组件
- **迭代指导**：关于在此设计系统中完善屏幕的提示

### 第三阶段：编写 DESIGN.md

将所有内容组装成标准的 DESIGN.md 格式。将其放置在项目目录的 `.stitch/DESIGN.md` 中（如果不存在，则创建 `.stitch/` 目录）。

> [!IMPORTANT]
> 你**必须**在文件顶部包含 YAML 前置符，包含 `name` 和 `colors` 映射，与 [examples/DESIGN.md](examples/DESIGN.md) 中的示例完全相同。这种结构化数据是其他技能解析设计系统所必需的。
>
> 如果不包含此 YAML 块，至少包含核心颜色令牌，则表示未能正确使用此技术。

使用 [examples/DESIGN.md](examples/DESIGN.md) 中的格式作为模板。该文件必须以 YAML 块开头，然后是 Markdown 部分：

```markdown
# 设计系统：[项目名称]
**项目 ID：** [如果知道，否则省略]

## 1. 视觉主题和氛围
[关于情绪、哲学和关键特征的丰富 2-段描述]

## 2. 色彩调色板和角色
### 主要基础
### 强调和交互
### 排版和文本层次结构
### 功能状态

## 3. 排版规则
### 层次结构与权重
### 间距原则

## 4. 组件样式
### 按钮
### 卡片和 [特定域容器]
### 导航
### 输入和表单
### [特定域组件]

## 5. 设计系统用于 Stitch 生成的说明
### 要使用的语言
### 颜色参考
### 组件提示
### 增量迭代
```

### 第四阶段：集成（可选）

如果用户希望将设计系统推入 Stitch：

1. 交给 `manage-design-system` 技术进行 MCP 创建/更新调用

如果用户只需要文档，则在第三阶段完成后即可完成。

## 质量检查清单

在交付 DESIGN.md 之前，请验证：

- [ ] 每个颜色都有一个描述性名称、十六进制代码和功能角色
- [ ] 排版包括字体家族、个性描述和完整层次结构
- [ ] 组件样式描述形状、颜色、状态和过渡
- [ ] 布局包括最大宽度、网格、断点和间距策略
- [ ] Stitch 生成说明使用自然语言，而不是 CSS 语法
- [ ] 氛围部分读起来像编辑性副本，而不是技术文档
- [ ] 近似重复的颜色已合并
- [ ] 文档捕捉了样式背后的意图，而不仅仅是原始值

## 更好提取的技巧

- **阅读注释和提交消息。** 开发人员经常在代码注释（`/* 英雄部分——呼吸空间 */`）和提交消息中记录设计意图。这些是理解“为什么”的黄金来源。
- **检查设计令牌库。** 如果项目使用 `style-dictionary`、`@tokens-studio` 或类似工具，这些文件是设计值的最权威来源。
- **主题文件比组件样式更具信号。** 定义调色板的 `theme.ts` 告诉你预期的设计系统；组件中分散的行内样式告诉你实际发布的样式。两者都很重要，但首先从主题开始。
- **Tailwind 配置是一个设计系统。** 如果项目有一个自定义的 `tailwind.config.js`，那么这*就是*设计系统——首先从中提取，然后检查组件以查找覆盖。
- **CSS 自定义属性是故意的。** 如果开发人员定义了 `--brand-primary`，他们告诉你这是一个设计令牌。尊重这一点。
