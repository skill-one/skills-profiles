# PyTorch PR 审核技能

审核 PyTorch 拉取请求，重点关注 CI 无法检查的内容：代码质量、测试覆盖率是否充分、安全漏洞和向后兼容性。

## 使用模式

### 无参数

如果用户使用 `/pr-review` 命令且不带任何参数，**不要执行审核**。相反，询问用户想要审核的内容：

> 我想让我审核什么？
> - PR 编号或 URL（例如，`/pr-review 12345`）
> - 本地分支（例如，`/pr-review branch`）

### 本地 CLI 模式

用户提供 PR 编号或 URL：

```
/pr-review 12345
/pr-review https://github.com/pytorch/pytorch/pull/12345
```

要进行详细的逐行具体评论的审核：

```
/pr-review 12345 detailed
```

使用 `gh` CLI 获取 PR 数据：

```bash
# 获取 PR 详情
gh pr view <PR_NUMBER> --json title,body,author,baseRefName,headRefName,files,additions,deletions,commits

# 获取差异
gh pr diff <PR_NUMBER>

# 获取 PR 评论
gh pr view <PR_NUMBER> --json comments,reviews
```

### 本地分支模式

审核当前分支中不在 `main` 分支中的更改：

```
/pr-review branch
/pr-review branch detailed
```

使用 git 命令获取分支更改：

```bash
# 获取当前分支名称
git branch --show-current

# 获取与 main 相比发生更改的文件列表
git diff --name-only main...HEAD

# 获取与 main 相比的完整差异
git diff main...HEAD

# 获取分支的提交日志
git log main..HEAD --oneline

# 获取与 main 相比的差异统计（更改的文件、插入、删除）
git diff --stat main...HEAD
```

对于本地分支审核：
- "摘要" 应根据提交消息和差异描述分支更改所实现的目标
- 在审核标题中使用当前分支名称，而不是 PR 编号
- 所有其他审核标准与 PR 审核相同

### GitHub Actions 模式

当通过 `@claude /pr-review` 在 GitHub PR 上调用时，该操作会预取 PR 元数据并将其注入提示中。通过提示中存在 `<formatted_context>`、`<pr_or_issue_body>` 和 `<comments>` 标签来检测此模式。

提示中已包含：
- PR 元数据（标题、作者、分支名称、增加/删除、文件数量）
- PR 正文/描述
- 所有评论和审核评论（带文件/行引用）
- 已更改文件列表，包括路径和更改类型

使用 git 命令获取差异和提交历史。基础分支名称在提示上下文中（查找 `PR Branch: <head> -> <base>` 或 `baseBranch` 字段）。

```bash
# 获取与基础分支的完整差异
git diff origin/<baseBranch>...HEAD

# 获取差异统计
git diff --stat origin/<baseBranch>...HEAD

# 获取此 PR 的提交历史
git log origin/<baseBranch>..HEAD --oneline

# 如果基础分支引用不可用，请先获取它
git fetch origin <baseBranch> --depth=1
```

在此模式下**不要**使用 `gh` CLI 命令——仅使用 git 命令。所有 PR 元数据、评论和审核都已存在于提示上下文中；仅通过 git 获取差异和提交日志。

## 审核理念

单行代码可能具有深远的全局影响：缺少设备保护会导致多 GPU 上的静默数据损坏，缺少 `Composite` 分发键会破坏所有 out-of-tree 后端，手动 dtype 检查而不是 `TensorIterator` 会静默跳过类型提升。**将每一行代码视为潜在的承重部分。**

1. **仅报告问题** — 审核输出必须仅包含问题、关注点和可操作的建议。**不要**提及正确完成的事项，**不要**表扬良好决策，**不要**解释为什么某事是合适的。如果一个部分没有问题，请完全省略它。读者的时间宝贵——每一句话都必须指向需要修复或进一步讨论的内容。
2. **调查，不要猜测** — 当不确定检查清单项目是否适用时，启动一个子代理来阅读相关代码。猜测错误的审核者会提供负面价值。
3. **审核设计，而不仅仅是实现** — 一个 PR 可能具有正确实现的糟糕设计。质疑侧信道通信、开/关私有标志，并要求新组件之间接口的明确文档。
4. **关注 CI 无法检查的内容** — 不要评论格式、代码检查、类型错误或 CI 失败。关注设计质量、接口正确性、线程安全性、向后兼容性影响、测试充分性和模式遵循情况。
5. **所有问题都必须修复** — 没有所谓的“小问题”。如果值得提及，就值得修复。每个不一致都会随着时间的推移降低代码库的质量。
6. **具体且可操作** — 引用文件路径和行号。命名作者应使用的函数/类/文件。
7. **匹配即时上下文** — 阅读同一文件中类似功能的现有实现方式。文件内的模式不匹配总是错误的。
8. **假设能力** — 作者了解 PyTorch；仅解释非显而易见的上下文。
9. **无重复** — 每个观察结果在审核输出的一个部分中仅出现一次。

### 使用子代理

审核检查清单很大。你无法在脑海中保留每个基础设施系统的完整上下文。**启动子代理**来调查检查清单项目是否适用：阅读周围代码、PR 应使用的基础设施或应存在的测试。为独立区域并行启动它们。一个典型的中等 PR 应该启动 3-8 个子代理。

子代理故意重叠。预期两三个不同的子代理用不同的语言报告相同的缺陷；这表明重要性，而不是多样性。在步骤 4 中进行协调，然后再为它花费验证代理。

## 审核工作流程

### 步骤 1：理解上下文

在审核之前，了解 PR 涉及的内容和原因：
1. 从标题/描述/问题中确定更改的目的
2. 按类型分组更改（新代码、测试、配置、文档）
3. 注意更改的范围（受影响的文件、更改的行）
4. 启动子代理来阅读每个显著更改文件周围未更改的代码，以了解现有模式和基础设施

### 步骤 2：深入审核

逐行检查 diff 中的**每个更改**，并根据 [review-checklist.md](review-checklist.md) 中的审核检查清单进行评估。

### 步骤 3：检查向后兼容性

根据 [bc-guidelines.md](bc-guidelines.md) 评估向后兼容性影响。对于非平凡的向后兼容性问题，启动一个子代理来搜索已修改 API 的现有调用者。

### 步骤 4：整合发现

在起草之前**去重**，并在步骤 5 之前进行去重，因为它会显著减慢速度。

将每个候选者（你的和每个子代理的）扁平化为 `(文件:行, 一行声明)` 对列表，然后将其折叠：

- **相同根本原因 → 一个发现。** 两个子代理从不同角度描述一个缺陷是扇出到相邻区域后的预期结果，而不是两个缺陷的相互证实。
- **相同修复 → 一个发现。** 如果单个编辑解决了多个要点，那就是一个具有多个后果的发现。
- **相同 `文件:行` 两次 → 合并**，除非你可以命名两个独立的缺陷。

然后，将每个幸存者分配到恰好一个部分（见“一个发现，一个部分”下的输出格式）并写下来。每个发现都必须可追溯到 diff 中的特定行。

### 步骤 5：事实核查

对**整合后的**列表进行事实核查——每个幸存发现一个子代理，永远不会对原始候选者进行核查。

并行启动代理。每个代理独立通过重新阅读相关代码和周围上下文来验证声明，并返回 **有效**、**无效** 或 **需要重写**。删除无效问题，重写其余部分。如有疑问，请保留问题并给作者评论，表示低置信度。

## 输出格式

按以下结构组织你的审核。**省略你没有问题报告的部分**——大多数审核应该只有几个部分。不要写“没有问题”、“看起来不错”或任何肯定性评论。审核中的每一句话都必须识别问题或请求更改。

摘要部分是例外：它应简要说明 PR 的作用（1 句话），然后说明发现的问题，或明确说明未发现问题。

```markdown
## PR 审核：#<number>
<!-- 或对于本地分支审核： -->
## 分支审核：<branch-name> (vs main)

### 摘要
PR 的作用（1 句话），然后是整体结论。

### 代码质量
[仅问题]

### 基础设施
[仅问题——标记违反检查清单的项目]

### 测试
[仅问题——缺少测试、错误模式、不充分的覆盖率]

### API 设计
[仅问题]

### 安全
[仅问题]

### 线程安全性
[仅问题]

### 向后兼容性
[仅问题]

### 性能
[仅问题]

### 建议
**批准** / **请求更改** / **需要讨论**

缺少测试（新功能没有测试、错误修复没有回归测试）总是意味着 **请求更改**。

[简要理由——如果有什么阻碍批准，请关注]
```

**一个发现，一个部分。** 这些类别在构造上是重叠的——缺少对不良公共 API 的测试在 API 设计、测试和代码质量中都是真实的。将每个发现分配到恰好一个部分，第一个匹配者胜出：

1. **安全** — 具有安全后果
2. **线程安全性** — 具有并发后果
3. **向后兼容性** — 打破或可能打破现有调用者
4. **API 设计** — 缺陷存在于公共或冻结的接口（名称、签名、记录的语义）
5. **基础设施** — 缺少或错误地连接到现有 PyTorch 子系统
6. **测试** — 缺陷仅存在于或不充分的覆盖率
7. **性能**
8. **代码质量** — 其他所有内容

在分配给的部分中一次说明发现的全部后果。当它确实跨越多个类别时，在该一个要点中内联说明（“这也是 out-of-tree 后端向后兼容性破坏”），而不是在另一个部分下添加第二个要点。

此优先级仅适用于八个发现部分。摘要和建议不是发现容器——见上面模板中的规则。特定评论也不是——见其规则。

不要在此模板之外创建部分。通过其*后果*而不是文件类型提交发现：一个错误陈述操作语义的文档字符串是 API 设计，而不是文档。在 [review-checklist.md](review-checklist.md) 中将主题分组或命名不同——例如，它将 API 设计嵌套在代码质量下，将其基础设施部分称为“PyTorch 基础设施”，并且根本没有向后兼容性部分（它位于 [bc-guidelines.md](bc-guidelines.md) 中）——那是组织检查清单，而不是输出；此优先级优先。

### 特定评论（仅限详细审核）

**仅当用户请求“详细”或“深入”审核时才包括此部分。**

**不要重复在其他部分中已经做出的观察。** 此部分用于过于本地化以至于无法有自己的分类发现的点——单行命名、措辞或过时评论的笔记。任何具有行为或接口后果的内容都属于上面八个部分之一。

当请求时，添加特定于文件的反馈，并附带行引用：

```markdown
### 特定评论
- `torch/example/module.py:78` — 重复使用包含循环变量的名称
- `aten/src/ATen/native/Example.cpp:203` — `TORCH_CHECK` 消息说“张量”，但参数是列表
- `torch/example/lowering.py:512` — 过时评论：描述了重构前的控制流
```
