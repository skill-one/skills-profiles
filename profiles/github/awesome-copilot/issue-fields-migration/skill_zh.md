# 问题字段迁移

[问题字段](https://github.blog/changelog/2026-03-12-issue-fields-structured-issue-metadata-is-in-public-preview/) 是组织级别的类型化元数据（单选、文本、数字、日期），用于替代基于标签的解决方案，提供结构化、可搜索、跨仓库的字段。每个组织都会预配置 `优先级`、`工作量`、`开始日期` 和 `目标日期`，并支持最多 25 个自定义字段。

这项技能将现有元数据批量迁移到问题字段，来源包括：

- **仓库标签**：将标签（如 `p0`、`p1`、`priority/high`）转换为结构化问题字段值（例如，优先级字段）。支持一次性迁移多个标签，并可选择迁移后删除它们。
- **项目 V2 字段**：将 GitHub 项目的字段值（单选、文本、数字、日期、迭代）复制到对应组织级别的问题字段。

## 使用场景

- 用户添加了与现有项目字段重叠的组织级别问题字段
- 用户希望在删除旧项目字段之前，将项目字段的值复制到问题字段
- 用户询问将项目字段数据迁移到/转移到/复制到问题字段
- 用户希望将仓库标签（例如，p0、p1、p2、p3）转换为问题字段值（例如，优先级字段）
- 用户询问用问题字段替换标签或在采用问题字段后清理标签

## 前置条件

- 目标组织必须已启用问题字段
- 问题字段必须在组织级别已存在
- 对于项目字段迁移：问题字段必须已添加到项目中
- 对于标签迁移：标签必须存在于目标仓库（多个）
- 用户必须对仓库（和项目，如果迁移项目字段）具有写入权限
- `gh` CLI 必须使用适当的范围进行身份验证

## 可用工具

### MCP 工具（只读操作）

| 工具 | 目的 |
|------|------|
| `mcp__github__projects_list` | 列出项目字段 (`list_project_fields`)，列出具有值的 项目项 (`list_project_items`) |
| `mcp__github__projects_get` | 获取特定项目字段或项的详细信息 |

### CLI / REST API

| 操作 | 命令 |
|------|------|
| 列出组织问题字段 | `gh api /orgs/{org}/issue-fields -H "X-GitHub-Api-Version: 2026-03-10"` |
| 读取问题字段值 | `gh api /repos/{owner}/{repo}/issues/{number}/issue-field-values -H "X-GitHub-Api-Version: 2026-03-10"` |
| 写入问题字段值 | `gh api /repositories/{repo_id}/issues/{number}/issue-field-values -X POST -H "X-GitHub-Api-Version: 2026-03-10" --input -` |
| 获取仓库 ID | `gh api /repos/{owner}/{repo} --jq .id` |
| 列出仓库标签 | `gh label list -R {owner}/{repo} --limit 1000 --json name,color,description` |
| 按标签列出问题 | `gh issue list -R {owner}/{repo} --label "{name}" --state all --json number,title,labels --limit 1000` |
| 从问题中移除标签 | `gh api /repos/{owner}/{repo}/issues/{number}/labels/{label_name} -X DELETE` |

有关完整 API 详细信息，请参阅 [references/issue-fields-api.md](references/issue-fields-api.md)、[references/projects-api.md](references/projects-api.md) 和 [references/labels-api.md](references/labels-api.md)。

## 工作流程

### 步骤 0：迁移源

询问用户他们正在迁移什么：

1. **"您正在迁移标签还是项目字段？"**
   - **标签**：继续到下方的 [标签迁移流程](#label-migration-flow)。
   - **项目字段**：继续到下方的 [项目字段迁移流程](#project-field-migration-flow)。

2. 如果用户说 **标签**：
   - 询问："哪些组织和仓库包含这些标签？"
   - 询问："您想迁移哪些标签？"（他们可以命名它们，或者先让我显示标签）

3. 如果用户说 **项目字段**：
   - 询问："可以分享您的项目链接，或者告诉我组织名称和项目编号吗？"
   - 询问："您想迁移哪个字段？"

### 标签迁移流程

当用户希望将仓库标签转换为问题字段值时，使用此流程。标签只能映射到 `single_select` 问题字段（每个标签名称映射到一个选项值）。

#### 阶段 L1：输入和标签发现

1. 询问用户：**组织名称** 和 **仓库（多个）** 以迁移。
2. 从每个仓库获取标签：

```bash
gh label list -R {owner}/{repo} --limit 1000 --json name,color,description
```

3. 获取组织问题字段：

```bash
gh api /orgs/{org}/issue-fields \
  -H "X-GitHub-Api-Version: 2026-03-10" \
  --jq '.[] | {id, name, content_type, options: [.options[]?.name]}'
```

4. **过滤**（对于标签较多的仓库）：如果仓库有 50+ 个标签，按常见前缀（例如，`priority-*`、`team-*`、`type-*`）或颜色分组。让用户在映射前过滤，例如 "显示匹配优先级的标签" 或 "显示蓝色标签"。一次不要倾倒 100+ 个标签。

5. 询问用户哪些标签映射到哪个问题字段和选项。支持以下模式：
   - **单个标签到单个字段**：例如，标签 "bug" → 类型字段，"Bug" 选项
   - **多个标签到一个字段**（批量）：例如，标签 p0、p1、p2、p3 → 优先级字段，具有匹配的选项
   - **多个标签到多个字段**：例如，p1 → 优先级 + 前端 → 团队。按单独的映射组处理。

6. **自动建议映射**：对于每个标签，尝试使用以下模式（按顺序）匹配问题字段选项：
   - **精确匹配**（不区分大小写）：标签 `Bug` → 选项 `Bug`
   - **前缀-数字** (`{prefix}-{n}` → `{P}{n}`)：标签 `priority-1` → 选项 `P1`
   - **去除分隔符**（连字符、下划线、空格）：标签 `good_first_issue` → 选项 `Good First Issue`
   - **子字符串包含**：标签 `type: bug` → 选项 `Bug`

   一次性向用户展示所有建议，让用户确认、更正或跳过。

**示例输出：**

```
github/my-repo 中的标签（显示相关部分）：
  p0, p1, p2, p3, bug, 增强, 前端, 后端

组织问题字段（single_select）：
  优先级：关键、P0、P1、P2、P3
  类型：错误、功能、任务
  团队：前端、后端、设计

建议映射：
  标签 "p0" → 优先级 "P0"
  标签 "p1" → 优先级 "P1"
  标签 "p2" → 优先级 "P2"
  标签 "p3" → 优先级 "P3"
  标签 "bug" → 类型 "Bug"
  标签 "前端" → 团队 "前端"
  标签 "后端" → 团队 "后端"
  标签 "增强" → （无自动匹配；手动映射或跳过）

确认、调整或添加更多映射？
```

#### 阶段 L2：冲突检测

在最终确定标签到选项的映射后，检查冲突。冲突发生在问题具有多个标签映射到**同一个**问题字段时（因为单选字段只能持有一个值）。

1. 按目标问题字段对标签映射进行分组。
2. 对于具有多个标签来源的字段，注意潜在的冲突。
3. 询问用户冲突解决策略：
   - **第一个匹配**：使用找到的第一个匹配标签（按标签映射列表的顺序）
   - **跳过**：跳过具有冲突标签的问题，并报告它们
   - **手动**：向用户展示每个冲突，让用户决定

**示例：**

```
潜在冲突：标签 "p0" 和 "p1" 都映射到优先级字段。
如果一个问题具有这两个标签，哪个值应该获胜？

选项：
  1. 第一个匹配（因为 "p0" 出现在映射列表的第一位）
  2. 跳过冲突问题
  3. 我会逐个决定
```

#### 阶段 L3：预飞行检查和数据扫描

1. 对于每个仓库，验证写入权限并缓存 `repository_id`：

```bash
gh api /repos/{owner}/{repo} --jq '{full_name, id, permissions: .permissions}'
```

2. 对于映射中的每个标签，获取匹配的问题：

```bash
gh issue list -R {owner}/{repo} --label "{label_name}" --state all \
  --json number,title,labels,type --limit 1000
```

   **警告**：`--limit 1000` 会静默截断结果。如果您预期一个标签可能有超过 1000 个问题，请手动分页或先验证总数（例如，`gh issue list --label "X" --state all --json number | jq length`）。

   **PR 过滤**：`gh issue list` 返回问题和拉取请求。如果用户只想迁移问题，请在 `--json` 输出中包含 `type` 并过滤 `type == "Issue"`。

3. 如果**所有选定的标签返回 0 个问题**，停止并告诉用户。建议：尝试不同的标签、检查拼写或尝试不同的仓库。不要进行空迁移。

4. 对于多仓库迁移，跨所有指定仓库重复执行。

5. 对于每个找到的问题：
   - 检查问题是否已在目标问题字段中设置了值（如果已设置，则跳过）。
   - 检测多标签冲突（问题具有相同字段的两个标签）。
   - 应用在阶段 L2 中选择的冲突解决策略。
   - 分类：**迁移**、**跳过（已设置）**、**跳过（冲突）**、**跳过（无匹配标签）**。

#### 阶段 L4：预览/干运行

在执行任何写入操作之前显示摘要。

**示例预览：**

```
标签迁移预览

来源：github/my-repo 中的标签
目标字段：优先级、类型、团队

| 类别                | 数量 |
|---------------------|------|
| 要迁移的问题        |   156 |
| 已设置（跳过）      |    12 |
| 冲突标签（跳过）    |    3 |
| 带标签的总问题      |   171 |

标签分解：
  "p1" → 优先级 "P1"：42 个问题
  "p2" → 优先级 "P2"：67 个问题
  "p3" → 优先级 "P3"：38 个问题
  "bug" → 类型 "Bug"：9 个问题

样本更改（前 5 个）：
  github/my-repo#101：优先级 → "P1"
  github/my-repo#203：优先级 → "P2", 类型 → "Bug"
  github/my-repo#44：  优先级 → "P3"
  github/my-repo#310：优先级 → "P1"
  github/my-repo#7：   类型 → "Bug"

迁移后，您是否还想从问题中移除已迁移的标签？（可选）

估计时间：~24s（156 个 API 调用，每个调用 0.15 秒）

继续？
```

#### 阶段 L5：执行

1. 对于每个要迁移的问题，写入问题字段值（与项目字段迁移相同的端点）：

```bash
echo '{"issue_field_values": [{"field_id": FIELD_ID, "value": "OPTION_NAME"}]}' | \
  gh api /repositories/{repo_id}/issues/{number}/issue-field-values \
    -X POST \
    -H "X-GitHub-Api-Version: 2026-03-10" \
    --input -
```

   将 `FIELD_ID` 替换为整数字段 ID（例如，`1`），将 `OPTION_NAME` 替换为选项名称字符串。

2. 如果用户选择移除标签，在成功写入字段后移除每个已迁移的标签：

```bash
gh api /repos/{owner}/{repo}/issues/{number}/labels/{label_name} -X DELETE
```

   包含空格或特殊字符的标签名称必须在 REST API 路径中使用 URL 编码（例如，`good%20first%20issue`）。

3. **节流**：调用之间 100ms 延迟。对 HTTP 429 使用指数退避（1s、2s、4s，最多 30s）。
4. **进度**：每 25 个项目报告一次状态（例如，"已迁移 75/156 个问题..."）。
5. **错误处理**：记录失败但继续。单独报告标签移除失败。
6. **最终摘要**：

```
标签迁移完成

| 结果                | 数量 |
|---------------------|------|
| 已设置字段          |   153 |
| 已移除标签          |   153 |
| 跳过                |    15 |
| 写入失败 (字段)     |     2 |
| 移除失败 (标签)     |     1 |

失败项目：
  github/my-repo#501：403 Forbidden（权限不足）
  github/my-repo#88： 422 Validation failed（仓库上字段不可用）
  github/my-repo#120：标签移除失败（404，标签已移除）
```

### 项目字段迁移流程

当用户希望将 GitHub 项目 V2 字段的值复制到对应组织级别的问题字段时，使用此流程。

按顺序遵循以下六个阶段。执行前始终预览。

#### 阶段 P1：输入和发现

1. 询问用户：**组织名称** 和 **项目编号**（或项目 URL）。
2. 获取项目字段：

```bash
# 使用 MCP 工具
mcp__github__projects_list(owner: "{org}", project_number: {n}, method: "list_project_fields")
```

3. 获取组织问题字段：

```bash
gh api /orgs/{org}/issue-fields \
  -H "X-GitHub-Api-Version: 2026-03-10" \
  --jq '.[] | {id, name, content_type, options: [.options[]?.name]}'
```

4. **过滤代理字段**：在项目上启用问题字段后，一些项目字段会作为 "代理" 条目出现，对于单选类型，`options: []` 为空。这些字段镜像实际的问题字段，应忽略。仅匹配具有实际选项值的项目字段。

5. 按名称自动匹配字段（不区分大小写），并兼容类型：

| 项目字段类型 | 问题字段类型 | 兼容性 |
|--------------|--------------|--------|
| TEXT         | text         | 是，直接复制 |
| SINGLE_SELECT| single_select| 是，需要选项映射 |
| NUMBER       | number       | 是，直接复制 |
| DATE         | date         | 是，直接复制 |
| ITERATION    | (无)         | 无等效；跳过并警告 |

6. 将建议的字段映射显示为表格。让用户确认、调整或跳过字段。

**示例输出：**

```
找到 3 个潜在字段映射：

| # | 项目字段      | 类型          | 问题字段        | 状态     |
|---|----------------|---------------|--------------------|------------|
| 1 | 优先级 (重命名) | SINGLE_SELECT | 优先级           | 自动匹配 |
| 2 | 截止日期       | DATE          | 截止日期           | 自动匹配 |
| 3 | 迭代           | ITERATION     | (无等效)    | 跳过    |

继续字段 1 和 2？您也可以添加手动映射。
```

#### 阶段 P2：选项映射（仅限单选字段）

对于每个匹配的单选对：

1. 比较项目字段和问题字段的选项名称（不区分大小写）。
2. 自动匹配名称相同的选项。
3. 对于任何未映射的项目字段选项，一次性显示所有未映射的选项摘要，并询问用户一次提供所有映射。不要逐个提示；将它们批量到一个交换中。
4. 显示最终选项映射表以供确认。

**示例输出：**

```
"发布 - 目标" 的选项映射

自动匹配（不区分大小写）:
  "GA" → "GA"
  "私有预览" → "私有预览"
  "公开预览" → "公开预览"

未映射的项目选项（需要您的输入）:
  1. "仅内部" → 哪个问题字段选项？（或跳过）
  2. "已弃用" → 哪个问题字段选项？（或跳过）
  3. "测试版" → 哪个问题字段选项？（或跳过）
  4. "已弃用" → 哪个问题字段选项？（或跳过）

尚未映射的问题字段选项： "内部", "日落", "测试版", "生命周期结束"

请一次性提供上述 4 个选项的映射（例如，"1→内部, 2→日落, 3→测试版, 4→跳过"）。
```

#### 阶段 P3：预飞行检查

在扫描项目之前，验证每个可能受影响的仓库的写入权限：

1. 从项目项（第一页），收集唯一的 `{owner}/{repo}` 集合。
2. 对于每个唯一仓库，验证认证用户具有问题写入权限：

```bash
gh api /repos/{owner}/{repo} --jq '{full_name, permissions: .permissions}'
```

3. 如果任何仓库显示 `push: false` 或 `triage: false`，在继续之前警告用户。那些仓库中的项目在写入时会失败。
4. 现在缓存每个仓库的 `repository_id`（整数）；您将在阶段 6 中需要它：

```bash
gh api /repos/{owner}/{repo} --jq .id
```

#### 阶段 P4：数据扫描

1. 使用 MCP 获取所有项目项。**重要**：对于具有超过 ~200 个项的项目，`gh api graphql --paginate` 不可靠（它将 JSON 响应连接起来而没有正确的分隔符，并且可能会超时）。使用 MCP 工具（它内部处理分页），或使用显式的基于游标的分页：

```bash
# 首选：使用 MCP 工具（自动处理分页）
mcp__github__projects_list(owner: "{org}", project_number: {n}, method: "list_project_items")

# 大型项目的回退：手动基于游标的分页
# 每页获取 100 个项，每次前进游标。
# 在获取下一页之前处理每一页，以避免内存问题。
# 保存进度（页码或最后一个游标），以便如果中断可以恢复。
```

2. 对于每个项：
   - 如果它是草稿项（不是实际问题），则跳过。
   - 提取源项目字段值。
   - 如果源值为空，则跳过。
   - 检查问题是否已在目标问题字段中设置了值：

```bash
gh api /repos/{owner}/{repo}/issues/{number}/issue-field-values \
  -H "X-GitHub-Api-Version: 2026-03-10"
```

   - 如果目标问题字段已具有值，则跳过（保留现有数据）。

3. 将每个项分类为以下之一：
   - **迁移**：具有源值，没有现有目标值
   - **跳过（已设置）**：目标问题字段已具有值
   - **跳过（无源）**：项目字段对此项为空
   - **跳过（草稿）**：项是草稿，不是实际问题
   - **跳过（未映射选项）**：单选值未映射

#### 阶段 P5：预览/干运行

在执行任何写入之前显示摘要。

**如果用户请求干运行**：显示完整的详细报告（列出每个问题，其当前值、建议的新值和跳过原因），然后停止。不要执行。

**否则（预览模式）**：显示摘要计数和更改样本，然后询问确认。

**示例预览：**

```
项目 #42 迁移预览

要迁移的字段：优先级、截止日期

| 类别               | 计数 |
|------------------------|-------|
| 要迁移的项目项       |   847 |
| 已设置（跳过）     |    23 |
| 无源值（跳过）     |   130 |
| 草稿项（跳过）     |    12 |
| 总项目项            | 1,012 |

样本更改（前 5 个）:
  github/repo-a#101: 优先级 → "高"
  github/repo-a#203: 优先级 → "中", 截止日期 → "2025-03-15"
  github/repo-b#44:  优先级 → "低"
  github/repo-a#310: 截止日期 → "2025-04-01"
  github/repo-c#7:   优先级 → "关键"

估计时间：~127s (847 个 API 调用，每个调用 0.15 秒)

继续迁移？这将更新 847 个问题，跨 3 个仓库。
```

#### 阶段 P6：执行

1. 使用在阶段 3 中缓存的 `repository_id` 值。

2. 对于每个要迁移的项，写入问题字段值：

```bash
echo '{"issue_field_values": [{"field_id": FIELD_ID, "value": "VALUE"}]}' | \
  gh api /repositories/{repo_id}/issues/{number}/issue-field-values \
    -X POST \
    -H "X-GitHub-Api-Version: 2026-03-10" \
    --input -
```

   将 `FIELD_ID` 替换为整数字段 ID（例如，`1`），将 `VALUE` 替换为值字符串。

3. **节流**：在 API 调用之间添加 100ms 延迟。对 HTTP 429 响应使用指数退避（1s、2s、4s，最多 30s）。
4. **进度**：每 25 个项目报告一次状态（例如，"已迁移 75/847 个项目..."）。
5. **错误处理**：记录失败但继续处理剩余项目。
6. **最终摘要**：

```
迁移完成

| 结果  | 计数 |
|-------|-------|
| 成功  |   842 |
| 跳过  |   165 |
| 失败  |     5 |

失败项目:
  github/repo-a#501: 403 Forbidden (权限不足)
  github/repo-b#88:  422 Validation failed (仓库上字段不可用)
  ...
```

## 重要说明

- **写入端点特性**：写入问题字段值的 REST API 使用 `repository_id`（整数），而不是 `owner/repo`。始终先使用 `gh api /repos/{owner}/{repo} --jq .id` 查找仓库 ID。
- **单选值**：REST API 接受选项**名称**作为字符串（不是选项 ID）。这使得项目字段和标签的映射变得简单。
- **读取值回**：从 API 响应中读取问题字段值时，使用 `.single_select_option.name` 获取人类可读的值。`.value` 属性返回内部选项 ID（例如 `1201` 的整数），而不是显示名称。
- **API 版本标头**：所有问题字段端点都需要 `X-GitHub-Api-Version: 2026-03-10`。
- **跨仓库项**：项目可以包含来自多个仓库的问题。按每个仓库缓存仓库 ID，避免重复查找。
- **保留现有值**：不要覆盖已设置的问题字段值。跳过这些项目。
- **迭代字段**：没有问题字段等效项。始终警告用户并跳过。
- **草稿项**：未链接到实际问题的项目项无法具有问题字段值。跳过并注明。
- **标签是仓库范围的**：与项目字段不同，标签按仓库存在。相同的标签名称可能存在于多个仓库中；迁移分别应用于每个仓库。
- **标签冲突**：问题可以具有多个标签映射到相同的单选字段。始终检测并解决这些冲突，然后再执行。
- **标签移除是可选的**：迁移后，用户可能想保留标签作为备份或移除它们。始终询问用户是否要移除。
- **URL 编码标签名称**：包含空格或特殊字符的标签在 REST API 路径中使用 URL 编码（例如，`good%20first%20issue`）。
- **为规模生成脚本**：对于 100+ 个问题的迁移，生成一个独立的 shell 脚本，而不是通过代理逐个执行 API 调用。这更快、可恢复，并避免代理超时问题。
- **幂等迁移**：重新运行迁移是安全的。已设置目标字段值的问题将被跳过。这意味着您可以安全地恢复部分迁移，而不会重复工作。
- **`--limit 1000` 截断**：`gh issue list --limit 1000` 会静默停止在 1000 结果处。对于具有更多问题的标签，使用 `--jq` 和基于游标的分页，或运行多个过滤查询（例如，按日期范围）。
- **macOS bash 版本**：macOS 预装 bash 3.x，不支持 `declare -A`（关联数组）。生成的脚本应使用 POSIX 兼容的构造，或在出现不兼容时注明并建议 `brew install bash`。
- **问题与 PR**：`gh issue list` 返回问题和拉取请求。如果迁移只应针对问题，请在 `--json` 输出中包含 `type` 并过滤 `type == "Issue"`。

## 示例

### 示例 1：完整迁移

**用户**： "我需要将我们的项目中的优先级值迁移到新的组织优先级问题字段"

**操作**：遵循 P1-P6 阶段。发现字段、映射选项、检查权限、扫描项、预览、执行。

### 示例 2：仅干运行

**用户**： "显示如果我迁移项目 #42 的字段会发生什么，但不要实际执行"

**操作**：仅遵循 P1-P5 阶段。显示完整的干运行报告，列出每个项目。不要执行。

### 示例 3：多个字段

**用户**： "将项目 #15 中的优先级和截止日期迁移到问题字段"

**操作**：与相同的工作流程，但一次性处理两个字段。在数据扫描期间，为每个项目收集所有映射字段的值。每个问题使用单个 API 调用写入所有字段值。

### 示例 4：单个标签到问题字段

**用户**： "我想将 'bug' 标签迁移到类型问题字段"

**操作**：路由到标签迁移流程。询问组织/仓库，列出标签，确认映射：标签 "bug" → 类型字段 "Bug" 选项。扫描具有该标签的问题，预览，执行。询问是否在迁移后移除标签。

### 示例 5：多个标签到一个字段（批量）

**用户**： "我们有很多 p0、p1、p2、p3 标签，并想将它们转换为优先级问题字段"

**操作**：路由到标签迁移流程。映射所有四个标签到优先级字段选项（p0→P0, p1→P1, p2→P2, p3→P3）。检查冲突（具有多个优先级标签的问题）。一次性总结所有更改。一次性执行。可选移除所有四个标签从已迁移的问题中。

### 示例 6：跨仓库标签迁移与标签移除

**用户**： "跨 github/issues、github/memex 和 github/mobile 迁移 'frontend' 和 'backend' 标签到团队问题字段，然后移除旧标签"

**操作**：路由到标签迁移流程。确认仓库和标签映射："frontend"→团队 "前端", "backend"→团队 "后端"。扫描所有三个仓库中具有这些标签的问题。检测冲突（具有两个标签的问题）。跨仓库预览。执行字段写入，然后从已迁移的问题中移除标签。报告每个仓库的统计信息。
