# 对象组件文档

通过分析当前实现来创建新的对象组件文档或更新现有的组件文档文件。

## 首先确定模式

在编写任何内容之前，选择工作流程：

1. 当用户提供现有的文档 Markdown 文件、指向文档路径，或明确要求刷新或修订现有文档时，使用**更新模式**。遵循 [references/update-mode.md](references/update-mode.md)。
2. 当用户提供源文件或文件夹、指向组件路径，或要求从代码生成文档时，使用**创建模式**。遵循 [references/create-mode.md](references/create-mode.md)。
3. 如果同时提供了代码和现有的文档文件，将现有的文档文件视为输出目标，并将当前源代码视为事实依据。
4. 如果请求不明确，尽可能根据路径类型推断模式：现有的 Markdown 文档文件表示更新模式；源/组件路径表示创建模式。

## 文档标准

- DOC-001：遵循 C4 模型文档级别（上下文、容器、组件、代码）
- DOC-002：与 Arc42 软件架构文档模板保持一致
- DOC-003：符合 IEEE 1016 软件设计描述标准
- DOC-004：使用敏捷文档原则（提供足够增加价值的文档）
- DOC-005：面向开发者和维护者作为主要受众

## 共享分析指南

- ANA-001：确定主要组件边界，以及输入是否表示文件夹、文件或现有文档目标
- ANA-002：检查源代码文件中的类结构、继承、组合和接口
- ANA-003：识别设计模式、架构决策和集成点
- ANA-004：记录或更新公共 API、接口、依赖关系和使用模式
- ANA-005：捕获方法参数、返回值、异步行为、异常和生命周期关注点
- ANA-006：评估性能、安全性、可靠性、可维护性和可扩展性特征
- ANA-007：推断数据流、协作模式以及与周围组件的关系
- ANA-008：使文档基于实现；避免编造代码不支持的行文

## 共享输出要求

- 使用 [assets/documentation-template.md](assets/documentation-template.md) 作为规范部分检查清单和基线结构。
- 以 Markdown 格式输出，具有清晰的标题层级、在必要时使用表格、为示例使用代码块，并在需要可视化架构关系时使用 Mermaid 图表。
- 使示例和接口描述与当前实现匹配，而不是使用通用占位符。
- 仅包含代码、项目结构、配置或明确声明的假设可以支持的信息。
- 当源覆盖不完整时，明确记录限制，而不是猜测。

## 语言特定优化

- LNG-001：**C#/.NET** - async/await、依赖注入、配置、释放、选项模式
- LNG-002：**Java** - Spring 框架、注解、异常处理、打包、依赖注入
- LNG-003：**TypeScript/JavaScript** - 模块、异步模式、类型、npm 依赖、运行时边界
- LNG-004：**Python** - 包、虚拟环境、类型提示、测试、依赖管理

## 错误处理

- ERR-001：如果路径不存在，解释预期的路径，以及技能是否需要源路径或现有的文档文件
- ERR-002：如果找不到相关的源文件，记录差距并建议下一个检查的可能位置
- ERR-003：如果无法从请求中推断文档目标，说明歧义，并且仅在推断不可能时才要求缺失的路径
- ERR-004：如果代码使用非标准的架构模式，记录自定义方法，而不是将其强制纳入通用模式
- ERR-005：如果源访问不完整，继续使用可用证据，并明确指出任何不支持的章节

## 工作流程

1. 确定任务是否为创建模式或更新模式。
2. 检查组件实现以及任何相关的文件，以了解其公共表面区域和内部结构。
3. 使用 [assets/documentation-template.md](assets/documentation-template.md) 作为共享文档骨架。
4. 应用 [references/create-mode.md](references/create-mode.md) 或 [references/update-mode.md](references/update-mode.md) 中的模式特定规则。
5. 生成或修订文档，使图表、示例、接口、依赖关系和质量属性反映当前实现。

## 完成标准

- 文档清晰地标识了组件目的、架构、接口、实现细节、使用模式、质量属性和参考文献。
- 前置字段对于所选模式是准确的。
- 示例和图表与实现匹配。
- 任何未知、差距或假设都明确指出。
