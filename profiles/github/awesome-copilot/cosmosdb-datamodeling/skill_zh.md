## 重要 Azure Cosmos DB NoSQL 背景

### 理解面向聚合的设计

在面向聚合的设计中，Azure Cosmos DB NoSQL 提供了多个级别的聚合：

1. 多文档容器聚合

  多个相关实体按共享同一分区键分组，但存储为具有不同 ID 的单独文档。这提供了：

   • 高效查询相关数据，使用单个 SQL 查询
   • 在分区内使用存储过程/触发器进行事务一致性
   • 访问单个文档的灵活性
   • 每个文档没有大小限制（每个文档限制为 2MB）

2. 单文档聚合

  多个实体组合成一个 Cosmos DB 文档。这提供了：

   • 跨所有数据原子更新
   • 单点读取检索所有数据。确保通过 API 引用文档的 ID 和分区键（示例 `ReadItemAsync<Order>(id: "order0103", partitionKey: new PartitionKey("TimS1234"));` 考虑使用 `SELECT * FROM c WHERE c.id = "order0103" AND c.partitionKey = "TimS1234"` 进行点读取示例）
   • 受 2MB 文档大小限制

设计聚合时，请考虑这两个级别。

### 常量供参考

• **Cosmos DB 文档限制**：2MB（硬限制）
• **自动扩展模式**：在最大 RU/s 的 10% 和 100% 之间自动扩展
• **请求单元 (RU) 成本**：
  • 点读取（1KB 文档）：1 RU
  • 查询（1KB 文档）：~2-5 RUs，具体取决于复杂性
  • 写入（1KB 文档）：~5 RUs
  • 更新（1KB 文档）：~7 RUs（更新比创建操作更昂贵）
  • 删除（1KB 文档）：~5 RUs
  • **关键**：大型文档（>10KB）的 RU 成本按比例增加
  • **跨分区查询开销**：每个物理分区扫描 ~2.5 RU
  • **实际的 RU 估计**：始终根据实际文档大小计算，而不是理论上的 1KB
  • **存储**：$0.25/GB-月
  • **吞吐量**：$0.008/RU/小时（手动），$0.012/RU/小时（自动）
  • **月度秒数**：2,592,000

### 关键设计约束

• 文档大小限制：2MB（硬限制，影响聚合边界）
• 分区吞吐量：每个物理分区最多 10,000 RU/s
• 分区键基数：目标是 100+ 不同值以避免热分区（基数越高越好）
• **物理分区数学**：总数据大小 ÷ 50GB = 物理分区数量
• 跨分区查询：与单分区查询相比，跨分区查询具有更高的 RU 成本和延迟，并且 RU 成本将随着物理分区数量的增加而增加。避免为高频模式或非常大的数据集建模跨分区查询。
• **跨分区开销**：每个物理分区为跨分区查询添加 ~2.5 RU 基本成本
• **大规模的影响**：100+ 物理分区使跨分区查询非常昂贵且无法扩展。
• 索引开销：每个索引属性都会消耗存储和写入 RU
• 更新模式：频繁更新索引属性或完全替换文档会增加 RU 成本（文档越大，影响越大）

## 核心设计理念

核心设计理念是开始时的默认模式。应用此默认模式后，你应该应用此设计模式部分的相关优化。

### 战略共位置

使用多文档容器将经常一起访问的数据组合在一起，只要它们在操作上可以耦合。Cosmos DB 提供容器级功能，如吞吐量配置、索引策略和更改流，这些功能在容器级别起作用。将过多数据组合在一起在操作上会耦合，并可能限制优化机会。

**多文档容器的好处：**

- **单个查询效率**：使用单个 SQL 查询检索相关数据，而不是多次往返
- **成本优化**：单个查询操作而不是多个点读取
- **延迟降低**：消除多个数据库调用的网络开销
- **事务一致性**：同一分区内的 ACID 事务
- **自然数据局部性**：相关数据物理存储在一起，以实现最佳性能

**使用多文档容器的时机：**

- 用户及其订单：分区键 = user_id，文档为用户和订单
- 产品及其评论：分区键 = product_id，文档为产品和评论
- 课程及其课程：分区键 = course_id，文档为课程和课程
- 团队及其成员：分区键 = team_id，文档为团队和成员

#### 多容器与多文档容器：正确的平衡

虽然多文档容器很强大，但不要强迫不相关的数据在一起。当实体具有以下不同的操作特征时，请使用多个容器：

**不同的操作特征：**

- 独立的吞吐量需求
- 不同的扩展模式
- 不同的索引需求
- 不同的更改流处理需求

**多个容器的操作优势：**

- **较低的爆炸半径**：容器级问题只影响相关实体
- **粒度吞吐量管理**：可以独立地为每个业务域分配 RU/s
- **清晰的成本归因**：了解每个业务域的成本
- **清晰的更改流**：更改流包含逻辑上相关的事件
- **自然的服务边界**：微服务可以拥有特定于域的容器
- **简化的分析**：每个容器的更改流只包含一个实体类型

#### 避免复杂的单容器模式

复杂的单容器设计模式混合不相关的实体会创建操作开销，对大多数应用程序没有有意义的优势：

**单容器反模式：**

- 所有容器 → 复杂过滤 → 难以分析
- 所有实体使用相同的吞吐量分配
- 所有更改流使用混合事件需要过滤
- 扩展影响所有实体
- 复杂的索引策略
- 难以维护和引导新开发人员

### 简化聚合边界

在初步聚合设计之后，您可能需要根据更深入的分析调整边界：

提升为单文档聚合

当多文档分析揭示：

• 访问相关性高于最初认为 (>90%)
• 所有文档总是一起获取
• 组合大小保持有界
• 从原子更新中受益

降级为多文档容器

当单文档分析揭示：

• 更新放大问题
• 大小增长问题
• 需要查询子集
• 不同的索引需求

拆分聚合

当成本分析显示：

• 索引开销超过读取收益
• 大聚合的热分区风险
• 需要独立的扩展

示例分析：

产品 + 评论聚合分析：

- 访问模式：查看产品详细信息（不查看评论） - 70%
- 访问模式：查看产品与评论一起 - 30%  
- 更新频率：产品每天更新，评论每小时更新
- 平均大小：产品 5KB，评论 200KB 总计
- 决策：多文档容器 - 低访问相关性 + 大小问题 + 更新不匹配

### 短路反规范化

短路反规范化涉及将相关实体的属性复制到当前实体中，以避免读取期间的额外查找。此模式通过在单个查询中启用频繁需要的数据来提高读取效率。当以下情况适用时使用此方法：

1. 访问模式需要额外的跨分区查询
2. 复制的属性主要是不可变的或应用程序可以接受过时的值
3. 属性足够小，不会显著影响 RU 消耗

示例：在电子商务应用程序中，您可以将产品名称从产品文档复制到每个订单项文档中，以便获取订单项时无需额外的查询以检索产品名称。

### 识别关系

识别关系使您能够消除跨分区查询并减少成本，使用父_id 作为分区键。当子实体不能在没有父实体的情况下存在时，请使用父_id 作为分区键，而不是创建需要跨分区查询的分离容器。

标准方法（更昂贵）：

• 子容器：分区键 = child_id
• 需要跨分区查询：查询跨分区以根据 parent_id 查找子实体
• 成本：跨分区查询的 RU 消耗更高

识别关系方法（成本优化）：

• 子文档：分区键 = parent_id, id = child_id
• 无需跨分区查询：直接在父分区内查询
• 成本节省：通过避免跨分区查询，显著减少 RU 消耗

使用此方法时：

1. 查询给定父 ID 的所有子实体：`SELECT * FROM c WHERE c.partitionKey = "product123"`
2. 获取特定评论：点读取，分区键="product123" AND id="review456"
3. 无需跨分区查询，节省大量 RU 成本

示例：产品评论容器

• 分区键 = ProductId, id = ReviewId
• 查询产品的所有评论：`SELECT * FROM c WHERE c.partitionKey = "product123"`
• 获取特定评论：分区键="product123" AND id="review456"
• 无需跨分区查询，节省大量 RU 成本

```json
    "type": "student"
  },
  {
    "id": "course_456", 
    "partitionKey": "student_123",
    "type": "course",
    "courseId": "course_456"
  },
  {
    "id": "lesson_789",
    "partitionKey": "student_123", 
    "type": "lesson",
    "courseId": "course_456",
    "lessonId": "lesson_789"
  }
]
```

这使您能够：

- 获取所有数据：`SELECT * FROM c WHERE c.partitionKey = "student_123"`
- 获取课程：`SELECT * FROM c WHERE c.partitionKey = "student_123" AND c.courseId = "course_456"`
- 获取课程：分区键="student_123" AND id="lesson_789"

### 具有自然边界的访问模式

复合分区键很有用，可以建模自然查询边界。

TenantData 容器：
- 分区键：tenant_id + "_" + customerId

```json
{
  "id": "record_123",
  "partitionKey": "tenant_456_customer_789", 
  "tenantId": "tenant_456",
  "customerId": "customer_789"

```

自然，因为查询始终是租户范围的，用户永远不会跨租户查询。

### 临时访问模式

Cosmos DB 支持丰富的日期/时间操作，可以在 SQL 查询中使用。您可以使用 ISO 8601 字符串或 Unix 时间戳存储时间数据。根据查询模式、精度需求和人可读性要求选择。

使用 ISO 8601 字符串：

- 人可读的时间戳
- 自然时间排序的 ORDER BY
- 可读性重要的业务应用程序
- 内置日期函数，如 DATEPART, DATEDIFF

使用数字时间戳：

- 紧凑存储
- 对时间值进行数学运算
- 高精度要求

创建包含日期时间属性的复合索引，以有效地查询时间数据，同时保持时间排序。

### 使用稀疏索引优化查询

Cosmos DB 自动索引所有属性，但您可以使用选择性索引策略创建稀疏模式。通过排除不需要索引的路径，有效地查询少数文档，减少存储和写入 RU 成本，同时提高查询性能。

使用选择性索引时，过滤掉超过 90% 的属性不需要索引。

示例：产品容器，其中只有促销项需要索引 sale_price

```json
{
  "indexingPolicy": {
    "includedPaths": [
      { "path": "/name/*" },
      { "path": "/category/*" },
      { "path": "/sale_price/*" }
    ],
    "excludedPaths": [
      { "path": "/*" }
    ]
  }
```

这减少了很少查询的属性的索引开销。

### 具有唯一约束的访问模式

Azure Cosmos DB 除了 id+partitionKey 组合之外，不会强制执行其他唯一约束。对于其他唯一属性，请使用应用程序级唯一性，使用条件操作或事务内的存储过程。

```javascript
// 存储过程用于创建具有唯一电子邮件的用户
function createUserWithUniqueEmail(userData) {
    var context = getContext();
    var container = context.getCollection();
    
    // 检查电子邮件是否已存在
    var query = `SELECT * FROM c WHERE c.email = "${userData.email}"`;
    
    var isAccepted = container.queryDocuments(
        container.getSelfLink(),
        query,
        function(err, documents) {
            if (err) throw new Error('Error querying documents: ' + err.message);
            
            if (documents.length > 1) {
                throw new Error('Email already exists');
            }
            
            // 电子邮件是唯一的，创建用户
            var isAccepted = container.createDocument(
                container.getSelfLink(),
                userData,
                function(err, document) {
                    if (err) throw new Error('Error creating document: ' + err.message);
                    context.getResponse().setBody(document);
                }
            );
            
            if (!isAccepted) throw new Error('The query was not accepted by the server.');
        }
    );
    
    if (!isAccepted) throw new Error('The query was not accepted by the server.');
}
```

此模式确保了唯一性约束，同时保持了性能。

### 分层分区键 (HPK) 用于自然查询边界

🔴 **新功能** - 仅在专用 Cosmos DB NoSQL API 中可用：

分层分区键使用多个字段作为分区键级别，提供自然查询边界，消除合成键的复杂性，同时优化查询性能。

**标准分区键**：

```json
{
  "partitionKey": {
    "version": 2,
    "kind": "MultiHash", 
    "paths": ["/accountId", "/testId", "/chunkId"]
  }
}
```

**查询优势**：

- 单分区查询：`WHERE accountId = "123" AND testId = "456"`
- 前缀查询：`WHERE accountId = "123"`（高效的跨分区）
- 消除合成键逻辑的自然层次

**考虑 HPK 的时候**：

- 数据具有自然层次结构（租户→用户→文档）
- 频繁前缀查询
- 想要消除合成分区键的复杂性
- 仅适用于 Cosmos NoSQL API 

**权衡**：

- 需要专用层（在服务器less 中不可用）
- 新功能，生产历史较少
- 查询模式必须与层次级别一致

### 使用写入分片处理高写入工作负载

写入分片将高卷写入操作分布在多个分区键上，以克服 Cosmos DB 每个分区的 RU 限制。此技术通过添加计算分片标识符到你的分区键中，将写入分布在多个分区，同时保持查询效率。

当写入分片是必要的：仅在多个写入集中在同一分区键值时才应用，这会创建瓶颈。大多数高写入工作负载自然分布在许多分区键上，不需要分片的复杂性。

#### 分片集中写入

当特定实体接收不成比例的写入活动，例如病毒社交媒体帖子每秒接收数千次交互，而典型帖子只偶尔活动。

PostInteractions 容器（有问题）：
• 分区键：post_id
• 问题：病毒帖子超过每个分区的 10,000 RU/s 限制
• 结果：在高参与度期间请求速率限制

分片解决方案：
• 分区键：post_id + "_" + shard_id (例如，"post123_7")
• 分片计算：shard_id = hash(user_id) % 20
• 结果：每个帖子将交互分布在 20 个分区

#### 分片单调递增键

顺序写入，如时间戳或自动递增 ID，集中在最近值上，在最新分区上创建热点。

EventLog 容器（有问题）：
• 分区键：date (YYYY-MM-DD 格式)
• 问题：所有今天的事件都写入同一日期分区
• 结果：限制为 10,000 RU/s，无论总容器吞吐量如何

分片解决方案：
• 分区键：date + "_" + shard_id (例如，"2024-07-09_4")  
• 分片计算：shard_id = hash(event_id) % 15
• 结果：每天的事件分布在 15 个分区

### 聚合边界和更新模式

当聚合边界与更新模式冲突时，根据 RU 成本影响优先考虑：

示例：订单处理系统
• 读取模式：始终获取包含所有项目的订单（1000 RPS）
• 更新模式：单个项目状态更新（100 RPS）

选项 1 - 合并聚合（单个文档）：
- 读取成本：1000 RPS × 1 RU = 1000 RU/s
- 写入成本：100 RPS × 10 RU（重写整个订单）= 1000 RU/s

选项 2 - 分离项目（多文档）：
- 读取成本：1000 RPS × 5 RU（查询多个项目）= 5000 RU/s  
- 写入成本：100 RPS × 10 RU（更新单个项目）= 1000 RU/s

决策：选项 1 由于读取成本显著降低而写入成本相同，因此更好

### 使用 TTL 建模临时数据

TTL 以成本效益的方式管理具有自然过期时间的临时数据。用于自动清理会话令牌、缓存条目、临时文件或特定时间段后变得不相关的通知。

TTL 在 Cosmos DB 提供立即清理 - 过期文档在几秒钟内被删除。使用 TTL 对于安全敏感和清理场景都很有用。您可以在 TTL 过期之前更新或删除文档。更新过期文档会通过修改 TTL 属性来延长其生命周期。

TTL 需要 Unix 纪元时间戳（自 1970 年 1 月 1 日 UTC 以来的秒数）或 ISO 8601 日期字符串。

示例：24 小时过期的会话令牌

```json
{
  "id": "sess_abc123",
  "partitionKey": "user_456",
  "userId": "user_456", 
  "createdAt": "2024-01-01T12:00:00Z",
  "ttl": 86400
}
```

容器级 TTL 配置：

```json
{
  "defaultTtl": -1,  // 启用 TTL，无默认过期
}
```

单个文档上的 `ttl` 属性覆盖容器默认值，为每种文档类型提供灵活的过期策略。
