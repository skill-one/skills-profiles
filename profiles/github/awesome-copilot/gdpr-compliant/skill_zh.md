# GDPR 工程技能

为工程师、架构师、DevOps 和技术负责人提供可操作的 GDPR 参考指南。
灵感来源于 CNIL 开发者指南以及 GDPR 第 5、25、32、33、35 条。

> **黄金法则：** 少收集，少存储，少暴露，少保留。

如需深入了解，请阅读 `references/` 目录中的参考文件：
- `references/data-rights.md` — 用户权利端点，DSR 工作流，RoPA
- `references/security.md` — 加密，哈希，密钥，匿名化
- `references/operations.md` — 云，CI/CD，事件响应，架构模式

---

## 1. 核心GDPR原则（第5条）

| 原则 | 工程责任 |
|---|---|
| 合法性、公平性、透明性 | 在 RoPA 中记录每项处理活动的法律依据 |
| 目的限制 | 为目的 A 收集的数据 **必须** 未经新的法律依据不得用于目的 B |
| 数据最小化 | 仅收集具有明确业务需求的字段 |
| 准确性 | 提供更新端点；将更正传播到下游存储 |
| 存储限制 | 在模式设计时定义 TTL — 永远不在之后定义 |
| 完整性 & 机密性 | 静态加密和传输加密；限制和审计访问权限 |
| 可问责性 | 维护合规证据；RoPA 随时可接受 DPA 检查 |

## 2. 默认隐私设计 & 默认隐私保护

**必须**
- 在创建时为每个存储个人数据的表添加 `CreatedAt`，`RetentionExpiresAt`。
- 将所有可选数据收集的默认值设置为 **关闭**。用户选择加入；他们永远不会选择退出默认开启的设置。
- 在构建高风险处理（生物识别、健康数据、大规模画像、系统性监控）之前进行 **DPIA**。
- 每当引入新的处理活动功能时，更新 **RoPA**。
- 在数据流向子处理商之前，与每个子处理商签署 **DPA**。

**必须不**
- 未经记录的法律依据就发布新的数据收集功能。
- 默认启用分析、跟踪或遥测，而未经明确同意。
- 在 RoPA 未列出的系统中存储个人数据。

---

## 3. 数据最小化

**必须**
- 将每个 DTO/模型字段映射到具体业务需求。移除未记录的字段。
- 使用 **独立的 DTO** 进行创建、读取和更新 — 永远不要重用同一个对象。
- 仅返回调用者有权查看的内容 — 使用响应投影。
- 在边缘处遮罩敏感值：返回 `****1234` 用于卡号，永远不要返回完整值。
- 从默认列表/搜索投影中排除敏感字段（出生日期、国籍ID、健康数据）。

**必须不**
- 如果请求/响应体可能包含个人数据，则记录完整请求/响应体。
- 将个人数据包含在 URL 路径段或查询参数中（CDN 日志、浏览器历史记录）。
- 未经明确法律依据收集 `dateOfBirth`、国籍ID 或健康数据。

---

## 4. 目的限制

**必须**
- 在代码注释和 RoPA 中记录每项处理活动的目的。
- 在将数据用于次要目的之前，获取新的法律依据或进行兼容性分析。

**必须不**
- 未经明确同意，将用于服务交付收集的个人数据共享给广告网络。
- 未经单独法律依据和用户通知，使用支持工单内容训练 ML 模型。

---

## 5. 存储限制 & 保留

**必须**
- 每个存储个人数据的表 **必须** 具有定义的保留期限。
- 通过计划任务（Hangfire、cron）自动执行保留 — 永远不要手动执行。
- 保留到期时匿名化或删除数据 — 永远不要在生产环境中静默保留过期数据。

**推荐默认值**

| 数据类型 | 最大保留时间 |
|---|---|
| 认证/审计日志 | 12–24 个月 |
| 会话/刷新令牌 | 30–90 天 |
| 邮件/通知日志 | 6 个月 |
| 非活跃用户账户 | 最后登录 12 个月后通知 → 删除 |
| 支付记录 | 税法要求（7–10 年），最小化 |
| 分析事件 | 13 个月 |

**应该**
- 添加 `RetentionExpiresAt` 列 — 在插入时计算。
- 使用软删除（`DeletedAt`），在擦除请求窗口（30 天）后执行计划硬删除。

**必须不**
- 无限期保留个人数据“以防将来有用”。

## 6. API 设计规则

**必须**
- **必须不**将个人数据包含在 URL 路径或查询参数中。
  - `GET /users/{userId}`
- 所有返回或接受个人数据的端点都需要身份验证。
- 从 JWT 中提取操作用户的身份 — 永远不要从请求体中提取。
- 在每个资源上验证所有权：`if (resource.OwnerId != currentUserId) return 403`。
- 使用 UUID 或不透明标识符 — 永远不要使用顺序整数作为公开资源 ID。

**应该**
- 对敏感端点（登录、数据导出、密码重置）进行速率限制。
- 设置 `Referrer-Policy: no-referrer` 和明确的 `CORS` 允许列表。

**必须不**
- 在 API 响应中返回堆栈跟踪、内部路径或数据库错误。
- 在认证 API 上使用 `Access-Control-Allow-Origin: *`。

---

## 7. 日志规则

**必须**
- 在应用程序日志中匿名化 IP — 遮罩 IPv4 的最后八位或 IPv6 的最后 80 位。
  - `192.168.1.xxx`
- **必须不**记录：密码、令牌、会话 ID、凭证、卡号、国籍 ID、健康数据。
- **必须不**记录可能包含个人数据的完整请求/响应体。
- 执行日志保留 — 在定义的周期后自动清除。

**应该**
- 记录 **事件** 而不是数据：`"User {UserId} updated email"` 而不是 `"Email changed from a@b.com to c@d.com"`。
- 使用结构化日志（JSON）并将 `userId` 作为内部标识符，而不是电子邮件地址。
- 将审计日志（敏感访问、管理员操作）与应用程序日志分开 — 不同的保留和 ACL。

---

## 8. 错误处理

**必须**
- 返回通用错误消息 — 永远不要暴露堆栈跟踪、内部路径或数据库错误。
  - `"Column 'email' violates unique constraint on table 'users'"`
  - `"A user with this email address already exists.""`
- 使用 **Problem Details (RFC 7807)** 对所有错误响应。
- 在服务器端记录完整错误，并附带关联 ID；仅向客户端返回关联 ID。

**必须不**
- 在错误响应中包含文件路径、类名或行号。
- 在错误消息中包含个人数据（例如，“User john@example.com not found”）。

## 9. 加密（摘要 — 请参阅 `references/security.md` 获取完整细节）

| 范围 | 最低标准 |
|---|---|
| 标准个人数据 | AES-256 磁盘/卷加密 |
| 敏感数据（健康、金融、生物识别） | AES-256 **列级别** + 通过 KMS 的信封加密 |
| 传输中 | TLS 1.2+（优先 1.3）；强制执行 HSTS |
| 密钥 | HSM 支持的 KMS；每年轮换 DEK |

**必须不**允许 TLS 1.0/1.1、空加密套件或硬编码的加密密钥。

---

## 10. 密码哈希

**必须**
- 使用 **Argon2id**（推荐）或 **bcrypt**（成本 ≥ 12）。永远不要使用 MD5、SHA-1 或 SHA-256。
- 每个密码使用唯一盐。仅存储哈希值。

**必须不**
- 以任何形式记录密码。在 URL 中传输密码。以明文存储重置令牌。

---

## 11. 密钥管理

**必须**
- 将所有密钥存储在 KMS 中：Azure Key Vault、AWS Secrets Manager、GCP Secret Manager 或 HashiCorp Vault。
- 使用预提交钩子（`gitleaks`、`detect-secrets`）防止密钥提交。
- 在员工离职、年度计划或怀疑泄露时轮换密钥。

**`.gitignore` 必须包含：** `.env`，`.env.*`，`*.pem`，`*.key`，`*.pfx`，`*.p12`，`secrets/`

**必须不**
- 将密钥提交到源代码。将密钥存储为明文环境变量默认值。

---

## 12. 匿名化 & 假名化（摘要 — 请参阅 `references/security.md`）

- **匿名化** = 不可逆 → 不在 GDPR 范围内。用于擦除后保留的记录。
- **假名化** = 可逆（使用密钥）→ 仍然是个人数据，风险降低。
- 删除用户时，对必须保留的记录（财务、审计）进行匿名化，而不是删除它们。
- 将假名化密钥存储在 KMS 中 — 永远不要与假名化数据存储在同一数据库中。

**必须不**在通过链接攻击可能重新识别的情况下称数据为“匿名化”。

---

## 13. 使用假数据进行测试

**必须**
- **必须不**在开发、测试或 CI 环境中使用生产个人数据。
- **必须不**在未先清理 PII 的情况下将生产数据库备份恢复到非生产环境。
- 使用合成数据生成器：`Bogus` (.NET)、`Faker` (JS/Python/Ruby)。
- 使用 `@example.com` 作为所有测试电子邮件地址。

## 14. 反模式

| 反模式 | 正确方法 |
|---|---|
| PII 在 URL 中 | 使用不透明 UUID 作为公共标识符 |
| 记录完整请求体 | 仅记录结构化事件元数据 |
| “永远保留”模式 | 在设计时定义 TTL |
| 开发/测试中的生产数据 | 合成数据 + 清理管道 |
| 跨团队共享凭证 | 单独账户 + RBAC |
| 硬编码密钥 | KMS + 密钥管理器 |
| 认证 API 上的 `Access-Control-Allow-Origin: *` | 明确的 CORS 允许列表 |
| 将同意与配置文件数据存储在一起 | 专用同意存储 |
| PII 在 GET 查询参数中 | POST 正文或认证会话 |
| 公共 URL 中的顺序整数 ID | UUID |
| “匿名化”数据具有准标识符 | 应用 k-匿名性，测试链接抗性 |
| 在 EEA 外混合备份区域 | 备份作业上的明确区域锁定 |

## 15. PR 审查清单

### 数据模型
- 每个新的 PII 列都有记录的目的和保留期限。
- 敏感字段（健康、金融、国籍 ID）使用列级别加密。
- 没有作为公开标识符的顺序整数主键。

### API
- URL 路径或查询参数中无 PII。
- 所有返回个人数据的端点都需要身份验证。
- 存在所有权检查 — 用户不能访问其他用户的资源。
- 对敏感端点应用速率限制。

### 日志
- 不记录密码、令牌或凭证。
- 匿名化 IP（遮罩 IPv4 的最后八位或 IPv6 的最后 80 位）。
- 在可能存在 PII 的地方不记录完整请求/响应体。

### 基础设施
- 没有公共存储桶或公共 IP 数据库。
- 新云资源标记为 `DataClassification`。
- 新存储资源启用静态加密。
- 新数据存储区域符合 EEA 要求或受 SCC 覆盖。

### 密钥 & CI/CD
- 源代码或提交的配置文件中无密钥。
- 新密钥添加到 KMS 和密钥清单文档。
- CI/CD 密钥在管道日志中遮罩。

### 保留 & 删除
- 保留执行作业或策略覆盖新数据存储或字段。
- 删除管道更新以覆盖新数据存储。

### 用户权利 & 治理
- 数据导出端点包括任何新的个人数据字段。
- 如果引入新的处理活动，则更新 RoPA。
- 新子处理商有签署的 DPA 和 RoPA 条目。
- 如果更改涉及高风险处理，则触发 DPIA。

---

> **黄金法则：** 少收集，少存储，少暴露，少保留。
>
> 你不收集的每字节个人数据都是你不会丢失、不会泄露、不会承担责任的字节。
