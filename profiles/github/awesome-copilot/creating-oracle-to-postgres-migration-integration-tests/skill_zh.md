# 为 Oracle 到 PostgreSQL 迁移创建集成测试

为单个目标项目中的数据访问工件生成集成测试用例。测试目标为 Oracle 并捕获其行为作为权威基线。它们被设计为逻辑上可移植的——因此它们可以在第 6 阶段迁移时无需重写即可存活——但在这一阶段它们不会针对 PostgreSQL 运行。

## 前置条件

- 测试项目必须已经存在并且可以编译（单独搭建框架）。
- 在编写测试之前，请先阅读现有的基础测试类和种子管理器约定。

## 工作流程

```
测试创建：
- [ ] 第 1 步：发现测试项目的约定
- [ ] 第 2 步：识别可测试的数据访问工件
- [ ] 第 3 步：创建种子数据
- [ ] 第 4 步：编写测试用例
- [ ] 第 5 步：审查确定性
```

**第 1 步：发现测试项目的约定**

阅读基础测试类、种子管理器和项目文件，以了解继承模式、事务管理以及种子文件约定。

**第 2 步：识别可测试的数据访问工件**

仅限于目标项目范围内。列出与数据库交互的数据访问方法——仓库、DAO、存储过程调用者、查询构建器。

**第 3 步：创建种子数据**

- 遵循现有项目中的种子文件位置和命名约定。
- 避免 `TRUNCATE TABLE` —— 保持现有数据库数据完整。
- 假设现有的业务行和查找行已经存在；仅添加对场景所需的最小、无冲突的种子记录。
- 不要提交种子数据；测试在事务中运行，事务会回滚。
- 确保种子数据不与其他测试冲突。
- 在依赖它的断言之前，加载并验证种子数据。
- 创建或重用一个测试 `LookupConstants` 类，用于跨种子构建器和断言使用的稳定查找 ID/代码。

**第 4 步：编写测试用例**

- 从基础测试类继承以获取自动事务创建/回滚。
- 确保范围内的每个触及数据库的方法至少有一个集成测试（或针对高风险行为分支的多个测试）。
- 断言逻辑输出（行、列、计数、错误类型），而不是平台特定的消息。
- 断言特定的预期值——当种子数据提供具体值时，永远不要断言一个值仅仅是非空或非空。
- 避免测试不存在或断言不可能发生的代码路径。
- 避免针对同一方法的多余断言。
- 对于文本参数，在适用的情况下，包括空字符串和 `NULL`/缺失输入的覆盖范围。
- 对于 datetime 行为，包括验证写入和读取回的值匹配的断言——使用 Oracle 列的精度（例如，对于没有小数秒的日期/时间列使用仅秒），而不是假设任何特定的数据库类型语法。

**第 5 步：审查确定性**

重新检查每个针对非空值的断言。确认每个断言都是针对种子数据的确定性。修复任何依赖于测试控制之外的数据库状态的断言。

## 关键约束

- **仅限第 3 阶段** —— 这些测试目标为 Oracle。在第 6 阶段或针对 PostgreSQL 目标项目时，不要调用此技能。
- **Oracle 是黄金来源** —— 测试捕获 Oracle 的预期行为。
- **断言可移植性** —— 在断言中避免平台特定的错误消息或语法，以便当测试项目在第 6 阶段迁移到 PostgreSQL 时，断言无需更改。
- **仅针对 Oracle 种子** —— 测试项目将在第 6 阶段迁移到 PostgreSQL；种子数据和基础设施在此之前保持 Oracle 目标。
- **仅限于一个项目** —— 不要为目标项目外的工件创建测试。
- **保留现有数据** —— 永远不要重写或删除现有的业务或查找行。
