# Python LLM 应用程序驱动开发

你正在构建一个**自动化评估流程**，对基于 Python 的 AI 应用程序进行端到端测试——以与真实用户相同的方式运行它，使用真实输入——然后使用评估器对输出进行评分，并通过 `pixie test` 生成通过/失败结果。

**你测试的是应用程序本身**——它的请求处理、上下文组装（它如何收集数据、构建提示、管理会话状态）、路由和响应格式化。应用程序使用 LLM，这使得输出非确定性——这就是为什么你使用评估器（LLM 作为法官、相似度分数）而不是 `assertEqual`——但测试下的是应用程序的代码，而不是 LLM。

在评估期间，应用程序自己的代码会真实运行——路由、提示组装、LLM 调用、响应格式化——没有任何东西被模拟或桩化。但是应用程序从外部来源（数据库、缓存、第三方 API、语音流）读取的数据是通过instrumentations替换为测试指定值的。这意味着每个测试用例都精确控制应用程序看到的数据，同时仍然执行完整的应用程序代码路径。

**规则：应用程序的 LLM 调用必须指向真实的 LLM。** 不要用假的实现来替换、模拟、桩化或拦截 LLM。LLM 是核心的价值生成组件——替换它会使得评估变成同义反复（因为你控制了输入和输出，所以分数没有意义）。如果项目的测试套件包含 LLM 模拟模式，那些是该项目自己的单元测试——绝对不要将其用于评估 Runnable。

**交付成果是一个包含真实分数的运行中的 `pixie test`**——不是计划、不是仅仅instrumentations、不是仅仅数据集。

这项技能是关于做工作，而不是描述它。阅读代码、编辑文件、运行命令、生成一个可工作的管道。

## 开始之前

**首先，激活虚拟环境**。确定项目的正确虚拟环境并激活它。虚拟环境激活后，运行技能资源中包含的 setup.sh 脚本。
该脚本更新 `eval-driven-dev` 技能和 `pixie-qa` python 包到最新版本，如果 pixie 工作目录尚未初始化，则初始化它，并在后台启动一个网页服务器以显示用户更新。

**设置错误处理——你可以跳过什么 vs. 必须成功什么：**

- **技能更新失败** → 可以继续。现有的技能版本是足够的。
- **pixie-qa 升级失败但已经安装** → 可以继续使用现有版本。
- **pixie-qa 未安装且安装失败** → **停止。** 请求用户帮助。没有 `pixie` 包，工作流无法继续。
- **`pixie init` 失败** → **停止。** 请求用户帮助。
- **`pixie start`（网页服务器）失败** → **停止。** 请求用户帮助。检查 pixie 根目录中的 `server.log` 以进行诊断。常见原因：端口冲突、缺失依赖项、环境缓慢。在没有网页服务器的情况下——用户需要它来查看评估结果，不要继续。

## 工作流程

按步骤 1–6 顺序进行，不要停止。在中间步骤不要请求用户确认——自己验证每个步骤并继续。

**如何工作——在执行任何其他操作之前阅读：**

- **一步一步来。** 只阅读当前步骤的说明。在处理步骤 1 时，不要阅读步骤 2–6。
- **仅在步骤指示时才阅读参考文件。** 每个步骤都指定一个特定的参考文件。在到达该步骤时阅读它——而不是之前。
- **立即创建工件。** 在阅读完子步骤的代码后，在继续之前编写该子步骤的输出文件。不要在多个子步骤积累理解后再编写任何东西。
- **验证后继续。** 每个步骤都有一个检查点。验证它，然后继续下一步。在验证当前步骤时不要规划未来的步骤。

**何时停止并请求帮助：**

某些障碍无法且不应绕过。当你遇到以下任何情况时，**立即停止并请求用户帮助**——不要尝试工作解决方案：

- **由于缺少环境变量或配置，应用程序无法运行**：应用程序需要环境变量或配置，而这些变量或配置未设置且无法推断。不要通过模拟、伪造或替换应用程序组件来绕过这一点——评估必须执行真实的生产品代码。请求用户修复环境设置。
- **指示项目损坏的应用程序导入失败**：如果由于缺少系统依赖项或兼容性 Python 版本（不仅仅是你可以安装的缺失 pip 包）导致应用程序的核心模块无法导入，请求用户修复项目设置。
- **模糊的入口点**：如果应用程序有多个同样合理的入口点，而项目分析没有澄清哪个最重要，请求用户目标哪个。

你应该自己解决的障碍（不要请求）：缺失的 Python 包（安装它们）、缺失的 `pixie` 包（安装它）、端口冲突（选择一个不同的端口）、文件权限问题（修复它们）。

**按顺序运行步骤 1–6。** 如果用户的提示明确说明早期步骤已经完成（例如，“运行现有测试”、“重新运行评估”），跳转到相应的步骤。如有疑问，从步骤 1 开始。

### 步骤 1：理解应用程序并定义评估标准

**首先，检查用户的提示中的特定要求。** 在阅读应用程序代码之前，检查用户要求的内容：

- **参考文档或规范**：提示是否提到要遵循的文件（例如，“遵循 EVAL_SPEC.md 中的规范”、“使用 REQUIREMENTS.md 中的方法”）？如果是，**首先阅读该文件**——它可能指定数据集、评估维度、通过标准或方法，这些可能会覆盖你的默认值。
- **指定的数据集或数据源**：提示是否引用特定的数据文件（例如，“使用 eval_inputs/research_questions.json 中的问题”、“使用 call_scenarios.json 中的场景”）？如果是，**阅读这些文件**——你必须将它们用作评估数据集的基础，而不是编造通用的替代方案。
- **指定的评估维度**：提示是否命名要评估的特定质量方面（例如，“评估事实性、完整性和偏见”、“测试身份验证和工具调用正确性”）？如果是，**每个命名维度都必须在测试文件中有一个对应的评估器**。

如果提示指定了上述任何内容，它们将优先。阅读并整合它们后再继续。

步骤 1 有三个子步骤。每个子步骤都读取它自己的参考文件，并生成它自己的输出文件。**在开始下一个子步骤之前，完全完成当前子步骤。**

#### 子步骤 1a：项目分析

> **参考**：现在阅读 `references/1-a-project-analysis.md`。

在查看代码结构或入口点之前，了解该软件在现实世界中的作用——它的目的、用户、真实输入的复杂性以及它在哪里失败。这种理解驱动了所有下游决策：哪个入口点最重要、定义什么评估标准、使用什么跟踪输入、以及创建什么数据集条目。在继续之前编写详细的上下文文件。**注意**：项目可能包含 `tests/`、`fixtures/`、`examples/`、模拟服务器和文档——这些是项目自己的开发基础设施，**不是评估管道的数据源**。在获取跟踪输入和数据集内容时忽略它们。

> **检查点**：`pixie_qa/00-project-analysis.md` 已编写——涵盖软件的作用、目标用户、能力清单（如果项目有的话，至少 3 个能力）、现实输入特征以及硬问题/失败模式（至少 2 个）。

#### 子步骤 1b：入口点与执行流程

> **参考**：现在阅读 `references/1-b-entry-point.md`。

阅读源代码以了解应用程序如何启动以及真实用户如何调用它。使用 `pixie_qa/00-project-analysis.md` 中的**能力清单**来优先考虑入口点——专注于执行最有价值能力的入口点，而不仅仅是找到的第一个入口点。在继续之前编写详细的上下文文件。

> **检查点**：`pixie_qa/01-entry-point.md` 已编写——涵盖入口点、执行流程、用户界面和 env 要求。

#### 子步骤 1c：评估标准

> **参考**：现在阅读 `references/1-c-eval-criteria.md`。

定义应用程序的用例和评估标准。从 `pixie_qa/00-project-analysis.md` 中的**能力清单**中导出用例。从 `pixie_qa/00-project-analysis.md` 中的**硬问题/失败模式**中导出评估标准。用例驱动数据集创建（步骤 4）；评估标准驱动评估器选择（步骤 3）。在继续之前编写详细的上下文文件。

> **检查点**：`pixie_qa/02-eval-criteria.md` 已编写——涵盖用例、评估标准及其适用范围。不要阅读步骤 2 的说明。

### 步骤 2：instrument，运行应用程序，并捕获参考跟踪

步骤 2 有三个子步骤。每个子步骤都读取它自己的参考文件。**在开始下一个子步骤之前，完成当前子步骤。**

#### 子步骤 2a：使用 `wrap` 进行instrument

> **参考**：现在阅读 `references/2a-instrumentation.md`。

在应用程序的数据边界处添加 `wrap()` 调用，以便评估 harness 可以注入受控输入并捕获输出。这使得应用程序可测试，而无需更改其逻辑。

> **检查点**：在所有数据边界处添加了 `wrap()` 调用。应用程序的每个评估标准（来自 `pixie_qa/02-eval-criteria.md`）都有一个对应的数据点。

#### 子步骤 2b：实现 Runnable

> **参考**：现在阅读 `references/2b-implement-runnable.md`。

编写一个 Runnable 类，让评估 harness 按照真实用户的方式调用应用程序。Runnable 应该简单——它只是将应用程序的真实入口点连接到 harness 接口。如果它变得复杂，则有问题。

> **检查点**：`pixie_qa/run_app.py` 已编写。Runnable 调用应用程序的真实入口点，并使用真实的 LLM 配置——没有模拟、没有伪造、没有组件替换。

#### 子步骤 2c：捕获并验证参考跟踪

> **参考**：现在阅读 `references/2c-capture-and-verify-trace.md`。

运行应用程序通过 Runnable 并捕获跟踪。跟踪证明 instrumentation 和 Runnable 正常工作，并提供在步骤 4 中创建数据集所需的数据形状。

> **检查点**：存在 `pixie_qa/reference-trace.jsonl`。所有预期的 `wrap` 条目和 `llm_span` 条目都出现。`pixie format` 显示所有评估所需的数据点。不要阅读步骤 3 的说明。

### 步骤 3：定义评估器

> **参考**：现在阅读 `references/3-define-evaluators.md` 以获取详细的子步骤。

**目标**：将步骤 1c 中的定性评估标准转换为可运行的评分函数。每个标准映射到内置评估器、**代理评估器**（任何语义或定性标准的默认值）或手动自定义函数（仅用于机械/确定性检查，如正则表达式或字段存在）。评估器映射工件在标准和数据集之间建立桥梁，确保每个质量维度都有一个评分器。选择评估器来衡量 `pixie_qa/00-project-analysis.md` 中确定的**硬问题**——而不仅仅是通用质量维度。

> **检查点**：所有评估器已实现。`pixie_qa/03-evaluator-mapping.md` 已编写，包含标准到评估器的映射和决策依据。不要阅读步骤 4 的说明。

### 步骤 4：构建数据集

> **参考**：现在阅读 `references/4-build-dataset.md` 以获取详细的子步骤。

**目标**：创建将所有内容联系起来的测试场景——Runnable（步骤 2）、评估器（步骤 3）和用例（步骤 1c）。每个数据集条目定义要发送给应用程序的内容、应用程序应从外部服务看到的数据以及如何评分结果。使用步骤 2 的参考跟踪作为数据形状和字段名称的来源。涵盖 `pixie_qa/00-project-analysis.md` 中的**能力清单**的条目，并包括针对 `pixie_qa/00-project-analysis.md` 中确定失败模式的条目。**不要使用项目的自己的测试 fixtures、模拟服务器或示例数据作为数据集 `eval_input` 内容**——使用真实世界数据。**应用程序中每个 `wrap(purpose="input")` 必须在每个条目的 `eval_input` 中有预捕获的内容**——在应用程序有输入 wraps 时，不要让 `eval_input` 为空。

> **检查点**：在 `pixie_qa/datasets/<name>.json` 创建了数据集，涵盖所有用例的多样化条目。**数据集真实性审计通过**——条目使用真实世界数据，在代表性规模上，没有项目测试 fixtures 污染，至少有一个条目针对具有不确定结果的失败模式，并且每个 `eval_input` 对所有输入 wraps 都有捕获的内容。不要阅读步骤 5 的说明。

### 步骤 5：运行 `pixie test` 并修复机械问题

> **参考**：现在阅读 `references/5-run-tests.md` 以获取详细的子步骤。

**目标**：端到端执行完整管道并使其在没有机械错误的情况下运行。此步骤严格关于修复 pixie QA 组件（数据集、Runnable、自定义评估器）中的设置和数据问题——**不是修复应用程序本身或评估结果质量**。一旦 `pixie test` 完成而没有任何错误，并针对每个条目生成真实的评估器分数，此步骤就完成了。

> **检查点**：`pixie test` 运行完成。每个数据集条目都有评估器分数（真实的 `EvaluationResult` 或 `PendingEvaluation`）。没有设置错误、没有导入失败、没有数据验证错误。
>
> 如果测试出错，那是一个 QA 组件中的机械错误——修复并重新运行。但一旦测试产生分数，继续。在这里不要评估结果质量——那是步骤 6。

**始终在测试产生分数后继续到步骤 6。** 分析是最终的必要步骤——如果没有它，待处理的评估永远不会完成，用户会得到未解释的原始分数，没有任何可操作的见解。不要在这里停止并请求用户是否继续。

**迭代运行的循环规则**：每次成功的 `pixie test` 调用都会创建一个具体的 `pixie_qa/results/<test_id>` 目录并开始一个新的分析周期。在编辑应用程序代码、提示、数据集、评估器或重新运行 `pixie test` 之前，完成该结果目录的步骤 6。不要跳过早期周期，只分析最后一次运行。

### 步骤 6：分析结果

> **参考**：现在阅读 `references/6-analyze-outcomes.md`——它包含完整的三阶段分析过程、编写指南和输出格式要求。

**目标**：通过结构化、数据驱动的流程分析 `pixie test` 结果，以生成关于测试用例质量、评估器质量和应用程序质量的可操作见解。此步骤完成待处理的评估，编写每个条目和每个数据集的分析，并生成优先级行动计划。每个陈述都必须有来自评估运行的**具体数据**支持——没有猜测，没有含糊其辞。

**持久化的分析工件**：在此简化工作流中，仅在数据集级别和测试运行级别持久化分析。这些工件仍然使用**详细版本**（用于代理消费：数据点、证据链、推理链）加上**摘要版本**（用于人类审查：简洁的 TLDR 可在 2 分钟内阅读）。不要创建每个条目的分析文件。

**硬完成门**：步骤 6**未完成**，直到以下所有内容都为真：

- 每个数据集目录中 `pixie_qa/results/<test_id>/dataset-*/entry-*/evaluations.jsonl` 的所有 `"status": "pending"` 条目都已替换为包含 `score` 和 `reasoning` 的评分结果。
- 每个数据集目录都有 `analysis.md` 和 `analysis-summary.md`。
- 测试运行根目录有 `action-plan.md` 和 `action-plan-summary.md`。
- 你已运行此技能 `resources/` 目录中的步骤 6 验证器脚本，并且它报告成功。

**明确不充分**：

- 编写一个顶级文件，例如 `pixie_qa/06-analysis.md`
- 说待处理的评估是用户在 Web UI 中审查的
- 说一个条目“可能通过”，而没有更新 `evaluations.jsonl`

## 网页服务器管理

pixie-qa 在后台运行一个网页服务器，用于向用户显示上下文、跟踪和评估结果。它由 setup 脚本自动启动（通过 `pixie start`，它启动一个分离的后台进程并立即返回）。

当用户完成评估驱动开发工作流时，告知他们网页服务器仍在运行，你可以使用以下命令清理它：

```bash
pixie stop
```

重要提示：网页服务器停止后，网页 UI 将无法访问。因此，只有在用户确认他们已完成所有网页 UI 功能时才停止服务器。如果他们想继续使用网页 UI，不要停止服务器。

并且，每当您重新启动工作流时，始终再次运行资源中的 setup.sh 脚本，以确保网页服务器正在运行：
