# 为 Oracle 到 PostgreSQL 迁移规划集成测试

分析单个目标项目，识别需要集成测试的数据访问组件，然后生成结构化、可操作的测试计划。

## 工作流程

```
进度：
- [ ] 第 1 步：识别数据访问组件
- [ ] 第 2 步：分类测试优先级
- [ ] 第 3 步：编写测试计划
```

**第 1 步：识别数据访问组件**

仅限于目标项目范围。查找直接与数据库交互的类和方法——仓库（repositories）、数据访问对象（DAOs）、存储过程调用者、执行 CRUD 操作的服务层。

**第 2 步：分类测试优先级**

根据迁移风险对组件进行排序。优先考虑使用 Oracle 特有功能的方法（refcursors、`TO_CHAR`、隐式类型转换、`NO_DATA_FOUND`），而非简单的 CRUD 操作。

**第 3 步：编写测试计划**

编写涵盖以下内容的 Markdown 计划：
- 可测试组件列表及方法签名
- 每个组件的推荐测试用例
- 种子数据需求
- 需验证的 Oracle→PostgreSQL 行为差异
- 覆盖映射，确保每个数据库交互点至少有一个测试用例（或高风险方法的合理用例集）

定义推荐测试用例时，明确包含：
- 文本参数在空字符串和 `NULL`/缺失值下的行为。
- 日期时间/时区断言，包括往返和比较行为。
- 目标列使用 `timestamp without time zone` 或 `timestamp(0)` 的场景，并明确时区应用预期。

## 输出

将计划写入：`.github/oracle-to-postgres-migration/Reports/{TARGET_PROJECT} Integration Testing Plan.md`

## 关键约束

- **单一项目范围** — 仅计划目标项目内组件的测试。
- **仅数据库交互** — 跳过不涉及数据库的业务逻辑。
- **Oracle 为黄金源** — 测试应捕获 Oracle 的预期行为，用于与 PostgreSQL 进行比较。
- **无多连接适配器** — 迁移后的应用程序被复制并重命名（例如，`MyApp.Postgres`），每个实例只针对一个数据库。
