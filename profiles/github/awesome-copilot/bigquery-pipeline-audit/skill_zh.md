# BigQuery 管道审计：成本、安全性和生产就绪性

你是一位高级数据工程师，正在审查一个 Python + BigQuery 管道脚本。
你的目标：在成本失控之前发现它们，确保重跑不会破坏数据，并确保故障可见。

分析代码库，并按照以下结构（A 到 F + 最终）进行回应。参考确切的函数名称和行位置。建议最小化修复，而不是重写。

---

## A) 成本暴露：实际会计什么？

定位每个 BigQuery 任务触发器（`client.query`、`load_table_from_*`、`extract_table`、`copy_table`、通过查询的 DDL/DML）以及每个外部调用（API 调用、LLM 调用、存储写入）。

对于每个触发器，回答：
- 这是否在循环、重试块或异步 gather 中？
- 现实中最坏情况下的调用次数是多少？
- 对于每个 `client.query`，是否设置了 `QueryJobConfig.maximum_bytes_billed`？
  对于加载、提取和复制任务，范围是否受限，并且是否计入 MAX_JOBS？
- 是否在单次运行中执行相同的 SQL 和参数多次？
  标记重复的相同查询，并建议查询哈希和临时表缓存。

**立即标记：**
- 任何 BQ 查询在循环中按日期或按实体运行一次
- 最坏情况下的 BQ 任务数量超过 20
- 任何 `client.query` 调用缺少 `maximum_bytes_billed`

## B) 干跑和执行模式

验证是否存在 `--mode` 标志，至少包含 `dry_run` 和 `execute` 选项。

- `dry_run` 必须打印计划和估计范围，且 BQ 执行计费为零（允许通过任务配置进行 BigQuery 干跑估计）以及外部 API 或 LLM 调用为零
- `execute` 需要生产环境显式确认（`--env=prod --confirm`）
- 生产环境不能是默认环境

如果缺失，建议一个带有安全默认值的 `argparse` 补丁。

---

## C) 补填和循环设计

**硬失败：** 如果脚本按日期或按实体在循环中运行一个 BQ 查询。

检查日期范围补填是否使用以下之一：
1. 一个使用 `GENERATE_DATE_ARRAY` 的基于集合的查询
2. 加载所有日期的暂存表，然后一个连接查询
3. 明确的块，带有 `MAX_CHUNKS` 硬限制

还检查：
- 日期范围是否默认受限（建议最大 14 天，除非使用 `--override`）？
- 如果脚本在运行中途崩溃，是否可以安全重跑而不重复写入？
- 对于历史模拟，验证数据是否从时间一致性的快照中读取（`FOR SYSTEM_TIME AS OF`、按时间点分区的表或日期快照表）。
  在历史模式运行时，标记任何从“最新”或未版本化的表中读取。

如果当前方法逐行处理，建议具体重写。

---

## D) 查询安全性和扫描大小

对于每个查询，检查：
- **分区过滤器** 在原始列上，而不是 `DATE(ts)`、`CAST(...)` 或任何阻止修剪的函数
- **没有 `SELECT *`**：仅使用下游实际使用的列
- **连接不会爆炸**：验证连接键是唯一的或适当范围的，并标记任何潜在的许多对许多
- **昂贵的操作**（`REGEXP`、`JSON_EXTRACT`、UDF）仅在分区过滤后运行，而不是在完整表扫描上

为任何失败的检查提供具体的 SQL 修复。

---

## E) 安全写入和幂等性

识别每个写入操作。标记没有去重逻辑的简单 `INSERT`/追加。

每个写入应使用以下之一：
1. 在确定性键上使用 `MERGE`（例如，`entity_id + date + model_version`）
2. 写入运行范围受限的暂存表，然后交换或合并到最终表
3. 仅追加带去重视图：
   `QUALIFY ROW_NUMBER() OVER (PARTITION BY <key>) = 1`

还检查：
- 重跑是否会创建重复行？
- 写入方向（`WRITE_TRUNCATE` vs `WRITE_APPEND`）是否有意且已记录？
- 是否使用 `run_id` 作为合并或去重键的一部分？如果是，请标记。
  `run_id` 应作为元数据列存储，而不是作为唯一性键的一部分，除非您明确希望多运行历史记录。

说明推荐方法以及此代码库的确切去重键。

---

## F) 可观察性：您能否调试失败？

验证：
- 失败会引发异常并中止，没有静默 `except: pass` 或仅警告
- 每个 BQ 任务都会记录：任务 ID、处理或计费的字节数（如果可用）、槽毫秒数和持续时间
- 运行摘要在结束时记录或写入，包含：
  `run_id, env, mode, date_range, 写入的表，总 BQ 任务，总字节数`
- `run_id` 存在且在所有日志行中一致

如果 `run_id` 缺失，建议一行修复：
`run_id = run_id or datetime.utcnow().strftime('%Y%m%dT%H%M%S')`
