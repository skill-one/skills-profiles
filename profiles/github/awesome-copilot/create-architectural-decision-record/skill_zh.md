# 创建架构决策记录

使用针对 AI 消费和人类可读性优化的结构化格式，为 `${input:DecisionTitle}` 创建 ADR 文档。

## 输入

- **背景**: `${input:Context}`
- **决策**: `${input:Decision}`
- **备选方案**: `${input:Alternatives}`
- **利益相关者**: `${input:Stakeholders}`

## 输入验证
如果任何必需的输入未提供或无法从对话历史中确定，请在继续生成 ADR 之前要求用户提供缺失信息。

## 要求

- 使用精确、无歧义的语言
- 遵循标准化的 ADR 格式，并包含前文
- 包含正面和负面后果
- 记录备选方案及其拒绝理由
- 结构便于机器解析和人类参考
- 对于多项目部分，使用编码的圆点符号（3-4 字母代码 + 3 位数编号）

ADR 必须保存在 `/docs/adr/` 目录中，命名格式为：`adr-NNNN-[title-slug].md`，其中 NNNN 是下一个连续的 4 位数（例如，`adr-0001-database-selection.md`）。

## 必需的文档结构

文档文件必须遵循以下模板，确保所有部分都正确填写。Markdown 的前文应按照以下示例正确结构化：

```md
---
title: "ADR-NNNN: [决策标题]"
status: "提议"
date: "YYYY-MM-DD"
authors: "[利益相关者姓名/角色]"
tags: ["架构", "决策"]
supersedes: ""
superseded_by: ""
---

# ADR-NNNN: [决策标题]

## 状态

**提议** | **接受** | **拒绝** | **被取代** | **已弃用**

## 背景

[需要此决策的问题陈述、技术约束、业务需求和环境因素。]

## 决策

[选择的解决方案及其选择的明确理由。]

## 后果

### 正面

- **POS-001**: [有益的结果和优势]
- **POS-002**: [性能、可维护性、可扩展性改进]
- **POS-003**: [与架构原则的一致性]

### 负面

- **NEG-001**: [权衡、限制、缺点]
- **NEG-002**: [引入的技术债务或复杂性]
- **NEG-003**: [风险和未来挑战]

## 考虑过的备选方案

### [备选方案 1 名称]

- **ALT-001**: **描述**: [简要技术描述]
- **ALT-002**: **拒绝理由**: [未选择此选项的原因]

### [备选方案 2 名称]

- **ALT-003**: **描述**: [简要技术描述]
- **ALT-004**: **拒绝理由**: [未选择此选项的原因]

## 实施说明

- **IMP-001**: [关键的实施方案注意事项]
- **IMP-002**: [如适用，迁移或发布策略]
- **IMP-003**: [监控和成功标准]

## 参考

- **REF-001**: [相关的 ADR]
- **REF-002**: [外部文档]
- **REF-003**: [参考的标准或框架]
```
