# 产品经理助手：功能识别与规范

本工作流将指导您通过系统化方法识别缺失功能、对其进行优先级排序，并为实施创建详细规范。

## 1. 项目理解阶段

- 审查项目结构以了解其组织方式
- 阅读README.md和其他文档文件以了解项目的核心功能
- 通过检查以下内容识别现有实现状态：
  - 主入口点（CLI、API、UI等）
  - 核心模块及其功能
  - 测试以了解预期行为
  - 任何占位符实现

**指导问题：**
- 该项目的首要目的是什么？
- 它解决了哪些用户问题？
- 当前实现中存在哪些模式？
- 文档中提到但未完全实现的功能有哪些？

## 2. 差距分析阶段

- 仅将文档中记载的功能与实际实现进行比较
- 识别缺乏实际功能的地方位符代码
- 寻找文档中提到但缺失稳健实现的功能
- 考虑用户旅程并识别中断或缺失的步骤
- 首先关注核心功能（而非锦上添花的功能）

**输出创建：**
- 创建一个潜在缺失功能列表（5-7项）
- 对于每个功能，记录：
  - 当前实现状态
  - 文档中的引用
  - 缺失时对用户体验的影响

## 3. 优先级排序阶段

- 对每个识别的差距进行评分：

**评分矩阵（1-5分制）：**
- 用户影响：多少用户受益？
- 战略一致性：是否符合核心使命？
- 实施可行性：技术复杂度？
- 资源需求：开发工作所需？
- 风险等级：潜在负面影响？

**优先级 = (用户影响 × 战略一致性) / (实施工作 × 风险等级)**

**输出创建：**
- 基于评分呈现3个最高优先级缺失功能
- 对于每个功能，提供：
  - 功能名称
  - 当前状态
  - 未实施时的影响
  - 对其他功能的依赖关系

## 4. 规范开发阶段

- 对于每个优先级排序的功能，开发详细但实用的规范：
  - 首先从哲学方法入手：简单优于复杂
  - 首先关注最小可行产品功能
  - 考虑开发者体验
  - 保持规范对实施友好

**每个功能规范包含：**
1. **概述与范围**
   - 解决什么问题？
   - 包含什么？明确排除什么？

2. **技术要求**
   - 核心功能需求
   - 用户界面（API、UI、CLI等）
   - 与现有代码的集成点

3. **实施计划**
   - 创建或修改的关键模块/文件
   - 简单代码示例展示方法
   - 清晰的数据结构和接口

4. **验收标准**
   - 如何知道完成？
   - 必须工作的具体功能
   - 应通过哪些测试？

## 5. GitHub问题创建阶段

- 对于每个规范，创建GitHub问题：
  - 清晰、描述性的标题
  - 详细的规范作为正文
  - 合适的标签（增强功能、高优先级等）
  - 在相关位置明确提及最小可行产品理念

**问题模板结构：**

# [功能名称]

## 概述
[功能及其目的的简要描述]

## 范围
[包含什么？明确排除什么]

## 技术要求
[具体技术需求和限制]

## 实施计划
[分步方法及简单代码示例]

## 验收标准
[功能完整的清晰要求列表]

## 优先级
[优先级排序的说明]

## 依赖关系
- **阻塞：** [被此问题阻塞的其他问题]
- **被阻塞：** [此问题依赖的其他问题]

## 实施规模
- **预估工作量：** [小/中/大]
- **子问题：** [如果此问题是父问题，链接到子问题]

## 5.5 工作分配优化

- **独立性分析**
  - 审查每个规范以识别真正独立的组件
  - 重构规范以最大化独立工作流
  - 在相互依赖组件之间创建清晰边界

- **依赖关系映射**
  - 对于具有不可避免依赖的功能，建立清晰的问题层级
  - 为整体功能创建父问题，为组件创建子问题
  - 明确记录“阻塞”和“被阻塞”关系

- **工作量平衡**
  - 将大型规范分解为更小的可管理子问题
  - 确保每个子问题代表1-3天的开发工作
  - 包含子问题特定的验收标准

**实施指南：**
- 使用GitHub问题链接语法创建明确关系
- 添加标签指示依赖状态（例如，“阻塞”，“先决条件”）
- 为每个问题包含预估复杂度/工作量以辅助冲刺计划

## 6. 最终审查阶段

- 总结所有创建的规范
- 突出功能之间的实施依赖关系
- 建议逻辑实施顺序
- 记录任何潜在挑战或注意事项

在整个过程中请记住：
- 倾向于简单而非复杂
- 从能工作的最小可行产品开始
- 关注开发者体验
- 建立可后续扩展的基础
- 考虑开源社区和贡献模式

本工作流体现的我们的方法应有助于保持功能规范和优先级排序的一致性，确保软件项目以用户为中心的方式演进。
