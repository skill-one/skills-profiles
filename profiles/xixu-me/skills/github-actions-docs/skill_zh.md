GitHub Actions 的问题很容易根据过时的记忆来回答。利用这项技能将答案基于官方 GitHub 文档，并返回最接近的权威页面，而不是通用的 CI/CD 建议。

## 使用场景

在以下情况下使用这项技能：

- GitHub Actions 概念、术语或产品边界
- 工作流 YAML、触发器、作业、矩阵、并发、变量、上下文或表达式
- GitHub 托管的运行器、更大的运行器、自托管运行器或 Actions 运行器控制器
- 产物、缓存、可重用工作流、工作流模板或自定义操作
- 密钥、`GITHUB_TOKEN`、OpenID Connect、产物证明或安全工作流模式
- 环境、部署保护规则、部署历史记录或部署示例
- 从 Jenkins、CircleCI、GitLab CI/CD、Travis CI、Azure Pipelines 或其他 CI 系统迁移
- 当用户需要文档、语法指导或官方参考时，排除工作流行为故障排除

不要使用这项技能：

- 特定的失败 PR 检查、缺失的工作流日志或 CI 故障排除。使用 `gh-fix-ci`。
- 通用 GitHub 拉取请求、分支或存储库操作。使用 `github`。
- CodeQL 特定的配置或代码扫描指导。使用 `codeql`。
- Dependabot 配置、分组或依赖更新策略。使用 `dependabot`。

## 工作流程

### 1. 对请求进行分类

在搜索之前，决定问题属于哪个类别：

- 入门或教程
- 工作流编写和语法
- 运行器和执行环境
- 安全和供应链
- 部署和环境
- 自定义操作和发布
- 监控、日志和故障排除
- 迁移

如果你需要一个快速的起点，加载 `references/topic-map.md` 并跳转到最接近的部分。

### 2. 首先搜索官方 GitHub 文档

- 将 `docs.github.com` 视为权威来源。
- 优先选择 <https://docs.github.com/en/actions> 下的页面。
- 使用用户的精确术语加上一个聚焦的 Actions 语句，例如 `workflow syntax`、`OIDC`、`reusable workflows` 或 `self-hosted runners` 进行搜索。
- 当多个页面都合理时，比较 2-3 个候选页面，选择最直接回答用户问题的页面。

### 3. 在回答前打开最佳页面

- 阅读最相关的页面，并在实际情况下阅读确切的章节。
- 仅使用主题地图来缩小搜索范围或显示可能的起始页面。
- 如果一个页面看起来被重命名、移动或缺失，请明确说明，并返回最近的权威页面，而不是猜测。

### 4. 使用基于文档的指导进行回答

- 用平实的语言直接回答。
- 包括确切的 GitHub 文档链接，而不仅仅是文档主页。
- 仅在用户要求时或文档页面需要示例时提供 YAML 或分步示例。
- 使任何推断都明确。好的措辞：
  - `根据 GitHub 文档，...`
  - `推断：这可能意味着...`

## 回答结构

除非用户要求深入，否则使用紧凑结构：

1. 直接回答
2. 相关文档
3. 示例 YAML 或步骤，仅当需要时
4. 明确的推断调用，仅当你不得不连接多个文档页面时

将引用保持在它们支持的声明附近。

## 搜索和路由技巧

- 对于概念问题，优先选择概述或概念页面，然后再选择深入的参考页面。
- 对于语法问题，优先选择工作流语法、事件、上下文、变量或表达式参考页面。
- 对于安全问题，优先选择 `Secure use`、`Secrets`、`GITHUB_TOKEN`、`OpenID Connect` 和产物证明文档。
- 对于部署问题，优先选择环境和部署保护文档，然后再选择云特定示例。
- 对于迁移问题，优先选择迁移中心页面，然后是特定平台的迁移指南。
- 如果用户要求一个初学者逐步指南，从教程或快速入门开始，而不是原始参考页面。

## 常见错误

- 根据记忆回答而不验证当前文档
- 链接 GitHub Actions 文档主页，而存在更窄的页面
- 混淆可重用工作流和组合操作
- 建议长期云凭证，而 OIDC 是更好的文档路径
- 将特定存储库的 CI 调试视为文档问题，而应交给 `gh-fix-ci`
- 让相邻域吸收请求，而 `codeql` 或 `dependabot` 更适合
