# 将 CMS 迁移到 Payload

通过源 CMS 数据交互式设计 Payload 集合。配置优先方法：在数据导入之前通过对话建立数据结构。

## 工作流

```
开始
  ↓
请求数据样本
  ↓
分析数据结构
  ↓
提出集合配置
  ↓
用户审阅 ──────────────┐
  │                        │
  ├─ 需要修改 ───→ 调整配置 ──→ (返回用户审阅)
  │
  └─ 看起来不错 ───→ 配置确认
                            ↓
                    还有其他集合？ ──────┐
                            │               │
                            ├─ 是 ──→ (返回请求数据样本)
                            │
                            └─ 否 ───→ 所有集合确认
                                              ↓
                                      讨论迁移方法
                                              ↓
                                            完成
```

## 第一阶段：数据分析

当用户提供数据（JSON、CSV 或描述其架构）时：

1. **识别字段类型** - 文本、数字、日期、关系、媒体、富文本
2. **发现模式** - ID、时间戳、嵌套对象、数组
3. **注意关系** - 外键、嵌入引用、链接内容类型
4. **标记歧义** - 可能是多种类型的字段、目的不明确

## 第二阶段：提出集合配置

根据分析呈现 Payload 集合配置：

```typescript
// 示例输出格式
export const Posts: CollectionConfig = {
  slug: 'posts',
  fields: [
    { name: 'title', type: 'text', required: true },
    { name: 'content', type: 'richText' },
    { name: 'author', type: 'relationship', relationTo: 'users' },
    // ...
  ],
}
```

解释每个字段的选择理由。当某项内容有多种可能（分组与 JSON、文本与文本区域、选择与关系），应询问而非假设。

## 第三阶段：与用户迭代

处理不确定性：必填字段、hasMany 关系、富文本与 HTML、自定义时间戳与内置。持续进行直至用户确认配置。

## 第四阶段：其他集合

每次确认后，询问：

> "我们是否应该为其他内容类型创建集合？"

如果需要，则返回第一阶段并提供新数据样本。

常见的相关集合提示：
- 媒体/上传
- 用户/作者
- 分类/标签
- 设置（全局）

## 第五阶段：迁移方法

仅当所有集合确认后，讨论数据导入：

1. **顺序很重要** - 哪些集合没有依赖关系？先迁移这些
2. **关系映射** - 如何将源 ID 映射到 Payload ID
3. **媒体处理** - 下载/重新上传与外部 URL
4. **富文本** - HTML 转换需求或保留原始

提供生成种子脚本或演示手动导入的选项。

## 需要澄清的事项

在整个过程中，注意以下事项：

- **ID 引用** - 它们是否指向其他集合的关系？
- **图像/文件 URL** - 上传字段或保留为外部 URL？
- **嵌套对象** - 分组、数组或区块？
- **本地化** - 任何字段需要按区域值？
- **访问控制** - 谁可以读写此集合？
- **相关内容类型** - 需要创建集合的分类、标签、作者？

## 关键：选择与关系

**这是最常见的迁移错误。** 看起来静态的数据通常需要动态处理。

当你看到重复的字符串值（分类、标签、类型、状态）：

```json
{ "category": "Technology" }
{ "category": "News" }
{ "category": "Technology" }
```

**不要假设它是选择字段。** 询问：

> "我看到 `category` 有 'Technology'、'News' 等值。这应该是：
> - 一个 **选择字段**，具有固定选项（值不会改变）
> - 一个 **关系**到分类集合（用户可以添加/编辑/删除分类）"

**默认使用关系** 对于以下看起来像的内容：
- 分类、标签、主题、标签
- 作者、指派者、审阅者
- 超出简单草稿/发布的状态
- 随时间可能扩展的类型

**仅用于：**
- 真正固定的枚举（是/否、草稿/发布/归档）
- 由业务逻辑定义而非内容的选项（支付状态、优先级级别）
- 改变会破坏功能的值（有代码依赖的角色类型）

如果创建关系，记得将相关集合（分类、标签等）添加到迁移计划。

## 常见陷阱

| 问题 | 处理方法 |
|-------|---------------|
| 用户提供部分数据 | 请求更多样本，特别是边缘情况 |
| 关系不明确 | 询问用户如何连接内容类型 |
| 富文本歧义 | 澄清：词汇编辑器、Slate 或存储原始 HTML |
| 缺少媒体集合 | 在引用前始终确认上传集合存在 |
| 过于复杂的嵌套数据 | 考虑扁平化或使用区块替代深层分组 |
