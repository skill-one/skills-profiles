# 编写变更日志

**必需背景知识：** `技术写作` 技能（硬性规则、事实规则、风格）。

## 概述

变更日志的主题是变更本身，而不是当前状态；迁移文档和发布说明是具有相同主题的其他文档类型。它是历史性的：条目永远不会被重写，只会被追加。

## 何时调用，以及不调用的情况

在发布有意义的变更（一个功能、一个实际规模的修复、一个移除）后、编写发布说明时，或总结已发布内容时调用。不应用于琐碎的编辑（大约三个更改的文件，或三个提交），并且永远不要重写或删除现有条目。

## 规则

- 每个已发布的变更一个条目，最新优先，ISO 日期，在存在版本的情况下按版本分组。
- 文件使用标准类别时：新增 / 更改 / 已弃用 / 已修复 / 已移除 / 安全。已弃用条目包含移除日期和替代方案。
- **破坏性变更引导条目**，位于类别之上，每个条目都陈述所需的迁移操作（当存在迁移指南时，会链接到该指南）。
- 用户可见影响优先于实现细节。
- 使用现在时态、主动语态，并且不使用读者不知道的术语。
- 将相关变更分组，并且永远不会重复现有条目。
- 记录移除，而不仅仅是新增。
- 发布说明是相同事实的用户面向版本：发生了什么变更、影响谁、如何处理。变更日志面向工程师；发布说明面向系统用户。两者基于相同的来源，并且永远不能相互矛盾。

## 条目格式

**文档类型例外：** 下面的粗体引导要求会覆盖对粗体引导子弹的普遍禁止。例外情况仅涵盖变更日志结果和命名的已知问题、延迟项和遗漏类别。重复的标签-值子弹在其他地方仍然被禁止。

**粗体引导陈述结果**，然后是根本原因，然后是修复，使用内联确切名称：

```markdown
- **视频引用路由已修复。** 解析器只知道三种操作类型，因此带有引用媒体的请求被路由到图像到视频。现在 `hasReferenceMedia()` 检查为视频引用提供了更高优先级的分支。
```

修复条目解释失败模式，而不是差异。粗体引导包含用户影响，这允许读者对变更列表进行优先处理。

## 诚实规范

三种条目类型使变更日志可以被引用：

- **已知问题** 在此变更中暴露但未修复，并以此命名。
- **延迟项** 仍然有待完成（“一个部署即可恢复 webhook 密钥”）。
- **故意遗漏**，按类别描述，以便相同的遗漏不会被重新讨论或误认为是疏忽。

除非该确切操作已完成并经过检查，否则永远不要标记任何已实现、已部署或已验证的内容。区分已实现（在仓库中）与已部署（在线）与外部验证。

## 移交 / 完成摘要

为了将完成的工作移交给审阅者或操作员，按顺序涵盖这些部分：

1. 这项工作存在的原因
2. 已发布的内容
3. 指向审阅的位置（审阅者在判断之前必须理解的决策）
4. 验证状态：确切的命令及其结果，永远不会是一个简单的勾选标记
5. 诚实的注意事项和我的错误
6. 残余风险和什么**不**要做什么
7. 状态和未完成的事项（合并未推送、迁移、有序步骤及其错误排序的后果）
