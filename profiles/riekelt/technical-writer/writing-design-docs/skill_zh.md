# 编写设计文档

**必备背景：** `technical-writing` 技能（先读前提，硬性规则，事实规则，风格）。

## 概述

设计文档是一个可讨论的提案：结论先行，每个非平凡的决策都在一个“为何与何为”框中说明，成本紧随效益之后列出，事实与提案分离。

## 何时使用，以及何时不用

适用于任何论证变更或记录设计的场景：提案、RFC、设计文档、规范、迁移计划、“是否应该”文档。**不**适用于记录已决定的决策（`recording-decisions`）、记录流程（`writing-runbooks`）或状态报告。

在压力下：提案通过其数据和明确成本进行说服，无论截止日期如何（`technical-writing` 规则；"简洁"不是例外）。当提供的事实没有来源时，标记为 `**[需要来源：...]**` 并继续编写（参见 `technical-writing` 技能中的 `references/truth.md`）；永远不要编造引用，也永远不要默默忽略事实。

## 框架

```markdown
# 标题：文档的作用

**副标题：用一句话锁定范围**

|                |                                            |
| -------------- | ------------------------------------------ |
| **状态**     | 草稿 / 请求评论                             |
| **负责人**      | [团队或角色]                             |
| **范围**      | [明确范围，包括不在此范围内的内容]   |
| **相关**    | [链接到同级文档]               |
| **受众**   | [必须阅读此文档的人]                       |

---

## 1. 摘要
[结论立即呈现。不是场合，不是方法。]

## 2. [背景 / 分析了什么]
## 3. [分析，按问题拆分]
## n. 开放性问题
## n+1. 效益与成本
[两者都要。仅效益读起来像销售文案。]
## n+2. 残余风险和不做什么
[只有在设计将工作交给其他团队时才需要。]

---

*结束语：哪些是事实，哪些是提案，以及在哪里需要输入。*
```

## 结构规则

- **编号章节** 并引用为 `ch. 7.1`。
- **目标和非目标都要。** 非目标（或“明确不改变”）部分说明哪些内容保持不变。
- **定义先于行为** 当术语模糊时：在使用前锁定“响应”、“符合资格”、“过时”等术语。
- **一个基础部分** 锁定设计所依赖的事实：事实/来源表，与命名提交进行核对。将已验证的事实与将要构建的内容分离。
- **附录** 使用字母（附录 A、B）并包含会淹没正文的内容：配置示例、术语表、清单。
- **事实存在于一个地方。** 链接到它；永远不要重复，即使在同一仓库的文档中也不要。
- **用 `**[DRAFT - input wanted]**` 标记未完成部分**，而不是省略它们。
- **开放性问题需要负责人**：一个名字、一个角色，或明确的“待填写”。
- **残余风险和不做什么** 在设计将工作交给其他团队时关闭文档。
- **没有行数预算**，但重复或强调的长度会超出；当长度超过大约 800 行时，拆分并让主文档链接到各部分。

## “为何与何为”框

每个非平凡的选择都有一个；读者对框的反应，而不是结论。

```markdown
> **为何与何为 - [用四个字描述选择]**
>
> **何为：** [选择，一句话，无理由]
>
> **为何：** [理由。也说明选择未解决的问题。]
>
> **考虑过的替代方案：**
> - *[替代方案]*: [其最强论点，以及为什么它仍然输了]
>
> **后备方案：** [如果这个不成功，什么会幸存]
```

- 没有最强论点就被否决的替代方案是稻草人。说出那个论点。
- 承认选择未解决的问题使文档更具可信度。
- 没有框用于无人会争议的选择；那是噪音。
- 在文档其他地方没有出现的替代方案不属于框：读者永远不会考虑它。一个这样的拒绝可以合理；连续几个简短的拒绝意味着框被填充了。

## 语气

- 文档保持为提案：“我们提议”和“是否说服你取决于你”，而不是“这将成为工作方式”。它设定方向，并留下详细选择开放。
- 标明成本。效益章节以价格结束：什么变得更难，人们必须忘掉什么，哪种自由消失了。
- 没有超级形容词，没有承诺语言。具体数字和可验证的陈述。
- 预期结果可能是负面的；提前说明：“预期结果是当前队列比提议的重写更好；这是一个有用的结果。”

## 完整性检查

在将规范或计划交给审阅者或执行者之前，检查五个模糊缺陷：

1. 未解决的占位符：任何字面意义上的 TBD、TODO、“稍后填写”或明显不完整的句子（标记的 `**[DRAFT - input wanted]**` 块是故意的；未标记的空白是缺陷）。
2. 缺少验收标准：没有具体、可独立测试的成功条件的需求。
3. 未定义的引用：提到的类型、端点、组件或表但未在任何地方定义。
4. 没有可验证的输出：产生无法由审阅者检查的任务（没有文件路径、没有命令、没有可观察的行为）。
5. 没有如何：没有可实施方向的结果（“适当处理错误”，但没有定义适当）。

对于执行计划，每个任务添加：目标、确切文件、显示的变更、具有具体场景的测试，以及验证命令。解释任何令人困惑的遗留问题（一个奇怪的目录名、一个遗留别名），而不是留下谜团。
