# 写作问题

**必需背景：** `technical-writing` 技能（硬性规则、事实规则、风格）。

## 概述

核心原则：**写问题时要确保问题在你离开后也能自行解决。** 说明结果，包含决定完成的验收检查，链接每个决策背后的证据，并命名每个开放部分的所有者。

## 何时使用，以及何时不用

在编写或编辑追踪器项、提交错误报告、将工作拆分为工单或编写验收标准时使用。**不要**用于权衡备选方案：当问题需要设计论证时，那是 `writing-design-docs`；问题链接设计文档，而不会内联它。这项技能仅涵盖写作，不涉及优先级或工作流建议。

追踪器适用“先读后写”：在提交前，阅读最多两个同类近期问题，并匹配它们的规范。当追踪器中的问题较少时，阅读现有内容并无论如何提交。

当报告人不可用时，使用命名空白而不是阻塞来提交。`technical-writing` 检查点（类型、受众、目的、非目标）是你要停下来询问的内容。缺失的内容细节（一个重现步骤、一条日志行、一个先前列事链接）成为问题内部明确拥有的开放项。

## “自行解决”测试

每个问题都回答一个陌生人会问的四个问题：

1. **结果是什么？** 这项工作完成后世界将处于什么状态，而不是到达那里的步骤。实施工作属于计划部分。
2. **什么决定完成？** 一个具体、可独立测试的验收检查。“适当处理错误”决定不了什么；“上传失败时显示重试横幅并记录 WARN 级别日志”才有效。
3. **证据是什么？** 决策或约束来自证据，链接来源：一个代码库路径、一个文档、一个 URL。
4. **谁拥有开放部分？** “仍需调查”而没有名字或角色的“模糊所有者”是被禁止的；指定一个或明确将字段标记为未分配。

## 问题类型

每个追踪器一个术语表，每行定义一个，并保持一致使用：

| 类型 | 定义 |
|---|---|
| Epic | 一系列工作；其描述说明结果并链接设计文档 |
| Story | 具有用户可见价值的东西，从用户的角度编写 |
| Task | 没有用户可见表面的工程工作 |
| Bug | 一个缺陷：当前行为与预期行为矛盾 |
| Spike | 一个有时间限制的调查，其输出是决策而不是代码 |

一个 Spike 的完成是决策被记录（见 `recording-decisions`），而不是“查看了”。

一个决策后跟一个工作体的结构适合两种形状：先有一个 Spike，决策后提交 Epic，或一个其第一个验收项是接受的 设计文档的 Epic。两者都有效；选择一个并说明。

## Story 和 Task 框架

问题描述是关于什么和为什么的规范：

```markdown
**问题 / 为什么：** [可观察的问题，从读者的角度，存在数字时附带数字]

**结果：** [完成后世界的状态；不是步骤]

**验收：**
- [ ] [可独立测试的检查]
- [ ] [另一个]

**超出范围：** [这个问题故意不涵盖的内容]

**开放项：** [每个都有命名所有者或角色，或明确的“未分配”]

**来源：** [代码库路径、文档、上述内容背后的测量数据]
```

将 `writing-design-docs` 中的五个模糊缺陷应用于验收列表：一个失败的“没有步骤”或“没有可验证输出”的验收检查是不可测试的。

Gherkin 风格的 given/when/then 是团队使用时的验收检查的接受格式；无论哪种方式，可测试性标准都适用。INVEST（独立、可协商、有价值、可估算、小、可测试）作为故事的大小检查：一个故事在提交前如果“小”或“可测试”失败，则应拆分。

## Bug 报告框架

先描述症状：下一个读者是在寻找错误。

```markdown
**症状：** [逐字错误字符串或可观察的误行为，可搜索]

**重现：** [编号步骤，每个步骤一个动作，从干净状态开始]

**预期：** [应该发生什么，附带说明来源，或明确的“未找到书面来源”而不是编造的参考]
**实际：** [实际发生什么]

**环境：** [版本、平台、重要的配置]

**开放项：** [每个都有命名所有者或角色，或明确的“未分配”]

**疑似原因：** [如果已调查；标记为假设，永远不要陈述为事实]
```

标题承载症状，而不是诊断：“提醒时间重复提醒”，而不是“调度器中的竞争条件”，除非原因已验证。

## 规则

- **一个家。** 问题拥有什么和为什么；代码库中的计划拥有如何。永远不要维护两个活跃副本。
- **工单键。** 它们存在于提交记录和计划文档中，永远不会存在于代码、注释、测试名称或用户可见字符串中。
- **相信代码，而不是问题状态。** 自我报告的状态很快就会过时；在构建导入的或旧的问题之前，通过代码库进行验证（搜索符号，检查历史记录）。
- **追加，不要重写。** 在进行中的问题上范围变更是通过日期追加的笔记，而不是无声的编辑。完成后发现的后续工作是一个新问题，绝不是对已关闭问题的编辑。
- **子任务。** 粗略的可审查切片，而不是每个微步骤；微步骤存在于计划中。
- **估算。** 标记为估算，并注明它们依赖的内容。
- **关闭问题。** 它记录了原因，特别是对于不会修复和重复的问题。
