# 技术写作

## 概述

技术文档的写作规范。规则以英文编写；文档保持其自身语言：一份荷兰语文档用荷兰语编写和审阅。结构和真实性规则适用于任何语言；`references/style.md` 中的词汇表是英文特定的，其他语言拥有自己的词汇表。核心原则：**一份文档陈述当前、经过验证的行为，结论优先，每个主张都有据可查，每个事实都存在于唯一的位置。** 简洁的文档优于夸大的文档。

这些规则适用于文档，而非聊天回复。长度和章节规则适用于连续文本，不适用于参考列表（如本文件）。

## 何时调用

为任何技术性文本加载此技能，然后在顶部加载匹配的文档类型技能。这些是路由提示；每个技能自身的主体是权威。

当仓库定期生成文档时，在项目记忆中记录调用：在其 CLAUDE.md 或平台的等效文件中添加一行，告诉代理为该处的任何技术性文本加载此技能。

| 任务是 | 也加载 |
|---|---|
| 提案、RFC、设计文档、规范或迁移计划 | `writing-design-docs` |
| 记录决策、ADR、决策日志条目 | `recording-decisions` |
| 变更日志条目、发布说明、"已发布内容" | `writing-changelogs` |
| 运行手册、设置指南、流程、故障排除条目 | `writing-runbooks` |
| 跟踪项：史诗、故事、任务、错误报告、探索性任务、验收标准 | `writing-issues` |
| 迁移或弃用指南 | `writing-runbooks` |
| 事后分析、事件报告、根本原因分析 | `writing-postmortems` |
| 文档化现有、文档不足的系统；用代码重新校准陈旧文档 | `documenting-legacy-codebases` |
| 流程、生命周期或交互图；绘制业务逻辑 | `diagramming-processes` |
| API 参考：端点、消息有效负载、DTO、CLI 命令、文件格式、Webhook | `documenting-contracts` |
| 审阅或重写他人的文本；交付任何文档前的最终步骤 | `reviewing-technical-prose` |

## 非目标

- 不适用于营销文案、社交帖子或 UI 微文案；只有 `references/truth.md` 中的真实性规则仍然适用于这些内容。
- 不决定内容：什么是真实的来自来源，而不是来自风格。
- 不授权重写遵循自身约定的现有文档；应用以下优先级规则。
- 不向要求使文档“引人注目”、“有说服力”或“令人信服”：数字说服人，语域保持朴素。

## 拟稿前的强制性检查点

在拟稿新文档或重要章节之前，在工作笔记中推导并陈述：

`Kind: <normative|descriptive|historical|runbook|reference> | Audience: <who> | Purpose: <the verb the reader must accomplish> | Non-goals: <what this deliberately does not cover>`

根据请求、来源和仓库上下文填写字段。陈述安全的假设，并在它不会实质性改变结果时继续。仅当未知信息会改变受众、实质或范围时才提问。不要编造事实来完成检查点；除非其模式要求，否则不要将检查点插入最终文档。

## 先读后写

在写下一行之前：

1. 阅读同一目录下最多两个可比文档；采用其结构、语调和约定。如果可比文档少于两个，则阅读所有可用示例，然后使用仓库级约定。不要因为目录是新的而阻塞。
2. 检查是否存在索引文档的 `README.md`。如果存在，将新文档添加到其中。
3. 检查主题是否已存在于某处。扩展所有者几乎总是比在旁边开始一个竞争性文档更好。

## 规则优先级

当指令冲突时，按以下顺序应用：

1. 真实性、安全性和历史完整性规则。
2. 活动文档类型技能中的明确例外。
3. 以下共享的硬规则。
4. 明确的模式和目标目录中的约定。
5. `references/style.md` 中的共享风格偏好。

现有实践仅控制高级规则未解决的选项。它不能削弱来源、重写接受的史实，或将未经验证的工作表示为已发布。文档类型例外必须指明它违反了哪些规则以及例外的边界。

作者的明确风格选择优先于共享风格偏好，且无其他例外。当作者说保持我的声音不变时，风格检查停止；真实性、安全性和历史性仍然具有约束力，无论谁反对。

## 在编辑前对文档进行分类

每种类型的编辑规则都不同。“更新文档以匹配代码”对五种类型中的两种是主动错误的。

| 类型 | 示例 | 编辑规则 |
|---|---|---|
| 规范性 | 架构原则、合同、风格指南 | 如果代码违反了合同，则不要稀释合同；记录违规行为。仅在合同本身命名已删除或重命名的概念时才编辑。 |
| 描述性 | 流程、组件文档、状态机 | 精确匹配代码。根据实现进行验证，而不是名称。 |
| 历史性 | 变更日志、旧规范、决策日志、已应用的迁移 | 从不重写历史。标记差异；用新条目取代。 |
| 运行手册 | 运行操作、故障排除、发布流程 | 更新以匹配现实；每一步都必须实际运行过。 |
| 参考 | API 文档、配置参考、索引 | 全面：每个键、每个标志，包括默认值和用法列。 |

如果整个文档描述了已删除的内容，则不要删除文件：用一行横幅（"> NOTE: 描述了已删除的组件 X；参见 Y”）标记为过时，并将删除工作留给所有者。

## 硬规则

不可协商的，在每份文档中：

- **不允许使用 em 连字符、en 连字符、` -- ` 连字符。** 使用逗号、冒号、分号、句号、括号或 ` - `（带空格作为旁注标记）作为连字符。纯连字符用于范围（`2026-2030`）。在交付前检查所有三种形式。
- **文档内不允许有变更日志部分和“最后更新”字段。** 这也适用于每个句子：描述当前行为，而不是以前的行为；“这个步骤替换了手动检查”属于迁移文档或发布说明，而不是在流程中。
- **在文本、注释、名称或字符串中不允许作为叙述状态交付历史**：没有阶段、任务 ID、票证键、SHA 或计划引用，它们仅描述了工作是如何交付的。一个固定的提交可以作为主张证据出现。票证键可以作为功能元数据出现在跟踪记录、提交信息、计划文档和引文中；永远不出现在代码注释或用户界面内容中。
- **永远不要将无法追溯到代码（在引用路径、固定提交、测试、文档或主要来源）中的事实**陈述为事实。将一个合理的猜测作为事实提出比“来源对此一无所知”更糟。参见 `references/truth.md`。
- **一个事实，一个归属。** 其他内容链接到所有者。摘要可以路由，永远不会决定：当一个索引和其来源不一致时，来源获胜，索引是错误。
- **接受的决策和应用的迁移是不可变的。** 更正是新日期的条目，永远不会编辑历史。
- **标题使用句子大小写**，永远不用标题大小写。

## 工作流程

1. **先读后写**（如上所述），并对文档进行分类。
2. **拟稿前声明**：填写上述检查点（类型、受众、目的、非目标）。
3. **逐级以结论优先的方式拟稿**：文档、章节、段落。没有铺垫，没有在结果之前提供背景的段落。每个章节以它得出的结论开头，而不是它是如何处理的。
4. **为每个主张提供依据**并标记其信心：`references/truth.md`。
5. **风格检查**：句子、单词、标题和禁止结构列表：`references/style.md`。
6. **交付前验证**：加载 `reviewing-technical-prose` 进行清单检查。通过实际遵循它们来检查参考。

## 受众

在开始之前，要知道你为谁写作。不是“用户”：实际的人、他们在哪里，以及他们必须完成的动词。

| 读者 | 他们需要什么 |
|---|---|
| 开发人员 | 背后的原因，以及明天他们的工作将发生的变化 |
| 技术主管 / 架构师 | 权衡、替代方案、长期后果 |
| 管理层 / 产品负责人 | 它能产出什么，成本是多少，哪些风险 |
| 外部方 | 没有团队名称或术语，没有解释 |

同时面向多个群体：摘要供最广泛的群体阅读，其余部分可以深入。如果一个短语需要脚注，那么需要重写，而不是脚注。

## 常见错误

- 从解决方案开始。首先问题，然后提案。
- 文档化代码已经显示的内容。文档拥有推理、约束、不变量和替代方案；代码拥有“什么”。
- 不可验证的主张：“更快”、“更好”没有数字或来源。添加数字或删除主张。
- 用合理的猜测填补空白，而不是命名空白。
- 模糊的所有者：“这仍然需要调查”没有名称或角色。
- 只列出的好处。每个提案都命名其成本。
- 在编辑过程中默默修剪、重新排序以强调或重写主机文档。编辑是外科手术：保留声音、结构、编号和 ID。
- 大约 800 行散文的文档：将其拆分，并让主文档链接到部分。
