# 测试变更

**必要背景：** `principal-engineering` 技能。测试工艺存在于 `writing-unit-tests` 中；该技能决定了变更需要哪些测试。

## 概述

测试是关于行为主张的可执行形式。修改行为但不触及测试的变更是一个无人写下的主张。随之而来两种失败模式：绿色套件覆盖了无法工作的代码，以及从未运行的测试或门控。

## 变更需要承担的测试

1. **变更中包含行为测试。** 行为变更上的空测试差异是评审发现，而非风格偏好。纯重构则相反：现有测试未经修改仍通过，这才是重构的定义。
2. **bug 修复需要回归测试。** 以失败模式命名，而非工单。作者展示两半：针对未修复代码的红色，针对修复的绿色。从未变红的回归测试只能证明它编译无误。
3. **场景具体且包含暴露的边界。** 通过基础和评审发现的边界案例以命名方式进入测试；仅测试演示路径，而非变更。当变更风险在于失败路径时，失败路径获得测试（参见 `handling-failures`：它需要记录的、输入的失败，且暴露是测试需要承担的行为）。
4. **每个任务都携带其验证命令。** 任务命名证明此变更的验证命令，可单独运行，且在评审者可执行的位置声明。"套件通过" 对未覆盖的内容毫无担保。
5. **断言必须具有区分性。** 无论变更如何通过测试的测试证明不了任何东西。一次破坏代码，确认测试变红，再恢复。非区分性断言是套件在行为已损坏的情况下仍保持绿色的原因。
6. **需要协调的聚合体获得不变量测试。** 项目声明关键路径（参见 `principal-engineering` 中的风险层级）上任何汇总、派生或镜像其他数据的东西，除了点示例外还需更多：测试断言协调本身（守恒模式），聚合体等于原始记录暗示的值。

## 红色测试规则

你拥有的门控中的红色测试必须修复，而非静音：削弱断言、删除测试或标记跳过以发布是将已检测缺陷转化为未检测缺陷。仅当测试断言了旧的行为错误，且变更明确说明时，修改测试才是合法的。首先归因，然后无论归属谁，修复测试；"预存在"只是脚注，绝非借口（参见 `verifying-before-done`）。

## 变更不需要承担的测试

- 不可达边界的测试（参见 `scoping-changes`：围住不可能发生的是带有良好意图的死代码）。
- 框架内部或生成代码的测试。在你们拥有的边界处测试它们的使用。
- 测试优先流程：测试是否优先是工作流（测试优先工作流技能，项目安装一个并管理）；此技能决定变更发布时必须存在的内容，无论其产出顺序。

## 常见错误

- "太小而无需测试。" 一行变更触及了无测试覆盖的行为，回归测试直到审计时才沉默。
- 测试修复而不重现 bug。红-绿的前半部分证明测试看到了缺陷。
- 感觉式覆盖率计数。将变更行为与命名它们的测试（与技术作者插件 `technical-writing/references/truth.md` 下 "Keeping documents true" 部分的文档覆盖率计数规则相同）进行计数。
- 永远添加无区分性的测试：一个任何合理缺陷都无法失败的断言。不同于合法的固定测试，它故意针对旧代码和新代码都通过，以保护未变更的相邻行为免受过度修正；固定测试说明其用途。
