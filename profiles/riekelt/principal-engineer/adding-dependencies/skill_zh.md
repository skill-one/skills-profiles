# 添加依赖项

**必需的背景知识：** `principal-engineering` 技能。

## 概述

依赖项是一种招聘，而不是一个片段：随着功能而来的是它的缺陷、它的发布节奏、它的传递树以及维护者的注意力持续时间。核心原则：**充分利用你已有的，审查你将采用的，锁定你已采用的，并记录原因。**

## 充分利用你已有的

按列表往下工作，在第一个能成立的级别停止；好的答案通常由两个级别组成，一个用于复杂部分的现有依赖项，以及你自己的几行代码围绕它：

1. **需求本身。** 投机性需求不是需求；跳过它，并在一行中说明。
2. **此代码库。** 几个文件之外的助手、类型或模式完成了这项工作；重用它。存储库中已有的东西的第二个副本是 `keeping-one-source-of-truth` 禁止的数据缺陷。
3. **标准库。** 在安装重复它的包之前，先阅读它的索引。
4. **平台。** 数据库约束优于应用程序代码，本地控件优于小部件库，运行时自己的原语优于包装器。
5. **项目已经携带的依赖项。** 它的传递树已经支付了费用。两个边界。你开始使用的传递依赖项是一个新的直接依赖项：声明它，将其锁定到已解析的版本，并轻量级审查它，因为代码已经发布。检查重用跨越的类：一个开发工具的传递提升到运行时将成本转移到每个消费者的安装上，而不仅仅是 CI。
6. **你自己的几行代码。** 拥有二十行代码胜过拥有一个陌生人的存储库，当二十行代码确实是全部所需时。
7. **只有通过所有六个：** 一个新的依赖项，经过以下审查。

## 审查你将采用的

- **整个招聘的成本**：它带来的传递树，安装和构建的重量，许可证与项目的冲突，安全历史记录（公告和一个扫描器运行时的供应链分数）。
- **检查脉搏**：最近的发布，问题如何得到回答，有多少人可以合并。一个承重包只有一个疲惫的拥有者是你在选择的风险。
- **阅读你将调用的部分**：你依赖的 API 表面及其失败模式，而不是 README 的承诺。基础也适用于别人的代码。
- **优先选择单一任务的工具** 而不是具有四十个功能的框架；其他三十九个功能无论如何都会随之而来，在重量和攻击面上。
- **记录决策。** 新的依赖项是一个决策：它的用途，权衡了什么，以及它离开的条件（通过 `recording-decisions` 安装的地方）。

## 依赖项立场

依赖项容忍度是项目声明的，就像它的风险级别一样：完全自包含（一些应用程序正确地完全禁止外部代码），经过策展的允许列表，或审查后添加。项目的规则或 CLAUDE.md 声明了哪个；当什么都没有时，询问系统必须永远不依赖的内容，并将答案视为声明。立场即使在不方便时也要得到尊重；改变它是一个记录的决策，而不是 npm install。

未声明的立场不是一个硬门槛：当今天没有人能回答时，在声明的假设立场下进行，在决策中记录假设，并跟踪声明问题与所有者。

## 锁定并证明

- 提交锁文件并锁定版本；CI 中的未锁定 `latest` 或基础镜像是一个定时炸弹，带有别人的时钟。
- 更新就像任何其他更改一样。在主要升级之前阅读发布说明（破坏性更改和迁移优先）。针对它运行测试 (`testing-changes`)。为主要的升级分配自己的提交，以便责任链保持可读；分组补丁升级可能会一起移动。
- 本地代码在树中携带其来源和版本；你不能更新你不能标记的东西。

## 移除

- 一个其工作消失的依赖项在移除工作的同一更改中离开；保留“以防万一”的包是第一级中的投机性需求，反向。
- 当依赖项只有一个小的调用点时，考虑拥有这些行代码。
- 未维护但承重是一个有所有者和计划的风险项，永远不会是希望。

## 常见错误

- 微型工具反射：树不会通过重大决策生长；它们一次一个小包地生长，每个包单独合理。
- 安装一个框架来调用一个函数。
- 依赖于包的内部或私有路径；只有公共契约是一个承诺。
- 将传递依赖项作为自己的导入：今天未声明，在下一个锁文件刷新时消失。如果你需要它，声明它。
- 添加依赖项以避免阅读存储库中已有的代码（第二级，跳过）。
- 没有来源就本地化，然后想知道副本是哪个版本。
- 一次性更新所有内容，然后二分法查找哪个升级破坏了构建。
