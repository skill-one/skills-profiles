# 防护架构

**必要背景：** `principal-engineering` 技能。

## 概述

结构不变式是承重契约：违反其中之一会暴露出一类错误，而非单个缺陷。**一个重要的不变式需要一个名称、一份书面理由以及一个机械防护；没有防护的不变式只是愿望。**

## 模式

1. **命名不变式。** 编号且可引用（"法则3"），每个包含一个声明（技术中立，旨在超越任何框架）、一个理由以及影响。理由是一个具体的失败叙事：当不变式被违反时出现的一类错误，以事件为背景，而非抽象概念。
2. **区分稳定与易变。** 原则文档很少变更且不命名类；其当前实现（标准所有者、防护机制、参考设计）存在于一个随代码变更的配套文档中。当两者不一致时，不变式起主导作用，实现文档得到修正。
3. **机械执行。** 每个可执行的变式都得到一个架构测试，使构建失败：依赖方向、包边界、分层规则、禁止的导入。无法通过构建强制执行的内容成为一项引用变式的命名审查检查。
4. **违反意味着重构，而非辩解。** 一个违反命名不变式的设计在构造上就是错误的：重构它，不要将例外辩解进规范。将契约削弱以匹配非合规代码是被禁止的举动；违规行为被记录，代码得到修正（这是技术文档插件应用于规范性文档的相同规则）。
5. **规范展示合规性。** 一个触及防护区域的架构需要命名其触及的不变式，并针对每个不变式展示其如何维护；审查者对照命名不变式检查声明，而非争论品味。
6. **例外是修正案。** 一个真正的例外提出修正案，命名其弯曲的不变式和弯曲边界；沉默的例外是使不变式成为建议的方式。这是唯一的合法例外形式，而第4点禁止所有其他形式；无法触及的所有者不会创建例外，因此变更等待或符合规范。一个真正的临时例外是一份有日期、有到期条件且经所有者签字的豁免，记录在易变实现文档中，而非通过修正稳定不变式以获得通过条件。
7. **未解释的防护排除是隐藏在构建中的违规。** 发现者向不变式的所有者揭示它。排除永远不构成下一个例子的先例；将排除列表扩展为"像其他人那样"确认侵蚀，而非遵循模式。

## 常见不变式类别

在大多数系统中值得防护，作为示例而非强制要求：

- 每个关注点一个标准所有者（参见 `keeping-one-source-of-truth`）。
- 依赖方向：领域从不导入交付机制。
- 关键路径隔离：没有I/O，且热路径上没有慢速或可选依赖。
- 关键关闭边界：一个无法评估的闸门必须拒绝（参见 `handling-failures`）。
- 迁移不可变性（参见 `principal-engineering` 中的硬规则）。

## 常见错误

- 原则文档充满类名：实现文档戴着错误的标题；将它们分开。
- 暂时添加导入。边界因单个便利导入而消亡；防护机制的存在是因为每个违规在局部是合理的。
- 审查中声明不变式但构建中不存在：执行频率与正确审查者出现频率完全一致。
- 以合规成本为由辩解违规。成本论据可能正确，但其正确形式是对不变式的修正，由所有者决定，记录（通过 `recording-decisions`，如果安装了该插件），而非在一个规范中的安静例外。
- 将原则写成品味（"偏好小模块"）而非契约（"模块X从不导入模块Y"）。契约可以导致构建失败；品味只能导致心情失败。
