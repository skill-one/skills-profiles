# 代码审查 Pro

找出真正的问题，证明每一个问题，并展示修复方法。简短的真正问题列表胜过冗长的可能问题列表。

## 工作流程

1. **设定范围。** 确定审查内容：粘贴的代码片段、特定文件、工作区差异（`git diff`、`git diff --staged`），或分支与其基线的差异（`git diff main...HEAD`）。对于差异，审查更改的行，但需要阅读足够的周边代码以了解它们是如何被调用的。

2. **在判断之前了解上下文。** 确定语言、框架和版本（检查 `package.json`、`pyproject.toml`、`go.mod` 等），代码是如何被调用的（HTTP 处理程序、作业、CLI、库），哪些输入是不受信任的，以及任何仓库约定（代码检查器、`CLAUDE.md`、现有模式）。在一个框架中是错误的模式，在另一个框架中可能是安全的；例如，React 转义 JSX 文本，所以跨站脚本攻击存在于 `dangerouslySetInnerHTML`、`href` 值和原始 HTML 池中。

3. 使用 [references/checklist.md](references/checklist.md) 按优先级顺序审查：
   1. 安全性
   2. 正确性和边缘情况
   3. 性能
   4. 可维护性和约定

4. **在报告之前验证每一个发现。** 对于每个候选问题，追踪数据流：输入来自哪里，攻击者或真实用户能否控制它，以及上游是否有任何内容已经验证或转义它？检查是否有测试覆盖它。如果你可以运行代码，用一个小测试或脚本重现错误。丢弃你无法支持的问题；标记其余问题为置信度级别。

5. **按以下格式排名并撰写报告。** 以最高严重性开头。将重复出现的一个问题的多个实例合并为一个发现，并包含所有位置。

## 严重性

- **关键** - 现在可利用或导致数据丢失/损坏：用户输入的注入、身份验证绕过、代码中的密钥、真实数据上的访问控制损坏。
- **高** - 在现实条件下可能存在错误或漏洞：共享状态的竞争条件、缺少授权检查、用户界面路径上的无界查询、隐藏失败的吞没错误。
- **中** - 今天正确但脆弱：受信任调用者后面的缺少输入验证、小数据上的 N+1 查询、状态所有权混乱。
- **低** - 代码风格、命名、小的简化。最多报告一小部分；跳过任何代码检查器或格式化器已经强制执行的内容。

## 输出格式

````markdown
# 代码审查：[范围]

**结论**：[发布 / 修复后发布 / 不发布] - [一句话解释原因]
**发现**：[n] 个关键，[n] 个高，[n] 个中，[n] 个低

## 关键

### 1. 用户搜索中的 SQL 注入（`src/api/users.ts:42`）
**类别**：A05:2025 注入 | **置信度**：高
**证据**：`q` 来自 `req.query` 并被插入到 SQL 字符串中；上游没有验证。
**影响**：任何调用者都可以读取或修改任意表。

当前：
```ts
const rows = await db.query(`SELECT * FROM users WHERE name LIKE '%${q}%'`);
```

修复：
```ts
const rows = await db.query("SELECT * FROM users WHERE name LIKE $1", [`%${q}%`]);
```

## 高
...

## 中
...

## 低
- `utils/date.ts:10` - [一行]

## 做得好的地方
[两到三个做得好的具体事项，让作者知道该保留什么。]

[范围之外或无法验证的文件、路径或关注点。]
````

## 导致差评的陷阱

- **不阅读调用者就报告。** "缺少验证" 通常在上一层已经验证。在标记之前先查看。
- **通用建议。** "考虑添加错误处理" 不是一个发现。命名失败：哪个调用会抛出错误，用户会看到什么，留下什么状态。
- **风格作为严重性。** 行长度、括号放置或个人偏好永远不会高于低。
- **过时的规则。** 检查当前使用的版本：当 React 编译器启用时，`useMemo`/`useCallback` 建议 会改变，许多 Node API 现在提供内置（`fetch`、`crypto.randomUUID`、`node:test`）。
- **无法编译的修复。** 每个 "修复" 块都必须对仓库中的语言和版本有效。如有疑问，请说明。
- **泛滥。** 超过大约 15 个发现会埋没关键问题。将长尾总结为一句话。
