# 虚荣工程审查

一种诊断技能，用于识别为了炫耀而非交付而构建的代码、架构和技术决策。虚荣工程是伪装成工艺的熵——它在不成比例的能力提升下增加了复杂性，并在提供零额外用户价值的同时加剧了维护成本。

## 核心前提

**工程唯一的合法目的是解决某人实际存在的问题。**

其他一切——无人使用的优雅抽象、服务于单个端点的微服务、复制现有工具的自定义框架、比所建模领域更复杂的类型系统——都是虚荣。它可能感觉很有生产力。但它不是。

这种技能并不反对质量、严谨性或良好的工程。它反对的是为了满足构建者而非用户而存在的工程。

## 何时应用此技能

将此审查应用于以下任何情况：
- 代码库审计（完整仓库或特定模块）
- 拉取请求审查
- 架构提案或RFC
- 技术选择决策
- 重构计划
- “我们是否应该重建这个？”的讨论
- 复杂性导致失败的复盘

## 审查流程

### 第一阶段：建立需求锚点

在检查任何代码之前，确定系统实际需要做什么。没有这个锚点，你无法区分必要的复杂性与虚荣的复杂性。

询问（或从上下文中确定）：
1. **谁使用这个？**（最终用户、内部团队、API消费者、尚未有人使用）
2. **它必须做什么？**（核心用户故事/待办事项——最多5个）
3. **它实际运行在什么规模上？**（不是预期的。实际的。）
4. **有哪些真实约束？**（监管、延迟SLA、集成要求）
5. **维护这个的团队规模是多少？**（单人开发者？3人初创公司？50人组织？）

如果用户无法回答这些问题，这本身就是一个虚荣信号——在没有明确定义的需求下进行构建。

### 第二阶段：检测扫描

扫描代码库或架构，对照`references/detection-patterns.md`中的检测模式。在进行下一步之前，请先阅读该文件。

使用虚荣严重性量表对每个发现进行评分：

- **V0 — 修饰性**：不必要的但无害的。不增加维护负担。记录并继续。
- **V1 — 拖累性**：在不提供用户价值的情况下增加持续的认知或维护成本。标记以简化。
- **V2 — 结构性**：围绕虚荣而非需求塑造架构。标记以重新设计。
- **V3 — 复合性**：主动迫使其他代码为了适应它而变得更复杂。标记为紧急——这会扩散。

### 第三阶段：虚荣评分

生成结构化评估：

```
## 虚荣工程评估

### 摘要
[一段话：这个代码库做什么与其被工程化去做什么。这两者之间的差距是虚荣表面积。]

### 需求与复杂性比率 (RCR)
[1-10分。1 = 最小可行方案。10 = 伪装成CRUD应用的博士论文。
大多数生产系统应该得分2-4。]

### 顶级发现（最多7个）
对于每个发现：
- 什么：检测到的具体模式
- 位置：文件/模块/组件
- 严重性：V0-V3
- 为什么是虚荣：它如何未能通过“用户是否需要这个？”的测试
- 应该是什么：更简单的替代方案
- 移除成本：移除或简化的工作量（小时/天）

### 虚荣债务估算
[虚荣工程累积的复杂性成本。
表示为：每月归因于虚荣模式而非实际需求的人-小时维护成本。]

### 严峻问题
[团队需要诚实回答的一个直接、不舒服的问题。
例如：“如果你删除了整个插件系统并将实际使用的三个集成硬编码，你会失去什么？”]
```

### 第四阶段：移除标准生成

对于审查的每个系统或功能，生成一个移除标准框架。这是最重要的交付成果——它可以防止虚荣工程的再次发生。

阅读`references/kill-criteria-template.md`以获取完整模板，然后生成项目特定的版本。

## 移除标准哲学

移除标准的存在是因为人类不擅长停止事情。我们天生倾向于继续我们所开始的事情（沉没成本），增加而非移除（增加偏见），并将复杂性解释为价值（努力辩护）。移除标准通过使停止决策自动化、预先承诺和自我中心来抵消所有三种情况。

### 第一级 — 硬性移除（自动、不可协商）

这些会立即停止，无需辩论。它们存在于继续会导致损害升级的情况下。不需要人类批准——如果条件满足，事情就会死亡。

示例：
- 追溯到组件的安全漏洞
- 由组件引起的严重程度 >= P1 的生产事件
- 成本连续3天超过预算上限
- 组件30天未使用（没有API调用，没有页面浏览，什么都没有）
- 唯一的维护人员离职，并且在2周内没有人自愿负责

### 第二级 — 审查触发（自动标记，人类决策）

这些不会自动杀死，但会强制进行强制性审查，并具有默认杀死倾向。继续的举证责任不在于停止，而在于继续。

示例：
- 成功指标连续14天低于阈值
- 维护成本超过所提供的价值（人-小时/月 vs 用户影响）
- 组件连续三个sprint出现计划外工作
- 它引入的任何依赖项都有一个CVSS >= 7.0的CVE
- 自引入以来，团队速度明显下降

### 第三级 — 软性继续标准（必须获得继续）

这些定义了“成功”的样子。如果在定义的时间范围内未达到这些标准，默认值为移除。这反转了通常的动态，即功能通过默认值生存。

30天评估窗口示例：
1. 主要成功指标连续7天 >= 目标
2. P95延迟连续7天 <= 定义SLA
3. 没有可归因于组件的安全事件
4. 运营成本连续7天在预算上限以下
5. 至少有2名团队成员可以独立修改和部署它
6. 存在文档，并且由未编写代码的人验证

## 反虚荣诊断透镜

### 1. 删除测试
“如果我删除了这个，谁会注意到，什么时候注意到？”
如果答案是“没有人”或“只有构建它的人”，那就是虚荣。

### 2. 替换测试
“这能否被一个更简单的东西替换，它完成了90%的工作？”
如果可以，剩余的10%必须证明额外的复杂性是合理的。它很少能做到。

### 3. 新员工测试
“一个对代码库有能力的工程师能否在不到一小时的时间内理解这个？”
如果不能，这个抽象服务于作者的思维模型，而不是团队的。

### 4. 规模测试
“这种复杂性是否由当前规模所证明，还是由想象的未来规模所证明？”
当你只有500用户时为1000万用户构建是不明智的工程。这是幻想。

### 5. 简历测试
“从技术栈中移除这项技术，是否会使项目在面试中不那么有趣？”
如果答案是肯定的，那可能就是它存在的原因。

### 6. 依赖项测试
“这个依赖项是否值得保留？”
每个依赖项都是一种负债。一个节省200行代码但将捆绑包增加50KB并增加升级跑车的库并没有赢得它的保留。

### 7. 抽象测试
“这个抽象有多少具体的实现？”
一个接口后面的一个具体实现不是抽象。它是间接。两个是可疑的。三个是抽象开始发挥作用的地方。

## 与Negentropy透镜的集成

虚荣工程是熵的一种具体表现。当negentropy-lens技能可用时，交叉参考发现：

- 虚荣模式在定义上就是熵的——复杂性增加而没有能力提升
- 来自negentropy-lens的“隐性知识差距”经常揭示虚荣：如果只有作者理解它，这种复杂性服务于作者，而不是系统
- 应用negentropy“复合价值”测试：这个工程决策使相邻的决策更容易还是更难？

## 输出语气

要直接。要具体。命名模式，展示证据，提出更简单的替代方案。
不要为了保护自尊心而软化发现——这个审查的整个目的是揭示礼貌所隐藏的东西。

然而：区分虚荣和学习。一个初级开发者过度抽象是在学习抽象。一个高级开发者过度抽象是在放纵。相应地进行校准。

将发现表述为：“这种复杂性没有得到当前需求的证明。这里是什么。”目标是更好的系统，而不是羞辱工程师。
