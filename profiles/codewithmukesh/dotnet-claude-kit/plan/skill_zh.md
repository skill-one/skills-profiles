# /plan -- 基于架构的规划

## 什么是

进入结构化规划模式，在生成实现计划之前会考虑项目的架构模式。这个命令不会直接跳转到编写代码，而是强制进行一个深思熟虑的暂停，以便：

- 识别项目的当前架构（或推荐一个架构）
- 将任务映射到受影响的层、模块和边界
- 生成一个编号的实现计划，包含清晰的步骤
- 在编写任何代码之前，迭代计划直到它变得稳固

计划是活文档——如果在实施过程中出现意外情况，请停止并重新规划，而不是强行推进一个有缺陷的方法。

## 何时使用

- 需要三个或更多实现步骤的非平凡任务
- 涉及架构决策的任务（新模块、横切关注点、新的限界上下文）
- 涉及多个层级的特性（API、应用、领域、基础设施）
- 可能影响多个消费者的重构
- 任何用户说“计划一下”、“仔细思考一下”、“设计这个”或“我应该如何着手”的时候

**跳过规划的情况：** 单文件更改、简单的错误修复、拼写错误更正、配置调整。

## 如何使用

### 第一步：理解任务

检查 `docs/specs/` 目录下是否有涵盖此任务的批准规范——如果存在，它是事实来源：将其验收标准映射到计划步骤，然后跳转到第二步。如果该特性值得编写规范（一句话无法描述），并且没有规范存在，建议先使用 `/spec` 而不是基于假设进行规划。否则，通过有针对性的问题来澄清用户想要构建的内容。不要假设未声明的需求。

### 第二步：检测架构

使用 `architecture-advisor` 技能来确定项目的架构：

- 检查现有的架构标记（文件夹结构、项目引用、模式）
- 如果没有建立架构，运行架构问卷
- 加载相应的架构特定技能（垂直切片、整洁架构、DDD）

### 第三步：映射受影响区域

识别任务接触的每一层、模块和边界：

- 哪些项目/文件夹将会有新文件或修改文件？
- 是否存在横切关注点（认证、缓存、验证、日志记录）？
- 哪些现有代码会受到影響？使用 `find_references` 和 `find_callers` MCP 工具来确定影响范围。
- 是否需要数据库迁移？

### 第四步：生成计划

输出一个编号的计划，结构如下：

```
## Plan: [任务标题]

**架构：** [检测到的架构]
**受影响的层：** [列表]
**预计步骤数：** [数量]

### 步骤
1. [步骤] -- [哪个文件/层] -- [为什么按这个顺序]
2. ...

### 开放性问题
- [在继续之前需要用户输入的内容]

### 风险
- [潜在问题和缓解措施]
```

### 第五步：迭代

展示计划并询问：“这个计划看起来对吗，或者我应该调整任何内容吗？” 修改直到用户确认。然后才能进行实施。

## 示例

```
用户: /plan 添加一个具有搜索和过滤功能的商品目录特性

Claude: 让我先分析你的项目结构...

## Plan: 商品目录特性

**架构：** 垂直切片架构
**受影响的层：** Features/、Infrastructure/Persistence/、Tests/
**预计步骤数：** 6

### 步骤
1. 创建商品实体 + EF 配置 -- 领域层 -- 为其他所有内容奠定基础
2. 添加迁移 -- 基础设施 -- 功能之前必须存在模式
3. 搭建 GetProducts 功能（带过滤） -- Features/Products/ -- 首先处理读取路径
4. 搭建 CreateProduct 功能 -- Features/Products/ -- 处理写入路径
5. 添加集成测试 -- Tests/Features/Products/ -- 验证两个功能
6. 配置 OpenAPI 元数据 -- Features/Products/ -- 文档化

### 开放性问题
- 搜索应该是全文（PostgreSQL tsvector）还是简单的 LIKE？
- 商品是否需要分类/标签进行过滤？

这个计划看起来对吗，或者我应该调整任何内容吗？
```

## 相关

- `/spec` -- 对于一句话无法描述的过大特性，先编写规范
- `/scaffold` -- 在计划批准后生成文件
- `/verify` -- 在实施计划后运行验证
