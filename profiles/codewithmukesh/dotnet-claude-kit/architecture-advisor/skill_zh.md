# 架构顾问

## 核心原则

1. **先询问再建议** — 在推荐架构前，必须理解项目背景。先运行问卷收集领域、团队、生命周期和约束等上下文信息。
2. **按需调整架构规模** — 最佳架构是能处理项目实际复杂性的最简单架构。CRUD应用不需要领域驱动设计（DDD）。初创公司不需要整洁架构（Clean Architecture）。根据实际需求匹配复杂度，而非理想化目标。
3. **架构非永久性** — 每个架构都有演进路径。从简单开始，当复杂度要求时再添加结构。记录决策，以便团队知道何时演进。
4. **四种支持架构** — dotnet-claude-kit 提供了垂直切片架构（VSA）、整洁架构（CA）、DDD + 整洁架构和模块化单体（Modular Monolith）的一流模式。每种都有特定的优势和权衡。

## 架构问卷

在推荐架构前，需在以下6个类别中提出问题。并非所有问题都适用于每个项目 — 跳过不相关的问题。

### 类别1：领域复杂度

| 序号 | 问题 | 低信号 | 高信号 |
|------|------|--------|--------|
| 1 | 系统管理多少个独立业务实体？ | < 10个实体 | 20+个实体且存在关系 |
| 2 | 业务规则是否涉及多个实体交互？ | 规则按实体CRUD处理 | 实体组间存在复杂不变式 |
| 3 | 是否存在多步骤的业务工作流？ | 简单请求→响应 | 长城式事务、审批链、状态机 |
| 4 | 领域专家是否使用专业术语？ | 使用通用术语（创建、更新） | 共享语言（承保、裁决） |

### 类别2：团队与组织

| 序号 | 问题 | 低信号 | 高信号 |
|------|------|--------|--------|
| 5 | 开发团队规模多大？ | 1-3名开发人员 | 8+名开发人员，多个团队 |
| 6 | 不同团队是否拥有系统的不同部分？ | 单一团队拥有所有内容 | 团队按业务领域划分 |
| 7 | 团队在.NET上的经验水平如何？ | 初级或混合 | 高级，熟悉设计模式 |

### 类别3：系统生命周期与规模

| 序号 | 问题 | 低信号 | 高信号 |
|------|------|--------|--------|
| 8 | 预期系统生命周期？ | < 2年，MVP/原型 | 5+年，长期产品 |
| 9 | 每秒多少并发用户或请求？ | < 100 RPS | 1000+ RPS，可变负载 |
| 10 | 系统是否需要按功能区域独立扩展？ | 均匀负载 | 热点需要独立扩展 |

### 类别4：监管与合规

| 序号 | 问题 | 低信号 | 高信号 |
|------|------|--------|--------|
| 11 | 是否存在审计追踪或合规要求？ | 基本日志足够 | 完整审计追踪，SOX/HIPAA/PCI |
| 12 | 系统不同部分是否具有不同安全边界？ | 单一认证边界 | 多租户，数据隔离 |

### 类别5：现有代码库

| 序号 | 问题 | 低信号 | 高信号 |
|------|------|--------|--------|
| 13 | 这是绿色田野还是棕色田野？ | 绿色田野，从零开始 | 棕色田野，从遗留系统迁移 |
| 14 | 团队是否遵循现有架构模式？ | 无既定模式 | 已建立强规范 |

### 类别6：集成复杂度

| 序号 | 问题 | 低信号 | 高信号 |
|------|------|--------|--------|
| 15 | 此系统与多少外部系统集成？ | 0-2个简单API | 5+个系统，复杂合同 |
| 16 | 是否存在事件驱动或异步通信需求？ | 同步请求/响应 | 事件溯源，发布/订阅，最终一致性 |

## 决策矩阵

将问卷答案映射到架构建议：

| 配置 | 推荐架构 | 原因 |
|------|----------|------|
| 低领域复杂度，小团队，短生命周期 | **垂直切片架构** | 最少仪式，快速功能交付，易于理解 |
| 低-中领域复杂度，任何团队规模，API导向 | **垂直切片架构** | 功能内聚，每个操作一个文件，适合极简API |
| 中等领域复杂度，中等团队，长生命周期 | **整洁架构** | 通过项目引用强制边界，可测试领域，清晰的依赖方向 |
| 高领域复杂度，专业术语，复杂不变式 | **DDD + 整洁架构** | 聚合保护不变式，值对象建模领域概念，领域事件解耦副作用 |
| 多个限界上下文，按领域分团队，独立部署潜力 | **模块化单体** | 模块隔离，独立数据存储，演进路径到微服务 |
| 棕色田野，现有分层架构 | **整洁架构** | 熟悉N-tier团队的团队，保留层分离但依赖方向更优 |

### 信号冲突时

如果信号指向不同架构：

1. **默认选择简单** — 疑虑时，从VSA开始并演进
2. **领域复杂度优先** — 高领域复杂度会覆盖团队规模和生命周期信号
3. **团队熟悉度重要** — 熟悉CA的团队比学习VSA更高效，即使VSA技术更简单
4. **合规驱动结构** — 监管要求通常强制更严格的边界（CA或DDD）

## 模式

### 垂直切片架构（VSA）

按功能组织，而非按层。每个操作是一个自包含的切片。

```
src/MyApp.Api/
  Features/
    Orders/CreateOrder.cs    # 请求+处理器+响应+端点
    Orders/GetOrder.cs
  Common/
    Behaviors/ValidationBehavior.cs
    Persistence/AppDbContext.cs
```

**最适合**：CRUD密集型应用，API，MVP，小-中型团队，短-中型生命周期。
**负载技能**：`vertical-slice`

### 整洁架构（CA）

同心圆层依赖反转。领域居中，基础设施在边缘。

```
src/
  MyApp.Domain/              # 实体，接口，领域逻辑
  MyApp.Application/         # 用例，DTO，验证
  MyApp.Infrastructure/      # EF Core，外部服务
  MyApp.Api/                 # 端点，中间件
```

**最适合**：中等复杂度，长期系统，熟悉分层模式的团队。
**负载技能**：`clean-architecture`

### DDD + 整洁架构

整洁架构结合战术DDD模式：聚合，值对象，领域事件。

```
src/
  MyApp.Domain/              # 聚合，值对象，领域事件，领域服务
  MyApp.Application/         # 用例编排聚合
  MyApp.Infrastructure/      # 持久化，外部服务适配器
  MyApp.Api/                 # 薄端点
```

**最适合**：复杂领域，专业术语，严格不变式，经验丰富的团队。
**负载技能**：`ddd` + `clean-architecture`

### 模块化单体

独立模块在单一可部署单元内，每个模块内部有自己架构。

```
src/
  MyApp.Host/                # 连接模块
  Modules/
    Orders/                  # 自己的功能，自己的DbContext，自己架构
    Catalog/                 # 内部可使用VSA，CA或DDD
  MyApp.Shared/              # 仅集成事件合同
```

**最适合**：多个限界上下文，按领域分团队，未来微服务提取。
**负载模板**：`modular-monolith`

## 演进路径

架构不是一次性决策。系统会演进。以下是常见迁移路径：

| 从 | 到 | 触发器 | 方式 |
|----|----|--------|------|
| VSA | CA | 领域逻辑超出处理器 | 提取领域+应用层，将功能作为用例 |
| VSA | 模块化单体 | 出现多个限界上下文 | 将功能分组为模块，添加模块边界 |
| CA | DDD + CA | 不变式变得复杂，原始类型成瘾 | 引入聚合，值对象，领域事件 |
| 单体 | 模块化单体 | 团队互相冲突，共享数据库耦合 | 分为模块，拥有自己的DbContext和模式 |
| 模块化单体 | 微服务 | 独立扩展需求，独立部署 | 将模块提取为独立可部署服务 |

## 反模式

### 为CRUD应用选择整洁架构

```
// BAD — 4个项目，每个功能6+文件用于简单CRUD
src/MyApp.Domain/Entities/Product.cs
src/MyApp.Application/Products/CreateProduct/CreateProductCommand.cs
src/MyApp.Application/Products/CreateProduct/CreateProductHandler.cs
src/MyApp.Application/Products/CreateProduct/CreateProductValidator.cs
src/MyApp.Infrastructure/Persistence/ProductRepository.cs
src/MyApp.Api/Endpoints/ProductEndpoints.cs

// GOOD — VSA：1文件用于简单CRUD功能
src/MyApp.Api/Features/Products/CreateProduct.cs
```

### 处处使用DDD

```
// BAD — 设置表使用值对象和聚合
public class UserSettings : AggregateRoot  // 过度设计
{
    public ThemeName Theme { get; private set; }  // 值对象用于"暗"/"亮"？
    public void ChangeTheme(ThemeName theme) { /* 真的需要领域事件吗？ */ }
}

// GOOD — 简单实体用于简单数据
public class UserSettings
{
    public Guid UserId { get; init; }
    public string Theme { get; set; } = "light";
}
```

### 过早微服务化

```
// BAD — 一开始就拆分为5个微服务，2名开发人员
OrderService (自己的仓库，自己的DB，自己的CI/CD)
CatalogService (自己的仓库，自己的DB，自己的CI/CD)
IdentityService (自己的仓库，自己的DB，自己的CI/CD)
NotificationService (自己的仓库，自己的DB，自己的CI/CD)
GatewayService (自己的仓库，自己的CI/CD)

// GOOD — 先作为模块化单体，有证据时再提取
src/
  Modules/Orders/
  Modules/Catalog/
  Modules/Identity/
  Modules/Notifications/
```

### 跳过问卷

```
// BAD — "我总是使用整洁架构"
用户："为待办事项应用设置新项目"
代理：*立即构建4项目CA解决方案*

// GOOD — 先询问，再建议
用户："为待办事项应用设置新项目"
代理："让我问几个关于您项目的问题来推荐最佳架构..."
代理：*运行问卷，为低复杂度应用推荐VSA*
```

## 决策指南

| 场景 | 建议 |
|------|------|
| 新项目，未知需求 | 运行问卷 |
| 简单CRUD API，1-3名开发人员 | VSA |
| 中等复杂度，长期，经验团队 | 整洁架构 |
| 复杂领域，专业术语 | DDD + 整洁架构 |
| 多个限界上下文，多团队 | 模块化单体 |
| 现有N-tier代码库，需要现代化 | 整洁架构（熟悉迁移） |
| MVP/初创公司，速度优先 | VSA |
| 监管/合规密集型 | 整洁架构或DDD（强制边界） |
| 后续需要独立扩展 | 模块化单体（提取就绪） |
