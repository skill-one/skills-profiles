# /de-sloppify — 7步清理流程

## 什么是

对一个.NET代码库运行有序的、经过验证的清理流程。顺序很重要：
首先进行格式化（它会影响每个文件——在处理其他任何事情之前先清除变动），最后移除死代码（早期的步骤会暴露它们）。随机的清理会遗漏问题并创建合并冲突；这个流程不会。

三条规则使其安全：

1. **每步后验证** — 步骤之间运行 `dotnet build` + `dotnet test`。一个导致问题的清理比它试图修复的混乱更糟。
2. **每步提交** — 每个步骤都是自己的提交，所以一个出错的第4步可以回滚，而不会丢失第1-3步。
3. **仅安全移除** — 在删除“死”代码之前，检查反射、依赖注入约定和序列化使用（Roslyn无法看到这些）。

每步命令、安全检查清单和代码示例位于 `references/cleanup-steps.md` 中——执行前请阅读它。

## 何时使用

- “清理”、“整理”、“去粗糙化”、“维护”、“技术债务”
- 大型功能合并或依赖升级后（新警告累积）
- 发布前强化，或定期的季度清理冲刺
- 性能工作前（移除死代码，将类密封以进行非虚拟化）
- 永不与功能工作混合——清理提交保持纯净

## 如何使用

### 第0步：选择步骤

| 场景 | 运行的步骤 |
|------|-------------|
| 全清理/发布前/季度 | 所有7步 |
| PR前快速整理 | 1, 2, 6 |
| 大型功能合并后 | 1, 2, 3, 4 |
| 依赖升级后 | 2, 3 |
| 性能工作前 | 4, 6 |
| CI警告阈值超过 | 仅3步 |
| 技术债务冲刺 | 4, 5 |

### 第1-7步（按顺序执行，详情见 `references/cleanup-steps.md`）

| # | 步骤 | 工具 | 提交信息 |
|---|------|------|----------------|
| 1 | 格式化所有代码 | `dotnet format` | `chore: 应用 dotnet format` |
| 2 | 移除未使用的using语句 | `dotnet format analyzers --diagnostics IDE0005` | `chore: 移除未使用的 using 语句` |
| 3 | 修复分析器警告 | MCP `get_diagnostics` → 按类别分诊 | `chore: 修复分析器警告` |
| 4 | 移除死代码 | MCP `find_dead_code` + **安全检查**（反射/依赖注入/序列化grep） | `chore: 移除死代码` |
| 5 | 解决 TODO | grep TODO/HACK/FIXME → 修复、创建问题或删除 | `chore: 解决 TODO 注释` |
| 6 | 封装非继承类 | MCP `get_type_hierarchy` 每个候选 + 测试项目grep | `chore: 封装非继承类` |
| 7 | 传播 CancellationToken | MCP `detect_antipatterns` → 追踪异步链 | `chore: 在异步链中传播 CancellationToken` |

每步后：`dotnet build` + `dotnet test`，然后提交。如果某步破坏了构建或测试，在继续前修复或回滚该步——永远不要将红色状态带入下一步。将结构化步骤（4, 6, 7）委托给 `refactor-cleaner` 代理。
