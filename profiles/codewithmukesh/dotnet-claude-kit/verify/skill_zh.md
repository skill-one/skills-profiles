# /verify -- 7阶段验证流程

## 什么是

运行一个顺序执行的7阶段验证流程，在各个层级捕获问题——从编译错误到微妙的反模式到格式漂移。每个阶段都会产生明确的PASS、WARN或FAIL，并附带详细信息。"看起来没问题"不是验证结果；状态表才是。关键失败（阶段1构建、阶段4测试）会中断流程，因为后续阶段无法在损坏的代码上产生有意义的结果。

该流程回答一个问题：**"这段代码是否准备好进行评审？"**

| 阶段 | 工具 | 捕获内容 | 关键性 |
|------|------|----------|--------|
| 1. 构建 | `dotnet build` | 编译错误、缺失引用 | 是 |
| 2. 诊断 | `get_diagnostics` (MCP) | 新的分析器警告、空值问题 | 新错误会导致FAIL |
| 3. 反模式检测 | `detect_antipatterns` (MCP) | async void、同步覆盖异步、`DateTime.Now`等 | 否 |
| 4. 测试 | `dotnet test` | 失败的测试、回归 | 是 |
| 5. 安全性 | `dotnet list package --vulnerable` + 扫描 | 密码、SQL注入、缺失认证、易受攻击的包 | 严重/高等级会导致FAIL |
| 6. 格式化 | `dotnet format --verify-no-changes` | 风格漂移、格式不一致 | 否 |
| 7. 差异评审 | `git diff` 分析 | 意外变更、调试残留、TODO | 否 |

## 何时使用

- 完成一个功能、修复bug或重大重构后
- 创建pull request前——非协商，必须执行完整流程
- 合并上游变更或更新依赖后
- 用户说"验证"、"检查所有内容"、"是否准备好"、"运行所有检查"
- 标记任务完成前的最后一步

### 运行哪些阶段

完整流程是默认选项。对于范围受限的变更，可以运行子集：

| 场景 | 阶段 | 备注 |
|------|------|------|
| 功能完成/预PR/新端点 | 所有7个 | 不能简化 |
| 修复bug | 1、2、4 | 如果没有测试覆盖，先添加测试 |
| 重构后 | 1、2、3、4 | 侧重正确性；如果安全敏感，可添加5-7 |
| 更新依赖 | 1、4、5 | 构建、测试、漏洞扫描 |
| 配置或仅测试变更 | 1、4 | 构建和测试 |
| 仅格式化 | 6 | 格式检查足够 |

不确定时，运行所有7个阶段。额外阶段耗时几分钟；遗漏的安全问题可能需要数天响应时间。永远不要选择性地运行阶段，因为变更"看起来安全"。

## 如何操作

### 阶段1：构建（关键——会中断流程）

```bash
dotnet build --no-restore --verbosity quiet
```

- 如果构建失败，停止。报告错误并在继续前修复——在无法编译的代码上，下游没有任何意义。
- 即使通过，也要捕获警告计数；新警告将在阶段2跟踪。
- 输出：PASS（0个错误）或FAIL（附带错误列表）

### 阶段2：诊断

使用Roslyn MCP的`get_diagnostics`工具，范围限定为变更的文件/项目（跨切面变更使用完整解决方案）。与基线比较——仅标记当前变更引入的新警告。常见发现：CS8600/CS8602（空值）、CS0219（未使用的变量）。

输出：PASS（0个新警告）/ WARN（新警告）/ FAIL（新错误）。将新警告视为工作——今天的CS8600是下个月的NullReferenceException。

### 阶段3：反模式检测

使用Roslyn MCP的`detect_antipatterns`工具对变更文件进行分析（广泛变更使用完整项目）。捕获：`async void`、同步覆盖异步（`.Result`、`.GetAwaiter().GetResult()`）、`new HttpClient()`、`DateTime.Now`/`UtcNow`替代`TimeProvider`、宽泛的`catch (Exception)`、日志中的字符串插值、缺失`CancellationToken`、EF读取查询未使用`AsNoTracking`。

输出：PASS（0个发现）/ WARN（发现）/ FAIL（关键反模式）

### 阶段4：测试（关键——会中断流程）

```bash
dotnet test --no-build --verbosity quiet
```

- 完整套件，或针对大型解决方案的受影响测试项目。
- 任何失败的测试都是FAIL——没有例外。在后续阶段前停止并修复。
- 如果没有测试项目：跳过，并建议添加测试。

输出：PASS（全部绿色）或FAIL（失败的测试名称+错误消息）

### 阶段5：安全扫描

```bash
dotnet list package --vulnerable --include-transitive
```

然后检查变更文件：硬编码的密码/连接字符串/API密钥、SQL注入（未参数化的原始SQL）、需要认证的端点缺失`[Authorize]`、宽松的CORS、缺失输入验证、禁用HTTPS或证书验证。

输出：PASS / WARN（中/低等级发现）/ FAIL（严重/高等级漏洞）

### 阶段6：格式检查

```bash
dotnet format --verify-no-changes --verbosity quiet
```

报告漂移但不自动修复。要解决，运行`dotnet format`并将变更包含在提交中。如果不存在`.editorconfig`，记为建议。

输出：PASS / WARN（附带文件列表）

### 阶段7：差异评审

分析`git diff --stat`和`git diff`（已暂存+未暂存）：
- 意外或无关的文件变更（`.vs/`、`bin/`、`obj/`、`.env`、密码）
- 调试残留（`Console.WriteLine`、生产路径中的`#if DEBUG`）
- 未解决的TODO/HACK/FIXME标记
- 范围不匹配——变更必须与任务/PR描述一致

输出：PASS（干净，符合意图）/ WARN（附带发现）

### 修复重试循环

单次通过很少能全部变绿。循环才是关键：

1. **识别**——哪个阶段失败，具体错误是什么
2. **修复**——做出最小化变更以解决它
3. **重跑**——如果修复改变了代码，从阶段1开始；否则从失败的阶段开始
4. **重复**——直到所有阶段通过，或问题需要用户输入

### 最终总结

```
## 验证结果

| 阶段 | 结果 | 详情 |
|------|------|------|
| 1. 构建 | PASS | 0个错误，0个警告 |
| 2. 诊断 | PASS | 0个新诊断 |
| 3. 反模式检测 | WARN | 1个缺失的CancellationToken |
| 4. 测试 | PASS | 47个通过，0个失败 |
| 5. 安全性 | PASS | 无发现 |
| 6. 格式化 | PASS | 干净 |
| 7. 差异评审 | WARN | 发现1个TODO标记 |

**结论：准备好评审**（2个非阻塞警告）
```

结论：**准备好评审**（全部PASS，或仅非阻塞WARN）或**需要修复**（任何FAIL，附带具体修复步骤）。对于预PR运行，将验证报告包含在PR描述中。

## 示例

```
用户: /verify

Claude: 运行7阶段验证流程...

阶段1：构建 ............ PASS (0个错误)
阶段2：诊断 .............. PASS (0个新警告)
阶段3：反模式检测 ..... WARN
  - src/Features/Orders/CreateOrder.cs:42 -- DateTime.Now使用，使用TimeProvider
阶段4：测试 ............ PASS (23个通过，0个失败，0个跳过)
阶段5：安全 ............. PASS
阶段6：格式 ............. PASS
阶段7：差异评审 ........ PASS

结论：准备好评审（1个非阻塞警告）

建议：在合并前将DateTime.Now替换为TimeProvider（第42行）。不阻塞，但CI中的反模式检查会失败。
```
