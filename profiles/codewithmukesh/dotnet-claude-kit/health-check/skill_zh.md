# /health-check — 8维度项目评估

## 什么是

运行一个基于数据的8维度健康评估，每个维度都使用A-F等级进行评分，并提供产生该等级的具体数据点，并将它们汇总成GPA。直觉不是评分依据：每个维度都使用MCP工具或CLI命令，并且每个低于A的等级都会附带具体、优先级高、预估所需努力程度的修复方案——“为OrderService、PaymentProcessor、ShippingCalculator添加测试类”是可操作的；而“提高测试覆盖率”则不是。

这项技能拥有该套件的**标准评分系统**。完整的评分标准、GPA等级标准和报告模板位于`references/grading-rubric.md`中——在运行评估时加载该文件。

语气是诊断性的，而非惩罚性的：C级是一个改进路径，而不是失败。

## 何时使用

- 新手或新项目入职——设定基准
- “这个项目健康状况如何？”，“给这个项目打分”，“代码库审查”，“成绩单”
- 发布前的质量门禁，或每月/每季度的维护审查
- 清理冲刺（`/de-sloppify`）之后——重新评分以展示进展
- 技术债务优先级排序——最低等级将获得下一个冲刺周期的关注

## 如何使用

### 第1步：选择范围

| 场景 | 维度 |
|------|------|
| 全面评估（入职、发布前、每月审查） | 所有8个 |
| 快速健康检查（冲刺中途检查点、演示前、合并后） | 仅1-4个 |
| 大型重构后 | 1（构建）、3（架构）、4（测试） |
| 依赖更新后 | 1（构建）、7（安全） |
| 清理冲刺后 | 仅重新评估已清理的维度 |

### 第2步：运行维度

阅读`references/grading-rubric.md`了解评分阈值，然后按维度收集数据。对于深度代码质量维度，将任务委托给`code-reviewer`代理并使用`code-review`技能。

| # | 维度 | 数据来源 |
|---|------|--------|
| 1 | 构建健康 | `dotnet build --no-restore` — 错误+警告 |
| 2 | 代码质量 | MCP `detect_antipatterns` — 仅读取`summary`，仅评分高置信度结果 |
| 3 | 架构 | MCP `get_project_graph` + `detect_circular_dependencies`（项目+类型） |
| 4 | 测试覆盖率 | MCP `get_test_coverage_map` — **首先检查`applicable`**（结构性，非行覆盖率） |
| 5 | 代码冗余 | MCP `find_dead_code(scope: "solution")` — 评分高置信度；忽略`conventionFiltered` |
| 6 | API表面 | MCP `get_public_api` + `find_references` — 过度暴露、返回类型一致性 |
| 7 | 安全态势 | `dotnet list package --vulnerable --include-transitive` + 密钥/认证快速检查（深度分析：`/security-scan`） |
| 8 | 文档 | 公共API的XML文档覆盖率+README时效性 |

### 第2.5步：分诊门禁（在分配任何等级之前）

检测器输出是证据，不是等级。在分配任何等级之前，首先通过这个门禁——这是防止杂乱计数变成错误字母的关键。

1. **读取`summary`，而不是违规列表。** `summary.byId`即使列表被截断也是完整的。永远不要对截断的列表进行抽样和外推。
2. **忽略`suppressed`。** 在报告中记录计数和`summary.suppressionConfig`，以便抑制措施保持可见。
3. **搁置`medium`。** 这些是审查项，不是评分输入。按类别总结它们；不要修复或计数它们。
4. **仅评分`high`。** 无论上下文如何，这些都是错误的。
5. **检查不变量。** 如果一个信号与目标存储库的CLAUDE.md文档中记录的故意行为相矛盾，则不变量优先——在评分前进行验证。
6. **先读取再断言。** 不要描述你未打开的发现。如果你无法打开所有发现，请报告你检查的那些，并说明情况。

根据`references/grading-rubric.md`中的分诊表进行填写。如果表格无法填写，则该维度尚未准备好评分。

### 第3步：评分和汇总

精确应用评分标准阈值——永远不要按曲线评分（“对于一个这个规模的项目相当不错”是标准如何侵蚀的方式；15个警告是一个C级，无论项目规模如何）。转换为GPA（A=4.0 … F=0.0），仅平均实际评分的维度——标记为“未评估”的维度将排除在GPA之外，永远不会被评分为一个F。

### 第4步：报告

使用`references/grading-rubric.md`中的模板生成报告卡：包含关键发现的评分表、总体GPA和优先级建议——每个建议都有命名类型/文件、优先级顺序和预估所需努力程度。如果存在之前的报告，则附加趋势比较表。

## 示例

```
用户: /health-check

Claude: 运行全面8维度评估...

| 维度 | 等级 | 关键发现 |
|------|------|--------|
| 构建健康 | A | 0个错误，2个警告 |
| 代码质量 | B | 4.2K行中有3个高置信度发现；31个未分诊的中置信度 |
| 架构 | A | 清晰方向，0个循环 |
| 测试覆盖率 | 未评估 | 驱动型套件——结构性指标无效 |
| 代码冗余 | B | 5个未使用的函数（79个按约定发现，不计入） |
| API表面 | B | 2个过度暴露的服务类型 |
| 安全 | A | 0个有漏洞的包 |
| 文档 | D | 30个公共API中有12个未文档化 |

总体GPA: 3.1（B）——基于7个实际评分的维度计算。

分诊: 44个AP005原始 → 所有日志和重新抛出包装器（中置信度）；2个AP004真实。

优先级: (1) `SystemSeeder` → `TimeProvider`，约15分钟； (2) 8个端点类的XML文档，约1天； (3) 审查44个catch块或按路径抑制。
```

## 相关

- `references/grading-rubric.md` — 标准评分标准、GPA等级、报告模板
- `/de-sloppify` — 健康检查暴露问题的清理流程
- `/security-scan` — 6层深度扫描（对应第7维度）
- `/code-review` — 按变更审查（此技能对整个项目进行评分）
- `/verify` — 变更集的通过/失败流程，而非评分评估
