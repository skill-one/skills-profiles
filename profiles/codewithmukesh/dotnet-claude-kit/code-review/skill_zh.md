# /code-review — MCP驱动的代码审查

## 什么是

执行多维度的代码审查，结合Roslyn MCP分析与结构化人工审查。遵循80/20原则：导致80%问题的20%代码（数据访问、安全、并发、集成边界）将得到彻底审查；风格和格式则留给工具处理。

审查维度：**正确性**（逻辑、边界情况、空值处理、异步陷阱）、**安全**（认证漏洞、注入、密钥、CORS）、**性能**（N+1、内存分配、缺少取消操作）、**架构合规性**（层违规、边界突破）、**测试覆盖率**（变更类型的行為测试）。

## 何时使用

- "审查这个"、"代码审查"、"PR审查"，在合并拉取请求之前
- 在重大重构后验证没有回归或设计漂移
- "我应该审查什么？"——决定在大型变更中审查工作的去向
- 在不熟悉的代码上入职并希望进行质量评估

## 如何使用

### 第1步：范围和评分冲击范围

识别变更文件（`git diff main...HEAD`、指定文件或模块）。为每个变更评分以确定审查深度——冲击范围决定深度，而非行数。一行中间件变更优先于300行重命名。

| 冲击范围 | 示例 | 深度 |
|---|---|---|
| 关键 | 中间件、认证、数据库迁移、共享内核、CI/CD | 彻底——每条代码路径 |
| 高 | 公共API变更、消息消费者、EF配置、新模块 | 聚焦——消费者+行為 |
| 中 | 遵循现有模式的 新功能、修复、新端点 | 标准——清单检查 |
| 低 | 文档、格式化、重命名、日志语句 | 略过——构建+测试通过 |

### 第2步：MCP分析（在阅读任何文件之前）

```
detect_antipatterns(projectFilter: "affected-project")   → async void, DateTime.Now, new HttpClient(), 广泛的catch
get_diagnostics(scope: "project", path: "affected-project") → 新警告、空值问题
```

区分新引入的问题与已存在的问题——关注新问题。

### 第3步：冲击范围验证

对每个修改的公共API：

```
find_references(symbolName: "ModifiedType")              → 消费者数量；高数量=高风险
get_dependency_graph(symbolName: "ModifiedMethod", depth: 2) → 滋生效应
```

检查调用者是否处理了变更的返回类型和新错误情况。

### 第4步：架构合规性

通过`get_project_graph`和`detect_circular_dependencies`验证依赖方向（领域→无；基础设施→应用→领域）。按架构：VSA功能不交叉引用；Clean Architecture领域无项目引用；模块化单体模块仅通过集成事件通信——模块的DbContext的`find_references`应仅在该模块内解析。

### 第5步：人工审查——优先级顺序

审查工具无法捕获的内容，优先处理高风险区域：

| 优先级 | 区域 | 检查 |
|---|---|---|
| 1 | 数据访问 | N+1（缺少Include/投影）、带用户输入的原始SQL、缺少CancellationToken |
| 2 | 安全 | 每个端点都有明确的`[Authorize]`/`[AllowAnonymous]`、输入验证、代码中无密钥、日志中无PII |
| 3 | 并发 | 端到端传递令牌、无`.Result`/`.Wait()`、线程安全的共享状态 |
| 4 | 集成 | 外部调用重试/超时、消费者幂等性、无被吞没的异常 |
| 5 | 正确性 | 业务逻辑、边界情况（空/空值/并发）、边界处实体映射到DTO |
| 6 | 测试 | 行為测试（非实现）；覆盖快乐路径+主要错误情况 |
| — | 风格/命名 | 仅在以上完成后提及；格式化器和分析器负责此部分 |

### 第6步：生成审查报告

每个发现都说明问题所在、为何重要以及如何修复。永远不要将安全漏洞隐藏在命名细节之下。

```markdown
## 代码审查：[范围]

### 摘要
[1-3句话：范围、风险等级、建议]

### 关键（必须合并前修复）
- **[标题]** — [文件:行] [问题所在。为何重要。如何修复。]

### 警告（应修复，产生技术债务）
- **[标题]** — [文件:行] [...]

### 建议（锦上添花）
- **[标题]** — [文件:行] [...]

### 架构合规性
[PASS/WARN与边界违规说明]

### 测试覆盖率
哪些变更类型有测试；需添加的具体场景]

### 值得称赞
- [始终包含——强化良好模式]
```

**快速审查**（1-2个文件，低冲击范围）：运行`detect_antipatterns` + `get_diagnostics`，检查正确性，输出摘要+问题+值得称赞。

## 示例

```
用户：/code-review 这个PR的变更

Claude：3个项目中有7个变更文件。CreateOrder触及数据访问和公共端点——高冲击范围。运行MCP分析...

## 代码审查：订单处理功能

### 摘要
添加CreateOrder/GetOrder端点，使用EF Core持久化。结构良好的VSA功能。合并前需关注两个问题。

### 关键（必须合并前修复）
- **缺少CancellationToken传播** — CreateOrder.cs:38
  调用SaveChangesAsync时未传递令牌。客户端断开连接仍消耗服务器资源。从处理器参数传递`ct`。

### 警告（应修复，产生技术债务）
- **GetOrder中的N+1查询** — GetOrder.cs:25
  加载Order时未使用`.Include(o => o.Items)`；序列化期间每个项目进行一次懒加载。使用急加载或投影。

### 建议（锦上添花）
- **密封处理器** — CreateOrderHandler.cs:10
  未设计为可继承；`sealed`启用虚函数消除。

### 架构合规性
PASS — 所有变更在Features/Orders/内，无层违规。

### 测试覆盖率
覆盖了快乐路径。添加验证失败和未找到的测试。

### 值得称赞
- 清晰的命令/查询分离；FluentValidation覆盖边界情况
- 响应DTO是记录，无实体泄漏
```
