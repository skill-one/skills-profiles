# /build-fix

## 什么是

工具包的自动迭代循环功能。它通过循环运行、解析失败、按根本原因分类、应用针对性修复、重新运行，将损坏的 `dotnet build`（或失败的 `dotnet test`）驱动变为绿色。它重复执行直到变绿或触发保护机制——这与经验丰富的开发者逐层解决红色错误墙的方式相同，但具有硬性限制以防止反复无效操作。

这不是单次修复。它处理级联错误，即修复一个问题会暴露下一个问题。

## 何时使用

- 构建损坏且存在多个编译器错误
- 代码变更或构建修复后测试失败
- 进行重大重构后，涉及类型名称、命名空间或签名
- 更新 NuGet 包后（尤其是主要版本升级）
- 合并存在冲突但未编译的分支后
- 执行脚手架或代码生成后需要手动调整
- 用户说：“修复构建”、“让它编译”、“让测试通过”、“继续直到它工作”、“继续修复”

## 如何使用

### 循环规范（适用于每个循环）

1. **有界迭代，始终** — 默认最大5次迭代，硬性上限10次（用户“继续”可扩展3次，不超过10次）。如果5次迭代无法解决，问题需要人工判断，而不是第6次相同的尝试。
2. **进度或退出** — 每次迭代必须减少错误/失败计数。修复尝试后出现相同错误 = 卡住：停止、报告并重新规划不同方法。绝不重试已失败的相同修复。
3. **修复前分类** — 按根本原因分组错误，优先修复最高杠杆点（一个缺失的 `using` 可能消除下游十几个错误）。
4. **每次迭代透明度** — 报告变更原因：
   `迭代 3/5：通过添加 using System.Text.Json 修复 CS0246，剩余 2 个`。绝不无声修改文件。
5. **原子性** — 每次迭代后代码库状态不恶化。如果迭代3失败，代码保持迭代2的状态。

### 主要流程：构建修复循环（最大5次迭代）

1. **构建** — 运行 `dotnet build`，捕获完整错误输出
2. **解析** — 提取每个 `error CS####` 及文件、行、消息
3. **分类** — 按根本原因分组：

   | 分类 | 代码 | 修复策略 |
   |---|---|---|
   | 缺失 using/引用 | CS0246, CS0234 | 添加 using、包或项目引用 |
   | 类型不匹配 | CS0029, CS1503 | 检查预期类型，强制转换或转换 |
   | API变更 | CS0117, CS7036 | 检查新签名，更新调用点 |
   | 可空性 | CS8600–CS8604 | 添加空检查、`?.` 或 `??` |
   | 模糊/重复 | CS0104, CS0121, CS0111 | 限定命名空间，删除重复 |
   | 缺失成员 | CS1061 | 检查拼写，验证成员存在 |
   | 缺失实现 | CS0535 | 实现接口/抽象成员 |
   | 过时API | CS0618 | 替换为推荐替代方案 |

4. **修复** — 应用针对性修复，优先处理根本原因/最高杠杆点错误
5. **重新构建** — 再次运行 `dotnet build`，比较错误计数
6. **评估** — 零错误：运行 `dotnet test` 作为合理性检查，报告成功。错误减少：继续。相同错误：卡住——退出并重新规划。错误增加：回滚迭代，报告回归。

### 变体：测试修复循环（最大5次；若跟在构建修复后则最大3次）

相同循环，相同保护机制，但使用 `dotnet test --no-build` 作为执行者，并增加一个关键步骤——**修复前诊断**：

1. 阅读测试——理解断言和设置
2. 阅读生产代码——理解实际行为
3. 判断错误位置：错误预期 → 修复测试；生产错误 → 修复代码；设置不完整 → 修复设置；契约变更 → 更新测试以匹配
4. **绝不削弱断言以使测试通过。**
   BAD: `Assert.Equal(expected, actual)` → `Assert.NotNull(actual)`。
   GOOD: 修复生产代码使原始断言通过。

### 安全保护机制（立即退出）

- **卡住** — 修复后出现相同错误/失败，或计数振荡（3 → 2 → 3）：报告无法修复的内容和人工应检查的内容
- **回归** — 迭代引入的错误多于修复的错误：回滚其变更，报告
- **级联失败** — 修复一个错误连续两次产生3个以上新错误：方法错误，停止
- **关键错误** — 错误SDK、缺失项目文件、损坏的解决方案或测试运行器本身失败：需要人工干预，停止
- **用户中断** — 完成当前迭代，报告进度，询问如何继续

### 其他循环

相同的规范——有界迭代、进度检测、安全保护机制——管理重构传递（`/de-sloppify`：每次目标后验证构建+测试，失败则回滚）和脚手架（`/scaffold`：生成后运行嵌套的构建修复和测试修复循环）。嵌套循环获得较小预算（父级5 → 嵌套3），最大嵌套深度2，总预算15。

### 使用的MCP工具

- `get_diagnostics` — 编译器错误/警告限定在文件或项目范围内
- `find_symbol` — 定位移动或重命名的类型
- `find_references` — 评估损坏的API变更影响范围
- `get_project_graph` — 修复引用错误的依赖顺序

## 示例

```
用户: /build-fix

Claude: 运行 dotnet build...
  在4个文件中发现12个错误。

  迭代 1/5:
  - 6个错误：缺失命名空间 (CS0246) — 添加 using 指令
  - 3个错误：类型不匹配 (CS1503) — 更新方法签名
  - 3个错误：接口未实现 (CS0738) — 包API变更

  重新构建... 剩余 3 个错误。

  迭代 2/5:
  - 3个错误：xunit.v3 升级后的 CS0738
    - IAsyncLifetime.InitializeAsync 现在返回 ValueTask（v2中为 Task），并来自 IAsyncDisposable 的 DisposeAsync
    - 更新 3 个测试用例到 ValueTask 签名

  重新构建... 0 个错误。构建变绿。

  运行 dotnet test... 所有 47 个测试通过。
  添加到 Memory > 包："xunit.v3 IAsyncLifetime 使用 ValueTask 签名"
```
