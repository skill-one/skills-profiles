# /spec — 持续改进的规范工作流

## 什么是

将一个想法转化为开发者与 Claude 明确同意的书面、版本化的规范——在任何规划或编码之前。契约：

- **绝不假设。** 想法中的每一个空白都变成一个问题。如果 Claude 捕捉到自己思考“可能”、“推测”或“通常方式”——这种想法是一个要问的问题，而不是要做的决定。
- **持续改进，但结构化。** 问题以专注的轮次（每次 3-5 个）跨九个维度进行——不是一次压倒性的倾倒，也不是一次礼貌的轮次就提前结束。
- **协议是明确的。** 规范具有状态生命周期：草稿 → 审查中 → 已批准。实施永远不会从草稿开始。批准需要开发者阅读最终文档并确认。
- **规范是文件，不是聊天。** 输出持久化到 `docs/specs/<NNN>-<slug>.md` 并在会话中存活。计划、测试和提交都引用它。

## 何时使用

- 任何一句话无法完全描述的功能
- 新产品或模块的想法（“我想添加团队工作区”）
- 在非平凡功能之前使用 `/plan` —— 计划会消耗已批准的规范
- 在实施过程中需求感觉模糊时：停止，`/spec`，重新规划
- 触发短语：“规范”、“需求”、“PRD”、“定义功能”、“验收标准”

**跳过情况：** 修复错误、重构、单个端点的 CRUD，其中实体很明显。

## 如何使用

### 第一步：捕获和重述

将原始想法用一段话重新表述：Claude 理解的内容，用自己的话。以“这是想法吗？我哪里理解错了？”结尾。在开发者确认重述之前不要开始质疑——质疑错误的想法浪费大家的时间。

### 第二步：提问轮次

按顺序处理九个维度。每一轮：选择 3-5 个最重要的未回答的承重问题（重塑后续问题的答案优先）。在挽具支持可选选项的地方，提供具有权衡的选项——并附带建议——但**开发者选择；建议永远不会默默应用**。

| # | 维度 | 需要明确的内容 |
|---|-------|---------------|
| 1 | 问题与用户 | 今天谁受影响，他们如何绕过它，成功看起来像什么 |
| 2 | 范围 | 这个迭代中包含什么，明确排除什么，MVP 线在哪里 |
| 3 | 领域与数据 | 实体、关系、生命周期（创建→存档→删除？）、保留 |
| 4 | API 协议 | 资源、端点、请求/响应形状、分页、版本控制 |
| 5 | 授权 | 谁能做什么，角色/声明模型、租户边界 |
| 6 | 边缘情况与失败模式 | 并发、重复、幂等性、部分失败、限制 |
| 7 | 非功能性 | 预期量、延迟预算、增长假设 |
| 8 | 集成 | 外部服务、发布事件、webhooks、副作用 |
| 9 | 验收标准 | 范围内每个行为的可测试 Given/When/Then |

**持续改进的提问规则：**

- 立即记录草稿规范中的每个答案——答案不是对话，是需求。
- 当场挑战矛盾：“第一轮你说 X；这个答案意味着非 X。哪个优先？”
- “我不知道”是一个合法答案 → 移动到**延迟决策**，开发者现在选择明确的回退（“默认软删除，直到决定”）。禁止沉默延迟。
- 当后续轮次为该维度产生零个新问题时，该维度完成。
- 提问阶段完成时，所有九个维度都完成。不要因为对话感觉长就停止——提前停止是假设悄悄溜入的方式。

### 第三步：草拟规范文件

从 `docs/specs/` 中现有的文件确定下一个编号（如果缺少目录则创建）。编写 `docs/specs/<NNN>-<slug>.md`：

```markdown
# 规范 NNN: <标题>

**状态：** 草稿
**日期：** <今天>

## 问题            <!-- 谁受影响，为什么现在 -->
## 范围              <!-- ### 包含 / ### 排除 —— 两者都明确 -->
## 领域模型       <!-- 实体、关系、生命周期 -->
## API 协议       <!-- 端点表格：动词、路由、请求、响应、错误 -->
## 授权            <!-- 谁能做什么 -->
## 边缘情况与失败模式
## 非功能性需求
## 集成
## 验收标准  <!-- Given/When/Then，编号 AC-1, AC-2, ... -->
## 延迟决策   <!-- 决策，选择的回退，重新触发器 -->
## 开放问题       <!-- 必须在批准前为空 -->
```

### 第四步：审查循环

将状态设置为 **审查中**。展示完整的规范并询问：“通读这个。哪里有错误、缺失或过度设计？” 将修正纳入并重新展示。重复直到开发者没有进一步更改。新答案可能会引发新问题——这是过程在运作，而不是收敛失败。

### 第五步：协议门

批准是一个故意的行动，绝不从沉默或“看起来不错”中推断。明确询问：“你批准这个规范吗？批准后，代码遵循规范——更改首先通过规范。” 批准后，设置 `**状态：** 已批准（<日期>）。

- **开放问题必须为空。** 如果有任何剩余，规范不能批准——明确解决或延迟每个问题。
- 如果实施后揭示了一个错误的假设：停止，将状态重置为审查中，与开发者一起修复规范，然后继续。代码永远不会默默偏离已批准的规范。

### 第六步：交接

- `/plan` 读取已批准的规范并将验收标准映射到实施步骤
- `/tdd` 将验收标准转化为第一个失败的测试（AC-n → 测试名称）
- 功能的提交引用规范：`feat: 团队工作区（规范 004）`

## 示例

```
用户：/spec 用户应该能够邀请团队成员

Claude：我理解的是：现有用户可以邀请另一个人加入他们的... 工作区？账户？这是我的第一个空白。
这是想法吗？我哪里理解错了？

用户：是的，邀请到他们的组织

Claude：第一轮——范围与用户：
  1. 被邀请人可以是没有任何现有账户的人，还是只有注册用户？
  2. 谁可以邀请——任何成员，还是只有管理员/所有者？
  3. 对待邀请有限制（每个组织、每个计划）？
  4. 范围外检查：批量邀请和 SSO 配置的成员——两者现在都排除？

用户：1：两者。2：管理员。3：无限制。4：正确，两者排除。

Claude：第二轮——边缘情况（你“两者”在问题 1 引发了这些）：
  1. 邀请一个已经有待处理的邀请的电子邮件——错误，还是重新发送？
  2. 邀请过期——7 天，30 天，永不？
  3. 被邀请人已经属于另一个组织——多组织成员还是拒绝？
  ...

[...轮次继续，直到所有九个维度都耗尽...]

Claude：规范写入到 `docs/specs/004-team-invitations.md`（审查中）。
通读它。哪里有错误、缺失或过度设计？

用户：看起来对。批准。

Claude：状态：已批准（2026-06-12）。下一步：/plan 将 AC-1..AC-9
映射到实施步骤。
```

## 相关

- `/plan` — 消耗已批准的规范；没有规范就不规划值得规范的特性
- `/tdd` — 验收标准成为第一个失败的测试
- `/scaffold` — 生成计划调用所需的切片
- `architecture-advisor` — 在第二步期间加载，如果功能强制进行架构决策
