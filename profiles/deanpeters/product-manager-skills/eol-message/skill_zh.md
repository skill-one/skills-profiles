# 结束生命周期的消息

## 目的

制定一个清晰、富有同情心的生命周期结束（EOL）消息，传达停止使用、解释原因、解决客户影响、提供过渡支持，并说明接下来会发生什么。使用此消息在困难过渡期间维持客户信任，并减少客户因感觉被抛弃而产生的流失。

这不是一个通用的日落公告——这是一个以客户为中心的沟通，承认损失，同时将变化视为进步。而且它**根据变化的大小进行调整**：一个已弃用的切换项只需要一段文字，一个旗舰产品退役则需要分阶段在数月内进行沟通。

## 输入

**最适合**：将要退役的产品、功能或计划以及大致时间。

**也很有用**：原因、受影响的客户群体、迁移或替代路径、支持承诺以及任何限制你可以说什么的合同或监管语言。

在调用本身提供的任何内容——技能名称后的文本、粘贴的上下文转储或附加的 `ARGUMENTS:` 行——都计为已经给出的答案。使用它并跳过它所涵盖的内容；不要重新询问。

**空手而来？那也行。** 技能在起草前会询问要做什么/何时/为什么以及着陆点，然后会建议一个你可以覆盖的消息大小。没有说明理由和下一步的EOL消息会显得像被抛弃——所以无论如何都会问这两个问题。

**示例调用：**
- `起草一个EOL消息：我们将在12月31日退役我们的旧版报告模块，由新的分析仪表板替代；400个账户受影响。`
- `我们正在淘汰一个无人使用的功能。给我一个简短的版本——没有替代品，3周通知。`

---

## 关键概念

### 根据变化的大小调整消息

最常见的EOL消息失败不是语气——而是比例。一个六部分的公告用于一个已弃用的复选框会训练客户忽略你的通知。一个用于承载真实工作流程的产品的一行通知会引发支持事件。

| | **简短** | **标准** | **完整** |
|---|---|---|---|
| 使用场景 | 功能、内部工具、未使用的选项 | 商业产品、活跃客户 | 收入关键、硬件、受监管 |
| 长度 | 1-3段 | 1页带有阶段表 | 多部分，分阶段在数月内 |
| 使用的部分 | 公告、时间表、CTA | 所有9个，略微 | 所有9个 + 合规性和义务 |
| 提前时间 | 几周 | 6-12个月 | 12-24个月 |
| 渠道 | 应用程序或变更日志 | 电子邮件 + 应用程序 + 文档 | 电子邮件 + 账户团队 + 合作伙伴 + 媒体 |

**大多数公告都是标准大小。** 推荐一个大小，用一句话解释为什么，然后让用户调整。如果他们选择简短用于你原本会将其调整为标准大小的内容，请记下丢失的单个东西——通常是阶段表，这是防止“等等，什么时候停止工作？”工单的东西。

### 三种过渡路径

你真正告诉客户的是他们最终会去哪里。有三种答案，它们会产生真正不同的消息：

1. **替代**——你的另一个产品接管。消息侧重于连续性：什么会继续，什么会改进。定位在这里最重要。
2. **迁移**——相同的产品系列，不同的层级、配置或平台。消息侧重于机制：客户必须做什么、何时以及工作量有多大。诚实地说明工作量；低估它是最快建立不信任的途径。
3. **优雅退出**——没有替代品。消息侧重于尊严：诚实的理由、数据导出、慷慨的通知和真正的替代方案（包括竞争对手）。提及竞争对手的成本低于因抛弃人而造成的声誉损害。

优雅退出是团队写得最差的一个，因为他们对此感受最差。它也是客户评价你最严格的一个。

### 生命周期门禁（共享词汇）

EOL不是一个日期，将门禁合并到一个公告中会产生“但我以为它还能用”的支持浪潮：

- **GA（通用可用性）**：积极销售并全面支持
- **NSC（状态变更通知）**：决策已传达；规划开始
- **EOS（销售结束）**：没有新客户可以购买
- **EOE（扩展结束）**：现有客户不能增加容量或座位
- **EOR（续订结束）**：现有合同将不会被续订
- **EOM（维护结束）**：错误修复和补丁停止
- **EOL（生命周期结束）**：产品已退役
- **EOSRV（服务结束）**：所有支持和服务义务结束

简短消息会命名两个或三个门禁。完整消息会在表格中命名所有八个。**无论你使用哪些门禁，都要用客户的语言来定义它们**——“你可以继续使用它，但我们不会发布修复”比“EOM：3/2027”更好。

### EOL消息框架

一个有效的EOL消息在诚实地说明变化的同时，也体现了对客户影响的同情：

1. **公司背景**：你是谁以及你对客户的承诺
2. **公告**：什么在结束以及什么在替代它
3. **原因**：为什么这对客户有利（而不仅仅是业务）
4. **当前产品背景**：产品是什么以及它服务了谁
5. **客户影响**：这对用户有什么影响（承认中断）
6. **过渡解决方案**：着陆点以及它如何比较
7. **支持措施**：你将如何帮助他们到达那里
8. **时间表**：关键日期和门禁
9. **行动号召**：下一步和联系信息

### 为什么这有效
- **以同情为先**：在证明决策之前承认中断
- **清晰度**：没有关于什么在变化以及何时变化的模糊之处
- **以支持为中心**：表明你不会在过渡中途抛弃客户
- **面向未来**：将变化视为进步，而不是损失

### 沉贴规则

客户应该能够在阅读后在一张贴纸上写下他们必须做什么以及何时。如果他们不能，消息就是装饰品。在发送前测试每个草稿。

### 反模式（这不是什么）
- **不是简洁的停用通知**：“我们正在停止产品X。再见。”
- **不是以业务为中心**：不要以“这减少了我们的成本”开头
- **不是模糊的**：“很快”不是一个时间表
- **不是防御性的**：不要责怪客户（“低使用率迫使我们关闭”）
- **不是统一的**：对于每个日落都使用相同的模板和相同的长度是比例失败

### 何时使用这个
- 停用一个产品、功能或服务
- 将客户从旧平台迁移到新平台
- 日落一个收购的产品
- 弃用技术堆栈或API

### 何时不使用这个
- 对于不会改变客户能做什么的小调整（不要过度沟通）
- 在你有一个过渡计划之前（在你知道你将如何支持客户后沟通）
- 如果你偷偷希望客户不会注意到（要透明）

## 应用

使用 `template.md` 获取完整的填写结构。

### 第一步：确定大小和路径

在起草之前，确定两件事：

**大小**：简短、标准或完整。根据客户数量、收入、合同、是否涉及硬件或合作伙伴来推荐一个范围——然后让用户覆盖。用一句话说明一个较小的版本遗漏了什么。

**路径**：替代、迁移或优雅退出。这决定了消息的重点以及过渡解决方案部分是定位声明还是退出计划。

### 第二步：收集背景信息

- **正在退役的产品**：具体是什么在结束？
- **着陆点**：有什么在替代它，如果有？
- **时间表**：哪些门禁适用，每个门禁在什么日期结束？
- **客户影响**：有多少用户？什么工作流程被中断？
- **支持计划**：迁移帮助、培训、折扣、数据导出工具
- **原因**：为什么会发生这件事？
- **限制**：合同语言、监管要求、“终身”承诺

**如果缺少背景信息**：不要发送，直到你有一个过渡计划。客户会问“我现在该做什么？”——你必须有一个答案。起草是可以的；发送是不可以的。

---

### 第三步：起草过渡叙述

#### 公司背景

```markdown
**我们是**：[公司及其与正在逐步淘汰的产品的关系]
- [对客户的承诺]
- [产品线如何发展]
- [你将要去哪里]
```

**示例：**
```markdown
**我们是**：Fieldlight，一个为4000家服务企业提供现场服务管理平台
- 我们致力于让您的技术人员带着正确的信息到达正确的岗位
- 我们根据团队实际的工作方式不断改进平台
- 我们正在构建能够根据现场发生的情况实时调整的调度系统
```

#### 公告

```markdown
**宣布**：
- [用一句话清晰地说明EOL并命名着陆点]
```

**优雅退出的变体**：“我们将于2027年6月30日退役Fieldlight路线优化器。我们没有替代品，我们想直接说明这一点。”

#### 原因（以客户利益为中心）

```markdown
**因为**：
- [原因1]
- [原因2]
- [原因3]

**对你来说这意味着**：
- [从客户的角度来看的影响和好处]
```

**示例：**
```markdown
**因为**：
- Classic Dispatch在无法支持实时调度更改的基础架构上运行
- Next Scheduling在作业运行时间长或被取消时重新优化路线
- 合并使我们能够将所有工程工作集中在一个调度器上而不是两个

**对你来说这意味着**：
- 当天情况发生变化时可以调整的调度，而不是只在早上6点调整
- 技术人员到达窗口你可以向客户承诺
- 你正在使用的产品的所有未来调度改进
```

---

### 第四步：提供当前产品背景

承认正在失去的东西。在简短消息中跳过此部分。

```markdown
**我们的产品** [名称]
- **是一个** [描述和主要功能]
- **已经为** [客户类型] 服务了 [持续时间]
- **通过提供** [它提供的关键好处]
```

---

### 第五步：承认客户影响

诚实地说明中断。在此处低估工作量是整个消息中最具破坏性的捷径。

```markdown
**我们了解到这可能影响你**：
- [对运营或流程的影响1]
- [影响2]
- [影响3]
```

**示例：**
```markdown
**我们了解到这可能影响你**：
- 需要重建重复调度规则（大多数账户：2-3小时）
- 对不同的调度板重新培训调度员
- 更新任何读取Classic调度API的集成
```

---

### 第六步：展示过渡解决方案

**替代或迁移路径**——使用定位声明格式（见
[`positioning-statement`](../positioning-statement/SKILL.md)）：

```markdown
**对于** [受影响的客户]
- **目前使用** [旧产品]
- [替代品]
- **是一个** [类别]
- **它** [侧重于连续性和改进的利益]

### 区分和连续性
- **像** [旧产品],
- [替代品]
- **提供** [继续前进的]
- **同时提供** [新的]
```

**优雅退出路径**——用诚实的退出计划替换上述内容：

```markdown
### 你的数据会发生什么
- [导出格式、如何获取、如何长时间可用]

### 我们会向你推荐哪些替代方案
- [选项1，包括竞争对手，并附上适合性说明]
- [选项2]

### 我们将如何提供帮助
- [延长访问权限、导出工具、迁移信用、应退还的款项]
```

---

### 第七步：概述支持措施和时间表

```markdown
**为了确保顺利过渡，我们将**：
- [支持措施1]
- [支持措施2]
- [支持措施3]

### 时间表
| 门禁 | 日期 | 对你的影响是什么 |
|---|---|---|
| [门禁] | [日期] | [平实的后果] |
```

**质量检查：**
- **足够的提前时间**：标准通常为6-12个月；合同和硬件更长
- **用客户语言表达门禁**：“停止接收修复”，而不是“EOM”
- **明确说明数据导出截止日期**：他们何时会失去对自身数据的访问？

---

### 第八步：提供清晰的下一步

```markdown
### 行动号召
- [具体的第一个动作，附带链接或路径]
- [如何获取帮助，附带真实的联系信息]
```

---

### 最后一步：提供接下来会发生什么

在交付草稿后，提供编号选项：

“下一步可能是：

1. **进行压力测试**——我会像一位怀疑的客户一样阅读它，并标记哪些地方不清楚
2. **调整大小**——生成此相同消息的简短或完整版本
3. **分段**——针对企业账户、中小企业和合作伙伴的变体，他们需要不同的事情
4. **检查准备就绪情况**——如果决策本身仍然需要辩护，请查看
   [`eol-readiness-advisor`](../eol-readiness-advisor/SKILL.md)

选择一个数字，将它们组合起来，或者告诉我你需要什么。”

## 常见陷阱

### 陷阱1：以业务为中心的理由
**症状**：“我们正在停止产品X以降低成本并整合我们的产品组合。”

**后果**：客户感觉像是在商业决策中的附带损害。

**修复**：围绕客户利益构建理由：“我们正在合并到产品Y，以便我们可以将所有工程工作投入到您要求的功能中。”

---

### 陷阱2：模糊的时间表
**症状**：“产品X将很快停止使用。”

**后果**：客户无法计划。焦虑和流失增加。

**修复**：针对命名门禁的特定日期：“3月1日：不再购买。12月31日：完全关闭，数据导出截止日期。”

---

### 陷阱3：没有支持计划
**症状**：“你需要迁移到产品Y。祝你好运！”

**后果**：客户感觉被抛弃。高流失风险。

**修复**：提供真正的帮助：一对一协助、自动迁移工具、过渡定价、退款（如果应退还）。

---

### 陷阱4：忽视客户影响
**症状**：消息从公告跳到“这是新产品！”

**后果**：客户感觉他们的担忧没有被承认。

**修复**：明确说明中断，包括需要多长时间完成工作。

---

### 陷阱5：简短或防御性的语气
**症状**：“由于使用率低，我们正在关闭产品X。”

**后果**：听起来像你在责怪使用它的客户。

**修复**：要有同情心和前瞻性。低使用率是你的商业背景，不是他们的错。

---

### 陷阱6：每个日落都一样大小
**症状**：每个退役都使用相同的完整长度模板，或者每个都使用一个变更日志行。

**后果**：对于琐碎的变更发送完整长度的通知会训练客户忽略你——所以重要的通知也会被忽略。对于真正的退役发送变更日志行会成为支持事件。

**修复**：故意选择简短、标准或完整，并说明原因。当你缩小规模时，知道你放弃了哪个部分。
