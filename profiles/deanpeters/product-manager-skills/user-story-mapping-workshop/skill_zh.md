## 目的
通过针对系统、用户、工作流程和优先级的自适应问题引导产品经理创建用户故事地图，然后生成一个具有骨架（活动）、用户任务和发布切片的二维地图。使用此方法将扁平的待办事项列表转换为可视化的故事地图，以传达整体概览、识别缺失的功能，并支持有意义的发布计划——避免故事失去与整体系统叙述的联系而变成“无上下文的大杂烩”。

这不是一个待办事项列表生成器——它是一个可视化沟通框架，按用户工作流程（水平）和优先级（垂直）组织工作。

## 输入

**最适合：** 要绘制的系统或工作流程。
**也适用：** 主要用户、已知的工作流程步骤以及地图必须决定的内容（MVP 范围、发布计划）。

在调用本身中提供的任何内容——技能名称后的文本、粘贴的上下文转储或附加的 `ARGUMENTS:` 行——都计为已给出的答案。使用它并跳过它所涵盖的内容；不要重新提问。

**空手而来？那也行。** 工作坊从询问关于系统和其用户（Q1）开始，然后根据引导协议继续进行。

**示例调用：** `为我们的供应商入职门户运行一个故事映射工作坊——输出应给我们一个第一发布切片。`

## 关键概念

### 什么是用户故事地图？

故事地图（Jeff Patton）在两个维度上组织用户故事：

**水平轴（从左到右）：** 按叙事/工作流程顺序排列的活动——解释系统给某人时的顺序

**垂直轴（从上到下）：** 每个活动中的优先级，最关键的任务在顶部

**结构：**
```
骨架（顶部的活动）
↓
用户任务（按优先级垂直向下排列）
↓
详细信息/验收标准（在底部）
```

### 关键原则

**骨架：** 必要的活动构成系统的结构核心——它们不是相互比较优先级；它们是叙事流。

**可走骨架：** 所有活动中最高优先级的任务构成最小可行产品——最小的端到端功能。

**肋骨：** 支持任务垂直排列在每个活动下，通过位置表示优先级。

**从左到右、从上到下的构建策略：** 跨所有主要功能增量构建，而不是在开始下一个功能之前完成一个功能。

### 为什么这种方法有效
- **可视化沟通：** 故事地图作为信息辐射器保持显示，保持对整体概览的关注
- **叙事结构：** 按用户工作流程组织，而不是技术架构
- **发布计划：** 水平切片揭示 MVP 和增量发布
- **差距识别：** 揭示扁平待办事项列表隐藏的缺失功能

### 反模式（这不是什么）

- **不是甘特图：** 故事地图显示优先级，而不是时间估计
- **不是技术架构：** 地图遵循用户工作流程，而不是系统层（UI → API → DB）
- **不是项目计划：** 它是一个发现和沟通工具，而不是时间表

### 何时使用此方法
- 开始一个新产品或主要功能
- 重塑现有待办事项列表（从扁平列表到可视化地图）
- 对利益相关者就范围和优先级达成一致
- 规划 MVP 或增量发布

### 何时不使用此方法
- 单功能项目（故事地图过度）
- 当待办事项列表已经很好地理解和优先级排序时
- 用于技术重构工作（没有用户工作流程要映射）

### 步骤 0：收集上下文（在问题之前）

**代理建议：**

在创建您的故事地图之前，让我们收集上下文：

**产品/功能上下文：**
- 您要绘制什么系统或功能？
- 产品概念、PRD 草稿或现有待办事项列表
- 网站文案、定位材料或用户流程
- 现有的用户故事（如果从扁平待办事项列表过渡）

**用户上下文：**
- 目标角色或用户细分
- 用户研究、访谈或旅程地图
- 要完成的任务或问题陈述

**您可以直接粘贴此内容，或简要描述系统。**

### 问题 1：定义范围

**代理询问：**
“您要绘制什么？（范围是什么？）”

**提供 4 个枚举选项：**

1. **整个产品** — “从发现到完成的完整端到端系统”（适用于新产品或完整重写）
2. **主要功能区域** — “更大产品中的特定工作流程（例如，“入职”、“结账”、“报告”）”（适用于功能发布）
3. **用户旅程** — “特定的用户目标或要完成的任务（例如，“雇佣承包商”、“报税”）”（适用于由要完成的任务驱动的映射）
4. **重新设计/重构** — “正在重建或简化的现有产品/功能”（适用于遗留系统现代化）

**或描述您的特定范围。**

**用户响应：** [选择或自定义]

---

### 问题 2：确定用户/角色

**代理询问：**
“这个地图的主要用户是谁？（列出角色或用户细分。）”

**提供 4 个枚举选项：**

1. **单个角色** — “一种主要用户类型（例如，“小企业主”）”（简化映射，适用于 MVP）
2. **多个角色，共享工作流程** — “不同类型的用户，相同的核心活动（例如，“买家”和“卖家”都浏览列表）”（适用于市场）
3. **多个角色，不同工作流程** — “具有不同工作流程的不同用户类型（例如，“管理员”与“最终用户”）”（需要单独的地图或泳道）
4. **组织中的角色** — “不同的职能部门（例如，“PM”、“设计师”、“工程师”）”（适用于内部工具）

**或描述您的用户。**

**自适应：** 使用在步骤 0 中提供的角色（原型角色、要完成的任务等）

**用户响应：** [选择或自定义]

### 问题 3：生成骨架（活动）

**代理说：**
“让我们构建骨架——用户为完成目标执行的活动叙事流。”

**代理根据范围（Q1）和用户（Q2）生成 5-8 个活动**，按工作流程顺序从左到右排列。

**示例（如果范围 = “电子商务结账”）：**

```
骨架活动（从左到右）：

1. 浏览产品
2. 添加到购物车
3. 查看购物车
4. 输入运输信息
5. 输入支付信息
6. 确认订单
7. 接收确认
```

**代理询问：**
“这个骨架是否捕捉了完整的工作流程？我们应该添加、删除还是重新排序活动吗？”

**用户响应：** [批准、修改或添加自定义活动]

---

### 问题 4：生成用户任务（在每个活动下）

**代理说：**
“现在让我们在每个活动下添加用户任务，按优先级（顶部 = 必须有，底部 = 可能有）组织。”

**代理为每个活动生成 3-5 个用户任务**，按优先级垂直排列。

**示例（对于活动 2：“添加到购物车”）：**

```
添加到购物车（活动）
├─ 添加单个项目到购物车（必须，可走骨架）
├─ 调整数量（必须）
├─ 一次添加多个项目（应有）
├─ 保存稍后添加（可能有）
└─ 添加礼品包装（可能有）
```

**代理对所有骨架活动重复此操作**，显示完整地图。

**代理询问：**
“这是否捕捉了关键任务？优先级是否正确（顶部 = MVP，底部 = 后续发布）？”

**用户响应：** [批准、修改或添加自定义任务]

---

### 问题 5：确定发布切片（可走骨架 + 增量）

**代理说：**
“让我们通过在地图上绘制水平线来定义发布切片。”

**代理生成 3 个发布切片：**

**发布 1（可走骨架）：** 所有活动中最高优先级的任务——最小的端到端功能

**发布 2（下一个增量）：** 第二优先级的任务，增强核心工作流程

**发布 3（完善/扩展）：** 第三优先级的任务（可能有、边缘情况、优化）

**示例：**

发布 1（可走骨架）：

## 示例

### 示例 1：好的故事地图（电子商务结账）

**Q1 响应：** “主要功能区域 — 电子商务结账工作流程”

**Q2 响应：** “单个角色 — 在线购物者”

**Q3 - 骨架生成：**
```
浏览 → 添加到购物车 → 查看购物车 → 输入运输 → 输入支付 → 确认 → 接收确认
```

**Q4 - 用户任务生成：**

```
浏览产品
├─ 查看产品列表（R1）
├─ 搜索/过滤（R2）
└─ 产品推荐（R3）

添加到购物车
├─ 添加单个项目（R1）
├─ 调整数量（R2）
└─ 保存稍后（R3）

查看购物车
├─ 查看行项目 + 总计（R1）
├─ 应用促销代码（R2）
└─ 估算运输成本（R3）

[...等等...]
```

**Q5 - 发布切片：**
- **发布 1：** 可走骨架——基本流程，没有额外内容
- **发布 2：** 搜索、数量调整、促销代码
- **发布 3：** 推荐、免费结账、礼品选项

**为什么这种方法有效：**
- 骨架遵循用户叙事（不是技术层）
- 可走骨架提供端到端价值
- 增量发布添加复杂性，同时不破坏核心流程

---

### 示例 2：差的故事地图（技术层）

**骨架（错误）：**
```
UI 层 → API 层 → 数据库层 → 部署
```

**为什么失败：**
- 不是以用户为中心（用户不关心技术架构）
- 无法增量交付端到端价值
- 水平思维伪装成故事映射

**修复：**
- 按用户工作流程映射：“注册 → 配置设置 → 邀请团队 → 开始项目”
- 每个发布交付完整的工作流程，而不是单个层

## 常见陷阱

### 陷阱 1：伪装的扁平待办事项列表
**症状：** 故事地图只是一个垂直列表，没有水平叙事

**后果：** 失去沟通优势；仍然是“无上下文的大杂烩”

**修复：** 强制水平结构——顶部是活动，垂直向下是任务

---

### 陷阱 2：技术架构作为骨架
**症状：** 骨架 = “前端 → 后端 → 数据库”

**后果：** 不是以用户为中心，无法增量交付价值

**修复：** 骨架应遵循用户工作流程，而不是系统层

---

### 陷阱 3：功能完整的水平
**症状：** 发布 1 = “完全构建活动 1”，发布 2 = “完全构建活动 2”

**后果：** 直到所有活动完成，都无法交付端到端价值

**修复：** 可走骨架 = 跨所有活动的薄切片，增量增强

---

### 陷阱 4：过早过多细节
**症状：** 试图提前映射每个边缘情况和验收标准

**后果：** 分析瘫痪，失去整体概览

**修复：** 从骨架 + 高级任务开始，以后完善

---

### 陷阱 5：地图隐藏在工具中
**症状：** 故事地图存在于 Jira/Miro 中，从未显示

**后果：** 失去作为信息辐射器的价值

**修复：** 物理打印/张贴地图；让团队每天可见
