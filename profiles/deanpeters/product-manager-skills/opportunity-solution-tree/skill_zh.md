## 目的
通过从利益相关者的请求中提取目标成果，生成机会选项（待解决的问题），映射潜在解决方案，并根据可行性、影响力和市场契合度选择最佳的概念验证（POC），指导产品经理创建机会解决方案树（OST）。使用此方法将模糊的产品请求转化为结构化的发现，确保团队在跳转到解决方案之前解决正确的问题——避免“功能工厂”综合征和过早地收敛于想法。

这不是一个路线图生成器——它是一个结构化的发现流程，输出经过验证的机会和可测试的解决方案假设。

## 输入

**最适合：** 您开始时使用的利益相关者请求或目标成果。
**也很有用：** 您已经拥有的客户证据、限制条件和正在推进的解决方案。

在调用本身提供的任何内容——技能名称后的文本、粘贴的上下文转储或附加的 `ARGUMENTS:` 行——都计为已经给出的答案。使用它并跳过它所涵盖的内容；不要重复提问。

**空手而来？那也没关系。** 该技能通过询问请求或期望的成果来启动，然后从中提取可衡量的目标成果。

**示例调用：** `根据此请求构建OST：'销售说我们需要一个移动应用程序，因为竞争对手已经有了。'`

## 关键概念

### 什么是机会解决方案树（OST）？

OST是一个视觉框架（Teresa Torres，《持续发现习惯》），它连接：
1. **期望成果**（业务目标或产品指标）
2. **机会**（客户问题、需求、痛点或期望，这些可能推动成果）
3. **解决方案**（解决每个机会的方法）
4. **实验**（验证解决方案的测试）

**结构：**
```
         期望成果 (1)
                |
    +-----------+-----------+
    |           |           |
机会   机会   机会 (3)
    |           |           |
  +-+-+       +-+-+       +-+-+
  | | |       | | |       | | |
 S1 S2 S3    S1 S2 S3    S1 S2 S3 (9个总解决方案)
```

### 为什么这种方法有效
- **成果驱动：** 从业务目标开始，而不是功能请求
- **先发散后收敛：** 在选择解决方案之前探索多个机会
- **问题导向：** 机会是问题，而不是伪装成问题的解决方案
- **可测试性：** 每个解决方案都映射到实验，而不仅仅是“构建并发布”
- **POC选择：** 在投入资源之前评估可行性、影响力和市场契合度

### 反模式（这不是什么）
- **不是功能列表：** 机会是客户面临的问题，而不是“我们需要深色模式”
- **不是先解决方案：** 不要从“我们应该构建X”开始——从“客户在挣扎于Y”开始
- **不是瀑布式规划：** OST是一个发现工具，而不是项目计划
- **不是一次性练习：** 随着您从实验中学习，OST会不断发展

### 何时使用此方法
- 利益相关者请求功能或产品计划
- 开始新产品领域的发现
- 澄清模糊的OKR或战略目标
- 优先考虑首先解决哪些问题
- 使团队对要推动的成果保持一致

### 何时不要使用此方法
- 当问题已经得到验证时（转移到解决方案测试）
- 用于战术性错误修复或技术债务（不需要发现）
- 当利益相关者要求特定解决方案时（首先解决对齐问题）

## 应用

使用 `template.md` 获取完整的填写结构。

此交互式技能遵循一个**两阶段流程**：

**阶段 1：** 生成OST（提取成果、识别机会、映射解决方案）
**阶段 2：** 选择POC（评估解决方案、推荐最佳起始点）

**产品上下文（如果可用）：**

- 使用数据、支持工单、流失原因

**您可以直接粘贴这些内容，或简要描述请求。**

## 阶段 1：生成机会解决方案树

### 问题 1：提取期望成果

**代理询问：**
“此计划的期望成果是什么？（您试图推动的业务或产品指标是什么？）”

**提供 4 个编号选项：**

1. **收入增长** — “增加ARR、从现有客户中扩展收入、新的收入来源”（适用于扩展型产品）
2. **客户留存** — “减少流失率、增加激活率、提高参与度/粘性”（适用于存在留存问题的成熟产品）
3. **客户获取** — “增加注册量、试用转化率、新用户增长”（适用于早期阶段或增长型产品）
4. **产品效率** — “减少支持成本、减少获取价值时间、提高运营指标”（适用于优化运营的成熟产品）

**或描述您的特定期望成果（要可衡量的：例如，“将试用到付费转化率从15%提高到25%”）。**

**用户响应：** [选择或自定义]

**代理提取并确认：**
- **期望成果：** [具体、可衡量的成果]
- **为什么重要：** [来自利益相关者请求或上下文的理由]

---

### 问题 2：识别机会（待解决的问题）

**代理根据期望成果和提供的上下文生成 3 个机会。**

**代理说：**
“根据您的期望成果（来自 Q1）和您提供的上下文，以下是 **3 个机会**（客户问题或需求），这些可能推动此成果：”

**示例（如果成果 = 增加试用到付费转化）：**

1. **机会 1：用户在试用期间没有体验到价值** — “新用户注册但未完成引导，从未达到‘啊哈时刻’，在看到核心价值之前就放弃了”
   - 证据：[来自上下文：引导分析、支持工单、退出调查]

2. **机会 2：定价不明确或不匹配** — “用户不确定付费计划是否值得；不了解他们为价格得到什么；定价页面令人困惑”
   - 证据：[来自上下文：定价页面处的转化漏斗流失、销售异议]

3. **机会 3：免费计划‘足够好’** — “用户无限期地留在免费层，因为它满足了他们的需求；没有升级的充分理由”
   - 证据：[来自上下文：免费增值用户留存数据、寻求规避支持工单]

**代理询问：**
“哪个机会感觉最关键要探索，或者您想修改/添加机会？”

**用户响应：** [选择或自定义]

---

### 问题 3：为选定的机会生成解决方案

**代理为选定的机会生成 3 个解决方案想法。**

**代理说：**
“对于 **机会 [X]：[名称]**，以下是 **3 个潜在解决方案** 来测试：”

**示例（如果机会 1 选择：用户在试用期间没有体验到价值）：**

1. **解决方案 1：引导式引导清单** — “引导用户逐步完成核心工作流的交互式清单（例如，'创建您的第一个项目'、'邀请队友'、'完成一项任务'）”
   - 假设：结构化指导增加完成率
   - 实验：A/B测试清单与无清单，测量激活率

2. **解决方案 2：价值触发器** — “当用户卡住时自动提示用户（例如，'您还没有创建项目——这里有一个模板来开始'）”
   - 假设：主动提示防止流失
   - 实验：跟踪提示的参与度，测量试用到付费提升

3. **解决方案 3：人工辅助引导** — “为高价值试用用户提供15分钟引导通话（企业、团队计划）”
   - 假设：个性化接触增加高意向用户的转化率
   - 实验：向50名试用用户提供，测量转化率与控制组

**代理询问：**
“您想探索另一个机会的解决方案，还是跳转到POC选择？”

**用户响应：** [选择或自定义]

## 阶段 2：选择概念验证（POC）

生成解决方案后，代理帮助选择要首先测试哪个解决方案。

---

### 问题 4：评估解决方案（可行性、影响力、市场契合度）

**代理说：**
“让我们评估您的解决方案，以选择最佳起始点。我将根据 **可行性**（构建难度）、**影响力**（可能推动成果的程度）和 **市场契合度**（与客户需求的一致程度）对每个解决方案进行评分。”

**代理生成评估表：**

| 解决方案 | 可行性（1-5） | 影响力（1-5） | 市场契合度（1-5） | 总分 | 理由 |
|----------|-------------------|--------------|------------------|-------------|-----------|
| 解决方案 1: 引导式引导清单 | 4 | 4 | 5 | 13 | 高可行性（UI模式）、已证明的影响力（行业标准）、强市场契合度（用户期望引导） |
| 解决方案 2: 价值触发器 | 3 | 3 | 4 | 10 | 中等可行性（需要分析集成）、适度影响力（取决于触发质量）、良好市场契合度 |
| 解决方案 3: 人工辅助引导 | 5 | 5 | 3 | 13 | 高可行性（无需开发工作）、高影响力（个性化接触）、较低市场契合度（无法扩展，仅限高接触） |

**评分标准：**
- **可行性：** 1 = 数月工作，5 = 几天/几周
- **影响力：** 1 = 微小成果推动，5 = 主要成果转变
- **市场契合度：** 1 = 客户不关心，5 = 客户主动请求此功能

**代理建议：**

**推荐 POC：解决方案 1（引导式引导清单）**

**为什么这个 POC：**
- 平衡可行性（可在 2-4 周内构建）与影响力（已证明的模式）
- 强市场契合度（用户期望引导）
- 可测试假设：“如果我们引导用户完成核心工作流，激活率将从 X% 提高到 Y%，因为 [理由]。”

**替代 POC：解决方案 3（人工辅助引导）**
- 如果您想快速学习且无需开发工作，从这里开始
- 手动与 20-50 名试用用户进行，收集定性反馈
- 使用学习成果来指导自动化解决方案（解决方案 1）

**不推荐用于 POC：解决方案 2（价值触发器）**
- 需要更多前期投入
- 影响力取决于触发质量（需要实验才能正确实现）
- 最好在验证核心引导流程后作为后续步骤

---

### 问题 5：定义实验

**代理询问：**
“您将如何测试此解决方案？实验是什么？”

**提供 3 个编号选项：**

1. **A/B 测试** — “构建 MVP，向 50% 的试用用户展示，比较转化率与控制组”（最佳用于：定量验证，需要流量）
2. **原型 + 可用性测试** — “创建可点击原型，观察 10 名用户尝试引导，收集定性反馈”（最佳用于：早期阶段验证，低流量）
3. **人工 concierge 测试** — “手动运行解决方案与 20 名用户（例如，亲自引导他们完成引导），测量结果”（最佳用于：快速学习，无需开发工作）

**或描述您的实验方法。**

**用户响应：** [选择或自定义]

## 常见陷阱

### 陷阱 1：伪装成解决方案的机会
**症状：** “机会：我们需要一个移动应用程序”

**后果：** 您已经在没有探索问题的情况下收敛到解决方案。

**修复：** 将机会重新定义为客户问题：“移动优先用户无法在移动设备上访问产品。”

---

### 陷阱 2：跳过发散（直接跳到一个解决方案）
**症状：** “我们知道解决方案是 [X]，只需要构建它”

**后果：** 错过更好的替代方案，没有学习。

**修复：** 每个机会至少生成 3 个解决方案。在收敛之前强制发散。

---

### 陷阱 3：成果过于模糊
**症状：** “期望成果：改善用户体验”

**后果：** 无法衡量成功，无法优先考虑机会。

**修复：** 使成果可衡量：“将NPS从30提高到50”或“将引导流失率从60%降低到40%。”

---

### 陷阱 4：没有实验（直接构建）
**症状：** 选择一个解决方案并直接跳到路线图

**后果：** 没有验证，高风险构建错误的事情。

**修复：** 每个解决方案都必须映射到实验。没有实验 = 没有OST。

---

### 陷阱 5：分析瘫痪（永远探索）
**症状：** 生成 20 个机会，50 个解决方案，从未选择一个

**后果：** 团队在发现中停滞不前，没有进展。

**修复：** 限制为 3 个机会，每个机会 3 个解决方案（总共 9 个）。选择 POC，运行实验，学习，迭代。
