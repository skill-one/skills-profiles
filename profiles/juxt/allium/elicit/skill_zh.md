# 诱导

这项技能通过对话引导你构建 Allium 规范。目标是揭示模糊之处，并生成一个能够捕捉软件所做之事而不规定实现的规范。

## 确定规范范围

在深入细节之前，先确定你要规范的是什么。并非所有内容都需要放在一个规范中。

### 首先要问的问题

**“这个规范的边界是什么？”** 一个完整的系统？一个单一的功能区域？一个大型系统中的单个服务？明确说明哪些内容在范围内，哪些内容不在范围内。

**“我们是否应该故意排除某些区域？”** 第三方集成可能是库规范。遗留功能可能不值得规范。某些功能可能属于单独的规范。

**“这是一个新系统还是已经存在代码？”** 如果存在代码，你正在用诱导进行蒸馏。现有代码会限制可实际规范的内容。

### 记录范围决策

在每个规范的开始处捕获范围：

```
-- allium: 3
-- interview-scheduling.allium

-- 范围：招聘流程的面试安排
-- 包含：候选人资格、面试、时间段管理、邀请、反馈
-- 排除：
--   - 认证（使用 oauth 库规范）
--   - 支付（不适用）
--   - 报表仪表板（单独规范）
-- 依赖：core.allium 中定义的用户实体
```

版本标记（`-- allium: N`）必须是每个 `.allium` 文件的第一行。使用当前的语种版本号。

## 找到合适的抽象级别

太具体会导致你规范实现。太抽象则会导致你说不出有用的东西。

### “为什么”测试

对于每个细节，问：“为什么利益相关者关心这个？”

| 细节 | 为什么？ | 包含？ |
|------|------|------|
| “用户使用 Google OAuth 登录” | 他们需要认证 | 也许不需要，“用户进行认证”可能就足够了 |
| “我们支持 Google 和 Microsoft OAuth” | 用户选择他们的提供者 | 是的，选择是领域级别的 |
| “会话在 24 小时后过期” | 安全/用户体验决策 | 是的，影响用户体验 |
| “会话存储在 Redis 中” | 性能 | 不，实现细节 |
| “密码必须为 12 个以上字符” | 安全策略 | 是的，影响用户 |
| “密码使用 bcrypt 哈希” | 安全实现 | 不，如何而不是什么 |

### “可以有不同的实现吗？”测试

问：“这个系统可以有不同的实现方式，同时仍然保持相同的功能吗？”

- 如果可以，它可能是一个实现细节。将其抽象化。
- 如果不可以，它可能是领域级别的。包含它。

例子：

- “通过 Slack 发送通知”。可以是电子邮件、短信等。抽象为 `Notification.created(channel: ...)`。
- “面试官必须在 3 小时内确认”。这个具体的截止日期在领域级别很重要。包含持续时间。
- “我们使用 PostgreSQL”。可以是任何数据库。不包括。
- “数据保留 7 年以符合法规”。法规要求。包含。

### “模板与实例”测试

这是一个事物类别，还是一个特定实例？

| 实例（实现） | 模板（领域级别） |
|-------------|-----------------|
| Google OAuth | 认证提供者 |
| Slack | 通知通道 |
| 15 分钟 | 链接过期持续时间（可配置） |
| Greenhouse ATS | 外部候选人来源 |

有时实例就是领域关注点。“我们专门与 Salesforce 集成”可能是一个竞争优势。“我们支持正好这三个 OAuth 提供者”可能是设计范围。

不确定时，询问利益相关者：“如果我们改变这个，系统会变成不同的系统，还是只是不同的实现？”

### 抽象级别

```
太抽象：          "用户可以做一些事情"
                    |
产品级别：         "候选人可以接受或拒绝面试邀请"
                    |
太具体：          "候选人点击一个按钮，POST 到 /api/invitations/:id/accept"
```

**表明你太抽象了。** 规范几乎可以描述任何系统。没有可测试的断言。产品负责人说“但这没有捕捉到……”

**表明你太具体了。** 你提到了技术、框架或 API。你描述了 UI 元素（按钮、页面、表单）。实现团队说“你为什么要规定我们如何构建这个？”

### 配置与硬编码

当你遇到特定值（3 小时、7 天等）时，问：

1. **这个值是一个设计决策吗？** 包含它。
2. **它可能因部署或客户而异吗？** 使其可配置。
3. **它是随机的吗？** 考虑是否要包含它。

```
-- 硬编码设计决策
rule InvitationExpires {
    when: invitation: Invitation.created_at + 7.days <= now
    ...
}

-- 可配置
config {
    invitation_expiry: Duration = 7.days
}

rule InvitationExpires {
    when: invitation: Invitation.created_at + config.invitation_expiry <= now
    ...
}
```

### 黑盒

某些逻辑很重要，但属于不同的级别：

```
-- 黑盒：我们知道它存在以及它考虑的内容，但不知道如何实现
ensures: Suggestion.created(
    interviewers: InterviewerMatching.suggest(
        considering: {
            role.required_skills,
            Interviewer.skills,
            Interviewer.availability,
            Interviewer.recent_load
        }
    )
)
```

规范说存在一个匹配算法，它考虑这些输入并产生面试官建议。规范没有说匹配如何工作、权重是什么或具体的算法。

这是正确级别的情况：当算法复杂且在演变时，当产品负责人关心输入和输出而不是内部结构，并且如果需要，可以单独详细规范来覆盖它。

## 阅读初始提示

在选择方法之前，评估用户带来的内容。初始提示告诉你从哪里开始。

**用户描述了一个流程。** “我们有一个招聘流程，候选人申请、筛选、面试，然后我们决定。” 他们正在以流程级别思考。从流程发现开始——让他们描述流程，然后帮助他们组织成规范结构。参考 [流程发现](./references/process-discovery.md)。

**用户命名了实体。** “我需要规范一个具有状态和转换的 Order 实体。” 他们已经在以结构级别思考。跳过流程发现，直接进行范围定义，然后填充细节。参考 [细节诱导](./references/detail-elicitation.md) 在处理规则和表面时。

**用户有一个模糊的想法。** “我们需要构建一个用于管理客户支持的东西。” 他们需要帮助塑造想法，然后再规范它。使用开放式问题从流程发现开始：“当客户寻求帮助时会发生什么？” 参考 [流程发现](./references/process-discovery.md)。

**用户有现有代码。** “我们有一个支付服务，我想捕获它所做的工作。” 这是用诱导进行蒸馏。指向 `distill` 技能，或者结合使用：从代码中蒸馏结构，从利益相关者那里诱导意图。

**用户有现有规范。** 首先阅读规范。使用 [评估规范](../allium/references/assessing-specs.md) 确定每个实体的成熟度。跳过规范已经覆盖的阶段——不要重新询问有范围注释的规范的范围问题，或者重新发现已经有转换图的流程。从每个实体需要的级别开始：有生命周期但没有规则的实体的细节诱导，有规则但没有失败路径的实体的障碍诱导。

## 诱导方法

### 阶段 0：流程发现

**目标：** 在识别结构之前，了解系统支持哪些流程。

并非每个会话都需要这个阶段。如果用户已经想到实体和生命周期，跳到阶段 1。如果他们以流程描述或模糊想法到达，从这里开始。

让用户用自己的话描述系统，然后再应用 Allium 结构。捕获流程、参与者、结果，然后组织成结构。参见 [流程发现](./references/process-discovery.md) 以获取具体技术。

**输出：** 流程名称和结果。大致的步骤顺序。参与者识别。足够编写一个粗略的规范（具有转换图和开放式问题的实体）。

**注意：** 太早跳到实体定义的冲动。保持在流程级别，直到流程清晰。

### 阶段 1：范围定义

**目标：** 了解我们正在规范什么以及边界在哪里。

要问的问题：

1. “这个系统本质上是什么？用一句话概括？”
2. “这个系统从哪里开始，到哪里结束？范围内与范围外是什么？”
3. “用户是谁？是否有不同的角色？”
4. “是否有现有系统与之集成？它们处理什么？”

如果阶段 0 被跳过，也问：“这个系统支持哪些关键流程？每个流程的成功看起来像什么？” 这将实体识别锚定到流程而不是孤立地枚举名词。这里也适用 [流程发现](./references/process-discovery.md) 中的技术——如果用户难以表达流程，使用过去时回忆和结果优先提问。

**输出：** 参与者和角色列表。核心实体列表（如果阶段 0 运行，则从流程中派生）。边界决策（外部是什么）。一句话描述。

**注意：** 范围蔓延（“它还做 X、Y、Z”，温和地重申）。假设知识（“显然它处理认证”，明确说明）。描述表明这是一个 [库规范](./references/library-spec-signals.md) 而不是特定于应用程序的逻辑（例如 OAuth、支付处理、电子邮件交付）。

### 阶段 2：快乐路径流程

**目标：** 从开始到结束追溯主要路径。

如果阶段 0 产生了一个行走骨架（参见 [流程发现](./references/process-discovery.md)），使用它作为起点。否则，问：“如果我们只能通过这个流程的一条路径，它会是什么？” 将骨架写成粗略的规范，并用领域术语描述它给用户听（参见 [评估规范](../allium/references/assessing-specs.md#communicating-with-stakeholders)）。

然后充实：“每个步骤由什么触发？谁参与？发生了什么变化？” 跟随一个实体通过其生命周期，捕获状态转换、参与者和触发器。

```
Candidacy:
  applied -> screening -> interviewing -> deciding -> hired | rejected
```

**输出：** 关键实体的转换图。主要触发器和结果。每个步骤的参与者分配。

**注意：** 太早跳到边缘案例（“但如果……”，记下它并保持在快乐路径上）。实现细节渗入（“API 端点……”，重定向到结果）。

在编写规范结构后，如果 CLI 可用，运行 `allium check` 修复结构问题——不要等到阶段 4 再验证。

在建立骨架后，参考 [细节诱导](./references/detail-elicitation.md) 以获取填充规则、表面和数据依赖的技术。

### 阶段 3：边缘案例和失败路径

**目标：** 发现什么会出错以及系统如何处理。

参考 [障碍诱导](./references/obstacle-elicitation.md) 以获取技术。关键方法：

- 使用预死测试：想象这个系统已经构建并且它失败了。出了什么问题？
- 在每个步骤：如果没有人做任何事在这里？一天后？一周后？
- 在每个交接：谁接管？他们如何知道轮到他们了？他们需要看到什么？
- 在每个转换：如果先决条件不满足？可以逆转吗？
- 对于外部依赖：信息如何进入系统？如果外部服务不可用会怎样？

**输出：** 异常转换。时间触发器与 `requires` 守卫。升级路径。终端错误状态。不变量。

**注意：** 无限循环（“然后它重试，然后再次重试……”，需要终端状态）。缺少升级，因为最终需要有人知道。

当利益相关者声明系统级属性（“余额永远不会为负”，“没有两个面试为同一候选人重叠”）时，这些是不变量候选者。将它们捕获为 `invariant Name { expression }` 声明。

在编写规则和异常转换后，如果 CLI 可用，运行 `allium check` 修复问题，然后再进行细化。

### 阶段 4：细化

**目标：** 验证并完成规范。

参考 [假设检查](./references/assumption-checking.md) 以获取技术。用领域术语描述规范所说的内容，并测试它是否符合用户的思维模型。通过具体的场景测试规范。测试排序假设。验证参与者分配。

如果 Allium CLI 可用，运行 `allium check` 并使用诊断来识别结构差距。如果 `allium analyse` 可用且规范包含规则和表面，运行它并使用发现来揭示流程级差距。参考 [行动化发现](../allium/references/actioning-findings.md) 了解如何将发现转化为领域问题。

要问的问题：

1. “查看 [实体]，这些状态是否完整？它可以处于任何其他状态吗？”
2. “我们是否遗漏了任何内容？”
3. “这个规则引用了 [X]，我们需要定义它吗，还是它是外部的？”
4. “这个细节在这里是否必要，还是应该存在于详细规范中？”

**技术：** 取一个具体场景并通过规范进行跟踪。“让我们说 Alice 申请了高级工程师职位。带我走过她候选人资格发生的事情。”

**输出：** 完整的实体定义。记录的开放式问题。延迟的规范。确认外部边界。

当相同的义务模式（例如序列化合同、确定性评估要求）在多个表面出现时，建议将其作为 `contract` 声明提取以供重用。

## 诱导原则

### 一次只问一个问题

不好：“你有哪些实体，它们可以处于哪些状态，谁可以修改它们？”

好：“这个系统管理哪些主要内容？”
然后：“让我们以 [Candidacy] 为例。它可以处于哪些状态？”
然后：“谁可以改变候选人资格的状态？”

### 探索后果

当出现选择时，不要只接受第一个答案。探索后果。

“你说过邀请在 48 小时后过期。然后会怎样？”
“如果候选人在我们重试后仍未响应呢？”
“如果他们永远不响应，这是否会使候选人永远卡住？”

这会揭示他们尚未做出的决策。

### 区分产品与实现

当你听到实现语言时，重定向：

| 他们说 | 你重定向 |
|------|------|
| “API 返回 404” | “所以用户被通知未找到？” |
| “我们存储在 Postgres 中” | “捕获了哪些信息？” |
| “前端显示一个模态框” | “用户被提示确认？” |
| “我们使用 cron 作业” | “这按计划发生，多久一次？” |

### 明确揭示模糊之处

记录一个开放式问题比假设更好。

“我不确定拒绝是否应将候选人返回到池中或完全移除。让我将其记录为开放式问题。”

```
open question "当候选人拒绝时，他们返回到池中还是退出？"
```

### 愿意迭代

修改早期决策是正常的。

“我们之前说过所有管理员都看到所有通知。但现在你描述了角色特定的仪表板。我们应该重新考虑这个吗？”

### 优先深度而非广度

首先完全开发最重要的实体。将其他实体保留为粗略的，并记录开放式问题。用户可以在后续会话中充实它们。试图在一个对话中开发所有实体到相同的级别，可能会导致上下文疲劳而未完成任何内容。

### 知道何时停止

并非所有内容都需要现在规范。

“这涉及到匹配算法如何工作。我们应该将其推迟到详细规范中吗？”

“我们已经覆盖了主要流程。报告仪表板听起来像是一个单独的规范。”
