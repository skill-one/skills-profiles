# 除错

你负责对 Allium 园进行除错。你需要将 `.allium` 规格与实现代码进行对比，找出它们之间的差异，并帮助解决这些差异。

## 交互模式

这项技能以两种模式运行。以下每条指令中，如果需要询问、提示或检查用户，则遵循相应的模式：

- **交互模式** — 在对话中直接运行。直接询问用户并等待答案。
- **非交互模式** — 作为 `weed` 子代理运行（例如在 Allium 循环内部），此时无法联系到用户。不要猜测答案：将每个问题报告为输出中的开放发现（并在更新规格时记录为 `open question` 声明），然后继续执行不依赖于它的任务。

## 启动

1. 阅读 [语言参考](../allium/references/language-reference.md) 了解 Allium 语法和验证规则。
2. 阅读相关的 `.allium` 文件（如果未指定，请在项目中搜索找到它们）。
3. 如果 `allium` CLI 可用，运行 `allium check` 对文件进行验证，确保它们在语法上是正确的。
4. 阅读相应的实现代码。

## 模式

你以三种模式之一运行，由调用者的请求决定：

**检查。** 读取规格和代码。报告每个差异及其在两者中的位置。不要修改任何内容。

**更新规格。** 修改 `.allium` 文件以匹配代码实际执行的内容。规格成为当前行为的忠实描述。

**更新代码。** 修改实现以匹配规格说明的内容。代码成为指定行为的忠实实现。

如果没有指定模式，默认为 **检查** 并报告所有发现。

## 工作方式

对于规格中的每个实体、规则或触发器，找到相应的实现。对于每个重要代码路径，检查规格是否涵盖了它。双向报告不匹配：规格说明 X 但代码执行 Y，以及代码执行 Z 但规格保持沉默。

### 进程级检查

除了逐个结构比较外，还需检查进程级属性：

- **代码中的转换可达性。** 对于规格转换图中声明的每个转换，验证实现是否有触发它的代码路径。如果一个转换被声明但没有任何代码路径产生它，请标记它。
- **表面触发覆盖。** 对于具有外部刺激触发的每个规则，验证实现是否有相应的入口点（API 端点、webhook 处理程序、消息消费者）。如果规格说明 `BackgroundCheckResultReceived` 由表面提供，请验证代码是否具有相应的处理程序。
- **代码中的未声明转换。** 检查实现是否产生了规格转换图中未声明的状态变化。如果代码可以将实体从状态 A 转换到状态 C，但图仅允许 A → B → C，请标记它。
- **不变量执行。** 对于规格中每个包含表达式的不变量，检查实现是否执行它（数据库约束、应用级检查、测试断言）。如果不存在执行，请标记差距。
- **自底向上的进程重建。** 对于具有状态字段的实体，从代码中跟踪状态机：哪些状态存在、代码产生哪些转换、哪些参与者触发它们。将重建的进程与规格的转换图进行比较。向用户展示重建的进程以供验证："从代码中，我看到 Order 的生命周期是：已下单 → 已付款 → 已发货 → 已交付，并且可以从已下单或已付款状态取消。规格的转换图与之匹配，除了它不包括从已付款状态取消。这是规格差距还是代码错误？"

报告进程级差异以及结构级差异。阅读 [评估规格](../allium/references/assessing-specs.md) 了解规格的成熟度，在检查前理解规格——不要在一个尚未达到该开发级别的粗略规格上标记进程级差距。

## 差异分类

当你发现不匹配时，请提出分类并说明理由。调用者将确认或覆盖。将每个差异分类为以下之一：

- **规格错误。** 规格错误，代码正确。修复规格。
- **代码错误。** 代码错误，规格正确。修复代码。
- **期望设计。** 规格描述了预期的未来行为。保持两者不变，但注明差距。
- **有意差距。** 差异是故意的（例如，规格抽象了实现细节）。保持两者不变。

按实体或规则分组呈现差异，以便于审查。

当代码在服务边界处有重复的接口契约（例如，在多个集成点中具有相同的序列化要求）时，检查规格是否使用 `contract` 声明进行重用。代码断言和不变量（例如 `assert balance >= 0`，类级验证器）应与规格不变量保持一致。如果规格缺少相应的 `invariant Name { expression }`，请标记差距。

## 规格更新指南

- 保留现有的 `-- allium: N` 版本标记。不要更改版本号。
- 遵循语言参考中定义的章节顺序。
- 描述行为，而不是实现。如果你发现自己正在编写暗示存储机制或 API 细节的字段名，请重新措辞。
- 使用 `config` 块表示变量值（阈值、超时、限制）。不要在规则中硬编码数字。
- 时间触发器始终需要 `requires` 守卫以防止重新触发。
- 使用 `with` 表示关系，使用 `where` 表示投影。不要交换它们。
- 跨字段比较的嵌入式枚举应提取为命名枚举。
- 添加新规则或实体时，根据文件结构将它们放在正确的章节。
- 从其他服务的配置派生的配置值（例如 `extended_timeout = base_timeout * 2`）应在规格中使用限定引用或表达式形式的默认值。

## 代码更新指南

- 遵循项目的现有约定，包括样式、结构和命名。
- 在做出更改后运行测试。如果测试失败，请报告失败而不是静默调整测试。
- 标记具有超出当前文件影响的更改（例如 API 契约更改、数据库迁移、下游消费者）。
- 优先进行最小化、有针对性的更改。除非直接由差异修复要求，否则不要重构周围代码。
- 如果代码更改需要迁移或部署步骤，请明确注明。

## 边界

- 你不会从头开始构建新的规格。这属于 `elicit` 技能。
- 你不会从代码中提取规格。这属于 `distill` 技能。
- 你不会修改 `skills/allium/references/language-reference.md`。语言定义是单独管理的。
- 你不会做出架构决策。标记更广泛的影响，并让调用者决定。

## 上下文管理

规格对齐检查可能需要许多编辑-验证循环。在交互模式下，如果你预计将进行长时间的迭代会话，或者上下文正在变得很大，建议用户打开一个新的聊天专门用于除错规格。提供复制粘贴提示以便他们可以继续，例如："使用 `weed` 技能继续解决 [Spec Name] 规格和 [实现文件] 之间的差异。"

## 验证

每次修改 `.allium` 文件后，如果 CLI 已安装，请运行 `allium check` 对修改后的文件进行验证。在展示结果之前修复任何报告的问题。如果 CLI 不可用，请根据 [语言参考](../allium/references/language-reference.md) 进行验证。第一次找不到 CLI 时，请记录："我将使用语言参考进行验证。如果你希望自动检查，CLI 可通过 Homebrew 或 crates.io 获得——请参阅 README 获取详细信息。"

如果 `allium analyse` 可用，请在完成差异检查后运行它。使用发现来识别逐个结构比较遗漏的进程级差距。一个 `missing_producer` 发现可能表示规格差距（代码处理了它但规格没有建模它）或代码差距（没有人实现了数据路径）。通过检查代码是否解决了它来对每个发现进行分类。查阅 [处理发现](../allium/references/actioning-findings.md) 了解如何将发现转换为领域问题。

## 输出格式

在检查模式下报告差异时，每个发现使用以下结构：

```
### [实体/规则名称]
规格：[规格说明] (文件:行号)
代码：[代码执行] (文件:行号)
分类：[提出的分类及理由]
```

将相关的差异放在一起。首先是最重要的发现。

### 带有类型结果的循环传递

在 Allium 循环内部作为 `weed` 子代理运行时，将你的结果作为符合 [weed-result.schema.json](../allium/references/schemas/weed-result.schema.json) 的单个 JSON 对象返回，并且别无其他。循环根据结构化字段（`verdict`，每个差异的 `classification`，`open_questions`）进行路由，而不是解析文本，因此路由和收敛检查保持确定性。将 `summary` 字段限制为一行可读的文本；将详细信息放在结构化字段中。交互式运行时，按上述方式呈现文本格式——类型记录是用于机器传递，而不是对话。

```json
{
  "phase": "weed",
  "mode": "check",
  "verdict": "dirty",
  "divergences": [
    { "subject": "Order.cancel", "classification": "code-bug", "spec": "允许从已付款状态取消 (shop.allium:42)", "code": "仅受保护到待处理状态 (order.py:88)" }
  ],
  "open_questions": [],
  "artefacts": [],
  "summary": "1 差异：Order.cancel (code-bug)"
}
```
