# 扩展

这项技能从 Allium 规范中生成测试。扩展是指植物通过母体枝条繁殖的方式：规范是母体，测试是后代。

确定性工具保证完整性（每个规范构造都映射到测试义务）。你负责实现桥梁：将规范构造与代码相关联，在项目的约定中生成测试。

## 交互模式

这项技能以两种模式运行。以下每个指令都要求或建议用户执行某些操作，并遵循模式：

- **交互式** — 在对话中内联运行。直接询问用户并等待答案。
- **非交互式** — 作为 `propagate` 子代理运行（例如在 Allium 循环内部），此时无法联系到用户。报告任何需要人类决策的情况——过于粗略的规范无法扩展、模糊的实现桥梁、未覆盖的义务——并在最终输出中继续执行不依赖于它的其他工作。

## 前置条件

在扩展测试之前，你需要：

1. **一个 Allium 规范** — 描述系统行为的 `.allium` 文件
2. **一个目标代码库** — 要测试的实现
3. **测试义务** — 从 `allium plan <spec>`（列出每个所需测试的 JSON）
4. **领域模型** — 从 `allium model <spec>`（描述实体形状、约束、状态机的 JSON）

如果 CLI 工具不可用，请使用测试生成分类法手动从规范中推导测试义务，参考 [`references/test-generation.md`](../allium/references/test-generation.md)。

## 模式

### 表面模式

从表面声明生成边界测试。当用户想要测试 API、UI 合约或集成边界时使用。

对于规范中的每个表面：

1. **暴露测试** — 验证 `exposes` 中的每个项目对指定参与者都是可访问的，包括对集合的 `for` 迭代
2. **提供测试** — 验证当其 `when` 条件为真时操作出现，否则隐藏，包括当相应规则的 `requires` 子句未满足时
3. **参与者限制测试** — 验证表面对其他参与者类型不可访问
4. **参与者识别测试** — 验证只有匹配参与者 `identified_by` 谓词的实体才能交互；对于具有 `within` 的参与者，验证交互限定在声明的上下文中
5. **上下文限定测试** — 验证当没有实体匹配 `context` 谓词时，表面实例不存在
6. **合约义务测试** — 验证 `demands` 由对方满足，`fulfils` 由此表面提供，包括所有类型签名
7. **保证测试** — 验证 `@guarantee` 注释在边界上保持有效
8. **超时测试** — 验证在表面的上下文中引用的时间规则触发
9. **相关导航测试** — 验证导航到相关表面解析到正确的上下文实体

### 规范模式

遍历完整的测试义务文档。当用户想要整个规范的综合测试覆盖时使用。

测试生成分类法中的类别：

- **实体和值类型测试** — 字段、类型、可选 (`?`) 空值处理、`when`-子句状态依赖存在、关系、连接查找、相等性
- **枚举测试** — 命名枚举之间的可比性、成员资格测试、内联枚举隔离
- **和类型测试** — 变体字段、类型守卫、完全性、通过变体名称创建、基础 `.created` 触发器窄化
- **派生值和投影测试** — 计算、过滤、`-> field` 提取、参数化派生值、`now` 易变性、集合操作
- **默认实例测试** — 无条件存在、字段值、默认值之间的交叉引用
- **配置测试** — 默认值、覆盖、强制参数、表达式形式默认值、限定引用、配置链
- **不变量测试** — 规则后验证、边缘情况、蕴涵逻辑、实体级不变量
- **规则测试** — 成功/失败/边缘情况、条件（确保 `if` 守卫读取结果状态）、实体创建、删除、批量更新、规则级 `for` 迭代、`let` 绑定、链式触发器
- **状态转换测试** — 有效/无效转换、终止状态、`transitions_to` 与 `becomes` 语义
- **时间测试** — 截止边界、防止重新触发、可选字段空值行为
- **表面测试** — 暴露、可用性、具有 `within` 限定的参与者识别、上下文限定、相关导航
- **合约测试** — 签名满足、`@invariant` 尊重、`demands`/`fulfils` 方向
- **跨模块测试** — 限定实体引用、外部触发器响应、类型占位符替换
- **跨规则交互测试** — 重复创建守卫、提供可用性
- **转换图测试** — 每个声明的边都可以通过其见证规则到达，未声明的转换被拒绝，终止状态没有出站规则，非终止状态至少有一个出口，枚举值与图边之间存在精确对应关系
- **状态依赖字段测试** — 在限定状态下存在，在限定状态外不存在，进入 `when` 集合时的存在义务，离开时的不存在义务，在移动到限定状态内或外时没有义务，收敛转换都设置该字段，访问 `when`-限定字段需要守卫，通过输入交集推断派生值 `when` 推理
- **场景测试** — 快乐路径、边缘情况、顺序独立性
- **数据流链测试** — 从表面捕获通过规则到下游规则预条件。对于每个链（表面提供触发器 → 规则确保字段 → 下游规则需要字段），生成一个集成测试，通过表面提交数据并验证它到达下游预条件。
- **可达性测试** — 从每个初始状态（通过 `.created()`）到每个终止状态，沿着转换图中的有效路径进行遍历。每个测试执行一个完整的生命周期。
- **死锁场景测试** — 对于 `allium analyse` 识别出潜在死锁的状态，生成测试将实体置于卡住状态，并验证它是否可以继续。
- **跨实体过程测试** — 对于跨越多个实体的过程，生成集成测试，在所有参与实体上从开始到终止状态执行完整过程。

如果 `allium analyse` 可用，使用其结果来优先考虑测试生成。`missing_producer` 或 `dead_transition` 发现表示一个值得用测试来执行的差距。`deadlock` 发现应生成一个测试记录实体无法摆脱卡住状态。参考 [行动发现](../allium/references/actioning-findings.md) 以了解发现类型分类法。

## 测试输出类型

### 1. 基于断言的测试

对于确定性义务：字段存在、枚举成员资格、转换有效性、表面暴露、状态依赖字段存在和不存在。这些是标准的单元/集成测试。

### 2. 基于属性的测试

对于不变量和规则属性。每个带表达式的不变量都成为一个 PBT 属性：
- 使用生成器规范生成一个有效实体状态
- 应用一系列规则（遵循声明的转换图，或从规则中推导出有效的序列）
- 检查不变量在每个步骤中都保持有效

使用项目的 PBT 框架：

| 语言 | 框架 | 发现 |
|------|------|------|
| TypeScript | fast-check | `package.json` |
| Python | Hypothesis | `pyproject.toml` |
| Rust | proptest | `Cargo.toml` |
| Go | rapid | `go.mod` |
| Elixir | StreamData | `mix.exs` |

如果没有 PBT 框架，则回退到基于断言的测试。

### 3. 状态机测试

对于具有状态枚举的实体。当声明了转换图时，遍历图中的每条路径。当没有声明图时，从规则中推导出有效转换。
- 验证转换通过见证规则成功
- 验证被拒绝的转换失败
- 验证每个状态的状态依赖字段根据其 `when` 子句存在或不存在
- 验证每个状态的不变量保持有效

状态机测试需要一个 **动作映射**：每个转换边的函数，它将源状态中的实体作为输入，并通过调用实际实现代码将其生产为目标状态。没有这个映射，测试框架可以描述通过图的有效路径，但不能执行它们。

构建动作映射：
1. 对于转换图中的每条边，在规范中找到见证规则
2. 找到实现该规则的代码（实现桥梁）
3. 编写一个测试动作，设置先决条件（`requires` 子句），调用代码，并返回目标状态中的实体
4. 在 `(from_state, to_state)` 键下注册该动作

一旦映射构建完成，PBT 框架可以遍历随机有效的路径：从任何非终止状态开始，选择一个随机出站边，应用其动作，检查所有实体级不变量，重复。路径长度和起始状态是随机生成的。这是规范转换图最完整的测试表达。

## 实现桥梁

你将规范构造与实现代码相关联，就像杂草技能用于发散检查一样。

### 对于表面测试

将表面映射到它们的实现：
- API 表面映射到端点（REST 路由、GraphQL 解析器、gRPC 服务）
- UI 表面映射到组件或页面
- 集成表面映射到消息处理器或 SDK 方法

通过阅读代码库发现映射。寻找命名模式、路由定义和处理器注册。

### 对于内部测试

对于规范中的每个规则：
1. 找到实现该规则的代码（服务方法、事件处理器、状态机转换）
2. 确定如何实例化涉及的实体（工厂、构建器、固定装置）
3. 确定如何调用规则（API 调用、方法调用、事件派发）
4. 确定如何断言后条件（数据库查询、返回值、事件断言）

### 对于时间测试

时间触发器（基于截止日期的规则）需要在测试中有一个可控制的时间源。如果实现使用墙上时间（`Instant.now()`、`System.currentTimeMillis()`），测试无法可靠地定位自己在截止日期之前、之中或之后。

在尝试时间测试之前，检查组件是否接受注入的时钟或时间参数。常见模式：构造函数上的 `Clock` 参数、方法上的纪元毫秒参数、`TimeProvider` 接口。如果存在接口，注入可控制的时间源。如果不存在，将此标记为测试基础设施差距：组件不支持时间注入。不要尝试通过睡眠或与墙上时间竞争来测试时间行为。

### 对于跨模块触发器链

当规则发出一个触发器，另一个规范的规则接收它（例如 Arbiter 发出 `ClerkReceivesEvent`，Clerk 处理它），测试该链需要多个组件连接在一起。

在生成跨模块测试之前：
1. 从计划输出中跟踪触发器发射图：哪些规则发出触发器，以及哪些其他规范的规则接收它们
2. 检查代码库是否有一个现有的集成测试固定装置将参与组件连接起来（管道测试、端到端测试帮助程序、测试 harness 类）
3. 如果固定装置存在，重用它。跨模块测试应组合现有的接线，而不是重建它
4. 如果没有固定装置，但代码库结构足够清晰以理解接线（服务构造函数、依赖注入、事件总线配置），则生成固定装置和测试
5. 如果接线过于复杂或难以自信生成，则生成带有 TODO 的测试骨架，标记组件接线需要的位置

跨模块测试本质上就是集成测试。它们验证规范的触发器链在组件边界上是否忠实实现。在单个组件测试通过后，优先考虑它们。

### 重用现有测试

在探索代码库时，注意哪些规范义务已经由现有测试覆盖。一个现有的集成测试，从事件提交到确认输出，执行了快乐路径，已经覆盖了多个 `rule_success` 义务和端到端场景。

当现有测试覆盖规范义务时，参考它而不是生成重复的测试。在集成级别，扩展技能的价值在于验证覆盖完整性与规范的义务列表，识别差距，并生成测试来填补它们——下面的协调步骤使此检查显式化。用生成的等效项替换工作正常的逐手写测试不会增加任何价值。

### 对于延迟规范

延迟规范在单独的文件中完全指定。当目标代码库不包含延迟规范的模块时，生成一个带有占位符的测试桩：

## 流程

1. **读取规范** — 理解实体、规则、表面、不变量、转换图、状态依赖字段、合约、配置、默认值。阅读 [评估规范](../allium/references/assessing-specs.md) 以评估规范的成熟度。一个粗略的规范（实体和转换图但没有规则）将产生有限的测试义务——主要是结构化测试。如果规范过于粗略，无法进行有意义的测试生成，建议在使用 `elicit` 或 `distill` 技能进一步开发规范之前，再扩展测试。具有规则和表面的规范可以启用完整的测试分类法，包括数据流链测试和可达性测试。
2. **读取测试义务** — 从 `allium plan` 输出或手动推导
3. **读取领域模型** — 从 `allium model` 输出或手动推导
4. **探索代码库** — 查找现有测试、测试框架、实体实现、规则实现
5. **将构造映射到代码** — 将规范实体/规则/表面与实现类/函数/端点相关联
6. **生成测试** — 生成遵循项目约定的测试文件
7. **验证测试编译/运行** — 确保生成的测试在语法上有效
8. **协调义务** — 确认每个义务都映射到一个覆盖测试，并自动覆盖任何差距（见 [义务协调](#obligation-reconciliation)）

### 发现清单

在生成测试之前，建立：

- [ ] 测试框架和运行器（Jest、pytest、cargo test 等）
- [ ] 如果存在 PBT 框架（fast-check、Hypothesis、proptest 等）
- [ ] 测试文件位置约定（同位、`__tests__/`、`tests/` 等）
- [ ] 实体/模型位置和模式（类、接口、结构）
- [ ] 测试数据的工厂/固定装置模式
- [ ] 状态转换如何实现（方法、事件、状态机）
- [ ] 表面如何实现（路由、控制器、解析器）
- [ ] 现有的测试帮助程序或实用程序
- [ ] 组件是否接受注入的时间源用于时间测试
- [ ] 是否存在跨模块触发器链的集成测试固定装置
- [ ] 哪些规范义务已经由现有测试覆盖

### 生成器意识

当生成器规范可用时，使用它们来生成有效的测试数据：

- 尊重字段类型和约束
- 对于具有转换图的实体，生成处于特定生命周期状态的实体，并根据 `when` 子句正确设置字段存在（例如，一个 `shipped` Order 有 `tracking_number` 和 `shipped_at` 填充；一个 `pending` Order 没有）
- 对于不变量，生成测试边界条件的状态
- 对于配置参数，除非测试覆盖，否则使用声明的默认值

### 义务协调

生成测试后，遍历完整的义务列表——从 `allium plan` 输出或手动推导——并将每个义务映射到覆盖它的测试，无论是本次运行生成的还是预先存在的。协调是静默的：义务是内部工作数据，因此不要叙述映射，打印义务列表或在一切顺利时显示覆盖率报告。

对于没有覆盖测试的每个义务，尝试覆盖它：

1. 生成缺失的测试，或扩展部分覆盖它的现有测试
2. 验证新测试编译并运行
3. 重新检查义务与结果

这是一个小循环，它需要与外部的 Allium 循环相同的保护（见 [驱动循环](../allium/references/driving-the-loop.md)）：

- **尝试上限** — 每个义务最多尝试 2 次。如果第二次尝试没有生成可编译的测试来覆盖它，则暂停该义务。
- **无进度上限** — 如果对剩余差距的完整遍历没有覆盖任何新内容，则停止；进一步的遍历将导致浪费。

当保护触发时，尚未覆盖的义务是协调中用户唯一看到的。报告每个义务的分类和简短原因：

- **基础设施差距** — 测试需要一个代码不提供的接缝：没有可注入的时钟用于时间义务，没有集成固定装置用于跨模块链
- **无法映射的构造** — 在代码优先流程中，没有实现代码与规范构造相关联；无法构建实现桥梁

缺失实现不是残留类别。在规范优先流程中，代码按设计不存在：针对预期接口编写测试并让它失败——失败的测试覆盖其义务，循环的实现阶段将其变为绿色。只有在无法编写任何测试的情况下，义务才会被揭示。

以一条总结行结束：`N 义务，M 覆盖，K 未覆盖`。当所有内容都被覆盖时，这一行是协调的唯一用户面输出。关于单个义务的沉默意味着它被覆盖；任何列出的内容都需要人类决策。当 propagate 在 Allium 循环内部运行时，这一行作为循环的汇总摘要，循环必须在不覆盖未报告原因的义务的情况下不将规范视为收敛。

### 记录篡改基线（在循环中）

在 Allium 循环中运行时，记录协调基线，以便循环的独立见证者稍后可以确认没有虚假篡改。在账本（`.allium-loop/<goal-slug>.json`，见 [驱动循环](../allium/references/driving-the-loop.md)）中：

- 在 `generated_test_hashes` 下为每个生成的测试文件写内容哈希（例如 sha256），按路径键入；
- 在 `reconciliation` 下记录协调摘要行。

哈希是 `witness` 技能重新推导的绝对真理：一个生成的测试，其哈希在没有中间 propagate 运行的情况下发生变化，是一个手工编辑的测试——循环必须永远不会在未报告违规的情况下收敛。记录基线是使该检查成为可能的原因；跳过它，`witness` 可以确认测试通过，但不能确认它们没有被削弱。这是廉价的簿记，不是报告——不要叙述它。

### 带有类型的结果（循环传递）

当作为 `propagate` 子代理在 Allium 循环内部运行时，将你的结果作为符合 [propagate-result.schema.json](../allium/references/schemas/propagate-result.schema.json) 的单个 JSON 对象返回，并且别无其他。循环根据结构化字段路由：`obligations` 和 `uncovered_obligations` 决定覆盖是否完整（循环必须在不 `uncovered_obligations` 为空的情况下不收敛），`generated_tests` 携带路径和哈希基线——相同的哈希，现在是一流的手递。保持 `summary` 字段为 `N 义务，M 覆盖，K 未覆盖` 行。使用 `[]` 表示空列表——不要省略它们。交互式运行时，摘要行仍然是以前整个用户面输出——类型记录是用于机器传递，而不是对话。

```json
{
  "phase": "propagate",
  "obligations": { "total": 12, "covered": 12, "uncovered": 0 },
  "uncovered_obligations": [],
  "generated_tests": [{ "path": "order.test.js", "hash": "sha256:9f2c…" }],
  "test_paths": ["order.test.js"],
  "open_questions": [],
  "summary": "12 义务，12 覆盖，0 未覆盖"
}
```

## 与其他工具的交互

- **distill** 从代码生成规范。这些规范为 propagate 提供输入。
- **weed** 检查一致性。在扩展测试后，weed 验证规范-代码匹配。
- **tend** 进化规范。规范更改后，再次运行 propagate 以更新测试。
- **elicit** 通过对话构建规范。一旦规范准备就绪，propagate 生成测试。

## 限制

- 生成的测试是一个起点。它们可能需要根据项目特定模式进行调整。
- 实现桥梁是 LLM 介导的。复杂或不寻常的代码库可能需要在映射上提供手动指导。
- 跨模块测试需要理解跨服务边界的组件接线。当代码库结构清晰时，可以生成完整的测试。当接线不透明时，生成带有 TODO 的测试骨架以进行手动设置。
- 运行时跟踪验证和模型检查是单独的工作流。
