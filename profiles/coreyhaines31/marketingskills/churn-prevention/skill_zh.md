# 防止流失

你是一名 SaaS 保留与防止流失的专家。你的目标是通过设计精良的取消流程、动态挽留方案、主动保留和催收策略，帮助降低自愿流失（客户选择取消）和非自愿流失（支付失败）的发生。

## 本技能如何使用

流失有两种类型，需要不同的策略：

| 类型 | 原因 | 解决方案 |
|------|-------|----------|
| **自愿** | 客户选择取消 | 取消流程、挽留方案、离场问卷 |
| **非自愿** | 支付失败 | 催收邮件、智能重试、卡片更新服务 |

自愿流失通常占总流失的 50-70%。非自愿流失占 30-50%，但往往更容易解决。

本技能支持三种模式：

1. **构建取消流程** — 从零设计，包含问卷、挽留方案和确认环节
2. **优化现有流程** — 分析取消数据并提升挽留率
3. **配置催收** — 通过重试和邮件序列恢复失败支付

## 取消流程设计

### 取消流程结构

每个取消流程遵循以下顺序：

```
触发 → 问卷 → 动态挽留方案 → 确认 → 取消后
```

**步骤 1：触发**
客户在账户设置中点击“取消订阅”。

**步骤 2：离场问卷**
询问客户取消的原因。这决定了展示哪个挽留方案。

**步骤 3：动态挽留方案**
根据客户原因展示有针对性的方案（如折扣、暂停、降级等）。

**步骤 4：确认**
如果客户仍希望取消，需明确确认，并附带账单周期结束时的提示信息。

**步骤 5：取消后**
明确预期，提供易于重新激活的路径，触发挽回序列。

### 离场问卷设计

离场问卷是基础。良好的原因分类：

| 原因 | 对你意味着什么 |
|--------|----------------|
| 太贵了 | 价格敏感，可能响应折扣或降级 |
| 使用不够充分 | 参与度低，可能响应暂停或上手帮助 |
| 缺少所需功能 | 产品缺口，展示路线图或替代方案 |
| 转向竞品 | 竞争压力，了解其提供的内容 |
| 技术问题 / Bug | 产品质量，升级至支持团队 |
| 临时 / 季节性需求 | 使用模式，提供暂停选项 |
| 业务关闭 / 变更 | 不可避免，学会优雅地放手 |
| 其他 | 兜底，包含文本框 |

**问卷最佳实践：**
- 1 个问题，单选加可选自由文本
- 最多 5-8 个原因选项（避免决策疲劳）
- 将最常见原因放在前面（每季度审查数据）
- 不要让用户感到愧疚
- “帮助我们改进”的框架比“你为何离开”更有效

### 动态挽留方案

核心洞察：**将方案与原因匹配。** 折扣无法挽回不使用产品的人；功能路线图无法挽回支付不足的人。

**方案-原因映射：**

| 取消原因 | 主要方案 | 备选方案 |
|------------|------------|----------------|
| 太贵了 | 折扣（2-3 个月的 20-30%） | 降级至更低价套餐 |
| 使用不够充分 | 暂停（1-3 个月） | 免费上手会话 |
| 缺少功能 | 路线图预览 + 时间线 | 替代方案指南 |
| 转向竞品 | 竞品对比 + 折扣 | 反馈会话 |
| 技术问题 | 立即升级至支持 | 信用 + 优先修复 |
| 临时 / 季节性 | 暂停订阅 | 临时降级 |
| 业务关闭 | 跳过方案（尊重现状） | — |

### 挽留方案类型

**折扣**
- 2-3 个月的 20-30% 折扣为最佳区间
- 避免 50% 以上的折扣（会训练客户为了折扣而取消后再次回来）
- 限时：“此方案在您离开此页面后过期”
- 显示节省的金额，而非仅百分比

**暂停订阅**
- 暂停时间最长 1-3 个月（更长的暂停很少恢复）
- 60-80% 的暂停用户最终会回到活跃状态
- 提前通知邮件自动恢复
- 保持其数据和设置完整

**套餐降级**
- 提供更低层级而非完全取消
- 展示保留内容 vs 失去内容
- 定位为“调整套餐尺寸”，而非“降级”
- 准备好后提供向上升级的简单路径

**功能解锁 / 延长**
- 解锁其尚未尝试的高级功能
- 延长高级层试用
- 对“价值不足”原因效果最佳

**个性化触达**
- 针对高价值账户（按 MRR 排在前 10-20%）
- 转接客户成功团队进行电话沟通
- 对个人公司由创始人发送个人邮件

## 流失预测与主动保留

最佳的挽留发生在客户点击“取消”之前。

### 风险信号

跟踪以下流失的前置指标：

| 信号 | 风险等级 | 时间范围 |
|--------|-----------|-----------|
| 登录频率下降 50% 以上 | 高 | 取消前 2-4 周 |
| 关键功能使用停止 | 高 | 取消前 1-3 周 |
| 支持工单激增后停止 | 高 | 取消前 1-2 周 |
| 邮件打开率下降 | 中 | 取消前 2-6 周 |
| 计费页面访问增加 | 高 | 取消前数天 |
| 团队席位被移除 | 高 | 取消前 1-2 周 |
| 发起数据导出 | 关键 | 取消前数天 |
| NPS 评分降至 6 以下 | 中 | 取消前 1-3 个月 |

### 健康评分模型

根据加权信号构建简单的健康评分（0-100）：

```
健康评分 = (
  登录频率评分 × 0.30 +
  功能使用评分   × 0.25 +
  支持反馈评分     × 0.15 +
  计费健康        × 0.15 +
  参与度评分      × 0.15
)
```

| 评分 | 状态 | 行动 |
|-------|--------|--------|
| 80-100 | 健康 | 升级机会 |
| 60-79 | 需关注 | 主动询问 |
| 40-59 | 高风险 | 干预活动 |
| 0-39 | 关键 | 个人触达 |

### 主动干预

**在客户考虑取消之前：**

| 触发条件 | 干预措施 |
|---------|-------------|
| 使用量下降 50% 以上，持续 2 周 | “我们注意到您未使用 [功能]。需要帮助吗？”邮件 |
| 临近套餐上限 | 升级提醒（非墙 — 付费墙负责处理此） |
| 14 天未登录 | 包含最新产品更新的重新参与邮件 |
| NPS 差评用户（0-6） | 24 小时内进行个人跟进 |
| 支持工单未解决超过 48 小时 | 升级 + 主动状态更新 |
| 30 天内进行年度续费 | 价值回顾邮件 + 续费确认 |

## 非自愿流失：支付恢复

支付失败导致了 30-50% 的流失，但也是最易恢复的。

### 催收栈

```
预催收 → 智能重试 → 催收邮件 → 宽限期 → 硬取消
```

### 预催收（预防失败）

- **卡片过期提醒**：在卡片过期前 30、15、7 天发送邮件
- **备用支付方式**：注册时提示提供第二种支付方式
- **卡片更新服务**：Visa/Mastercard 自动更新计划（减少硬性拒绝 30-50%）
- **预计费通知**：年度套餐在扣款前 3-5 天发送邮件

### 智能重试逻辑

并非所有失败都一样。根据拒绝类型制定重试策略：

| 拒绝类型 | 示例 | 重试策略 |
|------------|----------|----------------|
| 软性拒绝（临时） | 资金不足、处理超时 | 7-10 天内重试 3-5 次 |
| 硬性拒绝（永久） | 卡片被盗、账户已关闭 | 不重试 — 要求更换卡片 |
| 需要验证 | 3D Secure、SCA | 发送客户更新支付信息 |

**重试时间最佳实践：**
- 重试 1：失败后 24 小时
- 重试 2：失败后 3 天
- 重试 3：失败后 5 天
- 重试 4：失败后 7 天（伴随催收邮件升级）
- 重试 4 次后：硬取消并保留重新激活路径

**智能重试技巧：** 在原本成功的那天日期重试（如果第一天工作过，就在第一天重试）。Stripe Smart Retries 会自动处理此功能。

### 催收邮件序列

| 邮件 | 时间 | 语气 | 内容 |
|-------|--------|------|--------|
| 1 | Day 0（失败） | 友好提示 | “您的支付未成功。请更新卡片。” |
| 2 | Day 3 | 有帮助的提醒 | “快速提醒 — 更新支付以保持访问权限。” |
| 3 | Day 7 | 紧迫 | “您的账户将在 3 天后暂停。请立即更新。” |
| 4 | Day 10 | 最终警告 | “最后机会，保持账户活跃。” |

**催收邮件最佳实践：**
- 直接提供支付更新页面的链接（如可能，无需登录）
- 展示将失去的内容（其数据、团队访问权限）
- 不指责（用“您的支付失败”而非“您未能支付”）
- 包含支持联系方式，以便获得帮助
- 纯文本在催收场景中表现优于设计过的邮件

### 恢复基准

| 指标 | 差 | 平均 | 好 |
|--------|------|--------|------|
| 软性拒绝恢复 | <40% | 50-60% | 70%+ |
| 硬性拒绝恢复 | <10% | 20-30% | 40%+ |
| 整体支付恢复 | <30% | 40-50% | 60%+ |
| 预催收预防 | 无 | 10-15% | 20-30% |

有关完整催收手册及提供商特定设置，请参阅 [references/dunning-playbook.md](references/dunning-playbook.md)。

## 指标与度量

### 关键流失指标

| 指标 | 公式 | 目标 |
|--------|---------|--------|
| 月度流失率 | 流失客户数 / 月初客户数 | <5% B2C，<2% B2B |
| 收入流失（净） | (流失 MRR - 扩展 MRR) / 月初 MRR | 负向（净扩展） |
| 取消流程挽留率 | 挽留数 / 总取消会话 | 25-35% |
| 方案接受率 | 接受的方案数 / 展示的方案数 | 15-25% |
| 暂停恢复率 | 恢复数 / 总暂停用户 | 60-80% |
| 催收恢复率 | 恢复数 / 总失败支付 | 50-60% |
| 取消用时 | 从首次流失信号到取消的天数 | 跟踪趋势 |

### 队列分析

按以下维度对流失进行分段：
- **获取渠道** — 哪些渠道带来更黏性的客户？
- **套餐类型** — 哪些套餐流失最多？
- **留存时间** — 大多数取消发生在何时？（30、60、90 天？）
- **取消原因** — 哪些原因在增长？
- **挽留方案类型** — 哪些方案对不同细分群体最有效？

### 取消流程 A/B 测试

每次测试一个变量：

| 测试 | 假设 | 指标 |
|------|--------|--------|
| 折扣比例（20% vs 30%） | 更高的折扣挽留更多 | 挽留率、LTV 影响 |
| 暂停时长（1 个月 vs 3 个月） | 更长的暂停增加恢复率 | 恢复率 |
| 问卷位置（方案前 vs 方案后） | 先问卷个性化方案 | 挽留率 |
| 方案呈现方式（弹窗 vs 全页） | 全页获得更多关注 | 挽留率 |
| 文案语气（共情 vs 直接） | 共情减少摩擦 | 挽留率 |

**如何运行取消流程实验：** 使用 **ab-testing** 技能设计统计学严谨的测试。PostHog 适合取消流程实验 — 其功能开关可在服务端将用户分为不同流程，其漏斗分析跟踪取消流程的每一步（问卷 → 方案 → 接受/拒绝 → 确认）。参见 [PostHog 集成指南](../../tools/integrations/posthog.md) 了解设置。

## 常见错误

- **完全没有取消流程** — 即时取消会错失挽留机会。即使简单的问卷 + 一个方案也能节省 10-15%
- **使取消难以查找** — 隐藏取消按钮会引发不满和差评。许多司法管辖区要求易于取消（FTC 点击取消规则）
- **所有原因都用相同方案** — 无差别折扣无法解决“缺少功能”或“使用不足”的问题
- **折扣过深** — 50% 以上的折扣会训练客户为了折扣而取消后再次回来
- **忽视非自愿流失** — 通常占总流失的 30-50%，且是最易解决的
- **没有催收邮件** — 让支付失败静默取消账户
- **愧疚式文案** — “您确定要抛弃我们吗？”会损害品牌信任
- **不跟踪挽留方案的 LTV** — “挽留”的客户 30 天后流失，说明并未真正挽留
- **暂停时间过长** — 超过 3 个月的暂停很少恢复。需设置上限
- **取消后无路径** — 让重新激活变得容易，并触发挽回邮件，因为一些流失用户仍会想回来

如果在 `.agents/product-marketing.md`（或 `.claude/product-marketing.md`，或在旧版设置中使用 `product-marketing-context.md` 文件名）存在，请先阅读它，再进行提问。使用该背景信息，仅针对已覆盖的内容或与该任务特定的信息再提问。

收集以下背景信息（如未提供则提问）：

### 1. 当前流失情况
- 月度流失率是多少？（如已知，区分自愿与非自愿）
- 活跃订阅者有多少？
- 每位客户的平均 MRR 是多少？
- 目前有取消流程，还是取消会即时发生？

### 2. 计费与平台
- 使用的计费提供商？(Stripe、Chargebee、Paddle、Recurly、Braintree)
- 按月度、年度还是两者计费？
- 是否支持套餐暂停或降级？
- 是否有现有的保留工具？(Churnkey、ProsperStack、Raaft)

### 3. 产品与使用数据
- 是否跟踪每位用户的特性使用情况？
- 能否识别使用下降的节点？
- 过去流失中是否有取消原因数据？
- 激活指标是什么？（留存用户与流失用户做了什么区别？）

### 4. 限制条件
- 是 B2B 还是 B2C？（影响流程设计）
- 是否需要自助取消？（某些法规要求易于取消）
- 离场时的品牌语气？（共情、直接、幽默）

## 本技能如何使用

流失有两种类型，需要不同的策略：

| 类型 | 原因 | 解决方案 |
|------|-------|----------|
| **自愿** | 客户选择取消 | 取消流程、挽留方案、离场问卷 |
| **非自愿** | 支付失败 | 催收邮件、智能重试、卡片更新服务 |

自愿流失通常占总流失的 50-70%。非自愿流失占 30-50%，但往往更容易解决。

本技能支持三种模式：

1. **构建取消流程** — 从零设计，包含问卷、挽留方案和确认环节
2. **优化现有流程** — 分析取消数据并提升挽留率
3. **配置催收** — 通过重试和邮件序列恢复失败支付

## 取消流程设计

### 取消流程结构

每个取消流程遵循以下顺序：

```
触发 → 问卷 → 动态挽留方案 → 确认 → 取消后
```

**步骤 1：触发**
客户在账户设置中点击“取消订阅”。

**步骤 2：离场问卷**
询问客户取消的原因。这决定了展示哪个挽留方案。

**步骤 3：动态挽留方案**
根据客户原因展示有针对性的方案（如折扣、暂停、降级等）。

**步骤 4：确认**
如果客户仍希望取消，需明确确认，并附带账单周期结束时的提示信息。

**步骤 5：取消后**
明确预期，提供易于重新激活的路径，触发挽回序列。

### 离场问卷设计

离场问卷是基础。良好的原因分类：

| 原因 | 对你意味着什么 |
|--------|----------------|
| 太贵了 | 价格敏感，可能响应折扣或降级 |
| 使用不够充分 | 参与度低，可能响应暂停或上手帮助 |
| 缺少所需功能 | 产品缺口，展示路线图或替代方案 |
| 转向竞品 | 竞争压力，了解其提供的内容 |
| 技术问题 / Bug | 产品质量，升级至支持团队 |
| 临时 / 季节性需求 | 使用模式，提供暂停选项 |
| 业务关闭 / 变更 | 不可避免，学会优雅地放手 |
| 其他 | 兜底，包含文本框 |

**问卷最佳实践：**
- 1 个问题，单选加可选自由文本
- 最多 5-8 个原因选项（避免决策疲劳）
- 将最常见原因放在前面（每季度审查数据）
- 不要让用户感到愧疚
- “帮助我们改进”的框架比“你为何离开”更有效

### 动态挽留方案

核心洞察：**将方案与原因匹配。** 折扣无法挽回不使用产品的人；功能路线图无法挽回支付不足的人。

**方案-原因映射：**

| 取消原因 | 主要方案 | 备选方案 |
|------------|------------|----------------|
| 太贵了 | 折扣（2-3 个月的 20-30%） | 降级至更低价套餐 |
| 使用不够充分 | 暂停（1-3 个月） | 免费上手会话 |
| 缺少功能 | 路线图预览 + 时间线 | 替代方案指南 |
| 转向竞品 | 竞品对比 + 折扣 | 反馈会话 |
| 技术问题 | 立即升级至支持 | 信用 + 优先修复 |
| 临时 / 季节性 | 暂停订阅 | 临时降级 |
| 业务关闭 | 跳过方案（尊重现状） | — |

### 挽留方案类型

**折扣**
- 2-3 个月的 20-30% 折扣为最佳区间
- 避免 50% 以上的折扣（会训练客户为了折扣而取消后再次回来）
- 限时：“此方案在您离开此页面后过期”
- 显示节省的金额，而非仅百分比

**暂停订阅**
- 暂停时间最长 1-3 个月（更长的暂停很少恢复）
- 60-80% 的暂停用户最终会回到活跃状态
- 提前通知邮件自动恢复
- 保持其数据和设置完整

**套餐降级**
- 提供更低层级而非完全取消
- 展示保留内容 vs 失去内容
- 定位为“调整套餐尺寸”，而非“降级”
- 准备好后提供向上升级的简单路径

**功能解锁 / 延长**
- 解锁其尚未尝试的高级功能
- 延长高级层试用
- 对“价值不足”原因效果最佳

**个性化触达**
- 针对高价值账户（按 MRR 排在前 10-20%）
- 转接客户成功团队进行电话沟通
- 对个人公司由创始人发送个人邮件

### 取消流程 UI 模式

```
┌─────────────────────────────────────┐
│  We're sorry to see you go          │
│                                     │
│  What's the main reason you're      │
│  cancelling?                        │
│                                     │
│  ○ Too expensive                    │
│  ○ Not using it enough              │
│  ○ Missing a feature I need         │
│  ○ Switching to another tool        │

│  ○ Temporary / don't need right now │
│  ○ Other: [____________]            │
│                                     │
│  [Continue]                         │
│  [Never mind, keep my subscription] │
└─────────────────────────────────────┘
         ↓ (选择“太贵了”)
┌─────────────────────────────────────┐
│  What if we could help?             │
│                                     │
│  We'd love to keep you. Here's a    │
│  special offer:                     │
│                                     │
│  ┌───────────────────────────────┐  │
│  │  25% off for the next 3 months│  │
│  │  Save $XX/month               │  │
│  │                               │  │
│  │  [Accept Offer]               │  │
│  └───────────────────────────────┘  │
│                                     │
│  Or switch to [Basic Plan] at       │
│  $X/month →                         │
│                                     │
│  [No thanks, continue cancelling]   │
└─────────────────────────────────────┘
```

**UI 原则：**
- 保持“继续取消”选项可见（不使用暗黑模式）
- 一个主要方案 + 一个备选方案，而非一堆选项
- 显示具体的金额节省，而非抽象百分比
- 尽可能使用客户的姓名和账户数据
- 移动端友好（许多取消操作在移动端进行）

有关按行业和计费提供商的具体取消流程模式，请参阅 [references/cancel-flow-patterns.md](references/cancel-flow-patterns.md)。

## 流失预测与主动保留

最佳的挽留发生在客户点击“取消”之前。

### 风险信号

跟踪以下流失的前置指标：

| 信号 | 风险等级 | 时间范围 |
|--------|-----------|-----------|
| 登录频率下降 50% 以上 | 高 | 取消前 2-4 周 |
| 关键功能使用停止 | 高 | 取消前 1-3 周 |
| 支持工单激增后停止 | 高 | 取消前 1-2 周 |
| 邮件打开率下降 | 中 | 取消前 2-6 周 |
| 计费页面访问增加 | 高 | 取消前数天 |
| 团队席位被移除 | 高 | 取消前 1-2 周 |
| 发起数据导出 | 关键 | 取消前数天 |
| NPS 评分降至 6 以下 | 中 | 取消前 1-3 个月 |

### 健康评分模型

根据加权信号构建简单的健康评分（0-100）：

```
健康评分 = (
  登录频率评分 × 0.30 +
  功能使用评分   × 0.25 +
  支持反馈评分     × 0.15 +
  计费健康        × 0.15 +
  参与度评分      × 0.15
)
```

| 评分 | 状态 | 行动 |
|-------|--------|--------|
| 80-100 | 健康 | 升级机会 |
| 60-79 | 需关注 | 主动询问 |
| 40-59 | 高风险 | 干预活动 |
| 0-39 | 关键 | 个人触达 |

### 主动干预

**在客户考虑取消之前：**

| 触发条件 | 干预措施 |
|---------|-------------|
| 使用量下降 50% 以上，持续 2 周 | “我们注意到您未使用 [功能]。需要帮助吗？”邮件 |
| 临近套餐上限 | 升级提醒（非墙 — 付费墙负责处理此） |
| 14 天未登录 | 包含最新产品更新的重新参与邮件 |
| NPS 差评用户（0-6） | 24 小时内进行个人跟进 |
| 支持工单未解决超过 48 小时 | 升级 + 主动状态更新 |
| 30 天内进行年度续费 | 价值回顾邮件 + 续费确认 |

## 非自愿流失：支付恢复

支付失败导致了 30-50% 的流失，但也是最易恢复的。

### 催收栈

```
预催收 → 智能重试 → 催收邮件 → 宽限期 → 硬取消
```

### 预催收（预防失败）

- **卡片过期提醒**：在卡片过期前 30、15、7 天发送邮件
- **备用支付方式**：注册时提示提供第二种支付方式
- **卡片更新服务**：Visa/Mastercard 自动更新计划（减少硬性拒绝 30-50%）
- **预计费通知**：年度套餐在扣款前 3-5 天发送邮件

### 智能重试逻辑

并非所有失败都一样。根据拒绝类型制定重试策略：

| 拒绝类型 | 示例 | 重试策略 |
|------------|----------|----------------|
| 软性拒绝（临时） | 资金不足、处理超时 | 7-10 天内重试 3-5 次 |
| 硬性拒绝（永久） | 卡片被盗、账户已关闭 | 不重试 — 要求更换卡片 |
| 需要验证 | 3D Secure、SCA | 发送客户更新支付信息 |

**重试时间最佳实践：**
- 重试 1：失败后 24 小时
- 重试 2：失败后 3 天
- 重试 3：失败后 5 天
- 重试 4：失败后 7 天（伴随催收邮件升级）
- 重试 4 次后：硬取消并保留重新激活路径

**智能重试技巧：** 在原本成功的那天日期重试（如果第一天工作过，就在第一天重试）。Stripe Smart Retries 会自动处理此功能。

### 催收邮件序列

| 邮件 | 时间 | 语气 | 内容 |
|-------|--------|------|--------|
| 1 | Day 0（失败） | 友好提示 | “您的支付未成功。请更新卡片。” |
| 2 | Day 3 | 有帮助的提醒 | “快速提醒 — 更新支付以保持访问权限。” |
| 3 | Day 7 | 紧迫 | “您的账户将在 3 天后暂停。请立即更新。” |
| 4 | Day 10 | 最终警告 | “最后机会，保持账户活跃。” |

**催收邮件最佳实践：**
- 直接提供支付更新页面的链接（如可能，无需登录）
- 展示将失去的内容（其数据、团队访问权限）
- 不指责（用“您的支付失败”而非“您未能支付”）
- 包含支持联系方式，以便获得帮助
- 纯文本在催收场景中表现优于设计过的邮件

### 恢复基准

| 指标 | 差 | 平均 | 好 |
|--------|------|--------|------|
| 软性拒绝恢复 | <40% | 50-60% | 70%+ |
| 硬性拒绝恢复 | <10% | 20-30% | 40%+ |
| 整体支付恢复 | <30% | 40-50% | 60%+ |
| 预催收预防 | 无 | 10-15% | 20-30% |

有关完整催收手册及提供商特定设置，请参阅 [references/dunning-playbook.md](references/dunning-playbook.md)。

## 指标与度量

### 关键流失指标

| 指标 | 公式 | 目标 |
|--------|---------|--------|
| 月度流失率 | 流失客户数 / 月初客户数 | <5% B2C，<2% B2B |
| 收入流失（净） | (流失 MRR - 扩展 MRR) / 月初 MRR | 负向（净扩展） |
| 取消流程挽留率 | 挽留数 / 总取消会话 | 25-35% |
| 方案接受率 | 接受的方案数 / 展示的方案数 | 15-25% |
| 暂停恢复率 | 恢复数 / 总暂停用户 | 60-80% |
| 催收恢复率 | 恢复数 / 总失败支付 | 50-60% |
| 取消用时 | 从首次流失信号到取消的天数 | 跟踪趋势 |

### 队列分析

按以下维度对流失进行分段：
- **获取渠道** — 哪些渠道带来更黏性的客户？
- **套餐类型** — 哪些套餐流失最多？
- **留存时间** — 大多数取消发生在何时？（30、60、90 天？）
- **取消原因** — 哪些原因在增长？
- **挽留方案类型** — 哪些方案对不同细分群体最有效？

### 取消流程 A/B 测试

每次测试一个变量：

| 测试 | 假设 | 指标 |
|------|--------|--------|
| 折扣比例（20% vs 30%） | 更高的折扣挽留更多 | 挽留率、LTV 影响 |
| 暂停时长（1 个月 vs 3 个月） | 更长的暂停增加恢复率 | 恢复率 |
| 问卷位置（方案前 vs 方案后） | 先问卷个性化方案 | 挽留率 |
| 方案呈现方式（弹窗 vs 全页） | 全页获得更多关注 | 挽留率 |
| 文案语气（共情 vs 直接） | 共情减少摩擦 | 挽留率 |

**如何运行取消流程实验：** 使用 **ab-testing** 技能设计统计学严谨的测试。PostHog 适合取消流程实验 — 其功能开关可在服务端将用户分为不同流程，其漏斗分析跟踪取消流程的每一步（问卷 → 方案 → 接受/拒绝 → 确认）。参见 [PostHog 集成指南](../../tools/integrations/posthog.md) 了解设置。

## 常见错误

- **完全没有取消流程** — 即时取消会错失挽留机会。即使简单的问卷 + 一个方案也能节省 10-15%
- **使取消难以查找** — 隐藏取消按钮会引发不满和差评。许多司法管辖区要求易于取消（FTC 点击取消规则）
- **所有原因都用相同方案** — 无差别折扣无法解决“缺少功能”或“使用不足”的问题
- **折扣过深** — 50% 以上的折扣会训练客户为了折扣而取消后再次回来
- **忽视非自愿流失** — 通常占总流失的 30-50%，且是最易解决的
- **没有催收邮件** — 让支付失败静默取消账户
- **愧疚式文案** — “您确定要抛弃我们吗？”会损害品牌信任
- **不跟踪挽留方案的 LTV** — “挽留”的客户 30 天后流失，说明并未真正挽留
- **暂停时间过长** — 超过 3 个月的暂停很少恢复。需设置上限
- **取消后无路径** — 让重新激活变得容易，并触发挽回邮件，因为一些流失用户仍会想回来

| 工具 | 适用场景 | 关键功能 |
