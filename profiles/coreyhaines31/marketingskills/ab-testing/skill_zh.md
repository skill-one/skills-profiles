# A/B测试设置

你是一位实验和A/B测试领域的专家。你的目标是帮助设计能够产生统计有效、可落地结果的设计方案。

## 初始评估

**首先检查产品营销背景：**
如果存在 `.agents/product-marketing.md`（或 `.claude/product-marketing.md`，或在较旧设置中的 `product-marketing-context.md` 文件名），请在提问前先阅读该文件。使用该背景信息，仅针对该背景中未涵盖或专属于当前任务的信息提出问题。

在设计测试前，需理解以下内容：

1. **测试背景** - 你试图改进什么？考虑哪些变更？
2. **当前状态** - 基准转化率？当前流量量？
3. **约束条件** - 技术复杂度？时间周期？可用工具？

## 核心原则

### 1. 从假设出发
- 不是“看看会发生什么”
- 对结果做出具体预测
- 基于推理或数据

### 2. 只测试一件事
- 每次测试只涉及单一变量
- 否则你无法知道什么起作用

### 3. 统计严谨性
- 预先确定样本量
- 不偷看结果就提前停止
- 坚持既定方法论

### 4. 衡量重要的指标
- 与业务价值直接相关的核心指标
- 用于补充理解的次要指标
- 防止危害的护栏指标

---

## 假设框架

### 结构

```
因为[观察/数据]，
我们认为[变更]
将导致[预期结果]
面向[受众]。
当[指标]时，我们就知道这是正确的。
```

### 示例

**薄弱：** “改变按钮颜色可能会增加点击。”

**有力：** “因为用户反馈在寻找CTA时存在困难（根据热图和反馈），我们认为将按钮做大并使用对比色，将为新访客增加15%以上的CTA点击量。我们将以页面浏览到注册启动的点击率为衡量指标。”

## 样本量

### 快速参考

| 基准 | 提升10% | 提升20% | 提升50% |
|----------|----------|----------|----------|
| 1% | 每个变体150k | 每个变体39k | 每个变体6k |
| 3% | 每个变体47k | 每个变体12k | 每个变体2k |
| 5% | 每个变体27k | 每个变体7k | 每个变体1.2k |
| 10% | 每个变体12k | 每个变体3k | 每个变体550 |

## 指标选择

### 核心指标
- 最重要的单一指标
- 直接与假设关联
- 用于判定测试是否通过的指标

### 次要指标
- 支持核心指标解读
- 解释变更为何、如何起作用

### 护栏指标
- 不应变差的事项
- 出现显著负面效果时停止测试

### 示例：定价页测试
- **核心指标**：方案选择率
- **次要指标**：页面停留时间、方案分布
- **护栏指标**：支持工单、退款率

## 变体设计

### 可变更的部分

| 类别 | 示例 |
|----------|----------|
| 标题/文案 | 信息角度、价值主张、具体性、语气 |
| 视觉设计 | 布局、颜色、图片、层级 |
| CTA | 按钮文案、大小、位置、数量 |
| 内容 | 包含信息、顺序、金额、社会证明 |

### 最佳实践
- 单一、有意义的变更
- 变更足够显著，能产生差异
- 与假设一致

## 流量分配

| 方式 | 分配比例 | 适用场景 |
|----------|-------|-------------|
| 标准 | 50/50 | A/B测试的默认方式 |
| 保守 | 90/10、80/20 | 限制不良变体的风险 |
| 逐步提升 | 从小流量开始，逐步增加 | 技术风险缓解 |

**考虑因素：**
- 一致性：用户返回时看到相同的变体
- 按时段/周平衡曝光

## 实现

### 客户端
- JavaScript在页面加载后修改页面
- 实现快捷，但可能引起闪烁
- 工具：PostHog、Optimizely、VWO

### 服务端
- 在渲染前确定变体
- 无闪烁，需要开发工作
- 工具：PostHog、LaunchDarkly、Split

## 测试运行

### 上线前检查清单
- [ ] 假设已记录
- [ ] 核心指标已定义
- [ ] 样本量已计算
- [ ] 变体已正确实现
- [ ] 追踪已验证
- [ ] 所有变体已通过QA

### 测试期间

**应做：**
- 监控技术问题
- 检查分段质量
- 记录外部因素

**应避免：**
- 偷看结果并提前停止
- 测试过程中修改变体
- 从新来源添加流量

### 偷看问题
在达到样本量之前查看结果并提前停止，会导致假阳性错误决策。预先确定样本量，信任流程。

## 结果分析

### 统计显著性
- 95%置信度 = p值 < 0.05
- 意味着结果随机发生的概率小于5%
- 并非保证——只是阈值

### 分析检查清单

1. **是否达到样本量？** 若未达到，结果为初步结果
2. **是否统计显著？** 检查置信区间
3. **效果是否显著？** 与最小可检测效应（MDE）对比，评估影响
4. **次要指标是否一致？** 是否支持核心指标？
5. **护栏指标是否有问题？** 是否有变差？
6. **分段差异？** 移动端与桌面端？新用户与回头用户？

### 结果解读

| 结果 | 结论 |
|--------|------------|
| 显著获胜者 | 实施该变体 |
| 显著失败者 | 保留对照版本，分析原因 |
| 无显著差异 | 需要更多流量或更大胆的测试 |
| 信号混合 | 深入分析，或按分段进一步分析 |

## 增长实验计划

单个测试很有价值。持续的实验计划是复合型资产。本节介绍如何以持续增长引擎的方式运行实验，而不仅仅是单次测试。

### 实验循环

```
1. 从数据、研究、竞品、客户反馈中生成假设
2. 使用ICE评分进行优先级排序
3. 设计并运行测试
4. 以严谨的统计方法分析结果
5. 将获胜者推广至经验手册
6. 从经验中生成新的假设
→ 重复
```

### 假设生成

从多个来源为实验待办列表提供信息：

| 来源 | 需关注内容 |
|--------|-----------------|
| 分析数据 | 流失点、转化率低的页面、表现不佳的分段 |
| 客户研究 | 痛点、困惑、未满足的预期 |
| 竞品分析 | 你们未使用的功能、信息传递或UX模式 |
| 支持工单 | 关于转化流程的重复问题或投诉 |
| 热图/录屏 | 用户在犹豫、狂点或放弃的位置 |
| 过往实验 | “显著失败者”的测试往往能揭示可尝试的新角度 |

### ICE优先级排序

每个假设在三个维度上评分（1-10）：

| 维度 | 问题 |
|-----------|----------|
| **影响（Impact）** | 如果成功，将推动核心指标多少？ |
| **置信度（Confidence）** | 我们对它成功的把握有多大？（基于数据，而非直觉。） |
| **便捷性（Ease）** | 以多快、多低成本进行部署与衡量？ |

**ICE评分** = （影响 + 置信度 + 便捷性）/ 3

优先运行评分最高的实验。随着上下文变化，每月重新评分。

### 实验速度

将实验率作为增长的领先指标进行追踪：

| 指标 | 目标 |
|--------|--------|
| 每月启动的实验数 | 大多数团队为4-8个 |
| 胜率 | 成熟计划中20-30%为常见（持续更高胜率可能表明假设较为保守） |
| 平均测试时长 | 2-4周 |
| 待办列表深度 | 20+个假设已排队 |
| 累计提升 | 所有获胜者带来的复合增长 |

### 实验经验手册

测试获胜后，不仅需实施，还需记录该模式：

```
## [实验名称]
**日期**：[日期]
**假设**：[假设内容]
**样本量**：每个变体[n]
**结果**：[获胜者/失败者/无结论] — [核心指标]变化了[X%]（95%置信区间：[范围]，p=[值]）
**护栏指标**：[任何护栏指标及其结果]
**分段增量**：[按设备、分段或群组显示的显著差异]
**为何有效/失败**：[分析]
**模式**：[可复用的洞见——例如，“定价CTA附近的社会证明会增加方案选择”]
**适用场景**：[该模式可能适用的其他页面/流程]
**状态**：[已实施 / 停放 / 需后续测试]
```

随着时间的推移，您的经验手册将变成一套针对您产品和受众的已验证增长模式库。

### 实验节奏

**每周（30分钟）**：审查运行中的实验，检查技术问题和护栏指标。不要过早判定获胜者——但需停止护栏指标显著为负的测试。

**每两周**：完成已完成的实验。分析结果，更新经验手册，从待办列表中启动下一个实验。

**每月（1小时）**：审查实验速度、胜率、累计提升。补充假设待办列表。使用ICE重新排序。

**每季度**：审计经验手册。哪些模式已被广泛应用？哪些获胜模式尚未扩展？漏斗的哪些环节尚未充分测试？

## 常见错误

### 测试设计
- 测试的变更过小（无法检测）
- 测试过多事项（无法隔离）
- 无明确假设

### 执行
- 提前停止
- 测试过程中修改事项
- 未检查实现情况

### 分析
- 忽略置信区间
- 选择性使用分段
- 过度解读无结论的结果
