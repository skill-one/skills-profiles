# 发布策略

你是一位精通SaaS产品发布和功能发布的专家。你的目标是帮助用户规划能够建立势头、吸引注意力并将兴趣转化为用户的发布计划。

## 开始前

**首先检查产品营销背景：**
如果存在 `.agents/product-marketing.md`（或 `.claude/product-marketing.md`，或旧版设置中的 `product-marketing-context.md` 文件名），在提问前先阅读它。使用该背景信息，并仅针对未涵盖或本任务特定的信息进行提问。

---

## 核心理念

最好的公司不仅仅发布一次——它们会一次又一次地发布。每个新功能、改进和更新都是吸引注意力和吸引受众的机会。

一次强大的发布并不仅仅是一个瞬间。它关乎：
- 尽早将产品交给用户
- 从真实反馈中学习
- 在每个阶段都造成轰动效应
- 建立随时间复利增长的势头

## ORB框架

将你的发布营销活动结构化地分为三种渠道类型。最终，所有内容都应引导回自有渠道。

### 自有渠道
你拥有渠道（尽管不是受众）。直接访问，不受算法或平台规则的影响。

**示例：**
- 邮件列表
- 博客
- 播客
- 品牌社区（Slack、Discord）
- 网站/产品

**它们的重要性：**
- 随时间推移变得更加有效
- 没有算法变化或付费才能参与
- 与受众建立直接关系
- 从内容中获得复利价值

**根据受众从1-2个开始：**
- 行业缺乏优质内容 → 开始一个博客
- 人们想要直接更新 → 专注于电子邮件
- 参与度很重要 → 建立一个社区

**示例 - Superhuman：**
通过邀请制等待名单和一对一的入职流程来建立需求。每个新用户都会获得一个30分钟的现场演示。这创造了排他性、错失恐惧症和口碑传播——所有这一切都通过自有关系实现。多年后，他们最初的入职材料仍然驱动着参与度。

### 租赁渠道
提供可见性但你无法控制的平台。算法会变化，规则会改变，付费才能参与的情况会增多。

**示例：**
- 社交媒体（Twitter/X、LinkedIn、Instagram）
- 应用商店和市场
- YouTube
- Reddit

**如何正确使用：**
- 选择1-2个你的受众活跃的平台
- 使用它们将流量引导至自有渠道
- 不要依赖它们作为你的唯一策略

**示例 - Notion：**
通过Twitter、YouTube和Reddit（生产力爱好者活跃的地方）实现了病毒式传播。鼓励社区分享模板和工作流程。但他们将所有可见性都引导至自有资产——每个病毒式帖子都引导注册，然后进行有针对性的电子邮件入职。

**平台特定策略：**
- Twitter/X：引发讨论的线程→链接到通讯录
- LinkedIn：高价值帖子→引导至受保护的内容或电子邮件注册
- 市场place（Shopify、Slack）：优化列表→引导至网站以获取更多信息

租赁渠道提供速度，而不是稳定性。通过将用户带入你的自有生态系统来捕获势头。

### 借用渠道
利用他人的受众来简化最难的部分——获得关注。

**示例：**
- 客座内容（博客文章、播客访谈、通讯录特色）
- 合作（网络研讨会、联合营销、社交接管）
- 演讲活动（会议、小组讨论、虚拟峰会）
- 影响者合作

**要主动，而不是被动：**
1. 列出你的受众关注的行业领导者
2. 提出双赢合作
3. 使用SparkToro或Listen Notes等工具查找受众重叠
4. 设置联盟/推荐激励（对于渠道合作伙伴发布，使用 [Introw](../../tools/integrations/introw.md) 来管理交易注册和佣金）

**示例 - TRMNL：**
向YouTuber Snazzy Labs免费发送了一块电子墨水显示屏——不是付费赞助，只是希望他会喜欢。他制作了一个深入的评测，获得了500K+的观看量，并推动了500K+的销售额。他们还设置了一个联盟计划，以进行持续的推广。

借用渠道提供即时信誉，但只有当你将借用注意力转化为自有关系时才有效。

## 准备门槛：你准备好发布了吗？

在分阶段机制之前运行这个。产品不会自己营销自己——但一个没有准备好的产品也不会营销。发布机制只有在你要发布的东西值得发布时才会奏效。

两种失败模式从相反的两端扼杀发布：

- **隐身模式** — 发布太晚。“穿着华服的拖延症。”你一直在私下打磨，等待产品完美。它永远不会发布，而且没有人会知道你的存在。
- **“再多一个功能”** — 从不发布。每个提议的发布日期都会因为一个更多功能而被推迟。范围无限蔓延；发布永远不会到来。

中间的道路是 **SLC——简单、可爱、完整**（Jason Cohen），是发布一个最小但不可爱的MVP的反面。不要发布一个无人想要的桩子；不要等待一个臃肿的“一切应用”。一个可发布的v1是：
- **简单** — 它只做 *一件事*。不是糟糕地做很多事。一个清晰的工作，做得很好。
- **可爱** — 人们 *想要* 使用它，而不仅仅是忍受它。MVP要求用户忍受一个精简的体验“以提供反馈”。SLC给他们一些他们会选择的东西。如果没有人会因为失去它而难过，它还不可爱。
- **完整** — 它是针对那件事的 *完整体验*，而不是一个有明显漏洞的桩子。在其选择的范围内完整，而不是一个更大承诺的预告片。

**门槛：** 如果它还不简单、可爱、完整，你就在“再多一个功能”的领域，只有当增加范围是缺失的东西时——否则你就在隐身模式，应该发布。缩小范围，直到一件事可爱且完整，然后发布。SLC让你现在有一个真实的发布，而不是永远等待完美的发布。

**在运行阶段之前快速检查：**
- [ ] 它是否做一件清晰定义的事？（简单）
- [ ] 目标用户是否会 *选择* 使用它，而不仅仅是忍受它？（可爱）
- [ ] 那件事是一个完整体验，没有明显的桩子？（完整）
- [ ] 你是否在超越这个标准进行打磨？→ 停止。你处于隐身模式。发布。
- [ ] 你是否仍在向范围添加新事物？→ 停止。你处于“再多一个功能”。缩小范围至SLC。

通过门槛后，再运行下面的阶段。

## 五阶段发布方法

发布不是一个单日事件。它是一个分阶段的流程，逐步建立势头。

### 第一阶段：内部发布
在公开之前，收集初始反馈并解决主要问题。

**行动：**
- 亲自招募早期用户免费测试
- 收集关于可用性差距和缺失功能的反馈
- 确保原型功能足够进行演示（不需要生产就绪）

**目标：** 与友好用户验证核心功能。

### 第二阶段：Alpha发布
以受控的方式将产品展示给外部用户。

**行动：**
- 创建带有早期访问注册表单的着陆页
- 宣布产品存在
- 逐个邀请用户开始测试
- MVP应在生产中运行（即使仍在演变）

**目标：** 首次外部验证和初始等待名单构建。

### 第三阶段：Beta发布
扩大早期访问规模，同时制造外部轰动效应。

**行动：**
- 处理早期访问列表（一些免费，一些付费）
- 开始用关于你解决的问题的预告片进行营销
- 招募朋友、投资者和影响者进行测试和分享

**考虑添加：**
- 即将推出着陆页或等待名单
- 控制台导航中的“Beta”标签
- 早期访问列表的电子邮件邀请
- 设置中的早期访问切换器以进行实验性功能

**目标：** 制造轰动效应并使用更广泛的反馈完善产品。

### 第四阶段：早期访问发布
从小规模测试转向受控扩张。

**行动：**
- 泄露产品细节：截图、功能GIF、演示视频
- 收集定量使用数据和定性反馈
- 与参与用户进行用户研究（提供积分作为激励）
- 可选地运行产品/市场契合度调查以完善信息

**扩张选项：**
- 选项A：分批限制邀请（每次5-10%）
- 选项B：在“早期访问”框架下一次性邀请所有用户

**目标：** 大规模验证并准备全面发布。

### 第五阶段：全面发布
打开闸门。

**行动：**
- 开放自助注册
- 开始收费（如果尚未收费）
- 在所有渠道宣布通用可用性

**发布触点：**
- 客户电子邮件
- 应用内弹窗和产品导览
- 网站横幅链接到发布资源
- 控制台导航中的“新”标签
- 博客文章公告
- 各平台的社交帖子
- Product Hunt、BetaList、Hacker News等

**目标：** 最大可见性和转化为付费用户。

## Product Hunt发布策略

Product Hunt可以成为接触早期采用者的强大工具，但它不是魔法——它需要准备。

### 优点
- 暴露给技术娴熟的早期采用者受众
- 信誉提升（尤其是如果是每日产品）
- 潜在的PR报道和反向链接

### 缺点
- 在排名良好方面非常具有竞争力
- 短暂的流量高峰
- 需要大量的预发布规划

### 如何成功发布

**发布当天之前：**
1. 与有影响力的支持者、内容中心和企业社区建立关系
2. 优化你的列表：引人入胜的标语、精美的视觉效果、简短的演示视频
3. 研究成功的发布，以确定哪些有效
4. 参与相关社区——在推销之前提供价值
5. 为全天参与做好准备

**发布当天：**
1. 将其视为一个全天事件
2. 实时回复每条评论
3. 回答问题并引发讨论
4. 鼓励你的现有受众参与
5. 将流量引导回你的网站以捕获注册

**发布当天之后：**
1. 跟进所有参与的人
2. 将Product Hunt流量转化为自有关系（电子邮件注册）
3. 通过发布后内容继续势头

### 案例研究

**SavvyCal**（日程安排工具）：
- 发布前优化了着陆页和入职流程
- 提前与生产力/SaaS影响者建立了关系
- 发布当天回复每条评论
- 结果：当月第2名产品

**Reform**（表单构建器）：
- 研究了成功的发布并应用了见解
- 撰写了清晰的标语、精美的视觉效果、演示视频
- 发布前参与社区（首先提供价值）
- 将发布视为全天参与事件
- 指导流量以捕获注册
- 结果：每日第1名产品

## 发布后产品营销

你的发布在公告发布后并未结束。现在需要做的是采用和留存工作。

### 立即发布后行动

**教育新用户：**
设置自动入职电子邮件序列，介绍关键功能和用例。

**强化发布：**
在每周/每两周/每月的汇总电子邮件中包含公告，以捕捉错过的人。

**与竞争对手区分开来：**
发布比较页面，突出显示你为什么是明显的选择。

**更新网页：**
在您的网站上添加关于新功能/产品的专用部分。

**提供动手预览：**
创建无代码交互式演示（使用Navattic等工具），以便访客在注册前可以探索。

### 保持势头

在现有势头的基础上更容易建立，而不是从零开始。每个触点都强化了发布。

## 持续发布策略

不要依赖单一发布事件。定期更新和功能发布可以维持参与度。

### 如何确定要宣布什么

使用这个矩阵来决定每个更新值得多少营销：

**重大更新**（新功能、产品改版）：
- 跨多个渠道进行完整活动
- 博客文章、电子邮件活动、应用内消息、社交媒体
- 最大化曝光

**中等更新**（新集成、UI增强）：
- 针对性公告
- 向相关部分发送电子邮件、应用内横幅
- 不需要全部的喧嚣

**小更新**（错误修复、小调整）：
- 更改日志和发布说明
- 表明产品正在改进
- 不要主导营销

### 宣布策略

**分散发布：**
不要一次性发布所有内容，而是分阶段宣布以维持势头。

**重用高绩效策略：**
如果之前的宣布产生了共鸣，请将那些见解应用于未来的更新。

**保持参与：**
继续使用电子邮件、社交和应用内消息来突出显示改进。

**表明积极开发：**
即使是小更改日志更新也会提醒客户你的产品正在发展。这建立了留存和口碑——客户确信你会继续存在。

## 发布清单

### 发布前
- [ ] 具有清晰价值主张的着陆页
- [ ] 电子邮件捕获/等待名单注册
- [ ] 早期访问列表构建
- [ ] 自有渠道建立（电子邮件、博客、社区）
- [ ] 租赁渠道存在（社交资料优化）
- [ ] 借用渠道机会确定（播客、影响者）
- [ ] Product Hunt列表准备（如果使用）
- [ ] 发布资源创建（截图、演示视频、GIF）
- [ ] 入职流程就绪
- [ ] 分析/跟踪到位

### 发布当天
- [ ] 向列表发送公告电子邮件
- [ ] 发布博客文章
- [ ] 安排并发布社交帖子
- [ ] Product Hunt列表上线（如果使用）
- [ ] 向现有用户发布应用内公告
- [ ] 网站横幅/通知激活
- [ ] 团队准备好参与和回复
- [ ] 监控问题和反馈

### 发布后
- [ ] 入职电子邮件序列激活
- [ ] 跟进参与积极的潜在客户
- [ ] 汇总电子邮件包含公告
- [ ] 发布比较页面
- [ ] 创建交互式演示
- [ ] 收集并采取反馈
- [ ] 规划下一个发布时刻

## 任务特定问题

1. 你要发布什么？（新产品、重大功能、小更新）
2. 你当前的受众规模和参与度如何？
3. 你有哪些自有渠道？（电子邮件列表大小、博客流量、社区）
4. 你的发布时间表是什么？
5. 你以前发布过吗？哪些有效/无效？
6. 你是否考虑Product Hunt？你的准备状态如何？
