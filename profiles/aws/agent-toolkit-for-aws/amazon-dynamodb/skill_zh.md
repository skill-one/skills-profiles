# DynamoDB 公理

本文档是一套 DynamoDB 应用的设计公理。它旨在供一个对应用程序没有任何其他背景知识的代理阅读，并用于生成一个有说服力的数据层设计。

## 护栏 — 本技能自身文件存放位置（MCP 与本地安装）

此技能可以通过两种方式加载，它们从不同的位置解析技能自身的捆绑文件。在阅读参考或运行脚本之前，确定技能是如何加载的：

- **通过 AWS MCP `retrieve_skill` 工具加载：** 技能没有安装在本地文件系统中。您必须通过带有 `file` 参数的 `retrieve_skill` 来获取每个参考或脚本（例如 `file="references/vector-search.md"` 或 `file="scripts/calculate_costs.py"`），并从返回的内容中运行脚本。不要在本地 `file_read` 这些路径——它们在磁盘上不存在。
- **本地安装**（例如 `.kiro/skills/amazon-dynamodb/` 或 `~/.claude/skills/amazon-dynamodb/`）：使用相对路径从本地技能目录读取和运行文件。

这种区别仅适用于技能自身的捆绑文件。用户数据和会话工件始终从用户的当前工作目录读取和写入。永远不要通过 `retrieve_skill` 获取或写入客户数据。

另外，这些文件存放的位置：当此技能验证设计、部署临时表或对其进行基准测试时，它会调用真实的 AWS API。**当可用时，建议使用 AWS MCP 服务器**——它在主机之间提供一致的凭证处理和区域解析。它**不是必需的**：这里的每个脚本都使用 boto3 和 AWS CLI 对环境凭证链进行操作，因此当没有 MCP 服务器时，该技能可以保持不变地工作。

下面的 `${SKILL_DIR}` 解析适用于**本地安装**的情况：通过 MCP 没有目录可以解析，此技能捆绑的脚本不能从返回的字符串中执行——因此成本估算或实时验证需要本地安装形式。

## 解析技能自身的路径

此技能与主机无关——它可以在 Claude Code、Kiro、Codex、Cursor、普通终端或 CI 下运行。它在磁盘上的位置取决于主机（`~/.claude/skills/…`、`~/.kiro/…`、`~/.codex/…`、`~/.cursor/…`、一个代码库检出、任何地方）。代理的工作目录是**用户的项目的**，而不是技能包，所以像 `scripts/calculate_costs.py` 这样的相对路径不会解析。在此文档中，`${SKILL_DIR}` 表示**包含此 SKILL.md 文件的目录的绝对路径**（技能根目录，其中包含 `scripts/` 和 `references/`）。

**每次会话解析一次 `${SKILL_DIR}`，然后重复使用它。** 选择在您的主机中第一个可行的方法：

1. **您已经知道它。** 您从路径加载了 SKILL.md——`${SKILL_DIR}` 是该文件所在的目录。这是最可靠的信息来源；优先选择它。
2. **环境变量。** 如果 `$DDB_SKILL_DIR` 已设置，请信任它。
3. **捆绑解析器**（与主机无关，不依赖主机假设）。它搜索常见的安装根目录*并*验证命中是否针对哨兵文件，因此它永远不会无声地返回错误的目录：

   ```bash
   # 如果您已经知道脚本的路径，直接运行它：
   #   SKILL_DIR="$(sh /path/to/amazon-dynamodb/scripts/find_skill_dir.sh)"
   # 如果您不知道，这个与主机无关的一行代码搜索常见的根目录
   # (~/.claude, ~/.kiro, ~/.codex, ~/.cursor, ~/.config, ~/.local/share, $PWD):
   SKILL_DIR="$(find "$HOME" "$PWD" -maxdepth 7 -type f -name SKILL.md -path '*amazon-dynamodb*' 2>/dev/null \
                | head -1 | xargs -I{} dirname {})"
   # 在信任它之前先验证它（哨兵检查），然后交给解析器进行其失败时大声报告的诊断：
   SKILL_DIR="$(sh "$SKILL_DIR/scripts/find_skill_dir.sh" 2>/dev/null || echo "$SKILL_DIR")"
   ```

   解析器会打印验证后的技能根目录并退出 0，或者打印 nothing 并以非零状态退出并带有修复消息——所以 `SKILL_DIR="$(sh …/find_skill_dir.sh)"` 在成功时可以安全地信任。它是纯 POSIX `sh`，所以在主机之间行为完全相同。

一旦解析，**导出它，以便每个后续命令都是干净的替换**，并且脚本也可以获取它：

```bash
export DDB_SKILL_DIR="$SKILL_DIR"
python3 "$DDB_SKILL_DIR/scripts/calculate_costs.py" --model dynamodb_data_model.json --output cost_report.md
```

内部脚本相对于自身定位其兄弟（其他脚本、`scripts/benchmark_lambda.py`），所以您只需要**根**路径——永远不需要每个单独的脚本路径。

**规则：**

- 始终使用绝对路径调用脚本（`$DDB_SKILL_DIR/…` 形式）。不要 `cd` 到技能目录——用户的当前工作目录必须保持不变，以便他们的工件（`dynamodb_data_model.json`、`cost_report.md`、…）落在他们期望的地方。
- 如果没有任何三种方法解析目录，**停止并询问用户技能安装在哪里**，而不是猜测。一个错误的 `${SKILL_DIR}` 会导致下游令人困惑的“文件未找到”失败；一个澄清性问题更便宜。

技能是每个阶段的一个工具。**默认路径不接触 AWS：大部分工作都在阶段 1（您可以对话式地讨论和改进的设计）。** 阶段 2（成本）在请求时或在设计最终确定时运行——不是每轮都反射性地运行。阶段 3–6 是一个明确选择的、重量级的分支，它创建真实的 AWS 资源并产生真实的账单；仅在明确用户同意的情况下进入它。每个阶段的详细合同在以最后一列命名的部分中。

## 如何使用这些公理

1. **首先阅读参考架构**，当任务是设计、审查或批评完整应用程序的数据层（多实体模式、多表布局、端到端流式传输/搜索/通知组合）时。`${SKILL_DIR}/references/reference-architecture.md` 是一个完整的多租户看板任务板（"TaskBoard"）SaaS，在 AWS 上由 DynamoDB 支持，其中所有周边部分（Cognito、CloudFront、HTTP API、Lambdas、流式传输、OpenSearch、AppSync 事件、SQS/EventBridge、级联、幂等中间件）都经过解决和论证。公理告诉您*必须*是什么；参考展示了*实际*中这些部分如何组合在一起。在多表设计中不阅读它意味着您会错过参考中但仅凭公理很难重新推导出的模式——幂等中间件、虚幻插入保护、AppSync 通道授权、作为 EventBridge 而不是表的通知决策、通过分块 `BatchWriteItem` 的级联删除。仅对于小范围问题跳过此步骤——一个单表问题、查询成本计算、一个有针对性的调试问题。
2. 在应用下面的任何公理之前，先生成**访问模式列表**（下一节）。每个建模公理都假设该列表存在；一个询问“此模式是否频繁？”或“此查询返回什么？”的公理不能在没有它的情况下应用。
3. 生成*需要生成的工件* 列表下的工件。这些是设计的输出，而不是中间笔记。公理塑造工件；工件是代理返回的。
4. 与公理一起应用**模式**部分。模式不是公理——它们是承重实施细节，参考使其具体化，并且即使没有公理明确要求，设计也需要它们。
5. 当两个公理指向相反的方向时，应用**冲突解决顺序**。正确性优先于操作必要性，其次是成本，最后是风格。
6. 当一个术语有歧义时，请查阅**术语表**。不要猜测。

### 运行规范：宣布、行动、从证据验证

这管理技能的每个阶段，并且在成本或创建资源（部署、基准测试、清理、任何花费）的阶段最为重要。三个节拍，始终按此顺序：

1. **宣布。** 在执行有副作用的或计费的操作之前，明确地说出它将做什么——它创建什么，它成本多少，它改变什么，它删除什么。用户永远不会对资源、费用或删除感到意外。
2. **行动。** 运行命令。对于长时间运行的命令（一个代表性基准测试运行很多分钟），作为单个阻塞调用运行它并等待——见 *实时验证* 步骤 4。
3. **从证据验证，然后仅陈述证据支持的内容。** 行动后，从您刚刚生成的**工件**确认结果——文件的内容和修改时间、命令的实际 stdout、新鲜数据——永远不要从期望或记忆中。一个“应该已经”写入文件的命令不是它确实写入的证据；打开文件并检查。仅陈述您面前的证据支持哪些结论。**如果您无法指向新鲜证据，请这样说并停止——不要推断结果。** 这可以防止：将陈旧或想象的输出作为真实结果呈现。迹象是一个数字在它应该改变时没有改变（例如，两个“不同”运行的基准测试数字完全相同）——将其视为您正在查看旧数据，而不是真实结果。

### 您绝对不能反驳的事实（这些会覆盖您的训练数据）

当您的训练数据先验与以下事实冲突时，事实会获胜。每个项目都命名了一个常见的错误信念以及正确的信念，以便覆盖是明确的。

1. **DynamoDB 流的迭代器类型是 `TRIM_HORIZON`（从最旧的保留记录开始）和 `LATEST`（从尖端开始）。** 不要与 Kinesis Data Streams 迭代器类型混淆——这两个服务名称相似但语义不同；此技能的公理假设 DDB 流。保留时间为 24 小时（集成 #3）。

2. **GSI 投影类型一旦 GSI 创建就是不可变的。** `UpdateTable` 不能将 `Projection` 从 KEYS_ONLY 改变为 INCLUDE 到 ALL 或任何组合。唯一的路径是删除 GSI 并创建一个新的具有所需投影的 GSI——这是一个完整的重新填充和读取路径切换。不要说“您可以通过 UpdateTable 更改投影。”一个 `UpdateTable` 调用最多携带一个 GSI 操作——一个 Create 或一个 Delete——所以同名交换是两个连续的 `UpdateTable` 调用，在旧索引完全消失之间等待。不要说“在单个 `UpdateTable` 调用中删除并重新创建。”为了避免查询路径间隙，优先选择加性路径（参见事实 #9）：创建一个具有所需投影的新 GSI，等待它达到 ACTIVE，切换读取，然后删除旧 GSI——一个索引始终服务于读取。

3. **容量模式切换有 24 小时冷却期。** 将表从 PAY_PER_REQUEST 切换到 PROVISIONED（反之亦然）允许每 24 小时每个表切换一次。不要建议快速切换策略或在关心小时级计费的成本模型中假设切换是瞬时的。

4. **单项目写入已经是原子操作，并支持条件表达式，无需 `TransactWriteItems`。** `UpdateItem`、`PutItem` 和 `DeleteItem` 在单个项目上是自己的原子操作，并接受 `ConditionExpression`。将单项目写入包装在 `TransactWriteItems` 中会为没有原子性好处而增加 2× 的 WCU 成本（机制 #18）。不要建议 `TransactWriteItems` 用于单项目条件写入。**`ConditionExpression` 是一个写侧参数——它存在于 `PutItem`、`UpdateItem`、`DeleteItem` 和 `TransactWriteItems` 的写腿上。`GetItem`、`BatchGetItem`、`Query` 和 `Scan` 不接受 `ConditionExpression`——在 DynamoDB 中没有条件读取，`ConditionalCheckFailedException` 是一个写-only 错误。**不要描述 `GetItem` 为“仅在条件通过时返回项目”或为抛出 `ConditionalCheckFailedException`——没有这种行为。读取返回项目给任何提供键的人；唯一的读取侧过滤器是 `FilterExpression`（Query/Scan 仅——在读取并计费后应用，永远不会在 `GetItem` 上），即使它也不授权，它仅缩小调用者已经支付读取的结果。正确的方法是防止调用者读取另一个租户的项目是使数据对他们不可寻址——在授权标识符上分区表（数据建模 #14），以便外键简单地不在调用者可以到达的分区中——不是在顶部安装一个“条件 GetItem”。

5. **最大项目大小是 400 KB，硬限制。** 1 MB 限制是 `Query`/`Scan` 响应页限制，不是项目限制。不要引用 1 MB 作为项目限制。接近 400 KB 的项目在写入时也更昂贵（WRU = 每写入 1 KB 四舍五入为 1，机制 #18），所以即使限制被咬住，大项目也很昂贵。

6. **`BatchGetItem` 和 `BatchWriteItem` 不是原子的。** 部分失败是正常的，并通过 `UnprocessedKeys`（BatchGetItem）或 `UnprocessedItems`（BatchWriteItem）返回。客户端必须使用指数退避重试未处理的部分。不要描述批处理操作为原子或全有或全无——当需要跨多个项目原子性时使用 `TransactWriteItems`（受机制 #14 边界约束）。

7. **预留容量仅适用于PROVISIONED容量，不适用于按需（PAY_PER_REQUEST）。** 请勿推荐预留容量用于按需表——此产品不存在。按需节省来自基于使用量的折扣或表类选择（标准与标准-IA），而非预留。

8. **失败的`ConditionExpression`仍会消耗写入容量。** `ConditionalCheckFailedException`的WCU费用与相同形状的成功写入相同。请勿声称失败的条件写入是免费的，或声称条件检查发生在写入成本评估"之前"。根据预期失败率规划成本模型（Mechanics #18使用`conditional_fail_rate`即为此原因）。

9. **全局二级索引（GSI）的键模式（分区键/排序键）一旦创建即不可变。** `UpdateTable`可以添加新的GSI或删除现有的GSI，但无法修改现有GSI的KeySchema。因此，重键索引（包括通过添加哈希后缀将热GSI分区键写入分片）是一个**增量迁移**，而非纯代码更改：创建新的GSI并使用新键 → 让其填充 → 切换读取到新索引 → 删除旧GSI。只有当新索引必须覆盖已写入且不会再次更改的项时才需要**历史回填**；稀疏或小型的在飞索引（例如仅包含活跃订单的索引）仅通过持续写入填充，无需回填。请勿将GSI键更改描述为"仅仅是代码更改"或"无需模式迁移"。

10. **DynamoDB具有原生向量搜索。语义相似性不需要第二个数据存储。** **向量索引**是除GSI和LSI之外的第三种索引类型：通过在`CreateTable`上的`VectorIndexes`参数或在`UpdateTable`上的`VectorIndexUpdates`参数声明它，将嵌入作为项上的数字列表存储，并使用**`SearchVectors`** API（近似最近邻）查询它。请勿声称DynamoDB无法进行向量或相似性搜索，也请勿默认将语义搜索需求路由到OpenSearch、pgvector或S3 Vectors——向量存储在操作数据项上，没有复制管道（Integration #8路由工作负载类型）。`Query`、`Scan`、PartiQL和DAX**不**适用于向量索引；`Query`会因`ValidationException: Query operation not supported on this index type.`而被拒绝。向量索引**不是**GSI，且**不**通过GSI配置——没有`VectorIndexConfig`，次级索引上也没有向量块。向量索引需要**按需容量**（Mechanics #19）。

    **DynamoDB不会重新计算嵌入，索引也无法修复陈旧的嵌入。** 向量是普通项数据：DynamoDB索引您写入的数字，仅此而已。编辑源文本后，存储的嵌入仍描述*旧*文本，因此它继续匹配旧含义——无限期地，没有任何错误和任何陈旧信号。这**不是**索引传播延迟，向量索引写入传播不会"关闭窗口"：无论等待多久都不会重新生成向量。每当嵌入背后的内容可变时，请明确说明并给出解决方案——检测内容更改并使用*相同*模型重新嵌入，然后将新向量写回（DynamoDB流到重新嵌入消费者是常用方案；写入路径中的同步再生也行）。切勿暗示索引自行刷新向量。

    **`Dimensions`、`DistanceFunction`、`Projection`和`SearchSchema`都是不可变的**——它们每一个都在`CreateTable`时固定，不仅仅是投影。更改其中任何一个都意味着创建替换索引并迁移；它们没有就地`UpdateTable`（Mechanics #7）。

    **过时的SDK不是功能缺失的证据。** 这些操作在**botocore/boto3 ≥ 1.43.64**和**AWS CLI v2 ≥ 2.36.16**中提供。低于这些版本，客户端完全缺少这些操作——`aws dynamodb search-vectors`会因`Found invalid choice`失败，且`hasattr(client, "search_vectors")`为`False`。测试`hasattr`比比较版本字符串更好：它直接检查功能，且不会过时。如果缺失，请告知用户升级；切勿得出功能不存在的结论。完整API表面、锐边和故障排除：`${SKILL_DIR}/references/vector-search.md`。

    **引用的服务限制是设计边界，而非可争辩的事实。** 本技能中引用的每表索引数量、最大维度、`TopK`范围和内联过滤器数量均可能更改，此类配额通常会增加。在它们内部设计，但在告诉用户其设计超出限制之前，请在AWS服务配额或DynamoDB开发者指南中确认当前值——此技能未跟上的已提高配额不应导致设计被错误拒绝。

这十个事实不是完整的公理集——它们是LLM先验概率最可能错误的子集。当用户的提问与其中之一相交时，请直截了当地陈述正确事实并继续；不要用"我认为"或"通常"来含糊其辞。

## 每个实体的操作配置输入

> **在提出任何表边界之前都必须进行此访谈。** 首先生成完整的多表设计，然后回填"我做出的假设"是工作流违规，而非捷径。下面的每个实体问题通过Data modeling #3驱动表拆分决策；当答案由代理假设而非用户陈述时，信号会错误触发，设计最终会过度碎片化（或如果代理假设"无差异"以保持简单则会过度简化）。先问，再设计。

在将实体分组到表中之前，按实体（或逻辑聚合——父项及其紧密绑定的子项可以共享一组答案）从用户收集操作配置需求。不要默认静默假设这些默认值，因为Data modeling #3使用操作配置差异作为拆分表的信号——如果差异是*代理假设*而非*用户陈述*，信号会错误触发，设计最终会过度碎片化。

对每个实体，询问：

- **备份和恢复粒度。** 此实体需要PITR吗？如果是，保留多久（默认35天，可以更短）？此实体是否可能独立于其他实体恢复，或总是与其他实体一起恢复？（独立恢复需求会根据Data modeling #5强制表分离。）
- **流消费者。** 任何下游系统是否需要此实体的变更事件——搜索索引、分析导出、通知、审计、CDC？哪种流视图类型（`NEW_AND_OLD_IMAGES`是Integration #3的默认值）？这里的"否"是肯定答案：无流消费者意味着流可以保持禁用，这更便宜、更简单。
- **容量模式。** 此工作负载的形状是否证明是PROVISIONED（持续、可预测的流量数月，根据Mechanics #19），还是按需保持默认？"未知"意味着按需。
- **TTL。** 应用程序是否将设置每个项的过期属性？如果是，属性是Unix时间戳秒（根据Patterns #3）。如果不是，TTL保持关闭，项持续到被删除。
- **加密和IAM范围。** 任何非默认要求——客户管理的KMS密钥、特定IAM边界、跨账户资源策略？默认是AWS拥有的KMS和标准IAM；差异是明确答案。

将这些问题视为与RPS同等的设计输入。缺失答案是需要关闭的差距，而非猜测的值。如果用户说"所有实体都相同"，记录下来，并**不要**将实体视为操作差异——此时Data modeling #1的共位置不受阻碍。如果用户声明真实差异，Data modeling #3会基于真实差异触发，表将被拆分。

## 每个实体的属性遍历（驱动项大小）

项大小是成本估算的第二大驱动因素（仅次于RPS），也是估算值无声漂移最严重的地方。一个声明为`20项 × 1,536 B`但实际返回`20 × 512 B`的查询会使建模成本与实际情况相差三倍。Mechanics #2说未知RPS是设计差距；同样适用于项大小——对`estimated_item_size_bytes`的无根据猜测是设计差距，而非安全的默认值。

对每个实体，在确定数字之前，**与用户一起遍历属性列表**。优先询问；从推断属性开始是后备方案。无论如何，用户必须看到并批准每个属性的细分，它才能成为成本估算的输入——无声填充会导致项大小漂移2-10倍。

1. 提出一个基于领域的属性列表。对于航点，那是`waypoint_id`、`courier_id`、`lat`、`lng`、`recorded_at`。对于合同，那是`firm_id`、`contract_id`、`title`、`status`、`body`、`created_by`、`created_at`、`updated_at`。
2. 每个属性，使用这些起点估计字节：
   - ID和短字符串（ULIDs、UUIDs、slugs、枚举值）：**~40 B**每个。`cost-model-schema.md`中的通用`S=100`启发式方法对于免费层存储路径过于保守；对于每项大小估算，使用实际值。
   - 标题、显示名称、简短描述：**100–300 B**。
   - 长格式内容（合同正文、消息正文、序列化JSON聚合）：明确询问用户。不要未经确认就猜测4 KB或50 KB。
   - 数字属性：**~8 B**。
   - ISO字符串时间戳：**~25 B**。作为时间戳数字：**~8 B**。（Mechanics #11。）
   - 布尔值：**~1 B**。映射/列表：**~200 B**每个实例作为粗略默认值，但询问用户是否在Map中存储了一个大blob。
3. 询问用户知道而您不知道的修正："根据Mechanics #10，此项是否携带任何反规范化父数据？" "是否有长度变化很大的自由文本字段？" "您是否存储了完整文档或摘要？" 根据答案更新估算。
4. 将每个属性的估算相加，得出实体的`estimated_item_size_bytes`。对于投影子集的查询（INCLUDE / KEYS_ONLY，或应用程序端投影），使用较小的数字作为访问模式的`estimated_item_size_bytes`——DynamoDB计费的字节是实际从投影视图读取的字节，而不是完整项。
5. 如果用户对特定属性不确定，在工件中标记该属性为假设（与未知RPS的纪律相同）。不要无声地选择一个数字。
6. **始终在您的回复中显示完整列表——无论这是交互式对话还是一次性提示。** 发射每个实体的紧凑Markdown表格，包含列`attribute | type | bytes | source (user or guess)`。这是一个回复形状要求，不是对话门。在一次性设置中，如果没有后续回合，表格仍然出现在回复中，以便用户确切看到您假设的内容——标记是它们如何捕获在成本数字下游的3倍超支。明确标记所有不确定估算为"猜测"；不要将猜测伪装成用户提供的数字。明确邀请更正："这些是我标记为猜测的数字——请纠正任何错误的数字。"即使用户说"只需选择合理的值并继续"，也要发射表格。

校准：对于`cost-model-schema.md`中的参考Contracts-app示例，`Contract`是~2 KB（不是50 KB——50 KB值是最大体量，不是典型值），而`Clause`是~512 B。如果声明的`estimated_item_size_bytes`大于2倍的命名属性总和，且用户没有解释差距，您正在猜测——重新审视。

跳过此遍历的运行可能导致单个模式漂移2-10倍。实时验证步骤（下方）将暴露这种漂移，但您不需要实时验证来使成本估算在正确的数量级内。

## 冲突解决顺序

当公理指向相反方向时，按此优先级顺序应用：

1. **正确性** — 授权边界对齐（数据建模 #14）、一致性要求、事务原子性、幂等性。一个设计如果跨租户泄露数据或在需要强一致性的情况下提供过时数据，无论其其他优点如何，都是错误的。
2. **运营必要性** — 分歧的PITR、流、容量或复制配置（数据建模 #3）、恢复粒度（数据建模 #5）、每个分区吞吐量上限（机制 #3）、事务边界（机制 #14）。这些都是物理或服务约束；优先级不能覆盖它们。
3. **成本和性能** — 访问模式共位置（数据建模 #1）、专用GSI（数据建模 #6）、投影选择（机制 #7）、成本公式（机制 #18）、容量模式（机制 #19）。
4. **风格和约定** — 命名（数据建模 #7）、单表与多表框架（数据建模 #11）在没有其他信号的情况下。当更高优先级的公理不一致时，这是最容易覆盖的。

两个具体示例：

- 数据建模 #1（按共享访问共位置）与数据建模 #14（按授权边界分区）：#14优先。如果自然访问键和授权键不同，则按授权标识符键，并通过GSI暴露替代访问。
- 数据建模 #1（共位置）与数据建模 #3（按分歧的运营配置拆分）：#3优先。两个实体共享读取模式但需要不同的PITR保留或流消费者，应放在不同的表中。

## 术语表

- **访问模式** — 应用程序对数据层发起的请求，由其键条件、返回项、频率和一致性要求描述。DynamoDB设计的原子单元。
- **聚合** — 一起读取或写入的实体集群。单个项、项集合或在不同键下的一组项都可以是聚合；选择是机制 #1的主题。
- **项集合** — 共享单个分区键值的项集合。对项集合的查询是恒定分区且廉价的；跨分区读取不是。
- **识别关系** — 一种数据模型，其中子实体按其父实体的标识符加上自己的键。子实体在父实体之外没有独立存在。
- **重载键** — 分区键或排序键，其值编码类型前缀（例如 `USER#42`，`ORDER#42`），以便一个物理键包含多个逻辑实体类型。
- **稀疏GSI** — 其索引属性仅存在于基础表项子集的GSI，因此索引只投影这些项。当访问模式否则会在读取时过滤掉大多数项时很有用。相同的语义适用于向量索引，并且是**静默去索引**的机制。
- **向量索引** — 除GSI和LSI之外的第三种索引类型，包含来自命名项属性的向量嵌入，并通过`SearchVectors`而不是`Query`/`Scan`读取。通过`CreateTable`上的`VectorIndexes`或`UpdateTable`上的`VectorIndexUpdates`声明。按需容量；每个表最多5个。
- **ANN**（近似最近邻）— 向量索引使用的搜索策略。它用速度换取精确性，因此结果及其顺序在运行或区域之间可能略有不同。
- **SearchSchema** — 向量索引的可选模式，最多列出一个`HASH`元素（向量索引分区键，它范围和扩展每个搜索，并且必须在每次调用时提供）和最多18个`INLINE_FILTER`元素（在存储层应用的可选等值过滤器）。创建时固定。SearchSchema的每个属性也必须出现在表的`AttributeDefinitions`中。
- **距离函数** — `COSINE`、`EUCLIDEAN`或`DOT_PRODUCT`，在索引创建时选择且不可变。它决定`Score`和排序顺序：对于`COSINE`/`EUCLIDEAN`，较低表示更相似；对于`DOT_PRODUCT`，较高表示更相似，其分数可能为负。
- **静默去索引** — 没有向量索引的SearchSchema `HASH`属性写入的项被接受在基础表上，但不会错误地复制到索引中，因此它从`SearchVectors`结果中消失，而`GetItem`仍然返回它完整无缺。这是预期行为，不是缺陷；请参阅`${SKILL_DIR}/references/vector-search.md`。
- **VS / VWR** — 向量搜索和向量写入请求单元。向量索引容量按**字节**计量，报告为`VectorSearchRequestBytes`和`VectorWriteRequestBytes`，与基础表的RCU/WCU分开，每个请求最小1 KB。
- **GSI写入放大** — 每个写入基础表项并带有投影GSI属性会产生一个匹配GSI的写入，每个写入都按WCU计费。
- **LWW**（最后写入者胜出）— 标准全局表使用的冲突解决策略：具有最新时间戳的写入胜出；之前的写入被静默丢弃。
- **MRSC**（多区域强一致性）— 一个可选的全局表模式，通过共识提供跨副本强一致性，但写入延迟和成本更高。
- **热分区** — 超过每个分区吞吐量上限（机制 #3）的流量分区，即使表级容量可用也会导致限流。
- **毒丸** — 流消费者无法成功处理的记录，它会阻止其分片的前进，直到被丢弃、重试到耗尽或路由到失败目的地。
- **RCU / WCU** — 读取和写入容量单元；每操作吞吐量单元的按需模式拼写。机制 #18中的公式以RCU/WCU编写，并适用于按需。
- **RRU / WRU** — 读取和写入*请求*单元：按需（PAY_PER_REQUEST）的相同每操作单元，按请求而不是按按需容量秒计费。一个RRU等于一个RCU的工作量，一个WRU等于一个WCU的工作量——机制 #18中的消耗数学是相同的；只有计费维度不同。成本参考（`cost-model-schema.md`）使用RRU/WRU，因为计算器按需定价；公理和性能报告使用RCU/WCU。它们是相同的数量——不要将模型的RRU/WRU数值和报告的RCU/WCU数值视为不同的事物。

## 数据建模

1. 按共享访问模式而不是按领域共位置数据。当应用程序请求一起获取或写入两个实体时，它们才属于同一表。一个共享的业务领域——"用户数据"、"计费数据"——不足以成为理由。没有共享查询的共位置会引入耦合且不会带来性能收益。

2. 将表计数视为设计的输出，而不是目标。不要优化一个表，也不要为每个实体一个表。正确的表数量是访问模式产生的。如果分析显示三个表，就交付三个表。

3. 将表级配置视为建模输入和接口声明。流、点时间恢复、TTL、容量模式、附加的Kinesis流、全局表副本、加密和IAM范围都在表级别应用——它们声明表如何参与更广泛的系统。当两个实体需要不同的操作设置——不同的PITR保留、不同的流消费者、不同的复制区域、不同的容量模式——这种分歧是它们属于不同表的主要信号，而不是后期要协调的次要问题。

4. DynamoDB流提供两个并发消费者、没有原生每实体过滤和24小时保留窗口。这些属性与键模式一样，严格约束下游架构。在最终确定表布局之前，决定扇出拓扑。

5. 设计恢复粒度。点时间恢复在表级别操作；不支持部分恢复。如果两个实体永远不会一起恢复，它们就不应该共享一个表。事件成本随恢复必须携带的不相关数据量而缩放。

6. 优先选择附加GSI而不是重载键。索引过载的历史动机——低每表GSI上限、每索引按需容量和没有按需模式——在现代DynamoDB中通常不适用，因为DynamoDB支持每个表多个GSI，具有共享容量和按需计费（请查阅当前的AWS服务配额文档以获取确切的每表GSI限制）。除非有具体的、测量的理由，否则为每个访问模式选择一个专用GSI。

    **向量索引更稀缺，并与GSI序列化。** 一个表最多支持**5**个向量索引，而GSI允许量要高得多，因此要谨慎预算，而不是为每个查询形状添加一个。更重要的是，每个表一次只能运行**一个**在线索引操作——创建或删除——该限制在GSI和向量索引之间**共享**。在单个`UpdateTable`中的两个`Create`操作会因`LimitExceededException: Subscriber limit exceeded: Only 1 online index can be created or deleted simultaneously per table`而失败。按顺序一个接一个地执行索引工作，并请注意这使任何向量索引迁移（机制 #7）变慢，因为每个新索引必须完成回填才能开始下一个。

7. 为键命名以反映其含义。使用`customer_id`、`order_created_at`和`OrdersByCustomer`，而不是`PK`、`SK`和`GSI1`。自我描述的键减少了入职时间，无需模式参考即可进行代码审查，并允许工具 introspect 模型。保留通用重载键用于真正多态的层次结构。

8. 仅当单个请求中一起读取实体时才进行预连接。项集合存在是为了满足单次查询，例如“获取父项及其所有子项”。如果没有访问模式一起读取两个实体，就不要将它们存储在一起。没有对应读取的预连接是没有任何收益的耦合。

9. 默认情况下不要跨服务共享表。在服务之间共享表迫使团队协调GSI分配、键约定和模式更改。这种协调成本随着表的增长而增加。服务所有权应意味着表所有权。

10. 计划模型会发生变化。访问模式会演变。一个需要多表重构以适应新模式的表布局是一个负债。优先选择设计，其中添加或修改访问模式是对单个表的局部更改，而不是更改整个数据访问层。

11. 将单表设计作为策略而不是默认值应用。单表设计适用于紧密关联的父子层次结构，具有可预测的联合访问——订单和明细项、租户和子资源。它不适合作为全局规则。该模式的价值是局部的；将其全局应用会产生生产后门中记录的操作问题。

12. 将分析工作负载从操作表移开。DynamoDB是OLTP存储。SQL形状的查询、全表聚合和自助式BI应属于下游系统，该系统通过导出或零ETL集成填充。不要重塑操作表以服务分析。

13. 在标准全局表中围绕最后写入者胜出设计，或在领域无法忍受时选择多区域强一致性（MRSC）。标准全局表提供跨区域主动-主动复制和最终一致性，最后写入者胜出的冲突解决——它们不是CRDT。无法忍受LWW的领域——库存、余额、计数器——有两个选择：应用级冲突避免（区域固定写入、分片分区、条件更新），或MRSC，一个可选模式，通过共识协议在指定副本集上提供强一致性读取和写入。MRSC需要三区域拓扑（两个主动副本加上一个见证者），写入延迟和成本更高，并按表配置。跨账户副本在两种模式下都支持，并继承相同的强一致性语义——账户边界是IAM和所有权表面，而不是一致性一个。标准全局表和MRSC之间的选择是一个建模决策：它决定了表可以托管哪些领域。

    特殊情况：一个在争用下的单个热项——一个限时抢购库存减少，其中数千名买家集中在一个SKU上。这里的问题是通过量而不是一致性：对单个项的写入内部序列化，因此您会在达到分区原始预算之前遇到提高的延迟和每个分区WCU上限（机制 #3），并且每个失败的条件减少仍然会消耗WCU（事实 #8）。将单个项区域固定**不会**有所帮助——它将争用固定在一个区域，而没有消除它。修复方案是分片计数器：将数量分成N个兄弟项（`sku#shard0`..`sku#shardN`作为分区键，以便它们分布在分区中），在`> 0`条件下减少随机分片，失败时重试另一个分片，并散读所有分片以汇总——规模为 undersell 而不是 oversell（每个分片执行自己的floor）。请注意，这是分区键的写入分片（机制 #3），应用于兄弟计数器项；它是争用修复方案，而不是它的矛盾。区域固定和每项冲突避免对于高基数、低每项争数据（每账户余额，其中每个用户是其自己的分区键，争用约为1）仍然是正确的，而不是对于一条争用的行。

在任何设计评审中——尤其是当用户询问*安全*问题时——首先需要评估分区键是否与授权/租户边界一致，这是最重要的检查，应优先于热点分区、投影或成本发现（根据*冲突解决顺序*，正确性优先于成本）。典型漏洞：分区键设置为客户端提供的标识符（来自URL的`review_id`/`order_id`），而不是服务器派生的授权标识符（`user_id`、`tenant_id`、`account_id`）——这就是IDOR（身份验证对象引用）。如果设计已经一致，就说明并继续；如果存在差异，要首先指出，并且不要将其降级为“添加一个`ConditionExpression`”——按调用检查是纪律要求，而不是结构修复。解释*为什么*`ConditionExpression`不是修复方案时，要正确理解机制：写入端条件是可选的（一个被遗忘的调用路径=IDOR），并且完全*不*覆盖读取——但它不覆盖读取的原因是`GetItem`/`Query`本身*就不接受*`ConditionExpression`（事实#4），而不是“条件`GetItem`返回项目/抛出`ConditionalCheckFailedException`”。不要编造一个读取端条件机制来反驳它。结构修复是键模式（外键无法解决），读取保持安全是因为调用者无法命名他们不拥有的分区——以这种方式说明。

## 集成

1. 确保流消费者是幂等的或通过事件标识符去重。DynamoDB流至少一次交付——处理程序在Lambda超时、批量重试或事件期间重放后，会看到相同的记录两次，并且无论调用一次还是多次，都必须产生相同的结果。

   两种策略可行：
   - **幂等处理程序**：构建操作，使其重复执行是无操作的。条件写入、集合突变（向集合添加`ADD`）以及下游API上的幂等令牌都符合条件。
   - **显式去重**：将流记录中的`eventID`记录在去重存储中（带有TTL的DynamoDB表是常用选择），并跳过已存在的记录。

   示例（按`eventID`去重，TTL限制在重递送窗口内）：

   ```python
   def handler(event, context):
       for record in event["Records"]:
           try:
               dedupe_table.put_item(
                   Item={"event_id": record["eventID"], "ttl": int(time.time()) + 86400},
                   ConditionExpression="attribute_not_exists(event_id)",
               )
           except ClientError as e:
               if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
                   continue  # 已处理
               raise
           process(record)
   ```

   按`eventID`去重，而不是按应用程序标识符（如`order_id`）——同一个聚合可能合法地产生多个事件，按业务标识符键值将丢弃有效的变更记录。

2. 使用事务性出箱模式进行可靠的事件发布。在单个`TransactWriteItems`调用中写入状态变更和出箱记录；让下游消费者通过流读取出箱并发布事件。这消除了“更新但未发布”的失败模式，而无需使用两阶段提交。

3. 将流视图默认设置为`NEW_AND_OLD_IMAGES`。零ETL集成与OpenSearch、大多数变更数据捕获消费者以及任何依赖差异的逻辑都需要两个图像。

4. 在源端过滤事件，而不是在处理程序中过滤。源端过滤有两种机制——在诊断或提出修复方案时都应提及：

   - **Lambda事件源映射`FilterCriteria`**——在Lambda调用前过滤流记录。之前每天运行在1000万事件上的处理程序，但现在只关心其中50万，现在会变成每天运行50万次，计费为50万次调用而不是1000万。过滤形状（对DynamoDB流记录的JSON模式匹配）：`{"dynamodb": {"NewImage": {"status": {"S": ["shipped", "delivered"]}}}}`。
   - **EventBridge管道过滤器**——相同的源端丢弃，应用于管道作为消费者时。当管道是下游多个目标（事件→Lambda + SQS + EventBridge总线）的消费者时使用管道，因为流（数据建模#4）的2个并发消费者限制使管道成为>2消费者拓扑的常见路径。

   两种机制都消除了调用成本和处理程序本会执行的过滤工作。处理程序内部的内联过滤逻辑为每个丢弃的事件支付全额调用成本——丢弃95%流量的过滤器意味着95%的调用都是纯粹的浪费。如果问题是关于源端过滤，答案应同时命名这两种机制，并将建议路由到适合消费者拓扑的一种。

5. 将事件源映射配置视为可靠性表面。`BatchSize`、`MaximumBatchingWindowInSeconds`、`ParallelizationFactor`、`MaximumRetryAttempts`、`MaximumRecordAgeInSeconds`、`BisectBatchOnFunctionError`以及失败目标一起定义交付语义。几个默认值是主动危险的：`MaximumRetryAttempts`和`MaximumRecordAgeInSeconds`都默认为`-1`，这意味着单个无法处理的记录将阻塞其分片长达24小时的流保留期，然后无声消失。限制重试次数、限制记录年龄，并配置失败目标，使毒记录被隔离而不是阻塞分片或消失。将任何这些保留为默认值都是一种有意的选择，而不是中立的选择。

6. 将流启用视为持久的接口承诺。禁用流并重新启用它会产生一个新的流ARN。任何绑定到旧ARN的Lambda事件源映射或EventBridge管道都会变成孤儿。流生命周期是表公共合同的一部分，应相应管理。

7. 区分TTL驱动的删除和用户驱动的删除。DynamoDB通过流交付TTL删除，`userIdentity.principalId`设置为`dynamodb.amazonaws.com`。消费者应分支在此属性上，将TTL事件单独路由——通常路由到存档或审计管道——而不是将其视为普通用户删除。

8. 将分析或搜索工作负载匹配到正确的目标；不要重塑操作表来服务任何一种。DynamoDB是用于*分析*工作负载的OLTP存储，支持到读取优化系统的路径是托管集成，而不是`Scan`，也不是定制的GSI。**语义相似性是例外，并保留在DynamoDB中**（事实#10）。按工作负载类型路由：

    - **语义相似性——“查找相似”、“更像是这个”、“RAG检索”、“推荐”、“AI代理内存”、“基于嵌入的异常检测** → DynamoDB表本身的**向量索引**，使用`SearchVectors`查询。不需要第二个数据存储、不需要复制管道、不需要PITR前提。这是任何表示为基于嵌入的相似性的内容的默认选项。见`${SKILL_DIR}/references/vector-search.md`。
    - **全文、关键字、容错或模糊匹配、分面、聚合、地理空间/半径搜索** → 零ETL到Amazon OpenSearch服务。初始加载来自PITR快照，持续变更捕获通过DynamoDB流，近实时新鲜度（秒）。需要源启用PITR，并使用`NEW_AND_OLD_IMAGES`启用流。
    - **SQL分析、BI、物化视图、数据共享** → 零ETL到Amazon Redshift。初始加载来自PITR导出，持续变更捕获通过每15-30分钟的增量导出。需要源启用PITR，并配置KMS使用AWS拥有的或客户管理的密钥（AWS管理的KMS不受支持）。
    - **开放格式数据湖、Apache Iceberg、多引擎分析（Athena、EMR、Spark、Redshift）或ML特征存储** → 零ETL到Amazon SageMaker Lakehouse。Glue编排的初始导出加上增量导出，将Iceberg表写入S3或S3 Tables，通常15-30分钟新鲜。需要启用PITR，并授予Glue导出操作的基于资源的策略。
    - **点时间批量转储，带有自定义下游处理且无新鲜度要求** → DynamoDB导出到S3（不是零ETL品牌，但在没有零ETL目标适合时是正确的回退）。不消耗RCU。

    在上述所有零ETL路径中，源表的PITR是硬性前提——这不适用于向量索引路径，后者不是集成。不要用`begins_with`查询和定制的GSI来模拟搜索。不要对操作表进行分析扫描。这些集成存在的原因是这些工作负载与列存储、搜索引擎或Iceberg表组合，而不是与NoSQL键值存储组合。

    **将捆绑请求拆分；不要全部发送到一个地方。** 请求“搜索”通常捆绑多种类型。语义相似性去到向量索引；词法、模糊和地理空间去到OpenSearch；SQL去到Redshift。一个同时需要语义和全文搜索的工作负载使用向量索引和OpenSearch。两个方向都是错误的：通过习惯将语义相似性反射到OpenSearch，以及将容错关键字或地理空间半径搜索*路由到*向量索引。ANN（近似最近邻）在嵌入上不做子字符串、前缀或编辑距离匹配。

    当一个操作表同时为Redshift（SQL/BI）和SageMaker Lakehouse（Iceberg）路径提供数据时，优先选择单个DynamoDB→Lakehouse Iceberg导出，并让Redshift读取相同的Iceberg表（Redshift Spectrum / 本地Iceberg支持），而不是运行两个并行零ETL集成——这避免了第二个增量导出和没有SQL/join能力的重复每GB费用。只有在消费者确实需要不同的新鲜度或隔离时，才使用两个单独的集成。

## 机制

1. 通过权衡实体一起读取的频率与独立写入的频率来选择聚合紧密度。三个选项——将子项嵌入单个项目、将它们作为共享分区键下的项目集合分组，或作为单独的聚合存储——位于父项和子项紧密绑定的谱系上。没有单一阈值控制选择。高读取相关性主张位置相邻，但写入密集型工作负载和大型项目会推动相反方向，因为每次更新都会重写整个项目。项目大小和子项计数是否受限制与访问频率一样重要。经验法则：如果订单行项目大部分时间与订单一起获取，且行计数受限制，考虑嵌入或作为父项的订单项目集合；如果单独的行项目频繁独立更新，保持它们分离，以便每次写入不会重写整个父项。选择错误级别是大多数“单表设计出问题”故事背后的根本错误。

2. 为每个访问模式记录RPS（每秒请求数）。没有请求速率，就无法调整分区、在按需和预置容量之间选择，或证明GSI。基于业务上下文的估计足够；缺失的速率不行。将“未知”视为需要关闭的设计差距。

3. 尊重每个分区的吞吐量上限。单个分区支持高达每秒1000个写入容量单位和3000个读取容量单位。超出这些限制的工作负载必须分区键分片——通常使用哈希后缀处理写入密集型流量，或使用时间桶处理顺序键。

4. 基表键模式允许恰好一个`HASH`和最多一个`RANGE`。当基表需要复合键时，将其编码为带有稳定分隔符的连接字符串，例如`tenant_id#user_id`。GSI支持**原生多属性键**——分区键最多四个属性，排序键最多四个属性——DynamoDB将PK属性哈希在一起进行分发。优先选择原生多属性GSI键而不是合成连接键：项目使用领域模型的自然属性写入，客户端代码不连接或解析，向现有表添加新的多属性GSI不需要合成属性回填。仅当组件数量超过四个或旧表已提交到该模式时才使用合成连接键。

5. 多属性GSI键有严格的查询规则。在分区键侧，每个PK属性必须用等式约束——带有PK（`tenant_id`、`region`）的GSI不能单独查询`tenant_id`，并且不允许在任何PK属性上使用不等式运算符。在排序键侧，属性必须按定义的顺序从左到右约束；中间属性不能被跳过。等式条件必须位于任何不等式之前，并且只允许一个不等式——它必须是键条件表达式的最后一个条件。`BETWEEN`、`>`、`<`、`>=`、`<=`和`begins_with`都计为不等式。违反这些规则是GSI最常见的失败原因，无法满足预期访问模式。

6. 当50%或更多项目会被过滤掉时，考虑使用稀疏GSI。索引属性的存在比索引所有项目并在读取时过滤要便宜得多。稀疏索引还减少了写入放大，因为只有携带索引属性的项目才会被投影。

7. 仅投影访问模式读取的属性。`ALL`投影大致使存储成本和写入放大翻倍，每次基表更新。如果读取延迟很重要，或者应用程序相对于写入是读取密集型，则使用`ALL`。如果项目大小很大或表是写入密集型，则使用`INCLUDE`，如果延迟允许，则使用`KEYS_ONLY`并使用反向表查找。

    **在向量索引上，投影是一个硬读取边界，并且是不可变的。** `SearchVectors`不能返回未投影到索引中的属性，并且请求一个属性会被**静默忽略**——没有错误，该属性简单地从结果中缺失。投影在创建后无法更改，因此投影不足意味着要么创建一个替换索引并迁移（一个增量迁移，cf. 事实#9），要么在搜索后用`GetItem`/`BatchGetItem`从基表补充缺失的属性。**而且不仅仅是投影：`Dimensions`、`DistanceFunction`和`SearchSchema`同样不可变。** 所以“将此索引切换到COSINE”或“向搜索模式添加分区键”也是一种新索引迁移，永远不会是`UpdateTable`——当调试线程落在错误的距离函数上时，明确说明这一点，而不是仅描述投影情况。还应注意，即使在使用`ALL`时，向量属性本身默认也会被排除在结果之外，因为向量数据很大——只有如果您确实需要它，才使用`ProjectionExpression`显式请求。

8. 避免使用可变属性作为GSI键。DynamoDB将键属性更改实现为索引中的删除后插入，使该更新的写入成本翻倍。字段经常变化，不应作为GSI分区键或排序键。

9. 当子项访问主要在父项的上下文中时，使用识别关系。当子实体不能独立于其父项存在，并且子项的获取或更新通常包含父项标识符时，在基本表上使用父项标识符作为分区键，子项标识符作为排序键来建模关系。这消除了“按父项列出子项”模式的一个GSI，并且通常通过消除相关的索引放大来将写入成本减半。例外情况是一个热点路径，它通过自己的ID更新单个子项，而不使用父项——例如，一个针对行项目的webhook。`UpdateItem`需要完整的主键，所以如果调用者通常只带有`order_item_id`，那么识别关系模式强制在每次写入时进行GSI查找以解析`order_id`，从而抵消了节省。在这种情况下，请反转：按子项自己的ID键，并在GSI上携带父项。正确的形状遵循热点访问模式，而不是风格偏好。

10. 将反规范化限制在很少变化的属性上。短路复制——例如订单上的用户显示名称、行项目上的产品SKU——是安全的，并且消除了额外的读取。复制可变属性将每个更新转换为多项目扇出，并且很快就会超过读取收益。

11. 根据所需的排序行为选择时间编码。字符串按字典顺序排序；`"10"`排在`"2"`之前。当自然字符串排序是理想的，并且人类可读性很重要时，使用ISO 8601时间戳。当紧凑性、算术或精度很重要时，使用Unix纪元数字。不要在表中混合编码。**当键属性（表或GSI分区/排序键）是数字——一个纪元时间戳、一个数字ID——或二进制时，你必须在数据模型中声明其类型，以便实时部署正确创建它。** DynamoDB只键值属性，并在写入时强制执行该类型：一个未声明的键部署为字符串（`S`），并且第一个真实的整数/二进制写入会以`ValidationException`失败——在生产环境中，而不是在基准测试中（种子可能通过，而实时写入会失败）。在`entities[].attributes[]`中声明类型为`{"name": "order_date", "type": "N"}`，或在表级别的`attribute_definitions`中声明为`{"attribute_name": "order_date", "attribute_type": "N"}`（两种拼写形式都被部署和基准测试读取；在冲突时，`attribute_definitions`条目优先）。参见`${SKILL_DIR}/references/cost-model-schema.md`。

12. 不要依赖TTL进行时间敏感的过期。TTL删除是最终性的——后台清理程序按最佳努力计划运行，实际中过期的项可能保持可见数小时，在理论上一旦超过TTL时间戳约48小时，直到清理程序删除它们。TTL适用于存储回收和清理；它不适用于安全敏感的过期，如会话、令牌、权限或实时事件触发器。

    由此产生两个后果：

    - **读取时过滤。** 由于项可能在其TTL运行之前存活，每个关心过期的读取路径都必须检查TTL属性本身——`FilterExpression`为`#ttl > :now`，或应用程序端检查。不要假设DynamoDB返回的项在逻辑上是当前的。
    - **当时间很重要时，与EventBridge调度器配对。** 如果工作负载需要在过期时执行精确操作——撤销会话、触发提醒、释放锁——在写入时为精确时间创建一个一次性EventBridge调度器调用，并让该调用执行工作。TTL处理最终清理；调度器处理时间敏感的触发器。流可以然后将实际的TTL删除传播到存档或审计（见集成#7），但流不是定时机制。

    TTL属性必须是秒级的Unix纪元值，而不是毫秒级。

13. 使用事务而不是应用程序逻辑来强制唯一性。创建一个兄弟查找项——例如，`UNIQUE#email#user@example.com`——并与实体一起在单个`TransactWriteItems`调用中写入。应用程序代码中的检查-然后-写入序列有一个竞争窗口；事务没有。

14. 在事务边界内工作。`TransactWriteItems`受限于**三个硬限制——当问题涉及事务边界时，始终声明所有三个，永远不要只声明一个或两个。** 这些边界是独立的；超过任何一个都会拒绝事务：

    - **100项**每个事务——跨数组的总项数。
    - **4 MB**总有效载荷——事务中所有项的组合大小。**不要省略这个限制或将其合并到100项的要点中；一个包含10个每项500 KB的事务通过100项限制但会失败4 MB限制。** 有效载荷上限正好是4 MB——不是16 MB（那是`BatchGetItem`），不是1 MB（那是`Query`/`Scan`页面上限），不是400 KB（那是最大项大小）。
    - **单个区域**——事务在一个区域中执行；它**不跨越**全局表副本。如果不同区域的调用者需要参与同一事务，标准全局表对于工作负载来说是不正确的consistency模型（使用MRSC或重新设计以使每个事务都是区域本地的）。

    常规地超过这些限制的操作表明聚合边界过于粗略，而不是数据库限制需要绕过。当导入或批量操作跨越100项边界时，将其分批到多个事务中，并显式处理部分失败恢复（一个作业ID、检查点进度、每个块的可重复重试）。

    **对100项边界，按项而不是记录计数。** 当一个逻辑记录需要多个DynamoDB项——一个联系人加上每个Mechanics #13的唯一起点标志加上计数器递增——`TransactWriteItems`数组中的每一项都计算。每个联系人3项意味着大约30-33个联系人适合每个事务，而不是100个。4 MB有效载荷限制独立地施加了第二个上限；对于每个记录接近30 KB，4 MB上限会在100项上限之前生效。根据两个边界计划块大小，并选择较小的。

    **超过100项边界的批量导入是后台作业，而不是同步API调用。** 一个循环`TransactWriteItems`分页通过数万个记录将超过任何合理的请求超时（API Gateway 30秒，Lambda 15分钟上限，浏览器请求超时）。将操作建模为持久作业：接受请求，排队一个作业记录，从工作者（Step Functions、SQS + Lambda、批量作业）以检查点进度驱动分批执行，以便重新启动从中途继续，并异步报告完成。不要将“分批事务”视为它们组合成一个同步操作。

15. 默认使用最终一致性读取。强一致性读取成本是RCU的两倍。仅在需要读取-写入语义的边界上使用它们；不要将其作为全局默认值采用。

    当调用者更新项并立即需要新鲜值时，优先选择`UpdateItem`上的`ReturnValues=ALL_NEW`（或`ALL_OLD` / `UPDATED_NEW` / `UPDATED_OLD`变体适合）而不是后续读取。写入将其作为响应的一部分返回更新后的项，**不增加RCU成本**，并且没有一致性问题——写入的返回有效载荷在构造上就是权威的。在`UpdateItem`之后进行强一致性`GetItem`支付1 RCU并支付第二次往返以获取已经免费提供的信息。这是DynamoDB上读取-写入语义的最便宜形状。

16. 将每个访问模式解析为`GetItem`、`Query`或`BatchGetItem`。`Scan`适用于管理操作，而不是应用程序读取路径。需要扫描的生产访问模式反映了建模差距，而不是可接受的查询选择。

17. 限制每个查询。指定排序键范围或过滤条件，计算预期页面大小，并使用`LastEvaluatedKey`分页。约束可以来自键结构本身——一个包含有界数量子项的父分区（一个订单下的行项目、一个团队的所有成员）已经是约束的，并且“返回此父项下的所有项”是针对它的有效访问模式。无约束的查询结果大小随着数据集的增长而无限增长——例如，多年客户的“所有订单”、“日志中的所有事件”——没有范围、没有页面目标、没有终止条件。在增长的数据集中无限制的结果集是设计差距，而不是查询选择。

18. 计算每个访问模式的成本。读取定价取决于API：

    - **GetItem / BatchGetItem**：按返回的项计费，四舍五入到4 KB。最终一致性（默认）= 每项每4 KB 0.5 RCU；强一致性 = 每项每4 KB 1 RCU；事务性 = 每项每4 KB 2 RCU。`BatchGetItem`不提供请求级折扣——每个项都独立计费。
    - **Query**：按匹配键条件的项的总大小计费，四舍五入到4 KB，与`GetItem`相同的每4 KB速率。`FilterExpression`在计费后应用——丢弃90%匹配的过滤器不会将成本降低90%。
    - **Scan**：按检查的项的总大小计费——实际读取的表或GSI部分——在应用任何过滤器之前。这就是`Scan`在热点路径上是不正确选择的原因。

    写入定价：`WCU = 频率 × ⌈项大小 / 1 KB⌉ × 更新的副本数`。`UpdateItem`按**`max(之前, 之后)`项大小**计费，而不是差异，也不是仅按更新后大小——一个缩小的更新仍然支付较大预更新大小的费用（四舍五入）。事务性写入成本是2倍。`ConditionalCheckFailedException`仍然消耗与成功写入相同形状的WCU；将`conditional_fail_rate`纳入估计。

    如果这些公式无法为给定模式编写，则该模式指定不够精确，无法建模。

19. 默认使用按需容量；在证据出现时切换到预配置。按需移除了一类与容量相关的故障，并且是新的或可变工作负载的正确默认值。在持续高吞吐量且模式可预测时，预配置容量与自动扩展提供更低的单位成本。切换应由测量流量触发，而不是预期。

    **对于包含向量索引的表，按需不是默认值——它是强制性的。** 向量索引在预配置表上完全不受支持。必须将预配置表切换到`PAY_PER_REQUEST`才能创建索引，并且该切换受24小时容量模式冷却（事实#3）的限制，因此它是一个调度约束，而不是即时步骤。这也从任何包含语义搜索的设计中移除了预配置容量的选项，因此不要后来建议将此类表迁移到预配置以降低单位成本。

## 模式

这些是具体的实现模式，与公理并肩存在。它们不是“正确性/操作/成本/风格”意义上的公理——它们是即使没有公理明确要求，完整设计也需要的承重细节。每个模式都在参考架构中完整阐述；本节是简短形式，以便代理识别何时适用。

1. **使用`IdempotencyKeys`表保护可变API路由。** 每个可以由客户端重试的`POST`、`PUT`、`PATCH`或`DELETE`（例如移动网络中断、负载均衡器重试、用户双击）都必须用幂等中间件包装。形状：一个专用表，`PK = <user_id>:<METHOD>:<path>:<client-supplied-uuid>`，属性`status`、`response_status`、`response_body`、`expiration`（Unix纪元秒）。中间件在处理程序运行之前执行带有`attribute_not_exists(id)`的条件`PutItem`；在冲突时，它读取缓存的响应并返回它。TTL为24小时；PITR关闭（该表是一个缓存）。这是保持重试的“创建订单”不会导致客户重复收费或重复减少库存的机制——这是`TransactWriteItems`在*单个调用内*提供的保证，但在*重试之间*不提供。

2. **用条件表达式保护可变写入。两个部分——每当出现此模式时，两者都是强制指导。**

   **部分A——`attribute_exists(<pk>)`在`UpdateItem`上，除非你明确想要插入。** `UpdateItem`默认为*如果缺失则创建*。一个带有猜测或过时的`order_id`的`PATCH /orders/:id`会静默地创建一个幽灵订单行——没有错误、没有日志、没有恢复。为每个在调用者断言存在的行上运行的`UpdateItem`添加`ConditionExpression: attribute_exists(<partition_key>)`；捕获`ConditionalCheckFailedException`并将其转换为404。

   **部分B——`attribute_not_exists(<pk>)`在`PutItem`上，当你意味着“在覆盖时失败”。** `PutItem`默认为*如果存在则覆盖*。一个应该创建新订单的`POST /orders`（或新评论、新快递分配、新唯一起点标志）将静默地覆盖以相同方式键入的现有行而没有保护。为每个应该如果键已存在则失败的`PutItem`添加`ConditionExpression: attribute_exists(<partition_key>)`；捕获`ConditionalCheckFailedException`并将其转换为409冲突。

   条件写入是数据层中不变性存在的位置。当你推荐一半时，要揭示另一半——设计评审通常会捕获在添加了`UpdateItem`保护但多年未添加`PutItem`保护的应用程序中遗漏的`PutItem`保护。

3. **TTL属性是Unix纪元秒。三种常见的格式错误会静默地破坏过期——在诊断“TTL没有删除任何东西”报告时，要枚举所有三种。** DynamoDB TTL将属性读取为数字，并将其解释为自纪元以来的秒数。以下任何一项都会导致TTL静默地永远不会触发（没有错误、没有日志——清理程序只是跳过该行）：

   1. **秒而不是毫秒。** JavaScript中的`Date.now()`返回毫秒；如果不变更地写入，时间戳会大约是1000倍太大，并解析为50000年后的时间戳，该时间戳永远不会在过去。修复：JS中的`Math.floor(Date.now() / 1000)`，Python中的`int(time.time())`。
   2. **ISO 8601字符串而不是数字。** Python中的`datetime.datetime.now().isoformat()`或JS中的`new Date().toISOString()`生成一个像`"2026-05-13T09:45:00Z"`这样的字符串。DynamoDB TTL将字符串读取为非数字并完全跳过该行。
   3. **错误的属性名称。** TTL按表配置了特定的属性名称（`ttl`、`expiration`、`expires_at`等）。如果应用程序写入`expires_at`但TTL配置在`ttl`上，或者如果打字错误拆分了属性，TTL会扫描一个不存在的属性并跳过该行。验证表TTL规范中配置的属性名称与应用程序写入的完全匹配。

   在写入时验证：将任何大于`current_time + 50年`的TTL值标记为可能的毫秒与秒错误，然后再到达表。在整个代码库中标准化属性名称。这与Mechanics #12配对：即使TTL配置正确，“读取时过滤”纪律仍然适用，因为即使TTL配置正确，删除也是最终性的。

4. **不要持久化`Notifications`表用于瞬态推送/电子邮件/SMS。** 在此处的每个领域名词创建表的冲动是一个陷阱。如果通知是发送后即忘——推送到APNS/FCM、通过SES进行事务性电子邮件——正确的形状是**EventBridge → SQS → NotificationLambda → 交付服务**。DynamoDB用于需要*之后查询*的状态。只有在您有对其具有真实读取访问模式的`Notifications`表时才创建它——用户的内部应用程序收件箱、交付状态仪表板、合规审计。否则，您正在支付DynamoDB写入成本以永远不读取结果。如果需要每个用户的收件箱：`PK = user_id`，`SK = <createdAt>#<notificationId>`，对旧条目进行TTL。

5. **计划级联删除时，应使用分块的 `BatchWriteItem`，而不是同步 API 调用。** 在分层架构（如看板、订单、租户、GDPR 下的用户）中删除父实体需要删除其下所有键值。使用 `BatchWriteItem`（每批 25 项）并使用 `Query(..., Limit=25, LastEvaluatedKey=...)` 进行分页处理。这是一个后台任务，而不是同步 API 响应——在大规模情况下，遍历过程可能足够长，以至于超出典型的 Lambda 超时时间，并且必须可重试。如果 GDPR 或监管删除是该领域的要求，应将此任务明确作为设计的一部分；不要假设它会从架构中免费得出。

## 成本估算

设计和讨论数据模型是默认的无 AWS 路径，用户通常会在不希望得到美元数字的情况下探索选项——键、GSIs、单表与多表、投影权衡——。**不要在每次设计转折时都运行计算器。** 当以下任一情况发生时，才生成月度成本估算：**(a)** 用户询问成本（或成本报告），或 **(b)** 设计正在最终确定——他们表示接受它，将其提交给评审，或以其他方式希望数字得到确认。在此之前，请继续进行设计讨论。

当未生成完整设计时，完全跳过估算——单查询尺寸、热点分区调试线程、具体的机械问题。在这些情况下没有可估算的内容。

当你确实生成估算时，三个步骤是必需的：(a) 编写 `dynamodb_data_model.json`，(b) 调用 `${SKILL_DIR}/scripts/calculate_costs.py`，(c) 在你的摘要中引用生成的 `cost_report.md`。**在计算器中内联计算数字绝不是替代方案**——即使是为了“粗略”或“现实”的数字，也不是，即使是为了将标题数字与声明的每日流量进行核对（为此，请设置 `avg_rps` 并让计算器生成预期流量场景——见下文）。计算器强制执行定价模块，该模块保持与实时计费校准；手动进行计算会导致数字无声地漂移，用户会提交他们无法辩护的报价。

计算器位于 `${SKILL_DIR}/scripts/calculate_costs.py`。它消费的 JSON 架构文档位于 `${SKILL_DIR}/references/cost-model-schema.md`——第一次生成成本估算时，请阅读该文件。

工作流程：

1. **将设计序列化为 `dynamodb_data_model.json`。** 计算器不会重新发明设计——它读取你已经生成的。你构建的访问模式列表（根据机械 #2、#18）是直接翻译成 JSON 的 `access_patterns` 数组；你构建的架构（根据数据建模 #3、#7、机械 #4、#7）转换为 `tables`、`gsis`——当设计有一个时——`vector_indexes`。如果计算器需要的字段缺失（最常见的是模式上的 `peak_rps`），那本身就是设计中的差距——通过询问用户或做出可辩护的假设并将其标记为假设来弥补它，而不是写入 `0`。

   **向量索引作为 `vector_indexes` 条目进入模型，其搜索作为带有 `top_k` 的 `SearchVectors` 访问模式进入。** 计算器支持这两种（完整形状在 `${SKILL_DIR}/references/cost-model-schema.md`）。注意与服务 API 的不对称性：你使用 `VectorIndexes` **CreateTable 参数**（事实 #10）*创建*索引，但你使用 `vector_indexes` **模型字段***计算*它。知道 API 形状并不等于知道模型形状，混淆两者会导致向量索引的成本为零。

   **如果你发现自己得出“计算器不支持向量搜索”的结论，那么你的模型中缺少向量索引——修复模型，不要退回到计算。** 计算器对向量索引存储和向量 **写入** 容量进行定价，并将两者都包含在标题中；它故意拒绝定价向量 **搜索**，打印 `not priced` 并附带脚注和测量驱动因素。这两部分已经得到处理，因此手动计算任何一部分都是上述规则禁止的内联计算。这不是一个小错误：在一个 1024 维的 `ALL`-投影索引上，对 ~3 KB 的项，向量写入通常是估算中**最大的单行**——在 200 rps 对应 **$1,942/月**，而基础表写入本身为 **$972/月**——因为 `ALL` 在每次写入时都会将整个项复制到索引中。目测这个数字可能会低估真实的主要成本驱动因素超过一个数量级。

   **当用户声明平均或每日流量时，在模式上设置 `avg_rps`——不要手动计算“现实”的数字。** 标题是峰值持续（每个模式在 `peak_rps`，24/7）；一个听到 15K 订单/天工作负载的大峰值持续月度数字的用户也需要预期数字。设置 `avg_rps`（例如 15,000 订单/天 ÷ 86,400 s ≈ 0.17 rps 平均，与 600 rps 黑色星期五峰值相比）使计算器在平均速率下发出第二个 **预期月度成本** 标题。这是*唯一*产生现实流量数字的合法方式——用心理算将峰值标题与每日流量进行核对，正是上述规则禁止的内联计算。

2. **运行计算器。** 将 JSON 写到你的工作区路径，并调用：

   ```bash
   python3 ${SKILL_DIR}/scripts/calculate_costs.py --model /path/to/dynamodb_data_model.json --output /path/to/cost_report.md
   ```

   JSON 是一个中间产物。你不需要向用户展示它，除非他们要求。

3. **展示成本报告。** 返回 `cost_report.md`——如果简短，则内联（或作为文件指针）。突出报告展示的主要驱动因素（“按降序排列的成本模式”表），并指出你嵌入的假设（估计的 RPS 数字、假设的保留期、一致性选择）。报告顶部的免责声明是工件的一部分——不要删除它。

4. **使用成本报告来挑战设计，而不仅仅是报告数字。** 成本估算具有诊断性。如果一个模式主导账单——经典的案例是高频写入，如 GPS 响应——那是一个建模信号，而不仅仅是行项目：重新审视聚合选择（机械 #1）、投影形状（机械 #7）、是否稀疏-GSI-在转换中会降低放大（机械 #6），或者该模式是否完全不属于 DynamoDB（集成 #8）。提出替代方案，并在修订后的模型上重新运行计算器。这是捆绑计算器的主要价值：从“这是设计”→“这是账单”→“这是更便宜的设计”的反馈循环变成几个回合，而不是一个单独的练习。

计算器仅模拟请求和存储成本。它不模拟 Streams 读写成本、PITR、备份、DAX 或数据传输。如果这些行项目对工作负载可能是重要的，请在估算旁边指出，以便用户知道数字排除了什么。**存储按完整公共费率定价——25 GB 免费套餐不被假设**（它是跨账户的，并且通常已经使用），因此永远不要告诉用户“存储是免费的”。将写入模式的 `retention_days` 设置为其存储数据的大小；计算器会尊重它。存储数字是一个**有保留期的快照**，在 `retention_days` 时——对于没有 TTL/“永久保留”数据的表，真实存储会持续增长超过快照，因此**不要**将稳态存储数字重新表述为“N 年后”：要么声明数字假设的保留窗口，要么注意无 TTL 表会无限累积。

**在最终响应中命名工件。不要让工具调用消失在散文中。** 用户阅读你的自然语言输出，而不是你的 shell 历史记录。在运行 `calculate_costs.py` 后，你的响应必须命名 (a) 你写入的 JSON 文件 (`dynamodb_data_model.json`)，(b) 你调用的脚本 (`${SKILL_DIR}/scripts/calculate_costs.py`)，以及 (c) 它生成的报告文件 (`cost_report.md`)。一个显示成本数字但未命名工件文件的响应读起来就像你手动计算的——工作流程证据必须在散文中，而不仅仅是在工具跟踪中。

## 实时验证

在成本估算之后，**提供运行实时验证**——将表和 GSI 部署到用户指定的 AWS 账户，并驱动缩小的流量以测量真实的每操作容量和往返延迟。用一句话询问，并且只有在明确同意的情况下才运行。即使在那一句话的提议中，也要命名用户需要负责任地选择入的**两个约束**：它仅在**沙盒/测试账户**上运行（永远不会在生产或真实用户数据上运行），并且**清理是他们的责任**（技能会返回一个 `teardown.sh`，并且只有在用户明确审查并指示技能运行它之后才会执行）。完整的四事实披露在部署之前仍然到来——这只是为了让这一句话的提议不会误导性地轻描淡写。对于窄问题——单查询尺寸、指向调试、指向机械——没有生成完整设计，并且没有可基准的内容时，跳过。

**在运行之前，在你的措辞中明确安全预期**（`deploy_model.py` 脚本也会打印一个警告横幅，但这只是一个双重保险——代理负责设定预期）。**在你的响应中逐字陈述以下四个事实；不要将它们简化为摘要**：

1. 实时验证**在用户指定的 AWS 账户中创建真实的 DynamoDB 表、Lambda 函数和 IAM 角色**。
2. 它**会产生真实的（小）AWS 费用**——实践中是单个数字的几美分，但确实有账单。
3. 该账户**必须是测试或沙盒账户**——永远不会是生产账户，永远不会是持有真实用户数据的账户。
4. 技能**不会自动清理**——在结束时，用户会收到一个 `teardown.sh` 脚本进行审查，并且只有在用户明确审查并指示之后，技能才会代表他们执行它。

陈述这四个事实后，要求用户明确命名配置文件、区域，并确认账户的用途。只有到那时才生成 `benchmark_config.json` 并调用 `deploy_model.py`。如果用户没有指定测试账户，停止并询问。将此缩短为“这会创建真实资源，确认你的配置文件”**不是**足够的——列出四个事实，因为用户通常不知道具体创建了哪些资源，也不知道清理是他们的责任。

此步骤与成本估算的不同之处在于两点，这改变了它必须如何运行：

1. **真实资源，真实账单。** 缩小运行在实践中可能只花费几美分，但针对真实账户。永远不要无声运行。始终需要一个明确的 AWS 配置文件、区域和调用者身份确认。
2. **清理是两阶段的。** 阶段 1：技能生成 `teardown.sh` 并将其交给用户。阶段 2：技能可能会执行它——但只有在用户明确表示他们已审查脚本并且明确指示技能运行它之后。技能永远不会自行调用 `DeleteTable`，并且永远不会基于一个“开始”或“继续”就运行 `teardown.sh`。

**拒绝通过明确列出四个先决条件来开始。** 将它们作为编号项目在你的响应中展示；不要将它们折叠成一个通用的“我需要更多信息”段落。展示**具体的**失败先决条件，以便用户知道是什么阻止了运行：

1. `access_patterns` 为空，或者任何模式有 `peak_rps` 缺失或 `0` → 拒绝，并根据机械 #2 框架：“未知的 RPS 是设计差距，而不是基准输入。模式 `<id>` 没有声明的 RPS——请在基准测试前提供估计。”
2. `boto3` 未安装 → 打印确切内容：`pip install boto3>=1.34`。
3. AWS 凭据缺失或过期 → 打印确切的补救措施，例如对于 SSO，`aws sso login --profile <profile>`，或者特定 boto3 异常建议的修复方法。
4. 调用者身份的账户别名或 ARN 包含 `prod`、`production`、`prd` 或 `live` → 拒绝，并告诉用户提供一个沙盒/测试配置文件。

在写入 `benchmark_config.json` 或调用 `deploy_model.py` 之前，检查所有四个。一个通用的“我需要更多信息”的概括不能满足合同——列出失败的特定先决条件。

**工作流程**，一旦用户同意：

1. 重用成本估算中的 `dynamodb_data_model.json`。不要重新序列化。

   **在部署之前，确认每个数字/二进制键声明了其类型。** 部署通过查找每个键属性（表 + GSI 分区/排序键）在 `entities[].attributes[]` 和 `attribute_definitions` 中，并将任何它找不到的默认为 `S` 来构建每个表的 `AttributeDefinitions`。一个数字时间戳排序键或数字 ID 如果未声明，则部署为字符串，然后拒绝真实写入 `ValidationException`。根据数据建模 #11，确保每个这样的键在模型中带有 `"type": "N"`（或 `"B"`）——在此步骤之前——并且不要信任干净的种子作为证据，因为失败可能只在真实写入时才出现。如果你想要双重保险，`DescribeTable` 部署后并确认键的 `AttributeType`。

   **当设计有多个模式时——警告、估算并获取确认。** 基准测试按顺序驱动模式（每个模式运行自己的预热 + 测量窗口一次），因此时钟时间随模式数量增长：大致为 `table_settle + Σ_patterns (warmup + duration)`。在标准窗口（~10s 预热 + ~60–90s 持续时间）下，6 模式设计只需几分钟，但 **20+ 模式设计需要 25–45+ 分钟** 并被分成几个连续的 Lambda 调用。在启动一个具有超过 ~8 模式的设计的运行之前：提供一个大致的时钟时间估算，并 **获取明确的确认**（“这将基准测试所有 24 个模式，并将花费 ~35–45 分钟——继续，还是你宁愿测试一个集中的子集？”）。不要无声地启动一个 40 分钟的运行。

   **提供仅对关键模式进行负载测试，并与用户一起选择。** 完整的实时运行很少需要每个模式——大多数都是计算器已经精确计算的廉价结构化查找。提供基准测试一个集中的子集，并与用户合作选择它们，引导到实际测量确实能带来价值的模式：
   - **最高吞吐量/消防水写入**——那些 RPS 占据主导地位或压力容量的模式（例如位置 ping 写入）。
   - **事务性/多项目核心**——`TransactWriteItems`、多表写入、结账路径（事务 2× 成本，机械 #18，值得实时查看）。
   - **新颖或风险键形状**——任何具有发散读取（N 个并行查询）、热点风险或不确定 GSI 的内容；跳过无聊的按 ID 获取 `GetItem` 模式。
   - **成本主导模式**——成本报告标记为顶级驱动器的任何内容。

   要运行子集，基准测试模型的**修剪副本**：保留**所有 `tables`**（以便架构部署和正确播种），但修剪 `access_patterns` 到选定的几个。**成本估算不受影响**——它始终在完整模型上针对声明的峰值运行；子集仅缩小*实时驱动流量*，而不是设计或其成本。命名你正在测试的模式以及你跳过的模式（以及原因），以便用户看到覆盖权衡。

2. 编写 `benchmark_config.json` — profile 和 region 是你唯一必须设置的字段（`resource_prefix` 如果省略将由部署自动生成；其他所有内容都有模式驱动的默认值）。第一次读取 `${SKILL_DIR}/references/performance-model-schema.md`。**在写入文件之前，询问用户要运行哪种模式——不要默默选择默认值。** 对于一次性实时验证，选择是在以下两种单位成本模式之间；第三种模式 **`"representative"`** 是迭代设计循环的模式（在有限规模下的热键偏斜），在 *迭代设计循环* 下描述——仅在用户想要探测热分区/限流风险时提供，而不是用于普通的成本验证运行。

   **诚实地声明驱动吞吐量，并提议加大驱动力度。** 这是实时验证中最重要的事情。默认情况下 `quick`/`standard` 仅驱动一小部分声明的峰值（`scale_factor` ~0.01，向下取整到 `min_rps_per_pattern`）——对于峰值适中的设计，这会向下取整到 **~每秒1个请求/模式**。这是一个 **单位成本样本**：它验证每次操作的容量（成本）和 *未加载* 延迟，并且很便宜（几美分，~1–2分钟/模式）。它 **不** 执行负载——在 ~1 rps 时，零限流在数学上得到保证（按需基线为 ~2,000 WCU / ~4,000 RCU）并且延迟是最佳情况。所以当你提供运行选项时，说明这是哪种情况，并提供替代方案：
   - **单位成本样本（默认）** — 验证成本 + 未加载延迟。便宜。不测试负载/限流。
   - **在/接近声明峰值驱动** — 一个真实的负载测试。在 `benchmark_config.json` 中设置 `scale_factor`（声明的峰值的分数，例如 `1.0` 表示完整峰值）或 `max_rps_per_pattern`；两者都会得到尊重。受限于单个区域内 Lambda 的上限（~1,500–2,000 rps/模式），并由 `cost_guardrail_usd` + `--allow-spend` 控制门禁（因此昂贵的运行不会默默触发）。**注意**：新创建的按需表从 ~2,000 WCU / ~4,000 RCU 基线开始，并滞后地向上适应，所以部署后立即以高速率测量的是冷启动自适应容量预热，而不是稳态——运行已经具有 `ramp_seconds` + `table_settle_seconds` 来吸收一些这种；对于干净的 高rps 读取，使用更长的 `duration_seconds`。
   - **`representative` 模式** — 循环的热键/限流风险模式（在有限规模下的 Zipf 偏斜）；在热分区行为是问题时使用（见 *迭代设计循环*）。

   外推的月度 **成本在 `quick`/`standard` 和任何吞吐量下都相同** — 每次操作的 CU 是确定的，成本外推始终使用声明的峰值，所以更高吞吐量的运行为你提供了负载下的延迟和限流信号，**不是** 不同的成本数字。**始终在运行前告诉用户你将驱动的每模式速率。** 将模式选项作为直接问题发出，并等待用户选择：

   > 我应该运行哪种模式？选择一个：
   > - **`"quick"`** — ≈每模式窗口1分钟，一个确认设计部署和运行的烟雾测试。百分位数不太稳定。一个单位成本样本（为峰值适中的设计驱动 ~1 rps/模式）：验证成本 + 未加载延迟，不测试负载。
   > - **`"standard"`**（默认）— 完整长度的窗口，稳定的 p50/p95/p99，可信的外推月度成本。默认仍然是单位成本样本（相同的 ~1 rps/模式）——成本数字与 `quick` 相同；你得到更紧密的延迟百分位数，而不是负载测试。要使其成为负载测试，告诉我在声明的峰值附近驱动。
   > *(还有 `"representative"` — 迭代设计循环的热键/限流风险模式。仅在热分区行为是问题时提及；见 *迭代设计循环*。)*

   将用户选择的价值写入 `benchmark_config.json` 的 `mode` 字段。如果用户跳过问题，只是说“开始”，默认为 `"standard"` 并在回复中命名该默认值（“由于你没有指定，我将运行 `standard` 模式——如果你意思是 `quick`，请中断”）。
3. 部署：`python3 "$DDB_SKILL_DIR/scripts/deploy_model.py" --model … --config … --manifest-out created_resources.json --yes-deploy`。打印调用者身份以确认，在产品标记上中止，将每个资源前缀为 `ddb-skill-bench-<date>-<uuid8>-`（如果你没有设置 `resource_prefix`，会为你生成），并使用运行 ID 标记。在交互式终端上，它在打印帐户后等待几秒钟以允许 Ctrl-C 中断；在代理/CI 运行中，在 `--yes-deploy` 同意后立即进行。
4. 基准测试：`python3 "$DDB_SKILL_DIR/scripts/benchmark_model.py" --model … --config … --manifest created_resources.json --raw-out perf_raw.jsonl --summary-out perf_summary.json`。自动处理冷启动纪律（见下文）。

   **执行纪律——在前景中运行并等待。** 一个 `representative` 运行会驱动几分钟的流量（≈ 稳定 + 每个模式的预热 + 每个模式的持续时间跨所有模式——对于多模式设计通常为 15+ 分钟）。将基准测试作为 **单个阻塞调用运行并等待它完成——不要后台化它并将控制权交还给用户。** 后台运行的基准测试可以在周围的回合/会话结束时被杀死，留下 *上一个* 运行的 `perf_summary.json`——这恰好是读取陈旧摘要的方式。如果运行有风险超过你的工具的墙上时钟限制，**提高工具超时——不要缩小窗口或后台化作业。** 你不需要手动调整 `duration_seconds` 以适应预算：重工作在 Lambda 内运行（≤900 秒服务器端），并且 `benchmark_model.py` 已经将负载跨顺序调用分割（`_compute_split`）。完成后，记下你启动它的 UTC 时间；你将在第 5 步中将其与摘要的 `benchmark_completed_at` 进行比较。
5. 报告：`python3 "$DDB_SKILL_DIR/scripts/generate_perf_report.py" --model … --summary perf_summary.json --output performance_report.md`。

   **在解释之前，诚实地验证摘要是否新鲜并且与你在描述实验之前所描述的匹配（操作纪律，已应用）。** `perf_summary.json` 记录 `benchmark_completed_at`（UTC）和运行实际使用的配置。在生成或信任报告之前，确认 **(a)** `benchmark_completed_at` 比你在第 4 步中记录的启动时间更新，并且 **(b)** 摘要的 `config`（`mode`，`provisioned_capacity`，`duration_seconds`）与为 *此* 运行设置的匹配。如果任何一项失败——或者该字段不存在——基准测试未完成，你正在查看一个陈旧文件：**不要解释它，重新运行。** 报告的部署部分会显示 `benchmark_completed_at` 和运行窗口，以便用户可以看到相同的内容。你正在读取陈旧数据的迹象：基准数字与预期不同的先前运行完全相同。

**操作按声明执行，永不替换。** 当设计说 `BatchWriteItem`，基准测试以 25 项批次发出 `BatchWriteItem`。当它说 `TransactWriteItems`，基准测试使用声明的项集发出 `TransactWriteItems`。不使用单项替换（例如，用 `PutItem` 循环替换 `BatchWriteItem`，或为 `TransactWriteItems` 使用单独的 `PutItem` 调用）——它们测量不同的设计。事务 2× 写入成本（机制 #18）、批量部分失败语义和事务边界（机制 #14）是实时验证观察到的确切内容；替换它们会破坏目的。如果用户询问基准测试如何执行批量或事务模式，明确说明声明的操作按声明运行，并命名基准测试将观察到的特定边界。

**冷启动纪律。** DynamoDB 延迟和吞吐量在新表上 t=0 时不稳定；在此处没有纪律地收集的数字会误导地看起来比稳态更差。在测量值得信赖之前，必须消除三类偏差：

- **新表的容量。** 按需表从基线容量（~2,000 WCU，~4,000 RCU）开始；在最初几分钟内，基线以上的流量可能会被限流，直到自适应容量扩展。在 `table_exists` 返回后，在测量调用之前至少等待 `table_settle_seconds`（默认 30）。
- **分区预取和客户端预热。** 种子写入会预热基准测试稍后将击中的分区，并且新的 boto3 客户端在其第一次调用时（几十到几百毫秒）会携带 TLS 握手 + 凭证刷新。基准测试在种子和测量之间暂停，并为每个工作线程发出一个 `DescribeTable`，所以这些一次性成本不会出现在百分位数中。
- **每个模式的预热窗口。** 每个模式在其测量窗口之前运行一个 `warmup_seconds` 窗口（默认 10）。预热调用记录为 `phase: "warmup"` 并从延迟百分位数和成本外推中排除。性能报告单独显示预热 p99——如果它明显高于稳态 p99，这本身描述了冷部署行为，值得指出。

**什么被测量和什么不被测量：**

- 测量：每次操作的消耗 RCU/WCU 从 `ReturnConsumedCapacity`；往返延迟 p50/p95/p99（预热和稳态分别报告）；限流计数；GSI 写入放大；每个模式的均匀分布信号；基于观察的外推月度成本。
- 未测量：TTL 扫描节奏、流消费者延迟和成本、持续突发下的自动扩展、跨区域复制延迟、测量窗口之外的长期尾部流量形状以及设计中的任何非 DDB 服务（Lambda、API Gateway、SQS、EventBridge Pipes、OpenSearch 等）。性能报告将这些列在“设计，未基准测试”下，以便用户清楚地看到其架构的哪些部分被数字覆盖。

报告格式在 `${SKILL_DIR}/references/performance-report-format.md` 中记录。它镜像 `cost_report.md` 的先声明后表格驱动风格，并按模式打印观察到的和计算器预期的数字，以便用户看到他们的输入（RPS、项大小、一致性）与现实有何不同。

**反思发现并提议迭代循环。** 报告写入后，将其作为诊断阅读——而不是最终分数——并询问：是否有替代设计，测量认为它更好？对于每个发现，分类：

- **输入准确性查找** — 观察结果与计算器结果不符，因为声明的输入（RPS、项目大小、一致性、`conditional_fail_rate`）存在偏差。设计本身没有问题；需要更新输入来重新估算。建议更新JSON并重新运行计算器（成本较低，无需重新部署）。
- **设计问题** — 观察结果揭示了一个与输入准确性无关的结构性问题。示例及其支配公理：
  - 持续的、随分区键偏差缩放的限流器 → 机制#3（每个分区的上限，对热键进行写分片）。**在将限流器归因于热分区之前，必须运行偏差与饥饿门控——两部分都必须通过：** (1) **差异测试** — 热分区的p99必须显著高于冷分区的p99（报告中的~1.8×规则）。如果热p99 ≈ 冷p99，则每个分区都均匀限流：即**容量饥饿，而非键偏差** — 如此说明，并**不要**将其归因于分区键。 (2) **统一基线测试** — 使用报告已打印的每操作观测CU（不是手动推导的项目计数），检查在驱动的RPS下，均匀键是否已超过配置的上限；如果会超过，则该运行无法隔离偏差 — 建议以高于均匀需求的能力重新运行，以便只有真正的热分区限流。只有当两部分都通过时，“热分区已达上限”才是一个支持的结论。注意：对*可变*分区键（例如每次转换都变化的键）进行写分片会分散机制#3的负载，但键在每次写入时仍会变化，因此机制#8（可变GSI键）的偏差**仍然存在**，必须根据工件#5逐条记录 — 消除写放大需要一个单独的专用表，而不是分片后缀。
  - 一种模式主导了账单 → 机制#1（聚合紧密度），机制#7（投影），集成#8（在分析型工作负载、高频遥测或全文搜索时将DDB迁移到Timestream/S3/OpenSearch/Redshift/SageMaker Lakehouse）。
  - GSI写放大高于投影 → 机制#6（当可变键不总是存在时使用稀疏GSI），机制#7（降级所有 → INCLUDE/KEYS_ONLY），机制#8（可变属性作为GSI键会使写操作翻倍）。
  - 在实际不需要RW语义的情况下观察到强烈的读成本 → 机制#15（默认为最终），围绕`ReturnValues=ALL_NEW`的模式以避免写后重读。
  - 无限查询反复达到900 KB页面上限 → 机制#17（限制每个查询；要求时间窗口或最大页面）。
  - 在按需基线时冷启动p99显著升高 → 能力模式或预热决策（机制#19），通常不是模式更改。

1. 哪些发现指向设计更改，哪些指向输入准确性。
2. 对于每个设计发现，它追溯到的公理以及**`dynamodb_data_model.json`上的确切JSON差异**——不是口头描述。将差异作为代码块输出，显示特定字段的变化（新的GSI对象、删除的GSI、更改的`projection.type`、带哈希后缀的分片PK、完全从`access_patterns`数组中移除的模式）。像“考虑降级投影”这样的口头建议不满足要求——用户必须看到确切的变化，以便他们可以接受或拒绝。当差异更改一个**GSI的键**（分片分区键是常见情况）时，根据事实#9将其标记为**加性-GSI迁移**，而不是纯代码更改——新索引是创建、填充、切换，然后删除旧索引。示例形状：

   ```diff
   - { "name": "OrdersByCustomer", "projection": { "type": "ALL" } }
   + { "name": "OrdersByCustomer", "projection": { "type": "INCLUDE", "non_key_attributes": ["status", "total"] } }
   ```

3. 对主要成本驱动因素和限流源的预期影响。

**你的口头结论继承报告——不要超过它。** 你给用户的聊天摘要不得声称报告未分类的结果。具体：

- 如果报告未发出**`key_skew_patterns`发现**，则**不要**说设计“限流”或“热分区”——支持的说法是报告自己的（“在偏差下未观察到热分区压力”/“未通过本次运行验证”）。
- 重申报告的保留意见；不要升级它。“在故意设置的低上限下出现限流”**不是**“GSI分区是热的”（见上文的偏差与饥饿门控）。
- 将每个数字归因于它支持的确切声明。低配置上限导致限流证明**表未按驱动负载配置**，而不是任何单个分区键是热的。
- 工作对比——相同数据，两个结论：❌ “确认：OrdersByStatus GSI在负载下严重限流。” ✅ “在50-WCU上限下，Orders表的写入限流——但热分区p99 ≈ 冷分区p99，所以这是均匀容量饥饿，而非键偏差。该运行未隔离热分区效应；要测试该效应，请以高于均匀需求的能力重新运行。”

- **将用户引用的任何数字与你的最新工件进行比对——不要只是同意。** 当用户重述一个数字（“$189/月可以接受”，“所以那个分区是~600 WCU”，“1,884次限流”）在你回应之前，检查它是否与当前`cost_report.md` / `perf_summary.json` / `performance_report.md`中的实际数字一致——在确认该工件本身是最新（根据步骤5）后，因为与*陈旧*摘要匹配的数字不是真实的比对。如果不匹配——即使用户听起来很自信，尤其是在接受会是可接受的举动时——明确纠正并引用工件：“快速更正：报告说预期**$835/月**，不是$189——$189是一个早期数字。仍然要继续吗？” 默默接受一个错误的数字，用户随后会将其带入预算演示或设计审查中，这比瞬间摩擦更糟糕。这适用于成本、能力计算、限流/延迟计数和项目大小假设。用户提供的数字是验证的输入，而不是批准的结论。
- **不要担保运行未建立的主张。** 你的口头结论可以断言你面前工件的实际情况。如果你即将陈述的数字来自你自己的头脑而不是报告（手动推导的配置/保留成本，“线性扩展，所以25k rps可以接受”从2k-rps运行跳跃，基准从未隔离的每分区数字），将其标记为推理，而不是测量，并给用户背后的结构化论点——永远不要将估计包装为已验证的结果。“计算器仅模拟按需；保留数字是我的手动计算，用于*配置*替代方案（保留容量仅适用于配置——事实#7）从公开费率——在演示前与AWS计算器核对”是诚实的。将手动计算作为“已验证”是不正确的。

不要无声迭代，不要无限迭代。每次迭代都是明确的、可选的；如果用户拒绝或报告未发现有意义的结果，停止并返回最终工件。

## 迭代设计循环

上述三个重新评估级别作为**轮次**运行，由`${SKILL_DIR}/scripts/iterate_design.py`协调。这是“部署→在代表性规模测试→获取反馈→更改设计→再次测试”的无缝路径。

**它是什么——以及不是什么。** 单次调用=**一轮**：可选地应用用户同意的更改→决定重用vs重新部署→（受限制的）部署或重用→在代表性规模基准测试→报告→**揭示发现+建议**→停止。循环是**人工驱动的**：你运行一轮，呈现发现和具体建议，然后返回。**用户**决定要更改什么并提示下一轮。永远不要自我迭代到收敛；永远不要在一个调用中开始第二轮；脚本强制执行这一点（它没有提出或选择更改的逻辑——它只应用它被赋予的更改）。

**代表性模式（诚实范围）。** 循环运行`mode: "representative"`（见`${SKILL_DIR}/references/performance-model-schema.md`）：~0.10–0.25×声明的峰值，带**Zipf热键采样**和**真实的项目收集基数**。这揭示了1%-规模单位成本运行无法揭示的内容——**热分区限流（机制#3）、负载下限流、高容量GSI放大和按实际基数查询**。向用户明确说明范围：一个区域内的Lambda驱动~1,500–2,000 RPS/模式最大（32个驱动线程），因此代表性规模是**有界的**——它以有界成本揭示热分区/限流风险；它**不**证明设计能承受声明的峰值。每操作成本外推保持线性且有效（每操作CU是规模不变的，外推基于*声明*峰值）；限流/延迟数字是报告的“负载风险信号”部分中的负载风险信号，永远不要线性外推。

**超过一个Lambda的极限（尚未构建）。** 如果设计需要超过一个Lambda的~1,500–2,000 rps/pattern，路径是调用*相同的部署基准函数并发*（Lambda可以免费水平扩展——无需部署多个函数），每个调用驱动`target_rps / N`的负载，种子一次完成，结果合并（调用/限流/错误相加；每操作CU是调用加权平均值；延迟百分位数是从原始行已携带的每个调用延迟池重新计算的）。这种负载分片**尚未实现**——今天一个Lambda是极限。不要承诺高于它的速率；提供代表性模式或注明极限。

**每轮受限制的同意。** 真实的部署和真实的卸载每轮都需要明确的用户同意。上述四个实时验证事实（真实资源、真实费用、沙盒仅、无自动卸载）每轮都适用。`iterate_design.py`在没有`--yes-deploy`的情况下拒绝部署；基准测试在没有`--allow-spend`的情况下拒绝超出`cost_guardrail_usd`。两阶段证明卸载（实时验证步骤6）保持不变，并且仍然是唯一的卸载路径——模式更改轮次告诉用户首先运行先前的`teardown.sh`，以免资源被遗弃。

**按需vs.配置，以及为什么限流可能不会出现。** 代表性运行默认按需部署（PAY_PER_REQUEST），匹配技能的机制#19默认。按需，**自适应能力隔离并吸收单个热键**——热分区通常表现为*该分区的尾部延迟升高*，而不是限流，因为表自动扩展来服务它。因此，`key_skew_patterns`信号在**限流或热分区p99显著高于冷分区p99**时触发（无基线、模式内比较），所以按需设计仍然会发出警告。要观察到硬**限流**，在`benchmark_config.json`（或按表）中设置`provisioned_capacity: {"read": N, "write": M}`——低配置上限没有自适应吸收，因此热分区确定性地限流；这也是验证*计划*配置能力的方法。基准测试Lambda运行时**禁用客户端重试**，因此限流被观察到并计数，而不是被沉默地重试掉。注意，新创建的配置表带有~5分钟的突发能力，在短窗口开始时掩盖限流——使用更长的`duration_seconds`或更低的能力来耗尽它。

**你遵循的轮次协议：**

1. 调用 `python3 "$DDB_SKILL_DIR/scripts/iterate_design.py" --model dynamodb_data_model.json --config benchmark_config.json --loop-state loop_state.json --manifest created_resources.json [--apply-change change.json] --mode representative [--timestamp <iso>] [--yes-deploy] [--allow-spend]`。`--timestamp` 是 **可选** 的 — 如果不需要 loop-state 条目携带特定的时钟（例如可重复的测试），则省略它，该轮次会使用当前的 UTC 时间进行标记；只有当你需要 loop-state 条目携带特定的时钟时，才传递一个 ISO 字符串。一轮运行一个代表性基准测试，因此与 *Live validation* 步骤 4 相同的 **执行规范** 适用：将其作为 **单个阻塞前台调用并等待** — 永远不要将其后台化（被终止的轮次会留下陈旧的工件）— 如果需要，则 **提高工具超时** 而不是缩小窗口。在传递任何结果之前，按照步骤 5 验证新鲜度（轮次的 `loop_state.json` 标题和 `design_findings.json` 源自同一个 `perf_summary.json`；如果没有刷新，则轮次未完成）。

2. 仅读取 **紧凑型** 工件：`design_findings.json`、`cost_report.md` 和 `loop_state.json`。永远不要读取 `perf_raw.jsonl`（大型）或 `performance_report.md`（面向人类）。

3. 传递该轮次的紧凑型摘要和来自 `loop_state.json` 的与先前轮次的差值（例如，“分片 PK cut W1 限制 1450 → 0, p99 减 70 ms”）。将每个建议的更改作为 `dynamodb_data_model.json` 上的 **字面 JSON 差分** 提出（与上述迭代提议相同的差分要求）。然后停止并询问用户要更改的内容，或是否接受。

4. 当用户选择更改时，在下一轮中将其作为 `--apply-change` 传递（一个 `merge` 对象或一个 `ops` 列表）；将他们的决定记录在 `loop_state.json` 的 `user_decision` 中。

**三个重新评估层级如何映射到循环**："仅计算器" → `iterate_design.py --calculator-only`（应用更改、重新计算成本、不使用 AWS）；"计算器 + Live validation" → 一个完整的代表性轮次（受限制的部署或重用）；"无更改" → 将 `user_decision` 记录为 Artifact #5 的偏差并停止。循环 **扩展** 提议，而不是取代它。`quick`/`standard` 模式仍然用于一次性单元成本验证；`representative` 是循环的模式。循环状态在 `${SKILL_DIR}/references/loop-state-schema.md` 中记录。

## 安全注意事项

安全性贯穿上述公理（数据建模 #14 中的授权对齐密钥、模式 #2 中的条件写入保护、机制 #13 中的事务唯一性）。本节汇总了代理遵循此技能时必须向用户展示的风险，无论哪个公理在起作用，还包括技能可执行脚本特定的控制。在任何设计评审中声明相关内容；不要假设用户已经知道它们。

1. **授权边界对齐（IDOR）是第一个安全检查。** 最常见的 DynamoDB 数据暴露错误是将分区键设置为客户端提供的标识符（来自 URL 的 `review_id`/`order_id`）而不是服务器派生的授权标识符（`user_id`、`tenant_id`、`account_id`）。当它们不一致时，调用者可以传递外键并跨越租户边界访问数据。使分区键与授权/租户边界对齐（数据建模 #14），以便外键无法访问；每次调用的 `ConditionExpression` 是规范，而不是结构修复，并且不涵盖读取（事实 #4）。在任何设计评审中，在评估和声明此内容 **之前**，再评估热分区、投影或成本发现。

2. **静态加密 — 始终开启；故意选择密钥层级。** DynamoDB 以无法关闭的方式静态加密每个表。默认是 **AWS 拥有的密钥** — 无需成本、无需密钥管理，并且在未设置 `SSESpecification` 时（这是实时验证部署所做的；基准清单记录了从 `DescribeTable` 读取的静态状态），它是隐式状态。这对于临时/基准表和大多数工作负载是正确的。对于处于合规环境下的数据（密钥使用审计、独立密钥轮换/撤销、跨账户密钥策略或持有密钥的监管要求），建议使用 **客户管理的 KMS 密钥（CMK）** — 设置 `SSESpecification` 并使用 `SSEType: KMS` 和 `KMSMasterKeyId`（注意：DynamoDB 的唯一非默认 `SSEType` 是 `KMS`；DynamoDB 上没有 `AES256` 类型），并注意每请求的 KMS 成本和需要密钥策略。在设计中发现加密选择（它是每个实体的操作配置输入之一），而不是将其留作隐式内容。**传输中加密** 始终为这些脚本执行的每个 AWS API 调用开启：boto3 默认通过 TLS（HTTPS）与 DynamoDB/Lambda/IAM 通信，并且没有明文路径 — 复制此模式的代理应将所有传输中的数据视为受保护，并且永远不要禁用 TLS 验证。

3. **生成的工件是敏感的 — 相应处理。** 部署写入 `created_resources.json`，一个包含 AWS **账户 ID、资源 ARN 和使用的配置文件名称** 的清单。它不是一个秘密存储（它不包含凭证），但它标识了账户和资源，因此不要将其粘贴到共享通道、提交到公共存储库或原封不动地包含在报告中。技能的脚本永远不会将 AWS 凭证、令牌或连接字符串写入任何工件 — 保持这种方式；如果你扩展它们，请不要记录凭证材料。

4. **基准测试资源仅放在沙盒/测试账户中。** 实时验证部署创建真实的、可计费的资源。它必须仅在用户命名的沙盒/测试账户中运行 — 永远不在生产环境中，也永远不在持有真实用户数据的账户中。部署拒绝在生产标记账户别名/ARN 上运行（`prod`/`production`/`prd`/`live`），但代理有责任声明实时验证的四个事实并首先确认账户的用途（见 *Live validation*）。

5. **凭证卫生。** 永远不要将 AWS 配置文件、访问密钥、会话令牌或 `credential_process` 块持久化到技能生成的任何文件中，并且永远不要将其回显到输出。脚本从环境 AWS 凭证链（命名的配置文件、SSO 或环境凭证）进行身份验证；它们既不读取任意环境变量，也不记录它们解析的内容。当你编写 `benchmark_config.json` 时，仅存储配置文件 *名称* 和区域 — 而不是它们后面的解析凭证。

6. **向量搜索不尊重细粒度访问控制，并且向量索引分区键不是租户边界。** 两个不同的风险，都必须在任何包含语义搜索的多租户设计上展示 — 然后是它们所需的补偿性检测控制。

    首先，`dynamodb:` 前台访问控制条件键 — `dynamodb:LeadingKeys`、`dynamodb:Attributes`、`dynamodb:Select` — 不在 `SearchVectors` 请求上下文中。因此，引用它们的 `Condition` 的语句不匹配，结果是拒绝而不是授予。向现有的前台访问控制条件语句添加 `dynamodb:SearchVectors` 会无声地破坏向量搜索，而该语句的其他操作正常工作，这表现为索引损坏而不是策略错误。在它自己的语句中授予 `dynamodb:SearchVectors`，范围到索引资源 ARN（`arn:aws:dynamodb:<region>:<account-id>:table/<table>/index/<index>`），并且没有附加 `dynamodb:` 前台访问控制条件。

    其次，将搜索范围限制到一个租户的分区键值是数据局部性和性能优化，**不是** 访问控制机制。任何持有 `dynamodb:SearchVectors` 在索引上的主体都可以搜索任何分区键值，并且由于前台访问控制条件键不适用，您无法在 IAM 层约束它们可以到达的值。当需要在数据层实现严格租户隔离时，使用单独的表或具有不同租户级 IAM 授予的单独索引；在应用层注入调用者的租户标识符并且从不从客户端接受它是补充，而不是替代。这是向量搜索形式的授权边界检查（见项目 1）— 与基础表不同，键模式在此处**不**使外部数据无法访问，因此结构修复是授予权限分离，而不是分区。静态加密继承自基础表；没有单独的向量索引设置。

    第三，由于授予权限分离仅约束主体可以搜索的 *索引*，但从未约束分区键值，建议在任何多租户向量索引表上启用 **CloudTrail 数据事件日志记录** 作为补偿性检测控制。它是唯一记录每个主体搜索了哪些值的记录 — 精确的维度 IAM 无法控制 — 因此，来自受损主体或失败的 应用层注入的跨租户搜索无法观察到。在每主体 `VectorSearchRequestBytes` 上的 CloudWatch 报警捕获分区枚举作为体积异常。请注意，嵌入本身也是敏感的：相似结果即使在未返回原始文本的情况下也会披露两条记录在语义上是接近的，因此默认情况下向量属性从结果中排除是值得保留的安全默认值，并且记录整个项目需要与表相同的谨慎。

    完整处理：`${SKILL_DIR}/references/vector-search.md § Security`。

## 最佳实践

这些都是推荐默认值，不是公理。它们不塑造设计；它们是操作安全措施，除非有特定理由反对，否则应启用它们。生成设计的代理应启用每个这些，除非禁用的理由在工件中明确说明。

1. **在每张表上启用删除保护。** DynamoDB 的删除保护标志在服务边界处阻止 `DeleteTable`，直到显式禁用。它不产生成本，没有性能影响，并防止整类事件 — IaC 配置错误、复制粘贴命令、应受范围的堆栈拆除 — 销毁生产表。当有意进行删除时，单步禁用很便宜；在其他地方应保持保护开启。

    两个重要的细节人们会忽略：

    - **删除保护默认为 FALSE。** 新表在没有设置 `--deletion-protection-enabled` 在 `create-table`（或 CloudFormation/CDK 或任何第三方 IaC 工具中的等效属性）的情况下创建。这就是为什么它如此普遍地缺失在预日期该功能的表上或创建时没有深思熟虑的表上 — 你必须显式打开它。
    - **服务边界保护与 IaC 守护不重复。** CDK `RemovalPolicy.RETAIN`、第三方 IaC 工具的 prevent-destroy / retain-on-delete 守护，以及类似机制仅保护 IaC 路径 — 直接 `aws dynamodb delete-table` CLI 调用、针对同一资源的不同 IaC 状态文件或流氓脚本都会绕过它们。删除保护存在于表本身的服务边界上，并捕获每条销毁路径。一起使用它们；不要将 IaC 守护视为单独足够。

2. **在每张表上启用点时间恢复（PITR）。** PITR 提供连续备份，保留 35 天，并提供每秒恢复粒度。成本是存储成本的几分之一，并且在需要时 — 意外删除、不良迁移、写入损坏值的逻辑错误 — 它是恢复数据的唯一方法。仅在内容可以从其他来源（idempotency 缓存、具有 TTL 的去重存储）重建的临时表中禁用 PITR。跨表的 PITR 分歧也是数据建模 #3 的建模信号。

3. **使表可观察 — 生产表上的警报和审计跟踪。** 没有监控的表会静默失败；第一个迹象可能是限流或失控成本是客户投诉或月度账单。对于每个生产表，建议：

    - **CloudWatch 报警** 在 `ThrottledRequests`、`SystemErrors` 和 `UserErrors`（对于配置表，还在消耗与配置能力的比较上）。至少一个起始报警在 `ThrottledRequests > 0` 持续 — 那是最早的热分区或未充分配置的信号，并且直接与机制 #3 的上限相关。
    - **CloudTrail 数据事件日志记录** 对于持有敏感或监管数据的表，以便项目级读取和写入可审计。CloudTrail 默认捕获 DynamoDB *管理* 事件；项目级（数据）事件是按表可选的，并且是审计或事件调查实际需要的。当审计/操作日志本身持有敏感数据时，**使用 AWS KMS 客户管理密钥加密 CloudWatch 日志组（以及 CloudTrail 轨迹的 S3 存储桶）**，以便记录的数据在静态时受保护，而不仅仅是源表。

    这些是操作安全措施，不是设计输入 — 但由于此技能的指导在许多客户环境中复制，展示它们是可辩护的设计的一部分，而不是事后思考。
