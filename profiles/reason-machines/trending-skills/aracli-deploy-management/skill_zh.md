# 部署 OpenClaw 代理系统

> 技能由 [ara.so](https://ara.so) 提供 — 2026 日历技能集合。

部署和管理 OpenClaw 兼容型 AI 代理系统的实用指南。涵盖基础设施选项、部署方法以及 CLI、API 和基于 MCP 的管理之间的权衡。

---

## 基础设施选项

### 1. 云虚拟机 (AWS, GCP, Azure, Hetzner)

启动虚拟机并将代理作为容器化服务运行。

```bash
# 示例：在云虚拟机上使用 Docker Compose
docker compose up -d agent-runtime
```

**优点：**
- 熟悉的运维工具 (Terraform, Ansible 等)
- 易于水平扩展 — 只需添加更多虚拟机
- 大多数提供商提供按量付费定价
- 完全控制网络和安全

**缺点：**
- 您负责正常运行时间 — 没有管理的重启或自愈
- GPU 实例价格很快就会变得昂贵
- 按需启动时会有冷启动

**最适合：** 已有云基础设施并希望完全控制的团队。

---

### 2. 管理容器平台 (Railway, Fly.io, Render)

无需直接管理虚拟机即可部署代理容器。

```bash
# 示例：Railway
railway up

# 示例：Fly.io
fly deploy
```

**优点：**
- 无需服务器管理 — 只需推送代码
- 内置健康检查、自动重启和扩展
- 易于预览环境以测试代理更改
- 通常包含日志和指标

**缺点：**
- 对底层机器的控制较少
- 与原始虚拟机相比，扩展时成本可能较高
- 免费或业余级别会有冷启动
- 大多数平台上的 GPU 支持有限或不存在

**最适合：** 希望快速行动而无需运维负担的小型团队。

---

### 3. 硬件直连 (Hetzner 专用服务器, OVH, Colo)

直接在物理服务器上运行代理，以获得每美元的最大性能。

```bash
# 示例：在硬件直连上使用 systemd 服务
sudo systemctl start agent-runtime
```

**优点：**
- 最佳性价比，尤其是在 GPU 工作负载方面
- 没有吵闹的邻居 — 可预测的延迟
- 完全控制硬件、内核、驱动程序
- 没有出口费用

**缺点：**
- 您管理一切：操作系统、网络、故障转移、监控
- 扩展意味着订购和配置新硬件
- 没有管理的负载均衡 — 您需要自己构建

**最适合：** 成本敏感型工作负载、GPU 密集型推理或运维技能强的团队。

---

### 4. 无服务器/边缘 (Lambda, Cloudflare Workers, Vercel Functions)

在边缘运行轻量级代理逻辑，无需持久基础设施。

```bash
# 示例：部署到 Cloudflare Workers
wrangler deploy
```

**优点：**
- 无闲置成本 — 仅按调用付费
- 全球分布且低延迟
- 无需服务器补丁或维护
- 自动扩展到零并返回

**缺点：**
- 执行时间限制 (通常为 30 秒至 300 秒)
- 调用之间没有持久状态
- 不适用于长时间运行的代理会话
- 有限的运行时环境 (无法运行任意二进制文件)

**最适合：** 状态less 代理端点、webhooks 或轻量级工具调用代理。

---

### 5. 混合

结合方法：使用管理平台部署 API 层，使用硬件直连部署代理运行时。

```
用户 → API (Railway/Vercel) → 代理运行时 (硬件直连 GPU)
```

**优点：**
- 每一层都在最具成本效益的基础设施上运行
- API 层获得管理扩展，代理层获得原始性能
- 可以独立迁移各层

**缺点：**
- 需要协调更多组件
- 层之间的跨网络延迟
- 需要维护多个部署管道

**最适合：** 需要廉价推理和精致 API 层的生产系统。

## 管理方法：CLI vs API vs MCP

一旦您的代理部署完成，您需要一种管理它们的方式 — 发送更新、检查状态、回滚。主要有三种方法。

### CLI

一个与您的代理基础设施通过 SSH 或 HTTP 通信的命令行工具。

```bash
# 典型 CLI 工作流程
mycli status
mycli deploy --service agent
mycli rollback
mycli logs agent --tail
```

**优点：**
- 对运维人员来说速度快 — 一个命令搞定
- 易于脚本化并与其他 CLI 工具组合
- 在 CI/CD 管道中效果很好
- 低开销，无需维护服务器端 UI

**缺点：**
- 需要终端访问和认证设置
- 难以与非技术人员共享
- 没有实时仪表板或视觉概览
- 每个工具都有其自己的 CLI 习惯需要学习

**最适合：** 由构建系统的团队进行日常运维。

---

### API

一个暴露部署操作的 REST 或 gRPC API。

```bash
# 通过 API 部署
curl -X POST https://deploy.example.com/api/v1/deploy \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"service": "agent", "version": "v42"}'

# 检查状态
curl https://deploy.example.com/api/v1/status
```

**优点：**
- 语言无关 — 任何 HTTP 客户端都可以使用
- 易于与仪表板、Slack 机器人或其他系统集成
- 可在 API 层强制执行认证、速率限制和审计日志
- 启用在顶部构建自定义 UI

**缺点：**
- 需要构建和维护 API 本身的基础设施
- 版本控制和向后兼容性成为您的问题
- 与直接 CLI 到服务器的延迟开销
- 认证令牌管理增加了复杂性

**最适合：** 构建内部平台或将部署集成到更大系统的团队。

---

### MCP (模型上下文协议)

将部署操作作为 MCP 工具暴露，以便 AI 代理可以直接管理基础设施。

```json
{
  "tool": "deploy",
  "input": {
    "service": "agent",
    "version": "latest",
    "strategy": "rolling"
  }
}
```

**优点：**
- 代理可以自我管理 — 部署、监控和回滚可自主执行
- 非技术人员可以使用自然语言界面 ("部署最新代理")
- 可与其他 MCP 工具 (监控、告警等) 组合
- 自然地融入代理工作流程

**缺点：**
- 新模式 — 工具较少经过实战检验
- 需要仔细的权限范围 (您不希望代理在没有监督的情况下强制推送到生产环境)
- 调试时调用方是 LLM 更困难
- 需要护栏：确认步骤、干运行模式、影响范围限制

**最适合：** 代理 DevOps 工作流程，其中 AI 代理参与部署生命周期。

## 对比矩阵

| | CLI | API | MCP |
|---|---|---|---|
| **设置速度** | 快 | 中等 | 中等 |
| **自动化** | 脚本/CI | 任何 HTTP 客户端 | 代理原生 |
| **受众** | 工程师 | 工程师 + 系统 | 工程师 + 代理 |
| **可观察性** | 终端输出 | 结构化响应 | 工具调用日志 |
| **认证模型** | SSH 密钥 / 令牌 | API 令牌 / OAuth | MCP 认证范围 |
| **最佳搭配** | 硬件直连、虚拟机 | 管理平台 | 代理协调器 |

---

## 建议

- **刚开始使用？** 使用管理平台 (Railway, Fly.io) 及其内置 CLI。运维负担最小。
- **成本重要？** 使用硬件直连和简单的 CLI 进行部署。性价比最高。
- **构建平台？** 投资一个 API 层。随着团队增长，回报率会提高。
- **代理工作流程？** 在现有 API 顶部添加 MCP 工具。不要用 MCP 替代您的 API — 包装它。
- **GPU 推理？** 硬件直连或保留云实例。无服务器不适用于长时间运行的推理。
