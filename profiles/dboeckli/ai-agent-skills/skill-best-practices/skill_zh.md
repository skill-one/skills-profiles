# 技能最佳实践

参考：https://resources.anthropic.com/hubfs/The-Complete-Guide-to-Building-Skill-for-Claude.pdf

## 指南

### 第 1 步：确定您的用例类别

确定您正在构建的技能类型：

- **文档与资产创建** — 一致性输出（文档、设计、代码）
- **工作流自动化** — 具有一致方法的多步骤流程
- **MCP 增强功能** — 基于 MCP 工具访问的工作流指导

在编写任何内容之前，定义 2-3 个具体的用例（见下文规划部分）。

### 第 2 步：创建文件夹和 SKILL.md

- 使用连字符命名文件夹（例如 `my-skill-name`）
- 在其中创建完全为 `SKILL.md`（区分大小写）
- 编写带有 `name` 和 `description` 的 YAML 前置信息（见技术要求）

### 第 3 步：编写描述 — 这是至关重要的部分

描述控制 Claude 加载您的技能的时间。它必须包括：

- **技能做什么**（WHAT）
- **何时使用它**（WHEN）（特定的触发短语）
- 可选：负面触发器（“不要用于...”）

参见“编写有效描述”以获取良好/不良示例。

### 第 4 步：编写主体指令

遵循推荐模板：`## 指令` → 编号步骤 → `## 示例` → `## 故障排除`
具体且可操作。将详细文档移至 `references/` 并链接到它们。

### 第 5 步：更新 CLAUDE.md 和 README.md

在创建或修改此存储库中的任何技能后，始终更新这两个文件中的技能表格：

- `CLAUDE.md` — “包含的技能”下的技能表格（触发列：触发时的一行描述）
- `README.md` — “Enthaltene Skills”下的技能表格（Beschreibung 列：德语一行描述）

这两个文件必须保持同步。此步骤是强制性的，不能跳过。

此外，在处理此存储库中的技能时，调用 `cc-best-practices` 技能以确保上下文和会话管理符合项目标准。

### 第 6 步：验证 YAML 和技能 CLI 兼容性

在测试或提交之前，从存储库根目录运行验证脚本：

```bash
bash .claude/skills/skill-best-practices/scripts/validate-skills.sh
```

在继续之前修复任何 `FAIL` 行。常见问题：

- `description` 使用块标量（`>` 或 `|`）→ 替换为引号单行字符串
- 父映射键下的子键未缩进 → 添加两个空格缩进

推送后，还运行远程检查以确认 `npx skills add --list` 找到所有技能：

```bash
bash .claude/skills/skill-best-practices/scripts/validate-skills.sh --remote
```

### 第 7 步：测试触发和功能行为

运行 10-20 个测试查询。目标：技能在约 90% 的相关查询中触发，并且永远不会在无关主题上触发。
迭代描述，直到触发可靠（见测试方法）。

### 第 7 步：根据信号进行迭代

- **触发不足** → 向描述中添加更多触发短语
- **触发过度** → 添加负面触发器，缩小范围
- **指令被忽略** → 将关键步骤移至顶部，使用明确的语言

## 示例

### 示例 1：从零开始构建新技能

用户说：“帮我创建一个在 Linear 中规划 Sprints 的技能”

操作：

1. 确定类别：工作流自动化 + MCP 增强功能
2. 定义用例：触发器 = "plan sprint", "create sprint tasks"；步骤 = 获取 Linear 状态 → 分析速度 → 创建任务
3. 创建文件夹 `linear-sprint-planner/SKILL.md`
4. 编写描述：“管理 Linear sprint 规划工作流。当用户说 'plan sprint', 'create sprint tasks', 或 'set up iteration' 时使用。”
5. 编写分步指令，包含 Linear MCP 工具调用
6. 使用 10 个触发短语进行测试；如果技能不会自动加载，则调整描述

结果：功能技能，在 Sprint 规划请求时自动触发，并执行完整工作流，而无需用户每次重新解释步骤。

### 示例 2：审查现有技能

用户说：“审查我的 SKILL.md 并提出改进建议”

操作：

1. 阅读 SKILL.md 前置信息 — 检查名称（连字符命名？），描述（WHAT + WHEN？少于 1024 个字符？触发短语存在？）
2. 检查主体 — 是否少于 5,000 个字？指令是否具体且可操作？是否有故障排除部分？示例？
3. 模拟触发 — 描述是否会导致 Claude 在正确的查询中加载此技能？
4. 按标准逐项报告结果：PASS / WARN / FAIL

结果：按优先级列出的改进建议，每个问题都有具体的修复方法。

### 示例 3：解决不会触发的技能

用户说：“我的技能从未自动加载，我总是必须手动调用它”

操作：

1. 阅读描述字段 — 是否过于笼统？（“帮助处理项目”不会起作用）
2. 检查是否缺少触发短语 — 是否包含用户实际会说的话？
3. 询问 Claude：“您何时会使用 [技能名称] 技能？” — Claude 会引用描述；差距会变得明显
4. 重新编写描述以添加具体触发短语并重新测试

结果：更新后的描述包含具体触发器；技能在相关查询中自动加载。

## 技能是什么？

技能是一个包含以下内容的文件夹：

- `SKILL.md`（必需）：带有 YAML 前置信息的 Markdown 指令
- `scripts/`（可选）：可执行代码（Python、Bash 等）
- `references/`（可选）：按需加载的文档
- `assets/`（可选）：输出中使用的模板、字体、图标

## 核心设计原则

**渐进式披露** — 三个级别：

1. YAML 前置信息：始终在系统提示中；告诉 Claude 何时加载技能
2. SKILL.md 主体：在相关时加载；完整指令
3. `references/` 中的链接文件：按需加载

**可组合性** — 技能与其他技能协同工作；不要假设排他性。

**可移植性** — 在 Claude.ai、Claude Code 和 API 上工作方式完全相同。

```

  1. ...
  2. ...
```

问自己：

- 用户想完成什么？
- 需要哪些多步骤工作流？
- 需要哪些工具（内置或 MCP）？
- 应该嵌入哪些领域知识？

### 三个技能类别

| 类别                      | 何时使用                                           | 关键技术                                      |
| ----------------------------- | ----------------------------------------------------- | --------------------------------------------------- |
| **文档与资产创建**         | 一致性、高质量的输出（文档、设计、代码）         | 风格指南、模板、质量检查清单                 |
| **工作流自动化**           | 具有一致方法的多步骤流程                      | 分步操作，带有验证门控，迭代循环             |
| **MCP 增强功能**           | 基于 MCP 工具访问的工作流指导                 | 顺序 MCP 调用，嵌入领域专业知识             |

## 技术要求

### 文件和文件夹命名

- 文件夹：**仅使用连字符**（例如 `notion-project-setup`） — 不允许空格、下划线或大写字母
- 文件：完全为 **`SKILL.md`**（区分大小写） — 没有变体
- 技能文件夹内不允许 `README.md`（将文档放在 `SKILL.md` 或 `references/` 中）

### YAML 前置信息

最小必需格式：

```yaml
---
name: your-skill-name
description: 它做什么。当用户询问 [具体短语] 时使用。
---
```

**`name`**（必需）：

- 连字符命名，无空格或大写字母
- 必须与文件夹名称匹配

**`description`**（必需）：

- 必须同时包含：技能做什么 AND 何时使用它（触发条件）
- 少于 1024 个字符
- 没有 XML 标签（`<` 或 `>`）
- 包含用户实际会说的话的具体触发短语
- 如相关，请提及文件类型

**可选字段**：

```yaml
license: MIT
compatibility: "需要 Python 3.10+"
metadata:
  author: 您的姓名
  version: 1.0.0
  mcp-server: 服务器名称
```

**安全限制 — 前置信息中禁止的内容**：

- XML 角括号（`< >`）
- 包含 "claude" 或 "anthropic" 的名称（保留）

## 编写有效描述

结构：`[它做什么] + [何时使用它] + [关键功能]`

**良好示例**：

```yaml
# 具体且可操作
description: 分析 Figma 设计文件并生成开发者交付文档。
  当用户上传 .fig 文件，询问 "设计规范"，"组件文档"，或 "设计到代码交付" 时使用。

# 包含触发短语
description: 管理 Linear 项目工作流，包括 Sprint 规划和任务创建。当用户提到 "sprint"，"Linear 任务"，或要求 "创建工单" 时使用。
```

**不良示例**：

```yaml
# 太模糊
description: 帮助处理项目。

# 缺少触发器
description: 创建复杂的分页文档系统。

# 太技术化，没有用户触发器
description: 实现项目实体模型，具有分层关系。
```

## 编写指令（SKILL.md 主体）

推荐结构：

```markdown
# 您的技能名称

## 指令

### 第 1 步：[第一个主要步骤]

清晰的解释。

### 第 2 步：...

## 示例

### 示例 1：[常见场景]

用户说： "..."
操作：

1. ...
   结果： ...

## 故障排除

### 错误：[常见错误消息]

**原因**：为什么发生
**解决方案**：如何修复
```

### 指令最佳实践

**具体且可操作**：

```
# 好
运行 `python scripts/validate.py --input {filename}` 检查数据格式。
如果验证失败，常见问题：
- 缺少必需字段（添加到 CSV）
- 无效的日期格式（使用 YYYY-MM-DD）

# 不好
验证数据后再继续。
```

**包含错误处理** — 记录常见错误及其原因和解决方案。

**清晰引用捆绑资源**：

```
在编写查询之前，参考 `references/api-patterns.md`：
- 速率限制指南
- 分页模式
```

**使用渐进式披露** — 保持 SKILL.md 聚焦于核心指令；将详细文档移至 `references/` 并链接到它们。将 SKILL.md 控制在 5,000 字以内。

**对于关键验证**，优先使用捆绑脚本而不是语言指令 — 代码是确定的，语言解释不是。

## 测试方法

### 1. 触发测试

运行 10-20 个查询。技能应在约 90% 的相关查询中触发，并且不应在无关主题上触发。

```
应触发：
- "帮助我设置新的 ProjectHub 工作区"
- "我需要创建一个 ProjectHub 项目"

不应触发：
- "天气怎么样？"
- "帮助我编写 Python 代码"
```

**调试**：询问 Claude "您何时会使用 [技能名称] 技能？" — 它会引用描述。

### 2. 功能测试

- 生成的输出有效
- API 调用成功
- 错误处理工作正常
- 覆盖边缘情况

### 3. 性能比较

比较 token 数量、工具调用和来回消息，使用技能与不使用技能。

**小技巧**：对单个具有挑战性的任务进行迭代，直到 Claude 成功，然后将成功的方案提取为技能。

## 故障排除

### 技能无法上传

| 错误                     | 原因                      | 修复                                |
| ------------------------- | -------------------------- | ---------------------------------- |
| "找不到 SKILL.md"        | 错误的文件名             | 将文件名重命名为 `SKILL.md`       |
| "无效的前置信息"         | YAML 格式                 | 添加 `---` 分隔符，关闭引号       |
| "无效的技能名称"         | 名称中包含空格或大写字母 | 使用连字符命名                     |

### 技能不触发（触发不足）

- 描述过于笼统
- 缺少用户实际会说的话的触发短语
- 缺少相关文件类型的提及

**修复**：向描述中添加更多具体的键词和短语。

### 技能触发过度（触发过度）

添加负面触发器并缩小范围：

```yaml
description: 高级 CSV 文件数据分析。用于统计建模、回归、聚类。不要用于简单的数据探索。
```

### 指令未执行

1. **过于冗长** — 保持简洁，使用项目符号，将细节移至 `references/`
2. **指令埋藏** — 将关键指令置于顶部，使用 `## 关键` 标题
3. **语言模糊** — 使用明确的语言： "CRITICAL: 在调用 X 之前，请验证：..."
4. **模型懒惰** — 添加到用户提示（比 SKILL.md 更有效）： "慢慢来，质量胜于速度，不要跳过验证步骤"

### 大上下文 / 慢响应

- 将详细文档移至 `references/`
- 将 SKILL.md 控制在 5,000 字以内
- 减少同时启用的技能数量（评估是否超过 20-50 个）
