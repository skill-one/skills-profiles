# Claude 代码最佳实践

基于官方 Anthropic 文档 https://code.claude.com/docs/en/best-practices。

最重要的约束条件：**Claude 的上下文窗口填满得很快，并且随着其填满，性能会下降。** 所有最佳实践都由此衍生。

---

## 指令

### 第 1 步：始终给 Claude 提供验证其工作的方法

提供一个可运行的检查（测试套件、构建退出代码、代码检查工具、差异脚本），以便 Claude 可以独立确认成功。要求 **证据**（测试输出、命令结果），而不仅仅是断言。

### 第 2 步：对于非平凡任务，使用“探索 → 规划 → 实现”的工作流程

进入 `/plan` 模式，让 Claude 先阅读代码库，然后起草计划，再编写任何代码。退出计划模式进行实现。仅适用于小型、显而易见的更改时跳过此步骤。

### 第 3 步：编写具体、范围明确的提示

命名文件（`@filename`），描述症状而不是猜测，引用现有模式。模糊的提示会产生模糊的结果。

### 第 4 步：保持 CLAUDE.md 简短且可操作

仅包含 Claude 无法从代码中推断的内容。每一行都应回答：“移除这部分会导致 Claude 出错吗？” 如果不是，就删除它。

### 第 5 步：积极管理上下文

在无关任务之间使用 `/clear`。对于同一个问题连续两次失败的更正后：清除并编写更好的提示。使用 `/compact <提示>` 进行聚焦压缩。

### 第 6 步：使用子代理进行调查和审查

让子代理探索不熟悉的代码或审查你的实现——它们在新的上下文中运行，没有对刚刚编写的代码的偏见。

## 示例

### 示例 1：正确实现功能

用户说：“我让 Claude 实现某事时，总是得到不稳定的结果”

操作：

1. 在提示中添加验证步骤：“编写一个 validateEmail 函数——实现后运行现有的测试套件，显示输出”
2. 如果没有测试： “编写该函数，并为其编写测试，运行它们，显示结果”
3. 设置一个 Stop 钩子，阻止回合完成，直到测试通过

结果：Claude 会迭代直到测试通过，而不是在代码看起来完成时停止。

### 示例 2：处理复杂的、多文件的更改

用户说：“我应该如何处理跨 10 个文件的重大重构？”

操作：

1. 进入 `/plan` 模式——Claude 探索而不进行更改
2. 询问：“阅读受影响的文件并编写逐步实现计划”
3. 如有必要，直接使用 `Ctrl+G` 编辑计划
4. 退出计划模式——Claude 按计划编码和验证
5. 运行子代理以在全新上下文中审查差异

结果：结构化的重构，具有可审查的计划，避免了混合探索/编写回合导致的上下文冲击。

### 示例 3：Claude 不断重复同样的错误

用户说：“我已经三次更正了 Claude 的同一个问题，但它仍然做错”

操作：

1. 运行 `/clear`——开始全新上下文
2. 确定原始提示中缺失了什么（缺失约束、缺失示例、范围模糊）
3. 编写新的初始提示，明确包含约束：“重要提示：在这些测试中不要使用模拟——使用真实的数据库连接”
4. 如果适用，将约束添加到 CLAUDE.md

结果：干净的会话和更明确指定的提示优于长时间的、累积更正的会话。

## 1. 给 Claude 提供验证其工作的方法

Claude 在工作看起来完成时停止。如果没有可运行的检查，你将成为验证循环。提供 Claude 可以读取的返回通过/失败信号的某物：测试套件、构建退出代码、代码检查工具、差异脚本。

- 在同一个提示中要求 Claude 运行检查并迭代。
- 设置 `/goal` 条件进行多回合验证。
- 使用 **Stop 钩子**阻止回合结束，直到脚本通过。
- 使用 **验证子代理**，以便审查者有全新上下文。

要求 Claude 显示 **证据**（测试输出、命令结果、截图），而不仅仅是断言成功。

**示例升级：**

> 之前：_"实现一个验证电子邮件地址的函数"_
> 之后：*"编写 validateEmail 函数。测试用例：user@example.com → true,
>
> > 无效 → false。实现后运行测试"*

---

## 2. 先探索，再规划，再编码

使用 **计划模式**（`/plan` 或 UI 切换）将阅读与编写分离。

1. **探索**——进入计划模式；Claude 读取文件而不进行更改。
2. **规划**——要求 Claude 编写详细的实现计划。按 `Ctrl+G` 在编辑器中直接打开计划进行编辑。
3. **实现**——退出计划模式；Claude 编码并对照计划进行验证。
4. **提交**——要求 Claude 提交并打开一个 PR。

当范围明确且修复较小（拼写错误、重命名、单行更改）时跳过规划。计划模式会增加开销——在更改涉及多个文件或你不熟悉代码时使用它。

---

## 3. 在提示中提供具体的上下文

Claude 可以推断意图，但不能读心。

| 策略             | 模糊                                           | 具体                                                                                                              |
| -------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| 任务范围限定     | _"为 foo.py 添加测试"_                      | _"为 foo.py 编写测试，覆盖用户未登录的边缘情况。避免使用模拟."_                         |
| 指向源代码     | _"ExecutionFactory 为什么有奇怪的 API?"_   | _"查看 ExecutionFactory 的 git 历史并总结其 API 如何演变"_                                     |
| 引用模式     | _"添加一个日历小部件"_                       | _"以 HotDogWidget.php 为模式参考，遵循其实现一个日历小部件"_                      |
| 描述症状     | _"修复登录错误"_                           | _"用户报告会话超时后登录失败。检查 src/auth/ 令牌刷新。编写失败的测试，然后修复它."_ |

**丰富的上下文技术：**

- 使用 `@filename` 直接引用文件。
- 粘贴截图或将图像拖入提示。
- 管道数据：`cat error.log | claude`
- 提供文档 URL（通过 `/permissions` 允许域名）。

## 4. 编写有效的 CLAUDE.md

CLAUDE.md 在每个会话开始时读取。保持它 **简短且易于人类阅读**——臃肿的 CLAUDE.md 文件会导致 Claude 忽略实际指令。

**包含：**

- Claude 无法猜测的 Bash 命令（例如，构建/测试命令）
- 与语言默认值不同的代码风格规则
- 测试说明和首选的测试运行器
- 仓库礼仪（分支命名、PR 规范）
- 项目特定的架构决策
- 开发者环境怪癖，所需的 env 变量
- 常见的陷阱或不明显的行为

**排除：**

- Claude 可以通过阅读代码推断出的一切
- Claude 已经知道的标凈语言规范
- 详细的 API 文档（链接代替）
- “编写干净代码”等显而易见的实践

对于每一行：_“移除这部分会导致 Claude 出错吗？”_ 如果不是，就删除它。

使用 `/context` 确认 Claude 加载了文件。使用 `@path/to/file` 在 CLAUDE.md 中的导入来选择性地导入其他文件。

## 5. 积极管理会话上下文

- `/clear` — 在**无关**任务之间重置上下文。
- `/compact <指令>` — 聚焦压缩（例如，`/compact 聚焦于 API 更改`）。
- `Esc + Esc` / `/rewind` — 打开回放菜单；恢复对话和/或代码状态到任何之前的检查点。
- `/btw` — 问一个快速的问题；答案出现在覆盖层中，永远不会进入对话历史。

**对于同一个问题连续两次失败的更正后：** 运行 `/clear` 并编写更好的初始提示，包含你学到的内容。干净的会话和更好的提示优于长时间的、累积更正的会话。

在 CLAUDE.md 中自定义压缩：

> *"压缩时始终保留修改的完整文件列表和任何
>
> > 测试命令"*

## 6. 使用子代理进行调查和审查

子代理在其自己的上下文窗口中运行并报告摘要，使你的主对话保持干净。

```
使用子代理调查我们的身份验证系统如何处理令牌刷新，以及我们是否有任何现有的 OAuth 工具可以重用。
```

实现后：

```
使用子代理审查此代码的边缘情况
```

使用 `/code-review` 技能对当前差异进行以错误为中心的对抗性审查。

## 7. 自动化和扩展

**非交互模式**——将 Claude 集成到 CI、预提交钩子、脚本中：

```bash
claude -p "列出所有 API 端点" --output-format json
claude -p "分析这个日志文件" --output-format stream-json --verbose
```

**跨文件分发**——循环通过任务：

```bash
for file in $(cat files.txt); do
  claude -p "将 $file 从 React 迁移到 Vue。返回 OK 或 FAIL。" \
    --allowedTools "Edit,Bash(git commit *)"
done
```

**并行会话**——使用 git worktrees 运行多个 Claude 会话，以便编辑不会冲突。编写者/审查者模式：

- 会话 A 实现功能。
- 会话 B 在全新上下文中审查差异（没有对刚刚编写的代码的偏见）。

**自动模式**——不间断执行，并带有后台安全检查：

```bash
claude --permission-mode auto -p "修复所有代码检查错误"
```
