## 规格

# Salesforce 自定义报表类型元数据知识

## 概述
自定义报表类型（CRT）定义了 Salesforce 报表的数据框架。它们指定一个主要对象、最多 3 个相关对象、它们之间的关系（连接），以及报表构建器中可用的字段。

## 目的
- 支持跨标准报表类型未涵盖的自定义对象和自定义关系进行报表
- 筛选报表构建器中使用的字段集（包括通过查找路径到达的字段）
- 控制内/外连接行为，以包含或排除没有相关记录的主要记录

## 配置

**文件扩展名：** `.reportType-meta.xml`。文件基本名是报表类型的开发者名称（例如 `AccountsWithProjects.reportType-meta.xml`）。每个 CRT 是一个单独的文件，不嵌套在对象文件夹下。

### 关键元素

顶层 `<ReportType>` 子元素：

| 元素 | 必填 | 备注 |
|------|------|------|
| `<fullName>` | 是 | API 标识符；必须与文件名匹配。字母、数字、下划线；必须以字母开头；不能有空格；不能有尾随下划线；不能有连续下划线 |
| `<label>` | 是 | 报表类型选择器中显示的人类友好名称 |
| `<description>` | 推荐 | 阐述业务“原因”——谁使用它以及他们学到了什么 |
| `<baseObject>` | 是 | 主要对象的 API 名称（例如 `Account`、`Project__c`）。创建后不能更改。所有对象，包括自定义和外部对象，都受支持（外部对象来自 API 38.0+） |
| `<category>` | 推荐 | 报表构建器类别——参见 `references/category-values.md` |
| `<deployed>` | 是 | `true` 表示对用户可见；`false` 表示在构建/迭代期间 |
| `<join>` | 条件性 | 添加相关对象及其连接行为。嵌套进一步的 `<join>` 块以表示更深层次的关系 |
| `<sections>` | 推荐 | 可用于报表类型的列组。虽然不是严格必需的，但没有列的报表没有用 |

`<sections>`（列组）子元素：

| 元素 | 必填 | 备注 |
|------|------|------|
| `<masterLabel>` | 是 | 报表构建器中显示的组标题 |
| `<columns>` | 条件性 | 每个组中暴露的字段 |

`<columns>`（单个字段）子元素：

| 元素 | 必填 | 备注 |
|------|------|------|
| `<field>` | 是 | 字段的 API 名称（或点式查找路径） |
| `<table>` | 是 | 字段所属的对象——基本对象名称或点式关系路径 |
| `<checkedByDefault>` | 是 | 如果列在报表构建器中默认选中，则为 `true` |
| `<displayNameOverride>` | 否 | 报表构建器中显示的自定义列标签，覆盖字段的默认标签 |

## 关键规则（首先阅读）

### 规则 1：如果 `<fullName>` 存在，它必须与文件名匹配
在源格式中，`fullName` 继承自 `Metadata` 并派生于文件名，因此从技术上讲是可选的。仓库约定是包含它。**如果你包含 `<fullName>`，其值必须与文件名（`.reportType-meta.xml` 之前的部分）完全匹配——相同字符、相同大小写、相同下划线。**

**错误**——文件名和 `<fullName>` 不匹配：
- 文件：`account_projects.reportType-meta.xml`
- `<fullName>AccountProjects</fullName>`
  (不匹配：文件使用 `account_projects`，fullName 使用 `AccountProjects`)

**正确**——文件名和 `<fullName>` 完全相同：
- 文件：`AccountProjects.reportType-meta.xml`
- `<fullName>AccountProjects</fullName>`

### 规则 2：连接语义——`outerJoin` 控制包含
每个 `<join>` 块都有一个 `<outerJoin>` 元素，它决定哪些主要记录出现在报表中：

| `<outerJoin>` 值 | 行为 | 报表构建器标签 |
|-------------------|------|----------------|
| `false` | 内连接——只有具有至少一个相关记录的主要记录 | "每个 'A' 记录必须至少有一个相关的 'B' 记录" |
| `true` | 外连接——所有主要记录，无论是否有相关记录 | "'A' 记录可能有也可能没有相关的 'B' 记录" |

**未指定时的默认值：** 当用户希望无论子记录是否存在都看到所有主要记录时，使用 `true`（外连接）。当报表只有在子记录存在时才有意义时，使用 `false`。

### 规则 3：每个对象都需要自己的 `<sections>` 块
CRT 中的每个对象（主要对象 + 每个连接对象）都必须有一个相应的 `<sections>` 块，列出用于报表的字段。没有对象的 `<sections>` 块，其字段不会出现在报表构建器中。

- 每个组的 `<masterLabel>` 是报表构建器中的组标题
- `<columns>` 条目列出字段——每个字段都有 `<field>`（API 名称）和 `<table>`（对象 API 名称）
- 对于通过查找路径到达的字段，在 `<field>` 中使用点表示法（例如 `Owner.Email`（所有者用户的电子邮件）或 `ReportsTo.CreatedBy.Contact.Owner.MobilePhone`）。`<table>` 仍然必须是拥有起始字段的对象。

### 规则 4：使用字段 API 名称，而不是标签
使用字段的精确 API 名称：标准字段使用其定义名称（`Name`、`CreatedDate`、`OwnerId`），自定义字段使用 `Field__c`。自定义对象必须包含 `__c`。

**错误：**
- `<field>Account Name</field>`

**正确：**
- `<field>Name</field>` 与 `<table>Account</table>`

### 规则 5：连接对象的关联路径
添加 `<join>` 时，`<relationship>` 元素必须使用从子对象指向父对象的查找/主从字段的**子关系名称**。对于自定义关系，这通常以 `__r` 结尾。

**错误：**
- `<relationship>Project</relationship>`（对于自定义子关系）

**正确：**
- `<relationship>Projects__r</relationship>`（子关系名称）
- `<relationship>Contacts</relationship>`（标准、非自定义子关系）

### 规则 6：连接链中最多 4 个对象
单个 CRT 最多可以连接**四个对象**（基本对象 + 最多 3 个通过嵌套 `<join>` 块添加的对象）。

### 规则 7：外连接之后不能有内连接
一旦连接链中包含外连接（`<outerJoin>true</outerJoin>`），每个后续嵌套连接也必须是一个外连接。在序列中较早位置的外连接之后不允许内连接。

**错误：**
```xml
<join>
    <outerJoin>true</outerJoin>        <!-- 外连接首先 -->
    <relationship>Contacts</relationship>
    <join>
        <outerJoin>false</outerJoin>   <!-- 错误：外连接之后有内连接 -->
        <relationship>Assets</relationship>
    </join>
</join>
```

**正确：**
```xml
<join>
    <outerJoin>true</outerJoin>
    <relationship>Contacts</relationship>
    <join>
        <outerJoin>true</outerJoin>    <!-- 外连接保持外连接 -->
        <relationship>Assets</relationship>
    </join>
</join>
```

### 规则 8：连接对象的 `<table>` 使用点式路径
在 `<sections>` 中，`<table>` 元素标识连接链中的每个列属于哪个对象。对于基本对象，直接使用对象名称（例如 `Account`）。对于连接对象，使用从基本对象开始的**点式关系路径**。

| 链中的对象 | `<table>` 值 |
|-----------------|-----------------|
| 基本（Account） | `Account` |
| 第一个连接（Account → Contacts） | `Account.Contacts` |
| 嵌套连接（Account → Contacts → Assets） | `Account.Contacts.Assets` |

### 规则 9：字段路径可以遍历查找
`<field>` 值可以引用通过查找关系到达的字段，使用点表示法——例如 `Owner.Email`（所有者用户的电子邮件）或 `ReportsTo.CreatedBy.Contact.Owner.MobilePhone`。`<table>` 仍然必须是拥有起始字段的对象。

### 规则 10：历史趋势字段使用 `_hst` 后缀
对于具有 `trackTrending=true` 的字段，`<field>` 和 `<table>` 中的 API 名称使用 `_hst` 后缀：

```xml
<columns>
    <checkedByDefault>false</checkedByDefault>
    <field>Field2__c_hst</field>
    <table>CustomTrendedObject__c.CustomTrendedObject__c_hst</table>
</columns>
```

### 规则 11：部署后不能更改主要对象
部署后，CRT 的 `<baseObject>` 被锁定。要更改主要对象，请创建新的 CRT 并停用旧的 CRT。

### 规则 12：`autogenerated` 保留用于历史趋势
`<autogenerated>` 元素（API 29.0+）标记 Salesforce 在对象启用了历史趋势时自动创建的 CRT。不要在手动编写的 CRT 上手动设置此元素。

## 生成工作流

### 第 1 步：收集需求
- 主要对象 API 名称（例如 `Account`、`Project__c`）
- 相关对象及其关系（每个关系哪个具有查找/主从字段）
- 对于每个关系：内连接（子记录必需）或外连接（子记录可选）？
- 每个对象要暴露哪些字段——目标是任务相关，而不是完整字段列表
- 受众和类别——这个应该出现在报表构建器选择器中的哪个位置？
- 是否现在作为 `deployed=true` 发送，还是保持 `deployed=false` 在迭代期间

### 第 2 步：检查现有示例
- 查看项目中在项目中的 CRT 模式
- 如果已从组织检索了现有报表类型，请与这些结构进行比较

### 第 3 步：编写规范
在编写之前记录：
- `fullName` 和 `label`
- `baseObject`
- 类别和 `deployed` 状态
- 连接链：对于每个相关对象——关系名称、外连接与内连接
- 组布局：每个对象一个组，字段有序列表
- 接受标准：报表运行时哪些记录应该出现，构建器中哪些字段可用

### 第 4 步：编写元数据文件

从 `examples/` 中的最接近示例开始，并根据用户的场景进行修改：

- 仅主要对象（无连接）→ `examples/AccountsWithIndustry.reportType-meta.xml`
- 外连接（即使没有子记录也包含主要记录）→ `examples/AccountsWithProjects.reportType-meta.xml`
- 嵌套内连接（每个级别都需要子记录）→ `examples/AccountProjectsWithTasks.reportType-meta.xml`

命名文件 `<DeveloperName>.reportType-meta.xml`。

### 第 5 步：验证
- 结构良好的 XML，具有正确的命名空间 (`xmlns="http://soap.sforce.com/2006/04/metadata"`)
- 文件名（不包含 `.reportType-meta.xml`）与 `<fullName>` 匹配，当 `<fullName>` 包含时
- `<baseObject>` 是有效的 API 名称，该对象已部署
- 每个 `<relationship>` 使用正确的子关系名称（自定义使用 `__r` 后缀）
- `<sections>` 中引用的每个对象都是 CRT 的一部分（主要或连接）
- 所有 `<field>` 引用在父 `<table>` 上存在，并使用 API 名称（不是标签）
- `<category>` 是有效的 Salesforce 类别值
- `<deployed>` 如果用户需要立即访问 CRT，则为 `true`

## 验证检查清单

### 通用检查
- [ ] 文件扩展名是 `.reportType-meta.xml`
- [ ] 文件基本名满足开发者名称规则（以字母开头，仅字母/数字/下划线，不能有空格，不能有尾随下划线，不能有连续下划线）
- [ ] 如果包含 `<fullName>`，它必须与文件基本名完全匹配（相同字符、大小写和下划线）
- [ ] `<label>` 是人类可读的，长度不超过 40 个字符
- [ ] `<description>` 解释了业务目的
- [ ] `<baseObject>` 使用有效的 API 名称，该对象已部署
- [ ] `<category>` 是有效的 `ReportTypeCategory` 枚举值
- [ ] `<deployed>` 设置适当（`true` 表示用户访问，`false` 表示进行中迭代）
- [ ] `<autogenerated>` 不手动设置（保留用于历史趋势的 CRT）

### 连接检查
- [ ] 每个 `<join>` 使用正确的子**关系名称**（不是查找字段的 API 名称）
- [ ] 自定义关系使用 `__r` 后缀
- [ ] `<outerJoin>` 故意设置：`true` = 子记录可选，`false` = 子记录必需
- [ ] 在序列中较早位置的外连接之后不出现内连接（`<outerJoin>false</outerJoin>`）
- [ ] 总对象数（基本 + 连接，包括嵌套）为 4 或更少

### 组检查
- [ ] CRT 中的每个对象都有相应的 `<sections>` 块
- [ ] 每个组的 `<masterLabel>` 是描述性的
- [ ] 每个 `<columns>` 都有 `<field>`（API 名称）和 `<table>`（对象 API 名称或点式路径）
- [ ] `<checkedByDefault>` 为每个列设置
- [ ] 基本对象的 `<table>` 是对象 API 名称（例如 `Account`）
- [ ] 连接对象的 `<table>` 使用点式关系路径（例如 `Account.Projects__r`、`Account.Projects__r.Tasks__r`）
- [ ] 字段引用使用 API 名称（不是标签）；自定义字段使用 `__c`
- [ ] 查找遍历字段使用点表示法（例如 `Owner.Email`）并将 `<table>` 设置为拥有起始字段的对象
- [ ] 历史趋势字段在适用情况下在 `<field>` 和 `<table>` 中使用 `_hst` 后缀
- [ ] 组内没有重复字段
