# SLDS 质量审计

审计 Lightning Web Components 以确保符合 SLDS 标准，并生成自动化的评分卡以及必要的手动审查关卡。结合 SLDS linter 输出与补充静态分析，以捕捉 linter 未发现的问题。

## 范围

同样适用于：
- 审计项目或组件集的 SLDS 合规性
- 在进行更改后的质量前后比较

不适用于：
- **修复** linter 违规 — 请使用 `design-systems-slds2-migrate` 而不是
- **构建** 新组件 — 请使用 `design-systems-slds-apply` 而不是
- **仅运行 linter** — 直接运行 `npx @salesforce-ux/slds-linter@latest lint .` 即可
- **完整的 WCAG 无障碍审计** — 此技能仅检查属性存在性（标签、替代文本、焦点指示器），不包括对比度比例、键盘流程或屏幕阅读器行为
- **特定框架模板审计** 超出 `.css`、`.html` 和 `.js` 文件 — JSX/TSX/Vue/Svelte 输出需要额外的手动审查

---

## 质量验证流程

```text
1. 运行 SLDS Linter     → 收集违规计数（linter 的工作）
2. 运行分析脚本       → 检查 linter 未覆盖的内容（补充）
3. 代理审查           → 必须的手动审查关卡
4. 评分与评级       → 计算自动评分 + 最终建议
5. 生成报告           → 生成格式化的评分卡
```

## 第 1 步：运行 SLDS Linter

运行 linter 以收集基线违规数据：

```bash
npx @salesforce-ux/slds-linter@latest lint <component-path> 2>&1
```

按规则计数违规。这些直接输入到 **Linter 合规性** 评分：

| 规则               | 影响 |
|-------------------|------|
| `slds/class-override` | 破坏主题、暗黑模式 |
| `slds/lwc-token-to-slds-hook` | SLDS 1 技术债务 |
| `slds/no-hardcoded-values` | 破坏主题、无障碍性 |

**Linter 合规性评分** = `100 - (total_violations × 10)`，最低为 0。

**如果 linter 不可用**（没有 Node.js、没有网络访问、CI 沙盒限制）：跳过此步骤，在报告标题中注明“Linter 未运行”，将 Linter 合规性标记为 N/A，并使用剩余的 4 个类别重新归一化到 100% 计算整体评分：

```text
Overall (linter unavailable) = (Theming × 0.29) + (Accessibility × 0.29)
                              + (CodeQuality × 0.21) + (ComponentUsage × 0.21)
```

## 第 2 步：运行补充分析

运行分析脚本以捕获 linter 未覆盖的问题。捆绑的分析器仅扫描 `.css`、`.html` 和 `.js` 文件：

```bash
node scripts/analyze-quality.cjs <component-path>
```

脚本输出 JSON 格式的结果，按严重性组织。它检查：

### CSS 检查（linter 补充）

| 检查               | 捕获的内容          | 严重性 |
|-------------------|---------------------|--------|
| 缺少后备值         | 没有 fallback 值的 `var(--slds-g-*)` | 严重 |
| 发明的钩子（T051） | 未在 `hooks-index.json` 中找到的 `--slds-g-*` 令牌（需要 `--hooks-index`） | 严重 |
| 钩子配对         | 没有匹配的前景钩子的背景钩子 | 警告 |
| `!important`       | 特定性覆盖         | 警告 |
| 魔术像素值         | 未使用间距钩子的硬编码 `px` | 警告 |
| 高 z-index        | z-index 值 > 99     | 警告 |
| 移除轮廓         | 没有 alternative focus style 的 `outline: none` | 警告 |

### JS 检查

| 检查               | 捕获的内容          | 严重性 |
|-------------------|---------------------|--------|
| 内联样式赋值       | `.style.*=` 直接属性赋值 | 警告 |
| SLDS 类操作       | 动态 `.classList.add('slds-*')` 操作 | 警告 |

### HTML 检查

| 检查               | 捕获的内容          | 严重性 |
|-------------------|---------------------|--------|
| LBC 输入标签       | 没有 `label` 属性的 `<lightning-input>` | 严重 |
| 图标替代文本       | 没有 `alternative-text` 的 `<lightning-icon>` | 严重 |
| 图像替代文本       | 没有 `alt` 的 `<img>` | 严重 |
| 标题层级         | 跳过标题层级（h2 到 h4） | 警告 |
| 正向 tabindex      | 非 0 或 -1 的 `tabindex` 值 | 警告 |
| 可点击的 divs     | `<div onclick>` 而不是 `<button>` | 警告 |
| 内联样式         | `style="..."` 属性 | 警告 |
| 原生元素         | 存在 LBC 替代方案时的 `<input>`、`<button>`、`<select>` | 警告 |

### 钩子配对验证

脚本检查背景/前景钩子是否语义配对：

```text
surface-* 背景     → on-surface-* 文本
surface-container-* bg    → on-surface-* 文本
accent-* 背景      → on-accent-* 文本
accent-container-* bg     → on-accent-* 文本
```

> **限制**：钩子配对按文件级别检查，而不是按选择器。一个在 `.classA` 中有 `surface-1`、在 `.classB` 中有 `on-accent-1` 的文件会通过，因为 surface 和 accent 系列 都存在。在手动审查（第 3 步）时按选择器审查配对正确性。

### 发明钩子检测（T051）

脚本将 CSS 中的每个 `--slds-g-*` 令牌与 `hooks-index.json` 进行交叉引用。任何在元数据中未找到的钩子都会被标记为严重 — 这捕获了最常见的代理错误，即从命名模式中发明钩子。

## 第 3 步：代理手动审查

这些检查需要理解组件的用途，并且无法可靠地自动化。审查每个并分类发现为：

- **阻断** — 不正确的蓝图结构、缺少必需状态，或语义/交互问题使组件无法用于生产
- **建议** — 值得改进的改进，但单独不会阻止发布

| 审查区域         | 查找内容          |
|-----------------|------------------|
| 加载状态         | 组件在获取数据时是否显示加载动画或骨架屏？ |
| 错误状态         | 是否向用户显示可操作的错误消息？ |
| 空状态         | 当没有数据时是否有有意义的空状态？ |
| 禁用状态         | 交互元素是否在视觉和功能上处理禁用？ |
| 语义 HTML       | 是否在适当的地方使用 `<nav>`、`<article>`、`<section>`？ |
| SLDS 蓝图合规性 | 卡片、模态框、表单是否遵循 SLDS 蓝图结构？ |

> 手动审查发现不会自动化，但会影响最终建议。不要仅报告自动评分作为最终结论。

## 第 4 步：计算自动评分和最终建议

### 组件复杂度

在评分之前，对组件进行分类以提供评分背景：

| 复杂度         | 标准          | 报告注释          |
|---------------|---------------|------------------|
| 小型         | 1-2 个文件，< 100 行总代码 | 评分是高置信度（小表面区域） |
| 中型         | 3-6 个文件，100-500 行总代码 | 评分反映典型组件        |
| 大型         | 7+ 个文件，500+ 行总代码 | 评分反映绝对问题计数 — 即使构建良好的大型组件也可能评分较低 |

在报告标题中包含复杂度分类。这防止了在 1000 行组件上的“B”与 20 行组件上的“B”被误读。

### 自动评分公式

```text
Category Score = 100 - (critical_issues × 10) - (warnings × 3) - (info × 1)
Minimum score: 0
```

### 类别和权重

| 类别           | 权重 | 来源          |
|---------------|------|---------------|
| Linter 合规性 | 30%  | SLDS linter 输出（第 1 步） |
| 主题           | 20%  | 脚本：后备值、钩子配对（第 2 步） |
| 无障碍性       | 20%  | 脚本：标签、替代文本、焦点（第 2 步） |
| 代码质量       | 15%  | 脚本：`!important`、内联样式、z-index（第 2 步） |
| 组件使用       | 15%  | 脚本：原生元素（第 2 步）加上手动语义/蓝图审查（第 3 步） |

### 自动整体评分

```text
Overall = (Linter × 0.30) + (Theming × 0.20) + (Accessibility × 0.20)
        + (CodeQuality × 0.15) + (ComponentUsage × 0.15)
```

### 自动评级阈值

| 评分       | 等级 | 含义          |
|-----------|------|---------------|
| 90-100    | A    | 优秀的自动评分 |
| 80-89     | B    | 良好的自动评分 |
| 70-79     | C    | 可接受的自动评分 |
| 60-69     | D    | 弱的自动评分  |
| 0-59      | F    | 失败的自动评分 |

### 手动审查关卡

在计算自动评分后，应用手动审查结果：

| 关卡       | 使用时机          | 对最终建议的影响          |
|-----------|------------------|--------------------------|
| 通过       | 没有手动发现      | 最终建议可以遵循自动评分  |
| 建议       | 仅非阻断手动发现      | 最终建议最多可以是“需要跟进” |
| 阻断       | 一个或多个阻断手动发现      | 最终建议是**不适用于生产**，无论自动评级如何 |

### 最终建议规则

结合自动评分和手动审查关卡：

| 最终建议         | 条件          |
|-----------------|---------------|
| 适用于生产       | 自动评级 A/B，无严重发现，手动关卡 = 通过 |
| 需要跟进       | 自动评级 A/B，无严重发现，手动关卡 = 建议 |
| 需要改进       | 任何严重发现，自动评级 C/D，或手动关卡 = 阻断 |
| 失败           | 自动评级 F    |

## 第 5 步：生成质量报告

使用 **[report-format.md](references/report-format.md)** 中的模板生成最终报告。默认使用 **紧凑格式** 进行初始输出，并按需扩展部分。

报告包括：
- 带有自动评级和最终建议的执行摘要
- 手动审查关卡结果（`Pass`、`Advisory` 或 `Blocking`）
- 按类别评分，带视觉指示器
- 按严重性组织的详细发现
- 具体的代码位置和建议
- 必需行动的清单

## 快速验证模式

进行快速质量检查，无需完整分析：

1. 运行 linter: `npx @salesforce-ux/slds-linter@latest lint <path>`
2. 按类型计数违规
3. 仅报告摘要

```text
快速质量检查: <component-name>
─────────────────────────────────────
Linter 违规:
  • 类覆盖:     0
  • 已弃用令牌:  3
  • 硬编码值:   5

快速自动评级: C（估计）
运行完整验证以获取详细报告。
```

## 边缘情况和误报

| 情况               | 指导          |
|-------------------|---------------|
| **无头组件**（仅 JS，无 HTML） | 跳过 HTML 检查；仅评分 CSS + linter 类别 |
| **包装/容器组件** | 可能合法地具有最少 CSS；不要惩罚钩子使用量低 |
| **有意使用的原生元素** | `<button>` 在自定义 SLDS 蓝图内是正确的；如果 `slds-*` 蓝图结构内，则抑制 C002 |
| **LEX 外的组件** | LWR/Experience Cloud 组件可能不使用 Lightning Base Components；在报告中注明上下文 |
| **测试/演示组件** | 降低标准 — 在报告中注明，但不要在警告上阻断 |

如果检查产生误报，请在报告中注明“抑制”并说明理由，而不是静默忽略。
