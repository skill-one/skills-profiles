# CMDB 设置协调器（服务云 ITSM）

通过展示有序的设置层级，将用户引导至服务云 ITSM 中的**配置管理数据库 (CMDB)** 启用过程，并将每个层级委托给专门的子技能执行，跟踪进度直至 CMDB 可端到端使用。每个子技能都在**Salesforce 托管的 Headless-360 MCP 服务器**上运行，因此相同的流程适用于**生产环境**和沙盒——组织与当前的 MCP 会话绑定，无需为每个用户单独安装 MCP。

## 目标

作为 CMDB 启用的顶层协调器。向用户展示有序层级，为每个层级调用适当的子技能，验证层级成功后再继续，并在每个层级完成后返回菜单，显示更新后的进度，直至 CMDB 准备就绪或用户停止。

## CMDB 前置条件堆栈（顺序为何重要）

CMDB 受到四层堆栈的限制。每个 CMDB Connect API 都会检查 `orgHasCMDBEnabled`，其值为 `orgHasCMDBPermission && OrgPreferences.CMDBEnabled`。如果失败，将返回 `403 FUNCTIONALITY_NOT_ENABLED`。这些层级必须**按顺序**满足：

```text
层级 0  组织 SKU / 许可证      组织必须已授予 ITSrvcsCnfgMgmnt 权限（版本/许可证/模板）。不可由任何 API 设置——仅验证。
层级 1  租户配置               CMDB 租户必须达到 PROVISIONED 状态（异步）。
层级 2  功能启用               启用 feature service-cloud-itsm-cmdb-integration 功能。这是内部设置 CMDBEnabled 并解除 403 防火墙的操作。
层级 3  用户访问               将 PSL + CMDB 权限集分配给用户。
层级 4  内容包                安装 CMDB 基础（基础）内容包。
层级 5  资产发现               启用 feature service-cloud-itsm-discovery-integration 并授予 Discovery 页面访问权限（IT 服务发现管理器权限集）。最后运行——依赖于基础 CMDB 功能和早期层级。
```

层级 0 是一个硬性前置条件：如果组织没有 CMDB SKU，**任何 API 都无法授予**，设置无法继续。协调器会清晰地展示此问题并停止。

## 行为

### 1. 从对话中提取上下文

在展示选项之前，扫描聊天历史记录以查找：

- 目标组织（别名/用户名）——每个子技能都需要
- 已完成的层级（跳过或标记为完成）
- 用户提到的任何约束（例如，“先启用它，我们稍后会分配用户”）

从**最新**的层级活动记录中推导层级状态。在长对话或**恢复**的对话中（例如，稍后继续的 Headless 会话），不要将早期高亮的层级视为仍然当前——从最新的子技能结果重新推导当前层级，如果存在歧义，请在重新展示菜单前再次确认用户。

### 2. 确认目标组织

CMDB 启用会对**真实组织**执行写入操作（租户配置、功能启用、权限集分配、包安装）。在执行任何操作之前，请向用户确认目标组织，并明确说明该组织将被修改。永远不要假设生产环境可以安全更改——要求用户明确确认组织。

### 3. 展示 CMDB 设置菜单

展示有序层级及其状态：

```text
CMDB 设置（通过 service-itsm-agentic-setup-cmdb-coordinate）

目标组织：<组织>   （以下所有步骤都针对此组织运行）

CMDB 按有序层级启用。每个层级必须成功后才能继续：
```

| #   | 层级                    | 操作说明                                                 | 状态  |
| --- | ------------------------ | ------------------------------------------------------------ | ------- |
| 0   | 许可证检查            | 确认此组织已获得 CMDB 许可（由版本/许可证设置——无法开启） | 待处理 |
| 1–2 | 配置并启用 CMDB          | 设置 CMDB 租户，然后启用 CMDB 功能，使其可用             | 待处理 |
| 3   | 分配用户访问权限       | 授予所选用户的 CMDB 访问权限                              | 待处理 |
| 4   | 安装内容包            | 安装 CMDB 基础（基础）内容                               | 待处理 |
| 5   | 启用资产发现           | 启用资产发现并授予 Discovery 页面访问权限（最后一步——需要先完成以上步骤） | 待处理 |

```text
我建议按顺序运行这些操作。您想从哪一步开始（或者我直接运行 1 → 5）？
```

每层使用单行单元格渲染——不要将层级拆分到堆叠行中或将单元格换行到第二行。将配置和启用步骤合并为单个行 `1–2`。仅显示具有对应且可工作的子技能的层级。**不要**显示占位符层级。

### 4. 委托给子技能

| 层级 | 子技能                  |
|-------|-------------------------|
| 0 (组织 SKU 检查) + 1 (租户配置) + 2 (功能启用) | `service-itsm-agentic-setup-cmdb-configure` |
| 3 (用户访问) | `service-itsm-agentic-setup-cmdb-access-assign` |
| 4 (内容包) | `service-itsm-agentic-setup-cmdb-bundle-deploy` |
| 5 (资产发现) | `service-itsm-agentic-setup-cmdb-discovery-configure` |

`service-itsm-agentic-setup-cmdb-configure` 拥有层级 0 的门禁。如果它报告组织未获得 CMDB 许可（`ITSrvcsCnfgMgmnt` 组织权限——内部细节；不要向用户展示开发者名称），则**停止整个流程**——后续层级无法成功。传达其简明语言消息，不要尝试层级 3 或 4。

### 5. 每个层级完成后

1. **验证**子技能报告的成功（功能 `ENABLED`、租户 `PROVISIONED`、分配确认、包安装启动）。如果失败，停止并展示失败——不要继续。
2. **更新状态**——将完成的层级标记为“完成”。
3. **建议下一步**在依赖顺序中。
4. **重新展示菜单**，显示更新后的状态。

### 6. 完成摘要

当所有可用层级完成（或用户停止）时，展示最终摘要：

```text
CMDB 设置 — 完成（通过 service-itsm-agentic-setup-cmdb-coordinate）

目标组织：<组织>
```

| #   | 层级                    | 状态 |
| --- | ------------------------ | ------ |
| 0   | 许可证检查            | 完成  |
| 1–2 | 配置并启用 CMDB          | 完成  |
| 3   | 用户访问              | 完成  |
| 4   | 内容包（基础）    | 完成  |
| 5   | 资产发现 + 访问 | 完成  |

```text
CMDB 已启用并准备就绪。具有分配权限集的用户现在可以处理配置项。接下来，您可以建模 CI、识别规则和关系。
```

## 功能依赖与推荐顺序

```text
0. 组织 SKU 检查          (前置条件——如果缺失则硬停止；任何 API 都无法授予)
1. 租户配置               (异步基础设施；必须达到 PROVISIONED 状态)
2. CMDB 功能启用         (设置 CMDBEnabled；解除 403 防火墙——包/CI API 在此之前仍为 403)
3. 用户访问             (PSL + 权限集；没有这些用户无法查看 CMDB)
4. 内容包                (CMDB 基础包；需要层级 2——包 API 在启用前为 403)
5. 资产发现             (启用 service-cloud-itsm-discovery-integration 并通过 IT 服务发现管理器权限集授予 Discovery 页面访问权限；最后层级——需要基础 CMDB 功能和早期层级；完成前被阻塞)
```

层级 1 和 2 由 `service-itsm-agentic-setup-cmdb-configure` 一起处理，因为层级 2 在层级 1 达到 `PROVISIONED` 状态后才能成功。将它们展示为单个步骤。

## 规则

- **始终**在标题中显示 "(via service-itsm-agentic-setup-cmdb-coordinate)"，以便用户知道此技能处于活动状态
- **始终**在运行任何层级之前确认目标组织，并说明该组织将被修改
- **始终**在执行操作前展示菜单——不要假设用户想执行哪个层级
- **永不**在未选择（或确认“全部运行”）的情况下运行层级
- **永不**在失败层级后继续——停止，用简明语言解释，并提供下一步操作
- 如果层级 0 失败（组织缺少 `ITSrvcsCnfgMgmnt`），**完全停止**并解释这是一个许可证/版本前置条件，任何 API 都无法授予
- 如果子技能报告前置条件缺失或失败，用友好、可操作的语言传达给用户——不要隐藏错误
- 跨对话跟踪进度——不要将已完成的层级重新展示为“待处理”。从最新的子技能活动重新推导当前层级，而不是从之前渲染的高亮中；在恢复或长对话中，不要假设最后高亮的层级仍然当前——如果存在歧义，请再次与用户确认
- **不要**在用户界面输出中暴露内部技术术语。这包括 Salesforce 记录 ID 和组织 ID、原始 HTTP 状态码（403、500、…）、API 错误代码（`FUNCTIONALITY_NOT_ENABLED`、`DUPLICATE_VALUE`、…）、内部端点/API 名称（`bundleListView`、`tenantProvisioningStatus`、…）、开发者名称（`ITSrvcsCnfgMgmnt`、`ItSrvcCnfgItmReadPsl`、…）以及 MCP/工具内部细节（`dispatch`、`headless-360`）。将所有内容翻译为简明的、人类可读的语言——例如，说“此组织未获得 CMDB 许可”而不是 "`ITSrvcsCnfgMgmnt` 是 false / 403”。作为下一步指针显示的子技能名称是允许的。将所有此类技术细节保留在自己的推理中，而不是屏幕上。

---

## 添加新层级

当创建新的 CMDB 子技能时（例如，可选的附加包、Discovery、识别规则），将它们添加到：(1) 步骤 3 中的菜单表格， (2) 步骤 4 中的委托表格，以及 (3) 上面的依赖顺序，保留有序层级模型。
