# 有效 LiteParse

使用 `lit` CLI 在本地从文档中提取文本——这是一个快速、无模型的解析器。这项技能是关于如何**低成本地**使用它：每次 `lit parse` 都会重新运行完整的提取，并且你每次将文本输入对话中，都会在后续的每一轮中付费。以下模式来自分析真实的代理跟踪记录，其中相同的 PDF 被解析了高达 **9 次**，而单次图像读取的成本高达 **140k+ 字符**的上下文。不要重复这些错误。

## 金科玉律：一次解析到文件，然后搜索文件

`lit parse` 每次调用时都会重新提取整个文档。每次搜索时重新解析是跟踪记录中 #1 的浪费。将文档解析一次到一个临时文件，然后针对该文件运行所有搜索：

```bash
# 每个文档只执行一次。--no-ocr 用于原生数字 PDF（几乎所有报告）——速度更快。
lit parse "/abs/path/doc.pdf" --format text --no-ocr -o /tmp/doc.txt && wc -l /tmp/doc.txt
```

然后用廉价的 Shell 工具搜索文件——**永远**不要再运行 `lit parse` 来搜索。

## 搜索纪律——最小化 ROUND-TRIPS，然后保持结果小

每次 Bash 调用都是一个完整的模型往返（延迟 + 重新读取上下文）。解析之后最大的浪费是一个**串行**循环：grep → 查看 → 再次 grep → `sed` 读取窗口 → 再次 grep。在跟踪记录中，这使轮次数翻倍，而只是读取文档。两条规则可以解决这个问题：

**1. 在同一个命令中获取上下文——不要先 grep 然后用 `sed`。** 使用 `grep -C` 使命中结果及其周围的行一起返回。这移除了常见情况下的后续 `sed` 轮次：

```bash
grep -n -i -C4 "total assets" /tmp/doc.txt | head -40      # 位置及其窗口，一轮
```

只有在你知道确切行号并且需要比 `-C` 提供的更宽的窗口时，才回退到 `sed -n 'A,Bp'`。

**2. 将独立的查找批量到一个命令中。** 当一个问题需要多个不同的信息（例如排放 *和* 收入）时，不要为每个术语花费一轮。用标签一起探测它们：

```bash
for q in "carbon intensity" "scope 1" "total revenue"; do \
  echo "=== $q ==="; grep -n -i -C3 "$q" /tmp/doc.txt | head -25; done
```

然后保持结果小：

- **始终用 `head` 限制输出**，并使用 `-n` 来显示行号。
- **不要盲目发散。** 目标是在 ≤3 个搜索命令中解决一个问题。如果两个目标化的 greps 没有锁定答案，切换到 `search.py`（下面）——不要继续每次一轮一个关键词变体。
- 倾向于使用 Bash `grep`/`sed` 在保存的文件上，而不是在 Read and Grep 工具上——往返次数更少，并且你精确控制输出大小。

## 关键词不确定时的排序搜索（捆绑辅助工具）

当两个目标化的 greps 没有锁定答案时，**停止 greping**——不要每次一轮一个关键词变体。运行捆绑的 BM25 排序器 ONCE，以单个命令中显示最相关的行窗口：

```bash
./.claude/skills/effective-liteparse/scripts/search.py /tmp/doc.txt -q "materiality assessment priority topics" -k 8 -e 5
```

`-k` = 匹配数量，`-e` = 每个窗口周围的行数（因此窗口会直接返回——不需要后续 `sed` 轮次）。它返回带行号的排序窗口。使用丰富的自然语言查询（一个字符串中包含多个同义词），而不是单个关键词。这取代了长链的猜测性 greps。

## 原生数字与扫描

- **原生数字 PDF**（真实文本层——几乎所有企业/金融/ESG 报告）：始终传递 `--no-ocr`。它更快，文本也相同。保留 OCR 会浪费时间。
- **扫描 PDF / 图像**：去掉 `--no-ocr`。如果值缺失或数字看起来不正确，请直观地读取页面（见下文），而不是信任 OCR。

## 直观读取页面——最后手段，一次截图，适度的 DPI

截图是你放入上下文中最昂贵的东西：一个单次高 DPI 页面 PNG 在一个跟踪记录中运行了 **~140k 字符**，并且代理经常重复渲染同一页面（默认 + 高分辨率）。

只有在文本/表格确实无法回答问题时才截图（密集的多列表格、图形、图表）。然后：

- 一次渲染**一个**页面，使用 `--target-pages "N"`（注意：它是 `--target-pages`，不是 `--pages`）。
- 使用**适度的 DPI (~150–200)**。不要从 300+ 开始；不要在更高 DPI 下重新渲染同一页面，除非文本实际上无法辨认。

```bash
lit screenshot "/abs/path/doc.pdf" --target-pages "13" --dpi 150 -o /tmp/shots/   # 然后读取 PNG
```

## 关于同一文档的许多问题

一次解析到文件已经涵盖了这一点：保留 `/tmp/doc.txt` 并在所有问题中重复使用它，而不是重新解析。

## 不要在序幕上浪费轮次

除非实际出现错误，否则跳过 `lit --version`、`ls -la` 和 `lit … --help`。直接进入解析。你需要的核心标志：

`--format text|json` · `--no-ocr` · `--target-pages "1-5,10"` · `--dpi <n>`（默认 150）·
`--ocr-language <iso>`。只有在需要边界框/布局时才使用 `--format json`——它更大；仍然搜索它，不要加载整个文件。

## 设置

PDF 可以直接使用。如果 `lit` 缺失：`npm i -g @llamaindex/liteparse`。办公文档需要 LibreOffice；图像需要 ImageMagick（两者都会自动转换为 PDF）。
