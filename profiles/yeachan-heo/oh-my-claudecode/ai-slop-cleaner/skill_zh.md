# AI冗余代码清理器

使用此技能清理AI生成的冗余代码，而不会偏离范围或改变预期行为。在OMC中，这是针对工作正常但感觉臃肿、重复、测试不足或过度抽象的代码的有限清理工作流。

## 使用场景

在以下情况下使用此技能：
- 用户明确说明 `deslop`、`anti-slop` 或 `AI冗余代码`
- 请求清理或重构感觉嘈杂、重复或过于抽象的代码
- 后续实现留下重复逻辑、死代码、包装层、边界泄漏或弱回归覆盖
- 用户通过 `--review` 想要仅限审阅员的反冗余处理
- 目标是简化清理，而不是新功能交付

## 不适用场景

在以下情况下不要使用此技能：
- 任务主要是新功能构建或产品变更
- 用户想要全面重构，而不是增量清理
- 请求是通用重构，没有任何简化或反冗余意图
- 行为过于模糊，无法通过测试或具体验证计划来保护

## OMC执行姿态

- 除非用户明确要求行为变更，否则保留行为。
- 在实际情况下，首先使用聚焦回归测试锁定行为。
- 在编辑代码之前编写清理计划。
- 优先删除而不是添加。
- 在引入新工具之前重用现有工具和模式。
- 除非用户明确要求，否则避免新依赖项。
- 保持差异小、可逆且聚焦于气味。
- 保持简洁和证据密集：检查、编辑、验证和报告。
- 将新用户指令视为本地范围更新，而不会丢弃先前的非冲突约束。

## 范围文件列表使用

当调用者已经知道安全的清理表面时，此技能可以限定为显式文件列表或更改文件范围。

- 适用场景：`oh-my-claudecode:ai-slop-cleaner skills/ralph/SKILL.md skills/ai-slop-cleaner/SKILL.md`
- 适用场景：一个Ralph会话仅传递该会话中更改的文件
- 即使范围是短文件列表，也要保留相同的回归安全工作流
- 除非用户明确要求，否则不要在更改文件范围时静默扩展为更广泛的清理工作

## Ralph集成

Ralph可以将此技能作为有界后审阅清理过程来调用。

- 在该工作流中，清理器以标准模式运行（不是 `--review`）
- 清理范围是Ralph会话的更改文件
- 清理过程后，Ralph会重新运行回归验证
- `--review` 仍然是审阅员仅限的后续模式，而不是默认的Ralph集成路径

## 审阅模式 (`--review`)

`--review` 是在清理工作草拟后的审阅员仅限过程。它存在是为了保留反冗余工作的显式作者/审阅员分离。

- **作者过程**：通过测试锁定清理更改。
- **审阅员过程**：检查清理计划、更改文件和验证证据。
- 同一个过程不能同时编写和自我批准高影响的清理，而没有单独的审阅步骤。

在审阅模式下：
1. 不要从编辑文件开始。
2. 审阅清理计划、更改文件和回归覆盖范围。
3. 特别检查：
   - 剩余的死代码或未使用的导出
   - 应该合并的重复逻辑
   - 仍然模糊边界的无用包装或抽象
   - 缺少测试或保留行为的弱验证
   - 看起来改变了行为而没有意图的清理
4. 生成带有必要后续的审阅员裁决。
5. 将需要的更改交回给单独的作者过程，而不是在一步中修复和批准。

## 工作流

1. **首先保护当前行为**
   - 确定必须保持不变的内容。
   - 在编辑之前添加或运行最窄的回归测试。
   - 如果测试不能首先进行，请在接触代码之前明确记录验证计划。

2. **在代码之前编写清理计划**
   - 将过程限定为请求的文件或功能区域。
   - 列出要移除的具体气味。
   - 从最安全的删除到风险更高的合并，按顺序安排工作。

3. **在编辑之前分类冗余代码**
   - **重复** — 重复的逻辑、复制粘贴分支、冗余的帮助程序
   - **死代码** — 未使用的代码、不可达的分支、过时的标志、调试遗留物
   - **无用的抽象** — 传递式包装器、推测性间接引用、单用途帮助程序层
   - **边界违规** — 隐藏的耦合、错误的职责、错误层级的导入或副作用
   - **缺少测试** — 未锁定的行为、弱的回归覆盖范围、边缘案例差距
   - **UI/设计默认值** — 使AI构建的界面感觉未经审阅的通用视觉模式

### UI/设计审阅员检查清单

将这些用作审阅提示，而不是绝对禁令。在具有明确理由时保留有意品牌、可访问性、产品密度或设计系统选择。

- **韩文可读性**：标记设置为11-12px的正文文本；韩文正文复制通常至少需要14px，除非适用经过验证的密集数据例外。
- **阴影克制**：质疑每个表面、标志、背景、卡片或图标上的框阴影；仅在阴影可以澄清提升或交互的地方保留阴影。
- **内容层次结构**：当标题已经传达信息时，删除重复的眼眉/标题/描述/额外 `<p>` 填充；除非它们是产品声音的一部分，否则避免通用表情符号徽章。
- **调色板理由**：当没有品牌或系统理由时，挑战默认的AI蓝/紫色调色板，特别是类似Tailwind的 `#3B82F6`。
- **布局节奏**：当产品上下文受益于节奏、强调、不对称性、轮播/便当处理或不同卡片权重时，避免过于完美的3或4列均匀网格。
- **渐变克制**：除非品牌故意拥有那种视觉语言，否则降低极端渐变。

4. **一次运行一个聚焦于气味的清理过程**
   - **过程1：死代码删除**
   - **过程2：重复移除**
   - **过程3：命名和错误处理清理**
   - **过程4：测试强化**
   - 每次运行后重新运行目标验证。
   - 不要将不相关的重构捆绑到同一个编辑集中。

5. **运行质量门**
   - 保持回归测试为绿色。
   - 运行相关代码检查、类型检查和单元/集成测试。
   - 当可用时，运行现有的静态或安全检查。
   - 如果门失败，修复问题或撤回有风险的清理，而不是强行通过。

6. **以密集证据的报告结束**
   始终报告：
   - **更改文件**
   - **简化**
   - **行为锁定 / 验证运行**
   - **剩余风险**

## 使用方法

- `/oh-my-claudecode:ai-slop-cleaner <目标>`
- `/oh-my-claudecode:ai-slop-cleaner <目标> --review`
- `/oh-my-claudecode:ai-slop-cleaner <文件-a> <文件-b> <文件-c>`
- 从Ralph：仅在Ralph会话的更改文件上运行清理器，然后返回Ralph进行清理后的回归验证

## 适用场景

**适用**：`deslop这个模块：太多的包装器、重复的帮助程序和死代码`

**适用**：`清理src/auth中的AI冗余代码，并收紧边界而不改变行为`

**不适用**：`重构auth以支持SSO`

**不适用**：`清理格式`
