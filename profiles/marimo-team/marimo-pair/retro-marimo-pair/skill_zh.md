# 会话回顾

你正在帮助一位 **marimo 团队成员** 回顾一次配对会话，以发现摩擦点并将其转化为改进。目标是始终针对以下一个或两个方面：

1. **marimo-pair 技能** (`github://marimo-team/marimo-pair`)
2. **`marimo._code_mode`** — 底层的笔记本元编程 API

这是一个 **对话**，而不是自动生成的报告。你提出发现的问题，用户决定哪些问题重要，然后你们一起决定如何处理这些问题。

## 安全护栏

- **绝对不要** 在未经明确用户批准的情况下编辑 `github://marimo-team/marimo-pair` 中的文件。
- **始终** 从会话分析（步骤 1）开始 — 不要直接跳到解决方案。
- **先呈现摩擦点，再讨论根本原因** — 让用户选择要深入探讨的问题。
- 如果用户以特定的投诉启动会话，请将分析集中在该问题上，但仍然要扫描背景中的其他摩擦点。

## 步骤 1：会话分析

回顾当前的对话并识别摩擦点。寻找以下迹象：

| 信号 | 要寻找的内容 |
|------|--------------|
| **用户沮丧** | 纠正（"不是那个"）、重复尝试、回退、困惑、语气变化 |
| **低效** | 执行一步任务需要多轮、过度设计、错误的 API 使用 |
| **错误** | 编译检查失败、运行时错误、静默失败、错误输出 |
| **变通方法** | 用户或 Claude 绕过限制而不是直接执行 |
| **上下文丢失** | Claude 忘记早期的指令、重新询问技能涵盖的内容 |

列出发现的摩擦点的编号总结。对于每个点，记录：
- 发生了什么（简述）
- 在对话的哪个位置发生的（引用或释义）
- 初始类别猜测（技能结构 / 技能差距 / API 问题 / 等）

然后询问：**"我们应该深入探讨哪些问题？或者我遗漏了什么吗？"**

## 步骤 2：根本原因讨论

对于用户选择的所有摩擦点，通过以下视角进行讨论：

| 视角 | 问题 | 示例改进 |
|------|------|----------|
| **技能结构** | 技能中包含正确信息但难以查找吗？埋藏在参考中 / 而它本应在 SKILL.md 中？ | 提升为护栏、重新结构渐进式披露 |
| **技能差距** | 技能中完全缺少信息吗？ | 添加新部分、示例或反模式 |
| **误导性文档** | 技能中说了什么导致 Claude 误入歧途？ | 修正文档、添加说明性示例 |
| **API 便利性** | `_code_mode` 在此任务中是否笨拙或不直观？ | 提出改进 API（更好的默认值、更清晰的错误） |
| **缺失的 API** | `_code_mode` 是否有它本应能做但实际不能做的事情？ | 设计新的 API 表面 |
| **API 错误** | `_code_mode` 的行为是否不正确？ | 描述错误、提出修复或变通方法 |
| **上下文窗口** | 由于上下文过长，Claude 是否忘记了指令？ | 更短、更突出的护栏 |

简要讨论每个视角，然后与用户共同确定最可能的根本原因。可以有多个共同导致的原因。

## 步骤 3：诊断与记录

回顾的目标是 **诊断**，而不是贡献。根据根本原因，编写团队可以采取的明确诊断报告 — 不要直接跳到提出或编写修复方案。

对于每个摩擦点，生成：

- **诊断** — 什么出错了以及为什么令人沮丧，用平实的语言说明
- **影响因素** — 技能结构、差距、误导性文档、API 便利性、缺失的 API、API 错误、上下文窗口（来自步骤 2）
- **考虑因素** — 权衡、开放性问题或修复方案合理需要满足的条件。在此处记录可能的改进方向，但将其框定为考虑因素而不是承诺的解决方案。

默认的下一步是将诊断 **记录为问题或讨论**，以便团队可以权衡 — 而不是立即进行贡献。具体的代码更改（技能编辑、API 设计）在问题/讨论存在并且用户明确选择进一步行动之后才会出现。

展示诊断并询问：**"要我将这记录为问题或讨论吗？"**

## 步骤 4：文件或跟进

### 默认：记录问题 / 讨论

为 marimo 团队清晰地编写以供分派：

- **问题**：发生了什么以及为什么令人痛苦
- **当前行为**：技能或 `_code_mode` 当前的行为
- **考虑因素**：权衡和开放性问题（不是承诺的解决方案）
- **示例**：会话中的最小代码片段或引用，如果有助于理解

将实际记录工作留给用户 — 不要自动记录。这是首选结果：为团队揭示摩擦点，而不是从回顾中直接发布修复。

### 只有在用户明确希望进一步时

技能编辑或 API 更改应跟随问题/讨论，而不是取代它。如果 — 并且只有在 — 用户明确要求现在编写更改：

1. 阅读目标文件在 `github://marimo-team/marimo-pair`
2. 向用户展示建议的 diff
3. 只有在明确同意后才能应用
4. 应用后，验证 SKILL.md 保持在 500 行以内（参考/ 文件没有限制）

### 结束

在完成选定摩擦点的循环后，询问用户是否要重新审视步骤 1 中剩余的项目，或者回顾是否完成。

```python
import marimo._code_mode as cm

async with cm.get_context() as ctx:
    # 列出所有公共方法/属性
    print([x for x in dir(ctx) if not x.startswith('_')])
    help(ctx)
```
