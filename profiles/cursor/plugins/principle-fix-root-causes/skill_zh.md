# 解决根本原因

在调试时，不要只解决表面现象。将每个问题追溯到其根本原因，并在那里进行修复。

**原因：** 表面现象的修复会累积。每个临时解决方案都会使系统更难理解，而真正的错误仍然存在。根本原因的修复在初期可能更慢，但会减少总体的调试时间。

**模式：**
- 首先重现问题
- 不断问“为什么”，直到找到根本原因
- 不要添加保护措施（向 silence a crash 添加 nil 检查是一种表面现象的修复）
- 如果一个临时解决方案需要一段长注释来解释，那么代码就是有问题的（修复代码，而不是注释）
- 查找模式，而不仅仅是实例（使用 grep 查找相同的模式，修复所有实例）
- 当卡住时，进行代码分析。不要猜测（添加日志，读取实际错误）

**重启问题：怀疑状态而非代码**

当出现“重启后失败”的情况时，首先怀疑过时的持久状态：配置文件、缓存、锁文件、序列化状态。如果清除状态文件可以恢复行为，则将状态验证作为修复的优先事项。
