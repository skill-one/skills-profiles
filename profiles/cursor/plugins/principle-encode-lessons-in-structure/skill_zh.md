# 在结构中编码经验教训

将重复的修复措施编码到机制（工具、代码、元数据、自动化）中，而不是文本说明。每个错误、人工纠正和意外结果都是一个学习信号。捕捉它，路由它，并关闭反馈回路。

**原因：** 文本说明很容易被忽略。它们需要读者注意、记忆和遵守。结构化机制（代码风格检查规则、元数据标记、运行时检查、自动化脚本）无需合作即可强制执行规则。

**模式：**
当你发现自己第二次写下相同的说明时：
1. 询问：这可以是代码风格检查规则、元数据标记、运行时检查或脚本吗？
2. 如果可以，将其编码。删除说明
3. 如果不可以（需要判断），使说明更加突出，并添加失败模式的示例

**选择最强的机制。** 当多个机制都适用时，选择该情境允许的最强机制（无法编译的不代表状态，然后是失败的代码风格检查或禁止的API，然后是标准辅助函数，然后是运行时检查），因为代理会复制周围代码已经做的事情，而较弱的防护措施将成为下一个模板。

**推论：** 如果修复措施是结构化的，则只使用结构化修复措施。说明是症状。

**反馈回路：**
- **捕捉每个纠正。** 当人工干预或测试失败时，判断这是偶然事件还是模式。
- **路由到正确的层级。** 偶然事件 -> 大脑笔记。重复修复 -> 技能或代码风格检查规则。系统性问题 -> 原则。
- **关闭反馈回路。** 不要只是记录。立即应用或创建具体的待办事项。

**反模式：**
- 记录而不记录（“我会记住的”不会持久化）
- 记录而不路由（关于应该存在的代码风格检查规则的大脑笔记是浪费，除非代码风格检查规则得到实现）
- 修复而不泛化（修复一个实例，而保留重复的模式）
