# 展示你的工作

保持一个标准的日志。

## 格式

一个单独的 TSV 文件，每行一个决策。单元格保持单行。证据是一个指针，而不是散文。

复制 `references/decision-log-template.tsv`（标题行）来开始一个干净的日志。列：

- **ts.** ISO8601 时间戳。
- **phase.** 阶段或工作流。
- **decision.** 选择或做了什么，一行。
- **why.** 简单的文字原因。如果一个原则驱动了它，就直白地说，而不是作为术语标签。
- **evidence.** 一个证明它的链接或路径：提交 SHA、PR 编号、`file:line`，或一个工件、跟踪或截图路径。永远不是一段话。
- **result.** 结果或谓词状态：`tests green`、`reverted`、`pixel-diff 0`、`INCONCLUSIVE`、`open`。

一个例子，用简单直白的语言，以便审阅者一眼就能读懂。

```
ts	phase	decision	why	evidence	result
2026-05-24T09:02:00Z	frame	先统计了工作，大约 100 个组件和 75 小时	在开始一个漫长的运行之前想知道工作量	commit 3a9f1c2	在开始之前发现了 5 件需要整理的事情
2026-05-24T09:40:00Z	harness	在改变任何东西之前对旧版本拍了快照	这样我们就可以比较旧版本和新版本，并捕获任何视觉变化	scripts/snapshot.sh, baseline/	保存了 120 张参考截图
2026-05-24T11:15:00Z	widget	将小部件样式迁移过来，但没有改变它的外观	保持更改小，结果相同	commit 7c21e0a, pixel-diff 0	外观相同，测试通过
2026-05-24T12:30:00Z	widget	因为一个助手的截图是空的而扔掉了他的工作	检查了实际的文件而不是相信它的摘要	worktree reset	reverted，收紧了下一次的说明
```

## 记录一行

以你告诉队友你做了什么的方式来写每个条目。简单直白的文字，具体的行动，没有 AI 术语或抽象的行话（**unslop** 技能也适用于日志文本）。

使用辅助工具 `scripts/log.sh <logfile> <phase> <decision> <why> <evidence> <result>`。它会打上 `ts`，在第一次使用时写入标题，删除多余的制表符/换行符，并将以 `=`, `+`, `-`, 或 `@` 开头的任何单元格前缀一个单引号。一个简单的 `printf` 追加一行也可以，但要小心相同的字节，如果单元格来自生成或用户提供的文本。

记录决策点和检查点，而不是每个行动：一个分支的选择，一个单元完成及其验证结果，一个转向或回滚及其触发因素，一个障碍出现，一个门控修复。对于循环运行，每行一个迭代。忽略琐碎的和显而易见的内容。

一个运行是一个代理对话，包括其后续回合以及任何对其的总结。一个拾取、一个替换代理或一个新的聊天开始一个新的运行。当一个运行添加到一个已经包含行的日志时，它的第一行 `phase` 是 `start`，另一个运行的第一行在 `start` 行之后也是 `start`。因此，一个回到后来回合的日志的运行首先读取日志的最后一行，以查看自上次运行以来是否有人写入。一个 `start` 行命名了它之前这个运行没有写入的行的 `ts` 范围，并且它的证据命名了这次运行，例如其代理 ID。对于 `start`，用于其他任何目的。

## 存放位置

默认情况下，日志是一个工作产物，不提交。将其保存在工作目录中的 `decisions.tsv`，或者在同时进行多个努力时保存在 `.audit/<task-slug>.tsv`，并且不要提交到 git。

只有当工作足够雄心勃勃以至于审阅者需要追踪来信任结果时才提交它。

## 规则

- 只追加不删除。一个错误的调用会得到一个新的行来覆盖它。永远不要编辑或删除历史记录。
- 优先使用由提交的脚本产生的证据，而不是手工制作的单个实例（**encode-lessons-in-structure** 原则技能）。

## 对照文本审计日志

在运行结束时，在交还之前，检查日志是否说了实话。在活动工作区的 `agent-transcripts/` 目录下读取这次运行的文本（系统提示命名了路径）。不要跨 `~/.cursor/projects/*` 进行 glob 匹配。那会读取不相关的私人聊天。按这次运行的行与实际发生的事情进行匹配。每个这样的行段从这次运行的 `start` 行开始，或者如果这次运行创建了日志，从第一行开始，并在下一个 `start` 行结束：

- 检查每一行是否映射到一个真实的决策或行动。
- 检查每一行的证据是否解析并显示了该行所声称的内容。
- 一个塑造了工作但未记录的分支、转向或放弃的方法是一个空白。添加它。

修正日志，而不是故事。审计永远不会编辑或删除一行，即使是一个虚构的行。当一行既不记录一个真实的决策也不记录一个真实的行动，或者其声明或证据是错误的时，添加一行来覆盖它，并包含实际发生的事情和解析的指针。这次审计不会检查这次运行行段之外的行。如果这次运行自己的工作表明其中之一是错误的，像任何错误的调用一样覆盖它。

## 跨模型审查轨迹

在交还之前，在一个与执行工作不同的模型系列上生成一个子代理。自我审查不是替代品。子代理读取审计轨迹和运行的文本，然后标记用户应该注意的内容。不是重做工作，而是扫描哪些地方次优或有风险。

- 使用弱证据或没有证据记录的决策。
- 在文本中跳过或声称没有证据的验证步骤。
- 在回顾中看起来有风险的选择（过早的、范围蔓延的、掩盖症状）。
- 用户在随意浏览时可能会忽略的空白。

每个产生轨迹的运行的回复都以“注意”部分结束。以审阅者的模型为单独的一行（`reviewed by <model>`），然后列出每个指向特定行或时刻的标记。“No flags”是一个有效的值。模型名称不是。

## 审查轨迹

从上到下阅读，跟随证据指针，抽查。GitHub 将提交的 TSV 渲染为表格。`column -s$'\t' -t decisions.tsv` 在终端中渲染它。

## 组合这个技能

其他技能将它们的审计轨迹路由到这里，而不是发明一个。通过名称引用它，并让它拥有格式。不要重述列。
