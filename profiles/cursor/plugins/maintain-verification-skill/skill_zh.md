# 维护验证技能

应用一变，特征图就会腐化。这个技能是 `/create-verification-skill`（或任何具有特征图的项目本地验证技能）生成的技能的维护循环。严格性的单位是特征，而不是每一句：覆盖所有特征文件来源并实时执行每个特征，不要终端化每个要点。

## 结果

选择一个，并说明：

- **干净** — 每个特征都有来源和实时覆盖；没有值得发布的内容。无分支，无PR。
- **已更改** — 一个PR发布已验证的文档、驱动程序或地图修正。
- **阻塞** — 覆盖无法完成或一个已验证的修复无法安全发布。准确说明是什么阻塞了它。

## 编辑范围

仅编辑验证技能自己的目录（其 SKILL.md、features/ 和它拥有的任何驱动程序脚本）。运行期间切勿编辑产品代码：地图描述的行为而应用不再执行的是文档漂移（修复地图）或产品回归（报告它，不要在文档中掩盖它）。

## 通过

0. **定位目标。** 找到要维护的验证技能：项目本地的技能，其主体具有启动/驱动部分和特征图（通常是 `.cursor/skills/verify-*/`）。多个候选者 → 询问哪个；无 → 停止，并指向 `/create-verification-skill` 而不是发明目标。

1. **索引卫生。** 阅读特征图README并全局其兄弟文件。修复缺失、多余、重复或死掉的条目。轻量级；无生成清单。

2. **来源波。** 每个特征文件一个只读子代理，并发启动。每个解释“这个面向用户的功能如何工作？”从来源，用引用标记可能的文档漂移，并返回一个简洁的实时验证配方。子代理永不驱动应用，永不编辑文件。返回形状：特征摘要 / 来源入口点 / 可能的漂移或无 / 一个配方。

3. **协调。** 每个特征文件都有一个返回的摘要。将重叠的配方合并为尽可能少的应用状态。抽查引用的漂移；不要重新证明干净的声明。清理最近的变更，查找地图中缺失的用户界面表面 — 在调用缺失之前，需要具体的来源路径。

4. **实时通过。** 即使来源看起来干净也需要。协调者拥有所有驱动；遵循验证技能自己的启动模型 — 一个长生命实例串行驱动服务器和UI，或为短生命CLI每个驱动一个新鲜隔离会话（技能的 Launch 部分决定，不是这个）。至少执行每个特征一次，并在整个通过中保持三个不变量，无论失败： (1) 永远不驱动自上次做奇怪事情以来未进行健康检查的实例 — 在第一次驱动前医生，在每次新的会话中医生（会话是单位），在每次失败的驱动后再次医生，如果医生看不到失败（一个在健康进程上的卡住UI状态），重置为已知状态或重新启动，而不是希望； (2) 迄今捕获的证据在每次清理中都存活，在命名位置检查，而不是假设； (3) 驱动开始时任何东西都不会比该驱动的有用性更持久 — 无论会话卡住、退出还是共享（对于共享实例，清理残留，而不是实例）。由技能漂移引起的医生失败是漂移：在编辑范围内修复它并重试一次 — 重新启动修复使其失效的任何东西，不再更多 — 在调用通过 `阻塞` 之前。无法访问的特征只有在具体的先决条件（认证、权限、操作系统、外部状态）和尝试的路线下才是 `verified-unreachable`；如果地图省略了该先决条件，那就是漂移。来自分诊的任何驱动程序修复在发布前都会实时重驱动。最终拆除发生在运行最后一次驱动之后 — 包括重新证明 — 所以没有任何东西比运行更持久（证据按技能保留）。

5. **分诊。** 错误或缺失的用户视角描述 → 文档漂移，修复它。工作行为驱动程序无法驱动 → 驱动程序差距，修复它；驱动程序修复遵循与生成相同的帮助规则（脚本可执行，在技能主体中记录调用）。应用行为实际上已损坏 → 产品差距；为用户记录它，不要把它放在这个PR中。

6. **发布或停止。** 对于已更改：一个PR发布已验证的修正，首先重新阅读每个更改文件。对于干净或阻塞：无PR，诚实地报告结果和覆盖范围。

在临时位置保留简洁的运行笔记（覆盖的特征、无法访问的先决条件、确认的漂移、结果）；不要提交它们。
