# 建模领域

将真实领域编码到数据结构中，而不是将其分散在条件语句中。

**原因：** 分散的布尔值、重复的形状假设以及跨文件的分支是偶然的复杂性。与领域匹配的结构使得无效状态无法表示，并删除了分支。在编写时选择它很便宜。稍后恢复它看起来像重构，并会被推迟。

**寻求以下结构：**

- 使用状态机代替分散的布尔值、阶段或生命周期检查。
- 使用带类型的对象/模型代替松散的参数或重复的形状假设。
- 使用映射、注册表、查找表或区分联合代替跨文件的分支。
- 使用Reducer或命令/事件模型代替临时的状态突变。
- 围绕一个领域知识主体的模块，而不是加载、验证、转换和保存的序列。执行顺序不是所有权。
- 小的模块边界，汇集重复的行为、所有权或不变量。
- 当数据访问模式需要时，使用队列、缓存、索引、图/树或规范化集合。
- 任何其他适合的结构。当都不适合时，弄清楚代码必须永远不允许什么，数据如何被读取，然后找到能精确编码这些的结构。

不要强迫抽象。如果当前的形状已经清晰、局部且不太可能增长，则优先考虑无聊的代码。对添加了间接性而没有删除分支、重复规则、无效状态或生命周期风险的抽象持怀疑态度。

你跳过了这一步的迹象是：一个新功能使现有的if/else链增加了一个新的分支，或者必须与第一个保持同步的第二个布尔值。时间分解是另一个迹象。以阶段命名的模块在步骤中重复相同的领域规则。
