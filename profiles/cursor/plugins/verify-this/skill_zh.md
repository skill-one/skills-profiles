# 验证此

验证不是回顾。它用可重复的证据来证明或反驳一个具体的声明。

## 何时使用

- 用户询问“验证这个”、“证明它有效”、“这个修复了吗”或“给我展示证据”。
- 软件缺陷修复需要前后可复现的测试。
- UI、CLI、API、性能或内存的声明需要测量。
- 测试通过，但用户可见的行为仍需确认。

不要用于模糊的声明，如“代码更干净了”。先要求一个可测量的声明。

## 工作流程

1. 将声明以可证伪的形式重述：条件、指标和阈值。
2. 选择能证伪它的最小本地表面。
3. 从旧状态捕获基线：合并基础、父提交、失败分支或当前有问题的可复现步骤。
4. 用相同的命令、数据、预热和环境从改变后的状态捕获处理结果。
5. 比较原始工件：数字、截图、终端记录、HTTP 响应、性能分析、堆快照或测试输出。
6. 返回一个明确的结论：`VERIFIED`、`NOT VERIFIED` 或 `INCONCLUSIVE`。

## 本地表面

- 代码行为：聚焦的单元/集成测试或最小的可复现脚本。
- CLI/TUI 行为：`control-cli`、终端记录或演示录制。
- UI 行为：`control-ui`、截图、无障碍快照或浏览器跟踪。
- API 行为：本地 HTTP/RPC 请求和响应差异。
- 性能：同机基线/处理时间或 CPU 性能分析。
- 内存：怀疑操作前后的堆快照。

## 工件布局

在安全写入工件时：

```text
/tmp/verify-this/<声明缩写>/
├── claim.md
├── timeline.md
├── baseline/
├── treatment/
├── diff/
└── verdict.md
```

如果工件可能包含敏感代码、提示、截图、HTTP 正文或堆数据，除非用户同意磁盘存储，否则只保留必要的内联证据。

## 结论规则

- `VERIFIED`：基线和处理结果在预期的方向上差异，达到声明的阈值，且没有明显的混杂因素。
- `NOT VERIFIED`：行为未改变、朝错误方向变化或未达到阈值。
- `INCONCLUSIVE`：没有有效的基线、信号噪声大、测量失败或环境差异使比较无效。

## 输出

使用此格式：

```text
VERIFIED | NOT VERIFIED | INCONCLUSIVE
声明：<可证伪的声明>

证据：
<指标/工件>：基线=<...>，处理=<...>，差异=<...>，阈值=<...>

理由：
<一个紧密的段落，说明证据和任何混杂因素>
```

不要淡化负面结果。清晰的 `NOT VERIFIED` 很有用。
