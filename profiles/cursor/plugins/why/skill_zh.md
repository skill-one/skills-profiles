# 为什么

调查代码背后的动机和意图。

`how` 技能的伴侣。`how` 回答代码做什么以及它是如何工作的。`why` 回答是什么力量导致了它的形状。

下面的每个 spawn 都命名了 `pstack-models.mdc` 规则中的一条角色行和默认值。将 `model` 设置为该行值，如果规则或该行缺失，则设置为默认值。当值为 `auto` 或 `inherit-parent` 时，请保持 `model` 未设置。如果任务工具拒绝 slug，请使用默认值并说明。如果它拒绝默认值，请使用来自其错误消息的同一系列的最近有效 slug。

## 操作姿态

以 **谨慎、小心和精确的调查员** 的姿态进行操作。对你知道的和你在推断的内容要诚实。阅读 `references/epistemics.md` 了解完整的信心框架和措辞指南。合成器必须遵循它。

## 第 1 步。理解目标和问题

解析用户在问什么。**目标** 通常是代码片段、模式、功能或命名的设计决策。**问题** 通常是设计理由、权衡、动机边缘案例、外部约束、死代码或广泛的扫历史。

如果目标模糊（例如，“为什么我们这样做？”但没有明确的指代对象），根据对话上下文（打开的文件、最近的编辑、光标位置、刚刚讨论的内容）做出你的最佳猜测。简要说明你的解释，以便用户在方向错误时可以重新引导，然后继续进行。

## 第 2 步。建立代码锚点

在生成调查员之前，将调查锚定在具体的代码上。你需要：

- 相关的文件路径和行范围
- 关键符号（函数名、类名、常量）
- 初始提交列表。最近几次触摸目标的提交。
- 合并提交中的 PR 编号（主题行中的模式 `(#1234)`）

内联构建这些内容。

```bash
# 查看最后触摸的提交的目标行
git blame -L <start>,<end> <file>

# 完整文件历史记录，包括补丁，通过重命名
git log --follow -p -- <file>

# 最后 N 次触摸文件的提交，PR 编号可见
git log --oneline -20 -- <file>

# 从提交消息中提取 PR 编号
git log -1 --format=%B <commit>
```

通过 `gh` 拉取 PR 正文和讨论，用于任何实质性的提交：

```bash
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews
```

捕获这些作为种子上下文（文件路径、符号、提交、PR 编号、链接的工单 ID）。将其传递给调查员。

## 第 3 步。并行生成调查员（默认姿态）

**默认使用完整的并行调查。**

### 发现

在生成调查员之前，列出 Cursor 环境中可用的 MCP。如果存在 `available-tools` 映射，请使用它。否则，检查 Cursor 暴露的 `mcps/` 目录中的启用 MCP 服务器。

将每个可用的 MCP 映射到一个证据类别：

1. 源代码历史记录
2. 问题/工单跟踪器
3. 长文档
4. 实时团队聊天
5. 基础设施可观察性
6. 错误/异常跟踪
7. 产品分析仓库

源代码总是可以通过 git 和 `gh` 访问。对于其他六个，使用 MCP 名称、服务器指令、工具名称和资源描述进行分类。如果一个 MCP 可以匹配多个类别，选择与其主要证据匹配的那个。将模糊案例记录在覆盖映射中。

目标是完整的 **覆盖映射**，而不是最小的映射。记录空值，不要跳过搜索。

在单个消息中启动所有匹配的调查员，以便它们并行运行。不要要求一个代理覆盖多个 MCP。

子代理配置（每个）：
- `subagent_type`: `generalPurpose`
- `model`: `why investigators` 行的值，默认 `grok-4.7-xhigh-fast`
- `readonly`: `false`（代理模式）。**不要使用 readonly/Ask 模式。** 它会移除 MCP 访问，这将禁用基于 MCP 的调查员。调查员仍然不应该写任何东西。

每个调查员获得：
1. 来自 `references/investigator-prompt.md` 的基础提示
2. 选择的 MCP 的类别剧本 `references/sources/<source>.md`，根据 `references/source-playbook.md` 中的示例进行适配
3. 跨越的 `references/sources/incident-postmortem.md` **如果目标代码看起来有防御性**（空检查、重试逻辑、超时处理、速率限制、功能标志、出口守卫、OOM 处理器）
4. 第 2 步的代码锚点（文件路径、符号、提交哈希、PR 编号、工单 ID）
5. 用户的原始问题

### 调查员名单。每个证据类别一个

为每个具有匹配 MCP 的类别生成一个调查员。每个调查员只拥有一个工具或 MCP。

每个条目命名类别和它独特揭示的“为什么”类型。用它来知道可以期待什么，如何命名空值（当类别返回空时），以及在罕见且可证明无关的情况下，如何证明跳过。

1. **源代码调查员**。Git 历史记录、`gh` 用于 PR、代码注释、测试。始终生成。唯一的保证来源。擅长揭示 *实施时捕获的审查理由*。

2. **问题/工单跟踪器调查员**（例如 Linear、Jira、GitHub Issues、Plane、Shortcut MCP）。擅长揭示 *产品或业务强制力量*。在为什么是工程外部时最强。

3. **长文档调查员**（例如 Notion、Confluence、Google Docs、Coda MCP）。擅长揭示 *长格式设计理由*。为什么在成为代码之前被写出来。

4. **实时团队聊天调查员**（例如 Slack、Discord、Microsoft Teams、Mattermost MCP）。擅长揭示 *从未达到文档的实时讨论*。当源代码、工单和文档纸迹薄弱时尤其重要。

5. **基础设施可观察性调查员**（例如 Datadog、New Relic、Honeycomb、Grafana、Splunk MCP）。基础设施/运行时视图。擅长揭示 *促使代码的基础设施和运行时现实*。在目标对基础设施信号做出反应（超时、重试、速率限制、断路器）时最强。

6. **错误/异常跟踪调查员**（例如 Sentry、Rollbar、Bugsnag、Airbrake MCP）。擅长揭示 *促使防御性或纠正代码的特定异常和错误轨迹*。在 catch 块、空检查、类型检查、重试和其他防御时最强。

7. **产品分析仓库调查员**（例如 Databricks、Snowflake、BigQuery、ClickHouse、dbt、Redshift MCP）。产品和数据视图。擅长揭示 *塑造代码的产品和数据现实*。在功能标志代码、实验驱动型发布、数据迁移和“这个数字从哪里来”的问题上最强。

### 何时跳过调查员

只有在有 **明确的、书面的理由** 并放在最终的“参考来源”部分时才跳过。两个有效理由：

- **在本环境中该类别没有可用的 MCP**。将其标记为差距，而不是选择。示例： “实时团队聊天跳过。没有匹配的 MCP，因此对话记录不可搜索。”

- **来源可证明无关**，而不仅仅是“可能无关”。高门槛。示例： “错误/异常跟踪跳过。目标是构建时脚本，没有运行时代码路径。”

如果你的范围评估表明这是一个单提交的简单目标，其中 PR 描述已经包含完整答案，你可以在确认所有七个可用的类别搜索将是冗余的之后，直接回答。明确说明。这应该是罕见的。

## 第 4 步。综合

生成一个综合器子代理：

- `subagent_type`: `generalPurpose`
- `model`: `why synthesizer` 行的值，默认 `claude-opus-5-5-max`
- `readonly`: `false`（代理模式）。综合器的质量检查会验证引用，这可能需要 MCP 访问。只读/Ask 模式会移除 MCP 并破坏这一点。

综合器获得：
1. 调查员发现，包括任何空结果和任何有理由跳过的类别
2. 第 2 步的代码锚点（文件路径、符号、提交哈希、PR 编号、工单 ID）
3. 用户的原始问题
4. 来自 `references/epistemics.md` 的信心框架
5. 来自 `references/synthesizer-prompt.md` 的综合器提示模板

## 第 5 步。展示

获取综合器的输出并将其展示给用户。你可以轻微编辑以提高清晰度或添加来自对话的上下文，但 **不要重写信心语言**。

## 输出格式

输出结构是 `references/synthesizer-prompt.md` 中的结构：问题、相关的代码、我们发现了什么、我们可以合理推断什么、竞争假设、我们不知道什么、参考来源、信心总结。根据需要进行调整，但保持信心分离完整，并保持参考来源作为每条调查员的一行，包括返回空或跳过的调查员，并说明原因。

在参考来源块之后，如果用户的“为什么”问题是实际更改此代码的前奏，将谱系发现转换为适合规划更改的保留/更改/避免/风险约束集。

## 常见失败模式要避免

- **近期偏差**。假设最近的提交是权威的。当前的形状通常是许多早期决策的累积。追溯回去。
