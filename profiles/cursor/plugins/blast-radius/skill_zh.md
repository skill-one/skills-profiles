# 爆炸半径

在代码提交前，找出某个改动会在其他地方引发的问题。用于评估“X的爆炸半径”、“这个改动可能破坏什么”或审查你还不信任的微小代码差异。

`how`和`why`的配套工具。`how`告诉你代码做了什么。`why`告诉你代码为什么这样设计。爆炸半径告诉你代码会在哪里引发问题。

列出调用者不是任务。代理可以在一秒钟内通过grep找到它们。任务是grep无法显示的破坏性grep。

## 不要相信你自己的分析报告

一个听起来正确的爆炸半径分析报告毫无价值。无论真假，它都显得很有说服力。所以不要交回分析报告。找出整个报告依赖的一两个事实，并通过运行代码来证明它们。

### 你有多确定

对于每个依赖的事实，将其尽可能低成本地下移到这个列表中，并说明它停止的位置。

1. 你说如此。单独看毫无价值。
2. 你指向了行号。真实的`file:line`，或库自己的源代码。
3. 你展示了坏情况不会发生。你一步步走完了失败过程，它并没有达到。
4. 你运行了它。一个脚本或测试调用真实代码，并在你出错时大声失败。
5. 你在运行的应用中复现了它。

第4步通常是一个小的脚本，它导入与应用程序一起发布的相同库，并调用你担心的确切函数。

## 步骤

1. 阅读改动。差异、它添加、修改和删除的符号，以及它现在不同的行为，包括差异没有说明的部分。使用`why`步骤2来获取PR和提交。
2. 找到它安全的原因。看起来有风险的改动大多数是因为一个事实而安全，比如“这个调用只删除已经死亡的缓存条目，不做其他事情”。找到这个事实。如果它成立，大多数有风险的情况会立即消除。在这里花时间，而不是在一个长长的可能列表上。
3. 查看grep停止的地方。阅读你调用的库的源代码，并检查其固定版本和任何本地补丁。弄清楚什么时候运行：微任务、卸载和拆除、Solid与React。跟随符号搜索遗漏的东西：API返回的JSON、数据库列、线路格式、另一种语言读取相同的字节、功能标志、下游三个跳点的代码。
4. 对每个风险保持诚实。给它一个真实发生的可能性和真实发生的成本。保留你确认的风险。将你检查并清除的项单独列出。与`why`相同的规则。引用真实的`file:line`，一个什么都没找到的搜索仍然是一个答案，并且永远不要编造调用者或API。
5. 证明那个事实。写一个脚本或测试来运行真实代码，运行它，并粘贴发生了什么。
6. 对于重大或广泛的改动，将其作为`arena`运行。问几个模型同一个问题，并合并答案。不同的模型会捕捉到不同的真实错误。

## 需要交回的内容

- **它做了什么。** 改动了什么，包括不明显的部分。
- **它安全的原因。** 陈述它，说明你达到了哪个步骤，并展示证据。如果你无法证明它，写未证明。
- **风险。** 每个风险命名如何破坏、`file:line`、可能性和严重程度，以及如何检查。粘贴重要项的证据。
- **已清除。** 你检查了什么以及为什么它没问题。
- **合并前。** 最便宜的测试或复现，可以捕捉到真实错误，包括你写的脚本。

通过`unslop`写它，引用真实代码，并在它公开之前删除任何私人信息。

**回复：** 上述分析报告，其中安全事实要么被证明，要么被标记为未证明。
