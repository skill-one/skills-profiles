# 制作杠杆

当工作并非微不足道时，制作一个工具来处理它，而不是手工完成。

**原因：** 两种收益。吞吐量：一个代码修改工具、生成器或脚本每次都以相同的方式完成工作，并且可以免费重新运行。信心：审查者可以阅读并重新运行该工具来检查工作。手工完成的更改只能通过重新执行来重新验证。一个确定性脚本将“相信我”转变为“运行这个”。

**模式：** 默认情况下制作杠杆。只有在任务微不足道时，即你一眼就能看到的一两个明显修改时，才跳过它。

- 首先手工完成第一个单元来学习配方，然后制作工具。通过在第一个单元上重新运行它并与你手工完成的版本进行差异比较来证明它。确保杠杆可以安全地重新运行。
- 使用代码修改工具或脚本进行编辑，使用生成器处理重复文件，使用转储到 SQLite 的查询进行数据分析，使用可重新运行的检查进行验证。
- 确定性杠杆优于发散。如果工具可以一次处理每个单元，请自己运行它。不要将委托发散到手工执行脚本可以完成的工作。
- 当你将工作分发到子代理时，将杠杆作为一个技能供它们所有成员阅读：配方、验证合同以及不可触碰的边界在一个工件中。将其保留在委托者的写入范围之外，这样它们就无法悄悄地编辑合同。
- 应用这个原则会产生一个文件。如果你引用了它，并且在差异中没有代码修改工具、脚本、生成器或委托技能，那么你没有应用它。
- 当工作超出会话范围时，提交杠杆。

**平衡：** 标准是微不足道，而不是重复。即使是一次性的，只要杠杆是使工作可检查的，仍然值得制作杠杆。根据 [懒惰协议](../principle-laziness-protocol/SKILL.md)，构建完成或证明工作的最小脚本，而不是框架。

与 [将经验教训编码在结构中](../principle-encode-lessons-in-structure/SKILL.md) 不同，后者将重复指令作为一个持久的护栏。这是针对你面前工作的吞吐量和可审查性。有关验证本身的脚本编写，请参阅 [证明它有效](../principle-prove-it-works/SKILL.md)。
