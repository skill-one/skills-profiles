# 创建验证技能

每个严肃的项目都需要一种脚本化的方式来驱动真实的应用并证明其行为：启动它，像用户一样使用其功能，并捕获证据。此技能作为项目本地技能（`.cursor/skills/verify-<app>/`）生成，针对特定的代码库。您编写的是为下一个代理生成的输出，而不是为人类编写：它将在任务中途被一个从未见过该应用的代理冷启动读取。

## 1. 访谈代码库，而非用户

从代码库中回答这些问题，并且只询问您无法观察的内容：

- **表面：** 用户实际触摸什么？Web UI、CLI/TUI、桌面应用、API、移动应用、库？代码库可以有多个；选择主要的一个并记录其余的。
- **运行：** 应用如何本地启动？优先选择代码库自己的开发命令（打包脚本、Makefile、README 快速启动）。记录端口、环境变量、种子数据、认证信息。
- **驱动：** 代理如何以编程方式与其交互？首先使用现有的 harness — Playwright/Cypress 测试、expect 脚本、PTY 辅助程序、可 curl 的端点、调试端口。只有然后选择通用配方：浏览器/CDP 用于 Web 和 Electron，tmux/PTY harness 用于 CLI/TUI，纯 HTTP 用于服务。
- **观察：** 可以捕获哪些证据？屏幕截图、终端会话记录、响应体、日志、退出代码、数据库状态。
- **隔离：** 两个实例能否并排运行（端口、数据目录、配置文件）？如果不能，请在生成的技能中说明：拒绝驱动共享实例可以避免破坏用户的会话。

如果签出无法按原样构建或启动，请先修复（或精确报告）再生成；针对损坏的基础编写的技能会教错误步骤。当无关的缺失资源阻止启动（API 从不服务的静态目录、示例配置文件），生成的技能可能会创建它，明确标记为验证脚手架，并在清理时删除它。

## 2. 生成技能

编写 `.cursor/skills/verify-<app>/SKILL.md`，使用 YAML 前置文本（`name: verify-<app>` 和一个命名应用的 `description`，以及何时使用它 — 没有前置文本，技能将不会注册）以及以下部分，每个部分都基于访谈的实际发现（不留占位符）：

- **启动：** 启动应用进行验证的确切命令，以及如何判断它已准备好（一条日志行、一个响应端口的提示符）。包括拆除步骤。对于短命的 CLI 或 TUI 没有服务器需要保持活动：启动意味着构建二进制文件（或安装依赖）一次，然后每个驱动都在其自己的隔离 PTY 或 tmux 会话中启动。
- **诊断：** 一个只读检查，回答“这个实例是否值得驱动？” — 进程是否正常、版本/构建是否正确、端口是否属于我们、认证是否有效。代理在出现任何问题时首先运行此检查。
- **驱动：** harness 配方，使用此代码库的真实选择器/命令，而不是示例。优先选择稳定的句柄（ARIA 标签、数据属性、提示字符串、路由路径）而不是坐标和选项卡顺序。
- **证据：** 为证明要捕获什么以及放在哪里。声明证明标准：执行真实用户路径，而不是内部设置器或仅测试端点；捕获操作和结果状态，而不仅仅是最终屏幕；验证副作用（写入文件、插入行、发送消息）与可见内容一起；仅在生产的边界已经隔离外部系统时使用模拟。当安全路径是干跑或测试模式时，通过观察（文件、网络、git 引用）而不是相信其名称来验证它实际跳过了什么：一些干跑仍然会触及网络或打开浏览器。
- **清理：** 如何拆除运行创建的实例。永远不要通过进程名称杀死；杀死您启动的。清理会删除实例和临时状态，永远不会删除证据：证明工件在拆除后仍然存在于技能命名的位置。
- **辅助程序：** 技能附带的所有脚本都是可执行的，其调用在技能正文中显示。读者必须反向工程的辅助程序不是辅助程序。

## 3. 种子功能映射

创建 `.cursor/skills/verify-<app>/features/README.md` 以及每个用户可见功能一个文件（从路由、命令、菜单或文档开始，目标为前 3-5 个）。遵循 [`references/feature-map-example/`](references/feature-map-example/) 中的形状，带有 README 索引和一个功能文件。每个文件从用户的角度回答：功能是什么、如何访问它、如何使用 harness 驱动它，以及什么可观察的最终状态证明它工作。四个 H2 是 `子功能`、`如何访问它（用户视角）`、`使用 <harness> 驱动它` 和 `注意事项`。地图是代码库维护的验证源；驱动一个方便的入口点的证明，当地图列出其他功能时是不完整的。

## 4. 在移交之前验证生成的技能

运行其自己的指令端到端一次：启动、诊断、驱动一个映射的功能（一个就足够；地图存在以便后续运行可以覆盖其余的）、捕获证据、清理。清理后，确认证据仍然存在于命名位置 — 消耗证明的清理会失败此步骤。修复失败的内容，并在每次失败迭代后运行生成的清理，这样损坏的尝试不会留下进程和端口。从未执行过的生成技能是草案，而不是交付物。

## 5. 提供维护循环

将用户指向 `/maintain-verification-skill` 以保持地图在应用变化时诚实。如果他们询问，才建议一个节奏。
