# 无评论

生成 Comment Sicko 任务。根据已接受的发现采取行动。

参考 Comment Sicko 提供的新视角。

## 范围

使用调用者的文件或差异。否则使用当前差异与基础分支（默认为 `main`）进行比较，包括工作树。

## 步骤

1. 使用 `subagent_type: "Comment Sicko"` 生成 `Task`，传入范围。不要重述其规则。
2. 检查其报告和差异。拒绝应用代码编辑、范围逃逸、受异常保护的删除、错误陈述的 `MUST KILL` 原因，以及将保留的故意代码视为有罪标记。我们代码的意外情况下的标记应保持可操作。不要恢复这些评论。保留的标记只有在证明其关于我们无法更改的内容时才有效。审计遗漏的范围性 lint 和 TypeScript 抑制。正确性或安全性抑制应保持为可操作的 `MUST KILL`。仅凭精确的例外和范围证明恢复删除。在接受薄的 `IMPORTANT` 或 `do not remove` 删除或保留之前，对其符号运行 `/how` 或 `/why`。如果删除是模糊的，不要恢复。如果保留被反驳或仍然模糊，删除它。撤销并重新运行一个被拒绝的报告，并命名失败。拒绝第二个，将其报告为打开状态，并失败 `/no-comments`。
3. 通过删除死路径、删除参数或使用真实 API 直接修复简单的已接受标记。如果任何修复需要形状，对已接受的集合和周围代码运行一次 `/architect`。停留在草图。架构形状。第 4 步实现。
4. 实现范围内的最小根本原因修复。移除所有命名的变通方法。如果根本原因超出范围，提交范围内的最小修复并报告其余部分为打开状态。**原则修复根本原因**和**原则从头开始重新设计**技能仅指导意图。两者均不授权扩大围栏或修复围栏外的实例。永远不要附加症状防护。
5. 约束性评论说 `do not remove`、`do not change wording` 或 `talk to X before changing`。保留关于我们无法更改的事物的保留。提供最便宜的范围性类型、运行时、测试或 CI lint。等待交互式批准。无人值守和评估需要调用者预先批准。如果批准，编码然后删除。否则删除，报告约束为打开状态，并勾勒出范围外的工作。
6. 报告删除计数、恢复的评论、重新运行、架构草图、修复、编码提议、编码、未执行的约束和其他打开的工作。
