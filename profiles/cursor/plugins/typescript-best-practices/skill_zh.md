# TypeScript 最佳实践

首先应用 **type-system-discipline** 原则。

| 规则 | 概要 |
|------|---------|
| 差异联合类型 | 使用 `kind` 字面量区分联合类型中的变体，以防止表示不可能的状态。不要使用可选字段集合。 |
| 品牌化类型 | 使用 `& { readonly __brand: "X" }` 品牌化原始类型，以防止它们被混淆。在边界处只验证一次。 |
| 构造性建模 | 构建形状，使得非法值无法被构造。例如使用 `[T, ...T[]]` 表示非空，使用 `[T, T][]` 表示偶数长度，使用 `start` 加 `duration` 表示范围。这不是运行时守卫，也不是对精化类型的期望。 |
| 最简单的全类型 | 保持 `T[]`，同时确保对其进行的所有操作都是全函数。仅在宽松类型强制 `!`、类型转换或抛出 "不应该发生" 的异常时，才加强为 `NonEmpty<T>`。 |
| `unknown` 而非 `any` | 外部数据是 `unknown`。 |
| 验证先于守卫 | 在手写逐属性类型守卫之前，使用仓库的运行时模式库并从模式中推断类型，例如 `z.infer`。 |
| 避免 `as` 类型转换 | 每个 `as` 都是一个等待运行时崩溃的类型转换。仅在验证后进行类型转换。 |
| 窄化层次结构 | 区分联合类型 > `in` 操作符 > `typeof`/`instanceof` > 用户定义的类型守卫 > `as`。 |
| 类型守卫 | 必须验证其声明。一个撒谎的守卫比 `as` 更糟糕，因为错误隐藏在表示安全的名称后面。将它们命名为 `isX` 或 `hasX`。 |
| 完备性检查 | 在默认分支中内联 `const _exhaustive: never = x;`，以便在添加新变体时编译器报错。 |
| `satisfies` 而非 `as` | 在不扩展字面量类型的情况下验证值。 |
| 边界验证 | 在数据跨入时解析为命名域类型。`Record<string, unknown>`（无论如何拼写）在解析时停止。信任内部类型。参见 **boundary-discipline** 原则。 |
| 基于模式的类型 | 在声明新接口之前，优先使用 `Pick`/`Omit`/`Parameters`/`ReturnType`/`Awaited`/`typeof`。 |
| 对象参数 | 传递对象而非位置参数，以便参数顺序自文档化。在热点路径（每帧渲染、标记器、解析器）上跳过。 |
| 真实测试 | 不要模拟可以运行的内容。优先使用具有泄漏/可丢弃检查的框架的真实测试原语，并在运行构建中验证 UI。仅在无法本地运行时才模拟。 |
| 结构化遥测 | 优先使用具有足够上下文以从 ID 调试的结构化日志诊断。已发布代码中不要使用 `console.log`。 |

示例：`references/patterns.md`。
