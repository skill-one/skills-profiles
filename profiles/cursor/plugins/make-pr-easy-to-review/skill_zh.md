# 使 PR 更易于审查

准备一个 PR，以便审查者能够快速理解其意图、重要文件和风险。默认目标是审查性，而不改变行为。

## 工作流程

1. 从用户提供的 URL 或当前分支解析目标 PR。
2. 检查提交记录、差异大小、更改的路径、生成的文件和 PR 描述。
3. 识别审查性问题：杂乱的提交、过时的描述、不相关的更改、混合机械和逻辑更改、缺失的测试或模糊的审查者入口点。
4. 在重写历史记录或强制推送之前提出计划。
5. 应用安全的改进，然后验证树或差异是否仍然与预期代码匹配。

## 历史清理

仅在用户要求或同意计划时才重写历史记录。在重写之前：

```bash
gh pr view <PR> --json title,headRefName,baseRefName,state,commits
git fetch origin <headRefName> <baseRefName>
ORIGINAL_TREE=$(git rev-parse origin/<headRefName>^{tree})
```

良好的提交分组通常遵循依赖顺序：

1. 模式/存储或生成的 API 定义。
2. 核心逻辑。
3. 连接和集成。
4. UI 或表面行为。
5. 测试。

重写后，验证内容一致性：

```bash
echo "原始树: $ORIGINAL_TREE"
echo "当前树:  $(git rev-parse HEAD^{tree})"
git diff origin/<headRefName> --stat
```

如果树意外更改，不要推送。

## 审查者指导

当代码行为应保持不变时，优先使用 PR 描述和审查笔记：

- 添加与实际差异匹配的 TL;DR。
- 将核心文件与生成或机械文件分开。
- 指出有风险的行为更改、迁移顺序、发布计划和测试覆盖率。
- 当问题追踪器、仪表板或设计文档解释意图时，链接它们。

## 安全限制

- 不要将有意义的行为更改隐藏在“清理”中。
- 除非用户明确要求，否则不要绕过钩子。
- 如果 PR 太大，无法通过笔记使其可审查，建议拆分而不是围绕问题进行润色。
