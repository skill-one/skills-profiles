# 回溯

**在开始或继续工作之前，你需要重建用户的最近工作上下文，并返回一个紧凑的胶囊，其中包含当前的状态以及下一步要做什么。**

保持简洁和主题相关。只阅读范围内所需的线程内容，然后停止。

你的上下文存在于两个记录中。你自己的聊天历史记录包含你所做和决定的内容。共享记录包含其他名称下同一代码周围发生的一切：用户持续报告的症状、已发布并回滚的修复、仍在生产环境中触发的错误。第二个记录是**为什么**技能搜索的内容，它会在源代码控制、问题跟踪器、聊天和问题渠道、长文档和错误跟踪中搜索。具有长错误链的功能将其大部分故事保留在那里，所以不要仅从你的记录中重建它。

记录存储在 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`，其中 `<slug>` 是工作区路径，去掉开头的斜杠并将每个斜杠转换为连字符（所以 `/Users/you/proj` 变成 `Users-you-proj`）。每一行是一个聊天消息。

1. 分类，然后路由。要继续的特定先前聊天是 `session-pickup` 播放剧本，而不是这个。将习惯转化为持久技能是 `automate-me`。你工作的可读摘要是一项不同的任务。回溯在执行操作之前加载最近聊天中的工作上下文。如果用户已经给你一个完整的状态胶囊（路径、分支、更改），则使用它并跳过挖掘。
2. 搜索前锁定范围。固定窗口（“最近”是一个真实范围，默认为最后 7 天），如果命名则指定主题，以及工作区（默认为活动工作区。未经请求，切勿读取另一个项目的记录）。陈述范围。切勿悄悄地将“全部”转换为“最近 N”。
3. 在你的聊天历史记录中发散。在快速、廉价的模型上生成并行子代理，每个子代理获取语料库的一部分。告诉每个子代理按实际修改时间（`ls -t`）排序候选者，而不是按 UUID 名称，首先使用主题进行 grep，然后只读取匹配的聊天及其相关区域，并跳过当前聊天以及明显的噪音（子代理、评估和测试聊天）。每个子代理返回相同的模式，每个聊天一个块：主题、用户的目标、决策、打开的线程、挣扎和纠正，以及工件（PR、工单、分支），每个都引用聊天 UUID。对于一两个聊天，跳过发散并直接搜索。原始记录保留在子代理中。主线程只获得它们的发现。
4. 每当主题命名功能、文件、子系统、区域或错误时，扫描共享记录。这是默认值，不是判断，并且“我在 X 上的工作”不会豁免它。将其交给**为什么**技能的源调查员，但将他们的问题从“为什么这样构建”引导到“当前状态是什么、什么尝试过但没有奏效、用户仍在报告什么”。重用其每个源的播放剧本，与聊天历史记录挖掘并行运行调查员，并继承其姿态：每个源一个调查员，空结果就是发现，跳过不可用的 MCP 并说明。将返回的内容折叠到简报中。仅对于没有命名目标的纯活动回溯（“这周我做了什么”），你的自己的历史记录和实时状态是全部答案，则跳过此步骤。
5. 与实时状态验证。获取挖掘和扫描浮现的 PR、分支和工单，并使用 `git` 和 `gh` 检查它们。当答案取决于代理实际做了什么（它运行的工具、读取的文件、遇到的错误）时，请阅读完整的记录，而不仅仅是修剪的本地副本。
6. 将简报写入下方的合同。按线程分组。保持在命名主题上。

## 输出合同

首先提供胶囊，然后是线程状态，然后是问题，然后是下一步行动。更详细的内容放在下面或被剪切。

- **胶囊。** 最多 5 个要点。这项工作是什么以及整体状态在哪里。
- **线程。** 每行一条，以确切的标签前缀：`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]` 或 `[planned, not started]`。没有标签的线程尚未完成，所以请标记它。
- **问题。** 最多 5 个，反复出现的问题。包括用户持续报告的症状以及任何已发布并回滚的修复，以便下一次尝试从上一次失败的地方开始。
- **下一步行动。** 最有用的单个下一步行动，具体。

相邻的功能或工单除非它阻塞这个，否则会排除在外。当胶囊和线程行超出屏幕时，在剪切线程之前剪切细节。通过 **unslop** 技能编写简报，引用聊天发现通过 UUID，引用共享记录发现通过其来源（PR #、工单 ID、聊天快照、错误跟踪器问题），并在任何公共输出之前清理私人上下文。

**回复：** 上述合同的简报。
