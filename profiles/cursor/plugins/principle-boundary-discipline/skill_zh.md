# 边界规范

在系统边界处放置验证、类型窄化以及错误处理。无条件信任内部代码。业务逻辑存在于纯函数中。外壳是薄而机械的。

**原因：** 分散的验证是嘈杂的、冗余的，并且会带来一种虚假的安全感。将逻辑从框架布线中分离出来，以便可以在不使用框架的情况下进行测试。

**模式：**
- **在边界处**（命令行参数、配置文件、外部API、网络协议）：验证、返回错误、防御性处理。
- **在系统内部：** 类型化数据、错误传播、无需重新验证。信任类型。
- **跨边界：** 暴露领域概念，而不是边界私有的表示。将通用机制保留在内部，将特殊策略放在边缘。

**应用：**

验证和错误处理：
- 在解析时（边界）验证配置，而不是在业务逻辑内部
- 在边界处将原始数据解析为领域类型
- 不要通过公共界面重新导出传输、存储、框架或线路类型
- 如果边界已经验证，则不要在调用链深处进行冗余的nil检查

代码组织：
- 业务逻辑在无框架依赖的纯函数中
- 解析函数：从原始字节到类型化状态的纯转换
- 提示构建：结构化状态输入，字符串输出
- 评分和评估：从状态到结果的纯转换

**测试：**
- “这些数据现在是否正在跨越系统边界？”如果不是，验证就是冗余的。
- “这能否是一个纯函数，外壳只需调用它？”如果是，将其提取出来。
