# 自动化我

这是一个引导流程，用于将用户的日常工作习惯转化为代理将遵循的技能。输出是一个针对用户的 `-mode` 技能（例如 `jay-mode`、`priya-mode`）。

该技能协调其他三个技能：一个内联挖掘流程（见步骤 1）、Cursor 的内置 `create-skill`（编写）、以及 **unslop** 技能（文风规范）。它按顺序执行它们。它不会取代它们。

## 流程

### 0. 检查现有技能

递归查找 `.cursor/skills/**/*-mode/SKILL.md` 和 `~/.cursor/skills/*-mode/SKILL.md`，匹配用户的用户名。模式技能可以存在于个人分类目录（`.cursor/skills/<handle>/`）中，而不仅限于顶层。如果存在，请使用 `AskQuestion` 确认意图（除非他们已经表示“更新我的技能”或类似内容）：

- 更新现有技能（重复运行时的默认选项）
- 重新开始（很少见，在执行之前询问原因）

更新模式会改变其余流程：
- 步骤 1 仅挖掘技能上次编辑后的历史记录（`git log -1 --format=%cI <path>`）。
- 步骤 2 询问发生了什么变化或缺失了什么，而不是从零开始捕获什么。
- 步骤 4 直接编辑现有文件。保留用户未反驳的部分。修订有新证据的部分。仅添加真正的新规则的新部分。

### 1. 挖掘历史记录

在扩展范围之前，定位活动工作区的会话记录。系统提示命名工作区的 `agent-transcripts/` 目录。仅使用该路径。不要在 `~/.cursor/projects/*/` 跨工作区边界，并读取与无关项目相关的私密聊天。

在该范围内调查最近的代理对话，寻找重复出现的模式。在历史记录的切片上运行多个并行子代理（例如最后 2-4 周，分成 3 个切片，以便每个切片都有足够材料）。每个切片挖掘子代理从父代理提供的、工作区范围的路径读取会话记录，寻找以下信号，并返回一个包含证据指针的短结构化模式列表。默认值得寻找的信号：

- 响应偏好（长度、语气、格式、“简化”更正）
- 委派习惯（子代理、模型、专用工作流、并行性）
- 验证立场（“完成”的含义、单元测试与可重复测试、审查者）
- 代码和文风规范（风格、引用的原则、检查/格式化工具）
- 流程规范（工作树、提交、拉取请求、审查/合并工具）
- 元偏好（在任务中途修复技能、提议新技能）

在提升信号之前进行交叉检查。在两个或多个切片中看到的模式是高置信度的。孤立的信号很弱，通常会被丢弃。

### 2. 直接询问用户

挖掘会遗漏尚未出现过的意图。使用 `AskQuestion` 工具（结构化多选）而不是让用户从零开始输入。

形状：一个或两个问题，每个问题有 4-6 个选项，`allow_multiple: true` 用于分类问题。从广泛的问题开始（“哪些领域最重要？”），然后针对选择的问题提供具体选项。在结构化轮次之后，一个自由形式的聊天问题可以捕捉选项遗漏的内容。

不要抛出 20 个问题。

### 3. 聚类发现

将组合信号分组为部分。常见的部分（仅使用适用的部分）：

- **响应风格**：长度、语气、格式。
- **自主性**：在不需要询问的情况下要做什么，MCP 工具的使用。
- **先理解**：在范围界定或调查更改时要使用的技能。
- **子代理**：默认、并行性、模型到任务、专用工作流。
- **文风 / 代码规范**：原则、检查工具、风格指南。
- **审查和验证**：可重复立场、验证技能、实时测试工具。
- **流程**：git 工作树、提交、拉取请求、审查/合并工具。
- **技能**：技能编写习惯、先修复技能、提议新技能。

**poteto-mode** 技能展示了形状。阅读它以获取粒度。不要复制其内容。用户的规则与 poteto-mode 的规则不同。

### 4. 起草技能

使用 Cursor 的内置 `create-skill` 技能编写技能。位置：

- 路径：保留现有模式技能的分类。对于新模式，当仓库为该用户名建立了个人分类时，使用 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`。否则默认为项目中的 `.cursor/skills/<handle>-mode/SKILL.md`（如果用户更喜欢个人技能）。
- 用户名：用户的名字或选择的标识符。
- Frontmatter `description`：在其名字 + `/<handle>-mode` + “以他们的风格工作”，而不是在“写代码”或“审查拉取请求”等通用关键词上触发。
- Frontmatter 格式：遵循 `create-skill` 的 YAML 规则。将 `description` 作为单个 YAML 标量。当标点符号或换行需要时，引用它或使用 `description: >-` 与缩进的续行。
- Frontmatter `disable-model-invocation: true` 默认。只有在用户明确希望他们的模式在每次回合上都应用时才退出。

### 5. 文风迭代

应用 **unslop** 技能和 `create-skill` 的写作指南到每一行。

向用户展示草稿并收集反馈。预期多次迭代。无情地删减。模式技能不是手册。

### 6. 部署

在 main 分支外的工作树中工作。提交并打开拉取请求。不要直接将 main 推送到 main。

## 安全机制

- **不要过度拟合单个对话。** 一次声明并在另一时间被反驳的偏好是噪音。在将其编码之前，需要多次实例。
- **不要耍聪明。** 重新陈述其他技能的内容、编造隐喻或为代理读者编写“诗意”的文风是没有益处的成本。保持其操作性。
- **引用，不要内联。** 用户依赖的其他技能应以路径引用形式出现，而不是粘贴摘录。对于他们在其他地方维护的任何原则文档也是如此。
- **保持部分最小。** 只有当用户在此处有特定、非默认的规则时才添加部分。“清晰沟通”不是一个部分。“短段落。在比较选项时使用表格。只有当项目真正平行时才使用项目符号。”是。
- **命名规范通用。** 在祈使句中使用“用户”或“人类”，而不是作者的名字。
- **不要强迫对称。** 如果用户没有值得写下来的流程规则，则完全跳过流程部分。

## 评估

`-mode` 技能是主观输出。`create-skill` 风格的测试/迭代基准循环在这里没有用。与用户进行“感觉检查”：它读起来像他们吗？是否遗漏了什么？然后发布。

只有在技能的触发准确率在实践中成为问题时，才运行描述优化循环。

## 不适用情况

- 用户想要一个特定任务的技能（不是工作习惯）：单独使用 `create-skill`，不需要挖掘。
- 用户想要捕获一个狭窄的工作流（例如“我如何写提交信息”）。这是一个常规技能，不是模式技能。
