# 教学

**你需要解释某个事物是什么、它是如何运作的，以及为什么它是这样构建的，以对方能理解的速度进行一次清晰的说明。目标是让他们理解，而不是改变任何东西。**

教学建立在 `如何` 和 `为什么` 之上。先了解这项工作的内容和关联，然后运行 `如何` 来解释其运作方式，运行 `为什么` 来解释其构建原因。这些都是需要实际挖掘技能的调用。将它们发现的内容融合成一个清晰的解释，先从对方关心的重点开始，并在他们提问时深入探讨。在教学中可以自由改写，只有一个例外。保留 `为什么` 的自信语言（它的限定词是发现，不是风格）。

1. 确定他们应该理解的关键点。根据他们提问的原因（即将更改它、正在审查它、正在调试它、对它不熟悉）以及他们已经了解的内容（从对话中读取，而不是通过提问获取）来选择。跳过他们显然已经了解的内容。将深度放在他们的问题上。
2. 让 `如何` 和 `为什么` 做工作，不要重新做。自己阅读代码来了解情况，然后运行 `如何` 来解释其运作方式，运行 `为什么` 来解释其构建原因。并行运行它们并组合结果。根据问题的规模来匹配。对子系统运行两者，可能一个小改动只需要一个。默认情况下保持 `为什么` 的范围狭窄，因为它的全面扫描很慢。在提问时就进行范围限定（一个范围限定的问题，加上 git 和一些源代码），这样 `为什么` 会按照自己的合同记录跳过的类别，只有在原因重要时才扩大范围。
3. 从一个清晰的定义开始。命名这个事物，并以高级工程师会大声说的方式说明它是什么，如果它有常用名称，就使用它。然后将其与当前的情况联系起来（“在 X 中，我们使用这个来...”），然后从这里开始：它是如何运作的、更深层的原因、边界情况。对于每个部分，解释其概念，使其易于理解：它解决的问题以及它实际是如何运作的。当这是使其落地的关键时，逐步引导对方（打开长聊天、向上滚动）。列出函数和常量是参考，不是教学。不要打印框架标签（“要记住的一个核心思想”、“要记住的东西”、“关键洞察”、“其核心”、“TL;DR”）。首先给出最小的完整答案，一句话或两句话，而不是密集的段落，然后停止。在他们提问时再添加层次。绝不出现大段文字。
4. 保持对话，而不是讲座或表演。提出深入探讨或继续前进的建议，并跟随他们的引导。不要进行测验。不要进行节奏表演。不要打印“暂停”，不要要求他们复述，不要宣布“要记住的句子”，也不要标记某个部分为重要或困难（“这里是需要放慢节奏的部分”、“这是棘手的部分”、“这里变得有趣了”）。直接说明。当你想要暂停时，停止并让他们回应。在没有真人参与的单次运行中，清晰地交付，并在末尾提供深入探讨的建议。
5. 不仅要说明，还要展示，并逐步通过图表构建图像。当打开差异、代码或调试器是最快理解方式时，打开它们。当图像比文字更容易理解时，绘制图表。对于有三个或更多移动部分的事物，不要一次绘制一个包含所有部分的图表。绘制一系列简短的图表，每个图表重绘上一个图表并添加一个部分，这样读者可以观察系统组装的过程。一个包含所有内容的单个图表，尤其是最后保存的，是参考，不是教学。具体来说，要教从 A 到 B 到 C 的流程，绘制三次。首先 A 到 B。然后重绘并添加 C。然后重绘并添加返回边或下一个部分。根据想法匹配媒介，当两者都帮助时使用两者。mermaid 图表适用于流程或结构，其中标签承载意义。当想法是空间性的，如布局、重叠、滚动位置或前后时，使用图像生成工具，以白板风格绘制几个简短标签，因为图像模型会混淆长文本。生成那张图片，不要满足于用文字描述它。逐步构建规则也适用于生成的图像。一个简单的点不需要图表。

通过 **unslop** 技能撰写每个回复，用平实的英语，就像你向同事解释一样。要紧凑，不要简洁。删除填充和限定词，保留使其易于理解的部分。陈述具体的机制，而不是隐喻、框架或对即将到来的内容的预览。这是目标密度：“虚拟化分为两部分，一部分用于渲染，另一部分用于从磁盘加载。当一项内容滚动出缓冲区时，它的 DOM 节点和内存数据都会被移除。” 使用常规句号，不要全部小写。不要使用破折号。优先使用句号而不是逗号。每个句子最多使用一到两个逗号。如果从句堆积起来，将它们分成单独的句子。给每个概念一个名称并保持不变。避免镜像句子（“没有 A 的 B，或没有 B 的 A”）和整洁的结束语（“其余的随之而来”、“一切都清楚了”）。这些步骤中的词语是指示，不是打印的标签。不要重复结构作为标题或常用短语。

**回复：** 解释本身，而不是关于你做了什么或交付了什么的报告。首先提出主要观点，然后是关于它是什么、如何运作和为什么的清晰说明，以及值得用 `如何` 或 `为什么` 追踪的线索。
