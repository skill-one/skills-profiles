# 安全审计

发现违反真实信任边界的漏洞，然后向所有者提供源证据、安全可复现、优先级和最小有效修复。这是一种防御性、源代码优先的工作流程。没有具体受影响的主体、资源或安全结果的候选项不是已确认的发现。

## 操作模式

此技能默认为指导模式。加载它不会授权完整的审计工作流程或文件创建。

- **指导模式**：对于安全问题、专注审查、方法、分派或特定发现的调查，仅使用与此技能相关的部分。不要自动运行所有六个阶段、创建输出目录或编写审计工件。当有用时，您可以启动专注代理；它们将结果返回到当前任务。
- **完整审计模式**：当用户明确要求审计或渗透测试代码库、要求全面的、综合的或端到端的安全审查，或请求报告工件时，使用完整工作流程。运行所有六个阶段并编写以下定义的文件。

如果请求可能意味着两种模式中的任何一种，请在创建文件或开始完整工作流程之前问一个专注的问题。

## 平台术语

此技能是代理中立的：

- **父代理**是协调运行并拥有共享状态的代理。
- **任务工具**是平台的委托或子代理机制。
- **`research` 代理**是用于专注源探索和事实验证的委托代理。
- **`general` 代理**是用于广泛调查和有界本地执行的委托代理。
- **`subagent_type:`** 在标题中命名运行该工作的两个委托代理角色中的哪一个。

使用等效的平台功能，同时保留角色、写隔离、提示和独立性边界。

## 通用执行安全

这些规则适用于两种操作模式。源检查是只读的。仅在提供所有这些控制的操作系统强制的沙盒内运行目标控制构建、测试、进程、浏览器、模拟器、模糊器和固定件处理：

- 没有外部网络；当检查需要本地客户端/服务器流量时，仅使用隔离的回环命名空间；
- 一个空环境，从显式的允许列表中填充安全值，具有 scratch-local `HOME`、临时目录和缓存；
- 只读目标和工具链，目标控制进程只能在其分配的 `scratch/` 目录内写入；以及
- 明确的低 CPU、内存、进程、文件大小、磁盘和墙时钟限制。

代理可以在分配的 `scratch/` 目录中创建可丢弃的源副本，当构建必须在源旁边写入时。在指导模式下，不要保留目标控制文件。在完整审计模式下，只有可信的父侧代码可以使用 Write isolation 下的程序将最小的非秘密结果提升到保留的 `artifacts/` 中。永远不要将保留的输出目录（除了代理自己的分配的 `scratch/`）暴露给目标代码，另一个代理的目录、主机主目录、凭证、套接字或共享服务，不要安装依赖项或让构建获取它们。仅使用本地已提供的工具和依赖项。如果无法强制执行所有控制，则不要执行目标代码：报告缺少沙盒功能作为需要验证的阻止器，并给出安全的验证计划。

使用虚拟主体、固定件和秘密。不要探测已部署的端点、外部服务、共享基础设施、生产身份、其他用户的数据或实时控制平面。不要针对实时或共享进程测试可用性、发布工件、更改发布版本、花费付费 API 配额或继续超出建立缺陷所需的最小本地效果。如果决定性事实在源之外或沙盒化固定件之外，则报告它需要验证。

## 完整审计设置

在完整审计模式下，在侦察之前解决这些值：

- **技能目录**：包含此 `SKILL.md` 的绝对目录。
- **目标**：审查的绝对仓库根目录。
- **仓库名称**：来自目录或本地 Git 远程的稳定仓库标识符。
- **输出目录**：目标外部的可写目录，默认为 `~/security-audit-skill/<repo-name>/run-<N>`，其中 `<N>` 是下一个未使用的整数。仅在用户明确选择它并且父代理验证整个目录被版本控制忽略的情况下，才在目标内部使用目录。否则停止并请求外部路径。
- **源引用**：审查的提交和是否工作树已脏。不要将未审查的生成或修改文件视为另一个版本。

### 写隔离

父代理创建并是唯一写入共享运行文件的：

- `run-metadata.json`
- `architecture.md`
- `coverage-ledger.json`
- `findings.json`
- `REPORT.md`
- `FINDINGS-DETAIL.md`
- `NEEDS-VALIDATION.md`

每个猎人或验证器都在 `<output-dir>/agents/<agent-id>/` 下获得一个唯一的根，具有单独的 `scratch/` 和 `artifacts/` 目录。规范代理 ID 匹配 `^[a-z0-9][a-z0-9_-]{0,63}$`，并且不能等于 Windows 设备名称，例如 `con`、`prn`、`aux`、`nul`、`com1` 通过 `com9` 或 `lpt1` 通过 `lpt9`。小写 ID 可防止大小写折叠冲突。代理和每个目标控制进程只能写入 `scratch/`；保留的 `artifacts/` 由父代理拥有，永远不会暴露给沙盒，并且只能由可信的父侧提升代码写入。代理不能更改共享文件、目标源、保留的工件或另一个代理的目录。不要使用 `/tmp` 或主机主目录作为可写回退。

在执行之前，父代理打开并保留对代理的 `scratch/` 和 `artifacts/` 根的可信、非继承的目录描述符，并记录预期的 scratch 相对工件文件的允许列表以及显式的每个文件和累积字节限制。永远不要将那些描述符传递给代理或沙盒。沙盒及其所有进程终止后，可信的父代理代码将每个允许列表文件单独提升：

1. 验证声明的相对路径：拒绝绝对路径、空路径、`.`、`..` 或符号链接组件。
2. 从保留的 scratch-root 描述符开始，使用无跟随目录相对操作逐个遍历父组件；永远不要通过路径重新打开。
3. 打开叶无跟随和非阻塞。
4. 使用 `fstat` 验证它是链接计数正好为 1 的普通文件，并且在其记录的每个文件和累积字节限制内。
5. 再次在从该描述符读取时执行这些限制。
6. 复制确切的验证大小，重复 `fstat`，并拒绝身份、类型、链接计数或大小的变化。
7. 对于目标，使用无跟随目录相对操作从保留的 artifacts-root 描述符开始遍历每个父组件；要求每个现有组件是真实目录，并在重新打开和验证它之前独占地创建任何缺失的目录。
8. 独占地创建叶，验证打开的目标是链接计数正好为 1 的普通文件，并从验证的源描述符复制，而不重新打开任何路径。
9. 在非 POSIX 系统上使用等效的竞争安全 API。
10. 永远不要递归复制或 glob scratch，将存档提取到 artifacts 中，或打开或提升符号链接、FIFO、套接字、设备、目录、硬链接文件、更改文件或超出其边界的文件。
11. 如果任何检查不可用、无法强制执行或失败，则丢弃 scratch 条目；如果它是决定性证据，则保留 `needs_validation` 并带有确切的提升阻止器。

[HUNTING.md](HUNTING.md) 和 [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md) 将此程序作为猎人提示和验证器提示的一个相同的分隔块携带；它以与此列表相同的顺序声明相同的规则。

对于重复的检查，记录命令、确切的测试输入、沙盒限制，以及仅允许列表的环境变量名称加上安全非秘密值，这些值需要重复它。永远不要捕获或复制环境、继承变量、凭证值、认证状态或无关主机路径。从空环境启动，而不是尝试在执行后编辑一个。

在委托之前，父代理写入 `run-metadata.json`，其中至少包含 `run_id`、`repo`、`target`、`source_ref`、`profile`、`scope_paths`、`budget`（如果未设置则为 null）、`execution_policy: "sandboxed-source-and-local-only"`、选定的伴随文件、先前的运行路径、共享文件所有者，以及 `run_status: "in_progress"`。仅当这些事实发生变化时才更新元数据；候选状态属于覆盖账本和 `findings.json`。

## 完整审计规划

本节中的覆盖范围、先前的运行、配置文件和预算要求仅适用于完整审计模式。

### 覆盖范围和先前的运行

没有一次通过是完整的。在狩猎之前构建确定性的覆盖计划，并在每个代理结果后更新它。[RECONNAISSANCE.md](RECONNAISSANCE.md) 定义了稳定的覆盖单元，[HUNTING.md](HUNTING.md) 定义了覆盖批评波。只有父代理更新账本。

如果存在先前的运行，则在规划当前运行之前读取每个兼容的 `coverage-ledger.json` 和 `findings.json`：

1. 将相关的当前源与每个先前的记录和单元进行比较。仅先前的源引用本身不能证明路径未更改。
2. 仅当其相关源和条件未更改并且其证据仍然满足当前合同时，才将先前的 `confirmed` 记录带入当前候选集。将其链接到当前账本单元的 `planned` 种子，保留其指纹，仅从猎人中排除仅携带的根原因，并将携带的记录通过当前最终验证路径发送；重新检查它的 Phase 3 验证器成为该单元的分配所有者并将它移动到 `candidate`。
3. 当先前的 `confirmed` 记录的相关源发生变化时，创建当前计划的重新验证单元。不要将该记录放在猎人排除列表上。它仅在当前独立验证建立当前路径和结果时才保持确认。
4. 将先前的 `needs_validation`、`deferred`、`blocked`、`out_of_scope` 和任何更改源单元设为当前工作。仍然外部的 `needs_validation` 记录只能在当前源跟踪检查并链接到当前 `planned` 单元后，其验证器重新检查提供其所有者和证据；该记录保留未解决的阻止器。这些先前的状态永远不会抑制当前单元。
5. 先前的相同源覆盖单元可以提供优先级，但它仍然在当前账本中可见。先前的 `rejected` 记录仅抑制未更改的失败声明，而不是其单元的覆盖范围；更改证据创建当前工作。
6. 读取先前的配置文件和范围。先前的 `quick` 或范围账本仅贡献其记录的证据和差距，永远不会暗示“其余的都很好”。

如果没有先前的账本，请在最终覆盖声明中说明。永远不要暗示一次运行就耗尽了目标。

### 运行配置文件和范围

在完整审计设置期间，从用户请求中选择配置文件或根据目标的规模和利益提出一个。在 `run-metadata.json` 中记录它（`profile`、`scope_paths`），并在报告中声明它。默认值是 `standard`。

- **`quick`** — 为小目标、重新运行或快速第一眼进行有界的通过。将账本单元粗化为显示 × 边界 × 攻击类（子系统使用固定的规范 `profile/quick/all-in-scope-subsystems` 标识符），运行恰好一个猎人波，然后运行恰好一个最终覆盖批评通过，并为候选项使用一个新鲜验证器进行候选验证和最终记录验证。不要启动后续猎人波：记录批评者接受的发现和重新分配为 `deferred`。
- **`standard`** — 写入的工作流程。
- **`deep`** — 用于高风险或大目标。按子系统和生命周期模式拆分账本单元，运行批评波以获得干净的通过，将候选验证和最终记录验证保留为单独的新鲜代理，并为 `prior_covered_same_source` 单元提供独立的第二遍。

一个**范围运行**审计一个子集：命名路径、一个子系统、一个伴随域或两个源引用之间的差异。仅针对在范围内的表面种子账本单元，并将所有其他内容记录为 `out_of_scope` — 永远不要记录为 `covered`。范围或 `quick` 运行必须将自己呈现为部分覆盖。

配置文件改变广度和冗余，永远不会改变证据标准。不要缩小候选门、源/本地执行边界、`needs_validation` 纪律、模式验证或 `confirmed` 记录的独立验证。

#### 成本预算

账本使花费可计算：一个单元大致相当于一个猎人分配，并且一个生存的候选者是 1 个或 2 个验证器分配，具体取决于配置文件。当用户设置预算——或者父代理为大型目标提议一个预算——在 `run-metadata.json` 中记录 `budget` 作为所有阶段中代理调用的最大次数。

在启动任何侦察代理之前应用严格的预算门。保留四个基线侦察调用，对于 `quick` 是一个最终后波批评，对于 `standard`/`deep` 是一个最终后波加一个独特的最终干净批评，并且至少有一个验证器调用。在重复此门之后，仅添加专注侦察。如果请求的预算无法资助该最小值，则不启动代理：请求更大的预算、更窄的范围或不同的配置文件。如果请求保持不变，则设置 `run_status: "incomplete"` 并带有 `incomplete_reason: "budget_cannot_fund_reconnaissance_and_reserves"`，并报告没有运行审计通过。

按此顺序花费：

1. 计数侦察、每个后波批评和单独的最终干净批评作为代理调用。
2. **在狩猎之前保留批评和验证**。对于 `quick`，保留它的一个后波最终批评。在每次 `standard` 或 `deep` 猎人波之前，保留一个立即后波批评加上一个独特的最终干净批评。还保留来自配置文件的验证器成本（大约 1 或 2 个代理每个预期的候选者；如有疑问，保留余额的 30% 作为批评保留后的验证器成本）。永远不要将猎人分配到任何保留中。
3. 按优先级顺序分配猎人到单元，直到狩猎配额用完。在那一波之后立即花费保留的后波批评；保留最终干净和验证保留。
4. 在后续波之前，再次保留其新的后波批评。如果剩余预算无法覆盖所需的批评调用和验证保留，则不从这个波启动猎人，将其计划的单元标记为 `deferred` 并带有原因 `budget_cannot_reserve_critics_and_validation`，并使用保留的最终干净批评记录由此产生的差距。

在波 1 之前，使用种子单元更新预侦察估计，包括预期的猎人计数、强制批评调用、验证保留，以及剩余预算是否覆盖计划。如果它显然无法，请说明并提出更紧的范围或更粗的配置文件，而不是在沉默中减少证据。如果后来的事实消耗了所需的最终批评保留，则不启动猎人，将所有计划工作标记为 `deferred`，将运行设置为不完整并带有原因 `critic_budget_exhausted`，并且不进行完整覆盖声明。

一个严格的总代理预算仍然可能因意外大的候选集或需要另一个独立验证的实质性 Phase 5 替换而超出。如果剩余预算无法验证每个候选者，则停止狩猎，在预算允许的情况下按指纹顺序验证候选者，并设置 `run_status: "incomplete"` 并带有 `incomplete_reason: "validation_budget_exhausted"`。保留每个未验证指纹链接到具有该未解决原因的 `candidate` 账本单元。不要将未验证的候选者放入 `findings.json`，将其重新标记为 `needs_validation` 或报告运行为完成。Phase 6 可能只会产生部分报告，如果它的第一部分声明候选验证不完整并列出受影响的指纹和单元。永远不要在用户设置的严格预算下静默超出。

## 核心原则

### 要求边界和结果

对于每个候选者，命名下信任主体、接受的输入或操作、预期控制、跨越的边界、受影响的主体或资源，以及具体观察到的或所有者可观察的结果。不要将一个缺失的最佳实践、猜测的部署行为、通用解析器崩溃或自我影响提升为安全发现。

### 使用有界本地证据

静态分析建立了源路径。沙盒化本地测试在所有执行控制可用时解析行为：一个最小的函数托盘、现有的单元测试、小的解析器固定件、虚拟租户集成测试、本地渲染的配置或有界隔离回环客户端。在错误返回值、未经授权的虚拟记录、清理器发现、策略差异或其他最小效果处停止。不要将本地检查扩展到最小边界结果之外，或产生持久性、故障后或隐藏材料。

### 尊重源可见性

部署控制、代理行为、提供者设置、浏览器标头、身份策略、代理 ACL、打包和拓扑是真实控制。如果它们是必需的并且从仓库中缺少，则不要假设存在或不存在。使用 `needs_validation` 并带有确切的缺失事实和一个安全的所有者观察或本地计划。

### 将优先级与确定性分开

只有 `confirmed` 记录接收严重性。可能性和影响必须反映已演示的条件和结果；整体严重性不能超过已演示的影响。`needs_validation` 意味着特定的基于源的边界假设被阻止，而不是低置信度的确认漏洞，并且它没有严重性。

使用这些锚点校准整体严重性：

- **critical** — 一个未经身份验证的参与者获得代码执行、完整数据存储访问或任意账户的接管。
- **high** — 一个参与者完全击败了明确的安全控制，并产生了真实后果：身份验证绕过、跨租户读取或写入、影响其他用户的存储脚本执行、经过身份验证的代码执行，或未经身份验证的远程停止共享服务。
- **medium** — 一个真实的边界违规，具有有限的爆炸半径、不常见的先决条件或后果仅限于狭窄的资源集。
- **low** — 非秘密内部的披露，或需要持续努力才能获得最小收益的效果。
- **informational** — 一个确认但影响最小的观察结果，主要用于作为更大发现的先决条件。

高/中区分：演示的结果是否完全击败了针对具有真实后果的动作的明确控制，或者只是削弱了它？如果你无法声明具体损害，严重性低于它给人的感觉。

### 推荐最小的有效源修复

对于每个确认的发现，确定代码必须强制执行的不变量，以及最窄的源更改，它在最后一个可信决策点强制执行它。优先考虑特定的仓库相对更改和回归测试，而不是通用的硬化建议。审计描述了修复；它不会修改目标源。

## 完整审计工作流程

在完整审计模式下，按顺序遵循所有六个阶段：

1. **侦察** — 使用 [RECONNAISSANCE.md](RECONNAISSANCE.md) 绘制源、信任边界、本地构建路径、伴随选择、先前证据和初始确定性覆盖账本。
2. **覆盖范围狩猎波** — 从账本分配隔离的猎人并使用 [HUNTING.md](HUNTING.md)、[ATTACK-CLASSES.md](ATTACK-CLASSES.md) 和选定的域伴随收集结构化候选结果。
3. **候选验证** — 整合指纹并将每个候选者提供给 [VALIDATION-AND-REPORTING.md](VALIDATION-AND-REPORTING.md) 中定义的新鲜源验证器。
4. **结构化输出** — 将所有最终的 `confirmed`、`needs_validation` 和 `rejected` 记录写入 `findings.json`；使用 `report-schema.json` 和 `validate-findings.cjs` 验证它，并使用 `validate-coverage-ledger.cjs` 验证覆盖声明。
5. **独立记录验证** — 使用新鲜代理验证最终源声明并协调更正或状态更改。
6. **目标无关报告** — 从最终记录派生 `REPORT.md`、`FINDINGS-DETAIL.md` 和 `NEEDS-VALIDATION.md`，其中不包含实时探测指令。

在以下两种终端状态之一结束运行之前： (a) 所有 Phase 6 工件都已写入并且两个验证器都通过，或 (b) 记录 `run_status: "incomplete"` 并带有其确切的理由和差距在报告中披露。永远不要在阶段中途停止。

## 反模式

1. 呈现为漏洞的清单偏差。
2. 没有可达到的边界违规的纵深防御建议。
3. 在有界本地证据不足的情况下进行实时或共享环境测试。
4. 猜测提供者、代理、浏览器、身份或部署行为不在源中。
5. 将预期的相同主体授权或自我影响视为跨边界结果。
6. 报告比观察到的效果更强的解析器或运行时效果。
7. 发射无法去重或验证的纯文本猎人结果。
8. 重新报告携带相同源先前的确认记录或将其用作锚定狩猎的示例。
9. 将严重性分配给 `needs_validation` 记录。
10. 在独立验证之前编写报告或让纯文本和 JSON 不一致。
