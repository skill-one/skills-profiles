# 在线评估工程

迭代构建在线评估器：

```text
检查追踪记录并访谈用户 -> 提出方向 -> 用户选择
-> 构建评估器 -> 测试、附加、验证 -> 审查并重复
```

在创建或修改评估器之前，请阅读 [参考资料/langsmith-api.md](references/langsmith-api.md)。

## 1. 检查追踪记录

向用户询问他们的 LangSmith 项目名称。获取最近的根级追踪记录并打印其结构。阅读 [参考资料/trace-inspection.md](references/trace-inspection.md)。查找：

- 运行名称和类型；
- 可用的输入和输出字段名称；
- 数据的形状和内容（截断的样本）；
- 哪些字段包含评估器所需的数据。

在对话中总结追踪记录结构：

```text
项目：名称
运行类型：链 | llm | 工具 | ...
输入字段：字段名称及其包含的内容
输出字段：字段名称及其包含的内容
样本：一个具有代表性的输入/输出对（截断）
```

保持用户参与：解释追踪记录结构及其含义，然后只询问追踪记录无法确定的信息。例如：“这个应用程序做什么？”，“哪个质量问题是首要的？”，或“什么故障绝不能发生？”

询问用户是否希望为本次会话中的评估器指定命名前缀（例如，`myapp-`，`v2-`，`dogfood-`）。如果他们提供前缀，请将其应用于所有评估器名称、提示中心处理程序和运行规则显示名称。如果他们拒绝，请使用纯描述性名称。

在理解追踪记录结构并描述了他们的担忧之前，不要提出评估器建议。

## 2. 讨论并选择评估方向

阅读 [参考资料/evaluator-design.md](references/evaluator-design.md)。基于追踪记录数据提出两个或三个评估标准。如果用户提供了前缀，请应用步骤 1 中的前缀。对于每个评估标准，提供：

```text
名称：描述性评估器名称（如果设置了前缀）
类型：LLM 作为法官 或 代码
衡量：评估的质量维度
评分：布尔值、浮点数（0-1）或整数；通过/失败的含义
所需字段：使用的追踪记录字段及其方式
理由：为什么选择这种类型和方法
```

示例：

```text
名称：响应相关性
类型：LLM 作为法官
衡量：响应是否回答了用户的问题
评分：布尔值；True = 相关，False = 不相关或无响应
所需字段：输入（用户问题），输出（助手响应）
理由：相关性是语义的，需要阅读理解；不能通过代码决定
```

推荐一个，并询问用户要构建哪个。在用户选择之前，不要实施。

## 3. 构建一个评估器

阅读 [参考资料/langsmith-api.md](references/langsmith-api.md)。构建选定的评估器。在执行任何 API 调用之前，向用户展示完整配置并获取批准。

**LLM 作为法官路径。** 首先定义 `ResponseSchema`，然后定义分数字段。编写提示消息，使用明确的评分标准来评估结果，而不是是否与参考答案匹配。使用步骤 1 中发现的字段名称设置 `variable_mapping`。向用户展示架构、提示、变量映射和评估器名称以供批准。在批准后，推送提示并创建评估器。报告评估器 ID。

**代码评估器路径。** 编写一个 `perform_eval(run, example=None)` 函数。它必须是自包含的（仅使用内置函数和标准库），访问 `run` 作为字典（`run.get("outputs")`），并返回 `{"key": ..., "score": ..., "comment": ...}`。向用户展示函数代码和评估器名称以供批准。在批准后，创建评估器。报告评估器 ID。

## 4. 测试、附加和验证

在附加之前，询问用户他们想要的采样率（1.0 = 每个追踪记录，0.5 = 一半，0.1 = 10%，或自定义）。不要默认静默。如果用户不确定，建议 1.0 进行初始测试。

询问用户是否希望在附加之前使用几个现有的追踪记录测试评估器。运行规则仅在新的追踪记录上触发，因此历史测试是验证新流量到达之前唯一的方法。

对于代码评估器，直接对获取的根级追踪记录执行 `perform_eval`，传递一个具有 `inputs`、`outputs` 和 `attachments` 键的字典。这可以在生产之前捕获运行时错误（错误的字段名称、字典与对象访问、缺失数据）。对于 LLM 评估器，验证配置：确认 `variable_mapping` 键与提示占位符匹配，确认映射的追踪记录字段存在，并检查映射的数据是否有意义。

如果测试发现错误，请在附加之前修复并重新创建。如果用户拒绝测试，请继续附加。

创建一个运行规则以将评估器连接到追踪记录项目。将用户的命名前缀应用于 `display_name`。确认评估器出现在评估器列表中并正确附加了项目。检查：

- 评估器附加和运行规则状态；
- 最近追踪记录的反馈和分数（来自历史测试或新追踪记录）；
- 分数是否与检查的追踪记录的预期匹配；
- 边缘情况处理（空输出、错误运行、意外结构）。

当评估器崩溃、评分错误或边缘情况失败时，修复并重新附加。在批准之前，确认评估器评分了预期的质量维度，而不是基础设施或数据形状失败。

## 5. 与用户一起审查

解释评估器名称和 ID、质量维度和评分方法、使用的追踪记录字段、采样率以及任何限制。询问用户是否批准、修改、删除或选择下一个方向。如果继续，请重用追踪记录发现，然后提出一个不同的质量维度。

## 不变量

- 每个评估器一个质量维度。
- 不要猜测字段名称；在实施之前始终检查追踪记录。
- 在进行 API 调用之前显示配置并获取用户批准。
- 代码评估器必须是自包含的：仅使用内置函数和标准库。
- 代码评估器将 `run` 作为普通字典接收；使用 `run.get("inputs")` 和 `run.get("outputs")`，而不是属性访问。`example` 参数必须默认为 `None`。
- 将 API 失败、认证错误和运行规则失败视为基础设施错误，而不是评估器错误。
