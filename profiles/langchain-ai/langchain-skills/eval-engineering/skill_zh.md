# 评估工程

## 流程

- 首先检查所有输入：仓库、Harness、可选的跟踪记录、现有的任务和运行记录、现有的世界知识以及人类目标。在提出工作建议之前，识别适用于当前任务的源文件和技能引用。
- 从这些输入中的可重用事实创建或更新小型项目世界知识技能。使用它来建议一个有根据的任务。
- 一起起草任务规范和世界技能。向用户展示两者，仅在 `Task.md` 中保留精确的任务真相，并直到用户批准它们之前进行完善。
- 实现已批准的任务，验证其环境和验证器，运行真实的 Harness，检查完整证据，并仅修复非代理故障。
- 使世界技能与运行结果一致，然后对下一个任务重复此流程。

## 术语

- **任务规范（Task Spec）**：`Task.md`，它描述了一个任务的输入、相关的代理条件、环境、评分、公平性以及开放决策。
- **任务（Task）**：可运行的指令、环境和验证器。
- **Harness**：代理 Harbor 的完整运行，包括提示、模型循环、工具、钩子、内存、会话和适配器。
- **环境（Environment）**：Harness 周围的文件、数据、服务、身份、权限、网络、时钟和可变状态。
- **验证器（Verifier）**：对结果进行评分或标记运行无效的独立检查。
- **世界知识技能（World Knowledge Skill）**：一个具有可重用项目特定知识、引用、脚本、资产和测试的本地仓库技能，这些内容有助于生成任务规范并构建未来的任务。
- **Spec2Task**：将已审阅的任务规范转换为已审核的可运行任务的完整循环。遵循 [任务实现](references/task-implementation.md) 了解其具体的构建顺序和参考路由。

## 1. 检查输入和现有的世界知识

在提出任务之前，审查用户提供的每个输入。使用与每个可用输入匹配的指导：

- 对于仓库、Harness、跟踪记录或依赖项，读取 [发现](references/discovery.md)。
- 对于现有的任务和运行记录，检查它们的指令、环境、验证器、奖励、轨迹和最终状态。当运行质量或故障影响新设计时，读取 [校准](references/calibration.md)。
- 对于现有的项目世界技能，读取 [世界知识](references/world-knowledge.md)，然后检查影响新任务的源代码和可重用方法。
- 对于人类目标和约束，读取 [任务设计](references/task-design.md)。
- 对于相关的基准示例，使用 [基准模式](references/patterns.md) 中的领域索引和源代码调用。

在提出问题之前检查仓库，因为源代码和测试可以回答这些问题。遵循活动的 Harness 通过提示、模型、工具、服务、状态、效果和聚焦测试。检查现有任务的指令、解析器、验证器、奖励路径和运行证据。

如果用户提供了跟踪记录，请审查完整的运行或线程。使用跟踪记录学习真实请求、依赖项行为、状态形状、错误和故障条件。不要将跟踪记录的答案视为独立的真相。

如果存在 `.agents/skills/<project>-world/SKILL.md`，请读取它。仅对于与当前任务相关的知识，遵循其路由。当引用的仓库路径、命令和脚本的准确性影响设计时，请检查它们。

## 2. 提出和选择任务

读取 [任务设计](references/task-design.md)，并使用 [基准模式](references/patterns.md) 中的索引查找相关的领域和源代码调用。除非任务跨越其他领域，否则专注于该领域。在检查后的第一个面向用户的设计响应中，提出一个基于仓库证据、提供的跟踪记录、现有覆盖范围或人类优先级的任务。说明：

- 真实工作和能力；
- 使情况变得非平凡的条件；
- 所需的环境和独立证据；
- 它可以检测的重要故障；
- 它与现有任务的不同之处；以及
- 主要的开放决策。

在同一响应中，显示相关的当前世界技能内容以及此任务建议的特定添加或更正。如果不存在世界技能，请显示将帮助创建此任务和未来任务的小型初始内容。将任务的精确请求、焦点记录、预期结果、隐藏真相和精确评分规则排除在世界技能之外。

在实施之前，让用户一起修改任务提案和世界知识。仅在真实的用户选择改变设计时才提供替代方案。

## 3. 编写和审查任务规范和世界技能

将 [任务模板](assets/task/Task.md.template) 复制到 `evals/<suite>/tasks/<task-id>/Task.md`。将所有特定于任务的设计放在这个文件中。同时，按照 [世界知识](references/world-knowledge.md) 创建或更新项目世界技能。确定由活动代理和仓库支持的项目技能位置。`.agents/skills/<project>-world/SKILL.md` 和 `.claude/skills/<project>-world/SKILL.md` 是常见的着陆点。如果存在已建立的项目约定，请遵循它。否则，解释建议的位置并在创建技能之前获得用户确认。在需要时，从 [世界技能模板](assets/world-skill/SKILL.md.template) 开始。

将每个 `Task.md` 放在与它描述的 Harbor 任务旁边：

```text
evals/<suite>/tasks/<task-id>/
├── Task.md              # 人类审查的控制平面规范
├── task.toml             # 必要的 Harbor 配置
├── instruction.md        # 必要的代理输入
├── environment/          # 必要的环境定义和可见状态
│   ├── Dockerfile        # 使用这个或 docker-compose.yaml
│   └── docker-compose.yaml # 可选；主要服务必须是 main
├── tests/
│   ├── test.sh           # 必要的 Harbor 验证器入口点
│   ├── test_*.py         # 可选的验证器辅助程序
│   └── fixtures/         # 可选的隐藏验证器数据
└── solution/
    └── solve.sh          # 可选的参考路径
```

永远不要将 `Task.md` 复制或挂载到被评估代理的工作区或镜像中。代理仅接收 `instruction.md` 和为运行打算的环境状态。

包括：

- 目的和源证据；
- 精确的输入和后续轮次；
- 仅与此任务相关的 Harness 条件；
- 初始状态、服务、访问权限、可见性、重置和生产差异；
- 必要的结果、禁止的效果、接受的替代方案和独立验证器证据；
- 公平性、泄漏风险和无效运行条件；以及
- 开放决策和假设。

向用户展示完整的任务规范和世界技能更改。解释世界技能中已有的内容、此任务添加或更正的内容以及仅在 `Task.md` 中保留的内容。通过相同的来回方式完善两者。仅在明确批准后，才标记任务规范为已批准。仅在用户审查它们之后，才将世界技能更改视为已接受。如果用户要求无暂停的端到端构建，请继续使用代理审查的 `Status: Draft` 并将世界技能更改标记为未审查。

如果实施改变了请求、可见信息、材料环境行为或评分边界，请更新 `Task.md` 并显示更改。将其状态重置为 `Draft`。显示差异并在将其设置为 `Approved` 之前要求明确的重新批准。

## 4. 应用 Spec2Task

遵循 [任务实现](references/task-implementation.md)。它提供了构建顺序，并将每个决策路由到环境、合成数据、验证器、Harbor 和校准参考。

对于现有项目，使用其固定的或支持 Harbor 版本。否则，使用安装的支持版本并记录它。仅在获得用户批准并说明兼容性原因时才升级。使用安装的 CLI 帮助作为命令合同。

在评分模型运行之前：

1. 除非用户已经授权该运行计划，否则与用户确认模型、试验次数、裁判、超时和最大预期成本。
2. 完成 [Harbor](references/harbor.md) 中的包审计。确认此精确任务所需的所有文件、入口点、路径、权限、配置值、挂载、服务和奖励输出是否存在并可通过 Harbor 工作。确认隐藏的任务、验证器、解决方案和秘密材料不存在于代理可见的镜像和工作区中。
3. 按照适合环境的方式检查设置和试验隔离。一个新鲜容器或工作树可以通过替换提供隔离。一个可重用的可变服务需要一个检查重置。不可变冻结数据只需要一个检查加载。参见 [任务实现](references/task-implementation.md)。
4. 执行任务依赖的每个操作。
5. 当存在时，运行参考路径。
6. 使用一个清晰的有效结果、一个有效的替代方案、一个现实的错误结果、一个捷径、一个禁止的附带更改以及缺失或损坏的证据来测试验证器。
7. 确认每个完成的验证器路径都写入有效的奖励和有用的证据，而不会暴露隐藏真相或秘密。

## 5. 运行和审计

通过 Harbor 运行实际的 Harness。读取完整的轨迹，而不仅仅是奖励。检查：

- 消息、模型调用、工具调用、结果、重试和错误；
- 初始和最终环境状态和外部效果；
- 服务、设置、就绪、重置和清理证据；
- 每个验证器标准、其证据、决策和错误；以及
- 解析的 Harness、模型、环境和裁判配置。

将每个不成功的运行分类为代理能力故障、缺失信息、Harness 缺陷、环境缺陷、验证器错误拒绝、验证器错误接受、泄漏或基础设施故障。在使用分数之前修复非代理故障。

模型比较是一个可选的校准策略，而不是完成规则。当它将回答一个真实的不确定性时，比较一个较弱的模型、目标模型或一个较弱的模型并重复试验，当行为可变时。阅读每个选定的跟踪记录。对比可以揭示不明确的输入、脆弱的设置、泄漏、捷径或奖励黑客。通过率和模型排序不能证明任务质量。

读取 [校准](references/calibration.md) 了解完整的审计方法。

## 6. 调整项目世界知识

在任务设计、实施和审计过程中使用 [世界知识](references/world-knowledge.md)。当工作提供将帮助另一个任务的证据时，添加或更正项目特定知识。这可能包括任务模式、环境方法、数据创建、验证器证据、运行程序、脚本、资产和示例。

在审计之后，使世界技能与完成的任务证明的内容一致。向用户展示：

- 提出的可重用知识；
- 支持它的证据；
- 另一个任务将如何使用它；
- 它应该在哪里；
- 以及什么仍然特定于已完成的任务。

删除或缩小任务证伪的想法。如果用户要求无暂停的自主端到端更新，请进行最小的支持更新，在最终审查中显示它，并且不要暗示人类批准了泛化。

最初只创建 `SKILL.md`。仅在其实际内容证明它们时才添加 `references/`、`scripts/`、`assets/` 或 `tests/`。

将已完成任务的请求、焦点状态、预期结果和精确标准保留在其相邻的 `Task.md` 中。不要复制已经在技能中明确的广泛指导。记录该指导的项目特定适应。

## 7. 重复

使用任务二和任务三来测试世界技能。检查它是否减少了重新发现、改进了任务规范、保留了重要关系、重用了已证明的操作或防止了已知的验证器缺陷。纠正缺失、过时或过于宽泛的规则。

当几个实质性不同的任务已经锻炼了共享知识，并且构建和验证方法清晰时，下一周期可以提出几个独立的任务规范：

1. 挖掘新的仓库、跟踪记录和人类证据。
2. 使用世界技能生成不同的任务规范。
3. 让人类审查规范。
4. 并行构建独立的已批准任务。
5. 单独审计每个任务。
6. 仅使用可重用的更正更新世界知识。

随着生产行为、用户优先级、代理和模型的变化，继续此循环。

## 依赖项、访问权限和安全

映射所需的系统、数据、角色、网络需求和安全设置方法。永远不要读取、打印、复制、存储或要求人类粘贴秘密值。告诉人类需要什么依赖项，为什么需要它，以及项目如何期望提供访问权限。默认为受控的本地、冻结或模拟依赖项。在评估期间永远不要写入生产。将访问权限、启动、重置、超时、裁判和验证器故障视为无效运行，而不是失败的代理工作。

## 仅在以下情况下完成

- `Task.md` 与构建的指令、环境和验证器匹配。
- 任务可以从代理可见或通常可发现的信息中解决。
- 环境可靠启动并以适当的方式通过替换、重置或不可变状态隔离试验，而不会泄漏隐藏真相。
- 有效和无效的验证器案例按预期行为。
- 至少读取了一个完整的真实 Harness 运行。
- 非代理故障已被修复或报告为未解决的限制。
- 当使用时，模型比较包括跟踪记录审查，而不仅仅是通过率。
- 项目世界技能已使用任务规范创建或更新，在处理过程中进行了审查，并与最终证据进行了协调。
- 用户收到了任务路径、运行命令、结果、证据和剩余限制。
