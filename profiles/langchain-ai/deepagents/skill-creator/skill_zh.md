# 技能创建器

### Deepagents 技能位置

deepagents CLI 从五个来源加载技能，按最低到最高优先级列出：

| # | 目录 | 范围 | 备注 |
|---|-----------|-------|-------|
| 0 | `<package>/built_in_skills/` | 内置 | 随 deepagents CLI 提供 |
| 1 | `$DEEPAGENTS_HOME/<agent>/skills/` | 用户（deepagents 别名） | `deepagents skills create` 的默认位置 |
| 2 | `~/.agents/skills/` | 用户 | 在代理工具之间共享 |
| 3 | `.deepagents/skills/` | 项目（deepagents 别名） | `deepagents skills create --project` 的默认位置 |
| 4 | `.agents/skills/` | 项目 | 在代理工具之间共享 |

`<agent>` 是代理配置名称（默认：`agent`）。当两个目录包含同名的技能时，优先级高的版本将生效——项目技能会覆盖用户技能，任何用户或项目技能都会覆盖内置技能。

示例目录布局：

```
$DEEPAGENTS_HOME/agent/skills/     # 用户技能（最低优先级）
├── skill-name-1/
│   └── SKILL.md
└── ...

<project-root>/.deepagents/skills/   # 项目技能（较高优先级）
├── skill-name-2/
│   └── SKILL.md
└── ...
```

## 核心原则

### 简洁至上

上下文窗口是一种公共资源。技能与代理需要的其他所有内容共享上下文窗口：系统提示、对话历史、其他技能的元数据以及实际的用户请求。

**默认假设：代理已经非常强大。** 只添加代理尚未拥有的上下文。挑战每一项信息：“代理真的需要这个解释吗？”以及“这段文字是否值得其 token 成本？”

优先选择简洁的示例而不是冗长的解释。

### 设置适当的自由度

根据任务的易碎性和可变性匹配具体的详细程度：

**高自由度（基于文本的指令）**： 当有多种方法有效、决策依赖于上下文或启发式方法指导方法时使用。

**中等自由度（伪代码或带参数的脚本）**： 当存在首选模式、可以接受一些变化或配置影响行为时使用。

**低自由度（特定脚本、少量参数）**： 当操作易碎且易出错、一致性至关重要或必须遵循特定顺序时使用。

将代理视为探索路径：狭窄的桥梁需要特定的护栏（低自由度），而开阔的田野允许许多路线（高自由度）。

### 技能的构成

每个技能都由一个必需的 SKILL.md 文件和可选的捆绑资源组成：

```
skill-name/
├── SKILL.md (必需)
│   ├── YAML 前置元数据 (必需)
│   │   ├── name: (必需)
│   │   └── description: (必需)
│   └── Markdown 指令 (必需)
└── 捆绑资源 (可选)
    ├── scripts/          - 可执行代码 (Python/Bash 等)
    ├── references/       - 意图按需加载到上下文中的文档
    └── assets/           - 用于输出的文件 (模板、图标、字体等)
```

#### SKILL.md (必需)

每个 SKILL.md 包含以下内容：

- **前置元数据** (YAML)：包含 `name` 和 `description` 字段。代理仅通过这些字段来确定何时使用技能，因此必须清晰全面地描述技能是什么以及何时使用它。
- **正文** (Markdown)：使用技能的指令和指导。仅在技能触发后（如果触发的话）才加载。

#### 捆绑资源 (可选)

##### 脚本 (`scripts/`)

可执行代码 (Python/Bash 等) 用于需要确定性可靠性或反复重写的任务。

- **包含时机**：当相同的代码被反复重写或需要确定性可靠性时
- **示例**：`scripts/rotate_pdf.py` 用于 PDF 旋转任务
- **优点**：token 效率、确定性、可能无需加载到上下文即可执行
- **注意**：脚本可能仍需要被代理读取以进行补丁或环境特定调整

##### 参考文献 (`references/`)

意图按需加载到上下文中的文档和参考材料，以指导代理的流程和思考。

- **包含时机**：对于代理在处理时应参考的文档
- **示例**：`references/finance.md` 用于财务模式、`references/mnda.md` 用于公司 NDA 模板、`references/policies.md` 用于公司政策、`references/api_docs.md` 用于 API 规范
- **用例**：数据库模式、API 文档、领域知识、公司政策、详细的流程指南
- **优点**：使 SKILL.md 精简，仅在代理确定需要时加载
- **最佳实践**：如果文件很大（>10k 字），请在 SKILL.md 中包含搜索模式
- **避免重复**：信息应存在于 SKILL.md 或参考文献文件中，而不是两者都有。除非它真正是技能的核心，否则优先选择参考文献文件以保持 SKILL.md 精简，同时使信息可发现而不占用上下文窗口。将仅保留必要的程序性指令和工作流指导在 SKILL.md 中；将详细的参考材料、模式示例移至参考文献文件。

##### 资产 (`assets/`)

不意图加载到上下文中的文件，而是用于代理生成的输出中的文件。

- **包含时机**：当技能需要用于最终输出的文件时
- **示例**：`assets/logo.png` 用于品牌资产、`assets/slides.pptx` 用于 PowerPoint 模板、`assets/frontend-template/` 用于 HTML/React 模板、`assets/font.ttf` 用于排版
- **用例**：模板、图像、图标、基础代码、字体、被复制或修改的示例文档
- **优点**：将输出资源与文档分离，使代理能够在不加载它们到上下文的情况下使用文件

#### 不应包含在技能中的内容

技能应仅包含直接支持其功能的基本文件。不要创建不必要的文档或辅助文件，包括：

- README.md
- INSTALLATION_GUIDE.md
- QUICK_REFERENCE.md
- CHANGELOG.md
- 等

技能应仅包含 AI 代理执行工作所需的必要信息。它不应包含关于创建它的过程、设置和测试程序、面向用户的文档等辅助上下文。创建额外的文档文件只会增加混乱和困惑。

### 逐步披露设计原则

技能使用三级加载系统来有效管理上下文：

1. **元数据（名称 + 描述）** - 始终在上下文中 (~100 字)
2. **SKILL.md 正文** - 当技能触发时 (<5k 字)
3. **捆绑资源** - 根据代理的需要 (无限制，因为脚本可以在不加载到上下文窗口的情况下执行)

#### 逐步披露模式

将 SKILL.md 正文保持在要点并少于 500 行，以最小化上下文膨胀。代理将静默地跳过超过 10 MB 的 SKILL.md 文件。当内容接近行数限制时，将其拆分到单独的文件中。当将内容拆分到其他文件中时，非常重要的一点是从 SKILL.md 中引用它们，并清楚地描述何时读取它们，以确保技能的读者知道它们的存在以及何时使用它们。

**关键原则**：当技能支持多个变体、框架或选项时，仅在 SKILL.md 中保留核心工作流和选择指导。将变体特定细节（模式、示例、配置）移至单独的参考文件。

**模式 1：高级指南与参考**

```markdown
# PDF 处理

## 快速入门

使用 pdfplumber 提取文本：
[code example]

## 高级功能

- **表单填写**：查看 [FORMS.md](FORMS.md) 获取完整指南
- **API 参考**：查看 [REFERENCE.md](REFERENCE.md) 获取所有方法
- **示例**：查看 [EXAMPLES.md](EXAMPLES.md) 获取常见模式
```

代理仅在需要时加载 FORMS.md、REFERENCE.md 或 EXAMPLES.md。

**模式 2：按领域组织**

对于具有多个领域的技能，按领域组织内容以避免加载不相关的上下文：

```
bigquery-skill/
├── SKILL.md (概述和导航)
└── reference/
    ├── finance.md (收入、计费指标)
    ├── sales.md (机会、管道)
    ├── product.md (API 使用、功能)
    └── marketing.md (活动、归因)
```

当用户询问销售指标时，代理仅读取 sales.md。

类似地，对于支持多个框架或变体的技能，按变体组织：

```
cloud-deploy/
├── SKILL.md (工作流 + 提供商选择)
└── references/
    ├── aws.md (AWS 部署模式)
    ├── gcp.md (GCP 部署模式)
    └── azure.md (Azure 部署模式)
```

当用户选择 AWS 时，代理仅读取 aws.md。

**模式 3：条件细节**

显示基本内容，链接到高级内容：

```markdown
# DOCX 处理

## 创建文档

使用 docx-js 创建新文档。查看 [DOCX-JS.md](DOCX-JS.md)。

## 编辑文档

对于简单编辑，直接修改 XML。

**对于跟踪更改**：查看 [REDLINING.md](REDLINING.md)
**对于 OOXML 详细信息**：查看 [OOXML.md](OOXML.md)
```

代理仅在需要这些功能时读取 REDLINING.md 或 OOXML.md。

**重要指南**：

- **避免深层嵌套引用** - 从 SKILL.md 保留一级深度的引用。所有参考文件应直接从 SKILL.md 链接。
- **结构化较长的参考文件** - 对于超过 100 行的文件，在顶部包含目录以便代理在预览时查看完整范围。

## 技能创建过程

技能创建涉及以下步骤：

1. 通过具体示例理解技能
2. 规划可重用的技能内容（脚本、参考文献、资产）
3. 初始化技能（运行 init_skill.py）
4. 编辑技能（实现资源并编写 SKILL.md）
5. 验证技能（运行 quick_validate.py）
6. 根据实际使用情况进行迭代

按顺序遵循这些步骤，除非有明确理由不适用，否则不要跳过。

### 步骤 1：通过具体示例理解技能

仅当技能的使用模式已经非常清楚时才跳过此步骤。即使在与现有技能合作时，它仍然很有价值。

要创建一个有效的技能，必须清楚地理解技能将如何被使用的具体示例。这种理解可以来自直接的用户示例或经过用户反馈验证的生成示例。

例如，在构建图像编辑技能时，相关的问题包括：

- “图像编辑技能应支持哪些功能？编辑、旋转、其他？”
- “你能给出一些使用此技能的示例吗？”
- “我可以想象用户会要求移除图像中的红眼或旋转图像。你想象此技能的其他使用方式是什么？”
- “用户会说些什么会触发此技能？”

为了避免让用户感到不知所措，避免在单个消息中问太多问题。从最重要的问题开始，并根据需要跟进以提高有效性。

当对技能应支持的功能有清晰的认识时，此步骤即告完成。

### 步骤 2：规划可重用的技能内容

要将具体示例转换为有效的技能，通过以下方式分析每个示例：

1. 考虑如何从头开始执行示例
2. 确定在重复执行这些工作流程时哪些脚本、参考文献和资产会很有帮助

示例：在构建 `pdf-editor` 技能以处理类似“帮助我旋转 PDF”的查询时，分析显示：

1. 旋转 PDF 需要每次重写相同的代码
2. `scripts/rotate_pdf.py` 脚本将有助于存储在技能中

示例：在为类似“为我构建一个待办事项应用”或“为我构建一个跟踪我的步骤的仪表板”的查询设计 `frontend-webapp-builder` 技能时，分析显示：

1. 编写前端 Web 应用需要每次使用相同的样板 HTML/React
2. 包含样板 HTML/React 项目文件 `assets/hello-world/` 模板将有助于存储在技能中

示例：在构建 `big-query` 技能以处理类似“今天有多少用户登录？”的查询时，分析显示：

1. 查询 BigQuery 需要每次重新发现表模式关系
2. 文档化表模式的 `references/schema.md` 文件将有助于存储在技能中

要建立技能的内容，分析每个具体示例以创建可重用资源列表：脚本、参考文献和资产。

### 步骤 3：初始化技能

此时，是实际创建技能的时候了。

仅当正在开发的技能已经存在，并且需要迭代或打包时才跳过此步骤。在这种情况下，请继续到下一步。

创建新技能有两种方法：

#### 选项 A：`init_skill.py`（推荐用于丰富的技能）

从头开始创建新技能时，运行 `init_skill.py` 脚本。该脚本生成一个新的模板技能目录，自动包含技能所需的一切，使技能创建过程更加高效和可靠。

用法：

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

对于 deepagents CLI，使用上面“Deepagents 技能位置”中列出的任何技能目录：

```bash
# 用户技能（默认）
scripts/init_skill.py <skill-name> --path "${DEEPAGENTS_HOME:-$HOME/.deepagents}/agent/skills"

# 项目技能
scripts/init_skill.py <skill-name> --path .deepagents/skills
```

该脚本：

- 在指定路径创建技能目录
- 生成带有正确前置元数据和 TODO 占位符的 SKILL.md 模板
- 创建示例资源目录：`scripts/`、`references/` 和 `assets/`
- 在每个目录中添加示例文件，可以自定义或删除

初始化后，根据需要自定义或删除生成的 SKILL.md 和示例文件。

#### 选项 B：`deepagents skills create`（快速启动）

内置 CLI 命令创建一个仅包含 `SKILL.md` 模板的技能——没有资源目录。用于只需要指令而不需要捆绑脚本、参考文献或资产的简单技能。

```bash
# 在用户技能目录中创建
deepagents skills create <skill-name>

# 在项目技能目录中创建
deepagents skills create <skill-name> --project
```

当技能将包含捆绑资源（`scripts/`、`references/`、`assets/`）时，使用 `init_skill.py`。使用 `deepagents skills create` 获取快速、最小的起点。

### 步骤 4：编辑技能

在编辑（新生成的或现有的）技能时，请记住技能是为代理使用的。包含对代理有益且非显而易见的信息。考虑哪些程序性知识、特定领域的细节或可重用资产将帮助代理更有效地执行这些任务。

#### 学习经过验证的设计模式

参考上述“逐步披露设计原则”和“核心原则”部分中关于顺序工作流、条件逻辑和输出格式化的既定模式。

#### 从可重用的技能内容开始

开始实施时，从上面确定的可重用资源开始：`scripts/`、`references/` 和 `assets/` 文件。注意此步骤可能需要用户输入。例如，在实现 `brand-guidelines` 技能时，用户可能需要提供品牌资产或模板存储在 `assets/`，或文档存储在 `references/`。

添加的脚本必须通过实际运行它们来测试，以确保没有错误并且输出与预期匹配。如果有很多类似的脚本，只需要测试代表性的样本以确保它们都工作，同时平衡完成时间。

任何不需要的示例文件和目录都应删除。初始化脚本在 `scripts/`、`references/` 和 `assets/` 中创建示例文件以演示结构，但大多数技能不需要所有这些文件。

#### 更新 SKILL.md

**编写指南**：始终使用祈使/不定式形式。

##### 前置元数据

使用 YAML 前置元数据编写 `name` 和 `description`：

- `name`：技能名称
- `description`：这是技能的主要触发机制，并帮助代理理解何时使用技能。
  - 包含技能做什么以及何时使用它的特定触发/上下文。
  - 包含所有“何时使用”信息——不在正文。正文仅在触发后才加载，因此正文中的“何时使用此技能”部分对代理没有帮助。
  - `docx` 技能的描述示例： “全面的文档创建、编辑和分析，支持跟踪更改、评论、格式保留和文本提取。用于处理专业文档（.docx 文件）时： (1) 创建新文档、 (2) 修改或编辑内容、 (3) 处理跟踪更改、 (4) 添加评论，或任何其他文档任务”

YAML 前置元数据中允许的其他字段是 Agent Skills 规范中的可选属性：`license`、`compatibility`、`allowed-tools` 和 `metadata`。不要包含这些字段之外的任何字段。

##### 正文

编写使用技能及其捆绑资源的指令。

### 步骤 5：验证技能

技能开发完成后，验证它以确保它满足所有要求：

```bash
scripts/quick_validate.py <path/to/skill-folder>
```

验证脚本检查：

- YAML 前置元数据格式和必需字段
- 技能命名约定（Unicode 小写字母数字，用连字符分隔，最多 64 个字符）
- 描述完整性（无尖括号，最多 1024 个字符）
- 必需字段：`name` 和 `description`
- 仅允许的前置元数据属性：`name`、`description`、`license`、`compatibility`、`allowed-tools`、`metadata`

如果验证失败，请修复报告的错误并再次运行验证命令。

### 步骤 6：迭代

测试技能后，用户可能会要求改进。这通常发生在使用技能后，对技能的表现有清晰的上下文。

**迭代工作流程**：

1. 在实际任务中使用技能
2. 注意遇到的困难或低效
3. 确定应如何更新 SKILL.md 或捆绑资源
4. 实施更改并再次测试
