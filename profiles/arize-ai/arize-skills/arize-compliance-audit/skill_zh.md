# Arize 合规性审计技能

当用户希望对其 AI 代理或 LLM 应用进行监管合规性审计时，请使用此技能。该技能扫描代码库以查找合规性差距，对照 Arize 仪器化记录审计轨迹覆盖情况，并生成定制的检查清单，可选择性提供修复建议。

**触发条件：** "审计我的应用以进行合规性"、"欧盟 AI 法要求"、"NIST AI RMF 检查清单"、"人工智能 GDPR"、"我的 AI 应用是否合规"、"合规性检查清单"、"监管审计"、"ISO 42001"、"AI 管理系统"、"AIMS 认证"。

## 免责声明

**在执行任何操作之前，请向用户逐字呈现此免责声明：**

---

> ⚠️ **法律免责声明**
>
> 此审计仅用于**指导**，不构成法律建议或完整的合规性评估。它根据公开可用的监管框架识别常见的技术模式和差距，但无法评估贵组织的具体法律义务、合同承诺、数据处理协议或操作流程。
>
> **不要将此输出作为合格法律顾问的替代品。** 监管合规性是一个复杂、地域特定且依赖于具体事实的判断。始终聘请合格律师或合规专家进行具有约束力的评估。

---

## 核心原则

- **优先检查而非修改** — 在建议更改之前理解代码库。
- **注重实践而非法律** — 生成可由开发者执行的项目，而非法律意见。
- **根据地域和用例进行定制** — 聊天机器人的义务与招聘工具不同。不要堆砌整个监管框架。
- **交叉引用仪器化记录** — 合规性需要审计轨迹；检查 Arize 跟踪是否捕获了监管机构期望的内容。
- **始终提供修复建议并确认** — 在呈现检查清单后，提供实施特定修复建议，但未经明确用户确认，绝不修改代码。
- **保持输出简洁并专注于生产** — 除非用户要求，否则不要生成额外的文档或摘要文件。
- **绝不嵌入字面凭证值** — 始终引用环境变量。绝不要求用户将秘密粘贴到编码代理聊天中。

## 第一阶段：框架选择和用例

在扫描代码之前，确定适用的合规性框架。

### 第一步 — 框架选择

使用 `AskUserQuestion` 工具询问用户哪些框架适用。**不要推断或自动选择** — 始终明确询问。

询问：

```
此审计应涵盖哪些合规性框架？
请选择所有适用的项（用数字回复，例如 "1, 3"）：

1. 欧盟框架 — 欧盟 AI 法、GPAI 实践守则、GDPR
   （如果最终用户或数据主体位于欧盟，则选择此项）

2. 美国框架 — NIST AI RMF、州法律（科罗拉多州 AI 法、纽约市 LL144）、HIPAA
   （如果在美国运营，则选择此项）

3. ISO 42001 — 国际 AI 管理系统标准
   （如果正在追求 ISO 42001 认证、全球运营或希望获得国际认可的基准，则选择此项）

您可以任意组合选择。如有不确定，请选择所有看似相关的项，我们可以在审计过程中进行缩小范围。
```

根据选择：
- **1 被选中** — 欧盟 AI 法、GPAI 实践守则、GDPR 适用。参见 [references/eu-ai-act-gpai.md](references/eu-ai-act-gpai.md)。
- **2 被选中** — NIST AI RMF、科罗拉多州 AI 法、纽约市 LL144、HIPAA 可能适用。参见 [references/us-ai-compliance.md](references/us-ai-compliance.md)。
- **3 被选中** — ISO 42001 AIMS 控制适用。参见 [references/iso-42001.md](references/iso-42001.md)。注意：ISO 42001 是一个组织管理系统 — 审计将涵盖技术上可审计的控制；纯粹的组织条款（领导力审查、内部审计）将单独标记。
- **多个被选中** — 所有选定的框架适用；审计涵盖要求的并集，在框架重叠时进行交叉引用。

### 第二步 — 确定用例类别

使用 `AskUserQuestion` 工具询问：**您的 AI 应用做什么？**

- **通用聊天机器人/助手** — 有限风险（欧盟）、一般义务（美国）
- **招聘/人力资源** — 高风险（欧盟第 6 条、附件 III）；科罗拉多州 AI 法适用；如果位于纽约，则适用纽约市 LL144
- **医疗保健** — 高风险（欧盟）；如果处理 PHI，则适用 HIPAA
- **信贷/金融** — 高风险（欧盟）；适用科罗拉多州 AI 法
- **教育** — 高风险（欧盟）
- **内容生成** — 有限风险（欧盟第 50 条透明度）；一般义务（美国）
- **GPAI 模型提供者** — GPAI 实践守则适用（欧盟）

### 第三步 — 确定风险等级

根据用例和选定的框架：
- **欧盟被选中**：根据 [references/eu-ai-act-gpai.md](references/eu-ai-act-gpai.md) 将其分类为不可接受/高/有限/最低。
- **美国被选中**：根据科罗拉多州 AI 法将其分类为高风险（具有后果性决策）或一般。
- **ISO 42001 被选中**：ISO 42001 中没有正式的风险等级分类，但请说明系统是否高风险（这会提高影响评估和偏差控制的优先级）。

### 第一阶段输出

呈现简要摘要：

```
选定的框架：{欧盟 / 美国 / ISO 42001 / 组合}
用例：            {类别}
风险等级：           {如果适用，则显示欧盟等级} / {如果适用，则显示美国等级}
适用：          {具体法规和标准的列表}
ISO 42001 注意：      {如果选中} 审计仅涵盖技术上可审计的控制；
                     组织条款将单独标记，但不会进行代码审计。
```

然后直接进入第二阶段。

## 第二阶段：代码库审计（只读）

**在此阶段期间，不要编写任何代码或创建任何文件。**

系统性地扫描代码库，跨七个领域查找合规性证据和差距。对于每个领域，运行列出的搜索并记录结果。

### A. 透明度和披露

**查找内容：**
- 用户界面字符串披露 AI 参与情况：在 UI 模板、API 响应和用户界面代码中搜索术语，如 `AI`、`人工智能`、`自动化`、`机器人`、`机器学习`、`由...生成`、`由...提供`
- 内容标记：AI 生成的输出（文本、图像、音频）上的标记
- 代码库中引用的服务条款、隐私政策

**担忧信号：** 用户界面代码中缺少任何 AI 披露，特别是如果应用程序生成内容或做出建议。

### B. 数据保护和隐私

**查找内容：**
- 代码中的 PII 字段名称：`email`、`phone`、`ssn`、`social_security`、`date_of_birth`、`address`、`name` 在提示、上下文或检索到的文档中
- 跟踪跨度属性中的 PII：检查 `input.value` 或 `output.value` 是否可能包含发送到 Arize 而未进行屏蔽的个人数据
- 同意机制：`consent`、`opt-in`、`opt-out`、`gdpr`、`ccpa` 引用
- DPIA 或隐私评估引用
- 数据保留和删除处理程序
- 数据主体权利：`right_to_access`、`right_to_erasure`、`data_subject_request`、`data_protection_officer`

### C. 安全

**查找内容：**
- 提示注入防御：输入验证、护栏库（`guardrails-ai`、`nemo-guardrails`、`rebuff`、`lakera`）、内容过滤、系统提示保护
- 数据丢失预防：在返回用户之前扫描输出，检测敏感数据
- 工具/函数调用控制：权限边界、允许列表、工具执行的沙盒化
- AI 端点的速率限制和身份验证
- 硬编码凭证：`api_key`、`secret`、`password`、`token` 字面值在源文件中（不是环境变量引用）

### D. 测试和评估

**查找内容：**
- 偏差和公平性测试：对人口统计均等性、影响比率、公平性指标的引用
- 红队测试或对抗性测试套件：提示注入测试、越狱测试
- 评估框架：Arize 评估器、自定义评估脚本、基于 `pytest` 的评估、实验基础设施
- A/B 测试或模型比较基础设施

### E. 文档

**查找内容：**
- 模型卡：`MODEL_CARD.md`、`model_card.json`、`model_card.yaml` 或类似文件
- 系统架构文档
- 提示和模型更新的变更日志或版本跟踪
- 事件响应文档

### F. 监控和可观察性

**查找内容：**
- Arize 跟踪设置：`arize-otel`、`register()`、`TracerProvider`、`opentelemetry`、`openinference` 导入
- 如果跟踪存在，检查覆盖范围：
  - 所有 LLM 调用都被跟踪（而不仅仅是部分）
  - 会话 ID 以支持对话连续性
  - 用户 ID 以支持数据主体请求
  - 错误跟踪和异常跨度
- 报警和漂移检测配置
- 跟踪保留配置

### G. 供应商管理

**查找内容：**
- 第三方 AI API 使用：OpenAI、Anthropic、Google、Azure、Bedrock、Cohere 导入或客户端实例化
- 模型版本控制：是否固定特定模型版本（例如，`gpt-4-0613`）或使用 `latest` / 未版本化标识符
- 供应商之间的回退和故障转移逻辑

### 第二阶段输出

呈现两份报告：

**第一部分 — 摘要表格**

| 领域 | 找到的证据 | 识别的差距 | 评级 |
|---|---|---|---|
| A. 透明度 | {发现} | {差距} | 合规 / 部分合规 / 不合规 / 不适用 |
| B. 数据保护 | {发现} | {差距} | ... |
| C. 安全 | {发现} | {差距} | ... |
| D. 测试 | {发现} | {差距} | ... |
| E. 文档 | {发现} | {差距} | ... |
| F. 监控 | {发现} | {差距} | ... |
| G. 供应商管理 | {发现} | {差距} | ... |

**第二部分 — 差距详情（对每个不合规或部分合规领域都必需）**

对于每个评为不合规或部分合规的领域，编写一个专门的子部分，包括：

1. **确切的代码路径** — 文件路径、行号和显示差距存在的相关代码片段。不要释义；引用实际代码。
2. **在特定应用程序中的重要性** — 解释此代码库的具体风险（例如，哪些工具可能被滥用，哪些数据流被暴露，攻击者或监管机构会看到什么）。
3. **缺失的内容** — 对应存在但不存在控制或代码的精确描述（例如，“一个在 OTLP 导出器触发之前对 `user_email` 进行哈希处理的跨度属性处理器”，而不是“添加 PII 屏蔽”）。

每个不合规/部分合规领域至少有一个子部分。不要省略此部分 — 它是工程团队审计的主要价值所在。

然后直接进入第三阶段。

## 第三阶段：合规性检查清单

使用第一阶段发现和 [references/compliance-checklist-template.md](references/compliance-checklist-template.md) 中的模板，生成**定制的合规性检查清单**。

### 检查清单生成规则

1. **仅包含相关部分。** 如果用户仅限美国，则跳过 GDPR 特定项。如果不是医疗保健，则跳过 HIPAA。如果不在纽约招聘，则跳过 LL144。
2. **标记第一阶段的项。** 找到证据的项：标记为 `Compliant`。存在差距的项：标记为 `Non-compliant` 并提供具体的修复建议。
3. **正确排序。** 关键 = 执法风险或系统禁止。高 = 法规要求。中 = 框架建议。低 = 最佳实践。
4. **修复建议要具体。** 不要说“实施输入验证”，而要说“添加一个护栏库（如 `guardrails-ai`）来验证 LLM 输入和输出，以符合您的内容策略”。
5. **包含仪器化交叉引用表**。如果未设置 Arize 跟踪，则将此标记为关键差距 — 审计轨迹由欧盟第 12 条和 NIST MAN-2.1 要求。

### 最终报告

呈现一个包含四个部分的单一综合报告：

**第一部分 — 审计范围（第一阶段摘要）**
- 选定的框架、用例、风险等级、适用法规

**第二部分 — 代码库发现（第一阶段摘要表格）**
- 领域表格（A–G）及其证据、差距和评级

**第三部分 — 差距详情（第一阶段扩展）**
- 每个不合规或部分合规领域一个子部分，每个子部分包含：确切的文件路径和行号、引用的代码片段、特定应用程序风险解释、缺失内容的精确描述。此部分是强制性的 — 永远不要省略它。

**第四部分 — 合规性检查清单（第三阶段）**
- 定制的检查清单，包括状态和修复建议、仪器化交叉引用表、优先级总结和推荐后续步骤

当用户要求报告文件时，将所有四个部分写入 `/tmp/<app-name>-compliance-audit-<YYYY-MM-DD>.md` 中的单个 markdown 文件。

在呈现报告后，提供第三阶段修复建议。

## 第三阶段：修复建议（可选）

在呈现检查清单后，提供实施特定修复建议。**始终使用 `AskUserQuestion` 工具在做出任何更改之前进行确认。**

### 修复建议类别

**添加依赖项** — 提供安装：
- 输入/输出验证的护栏库（例如，`guardrails-ai`、`nemo-guardrails`）
- PII 检测/屏蔽包（例如，`presidio-analyzer`、`scrubadub`）
- 内容安全分类器

**插入代码** — 提供添加：
- 用户界面输出中的 AI 披露字符串（模板、API 响应）
- 在导出到 Arize 之前对跨度属性进行 PII 屏蔽
- AI 端点的输入验证/清理
- 用于数据主体请求支持的跟踪跨度上的用户 ID 属性

**创建文档模板** — 提供生成：
- 模型卡模板（带有标准部分的 markdown 文件）
- 事件响应计划模板
- 数据处理记录模板

**配置监控** — 通过相关技能设置：
- Arize 评估器以进行偏差检测和内容安全（通过 `arize-evaluator` 技能）
- 用于审计轨迹覆盖的跟踪（通过 `arize-instrumentation` 技能）

### 修复建议规则

- 将每个修复建议呈现为**独立的、可确认的操作**。永远不要批量应用更改。
- 显示将更改的确切内容（文件、代码差异概念），然后使用 `AskUserQuestion` 工具在应用之前获取确认。
- 遵循现有的代码风格和项目约定。
- 永远不要嵌入凭证 — 始终使用环境变量。
- 测试更改后应用程序是否仍然可以构建。

## 技能编排

当第一阶段或第二阶段的差距需要其他 Arize 技能的功能时，提供调用它们。**始终使用 `AskUserQuestion` 工具在调用另一个技能之前询问，并解释其与合规性差距的相关性。**

| 差距 | 调用技能 | 原因 |
|---|---|---|
| 无跟踪 / 审计轨迹不完整 | `arize-instrumentation` | 欧盟第 12 条和 NIST MAN-2.1 要求事件记录；Arize 跟踪提供此功能 |
| 无偏差或安全评估 | `arize-evaluator` | 创建 LLM 作为法官的评估器，用于公平性、内容安全或质量监控 |
| 需要跟踪导出以进行合规性证据 | `arize-trace` | 导出跨度以用于监管文档或事件调查 |
| 需要人工审核高风险决策 | `arize-annotation` | 根据欧盟第 14 条设置注释队列，进行人工监督 |
| 需要深度链接以共享合规性证据 | `arize-link` | 生成特定跟踪、跨度或评估的 URL，供利益相关者审查 |

## 仪器化交叉引用

如果已设置 Arize 跟踪，请验证其是否满足合规性要求：

| 合规性需求 | 需要的跟踪数据 | 检查内容 |
|---|---|---|
| AI 决策的审计轨迹 | 所有 LLM 跨度及其输入/输出 | 验证所有 LLM 客户端调用都被跟踪，而不仅仅是部分 |
| 数据主体访问请求 | 跨度上的用户 ID 属性 | 检查 `user.id` 或自定义用户标识符属性 |
| 跟踪中的 PII | 跨度中的敏感数据 | 检查 PII 是否未经屏蔽地通过 — 如果是，则标记 |
| 事件调查 | 带有完整上下文的错误跨度 | 检查异常跟踪和跨度上的错误状态 |
| 保留要求 | 跟踪数据保留所需时间段 | 欧盟：适当期限（高风险至少 6 个月）；HIPAA：6 年 |
| 偏差监控 | 人口统计或组属性 | 检查支持公平性分析的元数据属性 |

如果 Arize 跟踪**未**设置，这是一个重要的合规性差距。提供："我运行 `arize-instrumentation` 技能以设置审计轨迹跟踪吗？监管框架（欧盟 AI 法第 12 条、NIST AI RMF MAN-2.1）要求 AI 系统的事件记录。"
