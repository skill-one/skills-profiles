# 创建或现代化技能

## 使用场景

在 `skills/` 下创建新技能时，或现有技能需要材料创作刷新时激活。

典型触发条件：
- "为...创建技能"
- "搭建 `skills/<name>/SKILL.md`"
- "将此工作流转换为可重用的技能"
- "改进此技能的元数据和触发提示"
- "使此技能更易于发现"
- "为技能设置引用/资源/辅助代理"

隐式触发条件：
- 重复任务持续需要相同的指令或安全边界
- 现有技能过于模糊、过长、路由不良或缺少结构
- 用户希望的是可重用的工作流包，而不是一次性提示

## 不适用场景

- 在 `skills/` 外编辑产品或应用程序代码
- 仅需微小拼写修改且无需创作工作流帮助的编辑
- 适合用文档、模板或脚本解决，无需可安装技能的请求
- 大规模无关的仓库重构
- 具有破坏性的命令或隐藏的网络自动化

## 必须输入

如果缺少必须输入，请先提出简洁的针对性问题。
使用 `assets/follow-up-questions.md` 作为默认问题库。

### 必填项

在起草前收集：
- 这是否为新建技能、更新或根本不是技能
- 目标仓库路径和预期技能目录
- 基础技能名称（在任何前缀/命名空间之前使用连字符命名法）
- 最终技能名称（使用连字符命名法；如果仓库有不同约定，默认为 `custom-<base-skill-name>`）
- 单句目的和用户结果
- 具体触发提示：触发短语、领域关键词、反触发条件
- 预期输出：技能产生的文件、命令或决策
- 安全边界和审批要求

### 条件输入

在相关时收集：
- 命名前缀、命名空间或目录约定
- 技能类别：能力提升或工作流/编码偏好
- 组成：独立、协调器或从属
- 仓库特定的所有权、生命周期或发布策略
- 协调器关系：`metadata.orchestrator` 用于从属技能，`metadata.skills` 用于协调器
- 目标状态（`active`、`experimental`、`deprecated`、`archived`）
- `compatibility` 文本（当技能有实际环境约束时）
- MCP 要求（`metadata.mcp.required` / `metadata.mcp.suggested`）
- `agents/` 中的辅助代理是否会增强范围、审查或触发调整
- 确定性自动化是否证明需要 `scripts/` 目录

### 可选输入

如果有用则捕获：
- `metadata.sponsor` 作为备份问责制（如果目录使用）
- 启动资产、清单、示例或模板
- 如果存在几乎匹配项且应改进而不是重复，则提供相关问题后续处理

### 元数据和结构约束

在编写文件前验证：
- `name`：1-64个字符，仅限小写字母/数字/连字符，必须与文件夹名称匹配，不能有首尾连字符，不能有连续连字符，不能有XML标签，不能有保留词
- 如果目标仓库没有前缀或命名空间约定，默认新技能为 `custom-<base-skill-name>`
- `description`：非空，<= 1024个字符，第三人称，无XML标签，说明技能做什么以及何时使用
  - 优先使用带内联 `USE FOR:` 和 `DO NOT USE FOR:` 提示的单引号YAML字符串
  - 示例：`description: '从验证的仓库上下文中起草发布说明。USE FOR: 发布摘要、变更日志准备。DO NOT USE FOR: 发布发布或编辑产品代码。'`
- `metadata.version`：遵循目标目录的起始版本规则；如果没有本地规则，新技能的安全默认值为 `"0.0.0"`
- `metadata.owner`：仅在目标目录要求明确所有权时包含；使用稳定的GitHub身份或等效团队处理
- `metadata.status`：仅在目标目录跟踪生命周期状态时包含；如果使用，保持为 `active`、`experimental`、`deprecated` 或 `archived`
- `metadata.tags`：保持相关标签，小写，使用连字符命名法
- `metadata`：除非关系字段明确需要列表或映射，否则使用简单的键/值元数据
- `license`：可选的顶层字段
- `compatibility`：可选的顶层字段；仅在技能有实际运行时、网络、工具或产品约束时包含

特定仓库的前缀规则、所有权/生命周期要求、发布策略和验证命令属于仓库本地说明或目录文档，而不是可移植技能包。

## 说明

### 第1步 — 编辑前检查安装副本来源

在编辑现有 `SKILL.md`（或其 `references/`、`assets/`、`agents/`）之前，检查仓库的 `apm.yml` 和 `apm.lock.yaml`。使用锁文件的依赖来源和部署文件所有权来确定目标是否来自外部APM依赖。如果是，目标是一个**安装副本**，而不是规范源。

**如果是安装副本：**
- 不要就地编辑 — 本地编辑可能会被下一次 `apm install` 或 `apm update` 覆盖，并且永远不会到达其他消费者。
- 告知用户文件是从 `<source>` 安装的；更改应在那里进行。
- 提供切换到 `<source>` 并在那里进行更改的选项，或起草针对它的错误/改进问题。
- 只有在用户明确确认一次性覆盖并接受它不会持久的情况下才本地编辑。

如果既不存在APM文件，目标没有匹配的部署文件所有权，或源与当前仓库匹配，则正常进行。

### 第2步 — 判断是否应为技能

1. 首先检查现有目录：
   - 如果现有技能涵盖请求，建议重用或更新而不是重复
   - 如果技能几乎匹配，建议改进它或打开问题
2. 如果请求更适合作为：
   - 普通仓库文档
   - 没有可重用代理行为的模板/清单
   - 没有技能路由价值的独立脚本
   - 对现有技能的微小复制编辑

### 第3步 — 起草前定义代表性请求

在编写长说明之前，至少捕获三个代表性请求：
- 用户请求或触发短语
- 技能应产生的行为
- 技能必须防止的错误或差距

用作验收标准。如果你无法定义现实的请求，范围未指定或不够可重用以成为技能。

### 第4步 — 分类技能并选择最小的有效结构

确定技能类型：
- `能力提升`：打包领域知识、工具或参考材料
- `工作流 / 编码偏好`：打包顺序、审查门禁、样式规则或变异顺序

确定组成：
- `独立`：不需要协调技能
- `协调器`：路由到配套技能，拥有共享门禁
- `从属`：仅在协调器下运行 — 记录该依赖关系

选择最小文件夹结构：
- `SKILL.md` 总是
- `references/` 用于长指导、示例、表格或平台特定细节
- `assets/` 用于模板、清单、样本输出和静态文件
- `agents/` 当运行时支持技能本地代理时用于专用辅助角色
- `scripts/` 仅当确定性自动化实质性提高安全性或可靠性时

保持引用在一级深度。不要创建嵌套链，这会强制部分读取。

### 第5步 — 起草最小可用 `SKILL.md`

首先编写最实用的主文档：
- 简洁的前置元数据，带有强烈的发现提示
- `使用场景` 和 `不适用场景`
- `必须输入`
- `说明`
- `预期输出`
- `安全与约束`

保持在300行以下。不同的运行时有不同的上下文限制 — 超过300行的文件在小运行时可能会退化并触发CI警告。超过500行的文件会失败CI。早期将溢出移至 `references/`。

优先选择简洁、具体的说明，而不是背景解释。假设代理有能
