# 问题创建

## 代理模式

此技能使用内部代理模式进行类型特定的草拟逻辑：

- `agents/bug.agent.md`：以问题为中心的问题草拟和筛选结构
- `agents/feature.agent.md`：以功能为中心的范围和验收结构
- `agents/user-story.agent.md`：以角色/工作流/场景驱动的故事结构
- `agents/task.agent.md`：以清单优先的任务分解和依赖规划
- `agents/devils-advocate.agent.md`：始终开启的质量合作者，在分类后提出关键问题（适度模式），并在明确要求时、范围/标准差距显著时或从 `fusion-issue-task-planning` 调用且存在两个或多个架构模糊信号时，运行完整的结构化访谈（审问模式）

代理模式根据问题类型分类内部激活。用户永远不会直接引用代理文件。共享门禁（标签、指派确认、草拟审查、发布确认和变异顺序）保留在此技能中。

## 何时使用

在将想法、问题、功能请求或用户需求转换为清晰的、可操作的 GitHub 问题时使用，并作为创建和更新问题的顶级路由器。

典型触发器：
- "创建一个问题"
- "草拟一个工单"
- "将此转换为 GitHub 问题"
- "帮助我构建这个工作项"
- "更新/维护/清理这个问题"
- "将此作为子问题/设置父问题/链接为子问题"

## 何时不用

- 实现代码更改
- PR 作者或审查
- 未产生问题草拟的一般研究
- 在没有明确用户确认的情况下修改 GitHub 状态

## 必须输入

在发布前收集：
- 目标存储库
- 问题意图/上下文和类型（问题、功能、用户故事、任务）
- 更新时现有问题编号/URL
- 存储库标签集（或确认有意跳过标签）。按会话缓存每个存储库的完整标签集；本地过滤。优先使用主机会话内存；否则使用 `.tmp/` 缓存文件（永远不会提交）。
- 父/相关问题链接和依赖方向（子问题与阻塞）
- 指派偏好（`@me`、特定人员或未指派）。重用缓存的指派候选结果；当用户给出 `@me` 或确切登录时跳过搜索。

如果必须的详细信息缺失，请从 `references/questions.md` 中提出简洁的澄清问题。
如果问题目的地不明确，请在草拟变异命令之前明确询问问题应创建/更新的位置。

## 说明

### 第 1 步 — 分类和路由

将请求分类为 `问题`、`功能`、`用户故事` 或 `任务`，然后激活匹配的代理模式：
- 问题 -> `agents/bug.agent.md`
- 功能 -> `agents/feature.agent.md`
- 用户故事 -> `agents/user-story.agent.md`
- 任务 -> `agents/task.agent.md`

如果存在歧义，仅询问必要的澄清问题。

魔鬼代言人检查：`agents/devils-advocate.agent.md` 始终以适度模式激活——它在分类后显示 2-3 个最重要的关注点，而不会中断流程。当用户要求“受审”、说“进行压力测试”、范围/标准差距显著或从 `fusion-issue-task-planning` 调用且存在两个或多个架构模糊信号时，在类型特定代理之前升级为审问模式进行完整的结构化访谈。魔鬼代言人返回确认的决策和注意到的风险，然后将任务交给类型特定的草拟代理。

### 第 2 步 — 解决存储库和模板

- 在任何变异之前解决目标存储库。
- 当没有明确给出存储库时，检查活动工作区中的贡献者指南（`CONTRIBUTING.md`、`contribute/`），这些指南定义了按类型默认问题路由规则。在询问用户之前应用那里找到的任何路由规则。
- 如果存储库中没有路由指南，请明确询问问题应创建的位置。
- 模板优先级：
  1. 存储库模板（`.github/ISSUE_TEMPLATE/`）
  2. 专家回退模板

### 第 3 步 — 检查重复项

在草拟/发布之前，使用 `mcp_github::search_issues` 运行一次专注的重复搜索并显示匹配项。
除非用户实质性更改了范围/标题，否则不要运行重复的广泛扫描。

### 第 4 步 — 首次草拟

在编写之前，检查用户偏好和会话内存中的首选草拟位置。如果存在存储的偏好，请使用它。如果找不到偏好且意图存在歧义，请询问一次并记住会话中的答案。如果没有找到偏好且没有可询问的内容，则默认为 `.tmp/{TYPE}-{CONTEXT}.md`。使用 GitHub Flavored Markdown 编写草稿。

### 第 5 步 — 审查和确认

- 首先请求内容编辑。
- 在变异之前明确请求发布确认。
- 除非用户明确确认，否则永远不会在首次草拟时发布/更新。

### 第 6 步 — 应用共享门禁

在变异之前确认：
- 标签（仅目标存储库中存在的标签）
- 指派意图（`@me`、特定登录或未指派）

共享门禁缓存策略：
- 对于 `owner/repo` 的第一次标签查找，获取存储库标签集一次并缓存它以供活动会话使用。当主机暴露会话内存时，优先使用 `/memories/session/<owner>-<repo>-labels.json`；否则使用 `.tmp/issue-authoring-labels-<owner>-<repo>.json`。
- 在缓存命中时，本地验证请求的标签。不要为每个请求的标签重复点查找。
- 如果主机仅暴露点标签查找且尚未存在缓存的标签集，不要逐个循环标签。询问是否要跳过可选标签或在第一次 `mcp_github::issue_write` 调用中仅包含用户确认的标签，并处理单个拒绝路径。
- 当需要查找指派者时，为活动会话按 `owner/repo`（或 `owner`）和查询键缓存候选结果。优先使用 `/memories/session/<owner>-<repo>-assignee-candidates.json` 或 `/memories/session/<owner>-assignee-candidates.json`；否则使用 `.tmp/issue-authoring-assignee-candidates-<owner>-<repo>.json`。
- 如果速率限制阻止可选标签或指派者增强，请询问是否在没有它们的情况下继续，而不是循环重试。

### 第 7 步 — 通过 MCP 变异（按顺序）

在明确确认后，按此顺序执行 MCP 变异：
1. `mcp_github::issue_write` 创建/更新，使用完整的已知负载（`title`、`body`，仅在支持时包含 `labels`、`assignees`、`type`）
2. 仅当在步骤 1 中未知且稍后可用时，执行可选的单次后续 `mcp_github::issue_write`
3. 仅当请求关系/顺序更改时，执行 `mcp_github::sub_issue_write`
4. 仅当明确请求阻止/状态笔记时，执行 `mcp_github::add_issue_comment`

如果由于缺少 MCP 服务器/认证/配置而导致变异失败：
- 清晰地解释失败原因
- 指导用户在 `references/mcp-server.md` 中完成设置步骤
- 在用户确认设置完成后重试

速率限制行为：
- 检测并清晰地报告速率限制失败（`API 速率限制超出`、`次要速率限制`、GraphQL 配额耗尽）。
- 当遇到速率限制时，停止非必要的查找并跳过可选增强。
- 保留草拟工件并返回安全的重试计划，而不是循环重试。
- 当存在等效 MCP 功能时，优先使用 MCP 工具而不是 ad hoc `gh api`/GraphQL 重试。
- 使用 GraphQL 回退时：每次变异消耗 5 个次要限制点（查询消耗 1 个），因此将字段批处理到单个变异调用中，并在变异调用之间至少暂停 1 秒。
- 在重试任何请求之前，尊重 `retry-after` 和 `x-ratelimit-reset` 标头。

`type` 规则：
- 仅当存储库配置了问题类型时才使用 `type`。
- 当可用时，使用按组织的缓存问题类型。
- 仅在缓存未命中或缓存无效时调用 `mcp_github::list_issue_types`。
- 如果不支持问题类型，则在此会话的其余时间内省略 `type`。

### 第 8 步 — 验证关系

在链接之前：
- 使用子问题进行分解
- 使用子问题顺序表示先决条件
- 确保没有矛盾的依赖图

使用 `references/instructions.md` 和 `references/mcp-server.md` 中的详细行为和负载示例。

## 核心行为保留

- 分类优先工作流
- 路由到代理模式工作流
- 首次草拟工作流
- 缺少关键上下文时的澄清问题
- 任何 GitHub 变异前的明确确认

使用 `references/instructions.md` 中的详细草拟指南。
回退模板位置：
- 问题：`assets/issue-templates/bug.md`
- 功能：`assets/issue-templates/feature.md`
- 用户故事：`assets/issue-templates/user-story.md`
- 任务：`assets/issue-templates/task*.md`

## 预期输出
- 选择的代理模式路径
- `.tmp` 下草拟问题文件路径
- 使用的模板源（存储库模板路径或回退资源路径）
- 提议的标题、正文摘要和标签
- 问题类型计划
- 依赖计划（顺序 + 提议的子问题/阻塞链接）
- 指派计划（谁将被指派，或明确的未指派决定）
- 明确状态：`Awaiting user content approval` 在任何发布/更新命令之前
- 找到的任何相关/重复问题链接
- 确认变异后要运行的精确创建/更新命令
- 确认变异后仅返回创建/更新的问题 URL/编号
- 当存储库模板缺失或薄弱时建议的模板维护后续操作

## 安全与限制

永远不要：
- 在没有明确用户确认的情况下运行 `mcp_github::issue_write` 创建/更新
- 在用户确认草拟内容正确之前发布/更新问题
- 假设用户希望发布到 GitHub
- 请求或暴露密钥/凭证
- 在没有明确确认的情况下执行破坏性命令

始终：
- 保持草拟简洁且可编辑
- 在问题文本中使用 WHAT/WHY 而不是实现 HOW
- 使用完整的存储库问题引用（例如 `owner/repo#123`）
- 在打算关闭时使用问题关闭关键词（例如 `fixes owner/repo#123`、`resolves owner/repo#123` 或 `closes owner/repo#123`）
