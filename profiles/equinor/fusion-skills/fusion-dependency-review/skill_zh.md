# 依赖项审查

结构化的审查工作流，用于依赖项更新 PR。生成一致的调研笔记，整合现有 PR 讨论内容、多角度分析，并在任何合并操作之前提供明确的维护者确认的可执行结论。

## 使用场景

当依赖项 PR 需要审查，并且您希望获得一致、可审计的决策流程时使用。

典型触发条件：

- "审查此依赖项 PR"
- "我们应该合并此依赖项更新吗？"
- "检查此 Renovate/Dependabot PR"
- "审查我们开放的依赖项 PR 之一"
- "此库更新中发生了什么变化？"
- "此依赖项更新是否安全可合并？"
- PR 标题包含依赖项更新模式（例如 `chore(deps):`、`fix(deps):`、`bump`、`update`）
- 用户分享依赖项更新 PR 的 URL

## 不适用场景

- 功能 PR 或应用程序代码审查（使用标准代码审查工作流）
- 依赖项自动化或机器人配置
- 无明确用户确认的情况下批准/合并
- 确定组织依赖项策略

## 必需输入

开始前收集：

- **仓库** 所有者和名称
- **PR 编号或 URL**，或包含包名、版本变更、变更文件和 CI 状态的 PR 摘要副本
- 可选：具体的审查关注点或审查范围

如果缺少必需的详细信息，请从 `references/questions.md` 中提出简洁的澄清问题。

如果 PR 目标缺失或模糊：

- 仅询问识别目标 PR 所需的最小后续问题。
- 当仓库上下文已知时，使用 GitHub MCP 列出可能的开放依赖项 PR，并让用户选择。
- 保持短列表简洁：当可用时，包括 PR 编号、标题、依赖项/包提示、作者和 CI 状态。

在 PR 中可用时自动提取：

- 正在更新的包和版本范围（从 → 到）
- 更改日志/发布说明 URL
- CI 状态
- 变更文件和依赖项生态系统
- 现有顶层 PR 评论、审查评论和未解决线程状态

## 指南

### 优先顾问编排

当运行时支持技能本地顾问时，优先选择此执行形状，而不是单个长线性传递：

1. 当 PR 目标缺失或模糊时，首先运行 `agents/target-pr-advisor.md`，以便审查从明确的依赖项 PR 开始。
2. 运行 `agents/research-advisor.md` 以标准化 PR 上下文、现有讨论、源列表和调研笔记。
3. 并行运行相同的标准化输入中的镜头顾问：
   - `agents/security-advisor.md`
   - `agents/code-quality-advisor.md`
   - `agents/impact-advisor.md`
4. 将组合的调研和镜头输出链接到 `agents/verdict-advisor.md` 以生成建议、置信度、准备状态、交接和确认措辞。
5. 仅当接受的下一步需要 PR 补丁、变基、冲突解决或合并就绪工作时，才将其链接到 `agents/source-control-advisor.md`。

保持镜头顾问狭窄且独立。父技能拥有统一审查，应保留顾问之间的分歧，而不是过早扁平化。

### 工作流摘要

1. 使用 `agents/target-pr-advisor.md` 和 `references/questions.md` 中的简洁提示解决目标 PR。
2. 使用 `agents/research-advisor.md`、`assets/review-tracker.md` 和 `assets/research-template.md` 收集上下文并构建共享证据包。
3. 并行运行 `agents/security-advisor.md`、`agents/code-quality-advisor.md` 和 `agents/impact-advisor.md`，使用相同的标准化研究包。
4. 使用 `agents/verdict-advisor.md` 生成建议、置信度、准备状态、后续操作和明确的维护者提示。
5. 仅在决策被接受且需要分支工作时，使用 `agents/source-control-advisor.md`。
6. 按照 `references/instructions.md` 跟随详细的实时 PR 合同：目标选择、检查点评论、决策门禁和交接时间。

## 资产

- `assets/research-template.md`：用于变更摘要、破坏性变更、已知问题和来源的调研评论结构
- `assets/verdict-template.md`：镜头评估、建议、置信度、准备状态和后续项目的裁决结构
- `assets/review-tracker.md`：用于上下文、验证、镜头结果和交接决策的工作清单和跟踪器

## 参考

- `references/instructions.md`：目标选择、实时 PR 检查点和决策顺序的详细执行合同
- `references/questions.md`：选择目标依赖项 PR 和界定审查范围的简洁后续问题

## 顾问

- `agents/target-pr-advisor.md`：解决要审查的确切依赖项 PR 或返回用户选择的短列表
- `agents/research-advisor.md`：第一遍；为所有后续顾问构建共享证据包
- `agents/security-advisor.md`：并行镜头传递；检查安全态势和攻击面变更
- `agents/code-quality-advisor.md`：并行镜头传递；检查上游稳定性、回归和 API 分裂
- `agents/impact-advisor.md`：并行镜头传递；检查仓库爆炸半径、CI 和后续工作
- `agents/verdict-advisor.md`：链接合成传递；将调研和镜头输出转换为单一决策
- `agents/source-control-advisor.md`：条件最终传递；在修补 PR 时处理变基、同步、验证重跑和推送安全性

如果辅助顾问不可用，请按行内相同编排：先调研，再镜头，然后裁决，仅在需要变更时才进行源控制。

## 预期输出

如果 PR 目标未解决，返回：

- 当实时 PR 搜索可用时，返回候选依赖项 PR 的简洁短列表
- 允许用户选择正确 PR 所需的最小后续问题
- 明确状态：`Awaiting user PR selection`

如果 PR 目标已解决，返回结构化审查，包含：

- 包名、版本变更和更新类型
- 现有 PR 讨论摘要（顶层评论、审查线程主题、未解决关注点）
- 调研摘要（更改日志高亮、破坏性变更、已知问题）
- 带证据的安全评估
- 带证据的代码质量评估
- 带证据的影响评估
- 裁决：建议、理由、置信度、准备状态和后续项目
- 当后续工作应成为跟踪问题时，交接建议
- 明确的行动提示给维护者

## 安全性与约束

- 此技能具有变更能力。仓库本地工作流指令在冲突时优先于行内指导。

永远不要：

- 无明确用户确认的情况下合并或批准依赖项 PR
- 通过将基础分支合并到 Dependabot 或 Renovate PR 分支来创建合并提交
- 当存在多个可能的依赖项 PR 时猜测要审查哪个 PR
- 跳过实时 PR 的研究检查点评论或最终裁决评论
- 因为不便利或重复而忽略现有审查者关注点
- 未检查实际状态就声称 CI 通过或安全无虞
- 在评论或日志中暴露密钥或令牌
- 出于便利而忽视安全关注点
- 编造未在来源中找到的更改日志条目或版本详细信息

始终：

- 当目标 PR 缺失或模糊时，提出最小的后续问题
- 为每个评估提供证据（链接到更改日志、CVE、CI 状态）
- 独立评估技术建议、证据置信度和机械合并就绪度
- 将待处理的检查或必需的批准视为就绪门禁，而不是技术原因来延迟
- 对于重大更新，要求明确的兼容性证据，而不仅仅是将 semver 类别视为低置信度
- 当仓库上下文存在但 PR 目标不存在时，列出候选依赖项 PR 以供用户选择
- 在对实时 PR 进行分析之前，通过 GitHub MCP 获取现有 PR 评论和审查线程
- 在每个传递中重用共享调研包，而不是在每个传递中重新发现相同的事实——这包括 PR 元数据、变更文件、CI 状态和现有讨论
- 不要在每个顾问中独立重新获取 PR 评论或审查线程；将研究顾问的预获取数据传递给所有镜头顾问
- 当运行时支持时，优先选择并行镜头分析，然后在所有镜头输出准备就绪后进行链接合成
- 在对实时 PR 进行任何分支变更之前，将研究检查点评论发布到 PR
- 在对实时 PR 进行任何批准或合并之前，将最终裁决评论发布到 PR
- 在修补 PR 之前明确分支同步或变基需求
- 当需要刷新时，将依赖项 PR 分支变基到最新基础分支；不要将基础分支合并到 PR 分支
- 将后续工作明确表示出来，而不是将其埋在审查笔记中
- 尊重维护者作为最终决策者
- 保持审查输出在一致、可重复的结构中
