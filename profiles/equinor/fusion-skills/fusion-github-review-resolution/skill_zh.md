# 解决 GitHub 审核评论

## 使用场景

当拉取请求存在未解决的行内审核评论，并且需要可重复、可审计的关闭工作流程时，使用此技能。

典型触发条件（技能应在所有这些条件下激活）：

**URL 模式 — 立即激活：**
- `https://github.com/<owner>/<repo>/pull/<number>#pullrequestreview-<id>`
- `https://github.com/<owner>/<repo>/pull/<number>`（当上下文暗示需要审核工作）

**明确的用户请求：**
- "修复审核评论"
- "处理此 PR 的审核反馈"
- "存在未解决的审核评论 — 修复它们"
- "解决此 PR 上的对话"
- "处理此 PR 上所有未解决的评论"
- "针对每个审核评论：修复、测试、提交、回复、解决"
- "关闭打开的审核线程"
- "检查此审核并在修复后解决对话"
- "解决未完成的审核反馈"
- "PR 有请求的变更 — 修复它"

**隐式 / 代理检测：**
- PR 处于 "请求变更" 状态，代理被要求处理它
- PR 存在未解决的审核线程，用户请求改进或合并 PR
- 代理正在处理 PR 时检测到打开的审核对话

## 不使用场景

- 不存在未解决的审核评论
- 请求仅用于总结或描述反馈，无需代码变更
- 所有目标线程均已解决或过时并已确认
- 分支/工作树有意设为只读

## 必需输入

执行前收集：
- 仓库所有者/名称
- 拉取请求编号或 URL
- 可选的评论范围 ID（例如 `pullrequestreview-<id>`）
- 分支/工作树决策（如果当前检出的分支已经是 PR 的头分支，则跳过询问 — 见步骤 1）
- 仓库所需的验证命令

> **当提供审核 URL 时** (`github.com/<owner>/<repo>/pull/<number>#pullrequestreview-<id>`),
> 自动提取所有者、仓库名、PR 编号和审核 ID。
> 仅分支/工作树选择和验证命令仍需确认。

可选：
- 链接的问题引用（例如 `equinor/fusion-core-tasks#432`）
- 当评论重叠同一文件时，首选的提交粒度偏好

## 指令

除非用户明确要求不同顺序，否则请按此阶段顺序执行：获取 → 分析 → 修复 → 验证 → 推送 → 回复 → 解决 → 验证。不要在 GitHub 线程突变与代码编辑重试之间交错。

1. 确定分支/工作树上下文
   - 首先检查当前检出的分支与 PR 的头分支是否匹配。
   - 如果当前分支已匹配 PR 的头分支，直接进入该分支 — 不要询问工作树。
   - 否则（当前分支不同，或工作区位于 `main`/`master` 等共享/长期分支上），在询问任何其他工作流问题之前，询问是否要使用专用的 git 工作树。
   - 如果是，使用/创建工作树并继续。

2. 收集未解决的评论并创建工作追踪器
   - 如果提供了带有 `#pullrequestreview-<id>` 的审核 URL，则在获取之前解析所有者、仓库名、PR 编号和审核 ID。
   - **复制或打开 `assets/review-resolution-checklist.md`—这将成为你的工作文档。** 在处理每个线程时，填写上下文部分并更新评论追踪表。
   - 获取 PR 的审核线程并过滤未解决的线程。
   - 如果提供了特定的审核 ID 或审核 URL，则限制为来自该审核的评论。
   - 在目标审核中，收集所有与该审核 ID 关联的评论（除非明确请求，否则不包括来自其他审核的回复）。
   - 构建工作列表：线程 ID、评论 ID、父审核 ID、文件路径、原始评论正文以及该线程中的所有后续回复（包括贡献者回复）。
   - 读取每个线程的完整回复链 — 贡献者可能已添加澄清、限制或附加上下文，这些都必须在决定如何解决评论时考虑。
   - 在任何 GitHub 突变之前，捕获目标线程 ID 的基线列表和未解决线程计数。

3. 理解、研究和判断每个评论
   - 阅读引用的文件和附近逻辑。
   - 判断反馈是否正确、部分正确、过时或错误，相对于当前代码、需求和上下文。
   - 审核者不自动正确；不要为了满足过时或错误的评论而进行代码变更。
   - 如果反馈正确，验证根本原因并确定最小的安全修复。
   - 如果反馈明显错误或过时，准备基于证据的简洁回复，而不是不必要地更改代码。
   - 如果不确定，检查相邻的测试/用法后再编辑。
   - 在本地研究后仍有疑问，则在进行代码变更或突变该审核线程之前，询问用户。

4. 修复、检查、提交（针对每个评论）
   - 仅对判断为有效或部分有效的评论应用专注的代码/文档变更。
   - 首先运行目标检查，然后运行所需的仓库检查。
   - 在实际情况下，每个评论创建一个提交。
   - 如果两个评论需要一个不可分割的变更，使用一个提交，并在回复中将两个评论映射到该提交。
   - 对于拒绝的评论，在工作追踪器中记录理由，以便最终的回复是明确和可审计的。

5. 所有修复完成后推送一次
   - 在创建所有与评论相关的提交后，推送分支更新一次。

6. 回复并解决每个审核评论
   - 在任何线程突变之前，优先使用结构化工具，顺序如下：
     1. 当前客户端会话中暴露的专用 GitHub MCP 审核线程回复/解决工具，
     2. 捆绑的 GraphQL 资产或捆绑的 `scripts/resolve-review-comments.sh`，
     3. 永远不要临时 Python 脚本、一次性批处理助手或盲目的 `gh api` 重试循环。
   - 从清单/追踪器中为每个目标线程准备一个计划的回复，在发布任何内容之前。
   - 如果回复/解决尝试出错、超时或返回不确定结果，重新获取当前线程状态后再重试。
    - 对于每个线程，这两个步骤是强制性的，并且必须按顺序一起执行，除非线程仍不确定并等待用户输入：
       1. **在线程上发布回复**：描述已更改的内容并包含提交哈希，或解释未进行代码变更的原因，因为评论错误/过时。
       2. **立即解决线程** — 在回复发布后解决，从不提前。
   - 每个线程最多尝试一次回复。
   - 如果存在与代理生成的回复等效的回复，则不要发布另一个回复；重用它，并且仅在线程仍未解决时解决。
   - 如果存在不同的代理生成的回复，则停止并手动检查，而不是堆叠另一个评论。
    - 不要解决仍不确定的线程；先将其升级给用户。
   - 不要在未回复的情况下解决线程。不要在解决线程之前发布回复。
   - 保持回复具体：命名已更改的文件/行和提交，而不仅仅是 "已修复"。

7. 验证关闭状态
   - 重新检查审核线程并确认没有目标未解决的线程剩余。
   - 确认目标未解决线程计数降至零，在此运行期间没有创建重复的代理回复。
   - 如果工作流期望绿色检查，重新检查最新的 CI 状态。

8. 询问是否要请求原始审核作者进行新审核
   - 修复推送后线程解决后，询问用户是否要请求原始审核评论作者进行新审核。
   - 如果是，请求该评论者的用户名进行审核，并报告请求已发送。

9. 可选的脚本执行
   - 使用 `scripts/get-review-comments.sh` 获取匹配的审核评论（包括与审核 ID 关联的子评论）。
   - 结果限制为前 100 个审核线程和每个线程的前 100 条评论。
   - 示例测试：
      - `skills/.experimental/fusion-github-review-resolution/scripts/get-review-comments.sh --owner equinor --repo fusion-skills --pr 27 --review-id 3837647674`
   - 使用 `--include-outdated` 当您需要来自过时匹配线程的评论时。
   - 使用 `scripts/resolve-review-comments.sh` 使用先干跑后提交的重复回复保护来回复+解决匹配的线程。
   - 保持默认的干跑行为；仅在提交并推送修复后使用 `--apply`。
   - 默认情况下，脚本拒绝向已包含一个认证用户回复的线程添加另一个认证用户回复；仅在手动检查后使用 `--allow-additional-reply`。
   - 示例干跑：
      - `skills/.experimental/fusion-github-review-resolution/scripts/resolve-review-comments.sh --owner equinor --repo fusion-skills --pr 27 --review-id 3837647674 --include-resolved`
   - 示例提交：
      - `skills/.experimental/fusion-github-review-resolution/scripts/resolve-review-comments.sh --owner equinor --repo fusion-skills --pr 27 --review-id 3837647674 --apply --message "Addressed in <commit>: <what changed>."`

## 工具映射（MCP vs GraphQL）

使用 GitHub MCP 工具进行高级 PR 操作和当前客户端暴露的任何专用审核线程突变。当 MCP 覆盖不足时，使用 GraphQL 进行线程级审核操作。

| 工作流操作 | 首选工具 | 备注 |
|---|---|---|
| 请求审核者 / 更新 PR 元数据 | `mcp_github_update_pull_request` | 适用于合作者审核者和标准 PR 更新。 |
| 创建或提交 PR 审核评论 | `mcp_github_pull_request_review_write` | 处理待处理的审核生命周期操作。 |
| 添加一般 PR 评论 | `mcp_github_add_issue_comment` | 向 PR 对话中添加问题样式评论，不是行内线程回复。 |
| 列出审核线程和评论 | `assets/pull-request-review-threads.graphql` | 使用 `gh api graphql -f query=@assets/pull-request-review-threads.graphql` 获取线程级上下文。 |
| 计数特定审核 ID 的未解决线程 | `assets/unresolved-thread-count-for-review.graphql` | 后处理响应（例如使用 `jq`）以按审核 ID 和未解决状态过滤。 |
| 回复审核线程 | `Dedicated MCP 审核线程回复工具`，否则 `assets/add-pull-request-review-thread-reply.graphql` | 当可用时优先使用 MCP 工具；否则使用捆绑的线程范围突变，而不是临时脚本。 |
| 解决审核线程 | `Dedicated MCP 审核线程解决工具`，否则 `assets/resolve-review-thread.graphql` | 使用当前客户端/会话的匹配结构化工具。 ⚠️ GraphQL 注意：`resolveReviewThread` 使用 `threadId`，而不是 `pullRequestReviewThreadId`。 |
| 列出 PR 审核评论（支持审核 URL/ID 查找） | `assets/pull-request-reviews.graphql` | 当从审核 URL 上下文开始时很有用。 |

> **小技巧：** 查看资产中的每个 `.graphql` 文件以获取完整的突变/查询语法和参数名称。

### GraphQL 成本意识

审核解决工作流程会进行多次 GraphQL 突变调用（每个线程回复+解决）。请谨慎：

- 突变成本为每个 5 个二级限制点（读取查询为 1 个），预算要充足。
- 在连续突变调用之间至少暂停 1 秒以避免二级速率限制。
- 保持 `first`/`last` 连接参数较小（仅在需要单页中所有线程时才使用 `first: 100`）。
- 如果返回二级速率限制错误或 `retry-after` 头，停止处理并尊重指示的等待时间后再重试。
- 总是优先使用客户端暴露的专用 MCP 审核线程工具，而不是原始 GraphQL。

### 令牌预算指导

- 一次性获取完整的线程列表并用于所有线程级工作；不要在回复和解决之间重新获取线程。
- 预算估计：对于 N 个未解决线程，预期 ~1 列表调用 + N 回复突变 + N 解决突变 = 1 + 2N 调用。10 个线程的审核成本约为 21 次调用。
- 如果线程计数超过 15，在工作流开始突变之前警告用户关于速率限制风险，并提议分小组批量处理。
- 从第一次获取中缓存 PR 元数据（标题、分支、CI 状态、已更改文件）并重用于提交消息和回复。
- 避免在步骤之间进行冗余的 PR 级读取；在单个解决运行中，数据不会改变。

## 预期输出

返回包含以下内容的简洁报告：
- 处理的评论数量，
- 处置摘要（修复、拒绝并说明理由、升级给用户），
- 更改的文件，
- 提交列表（哈希+消息），
- 运行的验证命令和结果，
- 推送确认，
- 每个线程的回复/解决确认，
- 完成的清单位置，
- 任何剩余未解决的线程或障碍。

## 链接问题使用

当提供问题时（例如 `equinor/fusion-core-tasks#432`）：
- 在进行中/最终摘要中提及问题，
- 保持实现与问题范围一致，
- 避免扩展到无关的 PR 自动化。

## 安全与限制

- 此技能具有突变能力。仓库本地工作流指令优先于行内指导，当它们冲突时。
- 永远不要在日志/回复中暴露秘密或令牌。
- 优先使用基于 argv 的进程执行，而不是 shell 插值命令字符串。
- 保持差异最小并限制为审核反馈。
- 不要假设审核反馈是正确的；首先将其与代码和需求进行推理。
- 如果评论在研究后仍不明确，则询问用户而不是猜测。
- 不要在发布具体的修复回复之前解决线程。
- 不要声称检查通过，除非命令实际上已运行。
- 不要强制推送；使用常规提交，并在所有修复后推送一次。
- 如果评论过时但仍未解决，则：
  - 使用清晰的解释和提交引用解决，
  - 或保持未解决并报告原因。
- 在脚本模式下，保持默认的干跑行为，并要求显式的 `--apply` 才能进行突变。
