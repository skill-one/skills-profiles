# 问题解决工作流

## 使用场景

当用户希望端到端地解决或继续 GitHub 问题，包括当前仓库的简短提示（如 `solve #123`）、直接的 GitHub 问题链接，或类似 `lets work on https://github.com/owner/repo/issues/123` 的请求时使用。

典型触发词：
- "lets solve #123"
- "solve #123"
- "work on #123"
- "lets work on https://github.com/owner/repo/issues/123"
- "https://github.com/owner/repo/issues/123"
- "continue work on issue #123"
- "implement issue #123 end-to-end"
- "work on this ticket: [issue URL]"
- "research, implement, and prepare a PR for this issue"

将 GitHub 问题链接视为与 `#123` 引用对于 `solve`、`fix`、`implement`、`continue`、`finish` 或 `work on` 等动词可互换。当没有其他竞争意图时，直接的 GitHub 问题链接可以作为主要请求负载。

## 不适用场景

- 仅请求问题草拟/作者
- 无需实施变更
- 禁止仓库写入操作

## 必须输入

执行前收集：
- 问题链接或 `owner/repo#number`
- 仓库和分支/工作树决策
- 接受标准和非适用范围约束
- 目标仓库所需验证命令

可选：
- 相关问题/PR
- 优先处理的风险区域
- 请求的提交/PR粒度

## 指令

1. 询问是否使用专用 git 工作树
   - 在任何其他工作流问题之前询问。
   - 如果是，使用/创建工作树并在那里继续。

2. 确认问题上下文和成功标准
   - 一次性读取问题正文、标签和关联讨论，然后重用该上下文而不是重新获取。
   - 重申可实施范围并明确列出非适用项。

3. 确认问题关闭工作的分配意图
   - 检查当前用户是否分配到主要问题。
   - 如果当前用户未分配，询问他们是否希望在继续前自行分配。
   - 对于此工作流将解决或关闭的每个子问题，检查分配状态一次并重用结果用于关闭决策。
   - 如果当前用户未分配到子问题，询问他们是否希望在解决/关闭前自行分配。

4. 应用低 token GitHub 策略
   - 当存在等效工具时，优先使用 MCP 支持的工具而不是临时的 `gh api` 或 GraphQL 调用。
   - 避免对标签、问题类型和重复检测进行重复查找。
   - 缓存每次运行时上下文（问题元数据、重复匹配、问题类型支持、标签集、分配候选者）并重用它——不要重新获取在此会话中已检索的数据。
   - 当委托给 `fusion-issue-authoring` 或其从属技能时，协调器的会话缓存规则适用：标签和分配候选者在每个仓库中只获取一次，问题类型在每个组织中只获取一次。
   - 仅当 MCP 覆盖不可用时才使用 GraphQL 回退，并且不要循环重试。
   - GraphQL 变更每次消耗 5 个二级限制点（查询为 1 个）；将字段批量到单个调用中，并在变更调用之间至少暂停 1 秒。
   - 预算意识：典型的实施会话（读取问题 + 重复检查 + 1-2 个变更 + 子问题链接）应保持在 ~20 个 MCP 读取调用和 ~5 个变更以下。如果运行总调用量接近 30+ 次，暂停可选增强并继续本地工作。
   - 尊重 `retry-after` 和 `x-ratelimit-reset` 标头；不要在指示的等待时间之前重试。
   - 如果达到速率限制，停止非必要操作，并在可能时继续本地实施/PR 准备。

5. 构建和跟踪具体计划
   - 创建按依赖排序的可操作待办事项。
   - 保持仅一个步骤处于进行中，并在完成工作时更新状态。

6. 编辑前进行研究
   - 检查相关文件、测试和相邻用法。
   - 优先进行根本原因修复而不是表面补丁。

7. 小范围变更中实施
   - 使每个变更与问题接受标准保持一致。
   - 避免无关的重构和生成的发布工件。

8. 增量验证
   - 首先运行目标检查，然后运行必需的项目检查。
   - 如果检查失败，修复相关问题并重新运行后再继续。

9. 准备 PR 就绪输出
   - 总结变更内容和原因。
   - 包括验证证据和已知后续事项。
   - 在 `.tmp/` 文件中起草 PR 正文，使用特定于问题/上下文的名称（例如，`.tmp/pr-body-issue-123-scope-summary.md`），而不是共享的 `.tmp/pr-body.md`。
   - 基于 `.github/pull_request_template.md` 起草草稿，并在实施过程中保持更新。
   - 询问要靶向的基线分支，并提出可能的默认值（通常是 `main`，或当前分支从中分出的分支）。
   - 询问 PR 是否应作为草稿打开或准备好审查。
   - 询问 PR 是否应分配给用户以及是否应链接相关问题。

10. 可选的 GitHub 变更步骤
   - 在任何 GitHub 变更（创建/编辑/评论/关闭）之前，请求明确的用户确认。
   - 如果请求，使用客观进度更新问题状态/评论。
   - 当存在等效操作时，优先使用 MCP 工具变更而不是临时的 API 调用。
   - 如果 GitHub API 速率限制阻止变更，明确报告失败，停止重试循环，并提出安全的重试序列。
   - 如果请求，使用仓库 PR 模板和 `.tmp/` PR 正文草稿文件，使用确认的基线分支、草稿/就绪状态、分配选择和相关问题链接创建或更新 PR。

## 预期输出

返回简洁的交付报告，包括：
- 实施范围与原始问题标准对比，
- 修改的文件，
- 验证命令和结果，
- 主要问题和受影响子问题的分配决定，
- 使用的 API 使用策略（MCP 优先/缓存重用/回退），
- 开放风险/阻塞项，
- PR 正文摘要（或创建时的 `.tmp/` 草稿文件路径）。

## 安全与约束

- 此技能具有变更能力。仓库本地工作流指令优先于内联指导，当存在冲突时。
- 永远不要请求或暴露密钥/凭证。
- 永远不要在未明确确认的情况下运行破坏性命令。
- 保持变更最小并限定于问题范围。
- 不要声称检查通过而未运行。
- 遵循仓库指令和贡献规则。
