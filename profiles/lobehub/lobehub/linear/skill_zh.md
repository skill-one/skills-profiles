# 线性问题管理

在使用 Linear 工作流之前，先了解可用的 Linear 工具，包括延迟工具，并检查它们的当前架构。根据功能（问题查询、图片、子问题、创建/更新、评论）选择工具，而不是固定的 MCP 前缀或历史工具名称。只有在发现缺失功能后才能报告。

## 工作流

1. **在开始使用问题查询功能之前，检索问题详情**。
2. **查看图片** — 问题描述中经常包含带有关键上下文的截图（原型图、错误状态、前后对比）。使用可用的图片提取或查看功能；仅阅读原始 Markdown 会错过报告者所看到的内容。
3. **使用可用的父级过滤器或问题关系字段检查子问题**。
4. **在开始计划或实施时立即标记为“进行中”** — 这向队友表明该问题已被分配，以免他们重复处理。
5. 在进入下一个问题之前，遵循 [按问题完成](#按问题完成)。

## 创建问题

在创建问题时，添加 `claude code` 标签。原因：该标签是团队过滤/审计 AI 生成问题的方法；没有它，这些问题会消失在一般积压队列中，团队会失去对 AI 贡献模式的可见性。

除非用户明确指定其他负责人或要求问题保持未分配状态，否则传递 `assignee: "me"`，以便将问题分配给经过身份验证的 Linear 用户。始终优先考虑明确的分配指令，而不是默认设置。

## 语言

使问题的语言与产生它的对话相匹配 — 如果你在讨论中文，就用中文写问题；如果讨论英文，就用英文写。原因：问题是对话的延续，强制切换语言会给开始话题的协作者造成翻译摩擦。

具体说明：

- 中文对话 → 中文正文；技术术语（文件路径、标识符、库名称、命令、错误消息）保持英文。
- 英文对话 → 英文正文。
- 代码块、文件路径和引用字符串始终保持其原始形式，无论周围语言如何。
- 这同样适用于**更新** — 在编辑现有问题（描述**和标题**）时，保留触发编辑的对话的语言；不要在重构过程中切换问题语言。

## 创建子问题树

当将父问题分解为子问题树（例如，LOBE-xxx 的任务分解）时，请遵循这些约定并检查可用的工具功能。

### 1. 标题前缀排序索引

Linear 支持子问题排序，但工具支持各不相同。检查发现的创建/更新架构中的排序字段，而不是假设某个 MCP 工具提供了这些字段。

解决方案：在标题本身中编码执行顺序：

```plaintext
[1]     [db]       添加架构字段
[2]     [db]       新建表 + 仓库
[3]     [service]  业务逻辑层
[4]     [api]      REST 端点
[4.1]   [sdk]      客户端 SDK 封装
[4.1.1] [app]      消费者集成
[4.1.2] [app]      UI 界面
[4.2]   [ui]       仪表板页面
```

即使面板会重新排序，读者也能一眼在脑海中重建依赖关系图。虚线编号 `[n.m.k]` 应该反映父子嵌套，以便索引和树结构一致。

### 2. 按逻辑父子关系嵌套子问题，而不是扁平地置于根下

Linear 支持**无限子问题深度**。一个根下有 8 个以上的同级列表很难扫描。按主从逻辑分组：

- 核心服务 → 其 SDK → SDK 消费者
- 当子问题更准确时，不要创建同级问题

在创建或移动问题时使用发现的架构设置父级关系（例如，当支持时 `parentId: "LOBE-xxxx"`）。移动父级不需要重写 `blockedBy` 关系。

### 3. 子问题创建顺序由 `blockedBy` 决定

`blockedBy` 要求被阻塞者先存在（你需要它的 LOBE-id）。因此：

1. **对 DAG 进行拓扑排序** — 叶子（无依赖）优先，根最后
2. 第一波创建无依赖的问题
3. 只有在收集了先前的响应中的阻塞者 ID 后才创建依赖问题
4. `blockedBy` 是**仅追加**的；再次传递它不会覆盖 — 安全重用

### 4. 尊重依赖顺序

在创建依赖问题之前收集阻塞者 ID。不要假设消息中工具调用的并行执行方式；使用活动工具支持的实际执行行为。

### 5. 保持每个子问题描述自包含

每个子问题应说明：

- 目标（1-2 行）
- 关键文件
- 具体变更 / 接受标准
- 依赖关系（通过 `LOBE-xxxx` 链接到阻塞问题）
- 验证步骤

实现者可能只打开子问题，而不是父问题 — 不要依赖仅存在于父问题描述中的上下文。

## 按问题完成

在开始下一个问题之前关闭每个问题；不要将所有 Linear 更新推迟到最后。重用该问题的状态更新和评论的现有授权，无需再次询问。

1. 完成实施和仓库要求的检查，包括相关测试；遵循仓库的 `AGENTS.md` 中的质量检查部分（在 LobeHub 中运行 `bun run check`）。
2. 当需要时使用 **pr** 技能创建 PR。在 PR 正文中包含 `Fixes LOBE-123`（或 `Closes` / `Resolves`），以便 Linear 可以链接它并在合并时关闭问题。
3. 在 PR 等待合并时将问题更新为 **“待审核”**，合并后更新为 **“完成”**。对于无需 PR 的工作，在结果和验证完成后标记 **“完成”**。
4. 主动添加或更新一个简洁的完成评论，包含结果行为、重要变更、验证和 PR 链接。PR 链接不能替代人类可读的摘要。如果现有评论已经涵盖了相同的结果，请不要发布重复评论。
