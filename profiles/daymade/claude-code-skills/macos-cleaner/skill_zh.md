# macOS 清理工具

诊断磁盘压力的实际来源，仅回收批准的空间，并证明清理操作未损坏用户数据或共存服务。

## 入口路由

选择能回答请求的最窄路径：

| 用户信号 | 路由 |
|---|---|
| Apple 内容缓存、`AssetCacheManagerUtil`、`CacheUsed`、`ActualCacheUsed`、iCloud 缓存或“需要更多缓存空间” | 在探测或建议命令前，完整阅读 `references/apple_content_caching.md` |
| Docker、OrbStack、镜像、容器或卷 | 阅读 `references/docker_analysis.md`；检查每个对象，且不要使用 prune-family 命令 |
| Docker 构建缓存 | 使用 `docker builder du` 进行测量；此工具报告它但不会删除它，因为 Docker 提供的是跨类别的 prune 控制，而不是逐条记录的意图 |
| Chrome、ChromeDriver、Playwright、Codex 计算机使用、Edge 或 Chromium 具有 large `*.code_sign_clone` 目录 | 完整阅读 `references/chromium_code_sign_clones.md`；使用捆绑的分析器分离活动、非活动和不明确的子项，且不要将 `du` 与物理释放等同 |
| 已存在的命名缓存、目录、应用程序或服务是嫌疑目标 | 首先检查该目标，并阅读 `references/cleanup_targets.md` 中匹配的语义；不要开始家目录或全盘扫描 |
| 来源确实未知 | 使用以下通用分析工作流；Mole 是可选的，不是通用的第一步 |

用户提供的范围排除项会覆盖所有通用扫描建议。当用户排除它们时，不要检查个人目录、凭证、数据库、应用程序状态或无关服务。

## 安全和授权协议

1. **将观察与变异分开。** 首先进行只读诊断。不要删除、停止服务、编辑设置、安装或升级工具，或在变异阶段运行可能改变状态的清理预览。
2. **确认确切目标。** 在远程 Mac 上，在任何其他工作之前记录当前主机身份。永远不要从 IP、旧 PID、目录名或先前报告中推断机器。
3. **在请求前计划。** 在任何状态改变之前，列出每个命令、它将改变的内容、预期的物理空间回收量、影响、可恢复性以及后置条件。然后，如果用户请求仅计划阶段，则停止。
4. **要求明确批准。** 如果用户提供了一个确切的确认短语，则需要该短语。否则，要求对列出的命令和目标进行不容置疑的批准。对一个计划的批准不会授权回退或更广泛的清理。
5. **使用精确的受支持控制——并首先检查它们是否存在已知缺陷。** 优先考虑应用程序的受支持的缓存管理命令或确切的对象 ID。“官方”和“精确”不是安全性的证据，因此在使用第一个受支持控制命令之前，在安装的版本中对该确切的命令进行已知问题检查：在工具的问题跟踪器中搜索命令名，以及其更改日志中查找在安装的版本之后发布的修复。具有开放、与版本相关的缺陷的命令不是此技能的受支持控制——将其视为下一规则中的跨类别命令，并要么升级以绕过该修复，要么使用确切的路径替代方案。如果不存在受支持控制，则只有在验证其所有者、确认应用程序已停止或目录以其他方式非活动、解释重建/重新下载影响并获得批准后，才能删除确切的应用程序拥有的缓存目录。永远不要针对广泛的缓存根或活动应用程序状态。
6. **永远不要使用 Docker prune-family 命令。** 这包括 image、container、volume、system、builder 和 buildx prune。跨类别删除不能表达逐个对象的用户意图。
7. **避免使用广泛的破坏性 Shell 形式。** 不要建议或执行广泛的 `rm -rf` 或 glob 删除。对于确切的已批准的普通文件，优先使用 Finder 垃圾箱。捆绑的遗留助手永久删除，并且只有有限的保护措施在下面记录；永远不要将其视为等同于垃圾箱。
8. **保留有价值的状态。** 不要仅为了增加报告的节省而针对用户文档、凭证、SSH 材料和活动数据库、应用程序配置或运行服务状态。在执行任何文件删除之前，阅读 `references/safety_rules.md`。
9. **执行遵循用户的授权。** 如果用户仅请求分析或想要亲自运行命令，则将命令移交给用户。如果用户要求代理修复机器并明确确认了范围计划，则执行确切的已批准命令并验证它们。未经单独批准的自动重复删除逻辑需要在写入或启用之前获得批准。
10. **快速失败。** 意外的非零命令、不匹配的后置条件、意外的目标或更改的依赖关系会停止清理。在决定它们是失败之前，解释记录的探测状态，例如 `lsof` 退出状态 1 且输出为空。报告部分状态；不要临时制定回退方案。
11. **在承诺从任何删除中释放物理空间之前，命名机制——并从创建命令而不是猜测中获取它。** `df` 之间的名义 `du` 总和和实际回收之间的差距意味着一个候选机制正在工作，并且**最强证据是创建文件夹的逐字命令**，因为复制动词单独决定了空间语义。在理论化之前，在会话历史中找到它；文件夹名或基于大小的推断不是机制。只有在找不到命令时，差距才会保持 `unknown`——不要用听起来最合理的机制来替代可以证明的机制。

    机制由 `du` 报告的内容和删除释放的内容区分（所有四个指标均在 2026-09-19、1 GiB 源、漂移控制下测量）：

    | 创建者 | `du` 名义 | 删除副本释放 |
    |---|---|---|
    | `cp` (裸) / `cp -a` | 完整的，按路径计数 | 完整的 | 独立的 inodes，独立的 extents |
    | **`cp -c` / `cp -cR`** (clonefile) | **完整的，按路径计数** | **≈0** | **不同的 inode，`nlink=1`，共享 extent** |
    | `ln` / `cp -l` (硬链接) | **计数一次**——兄弟读取 `0` | **≈0** | **相同的 inode，`nlink=2`** |
    | 本地 APFS 快照 | 完整的 | 在快照被缩减之前 ≈0 | `tmutil listlocalsnapshots /` |

    此表存在以消除两个陷阱。**克隆文件和硬链接行在 `du` 上相反但在删除时相同**——两者都释放 ≈0，因此“删除它释放了 nothing”无法将它们区分开，而 `du` 可以：硬链接的兄弟计数一次（或作为 `0`），克隆文件的副本计数完整。并且**校准错误的复制动词证明不了任何东西**：由于探测使用了裸 `cp`，而文件夹是用 `cp -cR` 构建的，因此 98 GiB 的差距被归因于错误的机制两次。在执行任何删除之前，使用与创建命令相同的标志运行探测。克隆文件值得标记为常见情况——macOS `cp` 默认为 `-c` 使用它，并且为交付/套件复制的目录通常带有它。

## 阶段协议

使用此状态机进行每个清理：

1. **观察——只读。** 捕获身份、磁盘基线、疑似子系统状态和配置、物理分配和关键服务健康。
1b. **在不可避免时授权有状态观察。** 如果需要更深层的证据需要创建临时容器、拉取镜像、挂载卷或写入快照，首先完成元数据观察，列出确切的观察命令及其副作用，并获得单独批准。观察批准不是清理批准。
2. **计划——无变异。** 首先通过入口门（四个步骤：目标确认、分类表、门规则、检查器——见下文），然后解释发现、命令、影响、恢复、预期释放和成功标准。在确认门停止。
3. **执行——仅批准的范围。** 在执行前立即重新读取实时状态，然后单独运行每个已批准命令并检查其退出状态和后置条件。
4. **验证——独立的重读。** 再次测量磁盘空间和子系统状态，重新检查受保护服务，并观察足够长的时间以检测立即填充。

不要将阶段 2 和 3 压缩为一个消息。旁边打印的计划与清理命令不是确认门。

## 阶段 1：只读诊断

### 建立基线

至少捕获：

```bash
/bin/date "+%F %T %Z %z"
/usr/sbin/scutil --get ComputerName
/usr/sbin/scutil --get LocalHostName
/usr/bin/sw_vers
/bin/df -k /System/Volumes/Data
/bin/df -h /System/Volumes/Data
```

使用 `df -k` 进行计算，使用 `df -h` 进行人类可读报告。将扩展、标签或旧报告视为提示，直到实时命令确认它。

在未知来源扫描之前建立成功目标。精确复制用户提供的空闲空间或容量目标。如果用户未提供，则报告当前值并要求 GiB、容量百分比或两者作为目标；不要编造一个。命名嫌疑诊断可以继续而没有清理目标，但有序的未知来源扫描不能声称停止条件，直到目标明确。

保持此第一阶段只读。不要运行 `scripts/cleanup_report.py`：它会创建本地状态目录和快照文件。在远程目标上，始终在该主机上运行直接的 `df` 命令；本地助手必须不能错误地测量控制器 Mac。

### 在广泛扫描之前遵循命名嫌疑

- 查询子系统自身的状态和设置。
- 在权限和用户范围允许时，仅在该确切数据路径上使用有界的 `du` 测量物理分配。
- 区分逻辑内容大小、稀疏文件表观大小、可清除空间和物理分配的字节。
- 对于 APFS 克隆，将 `du` 标记为路径计费或名义，而不是物理：共享 extent 可以分配给每个路径，因此实际释放直到删除和 `df` 读回后才会未知。
- 对于疑似增长的日志，在两个或多个时间戳记录确切的文件大小。一个大型文件或一个最近的 mtime 不会证明持续增长。
- 捕获用户标记为关键的所有共存服务的当前进程、监听器、启动机制和支持的健康探测。在每个检查点重新解析 PIDs。

如果已知嫌疑单独可以满足用户的空闲空间目标，则不要扫描无关的个人或开发目录“以防万一”。

### 当来源未知时的通用分析

运行能识别足够物理空间以满足目标的最小有序序列。仅在具有受支持的精确操作和可辩护的预期物理释放的候选者可以满足它时才停止。原始分配总量、逻辑缓存大小、共享 Docker 层、Trash 移动和未经验证的“潜在节省”不会满足停止条件。

不要让物理置信度排名隐藏用户最大的可见热点。当名义/路径计费候选者大于建议的操作时，显示两个数字并解释其物理释放的不确定性。按可辩护的物理释放、安全性和努力排名；将名义大小报告为单独的列，而不是将其无声地视为零或完全可回收。

| 顺序 / 信号 | 只读操作 | 停止或继续 |
|---|---|---|
| 1. 始终 | 捕获身份和 `df -k/-h`；清点用户排除项 | 在目标不匹配时停止 |
| 2. 缓存/日志压力，以及 `~/Library/Caches`、`~/Library/Logs`，以及 XDG 开发缓存被批准为仅用户范围的读取范围 | `uv run scripts/analyze_caches.py --user-only --include-dev` | 当测量的候选者可以满足目标时停止 |
| 3. 开发工具存在且脚本的固定范围被批准 | `uv run scripts/analyze_dev_env.py` 读取 Docker/包管理器以及现有的 `~/Projects`、`~/workspace`、`~/dev`、`~/src` 和 `~/code` 根 | 将 Docker/OrbStack 结果路由到其专用参考；当任何固定根超出范围时跳过此辅助工具 |
| 4. 未安装应用程序的残留物合理且其固定根被批准 | `uv run scripts/find_app_remnants.py` 读取 `/Applications`、`~/Applications` 和四个记录的 `~/Library` 应用程序状态根 | 将每个结果视为候选者，永远不会证明放弃；当该范围未获批准时跳过 |
| 5. 一个包含内容的路径被明确批准 | `uv run scripts/analyze_large_files.py --threshold 100MB --path "<approved-path>"` | 当没有批准路径时，不要将 `~`、下载、文档或数据卷根替换为 `--` |
| 6. 在有界检查之后仍然未知，并且用户明确批准 Mole 的固定广泛扫描根 | 阅读 `references/mole_integration.md` 并通过 TTY 使用 `mo analyze` | Mole 不能接受任意的路径范围；当批准比其记录的根更窄时跳过它 |

一个 `<approved-path>` 是用户命名或在其范围描述后明确接受的精确路径。如果不存在，则跳过大文件和重复内容扫描，说明此证据分支未获授权，并继续使用非内容承载证据。除非用户单独授权该更改，否则不要在只读阶段安装或升级 Mole。

Mole 的分析器扫描一组固定的内容，包括家目录、应用程序数据、系统库、应用程序和卷。在结果内部的导航不会使底层的扫描路径范围。如果该广泛的读取范围未获批准，则不要运行 Mole；停止已收集的有界证据或请求缺少的扫描授权。对于明确批准的重复文件调查，阅读 `references/cleanup_targets.md` 中的“可选重复文件”部分。它是只读的，并且永远不会使用自动删除选项。

**一个大型数据文件夹不是缓存——建议其删除需要一个证据链，而不是大小排名。** 当发现一个大的项目资产/媒体/数据集目录（不是缓存，不是应用程序残留物）时，**不要仅凭大小将其放入操作集**：阅读 `references/proving-redundancy-before-deletion.md` 并爬上它的梯子（文件级重复 → 创建来源 → 引用检查 → 会话历史工具调用普查 → .DS_Store → 项目的决策记录）之前不要提出任何东西。交付物是证据表；无法证明的行（纯手动使用）永远不会交给用户，也永远不会掩盖它。

当发现被扩展到子代理时，每个代理都只返回候选者和测量值——分类、接受和提议发生在运行阶段 2 入口门的会话中。子代理的清单是分类表的输入，永远不会是计划。

### Docker 和 OrbStack

在报告 Docker 节省之前阅读 `references/docker_analysis.md`。单独列出每个 image、container 和 volume；检查引用和类似数据库的内容；使用实际的稀疏文件分配而不是表观大小。报告为悬挂的资源不是其数据无价值的证据。构建缓存测量受支持，但构建缓存删除故意超出范围，因为可用的 Docker 控制是 prune-family 操作。
