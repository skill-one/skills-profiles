# 深入研究

创建具有严格格式控制、证据映射、来源管理和多轮综合的高保真研究报告。

## 架构：主代理 + 子代理

```
主代理 (协调器 — 最小化原始搜索上下文)
  |
  P0: 环境和来源策略设置
  |
  P1: 问题和主张映射 (决策问题、证据路线、停止规则)
  |
  派发 ──→ 子代理 A ──→ 写入 task-a.md ──┐
           ──→ 子代理 B ──→ 写入 task-b.md ──┤ (并行)
           ──→ 子代理 C ──→ 写入 task-c.md ──┘
  |                                               |
  |     research-notes/  <────────────────────────┘
  |
  P2: 构建证据包 + 引用注册表
  P3: 带有反证和未知因素的证据映射大纲
  P4: 从证据包中生成草稿；重新打开决定性原始文件
  P5: 反复审阅 (主张、置信度、替代方案)
  P6: 验证每个承重主张和确切事实
  P7: 精炼 → 最终报告带置信度标记
```

**上下文规范：** 在任务工作区中保留原始搜索结果噪声。将证据包传递给主代理，包括定位器和简短的来源摘录。笔记是路由辅助工具，不是权威：主代理必须为每个承重主张、冲突主张以及报告中使用的确切数字/日期/引文打开原始来源。

## 模式选择

在开始之前确定研究模式：

| 维度 | 选项 |
|-----------|---------|
| **主题模式** | 企业研究 (公司/企业) 或 一般研究 (行业/政策/技术) |
| **深度模式** | 标准 (多个决策问题或有争议的证据) 或 轻量级 (一个有边界的问题和小的证据表面) |

- **企业研究模式**：以问题为导向的公司研究，仅在它们有助于回答决策时才选择分析框架
- **一般研究模式**：带来源治理的标准 P0-P7 研究流程
- **深度选择**：根据未解决问题的数量和后果选择，而不是提示长度、任务数量或目标字数

## 来源治理 (V6)

### 来源可访问性分类

按可访问性对每个来源进行分类：

| 可访问性 | 定义 | 示例 | 使用规则 |
|--------------|------------|----------|------------|
| `public` | 任何外部研究人员都可以无身份验证访问 | 公共网站、新闻文章、WHOIS (无隐私)、学术论文 | ✅ 总是允许 |
| `semi-public` | 需要注册或有限访问 | LinkedIn 个人资料、Crunchbase 基本版、行业报告 (免费版) | ✅ 允许披露 |
| `exclusive-user-provided` | 用户的付费订阅、私有 API、专有数据库 | Crunchbase Pro、PitchBook、私有数据源、内部数据库 | ✅ **允许** 用于第三方研究 |
| `authorized-first-party` | 用户授权的关于用户自己组织的记录、交易或工作 | 合同、发票、CRM 记录、会议记录 | ✅ 可能建立内部业务事实；标记来源 |

**第一方边界：** 用户授权的记录可以建立组织做了什么、同意什么、支付什么、交付什么或观察到什么。它们不作为对市场地位、客户情绪、监管合规性或第三方主张的独立外部验证。永远不要将内部记录重新标记为外部发现。

**✅ EXCLUSIVE INFORMATION ADVANTAGE**: 你 SHOULD:
- 使用用户的 Crunchbase Pro 研究竞争对手
- 使用用户的专有数据库进行市场研究
- 使用用户的私有 API 进行投资分析
- 利用用户提供的任何专有来源进行第三方研究

### 来源类型标签

每个来源还必须使用以下标签：

| 标签 | 定义 | 示例 |
|-------|------------|----------|
| `official` | 主要来源、官方文件 | 公司 SEC 文件、政府报告、官方博客 |
| `academic` | 同行评审研究 | 期刊文章、会议论文、学位论文 |
| `secondary-industry` | 专业分析 | 行业报告、分析师覆盖、贸易出版物 |
| `journalism` | 新闻报道 | 可靠的媒体机构、调查性报道 |
| `community` | 用户生成的内容 | 论坛、评论、社交媒体、问答网站 |
| `other` | 未分类或混合 | 聚合器、未验证来源 |

**覆盖诊断：** 跟踪来源数量、域名、来源类型组合和集中度以揭示覆盖不足。仅凭这些总数单独通过或不通过研究。根据每个决策问题和承重主张是否具有适合目的的证据、是否寻求反证以及剩余未知因素是否明确来设置门禁。

## AS_OF 日期政策

在 P0 中明确设置 AS_OF 日期。对于所有与时间相关的声明：
- 每个引用都包含来源发布日期
- 如果来源比相关时间范围旧，则降低置信度
- 为每个声明类别定义新鲜度范围并标记其外部的材料；一个通用年龄截止日期只是一个诊断

## P0: 环境与策略设置

在开始之前检查功能：

| 检查 | 要求 | 缺失的影响 |
|-------|-------------|-------------------|
| 必要的证据通道可用 | 必要的 | 范围变窄或受影响的问号标记为未知 |
| 原始来源检索可用 | 对于承重主张是必要的 | 不要将摘要/片段提升为最终证据 |
| 子代理派发 | 优选 | 降级为顺序 |
| 文件系统可写 | 必要的 | 仅限内存笔记 |

设置策略变量：
- `AS_OF`: 今天的日期 (YYYY-MM-DD) - 对于有时间主题是强制性的
- `MODE`: 标准 (默认) 或 轻量级，由问题映射证明
- `SOURCE_TYPE_POLICY`: 强制执行官方/学术/次要/新闻/社区/其他标签
- `COUNTER_REVIEW_PLAN`: 每个临时结论会推翻哪些证据

报告：`[P0 完成] 子代理：{是/否}。模式：{标准/轻量级}。AS_OF：{YYYY-MM-DD}。`

在研究特定公司时，使用专用工作流程按问题路由证据。将六个维度视为覆盖图，而不是强制报告大纲。

### 企业工作流程概述

```
企业研究进度：
- [ ] E1: 摄取 — 确认公司实体、研究深度、格式合同
- [ ] E2: 以问题为导向的证据收集跨相关维度
  - [ ] D1: 公司基本要素 (实体、成立、融资、所有权)
  - [ ] D2: 业务与产品 (细分、产品、收入结构)
  - [ ] D3: 竞争地位 (行业排名、竞争对手、壁垒)
  - [ ] D4: 金融与运营 (3 年财务报表、效率指标)
  - [ ] D5: 近期发展 (6 个月事件、战略信号)
  - [ ] D6: 内部/专有来源 (或注明限制)
- [ ] E3: 可选分析框架根据决策选择 (或无)
- [ ] E4: 每个阶段转换时的主张/证据/未知检查
- [ ] E5: 使用用户请求的结构起草
- [ ] E6: 多轮起草 + UNION 合并 (与一般步骤 6-7 相同)
- [ ] E7: 提交草稿供人工审查和迭代
```

## P1: 研究任务板

将任务分解为决策问题。仅在单独的证据路线或专业知识使工作更清晰时创建任务。

每个任务分配包括：
- **专家角色**：专家角色 (例如，"政策历史学家"、"生态系统映射器")
- **目标**：一句调查目标
- **查询**：2-3 个预先计划的搜索查询
- **深度**：DEEP (获取 2-3 篇完整文章) 或 SCAN (片段足够)
- **输出**：研究笔记文件路径
- **并行组**：组 A (独立) 或组 B (依赖于组 A)
- **决策问题**：这个任务帮助回答的确切问题
- **承重主张**：会改变结论的临时主张
- **反证**：什么会削弱或推翻每个主张
- **证据路线**：哪些来源所有者或记录系统实际上可以观察到事实
- **停止规则**：什么被视为已回答、矛盾或仍然未知

### 任务分解规则

1. 每个任务涵盖一个连贯的子主题，专家会拥有
2. 组 A 任务必须逻辑上独立；通过基础证据、所有权和动机评估来源独立性，而不是域名数量
3. 每个并行组最多 3 个任务 (并发限制)
4. 每个任务必须标记时间敏感的主张、寻求反证和预期的引用老化风险

### 企业研究集成

在企业研究模式下，将问题映射到相关维度，而不是自动创建所有六个任务：
- 任务 A：公司基本要素 (实体、成立、融资、所有权)
- 任务 B：业务与产品 (细分、产品、收入结构)
- 任务 C：竞争地位 (行业排名、竞争对手、壁垒)
- 任务 D：金融与运营 (3 年财务报表、效率指标)
- 任务 E：近期发展 (6 个月事件、战略信号)
- 任务 F：授权第一方记录 (当它们可以回答业务事实时；永远不会计为外部证实)

报告：`[P1 完成] {N} 个任务在 {M} 个组中。正在派发组 A。`

## 企业研究模式 (专用管道)

在研究特定公司时，将每个决策问题通过相关企业维度。使用维度查找缺失的证据路径；不要默认运行所有六个或添加量化框架。

### E1: 摄取

与上面 P0/P1 相同，加上：
- 确认正在研究的确切法律实体 (母公司 vs 子公司)
- 根据决策问题、证据难度和请求的输出选择研究深度；页数是规划诊断仅
- 确定任何特定的比较目标 (基准公司)

## P2: 派发 + 调查

子代理使用 [references/subagent_prompt.md](references/subagent_prompt.md) 执行任务，并以 [references/research_notes_format.md](references/research_notes_format.md) 的格式输出证据包。

### 使用子代理 (Claude Code / Cowork / DeerFlow)

1. 并行派发组 A 任务 (最多 3 个并发)
2. 每个子代理搜索、获取并标记来源类型
3. 每个来源行包括 `Source-Type` 和 `As Of`
4. 等待组 A 完成
5. 派发组 B (可以读取组 A 笔记)

### 子代理输出要求

每个 task-{id}.md 必须包含：
- **问题状态**：已回答 / 矛盾 / 未知，以及停止证据
- **来源部分**：来自实际检索的稳定定位器，包括来源类型、可访问性、日期和来源家族身份
- **主张-证据表**：主张、证据摘录/定位器、范围、置信度，以及是否打开原始来源
- **反证和未知**：什么被寻求、什么被找到、什么仍然未解决

### 无子代理 (降级模式)

主代理顺序执行任务，充当每个专家。保留原始搜索噪声在最终证据包之外；当重现性重要时保留查询日志。

### 企业研究：六维度收集

遵循 [references/enterprise_research_methodology.md](references/enterprise_research_methodology.md) 进行：
- 每个维度详细的收集工作流 (查询策略、数据字段、验证)
- 数据来源优先级矩阵 (P0-P3 排名)
- 声明特定证实和冲突处理规则

**关键原则**：
- 证据驱动：每个结论都必须追溯到可引用的来源
- 证实：第二个来源仅在它是独立于相同的底层披露或数据集时才增加权重
- 限制判断：明确标记推测，避免未经证实的声明
- 结构化呈现：通过表格、列表、层次结构呈现复杂信息

在每个维度完成后运行 L1 质量检查 (见 enterprise_quality_checklist.md)。

每个任务的状态：`[P2 任务-{id} 完成] {N} 个来源，{M} 个发现。`
所有状态：`[P2 完成] {N} 个任务完成，{M} 个总来源。正在构建注册表。`

### E3: 仅在有用时选择分析框架

仅在用户的决策从框架中受益时加载 [references/enterprise_analysis_frameworks.md](references/enterprise_analysis_frameworks.md)。使用 SWOT 进行战略选项框架，使用风险矩阵进行具有明确概率/影响输入的决策，并且仅在权重和比例合理时使用评分。而不是编造条目或精度，而是省略框架。

分析完成后运行 L2 质量检查。

### E4: 质量控制

从 [references/enterprise_quality_checklist.md](references/enterprise_quality_checklist.md) 进行三级检查：
- **L1 (数据)**：来源数量、归因、交叉验证、时效性
- **L2 (分析)**：决策问题覆盖范围、主张支持、反证以及使用框架时的框架适应性
- **L3 (文档)**：结构合规性、格式一致性、可读性、附录

### E5: 使用企业模板起草

仅在它与请求的决策匹配时使用来自 enterprise_quality_checklist.md 的 7 章企业报告模板。否则根据问题映射调整结构。
1. 公司概述
2. 业务与产品结构
3. 市场与竞争地位
4. 金融与运营分析
5. 风险与关注点
6. 近期发展
7. 综合评估与结论

附录：数据来源索引、术语表、免责声明。

### E3-E7: 企业分析、起草和审查

- **E3: 结构化分析** — 仅当它改进决策且其输入合理时，从 [references/enterprise_analysis_frameworks.md](references/enterprise_analysis_frameworks.md) 选择框架；否则使用主张-证据表
- **E4: 质量控制** — 根据 [references/enterprise_quality_checklist.md](references/enterprise_quality_checklist.md) 运行 L1/L2/L3 检查
- **E5: 起草** — 使用 7 章企业模板
- **E6-E7: 多轮起草和审查** — 与 P4-P7 下方相同

## P3: 引用注册表 + 来源治理

主代理读取所有任务笔记并构建统一注册表。

### 注册表过程

1. 读取每个任务文件的主张-证据表和来源
2. 合并来源；重复 URL 但也组多个从同一研究、申报、新闻稿、数据集、采访或赞助商派生的出版物为一个证据家族
3. 按首次出现分配顺序 [n] 编号
4. 标签：来源类型、可访问性、AS_OF 日期、证据家族、权威、独立性限制和任务 ID
5. 构建一个主张覆盖矩阵：支持证据、反证、决定性原始已检查和剩余未知
6. 记录排除的来源及其原因。不要仅因任意分数排除来源；将其限制为它可以支持的声明

### 注册表输出格式

```
引用注册表

批准：
[1] 作者/组织 — 标题 | URL | 来源类型: 官方 | 可访问性: 公共 | 证据家族: 申报-123 | 日期: 2026-03-01 | task-a
[2] ...

排除：
x 来源 | URL | 来源类型: 次要行业 | 可访问性: 公共 | 证据家族: 未知 | 原因: 无法检索原始记录；摘要不能承载主张

诊断：{批准}/{总数}, {N} 域名, {N} 独立证据家族, 来源类型组合
覆盖范围：{回答}/{总数问题}; {N} 未解决的承重主张
```

**关键规则：** 这些 [n] 是最终的。P5 只能引用批准列表。排除的来源永远不会再次出现。

**授权第一方处理：** 在研究用户的自己组织或资产时：
1. 使用授权的原始记录为它们直接记录的内部业务事实
2. 标记为 `authorized-first-party` 并说明是谁的记录
3. 仅当声明需要外部证实时才寻求外部来源
4. 保持结论明确：内部建立、外部证实、矛盾或外部未知

**专有来源处理：** 当用户明确提供他们的付费订阅或私有 API 用于第三方研究时 (例如，"使用我的 Crunchbase Pro 研究竞争对手")，你应该：
1. 接受它为 "exclusive-user-provided" 可访问性
2. 使用它作为竞争优势
3. 正确引用注册表
4. 如果没有独立的等价物，保留来源的有效第一方范围并标记外部声明为未知

报告：`[P3 完成] {回答}/{总数} 问题回答。{N} 个承重主张支持，{M} 个未解决。来源总数是诊断。`

### 处理信息黑箱

在研究没有公共足迹的实体时：

**外部研究人员会发现什么：**
- WHOIS: 隐私保护 → 没有所有者信息
- 网络搜索：没有新闻，没有新闻稿
- 社交媒体：没有公司页面
- 商业注册处：没有公共 API 或需要本地访问
- 结果：**完整信息黑箱**

**正确响应：**
```
发现：无公开信息可用

检查的来源：
- WHOIS (公共): 隐私保护 [失败]
- 公司注册处 (公共): 访问被拒绝/无 API [失败]
- 新闻媒体：没有报道 [失败]
- 公司网站：占位符仅 [最小]

结论：从外部视角无法验证公司存在
找到的来源：0 (或最小，例如，仅 WHOIS 显示域名存在)
置信度：N/A - 证据不足
```

**不要：**
- ❌ 将内部建立的事实描述为独立外部证实
- ❌ 单独基于域名注册就假设公司存在
- ❌ 用推测填充缺失数据
- ❌ 当它直接建立内部业务事实时丢弃授权第一方记录

**要：**
- ✅ 清楚地说明外部研究人员可以/不能验证
- ✅ 将授权第一方事实作为内部建立，与外部可见性分开报告
- ✅ 记录所有失败的搜索尝试
- ✅ 将主张标记为 [未验证] 或完全省略
- ✅ 当证据无法回答决策问题时缩小或停止
- ✅ 建议直接联系进行尽职调查

## P4: 证据映射大纲

主代理读取证据包 + 注册表以构建大纲，然后重新打开决定性原始文件。

1. 识别跨任务模式
2. 主题优先设计，而不是任务顺序优先设计
3. 将每个部分映射到特定发现，并使用来源编号
4. 标记需要反复审阅的部分
5. 使用 AS_OF 检查标记时效性敏感的主张
6. 将每个承重主张标记为支持 / 矛盾 / 未知

大纲格式：
```
## N. {部分标题}
来源：[1][3][7] 来自任务 a, b
主张：{来自任务-a 发现 3 的主张}, {来自任务-b 发现 1 的主张}
反主张候选：{替代解释}

差距：{有限的官方证据}
```

## P5: 从笔记起草

使用 [references/report_template_v6.md](references/report_template_v6.md) 按部分逐个编写，并根据用户的格式合同进行调整。

**规则：**
- 每个事实声明都需要引用 [n]
- 数字/百分比必须有来源
- 每个部分添加 **置信度标记**：高/中/低及其理由
- 添加 **反主张句子** 当证据冲突时
- 新来源只能通过相同的注册表和验证路径进入
- 使用 [未验证] 对于未支持的说法

**反幻觉：**
- 主代理从不将笔记视为权威；为每个承重主张、冲突主张以及报告中使用的确切数字/日期/引文重新打开原始来源
- 主代理从不编造 URL；每个定位器必须来自实际搜索结果
- 主代理从不信任笔记作为权威 — 使用包进行路由，然后重新打开决定性原始来源
- 主代理从不编造数据；未支持的主张保持未知或被省略

状态：`[P5 进行中] {N}/{M} 部分，~{字} 字。`

## P6: 反复审阅 (强制)

对于每个主要结论，执行相反观点的检查。这些检查不自动需要另一个代理或团队；使用独立审查员仅当用户请求或适用的工作区指令要求时：

1. **结论可能错误吗？**
2. **哪些高影响主张依赖于一个证据家族，即使许多域名重复它？**
3. **哪些主张缺乏可以直接观察事实的来源？**
4. **是否使用过时的来源进行时效性敏感的主张？**
5. **仅报告证据支持的问题；零发现是一个有效结果。** 明确说明未解决的未知性。不要编造问题或重复完成的检查仅为了达到问题数量。

### 使用反复审阅团队 (可选)

对于全面的并行审查，使用反复审阅团队：

```bash
# 1. 准备输入
counter-review-inputs/
  ├── draft_report.md
  ├── citation_registry.md
  ├── task-notes/
  └── p0_config.md

# 2. 并行派发到 4 个专家代理
SendMessage to: claim-validator
SendMessage to: source-diversity-checker
SendMessage to: recency-validator
SendMessage to: contradiction-finder

# 3. 等待所有专家完成

# 4. 发送到协调员进行综合
SendMessage to: counter-review-coordinator
  inputs: [4 个专家报告]

# 5. 接收最终 P6 反复审阅报告
```

有关详细使用说明，请参阅 [references/counter_review_team_guide.md](references/counter_review_team_guide.md)。

### 手动反复审阅 (默认)

当没有选择审查团队时，直接执行这些证据检查。如果用户请求或适用的工作区指令要求，获取个人独立审查：
- 验证每个承重主张与其决定性原始来源
- 检查是否证实来源真正独立并且能够观察主张
- 验证时效性敏感主张上的 AS_OF 日期
- 记录对立解释

### 输出

仅包括证据支持的有争议内容在最终报告中。仅当存在此类争议时才使用编号。如果没有，请明确说明；永远不要填充占位符争议以满足模板。单独报告未解决的未知性，或说明不再存在。

```
## 核心争议 / Key Controversies
未发现有证据支持的核心争议。
未解决的不确定性：无。
```

上面的示例仅适用于两个声明都受完成的检查支持；否则列出实际的争议或未解决的问题。

报告：`[P6 完成] {N} 个问题发现：{关键} 关键, {高} 高, {中} 中。`

## P7: 验证

在最终确定之前进行交叉检查：

1. **注册表交叉检查**：列出报告中的每个 [n] 与批准的注册表
2. **承重检查**：追溯到每个决定性结论、确切数字/日期/引文和争议性事实的原始来源
3. **样本低影响主张**：仅作为诊断使用点检查；当其中一个失败时，扩展到受影响的完整类别
4. **验证未重新出现的排除来源**
5. **检查关键主张的证据家族集中度**

报告：`[P7 完成] {N} 个点检查, {M} 个违规修复。`

## 反模式

- 无并行起草的单一通过
- 按部分而不是完整报告草稿拆分通过
- 忽略格式合同或用户模板
- 没有引用或证据表映射的主张
- 没有标记差异的冲突日期
- 没有验证就复制外部 AI 输出
- 删除中间草稿或原始研究输出
- **主代理信任笔记作为权威** — 使用包进行路由，然后重新打开决定性原始来源
- **编造 URL** — 仅使用来自实际搜索结果的 URL
- **复活排除的来源** — P3 排除的来源永远不会再次出现
- **缺少 AS_OF 对于时效性敏感的主张** — 总是包括来源日期
- **跳过证据检查** — 完成 P6，仅报告支持的证据，并允许零问题当没有问题建立时。
- **FIRST-PARTY OVERCLAIM** — 授权记录可以建立内部业务事实，但不能模仿外部验证
- **忽略专有来源** — 当用户提供 Crunchbase Pro 等用于竞争对手研究时，使用它
