# 会议记录助手

通过迭代审查，将原始会议记录转化为全面、有证据支持的会议纪要。

## 快速入门

**预处理（可选但推荐）：**
- **文档转换**：使用 `doc-to-markdown` 技能先将 .docx/.pdf 转换为 Markdown（保留表格/图片）
- **记录清理**：使用 `transcript-fixer` 技能修复 ASR/STT 错误（如果记录质量差）
- **上下文文件**：准备 `context.md` 包含团队目录，以便准确识别发言人

**核心工作流程：**
1. 读取用户提供的记录
2. 如果用户提供了项目特定的上下文文件（可选），则加载（可选）
3. **智能文件命名**：根据内容自动生成文件名（见下文）
4. **发言人识别**：如果记录中有 "Speaker 1/2/3"，首先要求用户在源平台上标记发言人并重新导出（见步骤 1.5 阶段 0）；仅从文本中推断作为后备
5. **多轮生成**：使用多个传递或隔离的上下文子代理，使用 UNION 合并
6. 使用 `[references/completeness_review_checklist.md](references/completeness_review_checklist.md)` 进行自我审查
7. 向用户展示草稿，供人类逐行审查
8. **跨 AI 比较**（可选）：人类可能提供其他 AI 工具（例如，Gemini，ChatGPT）的输出 - 合并以减少偏差
9. 反馈迭代，直到人类批准最终版本

### 智能文件命名

根据记录内容自动生成输出文件名：

**模式**：`YYYY-MM-DD-<主题>-<类型>.md`

| 组件 | 来源 | 示例 |
|------|------|------|
| 日期 | 记录元数据或首次提及的日期 | `2026-01-25` |
| 主题 | 主要讨论主题（2-4 个词，kebab-case） | `api-design`, `product-roadmap` |
| 类型 | 会议类别 | `review`, `sync`, `planning`, `retro`, `kickoff` |

**示例：**
- `2026-01-25-order-api-design-review.md`
- `2026-01-20-q1-sprint-planning.md`
- `2026-01-18-onboarding-flow-sync.md`

**在写入之前要求用户确认建议的文件名。**

```

- [ ] 步骤 1.5：发言人识别（如果记录中有 "Speaker 1/2/3"）
  - [ ] 阶段 0 首先要求用户在源平台上标记发言人（飞书妙记 / 腾讯会议），重新导出，使用标记的记录
  - [ ] 仅作为后备（源标记不可用或用户拒绝）：

  - [ ] 将每个声明与可检索层（关键决策 / 行动项 / 待办事项 / 开放性问题）进行匹配，按组件，使用词汇锚点
  - [ ] 在任何推广之前进行撤权扫描；使用 [self-test promoted] 标签 + 可搜索的逐字引用；不确定 → 开放性问题

- [ ] 步骤 4：向用户展示草稿以供人类审查
- [ ] 步骤 5：跨 AI 比较（如果人类提供外部 AI 输出）

注意：<output_dir> = 最终会议纪要保存的目录（例如，project-docs/meeting-minutes/）
注意：<transcript-name> = 从记录文件派生的名称（例如，2026-01-14-api-design）
```

### 步骤 1：读取和分析记录

分析记录以识别：
- 会议主题和与会者
- 带有支持性引文的重大决策
- 带有所有者的行动项
- 延迟事项 / 开放性问题

### 步骤 1.5：发言人识别（当需要时）

**触发条件**：记录仅包含通用标签，如 "Speaker 1", "Speaker 2", "发言人1" 等。

#### 阶段 0：源端标记（始终首先尝试）

当记录来自支持手动发言人标记的平台（飞书妙记 / 腾讯会议，或任何具有会议编辑页面的工具）时，**停止并要求用户在源平台上标记发言人，然后重新导出/重新导入标记的记录**，然后生成会议纪要。将源页面链接发送给用户——它通常在记录的 frontmatter 中 (`minute_url`, 会议 URL)。

为什么优于推断：
- 平台标记是实际听到声音的人类——权威来源。基于文本的推断只能解决在会议中被提及的发言人；其他人则保持猜测。
- 合并的段落在文本中无法单独恢复——无论推断多么努力都无法修复，但源端重新标记可以修复。
- 推断输出强制 `[inferred]` 标记到处都是，并且需要逐个发言人的手动审查回合；源标记产生干净的真相一次。

仅当以下情况时才回退到阶段 A–C 以下：
（a）用户明确表示要推断，或
（b）源无法标记（原始音频文件，没有平台页面，没有编辑权限）。在回退中，每个映射都必须附带证据和置信度，未解决的标签保持不变（永远不要强制分配），当用户稍后标记源时，回去更正会议纪要。

**回退方法**（受 Anker 技能启发）：

#### 阶段 A：特征分析（模式识别）

对每个发言人进行分析：

| 特征 | 查找内容 |
|------|----------|
| **词数** | 总词数（高 = 高级/领导，低 = 观察者） |
| **段落数** | 他们说话的次数（频繁 = 积极参与者） |
| **平均段落长度** | 每次发言的平均词数（长 = 演讲者，短 = 响应者） |
| **填充词比率** | 填充词的百分比（对/嗯/啊/就是/然后） - 低 = 准备充分的发言人 |
| **说话风格** | 正式/非正式，技术深度，决策权威 |
| **主题重点** | 他们讨论最多的领域（后端，前端，产品等） |
| **交互模式** | 其他人是如何问他们的？他们是否分配任务？ |

**分析输出示例：**
```
发言人分析:
┌──────────┬────────┬──────────┬─────────────┬─────────────┬────────────────────────┐
│ 发言人  │ 词数   │ 段落   │ 平均长度  │ 填充词 %    │ 角色猜测             │
├──────────┼────────┼──────────┼─────────────┼─────────────┼────────────────────────┤
│ 发言人1  │ 41,736 │ 93       │ 449 字符   │ 3.6%        │ 主讲人 (99% 的内容)│
│ 发言人2  │ 101    │ 8        │ 13 字符    │ 4.0%        │ 对话者 (简短的响应)  │
└──────────┴────────┴──────────┴─────────────┴─────────────┴────────────────────────┘

推断规则:
- 占比 > 70% + 平均长度 > 100字 → 主讲人
- 平均长度 < 50字 → 对话者/响应者
- 语气词占比 < 5% → 正式/准备充分
- 语气词占比 > 10% → 非正式/即兴发言
```

#### 阶段 B：上下文映射（如果提供了上下文文件）

当用户提供项目上下文文件（例如，`context.md`）时：

1. 加载团队目录部分
2. 将特征模式与已知团队成员匹配
3. 跨参考角色与说话模式

**上下文文件应包含：**
```markdown
## 团队目录
| 名称 | 角色 | 沟通风格 |
|------|------|---------------------|
| Alice | 后端负责人 | 技术，果断，分配后端任务 |
| Bob | 产品经理 | 产品导向，询问需求问题 |
| Carol | TPM | 流程导向，跟踪时间线/资源 |
```

#### 阶段 C：继续进行前的确认

**关键**：永远不要默默假设发言人身份。

向用户展示分析摘要：
```
发言人分析:
- 发言人 1 → Alice (后端负责人) - 基于：技术重点，任务分配模式
- 发言人 2 → Bob (产品经理) - 基于：产品问题，需求讨论
- 发言人 3 → Carol (TPM) - 基于：时间线问题，资源跟踪

请确认或更正这些映射，然后再继续。
```

在用户确认后，在整个文档中一致地应用映射。

### 步骤 1.7：记录质量评估（可选）

评估记录质量以确定处理深度：

**评分标准（1-10 分级）：**

| 因素 | 分数影响 |
|------|-------------|
| **内容量** | >10k 字符：+2，5-10k：+1，<2k：上限为 3 |
| **填充词比率** | <5%: +2, 5-10%: +1, >10%: -1 |
| **发言人清晰度** | 主要发言人 >80%: +1 (清晰的演讲者) |
| **技术深度** | 高技术内容: +1 |

**质量级别：**

| 分数 | 级别 | 处理方法 |
|------|------|---------------------|
| ≥8 | **高** | 完整结构的会议纪要，包括所有部分，图表，引文 |
| 5-7 | **中** | 标准会议纪要，重点于关键决策和行动项 |
| <5 | **低** | 仅摘要 - 简要要点，跳过详细转录 |

**示例评估：**
```
📊 记录质量评估:
- 内容: 41,837 字符 (+2)
- 填充词比率: 3.6% (+2)
- 主要发言人: 99% (+1)
- 技术深度: 高 (+1)
→ 质量分数: 10/10 (高)
→ 推荐: 完整结构的会议纪要，包括图表
```

**用户决策点**：如果质量低 (<5)，要求用户：
> "记录质量低 (碎片对话/噪音较多). 生成完整会议纪要还是仅摘要？"

### 步骤 2：多轮初始生成（关键）

**单次传递绝对会丢失内容。** 使用多轮生成并使用**冗余完整传递**：

#### 核心原则：多次完整传递 + UNION 合并

每个传递生成**完整的会议纪要（所有部分）**。多个传递使用隔离的上下文可以捕获不同的细节。UNION 合并整合所有发现。

**❌ 错误：窄焦点传递**（浪费 token，导致偏差）
```
传递 1: 仅提取决策
传递 2: 仅提取行动项
传递 3: 仅提取讨论
```

**✅ 正确：完整传递使用隔离的上下文**
```
传递 1: 读取记录 → 生成完整会议纪要 → 写入到: <output_dir>/intermediate/<transcript-name>/version1.md
传递 2: 新鲜上下文 → 读取记录 → 生成完整会议纪要 → 写入到: <output_dir>/intermediate/<transcript-name>/version2.md
传递 3: 新鲜上下文 → 读取记录 → 生成完整会议纪要 → 写入到: <output_dir>/intermediate/<transcript-name>/version3.md
合并: UNION 所有版本，激进地包含所有图表 → draft_minutes.md
最终: 将草稿与记录进行比较，添加任何遗漏 → final_minutes.md
```

#### 策略 A：顺序多传递（每个传递生成完整会议纪要）

```
传递 1: 读取记录 → 生成完整会议纪要 → 写入到: <output_dir>/intermediate/version1.md
传递 2: 新鲜上下文 → 读取记录 → 生成完整会议纪要 → 写入到: <output_dir>/intermediate/version2.md
传递 3: 新鲜上下文 → 读取记录 → 生成完整会议纪要 → 写入到: <output_dir>/intermediate/version3.md
合并: 读取所有版本 → UNION 合并（合并重复内容）→ 写入到: draft_minutes.md
最终: 将草稿与记录进行比较 → 添加任何遗漏 → final_minutes.md
```

#### 策略 B：并行多代理（首选）

**必须使用 Task 工具**以并行方式启动多个子代理，具有**隔离的上下文**，每个代理生成**完整的会议纪要**：

**使用 Task 工具的实现：**
```
// 并行启动所有 3 个子代理（必须是单条消息，3 个 Task 工具调用）
Task(subagent_type="general-purpose", prompt="从记录生成完整会议纪要...", run_in_background=false) → version1.md
Task(subagent_type="general-purpose", prompt="从记录生成完整会议纪要...", run_in_background=false) → version2.md
Task(subagent_type="general-purpose", prompt="从记录生成完整会议纪要...", run_in_background=false) → version3.md

合并阶段:
  读取: <output_dir>/intermediate/<transcript-name>/version1.md
  读取: <output_dir>/intermediate/<transcript-name>/version2.md
  读取: <output_dir>/intermediate/<transcript-name>/version3.md
  → UNION 合并，合并重复内容，包含所有图表 → 写入到: draft_minutes.md

最终审查:
  读取: draft_minutes.md
  读取: original_transcript.md
  → 比较 & 添加遗漏 → 写入到: final_minutes.md
```

**子代理提示必须包含：**
1. 完整的记录文件路径
2. 完整的输出文件路径（version1.md, version2.md, version3.md 在记录特定的子目录中）
3. 要加载的上下文文件（如果提供项目特定的上下文，meeting_minutes_template.md）
4. 用户提供的参考图像/文档
5. 输出语言要求（匹配用户的语言偏好，保留英文技术术语）
6. 引文格式要求（见引文格式要求部分）
7. 决策识别规则：通过元素而不是措辞识别决策——嵌入在叙述/案例评论中的指令，如果它具有权威（谁），行动（做什么），以及可选的条件（何时）。精度限制：当不确定某项是否是真正的决策时，将其路由到开放性问题而不是关键决策（永远不要通货膨胀决策表）。

多次完整传递有效的原因：
- 每个传递独立地分析相同的内容
- 不同的上下文状态捕获不同的细节（单个传递无法捕获所有内容）
- 传递 1 可能捕获决策 X 但遗漏行动项 Y
- 传递 2 可能捕获行动项 Y 但遗漏决策 X
- UNION 合并捕获 X 和 Y

隔离上下文的重要性：
- 每个传递/代理都从新鲜的状态开始，没有先前的假设
- 没有传递之间的交叉污染
- 不同的“视角”自然地从上下文隔离中产生

#### 使用文件系统进行渐进式上下文卸载（使用文件系统）

**关键**：将每个传递输出写入文件，而不是对话上下文。**

**路径约定**：所有中间文件应创建在 `<output_dir>/intermediate/` 下的**特定于记录的子目录**，以避免不同记录处理时发生冲突。

**关键**：使用记录特定的子目录结构：

```
<output_dir>/intermediate/<transcript-name>/version1.md
<output_dir>/intermediate/<transcript-name>/version2.md
<output_dir>/intermediate/<transcript-name>/version3.md
```

示例：如果最终会议纪要将保存为 `project-docs/meeting-minutes/2026-01-14-api-design.md`，则：
- 中间文件: `project-docs/meeting-minutes/intermediate/2026-01-14-api-design/version1.md`
- 这可以防止在处理多个记录时发生冲突
- `intermediate/` 文件夹应添加到 `.gitignore`（临时工作文件，不是最终交付物）
- **记录特定的子目录** 在处理多个记录时防止冲突

```
// 首先创建记录特定的子目录
mkdir: <output_dir>/intermediate/<transcript-name>/

// 并行启动所有 3 个子代理（必须是单条消息，3 个 Task 工具调用）
Task 1 → 写入到: <output_dir>/intermediate/<transcript-name>/version1.md (完整会议纪要)
Task 2 → 写入到: <output_dir>/intermediate/<transcript-name>/version2.md (完整会议纪要)
Task 3 → 写入到: <output_dir>/intermediate/<transcript-name>/version3.md (完整会议纪要)

合并阶段:
  读取: <output_dir>/intermediate/<transcript-name>/version1.md
  读取: <output_dir>/intermediate/<transcript-name>/version2.md
  读取: <output_dir>/intermediate/<transcript-name>/version3.md
  → UNION 合并，合并重复内容，包含所有图表 → 写入到: draft_minutes.md

最终审查:
  读取: draft_minutes.md
  读取: original_transcript.md
  → 比较 & 添加遗漏 → 写入到: final_minutes.md
```

**文件系统进行上下文卸载的好处：**
- 对话上下文保持干净（避免 token 溢出）
- 中间结果持久化（如果需要可以重新读取）
- 每个传递都从新鲜的内容窗口开始
- 合并阶段仅读取所需内容
- **人类可以检查中间文件以供审查** - 对理解每个传递捕获了什么至关重要
- 支持非常长的记录，超出上下文限制
- **启用后置调试** - 如果最终输出缺少内容，人类可以跟踪哪个传递遗漏了它

**重要**：始终在记录特定的子目录中保留中间版本：
- `<output_dir>/intermediate/<transcript-name>/version1.md`, `version2.md`, `version3.md` - 每个子代理输出
- 这些文件帮助人类审查者理解合并过程
- 不要在合并后删除中间文件
- 人类可能想要比较中间版本以了解覆盖差距
- **将 `intermediate/` 添加到 `.gitignore`** - 这些是临时工作文件，不是最终交付物
- **记录特定的子目录** 在处理多个记录时防止冲突

#### 输出要求

- **中文输出**，保留英文技术术语
- **基于证据的决策** - 每项重大决策都需要支持性引文
- **结构化部分** - 执行摘要，关键决策，讨论，行动项，待办事项
- **正确的引文格式** - 见引文格式要求部分
- **Mermaid 图表**（强烈建议）- 图表使会议纪要超越了纯文本。它们使复杂的讨论对人类审查者来说更容易理解。
- **以上下文开头的文档结构** - 将所有审查过的工件（UI 模拟图，API 文档，设计图像）放在文档顶部（在元数据之后，执行摘要之前）以建立上下文，然后再阅读讨论；将图像复制到 `meeting-media/<meeting-name>/` 文件夹，并使用 `![description](meeting-media/...)` 语法嵌入行内；包含与视觉的简要描述 - 这创建了“高级”人类可读的会议纪要，读者在阅读讨论之前理解了讨论的内容

## 人在回路迭代（必要）

会议纪要**不是一次性输出**。高质量的会议纪要通过多次审查周期才能生成：

### 人类审查为何关键

1. **术语冲突**：人类知道现有系统命名（例如，"Note" 已经意味着评论在现有系统中）
2. **领域上下文**：人类可以发现术语可能与其他术语混淆（例如，"UserProfile" vs "Account"）
3. **组织知识**：人类知道团队约定和先前的决策
4. **完整性差距**：人类可以要求“深度审查”审查，当感觉缺少内容时

### 示例迭代模式

```
第一轮：初始生成
  └─ 人类审查：检查原始记录以查找遗漏的内容
第二轮：深度记录审查，添加遗漏内容
  └─ 人类审查：UserProfile 与现有 Account 实体命名冲突
第三轮：更新术语以使用 "CustomerProfile" 考虑
  └─ 人类审查：Note 字段与现有评论系统冲突
第四轮：更新以使用 "Annotation" 考虑
  └─ 人类批准：最终版本准备就绪
```

### 关键原则

**AI 生成第一稿；人类完善到最终版本。** 永远不要假设第一输出是完整的或使用正确的术语。始终鼓励人类审查并准备好多次迭代周期。

## 反模式

- ❌ **当源平台支持标记时，从文本中推断发言人身份** - 首先要求用户在飞书妙记 / 腾讯会议源平台上标记发言人并重新导出（步骤 1.5 阶段 0）；文本推断仅解决在会议中被提及的发言人；无法从文本中恢复合并的段落
- ❌ **使用与生成草稿相同的心理模型进行自我审查** - 步骤 3 的清单只能验证传递已经分类的内容；共享的盲点（例如，叙述性声音指令）会存活下来。运行步骤 3.5 的新鲜上下文检索自我测试；其提取器永远不会看到草稿
- ❌ **在自我测试缺失扫描之前推广自我测试缺失** - 在会议中撤权的决策，推广为原样：将虚假的决策写入表格——这是自我测试使会议纪要比跳过它更糟糕的唯一方法
- ❌ **将自我测试报告为二进制“通过”** - 总是报告 "枚举 N / 匹配 M / 推广 K / 不确定列表"；一个绿灯带数字训练人类停止阅读
- ❌ **单次传递生成** - 单次传递绝对会丢失内容
- ❌ **非重叠部分** - 每个传递必须覆盖完整的记录，而不是按部分分割
- ❌ **窄焦点传递** - 每个传递必须生成完整的会议纪要（所有部分），而不是仅一个部分类型（浪费 token，导致偏差）
- ❌ 通用摘要没有支持性引文
- ❌ 行动项分配给“团队”而不是特定的人
- ❌ 缺少数值（优先级，范围，状态计数）
- ❌ 状态机不完整的状况
- ❌ 循环辩论逐字转录而不是总结
- ❌ 在多版本合并过程中删除内容
- ❌ 声称“没有缺失”而不进行逐部分审查
- ❌ 将第一稿视为最终稿而不进行人类审查
- ❌ 使用术语而不检查是否存在冲突
- ❌ 子代理之间共享上下文（导致交叉污染和遗漏内容）
- ❌ 将所有中间输出保留在对话上下文中（导致 token 溢出，使用文件系统）
- ❌ **纯文本会议纪要没有图表** - 架构/模式讨论值得视觉表示
- ❌ **删除合并后的中间文件** - 保留供人类审查和调试
- ❌ **盲目复制外部 AI 输出** - 始终在合并之前与记录进行验证
- ❌ **忽略跨 AI 比较机会** - 不同的 AI 模型捕获不同的细节
- ❌ **使用顺序子代理执行** - 必须使用多个 Task 工具调用在单条消息中并行启动 v1, v2, v3 子代理
- ❌ **平面中间目录** - 必须使用记录特定的子目录 `intermediate/<transcript-name>/` 以避免不同记录处理时发生冲突
- ❌ **行内引文格式** - 引文必须使用单独行的 blockquote 格式，而不是行内 `> "quote"`
- ❌ **在合并过程中遗漏图表** - 必须激进地包含所有来自所有版本的图表，即使它们看起来相似
- ❌ **突出显示琐碎的术语差异** - 不要突出显示发言人之间的 trivial 术语差异（例如，“backend architecture” vs “backend” 或 “API” vs “endpoint”）；这些是等效术语，突出显示这些差异是不尊重的
- ❌ **跨部分重复内容** - 不要在多个部分中重复相同的信息（例如，API 端点表在“讨论”和“参考”中）；将内容放在一个权威位置，如果需要则引用它
- ❌ **创建不存在的链接** - 不要创建指向仓库中不存在的文件的 markdown 链接（例如，`[doc.md](reviewed-document)`）；使用纯文本表示不在仓库中的外部/本地文档
- ❌ **在合并过程中丢失内容** - 在移动或合并部分时，验证所有项目符号和详细信息是否保留；永远不要总结掉像“支持批量操作”或“按钮触发自动保存”这样的具体细节
- ❌ **在角色标题后附加域详细信息** - 使用 ONLY Team Directory 中的角色列进行发言人归属（例如，"Backend", "Frontend", "TPM"）；不要附加专长，如“Backend, Infrastructure”或“Backend, Business Logic” - 所有具有相同角色的团队成员应具有相同的归属
