# 提示优化器

## 概述

使用 EARS（易于需求语法的方法）将模糊的提示优化为精确、可执行的具体规范——这是一种劳斯莱斯级的方法论，用于将自然语言转换为结构化、可测试的需求。

**灵感来源：** 该技能将 EARS 与领域理论相结合的方法受到了 [阿星AI工作室 (A-Xing AI Studio)](https://mp.weixin.qq.com/s/yUVX-9FovSq7ZGChkHpuXQ) 的启发，该工作室展示了 EARS 在提示增强方面的实际应用。

**四层增强过程：**

1. **EARS语法转换** - 将描述性语言转换为规范性规范
2. **领域理论应用** - 应用相关的行业框架（GTD、BJ Fogg、格式塔心理学等）
3. **示例提取** - 提取具体的用例并使用真实数据
4. **结构化提示生成** - 使用角色/技能/工作流/示例/格式框架进行格式化

## 何时使用

在以下情况下使用：
- 用户提供模糊的功能请求（“构建一个仪表板”、“创建一个提醒应用”）
- 需求缺乏特定的条件、触发器或可衡量的结果
- 自然语言描述需要转换为可测试的规范
- 用户明确要求提示优化或需求细化

## 六步优化工作流程

### 第1步：分析原始需求

识别弱点：
- **过于宽泛** - “添加用户认证” → 缺少密码要求、会话管理
- **缺少触发器** - “发送通知” → 缺少通知触发的时间和原因
- **模糊的行动** - “使其用户友好” → 没有可衡量的可用性标准
- **没有约束** - “处理支付” → 缺少安全、合规要求

### 第2步：应用EARS转换

将需求转换为EARS模式。有关完整的语法规则，请参阅 `references/ears_syntax.md`。

**五个核心模式：**
1. **通用模式**：`系统应当 <行动>`
2. **事件驱动模式**：`当 <触发器>，系统应当 <行动>`
3. **状态驱动模式**：`当 <状态>，系统应当 <行动>`
4. **条件模式**：`如果 <条件>，系统应当 <行动>`
5. **不希望的行为**：`如果 <条件>，系统应当阻止 <不希望的行动>`

**快速示例：**
```
之前： "创建一个具有任务管理的提醒应用"

之后（EARS）：
1. 当用户创建任务时，系统应当指导将任务分解为可执行的子任务
2. 当任务截止日期在30分钟内且用户尚未开始时，系统应当发送带有声音警报的通知
3. 当用户完成子任务时，系统应当更新进度并提供积极反馈
```

**转换清单：**
- [ ] 识别隐含的条件并使其明确
- [ ] 指定触发事件或状态
- [ ] 使用精确的行动动词（应当、必须、应该）
- [ ] 添加可衡量的标准（“在30分钟内”、“至少8个字符”）
- [ ] 将复合需求分解为原子声明
- [ ] 移除模糊语言（“用户友好”、“快速”）

### 第3步：识别领域理论

将需求与已建立的框架匹配。有关完整目录，请参阅 `references/domain_theories.md`。

**常见的领域映射：**
- **生产力** → GTD、番茄工作法、艾森豪威尔矩阵
- **行为改变** → BJ Fogg模型（B=MAT）、原子习惯
- **用户体验设计** → 希克定律、菲茨定律、格式塔心理学原理
- **安全性** → 零信任、纵深防御、隐私设计

**选择过程：**
1. 从需求关键词中识别主要领域
2. 匹配2-4个互补的理论
3. 将理论原则应用于特定功能
4. 在增强的提示中引用理论以增加可信度

### 第4步：提取具体示例

生成具有真实数据的特定示例：
- 用户场景： "当用户在移动设备上登录..."
- 数据示例： "产品：'笔记本电脑'，价格：$999，库存：15"
- 工作流示例： "任务：撰写报告 → 子任务：研究（2小时），草稿（3小时），编辑（1小时）"

示例必须具有 **真实性**、**具体性**、**多样性**（成功/失败/边缘情况）和 **可测试性**。

### 第5步：生成增强提示

使用标准框架进行结构化：

```markdown
# 角色
[具有领域专业知识的特定专家角色]

## 技能
- [核心能力1]
- [核心能力2]
[列出5-8个与领域理论一致的技能]

## 工作流
1. [阶段1] - [关键活动]
2. [阶段2] - [关键活动]
[完整的逐步流程]

## 示例
[具有真实数据的具体示例，而不是占位符]

## 格式
[精确的输出规范：
- 文件类型、结构要求
- 设计/样式期望
- 技术约束
- 交付清单]
```

**质量标准：**
- **角色具体性**： "专注于时间管理应用的 产品设计师" > "设计师"
- **理论基础**：明确引用框架
- **可执行的工作流**：清晰的输入/输出和决策点
- **具体示例**：真实数据，而不是 "示例1"、"示例2"
- **可衡量的格式**：具体要求，而不是 "良好设计"

### 第6步：展示优化结果

以结构化格式输出：

```markdown
## 原始需求
[用户的模糊需求]

**识别的问题：**
- [问题1：例如，"缺少特定的触发条件"]
- [问题2：例如，"没有可衡量的成功标准"]

## EARS转换
[编号的EARS格式化需求列表]

## 领域与理论
**主要领域：** [例如，认证安全性]

**适用理论：**
- **[理论1]** - [简要相关性]
- **[理论2]** - [简要相关性]

## 增强提示
[完整的角色/技能/工作流/示例/格式提示]

---

**如何使用：**
[简要的关于如何应用提示的指导]
```

## 快速参考

**应该做：**
✅ 将复合需求分解（每个需求一个EARS声明）
✅ 指定可衡量的标准（数字、时间段、百分比）
✅ 包括错误/边缘情况
✅ 基于已建立的理论
✅ 使用具有真实数据的具体示例

**不应该做：**
❌ 避免模糊语言（“快速”、“用户友好”）
❌ 不要假设隐含的知识
❌ 不要在一个声明中混合多个行动
❌ 示例中不要使用占位符
