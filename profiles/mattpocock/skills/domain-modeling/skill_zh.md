# 领域建模

在设计中主动构建并完善项目的领域模型。这是一项*主动*的练习：对术语进行质疑、构思边界情形场景，并在概念清晰的那一刻及时记录术语表与决策。（仅仅*阅读* `CONTEXT.md` 以获取词汇并不是这项技能：这只是一个任何技能都能做的单行习惯。这项技能的适用场景是当你正在改变模型，而不是仅仅消费模型。）

## 文件结构

大多数仓库具有单一上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录下存在 `CONTEXT-MAP.md`，则仓库包含多个上下文。该地图指向每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← system-wide decisions
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← context-specific decisions
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需创建文件：只有当你有内容可写时才创建。如果没有 `CONTEXT.md`，则在第一个术语被解析时创建它。如果没有 `docs/adr/`，则在需要第一个 ADR 时创建它。

## 在会话期间

### 与术语表进行挑战

当用户使用的术语与 `CONTEXT.md` 中现有的表述相冲突时，应立即指出："术语表中将'取消'定义为 X，但你似乎指的是 Y。到底是哪个？"

### 精炼模糊语言

当用户使用模糊或含义重叠的术语时，提出一个精确的标准术语。"你说的是'账户'：是指 Customer 还是 User？这是两个不同的概念。"

### 讨论具体场景

在讨论领域关系时，用具体场景对其进行压力测试。构思能够探测边界情形的场景，迫使用户明确区分不同概念之间的边界。

### 与代码交叉参照

当用户说明某事物如何运作时，检查代码是否一致。如果发现矛盾，及时指出："你的代码取消了所有 Orders，但你刚才说可以部分取消。哪一个才是正确的？"

### 内联更新 CONTEXT.md

当术语被解析后，立即在 `CONTEXT.md` 中更新。不要批量处理：它们发生时就及时记录。请使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应完全不含实现细节。不要将 `CONTEXT.md` 视为规范、草稿或实现决策的存储仓库。它仅是一份术语表，别无其他。

### 谨慎提供 ADR

仅在以下三个条件同时满足时才提出创建 ADR 的请求：

1. **难以逆转**：日后改变想法的成本是显著的
2. **脱离上下文令人惊讶**：未来读者会疑惑"他们为何如此做？"
3. **真实权衡的结果**：存在真实的替代方案，且你是基于特定原因选择了其中之一

若三者中缺少任何一项，则跳过 ADR。请使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
