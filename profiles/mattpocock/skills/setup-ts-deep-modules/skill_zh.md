# 设置 TS 深模块

将此仓库中的每个包都设置为**深模块**：在小的接口背后隐藏大量行为。一个包的公共表面是其**入口点**（位于包根目录的文件），而其子文件夹中的所有内容都是隐藏的。这项技能会安装 [dependency-cruiser](https://github.com/sverweij/dependency-cruiser) 以及使入口点成为唯一入口的规则，然后验证这些规则的有效性。

对于词汇（深模块、接口、接口、深度），使用 "codebase-design" 调用技能工具，并使用其语言。

## 强制执行的形状

```
src/packages/
  <name>/
    index.ts        ← 一个入口点（公共的）。从外部导入这个。
    client.ts       ← 另一个入口点。包可以公开多个。
    lib/            ← 实现：对外隐藏，可以互相导入。
    tests/          ← 同一位置的测试和固定装置（一个子文件夹，所以是私有的）。
```

公共表面是包的**根文件**，而不是一个指定的 `index.ts`。按惯例，实现代码位于 `lib/` 中，测试位于 `tests/` 中，从而为每个包提供相同的两文件夹形状。规则本身是通用的：*任何*子文件夹中的*任何*内容都是私有的，因此你永远不会扩展配置来添加一个文件夹。

四条规则，全部为 `error`：

1. **入口点边界**：包外的代码（应用代码或另一个包）只能导入该包的入口点（其根文件），而不能导入其子文件夹中的任何内容。
2. **包内自由**：一个包的文件可以自由地互相导入。
3. **通过入口点进行测试**：`<pkg>/tests/` 下面的文件可以导入任何包的入口点及其自己的 `tests/` 固定装置，但不能导入任何包的子文件夹内部（甚至不能导入自己的）。跨包的集成测试是允许的；深层次导入是不允许的。
4. **无循环**：没有依赖循环。

**入口点，而不是一个桶。** 由于公共表面是*每个*根文件，一个包可以公开多个小的入口点（`index.ts`、`client.ts`、`server.ts`），而不是通过一个巨大的 `index.ts` 来传递所有内容。重新导出整个子树的后端文件是不被鼓励的；保持入口点小，并将实现隐藏在子文件夹中。

分层（哪些包可以依赖哪些包）是一个*不同*的问题，并且作为此仓库配置中的注释桩留给该仓库填充。

## 步骤

### 1. 检测环境

- **包管理器**：`pnpm-lock.yaml` → pnpm，`yarn.lock` → yarn，`bun.lockb` → bun，否则 npm。使用它来执行下面的每个命令（`pnpm`/`yarn`/`npm run`/`bunx`）。
- **包根目录**：如果存在 `src/`，则使用 `src/packages`，否则使用 `packages`。如果仓库已经有一个不同的明显惯例，请与用户确认选择。
- **现有配置**：检查是否存在 `.dependency-cruiser.*` 文件。如果存在，则**不要**覆盖它：合并四条规则和选项，并告诉用户你添加了什么。

**完成时**：包管理器、包根目录和现有配置状态都已知晓。

### 2. 安装 dependency-cruiser

使用检测到的包管理器将 `dependency-cruiser` 作为开发依赖项安装。

**完成时**：`dependency-cruiser` 在 `devDependencies` 中。

### 3. 编写配置

将 [`dependency-cruiser.config.cjs`](./dependency-cruiser.config.cjs) 复制到仓库根目录作为 `.dependency-cruiser.cjs`。将 `PACKAGES_ROOT` 设置为步骤 1 中检测到的根目录。规则是基于路径深度和扩展名无关的，因此不需要进行其他调整。

**完成时**：`.dependency-cruiser.cjs` 存在，具有正确的 `PACKAGES_ROOT`，并且四条禁止规则存在。

### 4. 将其连接到检查

- 添加一个 `lint:boundaries` 脚本：`depcruise <packages-root>`（或 `depcruise src`）。
- 将其合并到仓库的伞形检查命令中，该命令已经运行类型检查（例如 `check` / `ci` / `validate` 脚本）。**不要**触碰 `tsconfig` 或添加路径别名。
- 如果没有伞形脚本，添加 `lint:boundaries` 并告诉用户将其包含在 CI 中。

**完成时**：`lint:boundaries` 存在，并且作为类型检查的同一命令的一部分运行。

### 5. 搭建示例包

创建一个已提交的 `<packages-root>/example/` 作为可复制模板：

- `index.ts` 是一个入口点。导出一个委托到内部文件的功能（这样包明显是*深*的，而不是一个传递式）。
- `lib/impl.ts`：一个位于**子文件夹**中的内部文件，由 `index.ts` 导入，但对外不可达。
- `tests/example.test.ts` 只导入 `../index`（一个入口点）并对其公共功能进行断言。

告诉用户这是一个起始模板，可以复制或删除。

**完成时**：示例包存在，通过根入口点公开其行为，并将 `impl` 隐藏在子文件夹中。

### 6. 验证规则的有效性

这是整个技能的完成标准：一个配置在违反时不失败是无用的。

1. 运行 `lint:boundaries`。它必须在干净的示例上**通过**。
2. 临时在 `tests/example.test.ts` 中添加一个深层次导入（例如 `import { thing } from "../lib/impl"`）。再次运行 `lint:boundaries`；它必须**失败**，并显示 `tests-through-entrypoints`。
3. 撤销深层次导入。再次运行一次，它必须**通过**。

**完成时**：你已经观察到通过，然后在深层次导入上失败，然后再次通过。如果步骤 2 没有失败，则规则没有正确连接，因此请在完成前修复。

### 7. 记录惯例

在包文件夹中（`<packages-root>/README.md`，位于它所管理的包旁边）编写一个 `README.md`，涵盖：`src/packages/<name>/` 的布局（根目录的入口点，`lib/` 用于实现，`tests/` 用于测试）、"只通过包的入口点（其根文件）导入"，以及如何运行 `lint:boundaries`。**明确禁止**后端文件：公开多个小的入口点，而不是通过一个索引重新导出整个子树。

然后从仓库的 agent-instructions 文件中添加一个**上下文指针**（如果存在 `CLAUDE.md`，则指向 `CLAUDE.md`，否则指向 `AGENTS.md`，如果两者都不存在，则创建 `AGENTS.md`）。一行就足够了，例如 `Packages are deep modules: see [src/packages/README.md](./src/packages/README.md) before adding or importing one.` 这使得代理发现边界规则，而不是遇到它。

**完成时**：`<packages-root>/README.md` 存在并禁止后端文件，并且仓库的 `CLAUDE.md`/`AGENTS.md` 链接到它。

## 注意事项

- 配置的 `$1` 反向引用（dependency-cruiser 的组匹配）是允许包访问其自己的内部内容，而外部人员无法访问的原因。不要将它们展平为每个包的单独规则。
- 公共与私有的决定基于**深度**：包的根文件是入口点；子文件夹中的任何内容都是私有的。传统的子文件夹是 `lib/`（实现）和 `tests/`，但规则没有硬编码它们：任何子文件夹都是私有的，因此新文件夹永远不会需要配置更改。添加一个入口点只是添加一个根文件（没有后端文件）。
- 包是**扁平的**：根下的一个直接子级。一个包的内部可以嵌套到任意深度；一个包不能包含另一个包。
- 使用 `.cjs`（而不是 `.js`），以便配置的 `module.exports` 在 `"type": "module"` 仓库中也能工作。
