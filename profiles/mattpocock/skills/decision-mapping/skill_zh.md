当需要利用多个智能体会话将一个松散的想法转化为计划时，调用此技能。它会在 Markdown 文件中创建一个有状态决策图，并引导用户在一系列票据中完成决策，以解决开放问题——可能需要原型设计、研究或深度审问。该地图与领域无关：它可以规划工程工作、课程内容，或任何符合相同结构的其他内容。

## 决策图

决策图是一个单一的紧凑 Markdown 文件，每个规划工作对应一个，随项目一起进行 git 跟踪。它是标准产物——**整个地图会作为上下文加载到每个会话中**，因此必须保持紧凑。

票据期间创建的资源应从地图中链接引用，而非在地图内部重复。

### 结构

条目（"票据"），每个都是一个独立部分，以简短的短横线风格 slug 作为键，读起来像一个微型标题（例如 `relational-db`、`auth-strategy`、`cache-layer`）——简洁到足以保持 token 高效，且在地图内唯一。

```markdown
## relational-db: Relational Or Non-Relational Database?

Blocked by: <slug>, <slug>
Status: open | in-progress | resolved
Type: Research | Prototype | Grilling | Task

### Question

<question-here>

### Answer

<answer-here>
```

slug 是规范标识符，用于每个 `Blocked by` 边和正文引用中；冒号后的标题为可选。当票据中 `Blocked by` 列表里的所有票据均为 `resolved` 时，该票据是 **已解锁** 的。一个会话通过设置 `Status: in-progress` 并保存地图来 **认领** 其票据，在任何工作之前完成，以便并发会话跳过它。

每张票据的大小应针对一个 100K token 智能体会话。

## 票据类型

共有四种票据类型：

- **Research**：阅读文档、第三方 API、或本地资源如知识库。生成一个 Markdown 摘要作为资源。当需要当前工作目录之外的知识时使用。
- **Prototype**：通过制作一个廉价、粗糙、具体的产物来提升讨论的保真度——大纲、粗略想法、存根，或通过 `/prototype` 技能编写的 UI/逻辑代码。将原型作为资源创建。当"它应该是什么样子"或"它应该如何表现"是关键问题时使用。
- **Grilling**：与智能体进行的对话。使用 `/grilling` 和 `/domain-modeling` 技能。一次问一个问题。默认情况。
- **Task**：讨论推进之前必须完成的实质性手工工作——无需决策、原型设计或研究。将数据从一处移动到另一处、注册第三方服务、配置访问权限。智能体能自动化的地方进行自动化；否则向人工提供精确的清单让他们手动完成。工作完成后即视为 **已解决**；答案记录完成的工作以及后续票据所依赖的任何产生的事实（凭证位置、新 URL、行数等）。

## 战争迷雾

地图在边界之外**故意**是不完整的。你的工作是调查边界，并按顺序解决票据以推进边界。逐节点推散战争迷雾——直到到达终点的路径清晰且无票据剩余。

## 调用

两个分支。无论哪种情况，**每个会话都以一个 [Handoff](#handoff)** 结束——每会话最多解决一张票据。

### 创建地图

用户以松散的想法调用。

1. 运行一个 `/grilling` 和 `/domain-modeling` 会话以浮现开放决策。逐一个问题。
2. 编写新的决策图——大部分为迷雾，识别边界，可简单判定的内容内联解决。
3. 交接。地图构建是单个会话的工作；不要同时解决票据。

### 梳理地图

用户以指向现有地图的路径调用。票据 slug **可选**——如果没有，则由你选择下一个决策，而非用户。

1. 将 **整个地图** 作为上下文加载。
2. 选择票据。如果用户指定了某个票据，则使用它。否则按文档顺序选择第一个 **已解锁** 的 `open` 票据 [认领它](#structure)：设置 `Status: in-progress` 并在任何工作之前保存。
3. 解决它，按需调用技能——包括任何 `## Notes` 区块中提到的技能。如有疑问，使用 `/grilling` 和 `/domain-modeling`。
4. 在票据正文中记录答案并设置 `Status: resolved`。
5. 添加新发现的票据，并设置正确的 `Blocked by` 边。如果所做的决策使地图其他部分失效，更新或删除那些节点。
6. 交接。

用户可并行运行未解锁的票据，因此预期有其他智能体在自己的会话中编辑地图。

## 交接

每个会话结束时，清空上下文并开启一个或多个新的会话。以 **Next steps**（下一步）区块结束，供用户复制粘贴。两种情况：

**仍有未解锁的票据。** 列出当前未解锁的票据，然后给出两个复制粘贴选项：一个用于单个会话的纯命令（由你选择下一个票据），以及每个未解锁票据一个固定的命令用于并行运行。每行粘贴一个全新的窗口——打开一个、一些或全部。

> **Next steps** — 3 tickets unblocked: `auth-strategy`, `cache-layer`, `rate-limits`。
> 清空上下文，然后开启新会话。
>
> **One session** — 解决下一个未解锁票据：
> ```
> 以 <path> 处的地图调用 `/decision-mapping`。
> ```
>
> **Parallel** — 每窗口一行，最多全部 3 个：
> ```
> 以 <path> 处的地图调用 `/decision-mapping`，票据 `auth-strategy`。
> 以 <path> 处的地图调用 `/decision-mapping`，票据 `cache-layer`。
> 以 <path> 处的地图调用 `/decision-mapping`，票据 `rate-limits`。
> ```

**没有未解锁的票据了。** 迷雾被推到足够远，到达终点的路径已清晰——地图已完成。（初始的 grilling 也可能完全浮现不出迷雾，这种情况下从未需要构建地图。）建议直接实施，或使用 `/to-prd` 安排多会话实现。

## 注意事项

一个可选区块，声明 **领域**、每个会话应 **consult**（咨询）的技能，以及规划浮现出的任意自由形式常设偏好。
