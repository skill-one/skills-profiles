# 诊断

针对棘手 Bug 的学科。仅在明确说明的情况下才能跳过阶段。

在探索代码库时，使用项目的领域术语表来获得相关模块的清晰心智模型，并检查你接触区域的 ADR（架构决策记录）。

## 第一阶段 — 建立反馈循环

**这是关键技能。** 其他都是机械操作。如果你有一个针对 Bug 的快速、确定性、可由代理运行的通过/失败信号，你就会找到原因——二分法、假设测试和仪器化都只是消耗这个信号。如果你没有，那么盯着代码也无法解决问题。

在此阶段投入不成比例的努力。**要积极。要富有创造力。拒绝放弃。**

### 构建反馈循环的方法——大致按此顺序尝试

1. 在能够触及 Bug 的任何接口处添加**失败的测试**——单元测试、集成测试、端到端测试。
2. 对运行中的开发服务器执行**Curl / HTTP 脚本**。
3. 使用包含输入数据的**CLI 调用**，并将标准输出与已知良好的快照进行比对。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，对 DOM/控制台/网络进行断言。
5. **重放捕获的跟踪记录。** 将真实的网络请求/有效载荷/事件日志保存到磁盘；在隔离的代码路径中重放它。
6. **一次性测试框架。** 启动系统的一个最小子集（一个服务、模拟依赖项），通过单个函数调用执行 Bug 代码路径。
7. **属性/模糊循环。** 如果 Bug 是“有时输出错误”，运行 1000 个随机输入并寻找失败模式。
8. **二分法测试框架。** 如果 Bug 出现在两个已知状态（提交、数据集、版本）之间，自动化“在状态 X 下启动、检查、重复”的操作，以便你可以 `git bisect run`。
9. **差异循环。** 将相同输入通过旧版本与新版本（或两个配置）运行并比对输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人类点击，使用 `scripts/hitl-loop.template.sh` 驱动他们，以便循环仍然结构化。捕获的输出会反馈给你。

构建正确的反馈循环，Bug 就有 90% 的几率被修复。

### 对反馈循环本身进行迭代

将循环视为一个产品。一旦你拥有一个循环，就要问：

- 我能让它更快吗？（缓存设置、跳过无关的初始化、缩小测试范围。）
- 我能让信号更清晰吗？（针对特定症状进行断言，而不是“没有崩溃”。）
- 我能让它更确定性吗？（固定时间、设置随机数种子、隔离文件系统、冻结网络。）

一个 30 秒的 flaky 循环几乎等同于没有循环。一个 2 秒的确定性循环是一种调试超能力。

### 非确定性 Bug

目标是干净的复现，但**更高的复现率**。循环触发 100 次，并行化，增加压力，缩小时间窗口，注入睡眠。一个 50%-flake 的 Bug 是可调试的；1% 就不可调试——持续提高复现率直到它可调试。

### 当你确实无法构建一个循环时

停止并明确说明。列出你尝试过的方法。向用户请求：(a) 访问能够复现它的环境，(b) 捕获的工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产仪器化的权限。**不要**在没有循环的情况下进行假设。

在进入第二阶段之前，确保你有一个你信任的循环。

## 第二阶段 — 复现

运行循环。观察 Bug 出现。

确认：

- [ ] 循环产生了用户描述的**失败模式**——而不是附近发生的不同失败。错误的 Bug = 错误的修复。
- [ ] 失败在多次运行中可复现（或对于非确定性 Bug，以足够高的频率可复现以进行调试）。
- [ ] 你捕获了确切的症状（错误消息、错误输出、慢速时间）以便后续阶段可以验证修复是否确实解决了它。

在复现 Bug 之前不要继续。

## 第三阶段 — 假设

在测试任何假设之前，生成 **3–5 个排序的假设**。单假设生成会锚定第一个看似合理的想法。

每个假设必须是**可证伪的**：说明它做出的预测。

> 格式："如果 <X> 是原因，那么改变 <Y> 将使 Bug 消失 / 改变 <Z> 将使其更糟。"

如果你无法说明预测，假设就是一个感觉——丢弃或使其更清晰。

**在测试之前向用户展示排序的列表。** 他们通常有领域知识可以立即重新排序（“我们刚刚部署了 #3 的更改”），或者知道他们已经排除的假设。廉价的检查点，巨大的时间节省。如果用户不在，不要阻塞——如果用户不在，继续使用你的排序。

## 第四阶段 — 仪器化

每个探测必须对应第三阶段的一个特定预测。**一次只改变一个变量。**

工具偏好：

1. 如果环境支持，使用**调试器 / REPL 检查**。一个断点胜过十个日志。
2. 在区分假设的边界处添加**目标日志**。
3. 从来不要“记录所有内容并使用 grep”。

**每个调试日志都使用一个唯一的前缀进行标记**，例如 `[DEBUG-a4f2]`。在最后清理时，这变成一个 grep。未标记的日志会保留；标记的日志会消失。

**性能分支。** 对于性能回归，日志通常是错误的。相反：建立基线测量（计时框架、`performance.now()`、分析器、查询计划），然后进行二分法。先测量，后修复。

## 第五阶段 — 修复 + 回归测试

在修复之前编写回归测试——但只有当存在**正确的接口**时。

一个正确的接口是指测试在调用点执行**真实的 Bug 模式**。如果唯一可用的接口太浅（单个调用者测试，而 Bug 需要多个调用者；无法复制触发 Bug 的链的单元测试），那里的回归测试会提供虚假的信心。

**如果不存在正确的接口，那本身就是一个发现。** 记录下来。代码库架构正在阻止 Bug 被锁定。将此问题标记为下一阶段的任务。

如果存在正确的接口：

1. 将最小化的复现转换为该接口处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 重新运行第一阶段的反馈循环针对原始（未最小化）场景。

## 第六阶段 — 清理 + 事后分析

在宣布完成之前必须执行：

- [ ] 原始复现不再复现（重新运行第一阶段的循环）
- [ ] 回归测试通过（或接口缺失已记录）
- [ ] 所有 `[DEBUG-...]` 仪器化已移除（`grep` 前缀）
- [ ] 一次性原型已删除（或移至清晰标记的调试位置）
- [ ] 确定正确的假设在提交 / PR 消息中说明——以便下一个调试者学习

**然后问：什么可以防止这个 Bug？** 如果答案涉及架构变更（没有好的测试接口、耦合的调用者、隐藏的耦合），将具体细节移交给 `/improve-codebase-architecture` 技能。在修复完成后提出建议，而不是在开始之前——你现在比开始时拥有更多信息。
