# 诊断

处理疑难缺陷的专业方法。仅在明确且有充分理由时跳过各阶段。

在探索代码库时，使用项目的领域术语表（glossary），以建立对相关模块的清晰心智模型；并检查你正在涉及的区域的 ADR（架构决策记录）。

## 第 1 阶段 — 构建反馈循环

**这是核心技能。** 其他一切均为机械性工作。如果你能为该缺陷构建一个快速、确定、可由智能体运行的通过/失败信号，你就能找到根源——二分法、假设检验和插桩分析，都只是消耗这一信号。如果你没有这样的信号，无论怎么盯着代码看都无法自救。

在此处投入不成比例的精力。**要大胆。要富有创造性。拒绝放弃。**

### 构建方法 —— 请按大致顺序依次尝试

1. **在能抵达该缺陷的任何接入点（seam）上编写**失败的测试——包括单元测试、集成测试、端到端（e2e）测试。
2. 针对运行中的开发服务器编写 **Curl / HTTP 脚本**。
3. 使用测试数据（fixture）调用 **CLI**，并将标准输出与已知正常（known-good）快照进行差异比对。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，并对 DOM、控制台、网络请求进行断言。
5. **重放捕获的追踪记录。** 将真实的网络请求 / 负载 / 事件日志保存到磁盘，并在隔离的环境下通过代码路径进行重放。
6. **临时测试工具（Throwaway harness）。** 启动系统的最小化子集（单个服务、使用模拟依赖），通过一次函数调用来触发缺陷代码路径。
7. **属性 / 模糊测试循环。** 如果缺陷表现为“有时输出错误”，运行 1000 个随机输入，寻找失败模式。
8. **二分法测试工具。** 如果缺陷出现在两个已知状态（提交、数据集、版本）之间，自动化“在状态 X 启动、检查、重复”的流程，以便可使用 `git bisect run` 进行二分。
9. **差异循环。** 将相同的输入在旧版本与新版本（或两种配置）下分别运行，并对比输出结果。
10. **需人工干预（HITL）的 Bash 脚本。** 最后手段。如果必须由人工点击，使用 `scripts/hitl-loop.template.sh` 驱动他们，以确保循环结构依然完整。捕获的输出将反馈给你。

构建正确的反馈循环，该缺陷便已修复 90%。

### 迭代优化循环本身

将循环视为一个产品。一旦你有了循环，请思考：

- 我能让它运行得更快吗？（优化缓存设置、跳过无关的初始化、缩小测试范围。）
- 我能让信号更精准吗？（针对具体的症状进行断言，而非仅断言“未崩溃”。）
- 我能让它更确定（可复现）吗？（固定时间、设置随机数生成器（RNG）种子、隔离文件系统、冻结网络。）

一个 30 秒不稳定的循环，比没有循环稍微好一点。一个 2 秒确定的循环，是调试的超能力。

### 非确定性缺陷

目标不是得到一个干净的重现，而是**更高的复现率**。重复触发 100 次，并行化，增加压力，收窄时间窗口，注入睡眠（sleep）。50% 概率出错的缺陷是可调试的；1% 的概率则不可调试——持续提高其发生率，直至达到可调试的程度。

### 当你确实无法构建循环时

停止，并明确说明这一点。列出你已尝试的方法。向用户索要以下内容：(a) 能够复现该缺陷的环境的访问权限，(b) 捕获的产物（HAR 文件、日志导出、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产环境插桩的权限。**绝不可在没有循环的情况下进行假设。**

在没有你认可的循环之前，不得进入第 2 阶段。

## 第 2 阶段 — 复现

运行循环，观察缺陷出现。

确认以下事项：

- [ ] 循环产生的失败模式与**用户**描述的一致——而非恰好相邻的另一种不同失败。缺陷不同 = 修复错误。
- [ ] 该失败在多次运行中均可复现（或对于非确定性缺陷，复现率足够高，可供调试使用）。
- [ ] 你已捕获具体的症状（错误信息、错误输出、耗时异常），以便后续阶段能验证修复确实解决了该问题。

在成功复现缺陷之前，不得继续推进。

## 第 3 阶段 — 假设生成

在测试任何假设之前，生成 **3–5 个按优先级排序的假设**。单一假设的生成方式以第一个合理想法为锚点。

每个假设都必须是**可证伪的**：明确陈述其所做出的预测。

**格式：** “如果 <X] 是原因，则 <改变 Y] 将使缺陷消失 / <改变 Z]  will make it worse."

如果你无法陈述预测，该假设便是一种“直觉”——予以丢弃或进一步提炼。

**在测试前将排序后的列表展示给用户。** 他们通常拥有能瞬间重新排序领域知识的经验（“我们刚刚部署了针对 #3 的修改”），或知道已经排除了哪些假设。这是廉价的检查点，能节省大量时间。若用户处于离线（AFK）状态，不要阻塞流程，按你的排序继续推进。

## 第 4 阶段 — 插桩

每个探测都必须映射到第 3 阶段中的具体预测。**每次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**（如环境支持）。一个断点胜过十条日志。
2. **针对假设差异的边界位置的定向日志**。
3. **绝不“记录所有日志并 grep（过滤）”。**

**为每条调试日志**打上唯一前缀，例如 `[DEBUG-a4f2]`。最后的清理工作只需一次 grep 即可完成。未加标签的日志会保留；加了标签的日志会被清除。

**性能分支。** 对于性能回归问题，日志通常不可靠。取而代之的是：先建立基线测量（计时测试工具、`performance.now()`、分析器、查询计划），再进行二分排查。先测量，后修复。

## 第 5 阶段 — 修复与回归测试

编写回归测试**先于修复**进行——但前提是存在**正确的接入点（seam）**。

正确的接入点是指在调用点能执行**真实缺陷模式**的测试位置。如果可用的接入点过于浅层（例如缺陷需要多个调用方，却只有单一调用方的测试；或单元测试无法复现触发缺陷的调用链），在此处编写回归测试会让人产生错误的信心。

**如果不存在正确的接入点，这本身就是一个发现。** 记录这一点。代码库的架构正在阻止该缺陷被锁定封堵。在下一阶段标记此问题。

若存在正确的接入点：

1. 将最小化复现案例转化为在该接入点上的**失败的测试**。
2. 观察其失败。
3. 应用修复方案。
4. 观察其通过。
5. 针对原始（未最小化）场景重新运行第 1 阶段的反馈循环。

## 第 6 阶段 — 清理与复盘

在宣告完成之前必须执行以下事项：

- [ ] 原始复现案例不再复现（重新运行第 1 阶段的循环）
- [ ] 回归测试通过（或接入点缺失已做记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（使用 `grep` 命令检索前缀）
- [ ] 临时原型已删除（或移动到明确标注的调试位置）
- [ ] 最终正确的假设已在提交 / PR 信息中说明——以便下一位调试者能够借鉴经验

**随后询问：什么原本可以防止此缺陷的出现？** 若答案涉及架构性修改（缺少合适的测试接入点、调用链纠缠、隐藏耦合），请将具体细节交接给 `/use-codebase-architecture` 技能。建议应在**修复生效之后**提出，而非之前——因为你现在的掌握信息，比启动调试时更充分。
