# 诊断 Bug

硬 Bug 的诊断纪律。仅在明确有充分理由时方可跳过各阶段。

在探索代码库时，阅读 `CONTEXT.md`（若存在），以对相关模块建立清晰的心理模型，并检查你正在涉及的区域的 ADR（架构决策记录）。

## 脱敏处理

本技能要求展示命令、输出和捕获的产物。**首先对每个机密进行脱敏**：在相应位置写入 `<REDACTED>`。构建循环时使用环境变量，确保凭据保留在环境中，而非出现在展示内容中。捕获的产物带有认证请求头：仅引用包含有效信号内容的行。

如果脱敏后的输出不足以诊断 Bug，请明确指出并询问用户。

## 第一阶段：构建反馈循环

**本技能的核心。其他内容均为机械性工作。** 如果你为该 Bug 有一个**严苛**的通过/失败信号（即针对该 Bug 时会变红），你就能找到原因；二分法、假设测试和插桩等手段都只是在消耗它。如果没有这样的信号，再长时间盯着代码也无法拯救你。

在此阶段投入**不成比例**的精力。**要果断。要有创造力。决不放弃。**

### 构建反馈循环的方法，大致按以下顺序

1. **Failing test** at whatever seam reaches the bug: unit, integration, e2e.
2. **Curl / HTTP script** against a running dev server.
3. **CLI invocation** with a fixture input, diffing stdout against a known-good snapshot.
4. **Headless browser script** (Playwright / Puppeteer) that drives the UI and asserts on DOM/console/network.
5. **Replay a captured trace.** Save a real network request / payload / event log to disk; replay it through the code path in isolation.
6. **Throwaway harness.** Spin up a minimal subset of the system (one service, mocked deps) that exercises the bug code path with a single function call.
7. **Property / fuzz loop.** If the bug is "sometimes wrong output", run 1000 random inputs and look for the failure mode.
8. **Bisection harness.** If the bug appeared between two known states (commit, dataset, version), automate "boot at state X, check, repeat" so you can `git bisect run` it.
9. **Differential loop.** Run the same input through old-version vs new-version (or two configs) and diff outputs.
10. **HITL bash script.** Last resort. If a human must click, drive _them_ with `scripts/hitl-loop.template.sh` so the loop is still structured. Captured output feeds back to you.

构建正确的反馈循环，Bug 即可修复 90%。

### 收紧循环

将循环视为产品。一旦获得**一个**循环，**收紧**它：

- 能否使其更快？（缓存设置、跳过无关初始化、缩小测试范围。）
- 能否使其信号更锐利？（针对具体症状进行断言，而非"未崩溃"。）
- 能否使其更确定性？（固定时间、设置随机数生成器种子、隔离文件系统、冻结网络。）

一个 30 秒的波动循环，与没有循环几乎无异；而一个 2 秒的确定性循环则紧密可靠，是调试的超能力。

### 非确定性 Bug

目标并非获得一个清晰的复现，而是**更高的复现率**。循环触发 100 次、并行化、增加压力、缩小时间窗口、注入休眠。50% 出错的 Bug 可调试；1% 的则不可调试，因此持续提高复现率，直至可调试。

### 当确实无法构建循环时

**停止并明确指出。列出你所尝试的方法。** 向用户寻求以下内容：（a）能复现该 Bug 的环境访问权限，（b）脱敏后的捕获产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或（c）添加临时生产插桩的权限。**不要**在没有循环的情况下继续假设。

### 完成标准：一个变红的严苛循环

当循环**严苛**且**具备变红能力**时，第一阶段即告完成：你可以指明**一条命令**（脚本路径、测试调用、curl 命令），且你已**至少运行过一次**（展示调用方式及其脱敏后的输出），并且该命令满足：

- [ ] **具备变红能力**：它驱动实际的 Bug 代码路径，并断言**用户的确切症状**，因此在该 Bug 上能变红、修复后能变绿。而非"运行时不报错"；它必须能够捕获该特定 Bug。
- [ ] **确定性**：每次运行结论相同（非确定性 Bug：按照前述要求，提供固定的、高复现率的条件）。
- [ ] **快速**：秒级，而非分钟级。
- [ ] **可由 Agent 运行**：可无人值守运行；仅可通过 `scripts/hitl-loop.template.sh` 让人类参与循环。

若你在创建该命令之前，发现自己正在通过阅读代码来构建理论，**立即停止：直接跳到假设正是本技能所要防止的失败。** 没有具备变红能力的命令，就没有第二阶段。

## 第二阶段：复现 + 最小化

运行循环。观察循环随 Bug 的出现而变红。

确认以下内容：

- [ ] 循环产生的故障模式与**用户**所描述的一致，而非附近偶发的其他故障。错误的 Bug 意味着错误的修复。
- [ ] 故障在多次运行中可复现（或，对于非确定性 Bug，以足够高的频率复现以支持调试）。
- [ ] 你已捕获确切的症状（错误信息、错误输出、慢速计时）以便后续阶段验证修复确实解决了该问题。

### 最小化

一旦变红，将复现缩小为**仍能变红的场景的最小规模**。逐一削减输入、调用者、配置、数据和步骤，每次削减后重新运行循环，仅保留对故障起决定性作用的部分。

为何如此：最小复现缩减了第三阶段（假设空间）的推测范围（留下更少可能因素），并成为第五阶段的干净回归测试。

当**剩余的所有元素都具有决定性作用**：移除其中任何一个元素都会使循环变绿。

在复现并完成最小化之前，不得继续。

## 第三阶段：提出假设

在测试任何假设之前，生成**3–5 个排序后的假设**。单一假设的生成以第一个合理的想法为锚点。

每个假设都必须**可证伪**：明确陈述其做出的预测。

格式：“如果 <X 是原因，那么 <改变 Y 将使 Bug 消失 / <改变 Z 将使其更严重。”

如果你无法陈述预测，则该假设仅为空想：丢弃或将其精炼。

**在测试前向用户展示排序后的列表**。用户通常拥有领域知识，可即时重新排序（"我们刚部署了 #3 的变更"），或已知已被排除的假设。这是一个廉价的检查点，也是节省大量时间的措施。不要等待它；如果用户处于离线状态（AFK），则按你的排序继续。

## 第四阶段：插桩

每个探针必须映射到第三阶段中的一个特定预测。**每次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**（若环境支持）。一个断点胜过十条日志。
2. **在区分假设的边界处进行定向日志记录**。
3. 切勿"记录所有日志并 grep"。

为每条调试日志标注唯一的标签前缀，例如 `[DEBUG-a4f2]`。末尾的清理工作只需一次 grep 即可完成。未标注的日志会保留，已标注的日志会被清除。

**性能分支**。对于性能回归问题，日志通常不可靠。相反：首先建立基线测量（计时测试框架、`performance.now()`、分析器、查询计划），然后进行二分排查。先测量，后修复。

## 第五阶段：修复 + 回归测试

在修复之前编写回归测试，但前提是存在**正确的测试接入点**。

正确的测试接入点是指测试能在调用点处复现**真实的 Bug 模式**。如果唯一可用的接入点过于浅层（Bug 需要多个调用者却只有单一调用者的测试，无法复现触发 Bug 的调用链的单测），在此处的回归测试会产生虚假信心。

**如果没有正确的测试接入点，这本身就是发现结果。** 记录这一情况。代码库架构正在阻碍 Bug 被锁定。将此问题标记并提交给下一阶段。

如果存在正确的测试接入点：

1. 将最小复现转换为在该接入点上的失败测试。
2. 观察其失败。
3. 应用修复。
4. 观察其通过。
5. 针对原始（未最小化）场景重新运行第一阶段反馈循环。

## 第六阶段：清理

在宣布完成之前必须执行：

- [ ] 原始复现不再复现（重新运行第一阶段循环）
- [ ] 回归测试通过（或未找到接入点的情况已记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（通过 `grep` 前缀）
- [ ] 临时原型已删除（或移至明确标注为调试位置的区域）
- [ ] 最终正确的假设已在提交/PR 消息中说明，以便下一位调试人员学习
