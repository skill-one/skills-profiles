# 诊断错误

针对顽固错误的学科。仅在明确说明的情况下才能跳过阶段。

在探索代码库时，如果存在 `CONTEXT.md`，请阅读它以获得相关模块的清晰心智模型，并检查您所接触区域的 ADR（架构决策记录）。

## 匿名化处理

这项技能要求您展示命令、输出和捕获的工件。**首先匿名化所有秘密**：将其替换为 `<REDACTED>`。构建针对环境变量的循环，以便凭证保留在环境中而不是您展示的内容中。捕获的工件包含认证头：仅引用携带信号的行。

如果匿名化后的输出不足以诊断错误，请说明并要求用户。

## 第一阶段：建立反馈循环

**这是这项技能。** 其他都是机械操作。如果您有一个针对错误的**严格**通过/失败信号（在出现此错误时变红），您将找到原因；二分法、假设测试和仪器化都只是消耗它。如果没有，无论您如何盯着代码，都无法解决问题。

在此阶段投入不成比例的努力。**要积极。要富有创造力。拒绝放弃。**

### 建立反馈循环的方法，大致按此顺序

1. 在达到错误的任何接口处运行**失败的测试**：单元测试、集成测试、端到端测试。
2. 对运行中的开发服务器运行**Curl / HTTP 脚本**。
3. 使用固定输入运行**CLI 调用**，并将标准输出与已知良好的快照进行比较。
4. 运行**无头浏览器脚本**（Playwright / Puppeteer），该脚本驱动 UI 并对 DOM/控制台/网络进行断言。
5. **重放捕获的跟踪**。将真实的网络请求/有效负载/事件日志保存到磁盘；在隔离的代码路径中重放它。
6. **一次性测试框架**。启动系统最小子集（一个服务、模拟依赖项），该框架通过单个函数调用来执行错误代码路径。
7. **属性/模糊循环**。如果错误是“有时输出错误”，运行 1000 个随机输入并查找失败模式。
8. **二分法测试框架**。如果错误出现在两个已知状态之间（提交、数据集、版本），自动化“在状态 X 下启动、检查、重复”以便 `git bisect run`。
9. **差异循环**。通过旧版本与新版本（或两个配置）运行相同输入并比较输出。
10. **HITL bash 脚本**。最后手段。如果必须由人类点击，使用 `scripts/hitl-loop.template.sh` 驱动他们，以便循环仍然结构化。捕获的输出将反馈给您。

建立正确的反馈循环，错误就有 90% 的几率被修复。

### 优化循环

将循环视为一个产品。一旦您有一个循环，**就优化它**：

- 我能使其更快吗？（缓存设置、跳过无关的初始化、缩小测试范围。）
- 我能使其信号更清晰吗？（针对特定症状进行断言，而不是“没有崩溃”。）
- 我能使其更确定吗？（固定时间、种子随机数生成器、隔离文件系统、冻结网络。）

一个 30 秒的易失性循环几乎等同于没有循环；一个 2 秒的确定性循环是调试的超级力量。

### 非确定性错误

目标是干净的重复，而不是**更高的重复率**。循环触发 100 次，并行化，增加压力，缩小时间窗口，注入睡眠。一个 50% 的易失性错误是可调试的；1% 是不可调试的，因此请不断提高速率直到它可调试。

### 当您确实无法建立循环时

停止并明确说明。列出您尝试过的方法。要求用户提供：(a) 访问任何可以重复错误的环境，(b) 一个匿名化的捕获工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 添加临时生产仪器化的权限。**不要**在没有循环的情况下进行假设。

### 完成标准：一个变红的严格循环

当循环**严格**且**变红**时，第一阶段完成：您可以命名**一个命令**（脚本路径、测试调用、curl），您已经**至少运行过一次**（显示调用及其输出，匿名化），并且该命令：

- [ ] **变红**：它驱动实际的错误代码路径并断言**用户的精确症状**，因此它可以在出现此错误时变红，在修复后变绿。不是“没有报错”；它必须能够**捕获此特定错误**。
- [ ] **确定性**：每次运行结果相同（易失性错误：固定、高重复率，如上所述）。
- [ ] **快速**：秒级，不是分钟级。
- [ ] **可自动运行**：您可以无人值守地运行它；循环中的人类仅通过 `scripts/hitl-loop.template.sh`。

如果您发现自己在此命令存在之前通过阅读代码来建立理论，**停止**：直接跳到假设是这项技能防止的失败。没有变红的命令，就没有第二阶段。

## 第二阶段：重复 + 最小化

运行循环。观察错误出现时它变红。

确认：

- [ ] 循环产生的失败模式与**用户**描述的失败模式相同，而不是附近发生的不同失败。错误错误 = 错误修复。
- [ ] 失败是可重复的（对于非确定性错误，重复率足够高以进行调试）。
- [ ] 您已捕获精确的症状（错误消息、错误输出、慢速时间）以便后续阶段可以验证修复是否确实解决了它。

### 最小化

一旦变红，将重复缩小到**仍然变红的场景最小**。一次一个地删除输入、调用者、配置、数据和步骤，每次删除后重新运行循环，并保留仅对失败负载的元素。

为什么这样做：最小重复缩小了第三阶段（剩余可怀疑的移动部分更少）的假设空间，并成为第五阶段的干净回归测试。

完成时**每个剩余元素都是负载**：删除其中任何一个都会使循环变绿。

在重复**并**最小化之前不要继续。

## 第三阶段：假设

在测试任何假设之前生成**3–5 个排序的假设**。单假设生成锚定在第一个可能的想法。

每个假设必须**可证伪**：说明它做出的预测。

> 格式：“如果 <X> 是原因，那么更改 <Y> 将使错误消失 / 更改 <Z> 将使其更糟。”

如果您无法说明预测，假设是一种感觉：丢弃或使其更清晰。

**在测试之前向用户展示排序列表**。他们通常有领域知识可以立即重新排序（“我们刚刚部署了 #3 的更改”），或者知道他们已经排除的假设。廉价的检查点，巨大的时间节省。如果用户不在，不要阻塞；如果用户不在，请继续使用您的排名。

## 第四阶段：仪器化

每个探测器必须映射到第三阶段的特定预测。**一次改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**如果环境支持。一个断点胜过十个日志。
2. **有针对性的日志**在区分假设的边界处。
3. 从不“记录所有内容并grep”。

**每个调试日志都使用唯一的前缀标记**，例如 `[DEBUG-a4f2]`。清理在最后变成单个 grep。未标记的日志保留；标记的日志被删除。

**性能分支**。对于性能回归，日志通常是错误的。相反：建立基线测量（计时框架、`performance.now()`、分析器、查询计划），然后二分法。先测量，后修复。

## 第五阶段：修复 + 回归测试

在修复之前编写回归测试，但只有当存在**正确的接口**时。

正确的接口是测试在调用点执行**实际错误模式**的接口。如果唯一可用的接口太浅（单个调用者测试时错误需要多个调用者，无法复制触发错误的链的单元测试），则在该接口的回归测试会给出虚假的信心。

**如果不存在正确的接口，这本身就是一个发现**。记录它。代码库架构阻止了错误被锁定。标记此问题以供下一阶段处理。

如果存在正确的接口：

1. 将最小化重复转换为该接口的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 重新运行第一阶段的反馈循环针对原始（未最小化）场景。

## 第六阶段：清理

完成之前必须执行：

- [ ] 原始重复不再重复（重新运行第一阶段的循环）
- [ ] 回归测试通过（或接口缺失已记录）
- [ ] 所有 `[DEBUG-...]` 仪器化已删除（`grep` 前缀）
- [ ] 一次性原型已删除（或移至明确标记的调试位置）
- [ ] 确定的假设在提交 / PR 消息中说明，以便下一个调试器学习
