# 转化为任务

将计划、规格或对话拆分为一组**任务**：追踪子弹式的垂直切片，每个切片均声明了**阻塞**它的任务。

应该已经向你提供了问题跟踪器与分诊标签的词汇表。若尚未提供，请告知用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的内容开展工作。若用户将引用（规格路径、问题编号或 URL）作为参数传入，请获取该内容，并读取其完整正文与评论。

### 2. 探索代码库（可选）

若尚未探索过代码库，请进行探索以了解代码的当前状态。任务标题与描述应使用项目的领域词汇表，并尊重你正在触及区域内的 ADR。

寻找机会对代码进行预加工，以降低实现难度。"先让改动变得容易，再完成容易的改动。"

### 3. 起草垂直切片

将工作拆分为 **tracer-bullet** 任务。

<vertical-slice-rules>

- 每个切片都必须贯穿（schema、API、UI、测试）每一层，且路径狭窄但**完整**（垂直切片，而非某单一层的水平切片）
- 已完成的切片可独立进行演示或验证
- 每个切片的规模应适配于单个全新的上下文窗口
- 任何预加工工作都应先行完成

</vertical-slice-rules>

为每个任务指定其**阻塞边**：必须先完成、才能开始的其他任务。没有任何阻塞边的任务可立即开始。

**宽幅重构是对垂直切片原则的例外。**
**宽幅重构**是指一次机械性改动（如重命名一列、重新输入共享符号），其**爆炸半径**会波及整个代码库，导致一次编辑同时破坏数千个调用点，且没有任何垂直切片能够顺利落地为绿色（通过）。

不要将其强行归入追踪子弹式任务；应按 **扩展–收缩** 流程进行。

首先扩展：在旧形式旁添加新形式，确保不出现任何破坏。

随后按照爆炸半径（按包、按目录）分批迁移调用点；每个批次作为一个被扩展步骤阻塞的任务，因旧形式仍存在，故分批迁移并保持每次批次的 CI 通过。

最后收缩：一旦不再有任何调用者，在由每个迁移批次阻塞的任务中删除旧形式。

当即便批次也无法独立保持绿色时，保持该流程，让各批次共享一条集成分支，且所有批次均阻塞于最终的整合与验证任务；此时仅能承诺在该处实现绿色。

### 4. 向用户提问

将提出的拆分方案以编号列表呈现。针对每个任务，展示以下信息：

- **标题**：简短的描述性名称
- **被...阻塞**：必须先完成的其他任务（若有）
- **交付内容**：该任务使功能端到端实现的行为

请用户确认：

- 粒度是否合适？（过粗 / 过细）
- 阻塞边是否正确：每个任务是否仅依赖于确实会制约它的任务？
- 是否需要对某些任务进行合并或进一步拆分？

持续迭代，直至用户确认该拆分方案。

### 5. 将任务发布到已配置的信息跟踪器

发布已通过的任务。**方式**取决于 `/setup-matt-pocock-skills` 配置的跟踪器；任务本身始终一致，仅阻塞边的形态有所不同：

- **本地文件** → 在每个任务下，于 `.scratch/<feature-slug>/issues/<NN>-<-slug>.md` 下编写一个文件，按依赖顺序编号（阻塞任务优先，从 `01` 开始）。每个文件的“被...阻塞”列出其所依赖的编号/标题。使用下方的单任务文件模板：每个任务一个文件，绝不使用单一的合并文件。
- **真实的信息跟踪器（GitHub、Linear，……）** → 按依赖顺序（阻塞任务优先）为每个任务发布一个 issue，以便每个任务的阻塞边能够引用真实的标识符。若平台支持原生的阻塞/子问题关系，则使用之；否则，将每个任务的“被...阻塞”设置为阻塞的 issue。除非另有指示，否则应用 `ready-for-agent` 分诊标签；由于任务结构本身即为可抓取形态，故可被智能体获取。

推进**前沿**：任何阻塞任务均已完成的任务。对于纯线性链，这意味着从上到下依次推进。

**不要**关闭或修改任何父级 issue。
