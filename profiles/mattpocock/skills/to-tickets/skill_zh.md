# 分解为工单

将计划、规范或对话分解为一系列 **工单**：追踪子弹式垂直切片，每个切片声明其 **阻塞** 的工单。

问题追踪器和筛选标签词汇表应该已经提供给你了。如果没有，请告知用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话中已有的上下文开始工作。如果用户将参考（规范路径、问题编号或 URL）作为参数传递，请获取并读取其完整正文和评论。

### 2. 探索代码库（可选）

如果你还没有探索代码库，请进行探索以了解代码的当前状态。工单标题和描述应使用项目的领域词汇表，并尊重你触及区域的 ADR。

寻找重构代码以简化实现的机会。"让变更变得容易，然后让容易的变更发生。"

### 3. 起草垂直切片

将工作分解为 **追踪子弹** 工单。

<vertical-slice-rules>

- 每个切片切透每一层（模式、API、UI、测试）的狭窄但完整的路径：垂直，而不是某一层的水平切片
- 完成的切片可以单独演示或验证
- 每个切片的大小适合在一个新的上下文窗口中
- 任何重构都应该首先进行

</vertical-slice-rules>

为每个工单分配其 **阻塞边**：必须先完成的其它工单。没有阻塞的工单可以立即开始。

**宽泛的重构是垂直切片的例外。** **宽泛的重构** 是一个机械变更（重命名列、重新类型化共享符号），其 **爆炸范围** 跨越整个代码库，因此单个编辑会同时破坏数千个调用点，没有任何垂直切片可以保持绿色。不要强迫它进入追踪子弹；按 **扩展-收缩** 的顺序进行。首先扩展：在旧形式旁边添加新形式，确保没有任何东西会中断。然后分批迁移调用点，每批的大小由爆炸范围决定（按包、按目录），每批有自己的工单，被扩展阻塞，保持 CI 每批都是绿色的，因为旧形式仍然存在。最后收缩：一旦没有调用者，删除旧形式，在一个被所有迁移批次阻塞的工单中。当即使批次单独也无法保持绿色时，保持顺序，但让它们共享一个集成分支，所有分支阻塞一个最终的集成和验证工单；只有在那里才承诺绿色。

### 4. 询问用户

将建议的分解以编号列表的形式呈现。对于每个工单，显示：

- **标题**：简短的描述性名称
- **阻塞**：哪些其它工单（如果有）必须先完成
- **交付内容**：这个工单使工作完成的端到端行为

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确：每个工单是否只依赖于真正阻塞它的工单？
- 是否有任何工单需要合并或进一步拆分？

迭代直到用户批准分解。

### 5. 将工单发布到配置的追踪器

发布批准的工单。**如何** 取决于追踪器 `/setup-matt-pocock-skills` 的配置；无论哪种方式，工单都是相同的，只有阻塞边的形状会变化：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每个工单编写一个文件，编号从 `01` 开始（按依赖顺序，阻塞工单优先）。每个文件的 "Blocked by" 列出它依赖的编号/标题。使用下面的每个工单文件模板：每个文件一个工单，从不合并为一个文件。

- **真实的问题追踪器（GitHub、Linear、…）** → 按依赖顺序（阻塞工单优先）发布每个工单为一个问题，以便每个工单的阻塞边可以引用真实标识符。使用平台的本地阻塞/子问题关系（如果有的话）；否则将每个工单的 "Blocked by" 设置为阻塞问题。除非另有指示，否则应用 `ready-for-agent` 筛选标签；工单按设计可被代理抓取。

处理 **前沿**：任何阻塞工单都完成的工单。对于纯线性链，这意味着从上到下。

**不要关闭或修改任何父问题。**
