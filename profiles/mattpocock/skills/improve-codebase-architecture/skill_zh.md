# 改进代码库架构

揭示架构层面的摩擦并提出**深化机会**：将浅层模块转化为深层模块的重构。目标是提升可测试性和 AI 可导航性。

本命令基于项目的领域模型，并构建在共享设计词汇之上：

- 使用 "codebase-design" 调用 Skill 工具，以获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、"接口是测试表面"、"一个适配器即假设性接缝，两个才是真实"）。在每一处建议中必须使用这些术语，不得滑向 "组件"、"服务"、"API" 或 "边界" 等表述。
- `CONTEXT.md` 中的领域语言为优质接缝赋予名称；`docs/adr/` 中的 ADR（架构决策记录）记录了本命令不应重新辩驳的决策。

## 流程

### 1. 探索

**扫描前的范围界定：遵循 YAGNI 原则。** 深化模块通过使未来对其的修改更加容易而获得回报，因此要特别关注代码库中近期发生变动部分。先决定*要看哪里*，再开始查看：

- 如果用户指定了方向（一个模块、子系统、痛点），直接采用该方向，并跳过下方推理。
- 否则，回溯一段合适的提交历史（`git log --oneline`），找出代码库的热区——那些反复出现的文件与区域，并让这些路径优先吸引你的注意力。如果变动分散且没有明显热区，则扩大搜索范围。

首先阅读项目的领域词汇表（`CONTEXT.md`）以及你正在接触区域内的任何 ADR。

然后派生一个子代理来遍历代码库。不要遵循僵化的启发式规则；有机地探索，并记录你在哪里遇到摩擦：

- 理解单一概念需要频繁在不同小型模块之间跳转的地方？
- 哪些模块是**浅层**的，其接口的复杂度几乎与实现本身一样复杂？
- 哪些情况仅为了可测试性而抽取了纯函数，但实际缺陷隐藏在调用方式中（缺乏**局部性**）？
- 紧密耦合的模块在接缝处发生泄漏的地方？
- 代码库中有哪些部分未经测试，或无法通过当前接口进行有效测试？

对你怀疑为浅层的地方应用**删除测试**：删除它是否会使复杂性集中，还是仅仅将其转移？"是，会集中" 就是你想要的信号。

### 2. 以 HTML 报告呈现候选方案

将一个自包含的 HTML 文件写入操作系统的临时目录，确保不会将任何内容带入代码库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（或在 Windows 上使用 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<%timestamp>.html`，确保每次运行获得新文件。

为用户打开该文件（Linux 上使用 `xdg-open <path>`，macOS 上使用 `open <path>`，Windows 上使用 `start <path>`），并向用户告知其绝对路径。

报告使用 **Tailwind via CDN** 处理布局与样式，并使用 **Mermaid via CDN** 绘制图表，适用于图表/流程/时序能可靠传达结构的情形。将 Mermaid 与手工制作的 CSS/SVG 视觉效果相结合：当关系以图形呈现（调用图、依赖关系、时序）时使用 Mermaid，当需要更富编辑性（全景图、剖面图、折叠动画）的视觉时，使用手工构建的 divs/SVG。每个候选方案都获得**前后对比可视化**。追求视觉呈现。

为每个候选方案渲染一张卡片，内容包括：

- **涉及文件**：涉及的哪些文件/模块
- **问题**：当前架构造成摩擦的原因
- **方案**：对将进行改动的一种通俗英语描述
- **优势**：从局部性和杠杆效应的角度进行解释，以及测试将如何改善
- **前后对比图示**：并排定制绘制，展示浅层性与深化过程
- **推荐力度**：`Strong`、`Worth exploring`、`Speculative` 之一，以徽章形式呈现

报告末尾设置**顶部推荐**部分：说明你优先处理哪个候选方案及原因。

**使用 CONTEXT.md 的领域词汇表述领域内容，使用 `/codebase-design` 的词汇表述架构内容。** 如果 `CONTEXT.md` 定义了 "Order"，则表述为 "Order 导入模块"，而非 "FooBarHandler"，也而非 "Order 服务"。

**ADR 冲突**：如果某个候选方案与现有 ADR 冲突，仅在摩擦足够真实、值得重新审视该 ADR 时才予以呈现。在卡片中明确标注（例如警告提示：_"与 ADR-0007 冲突，但因……值得重新开启"_）。不要罗列 ADR 所禁止的所有理论改造。

详见 [HTML-REPORT.md](HTML-REPORT.md) 获取完整的 HTML 框架、图示模式与样式指南。

暂不提出接口。文件写入完成后，询问用户："这些方案中，您想探索哪一项？"

### 3. 深度讨论循环

用户选定候选方案后，调用 Skill 工具，使用 "grilling" 与用户共同走决策树：约束条件、依赖关系、深化模块的结构、接缝后方的接口、能够存活的测试。

决策逐渐清晰时，副作用会内联发生；随进行过程中，调用 Skill 工具，使用 "domain-modeling" 以保持领域模型同步更新：

- **以 `CONTEXT.md` 中不存在的概念命名深化后的模块？** 将该术语添加到 `CONTEXT.md`。如果文件不存在，则延迟创建。
- **在对话中锐化模糊术语？** 立即更新 `CONTEXT.md`。
- **用户以至关重要（实质性）的原因拒绝该候选方案？** 提供一个 ADR，以如下方式表述："是否将此项记录为 ADR，以便未来的架构评审不再重新提出它？" 仅当该原因会在未来探索者中确实需要时，才提供此项；跳过临时性原因（如"现阶段不值得"）和显而易见的原因。
- **想要为深化后的模块探索替代接口？** 调用 Skill 工具，使用 "codebase-design"，并运用其 design-it-twice 并行子代理模式。
