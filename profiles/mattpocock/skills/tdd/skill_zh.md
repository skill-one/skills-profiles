# 测试驱动开发

TDD 是红 → 绿的循环。本技能是该循环的参考指南，确保循环生成的测试具有持久价值：什么是好的测试，测试应放在何处，反模式，以及循环的规则。每一部分在每个循环中均适用：在循环之前和之中查阅，而非之后。

在探索代码库时，阅读 `CONTEXT.md`（如果存在），使测试名称和接口词汇与项目的领域语言保持一致，并尊重你所涉及的区域的 ADR（架构决策记录）。

## 什么是好的测试

测试通过公共接口验证行为，而非实现细节。代码可以完全改变，但测试不应改变。好的测试读起来像一份规格说明："用户可以使用有效的购物车进行结算" 明确告知你存在何种能力，且因其不关注内部结构，能够经受重构。

参阅 [tests.md](tests.md) 获取示例，以及 [mocking.md](mocking.md) 获取模拟指南。

## 接缝：测试所在之处

**接缝（seam）** 是指你在测试时所处的公共边界：在不深入内部的前提下观察行为的接口。测试存在于接缝处，绝不可针对内部实现进行测试。

**仅在预定的接缝处进行测试。** 编写任何测试之前，先明确待测试的接缝，并与用户确认。任何测试都不得在未确认的接缝处编写。无法测试所有内容，因此提前约定接缝，能使测试工作聚焦于关键路径和复杂逻辑，而非每个边界情况。

询问："公共接口是什么，哪些接缝应该进行测试？"

当该接口的形状本身存疑（模块深度如何、接缝应位于何处、接口应暴露什么），调用 Skill 工具，传入 "codebase-design" 获取词汇表。它是模块、接口、深度、接缝、适配器、杠杆与局部性等术语的共享来源，是需查阅的参考，而非需运行的会话。

## 反模式

- **实现耦合（Implementation-coupled）**：模拟内部协作对象，测试私有方法，或通过旁路验证（如不通过接口而直接查询数据库）。其征兆：在重构时测试会失败，但行为并未改变。
- **同义反复（Tautological）**：断言以与代码相同的方式重新计算期望值（如 `expect(add(a, b)).toBe(a + b)`、以相同方式手工推导的快照、将常量断言等于自身），因而在结构上必然通过，永远无法与代码产生分歧。期望值必须来自独立的真值来源：已知正确的字面量、已验证的示例、规格说明。
- **水平切片（Horizontal slicing）**：先编写所有测试，再进行所有实现。批量测试验证的是_想象_中的行为：你测试的是事物的_结构_，而非面向用户的行为；测试对实际变更不敏感；在理解实现之前就承诺了测试结构。应改用**垂直切片（vertical slices）**：一次测试 → 一次实现 → 重复，每次测试都是**追踪子弹（tracer bullet）**，根据上一个循环所教的内容做出响应。

## 循环规则

- **先红后绿。** 首先编写失败的测试，然后只编写足以使其通过的最小代码。不要预想未来测试，也不要添加推测性功能。
- **一次一个切片。** 每个循环中，一个接缝、一个测试、一次最小实现。
- **重构不属于循环的一部分。** 它属于评审阶段（参见 `code-review` 技能），而非红 → 绿的实现循环。
