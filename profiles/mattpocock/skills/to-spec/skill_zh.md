## 处理流程

1. 探索代码库，以了解代码库的当前状态（如果你尚未探索）。在整个规范中使用项目领域术语词汇，并尊重你所涉及领域的任何架构决策记录（ADR）。

2. 勾勒出你将要测试该功能时涉及的连接点（seams）。应优先使用现有连接点，而非新连接点。使用尽可能高的连接点。如果需要新连接点，则在你能做到的最高位置提出它们。代码库中跨越的连接点越少越好——理想数量为一个。

与用户确认这些连接点是否符合其预期。

3. 使用下方模板编写规范，然后将其发布到项目问题跟踪器。应用 `ready-for-agent` 分诊标签——无需额外分诊。

## 实现决策

一个记录了所作出的实现决策的列表。这些决策可能包括：

- 将被构建/修改的模块
- 将被修改的模块的接口
- 开发者提供的技术澄清
- 架构决策
- 模式变更
- API 契约
- 具体交互

不要包含具体的文件路径或代码片段。它们可能很快就会过时。

例外：如果原型产出了比文字描述更精确地编码某项决策的片段（状态机、reducer、模式、类型形状），请在相关的决策中内联该片段，并简要说明其来自原型。只保留决策丰富的内容，而不是可运行演示，只需保留重要的部分。
