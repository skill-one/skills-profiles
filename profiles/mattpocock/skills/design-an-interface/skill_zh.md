# 设计界面

依据《A Philosophy of Software Design》中的“Design It Twice”，你的首个想法通常并非最优解，需生成多个**截然不同**的设计方案，随后进行对比。

## 工作流

### 1. 收集需求

设计之前，需明确以下内容：

- [ ] 该模块解决了什么问题？
- [ ] 调用方是谁？（其他模块、外部用户、测试用例）
- [ ] 核心操作有哪些？
- [ ] 是否存在约束条件？（性能、兼容性、现有规范模式）
- [ ] 哪些内容应内部隐藏，哪些需要对外暴露？

请思考：“该模块需要实现哪些功能？哪些用户将使用它？”

### 2. 并行生成设计方案（子代理）

使用 Task 工具同时派生 3 个及以上的子代理，每个必须产出**截然不同**的方案。

```
每个子代理的提示词模板：

Design an interface for: [模块描述]

Requirements: [收集到的需求]

Constraints for this design: [为每个代理分配不同的约束]
- Agent 1: "Minimize method count - aim for 1-3 methods max"
- Agent 2: "Maximize flexibility - support many use cases"
- Agent 3: "Optimize for the most common case"
- Agent 4: "Take inspiration from [specific paradigm/library]"

输出格式：
1. 接口签名（类型/方法）
2. 使用示例（调用方的使用方式）
3. 该设计内部隐藏的内容
4. 该方案的优势与权衡
```

### 3. 呈现设计方案

依次展示每个设计方案，需包含以下内容：

1. **接口签名**：包含类型、方法、参数
2. **使用示例**：调用方实际的使用方式
3. **内部隐藏内容**：已收敛的内部复杂逻辑

按顺序呈现设计方案，以便用户在对比前充分理解各项方案。

### 4. 对比设计方案

展示全部设计方案后，从以下维度展开对比：

- **接口简洁性**：方法更少、参数更简单的方案
- **通用性 vs 专用性**：灵活性与专注度的权衡
- **实现效率**：现有形态是否便于实现高效内部逻辑？
- **深度**：小接口隐藏大量复杂逻辑的模块（优）vs 大接口配套薄实现的模块（劣）
- **正确使用的便利性** vs **误用的便利性**

以正文形式阐述各项权衡，避免使用表格，同时重点标注设计方案差异最大的部分。

### 5. 综合优化

最优设计方案往往融合多个方案的思路，请思考：

- “哪一项方案最契合您的核心使用场景？”
- “是否有其他方案中的设计元素值得融入其中？”

## 评估标准

依据《A Philosophy of Software Design》中的标准：

**接口简洁性**：方法越少、参数越简单，越易于学习和正确使用。

**通用性**：无需修改即可适配未来使用场景，但需避免过度泛化。

**实现效率**：现有接口形态是否便于实现高效内部逻辑，还是会导致内部逻辑实现困难？

**深度**：小接口隐藏大量复杂逻辑的模块属于深度模块（优）；大接口配套薄实现的模块属于浅模块（需避免）。

## 常见反模式

- 禁止子代理产出相似设计方案，必须强制实现差异化
- 不得跳过对比环节，对比的价值在于差异对照
- 无需开展实现工作，本环节仅聚焦接口形态
- 不得基于实现成本进行评估
