# 设计界面

基于《软件设计哲学》中的“设计两次”原则：你的第一个想法不太可能是最好的。生成多个截然不同的设计方案，然后进行比较。

## 工作流程

### 1. 收集需求

在设计之前，需要理解：

- [ ] 该模块解决什么问题？
- [ ] 调用者是谁？（其他模块、外部用户、测试）
- [ ] 关键操作是什么？
- [ ] 有任何限制吗？（性能、兼容性、现有模式）
- [ ] 什么应该隐藏内部，什么应该暴露？

提问：“该模块需要做什么？谁会使用它？”

### 2. 生成设计方案（并行子代理）

使用任务工具同时生成3个或更多的子代理。每个子代理必须产生一个**截然不同**的方法。

```
每个子代理的提示模板：

为：[模块描述] 设计一个界面

需求：[收集到的需求]

该设计的限制：[为每个代理分配不同的限制]
- 代理1：“最小化方法数量 - 最多1-3个方法”
- 代理2：“最大化灵活性 - 支持多种用例”
- 代理3：“针对最常见的用例进行优化”
- 代理4：“从[特定范式/库]中获取灵感”

输出格式：
1. 界面签名（类型/方法）
2. 使用示例（调用者如何使用它）
3. 该设计隐藏的内部细节
4. 该方法的权衡
```

### 3. 展示设计方案

按顺序展示每个设计方案，并包含：

1. **界面签名** - 类型、方法、参数
2. **使用示例** - 调用者实际如何使用它
3. **隐藏的内容** - 内部保留的复杂性

按顺序展示设计，以便用户在比较前能够吸收每种方法。

### 4. 比较设计方案

展示所有设计后，比较它们在以下方面：

- **界面简洁性**：更少的方法、更简单的参数
- **通用性 vs 专用性**：灵活性 vs 聚焦
- **实现效率**：接口形状是否允许高效的内部实现？
- **深度**：小界面隐藏显著复杂性（好）vs 大界面但实现薄弱（坏）
- **正确使用的便捷性** vs **误用的便捷性**

用散文讨论权衡，而不是表格。突出设计差异最大的地方。

### 5. 综合分析

通常最好的设计结合了多个选项的见解。提问：

- “哪个设计最适合你的主要用例？”
- “其他设计中有任何值得包含的元素吗？”

## 评估标准

来自《软件设计哲学》：

**界面简洁性**：更少的方法、更简单的参数 = 更容易学习和正确使用。

**通用性**：能够处理未来的用例而无需更改。但要警惕过度通用。

**实现效率**：接口形状是否允许高效的实现？还是强迫内部实现笨拙？

**深度**：小界面隐藏显著复杂性 = 深度模块（好）。大界面但实现薄弱 = 浅度模块（避免）。

## 反模式

- 不要让子代理产生相似的设计 - 强制差异
- 不要跳过比较 - 价值在于对比
- 不要实现 - 这纯粹是关于接口形状
- 不要基于实现工作量的评估
