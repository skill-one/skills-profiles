# 原型

一个原型是**用于回答问题的临时代码**。问题决定了它的形态。

## 挑选分支

利用用户的提示、周围的代码，或询问用户是否在位，明确正在回答的问题是什么：

- **"逻辑/状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建单个可共享的 HTML 文件（包含自由试玩按钮以及标签页式引导式走查），通过难以在纸上推演的用例驱动状态机，且非开发人员也能操作。
- **"它应该是什么样子？"** → [UI.md](UI.md)。在单条路由上生成多个截然不同的 UI 变体，通过 URL 搜索参数和悬浮底部栏进行切换。

这两个分支产出的产物差异很大，弄错会导致整个原型作废。如果问题确实存在歧义且无法联系到用户，默认采用与周围代码匹配度更高的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部注明该假设。

## 两者通用的规则

1. **从第一天起即为临时代码，并明确标注。** 将原型代码放置在即将实际使用的位置附近（紧挨着正在原型的模块或页面），以便上下文显而易见，但命名需让非专业读者能看出它是原型而非正式生产代码。对于临时 UI 路由，遵循项目既有的路由规范，不要自行创建新的顶层结构。
2. **易于运行。** UI 原型只需在项目的任务运行器中执行一条命令即可启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是一个用户双击即可打开的单个 HTML 文件。无论哪种方式，启动都无需任何思考。
3. **默认不持久化。** 状态保存在内存中。持久化正是原型需要验证的对象，而非依赖项。如果问题明确涉及数据库，请使用一个带有明确“PROTOTYPE, wipe me”名称的临时数据库或本地文件。
4. **跳过打磨。** 不进行测试，不进行超出让原型能运行所需的错误处理，不引入抽象层。其目的是快速获取经验。
5. **展示状态。** 在每次逻辑操作后，或在每次 UI 变体切换时，打印或渲染完整的、相关的状态，以便用户能看到具体发生了哪些变化。
6. **完成后记录。** 将任何已验证的决策融入真实代码中，然后将原型本身作为**主要来源**记录下来：将其提交到脱离 main 的临时分支上，并在实现问题的说明中留下指向该分支的上下文链接。同样将答案（即最终结论以及它所解决的问题）记录在问题或提交中。main 分支仅保留已验证的决策。
