# 原型

原型是**一次性代码，用于回答问题**。问题决定了它的形态。

## 选择分支

根据用户的提示、周围的代码或询问用户来识别正在回答哪个问题：

- **"这个逻辑/状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个可共享的HTML文件（免费试玩按钮加上选项卡式引导式演示），将状态机推进那些在纸上难以推理的案例，并且非开发者也能操作。
- **"这个应该看起来像什么？"** → [UI.md](UI.md)。在单个路由上生成多个截然不同的UI变体，可通过URL搜索参数和一个浮动底部栏进行切换。

这两个分支产生的产物非常不同，所以选错会浪费整个原型。如果问题确实模糊且用户无法联系，默认选择与周围代码更匹配的分支（后端模块→逻辑；页面或组件→UI），并在原型的顶部说明假设。

## 适用于两者的规则

1. **从一开始就是一次性代码，并明确标记为如此。** 将原型代码放置在它实际将使用的地方附近（原型化模块或页面的旁边），以便上下文一目了然，但命名时要让随意阅读的人能看出这是一个原型，而不是生产代码。对于一次性UI路由，遵循项目现有的路由约定；不要发明一个新的顶层结构。
2. **运行起来非常简单。** UI原型从一个项目任务运行器中的命令开始：`pnpm <名称>`、`python <路径>`、`bun <路径>`等。逻辑演示是一个用户双击的单个HTML文件。无论如何，启动它都不需要思考。
3. **默认不持久化。** 状态存储在内存中。持久化是原型正在检查的东西，而不是它应该依赖的东西。如果问题明确涉及数据库，请连接到一个临时数据库或一个带有清晰"PROTOTYPE, 删除我"名称的本地文件。
4. **跳过润色。** 没有测试，没有超出使原型可运行的错误处理，没有抽象。目的是快速学习。
5. **暴露状态。** 在每个操作（逻辑）之后或每个变体切换（UI）时，打印或渲染完整的相关状态，以便用户可以看到发生了什么变化。
6. **完成后捕获。** 将任何已验证的决策合并到真实代码中，然后将原型本身捕获为**主要来源**：将其提交到一个一次性分支，出主线，并在实现问题中留下一个指向该分支的上下文指针。同时捕获答案（裁决和它解决的问题）到问题或提交中。主线分支只保留已验证的决策。
