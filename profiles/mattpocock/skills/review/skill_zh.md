对用户提供的 `HEAD` 与固定点之间差异的**两轴审查**：

- **标准（Standards）** — 代码是否符合该仓库文档中记录的编码规范？
- **规格（Spec）** — 代码是否忠实实现了来源 issue / PRD / 规格？

两条轴线均以**并行子代理**方式运行，互不污染彼此的上下文，随后由本技能汇总其发现结果。

应已向您提供问题跟踪器——若 `docs/agents/issue-tracker.md` 缺失，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定点

用户所述即为固定点——可为提交 SHA、分支名、标签、`main`、`HEAD~5` 等。若用户未指定，则请其提供。

一次性记录差异命令：`git diff <fixed-point)...)...HEAD`（三点连接符，即与合并基线进行比对）。同时通过 `git log <fixed-point)..HEAD --oneline` 记录提交列表。

在继续之前，需确认固定点解析正常（`git rev-parse <fixed-point)`）且差异不为空。若引用无效或差异为空，应在此处直接失败——而非在两个并行子代理内部失败。

### 2. 识别规格来源

按以下顺序查找来源规格：

1. 在提交信息中的 issue 引用（如 `#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. 位于 `docs/`、`specs/` 或 `.scratch/` 下、与分支名或功能匹配的 PRD/规格文件。
4. 若未找到任何内容，则询问用户规格位于何处。若用户表示不存在，**规格（Spec）** 子代理将跳过，并报告“无可用规格”。

### 3. 识别规范来源

仓库中任何记录代码编写方式的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库已记录的内容之上，**标准（Standards）** 轴线始终附带下方所示的**异味基线**——一套固定的 Fowler 代码异味（_Refactoring_，第 3 章），即使仓库未做任何说明，该基线同样适用。有两项规则将其约束：

- **仓库优先。** 已记录的文档规范始终优先；若仓库规范认可基线中会被标记的内容，则压制该异味。
- **始终为判断性决策。** 每种异味均为带有标签的启发式规则（如“可能产生特征嫉妒”），而非硬性违规——且与此处任何规范一样，跳过工具已强制执行的任何内容。

每种异味需先阅读其**含义** → **修复方式**，并与差异进行匹配：

- **晦涩的名称（Mysterious Name）** — 函数、变量或类型名称无法体现其功能或所包含的内容。→ 将其重命名；若无法得出合乎逻辑的名称，则说明该设计不够清晰。
- **重复代码（Duplicated Code）** — 变更中同一逻辑形态在多个片段或文件中重复出现。→ 提取共享形态，在两者中调用。
- **特征嫉妒（Feature Envy）** — 某个方法越界访问其他对象的数据，超过其自身所需。→ 将该方法移至其所嫉妒的对象的数据上。
- **数据簇（Data Clumps）** — 少数相同的字段或参数总是共同移动（某种类型渴望诞生）。→ 将它们整合为一个类型，传递该类型。
- **原始类型迷恋（Primitive Obsession）** — 使用原始类型或字符串代替本应拥有独立类型的领域概念。→ 为该概念提供其专属的小型类型。
- **重复开关（Repeated Switches）** — 在变更中，同一 `switch`/`if` 级联作用于同一类型时不断重复。→ 以多态替代，或使用两个站点共享的一个映射表。
- **全面外科手术（Shotgun Surgery）** — 一处逻辑变更迫使差异在多个文件中分散修改。→ 将相关变更集中到一个模块中。
- **异质变更（Divergent Change）** — 某个文件或模块因多个不相关原因被编辑。→ 进行拆分，使每个模块仅因一个原因变更。
- **推测性泛化（Speculative Generality）** — 为规格中不存在的需求而添加的抽象、参数或钩子。→ 将其删除；待真实需求出现时再内联回去。
- **消息链（Message Chains）** — 调用者无需依赖的冗长 `a.b().c().d()` 导航。→ 将这种遍历隐藏在第一个对象上的单一方法之后。
- **中介（Middle Man）** — 主要仅将请求向下转发的类或函数。→ 将其删除，直接调用真实目标。
- **拒绝继承（Refused Bequest）** — 子类或实现者忽略或覆盖了大部分继承的内容。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

通过一条消息发出两次 `Agent` 工具调用。两个子代理均使用 `general-purpose` 子代理。

**标准（Standards）子代理提示词** — 需包含：

- 完整的差异命令与提交列表。
- 第 3 步中找到的规范来源文件列表，**以及第 3 步中的异味基线完整内容**——子代理无法访问其他资料。
- 摘要：“报告——针对相关文件/代码片段——(a) 差异中违反已记录规范的所有位置：引用规范（文件 + 规则）；以及 (b) 您发现的任何基线异味：命名并引用代码片段。区分硬性违规与判断性决策——已记录规范的违背可以是硬性的，但基线异味始终是判断性决策，且已记录的文档规范优先于基线。跳过工具已强制执行的任何内容。字数不超过 400 字。”

**规格（Spec）子代理提示词** — 需包含：

- 完整的差异命令与提交列表。
- 规格的路径或获取到的内容。
- 摘要：“报告：(a) 规格中要求但缺失或不完整的待满足求；(b) 差异中未按规格要求的行为（范围蔓延）；(c) 看似已实现但实现有误的待满足求。每个发现均引用对应的规格行。字数不超过 400 字。”

若规格缺失，则跳过规格子代理，并在最终报告中注明此事。

### 5. 汇总

将两份报告以 `## 标准` 和 `## 规格` 标题呈现，原文或略作清理即可。**不要**合并或重排发现结果——两条轴线被有意分离（参见 _Why two axes_）。

以一行摘要结尾：各轴线上的发现总数，以及该轴线内最严重的问题（若有）。不要在轴线间选定单一胜者——这正是分离所旨在防止的重排。

## 为何采用两条轴线

变更可能通过一条轴线而失败另一条：

- 遵循了所有标准但实现了错误内容的代码 → **标准通过，规格失败。**
- 代码准确实现了 issue 的要求，但破坏了项目规范 → **规格通过，标准失败。**

分开报告这两项结果，能防止其中一条轴线掩盖另一条轴线的问题。
