双轴审查 `HEAD` 与用户提供的固定点之间的差异：

- **标准** — 代码是否符合此仓库的文档编码标准？
- **规范** — 代码是否忠实地实现了原始问题 / PRD / 规范？

这两个轴都作为 **并行子代理** 运行，以免它们相互污染上下文，然后此技能汇总它们的发现。

问题追踪器应该已经提供给你了 — 如果缺少 `docs/agents/issue-tracker.md`，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定固定点

无论用户所说的固定点是什么 — 提交哈希、分支名称、标签、`main`、`HEAD~5` 等。如果他们没有指定一个，请询问。

一次性捕获 diff 命令：`git diff <固定点>...HEAD`（三个点，以便比较的是合并基点）。同时记录通过 `git log <固定点>..HEAD --oneline` 获取的提交列表。

在进行下一步之前，确认固定点解析 (`git rev-parse <固定点>`) 且 diff 非空。一个坏的引用或空的 diff 应该在这里失败 — 而不是在两个并行子代理内部。

### 2. 确定规范来源

按以下顺序查找原始规范：

1. 提交信息中的问题引用 (`#123`、`Closes #45`、GitLab `!67` 等) — 通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传递的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名称或功能匹配的 PRD/规范文件。
4. 如果未找到任何内容，请询问用户规范在哪里。如果他们说没有规范，**规范** 子代理将跳过并报告“没有可用规范”。

### 3. 确定标准来源

仓库中任何记录代码应该如何编写的文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库记录的内容之上，标准轴始终携带 **气味基线** — 一组固定的 Fowler 代码气味（_重构_，第 3 章），即使仓库未记录任何内容也适用。它由两条规则约束：

- **仓库覆盖。** 文档化的仓库标准总是优先；如果它支持基线会标记的内容，则抑制气味。
- **始终是判断。** 每个气味都是一个标记启发式（“可能的特征依赖”），而不是硬性违反 — 并且，像这里任何标准一样，跳过工具已经强制执行的内容。

每个气味读取 *它是什么* → *如何修复*；将其与 diff 匹配：

- **神秘名称** — 一个函数、变量或类型的名称不揭示其用途或内容。→ 重命名它；如果没有诚实的名称，则设计模糊。
- **重复代码** — 相同的逻辑形状出现在更改的多个代码块或文件中。→ 提取共享形状，从两者中调用。
- **特征依赖** — 一个方法比自己的数据更多地访问另一个对象的数据。→ 将方法移动到它依赖的数据上。
- **数据块** — 相同的几个字段或参数始终一起出现（一个类型想要出生）。→ 将它们捆绑成一个类型，传递该类型。
- **原始类型痴迷** — 一个原始类型或字符串代替了值得它自己的类型的领域概念。→ 给概念自己的小类型。
- **重复开关** — 在更改中对同一类型的相同 `switch`/`if`-级联重复。→ 用多态性替换，或者一个映射共享两个位置。
- **霰弹外科手术** — 一个逻辑更改迫使更改分散在 diff 的许多文件中。→ 将更改的内容聚集到一个模块中。
- **分歧变更** — 一个文件或模块因多个不相关的原因被编辑。→ 分开，使每个模块只有一个原因更改。
- **推测泛化** — 添加了规范没有需求的抽象、参数或挂钩。→ 删除它；回退到真正需求出现之前。
- **消息链** — 调用者不应依赖的长时间 `a.b().c().d()` 导航。→ 将导航隐藏在第一个对象上的一个方法后面。
- **中间人** — 主要只是将请求转发的类或函数。→ 删除它，直接调用真实目标。
- **拒绝继承** — 一个子类或实现者忽略或覆盖了继承的大部分内容。→ 放弃继承，使用组合。

### 4. 并行启动两个子代理

发送一条包含两个 `Agent` 工具调用的消息。使用 `general-purpose` 子代理。

**标准子代理提示** — 包括：

- 完整的 diff 命令和提交列表。
- 第 3 步中找到的标准来源文件列表，**加上第 3 步中的气味基线**（完整粘贴） — 子代理没有其他访问它的方式。
- 简要说明：“报告 — 每个文件/代码块相关 — (a) 每个违反文档标准的 diff 位置：引用标准（文件 + 规则）；以及 (b) 任何发现的基线气味：命名并引用代码块。区分硬性违反与判断 — 文档化标准违规可以是硬性的，但基线气味总是判断，并且文档化的仓库标准优先于基线。跳过工具已经强制执行的内容。少于 400 字。”

**规范子代理提示** — 包括：

- diff 命令和提交列表。
- 规范的路径或获取的内容。
- 简要说明：“报告： (a) 规范要求但缺失或部分的内容； (b) diff 中未要求的行为（范围蔓延）； (c) 看起来已实现的规范，但实现看起来错误的内容。为每个发现引用规范行。少于 400 字。”

如果规范缺失，跳过规范子代理并在最终报告中注明。

### 5. 汇总

在 `## 标准` 和 `## 规范` 标题下呈现两个报告，逐字或稍作清理。**不要** 合并或重新排序发现 — 这两个轴是故意分离的（见 _为什么有两个轴_）。

以一条总结结束：每个轴的总发现，以及每个轴内的最严重问题（如果有）。不要跨轴选择一个赢家 — 这正是分离存在的目的。

## 为什么有两个轴

一个更改可以通过一个轴而失败另一个轴：

- 遵循每个标准但实现了错误内容的代码 → **标准通过，规范失败。**
- 做了问题要求的确切内容但打破了项目约定的代码 → **规范通过，标准失败。**

将它们分别报告可以防止一个轴掩盖另一个轴。
