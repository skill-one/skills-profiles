# Codebase 设计

设计**深度模块**：在简洁的接缝处，通过该接口，以较小的接口承载大量行为，并可通过该接口进行测试。在设计或重构代码时，请始终使用这种表述和这些原则。目标是为调用方提供杠杆效应，为维护者提供局部性，为所有人提供可测试性。

## 术语表

请严格使用这些术语，不要将“组件”“服务”“API”或“边界”替换为其他表述。语言的一致性才是核心要点。

**模块**：任何拥有接口和实现的实体。刻意与规模无关：可以是函数、类、包，或跨越层级的切片。**应避免**：单元、组件、服务。

**接口**：调用方必须了解该模块才能正确使用它的全部内容：包括类型签名，以及不变式、顺序约束、错误模式、所需配置和性能特征。**应避免**：API、签名（过于狭窄，仅指类型层面的表面）。

**实现**：模块内部的内容，其代码体。与**适配器**不同：某物可以是一个小的适配器，但拥有大的实现（如 Postgres 仓库）；也可以是一个大的适配器，但拥有小的实现（如内存假对象）。当接缝是讨论主题时使用“适配器”；否则使用“实现”。

**深度**：接口层面的杠杆效应。调用方（或测试）每掌握一定量的接口，即可调用的行为量。当大量行为位于较小的接口背后时，模块即为**深度**模块；当接口的复杂度与实现几乎相当时，即为**浅层**模块。

**接缝**（Michael Feathers）：你可以在无需编辑该处即可修改行为的位置；模块接口所在的位置。接缝置于何处是其自身的方案决策，与接缝后放置的内容相互独立。**应避免**：边界（过度承载 DDD 的有界上下文）。

**适配器**：在接缝处满足接口的具体事物。描述的是**角色**（它填补什么位置），而非**实质**（内部是什么）。

**杠杆效应**：调用方从深度中获得的收益。每掌握一定接口，便获得更多能力。一个实现可在 N 个调用点处，并为 M 个测试实现价值回报。

**局部性**：维护者从深度中获得的收益。变更、缺陷、知识与验证集中于单一位置，而非分散在调用方各处。一次修复，处处生效。

## 深度与浅层

**深度模块** = 较小的接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅层模块** = 较大的接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

在设计接口时，请自问：

- 我能否减少方法的数量？
- 我能否简化参数？
- 我能否将更多复杂性隐藏在内部？

## 原则

- **深度是接口的属性，而非实现的属性。** 深度模块在内部可以由小型、可模拟、可替换的部分组成；这些部分只是接口的一部分。一个模块既可以有**内部接缝**（仅对自身实现私有，由其自身测试使用），也可以有位于接口处的**外部接缝**。
- **删除测试。** 想象删除该模块。如果复杂性消失，则它只是一个透传；如果复杂性在 N 个调用方处重新出现，则它自身是有价值的。
- **接口即测试表面。** 调用方与测试通过相同的接缝。如果你想在接口之外进行测试，那么该模块很可能形状不当。
- **一个适配器意味着假设的接缝，两个适配器意味着真实的接缝。** 除非某物在接缝处确实存在变化，否则不要引入接缝。

## 面向可测试性设计

良好的接口使测试自然化：

1. **接受依赖，而非创建依赖。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而非产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **较小的表面区域。** 方法越少，所需测试越少；参数越少，测试配置越简单。

## 关系

- **模块**有且仅有一个**接口**（其向调用方和测试呈现的表面）。
- **深度**是**模块**的属性，以**接口**为衡量标准。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**位于**接缝**处，并满足**接口**。
- **深度**为调用方产生**杠杆效应**，为维护者产生**局部性**。

## 不推荐的框架表述

- **将深度视为实现行数与接口行数之比**（Ousterhout）：奖励填充实现代码。我们采用“深度即杠杆效应”的表述。
- **将“接口”理解为 TypeScript 的 `interface` 关键字或类的公共方法**：过于狭窄。此处的接口包含了调用方必须了解的所有事实。
- **“边界”**：过度承载 DDD 的有界上下文。请使用**接缝**或**接口**。
