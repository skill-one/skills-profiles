# 代码库设计

设计**深度模块**：在小的接口背后封装大量行为，放置在干净的接口处，通过该接口进行测试。无论何时进行代码设计或重构，都要使用这种语言和这些原则。目标是给调用者提供便利，给维护者提供局部性，给所有人提供可测试性。

## 术语表

使用以下术语，不要替换"组件"、"服务"、"API"或"边界"。一致的语言是整个要点。

**模块**：具有接口和实现的任何事物。有意地与规模无关：一个函数、类、包或跨层级的切片。_避免使用_：单元、组件、服务。

**接口**：调用者正确使用模块所需了解的所有内容：类型签名，但还包括不变性、顺序约束、错误模式、所需配置和性能特征。_避免使用_：API、签名（过于狭窄，它们仅指类型级别的表面）。

**实现**：模块内部的内容，其代码主体。与**适配器**不同：一个事物可以是一个具有大实现的适配器（例如Postgres仓库），也可以是一个具有小实现的适配器（例如内存中的假对象）。当接口是主题时，使用"适配器"；否则使用"实现"。

**深度**：在接口处的便利性。调用者（或测试）每学习一个接口单元可以执行的行为量。当大量行为位于小接口背后时，模块是**深度**的；当接口几乎与实现一样复杂时，模块是**浅层**的。

**接口缝隙** _(Michael Feathers)_：你可以在不修改该位置的情况下更改行为的位置；模块接口存在的地方。将缝隙放在哪里是其自己的设计决策，与其背后是什么无关。_避免使用_：边界（在DDD的限界上下文中过载）。

**适配器**：在缝隙处满足接口的具体事物。描述*角色*（它填补了什么位置），而不是*实质*（它里面有什么）。

**便利性**：调用者从深度中获得的内容。每学习一个接口单元，他们可以获得更多的功能。一个实现可以在N个调用站点和M个测试中偿还一次。

**局部性**：维护者从深度中获得的内容。更改、错误、知识和验证集中在一点，而不是分散到调用者。修复一次，到处都修复了。

## 深度与浅层

**深度模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   小接口           │  ← 少量方法，简单的参数
├─────────────────────┤
│                     │
│  深度实现          │  ← 隐藏了复杂的逻辑
│                     │
└─────────────────────┘
```

**浅层模块** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│       大接口           │  ← 许多方法，复杂的参数
├─────────────────────────────────┤
│  薄实现                │  ← 仅传递通过
└─────────────────────────────────┘
```

设计接口时，请询问：

- 我能否减少方法数量？
- 我能否简化参数？
- 我能否将更多复杂性隐藏在内部？

## 原则

- **深度是接口的特性，而不是实现的特性。** 一个深度模块可以由小、可模拟、可替换的部分内部组成；它们不属于接口。一个模块可以有**内部缝隙**（仅限于其实现，由其自己的测试使用）以及其接口处的**外部缝隙**。
- **删除测试。** 想象删除模块。如果复杂性消失，它是一个传递。如果复杂性在N个调用者中重新出现，它是在发挥作用。
- **接口是测试表面。** 调用者和测试穿过同一个缝隙。如果你想要测试*接口之外*的内容，模块可能形状不正确。
- **一个适配器意味着一个假设的缝隙。两个适配器意味着一个真实的缝隙。** 除非缝隙两侧实际上存在变化，否则不要引入缝隙。

## 为可测试性而设计

好的接口使测试变得自然：

1. **接受依赖项，而不是创建它们。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面区域。** 方法越少，需要的测试越少。参数越少，测试设置越简单。

## 关系

- 一个**模块**恰好有一个**接口**（它向调用者和测试展示的表面）。
- **深度**是**模块**的特性，相对于其**接口**进行衡量。
- 一个**缝隙**是**模块**的**接口**存在的地方。
- 一个**适配器**位于**缝隙**处，并满足**接口**。
- **深度**为调用者提供**便利性**，为维护者提供**局部性**。

## 被拒绝的框架

- **深度是实现行数与接口行数的比率**（Ousterhout）：奖励填充实现。我们使用深度作为便利性代替。
- **"接口"作为TypeScript的`interface`关键字或类的公共方法**：过于狭窄：这里的接口包括调用者必须知道的每个事实。
- **"边界"**：在DDD的限界上下文中过载。说**缝隙**或**接口**。
