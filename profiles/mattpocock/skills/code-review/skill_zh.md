两轴审查 `HEAD` 与用户提供的固定点之间的差异：

- **标准**：代码是否符合本仓库记录的编码规范？
- **规范**：代码是否忠实地实现了原始问题 / 规范？

两个轴均作为 **并行子代理** 运行，以避免污染彼此的执行上下文，随后本技能将对它们的发现结果进行汇总。

应向您提供问题跟踪器。如果 `docs/agents/issue-tracker.md` 缺失，请告知用户运行 `/setup-matt-pocock-skills`。

## 处理流程

### 1. 确定固定点

用户所说的内容即为固定点（一个提交 SHA、分支名、标签、`main`、`HEAD~5` 等）。如果他们未指定其中一个，请向他们询问。

一次性记录差异命令：`git diff <fixed-point>`...`HEAD`（使用三点号，即与合并基进行比较）。同时通过 `git log <fixed-point>`..`HEAD` --oneline` 记录提交列表。

在继续之前，请确认固定点能够解析（`git rev-parse <fixed-point>`...）且差异不为空。错误的引用或空的差异应在此处导致失败，而不是在两个并行的子代理内部失败。

### 2. 识别规范来源

按以下顺序查找原始规范：

1. 提交信息中的问题引用（`#123`、`Closes #45`、GitLab `!67` 等），通过 `docs/agents/issue-tracker.md` 中记录的流程获取。
2. 用户作为参数传递的路径。
3. 位于 `docs/`、`specs/` 或 `.scratch/` 目录下、与分支名或功能相匹配的规范文件。
4. 若未找到，请询问用户规范在哪里。如果他们表示不存在规范，则 **规范** 子代理将跳过并报告“无可用规范”。

### 3. 识别标准来源

仓库中任何记录代码应如何编写的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库记录的任何内容之上，标准轴始终包含下方的 **气味基准（smell baseline）**：一组固定的 Fowler 代码异味（_Refactoring_，第 3 章），即使仓库未做任何文档说明，该基准依然适用。两条规则约束其应用：

- **The repo overrides.** 已记录的仓库标准始终优先；若标准倡导了基准会标记的内容，则抑制该异味。
- **始终是判断性操作。** 每个异味都是带有标签的启发式规则（“可能存在的特征嫉妒”），绝非硬性违规。如同此处其他标准一样，跳过任何工具已强制执行的代码。

每个异味均说明其*是什么* → *如何修复*；请将其与差异进行匹配：

- **Mysterious Name（神秘名称）**：一个函数、变量或类型，其名称无法揭示其执行的操作或所承载的内容。 → 重命名它；若无法得出合理的名称，则说明该设计不够清晰（模糊）。
- **Duplicated Code（重复代码）**：变更中相同的逻辑形态出现在多个片段或文件中。 → 提取共享的形态，并从中调用。
- **Feature Envy（特征嫉妒）**：一个方法越界访问了其他对象的数据，超过了其自身所需。 → 将该方法移动到它所嫉妒的数据对象上。
- **Data Clumps（数据簇）**：相同的少数字段或参数始终一起传递（一个类型渴望诞生）。 → 将它们打包成一个类型，并传递该类型。
- **Primitive Obsession（原语迷恋）**：一个为需要拥有独立类型的领域概念而使用原语或字符串。 → 为该概念赋予其专属的小型类型。
- **Repeated Switches（重复切换）**：同一类型上的相同 `switch`/`if`-级联在变更中多次递归出现。 → 用多态替换，或使用一个两个站点共享的映射。
- **Shotgun Surgery（全面手术）**：一项逻辑变更在差异中强制在多个文件中产生分散的修改。 → 将需要变更的内容聚合到一个模块中。
- **Divergent Change（差异化的变更）**：一个文件或模块因多个无关的原因而被修改。 → 拆分，使每个模块只为一个原因而变更。
- **Speculative Generality（过度泛化的抽象）**：为规范中并未有的需求而添加的抽象、参数或钩子。 → 删除这些内容；直到出现实际需求再内联回去。
- **Message Chains（消息链）**：调用者不应依赖的冗长 `a.b().c().d()` 导航。 → 将这种遍历隐藏在首个对象上的一个方法之后。
- **Middle Man（中间人）**：一个主要只是转发任务的类或函数。 → 删除它，直接调用真正的目标。
- **Refused Bequest（拒绝继承）**：一个子类或实现者忽略了或覆盖了其继承的大部分内容。 → 放弃继承，使用组合。

### 4. 并行启动两个子代理

**标准子代理提示词**应包含：

- 完整的差异命令和提交列表。
- 在步骤 3 中找到的标准来源文件列表，**以及步骤 3 中的气味基准**完整粘贴（子代理没有其他途径访问这些信息）。
- 简报：“报告：(a) 差异中所有违反已记录标准的地方：引用标准（文件 + 规则）；(b) 发现的任何基准异味：说明其名称并引用代码片段。区分硬性违规与判断性操作：已记录标准的违反可能属于硬性违规，但基准异味始终是判断性操作，且已记录的仓库标准会覆盖基准。跳过任何工具已强制执行的代码。字数不超过 400 字。”

**规范子代理提示词**应包含：

- 差异命令和提交列表。
- 规范的路径或获取的内容。
- 简报：“报告：(a) 规范要求但缺失或不完整的需求；(b) 差异中未经规范要求的行为（范围蔓延）；(c) 看似已实现但实现有误的需求。每个发现均引用规范的原文。字数不超过 400 字。”

如果规范缺失，请跳过规范子代理，并在最终报告中注明这一点。

### 5. 汇总

在 `## 标准` 和 `## 规范` 标题下呈现两个报告，原文或轻微清理即可。**不要**合并或重新排序发现结果，因为这两个轴是故意分离的（见 _为什么有两个轴_）。

以一行总结结尾：各轴的总发现数，以及各轴中最严重的问题（若有）。**不要**在轴间选出单一的胜出项：这正是分离所旨在防止的重新排序。

## 为什么有两个轴

一项变更可以在一个轴上通过，而在另一个轴上失败：

- 符合每一项标准但实现内容错误的代码 → **标准通过，规范失败。**
- 完全按照问题要求实现，但违反了项目规范的代码 → **规范通过，标准失败。**

分别报告它们，可以避免其中一个轴掩盖另一个轴的问题。
