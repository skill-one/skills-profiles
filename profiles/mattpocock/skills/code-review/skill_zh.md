双轴审查 `HEAD` 与用户提供的固定点之间的差异：

- **标准**：代码是否符合此仓库的文档编码标准？
- **规范**：代码是否忠实地实现了原始问题/规范？

这两个轴都作为 **并行子代理** 运行，以免相互污染上下文，然后此技能汇总它们的发现。

问题追踪器应该已经提供给你了。如果缺少 `docs/agents/issue-tracker.md`，请告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定固定点

无论用户所说的固定点是什么（一个提交哈希、分支名、标签、`main`、`HEAD~5` 等）。如果他们没有指定，请询问。

一次性捕获 diff 命令：`git diff <固定点>...HEAD`（三个点，以便与合并基进行比较）。同时记录通过 `git log <固定点>..HEAD --oneline` 获取的提交列表。

在进行下一步之前，确认固定点解析 (`git rev-parse <固定点>`) 且 diff 非空。一个坏的引用或空的 diff 应该在这里失败，而不是在两个并行子代理内部。

### 2. 确定规范来源

按以下顺序查找原始规范：

1. 提交信息中的问题引用（`#123`、`Closes #45`、GitLab `!67` 等），通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传递的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规范文件。
4. 如果未找到任何内容，请询问用户规范在哪里。如果他们说没有规范，**规范** 子代理将跳过并报告“没有可用规范”。

### 3. 确定标准来源

仓库中任何文档说明代码应该如何编写的文件，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库文档的基础上，标准轴始终携带 **气味基线**：一组固定的 Fowler 代码气味（_重构_，第 3 章），即使仓库未进行任何文档化也适用。它由两条规则约束：

- **仓库覆盖**。文档化的仓库标准总是优先；如果它支持基线会标记的内容，则抑制气味。
- **始终是判断**。每个气味都是一个标记启发式（“可能的特征依赖”），而不是一个硬性违规。像这里任何标准一样，跳过工具已经强制执行的内容。

每个气味读取 *它是什么* → *如何修复*；与 diff 匹配：

- **神秘名称**：函数、变量或类型，其名称无法揭示其作用或包含的内容。→ 重命名它；如果没有诚实的名称，设计就模糊不清。
- **重复代码**：相同的逻辑形状出现在更改的多个代码块或文件中。→ 提取共享形状，从两者中调用。
- **特征依赖**：一个方法访问另一个对象的数据比访问自己的数据更多。→ 将方法移动到它依赖的数据上。
- **数据块**：相同的几个字段或参数经常一起出现（一个类型想要诞生）。→ 将它们捆绑成一个类型，传递该类型。
- **原始类型痴迷**：一个原始类型或字符串代替了值得它自己的类型的领域概念。→ 给概念赋予它自己的小类型。
- **重复的开关**：在更改中对同一类型的相同 `switch`/`if`-级联。→ 用多态性替换，或一个映射共享两个位置。
- **散弹手术**：一个逻辑更改迫使在 diff 的许多文件中进行分散的编辑。→ 将更改的内容聚集到一个模块中。
- **分歧变更**：一个文件或模块因多个不相关的原因被编辑。→ 分开，使每个模块只有一个原因进行更改。
- **推测的普遍性**：为规范没有的需求添加的抽象、参数或钩子。→ 删除它；反引用直到出现真实需求。
- **消息链**：调用者不应依赖的 `a.b().c().d()` 长导航。→ 隐藏行走在第一个对象上的一个方法后面。
- **中间人**：一个主要只是将请求转发的类或函数。→ 删除它，直接调用真实目标。
- **拒绝继承**：一个子类或实现者忽略或覆盖了继承的大部分内容。→ 放弃继承，使用组合。

### 4. 并行启动两个子代理

**标准子代理提示** 应包括：

- 完整的 diff 命令和提交列表。
- 第 3 步中找到的标准来源文件列表，**加上第 3 步中的气味基线**（完整粘贴）（子代理无法访问其他内容）。
- 简要说明：“报告，按文件/代码块的相关性，(a) 每个违反文档标准的地方：引用标准（文件 + 规则）；以及 (b) 任何发现的基线气味：命名它并引用代码块。区分硬性违规与判断：文档标准违规可以是硬性的，但基线气味总是判断，并且文档化的仓库标准优先于基线。跳过工具已经强制执行的内容。少于 400 字。”

**规范子代理提示** 应包括：

- diff 命令和提交列表。
- 规范的路径或获取的内容。
- 简要说明：“报告： (a) 规范要求但缺失或部分的内容； (b) diff 中未要求的行为（范围蔓延）； (c) 看起来已实现的规范，但实现看起来错误的内容。为每个发现引用规范行。少于 400 字。”

如果规范缺失，跳过规范子代理，并在最终报告中注明。

### 5. 汇总

在 `## 标准` 和 `## 规范` 标题下呈现两个报告，原文或轻微清理。**不要** 合并或重新排序发现，因为这两个轴是故意分离的（见 _为什么有两个轴_）。

以一条简短总结结束：每个轴的总发现，以及每个轴内的最严重问题（如果有）。不要跨轴选择单一赢家：这是分离存在的目的，以防止重新排序。

## 为什么有两个轴

一个更改可以通过一个轴而失败另一个轴：

- 符合所有标准但实现了错误内容的代码 → **标准通过，规范失败。**
- 代码完全实现了问题要求但打破了项目的惯例 → **规范通过，标准失败。**

将它们分别报告可以防止一个轴掩盖另一个轴。
