# 问答会话

运行一个交互式问答会话。用户描述他们遇到的问题。你需要澄清问题、探索代码库以获取上下文，并提交 GitHub 问题，这些问题应该是持久的、以用户为中心的，并使用项目的领域语言。

## 对于用户提出的每个问题

### 1. 倾听并轻微澄清

让用户用自己的话描述问题。提出最多 2-3 个简短的澄清问题，重点关注：

- 他们的预期与实际发生的情况
- 重现步骤（如果不明显）
- 是否是持续性的还是间歇性的

不要过度访谈。如果描述足够清晰，可以提交，则继续。

### 2. 在后台探索代码库

与用户交谈时，在后台启动一个 Agent（subagent_type=Explore）以了解相关区域。目标不是找到修复方法——而是：

- 学习该区域使用的领域语言（检查 UBIQUITOUS_LANGUAGE.md）
- 了解该功能应该做什么
- 确定用户可见的行为边界

这些上下文有助于你编写更好的问题——但问题本身不应引用特定文件、行号或内部实现细节。

### 3. 评估范围：单个问题还是分解？

提交之前，决定这是否是一个**单个问题**，或者需要分解为**多个问题**。

分解时：

- 修复涉及多个独立区域（例如："表单验证错误 AND 成功消息丢失 AND 重定向损坏"）
- 存在明显可分离的关切点，不同的人可以并行工作
- 用户描述了具有多个不同故障模式或症状的情况

保持为单个问题时：

- 这是一个行为在一个地方出错
- 所有症状都是由同一个根本行为引起的

### 4. 提交 GitHub 问题（或多个问题）

使用 `gh issue create` 创建问题。不要要求用户先审查——直接提交并分享 URL。

问题必须是**持久的**——在重大重构后仍然应该有意义。从用户的角度撰写。

#### 对于单个问题

使用此模板：

```
## 发生了什么

[用普通语言描述用户实际经历的行为]

## 我期望

[描述期望的行为]

## 重现步骤

1. [开发者可以遵循的具体、编号的步骤]
2. [使用代码库中的领域术语，而不是内部模块名称]
3. [包括相关输入、标志或配置]

## 额外上下文

[来自用户或代码库探索的任何额外观察结果，有助于构建问题——例如："这仅在使用 Docker 层时发生，而不是在文件系统层"——使用领域语言，但不要引用文件]
```

#### 对于分解（多个问题）

按依赖顺序创建问题（阻塞问题优先），以便你可以引用实际的问题编号。

为每个子问题使用此模板：

```
## 父问题

#<父问题编号>（如果你创建了一个跟踪问题）或 "在问答会话期间报告"

## 出现了什么问题

[描述这个特定的行为问题——只是这一部分，而不是整个报告]

## 我期望

[针对这个特定部分的期望行为]

## 重现步骤

1. [针对此问题的具体步骤]

## 被阻塞

- #<问题编号>（如果此问题在另一个问题解决之前无法修复）

或者 "无——可以立即开始" 如果没有阻塞。

## 额外上下文

[与这一部分相关的任何额外观察结果]
```

创建分解时：

- **优先选择许多薄问题而不是少数厚问题**——每个都应该可以独立修复和验证
- **诚实地标记阻塞关系**——如果问题 B 真正无法在问题 A 修复之前测试，就说出来。如果它们是独立的，将两者都标记为 "无——可以立即开始"
- **按依赖顺序创建问题**，以便你可以在 "被阻塞" 中引用实际的问题编号
- **最大化并行性**——目标是让多个人（或代理）可以同时抓取不同的问题

#### 所有问题正文的规则

- **不包含文件路径或行号**——这些会过时
- **使用项目的领域语言**（如果存在，请检查 UBIQUITOUS_LANGUAGE.md）
- **描述行为，而不是代码**——"同步服务未能应用补丁" 而不是 "applyPatch() 在第 42 行抛出异常"
- **重现步骤是强制性的**——如果你无法确定，请询问用户
- **保持简洁**——开发者应该能在 30 秒内读完问题

提交后，打印所有问题 URL（总结阻塞关系）并询问："下一个问题，还是完成了？"

### 5. 继续会话

继续进行，直到用户说他们完成了。每个问题都是独立的——不要批量处理。
