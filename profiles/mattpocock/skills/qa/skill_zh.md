# QA 会话

启动交互式 QA 会话。用户描述所遇到的问题。你需要进行澄清，探索代码库获取上下文，并提交持久、面向用户、使用项目领域语言的 GitHub 问题。

## 针对用户提出的每个问题

### 1. 倾听并适当澄清

让用户用自己的语言描述问题。最多提出 **2-3 个简短的澄清问题**，重点关注：

- 他们预期的情况与实际发生的情况
- 复现步骤（如果不太明确）
- 问题是否一致出现还是间歇性出现

不要过度询问。如果描述已经足够清晰可以提交，则继续进行。

### 2. 在后台探索代码库

在与用户交流的同时，在后台启动一个 Agent（subagent_type=Explore）以理解相关区域。目标是**不是**寻找修复方案，而是：

- 学习该区域使用的领域语言（检查 UBIQUITOUS_LANGUAGE.md）
- 了解该功能应当实现什么
- 确定面向用户的行为边界

这些上下文有助于你编写更好的问题——但问题本身**不应**引用具体文件、行号或内部实现细节。

### 3. 评估范围：单个问题还是需要拆分？

提交之前，决定这是**单个问题**，还是需要**拆分为多个问题**。

需要拆分的情况：

- 修复方案跨越多个独立领域（例如"表单验证错误 且 成功提示缺失 且 重定向失效"）
- 存在明显可分离的关切点，可由不同人员并行处理
- 用户描述的内容存在多种不同的故障模式或症状

保持为单个问题的情况：

- 某处存在一项错误的行为
- 所有症状都由同一个根本行为导致

### 4. 提交 GitHub 问题

使用 `gh issue create` 创建问题。**不要**先让用户审核，只需提交并分享链接。

问题必须**持久化**——在重大重构后仍然有意义。以用户的视角撰写。

#### 针对单个问题

使用此模板：

```
## What happened

[用通俗语言描述用户实际遇到的行为]

## What I expected

[描述期望的行为]

## Steps to reproduce

1. [开发者可以遵循的具体、带编号的步骤]
2. [使用代码库中的领域术语，而非内部模块名称]
3. [包含相关的输入、标志或配置]

## Additional context

[来自用户或代码库探索的额外观察，有助于界定问题——例如"仅在使用 Docker 层时发生，而非文件系统层"——使用领域语言，但不要引用文件]
```

#### 针对拆分情况（多个问题）

按依赖顺序创建问题（先创建阻塞性问题），以便可以引用真实的问题编号。

为每个子问题使用此模板：

```
## Parent issue

# <parent-issue-number（若已创建跟踪问题）或 "Reported during QA session"

## What's wrong

[描述此特定行为问题——仅描述此部分，而非整个报告]

## What I expected

[针对此具体部分的期望行为]

## Steps to reproduce

1. [针对此问题特有的步骤]

## Blocked by

- # <issue-number（若该问题无法在其他问题解决后才能修复）

或 "None — can start immediately"（若无阻塞项）

## Additional context

[与本切片相关的任何额外观察]
```

当创建拆分时：

- **优先创建多个薄问题，而非少数厚问题** ——每个问题应独立可修复和可验证
- **如实标注阻塞关系** ——如果问题 B 确实无法在问题 A 修复后才能测试，需说明这一点。若相互独立，则将两者均标注为"None — can start immediately"
- **按依赖顺序创建问题**，以便在"Blocked by"中引用真实的问题编号
- **最大化并行度** ——目标是让多人（或 Agent）可同时领取不同的问题

#### 所有问题正文的规则

- **不使用文件路径或行号** ——这些信息会过时
- **使用项目的领域语言**（如存在 UBIQUITOUS_LANGUAGE.md，请检查）
- **描述行为，而非代码** ——"同步服务无法应用补丁"而非"applyPatch() 在第 42 行抛出异常"
- **必须提供复现步骤** ——如果无法确定，则询问用户
- **保持简洁** ——开发者应在 30 秒内阅读完该问题

提交后，打印所有问题链接（并总结阻塞关系），并询问："下一个问题，还是我们已结束？"

### 5. 继续会话

持续进行，直到用户表示已完成。每个问题相互独立——不要批量处理。
