# Ask Matt

你记不住所有技能，所以去问。

一个**flow**是穿过技能的路径。大部分路径沿着一条**main flow**运行，两条**on-ramps**汇入其中。其他都是独立的，或者是运行在底层的基础词汇层。

## 主流程：想法 → 交付

大多数工作所走的路线。你有一个想法，想要它被实现。

1. **`/grill-with-docs`** 通过访谈打磨想法。在**working directory**（工作目录）中工作时随时从这里开始：它是有状态的，保留它学到的内容在 `CONTEXT.md` 和 ADRs 中。（没有工作目录？改用 `/grill-me`，在 Standalone 部分有说明。两者都运行相同的 `/grilling` 原语；`grill-with-docs` 是留痕的，因此在有仓库可以留痕时，它比后者更好。）
2. **分支：能在对话中解决所有问题吗？** 如果一个问题需要可运行的答案（状态、业务逻辑、必须看到的 UI），就通过**`/handoff`**（双向）绕行到原型，原型保存在自己的目录中（这正是 `/handoff` 的用途；见 Phase boundaries）：
   - 通过 **`/handoff`** 输出，然后针对该文件开启新的会话，
   - **`/prototype`** 用临时代码回答问题，
   - **`/handoff`** 带回学到的内容，并从原始想法线程中引用它。
3. **分支：这是多会话的构建吗？**
   - **是** → **`/to-spec`**（将线程转化为规格），然后 **`/to-tickets`** 将其拆分为 tracer-bullet 工单，每个工单声明其**blocking edges**（阻塞边缘）。在本地跟踪器中，每个工单是一个文件，位于 `.scratch/<feature>/issues/` 下，手动按块优先处理；在真正的跟踪器中，边缘变为原生的阻塞链接，因此任何阻塞已完成工单都可以被获取：为每个工单启动 **`/implement`**，**`/clear`ing** 上下文（清理上下文）在每个之间。每个工单都是自包含的，所以最后一个工单的上下文是可丢弃的。
   - **否** → **`/implement`** 在这里，在同一上下文窗口内进行。

   无论如何，**`/implement`** 都会通过驱动**`/tdd`**（内部，逐 red-green slice）构建每个 issue，然后通过运行 **`/code-review`** 结束，这是一个对 diff 的双轴审查（Standard + Spec），随后提交。当你只想在不具备完整规格的情况下优先构建具体的测试行为时，直接使用 **`/tdd`**；当你想审查分支或 PR 对固定点的符合性时，直接使用 **`/code-review`**。

### 上下文卫生

保持步骤 1–3 在**一个不中断的上下文窗口**中（在 `/to-tickets` 之后不要压缩或清理上下文），使 grilling、规格和工单都建立在相同的思考之上。每个 `/implement` 然后重新开始，基于工单进行工作。

这一限制是**[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：在这个窗口内（在顶尖模型中约为 150k tokens），模型仍能锐利推理。如果会话在 `/to-tickets` 之前接近该限制，不要推入降级状态；在最近的阶段边界处执行 `/compact` 并继续（见 Phase boundaries）。

## 入口（On-ramps）

生成工作并汇入主流程的起始情况。

- **问题与请求堆积** → **`/triage`**。它通过分诊角色移动问题，并生成可供 agent 使用的问题，**`/implement`** 稍后接手。

  Triage 仅用于**你未创建**的问题：bug 报告、收到的功能请求、任何原始到达的内容。`/to-tickets` 生成的工单已经是可供 agent 使用的，所以不要对它们进行 Triage。

- **出现问题** → **`/diagnosing-bugs`**。对于那些不易通过初步查看发现的问题：难以用初次观察解决的问题、间歇性故障、在两个已知正常状态之间出现的回归问题。它在拥有**紧密的反馈循环**（一个命令在此 bug 上已会变红）之前拒绝理论分析，然后通过回归测试进行修复。其事后复盘会将发现——即没有合适的接缝来锁定 bug——移交给**`/improve-codebase-architecture`**。

- **一个庞大、模糊的工程：全新项目或巨大的功能构建，一次会话无法完成** → **`/wayfinder`**，这是此处认知需求最高的流程。当从这里到目的地的路径尚未可见时，它绘制一条**共享地图**，包含**决策工单**，并逐个解决，产生**决策，而非交付物**，直到雾气散去、路径清晰。当**`/grill-with-docs`** 能打磨你可以在一个会话中持有的想法时，wayfinder 用于你无法在一个会话中持有的想法，它更慢、更密集，因此仅用于这种情况，绝不可用于范围明确的特性。

  当地图清晰时，**它会移交，而非构建**：在 **`/to-spec`** 处汇入主流程，该处将地图关联的决策压缩为可构建的计划，然后按常规进行 `/to-tickets` 和 `/implement`。直接将地图循环交给 `/implement` 会跳过压缩，并丢弃关联的细节，因此仅在工程实际上很小的情况下才直接进行 `/implement`。

## 代码库健康

不是功能工作，只是维护。

- **`/improve-codebase-architecture`** 在你有空闲时间维持代码库对 agent 可操作时运行。它暴露**深化机会**；选择其中一个**生成一个想法**，你可以在 `/grill-with-docs` 处将其带入主流程。它是发现候选者的调查；**`/codebase-design`**（下文）是你选择该选项的测试场。

## 底层词汇

两个由模型调用的引用，运行在其它技能之下，每个都是其词汇的单一事实来源。当**过程**不是问题，而是**词语**有问题时，直接使用它们；或者让上方的技能将它们引入。

- **`/domain-modeling`**：精炼项目的**领域**语言：质疑模糊术语，解决过载的词汇（“账户”执行三项任务），将难以逆转的决策记录为 ADR。它是**`/grill-with-docs`** 维持 `CONTEXT.md` 成为清晰术语表的积极纪律。
- **`/codebase-design`** 是设计模块**形状**的深层模块词汇（模块、接口、深度、接缝、适配器、利用、局部性）：在清晰的接缝背后，大量行为由小型接口承载。**`/tdd`** 和 **`/improve-codebase-architecture`** 都使用它。

## 阶段边界

**phase** 是会话内的工作块：grilling、实现、QA。在两个 phase **之间**的边界，你有五个选项，选择它们是最模糊的决定：

- **继续**：保持原状。零成本，零损失。
- **`/clear`**：清空窗口，当这里对下一步不重要时。
- **`/handoff`** 写入可移植的 markdown 文件。范围窄：仅用于**新 harness**、**新目录**、**同事**，或在阶段中途 fork 一个副任务。它带来的是可移植性。
- **子代理（Subagent）**：将范围紧密的任务发送到其独立窗口，并获取报告返回。
- **`/compact`** 压缩此上下文，并以它为种子开启新的会话。这是**默认选项**，位于树底而非首个到达处。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 获取有序树：五个问题、每个分支背后的推理，以及为什么主来源成本使 **Continue** 成为应首先排除的选择。在边界**处**做决定；在阶段中途，继续或将其余部分拆分为子代理。

## 独立（Standalone）

完全脱离主流程。

- **`/grill-me`**：与 **`/grill-with-docs`** 相同的持续访谈，但**无状态**：它不本地保存任何内容，也不构建 `CONTEXT.md`。当**你不在工作目录**中（精炼计划、设计、文本片段，任何没有其下仓库的内容）时使用它。如果你在工作目录中，改用 `/grill-with-docs`：它运行相同的访谈并留下纸面记录，因此它严格来说是更好的选择。
- **`/grilling`** 本身是访谈原语：轮次、前沿、事实是 agent 的工作，决策是你的工作。**`/grill-me`** 和 **`/grill-with-docs`** 是两个命名的进入方式，**`/triage`**、**`/wayfinder`** 和 **`/improve-codebase-architecture`** 都内部运行它。仅当你想不带包装的访谈时，直接使用它。
- **`/resolving-merge-conflicts`** 按 hunk（块）逐块处理进行中的合并或 rebase 冲突，通过追溯到每侧主来源的**意图**来解决，而非选择行，然后完成操作。它从不运行 `--abort`。独立且脱离所有流程：当你已经处于冲突中时使用它。
- **`/prototype`** 是一个小型、临时程序，用于回答一个设计问题：这个状态模型感觉是否正确，或者这个 UI 应该是什么样子。临时性是代码编写方式的一个约束，而非销毁它的承诺：答案融入实际代码，且原型本身作为 **main** 分支外的 **`prototype/<name>`** 分支保留为**主来源**，并从实现 issue 指向它。它是主流程步骤 2 中的绕行，但当纸上难以确定设计问题时，随时使用它。
- **`/research`**：将阅读工作委托给**后台 agent**：它针对**主来源**调查问题，然后在仓库中留下引用来源的 markdown 文件。它阅读时，你继续工作。它生成的文件是需要通过 **`/grill-with-docs`** 带入**主流程**的内容，因为研究为思考提供输入，而非替换它。
- **`/to-questionnaire`** 在阻碍你的东西既不在你的脑海中，也不在代码库中，而是在**他人**处时出现，它向他们发送问卷以填写。它是 **`/grill-me`** 的逆：不是就主题访谈你，而是访谈你关于**发送**（去向、所需返回），并将问题对准差距。返回的内容是 **`/grill-with-docs`** 或 **`/to-spec`** 的材料。
- **`/wizard`** 用于仅**人类**能执行步骤：基础设施开通、设置凭据或 CI 秘密、点击不熟悉的第三方仪表板、运行一次性迁移或切换。它生成交互式 bash 脚本，打开每个 URL，捕获每个值，并写入 `.env` 和 GitHub 秘密，使流程不再需要每次都向 agent 重新解释。由模型调用，因此当 agent 遇到仅你能通过的地步时，会立即使用它。如果 agent 能自行完成，它应该；这是真正处于人类循环中的情况。
- **`/wait-what`** 是消息未送达时的纠正措施。在对话中途、任何其他技能内部使用它，agent 会用你用缺失的上下文补充的、通俗英语，使用 **`CONTEXT.md`** 词汇，重新提出它刚才所说的话。它在事后生效；**`/grill-with-docs`** 是提前的治愈方法，因为早期商定的共同语言是阻止术语产生的基础。
- **`/teach`**：通过多个会话学习概念，使用当前目录作为有状态工作区。
- **`/writing-for-agents`** 是编写 agent 消费的文件的参考：技能、`AGENTS.md`、被指向的文档。

## 前提条件

**`/setup-matt-pocock-skills`**：在首次执行任何工程流程之前运行，以配置其他技能所假设的问题跟踪器、分诊标签和文档布局。自定义问题跟踪器也适用。
