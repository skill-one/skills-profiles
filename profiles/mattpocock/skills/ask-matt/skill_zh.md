# 询问马特

你不会记得所有技能，所以请提问。

一个**流程**是通过技能的路径。大多数路径沿着一个**主流程**运行，两个**匝道**合并到它上面。其他所有内容都是独立的，或者是一个在下面运行的词汇层。

## 主流程：想法→交付

大多数工作经过的路线。你有一个想法，并希望它被构建。

1. **`/grill-with-docs`** 通过访谈来磨炼想法。无论何时你**在 working directory 中工作**，都可以从这里开始：它是状态化的，保留它在 `CONTEXT.md` 和 ADRs 中学到的知识。（没有 working directory？使用 `/grill-me` 代替，它属于独立模式。两者都运行相同的 `/grilling` 原语；`grill-with-docs` 是留下纸条的那个，当有仓库可以留下它时，它是两者中更好的那个。）
2. **分支：你能通过对话解决所有问题吗？** 如果一个问题需要一个可运行的答案（状态、业务逻辑、你必须看到的 UI），则通过原型绕行，由 **`/handoff`** 在两个方向上 bridged（原型存在于它自己的目录中，这正是 `/handoff` 的用途；见阶段边界）：
   - **`/handoff`** 输出，然后针对该文件打开一个新会话，
   - **`/prototype`** 用一次性代码回答问题，
   - **`/handoff`** 回传你学到的知识，并从原始想法线程中引用它。
3. **分支：这是一个多会话构建吗？**
   - **是** → **`/to-spec`**（将线程转换为规范），然后 **`/to-tickets`** 将其拆分为跟踪弹射票，每个票都声明其**阻塞边**。在一个本地跟踪器上，每个票在 `.scratch/<feature>/issues/` 下是一个文件；手动按阻塞顺序工作；在一个真实跟踪器上，边成为本地的阻塞链接，因此任何阻塞已完成的票都可以被获取：为每个票启动 **`/implement`**，**`/clear`ing context between each one**。每个票都是自包含的，所以最后一个票的上下文是可丢弃的。
   - **否** → 直接在这里启动 **`/implement`**，在同一个上下文窗口中。

   无论哪种方式，**`/implement`** 通过内部驱动 **`/tdd`**（一次一个 red-green 切片）来构建每个问题，然后通过运行 **`/code-review`** 来关闭，这是一个双轴审查（标准+规范）的 diff，然后才提交。当你只想先构建一个具体的行行为测试而不需要完整的规范时，单独使用 **`/tdd`**，并且当你想审查一个分支或 PR 时，总是使用 **`/code-review`**。

### 上下文卫生

将步骤 1-3 保持在**一个不间断的上下文窗口**中（不要压缩或清除，直到 `/to-tickets` 之后）以便 grilled、规范和票都建立在相同的思考上。然后每个 **`/implement`** 都从票开始，重新开始工作。

这个限制是**[智能区](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍然能够清晰推理的窗口（在最新的模型上约为 150k 个 token）。如果一个会话在 `/to-tickets` 之前接近它，不要在退化的情况下继续；在最近的阶段边界处运行 `/compact` 并继续（见阶段边界）。

## 匝道

一个起始情况，它会生成工作，然后合并到主流程。

- **积压的 Bug 和请求** → **`/triage`**。它将问题通过 triage 角色并产生代理就绪的问题，然后 **`/implement`** 后面会拾取它们。

  Triage 仅用于**你没有创建**的问题：bug 报告、传入的功能请求、任何原始到达的内容。由 `/to-tickets` 产生的票已经准备好供代理使用，所以**不要 triage 它们**。

- **某事出错了** → **`/diagnosing-bugs`**。对于困难的问题：那个抵抗第一眼看的 bug、间歇性出现的 flake、在两个已知良好状态之间悄悄引入的回归。它拒绝理论化，直到它有一个**紧密的反馈循环**（一个已经在 *这个* bug 上变红的命令），然后用回归测试来修复。当真正的发现是没有好的接缝来锁定 bug 时，它的事后分析会交由 **`/improve-codebase-architecture`**。

- **一个巨大的、模糊的努力：一个绿色字段项目或一个太大的功能构建，无法在一个会话中完成** → **`/wayfinder`**，这是这里最需要认知能力的流程。当从这里到目的地的路径还不清楚时，它会绘制一个**共享地图**的**决策票**在问题跟踪器上，并逐个解决它们，产生**决策，而不是交付物**，直到雾气被推回，道路清晰。当 **`/grill-with-docs`** 磨炼一个你可以在一个会话中持有的想法时，wayfinder 是用于你无法持有的想法，它更慢更密集，所以只在确实需要时使用它，绝不用于范围明确的功能。

  当地图清晰时，**它转交，而不是构建**：在 **`/to-spec`** 上合并到主流程，这会将地图的链接决策折叠成一个可构建的计划，然后 `/to-tickets` 和 `/implement` 如常。直接将地图循环到 `/implement` 跳过这个折叠并丢弃链接的细节，所以只有当努力确实很小时才直接到 `/implement`。

## 代码库健康

这不是功能工作，只是维护。

- **`/improve-codebase-architecture`** 每当你有空闲时间时运行，以保持代码库对代理操作良好。它揭示**加深的机会**；选择一个 _生成一个想法_，你可以在主流程的 `/grill-with-docs` 中带入。这是找到候选者的调查；**`/codebase-design`**（下面）是设计选定项的基准。

## 词汇层

两个模型调用的参考，它们在其他的技能下面运行，每个都是其词汇量的唯一来源。当**单词**而不是流程是问题时，直接使用它们；或者让上面的技能将它们拉进来。

- **`/domain-modeling`**：磨炼项目的*领域*语言：挑战一个模糊的术语，解决一个重载的词（“account”做三个工作），将一个难以逆转的决定记录为 ADR。这是 `/grill-with-docs` 驱动的主动学科，以保持 `CONTEXT.md` 是一个干净的词汇表。
- **`/codebase-design`** 是深度模块词汇（模块、接口、深度、接缝、适配器、利用、局部性）用于设计模块的*形状*：在干净的接缝处一个小接口后面有很多行为。`/tdd` 和 `/improve-codebase-architecture` 都使用它。

## 阶段边界

一个**阶段**是一个会话中的一段工作：grilling、实现、QA。在两个阶段之间的**边界**上有五个选项，在它们之间做出选择是这个整个地图中最模糊的决定：

- **继续**：留在原地。不花钱，不损失。
- **`/clear`**：清空窗口，当这里没有什么对下一步重要。
- **`/handoff`** 写一个可移植的 markdown 文件。狭窄：仅用于**新的 harness**、**新的目录**、**同事**，或者在中途分支一个侧任务。它买的是可移植性。
- **子代理**：将一个范围紧密的任务发送到它自己的窗口并返回报告。
- **`/compact`** 压缩这个上下文并在一个新的会话中播种它。**默认值**，在树的底部而不是第一个选择。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 以获取有序树：五个问题、每个分支背后的推理，以及为什么主要来源成本使**继续**成为首先排除的那个。在边界**处**做出决定；中途，继续或把其余部分分成子代理。

## 独立模式

完全脱离主流程。

- **`/grill-me`**：与 `/grill-with-docs` 相同的 relentless 访谈，但**无状态**：它不会在本地保存任何内容，也不会构建 `CONTEXT.md`。当你**不在 working directory 中工作**时使用它（磨炼计划、设计、写作的一部分，任何没有仓库在下面的东西）。如果你在一个 working directory 中，请使用 `/grill-with-docs` 代替：它运行相同的访谈并留下纸条，所以它是严格上更好的那个。
- **`/grilling`** 是访谈原语本身：回合、前沿、事实是代理的工作，决定是你的。`/grill-me` 和 `/grill-with-docs` 是进入的两个命名方式，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要没有包装的访谈时才直接使用它。
- **`/resolving-merge-conflicts`** 通过 hunk by hunk 工作 in-progress merge 或 rebase 冲突，通过指向每一边的主要来源的意图来解析，而不是通过选择行，然后完成操作。它从不运行 `--abort`。独立模式，脱离每个流程：当你在中途冲突时使用它。
