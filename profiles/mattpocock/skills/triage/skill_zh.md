# 分诊

通过一组分诊角色组成的小型状态机，将项目问题追踪器中的议题进行流转。

如果本仓库将外部拉取请求视为请求面（参见问题追踪器配置），则分诊也涵盖它们：**PR 是带有附加代码的议题**，使用相同的角色、状态和状态机，下面标注了少数针对 PR 的改动。请根据追踪器配置将单纯的 `#42` 解析为议题或 PR。

分诊期间发布到问题追踪器的每条评论或议题 **必须** 以以下免责声明开头：

```
>A *本分诊期间由 AI 生成。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写持久的代理简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的工作方式

## 角色

两个 **类别** 角色：

- `bug`：存在问题
- `enhancement`：新功能或改进

五个 **状态** 角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：已完全明确，可供 AFK 代理处理
- `ready-for-human`：需要人工实现
- `wontfix`：不予处理

对于 PR，相同的状态是相对于附加代码来理解的：`ready-for-agent` 表示已附上简报，代理应针对该差异进行下一步操作；`ready-for-human` 表示已准备好由人工合并。

每个分诊过的议题应恰好包含一个类别角色和一个状态角色。如果状态角色冲突，请标记并询问维护者，再进行任何其他操作。

这些是规范的角色名称。问题追踪器中实际使用的标签字符串可能不同。映射关系应已提供给您。如果未提供，请告知用户运行 `/setup-matt-pocock-skills`。

状态转换：未标记的议题通常首先进入 `needs-triage`；之后可流转至 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告者回复后返回 `needs-triage`。维护者可随时进行覆盖；标记看似异常的转换并事先询问后再继续操作。

## 调用方式

维护者调用 `/triage` 并以自然语言描述其需求。解读请求并执行操作。示例：

- "显示任何需要我注意的事项"
- "让我们查看 #42"（议题或 PR）
- "将 #42 移至 ready-for-agent"
- "有哪些事项可供代理接手？"

## 显示需要关注的事项

查询问题追踪器，并按最旧优先顺序呈现三个分组：

1. **未标记 (Unlabeled)**：从未分诊过。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次分诊备注以来有报告者活动**：需要重新评估。

当 PR 处于范围内时，将这些分组包含外部 PR，并为每行添加 `[PR]` 或 `[issue]` 标签。发现机制仅展示 *外部* PR（追踪器配置定义了何为外部），因此协作者在途中的 PR 不属于分诊工作。此过滤仅用于发现；无论作者是谁，明确指定的 PR 始终会被分诊。

展示数量以及每项的一行摘要，由维护者自行选择。

## 对特定议题或 PR 进行分诊

1. **收集上下文。** 阅读完整的议题或 PR（正文、评论、标签、作者、日期；对于 PR，还需读取差异）。解析任何先前的分诊备注，以免重复询问已解答的问题。使用项目的领域术语表探索代码库，并尊重该领域的 ADR。对代码库进行两项检查：(a) **冗余性**：通过领域概念（而非仅请求的表述）搜索是否存在请求行为的现有实现，并报告搜索位置。如果找到，则属于已实现的 `wontfix`（第 5 步）。(b) **先前拒绝**：阅读 `.out-of-scope/*.md`，并找出任何与此请求相似的内容。

2. **建议 (Recommend)。** 向维护者说明您对类别和状态的建议及理由，并附上与请求相关的简要代码库摘要（包括是否已实现）。等待指示。

3. **核实主张 (Verify the claim)。** 在进一步询问之前，检查该主张是否成立。对于 bug，根据报告者的步骤进行复现。对于 PR，确认差异是否实现了其声称的功能：执行检出，运行相关的测试或命令。报告结果：已确认（并附带代码路径）、未通过，或信息不足（强烈的 `needs-info` 信号）。确认的验证会使代理简报强得多。

4. **审查 (Grill, if needed)。** 如果请求需要进一步明确，调用 Skill 工具两次，分别用于“审查”和“领域建模”，分轮次的提问，使请求成型，并在决策落地时内联更新 `CONTEXT.md`/ADRs。

5. **应用结果 (Apply the outcome)：**
   - `ready-for-agent`：发布代理简报评论 ([AGENT-BRIEF.md](AGENT-BRIEF.md))。
   - `ready-for-human`：与代理简报相同的结构，但需注明为何无法委派（判断性决策、外部访问、设计决策、手动测试）。
   - `needs-info`：发布分诊备注（下方为模板）。
   - 对于 `wontfix`，关闭议题，评论取决于 *原因*：
     - **已实现**：代码库中已存在该变更。指向其所在位置；**不要**写入 `.out-of-scope/`（该知识库用于 *已拒绝* 的请求，而非已构建的内容）。
     - **拒绝（bug）**：礼貌地解释后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接至其位置，然后关闭 ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md))。
   - `needs-triage`：应用该角色。如有部分进展，可添加可选评论。

## 快速状态覆盖

如果维护者表示“将 #42 移至 ready-for-agent”，信任其操作并直接应用该角色。确认即将执行的操作（角色变更、评论、关闭），然后执行。跳过审查。若在没有审查会话的情况下移至 `ready-for-agent`，请询问他们是否需要编写代理简报。

## needs-info 模板

```markdown
## 分诊备注

**目前已确立的内容：**

- 要点 1
- 要点 2

**仍需要您 (@reporter) 提供的信息：**

- 问题 1
- 问题 2
```

在“目前已确立的内容”下记录审查过程中解决的所有事项，以免工作丢失。问题必须具体且可执行，不能是“请提供更多信息”。

## 恢复之前的会话

如果在议题或 PR 上存在先前的分诊备注，请阅读它们，检查报告者是否已解答任何未决问题，并在继续之前呈现更新后的情况。不要重复询问已解答的问题。
