# 筛选

将项目问题追踪器上的问题通过一个小型状态机进行筛选角色处理。

如果这个仓库将外部拉取请求视为请求表面（参见问题追踪器配置），筛选也包括它们：**一个PR是一个附带代码的问题**，使用相同的角色、相同的状态和相同的状态机，下面标记一些“针对PR”的变更。根据追踪器配置解析裸的`#42`到一个问题或PR。

在筛选期间发布到问题追踪器的每个评论或问题**必须**以这个免责声明开头：

```
> *这是在筛选期间由AI生成的。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写持久的代理摘要
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/`知识库的工作方式

## 角色

两个**类别**角色：

- `bug`：某物已损坏
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：完全指定，准备好由离线代理处理
- `ready-for-human`：需要人工实现
- `wontfix`：不会处理

对于PR，相同的状态针对附加的代码：`ready-for-agent`意味着已附加摘要，代理应在diff上采取下一步行动；`ready-for-human`意味着它已准备好供人类合并。

每个筛选的问题应该正好携带一个类别角色和一个状态角色。如果状态角色冲突，先标记它并询问维护者，然后再做任何其他事情。

这些都是规范的角色名称。问题追踪器中实际使用的标签字符串可能不同。映射应该已经提供给过你。如果没有，告诉用户运行`/setup-matt-pocock-skills`。

状态转换：未标记的问题通常首先进入`needs-triage`；从那里它将移动到`needs-info`、`ready-for-agent`、`ready-for-human`或`wontfix`。`needs-info`在报告者回复后返回`needs-triage`。维护者可以随时覆盖；标记看起来不寻常的转换并在继续之前询问。

## 调用

维护者调用`/triage`并使用自然语言描述他们想要的内容。解释请求并采取行动。示例：

- "显示需要我注意的任何内容"
- "让我们看看#42"（问题或PR）
- "将#42移动到ready-for-agent"
- "什么已准备好供代理拾取？"

## 显示需要关注的内容

查询问题追踪器并按最旧的顺序呈现三个桶：

1. **未标记**：从未筛选过。
2. **`needs-triage`**：评估正在进行中。
3. **`needs-info`带有报告者自上次筛选以来的活动**：需要重新评估。

当PR在范围内时，包括外部PR在这些桶中，并标记每一行`[PR]`或`[issue]`。发现表面仅*外部*PR（追踪器配置定义了谁被视为外部），因此协作者的进行中的PR不是筛选工作。此过滤器仅用于发现；显式命名的PR始终会被筛选，无论作者是谁。

显示计数并为每个项目显示一行摘要。让维护者选择。

## 筛选特定的问题或PR

1. **收集上下文**。阅读完整的问题或PR（正文、评论、标签、作者、日期；对于PR，还包括diff）。解析任何先前的筛选笔记，以便不要重新询问已解决的问题。使用项目的领域词汇表探索代码库，尊重该区域的ADR。对代码库运行两个检查：(a) **冗余**：通过领域概念搜索现有请求行为的实现（而不仅仅是请求的措辞），并报告你搜索过的地方。如果找到，它是一个已实现的`wontfix`（步骤5）。(b) **先前的拒绝**：阅读`.out-of-scope/*.md`并展示任何与该请求相似的。

2. **建议**。告诉维护者你的类别和状态建议及理由，并提供与请求相关的代码库摘要（包括是否已实现）。等待指示。

3. **验证声明**。在进行任何质询之前，检查声明是否成立。对于bug，根据报告者的步骤进行重现。对于PR，确认diff是否做了它声称的事情：检出它，运行相关的测试或命令。报告发生了什么：确认（带代码路径）、失败或细节不足（一个强烈的`needs-info`信号）。确认的验证会生成一个更强的代理摘要。

4. **质询（如果需要）**。如果请求需要充实，调用技能工具两次，用于“质询”和“领域建模”，并一次一轮问题将问题质询成型，磨利领域术语并随着决策落地而直接更新`CONTEXT.md`/ADRs。

5. **应用结果**：
   - `ready-for-agent`：发布一个代理摘要评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：与代理摘要结构相同，但注明为什么不能委托（判断调用、外部访问、设计决策、手动测试）。
   - `needs-info`：发布筛选笔记（模板如下）。
   - 对于`wontfix`，关闭问题，评论取决于*为什么*：
     - **已实现**：更改已存在于代码库中。指向它所在的位置；**不要**写入`.out-of-scope/`（该KB用于*拒绝*的请求，而不是构建的）。
     - **拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **拒绝（enhancement）**：写入`.out-of-scope/`，从评论中链接到它（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)），然后关闭。
   - `needs-triage`：应用角色。如果有部分进展，可选评论。

## 快速状态覆盖

如果维护者说“将#42移动到ready-for-agent”，信任他们并直接应用角色。确认你将要做什么（角色更改、评论、关闭），然后行动。跳过质询。如果在没有质询会话的情况下移动到`ready-for-agent`，询问他们是否想要编写代理摘要。

## needs-info模板

```markdown
## 筛选笔记

**到目前为止我们已确定的：**

- 点1
- 点2

**我们从您 (@reporter) 还需要的：**

- 问题1
- 问题2
```

在质询期间捕获所有已解决的问题，放在“已确定”下，以免工作丢失。问题必须具体且可操作，而不是“请提供更多信息”。

## 恢复之前的会话

如果问题或PR上存在先前的筛选笔记，读取它们，检查报告者是否已回答任何悬而未决的问题，并在继续之前呈现更新后的情况。不要重新询问已解决的问题。
