# 规范实现

系统性地执行已批准的规范提案，通过按顺序执行任务、进行适当的测试和验证。

## 快速入门

实现遵循每个任务的读取→执行→测试→验证周期：
1. 读取完整提案和任务列表
2. 按顺序逐个执行任务
3. 测试每个已完成的任务
4. 仅在验证通过后标记完成

**关键规则**：使用 TodoWrite 跟踪进度。切勿跳过任务或将未完成的工作标记为已完成。

## 工作流程

复制此清单并跟踪进度：

```
实现进度：
- [ ] 第 1 步：加载和理解提案
- [ ] 第 2 步：设置 TodoWrite 任务跟踪
- [ ] 第 3 步：按顺序执行任务
- [ ] 第 4 步：测试和验证每个任务
- [ ] 第 5 步：更新活规范（如适用）
- [ ] 第 6 步：标记提案为已实现完成
```

### 第 1 步：加载和理解提案

开始之前，阅读所有背景信息：

```bash
# 读取提案
cat spec/changes/{change-id}/proposal.md

# 读取所有任务
cat spec/changes/{change-id}/tasks.md

# 读取规范差异以理解需求
find spec/changes/{change-id}/specs -name "*.md" -exec cat {} \;
```

**理解**：
- 为什么需要这个变更（来自 proposal.md）
- 预期结果是什么
- 哪些规范将受影响
- 接受标准是什么（来自场景）

### 第 2 步：设置 TodoWrite 任务跟踪

在开始工作前，将 tasks.md 中的任务加载到 TodoWrite：

```markdown
**模式**：
读取 tasks.md → 提取编号列表 → 创建 TodoWrite 条目

**示例**：
如果 tasks.md 包含：
1. 创建数据库迁移
2. 实现 API 端点
3. 添加测试
4. 更新文档

则创建 TodoWrite 为：
- content: "创建数据库迁移", status: "in_progress"
- content: "实现 API 端点", status: "pending"
- content: "添加测试", status: "pending"
- content: "更新文档", status: "pending"
```

**为什么这很重要**：TodoWrite 为用户提供进度可见性，并确保不会遗漏任何任务。

### 第 3 步：按顺序执行任务

按顺序逐个处理任务：

```markdown
对于每个任务：
1. 在 TodoWrite 中标记为 "in_progress"
2. 执行工作
3. 测试工作
4. 仅在验证通过后标记 "completed"

绝对不要跳过或在不测试的情况下批量处理多个任务。
```

**任务执行模式**：

```markdown
## 任务：{任务描述}

**内容**：[简要解释这个任务做什么]

**实现**：
[代码更改、文件编辑、运行的命令]

**验证**：
[如何验证这个任务已完成]
- [ ] 代码编译/运行
- [ ] 测试通过
- [ ] 满足需求场景

**状态**：✓ 完成 / ✗ 阻塞 / ⚠ 部分完成
```

### 第 4 步：测试和验证每个任务

完成每个任务后，验证其是否正常工作：

**对于代码任务**：
```bash
# 运行相关测试
npm test # 或 pytest, cargo test, 等。

# 运行代码检查器
npm run lint

# 检查类型（如适用）
npm run type-check
```

**对于数据库任务**：
```bash
# 验证迁移运行
npm run db:migrate

# 检查模式是否匹配预期
npm run db:schema
```

**对于 API 任务**：
```bash
# 手动测试端点
curl -X POST http://localhost:3000/api/endpoint \
  -H "Content-Type: application/json" \
  -d '{"test": "data"}'

# 或运行集成测试
npm run test:integration
```

**仅当所有验证通过后，才标记任务完成**。

### 第 5 步：更新活规范（如适用）

在实现过程中，如果发现规范差异需要更新：

1. **在 proposal.md 或笔记文件中记录发现**
2. **在实现过程中，切勿修改规范差异**
3. **实现完成后，考虑是否需要调整规范**

**注意**：规范差异在归档（第 6 步）时合并，而不是在实现过程中。

### 第 6 步：标记提案为已实现完成

所有任务完成后：

```bash
# 创建完成标记
echo "实现完成：$(date)" > spec/changes/{change-id}/IMPLEMENTED
```

**通知用户**：
```markdown
## 实现完成

**变更**：{change-id}
**已完成任务**：{数量}
**测试**：全部通过

**下一步**：归档此变更以将规范差异合并到活文档中。
准备好时，说 "openspec archive {change-id}" 或 "归档此变更"。
```

## 最佳实践

### 模式 1：阻塞任务

如果任务无法完成：

```markdown
**标记为阻塞**：
- 保持状态为 "in_progress"（不是 "completed"）
- 清晰地记录阻塞原因
- 创建新任务以解决阻塞
- 立即通知用户

**示例**：
任务： "实现支付处理"
阻塞： "缺少支付网关 API 凭证"
操作： 创建新任务 "获取支付网关凭证"
```

### 模式 2：任务依赖

如果任务有依赖关系，在开始前验证先决条件：

```bash
# 示例：数据库迁移必须在 API 代码之前运行
# 检查迁移状态
npm run db:status

# 仅在迁移成功后继续 API 任务
```

### 模式 3：增量测试

逐步测试，而不是在最后：

**良好**：
```
任务 1：创建模型 → 测试模型 → 标记完成
任务 2：创建 API → 测试 API → 标记完成
任务 3：添加验证 → 测试验证 → 标记完成
```

**不良**：
```
任务 1, 2, 3 → 实现所有 → 测试所有 → 调试失败
```

### 模式 4：活文档

**边进行边**更新 README、API 文档和注释：

```markdown
添加新 API 端点时，同时：
- 更新 API 文档
- 添加示例请求/响应
- 更新 OpenAPI/Swagger 规范
- 添加行内代码注释
```

## 高级主题

**并行工作**：如果任务真正独立（例如，分离的模块），可以并行处理，但每个任务必须独立测试。

**集成点**：当存在任务依赖关系时，使用集成测试验证连接是否正常。

**回滚策略**：对于有风险的变化，在部署前创建回滚任务。

## 常见模式

### 模式 1：数据库 + API + UI

典型顺序：
1. 数据库模式/迁移
2. 数据访问层（模型）
3. 业务逻辑层（服务）
4. API 端点（控制器）
5. UI 集成
6. 端到端测试

### 模式 2：特性标志

用于渐进式发布：
1. 在标志后实现特性
2. 标志启用时测试
3. 标志禁用时部署
4. 逐步启用标志
5. 全部发布后移除标志

### 模式 3：破坏性变更

对于 API 破坏性变更：
1. 实现新版本（v2）
2. 保持旧版本（v1）运行
3. 向 v1 添加弃用警告
4. 将用户迁移到 v2
5. 移除 v1（单独的任务/提案）

## 应避免的反模式

**不要**：
- 跳过单个任务的测试
- 在验证前标记任务完成
- 忽略失败的测试（"稍后修复"）
- 在测试前批量处理多个任务
- 在实现过程中修改活规范
- 无序工作（依赖关系会中断）

**要**：
- 立即测试每个任务
- 在继续前修复失败的测试
- 实时更新 TodoWrite
- 清晰记录阻塞原因
- 向用户通报进度
- 保持提交原子化和描述性

## 故障排除

### 问题：任务完成后测试失败

**解决方案**：
```markdown
1. 不要标记任务完成
2. 调试失败
3. 修复代码
4. 重新运行测试
5. 仅在通过后标记完成
```

### 问题：任务太大

**解决方案**：
```markdown
1. 分解为子任务
2. 更新 TodoWrite 为子任务
3. 顺序完成子任务
4. 所有子任务完成后标记父任务完成
```

### 问题：依赖未满足

**解决方案**：
```markdown
1. 暂停当前任务
2. 先完成依赖
3. 测试依赖
4. 继续原始任务
```
