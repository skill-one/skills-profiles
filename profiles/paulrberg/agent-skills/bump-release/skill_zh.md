# 版本更新发布

如果这些说明已经在通过斜杠或美元符调用时存在于对话中，请直接遵循它们；
不要通过技能工具再次调用此技能。

发布一个包或多个版本更新包，包括版本号变更、变更日志条目、提交记录和标签。支持
单包仓库、工作区单一代码库、稳定版本发布、测试版本发布和模拟运行。

## 参数

- `packages`: 可选的包名或目录。在单包仓库中可省略。
- `version`: 可选的显式 semver 版本。仅适用于用户选择的单个包。
- `--beta`: 创建或推进 `-beta.X` 预发布版本。
- `--dry-run`: 预览而不修改文件、提交或添加标签。

## 辅助接口

从本 `SKILL.md` 中解析 `<skill-dir>`。将辅助标准输出作为 JSON，并将诊断信息输出到标准错误。

```sh
node "<skill-dir>/scripts/plan-release.mjs" \
  [--cwd <repo>] [--beta] [--dry-run] [--version <semver>] \
  [--package <name-or-dir>]...
```

只读的发现输出具有 `schemaVersion: 2`。它报告包标识、完整的每个包的 `changedFiles`、工作区依赖关系和声明的范围、先前的标签事实、选定的目标和工作树状态。`changeHints` 基于文件名，是明确的非权威导航提示。永远不要使用它们来决定发布的相关性或变更日志的包含。

在代理决定每个稳定补丁/次要/主要版本后，将发现 JSON 写入临时文件并运行：

```sh
uv run "<skill-dir>/scripts/finalize-release-plan.py" \
  --discovery <discovery.json> \
  [--version <package>=<semver>]...
```

最终化器执行预发布和显式版本转换、稳定预发布版本提升、npm 范围满足、简单的依赖范围建议和依赖排序。它报告复杂范围、同伴范围、依赖循环以及代理未提供的稳定版本为未解决的决策。当不满足的依赖关系添加了依赖项时，选择该包的发布版本并使用另一个 `--version` 赋值重新运行。最终化器永远不会选择常规发布幅度或依赖策略。

对于每个写入的稳定变更日志，验证其确定性结构：

```sh
uv run "<skill-dir>/scripts/validate-changelog.py" \
  --file <CHANGELOG.md> --version <semver> --date <YYYY-MM-DD> [--tag <tag>]
```

这检查预期的发布和日期、标题/类别顺序、允许的类别、列表结构和发布链接标签。它不判断重要性、措辞或语义类别。

## 工作流程

1. 使用用户参数直接运行发现。退出 `2` 表示目标不是可发布的 Git/包仓库；退出 `64` 表示输入无效。任一情况都停止。
2. 需要 `workingTree.clean`。不要吸收无关的工作。
3. 解析未知或模糊的包选择。显式的用户版本保持单包限制。
4. 检查每个目标的完整 `changedFiles` 和与其先前标签的净差异。决定是否值得发布这些存活的变更。运行时环境、重构、文档、测试和工具都可以在上下文中相关；文件名永远不会决定这一点。
5. 对于每个没有显式版本的稳定相关目标，从面向消费者的变更中选择补丁、次要或主要版本。对于测试版本发布，让最终化器计算机械转换。
6. 运行最终化器。检查未满足的工作区依赖关系。仅当该策略适用时才接受其建议；明确选择同伴和复杂范围策略。添加依赖项及其代理选择的发布版本，然后重新运行，直到包集和依赖顺序解决。
7. 对于模拟运行，报告排序的包/版本计划、范围编辑、变更日志/标签/提交操作以及代理决定的跳过。在写入之前停止。
8. 对于稳定版本发布，读取 `references/common-changelog.md` 并从有界的净差异中写入面向消费者的条目。代理拥有条目选择、措辞、重要性和类别。测试版本发布不会更新变更日志。
9. 更新清单和接受的依赖范围。使用辅助工具验证每个稳定变更日志。
10. 使用仓库最窄的已建立命令进行一次格式化。
11. 在依赖项之前提交和标记依赖项。每个包使用一个提交和一个带注释的标签：
    - 单包提交：`docs: 发布 <version>`;
    - 单一代码库提交：`docs: 发布 <package> <version>`;
    - 单包标签：遵循观察到的 `v<version>` 或裸 semver 事实；
    - 单一代码库标签：遵循观察到的包标签事实，默认为 `<package-dir>@<version>`。
12. 不要推送。成功后，建议一个精确的 `git push origin <tag>...` 命令，其中仅包含此执行创建的标签；不要使用 `--tags`。
13. 在最终报告之前，检查 `.github/workflows/` 以查找创建或发布 GitHub 发布的活跃工作流。文件名如 `release.yml` 是提示而非证明。使用 `$cli-gh` 只读方式检查仓库是否具有维护 GitHub 发布的已建立历史。如果它有，根据这些规则，在用户批准的情况下，为每个新标签提供创建 GitHub 发布的提议：
    - 一个标签和发布 CI 存在：不要提供手动发布创建；标签推送应触发 CI。
    - 一个标签但没有发布 CI 存在：提供使用 `$cli-gh` 创建发布。
    - 将一起推送多个标签：即使存在发布 CI，也提供使用 `$cli-gh` 为每个标签创建一个发布，因为多标签推送不太可能可靠地触发该自动化。

    永远不要在未经用户批准的情况下创建 GitHub 发布。如果发布历史无法验证，报告为未知，并且不要提供写入。

## 安全性和完成

辅助工具失败表示输入格式错误、违反不变量或验证失败；代理未解决的决策是 JSON 中的数据，而不是辅助工具失败。发现和模拟运行是只读的。在最终稳定的包集确定之前，不要写入变更日志，并且在发现报告观察到的事实时不要推断标签约定。

模拟运行完成需要一个基于发现的、代理审查的行动预览，且零写入。发布完成需要验证的清单和稳定变更日志、格式化、每个包在依赖顺序中的一个提交和带注释的标签，以及创建的提交/标签报告、代理决定的跳过、确切的标签推送命令和任何适用的 GitHub 发布提议。

使用 `### ⛔ 发布停止 — 工作树不干净`、`### ⚠️ 确认发布计划`、`### 🔎 发布预览 — 未写入文件、提交或标签` 或 `### 🏁 发布完成` 作为适用情况。保持辅助工具 JSON、版本、哈希值、标签、命令和变更日志文本精确且无装饰。
