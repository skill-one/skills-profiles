# 效果 3

从项目本地架构应用效果 3 语义，最窄的相关引用，以及与目标已安装包匹配的源。

## 工作流

不要仅仅因为文件导入 `effect` 就激活此工作流。对于非平凡的效果工作：

1.  解析目标包或工作区及其确切的已安装 `effect` 和相关 `@effect/*` 版本。如果 `effect` 不是 3.x 版本，则停止，因为此技能不适用。
2.  检查相邻服务、层、错误、模式、运行时边界和测试。本地约定决定组织方式；已安装包证据决定 API 事实。
3.  阅读 `references/critical-rules.md`，然后只阅读以下特定于任务的引用。
4.  在编辑之前，对照目标工作区可见的包安装情况，验证每个不确定的导入、签名或行为。
5.  实现与项目和更改的语义一致的 最小模式，并运行覆盖更改语义的最窄测试或类型检查。

## 证据顺序

使用目标工作区的清单文件和锁文件来识别版本。按顺序优先使用：

1.  已安装包的 `src/`、README、测试和变更日志；
2.  当源代码未分发时，其发出的声明；
3.  匹配的官方包工件或源标签。

不要为了获取文档而安装或更新依赖项。不要信任不相关的检出或与目标已安装版本不匹配的源分支。如果无法验证确切行为，则停止猜测，而不是猜测。

## 边界

- 除非效果边界提供具体依赖项、可测试性、资源安全性或错误模型的好处，否则保持纯辅助函数、常量和路径操作为纯函数。
- 除非用户请求重新设计，否则保留现有的领域 facade 和服务/运行时边界。
- 在 IO 边界处优先使用带类型的失败和作用域资源；仅在编码或边界验证需要时才选择 Schema 支持的错误/模型。
- 不要为了替换小的平台调用而放宽环境要求。

对于更改，完成需要与本地效果架构一致的代码、在需要时选择的引用和已安装源，以及覆盖更改语义的最窄测试/类型检查。只读工作需要报告结论的证据。在验证的编辑后以 `### ⚡ 效果 — ✅ 更改完成` 结束，对于只读工作以 `### ⚡ 效果 — 🔎 已审查，未写入文件` 结束，一句话命名使用的边界或模式，并添加 `### 🧪 验证` 带有确切的范围命令/结果。如果需要验证不完整，则使用 `### ⚡ 效果 — ⛔ 阻止`。仅用于非阻塞的注意事项时添加 `### ⚠️ 限制`。永远不要装饰带类型的错误、Schema 消息、日志、测试、生成的 JSON/API 响应或命令输出。
