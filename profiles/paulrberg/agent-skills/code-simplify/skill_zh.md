# 代码简化

## 目标

在保持行为、公共契约和副作用的同时简化代码。默认执行完整的简化流程：应用高置信度的简化，这些简化能显著提升可理解性或降低缺陷风险，包括在安全的情况下进行命名/意图清理。

## 参数

- 路径、模式、提交/范围或范围短语：用于范围解析步骤 2。
- `--no-report`：跳过完整面向用户报告，并返回简短的调用者工作笔记。
- `--no-verify`：跳过验证，因为父级协调器将单独验证最终结果。
- 默认：执行完整简化流程，验证受影响的行为，并呈现完整报告。

## 范围解析

一次性解析范围，然后在运行其余部分时将结果视为固定。

1. 验证仓库上下文：`git rev-parse --git-dir`。如果失败，停止并告知用户从 git 仓库运行。
2. 如果请求命名目标——文件路径/模式、提交/范围、自然语言子集（例如 "解析器更改"），或包含每行一个仓库相对路径的 `resolved-scope` 围栏块——范围就是这些目标。在继续之前将自然语言子集映射到具体路径。
3. 否则，范围**仅**为会话修改文件：在此会话中创建或编辑的文件。不包括其他未提交的更改。
4. 如果没有会话修改文件，或早期的对话历史记录在此上下文中不可见，则回退到所有未提交文件，每个命令运行一次：
   - 跟踪：`git diff --name-only --diff-filter=ACMR`
   - 未跟踪：`git ls-files --others --exclude-standard`
   - 合并两个列表并去重。
5. 除非明确请求，否则从手动简化中排除生成文件、托管的文件、批量文件和低信号文件：锁文件、压缩的包、构建输出、生成输出、托管代码和大型数据快照。当排除文件与正确性相关时，发出可选的标记为 `excluded-scope` 的围栏代码块，每行一个仓库相对路径或通配符，并通过验证或不变量检查覆盖它们。
6. 如果范围解析为零文件，报告并停止。
7. 将范围作为标记为 `resolved-scope` 的围栏代码块发出，每行一个仓库相对路径。该块是权威的：不要重新运行范围命令或事后重新审视排除项。

## 操作规则

- 在编辑前声明假设。如果有多个解释会改变简化或验证策略，请呈现它们并停止等待指示。
- 精确保留运行时行为。保持输入、输出、副作用和错误行为稳定。
- 优先考虑项目约定而非个人偏好。从现有代码、代码检查工具、格式化工具和测试中推断约定。
- 进行小而可逆的编辑。每行更改都应该追溯到用户的请求、请求的清理或您自己编辑引起的清理。
- 编写解决请求问题的最小代码。不要添加用户未请求的功能、一次性抽象、推测性灵活性或可配置性。
- 仅清理您自己的混乱：删除您的更改使不再使用的导入、变量、函数和文件；在残余风险中提及现有死代码，而不是删除它。
- 仅在它们能带来具体的清晰度或安全性收益且可以安全验证时，才运行仅命名的重构。
- 对于生成文件、托管文件、批量文件或低信号文件，在可能的情况下简化生成器、模式或契约，并通过不变量检查验证输出，而不是手动编辑每个生成的行或文件。
- 当行为可能改变时，立即指出不确定性。

## 工作流程

### 1) 确定范围

- 应用范围解析部分。
- 将任何 `excluded-scope` 块视为手动简化之外但验证计划之内。

### 2) 构建行为基线

- 读取周围上下文，而不仅仅是更改的行。
- 确定必须保持不变的不变量：
  - 函数签名和导出的 API
  - 状态转换和副作用
  - 持久化/网络行为
  - 外部依赖的用户界面消息和错误语义
- 记录可用的验证命令（代码检查工具、测试、类型检查）。
- 在编辑前定义成功标准。对于多步骤工作，声明一个简短计划，其中每一步都命名其验证检查。

### 3) 筛选简化机会

- 默认不编辑，除非简化是高置信度且能显著提升可理解性、移除当前更改的清理或降低缺陷风险。
- 优先考虑局部、保持行为的编辑而非广泛的重写。
- 跳过无操作流程。如果作用域内的代码已经足够清晰，报告这一点，而不是浪费时间。
- 仅在存在具体的清晰度或安全性收益且存在安全验证路径时，才重命名标识符或拆分辅助函数。永远不要为了口味而改变 API 的形状。

### 4) 应用简化流程

按顺序应用完整清单：

1. 控制流：
   - 使用守卫子句和提前返回展平深层嵌套。
   - 用更清晰的条件语句替换嵌套的三元运算符。
2. 命名和意图：
   - 当局部上下文支持安全重命名时，重命名模糊的标识符。
   - 将混合关注点分离成具有意图揭示名称的小辅助函数。
3. 重复：
   - 删除明显的重复。
   - 仅当至少两个真实调用位置受益且抽象减少认知负担时才抽象。
4. 数据塑形：
   - 当可读性提高时，将密集的转换链分解为命名的中间步骤。
   - 除非明确且测量到改进，否则保持热路径性能特征稳定。
5. 类型和契约清晰度：
   - 当类型注解提升可读性和安全性而不强制广泛变更时，添加或收紧类型注解。
   - 除非要求更改它们，否则保留外部接口。

### 5) 强制安全约束

- 除非明确请求，否则不要将同步 API 转换为异步（或反向）。
- 除非行为保持等效且已验证，否则不要更改错误传播策略。
- 不要删除编码操作意图的日志记录、遥测、守卫或重试。
- 不要将特定领域的步骤合并为隐藏意图的通用辅助函数。

### 6) 验证

当设置了 `--no-verify` 时跳过。否则按照验证部分下方进行验证。

### 7) 报告

生成下方报告部分。

## 简化启发式规则

- 优先考虑显式的局部变量，而不是嵌套的行内表达式，当它减少认知负担时。
- 优先考虑每个条件的一个清晰分支，而不是紧凑但模糊的条件树。
- 保持函数长度可控，但不要为了行数而拆分。
- 保留解释意图、不变量或非明显约束的注释。
- 删除重述明显代码行为的注释。
- 优化下一维护者的理解时间，而不是最小字符数。

## 反模式

- 不要执行推测性架构重写。
- 不要在简化小局部更改时引入框架级模式。
- 不要用不透明的工具层替换可理解的重复。
- 不要将不相关的清理捆绑到一个补丁中。
- 不要为不可能的场景添加错误处理。
- 不要为了自身而保留代码量；如果存在更简单的等效方法，使用它或解释为什么它不满足请求。

## 验证

运行验证受影响行为的窄检查：

- 受影响文件的格式化/代码检查工具
- 受影响模块的针对性测试
- 相关时的类型检查
- 任何相关 `excluded-scope` 输出的不变量检查

仅在风险值得时运行更广泛的检查，尤其是在简化触及共享契约时。命名每个跳过的检查及其原因。

## 报告

当设置了 `--no-report` 时跳过；返回简短的工作笔记：受影响范围、关键简化、残余风险。

使用这些部分标题，按此顺序。省略不应用的章节——不要编号，不要留空或留占位符。

### 范围

更改的文件和区域，以及任何 `excluded-scope` 条目及其使用的验证策略。

### 简化

每个有意义的更改一个句子，专注于可读性或可维护性的收益。明确确认行为保留假设。

### 验证

运行的命令和结果，包括跳过的检查。

### 残余风险

每行一个风险：`假设 <假设>; 如果错误，<什么会中断>; 通过 <命令或检查> 验证。` 简明语言——扩展或解释特定领域的术语。包括需要用户决策的问题，直接提问。当没有时，写 `None.`。

## 停止条件

在以下情况下停止并请求指示：

- 简化需要更改公共 API/契约。
- 要求不明确或竞争解释会产生显著不同的编辑。
- 行为一致性无法自信验证。
- 代码因领域约束而故意复杂。
- 请求的范围暗示更大的重构而非简化。
