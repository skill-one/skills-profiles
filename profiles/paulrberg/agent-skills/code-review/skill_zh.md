# 代码审查

## 目标

在变更代码中找出有证据支持的、高影响力的缺陷。优先考虑正确性、安全性、数据完整性、shell/配置安全性和回归问题，而非样式问题。

## 参数

- 路径、模式、提交/范围或范围短语：用于范围解析步骤 2。
- `--fix`：内部构建发现结果，按严重性顺序应用建议的修复，然后生成一份最终报告并按照验证部分进行验证。不要输出单独的预修复报告。
- `--with-profile <name>`：强制使用可选的域配置文件，通过名称或文件名（例如 `--with-profile shell`）。可重复。
- `--skip-profile <name>`：跳过可选的域配置文件，通过名称或文件名（例如 `--skip-profile naming`）。可重复。如果 `--with-profile` 和 `--skip-profile` 都指定了相同的配置文件，则跳过优先。
- 默认：报告发现结果并在编辑前等待确认。

## 范围解析

一次性解析范围，然后将结果作为运行其余部分的固定值。

1. 验证仓库上下文：`git rev-parse --git-dir`。如果失败，停止并提示用户从 git 仓库运行。
2. 如果请求命名目标——文件路径/模式、提交/范围、自然语言子集（例如 "解析器变更"），或包含每行一个仓库相对路径的 `resolved-scope` 围栏块——范围就是这些目标。在继续之前将自然语言子集映射到具体路径。
3. 否则，范围仅限于会话修改的文件：在此会话中之前创建或编辑的文件。不包括其他未提交的变更。
4. 如果没有会话修改的文件，或早期的对话历史记录在此上下文中不可见，则回退到所有未提交的文件，每个命令运行一次：
   - 跟踪的：`git diff --name-only --diff-filter=ACMR`
   - 未跟踪的：`git ls-files --others --exclude-standard`
   - 合并两个列表并去重。
5. 除非明确请求，否则从手动审查中排除生成文件、托管的代码、批量文件和低信号文件：锁文件、压缩的包、构建输出、生成输出、托管的代码和大型数据快照。当排除的文件与正确性相关时，输出一个可选的标记为 `excluded-scope` 的围栏代码块，每行一个仓库相对路径或通配符，并通过验证或不变量检查覆盖它们。
6. 如果范围解析为零个文件，报告并停止。
7. 将范围作为标记为 `resolved-scope` 的围栏代码块输出，每行一个仓库相对路径。该块是权威的：不要重新运行范围命令或之后重新考虑排除项。

## 工作流程

### 1) 解析范围

- 应用范围解析部分，然后读取差异以及最小的周边上下文。
- 将任何 `excluded-scope` 块视为手动审查之外但验证计划之内。

### 2) 应用检查

- 根据变更的行为和触及的风险表面对文件进行分类。
- 应用核心检查以及匹配的配置文件（根据配置文件分发），尊重 `--with-profile` 和 `--skip-profile`。
- 对于生成文件、托管的代码、批量文件或低信号文件，审查生成器、模式、契约或约束它们的不变量，而不是手动审查每个生成的行或文件。

### 3) 构建发现结果

- 生成带有位置、影响、证据、置信度和具体修复的发现结果。
- 使用严重性模型分配严重性。

### 4) 修复或等待

- 默认：报告发现结果并在编辑前等待确认。
- 使用 `--fix`：按严重性顺序（`CRITICAL -> HIGH -> MEDIUM -> LOW`）应用所有建议的修复，然后按照验证部分进行验证。第一个面向用户的发现报告是修复后的最终报告。

### 5) 报告

生成以下报告部分。

## 审查视角

将用户的请求视为判断差异的边界。

- 揭示隐藏的假设：如果行为意图不明确或多种解释会导致不同的修复，则停止或记录假设为残留风险，而不是猜测。
- 优先选择最小的可辩护修复。当单次使用的抽象、推测性可配置性、额外功能和广泛的重写增加风险或审查负担时，标记它们。
- 将不相关的变更视为可疑：相邻的重构、仅格式化的编辑、已删除的现有死代码或样式转换需要直接追溯到请求。

## 核心审查检查

每次运行时应用。

- `CORE-001` 行为回归（`HIGH`）：变更分支/状态转换改变了外部行为。
- `CORE-002` 错误路径安全性（`HIGH`）：失败可能级联、崩溃或返回不安全的默认值。
- `CORE-003` 边界处理（`HIGH`）：未处理空值/空值/溢出/边缘输入。
- `CORE-004` 资源清理（`MEDIUM`）：泄漏的定时器/监听器/句柄/连接。
- `CORE-005` 复杂性热点（`MEDIUM`）：变更引入了可避免的耦合或隐藏的副作用。
- `CORE-006` 测试缺口（`MEDIUM`）：变更的行为没有目标测试覆盖。
- `CORE-007` 范围过广的变更（`MEDIUM`）：变更的行没有直接追溯到用户的请求或由变更引起的验证清理。
- `CORE-008` 推测性复杂性（`MEDIUM`）：新的抽象、可配置性、灵活性或不可能情况处理增加了代码而没有证明的需求。
- `CORE-009` 弱成功标准（`MEDIUM`）：实现缺乏清晰的验证目标来改变其声称的行为。

## 配置文件分发

配置文件分发是风险触发的和全面的。读取每个实质性改进缺陷发现的非跳过配置文件，对于触及的风险表面；文件扩展名不足以覆盖核心检查时的变更。每个选定的配置文件完整读取一次；每个配置文件适合单个读取，因此永远不要分页或重读。

首先尊重 `--skip-profile` 排除。在排除后添加 `--with-profile` 配置文件。除非跳过，否则包含 `references/profiles/naming.md`。

- `references/profiles/security.md`：认证、外部输入、密钥、加密、公共网络表面、不安全的解析。
- `references/profiles/configuration.md`：环境/配置、超时、重试、池、限制、资源调整、发布控制。
- `references/profiles/go.md`：Go 服务、CLI、并发、上下文传播、错误处理、模块或测试。
- `references/profiles/typescript-react.md`：TypeScript/JavaScript/React/Node 行为变更，其中类型、渲染、运行时、包或异步语义很重要。
- `references/profiles/python.md`：Python 服务、脚本、异步工作负载、打包、数据处理或 IO 密集型变更。
- `references/profiles/shell.md`：shell 脚本、CI 命令块、部署脚本、安装器命令或命令引用。
- `references/profiles/data-formats.md`：CSV/JSON/YAML/binary 导入/导出/解析、模式、生成数据、迁移或 fixture 更新。
- `references/profiles/naming.md`：命名/意图清晰度。在每次审查中运行，除非跳过。

## 生成和批量文件

- 除非用户明确要求检查，否则从手动审查中排除生成文件、托管的代码、批量文件和低信号文件。
- 优先审查创建或约束它们的源：生成器代码、模式、迁移、模板、锁文件更新意图、fixture 合约或序列化/反序列化路径。
- 使用不变量检查验证受影响的输出，例如重新生成差异、模式验证、解析器往返、行数、校验和、目标 fixture 测试或包管理器锁文件检查。
- 在范围或验证中提及排除的文件，当它们影响置信度时。

## 严重性模型

- **CRITICAL**：可利用的安全漏洞、数据丢失路径或关键路径的停机风险。
- **HIGH**：逻辑缺陷或性能故障，可能破坏核心行为。
- **MEDIUM**：可维护性/可靠性问题，可能在未来导致缺陷。
- **LOW**：局部清晰度/样式/文档改进。

## 证据规则

- 将每个发现结果与在真实、已验证位置的具体代码证据相关联；永远不要编造文件路径或行号。
- 显示触发失败的输入或状态以及导致失败的变更的行或缺失的守卫。
- 简洁地说明影响范围和失败模式。
- 合并重复的发现结果。
- 优先选择有针对性的修复而非广泛的重写。
- 对于范围或简单发现结果，引用变更的行和它没有服务的请求行为。
- 提及无关的死代码作为残留风险；除非用户要求清理，否则不要建议删除它。
- 除非它们创建操作风险，否则将样式问题保持在 LOW。

## 验证

运行验证触及的行为的最窄检查：

- 已触及文件的格式化/检查
- 已触及模块的目标测试
- 相关时进行类型检查
- 任何相关 `excluded-scope` 输出的不变量检查

仅在风险值得时运行更广泛的检查，尤其是在修复触及共享契约时。命名每个跳过的检查和原因。

## 报告

使用这些部分标题，按此顺序。省略不适用部分——不要编号，不要留空或留占位符。

### 范围

审查的文件和任何 `excluded-scope` 条目以及用于它们的验证策略。

### 发现结果

按严重性排序：`CRITICAL -> HIGH -> MEDIUM -> LOW`。对于每个发现结果：

- `[SEVERITY] 标题 — 路径/到/文件.ext:行`
- 影响：具体用户/系统影响。
- 证据：确切的代码行为或差异证据。
- 修复：最小的实际修复。
- 置信度：`high | medium | low`。

### 建议的修复

仅在未使用 `--fix` 时。

### 已应用的修复

仅在使用 `--fix` 时。列出每个更改并引用文件。

### 验证

运行的命令和结果，包括跳过的检查。

### 残留风险

每行一个风险：`假设 <假设>; 如果错误，<什么会破坏>; 通过 <命令或检查> 验证。` 简洁语言——扩展或解释特定于领域的术语。包括需要用户决策的问题，直接表达。当没有时，写 `None.`。

## 停止条件

在以下情况下停止并请求指示：

- 修复需要 API/契约重新设计。
- 行为意图过于模糊无法分类严重性。
- 多种可能的解释会导致实质性的不同发现结果或修复。
- 需要的验证工具不可用且风险很高。
