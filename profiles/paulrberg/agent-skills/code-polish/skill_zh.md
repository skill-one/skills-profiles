# 代码润色

一次性解决作用域问题，仅进行高置信度的简化，按风险修复已发现的缺陷，并验证最终状态。

## 模式

- `--simplify`：仅简化。
- `--review`：仅审查和修复。
- 不使用或同时使用：简化，然后审查简化后的结果。
- `--with-profile <name>` / `--skip-profile <name>`：添加或抑制审查配置文件；`skip` 优先。

## 固定作用域

1. 需要一个 Git 仓库。
2. 使用明确的路径、模式、范围、自然语言目标，或在存在时使用 `resolved-scope` 块。
   否则仅使用本次会话中修改的文件；如果会话历史不可用，则使用所有未提交的跟踪和未跟踪文件。
3. 除非明确请求，否则从手动审查中排除锁文件、生成输出、托管的代码、压缩的包和大型数据快照。
   通过它们的生成器、模式或不变量验证相关排除的输出。
4. 解析并保留一个权威的作用域集和可选的排除项以执行。不要之后扩大或重新计算作用域。如果为空，则停止。

## 简化

保留公共契约、输入、输出、副作用、错误行为、性能敏感特征、遥测和操作守卫。仅应用具有具体理解或缺陷风险益处的更改：

- 平坦化可避免的控制流嵌套；
- 澄清误导性名称或密集转换；
- 当抽象减少总体复杂性时，移除真实重复；
- 在不引起广泛变更的情况下，收紧局部类型和契约；
- 仅移除由本次会话编辑引起的死代码。

不要按行数拆分，执行架构清理，转换同步/异步 API，添加推测性可配置性，或用单次使用的抽象替换可读的重复。无操作是一个有效结果。

## 审查和修复

根据用户请求判断差异。优先级 `CRITICAL → HIGH → MEDIUM → LOW`：

- **CRITICAL**：可利用的安全漏洞、数据丢失或关键停机路径。
- **HIGH**：影响核心行为的错误路径、边界或性能缺陷。
- **MEDIUM**：资源泄漏、复杂热点、测试缺口、范围过大的变更、推测性复杂性或可能导致缺陷的弱成功标准。
- **LOW**：具有真实维护成本的局部清晰度或样式问题。

每个发现都必须引用一个经过验证的位置、触发输入/状态、失败模式、影响范围和更改代码中的证据。合并重复项并应用最小的可辩护修复。当意图不明确时，停止或记录假设，而不是猜测。

选择每个适用的配置文件并只读一次：

| 表面                                                         | 配置文件                 |
| ------------------------------------------------------------- | ----------------------- |
| 认证、密钥、加密、外部输入/网络、不安全解析                 | `security`              |
| 环境、配置、超时、重试、池、限制                             | `configuration`         |
| Go 行为、并发、上下文、错误                                 | `go`                    |
| Rust、Cargo/workspaces、异步/并发、不安全/FFI               | `rust`                  |
| TypeScript 类型、模块、包、异步行为                         | `typescript`            |
| Python 服务、脚本、异步、打包、数据 IO                       | `python`                |
| shell、CI、部署、安装程序、引号                             | `shell`                 |
| CSV/JSON/YAML/binary、模式、迁移、生成数据                   | `data-formats`          |
| 命名和意图清晰                                             | `naming` 除非跳过     |

配置文件位于 `references/profiles/<name>.md`。未选择的配置文件是停止条件。

## 验证和报告

运行最窄的格式化器/检查器、目标测试、类型检查和不变量检查，以证明最终触达的行为。
仅针对共享契约扩大。命名跳过的检查和原因。

用文件数量和最小的有用仓库相对根、通配符、范围或用户提供的目标总结作用域。
不要仅仅为了证明作用域而枚举每个文件；仅命名小范围显式作用域或澄清例外和发现的路径。发现包括严重性、位置、影响、证据、修复和置信度。残余风险说明假设、如果错误的结果和如何检查它。在 `问题和注意事项` 下，将经过验证的修复和证据分组为 `已解决`，将剩余问题、限制或未验证的假设分组为 `打开`，并附上影响和下一步。省略空组并报告每个项目一次；将中性行文和同意的决策放在变更或作用域下。保留 `blocker` 用于阻止所需工作的情况，保留 `risk` 用于特定的潜在不利结果。解决方法在底层问题仍然影响结果时将项目保持为打开状态。完成需要固定作用域、可追溯的编辑/发现和验证证据。

将成功的报告渲染为 `### ✨ 代码润色 — ✅ 完成`，一个小型摘要计数表，一个紧凑的 `作用域` 摘要，`### ✨ 简化`，`### 🧪 验证` 和 `### 问题和注意事项`，省略不适用部分。
当审查运行且未发现缺陷时，说明 `✅ 未发现经过验证的审查发现。` 如果以下停止条件阻止完成，则带头 `### ✨ 代码润色 — ⛔ blocked` 并报告证据和所需决策。保留严重性标记、配置文件 ID、命令、位置、复现输入和安全证据精确且未装饰。

当行为一致性或所需高风险验证无法建立，或修复需要未经请求的公共契约变更或更大规模的重设计时停止。
