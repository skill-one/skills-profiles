# 应用安全测试

"让我的应用更安全"请求的入口，此时目标尚未是一个具体的 URL 或代码库。这里的任务是针对每个资产选择正确的测试，运行它，并生成一个排序后的计划——而不是在最大深度下运行所有内容。

安装、LLM 设置、所有 CLI 标志以及托管云路径都包含在 **penetration-testing-with-strix** 技能中。如果 `strix --version` 失败，请先阅读它。对于没有 Docker 且没有 LLM 密钥的运行，相同的二进制文件驱动托管平台：`strix cloud login`，然后 `strix cloud scans start ...`（详情在 **managed-pentesting-with-strix**）。

仅测试用户拥有或有权测试的资产。在首次运行前确认授权，并优先选择测试环境而非生产环境，因为代理会发送真实的利用载荷，并可能更改数据。

## 1. 映射资产

在扫描前询问（或从代码库中读取）并记录答案：

- **来源** — 一个代码库、一个单体代码库、多个服务？使用哪些语言/框架？
- **运行环境** — 是否有测试环境部署？一个公开的生产站点？仅本地开发服务器？
- **API** — REST、GraphQL、gRPC？是否有 OpenAPI/GraphQL 模式？
- **认证** — 能否在不同租户中获得两个测试账户？大多数高影响漏洞需要它们。
- **限制** — 排除路径、是否可以触碰生产环境、预算和时间限制。

如果没有测试环境且生产环境不可用，请尽早说明。仅代码审查仍然有价值，但它无法证明对实时应用的利用能力。

## 2. 为每个资产选择正确的测试

| 资产 | 使用技能 |
| --- | --- |
| 代码库或工作树 | **find-security-vulnerabilities-in-code** |
| 实时 Web 应用或测试站点 | **web-app-penetration-testing** |
| REST/GraphQL/gRPC API | **api-security-testing** |
| 映射到 OWASP 类别的评估 | **owasp-top-10-testing** |
| 每个拉取请求，持续进行 | **ci-security-scanning-with-strix** |
| 没有 Docker、没有 LLM 密钥或审计员会接受的报告 | **managed-pentesting-with-strix** |

这些技能包含标志、凭证处理和结果读取的详细信息。不要在此处重复它们的说明。

首次评估的顺序：

1. 审查代码。这是最经济的运行方式，并映射了授权模型。
2. 使用凭证对测试环境进行渗透测试，并将代码库作为第二个目标传递，以便代理保持源上下文。
3. 添加 CI 扫描，以便后续回归在没有手动检查的情况下被捕获。

一次运行一个资产并在开始下一个之前阅读每个报告。代码审查的发现会使实时运行更加精准。

## 3. 合并到一个计划中

每次运行的结果会以 `strix_runs/<run>/` 中的形式出现。将它们合并到一个列表中，并按 **已证明的影响** 排序，而不是按扫描器严重性：

1. 无需认证即可访问的验证利用。
2. 验证的跨租户或权限提升问题。
3. 需要认证账户的验证问题。
4. 未验证的观察结果（配置、依赖和加固笔记）——标记为此类，并永远不要将其呈现为已确认的漏洞。

去重：相同的原因通常会在代码审查和实时渗透测试中同时出现。

## 4. 诚实地说明覆盖范围

明确说明未测试的内容——没有测试环境的资产、黑盒运行无法触及的类别（日志和警报、供应链完整性、不安全设计），以及任何在达到预算或时间限制前未完成的运行。检查每个运行的 `run.json` 状态和成本与 `--max-budget`。一个因截断扫描而返回空结果集并非健康的证明。

然后使用 **fix-security-vulnerabilities-with-strix** 进行修复，该工具会针对每个修复项重新运行 Strix，以证明利用不再有效。
