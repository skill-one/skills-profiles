# 对 OWASP Top 10 进行测试

OWASP Top 10 是一个风险类别分类法，而不是一个测试套件——“OWASP Top 10 测试”意味着针对实际应用程序执行每个类别，并报告实际可利用的内容。Strix 的代理程序进行利用；这项技能涵盖了按类别逐个运行并如实报告覆盖范围。

**使用当前版本：[OWASP Top 10:2025](https://owasp.org/Top10/)**（第八版，取代2021版）。在针对旧版本之前，请先询问用户——一些合规性检查清单仍然参考2021版，而标记有错误版本的报告具有误导性。与2021版的主要区别：**SSRF 被合并到 A01**，**A03 软件供应链故障** 扩展了旧的“易受攻击和过时的组件”，**A10 处理异常条件不当** 是新的；A02 安全配置错误已从5移至2。

安装、LLM 设置以及托管云替代方案：**penetration-testing-with-strix**。对于没有 Docker 和没有 LLM 密钥的运行，相同的二进制文件驱动托管平台：`strix cloud login`，然后 `strix cloud scans start ...`（详情在 **managed-pentesting-with-strix**）。

## 代理可以和不可以测试的内容

要如实告知用户这一点——声称全部十个类别都测试完毕是具有误导性的。

| 类别 (2025) | 覆盖范围 |
|---|---|
| A01 未经身份验证的访问控制（包括 SSRF） | **强**——跨用户/租户访问、权限提升、IDOR 和 SSRF（包括盲测、通过带外回调）都已验证可利用。需要两个账户加上一个特权账户来证明授权部分。 |
| A02 安全配置错误 | **强**——调试端点、详细错误、宽松的 CORS、缺失加固、默认凭证、暴露的管理界面。 |
| A03 软件供应链故障 | **部分**——版本指纹识别，以及当源代码提供时进行易受攻击/过时依赖项审查。构建系统和分发基础设施的妥协（该类别更广泛的另一半）不在运行时扫描范围内——与 SCA 加上构建来源控制配合使用。 |
| A04 密码学故障 | **部分**——传输配置、传输中未加密的数据、响应中泄露的密钥和令牌。静态加密和密钥管理需要源代码或基础设施审查。 |
| A05 注入 | **强**——SQL/NoSQL/命令/模板注入和 XSS，已验证可利用。 |
| A06 不安全设计 | **部分**——业务逻辑滥用（价格/数量篡改、工作流跳过、竞态条件）在可访问时被发现；设计意图仍需人工审查和威胁建模。 |
| A07 身份验证故障 | **强**——身份验证绕过、弱会话/令牌处理、密码重置和 MFA 缺陷。 |
| A08 软件或数据完整性故障 | **部分**——可访问的不安全反序列化和未签名更新路径；CI/CD 信任边界不可在运行时测试。 |
| A09 安全日志记录和警报故障 | **不可从外部测试**——需要审查日志记录和警报管道。如实说明，而不是报告为通过。 |
| A10 处理异常条件不当 | **部分**——代理主动探测错误处理和故障打开行为（畸形输入、强制错误、竞态和超时条件）并报告泄漏或绕过控制的内容；内部错误路径的全面覆盖需要源代码审查。 |

对于 API，使用 **OWASP API 安全 Top 10 (2023)** 进行相同的练习——API1 BOLA，API3 未经身份验证的对象属性级授权（2019 年过度数据暴露 + 批量赋值合并），API5 未经身份验证的函数级授权——使用 **api-security-testing** 技能。

## 运行测试

最大类别覆盖范围来自为代理提供源代码和运行实例，以及两个权限级别的凭证：

```bash
strix -n \
  -t https://github.com/org/app \
  -t https://staging.example.com \
  --scan-mode deep --max-budget 30 \
  --instruction "OWASP Top 10:2025 评估。系统性地覆盖每个类别，并将每个发现映射到其 2025 类别 ID。
账户：userA@example.com/<pw>（组织 1），userB@example.com/<pw>（组织 2），admin@example.com/<pw>。
优先级：A01（跨组织访问、权限提升、SSRF），A02，A05，A07，A10。
不在范围内：/billing/*，出站邮件。"
```

- `--scan-mode deep` 在这里很重要：系统地遍历十个类别不是快速扫描。
- 没有第二个账户，A01 结果在结构上是不完整的——在报告中如实说明，而不是暗示。
- 需要面向审计员的 PDF？通过托管平台运行它，并提取技术报告（**managed-pentesting-with-strix**）。

## 如实报告

从 `strix_runs/<run>/`，按类别和状态对 `vulnerabilities/*.md` 进行分组，每个类别说明：尝试了什么、验证了什么、什么无法评估（A09 总是；A03/A04/A06/A08/A10 部分无法评估）。使用所使用的版本标记报告。在提交给用户之前，自己验证每个 PoC。

`0` 退出代码意味着在分析的范围内**没有验证可利用的内容**——检查 `run.json` 状态和成本与 `--max-budget` 对比；预算限制的运行不是完成的评估。

## 然后修复并重新测试

使用 **fix-security-vulnerabilities-with-strix** 进行修复，并重新运行以证明每个漏洞已被关闭。为了在应用程序变化时保持持续覆盖，使用 **ci-security-scanning-with-strix** 对拉取请求进行门控。
