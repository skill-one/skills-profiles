# 测试守卫

你正在审查待发布的生成或修改后的测试代码。在第一次编写测试后的测试呈现、提交或合并之前，执行以下规则。做一个敏锐的审查者，而不是一个吹毛求疵的人：标记那些浪费维护工作或隐藏真实错误的内容，忽略外观上的偏好。

这些规则的存在是因为编码代理过度生成测试。常见的失效模式：模拟器过重的单元测试断言实现细节、几乎重复的测试主体但仅值不同、以及重新验证框架而不是项目逻辑的测试。每个在差异中看起来都很高效，但维护成本却永远高昂。

## 此技能何时激活

- 编码代理刚刚用任何语言编写了新的测试函数或测试文件
- 你正在编辑现有的测试
- 你正在审查包含测试更改的差异
- 用户要求你编写、添加或审查测试

## 首先适应项目

这些规则是通用的，但它们的适用性不是。在审查之前：

1. 检查项目的代理指令（CLAUDE.md、AGENTS.md）和测试文档。当项目特定的测试规则与该技能冲突时，项目特定的测试规则优先。
2. 确定测试堆栈，然后阅读匹配的参考以获取具体模式：
   - Python / pytest → [references/pytest.md](references/pytest.md)
   - PHP / PHPUnit / Pest / WordPress → [references/phpunit.md](references/phpunit.md)
   - JavaScript / TypeScript / Jest / Vitest → [references/jest.md](references/jest.md)
3. 如果项目调用 LLM API、使用代理框架或连接可观察性/遥测，请也阅读 [references/llm-app-testing.md](references/llm-app-testing.md) — 它为 LLM 应用程序添加了三个特定规则。
4. 映射项目的系统边界：网络调用、数据库、文件系统、时钟和随机性、第三方 SDK、LLM API。现有的固定装置和测试辅助程序通常揭示了项目在哪里已经划定了这些界限。

## 该做什么

1. 阅读测试代码：差异、新文件或正在修改的部分。
2. 检查每个测试是否符合以下规则。
3. 简洁地报告违规行为：规则编号、位置、为何违规、建议的修复方案。
4. 如果用户在测试编写之前明确调用此技能，则在编写时应用规则 — 不要先编写违规行为然后再标记它们。

编写新测试时，针对每个测试询问：“这个测试捕获了其他测试套件中未捕获的什么具体错误？” 如果你不能清楚地回答，就不要编写它。

## 九条规则

### 规则 1：测试行为，而非实现
从调用者的角度测试代码的行为。断言返回值和可观察的副作用。永远不要断言内部辅助函数是否用特定参数调用 — 这种测试在每次重构时都会失效，而捕获不到任何错误。

**违规模式：** 断言内部函数的模拟器被调用，而该函数不是系统边界。
**修复方案：** 断言调用者观察到的返回值或状态变化。

### 规则 2：每个模拟器都必须有理由
仅在系统边界处模拟：网络和 HTTP 调用、LLM API、数据库、外部文件上的文件系统 I/O、时钟和随机性、第三方 SDK。永远不要模拟内部类或辅助函数以隔离“单元” — 你创建的接口隐藏了值得捕获的集成错误。

当你模拟一个边界时，断言调用者如何处理响应，而不是模拟器是否接收了特定参数。

### 规则 3：每个测试一个场景，数据驱动处理变体
如果两个或多个测试具有相同的设置且仅在输入/输出值上不同，将它们合并为一个数据驱动测试（`@pytest.mark.parametrize`、PHPUnit `#[DataProvider]`、Jest `test.each`）。

**当单独的测试是正确时：** 设置不同、断言不同、模拟器配置不同，或真实的不同场景恰好执行了同一个函数。

### 规则 4：每个测试都必须证明其存在的合理性
询问：“这个测试捕获了其他测试未捕获的什么错误？” 删除仅捕获拼写错误、验证数据类的默认值或测试简单传递逻辑的测试。

**常见的无理由测试：** 构造函数设置属性、函数拒绝类型系统已经禁止的输入、日志消息的字符串格式化、常量等于其字面值。

### 规则 5：为场景命名测试
模式：`test_<场景>_<预期结果>`。名称应像需求一样阅读，而不是重复函数签名。

| 坏的 | 好的 |
|-----|------|
| `test_parse_response_missing_field` | `test_malformed_response_falls_back_to_default` |
| `test_get_language_no_class` | `test_element_without_class_returns_empty_language` |
| `test_add_tags_single_string` | `test_single_tag_normalizes_to_list` |

### 规则 6：生产回归测试是神圣的
重现真实生产错误的测试总是合理的。在名称或注释中引用事件（日期、问题 ID 或简短描述），并且永远不要删除它们。它们豁免于规则 4 — 它们的合理性是事件。

### 规则 7：不要为框架保证编写测试
不要测试验证库是否验证、ORM 是否提交、路由器是否返回 404 或测试框架的固定装置是否工作。测试你框架之上的逻辑。

**违规模式：** 一个测试，即使你删除了所有项目的自定义代码并仅保留框架默认值，它仍然会通过。

### 规则 8：状态和值对象是真实的，永远不要模拟
永远不要模拟数据模型、DTO、实体或状态对象。构造一个真实实例。模拟状态隐藏字段名拼写错误和验证错误 — 正是值得捕获的错误。如果构造真实对象很痛苦，那不是模拟的理由；添加一个小型构建器或工厂辅助程序。

### 规则 9：测试的基础设施使用真实基础设施
当数据库查询、模式行为或持久化逻辑是测试的主题时，使用带有真实迁移的实时测试数据库运行。模拟会话那里测试不到任何东西。当持久化只是测试行为的一个副作用时，模拟数据库是没问题的。

## 报告格式

在标记违规行为时，使用此格式：

```
**规则 N 违规** 在 `tests/path/file.ext::<测试名称>`
- 什么： <一句话描述违规行为>
- 修复方案： <一句话描述要做什么替代方案>
```

按文件分组违规行为。如果一个文件没有违规行为，不要提及它。

## 严重性指南

并非所有违规行为都相同。使用判断：

- **必须修复：** 规则 1、2、8 — 这些隐藏了真实错误或使测试变得脆弱
- **应该修复：** 规则 3、4、5、7 — 这些导致膨胀和维护拖累
- **神圣的：** 规则 6 — 永远不要删除，总是允许
- **值得注意：** 规则 9 — 测试架构；标记它，但不要因为它而阻止小更改

## 此技能不做什么

- 它不运行测试。使用项目的测试运行器来运行测试。
- 它不强制代码风格 — 那是代码分析器的工作。
- 它不决定要测试什么 — 只决定如何测试。
- 它不标记你未修改文件的预现有违规行为，除非要求审计。
