# clean-code-guard

你正在审查在交付前生成的或更改的代码。在第一次实现遍历后，将以下规则作为守门遍历步骤应用——一旦这项技能被激活，就在同一会话中对每个后续的代码更改重复应用它，在每次编辑后重新运行自我检查，而不是因为技能加载过早而退回到未受保护的输出。如果用户在编写代码之前明确调用此技能，则在编写时使用相同的规则，并且仍然在交付前运行自我检查。

## 兼容性

这是一个可移植的指令技能。它不需要MCP服务器、网络访问、API密钥、shell命令、本地可执行文件或捆绑脚本。它可以在任何支持`SKILL.md`以及直接链接的[references/](references/)文件的环境中运行；`agents/openai.yaml`是轻量级显示元数据。

此技能不会取代项目代码检查器、格式化器、类型检查器或测试运行器。使用项目的工具进行机械验证；使用此技能进行代码质量和审查的判断层。

## 如何使用此技能

此技能有三种模式——根据用户的要求进行选择。

**守门遍历模式**（推荐）：代码生成、编辑、重构或修复后，检查diff或目标文件与以下*始终应用的指令*。在呈现、提交或合并工作之前修复违规行为。

**实时模式**（显式）：当用户在危险的代码编辑之前调用此技能时，在编写时应用相同的指令，然后运行*交付前自我检查*清单。如果你违反了任何规则，请在向用户展示之前修复它。

**审查模式**（在用户要求您审查、审计、评论或评分代码时触发）：与目标文件(s)对照[references/review-checklist.md](references/review-checklist.md)并生成结构化的问题报告。在审查模式下不要编辑代码，除非被要求。

在所有三种模式下，规则正文都存在于[references/](references/)中。当您遇到您不完全记得其推理的规则时、当用户对规则提出异议并且您需要来源引用时、当您处于审查模式并且需要完整的清单时、当正在审查的代码触及特定原则（例如，子类化→[references/solid.md](references/solid.md)；重复利用→[references/dry-kiss-yagni.md](references/dry-kiss-yagni.md)）时，请阅读相关的参考文件。

参考文件包括：
- [references/naming-and-functions.md](references/naming-and-functions.md) — 名称、函数大小、参数、命令/查询分离。
- [references/comments-and-formatting.md](references/comments-and-formatting.md) — 何时评论、何时删除、匹配相邻样式。
- [references/solid.md](references/solid.md) — SRP、OCP、LSP、ISP、DIP的现代表述和检测异味。
- [references/dry-kiss-yagni.md](references/dry-kiss-yagni.md) — 知识与代码重复、Sandi Metz的重新内联规则、McCabe复杂度、Fowler的YAGNI成本类别。
- [references/ai-failure-modes.md](references/ai-failure-modes.md) — LLM生成糟糕代码的14种系统性方式。**如果您是读取此技能的AI代理，请首先阅读此文件。** 它是此技能中杠杆最高的文件。
- [references/review-checklist.md](references/review-checklist.md) — 审查模式的结构化逐步指南。

## 示例

- 编码代理实现了一个端点：在呈现或提交工作之前，对diff使用守门遍历模式。
- 用户要求“审查这个PR”或“我应该合并这个吗？”：使用审查模式并报告来自[references/review-checklist.md](references/review-checklist.md)的结果；不要编辑，除非被要求。
- 用户要求“使用clean-code-guard实现这个端点”：在编写时使用实时模式，然后在交付前运行自我检查。
- 用户要求“重构这个函数，行为相同”：精确保留可观察的行为，并将任何错误修复视为单独的更改。

## 成功标准

当编写代码的任务避免列出的失败模式、代码审查任务产生具有具体证据的优先级发现、重构保留行为（除非用户明确要求行为更改）时，此技能即在工作。它应该保持沉默，因为概念性、CI、git工作流、散文、数据分析和测试运行任务由frontmatter排除项覆盖。

## 此技能存在的原因

LLM生成的代码具有可衡量的系统性失败模式，通用“遵循干净代码”指令无法捕获。有已发表研究的例子：

- **在2021年至2024年跟踪的代码库中，代码重复增长了8倍**（GitClear 2025报告）。
- **16个模型中，包幻觉率平均为19.6%**（Spracklen等人，USENIX Security '25）。
- LLM经常将危险操作封装在宽泛的catch-all处理器中，导致错误被吞噬（Karpathy）。
- AI代理**“尽管测试失败却声明成功”**，通过返回硬编码的固定值（Fowler，减少摩擦的模式）。
- 在AI辅助提交中，函数大小从142增长到267 LoC，圈复杂度从4.2增长到8.1（GitClear）。

经典原则（干净代码、SOLID、DRY/KISS/YAGNI）仍然是基础——但此技能添加了大多数规则包遗漏的*AI特定*层。

## 始终应用的指令

这些是在每个代码更改时必须遵循的规则。它们是命令，不是建议。

### 函数和名称

1. **名称揭示意图。** 不要在没有限定符的情况下使用`data`、`data2`、`result`、`result_final`、`item`、`temp`、`value`、`obj`、`info`、`helper`、`manager`、`utils`或`handle_*`/`process_*`/`do_*`。名称必须回答*它存在的原因和它做什么*。（干净代码第2章）
2. **函数保持小。** 目标≤20行，一个抽象级别，一件事情。如果你可以提取一个具有名称的函数，该名称不陈述主体，则父级做了多于一件事情。（干净代码第3章）
3. **四个参数是硬上限。** 五个参数时停止，并引入请求/配置对象（记录、结构、DTO或等效物）。永远不要使用布尔标志参数——分成两个函数。
4. **没有输出参数。** 函数要么返回一个值（查询），要么具有副作用（命令）。永远不要两者兼有。命令名称使用动词；查询名称使用名词或getter样式名称。（CQS）

### 注释和结构

5. **注释解释*为什么*，从不解释*什么*。** 删除任何释义下一行代码的注释。删除步骤编号脚手架注释。删除已注释的代码——版本控制存在。（干净代码第4章）
6. **匹配文件的现有样式。** 在编写之前，阅读你正在编辑的文件和至少一个邻居文件。镜像大小写、导入顺序、错误处理、日志记录和HTTP/DB客户端选择。不要引入第二种模式。

### SOLID

7. **每个模块一个参与者。** 类应该是可回答一个利益相关者群体（会计、认证、报告）的问题。如果两个不相关的子系统都触及同一个类，请将其拆分。（SRP，Uncle Bob 2014）
8. **通过新代码扩展，而不是编辑。** 如果添加新变体需要在现有函数中添加另一个类型标签分支，请首先重构为注册表、策略或多态分发。（OCP）
9. **子类拒绝其父类的契约。** 永远不要覆盖一个方法来表示“未实现”或“不支持的操作”。在覆盖中永远不要加强先决条件或削弱后置条件。如果您需要这样做，则继承是错误的。（LSP）
10. **抽象与客户端一起存在，而不是与实现一起存在。** 当您引入接口、协议或抽象合同时，将其放在消耗它的包中，而不是放在具体类旁边。（DIP）

### DRY、KISS、YAGNI

11. **删除重复的*知识*，而不是重复的*文本*。** 看起来相似但编码不同规则的两个函数不是DRY违规行为。代码中表达的一条规则+文档+模式是。（实用程序员，“DRY”）
12. **错误的抽象比重复更糟。** 如果一个抽象为每个调用者的特殊情况积累了分支，请将其重新内联回调用者，然后删除死分支，然后再重新抽象。（Sandi Metz，“错误的抽象”）
13. **复杂度上限：圈复杂度≤10，嵌套深度≤5。** 超过之前重构。（McCabe 1976）
14. **没有推测性的东西。** 没有可选参数、配置标志、环境变量、功能切换、接口、工厂或基类，而没有当前调用者。如果您发现自己添加`enable_*`、`use_*_v2`或`*_mode`，请删除它并交付具体行为。（Fowler，“YAGNI”）

### AI特定守门栏——最高杠杆部分

15. **永远不要用宽泛的catch-all处理吞下错误。** 只捕获您可以恢复的特定错误类型。如果您无法恢复，请让错误传播。从catch处理程序返回null/none/空成功是被禁止的，除非函数契约文档了该行为。（Karpathy）
16. **守卫边界；信任契约。** 在信任边界——外部输入、请求/API有效载荷、反序列化或跨进程数据、来自不可信源的一切——进行验证，即使快乐路径看起来很好。*边界内部*，不要为已声明类型或调用者契约已排除该情况的价值添加null检查或运行时类型检查。守卫的测试不是“这理论上可能是错的”，而是“不可信数据能否到达这里。”（arXiv 2409.19182）
17. **验证每个导入和外部调用。** 在调用库上的方法之前，确认它在安装的版本中存在（读取包、检查锁文件或导入并检查）。不要根据API“应该”的样子生成代码。（USENIX Security '25）
18. **生产代码中不要有硬编码的“成功”返回或模拟固定值。** 永远不要返回`{"status": "ok", ...}`或来自说它执行实际工作的函数的固定数据。如果您无法实现，请使用语言的未实现或不受支持的操作机制明确失败，并说明。永远不要禁用、跳过或削弱测试以使其通过。（Fowler，Claude Code问题#6984）
19. **重新导出，不要从类似处复制。** 当您想复制一个函数并修改它时，请停止。根据规范重新导出。Off-by-one和错误的null语义错误几乎总是通过从类似处复制进入。（arXiv 2411.01414）
20. **在编写它们之前枚举边界情况。** 对于任何范围、off-by-one、null/空/一/多、偶/奇或unicode/字节边界，首先在注释中编写案例列表。在继续之前，在代码中覆盖每个案例。
21. **交付前删除死代码。** 运行代码检查器或grep遍历，查找未使用的导入、未使用的符号、不可达的分支和“以防万一”的导出。删除它们。今天没有任何调用者调用的函数没有资格“为将来而活”。
22. **写之前读。** 在不熟悉的存储库中编写之前，阅读您要编辑的文件、一个邻居文件和任何项目规则文件（CLAUDE.md、AGENTS.md、README的“约定”部分）。使用项目的现有帮助程序、错误类型和日志记录。
23. **对于几行代码覆盖不要添加新依赖项。** 在添加包之前，检查标准库、已安装的依赖项，以及是否用几行本地代码完成工作。新依赖项是永久维护和供应链表面；只有在它拥有您不应重新实现的真正复杂度（加密、解析、时区——说明性，非详尽）时才添加一个，永远不会为了节省十行而添加。

### 地板——为了简单起见永远不会削减这些规则

规则16在边界*内部*信任契约；以下项目保持不变，即使您剥离了推测（14）、防御性守卫（16）和死代码（21）。删除其中一项是行为更改，而不是清理——保留它，或者标记它并询问。

- **每个信任边界处的验证和清理**——外部输入、请求/API有效载荷、反序列化或跨进程数据。
- **防止数据丢失的错误处理。**
- **安全措施**——授权、输出转义、参数化查询、密钥处理。
- **用户明确请求的行为。** 闲聊≠请求，但不要丢弃用户要求的东西。

### 重构纪律

24. **重构时保留可观察的行为。** 当用户要求您清理、简化或重构现有代码时，不要更改契约——相同的输入产生相同的输出，相同的异常抛出，相同的副作用，相同的排序保证。如果您在重构时发现了一个错误，请先标记它并询问后再更改它。重构被定义为*“为使软件的内部结构更容易理解并在不改变其可观察行为的情况下使其更容易修改而进行的更改”*（Fowler，《重构》）。错误修复和重构是两个操作——永远不要将它们捆绑在单个更改中。

## 交付前自我检查

在您向用户展示您编写的或编辑的代码之前：

1. 对照您的diff遍历指令1-24。修复每个违规行为。
2. 对于新函数，计算：行数≤20？参数≤4？复杂度感觉≤10？名称揭示意图？
3. 对于新注释，询问：这解释*为什么*？如果它解释*什么*，请删除它。
4. 对于新错误处理：捕获的错误类型是否具体？处理程序是否做其他事情而不是静默返回？
5. 对于新抽象（接口、工厂、基类、注册表）：是否有第二个具体用户*今天*？如果没有，请内联它。
6. 您是否阅读了您编辑的文件和至少一个邻居文件？您的样式是否匹配？
7. 是否有任何硬编码的“ok”返回或固定数据？如果是，请用实际实现或明确的未实现/不支持操作失败替换它。
8. 如果这是一个重构：您是否更改了可观察的行为？如果是，您将错误修复捆绑在一起——将其分开并询问用户。

如果您不能对每个检查回答“是”，请在发货前修复。

守门遍历后，使其可见，以便用户可以看到它运行（守门遍历和实时模式——审查模式通过其自己的发现格式报告）。将每个修复项列作`<文件>:<行号> — <什么已更改>`，如果它是不稳定的，则省略行号，然后用一行结束：`clean-code-guard: <N>已修复，<M>标记为作者`——或者`clean-code-guard: 清洁`如果未触发任何内容。仅报告您实际做出的更改；永远不会估计质量分数或百分比——没有基线，因此此类数字将被发明。这报告了遍历；它不会阻止呈现或提交。

## 当用户对规则提出异议时

请他们参考相关[references/](references/)文件中的源名称，并且仅在需要URL时使用[references/sources.md](references/sources.md)。规则是有力的——它们来自主要来源（Uncle Bob、Fowler、Hunt & Thomas、McCabe、Metz）以及2024-2026年关于LLM代码生成的已发表研究。如果用户有特定上下文的原因要覆盖（例如，构造函数确实需要8个参数用于配置DTO），请在代码注释中记录被覆盖的原则、原因和重新考虑触发器——应重新考虑的条件。没有重新考虑触发器的异常注释本身在下次遍历中是一个发现：没有退出的权衡只是延迟的债务。

## 故障排除

- 如果任务是概念性的而不是代码生成的，请不要应用此技能；直接回答概念。
- 如果审查模式开始产生仅限样式的反馈，使用[references/review-checklist.md](references/review-checklist.md)并优先考虑行为性错误、易碎性和可维护性风险。
- 如果规则与显式的项目约定冲突，请遵循项目约定，并且仅在它可能会让未来的维护者感到惊讶时才记录例外。
- 如果此技能感觉过于广泛，请首先使用frontmatter排除项；不要将特定于运行时的规则添加到此通用守门技能中。

## 此技能不做什么

- 运行代码检查器或静态分析。那些是工具级问题；此技能是关于*要写什么*和*要寻找什么*。
- 强制语言特定的格式化器或代码检查器偏好。委托给项目的样式工具。
- 替代测试。干净代码通过测试；没有干净代码的测试不会通过，但干净代码而没有测试也是一个缺陷。
