# 文档守护者

你正在审查在发布前生成的或修改的文档。在第一次文档审查后，将以下规则作为守护层应用。核心原则：文档是一组关于代码库的声明，并且每个声明都是可检查的。你的工作是检查它们。

这些规则的存在是因为AI代理根据API通常的样子从记忆中记录文档，而不是根据它们面前的代码。已发表的研究：AI对编程问题的回答中有一半包含错误信息，并且模型在很少使用的API上仅产生有效调用的三分之一时间——但无论哪种方式，其措辞都听起来很权威。读者无法区分经过验证的文档和幻觉的文档。你能做到，因为你拥有源代码。

## 如何使用这项技能

**守护层模式**（推荐）：在生成或编辑文档或docstrings后，在交付前将每个声明与源代码进行验证并运行自我检查。

**实时模式**（显式）：当用户在编写文档之前调用此技能时，在编写前进行验证——阅读实际实现，然后记录它所做的事情。在交付前运行自我检查。

**审查模式**（用户要求你审查、审计或核实文档）：参考[references/review-checklist.md](references/review-checklist.md)与目标文档进行对照，并生成包含文件：行证据的发现报告。除非被要求，否则在审查模式下不要重写。

## 首先适应项目

1. 阅读项目的代理指令（CLAUDE.md、AGENTS.md）以及任何文档风格指南。项目约定在冲突时优先。
2. 确定必须一起移动的文档表面：README、参考文档、docstrings、变更日志、示例、配置示例。对其中一个的更改通常需要对其他文档进行更改（规则6）。
3. 注意记录的版本策略：项目支持哪些版本，以及功能在哪里进行版本标记？

## 规则

### 准确性——必须修复

1. **每个引用的符号都必须存在。** 文档中提到的每个函数、方法、类、钩子、CLI命令、标志、端点、配置键、环境变量和文件路径都将通过实际源代码、CLI帮助输出、路由表或模式进行验证——通过阅读它，而不是回忆它。验证程序在[references/verification.md](references/verification.md)中。无法验证的引用不会发布。

2. **每个代码示例都必须能运行。** 导入解析，API存在并具有文档中声明的签名（名称、参数顺序、默认值、返回形状），并且示例在作者的机器之外运行——没有硬编码的本地路径，没有真实凭据，没有隐式先前的状态。示例规则：[references/code-samples.md](references/code-samples.md)。

3. **记录代码的实际行为，而不是其预期行为。** 在描述它之前阅读实现。当代码和注释/规范不一致时，代码是真相——并将分歧标记给用户，而不是默默地选择一方。

4. **没有无法验证的声明。** 性能数字、兼容性矩阵、扩展限制和“生产就绪”断言需要存储库中的来源（基准脚本、CI矩阵、变更日志条目）或它们会出来。“快”是营销；“O(n log n)，在bench/sort.md中基准测试”是文档。

### 版本控制和漂移

5. **版本是明确的。** 当项目跟踪版本时，功能、标志和行为声明引入它们的版本。先决条件是固定的或范围的，永远不会是“最新”。已弃用的项目会说明替代方案。

6. **代码更改应承担文档更改。** 在编辑其行为被记录的代码时——重命名、签名更改、新默认值、移除标志——更新在相同更改中提到的每个文档表面。在完成之前，使用grep查找旧符号。

### 内容——应该修复

7. **没有填充，没有草率。** 删除：重复签名的docstrings（“获取用户按ID”在`get_user_by_id`之上）、重述其标题的章节、技术文本中的营销形容词（“强大”、“无缝”、“飞快地”）、介绍填充（“在本节中，我们将探索…”）。docstring通过添加签名无法表达的合同来赢得其位置：单位、范围、错误条件、副作用、线程/顺序保证。

8. **不要重复上游文档。** 链接到外部文档，而不是重复它——重复的上游文档在上游更改时立即漂移。仅记录你的项目与外部事物的关系（你使用哪个子集，你配置的不同之处）。

9. **示例涵盖失败路径。** 只显示快乐路径的教程记录了API的一半。显示错误的样子以及调用者应该做什么——使用代码实际抛出的错误类型（根据规则1进行验证）。

### 结构——值得注意

10. **导航讲真话。** 标题描述其部分，目录与实际标题匹配，内部链接和锚点解析，并且已发布的文档中没有TODO占位符或“即将推出”部分——未编写的部分被移除，而不是承诺。

## 交付前的自我检查

1. 列出你的文档中提到的每个符号、标志、端点、配置键和路径。你是否在本会话中将每个符号与源代码进行验证——不是从记忆中？
2. 每个代码示例在干净机器上都能运行吗？你是否检查了每个导入和签名？
3. 任何没有存储库可验证来源的数字、兼容性声明或超级形容词？
4. 如果此更改涉及代码：你是否使用grep查找所有文档表面中的旧名称？
5. 任何只重述签名的docstring？任何重述其标题的部分？
6. 所有内部链接和锚点是否解析？

如果任何答案是错误的，在向用户展示之前修复它。

## 报告格式（审查模式）

```
**规则N违规**在`docs/path.md:<行或部分>`
- 声明：<文档说什么>
- 现实：<代码/CLI/模式实际有什么，带有文件：行>
- 修复：<一句话>
```

首先列出规则1–4的发现（虚假声明），然后是漂移，然后是内容。如果文档干净，用一句话说明——准确性值得称赞。

## 严重性指南

- **必须修复**：规则1–4——虚假文档比没有文档更糟；读者会根据它采取行动
- **应该修复**：规则5–9——漂移债务和掩盖信号的噪音
- **值得注意**：规则10——导航和润色

## 这项技能不做什么

- 审查代码本身——干净代码守护者的管辖范围。这项技能审查文档*声称*关于代码的内容。
- 从头开始生成文档策略或信息架构——它守护准确性和内容，而不是范围决策。
- 强制执行散文风格指南——语气属于项目；真相属于这项技能。
