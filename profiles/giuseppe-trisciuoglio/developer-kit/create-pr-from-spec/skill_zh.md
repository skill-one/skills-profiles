# 从规范创建拉取请求

使用位于 `${workspaceFolder}/.github/pull_request_template.md` 的 `pull_request_template.md` 模板为规范创建 GitHub 拉取请求。

## 概述

此技能可从规范中直接自动化创建 GitHub 拉取请求。它遵循结构化流程：

1. 分析规范模板要求
2. 使用目标分支创建草稿 PR
3. 验证不存在重复的 PR
4. 使用符合模板的内容更新 PR 主体和标题
5. 将 PR 标记为待审核
6. 自动分配给创建者
7. 向用户返回 PR URL

**主要优势：**
- ✅ 从规范自动创建 PR
- ✅ 符合模板的 PR 主体和标题
- ✅ 防止重复 PR
- ✅ 自动分配给创建者
- ✅ 规范到 PR 的流程优化

## 何时使用

在以下情况下使用此技能：

1. **规范已准备好合并** - 将最终化的规范转换为 PR
2. **需要自动创建 PR** - 避免手动草拟 PR
3. **需要模板合规** - 确保 PR 符合 `pull_request_template.md`
4. **从多个规范创建 PR** - 批量处理规范到 PR
5. **团队协作** - 将规范作为 PR 分享以供审核

**触发短语：**
- "从规范创建拉取请求"
- "将规范转换为 PR"
- "为规范打开 PR"
- "将规范作为拉取请求提交"
- "自动化 PR 创建"

## 说明

### 前置条件

在使用此技能前，请确保：
- 规范文件已最终化并准备好审核
- 已指定目标分支（例如 `main`、`develop`）
- 存在于仓库中的 `.github/pull_request_template.md`
- 您有创建 PR 的写入权限

### 步骤详解

**1. 分析规范模板**
- 从 `${workspaceFolder}/.github/pull_request_template.md` 提取要求
- 使用搜索工具解析模板部分和占位符

**2. 创建拉取请求草稿**
- 使用 `create_pull_request` 工具创建目标分支的草稿 PR
- 首先使用 `get_pull_request` 验证不存在现有 PR 以防止重复
- 如果 PR 已存在，停止并向用户报告

**3. 获取拉取请求变更**
- 使用 `get_pull_request_diff` 工具分析差异
- 在更新前验证代码变更是否正确

**4. 更新拉取请求**
- 使用 `update_pull_request` 工具填充 PR 主体和标题
- 结合步骤 1 的模板部分
- 确保所有必填字段已填写

**5. 标记为待审核**
- 使用 `update_pull_request` 工具将状态从草稿更改为待审核
- 验证 PR 不再处于草稿模式

**6. 分配拉取请求**
- 使用 `get_me` 获取当前用户信息
- 使用 `update_issue` 工具将 PR 分配给创建者

**7. 返回拉取请求 URL**
- 向用户提供可点击的 PR URL
- 包含 PR 内容摘要

## 示例

### 示例 1：基本 PR 创建

```bash
输入：从规范创建到 main 分支的 PR
流程：
  1. 分析 pull_request_template.md
  2. 创建指向 main 的草稿 PR
  3. 检查现有 PR
  4. 更新 PR 标题："feat: [规范中的功能名称]"
  5. 使用模板部分更新 PR 主体
  6. 标记为待审核
  7. 分配给创建者
输出：https://github.com/user/repo/pull/123
```

### 示例 2：符合模板的 PR

```markdown
PR 标题：feat: 实现用户认证系统

PR 主体：
## 描述
实现基于 JWT 的认证，带令牌刷新机制

## 相关问题
关闭 #456

## 变更
- 添加 JWT 中间件
- 实现令牌验证
- 添加令牌刷新端点

## 测试
- 认证中间件的单元测试
- 令牌端点的集成测试

## 检查清单
- [x] 测试通过
- [x] 文档更新
- [x] 无破坏性变更
```

### 示例 3：重复预防

```bash
输入：从规范创建 PR
检查：当前分支的 PR 是否已存在？
  → 是：报告错误，不创建重复
  → 否：继续创建 PR
输出："PR 已存在于 https://github.com/user/repo/pull/789"
```

## 要求

- 单个拉取请求用于完整的规范
- 清晰的标题和主体标识规范/功能
- PR 主体符合 `pull_request_template.md` 结构
- 验证不存在重复的拉取请求
- PR 自动分配给创建者
- 不留下草稿 PR

## 成功标准

- ✅ 无错误创建 PR
- ✅ PR 主体符合 `pull_request_template.md` 结构
- ✅ PR 标题清晰标识规范/功能
- ✅ 分支不存在重复 PR
- ✅ PR 分配给创建者
- ✅ 返回 PR URL 给用户
- ✅ PR 已准备好审核（非草稿）

## 限制和警告

⚠️ **重要：**
- PR 创建需要仓库写入权限
- 创建 PR 前必须存在目标分支
- 模板文件必须存在于 `.github/pull_request_template.md`
- 无法在无有效分支目标的情况下创建 PR
- 将检测并拒绝重复 PR
- PR 分配需要有效的 GitHub 用户

🚫 **限制：**
- 不自动执行代码审核
- 不触发 CI/CD 管道
- 不自动合并 PR
- 无法修改现有代码，仅修改 PR 元数据

## 最佳实践

1. **创建前验证** - 转换为 PR 前始终审核规范
2. **使用描述性标题** - PR 标题应清晰指示功能/修复目的
3. **完整填写模板** - 确保所有必需的模板部分已填写
4. **关联问题** - 在 PR 主体中包含问题引用
5. **先测试** - 确保所有测试通过前创建 PR
6. **团队审核** - 标记为待审核前获取团队批准
7. **清理 git 历史记录** - 确保提交干净且文档完善

## 使用的工具

- `search` - 分析规范模板要求
- `create_pull_request` - 以草稿模式创建新 PR
- `get_pull_request` - 创建前检查现有 PR
- `get_pull_request_diff` - 分析 PR 变更
- `update_pull_request` - 更新 PR 标题、主体和状态
- `update_issue` - 将 PR 分配给创建者
- `get_me` - 获取当前用户信息
