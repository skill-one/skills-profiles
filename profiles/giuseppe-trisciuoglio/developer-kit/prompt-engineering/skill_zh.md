# 提示工程

## 概述

使用这项技能来设计清晰、可测试和可重用的提示系统。
它涵盖提示起草、优化、评估以及面向生产的
少样本提示、推理工作流、模板和系统提示的模式。

在此文件中保持主要工作流，仅加载您应用的模式的目标参考文件。

## 何时使用

在以下情况使用这项技能：

- 用户要求编写、重写或改进提示
- 提示需要更好的结构、可靠性或输出格式
- 需要少样本示例或推理脚手架
- 必须创建系统提示或可重用提示模板
- 现有提示需要可衡量的优化和测试

当您需要对特定模式需要更深入的指导时，请阅读 `references/` 中的相关文件。

## 核心模式

### 1. 少样本学习

#### 示例选择策略
- 使用 `references/few-shot-patterns.md` 获取全面的示例选择框架
- 平衡示例数量（3-5 个最佳）与上下文窗口限制
- 在示例集中包含边缘案例和边界条件
- 优先考虑涵盖问题空间变化的多样化示例
- 按从简单到复杂的顺序排列示例，以实现渐进式学习

#### 少样本示例（情感分类）
```
将情感分类为正面、负面或中性。

文本："我爱这个产品！它超出了我的期望。"
情感：正面
推理：热情的语言、正面形容词、满意度

文本："当我在上传大文件时，该应用程序会崩溃。"
情感：负面
推理：关于功能的投诉、挫败感指标

文本："它按时送达，与描述相符。"
情感：中性
推理：事实陈述，没有强烈情绪

文本："{user_input}"
情感：
推理：
```

### 2. 思维链推理

#### 实现模式
- 参考 `references/cot-patterns.md` 获取详细的推理框架
- 使用 "让我们逐步思考" 来启动零样本思维链
- 为少样本思维链提供完整的推理轨迹
- 通过采样多个推理路径实现自洽性
- 在推理链中包含验证和确认步骤

#### 思维链模板结构
```
让我们逐步处理：

步骤 1：{将问题分解}
分析：{详细推理}

步骤 2：{识别关键组件}
分析：{组件分析}

步骤 3：{综合解决方案}
分析：{解决方案论证}

最终答案：{有信心的结论}
```

### 3. 提示优化

#### 优化过程
- 使用 `references/optimization-frameworks.md` 获取全面的优化策略
- 在优化尝试之前测量基线性能
- 实施单变量更改以进行准确的归因
- 跟踪指标：准确率、一致性、延迟、token 效率
- 使用统计显著性检验进行 A/B 验证
- 记录优化迭代及其影响

跟踪这些指标：准确率、一致性、token 效率、鲁棒性、安全性。参见 `references/optimization-frameworks.md` 获取测量工具。

### 4. 模板系统

#### 模板设计原则
- 参考 `references/template-systems.md` 获取模块化模板框架
- 使用清晰的变量命名规范（例如，`{user_input}`、`{context}`）
- 实现条件部分以处理不同场景
- 设计基于角色的模板以用于特定用例
- 创建分层模板组合模式

#### 模板结构示例
```
# 系统上下文
您是一个在 {domain} 领域具有 {expertise_level} 经验水平的 {role} 角色。

# 任务上下文
{if background_information}
背景：{background_information}
{endif}

# 指令
{task_instructions}

# 示例
{example_count}

# 输出格式
{output_specification}

# 输入
{user_query}
```

### 5. 系统提示设计

#### 系统提示组件
- 使用 `references/system-prompt-design.md` 获取详细的设计指南
- 定义清晰的角色规范和专业知识边界
- 建立输出格式要求和结构约束
- 包含安全指南和内容政策遵守
- 设置背景信息和领域知识的上下文

#### 系统提示框架
```
您是一位在 {domain} 领域具有 {experience_level} 经验的专家 {role}。

## 核心能力
- 列出特定的能力和专业知识领域
- 定义知识范围和限制

## 行为指南
- 指定交互风格和沟通方法
- 定义错误处理和不确定性协议
- 建立质量标准和验证要求

## 输出要求
- 指定格式期望和结构要求
- 定义内容包含和排除标准
- 建立一致性和验证要求

## 安全和伦理
- 包含内容政策遵守
- 指定偏见缓解要求
- 定义伤害预防协议
```

## 实施工作流

### 工作流 1：根据需求创建新提示

1. **分析需求**
   - 确定任务复杂性和推理需求
   - 确定目标模型的能力和限制
   - 定义成功标准和评估指标
   - 评估是否需要少样本学习或思维链推理

2. **选择模式策略**
   - 使用少样本学习进行分类或转换任务
   - 应用思维链用于复杂推理或多步骤问题
   - 实施模板系统以用于可重用的提示架构
   - 设计系统提示以实现一致的行为要求

3. **起草初始提示**
   - 使用清晰的章节和逻辑流程结构提示
   - 包含相关的示例或推理演示
   - 指定输出格式和质量要求
   - 包含安全指南和约束

4. **验证和测试**
   - 使用至少 3 个输入进行测试：一个成功路径、一个边缘案例、一个对抗性输入
   - 对照定义的成功标准测量准确率和 token 使用情况
   - 一次更改一个变量，重新测试，仅保留改进指标的更改
   - 记录优化决策及其理由

### 工作流 2：优化现有提示

1. **性能分析**
   - 测量当前提示的性能指标
   - 识别失败模式和错误模式
   - 分析 token 效率和响应延迟
   - 评估多次运行的一致性

2. **优化策略**
   - 应用系统 A/B 测试和单变量更改
   - 使用少样本学习改进任务遵循度
   - 实施思维链推理以用于复杂任务组件
   - 优化模板结构以提高清晰度

3. **实施和测试**
   - 使用步骤 1 中的相同测试用例对优化后的提示重新运行
   - 如果准确率 < 基线，则撤销更改并尝试不同的假设
   - 如果准确率 >= 基线但 < 90%，则返回步骤 2 并使用新策略
   - 记录获胜的更改及其测量影响

### 工作流 3：扩展提示系统

1. **模块化架构设计**
   - 将复杂提示分解为可重用组件
   - 创建模板继承层次结构
   - 实现动态示例选择系统
   - 构建自动化质量保证框架

2. **生产集成**
   - 实现提示版本控制和回滚功能
   - 创建性能监控和警报系统
   - 构建自动化测试框架以验证提示
   - 建立更新和部署工作流

## 质量门禁

- 在交付前，在 10 个以上多样化的测试用例上准确率 >90%
- 在 3 次以上重复运行中方差 <5%
- 优雅地处理所有边缘案例和对抗性输入
- 每个测试用例的输出格式都与规范匹配

## 最佳实践

- 一次优化一个变量，以便结果保持可归因
- 保持提示明确说明任务、上下文、约束和输出格式
- 优先选择少量强示例而不是许多重复的示例
- 对抗性输入、边缘案例和成功路径测试提示
- 将长模式详细信息移动到 `references/` 而不是使 `SKILL.md` 膨胀

## 限制和警告

- 不要假设更长的提示更好；额外的细节通常会增加歧义
- 避免在简洁的推理就足够的情况下暴露隐藏的推理需求
- 在声称改进之前，在代表性输入上验证提示
- 因为行为因模型而异，所以模型特定的假设必须明确

## 常见陷阱和解决方案

| 陷阱 | 解决方案 |
|---|---|
| 输出格式错误 | 在提示的末尾添加具体的输出示例 |
| 答案不一致 | 添加 2-3 个少样本示例以显示预期的推理 |
| 虚构 | 添加 "如果不确定，请说'我不知道'" + 约束答案域 |
| 太啰嗦 | 添加明确的字数/句子限制 + "保持简洁"指令 |
| 遗漏边缘案例 | 添加边缘案例少样本示例 |

## 限制

- 在目标模型上测试——能力和 token 限制各不相同
- 将少样本示例限制为 3-5 个以管理上下文使用
- 在生产前使用特定领域的测试用例进行验证
