# 学习

自主分析项目的代码库，以发现开发模式、规范和架构决策，然后为 Claude Code 生成项目规则文件，存储在 `.claude/rules/` 目录下。

## 概述

此技能在两代理架构中充当 **协调器**。它协调整体工作流程：收集项目上下文、将深度分析委托给 `learn-analyst` 子代理、过滤和排序结果、向用户展示发现结果，并将批准的规则持久化到 `.claude/rules/`。

关注点的分离确保分析师以专注的取证提示操作，而协调器管理用户交互和文件持久化。

## 何时使用

在以下情况下使用此技能：

- 用户要求“从该项目中学习”或“理解项目规范”
- 用户希望从现有代码库自动生成 `.claude/rules/` 文件
- 用户要求“提取项目规则”或“发现模式”
- 用户希望 Claude Code 学习项目的编码标准
- 加入新项目后，希望将现有规范文档化
- 在开始大型功能之前，确保 Claude 遵循项目模式

**触发短语：** "从项目中学习"、"提取规则"、"分析规范"、"发现模式"、"生成项目规则"、"学习代码库"、"自动生成规则"

## 说明

### 第一阶段：项目上下文评估

在委托给分析师之前，收集高级项目上下文：

1. **验证项目根目录**：确认当前工作目录是项目根目录（包含 `package.json`、`pom.xml`、`pyproject.toml`、`go.mod`、`.git/` 或类似标记）

2. **检查现有规则**：扫描预存在的规则文件，了解已经记录了什么：

```bash
# 检查现有规则
ls -la .claude/rules/ 2>/dev/null || echo "未找到 .claude/rules/ 目录"
cat CLAUDE.md 2>/dev/null || echo "未找到 CLAUDE.md"
cat AGENTS.md 2>/dev/null || echo "未找到 AGENTS.md"
ls -la .cursorrules 2>/dev/null || echo "未找到 .cursorrules"
```

3. **评估项目规模**：快速了解项目范围：

```bash
# 快速项目概述
find . -maxdepth 1 -type f -name "*.json" -o -name "*.toml" -o -name "*.xml" -o -name "*.gradle*" -o -name "Makefile" -o -name "*.yaml" -o -name "*.yml" | head -20
find . -type f -name "*.ts" -o -name "*.js" -o -name "*.java" -o -name "*.py" -o -name "*.go" -o -name "*.php" | wc -l
```

4. **告知用户**：简要告诉用户发现了什么，并且即将开始分析：
   - "我发现了一个 [TypeScript/NestJS] 项目，包含 [N] 个源文件和 [M] 个现有规则。开始深度分析..."

### 第二阶段：委托给分析师子代理

调用 `learn-analyst` 子代理执行深度代码库分析。

使用 **任务工具** 将分析委托给 `learn-analyst` 代理：

- **代理**：`learn-analyst`
- **提示**："分析当前工作目录中的代码库。遵循完整流程：发现、模式提取、分类和优先级排序。以 JSON 报告的形式返回您的发现。"
- **模式**：同步运行以直接接收 JSON 报告

分析师将返回一个结构化的 JSON 报告，其中包含分类的发现结果。

### 第三阶段：审查和过滤结果

处理分析师的报告：

1. **解析分析师返回的 JSON 报告**
2. **验证发现结果**：确保每个发现结果包含：
   - 清晰的标题
   - 来自至少 2 个文件的证据
   - 影响分数 ≥ 4（丢弃低影响结果）
   - 结构良好的 markdown 内容
3. **与现有规则去重**：将每个发现结果的标题和内容与现有的 `.claude/rules/` 文件进行比较。跳过重复现有规则的结果。
4. **选择前 3 个**：从剩余结果中，按影响分数选择前 3 个。如果过滤后少于 3 个，则展示剩余的所有结果。
5. **如果零个发现结果**：告知用户项目已经很好地记录了，或者没有发现重要的未记录模式。

### 第四阶段：向用户展示

以清晰、结构化的格式向用户展示过滤后的结果：

```
我分析了您的代码库，发现了 N 个值得记录为项目规则的模式：

1. **[规则]** <标题> (影响：X/10)
   <一句话解释>

2. **[规则]** <标题> (影响：X/10)
   <一句话解释>

3. **[规则]** <标题> (影响：X/10)
   <一句话解释>
```

然后使用 **AskUserQuestion** 询问用户确认：

- 提供选项："保存所有 N 个规则"、"让我选择要保存哪些"、"取消 — 不保存任何内容"
- 如果用户希望逐个选择，则逐个展示每个规则并提供 "保存 / 跳过" 选项
- **永远不要自动保存** — 始终需要用户明确批准

### 第五阶段：持久化批准的规则

对于每个批准的规则：

1. **确保目录存在**：

```bash
mkdir -p .claude/rules
```

2. **生成文件名**：使用发现的 `title` 字段转换为连字符命名法：
   - 示例：`"API 响应封装规范"` → `api-response-envelope-convention.md`
   - 避免使用通用名称，如 `rule-1.md` 或 `learned-pattern.md`

3. **检查冲突**：在写入之前，检查是否已存在同名文件：
   - 如果存在，向用户展示差异并询问是否要替换、合并或跳过

4. **写入规则文件**：在 `.claude/rules/` 中创建文件，包含分析师预格式化的内容

5. **向用户确认**：保存后，列出所有创建的文件：

```
✅ 规则保存成功：

  .claude/rules/api-response-envelope-convention.md
  .claude/rules/基于功能的模块组织.md
  .claude/rules/DTO 验证规范.md

这些规则将在未来的会话中自动应用于 Claude Code。
```

## 最佳实践

1. **在项目早期运行**：加入新项目时使用此技能，快速文档化规范
2. **保存前审查**：始终验证生成的规则是否适合您的项目
3. **迭代**：随着项目的发展定期运行此技能 — 可能会出现新模式
4. **保存后编辑**：生成的规则是起点；根据您的具体偏好进行修改
5. **提交规则到 git**：`.claude/rules/` 文件是项目特定的，应进行版本控制，以便整个团队受益

## 限制和警告

### 关键限制

1. **未经确认永不保存**：在写入任何文件之前始终询问用户
2. **仅限项目本地**：仅在当前项目目录的 `.claude/rules/` 中写入，绝不要写入全局路径
3. **只读分析**：分析师子代理不得修改任何项目文件
4. **基于证据**：每个规则都必须有来自代码库的具体证据支持
5. **不凭空捏造**：不要编造代码库中实际不存在的模式
6. **尊重现有规则**：未经用户明确批准，不要覆盖现有规则
7. **保持规则专注**：每个规则文件应针对一个特定的规范或模式

### 限制

- **大型单体仓库**：在非常大的代码库上分析可能需要更长时间。分析师扫描代表性样本，而不是每个文件。
- **多语言项目**：在多语言项目中，按语言生成规则。确保规则标题表明语言范围。
- **现有规则冲突**：如果项目已经具有全面的 `.claude/rules/`，此技能可能发现很少或没有新模式。这是预期的。
- **动态模式**：某些模式仅在运行时出现（例如，中间件排序）。此技能专注于静态代码库分析。

## 示例

### 示例 1：从 NestJS 项目中学习

**用户请求：** "从该项目中学习"

**第一阶段 — 上下文评估：**
```
发现：TypeScript/NestJS 项目，包含 142 个源文件
现有规则：.claude/rules/ 中 0 个文件
开始深度分析...
```

**第四阶段 — 展示：**
```
我分析了您的代码库，发现了 3 个值得记录为项目规则的模式：

1. **[规则]** 基于功能的模块组织 (影响：9/10)
   所有模块遵循 src/modules/<功能>/，包含控制器、服务、DTO、实体子目录。

2. **[规则]** DTO 验证规范 (影响：8/10)
   所有 DTO 使用 class-validator 装饰器，并遵循 Create/Update 命名模式。

3. **[规则]** 错误响应封装 (影响：7/10)
   所有 API 错误返回 { statusCode, message, error } 一致的封装格式。

保存所有 3 个规则？ [保存所有 / 让我选择 / 取消]
```

**第五阶段 — 持久化：**
```
✅ 规则保存成功：

  .claude/rules/基于功能的模块组织.md
  .claude/rules/DTO 验证规范.md
  .claude/rules/错误响应封装.md

这些规则将在未来的会话中自动应用于 Claude Code。
```

### 示例 2：具有现有规则的项目

**用户请求：** "发现项目模式"

**第一阶段 — 上下文评估：**
```
发现：Java/Spring Boot 项目，包含 87 个源文件
现有规则：.claude/rules/ 中 4 个文件
开始深度分析...
```

**第三阶段 — 过滤后：**
```
分析师发现了 6 个模式，但 4 个与您的现有规则重复。
去重后，剩余 2 个新模式：

1. **[规则]** 仓库方法命名 (影响：7/10)
   所有自定义仓库方法使用 findBy/existsBy/countBy 前缀规范。

2. **[规则]** 集成测试数据库策略 (影响：6/10)
   集成测试使用 @Testcontainers 与 PostgreSQL 和 @Sql 用于固定装置。

保存这些 2 个规则？ [保存所有 / 让我选择 / 取消]
```
