# Bug Fix Brief (BFB)

## 概述

该技能生成一个 Bug Fix Brief (BFB)：一个结构化的文档，位于 `docs/bfb/` 目录中，统一捕获每个 Bug 修复的根因、复现步骤、修复选项和检查清单。

## 何时使用

- 用户要求创建 BFB
- 用户希望以结构化的方式记录 Bug 修复
- 在识别出 Bug 的根因并实施修复之前

**触发条件：** "create BFB", "document bug", "bug fix brief", "document fix"

## 说明

### 第一阶段：收集信息

检查现有编号：
```bash
ls docs/bfb/ 2>/dev/null || echo "目录不存在"
```

向用户询问：
- BFB 编号（或建议下一个连续编号）
- 简洁的标题（3-5 个词，使用连字符命名法）
- 问题链接（例如 #1287）
- 环境（Prod/Stg/Dev）+ 版本
- 观察到的行为与预期行为
- 导致问题的文件/函数/行

### 第二阶段：生成模板

完成完整的 BFB 模板：

```markdown
## BFB-XXX: [标题]

**参考：** [问题链接]
**环境：** [环境] `vX.Y.Z`
**日期：** YYYY-MM-DD

---

### 1. Bug
- **观察到的行为：** [错误行为]
- **预期行为：** [正确行为]

### 2. 复现步骤
```
1. ...
2. ...
→ [错误/输出]
```

### 3. 根因
`path/file.ext` — `function()` @ 行 N
[为什么会发生，最多 3 行]

### 4. 决策
| 选项 | 修复 | 选择 |
|------|------|------|
| A | [描述] | ✅/❌ |
| B | [描述] | ✅/❌ |

**理由：** [为什么]

### 5. 修复
- [ ] [变更 1]
- [ ] [测试]
- [ ] [验证复现]

### 6. 备注
[重复模式、链接、警告]
```

### 第三阶段：确认

显示生成的 BFB，并使用 AskUserQuestion 询问：
- "创建 BFB"
- "编辑后再创建"
- "取消"

### 第四阶段：写入磁盘

仅经批准后：
```bash
mkdir -p docs/bfb
```

写入 `docs/bfb/BFB-XXX-title.md`

## 示例

**输入：** "create BFB for login email null crash"

**最终输出：**
```markdown
## BFB-042: Login crash with null email

**参考：** #1287
**环境：** Prod `v2.4.1`
**日期：** 2026-05-02

---

### 1. Bug
- **观察到的行为：** App 在邮箱字段为空时崩溃
- **预期行为：** 显示错误消息 "Email required"

### 2. 复现步骤
```
1. 打开登录界面
2. 不输入邮箱直接点击 "Login"
→ NullPointerException @ AuthManager.kt:34
```

### 3. 根因
`AuthManager.kt` — `validateEmail()` @ 行 34
缺少对 email.trim() 的空值检查

### 4. 决策
| 选项 | 修复 | 选择 |
|------|------|------|
| A | 添加安全调用 `?.` | ✅ |
| B | 使用 Result 类型重构 | ❌ |

**理由：** 选项 A 最小化改动，无影响。

### 5. 修复
- [ ] 添加 `email?.trim()?.isNotEmpty() == true`
- [ ] 测试 `validateEmail_null_returnsFalse()`
- [ ] 验证复现

### 6. 备注
- 检查其他表单的空值检查

## 最佳实践

1. **连续编号**：BFB-001, BFB-002，无空号
2. **简洁标题**：3-5 个词，文件名使用连字符命名法
3. **根因**：精确的文件、函数、行
4. **2+ 修复选项**：包含优缺点和理由
5. **可验证的检查清单**：每项都必须可测试

## 限制和警告

- **需要确认**：写入前必须询问
- **根因最多 3 行**：保持简洁
- **目录 `docs/bfb/`**：不存在时需创建
