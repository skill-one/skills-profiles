# 构建最小可行产品

按照 `docs/product-roadmap.md` 中的任务顺序依次执行每个任务，直至所有任务都被标记为完成。

## 设置

首先阅读 `docs/product-roadmap.md` — 它是构建内容和顺序的权威来源。`docs/prd.md` 是其背后的技术规范；`docs/design.md` 包含视觉设计令牌；`docs/product-vision.md` 包含产品策略。不要一次性加载这些文档 — 每个阶段会列出需要阅读的具体参考部分，以及任务备注行指向的内容。如果 `docs/product-roadmap.md` 或 `docs/prd.md` 不存在，请停止并提示用户先运行 **产品规划** 技能（属于 BuilderOS：https://github.com/BuildGreatProducts/builder-os）。

## 工作循环

重复执行直至路线图中的所有任务完成：

1. **找到第一个未勾选的任务** (`- [ ]`)。任务顺序是经过精心设计的 — 不要跳过任务。
2. **阅读任务需求** — 其文件和备注行，以及当前阶段的参考部分（如果本次会话尚未阅读）。
3. **按指定要求实现任务** — 文件路径、包名和配置值都是经过深思熟虑的。遵循仓库的 `CLAUDE.md`/`AGENTS.md` 指南：实现满足任务的最简单方案，不添加推测性功能，仅进行精准修改。
4. **在继续之前进行测试和验证。** 在任务备注行末尾运行验证步骤，运行应用程序，运行现有测试，并为新逻辑添加测试。如果验证失败，请先修复 — 不要标记失败的任务为完成或以损坏的应用程序开始下一个任务。
5. **标记任务完成** — 将 `- [ ]` 改为 `- [x]` 并更新标题状态行 (`**Status:** X/Y 任务完成`, `**当前阶段:** ...`)。
6. **在每个阶段边界处：** 运行应用程序端到端并确认阶段的 **目标** 可实现且可演示，然后才能开始下一个阶段。这里不使用 git 或 GitHub actions — 版本控制会在每个阶段完成后一次性进行。

## 规则

- PRD 的技术栈选择是最终决定 — 请按指定实现，不要替换替代方案。
- 视觉样式来自 `docs/design.md` 令牌 — 不要自行发明颜色、字体或间距。如果 `docs/design.md` 不存在，请遵循路线图的 **基础阶段** 指导：在开始样式工作前提示用户先运行 **设计系统** 技能。
- 如果任务含糊不清或与 PRD 冲突，请检查其引用的 PRD 部分；如果仍然不清楚，请提出一个具体问题而不是猜测。
- 如果必要的工作未在任何任务中涵盖，请提出并建议添加任务 — 不要在沉默中扩大范围。
- 持续进行直至 `**Status:** Y/Y 任务完成`：所有任务都被标记，每个阶段都经过验证，魔法时刻端到端运行正常。
- 在所有阶段完成前不使用 git 或 GitHub actions（初始化、提交、分支、推送、PR） — 版本控制是收尾步骤，不是工作循环的一部分。

## 收尾

当所有任务都被标记完成且魔法时刻已端到端验证后：

1. **初始化 git 并创建初始提交。** 如果项目还不是 git 仓库，请运行 `git init`，为技术栈添加合理的 `.gitignore`（依赖项、构建输出、`.env` 文件 — 不要提交密钥），并使用初始提交信息命名产品并注明 MVP 构建已完成。如果项目已经是 git 仓库，请在当前分支上提交构建。
2. **询问用户是否要连接远程仓库。** 不要自行创建或推送任何内容 — 请询问："要让我将此连接到远程仓库吗？我可以在 GitHub（公开或私有）上创建一个，或连接现有 URL。" 如果同意，将其设置为 `origin`，推送并确认推送成功。如果不同意，保留本地状态并告知他们提交已准备好随时推送。
