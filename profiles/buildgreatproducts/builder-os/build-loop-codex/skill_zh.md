# Codex 构建循环

质量门控功能工作：没有东西能在“它能编译”时就发布——每个增量都会被构建、审查、端到端测试并修复，然后用户才会听到“完成”的消息。

## 工作来源

- **存在计划文件**（路线图、重构计划或带有 `- [ ]` 复选框的任务列表——在代码库中搜索）：处理第一个未勾选的任务。任务是有意排序的——永远不要跳过。如果计划引用了规范文档，只阅读与当前任务相关的部分。
- **没有计划（或请求超出其范围）：** 根据用户的提示构建。将其表述为一个可验证的目标，并附带 2-4 个成功标准，在构建前通过一条消息确认范围。

## 循环

每个任务（或每个提示的功能）运行一次。直到每个步骤都通过，才不推进。

1. **构建。** 精确实现任务指定的内容。最简单的满足要求的实现，手术刀式的修改，没有推测性范围。匹配现有项目的约定。

2. **审查。** 运行 **`/review`** 并选择 **“审查未提交的更改”**。如果更改涉及认证、支付、用户输入或数据访问，通过 **“自定义审查说明”**（例如“关注安全漏洞和未验证的输入”）进行第二次检查。在范围内修复所有发现的问题——错误、安全问题、边缘情况、性能、你修改的文件中的样式。如果项目有设计系统规范（设计令牌文件、DESIGN.md、主题配置），请将 UI 更改与它进行对照——不要硬编码颜色、类型或间距以绕过令牌。对于未触及的代码中的预存问题，在报告中注明而不是默默修复。重新运行 `/review` 直到干净。如果发现的问题与任务或规范相矛盾，规范优先——标记分歧。

3. **端到端测试。** 运行任务的验证步骤（或成功标准）。运行完整的测试套件——之前通过的所有内容仍然必须通过。为新的逻辑添加测试。然后像用户一样使用功能：运行应用程序，执行真实的流程，包括空、加载和错误状态。

4. **修复。** 测试发现的问题会回到循环：修复 → `/review` → 重新测试。永远不要将失败的任务标记为完成；永远不要在应用程序损坏的情况下开始下一个任务。

5. **继续。** 将任务标记为 `- [x]`，更新计划中的任何进度/状态行，并循环到下一个任务，直到请求的范围完成。

6. **报告。** 完成时，告诉用户：构建了什么和计划进度，修复的审查发现和任何推迟的事项，如何验证（测试+流程执行），以及下一步需要他们注意什么。诚实地说明任何不稳定或部分验证的事项。

## 规则

- 跳过审查或未经测试的工作 = 未完成的工作。
- 不要重新审议计划决策；如果任务似乎错误，问一个具体的问题，而不是猜测。
- 发现没有任务涵盖的工作？将其呈现出来并提出一个任务——永远不要默默扩大范围。
