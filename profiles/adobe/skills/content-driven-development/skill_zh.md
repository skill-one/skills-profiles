# 内容驱动开发 (CDD)

为 AEM Edge Delivery Services 配置内容驱动开发 (CDD) 工作流。此工作流确保代码是针对真实内容构建的，并且作者友好的内容模型。

**关键提示：** 在开始编写或修改代码之前，请务必先识别或创建您将用于测试更改的内容。

## 使用此技能的场景

使用 CDD 进行所有 AEM 开发任务：
- ✅ 创建新模块
- ✅ 修改现有模块（结构或功能更改）
- ✅ 核心装饰功能更改
- ✅ 需要验证的 Bug 修复
- ✅ 任何影响作者创建或结构化内容方式的代码

**不要**用于：
- 仅文档更改
- 不影响作者环境的配置更改
- 尚未需要代码更改的研究任务

## 哲学思想

内容驱动开发优先于在编写代码之前创建或识别测试内容。这确保了：
- 代码是针对真实内容构建的
- 作者友好的内容模型
- 开发过程中的验证

**可选：理解 CDD 原则**

如果：
- 用户询问关于“内容优先”方法的原因
- 您需要理解 CDD 决策背后的推理
- 您不确定是否应优先考虑作者体验还是开发者体验

请阅读 [references/cdd-philosophy.md](references/cdd-philosophy.md)。否则：请遵循以下工作流步骤。

## 第 0 步：创建待办事项列表

**第一步：** 使用 TodoWrite 工具创建包含以下 8 项任务的待办事项列表：

1. **启动开发服务器**（如果未运行）
   - 成功：开发服务器正在运行，可以访问 http://localhost:3000

2. **分析和计划**
   - 成功：文档化清晰的理解 + 定义了验收标准

3. **设计内容模型**
   - 成功：文档化并验证了内容结构

4. **识别/创建测试内容**
   - 成功：可访问的测试内容覆盖所有场景

5. **实现**
   - 成功：功能在所有视口下均可工作

6. **检查和测试**
   - 成功：所有检查均通过

7. **最终验证**
   - 成功：所有验收标准均已满足，一切正常

8. **发布**
   - 成功：创建包含预览链接的 PR 用于验证

**当待办事项列表完成时：** 创建包含所有 8 项任务的待办事项列表

## 第 1 步：启动开发服务器

**检查开发服务器是否正在运行：**

```bash
curl -s -o /dev/null -w "%{http_code}" http://localhost:3000
```

预期：`200`（服务器正在运行）或连接错误（服务器未运行）

**如果未运行，启动它：**

```bash
aem up --no-open --forward-browser-logs
```

**注意：**
- 如果可能，请在后台运行（开发服务器需要保持运行状态）
- 需要 AEM CLI 全局安装：`npm install -g @adobe/aem-cli`
- 替代方案：`npx -y @adobe/aem-cli up --no-open --forward-browser-logs`

**重要提示：** 检查命令输出中的错误。常见问题：
- 端口 3000 已被占用
- AEM CLI 未安装
- 配置错误

**启动后，验证其是否正在运行：**

```bash
curl -s -o /dev/null -w "%{http_code}" http://localhost:3000
```

预期：`200`

**成功标准：**
- ✅ 开发服务器正在运行
- ✅ http://localhost:3000 返回 200
- ✅ 服务器启动输出中没有错误

**当待办事项完成时：** 开发服务器确认正在运行且可访问

---

## 第 2 步：分析和计划

**调用：** analyze-and-plan 技能

**提供：**
- 用户任务描述
- 屏幕截图、设计文件或现有 URL（如果可用）以匹配设计

**analyze-and-plan 技能将：**
- 引导您完成特定任务的特定分析
- 帮助定义验收标准
- 如果提供，则分析视觉设计/模型
- 创建文档化的分析以供参考

**成功标准：**
- ✅ 需求分析
- ✅ 定义了验收标准
- ✅ 分析已记录到文件以供后续步骤使用

**当待办事项完成时：** 分析已记录且验收标准已定义

---

## 第 3 步：设计内容模型

**如果：** 仅进行 CSS 更改且不影响内容结构，则跳过

**调用：** content-modeling 技能

**提供：**
- 第 2 步的分析（内容需求、作者输入）
- 模块名称和用途

**content-modeling 技能将：**
- 设计表格结构（行、列、语义格式）
- 验证最佳实践（每行 4 个单元格、语义格式）
- 为作者记录内容模型

**成功标准：**
- ✅ 设计了内容模型（定义了表格结构）
- ✅ 验证了最佳实践
- ✅ 记录了内容模型

**当待办事项完成时：** 内容模型已设计和记录

---

## 第 4 步：识别/创建测试内容

**目标：** 以可访问的测试内容 URL（覆盖所有测试场景）结束此步骤

**根据您的具体情况选择最佳路径：**

---

### 选项 A：用户提供的测试 URL

**使用场景：** 用户已经拥有内容并提供了 URL

**操作步骤：**
1. 验证 URL 加载：`curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/path`
2. 预期：`200` 状态
3. 记录 URL
4. 标记完成

---

### 选项 B：新模块（无现有内容）

**使用场景：** 构建一个尚不存在的新模块

**操作步骤：**
1. 跳过搜索（目前没有内容可以查找）
2. 使用以下方法之一创建测试内容：

**方法 1：CMS 内容（推荐）**
1. 要求用户在他们的 CMS（Google Drive/SharePoint/DA/Universal Editor）中创建内容
2. 提供第 3 步的内容模型作为参考
3. 等待用户提供 URL
4. 验证：`curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/path`
5. 预期：`200` 状态

> **使用 DA：** 如果您需要将 HTML 内容编程方式推送到 DA（而不是要求用户创建内容），请首先调用 **da-auth** 技能以获取有效的 `DA_TOKEN`，然后使用 DA Admin API (`POST https://admin.da.live/source/{org}/{repo}/{path}`) 推送内容并触发预览。

**方法 2：本地 HTML（临时）**
1. 在 `drafts/tmp/{block-name}.plain.html` 中创建 HTML 文件
2. 跟随第 3 步内容模型的表格结构
3. 阅读 [references/html-structure.md](references/html-structure.md) 获取本地 HTML 文件格式指南
4. 重新启动开发服务器：`aem up --html-folder drafts --no-open --forward-browser-logs`
5. 验证：`curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/drafts/tmp/{block-name}`
6. 预期：`200` 状态
7. **注意：** 用户必须在 PR 之前创建 CMS 内容（需要预览链接）

---

### 选项 C：现有模块

**使用场景：** 修改、修复或样式化现有模块

**操作步骤：**

**首先：搜索现有内容**
1. 调用 find-test-content 技能
2. 提供：模块名称，开发服务器 URL（可选，默认为 localhost:3000）

**find-test-content 将执行：**
- 搜索包含模块的现有内容页面
- 自动检测并报告所有变体
- 报告：包含实例计数和变体信息的 URL

**然后：评估搜索结果**

**如果找到足够的内容：**
1. 记录 URL
2. 验证 URL 加载：`curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/path`
3. 预期：`200` 状态
4. 标记完成

**如果未找到内容或覆盖不足：**
1. 使用选项 B 中的方法创建额外的测试内容
2. 验证 URL 加载
3. 标记完成

---

**成功标准：**
- ✅ 可访问的测试内容 URL（覆盖所有测试场景）
- ✅ 内容覆盖所有测试场景（变体、边缘情况）
- ✅ 验证 URL（返回 200）

**当待办事项完成时：** 识别/创建了测试内容并验证

---

## 第 5 步：实现

**调用：** building-blocks 技能

**提供：**
- 第 3 步的内容模型（如果适用）
- 第 4 步的测试内容 URL
- 第 2 步的分析/需求
- 更改类型：新模块、现有模块修改、仅 CSS 等

**building-blocks 技能将：**
- 根据更改类型引导实现方法
- 处理 JavaScript 装饰（如果需要）
- 处理 CSS 样式（移动优先、响应式）
- 确保开发过程中在浏览器中进行迭代测试

**成功标准：**
- ✅ 代码实现完成
- ✅ 功能在所有视口（移动、平板、桌面）下均可工作
- ✅ 无控制台错误

**当待办事项完成时：** building-blocks 技能报告实现完成并在视口下工作

---

## 第 6 步：检查和测试

**操作步骤：**

```bash
npm run lint
```

**如果存在检查错误：**
1. 修复问题（使用 `npm run lint:fix` 自动修复可修复的问题）
2. 重新运行检查直到干净

**运行现有测试：**

```bash
npm test
```

**注意：** 单元测试是可选的，并且仅适用于逻辑密集型实用程序。testing-blocks 技能（在第 5 步由 building-blocks 调用）处理浏览器测试。此步骤捕获任何剩余的检查错误并运行项目的测试套件。

**成功标准：**
- ✅ `npm run lint` 通过且无错误
- ✅ `npm test` 通过（如果存在测试）

**当待办事项完成时：** 所有检查和测试均通过

---

## 第 7 步：最终验证

**操作步骤：**

1. **回顾第 2 步的验收标准**
   - 阅读在第 2 步创建的分析文档
   - 检查每个验收标准是否已满足

2. **最终浏览器检查**
   - 在浏览器中加载测试内容 URL
   - 检查移动、平板和桌面视口
   - 验证无控制台错误
   - 确认无视觉回归

3. **验证无回归**
   - 如果修改现有模块：测试现有变体是否仍然工作
   - 如果修改核心功能：检查几个页面

**成功标准：**
- ✅ 满足第 2 步的所有验收标准
- ✅ 在所有视口下均可工作
- ✅ 无控制台错误
- ✅ 现有功能无回归

**当待办事项完成时：** 验证了所有验收标准且未发现回归

---

## 第 8 步：发布

**操作步骤：**

1. **创建特性分支（如果尚未在分支上）：**
   ```bash
   git checkout -b block-name
   ```

2. **仅暂存特定文件：**
   ```bash
   git add blocks/{block-name}/{block-name}.js blocks/{block-name}/{block-name}.css
   # 仅添加您工作的文件 - 绝对不要使用 `git add .`
   ```

3. **使用常规提交格式提交：**
   ```bash
   git commit -m "feat(block-name): 添加新模块"
   ```
   在提交信息中包含相关详细信息，并在页脚中添加代理归因（代理添加 `Co-authored-by: cursor <noreply@cursor.com>`）

4. **推送至特性分支：**
   ```bash
   git push origin HEAD
   ```

5. **创建包含预览链接的 PR：**
   - 分支预览 URL 格式：`https://{branch}--{repo}--{owner}.aem.page/{path}`
   - 示例：`https://carousel--aem-skills-demo--shsteimer.aem.page/`
   - **必需：** 在 PR 描述中包含预览链接（用于自动 PSI 检查）
   - 如有必要，添加多个预览链接（例如，不同变体、边缘情况）

   **确定是否需要草稿 PR：**

   创建 **草稿 PR** 当：
   - ✅ 仅本地测试内容存在用于新功能/变体
   - ✅ 测试内容展示了尚未在 CMS 中的新功能
   - ✅ 您需要用户在最终验证之前创建 CMS 内容

   创建 **常规 PR** 当：
   - ✅ 所有测试内容存在于 CMS 且可预览
   - ✅ 更改仅影响现有内容（回归可以通过现有 CMS 内容测试）

   **草稿 PR 的流程：**
   1. 使用 `gh pr create --draft` 创建草稿 PR
   2. 包含现有内容预览链接（如果适用，用于回归测试）
   3. 在 PR 描述中包含下一步操作（见模板）：
      - 描述本地使用的测试内容及其覆盖的场景
      - 建议创建相同/类似内容并预览，并将链接添加到 PR
      - 步骤应简明但可操作，供任何审阅者参考
   4. 指示用户按照以下步骤创建 CMS 内容：
      - 在浏览器中打开本地测试内容：`http://localhost:3000/drafts/tmp/[test-file]`
      - 右键单击 AEM Sidekick 扩展
      - 点击“查看文档源”选项
      - 使用复制按钮复制文档内容
      - 粘贴到 Word/Google Docs/文档作者（对于 UE：用作指南，直接复制/粘贴无效）
      - 预览 CMS 内容
   5. 用户将预览链接添加到 PR 描述并标记 PR 准备审查（或代理使用用户输入）

**PR 描述模板：**

使用此模板为所有 PR（包括所有相关预览链接并按需调整）：

```markdown
## 描述
简要描述更改

[如果存在问题]
修复 #<gh-issue-id>

测试 URL：

[重复所有相关测试 URL]
- 之前：https://main--{repo}--{owner}.aem.page/{path}
- 之后：https://{branch}--{repo}--{owner}.aem.page/{path} 

[如果仅本地测试内容（草稿 PR）：]

此 PR 目前为 **草稿**，等待创建 CMS 测试内容。

### 下一步操作：

[在此处添加相关步骤]
```

**成功标准：**
- ✅ 提交的更改具有正确的消息格式和归因
- ✅ 推送到特性分支（不是 main）
- ✅ 创建了包含描述中预览链接的 PR

**当待办事项完成时：** PR 已创建并准备审查

## 相关技能

- **analyze-and-plan**：在第 2 步中调用，用于需求分析和验收标准
- **content-modeling**：在第 3 步中调用，用于设计内容模型
- **da-auth**：在 DA 或编程方式触发 DA 预览之前获取有效的 Adobe IMS token — 在第 4 步开始时调用
- **find-test-content**：在第 4 步选项 C 中调用，用于查找现有内容
- **building-blocks**：在第 5 步中调用，用于实现
- **testing-blocks**：由 building-blocks 在第 5 步中调用，用于浏览器测试
- **block-collection-and-party**：用于查找类似模块和参考实现

## 应避免的反模式

违反 CDD 原则的常见错误：
- ❌ 在了解内容模型之前开始编写代码
- ❌ 在看到真实示例之前假设内容结构
- ❌ 创建对作者不友好的内容模型
- ❌ 为了节省时间而跳过内容创建（后期会花费更多时间）
