# 内容创作分析

确定每个内容序列的创作方式：默认内容还是特定模块。

## 使用此技能的场景

在以下情况下使用此技能：
- 您拥有页面结构，其中包含内容序列（来自identify-page-structure技能）
- 您拥有模块清单（本地 + Block Collection）
- 准备按照David的模型进行创作决策

**由以下技能触发：** page-import技能（第3步）

## 前置条件

从identify-page-structure技能中，您需要：
- ✅ 带有样式说明的部分边界
- ✅ 每个部分的序列内容（中性描述）
- ✅ 模块清单（本地 + 带有目的的Block Collection）
- ✅ screenshot.png用于视觉参考

## 相关技能

- **page-import** - 触发此技能的协调器
- **identify-page-structure** - 提供部分结构和模块清单
- **content-modeling** - 当模块选择不明确时，此技能会触发它
- **block-collection-and-party** - 此技能用于验证模块
- **generate-import-html** - 使用此技能的输出来创建HTML

## **重要提示：第3步e执行触发条件**

完成第3步（分析所有序列）后，如果满足以下条件，您**必须**执行第3步e：
- ✅ 至少有一个部分包含恰好一个序列，该序列变成了一个模块
- ✅ 该部分具有与identify-page-structure不同的背景样式

如果没有部分满足这些条件 → 跳过第3步e
如果有任何部分满足这些条件 → 为每个符合条件的部分执行第3步e

## 内容创作分析工作流

**背景：** 现在您拥有：
- 带有样式的部分边界
- 每个部分的序列内容
- 可用的模块调色板

**对于每个内容序列，请按照以下强制流程操作：**

---

### 第3步a：强制执行 - 默认内容检查（首先！）

**问题：** "作者能否在Word/Google Docs中通过正常输入创建此内容？"

**默认内容意味着：**
- ✅ 标题、段落、列表
- ✅ 文本中的内联图片
- ✅ 简单引号
- ✅ 只是...输入内容

**不是默认内容意味着：**
- ❌ 重复结构化模式（卡片网格、功能列表）
- ❌ 交互式组件（手风琴、选项卡、轮播）
- ❌ 复杂布局（并排列、分割内容）
- ❌ 需要特定结构进行装饰

**决策：**
- 如果是（可以正常输入）→ **标记为默认内容，完成** ✅
- 如果不是（需要结构）→ **继续执行第3步b**

**示例：**
```
"居中大型标题，段落，两个按钮"
→ 作者能否正常输入标题、段落、链接？是
→ 决策：默认内容 ✅

"居中两个按钮"
→ 作者能否正常输入两个链接？是
→ 决策：默认内容 ✅

"网格中的四个项目，每个项目带有图片、标题、描述"
→ 作者能否正常输入？否 - 需要网格结构
→ 决策：继续执行第3步b ➡️

"可展开的问题和答案"
→ 作者能否正常输入？否 - 需要交互/装饰
→ 决策：继续执行第3步b ➡️
```

---

### 第3步b：模块选择（仅当不是默认内容时）

**在模块清单上下文中询问：** "作者会选择哪个可用模块来创建此内容？"

**决策树：何时触发content-modeling**

**明显匹配（不要触发content-modeling）：**

模式与模块目的1:1匹配：
- "带图片/文本的项目网格" + 看到"cards"模块 → 使用它 ✅
- "可展开的问题" + 看到"accordion"模块 → 使用它 ✅
- "选项卡内容面板" + 看到"tabs"模块 → 使用它 ✅
- "并排内容" + 看到"columns"模块 → 使用它 ✅
- "旋转图片" + 看到"carousel"模块 → 使用它 ✅

**明显匹配的标准：**
- 内容描述与模块目的完全匹配
- 结构没有歧义
- 模块存在于清单中

**不明确匹配（触发content-modeling）：**

不确定使用哪个模块：
- "三个带图片的项目" - 可以是cards？可以是columns？→ 触发
- "带图标的特性列表" - cards？自定义列表模块？→ 触发
- "带照片的客户引言" - 引言模块？cards？证言模块？→ 触发

清单中缺失：
- 内容需要结构，但没有匹配的模块 → 触发
- content-modeling可以推荐规范模型或建议创建自定义模块

复杂的创作考虑：
- "英雄式内容，但位于页面中间" → 触发
- "卡片式项目，但只有两个" → 触发
- 需要作者创作模型验证 → 触发

**不明确匹配的标准：**
- 多个模块可能适用
- 没有明显的模块匹配
- 需要创作模型验证
- 可能需要创建自定义模块

---

### 第3步c：验证模块是否存在（如果需要）

**仅当模块不在Block Collection公共集中时：**

触发**block-collection-and-party**技能来：
- 确认模块存在
- 获取实时示例URL
- 审查内容模型

---

### 第3步d：获取模块HTML结构（生成HTML之前）

**关键点：** 在下一个技能中生成任何HTML之前，获取所有将要使用的模块的预装饰HTML结构。

```bash
# 获取每个模块的结构示例
node .claude/skills/block-collection-and-party/scripts/get-block-structure.js cards
node .claude/skills/block-collection-and-party/scripts/get-block-structure.js tabs
node .claude/skills/block-collection-and-party/scripts/get-block-structure.js accordion
node .claude/skills/block-collection-and-party/scripts/get-block-structure.js columns
```

**为什么这可以防止错误：**
- 显示确切的行/列结构（例如，cards：每个卡片=1行，2列）
- 揭示所有变体（例如，“Cards” vs “Cards (无图片)）
- 显示干净的HTML，没有装饰
- 防止第1个HTML生成错误：结构错误

**使用输出来：**
1. 了解每行应有多少列
2. 看图片与内容的位置
3. 将您的内容与正确的变体匹配
4. 生成与预期结构完全匹配的HTML

---

### 第3步输出格式

**所有序列的完整分析：**

```

  - 序列1：居中大型标题，段落，两个行动号召按钮

    → 备注：突出样式是CSS问题

  - 序列2：两个图片并排
    → 决策：columns模块（2列）

    → 决策：默认内容
    → 原因：只是一个标题 - 作者输入它

    → 原因：重复结构化模式，需要模块

  - 序列3：居中两个按钮

  - 序列1：眉部文本，标题，段落，垂直堆叠的按钮

    → 原因：作者正常输入文本和链接

  - 序列1：带三个可切换内容面板的选项卡导航
    → 决策：tabs模块

    → 明显匹配，清单中有"tabs"模块
```

---

### 第3步e：验证部分样式（仅限单模块部分）

**⚠️ 执行触发条件：** 此步骤在完成第3步后执行。如果且仅当满足以下条件时执行此步骤：
- ✅ 您已完成第3步（识别了哪些序列变成了模块）
- ✅ 至少有一个部分包含恰好一个序列，该序列变成了一个模块
- ✅ 该部分具有与identify-page-structure不同的背景样式

如果没有部分满足这些条件 → 完全跳过第3步e，继续执行下一个技能

如果有任何部分满足这些条件 → 您必须为每个符合条件的部分执行以下所有子步骤

---

**为什么此验证很重要：**

当部分包含单个模块时，背景样式可能是：
- **模块特定设计**（例如，带有深色背景图片的英雄）→ 不要添加section-metadata
- **部分容器样式**（例如，深色部分带有tabs模块）→ 添加section-metadata

如果没有验证，我们可能会添加不必要的section-metadata，这与模块样式冲突或使创作更复杂。

**包含多个序列的部分：** 始终保留section-metadata（样式适用于所有内容，在第3步e中未验证）

---

**对于每个恰好包含一个模块的部分，执行所有这些子步骤：**

**子步骤1：识别候选部分**

查看您的第3步输出。找到以下部分：
- 部分包含恰好1个内容序列
- 该序列变成了一个模块（不是默认内容）
- 部分具有与identify-page-structure不同的背景样式

**示例：**
```
部分1（深蓝色）：
  - 序列1：大型居中标题，段落，两个行动号召按钮
    → 决策：Hero模块

部分3（灰色）：
  - 序列1：带三个可切换面板的选项卡导航
    → 决策：Tabs模块
```

---

**子步骤2：对于每个候选部分，检查screenshot.png**

打开screenshot.png并检查部分的外观。

**提出这些问题：**

**Q1：背景是图片（照片、渐变、插图）吗？**
- 如果是 → 可能是模块特定设计
- 如果不是（纯色）→ 继续到Q2

**Q2：内容填充了彩色区域边缘，还是内容周围有可见的部分填充？**
- 边缘填充（全出血）→ 可能是模块特定设计
- 内容周围有可见填充 → 可能是部分容器样式

**Q3：模块类型通常具有自己的背景样式吗？**
- Hero，横幅，全宽行动号召 → 通常有自己的背景
- Tabs，accordion，cards，columns → 通常使用部分背景

---

**子步骤3：做出决策**

根据您的分析，为每个单模块部分做出决策：

**跳过section-metadata如果：**
- 背景是图片/渐变（模块特定）
- 内容是全出血/边缘填充（可见部分填充）
- 模块类型通常具有内在背景（hero，banner）

**保留section-metadata如果：**
- 背景是纯色，有可见部分填充
- 模块类型通常继承部分样式（tabs，cards，accordion）
- 样式明显提供容器上下文（不是模块设计）

---

**子步骤4：记录您的决策**

对于每个验证的部分，记录：
- 部分编号
- 模块类型
- 背景分析（图片 vs 纯色，全出血 vs 填充）
- 决策（保留或跳过section-metadata）
- 原因

**示例输出：**
```
已验证部分：

部分1（深蓝色）：
  - 模块：Hero
  - 背景：全宽深蓝色渐变图片
  - 布局：边缘填充，无可见部分填充
  - 决策：跳过section-metadata
  - 原因：背景是hero的设计，不是部分样式

部分3（灰色）：
  - 模块：Tabs
  - 背景：纯灰色（#f5f5f5）
  - 布局：内容居中，有可见填充（两侧约80px）
  - 决策：保留section-metadata style="grey"
  - 原因：部分为tabs模块提供容器样式
```

---

**不确定时：**

如果您不确定背景是模块特定还是部分范围：
- **默认保留section-metadata**（更安全，作者可以删除而不是添加）
- **在您的文档中添加注释**解释模糊之处
- 考虑向用户寻求指导

---

**第3步e完成检查清单：**

在继续下一个技能之前，验证您已完成：
- ✅ 识别了所有单模块部分，具有背景样式
- ✅ 检查了每个候选部分的原始screenshot
- ✅ 对每个候选部分回答了Q1、Q2、Q3
- ✅ 为每个候选部分做出了跳过/保留决策
- ✅ 记录了每个决策的原因
- ✅ 更新了部分样式说明，包含验证决策
- ✅ 传递了这些输出到generate-import-html技能

---

## 最终输出

此技能提供完整的内容创作分析：

**1. 所有序列的创作决策：**
- 每个序列标记为DEFAULT CONTENT或特定模块名称
- 记录了原因

**2. 获取模块结构：**
- 所有将使用的模块的HTML结构示例

**3. 部分样式验证（如果适用）：**
- 更新了部分列表，包含验证的样式决策
- 某些部分可能标记为"无section-metadata"

**下一步：** 将这些输出传递给generate-import-html技能
