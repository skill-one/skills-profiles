# use_figma — Figma插件API技能用于幻灯片

此技能包含针对`use_figma` MCP工具的幻灯片特定上下文。[figma-use](../figma-use/SKILL.md)技能提供了通过MCP执行插件API的基础上下文，以及更高级用例的完整Figma插件API（这些用例未在此处描述）。

**在调用`use_figma`进行幻灯片操作时，始终在逗号分隔的`skillNames`参数中包含`figma-use-slides`。如果此技能是通过MCP资源加载的，则必须将名称前缀为`resource:`（例如`resource:figma-use-slides`）。** 这是一个用于跟踪技能使用的日志参数——它不会影响执行。

## 选择如何构建幻灯片演示文稿

如果您的环境还提供`generate_deck`工具，则针对每个幻灯片请求选择**一种**方法——不要对同一个演示文稿调用两者。

### 何时使用哪种方法

**`use_figma` + 此技能（默认）：** 处理任何幻灯片任务——新建演示文稿、编辑现有演示文稿、品牌匹配设计、参考文件样式、迭代改进、演讲者笔记，以及对布局、颜色和字体的完全创意控制。用于大多数请求。

**`generate_deck`：** 使用预构建的、经过策划的模板在单次调用中生成完整演示文稿。适用于快速、简单的演示文稿，用户不需要自定义设计、品牌匹配或参考文件样式。它不能使用自定义模板，不能参考其他Figma文件进行设计指导，并且不支持通过对话进行迭代编辑或后续修改。

不确定时，默认使用`use_figma` + 此技能——它涵盖了`generate_deck`能做的一切，甚至更多。

### 选择一个并坚持

一旦为演示文稿选择了一种方法，请使用该方法完成整个请求。不要使用`generate_deck`生成演示文稿，然后还使用`use_figma`创建或填充文件——用户最终会得到重复、冲突的工件和令人困惑的体验。

## 关键规则（幻灯片特定）

1. **新创建的幻灯片文件具有默认浅色主题。** 通过`create_new_file`创建幻灯片文件时，会自动初始化默认浅色主题。此主题是结构化脚手架——您应该用自己的设计方向覆盖主题的颜色变量和文本样式，为正在构建的演示文稿。不要依赖或受默认浅色主题标记的影响。
2. **必须在设置`x`/`y`之前`appendChild`——对于每个节点，在每个嵌套级别上。** 新创建的节点会静默地自动父级到幻灯片上下文中，绝对坐标为`(240, 240)`（幻灯片网格的`GRID_PADDING`）。在`appendChild`之前写入`x`/`y`会导致值存储在隐藏的原点处；一旦您附加了真实的父级，节点就会位于`(预期值 − 240, 预期值 − 240)`。此错误是**间歇性的**——同一脚本中的某些帧可以避免它，因此一个工作测试并不能证明您是安全的。**签名识别：** 如果任何节点最终位于`(−240, −240)`，您在设置它之前设置了`x`/`y`。不要尝试通过将240加回来来补偿——这在重试时会产生更差的输出。相反，修复顺序。有关使顺序不可能出错的辅助模式，请参阅[slide-gotchas.md](references/slide-gotchas.md#position-after-appendchild-critical)。
3. **SLIDE_GRID和SLIDE_ROW是抽象节点**——不要访问它们上的`.fills`、`.effects`或布局属性。只有`SLIDE`节点（类型为`'SLIDE'`）扩展`BaseFrameMixin`。**例外：** `SLIDE_ROW.name`是可设置的——这就是插件如何重命名幻灯片部分（例如`slideRow.name = "Intro"`）。请参阅[slide-lifecycle.md](references/slide-lifecycle.md)。
4. **`get_metadata`对幻灯片文件不起作用。** 使用`use_figma`只读脚本进行验证。在`closePlugin()`输出中返回创建的节点位置，并验证没有重叠的边界框。
5. **在幻灯片中不要调用`figma.createPage()`。** 它会抛出`TypeError: figma.createPage no such property 'createPage' on the figma global object`——`createPage()`是仅适用于设计文件API的（`figma.com/design/...`）；幻灯片URL是`figma.com/slides/...`。相反，使用幻灯片网格（`SLIDE_GRID` / `SLIDE_ROW` / `SLIDE`）来组织演示文稿结构——请参阅[slide-lifecycle.md](references/slide-lifecycle.md)和[slide-grid.md](references/slide-grid.md)。
6. **永远不要删除现有幻灯片以重新构建它们。** 当被要求改进、重新设计或重新设计演示文稿时，请就地修改现有幻灯片。只有在用户明确要求“从头开始”或“从头开始”时，才删除幻灯片。

## 设计思维

并非每个任务都需要相同深度的设计思维。在执行任何操作之前，确定您处于哪个档位：

- **内容/属性编辑**——更改文本、交换颜色、更新数字、修复对齐方式、调整元素大小。跳过设计思维。只需进行更改并匹配现有内容。
- **结构添加**——添加幻灯片、重新设计部分布局、更改演示文稿的颜色调色板、引入新的视觉元素。这包括要求“改进”、“重新设计”或“重新设计”演示文稿的请求——这些是就地编辑现有内容，而不是新建演示文稿。设计思维适用，但在*继承*模式下：现有演示文稿是您的设计语言。检查它、匹配其调色板、类型、空间习惯和主题。扩展演示文稿的现有特征，而不是重新发明它。
- **新建演示文稿**——从空白文件或从头开始构建演示文稿。完全适用以下所述的设计思维。

对于现有演示文稿的结构添加：运行检查脚本（如下所述）并拍摄屏幕截图，然后再进行更改。对于“什么颜色故事？”和“什么类型处理？”的答案已经在文件中——您的工作是阅读它们并保持一致。[slide-design.md](references/slide-design.md)中的设计原则描述了您要*匹配*的内容，而不是您要*选择*的内容。

### 新演示文稿设计流程

在为新建演示文稿编写任何Plugin API代码之前，确定它应该*感觉*如何。Figma用户有很高的视觉期望——看起来像是从通用模板生成器中出来的演示文稿会因为错误的原因而突出。

1. **阅读简报。** 演示文稿在传达什么内容，以及传达给谁？投资者演讲、团队回顾、产品发布和技术深度解析都需要不同的视觉处理。设计应与内容密不可分。
2. **检查设计语言。** 在发明任何东西之前，查看用户已经给您的。提示中的品牌指南——颜色调色板、字体规范、标志规则、语气描述——已经做出的设计决策。参考Figma文件的链接是您应该研究的设计语言，而不是快速浏览。用户输入越具体，您自己应该发明的就越少。当用户提供参考时，您的工作从*设计师*转变为*解释者*：提取设计语言并忠实地将其应用于新内容。
3. **确定剩余立场。** 如果用户提供了一个完整的品牌系统，您的创作自由度在于布局、节奏和构图——而不是颜色或类型。如果他们只给您一个用于灵感的参考幻灯片，您有更多的空间，但仍应反映其特征。如果他们什么都没给，那么您拥有每个决定——选择一个颜色故事、一个类型处理、一种组织空间的方式，并在每张幻灯片上坚持到底。具有清晰视角（即使是安静的）的演示文稿总是比在每个决定上保持安全的演示文稿读起来更好。“确定立场”的范围与用户提供的范围成反比。
4. **给它一个签名。** 每个好演示文稿至少有一个元素，如果它在上下文中看到它，您会认出来：一个独特的调色板、一个意想不到的布局节奏、一个重复的形状语言。在根据品牌指南工作时，签名应来自品牌语言——放大已经存在的东西，而不是添加外来事物。在从头开始设计时，在开始构建之前决定签名是什么。

### 阅读参考文件

当用户提供一个Figma文件链接作为参考时，在设计任何东西之前研究它。您提取的内容取决于文件是什么：

- **一个幻灯片文件**：`get_metadata`对幻灯片文件不起作用。使用`get_screenshot`捕获单个幻灯片以获取视觉参考，并使用具有参考文件`fileKey`的`use_figma`运行只读脚本，以提取主题变量、颜色调色板、字体选择和布局模式。
- **一个设计文件**：`get_design_context`为您提供全面的设计数据——颜色、字体、布局结构。`get_screenshot`提供视觉参考。使用两者。

参考文件中要查找的内容：颜色调色板（哪个色调领先，强调色是什么，背景有多暗/多亮）、类型选择（家族、权重、如何处理层次结构）、空间习惯（内容锚点在哪里、有多少空白、是否超出边缘）、任何重复的主题（形状、线条处理、装饰元素）。这些都是您继承的决策——其他一切都是您的。

要遵循参考的紧密程度取决于用户的要求。“让它看起来像这个”意味着用新内容复制设计语言。“使用这个以获取灵感”意味着反映其特征，但让它成为自己的。“这是我们的品牌演示文稿”意味着提取品牌系统并始终如一地应用它。不确定时，尽量靠近参考——让用户要求您偏离比让您撤销与他们的品牌冲突的已发明选择更容易。

加载[slide-design.md](references/slide-design.md)以获取有关颜色、类型、布局模式、构图以及要避免的内容的特定指导。当您有参考文件或品牌指南时，将slide-design.md的原则视为用户*未*做出的决定的默认值——而不是覆盖他们已做出的决定。

## 演示文稿构建工作流

在构建5张或更多幻灯片的演示文稿时，使用此两阶段工作流。它替换了来自[figma-use](../figma-use/SKILL.md)第6节的通用增量工作流，专门针对演示文稿构建——原则仍然适用，但节奏发生了变化。

### 第一阶段——设计与计划

完成上述设计思维过程（阅读简报、检查设计语言、确定立场、给签名），然后在编写任何`use_figma`代码之前，制作涵盖整个演示文稿的幻灯片计划：

1. **逐张幻灯片计划。** 对于每张幻灯片：其目的/内容、空间描述的布局方法（例如“标题锚定左上角，规格卡片填充右三分之一，装饰性圆圈从右上角边缘出血”）、背景处理（深色/浅色/渐变）。在计划期间不要计算像素坐标——用空间术语描述布局。坐标计算发生在代码生成期间。
2. **共享常量。** 声明您将使用的字体家族和样式、颜色调色板作为命名角色（主要、强调、bgDark、表面、textPrimary、textMuted等），以及重复的主题或签名元素。
3. **布局多样性检查。** 按顺序阅读幻灯片计划。如果布局描述感觉重复——“两列、两列、网格、两列”——在构建之前重新排列。这是多样化最便宜的时刻。请参阅[slide-design.md](references/slide-design.md)中的反模式。
4. **代码前言。** 写出您将在每个构建脚本顶部粘贴的可重用前言：一个`const C = { ... }`颜色调色板对象、一个`Promise.all([...])`字体加载块，以及来自[slide-gotchas.md](references/slide-gotchas.md#position-after-appendchild-critical)的`addFrame`/`addText`/`addRect`辅助函数。

### 第二阶段——构建

执行计划，以大批量执行。目标是最大限度地减少思考-构建周期——而不是最小化每个脚本中的元素。

- **每个`use_figma`调用3–5张幻灯片。** 结构相似的幻灯片（例如一系列产品功能幻灯片）可以放在同一个批次中。每张幻灯片都是一个独立的子树——跨幻灯片依赖不存在，因此大批量是安全的。
- **在批次之间不要重新计划。** 设计在第一阶段已确定。如果一批次成功并通过验证，请立即移动到下一批次。只有在批次失败或产生需要更改方法的视觉问题时才重新计划。
- **在每个构建脚本顶部粘贴代码前言**（颜色、字体、辅助函数）。从第一阶段逐字复制它——不要重新推导。
- **使用来自[slide-gotchas.md](references/slide-gotchas.md#batch-validation-script)的确定性批次验证脚本验证每个批次。** 这检查重叠元素、文本剪切和边界外的节点，大约需要3秒钟。如果检查通过，则无需截图继续。如果它失败，请拍摄受影响幻灯片的截图并修复后再继续。
- **仅在检查点拍摄屏幕截图**——在第一批次之后（验证视觉系统：颜色、字体、设计方向），以及最终批次之后（整体质量）。使用`await slide.screenshot()`拍摄1–2张有代表性的幻灯片的屏幕截图，而不是使用单独的`get_screenshot`调用。
- **始终从每个构建脚本返回所有创建的节点ID**，一如既往。

## 部分

部分是幻灯片网格中的水平行——每一行都是一个部分。名称显示在编辑器中（行旁边）和演示者视图中（以便演讲者可以跳转到组）。它们是编辑演示文稿的人的组织工具——用户拥有断点位置，而不是您。

### 当被要求组织演示文稿

“组织这个演示文稿”是模糊的——分组、重新排序、删除重复项或重新结构。在伸手`AskUserQuestion`之前阅读演示文稿。

**默认：建议，不要询问。** 大多数演示文稿都有线索——标题书签、编号用例、重复的*之前/之后*对、过渡幻灯片（“然后X进入聊天”）、*谢谢*。当线索存在时，选择部分并在一条确认消息中显示它。批次内的边界调用（例如一个*用例*行与三个，过渡幻灯片的位置）是可逆的——选择一个并继续。

**后备：当线索缺失时询问。** 如果幻灯片是任意顺序排列的，或者没有脊柱，请询问哪些范围应该组合在一起，以及如何命名它们。不要用三分之一来代替阅读。

### 命名+范围

名称应该简短（1–3个词）、具体（*演示*比*展示和讲述*更好），并且在演示文稿中保持一致。两到五个部分是典型的；只有对于长或重复的演示文稿才更多。名称不是幻灯片标题——它们有助于找到一组，而不是描述其内容。

### 重命名部分

`getSlideGrid()`返回`SlideNode[][]`——内部数组是纯JS数组，其中包含幻灯片，而不是`SLIDE_ROW`节点。在那些数组上设置`.name`会静默无操作。要重命名部分，请遍历节点树并在实际的`SLIDE_ROW`上设置`.name`：

```js
const slideGrid = figma.currentPage.children.find(c => c.type === "SLIDE_GRID");
slideGrid.children[0].name = "Intro";
```

## 演讲者笔记

演讲者笔记是每个幻灯片的演讲者的私人伴侣。它们出现在演示者视图中（仅对演讲者可见，而不是观众），并在现场演示期间作为脚本、提示单或谈话要点参考。

### 何时编写演讲者笔记

- **当被要求时**：如果用户要求演讲者笔记、演讲者笔记、谈话要点或演示文稿的脚本，请为每张具有实质性内容的幻灯片编写笔记（跳过部分分隔符或纯装饰性幻灯片，除非有可说的内容）。
- **演示者准备好的演示文稿**：如果用户明确要求一个可以立即用于现场演示的演示文稿，演讲者笔记很有用。当它们有助于演讲者理解节奏、过渡或幻灯片上未显示的上下文时，请添加它们。
- **稀疏或视觉幻灯片**：如果幻灯片围绕图表、图像、隐喻或挑衅性问题构建，笔记可以帮助解释演讲者应该说什么。对于图像密集型、图表密集型或视觉稀疏的幻灯片，当视觉上下文很重要时，使用`node.screenshot()`拍摄屏幕截图，但默认情况下不要为每张幻灯片拍摄屏幕截图——图像消耗上下文预算。
- **不要未经提示添加笔记**：对于正常的幻灯片编辑、布局工作或更新现有演示文稿，除非用户要求，否则不要填充演讲者笔记。添加笔记会改变演示流程，并可能让演示文稿所有者感到意外。

### 好的演讲者笔记是什么样的

演讲者笔记是给*演讲者*的，而不是给观众的。它们应该感觉像一个值得信赖的同事俯身过来低声说“这是您要说的话”。好的笔记：

- **补充幻灯片，而不是重复它。** 如果幻灯片说“收入增长了40%”，笔记不应该说“收入增长了40%”。它们应该解释为什么增长，观众应该记住什么，或者这个问题通常会引发什么问题。
- **简洁且可扫描。** 演讲者在说话中扫视时需要立即找到他们的位置。使用简短的要点，而不是密集的段落。每个要点应该是一个想法。
- **包括过渡。** 最好的笔记告诉演讲者如何*移动*到下一张幻灯片：“在掌声停息后…”或“这建立在之前的点上——回顾40%的数字。”
- **携带幻灯片无法携带的上下文。** 数据来源（“来源：2025财年第四季度内部指标，尚未公开”）、限制（“如果CFO在房间里，请跳过这张幻灯片”）、时间提示（“这是中点——您应该大约在10分钟”）、预期的提问（“他们会问关于利润率——请参阅附录幻灯片14”）。
- **匹配演示的语气。** 投资者演讲的笔记是精确和排练好的。团队回顾的笔记是随意和灵活的。关键演讲的笔记可能包括舞台指示。匹配上下文中的语气。

### 演讲者笔记中要避免的内容

- **完整脚本**：墙文本笔记鼓励逐字阅读，这会导致糟糕的演示。如果用户明确要求脚本，请编写一个，但默认使用要点。
- **面向观众的格式**：笔记对观众不可见。不要优化它们以供非演讲者阅读。
- **与幻灯片的冗余**：如果幻灯片是自解释的（“谢谢”带有联系信息），则不需要笔记。留下幻灯片的笔记为空是没问题的。

### 格式

`slide.speakerNotes`接受markdown字符串。优先使用要点作为主要结构；粗体对于强调演讲者不应跳过的关键短语很有用。请参阅[slide-properties.md](references/slide-properties.md#supported-formatting)以获取完整的支持（列表、粗体、斜体、删除线）和不受支持（标题、代码块、内联代码、链接）的markdown列表。

## 检查幻灯片文件

目前还没有专门用于幻灯片文件的读取工具。使用只读`use_figma`进行检查，并使用`get_screenshot` / `await node.screenshot()`获取视觉上下文。

- **创建之前检查。** 在创建任何东西之前，运行只读`use_figma`以发现已经存在的内容——幻灯片、文本、组件、命名约定。[figma-use](../figma-use/SKILL.md)第6节“先检查”模式在此处适用。
- **`get_metadata`对幻灯片文件不起作用**——它仅支持`figma`（设计）编辑器类型。
- **`console.log()`输出不会被返回**——只有`return`值会返回。始终`return`您需要的数据。
- **使用`get_screenshot`获取视觉上下文**——传递有效的`nodeId`以获取屏幕截图。您也可以在`use_figma`脚本中内联使用`await node.screenshot()`。

### 快速检查脚本

**列出演示文稿中的所有幻灯片：**
```js
const grid = figma.getSlideGrid();
return grid.map((row, rowIdx) =>
  row.map((slide, colIdx) => ({
    id: slide.id,
    name: slide.name,
    row: rowIdx,
    col: colIdx,
    isSkipped: slide.isSkippedSlide,
    speakerNotes: slide.speakerNotes,
  }))
);
```

**从特定幻灯片获取文本内容：**
```js
const slide = figma.getNodeById("TARGET_SLIDE_ID");
// findAllWithCriteria使用索引类型查找——比在具有许多形状/图像的幻灯片中使用findAll(n => n.type === 'TEXT')快得多。
const textNodes = slide.findAllWithCriteria({ types: ["TEXT"] });
const fontsToLoad = new Set();
for (const t of textNodes) {
  if (t.fontName !== figma.mixed) {
    fontsToLoad.add(JSON.stringify(t.fontName));
  } else {
    const segments = t.getStyledTextSegments(["fontName"]);
    for (const seg of segments) fontsToLoad.add(JSON.stringify(seg.fontName));
  }
}
for (const f of fontsToLoad) {
  await figma.loadFontAsync(JSON.parse(f));
}
return textNodes.map(t => ({
  id: t.id,
  name: t.name,
  characters: t.characters,
  x: t.x,
  y: t.y,
  width: t.width,
  height: t.height,
}));
```
