# 技能：验证 Unity URP 渲染图渲染器功能

## 目的
审查 Unity 6+ URP 渲染图的 `ScriptableRendererFeature` 及其相关的通道实现，查找与材质绑定、资源连接、渲染图纹理创建、静态渲染函数结构、全局资源暴露和 API 版本使用相关的正确性问题。

## 使用场景
在以下情况下使用此技能：
- 审查 AI 生成的 Unity URP 渲染图渲染器功能代码
- 在集成前验证自定义的 `ScriptableRendererFeature`
- 检查常见的渲染图资源连接和通道设置错误
- 诊断可疑但合理的渲染图通道实现
- 审查自定义光栅/混合/复制通道是否使用了最合适的渲染图辅助 API

## 输入
该技能应期望以下输入：
- **Unity 版本**
- **URP 版本**
- **待审查的渲染图渲染器功能代码**
  - `ScriptableRendererFeature`
  - 相关的通道代码
  - 或两者
- **预期行为**
- **预期的输入/输出**（如果已知）
- **可选约束**
  - 项目规范
  - 必需的通道类型
  - 已知资源
  - 必需的材质/着色器属性

## 输出格式
该技能必须以以下结构返回结果：

### 1. 验证摘要
对实现的简短整体评估。

### 2. 确认的问题
直接由提供的代码支持的具体问题。

### 3. 可能的问题 / 风险假设
依赖于缺失上下文或信息不完整潜在的的问题。

### 4. 推荐的修复方案
针对每个问题的最小化目标修复。

### 5. 修正代码片段
在必要时提供的小段修正代码。

### 6. 缺失信息
验证代码所需的高置信度信息。

## 验证检查清单

### 1. 材质绑定
检查以下内容：
- 材质声明清晰
- 序列化材质在需要时正确暴露
- 材质正确传递到通道
- 必要时存在空值处理
- 声明的材质实际被使用
- **所有必需的材质输入在执行前绑定**
- **当着色器期望时显式绑定主要输入纹理**
- 辅助纹理和参数纹理也显式绑定
- 纹理/属性绑定与着色器期望的属性名称匹配

标记为问题时：
- 声明或传递材质但未实际使用
- 仅绑定次要纹理或参数而省略主要输入纹理
- 通道绑定遮罩/噪声/辅助纹理但未绑定主要颜色/输入纹理
- 假设必需的着色器属性存在而未设置
- 属性名称不一致或模糊
- 代码依赖隐式主纹理绑定而通道模式要求显式绑定

推荐的模式：
1. 清晰创建或分配材质
2. 显式绑定主要源纹理
3. 显式绑定所有辅助纹理
4. 属性名称一致且有意
5. 处理或报告空值或缺失资源情况

### 2. 纹理资源连接
检查以下内容：
- 采样/读取纹理、写入目标和辅助纹理清晰区分
- 使用 `UseTexture(...)` 的纹理适用于读取访问
- 使用 `SetRenderAttachment(...)` 的纹理适用于写入目标
- 源、目标和辅助资源不被混淆
- 所有预期的纹理显式连接
- 材质涉及时纹理属性名称明确且一致
- 实现不凭空创造纹理可用性
- 多纹理资源使用显式处理而非隐式

标记为问题时：
- 意图作为输入/读取资源的纹理未合理地用作写入目标
- 目标/写入目标与采样输入混淆
- 辅助纹理未清晰源或连接
- 通道设置中缺失必需的纹理资源
- 读取/写入资源角色模糊或不一致

### 3. 执行结构 / 静态渲染函数
检查以下内容：
- 渲染函数声明为 `static`
- 执行结构匹配目标通道类型和 API 风格
- 通道数据正确连接到执行
- 资源在正确阶段访问
- 执行逻辑与预期渲染通道行为一致
- 渲染函数使用的每个 `PassData` 字段在通道设置中显式分配
- 实现不依赖默认值或先前分配的 `PassData` 状态
- 存储在 `PassData` 中的资源句柄为当前帧/通道记录分配新鲜值且不因先前使用而悬空

标记为问题时：
- 渲染函数不是 `static`
- 实现使用实例方法而 API 模式期望静态渲染函数
- 通道数据或必需资源通过实例状态访问而非提供给静态函数的通道数据/上下文
- 执行流程与预期的渲染图或通道执行模式不匹配
- 渲染函数中读取 `PassData` 字段但未在通道设置中清晰分配
- 部分重新分配 `PassData` 字段而其他字段保留先前池化使用中的旧值
- 存储在 `PassData` 中的资源句柄可能因未完全重新分配而延续自前一帧或通道
- 实现因通道数据未每次记录时完全初始化而风险使用悬空或过时的句柄

推荐：
- 在每次 `RecordRenderGraph(...)` 调用中显式分配每个 `PassData` 字段
- 将 `PassData` 视为每次记录的瞬态数据而非持久状态
- 避免部分初始化池化的通道数据对象

### 4. 渲染图描述符验证
检查以下内容：
- 实现默认不通过创建新的 `TextureDesc` 而直接使用可直接使用的图派生描述符
- 当纹理应匹配活动渲染目标时，描述符首先从相关渲染图资源获取，例如：
  - `resourceData.activeColorTexture.GetDescriptor(renderGraph)`
  - 或其他适当的现有图支持资源
- 仅修改实际需要不同的字段后源描述符
- 故意保留或故意覆盖描述符字段，如名称、深度位、格式和 MSAA
- 任何手动重建描述符数据的合理性由特定需求证明

标记为问题时：
- 代码在未尝试重用图派生描述符的情况下创建新的 `TextureDesc`
- 默认情况下手动将宽度和高度复制到新的描述符结构
- 使用 `cameraTargetDescriptor` 作为主要源而图派生描述符更准确
- 意外丢失 MSAA、图形格式或与活动渲染目标兼容性等重要属性
- 描述符重建仅作为便利快捷方式而非必要偏离源资源

推荐规则：
- **除非图派生描述符无法直接使用或纹理必须有意偏离源资源，否则不创建新的 `TextureDesc`。**

推荐模式：
1. 从相关渲染图资源获取描述符
2. 仅修改必须更改的字段
3. 尽可能从派生描述符创建纹理

示例：

#### 推荐
```csharp
RenderTextureDescriptor desc = resourceData.activeColorTexture.GetDescriptor(renderGraph);
desc.depthBufferBits = 0;
desc.name = "New name";
// 其他期望参数
passData.targetTexture = renderGraph.CreateTexture(desc);
```

### 5. 手动复制通道简化
检查以下内容：
- 简单的纹理复制操作不使用内置渲染图辅助工具实现完整的自定义光栅通道
- 仅读取一个纹理并将其未更改地写入另一个目标的通道适当简化
- 实现优先选择目标 API/平台上下文中最合适的内置辅助工具
- 默认不推荐 `AddCopyPass(...)` 如果当前环境中应优先使用更兼容的 `AddBlitPass(...)` 重载

标记为问题时：
- 仅存在以将一个纹理复制到另一个纹理的光栅通道
- 通道不使用材质和自定义处理
- 渲染函数仅执行简单的混合/复制等效操作
- 实现使用完整的自定义光栅通道而内置复制/混合辅助工具可以更直接表达相同行为

推荐：
- 使用最合适的 `AddBlitPass(...)` 重载进行直接的复制类操作（当这是推荐且更兼容的路径时）
- 仅在明确适合且支持目标 API/平台上下文时使用 `AddCopyPass(...)`
- 仅在复制需要额外逻辑或非平凡行为时使用自定义光栅通道

### 6. 手动混合通道简化
检查以下内容：
- 直观的 全屏材质混合不使用自定义光栅通道而 `renderGraph.AddBlitPass(...)` 可以更直接表达相同行为
- 仅在需要额外逻辑或非平凡行为时使用自定义光栅通道进行混合
- 简单的源到目标材质混合使用最直接的渲染图辅助工具

标记为问题时：
- 光栅通道读取一个源纹理并写入一个目标纹理
- 通道使用材质但无额外自定义通道逻辑
- 渲染函数仅执行简单的全屏混合
- `renderGraph.AddBlitPass(...)` 提供更清晰的等效结果

推荐：
- 使用 `renderGraph.AddBlitPass(...)` 进行直观看的全屏材质混合
- 仅在需要额外逻辑、多个操作、条件行为或特殊设置时使用自定义光栅通道

### 7. 全局资源暴露
检查以下内容：
- 纹理和缓冲区除非明确请求或下游消费者清晰需要否则不全局暴露
- 在渲染图通道中需要全局暴露时，实现使用适当的渲染图发布机制
- 不使用直接命令缓冲区全局状态突变作为渲染图资源发布的替代
- 全局暴露不无故扩展资源生命周期或减少别名机会

标记为问题时：
- 使用 `SetGlobalTextureAfterPass` 而无清晰消费者
- 在渲染图通道中使用 `context.cmd.SetGlobalTexture(...)` 而渲染图资源发布是适当的机制
- 全局暴露用作便利快捷方式而非显式通道到通道连接
- 引入不必要的隐藏耦合
- 因下游 `UseGlobalTexture(...)` 或 `UseAllGlobalTextures()` 使用，全局暴露的纹理可能保持比必要更长的生命周期，增加内存压力或减少别名机会

推荐：
- 默认不全局暴露
- 尽可能显式资源连接
- 仅在渲染图中真正需要全局发布时使用 `builder.SetGlobalTextureAfterPass(...)`
- 资源生命周期尽可能保持为本地和短寿命

### 8. 渲染器功能输入声明
检查以下内容：
- `ScriptableRendererFeature` 及其相关通道使用 `ConfigureInput(...)` 在需要时声明必需的管道输入
- 请求的输入标志与功能预期行为和可见资源使用匹配
- 通道不依赖管道提供的输入而不在目标 API 模式要求下声明
- 默认不声明不必要的输入，特别是当它们可能引入额外复制、中间资源或避免可性能成本

标记为问题时：
- 功能的通道使用或明显预期使用管道提供的输入但未使用 `ConfigureInput(...)` 声明
- `ConfigureInput(...)` 请求功能/通道未使用的输入
- 声明的输入标志与预期效果行为不匹配
- 效果描述、代码和声明输入暗示冲突要求
- 不必要的声明输入可能强制额外复制、额外通道工作或其他可避免的性能成本

分类指导：
- 当代码清晰显示使用必需输入但未声明时标记为 **确认问题**
- 当预期效果暗示必需输入但可见代码未完全证明着色器/资源使用时标记为 **可能问题**
- 当不必要的输入声明可能引入额外复制或其他可测量的运行时成本时将问题视为更高严重性

## 安全边界
该技能必须：
- 避免凭空创造不支持的 API
- 区分 **确认** 问题与 **可能** 问题
- 优先选择最小化目标修复而非广泛重写
- 解释每个问题为何重要
- 标记隐藏耦合和不必要的全局状态
- 说明何时提供的代码不足以完全确定

## 非目标
- 保证运行时正确性
- 除非必要否则不重写整个渲染器功能
- 验证无关的游戏逻辑
- 除非直接与通道连接或绑定相关否则不验证着色器内部

## 评估标准
成功的验证应：
- 捕获真实的连接和 API 问题
- 识别可疑但合理的错误
- 提供可操作的修复方案
- 避免虚假确定性
- 提高对生成渲染通道代码的信任
