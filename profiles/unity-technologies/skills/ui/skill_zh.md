确定项目适用的 UI 系统并路由到相应的专业技能。

## 何时路由 vs 直接回答

**当路由到专业技能时：**
- 用户希望理解、编辑或生成特定的 UI 元素
- 用户引用了特定的文件或 UI 对象
- 用户要求 UI 修改或创建

**直接回答（不进行路由）时：**
- 用户提出比较/教育类问题（例如，“UI Toolkit 和 uGUI 有什么区别？”）
- 用户询问 UI 系统的功能或建议（例如，“我应该使用 UI Toolkit 还是 uGUI 来开发移动端？”）
- 用户需要 Unity UI 架构的概念性解释

## 路由逻辑

**步骤 1：检查显式的文件引用或关键词：**

| 用户提及 | 路由到 |
|----------|--------|
| `.uxml` 或 `.uss` 文件（包括在 `/Editor/` 中） | `ui-uitk` |
| "UI Toolkit"、"UITK"、"UIElements"、"CreateGUI" | `ui-uitk` |
| Canvas 预制件/对象，带有 UI 的 `.prefab` | `ui-ugui` |
| "uGUI"、"Canvas"、"RectTransform"、"传统 UI" | `ui-ugui` |
| "IMGUI"、"OnGUI"、"OnInspectorGUI"、"即时模式" | `ui-imgui` |
| Figma URL（`figma.com/design/...`）、"Figma"、"从 Figma 导入" | 不适用 — 见下文 |

**对于与编辑器相关的请求（EditorWindow、自定义 inspector、PropertyDrawer）：**
- 如果未提及明确的 UI 系统 → **转到步骤 2** 以检测项目的编辑器 UI 系统
- 如果未检测到现有模式，默认为 `ui-uitk` 用于新的编辑器 UI
- 仅在项目仅使用 IMGUI 或用户明确要求 IMGUI 时使用 `ui-imgui`

如果找到显式的文件或关键词，立即激活相应的技能。

**步骤 2：如果仍不明确，从项目检测：**

搜索项目以确定使用的 UI 系统：

| 查找 | 表示 |
|------|------|
| `.uxml` 或 `.uss` 文件（包括在 `/Editor/` 中） | UI Toolkit（运行时或编辑器） |
| 场景中的 `UIDocument` 组件 | UI Toolkit（运行时） |
| 使用 `CreateGUI()` 方法的编辑器脚本 | UI Toolkit（编辑器） |
| 场景/预制件中的 `Canvas` | uGUI |
| 大量使用 `RectTransform` | uGUI |
| 使用 `OnGUI()` 或 `OnInspectorGUI()` 的编辑器脚本 | IMGUI（传统编辑器） |

**步骤 3：如果仍不明确，询问或默认：**

- 对于现有项目：检测并遵循已使用的框架（步骤 2）
- 对于没有 UI 的新项目：询问用户更喜欢哪个框架（UI Toolkit vs uGUI），简要解释 UI Toolkit 是现代的/CSS 风格的，而 uGUI 是基于 Canvas 的成熟的
- 对于用户没有偏好的新运行时/游戏 UI：默认为 uGUI（`ui-ugui`）
- 当用户提及移动端/性能限制或较旧的 Unity 版本（预 6.0）时：倾向于 uGUI（`ui-ugui`）

## 请求类型

专业技能处理三种类型的请求：

| 类型 | 示例 |
|------|------|
| **理解** | "这个按钮有什么作用？"、"这个布局是如何设计的？"、"解释这个 UI" |
| **编辑** | "更改这个颜色"、"在这里添加一个标签"、"修复这个布局" |
| **生成** | "创建一个菜单"、"制作一个物品栏界面"、"构建一个设置面板" |

根据 UI 系统，将所有类型的请求路由到相应的专业技能。

## 可用的子技能

### UI Toolkit — `ui-uitk`
- 适用于使用 UI Toolkit（运行时游戏 UI 和编辑器工具）的 Unity 6.0+ 项目
- **理解**、**编辑** 和 **生成** `.uxml` 和 `.uss` 文件
- 现代、CSS 风格的样式方法
- 新编辑器窗口（CreateGUI）和现有 UI Toolkit 项目的首选

### uGUI — `ui-ugui`
- 适用于使用 Unity 基于 Canvas 的 UI 系统的项目
- **理解**、**编辑** 和 **生成** Canvas 层级结构
- 使用布局组进行响应式设计
- 新运行时/游戏 UI 的默认选择，当用户没有框架偏好时

### IMGUI — `ui-imgui`
- 适用于使用 OnGUI/即时模式的传统编辑器工具
- 仅在项目具有现有的 IMGUI 编辑器代码或用户明确要求 IMGUI 时使用
- **理解**、**编辑** 和 **生成** 使用 OnGUI 构建的 EditorWindow、inspector、PropertyDrawers
- 不适用于运行时游戏 UI — 对于新的编辑器工具，除非项目已专用于 IMGUI，否则使用 UI Toolkit

### Figma 设计导入 — 在此不可用

导入 Figma 设计需要 Unity 的 Figma 集成服务，该服务仅在 Unity AI Assistant 内存在。没有客户端等效服务，因此不要承诺它。

如果用户提供 Figma URL，说明自动导入在此不可用，并提供替代方案：询问他们描述或截图屏幕，然后使用上述相应的框架技能构建。

## 常见指南（所有 UI 系统）

### 范围纪律

**仅执行请求的操作：**
- 问题 → 不进行修改地回答
- 针对性编辑 → 仅修改指定内容
- 生成 → 仅创建请求的文件
- 除非明确要求，否则不要主动添加脚本

**这些不涉及脚本：**
- "合适的按钮" → 风格良好的按钮
- "可工作的 UI" → 可渲染的有效 UI
- "菜单界面" → 仅视觉布局

### 规范

**优先遵循项目模式。** 在应用默认设置之前搜索现有文件。

| 类型 | 规范 |
|------|------|
| 元素名称 | 遵循项目模式，或使用驼峰命名法 |
| 文件组织 | 匹配现有项目结构 |

### 工作流程

1. **确定 UI 系统** — 使用上述路由逻辑
   - 对于 Figma 请求，告知用户自动导入在此不可用，然后从他们的描述或截图开始，并继续框架检测
2. **激活专业技能** — 路由到 `ui-uitk`、`ui-ugui` 或 `ui-imgui`
3. **技能处理请求** — 根据适当性进行理解、编辑或生成

## 处理混合项目

许多 Unity 项目同时使用多个 UI 系统（例如，使用 UI Toolkit 开发运行时游戏 UI 和编辑器工具）。当检测到多个系统时：

- **对于运行时 UI 请求**（菜单、HUD、游戏屏幕）→ 路由到已使用的运行时系统（UITK 或 uGUI）
- **对于编辑器工具请求**（自定义 inspector、编辑器窗口）：
  - **优先使用 UI Toolkit**（CreateGUI）构建新的编辑器 UI — 这是现代方法
  - 仅在项目的现有编辑器工具专用于 IMGUI，或用户明确要求 IMGUI 时使用 IMGUI
  - 检查现有的编辑器 `.uxml` 文件以确认 UI Toolkit 的使用
- **在混合项目中创建新的运行时 UI** → 匹配类似现有 UI 使用的模式；如果不存在类似现有 UI 且用户没有偏好，则使用 uGUI
