# oh-my-issues

将问题积压转化为路线图。问题只是症状数据，不是工作单元——工作单元是产生它们的架构缺陷。最终状态是 `open issues == open plans`，1:1。

## 核心原则

停止逐个关闭问题。将具有单一架构修复的多个症状分组到一个集群中，给集群一个标准的家（一个计划主问题 + 一个 `plans/0X-*.md` 设计文档），使用标准重定向关闭每个子问题，并为每个集群提交一个 PR 来原子性地关闭所有子问题。新报告的 Bug 被追加到匹配的主问题中作为 "Round N" 评论，而不是作为新的跟踪问题打开。

这通过三种方式复合：架构修复淘汰整个症状家族，计划的测试矩阵在 CI 中制度化预防，标准化的分派使剩余的流入成本较低。

## 何时使用

- 仓库有 20+ 个开放问题，并且许多问题感觉像是重复的或同一缺陷的平台特定症状。
- 用户要求对问题列表进行 "triage"、"consolidate"、"cluster"、"dedupe"、"group" 或 "make a plan from"。
- 提交了一个新 Bug，用户想知道它是否属于现有工作。
- 用户想要提交一个聚焦的 PR 来解决一系列相关的问题。

## 何时 NOT 要使用

- 少于 ~15 个开放问题：直接关闭它们。
- 问题确实是独立的（没有共享的根本原因）：每个问题一个修复是正确的。
- 仓库缺乏 `plans/` 纪律，并且用户不希望引入这种纪律——先提议，不要强加。

## 三种模式

### 模式 1：集群传递（初始减少）

当积压从未被整合时使用。目标：通过一次操作将 N 个问题减少到 N 个计划主问题。

1. **完整阅读所有内容。** 获取每个开放问题的正文 *和* 其评论线程——不仅仅是标题。没有完整文本，表面级别的分组会失败，并且重现步骤、链接的重复和诊断输出通常存在于评论中而不是原始正文中。见下文 "GitHub CLI primitives" 以获取正确的分页列表 + 每个问题的评论获取（单个 `gh issue list` 调用**不会**返回评论正文）。
2. **按根本原因而不是表面进行集群。** 集群的问题是 *一个架构变更是否可以淘汰所有这些问题？* ——而不是 *这些问题是否提到同一个词？* "Windows" 是一个表面；"spawn 合约被主机 shell 违反" 是一个根本原因。具有不同表面的两个问题可以共享一个集群（例如，在两个不同的代码路径中共享一个缺失的 env 隔离边界的环境变量泄漏）。
3. **将每个集群命名为一个架构问题。** 标题格式：`[plan-XX] <架构缺陷> — <一行范围>`。示例：`[plan-02] Spawn-Contract Templating — 在所有主机上规范 ${CLAUDE_PLUGIN_ROOT} 解决方案`。标题必须暗示修复，而不是主题。
4. **为每个集群打开一个主问题**，正文列出了：架构缺陷、子问题（按问题编号）、修复顺序和所需的测试矩阵（主机 × IDE × shell 等）以防止回归。
5. **将每个主问题镜像为 `plans/0X-<slug>.md`** 在仓库中。问题是公共跟踪器；文档是设计。它们相互引用。
6. **关闭每个子问题** 使用标准重定向评论（见下文）并标记 `not planned`。
7. **验证最终状态：** `gh issue list --state open` 返回的正好是主问题，并且没有其他内容。

约 100 个问题的目标形状：4–8 个主问题。超过 10 个意味着你正在按表面进行集群；少于 3 个意味着集群过于宽泛，无法每个都作为一个 PR 来发布。

### 模式 2：分派（新报告的 Bug，稳定状态）

当在整合完成后报告新问题时使用。目标：永远不要让问题列表重新积累。

1. **完整阅读新问题的正文。**
2. **将症状与现有的计划主问题进行模式匹配。** 对于每个开放的主问题，问：*这里描述的修复是否也会修复这个新 Bug？* 如果是 → 它属于那个计划。
3. **如果存在匹配**，在主问题上的 "Round N" 评论中发布：
   - 通过编号命名新子问题
   - 用一句话描述症状
   - 概述具体的修复（1–3 行，例如 `"guard with `case \"$_SH\" in /*.exe|\""` `_SH=bash ;; esac`"`)
   - 添加 Bug 暴露的任何新测试矩阵单元
4. **关闭子问题** 使用标准重定向评论，`not planned`。
5. **如果不存在匹配** 并且 Bug 确实是新的：打开一个新的计划主问题 + `plans/0X-*.md`。抵制这种做法。大多数 Bug 都是现有计划的孩子。

### 模式 3：捆绑（发布集群）

当计划切片准备发布时使用。目标：一个 PR 原子性地关闭 N 个子问题。

1. **列出主问题的子问题。** 从主问题正文和整合评论中收集路由到此计划的每个子问题编号。
2. **验证每个子问题的症状是否被架构修复覆盖**。如果子问题没有被覆盖，PR 还未准备好或该子问题属于不同的计划。
3. **生成 PR 描述**：标题是计划切片（例如 `"fix(spawn): 规范 ${CLAUDE_PLUGIN_ROOT} 解决方案"`）；正文列出每个子问题，使用 `Closes #N` 以便 GitHub 在合并时自动关闭它们。
4. **将计划的测试矩阵添加到 CI** 在同一个 PR 中。没有矩阵，集群将会重新出现。
5. **合并后**，只有当每个子问题都被覆盖时才能关闭主问题。如果计划仍有剩余范围，保持主问题开放并将 PR 作为部分发布的检查点链接。

## 计划主问题的命名

计划主问题的标题必须暗示其修复。

| 坏的（表面） | 好的（架构） |
|---|---|
| Windows Bug | Spawn-Contract Templating 跨主机 |
| Worker crash | Worker / Daemon 生命周期加固 — 监督、健康、重试 |
| 认证问题 | Worker 环境隔离 — 从 SDK 子进程剥离主机 CLI 环境 |
| 安装失败 | 安装器失败透明度 — 跨 IDE 错误分类 + 12×4 测试矩阵 |

如果你不能写一个架构范围的一行，那么集群是错误的。

## 标准化的重定向评论

在每个子问题关闭时使用此确切措辞。一致性使贡献者可以一眼识别模式，并保持审计轨迹可搜索。

```text
合并到 #<MASTER> (plan-XX)。根本原因和修复顺序在那里与集群的其他部分一起跟踪——请跟随那个问题以了解进展。
```

关闭为 `not planned`（不是 `completed`）——子问题是一个症状，不是一个工作单元。

## GitHub CLI 基本操作

解决仓库：

```bash
repo_json=$(gh repo view --json owner,name)
owner=$(jq -r '.owner.login // .owner.name' <<<"$repo_json")
repo=$(jq -r '.name' <<<"$repo_json")
```

列出所有开放问题（读取所有内容的传递）。两个注意事项：
- `gh issue list --json comments` 返回的只是一个计数占位符，而不是评论正文。你必须使用 `gh issue view <N> --json comments` 按每个问题获取评论。
- 任何显式的 `--limit` 如果积压较大，会静默截断。始终先检查总开放计数。

```bash
# 1. 确认总数——永远不要相信任意的 --limit。
# 注意：GitHub 的 REST API 将 PR 视为问题，因此 /repos/{owner}/{repo} 的 .open_issues_count
# 实际上是问题 + PR。使用搜索 API 获取问题计数。
total=$(gh api "search/issues?q=repo:$owner/$repo+is:issue+is:open" --jq '.total_count')
echo "Open issues: $total"

# 2. 列出正文（设置 --limit 至少为真实总数）
gh issue list --state open --limit "$total" \
  --json number,title,body,labels,author,createdAt

# 3. 对于每个问题，获取其完整的评论线程
for n in $(gh issue list --state open --limit "$total" --json number --jq '.[].number'); do
  echo "=== Issue #$n ==="
  gh issue view "$n" --json comments \
    --jq '.comments[] | "\(.author.login) (\(.createdAt)): \(.body)"'
done
```

如果 `total > 1000`，通过 REST API 分页：`gh api "repos/$owner/$repo/issues?state=open&per_page=100&page=N"` 循环直到结果数组为空（注意这包括 PR，所以过滤 `select(.pull_request|not)`）。

打开一个计划主问题：

```bash
gh issue create \
  --title "[plan-02] Spawn-Contract Templating — 规范 ${CLAUDE_PLUGIN_ROOT} 跨主机解决方案" \
  --body-file plans/02-spawn-contract-templating.md \
  --label plan,plan-02
```

发布整合评论 + 关闭子问题：

```bash
gh issue comment <CHILD> --body "合并到 #<MASTER> (plan-XX)。根本原因和修复顺序在那里与集群的其他部分一起跟踪——请跟随那个问题以了解进展。"
gh issue close <CHILD> --reason "not planned"
```

向主问题追加 "Round N" 分派评论：

```bash
gh issue comment <MASTER> --body "$(cat <<'EOF'
**Round N 整合**

- #<CHILD> (<一行症状>) 被整合到这个计划中作为 <分类>。

提议修复：<1–3 行草图>。

添加矩阵单元：<主机/IDE/shell 组合>。
EOF
)"
```

验证最终状态：

```bash
gh issue list --state open --json number,title \
  | jq -r '.[] | "\(.number)\t\(.title)"'
```

输出应该是正好计划主问题。

## 计划主问题正文模板

保存为 `plans/0X-<slug>.md` 并用作 `--body-file` 对于主问题。

```markdown
# [plan-XX] <架构缺陷> — <一行范围>

## 缺陷

<一段话：结构上是什么被破坏了，为什么它产生了观察到的症状家族。>

## 子问题

- #N — <症状一行>
- #N — <症状一行>
- ...

## 修复顺序

1. <第一个架构变更——有界、可审查>
2. <第二个>
3. ...

## 测试矩阵

| 轴 A | 轴 B | 需要的行为 |
|---|---|---|
| ... | ... | ... |

矩阵存在于 CI 中。未来的回归必须在用户可以提交之前失败 CI。

## 超出范围

<这个计划故意不涵盖的内容，以及指向其他计划主问题的指针。>
```

## 健康检查

定期对计划主问题运行以捕获失败模式。

- **墓地主问题：** 主问题积累了 5+ 个 "Round N" 评论而没有发布 PR。该计划需要一个强制 PR 或必须被拆分。
- **过于宽泛的主问题：** 子问题的修复无法适合一个 PR。拆分为两个具有较窄范围的计划。
- **表面集群主问题：** 子问题共享主题但不是修复。按根本原因重新集群；一些子问题属于不同的计划。
- **问题与文档之间的漂移：** 计划主问题正文和 `plans/0X-*.md` 不一致。选择一个作为规范（文档），并从它重新生成问题正文。

## 停止条件

对于集群传递：停止当 `gh issue list --state open` 返回正好是主问题时。

对于分派：停止当新子问题被关闭并且主问题有一个 Round-N 条目时。

对于捆绑：停止当 PR 被合并并且每个列出的子问题都被 `Closes #N` 自动关闭时。

## 值得拒绝的失败模式

- **在完整阅读每个问题正文之前过早集群。** 不要这样做。
- **在主问题打开之前关闭子问题。** 子问题必须始终有一个重定向目标。
- **使用重定向评论来关闭不是症状的问题**（例如，没有共享根本原因的真实功能请求）。这些保持开放或有自己的跟踪。
- **在所有列出的子问题被发布之前关闭主问题。** 主问题是合同；提前关闭它会破坏审计轨迹。
