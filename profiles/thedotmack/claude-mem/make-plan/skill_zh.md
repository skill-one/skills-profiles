# 制定计划

你是一个**编排者**。分阶段创建一个LLM友好的计划，这些阶段可以在新的聊天上下文中依次执行。

## 分工模型

使用子代理进行*事实收集和提取*（文档、示例、签名、grep结果）。将*综合和计划撰写*保留给编排者（阶段边界、任务框架、最终措辞）。如果一个子代理报告不完整或缺乏证据，请在最终确定之前通过有针对性的读取/grep进行重新检查。

### 子代理报告协议（强制要求）

每个子代理的响应必须包括：
1. 查阅的来源（文件/URL）以及读取的内容
2. 具体发现（确切的API名称/签名；确切的文件路径/位置）
3. 可复制代码片段的位置（示例文件/部分）
4. "信心"注释 + 已知的空白（可能仍然缺失的内容）

如果子代理报告结论但没有来源，请拒绝并重新部署子代理。

## 计划结构

### 阶段 0：文档发现（始终为第一步）

在计划实施之前，部署"文档发现"子代理来：
1. 搜索并读取相关文档、示例和现有模式
2. 确定实际可用的API、方法和签名（而不是假设的）
3. 创建一个简短的"允许的API"列表，并引用具体的文档来源
4. 注明任何需要避免的反模式（不存在的函数、已弃用的参数）

编排者将发现结果整合为单个阶段 0 输出。

### 每个实施阶段必须包括

1. **要实现的内容** — 将任务框架设置为从文档中复制，而不是转换现有代码
   - 好："从文档/examples.ts:45-60复制V2会话模式"
   - 坏："将现有代码迁移到V2"
2. **文档引用** — 引用具体的文件/行以遵循模式
3. **验证清单** — 如何证明此阶段已工作（测试、grep检查）
4. **反模式防护** — 不应该做什么（虚构的API、未记录的参数）

### 最终阶段：验证

1. 验证所有实现与文档一致
2. 检查反模式（grep已知的不良模式）
3. 运行测试以确认功能

## 关键原则

- 文档可用性≠使用：明确要求阅读文档
- 任务框架很重要：指导代理到文档，而不仅仅是结果
- 验证>假设：要求证据，而不是关于API的假设
- 会话边界：每个阶段应该是自包含的，并具有自己的文档引用

## 需要避免的反模式

- 虚构"应该存在"的API方法
- 添加文档中未提及的参数
- 跳过验证步骤
- 假设结构而不检查示例

## 参见

- `oh-my-issues` — 问题的另一面。当你要制定的计划是基于问题或功能积压而不是新想法时，首先通过`oh-my-issues`将问题按根本原因聚类到计划主文档和`plans/0X-*.md`设计文档中。然后`make-plan`对单个计划切片的设计文档进行操作。
