# 每周摘要

生成一个项目完整 claude-mem 历史的多章节连续叙事摘要。与 `timeline-report`（一个长报告）不同——这个工具按 ISO 周生成一个摘要，每个子代理读取前一周的延续块，使故事保持连贯。

**章节数量等于时间线覆盖的 ISO 周数。** 一个有 2 周数据的项目的产出 2 个章节；一个有 30 周数据的项目的产出 30 个章节。没有固定长度——先计算周数，再根据这个数量驱动管道。

## 使用场景

当用户要求以下内容时触发：

- "每周摘要"
- "每周故事"
- "连续时间线"
- "项目[项目名]的故事章节"
- "每周运行一次摘要"
- "每周继续故事"

如果用户想要一个单一的、全面的报告，请使用 `timeline-report`。这个技能用于连续章节格式。

## 前置条件

- claude-mem 工作器正在运行
- 项目至少有一个 ISO 周的观察记录（管道可以优雅地退化——即使 N=1 也可以工作）
- 一个用户舒适的干净输出目录

**解决工作器端口**（执行一次，重用 `$WORKER_PORT`）：

```bash
WORKER_PORT="${CLAUDE_MEM_WORKER_PORT:-$(node -e "const fs=require('fs'),p=require('path'),os=require('os');const uid=(typeof process.getuid==='function'?process.getuid():77);const fallback=String(37700+(uid%100));try{const s=JSON.parse(fs.readFileSync(p.join(os.homedir(),'.claude-mem','settings.json'),'utf-8'));process.stdout.write(String(s.CLAUDE_MEM_WORKER_PORT||fallback));}catch{process.stdout.write(fallback);}" 2>/dev/null)}"
```

## 工作流程

### 第 1 步：确定项目名称

与 `timeline-report` 相同的工作树检测模式。在一个工作树中，数据源是**父项目**：

```bash
git_dir=$(git rev-parse --git-dir 2>/dev/null)
git_common_dir=$(git rev-parse --git-common-dir 2>/dev/null)
if [ "$git_dir" != "$git_common_dir" ]; then
  parent_project=$(basename "$(dirname "$git_common_dir")")
else
  parent_project=$(basename "$PWD")
fi
echo "$parent_project"
```

### 第 2 步：获取完整时间线并保存

```bash
mkdir -p .scratch
curl -s "http://localhost:${WORKER_PORT}/api/context/inject?project=PROJECT_NAME&full=true" \
  > .scratch/cm-timeline.md
wc -l .scratch/cm-timeline.md
```

合理性检查：确认文件非空，并具有预期结构（前言，然后日期标题如 `### Mon DD, YYYY`，然后数字观察行 `<id> <time> <emoji> <title>` 和会话边界行 `S<n> <prompt> (Mon DD at HH:MMpm)`）。

### 第 3 步：将时间线按 ISO 周分割成文件

编写一个 Python 脚本到 `.scratch/split-timeline.py`，要求：

1. 解析日期标题 (`### Mon DD, YYYY`)。
2. 通过 `date.isocalendar()`（周一为起始）将日期分组到 ISO 周。
3. 每周生成一个文件到 `docs/timeline-weeks/<YYYY>-W<NN>-<MonDD>-to-<MonDD>.md`，保留每天的部分原样。
4. 运行双重检查：总观察记录分布必须等于源文件中的计数。

输出结构（文件名示意）：

```
docs/timeline-weeks/
  README.md                       # 每周索引表
  YYYY-W<NN>-MonDD-to-MonDD.md    # 每个ISO周一个
  ...
```

每个每周文件应保留原始每日部分原样。在此阶段不要释义——摘要代理需要原始保真度。

**在启动管道前计算结果文件数量**。这个数量是 `TOTAL`，驱动后续所有步骤。空周（活跃周之间没有观察记录）应被跳过——管道仅对有内容的周操作。

### 第 4 步：构建每周索引 README

编写 `docs/timeline-weeks/README.md`，包含一个 markdown 表格：周 | 日期 | 观察记录 | 会话 | 文件。这成为操作员的路线图，并帮助代理理解节奏（高峰周与低谷周）。

### 第 5 步：运行连续子代理管道

**关键：子代理按顺序运行，不是并行运行。** 每个代理接收前一个代理的延续块。这是这个技能的核心——没有它你将得到 N 个独立的摘要；有了它你将得到一个 N 章节的连续叙事。

创建输出目录：

```bash
mkdir -p docs/timeline-weeks/digests
```

按时间顺序，为每个周，以任务子代理（通用型）发送以下提示模板。**等待每个代理完成再启动下一个。** 从结果中捕获延续块，并将其作为 `STORY_SO_FAR` 注入下一个提示。

#### 子代理提示模板

```
你正在编写 {PROJECT} 项目的开发历史每周摘要的第 {N} 章，共 {TOTAL} 章。第 1 到 {N-1} 章已经写完。{SPECIAL_NOTE: 例如 "这是最大的周", "这是低谷", "这是最后一章", "这是唯一的一章——既是第一周也是最后一周"}。

**源文件（完整读取）：**
{ABSOLUTE_PATH_TO_WEEK_FILE}

**输出摘要文件（写入）：**
{ABSOLUTE_PATH_TO_DIGEST_FILE}

**源文件格式键：**
- 像像 `1 7:59p 🔵 Save hook file is empty` 这样的数字行是观察记录（ID, 时间, 类型-emoji, 标题）
- `S##` 行是会话边界（启动会话的用户提示）
- Emoji 图例：🎯会话 🔴修复bug 🟣功能 🔄重构 ✅变更 🔵发现 ⚖️决策 🚨安全警报 🔐安全笔记 🤫敏感

**到目前为止的故事（从第 {N-1} 周延续）：**

{STORY_SO_FAR_BLOCK_OR_EMPTY_FOR_WEEK_1}

**你的摘要必须包括：**
1. **标题行** — `# 第 {N} 周 (W##): {DATE_RANGE} — [你选择的副标题]`
2. **一句话标签** — 这一周的内容，用普通英语表达
3. **叙事部分** ({BUDGET}) — 讲述故事。解决前几周的数据显示已解决的线索。引入新的弧线。使用具体的观察记录细节。
4. **延续/开启/解决的线索** 部分
5. **悬念/接下来会发生什么**
6. **延续块** 在文件底部，用 ```carry-forward ... ``` 括起来——为下一周的代理提供结构化交接。

**延续纪律：**
- 约 350 字。
- 严厉修剪：除非是活跃未解决的悬念，否则删除本周未出现的弧线。
- 删除 2 周以上未出现的角色，除非它们对长期弧线起支撑作用。
- 质量比完整性更重要。下一个代理会继承你提到的内容；谨慎提及。

必须包含的延续子部分：
- **活跃弧线** — 下一个代理应关注的持续主题/项目
- **角色** — 值得注意的命名系统/人员/工具（持续+新）
- **未解决** — 开放性问题或未完成的工作
- **语气笔记** — 故事是如何讲述的（声音、视角、语气演变）

**语气规则：**
- 第三人称叙述者，尖锐，观察性强。不要幼稚。
- AI 是 "Claude"；人类是 "{USER_FIRST_NAME}"。
- 将代码库组件视为角色——无论项目中的重复命名系统是什么（例如一个工作器、一个队列、一个进程管理器、一个重复的 bug、一个不可靠的迁移）。不要从其他项目导入名称；使用这个项目观察记录中出现的名称。
- 不要制造戏剧性。命名实际存在的内容。
- 每周跟踪用户的提示-语气演变（挫败标记、升级语言、语气变化）。
- 如果项目对其自身行为有元递归（例如一个记录自己工作的工具、一个调试自己的 AI 代理、一个捕获自身回归的系统），请注意。
- 观察新的反派或配角并命名他们。
- 对于低谷/沉默周：沉默就是故事。不要填充。命名未发生的事情。
- 对于激增周（>2,000 个观察记录）：选择 4-7 个脊柱弧线并讲好它们。不要罗列。

**重要：** 不要推测源文件中未包含的内容。

写入文件后返回：
1. 你写入的文件路径
2. 延续块原样
3. 一句话总结这一周
```

#### 按观察记录数量划分的叙事预算

按周的量成比例调整叙事长度：

| 观察记录数量 | 叙事部分预算 |
| --- | --- |
| < 100 | 200–400 字 |
| 100–500 | 300–600 字 |
| 500–1,500 | 500–900 字 |
| 1,500–3,000 | 700–1,100 字 |
| 3,000+ | 800–1,300 字 |

将这些填充到每个周的提示的 `{BUDGET}` 槽中。

#### 第 1 周

对于第 1 周，传递空的 `STORY_SO_FAR_BLOCK`，并指示它是起源章节——代理应建立初始角色、语气和弧线。

#### 最后 1 周

最后 1 周得到不同的结尾：**没有延续块**。相反，指示代理写入 `## 我们现在在哪里` 部分（约 250 字），命名写入时刻仍然开放的内容。告诉代理项目仍在进行中——摘要结束；故事没有结束。不要给故事一个虚假的结尾。

#### 当 N = 1（单周项目）

将两种处理方式应用于同一章节：空的 `STORY_SO_FAR_BLOCK` 和 `## 我们现在在哪里` 而不是延续块。代理在一遍中写入起源和结尾。不要引用不存在的先前或后续章节。

### 第 6 步：为可排序顺序重命名文件

代理写入的摘要文件名类似于 `YYYY-W<NN>-digest.md`。这些已经按 ISO 周排序（直到项目在一个项目名内跨越年份边界），但**添加一个零填充的数字前缀**，以便人类在浏览或脚本操作目录时顺序明确：

```bash
cd docs/timeline-weeks/digests
total=$(ls *.md | wc -l | tr -d ' ')
width=${#total}                  # 1 for N<10, 2 for N<100, 3 for N<1000
[ "$width" -lt 2 ] && width=2    # 总是填充至少 2 位以增强可读性
i=0
for f in *.md; do
  printf -v prefix "%0${width}d" $i
  mv "$f" "${prefix}-$f"
  i=$((i+1))
done
```

结果 N=30: `00-...md` 到 `29-...md`。N=4: `00-...md` 到 `03-...md`。N=120: `000-...md` 到 `119-...md`。**总是零填充**——`1-...md` 和 `10-...md` 没有零填充会排序错误。

不要在文件内部也添加顺序编号到摘要标题行。文件名前缀用于排序；标题保持干净：`# 第 N 周 (W##): 日期 — 副标题`。

### 第 7 步：报告完成

告诉用户：
- 摘要的总周数 (N)
- 输出目录路径
- 覆盖的日期范围
- 任何沉默/低谷周值得标记的
- 由最终章节代理编写或由操作员从最终代理的 `## 我们现在在哪里` 部分组成的总结性一句话。

## 管道纪律

这些规则是从端到端运行管道中产生的。每次都编码它们：

1. **按顺序，不是并行。** 整个要点是延续链。并行会破坏它。
2. **延续是有限的。** 没有主动修剪会膨胀。告诉每个代理：限制在 ~350 字，删除休眠弧线，删除缺席角色。
3. **明确跟踪语气演变。** 用户跨周提示风格是一个故事弧线。挫败标记随时间变化（无论这个项目数据中它们是什么）。命名这些变化。
4. **将组件视为角色。** 在观察记录中出现的任何重复命名系统都是这个项目的反派和配角。跨周稳定的角色构建叙事连贯性。
5. **尊重沉默。** 低谷周（10–100 个观察记录）是真实的章节。命名未发生的事情。不要填充。
6. **不要制造戏剧性。** 只观察数据。如果项目是自反的，递归就是戏剧；你不需要添加更多。
7. **最后 1 周：没有虚假结尾。** 摘要结束；项目没有结束。写 `## 我们现在在哪里`，而不是“结束”。

## 错误处理

- **空时间线**：项目名称错误，或工作器未运行。`curl -s "http://localhost:${WORKER_PORT}/api/search?query=*&limit=1"` 验证。
- **工作器未运行**：通过你的常规方法启动它或检查 `ps aux | grep worker-service`。
- **子代理返回格式错误的延续**：通过正则表达式（` ```carry-forward ... ``` `）提取延续块并原样传递。如果缺失，要求代理重试，并明确指示“你的回复必须包括用 ```carry-forward ... ``` 括起来的延续块，在文件末尾”。
- **一个代理在管道中途失败**：重试该周，使用相同的延续。不要跳过——链会中断。
- **延续增长超过 ~500 字**：在后续提示中收紧纪律指令。明确要求修剪。

## 示例

### 长期项目 (~30 周)

用户：“为 [项目] 从头到尾制作每周摘要”

1. 解决工作器端口，检测项目名称。
2. 获取完整时间线 → `.scratch/cm-timeline.md`。
3. 运行 `.scratch/split-timeline.py` → N 个每周文件在 `docs/timeline-weeks/`（例如 30）。
4. 生成 `docs/timeline-weeks/README.md` 索引。
5. 连续启动 N 个子代理，每周一个。每个代理都接收前一周的延续。第 1 章开始时 `STORY_SO_FAR_BLOCK` 为空；最后 1 章写入 `## 我们现在在哪里` 而不是延续块。
6. 重命名摘要，添加零填充的顺序前缀（`00-...md` 到 `29-...md`）。
7. 报告总章节数、日期范围、任何低谷/高峰值得标记的、最终代理生成的总结性一句话。

### 短期项目 (~3 周)

相同流程，只是规模更小。N=3，所以：
- 章节 1：空的 `STORY_SO_FAR_BLOCK`，建立角色/语气/弧线。
- 章节 2：接收章节 1 的延续，在此基础上构建。
- 章节 3：接收章节 2 的延续，但得到最后章节的处理（`## 我们现在在哪里` 而不是延续块）。
- 文件名：`00-...md`，`01-...md`，`02-...md`。

### 单周项目 (N=1)

将两种处理方式应用于唯一章节：空的 `STORY_SO_FAR_BLOCK`，`## 我们现在在哪里` 结尾，没有跨章节引用。文件名：`00-...md`。
