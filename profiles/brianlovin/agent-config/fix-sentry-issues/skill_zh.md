# 解决 Sentry 问题

## 原则

**Sentry 错误不是问题，它是一个信号。**

你的目标不是关闭 Sentry 问题。你的目标是发现根本原因，理解应用程序出错了什么，并修复潜在缺陷。正确地完成这些后，关闭 Sentry 问题只是一个副作用。

问 **"为什么会失败？"** — 而不是 **"如何让 Sentry 安静？"** 永远不要将日志级别更改视为修复。回退路径意味着用户体验下降；追踪主路径失败的原因并在上游修复它。

## 反模式（不要这样做）

- **未经调查就批量归类为"预期"**。看到回退并不意味着你理解了失败。追踪完整的输入路径。
- **将"有回退"视为"不是问题"**。主路径为什么会失败？我们能在上游阻止它吗？
- **将多个问题合并到一个 PR 中**。每个问题都有自己的根本原因。单独修复（除非调查证明原因相同）。
- **丢弃错误详情**。永远不要从 `catch (error)` 中移除 `error`，或者剥离状态码。这些数据是你理解失败的方式。
- **在分派时决定修复方案**。只分类为"调查"或"忽略"。你不知道修复方案，直到调查完成。

**日志级别降级仅在真正预期的状态**（例如，可选列缺失、资源已删除）时有效** — 而不是用于有回退的失败。

## 第一阶段：发现与分派

使用 Sentry MCP（首先使用 `ToolSearch` 加载工具）：`find_organizations` → `find_projects` → `search_issues` 使用 `naturalLanguageQuery: "所有未解决的按事件排序的问题"`。

构建分派表格。操作 = **调查** 或 **忽略** 仅：

| ID | 标题 | 事件 | 操作 | 原因 |
|----|-------|--------|--------|--------|
| PROJ-A | 保存时出错 | 14 | 调查 | 用户可见的保存失败 |
| PROJ-B | GM_register... | 3 | 忽略 | Greasemonkey 扩展 |

**调查**：多个事件、用户体验下降、高量级警告、每次运行都重复出现。
**忽略**：浏览器扩展代码、`ChunkLoadError`（自我解决）、单事件瞬态、已修复。

应用：`mcp__sentry__update_issue(..., status: "ignored")` 或 `status: "resolved"` 用于已修复。

## 第二阶段：调查（一次一个问题）

按顺序完成这些步骤。不要跳过或批量处理问题。

1. **拉取事件级数据** — 问题摘要隐藏了细节。使用 `get_issue_details` 和 `search_issue_events` 使用 `naturalLanguageQuery: "所有带额外数据的事件"`。提取：URL、参数、堆栈跟踪、状态码、时间戳。

2. **交叉引用 Axiom** — 事件有 `traceId`。`axiom query "['shiori-events'] | where traceId == '<traceId>'" -f json` 获取周围上下文（authMethod、client_version、请求元数据）。

3. **阅读失败代码路径** — 跟随堆栈跟踪。阅读每个文件。在提出更改前理解它。

4. **向上游追踪输入路径** *(最常被跳过，最重要)* — 哪些数据到达了失败的函数？它本应到达这个路径吗？是否有缺失的过滤器？输入是否错误（二进制 URL、重定向、格式错误）？我们能在上游阻止错误输入吗？

5. **复现** — 使用 Sentry 中的实际失败输入。用确切的数据调用函数。`fetch()` 超时的 URL。验证你的理解。

6. **识别根本原因** — 为什么这个输入会失败？为什么它会到达这个路径？正确的修复是什么？（例如，"在 Firecrawl 之前过滤二进制 URL" — 而不是"抑制日志"）

| 模式 | 真正的修复 |
|---------|----------|
| 外部 API 在某些 URL 上失败 | 在发送前过滤/验证输入 |
| 超时 | 调查什么很慢；调整超时或输入大小 |
| DB "无效 json" | 插入前清理 |
| 定时任务上的陈旧引用 | 检测陈旧性，自动清理 |

## 第三阶段：修复

每个问题一个分支。`git checkout main && git pull && git checkout -b fix/<描述性名称>`

- **先写测试** — 使用实际 Sentry 事件的数据。修复前测试失败，修复后通过。
- **实现** — 修复根本原因，而不是症状。如果修复主要是日志级别更改，停止：你调查了为什么失败，还是只是抑制？
- **验证** — 测试通过，代码风格检查通过，修复处理了实际失败的输入。
- **PR** — 包括 **根本原因**（上游原因）和 **修复**（更改了什么以及为什么阻止了失败）。合并后才能在 Sentry 中解决。
