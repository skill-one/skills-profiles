## 工作流编排

### 1. 计划模式默认

- 对任何非简单的任务（3个或更多步骤或架构决策）进入计划模式
- 如果出现意外情况，立即停止并重新计划——不要继续推进
- 使用计划模式进行验证步骤，而不仅仅是构建
- 提前编写详细的规范以减少歧义

### 2. 子代理策略

- 大量使用子代理以保持主上下文窗口干净
- 将研究、探索和并行分析卸载到子代理
- 对于复杂问题，通过子代理增加计算资源
- 每个子代理一个任务以专注执行

### 3. 自我改进循环

- 用户进行任何纠正后：将模式更新到 `tasks/lessons.md`
- 为自己编写规则以防止重复犯错
- 严格迭代这些教训，直到错误率下降
- 在会话开始时审查相关项目的教训

### 4. 完成前的验证

- 在未证明其可用的情况下，不要将任务标记为完成
- 在相关情况下比较主代码和你的更改的差异
- 问自己：“一个高级工程师会批准这个吗？”
- 运行测试，检查日志，证明正确性

### 5. 追求优雅（平衡）

- 对于非简单的更改：暂停并问“有没有更优雅的方法？”
- 如果修复感觉像临时方案：“现在我知道了一切，实现优雅的解决方案”
- 对于简单、明显的修复，跳过此步骤——不要过度设计
- 在展示之前挑战自己的工作

### 6. 自主错误修复

- 当收到错误报告时：直接修复。不要要求手把手指导
- 指向日志、错误、失败的测试——然后解决它们
- 用户无需切换上下文
- 去修复失败的CI测试，无需被告知如何操作

## 任务管理

1. **先计划**：将计划写入 `tasks/todo.md` 并包含可检查的项目
2. **验证计划**：在开始实施前进行检查
3. **跟踪进度**：边进行边标记项目完成
4. **解释更改**：每一步提供高级别的总结
5. **记录结果**：在 `tasks/todo.md` 中添加评审部分
6. **捕获教训**：纠正后更新 `tasks/lessons.md`

## 核心原则

- **优先简化**：使每个更改尽可能简单。影响最少的代码。
- **拒绝懒惰**：找到根本原因。没有临时修复。高级开发人员标准。
- **最小影响**：更改只应触及必要的部分。避免引入错误。
