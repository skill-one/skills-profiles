# 测试驱动开发

## 哲学

**核心原则**：测试应该通过公共接口验证行为，而不是实现细节。代码可以完全改变；测试不应该改变。

**好的测试**是集成式的：它们通过公共API执行真实的代码路径。它们描述系统_做什么_，而不是_如何_做。一个好的测试读起来像规范 - "用户可以使用有效的购物车结账"准确地告诉你存在什么功能。这些测试能够经受重构，因为它们不关心内部结构。

**坏的测试**与实现耦合。它们模拟内部协作、测试私有方法，或通过外部方式验证（例如直接查询数据库而不是使用接口）。警告信号：当你重构时测试失败，但行为没有改变。如果你重命名一个内部函数并且测试失败，那么这些测试是在测试实现，而不是行为。

参见[tests.md](tests.md)获取示例和[mocking.md](mocking.md)获取模拟指南。

## 反模式：水平切片

**不要先写所有测试，然后写所有实现。** 这就是"水平切片" - 将RED视为"写所有测试"，将GREEN视为"写所有代码"。

这会产生**糟糕的测试**：

- 大批量编写的测试测试的是_想象中的_行为，而不是_实际_行为
- 你最终测试的是事物的_形状_（数据结构、函数签名），而不是面向用户的行为
- 测试对真实变化变得不敏感 - 当行为破坏时它们通过，当行为正常时它们失败
- 你超出了你的视野，在理解实现之前就承诺测试结构

**正确方法**：通过跟踪弹头进行垂直切片。一个测试 → 一个实现 → 重复。每个测试响应你从上一个周期学到的内容。因为你刚刚编写了代码，你知道确切的行为是什么以及如何验证它。

```
错误（水平）:
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确（垂直）:
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
  ...
```

## 工作流程

### 1. 规划

在编写任何代码之前：

- [ ] 与用户确认需要哪些接口变更
- [ ] 与用户确认要测试哪些行为（优先级）
- [ ] 识别[深度模块](deep-modules.md)的机会（小接口，深实现）
- [ ] 设计[可测试性](interface-design.md)的接口
- [ ] 列出要测试的行为（不是实现步骤）
- [ ] 获得用户对计划的批准

问： "公共接口应该是什么样子？哪些行为是最重要的要测试的？"

**你不能测试所有东西。** 与用户确认哪些行为最重要。将测试工作重点放在关键路径和复杂逻辑上，而不是每个可能的边缘情况。

### 2. 跟踪弹头

编写一个测试来确认系统的一件事：

```
RED:   为第一个行为编写测试 → 测试失败
GREEN: 编写最小的代码以通过 → 测试通过
```

这是你的跟踪弹头 - 证明端到端路径是有效的。

### 3. 增量循环

对于每个剩余的行为：

```
RED:   编写下一个测试 → 失败
GREEN: 最小的代码以通过 → 通过
```

规则：

- 一个测试一次
- 只要有足够的代码通过当前测试
- 不要预期未来的测试
- 保持测试专注于可观察的行为

### 4. 重构

所有测试通过后，查找[重构候选](refactoring.md)：

- [ ] 提取重复
- [ ] 深化模块（将复杂性隐藏在简单的接口后面）
- [ ] 在自然的地方应用SOLID原则
- [ ] 考虑新代码揭示了现有代码的哪些信息
- [ ] 每次重构步骤后运行测试

**在RED时不要重构。** 先达到GREEN。

## 每个周期的检查清单

```
[ ] 测试描述行为，而不是实现
[ ] 测试只使用公共接口
[ ] 测试能够经受内部重构
[ ] 代码对这个测试是最小的
[ ] 没有添加推测性功能
```
