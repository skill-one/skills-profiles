# 迁移 Expo 模块

在不更改其可观察的 JS API 的情况下，迁移现有 Expo 模块的 Swift 部分。将当前的 JS/TypeScript 界面和测试视为兼容性契约。除非用户明确扩展任务，否则将 Kotlin 留在 1.0 DSL 上。

## 前置条件

使用 `expo` `57.0.21` 或更高版本。较早的 `57.x` 版本可以编译宏，但缺少许多 2.0 功能和性能优化，因此不要以它们为目标。编辑之前，检查目标安装的版本（`package.json`/lockfile 中的 `expo`，或 `npm ls expo`）。如果它较旧，请停止并告诉用户先升级。

检查示例应用的自己的 `package.json`，而不仅仅是模块根。示例应用是你在第 4 步中构建和启动的集成界面，因此它需要相同的基础。

这是一个基础，而不是保证：`57.x` 内确切的宏和核心界面仍然存在差异，因此第 2 步必须仍然验证签出的源。

SDK 57 将宏作为 **实验性和未记录的** 提供，官方 Beta 版本在 SDK 58 中。API 仍然可能在你下面发生变化。在进行大规模迁移之前，告诉用户这一点，并优先选择增量混合模式而不是整体转换模块。

## 参考

- 在更改源之前阅读 `references/migration-map.md`。它包含 1.0 到 2.0 的映射、语义陷阱和混合模式规则。
- 阅读 `references/example.md`，以了解一个模块通过混合模式到完整迁移的完整前后演练。当你需要查看每个成员规则如何组合时，请参考它。
- 当签出的 `expo-modules-core` 版本或分支不知道支持每个请求的宏时，阅读 `references/compatibility.md`。它解释了如何验证实际的编译时和运行时界面，而不是根据版本号猜测，并列出了宏插件通过 `0.10.0` 获得了什么。

## 工作流程

### 1. 建立契约

编辑之前，检查存储库说明和工作树。定位 Swift 模块类、记录、共享对象、原生视图、JS/TS 绑定、测试、示例应用、podspec、`expo-module.config.json` 以及安装或签出的 `expo-modules-core`。

在重写每个导出项之前，列出每个项：

- 模块和共享对象 JS 名称
- 函数名称、参数数量、标签、默认值、可空性、同步/异步行为、错误和队列/线程语义（注意哪些 `AsyncFunction` 身体执行阻塞或长时间运行的工作，以及任何 `.runOnQueue(...)`）
- 属性名称、可变性以及常量缓存行为
- 事件线名称和有效载荷形状
- 记录字段名称、默认值、必需性以及可空性
- 共享对象构造函数和实例/静态位置（`Function` 与 `StaticFunction`/`StaticAsyncFunction`）
- 生命周期钩子和视图

使用 TypeScript 声明和 JS 调用位置来解决歧义。在语法迁移期间不要无声地“改进”必需性、重命名事件或更改同步行为。

### 2. 验证可用的 2.0 界面

检查目标实际使用的依赖项中的宏声明和匹配的核心钩子。不要假设 2.0 设计中的所有项都存在，因为一个宏可以编译。

将每个 1.0 项分类为：

- **迁移**：它的宏和必需的核心运行时支持都存在。
- **保留在 DSL 中**：混合模式安全地保留它，或者 2.0 缺少等效项。
- **阻止**：迁移会更改 JS 契约或需要不可用的运行时支持。

优先选择增量混合模式结果而不是推测生成的代码。保留任何剩余的 DSL 元素的 `definition()`；只有当它为空并且解析的模块名称由 `@ExpoModule` 保留时才删除它。

### 3. 应用迁移

一次迁移一个语义组：模块命名、函数、属性/常量、事件、共享对象，然后是记录。保持 diff 窄。

遵循这些不变量：

- 当 Swift 命名规则或宏默认值与不同时，显式保留每个现有的 JS 可见名称。
- 保持原始可选/默认行为。一个可选的 1.0 记录字段仅仅因为 2.0 可以表达必需字段而不会变为必需。
- 除非签出的宏组和解发它们，否则不要迁移同 JS 名称的重载。
- 保留异步线程行为。1.0 的 `AsyncFunction` 身体在 JS 线程之外运行；2.0 的 `async` `@JS` 成员从它开始并在第一个 `await` 时离开。一个从不等待的身体因此阻塞 JS 线程，JS 签名没有变化。审核第一个 `await` 之前运行的内容，并且永远不要在 JS 实体上留下阻塞 I/O。使用 `@JS(.concurrent)` 修复，或者重构到 Swift 并发或延续上。队列固定的函数得到相同的处理。参见 `references/migration-map.md` 中的线程部分。
- 在迁移视图、联合、同步事件、共享对象静态成员或自由形式 `Any` 参数之前验证核心支持。宏插件在所有这些方面都领先于核心，因此检查签出的核心而不是插件版本，并将不支持的成员保留在 1.0 DSL 上。`references/compatibility.md` 有每个功能的能力检查。
- 保持 `expo-module.config.json` 列出每个模块类在 `apple.modules` 下。条目是裸的 Swift 类名，因此迁移期间重命名类会无声地断开模块：它构建，然后在运行时不存在。迁移的类也必须保持 `public` 或 `open`。SDK 58 的自动发现是淘汰这些条目的原因。
- 除非用户请求 API 更改，否则不要更改 Kotlin、JS 包装器或公共 `.d.ts` 文件。
- 永远不要将宏生成的符号写入模块的源。宏发出它们；手写或覆盖它们不是迁移的一部分。

每次迁移一组后，搜索应该已移动的旧 DSL 条目和调用位置。避免广泛的格式化或无关的清理。

### 当 2.0 等价项缺失或一组失败时

当第 2 步将一个项分类为 **阻止**，或者迁移的一组失败构建或破坏契约时，不要强迫它。在那个组上停止并：

1. **询问用户如何进行** 该项，有两个选项：
   - **共存**：在迁移的 `@ExpoModule`（混合模式）旁边保留该项在 1.0 `definition()` DSL 中，并继续处理其他组。
   - **回滚**：回滚该组的编辑，将其保留为未更改的 1.0 状态，然后继续。

   当混合模式被验证为安全时，默认选择共存，因为它保留了最多的进度。当半完成的更改将模块置于无法增量修复的非构建状态时，选择回滚。

2. **在 `expo/expo` 上打开一个跟踪问题**，注明 2.0 尚未涵盖的功能，以便记录差距而不是无声地绕过。使用 `gh issue create --repo expo/expo` 并在发布前与用户确认（根据存储库约定，未经批准不要发布面向外部的评论）。包括：
   - 1.0 成员及其 JS 契约
   - 缺失的具体宏或核心钩子（引用 `references/compatibility.md` 中的证据差距）
   - 签出的 `expo-modules-core` 版本/分支

   在手交中引用该问题，以便剩余的 DSL 条目可以追溯到已知限制。

继续处理顺利迁移的组；一个阻止的成员不会阻止其他成员。

### 4. 验证行为

首先运行最窄的可用检查，然后是真实的集成界面：

1. 将 Apple 模块与目标 `expo-modules-core` 构建或类型检查。
2. 运行原生单元测试和 JS/TS 测试。
3. 如果存储库提供示例应用，则构建并启动它。
4. 确认 `expo-module.config.json` 仍然为 `apple.modules` 下命名每个模块类，与 Swift 类名保持一致。陈旧的条目构建干净，仅在运行时失败，因此示例应用必须实际解析模块，而不仅仅是编译。
5. 将最终导出的界面与第 1 步的清单进行比较。
6. 搜索陈旧的 `Name`、迁移的 `Function`/`AsyncFunction`/`StaticFunction`/`StaticAsyncFunction`/`Property`/`Constant`/`Events` 条目、旧的 `sendEvent` 调用、`@Field` 和重复注册。搜索你编写的源，而不是宏扩展输出。

单独的扩展测试是不充分的：生成的宏代码可以看起来正确，但在与不匹配的核心链接或运行时失败。如果依赖项更改或宏插件标志缺失，按适当方式重新安装 JS 依赖项，运行存储库的 CocoaPods 安装工作流，并在诊断插件通信失败之前重启 Xcode。

## 手交

永远不要向用户打印宏生成的或核心内部符号名称。`references/compatibility.md` 引用了它们，以便你可以用它们进行 grep，但它们是实施细节，在插件版本之间会发生变化，并且在报告中是噪音。通过宏（`@JS static`、`@Event(sync:)`）和可观察的 JS 行为命名功能。说“已安装的核心尚未支持解码自由形式字典参数”，而不是缺失方法的名称。例外是在 `expo/expo` 上的跟踪问题，其中具体的缺失钩子是重点。

报告：

- 哪些成员迁移到 2.0
- 哪些成员有意保留在 1.0 DSL 中及其原因
- 任何兼容性敏感的选择，尤其是事件名称、记录必需性、常量和队列
- 运行的命令和任何未完成的验证

## 提交反馈
如果你遇到错误、误导性或过时的信息，请报告给 Expo 以改进：
```bash
npx --yes submit-expo-feedback@latest --category skills --subject "expo-migrate-module" "<可操作的反馈>"
```
只有当你有具体且可操作的反馈时才提交。尽可能提供相关的上下文。
如果 AI 代理反复失败或用户不得不接管 Expo 任务，加载 `expo-skill-feedback` 技能并遵循其 eval-candidate 流程，而不是重复使用上面的命令。
