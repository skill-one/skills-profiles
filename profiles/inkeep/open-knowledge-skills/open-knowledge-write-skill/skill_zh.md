# 编写 OpenKnowledge 技能

你正在帮助用户编写一个 **代理技能** —— 一个 `SKILL.md` 文件（以及可选的 `references/` 和 `scripts/` 文件夹），用于指导 AI 代理如何执行一项重复性任务。在 OpenKnowledge 中，技能是一种一等、版本化、可安装的工件：你使用 `write` / `edit` 技能动词来编写它，然后将其安装到用户的编辑器中。

技能的价值在于它们能够在 **正确的时机被识别** 并 **被忠实地遵循**。大部分的技巧在于两个地方：一个可靠触发的 `description`，以及一个足够简短具体的主体，让代理能够真正执行它所说的内容。按顺序完成以下步骤，但可以跳转到用户当前的进度。

## 第 1 步 — 捕获意图并分类技能

**门禁 — 在构建之前检查是否已存在。** 首先使用 `skills({})` 列出已管理的技能，然后使用 `skills({ name })` 读取任何可能的匹配项；这些是 OpenKnowledge 已管理的项目/全局技能。在起草时之前，使用 `skills({ query: "<2-4 触发词>" })` 搜索公共市场，当任务听起来超出当前项目的可重用时。每个市场行返回 `name`、`source` 和 `description`；检查最强大的描述，然后使用 `import({ source, skill: name, add: [...] })` 导入一个候选者，并且只有在重用是正确选择时才进行修改。仅在 OK MCP 的 `skills({ query })` 路径不可用时，才使用 Vercel 的 `find-skills` 技能、`npx skills find <query>` 或手动 `skills.sh` 搜索。如果用户已经打开了一个技能页面，请将完整的技能页面 URL 作为 `source` 传递，例如 `import({ source: "https://www.skills.sh/<owner>/<repo>/<skill>", add: [...] })` — 中间部分是 REPO，而不是字面的 `skills`。在此流程中不要运行 `npx skills add`，因为默认安装路径是：通过 OpenKnowledge (`import({ source, skill, add })`) 导入，这样技能会作为一个真实的文件夹，带有可追溯性、版本控制和管理的扩散；`add` 指定它去哪里，`install` 之后改变它的位置。使用用户请求中的 2-4 个具体触发短语加上域名或工具名称，然后打开/阅读最强劲候选者的描述，再进行判断。如果现有或公共技能涵盖了大部分内容，请停止并 **建议重用** —— 几乎重复且触发词重叠会导致误触发并稀释两者。如果公共技能接近但不完全相同，请与用户决定是否将其导入/修改到 OpenKnowledge 中，使用 Skills CLI 在 OK 外安装，或编写一个更窄的辅助技能，其 `description` 明确地将控制权交给它。只有在它确实不同时才构建新技能。在起草或编写任何内容之前，展示重叠和已安装技能加上市场搜索结果。这是一个披露门禁：告诉用户你检查了什么，什么匹配了，以及为什么重用/导入/修改/新技能是下一步正确的操作。在技能编写完成后永远不要发现重叠。如果 `skills({ query })` / `skills.sh` 无法访问，请明确说明并继续进行已安装技能检查。

只问你能推断不到的问题：

- **这个技能应该处理什么重复性任务**？得到一个具体的例子。
- **技能类型**，因为它决定了应用的严格程度：
  - **参考/技术**（大多数技能）—— "如何做 X。" 正文，示例。
  - **学科** —— 强制代理在压力下倾向于跳过的一种行为（例如："始终先写一个失败的测试"）。这些需要在第 4-6 步中进行压力测试；参考技能不需要。
- **自由度**（根据任务脆弱性校准主体精确度）：
  *高*（自由文本 — 判断任务），*中*（参数化步骤），*低*（一个固定的 `scripts/` 命令 — 当任何偏差导致结果失败时）。不要过度指定判断任务或低估脆弱任务。

## 第 2 步 — 首先解决范围（永远不要无声推断）

范围决定了技能的存储位置以及 `install` 的扩散范围。这是用户的决定，并且有不同的影响范围 — 使其明确。

| 范围 | 存储在 | `install` 扩散到 |
| --- | --- | --- |
| **全局** | 你家技能根目录下的真实文件夹（例如 `~/.claude/skills/<name>/`） | 你的编辑器，在 **每个** 项目中 |
| **项目** | 当前仓库技能根目录下的真实文件夹（例如 `.claude/skills/<name>/` 或 `.agents/skills/` 中心 — 通过 git 共享） | 当前项目的编辑器；队友在 `git pull` 时获得 |

默认启发式算法：在 OK 项目内，任务特定于它 → **项目**；"适用于我的所有工作 / 全局" → **全局**；否则问一个问题。在编写之前说明选择及其后果。

**正在开发技能仓库或插件？那么两者都不适用。** 如果你正在工作的仓库本身是一个技能 *分发* — 一个插件（例如 `.claude-plugin/` 声明或市场列表）或一个将技能作为 `skills/<name>/` 存放供他人导入的目录仓库 — 你正在编写的技能是该仓库的 **产品**，而不是安装到其中。按照仓库自己的布局，在它的兄弟技能旁边编写它，遵循仓库已经使用的格式。**不要** 将其放在 `.claude/skills/` 或 `.agents/skills/` 下，并且**不要** `install` 它：消费者通过安装插件或从仓库导入来获取它，而插件的自身仓库不会加载任何来自自身的内容。`install` 仅适用于当前项目或用户应加载的技能。如果你不确定该仓库是分发还是消费者，请询问 — 写到错误的位置会导致技能无人能找到。

## 第 3 步 — 规划内容

- **主体** = 持久化、可重用的指令 — 不超过 500 行。如果它增长到超过这个长度，请将深度移动到 `references/<topic>.md`（仅在需要时加载），并从主体指向它。对于 **项目** 技能，参考会自动在图中连接，无论主体如何提及，反引号 `` `references/<topic>.md` ``
路径都可以；仅在您希望提及是可点击的内联链接时，才使用 `[[references/<topic>]]` 维基链接。对于 **全局** 技能，使用普通的反引号路径 — 全局参考不是图文档，所以在那里使用维基链接会悬空。保持参考 **一级深度**。
- **不要包含**：README/CHANGELOG/QUICK_REFERENCE、技能本身的安装说明、版本历史或任何主机特定内容。技能是说明，而不是关于说明的文档。
- 对于 **学科** 技能，规划你正在纠正的失败模式以及你将如何证明该技能修复了它（第 4 步）。

## 第 4 步 — RED 基线（仅限学科技能）

在编写技能之前，在没有技能的情况下运行场景并捕获代理做错的事情 — 逐字记录，包括它的理由（"测试太简单所以我跳过了"）。这些理由是技能主体必须关闭的确切漏洞。在一个新的代理会话中重新运行场景，技能不存在 — 一个新的聊天、一个子代理或第二个终端 — 并保留会话记录；如果你没有办法干净地运行它，请与用户一起推理基线。对于普通的参考技能，跳过此阶段。

## 第 5 步 — 起草技能

使用技能动词（fs-direct；如果服务器正在运行，实时预览会更新）编写源代码：

```
write({ skill: { name: "<lowercase-hyphen-name>", description: "<triggers>", body: "<markdown>", scope: "project" } })
```

前文合同（在编写时验证 — 得到正确的）：
- `name` — 小写字母、数字、连字符；≤64；**等于目录名**。
- `description` — **≤1024 字符，无 XML 标签，无 `version` 字段**。见第 7 步。
- 除此之外。OK 从不注入自己的前文；账本存在于 `.ok/`。

将主体作为对代理的直接指令编写（祈使句，第二人称），具体而不是抽象。

通过技能动词添加深度文件 — `references/*.md`（按需加载）和 `scripts/*`（显示为文本，OK 永不执行） — 永远不要使用原生的 `Write`/`cat`：

```
# 写一个或多个包文件（与主体无关 — 无需重新发送 SKILL.md）
write({ skill: { name: "<name>", files: [{ path: "references/tiers.md", content: "..." }] } })

# 在一个包文件中进行外科手术编辑（镜像 `edit({ document })`）
edit({ skill: { name: "<name>", file: "references/tiers.md", find: "...", replace: "..." } })

# 列出包，然后读取一个文件（没有原生的 `cat`）
skills({ name: "<name>" })                         # → files: [{ path, kind }]
skills({ name: "<name>", file: "references/tiers.md" })   # → { path, kind, text }

# 删除特定的包文件（省略 `files` 以删除整个技能）
delete({ skill: { name: "<name>", files: ["references/tiers.md"] } })
```

路径是技能相对的，并且必须保持在技能目录内（没有 `../`，没有绝对路径）。`references/` 和 `scripts/` 是常规的家园，也是首选的；其他根（`assets/`，每个 harness 目录）也是接受的，因为发布的技能会发送它们，并且导入会原样保留它们。保持参考一级深度。一个项目的 `.md` 参考成为一个自动连接到其 SKILL 的实时内容文档，无论主体如何提及 — 反引号 `` `references/<name>.md` `` 路径就像 `[[references/<name>]]` 维基链接一样连接到图中。仅在您希望获得可点击的内联链接时，才使用维基链接（或 `[label](references/<name>.md)`）。

全局技能不同：它们的参考不是图文档，所以使用普通的反引号路径。维基链接会在那里悬空。

## 第 6 步 — GREEN 评估 + 重构

使用技能重新运行场景。对于学科技能，**进行压力测试**：组合 2-3 个压力（时间、权威、沉没成本），并确认代理仍然遵循规则 — 然后修补任何漏洞并重新测试（`references/pressure-testing.md`）。对于参考技能，确认代理现在正确执行任务，并且主体不是比它需要的更长。删除代理已经知道的内容。

## 第 7 步 — 优化描述（这是使技能触发的关键）

描述是代理在决定是否加载技能时看到的**唯一**东西。得到正确的 (`references/description-optimization.md`)：
- **触发词，而不是摘要。** 用用户的语言和措辞说明何时使用它 — **不是** 主体的工作流程摘要。在描述中总结工作流程会使代理遵循描述并跳过主体。
- **具体且稍微强硬** 以对抗触发不足：命名应激活它的情境、动词和措辞。
- 与近失查询进行精神检查：应该触发它的措辞和不应触发的相邻措辞。

## 第 8 步 — 安装（选择它可用的位置）

技能已经为读取它所在的文件夹中的任何代理而活着 — 它自己的文件夹就是技能（没有草稿状态）。`install` 管理它在哪里还可以使用，加性：

```
install({ name: "<name>", add: ["codex", "opencode"] })   // 添加位置
install({ name: "<name>", remove: ["codex"] })            // 移除位置
install({ name: "<name>", add: ["codex"], mode: "link" }) // ...作为符号链接
install({ name: "<name>", convert: ["codex"], mode: "copy" })  // 改变一个位置的形式
install({ name: "<name>", source: ".team/skills" })       // 移动真实文件夹（单独运行）
```

位置 ID 是编辑器主机 ID (`claude` … `pi`), `agents`（供应商中立的中心），或自定义根路径，如 `.team/skills`。

**位置采取的形式。** `mode` 仅适用于调用命名的位置 — 那些在 `add` 中，或在 `convert` 中 — 以及其他任何东西。在 `add` 上省略它，新的位置将采用技能已经使用的形式。没有技能范围的模式：安装永远不会重写你没有命名的位置。

**每个形式的意义。** 符号链接指向源，所以它不能漂移。副本是其自己的文件夹并自动从源刷新 — 直到有人手动编辑它，届时它会分支，并且永远不会再次被覆盖。

**生命周期。** 使用 `edit({ skill })` 编辑；它路由到源并在原地版本化。没有 "卸载所有" — 移除所有其他位置仍然会为它的代理加载源文件夹，并且技能仅通过 `delete({ skill })` 停止存在，它会移除源和每个位置。使用 `history({ skill })` → `restore_version({ skill, version })` 回滚**项目**技能；全局技能在此构建中是无版本的。对于项目技能，提交技能文件夹 — 它们是 git 中的普通文件，所以队友在 `pull` 时会获得它们。

## 提醒

- 优先考虑一个良好的技能而不是许多重叠的技能；仅在触发词不同时才拆分。（第 1 步的门禁就是在这里强制执行这一点 — 不要留下重叠以备后查。）
- 范围是唯一的位置决策 — 不要将 harness/format/toolchain 假设折叠到其中，并且不要将一个假设嵌入范围问题的措辞中。你正在编写一个 OpenKnowledge 技能：使用 `write({ skill })` 编写它 — 它会作为一个真实的文件夹出现在项目的默认技能家园，带有可追溯性和版本控制 — 并使用 `install` 扩散；不要手动分散副本到编辑器目录中，因为 `install` 拥有扩散并从源刷新未编辑的副本（手动编辑的副本会分支并停止刷新）。如果你加载这个流程，请通过它进行编写。
- 将关于技能行为（版本控制、安装目标、范围语义）的声明基于此指南或工具描述 — 不要从假设中断言系统事实。
- 避免没有说明理由的笼统的 ALWAYS/NEVER 规则 — 它们看起来像噪音并且会被忽略。解释原因。
- 一个具有可执行 `scripts/` 的技能会逐字投影到另一个代理的信任域 — 只包括用户已审查的脚本。
