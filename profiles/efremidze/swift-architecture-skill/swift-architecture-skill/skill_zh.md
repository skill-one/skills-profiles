# Swift 架构技能

## 概述

使用此技能为 SwiftUI/UIKit 代码库选择最佳 Swift 架构方案，并将其应用于用户的任务。

要快速浏览不同方案，请使用 `references/_index.md`。

## 快速路径

在选择架构之前，始终捕获以下信息：
- 任务类型（新功能、重构、PR 审查、调试）
- UI 堆栈（SwiftUI、UIKit 或混合）
- 最小部署目标（iOS 17+ 支持 `@Observable`；iOS 16 需要 `ObservableObject`）
- 范围（单屏、多屏、全局应用）
- 状态和效果复杂度
- 团队熟悉度和依赖容忍度
- 现有约定

然后：
- 如果用户明确指定了架构，将其视为初始候选方案并先进行适配检查
- 如果未指定架构，加载 `references/selection-guide.md` 并根据所述约束推断最佳适配方案
- 如果最佳适配方案结合了多种模式，为功能边界命名一个 **主要** 方案，为支持性关注点命名一个 **次要** 方案
- 选择 **快速推荐模式** 进行单功能指导，约束条件清晰
- 选择 **深度重构模式** 进行迁移、混合架构或模块边界变更

## 快速推荐模式

在以下情况下使用此模式：
- 范围为单个功能或屏幕
- 约束条件清晰到可以推荐一个主要模式
- 用户主要需要推荐、脚手架或审查清单

交付：
- 适配结果（`fit` 或 `mismatch`）
- 基于请求的 1-2 个原因
- 选定的参考文件
- 针对功能的具体结构、状态、依赖、异步和测试指导

## 深度重构模式

在以下情况下使用此模式：
- 请求跨越多个模块或屏幕
- 代码库已经混合了架构
- 用户正在从一种模式迁移到另一种模式

交付：
- 当前状态评估
- 目标架构推荐（包含适配结果）
- 带有边界变更的增量迁移路径
- 过渡过程中的风险、权衡和验证点

## 架构路由器

如果用户明确指定了架构，将其视为初始候选方案并在提交前进行适配检查：
- 验证 UI 堆栈适配（SwiftUI/UIKit/mixed）、状态复杂度、效果编排需求、团队熟悉度和现有代码库约定
- 如果适配，继续使用请求的架构
- 如果与关键约束不匹配，明确解释不匹配情况并推荐 `references/selection-guide.md` 中最接近的替代方案
- 如果用户仍然坚持不匹配的架构，采取风险缓解计划并提前说明风险

架构参考映射：
- MVVM → `references/mvvm.md`
- MVI → `references/mvi.md`
- TCA → `references/tca.md`
- Clean Architecture → `references/clean-architecture.md`
- VIPER → `references/viper.md`
- Reactive → `references/reactive.md`
- MVP → `references/mvp.md`
- Coordinator → `references/coordinator.md`

组合路由：
- Coordinator 通常是次要的，除非用户的主要问题是流程所有权、深度链接或可重用导航。
- Reactive 通常是次要的，当流存在于 MVVM、MVP、VIPER、MVI 或 TCA 呈现边界内时。
- Clean Architecture 通常是主要的，用于应用/模块分层，MVVM、MVP 或 TCA 作为呈现模式。
- 结合使用时，在给出文件结构或代码前，阅读两个参考并确定每个边界由哪种模式负责。

## 分析现有代码库（适用时）

当代码已存在时：
- 检测当前架构和 DI 风格
- 记录并发模型（async/await、Combine、GCD、混合）
- 将建议与本地约定对齐

## 安全边界

- 不要强制为小功能切换架构，如果当前本地模式仍然合理。
- 保留现有约定，除非不匹配严重到需要变更。
- 除非用户明确接受该权衡或代码库已使用，否则不要引入新的框架依赖，如 TCA。
- 优先选择最小的架构变更，以清晰解决请求。
- 保持指导架构特定；除非模式之间的边界明确，否则不要混合方案。
- 对于组合模式，避免合并职责：先确定主要边界，然后仅将次要方案应用于其关注点。

## 生成具体交付物

阅读选定的架构参考，将其指导转换为针对用户请求的交付物：

- **文件和模块结构**：特定于功能的目录布局和文件名
- **状态和依赖边界**：具体类型、协议和注入点
- **异步策略**：取消、Actor 隔离和错误路径
- **测试策略**：测试内容、如何模拟依赖和示例测试结构
- **迁移路径**（用于重构）：从当前架构到目标架构的增量步骤
- **UI 堆栈适配**：为选定架构的 SwiftUI 和 UIKit 指导差异

## 输出要求

- 将推荐范围限制在请求的功能或审查任务。
- 优先使用基于协议的依赖注入和显式状态建模。
- 标记现有代码中的反模式并提供直接修复。
- 在所有异步流程中包含取消和错误处理。
- 对于明确的架构请求，包含一个简短的适配结果（`fit` 或 `mismatch`）和 1-2 个原因。
- 对于不匹配的情况，包含一个最接近的替代方案及其为何更符合所述约束。
- 编写代码时，仅包含与任务相关的模式——不要堆砌整个方案。
- 将参考片段视为说明性内容；除非用户请求可运行代码，否则不要添加完整的编译脚手架。
- 仅提出最小阻塞问题；否则，在前面明确说明假设。
- 在审查 PR 时，使用架构特定清单并指出具体的违规情况及行级修复。

## 验证清单

在最终确定前：

1. 确认选定的模式与用户的约束和堆栈匹配
2. 确认依赖注入、状态所有权、效果和测试策略已覆盖
3. 在推荐架构变更时明确指出迁移风险
4. 以用户功能为背景，结束所选架构的 PR 审查清单
