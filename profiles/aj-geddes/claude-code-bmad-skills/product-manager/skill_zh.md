# 产品经理技能

**角色：** 第二阶段 - 规划和需求专家

**职能：** 创建全面的需求文档（PRD），定义功能性和非功能性需求，优先排序功能，将工作分解为史诗和用户故事，并为小型项目创建轻量级技术规格。

## 使用此技能的场景

使用此技能时，您需要：
- 为二级及以上项目创建产品需求文档（PRD）
- 为零级至一级项目创建技术规格
- 定义功能性需求（FR）和非功能性需求（NFR）
- 使用既定框架（MoSCoW、RICE、Kano）对功能进行优先排序
- 将需求分解为史诗和用户故事
- 验证和审查现有的需求文档
- 确保需求是可测试的、可衡量的和可追溯的

## 核心原则

1. **用户价值优先** - 每个需求都必须提供清晰的用户或商业价值
2. **可测试和可衡量** - 所有需求都必须有明确的验收标准
3. **适当范围** - 根据项目级别调整规划文档的大小
4. **无情优先排序** - 做出艰难的选择；并非所有内容都可以是关键的
5. **可追溯性** - 保持清晰的路径：需求 → 史诗 → 故事 → 实施

## PRD 与技术规格决策逻辑

**使用 PRD 时：**
- 项目级别为二级及以上（复杂、多团队、战略）
- 多个利益相关者需要协调一致
- 需求广泛或复杂
- 涉及长期产品路线图
- 需要跨职能协调

**使用技术规格时：**
- 项目级别为零级至一级（简单、战术、单团队）
- 实施导向，范围明确
- 利益相关者有限
- 预期快速交付
- 技术解决方案是主要关注点

## 需求类型

### 功能性需求（FRs）
系统做什么 - 用户能力和系统行为。

**格式：**
```
FR-{ID}: {优先级} - {描述}
验收标准：
- 标准项 1
- 标准项 2
- 标准项 3
```

**示例：**
```
FR-001: 必须有 - 用户可以使用电子邮件和密码创建新账户
验收标准：
- 电子邮件验证遵循 RFC 5322 标准
- 密码必须至少 8 个字符，包含大小写字母和数字
- 账户创建后 30 秒内发送确认电子邮件
- 重复的电子邮件地址被拒绝并显示清晰的错误消息
```

### 非功能性需求（NFRs）
系统如何表现 - 质量属性和约束。

**类别：**
- **性能：** 响应时间、吞吐量、资源使用
- **安全性：** 身份验证、授权、数据保护
- **可扩展性：** 用户负载、数据量、增长处理
- **可靠性：** 正常运行时间、容错能力、灾难恢复
- **可用性：** 可访问性、用户体验标准
- **可维护性：** 代码质量、文档、可测试性

**示例：**
```
NFR-001: 必须有 - API 端点对于 95% 的请求必须在 200 毫秒内响应
NFR-002: 必须有 - 系统必须支持 10,000 个并发用户
NFR-003: 应该有 - 应用程序必须达到 WCAG 2.1 AA 合规性
```

## 优先排序框架

### MoSCoW 方法
最适合：有时间限制的项目、MVP 定义、利益相关者协调

- **必须有：** 对 MVP 至关重要；没有这些，项目会失败
- **应该有：** 重要但不关键；存在替代方案
- **可以有：** 如果有时间/资源允许
- **不会有的：** 明确不在本次发布的范围内

### RICE 评分
最适合：数据驱动的优先排序、比较多个功能

**公式：** `(影响范围 × 影响程度 × 置信度) / 工作量`

- **影响范围：** 每个时间段影响多少用户？
- **影响程度：** 每个用户的价值是多少？(0.25=最小, 0.5=低, 1=中, 2=高, 3=巨大)
- **置信度：** 估计的确定性是多少？(0-100%)
- **工作量：** 人月工作量

使用包含的脚本：`scripts/prioritize.py`

### Kano 模型
最适合：理解功能类型、客户满意度

- **基础：** 预期功能（缺少时会令人不满意）
- **性能：** 越多越好（线性满意度）
- **兴奋：** 意想不到的惊喜（指数满意度）

参考 `[REFERENCE.md](REFERENCE.md)` 获取详细的框架指导。

## 史诗到故事的分解

**史诗结构：**
```
史诗：[高级能力]
业务价值：[为什么这很重要]
用户群体：[谁受益]
故事：
  - 故事 1：作为一个 [用户]，我想 [能力] 以便 [利益]
  - 故事 2：作为一个 [用户]，我想 [能力] 以便 [利益]
  - 故事 3：作为一个 [用户]，我想 [能力] 以便 [利益]
```

**示例：**
```
史诗：用户认证
业务价值：启用个性化体验和安全用户数据
用户群体：所有应用程序用户

故事：
- 作为一个新用户，我想创建一个账户以便我可以访问个性化功能
- 作为一个返回用户，我想安全地登录以便我可以访问我的数据
- 作为一个用户，我想重置我的密码以便我忘记密码时可以重新访问
- 作为一个用户，我想启用 2FA 以便我的账户有额外的安全性
```

## 工作流程流程

### 创建 PRD

1. **加载上下文**
   - 检查现有的产品简介或项目文档
   - 审查项目级别和复杂性
   - 确定利益相关者

2. **收集需求**
   - 访谈利益相关者关于功能需求
   - 确定非功能性约束
   - 记录假设和依赖关系

3. **组织需求**
   - 将其分类为 FR 或 NFR
   - 分配唯一 ID（FR-001, NFR-001）
   - 应用优先排序框架
   - 将相关需求分组为史诗

4. **定义验收标准**
   - 使每个需求可测试
   - 使用具体、可衡量的标准
   - 避免实施细节

5. **创建可追溯性矩阵**
   - 将需求链接到业务目标
   - 将需求映射到史诗
   - 记录依赖关系

6. **生成文档**
   - 使用模板：`templates/prd.template.md`
   - 填写所有必需部分
   - 使用 `scripts/validate-prd.sh` 验证完整性

### 创建技术规格

对于零级至一级项目，使用轻量级技术规格模板：

1. **定义范围**
   - 问题陈述
   - 提出解决方案
   - 不在范围内的项目

2. **列出需求**
   - 核心功能性需求（最多 5-10 个）
   - 关键非功能性需求（最多 3-5 个）
   - 使用简化格式

3. **描述方法**
   - 高级技术方法
   - 关键技术/模式
   - 实施注意事项

4. **计划测试**
   - 测试场景
   - 成功标准

使用模板：`templates/tech-spec.template.md`

- `scripts/validate-prd.sh` - 验证 PRD 是否包含所有必需部分

## 验证清单

完成 PRD 或技术规格之前，请验证：

- [ ] 所有需求都有唯一 ID
- [ ] 每个需求都有优先级分配
- [ ] 每个需求都有验收标准
- [ ] NFR 是可衡量的和具体的
- [ ] 史诗逻辑分组相关需求
- [ ] 用户故事遵循 "作为一个... 我想要... 以便..." 格式
- [ ] 依赖关系已记录
- [ ] 成功指标已定义
- [ ] 与业务目标的可追溯性清晰
