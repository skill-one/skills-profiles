# 技能创建器

创建、评估和迭代高质量的代理技能。此技能指导整个生命周期：规划技能应做什么，编写 SKILL.md 和参考文件，根据评分标准进行质量评分，并迭代直到技能达到生产标准。

**哲学：** 优秀的技能不是长技能，而是 *精确* 的技能：详尽的触发器、明确的默认值、清晰的步骤和退出门、通过参考文件延迟复杂性，以及结构化的输出模板。

**核心规则 — 始终动态，永不静态：** 技能必须检测在运行时可用的工具、库和认证，并相应地调整其行为。永远不要硬编码单一方法。始终提供一个带有决策树和回退路径的检测流程。参见 `references/dynamic-calling.md` 获取完整模式目录。

---

## 第 1 步：了解用户需求

将请求分类为以下模式之一：

| 用户意图 | 模式 | 跳转到 |
|---|---|---|
| 创建一个全新的技能 | **创建** | 第 2 步 |
| 改进 / 修复现有技能 | **改进** | 第 6 步 |
| 评估 / 评分技能的质量 | **评估** | 第 7 步 |

如果模糊不清，请询问：“您是想创建新技能、改进现有技能还是评估技能？”

### 收集需求（创建模式）

在编写任何内容之前，回答以下问题（如果不清楚，请询问用户）：

| 问题 | 重要性 |
|---|---|
| 技能自动化的任务是什么？ | 定义核心工作流程 |
| 目标用户是谁？ | 确定复杂性和术语级别 |
| 它使用哪些工具/API/CLI？ | 确定依赖项和平台限制 |
| 用户提供什么作为输入？ | 定义参数和默认值 |
| 输出应该是什么样子？ | 定义响应模板 |
| 它是否需要 API 密钥或凭证？ | 确定 `required_environment_variables` |
| 它应该在 Claude.ai 上运行还是仅在 CLI 上运行？ | 确定平台字段和动态命令 |

## 第 2 步：规划技能架构

在编写 SKILL.md 之前，规划结构。阅读 `references/architecture-patterns.md` 获取有关每个模式的详细指导。

### 选择结构模式

| 模式 | 使用场景 | 步骤 | 示例 |
|---|---|---|---|
| **线性** | 单个工作流程，无分支 | 5-7 | earnings-preview, etf-premium |
| **路由器** | 在一个总标题下有多个子任务 | 3 + 子技能 | stock-correlation (4 个子技能) |
| **方法论** | 复杂领域框架，具有顺序门 | 7-9 | sepa-strategy (9 步交易方法论) |
| **小部件** | 生成交互式 UI 输出 | 4-5 | options-payoff (提取 + 计算 + 渲染) |
| **API 封装器** | 封装具有许多端点的外部 API | 3-5 + 重参考 | fintel-data (6 步，1 个参考文件) |

### 规划步骤大纲

在编写内容之前，列出步骤名称。每个技能都应该有：

1. **检测流程**（第 1 步）-- 动态检测可用工具、认证状态和运行时环境；构建决策树以选择使用哪种方法
2. **核心方法论**（第 2-N 步）-- 实际工作，带有通过/失败门；每个调用外部工具的步骤都应该根据第 1 步检测到的内容提供方法替代方案
3. **响应用户**（最后一步）-- 结构化输出模板

总共目标 **5-9 步**。超过 9 步意味着该技能应该被拆分或使用路由器模式。

### 规划检测流程

每个接触外部工具的技能都必须以运行时检测流程开始。阅读 `references/dynamic-calling.md` 获取所有模式。检测流程回答：

| 问题 | 如何检测 | 决策 |
|---|---|---|
| CLI 工具是否安装？ | `command -v tool` | CLI 路径与 Python 回退 |
| 用户是否已认证？ | `tool auth status` / `echo $API_KEY` | 跳过认证设置或引导设置 |
| 哪个运行时有库？ | 终端中的 `import lib` 与 `execute_code` | 路由到正确的运行时 |
| 是否有更丰富的工具可用？ | `gh --version` 与 `git --version` | 丰富路径与最小路径 |
| 是否可以访问实时数据？ | `curl -s endpoint` | 实时数据与缓存/默认 |

检测输出会输入到技能其余部分遵循的 **决策树**。永远不要假设 — 始终检查。

### 规划参考文件

决定什么放入 SKILL.md 与 references/：

| SKILL.md（约 250 行） | references/ |
|---|---|
| 分步工作流程 | 详细 API 文档 |
| 路由/决策表 | 代码模板（>20 行） |
| 参数默认值表 | 公式和边缘情况 |
| 输出格式模板 | 故障排除数据库 |
| 快速示例（1-3） | 全面示例（4 个以上） |

## 第 3 步：编写 SKILL.md

阅读 `references/writing-guide.md` 获取有关编写每个部分的详细说明。阅读 `references/frontmatter-guide.md` 获取完整的 YAML 字段参考。

### 关键规则

1. **前文信息优先**：`name`（小写连字符，最多 64 个字符）和 `description`（详尽的触发器列表，最多 1024 个字符）是必需的。描述需要 5 个以上的触发器，包括横向入口点。

2. **第 1 步 = 检测流程**：使用 `!`command`` 带回退检测可用工具、认证状态和运行时。构建带有多个方法路径的决策树（例如，首选 CLI，Python 回退，内置工具作为最后手段）。永远不要硬编码单一工具 — 始终检测和适应。参见 `references/dynamic-calling.md`。

3. **核心步骤与方法替代方案**：每个调用外部工具的步骤都应该至少提供 2 个基于第 1 步检测到的路径。使用模式：“如果 `TOOL_A` 检测到 → 方法 1，否则 → 方法 2。” 每个步骤都应获得 `## Step N: [动词] [对象]`，如果路由则使用决策表，如果评估则使用通过/失败门，并为深入内容提供参考指针。

4. **默认值表**：每个参数必须有明确的默认值。没有任何技能应该因等待输入而停滞。

5. **最后一步 = 输出模板**：编号每个输出部分。指定每个部分确切的数据。如果评估，则包括一个裁决/评分系统。

参见 `references/skill-examples.md` 获取每个模式的注释示例。

---

## 第 4 步：编写参考文件

阅读 `references/writing-guide.md` 获取完整的参考文件编写指南。

### 关键规则

1. **命名**：`lowercase-hyphenated.md`，每个概念集群一个文件
2. **大小**：快速查找 50-150 行，深入指南 150-400 行，目录 400-900 行
3. **结构**：H1 标题，H2 部分，代码块，表格，边缘情况部分在末尾
4. **链接**：在 SKILL.md 步骤中使用反引号路径，并在末尾使用 `## 参考文件` 部分

## 第 5 步：交付前的质量检查

运行技能通过 `references/quality-rubric.md` 中的质量评分标准。评分每个维度。

### 快速检查清单

- [ ] 前文信息包含 `name` 和 `description`（两者都是必需的）
- [ ] 描述包含 5 个以上的不同触发器短语
- [ ] 描述包括横向入口点
- [ ] SKILL.md 低于 300 行（理想情况下低于 250）
- [ ] 每个参数都有明确的默认值
- [ ] 步骤编号（## Step N: ...）
- [ ] 每个步骤都有一个明确的退出条件或交付成果
- [ ] 最后一步指定了编号的输出结构
- [ ] 复杂内容在参考文件中，不在行内
- [ ] 参考文件指针使用反引号路径
- [ ] 第 1 步有一个检测流程，带有 `!`command`` 检查和回退（`|| echo "..."`）
- [ ] 检测流程产生一个带有 2 个以上方法路径的决策树
- [ ] 核心步骤根据检测结果调整行为（不是硬编码到一个工具）
- [ ] 不同运行时被视为不同环境（终端与 execute_code）
- [ ] 在适当的地方包含法律/道德免责声明
- [ ] 没有硬编码的股票列表、工具路径或会过时的静态数据

如果任何项目失败，在交付给用户之前修复它。

## 第 6 步：改进现有技能

当用户要求改进技能时：

### 6a: 阅读当前技能

使用 `skill_view(name)` 加载技能或直接读取 SKILL.md。还阅读所有参考文件。

### 6b: 根据评分标准评分

使用 `references/quality-rubric.md` 中的质量评分标准。向用户展示评分明细：

| 维度 | 评分 | 问题 |
|---|---|---|
| 触发器质量 | 6/10 | 缺少初学者短语 |
| 默认值覆盖 | 3/10 | 没有默认值表 |
| 步骤结构 | 8/10 | 良好，但第 3 步缺少退出门 |
| 输出模板 | 4/10 | 模糊的“总结结果” |
| 参考文件使用 | 7/10 | 良好拆分，但缺少故障排除 |

### 6c: 提出具体改进建议

列出按影响排名的具体更改：

1. [最高影响] 添加包含 8 个以上参数的默认值表
2. [高影响] 重写描述，包含 10 个以上触发器短语
3. [中等影响] 在最后一步添加结构化输出模板
4. ...

### 6d: 应用更改

用户批准后，编辑技能。使用 `skill_manage(action='patch', ...)` 进行有针对性的更改或 `skill_manage(action='edit', ...)` 进行完整重写。

## 第 7 步：评估技能

当用户要求评估或评分技能时：

### 7a: 加载和分析

读取完整的 SKILL.md 和所有参考文件。计算行数、步骤数、触发器数、默认值、参考文件数。

### 7b: 根据评分标准评分

使用 `references/quality-rubric.md` 中的综合评分标准。在 1-10 的量表上为每个维度评分。

### 7c: 呈现评分卡

```
## 技能质量评分卡：[skill-name]

| # | 维度 | 评分 | 备注 |
|---|---|---|---|
| 1 | 触发器质量 | 8/10 | 12 个触发器，包括横向入口点 |
| 2 | 默认值覆盖 | 9/10 | 所有 11 个参数都有默认值 |
| 3 | 步骤架构 | 8/10 | 5 个清晰步骤带门 |
| 4 | 参考文件策略 | 7/10 | 2 个文件，可以使用故障排除 |
| 5 | 动态内容 | 10/10 | 检查 + 实时数据注入 |
| 6 | 输出模板 | 9/10 | 5 个编号部分 + 裁决 |
| 7 | 错误处理 | 6/10 | 缺少数据处理不明确 |
| 8 | 代码/公式质量 | 8/10 | 可工作的 JS，可复制粘贴 |
| 9 | SKILL.md 简洁性 | 7/10 | 196 行，在目标范围内 |
| 10 | 领域准确性 | 9/10 | BS 公式正确，边缘情况覆盖 |

**总体：81/100** -- 生产质量

### 顶部 3 个改进
1. ...
2. ...
3. ...
```

### 基准参考

为了参考，以下是此存储库中已知高质量技能的评分：

| 技能 | 评分 | 原因 |
|---|---|---|
| sepa-strategy | ~90/100 | 9 步，7 个参考文件，详尽的触发器，结构化裁决 |
| options-payoff | ~85/100 | 强大的默认值，可工作的代码，实时数据，干净的输出 |
| stock-correlation | ~80/100 | 路由器模式，4 个子技能，良好的默认值 |

## 第 8 步：响应用户

### 创建模式

交付：
1. 完整的 SKILL.md 内容
2. 所有参考文件
3. 技能目录的 README.md
4. 质量评分卡（来自第 5 步）
5. 建议的下一步（测试它，迭代，发布）

### 改进模式

交付：
1. 前/后质量评分
2. 已做更改的摘要
3. 剩余改进机会

### 评估模式

交付：
1. 完整的评分卡
2. 与基准技能的比较
3. 优先改进列表
