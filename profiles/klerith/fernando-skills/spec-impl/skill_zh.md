## 说明

严格按以下四个阶段顺序执行。**如果前一个阶段未正确完成，则不要进入下一个阶段。**

---

### 阶段 1 — 识别规范

接收到的参数是：`$ARGUMENTS`

如果 `$ARGUMENTS` 为空：

- 列出 `specs/` 中的文件（您已经在上面看到了）。
- 要求用户指定规范的准确名称。
- 停止并等待答案。不要继续。

如果 `$ARGUMENTS` 有值：

- 在 `specs/` 中查找该文件。用户可能写了完整名称（`01-mvp-arkanoid`）、仅数字（`01`）或仅缩写（`mvp-arkanoid`）。尝试在任何这些情况下找到正确的文件。
- 如果找不到文件，显示可用规范并要求用户更正名称。
- 如果找到文件，继续到阶段 2。

---

### 阶段 2 — 验证规范状态

使用 Read 工具或 `cat` 读取阶段 1 中定位的规范文件。

在文件内容中查找包含规范状态的行。标题标签通常是 `**Status:**`（英文）或 `**Estado:**`（西班牙文），但它可能使用任何语言。按位置（状态行靠近规范的顶部）和周围的状态机进行匹配，而不是按确切的标签。

**绝对规则**：只有状态表示“已批准”时才能继续——无论使用的语言是什么。

将以下任何一项（以及其他语言的等效词）视为**已批准**状态并继续：

- 英文：`Approved`
- 西班牙文：`Aprobado`
- 葡萄牙文：`Aprovado`
- 法文：`Approuvé`
- 德文：`Genehmigt`
- 意大利文：`Approvato`
- …或其他任何明确表示“已批准”的语言词汇

任何其他内容（草稿 / Borrador、审核中 / En revisión、已实现 / Implementado、已过时 / Obsoleto 或任何未识别的值）都表示**停止**并显示以下错误消息。

| 状态类别                          | 示例（任何语言）                               | 操作                                                                    |
| --------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------- |
| 已批准                            | `Approved`, `Aprobado`, `Aprovado`, `Approuvé`, … | 继续到阶段 3。                                                           |
| 草稿                              | `Draft`, `Borrador`, …                        | 停止。显示以下错误消息。                                                |
| 审核中                            | `In review`, `En revisión`, …                 | 停止。显示以下错误消息。                                                |
| 已实现                            | `Implemented`, `Implementado`, …                | 停止。显示以下错误消息。                                                |
| 已过时                            | `Obsolete`, `Obsoleto`, …                      | 停止。显示以下错误消息。                                                |
| 状态行未找到 / 未识别的值         | —                                             | 停止。文件未按预期格式编写。告知用户此情况。                             |

如果您不确定某个值是否表示“已批准”，**不要假设**。停止并要求用户澄清或更新规范为规范用语。

**状态不表示“已批准”时的标准错误消息：**

```
❌ 我无法实现此规范。

当前状态：[找到的状态]
我只处理状态表示“已批准”（例如 `Approved`, `Aprobado` 或其他语言的等效词）的规范。

要继续，您有两个选项：
  1. 如果规范已准备好实现，请打开它并将状态手动更改为“Approved”（或您的团队使用的等效术语）。
     此更改由人类而非代理完成。
  2. 如果规范仍需工作，请使用 /spec [name] 继续它。
```

不要提供其他选项，不要建议“如果您想，我仍然可以开始”。此块是故意的。

---

### 阶段 3 — 创建 git 分支并切换到它

一旦您确认状态表示 `Approved`：

0. **首先检查工作区。** 查看会话上下文中 `git status --short` 的输出。如果它**不为空**，停止并显示待处理的更改，然后询问：

   ```
   ⚠️ 工作区中有未提交的更改。
   切换分支会将它们带到新分支。您想做什么？
     1. 自己提交或暂存它们，然后重新运行此命令（推荐）
     2. 继续操作——更改将转移到新分支
   ```

   等待答案。**除非用户明确要求，否则不要替他们暂存或提交**。如果工作区干净，直接跳到步骤 1，无需提及。

1. 从规范文件的完整名称中派生分支名称，不带扩展名。格式：`spec-NN-slug`。示例：

   - `01-mvp-arkanoid.md` → 分支 `spec-01-mvp-arkanoid`
   - `02-powerups.md` → 分支 `spec-02-powerups`

2. 从会话上下文中显示的**分支创建配置**中读取 `AutoCreateBranch` 标志。

   - 如果配置文件不存在、值缺失或值未识别 → 视为 `true`（默认）。
   - 仅明确 `false`（任何大小写）禁用自动分支创建。

   **如果 `AutoCreateBranch` 是 `true`（默认）：** 直接进行。

   - 如果分支**不存在**：使用 `git checkout -b spec-NN-slug` 创建它。
   - 如果它**已存在**：这意味着之前的工作正在继续。切换到它，读取分支上的 `git log --oneline`，并告知用户哪些计划步骤已完成，以及您建议从哪个步骤继续。在确认继续点之前不要实施任何操作。
   - 在这两种情况下：使用 `git checkout spec-NN-slug` 切换到分支，并确认更改成功后继续。

   **如果 `AutoCreateBranch` 是 `false`：** 在操作 git 之前询问。显示：

   ```
   AutoCreateBranch 设置为 false。
   创建并切换到分支 spec-NN-slug？ [y/N]
   ```

   - 如果用户回答**是**：按上述 `true` 情况创建/切换到分支。
   - 如果用户回答**否**或留空：**不要创建任何分支**。告知用户您将在当前分支（会话上下文中显示的分支）上实施，并要求明确确认继续。不要即兴发挥——等待答案。

3. 向用户视觉确认规范已准备好，以及哪个分支是活动的：

   ```
   ✅ 准备实施。

   规范：   specs/NN-slug.md
   分支：   spec-NN-slug  (活动)   (← 或当前分支，如果未创建新分支)
   状态：   已批准   (← 回显规范中实际找到的值)
   ```

4. **不要立即开始实施。** 首先向用户显示规范摘要，以便他们有新鲜感。提取并显示：
   - **目标**（位于 `**Objective:**` / `**Objetivo:**` / 等效标签后的行）。
   - **范围**（`## Scope` / `## Alcance` / 等效部分）。
   - **实施计划**（编号步骤的段落——`## Implementation plan` / `## Plan de implementación` / 等效）。
   - **验收标准**（检查清单——`## Acceptance criteria` / `## Criterios de aceptación` / 等效）。

按意义匹配部分标题，而不是按确切的措辞——规范可能使用任何语言编写。

---

### 阶段 4 — 逐步实施

在显示规范摘要后，告诉用户：

```
我将严格按照实施计划进行规范实施。
我会在每一步后暂停，以便您审查差异。

我们要从步骤 1 开始吗？
```

等待明确的确认（“是”、“继续”、“开始”或等效）。没有它不要开始。

一旦确认，在实施过程中遵循以下规则：

**永远不要自动提交。** 不按步骤，也不在最后。您编写代码并显示差异；提交是用户的决定和用户的命令。只有在他们明确要求时才提交。

**最重要的规则**：按规范实施。如果您认为规范中的某些内容不理想，请作为观察结果提及，但按约定实施。对规范的更改应进入规范，而不是通过意外进入代码。

**工作节奏：**

- 实施计划中的一个步骤。
- 显示您修改的文件和所做操作的摘要。
- 说：`步骤 N 完成。您能审查差异并告诉我是否继续步骤 N+1 吗？`
- 等待确认后再继续。

**如果在实施过程中发现规范未解决的歧义：**

- 停止。
- 准确描述歧义。
- 提供两个或三个具体选项。
- 等待用户的决定。
- 不要即兴发挥。

**如果用户要求实施规范范围之外的内容：**

- 提醒他们这是此规范范围之外的内容。
- 建议将此内容记录在下一个规范中。
- 不要在此分支上实施它。

**完成最后一步时：**

```
✅ 计划的所有步骤都已实施。

下一步：逐个验证规范的验收标准。
如果它们都通过，请将规范状态更新为“Implemented”（或您仓库语言的等效词），并在合并此分支之前进行最终提交。
```

## 预期行为的摘要

```
/spec-impl 01-mvp-arkanoid

  阶段 1  →  找到 specs/01-mvp-arkanoid.md
  阶段 2  →  读取状态 → "Approved"（或 "Aprobado", 等等）→ ✅ 继续
  阶段 3  →  git checkout -b spec-01-mvp-arkanoid → git checkout spec-01-mvp-arkanoid
              显示目标、范围、计划和标准
  阶段 4  →  逐步实施，每一步后暂停
              最后提醒验证验收标准

/spec-impl 02-powerups  (状态：草稿 / Borrador)

  阶段 1  →  找到 specs/02-powerups.md
  阶段 2  →  读取状态 → "Draft" → ❌ 停止
              显示标准错误消息
              不创建分支，不接触代码
```

**分支创建受 `AutoCreateBranch` 标志** 控制，位于 `specs/.spec-config.yml` 中。它默认为 `true`（自动创建分支，如上所示）。将其设置为 `false` 以使阶段 3 在创建分支前询问 `[y/N]`。
