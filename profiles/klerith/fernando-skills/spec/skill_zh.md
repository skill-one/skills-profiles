# /spec — 引导式规范设计器

## 会话上下文

今天的日期（用于规范头部，切勿猜测）：
!`date +%F`

已存在的规范：
!`ls specs/ 2>/dev/null || echo "specs/ 文件夹尚未存在"`

---

这项技能帮助你遵循规范驱动方法来生成有用的规范。**这里不编写代码。** 你的工作是帮助用户明确他们想要构建的内容，在定义不够清晰时提出问题，并逐段开发规范，直到它准备好被保存到 `specs/` 中。

## 哲学

规范不是装饰性的文档。它是驱动后期执行的合同。如果规范含糊不清，代码就会自行其是。这就是为什么这个流程在**定义阶段故意放慢速度**，在**编写阶段快速进行**。

阅读 `template.md`（与这项技能位于同一目录下），以了解规范将遵循的完整结构。在每一步都要参考它。

## 命令流程

- 按顺序遵循四个阶段。**切勿跳过阶段 2** — 问题才是整个要点。如果用户想要更快，提醒他们一个糟糕的规范的代价将在后期代码中付出。（阶段 3 在阶段 2 真正完成后有一个快速路径；见下文。）
- 你的回复必须与初始提示使用相同的语言。例如：如果初始提示是西班牙语，你的回复必须是西班牙语；如果是英语，你的回复必须是英语。

### 阶段 1 — 理解上下文

在询问关于功能的问题之前，确保你有了项目上下文：

1. 如果存在，阅读项目记忆文件。按顺序尝试并停在第一个命中：`CLAUDE.md`，`AGENTS.md`，`GEMINI.md`，`README.md`。这使技能适应运行它的任何代理（Claude Code，Codex，Gemini CLI 等）。
2. 查看会话上下文中 `specs/` 的列表，以了解哪些规范已经存在以及它们的编号方式。
3. 如果存在之前的规范，至少阅读最新的两个，以了解项目的约定 — 包括它们**编写的语言**以及它们用于状态和章节标题的确切措辞。新规范必须与现有的规范匹配。

如果 `$ARGUMENTS` 参数为空，请向用户询问他们想要构建内容的**一句话**描述。如果描述不适合一句话，那就是第一个信号，表明功能太大 — 建议将其拆分后再继续。

### 阶段 2 — 通过提问进行澄清

这是命令中最重要的阶段。你的工作在这里是**检测歧义并提问**，而不是假设。

一次提出 3 到 5 个问题（不是一次一个单独的问题接着另一个单独的问题 — 那样令人筋疲力尽）。每次提出一个块后，等待回答再继续。

**你应该始终考虑的问题类别：**

- **范围：** 什么在范围内，什么不在？功能的哪些部分被推迟到另一个规范中？
- **数据：** 引入了哪些新结构？它们如何命名？它们存放在哪里？
- **集成：** 这个功能依赖于之前的规范吗？它修改了现有内容还是仅添加？
- **持久化：** 任何在会话之间保存的内容吗？在哪里？使用什么版本控制？
- **用户体验和状态：** 它工作时的外观是什么？它失败时的外观是什么？是否有中间状态？
- **风险：** 什么会破坏它？降级情况下会发生什么？
- **已关闭的决策：** 用户是否已经做出任何决策并且不希望重新打开？

**如何措辞问题：**

- 使用具体的问题，而不是开放式问题。❌ "你怎么想象持久化？" → ✅ "持久化是 localStorage、IndexedDB 还是磁盘上的 JSON 文件？"
- 当你提供选项时，给出 2-4 个，标明哪个是你的推荐选项以及为什么。
- 如果你的代理提供原生的多选问题工具（在 Claude Code 中：`AskUserQuestion`），用它来提出这些块，而不是将选项作为散文写入 — 用户选择而不是输入。将你的推荐选项放在前面并标记它。如果没有这样的工具，则回退到编号的 markdown 列表。
- 如果你发现一个会打开潘多拉魔盒的答案（例如，“我们还想要多人游戏”），指出它值得自己的规范，并询问我们是否将其排除在此范围的之外。

**何时停止提问：**

当你能够不假设任何内容就回答这三个问题时停止提问：

1. 哪些文件会出现或改变？
2. 第一个可执行步骤是什么，最后一个是什么？
3. 如何验证功能已完成？

如果你仍然无法回答其中一个问题，继续提问。

### 阶段 3 — 编写规范

一旦阶段 2 结束，决定如何编写它：

**如果你已经拥有所有需要的信息** — 意味着你能够不假设任何内容就回答阶段 2 的三个问题（哪些文件改变，第一个和最后一个可执行步骤是什么，如何验证它已完成）— 那么**不要逐段编写**。编写完整的规范并直接跳到阶段 4 保存文件。不要请求逐段确认，也不需要先显示草稿以供批准：用户已经在阶段 2 中回答了一切，重新提问会增加摩擦。用户审查保存的文件并在需要时提出更改。

**只有在信息仍然缺失**（用户缩短了阶段 2，一个答案含糊不清，或者某些章节无法在不编造内容的情况下编写）的情况下，**逐个开发章节**，显示每个章节并等待确认后再移动到下一个。

在两种情况下，内容都遵循相同的顺序：

1. **头部**（状态、依赖项、日期、一句话目标）。一句话目标至关重要 — 如果它不适合一句话，请返回阶段 2。
2. **范围**（什么在范围内，什么不在）。"不在" 必须明确。
3. **数据模型**（具有真实名称的具体结构）。如果功能没有引入新数据，跳过此章节并明确说明。
4. **实施计划**（编号的步骤，每个步骤都保持系统功能）。
5. **验收标准**（布尔值检查清单，不是理想化的）。
6. **已做出的决策和被放弃的决策**（附有简要理由）。
7. **已识别的风险**（仅当适用时 — 如果没有相关风险，则跳过）。

**在逐个开发模式下，每个章节之后：**

- 以 markdown 格式显示它。
- 询问："这个章节保持原样还是你想调整它？"
- 如果用户要求更改，应用它们并再次显示。
- 只有在用户确认后才能移动到下一个章节。

**常见的错误要避免：**

- 生成不可验证的验收标准（“它运行良好”）。
- 将不属于范围的内容放入实施计划。
- 假设用户没有确认的文件名或结构。
- 跳过决策部分 — 这个部分具有最长期的价值观。

### 阶段 4 — 保存规范

当内容准备就绪时（无论是因为你已经拥有所有信息，还是因为所有章节都已确认）：

1. 从会话上下文中的 `specs/` 列表中确定下一个顺序编号。取最高现有编号并加一，用两位数字进行零填充。如果最后一个编号是 `02-powerups.md`，这个编号将是 `03-`。如果 `specs/` 为空或缺失，从 `01-` 开始。
2. 从目标中生成一个短的小写连字符分隔的名称（例如 `levels-and-highscores`）。有关 **参数** 的部分说明了当 `$ARGUMENTS` 是名称时的情况。
3. 使用会话上下文中的日期作为 `**日期：**` 字段。**切勿写入你没有从那里读取的日期。**
4. 直接将所有章节写入 `specs/NN-slug.md`。**不要请求写入权限，也不要询问文件名是否合适** — 在最终确认中宣布路径。只有在目标文件已存在时才询问。
5. 默认将状态标记为 `草稿`（或此存储库中现有规范使用的等效词语）。**不要自动将其标记为 `已批准`** — 用户在重新阅读后才会这样做。
6. 如果头部列出了依赖项（`**依赖于：** SPEC 01`），检查每个引用的规范是否实际存在于 `specs/` 中。如果有一个不存在，请这样说，而不是编写悬空的引用。
7. **如果配置文件不存在，则进行播种。** 检查 `specs/.spec-config.yml`。如果它**缺失**，用以下默认内容创建它。如果它**已经存在，则保持不变** — 永远不要覆盖用户的设置。

   ```yaml
   # spec 工作流配置
   #
   # AutoCreateBranch — 控制是否自动创建 git 分支。
   #   true  (默认) → /spec-impl 创建并切换到 spec-NN-slug 而不询问
   #   false           → /spec-impl 在创建分支前询问 [y/N] 确认
   AutoCreateBranch: true
   ```

8. 向用户确认：
   - 创建的文件路径。
   - 提醒：规范处于 `草稿` 状态。重新阅读后将其更改为 `已批准`。
   - 如果刚刚创建了 `specs/.spec-config.yml`，请提及它存在，并且 `AutoCreateBranch` 默认为 `true`（将其设置为 `false` 以自行控制分支创建）。
   - 下一步：一旦审查和批准，运行 `/spec-impl NN-slug` 来实现它。
   - **到此为止。** 不要建议实现规范、编写代码或采取任何进一步行动。

## 硬性规则

- **在此命令期间切勿编写代码。** 只有最终规范的 `.md` 文件。
- **保存规范后切勿建议实现规范。** 你的工作在文件写入时结束。用户在准备好时运行 `/spec-impl`。
- **切勿假设用户未确认的决策。** 如果信息缺失，请提问 — 在阶段 2，这是提问的地方。
- **在阶段 3 不要重新询问阶段 2 中已经回答的问题。** 如果信息完整，编写整个规范并保存。逐段确认是信息不完整时的回退方案，不是默认方案。
- **如果用户想要加快速度并跳过阶段 2**，提醒他们："现在提问可以节省后期的时间。你确定要跳过它们吗？"。如果他们坚持，尊重他们的决定，但在规范的决策部分记录下来（“快速定义而无需详细澄清”）。
- **如果功能太大**（不适合一句话，涉及系统的三个以上领域，需要在四个或更多领域做出决策），建议将其拆分为两个或多个规范再继续。

## 提问时的语气

要直接和具体。不要为提问道歉。不要使用“如果你不介意…”或“你也许可以…”之类的短语。用户调用这项技能恰恰是因为他们希望你来提问。使用具体的问题，多个问题时每行一个，并编号以便于回答。

一个结构良好的块示例：

> 在编写数据模型之前，我需要澄清三件事：
>
> 1. **持久化。** localStorage、IndexedDB 或磁盘上的 JSON 文件？推荐：如果数据小于 5MB 且不需要查询，则使用 localStorage。
> 2. **版本控制。** 当格式更改时会发生什么？选项： (a) 键名前缀版本，(b) 忽略并重建，(c) 加载时迁移。
> 3. **隐私。** 数据是否敏感？如果是，是否加密？是否在登出时删除？

## 参数

`$ARGUMENTS` 是**功能描述**，不是文件名。将其视为阶段 1 的起点，并在阶段 4 从目标中推导出名称。

唯一的例外：如果 `$ARGUMENTS` 已经是一个没有空格的小写连字符分隔的标记（例如 `/spec levels-and-highscores`），它可能在描述和名称之间是模糊的 — 将其用作名称**并**用作描述的种子，而无需确认。

如果他们没有参数调用 `/spec`，首先询问一句话描述。
