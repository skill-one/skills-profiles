# 数据库流量控制建议

## 目的

针对 PlanetScale Postgres，建议流量控制预算和规则，以保护关键流量免受失控查询、流量峰值、批处理作业、代理和第三方集成的影响。未经批准，不得创建或更改预算。

## 前置条件

仅对 PlanetScale Postgres 运行此技能。

在建议规则之前，需检查：

- 当前预算和规则。
- 洞察查询模式。
- 当前查询标签。
- 应用程序路由和作业。
- 已知的 критически важные 路径。
- 已知的昂贵非关键路径。
- 活跃事件或近期异常。

如果查询标签缺失，建议先进行标签化，除非需要为立即已知的违规者创建特定的指纹规则。

## 候选流量切片

查找：

- 导出。
- 报表。
- 搜索端点。
- 管理员仪表板。
- 批量填充。
- 工作人员和工作队列。
- 第三方系统的 webhook。
- BI 工具。
- 代理生成的读取查询。
- 高频轮询。
- 已知的昂贵查询指纹。
- 客户触发的具有高变异性的端点。

## 预算模式

按以下顺序建议：

1. 首先为正常推广使用 `warn` 模式。
2. 观察警告和误报。
3. 调整标签、指纹和阈值。
4. 仅在获得明确批准并存在紧急回滚路径的情况下，切换到 `enforce` 模式。

除非存在活跃事件且操作员明确要求紧急缓解，否则不建议直接从 `enforce` 模式开始。

## 规则策略

当标签稳定且有限时，优先使用基于标签的规则：

- `source=agent`
- `source=bi`
- `feature=export`
- `feature=report`
- `route=/admin/reports`
- `job=DailyBackfill`
- `service=analytics-worker`

在以下情况下使用指纹规则：

- 特定的已知查询模式具有危险性。
- 标签缺失或不可靠。
- 查询来源难以归因。

为每个实质性不同的流量类别使用单独的预算。

不要将不相关的流量合并到一个预算中，因为这会隐藏预算消耗者。

## 建议的默认预算

将这些用作建议模式，而不是盲目应用的具体值。

### 代理预算

目标：标记为 `source=agent` 或 `source=mcp` 的查询。

意图：防止代理耗尽应用程序流量。

模式：从 `warn` 模式开始。

建议：代理应优先使用副本和只读范围。写入操作需要人工批准。

### 导出/报表预算

目标：`feature=export`、`feature=report` 或特定报表路由/作业。

意图：防止客户触发的报表耗尽所有数据库资源。

模式：从 `warn` 模式开始；观察后考虑 `enforce` 模式。

### 背景作业预算

目标：工作人员服务、队列或作业标签。

意图：防止批量填充和重试耗尽交互式流量。

模式：首先使用 `warn` 模式；仅在确认队列背压行为后使用 `enforce` 模式。

### 第三方集成预算

目标：`source=integration`、合作伙伴特定的有限标签或用于入站集成调用的路由模板。

意图：隔离不可预测的合作伙伴行为。

模式：首先使用 `warn` 模式。

### 已知指纹预算

目标：特定的昂贵查询指纹。

意图：在代码或架构修复期间，限制已知的病态查询。

模式：除非紧急情况，否则首先使用 `warn` 模式。

## “每个标签值”策略

当 PlanetScale 支持为选定标签的每个唯一值单独应用预算时，建议为以下有限标签使用此策略：

- `application`
- `service`
- `route`（标准化后）
- `job`
- `feature`
- `source`

不建议为用户 ID、请求 ID、原始租户 ID、电子邮件、UUID 或原始 URL 等无限标签使用此策略。

## 限制和注意事项

每项建议都必须解释：

- 流量控制限制资源使用，不能替代查询调优。
- 它不是 Web 应用程序防火墙。
- 它不能替代应用程序级别的速率限制。
- 限制是安全护栏，而不是针对每种失败模式的精确保证。
- 坏标签会创建坏规则。
- `enforce` 模式可能会拒绝查询并影响应用程序行为。

## 输出格式

针对每个建议的预算：

- 预算名称。
- 目标分支。
- 模式：关闭、`warn` 或 `enforce`。
- 匹配的流量切片。
- 规则类型：标签、指纹、键空间、查询类型。
- 建议的标签或指纹。
- 限制理由。
- 洞察中支持该建议的查询。
- 安全风险。
- 测试/观察计划。
- 回滚计划。
- 批准要求。

最后添加：

“未创建、更新、删除或执行任何流量控制预算或规则。”
