# Schema recommendations agent loop

## 目的

将 PlanetScale schema recommendations 作为高质量输入提供给 agents。将推荐转换为安全的实施计划、问题、分支、迁移或拉取请求。不要直接应用推荐。

## 输入

收集：

- 打开的 schema 推荐。
- 推荐类型。
- 受影响的表、键空间、架构和查询模式。
- 建议的 DDL。
- 支持的 Insights 证据。
- 应用程序仓库和迁移系统。
- 引擎：Vitess 或 Postgres。
- 目标分支。

## 需要识别的推荐类型

- 为低效查询添加索引。
- 移除冗余索引。
- 防止主键 ID 耗尽。
- 删除未使用的表。
- 升级遗留字符集或排序规则。
- 其他 DDL 推荐。

## 分诊问题

对于每个推荐，回答：

- 这个是否仍然开放且相关？
- 哪些查询模式触发了它？
- 哪些应用程序代码路径生成这些查询？
- 推荐是否可以在应用程序的迁移框架中安全地表达？
- ORM/架构真实来源是否需要更改？
- 是否可以在非生产分支上测试？
- 对读取、写入、存储和部署时间的预期影响是什么？
- 是否有回滚或还原路径？
- 是否有竞争的推荐或迁移？

## 引擎特定的实施路径

### Vitess

推荐路径：

1. 创建或使用开发分支。
2. 仅在批准后才能将 schema 变更应用到该分支。
3. 仅在批准后才打开部署请求。
4. 使用部署请求审查来检查 schema、分片影响、数据丢失警告、lint 错误和冲突。
5. 除非明确证明即时部署是合理的，否则使用正常安全的迁移路径。
6. 仅在批准后才部署。
7. 部署后监控 Insights 和异常状态。

批准前的默认输出：带有迁移提议的问题或 PR，而不是实时部署请求。

### Postgres

推荐路径：

1. 尽可能将 DDL 转换为应用程序的迁移框架。
2. 在非生产分支上测试。
3. 运行应用程序测试和相关查询检查。
4. 打开 PR。
5. 仅在批准后才应用生产迁移。
6. 使用备份/PITR 运行程序作为恢复计划，而不是迁移审查的替代方案。

批准前的默认输出：迁移 PR 或问题，而不是生产 DDL。

## 代码库关联

当仓库可用时：

- 搜索表和列名。
- 搜索 ORM 模型定义。
- 搜索迁移。
- 从 Insights 搜索查询指纹、路由标签、作业名称和控制器/操作名称。
- 确定推荐是否应实施在数据库 DDL、ORM 架构、原始迁移或应用程序查询代码中。

## 提出实施前的安全检查

在直接应用时阻止：

- 推荐已过时或已解决。
- 受影响的表足够小以至于收益不明确。
- 索引与现有索引重复。
- 索引在写入密集型工作负载中会造成伤害而没有足够的读取收益。
- 表看起来未使用，但仓库引用不明确。
- 删除表或索引缺乏所有者确认。
- 迁移框架具有不同的架构真实来源。
- 推荐针对生产且没有分支/测试计划。

## 输出

对于每个推荐，生成：

- 推荐ID/编号。
- 类型。
- 严重性和预期收益。
- Insights 证据。
- 受影响的架构。
- 建议的 DDL。
- 应用程序代码所有者或可能的位置。
- 安全实施路径。
- 验证计划。
- 回滚/还原计划。
- 批准要求。

最后以：

“未应用任何 schema 推荐。”结束。
