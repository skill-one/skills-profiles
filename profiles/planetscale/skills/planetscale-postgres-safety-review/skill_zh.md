# Postgres 安全审查

## 目的

为 PlanetScale Postgres 数据库推荐最佳实践。重点关注可用性保护、应用隔离、恢复、安全自动化和可观察性。不要应用任何变更。

## 分支和模式工作流

PlanetScale Postgres 分支不使用 Vitess 风格的部署请求。模式变更直接在每个分支上进行，生产环境中的模式变更应通过应用的正常迁移工作流管理，并包含分支验证步骤。

检查：

- 是否存在开发或测试分支。
- 分支是否为空或从备份中恢复。
- 迁移是否在生产前在分支上进行测试。
- 应用程序迁移是否可逆或有文档化的回滚策略。
- 生产 DDL 是否经过手动审查。

推荐：

- 创建或使用非生产分支进行迁移测试。
- 在该分支上运行迁移验证和应用程序测试。
- 将生产迁移应用视为一个明确的人工批准的部署步骤。
- 使用 PITR/备份恢复分支进行事件恢复，而不是作为自动回滚机制。

未经批准，不要创建分支、运行迁移或恢复备份。

## 角色和最小权限

检查应用程序是否使用默认角色。将其标记为安全漏洞。

推荐：

- 为应用程序服务器使用用户定义的应用程序角色，而不是默认角色。
- 按服务、环境和访问模式分离角色。
- 为分析、仪表板、报告和不需写入的代理使用只读角色。
- 为自动化使用短期存在或用途受限的角色。
- 当 Terraform 管理PlanetScale Postgres角色时，对于密码应保持在Terraform状态之外的 角色，优先使用 `planetscale_postgres_redacted_branch_role`；通过API或仪表板重置密码，并将其存储在团队的密钥管理器中。
- 文档化无需应用程序停机即可进行的凭证轮换。

未经批准，不要创建、重置、删除或轮换角色。

## pg_strict

检查应用程序角色是否启用了 pg_strict。

推荐在生产应用程序角色上启用 pg_strict，前提是工作负载可以容忍没有 `WHERE` 的危险 `UPDATE` 或 `DELETE` 导致的阻塞。

推荐推行方案：

1. 启用警告模式或在可能的情况下评估非生产环境。
2. 修复会被阻塞的查询。
3. 为应用程序角色启用严格阻塞。
4. 文档化批准的临时覆盖程序。

未经批准，不要启用 pg_strict，因为它会在新连接建立后阻塞应用程序查询。

## 查询洞察和 pginsights

审查：

- 慢查询。
- 高行读取查询。
- 高 CPU 查询模式（Insights API 上的 `sort=cpuTime` 或 `sort=percentCpuTime`）。
- 高频查询。
- 出错查询。
- 活跃异常。
- 查询标签。
- 是否启用了字面值/原始查询收集。

原始查询收集受 `pginsights.raw_queries` 集群参数管理，在仪表板扩展选项卡中按分支配置。数据库API对象还携带一个 `insights_raw_queries` 字段；当这两个表面不同时，集群参数是有效的收集状态。仅报告有效状态——永远不要将这两个表面描述为矛盾或不一致。

推荐：

- 将原始查询收集视为一项功能，根据 `../planetscale-query-insights-and-tags/SKILL.md`：当模式级数据无法隔离病态调用时，原始收集是机制。在客户的数据处理需求限制下，范围启用（事件窗口、定义保留期）和禁用收集都是有效结果；记录理由。
- 使用标签进行归因，使用原始收集进行调用级深入分析；它们是互补的工具。
- 使用部署 SHA 和路由/作业标签将回归与应用程序部署相关联。

## 查询标签

评估 SQL 注释是否包含结构化的 SQLCommenter 标签。

推荐支持 Insights 和 Traffic Control 的标签：

- `application`
- `service`
- `route` 使用标准化路由模板，而不是具体 URL
- `controller` 和 `action` 在相关情况下
- `job` 或 `queue` 用于后台工作
- `feature` 用于昂贵的功能，如导出或报告
- `environment`
- `release_sha`
- `tenant_tier` 仅当基数有限时
- `source` 用于代理、脚本、BI 工具、集成和 MCP

避免使用高基数或敏感标签：

- 用户 ID
- 请求 ID
- 邮箱
- 会话 ID
- 租户 ID 除非明确限制并接受
- 带有标识符的原始 URL 路径
- 访问令牌、密钥或 API 密钥

## 数据库流量控制

对于 Postgres，当数据库具有以下模式时推荐使用 Traffic Control：

- 公开或客户触发的昂贵功能。
- 导出、报告、分析或非结构化搜索共享 OLTP 数据库。
- 可能导致交互式流量饥饿的后台作业。
- 查询量不可预测的第三方集成。
- 代理生成的查询。
- 偶尔失控的已知查询指纹。
- 需要限制数据库资源使用的租户或路由类。

默认推荐：

- 在 `warn` 模式下启动预算。
- 尽可能使用查询标签。
- 使用指纹特定规则针对已知违规者。
- 仅在观察到警告并确认没有关键流量被阻塞后使用强制模式。
- 维护一个紧急禁用程序。

未经批准，不要创建预算或执行规则。

## 备份和 PITR

检查：

- 自动备份计划。
- 保留窗口。
- WAL/PITR 可用性。
- 防止删除的手动备份。
- 恢复演练历史记录。
- 恢复运行手册。

推荐：

- 确认默认备份满足客户的 RPO/RTO。
- 如果客户的恢复窗口超过默认值，则增加保留期或添加备份计划。
- 如果 Terraform 是客户的真实来源，则在 Terraform 中管理备份策略，以便保留和计划变更与基础设施代码的其他部分一起审查。
- 在新分支上运行恢复演练。
- 文档化恢复后的确切应用程序切换程序。

未经批准，不要恢复或创建紧急备份。紧急备份可能会影响性能，应将其视为一项运营操作。

## 连接、连接池和网络安全

检查：

- 应用程序是否使用直接端口 5432 或 PgBouncer 端口 6432。
- 连接池大小是否与运行时和部署模型匹配。
- 无服务器或边缘环境是否可能创建连接风暴。
- 通过 `pscale branch connections top` 查看实时连接/会话压力，包括诊断活动事件时的阻塞者和空闲事务会话。
- 是否配置了私有连接。
- 是否配置了 IP 限制。
- 是否意外保留了公开访问。

推荐：

- 对于高 churn 应用程序连接，在可接受事务池限制的情况下使用 PgBouncer。
- 对于 PgBouncer 事务模式无法支持的会话依赖功能，使用直接连接。
- 使用 AWS PrivateLink 或 GCP Private Service Connect 满足私有网络需求。
- 使用 IP 限制减少公开暴露。
- 明确说明私有连接不会自动阻止公开访问；需要 IP 限制或等效控制才能实现私有-only 姿态。

未经批准，不要更改网络限制。网络变更可能会中断应用程序连接。

## 扩展

审查与安全性和可观察性相关的已启用和可用扩展：

- `pginsights`
- `pg_strict`
- `pg_stat_statements`
- `auto_explain`
- `pg_squeeze`
- `pg_cron`
- `pg_partman_bgw`
- `pg_hint_plan`
- TimescaleDB（如果与时间序列功能相关）

仅在用例明确时推荐扩展。`auto_explain` 可用于 PlanetScale Postgres，并在配置了参数（如 `auto_explain.log_min_duration`）时记录慢查询的执行计划；当慢查询计划捕获会显著改善诊断且日志量可接受时推荐它。当 Terraform 是客户的真实来源时，Postgres 分支参数和支持的扩展可以在那里管理，但参数或扩展变更仍需要与仪表板变更相同的批准和重启影响审查。某些扩展激活路径需要仪表板变更和数据库重启；未经批准，不要启用它们。

## Postgres 的 webhook 推荐

评估并推荐以下 webhook：

- `branch.anomaly`
- `branch.out_of_memory`
- `branch.primary_promoted`
- `branch.ready`
- `branch.start_maintenance`
- `cluster.storage`
- `database.access_request`
- `branch.schema_recommendation`（如果可用）
- `webhook.test` 用于设置验证

推荐自动化行为：

- 提醒：异常、内存不足、主节点提升、存储、维护。
- 代理摄入：异常、模式推荐。
- 人工批准：任何生成的流量控制、模式、角色或网络变更。

## 输出

返回：

- 当前 Postgres 安全态势。
- 最高风险的可用性漏洞。
- 推荐的 Traffic Control 计划。
- 推荐的角色和 pg_strict 计划。
- 推荐的备份/PITR 计划。
- 推荐的网络态势计划。
- 推荐的查询标签计划。
- 需要批准的拟议变更。

以：

“未对 Postgres 应用任何变更。”结束。
