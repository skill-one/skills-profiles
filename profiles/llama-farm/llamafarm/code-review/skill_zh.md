# 代码审查技能

你正在对一个 diff 进行全面的代码审查。你的任务是分析变更的代码是否存在安全漏洞、反模式和质量问题。

## 输入模型

此技能期望在调用前提供上下文中的**diff**。调用者负责生成 diff。

**示例调用：**
- 用户粘贴 PR diff，然后运行 `/code-review`
- 代理运行 `git diff HEAD~1`，然后调用此技能
- CI 工具提供待审查的 diff 内容

如果上下文中没有 diff，请要求用户提供或提供生成 diff 的选项（例如 `git diff`，`git diff main..HEAD`）。

---

## 域检测

根据 diff 中的目录路径自动检测要应用哪些检查清单：

| 目录 | 域 | 检查清单 |
|------|----|---------|
| `designer/` | 前端 | 读取 `frontend.md` |
| `server/` | 后端 | 读取 `backend.md` |
| `rag/` | 后端 | 读取 `backend.md` |
| `runtimes/universal/` | 后端 | 读取 `backend.md` |
| `cli/` | CLI/Go | 仅执行通用检查 |
| `config/` | 配置 | 仅执行通用检查 |

如果 diff 跨越多个域，则加载所有相关的检查清单。

---

## 审查流程

### 第 1 步：解析 diff

从 diff 中提取：
- 变更的文件列表
- 变更的行（添加和修改）
- 基于文件路径检测到的域

### 第 2 步：初始化审查文档

使用**temp-files 模式**创建审查文档：

```bash
SANITIZED_PATH=$(echo "$PWD" | tr '/' '-')
REPORT_DIR="/tmp/claude/${SANITIZED_PATH}/reviews"
mkdir -p "$REPORT_DIR"
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
FILEPATH="${REPORT_DIR}/code-review-${TIMESTAMP}.md"
```

使用此架构初始化：

```markdown
# 代码审查报告

**日期**：{当前日期}
**审查者**：代码审查代理
**来源**：{例如，"PR diff"，"未暂存的变更"，"main..HEAD"}
**变更文件数**：{数量}
**检测到的域**：{列表}
**状态**：进行中

## 摘要

| 类别 | 检查项数 | 通过 | 失败 | 发现的问题 |
|------|----------|------|------|-----------|
| 安全 | 0 | 0 | 0 | 0 |
| 代码质量 | 0 | 0 | 0 | 0 |
| LLM 代码异味 | 0 | 0 | 0 | 0 |
| 影响分析 | 0 | 0 | 0 | 0 |
| 简化 | 0 | 0 | 0 | 0 |
{基于检测到的域添加的特定域类别}

## 详细发现

{随着审查的进行在此处添加发现的问题}
```

### 第 3 步：审查变更的代码

对于每个检查清单项：

1. **仅将反馈范围限制为 diff 行** - 仅在变更的代码中标记问题
2. **使用文件上下文** - 读取完整文件内容以了解周围的代码
3. **应用相关检查** - 使用域相关的检查清单项
4. **记录发现** - 记录在变更代码中发现的每个违规行为

**关键原则**：审查的是 diff。文件的其余部分仅提供上下文以使审查准确。

### 第 4 步：影响分析

检查 diff 是否可能影响代码库的其他部分：

- **变更的导出/接口** - 搜索可能中断的其他使用情况
- **修改的 API 签名** - 检查需要更新的调用者
- **更改的共享工具** - 查找可能受影响的消费者
- **配置/架构变更** - 查找依赖于旧结构的代码

将任何未记录的影响报告为发现的问题，并根据风险确定严重程度。

### 第 5 步：记录每个发现

对于每个发现的问题，添加一个条目：

```markdown
### [{类别}] {项目名称}

**状态**：失败
**严重程度**：关键 | 高 | 中 | 低
**范围**：变更代码 | 影响分析

#### 违规

- **文件**：`path/to/file.ext`
- **行号**：42-48（来自 diff）
- **代码**：
```
// 来自 diff 的有问题的代码片段
```
- **问题**：{解释什么不正确}
- **建议**：{如何修复它}
```

### 第 6 步：完成报告

完成所有检查后：

1. 更新摘要表格中的最终计数
2. 添加执行摘要：
   - 发现的总体问题数
   - 需要立即关注的关键问题
   - 影响分析结果
   - 修复建议的优先级顺序
3. 更新状态为 "完成"
4. 告知用户报告的位置

## 通用审查类别

这些检查适用于所有变更的代码，无论域如何。

---

## 类别：安全基础

### 硬编码的密钥

**检查 diff 中的**：
- 变更代码中的 API 密钥、密码、密钥
- 模式：`api_key`、`apiKey`、`password`、`secret`、`token`、`credential` 与字面值一起使用

**通过标准**：diff 中没有硬编码的密钥（应使用环境变量）
**严重程度**：关键

---

### Eval 和动态代码执行

**检查 diff 中的**：
- JavaScript/TypeScript：`eval(`、`new Function(`、`setTimeout("`、`setInterval("`
- Python：`eval(`、`exec(`、`compile(`

**通过标准**：变更行中没有动态代码执行
**严重程度**：关键

---

### 命令注入

**检查 diff 中的**：
- Python：`subprocess` 与 `shell=True`、`os.system(`
- Go：`exec.Command(` 与未清理的输入

**通过标准**：shell 命令中没有未验证的用户输入
**严重程度**：关键

---

## 类别：代码质量

### 控制台/打印语句

**检查 diff 中的**：
- JavaScript/TypeScript：`console.log`、`console.debug`、`console.info`
- Python：`print(` 语句

**通过标准**：生产代码变更中没有调试语句
**严重程度**：低

---

### TODO/FIXME 注释

**检查 diff 中的**：
- `TODO:`、`FIXME:`、`HACK:`、`XXX:` 注释

**通过标准**：新的 TODO 应在问题中跟踪
**严重程度**：低

---

### 空的 catch/except 块

**检查 diff 中的**：
- JavaScript/TypeScript：`catch { }` 或 `catch(e) { }`
- Python：`except: pass` 或空的 except 块

**通过标准**：所有错误处理程序记录或重新抛出
**严重程度**：高

---

## 类别：LLM 代码异味

### 占位符实现

**检查 diff 中的**：
- `TODO`、`PLACEHOLDER`、`IMPLEMENT`、`NotImplemented`
- 仅返回 `None`、`返回 []`、`返回 {}` 的函数

**通过标准**：生产代码中没有占位符实现
**严重程度**：高

---

### 过于通用的抽象

**检查 diff 中的**：
- 名称如 `GenericHandler`、`BaseManager`、`AbstractFactory` 的新类/函数
- 没有明确重用理由的抽象

**通过标准**：抽象由实际重用证明
**严重程度**：低

---

## 类别：影响分析

### 打破变更

**检查 diff 是否修改**：
- 导出的函数/类 - 搜索其他地方导入
- API 端点 - 搜索调用者
- 共享类型/接口 - 搜索使用情况
- 配置架构 - 搜索消费者

**通过标准**：已识别并记录所有受影响的代码
**严重程度**：高（如果发现未记录的影响）

---

## 类别：简化

### 重复逻辑

**检查 diff 中的**：
- 重复的代码模式（不仅仅是语法相似性）
- 复制粘贴的代码带有微小变化
- 类似的验证、转换或格式化逻辑

**通过标准**：变更代码中没有明显的重复
**严重程度**：中
**建议**：将共享逻辑提取为可重用函数

---

### 不必要的复杂性

**检查 diff 中的**：
- 深度嵌套的条件（超过 3 级）
- 执行多个不相关事情的函数
- 过于复杂的控制流

**通过标准**：代码是合理的扁平化和专注的
**严重程度**：中
**建议**：使用早期返回、提取辅助函数

---

### 繁琐模式

**检查 diff 中的**：
- 语言中有更简单替代方案的模式
- 重复的空值检查或类型断言
- 不必要的中间变量

**通过标准**：代码使用语言内置模式
**严重程度**：低
**建议**：使用语言内置功能简化

---

## 域特定审查项

根据检测到的域，读取并应用相应的检查清单：

- **检测到前端**（`designer/`）：读取 `frontend.md` 并将检查应用于变更的代码
- **检测到后端**（`server/`、`rag/`、`runtimes/`）：读取 `backend.md` 并将检查应用于变更的代码

## 最终摘要模板

```markdown
## 执行摘要

**审查完成**：{时间戳}
**总体发现**：{数量}

### 关键问题（必须修复）
1. {问题 1}
2. {问题 2}

### 影响分析结果
- {任何打破变更或未记录影响的摘要}

### 高优先级（应修复）
1. {问题 1}
2. {问题 2}

### 建议
{基于审查变更的整体建议}
```

---

## 代理的注意事项

1. **限制为 diff**：仅在变更行中标记问题。不要审查未变更的代码。

2. **使用上下文**：读取完整文件以了解变更，但反馈仅针对 diff。

3. **检查影响**：当变更触及导出、API 或共享代码时，搜索受影响的消费者。

4. **保持具体**：为每个发现包括文件路径、行号（来自 diff）和代码片段。

5. **优先级**：立即标记关键安全问题。

6. **提供解决方案**：每个发现都应包括如何修复它的建议。

7. **逐步更新**：在每次检查类别后更新审查文档，而不是在最后。
