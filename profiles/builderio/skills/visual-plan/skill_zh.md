# Agent-Native 计划

Agent-Native 计划是一种结构化视觉规划模式，用于编码代理。构建你通常用 Markdown 编写的计划，但作为一个可扫描的文档，其中包含可编辑的模块：内联图表、代码片段、开放式问题，以及可选的顶部视觉审查区域（线框画画布、可交互原型或两者在选项卡中）。架构和后端计划仅保留为文档；UI 和产品计划从顶部画布/原型开始（Visual Surface Choice 部分拥有该规则）。

`/visual-plan` 是打包命令和主要入口点。从任务中选择审查模式：UI 优先，当工作主要是产品 UI 且审查应从屏幕开始时；原型优先，当审查应从可交互原型开始时；设计优先，当审查需要全保真品牌屏幕时；或视觉输入，当用户明确希望在规划之前进行问卷调查时。当存在 Codex、Claude Code、Markdown 或粘贴的计划时，`/visual-plan` 使用该源计划作为起点，并从它构建审查表面，而不是重新开始。

## 何时使用

每当计划作为可审查的工件比聊天段落更好时，请创建或调整视觉计划。这包括适度的工作，例如单个 UI 表面带状态、小型工作流、产品的前/后更改，或需要一致性的组件/API/数据形状决策，以及较大的多文件、模糊、长时间运行、有风险或 UI 密集型工作。当架构/数据流/UI 方向/选项/开放式问题受益于内联图表或结构化块时使用它，当用户需要在实施之前对方向做出反应时，或当现有文本计划需要一个更丰富的审查表面时使用它。

## 计划纪律

- **谨慎地设置门槛。** 视觉计划是一个更丰富的审查表面，而不仅仅是一个用于大型项目的工具。当用户需要在代码之前查看、比较、评论或批准方向时，即使对于适度的 UI/状态/工作流更改也要使用它。跳过真正琐碎、无歧义的工作——拼写错误、单行修复、单个明确定义的函数、任何您都可以用一句话描述的差异——并直接进行更改。永远不要用填充内容来填充计划，也永远不要发布单步计划。
- **在起草之前进行研究。** 首先阅读实际文件、操作、模式和模式；命名实际的文件、符号和数据形状，而不是凭空捏造。在提出端点之前检查现有的 `actions/`，并优先使用命名客户端帮助程序而不是原始获取。将广泛的探索委托给子代理。以重用为起点：对于每个步骤，在添加之前命名它重用的内容——现有的操作、模式、组件、帮助程序——以便计划解释真正新的差异，而不是重新描述已经存在的内容。
- **首先决定难以逆转的赌注。** 对于非琐碎的后端、数据或 API 工作，先勾勒出功能的方向，然后指出一旦数据或调用者依赖它们就难以撤销的决策——线格式、公共 ID、数据模型形状、认证和所有权边界——并在计划中正确处理这些决策，即使大部分功能稍后才会发布。然后范围到最小的第一版，证明方法而不封锁它，说明包含的内容和明确推迟的内容。
- **在正确的层次上保留示例。** 当用户的想法是广泛的框架、产品或运营模式更改时，不要将其压缩为用户提到的第一个具体示例、提供者或同步路径。将核心抽象与激励示例和应用程序/提供者适配器分开。使用示例使计划易于理解，但除非它们是整个请求的范围，否则将它们标记为示例。
- **发布独立的计划。** 如果用户粘贴、引用或已经有了 Codex / Claude Code / Markdown 计划，将其视为源材料，但重写发布的计划作为一个干净的独立提案。保留源计划的有用意图和代码库事实，将推断的视觉标记为推断的，并避免在计划本身中描述更新为先前草稿的更正。在执行重大步骤之前，重新阅读批准的计划。
- **使第一次阅读具体化。** 如果计划打算与聊天外的人共享，或者如果概念是抽象的，请在顶部附近以一个具体的产品示例开始，然后再是模式表、架构或路线图。对于具有 UI 能力的概念，这通常意味着一个显示真实用户工作流程的顶部画布应用状态，用产品术语表示。不要依赖于仅在对话中才有意义的短语，也不要将计划描述为“不是旧想法”；直接陈述积极的模型。
- **规划是只读的。** 在构建或审查计划时，不要进行任何源编辑。只有在用户批准方向后，才开始编辑。
- **澄清而不是假设。** 不要询问如何构建它——在计划中探索和展示方法和选项。只有在歧义会改变设计并且您无法从代码中解决时，才提出澄清性问题；使用主机代理的正常 ask-user-question 流，并在最终确定之前分批提出 2-4 个高杠杆问题。不要为普通澄清或预检调用 `create-visual-questions`；将其保留为视觉输入模式，当用户明确要求视觉输入问卷时。否则，明确说明假设并继续，并将任何未解决的问题保留在计划底部的 `question-form` 开放式问题块中。对于复杂的计划，在交接之前进行最终开放式问题检查：如果某个决策会影响架构、范围、UX、数据形状或发布，则在计划中说明其理由或将其放入底部的表单中，并建议默认值。
- **计划是批准的门槛。** 在显示它之后，在您编写代码之前，请用户审查和批准，并命名受其影响的文件/区域。提出计划并请求确认是批准步骤——不要询问一个单独的“这个看起来怎么样？”的问题。
- **文档是事实来源，而不是聊天。** 当范围发生变化时，使用 `update-visual-plan` 更新计划，而不是仅在聊天中更改方向，并使更新后的文档保持独立。不要在计划本身中描述更新为先前草稿的更正。在执行重大步骤之前，重新阅读批准的计划。

## 创建结构化 Agent-Native 计划——绝不内联

交付物始终是结构化的 Agent-Native 计划，而不是仅聊天计划。托管 Plan MCP 连接器（`plan` 服务器，或遗留 `agent-native-plans`）是默认的协作和评论表面；它不是拒绝规划模式作为外部依赖项或租用层的理由。计划是可移植的源工件（`plan.mdx`，可选的 `canvas.mdx` / `prototype.mdx`，JSON 和 HTML 导出），所有权敏感的工作流可以使用本地文件模式或自托管/自定义 Plan 应用 URL 而不放弃技能的审查纪律。不要建议用户跳过 `/visual-plan`，因为默认表面是托管的；为用户的所有权、隐私、共享和品牌需求选择正确的 Plan 模式。

默认情况下，通过 Plan MCP 连接器创建计划，并且绝不将其作为内联聊天内容交给——没有 Markdown 课文、ASCII 绘图、表格或围栏线框。如果 `plan`（或遗留 `agent-native-plans`）工具不可见，通过主机的 `tool_search` 首先发现它们；如果它们仍然丢失，请停止并给用户提供客户端特定的重新连接步骤，而不是即兴创作一个内联计划。在发布之前，或者每当出现连接器或身份验证错误时，请阅读此技能目录中的 `references/connection.md`——它是“绝不内联”规则、连接器发现和每个客户端重新连接步骤的唯一事实来源。本地文件隐私模式（在 Tool Guidance 之后）是例外。

## 核心工作流

本节描述默认的托管 Plan MCP 工作流。如果 `AGENT_NATIVE_PLANS_MODE=local-files` 被设置，或者用户要求完全本地文件/无托管 Plan 写入，请使用 **本地文件隐私模式**；仅转发代码研究和计划组合指导。

1. 遵循主机代理的正常规划流程：检查代码库，在有用时委托广泛的探索，收集所需的信息，并在生成计划之前根据需要提出本地澄清问题。如果存在源计划，从用户的粘贴、引用的文件或最近的可见代理上下文中收集其确切文本；不要凭空捏造源文本。
2. 调用 `get-plan-blocks` 获取权威的块目录——不要从记忆中的标签进行创作。然后调用匹配模式的创建工具：
   `create-visual-plan` 用于文档优先的计划（架构、后端、数据、重构、API），`create-ui-plan` 用于 UI 优先的计划，`create-prototype-plan` 用于原型优先的计划，`create-plan-design` 用于设计优先的计划，`create-visual-questions` 仅在用户明确要求视觉输入问卷时使用。当存在源计划时，将 `planText` 作为参数传递，并在生成独立计划文档的同时保留原始计划的有用意图，而不是重新开始。
3. 对于 UI/产品计划，首先使用主要的线框图和注释状态组成顶部画布，然后使用本地块编写文档（见 `references/canvas.md` 和 `references/document-quality.md`）。对于具有用户界面影响的产品架构计划，在抽象架构或模式表之前添加一个具体的“在应用中看起来像什么”的视觉。保持文档与代理通常输出的独立 Markdown 计划接近。如果提供了现有计划，请在不参考先前草稿或解释此版本与先前版本有何不同的情况下，继续保留正确的 факты 和决策。对于非视觉计划，跳过顶部视觉表面（Visual Surface Choice 下面拥有该规则），并将 `diagram`、`data-model`、`api-endpoint`、`diff`、`file-tree`、`code` 和 `annotated-code` 块直接放在相关的文本旁边。
   宽文档布局由渲染器拥有，并有意允许：只有字面代码审查表面（`diff`、`annotated-code`）和具有垂直方向或 diff 类似子元素的 `tabs` 块比文本更宽。除非它们自己的渲染器另有说明，否则将 `api-endpoint`、`openapi-spec`、`data-model`、`json-explorer`、`wireframe`、问题 和 `custom-html` 块保持在正常文档流中。
4. 显示返回的计划链接或内联 MCP 应用，并要求用户审查。始终在聊天中包含实际的 URL，以便下一步是在 CLI 或其他纯文本主机中单击。当主机暴露嵌入式浏览器/预览面板并且工具可以自动打开任意 URL 时，请自动打开返回的计划 URL 以便方便审查——这是一种便利性和烟雾测试，绝不是唯一的交接或访问模型。计划应针对本地代理和本地浏览器会话自动加载；如果登录的嵌入式浏览器无法读取本地计划，而匿名/工具检查可以读取，请修复应用程序/操作所有权或访问路径，而不是手动修补一个计划。对于高风险计划（架构、后端、数据、多文件或有风险），同时用户阅读时，也启动 **交接前的自我审查**，而不是在交接上阻塞它。
5. 对于托管计划，在编辑之前、审查之后、任何长时间暂停之后以及最终响应之前调用 `get-plan-feedback`。将 `anchorDetails`、resolver 意图、最近的审查事件以及来自浏览器交接的任何聚焦截图视为事实来源，以了解确切发生了什么以及每个评论指向的确切内容。
6. 对于托管计划，使用 `update-visual-plan` 应用更改，优先使用有针对性的 `contentPatches`。将顶级 `content` 有效负载视为完整替换，而不是合并；不要发送一个部分 `content` 对象来添加画布或一个块。如果无法避免完整替换或 `replace-blocks`，请在写入之前立即调用 `get-visual-plan`，将它的 `plan.updatedAt` 作为 `expectedUpdatedAt`，并继续转发每个现有块和视觉表面。永远不要重用来自先前阅读或反馈有效载荷的修订。
7. 在每次托管计划写入后，再次调用 `get-visual-plan` 并比较持久化的文本、块 ID/计数、画布框架和原型与预期结果。成功的突变响应并不是证明无关内容幸存的证据。如果编辑解决了代理目标的反馈，只有在您实际解决了代理目标的评论后，才调用 `resolve-plan-comment` 为该线程，并调用 `consume-plan-feedback` 为其评论；执行两者，以便解决的目标反馈既不会明显打开，也不会作为待处理工作返回。
8. 对于托管计划，仅在用户想要一个可共享的收据或仓库检查入档时，才使用 `export-visual-plan`。

## 交接前的自我审查

此对抗性自我审查传递是可选的，不是默认的：仅对高风险计划运行它——不可逆的迁移、安全敏感的工作，或当用户明确要求额外的严格性时——否则跳过它。它大致将计划生成的成本翻倍，因此对于小型、仅 UI、单决策或普通计划，默认是跳过，而不是运行它。在运行时保持传递廉价且非阻塞：

- **首先显示计划，同时审查。** 发布链接并让用户开始阅读，然后并行运行审查——决不使用户等待它。
- **审查已编写的计划；不要重新研究。** 批评计划文本及其自己的块。在起草时已经进行了基础工作，因此审查检查输出而不是重新探索代码库。
- **生成一个怀疑的审查者**，其唯一工作是找到薄弱、缺失或错误的地方——不是表扬。将其指向：难以逆转的决策，一旦数据或调用者依赖它们就难以撤销——线格式、公共 ID、数据模型形状、认证和所有权边界——并在计划中正确处理这些决策，即使大部分功能稍后才会发布。然后范围到最小的第一版，证明方法而不封锁它，说明包含的内容和明确推迟的内容。
- **修复而不是询问。** 使用 `update-visual-plan` `contentPatches` 应用明确的修复——模糊的非目标、无锚点的声明、一个明显的缺失决策（“当 X 发生时会发生什么？”，“为什么不是 Y？”）；将真正的判断问题路由回用户，而不是自己决定它们。
- **在阅读中不要让用户感到意外。** 对于大型计划，在编辑器加载之前应用补丁；否则，简要说明正在运行自我审查，以便用户预期计划在它们下面正在更改。下次响应时，总结审查更改的内容以及用户需要决定的内容。

## 视觉表面选择

在创建计划之前或阅读源计划之后选择表面。默认情况下，不要添加视觉铬。对于 UI/产品计划，顶部画布通常是主要的审查表面。将第一个有意义的线框图放在那里，而不是作为文档体块埋藏。当状态很重要时，使用多个画布艺术板，例如默认视图、溢出菜单或弹出框、侧面板、加载或错误。使用 `targetId` 加上 `placement` 在线框旁边放置简短注释；将实现细节、权衡、文件映射、数据合同、风险和验证保留在画布下方的文档体中。

当用户要求流程、故事板、旅程、线框画或“看起来像什么”时，将其视为画布优先请求。为每个用户可见状态使用一个艺术板，仅连接相邻的转换，并使用简短的画布注释进行产品注释。不要用文档体的 `diagram` 块来代替请求的故事板，仅仅因为 HTML 图表编写起来更快；图表应保留在线框下方用于后端机制、架构或数据流解释。

保留产品线框画和解释性/元图表分开。从看起来像正在讨论的应用状态的纯屏幕开始，不要嵌入调用正文或架构注释。将箭头、标签、合同、数据流和模式解释放在单独的注释、单独的画布图表或文档体中。

当计划涉及现有应用时，在绘制之前检查当前外壳/组件。第一个艺术板应看起来像真实应用，密度相同：现有的侧边栏、工具栏放置、溢出菜单、应用外壳和框架代理外壳保留在它们真实的位置。将次要表面建模为单独的状态，例如右上角的溢出弹出框、表单、面板、加载状态或单独的 AgentSidebar，而不是发明一个永久性的检查器或折叠框架外壳到产品 UI 中。

- **对于仅架构、仅后端、数据迁移、仅复制或其他非视觉计划，** **没有视觉表面**。不要使用顶部画布进行架构图表、依赖关系图、文件计划、API 合同或仅数据流审查。当关系需要视觉解释时，使用一个空间图表每个建议或决策。优先使用分组区域、层、象限、矩阵或前/后面板，而不是单轴链，除非关系确实是顺序的。
- **仅画布** 用于静态屏幕、前/后比较、组件状态、小型弹出框或不需要点击的视觉方向。将那些线框图放在 `content.canvas` 中，并省略 `content.prototype`。
- **画布 + 原型** 用于多步骤 UI 流程、引导、向导、审查/批准流程、导航更改或任何需要审查者操作的行为。将静态线框图保留在 `content.canvas` 中，在 `content.prototype` 中添加对齐的功能原型，并依赖顶部的视觉选项卡在它们之间切换。当两个表面都存在时，默认打开 Wireframes 选项卡；原型作为交互式后续视图仍然可用。
- **默认为线框图。** 干净、极简的 UI、高 UX 标准或对 Linear/Vercel 的参考描述了内容和密度条；它们不要求全保真设计模式。除非用户明确要求品牌、像素精确、生产级或全视觉设计，否则使用渲染器拥有的线框图。这使每个画布屏幕都可检查，并且其全部内容都可见。
- **原型优先** 当用户要求操作 UI 或当交互是主要问题时。使用 `create-prototype-plan`，它仍然保留静态模拟，这仍然很有用。

对于混合画布 + 原型计划，重用标签和 ID；除非明确单个表面，否则一起修补表面。对于输出审计，请阅读可观察性技能：支持单应用和 workspace 表格，保留应用预览，并使审计、综合、差异和应用更改由管理员管理。

将“更高保真度”、“像素精确”、“抛光模拟”、“生产级”、“真实设计”和“不是草图/线框图”视为设计优先语言，即使请求中也包含“模拟”。对于新计划，使用 `create-plan-design`。对于现有计划，保留相同的计划 ID，并调用 `update-visual-plan` 使用 `set-visual-render-mode` 补丁，使用 `renderMode: "design"`，并在同一更新中添加升级的屏幕 HTML/CSS；将结果建立在真实应用外壳、令牌、排版、间距和状态之上，并添加稳定的 `data-design-id` 目标。将作用域样式放在每个屏幕的 `css` 字段中，永远不要放在 `<style>` 标签中。查看器本地 Clean 切换仅更改一个浏览器的线框图偏好；它不是保真度升级。不要创建一个重复计划来处理保真度后续处理。

## 线框图质量——阅读 `references/wireframe.md`

UI 回顾/计划线框图必须满足严格的保真度标准——全宽铬、固定底部栏、真实产品内容、前/后可比较性、正确的 `surface` 预设、`--wf-*` 令牌而不是十六进制，并且没有 `<html>`/`<style>`/font 标签。在编写任何线框图 / `<Screen>` / `WireframeBlock` 之前，请阅读此技能目录中的 `references/wireframe.md`——它是 HTML 线框图保真度的唯一事实来源，与 `/visual-plan` 和 `/visual-recap 完全相同的字词。不要从记忆中编写线框图。

## 画布——阅读 `references/canvas.md`

画布是静态 UI 模拟的唯一事实来源：`surface` 锁定每个艺术板的占位符，混合表面按车道布局，注释是纯文本设计者注释，由 `targetId`/`placement` 锚定，编辑是外科手术 `contentPatches`。在编写或编辑任何画布、艺术板或注释之前，请阅读此技能目录中的 `references/canvas.md`——它是画布/艺术板机制的唯一事实来源。不要从记忆中编写画布布局。画布艺术板使用与文档体 `WireframeBlock` 屏幕相同的 HTML 线框图路径：使用语义 HTML 片段编写 `<Screen surface="..." html={...} />`。不要在画布 `<Screen>` 标签内编写新的 kit-tree 子元素，例如 `<FrameScreen>`, `<Card>`, `<Row>`, 或 `<Btn>`；这些是旧计划的传统兼容性标记，会产生脆弱的画布布局。

## 文档质量——阅读 `references/document-quality.md`

文档是一个严肃的技术计划，而不是营销：结果优先、正文优先、自包含、由正确的本地块构建，开放式问题在单个底部的 `question-form` 中，并在交接前进行视觉检查。在编写计划文档之前，请阅读此技能目录中的 `references/document-quality.md`——它是文档质量标准的唯一事实来源。不要从记忆中编写文档。

## 好与坏的示例——阅读 `references/exemplar.md`

为了了解标准——一个优秀的 UI 优先计划和 `/visual-plan`，以及要避免的反模式——在编写计划之前，请阅读此技能目录中的 `references/exemplar.md`。

## 编写不变量

将它们视为数据完整性检查，而不是可选的润色：

- `content` 是完整的替换。传递 `content` 或模式的便利性数组（`screens`/`transitions` 或 `states`/`components`），永远不要两者都传递。创建操作拒绝混合来源，因此第二个有效负载不能默默地丢弃 CSS、框架或文档块。
- 设计屏幕的 `css` 是工件的一部分。将它在匹配的画布框架和对应的原型屏幕上保持，并使用渲染器拥有的 `--wf-*` 令牌来传输可移植的颜色和排版。
- 富文本 `data.markdown` 必须包含实际的运行时换行符。不要将一个包含字面值 `\n` 转义文本的单行 Markdown 值交给计划，这将使整个部分显示为一个标题。转义的新行仅在代码示例中是允许的，前提是周围的 Markdown 仍然有实际的换行符。
- 画布艺术板不滚动。保持线框图 HTML 在自然流中，当屏幕超过表面预设时，设置更大的框架 `height`；保留表面宽度，并在交接前在默认缩放下检查底部边缘。在每次托管写入后，重新阅读结构化内容并检查活动的 Plan 表面。有效的 JSON 有效负载不是证明 CSS 加载或 Markdown 渲染为预期标题、段落和列表结构的证据。

## 工具指导

- `create-visual-plan`: 为每个代理任务/运行启动一个结构化视觉计划，或通过传递 `planText` 导入现有的文本计划；`content` 可能不包含视觉表面、仅画布或画布 + 原型。
- `create-ui-plan`: 当工作主要是产品 UI 时，启动 UI 优先的计划。
- `create-prototype-plan`: 启动具有功能顶部审查表面的原型优先计划。如果交互本身也必须是高保真，请将每个屏幕的 `renderMode` 设置为 `design`，并通过 `css` 传递作用域样式；否则使用 `create-plan-design` 进行设计优先审查。
- `create-plan-design`: 启动具有可选匹配原型选项卡的全保真品牌设计选项卡计划。
- `convert-visual-plan-to-prototype`: 将现有的 HTML 线框图画布转换为原型计划。
- `create-visual-questions`: 仅在用户明确要求视觉输入问卷时使用，而不是作为 `/visual-plan` 预检。
- `update-visual-plan`: 使用有针对性的 `contentPatches` 修订内容、状态或评论（见核心工作流步骤 6-7）。使用 `set-visual-render-mode` 与 `renderMode: "design"` 将现有计划提升到高保真度，并与故意的屏幕 HTML/CSS 一起进行更新；仅使用渲染模式本身仅删除草图处理。`replace-blocks` 和完整 `content` 替换需要 `expectedUpdatedAt` 从一个新鲜的 `get-visual-plan` 调用获取。
- `read-visual-plan-source`: 读取规范化计划作为 `plan.mdx`、可选的 `canvas.mdx`、可选的 `.plan-state.json` 和 JSON。
- `patch-visual-plan-source`: 通过稳定的块、艺术板、注释、组件或线框节点 ID 应用细粒度 MDX AST 补丁。优先使用这些有针对性的操作；`replace-file` 需要来自新鲜 `get-visual-plan` 调用的 `expectedUpdatedAt`。
- `import-visual-plan-source`: 从 MDX 文件夹创建或替换计划。
- `get-visual-plan`: 读取当前结构化计划、导出的 HTML、注释和 `plan.updatedAt`；它还返回源工作流的 MDX 文件夹。在破坏性写入之前立即重新读取它以获取并发围栏，并在每次写入后再次读取以验证持久化状态。
- `get-plan-feedback`: 读取未消费的人类反馈。频繁使用它；它返回分组线程、确切的锚点细节、预期的 resolver 和最近的审查事件有效负载，以便代理仅对指向它们的评论采取行动。
- `get-plan-blocks`: 在创作之前解析块标签——不要记忆标签；首先调用它以获取来自实时块注册中心的权威标签名称、必需字段和 prop 形状。
- `export-visual-plan`: 导出 HTML、Markdown 降级、结构化 JSON 和 MDX 文件以供仓库检查入档。

当用户批评计划的样式或结构时，修复渲染器或此技能——绝不手动编辑存储的计划。将反馈转化为更好的指导。

## 本地文件隐私模式——阅读 `references/local-files.md`

当用户想要没有托管 Plan 数据库写入——没有 DB 写入、没有 Plan MCP 发布、完全本地/离线/私有规划、仓库拥有的源代码控制工件或 `AGENT_NATIVE_PLANS_MODE=local-files` — 不要调用任何托管 Plan 工具，除了模式仅 `get-plan-blocks` 目录查找。编写本地 MDX 文件夹并通过 `plan local check` / `plan local serve` / `plan local verify` 预览它。在使用本地文件模式之前，请阅读此技能目录中的 `references/local-files.md`——它是完整合同（目录查找、MDX 文件夹布局、本地桥接命令和您必须不调用的托管工具）的唯一事实来源。仅转发代码研究和计划组合指导；托管内容被本地桥接取代。

## 解释评论锚点

本节适用于托管计划具有 `get-plan-feedback` / `update-visual-plan`。在本地文件模式下，不要调用托管反馈或更新工具；直接解释文件/聊天反馈，编辑 MDX 文件，重新运行本地桥接检查/服务/验证命令，并报告新的本地 URL。

`get-plan-feedback` 返回丰富的锚点——在执行任何评论之前阅读它们。

- **坐标框架。** `targetX`/`targetY` 是元素名称由 `targetSelector`/`targetKind` 指定的元素内的百分比。裸 `x`/`y` 是整个计划文档的百分比。`canvasX`/`canvasY` 是设计画布上的原始板世界像素（当可用时给出板大小）。
- **线框图销钉。** 锚点在线框上包括 `targetNodeId` 和 `targetNodePath`（例如 `card > list > listItem "Acme Inc"`）识别的确切 kit 节点。直接使用 `targetNodeId` 与线框图节点修补操作；使用来自设计艺术板的 `data-design-id` 值与 `update-design-element-style`。优先使用节点 ID/路径而不是原始坐标；仅在没有任何节点 ID 的情况下，才 fallback 到坐标加上浏览器交接的聚焦截图（红色圆圈标记的确切点）。

## 可见性与共享

使用 `set-resource-visibility` 更改谁可以看到计划（例如公共、登录或组织范围）。使用 `share-resource` 通过电子邮件或角色授予特定用户或角色的访问权限。在共享任何覆盖未发布或私有工作的计划之前设置可见性——默认为满足审查需求的狭窄范围。

## 设置与身份验证

进入计划的两种方式。

**编码代理（CLI）。** 使用 Agent-Native CLI 一次安装。该命令安装计划技能，注册托管 Plan MCP 连接器，并在同一步骤中运行选择的本地客户端的 auth/setup（设置时的一次性浏览器登录——这是预期的），因此该客户端中的第一个工具调用不会遇到 OAuth 墙：

```bash
npx @agent-native/core@latest skills add visual-plans
```

之后，`/visual-plan`、`/visual-recap` 和 `/visualize-repo` 是安装的斜杠命令。如果您只需要一个命令，请使用 `skills add visual-plan`、`skills add visual-recap` 或 `skills add visualize-repo` 而不是。其他规划模式（`create-ui-plan`、`create-prototype-plan`、`create-plan-design`、`create-visual-questions`) 是 MCP 工具，可以从 `/visual-plan` 访问，而不是单独的斜杠命令。传递 `--no-connect` 以注册连接器而不进行身份验证，然后在您准备好时运行 `npx @agent-native/core@latest connect https://plan.agent-native.com --client all`，或者选择更窄的 `--client`。身份验证和 MCP 工具加载是每个客户端配置/会话的。

**浏览器（您要与之共享的人）。** 打开计划编辑器并创建和编辑，无需注册即可工作——您作为访客工作。仅在您想要保存或共享时才登录；仅在您明确要求视觉输入问卷时才登录；登录后，将您作为访客制作的计划声明为您的帐户中的计划。

共享和评论需要帐户：公共/共享计划可通过链接查看，但评论需要 Agent-Native 帐户。

对于完全离线、无帐户使用，请本地运行计划应用并将计划同步到您的仓库作为 MDX。此本地模式是高级路径，不是默认的托管流程。

对于仓库范围的视觉文档，运行

```bash
npx @agent-native/core@latest visualize-repo --open
```

以创建/更新 `agent-native.json`，播种 `.agent-native/visual-docs/repo-overview`，并打开本地桥接。

如果 Plans 工具返回 `needs auth`、`Unauthorized` 或 `Session terminated`，不要继续重试它——停止并给用户提供客户端特定的重新连接步骤，从 `references/connection.md`，然后在连接器可用时继续。

托管默认：连接 `https://plan.agent-native.com/mcp`。不要在技能文件中放置共享密钥。
