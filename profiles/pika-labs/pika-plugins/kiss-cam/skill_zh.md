# kiss-cam

一个两步调制的pika流程：观众视角Jumbotron静态图（`gpt-image-2`）→ 15秒赛场内亲吻摄像机片段，包含PA解说员评论和观众反应（`kling-v3-omni`，第一帧锁定为静态图）。趋势外观已校准——直接通过参考图像。提示中无文本替换；主题仅通过`images`锚定。不要使用`${subject_a}` / `${subject_b}`占位符。步骤1和步骤2提示是逐字逐句的，不是脚手架。

## 前置条件

主机中可用pika MCP。工具名称前缀因挂载点而异——使用主机暴露的任何内容。需要的工具：身份余额、资产上传、图像生成、参考视频生成，以及在生成未直接完成时异步状态跟踪。

## 成本透明门

在执行任何付费MCP调用之前，调用一次`identity_balance({verbose: true})`。显示当前余额、近期消耗率和剩余运行时间，然后用以下确切消息锁定运行：

> 预计成本：GPT-image-2 Jumbotron静态图约1,500-3,500信用点（~$15-$35），一个或两个Kling v3-omni专业15秒渲染（包括一个带有更改有效负载的步骤2纠正重试），以及飞行后analyze_media QA。这超过了$5，请回复`proceed`继续或`cancel`停止。

在用户回复`proceed`之前，不要调用任何付费MCP工具。如果用户回复`cancel`，则不生成。这是唯一的yes/no门；在`proceed`之后，管道端到端运行。

## 生成前时钟保护

在两个主题参考URL解析并通过成本门后，在技能开始时启动计时器。第一个付费生成调用是步骤1 `generate_image_edit`，必须在技能开始后的5分钟内调用。如果在技能开始后的5分钟内未调用`generate_image_edit`，则在任何付费生成调用之前停止，并报告`failed_pre_generation_timeout`以及到目前为止的内容：主题URL状态、上传状态、成本门状态、步骤1提示准备状态和确切阻塞器。不要继续完善Jumbotron提示、摄像机语言或样式锁定措辞。

在每次准备阶段后并在付费生成调用之前打印单行进度检查点：
- `Stage 1/3 done — subject references resolved and uploaded.`
- `Stage 2/3 done — cost gate passed, locking the Jumbotron still prompt.`
- `Stage 3/3 done — still prompt locked, calling GPT-image-2 now.`

提示和静态图措辞迭代最多2次，在步骤1之前。在最多2次迭代后，将您拥有的内容发送到`generate_image_edit`；不要继续完善记分牌细节、赛场氛围或亲吻摄像机图形语言。

## 长任务`task_status`轮询

当任何长任务生成调用返回带有或未带有初始状态的`task_id`时，包括`{task_id}`、`{task_id, status: "queued"}`或初始`queued`、`running`或`processing`状态，立即记录任务ID和开始时间。

- 在终端状态（`completed | failed | cancelled`）之前，以紧密循环调用`task_status({task_id})`。不要手动睡眠和不要Bash轮询；工作线程保持每个状态调用打开。
- 在状态为`queued`、`running`或`processing`时，每60秒发出一条可见的进度行：`Seedance i2v queued for {N}m {S}s... still processing`。在轮询GPT-image-2或Kling任务时替换提供者/阶段标签。
- 在`completed`时，展开返回的结果URL并继续。
- 在`failed`或`cancelled`时，向用户展示失败，包括`task_id`、状态和最后的状态消息。
- 从原始提交后15分钟，如果任务仍然非终端，调用`task_cancel({task_id})`，然后向用户展示失败。如果取消报告任务已经是终端状态，再次调用状态一次并报告终端结果。
- 在原始任务仍然是`queued`、`running`或`processing`时，不要提交重复请求。

## 步骤0 — 摄入

如果使用空参数且没有可用的先验上下文，打印此菜单并停止：

> **哪两个主题应该在亲吻摄像机上？** 必须提供：
>
> - **主题A参考照片** — 本地路径或HTTPS URL
> - **主题B参考照片** — 本地路径或HTTPS URL

如果一张照片已经存在，只询问缺失的照片。在两者都到达之前运行会留下步骤1中缺失的`images`条目，并产生一个不一致的静态图。

- **主题A参考照片** *(必需)* — 本地路径或https URL。保存为`state.subject_a_url`。
- **主题B参考照片** *(必需)* — 本地路径或https URL。保存为`state.subject_b_url`。

对于每个：如果已经是`https://…` URL，则直接使用它。如果是本地路径 → `upload_asset` → PUT字节到`presigned_url` → 使用`public_url`。在Claude桌面版上，粘贴的内置图像无法到达MCP——询问一次URL或`.zip`附件（这是允许的澄清；一旦两个URL都存在，只有成本门剩余）。

任何一个主题都可以是任何视觉风格——照片级真实人类、3D渲染角色、设计师玩具、插画头像、雕塑小雕像等。该配方保留了参考使用的任何风格；不要用不同的风格重新绘制。**任何地方都不使用名称**——亲吻摄像机图形没有带有名称的 chyron。只是两个主题被捕捉在Jumbotron上。

运行成本透明门，然后在一条线上确认（“为这对人生成麦迪逊广场花园亲吻摄像机时刻…”）并开始。**成本门之后没有进一步的yes/no门**——管道端到端运行。

## 步骤1 — 观众视角Jumbotron静态图（`generate_image_edit`，gpt-image-2）

亲吻摄像机图形+记分牌+复古框架在帧0被烘焙到静态图中——承重，因此Kling在步骤2中将整个装饰UI视为像素锁定的烧入UI，而不是在片段中动画它。

**为什么gpt-image-2（且没有备用方案）：** 更清晰的LED面板细节（记分牌数字、亲吻摄像机排版、复古装饰边缘）和比替代提供者更强的参考锁定；LED清晰度+外观组合是卖点。在`moderation_blocked`响应时，重新滚动相同的调用而不是切换提供者——在早期试验中，替代方案产生了较软的外观和较软的LED细节。我们调用gpt-image-2时为1K 16:9（1792×1024）；更高分辨率的变体在这里没有帮助，因为Kling专业输出1080p。

重试预算：步骤1 gpt-image-2静态图生成最多3次总尝试，包括审核命中和自我检查重新滚动。`moderation_blocked`计入此步骤1上限。在每次付费静态图调用之前跟踪`state.step1_attempt_count`。

**为什么Jumbotron-POV手机拍摄（而不是电视广播叠加）：** 第一次迭代产生了一个带有粉色心形亲吻摄像机图形的电视广播切away——用户反馈是“亲吻摄像机图形丑陋，看看真实视频中真实的亲吻摄像机时刻的样子。” 网络上几乎所有的真实病毒亲吻摄像机片段都是观众手机拍摄的Jumbotron（奥巴马时代美国篮球亲吻摄像机、Sarah Hyland / Wells Adams亲吻摄像机等）。Jumbotron拍摄构图击中了用户实际关联到“真实亲吻摄像机”的美学——复古红色边框+闪亮的爱心+手写Kiss Cam脚本+相邻的LED记分牌面板+赛场黑暗+粉丝用手机拍摄。

**`prompt`** (逐字逐句，发送原样——无模板替换):

```
从麦迪逊广场花园内拥挤的观众席向下拍摄的观众视角手机截图，拍摄者为坐在较低看台上的粉丝，抬头看着巨大的悬挂式Jumbotron显示赛场内“亲吻摄像机”片段。真实粉丝拍摄的手机视频美学——TikTok / Instagram在线亲吻摄像机片段风格。

前景（帧底部的20%）：几排前面粉丝的背影/头部的剪影，略微失焦，黑暗；几部手机举起来拍摄Jumbotron，明亮的手机屏幕可见。

中景/上部80%：Jumbotron在中心上方主导，明亮的LED面板与黑暗的赛场天花板和上方电缆形成对比。轻微的手机相机倾斜，略微偏离自然手持构图。周围赛场昏暗，隐约可见上层看台剪影。

Jumbotron的中央LED面板以标志性的复古赛场亲吻摄像机风格显示亲吻摄像机片段：
- 厚重的深猩红色发光装饰边框。
- 明亮的红色闪亮卡通心形图标在角落和边缘发光。
- 深红色边框中有微妙的白色星形纹理。
- 在中心底部，大号流动的白色手写“Kiss Cam”带有红色发光和阴影。

在Jumbotron的亲吻摄像机框架内，两个主题以双人镜头胸部向上构图：
- 左边（主题A）是第一个参考图像中的角色——保留他们的确切外观和确切视觉风格（中等、风格化程度、调色板、渲染属性）。不要用不同的风格重新绘制。主题A害羞地微笑，一只手靠近脸，看起来被吓了一跳并咯咯笑。
- 右边（主题B）是第二个参考图像中的角色——保留他们的确切外观和确切视觉风格。不要用不同的风格重新绘制。主题B直立坐在人类比例旁边，头部略微转向主题A。
- 他们在框架周围：穿着蓝橙球衣的拥挤的尼克斯球迷，笑着，指着，微笑着看亲吻摄像机。

Jumbotron的相邻LED面板显示：“尼克斯57 — 公牛61”，第四节，时钟“4:32”，带有球队标志。小号“麦迪逊广场花园” / “MSG” / AT&T品牌。

手机相机美学：轻微运动模糊，轻微手持缺陷，黑暗区域略 noisy，明亮LED略微过曝，16:9宽高比，真实观众视角。看起来像是从粉丝拍摄的Instagram / TikTok亲吻摄像机片段中提取的静态图像。
```

**调用参数:**

- `provider`: `gpt-image-2` (承重——最清晰的LED面板细节和最强的参考锁定；没有备用提供者，在步骤1预算内只重新滚动相同的调用)
- `images`: `[state.subject_a_url, state.subject_b_url]` *(顺序很重要——主题A必须是索引0，主题B是索引1；提示的“第一个/第二个参考图像”指的是数组索引)*
- `aspect_ratio`: `16:9`
- `quality`: `medium` *(默认为速度；`high`现在已公开，但~2分钟/调用——仅在保真度重要时使用)*
- `output_format`: `png`

**不要传递任何主题的文本特征描述。** 上述提示已经仅将每个主题描述为“来自第一个/第二个参考图像的角色”——这是故意的。描述头发/脸/衣服/配饰的文本与参考图像冲突并导致漂移：口头特征覆盖视觉参考，模型将主题同化到描述中。

参考图像包含所有身份+风格信息；提示仅添加风格保留锁定。这适用于任何参考风格——照片级真实、3D渲染、雕塑、插画等——而无需命名风格。

将返回的URL保存为`state.kisscam_still_url`。

**代理端自我检查步骤2前**：视觉检查——如果“Kiss Cam”拼写错误，记分牌看起来不对，或任何主题的外观漂移，在步骤1上限内重新滚动步骤1。下游所有内容都像素锁定到这个图像。这是代理自己的检查——不要询问用户。

**失败时** (`moderation_blocked`来自gpt-image-2——通常是女性/女性主题配对+"kiss cam"措辞)：在步骤1预算内重新滚动相同的调用；不要切换提供者——替代方案产生了较软的外观和较软的LED细节。

## 步骤2 — 赛场内亲吻摄像机片段（`generate_reference_video`，kling-v3-omni）

Kling-omni `image_types: ["first_frame"]`将静态图锁定为字面帧0，因此Jumbotron、记分牌、亲吻摄像机框架、心形、手写“Kiss Cam”文本和前景粉丝剪影在所有15秒内都保持像素锁定。只有亲吻摄像机框架内的内容会动画。

**调用参数:**

- `provider`: `kling`
- `kling_model`: `kling-v3-omni`
- `duration`: `15`
- `aspect_ratio`: `16:9`
- `quality_mode`: `pro` (1080p)
- `reference_images`: `[state.kisscam_still_url]` *(使用最新值——步骤1重试会覆盖它)*
- `image_types`: `["first_frame"]`
- `sound`: `true`
- `prompt_adherence`: `strict`
- `negative_prompt` (逐字逐句):

```
场景切换，记分牌变化，Kiss Cam文本变化，图形变形，角色变成真实，角色变成2D，身份漂移，云台稳定，夸张的表演，戏剧性表情，过度表演，对着镜头做鬼脸，卡通反应，主题同步PA解说员对话，角色说着解说员台词，主题的嘴随着屏幕外的声音移动，主题对着镜头说话，屏幕上唇同步
```

`prompt_adherence: strict`与完整的`negative_prompt`锚定一起是承重——没有它们，Kling在片段中动画记分牌或“Kiss Cam”文本，主题会回归过度表演/唇同步离屏PA解说员。

**`prompt`** (逐字逐句，约2400字符——因为Kling提示长度限制为2500字符，所以保持预先修剪):

```
第一帧：在麦迪逊广场花园的Jumbotron亲吻摄像机片段的观众视角手机拍摄。粉丝拍摄的TikTok / Instagram亲吻摄像机片段风格。手持手机，不是专业广播。

摄像机：连续手持拍摄。轻微的微观晃动。在15秒内向亲吻摄像机面板缓慢平滑推进。

锁定：Jumbotron、记分牌（尼克斯57 / 第四节 4:32 / 公牛61）、红色亲吻摄像机边框、闪亮的心形图标、手写“Kiss Cam”脚本、AT&T品牌、黑暗赛场、前景粉丝剪影——所有内容都一致。

在亲吻摄像机框架内：
两个主题都是第一个参考静态图中的亲吻摄像机框架内显示的两个角色——在15秒内保留他们的确切外观和确切视觉风格。不要用不同的风格重新绘制任何主题。他们以微妙、克制、真实的生活动作在其原始风格内动画——小自然眨眼、轻柔呼吸、轻微头部转动、短暂微微笑。既不僵硬冻结，也不过度表演。表情水平是当真实的人被体育场摄像机意外捕捉时显示的水平。
背景中尼克斯球迷自然反应。

时间线（所有反应都保持微妙和人类规模）:
0-3s: 主题A注意到相机，小尴尬的微笑，看向主题B。主题B稍晚注意到，柔和的自然意识，开始微笑。背景粉丝轻轻反应。
3-7s: A和B交换一个短暂的热望眼神，分享一个安静的小笑声。脸部放松成自然的微笑。
7-11s: A和B leans in and share a gentle kiss on the lips — brief, sweet, natural, not staged. 群众轻声欢呼。

音频（非叙事性/仅离屏）——主题A和主题B始终保持沉默，嘴巴闭合，不要唇同步任何对话：
- 赛场环境音效贯穿始终。
- 离屏性别中性的PA解说员（不是任何可见主题——一个看不见的体育场声音），放大，略回声，俏皮。
  0-3s: "哦，在花园的亲吻摄像机——看看这个!"
  3-7s: "哈哈——看看他们是否接受!"
  7-11s: 群众爆发出“AWWWS”，欢呼，掌声逐渐增强。
  11-15s: PA笑着说：“今晚在花园有大事发生!”
- 手机麦克风比PA回声更响地捕捉到附近的球迷。
```

**为什么“在原始风格内微妙、克制、真实的生活动作”（而不是“仅微妙动作”，一个特定风格标签，或一个表情微反应列表）**:

- *第一次迭代*用“仅头部/眼睛轻微移动——保持像乙烯基玩具一样”约束风格化主题——看起来冻结并粘贴。
- *第二次迭代*命名特定风格（“皮克斯质量3D角色”），这迫使主题转向该外观，即使参考是不同的风格。
- *第三次迭代*说“自然地和生活化地表达”并带有加载的微反应列表（“眼睛变宽，嘴巴张开以示震惊，脸颊抬起时微笑，手放到脸上”）——主题然后过度表演，对着镜头做鬼脸，变得戏剧化。

工作框架保持风格保留锁定，但指定了在体育场摄像机意外捕捉到某人时的微妙、克制、真实的生活动作水平——与`negative_prompt`中的“夸张表演 / 戏剧性表情 / 过度表演 / 对着镜头做鬼脸 / 卡通反应”一起，以抑制回归到第三次迭代失败模式。

保存返回的视频URL为`state.kisscam_video_url`。如果生成异步完成，请遵循MCP工具返回的状态处理。客户端层超时会产生上游任务孤儿——没有恢复处理手柄。不要提交重复请求。向用户展示孤儿上游任务风险，然后在获得可恢复任务处理手柄或明确操作员确认之前等待任何重试。
