# App Store 屏幕设计

使用品牌加真实产品屏幕，在 iPhone 6.9 英寸尺寸（1290×2796）制作一个 5-6 屏幕的 App Store 活动。产品屏幕可以来自原始导出、Figma/源文件，或通过 Pika MCP 获取的公共 App Store 列表。以故事驱动、醒目的风格、严格遵循品牌规范。

这是与 `build-a-brand` 技能的姊妹技能——它消耗该技能的 `brand.md` 规范，但同样适用于用户提供的任何品牌规范。

## 成本透明度门禁

在执行任何付费 MCP 调用之前，调用一次 `identity_balance({verbose: true})`。显示当前余额、近期消耗率和剩余运行时间，然后使用以下确切消息门禁运行：

> 预计成本：使用 GPT-image-2、PNG 渲染、post-render analyze_media QA 和全分辨率单个 PNG QA 制作典型的 5-6 屏幕集，大约需要 150-300 信用点（约 1.50-$3.00）。这低于 $5，但回复 `proceed` 继续，或回复 `cancel` 取消。

在用户回复 `proceed` 之前，不要调用任何付费 MCP 工具。如果用户回复 `cancel`，则停止而不生成。对于非交互式 `--quick` 或 `--config` 调用者，要求在配置中设置 `cost_ack=proceed`；如果缺失，则用估计值而不是花费信用点。

## 交付成果

5 或 6 个 PNG，编号保存到 `~/Desktop/[app-name]-app-store-screens/`（或用户喜欢的任何位置）：

```
01_hook.png            ← 最大主张，作为搜索结果缩略图
02_value.png           ← 应用程序做得最好的那件事
03_feature_a.png       ← 具体功能
04_feature_b.png       ← 另一个具体功能
05_proof.png           ← 社会证明、奖项、“被喜爱”，差异化
06_close.png           ← 可选的第六屏——更近/CTA/品牌 flourish
```

以及一个预览图 `_preview.png`，一目了然地显示所有 6 个屏幕。

## 工作流程

### 第 0 步——输入和风格选择

如果使用空参数且没有可用的品牌/截图/演示上下文，则打印此菜单原文并停止。在需要输入存在之前，不要生成图像或渲染 HTML。

> **我应该制作什么样的 App Store 截图集？** 必须提供：
>
> - **品牌规范** — `brand.md` 或包含名称、调色板、字体、声音和图像方向的等效品牌笔记；或 App Store URL/应用名称，如果您希望我首先获取列表并草拟品牌阅读
> - **原始产品截图** — 导出的 PNG、可以导出它们的 Figma/源文件、截图文件夹，或 App Store URL/应用名称，我可以使用 Pika MCP 获取
> - **或者一个虚构应用演示简报** — 仅用于发布演示/概念，其中没有真实产品存在；说 `demo_mode: true` 并提供虚拟应用做什么
>
> 可选：参考 App Store 截图、情绪板、首选屏幕数量（5 或 6）、输出文件夹。

在交互模式下，如果用户提供了部分输入，则仅询问缺失的必要项目并停止。如果适用非交互式快速通道，请使用步骤 0.5 代替。必要输入：
- `brand.md` 或包含名称、调色板、字体、声音和图像方向的等效品牌规范；如果用户给出 App Store URL 并要求您“帮助创建它”，请首先获取列表，并从列表/图标/截图草拟推断品牌规范以供批准
- 一个产品源：原始产品截图、可以导出它们的 Figma/源文件，或可以通过 Pika MCP 获取的 App Store URL/应用名称
- 仅对于虚构发布演示，`demo_mode: true` 与 `demo_brief` 是真实产品截图的替代方案；使用下面的虚构应用演示模式路径
- 可选参考截图或情绪板，如果他们想要特定的 App Store 风格

### 第 0.5 步——非交互式快速通道

当调用者传递 `--quick` 或 `--config <path>`，或者调用者声明他们正在从 CI、子代理、批处理作业或任何其他非交互式外壳运行时，使用此路径。

此部分优先于以下交互式询问/等待指令。当适用时，使用此快速通道，并且不要落入多轮输入，除非所需的品牌和产品截图或明确的演示模式输入确实不可用。

- `--config <path>` 指向一个包含预定义选择的 JSON 文件：`brand_spec`、`product_screenshots`、`app_store_url`、`website_url`、`reference`、`style`、`screen_count`、`narrative_arc`、`demo_mode`、`demo_brief` 和 `output_folder`。
- `--quick` 意味着选择默认样式，除非提供了参考，否则从提供的品牌规范或 App Store 列表推断品牌阅读，自己草拟 5-6 屏幕弧线，然后继续。
- 对于 `--quick` 或 `--config`，不要在风格选择、品牌阅读回放、参考规则回放或 5-6 屏幕策略提案时停止确认。记录假设并继续设计/渲染。
- 如果既没有真实产品截图，也没有明确的 `demo_mode: true` 与 `demo_brief`，则停止，并使用紧凑的缺失字段列表而不是开始多轮 Q&A 循环。

#### 虚构应用演示模式

仅当调用者明确说明这是虚构应用、假应用、发布演示、概念演示或通过配置传递 `demo_mode: true` 时，才使用此模式。不要对真实产品使用演示模式。

演示模式允许在没有真实产品截图的情况下创建符合品牌声音的代表性 UI 模拟，但输出必须标记为仅限演示的概念作品，而不是生产资源。将编造的屏幕视为故事化的 QRT/演示工件，而不是 App Store Connect 准备好的真实产品的证据。

- 需要一个 `demo_brief` 或足够的用户提供的虚拟产品概念细节来定义应用的核心工作、受众、3-5 个功能以及证明/CTA 角度。
- 生成与该简报内部一致的 UI 状态；不要暗示真实客户、真实评论、真实指标或真实集成，除非提示明确提供了它们。
- 在交付说明和联系表标签中添加演示仅披露：“演示 UI 概念——不是生产资源，也不是真实产品截图。”

在非交互模式下，只有在配置设置 `demo_mode: true` 并提供 `demo_brief` 时才继续；否则，停止并提供紧凑的缺失字段列表。

在交互模式下，当必要输入存在时，以简短的议程开头，并直接询问一个风格问题。这是了解用户是否想要默认样式或特定参考的最便宜的时刻。在非交互式快速通道中，除非提供 `reference` 或 `style`，否则选择默认样式，记录假设并继续。

```
这是如何工作的：
1. **阅读你的品牌 + 截图** — 我吸收品牌声音、调色板、类型，并弄清楚应用实际上做什么
2. **策略** — 我提出一个 5-6 屏幕的叙事弧线（钩子→价值→功能→证明→结束），并为每个屏幕提供标题，在任何设计之前
3. **设计 + 生成** — 我设计每个布局，在 1290×2796 中合成
4. **预览** — 我交付 PNG + 联系表，以便您能够一次性查看整个活动

在开始之前的一个快速问题——**您想要默认样式，还是特定的样式？**

- **默认** — 干净、克制，屏幕显示未受影响。全帧设备，标题 + 副标题在上方，实心品牌颜色背景，品牌声音文本。编码在 `references/default-layout.md` 中。这是我能很好地交付的内容。
- **特定的样式** — 分享一个清晰的参考：您喜爱的 App Store 页面的截图（Notion、Calm、Things、Headspace，任何东西），一个 figma 文件，一个情绪板图像。我会研究它，提取布局规则（设备大小 + 位置，标题处理，背景，任何品牌特有的装饰），在我设计之前回放我所阅读的内容，然后构建活动——**使用您的品牌调色板、字体、声音和摄影风格**。所以如果参考使用的是肩部照片，我会使用您的品牌摄影风格生成一个肩部照片 (`gpt-image-2` 接受参考作为样式输入)。参考决定布局；您的品牌决定外观。

如果您不告诉我，我会选择默认的。

> **为什么没有“jazzed up”自动模式。** 做出丰富的/多样的/戏剧性的布局需要视觉判断调用（透视、层叠、排版层次结构、色彩平衡），这些没有程序化答案。当用户想要丰富性而没有参考时，我的近似值往往看起来很业余。要求提供具体的参考，让我提取具体的规则来复制，而不是自由发明——用户有办法验证我是否 aiming at the right thing.

基于答案的两个下游路径：
- **默认** → 严格按照 `references/default-layout.md` 的端到端。每个屏幕使用相同的布局骨架；颜色 + 内容的差异提供多样性。这会产生一致的品牌纪律性工作。
- **复制参考** → 研究参考，提取规则，将用户的品牌输入其中。有关完整过程的“参考驱动路径”请参阅下方。

如果用户无法或不愿提供参考，但仍然想要比默认更多，请温和地提出反馈——解释如果没有参考，您将交付默认的加上他们的品牌颜色，这比猜测“刺激”更好。不要在运行时发明“jazzed”样式。

### 第 1 步——阅读品牌和产品

#### App Store 列表路径

如果用户提供 `apps.apple.com` URL、数字 App Store 应用 ID 或应用名称搜索词作为产品源，首先尝试 Pika MCP `fetch_appstore_screens`，因为它更快、更稳定，并返回托管截图/图标资源，准备好用于后续渲染步骤：

```
fetch_appstore_screens(
  query: <app_store_url | numeric_app_id | search_term>,
  country: "us",
  max_screens: 10,
  include_icon: true
)
```

使用返回的 `metadata`、`icon` 和 `screenshots` 作为产品源。返回的截图 `url` 值已经是 Pika 托管的 HTTPS 资源，可以直接在后续的 `html_to_png` 阶段使用。

如果用户提供了一个特定国家/地区的 App Store URL，则尽可能保留调用工具时的商店国家。如果国家不明确，则默认为 `"us"`，除非用户要求另一个商店。

如果 MCP 工具不可用、未经身份验证或返回没有截图，说明发生了什么，然后使用最不脆弱的回退可用：其他读取/获取工具、官方 App Store/iTunes 元数据端点或用户提供的截图。保持回退基于真实的列表资源；不要编造产品 UI。

#### 源截图准备

在选择默认手机布局之前，对每个获取或用户提供的源截图进行分类，并记录您将使用的 `source_treatment`：

- `clean_ui_capture` - 原生应用 UI 适合设备模拟。
- `composed_marketing` - 完成的 App Store 营销屏幕，不是干净的内置截图。
- `legacy_footer_cleanup` - 干净的 UI，只需要在列表品牌页脚或水印清理后才能嵌入设备。

一个 `composed_marketing` 源是一个预先组合的营销屏幕。常见信号：已经放置在手机上方的标题或副标题，手机边缘出血或裁剪，背景已经是活动艺术，源图像已经是完成好的 1290x2796 App Store 屏幕，而不是干净的 产品 UI。2025 年 Notion 列表使用此模式。

当源是 `composed_marketing` 时，不要将其重新框定在另一个设备模拟中，不要在预制的标题上添加、写入或生成第二个标题/副标题。优先选择 `clean_ui_capture`：在产品网站、引导或网络应用上使用 `capture_website`，当存在可捕获的真实 UI 表面时，或要求模拟器/Figma/原始 UI 导出。如果没有任何干净的 UI 表面可用，则使用 `source_treatment=composed_passthrough`：将组合源原样呈现为屏幕/背景，仅进行最小的交付框架、编号或联系表标签。不要依赖裁剪底部 6-8% 来修复组合源；这将移除错误区域，并保留双标题失败。

对于遗留源截图，检查它们是否有页脚水印出血或列表品牌页脚，这些将在生成的活动中造成杂乱。R4 Notion 列表将其暴露为原始页脚，阅读 `NOTION · NOTES, TASKS, AI` 重叠底部内容。如果获取或用户提供的干净 UI 源截图具有这种类型的水印，则在嵌入之前裁剪或遮罩底部 6-8%。不要将原始截图直接放置在设备中。

在 HTML 阶段使用准备好的截图包装器，并将顶部源锚定。包装器必须定义自己的几何形状；不要依赖 `height:100%`，除非每个父级直到设备都有明确的高度。

```html
<div class="source-screen-crop source-screen-crop--phone" style="
  width:100%;
  aspect-ratio:1290 / 2796;
  overflow:hidden;
  position:relative;
">
  <img src="s://screen01" style="
    width:100%;
    height:calc(100% / 0.92);   /* 显示顶部 92% 的内容，裁剪底部 8% */
    object-fit:cover;
    object-position:top center;
    display:block;
">
</div>
```

如果 8% 的裁剪会移除真实产品 UI，请使用品牌颜色渐变覆盖底部页脚，但仍然在截图进入最终设备模拟之前移除水印出血。

#### 处理 Mac-app 或混合-app 截图

`fetch_appstore_screens` 可能返回横向 Mac 截图（例如 1290×806），而不是 iPhone 竖向截图（1290×2796）对于 Mac 独占或混合 iOS/Mac 应用，例如 Things 3、Drafts、Numbers、Day One、OmniFocus 或 BBEdit。在选择默认 iPhone 竖向布局之前检测到此：

定向规则是 `aspect_ratio_w > aspect_ratio_h`，或者当只有像素维度存在时，是 `width > height`。

```
mac_shots = [s for s in screenshots if s.aspect_ratio_w > s.aspect_ratio_h]
# 当明确的长宽比不存在时，等效于此：
mac_shots = [s for s in screenshots if s.width > s.height]
```

如果 `mac_shots` 非空，则使用嵌入卡片布局 `references/mac-app-layout.md` 而不是全帧设备快照。对于 Mac 独占或混合应用，将每个横向截图嵌入到 1290×2796 竖向画布内的圆角 UI 卡片中，而不是将其裁剪到 iPhone 框架中，不进行信箱处理，或将其视为全帧设备。Things 3 的 round-2 基准验证了这种方法：Mac 截图保持可读性，而竖向活动仍然适合 App Store Connect。

源截图准备仍然适用于 Mac 卡：在嵌入横向截图之前，检查它们是否有列表品牌页脚或页脚水印出血。不要在 Mac UI 上使用手机竖向裁剪。使用专用的卡片包装器（例如 `source-screen-crop--mac`）保留横向长宽比；如果需要清理，请优先使用窄底掩码/渐变或卡片内的小横向保留底裁剪。

#### App Store 列表过薄门禁

在 `fetch_appstore_screens` 之后，计算显示真实产品 UI 的可用截图数量。如果列表返回少于 3 个可用截图，则将其视为过薄的 App Store 列表。

- 不要通过幻觉 UI 创建 5-6 屏幕活动。真实产品 UI 是设备框架的默认要求。
- 交互模式：在策略之前停止，并提供两个选择：
  1. **网站捕获路径** — 使用 `capture_website` 或提供的网站/引导 URL 捕获真实产品表面，然后继续使用这些捕获作为产品截图。
  2. **真实截图路径** — 在继续之前，要求模拟器导出、Figma 框架或其他产品 UI 捕获。
  不要提供合成的设备 UI 用于真实产品。如果用户明确转向虚构发布/概念演示，则路由到 Fictional app demo mode 并要求 `demo_mode: true` 与 `demo_brief`。

在获取后，仅从列表和视觉效果中推断草稿品牌阅读：应用名称、类别、可见调色板、可能的类型方向、从副标题/描述中提取的声音，以及值得注意的 UI 瞬间。在交互模式下，将其作为临时的品牌规范阅读，并要求用户更正之前，然后提出 5-6 屏幕弧线。在非交互式快速通道中，将其作为临时品牌规范记录，并继续。

#### 参考驱动路径：如何将用户的品牌应用于参考的风格

参考描述了布局/样式的样子。品牌描述了要使用的颜色/字体/声音/摄影。该技能的工作是将参考的视觉结构复制，但使用用户的品牌进行渲染：从参考中提取两个东西，从品牌中提取两个东西：

**从参考中提取结构规则：**
- 设备大小（作为画布的百分比）和倾斜角度
- 标题处理（大小、位置、颜色逻辑——关键字上使用强调？着色背景药丸？）
- 背景处理（实色、照片、渐变、抽象元素）
- 英雄图像模式（手持手机、肩部拍摄、真实主题突破手机、3D 对象漂浮等）
- 调用/拉出模式（带箭头的对话气泡、浮动卡片、宝丽来框架等）
- 重复规则：每个屏幕使用相同的布局，还是每个插槽都不同？

**从品牌中应用具体内容：**
- 调色板（将参考中使用的实色块替换为品牌颜色）
- 字体（将参考中使用的类型替换为品牌显示 + 正文字体）
- 声音（用品牌声音重写所有标题/副标题——不要复制参考的单词）
- 摄影方向（任何生成的图像都遵循品牌的摄影规则——对于 DeltaStream，那是纪录片 35mm，黄金时刻，真实公寓，每个画面都有黄油色调，真实演员多样性）
- 氛围（温暖与临床，俏皮与专家，等）

**对于生成的英雄图像：** 通过 `generate_image_edit` 将参考作为 `images` 传递给 `gpt-image-2`。该工具支持最多 16 个参考图像。当参考使用独特的照片构图（手持手机，肩部拍摄，人物突破屏幕，3D 角色出现）时使用此功能。与品牌的摄影规则结合使用：

```
Reference: [用户的参考照片——例如，昆虫应用的手持手机与蝴蝶]

提示：在参考图像的完全构图和照明风格中——手持手机以相同的角度和比例——但根据 [BRAND] 摄影规则渲染主题和场景：纪录片 35mm，黄金时刻的窗户光，真实公寓，黄油色调的陶瓷杯可见，中位数混合种族演员，35mm 电影颗粒。垂直 9:16 竖向肖像。
```

这是如何在没有复制参考内容的情况下获得参考样式的样子。手持+手机构图转移；照明/演员/设置来自品牌。

**在交互模式下，在设计中提出提取的规则。** 写出简短的要点列表（“设备 75% 画布倾斜 -8°，标题在黄色药丸上方的设备上方，肩部拍摄英雄，墨水调用与弯曲箭头”）并确认用户是否正确阅读了参考。在非交互式快速通道中，记录提取的规则并继续。然后应用这些规则一致地构建所有 6 个屏幕。不要在活动过程中偏离。

然后实际阅读：

- **`brand.md`** — 提取：品牌名称、标语、调色板（带有十六进制），显示字体 + 正文字体，声音形容词，声音示例，禁止词，摄影/插图方向，情绪词。如果文件是不同的格式（PDF，纯文本笔记），解析其中内容，并在交互模式下询问缺失的任何差距。在非交互式快速通道中，记录合理的假设以填补非关键差距——不要编造品牌。
- **产品截图** — 打开每个截图，形成一个诚实的心理模型：*这个应用实际上做什么？* 注意核心 UI 模式（信息流，聊天，画布，列表，地图，等），主要操作表面，以及任何“哇时刻”屏幕（生成结果，美丽状态，独特交互）。
- 如果你可以使用 `analyze_media` 在不加载它们为图像的情况下检查截图，请这样做——它对于快速扫描更快。

**然后阅读你所发现的**（3-5 行，对话式）：

```
ok — 阅读中 [brand name]: [tagline]. 调色板: [颜色]. 声音: [形容词]. 应用看起来像 [X] — 我看到 [特定 UI 提示 1] 和 [特定 UI 提示 2]. 最突出的屏幕是 [screen N]，因为 [原因]. 正确我哪里错了，否则我会提出 6 屏幕弧线。

交互模式：等待确认后再提出策略。便宜地捕获误读。

非交互式快速通道：将品牌阅读视为临时性的，记录假设并继续到策略。

### 第 2 步——提出 6 屏幕策略

在设计任何东西之前，将叙事弧线作为纯文本写出来。每个屏幕都需要：

- **角色**（钩子 / 价值 / 功能 / 证明 / 结束）
- **标题**（5-8 个字，用品牌声音——见“副本”部分）
- **可选副标题**（一行短）
- **布局原型**（见下文——不要画它）——名称它，不要画它
- **它所使用的原始截图**（文件名）——或“无，全出血排版”
- **证明屏幕仅限证明工件**——至少一个可见的证明工件，例如星级行、编辑推荐徽章、评论卡、评论计数芯片、奖项徽章或源引用卡。证明屏幕不得仅包含文本。
