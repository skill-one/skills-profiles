# 文档编写技巧

@./../_shared/metabase-style-guide.md

## 编写文档时

### 从这里开始

1. **这是为谁准备的？** 根据受众调整复杂度。不要过度简化困难的事情，也不要过度复杂简单的事情。
2. **他们需要什么？** 快速引导他们找到答案。没有人想在文档中停留比必要更长的时间。
3. **你遇到了什么困难？** 学习时遇到的那些常见问题？回答它们（不要字面包括问题）。

### 编写流程

**草稿：**

- 像告诉同事一样写出步骤/解释
- 先说明要做什么，再解释为什么
- 使用陈述观点的标题："在添加用户前设置 SAML" 而不是 "SAML 配置时机"

**编辑：**

- 大声朗读。听起来像你在说话吗？如果太正式，请简化。
- 删除任何不能直接帮助读者的内容
- 检查每个段落有一个明确的目的
- 验证示例确实可以工作（不要给出会报错的示例）

**润色：**

- 使链接具有描述性（永远不要用"这里"）
- 反引号仅用于代码/变量，**粗体**用于 UI 元素
- 美式拼写，序列逗号
- 保持图像最小化，范围紧密

**格式：**

- 编辑后对文件运行 prettier：`bun run prettier --write <file-path>`
- 这确保了所有文档的格式一致

### 常见模式

**说明：**

```markdown
运行：
\`\`\`
command-to-run
\`\`\`

然后：
\`\`\`
next-command
\`\`\`

这确保你得到最新的更改。
```

不是："(记得在 X 之前运行 Y...)" 埋在段落中。

**标题：**

- "使用环境变量进行配置" ✅
- "环境变量" ❌（太模糊）
- "如何使用环境变量进行配置" ❌（太啰嗦）

**链接：**

- "查看 [SAML 文档](link)" ✅
- "在 [这里](link) 阅读文档" ❌

### 注意事项

- 将任务描述为"简单"（你不知道读者的背景）
- 讨论 Metabase 功能时使用"我们"（使用"Metabase"或"它"）
- 正式语言："utilize"、"reference"、"offerings"
- 太有活力：多个感叹号
- 将行动淹没在解释中
- 无法工作的代码示例
- 将会过时的数字

### 快速参考

| 应该这样写                 | 不应该这样写           |
| -------------------------- | ------------------ |
| people, companies          | users              |
| summarize                  | aggregate          |
| take a look at             | reference          |
| can't, don't               | cannot, do not     |
| **Filter** 按钮          | \`Filter\` 按钮  |
| 查看 [文档](link)         | 点击 [这里](link) |
