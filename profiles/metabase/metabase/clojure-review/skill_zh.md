## 审查指南

**需要指出的问题：**

- 检查是否符合 Metabase Clojure 风格指南（见上文）
- 如果工作目录中存在 `CLOJURE_STYLE_GUIDE.adoc`，也需检查是否符合社区 Clojure 风格指南
- 指出所有风格指南违规问题

**不要发布的内容：**

- 不要发布祝贺他人进行琐碎更改或遵循风格指南的评论
- 不要发布确认“看起来不错”或告诉他们做得正确的评论
- 只发布关于风格违规或潜在问题的评论

避免使用的示例不良代码审查评论：

> 此 TODO 注释格式正确，包含作者和日期 - 做得不错！

> 向查询添加 limit 1 - 这使测试更高效而不改变其行为。

> kondo 忽略注释放置在此处是恰当的

> 测试名称按风格指南要求以 -test 结尾。

**特殊情况：**

- 不要发布关于缺少括号的评论（这些问题将由代码检查器捕获）

## 快速审查清单

使用此清单高效扫描更改：

### 命名

- [ ] 描述性名称（不要使用 `tbl`、`zs'`）
- [ ] 纯函数以描述其返回值的名词命名
- [ ] 变量和函数使用 `kebab-case`
- [ ] 产生副作用的函数以 `!` 结尾
- [ ] 函数名中不要重复命名空间别名

### 文档

- [ ] 位于 `src` 或 `enterprise/backend/src` 的公共变量具有有用的文档字符串
- [ ] 文档字符串使用 Markdown 语法
- [ ] 引用使用 `[[其他变量]]` 而不是反引号
- [ ] TODO 注释包含作者和日期：`;; TODO (姓名 2025-01-01) -- 描述`

文档字符串内容 — 对照风格指南中反模式表检查所有新编写的或重写的文档字符串。单独阅读 diff 的文档字符串，与代码分开：散文是审查注意力滑落的地方，长文档字符串看起来是勤奋而不是通常的负债。

### 代码组织

- [ ] 除非在其他地方使用，否则所有 `^:private`
- [ ] 避免使用 `declare`（公共函数靠近末尾）
- [ ] 尽可能将函数限制在 20 行以内
- [ ] 定义形式中不要有空白、非注释行（`let`/`cond` 中的成对结构除外）
- [ ] 行长度 ≤ 120 个字符

### 测试

- [ ] 为不同的测试用例使用单独的 `deftest` 形式
- [ ] 纯测试标记为 `^:parallel`
- [ ] 测试名称以 `-test` 或 `-test-<数字>` 结尾

### 模块

- [ ] 正确的模块模式（OSS：`metabase.<模块>.*`，EE：`metabase-enterprise.<模块>.*`）
- [ ] API 端点位于 `<模块>.api` 命名空间
- [ ] 公共 API 位于 `<模块>.core` 并使用 Potemkin
- [ ] 不要使用 `:clj-kondo/ignore [:metabase/modules]` 欺骗模块检查器

### REST API

- [ ] 存在响应模式（`:- <模式>`）
- [ ] 查询参数使用 `kebab-case`，请求体使用 `snake_case`
- [ ] 路由使用单数名词（例如，`/api/dashboard/:id`）
- [ ] `GET` 没有副作用（除分析外）
- [ ] Malli 模式详细完整
- [ ] 所有新端点都有测试

### MBQL

- [ ] 在 `lib`、`lib-be` 或 `query-processor` 模块之外不要进行原始 MBQL 操作
- [ ] 使用库和 MBQL 5，而不是遗留 MBQL

### 数据库

- [ ] 模型和表名是单数名词
- [ ] 使用 `t2/select-one-fn` 而不是选择整行以获取单列
- [ ] 逻辑在 Toucan 方法中，而不是在辅助函数中

### 驱动程序

- [ ] 新的多方法在 `docs/developers-guide/driver-changelog.md` 中记录
- [ ] 将 `driver` 参数传递给其他驱动程序方法（不要硬编码驱动程序名称）
- [ ] `read-column-thunk` 中的逻辑最小化

### 其他

- [ ] 可能时示例数据以鸟类为主题
- [ ] Kondo 代码检查器抑制使用正确格式（不要 `#_:clj-kondo/ignore` 关键字形式）

## 模式匹配表

快速扫描常见问题：

| 模式                                      | 问题                                                       |
| -------------------------------------------- | ----------------------------------------------------------- |
| `calculate-age`、`get-user`                  | 纯函数应以描述其返回值的名词命名：`age`、`user`               |
| `update-db`、`save-model`                    | 缺少 `!` 表示副作用：`update-db!`、`save-model!`             |
| `snake_case_var`                             | 应使用 `kebab-case`                                       |
| 没有文档字符串的公共变量                   | 添加文档字符串解释其用途                                    |
| `;; TODO 修复这个问题`                       | 缺少作者/日期：`;; TODO (姓名 2025-01-01) -- 描述`            |
| `(defn foo ...)` 在其他命名空间中使用        | 应为 `(defn ^:private foo ...)`                            |
| 函数 > 20 行                              | 考虑拆分为更小的函数                                      |
| `/api/dashboards/:id`                        | 使用单数：`/api/dashboard/:id`                            |
| 查询参数使用 `snake_case`                   | 查询参数应使用 `kebab-case`                                |
| 没有测试的新 API 端点                   | 为端点添加测试                                          |

## 反馈格式示例

**对于风格违规：**

> 此纯函数应以描述其返回值的名词命名。考虑使用 `user` 而不是 `get-user`。

**对于缺少文档：**

> 此公共变量需要一个文档字符串来解释其用途、输入和输出。

**对于不属于其所有者的代码文档：**

> 这描述了 `lib` 如何决定内部分桶策略。如果这些改变，这里不会出错，但会无声过时 — 删除它，让 `available-binning-strategies` 解释自己的行为。

**对于属于代码主体内容的文档字符串：**

> 这段解释了分支这样排序的原因，这是编辑 `cond` 时需要的信息 — 但调用者无法利用它。将其移到 `cond` 上方的行内注释。

**对于组织问题：**

> 此函数仅在此命名空间中使用，因此应标记为 `^:private`。

**对于 API 规范：**

> 查询参数应使用 `kebab-case`。将 `user_id` 改为 `user-id`。
