# 文档评审技能

@./../_shared/metabase-style-guide.md

## 评审模式检测

**重要提示：开始评审前，请确定使用哪种模式：**

1. **PR评审模式**：如果`mcp__github__create_pending_pull_request_review`工具可用，您正在评审GitHub的PR
   - 使用待处理评审工作流将所有问题作为一个整体进行评审
   - 遵循以下"PR评审模式格式"中的工作流步骤

2. **本地评审模式**：如果MCP工具不可用，在对话中输出问题
   - 按编号Markdown列表格式化所有问题（如"反馈格式"中所述）

## 评审流程

1. **检测评审模式** - 检查`mcp__github__create_pending_pull_request_review`是否可用
2. 通读一次变更以理解意图
3. 检查所有违反风格指南或显著影响可读性的问题
4. 仅标记值得提及的问题 - 如果不会对读者产生实质性影响，则跳过
5. **必须：所有反馈按顺序编号** - 从问题1开始，为每个发现的问题递增编号

## 评审清单

通读diff查找以下问题：

**语气和语调：**

- [ ] 正式/企业用语（如"utilize"而非"use"、"offerings"等）
- [ ] 使用"users"而非"people"或"companies"
- [ ] 过多的感叹号或过于轻快的语气
- [ ] 告诉读者某事很酷，而不是展示给他们看

**结构和清晰度：**

- [ ] 重要信息隐藏而非突出
- [ ] 重复冗长的文本几乎没有价值
- [ ] 没有明确目的的段落
- [ ] 含糊不清的标题无法传达要点
- [ ] 指令在说明"做什么"之前先解释"为什么"
- [ ] 将任务描述为"简单"或"容易"

**链接和引用：**

- [ ] 使用"here"链接而非描述性文本
- [ ] 标题中的链接（除非整个标题是链接）

**格式：**

- [ ] 使用"and"替代&（专有名词除外）
- [ ] 列表格式不一致

**代码和示例：**

- [ ] 无法工作或会产生错误的代码示例
- [ ] 命令未按执行顺序排列
- [ ] 全屏截图而非范围UI元素
- [ ] 过多或不必要的图片

**句子结构：**

- [ ] 在引入新术语时过度使用代词

## 快速扫描表

| 模式                       | 问题                                         |
| ----------------------------- | --------------------------------------------- |
| we can do X, our feature      | 应为"Metabase"或"it"                  |
| click here, read more here    | 需要描述性链接文本                    |
| easy, simple, just            | 移除居高临下的限定词               |
| users                         | 如有可能，应使用"people"或"companies" |

## 反馈格式

**强制性要求：每个问题必须从问题1开始按顺序编号。**

这种编号格式是不可协商的。它允许用户有效地引用特定问题（例如，"修复问题1、3和5"）并跟踪哪些反馈已被处理。

### 本地评审模式格式

在对话中输出问题（本地模式）时，使用此格式：

```markdown
## 问题

**问题1：[简要标题]**
行X：问题的简短描述
[代码或示例]
建议的修复或简短说明

**问题2：[简要标题]**
行Y：问题的描述
建议的修复或说明

**问题3：[简要标题]**
...
```

**示例：**

> **问题1：正式语气**
> 行15：这可以更口语化。考虑："你不能..."而非"你不能..."

> **问题2：模糊标题**
> 行8：标题可以更具体。直接陈述要点："升级前运行迁移"而非"升级过程"

### PR评审模式格式

向GitHub发布时（PR模式），使用**待处理评审工作流**：

**工作流步骤：**

1. **开始评审**：使用`mcp__github__create_pending_pull_request_review`开始待处理评审
   - 这会创建一个草稿评审，直到提交才可见

2. **获取diff信息**：使用`mcp__github__get_pull_request_diff`了解代码变更和行号
   - 这有助于您确定正确的文件路径和行号以进行评论

3. **识别所有问题**：通读所有变更并识别每个值得提及的问题
   - 在发布任何评论之前收集所有问题
   - 按顺序编号（问题1、问题2、问题3等）

4. **添加评审评论**：使用`mcp__github__add_pull_request_review_comment_to_pending_review`为每个问题添加评论
   - **关键**：使用多个工具调用并行发布所有评论
   - 每条评论应引用diff中的特定文件路径和行号
   - 每条评论正文应以`**问题N：[简要标题]**`开头
   - 包括描述和建议的修复

5. **提交评审**：使用`mcp__github__submit_pending_pull_request_review`一次性发布所有评论
   - 使用事件类型`"COMMENT"`（非"REQUEST_CHANGES"）使其非阻塞
   - **不要包含正文消息** - 留空正文或完全省略
   - 所有评论将作为一个整体评审一起显示

**评论格式示例：**

```
**问题1：正式语气**

这可以更口语化。考虑："你不能..."而非"你不能..."
```

**重要提示**：
- 每个问题都应附有一个待处理评审的评审评论
- 按顺序编号所有评论（问题1、问题2、问题3等）
- 始终以`**问题N：[简要标题]**`开头评论正文
- **必须并行添加所有评论在一个响应中** - 不要在单独的响应中逐一添加
- 不要向对话输出摘要消息 - 仅发布GitHub评审评论
- 提交评审时，不要包含正文参数（或留空）以避免在PR中混入摘要文本
- 提交后，评审将作为一个包含多个评论的整体显示

## 最终检查

1. 从您的评估中移除任何在解决后不会对读者产生实质性影响的问题。仅标记值得作者花时间修复的问题。
2. **验证所有问题是否按顺序编号**，从问题1开始，编号无遗漏。
3. 确认格式完全匹配：`**问题N：[简要标题]**`，其中N是问题编号。
4. **在PR模式下**：验证每个问题是否作为单独的GitHub评论发布（而非输出到对话）。
