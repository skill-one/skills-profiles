# /layers-orient

*假设 `/layers-intro` 已加载以提供框架上下文。*

Orient 是一种快速诊断工具，是其他技能进行工作的入口，用于发现**当前的决策**。它映射了所有七个层级的决策现状，识别瓶颈——即存在未解决或存在风险的最低层级——并建议下一步应关注何处。

它不是对任何层级的深入分析。那是各个层级技能的作用。Orient 回答了之前的问题：*哪个层级最需要紧急关注？* 保持其快速和简洁——输出是一个简短的审计和一个建议，而不是一份报告。

**它评估的内容：**
- 每个层级的关键决策是否已做出，以及其稳固程度
- 被视为稳固的决策是否实际上是假设
- 哪个层级存在未解决的工作，为上层级创造风险

**质量信号——当 Orient 运用得当时：**
- 明确指出瓶颈层级，而不是模糊地暗示
- 将假设层级与稳固层级区分开来——它们需要不同的回应
- 建议与特定技能相关联，并说明理由

---

## 引导式会话

*描述你的设计情况以及是什么促使你选择使用它，或者说“让我们开始 Orient”来启动。*

（记录是可选的且轻量级的——参见 `/layers-intro`。对于 Orient，通常只需要保留审计表本身。）

然后询问：
1. 你正在处理哪个产品或功能？
2. 你现在面临什么设计挑战？
3. 这项工作进展到什么程度——早期探索、积极设计，还是修复现有产品中的问题？

倾听关于哪些层级已经处理过，哪些层级薄弱或缺失的线索。

---

### 层级审计

针对每个层级提出一个或两个有针对性的问题。将每个层级评为：
**稳固** / **部分** / **假设** / **薄弱** / **未开始** / **不适用**

**观察到的行为**
*"你有什么用户研究？是否与用户交流过、观察过，或者有分析数据？还是这主要基于团队认为用户会做什么？)*

**领域**
*"你对该产品运营的空间有多了解——现实世界的概念、术语，以及你的产品进入画面之前用户如何思考？)*

**用户需求**
*"你能说明用户试图实现的目标是什么——不是功能，而是底层工作和为什么它很重要？你有工作故事或类似内容吗？)*

**产品与服务策略**
*"你知道这项工作针对的具体用户需求以及它旨在实现什么业务成果吗？机会与业务目标之间的联系是明确的，还是非正式的？)*

**概念模型**
*"产品是否有关于其处理的对象的清晰模型——这些对象的存在方式、如何连接以及你使用的词汇？这是否在团队中共享，还是每个人有自己的版本？)*

**交互结构与流程**
*"你是否对关键用户旅程有清晰的了解——地点、步骤、决策点？有原型、粗略流程、可运行的代码或可以叙述的描述吗？)*

**界面**
*"是否存在需要融入其中的现有设计系统、视觉语言或组件库？)*

### 瓶颈分析

识别**瓶颈层级**：存在薄弱、假设或未开始状态的最低层级。明确说明：缺失了哪些决策，以及这对上层级创造了什么风险？

同时标记**假设层级**——被视为已决定但未验证的层级。看似稳固的假设往往是隐藏最危险决策的地方。

如果设计师有截止日期或约束条件会改变计算结果，请承认这一点。有时正确的做法不是最基础的那一个——明确说明这种权衡，而不是忽视它。

### 建议

建议运行下一个特定技能，并说明原因：

- 概念模型 → `/layers-conceptual-model`
- 产品策略 → `/layers-product-strategy`
- 用户需求 → `/layers-user-needs`
- 领域 → `/layers-domain`
- 交互结构 → `/layers-interaction-flow`
- 观察到的行为 → `/layers-observed-behaviour`

结束于：*"现在想运行 [技能]，还是先对这幅图中的某些内容提出异议？"*
