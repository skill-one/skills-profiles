# /layers-conceptual-model

*假设已加载 `/layers-intro`。这项技能是一个技术库，而非脚本——参见那里的“如何使用这些技能”。*

概念模型是最常被忽视的承重层。它定义了产品识别的对象、它们之间的关系、它们可以处于的状态，以及所有这些的词汇——这是一个关于产品如何对其领域进行建模的刻意决策，独立于任何界面。

它**不是**用户的混乱心智模型（那是领域层），也**不是**数据库模式、线框图或流程图。但这个模型与工程师构建的内容之间的差距很重要：一个巨大且未经审视的差距既是用户体验债务（用户遇到与模型相矛盾的产品），也是技术债务（系统难以演进）。

---

## 该层做出的决策

- 产品识别的对象是什么，以及每个对象的边界在哪里
- 这些对象如何关联——基数性，以及一个对象扮演多个命名角色的情况
- 用户可以对每个对象做什么或与它做什么
- 对象可以处于什么状态，以及哪些转换是重要的
- 产品的词汇——每个概念一个名称，每个名称一个概念

如果这些决策中没有任何一个是真正开放的，你可能现在就不需要这个层了。与其为了形式而工作，不如这样说。

---

## 纪律——使模型保持诚实的要素

按任何顺序应用于你生产的任何内容。它们是这个层的高价值部分。

- **仅限真实对象。** 真正的对象是 *可实例化的*（可以有多个）、*结构化的*（有自己的属性），并且 *有用的*（用户关心它本身）。这能捕捉到两种错误：属性被提升为对象，以及——更常见的是——**实例被误认为对象**： "CAC" 和 "ROAS" 不是对象，它们是对象 **Metric** 的实例。当多个名词属于同一类时，将类型建模为对象；具体的名称是实例或值。
- **属性实际上是关系。** 如果一个属性只是模型中另一个对象的名称或 ID，将其建模为关系——不要重复它。
- **当一个对象扮演多个角色时命名其角色。** "属于一个 User（作为 referrer）"，而不是 "属于一个 User"。
- **不要有推测性的添加。** 每个对象、属性、操作和关系都应该追溯到一个明确说明的用户需求。这里的范围蔓延会通过每一层传递。 （追溯到 *策略词汇* 不算——策略词汇还不是对象。）
- **可成为对象 ≠ 应该是首要的。** "真实对象仅限" 测试告诉你某物 *可以* 成为对象——并不意味着产品应该承诺将其作为首要的、持久的、有状态实体。这种提升是一个有成本的设计赌注。通过具体用途来证明它：*什么流程或工作迫使这个事物持久化、保持状态并被返回？* 如果没有，它是暂时的，或者它是过早的。当对象的存在仅仅是因为一个未经验证的策略赌注时，将其标记为 **临时的**——将其建模为假设，不要 "锁定" 它，并且在赌注被测试之前不要在它上面构建上层。

- **动词精确性。** 一个通用动词（编辑、删除、更新）是否隐藏了具有不同现实后果的操作？ "编辑地址" 混淆了纠正打字错误（覆盖是好的）与记录房屋搬迁（应该保留历史）。当一个通用动词可能意味着真正不同的事情时，分别命名操作——"纠正地址" 与 "注册地址变更" 不是啰嗦，而是精确。
- **实现不是设计。** 当讨论如何存储、生成或计算某事时，将其引导到用户可以做什么以及引用它的内容会发生什么。标记真正纠缠的问题以进行工程对话，而不是强迫过早的答案。

## 技术

选择适合实时决策的技术——不要运行所有技术。

| 技术 | 用于 |
|---|---|
| **名词搜寻 + OOUX**（Sophia Prater） | 从研究或领域笔记中提取对象。当你有自然语言要挖掘时的默认方法。使用上述 "真实对象仅限" 测试将名词分为对象 / 属性 / 实例或值 / 暂存（UI 元素、模糊抽象、被当作名词的行动），使用上述 "真实对象仅限" 测试。 |
| **对象定义** | 确定一个对象：它是什么（一句话，用户的视图）、它的属性、它的关系（基数性 + 角色名称），以及它的操作。 |
| **先绘制流程图**（向前推进，向后拉回） | 对象性是不确定的——某个事物是否应该是持久对象取决于它的使用方式。构建流程图（`/layers-interaction-flow`）以查看必须持久化、保持状态或返回的内容，然后回来正式化这些内容。通常是区分真实对象和临时对象最快的方法。 |
| **关系对象图**（`erDiagram`） | 一起查看对象和关系，捕捉缺失、反转或虚假的连接。 `\|\|`=恰好一个，`o{`=零或多个，`\|{`=一个或多个；多的一侧有鸟的脚；标签读取第一个实体 → 第二个。 |
| **状态转换图**（`stateDiagram-v2`） | 对于状态变化会影响用户可以做什么的对象——命名状态、转换，以及每个状态禁止的内容。 |
| **操作（CTA）清单** | 列出用户可以采取的所有操作，跨所有对象，在一个地方——产品的号召性用语词汇。将它们一起列出（而不是按对象列出）会暴露不一致（一个操作的不同操作 Add vs Create vs New），以及过度扁平化（一个动词隐藏了不同的操作）。 |
| **通用语言清单** | 解决命名问题。对于每个有争议的概念：选定的术语、拒绝的替代方案，以及原因。每个概念一个名称，每个名称一个概念——在 UI、帮助文本、API 名称和内部讨论中。 |
| **语义 IxD / 操作语法**（Rosenberg） | 审计多个操作和对象之间的动词一致性和精确性。 |
| **事件风暴——命令/策略**（Brandolini） | 处理密集型领域：从发生的事情开始，回溯到涉及的对象。 |
| **卡片分类** | 词汇在用户或团队之间不明确或有争议。 |
| **走遍现有产品** | 重新设计：当前的 UI 揭示了隐含的模型——将其与用户实际思考的方式进行比较。 |

同时探索 `/layers-intro` 中的**时间决策**——中间操作状态、读模型延迟、关系时间性、删除语义、历史——对于任何对象，如果它们会带来问题。

## 与设计师合作

确定上述哪些决策是活跃的。提供适合的技术：如果材料可供挖掘，使用名词搜寻；如果重新设计，使用走遍产品；如果对象已知且只有它们的形状是开放的，直接进行对象定义。做下一个有用的事情，而不是整个工具包。

只记录残留物——得到确定的对象定义（并且仍然是 **临时的**，有待于赌注或流程），任何编码真实关系或生命周期的图表，词汇调用，以及开放的问题（感觉薄弱的对象，推迟给工程的问题）。不要写一个设计师不会重读的报告。

如果领域工作尚未完成，明确地说：这个模型是一个假设，直到有证据。

当对象和操作稳定时，下一步自然是通过它们设计用户如何移动——`/layers-interaction-flow`。
