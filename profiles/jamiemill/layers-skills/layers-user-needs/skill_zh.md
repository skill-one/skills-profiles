# /layers-user-needs

*假设已加载 `/layers-intro`。这项技能是一个技术库，而非脚本——请参阅那里的“如何使用这些技能”。*

用户需求是我们认为用户试图实现的目标及其原因——这是一种基于观察行为和领域知识的解释，而非对现实的直接捕捉。这一层位于观察的混乱原始材料与解决方案空间的刻意决策之间。

此处的输出是**机会**：需求（用户想要实现的目标）、痛点（导致摩擦的原因）和愿望（他们重视的改进）。三者皆有效——引出所有三者。

---

## 该层做出的决策

- 我们正在定义需求的用户具体是谁——以及处于何种情境
- 他们试图做什么工作：功能性、情感性和社会性
- 哪些需求有证据支撑，哪些是假设
- 哪些需求最重要，以及为什么

如果需求已经清晰且有证据支撑，不要为了重复而重新引出它们——直接进入 `/layers-product-strategy`。

---

## 学科——使需求保持诚实的方法

- **需求而非解决方案。**“当我需要报告时，我想导出到CSV”是一个解决方案。将其推向潜在需求。
- **剥离机制。**如果“当”从句引用您的特定解决方案（您的仪表板、您的CSM、您的每周邮件），您描述的是当前系统，而不是需求。独立于服务它的对象或内容重新陈述：*用户在需要此功能时，情况如何？* 需求源于状态，而非机制。
- **“当”必须是可想象的。**具体到足以看到它发生的时刻——由事件、感觉、节奏或跨越的阈值触发。推进直到它变得具体。
- **引出情感和社会性工作，而不仅仅是功能性。**即使它们在塑造行为，它们也经常被表达不足。明确询问通常会揭示它们。（功能性→交互与模型；情感性→表面语气/反馈；社会性→表面，有时是策略。）
- **标记信心：**观察到的/推断的/假设的。
- **变通方法是信号。**足以激励电子表格或变通邮件的需求是一个强烈的需求。

## 技术

工作故事是默认选项；其余技术适用于特定情境。

| 技术 | 何时使用 |
|---|---|
| **工作故事**（JTBD） | 默认。*当 [情境]，我想要 [动机]，以便 [结果]。* 阻止解决方案；"当"从句强制具体性。 |
| **用户故事** | 团队更喜欢基于角色的框架或现有的敏捷工作流程。 |
| **主要任务分析**（Gerry McGovern） | 大型现有用户群——通过频率识别最重要的任务。统计的、基于调查的。 |
| **角色 + 场景** | 与认为原型是思考方式的相关方沟通。适合对齐；对设计来说不够精确。 |
| **ODI期望结果**（Ulwick） | 精确、可衡量的陈述——"在 [情境] 下最小化 [指标]"。直接映射到机会评分。 |
| **揭示隐藏需求** | 提示找到被忽视的内容：用户在您关注的时刻之前/之后做什么；他们希望不必做的事情；变通方法目前服务的功能。 |
| **粗略优先级排序** | 按重要性×当前服务不佳程度排序。一个既重要又服务不佳的需求是一个高价值机会。保持粗略——精确评分是策略工作。 |

## 与设计师合作

首先确定用户是谁以及处于何种情境——不是“用户”，而是哪种类型，何时。如果有多个不同需求类型的独特类型，请分别处理。注意来源（研究、领域知识或假设）；如果是假设，请标记并计划验证。

然后通过上述学科处理设计师提出的需求，并探查隐藏的需求。提供适合的技术——默认使用工作故事，ODI在可衡量性重要时使用，主要任务在存在大量用户群时使用。不要执行固定顺序。

仅捕获残留物：带信心评分的优先级需求、未优先级但已揭示的需求（以免丢失）、差距（可能真实的未支撑需求）以及用户类型之间的任何矛盾。将其限制为承载决策的内容。

这些需求是 `/layers-product-strategy` 的机会。如果它们大多是假设的，请考虑 `/layers-observed-behavior` 在构建基于它们的策略之前收集证据。
