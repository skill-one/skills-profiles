# /layers-domain

*假设 `/layers-intro` 已加载。这项技能是一个技术库，而非脚本——请参阅那里的“如何使用这些技能”。*

领域层映射的是独立于任何产品的现实世界中存在的事物：用户带来的概念、术语、流程、关系和心智模型。这是观察，而非设计。

---

## 该层做出的决策

- 该领域中的关键概念是什么，以及它们如何关联
- 人们使用的语言——以及语言冲突或分化的地方
- 自然接缝所在：使用相同词汇但含义不同的社群
- 事件和流程如何随时间结构化领域的活动

如果领域已经被充分理解和无争议，你可能不需要这一层——直接进入概念模型。

---

## 学科——使领域工作保持诚信的要素

- **不要解决矛盾——记录它们。** 混乱且不一致的领域语言是*数据*：它表明社群的分歧之处以及产品后续需要做出选择的地方。解决工作属于概念模型，而非此处。将**同义词**（同一事物，不同名称）和**多义性**（同一名称，不同语境下代表不同事物）作为发现记录下来，而非问题。
- **停留在现实世界。** 每当答案漂移到产品或界面决策时，都要进行反驳。问题永远是产品进入领域*之前*领域是如何运作的。
- **真实对象与实例**（用于名词采集）。真实对象是*可实例化*的（可以有许多）、*结构化*的（拥有自己的属性）和*有用*的（人们关心它本身）。注意识别被误认为对象的实例：“CAC”、“ROAS”、“LTV”不是对象，它们是对象**Metric**的实例。标记每个名词*对象 / 属性 / 实例或值 / 不明确*——并且不要过度筛选；概念模型会进行分类。
- **信念与现实。** 如果你映射的是团队信念而非研究事实，请全程说明——这是团队的模型，不一定是用户体验领域的实际方式。

---

## 技术

选择适合的——概念图加上术语审计通常是核心。

| 技术 | 使用场景 |
|---|---|
| **概念图 / 气泡图** (`graph TD`/`LR`) | 领域复杂且理解不足。非正式的节点和线条图显示概念如何关联，而无需过早构建结构。 |
| **术语审计** | 按概念记录：使用的名称、谁在何时使用哪些名称，以及冲突是同义还是多义。不要选赢家。 |
| **边界上下文映射** | 社群内部共享词汇，但在不同群体间存在分歧。命名并描述每个接缝——当模型定义时，这将很重要。 |
| **名词采集** | 收集所有出现的名词，标记对象 / 属性 / 实例或值 / 不明确。概念模型的原材料。 |
| **领域事件风暴**（Brandolini） | 流程密集型领域。在时间轴上用过去时命名重要事件；记录触发因素和结果。围绕事件的对象可能需要后续的状态图。 |
| **专家访谈** | 领域知识存在于人而非文档中——揭示隐性知识和有争议的术语。 |
| **文档与工件分析** | 领域产生合同、表格、发票，揭示自然结构和词汇。 |
| **竞争分析** | 进入已建立的领域——现有产品揭示了他人如何建模，以及他们存在哪些分歧。 |
| **影子跟踪** | 工作流程难以表达；观察会揭示人们实际做什么。 |

## 与设计师合作

从询问你正在映射哪个领域、谁在其中运作以及他们试图在产品存在之前完成什么开始。然后揭示概念——倾听名词（候选对象）、动词（流程）和自然词汇，包括人们*实际称呼*事物的名称。

提供适合实时问题的技术：关系不明确时用概念图，语言有争议时用术语审计，领域流程密集时用事件风暴。做下一件有用的事，而不是全部都做。

只记录残留物——如果概念图证明其价值，则记录概念图；记录文档化的术语冲突和边界上下文，任何关键事件，以及名词采集。这是原材料，而非完成文档。

当领域映射完成后，名词采集是 `/layers-conceptual-model` 的起点。
