# /layers-interaction-flow

*假设 `/layers-intro` 已加载。这项技能是一套技术，而非脚本——参见那里的“如何使用这些技能”。*

交互结构和流程层定义了用户如何与产品交互：他们浏览的地点、可用的操作方式、呈现的内容以及状态之间的转换流程。它位于概念模型（定义*存在什么*）之上，外观（定义*如何呈现*）之下。

面包板始终针对特定用户在特定情境下执行特定任务。在开始之前，先了解任务故事。

---

## 该层做出的决策

- 该流程移动的独立地点
- 每个地点用户可以执行的操作以及每个操作通向何处
- 每个地点需要展示的内容
- 失败路径、空状态和边界情况下的处理方式
- 流程在满足任务需求的同时尽可能保持简洁

如果底层的概念模型不稳定，基于其构建的流程往往需要重新设计——先检查这一点。

---

## 规范——使流程保持真实的原则

- **每个操作都有命名的目标地点。**“提交→通向何处？”如果无法命名，则是一个未决决策。
- **边界是必须步骤，而非事后考虑。** 面包板测试失败路径（验证、服务器错误、断开连接、超时、并发编辑）、空状态和加载状态、操作后状态以及取消路径。每个空白都是未决的设计决策——命名它。
- **无破损对象。** 对于该流程中的每个概念模型对象，其属性和操作应一起可用——而不是分散在屏幕上且无跨链接。
- **无孤立对象。** 每个模型关系应在流程中可见且可导航，或者应有明确决策表明无需如此。
- **词汇与模型的通用语言一致。**
- **命名地点是设计决策**——描述性且对用户有意义（“推荐仪表板”，而非“第3页”）。
- **保持简洁。** 对于单个任务故事，超过5-6个地点是一个需要寻找可合并内容的信号。

---

## 面包板符号

```
地点名称
- 操作→目标地点
- 操作→目标地点
[ 该地点展示的内容 ]
```

## 技术

面包板测试是默认方法；其余技术适用于特定情况。

| 技术 | 在以下情况下使用 |
|---|---|
| **面包板测试** (Ryan Singer / Shape Up) | 默认。文本符号迫使交互逻辑在视觉设计改变变得昂贵之前确定。 |
| **以用户身份走流程** | 叙述：“我是一个执行[情境]的用户。我到达[地点]，我看到[内容]，我想[动机]，所以我[操作]…” 走快乐路径，然后走每条边界。找到未决决策的最快方法。 |
| **用户故事地图** (Jeff Patton) | 复杂产品、多种用户类型、增量规划。活动→任务→故事在时间线上展开。 |
| **任务分析** | 重新设计现有流程——分解当前任务以找到摩擦、错误和变通方法集中的地方。 |
| **服务蓝图** | 流程跨越渠道或涉及后台操作（员工、系统、第三方）。 |
| **关键用户旅程** | 决定要处理哪个流程——实现核心价值的最短路径（高流量、高收入、指标关键）。 |
| **流程图** (`graph LR`) | 仅用于方向——按时间顺序从左到右阅读。文本面包板保持主要工件；图表会丢失条件细节。 |

## 与设计师合作

确定流程服务的任务故事、用户起始地点以及成功标准。如果重新设计，先描述当前流程——它揭示了已做出的决策，其中许多是无意中做出的。然后命名地点、映射操作和目标地点，并包括其边界走流程，应用上述规范。条件——操作何时可用或不可用——通常是隐藏真正决策的地方。

提供适合的技术：面包板测试适用于大多数流程，任务分析适用于重新设计，故事地图适用于大量规划。做下一件有用的事，而不是所有事。

仅捕获残留物：面包板（地点、操作、目标地点、内容、关键条件状态）、流程图（如果有助于方向）、未决决策（空白和未解决的边界情况），以及取决于未决底层决策的风险。

面包板定义交互逻辑而不提交视觉形式。在转向外观之前，确保底层的概念模型稳定。
