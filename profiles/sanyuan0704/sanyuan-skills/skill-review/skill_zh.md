# 技能评审

**铁律**：要具体且可执行。不要说“可以改进”而不说明具体要改什么以及为什么这对模型输出质量很重要。

## 工作流程

```
技能评审进度：

- [ ] 第一步：加载目标 ⚠️ 必须执行
  - [ ] 1.1 确定技能路径
  - [ ] 1.2 阅读SKILL.md并列出所有文件
- [ ] 第二步：分析 ⚠️ 必须执行
  - [ ] 2.1 结构合规性
  - [ ] 2.2 描述质量
  - [ ] 2.3 工作流设计
  - [ ] 2.4 令牌效率
  - [ ] 2.5 反模式检测
- [ ] 第三步：报告 ⚠️ 必须执行
  - [ ] 3.1 优势（做得好的地方）
  - [ ] 3.2 建议（优先级改进）
```

## 第一步：加载目标 ⚠️ 必须执行

确定要评审的技能。接受以下输入：
- 明确路径：`/skill-review 路径/到/技能`
- 当前目录上下文：如果用户已经在技能文件夹中
- 技能名称：在工作区中搜索匹配的技能目录

阅读完整的SKILL.md并列出技能目录中的所有文件。统计SKILL.md的行数——这是一个关键指标。

## 第二步：分析 ⚠️ 必须执行

加载references/review-criteria.md以获取详细标准。从五个维度评估技能：

### 2.1 结构合规性

需要回答的问题：
- 目录是否遵循标准布局（SKILL.md、scripts/、references/、assets/）？
- SKILL.md是否少于500行？
- 前置内容是否只包含`name`和`description`（以及可选的`allowed-tools`、`license`、`metadata`）？
- 是否有不必要的文件（README.md、CHANGELOG.md、LICENSE重复）？
- 参考资料是否按领域组织，并有一级嵌套？

### 2.2 描述质量

需要回答的问题：
- 描述是否包含具体的触发关键词和短语？
- 是否使用关键词轰炸（同一意图的多种表述方式）？
- 是否自包含——路由器是否能在不阅读正文的情况下理解这个技能的作用？
- 是否避免将“何时使用”信息放在正文而不是描述中？
- 用户的自然语言查询是否与这个描述匹配？

### 2.3 工作流设计

需要回答的问题：
- 是否有可追踪的清单，格式便于复制粘贴？
- 关键步骤是否标记为⚠️ 必须执行或⛔ 阻塞？
- 在破坏性/生成性操作之前是否有确认关卡？
- 工作流是否线性渐进，还是跳跃式？
- 在需要复杂性的地方是否使用子步骤？

### 2.4 令牌效率

需要回答的问题：
- 顶部是否有铁律或核心约束？
- SKILL.md是否只包含Claude已经不知道的内容？
- 参考资料是否按需加载，而不是一次性全部加载？
- 指令是否为命令式形式（而不是“你应该...”）？
- 是否执行脚本而不是加载到上下文中？
- SKILL.md和参考文件之间是否存在冗余？

### 2.5 反模式检测

检查以下已知不良模式：
- 模糊指令（“确保质量良好”、“使其更好”）
- 占位符残留（TODO、FIXME、xxx、TBD）
- 对Claude已经知道的事情进行过度指定
- 没有反模式部分（模型没有针对懒惰默认值的护栏）
- 缺少交付前检查清单（没有具体的验证标准）
- 巨大的单体SKILL.md，没有参考提取
- 描述“什么”而不是约束“如何”的指令

## 第三步：报告 ⚠️ 必须执行

### 输出格式

按以下顺序呈现评审结果：

**1. 优势**——这个技能做得好的地方。要具体：引用实际起作用的行或模式。即使是弱技能，至少要有2个优势（找出可挽救的部分）。

**2. 建议**——按影响排序的改进（最高优先级优先）。每条建议必须包括：
- **什么**：发现的特定问题
- **哪里**：文件和位置
- **修复**：具体的可执行更改（在有帮助时显示前后对比）

如果有很多建议（5个以上），则按维度分组。否则，以扁平的优先级列表呈现。

### 语气

- 直接、建设性、同事式
- 首先强调真实的优势——不是填充式表扬
- 建议是机会，不是失败
- 如果技能已经很稳固，简要说明并继续

## 此技能的反模式

- 给出模糊表扬（“结构不错！”）而不引用具体起作用的地方
- 列出问题但没有可执行的修复方案
- 根据个人喜好而不是文档原则进行评审
- 对简单技能建议过度设计
- 标记技能有意省略的功能（检查简单性是否是重点）
