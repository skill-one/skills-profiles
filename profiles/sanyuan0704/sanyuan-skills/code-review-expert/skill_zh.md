# 代码审查专家

## 概述

对当前的git变更进行结构化审查，重点关注SOLID原则、架构、可移除候选项和安全隐患。默认为审查输出，除非用户要求实施变更。

## 严重程度等级

| 等级 | 名称 | 描述 | 操作 |
|------|------|------|------|
| **P0** | 严重 | 安全漏洞、数据丢失风险、正确性问题 | 必须阻止合并 |
| **P1** | 高 | 逻辑错误、显著的SOLID原则违反、性能回归 | 应在合并前修复 |
| **P2** | 中 | 代码异味、可维护性担忧、轻微的SOLID原则违反 | 本次PR内修复或创建后续任务 |
| **P3** | 低 | 风格、命名、轻微建议 | 可选改进 |

## 工作流程

### 1) 预检上下文

- 使用`git status -sb`、`git diff --stat`和`git diff`来界定变更范围。
- 如有需要，使用`rg`或`grep`查找相关模块、用法和契约。
- 确定入口点、所有权边界和关键路径（认证、支付、数据写入、网络）。

**特殊情况：**
- **无变更**：如果`git diff`为空，通知用户并询问是否要审查暂存变更或特定提交范围。
- **大变更（>500行）**：先按文件总结，然后按模块/功能区域分批审查。
- **混合关注点**：按逻辑功能分组，而非按文件顺序。

### 2) SOLID + 架构异味

- 加载`references/solid-checklist.md`获取具体提示。
- 查找：
  - **SRP**：职责不相关的过载模块。
  - **OCP**：频繁修改以添加行为而非扩展点。
  - **LSP**：破坏预期或需要类型检查的子类。
  - **ISP**：包含未使用方法的宽接口。
  - **DIP**：高级逻辑与低级实现强耦合。
- 提出重构时，解释*为何*能提升内聚/耦合，并概述最小化、安全的拆分方案。
- 如果重构非简单，建议分步计划而非大改。

### 3) 可移除候选项 + 迭代计划

- 加载`references/removal-plan.md`获取模板。
- 识别未使用、冗余或已禁用的功能标记代码。
- 区分**立即安全删除** vs **计划延迟删除**。
- 提供后续计划，包含具体步骤和检查点（测试/指标）。

### 4) 安全性和可靠性扫描

- 加载`references/security-checklist.md`获取覆盖范围。
- 检查：
  - XSS、注入（SQL/NoSQL/命令）、SSRF、路径遍历
  - 认证/授权差距、缺失租户检查
  - 密钥泄露或日志/环境/文件中的API密钥
  - 速率限制、无界循环、CPU/内存热点
  - 不安全的反序列化、弱加密、不安全默认值
  - **竞态条件**：并发访问、检查后执行、TOCTOU、缺失锁
- 指出**可利用性**和**影响**。

### 5) 代码质量扫描

- 加载`references/code-quality-checklist.md`获取覆盖范围。
- 检查：
  - **错误处理**：被吞没的异常、过于宽泛的catch、缺失错误处理、异步错误
  - **性能**：N+1查询、热点路径CPU密集操作、缺失缓存、无界内存
  - **边界条件**：null/undefined处理、空集合、数值边界、差一错误
- 标记可能导致静默失败或生产事故的问题。

### 6) 输出格式

按以下结构组织审查：

```markdown
## 代码审查摘要

**审查文件**：X个文件，Y行变更
**整体评估**：[APPROVE / REQUEST_CHANGES / COMMENT]

---

## 发现问题

### P0 - 严重
(无或列出)

### P1 - 高
1. **[文件:行]** 简短标题
  - 问题描述
  - 建议修复

### P2 - 中
2. (继续编号跨章节)
  - ...

### P3 - 低
...

---

## 移除/迭代计划
(如适用)

## 额外建议
(非阻塞的可选改进)
```

**行内注释**：使用此格式记录文件特定发现：
```
::code-comment{file="path/to/file.ts" line="42" severity="P1"}
问题描述和建议修复。
::
```

**干净审查**：如无问题，明确说明：
- 检查内容
- 未覆盖区域（例如，“未验证数据库迁移”）
- 残余风险或建议的后续测试

### 7) 下一步确认

展示发现后，询问用户如何继续：

```markdown
---

## 下一步

我发现了X个问题（P0：_，P1：_，P2：_，P3：_）。

**您希望如何处理？**

1. **全部修复** - 我将实施所有建议修复
2. **仅修复P0/P1** - 处理严重和高优先级问题
3. **修复特定项** - 告知要修复哪些问题
4. **无变更** - 审查完成，无需实施

请选择选项或提供具体指示。
```

**重要**：用户未明确确认前，**不要**实施任何变更。这是审查优先的工作流程。
