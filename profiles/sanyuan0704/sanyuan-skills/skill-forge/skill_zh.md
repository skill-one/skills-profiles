# 技能锻造

**铁律**：技能中的每一行代码都必须证明其代币成本。如果它不能让模型的输出更好、更一致或更可靠——那就删掉它。

## 什么是技能

技能是Claude的“入职指南”——将其从通用代理转变为具有程序知识、领域专业知识和捆绑工具的专用代理。

```
skill-name/
├── SKILL.md           # 必须的：工作流程 + 指令 (<500行)
├── scripts/           # 可选的：确定性、可重复的操作
├── references/        # 可选的：按需加载到上下文中
└── assets/            # 可选的：用于输出，从不加载到上下文中
```

**默认假设**：Claude已经非常聪明。只添加Claude不知道的内容。质疑每一个段落：“这值得它的代币成本吗？”

## 工作流程

复制这个检查清单并在完成时打勾：

```
技能锻造进度：

- [ ] 第1步：理解技能 ⚠️ 必须的
  - [ ] 1.1 明确目的和具体用例
  - [ ] 1.2 收集3个以上的具体使用示例
  - [ ] 1.3 确定触发场景和关键词
- [ ] 第2步：规划架构
  - [ ] 2.1 确定可重用资源（脚本、参考、资源）
  - [ ] 2.2 设计渐进式加载策略
  - [ ] 2.3 设计参数系统（如果适用）
- [ ] 第3步：初始化 ⛔ 阻塞（如果技能已存在则跳过）
  - [ ] 运行 init_skill.py
- [ ] 第4步：编写描述
  - [ ] 加载 references/description-guide.md
  - [ ] 应用关键词轰炸技术
- [ ] 第5步：编写 SKILL.md 正文
  - [ ] 5.1 设置铁律
  - [ ] 5.2 设计工作流程检查清单
  - [ ] 5.3 添加确认门
  - [ ] 5.4 添加参数系统（如果适用）
  - [ ] 5.5 应用写作技巧
  - [ ] 5.6 添加反模式列表
  - [ ] 5.7 添加交付前检查清单
- [ ] 第6步：构建资源
  - [ ] 6.1 实现和测试脚本
  - [ ] 6.2 编写参考文件
  - [ ] 6.3 准备资源
- [ ] 第7步：审查 ⚠️ 必须的
  - [ ] 运行交付前检查清单（第9步）
  - [ ] 向用户展示摘要以确认
- [ ] 第8步：打包
  - [ ] 运行 package_skill.py
- [ ] 第9步：根据实际使用进行迭代
```

## 第1步：理解技能 ⚠️ 必须的

问自己：
- 这个技能解决了Claude单独无法很好地完成的具体问题是什么？
- 用户会实际输入什么来触发这个技能？
- 3-5个具有实际输入和预期输出的具体使用示例是什么？

如果不清楚，请向用户提问（不要一次性问所有问题——从最关键的问题开始）：
- “你能给我3个使用这个技能的示例吗？”
- “你会实际说什么来触发它？”
- “一个好的输出是什么样的？”

在获得至少3个具体示例之前，不要继续进行。

## 第2步：规划架构

对于每个具体示例，问：
1. 哪些操作是确定性和可重复的？→ `scripts/`
2. Claude在特定步骤需要哪些领域知识？→ `references/`
3. 哪些文件用于输出但不在推理中使用？→ `assets/`

关键约束：
- SKILL.md必须保持在500行以内——所有其他内容都放入`references/`
- 参考资料按领域组织，仅一层嵌套
- 加载 references/architecture-guide.md 以获取渐进式加载模式和组织策略

## 第3步：初始化 ⛔ 阻塞

如果正在处理现有的技能，请跳过。否则运行：

```bash
python3 scripts/init_skill.py <skill-name> --path <输出目录>
```

该脚本创建一个模板，包含铁律占位符、工作流程检查清单和正确的目录结构。

## 第4步：编写描述

这是技能中最被低估的部分。描述决定了：
1. 技能是否会自动触发
2. 用户是否会通过搜索找到它

加载 references/description-guide.md 以获取关键词轰炸技术和好/坏示例。

关键规则：永远不要在 SKILL.md 正文中将“何时使用”信息放在里面。正文在触发后加载——太晚了。

## 第5步：编写 SKILL.md 正文

根据每个子步骤的需要加载参考文件：

### 5.1 设置铁律

问：“模型使用这个技能最可能犯的一个错误是什么？”
写一个规则来防止它。将其放在 SKILL.md 的 frontmatter 之后的最顶端。

→ 加载 references/writing-techniques.md 以获取铁律模式和红旗信号。

### 5.2 设计工作流程检查清单

创建一个可跟踪的检查清单，包含：
- ⚠️ 必须的：对于不能跳过的步骤
- ⛔ 阻塞的：对于先决条件
- 子步骤嵌套：用于复杂步骤
- （条件性的）：对于依赖于先前选择的步骤

→ 加载 references/workflow-patterns.md 以获取检查清单模式和示例。

### 5.3 添加确认门

强制模型在以下情况下停止并询问用户：
- 破坏性操作（删除、覆盖、修改）
- 具有显著成本的生成性操作
- 基于分析应用更改

→ 加载 references/workflow-patterns.md 以获取确认门模式。

### 5.4 添加参数系统（如果适用）

如果技能受益于 `--quick`、`--style`、`--regenerate N` 等标志：

→ 加载 references/parameter-system.md 以获取 $ARGUMENTS、标志、argument-hint 和部分执行模式。

### 5.5 应用写作技巧

三种能显著提高输出质量的技巧：

1. **问题式指令**：给出问题，而不是模糊的指令
2. **反模式文档**：列出不要做的事情
3. **铁律 + 红旗**：防止模型走捷径

→ 加载 references/writing-techniques.md 以获取所有三个技巧的示例。

### 5.6 添加反模式列表

问：“Claude对这个任务的懒惰默认会是什么样子？” 然后明确禁止它。

→ 加载 references/writing-techniques.md 以获取反模式示例。

### 5.7 添加交付前检查清单

添加具体的、可验证的检查。每个项目必须足够具体，以便模型可以通过查看输出来检查它。不是“确保高质量”，而是“没有剩余的占位符文本（TODO、FIXME、xxx）。”

→ 加载 references/output-patterns.md 以获取检查清单模式和基于优先级的输出。

### 写作原则

- **简洁**：只添加Claude不知道的内容
- **祈使句形式**：“分析输入”而不是“你应该分析输入”
- **匹配自由与脆弱性**：窄桥 → 具体的护栏；开阔地带 → 多条路线
  - 高自由度（文本）：多种有效方法
  - 中等（伪代码/参数）：首选模式，允许一些变化
  - 低（特定脚本）：脆弱操作，一致性至关重要

## 第6步：构建资源

### 脚本
- 封装确定性、可重复的操作
- 脚本执行时不加载到上下文中——大幅节省代币
- 打包前测试每个脚本
- 在 SKILL.md 中，仅记录命令和参数，不记录源代码

### 参考资料文件
- 按领域组织，而不是按类型
- 仅一层嵌套
- 从 SKILL.md 引用的每个文件都有明确的“何时加载”说明
- 大文件（>100行）应在顶部添加目录

### 资源
- 输出中使用的模板、图像、字体
- 不加载到上下文中，仅通过路径引用

→ 加载 references/architecture-guide.md 以获取详细模式。

## 第7步：审查 ⚠️ 必须的

在打包前向用户展示技能摘要并确认。

### 交付前检查清单

#### 结构
- [ ] SKILL.md 在500行以内
- [ ] Frontmatter 仅包含 `name` 和 `description`（以及可选的 `allowed-tools`、`license`、`metadata`）
- [ ] 描述包含触发关键词和使用场景
- [ ] 没有README.md、CHANGELOG.md 或其他不必要的文件
- [ ] 没有从初始化留下的示例/占位符文件

#### 质量
- [ ] 顶部有铁律或核心约束
- [ ] 有带 ⚠️/⛔ 标记的可跟踪工作流程检查清单
- [ ] 破坏性/生成性操作前有确认门
- [ ] 使用问题式指令，而不是模糊的指令
- [ ] 列出反模式（不要做什么）
- [ ] 参考资料按进度加载，而不是一次性全部加载

#### 资源
- [ ] 脚本已测试并可执行
- [ ] 参考资料按领域组织，深度为1
- [ ] 大型参考资料有目录
- [ ] 资源用于输出，不加载到上下文中

#### 要避免的反模式
- 将所有内容都塞进一个巨大的 SKILL.md (>500行)
- 模糊的描述，如“一个用于X的工具”
- 没有工作流程——让模型自由发挥
- 没有确认门——模型未经检查到完成
- 模糊的指令，如“确保高质量”而不是具体检查
- 包括 README.md、INSTALLATION_GUIDE.md 或其他文档文件
- 在正文而不是描述字段中包含“何时使用”信息

## 第8步：打包

```bash
python3 scripts/package_skill.py <path/to/skill-folder> [output-directory]
```

打包前自动验证。修复错误并重新运行。

## 第9步：迭代

实际使用后：
1. 注意模型在哪里遇到困难或不一致
2. 确定需要改进的工作流程步骤
3. 添加更具体的指令、示例或反模式
4. 重新测试和重新打包
