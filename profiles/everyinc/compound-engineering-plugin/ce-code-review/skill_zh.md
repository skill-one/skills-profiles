# 代码审查

帮助调用者在其商定的范围内交付正确的变更。发现那些后果值得采取行动的缺陷和改进；根据代码的预期行为和项目要求来评判代码，而不是基于首选的重写。即使差异很小，严重的缺陷仍然很重要。充分的变更不需要发现任何问题。

**完成标准：** 当所需的审查和验证完成时，保留的问题需要有源代码支持，并且调用者对任何剩余的覆盖率限制有明确的结果。仅在调用者授权的情况下应用，并遵循以下规则。

## 资产根目录

<!-- ce-docs-root:start -->
**在组合任何资产路径之前，必须解决 CE 资产根目录 `<root>`。**

- **读取** 从 `<repo-root>/.compound-engineering/config.yaml` 中读取 `docs_root` (`<repo-root>` = `git rev-parse --show-toplevel`)，仅读取它。不要从 `config.local.yaml` 中读取。未设置 -> `<root>` 是 `docs`，与之前完全相同。
- **验证** 设置的值：一个相对于仓库的目录，其真实路径（解析符号链接后）仍然在仓库内，既不是仓库根目录，也不在 `.git/` 下。否则以错误命名 `docs_root` 和值停止——绝不能回退到 `docs`。
- **使用** `<root>` 作为唯一的资产位置：如果不存在则创建它，使用此技能自己的子目录，将每个路径组合为 `<root>/<subdir>`，并且永远不要再读取 `docs`。
<!-- ce-docs-root:end -->

## 执行骨干

按顺序执行以下步骤；参考文件提供详细信息，但永远不会改变顺序。进入管理该步骤工作的步骤时读取每个参考文件；在该步骤之前进行的读取不满足它，并且仅传递给叶子的参考文件不是你读取的参考文件。

1. 首先读取 `references/modes-and-output.md`。它解决了争论、冲突、快速审查的短路、审查深度门控以及此调用返回的内容。
2. **阶段 1。** 读取 `references/scope.md` 并解决审查的差异、范围模式以及确定性范围信号。然后在阶段 2 应用该审查深度门控。Lite 会在没有后续骨干参考的情况下结束运行；lite 和专注的每次运行都从此上下文通过 `references/depth-paths.md` 开始。
3. **阶段 2。** 读取 `references/intent-and-plan.md`，为每个审查者编写意图摘要，并发现阶段 6 验证需求时使用的计划。
4. **阶段 3。** 读取 `references/persona-catalog.md` 和 `references/select-and-route.md`，然后选择变更风险所需的审查者，找到适用的标准文件，并决定对抗性审查将如何运行。
5. **阶段 3d。** 当对抗性审查被选中用于本地审查的树时，启动并持久化 `references/cross-model-review.md` 定义的受认可的跨模型作业，**在任何本地角色分发之前**。调用此技能本身就是对其配置的或允许列表中的对等路由的授权，一旦你做出了对接受者和离开机器的代码的必要披露。不要再次要求用户确认，并且不要因为用户没有重复授权而跳过对等。明确的用户对外部审查的禁止可以覆盖它，设置 `cross_model_review_mode: off` 且没有实时选择入的签出也会被解决；两者都在你绑定路由之前解决。启动的对等会在此阶段取代本地对抗性角色，并且只有当范围、允许列表、访问、认证或启动失败时才会保留本地回退在清单中；后续阶段可能会在参考文件声明的条件下恢复本地审查者。一个启动的对等会替换此阶段的本地对抗性角色，并且只有当签出设置 `cross_model_review_mode: off` 且没有实时选择入时才会保留本地回退在清单中；后续阶段可能会在参考文件声明的条件下恢复本地审查者。
6. **阶段 4。** 读取 `references/dispatch-reviewers.md`。将选定的本地审查者作为一组并发批次收集在此轮次中，大小为主机活动代理的容量。只有在终端结果在手中时才会收集每个成功的启动：消耗有效的紧凑返回，记录工具错误或格式不良输出作为失败的审查者，并且启动确认本身不是结果。使用主机的阻塞收集功能来接收异步收件，在参考文件声明的范围内，之后未收集的审查者是失败的审查者；终端结果可能作为调用的返回、阻塞等待的返回或主机交付的终端消息（命名启动并携带其负载）到达；进度更新不是。如果无法可靠地收集启动的工作，请停止它，并且对于任何持久化的对等（跨模型作业），在其参考描述的清理之前运行，然后返回失败结果，并且永远不要在等待它的情况下结束轮次。将本地审查分离到轮询的背景作业是禁止的。跨模型对等是唯一分离的工作，并且它可以与此批次重叠。
7. **阶段 5 和 6。** 一旦每个审查者的结果都在，编写 `references/finish-input.md` 定义的完成输入并停留在该参考文件中：它拥有验证器启动和运行资产列表。按顺序分派它命名的两个叶子子代理，每个子代理都使用 `references/finish-review.md` 种子，叶子从磁盘读取它而你不会打开：一个合并叶子，一次合并对等的发现后从运行目录合并，然后，在你启动并收集它选择的验证器后，一个报告叶子，渲染报告。叶子不会启动子代理；你启动每一个。逐字发出报告叶子的返回作为此技能的响应。永远不要直接从原始审查者资产合成，并且永远不要在分派上下文中合并或渲染。在多代理路径中，仅发出此技能的报告：不要同时调用本机发现或报告工具，该工具仅属于快速审查的短路。

## 运行原则

- **默认仅报告；永不推送。** 一个纯 `ce-code-review` 调用会产生发现，但不会应用它们。进入应用阶段需要 `apply:local`，或调用提示中明确的用户请求应用或修复此审查的发现；已弃用的 `mode:autofix` 令牌既不是。`mode:agent` 永远不会修改树，即使它嵌套在一个稍后应用发现的工作流中。永不推送、打开 PR 或提交工单在任何模式下。
- **无阻塞提示。** 永远不要使用 `AskUserQuestion`、`request_user_input`、`ask_user` 或其他阻塞问题工具。从明确令牌、git 状态、PR 元数据和对话中推断意图、计划和范围。注意覆盖率或裁决中的不确定性——不要停止以询问。
- **仅显式修改。** 永远不要运行 `gh pr checkout`、`git checkout`、`git switch` 或类似的分支切换命令。传递 PR 号码、URL 或分支名称选择 **审查范围**，而不是修改工作树的权限。未提交的工作只能从持有它的签出中审查，因此要在一个特性分支上审查它，停留在该分支（或你自己签出它），并传递 `base:` 或无目标。
- **报告结果，而不是机制。** 你向用户展示的是关于审查的内容：正在审查什么、包含哪些覆盖率以及每个条件镜头的一行原因、独立的跨模型传递，以及发现。命名用户会识别的内容，例如 PR 号码、审查者的关注点或对等模型。此技能的内部标签、分派账本和设置说明应保留在用户界面文本之外。永远不要声称关于对等比其接收证实的更多。这管理了你显示和隐藏的内容，而不是措辞；使用你自己的声音。
