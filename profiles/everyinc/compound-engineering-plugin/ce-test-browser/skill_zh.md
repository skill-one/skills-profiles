# 浏览器测试技能

使用当前 harness 中可用的最佳批准浏览器驱动程序，对受 PR 或分支影响的页面运行端到端浏览器测试。

**完成：** 测试通过报告其发现的内容——要么是摘要，其中每个受影响的路由都标记为通过、失败或跳过，并且每个跳过都附带其原因；要么在预检拦截器阻止测试在执行任何路由之前就停止时，拦截器和清除它的内容。未能达到任何内容，或者因为无人能够访问而将路由从摘要中删除，是此完成条件旨在防止的失败。

## 模式

- **手动（默认）：** 用户控制开发服务器。当备用驱动程序为 `agent-browser` 时，询问是否要运行带头的或无头的。
- **管道（`mode:pipeline`）：** 由 LFG 或其他自动化运行器触发。运行无需人工干预——从不等待问题。从该技能的目录中读取 `references/pipeline-orchestration.md` 并遵循它；它覆盖端口选择（步骤 4，确定开发服务器端口）、开发服务器启动（步骤 5，验证开发服务器正在运行）和可见性提示（步骤 6，设置可见性），在启动服务器的块内使用 `--free` 运行相同的端口脚本。

## 浏览器驱动程序策略

在第一个浏览器操作之前选择驱动程序：

1. **优先使用主机本地的集成浏览器。** 当活动 harness 中的浏览器控制表面嵌入其中或直接拥有它时，可以使用它来导航本地 URL、检查渲染和交互状态、点击/填写/按下、捕获屏幕截图并检查控制台错误。单独配置的浏览器扩展或集成不是主机本地的。在浏览器工作之前加载并遵循所选功能的自己的说明。
2. **否则回退到 `agent-browser`。** 在运行任何命令之前阅读 `references/agent-browser-driver.md`。
3. **不要引入第三个浏览器堆栈。** 永远不要安装或替换独立的 Playwright、Puppeteer、单独配置的浏览器扩展或 MCP 或其他临时浏览器自动化。所选主机本地浏览器中暴露的 Playwright API 仍然是主机本地的；它不是独立的 Playwright。

为整个运行使用一个驱动程序。如果初始化在第一个路由测试之前失败，则所选主机本地驱动程序可以回退到 `agent-browser`。测试开始后，不要混合驱动程序会话、元素引用、屏幕截图或身份验证状态。

## 工作流程

在步骤 3（将更改的文件映射到路由）之前，从该技能的目录中读取 `references/route-and-report.md`。它包含路由映射模式、端口和服务器命令、每页检查、两个面向用户的提示以及摘要格式。

1. **根据上述策略选择驱动程序并记录它。** 这也需要一个包含要测试更改的 git 仓库。
2. **从参数确定测试范围：** PR 编号 → `gh pr view [number] --json files -q '.files[].path'`；`current` 或空 → `git diff --name-only main...HEAD`；分支名称 → `git diff --name-only main...[branch]`。
3. **将更改的文件映射到路由** 并构建要测试的 URL 列表。
4. **确定开发服务器端口。** `scripts/resolve-port.sh` 解析它并在标准输出上单独打印端口：显式端口参数；否则 `package.json` dev/start 脚本中的 `--port` 标志；否则 `.env`、`.env.local` 或 `.env.development` 中的 `PORT=`；否则 `3000`。当用户提供了 `--port N` 或当当前项目指令已在上下文中说明开发服务器端口时，传递显式端口。不要在指令文件中搜索一个：文档中的散文提及、示例和故障排除是不可靠的和易产生误报的，而配置文件和 `.env` 是值得信赖的。每种模式都在需要端口的 shell 调用中运行该脚本，因此不需要任何端口值在 shell 调用之间生存或转录自散文；参考给出了命令。手动模式使用该端口原样：用户控制他们自己的服务器，因此不要扫描其他替代方案。
5. **在询问带头的/无头的之前，验证开发服务器正在运行——** 手动运行没有服务器会在这里停止，所以先询问会浪费问题。
6. **设置可见性，然后验证根。** 可见性与无人干预执行是独立的：
   - **主机本地的集成浏览器：** 保持其正常的集成表面可见且非阻塞，以便用户在有用时可以观看进度。不要在路由更改时反复窃取焦点。这在手动和管道模式中都适用。
   - **`agent-browser` 回退，管道模式：** 无头运行，不询问。
   - **`agent-browser` 回退，手动模式：** 使用主机中已有的阻塞问题工具询问用户是否要运行带头的或无头的（通过功能匹配，而不是通过主机特定名称）。当前工具列表中的存在证明该工具存在；永远不要调用面向用户的问题工具来发现它是否存在。如果列出了匹配的工具但已卸载，请使用主机的工具发现原语加载该功能——不要搜索另一个主机的工具名称。只有在列表中没有这样的工具或真实的调用问题时才回退到在主机的用户可见聊天表面上呈现选项。永远不要无声地跳过问题。

   然后导航到 `http://localhost:<port>`，捕获其渲染或交互状态，并在迭代之前确认根正在提供服务。
7. **测试每个受影响的页面** — 导航、检查新鲜状态、执行关键交互、捕获证据。
8. **在需要外部交互的流程中进行人工验证（OAuth、电子邮件、支付、短信、第三方 API）：** 暂停并询问。**管道模式不暂停**——将每个此类流程记录为跳过并附带原因，然后继续。
9. **通过捕获错误状态和确切的复现来处理失败**，然后询问是否要立即修复或跳过。**管道模式不询问**——记录失败并继续。
10. **以参考给出的格式报告摘要。**
