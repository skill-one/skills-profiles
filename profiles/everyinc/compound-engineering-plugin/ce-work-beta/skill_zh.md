# 工作执行命令

高效执行工作，同时保持质量并完成功能。

## 简介

该命令接受工作文档（计划或规范）或描述工作的纯提示，并系统地执行。重点是快速理解需求、遵循现有模式并在整个过程中保持质量，以**交付完整的功能**。

**Beta发布说明**：当您想试用Codex委托时，手动调用`ce-work-beta`。在Beta期间，规划和工作流程交接仍指向稳定的`ce-work`，以避免双路径编排复杂性。

## 输入文档

<input_document> #$ARGUMENTS </input_document>

## 参数解析

解析`$ARGUMENTS`中的以下可选标记。在解释其余部分为计划文件路径或纯提示之前，删除每个识别的标记。

| 标记 | 示例 | 效果 |
|-------|---------|--------|
| `delegate:codex` | `delegate:codex` | 激活计划执行的Codex委托模式 |
| `delegate:local` | `delegate:local` | 即使配置中启用，也停用委托 |

所有标记都是可选的。当不存在时，回退到以下解析链。

**模糊激活**：也识别如"使用codex"、"委托给codex"、"codex模式"或"委托模式"等命令式委托意图短语，它们等同于`delegate:codex`。提示中提及"codex"（例如，"修复codex转换器错误"）**不能**激活委托——只有明确的委托意图才会触发它。

**模糊停用**：也识别如"无codex"、"本地模式"、"标准模式"等短语，它们等同于`delegate:local`。

### 设置解析链

从参数中提取标记后，使用此优先级链解析委托状态：

1. **参数标志** -- 当前调用中的`delegate:codex`或`delegate:local`（最高优先级）
2. **配置文件** -- 从以下配置块中提取设置。`work_delegate`的值为`codex`会激活委托；`false`会停用委托。
3. **硬默认值** -- `false`（委托关闭）

**读取配置。** 仓库根目录在技能加载时预解析：
!`git rev-parse --show-toplevel 2>/dev/null || true`

如果上面的行是绝对路径，则将其用作`<repo-root>`。如果它为空或仍然显示反引号命令字符串（一个未运行预解析的非Claude托架），则在运行时通过使用shell工具解析`git rev-parse --show-toplevel`来解析`<repo-root>`。然后使用原生文件读取工具（例如，Claude Code中的`read`，Codex中的`read_file`）读取`<repo-root>/.compound-engineering/config.local.yaml`。如果无法解析根目录或文件不存在，所有设置都会回退到默认值。否则，提取以下键的值。

如果任何设置具有无法识别的值，则该设置会回退到硬默认值。对于没有硬默认值的可选设置（`work_delegate_model`，`work_delegate_effort`），无法识别或无法解析的值解析为**未设置**——相应的标志在`codex exec`调用中被省略，Codex从`~/.codex/config.toml`中解析。永远不要将无效值替换为CLI标志。

配置键：
- `work_delegate` -- `codex`或默认`false`
- `work_delegate_consent` -- `true`或默认`false`
- `work_delegate_sandbox` -- `yolo`（默认）或`full-auto`
- `work_delegate_decision` -- `auto`（默认）或`ask`
- `work_delegate_model` -- 要使用的Codex模型。可选——当未设置或无法解析时，会回退到用户的`~/.codex/config.toml`默认值。传递——任何非空字符串都可作为有效值；只有YAML解析失败或空值才会解析为未设置。
- `work_delegate_effort` -- `minimal`、`low`、`medium`、`high`或`xhigh`之一。可选——当未设置或设置为枚举之外的值时，解析为未设置并回退到用户的`~/.codex/config.toml`默认值。

将解析的状态存储供下游使用：
- `delegation_active` -- 布尔值，指示委托模式是否开启
- `delegation_source` -- `argument`或`config`或`default`——委托是如何解析的（用于环境保护来决定通知的详细程度）
- `sandbox_mode` -- `yolo`或`full-auto`（来自配置或默认`yolo`）
- `consent_granted` -- 布尔值（来自配置`work_delegate_consent`）
- `delegate_model` -- 来自配置的字符串，或未设置（回退到Codex配置）
- `delegate_effort` -- 来自配置的字符串，或未设置（回退到Codex配置）。对每个批次努力选择进行下限；不直接传递给`codex exec`。
- `effective_effort` -- 每个批次派生的值（`default | medium | high | xhigh`），在每次批次之前根据`delegate_effort`和`references/codex-delegation-workflow.md`（"每个批次的努力"）计算。将`codex exec`调用的`delegate_effort`替换为该值。

## 执行工作流程

### 阶段0：输入筛选

根据在`<input_document>`中提供的内容确定如何进行。

**计划文档**（输入是一个指向现有计划或规范的文件路径）：首先读取计划的元数据——markdown计划的YAML前缀，或HTML计划的可见标题文本（两种格式都包含相同的字段）。如果它包含`execution: knowledge-work`，这是一个**非代码计划**——读取`references/non-code-execution.md`并遵循该例外，而不是此工作流程的其余部分。否则（该字段不存在或`execution: code`）→ 跳到阶段1并运行正常的代码生命周期。（标记检查存在于此处，在处理计划文档内部，因为检测标记需要已经有一个文件；"纯提示"下面不受影响。）

**纯提示**（输入是工作描述，而不是文件路径）：

1. **扫描工作区域**

   - 识别基于提示可能更改的文件
   - 查找这些区域的现有测试文件（搜索导入、引用或共享名称与实现文件名称的测试/规范文件）
   - 注意受影响区域的本地模式和约定

2. **评估复杂性和路由**

   | 复杂性 | 信号 | 操作 |
   |-------|---------|--------|
   | **简单** | 1-2个文件，没有行为更改（拼写错误、配置、重命名） | 继续阶段1步骤2（环境设置），然后直接实现——不需要任务列表，不需要执行循环。如果更改触及行为代码，则应用测试发现 |
   | **小/中** | 范围清晰，约10个文件以下 | 从发现中构建任务列表。继续阶段1步骤2 |
   | **大** | 跨越性、架构决策、10+个文件、触及认证/支付/迁移 | 告知用户这将受益于`/ce-brainstorm`或`/ce-plan`来暴露边缘情况和范围边界。尊重他们的选择。如果继续，构建任务列表并继续到阶段1步骤2 |

### 阶段1：快速启动

1. **读取计划并澄清** _(如果从阶段0带有纯提示到达则跳过)_

   - 完全读取工作文档
   - 将计划视为决策产物，而不是执行脚本
   - 如果计划包含如`Implementation Units`、`Work Breakdown`、`Requirements`（或遗留`Requirements Trace`）、`Files`、`Test Scenarios`或`Verification`等部分，则使用它们作为执行的主要来源材料
   - 检查每个实现单元上的`Execution note`——这些包含该单元的计划执行姿态信号（例如，测试优先或特征优先）。在创建任务时注意它们。
   - 检查是否有`Deferred to Implementation`或`Implementation-Time Unknowns`部分——这些都是规划者有意留给你在执行期间解决的疑问。在开始之前注意它们，以便它们在执行过程中指导你的方法，而不是在任务中途让你感到惊讶
   - 检查是否有`Scope Boundaries`部分——这些都是明确的无目标。如果实施开始将你拉向相邻的工作，请参考它们
   - 审查计划中提供的任何引用或链接
   - 如果用户在此会话中明确要求TDD、测试优先或特征优先执行，即使计划没有`Execution note`也要尊重该请求
   - 如果有任何不清楚或不明确的地方，请提出澄清问题
   - 如果需要澄清问题，请获得用户对已解决答案的批准。如果不需要澄清问题，则无需单独的批准步骤——计划的范围是计划的权威，而不是可以重新协商的
   - **不要跳过这个** - 不如现在提问，以免构建错误的东西
   - **在执行期间不要编辑计划正文。** 计划是一个决策产物；进度存在于git提交和任务跟踪器中，而不是计划中。`ce-work`不会修改计划——无论它是否交付，都由git决定，而不是记录在文档中。遗留计划可能包含在单元标题上带有`- [ ]` / `- [x]`标记或`status:`字段——忽略它们作为状态；单元完成是在执行期间根据当前文件状态确定的。

2. **设置环境**

   首先，检查当前分支：

   ```bash
   current_branch=$(git branch --show-current)
   default_branch=$(git symbolic-ref refs/remotes/origin/HEAD 2>/dev/null | sed 's@^refs/remotes/origin/@@')

   # 如果远程HEAD未设置，则回退
   if [ -z "$default_branch" ]; then
     default_branch=$(git rev-parse --verify origin/main >/dev/null 2>&1 && echo "main" || echo "master")
   fi
   ```

   **如果已经在特性分支上**（不是默认分支）：

   首先，检查分支名称是否**有意义**——像`feat/crowd-sniff`或`fix/email-validation`这样的名称告诉未来的读者这项工作是什么。自动生成的工作树名称（例如，`worktree-jolly-beaming-raven`）或其他不透明的名称则没有。

   如果分支名称无意义或自动生成，建议在继续之前重命名它：
   ```bash
   git branch -m <meaningful-name>
   ```
   从计划标题或工作描述中推导出新名称（例如，`feat/crowd-sniff`）。将重命名作为继续的推荐选项呈现。

   然后询问："继续在`[current_branch]`上工作，还是创建一个新分支？"
   - 如果继续（无论是否重命名），则继续到步骤3
   - 如果创建新分支，则遵循选项A或B下面

   **如果处于默认分支上**，选择如何继续：

   **选项A：创建一个新分支**
   ```bash
   git pull origin [default_branch]
   git checkout -b feature-branch-name
   ```
   使用基于工作的有意义名称（例如，`feat/user-authentication`，`fix/email-validation`）。

   **选项B：使用工作树（推荐用于并行开发）**
   ```bash
   skill: ce-worktree
   # 确保隔离：检测现有工作树，优先使用托架的原生工作树工具，否则从默认分支创建一个
   ```

   **选项C：继续在默认分支上**
   - 需要用户明确确认
   - 只有在用户明确说"是的，提交到[default_branch]"后才能继续
   - 永远不要直接提交到默认分支，除非有明确的权限

   **推荐**：如果您想同时处理多个功能，请使用工作树。如果您想保持默认分支干净，同时进行实验，请使用工作树。如果您计划频繁切换分支，请使用工作树。

3. **创建任务列表** _(如果阶段0已经构建了一个，或者如果阶段0路由为简单)_
   - 使用平台的任务跟踪工具（Claude Code中的`TaskCreate`/`TaskUpdate`/`TaskList`，Codex中的`update_plan`，或其他托架上的等效项）将计划分解为可执行的任务
   - 从计划的实现单元、依赖关系、文件、测试目标和验证标准中派生任务
   - 当计划为实现单元定义U-IDs时，将单元的U-IDs作为任务主题的前缀保留（例如，"U3: 添加解析器覆盖"). 这将阻止阻塞引用、延迟工作注释和最终摘要与计划使用的相同标识符保持锚定，因此跨计划编辑的进度和可追溯性保持明确。
   - 将每个单元的`Execution note`（如果存在）带入任务
   - 对于每个单元，在实现之前读取`Patterns to follow`字段——这些指向特定的文件或约定以进行镜像
   - 使用每个单元的`Verification`字段作为该任务的主要"完成"信号
   - 不要期望计划包含实现代码、微步TDD指令或确切的shell命令
   - 包括任务之间的依赖关系
   - 基于需要首先做什么来设置优先级
   - 包括测试和质量检查任务
   - 保持任务具体且可完成

4. **选择执行策略**

   **委托路由门**：如果`delegation_active`为true**并且**输入是计划文件（不是纯提示），请读取`references/codex-delegation-workflow.md`并遵循其预委托检查和委托决策流程。如果所有检查都通过并且委托继续，强制**串行执行**并直接进入阶段2，使用工作流的批量执行循环。如果任何检查禁用委托，则回退到标准策略表下面。如果委托是活跃的，但输入是纯提示（没有计划文件），则将`delegation_active`设置为false，并附上简短说明："Codex委托需要计划文件——使用标准模式。"然后继续使用标准策略选择下面。

   在创建任务列表后，根据计划的大小和依赖关系结构决定如何执行：

   | 策略 | 使用场景 |
   |----------|-------------|
   | **内联** | 1-2个小的任务，或需要用户在执行中途交互的任务。**纯提示工作的默认值**——纯提示很少产生足够的结构化上下文来证明子代理派遣 |
   | **串行子代理** | 3+个具有相互依赖关系的任务。每个子代理都获得一个专注于一个单元的新上下文窗口——防止跨多个任务上下文退化。需要计划单元元数据（目标、文件、方法、测试场景） |
   | **并行子代理** | 3+个通过并行安全检查（见下文）的独立单元。同时派遣独立单元，在完成先决条件后运行依赖单元。需要计划单元元数据 |

   **并行安全检查**——在选择并行派遣之前必须执行：

   1. 从每个候选单元的`Files:`部分构建文件到单元映射（创建、修改和测试路径）
   2. 检查交集——任何文件路径出现在2+个单元中意味着重叠
   3. **如果发现重叠**并且工作树隔离不可用：降级为串行子代理。记录原因（例如，"单元2和单元4共享`config/routes.rb`——使用串行派遣"). 串行子代理仍然提供上下文窗口隔离，而无需共享目录写入竞争。
   4. **如果发现重叠**并且工作树隔离可用：并行派遣仍然是安全的——子代理在隔离的工作树中工作，重叠会作为可预测的合并冲突出现，由协调器通过下面的后批次流程处理。记录预测的重叠，以便后批次流程知道要预期的合并冲突。

   即使没有文件重叠，共享协调器工作目录的并行子代理也会面临git索引竞争（并发暂存/提交会损坏索引）和测试干扰（并发测试运行会拾取彼此的进行中的更改）。工作树隔离消除了这两种情况；共享目录回退约束（见下文）缓解了这些问题。

   **子代理隔离**——给每个并行子代理自己的工作树：
   - **Claude Code (`Agent`工具)**: 传递`isolation: "worktree"`和`run_in_background: true`。托架在`.claude/worktrees/agent-<id>`下为每个子代理创建一个工作树，并在自己的分支上。在使用此之前，请验证`.claude/worktrees/`是否被git忽略。
   - **其他平台**——没有内置工作树隔离：子代理共享协调器的目录。

   **子代理派遣**使用您可用的子代理或任务生成机制。对于每个单元，给子代理：
   - 计划文件的全路径（用于整体上下文）
   - 特定单元的Goal、Files、Approach、Execution note、Patterns、Test scenarios和Verification
   - 与该单元相关的任何已解析的延迟问题
   - 指令检查该单元的测试场景是否涵盖所有适用的类别（快乐路径、边缘情况、错误路径、集成）并在需要时补充差距，然后再编写测试

   **系统级测试检查**——在标记任务完成之前，暂停并询问：

   | 问题 | 做什么 |
   |----------|------------|
   | **运行此操作时会发生什么？** 回调、中间件、观察者、事件处理程序——从您的更改向外追踪两级。 | 阅读实际代码（而不是文档）中您触摸的模型的回调，请求链中的中间件，`after_*`钩子。 |
   | **我的测试是否执行了真实的链？** 如果每个依赖项都被模拟，测试证明您的逻辑在隔离状态下工作——它什么也没说关于交互。 | 编写至少一个集成测试，它使用真实对象通过完整的回调/中间件链。与交互的层不使用模拟。 |
   | **失败是否会导致遗留状态？** 如果您的代码在调用外部服务之前持久化状态（数据库行、缓存、文件），当服务失败时会发生什么？重试是否会导致重复？ | 使用真实对象追踪失败路径。如果状态在风险调用之前创建，请测试是否清理或重试是幂等的。 |
   | **还有哪些接口暴露此功能？** 混合、DSL、替代入口点（Agent vs Chat vs ChatMethods）。 | 在相关类中grep此方法/行为。如果需要一致性，请现在添加它——不要作为后续操作添加。 |
   | **各层的错误策略是否一致？** 重试中间件 + 应用程序回退 + 框架错误处理——它们是否冲突或创建双重执行？ | 列出每个层中的具体错误类。验证您的救援列表与下层实际引发的错误是否匹配。 |

   **何时跳过**：没有回调、没有状态持久化、没有并行接口的叶节点更改。如果更改是纯添加性的（新的帮助方法、新的视图部分），则检查需要10秒，答案是"没有触发，跳过"。

   **当这最重要的时候**：任何更改触及具有回调的模型、错误处理具有回退/重试、或通过多个接口暴露的功能。

### 阶段2：执行

1. **任务执行循环**

   对于优先级顺序中的每个任务：

   ```
   while (tasks remain):
     - 将任务标记为进行中
     - 从计划或阶段0发现期间发现的任何参考文件中读取任何文件
     - **如果单元的工作已经存在并且与计划的意图匹配**（文件存在并具有预期的功能，或者单元的`Verification`标准已经由当前代码满足），工作很可能在先前的分支或会话中已交付。验证它是否匹配，将任务标记为完成，然后继续。不要默默地重新实现。
     - 搜索代码库中的相似模式
     - 查找正在更改的实现文件的现有测试文件（测试发现——见下文）
     - 如果委托激活：分支到Codex委托执行循环
       (见`references/codex-delegation-workflow.md`)
     - 否则：按照现有约定实现
     - 添加、更新或删除测试以匹配实现更改（见测试发现下面）
     - 运行系统级测试检查（见下面）
     - 在更改后运行测试
     - 评估测试覆盖率：此任务是否更改了行为？如果是，是否编写或更新了测试？如果没有添加测试，是否有故意的理由（例如，纯配置，没有行为更改）？
     - 将任务标记为完成
     - 评估是否需要增量提交（见下面）

   当单元带有`Execution note`时，尊重它。对于测试优先的单元，在实现该单元之前编写失败的测试。对于特征优先的单元，在更改之前捕获现有行为。对于没有`Execution note`的单元，按实用主义进行。

   执行姿态的约束：
   - 在测试优先的工作中，不要在同一步骤编写测试和实现
   - 不要跳过验证新测试在实施修复或功能之前是否失败
   - 不要超出当前行为切片过度实现，当在测试优先的工作中
   - 对于纯重命名、纯配置和纯样式工作，跳过测试优先的纪律

   **测试发现**——在实现更改到文件之前，找到其现有测试文件（搜索导入、引用或共享命名模式的测试/规范文件）。当计划指定测试场景或测试文件时，从那里开始，然后检查计划可能没有列出的其他测试覆盖。实现文件的更改应附带相应的测试更新——新行为的新测试，修改的测试，删除的测试或更新的测试。

   **测试场景完整性**——在为具有功能的单元编写测试之前，检查计划的`Test scenarios`是否涵盖所有适用的类别。如果缺少类别或场景模糊（例如，"验证正确"而不命名输入和预期结果），则从单元的上下文中补充，然后再编写测试：

   | 类别 | 适用场景 | 如何推导如果缺失 |
   |----------|----------------|------------------------|
   | **快乐路径** | 总是适用于具有功能的单元 | 阅读单元的Goal和Approach以获取核心输入/输出对 |
   | **边缘情况** | 当单元具有有意义的边界（输入、状态、并发）时 | 识别边界值、空/nil输入和并发访问模式 |
   | **错误/失败路径** | 当单元具有失败模式（验证、外部调用、权限）时 | 列出单元应拒绝的无效输入，应强制执行权限/认证拒绝，以及应处理的下游失败 |
   | **集成** | 当单元跨越层时（回调、中间件、多服务） | 识别跨层链并编写一个场景，无需模拟地执行它 |

   **系统级测试检查**——在标记任务完成之前，暂停并询问：

   | 问题 | 做什么 |
   |----------|------------|
   | **运行此操作时会发生什么？** 回调、中间件、观察者、事件处理程序——从您的更改向外追踪两级。 | 阅读实际代码（而不是文档）中您触摸的模型的回调，请求链中的中间件，`after_*`钩子。 |
   | **我的测试是否执行了真实的链？** 如果每个依赖项都被模拟，测试证明您的逻辑在隔离状态下工作——它什么也没说关于交互。 | 编写至少一个集成测试，它使用真实对象通过完整的回调/中间件链。与交互的层不使用模拟。 |
   | **失败是否会导致遗留状态？** 如果您的代码在调用外部服务之前持久化状态（数据库行、缓存、文件），当服务失败时会发生什么？重试是否会导致重复？ | 使用真实对象追踪失败路径。如果状态在风险调用之前创建，请测试是否清理或重试是幂等的。 |
   | **还有哪些接口暴露此功能？** 混合、DSL、替代入口点（Agent vs Chat vs ChatMethods）。 | 在相关类中grep此方法/行为。如果需要一致性，请现在添加它——不要作为后续操作添加。 |
   | **各层的错误策略是否一致？** 重试中间件 + 应用程序回退 + 框架错误处理——它们是否冲突或创建双重执行？ | 列出每个层中的具体错误类。验证您的救援列表与下层实际引发的错误是否匹配。 |

   **何时跳过**：叶节点更改没有回调、没有状态持久化、没有并行接口。如果更改是纯添加性的（新的帮助方法、新的视图部分），则检查需要10秒，答案是"没有触发，跳过"。

   **当这最重要的时候**：任何更改触及具有回调的模型、错误处理具有回退/重试、或通过多个接口暴露的功能。

## 关键原则

### 快速启动，更快执行

- 一次在开始时澄清一次，然后执行
- 不要等待完美的理解——提问并行动
- 目标是**完成功能**，而不是创建完美的流程

### 计划是你的指南

- 工作文档应参考相似的代码和模式
- 加载这些参考并遵循它们
- 不要重新发明——匹配现有的内容

### 边执行边测试

- 每次更改后运行测试，而不是在最后运行
- 立即修复失败
- 持续测试可防止大的意外

### 质量是内置的

- 当Tier 1可用或Tier 2标准匹配时（见`shipping-workflow.md`）进行审查

### 交付完整的功能

- 在继续之前标记所有任务为完成
- 不要留下80%完成的功能
- 完成的功能交付优于完美的功能未交付

## 应避免的常见陷阱

- **分析瘫痪** - 不要过度思考，读取计划并执行
- **跳过澄清问题** - 现在提问，而不是在构建了错误的东西之后
- **忽略计划参考** - 计划有链接是有原因的
- **在最后测试** - 持续测试或遭受后期痛苦
- **忘记跟踪进度** - 随着任务的完成更新任务状态，否则会失去跟踪已完成的任务
- **80%完成综合症** - 完成功能，不要过早结束
- **没有理由跳过审查**——当Tier 1可用时使用；仅在使用`shipping-workflow.md`中的标准才升级到Tier 2；记录跳过两者的情况
- **将计划重新范围化为人类时间的阶段**——计划的Implementation Units定义了执行的范围。不要为每个单元估算人工小时，建议多天细分，或要求用户为"此会话"选择单元子集。代理以代理速度执行，上下文窗口压力通过子代理派遣（阶段1步骤4）解决，而不是通过分阶段会话。如果一个计划文件输入确实太大，无法进行单次执行，请明确说明，并建议用户返回到`/ce-plan`以减少范围——不要发明会话阶段作为解决方案。对于纯提示输入，阶段0的"大"路由已经处理了超范围的工作
