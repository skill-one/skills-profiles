# Agent-Native 架构审计

对代码库进行全面审查，对照 agent-native 架构原则，并行启动每个原则的子代理，并生成评分报告。

## 核心原则审计

1. **动作对等** - "用户能做的，代理也能做"
2. **工具作为基础** - "工具提供能力，而非行为"
3. **上下文注入** - "系统提示包含关于应用状态的动态上下文"
4. **共享工作区** - "代理和用户在同一数据空间工作"
5. **CRUD 完整性** - "每个实体都具有完整的 CRUD (创建、读取、更新、删除)"
6. **UI 集成** - "代理动作立即反映在 UI 中"
7. **能力发现** - "用户可以发现代理能做什么"
8. **提示原生功能** - "功能是定义结果的提示，而非代码"

## 工作流程

### 第一步：加载 Agent-Native 技能

首先，调用 agent-native-architecture 技能以理解所有原则：

```
/ce-agent-native-architecture
```

选择选项 7（动作对等）以加载完整参考材料。

### 第二步：启动并行子代理

使用平台的子代理原语（在 Claude Code 中为 `Agent` 配置 `subagent_type: Explore`，在 Codex 中为 `spawn_agent` 配置 `agent_type: "explorer"`，在 Pi 中通过 `pi-subagents` 扩展配置 `subagent` 配置 `agent: "scout"`），启动 8 个并行子代理，每个原则一个。每个代理应：

1. 枚举代码库中的所有实例（用户动作、工具、上下文、数据存储等）
2. 检查是否符合该原则
3. 提供具体的分数，如 "X out of Y (百分比%)"
4. 列出具体差距和建议

**代理 1：动作对等**
```
审计动作对等 - "用户能做的，代理也能做。"

任务：
1. 枚举前端所有用户动作（API 调用、按钮点击、表单提交）
   - 搜索 API 服务文件、获取调用、表单处理
   - 检查路由和组件中的用户交互
2. 检查哪些有对应的代理工具
   - 搜索代理工具定义
   - 将用户动作映射到代理能力
3. 分数："代理能做 X out of Y 个用户动作"

格式：
## 动作对等审计
### 发现的用户动作
| 动作 | 位置 | 代理工具 | 状态 |
### 分数：X/Y (百分比%)
### 缺失的代理工具
### 建议
```

**代理 2：工具作为基础**
```
审计工具作为基础 - "工具提供能力，而非行为。"

任务：
1. 查找并读取所有代理工具文件
2. 将每个工具分类为：
   - 基础（良好）：读取、写入、存储、列出 - 无需业务逻辑即可实现能力
   - 工作流（不良）：编码业务逻辑、做决策、编排步骤
3. 分数："X out of Y 个工具是基础工具"

格式：
## 工具作为基础审计
### 工具分析
| 工具 | 文件 | 类型 | 理由 |
### 分数：X/Y (百分比%)
### 有问题的工具（应为基础的工具工作流）
### 建议
```

**代理 3：上下文注入**
```
审计上下文注入 - "系统提示包含关于应用状态的动态上下文。"

任务：
1. 查找上下文注入代码（搜索 "context"、"system prompt"、"inject"）
2. 读取代理提示和系统消息
3. 枚举已注入与应注入的内容：
   - 可用资源（文件、草稿、文档）
   - 用户偏好/设置
   - 最近活动
   - 列出的可用能力
   - 会话历史
   - 工作区状态

格式：
## 上下文注入审计
### 上下文类型分析
| 上下文类型 | 已注入 | 位置 | 备注 |
### 分数：X/Y (百分比%)
### 缺失的上下文
### 建议
```

**代理 4：共享工作区**
```
审计共享工作区 - "代理和用户在同一数据空间工作。"

任务：
1. 识别所有数据存储/表/模型
2. 检查代理是否读取/写入相同表或不同表
3. 查找沙盒隔离反模式（代理有独立数据空间）

格式：
## 共享工作区审计
### 数据存储分析
| 数据存储 | 用户访问 | 代理访问 | 是否共享 |
### 分数：X/Y (百分比%)
### 独立数据（反模式）
### 建议
```

**代理 5：CRUD 完整性**
```
审计 CRUD 完整性 - "每个实体都具有完整的 CRUD。"

任务：
1. 识别代码库中的所有实体/模型
2. 对每个实体，检查是否存在代理工具以支持：
   - 创建
   - 读取
   - 更新
   - 删除
3. 按实体和整体评分

格式：
## CRUD 完整性审计
### 实体 CRUD 分析
| 实体 | 创建 | 读取 | 更新 | 删除 | 分数 |
### 总体分数：X/Y 个实体具有完整的 CRUD (百分比%)
### 不完整的实体（列出缺失的操作）
### 建议
```

**代理 6：UI 集成**
```
审计 UI 集成 - "代理动作立即反映在 UI 中。"

任务：
1. 检查代理写入/更改如何传播到前端
2. 查找：
   - 流式更新（SSE、WebSocket）
   - 轮询机制
   - 共享状态/服务
   - 事件总线
   - 文件监视
3. 识别"静默动作"反模式（代理更改状态但 UI 未更新）

格式：
## UI 集成审计
### 代理动作 → UI 更新分析
| 代理动作 | UI 机制 | 立即？ | 备注 |
### 分数：X/Y (百分比%)
### 静默动作（反模式）
### 建议
```

**代理 7：能力发现**
```
审计能力发现 - "用户可以发现代理能做什么。"

任务：
1. 检查以下 7 种发现机制：
   - 引导流程展示代理能力
   - 帮助文档
   - UI 中的能力提示
   - 代理在响应中自我描述
   - 建议的提示/动作
   - 空状态指导
   - 斜杠命令 (/help, /tools)
2. 对 7 种机制评分

格式：
## 能力发现审计
### 发现机制分析
| 机制 | 存在？ | 位置 | 质量 |
### 分数：X/7 (百分比%)
### 缺失的发现
### 建议
```

**代理 8：提示原生功能**
```
审计提示原生功能 - "功能是定义结果的提示，而非代码。"

任务：
1. 读取所有代理提示
2. 将每个功能/行为分类为（参考）：
   - 提示（良好）：自然语言定义结果
   - 代码（不良）：硬编码业务逻辑
3. 检查行为变化是否需要编辑提示而非更改代码

格式：
## 提示原生功能审计
### 功能定义分析
| 功能 | 定义在 | 类型 | 备注 |
### 分数：X/Y (百分比%)
### 代码定义的功能（反模式）
### 建议
```

- [ ] 所有 8 个子代理完成审计

## 可选：单一原则审计

如果 $ARGUMENTS 指定单一原则（例如，"动作对等"），仅运行该子代理，并仅提供该原则的详细发现。

有效参数：
- `action parity` 或 `1`
- `tools` 或 `primitives` 或 `2`
- `context` 或 `injection` 或 `3`
- `shared` 或 `workspace` 或 `4`
- `crud` 或 `5`
- `ui` 或 `integration` 或 `6`
- `discovery` 或 `7`
- `prompt` 或 `features` 或 `8`
