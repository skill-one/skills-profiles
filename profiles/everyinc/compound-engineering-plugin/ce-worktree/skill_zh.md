# 工作树隔离

确保当前工作在隔离的工作空间中进行，不会干扰用户的默认检出。大多数编码框架现在在会话开始时默认创建一个工作树，因此常见情况是**隔离已经存在**。

**完成条件：** 调用者正在一个隔离的树中工作（现有的或新创建的），并且已经报告了其路径和分支，或者报告了一个阻塞器。

**操作顺序：** 检测现有隔离 -> 优先使用原生工作树工具 -> 回退到纯 git。永远不要创建框架无法看到的工作树。

**两种模式，由调用者的需求设置：**

- **新建工作（默认）。** 没有命名的引用 —— 从一个基础（主干）创建一个新分支。这是 `ce-work` 和 `ce-code-review` 在用户选择工作树选项时使用的。
- **隔离现有引用。** 调用者命名一个 PR 头、分支或提交 —— 将工作树附加到该引用，而不是创建一个新分支。**一个分支一次只能在一个工作树中检出。** 如果命名的引用已经在任何地方检出（最常见的是作为默认检出的当前分支），则**不要**创建第二个工作树 —— 报告它已经在 `<路径>` 中检出，并让调用者处理（就地工作；或者，如果需要一个干净的独立树，则在同一提交处创建一个*分离*的工作树）。

## 第 0 步：检测现有隔离

比较**解析的绝对** git 目录与**解析的绝对**公共 git 目录。Git 根据当前目录混合绝对和相对形式（从正常检出的子目录中，`--git-dir` 返回绝对值，而 `--git-common-dir` 可能是相对值），因此原始字符串比较会产生一个错误的“已经隔离”：

```bash
git rev-parse --absolute-git-dir                     # 当前工作树的绝对 git 目录
(cd "$(git rev-parse --git-common-dir)" && pwd -P)   # 绝对共享（公共）git 目录
```

**相等** -> 正常检出；继续到第 1 步。

**不相等** -> 一个链接的工作树 *或* 一个子模块。使用 `git rev-parse --show-superproject-working-tree` 区分：

- **非空** -> 子模块；将其视为正常检出并继续到第 1 步。
- **空** -> **已经隔离**。报告工作树路径 (`git rev-parse --show-toplevel`) 和当前分支，然后**就地工作**——工作树中的工作树会落在错误的位置，并且对创建当前工作树的框架不可见。在隔离现有引用模式下，在这里检出该引用（如果它已经是当前的除外），而不是嵌套一个工作树。

## 第 1 步：优先使用框架的原生工作树工具

如果框架提供了一个原生工作树原语——例如一个 `EnterWorktree` / `WorktreeCreate` 工具、一个 `/worktree` 命令或一个 `--worktree` 标志——使用它并停止。原生工具放置、跟踪和清理工作树，以便框架可以管理它。在后台的 `git worktree add` 创建框架无法看到、导航或清理的幽灵状态。

## 第 2 步：Git 回退

只有在没有原生工具**并且**第 0 步未发现现有隔离时。

1. **从仓库根目录运行：** `cd "$(git rev-parse --show-toplevel)"`。以下路径是仓库根相对的，但技能从用户当前目录运行——没有这个，`.worktrees/<分支>` 和 `.gitignore` 编辑会落在子目录中（例如 `src/.worktrees/...`）。
2. 从工作描述中选择一个有意义的分支名（例如 `feat/login`、`fix/email-validation`）——永远不要使用不透明的自动生成名。基础：origin 的默认分支，否则 `main`。
3. **在创建任何东西之前确保 `.worktrees/` 被忽略：** `git check-ignore -q .worktrees/` ——**带尾随斜杠**，这样即使目录存在之前，现有的目录仅规则 `.worktrees/` 也会被尊重（没有斜杠时探测会错过它并弄脏正确配置的仓库）。未忽略 -> 在 `.gitignore` 中添加一行 `.worktrees/`。
4. 使用 `git fetch origin <from-branch>` 刷新基础。这**不是致命的**——没有 `origin` 远程、不同名的远程或本地分支不是中止；继续使用本地引用。
5. 根据模式创建工作树：
   - **新建工作：** `git worktree add -b <branch-name> .worktrees/<branch-name> origin/<from-branch>`（如果 `origin/<from-branch>` 不存在，则使用本地 `<from-branch>` 引用）。
   - **现有分支或标签：** `git worktree add .worktrees/<slug> <target-ref>`。
   - **PR：** 在一个**本地分支**上检出它——`git fetch origin pull/<n>/head:pr-<n>` 然后 `git worktree add .worktrees/pr-<n> pr-<n>`。永远不要使用分离的 `FETCH_HEAD`：那样会孤立的修复循环的提交，而不是更新 PR。（对于推送到 PR 的跟踪，创建它分离——`git worktree add --detach .worktrees/pr-<n>`——然后 `cd` 进去并运行 `gh pr checkout <n>`，这是安全的）。
   - 如果 git 报告引用已经在其他地方检出，应用上述一个分支一个工作树的规则——不要强制创建第二个工作树。
6. `cd` 进入它，然后报告路径和分支。

如果 `git worktree add` 因沙盒或权限错误失败，请求的隔离不存在。**不要**在当前检出中继续——用户选择隔离正是为了避免这种情况。报告失败并询问，提供选项，例如“在当前检出中工作”或“停止并解决权限问题”，使用主机已经当前工具列表中的阻塞问题工具（按能力匹配，而不是按主机特定名称）。当前工具列表中的存在证明工具存在；永远不要调用用户界面问题工具来发现它是否存在。如果列出的匹配工具已卸载，使用主机的工具发现原语加载该能力——不要搜索另一个主机的工具名。只有在列表中没有这样的工具或真实的调用调用错误时，在聊天中显示编号选项并等待回复。永远不要跳过确认，并且不要自动重试替代路径。
