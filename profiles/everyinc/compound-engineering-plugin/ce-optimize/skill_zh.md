## 持久化纪律

磁盘上的实验日志是事实来源。写入顺序是测量、写入、验证，然后向用户展示。**现在读取 `references/persistence.md`** 了解检查点 CP-0 到 CP-5、文件布局和恢复。下面的阶段标记每个检查点所在位置。

## 阶段

四个阶段按顺序运行。每个阶段命名它无法启动的参考。全新运行不会跳过任何阶段：更难的优化会花费更长时间在一个阶段，而不是运行更少的阶段。

**恢复不是全新运行。** 在恢复时，仅进入阶段 0 足够检测运行并恢复日志缺失的任何 `result.yaml` 标记。然后从记录的阶段继续：跳过日志证明已完成的工作，并重新进入任何它未通过的审批检查。检查点证明产生它的工作，而不是用户决策：日志不记录审批，因此未见过用户批准的恢复会再次呈现阶段 1 门。

**阶段 0：设置。** 输入是一个目标，或指向 spec YAML 的路径。它来自用户或调用技能。如果两者都没有提供，询问：“你想优化什么？描述目标，或提供优化 spec YAML 文件的路径。” 加载或构建 spec 并保存它（CP-0）：**读取 `references/spec.md`**。然后搜索先前的学习内容，检测运行身份，并创建分支和临时空间。**读取 `references/measurement.md`** 了解阶段 0 和阶段 1 的其余部分。

**阶段 1：测量框架。** 构建或验证框架，写入基线（CP-1），探测并行性，检查工作树预算。两个门会停止运行：

- **干净树门。** 在 `scope.mutable` 或 `scope.immutable` 中的任何文件存在未提交更改时不要继续。参考定义了检查和要询问的内容。
- **用户审批门。** 展示阶段 1 组装的内容；参考列出了要包含的内容。如果主要类型是 `judge` 且 `max_total_cost_usd` 未设置，明确说明支出无上限。提供继续、修复问题、调整 spec。调整 spec 仅在日志未包含来自它的任何内容（没有假设后备库和没有实验）时可用，并且它会将运行返回阶段 1 以确保基线与新 spec 匹配。一旦 spec 产生的任何内容存档，该 spec 在运行中固定。**在用户明确批准之前不要进入阶段 2。** 然后从磁盘重新读取 spec 和基线。

**阶段 2：假设生成。** 分析当前方法，对假设进行排序，记录后备库（CP-2）。在更便宜的定位测量会改变保留或跳过时，不要调度实现实验。**读取 `references/loop.md`** 了解本阶段和阶段 3。一个门：**依赖项预审批。** 收集所有假设中的每个新依赖项，并展示完整列表进行批量审批。用户不批准的依赖项保留在后备库中，在批次选择中被跳过，并在收尾时返回。

**阶段 3：优化循环。** 选择一批，调度实验，每个结果落地时持久化（CP-3），用 `scripts/decide.mjs` 评估，更新状态和摘要（CP-4），然后检查是否停止。一旦任何七个标准之一成立，立即停止：所有声明的必要目标已满足、最大迭代次数、最大小时数、裁判预算耗尽、平台期、用户中断或没有可运行的假设，`references/loop.md` 精确说明每一个。否则开始下一批。

**阶段 4：收尾。** **读取 `references/wrap-up.md`** 了解延后的假设、摘要、保留内容、清理和完成后的选项。CP-5 标记日志最终。**只有在用户选择不返回阶段 3 的选项后，才写入它。** 两个选项会返回：继续，以及批准延后的依赖项。
