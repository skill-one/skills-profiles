# 调试和修复

找出失败的根源，然后在用户选择时，以测试优先的原则进行修复。

**完成条件：** 从触发因素到症状的因果关系链被完整陈述，并附带文件：行号证据，或者已经移交了经过验证的修复（PR、提交，或用户选择的停止点），或者已经交付了仅用于诊断的摘要。**升级而不是坚持：** 2-3个假设被穷尽而没有确认，或者3次失败的修复尝试，意味着诊断*为什么*而不是再次尝试——这就是 `references/investigate.md` 描述的智能升级。一个假设，一次更改；同时更改多个以查看什么有效是散弹调试。

`<bug_description>` 是这个技能被调用时传入的内容——一个失败描述、`mode:` 令牌，或问题引用（`#123`、`org/repo#123`、一个问题URL）——来自用户或调用技能（`ce-babysit-pr` / `lfg` 在 `mode:pipeline` 传递失败的作业和日志尾部；`lfg` 的缺陷路线传递 `mode:return-to-caller` 和用户自己的引用）。如果未提供任何内容，则为空。


## 模式

默认是 **交互式**：调查，运行第2阶段的修复选择门，然后运行第4阶段的移交。

**`mode:pipeline`**（由编排器如 `ce-babysit-pr` 或 `lfg` 设置）：完全非交互式运行，并且永远不会调用阻塞式提问工具。从 `<bug_description>` 中移除令牌，然后 **阅读 `references/pipeline-mode.md` 并遵循它**——它用保守的默认值覆盖了所有“询问用户”的点，将第2阶段的修复门替换为“修复收敛性错误，推迟发散性错误”，并将第4阶段的移交替换为具有精确 `status` 的结构化返回，`status` 恰好是 `fixed-and-pushed | fixed-not-pushed | diagnosed-no-fix | flaky-infra | needs-human`。调用者根据这些精确的拼写分支，所以永远不要重命名、缩写或添加到它们。

**`mode:return-to-caller`**（由 `lfg` 在其缺陷路线上设置）：非交互式运行，但调用者拥有修复后的所有内容。移除令牌，然后 **阅读 `references/return-to-caller.md` 并遵循它**——它保留第0-3阶段和收敛或推迟修复的边界，应用第3阶段的分支规则，使修复落在特性分支上，提交修复拥有的文件而不推送，跳过修复后的精炼和审查步骤，并返回 `status` 恰好是 `fixed | diagnosed-no-fix | needs-human | blocked` 的结构化结果。相同的拼写规则适用。


## 阻塞式提问

每当这个技能向用户提问时，使用主机中当前工具列表中已有的阻塞式提问工具（按能力匹配，而不是按主机特定名称）。存在于当前工具列表中是工具存在的证明；永远不要调用面向用户的提问工具来发现它是否存在。如果列出了匹配的工具但已卸载，使用主机的工具发现原语来加载该能力——不要搜索另一个主机的工具名称。仅在列表中没有此类工具或真实的提问调用出错时，才回退到主机聊天界面的编号选项。永远不要无声地跳过提问，并且永远不要在未响应的情况下结束阶段。


## 证据中的秘密

调试不断显示原始输出——命令结果、捕获的有效载荷、日志摘录——并且套件可能在命令运行时渲染命令的输出，所以在构造命令时检查秘密，而不是之后。将凭证保存在环境变量中而不是命令行上；当命令的输出可能包含秘密（详细 HTTP 跟踪、转储的标题、配置或环境打印）时，将其捕获到文件中，并仅显示清理后的摘录，将 `<REDACTED>` 写在每个秘密的位置。没有秘密（凭证、令牌、认证头、连接字符串）出现在显示的、写入的或提交的任何内容中。如果清理移除了诊断所需的内容，请说明并询问用户，而不是取消脱敏。


## 证据根

仅在您首次组成 `<root>/` 路径时才解析 `<root>`——一次不组成任何证据路径的运行将完全跳过此步骤。

**在组成任何证据路径之前，解析 CE 证据根 `<root>`。**

- **读取** 从 `<repo-root>/.compound-engineering/config.yaml` 中读取 `docs_root` 仅（`<repo-root>` = `git rev-parse --show-toplevel`）。不要从 `config.local.yaml` 读取它。未设置 -> `<root>` 是 `docs`，与之前完全相同。
- **验证** 设置的值：一个相对于仓库的目录，其真实路径（符号链接解析后）仍然在仓库内，既不是仓库根目录，也不在 `.git/` 下。否则，用错误名称 `docs_root` 和值停止——永远不要回退到 `docs`。
- **使用** `<root>` 作为唯一的证据位置：如果不存在则创建它，使用此技能自己的子目录，将每个路径组成 `<root>/<subdir>`，并且永远不要再读取 `docs`。

## 执行流程

五个阶段按顺序：**0 分诊 -> 1 调查 -> 2 根本原因 -> 3 修复 -> 4 移交。** 除了 0 阶段的 trivial-bug 快速路径外，没有跳过和复杂性级别。一个硬错误在每个阶段花费更长的时间；它不会进入较少的阶段。

**现在阅读 `references/investigate.md` 并遵循它以进行第 0-2 阶段**——问题获取、重现、环境健全性和脏树暂存实验、反向跟踪、跟踪器/PR 历史搜索、假设基础，以及升级表。下面仅陈述门。

**记录中的问题。** 如果用户给您传递了一个工单或问题，那么这个错误已经在其中某个系统中存在，无论它是什么；一个 Sentry 问题与一个 Linear 工单一样重要。将它的标识符和 URL 传递到第 4 阶段。如果输入只是一个堆栈跟踪、测试路径或描述，则此运行**没有记录中的问题**。这是一个普通状态，不是需要填补的空白：没有记录地发送修复，永远不会打开工单来制造记录，也永远不会询问用户是否要。第 1 阶段的跟踪器搜索读取先前的工作，并且**永远不会为错误建立新家园**。一个现有的此错误工单是在第 4 阶段*链接*，而不是创建。

**trivial-bug 快速路径**（原因可从输入中读取、一行修复、无需深度跟踪）仍然运行第 2 阶段的修复选择门，然后再编辑：它节省了调查仪式，而不是用户是否要应用修复的选择。

**选择回归测试。** 确认的缺陷的回归测试属于现有覆盖率已经拥有该行为的任何地方：从现有的测试开始，而不是从新文件开始。在编写第 2 阶段的建议之前，阅读 `references/fix.md` 以了解家园和命名规则，而不仅是在第 3 阶段的编辑之前。一个因为更改故意反转它断言的行为而失败的测试没有错误的期望——那是下面的发散情况，被推迟而不是更新。


### 第 2 阶段门：先呈现，然后询问

**因果关系链门：** 在您能够解释完整的链——触发因素通过每个步骤到观察到的症状——没有任何空白之前，不要继续到第 3 阶段。“不知何故 X 导致 Y”是一个空白。只有用户才能在调查受阻时授权基于最佳假设继续。

一旦根本原因得到确认，将发现结果作为用户可见的块写入：因果关系链和文件：行引用；建议的修复和它更改的文件；要使用、添加、修改或加强的测试，以及现有测试是否应该已经捕获到；以及任何相关工单或 PR 以及它如何塑造建议——如果打开的 PR 已经修复了这个问题，请先提供该链接，而不是一个全新的修复。

**门前的同轮呈现：** 在完全写入该发现块后（在本轮或立即前一个助手消息中）不要打开修复选择问题——在模态套件上，阻塞式提问工具仅渲染它自己的茎，所以仅在“根本原因已确认”上触发问题会留下用户在没有因果关系链的情况下选择。命名选项不是呈现发现，并且在选择后承诺解释太晚了。

当请求尚未授权下一个操作时，询问（根据 **阻塞式提问**）要采取哪条路径，提供以下三个选项。显式的修复请求是第 3 阶段。显式的仅诊断请求跳到第 4 阶段。`mode:pipeline` 和 `mode:return-to-caller` 从不询问。测试建议无论哪种方式都是诊断的一部分。

1. **立即修复它**——继续到第 3 阶段
2. **仅诊断——我将自行处理**——跳过修复，写入第 4 阶段的摘要，结束技能
3. **重新思考设计**（`ce-brainstorm`）——仅在错误无法在当前设计中修复时：根本原因是错误的职责或接口而不是错误的逻辑，需求本身是错误的，或者每个候选修复都是围绕不再成立的假设的工作绕过。大小本身不是设计问题。

**`mode:pipeline` 和 `mode:return-to-caller`：** 不要询问。继续到第 3 阶段并应用一个**收敛**修复；一个**发散**修复——一个会反转故意合同/行为/产品决策的修复，包括一个“失败”的测试断言预期行为——被推迟，而不是应用，根据 `references/pipeline-mode.md` 或 `references/return-to-caller.md`。在这里永远不要路由到 `ce-brainstorm`；设计问题变成了 `needs-human` 残余。


### 第 3 阶段：修复

如果用户选择了“仅诊断”，跳到第 4 阶段的摘要。如果他们选择了“重新思考设计”，控制已转移到 `ce-brainstorm` 并结束此技能。

**在编辑任何文件之前阅读 `references/fix.md`** — 测试优先序列、失败修复规则和纵深防御和事后分析触发器。两个规则决定修复是否可以开始，所以它们保留在这里：

- **分支。** 检查 `git status`；如果用户在需要修改的文件中有未暂存的更改，请在编辑前确认。如果当前分支是默认分支，则创建特性分支而不询问——从错误中派生名称，`git checkout -b <name>`，并说明您移动到了哪个分支。通过将当前分支与 `main`、`master` 或 `git rev-parse --abbrev-ref origin/HEAD`（带 `origin/` 前缀去除）进行比较来检测默认值——原始输出是 `origin/<name>`，所以未去除比较永远不会匹配。
- **记录修复前的范围：** 当前 `HEAD`、`git status --short` 是否干净，以及任何预先存在的已更改文件。然后保持一个**修复拥有的文件**（为此错误更改的测试和实现）的列表，以便您在处理时工作。第 4 阶段从此记录回答它的问题，并且无法在之后重建它。


### 第 4 阶段：移交

**`mode:pipeline` — 跳过整个交互式移交。** 没有精炼或审查步骤，没有残余问题，没有预览，没有学习捕获提议。根据 `references/pipeline-mode.md` 提交并推送收敛性修复，然后发出该引用的**结构化返回**。发散 / 需要人类的项在那里推迟（打开线程或调用者的运行报告评论——永远不会是 PR-body 部分）。**`mode:return-to-caller` — 同样跳过：** 在特性分支上提交修复拥有的文件，不推送任何内容，并发出 `references/return-to-caller.md` 定义的结构化返回。在这两种模式下，返回是此技能写入的最后一件事。它结束此技能，而不是回合。调用者在同一会话中运行，并且其下一步遵循返回；不要向它宣布移交。本节的其余部分仅适用于交互式路径。


**结构化摘要** — 总是首先写入：

```
## 调试摘要
**问题**：[什么被破坏了]
**根本原因**：[完整的因果关系链，带文件：行号引用]
**推荐测试**：[为防止再次发生要添加/修改的测试，带具体的文件和断言指导]
**修复**：[发生了什么更改——或者如果第 3 阶段被跳过，则为“仅诊断”]
**预防措施**：[添加的测试覆盖率；如果适用，纵深防御]
**信心**：[高/中/低]
```

**如果第 3 阶段被跳过**，在摘要后停止——用户已经表示他们要自行处理。不要提示。

**如果第 3 阶段运行**，现在阅读 `references/post-fix-handoff.md` 并遵循它，然后再路由。它定义了修复后的质量步骤：上下文覆盖检查、机械修复的跳过规则、保持 `ce-simplify-code` 和 `ce-code-review` 不参与无关分支工作的范围，如何处理剩余发现，`## 修复后质量` 块，以及提供学习捕获的准则。所有这些都不出现在本文体中。下面的路由命名运行*哪个*操作，而不是使它安全的范围规则，所以它不能被即兴创作。跳过阅读会发送未经审查的修复，让审查深入到无关分支工作，并将接受的发现困在会话中。

#### 路由

**将修复部署，不要携带用户没有主动提供的东西**——不进入提交，不进入推送，不进入 PR。不要询问是否要打开 PR；权限不是门。两个问题决定移交。从第 3 阶段记录的预修复范围回答它们，而不是分支是如何存在的。**通过平台的技能调用原语本身**触发操作——永远不要仅仅告诉用户要键入命令。

**1. 可以放入提交中的内容——修复拥有的文件和任何其他东西。** 这是问题中任何提交技能的约束，而不是它自己的操作。它在每条路线上都保持不变，无论是远程还是本地。在这里不要提交。

- 如果没有修复拥有的文件携带预先存在的编辑，则这些文件是提交范围。将它们传递给要提交的技能。
- 如果修复拥有的文件已经携带了用户的编辑，则无法分离它们：`ce-commit` 在文件级别分组，并且永远不会拆分文件。根据 **阻塞式提问** 在任何东西提交之前询问是否要提交该文件（包括他们的编辑）、留下修复未提交，或停止。只有第一个答案会继续。其他两个会结束移交，所以问题 2 从不运行并且没有东西提交；说明留下了什么以及为什么。每个选项都会失去代理无法代表用户选择的东西，这就是为什么这个问题幸存的原因。第 3 阶段的确认覆盖了*编辑*文件，而不是将用户的编辑与修复一起提交。

**2. 谁提交，以及是否发布。** 恰好有一个运行。

- **发布** 当且仅当所有三个都成立时：预修复树是干净的，分支上的任何内容都是用户尚未提供的作业，并且 `origin` 是 **PR-capable**：某个地方 `gh` 实际上可以打开 PR。以适合您面前仓库的方式建立这些。有两个事实比看起来更不明显。
  - `ce-commit-push-pr` 推送**整个分支**，并且它的 PR 跨越了它上的每个提交，而不仅仅是您的修复。所以问题是关于分支，而不是您的差异。它还在创建 PR 之前推送，所以远程 `gh` 无法打开 PR 会留下分支发布但没有 PR。
  - 已经推送的并不是已经**提供**的。在开放 PR 下的提交处于审查中，所以它们是提供的，并且此运行更新该 PR 而不是打开第二个。为备份或触发 CI 推送的提交不是提供的，并且第一个 PR 会发布它们。与远程进行比较，而不是本地引用：一个本地分支，包括第 3 阶段可能从中分支的默认分支，本身可以比推送的更前。
  如果您无法建立所有三个，请选择本地路线；这是安全的方向，预览不是它的替代品。否则预览将要提交的内容，在哪个分支上，以及是否打开或更新 PR，然后**调用 `ce-commit-push-pr` 技能并使用 `branding:on`**。它在问题 1 的范围内提交，所以不要先提交。预览是一个陈述，不是一个问题。显示结果的 PR URL。
- **保留本地** 当任何三个中的任何一个失败时。在问题 1 的范围内调用 `ce-commit` 技能并推送无。用一行说明什么保留在本地以及为什么，并说明您将在请求时推送并打开 PR。不要先询问；本地提交是可逆的。
- **不是 git 仓库**：不提交。在摘要和品质块后停止。

**上下文覆盖**（“不要从技能打开 PRs”，“仅提交”，“在修复后停止”）——遵循用户所说的话，并且**在这里停止**，如果他们要求的话，不要提交。模糊的语气提示不是覆盖。


**PR 打开后**——应用引用的学习捕获标准。只有当这个门使修复合格时，才提供捕获；如果用户接受，调用 `ce-compound` 技能，然后仅提交和推送 `ce-compound` 实际写入或更新的工件，以便打开的 PR 拿到它们。如果它什么也没写，则不提交文档。
