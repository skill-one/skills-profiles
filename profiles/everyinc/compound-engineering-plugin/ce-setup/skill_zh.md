# 复合工程设置

## 交互方式

使用当前工具列表中已有的主机阻塞式问题工具来询问以下每个问题（按能力匹配，而非特定主机名称）。当前工具列表中的存在证明该工具存在；切勿调用面向用户的问题工具来发现其是否存在。如果匹配的工具已列出但未加载，则使用主机的工具发现原语来加载该能力——不要搜索其他主机的工具名称。仅在列表中不存在此类工具或实际问题调用出错时，才回退到主机用户可见的聊天界面上的编号列表。切勿无声地跳过或自动配置。

`ce-setup` 是一个轻量级健康检查和本地仓库配置助手。它**不**批量安装所有可选依赖项。缺失的工具被报告为可选能力，以便用户仅安装他们使用的流程。

## 包脚手架

当调用命名要添加、创建或脚手架的复合包（`pack:<id>` 参数，或相同请求的文本形式）时，从该技能的目录中读取 `references/pack-scaffold.md` 并按其替换阶段 1-2（诊断和修复本地仓库问题）：它在用户批准后、自行运行健康检查并向阶段 3（摘要）报告之前，仅写入包及其配置条目。

## 资产出根解析

每个写入或读取资产生成目录（`solutions`、`plans`、`ideation` 和其他 CE 拥有的树）的复合工程技能通过以下规则解析其根。`ce-setup` 包含规范声明并报告解析的根，以便操作员可以在运行其他技能之前确认产出物存放位置。

<!-- ce-docs-root:start -->
**在组合任何资产生成路径之前，解析 CE 资产出根 `<root>`。**

- **读取** `<repo-root>/.compound-engineering/config.yaml` 中的 `docs_root` 仅（`<repo-root>` = `git rev-parse --show-toplevel`）。不要从 `config.local.yaml` 中读取它。未设置 -> `<root>` 是 `docs`，与之前相同。
- **验证** 设置值：一个仓库相对目录，其真实路径（解析符号链接后）仍位于仓库内，且既不是仓库根目录也不在 `.git/` 下。否则报错，并命名 `docs_root` 和值——永不回退到 `docs`。
- **使用** `<root>` 作为唯一资产生成位置：如果不存在则创建它，将每个路径组合为 `<root>/<subdir>` 并使用该技能自己的子目录，且永不另外读取 `docs`。
<!-- ce-docs-root:end -->

## 阶段 1：诊断

### 第 1 步：确定插件版本

通过读取平台暴露的插件元数据或清单来检测已安装的复合工程插件版本。如果无法确定版本，则跳过此步骤。

如果找到版本，则通过 `--version` 将其传递给检查脚本。否则省略该标志。

### 第 2 步：运行健康检查

在运行脚本之前，显示：

```text
Compound Engineering -- 正在检查您的环境...
```

运行捆绑的检查脚本。将 `SKILL_DIR` 设置为您加载此 `ce-setup` SKILL.md 的绝对目录——Bash 工具的当前工作目录是用户的项目，而不是技能目录，因此裸 `scripts/` 路径将无法解析：

```bash
SKILL_DIR="<包含此 SKILL.md 的目录的绝对路径>";
if [ -f "$SKILL_DIR/scripts/check-health" ]; then bash "$SKILL_DIR/scripts/check-health" --version VERSION; else echo "未在 $SKILL_DIR/scripts/check-health 找到捆绑的健康脚本；从 ce-setup 中运行内联检查。"; fi
```

如果步骤 1 无法确定版本，则使用不带 `--version VERSION` 的相同命令。

如果脚本不可用，则运行 `references/repo-fixes.md` 中列出的内联等效项。

向用户显示诊断输出。缺失的可选工具不是设置失败。健康报告包括解析的资产生成根和提供它的配置层（根据上述资产生成根解析）；显示该行，以便操作员可以确认 CE 产出物将写入的位置。缺失 `config.yaml` 是报告的缺失，而不是项目问题。

### 第 3 步：决定是否需要修复

本地仓库修复的健康报告仅适用于报告诊断的检出。如果阶段 2 将写入不同的可写检出，则首先诊断该检出。会话级发现（如插件版本和可选工具）仍来自此会话的阶段 1。

在健康报告后，根据可写检出可用性决定阶段 2：

- 如果此会话有一个可写的 git 检出，则本地运行阶段 2，即使 `project_issues` 为 0。阶段 2 总是刷新示例，并且当该文件缺失时始终提供创建 `config.yaml` 的选项。
- 如果此会话没有可写的检出，但用户命名了仓库并且 harness 暴露了具有可写检出的远程仓库工作表面，则在该表面上运行阶段 2 并在阶段 3 报告远程本地修复。
- 否则跳过阶段 2 并进入阶段 3，说明由于没有可写的检出而跳过了本地写入。

如果报告命名了遗留的复合码典工具映射，则按照此技能目录中的 `references/legacy-codex-tool-map.md` 提供删除。该块存在于用户的 Codex 主目录中，而不是检出中，因此无论是否运行阶段 2，该提议都有效。

此外，当报告命名这些项目问题时，也进行修复：

- 过时的 `compound-engineering.local.md`
- `.compound-engineering/config.local.yaml` 存在但未安全 git 忽略
- `.compound-engineering/config.example.yaml` 缺失或过时
- 健康报告标记 `ce-work` 技能实现引擎不可用或无效，检测到已退役的标量路由键，或报告了格式错误的休眠 `work_engine_preferences` 或格式错误的 `work_engine_effort`
- 健康报告标记 `docs_root` 无效（`Invalid docs_root ...`）——直到修复后，CE 产出物才会被写入

如果可选工具缺失，则不要提供批量安装。诊断已经打印了相关的安装命令或项目 URL。说明：“仅安装您使用的可选工具。”

## 阶段 2：修复本地仓库问题

在做出任何本地仓库更改之前，从该技能的目录中读取 `references/repo-fixes.md`。它包含步骤 4-9：删除过时的 `compound-engineering.local.md`、刷新示例配置、提供创建 `config.yaml` 的选项、修复无效的 `work_engine_preferences` 和 `docs_root`、两个 `.gitignore` 提供的选项以及代理指令提供的选项（知识库提及、复合指令和 `ce-noslop` 的聊天注册指令）。

那里的所有路径都从仓库根目录（`git rev-parse --show-toplevel`）解析，而不是当前工作目录。维护生成的示例文件是阶段 2 自行执行的工作——刷新 `config.example.yaml` 和删除过时的 `config.local.example.yaml`。对用户拥有的每个文件的更改只有在用户批准后才会提供和应用。

## 阶段 3：摘要

**用户可运行的调用渲染。** 在设置摘要中，默认使用 `/ce-setup`；仅在活动主机是 Codex 或明确文档了美元前缀技能调用时使用 `$ce-setup`。在 oh-my-pi (`omp`) 上，使用 `/skill:ce-setup`。仅渲染调用作为内联代码并输出一种形式。

显示简要摘要：

```text
✅ Compound Engineering 设置完成

已修复：     <应用的修复，或无>
已跳过：   <拒绝的修复，或无>
可选：  <缺失的可选工具，或全部可用>

随时运行 `<渲染的调用>` 重新检查。
```
