最近简化代码以增强清晰度、可重用性、质量和效率，同时保持行为完全一致。优先考虑可读、明确的代码，而非紧凑代码——代码行数减少不是目标。

## 第一步：确定范围

按以下顺序解决简化范围：

1. **用户命名的范围**具有权威性；不要扩大它。
2. **否则，在git中**，使用当前分支相对于其基础。如果没有可用的基础，使用暂存和未暂存的更改（`git diff HEAD`）。
3. **在git外部或没有差异时**，使用用户命名的文件或对话中较早编辑的文件。

如果以上任何一项都未产生非空范围，则停止并询问用户要简化什么，而不是猜测。使用当前工具列表中已有的主机阻止问题工具（按能力匹配，而非按特定主机名称）。当前工具列表中的存在证明该工具存在；永远不要调用面向用户的问题工具来发现其是否存在。如果列出的匹配工具未加载，则使用主机的工具发现原语加载该能力——不要搜索其他主机的工具名称。仅在列表中找不到此类工具或真实问题调用出错时，才回退到主机用户可见聊天界面的编号选项。永远不要无声地跳过问题。

**预检。** 如果范围没有实质性的用户编写的代码——只有文档、生成或第三方文件、依赖项或锁文件，或机械性重复——则报告没有可简化的内容并停止，无需审查。对于混合范围，仅保留代码。此检查是关于变更类型，而非其大小：明确的小范围仍然运行，任何大小或成本阈值都是调用者设置的。

当平台的任务跟踪功能可用时，显示审查、应用和验证结果，而无需为每个审查者创建一个任务。否则继续，无需在聊天中模拟任务列表。

## 第二步：并行启动3个审查代理

通过平台的子代理原语（在Claude Code中为`Agent`/`Task`，在Codex中为`spawn_agent`）发送三个通用子代理——代码重用、代码质量和效率审查者，如果可用；否则内联或串行运行审查。对于每个审查者，从该技能的目录中读取其提示资产，并将**完整文件内容**作为子代理的提示传递，以及已确定的范围（完整的差异或文件集），以便它具有完整的上下文：

- `references/personas/code-reuse-reviewer.md`
- `references/personas/code-quality-reviewer.md`
- `references/personas/efficiency-reviewer.md`

不要从记忆中改述这些标准。读取每个文件并逐字传递，否则审查者会失去保持行为一致性的规则。

**有界调度。** 将三个审查者排队，并仅启动 harness 接受的代理数量。并发性或活动代理限制错误表示 harness 已满，而非审查者失败：保留审查者排队并在槽位空闲后重试。当调度无法通过活动工作、支持释放或更正调用时，使用相同的提示资产内联运行该通过，并披露替代方案。

**代理生命周期。** 在清理前收集终端结果，包括失败。当 harness 提供调用者拥有的清理时，关闭或释放审查者拥有的代理，然后重新填充槽位、推进阶段或返回。不要向无剩余工作的已完成代理发送消息。不要从完成或中断中推断释放容量，或编造清理操作。

**模型选择。** 当当前 harness 暴露已知覆盖时，使用平台的平衡中端模型为这些审查者。在 Claude Code 中这是 Sonnet 类。在 Codex 中，仅在活动调度原语暴露显式模型或自定义代理选择器时应用此级别；仅任务措辞不能选择不同模型。否则省略覆盖并继承父模型——在父模型上的工作通过优于损坏的调度。

**权限模式。** 在调度调用中省略 `mode` 参数，以便应用用户配置的权限设置。

## 第三步：修复问题

仅当所有三个审查结果都完成后（无论由子代理返回还是内联生成）才继续。直接应用有价值的发现；将误报和低价值发现记录为跳过，无需询问用户。

在需要评估发现时，超出已确定范围进行检查，但仅编辑该范围及其所需的导入/导出行。对于用户命名的文件或目录范围，这些导入/导出行也必须在其中；跳过任何会编辑范围外变更边界的修复。

每个修复必须保持输出、错误、副作用和顺序。如果无法确定，则跳过。

一旦验证当前未发布的范围内的早期迭代中仅存在的接口或数据形状没有已部署、持久化、公开、外部、依赖分支或存储库调用者超出已确定范围，它就不再是受保护的行为。仅在所有必需调用者更新都符合现有变更边界时才移除该兼容路径；否则保留它。

**永远不要简化掉安全检查。** 保留信任边界验证、数据丢失保护、安全检查和可访问性功能。跳过任何会削弱或移除其中之一的发现。

**尊重调用者传递的结构锚点。** 带有结构锚点约束的计划路径是上下文，而非范围。保留其 `session-settled:` 关键技术决策，包括有意重复或分离。

## 第四步：验证行为是否保持

运行项目范围的类型检查和代码检查。运行与爆炸半径匹配的测试：针对本地更改的范围测试，针对共享或广域更改的更广泛测试，以及当运行器无法范围测试时运行完整套件。

报告检查名称和相关信息输出中的失败。修复简化引起的失败或撤销负责的更改；永远不要放宽断言、削弱类型或跳过测试。

如果未配置测试套件、代码检查或类型检查，则在摘要中明确说明；不要无声地跳过验证。

## 第五步：总结

总结哪些原本就合理，哪些有所改进。报告按重用、质量和效率应用的计数、跳过计数和检查结果。如果未发生变化，请说明。不要使用净移除行数作为成功指标。
