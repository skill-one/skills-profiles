# 文档评审

帮助作者完成一份可用于执行约定工作的可靠文档。发现可能改变工作结果或实质性阻碍执行的问题，并在现有权限范围内解决这些问题。根据文档是否指导正确工作来评判，而不是根据其包含的细节多少。即使缺陷很小，严重后果也值得关注。一份充分的文档无需修改。

评审者角色提供证据；判断权在你。对照整个文档、项目事实和既定决策检查他们的主张。在编辑权限和评审者要求所声明的综合参考范围内，纠正阻止现有决策执行的已证实错误。仅返回仍需权限的宝贵改进、用户才能提供的后续选择或关键信息，以及有用的观察结果。

**完成条件：** 每位选定的评审者都已返回或被命名为覆盖范围失败者、保留的发现对约定工作有已验证后果，并且分配给 Apply 的所有授权更正都已执行并检查。通过交互式批准或决策过程报告最终状态，或在非交互模式下以结构化文本返回。

## 交互模式规则

**在其他任何操作之前，先读取 `references/modes.md`。** 它定义了如何检测模式、非交互式参数契约以及问题工具规则：匹配主机当前工具列表中已有的阻塞式问题工具（从不调用面向用户的问题工具来发现它）、如果它被列出但未加载，则在交互流程顶部预加载它，并且仅在 harness 真正缺乏时才回退到编号列表。

无论如何，要求用户决策的问题都会调用工具或大声回退。将其作为纯文本叙述是一个错误。

## 工具根

仅在无路径交互分支中解析 `<root>`，该分支发现 `<root>/plans/` 下最新的计划。其他运行读取其被传递的路径处的文档。因此，绝对路径或非交互式评审——`/tmp/plan.md`，可能在任何存储库之外——永远不会依赖于它不需要的存储库根或 CE 配置。

<!-- ce-docs-root:start -->
**在组合任何工具路径之前，先解析 CE 工具根 `<root>`。**

- **读取** `docs_root` 从 `<repo-root>/.compound-engineering/config.yaml` 仅（`<repo-root>` = `git rev-parse --show-toplevel`）。不要从 `config.local.yaml` 读取它。未设置 -> `<root>` 是 `docs`，与之前完全相同。
- **验证** 设置的值：一个相对存储库目录，其真实路径（解析符号链接后）仍位于存储库内，且既不是存储库根也不是 `.git/` 下。否则，以错误命名 `docs_root` 和值停止——永远不会回退到 `docs`。
- **使用** `<root>` 作为唯一的工具位置：如果不存在则创建它，使用此技能自己的子目录组合每个路径为 `<root>/<subdir>`，并且永远不会也读取 `docs`。

## 第一阶段：获取和分析文档

**现在读取 `references/document-intake.md`。** 它涵盖了每种模式下如何获取文档、当找不到文档时该做什么和说什么，以及分类信号。

其中的两条规则适用于每个后续步骤。

**在任何分发之前进行验证。** 每个解析路径必须在磁盘上可读。如果有一个不可读，则分发**无**角色：评审者从文件系统读取，因此他们无法访问仅存在于未检出的分支上的路径（问题 #925）。

**按内容分类，而不是准备标签或文件路径。** 仅包含产品合同的统一工具是 **`unified-requirements`**；缺少实现部分是预期的。任何实现规划使其成为 **`unified-plan`**，包括需要评审的不完整或受阻规划。其他工具使用传统的 `requirements` / `plan` 分割。

HTML 统一工具采用相同的路径。每个修复都落在文档的原始格式中；永远不会将 Markdown 插入 HTML。该参考涵盖了具有 ID 的项。将分类传递给每个角色，放在 `{document_type}` 槽位。

## 第二阶段：宣布和分发角色

仅在 `references/document-intake.md` 中的完成评审重用条件通过时才跳过分发；继续使用该证据进入第三阶段。

**为每个条件角色读取 `references/persona-selection.md`** 激活信号和宣布格式。其中两条信号在合理证据上过度激活：`security-lens-reviewer` 上的敏感数据绑定，以及 `adversarial-document-reviewer` 上的挑战表面门槛。然后读取 **`references/dispatch.md`** 用于有效载荷变量、切片、模型分层和评审者失败处理。

团队始终是 `coherence-reviewer` 和 `feasibility-reviewer`，以及每个激活的条件角色。在任何分发之前，用每个角色的个人理由宣布团队。

通过平台的子代理原语以**有界并行性**分发通用子代理。用其 `references/personas/<reviewer-name>.md` 的全部内容为其播种。永远不会按类型或名称分发独立的代理。

容量拒绝是背压，不是评审者失败：等待并重试。如果容量无法恢复且选定的评审者仍未被分发，则按照 `references/cross-model-review.md` 的描述收集并清理任何已启动的跨模型作业，然后停止为不完整，没有综合、修复或成功交接。保留收集的结果，并报告哪些评审者完成、失败或无法运行，以及原因。

### 跨模型判断传递

如果任何**条件判断三重奏**被激活，则运行此传递：`adversarial-document-reviewer`、`product-lens-reviewer`、`security-lens-reviewer`。遵循 `references/cross-model-review.md`，它定义了整个传递：确认主机、用于整个文档的单一目标和路线、在机器离开之前的信息披露，以及如何启动、收集和折叠同伴。

传递是可加的且非阻塞的：失败或超时不会停止任何操作，并在 Coverage 中命名。首先检查签出的 `cross_model_review_mode` 设置，它可以以命名理由跳过传递。仅在 `CROSS_MODEL_PEERS` 设置时才过滤接收者——未设置意味着无过滤，而不是未批准。永远不会在显式模型或接收者上静默更改。

## 第三至五阶段：综合、展示和下一步行动

等待所有已分发的代理返回，包括任何跨模型 `<reviewer-name>-<provider>.json` 返回。然后读取 `references/synthesis-and-presentation.md`。它定义了综合、每个发现如何按置信度和修复类别路由、修复应用、非交互式结果格式，以及路由问题的交接。在促进协议时，只有具有 `independence_verified: true` 的工具才被视为独立评审者。

**仅交互模式。** 读取 `references/walkthrough.md` 用于分组确认、路由问题以及每个发现的逐项走遍。读取 `references/bulk-preview.md` 用于最佳判断路由、追加到开放问题以及自动解析的批量操作预览。在评审证据完成之前，无论是新收集的还是有效复用的，都不要加载它们，并且非交互式运行根本不会加载它们——它会在结构化评审结果处停止。
