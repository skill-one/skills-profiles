# 工作执行命令

## 结果

- **结果：** 从计划、规范或具体工作提示中实现的、本地验证的变更集。
- **下一个消费者：** 在独立使用中，交付工作流将验证的变更通过审查和交付。在返回调用者模式中，调用工作流接收结构化的实现和验证结果，并拥有其剩余的关卡。
- **完成：** 所有范围内的任务都已完成，所需的验证证据已记录，相关检查通过，运行达到以下任一状态：拥有的交付交接（带有代码审查收据或明确的跳过短语——参见第3-4阶段）、完整的返回结果或明确的阻塞器。
- **意图：** 完成请求的功能，而无需重新协商计划或转移规范集成权限。工作者接收有界单元；主机协调器检查实际变更，并拥有权威验证和规范提交。

## 执行工作流

**必须读取捆绑的引用，绝不能近似。** 从本技能加载的 `SKILL.md` 目录中解析下面命名的每个引用或脚本路径，使用 harness 供应的完整技能路径，并且绝不能通过 glob 目标仓库来查找捆绑文件。在进入其管辖的阶段时读取每个引用；在该阶段之前进行的读取不满足要求，并且本文件指示再次读取的引用在其步骤中即使已经处于上下文中也会再次读取。如果 harness 没有暴露技能目录，或者无法读取所需的文件，则在管辖该操作的步骤之前停止并报告缺失的文件。不要从记忆中重建其规则；报告缺失引用，而不是继续原生操作。

### 第0阶段：输入分类

**恢复激活优先。** 在将输入分类为计划、路径、空白或裸提示之前，识别要恢复、检查、回收或清理现有运行的请求。恢复永远不会派遣新工作者、选择新路线、发现另一个计划、重新运行完成的验证或进入任一交付路径。如果运行 ID 缺失，则请求它；绝不能猜测。

在任何其他输入决策之前，读取 `references/input-triage.md`。它决定源解析、控制令牌、恢复、只读发现、计划就绪性、非代码路由、空白输入和裸提示尺寸。它在此处的三个规则如下：

- 裸提示是平凡的——一个或两个文件，没有行为变更——则跳过任务列表，但在写入之前仍解析其执行引擎。纯粹的机械 diff 也不需要 post-PR 观察。当不确定时，采取更完整的路线。
- 裸提示在本会话中已经由 `ce-plan` 尺寸的，则执行，而不是再次计划。用户会权衡的决定作为问题提出，而不是作为返回到 `ce-plan` 或 `ce-brainstorm` 的路线。
- 如果无法读取该引用，则停止；绝不能将控制令牌或不可执行的艺术品视为代码工作。

当分类选择返回调用者模式时，立即读取 `references/return-to-caller.md` 并记录它如何管辖此运行的结束。如果无法读取，则在任何变更之前停止；不要回退到独立行为。

### 第1阶段：快速启动

1. **建立工作区。** 在移动分支、编辑、派遣或提交之前，读取 `references/workspace-setup.md`。它决定可写入的检出、计划澄清、分支放置、预工作清单、已脏文件和任务设置。没有可写入的规范检出时不写入，并且除非用户在本会话中明确指示，否则绝不在真实的默认分支上写入。

   **不要提交或发布用户未提供的任何内容。** 当一个单元需要已脏的文件时，独立模式询问一次是否包含或排除该文件。返回调用者模式既不询问也不编辑它；它返回阻塞，并命名冲突以及如何恢复。

2. **解析引擎，然后策略。** 在有界计划摄入和任务推导之后，但在选择执行、写入、派遣或提交的单元之前，读取 `references/execution-engines.md` 并完成其路线选择。它无论是否有类型绑定都适用；只有当该引用选择它或耗尽允许的回退时，原生执行才合格。引擎选择永远不会改变如何结束运行的引用。

   如果选择跨模型执行，则在任何内容或权限跨越到其他模型之前，读取 `references/cross-model-execution.md`。它定义控制器初始化、初始化后引擎锁定、有界出口、事务、恢复和收据。

   在选择内联、串行或并行执行之前，以及在派遣任何工作者之前，读取 `references/execution-strategy.md`。它决定调度、隔离、每个工作者接收的数据包、工作者生命周期和集成。主机协调器保持权威验证并做出规范提交。

### 第2阶段：执行

在第一个实现写入之前，包括在平凡路线中，读取 `references/implementation-loop.md`。它决定证据的选择、验证、何时停止单元、增量提交、遵循现有模式、持续测试、简化停止点、UI 工作、进度跟踪和已确定的决策。

本文件中的提交规则在整个过程中保持有效：每个实现提交仅命名该单元拥有的文件。裸 `git commit` 可以吸收用户的现有索引，因此它是禁止的。

### 第3-4阶段：质量检查和收尾工作

在任务和本地验证完成后，独立模式在任何质量检查或交付之前读取 `references/shipping-workflow.md`。它决定简化、代码审查收据和回退、剩余发现、最终验证和交付。

**代码审查完成关卡（仅限独立模式）。** 代码审查必须在交付之前实际发生。运行未完成，必须不调用提交或交付技能，并且必须不在交付引用记录了实际完成的 `ce-code-review` 收据或其确切授权跳过状态之一之前报告交付完成。绝不能替代精神自我审查或之前已应用的发现。此规则不适用于返回调用者模式。

## 返回调用者模式

返回调用者模式仅执行实现和本地验证。它必须不进入第3-4阶段或运行最终简化、代码审查、PR 创建、CI 观察、看护或任何其他独立交付操作；调用者拥有这些步骤。

在发出结果之前，再次读取 `references/return-to-caller.md`。它唯一定义了完整的返回结果、证据完整性检查、路线和模型记录、恢复语义和 `standalone_shipping_skipped: true`。不要从此文件构建完整结果。

如果在该引用在计划或实现创建状态后失败，则保留每个已更改文件、提交、工作区和控制器记录。返回此文件的最小阻塞结果：`status: blocked`，`plan_path`，`run_id` 当已知时，`changed_state`，`blockers` 命名缺失引用，以及 `recovery_path`。不要擦除部分状态，报告成功，或陷入独立交付路径。
