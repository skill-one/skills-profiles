# Git 提交、推送和 PR

**询问用户：** 使用当前工具列表中已有的主机阻止问题工具（按能力匹配，而不是按主机特定名称）。当前工具列表中的存在证明该工具存在；永远不要调用面向用户的问题工具来发现其是否存在。如果列表中列出了匹配的工具但已卸载，则使用主机的工具发现原语来加载该能力——不要搜索另一个主机的工具名称。只有在列表中没有此类工具或真实的提问调用出错时才回退到在聊天中询问，并且永远不要无声地跳过提问。

## 模式

- **仅描述** — 用户只想获得描述（“编写/草拟 PR 描述”、“描述此 PR”、“粘贴的 PR URL 或编号”）。仅运行步骤 4 并打印结果。仅在请求时才应用它。传递粘贴的 PR 引用，以便 Pre-A 解决范围。
- **描述更新** — 刷新或重写现有 PR 的描述，没有提交或推送意图。通过以下上下文规则解决 PR 存在性：exit-0 `[]` 表示“没有打开的 PR”（报告并停止），非零退出表示**未知**（解决授权或连接性，然后停止直到存在性已知）。**对于打开的 PR**，在 PR 模式下运行步骤 4 在该 URL 上，然后运行步骤 5 预览、确认并通过 `gh pr edit` 应用。
- **完整工作流** — 否则：步骤 1-5。当意图或偏好需要堆栈时，改为进入 **堆栈模式**。

**`mode:pipeline` 修饰符**，由 `lfg` 等编排调用者设置。以非交互方式运行解析的模式并抑制所有阻止性提问。每个被抑制的提问都采用保守默认值：不重写现有 PR、保留分支、无法解决的基线停止而不是猜测，以及直接应用描述更新预览，因为该调用是应用意图。管道堆栈模式仅使用调用中的意图和范围，并将姿态传递给交接。

## 堆栈模式（可选）

**仅可选。** 当意图或立场偏好需要多 PR 堆栈时进入。显式堆栈请求是**必需意图**——不要将其重新读取为具有自定义 `--base` 的单个 PR。**不要**主动建议 PR 堆栈。当用户**没有**请求时，**拒绝**无意义的堆栈（一个逻辑更改、人为切片）并保持单 PR。

在堆栈模式下，在步骤 3 之前加载 `references/stack-submit.md` 并仅遵循其探测、拓扑和回顾性构建；该逐层提交流程替换了普通的步骤 3。**不要在那里提交。** 步骤 5 处理提交、`gh stack` CLI 依赖项和残留物，以及交接姿态：默认为 `posture:stack-ready`，只有在显式提交意图时才为 `posture:stack-land`，从**底部打开的非草稿** PR 开始。不要向此技能的参数提示添加 `posture:`。

## 上下文

**在步骤 1 之前阅读 `references/context.md`。** 它定义了命令表、退出码含义、分支和分离 HEAD 陷阱，以及分支和 PR 解决步骤 1-2 使用的规则。其中两条规则也属于这里。永远不要询问是否分支：分离的 HEAD 或有工作的默认分支会创建一个，而没有任何工作的默认分支会报告并停止。并且对于常规提交，当模糊时默认为 `fix:` 而不是 `feat:`，除非用户覆盖。

三条规则控制运行。

**每个 `git` 和 `gh` 探测都是其自己的 argv-form 调用**，收集和重新验证一样，并且其退出状态是控制流。参考给出了原因并命名了此技能固定的两个复合配方。

**探测输出是一个快照。** 在每个有后果的操作之前重新验证分支、远程和 PR 状态：步骤 3 的推送、步骤 5 的创建。

**只有从基础仓库查询返回的 exit-0 `[]` 才表示“没有打开的 PR。”** 非零退出是**未知**，永远不会是“无”。在分支检出时，使用 `-R` 目标基础并仅传递分支名称，因为 `--head <owner>:<branch>` 默默返回 `[]`。对于结果，**不要**盲目地取索引 0：匹配 HEAD 所有者和分支，并在模糊匹配时停止。注意该条目的 URL 和正文——步骤 5 使用 URL 来选择现有 PR 路径，步骤 4 重写现有正文。

## 产物根

当存档开启时，一次性解析 `<root>`：它在 `<root>/explainers/` 下写入解释器。

<!-- ce-docs-root:start -->
**在组合任何产物路径之前解析 CE 产物根 `<root>`。**

- **读取** `docs_root` 从 `<repo-root>/.compound-engineering/config.yaml` 仅（`<repo-root>` = `git rev-parse --show-toplevel`）。不要从 `config.local.yaml` 读取它。未设置 -> `<root>` 是 `docs`，与之前完全相同。
- **验证** 设置的值：一个相对仓库的目录，其真实路径（符号链接解析后）仍然在仓库内，并且既不是仓库根也不是在 `.git/` 下。否则停止并报错命名 `docs_root` 和值——永远不要回退到 `docs`。
- **使用** `<root>` 作为唯一产物位置：如果不存在则创建它，将每个路径组合为 `<root>/<subdir>` 并使用此技能自己的子目录，并且永远不要也读取 `docs`。

## 步骤 3：提交和推送

**阅读 `references/commit-and-push.md`** 了解提交/推送机制和通过 `references/branch-creation.md` 处理默认分支。如果堆栈模式提交了其层，则跳到步骤 4；步骤 5 提交它们。

**项目发布门。** 在发布提交之前，从项目当前上下文中的活动指令和约定以及任何额外作用域指令中解决每个适用的 pre-push 或 review-ready 要求。只有对正在发送的确切提交状态有效的证据才满足它们；否则在外部写入之前停止并报告缺失或失败的内容。如果没有，则继续。

永远不要使用 `git add -A` 或 `git add .`。在添加和提交中都命名文件，以便未关联的已暂存文件保持在外。尊重 `exclude:<paths>`：保留并报告它们。

## 步骤 4：组合 PR 标题和正文

**你必须完整阅读 `references/pr-description-writing.md`** — 它定义了标题和正文内容规则，包括在重写时保留现有 `Related:` / `Fixes` 的规则。然后阅读 **`references/compose.md`** 了解在组合之前需要做出的三个决定：证据决定；教学决定，其中 `pr_teaching_section` 默认**开启**，`pr_teaching_archive` 默认**关闭**，并且只有**活动（非注释）**的键会改变其中任何一个；以及品牌决定，其中品牌**关闭**除非此调用携带 `branding:on` 或用户在此提示中请求复合工程品牌。

如果步骤 1 找到现有 PR，则将其 URL 传递给步骤 4，以便 PR 模式获取现有正文。

## 步骤 5：应用和报告

**阅读 `references/apply-and-handoff.md`** 了解应用、预览、存档和交接。在 `gh pr create` 之前重新检查 PR 存在性：匹配的 PR 采用现有 PR 路径，exit-0 `[]` 创建，非零阻止。通过 `--body-file <path>` 传递正文，永远不要通过 stdin——`gh` 用空正文退出 0。

**在这里决定完成。** 交互式完整工作流或管道堆栈提交**未完成**，直到 `ce-babysit-pr` 拥有已发布 PR 的后续处理。仅报告 PR URL 不是成功。加载调用者以选择监控模式。如果在此会话中运行它，则继续直到其停止条件允许最终报告。

只有 `babysit:off`、CE 配置的 `auto_babysit: false` 或 `references/apply-and-handoff.md` 中的“不要触发”情况会跳过它。没有其他监视替代：不是 `ci-watcher`，不是 `gh pr checks --watch`，不是手写的轮询，不是“稍后”。如果无法加载或启动 `ce-babysit-pr`，则停止并报告它被阻止。
