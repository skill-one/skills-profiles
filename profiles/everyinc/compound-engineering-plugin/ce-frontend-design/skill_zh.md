# 前端设计

指导创建独特且符合生产标准的前端界面，避免通用的AI美学。这项技能涵盖完整生命周期：检测现有设计、规划设计、有意构建，以及视觉验证。

## 权威层级

这项技能中的每条规则都是默认值，而非强制规定。

1. **现有设计系统/代码库模式** -- 最高优先级，始终尊重
2. **用户的明确指令** -- 覆盖技能默认值
3. **技能默认值** -- 在绿野工作或用户要求设计指导时应用

在具有既定模式的现有代码库中工作时，遵循这些模式。当用户指定与默认值相矛盾的方向时，遵循用户。

## 工作流程

```
检测上下文 -> 规划设计 -> 构建 -> 视觉验证
```

---

## 第0层：上下文检测

在进行任何设计工作之前，检查代码库中的现有设计信号。这决定了技能的多少主观指导适用。

### 要查找的内容

- **设计令牌/ CSS变量**： `--color-*`，`--spacing-*`，`--font-*` 自定义属性，主题文件
- **组件库**： shadcn/ui，Material UI，Chakra，Ant Design，Radix，或项目特定的组件目录
- **CSS框架**： `tailwind.config.*`，`styled-components` 主题，Bootstrap 导入，具有一致命名规则的 CSS 模块
- **排版**： HTML/CSS 中的字体导入，`@font-face` 声明，Google Fonts 链接
- **调色板**： 定义的颜色范围，品牌颜色文件，设计令牌导出
- **动画库**： Framer Motion，GSAP，anime.js，Motion One，Vue Transition 导入
- **间距/布局模式**： 一致的间距比例使用，网格系统，布局组件

使用平台的原生文件搜索和内容搜索工具（例如，Claude Code 中的 Glob/Grep）扫描这些信号。不要使用 shell 命令进行常规文件探索。

### 模式分类

根据检测到的信号，选择模式：

- **现有系统**（跨多个类别检测到4个以上信号）：顺从它。技能的美学观点（排版、颜色、动画）让位于既定系统。结构指导（组合、文案、无障碍性、验证）仍然适用。
- **部分系统**（检测到1-3个信号）：遵循现有设计；仅在未检测到约定的地方应用技能默认值。例如，如果配置了 Tailwind 但不存在组件库，则遵循 Tailwind 令牌，并应用技能对组件结构的指导。
- **绿野**（未检测到信号）：完全适用技能指导。
- **模糊**（信号矛盾或不明确）：在进行下一步之前询问用户。

### 询问用户

当上下文模糊时，使用平台的阻塞问题工具：Claude Code 中的 `AskUserQuestion`（如果其模式未加载，请先使用 `ToolSearch` 调用 `select:AskUserQuestion`），Codex 中的 `request_user_input`，Gemini 中的 `ask_user`，Pi 中的 `ask_user`（需要 `pi-ask-user` 扩展）。仅在 harness 中不存在阻塞工具或调用出错时（例如，Codex 编辑模式）才回退到在聊天中呈现选项——不是因为需要加载模式。永远不要无声地跳过。如果用户拒绝选择，则假设“部分”模式并保守进行。

示例问题：“我发现了 [检测到的信号]。我应该遵循您现有的设计模式还是创建独特的设计？”

## 第1层：构建前规划

在编写代码之前，编写三个简短陈述。这有助于建立一致性，并为用户提供在代码编写之前重新定向的检查点。

1. **视觉论点** -- 一句话描述情绪、材质和能量
   - 绿野示例：“简洁的编辑感，大量空白，衬线标题，柔和的大地色系”或“密集的数据驱动型仪表板，等宽字体强调，深色表面层级”
   - 现有代码库：描述*现有*美学以及新工作将如何扩展它

2. **内容计划** -- 页面上有什么以及顺序如何
   - 登录页面：英雄、支持、详情、CTA
   - 应用程序：主要工作区、导航、次要上下文
   - 组件：它有哪些状态，它传达什么

3. **交互计划** -- 2-3 个具体的运动想法，改变感觉
   - 不是“添加动画”，而是“英雄加载时的交错淡入，滚动时各部分之间的视差，卡片悬停时的缩放”
   - 在现有代码库中，仅描述添加的交互，使用现有的动画库

## 设计指导核心

这些原则适用于所有上下文类型。每个原则都让位于现有设计系统和用户指令，按照权威层级。

### 排版

- 选择独特且具有特色的字体。除非现有代码库使用它们，否则避免常用字体（Inter，Roboto，Arial，系统默认）。
- 最多两种字体，没有明确理由增加更多。将显示/标题字体与正文字体配对。
- *在检测到现有字体选择时让位于现有字体选择。*

### 颜色和主题

- 使用 CSS 变量承诺一个协调的调色板。一个主导颜色和锐利强调色比胆怯、均匀分布的调色板表现更好。
- 没有紫色在白色上的偏见，没有暗黑模式偏见。根据上下文在亮色和暗色之间变化。
- 默认一个强调色，除非产品已经有一个多色系统。
- *在检测到现有颜色令牌时让位于现有颜色令牌。*

### 组合

- 从组合开始，而不是组件。将第一个视口视为海报，而不是文档。
- 在添加 chrome（边框、阴影、卡片）之前，使用空白、对齐、比例、裁剪和对比度。
- 默认无卡片布局。卡片仅在它们作为用户交互的容器时允许（可点击项、可拖动单元、可选选项）。如果移除卡片样式不会损害理解，则不应是卡片。
- *所有组合规则都是默认值。用户可以覆盖它们。*

### 运动

- 为视觉主导型工作制作 2-3 个有意运动：一个进入序列，一个滚动链接或深度效果，一个悬停/揭示过渡。
- 如果项目存在现有的动画库，请使用它。
- 当未找到现有库时，使用框架条件默认值：
  - **CSS 动画**作为通用基线
  - **Framer Motion**用于 React 项目
  - **Vue Transition / Motion One**用于 Vue 项目
  - **Svelte 过渡**用于 Svelte 项目
- 运动应在快速录制中可见，在移动设备上流畅，并在整个页面中保持一致。如果纯粹装饰性，请移除。

### 无障碍性

- 默认使用语义 HTML：`nav`，`main`，`section`，`article`，`button`——不是所有内容都用 div。
- 颜色对比度满足 WCAG AA 最小值。
- 所有交互元素都有焦点状态。
- 当做得好的时候，无障碍性和美学并不矛盾。

### 图像

- 当需要图像时，优先考虑真实或逼真的摄影，而不是抽象渐变或虚假的 3D 对象。
- 选择或生成具有稳定色调区域的图像，用于文本叠加。
- 如果环境中提供图像生成工具，请使用它们来创建上下文相关的视觉，而不是占位符股票。

## 上下文模块

选择适合正在构建的内容的模块。在现有应用程序内部工作时，默认使用模块 C，无论功能是什么。

### 模块 A：登录页面和营销（绿野）

**默认部分顺序：**
1. 英雄——品牌/产品，承诺，CTA，一个主导视觉
2. 支持——一个具体功能、优惠或证明点
3. 详情——氛围、工作流程、产品深度或故事
4. 最终 CTA——转化，开始，访问或联系

**英雄规则（默认）：**
- 一个组合，而不是仪表板。全屏图像或主导视觉平面。
- 品牌优先，标题其次，正文第三，CTA 第四。
- 保持文本列窄，并锚定到图像的平静区域。
- 总共不超过 6 个部分，没有明确理由。
- 一个 H1 标题。一个主要 CTA 在视口上方。

**文案：**
- 让标题承载意义。支持文案通常是简短的一句话。
- 使用产品语言，而不是设计评论。UI 中没有提示语言或 AI 评论。
- 每个部分只有一个任务：解释、证明、加深或转化。
- 每个句子都应该有其存在的价值。默认情况下，少写文案，而不是多写。

### 模块 B：应用程序和仪表板（绿野）

**默认模式：**
- 平静的表面层级，强烈的排版和间距，少量颜色，密集但可读的信息，极少的 chrome。
- 围绕：主要工作区、导航、次要上下文/检查器、一个清晰的强调色用于动作或状态。
- 卡片仅在卡片是交互容器时使用（可点击项、可拖动单元、可选选项）。如果移除卡片样式不会损害理解，则不应是卡片。

**文案（实用，非营销）：**
- 优先考虑定向、状态和动作，而不是承诺、情绪或品牌声音。
- 部分标题应该说明该区域是什么或用户可以在哪里执行操作。好：“计划状态”，“搜索指标”。坏：“释放您的潜力”。
- 如果一个句子可以出现在登录页面的英雄中，请重写它，直到它听起来像产品 UI。
- 判定标准：如果操作员只扫描标题、标签和数字，他们能否立即理解页面？

### 模块 C：组件和功能（现有应用程序中的默认）

为添加到现有应用程序：

- 匹配现有的视觉语言。此模块是关于制作一个属于其中一部分的内容，而不是一个突出显示的内容。
- 继承间距比例、边框半径、颜色令牌和排版。
- 专注于交互质量：清晰的状​​态（默认、悬停、激活、禁用、加载、错误），状态之间的平滑过渡，明显的可供性。
- 一个新组件不应引入一个新的设计系统。如果现有应用程序使用 4px 边框半径，则不要添加一个具有 8px 的组件。

## 默认反对（可覆盖）

这些都是技能的主观意见。用户可以覆盖任何一项。

- 通用 SaaS 卡片网格作为第一印象
- 紫色在白色上的颜色方案，暗黑模式偏见
- 绿野工作中过度使用的字体（Inter，Roboto，Arial，Space Grotesk，系统默认）
- 英雄部分堆满统计数据、时间表、药丸集群、标志云
- 重复相同情绪陈述的不同措辞的部分
- 没有叙事目的的轮播
- 多个竞争的强调色
- 装饰性渐变或抽象背景取代真实视觉内容
- 听起来像设计评论的文案（“体验无缝集成”）
- 分屏英雄，文本位于图像的繁忙一侧

### 总是避免（质量底线）

这些都是真正的质量缺陷，没有用户会想要。

- 提示语言或 AI 评论泄漏到 UI 中
- 破坏性对比——文本在图像或背景上无法阅读
- 交互元素没有可见的焦点状态
- 当存在适当的 HTML 元素时，使用语义 div 汤汁

## 判定标准

在进行视觉验证之前进行快速自我审查。并非所有检查都适用于每个上下文——根据判断哪些是相关的。

- 品牌或产品在第一屏上是否 unmistakable？
- 是否有一个强烈的视觉锚点？
- 是否可以通过扫描标题来理解页面？
- 每个部分是否只有一个任务？
- 使用它们的地方是否真的需要卡片？
- 运动是否提高了层级或氛围，或者只是在那里？
- 如果所有装饰性阴影都被移除，设计是否感觉高端？
- 文案听起来像产品，而不是像提示？
- 新工作是否与现有设计系统匹配？（模块 C）

## 视觉验证

实施后进行视觉验证。这是一个理智检查，而不是像素完美的审查。一次通过。如果有明显的问题，请修复。如果看起来很牢固，请继续。

### 工具偏好级联

使用第一个可用的选项：

1. **现有项目浏览器工具**——如果 Playwright、Puppeteer、Cypress 或类似的已经在项目的依赖项中，请使用它。不要引入新的依赖项只是为了验证。
2. **浏览器 MCP 工具**——如果代理的环境中提供浏览器自动化工具（例如，claude-in-chrome），请使用它们。
3. **agent-browser CLI**——如果其他选项不可用并且安装了 `agent-browser`，请使用它。如果未安装，请通知用户：“`agent-browser` 未安装。运行 `/ce-setup` 安装所需依赖项。” 然后跳到下一个选项。
4. **心理审查**——如果无法访问浏览器（无头 CI、无安装权限），则将判定标准作为自我审查应用，并注明跳过了视觉验证。

### 要评估的内容

- 输出是否与构建前计划中的视觉论点匹配？
- 是否有明显的视觉问题（破坏的布局、无法阅读的文本、缺失的图像）？
- 它是否看起来像上下文模块预期的样子（登录页面感觉像登录页面，仪表板感觉像仪表板，组件适合其周围环境）？

### 范围控制

一次迭代。拍一张屏幕截图，根据判定标准进行评估，修复任何明显问题，然后继续。将屏幕截图包含在交付物中（PR 描述、对话输出等）。

对于多次迭代（多次屏幕截图-评估-修复）的改进，请参阅 `ce-design-iterator` 代理。

## 创造力

这项技能提供结构，但目标是独特且避免 AI 拙劣的作品——而不是公式化输出。

对于绿野工作，坚持大胆的美学方向。考虑语气：残酷极简、极繁、复古未来主义、有机/自然、奢华/精致、俏皮、编辑、残酷主义、艺术装饰、柔和/粉彩、工业——或者创造一个适合上下文的东西。有无数种风味。使用这些作为灵感，但设计一个与项目真实相符的东西。

问：什么让它难忘？什么是一个人会记住的东西？

根据美学愿景匹配实现复杂性。极繁设计需要复杂的代码、广泛的动画和效果。极简设计需要克制、精确，以及对间距、排版和微妙细节的仔细关注。优雅来自执行愿景的质量，而不是强度。
