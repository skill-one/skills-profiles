# 产品策略

**当前年份为 2026** - 在文档中标注日期时使用。

`ce-strategy` 负责编写和维护 `STRATEGY.md` 的一部分 - 这是位于仓库根目录的项目文档，它记录了项目的本质、服务对象、成功方式以及团队的投资方向。该文件与其他工具和人员共享；此技能仅编写名为 `references/strategy-template.md` 的部分。下游技能在文件存在时读取它：`ce-ideate`、`ce-brainstorm` 和 `ce-plan` 用于判断哪些工作符合策略；`ce-product-pulse` 用于获取产品名称和关键指标；`ce-dogfood` 用于获取主要用户画像。这些技能解析的合同是文件的前置内容键和此技能的章节标题 - 保持每个章节的这些内容；一个现有章节已经包含的意义将被合并到其中 (`references/update-run.md`)。

**完成标准：** `STRATEGY.md` 存在于仓库根目录，并且用户已经看到了将要编写的内容并进行了编辑。对于此技能格式下的文件，所有必需章节都从未被反对的答案中填写（或明确地推迟到链接的遗留文档），并且文件与 `references/strategy-template.md` 匹配。对于任何其他格式的文件，完成标准是用户批准的最小编辑，文档结构保持不变。如果用户在两轮中无法完善某个章节，则按原样编写并在聊天中命名为值得回顾 - 这是一个完成的运行，而不是被阻塞的运行。

## 边界

- **锚定，而非规划。** 策略是产品是什么以及为什么。功能属于 `ce-brainstorm`，时间表和优先级在问题跟踪器中，实施计划在 `ce-plan` 中；不要让它们蔓延到文档中，也不要更新跟踪器或协调进行中的工作。
- **用户回答；仓库仅提供问题的基础。** 使用证据提出更尖锐的问题，而不是填写章节。不要从仓库中推导策略。
- **短小是特征。** 拒绝扩展，而不是添加章节。
- **记录哪些指标重要以及它们存放的位置**，而不是它们今天读取的内容。
- **意义是合同；形状属于创建文档的人。** 一个完全由此技能 (`references/update-run.md` 验证) 维护的文件在每次写入时都保持内部格式：标题重命名，章节按模板的当前顺序排列，提供缺失的必需章节。不要因为文件原则上被共享就将其视为多作者文件。任何其他形状的文件（手写或来自其他工具）都按意义读取并在其自身形状和语境内编辑：不重构为模板，不接受未经邀请的前置内容或标题。无论如何，永远不会编辑的两件事是：一个带有作者批准标记的章节（例如 `<!-- <tool>: author-approved 2026-07-10 -->`），以及用户不拥有的文档。对于这些，报告冲突，或编写一个链接到它的单独文件。定向更新将保留其他所有章节的内容完全不变。该章节的位置遵循相同的所有权测试：一个仅拥有的文件采用模板的顺序；一个多作者文件永远不会重新排序。`references/update-run.md` 定义了其余部分，并且在编辑现有文件之前是必读的。

## 提问和路由

通过当前工具列表中已有的主机阻塞问题工具一次只问一个问题。按能力匹配；永远不要探测用户界面工具来发现它。只有在没有此类工具列出或真实问题调用出错时，才回退到可见聊天表面的编号选项。永远不要无声地跳过问题。

此技能被调用的任何参数——当前提示或对话中由用户或调用技能提供的——都是焦点提示：要重新审视的章节 (`metrics`、`positioning`、`tracks`；旧名称如 `approach` 或 `who it's for` 映射到当前章节）或范围提示。如果没有，则开放式进行，并让文件状态决定路径。

## 阶段 0：锚定和路由

阶段 0 生成一个仓库模型并决定下一个阶段运行什么，无论 harness 读取什么。`references/grounding.md` 是一个非可选加载：它包含完整源列表、争议问题的措辞和焦点提示。

**仓库模型** 是你对这个产品的工作理解。如果存在，则读取 `STRATEGY.md`。从其声明意图和结构中获取产品的本质——README、`CONCEPTS.md`、`docs/`、同辈文档（如 `PRODUCT.md`）、代码组织围绕的内容——并将这种读取绑定到“这是什么以及为谁服务”而不是整个仓库的分析。从最近的提交或 PR 中获取当前关注的点。注意力仅影响 Tracks 问题，并且在更新运行中存在陈旧性；如果它与声明意图不一致，那是一个用户的问题，而不是结论。在第一个问题之前在聊天中显示模型：三到五行关于你认为产品是什么、它似乎为谁服务以及注意力在哪里，每行都标明来源，并邀请更正。如果模型没有提供产品的名称，请在这里询问——模板的前置内容和标题需要它。一个没有实质性内容的仓库是正常路径：用一句话说明，并运行无锚定的访谈。

**下一个阶段** 由文件状态用一句话宣布：没有文件 -> 阶段 1（"未找到策略文档 - 让我们编写它。"），在 `references/grounding.md` 中适用遗留同辈提议时；文件存在 -> 阶段 2（"找到现有策略 - 让我们审查和更新。"）。

## 阶段 1：首次访谈

在第一个问题之前读取 `references/interview.md` - 一个非可选加载。开场问题、反对规则、反模式示例、质量标准、每个主机的阻塞问题工具以及两轮限制都生活在这里；从记忆中即兴发挥会产生一个被动的转录，而不是策略文档。

按此顺序运行访谈（文档本身遵循模板的顺序；边界在压力测试之后提出，其内容来自边界的内容）：

1. 目的
2. 定位
3. 用户
4. 关键指标
5. 轨道
6. 压力测试
7. 边界（始终编写）
8. 里程碑（可选）
9. 品牌（可选）

当每个章节都被捕获时，读取 `references/strategy-template.md`，填写它，在聊天中展示完整草稿，提供一轮编辑，然后编写 `STRATEGY.md`。

## 阶段 2：更新运行

首先读取 `references/update-run.md` - 一个非可选加载，在摘要、漂移检查或任何问题之前。它决定如何提出漂移候选，哪个章节被重新审视，以及什么保持不变。更新运行用 3-5 行总结文件当前状态，并命名仓库模型建议为陈旧的章节作为候选而不是裁决。然后重新审视焦点提示命名的章节，或用户在询问时选择的章节。用户可以选择任何章节；首先列出漂移候选，作为建议而不是唯一选择。其他所有章节的内容保持不变，其位置遵循 `references/update-run.md` 中的所有权测试。问题和反对意见仍然来自 `references/interview.md`，就像这是一个首次运行一样应用。

## 阶段 3：下游交接

用一句话说明文件的位置，以及 `ce-ideate`、`ce-brainstorm` 和 `ce-plan` 在它们的下一次运行中将其作为基础。如果还没有下游技能运行到这里，建议 `ce-ideate` 或 `ce-brainstorm` 作为下一步。
