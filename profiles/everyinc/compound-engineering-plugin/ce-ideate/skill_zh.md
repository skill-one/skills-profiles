# 生成改进建议

**当前年份是2026年** — 在编写文档和检查近期成果时使用此年份。

`ce-ideate` 在 `ce-brainstorm` 之前运行。这项技能回答“哪些想法值得探索？” `ce-brainstorm` 接着回答选定想法应代表什么。`ce-plan` 回答如何构建它。

**已完成：** 当根目录存在时，排名靠前的构思成果会写入 `<root>/ideation/`，否则写入 CE 临时路径。每个生成想法都经过批判，幸存者被解释说明。用户将获得下一步操作菜单。没有要求、计划或代码。

## 边界

1. **构思前先进行基础工作。** 没有任何与仓库分离的建议。
2. **生成多个、批判全部、仅解释幸存者。** 在批判任何内容之前生成完整候选列表。拒绝必须是明确的，并附带原因；这不是乐观的排名。
3. **将用户引导至行动构思。** 从构思输出直接跳转到计划是禁止的。
4. **永不针对未识别的主题进行派遣。** 通过当前工具列表中已有的主机阻塞问题工具进行询问（按能力匹配，而不是按特定主机名称）。当前工具列表中的存在证明该工具存在；永不调用面向用户的问题工具来发现其是否存在。如果匹配的工具已列出但未加载，则使用主机的工具发现原语加载该能力 — 不要搜索其他主机的工具名称。如果列表中没有此类工具，则在用户可见表面提供编号选项。永不无声地跳过问题。保留“让我惊喜”作为真实选项，以及一个可干净退出的取消选项。不要询问解决方案方向、约束、受众、语气或成功标准；`ce-brainstorm` 会询问这些。如果超过3个问题，构思流程就是错误的。
5. **永不打印内部分类标签。** 标签 `repo-grounded`、`elsewhere-software` 和 `elsewhere-non-software` 仅决定派遣哪些代理。用主题自己的话向用户描述该模式。
6. **基础工作失败时发出警告并继续进行。**
7. **在派遣前向用户显示成本线。**

**焦点提示** 是此运行被用户或调用技能传入的可选上下文。此技能的其余部分称其为 `{focus_hint}`。

## 成果根目录

成果存放在 `<root>/ideation/` 下，学习成果从 `<root>/solutions/` 中读取。仅在您准备编写这些路径之一时解析 `<root>`，并且在模式分类之前永不解析 — 未知的或无仓库运行写入临时目录，并且永远不需要它。将解析的路径传递给子代理，而不是配置。

<!-- ce-docs-root:start -->
**在编写任何成果路径之前解析 CE 成果根 `<root>`。**

- **读取** `docs_root` 从 `<repo-root>/.compound-engineering/config.yaml` 仅 (`<repo-root>` = `git rev-parse --show-toplevel`)。不要从 `config.local.yaml` 读取它。未设置 -> `<root>` 是 `docs`，与之前完全相同。
- **验证** 设置的值：一个相对仓库的目录，其真实路径（解析符号链接后）仍位于仓库内，并且既不是仓库根目录也不在 `.git/` 下。否则以错误命名 `docs_root` 和值停止 — 永不回退到 `docs`。
- **使用** `<root>` 作为唯一成果位置：如果不存在则创建它，使用此技能自己的子目录组成每个路径为 `<root>/<subdir>`，并且永不也读取 `docs`。

## 阶段 0：恢复和范围

此阶段名称的两个读取都是必需的，即使主题、模式和格式看起来很清晰。这两个引用定义了恢复检查、格式决策和范围分类。在此之前，这里没有任何内容被解析。

**输出模式是排他的。** 运行产生 HTML（`.html`）或 markdown（`.md`），从不两者兼有。优先级从此提示中的请求开始，通过声明的用户偏好和配置 (`ideate_output:`)，降至 `html` 默认；无头运行以相同方式解析格式，没有任何管道覆盖。

每当解析格式时，都要读取 `references/output-mode.md`。读取是必需的。它定义了每个决策步骤，以及决定此运行是否更新现有文档而不是写入新文档的30天近期工作检查。

<!-- ce-config-layers:start -->
**从两个仓库文件解析普通 CE yaml 键。**

- **读取** `<repo-root>/.compound-engineering/config.local.yaml`，然后 `config.yaml` (`<repo-root>` = `git rev-parse --show-toplevel`)。跳过缺失文件。Gitignore 不改变解析。
- **以第一个活动的值（非注释）获胜。** 对于标量，空值是未设置的；无效值继续到下一层，然后是技能默认值。对于列表和映射，存在的键 — 包括空列表或映射 — 会替换整个键。
- **不要** 使用此规则用于 `docs_root` — 该键仅存在于 `config.yaml`。
<!-- ce-config-layers:end -->

**非软件路由。** 一个不是关于软件的主题运行其他模式基础工作，而不是仓库扫描。然后它遵循 `references/universal-ideation.md` 而不是阶段 2 的框架和阶段 5 的菜单。可交付成果仍然会自动写入。

**阶段 0 检查。** `references/scope-gates.md` 定义了每个阶段 0 检查，以及惊喜和战术运行中的变化。当主题无法识别时询问。`go deep` 比战术信号更优先。

## 阶段 1：模式感知基础工作

在派遣任何基础工作代理之前，读取 `references/grounding.md`。读取是必需的。该引用定义了本阶段的所有派遣，包括在两个派遣块之前运行的路由测试。基础工作并行运行，在**前台**。

草稿存储在有效用户的私人 CE 根目录下：`/tmp/compound-engineering-<uid>` 当可用时，否则是验证的 `$TMPDIR` 回退，并且永不 `.context/`。生成一个 8-hex `<run-id>` 并重用它作为缓存和每个检查点。

## 阶段 1.5：主题表面分解

在派遣框架之前，将主题分解为 3-5 个正交的**轴** — 要思考的主题方面。读取 `references/decomposition.md`。惊喜模式是唯一跳过此阶段的案例。该文件自己的标准决定主题是否太小而无法分割，因此在该读取之后做出该判断。将轴列表或跳过原因追加到基础工作摘要下 `Topic axes`。证据侦察员仅限于仓库模式。

## 阶段 2：发散构思

在构建任何派遣提示之前，读取 `references/divergent-ideation.md`。舰队、框架和生成规则仅存在于那里。当其合并、综合和轴覆盖步骤完成时，继续 `references/post-ideation-workflow.md`，它将其命名为下一个必需的读取。
