<极其重要>
这是一个设计规范技能，而不是实现技能。不可协商的规则：
1. 不要从这个技能编写生产 UI 代码。产出规范 + 锁定的设计语言，并将构建委托给工程代理。我们拥有设计规范；代理实现它。
2. 在指定屏幕之前，承诺一个独特的审美身份，并通过反事实默认测试：如果你会为任何类似的简报生产这个相同的外观，它就是默认的——改变它。
3. 通过名称禁止 AI 滑稽 (`references/anti-slop.md`)。滑稽测试控制工作：如果有人可以说“AI 制作的”而没有疑问，它就失败了。
4. 在 `DESIGN.md` 中锁定设计语言，并将每个屏幕绑定到它。身份内的变化，绝不之间。每次后续功能或会话首先重读 `DESIGN.md`。
5. 如果用户提供灵感链接，使用 `browse` 技能访问它们并综合——永远不要克隆单个参考，也绝不继承它的滑稽。
6. 在交接之前运行设计预飞行门禁。如果单个框不能诚实地勾选，它就没有完成。
7. 保持使我们与众不同的严谨性：状态覆盖范围、流程/边缘情况以及可访问性——永远不要跳过它们。
</极其重要>

# frontend-design-ui-ux

## 输入

- `$request`：要设计的功能、页面、组件或 UX 问题——加上可选的灵感 URL。

## 目标

产出独特、一致且可构建的设计包——一个委托的工程代理直接实现的规范。所有工件都在 `.ulpi/design/` 下编写：

- `.ulpi/design/DESIGN.md` — 锁定的设计语言（身份、调色板、类型、比例、签名、声音、选择的设计系统）。项目范围的；每次会话首先重读。
- `.ulpi/design/<feature>.md` — 每个功能的规范：用户流程 + 状态、组件规范和构建交接（目标代理 + 接受标准）。绑定到 `DESIGN.md`。

## 步骤 0：发现和输入

解决：目标用户 · 产品目标 · 设备/使用上下文 · 现有的设计系统或品牌限制 · 可访问性预期。问一次：**“你有欣赏的参考网站或设计吗？粘贴 1–4 个 URL。”**

如果问题定义不明确，请提问——但最多几个集中的问题；永远不要长时间的审问。**成功标准**：问题用用户 + 产品术语进行框架化，并且灵感链接（如果有）被收集。

## 步骤 1：灵感摄入（可选）

如果用户提供了链接，使用 `browse` 技能访问每个链接，提取其设计 DNA（类型、颜色、形状、间距、布局），并为每个网站提炼一条 DNA 笔记。综合它们——永远不要克隆一个。如果 `browse` 不可用或链接无法访问，请要求用户描述氛围并继续。

加载 `references/inspiration-intake.md`。**成功标准**：每个参考被简化为可重用的 DNA，知道要拿什么和要拒绝什么——或者干净地跳过。

## 步骤 2：设计阅读和审美方向

以一个永远不会发布模板化外观的设计负责人身份来处理。在任何标记之前消除默认审美反射：

- 发出一个一条线的 **设计阅读**（感觉 + 赌注）。
- 从 `references/anti-slop.md` 中的菜单承诺一个命名的审美方向；从简报中为其辩护（如果有任何灵感 DNA）。
- 运行 **反事实默认测试**：这个外观会是任何类似简报的你的答案吗？如果是，改变它。
- 可选地设置品味旋钮 (`design_variance` / `motion_intensity` / `visual_density`，1–10) 并 **根据方向匹配复杂性**（极简主义 → 精致；极简 → 节制、精确、空白）。

加载 `references/anti-slop.md` 以获取方向菜单、模式词汇和命名禁止。**成功标准**：一个承诺的、特定于简报的方向，它不是一个通用的默认值。

## 步骤 3：推导并锁定设计语言 → 编写 `.ulpi/design/DESIGN.md`

确定 **注册**（品牌 vs 产品），对于 `product`，确定要构建的 **设计系统**（见 `references/design-system-routing.md`）。然后推导并锁定身份：调色板（OKLCH、调色中性、60-30-10、WCAG 检查）、类型角色在对比轴上配对、一个间距/半径/运动比例、**签名** 和声音。写入 `.ulpi/design/DESIGN.md`——每个屏幕都绑定到的真实性来源。

加载 `references/design-language-lock.md`（工件 + 锁定规则）、`references/design-tokens-template.md`（推导方法）和 `references/design-system-routing.md`（简报→系统映射）。**成功标准**：一个完整的、锁定的 `.ulpi/design/DESIGN.md`；没有通用的默认身份。

## 步骤 4：建模流程和状态

记录主要旅程、分支/决策和完整的状态模型——加载、空、部分、成功、错误——加上边缘情况（刷新、会话过期、后退、离线）。写入 `.ulpi/design/<feature>.md`。使用 `references/user-flow-template.md`。**成功标准**：行为在状态中覆盖，而不仅仅是快乐路径。

## 步骤 5：指定组件和交互规则

对于每个组件定义：目的、变体、props/数据、状态、交互反馈、响应行为和可访问性（ARIA、键盘、屏幕阅读器、焦点）。将每个视觉值绑定到 `.ulpi/design/DESIGN.md`；追加到同一 `.ulpi/design/<feature>.md`。使用 `references/component-spec-template.md`。**成功标准**：委托的工程师可以在不猜测的情况下构建它，并且没有身份漂移。

## 步骤 6：设计预飞行门禁

运行 `references/design-preflight.md` 从头到尾——身份锁定、反滑稽、状态覆盖范围、可访问性、布局工艺、认知负荷和评分的自我批评。几个项目是机械计数。修复任何失败的框或任何评分 ≤ 2 的轴，用一句话说明你改变了什么以及为什么（修订并辩护），然后重新运行。**成功标准**：每个框都被勾选，并且没有批评轴 ≤ 2。

## 步骤 7：构建交接（委托构建）

在 `.ulpi/design/<feature>.md` 的末尾最终确定委托简报：目标工程代理、选择的 `design_system`（+ 其设置笔记）和接受标准——并指示：*"精确实现这个规范。用我们锁定的标记主题设计系统；不要重新设计或重新实现其组件。"* 构建被委托给代理；这个技能永远不会编写 UI。

### 代理选择

| 标准 | 目标代理 |
|------|---------|
| 服务器端渲染 / SEO / 应用路由 / 服务器操作 | `nextjs-senior-engineer` |
| 纯 SPA / 客户端仅 / CLI 网页 UI / Electron-Tauri | `react-vite-tailwind-engineer` |
| 静态网站没有 SSR | 任何（问用户） |
| 不明确 | 问用户 |

**成功标准**：一个委托的代理可以拿起 `.ulpi/design/DESIGN.md` + `.ulpi/design/<feature>.md` 并直接实现它，而无需重新设计。

## 指导方针

- 不要从这个技能实现生产 UI 代码；产出规范并交接。
- 不要发布一个通用的默认身份——根据简报推导调色板和类型；滑稽测试控制输出。
- 不要让屏幕从 `DESIGN.md` 漂移：身份内的变化，绝不之间。
- 不要克隆单个灵感参考，也绝不继承它的滑稽。
- 不要跳过可访问性、状态覆盖范围或响应行为——它们是我们的优势。
- 不要在需要具体工件时产出模糊的设计散文。
- 如果 `browse` 或图像工具缺席，不要阻塞——优雅降级并从简报继续。

## 何时加载参考

- `references/inspiration-intake.md` — 使用 `browse` 访问参考链接并提取 DNA（步骤 1）。
- `references/anti-slop.md` — 方向菜单、命名的 AI 滑稽禁止和滑稽测试（步骤 2、3、6）。
- `references/design-language-lock.md` — `DESIGN.md` 工件和一致性锁定规则（步骤 3）。
- `references/design-system-routing.md` — 简报→设计系统映射 + 诚实规则（步骤 3，产品注册）。
- `references/design-tokens-template.md` — 每个简报的颜色/类型推导方法 + 中性比例（步骤 3）。
- `references/user-flow-template.md` — 用户旅程和接受流程（步骤 4）。
- `references/component-spec-template.md` — 组件简报和接口合同（步骤 5）。
- `references/design-preflight.md` — 交接前的质量和一致性门禁（步骤 6）。

## 输出合同

在 `.ulpi/design/` 下编写并报告：

1. 设计阅读 + 承诺的审美方向（以及灵感 DNA，如果有）
2. `.ulpi/design/DESIGN.md` — 锁定的设计语言（注册、设计系统、调色板、类型、比例、签名、声音）
3. `.ulpi/design/<feature>.md` — 流程和状态
4. — 组件规范（同一文件）
5. 预飞行结果（每个框都被勾选，没有批评轴 ≤ 2）
6. 构建交接 — 目标代理 + 设计系统 + 接受标准（“精确实现这个；不要重新设计”）
