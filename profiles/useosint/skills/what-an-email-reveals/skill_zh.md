# 一封电子邮件揭示的信息

电子邮件地址通常是调查中最有价值的筛选器：它包含姓名、域名、账户历史记录和入侵痕迹。初学者错误是试图证明该地址存在。存在是最不有趣的事情，它是最难被动建立的事情，而建立它的技术会暴露你。首先分析结构和痕迹；将验证视为一种附加功能。

永远不要将邮件发送到主题作为研究技术。

## 第 1 步 — 授权范围

阅读 [../../ETHICS.md](../../ETHICS.md)。记录主题、目标、边界内筛选器、边界外操作和管辖权。预先决定是否授权*交互式*探测——SMTP 会话、密码重置流程、注册表单枚举——这通常是禁止的。以下内容除非另有说明，否则都是被动的。

**完成时**：范围已记录，交互式探测决策已记录。

## 第 2 步 — 解析和验证

有三件事被称为“电子邮件验证”。它们是不可互换的。

| 方法 | 它证明了什么 | 成本 |
|---|---|---|
| 语法 | 字符串可以是地址 | 免费、被动、无法证明邮箱信息 |
| 域 / MX | 域存在并接受邮件 | 免费、被动、`dig MX example.com` |
| SMTP `RCPT TO` 探测 | 服务器声称邮箱存在 | 交互式、通常被阻止或被欺骗，并且会被记录 |

执行前两种。第三种——打开 SMTP 会话并发出 `RCPT TO` 查看服务器是否接受接收者——是与主题的邮件基础设施的实时对话，从你的 IP 地址。它会被记录，你的地址范围会被列入黑名单，并且对于**全接收域**它是无用的：全接收域接受每个接收者，所以每个地址“都存在”。灰度列表、陷阱和接受后反弹策略会产生同样的无用答案。第三方验证 API 大多封装了相同的探测；暴露转移到供应商，准确性限制不会改变。

然后解析本地部分。`first.last`、`flast`、`firstl`、`f.last` 都暗示一个姓名，在公司域名上是一个全公司范围的惯例——参见 [reference/corporate-formats.md](reference/corporate-formats.md)。

**Gmail 规范化很重要**。Gmail 忽略本地部分的点以及 `+` 后面的所有内容。`j.doe+news@gmail.com`、`jdoe@gmail.com` 和 `jd.oe@gmail.com` 是同一个邮箱。后果：在两次泄露中看起来不同的地址可能是同一个人，并且 `+tag` 经常命名地址被分配到的服务，这是关于主题在哪里持有账户的自由情报。并非所有提供者都这样做——在假设之前先检查。

**完成时**：地址被评定为有效/无效/未知，规范化形式被记录，姓名假设被写下来。

## 第 3 步 — Gravatar

Gravatar 通过将地址转换为小写、修剪后的地址的 MD5 哈希来映射地址到一个公共头像。计算哈希并请求头像；返回的图像意味着该地址已注册该服务，关联的公共资料可以包含显示名称、位置、链接到其他账户，以及其他平台上的验证账户。

```bash
printf '%s' "jdoe@example.com" | tr 'A-Z' 'a-z' | md5sum
```

免费、被动、无需密钥。运行头像通过 `find-the-original-image`。将默认回退图像视为“没有 Gravatar”，而不是“地址无效”。

**完成时**：检查了 Gravatar 存在性并捕获了任何资料字段。

## 第 4 步 — 这个地址在哪里注册

诚实的立场：通过电子邮件进行可靠的账户枚举是一个*预言机*问题。密码重置和注册表单会披露地址是否已注册，这正是为什么工具存在以自动化它们——这也是为什么这样做是交互式的、通常违反服务条款，并且可能通知（重置请求可以邮件给主题）。标记它，明确授权它，或者不要这样做。

无成本的被动替代方案：

- 用间谍的方式在引号中搜索完整地址，以及单独的本地部分。
  简历、会议程序、邮件列表存档、`WHOIS` 历史记录和提交的配置文件充满了地址。
- 运行 `what-leaked-about-you`。泄露成员资格是回答“这个身份使用了哪些服务”的最佳答案，并且是回顾性的而不是交互式的。
- 将本地部分推入 `hunt-a-handle` 作为用户名种子。
- 通过 `secrets-in-git-history` 在代码托管中搜索提交元数据中的地址。

**完成时**：服务列表已汇编，并且每个条目都标记了被动或交互式的来源。

## 第 5 步 — 如果你有消息，请阅读头信息

仅适用于您合法拥有消息时。头信息是电子邮件停止成为筛选器并成为证据的地方。

从下往上阅读 `Received:` 链：最底部的是最早的跳转，并且源主机在那里，除非发送平台删除了它。第一个您信任的服务器以下的所有内容都可以被完全伪造。

- `Message-ID` — 域名部分和 ID 的形状通常可以识别发送平台或邮件客户端，即使可见头信息是装饰性的。
- `Authentication-Results` — 接收服务器的 SPF、DKIM 和 DMARC 判决。DKIM `pass` 是头信息块中最强的事情：它是内容上的加密签名，所以它会在转发声明中存活下来。
- `X-Mailer` / `User-Agent` — 客户端指纹，经常被批量邮件工具保留。
- `Return-Path` vs `From` — 不匹配对于邮件列表是正常的，在直接通信中是可疑的。

按字段指南：
[reference/header-fields.md](reference/header-fields.md)。

**完成时**：已识别原始基础设施或明确声明为无法恢复。

## 哪里会出错

- **全接收域完全击败验证**。所有内容都验证。通过测试一个您编造的地址来检测一个；如果随机字符串验证，则该域的所有结果都是无意义的。
- **一次性和转发服务**。一次性域名意味着地址从未打算持久；中继和别名服务（包括提供商提供的私有中继地址）意味着可见地址是一个围绕您无法看到的邮箱的包装。两者都限制了地址可以走多远——早期识别它们，而不是浪费时间。
- **角色地址** (`info@`、`sales@`、`admin@`) 属于功能，而不是人。将一个归因于个人是最常见的严重错误，在电子邮件 OSINT 中，并且它会在报告中存活下来，因为它看起来像是一个发现。
- **推断地址是假设**。从公司模式中推导出 `j.doe@company.com` 给出一个合理的地址，而不是一个真实的地址。标记为推断，永久。
- **泄露数据不是当前所有权的证明**。地址会被放弃，由提供商回收，并且会被重新分配给同一公司的新的员工。
- **转发与伪造无法区分**。邮件列表和安全网关以看起来像篡改的方式重写头信息。

## 置信度评级

- **确认** — 来自地址的 DKIM 通过消息，或者地址由主题发布在他们对源控制的平台上，或者经过验证的 Gravatar 资料与单独确认的身份匹配。
- **可能** — MX 有效，出现在泄露中并伴有佐证筛选器，并且本地部分与主题的姓名模式匹配。
- **未确认** — 从公司格式推断，或在一个聚合器或组合列表中找到，没有第二个来源。
- **拒绝** — 证明是全接收域且没有支持证据，一个已知的可一次性域名且没有链接活动，或者角色地址归因于个人，没有基于域的理由。

## 工作示例

给定 `j.okonkwo@northwind-eng.example`。`dig MX` 返回托管提供者的记录——该域名接收邮件。Gravatar：没有头像，所以没有资料转换。

会议 PDF 中的两个员工地址是 `t.mwangi@` 和 `s.aldridge@`，所以惯例是 `first-initial.lastname`。这使得 `j.okonkwo@` 结构上是一致的——关于格式的证据，而不是关于这个人存在的证据。不运行 SMTP 探测；交互步骤在此范围内之外。

死胡同：`what-leaked-about-you` 对该地址返回无结果，最初读作“不是真实用户”。重新运行针对从代码托管提交中恢复的 Gmail 规范化个人地址，给出三个泄露，其中一个是一个开发者论坛，其中包含用户名 `sunfish_ada`。该用户名转到 `hunt-a-handle`。公司地址保持评定为推断；个人地址是工作筛选器。

## 转换点

| 新筛选器 | 技能 |
|---|---|
| 从本地部分或 Gravatar 获取姓名 | `find-anyone` |
| 本地部分作为用户名 | `hunt-a-handle` |
| 电子邮件域名 | `who-owns-this-domain`、`recon-a-domain-passively` |
| 从公司域名获取雇主 | `x-ray-a-company` |
| 泄露出现 | `what-leaked-about-you` |
| 提交或配置中的地址 | `secrets-in-git-history` |
| 头信息中的原始 IP | `find-exposed-servers` |
| Gravatar 或资料头像 | `find-the-original-image` |
| 在转储或频道中发布的地址 | `find-leaks-in-the-wild` |

## 法律和 ToS 注意事项

SMTP 探测和密码重置枚举是交互式的，通常被服务条款禁止，并且在某些司法管辖区可能被认为是对系统的未经授权的询问。在使用它们之前，请书面授权它们。根据 GDPR 和英国数据保护法，电子邮件地址本身就是个人数据——只收集目标需要的内容，加密存储，并设置与案件文件一起的删除日期。您拥有的消息内容可能包含独立的保密或特权义务，与 OSINT 问题无关。

## 第 6 步 — 报告

运行 `write-the-intel-brief`。声明有效性和如何建立，域名是否是全接收域，服务列表及其被动/交互来源，泄露暴露，以及身份归因及其置信度等级。

**完成时**：每个地址都被标记为观察到或推断，并且没有推断地址被声明为事实。
