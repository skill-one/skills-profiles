# git历史中的秘密

一个仓库是三种智能产品：真实电子邮件地址的人员列表、组织基础设施的地图，以及无人打算发布的凭证存储库。昂贵的错误是扫描工作区。从HEAD中删除的秘密将永远留在历史中，从分支中删除的提交可以通过分叉网络访问——只扫描已检出的内容，你正在搜索秘密确实被删除的地方。

## 你拥有的，以及如何开始

| 你拥有 | 从...开始 | 为什么 |
|---|---|---|
| 组织名称 | 公开组织成员，然后是他们个人的仓库 | 公司仓库受到审查；个人仓库不受审查 |
| 开发者的姓名或昵称 | 跨其仓库的提交电子邮件 | 提供其他任何东西都给不了你的电子邮件 |
| 提交电子邮件 | 跨主机反向搜索；解析任何noreply ID | 将跨组织和平台的账户链接起来 |
| 疑似的凭证泄露 | 在镜像克隆上运行两个扫描器，所有引用 | 仅HEAD扫描完全错过了要点 |
| 特定的字符串——主机名、密钥前缀 | 在所有引用中用`git log -S`探针 | 告诉你它何时进入以及何时离开 |
| 活域名 | 检查暴露的`.git`——参见法律声明 | 如果授权，从Web服务器获取完整历史 |
| 仅仅是一个公司网站 | 搜索该组织内部域名 | 找到与组织没有明显联系的仓库 |

## 提交电子邮件泄露

Git在每个提交中记录一个作者身份，这是自我声明的而不是经过验证的。这有利有弊：电子邮件可以轻易伪造，而且它们也是代码托管身份和真实邮箱之间最可靠的公共链接。

```bash
git clone --mirror https://github.com/example-org/example-repo.git repo.git
git --git-dir=repo.git log --all --format='%an <%ae>' | sort -u
```

GitHub的Web界面不显示提交电子邮件，这导致人们认为它们是隐藏的。它们不是。将任何提交URL追加`.patch`以获取邮件格式补丁，其`From:`头包含作者姓名和电子邮件；API在`commit.author.email`下返回相同内容。

```bash
curl -s https://github.com/example-org/example-repo/commit/<sha>.patch | head -5
curl -s https://api.github.com/repos/example-org/example-repo/commits/<sha> | jq .commit.author
```

**noreply模式是值得充分理解的部分。** 启用电子邮件隐私的用户提交为`username@users.noreply.github.com`，或在新形式中为`12345678+username@users.noreply.github.com`。第二种形式泄露了账户的**数字用户ID**，它是不可变的，并且会存活于账户进行的任何重命名，因此旧提交会指向今天持有它的人：

```bash
curl -s https://api.github.com/user/12345678 | jq '.login, .created_at'
```

这击败了重命名：一个在很久以前就被废弃的昵称下的旧提交指向了用户的当前身份。在主题方面的互补失败是启用电子邮件隐私*在提交多年之后*——在此日期之前的每个提交都包含真实地址，因此拉取所有历史记录的作者列表。

## 将组织枚举为社交图谱

公司仓库受到审查。个人仓库不受审查，开发者将相同的基础设施放在两者中。枢轴是组织到人到个人账户。

公开组织成员是自愿加入的，因此是不完整的，所以进行三角测量：`https://api.github.com/orgs/<org>/public_members`给出选择可见的成员，而跨每个组织仓库的作者列表给出实际提交的每个人，包括那些从未公开过的人以及那些已经离开的人。

从每个人那里拉取仓库、Gist、关注者、关注、星标和监视的仓库。星标和关注是未被充分利用的：没有人为了隐私而管理它们，并且它们比任何个人资料字段更诚实地映射了兴趣、雇主、副项目和职业关系。一群开发人员都星标了同一个看起来很内部的工具，他们是同事。

公开活动事件覆盖一个较短的近期窗口，但公开事件流也作为历史存档数据集发布，将分析扩展回数年。聚合的提交时间戳给出工作时间和时区。

## 代码搜索及其真实限制

主机代码搜索在公共仓库中查找字符串。搜索只有这个组织会写的：内部主机名、私有包名、云账户ID、电子邮件域。公司名称找到营销文案；内部域名找到基础设施。

限制比语法更重要，因为每个都是沉默的差距。代码搜索仅覆盖**默认分支**——没有历史记录，没有其他分支——因此被删除的秘密在结构上对它来说是看不见的。**并非每个仓库都被索引**：非常大的仓库，以及没有独立活动的分叉，通常被排除在外。通常需要身份验证，速率限制很严格。并且匹配是基于令牌的，因此较长令牌内的子字符串可能不会按你期望的方式匹配。

将代码搜索视为一个发现工具，它告诉你*哪些仓库*要克隆。实际工作是在本地完成的。

## 删除后仍然存活的

- **从HEAD中删除的秘密仍然存在于历史中。** 删除文件是一个提交，而不是擦除；重写历史记录不会触及克隆、分叉或缓存；而且几乎没有人之后会轮换，因为删除感觉像是修复。
- **分叉网络中的提交通过SHA保持可访问**，即使分支被删除、PR被关闭未合并或分叉被删除。将仓库设为私有不会撤回已到达分叉的内容，强制推送的提交是悬而未决而不是消失。
- **Gist是未列出的，而不是私有的**——任何拥有URL的人都可以读取一个“秘密”Gist，并且URL会泄露到日志、聊天和工单中。
- **CI日志在公共仓库上是公开的。** 已知的秘密值屏蔽失败，每当值被base64编码、连接、URL编码或由子进程打印时。问题和PR附件同样由不透明的URL提供，并且在问题或仓库消失后仍然可检索。

## 正确扫描

镜像克隆，然后运行两个扫描器——它们的检测器和误报配置文件不同，并且没有一个是一个超集。然后用它们没有检测器的字符串探针：内部域名、云账户ID、来自配置文件的主机名。

```bash
trufflehog git file://./repo.git
gitleaks detect --source=. -v
git log --all --source -S'internal.example.com' --oneline
git log --all --diff-filter=D --name-only --format='%H %aI %an'
```

**关于验证的一个警告。** TruffleHog可以通过调用提供者的API来确认候选者是活跃的。这是一个与第三方使用其他人凭证的交互，并且会写入他们的日志。在授权评估中通常是预期的。在评估之外，不要这样做。

[reference/git-archaeology.md](reference/git-archaeology.md)中的命令；要grep的内容以及如何在[reference/high-signal-indicators.md](reference/high-signal-indicators.md)中分诊命中。

## 暴露的.git目录

一个将工作区复制到Web根的部署会发布`.git`，并且从`.git/config`、`.git/HEAD`和对象存储中可以重建整个历史——来源、凭证、作者身份，一切。

观察到这样的路径存在，通过搜索索引或现有的扫描结果，是被动性的。**检索它不是。** 下载一个`.git`目录是访问一个系统并从它获取数据，并且没有配置错误构成权限。只有在书面授权下；否则，报告它。

## 哪里出错了

- **作者身份是自我声明的。** 任何人都可以以任何人的身份提交；提交中的电子邮件是一个声明，而不是作者身份的证明。已签署的提交是例外，你应该验证的是签名，而不是字符串。
- **机器人主导提交计数。** CI、依赖机器人合并自动化产生了大量使用合成身份的提交。在得出关于人们的任何结论之前过滤它们。
- **变基和合并压缩会重写作者身份。** 提交者成为执行合并的人，并且合并会压缩许多作者为一个。不在日志中并不代表不在项目中。
- **时区推断是模糊的。** 笔记本电脑可以旅行，偏移量可以手动设置，CI在UTC时间提交。只有相互印证。
- **测试用例和文档示例看起来与凭证完全一样**，并且提供者示例会传播到数千个仓库。先搜索。
- **按设计公开的密钥不是泄露。** 可发布且引用者锁定浏览器密钥是打算发布的；将一个泄露报告为违规会损害你在真实发现上的信誉。
- **同名组织或打字错误不是你的目标**，并且仅历史发现的通常比当前发现更活跃，因为删除而不轮换是常态。

## 置信度分级

- **确认**——一个noreply数字ID解析到账户的身份链接，或者相同的提交电子邮件出现在多个已经与该人关联的账户下。一个凭证泄露，其格式有效，其范围由周围上下文确定，有提交SHA和日期。
- **可能**——一个独特的电子邮件或昵称在具有一致提交时间的多个仓库中重复出现，或者在一个真实配置文件中（不在测试路径中）有一个凭证形状的字符串。
- **未确认**——一个未签署提交的作者字符串；一个常见的昵称；一个扫描器在测试用例或文档示例中的命中；一个范围不明的凭证。
- **拒绝**——一个记录的占位符、一个可发布的密钥，或一个作为活跃泄露呈现的过期临时凭证。

记录每个发现的仓库、提交SHA、日期和文件路径。SHA是一个不可变的引用；行号不是。

## 实例分析

目标：绘制一个公司工程团队，其站点名称仅限于高管。

在内部域名`svc.example-corp.net`上的代码搜索返回三个仓库，没有一个携带公司名称。镜像克隆它们返回了十四个不同的作者电子邮件，其中十一个属于公司，三个属于个人。

一个作者提交为`48211903+dhaverford@users.noreply.github.com`。解析数字ID返回了一个*不同的*当前用户名——账户被重命名了，旧的昵称链接到会议演讲和个人博客，而当前用户没有。

死胡同：gitleaks在一个测试用例中标记了一个AWS形状的密钥，并且搜索该字符串发现它在AWS自己的文档中找到了完全相同的字符串。放弃，并记录为放弃，以免有人再次提出。

真正的发现是一个`terraform.tfstate`在两年前的同一周添加和删除，从历史记录中恢复。没有活跃凭证，但有四个内部主机名和一个云账户ID——用于`find-hidden-subdomains`的基础设施。

评级：团队花名册**可能**，因为提交作者身份是自我声明的且未经证实。重命名链接**确认**——数字ID是不可变的。

## 法律、披露和一条硬规则

**永远不要用你发现的凭证进行身份验证。** 不是检查它是否有效，不是只读，不是一次。在大多数司法管辖区，这是未经授权的访问，发布不会授予权限。从格式、上下文和元数据中确定有效性，除此之外别无其他。参见[../../ETHICS.md](../../ETHICS.md)。

一个看起来活跃的凭证会产生披露的义务。立即通过安全联系人、`security.txt`路由或主机的漏洞渠道报告；给出仓库、提交SHA和文件路径；明确说明历史重写是不够的，凭证必须被**轮换**；只保留一个脱敏参考；不要发布任何内容。运行自动秘密扫描合作关系的托管可能已经撤销了令牌，但这不会消除告知某人的义务。

克隆公共仓库是正常使用；批量克隆和高速率API查询会受到速率限制，并且可能违反条款。提交电子邮件在GDPR和类似法规下是个人数据——无论仓库的状态如何——收集最少的信息并设置保留期。
