# 查找隐藏的子域名

组织忘记管理的托管主机才是值得寻找的目标，而大多数此类主机在有人请求TLS证书时都自行暴露了存在。证书透明度（Certificate Transparency）将这一过程转化为一个可搜索、永久、历史性的索引——免费且完全被动。初学者的错误是将CT命中视为活跃主机：你拉取的大部分内容都无法解析，而这些信息也是有价值的，并非噪音。

## 首先从哪个来源开始

| 你持有 | 从...开始 | 原因 |
|---|---|---|
| 顶级域名 | crt.sh通配符查询 | 最广泛的免费覆盖范围，包括早已失效的域名 |
| 使用通配符证书的域名 | 被动DNS，然后是存档 | CT只会显示 `*.example.com` |
| 对命名规则的猜测 | CT学习规则，然后是单词列表 | 在暴力破解任何内容之前先了解模式 |
| 组织名称，而非域名 | 按主题组织机构搜索证书 | 找到你不知道他们拥有的域名 |
| 你已有的证书 | 其SANs，然后是其序列号和颁发者 | SANs提供兄弟证书；序列号可在其他地方找到确切的证书 |
| 仅需要*当前*主机 | 解析候选列表 | CT本质上是历史的；DNS是活跃性的判别者 |

## CT实际工作原理

CA将它们签发的每个证书提交到可进行密码学验证的公共日志中。日志返回一个已签名的证书时间戳，主流浏览器拒绝信任不携带合格日志SCTs的公开信任证书。因此，参与不是自愿的：如果证书在浏览器中有效，它就在日志中。

对你重要的三个后果：

- **不会删除任何内容。** 日志是追加-only的。五年前出现在证书中的主机名在主机消失后仍然存在。
- **你会看到预证书和证书。** CA首先记录预证书，然后是最终证书，因此大多数名称至少出现两次。去重。
- **仅覆盖公开信任的证书。** 私有/内部CA、自签名证书或Cloudflare源证书永远不会到达日志。CT完全无视这些主机。

## crt.sh

Web界面使用 `?q=`，其中 `%` 是通配符，`output=json` 提供机器可读的结果。

```bash
# 查找example.com或其子域名中所有出现过的名称
curl -s 'https://crt.sh/?q=%25.example.com&output=json' \
  | jq -r '.[].name_value' | sed 's/^\*\.//' | sort -u

# 当你希望偏向当前基础设施时，跳过过期证书
curl -s 'https://crt.sh/?q=%25.example.com&output=json&exclude=expired' | jq -r '.[].name_value'

# 对组织名称进行身份搜索，可找到未提及的域名
curl -s 'https://crt.sh/?q=Example+Corporation&output=json' | jq -r '.[].name_value'
```

`q` 参数是身份搜索：它匹配域名，也匹配主题字段（如组织名称），这就是你如何找到简报中未提及的域名。

有用的JSON字段：`name_value`（证书上的所有名称，以换行符分隔）、`common_name`、`issuer_name`、`not_before` / `not_after`、`serial_number`、`entry_timestamp` 和 `id`（打开 `https://crt.sh/?id=<id>` 阅读证书）。

crt.sh还通过Postgres公开其数据库只读访问——主机 `crt.sh`，端口 5432，用户 `guest`，数据库 `certwatch`。这允许你针对证书索引编写真实的SQL查询，而不是分页JSON。这是一个共享的免费服务：保持查询范围有限，如果你过度查询可能会被切断。

其他CT前端和替代方案及其覆盖范围和访问模型在 [reference/subdomain-sources.md](reference/subdomain-sources.md) 中。

## SAN字段是关键

浏览器忽略通用名称（Common Name）；`subjectAltName` 扩展包含实际覆盖的主机名列表。将其视为一个团队一起部署的声明：

- 一个包含少量相关名称的证书是故意的分组——这些主机属于同一服务，并且可能由同一管理员管理。
- 一个包含几十个无关名称的证书是托管提供商或CDN的捆绑证书。**这些名称是其他客户，而不是你的目标资产。** 这是基于CT的枚举中最大的误报来源。
- 一个证书上包含来自*不同可注册域名*的名称是好发现：这意味着一个运营商管理两者，这会暴露收购、品牌重塑和未公开的兄弟品牌。在得出结论之前进行验证——见上述捆绑陷阱。
- 内部名称在此处持续泄露：`jira`、`owa`、`vpn`、`*.corp.example.com`、带有机架或数据中心代码的主机名，以及从未公开发布的产品代码名称。

## 通配符隐藏，不揭示

`*.example.com` 覆盖所有子域名，但名称本身并不包含任何子域名。一个切换到通配符的组织（通常与DNS-01 ACME自动化一起使用）从那时起在CT中实际上变得暗淡。当你看到一个通配符时：

- 在通配符之前挖掘CT，当时存在每个主机的证书。
- 转向被动DNS，它记录答案而不是证书。
- 检查存档和搜索索引中的主机名（`read-deleted-pages`、`google-like-a-spy`）。
- 寻找由于技术原因必须保留自己证书的主机：通配符覆盖不到的更深层次标签（`a.b.example.com` 需要自己的证书），以及位于不同顶级域名上的任何内容。

## 结合来源，然后解析

CT提供历史记录。被动DNS提供观察到的现实。单词列表提供无人发布的名称。使用所有三个，并按来源标记它们，因为你可以分配的置信度取决于名称的来源。

```bash
subfinder -d example.com -all -silent -o passive.txt   # 聚合多个被动来源
amass enum -passive -d example.com                     # 不同的来源组合，较慢
dnsx -l passive.txt -a -resp -silent                   # 将候选解析为A记录
```

解析将候选分为三个桶：解析到地址、解析到CNAME（读取目标——它命名了供应商，悬空的一个是接管候选以报告）、或者完全无法解析。死名称仍然是发现：它们标记了基础设施，暴露了命名约定，有时会再次解析。

**在信任任何暴力破解结果之前，先检测通配符DNS。** 解析一个不可能存在的随机名称，例如 `zzq7x-nonexistent.example.com`。如果它响应，该区域解析所有内容，并且你的整个暴力破解列表都是误报。

明确界限：查询CT、被动DNS、搜索引擎和存档永远不会接触目标。通过公共递归解析器解析候选名称实际上是不可见的，但确实会生成查询。单词列表暴力破解是高容量的DNS流量，目标DNS提供商会看到，并且可能会根据流量和司法管辖区进行速率限制或阻止。使用 `httpx` 等工具对结果进行HTTP探测**是主动的**——你正在连接到目标的服务器。在你的范围笔记中标记暴力破解和探测，如果参与是被动仅的，则跳过它们。

## 名称模式意味着什么

不要将所有发现的托管主机视为平等。`dev`、`staging`、`uat`、`vpn`、`legacy`、`old` 和管理面板比 `www` 带有非常不同的风险和后续操作。分类表在 [reference/name-pattern-triage.md](reference/name-pattern-triage.md) 中。

## 哪里会出错

- **捆绑和多租户证书。** 共享主机和CDN证书将无关客户放在一个证书上。始终检查证书上的其他名称是否可能属于你的目标，然后再采用它们。
- **CT不是资产清单。** 它是证书请求的记录。内部CA后面的主机、自签名证书、源证书或纯HTTP主机都缺失。永远不要将基于CT的列表报告为完整。
- **名称比主机存活。** 大多数历史CT名称都是死的。一个包含400个子域但无法解析的列表是400个未经验证的声明。
- **名称比所有权存活。** 当域名属于前一个所有者时签发的证书，即使当前所有者查询时仍然会显示。通过 `who-owns-this-domain` 检查 `not_before` 与域的注册和转让历史。
- **CNAME指向的第三方不是目标的资产。** 目标拥有的主机指向SaaS租户是目标的关系，而不是其基础设施。不要将供应商暴露视为目标的暴露。
- **聚合器存在分歧，且默默无闻。** 每个工具查询不同的来源集；免费层会截断结果而不告诉你。两个工具返回相同的50个名称，可能都在读取同一个来源。
- **故意污染。** 任何人都可以为他们在看起来像目标域上的受控名称获取证书。拼写劫持会在CT搜索中显示为目标的自己的主机。逐字符检查可注册域名。

## 置信度分级

- **确认资产**——名称解析，并且它属于你已验证注册的域名，基础设施与目标的其他主机一致（同一ASN、同一证书颁发者、同一命名约定）。
- **可能资产**——在已验证的目标域名下但不再解析的CT名称，或解析到供应商的共享平台上的名称。真实名称，未验证当前状态。
- **未确认**——来自捆绑无关客户的证书的名称、通配符DNS区域中的暴力破解命中、不同可注册域名上的名称且没有佐证链接，或你未见过底层证书或DNS答案的聚合器结果。

记录每个主机：名称来源、证书 `id` 或被动DNS来源、`not_before` 日期、解析结果和时间戳。

## 实例分析

目标：`example-health.test`，范围是被动仅的。

crt.sh使用 `%25.example-health.test` 返回61个唯一名称。去重预证书/证书对将其减少到38个。三个立即有趣：`vpn-uat.example-health.test`、`jira.internal.example-health.test` 和 `billing-legacy.example-health.test`。

一个证书包含九个无关公司的44个名称——一个托管提供商的捆绑。丢弃不是目标的43个。这是死胡同，并且它会使报告比真实发现膨胀更多。

解析38个：12个响应。`jira.internal` 无法公开解析，但其在证书中的存在确认了内部命名约定和Jira实例——即使没有主机可供查看也值得注意。`vpn-uat` 解析到某个设备供应商的网络块，这会转到 `find-exposed-servers`。

从一个证书的组织名称进行身份搜索返回两个 `examplehealth-group.test` 的证书，一个在简报中无人提及的域名。通过 `who-owns-this-domain` 进行WHOIS显示相同的注册组织。这是扩展参与的转折点。

评级：12个解析主机**确认**，`jira.internal` **可能**（真实名称，无法公开访问），兄弟域名**可能**有待企业申报。

## 转折点

| 新选择器 | 跳转到 |
|---|---|
| 活跃主机名及其IP | `find-exposed-servers` |
| 兄弟和收购的域名 | `who-owns-this-domain`、`who-really-owns-it` |
| 从证书主题获取的组织名称 | `x-ray-a-company` |
| 具有历史内容的死主机名 | `read-deleted-pages` |
| 开发/测试主机名，看起来像仓库的名称 | `secrets-in-git-history` |
| 在新发现主机上索引的文件 | `google-like-a-spy` |
| 用于结构化的大型主机/域名/IP集 | `graph-the-network` |

## 法律和ToS注意事项

读取CT日志和被动DNS是设计为发布：数据存在以供阅读。两个限制是真实的。首先，像crt.sh这样的免费服务是共享基础设施——过度的自动查询会阻止你并是不礼貌的；使用有限查询并缓存结果。其次，DNS暴力破解和HTTP探测将流量发送到目标，并且根据流量和司法管辖区，可能会被视为未经授权的活动；根据 [../../ETHICS.md](../../ETHICS.md) 将它们限制在书面的范围内。发现一个悬空的CNAME或暴露的测试主机迫使你必须报告它，而不是测试它。
