参数：`$ARGUMENTS`。语法：`[<分支>] [<仓库>] [-- <任务>]`。

- **分支** — 可选；新工作树的分支名。如果省略，则选择一个（见下文步骤 1）。
- **仓库** — 可选路径或名称；在指定仓库中创建工作树，而不是会话当前仓库。
- **任务** — 可选；在新工作树中执行的操作。无任务则进入工作树并等待。

`--` 前面的标记是分支和/或仓库。路径形标记（以 `/`、`~`、`./` 或 `../` 开头）是仓库。裸名称可以是两者之一，因此需要做出判断。当当前仓库已有该名称的分支时，它是分支，就像 `wt switch` 本身一样。否则，当存在该名称的 git 仓库时（用户存放仓库的位置，除了当前仓库，或在类似 `~/workspace` 的工作空间目录中），它是仓库；当不存在时，它是分支（`docs` 是分支，而不是当前仓库的 `docs/` 目录）。被读取为仓库的名称会携带其绝对路径：该路径，而不是裸标记，是步骤 3 中的 `<仓库>`。两个都读取为分支的标记不符合语法——请询问。如果没有 `--`，则判断任务从何处开始：作为分支名（`fix-auth`）或仓库的引导标记被消耗，其余部分是任务；否则整个输入是任务（`fix the parser bug` 没有分支形引导——全部是任务）。

```
/wt-switch-create my-feature -- fix the parser bug
/wt-switch-create -- fix the parser bug
/wt-switch-create my-feature ~/workspace/other-repo -- fix the parser bug
/wt-switch-create my-feature
```

## 要做什么

在每次调用中，创建工作树是首要任务，在任何其他工作之前。调用本身就是创建它的明确请求；研究或只读任务同样如此。

<!-- 维护者：rationale.md（同一目录）涵盖了此 harness 规则和设计选择——在重新添加保护或路由之前阅读它。 -->

1. **如果未给出分支名，则选择分支名**：简短，来自任务并与现有工作树名称一致，或者，在会话期间，来自要移动的工作；如果没有可推导的内容，则询问。

2. **如果没有仓库参数，则一次性创建并进入**：
   `EnterWorktree({name: "<分支>"})`。Worktrunk 的 `WorktreeCreate` 钩子运行 `wt switch --create`，因此结果是普通布局的 `wt` 工作树，用户不会看到确认提示。成功后，执行任务（或，如果没有任务文本，则确认其已准备好并等待）。

   在会话期间，跨工作树携带未提交的工作：在 `EnterWorktree` 调用之前执行 `git stash push -u`，然后在调用之后执行 `git stash pop`——调用将会话重新根植到新工作树中，并且 stash 在所有工作树之间共享。

3. **否则使用 `wt` 创建并按路径进入**。两种情况会进入此步骤：一个仓库参数，步骤 2 无法处理，以及步骤 2 失败，其错误说明是哪个——`✗ 分支 <分支> 已存在`，或 `已在工作树会话中`。使用 `Bash` 调用创建（为当前仓库省略 `-C <仓库>`）：

   ```
   wt -C <仓库> switch --create <分支> --no-cd --format=json
   ```

   标准输出是 JSON，其 `path` 字段是工作树的绝对路径（状态行输出到 stderr）。在 `Branch <分支> 已存在`：如果用户指定了分支名，则不使用 `--create` 重新运行（它进入分支，如果缺少则创建其工作树）；如果步骤 1 选择了名称，则选择另一个并重新运行。任何其他失败（不是 git 仓库，无效名称）：报告它并停止。

   如果有仓库参数，下一步在其自己的 `Bash` 调用中执行 `cd <仓库>`。`EnterWorktree` 仅在当前工作目录所在的仓库中重新根植，并且 worktrunk 的 `PermissionRequest` 钩子仅对相同仓库的 `wt` 工作树回答调用请求的确认。如果 `cd` 报告 `Shell cwd was reset`，则仓库无法访问：跳过进入并按 **无法访问** 下文所述返回。

   然后调用 `EnterWorktree({path: "<从 JSON 获取的路径>"})`。

   - **接受** → 会话将在工作树中重新根植。执行任务（或，如果没有任务文本，则确认其已准备好并等待）。
   - **工具错误**——工具运行并返回错误（`Cannot enter worktree: …`）→ 优雅处理；没有移动任何内容，并且所有情况都有恢复方法。常见原因是会话已在工作树中根植（或一个固定的代理），这限制了进入当前仓库的 `.claude/worktrees/`，并排除了即使是同一仓库的 `wt` 兄弟。恢复测试是您是否可以 `cd` 进入工作树，当它在允许的目录中时，这有效。因此 `cd <路径>` 并读取结果：
     - 没有 `Shell cwd was reset` 提示 → 它卡住了；工作树是可访问的。在那里工作，但裸 `cd` 不是跟踪的重新根植，因此 cwd 可以在回合之间恢复到会话的启动工作树（并在 spawned 子代理中）；使用 `git -C <路径>` / `wt -C <路径>` 命令固定，而不是依赖 `cd` 来持久化。
     - `Shell cwd was reset` → **无法访问。** 停止并要求用户使 `cd` 重置的目录可访问：将包含仓库及其工作树的父目录（如 `~/workspace`）添加到 `permissions.additionalDirectories`（持久，每个会话），或在当前会话中运行 `/add-dir` 在它上面。然后从该 `cd` 继续进行。不要通过 `cd` 在每个命令上重置绝对路径来磨磨蹭蹭。
   - **拒绝**——调用本身被拒绝，没有工具错误 → 无论拒绝如何措辞，它都是用户对 Claude Code 显示的进入 `.claude/worktrees/` 外工作树的确认回答，除非没有用户可以询问（拒绝说会话无法提示），这决定不了什么——采取上述恢复方法。在用户的回答上：刚刚创建的 `wt` 工作树仍然存在；只有进入没有发生。如果你进入任何你移动的仓库，请返回，然后报告工作树的路径并询问如何继续，因为通过 `cd` 到达它将覆盖该回答。

## 清理

工作树是一个普通的工作树工作树：它出现在 `wt list` 中，并像任何其他一样通过 `wt merge` / `wt remove <分支>` 合并或删除。不要未经提示删除它。

来自步骤 2 的工作树，会话从未接触过——没有更改的文件，没有提交——会在会话结束时清理，包括分支；写入它的任何内容都会保留它。来自步骤 3 的工作树始终保留。如果用户在会话期间要求离开，`ExitWorktree({action: "keep"})` 将会话返回到其原始目录；`ExitWorktree` 不能删除通过路径进入的工作树，因此删除这些总是 `wt remove <分支>`。

## 范围

命令的权限是创建一个工作树（如果在给定的情况下，在指定的仓库中）并在其中执行请求的任务。提交、推送和合并仍然需要每个用户明确的权限。
