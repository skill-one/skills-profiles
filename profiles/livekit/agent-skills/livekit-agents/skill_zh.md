# LiveKit 云端智能代理开发

本指南为使用 LiveKit 云构建语音 AI 代理提供主观建议。它假定您正在使用 LiveKit 云（推荐路径），并编码 *如何着手* 代理开发，而非 API 具体细节。所有关于 API、方法和配置的真实信息必须来自实时文档。

**本指南适用于 LiveKit 云开发者。** 如果您正在自托管 LiveKit，某些建议（尤其是围绕 LiveKit Inference 的建议）将不会直接适用。

## 必须阅读：开始前请检查此清单

在编写任何代码之前，请完成此清单：

1. **阅读整个指南文档** - 即使 MCP 可用，也不要跳过任何部分
2. **确保已连接 LiveKit 云项目** - 您需要从云项目中获取 `LIVEKIT_URL`、`LIVEKIT_API_KEY` 和 `LIVEKIT_API_SECRET`
3. **设置文档访问权限** - 如果可用，请使用 MCP，否则使用网络搜索
4. **计划编写测试** - 每个代理实现必须包含测试（见下文测试部分）
5. **对照实时文档验证所有 API** - 不要依赖模型内存来处理 LiveKit API

无论 MCP 是否可用，此清单都适用。MCP 提供文档访问权限，但**不会取代本指南中的指导**。

## LiveKit 云端设置

LiveKit 云是让语音代理快速运行的最快方式。它提供：

- 管理基础设施（无需部署服务器）
- **LiveKit Inference** 用于 AI 模型（无需单独的 API 密钥）
- 内置的噪音消除、语音检测和其他语音功能
- 简单的凭证管理

### 连接到您的云项目

1. 如果尚未注册，请访问 [cloud.livekit.io](https://cloud.livekit.io) 注册
2. 创建项目（或使用现有项目）
3. 从项目设置中获取您的凭证：
   - `LIVEKIT_URL` - 您项目的 WebSocket URL（例如，`wss://your-project.livekit.cloud`）
   - `LIVEKIT_API_KEY` - 用于身份验证的 API 密钥
   - `LIVEKIT_API_SECRET` - 用于身份验证的 API 密钥

4. 将这些设置为环境变量（通常在 `.env.local` 中）：
```bash
LIVEKIT_URL=wss://your-project.livekit.cloud
LIVEKIT_API_KEY=your-api-key
LIVEKIT_API_SECRET=your-api-secret
```

LiveKit CLI 可以自动化凭证设置。请查阅 CLI 文档以获取当前命令。

### 使用 LiveKit Inference 处理 AI 模型

**LiveKit Inference 是使用 LiveKit 云处理 AI 模型的推荐方式。** 它提供对领先的 AI 模型提供商的访问权限——所有这些都通过您的 LiveKit 凭证，无需单独的 API 密钥。

LiveKit Inference 的优势：

- 无需为每个 AI 提供商管理单独的 API 密钥
- 通过您的 LiveKit 云账户整合账单
- 针对语音 AI 工作负载进行优化

请查阅文档以获取可用模型、支持的提供商和当前使用模式。文档始终包含最新信息。

## 严格规则：永远不要依赖模型内存来处理 LiveKit API

LiveKit Agents 是一个快速发展的 SDK。模型训练数据一旦创建就会过时。在处理 LiveKit 时：

- **永远不要假设** 从内存中获取 API 签名、方法名称或配置选项
- **永远不要猜测** SDK 行为或默认值
- **始终对照实时文档** 在编写代码前进行验证
- **始终引用** 文档来源来实施功能

即使对 API 很有信心，也必须验证。

## 语音代理架构原则

语音 AI 代理与基于文本的代理或传统软件具有根本不同的要求。请内化这些原则：

### 延迟至关重要

语音对话是实时的。用户期望在数百毫秒内而不是几秒内获得响应。每个架构决策都应考虑延迟影响：

- 最小化 LLM 上下文大小以减少推理时间
- 在活动对话期间避免不必要的工具调用
- 优先使用流式响应而不是批量响应
- 设计失败路径（网络延迟、API 超时）

### 上下文膨胀会降低性能

大型系统提示和广泛的工具列表会直接增加延迟。一个具有 50 个工具和 10,000 个 token 的系统提示的语音代理，无论模型速度如何，都会感觉迟缓。

设计具有最小可行上下文的代理：
- 仅包含与当前对话阶段相关的工具
- 保持系统提示简洁
- 删除未在当前阶段实际需要的工具和上下文

### 用户不读，他们听

语音界面约束与文本不同：
- 长响应会使用户沮丧——保持输出简洁
- 用户无法滚动——确保首次交付的清晰度
- 中断是正常的——设计优雅的处理方式
- 沉默会感觉不完整——在需要时确认处理状态

## 工作流架构：交接和任务

复杂的语音代理不应是单体。LiveKit Agents 支持结构化工作流，这些工作流在处理复杂用例的同时保持低延迟。

### 单体代理的问题

单个代理处理整个对话流程会累积：
- 每种可能操作的工具（膨胀的工具列表）
- 每个对话阶段的说明（膨胀的上下文）
- 所有场景的状态管理（复杂性）

这会导致延迟并降低可靠性。

### 交接：代理到代理的转换

交接允许一个代理将控制权转移给另一个代理。使用交接来：
- 分离不同的对话阶段（问候 → 摘要 → 解决）
- 隔离专业能力（一般支持 → 计费专家）
- 管理上下文边界（每个代理只包含它需要的部分）

围绕自然对话边界设计交接，在这些边界处可以总结上下文，而不是整体转移。

### 任务：范围明确的操作

任务是指定范围的提示，旨在实现特定结果。使用任务来：
- 执行不需要完整代理能力的离散操作
- 在需要专注提示比通用代理更优的情况下使用
- 在只需要特定能力时减少上下文

请查阅文档以获取关于交接和任务的实现细节。

## 必须使用：为代理行为编写测试

语音代理行为是代码。每个代理实现必须包含测试。不进行测试就发布代理等于发布未经测试的代码。

### 强制测试工作流程

在构建或修改 LiveKit 代理时：

1. **创建 `tests/` 目录**（如果尚不存在）
2. **在考虑实现完成之前至少编写一个测试**
3. **测试用户请求的核心行为**
4. **运行测试** 以验证它们是否通过

### 测试驱动开发流程

在修改代理行为（指令、工具描述、工作流）时，首先编写针对预期行为的测试：

1. 定义代理在特定场景中应执行的操作
2. 编写验证此行为的测试用例
3. 实现功能
4. 迭代直到测试通过

这种方法可以防止发布“看似工作”但在生产中失败的代理。

### 每个代理测试应涵盖的内容

至少编写测试以涵盖：
- **基本对话流程**：代理对问候做出适当响应
- **工具调用**（如果存在工具）：工具使用正确的参数被调用
- **错误处理**：代理优雅地处理意外输入

测试应侧重于：
- **工具调用**：代理是否调用正确的工具并使用正确的参数？
- **响应质量**：代理是否为给定输入生成适当的响应？
- **工作流转换**：交接和任务是否正确触发？
- **边缘情况**：代理如何处理意外输入、中断、沉默？

### 测试实现模式

使用 LiveKit 的测试框架。通过 MCP 查阅测试文档以获取当前模式：
```
search: "livekit agents testing"
```

该框架支持：
- 模拟用户输入
- 验证代理响应
- 工具调用断言
- 工作流转换测试

### 为何这是非协商的

在手动测试中“看似工作”的代理在生产中经常失败：
- 提示更改会无声地破坏行为
- 工具描述会影响工具何时被调用
- 模型更新会改变响应模式

测试可以在用户发现问题之前捕获这些问题。

### 跳过测试

如果用户明确要求不进行测试，请按其要求进行，但请通知他们：
> "我已按要求构建了未进行测试的代理。我强烈建议在部署到生产环境之前添加测试。语音代理难以手动验证，测试可以防止无声的回归。"

## 需要避免的常见错误

### 过载初始代理

从一个“做所有事情”的代理开始，并随着时间的推移添加工具/指令。相反，应从一开始就设计工作流结构，即使初始实现很简单。

### 直到问题出现才考虑延迟

延迟问题会累积。在开发中感觉“有点慢”的代理在真实网络条件下会变得无法使用。持续测量和优化延迟。

### 不理解就复制示例

文档中的示例展示了特定模式。不理解代码目的就复制代码会导致臃肿、结构不良的代理。在包含每个组件之前，了解每个组件的作用。

### 因为“只是提示”而跳过测试

代理行为是代码。提示更改与代码更改一样会影响行为。以与传统软件相同的严格程度测试代理行为。**永远不要在没有至少一个测试文件的情况下交付代理实现。**

### 假设模型知识是当前的

重申关键规则：永远不要依赖模型内存来处理 LiveKit API。SDK 的演变速度比模型训练周期更快。验证所有内容。

## 总结

使用 LiveKit 云构建有效语音代理需要：

1. **使用 LiveKit 云 + LiveKit Inference** 作为基础——这是最快进入生产的路径
2. **对照实时文档验证所有内容**——永远不要依赖模型内存
3. **在每次架构决策点最小化延迟**
4. **使用交接和任务** 来管理复杂性
5. **在更改前后测试行为**——没有测试就绝不发布
6. **保持上下文最小**——仅包含当前阶段需要的部分

这些原则无论 SDK 版本或 API 如何更改都仍然有效。对于所有实现细节，请通过 MCP 查阅 LiveKit 文档。
