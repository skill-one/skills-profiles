# 工作流技能提取器

将已完成的工作流转换为可重用的代理技能。具体来说，此技能从**已经发生**的交互或工作流中提取模式，并将其打包。

> [!警告] **在编写任何代码或 SKILL.md 内容之前，您必须完成阶段 1（头脑风暴）。** 跳过头脑风暴会产生过于僵化或过于模糊的技能。头脑风暴对话是此过程最重要的部分。

## 阶段 1：头脑风暴（必填）

与用户进行**迭代的双向对话**。不要一次性问所有问题。从下面的库中每轮挑选 2-3 个相关问题，完善您的理解，并询问后续问题。

### 第一轮：理解工作流

首先总结您从工作流中观察到的内容，然后询问：

1.  "这是我对工作流的理解：[总结]。这是准确的吗？您会做哪些改变？"
2.  "这个工作流的预期输入和输出是什么？"
3.  "您预计多久运行一次这个工作流？它是周期性的还是一次性的？"

### 第二轮：灵活性和错误处理

针对工作流中确定的每个步骤，确定其僵化程度：

1.  "对于 [步骤 X]，如果主要方法失败（例如，API 停机，无结果），代理应该：(a) 请求您的指导，(b) 自动尝试替代方法，还是 (c) 大声报错？"
2.  "是否有任何步骤需要精确方法（例如，必须使用特定数据库），与任何合理方法都可以的步骤？"
3.  "技能应该默默地处理边缘情况，还是将它们展示给用户？"

### 第三轮：依赖项和资源

在问这些问题之前，检查您已安装的技能中哪些与工作流重叠。如果科学包中的现有技能涵盖了某个步骤，新技能**必须**引用它——不要提供自包含选项。

1.  "我注意到工作流使用了由 [现有技能 X、技能 Y] 涵盖的功能。新技能将引用这些，而不是重新实现它们。您希望我整合其他哪些工具或技能？"
2.  "对于此工作流中使用的服务，是否有任何 API 速率限制我应该注意的，而现有技能尚未涵盖？"
3.  "是否有特定文件提供重要的科学背景，用于创建此技能？例如：API 文档、参考论文、示例数据集或特定领域的笔记。如果是，请分享它们，我将将其内容整合到技能的参考材料中。"

### 第四轮：范围和形状

1.  "我们的工作流涵盖了 [X、Y、Z]。我应该将所有这些都提取到技能中，还是还有其他重要功能需要包含？反之，是否有任何这些需要排除？"
2.  确定技能是否需要任何代码。如果任何步骤涉及调用 API、处理数据、读取/写入文件或计算结果，则技能**需要代码**，您应该默认使用 CLI 模式。仅在每一步都是纯粹的推理、协调现有工具或遵循没有程序性工作的事先书面协议时，才使用纯文本指令技能。用 plain language 向用户确认您的评估：
    -   如果需要代码："这些步骤涉及 [从 API 获取数据 / 处理文件 / 计算结果]，因此我将创建一个辅助脚本，代理可以为您运行。脚本将包含简单的命令，如 `search`、`fetch`、`analyze` 等——您不需要自己编写任何代码。这样听起来对吗？"
    -   如果不需要代码："这个工作流完全是关于遵循一系列步骤和使用现有工具——不需要新代码。我将它编写为代理遵循的一组清晰指令。这样听起来对吗？"
3.  如果将创建辅助脚本："我正在考虑脚本应该有这些命令：[用 plain English 提出的建议命令，例如 '搜索蛋白质'、'获取结果'、'比较序列']。您会添加或更改什么？"
4.  "技能应该叫什么名字？建议名称：`[建议]`。"

### 第五轮：测试（可选）

1.  "您能提供一个示例查询和预期答案，让我用来验证技能按预期工作吗？例如：'如果我问 [问题]，技能应该产生 [答案]'。这是可选的，但在开发过程中有助于我验证技能。"

### 头脑风暴完成标准

当您能够自信地回答所有以下问题时，即可进入阶段 2：

-   [ ] 工作流的目的和范围是什么？
-   [ ] 输入和输出是什么？
-   [ ] 哪些步骤是严格的，哪些是灵活的？
-   [ ] 哪些现有技能应该被引用？
-   [ ] 需要哪些新脚本（如果有）？
-   [ ] 哪些速率限制适用？
-   [ ] 如何处理错误？
-   [ ] 工作流需要任何代码吗？（是 → CLI 模式；否 → 指令仅模式）
-   [ ] 技能应该在哪里安装？（本地、全局或自定义路径）
-   [ ] 是否有用于验证的示例查询/答案？

## 阶段 2：技能设计

生成**设计文档**（作为工件/实施计划），并向用户提交以供批准。文档必须包括：

1.  **技能名称和描述**（遵循 YAML 前置规则：名称 ≤64 个字符，小写 + 连字符；描述 ≤1024 个字符）。
2.  **目录结构**，显示所有计划文件和**安装位置**（本地、全局或自定义——见规则 7）。
3.  **引用的现有技能**，并说明每个技能的理由。
4.  **新脚本**（如果有），建议子命令和参数。
5.  **速率限制策略**，适用于现有技能未涵盖的任何 API。
6.  **每步的错误处理策略**。

**在进入阶段 3 之前，等待用户明确批准。**

## 阶段 3：实施

### 指导原则

技能实施的一般指南：

-   使用 `uv run`，不要使用 `python` 或 `python3`。
-   优先使用随默认 Python 3 安装一起提供的 stdlib 库（`urllib` 优先）；如果可能，避免需要额外安装的库。
-   速率限制必须在代码中记录并遵守。优先使用**基于文件锁的速率限制**，以便在同一台机器上共享的并发子代理共同尊重该限制。查看科学技能包中的其他技能，以获取跨进程安全的典型实现。
-   技能输出必须 <500 行或重定向到文件。长输出文件应该被程序性地处理以提取相关字段。
-   建议使用连字符作为技能名称和 YAML `name:` 字段。

### 规则 1：重用现有技能

当工作流使用由已安装的现有技能涵盖的功能时，新的 SKILL.md **必须**通过名称引用它，而不是重新实现。在 SKILL.md 中包含**依赖项**部分，列出所需技能并简要说明每个技能的理由。

### 规则 2：新 API 的速率限制

对于任何**未**由现有技能涵盖的 API 交互，生成的 CLI 脚本**必须**实现速率限制。在编写任何速率限制代码之前，**查找 API 的官方速率限制指南**：检查用户在头脑风暴期间提供的任何文档，然后在网络上搜索 API 的公共文档。如果找不到任何记录的速率限制，**默认为每秒 1 个请求**。速率限制模式直接构建在 CLI 模板 `references/cli_script_template.py` 中——查看 `RateLimitError` 类和 API 客户端的 `_request` 方法。

关键要求：

-   使用 `time.monotonic()` 进行计时（不要使用 `time.time()`）。
-   根据记录的速率限制计算延迟。
-   对于瞬态错误（5xx），实现具有指数退避的重试。
-   当收到 HTTP 429 时，引发专门的 `RateLimitError`。
-   将重试尝试记录到 stderr，以便代理可以观察进度。
-   在错误消息中包含 URL 和速率限制值。
-   对于不可重试的 HTTP 错误（例如 400、403、404），读取并包含响应正文在错误消息中——不仅仅是状态码。API 响应正文包含可操作的详细信息（例如，“无效参数”），使代理能够自我纠正。

### 规则 3：CLI 脚本模式（需要代码时的默认选择）

**这是默认选择。** 如果工作流中的**任何**步骤涉及 API 调用、数据处理、文件 I/O、计算或任何其他程序性工作，请使用 `argparse` 生成多命令 CLI 脚本。遵循 `references/cli_script_template.py` 中的模板。

关键要求：

-   每个主要工作流步骤都成为一个子命令。
-   所有子命令都接受 `--output` 以将结果写入文件。
-   使用 `json.dump` 并设置 `indent=2` 以生成 JSON 输出。
-   打印成功消息并包含输出文件路径。
-   出错时退出代码为 1。
-   将 `--limit` 等参数设为**必需**（无沉默默认值）。这迫使代理明确指定值，防止它假设它检索了“所有”结果时被沉默地限制。

### 规则 4：默认为文件输出

所有脚本和工作流**必须**将输出写入文件，而不是 stdout。stdout 只应包含简短的状态消息（例如，“成功！数据写入：results.json”）。这是至关重要的，因为：

-   API 响应可能非常大，并在终端输出中截断。
-   文件输出是 token 效率的——代理使用 `jp` 或 Python 一行代码读取它需要的字段。
-   大型 stdout 输出浪费上下文窗口空间。

### 规则 5：指令仅模式（仅当不需要代码时使用）

仅在工作流需要**零**程序性工作时使用此模式——即每一步都是纯粹的编排、推理、多技能协调或遵循事先书面协议。如果任何步骤需要代码（API 调用、数据处理、文件 I/O 等），请改用规则 3 中的 CLI 模式。生成一个具有结构化工作流部分的 SKILL.md：

```markdown
## 工作流

### 1. 步骤名称
- 要做什么的描述
- 使用哪个技能以及如何使用

### 2. 下一步
...
```

### 规则 6：SKILL.md 结构

每个生成的 SKILL.md 必须遵循此结构：

```markdown
---
name: {skill-name}
description: >-
  {description}
---

# {技能标题}

## 概述
{技能做什么的简要描述。}

## 依赖项
{列出所需技能，如果有。}

## 快速入门
{启动的最小示例。}

## 实用脚本（如果基于 CLI）
{用示例记录每个子命令。}

## 工作流（如果指令仅）
{编号步骤，提供清晰指令。}

## 速率限制（如果适用）
{记录速率限制以及如何执行。}

## 常见错误
{列出 2-3 个常见陷阱。}
```

### 规则 7：技能位置

技能可以**本地**安装（项目特定、每个工作区）或**全局**安装（跨所有项目可用）。询问用户是否希望本地安装、全局安装或使用自定义安装路径。

技能路径由代理 CLI（本地路径相对于项目根目录）：

-   **Claude 代码**：本地 `.claude/skills/`，全局 `~/.claude/skills/`
-   **Codex**：本地 `.agents/skills/`，全局 `~/.agents/skills/`
-   **Antigravity 2.0**：本地 `.agents/skills/`，全局 `~/.gemini/config/skills/`
-   **Gemini CLI**：本地 `.gemini/skills/`，全局 `~/.gemini/skills/`
-   **OpenCode**：本地 `.opencode/skills/`，全局 `~/.config/opencode/skills/`

对于其他 CLI，请自行查找本地和全局技能路径。

## 阶段 4：验证

实施完成后：

1.  **手动测试技能**，通过使用自然语言提示调用代理来触发新技能。

2.  **如果在头脑风暴期间提供了示例查询/答案**，请运行它通过技能并验证输出是否符合预期。
