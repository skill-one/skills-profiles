## 执行前检查

**检查扩展钩子（在规范之前）**：

- 检查项目根目录中是否存在 `.specify/extensions.yml`。
- 如果存在，则读取它并查找 `hooks.before_specify` 键下的条目。
- 如果 YAML 无法解析或无效，不要静默跳过：告知用户无法读取 `.specify/extensions.yml`（包括解析错误），并且没有检查任何钩子，包括任何注册的强制（`optional: false`）钩子，然后正常继续。
- 过滤掉 `enabled` 显式为 `false` 的钩子。将没有 `enabled` 字段的钩子视为默认启用。
- 对于每个剩余的钩子，**不要**尝试解释或评估钩子 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或者它是空/无，则将钩子视为可执行。
  - 如果钩子定义了非空的 `condition`，则跳过该钩子，并将条件评估留给 HookExecutor 实现。
- 在从钩子命令名称构建命令调用时，将点（`.`）替换为连字符（`-`）。例如，`speckit.git.commit` → `/speckit-git-commit`。
- 对于每个可执行的钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子** (`optional: true`)：

    ```text
    ## 扩展钩子

    **可选预钩子**：{extension}
    命令：`/{command}`
    描述：{description}

    提示：{prompt}
    要执行：`/{command}`
    ```

  - **强制钩子** (`optional: false`)：

    ```text
    ## 扩展钩子

    **自动预钩子**：{extension}
    执行：`/{command}`
    EXECUTE_COMMAND: {command}

    在继续到 Outline 之前，等待钩子命令的结果。
    ```

    在发出上述块后，您**必须**实际调用钩子并等待其完成才能继续。以与您在此代理/会话中自己运行命令相同的方式运行它（调用方式可能与上面显示的 `{command}` 字符串字面量不同，例如，技能模式代理将其作为 `/skill:speckit-...` 或 `$speckit-...` 运行）。仅发出块本身不会运行钩子。
- 如果没有注册钩子或 `.specify/extensions.yml` 不存在，则静默跳过。

## Outline

用户在触发消息中 `/speckit-specify` 后输入的文本**是**功能描述。假设即使 `$ARGUMENTS` 出现在字面量下方，您也始终可以在本次对话中获取它。除非用户提供了空命令，否则不要要求用户重复它。

根据功能描述，执行以下操作：

1. **生成简洁的短名称**（2-4 个词）用于功能：
   - 分析功能描述并提取最相关的关键词。
   - 创建一个 2-4 个词的短名称，以捕捉功能的本质。
   - 尽可能使用动作-名词格式（例如，“add-user-auth”，“fix-payment-bug”）。
   - 保留技术术语和缩写（OAuth2、API、JWT 等）。
   - 保持简洁但描述性足够，以便一眼了解功能。
   - 示例：
     - "我想添加用户认证" → "user-auth"
     - "为 API 实现 OAuth2 集成" → "oauth2-api-integration"
     - "创建用于分析的仪表板" → "analytics-dashboard"
     - "修复支付处理超时错误" → "fix-payment-timeout"

2. **分支创建**（可选，通过钩子）：

   如果在上述执行前检查中成功运行了 `before_specify` 钩子，它将创建/切换到 git 分支，并输出包含 `BRANCH_NAME` 和 `FEATURE_NUM` 的 JSON。记下这些值以供参考，但分支名称**不**决定规范目录名称。

   如果用户显式提供了 `GIT_BRANCH_NAME`，则将其传递给钩子，以便分支脚本使用确切值作为分支名称（绕过所有前缀/后缀生成）。

3. **创建规范功能目录**：

   规范位于默认的 `specs/` 目录下，除非用户显式提供 `SPECIFY_FEATURE_DIRECTORY`。

   **`SPECIFY_FEATURE_DIRECTORY` 的解析顺序**：
   1. 如果用户显式提供了 `SPECIFY_FEATURE_DIRECTORY`（例如，通过环境变量、参数或配置），则使用它原样。
   2. 否则，在 `specs/` 下自动生成它：
      - 检查 `.specify/init-options.json` 中的 `feature_numbering`（首选）或 `branch_numbering`（已弃用，仅用于迁移——将在未来版本中删除）。
      - 如果 `"timestamp"`：前缀为 `YYYYMMDD-HHMMSS`（当前时间戳）。
      - 如果 `"sequential"` 或不存在：前缀为 `NNN`（扫描 `specs/` 中现有目录后的下一个 3 位数字）。
      - 构建目录名称：`<前缀>-<短名称>`（例如，`003-user-auth` 或 `20260319-143022-user-auth`）。
      - 设置 `SPECIFY_FEATURE_DIRECTORY` 为 `specs/<目录名称>`。
      - 如果使用了 `branch_numbering`（并且 `feature_numbering` 不存在），则发出一条警告行："⚠️ `branch_numbering` 在 init-options.json 中已弃用。重命名为 `feature_numbering`。"

   **创建目录和规范文件**：
   - `mkdir -p SPECIFY_FEATURE_DIRECTORY`
   - 通过 Spec Kit 预设/模板解析堆栈解析活动的 `spec-template`（相当于 `specify preset resolve spec-template`）。
   - 将解析的 `spec-template` 文件复制到 `SPECIFY_FEATURE_DIRECTORY/spec.md` 作为起点。
   - 设置 `SPEC_FILE` 为 `SPECIFY_FEATURE_DIRECTORY/spec.md`。
   - 将解析的路径持久化到 `.specify/feature.json`：

     ```json
     {
       "feature_directory": "<解析的功能目录>"
     }
     ```

     写入实际解析的目录路径值（例如，`specs/003-user-auth`），而不是字面量字符串 `SPECIFY_FEATURE_DIRECTORY`。
     这允许下游命令（`/speckit-plan`、`/speckit-tasks` 等）无需依赖 git 分支名称约定即可定位功能目录。

   **重要**：
   - 您必须仅在每个 `/speckit-specify` 调用中创建一个功能。
   - 规范目录名称和 git 分支名称是独立的——它们可以相同，但这由用户选择。
   - 规范目录和文件始终由此命令创建，而不是由钩子创建。

4. 加载解析的活动 `spec-template` 文件以了解所需的章节。

5. **IF EXISTS**：加载 `.specify/memory/constitution.md` 以获取项目原则和治理约束。

6. 按照以下执行流程：
   1. 从参数中解析用户描述
      如果为空：错误 "未提供功能描述"
   2. 从描述中提取关键概念
      识别：参与者、动作、数据、约束
   3. 对于不明确的方面：
      - 基于上下文和行业标准进行有根据的猜测。
      - 只有在以下情况下才标记为 `[NEEDS CLARIFICATION: specific question]`：
        - 该选择显著影响功能范围或用户体验。
        - 存在多个合理的解释，具有不同的影响。
        - 没有合理的默认值。
      - **限制**：最多 3 个 `[NEEDS CLARIFICATION]` 标记。
      - 优先考虑澄清：范围 > 安全/隐私 > 用户体验 > 技术细节
   4. 填充用户场景和测试部分
      如果没有明确用户流程：错误 "无法确定用户场景"
   5. 生成功能需求
      每个需求都必须可测试。
      为未指定细节使用合理的默认值（在假设部分中记录假设）。
   6. 定义成功标准
      创建可衡量的、与技术无关的结果。
      包括定量指标（时间、性能、容量）和定性指标（用户满意度、任务完成）。
      每个标准都必须能够在不了解实现细节的情况下验证。
   7. 识别关键实体（如果涉及数据）。
   8. 返回：成功（规范已准备好进行规划）

7. 使用模板结构将规范写入 `SPEC_FILE`，将占位符替换为从功能描述（参数）中派生的具体细节，同时保留章节顺序和标题。

8. **规范质量验证**：在写入初始规范后，根据质量标准进行验证：

   a. **创建规范质量检查清单**：使用检查清单模板结构生成检查清单文件，位于 `SPECIFY_FEATURE_DIRECTORY/checklists/requirements.md`，包含以下验证项：

   ```markdown
   # 规范质量检查清单：[功能名称]

   **目的**：在继续规划之前验证规范的完整性和质量
   **创建**：[日期]
   **功能**：[Link to spec.md]

   ## 内容质量

   - [ ] 无实现细节（语言、框架、API）
   - [ ] 聚焦于用户价值和业务需求
   - [ ] 面向非技术利益相关者
   - [ ] 所有必需章节已完成

   ## 需求完整性

   - [ ] 无 `[NEEDS CLARIFICATION]` 标记剩余
   - [ ] 需求是可测试且无歧义的
   - [ ] 成功标准是可衡量的
   - [ ] 成功标准是与技术无关的（无实现细节）
   - [ ] 所有验收场景已定义
   - [ ] 已识别边缘情况
   - [ ] 范围明确界定
   - [ ] 依赖项和假设已识别

   ## 功能就绪

   - [ ] 所有功能需求都有明确的验收标准
   - [ ] 用户场景涵盖主要流程
   - [ ] 功能满足成功标准中定义的可衡量结果
   - [ ] 规范中未泄露任何实现细节

   ## 备注

   - 标记为不完整的项需要在 `/speckit-clarify` 或 `/speckit-plan` 之前更新规范
   ```

   b. **运行验证检查**：根据每个检查清单项审查规范：
   - 对于每个项，确定是否通过或失败
   - 记录发现的具体问题（引用相关的规范部分）

   c. **处理验证结果**：

   - **如果所有项都通过**：标记检查清单为完成，并继续到必需的执行后钩子部分

   - **如果项失败（不包括 `[NEEDS CLARIFICATION]`）**：
     1. 列出失败的项和具体问题
     2. 更新规范以解决每个问题
     3. 重新运行验证，直到所有项通过（最多 3 次迭代）
     4. 如果 3 次迭代后仍然失败，则在检查清单备注中记录剩余问题并警告用户

   - **如果 `[NEEDS CLARIFICATION]` 标记剩余**：
     1. 从规范中提取所有 `[NEEDS CLARIFICATION: ...]` 标记
     2. **限制检查**：如果标记超过 3 个，请保留 3 个最关键的（按范围/安全/UX 影响），并为其余部分进行有根据的猜测
     3. 对于每个需要澄清的（最多 3 个），以以下格式向用户呈现选项：

        ```markdown
        ## 问题 [N]：[主题]

        **上下文**：[引用相关的规范部分]

        **我们需要了解什么**：[来自 NEEDS CLARIFICATION 标记的特定问题]

        **建议答案**：

        | 选项 | 答案                    | 影响                          |
        | ------ | ------------------------- | ------------------------------------- |
        | A      | [第一个建议答案]  | [这对功能意味着什么]     |
        | B      | [第二个建议答案] | [这对功能意味着什么]     |
        | C      | [第三个建议答案]  | [这对功能意味着什么]     |
        | Custom | 提供您自己的答案   | [解释如何提供自定义输入] |

        **您的选择**： _[等待用户响应]_
        ```

     4. **关键 - 表格格式**：确保 markdown 表格格式正确：
        - 使用一致的间距，管道对齐
        - 每个单元格应包含空格：`| 内容 |` 而不是 `|内容|`
        - 标题分隔符必须至少有 3 个连字符：`|--------|`
        - 测试 markdown 预览中表格是否正确渲染
     5. 顺序编号问题（Q1、Q2、Q3 - 最多 3 个总问题）
     6. 在等待响应之前一起呈现所有问题
     7. 等待用户对所有问题的选择做出响应（例如，"Q1: A, Q2: Custom - [细节], Q3: B"）
     8. 通过用户选择或提供的答案更新规范，替换每个 `[NEEDS CLARIFICATION]` 标记
     9. 所有澄清解决后重新运行验证

   d. **更新检查清单**：每次验证迭代后，更新检查清单文件以显示当前的通过/失败状态

## 快速指南

- 关注用户需要的**什么**以及**为什么**。
- 避免如何实现（不涉及技术栈、API、代码结构）。
- 面向业务利益相关者，而不是开发人员。
- **不要**创建嵌入在规范中的任何检查清单。那将是另一个命令。

### 章节要求

- **必需章节**：每个功能都必须完成
- **可选章节**：仅在相关时包含
- 当章节不适用时，完全删除它（不要保留为 "N/A"）

### 对于 AI 生成

从用户提示创建此规范时：

1. **做出有根据的猜测**：使用上下文、行业标准和常见模式来填补空白
2. **记录假设**：在假设部分中记录合理的默认值
3. **限制澄清**：最多 3 个 `[NEEDS CLARIFICATION]` 标记 - 仅用于对关键决策的澄清，这些决策：
   - 显著影响功能范围或用户体验
   - 具有多个合理的解释，具有不同的影响
   - 缺乏任何合理的默认值
4. **优先考虑澄清**：范围 > 安全/隐私 > 用户体验 > 技术细节
5. **像测试员一样思考**：每个模糊的需求都应失败 "可测试且无歧义" 的检查项
6. **需要澄清的常见区域**（如果不存在合理的默认值）：
   - 功能范围和边界（包括/排除特定用例）
   - 用户类型和权限（如果可能存在多个冲突的解释）
   - 安全/合规要求（当法律/财务重要时）

**合理的默认值示例**（不要询问这些）：

- 数据保留：该领域行业标准实践
- 性能目标：标准 Web/移动应用预期，除非指定
- 错误处理：用户友好的消息，带有适当的回退
- 认证方法：Web 应用中的标准会话或 OAuth2
- 集成模式：使用项目适当的模式（Web 服务使用 REST/GraphQL，库使用函数调用，工具使用 CLI 参数等）

### 成功标准指南

成功标准必须：

1. **可衡量**：包括特定指标（时间、百分比、计数、速率）
2. **与技术无关**：不提及框架、语言、数据库或工具
3. **以用户/业务为中心**：从用户/业务角度描述结果，而不是系统内部
4. **可验证**：可以在不了解实现细节的情况下测试/验证

**良好示例**：

- "用户可以在 3 分钟内完成结账"
- "系统支持 10,000 个并发用户"
- "95% 的搜索在 1 秒内返回结果"
- "任务完成率提高了 40%"

**不良示例**（以实现为中心）：

- "API 响应时间低于 200ms"（太技术性，使用 "用户立即看到结果"）
- "数据库可以处理 1000 TPS"（实现细节，使用用户面
