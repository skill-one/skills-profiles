## 执行前检查

**检查扩展钩子（在澄清之前）**：

- 检查项目根目录中是否存在 `.specify/extensions.yml`。
- 如果存在，则读取它并查找 `hooks.before_clarify` 键下的条目。
- 如果 YAML 无法解析或无效，不要无声地跳过：告知用户无法读取 `.specify/extensions.yml`（包括解析错误），并且没有检查任何钩子，包括任何注册的强制（`optional: false`）钩子，然后正常继续。
- 过滤掉 `enabled` 显式为 `false` 的钩子。将没有 `enabled` 字段的钩子视为默认启用。
- 对于每个剩余的钩子，**不要**尝试解释或评估钩子 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或者它是空/空，则将钩子视为可执行。
  - 如果钩子定义了非空的 `condition`，则跳过该钩子，并将条件评估留给 HookExecutor 实现。
- 在从钩子命令名称构建命令调用时，将点（`.`）替换为连字符（`-`）。例如，`speckit.git.commit` → `/speckit-git-commit`。
- 对于每个可执行的钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子** (`optional: true`)：

    ```text
    ## 扩展钩子

    **可选预钩子**：{extension}
    命令：`/{command}`
    描述：{description}

    提示：{prompt}
    执行：`/{command}`
    ```

  - **强制钩子** (`optional: false`)：

    ```text
    ## 扩展钩子

    **自动预钩子**：{extension}
    执行：`/{command}`
    EXECUTE_COMMAND: {command}

    在继续到 Outline 之前，等待钩子命令的结果。
    ```

    在发出上述块后，您**必须**实际调用钩子并等待其完成才能继续。以您在此代理/会话中自己运行命令的方式运行它（调用方式可能与上面显示的 `{command}` ID 不同，例如，技能模式代理将其运行为 `/skill:speckit-...` 或 `$speckit-...`）。仅发出块本身不会运行钩子。
- 如果没有注册钩子或 `.specify/extensions.yml` 不存在，则无声地跳过

## Outline

目标：检测并减少活动功能规范中的歧义或缺失决策点，并将澄清直接记录在规范文件中。

注意：此澄清工作流预计在调用 `/speckit-plan` 之前运行（并完成）。如果用户明确表示要跳过澄清（例如，探索性尖峰），您可以继续，但必须警告下游返工风险增加。

执行步骤：

1. 从仓库根目录运行 `.specify/scripts/bash/check-prerequisites.sh --json --paths-only` **一次**（组合 `--json --paths-only` 模式 / `-Json -PathsOnly`）。解析最小的 JSON 有效负载字段：
   - `FEATURE_DIR`
   - `FEATURE_SPEC`
   - （可选地捕获 `IMPL_PLAN`，`TASKS` 以便将来串联流程。）
   - 如果 JSON 解析失败，则中止并指示用户重新运行 `/speckit-specify` 或验证功能分支环境。
   - 对于像 "I'm Groot" 这样的参数中的单引号，使用转义语法：例如 'I'\''m Groot'（如果可能，也可以使用双引号："I'm Groot"）。

2. **如果存在**：加载 `.specify/memory/constitution.md` 以获取项目原则和治理约束。

3. 加载当前规范文件。使用此分类结构进行结构化歧义和覆盖扫描。对于每个类别，标记状态：清晰 / 部分缺失。生成一个用于优先级的内部覆盖图（除非没有问题会提出，否则不要输出原始图）。

   功能范围和行为：
   - 核心用户目标和成功标准
   - 明确的超出范围声明
   - 用户角色 / 个性差异

   领域和数据模型：
   - 实体、属性、关系
   - 身份和唯一性规则
   - 生命周期/状态转换
   - 数据量 / 规模假设

   交互和 UX 流程：
   - 关键用户旅程 / 序列
   - 错误/空/加载状态
   - 可访问性或本地化说明

   非功能性质量属性：
   - 性能（延迟、吞吐量目标）
   - 可扩展性（水平/垂直、限制）
   - 可靠性和可用性（正常运行时间、恢复预期）
   - 可观察性（日志记录、指标、跟踪信号）
   - 安全和隐私（身份验证/零身份验证、数据保护、威胁假设）
   - 合规性 / 监管约束（如果有）

   集成和外部依赖：
   - 外部服务和 API 以及故障模式
   - 数据导入/导出格式
   - 协议/版本假设

   边缘情况和故障处理：
   - 负面场景
   - 速率限制 / 流量限制
   - 冲突解决（例如，并发编辑）

   约束和权衡：
   - 技术约束（语言、存储、托管）
   - 明确的权衡或拒绝的替代方案

   术语和一致性：
   - 规范词汇表术语
   - 避免 同义词 / 已弃用的术语

   完成信号：
   - 可接受标准测试可行性
   - 可衡量的完成定义样式指标

   其他 / 占位符：
   - TODO 标记 / 未解决的决策
   - 歧义的形容词（"健壮"、"直观"）缺乏量化

   对于状态为部分或缺失的每个类别，除非：
   - 澄清不会实质性地改变实现或验证策略
   - 该项目专门关于实现方法、技术栈比较或任务分解（内部记录）

4. 生成（内部）一个优先级队列的候选澄清问题（最多 5 个）。不要一次全部输出。应用以下约束：
   - 整个会话中最多 5 个问题。
   - 每个问题必须能够用以下任何一种方式回答：
     - 一个简短的选择题（2-5 个不同的、互斥的选项），或
     - 一个单词 / 短语回答（明确限制："回答不超过 5 个字"）。
   - 仅包括其答案实质性影响架构、数据建模、任务分解、测试设计、UX 行为、运营就绪或合规验证的问题。
   - 确保类别覆盖平衡：首先尝试覆盖最高影响的未解决类别；避免在单个高影响区域（例如，安全态势）未解决时询问两个低影响问题。
   - 排除已回答的问题、琐碎的样式偏好或计划级执行细节（除非阻塞正确性）。
   - 优先考虑减少下游返工风险或防止对齐的接受测试的澄清。
   - 如果有超过 5 个类别未解决，则按（影响 * 不确定性）启发式选择前 5 个。

5. 顺序提问循环（交互式）：
   - 一次只呈现一个确切的问题。
   - **问题编写质量（适用于每个问题，选择题或简答题）**：
     - 以 `**问题：**` 开头，后跟一个以 `?` 结尾的完整疑问句。问题文本在 `?` 之前必须单独有意义。
     - **永远**不要使用主题标签、部分标题或需求 ID 作为问题本身。例如，`Acceptance device/runtime matrix (FR-023)` 是无效的——它是一个标签，不是问题。
     - 在 `?` 之后，唯一允许的后缀是可选的括号内需求/问题 ID。确切格式：`**问题：** <疑问句>?` 或 `**问题：** <疑问句>? (FR-023)`。永远不要将 ID 放在 `?` 之前，并且永远不要使用 ID（单独或与主题标签一起）作为整个提示。
     - 紧接着问题行，添加一个简明扼要的 "为什么重要" 句子（接受或交付的利害关系）之前。
     - 使用日常用语；仅在定义相同句子的情况下引入术语。自我检查：一个不知道 Spec Kit 的读者仅凭问题行就能回答。简洁即可；晦涩的标签不可取。
   - 对于选择题：
     - **分析所有选项** 并根据以下确定**最合适的选项**：
       - 项目的最佳实践
       - 类似实现中的常见模式
       - 风险降低（安全、性能、可维护性）
       - 与规范中可见的任何明确项目目标或约束对齐
     - 将**推荐选项**突出显示在顶部，并提供清晰的理由（1-2 句话解释为什么这是最佳选择）。
     - 格式为：`**推荐：** 选项 [X] - <理由>`
     - 然后以 Markdown 表格形式渲染所有选项：

     <!-- markdownlint-disable MD058 -->

     | 选项 | 描述                                                                                         |
     | ---- | --------------------------------------------------------------------------------------------------- |
     | A    | <选项 A 描述>                                                                              |
     | B    | <选项 B 描述>                                                                              |
     | C    | <选项 C 描述>（如有需要，可添加 D/E，最多 5 个）                                                  |
     | 简短 | 提供不同的简短答案（<=5 个字）（仅当自由形式替代方案合适时包含） |

     <!-- markdownlint-enable MD058 -->
     - 在表格之后，添加：`您可以回复选项字母（例如，"A"），通过说 "yes" 或 "recommended" 接受推荐，或提供您自己的简短答案。`

   - 对于简答题样式（没有有意义的离散选项）：
     - 根据最佳实践和上下文提供您的**建议答案**。
     - 格式为：`**建议：** <您提出的答案> - <简要理由>`
     - 然后输出：`格式：简短答案（<=5 个字）。您可以通过说 "yes" 或 "suggested" 接受建议，或提供您自己的答案。`
   - 用户回答后：
     - 如果用户回复 "yes"、"recommended" 或 "suggested"，则使用您之前声明的推荐/建议作为答案。
     - 否则，验证答案是否映射到选项或符合 <=5 字约束。
     - 如果不明确，请快速消除歧义（计数仍属于同一问题；不要前进）。
     - 满意后，将其记录在工作内存中（不要立即写入磁盘），然后转到下一个排队的问题。
   - 当出现以下情况时停止提问：
     - 所有关键歧义在早期解决（剩余排队项变得不必要），或
     - 用户发出完成信号（"done"、"good"、"no more"），或
     - 您达到 5 个已问问题。
   - 永远不要提前透露未来排队的问题。
   - 如果开始时没有有效问题，请立即报告没有关键歧义。

6. 每次接受答案后的集成（增量更新方法）：
   - 维护规范（在开始时加载一次）和原始文件内容的内存表示。
   - 对于此会话中的第一个集成答案：

   - 然后立即将澄清应用于最合适的部分：
     - 功能歧义 → 更新或添加功能需求的点。
     - 用户交互 / 演员区分 → 使用澄清的角色、约束或场景更新用户故事或演员子部分（如果存在）。
     - 数据形状 / 实体 → 更新数据模型（添加字段、类型、关系）并保留顺序；简要记录添加的约束。
     - 非功能性约束 → 在可衡量的成果 > 可衡量的结果中添加/修改可衡量的标准（将模糊形容词转换为指标或明确目标）。
     - 边缘情况 / 负面流程 → 在边缘情况 / 错误处理下添加新的点（如果模板提供此类占位符）。
     - 术语冲突 → 在规范中标准化术语；仅在必要时保留原始术语，并添加 `(以前称为 "X")` 一次。
   - 如果澄清使早期模糊的声明失效，则替换该声明，而不是重复；不要保留过时的矛盾文本。
   - 每次集成后保存规范文件，以最大程度地减少上下文丢失的风险（原子覆盖）。
   - 保留格式：不要重新排序不相关的部分；保持标题层次结构完整。
   - 保持每个插入的澄清简短且可测试（避免叙述漂移）。

7. 验证（每次写入后和最终遍历执行）：
   - 澄清会话包含每个接受答案的恰好一个点（无重复）。
   - 已问（接受）问题 ≤ 5。
   - 更新部分不包含新的模糊占位符，该占位符旨在解决新答案。
   - 没有保留矛盾的早期声明（扫描当前无效的替代选项已移除）。
   - Markdown 结构有效；仅允许的新标题：`## 澄清`，`### 会话 YYYY-MM-DD`。
   - 术语一致性：所有更新部分使用相同的规范术语。

   - 如果它不存在，则无声地跳过此步骤。
   - 如果它存在：

     2. 识别所有 GitHub 任务列表复选框行——与 `- [ ]`、`- [x]` 或 `- [X]`（不区分大小写，容忍嵌套项的领先空白）匹配的行，忽略所有其他内容（标题、注释、非复选框点、元数据）。
     3. 对于每个复选框行，将其当前标记状态（已检查或未检查）和项目文本记录到快照列表中。
     4. 重新评估每个复选框项相对于**更新**的规范（在步骤 7 中刚刚保存的版本）。
     5. 对于每个复选框项，仅在其检查/未检查状态实际改变时更新：
        - 如果项目现在通过且未检查：将 `[ ]` 改为 `[x]`。
        - 如果项目现在失败且已检查：将 `[x]`/`[X]` 改为 `[ ]`。
        - 如果状态未改变：保持标记不变（保留现有大小写以避免外观差异）。
     6. 保存更新的检查清单文件。**仅切换 `[ ]`/`[x]` 标记部分**，其状态已更改的复选框行。所有其他文件内容——标题、元数据、注释、行顺序、空白——必须保持不变以避免嘈杂的差异。
     7. 比较快照与当前状态，以计算三个列表用于完成报告：
        - **新通过**：更改从未检查到检查的项目。
        - **回退**：更改从未检查到检查的项目。
        - **仍未检查**：保持未检查的项目。
     8. 记录检查/总数复选框项（例如，"12/16 → 15/16 项通过"）。

行为规则：

- 如果没有发现有意义的歧义（或所有潜在问题都是低影响的），则回复："未检测到值得正式澄清的关键歧义。"并建议继续。
