### 3. 构建语义模型

创建内部表示（输出中不包括原始工件）：

- **需求清单**：对于每个功能需求（FR-###）和成功标准（SC-###），记录一个稳定的键。当存在时，使用显式的 FR-/SC- 标识符作为主要键，并且还可以选择派生一个祈使短语别名以提高可读性（例如，“用户可以上传文件”→ `user-can-upload-file`）。仅包括需要可构建工作的成功标准项（例如，负载测试基础设施、安全审计工具），并排除发布后结果指标和业务 KPI（例如，“将支持工单减少 50%”）。
- **用户故事/动作清单**：具有接受标准的离散用户动作
- **任务覆盖映射**：将每个任务映射到一个或多个需求或故事（通过关键词/显式引用模式，如 ID 或关键短语进行推断）
- **宪法规则集**：提取原则名称和 MUST/SHOULD 规范性声明

### 4. 检测传递（令牌高效分析）

专注于高信号发现。限制为总共 50 个发现；将剩余部分汇总到溢出摘要中。

#### A. 重复检测

- 识别近似重复的需求
- 标记低质量措辞以供合并

#### B. 歧义检测

- 标记缺乏可衡量标准的模糊形容词（快速、可扩展、安全、直观、健壮）
- 标记未解决的占位符（TODO、TKTK、???、`<placeholder>` 等）

#### C. 未明确说明

- 具有动词但缺少对象或可衡量结果的需求
- 缺乏与接受标准对齐的用户故事
- 引用规范/计划中未定义的文件或组件的任务

#### D. 宪法对齐

- 任何与 MUST 原则冲突的需求或计划元素
- 缺少宪法规定的强制部分或质量门禁

#### E. 覆盖差距

- 没有相关任务的需求
- 没有映射到需求/故事的任务
- 需要可构建工作的成功标准（性能、安全、可用性）未在任务中反映

#### F. 不一致性

- 术语漂移（跨文件不同地命名同一概念）
- 计划中引用但在规范中缺失的数据实体（反之亦然）
- 任务排序矛盾（例如，集成任务在基础设置任务之前而没有依赖说明）
- 冲突的需求（例如，一个要求 Next.js，而另一个指定 Vue）

### 5. 严重性分配

使用此启发式方法来优先处理发现：

- **CRITICAL**：违反宪法 MUST、缺少核心规范工件，或需求与零覆盖且阻止基本功能

- **MEDIUM**：术语漂移、缺少非功能性任务覆盖、未明确说明的边缘情况
- **LOW**：样式/措辞改进、不影响执行顺序的轻微冗余

## 操作原则

### 上下文效率

- **最小高信号令牌**：专注于可操作的发现，而不是详尽的文档

- **确定性结果**：在不更改的情况下重新运行应产生一致的 ID 和计数

- **零问题优雅报告**（发出成功报告并包含覆盖率统计）
