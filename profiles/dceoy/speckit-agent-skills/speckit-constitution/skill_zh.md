## 用户输入

```text
$ARGUMENTS
```

在继续之前，您**必须**考虑用户输入（如果非空）。

## 范围保护

此命令自身的工作仅限于更新项目章程本身。依赖的模板和命令在运行时读取章程，在此处不会被修改。

- 将用户输入的每个部分分类为章程内容或单独的、非治理意图。
- 如果输入包含功能实现、代码生成、重构、构建或部署请求，您**必须**不执行它们。将它们提取为延迟意图。
- 您**必须**不创建、修改或删除与应用程序源文件、功能路由、组件、测试、部署文件或其他与章程工作流无关的工件。
- 如果不确定某条指令是否为章程内容，请在做出更改前请求澄清。
- 完成章程更新后，为每个延迟意图包含一个“下一步操作”部分。列出原始意图，并建议适当的后续 Spec Kit 命令，例如 `/speckit-specify`，但不调用它。
- 如果没有非治理意图，则省略“下一步操作”部分。

## 执行前检查

**检查扩展钩子（在章程更新之前）**：

- 检查项目根目录中是否存在 `.specify/extensions.yml`。
- 如果存在，读取它并查找 `hooks.before_constitution` 键下的条目
- 如果 YAML 无法解析或无效，不要无声地跳过：告诉用户 `.specify/extensions.yml` 无法读取（包括解析错误），并且没有检查钩子，包括任何注册的强制（`optional: false`）钩子，然后正常继续
- 过滤掉 `enabled` 显式为 `false` 的钩子。将没有 `enabled` 字段的钩子视为默认启用。
- 对于每个剩余的钩子，**不要**尝试解释或评估钩子 `condition` 表达式：
  - 如果钩子没有 `condition` 字段，或者它是 null/空，将钩子视为可执行
  - 如果钩子定义了非空的 `condition`，跳过钩子，并将条件评估留给 HookExecutor 实现
- 在从钩子命令名称构建命令调用时，将点（`.`）替换为连字符（`-`）。例如，`speckit.git.commit` → `/speckit-git-commit`。
- 对于每个可执行的钩子，根据其 `optional` 标志输出以下内容：
  - **可选钩子** (`optional: true`)：

    ```text
    ## 扩展钩子

    **可选预钩子**：{extension}
    命令：`/{command}`
    描述：{description}

    提示：{prompt}
    要执行：`/{command}`
    ```
  - **强制钩子** (`optional: false`)：

    ```text
    ## 扩展钩子

    **自动预钩子**：{extension}
    执行：`/{command}`
    EXECUTE_COMMAND：{command}

    在继续到 Outline 之前，等待钩子命令的结果。
    ```

    在发出上述块后，您**必须**实际调用钩子并等待它完成才能继续。以您在此代理/会话中自己运行命令的方式运行它（调用可能与上面显示的 `{command}` 字面量 ID 不同，例如，技能模式代理作为 `/skill:speckit-...` 或 `$speckit-...` 运行它）。仅发出块不会运行钩子。
- 如果没有注册钩子或 `.specify/extensions.yml` 不存在，则无声地跳过

## Outline

您正在更新 `.specify/memory/constitution.md` 中的项目章程。在命令执行时，活动的章程脚本是通过对 `constitution-template` 通过 Spec Kit 预设/模板解析堆栈解析得出的。

遵循以下执行流程：

1. 从仓库根目录运行 `.specify/scripts/bash/resolve-template.sh constitution-template --json` 并将 `TEMPLATE_CONTENT` 解析为活动模板。
   - 共享解析器在核心模板回退之前应用项目覆盖，组合预设层和扩展层。它必须在继续之前成功。
   - 如果失败，停止并报告解析错误；不要仅使用一个贡献的模板层继续。
   - 如果 `.specify/memory/constitution.md` 存在，将其加载为当前项目特定值和修订的来源。保留在应用新解析的脚手架时仍然适用的信息。
   - 如果不存在，使用解析的模板作为初始文档。
   - 不要写回任何版本化的模板层。
   - 识别每个形式为 `[ALL_CAPS_IDENTIFIER]` 的占位符标记。
     **重要**：用户可能需要比模板中使用的原则更少或更多。如果指定了数字，请尊重这一点 - 遵循一般模板。您将相应地更新文档。

2. 收集/推导占位符的值：
   - 如果用户输入（对话）提供了值，则使用它。
   - 否则，从现有的仓库上下文（README、文档、如果嵌入则嵌入的先前章程版本）中推断。
   - 对于治理日期：`RATIFICATION_DATE` 是原始采用日期（如果未知则询问或标记 TODO），`LAST_AMENDED_DATE` 如果做出更改则是今天，否则保持之前。
   - `CONSTITUTION_VERSION` 必须根据语义版本规则递增：
     - MAJOR：向后不兼容的治理/原则删除或重新定义。
     - MINOR：添加新原则/部分或实质性扩展指南。
     - PATCH：澄清、措辞、拼写错误修复、非语义改进。
   - 如果版本提升类型不明确，请在最终确定之前提出理由。

3. 使用解析的模板作为所需结构起草更新的章程内容：
   - 用具体文本替换每个占位符（不要留下括号内的标记，除非是项目选择不定义的故意保留的模板槽位——明确说明任何留下的）。
   - 保留标题层次结构，注释可以在替换后删除，除非它们仍然提供澄清指导。
   - 确保每个原则部分：简洁的名称行、段落（或项目符号列表）捕获不可协商的规则、如果不明显则显式说明理由。
   - 确保治理部分列出修订程序、版本控制策略和合规性审查期望。

4. 在更新后，在章程文件顶部作为 HTML 注释生成同步影响报告。
   此报告是供人类审查修订的临时草稿材料，不是治理内容；预计在提交修订后的章程文件之前将其删除。
   - 版本更改：旧 → 新
   - 修改的原则列表（旧标题 → 如果重命名则新标题）
   - 添加的部分
   - 删除的部分
   - 如果有任何占位符故意延迟，则列出后续 TODO。

5. 最终输出前的验证：
   - 没有剩余未解释的括号标记。
   - 版本行与报告匹配。
   - 日期 ISO 格式 YYYY-MM-DD。
   - 原则是声明性的、可测试的，并且没有模糊语言（"应该" → 在适当的地方替换为 MUST/SHOULD 理由）。

6. 将完成的章程写回 `.specify/memory/constitution.md`（覆盖）。

7. 向用户输出最终摘要，包括：
   - 新版本和提升理由。
   - 任何 TODO 占位符或需要手动跟进的延迟项。
   - 建议的提交信息（例如，`docs: 修订章程到 vX.Y.Z (原则添加 + 治理更新)`）。
   - 任何延迟的非治理意图的“下一步操作”部分。

格式和样式要求：

- 使用模板中完全相同的 Markdown 标题（不要降级/升级级别）。
- 将长理由行包装起来以保持可读性（理想情况下 <100 字符），但不要用不自然的换行强制执行。
- 在部分之间保留一个空行。
- 避免尾随空格。

如果用户提供部分更新（例如，仅一个原则修订），仍然执行验证和版本决策步骤。

如果关键信息缺失（例如，批准日期确实未知），插入 `TODO(<FIELD_NAME>): 解释` 并包括在同步影响报告的延迟项下。

仅写入 `.specify/memory/constitution.md`；不要创建或修改模板源文件。
