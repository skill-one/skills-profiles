# Google Cloud 解决方案架构工作流

## 工作流概述

该工作流包含以下阶段：

*   **阶段 1：需求发现**。收集与用户需要协助的云工作负载或用例相关的详细需求。
*   **阶段 2：解决方案架构**。使用阶段 1 中收集的需求，为云工作负载或用例生成详细的解决方案架构。
*   **阶段 3：解决方案验证**。创建验证已生成解决方案的计划，生成验证说明和脚本，并将其提供给用户执行（或经用户明确授权进行干跑验证）。
*   **阶段 4：解决方案打包和展示**。整合已生成的内容，并展示解决方案。

**关于工作流的重要说明**：

*   **严格的阶段划分**：在阶段 1（需求发现）中，当您向用户询问澄清问题时，不要推荐、提出或概述任何架构设计、技术分解、云服务或组件映射。在功能和非功能需求彻底评估之前提出解决方案会导致确认偏差，并过早地将解决方案锚定在特定产品、功能或工具上。

*   **迭代审批与任务转换**：对于此工作流中的每个交付物（技术分解、产品推荐、图表、架构描述和部署脚本），请明确将您的输出展示给用户以供审批。如果用户要求修改，请迭代修订内容，直到获得批准后再进入后续任务或阶段。

*   **代码和脚本的无自主执行**：未经用户明确、无歧义的授权，不要运行您生成的任何脚本或代码。自主执行脚本可能会配置未计划的云资源（导致意外成本）、修改运行中的基础设施，或带来安全和安全风险。始终提供让用户手动执行命令的选项。

*   **可以跳过某些阶段的情况**：如果用户的提示表明此工作流中的特定阶段或任务已完成或已批准（例如，“需求发现阶段已完成”、“产品选择已批准”或“架构已确认”），请不要重复该阶段或任务。直接跳转到请求的任务（例如生成技术分解、推荐产品或编译解决方案指南）。

## 阶段 1：需求发现

1.  收集与用户需要协助的工作负载或用例相关的以下需求。

    **关键**：在用户提供这些需求之前，您绝不能生成任何架构设计、产品推荐或技术分解。

    *   **功能需求**：请用户描述其工作负载的业务流程、活动和用例。
    *   **非功能需求**：请用户描述安全、隐私、合规、可靠性、灾难恢复、成本、运营、性能和可持续性方面的需求。
        *   **关键**：如果非功能需求缺失或不完整，您必须要求用户描述需求，并明确解释其重要性（例如，因为它们直接决定了运营 SLA、可用性级别、扩展配置、成本预算、资源类型和安全态势）。
    *   **当前状态**：询问工作负载是否目前在其他云提供商或本地运行（如果是，请提示提供现有部署的架构）。
    *   **系统依赖关系**：请用户描述其应用程序与其他工作负载、产品、系统或工具之间的任何依赖关系。

2.  审查用户迄今为止提供的输入，并检查是否存在任何模糊不清或矛盾之处（例如，完全网络隔离与零互联网暴露的冲突目标，与从公共 API 进行实时摄取）。

    如果您在用户的需求数据中发现任何模糊不清或矛盾之处，您必须：

    *   清晰地描述模糊不清和矛盾之处。
    *   解释为什么矛盾的需求数不能同时满足。
    *   要求用户澄清其权衡偏好和选择，以解决模糊不清和矛盾之处。
        *   如果用户将选择权委托给您（例如，用户回复“做你认为最好的”或“你决定”），则提供明确的建议来解决模糊不清或矛盾之处，解释您的推理，并要求用户批准您的建议。

    **关键**：直到您识别的所有模糊不清和矛盾之处都得到解决，否则不要推荐或生成任何架构设计、技术分解或 Google Cloud 产品推荐。模糊不清或矛盾的需求会导致无效的架构假设。

3.  生成工作负载组件的技术分解，将解决方案分解为逻辑组件。在进入阶段 2 之前，向用户展示并获取批准。

    **关键**：在进入阶段 2 之前，确保用户已批准技术分解。技术分解与用户需求的不一致将使此工作流后续阶段的输出无效。

## 阶段 2：解决方案架构

使用阶段 1 中批准的需求生成全面的解决方案架构。

### 所有生成内容的基础

为确保此阶段每个任务生成的內容与最新的官方 Google Cloud 指南一致，您必须使用以下资源对生成内容进行基础：

*   Google Developer Knowledge MCP 服务器
    *   服务器：https://developerknowledge.googleapis.com/mcp
    *   工具：
    *   `developerknowledge:search_documents`
    *   `developerknowledge:get_documents`
    *   `developerknowledge:answer_query`
*   https://github.com/google/skills 中的相关技能
*   官方 Google Cloud 文档，包括以下内容：
    *   与工作负载技术类别相关的参考架构和设计指南：`references/architecture-guides.md`
    *   与工作负载相关的产品和主题的决策指南：`references/decision-making-guides.md`
    *   与工作负载相关的产品和主题的最佳实践指南：`references/best-practices-guides.md`

对于生成指南中的每个项目，您必须包含对相关官方 Google Cloud 文档页面的引用。

### 任务 2.1：识别工作负载所需的 Google Cloud 产品和功能

1.  推荐适合用户工作负载每个组件的产品和功能。

    **关键**：

    *   不要推荐任何已弃用、已退役、已停用或不受支持的产品或功能。要检查产品或功能的状态，请使用 `developerknowledge:answer_query` 或 `developerknowledge:search_documents` 并使用查询字符串，如：“{product_name} 发布状态”。
    *   如果多个产品或功能可用于工作负载的某个组件，则执行以下操作：
        *   推荐最合适的产品或功能。当存在替代产品时，相关的产品文档可能会提供有关何时选择每个产品的指导。遵循该指导。
        *   提及可用的替代产品或功能。
        *   解释每个替代产品或功能的优缺点。

2.  将生成的产品推荐展示给用户，并询问是否需要任何更改。

    **关键**：在同一个回合中不要生成任何其他内容（架构图表、描述或部署配置）。在用户批准产品选择之前，立即停止执行。

3.  用户批准产品选择后，继续执行任务 2.2。

### 任务 2.2：生成架构图表

1.  使用 Mermaid 格式生成架构图表：https://github.com/mermaid-js/mermaid。
2.  在继续执行任务 2.3 之前，向用户展示生成的图表并获取批准。

### 任务 2.3：生成架构描述

1.  生成描述，解释每个组件的目的、组件之间的关系以及任务流或数据流。
2.  在继续执行任务 2.4 之前，向用户展示生成的架构描述并获取批准。

### 任务 2.4：生成设计建议

1.  根据工作负载的需求，为架构中的每个组件生成设计建议和最佳实践，以优化其配置。
    **重要**：

    *   在生成设计建议时，请包含以下内容：
        *   阶段 1 中收集的功能需求。
        *   阶段 1 中收集的非功能需求。
    *   为生成非功能需求的指南，请根据需要使用以下技能：
        -   `google-cloud-waf-security`
        -   `google-cloud-waf-reliability`
        -   `google-cloud-waf-cost-optimization`
        -   `google-cloud-waf-operational-excellence`
        -   `google-cloud-waf-performance-optimization`
        -   `google-cloud-waf-sustainability`

    如果当前工作空间中不可用任何 `google-cloud-waf-*` 技能，请直接从 `references/best-practices-guides.md` 中的文档参考推导设计指南。

2.  将生成的建议展示给用户，并在继续执行任务 2.5 之前获取批准。

### 任务 2.5：生成部署指南

1.  生成部署指南，包括基础设施即代码和启用用户部署解决方案的说明。
2.  在继续执行阶段 3 之前，向用户展示生成的部署指南并获取批准。

## 阶段 3：解决方案验证

### 任务 3.1：部署前验证

1.  创建部署前计划，以静态验证已生成的解决方案，并验证其是否满足工作负载的需求，而无需配置实时资源：
    *   **部署干跑**：使用干跑命令（例如 `terraform plan` 或（在支持的情况下）`gcloud ... --dry-run`）验证基础设施语法并预览将要配置的资源。
    *   **架构与策略分析**：对网络路由拓扑、防火墙规则和 IAM 执行进行静态验证，以符合最佳实践。
2.  向用户展示静态验证计划，并获取用户执行干跑命令的明确授权。如果用户授权，则运行命令；否则，或如果用户更喜欢，请提供用户可以手动运行的精确命令。
3.  解决干跑检查期间发现的任何错误或策略差异，直到验证成功。
4.  继续执行任务 3.2

### 任务 3.2：运行时验证（部署后）

1.  询问用户是否选择现在部署基础设施以执行实时运行时验证，或直接跳转到阶段 4。
2.  **如果用户选择部署基础设施**：
    *   用户部署基础设施后，生成运行时验证命令（使用 `curl`、`ping` 或 `gcloud` 等工具），并将其提供给用户执行，以测试实时端点可达性、网络路径和负载均衡器路由。
    *   解决部署或运行时路由问题，直到检查通过。
3.  继续执行阶段 4。

## 阶段 4：解决方案打包和展示

将所有生成的文本和代码工件打包，以进行最终展示。

1.  将阶段 2 和阶段 3 生成的文本工件整合到一个名为 `solution-architecture-guide.md` 的 Markdown 文件中，基于 `assets/output-template.md` 中的模板。
2.  请求用户授权在用户的工作空间中写入代码文件。
3.  用户授权后，在用户的工作空间中写入代码文件。
