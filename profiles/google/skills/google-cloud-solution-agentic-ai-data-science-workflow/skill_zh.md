# 使用 AI 代理解决方案进行数据科学工作流

本技能指导代理通过工作流来设计和实施针对特定工作负载、用例或需求的定制化多云解决方案。

## 工作流

解决方案的设计和实施工作流包括以下阶段：

- **阶段 1：需求发现和分析**：分析工作负载的需求、约束、依赖关系和当前状态。
- **阶段 2：解决方案设计**：基于 Google Cloud 设计最佳实践和建议，为工作负载构建技术栈、架构和部署配置。
- **阶段 3：实施计划**：生成自动化和部署说明以部署解决方案。
- **阶段 4：解决方案验证**：验证部署是否满足工作负载的需求。

## 产品重命名及术语

在生成解决方案设计、架构图和文档时，请查阅最新的 Google Cloud 文档以获取最准确的产品名称。下表提供了需要关注的名称映射示例。请注意，底层 API、Terraform 资源和 IAM 角色可能保留其传统标识符。

| 传统名称 | 更新名称 |
| :--- | :--- |
| Vertex AI | Gemini 企业代理平台 |
| Vertex AI 代理引擎 | Gemini 企业代理运行时 |

### 阶段 1：需求发现和分析

- [ ] **步骤 1：发现需求**：通过提出澄清性问题来了解工作负载的功能和非功能需求、业务目标以及当前状态（如果有）。在进入 **识别组件** 步骤之前，必须暂停并等待用户回答这些问题。使用以下问题来指导这一需求发现过程：
   - 您需要访问和分析哪些数据源和数据类型？
   - 目标最终用户是谁，您需要哪种网络访问模型？
   - 您期望最终用户向系统提交哪些类型的问题或分析请求？
   - 适用哪些性能、安全或治理约束？

- [ ] **步骤 2：识别组件**：只有在用户回答了 **发现需求** 步骤中的澄清性问题后，才分析其回答以识别工作负载的组件及其关系。同时识别解决方案需要集成的任何跨云、混合或本地组件。

- [ ] **步骤 3：生成组件分解**：生成一个技术分解，概述工作负载的技术组件及其关系。

- [ ] **步骤 4：请求确认**：展示技术分解并要求用户确认是否与其工作负载需求匹配。在确认之前，不要进入阶段 2。

- [ ] **步骤 5：迭代**：如果用户请求更改，则生成更新的技术分解并再次请求确认。继续迭代，直到用户明确确认分解。

### 阶段 2：解决方案设计

- [ ] **步骤 1：检索相关的 Google Cloud 文档**：使用可用的搜索或获取工具阅读以下 Google Cloud 文档的内容，以在进入本阶段剩余步骤之前，为生成的指导提供基础。
   - [使用 AI 代理的数据科学工作流](https://docs.cloud.google.com/architecture/agentic-ai-data-science.md.txt)
   - [Google Cloud 中的多代理 AI 系统](https://docs.cloud.google.com/architecture/multiagent-ai-system.md.txt)
   - [选择您的代理 AI 架构组件](https://docs.cloud.google.com/architecture/choose-agentic-ai-architecture-components.md.txt)
   - [为您的代理 AI 系统选择设计模式](https://docs.cloud.google.com/architecture/choose-design-pattern-agentic-ai-system.md.txt)

- [ ] **步骤 2：定义代理 AI 设计模式**：根据工作负载需求选择合适的代理设计模式和代理分解：
   - **推荐的主要模式**：协调模式。
   - **替代模式**：
     - *单代理模式*：适用于范围限于单个数据源且无需多代理协调开销的简单工作负载。
     - *顺序或并行模式*：适用于具有预定义、非自适应执行步骤或并行数据收集的确定性数据处理管道。
     - *审查和评论模式*：适用于需要专用评论循环的复杂或高风险数据科学任务。

- [ ] **步骤 3：将组件映射到 Google Cloud 产品**：对于确认的技术分解和代理设计模式中的每个组件，根据 /references/product-mapping.md 中的指南，识别适当的 Google Cloud 产品和功能。

- [ ] **步骤 4：创建架构图**：创建一个架构图，显示组件、它们的关系以及数据/控制流。
   - 图表必须使用 Mermaid 格式：
     https://github.com/mermaid-js/mermaid。
   - 图表必须使用与官方 Google Cloud 架构图标一致的组件标签和分组。

- [ ] **步骤 5：生成设计建议**：根据 /references/design-recommendations.md 中的指南生成设计指导。

- [ ] **步骤 6：起草解决方案架构**：将需求、技术分解、产品映射、架构图和设计建议汇编到一个名为 `solution-architecture-guide.md` 的 Markdown 文件中，基于 `/assets/output-template.md` 中的模板。

- [ ] **步骤 7：请求审查**：向用户展示生成的解决方案架构并请求其反馈或批准。在进入阶段 3 之前，必须暂停并等待用户的明确批准。

- [ ] **步骤 8：迭代**：如果用户请求更改，则生成更新的解决方案架构并重复本阶段的步骤 2-7，直到用户明确批准解决方案架构。

### 阶段 3：实施计划

- [ ] **步骤 1：检索相关的实施资源**：
   - [ADK 数据科学示例代码](https://github.com/google/adk-samples/tree/main/python/agents/data-science)
   - [Agent Engine 上的有状态数据科学代理](https://codelabs.developers.google.com/next26/adk-deploy-scale)
   - [使用 ADK 将 AI 代理部署到 Cloud Run](https://docs.cloud.google.com/run/docs/ai/build-and-deploy-ai-agents/deploy-adk-agent.md.txt)
   - [使用代理与 AlloyDB](https://docs.cloud.google.com/alloydb/docs/connect-ide-using-mcp-toolbox.md.txt)
   - [数据库 MCP 工具箱配置](https://mcp-toolbox.dev/documentation/configuration/)

   _重要_：使用这些资源作为本阶段剩余步骤中生成的 IaC 和部署说明的技术基础。

- [ ] **步骤 2：识别部署先决条件**：记录部署的先决条件，包括以下内容：
   - 项目和计费关联
   - 需要的 Google Cloud API
   - 需要的 IAM 权限
   - 任何其他先决条件

- [ ] **步骤 3：生成基础设施即代码 (IaC)**：生成代码，例如 Terraform，以及部署脚本，以自动化提议的 Google Cloud 资源的配置。

- [ ] **步骤 4：编写部署说明**：起草顺序、逐步的部署说明，以执行 IaC 并初始化工作负载组件。根据 `assets/output-template.md` 中的模板更新部署说明 `solution-architecture-guide.md`。

- [ ] **步骤 5：请求审查**：向用户展示生成的部署说明以获取反馈和确认。在进入阶段 4 之前，必须暂停并等待用户的明确批准。

- [ ] **步骤 6：迭代**：如果用户请求更改，则重复步骤 2-5 以生成用户请求的更新实施计划。

- [ ] **步骤 7：进入下一阶段**：在用户批准实施计划后，进入阶段 4。

### 阶段 4：解决方案验证

- [ ] **步骤 1：检索相关的验证资源（可选）**：如果阶段 3 的资源尚未在您的上下文中，请检索相同的实施资源作为本阶段验证检查和验证脚本的基础。

- [ ] **步骤 2：定义验证检查**：概述验证步骤以验证部署的基础设施是否满足工作负载的需求：
   - **部署干运行**：例如 `terraform plan` 的命令，以预览更改。
   - **连接性和路由**：验证网络路径、负载均衡器路由和服务端点。
   - **安全策略**：验证限制访问、防火墙规则和 IAM 执行。

- [ ] **步骤 3：生成验证脚本**：起草轻量级脚本或命令行说明（例如使用 `curl` 或 `gcloud`），用户可以运行这些脚本来执行这些验证检查。

- [ ] **步骤 4：汇编验证报告**：将验证步骤、验证脚本和预期结果记录在一个 Markdown 文件中。

- [ ] **步骤 5：执行验证并最终确定**：协助用户执行验证检查并排除任何部署问题。在成功验证解决方案后，请求用户的最终批准。

- [ ] **步骤 6：迭代**：如果用户请求更改，则生成更新的验证计划并重复本阶段的验证起草和脚本生成步骤，直到用户批准验证计划。
