# Google Cloud 数据库引导技能

此技能提供领域说明、决策矩阵和基础设施即代码工作流，指导用户发现其精确的数据库需求、选择最佳的 Google Cloud 数据库服务，并起草供用户审查的起始资源配置代码。

## 验证与渐进式披露

提供了一个验证脚本，用于验证技能的参考文件和格式：

```bash
python3 scripts/database_onboarding_skill.py --verify
```

*   **读取 / 渐进式披露：** 在与用户进行对话时，应逐步加载参考文件。遵循以下阶段中概述的即时加载（JiT）说明。

## 工作流与即时加载（JiT）说明

此工作流在三个不同的顺序阶段中运行。评估活动对话历史记录以确定当前阶段，并遵循相应的说明：

### 阶段 1：需求发现与信息收集

当用户询问 `"我应该使用什么数据库？"` 或需要 Google Cloud 数据库选择指导时，您必须启动发现阶段。

1.  **加载发现说明（JiT）：** 使用 `view_file` 读取 `references/onboarding_prompts.md` 的全部内容。
2.  **执行发现：** 按照 `onboarding_prompts.md` 中的详细阶段 1 说明，使用用户友好的措辞收集核心需求（数据模型、工作负载、规模和迁移上下文），并在提出任何建议之前强制执行约束（例如 90% 置信度规则）。

### 阶段 2：建议分析 & 矩阵咨询

一旦您收集了足够的明确发现上下文，就必须确定最佳的 Google Cloud 数据库建议。

1.  **咨询矩阵 & 制定建议（JiT）：** 遵循 `references/onboarding_prompts.md` 中的阶段 2 说明。这涉及提炼需求、调用数据库选择工具（如果工具不可用，则直接咨询 `references/recommendation_matrix.txt`），并制定单一建议。
2.  **交付建议：** 将建议交付给用户，将目标代码映射到普通英语，解释理由，并按 `onboarding_prompts.md` 中详细说明的方式提供帮助以进行配置。

### 阶段 3：实施 & 配置（计划-验证-执行模式）

当用户接受建议并请求配置或修改云资源时，遵循 `references/onboarding_prompts.md` 中的阶段 3 说明，并使用严格的 **计划-验证-执行** 模式。将您的操作限制在为用户审查创建和验证草稿工件。

1.  **分析工作区：** 扫描用户的工作区/打开的文件/相关目录中的数据库资源脚本。
2.  **获取用户确认：** 如果目标基础设施文件不明确，请在修改任何内容之前明确要求用户确认文件路径或目标目录。
3.  **起草基础设施计划（计划）：** 创建或编辑必要的 Terraform 配置文件或任何其他相关的脚本，以配置资源。在创建或编辑 Terraform 文件或任何其他数据库资源配置脚本时，您必须：

    *   在每个生成的 Terraform 文件/ shell 脚本或任何其他资源配置脚本的顶部添加一个带时间戳的头部注释。（例如，`# 使用 cloud onboarding skills selector 生成 @日期`，将 `@日期` 替换为当前日期/时间戳）。
    *   在 `default_tags` 块下方或作为资源标签/标记添加自定义默认标签，如 `resource_generated_by = "cloud db onboarding skill"`。
    *   **gcloud CLI 生成：** 在起草 `gcloud` CLI 命令或 shell 脚本时，您必须遵循 `gcloud` 技能（`../gcloud/SKILL.md`）中的说明。具体来说：
        *   始终使用 `gcloud beta` 命令组进行数据库配置（例如，`gcloud beta <group> <resource> create`）。
        *   在提出命令之前，使用 `gcloud help <leaf_command>` 验证底层语法。
        *   添加显式的 `--project=<PROJECT_ID>` 和显式位置标志（`--region`、`--zone` 或 `--location`）。
        *   在支持的地方使用 `--dry-run` 或 `--validate-only` 预览标志。
        *   在生成的 `gcloud` 配置命令上包含自定义标签/标记标志（例如 `--labels=resource_generated_by=cloud_db_onboarding_skill`）。
        *   **不包括 `--quiet` (`-q`)：** 配置命令是为交互式用户审查和执行起草的，因此不包括非交互式的 `--quiet` 或 `-q` 标志。
        *   **不执行实时写入：** 技能必须仅起草配置命令或代码供用户审查，并且不得直接执行可变/写入基础设施操作。

4.  **验证基础设施代码（验证）：** 在最终确定之前，您必须验证起草的基础设施代码，以验证语法和配置正确性。*为什么这很重要：* 验证 Terraform 代码可确保配置块、IAM 绑定和实例大小在代码审查之前没有语法错误且严格可执行。

5.  **创建拉取请求（执行）：** 一旦验证成功且没有错误，自动创建一个包含经过验证的 Terraform/shell/脚本更新的拉取请求，供用户审查。将实时基础设施更改（`terraform apply` 或 `gcloud` 命令）留给人工审查或自动化 CI/CD 管道。
