# 在 Google Cloud 上构建和部署 AI 代理

本技能指导代理完成设计和实施定制多产品云解决方案的工作流程，以满足特定的业务负载、用例或需求。

## 工作流程

解决方案的设计和实施工作流程分为以下阶段：

*   **阶段 1：需求发现和分析**：分析业务负载的需求、约束、依赖关系和当前状态。
*   **阶段 2：解决方案设计**：基于 Google Cloud 设计最佳实践和建议，为业务负载构建技术堆栈、架构和部署配置。
*   **阶段 3：实施计划**：生成自动化指令以部署解决方案。
*   **阶段 4：解决方案验证**：验证部署是否满足业务负载的需求。

将此检查清单复制到您的活动任务/计划工件中，以跨四个阶段跟踪进度：

-   [ ] 阶段 1：需求发现和分析已完成并确认。
-   [ ] 阶段 2：解决方案架构已生成并批准。
-   [ ] 阶段 3：实施计划已生成并批准。
-   [ ] 阶段 4：解决方案验证已生成并批准。

### 阶段 1：需求发现和分析

1.  **发现需求**：收集和理解业务负载的功能和非功能需求、业务目标以及当前状态（如有），包括其架构、依赖关系和约束。

    *重要*：首先，检查用户的初始提示是否已经回答了以下问题，或者提示是否明确要求您根据给定的一组参数提出解决方案架构/图。

    -   如果用户的提示提供了充分的需求，并且明确要求提出架构提案或图，则跳过以下问题的提问，直接进入**推荐代理设计模式**步骤。
    -   如果用户的提示没有提供充分的需求，则完成以下步骤以收集缺失信息：

        1.  请用户描述其业务负载的功能需求：业务流程、活动和用例。
        2.  请用户描述其业务负载的非功能需求（安全性、隐私、合规性、可靠性、灾难恢复、成本、运营、性能和可持续性）。
        3.  请用户说明 AI 代理需要访问哪些现有系统、知识库、产品文档或其他文档，以提供基于事实的指导。
        4.  请用户描述其对其他业务负载、产品或工具的依赖关系（如有）。
        5.  审查用户目前提供的输入，并检查输入中是否存在任何模糊不清或矛盾之处。

            如果您在用户提供的输入中发现了任何模糊不清或矛盾之处，则针对您发现的每个模糊不清或矛盾之处执行以下操作：

            *   描述模糊不清或矛盾之处。
            *   询问用户希望如何解决模糊不清或矛盾之处。
                *   如果用户将选择权委托给您（例如，用户回复“做你认为最好的”或“你决定”），则提供清晰的建议来解决模糊不清或矛盾之处，解释您的推理，并询问用户是否批准您的建议。

            **关键**：在您根据上述指导解决所有您发现的模糊不清或矛盾之处之前，您必须**不**推荐或生成任何架构设计、技术分解或 Google Cloud 产品建议。

    2.  **推荐代理设计模式**：评估业务负载的复杂性、工作流程、延迟和成本需求，以推荐代理设计模式：

        -   **单代理系统**：推荐用于简单任务，作为优化核心逻辑和工具的有效起点。
        -   **多代理系统**：推荐用于需要多个专业代理协作解决复杂问题的情况。

    3.  **识别组件**：根据需求分析，生成业务负载的技术分解。技术分解必须识别业务负载的逻辑组件及其关系。同时，识别解决方案需要集成的任何跨云组件、混合组件或本地组件。

    4.  **请求确认**：请用户确认推荐的代理设计模式和技术分解是否满足其业务负载的需求。

    5.  **迭代**：如果用户请求更改，则生成更新的技术分解，并请用户确认更改。继续迭代，直到用户确认技术分解。只有在用户确认技术分解后，才能进入下一阶段。

### 阶段 2：解决方案设计

1.  **从 `references/related-guidance.md` 中检索相关的 Google Cloud 指南**。

    *重要*：使用从 `references/related-guidance.md` 检索到的内容，为该阶段剩余步骤中生成的指导提供事实依据。

2.  **将组件映射到 Google Cloud 产品**：对于确认的技术分解中的每个组件，通过查阅 [product-mappings.md](references/product-mappings.md) 来识别适当的 Google Cloud 产品和功能，以获取详细的建议、权衡和替代方案，涵盖网络、前端、代理/模型运行时、内存存储和工具。

3.  **创建架构图**：以 Mermaid 格式创建架构图：https://github.com/mermaid-js/mermaid。该图应显示组件、它们之间的关系以及数据/控制流。

4.  **生成设计建议**：根据以下 Google Cloud 最佳实践和建议生成设计指导。使用 `references/related-guidance.md` 中的信息，重点参考 `references/design-principles.md` 中的指导。

5.  **起草解决方案架构**：将需求、技术分解、产品映射、架构图和设计建议汇编到一个 Markdown 文件中，该文件符合 [solution-template.md](assets/solution-template.md) 中的格式。将此文档保存到工作区中，命名为 `solution-architecture.md`。

6.  **请求审查**：直接向用户展示生成的解决方案架构（包括完整的 `mermaid` 围栏代码块用于图表），并明确请求他们的反馈或批准。在展示架构时，请用户批准您继续实施计划。

7.  **迭代**：如果用户请求更改，则生成更新的解决方案架构，并重复从“将组件映射到 Google Cloud 产品”到“请求审查”的步骤，直到用户批准解决方案架构。

### 阶段 3：实施计划

1.  **检索相关的实施资源**：

    *重要*：使用 `references/related-guidance.md` 中的资源作为基础设施即代码 (IaC) 和您在阶段剩余步骤中生成的部署指令的技术基础。

2.  **识别部署先决条件**：记录部署的先决条件，包括以下内容：

    -   项目和计费关联
    -   所需的 Google Cloud API
    -   所需的 IAM 权限
    -   任何其他先决条件

3.  **生成基础设施即代码 (IaC)**：生成代码（例如 Terraform）和部署脚本，以自动化提议的 Google Cloud 资源的配置。

    -   在适当的情况下，与原始基础设施脚本一起或替代原始基础设施脚本，指示用户使用 Agents CLI 命令 (`agents-cli scaffold create` 或 `agents-cli scaffold enhance`) 来设置或增强项目结构、部署配置和 CI/CD 管道。

4.  **编写部署指令**：起草按顺序执行的、分步骤的部署指令，以执行 IaC 并初始化业务负载组件。将部署先决条件、IaC 和部署指令汇编到一个 Markdown 文件中，该文件符合 [implementation-template.md](assets/implementation-template.md) 中的格式。将此文档保存到工作区中，命名为 `implementation-instructions.md`。

    -   指令**必须**提供定义有状态代理节点的 ADK 代码，该节点接收提示、调用模型并返回工具执行请求。
    -   指令**必须**展示如何使用模型上下文协议 (MCP) 标准注册工具，例如数据库读取器。
    -   如果将代理部署到 Cloud Run，指令**必须**展示如何配置 Cloud Run 以在代理空闲时扩展到零，从而降低运行时成本。
    -   指令**必须**建议使用加密环境变量来存储模型参数或私有 API 凭据。加密有助于防止敏感凭据在纯文本容器日志流中暴露。
    -   在适当的情况下，指令**必须**指定使用 Agents CLI `agents-cli deploy` 命令（与原始基础设施/部署脚本一起或替代）来运行部署。

5.  **请求审查**：向用户展示生成的部署指令，并明确请求他们的反馈和确认。

6.  **迭代**：如果用户请求更改，则生成更新的实施计划，并重复从“生成基础设施即代码 (IaC)”到“请求审查”的步骤，直到用户批准实施计划。

### 阶段 4：解决方案验证

1.  **检索相关的验证资源**：

    *重要*：使用 `references/related-guidance.md` 及其验证模式作为您在阶段剩余步骤中生成的验证检查和验证脚本的基础。

2.  **定义验证检查**：概述验证步骤，以验证已部署的基础设施是否满足业务负载的需求：

    -   **部署干运行**：例如 `terraform plan` 命令预览更改。包括运行代理部署在干运行模式下的指令（例如，使用 `agents-cli deploy --dry-run` 或 `-n`）预览步骤和 Terraform 执行，然后再推送到生产环境。
    -   **本地测试和质量验证**：建议使用 Agents CLI 在本地运行和测试代理逻辑 (`agents-cli run`)，并进行系统评估 (`agents-cli eval run`)，以在部署前验证代理质量和性能。
    -   **连接性和路由**：验证网络路径、负载均衡器路由和服务端点。
    -   **安全策略**：验证受限访问、防火墙规则和 IAM 执行。

3.  **生成验证脚本**：起草轻量级脚本或命令行指令（例如，使用 `curl`、`gcloud` 或 `agents-cli`），用户可以运行这些脚本来执行这些验证检查。

    -   验证计划**必须**包括使用 Agents CLI 进行本地运行、评估和部署后验证检查的指令（例如，`agents-cli run --url <service-url>` 来测试已部署的服务端点）。

4.  **汇编验证计划**：将验证步骤、验证脚本和预期结果记录在一个 Markdown 文件中，该文件符合 [validation-template.md](assets/validation-template.md) 中的格式。将此文档保存到工作区中，命名为 `validation-plan.md`。

5.  **请求审查**：向用户展示验证计划，并明确请求他们对验证计划的反馈或批准。

6.  **执行验证并最终确定**：协助用户执行验证检查并排除任何部署问题。在解决方案成功验证后，请求用户的最终批准。

7.  **迭代**：如果用户请求更改，则生成更新的验证计划，并重复从“定义验证检查”到“请求审查”的步骤，直到用户批准验证计划。
