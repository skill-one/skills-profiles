# 使用 GKE 和 AlloyDB 为企业搜索构建 RAG

此技能提供了一个工作流程，用于设计和实现一个安全、低延迟、高精度的 RAG 支持型对话式搜索解决方案，用于私有企业内容。该方案使用 AlloyDB 数据库、云存储和 Google Kubernetes Engine (GKE) 集群来托管所有应用程序组件，包括一个开源模型和一个开源推理框架。

## 工作流程概述

该工作流程由以下阶段组成：
*   **阶段 1：需求发现**。收集与用户需要协助的云工作负载或用例相关的详细需求。
*   **阶段 2：解决方案架构**。使用阶段 1 中收集的需求，为云工作负载或用例生成详细的解决方案架构。
*   **阶段 3：解决方案验证**。创建一个验证生成解决方案的计划，生成验证说明和脚本，并运行验证。
*   **阶段 4：解决方案打包和展示**。整合生成的内容，并展示解决方案。

**关于工作流程的重要说明**：

*   **严格的阶段分离**：在阶段 1（需求发现）中，当您向用户提出澄清问题时，**不要**推荐、提出或概述任何架构设计、技术分解、云服务或组件映射。

*   **何时可以跳过某些阶段**：如果用户的提示表明此工作流程中的特定阶段或任务已经完成或已批准（例如，“需求发现阶段已完成”、“产品选择已批准”或“架构已确认”），**不要**重复该阶段或任务。相反，直接跳转到请求的任务（例如，生成技术分解、推荐产品或编制解决方案指南）。

## 阶段 1：需求发现

在此阶段，您必须收集与用户希望在 Google Cloud 中设计和部署的 RAG 工作负载相关的详细需求。

严格按照指定顺序完成以下步骤：
1.  要求用户描述工作负载的功能需求，包括数据类型（结构化、非结构化）、摄取频率和对话式功能（例如，多轮聊天、引用要求）。
2.  要求用户描述以下非功能性需求：
    *   **安全、隐私和合规性**：例如，网络隔离、私有端点、数据驻留和合规性要求。
    *   **可靠性**：例如，扩展性、高可用性、对区域或区域故障的弹性、RTO 和 RPO 的灾难恢复目标。
    *   **成本**：例如，计算、存储和数据库资源的成本。
    *   **运营卓越**：例如，监控、警报和日志记录。
    *   **性能**：例如，数据上传速度、生成嵌入向量的性能预期、模型响应和数据检索查询（包括向量和混合搜索）的延迟要求。
    *   **可持续性**：例如，碳足迹、低碳区域。
3.  询问用户当前的工作负载是否在其他云服务提供商或本地运行。
    *   如果用户的答案是“是”，则要求用户描述当前部署的架构。
    *   如果用户的答案是“否”，则继续下一步。
4.  要求用户描述对其他工作负载、产品或工具（例如，身份提供商、外部源、CRM/ERP 数据库集成）的任何依赖关系。

5.  审查用户迄今为止提供的输入，并检查是否存在任何模糊不清或矛盾之处。

    如果您在用户提供的需求中识别到任何模糊不清或矛盾之处，则针对您识别到的每个模糊不清或矛盾之处执行以下操作：
    *   描述模糊不清或矛盾之处。
    *   询问用户希望如何解决模糊不清或矛盾之处。
        *   如果用户将选择权委托给您（例如，用户回复“做你认为最好的”或“你决定”），则提供清晰的建议来解决模糊不清或矛盾之处，解释您的推理，并要求用户批准您的建议。

    **关键**：直到您识别出的所有模糊不清和矛盾之处都按照前面的指导得到解决，您**必须**不得推荐或生成任何架构设计、技术分解或 Google Cloud 产品建议。

6.  **重要**：如果存在来自步骤 5 的未解决的矛盾或模糊不清之处，**不要**开始此步骤。

    生成工作负载组件的技术分解。技术分解必须将解决方案分解为逻辑组件，如下所示：
    *   **数据摄取**：用于原始企业文档的 Blob 存储。
    *   **数据处理和分块**：用于提取数据、清理数据并分块的容器化管道。
    *   **嵌入向量生成**：将数据块转换为嵌入向量的容器化服务。
    *   **存储和索引嵌入向量**：用于存储嵌入向量的向量化 SQL 数据库。
    *   **处理非向量数据**：准备非向量数据，如表、视图和聚合，以便进行数据检索。分析是否可以在原始数据模式上应用任何索引、分区或其他性能技术。
    *   **查询和检索**：接受客户端查询、识别意图，并将路由到检索工作流，该工作流可能包括将请求转换为嵌入以进行语义搜索、提取并应用过滤器以进行过滤搜索或向混合搜索提供所有内容。
    *   **提示增强**：使用检索到的上下文增强提示。
    *   **响应生成**：从模型请求和生成响应。
    *   **响应合理性检查**：使用 AI 模型评估响应，并根据定义的标准执行程序检查。
7.  要求用户批准生成的技术分解。

    **关键**：您**必须**立即停止执行，调用更多工具（例如，文件编辑器、搜索或代码工具），并等待用户在聊天中提供反馈或批准。在收到用户的明确批准之前，**不要**编译架构、推荐产品、构建映射或编写任何文件/草稿以供阶段 2 使用。
8.  如果用户请求更改，则生成更新的技术分解。
9.  重复步骤 5 至 8，直到用户批准生成的技术分解。
10. 只有在用户明确批准技术分解后，才能继续阶段 2。

    **重要**：在技术分解获得批准之前，您**严格禁止**推荐产品选择、生成架构图或起草设计建议。

## 阶段 2：解决方案架构

### 所有生成内容均需基于官方指南

为确保生成的内容与最新的官方 Google Cloud 指南一致，您必须使用以下资源来为每个此阶段的任务锚定生成的内容：
*   Google 开发者知识 MCP 服务器：
    https://developers.google.com/knowledge/mcp.md.txt
    *   服务器：https://developerknowledge.googleapis.com/mcp
        *   工具：
            *   `developerknowledge:search_documents`
            *   `developerknowledge:get_documents`
            *   `developerknowledge:answer_query`
*   https://github.com/google/skills 中的相关技能
*   官方 Google Cloud 文档，包括以下内容：
    *   **主要架构参考**：
        https://docs.cloud.google.com/architecture/rag-capable-gen-ai-app-using-gke.md.txt
    *   **架构指南和决策指南**：
        -   `references/product-selection-recommendations.md`
        -   `references/design-recommendations.md`
        -   `references/related-documentation.md`

对于生成指南中的每个项目，您必须包含对相关官方 Google Cloud 文档页面的引用。

### 任务 2.1：确定工作负载所需的 Google Cloud 产品和功能

1.  推荐适用于用户工作负载每个组件的合适产品和功能。

    **重要**：您推荐 Google Cloud 产品和功能**必须**与 `references/product-selection-recommendations.md` 中的指南一致。
2.  展示生成的产品建议，并要求用户批准建议。
3.  如果用户请求更改，则进行所需更改。
4.  重复步骤 2 和 3，直到用户批准产品建议。
5.  用户批准产品建议后，继续任务 2.2。

### 任务 2.2：生成架构图

1.  使用 Mermaid 格式生成架构图：
    https://github.com/mermaid-js/mermaid。

    该图必须显示架构组件之间的数据流和请求流，基于您生成的技术组成。

    以下是架构图应显示的数据流和请求流的**示例**：
    *   **嵌入管道（批处理/流式）**：数据源 -> Cloud Storage -> Cloud Storage FUSE -> GKE Ray Worker（分块）--> 使用 GemmaEmbedding 生成嵌入 -> AlloyDB。
    *   **服务管道（实时）**：用户客户端 -> GKE 前端（LangChain 协调）-> 数据库查询（对向量存储进行语义或混合搜索）-> 检索匹配数据 -> 增强提示 -> Gemma vLLM 端点 API -> 输出（责任 AI 过滤）-> 用户客户端。
2.  将生成的图展示给用户，并要求用户批准架构图。
3.  如果用户请求更改，则进行所需更改。
4.  重复步骤 2 和 3，直到用户批准架构图。
5.  用户批准架构图后，继续任务 2.3。

### 任务 2.3：生成架构描述

1.  生成一个描述，解释每个组件的目的、组件之间的关系以及任务流或数据流。
2.  将生成的架构描述展示给用户，并要求用户批准描述。
3.  如果用户请求任何更改，则进行所需更改。
4.  重复步骤 2 和 3，直到用户批准架构描述。
5.  用户批准架构描述后，继续任务 2.4。

### 任务 2.4：生成设计建议

1.  根据工作负载的需求，生成设计建议和最佳实践，以优化架构中每个组件的配置。

    **重要**：您生成的设计建议和最佳实践**必须**与以下文件中列出的资源中的指南一致：
    -   `references/related-documentation.md`
    -   `references/design-recommendations.md`
2.  将生成的建议展示给用户，并询问用户是否需要任何更改。
3.  如果用户需要更改，则进行所需更改。
4.  重复步骤 2 和 3，直到用户确认生成的设计建议满足其需求。
5.  继续任务 2.5。

### 任务 2.5：生成部署指南

1.  生成部署解决方案的指南，包括以下内容：
    *   用于创建所需基础设施资源的 Terraform 代码。
    *   部署工作负载的步骤或脚本，例如 Ray-on-GKE（KubeRay 协调器和工作者节点）和 LangChain 前端部署。

    **重要**：您生成的部署指南**必须**与以下资源中的指南一致：
    -   `references/related-documentation.md`
    -   `references/design-recommendations.md`
    -   https://github.com/google/skills 中的相关技能
2.  将生成的部署指南展示给用户，并询问用户是否需要任何更改。
3.  如果用户请求更改，则进行所需更改。
4.  重复步骤 2 和 3，直到用户确认生成的部署指南满足其需求。
5.  继续阶段 3。

## 阶段 3：解决方案验证

1.  创建一个验证生成解决方案的计划。该计划必须概述验证生成解决方案是否符合工作负载需求的必要步骤。以下是一些验证步骤的示例：
    *   **部署干运行**：运行 `terraform plan` 等命令以预览将配置的基础设施资源。
    *   **连接性和路由**：验证网络路径、负载均衡器路由和服务端点。
    *   **向量索引**：验证向量索引是否在 AlloyDB 数据库中正确创建和填充。这可能涉及查询数据库以检查索引状态和内容。
    *   **嵌入管道**：测试从数据摄取到向量存储的端到端嵌入管道，确保文档被分块、嵌入并正确存储。
    *   **检索延迟**：测量对 AlloyDB 向量存储的向量和混合搜索查询的延迟，以确保性能满足要求。
    *   **检索准确性**：执行样本查询并评估检索到的文档或块的相关性。
    *   **安全策略**：验证受限访问、防火墙规则和 IAM 执行。
2.  将验证计划展示给用户并请求反馈或批准。
3.  如果用户请求更改，则按需更新计划。
4.  重复步骤 2 和 3，直到用户批准验证计划。
5.  使用 `curl` 或 `gcloud` 等工具生成脚本或命令，以执行批准的验证计划中的步骤。
6.  请求用户允许执行验证检查。
7.  如果用户给予许可，则运行验证检查并排除任何部署问题。
8.  当所有验证检查通过时，继续阶段 4。

## 阶段 4：解决方案打包和展示

1.  将阶段 2 中生成的最终文本工件整合到一个名为 `solution-architecture-guide.md` 的 Markdown 文件中，基于 `assets/output-template.md` 中的模板。
2.  请求用户允许在用户的工作区中写入代码文件。
3.  用户给予许可后，在用户的工作区中写入最终代码文件。
