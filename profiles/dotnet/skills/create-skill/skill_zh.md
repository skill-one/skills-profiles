# 创建技能

此技能可帮助您搭建符合 Agent Skills 规范和 dotnet/skills 仓库约定的新代理技能。

## 何时使用

- 从零开始创建新技能
- 生成带有正确 frontmatter 的 SKILL.md 文件
- 设置技能目录结构（可选文件夹）
- 确保符合 agentskills.io 规范

## 不应使用的情况

- 修改现有技能（直接编辑）
- 诊断或修复评估失败的技能（使用 `improve-skill-quality`）
- 编写技能的 `eval.yaml`（使用 `create-skill-test`）
- 创建自定义代理（使用 agents/ 目录模式）

## 输入

| 输入 | 必填 | 描述 |
|------|------|------|
| 技能名称 | 是 | 全小写，仅包含字母、数字和连字符（例如，`code-review`，`ci-triage`） |
| 描述 | 是 | 说明技能的作用以及代理何时应使用它（1-1024 字符） |
| 目的 | 是 | 一段描述结果的内容 |
| 工作流步骤 | 推荐 | 代理应遵循的编号步骤 |

## 工作流

### 第 1 步：验证技能名称

确保名称：
- 仅包含小写字母、数字和连字符
- 不以连字符开头或结尾
- 不包含连续的连字符
- 长度在 1-64 个字符之间

### 第 2 步：编写描述——它是路由器

`description` 是运行时在决定是否加载技能时看到的**唯一**文本。
一个完美的内容背后若有一个薄弱的描述，则永远不会运行。

```yaml
---
name: <skill-name>
description: <它做什么>. USE FOR: <症状、错误代码、工件名称、引用的用户请求>. DO NOT USE FOR: <附近但错误的意图、拥有该意图的技能>.
---
```

- 以动作动词开头，使用用户自己的语言：症状、错误代码（`CS1501`，`MSTEST0014`）、工件名称（`.testsettings`，`binlog`）以及开发者会输入的请求。
- 基于真实的**区分标准**而不是主题对兄弟技能进行划分。"抽象已存在吗？"可以区分两个技能；"测试"则不能。在**双方**兄弟技能中添加匹配的排除项。
- 声明那些原本会路由到兄弟技能的模糊词汇。如果提示说"审查我的测试"而一个兄弟技能拥有"审查"，则应明确说明。
- 检查每个 `DO NOT USE FOR` 子句是否与技能存在的场景相符——像"已处于 v3"这样的排除项可能会阻止升级后的修复，而修复正是技能的目的。
- 预算：每个描述最多 1,024 个字符，整个插件的渲染技能菜单也有预算。一个用户应永远不会直接调用的辅助技能可以设置 `disable-model-invocation: true` 以释放菜单空间，同时保持可通过名称调用。

### 第 3 步：针对基线模型的增量编写

每个技能都会与**未加载任何技能**的相同模型进行逐项评分。模型已无辅助即可生成的内容价值为零；使模型变慢或更保守的内容价值低于零。有关完整证据，请参阅
[improve-skill-quality/references/writing-for-baseline-delta.md](../improve-skill-quality/references/writing-for-baseline-delta.md)。

| 做 | 而不是 |
|----|--------|
| 编码模型原本会做错的决策 | 重述模型已复制的 API 签名 |
| "当 A 时做 B，永不做 C，验证 D" 表格 | 可行的替代方案列表 |
| 具体的输出合同（精确命令、判定行、发现表格） | "考虑..."，"你可能想..." |
| 根据输入大小调整输出结构 | 为 8 个测试套件创建 12 个部分的仪表板 |
| 防止过度应用的停止条件 | 在测量前行动，重写工作代码 |
| 指示代理发现仓库路径 | 将可发现路径标记为必需输入 |
| 如实报告恢复/构建/测试失败 | 在命令失败后声称成功 |
| 通过编译或探测验证承重 API 声明 | 信任读取的来源 |
| 用 `references/` 隔离罕见或昂贵的路径 | 一个包含所有路径的大型 SKILL.md |

不要过度纠正：一个比基线更短且可操作性更低的技能仍然会失败。

### 第 4 步：创建技能目录

```
plugins/<plugin>/skills/<skill-name>/
└── SKILL.md
```

### 第 5 步：使用 frontmatter 生成 SKILL.md

创建第 2 步中起草的 frontmatter 的文件。

### 第 6 步：添加主体内容部分

包含以下推荐部分：

1. **目的**：一段描述结果的内容
2. **何时使用**：适用场景的要点列表
3. **不应使用的情况**：边界和排除项
4. **输入**：必需和可选输入的表格
5. **工作流**：带检查点的编号步骤
6. **验证**：如何确认技能正确工作
7. **常见陷阱**：已知陷阱及如何避免

### 第 7 步：添加可选目录（如果需要）

```
plugins/<plugin>/skills/<skill-name>/
├── SKILL.md
├── scripts/       # 代理可以运行的执行代码
├── references/    # 额外文档按需加载
└── assets/        # 模板、图像、数据文件
```

使用相对于包含 `SKILL.md` 的目录的路径引用捆绑文件，例如
`references/details.md` 或 `scripts/validate.ps1`。不要指示代理搜索技能的安装目录。如果缺少捆绑文件导致结果质量下降，允许列出一个已知的捆绑文件目录，并要求代理报告减少的覆盖率。

### 第 8 步：更新 CODEOWNERS

在 `.github/CODEOWNERS` 中为新的技能及其测试目录添加条目：

```
/plugins/<plugin>/skills/<skill-name>/  @owner-team
/tests/<plugin>/<skill-name>/           @owner-team
```

匹配同一插件中兄弟技能使用的所有者模式。

### 第 9 步：验证技能

- 确认 frontmatter 字段有效
- 确保 SKILL.md 不足 500 行
- 检查文件引用使用相对路径
- 验证指令可执行且具体
- 运行 `dotnet run --project eng/skill-validator/src/SkillValidator.csproj -- check --plugin ./plugins/<plugin>`

### 第 10 步：添加评估

没有 `eval.yaml` 的技能没有证据表明它比基线有所改进。使用
`create-skill-test` 在同一拉取请求中添加一个，并为其统计功效调整大小——低于五个不同刺激的评估永远无法返回通过判定。

例外是一个带有 `disable-model-invocation: true` 的辅助技能：模型无法自我激活它，因此激活评分的评估比较两个相同的分支。通过加载它的技能的评估来覆盖它。

## SKILL.md 模板

创建新技能时使用此模板：

```markdown
---
name: <skill-name>
description: <1-1024 字符描述技能的作用和何时使用>
---

# <技能标题>

<一段描述技能目的和结果的文字。>

## 何时使用

- <场景 1>
- <场景 2>

## 不应使用的情况

- <排除项 1>
- <排除项 2>

## 输入

| 输入 | 必填 | 描述 |
|------|------|------|
| <输入名称> | 是/否 | <描述> |

## 工作流

### 第 1 步：<动作>

<此步骤的说明>

### 第 2 步：<动作>

<此步骤的说明>

## 验证

- [ ] <验证步骤 1>
- [ ] <验证步骤 2>

## 常见陷阱

| 陷阱 | 解决方案 |
|------|------|
| <问题> | <如何避免或修复> |
```

## 验证清单

创建技能后验证：

- [ ] 技能名称与目录名称完全匹配
- [ ] 技能名称全小写且仅包含连字符
- [ ] 描述非空且不足 1024 字符
- [ ] SKILL.md 正文不足 500 行
- [ ] 指令具体且可执行
- [ ] 捆绑文件路径相对于包含 `SKILL.md` 的目录
- [ ] 缺少捆绑文件不会导致静默退化
- [ ] 工作流有编号步骤和清晰的检查点
- [ ] 验证部分存在且具有可观察的成功标准
- [ ] 不包含密钥、令牌或内部 URL
- [ ] `.github/CODEOWNERS` 为新技能及其测试目录添加条目
- [ ] 描述命名具体触发器并排除最近的兄弟技能
- [ ] 每个部分都会改变无技能模型原本会做错的决策
- [ ] 技能说明何时**不应**行动，以及诚实的失败报告应如何显示
- [ ] 存在 `eval.yaml` 并清除不同刺激的底线（或技能是 `disable-model-invocation: true` 且通过其消费者覆盖）

## 常见陷阱

| 陷阱 | 解决方案 |
|------|------|
| 名称包含大写字母 | 仅使用小写：`code-review` 而不是 `Code-Review` |
| 描述模糊 | 包含它做什么**以及**何时使用它 |
| 指令模糊 | 使用编号步骤和具体动作 |
| 缺少验证步骤 | 添加验证成功的检查点 |
| SKILL.md 太长 | 将详细内容移至 `references/` 文件 |
| 硬编码环境假设 | 在 `compatibility` 字段中记录要求 |
| 缺少 CODEOWNERS 条目 | 为 `/plugins/<plugin>/skills/<skill-name>/` 和 `/tests/<plugin>/<skill-name>/` 添加条目，匹配兄弟技能的所有者模式 |
| 技能重述模型已知的内容 | 删除；技能的评分是相对于无技能模型的增量 |
| 可发现路径列为必需输入 | 指示代理发现它们，否则代理会停止并询问用户 |
| 描述按主题对兄弟技能进行划分 | 基于**真实区分标准**进行划分，并在双方排除 |
| 排除条款阻止技能自身的用例 | 重新阅读每个 "do not use for" 子句与实际工作流程阶段 |
| 没有评估添加技能 | 在同一 PR 中添加 `eval.yaml`；未评估的技能不携带证据 |
