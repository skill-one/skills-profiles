# 可空引用迁移

在现有代码库中启用 C# 可空引用类型 (NRTs) 并系统性地解决所有警告。结果是一个项目（或解决方案），其中包含 `<Nullable>enable</Nullable>`，没有可空警告，并且公共 API 表面准确注释——为编译器和消费者提供可靠的空值信息。

## 使用场景

- 在现有 C# 项目或解决方案中启用可空引用类型
- 在启用该功能后，系统性地解决 CS86xx 可空警告
- 注释库的公共 API 表面，以便消费者获得准确的空值信息
- 升级依赖项，该依赖项已添加可空注释并出现新警告
- 分析已启用 NRTs 的代码库中的抑制项，以确定是否可以删除它们

## 不应使用场景

- 项目已经具有 `<Nullable>enable</Nullable>` 并且没有警告——迁移完成，除非用户想要重新检查抑制项以删除不必要的项（见步骤 6）
- 用户只想抑制警告而不修复它们（不推荐这样做）
- 代码针对 C# 7.3 或更早版本，这些版本不支持可空引用类型

## 输入

| 输入 | 必需 | 描述 |
|-------|----------|-------------|
| 项目或解决方案路径 | 是 | 要迁移的 `.csproj`、`.sln` 或构建入口点 |
| 迁移范围 | 否 | `project-wide`（默认）或 `file-by-file`——控制实施策略 |
| 构建命令 | 否 | 如何构建项目（例如，`dotnet build`、`msbuild` 或特定于存储库的构建脚本）。如果未提供，则从存储库中检测 |
| 测试命令 | 否 | 如何运行测试（例如，`dotnet test` 或特定于存储库的测试脚本）。如果未提供，则从存储库中检测 |

## 工作流程

> 🛑 **零运行时行为变化。** NRT 迁移严格是元数据和注释练习。生成的 IL 必须保持不变——没有新的分支，没有新的空值检查，没有改变的控制流，没有添加或删除方法调用。唯一可接受的更改是可空注释（`?`）、可空属性（`[NotNullWhen]` 等）、`!` 运算符（仅元数据）和 `#nullable` 指令。如果在迁移过程中发现缺少运行时空值保护或潜在的 bug，**不要直接在行内修复**。相反，在位置处提供插入 `// TODO: 考虑添加 ArgumentNullException.ThrowIfNull(param)` 注释的提议，以便用户可以将其作为单独的更改来解决。**不要将行为修复与注释提交混合**。

> **提交策略：** 在每个逻辑边界处提交——启用 `<Nullable>` 后（步骤 2）、修复解引用警告后（步骤 3）、注释声明后（步骤 4）、应用可空属性后（步骤 5）以及清理抑制项后（步骤 6）。这使每个提交保持专注且可审查，并防止如果后续步骤发现需要重新思考的设计问题而丢失工作。对于文件逐个迁移，单独提交每个文件或相关文件批处理。

### 步骤 1：评估准备情况

> **可选：** 运行 `scripts/Get-NullableReadiness.ps1 -Path <project-or-solution>` 以自动执行以下检查。脚本报告 `<Nullable>`、`<LangVersion>`、`<TargetFramework>`、`<WarningsAsErrors>` 设置以及 `#nullable disable` 指令、`!` 运算符和 `#pragma warning disable CS86xx` 抑制的计数。使用 `-Json` 获取机器可读输出。

1. 确定项目如何构建和测试。查找构建脚本（例如，`build.cmd`、`build.sh`、`Makefile`）、`.sln` 文件或单独的 `.csproj` 文件。如果存储库使用自定义构建脚本，则在整个工作流程中使用它而不是 `dotnet build`。
2. 运行 `dotnet --version` 以确认已安装 SDK。可空引用类型 (NRTs) 需要 C# 8.0+（`.NET Core 3.0` / `.NET Standard 2.1` 或更高版本）。
3. 打开 `.csproj`（如果属性在存储库级别设置，则为 `Directory.Build.props`）并检查 `<LangVersion>` 和 `<TargetFramework>`。如果项目多目标，请记录所有 TFMs。

> **如果语言版本或目标框架不足，则停止。** 如果 `<LangVersion>` 低于 8.0，或者项目针对默认为 C# 7.x 的框架（例如，没有显式 `<LangVersion>` 的 `.NET Framework 4.x`），则无法按原样启用 NRTs。明确告知用户需要更改的内容（设置 `<LangVersion>8.0</LangVersion>` 或更高版本），并询问他们是否想要进行更新并继续，或中止迁移。**不要无声地继续或假设更新是可接受的**。
4. 检查 `<Nullable>` 是否已经设置。如果它设置为 `enable`，则跳到步骤 5 以审计剩余警告。
5. 确定项目类型——这将塑造迁移过程中注释的优先级：
   - **库**：首先关注公共 API 合同。公共参数或返回类型上的每个 `?` 都是消费者依赖的合同更改。要精确和保守。
   - **应用程序（Web、控制台、桌面）**：关注边界处的空值安全性——反序列化、数据库查询、用户输入、外部 API 响应。内部管道可以更自由地注释。
   - **测试项目**：注释精确度较低。在测试设置和断言中更自由地使用 `!`，因为空值永远不会预期。专注于确保测试代码干净地编译。

### 步骤 2：选择实施策略

根据代码库的大小和活动级别选择以下策略之一。建议用户并确认后再继续。

> **多项目解决方案：** 按依赖顺序迁移——首先迁移共享库和核心项目，然后迁移使用它们的那些项目。首先注释依赖项可以消除其消费者中的级联警告，并防止重复工作。

无论采用何种策略，**从中心开始向外工作**：从具有很少依赖项但被广泛使用的核心领域模型、DTOs 和共享实用类型开始。首先注释这些可以消除整个代码库中的级联警告，并给出最大的努力回报。然后继续处理依赖于核心类型的高级服务、控制器和 UI 代码。这种方法最大限度地减少了每个步骤的警告数量，并防止因大型项目全面启用而淹没大量警告。最好为每个项目或每个层创建至少一个 PR，以保持更改集可审查和专注。如果需要注释的数量相对较少，则单个项目全面启用和单个 PR 可能是合适的。

#### 策略 A — 项目全面启用（小型到中型项目）

当项目少于大约 50 个源文件或团队希望一次性完成时最佳。

1. 在 `.csproj` 中的 `<PropertyGroup>` 中添加 `<Nullable>enable</Nullable>`。
2. 构建并一次性解决所有警告。

#### 策略 B — 先警告后注释（大型或活跃项目）

当代码库很大或由多个贡献者积极开发时最佳。

1. 在 `.csproj` 中添加 `<Nullable>warnings</Nullable>`。这启用了警告，但不会改变类型语义。
2. 构建，修复来自步骤 3 及以后的警告。
3. 更改为 `<Nullable>enable</Nullable>` 以激活注释——这将触发第二波警告。
4. 解决来自步骤 4 及以后的注释阶段警告。

#### 策略 C — 文件逐个（非常大的项目）

适用于大型遗留代码库，其中全面启用会产生无法管理的警告数量。

1. 在项目级别设置 `<Nullable>disable</Nullable>`（或省略）。
2. 在迁移每个文件时在其顶部添加 `#nullable enable`。
3. 按依赖顺序优先处理文件：首先处理共享实用工具和模型，然后处理更高级别的消费者。

> **构建检查点：** 在启用 `<Nullable>`（或向第一批文件添加 `#nullable enable`）后，执行**清理构建**（例如，`dotnet build --no-incremental`，或先删除 `bin`/`obj`）。增量构建仅重新编译已更改的文件，并将未更改文件的警告隐藏。记录初始警告计数——这是要减少的基线。在修复警告之前，请先确认项目仍然可以编译。在此工作流程中的后续所有构建检查点都使用清理构建。

### 步骤 3：修复解引用警告

> **优先级：** 按依赖顺序处理文件——首先从其他代码依赖的核心模型和共享实用工具开始，然后移动到更高级别的消费者。在每个文件中，首先修复公共和保护成员（这些定义了合同），然后修复内部和私有成员。这种顺序最大限度地减少了级联警告：修复核心类型的注释通常会自动解决其消费者中的警告。

构建项目并处理解引用警告。这些是最常见的：

| 警告 | 含义 | 典型修复 |
|---------|---------|-------------|
| CS8602 | 可能空引用的解引用 | 优先选择仅注释修复：如果空值有效，则使上游类型可空 (`T?`)，或者如果可以验证在此点值永远不会为空，则使用 `!`。添加空检查或 `?.` 会改变运行时行为——将它们保留在单独的提交中（见零行为更改规则） |
| CS8600 | 将可能空的转换为非可空类型 | 如果空值有效，则将目标类型添加 `?`，或者如果可以验证值在此点永远不会为空，则使用 `!`。添加空保护会改变运行时行为 |
| CS8603 | 可能空引用返回 | 如果方法可以真正返回空，则将返回类型更改为可空 (`T?`)。**如果方法可以真正返回空，则不要用 `!` 抑制**——修复返回类型。这是 NRT 迁移中的最重要规则：非可空返回类型是对每个调用者的承诺，即永远不会返回空 |
| CS8604 | 可能空引用参数 | 如果空值有效，则将参数标记为可空，或者如果参数可以验证为非空，则使用 `!`。在传递之前添加空检查会改变运行时行为 |

> ❌ **不要使用 `?.` 作为快速修复解引用警告的方法。** 将 `obj.Method()` 替换为 `obj?.Method()` 会无声地改变运行时行为——调用被跳过而不是抛出。只有在您有意要容忍空值时才使用 `?.`。

> ❌ **不要随意使用 `!` 来抑制警告。** 每个 `!` 都是一个值永远不会为空的声明。如果该声明是错误的，您就隐藏了一个 `NullReferenceException`。添加空检查或使类型可空代替。

> ❌ **永远不要使用 `return null!` 来保持非可空返回类型。** 如果方法返回 `null`，则返回类型必须为 `T?`。编写 `return null!` 会将空值隐藏在非可空签名后面——调用者信任签名，跳过空检查，并在运行时遇到 `NullReferenceException`。这适用于 `null!`、`default!` 和任何使编译器接受非可空位置中的空的转换。`!` 在返回值上的唯一可接受用法是当值**可证明永远不会为空**，但编译器无法看到为什么。

> ⚠️ **不要在值类型上添加 `?`，除非您打算更改运行时类型。** 对于引用类型，`?` 是元数据。对于值类型（`int`、枚举、结构），`?` 将类型更改为 `Nullable<T>`，改变方法签名、二进制布局和装箱行为。

**每个警告的决策流程图：**

1. **设计是否允许空值？**
   - **是** → 在声明中添加 `?`（使其可空）。
   - **否** → 转到步骤 2。
   - **不确定** → 在继续之前询问用户。
2. **您能否证明在此点值永远不会为空？**
   - **是，但编译器无法看到代码路径** → 添加 `!` 并附上解释原因的注释。
   - **是，通过添加保护** → 添加空检查 (`if`, `??`, `is not null`)。
   - **否** → 类型应该是可空的（回到步骤 1——答案是“是”）。

指导：

- 优先使用显式空检查 (`if`, `is not null`, `??`) 而不是空值消除运算符 (`!`)。
- 只有当您能证明值永远不会为空，但编译器无法看到时，才使用空值消除运算符，并添加解释原因的注释。
- 保护库（例如，Ardalis.GuardClauses、Dawn.Guard）通常使用 `[NotNull]` 装饰参数，这会在保护调用后缩小空状态。在 `Guard.Against.NullOrEmpty(value, nameof(value))` 后，编译器已经将 `string?` 缩小为 `string`——在后续赋值处不要添加冗余的 `!`。在假设编译器需要帮助之前，检查保护方法是否使用 `[NotNull]`。
- 当方法可以真正返回空时，应将返回类型更改为 `T?`——不要在非可空签名后面隐藏空值。
- `Debug.Assert(x != null)` 像编译器一样充当空状态提示，就像 `if` 检查一样。在方法或块的顶部使用它，以告知流分析器关于不变量，并消除该作用域中的后续 `!` 运算符。注意：`Debug.Assert` 通知编译器，但在发布构建中被剥离——它不会在运行时保护免受空值影响。对于公共 API 边界，优先使用显式的空检查或 `ArgumentNullException`。
- 如果您发现自己需要在内部方法的每个调用位置添加 `!`，请考虑使该参数可空。将 `!` 保留用于编译器确实无法证明非空性的情况。
- 当布尔返回帮助方法的返回值保证可空参数非空时（例如，`if (IsValid(x))` 暗示 `x != null`），优先在帮助方法的参数上添加 `[NotNullWhen(true)]` 而不是在每个调用位置使用 `!`。这是一个仅元数据的更改（没有行为更改），可以消除下游的 `!` 运算符，同时向编译器提供真实的流信息。
- 对于在构造后始终设置的字段（例如，由框架、`Init()` 方法或构建模式设置），优先使用字段声明上的 `= null!` 而不是在每个使用位置添加 `!`。被访问 50 次的字段应该有一个 `= null!`，而不是 50 个 `field!` 断言。这使字段在类型系统中保持非可空，同时承认后期初始化。在可能的情况下，在初始化方法上添加 `[MemberNotNull]`。
- 对于返回 unconstrained 类型参数 `default` 的泛型方法（例如，`FirstOrDefault<T>`），使用 `[return: MaybeNull] T` 而不是 `T?`。在 unconstrained 泛型上使用 `T?` 会将值类型签名更改为 `Nullable<T>`，改变方法签名、二进制布局和装箱行为。`[return: MaybeNull]` 保留原始签名，同时传达返回可能为空值的信息。
- LINQ 的 `Where(x => x != null)` 不会将 `T?` 缩小为 `T`——编译器无法跟踪通过传递给泛型方法的 lambda 的空值。使用 `source.OfType<T>()` 以正确地缩小类型来过滤空值。

> **构建检查点：** 在修复解引用警告后，构建并确认仍然没有 CS8602/CS8600/CS8603/CS8604 警告，然后移动到注释警告。

### 步骤 4：注释声明

首先决定每个成员的**预期空值**，根据其设计目的——这个参数是否接受空值？这个返回值是否可能为空？相应地注释，然后解决任何产生的警告。不要让警告驱动您的注释；这会导致过度注释 `?` 或随意散布 `!` 来抑制编译器。

> **何时询问用户：** 不要猜测 API 合同。绝对不要仅凭使用频率或命名约定来推断空值意图——如果代码或文档中没有明确的意图，请询问用户。具体来说，在以下情况下询问： (1) 更改公共方法的返回类型为可空或向公共参数添加 `?`——这会更改消费者依赖的 API 合同；(2) 当设计意图不明确时，决定属性是否应该为可空还是必需；(3) 在您无法从上下文中确定空是否为有效状态时，选择空检查和 `!` 之间的转换。对于使用情况明显的地方，内部/私有代码可以更自由地使用 `!`，因为它不会影响外部调用者。

> ❌ **不要让警告驱动注释。** 首先决定每个成员的预期空值，然后注释。到处添加 `?` 以消除警告会适得其反——调用者必须添加不必要的空检查。仅当空值是有效值时才使用 `?`。

> ⚠️ **返回类型必须反映语义空值，而不仅仅是编译器满意度。** 一个常见的错误是删除返回类型中的 `?`，因为实现使用 `default!` 或一个使编译器满意的转换。如果方法按设计可以返回空，则其返回类型必须为可空——无论编译器是否警告。关键模式：
> - 以 `*OrDefault` 命名的 方法（`FirstOrDefault`、`SingleOrDefault`、`FindOrDefault`）→ 返回类型必须为可空 (`T?`, `object?`, `dynamic?`)，因为“或默认”意味着“或空”对于引用类型。
> - `ExecuteScalar` 和类似的数据库方法 → 返回类型必须为 `object?`，因为结果可以是 `DBNull.Value` 或空，当没有匹配的行时。
> - `Find`、`TryGet*`（out 参数）、查找方法 → 当项目可能不存在时，返回类型应为可空。
> - 任何文档化或设计为在失败、未找到或空输入时返回空值的方法 → 可空返回类型。
>
> 编译器无法捕获返回类型中缺少 `?` 的情况，当实现使用 `!` 或 `default!` 隐藏空值时。这使注释对消费者来说不正确——他们信任非可空签名并跳过空检查，导致运行时出现 `NullReferenceException`。

> ⚠️ **不要删除现有的空参数验证。** 非可空注释仅是编译时提示——它不会阻止运行时传递空值。使用旧版 C# 版本、其他 .NET 语言、反射或 `!` 的调用者仍然可以传递空值。

> ⚠️ **标记缺少运行时空值验证的公共 API 方法——但不要添加检查。** 在注释过程中，检查每个 `public` 和 `protected` 方法：如果参数是非可空的 (`T`, 不是 `T?`)，则应该有一个运行时空值检查（例如，`ArgumentNullException.ThrowIfNull(param)` 或 `if (param is null) throw new ArgumentNullException(...)`）。如果没有，则在运行时传递空值会导致在方法体深处出现 `NullReferenceException` 考虑到入口点的 `ArgumentNullException`。添加空保护是运行时行为更改，不能作为 NRT 迁移的一部分。相反，询问用户是否希望在位置处插入 `// TODO: 考虑添加 ArgumentNullException.ThrowIfNull(param)` 注释。这对于库尤其重要，因为调用者可能没有启用 NRTs。

> **具有定义空值行为的方法应该接受可空参数。** 如果方法优雅地处理空输入——返回空值、返回默认值或返回失败结果而不是抛出异常——参数应该是 `T?`, 不是 `T`。BCL 遵循此约定：`Path.GetPathRoot(string?)` 对于空输入返回空值，而 `Path.GetFullPath(string)` 抛出异常。仅当空值导致异常时才使用非可空参数。将参数标记为非可空，而方法实际上容忍空值，会强制调用者添加不必要的空检查。

> **灰色地带：** 当参数既未验证也未清理也未文档化是否为空时，请考虑：(1) 在您的代码库中是否 ever 传递空值？如果是，则可空。(2) 调用者是否可能使用空值作为“默认”或无操作占位符？如果是，则可空。(3) 同一区域的类似方法是否接受空值？如果是，则为了一致性而可空。(4) 如果方法基本上无视空值，只是碰巧能工作，但空值对 API 的目的没有语义意义 → 非可空。当在可空和不可空之间不确定参数时，优先选择可空——它更安全，并且可以以后收紧。

在解引用警告解决后，解决注释警告：

| 警告 | 含义 | 典型修复 |
|---------|---------|-------------|
| CS8618 | 非可空字段/属性在构造函数中未初始化 | 初始化成员，使其可空 (`?`)，或使用 `required` (C# 11+)。对于在构造函数之外始终设置的字段（例如，由框架生命周期方法、`Init()` 调用或构建模式设置），使用 `= null!` 来声明意图，同时保持字段在每次使用时非可空。如果辅助方法初始化字段，请在该方法上添加 `[MemberNotNull(nameof(field))]`，以便编译器知道该字段在调用后是非空的 |
| CS8625 | 不能将空字面量转换为非可空类型 | 使目标可空或提供非空值 |
| CS8601 | 可能空引用赋值 | 与 CS8600 相同技术 |

对于每个类型，决定：**这个成员是否可能为空？**

- **是** → 在其声明中添加 `?`。
- **否** → 确保它在每个构造函数路径中初始化，或将其标记为 `required` (C# 11+)。
- **否，但它是在构造函数之后设置的**（例如，由框架方法、`Init()` 方法或两阶段初始化模式设置）→ 在字段声明中使用 `= null!`。这使字段的类型在每次使用时非可空，同时告诉编译器“我保证在访问之前它会设置。” 这远优于在每次使用位置添加 `!`——被访问 50 次的字段需要 50 个 `!` 而不是一个 `= null!`。如果初始化是由特定方法完成的，还考虑在该方法上添加 `[MemberNotNull(nameof(field))]`。

优先将注释工作集中在公共和受保护的 API 上——这些定义了消费者依赖的合同。内部和私有代码可以更自由地使用 `!`，因为它不会影响外部调用者。

> **构建检查点：** 在注释声明后，构建并确认仍然没有 CS8618/CS8625/CS8601 警告，然后移动到可空属性。

### 步骤 5：应用可空属性以处理高级场景

当简单的 `?` 注释无法表达空合同时，应用 `System.Diagnostics.CodeAnalysis` 中的属性——有关完整属性表（`[NotNullWhen]`、`[MaybeNullWhen]`、`[MemberNotNull]`、`[AllowNull]`、`[DisallowNull]`、`[DoesNotReturn]` 等）以及每个属性的用法指导，请参阅 [references/nullable-attributes.md](references/nullable-attributes.md)。

> **构建检查点：** 应用可空属性后，构建以验证属性解决了目标警告，并且没有引入新的警告。

### 步骤 6：清理抑制项

> **可选：** 重新运行 `scripts/Get-NullableReadiness.ps1` 以获取项目当前 `#nullable disable` 指令、`!` 运算符和 `#pragma warning disable CS86xx` 抑制的计数。

1. 搜索作为临时工作区添加的任何 `#nullable disable` 指令或 `!` 运算符。
2. 对于每个，确定抑制项是否仍然需要。
3. 删除不再必要的抑制项。对于任何剩余的，添加解释原因的注释。
4. 搜索 `#pragma warning disable CS86` 以查找被抑制的可空警告，并评估是否可以修复底层问题。

> **构建检查点：** 删除抑制项后，再次构建——删除 `#nullable disable` 或 `!` 可能会暴露需要修复的新警告。

### 步骤 7：验证

1. 构建项目并确认没有可空警告。
2. 在项目文件中添加 `<WarningsAsErrors>nullable</WarningsAsErrors>` 以永久防止可空回归。这是项目文件等效于 `dotnet build /warnaserror:nullable`。
3. 运行现有测试以确认没有回归。
4. 如果项目是库，检查公共 API 表面以验证可空注释与预期合同匹配（接受 null 的参数是 `T?`，拒绝 null 的参数是 `T`）。

> **在报告成功完成迁移之前进行验证。** 零警告并不意味着迁移是正确的。在报告成功之前： (1) 快速检查公共 API 签名——确认 `?` 注释与实际设计意图匹配，而不仅仅是编译器沉默；(2) 验证没有添加 `?.` 运算符会改变运行时行为（在 diff 中搜索 `?.`）；(3) 确认没有删除 `ArgumentNullException` 检查；(4) 检查 `!` 运算符很少出现，并且每个运算符都有证明性的注释。

- [ ] 项目文件包含 `<Nullable>enable</Nullable>`（或文件逐个策略的 `#nullable enable` 每个文件）或解决方案
- [ ] 构建产生零 CS86xx 警告
- [ ] 在项目文件中添加 `<WarningsAsErrors>nullable</WarningsAsErrors>` 以防止回归
- [ ] 测试通过且没有回归
- [ ] 没有 `#nullable disable` 指令剩余，除非有注释解释原因
- [ ] 空值消除运算符 (`!`) 很少出现，每个运算符都有证明性的注释
- [ ] 公共 API 签名准确反映空合同
- [ ] 对于公共库：`nullable-breaking-changes.md` 中记录了破坏性更改，并由用户审查

### 代码审查清单

可空迁移更改需要比典型 diff 更广泛的审查：

1. **验证没有行为更改**：确认 `?` 和 `!` 是唯一添加项——没有偶然的 `?.`，没有删除空检查，没有新的分支。生成的 IL 应该保持不变，除了可空元数据。
2. **审查显式注释更改**：对于每个添加到参数或返回类型的 `?`，确认它是否与预期设计匹配。该方法是否真的接受 null？它是否真的可以返回 null？

## NRT 注释引起的破坏性更改（库）

对于库，请参阅 [references/breaking-changes.md](references/breaking-changes.md)——NRT 注释是公共 API 合同的一部分，不正确的注释对消费者来说是源代码破坏性更改。

## 常见陷阱

| 陷阱 | 解决方案 |
|-------|----------|
| 滥用 `!` 来抑制警告 | `!` 运算符隐藏错误。添加空检查或使类型可空代替 |
| 将所有内容标记为 `T?` 以快速消除警告 | 过度注释 `?` 会适得其反——调用者必须添加不必要的空检查。仅当空值是有效值时才使用 `?` |
| 构造函数未初始化所有非可空成员 | 在每个构造函数中初始化字段和属性，使用 `required` (C# 11+)，或使成员可空 |
| 序列化绕过构造函数——非可空 ≠ 运行时安全性 | 序列化器在不调用构造函数的情况下创建对象，因此非可空 DTO 属性在运行时仍然可能为空。有关详细指导，请参阅步骤 4 中的“DTOs 与领域模型” |
| 生成的代码产生警告 | 如果生成的文件包含 `<auto-generated>` 注释，则它们会自动排除在可空分析之外。如果警告仍然存在，则在生成的文件顶部添加 `#nullable disable` 或配置 `.editorconfig` 使用 `generated_code = true` |
| 多目标项目和旧 TFMs | NRT 注释在旧 TFMs（例如，.NET Standard 2.0）与 C# 8.0+ 编译，但可能不存在可空属性，如 `[NotNullWhen]`。使用 NuGet 的 `Nullable` 多重填充包，或内部定义属性 |
| 升级依赖项后警告重新出现 | 依赖项添加了可空注释。这是预期且有益的——按照步骤 3–5 修复新警告 |
| 在注释时意外更改行为 | 将 `?` 添加到类型或 `!` 添加到表达式是仅元数据的，不会改变生成的 IL。但将 `obj.Method()` 替换为 `obj?.Method()`（空条件表达式）会改变运行时行为——调用被无声地跳过而不是抛出。只有在您有意要容忍空值时才使用 `?.`，而不是作为快速修复警告的方法 |
| 将 `?` 添加到值类型（枚举、结构） | 对于引用类型，`?` 是仅元数据的注释，没有运行时效果。对于值类型（如 `int` 或枚举），`?` 将类型更改为 `Nullable<T>`，改变方法签名、二进制布局和装箱行为。仔细检查您是否只添加了 `?` 到引用类型，除非您确实打算使值类型可空 |
| 移除现有的空参数验证 | 非可空注释仅是编译时提示——调用者仍然可以运行时传递空值。保留现有的 `ArgumentNullException` 检查。有关详细信息，请参阅步骤 4 |
| `var` 推断空值 | 当使用 `var` 时，推断类型包括从分配表达式继承的空值，这与其他地方显式声明 `T` 与 `T?` 显然不同。流分析器从该点向前确定实际的空状态，但推断的声明类型可能包含您未预期的空值。如果精确的声明空值很重要，请使用显式类型而不是 `var` |
| 消费未注释的库（可空遗忘型） | 当依赖项未选择可空注释时，编译器将所有类型视为“遗忘型”——您不会因为解引用或分配 null 考虑到空值而获得警告。这会给人一种虚假的安全感。将来自遗忘型 API 的返回值视为潜在的 null，尤其是那些可能返回 null 的方法（字典查找、`FirstOrDefault` 风格调用）。在可能的情况下，升级依赖项或包装调用 |
