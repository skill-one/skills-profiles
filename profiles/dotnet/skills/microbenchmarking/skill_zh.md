# Benchmark编写指南

BenchmarkDotNet (BDN) 是一个用于编写和运行微基准的.NET库。在本指南中，“BDN”指代BenchmarkDotNet。

> **注意**：对LLM编写BenchmarkDotNet基准的评估揭示了由于对BDN行为过时假设而导致的常见错误模式——特别是在最近的版本中更改的运行时比较、作业配置和执行默认值方面。本指南中的参考文件包含经过验证的当前信息。**在编写任何代码之前，您必须阅读与任务相关的参考文件**——您的训练数据可能包含过时或不正确的BDN模式。

## 关键概念

- **作业**——描述如何运行基准：运行时、迭代次数、启动次数、运行策略和环境设置。可以配置多个作业，在不同的条件下运行相同的基准。
- **基准用例**——一个方法 × 一个参数组合 × 一个作业。BDN测量的基本单元。
- **操作**——被测量的逻辑工作单元。所有BDN输出列（均值、误差等）报告每个操作的时间。
- **调用**——对基准方法的单次调用。默认情况下，1次调用 = 1次操作。使用`OperationsPerInvoke=N`时，每次调用计为N次操作。
- **迭代**——计时批次的调用。BDN测量迭代中所有调用的总时间，然后除以总操作数以获得每次操作的时间。

## 基准是比较工具

单个基准数字的价值有限——它可以确认测量的数量级，但确切值会随机器、操作系统和运行时配置的变化而变化。当与某个事物进行比较时，基准最有用。在编写基准之前，确定当前任务的**比较轴**：

- **方法（A与B）**：在同一运行中并排比较替代实现。
- **运行时**：在.NET版本之间比较相同代码（例如，net8.0与net9.0）。
- **包版本**：比较不同版本的NuGet依赖项。
- **构建（之前/之后）**：将旧代码的保存DLL与当前源代码进行比较。
- **运行时配置（GC模式、JIT设置）**：了解运行时设置如何影响性能——通过单个运行中的多个作业进行比较。
- **规模（N=100与N=1000）**：了解随着输入大小增长，性能如何变化。
- **硬件/操作系统**：跨不同机器或操作系统进行比较——需要在每个环境中分别运行。
- **历史测量**：与在先前时间点记录的测量值进行比较。

BDN可以在单个运行中并排比较前六个轴，但每个都需要特定的CLI标志或配置，这与您可能期望的不同——在配置比较之前，请阅读[参考/comparison-strategies.md](references/comparison-strategies.md)以获取每种策略的正确方法。

## 用例和基准生命周期

开发者编写基准有四个不同的原因，每个原因都会改变基准的设计方式以及它应该存放在哪里：

1. **覆盖套件**：编写基准以最大化真实用例模式的覆盖范围，以便检测影响大多数用户的回归。这些基准是永久的——它们属于项目的基准套件，遵循其约定（目录结构、基类、命名），并提交到版本控制中。

2. **问题调查**：有人报告了一个特定的性能问题。编写基准以重现和诊断该特定问题。这些基准是任务范围的——它们在调查期间持续存在（重现 → 隔离 → 验证修复），但不是永久套件的一部分。

3. **变更验证**：开发人员有一个PR或变更，希望在合并之前了解其性能特征。这些基准是任务范围的——它们在审查周期内持续存在，但不会被提交。

4. **开发反馈**：开发人员正在积极处理一个任务，并希望使用基准来评估方法并获得早期信息。这些基准是任务范围的，并且是丢弃的——它们在开发会话期间持续存在，但在做出决定时被删除。

对于用例1，按照其约定添加到现有的基准项目。对于用例2-4，在工作目录中创建一个独立的项目，该目录在任务期间持续存在，但显然不是永久代码库的一部分。

对于**覆盖套件**基准，从真实调用者的角度进行设计——这个API使用哪些代码模式，它们传递哪些输入，以及哪些性能特征对它们很重要。每个永久基准都应该通过现实世界的相关性来证明其维护成本。对于**临时基准**，有意保持用例数量——每个额外的测试用例都会增加墙钟时间（阅读[成本意识](#cost-awareness))。

## 成本意识

每个基准用例（一个方法 × 一个参数组合 × 一个作业）在默认设置下需要**15-25秒**。`[Params]`创建笛卡尔积：两个`[Params]`在5个方法中有3和4个值 = 60个用例 ≈ 20分钟。多个作业会进一步乘以这个时间。在运行之前，估计总用例数，并将作业预设与情况匹配：

| 预设 | 每用例时间 | 使用时机 |
|------|------------|----------|
| `--job Dry` | <1秒 | 验证正确性——确认编译和执行而不进行测量 |
| `--job Short` | 5-8秒 | 开发或调查期间的快速测量 |
| *(默认)* | 15-25秒 | 覆盖套件的最终测量 |
| `--job Medium` | 33-52秒 | 当结果很重要时，提高置信度 |
| `--job Long` | 3-12分钟 | 高统计置信度 |

如果基准运行时间比预期长，结果似乎不稳定，或者您需要调整迭代次数或执行设置，请阅读[参考/bdn-internals-and-tuning.md](references/bdn-internals-and-tuning.md)以获取有关BDN执行管道和配置选项的详细信息。

## 入口点和配置

BDN程序使用**`BenchmarkSwitcher`**（为人类提供交互式基准选择，解析CLI参数）或**`BenchmarkRunner`**（直接运行指定的基准）。两者都支持CLI标志，如`--filter`和`--runtimes`，但只有在通过`args`传递时才支持——如果没有，CLI标志将被静默忽略。使用`BenchmarkSwitcher`时，始终传递`--filter`以避免在交互式提示上挂起。

通过**属性**、**配置对象**和**CLI标志**自定义BDN行为。

阅读[参考/项目设置和运行.md](references/project-setup-and-running.md)以获取入口点设置、配置对象模式以及CLI标志。如果您需要收集除墙钟时间之外的数据——例如内存分配、硬件计数器或分析跟踪——请阅读[参考/诊断器和导出器.md](references/diagnosers-and-exporters.md)。

## 运行基准

BenchmarkDotNet控制台输出非常冗长——每个用例显示数百行，显示内部校准、预热和测量详细信息。将所有输出重定向到文件，以避免在冗长的迭代输出上消耗上下文：

```
dotnet run -c Release -- --filter "*MethodName" --noOverwrite > benchmark.log 2>&1
```

每个基准方法可以持续几分钟。与其一次性运行所有基准，不如使用`--filter`分批运行子集（例如每次调用一个或两个方法），读取结果，然后运行下一个子集。这可以使每次调用保持简短——避免会话或终端超时——并允许您逐步验证结果。阅读[参考/项目设置和运行.md](references/project-setup-and-running.md)以获取过滤器语法、CLI标志和项目设置。

每次运行后，从结果目录中读取Markdown报告（`*-report-github.md`）以获取摘要表。只有在调查错误或意外结果时，才读取`benchmark.log`。

## 编写新的基准

### 第1步：规划测试用例

在编写任何代码之前，确定：

- 该基准服务于哪个用例（覆盖、调查、变更验证或开发反馈）。
- 哪个比较轴适用（数字将与什么进行比较？）。
- 基于调用者实际如何使用API，要基准测试哪些真实场景。

每个基准用例都应该证明其成本。未覆盖的场景通常比另一个已覆盖的参数组合更有价值，但当特定参数维度确实会影响性能特征时，深度是合理的。

确定测试用例列表。对于每个测试用例，思考：

- **如何表达变化**：BenchmarkDotNet提供了多种机制来参数化基准——`[Params]`和`[ParamsSource]`用于属性级参数，`[Arguments]`和`[ArgumentsSource]`用于方法级参数，`[ParamsAllValues]`用于枚举`bool`或枚举的所有值，以及`[GenericTypeArguments]`用于在泛型基准类上变化类型参数。选择最适合所变化维度的机制。阅读[参考/编写基准.md](references/writing-benchmarks.md)以获取所有选项和正确性模式的完整集。
- **输入数据来自哪里**——考虑哪些来源是适当的（可以组合使用）：
  - 固定值——小而固定的值，其中输入的确切值很重要（例如，特定字符串、已知边缘情况大小）。存储在字段或`[Params]`中，以避免常量折叠。
  - 资源文件——静态数据太大或不适合嵌入源代码，例如二进制大块。
  - 通过`[ParamsSource]`/`[ArgumentsSource]`/`[GlobalSetup]`程序生成——当数据形状比具体内容更重要，或者输入必须按大小参数化时。
- **是否适合随机性**：如果使用生成数据，请使用种子随机性以实现可重复性。在生成随机数据时，使用足够大的样本，以便生成的分布具有代表性（例如，4个随机值可能会聚集在一个狭窄的范围内，而1000个会更好地执行整个分布）。

### 第2步：实现基准

对于**覆盖套件**基准，添加到现有的基准项目并遵循其约定。对于**临时基准**（调查、变更验证、开发反馈），创建一个独立的项目——阅读[参考/项目设置和运行.md](references/project-setup-and-running.md)以获取项目设置和入口点配置。

**添加BenchmarkDotNet包**：始终使用`dotnet add package BenchmarkDotNet`（不带版本）——这允许NuGet解析最新兼容版本。**不要**手动编写带有版本号的`<PackageReference>`到`.csproj`中；培训数据中的BDN版本已过时，并且可能缺乏对当前.NET运行时的支持。

编写基准代码。遵循[参考/编写基准.md](references/writing-benchmarks.md)中的模式，以避免常见的测量错误——特别是：

- **从基准方法返回结果**以防止死代码消除
- **将初始化移至`[GlobalSetup]`**——基准方法内的设置会被测量；仅在基准必须重置迭代之间状态时使用`[IterationSetup]`
- **不要添加手动循环**——BDN会自动控制调用次数
- **标记基线**当比较替代方案时——使用`[Benchmark(Baseline = true)]`进行方法级比较，或在多作业比较中在作业上使用`.AsBaseline()`，以便结果显示相对比率
- **将输入存储在字段或`[Params]`中**，而不是作为字面量或`const`值——JIT可以在编译时折叠常量表达式，使基准测量预计算结果而不是实际计算

### 第3步：验证和运行

在长时间运行之前进行验证：

1. 首先使用`--job Dry`运行，以捕获编译错误和运行时异常，而无需在测量上花费时间。
2. 使用默认设置运行单个代表性用例，以验证输出看起来是否正确，数字是否在预期范围内。
3. 验证通过后，再运行完整套件。

在迭代基准设计时，使用`--job Short`，直到有信心，然后切换到默认设置以获取最终数字。
