# 代码测试生成技能

一种使用协调的多智能体管道为任何编程语言生成全面、可工作的单元测试的 AI 驱动技能。

## 不可协商的执行合同

在编辑前分类范围：

- **广泛**（项目/包范围的套件，或多个生产文件/模块）：在实现前，在解析的非暂存 `<TESTAGENT_DIR>` 中创建 `research.md` 和 `plan.md`，然后在最终测试质量审查后在那里创建 `status.md`。如果这些文件不存在，广泛的流程是不完整的。
- **聚焦**（用户明确限制工作范围为一个函数/类/文件或一个缺失的方法）：不要创建中间状态文件或扩展到多个智能体。即使只有一个源模块存在，稀疏的项目范围请求仍然是广泛的。

对于任何范围，运行最窄的相关测试命令直到干净退出，并以紧凑的 `Requirement | Evidence` 表格结束。每个请求的行为必须引用确切的测试名称；验证行引用成功的命令。
对于聚焦工作，“没有中间状态文件”仅改变流程，而不是最终证据合同。

中间状态文件是内部工作数据，永远不会是交付物。保持 `<TESTAGENT_DIR>` 非暂存，永远不要将其或其文件放在版本控制的工作区内容中，永远不要修改 `.gitignore` 来隐藏它们。

将完整性视为一个需求矩阵，而不是测试计数的目标。给每个独立请求的状态、边界、错误路径或交互分配自己的具体断言。只有在一次执行真正证明整个请求的组合时才组合用例；不要让参数化的快乐路径用例代替空状态、无效区分器或边界之前/之中/之后。
对于命名多个生产模块或层的广泛请求，给每个命名的模块直接测试其非平凡公共行为。跨模块测试证明组合，但不会替代请求的模块级覆盖率。通过行为矩阵判断范围，而不是匹配或超过原始测试计数。

对于**广泛或全面**的请求，显式矩阵是底线，而不是上限。满足它后，检查每个目标 API 的可观察等价划分和不变量，这些不变量提示没有在提示中命名：身份、空、单例和代表性内部输入；确切的边界加上一个立即相邻的值；无效划分；以及排序、单调性、回滚、容量、截断或由实现暗示的状态不变量。为每个不同的划分添加一个与现有证明不同的变异相关用例，使用参数化或表格驱动用例为兄弟用例。当剩余输入执行相同的分支和不变量时停止，而不仅仅是在显式清单完成时；永远不要仅为了提高计数而添加用例。

## 何时使用此技能

当你需要时使用此技能：

- 为整个项目或特定文件生成单元测试
- 改善现有代码库的测试覆盖率
- 创建遵循项目约定的测试文件
- 编写实际编译和通过的测试
- 为新功能或未测试的代码添加测试
- 生成或扩展 MSTest 套件；在此条技能建立范围和项目约定后加载 `writing-mstest-tests` 作为支持性指导

## 何时不用

- 运行或执行现有测试（使用 `run-tests` 技能）
- 在测试框架之间迁移（使用迁移技能）
- 回答 MSTest API/模式或现代化问题，但不要求生成测试（使用 `writing-mstest-tests`）
- 调试失败的测试逻辑

## 工作原理

此技能协调多个专业智能体在 **研究 → 规划 → 实现** 管道中：

### 管道概述

```text
┌─────────────────────────────────────────────────────────────┐
│                     测试生成器                          │
│ 协调整个管道并管理状态            │
└─────────────────────┬───────────────────────────────────────┘
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
┌───────────┐  ┌───────────┐  ┌───────────────┐
│ 研究者   │  │ 规划者   │  │ 实现者     │
│          │  │          │  │             │
│ 分析代码库 │  │ 创建     │  │ 按阶段编写测试 │
│          │→ │ 阶段化计划 │→ │             │
└───────────┘  └───────────┘  └───────┬───────┘
                                      │
                    ┌─────────┬───────┼───────────┐
                    ▼         ▼       ▼           ▼
              ┌─────────┐ ┌───────┐ ┌───────┐ ┌───────┐
              │ 构建者   │ │ 测试者 │ │ 修复者 │ │ 格式化器 │
              │          │ │       │ │       │ │       │
              │ 编译代码  │ │ 运行测试 │ │ 修复错误│ │ 格式化代码 │
              └─────────┘ └───────┘ └───────┘ └───────┘
```

## 分步说明

### 第 1 步：确定用户请求

确保你理解用户在请求什么以及范围是什么。
当用户对测试风格、覆盖率目标或约定没有明确要求时，从 [unit-test-generation.prompt.md](unit-test-generation.prompt.md) 源引指南。此提示提供了发现约定、参数化策略、覆盖率目标（目标是 80%）和特定语言模式的最佳实践。

### 第 2 步：在调用任何东西之前确定请求的大小

根据范围匹配机械。在一个文件请求上运行完整管道会消耗回合和工具调用，而不会改进测试。

| 范围 | 看起来像什么 | 如何运行它 |
| --- | --- | --- |
| **聚焦** | 一个函数、类或文件；“仅测试 X”；扩展现有套件以包含缺失的用例 | 跳过中间状态文件和子智能体扩展。在实现前，将要求清单保存在你的脑海中（或保存在最终表格中），只读取目标和一个相邻的测试以获取约定，编写测试，运行最窄的测试命令，在线审查自己的断言。 |
| **广泛** | 一个项目、包或模块集；“综合套件”；跨多个文件清除的覆盖率阈值 | 在第 3 步中运行完整的研究 → 规划 → 实现管道，在 `<TESTAGENT_DIR>` 下有中间状态文件和下面的完成合同。 |

当不确定时，从聚焦开始，如果请求跨越多个文件，再升级。升级成本一个额外的通过；在聚焦请求上运行广泛管道会花费几个。

在结束聚焦请求之前，一起检查所有三个条件：

1. 每个命名的行为都有一个具体的断言，包括每个请求的边界或错误路径；
2. 窄测试命令成功退出；
3. 最终的 `Requirement | Evidence` 表格将那些行为映射到确切的测试名称，并引用那个成功的命令。

不要用关于已覆盖区域的散文列表替换它，即使对于单个函数请求也是如此。

### 第 3 步：调用测试生成器（广泛范围）

首先调用 `code-testing-generator` 智能体，并提供你的测试生成请求：

```text
为 [要测试的路径或描述] 生成单元测试，遵循 [unit-test-generation.prompt.md](unit-test-generation.prompt.md) 指南。将当前工作区视为权威的，即使它是稀疏的、看起来空的、合成的或缺少跟踪文件；永远不要恢复或重建它，包括使用 `git checkout`、`git restore`、`git reset` 或 `git clean`。
```

测试生成器将自动管理整个管道。

如果 `code-testing-generator` 不可用，不要跳过工作流。执行相同的研究 → 规划 → 实现序列，按如下所述解析 `<TESTAGENT_DIR>`，在那里创建中间状态文件，并应用相同的完成合同。

对于广泛范围，在创建中间状态文件之前解析一个绝对 `<TESTAGENT_DIR>`：

1. 优先使用主机提供的会话工件或临时目录。
2. 否则，在 Git 工作树中运行 `git rev-parse --path-format=absolute --git-path testagent`；这返回一个在工作树特定 Git 元数据中的路径，无法暂存。
3. 在 Git 外部，在操作系统临时目录下创建一个唯一目录。

将绝对目录传递给每个管道智能体。路径可能在仓库的 `.git` 元数据目录中，但它必须不是版本控制的工作区内容，不会出现在 `git status` 中，或可以被暂存。

### 第 4 步：使用有限上下文执行

对于多文件请求：

1. 在实现前，将每个显式用户要求转换为一个清单。包括请求的层、要模拟的协作者、边界情况、集成、覆盖率阈值和报告工件。逐字复制多条件要求——它们必须每个映射到一个测试，该测试执行整个组合。
2. 只研究请求的模块或项目，并将清单和紧凑的目标清单写入 `<TESTAGENT_DIR>/research.md`。
3. 重用清单、符号引用和确定性配对工具，而不是读取每个源文件和测试文件。
4. 对于 C#、Python、TypeScript/JavaScript、Go、Java、Rust、Ruby、Kotlin、Swift、PowerShell 或 C++ 的多文件范围，运行一次 `find-untested-sources` 并消耗其配对和建议路径输出；不要手动重复发现。
5. 一次规划每个目标文件，然后按顺序实现阶段。将每个清单项映射到至少一个具体测试或解释为什么它被阻塞。
6. 在修复周期中构建和测试窄目标；在结束时运行工作级验证一次。
7. 在报告成功之前，重新打开生成的测试，并验证每个清单项与具体的测试名称和断言。仅覆盖率本身不是证据，证明请求的模拟接缝、边界、状态转换或属性组合已被测试。
8. 只有当仓库没有代表性测试且基础扩展不足时，才从 `code-testing-extensions` 读取语言示例。
9. 对于 .NET，在选择命令或创建文件之前，先区分 SDK 风格与经典非 SDK。在经典项目中，保留 `packages.config`、现有框架/模拟版本和自定义基础固定件，将每个新测试文件添加到项目显式的 `<Compile Include>` 项中，并使用仓库的 MSBuild/test 运行器命令。永远不要为了生成测试而现代化项目或依赖堆栈。
10. 对于 MSTest，在选择异常断言之前检查固定包版本。MSTest 3.5.x 使用 `Assert.ThrowsException<T>`；不要用 `[ExpectedException]`、`Assert.Throws<T>` 或 `Assert.ThrowsExactly<T>` 替代。

### 完成合同

每个范围必须满足下面的 3-5 点。1 和 2 是**广泛范围**的工件：对于聚焦请求，相同的推理在线发生，并且不编写中间状态文件。

在所有这些都为真之前，不要报告完成：

1. *(广泛范围)* `<TESTAGENT_DIR>/research.md` 记录了有界目标清单、现有测试约定和接受清单。
2. *(广泛范围)* `<TESTAGENT_DIR>/plan.md` 将每个清单项映射到计划的测试或显式阻塞器。
3. 生成的测试使用最窄的相关测试命令编译并通过。
4. 每个显式用户要求都由一个具体的测试和断言支持。即使覆盖率已经通过，也要修复缺失的模拟接缝、边界情况、状态转换和属性组合。在最终摘要中，为每个清单项引用至少一个生成的测试名称，以便完成是可审计的；如果一个项目没有测试可以引用，请继续实施或报告它为阻塞。对于非行为性要求，如脚手架、范围限制、命令或覆盖率工件，引用相关文件、命令或报告，而不是强迫测试名称映射。
   通过的套件即使测试较少也不会自动较弱：通过每个独立请求的行为是否有直接、非冗余的证据来判断完整性，而不是原始测试量。
   对于广泛/全面范围，还验证每个可观察的等价划分和不变量是否在有限的目标 API 中有一个变异相关用例，即使提示没有命名它。
   当请求命名多个模块时，验证除了任何端到端组合测试外，每个模块自己的非平凡公共行为是否都有直接测试证据。
5. 审查生成的测试以查找行为差距和弱断言。在广泛范围内，当可用时，调用 `test-gap-analysis` 和 `assertion-quality`，并将发现和修复记录在 `<TESTAGENT_DIR>/status.md>` 中。在聚焦范围内，进行等效审查——重新阅读每个生成的断言与源代码——而无需启动额外的通过。

最终响应必须包含一个紧凑的 `Requirement | Evidence` 表格。
行为性行引用确切的生成测试名称。非行为性行引用相关项目文件、验证命令或覆盖率报告。一个测试区域的通用列表不能替代按要求提供证据。

**在每个行中逐字引用用户的请求。** 当请求命名一个特定组合时——“一个复合折扣、区域税和基于重量的运费都适用的案例”、“总和折扣与链式折扣之间的区别”、“每个类的构造函数验证”——该行必须引用一个证明正好是这个的测试。一个仅仅执行相同协作者的测试并不满足关于它们交互的要求，并且每个类的要求需要一个每个类的引用。

**引用干净的运行，而不是尝试。** 支持证据表格的命令必须成功完成：引用最终的通过测试摘要，并在请求阈值时，引用一个退出为 0 的每个模块覆盖率表。如果最后一个覆盖率运行退出非零，请修复它并重新运行，然后再报告；永远不要从失败或部分运行中推断阈值清除。

在报告之前，检查最终工作树更改，并确认 `research.md`、`plan.md`、`status.md` 和任何其他中间状态文件不在计划提交的更改中。

## 状态管理

广泛范围运行将中间状态文件存储在由主机临时存储、Git 元数据或操作系统临时目录支持的不可暂存的 `<TESTAGENT_DIR>` 中。聚焦请求不会创建这些文件：

| 文件                     | 目的                      |
| ------------------------ | ---------------------------- |
| `<TESTAGENT_DIR>/research.md` | 代码库分析结果    |
| `<TESTAGENT_DIR>/plan.md`     | 阶段化实施计划   |
| `<TESTAGENT_DIR>/status.md`   | 最终质量审查和修复 |

## 要求

- 项目必须有配置好的构建/测试系统
- 测试框架应已安装（或可安装）
- VS Code 与 GitHub Copilot 扩展

经典非 SDK .NET 项目在它们现有的构建/测试工具链可用时受支持。当它在当前机器上不可用时，智能体仍然可以添加和注册兼容版本的测试，但必须报告执行为阻塞，而不是用 `dotnet test` 替代。

## 故障排除

### 测试不编译

`code-testing-fixer` 智能体会尝试解决编译错误。检查 `<TESTAGENT_DIR>/plan.md` 以获取预期的测试结构。调用 `code-testing-extensions` 技能并阅读语言特定扩展文件以获取错误代码参考（例如，`.NET` 的 `dotnet.md`）。

### 测试失败

生成测试中的大多数失败都是由**断言中的错误预期值**引起的，而不是生产代码错误：

1. 读取实际测试输出
2. 读取生产代码以理解正确行为
3. 修复断言，而不是生产代码
4. 永远不要仅为了使测试通过而将测试标记为 `[Ignore]` 或 `[Skip]`

### 检测到错误的测试框架

在初始请求中指定你首选的框架：“为 Jest 生成测试...”

### 环境依赖的测试失败

依赖于外部服务、网络端点、特定端口或精确时间戳的测试在 CI 环境中会失败。专注于具有模拟依赖关系的单元测试。

### 在完整解决方案上构建失败

在阶段实施期间，仅构建特定的测试项目以加快速度。在所有阶段完成后，运行一次完整的非增量工作区构建以捕获跨项目错误。
