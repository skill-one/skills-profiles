# 规划 Blazor UI 变更

当被要求构建一个复杂的 UI 功能时，**首先规划组件分解，然后立即实施**。一个单一的整体页面组件几乎永远不会是正确的答案——将 UI 分解为专注的、可组合的组件。

## 规划工作流程

### 第 1 步 — 绘制视觉区域图

阅读需求并识别每个独立的视觉区域。每个拥有自己的数据、行为或布局责任的区域都是一个组件候选。

绘制组件树：

```
InventoryDashboard          (页面 — 拥有数据，协调布局)
├── StockSummaryBar         (只读统计：总项目数、低库存计数、价值)
├── InventoryFilters        (搜索框、分类下拉菜单、库存级别切换)
├── InventoryTable          (可排序的产品表格)
│   └── InventoryRow        (单个产品行，支持内联编辑/删除)
└── AddProductForm          (用于新产品的滑出式表单)
```

识别组件的规则：
- **明确的职责** — 一个区域拥有自己的状态或行为 → 分离为独立组件
- **重复的结构** — 列表中的项目、网格中的卡片 → 提取项目模板
- **独立的交互性** — 处理用户输入且与其他兄弟组件分离的模块 → 分离为独立组件
- **大小** — 任何单独存在时会超过 ~150 行标记的模块 → 分割

### 第 2 步 — 分类每个组件

对于树中的每个组件，确定：

| 组件 | 操作 | 渲染模式 | 拥有的状态 | 预计行数 |
|-----------|--------|-------------|-------------|-------------|
| InventoryDashboard | 创建 | InteractiveServer | 产品列表、筛选状态 | ~80 |
| StockSummaryBar | 创建 | (继承) | 无 — 接收数据 | ~30 |
| InventoryFilters | 创建 | (继承) | 搜索文本、选中的分类 | ~60 |
| InventoryTable | 创建 | (继承) | 排序列、排序方向 | ~50 |
| InventoryRow | 创建 | (继承) | 内联编辑模式标志 | ~60 |
| AddProductForm | 创建 | (继承) | 表单模型 | ~80 |

**一个页面组件如果包含超过 ~200 行的标记+代码，则过于庞大。** 如果您的估计显示单个组件超过该限制，请进一步拆分。

### 第 3 步 — 设计数据流

识别每份数据的**状态所有者**，然后绘制其流动路径：

```
InventoryDashboard (拥有：products[], filters)
  │
  ├─ [参数] products ──→ StockSummaryBar (读取聚合统计)
  │
  ├─ [参数] filters ──→ InventoryFilters
  │   └─ EventCallback<Filters> OnFiltersChanged ──→ InventoryDashboard
  │
  ├─ [参数] filteredProducts ──→ InventoryTable
  │   └─ [参数] product ──→ InventoryRow
  │       ├─ EventCallback<Product> OnSave ──→ InventoryTable ──→ InventoryDashboard
  │       └─ EventCallback<Product> OnDelete ──→ InventoryTable ──→ InventoryDashboard
  │
  └─ EventCallback<Product> OnProductAdded ←── AddProductForm
```

规则：
- 数据总是通过 `[参数]` **向下**流动
- 事件总是通过 `EventCallback<T>` **向上**流动
- 页面/父组件**拥有数据**，并将过滤/转换后的视图传递给子组件
- 子组件**永不修改参数** — 它们通过回调通知父组件
- 如果数据需要跨越超过 2 个级别且中间组件不需要，使用级联值或作用域服务

### 第 4 步 — 识别复用机会

在创建新组件之前，检查项目中是否已有组件可以满足需求。寻找：
- 符合结构的现有列表项组件
- 项目中已有的共享筛选/搜索组件
- 接受模板的通用组件（例如，`DataTable<T>`、`Pagination`）

如果一个组件将在多个页面中使用，将其放置在 `Shared/` 或 `Components/` 文件夹中。

### 第 5 步 — 排序实施顺序

自底向上构建——先创建叶组件，然后构建组合它们的父组件：

1. **模型/DTOs** — 定义数据形状
2. **服务** — 数据访问、业务逻辑（接口+实现）
3. **叶组件** — 没有子组件的组件（InventoryRow、StockSummaryBar）
4. **容器组件** — 组合叶组件的组件（InventoryTable、InventoryFilters）
5. **页面组件** — 组合所有组件，注册路由
6. **配置** — DI 注册、渲染模式设置

每个组件应该是独立可编译的。切勿引用尚未存在的组件。

## 输出格式

简要展示计划，然后**立即开始实施**——切勿停留在计划阶段或请求确认前编写代码。计划是一个思考工具，而不是交付物。

```markdown
## 组件计划：[功能名称]

### 组件树
[ASCII 树形图显示父子关系]

### 组件表
| 组件 | 操作 | 渲染模式 | 目的 | 预计行数 |
|-----------|--------|-------------|---------|------------|
| ... | ... | ... | ... | ... |

### 数据流
[状态所有者] → [参数向下] → [事件回调向上]

### 实施顺序
1. [第一个要创建的文件 — 为什么]
2. [第二个文件 — 为什么]
...
```

输出计划后，**立即按顺序开始实现**组件。不要等待批准或询问“是否继续？”——计划是您遵循的指南，而不是用户批准的提案。

## 应避免的反模式

| 反模式 | 为什么错误 | 正确方法 |
|-------------|----------------|-----------------|
| 500+ 行的单个页面组件 | 难以测试、复用或维护 | 分解为专注组件 |
| 通过中间组件传递 10+ 个参数 | 参数穿透隐藏意图 | 使用级联值或作用域状态服务 |
| 子组件从 API 获取自己的数据 | 多个组件进行冗余调用 | 父组件拥有数据，通过参数传递 |
| 复杂标记的列表项内联渲染 | 重复逻辑、无法复用、难以测试 | 将项目模板提取为独立组件 |
| 在一个文件中构建所有内容，然后“稍后重构” | 重构很少发生；单体应用直接发布 | 事先规划分解 |
| 用于一次性用途的通用组件 | 过度设计增加复杂性 | 仅在证明复用时提取通用组件 |

## 指导原则

- **简要规划，立即实施。** 编写简洁的组件表和数据流图，然后立即创建 `.razor` 文件——切勿停留在计划阶段。
- **优先选择多个小组件而非一个大组件。** 单一明确目的的组件更容易理解、测试和复用。
- **状态所有权是首要决策。** 在编写获取逻辑之前，确定哪个组件拥有数据。
- **自底向上构建。** 先创建叶组件，以便父组件可以立即引用它们。
- **组件命名应基于其渲染内容，而非内部实现：** `ProductCard` 而不是 `ProductRenderer`，`OrderFilters` 而不是 `FilterHandler`。
