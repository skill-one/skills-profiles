# MSTest v3 到 v4 迁移

将测试项目从 MSTest v3 迁移到 MSTest v4。结果是一个使用 MSTest v4 的项目，可以正常构建、通过测试，并涵盖所有源不兼容和行为变化。MSTest v4 与 MSTest v3 **不是二进制兼容**的——任何针对 v3 编译的库都必须重新针对 v4 进行编译。

## 首先采取的行动

在搜索网络或凭记忆回答之前，检查提供的项目和源代码。将请求分类为专注的源修复、运行时行为变化、CI 发现问题、兼容性问题或完整迁移，然后按照下表中的匹配行进行操作。干净的编译并不排除这项技能：发现失败、`TestContext` 生命周期异常和测试历史变化是运行时迁移失败。

## 何时使用

- 升级 `MSTest.TestFramework`、`MSTest.TestAdapter` 或 `MSTest` 元包从 3.x 到 4.x
- 升级 `MSTest.Sdk` 从 3.x 到 4.x
- 更新到 MSTest v4 包后修复构建错误
- 升级到 MSTest v4 后解决测试执行中的行为变化
- 更新自定义 `TestMethodAttribute` 或 `ConditionBaseAttribute` 实现，以适应 v4

## 何时不用

- 项目已使用 MSTest v4 并可以正常构建——迁移已完成
- 从 MSTest v1 或 v2 升级——首先使用 `migrate-mstest-v1v2-to-v3`，然后返回这里
- 项目未使用 MSTest
- 在测试框架之间迁移（例如，从 MSTest 迁移到 xUnit 或 NUnit）

## 输入

| 输入 | 是否必需 | 描述 |
|-------|----------|-------------|
| 项目或解决方案路径 | 否 | 包含 MSTest 测试项目的 `.csproj`、`.sln` 或 `.slnx` 入口点。**自行发现**它通过工作目录的通配符；仅在找不到或选择确实模棱两可时才询问 |
| 构建命令 | 否 | 如何构建（例如，`dotnet build`，一个仓库构建脚本）。如果未提供，则自动检测 |
| 测试命令 | 否 | 如何运行测试（例如，`dotnet test`）。如果未提供，则自动检测 |

## 可能改变结果的决定

| 检测到的请求或状态 | 必需的操作 |
|---|---|
| 在当前工作区中提供了文件 | 在那里搜索并打开返回的原始路径。技能目录不是项目目录。如果有一个工具拒绝一个有效的路径，请尝试使用另一个可用的读取器/编辑器；不要要求用户提供你可以发现的路径。 |
| 用户要求将更改应用于提供的文件：“修复我的项目/文件”、“请更新此源代码”、“进行更改”或“然后构建和运行” | 编辑每个受影响的实例。针对实际包版本运行最窄的有意义的构建/测试命令；技能激活不是停止建议的理由。 |
| 用户询问“我应该期待什么？”、“我该如何修复这些更改？”、兼容性建议或计划 | 直接从实际项目状态回答，即使源代码可见。保持单个症状的答案集中；仅包含改变决策的相邻风险。 |
| 全部迁移中的不支持的 TFM | 首先更新 TFM，然后更新 MSTest 包，然后修复源代码中断。不要将此顺序隐藏在发布说明清单中。 |
| 自定义 `TestMethodAttribute` 子类 | 将 `ExecuteAsync`、调用信息传播、显示名称处理和子类的重试/结果语义视为一个耦合迁移。修复实际的类，而不是占位符示例。 |
| `MSTest.Sdk` v4 源/API 错误 (`ManagedType`、`TestTimeout`、`Contains`) | 提供确切的源替换，然后添加相邻的运行器警告：MTP 模式不再提供 `Microsoft.NET.Test.Sdk`；仅在 VSTest 发现仍然需要时才添加它。 |
| `MSTest.Sdk` v4 加 `vstest.console` | 这是一个 v4 的变化：MTP 模式不再引入 `Microsoft.NET.Test.Sdk`。保留 MTP 并为过渡性 VSTest 发现添加该包，选择 `UseVSTest`，或将 CI 切换到 `dotnet test`；说明该选择保留了哪个运行器。 |

## 响应指南

- **始终首先识别当前版本**：在推荐任何迁移步骤之前，明确声明项目中检测到的 MSTest 版本（例如，“您的项目使用 MSTest v3 (3.8.0)”）。这确认了你已阅读项目文件，并使迁移建议有依据。
- **解决目标版本，而不是假设**：当用户询问“最新”时，查询项目的配置包源并选择执行时可用最新的 MSTest v4 稳定版本。永远不要在没有检查的情况下将此技能的示例版本复制到结果中。保持所有 MSTest 包在相同的解析版本上。
- **专注修复请求**（用户在升级后具有特定的编译错误）：仅解决来自步骤 3 的相关破坏性更改。仅在请求的交付品是源代码更改时才进行编辑；“我该如何修复这些？”仍然是一个答案请求。**始终提供具体的修复代码**，使用用户的实际类型和方法名称。如果固定装置仍然引用 v3，则不要声称绿色的 v3 构建验证了 v4 兼容性；要么在请求时更新包，要么声明验证边界。对于自定义 `TestMethodAttribute` 子类，显示包括调用信息传播到基本构造函数的完整修复类。提及任何可能在此之前捕获此问题的相关分析器（例如，MSTEST0006）。如果项目使用 `MSTest.Sdk`，还说明 v4 MTP 模式不再提供 `Microsoft.NET.Test.Sdk` 以及这是否影响可见的运行器。不要逐步介绍整个迁移工作流程。
- **“应该期待什么？”问题**（用户在升级前询问关于破坏性更改）：展示来自步骤 3 快速查找表的**所有主要破坏性更改**——而不仅仅是当前代码中可见的更改。对于每个更改，提供一个单行修复摘要。还提及来自步骤 4 的关键行为变化（尤其是 TestCase.Id 历史影响和 TreatDiscoveryWarningsAsErrors 默认值）。如果项目代码可用，请突出显示哪些更改直接适用。
- **完整迁移请求**（用户希望完整迁移）：遵循下面完整的迁移工作流程。
- **行为/运行时症状报告**（用户描述了测试执行差异而没有构建错误）：将描述的症状与步骤 4 中的行为变化表进行匹配。提供有针对性的、针对症状的建议。提及用户应警惕的其他行为变化。除非用户也有构建错误，否则不要逐步介绍源破坏性更改。
- **CI/测试发现问题**（测试未被发现、`vstest.console` 停止工作、升级后 CI 管道失败）：专注于 4.5（MSTest.Sdk v4 不再在其默认 MTP 模式下包含 `Microsoft.NET.Test.Sdk`——它仍然需要用于 vstest.console）和 4.4（TreatDiscoveryWarningsAsErrors）。清楚地解释根本原因，并给出所有三个路径：在保留 MTP 的同时添加 `Microsoft.NET.Test.Sdk`，将 `UseVSTest` 设置为切换项目运行器，或将 CI 切换到 MTP 本地 `dotnet test`。不要逐步介绍完整迁移工作流程。
- **解释性问题**（用户询问“这是一个已知更改吗？”、“我还需要注意什么？”）：解释相关更改并提出建议。提及用户可能接下来会遇到的相关更改。不要规定完整的迁移程序。
- **结果证明**：在实施工作结束时，提供检测到的 v3 版本、解析的 v4 版本、运行器选择、更改的文件以及实际的构建/测试计数。永远不要报告推断的构建、VSTest 兼容性、发现或通过测试。
