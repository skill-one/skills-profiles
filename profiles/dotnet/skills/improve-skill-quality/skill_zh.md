# 提升技能质量

将一个失败或不令人信服的评估转化为有针对性的修复。这个仓库中最常见的错误是针对一个真正原因是评估、测试用例或测试框架的裁决而重写技能文本。先分类，再修复。

## 何时使用

- 评估裁决是回归、功能不足或"没有可信的改进"。
- 技能在独立测试中获胜但在插件测试中未获胜，或报告"未激活"。
- `/evaluate` 报告"评估运行但未产生结果"。
- 技能得分良好但成本过高（token、回合数、墙时间、插件菜单预算）。
- 决定是否加强或淘汰一个持续表现不佳的技能。

## 何时不用

- 从头创建新技能 — 使用 `create-skill`。
- 从头创建新的 `eval.yaml` — 使用 `create-skill-test`。
- 修改测试框架本身（`eng/skill-validator`、`eng/vally-adapter`、`evaluation*.yml`）。

## 输入

| 输入 | 必填 | 描述 |
|-------|----------|-------------|
| 裁决证据 | 是 | `/evaluate` PR 评论，或运行工件中的 `results.json` |
| 失败测试的文本记录 | 对于内容修复是 | 基线输出与技能输出对比，以及裁判陈述的理由 |
| 刺激-投票 W/T/L 和重复运行 W/T/L | 是 | 将跨任务证据与可靠性分离 |
| 每个分支的激活状态 | 是 | 独立分支和插件分支的激活是不同的失败 |

## 工作流程

### 第 1 步：在形成假设之前获取证据

阅读 [InvestigatingResults.md](../../../eng/vally-adapter/InvestigatingResults.md) 了解如何下载工件和读取 `results.json`。针对每个失败的刺激提取：

- 权威的刺激-投票 W/T/L 和单独的重复运行 W/T/L
- 在**独立**和**插件**分支中的激活状态，分别
- 每个失败测试中裁判的逐字理由
- 是否有测试出错、超时或产生空输出

在能够引用一个失败测试及其裁判理由之前，不要更改技能内容。对于其他原因类别，证据是不同的：测试框架故障从作业日志和规范中诊断，功能问题从测试记录中诊断 — 两者都没有失败测试可供引用，要求一个失败测试会导致人们重写文本。

### 第 2 步：分类失败原因

按此表格向下查找，并在第一个匹配的行停止。行按症状被误诊为技能内容问题的频率排序 — 测试用例行排在首位，因为测试用例故障也表现为设置或可靠性故障，并被错误地归入此类。

| 症状 | 真正原因类别 | 前往 |
|---------|------------------|-------|
| 一个测试用例无法构建、未被 git 跟踪、以错误原因失败或自相矛盾 | 测试用例 | 第 4 步 |
| 没有 `results.json`、"未产生结果"或规范从未加载 | 测试框架 / 规范加载 | 第 3 步 |
| 测试出错、超时或返回空输出 | 可靠性 | 第 3 步 |
| 轨迹不匹配、一个测试出错或摘要不一致 — 裁决报告为"未决" | 可靠性（非功能不足） | 第 3 步 |
| 正面记录（例如 16W/8T/1L）、比较结果确定，但裁决仍未通过 | 统计功能不足 | 第 5 步 |
| 技能分支与基线分支按构造相等 | 评估设计 | 第 6 步 |
| 激活且在质量上失败，裁判指出了一个具体缺陷 | 技能内容 | 第 7 步 |
| 独立分支激活，插件分支未激活 | 激活 / 路由 | 第 8 步 |
| 两个分支均未激活 | 前置字段描述 | 第 8 步 |
| 获胜但成本远高于基线 | 范围和成本 | 第 7 步 |

当比较结果确定时，裁决才是一个*测量*结果：`adapt.mjs` 要求在报告通过或回归之前，没有出错的测试、没有不匹配的轨迹，并且摘要一致。在将其读作功能不足问题之前，请确认这一点。

### 第 3 步：排除测试框架和可靠性原因

参见 [references/eval-triage.md](references/eval-triage.md) 获取完整目录。常见的有：

- 声明 `config:` 和 `defaults:` 的规范被 vally 拒绝，作业仍然退出 0，PR 评论指责"瞬态基础设施"。将它们合并为一个 `defaults:` 块。
- 出错的测试不一定是测试用例问题 — 裁判端认证和 `session.idle` 故障从裁决中看起来相同，需要测试框架修复，而不是 SDK 固定。
- `expect_tools: [bash]` 在建议性问题上强制恢复或构建，并将答案变成超时，没有质量提升。
- 真实的代码生成刺激需要大约 360 秒；超时产生空输出，这会失败所有评分器并隐藏真实质量信号。
- 不匹配的轨迹、一个出错的测试或一个不一致的摘要使比较**未决**：剩余匹配的测试有偏差，因此记录不是测量的零，不能读作功能不足或内容问题。

### 第 4 步：在触摸技能之前验证测试用例

运行 `python eng/eval-quality/check_eval_quality.py` — 它会阻塞 11 种可能导致真实结果缺陷的类别。然后手动确认：

- 每个测试用例的行为与其刺激假设一致 — 意图健康的测试用例构建，意图失败的测试用例按刺激指定的确切原因失败，而不是其他原因；
- 每个引用的测试用例都在 git 索引中（`git ls-files`），而不仅仅是在磁盘上 — `.gitignore` 已默默吞噬了提交的覆盖测试用例；
- 一个测试用例永远不会在两个地方声明相互矛盾的事实 — 一个声明 `line-rate`、摘要总计和 `<line>` 元素不同的 Cobertura 报告是典型的案例 — 或者两个分支确实读取了不同的真相。

### 第 5 步：检查评估是否可能通过

门有两个独立的门槛，混淆它们是常见的误诊：

1. **不同的刺激 ≥ 5。** 低于这个值的裁决报告为 `underpowered` — 永远不会通过，永远不会是回归。
2. **符号检验必须在*不一致*（非平局）刺激投票上达到 p ≤ 0.05。** 平局不会被默默丢弃；它们会降低不一致计数。

| 不一致刺激投票 | 通过的记录 | p |
|---:|---|---:|
| ≤ 4 | 无，无论技能有多好 | ≥ 0.0625 |
| 5–7 | 仅零损失（5W/0L） | 0.031 |
| 8 | 可存活一个损失（7W/1L） | 0.035 |

因此，在恰好 5 个刺激时，一个平局是致命的 — 它会留下 4 个不一致。在 6 个刺激时
一个平局是可存活的（5W/1T/0L）；在 7 个，最多两个（5W/2T/0L）。损失不是。

因此，一个正面记录但裁决失败的记录是功能不足问题，而不是内容问题。通过添加**区分性刺激**来修复它。提高 `runs` 衡量同一任务的可靠性，无法清除底线。

### 第 6 步：检查两个分支是否完全不同

一个比较技能与其自身的评估测量裁判噪音：

- 一个休眠保护 (`expect_activation: false`) 必须**不**也设置 `constraints.reject_skills`。
  这会使技能分支无技能，因此激活合同无法观察劫持。
  版本 4 的模式保留了相同的分支比较用于诊断，但将其排除在偏好推断之外；意外的独立激活仍然会阻止通过。
- 一个 `disable-model-invocation: true` 的技能在面向模型的技能分支中不存在，因此其直接评估比较两个相同的分支，无论评分器是否检查激活或答案内容。通过消费者结果来覆盖它；例如，`filter-syntax` 通过 `run-tests` 和 `mtp-hot-reload` 覆盖。
- 一个 `config` 缺少其必需键的评分器什么也不执行，因此刺激比它看起来少一个断言。

### 第 7 步：针对失败测试修复技能内容

现在更改技能。应用 [references/writing-for-baseline-delta.md](references/writing-for-baseline-delta.md) 中的模式；最常翻转损失的模式：

- 用模型已经知道的参考文本替换决策，否则模型会做错。
- 添加停止条件，以防止强技能过度应用 — 但不要过度纠正，以至于回答比基线更狭窄。
- 按输入大小调整输出结构；一个仪表板对于一个 8 测试套件输给直接答案。
- 要求真实的验证报告；在失败恢复后声称"构建成功"是一个自动损失。
- 通过编译或探测验证承重 API 声明，而不是通过阅读源代码。
- 对于成本回归，将罕见或昂贵的路径置于 `references/` 读取之后，并将任何编排调整为用户的范围。

### 第 8 步：修复激活

激活失败是前置字段和路由失败，不是主体失败。参见 [references/eval-triage.md](references/eval-triage.md)。总结：

| 失败 | 修复 |
|---------|-----|
| 任何分支未激活 | 将用户自己的话放入 `description`：症状、错误代码、工件名称、引用的请求 |
| 一个兄弟技能赢得了提示 | 在 `description` 中声明确切的不明确词语，并在**两个**兄弟技能上添加匹配的排除项 |
| 模型完全没有任何技能回答 | 在描述中提高赌注，减少插件菜单的拥挤，通过插件分支验证 |
| 边界排除了真实场景 | 重新阅读每个"不用于"条款，与每个评估提示和真实工作流程阶段相对比 |
| 描述在 1,024 字符上限 | 切割重述的主体内容，而不是触发短语；检查插件菜单预算 |

### 第 9 步：重新验证

```bash
dotnet run --project eng/skill-validator/src/SkillValidator.csproj -- check --plugin ./plugins/<plugin>
python eng/eval-quality/check_eval_quality.py
./eng/run-skill-evals.sh <plugin> <skill>
```

然后通过提交一个包含 `/evaluate`（已更改文件 → 审查更改）的 PR 审查来请求官方运行，这会将运行绑定到已审查的提交。在根据结果声明回归之前，请确认技能有效负载确实发生了变化 — 在字节相同的 内容上重新运行已将 7W/2T/2L 变为 4W/5T/2L。

## 验证

- [ ] 对于内容修复，PR 描述中引用了失败测试和裁判的陈述理由。
- [ ] 在编辑任何内容之前对失败进行了分类。
- [ ] `check_eval_quality.py` 和 `skill-validator check` 都通过。
- [ ] 不同的刺激计数清除了目标效果和观察到的平局率的功能不足门槛。
- [ ] 独立**和**插件激活都报告。
- [ ] PR 正文记录了根本原因、修复和验证，以便经验教训可重用。

## 常见陷阱

| 陷阱 | 解决方案 |
|---------|----------|
| 响应功能不足的裁决重写技能文本 | 功能不足意味着不同的刺激太少；添加区分性刺激 |
| 在已经具有 `config:` 的规范中添加 `defaults: runs:` | 合并到一个 `defaults:` 块；vally 拒绝具有两者的规范 |
| 填充 `runs` 以清除刺激底线 | 重复测量一个任务的可靠性；添加刺激 |
| 将出错的测试视为测试用例非确定性 | 首先读取 stderr；裁判端认证故障需要测试框架修复 |
| 修复一个"错误"答案，而测试用例实际上使其错误 | 在归咎于响应之前检查测试用例自洽性 |
| 加强一个无人使用且什么也不通过的技能 | 弱评估信号加上薄弱的遥测是有效的退役案例 |
| 没有重新运行就落地修复 | 验证调用的有效负载是否包含修复；裁判噪音是真实的 |
