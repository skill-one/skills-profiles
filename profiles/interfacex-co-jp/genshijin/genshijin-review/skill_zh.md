评论内容应简洁且可操作。一行一条意见。位置、问题、修正。禁止前置。

## 规则

**格式:** `L<line>: <问题>。<修正>。` — 多文件时 `<file>:L<line>: ...`

**严重度前缀（混合时）:**
- 🔴 `bug:` — 已损坏。直接关联事件
- 🟡 `risk:` — 能运行但脆弱（race, null未检查, 握挤error）
- 🔵 `nit:` — 风格、命名、微观优化。可无视作者
- ❓ `question:` — 纯粹疑问。非建议

**删除:**
- 「注意到〜」「看起来像〜」「建议考虑〜」
- 「只是建议但是」→ 使用 `nit:`
- 「很棒的工作」「总体看起来不错」— 开头一次，无需单独评论
- 行操作说明 — diff 就能明白
- 模糊（「可能」「大概」「〜我认为」）— 不确定则 `question:`

**保留:**
- 准确行号
- 符号、函数名、变量名用反引号
- 具体修正（禁止「重构考虑」）
- 问题文中的非自明「为什么」

## 示例

❌ 「L42 看起来没有检查 user 对象是否为 null 就访问 email 属性。如果 DB 中找不到 user 可能会崩溃。建议添加 null 检查。」

✅ `L42: 🔴 bug: .find() 后 user 可能为 null。.email 前添加 guard。`

❌ 「这个函数做了很多事，分成小函数会更容易读。」

✅ `L88-140: 🔵 nit: 50行函数4职责。抽取 validate/normalize/persist。`

❌ 「API 返回 429 时考虑了吗？应该处理。」

✅ `L23: 🟡 risk: 429 无重试。用 withBackoff(3) 包裹。`

## 自动明确化

以下用普通段落描述，非简洁模式：
- 安全性意见（CVE 级需附带 URL 和充分说明）
- 架构异议（需有依据，单行不足以说明）
- 新人入职背景（需要「为什么」）

意见后立即恢复。

## 边界

- 仅评论。禁止代码修正、approve/request-changes、linter 执行
- 输出为 PR 可贴附格式
- 「原始人评论禁止」「通常模式」可解除
