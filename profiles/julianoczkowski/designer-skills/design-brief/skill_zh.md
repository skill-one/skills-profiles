这项技能通过结构化对话创建设计简报。如果某些步骤不必要，您可以跳过它们。

## 示例提示

- "为引导流程撰写简报"
- "在开始构建之前，我需要规划一个设置页面"
- "帮助我定义营销落地页的方向"
- "为这个显示项目健康指标的面板撰写简报"

## 流程

1. 向用户询问他们想要构建的详细描述，包括目标用户、任何已有的约束或想法。

2. 探索现有的代码库以了解当前状态。特别扫描以下内容：
   - **CSS变量/符号**：名为`tokens.css`、`variables.css`、`theme.css`的文件，或带有自定义属性的`:root`声明
   - **Tailwind配置**：`tailwind.config.js`或`tailwind.config.ts`，检查`theme.extend`中的自定义值
   - **UI框架主题**：Material UI的`createTheme`，Chakra的`extendTheme`，shadcn的`globals.css`和`components.json`
   - **组件目录**：`components/`、`ui/`、`shared/`或包含可重用UI元素的任何文件夹
   - **Storybook**：`.storybook/`目录或`*.stories.*`文件指示已记录的组件库
   - **设计符号文件**：JSON符号文件（Style Dictionary格式，Figma符号导出）
   - **package.json UI依赖项**：tailwindcss、@mui/material、@chakra-ui/react、@radix-ui、lucide-react、framer-motion等
   - **字体加载**：HTML中的Google Fonts链接、`@font-face`声明、CSS/配置中的字体导入
   - **现有页面/布局**：路由文件、布局组件、页面模板显示已建立的模式
   - 如果组件存在，将它们视为起始词汇。简报应扩展，而不是替换。

3. 对用户进行无休止的访谈，了解设计的各个方面，直到达成共识。沿着设计的每个分支，逐一解决决策之间的依赖关系。对于每个问题，提供您的建议答案。

   至少涵盖：
   - 主要用户的目标任务（JTBD）是谁，他们试图完成什么？
   - 这个界面的成功标准是什么？
   - 情感基调是什么？（平静、紧急、俏皮、权威、温暖、临床）
   - 这个产品应该像哪些现有的产品、网站或风格？它不应该像什么？
   - 硬性约束是什么？（设备、无障碍要求、性能预算、品牌指南）
   - 这个界面将包含哪些内容？占位符与真实内容的区别是什么？

4. 一旦完全理解，使用以下模板编写简报。

## 文件输出

将简报保存到`.design/<功能缩写>/DESIGN_BRIEF.md`，其中`<功能缩写>`是来自要设计的功能或页面的简短、小写、连字符名称（例如，`onboarding-flow`、`settings-page`、`project-dashboard`）。

此文件夹结构确保多次为不同功能运行设计流程时不会覆盖之前的工作。所有后续技能（信息架构、设计符号、简报到任务、设计评审）都将从此同一子文件夹读取和写入。

示例：

```
.design/
├── onboarding-flow/
│   └── DESIGN_BRIEF.md
└── settings-page/
    └── DESIGN_BRIEF.md
```

## 简报模板

```markdown
# 设计简报：[功能/页面名称]

## 问题

用户面临的问题是什么，从他们的角度描述。不是技术性的。不是商业指标。是人类的摩擦。

## 解决方案

这个界面如何解决这个问题，描述为体验，而不是功能列表。

## 体验原则

最多三个指导每个设计决策的原则。每个原则应解决一种张力。
示例："渐进式披露胜过 upfront 复杂性" 或 "自信胜过速度。"

1. [原则] -- [这意味着在实践中是什么]
2. [原则] -- [这意味着在实践中是什么]
3. [原则] -- [这意味着在实践中是什么]

## 美学方向

- **哲学**：[命名的哲学或描述性的氛围。参见 /frontend-design 技能获取参考。]
- **基调**：[情绪基调]
- **参考点**：[这个产品应该像哪些现有的产品、网站或风格]
- **反参考点**：[这个产品不应该像什么]

## 现有模式

代码库中已经存在的组件、符号和约定，这个设计必须尊重或扩展。

- 字体：[当前使用的字体]
- 颜色：[当前调色板/变量]
- 间距：[当前比例]
- 组件：[将被重用或扩展的现有组件]

## 组件清单

这个功能需要的 UI 组件列表。对于每个组件，注明其是否存在、需要修改还是新创建。

| 组件 | 状态                | 备注    |
| --------- | --------------------- | -------- |
| [名称]    | 存在 / 修改 / 新建 | [详情] |

## 关键交互

关键交互模式。描述用户做什么以及界面如何响应。关注状态变化、过渡和反馈。

## 响应式行为

布局如何跨断点适应。注意任何在移动设备上改变行为（不仅仅是大小）的组件。

## 无障碍要求

这个界面最低要求。包括对比度比例、键盘导航、屏幕阅读器考虑和焦点管理。

## 不在范围内

这个简报明确不涵盖的内容。要具体。这可以防止在构建过程中出现范围蔓延。
```
