这项技能会对已构建的内容进行结构化设计评审，对照设计简报和选择的美学理念进行衡量。

> **关键 — 视觉截图捕获**
>
> 你必须在每次设计评审中捕获运行应用程序的截图。单独的代码评审是不够的——你需要看到用户所看到的内容。遵循下面第 3 步中的截图捕获协议。这不是可选的。

## 示例提示

- "评审我刚刚构建的内容"
- "对登录页面进行设计评论"
- "对照简报进行检查"
- "这是截图。看起来怎么样？" [粘贴截图]
- "在发布前进行质量保证通过"

## 流程

1. **阅读简报。** 查找活动功能的简报，位于 `.design/<功能缩写>/DESIGN_BRIEF.md`。如果 `.design/` 下存在多个功能文件夹，请询问用户要评审哪个功能。如果不存在 `.design/` 文件夹，则回退到项目根目录中的 `DESIGN_BRIEF.md`。如果都不存在，请询问用户预期的设计方向是什么。

2. **探索已构建的代码。** 检查所有创建或修改的组件、页面和样式文件。特别扫描以下内容：
   - 所有新修改的组件及其与现有组件的关系
   - Token/变量使用：组件是否使用共享 Token 或硬编码值？
   - 重复组件应合并
   - 文件命名和组织：新文件是否遵循项目的规范？
   - 了解实际构建的内容，而不是计划的内容。

3. **捕获运行应用程序的截图。**

   这一步是**强制性的**。不要跳过它。不要仅依赖用户提供的截图。

   ### 截图工具优先级

   按顺序尝试每个选项。使用第一个可用的工具：
   1. **Playwright MCP（首选）。** 检查 `plugin-playwright-playwright` MCP 服务器是否可用。如果可用，使用它——它提供了对视口大小、全页捕获和文件命名的精确控制。
   2. **Cursor IDE 浏览器（次选）。** 如果 Playwright MCP 不可用，使用 `cursor-ide-browser` MCP 服务器的 `browser_take_screenshot` 工具。它具有相同的核心功能。
   3. **询问用户（最后手段）。** 如果既没有 MCP 服务器也没有应用内浏览器可用，你必须要求用户手动提供截图。具体说明你需要什么：
      - "我没有访问浏览器工具。为了完成视觉评审，我需要运行应用程序的截图。请提供："
      - 在**桌面**宽度（1280px）下的全页截图
      - 在**平板**宽度（768px）下的全页截图
      - 在**移动**宽度（375px）下的全页截图
      - 深色模式变体（如果适用）
      - 任何需要评审的特定组件或交互状态
      - 要求用户直接在聊天中粘贴/附加图像，或将其保存到 `screenshots/` 文件夹中。
      - **不要跳过视觉评审。** 等待用户提供截图后再继续执行清单。

   ### 截图保存位置

   所有截图必须保存到功能 `.design/` 目录内的 `screenshots/` 子文件夹中——与 `DESIGN_BRIEF.md` 和其他设计流程文件相同的文件夹。

   路径模式：`.design/<功能缩写>/screenshots/`

   如果简报位于 `.design/onboarding-flow/DESIGN_BRIEF.md`，截图保存到 `.design/onboarding-flow/screenshots/`。如果不存在，则创建该文件夹。

   如果不存在 `.design/` 文件夹（遗留项目或独立评审），则回退到项目根目录中的 `screenshots/` 文件夹。

   使用描述性文件名编码捕获的内容：

   ```
   .design/
   └── onboarding-flow/
       ├── DESIGN_BRIEF.md
       ├── DESIGN_REVIEW.md
       └── screenshots/
           ├── review-homepage-desktop-1280.png
           ├── review-homepage-tablet-768.png
           ├── review-homepage-mobile-375.png
           ├── review-homepage-dark-mode-desktop-1280.png
           └── review-card-component-hover.png
   ```

   ### 截图捕获协议

   **a. 导航到应用程序。** 如果项目不明确（例如 `http://localhost:3000`），请询问用户 URL。使用 `browser_navigate` 打开它。

   **b. 捕获响应式断点。** 至少捕获每个关键页面/视图的以下三个视口：

   | 断点 | 宽度 × 高度 | 文件名后缀 |
   | ---- | ---------- | ---------- |
   | 移动 | 375 × 812   | `-mobile-375` |
   | 平板 | 768 × 1024  | `-tablet-768` |
   | 桌面 | 1280 × 800  | `-desktop-1280` |

   使用 `browser_resize` 在每次截图前设置视口。使用 `browser_take_screenshot` 并设置 `fullPage: true` 来捕获整个可滚动的页面，并使用 `filename` 参数指向 `screenshots/` 文件夹。

   **Playwright MCP 示例序列**（假设功能缩写是 `onboarding-flow`）：

   ```
   1. browser_navigate → { url: "http://localhost:3000" }
   2. browser_resize   → { width: 1280, height: 800 }
   3. browser_take_screenshot → { type: "png", filename: ".design/onboarding-flow/screenshots/review-homepage-desktop-1280.png", fullPage: true }
   4. browser_resize   → { width: 768, height: 1024 }
   5. browser_take_screenshot → { type: "png", filename: ".design/onboarding-flow/screenshots/review-homepage-tablet-768.png", fullPage: true }
   6. browser_resize   → { width: 375, height: 812 }
   7. browser_take_screenshot → { type: "png", filename: ".design/onboarding-flow/screenshots/review-homepage-mobile-375.png", fullPage: true }
   ```

   **c. 捕获交互状态（当相关时）。**
   - 按钮、卡片、链接上的悬停状态
   - 表单字段的焦点状态
   - 下拉菜单、模态框、菜单的打开状态
   - 表单的错误/成功状态
   - 加载和空状态

   **d. 捕获深色模式（如果项目支持）。** 切换深色模式并重复响应式断点捕获，文件名中包含 `-dark-mode`。

   **e. 捕获特定组件。** 如果评审专注于特定组件，使用 `element` 和 `ref` 参数仅捕获该元素。

   ### 分析每个截图

   捕获后，对照设计简报对每个截图进行视觉分析。对于每个截图：
   - 与简报的美学方向进行比较
   - 检查视觉层次：最重要的元素是否最突出？
   - 检查间距一致性：边距和填充是否均匀且有意？
   - 检查颜色：调色板是否与简报的方向一致？
   - 检查排版：字体大小、粗细和间距是否视觉正确？
   - 检查响应式适应：布局是否正确重组（不仅仅是缩小）？
   - 注意代码评审单独会遗漏的渲染问题（字体加载失败、损坏的图像、布局溢出、z-index 问题、不正确的 border-radius、颜色不匹配）

   在评审输出中引用特定截图的文件名，以便发现结果可追溯。

4. **运行以下评审清单。** 对于每个类别，记录通过和需要改进的内容。要具体。引用确切的组件、文件、行号和截图文件名。

5. **生成优先级改进列表。** 按严重程度分组问题：
   - **必须修复**：损坏的功能、无障碍访问失败、与简报的主要偏差。
   - **应该修复**：不一致性、缺失状态、响应式问题。
   - **可以改进**：抛光、动画改进、排版微调。

6. 将评审保存为 `DESIGN_REVIEW.md`，位于功能的 `.design/<功能缩写>/` 文件夹内（与 `DESIGN_BRIEF.md` 相邻）。如果不存在 `.design/` 文件夹，则保存到项目根目录。包括一个“已捕获截图”部分，列出所有捕获的截图及其路径。如果用户更喜欢，直接呈现评审。

## 评审清单

### 视觉层次

- 每个页面/视图上最重要的内容是否最视觉突出？
- 类型比例是否创建清晰的重要性级别（标题、副标题、正文、说明文字）？
- 交互元素（按钮、链接、输入）是否有足够的视觉重量，无需寻找？
- 是否有清晰的阅读顺序？你能追踪眼睛首先、其次、第三去哪里吗？

### 一致性

- 间距值是否一致？检查填充和边距与已建立的规模（4px/8px 基础或项目使用的任何其他规模）。
- 颜色是否使用一致？确保相同的语义含义始终映射到相同的颜色（主要操作、错误、成功状态、禁用状态）。
- 边框半径、阴影值和字体大小是否从共享集中重用，还是有临时的值？
- 相似的组件是否看起来和行为相似？（例如，所有卡片、所有表单字段、同一类别的所有按钮。）

### 美学保真度

- 实现是否与简报中命名的哲学相匹配？
- 有人看到这个时会立即认出预期的美学方向吗？
- 是否有打破美学的元素（一个通用组件在一个 otherwise 独特的界面中、一个冲突的字体、一个不合适的颜色）？
- 细节级别是否与哲学相匹配？（极简主义设计不应有不必要的装饰。极繁主义设计不应有空、未完成区域。）

### 组件质量

- 代码库中的现有组件是否正确显示，还是被重新实现了？
- 新组件是否遵循与现有组件相同的 API 模式（props、命名、文件组织）？
- 是否有重复组件应合并？

### 状态和交互

- 交互元素是否具有所有必要的状态：默认、悬停、焦点、活动、禁用？
- 表单字段是否具有状态：空、填充、错误、成功、禁用？
- 是否处理加载状态？空状态？
- 过渡和动画是否与哲学的运动指南相匹配？
- 是否对每个用户操作都有视觉反馈？

### 响应式行为

- 布局是否在移动（375px）、平板（768px）和桌面（1280px+）上工作？
- 组件是否适当适应？（不仅仅是缩小，而是重新组织。）
- 移动上的触摸目标大小是否足够（最小 44x44px）？
- 文本是否在所有断点上都可读？没有太小或太宽的文本（最大 65-75 个字符）。

### 无障碍访问

- 颜色对比度：文本/背景组合是否满足 WCAG AA（正文 4.5:1，大文本 3:1）？
- 键盘导航：是否每个交互元素都可以仅通过键盘访问和激活？
- 焦点指示器：焦点环是否可见且样式一致？
- 语义 HTML：标题是否按顺序排列？是否使用地标（main、nav、header、footer）？表单标签是否关联？
- 屏幕阅读器：图像是否有替代文本？图标是否有标签？装饰性元素是否对辅助技术隐藏？
- 运动：是否有为需要它的用户提供的减少运动媒体查询？

### 排版

- 字体是否实际加载？（检查 FOIT/FOUT 闪烁。）
- 行长度是否适合阅读（正文 45-75 个字符）？
- 行高是否适当（正文 1.4-1.6，标题更紧）？
- 类型比例是否有意，还是大小是任意的？

### 深色模式

- 如果项目有深色模式 Token，是否正确应用？
- 所有颜色值是否使用 CSS 变量（而不是不会切换的硬编码十六进制值）？
- 深色调色板是否感觉有意，还是只是一个简单反转？
- 阴影是否为深色模式调整（更暗、更透明）？
- 重点颜色是否在深色背景下保持足够的对比度？
- 是否有工作切换机制或 `prefers-color-scheme` 支持？

### 移动优先

- 布局是否移动优先构建（使用 `min-width` 媒体查询，而不是 `max-width`）？
- 移动布局是否在 375px 上工作，没有水平滚动？
- 导航是否为移动适配（不是溢出的桌面导航）？
- 触摸目标至少 44x44px？
- 移动上的正文至少 16px？
