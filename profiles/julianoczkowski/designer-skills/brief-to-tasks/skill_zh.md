这项技能能够将设计简报转化为有序的、可构建的任务列表。每个任务都是一个垂直切片：一个可以独立构建、审查和验证的 UI 片段。

## 示例提示

- "将简报分解为任务"
- "我应该先构建什么？"
- "从设计简报创建任务列表"
- "规划此功能的构建顺序"

## 流程

1. 读取设计简报。查找 `.design/*/DESIGN_BRIEF.md`。如果存在多个子文件夹，则使用最新修改的子文件夹，或询问用户他们正在处理哪个功能。同时检查 `INFORMATION_ARCHITECTURE.md` 和同一子文件夹中的 token 文件。如果都不存在，则询问用户他们正在构建什么。

2. 探索现有代码库以了解已经构建了什么。特别扫描：
   - **组件目录**：`components/`、`ui/`、`shared/`，并列出每个组件的名称
   - **现有页面/视图**：此功能必须与之共存已构建的内容
   - **Token/主题文件**：`tokens.css`、`globals.css`、Tailwind 配置、主题提供者
   - **文件命名规范**：kebab-case、PascalCase、文件如何组织（按功能、按类型）
   - **测试文件**：如果组件旁边存在测试，新任务应包含测试预期
   - **package.json 依赖项**：已安装的 UI 库、动画库和图标集
   - 将每个相关组件分类为：将按原样重用、需要修改或尚未存在。只有需要修改或创建的组件会获得自己的任务。

3. 将工作分解为垂直切片。每个任务应：
   - 可独立构建（除非特别说明，否则一个任务不应阻塞另一个任务）。
   - 包含结构、样式和交互（不能是“构建 HTML”然后“添加 CSS”然后“添加 JS”作为单独的任务）。
   - 可验证：可以查看结果并确认其与简报匹配。
   - 足够小，可以在单次会话中完成。

4. 按以下顺序排列任务：
   - **依赖项优先**：基础元素（token、布局外壳、共享组件）优先于特定页面的工作。
   - **视觉优先级**：将最突出的 UI 元素放在前面，以便用户可以在投入细节之前验证美学方向。
   - **风险优先**：将最困难或最不确定的部分放在前面，以便在围绕它们构建其他内容之前暴露问题。

5. 将任务列表保存为 `TASKS.md`，保存在与设计简报相同的 `.design/<feature-slug>/` 子文件夹中。

## 任务列表模板

```markdown
# 构建任务：[功能/页面名称]

生成自：.design/<feature-slug>/DESIGN_BRIEF.md
日期：[日期]

## 基础
- [ ] **[任务名称]**：[用一句话描述要构建的内容和“完成”的状态]。 _重用：[如果有的话，现有组件/token]。_
- [ ] **[任务名称]**：[描述]。 _新组件。_

## 核心UI
- [ ] **[任务名称]**：[描述]。 _依赖：[如果有的话，任务名称]。_
- [ ] **[任务名称]**：[描述]。

## 交互与状态
- [ ] **[任务名称]**：[描述]。覆盖：[状态列表，例如，悬停、加载、错误、空]。
- [ ] **[任务名称]**：[描述]。

## 响应式与润色
- [ ] **[任务名称]**：[描述]。断点：[哪些断点]。
- [ ] **[任务名称]**：无障碍性检查。 [简报中的具体检查]。

## 审查
- [ ] **设计审查**：对简报运行 /design-review。
```

## 规则

- 每个任务必须参考它是否重用、修改或创建组件。
- 不要创建一个仅“设置项目”或“创建文件结构”的任务。这些不是垂直切片。
- 如果简报指定了美学理念，请在第一个构建任务中注明，以便立即建立视觉方向。
- 将相关任务分组，但不要超过一个级别的嵌套。扁平列表更容易处理。
