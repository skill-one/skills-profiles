# 系统文献综述技能

## 概述

该技能能够针对某一研究主题，在多篇学术论文中生成结构化的**系统文献综述 (SLR)**。给定一个主题查询，它会搜索 arXiv，并行地从每篇论文中提取结构化元数据（研究问题、方法论、关键发现、局限性），并在整个集合中综合主题，最终输出一份具有一致引用的报告。

**与 `学术论文综述` 的区别**：该技能对单篇论文进行深度同行评审。而本技能在多篇论文中进行广度优先综合。如果用户给您一个论文 URL 并要求“评审这篇论文”，请转接到 `academic-paper-review`。

## 何时使用此技能

当用户需要以下任何一项时，请使用此技能：

- 主题的文献综述（“调查 transformer 注意力变体”，“评审扩散模型的文献”）
- 多篇论文的综合（“最近关于 X 的论文有哪些发现”，“比较 Y 论文的方法论”）
- 具有一致引用格式的系统综述（“使用 APA 格式对 Z 进行 SLR”）
- 主题的注释文献目录
- 某一领域在特定时间窗口内的研究趋势概述

**不使用此技能的情况**：

- 用户只提供一篇论文并要求评审（使用 `academic-paper-review`）
- 用户提出一个不需要综合多个来源的事实性问题（直接回答）
- 用户需要一般性网络研究而不需要学术严谨性（使用标准网络搜索）

## 工作流程

工作流程分为五个阶段。请按顺序执行。

### 阶段 1：规划

在进行任何检索之前，请与用户确认以下内容。如果其中任何一项不明确，请提出**一个**涵盖缺失部分的问题。不要一次只问一个问题。

- **主题**：用普通英语描述的研究领域（例如“transformer 注意力变体”）。
- **范围**：多少篇论文（默认 20 篇，硬性上限 50 篇），可选时间窗口（例如“过去 2 年”），可选 arXiv 类别（例如 `cs.CL`，`cs.CV`）。
- **引用格式**：APA、IEEE 或 BibTeX（如果用户未指定且似乎没有为特定会议撰写，则默认为 APA）。
- **输出位置**：保存最终报告的位置（默认 `/mnt/user-data/outputs/`）。

如果用户说“50+ 篇论文”，请礼貌地将其限制在 50 篇，并解释超过该数量后综合质量会迅速下降——对于更大的综述，他们应该按子主题进行分割。

### 阶段 2：搜索 arXiv

调用捆绑的搜索脚本。**不要**尝试通过其他方式抓取 arXiv，也不要编写自己的 HTTP 客户端——该脚本正确处理 URL 编码、Atom XML 解析和 ID 规范化。

```bash
python /mnt/skills/public/systematic-literature-review/scripts/arxiv_search.py \
  "<topic>" \
  --max-results <N> \
  [--category <cat>] \
  [--sort-by relevance] \
  [--start-date YYYY-MM-DD] \
  [--end-date YYYY-MM-DD]
```

**重要提示——在搜索前提取 2-3 个核心关键词**。不要将用户的完整主题描述作为查询。在调用脚本之前，将主题精简为其 2-3 个最核心的术语。去掉限定词，如“在计算机视觉中”、“用于 NLP”、“变体”、“最近”——这些应该放在 `--category` 或 `--start-date` 中，而不是查询字符串中。

**查询短语——保持简短**。该脚本会将多词查询用双引号括起来进行短语匹配。这意味着：

- `"diffusion models"` → 搜索确切的短语 → 好，返回相关的论文。
- `"diffusion models in computer vision"` → 搜索这个确切的 5 词短语 → **太具体，很可能返回 0 结果**，因为很少论文包含这个确切的字符串。

使用**2-3 个核心关键词**作为查询，并使用 `--category` 来缩小领域，而不是将领域名称塞进查询中。示例：

| 用户说 | 好的查询 | 坏的查询 |
|---|---|---|
| "diffusion models in computer vision" | `"diffusion models" --category cs.CV` | `"diffusion models in computer vision"` |
| "transformer attention variants" | `"transformer attention"` | `"transformer attention variants in NLP"` |
| "graph neural networks for molecules" | `"graph neural networks" --category cs.LG` | `"graph neural networks for molecular property prediction"` |

该脚本将一个 JSON 数组打印到标准输出。每篇论文包含：`id`，`title`，`authors`，`abstract`，`published`，`updated`，`categories`，`pdf_url`，`abs_url`。

**排序策略**：

- **始终使用 `relevance` 排序**——arXiv 的 BM25 风格评分确保结果确实与用户的主题相关。`submittedDate` 排序返回该类别中最新的提交论文，无论主题相关性如何，这会产生大量不相关的结果。
- 当用户要求“最近”的论文或给出时间窗口时，使用 `--sort-by relevance` **结合 `--start-date`** 来限制时间范围，同时保持结果的相关性。例如，“最近的扩散模型论文” → `--sort-by relevance --start-date 2024-01-01`，而不是 `--sort-by submittedDate`。
- `submittedDate` 排序仅在用户明确要求按时间顺序（例如“按发布顺序显示我论文”）时适用。这种情况很少见。
- `lastUpdatedDate` 很少有用；除非用户要求，否则忽略它。

**只运行一次搜索**。如果结果看起来不完美，**不要**尝试用修改后的查询重试——arXiv 的相关性排名就是这样。重试不同的查询短语会浪费工具调用，并可能超出递归限制。如果结果确实为空（0 篇论文），请告诉用户并建议他们扩大主题或移除类别过滤器。

**如果脚本返回的论文数量少于请求的数量**，这是 arXiv 查询结果的实际大小。**不要**填充列表——向用户报告实际数量并继续进行。

**如果脚本失败**（网络错误，从 arXiv 返回非 200 状态码），请告诉用户错误类型并停止。**不要**尝试编造论文元数据。

**不要将搜索结果保存到文件**——JSON 始终保留在您的上下文中供阶段 3 使用。在整个工作流程中，唯一保存的文件是阶段 5 中的最终报告。

### 阶段 3：并行提取元数据

**您必须通过 `task` 工具将提取工作委托给子代理——不要自己提取元数据**。这是强制性的。具体来说，**不要**做以下任何事：

- ❌ 写 `python -c "papers = [...]"` 或任何 Python/bash 脚本来处理论文
- ❌ 在自己的上下文中通过逐个读取摘要来提取元数据
- ❌ 使用除 `task` 之外的任何工具进行此阶段

相反，**您必须**调用 `task` 工具来启动子代理。原因：在您自己的上下文中提取 10-50 篇论文会消耗过多的 token，并降低阶段 4 中的综合质量。每个子代理在隔离的上下文中运行，仅包含其批次的论文，产生更干净的提取。

将论文分成大约 5 篇的批次，然后对于每个批次，调用 `task` 工具并使用 `subagent_type: "general-purpose"`。每个子代理接收论文摘要作为文本，并返回结构化的 JSON。

**并发限制：每回合最多 3 个子代理**。DeerFlow 运行时强制执行 `MAX_CONCURRENT_SUBAGENTS = 3`，并将静默丢弃同一回合中的任何额外调度——LLM 不会被告知发生了这种情况，因此请严格遵循以下决策表。

**回合策略——使用此决策表，不要自己计算拆分**：

| 论文数量 | 大约 5 篇论文的批次 | 回合 | 每回合子代理数量 |
|---|---|---|---|
| 1–5 | 1 批次 | 1 回合 | 1 个子代理 |
| 6–10 | 2 批次 | 1 回合 | 2 个子代理 |
| 11–15 | 3 批次 | 1 回合 | 3 个子代理 |
| 16–20 | 4 批次 | 2 回合 | 3 + 1 |
| 21–25 | 5 批次 | 2 回合 | 3 + 2 |
| 26–30 | 6 批次 | 2 回合 | 3 + 3 |
| 31–35 | 7 批次 | 3 回合 | 3 + 3 + 1 |
| 36–40 | 8 批次 | 3 回合 | 3 + 3 + 2 |
| 41–45 | 9 批次 | 3 回合 | 3 + 3 + 3 |
| 46–50 | 10 批次 | 4 回合 | 3 + 3 + 3 + 1 |

**同一回合中永远不要发送超过 3 个子代理**。当一行说“2 回合 (3 + 1)”时，这意味着：第一回合并行发送 3 个子代理，等待所有 3 个完成，然后在第二回合发送 1 个子代理。在主代理级别，回合是严格按顺序执行的。

如果论文数量落在两行之间（例如 23 篇），向上舍入到下一行的布局，但只发送您实际需要的批次数量——决策表给出形状，而不是严格的处方。

**在主代理级别进行批处理**：您已经从阶段 2 获得了每篇论文的摘要，因此每个子代理接收纯文本输入。子代理不需要访问网络或沙盒——他们的唯一工作是读取文本并返回 JSON。不要要求子代理重新运行 `arxiv_search.py`；这会浪费 token 并可能导致速率限制。

**每个子代理接收到的内容**，作为结构化提示：

```
执行此任务：从以下 arXiv 论文中提取结构化元数据和关键发现。

论文：
[论文 1]
arxiv_id: 1706.03762
title: Attention Is All You Need
authors: Ashish Vaswani, Noam Shazeer, ...
published: 2017-06-12
abstract: <完整摘要文本>

[论文 2]
arxiv_id: ...
...

对于每篇论文，返回一个具有以下字段的 JSON 对象：
- arxiv_id (字符串)
- title (字符串)
- authors (字符串列表)
- published_date (字符串，YYYY-MM-DD)
- research_question (1 句话，论文解决的问题)
- methodology (1-2 句话，他们如何解决问题)
- key_findings (3-5 个要点，他们实际发现了什么)
- limitations (1-2 句话，他们承认的或明显缺失的内容)

将结果作为 JSON 数组返回，每个对象对应一篇论文，顺序与输入相同。不要包含任何文本，不要包含前言，不要包含 Markdown 箍栏，只返回数组。
```

**解析子代理结果**：任务工具返回带有固定前缀的字符串，如 `Task Succeeded. Result: [...JSON...]`。在尝试解析 JSON 之前，去掉 `Task Succeeded. Result: ` 前缀（或 `Task failed.` / `Task timed out.` 前缀）。如果一批次失败或返回无法解析的 JSON，请记录它，注明受影响的论文，并继续处理剩余批次——不要因为一个坏批次而使整个综合失败。

所有回合完成后，将每个批次的数组扁平化为一个论文元数据对象列表，保留顺序。

### 阶段 4：综合和格式化

现在生成最终的 SLR 报告。这里有两件事发生：跨论文综合（主题分析）和引用格式化。

**跨论文综合**：报告必须不仅仅是列出论文。至少需要识别：

- **主题**：3-6 个在集合中反复出现的研究方向、方法或问题框架。
- **共识**：多篇论文同意的发现。
- **分歧**：论文得出不同结论或使用不兼容方法的地方。
- **空白**：集体文献尚未解决的问题（通常在“局限性”字段中明确说明）。

如果论文集合太小或太异质，无法支持主题综合（例如 5 篇论文涵盖截然不同的子主题），请在报告中明确说明——不要强迫不存在的主题。

**引用格式化**：确切的格式取决于用户偏好。只读取与用户请求的格式匹配的模板文件，不要读取所有三个：

- [templates/apa.md](templates/apa.md) — APA 第 7 版。社会科学和大多数 CS 期刊的默认格式。当用户请求 APA 或未指定格式时使用。
- [templates/ieee.md](templates/ieee.md) — IEEE 数字引用。当用户针对 IEEE 会议或期刊，或明确要求 IEEE 时使用。
- [templates/bibtex.md](templates/bibtex.md) — BibTeX 条目。当用户提到 BibTeX、LaTeX 或需要机器可读的参考文献时使用。**重要**：arXiv 论文引用为 `@misc`，而不是 `@article`——BibTeX 模板明确覆盖这一点。

每个模板都包含引用规则和完整的报告结构（执行摘要、主题、每篇论文的注释、参考文献、方法论部分）。请逐字逐句地遵循模板的结构编写报告正文，然后从阶段 3 的元数据中填充内容。

### 阶段 5：保存和展示

将完整报告保存到 `/mnt/user-data/outputs/slr-<topic-slug>-<YYYYMMDD>.md`，其中 `<topic-slug>` 是主题的小写连字符版本（例如 `transformer-attention`）。然后调用 `present_files` 工具并传入该路径，以便用户可以下载。

**在聊天消息中**，显示一个简短预览，以便用户在不打开文件的情况下立即看到价值：

1. **执行摘要**——报告顶部的 3-5 句话，逐字逐句。
2. **主题列表**——您在阶段 4 综合中识别的主题的简短列表（仅主题名称+简短说明，不是完整的主题部分）。
3. **论文数量+指向文件的指针**——例如，“包含 20 篇论文的完整报告、每篇论文的注释和格式化参考文献，保存到 `slr-transformer-attention-20260409.md`。”

**不要**将完整的 2000+ 字报告直接嵌入——每篇论文的注释、参考文献和方法论都属于文件。预览是为了让用户一眼就能判断报告的价值，并决定是否打开它。

## 示例

**示例 1：典型的 SLR 请求**

用户：“对最近的 transformer 注意力变体进行系统文献综述，20 篇论文，APA 格式。”

您的流程：
1. 阶段 1：确认主题（transformer 注意力变体），范围（20 篇论文，默认时间窗口），格式（APA）。如果任何内容不明确，只问**一个**澄清问题（例如，“是否有特定的时间窗口，或者我应该默认为过去 3 年？”）。
2. 阶段 2：`arxiv_search.py "transformer attention" --max-results 20 --sort-by relevance --start-date 2023-01-01`。
3. 阶段 3：20 篇论文 → 回合 1 = 3 个子代理 × 5 篇论文 = 15 篇覆盖，回合 2 = 1 个子代理 × 5 篇论文 = 5 篇覆盖。聚合。
4. 阶段 4：读取 `templates/apa.md`，使用其结构编写报告，使用阶段 3 的元数据填充主题 + 每篇论文的注释。
5. 阶段 5：保存到 `slr-transformer-attention-20260409.md`，调用 `present_files`。

**示例 2：小集合请求中的歧义**

用户：“为我调查几篇关于扩散模型的论文。”

您的流程：
1. 阶段 1：“几篇”是模糊的。问**一个**问题：“您需要多少篇论文——10 篇、20 篇还是 30 篇？以及是否有引用格式偏好（默认为 APA）？”
2. 用户回复“10，BibTeX”。
3. 阶段 2：`arxiv_search.py "diffusion models" --max-results 10 --category cs.CV`。
4. 阶段 3：10 篇论文 → 单回合，2 个子代理 × 5 篇论文。
5. 阶段 4：读取 `templates/bibtex.md`，使用 `@misc` 条目（不是 `@article`）。
6. 阶段 5：保存并展示。

**示例 3：超出范围请求**

用户：“这里有一篇论文 (https://arxiv.org/abs/1706.03762)。你能评审它吗？”

这是单篇论文的同行评审，不是文献综述。不要使用此技能。转接到 `academic-paper-review`。

## 注意事项

- **前提条件：`subagent_enabled` 必须为 `true`**。阶段 3 需要 `task` 工具进行并行元数据提取。此工具仅在运行时配置中 `subagent_enabled` 设置为 `true` (`config.configurable.subagent_enabled`) 时加载。如果没有它，`task` 工具将不会出现在可用工具中，阶段 3 不能按设计执行。
- **仅限 arXiv，按设计**。此技能不查询 Semantic Scholar、PubMed 或 Google Scholar。arXiv 涵盖了 CS/ML/物理/数学预印本的大部分内容，这是 DeerFlow 用户最常想要调查的。多源学术搜索应属于专用的 MCP 服务器，而不是在此技能内部。
- **50 篇论文的硬性上限**。这与阶段 3 的并发策略（每回合最多 3 个子代理，每个约 5 篇论文，最多约 3 个回合）相关。超过 50 篇的综述会降低综合质量，最好按子主题分割。
- **阶段 3 要求子代理启用**。此技能的并行提取步骤强制要求 `task` 工具，该工具仅在运行时 `subagent_enabled=true` 时可用。如果子代理不可用，请不要声称执行阶段 3 的并行计划；相反，告诉用户必须启用子代理才能执行完整工作流程，或者提供缩小/分割请求以进行手动评审。
- **子代理结果是字符串，不是对象**。始终去掉 `Task Succeeded. Result: ` / `Task failed.` / `Task timed out.` 前缀，然后解析 JSON 负载。
- **`id` 字段是裸的 arXiv ID**（例如 `1706.03762`），不是 URL，也没有版本后缀。`abs_url` / `pdf_url` 包含完整 URL，如果您需要它们。
- **综合，不是列表**。最终报告必须识别主题并在论文之间进行比较。只列出论文一篇接一篇的报告是一种失败模式——如果您找不到主题，请明确说明，而不是编造它们。
