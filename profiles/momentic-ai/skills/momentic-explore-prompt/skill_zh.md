# 生成 explore-prompt.md

## 该文件的作用

explore agent (`momentic ai explore diff` 在 git 范围内运行，或
`momentic ai explore latest` 在整个应用上运行) 识别变化的用户旅程，并为它们构建 Momentic 测试。两者都接受附加到 explorer 系统提示符的额外指令，通过两个可重复的选项：

- `--prompt <text>` — 行内文本。可重复。
- `--prompt-file <path>` — 其内容将被附加的文件。可重复。

传递任何 `--prompt` 或 `--prompt-file` 都会替换项目的云自定义提示符。组合指令是所有 `--prompt-file` 内容，后跟所有 `--prompt` 值，每个按传递的顺序排列——因此多个标志会堆叠，而不是一个覆盖另一个。

`explore-prompt.md` 是传递给 `--prompt-file` 的常规文件。它是
**特定于仓库的**：它告诉 explorer 该仓库中存在哪些应用，其测试必须针对的 URL，如何登录，生成的测试的确切保存位置，以及它必须遵循的任何特殊规则。它**不是**重新陈述一般 Momentic 行为的地方——那已经存在于 `momentic-test` 技能中。

用法：

```sh
momentic ai explore diff --prompt-file ./explore-prompt.md
```

## 首先收集仓库信息

不要凭记忆编写提示符。检查仓库并确认每个事实：

1. **测试中的应用程序。** 列出所有前端/应用程序，生成的测试将驱动它们。对于每个应用程序，确定测试必须访问的 URL。这是在运行时使用的已部署/服务 URL，通常**不是**本地编写时使用的 Vite/开发 URL。交叉检查 `momentic.config.yaml`
`environments[].baseUrl` 以及每个应用程序在 CI（运行 `momentic ai explore diff` 的工作流）中是如何启动的。
2. **身份验证。** explorer 应如何登录？优先使用可重用的登录模块——记录其确切的 `name` 和 `id`。注意访问假设（例如，“此用户可以访问应用程序的所有部分”）。
3. **测试位置。** 每个应用程序的测试所属的文件夹，相对于工作区表示，包括任何强制性的路径前缀。使约束条件明确无误。
4. **临时性 / 嵌套测试。** 作为探索运行副作用创建的测试必须保存的位置（通常是单个 git 忽略的 `momentic/junk/` 文件夹）。确认哪个路径被 git 忽略。
5. **特殊规则。** 外部持久化数据，在运行中生存（必须在每次运行时随机化以避免冲突），身份验证特殊性，不稳定区域，基础 URL 缓存标志等。

## 要生成的结构

编写简洁、命令式的 markdown。建议的章节：

- **应用程序和目标 URL** — 每个应用程序一个要点：名称 — 测试必须针对的 URL — 目的 — 如何服务/运行 — 如果需要身份验证，登录模块（名称 + id）。
- **旅程 → 应用程序映射** — 如何将范围内的 diff 映射到受其影响的应用程序，以便驱动正确的编辑器/端口。
- **测试位置规则** — 每个应用程序的目标文件夹，带有明确的 `HARD RULE` 调用，用于任何强制性的前缀。否则，explorer 将在错误的位置保存测试。
- **临时性 / 嵌套测试规则** — 每个嵌套测试必须落入的 git 忽略的垃圾文件夹，以及命名文件 `junk-*` 不计算。
- **要特别注意的特殊规则** — 上面收集的特定于仓库的陷阱。

## 好提示符的规则

- 目标 URL 必须是测试实际运行的 URL，绝不能是作者编写的开发服务器 URL。
- 对路径约束要明确，并使用 `HARD RULE:` 调用——路径错误是最常见且最昂贵的 explorer 失败。
- 保持特定于仓库且简短。省略任何已由一般 Momentic 文档/技能涵盖的内容。
- 通过 `name` 和 `id` 引用登录模块，以便 explorer 可以锁定确切模块。

## 参考模板

下面是一个仅作占位符的骨架，包含好提示符的章节。用您的仓库的真实应用程序、URL、模块和文件夹填写括号内的值——不要提交占位符。

```md
该仓库有 <N> 个前端应用程序。测试运行时，每个应用程序都提供在以下 URL——目标是这些，而不是本地编写时使用的开发服务器 URL。

- <app-name> — <一句话目的> at <https://url-tests-must-target>。首先使用名为 `<login-module-name>` (id: <login-module-id>) 的模块登录。
  <访问假设，例如此用户可以访问应用程序的所有部分>。
- <app-name-2> — <目的> at <https://url-2>。测试必须使用 <https://url-2> 作为其基础 URL。

在识别变化的用户旅程时，将每个范围内的 diff 映射到上述应用程序，以便驱动正确的应用程序/端口。

将新测试放在与应用程序驱动匹配的文件夹中。每个目标路径相对于您的工作区，并且 `<mandatory-prefix>/` 段是强制性的——永远不要省略它：

- <app-name> 旅程 → <mandatory-prefix>/<app-folder>/。
- <app-name-2> 旅程 → <mandatory-prefix>/<app-2-folder>/。

HARD RULE — 在编写的测试中保留 `<mandatory-prefix>/` 前缀。保存到省略它的任何路径都是硬失败。

HARD RULE: 任何作为构建另一个测试的副作用创建的测试都是临时性的，并且必须保存到 git 忽略的 `<junk-folder>/` 目录。命名文件 `junk-*` 不计算——只有那个目录被 git 忽略。

要特别注意的一些特殊规则：

- <quirk, 例如外部同步数据在运行中生存——每次运行时随机化您写入的任何数据，以避免运行冲突>。
```
