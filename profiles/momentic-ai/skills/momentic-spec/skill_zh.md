# Momentic 规范驱动开发

在实现产品功能之前，先以 Momentic 测试的形式编写预期的产品行为。
测试定义了契约；不要让测试去适应实现。

## 不可协商的顺序

1. 读取仓库指南、`momentic.config.yaml` 以及附近的测试和模块。
2. 确定并报告预期受影响的精确 Momentic 测试。
3. 在更改产品代码之前创建或修改这些测试。
4. 将测试差异作为产品规范进行审查。
5. 只有在此时才实现产品变更。
6. 在实现过程中使用快速代码级检查；不要在每次编辑或提交后运行 Momentic。
7. 在一个持久的端到端检查点，准备所需的测试状态，启用现在应该通过的受影响测试，并询问是否运行最小的受影响集。

在预期的测试规范存在于磁盘上之前，不要开始产品实现。如果用户更改了需求，请先再次更新规范。

## 选择受影响的测试

- 如果用户指定了特定的现有测试，从这些测试开始，并保持工作集中于它们。只有在仓库证据表明另一个测试或共享模块直接受影响时，才扩展这个集合。
- 对于新的用户可见功能，创建描述新用户旅程的最小新测试或测试。
- 对于更改的功能，更新描述旧行为的现有测试，而不是添加重复的覆盖范围。
- 跟踪共享组件和模块足够远，以找到真实的行为影响。不要仅凭文件名就推断受影响的集合。
- 如果没有受影响的 Momentic 测试，在做出产品变更之前说明原因。不要仅仅为了生成测试差异而进行外观上的测试编辑。

在编辑产品代码之前，报告每个受影响的测试路径以及它将被添加、更改还是保持不变。

## 首先编写产品规范

预实现的测试应该描述请求的结果，即使当前产品还不能满足它。

- 保留无关的设置、拆卸、数据、断言和测试意图。
- 不要因为这与当前实现匹配而削弱断言或保留旧行为。
- 当实现或必需的依赖项尚未准备好，并且测试预期不会通过时，将测试标记为 `disabled: true`。记录它被禁用的原因以及启用它之前必须变为真的事项。
- 不要仅仅因为本地凭证或可运行的运行环境不可用而使用 `disabled: true`。这是一个验证限制，不一定是预期的产品故障。
- 保持差异狭窄。一个更改的产品契约通常应该有一个集中的测试差异。

在编写测试后，总结预期的失败或禁用行为，并在实现它之前确认测试是否表达了用户的要求。

## 遵循代码库的测试语言

阅读附近的测试并遵循其建立的约定，包括文件夹放置、命名、模块、设置、数据以及对 AI 检查、页面检查或元素检查的偏好。在代码库没有表达偏好的地方应用基线 Momentic 实践：

- 优先使用原生 Momentic 步骤和自然语言目标，而不是 JavaScript 或选择器。
- 保持断言最小化并用户驱动，在灵活的操作后进行明确的结果检查。
- 对于身份验证、设置和导航等已建立的流程，重用现有模块，而不是内联重新创建这些流程。
- 除非请求的产品契约需要它，否则不要重新组织或修改共享模块。考虑所有消耗已更改模块的测试。
- 不要通过更改测试来绕过真实的产品故障。

## 优先为新的规范使用 AI 行动 V3

对于新测试，当高级目标更清晰地读作产品规范时，优先使用 AI 行动 V3 `act:` 步骤，特别是对于长流程。重用已知子流程的现有模块，并使用 `act:` 来处理新行为，而不是将可重用的设置隐藏在一个大的目标中。

保持目标简短、具体和结果导向。将 `act:` 步骤与附近测试中使用的相同断言样式配对，以便测试验证结果，而不仅仅是代理停止。

AI 行动 V3 在成功运行后缓存生成的步骤，并在缓存的步骤缺失时自我修复：

- 对稳定的产品流程保持缓存启用。缓存的重新运行更快且更确定。
- 仅当目标本质上动态且应在每次运行时重新导出时设置 `cache: false`，例如打开最新记录或响应频繁变化的内容。
- 不要禁用缓存以隐藏过时或不正确的规范。当预期行为发生变化时，更新目标或步骤描述，以便其缓存标识发生变化。
- 当 MCP 预览为将持久化的步骤返回 `CacheId` 时，将缓存 ID 带入保存的步骤，如 `momentic-test` 技能所要求的。

## 在持久的端到端检查点运行

Momentic 是真正的端到端验证，而不是编码代理的内部反馈循环。不要在每次文件编辑、实现步骤、提交或小型重构后运行受影响的 Momentic 测试。

默认情况下不要执行 Momentic 测试。允许编辑和 linting Momentic 测试而无需确认，但测试执行可能需要时间并消耗积分。在持久的检查点：

1. 在运行 Momentic 之前停止。
2. 告诉用户你建议运行哪些测试，以及当已知时，预期的持续时间或积分影响。
3. 询问用户是否要运行它们。
4. 只有在明确确认后才能运行。直接请求运行指定的测试视为确认。

确认仅涵盖建议的运行。除非用户明确授权迭代重新运行，否则在另一次 Momentic 执行之前再次询问。如果用户拒绝或不确认，请继续进行非 Momentic 检查，并报告测试未运行。

在构建时使用更快的仓库检查，如单元测试、类型检查和 linting。当应用程序达到一个逻辑检查点，该检查点是持久的并且可以通过真实 UI 使用时运行 Momentic：

- 对于小型更改，检查点通常是完全实现的更改。
- 对于多阶段或特别大的功能，检查点可以是一个完成的、可独立使用的 UI 片段，它需要所有受影响测试的先决条件。不要等待整个功能，当有意义的组件已经可以端到端测试时。
- 不要将任意的提交边界视为检查点。决定性问题是一个用户是否可以通过产品执行预期行为并观察到指定结果。

在每个检查点，建议最小的受影响测试集。在确认后，运行一次，诊断失败，并做出连贯的修复。在重新运行之前再次请求确认，除非已经授权迭代重新运行，并且只有在有合理预期端到端结果发生变化时才重新运行。保持未来的规范禁用，直到检查点存在。

## 拥有测试数据和应用程序状态

实现产品变更的编码代理负责使检查点干净可运行。在调用 Momentic 之前，识别并建立所需的数据、账户状态、功能标志、权限、集成和服务状态。不要将先决条件的创建留给浏览器代理通过无关的 UI 流程来改进。

优先使用现有的测试设置设施。当应用程序缺乏可靠的方式来创建先决条件时，鼓励编码代理构建安全的、仅限测试环境的功能，例如：

- idempotent 端点或脚本，用于播种确定性记录和状态
- 用于真实测试数据的 fixtures 和 factories
- 专用的测试账户、角色和身份验证状态
- 用于功能标志或外部服务替代品的测试控制
- 范围清理或唯一数据机制，以防止跨运行污染

任何新的测试功能都必须在生产中不可访问，明确限制为批准的测试环境，在适当的地方进行身份验证，范围狭窄，并且可以重复调用，安全可靠。永远不要添加生产后门，削弱生产授权，或将测试行为编码在种子机制中。

记录设置契约，并在 Momentic 运行之前执行它，或者从测试的已建立设置部分调用它。生成的测试应该可以从干净的环境重复运行，而无需依赖先前运行中的偶然状态。

## 安全地编辑和验证

使用安装的 `momentic-test` 技能进行详细的编写、格式和 MCP 指导。

- 当更改很小且预期步骤清晰时，直接编辑 v2 测试 (`fileType: momentic/test/v2`)。
- 不要直接编辑 v1 测试 YAML。使用 Momentic MCP 工具来持久化 v1 变更。
- 当 UI 发现、实时状态或定位器行为不确定时，使用 MCP 浏览器验证。
- 在可能的情况下，在产品实现之前对测试规范进行 linting。
- 在持久的端到端检查点，从现在预期会通过的测试中删除 `disabled: true`，建立其所需状态，并询问是否运行最小的受影响集。
- 只有当测试仍然有意不预期通过时才将其禁用，并在交接中包括原因和启用条件。

在实现后运行仓库要求的产品代码检查。在交接中，列出受影响的测试、它们的启用或禁用状态、实现的产品行为以及运行或未运行的每个验证。
