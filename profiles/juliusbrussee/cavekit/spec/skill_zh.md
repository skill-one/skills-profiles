# spec — spec 修改器

若尚未加载，请读取存储库根目录下的 `FORMAT.md`。原始人技能适用于此处的所有写入操作。

## 调度

检查用户请求和项目状态：

1. 存储库根目录下不存在 `SPEC.md` 且参数描述了想法 → **新建**
2. 存储库根目录下不存在 `SPEC.md` 且参数中包含 `from-code` → **提取**
3. 存储库根目录下存在 `SPEC.md` 且参数以 `bug:` 开头 → **回溯**
4. 存储库根目录下存在 `SPEC.md` 且参数以 `amend` 开头 → **修订**
5. 存储库根目录下存在 `SPEC.md` 且无参数 → 询问用户选择何种模式

## 输入 — spec 是唯一的修改器

其他动词生成材料；spec 将其写入。将它们的交接块输入到正确的部分，显示差异，在确认后写入：

- **grill** → 锋利的 §G + §C
- **research** → §R 行（若不存在则添加 §R 部分）
- **review** → 草拟的 §V 行 + 风险裁决
- **deepen** → §I/§V/§T 修订

⊥ 重新编写交接块未命名的部分。部分所有权（参见 `FORMAT.md`）。

## 新建 — 想法 → spec

输入：用户想法。如果它模糊不清，优先运行 **grill**。

步骤：

1. 提取目标（1 行，原始人风格）→ §G。
2. 列出用户声明或暗示的约束 → §C。
3. 列出用户命名的外部接口 → §I。
4. 仅当 **research** 运行时才添加 §R 部分 — 否则省略该部分（调整大小）。
5. 提出初始不变式 → §V（编号 V1…）。
6. 将目标分解为有序任务 → §T 管道表格，所有状态为 `.`, id 为 T1…
7. 创建仅含标题行的 §B 部分（`id|date|cause|fix`）。

写入 `SPEC.md`。向用户显示完整文件。询问："spec 确认？`/review` 如果高爆炸半径，否则 `/build`。"

## 提取 — 代码 → spec

遍历存储库。生成 §G（从 README/package.json/main 条目推断），§C（从栈推断），§I（枚举公共 API/CLI/配置），§V（从测试和断言推导），§T（每个已知 TODO 或缺失测试一个任务），§B（空）。

原始人风格。用文本中的 `?` 标记不确定项，以便用户确认。

## 回溯 — 错误 → §B + §V

输入：`bug: <描述>`。

步骤：

1. 解析错误描述。
2. 找到根本原因（阅读相关代码）。
3. 判断：新的不变式能否捕获重复发生？如果可以 → 草拟 `V<下一个>`。
4. 添加 §B 行：`B<下一个>|<日期>|<原因>|V<N>`。
5. 添加新的不变式到 §V。
6. 如果修复也改变行为 → 添加/更新 §T 行。
7. 显示差异。仅在用户确认后应用。

规则：每个错误都获得一个 §B 条目。不变式可选但推荐。

## 修订 — 针对性编辑

输入：`amend §V.3` 或 `amend §T` 等。

读取该部分。显示当前内容。询问用户要做的更改。写入。显示差异。

从不默默重写用户未命名的部分。

## 输出规则

- 根据 `FORMAT.md` 采用原始人格式。
- 保留标识符、路径、代码原样。
- 编号单调 — 永不重用 §V.N 或 §B.N。
- §T 行 `cites` 列 ! 列出 §V/§I 依赖：`T5|.|impl auth mw|V2,I.api`。

## 非目标

- 无子代理。主线程写入。
- 无仪表盘，无日志，无除 `SPEC.md` 本身外的状态文件。
- spec 后不自动构建。用户显式调用构建。
