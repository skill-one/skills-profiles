# build — 实现规范

单线程原生计划→执行。你是主 Claude。没有集群。

## 加载

1. 读取 `SPEC.md`。如果缺失 → 告知用户先调用规范技能。停止。
2. 如果未加载，读取 `FORMAT.md` 一次。
3. 如果存在 §R → 读取外部事实，构建必须遵守，⊥ 重新推导或矛盾。
4. 解析调用参数：
   - `§T.n` → 仅该任务
   - `--next` → 具有状态 `.` 或 `~` 的最低编号行
   - `--all` 或空 → 按 §T 顺序的每个 `.` 行

高影响范围（共享模块、认证、数据、金钱、公共 §I）？先运行 `/review`。简单且可逆？跳过规划仪式，直接执行步骤 EXECUTE。

## 规划

原生计划模式 — 你将其委派，而不是重新发明任务分解。对于选定的任务：

1. 引用所有适用的 §V 不变量。规划必须尊重所有。
2. 引用所有接触的 §I 接口。规划必须保持形状。
3. 列出要创建/编辑的文件。
4. **验证合约** — 指明证明每个 §V 触及的精确测试/验收标准。是哪个测试，而不是“添加测试”。仅“做 TDD”会适得其反；规范说明 *要检查什么*。每个触及的 §V → 一个命名的测试，该测试首先失败。
5. 命名验证命令（测试、构建、校验） — 这是外部神谕。绿色 = 完成；⊥ “看起来完成了”。

显示计划。等待用户确认，除非自动模式。

## 执行

按顺序对每个任务：

1. 将 §T.n 状态单元格 `.` → `~`。仅写入到 SPEC.md。
2. 按计划编辑代码。
3. 运行验证命令。
4. **通过** → 将 `~` → `x`。下一个任务。
5. **失败** → 调用反向传播技能。不要盲目重试。

## 失败 → 反向传播

在测试/构建失败时：

1. 读取失败输出。
2. 询问：失败是 (a) 我的代码错误，(b) 规范错误，还是 (c) 未指定的边缘情况？
3. 如果 (a) → 修复代码，重新运行。不更改规范。
4. 如果 (b) 或 (c) → 先用 `bug: <原因>` 调用规范技能，让它更新 §V 和 §B，然后针对更新后的规范继续构建。

规则：不要在考虑反向传播的情况下无声地修复根本原因。§B 是防止重复的内存。

## 写入策略

- 仅翻转 §T 状态。构建不进行其他 SPEC.md 编辑。
- 其他规范编辑 → 调用规范技能。
- 每个完成 §T 后提交。消息：`T<n>: <目标行>` + §V 引用。

## 验证

任务 `x` 仅当：

- 验证命令（神谕）退出 0。
- 每个 §V 触及的验证合约中的命名测试都通过。
- 没有 §V 不变量退化（在最后运行完整测试套件）。

## 非目标

- 没有子代理。没有并行工作。仅主线程。
- 没有进度仪表板。`cat SPEC.md | grep §T` 是仪表板。
- 超出选定任务范围之外没有推测性工作。
