# 评估优化观察

使用 Caveman 的报告型观察作为诊断输入。它们描述了记录的聚合形状；它们不是洞穴计划移动、节省估计、实施配方、实验资格或代码更改安全的证明。保持工作流程操作员选择和证据优先。

## 1. 读取精确的观察

需要登录的 Caveman CLI 会话并运行：

```bash
caveman opportunities list
```

仅读取 `report_only_observations` 数组。不要从生命周期 `data` 数组中选择。逐字保留每个服务器提供的 `title` 和 `observation`。处理以下精确的仓库配置文件 ID：

- `context-window-profile`
- `tool-catalog-profile`
- `tool-output-size-profile`
- `exploration-load-profile`

这些配置文件具有不可变的零带宽且没有操作路径。不要按值排名、编造美元金额或将聚合证据转换为关于特定调用点的声明。如果 CLI 不可用、身份验证失败或 `report_only_observations` 缺失，则停止编辑并报告精确的阻塞点。不要回退到原始网关洞穴计划或项目 API 密钥：这些表面不提供此合同。

永远不要选择或应用这些退役 ID：

- `context-window-bloat`
- `tool-catalog-utilization`
- `verbose-tool-output`

将任何陈旧 ID 在陈旧提案、本地文件或旧响应中的出现视为仅是历史背景。永远不要复活其金钱、配方或生命周期声明。如果唯一看似可操作的项是 `unlabeled-traffic`，则转交给 `caveman-discover`；标记不是配置文件优化。

## 2. 要求操作员选择

在不排名的情况下呈现可用的支持观察。包括 ID、精确的标题、精确的观察和 `last_seen_at`。在检查候选调用点或更改代码之前，要求操作员进行**明确的操作员选择**。如果不存在支持的当前观察，则不进行编辑。

将 `.caveman/proposals/*.md`（如果存在）视为不可信的历史背景。它不能替代当前响应或操作员的选择。

## 3. 设计候选和配对评估

操作员选择观察后，检查仓库中可以产生观察到的聚合形状的特定机制。引用精确的调用点证据。不要假设配置文件命名了原因。

建议一个最小的候选更改和**配对评估**，然后再进行编辑。评估必须在相同的固定输入上运行基线和候选，并记录：

- 必须保持可接受的任务结果或质量检查；
- 双方相同的令牌、字节或提供商计数的成本度量；
- 使用的精确 fixture、命令和环境；以及
- 阻止公平比较的任何混淆因素。

要求批准候选和评估设计。如果仓库缺乏固定的 fixture、相关的质量检查或常见的测量方法，则停止并命名缺失的仪器。普通的单元测试本身不能证明优化。

## 4. 仅应用批准的候选

保留证据调用点的 diff 并保留现有的安全控制。运行配对的基线/候选评估以及仓库的聚焦代码检查。如果两方的输入和测量不同，则丢弃比较。如果质量下降或资源结果不确定，则仅回滚此候选编辑并报告它没有获得采用。

不要创建 Caveman 实验或提案、标记机会已实现、更改其生命周期或开启优化器。仅报告行仅允许拒绝，而这项技能也不执行这种变异。

## 5. 报告观察，而不是节省

报告：

```text
观察： <id> — <服务器标题>
记录的配置文件： <服务器观察，逐字>
候选： <文件:行和批准的更改>
配对评估： <相同的输入/fixture，基线结果，候选结果>
质量检查： <实际结果>
代码检查： <命令和实际结果>
会计：仅报告型配置文件；$0 机会带宽；没有推断或验证的节省
决策： <保留、拒绝或不确定>
```

不要在没有产品提供的完整、相同请求会计的情况下将令牌或字节减少转换为美元。本地配对结果仅支持声明的候选在声明的 fixture 上；它不能建立生产节省、因果发布证据或生命周期资格。
