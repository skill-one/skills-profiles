请编写简洁且精确的提交信息。使用常规提交格式。不要有废话。关注原因而非结果。

## 规则

**主题行：**
- `<类型>(<范围>): <祈使句摘要>` — `<范围>`是可选的
- 类型：`feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `chore`, `build`, `ci`, `style`, `revert`
- 祈使语气："添加", "修复", "删除" — 而不是 "添加了", "添加", "正在添加"
- 尽可能≤50个字符，硬性上限72个字符
- 不带句号
- 冒号后的大小写需与项目约定一致

**正文（仅当需要时）：**
- 当主题行已足够说明时，完全省略
- 仅在以下情况添加正文：非显而易见的原因，破坏性变更，迁移说明，关联的issue/PR
- 在72个字符处换行
- 使用短横线`-`而非星号`*`
- 在末尾引用issue/PR：`Closes #42`, `Refs #17`

**绝对不能包含的内容：**
- "此提交执行了X", "我", "我们", "现在", "当前" — 差异已说明
- "应...的要求" — 使用Co-authored-by后缀
- "由Claude Code生成"或任何AI归属 — 除非用户自己的规则要求添加`Assisted-by`/AI归属后缀，则添加
- Emoji（除非项目约定要求）
- 当范围已说明时，重复文件名

## 示例

差异：为用户资料添加新端点，正文解释原因
- ❌ "feat: 添加一个从数据库获取用户资料信息的端点"
- ✅
  ```
  feat(api): 添加 GET /users/:id/profile

  移动客户端需要资料数据，而不需要完整的用户负载，以减少冷启动屏幕上的LTE带宽。

  Closes #128
  ```

差异：破坏性API变更
- ✅
  ```
  feat(api)!: 将 /v1/orders 重命名为 /v1/checkout

  破坏性变更：使用 /v1/orders 的客户端必须在2026-06-01之前迁移到 /v1/checkout。旧路由在该日期后返回410状态码。
  ```

## 自动清晰度

对于破坏性变更、安全修复、数据迁移、任何回滚先前提交的内容，始终包含正文。不要将这些压缩为仅主题行 — 未来的调试者需要上下文。

## 边界

仅生成提交信息。不会运行`git commit`，不会暂存文件，不会修改。将信息作为代码块输出，准备粘贴。"停止原始人式提交"或"正常模式"：恢复详细提交风格。
