# 审查原始人证据

以只读操作员身份行事。根据当前的原始人数据得出结论，而不是基于仓库的猜测。永远不要从这个技能开始、批准、取消或回滚实验。

## 硬性规则

1. 将这些桶分开：
   - 测量的提供商完整列表价格成本；
   - `inferred`每日剩余空间；
   - `verified`账本节省；
   - 证据成本。
   永远不要添加或重新标记它们。
2. 除非用户明确要求审查有效载荷，否则不要获取提示、完成、工具或工件的有效载荷。元数据、跨度、时间、模型、令牌计数、状态和优化器归因足以进行默认审查。
3. 将每个读取范围限定在原始人上下文选择的项目内。永远不要提供组织ID。
4. 空结果证明当前没有信号，而不是零成本或零风险。
5. 引用使用的跟踪ID和精确的时间窗口。不要仅凭汇总数据就声称因果关系。

## 第1步 — 加载上下文

优先使用MCP：

```text
caveman_context {}
```

CLI备用方案：

```bash
caveman cloud whoami
caveman cloud projects list
```

如果登录或项目选择缺失，则停止。要求用户运行`caveman login`或选择一个项目；永远不要猜测。

## 第2步 — 建立基线

使用`caveman_report`进行：

- `overview`
- `costs`
- `score`
- `workflows`
- `verified_savings`

然后使用`caveman_plan`进行排名每日剩余空间。如果问题范围较窄，则跳过不相关的报告。读取最短的集合即可回答问题。

CLI备用方案：

```bash
caveman cloud costs
caveman cloud score
caveman cloud plan --json
```

在解释方向之前，说明报告窗口和基础。

## 第3步 — 使用跟踪测试主要解释

使用`caveman_trace_search`。选择一个有限的时间窗口和封闭的过滤器：
工作流、代理、模型、提供商、错误代码、运行时模式、缓存状态、优化ID、状态类、令牌/成本/延迟界限、压缩或监控判定。

有用的分组：

- `workflow` — 查找导致成本或失败的作业；
- `model` — 比较模型组合；
- `session` — 隔离重试或循环行为；
- 未分组 — 识别精确的跟踪。

将可疑组与对照组或较早的有限时间窗口进行比较。不要从一个昂贵的跟踪中推断因果关系。

CLI备用方案：

```bash
caveman cloud traces search \
  --workflow <slug> \
  --from <RFC3339> \
  --to <RFC3339> \
  --sort total_cost_usd \
  --dir desc \
  --limit 25
```

## 第4步 — 检查代表性跟踪

为少量高信号跟踪ID调用`caveman_trace_get`。检查请求和跨度元数据、延迟、状态、令牌计数、缓存状态、应用的优化器和模型路由。保持有效载荷检索关闭。

CLI备用方案：

```bash
caveman cloud traces show <trace-id> --spans
```

## 第5步 — 报告

使用此格式：

```text
## 原始人证据审查

范围：<项目> · <从>到<到>
测量成本：<值和基础>
验证节省：<账本值，保持分开>
推断剩余空间：<每日范围，保持分开>

发现：
1. <发现> — <汇总证据> — 跟踪 <ids>
2. <发现> — <汇总证据> — 跟踪 <ids>

未证实：
- <缺乏对照组、跟踪或评估的合理解释>

下次只读检查：
- <一个有限查询>

可能操作：
- <仅提出建议；使用caveman-manage进行只读生命周期审查和安全门>
```

如果数据缺失，则命名缺失的信号并在最强支持声明处停止。永远不要将目录子总计变成发票或将实验结果变成验证节省。
