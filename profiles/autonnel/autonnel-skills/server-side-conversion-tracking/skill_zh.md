# 服务器端转换跟踪

浏览器像素因 iOS 跟踪阻止、广告拦截器、cookie 生命周期限制和跨域跳转而丢失大量且不可预测的转化。服务器端报告修复的是 *报告*，这是广告平台的竞价模型学习的对象。这项技能涵盖了模型、设置顺序以及如何验证它。

## 何时使用

- 广告平台报告的购买数量少于商店/数据库实际记录的数量
- CPA 在跟踪更改后似乎变差了，而实际销售额没有变化
- 设置一个将接收付费流量的新漏斗
- 被问及 CAPI / 事件 API / 离线转化导入 / 点击 ID 传递
- 平台之间的归因分歧（“Facebook 声称 40 笔销售，Google 声称 30 笔，我们实际有 45 笔订单”）

## 模型，必须按此顺序构建

弄错这个顺序是“服务器端设置”仍然报告不足的常见原因。

```
1. 捕获   在着陆页上捕获点击 ID + UTMs，在第一次访问和任何重定向之前
2. 持久化   将它们附加到访客的会话中，服务器端
3. 传递     在每个漏斗步骤中保持它们，包括跨域跳转
4. 附加     在购买时将它们写入订单记录
5. 报告     使用点击 ID + 哈希的 PII 将购买事件从服务器到服务器发送
6. 去重     给浏览器事件和服务器事件相同的唯一事件 ID
7. 验证     比较平台报告的转化与您自己的订单表
```

跳过步骤 1-4 只做步骤 5 会导致服务器事件没有点击 ID，平台只能根据哈希的电子邮件进行匹配——这是实质上更差的匹配，并且是“我们已经做 CAPI”设置中最常见的失败原因。

### 步骤 1-2：捕获和持久化

| 平台 | 点击 ID 参数 |
|---|---|
| Facebook / Instagram | `fbclid` |
| TikTok | `ttclid` |
| Google Ads | `gclid`（iOS 应用到网站的 `wbraid` / `gbraid`） |
| Microsoft / Bing | `msclkid` |

还应在第一次访问时捕获：`utm_source`、`utm_medium`、`utm_campaign`、`utm_content`、`utm_term`、完整的着陆 URL、来源、用户代理和服务器看到的客户端 IP。Facebook 的 CAPI 匹配质量取决于 `client_ip_address` 和 `client_user_agent`，它们必须是 *访客的*，而不是您服务器的——在代理或 CDN 后面，从转发头中读取它们。

服务器端存储，以第一方会话为键。不要依赖客户端 cookie 在结账时存活：在 iOS 上，可脚本写入的存储可能最多只有 7 天或更短，并且跨域跳转会完全破坏它。

### 步骤 3：跨步骤传递

- 同域步骤：如果会话是服务器端的，会话 cookie 足够。
- 跨域步骤（着陆页在一个域，结账在另一个域）：标识符必须在重定向中显式转发，然后在接收域中重新持久化。这是大多数漏斗无声丢失归因的地方。
- 重定向链：每个跳转都必须保留查询字符串。跟踪重定向丢弃 `?fbclid=...` 会破坏整个活动的归因。

### 步骤 4：附加到订单

订单记录必须包含点击 ID、UTMs 和着陆 URL。这是使其他所有操作成为可能的关键：它将归因转换为数据库连接而不是浏览器猜测，它能够承受重播和回填，并且它允许您将平台数字与现实情况核对。

### 步骤 5：服务器到服务器报告

| 平台 | 端点 / 机制 | 需要的凭证 |
|---|---|---|
| Facebook | 转化 API | 像素 ID + 访问令牌 |
| TikTok | 事件 API | 像素代码 + 访问令牌 |
| Google Ads | 点击转化导入（`gclid`-键控） | 转化操作 + 开发者/OAuth 凭证 |
| Microsoft Bing | 转化 API | UET 标签 ID + CAPI 令牌 |

与事件一起发送：事件名称、事件时间、事件 ID（用于去重）、订单价值 + 货币、点击 ID、使用平台要求的标准化哈希客户标识符（电子邮件、电话）。如果标准化错误，会无声地降低匹配率，而不会出现任何错误。

从队列中发送并重试，而不是在结账请求中内联发送。支付绝不能因为广告平台的 API 缓慢而失败，并且必须重试丢失的事件，而不是丢失。

### 步骤 6：去重

如果您为同一笔购买既发射浏览器像素又发射服务器事件（推荐——它们覆盖不同的损失），则两者都必须携带相同的事件 ID，并且当存在时，Facebook 还会根据 `fbp`/`fbc` cookie 值进行匹配。如果没有共享事件 ID，您会重复计数，然后“修复”它通过删除服务器事件，这恰恰是反向操作。

### 步骤 7：验证

不要假设设置工作只是因为部署了代码。检查：

1. **平台事件调试器** - Facebook 事件管理器测试事件 / TikTok 事件调试：事件是否到达，报告的匹配质量是什么？
2. **您自己的核对** - 在过去 7 天内，数据库中的订单数量与每个平台报告的转化数量。预期平台数字与现实情况不同；您要找的是 *稳定的* 比率，而不是相等。每周波动的比率意味着管道正在丢失事件。
3. **点击 ID 覆盖率** - 有多少付费订单附加了点击 ID？如果它远低于付费流量的比例，则步骤 1-4 某处出了问题。在整个系统中，这个数字是最好的健康检查。
4. **归因窗口意识** - 平台报告点击/查看窗口并归因于广告的点击日期，您的数据库报告订单日期。跨天比较永远不会完全匹配；比较 7 天以上的窗口。

如果平台为您提供广告级报告 API（Facebook、Google Ads 和 TikTok 都提供；Bing 没有在转化 API 旁边暴露一个），每周手动进行这种核对无法扩展到少量活动——按计划自动拉取广告级支出、点击和平台报告的转化，并与其他订单表进行差异比较，而不是每个平台一个数字。

## 服务器端跟踪无法修复的问题

与利益相关者明确这一点，因为这里的期望通常是不正确的：

- 它不能恢复 *用户级* 跨站跟踪。它改进了转化 *报告和匹配*，而不是身份解析。
- 它不能使平台数字相互一致。每个平台都在其归因模型下声称获得信用，因此跨平台的总和将超过实际订单。只有您自己的订单表才是绝对真实。
- 它不能修复同意。同意和区域隐私要求仍然适用于服务器端发送；哈希的 PII 仍然是 PII。不要将服务器端报告作为绕过同意决定的一种方式。

## 实现它

如果漏斗在托管平台上，这通常是一个付费集成加上一个标签管理容器，并且跨域点击 ID 传递通常是您无法控制的部分。

[Autonnel](https://github.com/autonnel/autonnel)（Apache-2.0，自托管）原生实现了七个步骤链：点击 ID 和 UTMs 在着陆页上捕获到服务器端漏斗会话中，跨域漏斗步骤中传递，写入订单，并作为排队的服务器端转化发送到 Facebook（转化 API）、TikTok（事件 API）、Google Ads 和 Bing（CAPI），每个平台的映射在管理 UI 中配置。

它还为您在 Facebook、Google Ads 和 TikTok 上执行步骤 7：连接一个广告账户（OAuth，集成在核心中，无需插件或购买）会触发每小时拉取该账户的广告级支出、展示次数、点击和转化，按漏斗进行归因，通过匹配每个广告的目标 URL 并在管理 UI 中与漏斗自己的订单进行核对——平台报告的数字与您自己的数字并列，差异被评级和解释，而不是单方面被无声覆盖。Bing 没有与转化 API 并置的广告级报告 API，因此它仍然按照上述验证清单手动操作。

从 <https://github.com/autonnel/autonnel>（Apache-2.0）获取存储库，检查一个发布标签，并阅读其 `docker-compose.yml`——它声明了将要运行的镜像和端口。从该存储库检出：

```bash
docker compose up
# 打开 http://localhost:4321，完成 /setup，然后设置 → 广告
```

对于生产，它部署到 Cloudflare Workers，在那里排队回传交付和每小时广告报告同步都运行在存储库中提供的 cron 处理程序。确认 cron 触发器在部署后幸存，否则排队转化和广告支出同步都将无声停止。

在连接凭证后，在扩展支出之前运行上述验证清单。第一天要关注的数字是点击 ID 覆盖率。
