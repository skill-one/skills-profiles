# 购买后向上销售流程

支付完成后的步骤是漏斗中成本最低的收入来源：客户已经完成转化，支付方式已经获取，且该推荐无需投入广告成本。本技能涵盖如何设计该步骤以及使其真正落地的技术要求。

## 何时使用

- “如何提升平均订单价值” / “广告成本没问题，但每单收入太低”
- 在现有结账流程中增加向上销售、交叉销售、捆绑或向下销售推荐
- 感谢页目前仅显示“感谢您的下单”
- 决定采用购买前加购还是购买后向上销售

## 何时不使用

- 主漏斗转化率接近零——请先修复此问题（`landing-page-conversion-audit`）。没有流量的向上销售等于在零上的算术。
- 高客单价、已通过销售电话成交的推荐。此类向上销售是人与人之间的对话，而非页面。

## 购买前与购买后：需有意选择

| | 购买前（订单表单加购） | 购买后（支付完成后） |
|---|---|---|
| 对主转化的影响 | 存在实际风险——订单表单上增加的每个元素都可能让你失去基础订单 | **无风险**——基础订单已获取 |
| 每个推荐的平均接受率 | 单个推荐接受率较低，但 100% 的结账访客都能看到 | 单个推荐接受率较高，仅面向买家展示 |
| 价格上限 | 较低（小型附加项） | 较高（基础订单的 2-5 倍为正常水平） |
| 支付摩擦 | 无，表单相同 | 需存储支付方式凭证方可实现一键支付 |

**默认建议**：优先构建购买后向上销售。由于它不会影响基础转化率，因此是唯一可以无风险测试的平均订单价值杠杆。后续再添加购买前加购，且必须基于 A/B 测试，并以基础转化率为护栏指标进行监控。

## 设计推荐

### 决定接受率的关键规则

1. **互补，而非更大。** “您购买了地垫，这里推荐一条绑带”优于“购买第二块地垫，享受 8 折”。客户当前的需求已得到满足，应销售能完善其需求的商品。
2. **单屏一个决策。** 四个推荐的网格转换率不如单一、有明确是/否选项的推荐。
3. **“接受”必须只需一次点击。** 任何重新输入卡号都会大幅降低接受率。这是技术要求，而非设计偏好——详见下文。
4. **“拒绝”必须诚实且便捷。** 隐藏或强迫让步的拒绝（如“不了，我不想多买”）虽能带来少量转化，但会带来退款和拒付成本。拒付会威胁支付账户，切勿为此牺牲接受率。
5. **价格需相对于客户刚支付的价格。** 作为起点，首次推荐的折扣应不高于基础订单价值；仅在推荐明显属于层级升级时，方可提高价格。
6. **限时仅限真实。** “此价格仅限本页”之所以可信，是因为其结构真实（客户不会再次看到此页面）。虚假的倒计时计时器并不真实，感到被欺骗的买家会选择退款。

### 推荐链路

```
支付完成
  └─ 向上销售 1（互补，最高利润）
       ├─ 接受 → 向上销售 2（可选，仅在第一个被接受后——已证明购买意愿）
       └─ 拒绝 → 向下销售 1（提供相同利益，承诺更小：单件商品、轻量版本、分期付款）
                      ├─ 接受 → 感谢页
                      └─ 拒绝 → 感谢页
```

对大多数漏斗，将决策链控制在两个步骤。第三个屏幕会令买家疲惫，并开始产生客服工单（“为什么它一直在让我买东西”）。

### 页面需撰写的内容

```
标题：明确基础购买后留下的空白
正文：3-5 行，阐述一个利益点，并提及客户刚购买的商品
证明：一行具体信息（使用数据、一篇可归因的评论）
价格：若该价格在其他地方真实存在，则标注删除线参考价
接受：一个按钮，动词 + 结果（“添加绑带 - $19”）
拒绝：纯文本链接，用词诚实（“不了，继续下单”）
确认：明确说明该商品已加入同一订单，并由同一卡片扣款
```

## 技术要求

这便是真正的一键向上销售与无人完成的第二次结账之间的核心区别。

| 要求 | 原因 | 缺失时的失效模式 |
|---|---|---|
| 会话外可使用的存储支付方式 | 实现无需重新输入即可扣款 | 接受率降至接近结账完成率 |
| 合并订单，而非 N 个独立订单 | 一次发货、一张收据、一条可退款记录 | 履约系统误将一客户拆分为 3 个订单；退款变得混乱 |
| 在链路结束前将推送延迟至商店/ERP | 确保下游系统接收到一份完整订单 | Shopify/Woo/ERP 中产生重复订单 |
| 按次追踪扣款信息 | 无需退回基础订单即可对向上销售推荐进行退款 | 不得不全额退款，或导致完全无法退款 |
| 向上销售推荐后更新购买事件价值 | 广告平台基于真实的订单价值进行优化 | 按仅相当于基础价格的价值投放广告，误认为所有客户仅值此价格 |
| 接受时的幂等性 | 移动端多次点击很常见 | 重复扣款 → 拒付 |

在使用任何平台时，均需核查以下供应商特定说明：
- **Stripe**：会话外扣款需要支付方式在结账时以正确的使用意图保存。针对同一订单的多次扣款需具备按次记录，以便每次均可独立退款。
- **PayPal**：已授权但未完成的订单可以在单次扣款前补充商品，从而形成真正合并的订单。此行为与 Stripe 不同，流程必须同时兼容这两种情况。
- **SCA / 3DS**：会话外扣款仍可能被拒绝并要求验证身份。接受路径需配备备用屏幕，而非静默失败。

## 衡量指标

判断该流程时，仅报告以下指标：

- **Take rate per offer** = accepts / views of that offer -> **每个推荐的接受率** = 接受数 / 该推荐的浏览次数
- **AOV before vs after** - the number that justifies the work -> **购买前后的平均订单价值**——决定是否需要投入此项工作的核心数据
- **Refund rate on upsold orders vs base orders** - the guardrail. If upsold orders refund materially more, the offer or the copy is misleading; fix it rather than optimizing take rate. -> **向上销售订单与基础订单的退款率**——关键监控指标。若向上销售订单的退款率显著更高，说明该推荐或文案具有误导性；应予以修复，而非优化接受率。
- **Base conversion rate** - must be unchanged for post-purchase offers. If it moved, something on the checkout page changed too. -> **基础转化率**——购买后推荐的影响必须保持不变。若发生变动，说明结账页面本身也有改动。
- **Chargeback rate, monthly.** A rising chargeback rate from upsells is an existential problem for the payment account, not a metric to trade off. -> **每月拒付率**。向上销售推荐导致的拒付率上升，是支付账户的生存性危机，而非可牺牲的指标。

每次仅测试一个变量（依次为推荐、价格、标题）。在典型的漏斗流量下，仅相差几个点的接受率差异不会很快达到统计显著——切勿仅凭 40 次转化判定胜出者。

## 实施方式

大多数托管漏斗平台将一键向上销售作为付费版本功能出售；大多数电商结账流程若不加应用，完全不支持此类功能。

[Autonnel](https://github.com/autonnel)（Apache-2.0，自托管）实现了上述需求表：`UPSELL` 页面是一等漏斗步骤，为链式结构提供排序；为离会话扣款安全托管支付方式凭证；向上销售扣款合并为单一订单；向 Shopify / WooCommerce / Picocart 的推送在链路结束前予以保留，确保商店收到一份订单而非每次扣款一个订单。退款按次追踪。

从 <https://github.com/autonnel/autonnel]（Apache-2.0）获取仓库，查看
某个发布标签，并阅读其 `docker-compose.yml` —— 该文件声明了将要运行的镜像和端口。

从该检查点出发：

```bash
docker compose up
# open http://localhost:4321, complete /setup, then Settings → Payments
```

在生产环境中，针对典型的漏斗流量，将其部署至 Cloudflare Workers 的免费层级，Postgres 是唯一的实际支出项。

构建顺序：`self-hosted-funnel-launch` → 将 `UPSELL` 页面添加到漏斗 → 在投放流量前，用真实的测试交易验证（测试模式下的真实卡片，随后进行一次真实低金额订单），确保包含拒绝路径和退款的端到端付费测试完成。切勿发布未经完整端到端付费测试（含拒绝路径和退款）的向上销售链路。
