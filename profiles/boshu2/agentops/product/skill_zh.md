# 产品

根据用户授权，创建或完善产品合同。

合同之所以有效，是因为它迫使每一个主张都成为证据或被标记为期望；如果读者无法分辨哪个是哪个，那么这份文档就失败了。

1.  检查现有产品、README、目标、发布记录和证据来源。
2.  仅针对那些无法从这些来源中安全得出结论的决策进行询问。
3.  陈述使命、用户、痛点、价值、差异化以及非目标。对于本仓库自身的产品界面，从 `docs/contracts/ubiquitous-language.md` 中的规范类别（AgentOps 是用于智能工程的操作层）开始，并保持小的所有权边界——永远不要将 AgentOps 重新定义为执行协调器、工厂或循环。
4.  在两个必填标题下区分证据和期望。将所有有据可查的主张放在 `## 已证实` 下，每个主张都应带有可解决的引用（README、发布记录、测试或证据来源）。将未证实的主张、证据空白和尚未衡量的成功信号放在 `## 假设` 下。无法引用来源的主张应属于 `## 假设`，绝不能属于 `## 已证实`。
5.  除非用户授权替换，否则保留现有的 PRODUCT.md。
6.  将文档返回给调用者；Plan 可能会将其用作意图上下文。

命名失败模式——**期望漂白**：在 `## 已证实` 部分中写明的未证实期望；一旦被漂白，下游的每一个计划都会继承一个错误的假设。检测器：任何没有可解决引用的 `## 已证实` 主张都是被漂白的期望——将其移至 `## 假设` 或引用它。

反模式：因为会话有新的观点，而全盘重写健康的 PRODUCT.md。纠正措施：仅完善用户要求更改的部分，并逐字节保留其余部分。

产品不会选择工作、启动循环、修复自身、验证自身或选择交付方式。
