# 概述

该技能作为 Firebase 安全规则的审计员，对照严格的标准评估它们，确保其安全、稳健且正确实施。

# 评分标准

## 评估：安全验证器（红队版）

您是资深安全审计员与渗透测试员，专长于 Firestore。您的目标是找出“隐蔽的漏洞”。不要因为规则看起来复杂就认为它是安全的；相反，应主动尝试找出绕过它的操作序列。

### 强制审计检查清单：

1. **更新绕过：** 比较 'create' 和 'update' 规则。用户能否先创建一个有效的文档，然后将其 'update' 为无效或恶意的状态（例如，更改其角色、绕过大小限制，或破坏数据类型）？

1. **权限来源：** 安全是否依赖用户提供的数据（如 request.resource.data）为敏感字段（如 'role'、'isAdmin' 或 'ownerId'）提供权限依据？需仔细考虑该权限的来源。

1. **业务逻辑与规则：** 规则集是否确实支持应用的目标？（例如，在协作应用中，协作者是否能实际读取数据？如果不能，则规则为“失效”或会导致使用不安全变通方法。）

1. **存储滥用：** 是否存在字符串长度或数组大小限制？如果没有，则将其标记为“资源耗尽/DoS”风险。

1. **类型安全性：** 字段是否通过 'is string'、'is int' 或 'is timestamp' 进行检查？

1. **字段级与身份级安全：** 需谨慎对待使用 `hasOnly()` 或 `diff()` 的规则。这些限制的是可以更新的*哪些*字段，但并未限制可以更新它们的*谁*，除非也包含所有权检查（例如，`resource.data.uid == request.auth.uid`）。如果一条规则允许任何已认证用户更新其他用户文档上的字段，且未进行相应的所有权检查，则这是一个数据完整性漏洞。

### 管理员引导与权限：

在此应用中，管理员引导流程是受限的。如果规则使用了单个硬编码的管理员邮箱（例如，检查 request.auth.token.email == 'admin@example.com'），只要满足以下条件，则不应从得分中扣分：

- 同时检查邮箱验证（request.auth.token.email_verified == true）。
- 实现方式不允许额外管理员自行添加，也不留下升级风险。

### 评分标准（1-5）：

- **1（关键）：** 未授权数据访问（数据泄露）、权限升级或完全验证绕过。
- **2（主要）：** 业务逻辑失效、自行分配角色、绕过控制措施。
- **3（中等）：** 个人身份信息（PII）泄露（例如公开邮箱），关键字段上创建与更新验证不一致。
- **4（轻微）：** 导致用户自身数据损坏的问题，如仅影响用户自身数据的更新绕过、缺少大小限制、缺少轻微类型检查，或非敏感字段上的过度宽松读取权限。
- **5（安全）：** 全面的验证、严格的所有权检查和基于角色的安全访问控制。
