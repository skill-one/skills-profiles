# 利益相关者更新

> 如果你看到不熟悉的占位符或需要检查哪些工具已连接，请参阅[CONNECTORS.md](../../CONNECTORS.md)。

根据受众和节奏生成定制化的利益相关者更新。

## 使用方法

```
/stakeholder-update $ARGUMENTS
```

## 工作流程

### 1. 确定更新类型

询问用户更新类型：
- **每周**：常规节奏的进展、障碍和下一步行动更新
- **每月**：高级别的总结，包括趋势、里程碑和战略一致性
- **发布**：功能或产品发布的公告，包括详细信息和影响
- **临时**：针对特定情况的单次更新（升级、转向、重大决策）

### 2. 确定受众

询问更新对象是谁：
- **高管 / 领导层**：高级别、结果导向、战略框架、简短
- **工程团队**：技术细节、实施背景、障碍、需要做出的决策
- **跨职能合作伙伴**：适当的详细内容、关注共同目标和依赖关系
- **客户 / 外部**：利益导向、清晰的路线图、无内部术语
- **董事会**：指标驱动、战略、风险导向、非常简洁

### 3. 从已连接工具中提取上下文

如果**~~项目追踪器**已连接：
- 提取路线图项和里程碑的状态
- 识别自上次更新以来完成的项
- 提取有风险或被阻塞的项
- 提取冲刺或迭代进度

如果**~~聊天**已连接：
- 搜索相关的团队讨论和决策
- 查找渠道中提出的障碍或问题
- 识别异步做出的关键决策

如果**~~会议记录**已连接：
- 提取最近的会议笔记和讨论摘要
- 查找相关会议中的决策和行动项

如果**~~知识库**已连接：
- 搜索最近的会议笔记
- 查找决策文件或设计评审

如果没有工具连接，请询问用户：
- 自上次更新以来完成了什么
- 当前障碍或风险
- 做出的或需要的关键决策
- 下一步是什么

### 4. 生成更新

使用以下模板和框架，为目标受众构建更新。

**针对高管**：简明扼要、状态颜色（绿/黄/红）、与目标相关的关键进展、做出的决策、风险及缓解措施、具体请求和下一个里程碑。保持在300字以内。

**针对工程团队**：已发布的内容（带链接）、进行中的内容（带负责人）、障碍、需要的决策（带选项和建议）、接下来要做什么。

**针对跨职能合作伙伴**：影响他们的即将到来的内容、他们需要准备的内容（带截止日期）、影响他们团队的决策、开放供输入的领域。

**针对客户**：新内容（以利益为导向）、即将到来、已知问题及解决方案、如何提供反馈。无内部术语。

**针对发布公告**：已发布的内容、为什么重要、关键细节（范围、可用性、限制）、成功指标、发布计划、反馈渠道。

### 5. 审查和交付

生成更新后：
- 询问用户是否需要调整语气、详细程度或重点
- 提供格式化交付渠道（电子邮件、聊天帖子、文档、幻灯片）
- 如果**~~聊天**已连接，提供发送消息的草稿

## 根据受众的更新模板

### 高管 / 领导层更新
高管希望：战略背景、与目标的进展、需要他们帮助的风险、需要他们输入的决策。

**格式**：
```
状态：[绿色 / 黄色 / 红色]

简明扼要：[一句话——最重要的信息]

进展：
- [已实现的成果，与目标/OKR相关]
- [达成的里程碑，带影响]
- [关键指标变化]

风险：
- [风险]：[缓解计划]。[如果需要帮助]。

需要决策：
- [决策]：[选项和建议]。需在[日期]前。

下一个里程碑：
- [里程碑]——[日期]
```

**高管更新的技巧**：
- 先结论，后过程。高管希望“我们发布了X，它推动了Y指标”，而不是“我们开了14个站立会议，解决了23个工单。”
- 保持在200字以内。如果他们想了解更多，他们会问。
- 状态颜色应反映你真实的评估，而不是你认为他们想听到的。黄色不是失败——它是良好的风险管理。
- 只包括你希望帮助的风险。除非他们需要知道，否则不要列出你已经处理的风险。
- 请求必须具体：“周五前对X做出决策”，而不是“需要支持”。

### 工程团队更新
工程师希望：明确的优先级、技术背景、解决的障碍、影响他们工作的决策。

**格式**：
```
已发布：
- [功能/修复]——[链接到PR/工单]。[如果影响显著，请说明]。

进行中：
- [项]——[负责人]。[预期完成]。[如果有障碍，请说明]。

决策：
- [已做出的决策]：[理由]。[如果存在，请链接到ADR]。
- [需要的决策]：[背景]。[选项]。[建议]。

优先级变化：
- [什么变了，为什么]

即将到来：
- [下一个项]——[为什么这些是下一个的背景]
```

**工程更新的技巧**：
- 链接到具体的工单、PR和文档。工程师希望点击查看详细信息。
- 当优先级变化时，解释原因。工程师在理解原因时更容易接受。
- 明确说明什么在阻塞他们，以及你正在做什么来解除阻塞。
- 不要浪费他们时间在不会影响他们工作的信息上。

### 跨职能合作伙伴更新
合作伙伴（设计、营销、销售、支持）希望：影响他们的即将到来的内容、他们需要准备的内容（带截止日期）、如何提供输入。

**格式**：
```
即将到来：
- [功能/发布]——[日期]。[这对你的团队意味着什么]。

我们需要你：
- [具体请求]——[背景]。在[日期]前。

已做出的决策：
- [决策]——[如何影响你的团队]。

开放供输入：
- [我们希望获得反馈的领域]——[如何提供反馈]。
```

### 客户 / 外部更新
客户希望：新内容、即将到来、如何受益、如何开始使用。

**格式**：
```
新内容：
- [功能]——[客户术语中的利益]。[如何使用它/链接]。

即将到来：
- [功能]——[预期时间]。[这对你的重要性]。

已知问题：
- [问题]——[状态]。[如有，请提供解决方案]。

反馈：
- [如何分享反馈或请求功能]
```

**客户更新的技巧**：
- 无内部术语。无工单号。无技术实施细节。
- 用客户能做什么来描述，而不是你建造了什么。
- 诚实说明时间线，但不要过度承诺。“本季度稍后”比可能错过日期更好。
- 只有在问题影响客户且你有解决方案计划时才提及已知问题。

## 状态报告框架

### 绿色 / 黄色 / 红色状态

**绿色**（按计划进行）：
- 按计划进行
- 没有重大风险或障碍
- 按时完成承诺和截止日期
- 当事情真的进展顺利时使用绿色——不要作为默认状态

**黄色**（有风险）：
- 进度比计划慢，或风险已出现
- 正在缓解，但结果不确定
- 可能需要干预或调整范围才能按时完成
- 主动使用黄色——越早标记风险，你拥有的选择就越多

**红色**（偏离计划）：
- 明显落后于计划
- 有重大障碍或风险，没有明确的缓解措施
- 没有重大干预（范围削减、资源增加、时间线延长）将无法按时完成
- 当你确实需要帮助时使用红色。不要等到太晚。

### 何时更改状态
- 在第一次出现风险时立即更改为黄色，而不是当你确定事情很糟糕时
- 当你耗尽所有选项并需要升级时更改为红色
- 只有在风险真正解决时才恢复为绿色，而不仅仅是暂停
- 更改状态时记录发生了什么——“由于[原因]更改为黄色”

## 风险沟通

### 风险管理的ROAM框架
- **已解决**：风险不再是问题。记录如何解决的。
- **已承担**：风险已被承认，有人正在积极管理它。说明负责人和缓解计划。
- **已接受**：风险已知，但我们选择不缓解而继续进行。记录理由。
- **已缓解**：已采取措施将风险降低到可接受水平。记录做了什么。

### 有效沟通风险
1. **明确说明风险**：“存在[事情]发生的风险，因为[原因]”
2. **量化影响**：“如果发生这种情况，后果是[影响]”
3. **说明可能性**：“这是[可能/可能/不可能]，因为[证据]”
4. **提出缓解措施**：“我们通过[行动]来管理这一点”
5. **提出请求**：“我们需要[具体帮助]以进一步降低此风险”

### 风险沟通中的常见错误
- 将风险隐藏在好消息中。当风险很重要时，先说风险。
- 含糊不清：“可能会有一些延迟”——指定什么、多长时间、为什么。
- 没有缓解措施地提出风险。每个风险都应该有一个计划。
- 等待太久。早期沟通的风险是规划输入。晚期沟通的风险是消防演习。

## 决策记录（ADRs）

### 架构决策记录格式
记录重要决策以供将来参考：

```
# [决策标题]

## 状态
[提议 / 已接受 / 已弃用 / 已被ADR-XXX取代]

## 背景
是什么情况需要做出决策？有哪些力量在起作用？

## 决策
我们决定什么？明确直接地陈述决策。

## 后果
这个决策有什么影响？
- 积极后果
- 消极后果或接受的权衡
- 这将在未来启用或阻止什么

## 考虑过的替代方案
评估了哪些其他选项？
对于每个选项：是什么，为什么被拒绝？
```

### 何时编写ADR
- 战略产品决策（目标市场细分、支持的平台）
- 重大技术决策（架构选择、供应商选择、自建与购买）
- 争议性决策，人们意见不一（记录理由以供将来参考）
- 限制未来选项的决策（选择技术、建立合作伙伴关系）
- 你预计人们会质疑的决策（在记忆犹新时记录背景）

### 决策记录技巧
- 在决策时立即编写ADR，而不是几周后
- 包括参与决策的人和最终拍板的人
- 丰富地记录背景——未来的读者没有今天的背景
- 即使是事后看来错误的决策，也可以记录——添加“被ADR-XXX取代”链接
- 保持简短。一页比五页更好。

## 会议主持

### 站立会议 / 每日同步
**目的**：暴露障碍、协调工作、保持势头。
**格式**：每个人分享：
- 自上次同步以来完成的成就
- 下一步要做什么
- 阻碍他们的内容

**主持技巧**：
- 保持15分钟。如果出现讨论，将其移至线下。
- 聚焦于障碍——这是站立会议最有价值的部分
- 跟踪障碍并跟进解决情况
- 如果没有同步内容，取消站立会议。尊重人们的时间。

### 冲刺 / 迭代计划
**目的**：为下一个冲刺承诺工作。就优先级和范围达成一致。
**格式**：
1. 回顾：上个冲刺已发布的内容、已携带的内容、已裁剪的内容
2. 优先级：这个冲刺最重要的东西是什么
3. 容量：团队能承担多少（考虑PTO、值班、会议）
4. 承诺：选择符合容量和优先级的积压项
5. 依赖关系：标记任何跨团队或外部依赖关系

**主持技巧**：
- 带来一个建议的优先级顺序。不要让团队从零开始排序。
- 反对过度承诺。承诺较少但可靠交付更好。
- 确保每个项都有明确的负责人和明确的验收标准。
- 标记范围不足或隐藏复杂性的项。

### 复盘
**目的**：反思做得好的地方、做得不好的地方，以及要改变的地方。
**格式**：
1. 设置场景：提醒团队目标并创造心理安全感
2. 收集数据：做得好的地方、做得不好的地方、令人困惑的地方
3. 产生见解：识别模式和根本原因
4. 做出决定：选择下一个冲刺尝试的1-3个具体改进
5. 结束：感谢人们提供诚实的反馈

**主持技巧**：
- 创造心理安全感。人们必须感到安全才能诚实。
- 聚焦于系统和流程，而不是个人。
- 限制为1-3个行动项。超过这个数，什么都不会改变。
- 跟进之前的复盘行动项。如果你从不跟进，人们会停止参与。
- 偶尔变换复盘格式，防止陈词滥调。

### 利益相关者评审 / 演示
**目的**：展示进展、收集反馈、建立一致性。
**格式**：
1. 背景：提醒利益相关者目标和他们上次看到的内容
2. 演示：展示已构建的内容。使用真实产品，而不是幻灯片。
3. 指标：分享任何早期数据或反馈
4. 反馈：结构化的提问和输入时间
5. 下一步：接下来要做什么以及下次评审的时间

**主持技巧**：
- 尽可能演示真实产品。幻灯片不是演示。
- 提问反馈收集：“你对X有什么反馈？”比“有什么想法？”更好
- 可视化地捕获反馈并承诺解决（或解释为什么不能解决）
- 设定关于在此阶段可采取行动的反馈的预期

## 输出格式

保持更新可扫描。使用粗体突出重点，使用项目符号创建列表。高管更新应少于300字。工程更新可以更长，但仍应结构化以供快速浏览。

## 技巧

- 利益相关者更新中最常见的错误是隐藏主要信息。从最重要的事情开始。
- 状态颜色（绿/黄/红）应反映现实，而不是乐观。黄色不是失败——它是良好的风险沟通。
- 请求应该是具体和可操作的。“我们需要帮助”不是一个请求。“我们需要在周五对X做出决策”是。
- 对于高管，用结果和目标来描述，而不是活动和任务。
- 如果有坏消息，先说。不要在好消息后隐藏它。
- 根据受众的注意力匹配长度。高管得到几个要点。工程团队得到他们需要的详细信息。
