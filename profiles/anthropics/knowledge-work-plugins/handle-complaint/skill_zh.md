通过链接两个技能来运行投诉解决工作流。读取投诉内容，收集上下文信息，起草回复，并提出解决方案以防止问题再次发生。

解析参数：
- `EMAIL_OR_TICKET_ID`（可选）— Gmail 会话 ID、HubSpot 工单 ID 或 "latest" 以获取最新的未解决投诉。如果省略，则要求所有者粘贴投诉文本。

## 第 1 步 — 加载投诉（ticket-deflector）

使用 `ticket-deflector` 技能工作流：

1. 如果提供了 ID：从 Gmail 或 HubSpot 拉取完整会话。
2. 如果是 "latest"：拉取最新的未解决 HubSpot 工单或标记为投诉/支持的 Gmail 会话。
3. 如果都不是：要求所有者直接粘贴投诉文本。
4. 识别：客户姓名、订单/账户信息、客户不满的内容、客户的要求。

## 第 2 步 — 拉取上下文

1. 在 HubSpot 中搜索客户的购买历史：过去的购买记录、之前的投诉、交易阶段、终身价值。
2. 在 PayPal 中搜索相关交易：订单状态、退款历史、争议状态。
3. 总结："这是一个 {新/老} 客户，在购买方面花费了 ${终身价值}，有 {0/N} 次之前的投诉。他们当前的问题是 {一句话}。"

## 第 3 步 — 起草回复（ticket-deflector）

使用 `ticket-deflector` 技能工作流为匹配语气的回复：

1. 根据严重程度和客户的历史起草回复：
   - 首次投诉且 LTV 高的客户 → 富有同情心、慷慨
   - 重复投诉的客户 → 专业、坚定、以解决方案为中心
   - 语气恶劣的客户 → 专业、简短、设定界限
2. 包括：确认、解释（如果已知）、解决方案提议、下一步。
3. 向所有者展示草稿。不要发送。

## 第 4 步 — 提出运营修复（customer-pulse）

1. 检查此投诉是否与已知主题匹配（来自之前的 `/customer-pulse-check` 运行或 HubSpot 中的类似投诉）。
2. 如果是模式： "这是本月第 {N} 次关于 {问题} 的投诉。考虑：{具体的运营变更}。"
3. 如果是孤例： "这看起来是一次孤例。未检测到模式。"

## 连接器故障

如果 Gmail 和 HubSpot 都无法访问，要求所有者粘贴投诉文本——该技能支持手动输入。如果 PayPal 缺失，则跳过交易查询并注明 "PayPal 未连接——订单状态不可用，仅根据投诉文本工作。"

## 审批关卡

- **未经所有者明确批准，不得发送回复。** 仅展示草稿。
- **不得自动发起退款或信用。** 提供选项；由所有者决定。
- **未经所有者确认，不得关闭工单或解决争议。**

## 输出

展示客户上下文总结、起草的回复以及任何基于模式的运营建议。询问："要发送此回复、编辑它，还是以其他方式处理？"
