# /ticket-triage

> 如果你看到不熟悉的占位符或需要检查哪些工具已连接，请参阅[CONNECTORS.md](../../CONNECTORS.md)。

对收到的支持工单或客户问题进行分类、优先级排序和路由。生成结构化的分诊评估，并提供建议的初始回复。

## 使用方法

```
/ticket-triage <工单文本、客户消息或问题描述>
```

示例：
- `/ticket-triage 客户说从今天早上开始他们的仪表板一直显示空白页面`
- `/ticket-triage 本月我的订阅被收取了两次`
- `/ticket-triage 用户无法连接他们的SSO — 在回调URL上收到403错误`
- `/ticket-triage 功能请求：他们希望将报告导出为PDF`

## 工作流程

### 1. 解析问题

读取输入并提取：

- **核心问题**：客户实际遇到了什么问题？
- **症状**：他们看到了什么具体行为或错误？
- **客户背景**：这个人是谁？是否有任何账户详情、计划级别或历史记录可用？
- **紧急信号**：他们是否被阻止？这是生产环境问题吗？影响了多少用户？
- **情绪状态**：沮丧、困惑、客观陈述、升级？

### 2. 分类和优先级排序

使用下方的分类税目和优先级框架：

- 分配一个**主要分类**（错误、使用指南、功能请求、账单、账户、集成、安全、数据、性能）和可选的次要分类
- 根据影响和紧急程度分配**优先级**（P1–P4）
- 确定问题映射到的**产品领域**

### 3. 检查重复和已知问题

在路由之前，检查可用资源：

- **~~支持平台**：搜索类似的开启工单或最近解决的工单
- **~~知识库**：检查已知问题或现有文档
- **~~项目追踪器**：检查是否存在现有的错误报告或功能请求

应用以下重复检测流程。

### 4. 确定路由

使用以下路由规则，根据分类和复杂性推荐哪个团队或队列应处理此问题。

### 5. 生成分诊输出

```
## 分诊：[单行问题摘要]

**分类**：[主要] / [如果适用，次要]
**优先级**：[P1-P4] — [简要理由]
**产品领域**：[领域/团队]

### 问题摘要
[2-3句客户遇到的问题摘要]

### 关键详情
- **客户**：[如果知道，姓名/账户]
- **影响**：[谁和什么受到影响]
- **解决方案**：[可用 / 不可用 / 未知]
- **相关工单**：[如果找到，链接到类似问题]
- **已知问题**：[是 — 链接 / 否 / 正在检查]

### 路由建议
**路由到**：[团队或队列]
**原因**：[简要理由]

### 建议的初始回复
[草拟对客户的首次回复 — 确认问题，
设定预期，如果可用则提供解决方案。
以下自动回复模板可作为起点。]

### 内部备注
- [任何对处理此问题的代理的附加背景信息]
- [如果是错误，请提供重现提示]
- [需要关注的升级触发条件]

### 6. 提供下一步操作

在展示分诊后：
- "需要我草拟完整回复给客户吗？"
- "我应该搜索更多此问题的背景信息吗？"
- "需要我检查这是否是追踪器中的已知错误吗？"
- "我应该升级这个问题吗？我可以使用/customer-escalation将其打包。"

## 分类税目

为每个工单分配一个**主要分类**和可选的**次要分类**：

| 分类 | 描述 | 信号词 |
|------|------|------|
| **错误** | 产品行为不正确或意外 | 错误、损坏、崩溃、无法工作、意外、错误、失败 |
| **使用指南** | 客户需要产品使用指导 | 如何、我可以、在哪里、设置、配置、帮助 |
| **功能请求** | 客户希望有不存在的能力 | 会很好、我希望、有任何计划、请求 |
| **账单** | 支付、订阅、发票或定价问题 | 收费、发票、支付、订阅、退款、升级、降级 |
| **账户** | 账户访问、权限、设置或用户管理 | 登录、密码、访问、权限、SSO、被锁定、无法登录 |
| **集成** | 与第三方工具或API连接问题 | API、webhook、集成、连接、OAuth、同步、第三方 |
| **安全** | 安全问题、数据访问或合规性问题 | 数据泄露、未经授权、合规性、GDPR、SOC 2、漏洞 |
| **数据** | 数据质量、迁移、导入/导出问题 | 缺失数据、导出、导入、迁移、错误数据、重复 |
| **性能** | 速度、可靠性或可用性问题 | 慢、超时、延迟、宕机、不可用、性能下降 |

### 分类确定提示

- 如果客户报告**同时**是错误和功能请求，错误是主要分类
- 如果由于错误而无法登录，分类是**错误**（不是账户）— 根本原因决定分类
- "以前可以工作，现在不行了" = **错误**
- "我希望它工作不同" = **功能请求**
- "如何让它工作？" = **使用指南**
- 不确定时，倾向于**错误** — 调查比忽略更好

## 优先级框架

### P1 — 关键
**标准**：生产系统宕机、数据丢失或损坏、安全漏洞、所有或大多数用户受影响。

- 客户完全无法使用产品
- 数据正在丢失、损坏或暴露
- 正在进行安全事件
- 问题正在恶化或范围扩大

**SLA预期**：1小时内回复。持续工作直至解决或缓解。每1-2小时更新一次。

### P2 — 高
**标准**：主要功能损坏、重要工作流程被阻塞、许多用户受影响、无解决方案。

- 核心工作流程被破坏，但产品部分可用
- 多个用户受影响或关键账户受影响
- 问题正在阻塞时间敏感的工作
- 没有合理的解决方案

**SLA预期**：4小时内回复。当天积极调查。每4小时更新一次。

### P3 — 中
**标准**：功能部分损坏、有解决方案、单个用户或小团队受影响。

- 功能无法正确工作，但有解决方案
- 问题不方便，但不阻塞关键工作
- 单个用户或小团队受影响
- 客户没有紧急升级

**SLA预期**：1个工作日内回复。3个工作日内解决或更新。

### P4 — 低
**标准**：轻微不便、外观问题、一般问题、功能请求。

- 不影响功能的外观或UI问题
- 功能请求和改进建议
- 一般性问题或使用指南查询
- 简单、有文档的解决方案的问题

**SLA预期**：2个工作日内回复。正常速度解决。

### 优先级升级触发条件

自动提高优先级，当：

- 客户等待时间超过SLA允许的时间
- 多个客户报告相同问题（检测到模式）
- 客户明确升级或提及高管参与
- 已有的解决方案停止工作
- 问题范围扩大（更多用户、更多数据、新症状）

## 路由规则

根据分类和复杂性路由工单：

| 路由到 | 条件 |
|------|------|
| **Tier 1（一线支持）** | 使用指南问题、已知问题有文档解决方案、账单查询、密码重置 |
| **Tier 2（高级支持）** | 需要调查的错误、复杂配置、集成故障排除、账户问题 |
| **工程** | 需要代码修复的确认错误、基础设施问题、性能下降 |
| **产品** | 需求量大的功能请求、设计决策、工作流程差距 |
| **安全** | 数据访问问题、漏洞报告、合规性问题 |
| **账单/财务** | 退款请求、合同纠纷、复杂账单调整 |

## 重复检测

在创建新工单或路由之前，检查重复：

1. **按症状搜索**：查找具有相似错误消息或描述的工单
2. **按客户搜索**：检查此客户是否对相同问题有开启的工单
3. **按产品领域搜索**：查找同一功能领域的最近工单
4. **检查已知问题**：与已记录的已知问题进行比较

**如果找到重复**：
- 将新工单链接到现有工单
- 通知客户这是一个正在跟踪的已知问题
- 将新报告中的任何新信息添加到现有工单
- 如果新报告增加紧迫性（更多客户受影响等），提高优先级

## 按分类的自动回复模板

### 错误 — 初始回复
```
感谢报告。我能理解[具体影响]会对你工作造成干扰。

我已将其记录为优先级[优先级]的问题，我们的团队正在调查。
[如果存在解决方案："同时，你可以[解决方案]。"]

我们将在[SLA时间]内更新你我们的发现。
```

### 使用指南 — 初始回复
```
问得好！[直接回答或链接到文档]

[如果更复杂："让我逐步指导你："]
[步骤或指导]

如果这有帮助，或者你有任何后续问题，请告诉我。
```

### 功能请求 — 初始回复
```
感谢你的建议——我能理解[能力]对你的工作流程的价值。

我已记录并分享给我们的产品团队。
虽然我不能承诺具体时间表，但你的反馈直接影响了我们的路线图优先级。

[如果存在替代方案："同时，你可能会发现[替代方案]对实现类似目标有帮助。"]
```

### 账单 — 初始回复
```
我理解账单问题需要及时处理。让我为你调查。

[如果直接："解决方案细节"]
[如果复杂："我现在正在审查你的账户，将在[时间]内给你答复。"]
```

### 安全 — 初始回复
```
感谢报告——我们认真对待安全问题，并立即正在审查。

我已将其升级到我们的安全团队进行调查。我们将在[时间]内与你更新我们的发现。

[如果需要行动："同时，我们建议[保护措施]。"]
```

## 分诊最佳实践

1. 在分类前阅读完整工单——后面的消息中的上下文经常改变评估
2. 按**根本原因**分类，而不仅仅是描述的症状
3. 不确定优先级时，倾向于更高——更容易降级而不是从错过SLA中恢复
4. 路由前始终检查重复和已知问题
5. 写内部备注，帮助下一个人快速获取上下文
6. 包括你已经检查或排除的内容，以避免重复调查
7. 标记模式——如果你看到重复出现相同问题，即使单个工单优先级低，也要升级模式
