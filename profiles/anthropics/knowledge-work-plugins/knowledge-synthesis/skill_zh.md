# 知识融合

企业搜索的最后一公里。从多个来源获取原始结果，并生成连贯、可信的答案。

## 目标

将以下内容转化为：

```
~~聊天结果："Sarah 在 #eng 中说：'让我们用 REST，GraphQL 对我们的用例来说过于复杂'"
~~邮件结果："主题：API 决策 — Sarah 的邮件确认 REST 方法及理由"
~~云存储结果："API 设计文档 v3 — 更新第 2 节以反映 REST 决策"
~~项目追踪结果："任务：最终确定 API 方法 — 由 Sarah 标记为完成"
```

转化为：

```
团队决定在 API 重构中使用 REST 而不是 GraphQL。Sarah 做出了决定，指出 GraphQL 对当前用例来说过于复杂。这周二在 #engineering 中讨论，周三通过邮件确认，设计文档已更新以反映该决定。相关的 ~~项目追踪任务已标记完成。

来源：
- ~~聊天：#engineering 讨论（1 月 14 日）
- ~~邮件："API 决策" 来自 Sarah（1 月 15 日）
- ~~云存储："API 设计文档 v3"（更新于 1 月 15 日）
- ~~项目追踪："最终确定 API 方法"（完成于 1 月 15 日）
```

## 去重

### 跨来源去重

相同的信息经常出现在多个地方。识别并合并重复内容：

**表明结果内容相同的信号：**
- 相同或非常相似的文字内容
- 相同的作者/发送者
- 时间戳在短时间内（同一天或相邻几天）
- 引用相同实体（项目名称、文档、决策）
- 一个来源引用另一个来源（"如 ~~聊天中讨论的"、"根据 ~~邮件"、"参见文档"）

**合并方法：**
- 合并为一个单一的故事条目
- 引用所有出现该内容的来源
- 使用最完整的版本作为主要文本
- 添加每个来源的独特细节

### 去重优先级

当相同信息存在于多个来源时，优先选择：
```
1. 最完整的版本（最丰富的上下文）
2. 最权威的来源（官方文档 > 聊天）
3. 最新的版本（最新更新对发展中的信息有效）
```

### 不去重的情况

当以下情况时保持为独立条目：
- 讨论相同主题但结论不同
- 不同的人表达不同观点
- 信息在来源之间有重要变化（决策的 v1 与 v2）
- 代表不同时间段

## 引用和来源归属

合成答案中的每一条声明都必须可归属于一个来源。

### 归属格式

内联引用直接来源：
```
Sarah 在周三的邮件中确认了 REST 方法。
设计文档已更新以反映这一点（~~云存储："API 设计文档 v3"）。
```

在末尾列出来源以保持完整性：
```
来源：
- ~~聊天：#engineering 讨论（1 月 14 日） — 初始决策线程
- ~~邮件："API 决策" 来自 Sarah Chen（1 月 15 日） — 正式确认
- ~~云存储："API 设计文档 v3" 最后修改于 1 月 15 日 — 更新规范
```

### 归属规则

- 始终标明来源类型（~~聊天、~~邮件、~~云存储等）
- 包括具体位置（频道、文件夹、线程）
- 包括日期或相对时间
- 在相关时包含作者
- 在可用时包含文档/线程标题
- 对于 ~~聊天，注明频道名称
- 对于 ~~邮件，注明主题行和发送者
- 对于 ~~云存储，注明文档标题

## 置信度级别

并非所有结果都同样可信。根据以下情况评估置信度：

### 新鲜度

| 新鲜度 | 置信度影响 |
|-------|-----------|
| 今天 / 昨天 | 高置信度（当前状态） |
| 本周 | 良好置信度 |
| 本月 | 中等 — 可能已变化 |
| 超过一个月 | 较低置信度 — 标记为可能过时 |

对于状态查询，应重点考虑新鲜度。对于政策/事实查询，新鲜度重要性较低。

### 权威性

| 来源类型 | 权威级别 |
|---------|---------|
| 官方维基 / 知识库 | 最高 — 经编辑维护 |
| 共享文档（最终版本） | 高 — 故意发布 |
| 邮件公告 | 高 — 正式沟通 |
| 会议记录 | 中高 — 可能不完整 |
| 聊天消息（线程结论） | 中等 — 非正式但实时 |
| 聊天消息（线程中段） | 较低 — 可能未反映最终立场 |
| 草稿文档 | 低 — 未最终确定 |
| 任务评论 | 上下文相关 — 取决于评论者 |

### 表达置信度

当置信度高（多个新鲜、权威来源一致）：
```
团队决定使用 REST 进行 API 重构。[直接陈述]
```

当置信度中等（单一来源或稍显陈旧）：
```
根据上个月 #engineering 的讨论，团队倾向于使用 REST 进行 API 重构。这可能自那时以来有所变化。
```

当置信度低（旧数据、非正式来源或冲突信号）：
```
我在 ~~聊天中找到一个三个月前的 API 迁移讨论参考，但找不到正式的决策文档。信息可能已过时。您可能需要向团队确认当前状态。
```

### 冲突信息

当来源不一致时：
```
我发现关于 API 方法的冲突信息：
- ~~聊天讨论（1 月 10 日）建议使用 GraphQL
- 但 Sarah 的邮件（1 月 15 日）确认了 REST
- 设计文档（更新于 1 月 15 日）反映了 REST

最新来源表明 REST 是最终决定，
但早期的 ~~聊天讨论首先探讨了 GraphQL。
```

始终展示冲突，而不是默默选择一个版本。

## 总结策略

### 对于小结果集（1-5 个结果）

提供每个结果的上下文。无需总结 — 给用户所有信息：
```
[直接从结果合成的答案]

[来源 1 的详细信息]
[来源 2 的详细信息]

来源：[完整归属]
```

### 对于中等结果集（5-15 个结果）

按主题分组并总结每个组：
```
[整体答案]

主题 1：[相关结果的总结]
主题 2：[相关结果的总结]

关键来源：[前 3-5 个最相关的来源]
完整结果：[数量] 项来自 [来源]
```

### 对于大结果集（15 个以上结果）

提供高级别的合成，并提供深入挖掘的选项：
```
[基于最相关结果的整体答案]

总结：
- [关键发现 1]（由 N 个来源支持）
- [关键发现 2]（由 N 个来源支持）
- [关键发现 3]（由 N 个来源支持）

主要来源：
- [最权威/相关的来源]
- [第二相关]
- [第三相关]

共找到 [总数] 个结果来自 [来源列表]。
需要我深入挖掘任何特定方面吗？
```

### 总结规则

- 以答案开头，而不是搜索过程
- 不要列出原始结果 — 将其合成成叙述
- 将来自不同来源的相关项目组合在一起
- 保留重要细节和注意事项
- 提供足够详细信息，让用户决定是否需要深入
- 如果结果集较大，始终提供更多细节的选项

## 合成工作流程

```
[所有来源的原始结果]
          ↓
[1. 去重 — 合并来自不同来源的相同信息]
          ↓
[2. 聚类 — 按主题/话题分组相关结果]
          ↓
[3. 排序 — 按查询相关性排序聚类和条目]
          ↓
[4. 评估置信度 — 新鲜度 × 权威性 × 一致性]
          ↓
[5. 合成 — 生成带归属的叙述性答案]
          ↓
[6. 格式化 — 根据结果数量选择适当的详细程度]
          ↓
[连贯的答案与来源]
```

## 反模式

**不要：**
- 按来源逐条列出结果（"来自 ~~聊天：... 来自 ~~邮件：... 来自 ~~云存储：..."）
- 仅因匹配关键词而包含不相关的结果
- 在方法说明下埋没答案
- 展示冲突信息而不标记冲突
- 遗漏来源归属
- 以与支持充分的 факты 相同的置信度呈现不确定信息
- 总结过于激进导致有用细节丢失

**要：**
- 以答案开头
- 按主题分组，而不是按来源
- 在适当时候标记置信度
- 明确展示冲突
- 将所有声明归属到来源
- 当结果集较大时提供深入挖掘的选项
