# /write-query - 编写优化后的 SQL 查询

> 如果你看到不熟悉的占位符或需要检查哪些工具已连接，请参阅 [CONNECTORS.md](../../CONNECTORS.md)。

根据自然语言描述编写 SQL 查询，针对你的特定 SQL 语法进行优化，并遵循最佳实践。

## 使用方法

```
/write-query <你需要的数据描述>
```

## 工作流程

### 1. 理解请求

解析用户的描述以识别：

- **输出列**：结果应包含哪些字段？
- **筛选条件**：哪些条件限制数据（时间范围、细分、状态）？
- **聚合操作**：是否有 GROUP BY 操作、计数、求和、平均值？
- **连接**：是否需要组合多个表？
- **排序**：结果应如何排序？
- **限制**：是否有 top-N 或采样要求？

### 2. 确定 SQL 语法

如果用户使用的 SQL 语法尚未知晓，询问他们使用哪种语法：

- **PostgreSQL**（包括 Aurora、RDS、Supabase、Neon）
- **Snowflake**
- **BigQuery**（Google Cloud）
- **Redshift**（Amazon）
- **Databricks SQL**
- **MySQL**（包括 Aurora MySQL、PlanetScale）
- **SQL Server**（Microsoft）
- **DuckDB**
- **SQLite**
- **其他**（请具体说明）

记住该语法，以便在同一会话中的后续查询中使用。

### 3. 发现模式（如果已连接数据仓库）

如果已连接数据仓库 MCP 服务器：

1. 根据用户的描述搜索相关表
2. 检查列名、类型和关系
3. 检查影响性能的分区键或聚簇键
4. 查找可能简化查询的预构建视图或物化视图

### 4. 编写查询

遵循以下最佳实践：

**结构：**
- 当查询包含多个逻辑步骤时，使用 CTE（WITH 子句）以提高可读性
- 每个逻辑转换或数据源使用一个 CTE
- 描述性地命名 CTE（例如，`daily_signups`、`active_users`、`revenue_by_product`）

**性能：**
- 生产查询中不要使用 `SELECT *` —— 只指定需要的列
- 尽早筛选（将 WHERE 子句尽可能推到基础表附近）
- 使用分区筛选器（尤其是日期分区）
- 对于具有大型结果集的子查询，优先使用 `EXISTS` 而不是 `IN`
- 使用适当的连接类型（当 INNER JOIN 适用时不使用 LEFT JOIN）
- 避免使用相关子查询，当连接或窗口函数可以工作时
- 注意避免爆炸连接（多对多）

**可读性：**
- 添加注释解释非明显逻辑的“原因”
- 使用一致的缩进和格式
- 使用有意义的短名称别名表（而不仅仅是 `a`、`b`、`c`）
- 将每个主要子句放在单独的一行

**特定语法的优化：**
- 应用特定语法的语法和函数（有关详细信息，请参阅 `sql-queries` 技能）
- 使用特定语法的日期函数、字符串函数和窗口语法
- 注意任何特定语法的性能特性（例如，Snowflake 聚簇、BigQuery 分区）

### 5. 展示查询

提供：

1. **完整的查询**，使用语法高亮显示的 SQL 代码块
2. **简要解释**每个 CTE 或部分的用途
3. **性能说明**（如果相关，例如预期成本、分区使用、潜在瓶颈）
4. **修改建议**——如何调整以适应常见变化（不同的时间范围、不同的粒度、附加筛选条件）

### 6. 提供执行选项

如果已连接数据仓库，提供运行查询和分析结果的服务。如果用户想自行运行，查询已准备好复制粘贴。

## 示例

**简单聚合：**
```
/write-query 过去 30 天按状态统计订单数量
```

**复杂分析：**
```
/write-query 群组留存分析——按用户注册月份分组，然后显示在注册后 1、3、6 和 12 个月仍活跃的用户百分比（至少有一次事件）
```

**性能关键：**
```
/write-query 我们有一个 5000 万行的事件表按日期分区。找出过去 7 天内事件数量最多的前 100 名用户及其最新事件类型。
```

## 小贴士

- 一开始就说明你的 SQL 语法，以立即获得正确的语法
- 如果你知道表名，请包含它们——否则 Claude 将帮助你找到它们
- 指定查询是否需要幂等性（安全重跑）或一次性
- 对于周期性查询，说明是否应参数化日期范围
