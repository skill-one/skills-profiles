# /draft-response

> 如果你看到不熟悉的占位符或需要检查哪些工具已连接，请参阅[CONNECTORS.md](../../CONNECTORS.md)。

根据情况、客户关系和沟通背景，起草一份专业的、面向客户的支持回复。

## 使用方法

```
/draft-response <关于客户问题、问题或请求的背景信息>
```

示例：
- `/draft-response Acme Corp 询问新仪表板功能何时发货`
- `/draft-response 客户升级——他们的集成已中断 2 天`
- `/draft-response 回应我们不会构建的功能请求`
- `/draft-response 客户遇到计费错误并希望立即获得解决方案`

## 工作流程

### 1. 理解背景

解析用户输入以确定：

- **客户**：沟通对象是谁？如果可用，请查找账户背景信息。
- **情况类型**：问题、问题、升级、公告、谈判、坏消息、好消息、跟进
- **紧急性**：这是否有时间敏感性？客户等待了多长时间？
- **渠道**：电子邮件、支持工单、聊天或其他（相应调整正式程度）
- **关系阶段**：新客户、已建立、沮丧/升级
- **利益相关者级别**：最终用户、经理、高管、技术、业务

### 2. 调查背景

从可用来源收集相关背景信息：

**~~电子邮件：**
- 与此客户就此主题的先前通信
- 之前共享的任何承诺或时间表
- 现有线程的语气和风格

**~~聊天：**
- 关于此客户或主题的内部讨论
- 来自产品、工程或领导层的任何指导
- 类似情况及其处理方式

**~~CRM（如果已连接）：**
- 账户详情和计划级别
- 联系信息和关键利益相关者
- 先前的升级或敏感问题

**~~支持平台（如果已连接）：**
- 相关工单及其解决方案
- 已知问题或解决方案
- SLA 状态和响应时间承诺

**~~知识库：**
- 官方文档或帮助文章以供参考
- 产品路线图信息（如果可共享）
- 政策或流程文档

### 3. 生成草稿

生成针对情况的回复：

```
## 草稿回复

**收件人：** [客户联系人姓名]
**主题：** [主题/话题]
**渠道：** [电子邮件 / 工单 / 聊天]
**语气：** [有同理心 / 专业 / 技术 / 庆祝 / 坦诚]

---

[草稿回复文本]

---

### 给您的笔记（内部——不要发送）
- **为何采用此方法：** [语气和内容选择的理由]
- **需要核实的事项：** [在发送前需要确认的任何事实或承诺]
- **风险因素：** [此回复中任何敏感事项]
- **需要跟进的事项：** [发送后的操作]
- **升级备注：** [如果此问题应先由他人审查]

```

### 4. 运行质量检查

在展示草稿之前，请核实：

- [ ] 语气与情况和关系相匹配
- [ ] 没有超出授权范围的承诺
- [ ] 没有不应对外部共享的产品路线图细节
- [ ] 准确引用了先前的对话
- [ ] 清晰的下一步行动和所有权
- [ ] 适合利益相关者级别（对高管来说不要太技术性，对工程师来说不要太模糊）
- [ ] 长度适合渠道（聊天较短，电子邮件较长）

### 5. 提供迭代版本

在展示草稿后：
- "想让我调整语气吗？（更正式、更随意、更有同理心、更直接）"
- "我应该添加或删除任何特定要点吗？"
- "想让我让这个更短/更长吗？"
- "我应该为不同的利益相关者起草一个版本吗？"
- "想让我也起草内部升级备注吗？"
- "我应该准备在 [X 天] 后如果没有回复，发送一条跟进消息吗？"

## 客户沟通最佳实践

### 核心原则

1. **以同理心为先**：在跳到解决方案之前，先承认客户的情况
2. **直接沟通**：直奔主题——客户很忙。开门见山。
3. **诚实**：从不夸大其词，从不误导，从不以术语隐藏坏消息
4. **具体**：使用具体细节、时间表和姓名——避免模糊语言
5. **承担责任**：在适当的时候承担责任。"我们"而不是"系统"或"流程"
6. **闭环**：每条回复都应该有明确的下一步行动或号召性用语
7. **匹配其能量**：如果他们沮丧，先表示同理心。如果他们兴奋，表现出热情。

### 回复结构

对于大多数客户沟通，请遵循此结构：

```
1. 确认/背景（1-2 句话）
   - 确认他们所说、所问或所经历的事情
   - 显示你理解他们的处境

2. 核心信息（1-3 段）
   - 提供主要信息、答案或更新
   - 具体且具体
   - 包括他们需要的相关信息

3. 下一步行动（1-3 个要点）
   - 你将做什么以及何时做
   - 他们需要做什么（如果有的话）
   - 下次何时会收到回复

4. 结尾（1 句话）
   - 热情但专业的结束语
   - 强调如果你需要帮助，你可以联系
```

### 长度指南

- **聊天/即时消息**：1-4 句话。立即切入重点。
- **支持工单回复**：1-3 短段落。结构化且易于扫描。
- **电子邮件**：最多 3-5 段。尊重他们的收件箱。
- **升级回复**：根据需要足够详细，但结构良好，带标题。
- **高管沟通**：越短越好。最多 2-3 段。数据驱动。

## 语气和风格指南

### 语气范围

| 情况 | 语气 | 特征 |
|------|------|------|
| 好消息/胜利 | 庆祝性 | 热情、温暖、祝贺、面向未来 |
| 例行更新 | 专业性 | 清晰、简洁、信息量、友好 |
| 技术回复 | 精确性 | 准确、详细、结构化、耐心 |
| 延迟交付 | 可靠性 | 诚实、道歉、行动导向、具体 |
| 坏消息 | 坦诚性 | 直接、有同理心、解决方案导向、尊重 |
| 问题/停机 | 紧迫性 | 立即、透明、可操作、令人安心 |
| 升级 | 高管级 | 镇定、承担责任、计划呈现、自信 |
| 计费/账户 | 精确性 | 清晰、事实、有同理心、解决方案导向 |

### 根据关系阶段调整语气

**新客户（0-3 个月）：**
- 更正式和专业
- 额外提供背景和解释（不要假设知识）
- 主动提供帮助和资源
- 通过可靠性和响应速度建立信任

**已建立客户（3 个月以上）：**
- 热情和协作
- 可以参考共享历史和之前的对话
- 更直接和高效的沟通
- 显示对他们目标和优先级的了解

**沮丧或升级客户：**
- 额外同理心和确认
- 响应时间紧迫
- 具体的行动计划和具体承诺
- 更短的反馈循环

### 写作风格规则

**要：**
- 使用主动语态（"我们会调查"而不是"这将被调查"）
- 使用 "I" 进行个人承诺，使用 "we" 进行团队承诺
- 指派行动时指定具体人员（"我们工程团队的 Sarah 将..."）
- 使用客户的术语，而不是内部术语
- 包括具体日期和时间，而不是相对术语（"2024 年 1 月 24 日星期五"而不是"几天内"）
- 使用标题或项目符号分隔长回复

**不要：**
- 使用企业术语或行话（"协同效应"、"利用"、"范式转变"）
- 将责任推给其他团队、系统或流程
- 使用被动语态以避免承担责任（"犯了错误"）
- 包括不必要的保留或含糊其辞，这会削弱信心
- 不必要地抄送人员——只包括需要参与对话的人员
- 过度使用感叹号（每封电子邮件最多一个，如果有的话）

## 情境特定方法

**回答产品问题：**
- 先直接回答
- 提供相关文档链接
- 如有必要，提供与正确资源连接的机会
- 如果你不知道答案：诚实地说，承诺找出答案，给出时间表

**回复问题或错误：**
- 确认这对他们工作的影响
- 说明你对此问题的了解及其状态
- 如有可用，提供解决方案
- 设定解决时间表预期
- 承诺定期更新

**处理升级：**
- 确认严重性和他们的沮丧情绪
- 承担责任（不要推卸或找借口）
- 提供明确的行动计划和时间表
- 确定负责解决的人员
- 如适用，提供会议或电话

**传达坏消息（功能停止、延迟、无法修复）：**
- 直接——不要隐藏消息
- 诚实解释原因
- 具体说明对他们的影响
- 提供替代方案或缓解措施
- 提供明确的下一步路线

**分享好消息（功能发布、里程碑、认可）：**
- 先强调积极结果
- 将其与他们的特定目标或用例联系起来
- 建议利用好消息的下一步行动
- 表达真诚的热情

**拒绝请求（功能请求、折扣、例外）：**
- 确认请求及其原因
- 诚实说明决定
- 解释原因，但不要轻视
- 如有可能，提供替代方案
- 留下未来对话的门

## 常见场景的回复模板

### 确认错误报告

```
嗨 [姓名]，

感谢您的报告——我可以看到 [具体影响] 对您的团队来说是多么令人沮丧。

我已确认问题并升级给我们的工程团队作为 [优先级级别]。目前我们知道的情况如下：
- [正在发生什么]
- [原因，如果已知]
- [解决方案，如果可用]

我将在 [具体日期/时间] 更新您解决时间表。
在此期间，[解决方案详情，如果适用]。

如果您有任何问题或如果这以其他方式影响了您，请让我知道。

最好的，
[您的姓名]
```

### 确认计费或账户问题

```
嗨 [姓名]，

感谢您联系此事——我理解计费问题需要立即关注，我想确保这个问题得到快速解决。

我查看了您的账户，看到的情况如下：
- [发生了什么——清晰的解释]
- [对他们账户的影响——费用、访问等]

我正在采取以下措施来修复此问题：
- [行动 1——带时间表]
- [行动 2——如果适用]

[如果立即修复： "这已纠正，您应在 [时间段] 内看到变化。"]
[如果需要调查： "我已将此升级给我们的计费团队，并在 [具体日期] 前给您更新。"]

对此造成的不便，我表示歉意。如果您有任何关于您账户的问题，请让我知道。

最好的，
[您的姓名]
```

### 回应您不会构建的功能请求

```
嗨 [姓名]，

感谢您分享此请求——我可以看到 [功能] 对 [他们的用例] 有价值。

我与我们的产品团队讨论了此事，我们近期没有计划构建此功能。主要原因是 [诚实、尊重的解释——例如，它服务于狭窄的用例，它与我们的架构方向冲突等]。

尽管如此，我想确保您的目标能够实现。以下是一些替代方案：
- [替代方案 1]
- [替代方案 2]
- [集成或解决方案，如果适用]

我还将您的请求记录在我们的反馈系统中，如果我们的方向发生变化，我会通知您。

这些替代方案对您的团队有用吗？我很乐意深入了解其中任何一个。

最好的，
[您的姓名]
```

### 停机或事件沟通

```
嗨 [姓名]，

我想直接联系您，告知您影响 [服务/功能] 的问题，我知道您的团队依赖于此。

**发生了什么：** [清晰的、非技术性解释]
**影响：** [它如何影响他们]
**状态：** [当前状态——调查中 / 已确定 / 修复中 / 已解决]
**解决时间预期：** [如果已知，请提供具体时间，或 "我们将每 X 小时更新一次"]

[如果适用： "在此期间，您可以 [解决方案]。"]

我正在亲自跟踪此问题，并在有解决方案时立即更新您。您也可以查看 [状态页面 URL] 获取实时更新。

对此造成的干扰，我表示歉意。我们对此事非常重视，并且 [如果已知，我们正在做什么来防止再次发生]。

[您的姓名]
```

### 在沉默后跟进

```
嗨 [姓名]，

我想跟进——我在 [日期] 发送了 [您发送的内容]，想确保它没有被淹没。

[简要提醒您需要从他们那里获得什么或您提供的帮助]

如果现在不方便，没关系——请告诉我何时更方便，我很乐意那时再联系。

最好的，
[您的姓名]
```

## 跟进和升级指南

### 跟进节奏

| 情况 | 跟进时间 |
|------|----------|
| 未回复的问题 | 2-3 个工作日 |
| 打开的支持问题 | 关键的每天，标准的 2-3 天 |
| 会议行动项 | 在 24 小时内（发送笔记），然后在截止日期时检查 |
| 一般性跟进 | 根据需要处理持续性问题 |
| 传达坏消息后 | 1 周检查影响和情绪 |

### 何时升级

**当升级给您的经理时：**
- 客户威胁要取消或大幅降级
- 客户要求超出您授权范围的例外
- 问题已超过 SLA 允许的未解决时间
- 客户要求与领导直接联系
- 您犯了需要高级别参与的错误

**当升级给产品/工程时：**
- 错误对客户的业务至关重要并阻止了他们的业务
- 功能差距导致竞争损失
- 客户有超出标准支持的独特技术要求
- 集成问题需要工程调查

**升级格式：**
```
升级：[客户姓名]——[一句话总结]

紧急性：[关键 / 高 / 中]
客户影响：[对他们来说什么坏了]
历史：[简要背景——2-3 句话]
我尝试了什么：[到目前为止采取的行动]
我需要什么：[需要的具体帮助或决策]
截止日期：[需要在此解决的时间]
```
