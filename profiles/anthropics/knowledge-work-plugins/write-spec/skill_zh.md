# 编写规范

> 如果你看到不熟悉的占位符或需要检查哪些工具已连接，请参阅 [CONNECTORS.md](../../CONNECTORS.md)。

编写功能规范或产品需求文档（PRD）。

## 使用方法

```
/write-spec $ARGUMENTS
```

## 工作流程

### 1. 理解功能

询问用户他们想要编写哪个功能的规范。接受以下任何一种输入：
- 功能名称（"SSO 支持"）
- 问题陈述（"企业客户不断要求集中式认证"）
- 用户请求（"用户希望将他们的数据导出为 CSV 格式"）
- 模糊的想法（"我们应该做些什么来改善新用户引导的流失"）

### 2. 收集背景信息

询问用户以下内容。要友好地沟通——不要一次性抛出所有问题。先问最重要的问题，然后逐步补充细节：

- **用户问题**：这个问题解决了什么？谁会遇到它？
- **目标用户**：这个功能服务于哪些用户群体？
- **成功指标**：我们将如何知道这个功能是否有效？
- **约束条件**：技术约束、时间表、监管要求、依赖关系
- **已有解决方案**：这个功能之前是否已被尝试过？是否存在现有解决方案？

### 3. 从已连接的工具中提取背景信息

如果 **~~项目追踪器** 已连接：
- 搜索相关的工单、史诗或功能
- 提取任何现有的需求或验收标准
- 确定对其他工作项的依赖关系

如果 **~~知识库** 已连接：
- 搜索相关的调研文档、之前的规范或设计文档
- 提取相关的用户调研结果
- 查找相关的会议记录或决策记录

如果 **~~设计** 已连接：
- 提取相关的模型图、线框图或设计探索
- 搜索与功能相关的设计系统组件

如果这些工具未连接，则完全基于用户提供的信息工作。不要要求用户连接工具——只需使用现有信息继续进行。

### 4. 生成 PRD

生成结构化的 PRD，包含以下部分。有关每个部分应包含内容的详细指导，请参阅下文中的 **PRD 结构**。

- **问题陈述**：用户问题、受影响者以及未解决该问题的后果（2-3 句话）
- **目标**：3-5 个与用户或业务指标相关的具体、可衡量的成果
- **非目标**：3-5 个明确不在范围内的内容，并简要说明每个非目标的理由
- **用户故事**：标准格式（"作为一个 [用户类型]，我想要 [功能] 以便 [收益]"），按角色分组
- **需求**：分类为必须实现（P0）、建议实现（P1）和未来考虑（P2），每个需求都附有验收标准
- **成功指标**：领先指标（变化快）和滞后指标（随时间变化），并附有具体目标
- **待解决问题**：未解决的问题，并标记需要回答的人（工程、设计、法律、数据）
- **时间表考虑**：硬性截止日期、依赖关系和分阶段实施

### 5. 审查和迭代

生成 PRD 后：
- 询问用户是否需要调整任何部分
- 提供扩展特定部分的选项
- 提供创建后续文档（设计简报、工程工单分解、利益相关者提案）

## PRD 结构

### 问题陈述
- 用 2-3 句话描述用户问题
- 谁会遇到这个问题以及频率
- 未解决该问题的成本（用户痛点、业务影响、竞争风险）
- 基于证据：用户调研、支持数据、指标或客户反馈

### 目标
- 功能应实现的 3-5 个具体、可衡量的成果
- 每个目标应回答："我们如何知道这个功能成功了？"
- 区分用户目标（用户获得什么）和业务目标（公司获得什么）
- 目标应该是成果，而不是产出（"将首次使用时间缩短 50%" 而不是 "构建新用户引导向导"）

### 非目标
- 功能明确不会做的 3-5 件事
- 版本中不在范围内的相邻功能
- 简要说明为什么每个非目标不在范围内（影响不够、太复杂、独立计划、时机不成熟）
- 非目标可防止实施过程中的范围蔓延，并设定利益相关者的预期

### 用户故事
用标准格式编写用户故事： "作为一个 [用户类型]，我想要 [功能] 以便 [收益]"

指南：
- 用户类型应具体到有实际意义（"企业管理员" 而不是 "用户"）
- 功能应描述他们想要完成什么，而不是如何完成
- 收益应解释 "为什么"——这个功能能带来什么价值
- 包括边缘案例：错误状态、空状态、边界条件
- 如果功能服务于多个角色，应包括不同类型的用户
- 按优先级排序——最重要的故事优先

示例：
- "作为一个团队管理员，我想要为我的组织配置 SSO，以便我的团队成员可以使用他们的企业凭证登录"
- "作为一个团队成员，我想要在访问登录页面时自动重定向到公司的 SSO 登录，以便我不需要记住单独的密码"
- "作为一个团队管理员，我想要看到哪些成员通过 SSO 登录，以便我验证推广是否有效"

### 需求

**必须实现（P0）**：没有这些，功能无法发布。这些代表了功能的最小可行版本。询问："如果我们删除这些，功能是否仍然解决了核心问题？" 如果不是，它们就是 P0。

**建议实现（P1）**：显著改善体验，但核心用例在没有它们的情况下也能工作。这些通常在发布后很快成为快速跟进。

**未来考虑（P2）**：明确不在 v1 范围内，但我们希望以支持它们的方式设计。记录这些可以防止未来出现导致它们难以实现的偶然架构决策。

对于每个需求：
- 清晰、无歧义地描述预期行为
- 包括验收标准（见下文）
- 注明任何技术考虑或约束
- 标记对其他团队或系统的依赖关系

### 待解决问题
- 在实施前或实施过程中需要答案的问题
- 每个问题标记需要回答的人（工程、设计、法律、数据、利益相关者）
- 区分阻塞问题（必须回答才能开始）和非阻塞问题（可以在实施过程中解决）

### 时间表考虑
- 硬性截止日期（合同承诺、活动、合规日期）
- 对其他团队工作或发布的依赖关系
- 如果功能太大无法在一个发布中完成，建议分阶段实施

## 用户故事编写

好的用户故事应该是：
- **独立**：可以独立开发和交付
- **可协商**：细节可以讨论，故事不是合同
- **有价值**：为用户带来价值（而不仅仅是团队）
- **可估算**：团队可以大致估算工作量
- **小**：可以在一个冲刺/迭代中完成
- **可测试**：有明确的方法验证其是否有效

### 用户故事中的常见错误
- 太模糊："作为一个用户，我想要产品更快"——具体应该更快什么？
- 解决方案导向："作为一个用户，我想要一个下拉菜单"——描述需求，而不是 UI 组件
- 没有收益："作为一个用户，我想要点击一个按钮"——为什么？它完成了什么？
- 太大："作为一个用户，我想要管理我的团队"——将其分解为具体功能
- 内部导向："作为工程团队，我们想要重构数据库"——这是一个任务，不是用户故事

## 需求分类

### MoSCoW 框架
- **必须实现**：没有这些，功能不可行。非协商。
- **应该实现**：对发布很重要但不是关键。高优先级的快速跟进。
- **可以考虑**：如果时间允许则理想。如果被删除不会延迟交付。
- **这次不会实现**：明确不在范围内。可能在未来的版本中重新考虑。

### 分类技巧
- 对 P0 要无情。必须实现列表越紧，发布越快，学习越快。
- 如果所有都是 P0，那么没有 P0。挑战每个必须实现："我们真的不能没有这个就发布吗？"
- P1 应该是你有信心很快会构建的内容，而不是愿望清单。
- P2 是架构保险——即使你现在不构建它们，它们也会指导设计决策。

## 成功指标定义

### 领先指标
发布后快速变化的指标（几天到几周）：
- **采用率**：有资格用户中尝试该功能的百分比
- **激活率**：完成核心操作的用戂数百分比
- **任务完成率**：成功完成目标的用戂数百分比
- **完成时间**：完成核心工作流所需时间
- **错误率**：用户遇到错误或死循环的频率
- **功能使用频率**：用户返回使用功能的频率

### 滞后指标
需要较长时间变化的指标（几周到几个月）：
- **留存影响**：这个功能是否提高了用户留存率？
- **收入影响**：它是否推动了升级、扩展或新收入？
- **NPS / 满意度变化**：是否改善了用户对产品的感受？
- **支持工单减少**：是否减少了支持负载？
- **竞争胜利率**：是否帮助赢得更多交易？

### 设定目标
- 目标应该是具体的："30 天内 50% 的采用率"，而不是 "高采用率"
- 基于可比功能、行业基准或明确假设设定目标
- 设定一个 "成功" 阈值和一个 "挑战" 目标
- 定义测量方法：什么工具、什么查询、什么时间窗口
- 指定何时评估：发布后 1 周、1 月、1 季度

## 验收标准

用 Given/When/Then 格式或清单格式编写验收标准：

**Given/When/Then**：
- Given [前提或背景]
- When [用户采取的操作]
- Then [预期结果]

示例：
- Given 管理员已为其组织配置了 SSO
- When 一个团队成员访问登录页面
- Then 他们会被自动重定向到组织的 SSO 提供商

**清单格式**：
- [ ] 管理员可以在组织设置中输入 SSO 提供商 URL
- [ ] 团队成员在登录页面上看到 "使用 SSO 登录" 按钮
- [ ] SSO 登录如果不存在则创建新账户
- [ ] SSO 登录如果电子邮件匹配则链接到现有账户
- [ ] 失败的 SSO 尝试显示清晰的错误消息

### 验收标准技巧
- 覆盖快乐路径、错误案例和边缘案例
- 具体说明预期行为，而不是实现方式
- 包括不应发生的情况（负面测试案例）
- 每个标准应该是独立可测试的
- 避免模糊词语："快"、"用户友好"、"直观"——具体说明这些意味着什么

## 范围管理

### 识别范围蔓延
范围蔓延发生在以下情况：
- 在规范批准后不断添加需求
- "小"的添加累积成一个显著更大的项目
- 团队构建了用户没有要求的功能（"趁我们在这里..."）
- 发布日期不断推迟而没有明确的重新范围
- 利益相关者添加需求而没有删除任何内容

### 防止范围蔓延
- 在每个规范中明确写非目标
- 要求任何范围添加都伴随着范围删除或时间表延长
- 在规范中明确区分 "v1" 和 "v2"
- 将规范与原始问题陈述进行对比——所有内容是否都服务于它？
- 限制调查时间："如果我们在 2 天内无法弄清楚 X，我们就删除它"
- 创建一个 "停车场" 来存放不在范围内的好想法

## 输出格式

使用 Markdown 并具有清晰的标题。保持文档可扫描——忙碌的利益相关者应该能够只通过标题和粗体文本来了解大意。

## 技巧

- 对范围要有自己的看法。紧密、定义明确的规范比广泛的模糊规范更好。
- 如果用户的想法太大无法在一个规范中完成，建议将其分解为多个阶段，并规范第一阶段。
- 成功指标应该是具体且可衡量的，而不是模糊的（"改善用户体验"）。
- 非目标是与目标同样重要的。它们可防止实施过程中的范围蔓延。
- 待解决问题应该是真正开放的——不要包括你可以从上下文中回答的问题。
