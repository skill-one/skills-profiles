# /kb-article

> 如果你看到不熟悉的占位符或需要检查哪些工具已连接，请参阅[CONNECTORS.md](../../CONNECTORS.md)。

从已解决的支持问题、常见问题或已记录的解决方案中起草一篇可发布的知识库文章。为可搜索性和自助服务结构化内容。

## 使用方法

```
/kb-article <已解决的问题、工单引用或主题描述>
```

示例：
- `/kb-article 如何配置 Okta 的 SSO — 上个月我为 3 位客户解决了这个问题`
- `/kb-article 工单 #4521 — 客户无法导出超过 10k 行的数据`
- `/kb-article 常见问题：如何设置 webhook 通知`
- `/kb-article 已知问题：在 Safari 16 上仪表板图表无法加载`

## 工作流程

### 1. 理解源材料

解析输入以识别：

- **问题是什么？** 原始问题、问题或错误
- **解决方案是什么？** 解决方案、替代方案或答案
- **谁受此影响？** 用户类型、计划级别或配置
- **这个问题有多常见？** 偶发问题或重复问题
- **哪种文章类型最合适？** 如何操作、故障排除、常见问题解答、已知问题或参考（见下文文章类型）

如果提供了工单引用，请查找完整上下文：

- **~~支持平台**：提取工单线程、解决方案和任何内部笔记
- **~~知识库**：检查是否已存在类似文章（更新还是创建新文章）
- **~~项目跟踪器**：检查是否有相关的错误报告或功能请求

### 2. 起草文章

使用下文提供的文章结构、格式标准以及可搜索性最佳实践：

- 遵循所选文章类型（如何操作、故障排除、常见问题解答、已知问题或参考）的模板
- 应用可搜索性最佳实践：客户语言标题、平实的开场白、确切的错误消息、常用同义词
- 保持可扫描性：标题、编号步骤、简短段落

### 3. 生成文章

带有元数据展示草稿：

```
## 知识库文章草稿

**标题：** [文章标题]
**类型：** [如何操作 / 故障排除 / 常见问题解答 / 已知问题 / 参考]
**分类：** [产品区域或主题]
**标签：** [可搜索标签]
**受众：** [所有用户 / 管理员 / 开发人员 / 特定计划]

---

[完整文章内容 — 使用下文相应的模板]

---

### 发布说明
- **来源：** [工单编号、客户对话或内部讨论]
- **需要更新的现有文章：** [如果与此内容重叠]
- **需要审阅的人：** [SME 或团队，如果技术准确性需要验证]
- **建议审阅日期：** [何时重新审视以确认准确性]
```

### 4. 提供下一步操作建议

生成文章后：
- "我检查一下知识库中是否已存在类似文章吗？"
- "我应该调整技术深度以适应不同的受众吗？"
- "我起草一篇配套文章（例如，与这篇故障排除指南一起的如何操作指南）？"
- "我应该创建一个仅限内部的版本，包含更多技术细节吗？"

## 文章结构和格式标准

### 通用文章元素

每篇 KB 文章都应包括：

1. **标题**：清晰、可搜索，描述结果或问题（不是内部术语）
2. **概述**：1-2 句话说明本文档涵盖的内容和目标受众
3. **正文**：适合文章类型的结构化内容
4. **相关文章**：链接到相关的配套内容
5. **元数据**：分类、标签、受众、最后更新日期

### 格式规则

- **使用标题（H2、H3）** 将内容分成可扫描的部分
- **使用编号列表** 用于顺序步骤
- **使用项目符号列表** 用于非顺序项
- **使用粗体** 用于 UI 元素名称、关键词和强调
- **使用代码块** 用于命令、API 调用、错误消息和配置值
- **使用表格** 用于比较、选项或参考数据
- **使用提示/注释** 用于警告、技巧和重要注意事项
- **保持段落简短** — 最多 2-4 句话
- **每节一个想法** — 如果一节涵盖两个主题，请拆分

## 为可搜索性写作

如果客户找不到文章，文章就毫无用处。优化每篇文章以供搜索：

### 标题最佳实践

| 好标题 | 坏标题 | 原因 |
|--------|--------|------|
| "如何配置 Okta 的 SSO" | "SSO 设置" | 具体包括客户搜索的工具名称 |
| "修复：仪表板显示空白页面" | "仪表板问题" | 包括客户遇到的症状 |
| "API 速率限制和配额" | "API 信息" | 包括客户搜索的特定术语 |
| "错误：导入数据时'连接被拒绝'" | "导入问题" | 包括确切的错误消息 |

### 关键词优化

- **包含确切的错误消息** — 客户会复制粘贴错误文本到搜索框
- **使用客户语言**，而不是内部术语 — "无法登录"而不是"身份验证失败"
- **包含常用同义词** — "删除/移除"、"仪表板/主页"、"导出/下载"
- **添加替代说法** — 从不同角度解决相同问题
- **使用产品区域标签** — 确保分类和标签与客户对产品的理解一致

### 开场白公式

用一句话重新表述问题或任务，使用平实的语言开始每篇文章：

- **如何操作**： "本指南将向您展示如何完成 X。"
- **故障排除**： "如果您看到 [症状]，本文档将解释如何修复它。"
- **常见问题解答**： "[客户用词的问题]？以下是答案。"
- **已知问题**： "一些用户正在遇到 [症状]。以下是我们知道的情况以及如何解决它。"

## 文章类型模板

### 如何操作文章

**目的**：完成任务的分步说明。

**结构**：
```
# 如何完成 [任务]

[概述 — 本指南涵盖的内容以及何时使用]

## 前提条件
- [开始前需要什么]

## 步骤
### 1. [操作]
[具体说明的指令]

### 2. [操作]
[指令]

## 验证是否成功
[如何确认成功]

## 常见问题
- [问题]：[解决方案]

## 相关文章
- [链接]
```

**最佳实践**：
- 每个步骤以动词开头
- 包含具体路径："转到设置 > 集成 > API 密钥"
- 提及每步后用户应该看到的内容（"您应该看到一个绿色的确认横幅"）
- 自己测试步骤或验证最近的工单解决方案

### 故障排除文章

**目的**：诊断和解决特定问题。

**结构**：
```
# [问题描述 — 用户看到的内容]

## 症状
- [用户观察到的内容]

## 原因
[为什么会发生 — 简洁的非术语解释]

## 解决方案
### 选项 1：[主要修复]
[步骤]

### 选项 2：[如果选项 1 不起作用的其他方案]
[步骤]

## 预防措施
[如何避免将来再次发生]

## 仍然有问题？
[如何获得帮助]
```

**最佳实践**：
- 以症状开头，而不是原因 — 客户搜索他们看到的内容
- 尽可能提供多个解决方案（首先提供最可能的修复方案）
- 包含一个"仍然有问题？"部分，指向支持
- 如果根本原因复杂，请保持面向客户的解释简单

### 常见问题解答文章

**目的**：对常见问题提供快速答案。

**结构**：
```
# [问题 — 使用客户语言]

[直接答案 — 1-3 句话]

## 详细信息
[如果需要，提供额外的背景、细微差别或解释]

## 相关问题
- [链接到相关常见问题解答]
- [链接到相关常见问题解答]
```

**最佳实践**：
- 在第一句话回答问题
- 保持简洁 — 如果答案需要逐步说明，则不是常见问题解答，而是如何操作
- 将相关常见问题解答分组并相互链接

### 已知问题文章

**目的**：记录已知错误或限制及其替代方案。

**结构**：
```
# [已知问题]：[简要描述]

**状态：** [调查中 / 替代方案可用 / 修复进行中 / 已解决]
**影响范围：** [谁/什么受影响]
**最后更新：** [日期]

## 症状
[用户体验]

## 替代方案
[绕过问题的步骤，或"没有替代方案"]

## 修复时间表
[预期修复日期或当前状态]

## 更新
- [日期]：[更新]
```

**最佳实践**：
- 保持状态最新 — 没有什么比过时的已知问题文章更能破坏信任
- 修复发布时更新文章并标记为已解决
- 如果已解决，请保留文章 30 天，以便仍在搜索旧症状的客户

## 审阅和维护周期

知识库如果没有维护就会退化。请遵循此计划：

| 活动 | 频率 | 谁负责 |
|------|------|--------|
| **新文章审阅** | 发布前 | 同行审阅 + SME 审阅技术内容 |
| **准确性审计** | 每季度 | 支持团队审阅高流量文章 |
| **过期内容检查** | 每月 | 标记 6 个月未更新的文章 |
| **已知问题更新** | 每周 | 更新所有打开的已知问题状态 |
| **分析审阅** | 每月 | 检查哪些文章的帮助性评分低或跳出率高 |
| **差距分析** | 每季度 | 确定没有 KB 文章的顶级工单主题 |

### 文章生命周期

1. **草稿**：已编写，需要审阅
2. **已发布**：可供客户使用
3. **需要更新**：标记为修订（产品变更、反馈或时间过长）
4. **已存档**：不再相关但保留以供参考
5. **已退役**：从知识库中移除

### 何时更新与创建新文章

**更新现有文章**时：
- 产品变更且步骤需要更新
- 文章基本正确但缺少细节
- 反馈表明客户对特定部分感到困惑
- 找到更好的替代方案或解决方案

**创建新文章**时：
- 新功能或产品区域需要文档
- 已解决的工单揭示空白 — 此主题没有文章
- 现有文章涵盖太多主题，应该拆分
- 不同受众需要以不同方式解释相同信息

## 链接和分类分类法

### 分类结构

将文章组织成与客户思维方式相匹配的层次结构：

```
入门指南
├── 账户设置
├── 首次配置
└── 快速入门指南

功能与如何操作
├── [功能区域 1]
├── [功能区域 2]
└── [功能区域 3]

集成
├── [集成 1]
├── [集成 2]
└── API 参考

故障排除
├── 常见错误
├── 性能问题
└── 已知问题

计费与账户
├── 计划和定价
├── 计费问题
└── 账户管理
```

### 链接最佳实践

- **从故障排除链接到如何操作**："有关设置说明，请参阅[如何配置 X]"
- **从如何操作链接到故障排除**："如果遇到错误，请参阅[Troubleshooting X]"
- **从常见问题解答链接到详细文章**："有关完整逐步说明，请参阅[指南 X]"
- **从已知问题链接到替代方案**：保持从问题到解决方案的链短
- **使用相对链接**在 KB 内部 — 它们比绝对 URL 在结构重组时更持久
- **避免循环链接** — 如果 A 链接到 B，B 不应链接回 A，除非两者都是真正有用的入口点

## KB 写作最佳实践

1. 为受挫且正在搜索答案的客户写作 — 要清晰、直接、有帮助
2. 每篇文章都应使用客户会输入的词语通过搜索找到
3. 测试您的文章 — 自己跟随步骤或让不熟悉主题的人跟随
4. 保持文章集中 — 一个问题，一个解决方案。如果文章变得太长，请拆分
5. 积极维护 — 错误的文章比没有文章更糟
6. 跟踪缺失内容 — 每个可以成为 KB 文章的工单都是内容空白
7. 衡量影响 — 没有流量或没有减少工单的文章需要改进或退役
