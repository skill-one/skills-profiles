# /customer-research

> 如果你看到不熟悉的占位符或需要检查哪些工具已连接，请参阅[CONNECTORS.md](../../CONNECTORS.md)。

针对客户问题、产品主题或与账户相关查询的多源研究。整合所有可用来源的发现，并附带明确的归属和置信度评分。

## 使用方法

```
/customer-research <问题或主题>
```

## 工作流程

### 1. 解析研究请求

确定需要哪种类型的研究：
- **客户问题**：客户提出需要答案的事情（例如，“我们的产品是否支持使用Okta进行SSO？”）
- **问题调查**：报告问题的背景（例如，“这个问题之前是否报告过？已知的解决方案是什么？”）
- **账户背景**：与特定客户的交往历史（例如，“上次Acme Corp询问此事时，我们告诉他们了什么？”）
- **主题研究**：与支持工作相关的通用主题（例如，“webhook重试逻辑的最佳实践”）

在搜索之前，明确你实际上在寻找什么：
- 这是一个有明确答案的事实性问题吗？
- 这是一个需要多个视角的背景性问题吗？
- 这是一个范围仍在定义中的探索性问题吗？
- 答案的受众是谁（内部团队、客户、领导层）？

### 2. 搜索可用来源

系统性地通过以下来源进行搜索，并根据已连接的内容进行调整。不要在第一个结果就停止——跨来源交叉验证。

**第一级 — 官方内部来源（最高置信度）：**
- ~~知识库（如果已连接）：产品文档、操作手册、常见问题解答、政策文件
- ~~云存储：内部文档、规格、指南、过去的研究
- 产品路线图（面向内部）：功能时间表、优先级

**第二级 — 组织背景：**
- ~~CRM笔记：账户笔记、活动历史、之前的答案、机会详情
- ~~支持平台（如果已连接）：之前的解决方案、已知问题、解决方案
- 会议笔记：之前的讨论、决策、承诺

**第三级 — 团队沟通：**
- ~~聊天：在相关频道中搜索该主题；检查团队成员之前是否讨论或回答过这个问题
- ~~电子邮件：搜索关于此主题的先前通信
- 日历笔记：会议议程和会议后笔记

**第四级 — 外部来源：**
- 网络搜索：官方文档、博客文章、社区论坛
- 公共知识库、帮助中心、发布说明
- 第三方文档：集成合作伙伴、补充工具

**第五级 — 推断或类比（当直接来源未提供答案时使用）：**
- 类似情况：以前如何处理类似问题
- 类似客户：对可比账户有效的方法
- 一般最佳实践：行业标准和社会规范

### 3. 整合发现

将结果整理成一个结构化的研究简报：

```
## 研究：[问题/主题]

### 答案
[清晰、直接的答案——以底线开头]

**置信度：[高 / 中 / 低]
[解释置信度级别的驱动因素]

### 关键发现

**来自[来源1]：**
- [具体细节的发现]
- [具体细节的发现]

**来自[来源2]：**
- [具体细节的发现]

### 背景和细微差别
[任何需要注意的例外情况、边缘情况或额外背景]

### 来源
1. [来源名称/链接] — [它贡献了什么]
2. [来源名称/链接] — [它贡献了什么]
3. [来源名称/链接] — [它贡献了什么]

### 缺失和未知
- [无法确认的内容]
- [可能需要主题专家验证的内容]

### 建议的下一步
- [如果答案需要提供给客户，采取的行动]
- [如果需要进一步研究，采取的行动]
- [如果需要验证，咨询谁]
```

### 4. 处理来源不足的情况

如果没有任何已连接的来源产生结果：

- 对主题进行网络研究
- 向用户请求内部背景：
  - "我在已连接的来源中找不到这个。关于这个主题，你们是否有内部文档或知识库文章？"
  - "你们的团队之前讨论过这个主题吗？我应该检查哪些~~聊天频道？"
  - "是否有主题专家会知道答案？"
- 对局限性保持透明：
  - "这个答案仅基于网络研究——请在与客户分享之前，与内部文档进行核对。"
  - "我找到了一个可能的答案，但无法从权威的内部来源进行确认。"

### 5. 面向客户时的注意事项

如果研究是为了回答客户的问题：

- 标记如果答案涉及产品路线图、定价、法律或安全主题，可能需要审核
- 记录如果答案与之前沟通的内容不同
- 建议客户界面的适当免责声明
- 提供起草客户回复的选项："基于这些发现，想让我起草对客户的回复吗？"

### 6. 知识捕获

研究完成后，建议捕获知识：

- "我应该将这些发现保存到您的知识库以供将来参考吗？"
- "想让我根据这项研究创建一个常见问题解答条目吗？"
- "这可能值得记录——我应该起草一个操作手册条目吗？"

这有助于建立机构知识，并减少团队内重复的研究工作。

## 来源优先级和置信度

### 按来源级别的置信度

| 级别 | 来源类型 | 置信度 | 备注 |
|------|-------------|------------|-------|
| 1 | 官方内部文档、知识库、政策 | **高** | 除非明显过时——检查日期 |
| 2 | CRM、支持工单、会议笔记 | **中高** | 可能主观或信息不完整 |
| 3 | 聊天、电子邮件、日历笔记 | **中** | 非正式，可能脱离背景或推测 |
| 4 | 网络、论坛、第三方文档 | **低中** | 可能不反映您特定的环境 |
| 5 | 推断、类比、最佳实践 | **低** | 明确标记为推断，不是事实 |

### 置信度级别

始终分配并传达置信度级别：

**高置信度：**
- 答案由官方文档或权威来源确认
- 多个来源相互印证相同答案
- 信息是最新的（在合理的时间范围内验证）
- "基于[来源]，我确信这是准确的。"

**中置信度：**
- 在非正式来源（聊天、电子邮件）中找到答案，但不是官方文档
- 单一来源无相互印证
- 信息可能稍显过时，但仍可能有效
- "基于[来源]，这种情况似乎属实，但建议与[团队/人员]确认。"

**低置信度：**
- 答案是从相关信息中推断的
- 来源过时或可能不可靠
- 跨来源发现相互矛盾的信息
- "我未能找到确凿的答案。基于[背景]，我的最佳评估是[答案]，但在与客户分享之前应进行验证。"

**无法确定：**
- 在任何来源中未找到相关信息
- 问题需要专业知识，而来源中不存在
- "我无法找到关于这个主题的信息。建议联系[建议的专家/团队]以获得确凿的答案。"

### 处理矛盾

当来源不一致时：
1. 明确记录矛盾
2. 确定哪个来源更具权威性或更新
3. 带有背景呈现两种观点
4. 建议如何解决差异
5. 如果面向客户：使用最保守/谨慎的答案，直到解决

## 何时升级与直接回答

### 直接回答的情况：
- 官方文档明确回答了问题
- 多个可靠来源相互印证答案
- 问题是非敏感的事实性问题
- 答案不涉及承诺、时间表或定价
- 你之前已用确认的准确性回答过类似问题

### 需要升级或验证的情况：
- 答案涉及产品路线图的承诺或时间表
- 定价、法律条款或特定合同问题
- 安全、合规或数据处理问题
- 答案可能设定先例或创造期望
- 在来源中找到矛盾信息
- 问题涉及特定客户的自定义配置
- 答案需要你不具备的专业知识
- 客户面临风险，错误的答案可能加剧情况

### 升级路径：
1. **主题专家**：用于技术或特定领域的问题
2. **产品团队**：用于路线图、功能或能力问题
3. **法律/合规**：用于条款、隐私、安全或监管问题
4. **计费/财务**：用于定价、发票或付款相关问题
5. **工程**：用于自定义配置、错误或技术根本原因
6. **领导层**：用于战略决策、例外情况或高风险情况

## 研究文档以供团队知识库使用

完成研究后，捕获知识以供将来使用。

### 记录时机：
- 问题之前出现或可能再次出现
- 研究需要大量工作来汇编
- 答案需要整合多个来源
- 答案纠正了常见的误解
- 答案涉及容易出错的知识点

### 记录格式：
```
## [问题/主题]

**最后核实：** [日期]
**置信度：** [级别]

### 答案
[清晰、直接的答案]

### 详情
[支持性细节、背景和细微差别]

### 来源
[信息来源]

### 相关问题
[这个问题可能有助于回答的其他问题]

### 审核笔记
[何时重新核实，什么可能会改变这个答案]
```

### 知识库卫生：
- 所有条目加日期戳
- 标记引用特定产品版本或功能的条目
- 每季度审核和更新条目
- 归档不再相关的条目
- 标记条目以供搜索（按主题、产品领域、客户细分）
