# 创建 Cowork 插件

通过引导式对话从零开始构建一个新的插件。引导用户完成发现、规划、设计、实现和打包等步骤，最终交付一个可安装的 `.plugin` 文件。

## 概述

插件是一个自包含的目录，通过技能、代理、钩子和 MCP 服务器集成扩展 Claude 的功能。此技能编码了完整的插件架构和一个五阶段工作流程，用于对话式创建。

流程：

1. **发现** — 了解用户想要构建什么
2. **组件规划** — 确定需要哪些组件类型
3. **设计与澄清问题** — 详细指定每个组件
4. **实现** — 创建所有插件文件
5. **审查与打包** — 交付 `.plugin` 文件

> **非技术输出**：保持所有面向用户的对话内容为平实语言。不要暴露实现细节，如文件路径、目录结构或模式字段，除非用户询问。用插件将做什么来描述一切。

## 插件架构

### 目录结构

每个插件都遵循此布局：

```
plugin-name/
├── .claude-plugin/
│   └── plugin.json           # 必须的：插件清单
├── skills/                   # 技能（带 SKILL.md 的子目录）
│   └── skill-name/
│       ├── SKILL.md
│       └── references/
├── agents/                   # 子代理定义（.md 文件）
├── .mcp.json                 # MCP 服务器定义
└── README.md                 # 插件文档
```

> **遗留 `commands/` 格式**：旧插件可能包含一个 `commands/` 目录，其中包含单个文件的 `.md` 命令。此格式仍然有效，但新插件应使用 `skills/*/SKILL.md` 而不是 `commands/` — Cowork UI 将两者呈现为单个“技能”概念，并且技能格式支持通过 `references/` 进行渐进式披露。

**规则：**

- `.claude-plugin/plugin.json` 始终是必需的
- 组件目录（`skills/`，`agents/`）位于插件根目录，而不是 `.claude-plugin/` 内
- 仅创建插件实际使用的目录
- 使用连字符小写命名所有目录和文件

### plugin.json 清单

位于 `.claude-plugin/plugin.json`。最小的必需字段是 `name`。

```json
{
  "name": "plugin-name",
  "version": "0.1.0",
  "description": "简要说明插件用途",
  "author": {
    "name": "Author Name"
  }
}
```

**命名规则**：连字符小写，全部小写字母和连字符，无空格或特殊字符。
**版本**：semver 格式（MAJOR.MINOR.PATCH）。从 `0.1.0` 开始。

可选字段：`homepage`，`repository`，`license`，`keywords`。

可以指定自定义组件路径（补充，不替换，自动发现）：

```json
{
  "commands": "./custom-commands",
  "agents": ["./agents", "./specialized-agents"],
  "hooks": "./config/hooks.json",
  "mcpServers": "./.mcp.json"
}
```

### 组件模式

每个组件类型的详细模式在 `references/component-schemas.md` 中。摘要：

| 组件                          | 位置            | 格式                      |
| ----------------------------- | --------------- | --------------------------- |
| 技能                         | `skills/*/SKILL.md` | Markdown + YAML 前置内容 |
| MCP 服务器                    | `.mcp.json`         | JSON                        |
| 代理（Cowork 中不常用）       | `agents/*.md`       | Markdown + YAML 前置内容 |
| 钩子（Cowork 中极少使用）      | `hooks/hooks.json`  | JSON                        |
| 命令（遗留）                  | `commands/*.md`     | Markdown + YAML 前置内容 |

此模式与 Claude Code 的插件系统共享，但你正在为 Claude Cowork 创建插件，这是一个用于知识工作的桌面应用程序。
Cowork 用户通常会发现技能最有用。**使用 `skills/*/SKILL.md` 构建新插件 — 除非用户明确需要遗留的单文件格式，否则不要创建 `commands/`。**

### 使用 `~~` 占位符的自定义插件

> **默认情况下不要使用或询问此模式。** 只有当用户明确表示他们希望组织外的人员使用插件时，才引入 `~~` 占位符。
> 如果用户似乎希望将插件外部分发，可以提及这是一个选项，但不要主动询问，使用 `AskUserQuestion`。

当插件打算与公司外的人员共享时，它可能需要根据个人用户进行调整。
您可能需要按类别而不是具体产品引用外部工具（例如，“项目跟踪器”而不是“Jira”）。
当需要共享时，使用通用语言并将这些标记为需要自定义，例如 `create an issue in ~~project tracker`。
如果使用任何工具类别，请在插件根目录编写 `CONNECTORS.md` 文件来解释：

```markdown
# Connectors

## 工具引用如何工作

插件文件使用 `~~category` 作为该类别中用户连接的任何工具的占位符。插件与工具无关 — 它们通过类别而不是具体产品描述工作流程。

## 此插件的连接器

| 类别        | 占位符         | 选项                         |
| ----------- | --------------- | ------------------------------- |
| 聊天            | `~~chat`            | Slack, Microsoft Teams, Discord |
| 项目跟踪器 | `~~project tracker` | Linear, Asana, Jira             |
```

### `${CLAUDE_PLUGIN_ROOT}` 变量

在钩子和 MCP 配置中用于所有插件内部路径引用。永远不要硬编码绝对路径。

## 引导工作流程

当您询问用户时，使用 `AskUserQuestion`。不要假设“行业标准”默认值是正确的。注意：`AskUserQuestion` 总是包括一个跳过按钮和用于自定义答案的自由文本输入框，因此不要将 `None` 或 `Other` 作为选项。

### 第一阶段：发现

**目标**：了解用户想要构建什么以及为什么。

询问（仅当不清楚时 — 如果用户的初始请求已经回答了问题，则跳过问题）：

- 这个插件应该做什么？它解决了什么问题？
- 谁将使用它以及什么上下文中使用？
- 它与任何外部工具或服务集成吗？
- 是否有类似的插件或工作流程可以参考？

总结理解并在继续之前确认。

**输出**：插件目的和范围的清晰陈述。

### 第二阶段：组件规划

**目标**：确定插件需要哪些组件类型。

根据发现答案，确定：

- **技能** — 它是否需要 Claude 应该按需加载的专业知识，或用户发起的操作？（领域专业知识、参考模式、工作流程指南、部署/配置/分析/审查操作）
- **MCP 服务器** — 它是否需要外部服务集成？（数据库、API、SaaS 工具）
- **代理（不常用）** — 是否有自动的多步骤任务？（验证、生成、分析）
- **钩子（罕见）** — 是否应在某些事件上自动发生某些操作？（执行策略、加载上下文、验证操作）

呈现组件计划表，包括您决定不创建的组件类型：

```
| 组件 | 数量 | 目的 |
|------|------|------|
| 技能 | 3    | X 的领域知识，/do-thing，/check-thing |
| 代理 | 0    | 不需要 |
| 钩子 | 1    | 验证写入 |
| MCP  | 1    | 连接到服务 Y |
```

在继续之前获得用户确认或调整。

**输出**：要创建的组件确认列表。

### 第三阶段：设计与澄清问题

**目标**：详细指定每个组件。在实现之前解决所有歧义。

针对计划中的每个组件类型，询问有针对性的设计问题。按组件类型分组呈现问题。等待答案后再继续。

**技能：**

- 哪些用户查询应触发此技能？
- 它涵盖哪些知识领域？
- 是否应包含用于详细内容的参考文件？
- 如果技能表示用户发起的操作：它接受哪些参数，需要哪些工具？（读取、写入、Bash、Grep 等）

**代理：**

- 每个代理应主动触发还是仅当请求时触发？
- 需要哪些工具？
- 输出格式应是什么？

**钩子：**

- 哪些事件？（PreToolUse、PostToolUse、Stop、SessionStart 等）
- 行为是什么 — 验证、阻止、修改、添加上下文？
- 基于提示（由 LLM 驱动）还是基于命令（确定性脚本）？

**MCP 服务器：**

- 服务器类型是什么？（stdio 用于本地，SSE 用于带 OAuth 的托管，HTTP 用于 REST API）
- 认证方法是什么？
- 应该暴露哪些工具？

如果用户说“你想做什么最好”，请提供具体建议并获取明确确认。

**输出**：每个组件的详细规范。

### 第四阶段：实现

**目标**：遵循最佳实践创建所有插件文件。

**操作顺序：**

1. 创建插件目录结构
2. 创建 `plugin.json` 清单
3. 创建每个组件（参考 `references/component-schemas.md` 获取确切格式）
4. 创建 `README.md` 记录插件

**实现指南：**

- **技能** 使用渐进式披露：简洁的 SKILL.md 正文（少于 3,000 字），详细内容在 `references/`。前置内容描述必须为第三人称，并包含具体的触发短语。技能正文是给 Claude 的指令，而不是给用户阅读的文档 — 将其写为关于 Claude 应做什么的指令。
- **代理** 需要一个描述，其中包含 `<example>` 块显示触发条件，以及 markdown 正文中的系统提示。
- **钩子** 配置放在 `hooks/hooks.json` 中。使用 `${CLAUDE_PLUGIN_ROOT}` 用于脚本路径。对于复杂逻辑，优先使用基于提示的钩子。
- **MCP 配置** 放在插件根目录的 `.mcp.json` 中。使用 `${CLAUDE_PLUGIN_ROOT}` 用于本地服务器路径。在 README 中记录所需的 env 变量。

### 第五阶段：审查与打包

**目标**：交付完成的插件。

1. 总结创建的内容 — 列出每个组件及其目的
2. 询问用户是否需要任何调整
3. 运行 `claude plugin validate <path-to-plugin-json>` 检查插件结构。如果此命令不可用（例如，在 Cowork 内运行时），请手动验证结构：
   - 存在 `.claude-plugin/plugin.json` 并包含至少包含 `name` 字段的合法 JSON
   - `name` 字段为连字符小写（仅包含小写字母、数字和连字符）
   - 插件引用的任何组件目录（`commands/`，`skills/`，`agents/`，`hooks/`）确实存在并包含预期格式的文件 — `.md` 用于命令/技能/代理，`.json` 用于钩子
   - 每个技能子目录包含 `SKILL.md`
   - 报告通过和未通过的内容，与 CLI 验证器相同的方式

在继续之前修复任何错误。
4. 打包为 `.plugin` 文件：

```bash
cd /path/to/plugin-dir && zip -r /tmp/plugin-name.plugin . -x "*.DS_Store" && cp /tmp/plugin-name.plugin /path/to/outputs/plugin-name.plugin
```

> **重要**：始终先在 `/tmp/` 创建 zip，然后复制到输出文件夹。直接写入输出文件夹可能因权限问题失败。

> **命名**：使用 `plugin.json` 中的插件名称作为 `.plugin` 文件（例如，如果名称是 `code-reviewer`，输出 `code-reviewer.plugin`）。

`.plugin` 文件将作为富预览出现在聊天中，用户可以浏览文件并通过按按钮接受插件。

## 最佳实践

- **从小处着手**：从最小的可行组件集开始。一个精心设计的技能插件比五个半成品组件更有用。
- **技能的渐进式披露**：核心知识在 SKILL.md 中，详细参考材料在 `references/`，工作示例在 `examples/`。
- **清晰的触发短语**：技能描述应包括用户会说到的具体短语。代理描述应包括 `<example>` 块。
- **技能是给 Claude 的**：写技能正文内容作为 Claude 应遵循的指令，而不是用户阅读的文档。
- **祈使句写作风格**：在技能中使用动词开头的指令（“解析配置文件”，而不是“你应该解析配置文件”）。
- **可移植性**：始终使用 `${CLAUDE_PLUGIN_ROOT}` 用于插件内部路径，永远不要硬编码路径。
- **安全性**：使用环境变量存储凭证，使用 HTTPS 连接远程服务器，使用最小权限工具访问。
