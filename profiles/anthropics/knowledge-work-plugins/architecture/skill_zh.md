# /architecture

> 如果你看到不熟悉的占位符，或者需要检查哪些工具已连接，请参阅 [CONNECTORS.md](../../CONNECTORS.md)。

创建架构决策记录 (ADR) 或评估系统设计。

## 使用方法

```
/architecture $ARGUMENTS
```

## 模式

**创建 ADR**： “我们应该使用 Kafka 还是 SQS 作为我们的事件总线？”
**评估设计**： “评审这个微服务提案”
**系统设计**： “设计我们应用的通知系统”

有关需求收集、可扩展性分析和权衡评估的详细框架，请参阅 **system-design** 技能。

## 输出 — ADR 格式

```markdown
# ADR-[编号]: [标题]

**状态**： 提案 | 已接受 | 已弃用 | 已取代
**日期**： [日期]
**决策者**： [需要签字的人]

## 背景
[情况是什么？有哪些影响因素？]

## 决策
[我们提议的改变是什么？]

## 考虑过的选项

### 选项 A：[名称]
| 维度 | 评估 |
|-------|------|
| 复杂性 | [低/中/高] |
| 成本 | [评估] |
| 可扩展性 | [评估] |
| 团队熟悉度 | [评估] |

**优点**： [列表]
**缺点**： [列表]

### 选项 B：[名称]
[相同格式]

## 权衡分析
[选项之间的关键权衡及明确理由]

## 后果
- [变得更容易]
- [变得更难]
- [我们需要重新审视的内容]

## 行动项
1. [ ] [实施步骤]
2. [ ] [后续行动]
```

## 小贴士

1. **提前说明约束条件** — “我们需要在两周内发布”或“必须处理 10K rps”会影响答案。
2. **命名你的选项** — 即使你倾向于某个方向，我也会通过明确的替代方案给出更平衡的分析。
3. **包含非功能性需求** — 延迟、成本、团队专业知识和维护负担与功能同等重要。
