# /compliance-check -- 合规审查

> 如果您看到不熟悉的占位符或需要检查哪些工具已连接，请参阅 [CONNECTORS.md](../../CONNECTORS.md)。

对拟议的行动、产品功能、营销活动或商业计划进行合规审查。

**重要提示**：此命令协助法律工作流程，但不会提供法律建议。合规评估应由合格的法律专业人士进行。监管要求经常变化；请务必通过权威来源核实当前要求。

## 使用方法

```
/compliance-check $ARGUMENTS
```

## 我需要您提供的信息

描述您打算做什么。示例：
- "我们想推出一个带有现金奖励的推荐计划"
- "我们正在我们的移动应用中添加生物识别认证"
- "我们需要在我们的美国数据中心处理欧盟客户数据"
- "营销部门想在广告中使用客户证言"

## 隐私法规概述

### GDPR（通用数据保护条例）

**范围**：适用于处理欧盟/欧洲经济区个人数据的个人，无论处理组织位于何处。

**内部法律团队的关键义务**：
- **合法基础**：识别并记录每种处理活动的合法基础（同意、合同、合法利益、法律义务、生命利益、公共任务）
- **数据主体权利**：在30天内响应访问、更正、删除、可携带性、限制和处理反对请求（复杂请求可延长60天）
- **数据保护影响评估（DPIA）**：对于可能导致对个人高风险的处理，需要执行DPIA
- **违规通知**：在意识到个人数据违规后72小时内通知监管机构；如果存在高风险，则在不适当的情况下通知受影响的个人
- **处理记录**：维护第30条的处理活动记录
- **国际传输**：确保在EEA外传输的适当保护措施（SCC、充分性决定、BCR）
- **DPO要求**：如果需要，任命数据保护官（公共机构、大规模处理特殊类别数据、大规模系统性监控）

**常见的内部法律接触点**：
- 审查供应商的DPAs以符合GDPR
- 向产品团队提供隐私设计要求建议
- 回应监管机构查询
- 管理跨境数据传输机制
- 审查同意机制和隐私声明

### CCPA / CPRA（加利福尼亚州消费者隐私法案 / 加利福尼亚州隐私权法案）

**范围**：适用于收集加利福尼亚州居民个人信息的公司，并满足收入、数据量或数据销售阈值。

**关键义务**：
- **知情权**：消费者可以要求披露收集、使用和共享的个人信息的披露
- **删除权**：消费者可以要求删除其个人信息
- **选择退出权**：消费者可以选择退出个人信息的销售或共享
- **更正权**：消费者可以要求更正不准确的个人信息的权利（CPRA新增）
- **限制使用敏感个人信息权**：消费者可以限制在特定目的上使用敏感PI（CPRA新增）
- **非歧视**：不能歧视行使权利的消费者
- **隐私声明**：必须在收集时或之前提供隐私声明，描述收集的PI类别和目的
- **服务提供者协议**：与服务提供者的合同必须限制PI的使用到指定的业务目的

**响应时间线**：
- 在10个工作日内确认收到
- 在45个日历日内做出实质性响应（可延长45天并通知）

### 其他需要关注的法规

| 法规 | 法域 | 关键差异 |
|---|---|---|
| **LGPD**（巴西） | 巴西 | 类似于GDPR；要求任命DPO；国家数据保护局（ANPD）执法 |
| **POPIA**（南非） | 南非 | 信息监管机构监督；需要处理注册 |
| **PIPEDA**（加拿大） | 加拿大（联邦） | 基于同意的框架；OPC监督；正在现代化 |
| **PDPA**（新加坡） | 新加坡 | 不再呼叫注册；强制违规通知；PDPC执法 |
| **隐私法**（澳大利亚） | 澳大利亚 | 澳大利亚隐私原则（APPs）；通知性数据违规方案 |
| **PIPL**（中国） | 中国 | 严格的跨境传输规则；数据本地化要求；CAC监督 |
| **UK GDPR** | 英国 | 英国脱欧后的版本；ICO监督；类似于EU GDPR，但具有英国特定的充分性决定 |

## DPA审查清单

在审查数据处理协议（DPA）或数据处理补充协议时，请验证以下内容：

### 必要元素（GDPR第28条）

- [ ] **主题和期限**：明确定义处理范围和期限
- [ ] **性质和目的**：对将发生什么处理以及为什么进行的具体描述
- [ ] **个人数据的类型**：正在处理的个人数据类别
- [ ] **数据主体类别**：正在处理谁的个人信息
- [ ] **控制者的义务和权利**：控制者的指示和监督权利

### 处理者义务

- [ ] **仅根据记录的指示处理**：处理者承诺仅根据控制者的指示处理（法律要求除外）
- [ ] **保密**：授权处理的人员已承诺保密
- [ ] **安全措施**：描述适当的技术和组织措施（第32条参考）
- [ ] **子处理者要求**：
  - [ ] 书面授权要求（一般或特定）
  - [ ] 如果一般授权：通知变更并有机会提出异议
  - [ ] 子处理者通过书面协议受相同义务约束
  - [ ] 处理者对子处理者的表现负责
- [ ] **数据主体权利协助**：处理者将协助控制者响应数据主体请求
- [ ] **安全和违规协助**：处理者将协助安全义务、违规通知、DPIA和事先咨询
- [ ] **删除或返还**：终止时，删除或返还所有个人数据（由控制者选择），并删除现有副本，除非法律保留要求
- [ ] **审计权利**：控制者有权进行审计和检查（或接受第三方审计报告）
- [ ] **违规通知**：处理者将在不适当的情况下通知控制者个人数据违规（理想情况下在24-48小时内；必须使控制者能够满足72小时监管期限）

### 国际传输

- [ ] **已确定传输机制**：SCC、充分性决定、BCR或其他有效机制
- [ ] **SCC版本**：如果适用，使用当前的欧盟SCC（2021年6月版本）
- [ ] **正确模块**：选择适当的SCC模块（C2P、C2C、P2P、P2C）
- [ ] **传输影响评估**：如果传输到没有充分性决定的国家的国家，则完成传输影响评估
- [ ] **补充措施**：技术、组织或合同措施，以解决传输影响评估中发现的差距
- [ ] **英国补充协议**：如果英国个人数据在范围内，则包括英国国际数据传输补充协议

### 实际考虑

- [ ] **责任**：DPA责任条款与（或）不与主要服务协议冲突
- [ ] **终止一致性**：DPA期限与服务协议一致
- [ ] **数据位置**：指定并接受处理位置
- [ ] **安全标准**：需要特定的安全标准或认证（SOC 2、ISO 27001等）
- [ ] **保险**：为数据处理活动提供足够的保险覆盖范围

### 常见DPA问题

| 问题 | 风险 | 标准立场 |
|---|---|---|
| 没有通知的空白子处理者授权 | 失去对处理链的控制 | 要求通知并有权提出异议 |
| 违规通知时间 > 72小时 | 可能无法及时通知监管机构 | 要求在24-48小时内通知 |
| 没有审计权利（或仅通过第三方报告进行审计权利） | 无法核实合规性 | 接受SOC 2 Type II + 有权在原因发生时审计 |
| 未指定删除时间线 | 数据可能被无限期保留 | 要求在终止后30-90天内删除 |
| 未指定数据处理位置 | 数据可能被处理到任何地方 | 要求披露处理位置 |
| 过时的SCC | 无效的传输机制 | 要求当前的欧盟SCC（2021年版本） |

## 数据主体请求处理

### 请求接收

收到数据主体请求时：

1. **识别请求类型**：
   - 访问（个人数据的副本）
   - 更正（纠正不准确的数据）
   - 删除/删除（"被遗忘权"）
   - 处理限制
   - 数据可携带性（结构化、机器可读格式）
   - 处理反对
   - 选择退出销售/共享（CCPA/CPRA）
   - 限制敏感个人信息的用途（CPRA）

2. **识别适用的法规**：
   - 数据主体位于何处？
   - 基于您组织的存在和活动，哪些法律适用？
   - 具体的要求和时间线是什么？

3. **验证身份**：
   - 确认请求者是谁
   - 使用与数据敏感性成比例的合理验证措施
   - 不要要求过多的文件

4. **记录请求**：
   - 收到日期
   - 请求类型
   - 请求者身份
   - 适用法规
   - 响应截止日期
   - 指定处理者

### 响应时间线

| 法规 | 初始确认 | 实质性响应 | 延长 |
|---|---|---|---|
| GDPR | 未指定（最佳实践：及时） | 30天 | +60天（通知） |
| CCPA/CPRA | 10个工作日 | 45个日历日 | +45天（通知） |
| UK GDPR | 未指定（最佳实践：及时） | 30天 | +60天（通知） |
| LGPD | 未指定 | 15天 | 有限扩展 |

### 免责和例外

在满足请求之前，请检查是否适用任何免责：

**跨法规的常见免责**：
- 法律索赔辩护或建立
- 法律义务要求保留
- 公共利益或官方权力
- 表达自由和信息（用于删除请求）
- 公共利益中的存档或科学/历史研究

**组织特定考虑**：
- 诉讼保留：处于法律保留状态的数据主体不能被删除
- 监管保留：财务记录、雇佣记录和其他类别可能有强制保留期
- 第三方权利：满足请求可能会对其他人的权利产生不利影响

### 响应流程

1. 在系统上收集请求者的所有个人数据
2. 应用任何免责并记录依据
3. 准备响应：满足请求或解释为什么（全部或部分）无法满足
4. 如果拒绝（全部或部分）：引用拒绝的具体法律依据
5. 通知请求者有权向监管机构提出投诉
6. 记录响应并保留请求和响应的记录

## 监管监控基础

### 需要监控的内容

保持对以下方面发展的了解：
- **监管指南**：监管机构（ICO、CNIL、FTC、州总检察长等）发布的新或更新的指南
- **执法行动**：罚款、命令和和解，这些行动表明监管重点
- **立法变化**：新的隐私法、现有法律的修订、实施条例
- **行业标准**：ISO 27001、SOC 2、NIST框架和特定行业要求的更新
- **跨境传输发展**：充分性决定、SCC更新、数据本地化要求

### 监控方法

1. **订阅监管机构的通信**（通讯录、RSS源、官方公告）
2. **跟踪相关法律出版物**，分析新发展
3. **审查行业协会更新**，获取特定行业指南
4. **维护监管日历**，列出已知即将到来的截止日期、生效日期和合规里程碑
5. **向法律团队简要介绍**影响组织处理活动的重大发展

### 升级标准

当监管发展直接影响组织的核心业务活动时，将监管发展升级给高级律师或领导层：
- 新法规或指南直接影响组织的核心业务活动
- 组织所在行业的执法行动表明了加强的监管审查
- 接近需要组织变更的合规截止日期
- 组织依赖的数据传输机制受到挑战或无效
- 监管机构启动涉及组织的调查或查询

## 建议

1. **具体**——"我们想向所有用户发送电子邮件"比"营销活动"更好。
2. **包括地理信息**——合规要求因司法管辖区而异。
3. **提及数据**——涉及哪些个人数据？这驱动了大多数合规要求。
