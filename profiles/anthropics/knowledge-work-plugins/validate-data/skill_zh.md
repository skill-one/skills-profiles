# /validate-data - 在分享前验证分析

> 如果你看到不熟悉的占位符或需要检查哪些工具已连接，请参阅[CONNECTORS.md](../../CONNECTORS.md)。

在分享给利益相关者之前，审查分析的准确性、方法和潜在偏差。生成信心评估和改进建议。

## 使用方法

```
/validate-data <要审查的分析>
```

分析可以是：
- 聊天中的文档或报告
- 文件（Markdown、笔记本、电子表格）
- SQL 查询及其结果
- 图表及其底层数据
- 方法和发现描述

## 工作流程

### 1. 审查方法和假设

检查：

- **问题表述**：分析是否在回答正确的问题？问题是否可能被不同地解释？
- **数据选择**：是否使用了正确的表格/数据集？时间范围是否合适？
- **总体定义**：分析的总体是否定义正确？是否存在意外的排除？
- **指标定义**：指标是否定义清晰且一致？它们是否与利益相关者理解的方式匹配？
- **基线和比较**：比较是否公平？时间段、队列大小和背景是否可比较？

### 2. 运行交付前质量保证检查清单

通读以下检查清单——数据质量、计算、合理性及展示检查。

### 3. 检查常见分析陷阱

系统性地对照以下详细陷阱目录（连接爆炸、幸存者偏差、不完整时期比较、分母变动、平均数的平均数、时区不匹配、选择偏差）。

### 4. 验证计算和汇总

在可能的情况下，抽查：

- 独立地重新计算几个关键数字
- 验证子总计是否加总到总计
- 检查预期情况下百分比是否加总到 100%（或接近）
- 确认年度/月度比较使用了正确的基期
- 验证过滤器在所有指标中是否一致应用

应用以下结果合理性检查技术（幅度检查、交叉验证、红旗检测）。

### 5. 评估可视化

如果分析包含图表：

- 坐标轴是否从适当的值开始（条形图为零）？
- 比较图表的尺度是否一致？
- 图表标题是否准确描述了显示的内容？
- 可视化是否可能误导快速读者？
- 是否存在截断的坐标轴、不一致的间隔或 3D 效果扭曲感知？

### 6. 评估叙述和结论

审查是否：

- 结论是否由显示的数据支持
- 是否承认替代解释
- 是否适当传达了不确定性
- 建议是否逻辑上遵循了发现
- 信心水平是否与证据强度匹配

### 7. 提出改进建议

提供具体、可操作的建议：

- 将加强结论的额外分析
- 利益相关者应注意的警示或限制
- 关键点的更好可视化或表述
- 利益相关者想要的缺失背景信息

### 8. 生成信心评估

在 3 级量表上对分析进行评级：

**准备分享**——分析在方法上合理，计算已验证，已注明警示。只有小的改进建议，没有阻碍。

**带警示分享**——分析基本正确，但有特定的限制或假设必须传达给利益相关者。列出所需的警示。

**需要修订**——发现具体错误、方法问题或缺失分析，应在分享前解决。列出所需更改及优先级顺序。

## 交付前质量保证检查清单

在将任何分析分享给利益相关者之前，运行此检查清单。

### 数据质量检查

- [ ] **来源验证**：确认使用了哪些表格/数据源。它们是否适合此问题？
- [ ] **新鲜度**：数据是否足够新以用于分析。注明“截至”日期。
- [ ] **完整性**：时间序列或缺失段是否存在意外空白。
- [ ] **空值处理**：检查关键列的空值率。空值是否适当处理（排除、插补或标记）。
- [ ] **去重**：确认没有因不良连接或重复源记录导致的重复计数。
- [ ] **过滤验证**：所有 WHERE 子句和过滤器是否正确。没有意外的排除。

### 计算检查

- [ ] **聚合逻辑**：GROUP BY 包含所有非聚合列。聚合级别与分析粒度匹配。
- [ ] **分母正确性**：率和百分比计算使用正确的分母。分母不为零。
- [ ] **日期对齐**：比较使用相同的时间段长度。部分时期被排除或注明。
- [ ] **连接正确性**：连接类型适当（INNER 对 LEFT）。多对多连接没有导致计数膨胀。
- [ ] **指标定义**：指标与利益相关者定义的方式匹配。任何偏差都已注明。
- [ ] **子总计加总**：预期情况下部分加总到整体。如果它们不匹配，解释原因（例如，重叠）。

### 合理性检查

- [ ] **幅度**：数字在合理的范围内。收入不是负数。百分比在 0-100% 之间。
- [ ] **趋势连续性**：时间序列中没有未解释的跳跃或下降。
- [ ] **交叉引用**：关键数字与其他已知来源（仪表板、先前报告、财务数据）匹配。
- [ ] **数量级**：总收入在正确的范围内。用户计数与已知数字匹配。
- [ ] **边界情况**：边界处会发生什么？空段、零活动时期、新实体。

### 展示检查

- [ ] **图表准确性**：条形图从零开始。坐标轴已标记。面板间尺度一致。
- [ ] **数字格式**：适当的精度。一致的货币/百分比格式。需要时使用千位分隔符。
- [ ] **标题清晰度**：标题陈述见解，而不仅仅是指标。指定日期范围。
- [ ] **警示透明度**：已明确说明已知限制和假设。
- [ ] **可重复性**：其他人可以根据提供的文档重现此分析。

## 常见数据分析陷阱

### 连接爆炸

**问题**：多对多连接无声地乘以行数，导致计数和总和膨胀。

**如何检测**：
```sql
-- 检查连接前后的行数
SELECT COUNT(*) FROM table_a;  -- 1,000
SELECT COUNT(*) FROM table_a a JOIN table_b b ON a.id = b.a_id;  -- 3,500 (哎呀)
```

**如何预防**：
- 始终在连接后检查行数
- 如果计数增加，调查连接关系（它真的是 1:1 或 1:多吗？
- 使用 `COUNT(DISTINCT a.id)` 而不是 `COUNT(*)` 当通过连接计数实体时

### 幸存者偏差

**问题**：仅分析今天存在的实体，忽略已删除、流失或失败的实体。

**示例**：
- 分析“当前用户”的行为忽略了流失用户
- 查看“使用我们产品的公司”忽略了那些评估后离开的公司
- 研究“成功”结果的属性而不研究“失败”的

**如何预防**：在得出结论之前，问“谁不在这个数据集中？”。

### 不完整时期比较

**问题**：将部分时期与完整时期进行比较。

**示例**：
- “1 月收入是 50K 美元，而 12 月的是 80K 美元”——但 1 月还没结束
- “本周的注册人数下降”——周三检查，与完整的前一周比较

**如何预防**：始终过滤到完整时期，或比较同一天/同数量天数。

### 分母变动

**问题**：时期之间的分母发生变化，导致比率不可比。

**示例**：
- 转化率提高，因为你改变了如何计算“符合条件的”用户
- 流失率变化，因为“活跃”的定义被更新

**如何预防**：在所有比较时期中使用一致的定义。注明任何定义变更。

### 平均数的平均数

**问题**：对预计算的均值取平均数，当组大小不同时会导致错误结果。

**示例**：
- 组 A：100 用户，平均收入 50 美元
- 组 B：10 用户，平均收入 200 美元
- 错误：平均数的平均值 = (50 + 200) / 2 = 125
- 正确：加权平均 = (100*$50 + 10*$200) / 110 = 63.64

**如何预防**：始终从原始数据聚合。永远不要平均预聚合的均值。

### 时区不匹配

**问题**：不同的数据源使用不同的时区，导致错位。

**示例**：
- 事件时间戳为 UTC，用户面日期为本地时间
- 每日汇总使用不同的截止时间

**如何预防**：在分析前将所有时间戳标准化到单一时区（推荐 UTC）。记录使用的时区。

### 分段中的选择偏差

**问题**：分段是根据你正在测量的结果定义的，导致循环逻辑。

**示例**：
- “完成入门的用户留存率更高”——显然，他们自我选择了
- “高级用户产生更多收入”——他们通过产生收入成为高级用户

**如何预防**：基于预处理特征定义分段，而不是结果。

### 其他统计陷阱

- **辛普森悖论**：当数据聚合与分段时，趋势反转
- **将相关性呈现为因果关系**，而没有支持证据
- **小样本量**导致不可靠的结论
- **异常值不成比例地影响平均值**（是否应使用中位数？
- **多重测试/挑拣**显著结果
- **前瞻偏差**：使用未来信息来解释过去事件
- **挑拣时间范围**：有利于特定叙述

## 结果合理性检查

### 幅度检查

对于分析中的任何关键数字，验证它是否通过“直觉测试”：

| 指标类型 | 合理性检查 |
|---|---|
| 用户计数 | 这个数字是否与已知的 MAU/DAU 数字匹配？ |
| 收入 | 这个数字是否与已知的 ARR 具有正确的数量级？ |
| 转化率 | 这个数字是否在 0% 和 100% 之间？是否与仪表板数字匹配？ |
| 增长率 | 50%+ 月度增长率现实吗，还是有数据问题？ |
| 平均值 | 给定你对分布的了解，平均值是否合理？ |
| 百分比 | 分段百分比是否加总到 ~100%？ |

### 交叉验证技术

1. **用两种不同的方法计算相同的指标**并验证它们是否匹配
2. **抽查单个记录**——选择几个特定实体并手动跟踪其数据
3. **与已知基准比较**——与已发布的仪表板、财务报告或先前分析匹配
4. **逆向工程**——如果总收入是 X，每用户收入乘以用户计数是否大约等于 X？
5. **边界检查**——当你过滤到单日、单个用户或单个类别时会发生什么？这些微观结果是否合理？

### 值得调查的红旗

- 任何指标在同期变化超过 50% 而没有明显原因
- 计数或总和是精确的圆数（表明有过滤器或默认值问题）
- 率正好为 0% 或 100%（可能表示数据不完整）
- 结果完美确认了假设（现实通常更混乱）
- 时间段或分段期间值相同（表明查询忽略了维度）

## 可重复性文档标准

### 分析文档模板

每个非平凡的分析都应包括：

```markdown
## 分析：[标题]

### 问题
[被回答的具体问题]

### 数据源
- 表：[schema.table_name]（截至 [日期]）
- 表：[schema.other_table]（截至 [日期]）
- 文件：[filename]（来源：[它来自哪里]）

### 定义
- [指标 A]：[如何计算]
- [分段 X]：[如何确定成员资格]
- [时间范围]：[开始日期] 到 [结束日期]，[时区]

### 方法
1. [分析方法的第 1 步]
2. [第 2 步]
3. [第 3 步]

### 假设和限制
- [假设 1 及其合理性]
- [限制 1 及其对结论的潜在影响]

### 关键发现
1. [支持证据的发现 1]
2. [支持证据的发现 2]

### SQL 查询
[所有使用的查询，带注释]

### 警示
- [读者在采取行动之前应知道的事情]
```

### 代码文档

对于任何可能重用的代码（SQL、Python）：

```python
"""
分析：月度队列留存
作者：[姓名]
日期：[日期]
数据源：事件表，用户表
最后验证：[日期]——结果与仪表板在 2% 以内匹配

目的：
    基于首次活动日期计算月度用户留存队列。

假设：
    - “活跃”意味着当月至少有一次事件
    - 排除测试/内部账户（user_type != 'internal'）
    - 整个过程中使用 UTC 日期

输出：
    队列留存矩阵，队列月为行，自注册以来的月数为列。
    值是留存率（0-100%）。
"""
```

### 分析版本控制

- 将查询和代码保存在版本控制（git）或共享文档系统中
- 注明使用的数据快照日期
- 如果使用更新数据重新运行分析，记录发生了什么以及为什么
- 链接到定期分析的先前版本以进行趋势比较

## 小贴士

- 在任何高风险演示或决策之前运行 /validate-data
- 即使是快速分析，进行合理性检查也受益匪浅——只需一分钟，就能挽救你的信誉
- 如果验证发现问题，修复它们并重新验证
- 与你的分析一起分享验证输出，以建立利益相关者的信心
