# Roadmap Update

> 如果您看到不熟悉的占位符或需要检查哪些工具已连接，请参阅 [CONNECTORS.md](../../CONNECTORS.md)。

更新、创建或重新排序产品路线图。

## 使用方法

```
/roadmap-update $ARGUMENTS
```

## 工作流程

### 1. 了解当前状态

如果 **~~项目追踪器** 已连接：
- 拉取当前路线图项目及其状态、负责人和日期
- 识别已逾期、有风险或最近完成的项目
- 揭示任何没有明确负责人或日期的项目

如果没有连接项目管理工具：
- 要求用户描述其当前路线图或粘贴/上传
- 接受任何格式：列表、表格、电子表格、截图或文本描述

### 2. 确定操作

询问用户想要做什么：

**添加项目**：向路线图中添加新功能、倡议或工作项
- 收集：名称、描述、优先级、估计工作量、目标时间范围、负责人、依赖项
- 基于当前优先级和容量建议其适合的位置

**更新状态**：更改现有项目的状态
- 选项：未开始、进行中、有风险、阻塞、已完成、取消
- 对于“有风险”或“阻塞”：询问阻塞原因和缓解计划

**重新排序**：更改项目的顺序或优先级
- 询问变化原因（新信息、策略转变、资源变化、客户反馈）
- 如有必要，应用优先级框架——见下文 **优先级框架** 中的 RICE、MoSCoW、ICE 和价值 vs 工作量
- 显示更改前后的对比

**调整时间线**：移动项目的日期
- 询问原因（范围变更、依赖项延迟、资源限制）
- 确定对依赖项的下游影响
- 标记已移动到硬截止日期之后的项目

**创建新路线图**：从零开始构建路线图
- 询问时间范围（季度、半年度、年度）
- 询问格式偏好（当前/下一/后续、季度列、与 OKR 对齐）——见下文 **路线图框架** 中的内容
- 收集要包含的倡议列表

### 3. 生成路线图摘要

生成包含以下内容的路线图视图：

#### 状态概览
快速总结：进行中 X 个项目，本期间完成 Y 个，有风险 Z 个。

#### 路线图项目
针对每个项目显示：
- 名称和一句话描述
- 状态指示器（按计划 / 有风险 / 阻塞 / 已完成 / 未开始）
- 目标时间范围或日期
- 负责人
- 关键依赖项

按以下方式分组项目：
- 时间范围（当前 / 下一 / 后续）或季度，取决于格式
- 或按主题/目标分组，如果用户有偏好

#### 风险和依赖项
- 阻塞或有风险的项目及其详细信息
- 跨团队依赖项及其状态
- 接近硬截止日期的项目

#### 本次更新的变更
如果这是对现有路线图的更新，总结发生了什么变更：
- 添加、删除或重新排序的项目
- 时间线变更
- 状态变更

### 4. 跟进

生成路线图后：
- 提供为特定受众格式化（高管摘要、工程细节、面向客户）的选项
- 提供起草关于路线图变更的沟通内容的选项
- 如果已连接项目管理工具，提供更新工单状态的选项

## 路线图框架

### 当前 / 下一 / 后续

最简单且通常最有效的路线图格式：

- **当前**（当前冲刺/月）：已承诺的工作。对范围和时间表有高度信心。这些是团队正在积极构建的事情。
- **下一**（未来 1-3 个月）：计划中的工作。对内容有良好信心，对确切时间有较少信心。已定义和优先排序但尚未开始。
- **后续**（3-6+ 个月）：方向性。这些是我们打算追求的战略赌注和机会，但范围和时间是灵活的。

何时使用：大多数团队，大多数时间。特别适合对外部或对领导层沟通，因为它避免了日期上的虚假精确性。

### 季度主题

围绕每个季度 2-3 个主题组织路线图：

- 每个主题代表一个战略投资领域（例如，“企业就绪”、“激活改进”、“平台可扩展性”）
- 在每个主题下，列出计划的具体倡议
- 主题应与公司或团队的 OKR 对齐
- 此格式使解释“为什么构建当前内容”变得容易

何时使用：当你需要展示战略一致性时。适合规划会议和高管沟通。

### 与 OKR 对齐的路线图

将路线图项目直接映射到目标和关键结果：

- 从该期间团队的 OKR 开始
- 在每个关键结果下，列出将推动该指标的倡议
- 包括每个倡议对关键结果的预期影响
- 这在构建内容与可衡量的结果之间建立了明确的责任制

何时使用：在基于 OKR 运作的组织中。适合确保每个倡议都有明确的“为什么”与可衡量的结果相关联。

### 时间线 / 甘特图

基于日历的视图，项目在时间线上显示：

- 显示开始日期、结束日期和持续时间
- 可视化并行性和顺序
- 适合识别资源冲突
- 显示项目之间的依赖关系

何时使用：工程执行规划。识别调度冲突。不适合对外部沟通（会创造虚假的精确性预期）。

## 优先级框架

### RICE 评分

在四个维度上对每个倡议进行评分，然后计算 RICE = (覆盖范围 x 影响 x 置信度) / 工作量

- **覆盖范围**：在给定时间段内，这将影响多少用户/客户？使用具体数字（例如，“每个季度 500 个用户”）。
- **影响**：这对每个受影响的用户有多大影响？在量表上评分：3 = 巨大，2 = 高，1 = 中，0.5 = 低，0.25 = 最小。
- **置信度**：我们对覆盖范围和影响估计有多自信？100% = 高置信度（有数据支持），80% = 中（有证据），50% = 低（直觉）。
- **工作量**：需要多少人月工作量？包括工程、设计和任何其他职能。

何时使用：当你需要一个定量的、有说服力的优先级时。适合比较大量待办事项。对于难以估计影响的战略赌注，不太适用。

### MoSCoW

将项目分为必须、应该、可以、不会：

- **必须**：没有这些，路线图就会失败。非谈判性承诺。
- **应该**：重要且预期，但交付可以在没有它们的情况下实现。
- **可以**：有吸引力但明显优先级较低。只有当容量允许时才包含。
- **不会**：在本期间明确超出范围。清晰列出很重要。

何时使用：规划发布或季度。与利益相关者协商哪些内容适合。适合推动优先级对话。

### ICE 评分

比 RICE 简单。在三个维度上对每个项目评分 1-10：

- **影响**：这将有多大程度推动目标指标？
- **置信度**：我们对影响估计有多自信？
- **易实施**：实施有多容易？（工作量的倒数——越高越容易）

ICE 评分 = 影响 x 置信度 x 易实施

何时使用：快速优先级排序功能待办事项。适合早期产品或当您没有足够数据使用 RICE 时。

### 价值 vs 工作量矩阵

在 2x2 矩阵上绘制倡议：

- **高价值、低工作量**（快速胜利）：首先做这些。
- **高价值、高工作量**（重大赌注）：仔细规划这些。值得投资，但需要适当规划。
- **低价值、低工作量**（填充项）：在有空闲容量时做这些。
- **低价值、高工作量**（资金陷阱）：不要做这些。从待办事项中删除。

何时使用：团队规划会议中的可视化优先级。适合建立对权衡的共同理解。

## 依赖项映射

### 识别依赖项

在以下类别中查找依赖项：

- **技术依赖项**：功能 B 需要功能 A 的基础设施工作
- **团队依赖项**：功能需要另一个团队（设计、平台、数据）的工作
- **外部依赖项**：等待供应商、合作伙伴或第三方集成
- **知识依赖项**：在开始之前需要研究或调查结果
- **顺序依赖项**：必须先发布功能 A 才能开始功能 B（共享代码、用户流程）

### 管理依赖项
- 在路线图中明确列出所有依赖项
- 为每个依赖项分配负责人（谁负责解决它）
- 设置“需要日期”：依赖项需要何时解决
- 在依赖项周围建立缓冲区——它们是任何路线图上风险最高的项目
- 早期标记跨团队边界依赖项——这些需要协调
- 制定应急计划：如果依赖项延迟，该怎么办？

### 减少依赖项
- 您能构建一个更简单的版本来避免依赖项吗？
- 您能通过使用接口合约或模拟并行化吗？
- 您能调整顺序以将依赖项提前吗？
- 您能把工作吸收到您的团队中，以消除跨团队协调吗？

## 容量规划

### 估计容量
- 从工程师数量和时间范围开始
- 减去已知开销：会议、轮值、面试、假期、带薪休假
- 常见经验法则：工程师将 60-70% 的时间用于计划中的功能工作
- 考虑新成员的团队适应时间

### 分配容量
大多数产品团队的健康分配：

- **70% 计划功能**：推进战略目标的路线图项目
- **20% 技术健康**：技术债务、可靠性、性能、开发者体验
- **10% 未计划**：缓冲区用于紧急问题、快速胜利和其他团队的请求

根据团队环境调整比例：
- 新产品：更多功能工作，较少技术债务
- 成熟产品：更多技术债务和可靠性投资
- 事故后：更多可靠性，较少功能
- 快速增长：更多可扩展性和性能

### 容量 vs 野心
- 如果路线图承诺超过容量，必须有所取舍
- 不要通过假装人们可以做得更多来解决容量问题——通过削减范围来解决
- 添加到路线图时，始终询问：“什么会移除？”
- 比起过度承诺和失望，承诺较少的事情并可靠地交付更好

## 沟通路线图变更

### 路线图变更时
路线图变更的常见触发因素：
- 领导层的新战略优先级
- 客户反馈或研究改变了优先级
- 技术发现改变了估计
- 另一个团队的依赖项延迟
- 资源变化（团队增长或缩小，关键人员离职）
- 竞争对手的举动需要应对

### 如何沟通变更
1. **承认变更**：直接说明什么在变以及为什么
2. **解释原因**：是什么新信息促成了这个决定？
3. **显示权衡**：为了腾出空间，什么被降级了？或者什么会延迟？
4. **显示新计划**：反映变更的更新路线图
5. **承认影响**：谁受影响以及如何？预期被降级项目的利益相关者需要直接听到这个消息。

### 避免路线图剧变
- 不要因为每条新信息就更改路线图。设定变更的阈值。
- 在自然的节奏（每月、每季度）批量更新路线图，除非事情真正紧急。
- 区分“路线图变更”（战略重新排序）和“范围调整”（正常的执行细化）。
- 跟踪路线图变更的频率。频繁变更可能表明战略不明确，而不是良好的响应能力。

## 输出格式

使用清晰、可扫描的格式。表格适合路线图项目。使用文本状态标签：**完成**、**按计划**、**有风险**、**阻塞**、**未开始**。

## 小贴士

- 路线图是一种沟通工具，不是项目计划。保持正确的海拔——主题和成果，而不是任务。
- 在重新排序时，始终询问发生了什么变化。优先级变化应由新信息驱动，而不是凭空想象。
- 早期标记容量问题。如果路线图的工作量超过团队可以处理的范围，请说明。
- 依赖项是路线图最大的风险。明确显示它们。
- 如果用户要求添加内容，始终询问什么会移除或移动。路线图在容量上是零和的。
