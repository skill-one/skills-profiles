# /customer-escalation

> 如果你看到不熟悉的占位符或需要检查哪些工具已连接，请参阅[CONNECTORS.md](../../CONNECTORS.md)。

将支持问题打包成一个结构化的升级简报，供工程、产品或管理层处理。收集背景信息，结构化复现步骤，评估业务影响，并确定正确的升级目标。

## 使用方法

```
/customer-escalation <问题描述> [客户名称或账户]
```

示例：
- `/customer-escalation Acme Corp间歇性返回500错误`
- `/customer-escalation 数据导出丢失行——本周有3个客户报告了此问题`
- `/customer-escalation SSO登录循环影响所有企业客户`
- `/customer-escalation 客户因缺少审计日志功能而威胁要流失`

## 工作流程

### 1. 理解问题

解析输入并确定：

- **什么出错了或需要什么**：核心的技术或产品问题
- **谁受影响**：特定客户、细分市场或所有用户
- **多长时间**：何时开始？客户等待了多久？
- **已尝试过什么**：任何故障排除或临时解决方案
- **为什么现在升级**：是什么让这个问题需要超出正常支持的注意力

使用下面的“何时升级与在支持中处理”标准来确认这值得升级。

### 2. 收集背景信息

从可用来源汇集相关信息：

- **~~支持平台**（如果已连接）：相关工单、沟通时间线、之前的故障排除
- **~~CRM**（如果已连接）：账户详细信息、关键联系人、之前的升级
- **~~聊天**：关于此问题的内部讨论、其他客户的类似报告
- **~~项目跟踪器**（如果已连接）：相关的错误报告或功能请求、工程状态
- **~~知识库**：已知问题或临时解决方案、相关文档

### 3. 评估业务影响

使用以下影响维度，量化：

- **范围**：影响了多少客户/用户？是否在增加？
- **深度**：受阻还是不便？
- **持续时间**：持续了多久？
- **收入**：ARR风险？影响的待处理交易？
- **时间压力**：硬性截止日期？

### 4. 确定升级目标

使用以下升级级别，确定正确的目标：L2支持、工程、产品、安全或管理层。

### 5. 结构化复现步骤（用于错误）

如果问题是错误，请遵循以下最佳实践，记录清晰的复现步骤，包括环境详细信息和相关证据。

### 6. 生成升级简报

```
## 升级：[一句话总结]

**严重性**：[关键 / 高 / 中]
**目标团队**：[工程 / 产品 / 安全 / 管理层]
**报告人**：[你的名字/团队]
**日期**：[今天的日期]

### 影响
- **受影响的客户**：[谁和多少]
- **工作流程影响**：[他们无法做什么]
- **风险收入**：[如果适用]
- **排队时间**：[这个问题持续了多久]

### 问题描述
[清晰、简洁的问题描述——3-5句话]

### 已尝试过什么
1. [故障排除步骤和结果]
2. [故障排除步骤和结果]
3. [故障排除步骤和结果]

### 复现步骤
[如果适用——遵循以下格式]
1. [步骤]

3. [步骤]
预期：[X]
实际：[Y]
环境：[详细信息]

### 客户沟通
- **最后向客户更新**：[日期和沟通内容]
- **客户期望**：[他们期望什么和何时]
- **升级风险**：[如果未在X时间内解决，他们会进一步升级吗？]

### 需要什么
- [具体请求——"调查根本原因"、"优先处理修复",
  "就X做出产品决策"、"批准Y的例外"]
- **截止日期**：[何时需要解决或更新]

### 支持背景信息
- [相关工单或链接]
```

### 7. 提供下一步行动

生成升级后：

- "想让我在目标团队的~~聊天频道中发布这个吗？"
- "我应该向客户更新一个中间响应吗？"
- "想让我设置一个后续提醒来检查这个问题吗？"
- "我应该起草一个面向客户的更新，说明当前状态吗？"

## 何时升级与在支持中处理

### 在支持中处理时：

- 问题有记录的解决方案或已知临时解决方案
- 它是一个配置或设置问题，你可以解决
- 客户需要指导或培训，而不是修复
- 问题是一个已知限制，有记录的替代方案
- 之前的类似工单在支持级别解决了

### 升级时：

- **技术**：确认的错误需要代码修复，需要基础设施调查，数据损坏或丢失
- **复杂性**：问题超出了支持诊断的能力，需要支持没有的访问权限，涉及自定义实现
- **影响**：多个客户受影响，生产系统宕机，数据完整性风险，安全问题
- **业务**：高风险客户，SLA即将违反或已违反，客户要求高管参与
- **时间**：问题已开放超过SLA，客户等待时间不合理，正常支持渠道没有进展
- **模式**：3个以上客户报告相同问题，反复出现的问题据称已修复，严重程度随时间增加

## 升级级别

### L1 → L2（支持升级）
**来源**：一线支持
**目标**：高级支持 / 技术支持专家
**何时**：问题需要更深入的调查、专门的产品知识或高级故障排除
**包含内容**：工单摘要、已尝试的步骤、客户背景

### L2 → 工程
**来源**：高级支持
**目标**：工程团队（相关产品领域）
**何时**：确认的错误、基础设施问题、需要代码更改、需要系统级调查
**包含内容**：完整的复现步骤、环境详细信息、日志或错误消息、业务影响、客户时间线

### L2 → 产品
**来源**：高级支持
**目标**：产品管理
**何时**：导致客户痛苦的特性差距、需要设计决策、工作流程不符合客户期望、竞争客户需求需要优先排序
**包含内容**：客户用例、业务影响、请求频率、竞争压力（如果已知）

### 任何 → 安全
**来源**：任何支持级别
**目标**：安全团队
**何时**：潜在数据泄露、未经授权的访问、漏洞报告、合规性问题
**包含内容**：观察到的内容、潜在的受影响对象、已采取的即时遏制措施、紧急程度评估
**注意**：安全升级绕过正常级别进程——立即升级，无论你的级别如何

### 任何 → 管理层
**来源**：任何级别（通常是L2或经理）
**目标**：支持领导、执行团队
**何时**：高风险客户威胁要流失、关键账户违反SLA、需要跨职能决策、需要政策例外、公关或法律风险
**包含内容**：完整的业务背景、风险收入、已尝试过什么、需要的具体决策或行动、截止日期

## 业务影响评估

升级时，尽可能量化影响：

### 影响维度

| 维度 | 需要回答的问题 |
|------|---------------|
| **范围** | 受影响的客户/用户有多少？是否在增加？ |
| **深度** | 他们受到多严重的影响？受阻还是不便？ |
| **持续时间** | 持续了多久？何时会变得关键？ |
| **收入** | 风险的ARR是多少？是否有影响的待处理交易？ |
| **声誉** | 这可能成为公开的吗？它是参考客户吗？ |
| **合同** | 是否违反SLA？是否有合同义务？ |

### 严重性简称

- **关键**：生产系统宕机、数据风险、安全漏洞，或多个高价值客户受影响。需要立即关注。
- **高**：主要功能损坏、关键客户受阻、SLA风险。需要当天关注。
- **中**：重大问题但有临时解决方案、重要但非紧急的业务影响。本周需要关注。

## 编写复现步骤

好的复现步骤是bug升级中最重要的东西。遵循以下最佳实践：

1. **从干净的状态开始**：描述起点（账户类型、配置、权限）
2. **具体**："点击仪表板页面右上角的导出按钮"而不是"尝试导出"
3. **包含确切值**：使用具体输入、日期、ID——而不是"输入一些数据"
4. **注意环境**：浏览器、操作系统、账户类型、功能标志、计划级别
5. **捕获频率**：总是可复现？间歇性？只在特定条件下？
6. **包含证据**：截图、错误消息（确切文本）、网络日志、控制台输出
7. **注意你排除了什么**："在Chrome和Firefox中测试——行为相同" "不是账户特定的——在测试账户中复现"

## 升级后的跟进节奏

不要升级后忘记。保持对客户关系的所有权。

| 严重性 | 内部跟进 | 客户更新 |
|-------|---------|---------|
| **关键** | 每2小时 | 每2-4小时（或按SLA） |
| **高** | 每4小时 | 每4-8小时 |
| **中** | 每日 | 每1-2个工作日 |

### 跟进操作
- 与接收团队联系以了解进展
- 即使没有新信息也要更新客户（"我们仍在调查——以下是我们知道的情况"）
- 如果情况变化，调整严重性（更好或更差）
- 在工单中记录所有更新以供审计
- 解决后关闭循环：确认客户、更新内部跟踪、捕获学习成果

## 降级

并非所有升级都会保持升级。当以下情况发生时降级：
- 找到根本原因，这是支持可解决的问题
- 找到临时解决方案，可以解除客户受阻
- 问题自行解决（但仍记录根本原因）
- 新信息改变了严重性评估

降级时：
- 通知你升级到的团队
- 在工单中更新解决方案
- 通知客户解决方案
- 记录学到的内容以供将来参考

## 升级最佳实践

1. 始终量化影响——模糊的升级会被降级
2. 包含错误的复现步骤——这是工程最需要的东西
3. 明确你需要的——"调查"与"修复"与"决定"是不同的请求
4. 设置并沟通截止日期——没有截止日期的紧急性是模糊的
5. 即使升级了技术问题，也要保持对客户关系的所有权
6. 主动跟进——不要等待接收团队来找你
7. 记录一切——升级路径对于模式检测和流程改进非常有价值
