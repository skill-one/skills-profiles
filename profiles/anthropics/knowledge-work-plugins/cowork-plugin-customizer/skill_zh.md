# 协作插件定制

为特定组织定制插件——无论是首次设置通用插件模板，还是调整和完善已配置的插件。

> **查找插件**：要查找插件的源文件，请运行 `find mnt/.local-plugins mnt/.plugins -type d -name "*<plugin-name>*"` 来定位插件目录，然后在修改之前阅读其文件以了解其结构。如果您找不到插件目录，用户可能正在远程容器中运行此对话。中止并告知他们：“目前仅在桌面应用的协作模式下可以定制插件。”

## 确定定制模式

找到插件后，检查是否存在以 `~~` 开头的占位符：`grep -rn '~~\w' /path/to/plugin --include='*.md' --include='*.json'`

> **默认规则**：如果存在 `~~` 占位符，则默认为 **通用插件设置**，除非用户明确要求定制插件的具体部分。

**1. 通用插件设置** — 插件包含以 `~~` 开头的占位符。这些是模板中的定制点，需要用实际值替换（例如，`~~Jira` → `Asana`，`~~your-team-channel` → `#engineering`）。

**2. 范围定制** — 不存在 `~~` 占位符，并且用户要求定制插件的具体部分（例如，“定制连接器”，“更新站立会议技能”，“更改工单工具”）。阅读插件文件以找到相关部分并仅关注这些部分。不要扫描整个插件或呈现不相关的定制项。

> **遗留 `commands/` 目录**：某些插件包含 `commands/` 目录。现在协作界面将这些与技能一起呈现为单个“技能”概念，因此在定制时，请将 `commands/*.md` 文件与 `skills/*/SKILL.md` 文件同样对待。

**3. 一般定制** — 不存在 `~~` 占位符，并且用户希望广泛修改插件。阅读插件文件以了解其当前配置，然后询问用户他们希望更改什么。

> **重要**：切勿更改正在定制的插件或技能的名称。不要重命名目录、文件或插件/技能名称字段。

> **非技术输出**：所有面向用户的输出（待办事项、问题、摘要）必须使用平实的非技术语言编写。切勿向用户提及 `~~` 前缀、占位符或定制点。用插件的功能和组织工具来解释一切。

## 定制工作流程

### 阶段 0：收集用户意图（仅限范围定制和一般定制）

对于 **范围定制** 和 **一般定制**（非通用插件设置），检查用户是否在请求中提供了自由形式的上下文（例如，“定制站立会议技能——我们每天早上在 #eng-updates 中进行异步站立会议”）。

- **如果用户提供了上下文**：记录它并用于在阶段 3 中预填答案——跳过询问用户已经在此处回答的问题。
- **如果用户没有提供上下文**：使用 `AskUserQuestion` 在继续之前问一个开放式问题。根据他们要求定制的对象调整问题——例如，“您对简短技能有什么更改想法？”或“您希望如何更改此插件的工作方式？”保持简短并针对他们的请求。

  使用他们的回复（如果有）作为其余阶段的其他上下文。

### 阶段 1：从知识 MCP 收集上下文

使用公司内部的知识 MCP 收集与定制范围相关的信息。有关按类别详细查询模式的更多信息，请参阅 `references/search-strategies.md`。

**收集的内容**（范围到相关的）：

- 组织使用的工具名称和服务
- 组织流程和工作流
- 团队约定（命名、状态、估算等级）
- 配置值（工作区 ID、项目名称、团队标识符）

**搜索来源**：

1. **Chat/Slack MCP** — 工具提及、集成、工作流讨论
2. **文档 MCP** — 欢迎文档、工具指南、设置说明
3. **电子邮件 MCP** — 许可通知、管理员邮件、设置邀请

记录所有发现结果以用于阶段 3。

### 阶段 2：创建待办事项列表

构建一个适当范围的更改待办事项列表：

- **对于范围定制**：仅包含与用户要求的具体部分相关的项目。
- **对于通用插件设置**：运行 `grep -rn '~~\w' /path/to/plugin --include='*.md' --include='*.json'` 查找所有占位符定制点。按主题分组。
- **对于一般定制**：阅读插件文件，了解当前配置，并根据用户的请求，确定需要更改的内容。

使用用户友好的描述，专注于插件的目的：

- **良好**： "了解公司在站立会议准备方面的工作方式"
- **不良**： "在 skills/standup-prep/SKILL.md 中替换占位符"

### 阶段 3：完成待办事项

使用阶段 0 和阶段 1 的上下文逐个处理每个项目。

**如果用户的自由形式输入（阶段 0）或知识 MCP（阶段 1）提供了明确的答案**：直接应用，无需确认。

**否则**：使用 `AskUserQuestion`。不要假设“行业标准”默认值是正确的——如果用户的输入或知识 MCP 没有提供具体答案，请询问。注意：`AskUserQuestion` 总是包含一个跳过按钮和用于自定义答案的自由文本输入框，因此不要将 `None` 或 `Other` 作为选项。

**更改类型**：

1. **占位符替换**（通用设置）：`~~Jira` → `Asana`，`~~your-org-channel` → `#engineering`
2. **内容更新**：修改说明、技能、工作流或与组织匹配的引用
3. **URL 模式更新**：`tickets.example.com/your-team/123` → `app.asana.com/0/PROJECT_ID/TASK_ID`
4. **配置值**：工作区 ID、项目名称、团队标识符

如果用户不知道或跳过，则保留值不变（对于通用设置，保留 `~~` 开头的占位符）。

### 阶段 4：搜索有用的 MCP

在定制项已解决后，连接在定制过程中识别或更改的工具的 MCP。有关完整工作流程、类别到关键词映射和配置文件格式的更多信息，请参阅 `references/mcp-servers.md`。

对于在定制过程中识别的每个工具：

1. 搜索注册表：`search_mcp_registry(keywords=[...])` 使用 `references/mcp-servers.md` 中的类别关键词，或如果已知，搜索特定工具名称
2. 如果未连接：`suggest_connectors(directoryUuids=["chosen-uuid"])` — 用户完成认证
3. 更新插件的 MCP 配置文件（检查 `plugin.json` 以获取自定义位置，否则在根目录下查找 `.mcp.json`）

收集所有 MCP 结果并在摘要输出中一起呈现（见下文）——在此阶段不要逐个呈现 MCP。

## 打包插件

在应用所有定制后，将插件作为 `.plugin` 文件打包给用户：

1. **压缩插件目录**（不包括 `setup/`，因为它不再需要）：
   ```bash
   cd /path/to/plugin && zip -r /tmp/plugin-name.plugin . -x "setup/*" && cp /tmp/plugin-name.plugin /path/to/outputs/plugin-name.plugin
   ```
2. **向用户展示文件**，并使用 `.plugin` 扩展名，以便他们可以直接安装。 （展示 .plugin 文件将向用户显示为富预览，他们可以在其中查看插件文件，并通过按按钮接受定制。）

> **重要**：始终首先在 `/tmp/` 中创建 zip 文件，然后复制到输出文件夹。直接写入输出文件夹可能会因权限问题失败并留下临时文件。

> **命名**：使用原始插件目录名称作为 `.plugin` 文件（例如，如果插件目录是 `coder`，输出文件应该是 `coder.plugin`）。在定制过程中不要重命名插件及其文件——仅替换占位符值并更新内容。

## 摘要输出

定制后，向用户展示按来源分组的所学内容的摘要。始终包括显示在设置过程中连接了哪些 MCP 以及用户仍需连接哪些 MCP 的 MCP 部分：

```markdown
## 从搜索 Slack

- 您使用 Asana 进行项目管理
- 计划周期为 2 周

## 从搜索文档

- 故事点使用 T 恤尺寸

## 从您的答案

- 工单状态为：待办、进行中、审核中、完成
```

然后展示在设置过程中连接的 MCP 以及用户仍需连接的 MCP，并提供如何连接它们的说明。

如果阶段 1 中没有可用的知识 MCP，并且用户至少需要手动回答一个问题，请在末尾添加一条注释：

> 顺便说一句，连接 Slack 或 Microsoft Teams 等来源可以让我在下次您定制插件时自动找到答案。
