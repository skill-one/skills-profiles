# 技能开发指南（Claude 代码插件）

本指南提供创建有效 Claude 代码插件技能的指导。

## 关于技能

技能是模块化、自包含的包，通过提供专业知识、工作流程和工具来扩展 Claude 的功能。将它们视为特定领域或任务的“入职指南”——它们将 Claude 从通用代理转变为配备过程性知识的专用代理，而任何模型都无法完全拥有这种知识。

### 技能提供的内容

1. 专业化工作流程 - 特定领域的多步骤流程
2. 工具集成 - 与特定文件格式或 API 交互的说明
3. 领域专业知识 - 公司特定知识、模式、业务逻辑
4. 打包资源 - 用于复杂和重复性任务的脚本、参考和资产

### 技能的构成

每个技能都包含一个必需的 `SKILL.md` 文件和可选的打包资源：

```
skill-name/
├── SKILL.md (必需)
│   ├── YAML 前置元数据 (必需)
│   │   ├── name: (必需)
│   │   └── description: (必需)
│   └── Markdown 说明 (必需)
└── 打包资源 (可选)
    ├── scripts/          - 可执行代码 (Python/Bash 等)
    ├── references/       - 意图按需加载到上下文中的文档
    └── assets/           - 用于输出的文件 (模板、图标、字体等)
```

#### SKILL.md (必需)

**元数据质量：** YAML 前置中的 `name` 和 `description` 决定 Claude 何时使用该技能。具体说明技能的作用以及何时使用它。使用第三人称（例如，“当需要...时，应使用此技能”，而不是“使用此技能”）。

#### 打包资源 (可选)

##### 脚本 (`scripts/`)

可执行代码 (Python/Bash 等)，用于需要确定性可靠性或反复重写的任务。

- **包含时机**：当相同代码被反复重写或需要确定性可靠性时
- **示例**：`scripts/rotate_pdf.py` 用于 PDF 旋转任务
- **优点**：令牌高效、确定性、可能无需加载到上下文中执行
- **注意**：脚本可能仍需被 Claude 读取以进行补丁或环境特定调整

##### 参考 (`references/`)

意图按需加载到上下文中以指导 Claude 处理和思考的文档和参考材料。

- **包含时机**：Claude 在工作时应参考的文档
- **示例**：`references/finance.md` 用于金融模式、`references/mnda.md` 用于公司 NDA 模板、`references/policies.md` 用于公司政策、`references/api_docs.md` 用于 API 规格说明
- **用例**：数据库模式、API 文档、领域知识、公司政策、详细工作流程指南
- **优点**：保持 SKILL.md 简洁，仅在 Claude 确定需要时加载
- **最佳实践**：如果文件很大（>10k 字），在 SKILL.md 中包含 grep 搜索模式
- **避免重复**：信息应存在于 SKILL.md 或参考文件中，而不是两者都有。除非它确实是技能的核心，否则请优先使用参考文件来存储详细信息——这可以在保持 SKILL.md 简洁的同时，使信息易于发现，而不会占用上下文窗口。将仅包含必要的程序性指令和工作流程指南保留在 SKILL.md 中；将详细的参考材料、模式和示例移至参考文件。

##### 资产 (`assets/`)

不意图加载到上下文中，而是用于 Claude 产生的输出中的文件。

- **包含时机**：当技能需要用于最终输出的文件时
- **示例**：`assets/logo.png` 用于品牌资产、`assets/slides.pptx` 用于 PowerPoint 模板、`assets/frontend-template/` 用于 HTML/React 模板、`assets/font.ttf` 用于排版
- **用例**：模板、图像、图标、基础代码、字体、被复制或修改的示例文档
- **优点**：将输出资源与文档分离，使 Claude 无需加载文件即可使用它们

### 渐进式披露设计原则

技能使用三级加载系统来高效管理上下文：

1. **元数据（名称 + 描述）** - 始终在上下文中 (~100 字)
2. **SKILL.md 正文** - 当技能触发时 (<5k 字)
3. **打包资源** - Claude 根据需要加载 (无限*)

*无限，因为脚本可以在不读取上下文窗口的情况下执行。

## 技能创建流程

要创建技能，请按顺序遵循“技能创建流程”，除非有明确原因跳过步骤。

### 第 1 步：通过具体示例理解技能

仅在技能的使用模式已经明确理解时才跳过此步骤。即使在使用现有技能时，它仍然很有价值。

要创建有效的技能，请明确理解技能将如何使用的具体示例。这种理解可以来自直接的用户示例或经过用户反馈验证的生成示例。

例如，在构建图像编辑技能时，相关的问题包括：

- “图像编辑技能应支持哪些功能？编辑、旋转、其他？”
- “你能给出一些使用此技能的示例吗？”
- “我可以想象用户会要求移除此图像中的红眼或旋转此图像。你想象此技能的其他使用方式是什么？”
- “用户会说些什么应该触发此技能？”

为了避免让用户感到不知所措，避免在单个消息中问太多问题。从最重要的问题开始，根据需要跟进以提高有效性。

当对技能应支持的功能有清晰的认识时，完成此步骤。

### 第 2 步：规划可重用技能内容

要将具体示例转换为有效的技能，通过以下方式分析每个示例：

1. 考虑如何从头开始执行示例
2. 识别在重复执行这些工作流程时有助于执行的脚本、参考和资产

示例：在构建用于处理“帮助我旋转此 PDF”查询的 `pdf-editor` 技能时，分析显示：

1. 旋转 PDF 需要每次都重写相同的代码
2. `scripts/rotate_pdf.py` 脚本将有助于存储在技能中

示例：在为“为我构建一个待办事项应用”或“为我构建一个跟踪我的步骤的仪表板”查询设计 `frontend-webapp-builder` 技能时，分析显示：

1. 编写前端 Web 应用需要每次都使用相同的 HTML/React 基础代码
2. 包含基础 HTML/React 项目文件的基础模板 `assets/hello-world/` 将有助于存储在技能中

示例：在构建用于处理“今天有多少用户登录？”查询的 `big-query` 技能时，分析显示：

1. 查询 BigQuery 需要每次都重新发现表模式和关系
2. 记录表模式的 `references/schema.md` 文件将有助于存储在技能中

**对于 Claude 代码插件：** 在构建钩子技能时，分析显示：
1. 开发人员需要反复验证 hooks.json 和测试钩子脚本
2. `scripts/validate-hook-schema.sh` 和 `scripts/test-hook.sh` 实用程序将有助于
3. `references/patterns.md` 用于详细的钩子模式，以避免 SKILL.md 膨胀

要确定技能的内容，分析每个具体示例以创建可重用资源列表：脚本、参考和资产。

### 第 3 步：创建技能结构

对于 Claude 代码插件，创建技能目录结构：

```bash
mkdir -p plugin-name/skills/skill-name/{references,examples,scripts}
touch plugin-name/skills/skill-name/SKILL.md
```

**注意：** 与使用 `init_skill.py` 的通用技能创建器不同，插件技能直接在插件的 `skills/` 目录中创建，结构更简单。

### 第 4 步：编辑技能

在编辑（新创建或现有）技能时，请记住该技能是为另一个 Claude 实例创建的。专注于包含对 Claude 有益且非显而易见的信息。考虑哪些程序性知识、特定领域细节或可重用资产将帮助另一个 Claude 实例更有效地执行这些任务。

#### 从可重用技能内容开始

开始实施时，从上面确定的可重用资源开始：`scripts/`、`references/` 和 `assets/` 文件。注意此步骤可能需要用户输入。例如，在实现 `brand-guidelines` 技能时，用户可能需要提供品牌资产或模板以存储在 `assets/` 中，或文档以存储在 `references/` 中。

此外，删除不需要的任何示例文件和目录。仅创建您实际需要的目录（references/、examples/、scripts/）。

#### 更新 SKILL.md

**写作风格：** 使用**祈使/不定式形式**（动词开头的指令），而不是第二人称。使用客观、指令性语言（例如，“要完成 X，请执行 Y”，而不是“你应该做 X”或“如果你需要做 X”）。这有助于 AI 消费的一致性和清晰性。

**描述（前置元数据）：** 使用第三人称格式，并包含具体的触发短语：

```yaml
---
name: 技能名称
description: 当用户询问“特定短语 1”、“特定短语 2”、“特定短语 3”时，应使用此技能。包括用户会说的应触发此技能的确切短语。具体且明确。
version: 0.1.0
---
```

**好的描述示例：**
```yaml
description: 当用户询问“创建钩子”、“添加 PreToolUse 钩子”、“验证工具使用”、“实现基于提示的钩子”，或提到钩子事件（PreToolUse、PostToolUse、Stop）时，应使用此技能。提供全面的钩子 API 指导。
```

**不好的描述示例：**
```yaml
description: 在处理钩子时使用此技能。  # 错误的人称，模糊
description: 当用户需要钩子帮助时加载。  # 不是第三人称
description: 提供钩子指导。  # 没有触发短语
```

要完成 SKILL.md 正文，回答以下问题：

1. 几句话说明技能的用途是什么？
2. 何时应使用技能？（将此包含在前置元数据描述中，并包含具体的触发短语）
3. 在实践中，Claude 应如何使用技能？上面开发的可重用技能内容都应被引用，以便 Claude 知道如何使用它们。

**保持 SKILL.md 简洁：** 正文目标为 1,500-2,000 字。将详细内容移至 references/：
- 详细模式 → `references/patterns.md`
- 高级技术 → `references/advanced.md`
- 迁移指南 → `references/migration.md`
- API 参考 → `references/api-reference.md`

**在 SKILL.md 中引用资源：**
```markdown
## 额外资源

### 参考文件

有关详细模式和技术的参考：
- **`references/patterns.md`** - 常见模式
- **`references/advanced.md`** - 高级用例

### 示例文件

`examples/` 中的工作示例：
- **`example-script.sh`** - 工作示例
```

### 第 5 步：验证和测试

**对于插件技能，验证与通用技能不同：**

1. **检查结构**：`plugin-name/skills/skill-name/` 中的技能目录
2. **验证 SKILL.md**：具有名称和描述的有效 YAML 前置元数据
3. **检查触发短语**：描述中包含用户会说的具体查询
4. **验证写作风格**：正文使用祈使/不定式形式，不是第二人称
5. **测试渐进式披露**：SKILL.md 简洁（~1,500-2,000 字），详细内容在 references/
6. **检查参考**：所有引用的文件都存在
7. **验证示例**：示例完整且正确
8. **测试脚本**：脚本可执行且工作正常

**使用技能审查代理：**
```
询问：“审查我的技能并检查它是否符合最佳实践”
```

技能审查代理将检查描述质量、内容组织和渐进式披露。

### 第 6 步：迭代

测试技能后，用户可能会要求改进。这通常发生在使用技能后，对技能表现有清晰的上下文。

**迭代工作流程：**
1. 在真实任务上使用技能
2. 注意到的困难或不效率
3. 确定如何更新 SKILL.md 或打包资源
4. 实施更改并再次测试

**常见改进：**
- 加强描述中的触发短语
- 将长段落从 SKILL.md 移至 references/
- 添加缺失的示例或脚本
- 澄清模糊的指令
- 添加边缘情况处理

## 插件特定注意事项

### 技能在插件中的位置

插件技能位于插件的 `skills/` 目录中：

```
my-plugin/
├── .claude-plugin/
│   └── plugin.json
├── commands/
├── agents/
└── skills/
    └── my-skill/
        ├── SKILL.md
        ├── references/
        ├── examples/
        └── scripts/
```

### 自动发现

Claude 代码自动发现技能：
- 扫描 `skills/` 目录
- 查找包含 `SKILL.md` 的子目录
- 始终加载技能元数据（名称 + 描述）
- 当技能触发时加载 SKILL.md 正文
- 根据需要加载参考/示例

### 无需打包

插件技能作为插件的一部分分发，而不是作为单独的 ZIP 文件。用户在安装插件时获得技能。

### 插件中的测试

通过本地安装插件来测试技能：

```bash
# 使用 --plugin-dir 测试
cc --plugin-dir /path/to/plugin

# 提出应触发技能的问题
# 验证技能加载正确
```

## 渐进式披露实践

### SKILL.md 中包含的内容

**始终加载（当技能触发时）：**
- 核心概念和概述
- 基本程序和流程
- 快速参考表格
- 指向参考/示例/脚本的指针
- 最常见的用例

**保持在 3,000 字以下，理想情况下 1,500-2,000 字**

### references/ 中包含的内容

**移至 references/（按需加载）：**
- 详细模式和高级技术
- 综合性 API 文档
- 迁移指南
- 边缘情况和故障排除
- 广泛的示例和逐步指南

**每个参考文件可以很大（2,000-5,000+ 字）**

### examples/ 中包含的内容

**工作代码示例：**
- 完整、可运行的脚本
- 配置文件
- 模板文件
- 真实世界使用示例

**用户可以直接复制和修改这些内容**

### scripts/ 中包含的内容

**实用脚本：**
- 验证工具
- 测试辅助工具
- 解析实用程序
- 自动化脚本

**应该是可执行的并记录在案**

## 写作风格要求

### 祈使/不定式形式

使用动词开头的指令，而不是第二人称：

**正确（祈使）：**
```
要创建钩子，请定义事件类型。
配置 MCP 服务器以进行身份验证。
使用前验证设置。
```

**不正确（第二人称）：**
```
你应该通过定义事件类型来创建钩子。
你需要配置 MCP 服务器。
你必须在使用前验证设置。
```

### 描述中的第三人称

前置元数据描述必须使用第三人称：

**正确：**
```yaml
description: 当用户询问“创建 X”、“配置 Y”...时，应使用此技能。
```

**不正确：**
```yaml
description: 当你想创建 X...时，使用此技能。
description: 当用户询问...时加载此技能。
```

### 客观、指令性语言

专注于要做什么，而不是谁应该做什么：

**正确：**
```
使用 sed 解析前置元数据。
使用 grep 提取字段。
在使用前验证值。
```

**不正确：**
```
你可以解析前置元数据...
Claude 应该提取字段...
用户可能会验证值...
```

## 应避免的常见错误

### 错误 1：触发描述薄弱

❌ **不好：**
```yaml
description: 提供与钩子工作的指导。
```

**为什么不好**：模糊、没有具体触发短语、不是第三人称

✅ **好：**
```yaml
description: 当用户询问“创建钩子”、“添加 PreToolUse 钩子”、“验证工具使用”，或提到钩子事件时，应使用此技能。提供全面的钩子 API 指导。
```

**为什么好**：第三人称、具体短语、具体场景

### 错误 2：SKILL.md 中内容过多

❌ **不好：**
```
skill-name/
└── SKILL.md  (8,000 字 - 所有内容都在一个文件中)
```

**为什么不好**：加载技能时上下文膨胀，详细内容始终加载

✅ **好：**
```
skill-name/
├── SKILL.md  (1,800 字 - 核心要素)
└── references/
    ├── patterns.md (2,500 字)
    └── advanced.md (3,700 字)
```

**为什么好**：渐进式披露，详细内容按需加载

### 错误 3：使用第二人称写作

❌ **不好：**
```markdown
你应该从阅读配置文件开始。
你需要验证输入。
你可以使用 grep 工具搜索。
```

**为什么不好**：第二人称、不是祈使形式

✅ **好：**
```markdown
从阅读配置文件开始。
在使用前验证输入。
使用 grep 工具搜索模式。
```

**为什么好**：祈使形式、直接指令

### 错误 4：遗漏资源引用

❌ **不好：**
```markdown
# SKILL.md

[核心内容]

[没有提及 references/ 或 examples/]
```

**为什么不好**：Claude 不知道参考文件的存在

✅ **好：**
```markdown
# SKILL.md

[核心内容]

## 额外资源

### 参考文件
- **`references/patterns.md`** - 详细模式
- **`references/advanced.md`** - 高级技术
```

## 最佳实践总结

✅ **要：**
- 描述中使用第三人称（“当需要...时，应使用此技能”）
- 包含具体触发短语（“创建 X”、“配置 Y”）

- 使用渐进式披露（将细节移至 references/)
- 使用祈使/不定式形式
- 清晰地引用支持文件
- 提供工作示例
- 创建用于常见操作的实用脚本
- 学习 plugin-dev 的技能作为模板

❌ **不要：**
- 任何地方使用第二人称
- 模糊的触发条件
- 将所有内容都放在 SKILL.md 中（没有 references/ 的情况下 >3,000 字）
- 使用第二人称（“你应该...”）
- 留下未引用的资源
- 包含损坏或不完整的示例
- 跳过验证

## 实施工作流程

为您的插件创建技能：

1. **理解用例**：确定技能使用的具体示例
2. **规划资源**：确定需要哪些脚本/参考/示例
3. **创建结构**：`mkdir -p skills/skill-name/{references,examples,scripts}`
4. **编写 SKILL.md**：
   - 前置元数据，包含第三人称描述和触发短语
   - 正文简洁（1,500-2,000 字）在祈使形式
   - 引用支持文件
5. **添加资源**：按需创建 references/、examples/、scripts/
6. **验证**：检查描述、写作风格、组织
7. **测试**：验证技能在预期触发时加载
8. **迭代**：根据使用情况进行改进

专注于强大的触发描述、渐进式披露和祈使写作风格，以创建有效的技能，这些技能在需要时加载并提供有针对性的指导。
