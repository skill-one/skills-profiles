# 技能创建器

一个用于创建新技能并迭代改进它们的技能。

从高层次来看，创建技能的过程如下：

- 确定你想让技能做什么以及大致如何做
- 撰写技能的草稿
- 创建一些测试提示，并在它们上运行带有访问权限的 claude
- 帮助用户从定性和定量两个方面评估结果
  - 虽然运行在后台，但如果还没有定量的评估（如果有，你可以使用或修改你认为需要改变的内容），则起草一些定量的评估。然后向用户解释它们（如果它们已经存在，则解释现有的评估）
  - 使用 `eval-viewer/generate_review.py` 脚本向用户展示结果供他们查看，并让他们查看定量指标
- 根据用户对结果的反馈（以及如果从定量基准中明显发现任何明显的缺陷）重新编写技能
- 重复直到你满意为止
- 扩展测试集并在更大规模上再次尝试

在使用此技能时，你的工作是弄清楚用户在此过程中的位置，然后跳入并帮助他们通过这些阶段。例如，也许他们想“我想制作一个用于 X 的技能”。你可以帮助他们缩小范围，撰写草稿，编写测试用例，确定他们想要如何评估，运行所有提示，并重复。

另一方面，也许他们已经有一个技能的草稿。在这种情况下，你可以直接进入评估/迭代部分。

当然，你应该始终保持灵活，如果用户说“我不需要运行大量的评估，只是和我一起感觉一下”，你可以那样做。

然后，在技能完成后（但顺序是灵活的），你还可以运行技能描述改进器，我们有一个完整的单独脚本用于优化技能的触发。

酷？酷。

## 与用户沟通

技能创建器可能会被对编码术语熟悉程度不同的人使用。如果你没听说过（而且你怎么会呢，它只是最近才开始），现在有一种趋势，Claude 的力量正在激励水管工打开他们的终端，父母和祖父母谷歌“如何安装 npm”。另一方面，大多数用户可能对计算机比较熟悉。

所以请注意上下文线索，以了解如何措辞你的沟通！在默认情况下，只是给你一些想法：

- “评估”和“基准”是边缘的，但可以
- 对于“JSON”和“断言”，你需要在用户明确知道这些是什么之后再使用它们，而无需解释它们

如果你不确定，可以简要解释术语，并且如果你不确定用户是否会理解，可以自由地用简短的定义来澄清术语。

## 创建技能

### 捕获意图

首先了解用户的意图。当前的对话可能已经包含用户想要捕获的工作流程（例如，他们说“把它变成一个技能”。如果是这样，请先从对话历史中提取答案——使用的工具、步骤的顺序、用户进行的更正、观察到的输入/输出格式。用户可能需要填写空白，并在继续到下一步之前确认。

1. 这个技能应该让 Claude 能够做什么？
2. 什么时候应该触发这个技能？（什么用户短语/上下文）
3. 预期的输出格式是什么？
4. 我们是否应该设置测试用例来验证技能是否正常工作？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流步骤）受益于测试用例。具有主观输出的技能（写作风格、艺术）通常不需要它们。根据技能类型建议适当的默认值，但让用户决定。

### 访谈和研究

主动询问关于边缘情况、输入/输出格式、示例文件、成功标准以及依赖项的问题。等到你弄清楚这部分后再编写测试提示。

检查可用的 MCPs - 如果对研究有用（搜索文档、找到类似的技能、查找最佳实践），如果可用，则通过子代理并行研究，否则内联。做好准备，以减少对用户的负担。

### 编写 SKILL.md

根据用户访谈，填写这些组件：

- **name**：技能标识符
- **description**：何时触发，做什么。这是主要的触发机制——包括技能做什么以及何时使用它的特定上下文。所有“何时使用”的信息都放在这里，而不是在正文中。注意：目前 Claude 有一个趋势，即“欠触发”技能——在它们有用时不会使用它们。为了解决这个问题，请使技能描述稍微“强迫”。例如，而不是“如何构建一个简单的快速仪表板来显示内部 Anthropic 数据”，你可以写“如何构建一个简单的快速仪表板来显示内部 Anthropic 数据。确保在用户提到仪表板、数据可视化、内部指标或想要显示任何类型的公司数据时使用此技能，即使他们没有明确要求“仪表板。””
- **兼容性**：必需的工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能的构成

```
skill-name/
├── SKILL.md (必需)
│   ├── YAML 前置文本 (name, description 必需)
│   └── Markdown 指令
└── 嵌套资源 (可选)
    ├── scripts/    - 用于确定性/重复性任务的执行代码
    ├── references/ - 需要在需要时加载到上下文中的文档
    └── assets/     - 用于输出的文件（模板、图标、字体）
```

#### 逐步披露

技能使用三级加载系统：

1. **元数据**（名称 + 描述）- 始终在上下文中（约 100 字）
2. **SKILL.md 正文** - 每当技能触发时都在上下文中（理想情况下少于 500 行）
3. **嵌套资源** - 需要时（无限制，脚本可以在不加载的情况下执行）

这些字数是大约的，如果你需要，可以自由地更长。

**关键模式：**
- 保持 SKILL.md 少于 500 行；如果你接近这个限制，请添加一个额外的层级，并提供清晰的指向，说明使用技能的模型应该去哪里继续跟进。
- 从 SKILL.md 中清晰地引用文件，并提供何时阅读它们的指导
- 对于大于 300 行的大文件，请包含目录

**域组织**：当技能支持多个域/框架时，按变体组织：

```
cloud-deploy/
├── SKILL.md (工作流 + 选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

Claude 只读取相关的参考文件。

#### 缺乏惊喜原则

不言而喻，技能不得包含恶意软件、利用代码或任何可能危害系统安全的内容。技能的内容不应在描述时让用户感到意外。不要配合创建误导性技能或设计用于促进未经授权的访问、数据泄露或其他恶意活动的技能。例如，“扮演 XYZ 角色”是可以的。

#### 编写模式

在指令中优先使用祈使句。

**定义输出格式** - 你可以这样做：

```markdown
## 报告结构
始终使用此确切模板：
# [标题]
## 执行摘要
## 关键发现
## 建议
```

**示例模式** - 包含示例很有用。你可以这样格式化它们（但如果“输入”和“输出”在示例中，你可能需要稍微偏离一点）：

```markdown
## 提交信息格式
**示例 1：**
输入：使用 JWT 令牌添加用户身份验证
输出：feat(auth)：实现基于 JWT 的身份验证
```

### 编写风格

尝试向模型解释为什么事情很重要，而不是使用强硬的 MUSTS。使用心智理论，并尝试使技能具有通用性，而不是针对特定示例过于狭窄。先写一个草稿，然后用新鲜的眼光审视它并进行改进。

### 测试用例

在编写技能草稿后，构思 2-3 个现实的测试提示——真实用户实际会说的那种。将它们与用户分享：[你不必使用此确切语言]“我想尝试几个测试用例。这些看起来对吗，或者你想添加更多？”然后运行它们。

将测试用例保存到 `evals/evals.json`。现在不要编写断言——只是提示。你将在下一步中起草断言，同时运行正在进行。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示",
      "expected_output": "预期结果的描述",
      "files": []
    }
  ]
}
```

查看 `references/schemas.md` 以获取完整架构（包括 `assertions` 字段，你将在下一步中添加它）。

## 运行和评估测试用例

这一部分是一个连续的序列——不要中途停止。不要使用 `/skill-test` 或任何其他测试技能。

将结果放在 `<skill-name>-workspace/` 中，作为技能目录的兄弟。在 workspace 中，按迭代组织结果 (`iteration-1/`, `iteration-2/` 等)，在其中，每个测试用例都有一个目录 (`eval-0/`, `eval-1/` 等)。不要事先创建所有这些——只是按需创建目录。

### 第一步：在同一轮中生成所有运行（带技能和基线）

对于每个测试用例，在同一轮中生成两个子代理——一个带技能，一个不带。这很重要：不要先生成带技能的运行，然后再回来生成基线。一次性启动所有内容，以便它们大约在同一时间完成。

**带技能的运行：**

```
执行此任务：
- 技能路径：<技能路径>
- 任务：<评估提示>
- 输入文件：<如果有任何评估文件，或“无”>
- 保存输出到：<workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 保存的输出：<用户关心的——例如，“.docx 文件”，“最终的 CSV”>
```

**基线运行**（相同的提示，但基线取决于上下文）：
- **创建新技能**：没有任何技能。相同的提示，没有技能路径，保存到 `without_skill/outputs/`。
- **改进现有技能**：旧版本。在编辑之前，快照技能 (`cp -r <skill-path> <workspace>/skill-snapshot/`)，然后将基线子代理指向快照。保存到 `old_skill/outputs/`。

为每个测试用例编写 `eval_metadata.json`（断言现在可以为空）。给每个评估一个描述性的名称，基于它正在测试的内容——不仅仅是“eval-0”。也使用此名称作为目录。如果此迭代使用新的或修改过的评估提示，为每个新的评估目录创建这些文件——不要假设它们从以前的迭代中继承。

```json
{
  "eval_id": 0,
  "eval_name": "在此处提供描述性名称",
  "prompt": "用户的任务提示",
  "assertions": []
}
```

### 第二步：在运行进行时，起草断言

不要只是等待运行完成——你可以利用这段时间进行有产品性的工作。为每个测试用例起草定量的断言，并向用户解释它们。如果断言已经存在于 `evals/evals.json` 中，请审查它们并向用户解释它们检查的内容。

好的断言是客观可验证的，并且具有描述性名称——它们应该在基准查看器中清晰易读，以便有人浏览结果时立即了解每个断言检查的内容。主观技能（写作风格、设计质量）最好进行定性评估——不要强迫断言在需要人类判断的事情上使用。

更新 `eval_metadata.json` 文件和 `evals/evals.json` 文件中的断言。还向用户解释他们将看到的内容——定性的输出和定量的基准。

### 第三步：在运行完成时，捕获时间数据

当每个子代理任务完成时，你会收到一个包含 `total_tokens` 和 `duration_ms` 的通知。立即将此数据保存到运行目录中的 `timing.json` 中：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获此数据的唯一机会——它通过任务通知提供，并且不会持久化到其他地方。处理每个通知，而不是尝试批量处理它们。

### 第四步：评分、汇总并启动查看器

一旦所有运行完成：

1. **对每个运行进行评分**——生成一个评分子代理（或内联评分），它读取 `agents/grader.md` 并评估每个断言与输出。将结果保存到每个运行目录中的 `grading.json` 中。评分.json 期望数组必须使用 `text`、`passed` 和 `evidence`（而不是 `name`/`met`/`details` 或其他变体）——查看器依赖于这些确切的字段名称。对于可以编程检查的断言，编写并运行一个脚本，而不是肉眼检查——脚本更快、更可靠，并且可以在迭代中重复使用。

2. **汇总到基准**——运行技能创建器目录中的聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这将生成 `benchmark.json` 和 `benchmark.md`，其中包含每个配置的通过率、时间和令牌，以及均值 ± 标准差和差异。如果手动生成 benchmark.json，请查看 `references/schemas.md` 以获取查看器期望的确切架构。
将带技能的版本放在其基线版本之前。

3. **进行分析师检查**——阅读基准数据并展示汇总统计数据可能隐藏的模式。查看 `agents/analyzer.md`（“分析基准结果”部分）以了解要查找的内容——例如，始终通过而不论技能的断言（非区分性）、高变差的评估（可能不稳定）以及时间/令牌权衡。

4. **启动查看器**，同时显示定性和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于迭代 2+，还传递 `--previous-workspace <workspace>/iteration-<N-1>`。

   **Cowork / headless 环境**：如果 `webbrowser.open()` 不可用或环境没有显示器，请使用 `--static <output_path>` 将其写入一个独立的 HTML 文件，而不是启动服务器。当用户点击“提交所有评论”时，反馈将作为 `feedback.json` 文件下载。下载后，将 `feedback.json` 复制到 workspace 目录以供下一次迭代使用。

注意：请使用 generate_review.py 创建查看器；不需要编写自定义 HTML。

5. **告诉用户**类似：“我已经在您的浏览器中打开了结果。有两个选项卡——“输出”允许您逐个查看每个测试用例并留下反馈，“基准”显示定量比较。完成后，请回来并告诉我。”

### 用户在查看器中看到的内容

“输出”选项卡一次显示一个测试用例：
- **提示**：给定的任务
- **输出**：技能生成的文件，尽可能内联显示
- **上一个输出**（迭代 2+）：折叠部分显示上一次迭代的输出
- **正式评分**（如果运行了评分）：折叠部分显示断言通过/失败
- **反馈**：一个文本框，在键入时自动保存
- **上一个反馈**（迭代 2+）：上次评论，显示在文本框下方

“基准”选项卡显示统计摘要：每个配置的通过率、时间和令牌，以及每个评估的细分和分析员观察。

通过上一/下一按钮或箭头键进行导航。完成时，他们点击“提交所有评论”，这将保存所有反馈到 `feedback.json`。

### 第五步：读取反馈

当用户告诉你他们完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "图表缺少坐标轴标签", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "完美，喜欢这个", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空的反馈意味着用户认为它很好。专注于用户有具体投诉的测试用例进行改进。

完成查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是循环的核心。你已经运行了测试用例，用户已经审查了结果，现在你需要根据他们的反馈来改进技能。

### 如何思考改进

1. **从反馈中泛化**。这里的大体情况是我们正在尝试创建可以在许多不同提示中被使用百万次（也许字面意义上，甚至更多谁知道）的技能。在这里，你和用户在只有几个示例上迭代，因为这样可以帮助更快地移动。用户对这些示例了如指掌，并且对他们来说快速评估新输出很方便。但如果你和用户正在编写的技能只在这些示例上工作，它就是无用的。与其说进行琐碎的过度拟合的更改，或者进行压迫性的限制性的 MUSTS，如果存在一些固执的问题，你可能会尝试使用不同的隐喻，或者建议不同的工作模式。尝试相对便宜，也许你会找到一些很棒的东西。

2. **保持提示简洁**。删除那些没有发挥作用的东西。确保阅读转录本，而不仅仅是最终输出——如果看起来技能正在让模型浪费时间做无生产性的事情，你可以尝试删除使模型这样做的那部分技能，看看会发生什么。

3. **解释原因**。努力解释你要求模型做的一切背后的原因。今天的 LLM 很聪明。它们有很好的心智理论，当给它们一个良好的 harness 时，它们可以超越死记硬背的指令并真正地实现事情。即使用户的反馈简洁或沮丧，也要努力理解任务以及用户为什么写他们写的东西，以及他们实际上写了什么，然后将这种理解转化为指令。如果你发现自己写的是 ALL 或 NEVER 在所有大写字母中，或者使用超级严格的结构，这是一个黄色标志——如果可能，重新构建并解释原因，以便模型理解你要求的东西为什么很重要。这是一种更有人性、更强大、更有效的方法。

4. **寻找跨测试用例的重复工作**。阅读测试运行的转录本，注意如果所有子代理都独立编写了类似的辅助脚本或采取了相同的多步骤方法来处理某事。如果所有 3 个测试用例都导致子代理编写了 `create_docx.py` 或 `build_chart.py`，这是一个强烈的信号，表明技能应该捆绑该脚本。编写一次，放在 `scripts/` 中，并告诉技能使用它。这将节省未来每次调用都不再重新发明轮子。

这项任务非常重要（我们正在尝试每年创造数十亿美元的经济价值！），你的思考时间不是障碍；花时间仔细思考。我建议写一个草稿修订版，然后以全新的眼光审视它并进行改进。真的尽力去理解用户的想法和需求。

### 迭代循环

改进技能后：

1. 将你的改进应用到技能
2. 重新运行所有测试用例到一个新的 `iteration-<N+1>/` 目录，包括基线运行。如果你在创建一个新技能，基线始终是 `without_skill`（没有技能）——这在迭代中保持不变。如果你在改进一个现有技能，请根据你的判断确定基线：用户带来的原始版本，或以前的迭代。
3. 使用 `--previous-workspace` 指向以前的迭代启动审查者
4. 等待用户审查并告诉你他们完成
5. 读取新的反馈，再次改进，重复

继续进行，直到：
- 用户说他们满意
- 反馈都是空的（一切看起来都很好）
- 你没有取得有意义的进展

## 高级：盲比较

对于你想要在两个技能版本之间进行更严格的比较的情况（例如，用户问“新版本实际上更好吗？”），有一个盲比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 以了解详细信息。基本思想是：给两个输出给一个独立的代理，不要告诉它哪个是哪个，让它判断质量。然后分析赢家为什么赢了。

这是可选的，需要子代理，大多数用户不需要它。人类审查循环通常足够了。

## 描述优化

SKILL.md 前置文本中的描述字段是决定 Claude 是否调用技能的主要机制。在创建或改进技能后，提供优化描述以获得更好的触发准确性的服务。

### 第一步：生成触发评估查询

创建 20 个评估查询——应该触发和不应该触发的混合。保存为 JSON：

```json
[
  {"query": "用户提示", "should_trigger": true},
  {"query": "另一个提示", "should_trigger": false}
]
```

查询必须是现实的，Claude Code 或 Claude.ai 用户实际上会输入的。不要抽象请求，而是具体和具体的请求，有相当多的细节。例如，文件路径、关于用户工作或情况的个人背景、列名和值、公司名称、URL。一点背景故事。有些可能是小写的或包含缩写或拼写错误或口语。使用混合的不同长度，并专注于边缘情况，而不是使它们清晰明确（用户将有机会签署它们）。

不良：`"格式化这些数据"`, `"从 PDF 中提取文本"`, `"创建一个简单的快速仪表板来显示内部 Anthropic 数据"`

良好：`"好的，我的老板刚刚发给我这个 xlsx 文件（它在我的下载中，可能叫'Q4 销售最终 FINAL v2.xlsx')，她想要我添加一个显示利润率的列，我认为收入在列 C，成本在列 D 我认为"`

对于 **应该触发** 的查询（8-10），思考覆盖范围。你想以不同的方式表达相同的意图——有些正式，有些随意。包括用户没有明确命名技能或文件类型但显然需要的情况。扔进一些不常见的用例和某些技能与另一个技能竞争但应该获胜的情况。

最有价值的是“近失”——共享关键字或概念但实际需要不同内容的查询。思考相邻域，模糊的措辞，其中简单的关键字匹配会导致触发，但实际上需要其他工具更合适，以及查询触及技能执行的内容，但在另一个工具更合适的情况下。

要避免的事情：不要使“编写一个斐波那契函数”作为“PDF 技能”的负面测试太容易——Claude 可以直接用基本工具处理它们。复杂的、多步骤的或专门的查询在描述匹配时可靠地触发技能，因为 Claude 可以直接用基本工具处理它们。这意味着你的评估查询应该足够实质性，以便 Claude 实际上可以从技能中受益。简单的查询，如“读取文件 X”，是糟糕的测试用例——无论描述质量如何，它们都不会触发技能。

### 第二步：与用户审查

使用 HTML 模板向用户展示评估集以供审查：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项的 JSON 数组（没有引号——它是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能的当前描述
3. 写入临时文件（例如，`/tmp/eval_review_<skill-name>.html`）并打开它：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询，切换应该触发，添加/删除条目，然后点击“导出评估集”
5. 文件下载到 `~/Downloads/eval_set.json` — 检查下载文件夹以获取最新版本，以防有多个（例如，`eval_set (1).json`）

这一步很重要——评估查询很差会导致描述很差。

### 第三步：运行优化循环

告诉用户：“这可能需要一些时间——我将后台运行优化循环，并定期检查它。”

将评估集保存到 workspace，然后后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

在运行期间，定期尾随输出以向用户提供更新，说明它处于哪个迭代以及分数看起来如何。

这会自动处理完整的优化循环。它将评估集分成 60% 训练和 40% 保留的测试，评估当前描述（运行每个查询 3 次以获得可靠的触发率），然后调用 Claude 提出改进建议，基于失败的内容。它重新评估每个新描述在训练和测试上的评估，最多迭代 5 次。完成后，它打开一个 HTML 报告在浏览器中显示每个迭代的分数，并返回 JSON，其中 `best_description` 由测试分数选择，而不是训练分数以避免过拟合。

### 技能触发的工作原理

理解触发机制有助于设计更好的评估查询。技能以名称 + 描述的形式出现在 Claude 的 `available_skills` 列表中，Claude 根据描述决定是否咨询技能。重要的是要知道，Claude 只会在它自己无法轻松处理的任务上咨询技能——简单的、单步骤的查询，如“读取此 PDF”可能不会触发技能，即使描述匹配完美，因为 Claude 可以直接用基本工具处理它们。复杂的、多步骤的或专门的查询在描述匹配时可靠地触发技能，因为 Claude 可以直接用基本工具处理它们。这意味着你的评估查询应该足够实质性，以便 Claude 实际上可以从技能中受益。简单的查询，如“读取文件 X”是糟糕的测试用例——无论描述质量如何，它们都不会触发技能。

### 第四步：应用结果

从 JSON 输出中获取 `best_description` 并更新技能的 SKILL.md 前置文本。向用户展示前后，并报告分数。

### 打包和展示（仅当 `present_files` 工具可用时）

检查你是否可以访问 `present_files` 工具。如果你不能，跳过这一步。如果你可以，打包技能并展示 .skill 文件给用户：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包后，引导用户到生成的 `.skill` 文件路径，以便他们可以安装它。

## Claude.ai 特定说明

在 Claude.ai 中，核心工作流程与相同（草稿 → 测试 → 审查 → 改进 → 重复），但由于 Claude.ai 没有子代理，一些机制发生了变化。这里是需要调整的地方：

**运行测试用例**：没有子代理意味着没有并行执行。对于每个测试用例，读取技能的 SKILL.md，然后按照其指令完成测试提示。逐个进行。这比独立的子代理（你编写了技能并运行它，所以你有完整的上下文）不那么严格，但这是一个有用的anity check——并且人类审查步骤可以弥补。跳过基线运行——只是使用技能来完成任务，如请求所示。

**审查结果**：如果你无法打开浏览器（例如，Claude.ai 的 VM 没有显示器，或者你在一个远程服务器上），跳过浏览器审查器。相反，直接在对话中呈现结果。对于每个测试用例，显示提示和输出。如果输出是一个用户需要查看的文件（如 .docx 或 .xlsx），将其保存到文件系统并告诉他们位置以便他们可以下载并检查它。直接在对话中请求反馈：“这个看起来怎么样？你有什么想要更改的吗？”

**基准测试**：跳过定量基准测试——它依赖于基线比较，在没有子代理的情况下没有意义。专注于用户的定性反馈。

**迭代循环**：与之前一样——改进技能，重新运行测试用例，请求反馈——只是中间没有浏览器审查器。你可以仍然将结果组织到迭代目录中，如果你有文件系统。

**描述优化**（`run_loop.py` / `run_eval.py`）应该可以在 Cowork 中正常工作，因为它使用 `claude -p` 通过子进程，而不是浏览器，但请在完成技能并确认它处于良好状态后，保存它。

**更新现有技能**：用户可能要求你更新现有技能，而不是创建新技能。在这种情况下：
- **保留原始名称**。注意技能的目录名称和 `name` 前置文本——使用它们不变。例如，如果已安装的技能是 `research-helper`，输出 `research-helper.skill`（不是 `research-helper-v2`）。
- **在可写位置复制到临时文件之前**。安装技能路径可能是只读的。将其复制到 `/tmp/skill-name/`，在那里编辑，然后从副本打包。
- **如果手动打包，请先在 `/tmp/` 中进行**，然后复制到输出目录——直接写入可能会因权限问题失败。

## Cowork 特定说明

如果你在 Cowork 中，需要知道的主要事情是：

- 你有子代理，所以主要工作流程（并行生成测试用例，运行基线，评分等）都有效。(但是，如果你遇到严重的超时问题，运行测试提示按顺序而不是并行也是可以的。)
- 你没有浏览器或显示器，所以在生成评估查看器时，使用 `--static <output_path>` 将其写入一个独立的 HTML 文件，而不是启动服务器。然后向用户提供一个链接，他们可以点击以在他们的浏览器中打开 HTML。
- 无论什么原因，Cowork 设置似乎使 Claude 不太愿意在运行测试后生成评估查看器，所以重申一下：无论你在 Cowork 中还是在 Claude Code 中，在运行测试后，你都应该始终生成评估查看器，以便人类在自行修改技能之前查看示例。使用 `generate_review.py`（而不是编写你自己的定制 HTML 代码）。
