# Claude 代码插件代理开发

## 概述

代理是处理复杂多步骤任务的独立子进程。理解代理结构、触发条件和系统提示设计，能够创建强大的自主功能。

**关键概念：**
- 代理用于自主工作，命令用于用户发起的操作
- Markdown 文件格式，带 YAML 前置文本
- 通过描述字段触发，并附带示例
- 系统提示定义代理行为
- 模型和颜色自定义

## 代理文件结构

### 完整格式

```markdown
---
name: agent-identifier
description: 当 [触发条件] 时使用此代理。典型触发场景包括 [散文场景1]、[散文场景2] 和 [散文场景3]。有关具体示例，请参阅代理正文中的“何时调用”部分。
model: inherit
color: blue
tools: ["Read", "Write", "Grep"]
---

你是 [代理角色描述]...

## 何时调用

[两到四个代表性散文场景，例如：]
- **[场景名称]。** [情况描述以及代理应执行的操作。]
- **[场景名称]。** [相同。]

**你的核心职责：**
1. [职责1]
2. [职责2]

**分析流程：**
[分步工作流]

**输出格式：**
[返回内容]
```

## 前置文本字段

### name (必填)

用于命名空间和调用的代理标识符。

**格式：** 仅限小写字母、数字和连字符
**长度：** 3-50个字符
**模式：** 必须以字母数字开头和结尾

**良好示例：**
- `code-reviewer`
- `test-generator`
- `api-docs-writer`
- `security-analyzer`

**不良示例：**
- `helper` (过于通用)
- `-agent-` (以连字符开头/结尾)
- `my_agent` (不允许下划线)
- `ag` (太短，< 3个字符)

### description (必填)

定义Claude何时触发此代理。**这是最重要的字段**——每当代理被注册时，它都会被加载到上下文中，以便 harness 可以决定何时派发。

**必须包含：**
1. 触发条件 ("使用此代理当...")
2. 典型触发场景的简短散文摘要
3. 指向代理正文中的"何时调用"部分的指针，用于详细示例场景

**格式：**
```
使用此代理当 [条件]。典型触发场景包括 [散文场景1]、[散文场景2] 和 [散文场景3]。有关具体示例，请参阅代理正文中的"何时调用"部分。
```

**最佳实践：**
- 在散文摘要中命名2-4个触发场景
- 覆盖主动（助手自我调用）和被动（用户请求）触发
- 覆盖同一意图的不同措辞
- 明确说明何时**不**使用代理
- 在正文"何时调用"部分以散文描述的要点列表形式包含详细场景

### model (必填)

代理应使用的模型。

**选项：**
- `inherit` - 使用与父级相同的模型（推荐）
- `sonnet` - Claude Sonnet（平衡）
- `opus` - Claude Opus（最强大，昂贵）
- `haiku` - Claude Haiku（快速，便宜）

**推荐：** 除非代理需要特定模型功能，否则使用 `inherit`。

### color (必填)

代理在 UI 中的视觉标识符。

**选项：** `blue`, `cyan`, `green`, `yellow`, `magenta`, `red`

**指南：**
- 在同一插件中为不同代理选择不同的颜色
- 为相似类型的代理使用一致的颜色
- 蓝色/青色：分析、审查
- 绿色：面向成功的任务
- 黄色：警告、验证
- 红色：关键、安全
- 紫色：创意、生成

### tools (可选)

限制代理访问特定工具。

**格式：** 工具名称数组

```yaml
tools: ["Read", "Write", "Grep", "Bash"]
```

**默认：** 如果省略，代理可以访问所有工具

**最佳实践：** 限制为最少需要的工具（最小权限原则）

**常见工具集：**
- 只读分析：`["Read", "Grep", "Glob"]`
- 代码生成：`["Read", "Write", "Grep"]`
- 测试：`["Read", "Bash", "Grep"]`
- 完全访问：省略字段或使用 `["*"]`

## 系统提示设计

Markdown 正文成为代理的系统提示。使用第二人称直接向代理撰写。

### 结构

**标准模板：**
```markdown
你是 [角色] 专精于 [领域]。

**你的核心职责：**
1. [主要职责]
2. [次要职责]
3. [附加职责...]

**分析流程：**
1. [第一步]
2. [第二步]
3. [第三步]
[...]

**质量标准：**
- [标准1]
- [标准2]

**输出格式：**
以以下格式提供结果：
- [包含内容]
- [结构方式]

**边缘情况：**
处理以下情况：
- [边缘情况1]：[如何处理]
- [边缘情况2]：[如何处理]
```

### 最佳实践

✅ **要：**
- 使用第二人称 ("你是...", "你会...")
- 明确职责
- 提供分步流程
- 定义输出格式
- 包含质量标准
- 处理边缘情况
- 保持在10,000个字符以内

❌ **不要：**
- 使用第一人称 ("我是...", "我会...")
- 含糊或通用
- 省略流程步骤
- 未定义输出格式
- 跳过质量指导
- 忽略错误情况

## 创建代理

### 方法1：AI辅助生成

使用此提示模式（提取自 Claude Code）：

```
根据此请求创建代理配置："[你的描述]"

要求：
1. 提取核心意图和职责
2. 设计该领域的专家角色
3. 创建包含以下内容的全面系统提示：
   - 清晰的行为边界
   - 具体方法
   - 边缘情况处理
   - 输出格式
   - "何时调用"部分列出2-4个触发场景的散文要点
4. 创建标识符（小写字母、连字符、3-50个字符）
5. 撰写描述，包含触发条件和触发场景的简短散文摘要

返回JSON，包含：
{
  "identifier": "agent-name",
  "whenToUse": "使用此代理当... 典型触发场景包括 [...]。有关具体示例，请参阅代理正文中的“何时调用”。",
  "systemPrompt": "你是..."
}
```

然后转换为代理文件格式，带前置文本。

参考 `examples/agent-creation-prompt.md` 获取完整模板。

### 方法2：手动创建

1. 选择代理标识符（3-50个字符，小写字母、连字符）
2. 撰写描述并附带示例
3. 选择模型（通常为 `inherit`）
4. 选择颜色进行视觉识别
5. 定义工具（如果限制访问）
6. 撰写上述结构的系统提示
7. 保存为 `agents/agent-name.md`

## 验证规则

### 标识符验证

```
✅ 有效：code-reviewer, test-gen, api-analyzer-v2
❌ 无效：ag (太短), -start (以连字符开头), my_agent (下划线)
```

**规则：**
- 3-50个字符
- 仅限小写字母、数字和连字符
- 必须以字母数字开头和结尾
- 不能包含下划线、空格或特殊字符

### 描述验证

**长度：** 10-5,000个字符
**必须包含：** 触发条件和示例
**最佳：** 200-1,000个字符，包含2-4个示例

### 系统提示验证

**长度：** 20-10,000个字符
**最佳：** 500-3,000个字符
**结构：** 清晰的职责、流程、输出格式

## 代理组织

### 插件代理目录

```
plugin-name/
└── agents/
    ├── analyzer.md
    ├── reviewer.md
    └── generator.md
```

`agents/` 中的所有 `.md` 文件都会自动发现。

### 命名空间

代理会自动命名空间化：
- 单个插件：`agent-name`
- 带子目录：`plugin:subdir:agent-name`

## 测试代理

### 测试触发

创建测试场景以验证代理是否正确触发：

1. 使用特定触发示例编写代理
2. 使用与测试中相似的措辞
3. 检查Claude是否加载了代理
4. 验证代理提供预期功能

### 测试系统提示

确保系统提示完整：

1. 给代理典型任务
2. 检查它是否遵循流程步骤
3. 验证输出格式是否正确
4. 测试提示中提到的边缘情况
5. 确认质量标准是否达标

## 快速参考

### 最小代理

```markdown
---
name: simple-agent
description: 当 [条件] 时使用此代理。典型触发场景包括 [触发1] 和 [触发2]。有关具体示例，请参阅代理正文中的“何时调用”部分。
model: inherit
color: blue
---

你是执行 [做X] 的代理。

## 何时调用

- **[场景A]。** [描述。]
- **[场景B]。** [描述.]

流程：
1. [步骤1]
2. [步骤2]

输出：[提供内容]
```

### 前置文本字段摘要

| 字段 | 必填 | 格式 | 示例 |
|------|------|------|------|
| name | 是 | 小写-连字符 | code-reviewer |
| description | 是 | 散文触发 | 使用当... 典型触发场景包括... |
| model | 是 | inherit/sonnet/opus/haiku | inherit |
| color | 是 | 颜色名称 | blue |
| tools | 否 | 工具名称数组 | ["Read", "Grep"] |

### 最佳实践

**要：**
- ✅ 在描述中命名2-4个触发场景（作为散文）
- ✅ 在正文"何时调用"部分以散文要点列表形式包含详细场景
- ✅ 撰写具体的触发条件
- ✅ 使用 `inherit` 作为模型，除非有特定需求
- ✅ 选择适当的工具（最小权限）
- ✅ 撰写清晰、结构的系统提示
- ✅ 彻底测试代理触发

**不要：**
- ❌ 使用没有触发场景的通用描述
- ❌ 省略触发条件
- ❌ 给所有代理相同的颜色
- ❌ 授予不必要的工具访问权限
- ❌ 撰写模糊的系统提示
- ❌ 跳过测试

## 实现工作流

为插件创建代理的步骤：

1. 定义代理目的和触发条件
2. 选择创建方法（AI辅助或手动）
3. 创建 `agents/agent-name.md` 文件
4. 撰写前置文本，包含所有必填字段
5. 按照最佳实践撰写系统提示
6. 在描述中命名2-4个触发场景（散文），并在正文"何时调用"部分详细说明
7. 使用 `scripts/validate-agent.sh` 进行验证
8. 使用真实场景测试触发
9. 在插件README中记录代理

专注于清晰的触发条件和全面的系统提示，以实现自主操作。
